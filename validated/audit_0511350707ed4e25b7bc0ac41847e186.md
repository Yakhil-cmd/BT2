Confirmed: `DeployCommands#env` inherits `TaskCommands#env`, so the label-derived arbitrary key set survives into deploy commands as well.

### Title
`GEM_PATH`-class env-key injection via unallowlisted PR label name reaches `git`/task/deploy subprocess environment - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment key with value `"true"` on top of the base environment, with no key allowlist. `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook body, and this unfiltered `@stack.env` is merged into `StackCommands#env`, `TaskCommands#env`, and `DeployCommands#env`, which are ultimately handed to `Command#unbundled_env` and `PTY.spawn`.

### Finding Description
The broken binding: the invariant "the set of keys in the environment hash reaching `PTY.spawn` is restricted to the deploy spec's `machine_env` and declared `VariableDefinition` names" does **not** hold for pull-request-label-derived keys.

Path:
1. `LabelCapturingHandler#capture_labels` stores `params.pull_request.labels.map(&:name)` directly into `PullRequest#labels` with no character/name allowlist: [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` over `super` with no allowlist: [2](#0-1) 
3. `StackCommands#env` (`super.merge(@stack.env)`) and `TaskCommands#env`/`DeployCommands#env` merge `@stack.env` early into the final command environment: [3](#0-2) [4](#0-3) [5](#0-4) 
4. `StackCommands#fetch`/`#git_clone` pass this `env` straight to the `git` `Command`: [6](#0-5) [7](#0-6) 
5. `Command#unbundled_env` merges `@env.stringify_keys` over `BASE_ENV` with **no allowlist at all**, and `Command#start` feeds this straight to `PTY.spawn`: [8](#0-7) 

Root cause: `Shipit::EnvironmentVariables#permit`, which is the actual allowlist mechanism in this codebase (`sanitize_env_vars` raising `NotPermitted` for unlisted keys), is applied **only** to user/API-supplied `env` params via `TaskDefinition#filter_envs` and `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`: [9](#0-8) [10](#0-9) [11](#0-10) . It is never invoked on the pull-request-label-derived keys produced by `ReviewStack#env`, so any label name the attacker sets — including `GEM_PATH`, `GEM_HOME`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `GIT_ASKPASS`, etc. — reaches the subprocess environment unfiltered. Existing tests already demonstrate this exact merge mechanism (with benign label names `WIP`/`BUG`): [12](#0-11)  and [13](#0-12) .

Because the attacker's own fork/branch is checked out into the task's working directory by `TaskCommands#clone`/`#checkout`, the attacker also controls the on-disk content that a poisoned `GEM_PATH` (or similar loader variable) can point at, turning the env-key injection into code execution when `bundle`/`ruby`/`require` consult that path during dependency installation or task/deploy steps.

### Impact Explanation
An attacker who can get a label applied to their own PR against a repository with review-stack provisioning enabled (`allow_all` or `allow_with_label` matching) can inject arbitrary environment variable names/values into every subsequent `git fetch`/`git clone` (`StackCommands#fetch`), task run, and deploy/rollback executed for that review stack, all running as `PTY.spawn` subprocesses on the Shipit deploy host. Combined with attacker-controlled repository content (their own fork's checked-out files), keys like `GEM_PATH`/`RUBYOPT`/`BUNDLE_GEMFILE` can be weaponized to achieve code execution on the deploy host during `bundle install`/`bundle exec` steps — Critical, RCE on the deploy host via `Command`/`PTY.spawn`. This is scoped to review stacks associated with the attacker's own PR/repository; it does not directly cross-contaminate other stacks' environments, but it is a full compromise of the process running the review-stack's task/deploy for that repository, repeatable on every webhook delivery (`opened`/`labeled`/`unlabeled`/`reopened`).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that creates a stack for the attacker's PR (`allow_all`, or `allow_with_label` with a label the attacker can apply), and the attacker's GitHub account must be able to attach a label to their own PR (per the stated attacker capability model). No Shipit secret, session, or API token is required — the whole path is driven by the GitHub webhook payload processed by `LabelCapturingHandler`/`OpenedHandler`. Cost is low: open a PR, add a label named `GEM_PATH` (or any dangerous env var name), wait for the review stack's task/deploy/fetch to run.

### Recommendation
Apply `EnvironmentVariables.with(...).permit(...)` (or an explicit static denylist/allowlist of safe label-derived keys) inside `ReviewStack#env` before merging label-derived keys into the stack environment, rejecting or dropping any label name that collides with sensitive variables (`GEM_PATH`, `GEM_HOME`, `RUBYOPT`, `BUNDLE_*`, `LD_PRELOAD`, `PATH`, `GIT_*`, etc.), and/or restrict label-derived keys to a documented, narrow prefix (e.g. `LABEL_`) that cannot collide with interpreter/tool-consumed variable names.

### Proof of Concept
minitest plan (extends the pattern already used by `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb`):
```ruby
test "#env allows a PR label to inject GEM_PATH into the command environment" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_path"]

  env = stack.env
  assert_equal "true", env["GEM_PATH"]

  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  task_env = Shipit::TaskCommands.new(task).env
  assert_equal "true", task_env["GEM_PATH"]

  command = Shipit::Command.new("git status", env: task_env, chdir: ".")
  assert_equal "true", command.unbundled_env["GEM_PATH"]
end
```
Binding under test (before/after): `stack.env["GEM_PATH"]` should be absent/rejected (expected: raises `EnvironmentVariables::NotPermitted` or is filtered) but is instead `"true"`, and `Command#unbundled_env["GEM_PATH"]` — the hash literally passed to `PTY.spawn` — equals `"true"` as well, proving the unfiltered key reaches the subprocess boundary.
