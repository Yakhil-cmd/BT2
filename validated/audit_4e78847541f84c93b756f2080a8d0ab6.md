## Title
Non-injective hash construction in arbiter contract text hash allows field-boundary collisions - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `getHashSrc()` builds the digest that authenticates the terms of an arbitrated contract (`getHash()`) by naively concatenating free-text, user-supplied fields. For contracts created before `exports.NEW_HASH_DATE`, fields are joined with **no separator at all** (`.join("")`); for contracts on/after that date, fields are joined with a fixed delimiter string `"[|#|]"` that is never checked for absence in the user-supplied field values. This is exactly the class of bug described in the reference report: a hash that is meant to unambiguously commit to a set of typed fields is instead built from a non-injective encoding, so two different sets of field values can produce an identical digest. [1](#0-0) 

### Finding Description
`getHashSrc()` is used to compute `objContract.hash`, which becomes the canonical identifier of the contract terms (`title`, `text`, `creation_date`, payer/payee addresses and names, `amount`, `asset`): [1](#0-0) 

`title` and `text` (and, in the legacy branch, `payer_name`/`payee_name`) are attacker/counterparty-controlled free-form strings with no length restriction or character filtering visible in `createAndSend`/`store`, and no escaping is applied before concatenation: [2](#0-1) [3](#0-2) 

For the legacy path (`creation_date <= NEW_HASH_DATE`, which as of today, 2026-09-14, is the path in effect since `NEW_HASH_DATE = '2026-11-01'` is still in the future), fields are joined with the empty string `""`. This means the boundary between `title` and `text` (and between `payer_name`, `arbiter_address`, `payee_name`) is not fixed in the resulting hash pre-image: `title="AB", text="CD"` produces the exact same source string as `title="A", text="BCD"`. Two structurally/semantically different contracts (different split of the same characters between `title` and `text`) hash to the same value.

Even after `NEW_HASH_DATE` when the delimiter `"[|#|]"` is introduced, the same non-injectivity persists as long as a party can include the literal substring `"[|#|]"` inside `title`/`text`/party names — nothing in the code strips or rejects it, so an attacker can still shift field boundaries while preserving the digest.

The signature on the arbitration contract response is bound to `objContract.title` via `signed_message` verification in `wallet.js`, and the contract hash is embedded directly on-chain as a data-feed key (`"CONTRACT_" + contract.hash`) used to determine the shared-address spending condition and the payout winner: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the shared-address definition and the data feed condition reference the contract only by `contract.hash` (not by the full text), and the hash itself is not an injective commitment to the underlying contract fields, an attacker who controls contract creation can present one set of terms to the counterparty for signature/display while the on-chain-referenced `hash` is compatible with a different, more favorable (to the attacker) reconstruction of `title`/`text`/party names that hashes to the same value.

### Impact Explanation
The `hash` computed by `getHashSrc`/`getHash` is the sole binding between the human-readable contract text (title/text/party names/amount/asset) and:
1. the on-chain shared-address definition condition `CONTRACT_<hash>` that gates fund release, and
2. the peer's cryptographic signature obtained via `respond()`/`validateSignedMessage` (which signs `objContract.title`, not the full contract).

Since the digest is not an injective function of its inputs, a malicious contract creator (the "offeror", an unprivileged AA/contract counterparty reachable by any user of the arbiter-contract feature) can construct two different `(title, text, ...)` tuples that collide on the same `hash`/`signed_message`, effectively enabling contract-term ambiguity attacks: the arbitrator or the counterparty could be shown/sign one narrative while a differently-parsed version of the same underlying byte string is the "real" record referenced by the on-chain condition and dispute resolution flow. This falls under AA/contract fund loss or dispute-resolution disagreement, consistent with the report's core impact class (using signature/hash ambiguity to misdirect fund release).

### Likelihood Explanation
Exploitation requires no cryptographic hash break — only the ability to choose the exact character content of `title`/`text`/party-name fields, which the contract-creation flow places entirely under the control of whichever party calls `createAndSend`. No length or delimiter-exclusion validation was found for these fields in `arbiter_contract.js`, so likelihood of a workable collision (choosing where to split characters between adjacent fields, or embedding the literal `"[|#|]"` delimiter) is high and requires no brute force at all in the legacy (no-delimiter) path — it is a deterministic, always-available string-boundary ambiguity, not a probabilistic hash collision.

### Recommendation
Replace the ad hoc string-join hashing in `getHashSrc()` with a length-prefixed or structured encoding that makes the mapping from fields to source string injective — e.g., use the existing canonical `object_hash.getJsonSourceString`/`getSourceString` (used elsewhere in the codebase precisely to avoid this class of bug, e.g. `object_hash.js` `getSignedPackageHashToSign`) on a plain object `{title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset}` instead of concatenating raw strings with a possibly-embeddable delimiter. Also retire the legacy no-delimiter (`.join("")`) branch or otherwise reject/escape any field containing the delimiter before hashing.

### Proof of Concept
1. Party A calls `createAndSend` (pre-`NEW_HASH_DATE`, i.e. current behavior as of 2026-09-14) with `title = "Pay 100"`, `text = "0USD to Bob"` and separately with `title = "Pay 10"`, `text = "00USD to Bob"`.
2. `getHashSrc` for the legacy branch joins with `""`: both contracts produce identical source string `"Pay 1000USD to Bob" + creation_date + payer_name + arbiter_address + payee_name + amount + asset` (assuming identical remaining fields), so `getHash()` yields the same `hash` for two different-looking contract texts. [7](#0-6) 
3. This same `hash` is used both as the value shown/signed by the peer (`signed_message` checked against `objContract.title` in `wallet.js`) and as the on-chain data-feed key `CONTRACT_<hash>` that the arbitrator uses to declare a winner and that gates the shared-address funds — allowing a party to exploit the ambiguity between the two colliding textual interpretations of the same on-chain-referenced contract. [8](#0-7)

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
