### Title
Creator fees can be permanently frozen if the pool creator's associated token account becomes frozen/blocked by a Token-2022 mint extension - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
`collect_creator_fee` and its permissionless counterpart both hard-code the fee destination to the pool creator's own associated token account, with no way to redirect the payout to any other account. If the mint used for `token_0`/`token_1` is an SPL Token-2022 mint with a freeze/deny-list style extension (e.g. `DefaultAccountState`, transfer-hook allow/deny-list, or a permanent-delegate/frozen-account scenario analogous to USDC/USDT blacklisting), and the creator's ATA for that mint ends up frozen or denied, the accumulated `creator_fees_token_0`/`creator_fees_token_1` can never be collected, mirroring the reported Ubiquity `collectRedemption` issue where funds could only be sent to `msg.sender`/a fixed address.

### Finding Description
`CollectCreatorFee` constrains the destination accounts to the creator's own ATA and nothing else: [1](#0-0) 

The permissionless variant is identical in effect — even though a third-party `payer` can trigger the call and pay for account creation, the recipient is still forced to be the same fixed creator ATA: [2](#0-1) [3](#0-2) 

Both instructions transfer the entire accrued `creator_fees_token_0`/`creator_fees_token_1` directly to this fixed ATA and then zero the accounting: [4](#0-3) 

The pool supports Token-2022 mints (as seen from the `token_program`/`token_program_2022` split used elsewhere, e.g. in `withdraw.rs`): [5](#0-4) 

Token-2022 mints can carry extensions (default frozen account state, transfer hooks implementing an allow/deny list) that behave like the USDC/USDT blacklist referenced in the analog report. Because the creator's ATA address is deterministically derived and fixed by the `associated_token::authority = creator` constraint, there is no parameter to specify an alternate destination account, unlike `withdraw`'s `token_0_account`/`token_1_account`, which are only constrained by mint (not by owner), giving withdrawing LPs freedom to redirect funds to any compatible token account they control.

### Impact Explanation
If the creator's ATA for a fee-bearing mint becomes frozen or denied by that mint's extension logic, the creator fee balance recorded in `pool_state.creator_fees_token_0`/`creator_fees_token_1` becomes permanently unclaimable: it continues to be excluded from `vault_amount_without_fee` (so it also cannot be reclaimed by depositors/withdrawers), and there is no owner-settable recipient to route around the frozen account. This is a permanent freezing of pool creator funds analogous to the referenced Medium-severity Ubiquity issue.

### Likelihood Explanation
The pool creator is a normal, unprivileged actor who can create pools with arbitrary Token-2022 mints supporting blocklist-style extensions. If such a mint's extension logic ever freezes/denies the creator's specific ATA (e.g., through a transfer-hook policy change or account-state extension), the creator has no recourse via any instruction in the program to relocate accrued fees.

### Recommendation
Add an optional/explicit destination account parameter (analogous to the report's suggested `to` parameter) to `CollectCreatorFee`/`CollectCreatorFeePermissionless`, allowing the pool creator to designate an alternate, unblocked token account to receive fees, rather than hard-constraining the destination to a single derived ATA.

### Proof of Concept
1. Pool creator initializes a pool where `token_0_mint` is a Token-2022 mint with a transfer-hook/deny-list or default-frozen-account extension.
2. Swaps accrue `creator_fees_token_0` in `pool_state`.
3. The creator's ATA for `token_0_mint` becomes frozen/denied by the extension's logic (equivalent to a blacklist event).
4. Creator calls `collect_creator_fee` (or any third party calls `collect_creator_fee_permissionless`); the `associated_token::authority = creator` constrained account is the only valid destination, so the transfer via `transfer_from_pool_vault_to_user` fails, and the accrued fee remains stuck in the vault indefinitely with no alternate collection path.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
```
