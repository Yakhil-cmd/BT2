### Title
Cross-organization webhook forgery via mismatched organization-authentication and repository-write bindings - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments (the documented "Using Multiple Github Applications" setup), `WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`), while every event handler resolves the actual target repository/stack using the separate `repository.full_name` field from the same attacker-controlled JSON body. Because nothing ties these two fields together, a tenant who knows their own organization's `webhook_secret` can forge a validly-signed webhook whose `owner.login` matches their own org but whose `full_name` targets a victim organization's repository, causing Shipit to process a fully attacker-controlled event against another tenant's stack.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `repository.owner.login` (falling back to `organization.login`), then `Shipit.github(organization: repository_owner)` selects the per-organization GitHub App config, including its `webhook_secret`, per the multi-app config schema: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` then just checks the HMAC of the raw body against that organization's secret: [5](#0-4) 

Once verification passes, every event handler ignores `repository.owner.login` entirely and instead resolves the target `Repository`/`Stack` from a different field of the same body, `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

Because the entire request body is attacker-controlled JSON (the handler simply does `JSON.parse(request.raw_post)`), an attacker who is a legitimate onboarded tenant of a multi-org Shipit install — and therefore knows the `webhook_secret` they themselves configured for their own GitHub App installation — can set `repository.owner.login` (or `organization.login`) to their own organization while setting `repository.full_name` to `victim-org/victim-repo`. `verify_signature` will validate successfully because it only checks the HMAC against the attacker's own known secret and the attacker's own organization name; it never checks that `owner.login` is consistent with `full_name`, nor that the resolved repository actually belongs to the authenticated organization.

This breaks the binding: `organization that authenticated == organization whose repository is written`, matching the report's "an organization that authenticated versus the repository that is written" bug class.

### Impact Explanation
With a forged, validly-signed webhook, the attacker can drive any handler logic against a victim's stack/repository using data they fully control:
- `PushHandler` can trigger `GithubSyncJob` on a victim stack with an attacker-chosen `after` SHA.
- `StatusHandler`/`CheckSuiteHandler` can inject fabricated commit statuses/check runs affecting deploy-gating decisions.
- `PullRequest` handlers (`OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, etc.) can create, archive, unarchive, or mutate review stacks and pull request records tied to a victim's repository.

This is a cross-repository write achieved purely by knowing a webhook secret for an *unrelated* organization in the same install, which is exactly the class of impact called out as Critical ("cross-repository writes").

### Likelihood Explanation
This requires the host application to use the documented multi-organization GitHub App configuration (`docs/setup.md`, "Using Multiple Github Applications") and requires the attacker to control (or be) a legitimately onboarded organization/tenant with a known `webhook_secret` for their own GitHub App — a standard, low-privilege configuration state, not requiring any Shipit session, API token, or GitHub App private key. No race condition timing is needed; the mismatch is deterministic and fully attacker-crafted per request.

### Recommendation
After signature verification, re-derive the organization from the same field the handlers use to locate the target repository (`repository.full_name`'s owner segment, or `organization.login` for org-scoped events) and require it to match `repository_owner`/the org whose secret validated the signature. Reject the webhook if the two do not match.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `attacker-org` (attacker's own tenant, secret known to attacker) and `victim-org` (unrelated tenant), per `docs/setup.md`'s multi-app schema.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully.
5. `WebhooksController#create` dispatches to `Shipit::Webhooks::Handlers::PushHandler`, which resolves the target via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` against the victim's stack — despite the request never having been authenticated by `victim-org`'s GitHub App.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
