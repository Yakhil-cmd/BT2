### Title
Unprivileged stake `Split` during active partitioned-rewards interval triggers `assert_eq!` panic in `build_updated_stake_reward`, causing a deterministic validator halt - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` assumes a stake account's `delegation.stake` cannot change between the reward-calculation snapshot and the later distribution partition block, and enforces this with a hard `assert_eq!` rather than returning a recoverable `DistributionError`. No mechanism in the stake program or the `Bank` transaction-processing path actually blocks stake mutation (e.g. `Split`) during the active `EpochRewardStatus` interval, so a stake-account owner can desynchronize the live `StakesCache` delegation from the value baked into `PartitionedStakeReward` and force the assert to fire when that partition is processed.

### Finding Description
`calculate_stake_rewards_and_commissions` snapshots each stake account's `delegation.stake` at the epoch-boundary calculation block and bakes the post-reward `new_stake.delegation.stake` into `PartitionedStakeReward.inflation.stake`, stored in `Bank::epoch_reward_status` for later, partitioned distribution [1](#0-0) . Distribution of that partition can occur many blocks later — partition indices are chunked and spread across up to 10% of the epoch's slots via `get_reward_distribution_num_blocks` [2](#0-1) .

When a partition is finally processed, `build_updated_stake_reward` reloads the account's *current* delegation from the live `stakes_cache_accounts` (not the calculation-time snapshot) and, when the `relax_post_exec_min_balance_check` feature is inactive, asserts that `current_stake.delegation.stake + stake_reward == precomputed_new_stake.delegation.stake`: [3](#0-2) 

The code comment on `store_stake_accounts_in_partition` explicitly relies on an assumption that is not enforced elsewhere: "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned" [4](#0-3) . However:
- No search of the stake program or `Bank` transaction-processing path found any check that references `EpochRewardStatus`/`RewardInterval` to gate stake-instruction execution.
- An explicit test, `test_rewards_period_system_transfer`, confirms that ordinary transactions (including transfers touching stake accounts) continue to be processed normally throughout the active rewards interval [5](#0-4) .

Since a stake account's staker/withdraw authority is fully controlled by its owner, an unprivileged attacker can submit a `Split` instruction against their own stake account (which reduces the source account's `delegation.stake`) any time after the calculation block but before that specific account's assigned partition block height is reached. This creates a mismatch between the live `stakes_cache_accounts` delegation and the value frozen into `PartitionedStakeReward`, causing the `assert_eq!` in `build_updated_stake_reward` to panic. Because this runs inside deterministic bank state-transition code executed by every validator replaying/producing that block, the panic is not an isolated node crash but a network-wide halt at that block.

### Impact Explanation
This is a liveness/DoS bug matching the Agave bug-bounty "epoch-boundary halt" category. The `assert_eq!` is a hard panic reachable from a fully unprivileged, ordinary stake-instruction flow (an attacker owning and controlling their own stake account), not requiring any leaked keys, validator control, or crafted snapshots. All validators processing the affected partition block would panic identically, producing a chain-wide halt rather than a benign per-node crash.

### Likelihood Explanation
Preconditions are realistic and fully attacker-controlled: the attacker only needs (1) an owned, funded stake account with a nonzero calculated reward for the current epoch, and (2) the `relax_post_exec_min_balance_check` feature to be inactive (this determines whether the `assert_eq!` branch, vs. the rent-adjustment branch, is taken). The distribution window for a given partition can span from a few blocks up to ~10% of an epoch's slots, giving ample opportunity to submit a `Split` transaction naming the target stake account before its partition is processed. This is deterministically reproducible in any test harness that advances banks through the reward-distribution interval.

### Recommendation
- Prevent stake-delegation mutation (Split, Withdraw, Merge, Deactivate/Delegate) on stake accounts while `EpochRewardStatus` is active for that account's assigned rewarded epoch, similar to how the vote program guards state during other bank-invariant windows, or
- Replace the `assert_eq!` in `build_updated_stake_reward` with a non-panicking `DistributionError` variant (e.g. `DelegationMismatch`) that causes the reward to be burned/skipped rather than aborting bank processing, consistent with how `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` are already handled as recoverable errors in the same function.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
