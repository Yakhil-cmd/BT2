This confirms the analog: in a multi-organization Shipit deployment (`secrets.github` keyed by multiple org names, each with its own `webhook_secret`, per `Shipit.github_app_config` at `lib/shipit.rb:196-200`), the field used to authenticate a webhook is not the field used to decide what gets written.

### Title
Webhook signature is validated against the payload's `repository.owner`/`organization` while handlers act on the unrelated `repository.full_name` (and `StatusHandler` on a global `sha`), allowing cross-organization forgery of CI status/deploy state - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the signing secret using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and only checks that the raw body's HMAC matches that org's `webhook_secret`. It never verifies that this organization is actually related to the `repository.full_name`/`sha` the handlers then act on. Handlers such as `PushHandler`, `CheckSuiteHandler`, pull-request handlers, and especially `StatusHandler` use a completely different field (`repository.full_name`, or nothing at all in `StatusHandler`) to decide which `Stack`/`Commit` to mutate.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-38` computes: [1](#0-0) 
and `repository_owner` is read straight from attacker-controlled JSON: [2](#0-1) 

`Shipit.github(organization:)` resolves a per-organization config/secret from `secrets.github`: [3](#0-2) 

So the signature only proves "this request was signed by organization X's webhook secret" - it does not prove anything about which repository/commit the payload subsequently references. Once verified, `create` hands the *entire* parsed JSON to the handlers unmodified: [4](#0-3) 

Handlers derive the target purely from body fields that were never covered by the org-binding check: [5](#0-4) [6](#0-5) 

`StatusHandler` is worse: it does not consult `repository` at all, it just matches any `Commit` by raw `sha` across the entire installation: [7](#0-6) 

This breaks the equality: `organization that authenticated the request == repository/commit that is written`. If Shipit hosts stacks for multiple GitHub organizations (a documented, supported configuration - each org has its own `webhook_secret` under `secrets.github`), an attacker who legitimately controls one onboarded org (and therefore knows/derives its `webhook_secret` via their own installed GitHub App) can:
1. Sign an arbitrary JSON body with their own org's secret.
2. Set `X-Github-Event: status`, with `sha` equal to a real commit SHA of a *different* org's tracked stack (visible publicly on GitHub) and `state: success`.
3. `verify_signature` succeeds because `repository_owner` in the body points to the attacker's own org, whose secret they used.
4. `StatusHandler#process` matches the victim's `Commit` purely by `sha` and calls `create_status_from_github!`, creating a `Status` for the victim stack.

`Status#after_create` callbacks (`enable_ci_on_stack`, `schedule_continuous_delivery`) can move a victim commit into a deployable/CI-green state and trigger continuous delivery: [8](#0-7) 

The same authentication/action mismatch also lets the attacker forge `push` (triggering `GithubSyncJob`/`sync_github` with an attacker-chosen `expected_head_sha`) and `check_suite` events against any `Repository.from_github_repo_name` match, since `PushHandler`/`CheckSuiteHandler` only key off `repository.full_name`, not the authenticated org: [9](#0-8) [10](#0-9) 

### Impact Explanation
An entity that is authenticated only as "organization A" can write CI/deploy-affecting state (fabricated commit statuses enabling continuous delivery, forced re-sync of commits with an attacker-chosen expected SHA, forced check-run refresh) into a completely different organization's repository/stack that it has no legitimate relationship with. Faking a passing CI status can push a victim stack into an auto-deployable state, which maps to the in-scope "unauthorized deploy" Critical impact category, since `Status` creation drives `schedule_continuous_delivery`.

### Likelihood Explanation
Exploitation only requires the attacker to control one organization already onboarded onto the shared Shipit instance (a normal, unprivileged tenant of a multi-org Shipit deployment) and to know a target commit SHA of another tenant's repository (public on GitHub). No Shipit session, API token, or GitHub App private key is needed - only the attacker's own legitimately-issued `webhook_secret`, which they can freely use to sign arbitrary bodies referencing other tenants' data.

### Recommendation
Bind the verified organization to the object actually mutated: after computing the signing organization, require that `repository.full_name`'s owner (and, for `StatusHandler`, the owning `Repository`/`Stack` of the matched `Commit`) matches the verified `repository_owner`/`organization`, rejecting (422) any event where they diverge. `StatusHandler` in particular should scope its `Commit` lookup by the repository whose organization was cryptographically verified, not by a bare `sha` match across all stacks.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` and `attacker-org`, each with distinct `webhook_secret`s (a standard supported multi-tenant setup per `lib/shipit.rb#github_app_config`).
2. As the operator of `attacker-org` (a normal, unprivileged tenant), craft a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<real commit sha belonging to victim-org's tracked stack>",
  "state": "success",
  "context": "ci/forced"
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, body)`.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` passes (it only checks `attacker-org`'s secret against the raw body). `StatusHandler#process` finds the victim's `Commit` by `sha` (no organization scoping) and creates a `success` `Status` for it, triggering `enable_ci_on_stack`/`schedule_continuous_delivery` on the victim's stack - despite the request never having been authenticated by or for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

  end
