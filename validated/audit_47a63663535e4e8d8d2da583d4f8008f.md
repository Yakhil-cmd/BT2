### Title
Webhook signature is bound to `repository.owner.login`, but event processing is not scoped to that owner, allowing cross-repository status forgery and unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the HMAC signature against based solely on `repository.owner.login` (or `organization.login`) extracted from the JSON body. [2](#0-1) [3](#0-2)  Once the signature is confirmed valid for *that* organization, the payload is dispatched to handlers that never re-check that the acted-upon resource (commit, stack, repository) actually belongs to the verified organization. `StatusHandler` in particular looks up commits globally by `sha` across all repositories/stacks in the Shipit instance and writes a status directly from attacker-supplied fields. [4](#0-3) 

### Finding Description
Shipit supports hosting multiple GitHub organizations behind one instance, each with its own App/webhook secret configured under a per-org key in `secrets.github`. [5](#0-4)  The binding the signature check is supposed to enforce is: *"the organization named in the payload = the organization whose secret validated the payload."* But the payload fields consumed by handlers (`sha`, `state`, `target_url`, `description`, `context`) are entirely independent of `repository.owner.login`/`organization.login`, and are never cross-checked against it.

Concretely:
1. `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and picks the matching `GitHubApp` to verify the signature. [6](#0-5) 
2. Once verified, `WebhooksController#create` blindly dispatches the entire parsed body to `Shipit::Webhooks.for_event(event)` handlers with no re-derivation of trust boundaries. [7](#0-6) 
3. `StatusHandler#process` finds commits by `sha` alone (`Commit.where(sha: params.sha)`), with no filter on repository/stack/owner, and calls `commit.create_status_from_github!(params)` for every match — even commits belonging to a completely different organization's stack. [1](#0-0) 

An attacker who controls (or has legitimately configured) their own GitHub App/organization entry in Shipit's multi-tenant config — i.e., they know their own org's `webhook_secret` — can sign a `status` webhook whose `repository.owner.login` is their own org (so the signature check passes) but whose `sha` value is the SHA of a commit belonging to a *victim* organization's stack. Because `StatusHandler` never checks that the commit's stack belongs to the verified organization, the forged status (e.g., `state: success`, arbitrary `context`/`description`) is written onto the victim's commit.

This breaks the equality that should hold: *organization authenticated by the webhook signature == organization whose repository/commit data is mutated by the handler*. Before the attack, only GitHub, acting for org X, can post a status for org X's commits. After the attack, an attacker who is a legitimate GitHub App owner for org A (their own tenant on the shared Shipit instance) can post a status for org B's commit, because the handler enforces no such equality.

### Impact Explanation
Commit statuses/CI checks are used by Shipit to gate deployability (`Commit#deployable?`, required CI checks, `require_ci` deploy flag) and continuous deployment. By injecting a forged `success` status onto a victim's commit for a CI context Shipit trusts (e.g., `ci/travis`), an attacker can make an otherwise-failing or unreviewed commit appear deployable, enabling an unauthorized deploy of that commit through the normal deploy API/continuous-deployment path once a legitimate Shipit user (or CD) triggers it. This crosses an organization boundary using only credentials for an unrelated tenant, satisfying the "unauthorized deploy" / "cross-repository writes" high-impact bar.

### Likelihood Explanation
Requires the attacker to control/own a GitHub App organization entry that is legitimately configured in this same multi-tenant Shipit instance (a scenario explicitly documented and supported: "Using Multiple Github Applications"). [8](#0-7)  Given that, no further privilege is needed — a single crafted `status` webhook, correctly signed with the attacker's own known secret, is sufficient. The commit `sha` values for other tenants' stacks are often knowable/guessable (they are real git commit hashes visible in the target repo's public/private history, PRs, etc.), so the main precondition is being a legitimate but unprivileged tenant in the multi-org deployment.

### Recommendation
In `Handler`/`StatusHandler` (and any other handler that looks up commits/stacks by attacker-supplied identifiers), scope the lookup by the repository derived from the verified `repository_owner`/organization, not just by `sha`. Concretely, `Commit.where(sha: params.sha)` should be scoped through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and further cross-checked that its `owner` matches the organization that validated the webhook signature in `WebhooksController`. More generally, `WebhooksController` should pass the verified organization identity down to handlers so every handler can assert that the resource it mutates belongs to that organization, rather than trusting `repository.full_name` implicitly.

### Proof of Concept
1. Shipit is configured with two tenants, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `app_id`/`webhook_secret` under `secrets.github.OrgA` / `secrets.github.OrgB`, per the documented multi-org setup. [9](#0-8) 
2. Attacker, as the legitimate owner of the `OrgA` GitHub App, knows `OrgA`'s `webhook_secret`.
3. Attacker learns (or guesses) the commit SHA of a commit in `OrgB`'s stack, e.g. from a public PR or exposed CI logs.
4. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
Body: {
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"},
  "sha": "<OrgB victim commit sha>",
  "state": "success",
  "context": "ci/travis",
  "target_url": "https://ci.example.com/fake"
}
```
5. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully (it was in fact signed with OrgA's secret). [2](#0-1) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit (since lookup is global by sha, not scoped to `OrgA`/`OrgA/some-repo`), and calls `create_status_from_github!`, writing a forged `success` status onto OrgB's commit. [1](#0-0) 
7. If OrgB's stack relies on that CI context for `deployable?`/CD gating, the forged status can enable an unauthorized deploy of the targeted commit.

Note: this analysis is based on the indexed source; I was unable to fully trace `Commit#create_status_from_github!` and the exact deployability-gating logic (`deployment_checks_passed?`) in this pass. If further confirmation of the exact deploy-gating mechanics is needed, a full Devin session with repository access would be required to inspect those files in full.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
