### Title

Overflow in RAY-scaled debt accrual permanently freezes a high-utilization market - (File: `contracts/pool/src/interest.rs`)

### Summary

A market with sufficiently large scaled debt can cross the `i128` RAY-value domain before reaching `MAX_BORROW_INDEX_RAY`, after which every operation that syncs the market reverts with `MathOverflow`. [1](#0-0) [2](#0-1) 

### Finding Description

`Controller::update_indexes` is permissionless and forwards caller-supplied `HubAssetKey` values to the pool’s index-accrual path. [3](#0-2) [4](#0-3) 

Every pool operation loads the market through `synced_market`, which unconditionally calls `interest::global_sync` before performing the requested action. [5](#0-4) 

`global_sync` repeatedly calls `accrue_chunk`, which evaluates `accrue_step` against the stored scaled `borrowed`, scaled `supplied`, borrow index, and supply index. [6](#0-5) [7](#0-6) 

The market’s utilization calculation converts scaled debt and scaled supply back to RAY-denominated original values via `scaled_to_original`, requiring `scaled_shares * index` to fit in `i128`. [8](#0-7) 

At the protocol’s admitted numeric boundary, one billion 18-decimal tokens produce approximately `1e36` RAY units of scaled debt, so a borrow index above roughly 170 RAY makes that product exceed `i128::MAX`. [1](#0-0) [9](#0-8) 

The repository’s regression test confirms that this value overflow occurs before `MAX_BORROW_INDEX_RAY`, so the intended index ceiling does not prevent the panic. [10](#0-9) 

Once the first accrual crosses the domain boundary, `repay` fails before burning debt because it loads a synced market first. [11](#0-10) 

`withdraw` fails for the same reason before resolving or burning the supplier’s position. [12](#0-11) 

Even `recapitalize` cannot recover the market because it also loads and syncs the overflowing market before calculating the backing shortfall. [13](#0-12) 

### Impact Explanation

This permanently freezes all funds associated with the affected hub asset: suppliers cannot withdraw, borrowers cannot repay, liquidations cannot reduce the position, and recapitalization cannot repair the book. [5](#0-4) [14](#0-13) 

Unlike an ordinary failed transaction, the first overflowing `update_indexes` leaves `last_timestamp` behind, so every subsequent transaction retries the same overflowing accrual and cannot progress the market. [15](#0-14) [16](#0-15) 

The affected physical pool balance therefore remains inaccessible even though the accounting state remains readable, satisfying permanent freezing of user funds and inability of that market to operate. [17](#0-16) [18](#0-17) 

### Likelihood Explanation

No privileged attacker action is required after market listing: an unprivileged borrower can open a large permitted borrow, leave the market to compound, and later call `update_indexes` with the affected `HubAssetKey`. [19](#0-18) [3](#0-2) 

The repository’s proof uses a one-billion-token 18-decimal market at 98% utilization, which is inside the protocol’s raw amount and utilization domains when caps and the interest-rate model permit that size. [20](#0-19) 

The likelihood is conditional rather than universal because smaller supply caps, lower maximum utilization, timely liquidation, or earlier repayment can prevent the scaled-debt/index product from reaching the overflow boundary. [21](#0-20) [22](#0-21) 

### Recommendation

Make accrual overflow-safe before materializing `scaled_shares * index`, rather than allowing `scaled_to_original` to panic after the debt crosses the RAY-value domain. [8](#0-7) [7](#0-6) 

Before applying each accrual chunk, compute the maximum safe index as `i128::MAX / scaled_borrowed` and clamp the next borrow index at the lesser of that headroom and `MAX_BORROW_INDEX_RAY`, then mark the market accrued instead of reverting. [15](#0-14) [10](#0-9) 

Additionally, reject new supply or debt whose RAY-scaled total cannot remain convertible through `MAX_BORROW_INDEX_RAY`, so admitted caps account for future index growth rather than only current `i128` validity. [23](#0-22) [24](#0-23) 

### Proof of Concept

The in-repository test establishes the sequence using an 18-decimal market, maximal admitted caps, a one-billion-token supply, and a 98% borrow:

```rust
let principal = 1_000_000_000i128 * 10i128.pow(18);
let debt = principal / 100 * 98;

controller.supply(
    bob,
    0,
    spoke_id,
    vec![(big18_key, principal)],
);

controller.supply(
    alice,
    alice_account,
    spoke_id,
    vec![(collateral_key, 1_000_000_000i128 * 10_000_000 * 3)],
);

controller.borrow(
    alice,
    alice_account,
    vec![(big18_key, debt)],
    None,
);
``` [20](#0-19) 

After ledger time advances enough for the next accrual to push `scaled_borrowed * borrow_index` beyond `i128::MAX`, a permissionless call to `update_indexes(caller, vec![big18_key])` returns `MathOverflow` while the stored index remains below `MAX_BORROW_INDEX_RAY`. [25](#0-24) 

Subsequent `withdraw(bob, supplier_account, vec![(big18_key, 1)], None)` and `repay(payer, borrower_account, vec![(big18_key, small_amount)])` both revert with the same `MathOverflow` before their state changes execute. [14](#0-13) [26](#0-25)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

pub(crate) fn mint_debt(env: &Env, cache: &mut Cache, position: &mut Ray, amount: i128) {
    require_positive_amount(env, amount);
    cache.require_reserves(amount);
    guards::require_liquidation_buffer(env, cache, amount);

    let minted = cache.calculate_scaled_borrow(amount);

    assert_with_error!(
        env,
        minted.raw() > 0,
        GenericError::BorrowRoundsToZeroShares
    );

    *position = position.checked_add(env, minted);
    cache.mint_debt(minted);
    guards::require_utilization_below_max(env, cache);
