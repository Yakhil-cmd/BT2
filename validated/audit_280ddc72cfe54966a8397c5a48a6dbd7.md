Based on my investigation, I found a legitimate structural analog to the Astaria M-15 bug within the Polkadot SDK codebase.

### Title
ERC20 Asset Transactor initiates zero-value ERC20 `transfer` calls that revert for non-compliant tokens, causing XCM asset transfer failures - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` unconditionally construct and dispatch a Solidity `IERC20::transfer` call via `pallet_revive::Pallet::<T>::bare_call` using the asset amount taken from XCM holding/matcher output, without ever checking whether that amount is zero. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same bug class as Astaria M-15: some ERC20 tokens (per the well-known "weird-erc20" catalog, e.g. LEND) revert when `transfer`/`transferFrom` is called with `value == 0`. `ERC20Transactor` is a `TransactAsset` implementation that bridges XCM asset transfers to Solidity ERC20 contracts deployed via `pallet-revive`. Both its withdraw and deposit paths build an ABI-encoded `IERC20::transferCall` with `value: EU256::from(amount)` and execute it via `bare_call` without any `if amount.is_zero() { return Ok(...) }` short-circuit: [3](#0-2) [4](#0-3) 

The rest of the codebase treats zero-value transfers as a special no-op case precisely to avoid such issues:
- `pallet-revive`'s own native-currency transfer helper: "This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers." [5](#0-4) 
- `pallet-contracts` transfer helper skips the call entirely when `value.is_zero()`. [6](#0-5) 
- `pallet-balances`/`Currency::transfer` is explicitly a no-op for zero value. [7](#0-6) 
- `pallet-assets`' `transfer_and_die`/`decrease_balance` early-exit for zero amount. [8](#0-7) 
- `pallet-vesting`'s `vested_transfer` early-exits for zero amount. [9](#0-8) 

`ERC20Transactor` is the only exception among these transfer primitives, despite being the one code path that talks directly to arbitrary, potentially non-standard, third-party-deployed ERC20 contracts (the same threat model as the original Astaria finding) rather than to trusted, in-runtime FRAME pallets.

Regarding attacker-controlled reachability: while `Fungibility`'s SCALE `Decode` implementation rejects a literal `Fungible(0)` in an incoming XCM message [10](#0-9) , zero-amount fungible credits can still be produced internally during XCM execution (e.g. by fee-swap/refund arithmetic) and inserted into `AssetsInHolding` without going through `Decode`. This exact bug class was already found and fixed once in this codebase for `SwapFirstAssetTrader::buy_weight`, where an exact-fee trade could yield a zero-amount credit that got wrapped into `AssetsInHolding` and propagated through `fees → refund_surplus → holding → drop_assets`: [11](#0-10)  That fix only patched the `AssetTrapped`-emission symptom for `cumulus-primitives-utility`; it did not add any general zero-amount guard to `ERC20Transactor`, so any equivalent zero-amount credit that reaches `ERC20Transactor::deposit_asset_with_surplus`/`withdraw_asset_with_surplus` (e.g. via `RefundSurplus`, exact-fee `PayFees`, or `AssetExchange` outputs when an ERC20-backed asset is configured as part of the `AssetTransactor`/fee-asset stack) will still trigger an ERC20 `transfer(_, 0)` call.

The analogous ERC20 wrapper in `pallet-revive`'s `impl_fungibles.rs` (`burn_from`/`mint_into`, used to implement `fungibles::Mutate` for ERC20 tokens) has the identical omission: [12](#0-11) 

### Impact Explanation
If the configured `AssetTransactor`/fee stack on a chain includes an ERC20 token (via `ERC20Transactor` or the `impl_fungibles.rs` `Mutate` implementation) whose contract reverts on zero-value `transfer` (a documented, real-world ERC20 pattern, not a hypothetical), then any XCM instruction that ends up moving/depositing/withdrawing a zero amount of that asset — including internally-derived zero amounts from fee/swap arithmetic — will cause `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`. Depending on where this occurs in the XCM program, this can abort an otherwise-legitimate multi-step XCM (fee refund, reserve transfer, exchange), trap the assets already withdrawn/held for that message (subject to `AssetTrapped`/claim mechanics), or otherwise deny the user their expected outcome — a loss-of-funds/availability impact analogous to, though narrower in blast radius than, the original Astaria M-15 (which affected every `claim()` at 100% withdraw ratio).

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the chain operator must configure an ERC20-backed asset (via `pallet-revive` contracts) into the `AssetTransactor`/`Trader`/`AssetExchanger` stack — this is a legitimate, intended use case of the newly-added `erc20_transactor.rs` module, not a misconfiguration; and (2) an execution path must produce a genuinely zero fungible amount for that asset at the `TransactAsset` boundary — demonstrated as a real, previously-triggered scenario in this very codebase (`pr_11389`, `SwapFirstAssetTrader::buy_weight` exact-fee case), and plausible in `RefundSurplus`/fee-refund flows generally. No privileged role or malicious actor is required — a normal user constructing an XCM with exact fees, or exact-amount swaps, can trigger the zero-surplus/zero-credit condition; the only "attacker-controlled" element is the choice of a non-standard ERC20 token, which is inherent to permissionless ERC20 deployment on `pallet-revive`.

### Recommendation
Add an early-return no-op guard for zero amounts in `ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` (and the analogous `burn_from`/`mint_into` in `substrate/frame/revive/src/impl_fungibles.rs`), mirroring the pattern already used in `pallet-revive`'s native transfer helper, `pallet-contracts`, `pallet-balances`, and `pallet-assets`: if `amount == 0`, return `Ok(...)` (with an appropriately empty `AssetsInHolding`/surplus) without invoking the ERC20 contract's `transfer` function.

### Proof of Concept
No executable PoC was run. This report is a static code-pattern analysis: I confirmed via direct code reading that `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` (`erc20_transactor.rs` lines 150–216, 225–306) unconditionally call `IERC20::transferCall` regardless of amount, contrasted against five other transfer primitives in the same codebase (`pallet-revive` `exec.rs`, `pallet-contracts` `exec.rs`, `pallet-balances` `impl_currency.rs`, `pallet-assets` `functions.rs`, `pallet-vesting` `lib.rs`) that all explicitly guard against zero-value transfers. I additionally located a merged PR (`pr_11389.prdoc`) confirming that zero-amount fungible credits can and do arise internally during XCM fee/swap processing in this codebase, establishing that the zero-amount precondition is reachable through normal (non-privileged) XCM usage rather than purely theoretical. I did not build a full local Rust/XCM integration test exercising the exact `ERC20Transactor` + reverting-on-zero contract combination end-to-end; a background engineering session would be needed to write and run such a reproduction against `substrate/frame/revive/fixtures/contracts` fixtures to confirm the exact failure mode and blast radius before this can be considered fully proven.

	/// Transfer some funds from `from` to `to`.
	///
	/// This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers.
	///
	/// If the destination account does not exist, it is pulled into existence by transferring the
	/// ED from `origin` to the new account. The total amount transferred to `to` will be ED +
	/// `value`. This makes the ED fully transparent for contracts.
	/// The ED transfer is executed atomically with the actual transfer, avoiding the possibility of
	/// the ED transfer succeeding but the actual transfer failing. In other words, if the `to` does
	/// not exist, the transfer does fail and nothing will be sent to `to` if either `origin` can
	/// not provide the ED or transferring `value` from `from` to `to` fails.
	/// Note: This will also fail if `origin` is root.
	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}
