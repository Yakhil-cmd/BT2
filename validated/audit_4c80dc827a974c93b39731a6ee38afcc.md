### Title
Webhook Signature Verified for Attacker's Own Organization but Handlers Act on a Repository Field Never Covered by That Signature - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to verify an inbound webhook by reading `repository.owner.login` (or `organization.login`) from the **unauthenticated** JSON body, then verifies the raw body against that org's `webhook_secret`. Once the signature check passes, the dispatched handlers (e.g. `PushHandler`, `StatusHandler`) identify which `Repository`/`Stack` records to mutate using a **different** field of the same unauthenticated body: `repository.full_name`. Nothing ties `repository.owner.login` to `repository.full_name`, so an attacker who legitimately controls the webhook secret for their *own* onboarded organization can forge a payload where the signature-selection field points at their own org (so the signature check passes with a secret they know) while the `full_name` field used for actual writes points at a completely different, victim organization's repository.

### Finding Description
The relevant binding is: `organization used to select verification secret == organization whose repository is written`. This binding is broken.

- Signature verification key selection uses only `repository.owner.login` / `organization.login`: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization: repository_owner)` looks up the `GithubApp`/`webhook_secret` configured for that org name, and `verify_webhook_signature` just checks the raw body HMAC against that org's secret: [3](#0-2) 

- Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, passing the entire raw JSON body (including the untouched `repository.full_name`) to handlers: [4](#0-3) 

- All handlers resolve the target repository/stacks purely from `payload.dig('repository', 'full_name')`, a field that was never checked against, or tied to, the value used to pick the verification secret: [5](#0-4) 

- `PushHandler` uses that repository resolution to trigger `stack.sync_github(expected_head_sha: ...)` on any non-archived stack matching the branch — a real write/sync action against the victim's stack: [6](#0-5) 

- `StatusHandler` writes commit statuses for any commit matching a supplied `sha`, independent of repository ownership checks beyond what `Handler#stacks` filters, and CI/deploy gating in Shipit relies on these statuses: [7](#0-6) 

Because a multi-tenant Shipit deployment configures a separate `webhook_secret`/GitHub App per organization (`config/secrets.development.shopify.yml` shows exactly this per-org shape): [8](#0-7) 

an attacker who is an admin of their own onboarded org (a legitimate, unprivileged-relative-to-the-victim tenant) knows their own org's `webhook_secret`. They can craft an arbitrary JSON payload, sign it with their own secret, but set `repository.full_name` to `victim-org/victim-repo` while leaving `repository.owner.login`/`organization.login` as their own org (whatever value resolves to their own secret). `verify_signature` succeeds because the signature genuinely matches the attacker's own secret for the attacker's own claimed org — it never confirms that the org used for verification is the org that owns the repository being acted upon in `full_name`.

### Impact Explanation
This crosses a repository/organization trust boundary without any actual GitHub-issued signature covering the acted-upon repository: an attacker holding a webhook secret for one tenant org can trigger `GithubSyncJob`-style resyncs, forge commit statuses (`commit.create_status_from_github!`), or drive other webhook-triggered side effects against another org's stack/repository that they have no legitimate relationship to. Forged commit statuses can influence CI gating decisions used by Shipit to permit deploys (`ci.require`), and forced `sync_github` calls can alter deployable commit state — this is a cross-organization write achieved by a party who is only a legitimate deputy for a different, unrelated tenant. This matches the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Requires the attacker to control (as an org admin) any org that is legitimately onboarded onto the same multi-tenant Shipit instance (this is a normal, low-privilege condition relative to the victim organization — it does not require compromising the victim's GitHub App, private key, or webhook secret, nor a Shipit `ApiClient` token or session). It only requires the ability to send an arbitrary raw HTTP POST (not necessarily a real GitHub delivery) to the public webhook endpoint. No collusion with, or privileges within, the victim organization/repository is needed.

### Recommendation
After signature verification, re-derive the organization from the same field used for the signature lookup and cross-check it strictly against the organization portion of `repository.full_name` (and any other org identifiers used deeper in handlers) before dispatching to handlers; reject the request if they diverge. Alternatively, bind handler-level repository resolution to the already-verified `repository_owner` value rather than independently trusting `repository.full_name`.

### Proof of Concept
1. Attacker legitimately onboards `attacker-org` onto the shared Shipit instance, obtaining its `webhook_secret`.
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` as `attacker-org`, fetches `attacker-org`'s `webhook_secret` via `Shipit.github(organization: 'attacker-org')`, and the signature matches — verification passes.
5. `PushHandler.call(params)` runs; `Handler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on the victim's stacks, despite the request never being authenticated against `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
