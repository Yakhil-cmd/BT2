The BOSH CLI issue is a workstation-side shell injection triggered when a compromised director feeds unsanitized data (e.g., hostnames) into a locally-invoked `ssh`/`scp` shell command. This bug class requires: (1) an operator-facing CLI that shells out using string interpolation, and (2) a remote/untrusted party controlling the interpolated value. There is no such analog reachable through a real Polkadot SDK entry point (signed extrinsic, contract call, or XCM message).

All process-spawning code found in the repo passes arguments as discrete `Vec<&str>`/`OsStr` values to `Command::new`/`tokio::process::Command`, never through a shell interpreter, and the spawned program paths are locally configured (not attacker-supplied): [1](#0-0) [2](#0-1) 

The only "attacker" in the BOSH scenario is a compromised Director acting on a CLI operator's local workstation — this is explicitly excluded by the prompt's constraint that "no malicious peer/node/validator/collator/relayer, controlled parachain, forged inherent or dishonest external chain is ever allowed," and there is no equivalent operator-workstation CLI component in the runtime/node code that consumes untrusted director-like input for shell execution.
