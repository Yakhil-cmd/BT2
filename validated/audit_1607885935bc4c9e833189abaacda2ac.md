### Title
Legacy `pattern` field inference maps non-bash/file events to `content`, silently disabling `event: all` Bash-blocking rules - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` infers the match field for legacy (simple-`pattern`) rules from the `event` value, but only special-cases `bash` and `file`; any other value (including the documented `all` event) is mapped to `field='content'`. Since `RuleEngine._extract_field` only reads `'command'` for the `Bash` tool and never checks `'content'` on Bash input, a rule authored with `event: all` and a dangerous-command pattern (e.g. `rm\s+-rf`) can never match against real `PreToolUse` Bash input, making the intended block a permanent no-op.

### Finding Description
In `plugins/hookify/core/config_loader.py` (`Rule.from_dict`), the legacy simple-pattern branch does: [1](#0-0) 
`event == 'bash'` → `field = 'command'`, `event == 'file'` → `field = 'new_text'`, and everything else (including the documented `all` event, per `plugins/hookify/README.md` and `SKILL.md` which list `all: Triggers on all events`) falls into `else: field = 'content'`.

When this rule is evaluated against a real Bash `PreToolUse` payload, `RuleEngine._rule_matches` → `_check_condition` → `_extract_field` is called with `field='content'`: [2](#0-1) 
`'content'` is not a key in Bash's `tool_input` (which only has `'command'`), so the direct-field check fails; the Stop/prompt special cases (`reason`, `transcript`, `user_prompt`) don't apply; and the `tool_name == 'Bash'` branch only returns a value when `field == 'command'`, not `'content'`. `_extract_field` therefore returns `None`, and `_check_condition` immediately returns `False` because `field_value is None`. The rule condition can never be satisfied for Bash input, so `_rule_matches` always returns `False` and the rule never fires, regardless of the pattern content.

This is reachable purely through ordinary rule authoring: a `.claude/hookify.*.local.md` file with `event: all`, `action: block`, and `pattern: rm\s+-rf` (a natural way to author a "block this dangerous command everywhere" rule, since `all` is a documented, first-class event value) is loaded by `load_rule_file` → `Rule.from_dict` and evaluated on every `PreToolUse` Bash call via `pretooluse.py`, but never actually blocks anything.

### Impact Explanation
This breaks the plugin's core safety/enforcement guarantee: a rule that is written and displayed as `action: block` for dangerous Bash commands is silently inert. A user (or a shared/template repository author) can ship or copy such a rule believing destructive commands (`rm -rf`, `chmod 777`, `dd if=...`, etc.) are blocked, while in reality they execute unimpeded. This is a silent safety-control bypass in the hook enforcement layer itself — the exact mechanism Claude Code relies on to gate `PreToolUse` actions — leading to a false sense of protection and unblocked execution of attacker- or prompt-injection-triggered destructive commands.

### Likelihood Explanation
Highly likely to be encountered in practice: `all` is a documented, valid event value (`README.md`, `SKILL.md`), and the "legacy simple pattern" format (`pattern:` field without `conditions:`) is presented as the primary, minimum-viable rule format in the docs and the `/hookify:configure` skill guidance. Any user/template author who picks `event: all` with a simple `pattern` for a Bash-blocking rule (rather than the more verbose `conditions:` format) triggers this bug deterministically and repeatably — no special timing or race condition is needed.

### Recommendation
In `Rule.from_dict`, do not collapse all non-`bash`/`file` events to `field='content'`. For `event == 'all'` (or unspecified), either generate multiple field-specific conditions (e.g., one for `command` and one for `new_text`/`content`) combined with OR semantics, or expand `_extract_field`/`_check_condition` to try all relevant fields for the actual `tool_name` at evaluation time rather than baking in a single field at parse time. At minimum, add explicit handling for `event == 'all'` to map to `command` when the actual tool is `Bash`.

### Proof of Concept
Unit test in a new `plugins/hookify/tests/test_all_event_bash_block.py`:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_all_event_bash_block_should_trigger_but_does_not():
    frontmatter = {
        "name": "block-rm-rf",
        "enabled": True,
        "event": "all",
        "action": "block",
        "pattern": r"rm\s+-rf",
    }
    rule = Rule.from_dict(frontmatter, "Dangerous rm command blocked!")
    assert rule.conditions[0].field == "content"  # bug: should be usable against Bash 'command'

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /important/data"},
    }
    result = engine.evaluate_rules([rule], input_data)
    # Expected (desired) behavior: blocking decision returned
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
    # Actual behavior: result == {} — the destructive command is NOT blocked
```
Running this against the current code shows `result == {}`, proving the `rm -rf` command is not blocked despite the rule declaring `action: block` for `event: all`.
