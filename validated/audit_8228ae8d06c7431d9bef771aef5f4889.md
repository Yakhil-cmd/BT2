### Title
Webhook status handler writes commit statuses without verifying the authenticated organization matches the target repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for signature verification based on a field taken from the *unverified* JSON body (`repository.owner.login`), then dispatches the same body to event handlers. `StatusHandler`, unlike `PushHandler` and `CheckSuiteHandler`, never re-checks that the repository referenced in the payload belongs to the organization that produced a valid signature; it looks up commits globally by `sha` alone and writes a `Status` record for every match, regardless of which stack/repository/organization owns that commit.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against using `repository_owner`, itself derived from the untrusted payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub App configurations keyed by organization, each with its own `webhook_secret`: [3](#0-2) 

Most handlers scope their side effects to the repository named in the payload via the shared `Handler#stacks`/`repository_name` helper: [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler`, however, never calls `stacks`/`repository_name` at all — it looks up commits **globally** by `sha` and writes a status onto every match: [7](#0-6) 

This breaks the binding "organization that authenticated == repository that is written": the organization whose `webhook_secret` validated the HMAC is derived from `repository.owner.login`, but the actual write (`Commit.where(sha:).create_status_from_github!`) is performed with no check that the matched commit's stack/repository belongs to that same organization. In a multi-org Shipit deployment, a request that is validly signed by Organization A's webhook secret can create/overwrite a CI status on a commit belonging to a stack owned by Organization B, as long as the attacker can get a `status` webhook fired with the target `sha` (e.g., by posting a commit status via the GitHub API against a repository they control in Organization A, using the victim's known commit SHA).

### Impact Explanation
Commit statuses are used by Shipit's deploy-gating logic (`ci.require`/commit checks) to determine whether a commit is deployable. Forging a "success" status for a commit in a stack the attacker does not otherwise have write access to can satisfy CI requirements and enable an **unauthorized deploy** — one of the explicitly listed Critical impacts. This is a cross-organization/cross-repository write of trust-bearing data (commit status), directly analogous to the reported issue where a value trusted implicitly for a later critical decision (an oracle price / here, a commit status) is not properly bound to the entity that is supposed to have produced it.

### Likelihood Explanation
Exploitation requires: (1) a Shipit instance configured with multiple GitHub Apps for multiple organizations (a documented, supported configuration), and (2) an attacker who has legitimate ability to trigger a genuinely-signed `status` webhook from one organization (e.g., by owning/administering a repository under Org A and calling the GitHub Statuses API with an arbitrary/known target `sha`). Because commit SHAs are public/guessable for public repositories and the `StatusHandler` performs no repository/organization scoping whatsoever, this is a plausible attack path in any multi-org Shipit installation, though it is limited to environments that use the multi-organization GitHub App feature.

### Recommendation
In `StatusHandler#process` (and any other handler that does not use `Handler#stacks`), scope the `Commit` lookup by the repository named in the payload (via `stacks`/`repository_name`) instead of a global `sha` lookup, so a status can only be applied to a commit whose stack belongs to the repository/organization that authenticated the webhook. Additionally, `WebhooksController#verify_signature` should re-validate, after signature verification, that the organization used to select the signing secret actually matches the repository owner referenced in the verified payload before any handler executes.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Create a Shipit stack in `OrgB` tracking a commit with SHA `S` that is required to have a passing status for deploy (`ci.require`).
3. As an attacker with control over a repository in `OrgA`, use the GitHub API to create a commit status with `sha=S`, `state=success` on that `OrgA` repository. GitHub sends a genuinely-signed `status` webhook to Shipit, signed with `OrgA`'s `webhook_secret`.
4. `WebhooksController#verify_signature` selects and validates against `OrgA`'s secret (matching `repository.owner.login` = `OrgA` in the payload) — verification succeeds.
5. `StatusHandler#process` executes `Commit.where(sha: 'S')`, matching the `OrgB` stack's commit (global lookup, no organization/repository filter), and calls `create_status_from_github!`, writing a "success" status onto the `OrgB` commit.
6. The forged success status satisfies `OrgB`'s `ci.require` check, allowing an unauthorized deploy of that commit in `OrgB` — despite the request never being signed by `OrgB`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
