### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, so a validly-signed status webhook from an attacker-controlled repository can flip CI state on any other stack's commit that happens to share the same SHA. This is realistic for shared-history scenarios such as forks and review-stack PRs, where the identical commit SHA legitimately exists in both the attacker's repo and the victim's stack.

### Finding Description
The broken binding: `commit.stack.repository == payload.repository` should always hold true when processing a status, but the code never checks it. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) , matching every `Commit` row across every `Stack`/repository in the database that shares that SHA, with no filter on `commit.stack.repository`.

`verify_signature` in `WebhooksController` only verifies that the raw payload was HMAC-signed by GitHub for the organization named in `payload.repository.owner.login` (or `payload.organization.login`) [4](#0-3) . It authenticates "this event genuinely came from GitHub for org X," but nothing ties the `sha` field inside the payload to a commit that must belong to org X's repositories. An attacker who owns/controls a repository (their own fork, or their own GitHub account/org, which is a legitimately configured `Shipit.github(organization: ...)` target) can trigger a real, validly-signed `status` webhook from that repository for any SHA they choose — including a SHA that also exists as a `Commit` row belonging to a victim's stack.

The realistic path to get a shared SHA: `review_stacks_enabled true, allow_all` auto-provisions a review stack from external pull requests, importing the PR head commit (and its SHA) from the attacker's fork into the victim stack's `commits` table. The attacker's fork is the same commit object with the same SHA, so the attacker can send a self-authenticated `status` webhook from their own fork repository containing that exact SHA and `context: ci/integration`, `state: success` (or `failure`). `StatusHandler` will match the `Commit` row in the victim's review stack and call `create_status_from_github!`, which updates `statuses`, recomputes `status`, and can trigger `stack.schedule_merges` / continuous delivery for that stack [5](#0-4) .

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is registered [6](#0-5) ; `verify_signature` checks organization-level HMAC only; the `ExplicitParameters` schema in `StatusHandler` validates field types/presence, not repository ownership [7](#0-6) .

### Impact Explanation
A payload authenticated for one repository (the attacker's own) can mutate CI/status state — and downstream deploy/merge/block decisions — for a commit belonging to a completely different repository/stack that the attacker does not control. This matches the "payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge" Critical impact category, since a forced `success` status can unblock `schedule_merges` and continuous delivery, and a forced `failure`/`error` can block a legitimate deploy. Blast radius is any stack whose commits table happens to contain a SHA the attacker can also produce a signed webhook for (most directly, review stacks created from external PRs under `review_stacks_enabled true, allow_all`).

### Likelihood Explanation
Preconditions: victim stack must have `review_stacks_enabled true, allow_all` (or otherwise ingest attacker-influenceable commits) so the attacker's PR-head SHA is recorded in the victim's `commits` table, and the attacker needs any repository under a Shipit-configured GitHub App/organization from which they can trigger a genuine `status` event (opening a PR from their own fork, then hitting the GitHub Statuses API on their own fork's commit, is sufficient — no Shipit credentials, GitHub team membership, or secrets required). This is inexpensive and repeatable per commit/PR.

### Recommendation
Scope the lookup to commits belonging to the repository that authenticated the webhook, e.g. resolve the `Stack`/`Repository` from `payload.repository.full_name` in `StatusHandler#process` and constrain `Commit.where(sha: params.sha, stack: Stack.where(repository: matched_repo))` (or join through `stack.repository`) before applying `create_status_from_github!`, mirroring the repository scoping already required for other handlers.

### Proof of Concept
1. Seed `stack_a` (victim) with `review_stacks_enabled: true, allow_all: true`, requiring status context `ci/integration`.
2. Seed `stack_b` (attacker-owned) for a different `Repository`.
3. Create a `Commit` with the same `sha` in both `stack_a.commits` and `stack_b.commits` (simulating the shared PR-head SHA from `review_stacks_enabled`).
4. Build a `status` payload with `repository.owner.login` matching `stack_b`'s org (so `verify_signature` passes for the attacker's own org), `sha` = shared SHA, `context: "ci/integration"`, `state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with a valid signature for `stack_b`'s org).
6. Assert: `stack_a.commits.find_by(sha: shared_sha).status.success?` is `true`, and/or `stack_a.schedule_merges`/`ContinuousDeliveryJob` was triggered — despite the webhook never having been signed for `stack_a`'s organization/repository. Equality check before: `commit_a.status.state != 'success'`; after: `commit_a.status.state == 'success'` even though only `stack_b`'s org authenticated the request — proving the divergence.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
