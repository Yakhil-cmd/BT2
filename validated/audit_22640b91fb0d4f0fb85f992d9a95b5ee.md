## Cross-repository commit status forgery via unscoped `StatusHandler` lookup

### Title
Cross-repository CI status forgery due to webhook signature scoped to organization but status write scoped only by commit SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies the GitHub webhook HMAC signature using the secret tied to the **organization/App derived from the payload itself**, but the handler that applies the event writes to **any** `Commit` record in the database that matches the SHA, without any scoping to the repository/organization that produced the signature. This breaks the equality that should hold: *organization that authenticated the webhook == repository whose commit/state is mutated*.

### Finding Description
The webhook signature is verified against a secret chosen from the payload's own `repository.owner.login` / `organization.login` field: [1](#0-0) [2](#0-1) 

This only proves that the payload was signed by *some* organization configured in `Shipit.github(organization: ...)` — i.e. that the sender legitimately controls a GitHub App/organization already registered with Shipit. It says nothing about which repository/stack the event is allowed to affect.

Once the signature check passes, `StatusHandler#process` applies the status update to every `Commit` row that matches the raw `sha` from the payload, with no filter on repository, stack, or organization: [3](#0-2) 

`Commit` records across the whole Shipit instance are looked up purely by `sha`; `Commit.by_sha`/`where(sha: ...)` is a global, cross-stack query, as also seen in the model: [4](#0-3) 

Because git commit SHAs are content-addressed, any two repositories that share history (a fork, a mirror, a repository that was renamed/re-added under a different owner, or a repo split off from a monorepo) will contain commits with **identical SHAs**. An attacker who controls (and has correctly configured a legitimate GitHub App/webhook secret for) **Repository A** — a fork or mirror of victim **Repository B**, both tracked as separate Shipit stacks — can send a `status` webhook whose signature validates against Organization A's secret, but whose `sha` corresponds to a shared ancestor commit that also exists in Repository B's `commits` table. `StatusHandler` will happily write the forged status (`state: success`, arbitrary `context`) onto Repository B's `Commit`, regardless of the fact that Organization A's webhook secret has nothing to do with Repository B.

This is the direct analog of the `PortfolioToken.deposit()` bug: the value that is verified/authorized (webhook signature ⇒ organization A) is not the same as the value the code actually mutates (any commit, in any repository, matching the raw SHA). Just as the AllBridge deposit trusted a state snapshot that could differ from the one used at execution, Shipit trusts that "signature verified" implies "this repository's data may be written," when in fact the write path performs no such check.

### Impact Explanation
A forged/attacker-controlled commit status can:
- Satisfy `ci.require` / blocking status checks configured in Repository B's `shipit.yml`, defined via `required_statuses`/`blocking_statuses` used by `StatusChecker` and `MergeRequest#any_status_checks_failed?` [5](#0-4) , causing an unqualified commit to appear CI-green.
- This can unblock an **unauthorized merge** (`MergeRequest#merge!`) or an **unauthorized deploy** of a commit that never actually passed CI in Repository B, satisfying the "unauthorized deploy, rollback or merge" Critical impact criterion, and constitutes a cross-repository write (Organization A writing into Repository B's data) satisfying the "cross-repository writes" criterion.

### Likelihood Explanation
Requires: (1) attacker controls a legitimate GitHub organization/App already registered as a webhook source in the Shipit instance (i.e., they administer some repository tracked by that Shipit instance — no privileged Shipit account, GitHub token, or `api_clients_secret` needed), and (2) a shared-history repository pair (fork/mirror/rename) that shares SHAs with the target stack — a realistic scenario for open-source forks, internal mirrors, or repositories split/renamed over time. No cryptographic SHA-1 collision attack is required since real shared history naturally produces identical SHAs across such repository pairs.

### Recommendation
Scope commit lookups (and all webhook side effects in general) by the `repository`/`stack` identified from the same authenticated payload, not by SHA alone. E.g., in `StatusHandler#process`, join through `Stack`/`Repository` matching the `repository.full_name` (or `organization.login`) that was used to select the webhook secret, e.g. `commit.stack.repository == expected_repository`, before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker administers GitHub org/App "Attacker-Org" which owns `attacker-org/lib` — a fork of `victim-org/lib`, sharing the commit `abc123...` from before the fork diverged. Both `attacker-org/lib` and `victim-org/lib` are tracked as separate stacks in the same Shipit instance (common for internal mirrors).
2. Victim's stack requires a CI status context, e.g. `ci/required`, on commit `abc123...` before it can merge/deploy, and that commit currently lacks the status (e.g. CI still pending or failing on `victim-org/lib`).
3. Attacker sends a `status` webhook to Shipit signed with Attacker-Org's real webhook secret:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid signature for Attacker-Org secret>
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/lib"}
}
```
4. `WebhooksController#verify_signature` verifies successfully against Attacker-Org's secret because `repository_owner` is taken from the same payload.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, which matches the `Commit` row belonging to `victim-org/lib`'s stack, and calls `create_status_from_github!`, writing a fabricated `success` status for `ci/required` onto the victim's commit — potentially unblocking merge/deploy on `victim-org/lib` despite Attacker-Org having no relationship to that repository.

      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1
