### Title
Integer overflow in JNI batch length validation bypasses size check, causing OOB reads in `verify_blob_kzg_proof_batch` / `verify_cell_kzg_proof_batch` - (File: `bindings/java/ckzg_jni.c`)

### Summary
The OpenCV advisory (CVE-2017-1000450) describes an integer overflow in a length-validation calculation that allows an out-of-bounds write. The analogous pattern in this repo is in the Java JNI bindings, where a caller-supplied count is multiplied by a fixed per-item size and compared against the actual native array length to validate that the array is big enough. The multiplication can wrap around on 64-bit `size_t`, letting a tiny array pass a check intended to guarantee it is large enough for `count` elements.

### Finding Description
In `Java_ethereum_ckzg4844_CKZG4844JNI_verifyBlobKzgProofBatch` the validation is: [1](#0-0) 

```
size_t count_native = (size_t)count;
size_t blobs_size = (size_t)(*env)->GetArrayLength(env, blobs);
if (blobs_size != count_native * BYTES_PER_BLOB) { ... return 0; }
```

`count` is a `jlong` argument controlled directly by the JVM caller, independent from the `blobs` byte array itself. `count_native * BYTES_PER_BLOB` is computed in `size_t` (64-bit) arithmetic. If `count_native = 2^64 / BYTES_PER_BLOB` (i.e. `count_native = 2^47` since `BYTES_PER_BLOB = 131072 = 2^17`), the product wraps to `0` modulo `2^64`. An empty (`0`-length) `blobs` array then satisfies `blobs_size == count_native * BYTES_PER_BLOB` (`0 == 0`), even though `count_native` is `2^47`. The same overflow pattern applies to `commitments_bytes_size` and `proofs_bytes_size` checks in the same function, and to the analogous size checks for `verifyCellKzgProofBatch` and other batch entry points in `bindings/java/ckzg_jni.c` and `bindings/elixir/native/src/ckzg_wrap.c`.

Once the check is bypassed, the huge, attacker/caller-controlled `count_native` is passed straight into `verify_blob_kzg_proof_batch(&out, blobs_native, commitments_native, proofs_native, count_native, settings)`, where the C function will iterate `count_native` times over the tiny (or zero-length) native buffers obtained via `GetByteArrayElements`, reading far outside the allocated buffer.

### Impact Explanation
This breaks the equality the size check is supposed to enforce (`actual_buffer_bytes == count * item_size`), letting a mismatched `count` reach the core verification routine. The result is an out-of-bounds read across memory the process does not own, which can crash the JVM process (segfault/abort) that hosts the KZG library — matching the "High" impact bucket of a single input aborting every node running this library. It does not directly enable a forged proof to verify, since the OOB memory is unlikely to produce a coherent, reproducible "true" verdict across nodes, but it is a reliable crash/DoS vector reachable purely with library inputs.

### Likelihood Explanation
Exploitability depends on whether the `count` argument passed into the JNI method can, in the real deployment, diverge from the actual array length — i.e., whether the higher-level client code (outside this repo, in consensus-client Java code invoking `CKZG4844JNI`) always derives `count` from `blobs.length` itself, or accepts it from an external/network-facing source. Within the scope of this repository, no bound check on `count`/`n` exists before performing the multiplication, so the primitive itself is present and unconditional in the binding layer. I could not fully verify the calling context in the actual consensus-client integration code (outside this repo), so I cannot confirm with certainty that this is remotely triggerable by network-supplied data as opposed to only by a buggy/malicious local caller of the JNI API.

### Recommendation
Before computing `count_native * BYTES_PER_BLOB` (and the analogous commitment/proof/cell size computations), validate `count_native` against an upper bound (e.g., check `count_native > SIZE_MAX / BYTES_PER_BLOB` before multiplying, or perform the division the other way: `blobs_size / BYTES_PER_BLOB != count_native`, and separately check `blobs_size % BYTES_PER_BLOB == 0`). Apply the same fix to every batched JNI/NIF entry point that multiplies a caller-provided count by a fixed item size for a length check (`verifyBlobKzgProofBatch`, `verifyCellKzgProofBatch`, and the Elixir NIF equivalents in `bindings/elixir/native/src/ckzg_wrap.c`).

### Proof of Concept
Not independently confirmed with a running harness (no execution tool available in this session). Conceptually: call `CKZG4844JNI.verifyBlobKzgProofBatch` with an empty `blobs`/`commitments_bytes`/`proofs_bytes` byte array and `count = 2^47` (or another `size_t` value making `count * BYTES_PER_BLOB` wrap to `0` mod `2^64`); the length check at `bindings/java/ckzg_jni.c:436` incorrectly passes, and `verify_blob_kzg_proof_batch` is invoked with `count_native = 2^47` against zero-length native buffers, causing out-of-bounds memory reads.
