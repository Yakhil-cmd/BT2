### Title
CCMenu API endpoint bypasses stack scoping, allowing a token minted for stack A to read stack B's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates via `ApiClient.authenticate(params[:token])` but overrides the `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of the inherited scoped `stacks.from_param!`, so it never checks that the requested stack matches `current_api_client.stack_id`. Any holder of a stack-scoped CCMenu token can substitute an arbitrary `stack_id` in the URL to read another stack's deploy status.

### Finding Description
The intended binding is: `stack_id` requested == `current_api_client.stack_id` (when the token is stack-scoped) OR the client is unscoped (`stack_id` is nil, meaning "any stack").

In `Api::BaseController`, the `stacks` method enforces this: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) , and the default `stack` method resolves through this scope.

However, `Api::CCMenuController` redefines `stack` to bypass that scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`authenticate_api_client` is also overridden to authenticate purely from the query-string `token` param (as CCMenu clients don't send Basic Auth headers), setting `@current_api_client` to whatever `ApiClient` the token verifies to [3](#0-2) . The `require_permission :read, :stack` before_action only checks `check_permissions!(operation, scope)`, which validates the permission string list (`permissions.include?("read:stack")`) and has no notion of which stack the client is bound to [4](#0-3) .

So for a token minted with `ApiClient.create!(stack: stack_a, permissions: ['read:stack'])`, a request to `/ccmenu/#{stack_b.to_param}?token=<token>` will: authenticate successfully (token is valid regardless of stack), pass the `read:stack` permission check (permission list contains `read:stack`, no stack comparison), and then resolve `stack` via `Stack.from_param!(params[:stack_id])` — unscoped lookup — returning stack B directly. `show` then renders stack B's `deploys_and_rollbacks.last` state as XML [5](#0-4) .

None of the guards mentioned in the audit rules apply here: there's no webhook signature to check, no `ExplicitParameters` schema on this param, and the `stacks` scope — the actual guard against this — is exactly what's being bypassed by the override.

### Impact Explanation
An attacker who legitimately possesses a CCMenu token scoped to stack A (e.g., by visiting `CCMenuUrlController#fetch` for a stack they collaborate on, or by being handed a CI status URL) can enumerate/guess other stacks' `to_param` (owner/repo/branch/environment identifiers, which are generally not secret) and read those other stacks' latest deploy/rollback status (running state, timestamps) without any authorization on that stack. This is an unauthenticated/unauthorized cross-tenant read of stack state, matching the "High - unauthenticated read of stack state" impact category. It is fully repeatable against any stack_id known to the attacker and does not require GitHub or Shipit secrets, only a valid CCMenu token for any one stack.

### Likelihood Explanation
Preconditions: attacker must possess one valid CCMenu token (trivially obtainable if they are a collaborator on any single stack, or if a token is exposed via a CI badge/URL, which is CCMenu's expected use case) and must know or guess the target stack's `to_param` (repo owner/name/branch/environment), which is typically public/discoverable information for a self-hosted CI dashboard. Attacker cost is a single HTTP GET request; the exploit is trivially repeatable across any number of stacks.

### Recommendation
In `Api::CCMenuController`, remove the overridden `stack` method (or have it delegate to the inherited scoped `stacks.from_param!(params[:stack_id])`) so that the stack lookup respects `current_api_client.stack_id`, consistent with every other endpoint in `Api::BaseController`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a token scoped to stack A cannot read stack B's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack(repository: create_repository(owner: 'other', name: 'other-repo'))

  client = ApiClient.create!(
    stack: stack_a,
    permissions: ['read:stack'],
    creator: shipit_users(:walrus),
    name: 'scoped-client'
  )

  # Binding under test: params[:stack_id] resolved stack must equal current_api_client.stack_id
  assert_equal stack_a.id, client.stack_id

  get "/ccmenu/#{stack_b.to_param}", params: { token: client.authentication_token }

  # Expect denial since stack_b != client.stack_id
  assert_response :not_found # or :forbidden
  # Currently fails: returns 200 with stack_b's XML, proving the broken binding
end
```
