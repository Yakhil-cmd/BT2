### Title
`pallet-nfts` `do_transfer` fails to clear `ItemAttributesApprovalsOf`, letting a previous owner's approved delegate keep write access to attributes after ownership changes - ([File: substrate/frame/nfts/src/features/transfer.rs])

### Summary
`pallet-nfts::do_transfer` explicitly clears the `approvals` field embedded in `ItemDetails` (transfer approvals) but never touches the separate `ItemAttributesApprovalsOf` storage map that tracks which delegate accounts are allowed to write attributes for an item under the `AttributeNamespace::Account(delegate)` namespace. This is structurally the same bug class as the reported `CouncilMember.sol` issue: an allowance/approval concept lives in storage that is decoupled from the primary ownership record, and transfer/burn logic only resets the ownership-coupled storage, leaving the decoupled approval alive and usable by an account that should have lost its authorization once the underlying asset changed hands.

### Finding Description
`Item<T,I>` stores `ItemDetails.approvals` (a `BoundedBTreeMap` of delegate -> deadline used only for the `transfer`/`approve_transfer` flow). `do_transfer` clears this map on every ownership change: [1](#0-0) 

However, item-attribute delegate approvals are tracked in a completely separate map, `ItemAttributesApprovalsOf<T, I>` (keyed by `collection`/`item`), populated by `do_approve_item_attributes` and only removed by `do_cancel_item_attributes_approval` or on full item burn: [2](#0-1) [3](#0-2) [4](#0-3) 

`do_transfer` (shown above) never calls `ItemAttributesApprovalsOf::<T, I>::remove(...)`. The permission check for writing an attribute in the `Account(delegate)` namespace, `is_valid_namespace`, only checks that the caller equals the namespace account and that it is present in `ItemAttributesApprovalsOf` — it performs no check that the delegate's approval was granted by the *current* item owner: [5](#0-4) 

So, if Alice (owner) approves delegate D via `approve_item_attributes`, then transfers the item to Bob via `transfer`, D remains present in `ItemAttributesApprovalsOf` and can still call `set_attribute` with `namespace = Account(D)` to write/overwrite item attributes on Bob's item — a namespace whose semantics are "pre-approved by the item owner" but whose approval was actually granted by a party who no longer owns the item.

This mirrors the report's root cause exactly: the ERC721-analog primary transfer function clears one approval-tracking structure but skips a second, independently-maintained approval mapping.

### Impact Explanation
A previously-approved account retains the ability to write item attributes (`AttributeNamespace::Account(delegate)`) on an NFT after it has been transferred to a new owner, without the new owner's consent. Attribute writes consume/require deposits reserved from the depositor (in this instance, from the delegate, per `do_set_attribute`), and give the stale delegate continuing metadata-control influence over an item they no longer have any relationship to. Depending on how consuming applications/marketplaces interpret `Account(delegate)`-namespaced attributes (e.g., trust marks, provenance data, or off-chain metadata resolution), this allows an unauthorized party to inject or persist attacker-controlled data on someone else's NFT post-transfer. This is a logic/authorization integrity break rather than a direct fund-theft primitive, consistent with a Medium-severity classification, matching the severity of the original report.

### Likelihood Explanation
High likelihood of occurrence in normal usage: any collection using the `Attributes` pallet feature and delegate-based attribute approvals (`approve_item_attributes`) combined with a subsequent unconditional `transfer` will hit this path. No privileged role, governance action, or malicious actor cooperation is required — a normal item owner approving a delegate and then transferring the item (a very ordinary sequence, e.g. selling an item after having approved a metadata-management delegate) is sufficient to leave the stale approval active. The new owner has no visibility into, or ability to detect, this residual permission without manually calling `cancel_item_attributes_approval` for every delegate (which they may not even know about).

### Recommendation
In `do_transfer` (substrate/frame/nfts/src/features/transfer.rs), clear `ItemAttributesApprovalsOf::<T, I>` for the `(collection, item)` pair alongside clearing `details.approvals`, unreserving any deposits held by delegates the same way `do_cancel_item_attributes_approval` does, or emit `ItemAttributesApprovalRemoved` events for each removed delegate to keep off-chain indexers consistent.

### Proof of Concept
Not independently executed in this environment (no Rust/FRAME test harness run was performed). The code-path evidence is direct and file/line-verifiable:
1. `Nfts::approve_item_attributes(owner, collection, item, delegate)` — inserts `delegate` into `ItemAttributesApprovalsOf` [6](#0-5) .
2. `Nfts::transfer(owner, collection, item, new_owner)` — calls `do_transfer`, which clears only `details.approvals` and never touches `ItemAttributesApprovalsOf` [7](#0-6) .
3. `Nfts::set_attribute(delegate, collection, Some(item), AttributeNamespace::Account(delegate), key, value)` — passes `is_valid_namespace` because `ItemAttributesApprovalsOf` still contains `delegate`, regardless of the fact that ownership moved to `new_owner` [5](#0-4) .

A minimal FRAME unit test (in `substrate/frame/nfts/src/tests.rs`, following the pattern of existing tests like `approval_lifecycle_works` and `clear_all_transfer_approvals_works`) would: create a collection, mint an item to account 2, call `approve_item_attributes(2, coll, item, account(3))`, call `transfer(2, coll, item, account(4))`, then assert that `set_attribute(account(3), coll, Some(item), Account(account(3)), key, value)` still succeeds — demonstrating the stale approval survives transfer. This test was not run in this session; the claim is based on direct code inspection of the guard conditions rather than an executed assertion.

	pub(crate) fn do_cancel_item_attributes_approval(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
		witness: CancelAttributesApprovalWitness,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals.remove(&delegate);

			let mut attributes: u32 = 0;
			let mut deposited: DepositBalanceOf<T, I> = Zero::zero();
			for (_, (_, deposit)) in Attribute::<T, I>::drain_prefix((
				&collection,
				Some(item),
				AttributeNamespace::Account(delegate.clone()),
			)) {
				attributes.saturating_inc();
				deposited = deposited.saturating_add(deposit.amount);
			}
			ensure!(attributes <= witness.account_attributes, Error::<T, I>::BadWitness);

			if !deposited.is_zero() {
				T::Currency::unreserve(&delegate, deposited);
			}

			Self::deposit_event(Event::ItemAttributesApprovalRemoved {
				collection,
				item,
				delegate,
			});
			Ok(())
		})
	}
