### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which per-organization `GithubApp` secret to validate a webhook against using `repository_owner`, a value taken from `repository.owner.login` (or `organization.login`) in the *unverified* JSON body. Once verification passes, every event handler instead identifies the target `Stack`/`Repository` using a completely different, equally attacker-controlled field: `repository.full_name`. Nothing ties these two fields together, so signing a payload with one organization's webhook secret does not guarantee the payload's declared repository actually belongs to that organization.

### Finding Description
`verify_signature` picks the signing app like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read straight out of the untrusted JSON body, purely to select which per-org HMAC secret (`GithubApp#webhook_secret`, set via `Shipit.github(organization:)`) to check against. The actual downstream identity used by every handler to resolve which `Stack` to mutate is a *different* field of the same untrusted body: `repository.full_name`. [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` and `repository.full_name` are never cross-checked against each other. The HMAC only proves "this byte stream was signed with organization X's secret" - it says nothing about which repository the byte stream *claims* to describe. This is the "organization that authenticated versus the repository that is written" trust-binding break called out for this bug class: the signature covers a field (`repository.owner.login`) that is not the field the engine actually acts on (`repository.full_name`).

Concretely, a legitimate holder of one org's GitHub App webhook secret (org `A`, which they administer/installed) can craft and correctly sign a payload where:
- `repository.owner.login` = `A` (so `Shipit.github(organization: "A")`'s secret verifies the HMAC), and
- `repository.full_name` = `"B/victim-repo"` (an unrelated organization `B`'s repository, tracked by a Shipit `Stack` they have no access to).

`Repository.from_github_repo_name("B/victim-repo")` resolves purely from `owner`/`name` columns populated from `full_name`, with no relation to the verified `repository_owner`: [4](#0-3) 

This lets the request reach handlers such as `PushHandler#process` (triggers `stack.sync_github`), the `pull_request` handlers (`archive!`/`unarchive!`/`ReviewStackAdapter#create!`), or the `status`/`commit_status` handlers, all scoped to `B`'s stack despite the signature only proving authorship by `A`. [5](#0-4) [6](#0-5) 

### Impact Explanation
This crosses a repository/organization authorization boundary that the engine is supposed to enforce with per-org webhook secrets: an entity that only proves control of organization `A`'s GitHub App configuration can trigger `GithubSyncJob`, force a review-stack archive/unarchive, or forge commit statuses/deploy-relevant state for a `Stack` belonging to organization `B`, purely because the code checks the wrong field. Depending on `B`'s `shipit.yml`/continuous-deployment configuration, a forced `sync_github` combined with forged `status`/`commit_status` events could push a `Stack` configured for continuous deployment to deploy attacker-influenced commits, which lands in "unauthorized deploy" territory. At minimum it is a cross-repository state-write/authorization bypass.

### Likelihood Explanation
Exploitation requires the attacker to control (or have configured) at least one organization's GitHub App entry in `Shipit.github`/`config/secrets*.yml` with its own `webhook_secret` — a realistic scenario for any Shipit instance hosting stacks for multiple orgs/teams, since each org's webhook secret is independently held by whoever manages that org's GitHub App/webhook settings. No repository write access, `ApiClient` token, or session to the target org `B` is required — only the secret for org `A`, which is explicitly assumed to be a lower-privilege, org-scoped credential in this multi-org design. This matches the "unprivileged attacker" framing: the attacker is privileged for org `A` only, not for the victim repository `B`.

### Recommendation
After verifying the HMAC, cross-validate that the field(s) actually consumed by handlers (`repository.full_name`, and by extension its embedded `owner`) match the `repository_owner`/`organization.login` used to select the signing secret — i.e., derive the handler's `Repository` lookup key from the same, already-verified `repository_owner`, or explicitly assert `full_name.split('/').first == repository_owner` before dispatching to `Shipit::Webhooks.for_event(event)`.

### Proof of Concept
1. Configure two organizations in `Shipit.github`, `A` (attacker-administered, secret `S_A`) and `B` (victim, tracked `Stack` `B/victim-repo`).
2. Attacker builds a `push` (or `pull_request`) webhook JSON body with `repository.owner.login = "A"` and `repository.full_name = "B/victim-repo"`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "A")` via `repository_owner`, verifies successfully, and dispatches to `Shipit::Webhooks.for_event('push')`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("B/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `B`'s stack, even though the signature never proved authorship for organization `B`.
