### Title
Silent `action:block` → `warn` downgrade due to non-canonical YAML indentation in custom frontmatter parser - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` is a hand-rolled YAML-subset parser that recognizes only three line shapes: indent==0 key:value, `- ` list items, and continuation lines with `indent > 2`. Any line that doesn't fit exactly one of these (e.g. a `action: block` line nested at 2-space indent under a `conditions:` list, which real YAML rejects with a parse error) is silently dropped instead of raising an error. Since `Rule.from_dict` falls back to `action = frontmatter.get('action', 'warn')`, a dropped `action: block` key silently becomes `warn`, and `RuleEngine.evaluate_rules` treats `warn` rules as non-blocking, allowing the matched dangerous command to execute with only a cosmetic warning message.

### Finding Description
`extract_frontmatter` (plugins/hookify/core/config_loader.py:87-195) processes frontmatter line-by-line with only three matching branches: top-level `indent == 0` key/value [1](#0-0) , list items starting with `-` [2](#0-1) , and dict-item continuation lines gated by a hardcoded `indent > 2` check [3](#0-2) . Any line whose indentation doesn't cleanly match one of these three shapes falls through all branches and is silently discarded with no error and no fallback handling.

If a rule file places `action: block` at 2-space indentation directly beneath a `conditions:` list item (a plausible mistake or attacker-crafted layout that PyYAML would reject as a scanner error because a plain mapping key at the same column as an unindented `-` marker is not a valid sequence continuation), the parser's state machine leaves `in_dict_item=True` from the prior list entry, so the `action` line hits neither the `indent==0` branch nor the `indent>2` continuation branch, and is dropped entirely rather than added to `frontmatter` or raising an exception.

`Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [4](#0-3) , defaulting silently to `"warn"`. In `RuleEngine.evaluate_rules`, only rules with `rule.action == 'block'` are added to `blocking_rules`; everything else goes to `warning_rules`, which only produces a `systemMessage` and returns without any `permissionDecision: "deny"`, allowing the tool call to proceed [5](#0-4) [6](#0-5) . `load_rule_file` never raises for this case (there is no exception to catch), so the malformed rule loads successfully as an apparently valid, enabled "warn" rule with no indication to the file author/reviewer that the intended `block` action was lost [7](#0-6) .

### Impact Explanation
This is an approval/hook-enforcement bypass: a `.claude/hookify.*.local.md` rule that a repo maintainer believes will `deny`/block dangerous `Bash` commands (e.g. `rm -rf`, arbitrary `exec`) silently degrades to a non-blocking warning. When Claude Code (or an attacker via a separate prompt-injection vector elsewhere in the same repo) subsequently triggers the matched dangerous command, `pretooluse.py` only emits a `systemMessage` warning and does not set `permissionDecision: "deny"`, so the destructive command executes anyway [8](#0-7) . This directly violates "deny means deny" and can result in unauthorized destructive command execution/data loss under a false sense of protection.

### Likelihood Explanation
Preconditions are minimal and match the stated threat model: the attacker only needs the ability to add/modify a file under `.claude/` in a repository Claude Code operates on (e.g., a merged PR or a cloned malicious repo), with no privileged access or social engineering beyond normal content review. The malformed indentation (2-space field nested under a `conditions:` list entry) is subtle enough to pass casual review as a stylistic YAML choice, and the custom parser never errors or logs a diagnostic distinguishing it from a correctly parsed `block` rule, making the downgrade fully silent and repeatable on every hook invocation.

### Recommendation
Replace the hand-rolled frontmatter parser with a real YAML parser (e.g. PyYAML `safe_load`) so indentation semantics match user expectations and malformed documents raise explicit, loud errors instead of silently dropping keys. If the custom parser must remain, add strict validation that fails closed (rejects/logs the rule file rather than defaulting `action` to `warn`) whenever a line cannot be unambiguously classified, and require `action` to be present and one of the allowed literal values, treating a missing/undecidable `action` for a rule with blocking intent as a hard load error rather than a silent default.

### Proof of Concept
Add a differential fuzz/unit test in `plugins/hookify/tests` (or a new test module) that:
1. Constructs frontmatter documents with `action: block` under a `conditions:` list using indentation variants (0, 1, 2, 3, 4+ spaces) for the `action` line and for dict-item continuation lines.
2. Parses each variant with `extract_frontmatter` and with `yaml.safe_load` (extracting the equivalent frontmatter block), asserting `Rule.from_dict(fm, msg).action == 'block'` for every variant that PyYAML successfully parses with `action: block` present at the document's top level, and asserting that inputs PyYAML rejects as invalid are also rejected (raise or return `None`) by `load_rule_file`, not silently accepted as a `warn` rule.
3. Concretely: for the 2-space-under-list-item case shown above, assert `rule.action == 'warn'` is produced by current code (demonstrating the bug), then after the fix assert either the file fails to load or `rule.action == 'block'` is preserved.
4. Add an integration test invoking `RuleEngine.evaluate_rules` with the resulting rule and a `tool_input.command = "rm -rf /"` payload, asserting the response lacks `permissionDecision: "deny"` under current code (bug reproduction) and contains it after the fix.
