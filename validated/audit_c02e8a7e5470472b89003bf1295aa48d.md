### Title
Autonomous Agents Can Never Recover Indivisible (Non-Fungible-Like) Assets Sent to Them - (File: aa_composer.js)

### Summary
The Lido report describes `transferToVault()` lacking any recovery path for ERC721 (non-fungible) tokens accidentally sent to the vault, permanently locking them. The Obyte analog of a non-fungible/indivisible asset is an asset defined with `fixed_denominations: true` (unique, serial-numbered coins, exactly like ERC721 items are unique, non-fungible units). In `aa_composer.js`, the AA response-composition logic is architecturally unable to construct any payment message for a `fixed_denominations` asset, so any such asset paid to an AA address is permanently stuck in the AA's balance with no way for the AA (or anyone) to send it back out — there is no recovery mechanism, mirroring the reported bug class exactly.

### Finding Description
When an AA (Autonomous Agent) receives a trigger unit whose payment output pays it in a `fixed_denominations` (indivisible) asset, the AA's balance for that asset is credited normally via `updateInitialAABalances` in [1](#0-0) , exactly as with any fungible or divisible asset.

However, when the AA (or the bounce/response machinery) later tries to construct any payment message sending that same asset back out, the composer code explicitly skips completing the payload for such assets and then strips any payment message for them out of the response unit entirely: [2](#0-1) 

and later: [3](#0-2) 

If, after this filtering, no messages remain, the AA silently produces an empty successful response (`handleSuccessfulEmptyResponseUnit(null)`), permanently absorbing the coins with zero possibility of transferring them onward. This is not a validation-layer restriction that could be worked around by a different message shape — the composer never populates `inputs` for `fixed_denominations` assets (`completePaymentPayload` is simply never called, comment: "will skip it later"), and the resulting message is unconditionally dropped before the unit is even built. There is no AA definition or oscript construct that can bypass this, because the restriction is hard-coded in the trusted node-side composer that every full node runs when computing AA responses (not merely client-side).

By contrast, base and divisible assets are fully supported for outgoing AA payments via `completePaymentPayload`, and the only other guarded case is private assets, which are rejected with an explicit error message ("sending private asset from AA") rather than silently vanishing. Indivisible assets have no equivalent explicit rejection at the oscript-authoring stage — an AA author can freely write `{app: 'payment', payload: {asset: X, outputs: [...]}}` for an indivisible asset X, and it will pass all AA-definition validation, yet the node will always silently drop it at response time.

### Impact Explanation
Any indivisible/fixed-denomination asset unit paid into an AA address — whether by a mistaken user, an asset issuer testing an AA-based exchange/vault contract, or an AA-to-AA chain trying to forward NFT-like coins — becomes permanently and irrecoverably frozen in that AA's balance. There is no `oscript` message, no state variable, and no protocol upgrade path exposed to AA authors that can move these funds back out; the restriction lives in the core, trusted `aa_composer.js` logic that runs identically on every node. This is a fund-freezing bug reachable by any ordinary AA trigger sender or asset issuer who interacts with an AA using an indivisible asset, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is high in any application where an AA is meant to hold, exchange, or act as an escrow/vault for indivisible assets (a common use case, since indivisible assets are Obyte's mechanism for non-fungible, serial-numbered digital items, analogous to ERC721 collectibles). Nothing in AA-authoring documentation, the `oscript` validator (`aa_validation.js`), or the trigger/response pipeline warns the AA author or the asset sender that indivisible assets cannot be sent back — the failure only manifests silently at execution time on every node.

### Recommendation
Either:
1. Add explicit, early rejection/bounce of trigger payments in `fixed_denominations` assets to AAs (mirroring the existing private-asset rejection at aa_composer.js:1329-1330), so senders get immediate, visible feedback and never lose funds to an AA that can't return them; or
2. Implement genuine support for AAs to construct valid indivisible-asset payment messages (picking specific serial-numbered coins analogous to `pickIndivisibleCoinsForAmount` in `indivisible_asset.js`), enabling AAs to actually transfer indivisible assets they hold.

Given the complexity of implementing (2) safely, (1) — validating at unit-acceptance time that no payment output routes a `fixed_denominations` asset to an AA address, or bouncing/refunding it immediately during trigger handling — is the minimal safe fix.

### Proof of Concept
1. Define asset `X` with `fixed_denominations: true` and issue several denominated, serial-numbered coins of `X`.
2. Deploy any AA whose template contains a rule like:
```
{
  messages: [{
    app: 'payment',
    payload: { asset: '{trigger.data.asset}', outputs: [{address: '{trigger.address}', amount: '{trigger.data.amount}'}] }
  }]
}
```
3. Send a trigger unit paying some coins of asset `X` to the AA address (as `payload.outputs` in a `payment` message with `asset: X`), along with base-asset trigger data requesting a "withdrawal" of `X` back to the sender.
4. Observe: `updateInitialAABalances` credits the AA's `aa_balances` for asset `X` (aa_composer.js:475-541). When the AA response is composed, the outgoing payment message for asset `X` is skipped (aa_composer.js:1327-1328) and then filtered out entirely (aa_composer.js:1356), producing an empty successful response — the `X` coins remain in the AA's balance forever, with no oscript path capable of extracting them.
