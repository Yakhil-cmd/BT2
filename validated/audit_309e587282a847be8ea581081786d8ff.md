### Title
`verify_webhook_signature` silently authenticates any request when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank, meaning any organization configured in Shipit without a `webhook_secret` accepts unsigned/forged webhooks. `WebhooksController#verify_signature` uses this result directly to gate dispatch to `PushHandler`/`CheckSuiteHandler`/etc., so a misconfigured (secret-less) org's real stacks can be driven by attacker-forged payloads with zero proof of GitHub origin.

### Finding Description
The broken binding: `verify_webhook_signature(signature, message) == true` should imply `signature` is a valid HMAC-SHA1 of `message` under the org's `webhook_secret`. Instead, for orgs where `@webhook_secret` is nil/blank, the equality holds unconditionally, regardless of `signature`.

Code path:
- `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence` [1](#0-0) .
- `verify_webhook_signature` starts with `return true unless webhook_secret` [2](#0-1) , before any HMAC comparison.
- `WebhooksController#verify_signature` resolves the app via `Shipit.github(organization: repository_owner)` (looked up from attacker-controlled `params.dig('repository','owner','login')`) and calls `verify_webhook_signature` [3](#0-2) , then `#create` parses the raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers with no further authentication check [4](#0-3) .

An attacker who knows (or can guess/enumerate) that some configured GitHub organization in Shipit's `secrets.github` config lacks a `webhook_secret` entry can `POST /webhooks` with `X-Github-Event: push` (or `pull_request`, `check_suite`, etc.), any/no `X-Hub-Signature`, and a JSON body naming `repository.owner.login` as that organization and `repository.full_name` as a real registered repository/stack. `verify_signature` resolves that org's `GitHubApp`, calls `verify_webhook_signature`, which short-circuits to `true`, and the forged payload is processed by the real handler exactly as if GitHub had sent it.

No other guard intercepts this: `drop_unhandled_event` only filters by event type presence, not authenticity [5](#0-4) ; there is no `ExplicitParameters` schema or session/API-token check on this controller since `WebhooksController` is unauthenticated by design (webhooks are meant to be verified purely by signature).

### Impact Explanation
An attacker can force real handlers (`PushHandler`, `CheckSuiteHandler`, `OpenedHandler`, etc.) to run against a legitimate stack belonging to any organization whose Shipit config omits `webhook_secret`, with a fully attacker-controlled payload. Depending on the handler this could trigger stack syncs, commit deployment status writes, PR-driven state changes — i.e., a payload not actually originating from GitHub mutating a real repository's stack/task state. This matches the "authentication bypass (forged webhook ... accepted)" Critical category. It is repeatable against every repository owned by any affected organization, for as long as that org's config entry lacks a secret.

### Likelihood Explanation
This requires no attacker secrets — only that a Shipit operator has configured an organization entry in `secrets.github` (multi-org schema, since `github_app_config(organization)` requires it) without setting `webhook_secret`. This is an operator misconfiguration, but the code provides no safety net: rather than failing closed (rejecting webhooks for a mis/under-configured org), `GitHubApp` fails open. Given `webhook_secret` is optional in config (`.presence`), and no startup/config validation enforces its presence, this is a plausible operational state, and exploitation cost for an attacker is a single unauthenticated HTTP POST.

### Recommendation
Change `verify_webhook_signature` to fail closed: if `webhook_secret` is blank, return `false` (or raise/log a configuration error) rather than `true`. Additionally, consider validating at boot/config-load time that every configured GitHub org has a non-blank `webhook_secret`, so misconfiguration is caught before deployment rather than silently disabling authentication.

test "#verify_webhook_signature returns false, not true, when webhook_secret is blank" do
  config_without_secret = double_github_app_config.deep_merge("webhook_secret" => nil)
  app_without_secret = GitHubApp.new(@organization, config_without_secret)

  # Binding under test: verify_webhook_signature(sig, body) == (sig authenticates body under secret)
  # LHS observed:
  result = app_without_secret.verify_webhook_signature(nil, '{"forged":"payload"}')
  # RHS expected (no secret => cannot authenticate => should be false)
  assert_equal false, result, "webhook signature verification must fail closed when no secret is configured"
end
