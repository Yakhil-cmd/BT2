### Title
ERC20Transactor credits/moves XCM holding by the requested amount instead of the actual balance delta observed on the ERC20 contract, causing accounting desync for fee-on-transfer/rebasing ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call an arbitrary ERC20 contract's `transfer`/`transferFrom`-equivalent (`IERC20::transferCall`) and, on a successful (`true`) return value, unconditionally credit the XCM holding register (or assume full deposit) with the *requested* `amount` rather than checking the actual balance change on the checking account / beneficiary. Any ERC20 contract matched by `ERC20Matcher` (`AccountKey20` location, i.e. any deployed `pallet-revive` contract address) that implements fee-on-transfer, deflationary/burn-on-transfer, or rebasing semantics will cause the runtime's XCM accounting to diverge from the actual token balances held by the checking account, analogous to the reported `CrabNetting.depositUSDC()` issue where `_amount` was trusted instead of measuring the real balance delta.

### Finding Description
`ERC20Transactor` is wired directly into Asset Hub Westend's production `AssetTransactors` tuple: [1](#0-0) 

The matcher `ERC20Matcher` matches *any* location of the shape `(0, [AccountKey20 { .. }])`, i.e. any 20-byte address, which in `pallet-revive` corresponds to any deployed smart contract: [2](#0-1) 

There is no allow-list or registration/vetting step for which ERC20 contracts can be referenced this way — any contract address that responds to the standard `IERC20::transfer`/`transferFrom` ABI and returns `true` is accepted by the transactor.

In `withdraw_asset_with_surplus`, the transactor calls `transfer(checking_address, amount)` from the user's origin. If the call succeeds and returns `true`, the code credits the XCM holding register with exactly `amount`, regardless of what the checking account actually received: [3](#0-2) 

Likewise, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the checking account and, on success, simply returns `Ok(surplus)` without decrementing anything by the shortfall or verifying that the beneficiary's balance increased by `amount`: [4](#0-3) 

If a user deploys (or an attacker deploys and gets it referenced in an XCM program) an ERC20 contract on `pallet-revive` whose `transfer`/`transferFrom` implementation burns or redirects part of the value (fee-on-transfer / tax token), then:
- On withdrawal, the checking account's real ERC20 balance increases by `amount - fee`, but the XCM holding register is credited with the full `amount`. This over-states what the runtime believes it "holds" in escrow relative to what the checking account actually possesses.
- On deposit, the checking account's balance is decreased by `amount` (its actual balance change, since it is the sender), but the beneficiary only receives `amount - fee`. The XCM executor's holding register, however, was already decremented by the full `amount` when it was taken for deposit — the discrepancy manifests as the checking account eventually going insolvent relative to future withdraw/deposit legs that assume `checking_account_balance == sum of net escrowed XCM holdings`.

Over repeated cross-chain transfers of such a token, the checking account (`ERC20TransfersCheckingAccount`, a `PalletId`-derived account: `py/revch`) will accumulate a persistent deficit between what the runtime's XCM accounting believes is escrowed and what the ERC20 contract actually holds for that account. This mirrors the CrabNetting bug precisely: the contract credits the internal ledger with the caller-supplied `amount` instead of measuring the actual balance delta before/after the `transfer` call.

### Impact Explanation
This causes a persistent bookkeeping desync between the runtime's XCM holding-register accounting and the actual ERC20 balance of the checking account for any fee-on-transfer/deflationary ERC20 contract referenced via `AccountKey20` locations. Depending on transfer volume and direction, this can eventually cause legitimate `deposit_asset`/`withdraw_asset` calls to fail (insufficient real balance vs. what the runtime believes is available) or under/over-credit destination accounts across chains for that specific token — an accounting integrity break scoped to whichever ERC20 tokens exhibit non-standard transfer semantics. It does not directly permit unbacked issuance of any *system* asset (native token, `pallet-assets` assets), since it is scoped to the ERC20 asset class matched by `ERC20Matcher`, but it is a genuine, demonstrably reachable Medium-severity accounting bug in production Asset Hub Westend runtime code, matching the class and severity of the referenced report.

### Likelihood Explanation
Likelihood is Medium: pallet-revive on Asset Hub Westend permits permissionless contract deployment, and any signed user can deploy a standard-interface ERC20 contract with fee-on-transfer logic and then reference it in an `AccountKey20` asset location within an XCM program executed via `pallet-xcm`'s `execute`/transfer extrinsics (a real, un-privileged user entry point). No governance, root, or validator/collator collusion is required — only deploying a contract and issuing an ordinary signed XCM transfer referencing it.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the checking/beneficiary account's ERC20 balance before and after the `transfer` call (via `IERC20::balanceOf`) and credit/debit the XCM holding register with the actual observed delta rather than the caller/XCM-requested `amount`. Alternatively, explicitly document and enforce (e.g., via an allow-list or a pre-flight balance-delta check at registration time) that only ERC20 contracts with standard, non-fee-on-transfer, non-rebasing semantics may be referenced through this transactor.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

			pallet_revive::Pallet::<T>::bare_call(

				asset_id,

			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))

					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
