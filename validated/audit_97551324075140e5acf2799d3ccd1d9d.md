No vulnerability found for this question.

The referenced report describes a Solidity-specific misconception: that the `private` visibility modifier hides a state variable's value from on-chain observers. This is a language-level EVM misunderstanding, not a code defect — `private` in Solidity only restricts *inheritance/external-call* access, not storage-slot readability, and Solidity/Foundry documentation confirms this.

There is no meaningful FRAME/Substrate analog to "force" here:

- FRAME storage has no `private`-like access modifier that developers might mistake for secrecy. All pallet storage items (`StorageValue`, `StorageMap`, etc.) are, by design and by explicit documentation, globally readable via the standard state RPCs — `state_getStorage`, `state_queryStorage`, `archive_v1_storage`, `chainHead_v1_storage`, etc. [1](#0-0) [2](#0-1) 
- The `pallet-revive` `get_storage`/`get_storage_var_key` runtime APIs similarly expose contract storage directly and openly as a first-class, intended feature for tooling/explorers — not a bypass of any confidentiality guarantee. [3](#0-2) 
- Where the codebase does handle genuinely sensitive material (e.g., keystore passwords, secret seed phrases), it uses `SecretString`/`ExposeSecret` wrappers and keeps that data off-chain in the local keystore, never in on-chain storage. [4](#0-3) [5](#0-4) 

Since blockchain/state transparency is the intended, documented behavior of FRAME storage (not an assumption a pallet author is misled into violating the way Solidity's `private` keyword misleads), there is no analogous confidentiality-violating bug to report here.

	pub fn get_storage_var_key(address: H160, key: Vec<u8>) -> GetStorageResult {
		let contract_info =
			AccountInfo::<T>::load_contract(&address).ok_or(ContractAccessError::DoesntExist)?;

		let maybe_value = contract_info.read(
			&Key::try_from_var(key)
				.map_err(|_| ContractAccessError::KeyDecodingFailed)?
				.into(),
		);
		Ok(maybe_value)
	}
