Based on my investigation, I found a directly analogous vulnerability pattern in `pox-5.clar`'s Bitcoin lockup verification logic. The external report's bug class — an unprivileged actor constructing an order/input that appears valid to the contract but breaks an implicit invariant, permanently harming a counterparty or double-counting value — maps onto the replay-protection gap in `validate-l1-lockup`.

### Title
Reused Bitcoin L1 lockup outpoints across multiple `register-for-bond` calls allow double-counting of stacking commitments - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1-lockup verification only rejects duplicate `(txid, output-index)` pairs *within a single call* via the `seen-outpoints` accumulator, which is freshly initialized to `(list)` on every invocation of `verify-l1-lockups`. There is no persistent, contract-wide map recording which Bitcoin outpoints have already been credited to a bond.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied `outputs` list using `validate-l1-lockup`, starting each time from `seen-outpoints: (list)`. [1](#0-0) 
The per-lockup validation checks the unlock height, script hash, amount, Merkle proof, and Bitcoin header, and rejects duplicates only against `seen-outpoints`, the accumulator scoped to the current call: [2](#0-1) 
Because this state is not persisted (no global `used-outpoints`/`spent-lockups` map is written to), the same valid Bitcoin transaction output — one real, single BTC lockup — can be presented again in a separate `register-for-bond` call, either for a different `bond-index`, or after the staker's first bond position is cleared/rolled over, and it will pass all the same cryptographic and script checks a second time, crediting its `amount` in sats again toward a new bond's `total-ustx`/reward-share accounting.

### Impact Explanation
Each successful `validate-l1-lockup` pass increases the `sum` (sats credited) returned by `verify-l1-lockups`, which downstream is used to size the staker's bond stake/reward share and (per the STX-lock handling in `pox_5.rs`/`pox-5.clar`) the amount of STX/rewards attributed to that Bitcoin commitment. Reusing the same on-chain BTC output across multiple bonds means sats are credited by an L1 proof that were only ever locked once on Bitcoin, i.e., double-counting a commitment — the exact class of equality violation ("sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment or reward") called out as in-scope Critical impact.

### Likelihood Explanation
Any unprivileged staker holding one valid Bitcoin timelock UTXO can trigger this without needing the bond admin, a miner, or another user's key — they simply call `register-for-bond` a second time (for a new/rolled bond index) supplying the identical `tx`/`output-index`/`header`/proof data that was already used and accepted in a prior call. No off-chain trust or unusual conditions are required beyond owning one BTC lockup output.

### Recommendation
Persist consumed outpoints in a durable, contract-wide Clarity map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), and have `validate-l1-lockup` check-and-set against that map (failing with a new `ERR_LOCKUP_ALREADY_CONSUMED` if already present) instead of relying solely on the call-scoped `seen-outpoints` list.

### Proof of Concept
1. Staker locks `X` sats to the correct timelock script on Bitcoin, producing one confirmed output `(txid, output-index)`.
2. Staker calls `register-for-bond` for `bond-index: 0`, supplying a valid Merkle proof for that output; `verify-l1-lockups`/`validate-l1-lockup` accept it and credit `X` sats toward bond 0's total, per the fold logic at [3](#0-2) .
3. After bond 0's rollover window opens (or for a separate `bond-index`), the staker calls `register-for-bond` again, submitting the *same* `tx`/`output-index`/`header`/Merkle proof.
4. Because `seen-outpoints` starts empty on this new call, all `asserts!` in `validate-l1-lockup` pass again, and `X` sats are credited a second time — to a second bond — without any additional BTC ever being locked.
