### Title
`handleERC20Transfer` Missing `onlyRegisteredToken` Guard Allows Operator to Mint/Drain Arbitrary Bridged Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.handleERC20Transfer()` accepts a caller-supplied `_tokenAddress` with only an `onlyOperators` guard. There is no `onlyRegisteredToken` check, unlike the outbound path `_requestERC20Transfer()`. With the default operator threshold of 1, a single malicious operator can call `handleERC20Transfer` with any token address — minting arbitrary tokens (in `modeMintBurn` mode) or draining any ERC20 held by the bridge (in lock/unlock mode) — without a corresponding legitimate cross-chain request.

### Finding Description

The outbound path `_requestERC20Transfer` enforces both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

The inbound path `handleERC20Transfer` enforces only `onlyOperators`: [2](#0-1) 

After passing the nonce check and vote, it unconditionally mints or transfers `_tokenAddress`: [3](#0-2) 

The `BridgeOperator` constructor sets the default threshold to **1** for all vote types, meaning a single operator can unilaterally execute a handle call: [4](#0-3) 

The `onlyRegisteredToken` modifier in `BridgeTokens` checks `registeredTokens[_token] != address(0)`: [5](#0-4) 

This check is entirely absent from `handleERC20Transfer`, creating an asymmetry between the request and handle paths.

### Impact Explanation

- **`modeMintBurn = true`** (child-chain bridge): A malicious operator calls `handleERC20Transfer(txHash, from, attacker, arbitraryHighValueToken, largeAmount, freshNonce, blockNum, "")`. The bridge calls `ERC20Mintable(arbitraryHighValueToken).mint(attacker, largeAmount)`. If the bridge holds minter role on that token (which it must for any registered token in mintBurn mode), the attacker receives freshly minted tokens with no corresponding burn on the parent chain.
- **`modeMintBurn = false`** (parent-chain bridge): The bridge calls `IERC20(arbitraryToken).safeTransfer(attacker, amount)`. Any ERC20 token sitting in the bridge contract (including tokens from legitimate locked deposits) can be drained to an arbitrary address.

This is an unauthorized mint/transfer of bridged assets — directly within the allowed impact gate.

### Likelihood Explanation

The default operator threshold is 1. In a typical service-chain deployment, the bridge deployer is the initial operator and the threshold is never raised unless explicitly configured. A single compromised or malicious operator key is sufficient to trigger this with no other preconditions. The `_voteValueTransfer` vote key is `keccak256(msg.data)`, which includes `_tokenAddress`, so with threshold=1 no other operator needs to agree. [6](#0-5) 

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` (and optionally `onlyUnlockedToken(_tokenAddress)`) to `handleERC20Transfer`, mirroring the outbound path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
    onlyUnlockedToken(_tokenAddress)     // ADD THIS
{
```

Similarly, `handleERC721Transfer` in `BridgeTransferERC721.sol` has the same missing guard and should receive the same fix. [7](#0-6) 

### Proof of Concept

Setup:
- Bridge deployed in `modeMintBurn = true` (child chain)
- `TokenA` (low value) is registered: `registeredTokens[TokenA] = TokenA_counterpart`
- `TokenB` (high value, e.g. WETH-equivalent) is NOT registered but the bridge holds minter role on it (e.g. from a previous registration that was deregistered, or a separate grant)
- Operator threshold = 1 (default)

Attack:
1. Attacker is a registered operator (or compromises one operator key)
2. Attacker calls:
   ```solidity
   bridge.handleERC20Transfer(
       fakeTxHash,   // any unused bytes32
       victim,
       attacker,
       TokenB,       // unregistered high-value token
       1_000_000e18, // large amount
       freshNonce,   // any nonce not yet used
       blockNum,
       ""
   );
   ```
3. `onlyOperators` passes. `_lowerHandleNonceCheck` passes (fresh nonce). `_voteValueTransfer` returns `true` (threshold=1). `_setHandledRequestTxHash` marks the fake hash. Then `ERC20Mintable(TokenB).mint(attacker, 1_000_000e18)` executes.
4. Attacker now holds 1,000,000 TokenB with no corresponding burn on the parent chain. The bridge's accounting is permanently corrupted for TokenB. [8](#0-7)
