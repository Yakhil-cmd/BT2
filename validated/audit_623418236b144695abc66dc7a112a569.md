Session Fixation on GitHub OAuth Callback — Pre-authentication Session ID Is Never Rotated - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` binds a `session[:user_id]` to the `User` record derived from a verified GitHub OAuth identity, but it never rotates the underlying Rack session identifier before doing so. Any session ID an attacker planted before the OAuth handshake remains valid and becomes privileged the moment the victim completes login through that same browser/session.

### Finding Description
The engine uses cookie-backed Rails sessions (`test/dummy/config/initializers/session_store.rb` configures `:cookie_store`), and `Shipit::Authentication#find_current_user` treats `session[:user_id]` as sufficient proof of identity for the entire app: [1](#0-0) .

The only place a `User` identity gets bound to a session is `GithubAuthenticationController#callback`: [2](#0-1) 

Note that `#logout` explicitly calls `reset_session` before clearing the session, and `force_github_authentication` also calls `reset_session` when forcing a re-login: [3](#0-2) [4](#0-3) . But `#callback` — the one path that elevates an anonymous session to an authenticated one — does not. It writes directly into the existing session hash (`session[:user_id] = sign_in_github(auth)`), so whatever session cookie/ID existed prior to the OAuth round-trip is preserved and simply gains privilege.

The trust binding this breaks, expressed as an equality that should hold but doesn't:
`session_id(before OAuth redirect) == session_id(after OAuth callback, now authenticated as victim)`

Framed against the report's bug class (a value trusted/rendered without being covered by the actual verification step): here the *GitHub identity is verified* by OmniAuth (`auth` is populated only after the provider validates the OAuth code), but the *session container* that the app subsequently trusts for all authorization decisions (`find_current_user`, `force_github_authentication`, `current_user.authorized?`) is never re-issued. The verification covers "who this GitHub account is," not "which session ID is allowed to represent that account." An attacker who controls the pre-auth session ID inherits the full trust conferred by the victim's OAuth completion.

### Impact Explanation
This is a classic session-fixation attack, explicitly enumerated as a valid High-severity analog in scope. If an attacker can plant/know a session identifier in the victim's browser (e.g., by getting the victim to visit the Shipit host with a crafted response setting the session cookie, or via a subdomain/related mechanism that can set cookies for the host), and then lure the victim through the `/github/auth/github` OAuth flow, the attacker's known session ID becomes an authenticated session bound to the victim's `User` once the victim completes GitHub login. The attacker can then use that same session ID to act as the victim: trigger deploys/rollbacks, view stack/task state, create `ApiClient` tokens under the victim's identity (`ApiClientsController#create` binds `creator: current_user`), and otherwise access anything gated by `Shipit::Authentication`.

### Likelihood Explanation
Exploitability depends on the attacker's ability to fix a session cookie in the victim's browser before the OAuth callback executes (a well-known technique when the app uses a persistent-name cookie store without ID rotation on login, and no `SameSite`/domain scoping issue is otherwise mitigating it — which is a separate condition to confirm operationally). Given the codebase already demonstrates awareness of session hygiene (explicit `reset_session` on logout and forced re-login), the omission specifically on the login-elevation path is a straightforward root-cause gap rather than a theoretical concern.

### Recommendation
Call `reset_session` (or otherwise regenerate the session ID) in `GithubAuthenticationController#callback` immediately before writing `session[:user_id]`, mirroring the pattern already used in `#logout` and in `force_github_authentication`'s fresh-login branch. Any values needed after reset (e.g. `return_url` from `omniauth.origin`) should be captured into local variables prior to the reset, since `reset_session` clears the session hash.

### Proof of Concept
1. Attacker obtains/fixes a session cookie value `S` for the Shipit host (e.g., by visiting the app first and capturing the `_session` cookie issued before authentication, then getting the victim's browser to adopt cookie `S` via any cookie-setting vector for the host/domain).
2. Attacker sends the victim a link to `Shipit::Engine`'s `/github/auth/github` while the victim's browser carries session cookie `S`.
3. Victim completes the GitHub OAuth consent flow; `GithubAuthenticationController#callback` executes and sets `session[:user_id] = <victim's User#id>` and `session[:authenticated] = true` on the *same* session `S`, without rotating it (`app/controllers/shipit/github_authentication_controller.rb:7-21`).
4. Attacker replays cookie `S` against Shipit; `Shipit::Authentication#find_current_user` resolves `session[:user_id]` to the victim's `User` record (`app/controllers/concerns/shipit/authentication.rb:40-42`), and the attacker now operates the UI/API as the victim (deploy, rollback, create `ApiClient` tokens, etc.).
