Based on my investigation, ocore's address-definition validator (`definition.js`) enforces a global `MAX_COMPLEXITY`/`MAX_OPS` budget for every operator, and for the operators that accept an oracle-address array (`in data feed`, `in merkle`) the code explicitly charges one complexity point per array element (`complexity += arrAddresses.length-1`), which caps how large those arrays can be. However, the `attested` operator does not follow this pattern.

### Title
Unbounded `arrAttestors` array in `attested` address-definition operator allows cheap, unbounded-cost validation - (File: `definition.js`)

### Summary
The `attested` operator in `validateDefinition()` accepts an array of attestor addresses (`arrAttestors`) and only validates that it is non-empty and that each element is a syntactically valid address, but it never bounds the array's length and never charges any extra complexity for it.

### Finding Description
In `validateDefinition()`'s `evaluate()` function, the `case 'attested':` branch does: [1](#0-0) 
It loops over `arrAttestors` calling `isValidAddress()` for every element, but unlike the sibling operators `in data feed` and `in merkle` — which explicitly add `complexity += arrAddresses.length-1` to charge one complexity unit per address in the array — the `attested` operator does not add any complexity for the size of `arrAttestors`: [2](#0-1) [3](#0-2) 

Because the overall per-definition budget is enforced only through `complexity`/`count_ops` counters: [4](#0-3) 
an attacker can craft an address (or asset) definition containing an `attested` clause with a very large `arrAttestors` array while only incurring the single fixed complexity cost of the `attested` op itself, since the array-length check loop runs unconditionally regardless of `MAX_COMPLEXITY`.

Crucially, `validateDefinition()` (and the loop over `arrAttestors`) is **not evaluated only once**. `validateAuthentifiers()` explicitly re-runs `validateDefinition()` on every unit signed by that address, as the code comments note ("we need to re-validate the definition every time... not just the first time"): [5](#0-4) 
So the large-array validation cost is paid again for every single unit an attacker-controlled (or attacker's own) address later posts.

### Impact Explanation
An unprivileged unit poster can define an address (or an asset's issue/transfer condition, since `bAssetCondition` is also accepted for `attested`) using this operator with an arbitrarily large `arrAttestors` array, bounded only by the maximum unit/message size, not by complexity accounting. Every subsequent unit that uses this address as an author (or references the asset condition) forces every validating node to re-run the O(n) `isValidAddress` loop over the full attestor list during `validateAuthentifiers`, imposing disproportionate CPU cost on all full nodes relative to the complexity fee actually charged to the attacker. Repeated broadcasting of units from such an address can be used to degrade validation throughput network-wide — this is the same class of "unbounded array processed without cost accounting" bug described in the report (there, an on-chain `allowedTokens` array that grows without a corresponding gas/cost cap; here, an `arrAttestors` array that grows without a corresponding complexity cap).

### Likelihood Explanation
Likelihood is moderate: constructing such a definition requires no special privilege, just posting an address-definition unit (or asset with `attested`/`transfer_condition`) with a large `arrAttestors` list, followed by repeatedly using that address as an author of new units, forcing repeated re-validation with each unit relayed across the network.

### Recommendation
Charge complexity proportional to `arrAttestors.length` in the `attested` case, mirroring the `in data feed`/`in merkle` operators (`complexity += arrAttestors.length - 1`), and/or impose an explicit maximum length on `arrAttestors` (as is already done for feed name/value/element lengths elsewhere in the same function).

### Proof of Concept
1. Attacker composes an address definition: `['attested', ['ATTESTED_ADDRESS', arrAttestors]]` where `arrAttestors` contains, e.g., 50,000 valid-looking addresses (still within overall unit payload byte limits since a 32-byte address + separators is small compared to typical max message sizes).
2. This definition passes `validateDefinition()` with a total complexity contribution of essentially 1 (no per-element charge), unlike `in data feed`/`in merkle`, which would have driven `complexity` past `MAX_COMPLEXITY` for a comparable-size array. [1](#0-0) 
3. The attacker posts this as their address's definition, then repeatedly posts new units authored by this address.
4. Each such unit triggers `validateAuthentifiers()` → `validateDefinition()` again on the full definition, forcing every validating node to loop over all 50,000 attestor addresses in `isValidAddress()` checks each time, at negligible complexity cost to the attacker. [5](#0-4)
