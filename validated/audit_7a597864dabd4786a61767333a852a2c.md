### Title
Scaled-supply × index `i128` overflow permanently freezes a market — `update_supply_index` panics and every entrypoint accrues first - (File: common/src/rates/index.rs)

### Summary
The analog to the Umee `StandardDeviation` overflow is the unguarded half-up multiply `supplied.mul(env, old_index)` inside `update_supply_index`. Where Umee squared an attacker-submitted exchange rate, here the protocol multiplies total scaled supply shares by the supply index; when `supplied * index / RAY` exceeds `i128::MAX`, `mul_div_half_up` widens to `I256`, fails `to_i128()`, and panics with `GenericError::MathOverflow`. Because index accrual runs before every state-changing verb, once the product crosses the representable ceiling the market can never accrue again and all user funds in it are frozen.

### Finding Description
`update_supply_index` in `common/src/rates/index.rs` computes the total supplied value with an exact (non-saturating) multiply:

```rust
// common/src/rates/index.rs:34
let total_supplied_value = supplied.mul(env, old_index);
```

`Ray::mul` resolves to `fp_core::mul_div_half_up`, which returns `MathOverflow` when `x * y / d` does not fit `i128` (`common/src/math/fp_core.rs:122-143`). The saturating variant `mul_div_floor_saturating` is used later in the same function (line 41) for the reward division, but the earlier `supplied * old_index` product is unsaturated.

The freeze is proven by the protocol's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-356`): after the market's `supplied * borrow_index`-driven value crosses the RAY ceiling, `update_indexes` reverts with `MATH_OVERFLOW`, and both `withdraw` and `repay` fail identically — "no repay, no withdraw, no liquidation". The `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` clamps do not protect this path because the panic fires on the value product, before any index cap can engage.

An unprivileged attacker reaches this through `supply`/`borrow` on the controller (raising `supplied` shares up to the market cap, which `require_cap_within_asset_domain` allows up to `i128::MAX / RAY` per asset) and then by calling `update_indexes` after interest accrual — no admin, oracle, or privileged role is involved in the trigger.

### Impact Explanation
Permanent freezing of funds. Once `scaled_to_original`/`update_supply_index` overflows, every verb accrues first and panics: suppliers cannot withdraw, borrowers cannot repay, liquidations cannot run, and `clean_bad_debt`/`recapitalize` — which also touch the cache — are blocked for that market book. The funds are not lost to a theft but are unrecoverable absent a code upgrade.

### Likelihood Explanation
Medium. The trigger requires `supplied * index / RAY > i128::MAX`, i.e. a market book within ~170× of the value ceiling while still growing — reachable only on a near-cap market that sustains high utilization so indexes keep compounding. A single attacker controlling the dominant supply position can hold the market at the cap and force continued accrual via permissionless `update_indexes`, but they must commit capital up to the cap and keep utilization high; the overflow cannot be triggered cheaply on a small or idle market. The cost is capital lockup, not a bypass — consistent with the report's "high difficulty" rating.

### Recommendation
- Make the value product saturating or cap-aware: compute `total_supplied_value` via `mul_div_floor_saturating`, or clamp `supplied`/`index` inputs to a domain where the product provably fits `i128` before multiplying.
- Alternatively, treat the `MathOverflow` inside accrual as a signal to freeze only the index growth (skip the reward step) rather than aborting the whole call, so withdraw/repay paths remain live.
- Add the certora-observed gap (`update_supply_index_capped` notes the panic is pruned by `assume(false)`) to the runtime invariants: assert `supplied * index / RAY <= i128::MAX` at cap-validation time (`require_cap_within_asset_domain`) so listings cannot admit a book that can outgrow the arithmetic domain.

### Proof of Concept
```rust
// Reproduces the freeze in tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization

// Advance time; each update_indexes accrues. Eventually supplied * index / RAY > i128::MAX:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
// Market is frozen permanently:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// MAX_BORROW_INDEX_RAY never engaged — panic precedes the cap check.
```

Root cause is `supplied.mul(env, old_index)` at `common/src/rates/index.rs:34` panicking via `mul_div_half_up` (`common/src/math/fp_core.rs:108-118`) once the scaled-supply value exceeds the `i128` domain, and accrual running first inside every controller verb.
