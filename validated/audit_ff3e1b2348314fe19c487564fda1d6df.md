### Title
Unauthenticated cross-repository stack status disclosure via `MergeStatusController#check` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController` explicitly skips authentication for `check` and `show`, but only `show` enforces a login gate (`current_user.logged_in?`) before revealing stack data. `check` has no equivalent guard, so `format.json { render(json: { stack_status: }) }` returns the computed `stack_status` for any stack resolvable from an attacker-supplied `referrer` (or `stack_id`) to a fully unauthenticated caller.

### Finding Description
The broken binding: `skip_authentication only: %i[check show]` is claimed to imply `authorized?`/login state is irrelevant for both actions, but in practice `show` re-establishes the equality `response_body == f(current_user.logged_in?)` via `return render('logged_out') unless current_user.logged_in?` [1](#0-0) , while `check` has no such check at all [2](#0-1) . This breaks the intended equality `authorized_or_logged_in? == response_carries_stack_status`: for `check`, the right side is always true regardless of the left side.

`stack` is resolved purely from request params, with no ownership or session check: if `stack_id` is absent, it is looked up from `referrer_parser.repo_owner` / `repo_name` (parsed from an arbitrary `https://github.com/<owner>/<repo>/pull/<n>` string in the `referrer` param) and optional `branch`, defaulting to the `production` environment [3](#0-2) . `stack_status` is then `stack.merge_status(backlog_leniency_factor: 1.0)` [4](#0-3) , exposed via `check`'s `format.json` branch to any caller since the class-level `skip_authentication only: %i[check show]` bypasses `force_github_authentication` for this action [5](#0-4) .

Attacker request: `GET /merge_status.json?referrer=https://github.com/<victim-owner>/<victim-repo>/pull/1` with no session cookie, no `branch` param (defaults to `production`). Response: `200 {"stack_status": "<state>"}` for any repository/stack tracked by the Shipit instance, disclosing whether the target's production stack is `success`, `faulty`, `locked`, `pending`, etc.

### Impact Explanation
Any unauthenticated internet user can enumerate the health/queue state of any repository's Shipit stack (locked, failing CI, queued, etc.) without a session, API token, or GitHub team membership — a cross-tenant unauthenticated read of stack state. This matches the "High" category: "unauthenticated read of stack state." It is fully repeatable against arbitrary repositories/stacks known to the attacker (repo names are typically public/guessable on GitHub), with no rate limiting or additional guard, though it does not itself allow mutation, deploy, or credential exfiltration.

### Likelihood Explanation
No preconditions beyond a target repository/stack existing in the Shipit instance and the attacker knowing (or guessing) its owner/name — trivial for any public GitHub repo. No Shipit session, secret, or GitHub credential is required; the request is a single unauthenticated GET. This is low-cost, high-feasibility, and trivially repeatable/scriptable across many repositories.

### Recommendation
Add the same login/authorization guard used in `show` to `check` (e.g., `render(json: {}, status: :unauthorized) unless current_user.logged_in?` before computing `stack_status`), or remove `check` from `skip_authentication` and instead perform an explicit lightweight authorization check that does not require a full GitHub App session but still validates the caller is permitted to view the specific stack.

### Proof of Concept
Add to `test/controllers/merge_status_controller_test.rb` style suite (functional test, no live GitHub, no session cookie):

```ruby
test "GET check as JSON without a session discloses stack_status" do
  session.delete(:user_id) # unauthenticated, mirrors "GET anonymous show" tests in file
  get :check, params: { referrer: 'https://github.com/Shopify/shipit-engine/pull/42', branch: 'master' }, format: :json
  assert_response :ok
  body = JSON.parse(response.body)
  assert body.key?('stack_status')
end
```
Assert the binding both before and after: before the request, `session[:user_id]` is nil and `current_user.logged_in?` is `false`; after the request, `response.status == 200` and `body['stack_status']` is present — i.e., `authorized?`/login state (`false`) does not match `response_carries_stack_status` (`true`), confirming the divergence. Compare against the existing `show` tests, which assert that an anonymous request instead renders a "please log in" message rather than any `stack_status`-bearing payload [6](#0-5) .
