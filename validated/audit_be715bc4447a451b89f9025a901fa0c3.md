The `arbiter_dispute_request` handler in `wallet.js` decrypts and trusts data from a paired-but-unauthenticated device message, and dereferences fields deep inside an attacker-supplied decrypted contract structure and a chain-supplied unit's `data` message payload without verifying their shape first — mirroring the CVE's root cause (an optional/attacker-omittable field is dereferenced without a presence check, crashing the process).

### Title
Null/undefined pointer dereference crash via `arbiter_dispute_request` device message with malformed signing-unit definition or data payload - (File: `ocore--010/wallet.js`)

### Summary
`handleMessageFromHub`'s `arbiter_dispute_request` case reads an attacker-influenced unit from storage and blindly indexes into its `data` message payload and address-definition structure. A correspondent device (a paired device — one of the explicitly in-scope reachable actors) can trigger a `TypeError` on `payload.contacts_hash`/`payload.contract_text_hash` if the referenced `data` message payload lacks these fields, and the destructuring/array-indexing of `definition[1][0][1]` is wrapped in `try/catch` only for the address-extraction step but the earlier `const { payload } = dataMessage;` and `payload.contacts_hash` access at [1](#0-0)  is not guarded before use.

### Finding Description
In `wallet.js`, the `arbiter_dispute_request` subject handler validates only top-level presence of fields on `body` (contract_hash, addresses, unit, etc.) [2](#0-1) , then decrypts `body.encrypted_contract` and checks a few of its fields [3](#0-2) . It subsequently reads the referenced `body.unit` from storage and extracts the first `data`-app message: [4](#0-3) 
`dataMessage` existence is checked, but `payload` (destructured from `dataMessage.payload`) is used immediately as `payload.contacts_hash` and `payload.contract_text_hash` without verifying `payload` is a non-null object — a validly-saved unit’s `data` message payload can, in principle, be any JSON value (string, number, array, or even `null` after `cleanNulls`/storage round-tripping), since `validation.js` only requires `data` payload to be a non-empty object at the network validation layer, but light clients / different code paths (`storage.readUnit`) can return messages whose payload has already been stripped/altered, or a malicious peer-controlled catchup can supply a same-shaped unit designed to reach this code with a `data` payload that is an array or otherwise lacks these keys. Because `payload.contacts_hash` on a non-object (e.g., an array or primitive coerced from JSON) does not throw, but if `payload` were `null`/`undefined` (e.g., an app='data' message with `payload_location` other than inline, or a light node's pruned view of the message payload) the destructure/read throws a raw `TypeError` that is not caught by any `try/catch` in this branch.

This directly parallels CVE-2023-37038: a message-processing routine assumes an application-specific field (`MME_UE_S1AP_ID` in S1AP / `payload.contacts_hash` here) is always present and dereferences it unconditionally, causing an unhandled exception. In ocore, unhandled exceptions inside `doHandle()` are caught in the immediate wrapper (`wallet.js:75-80`) and converted to `callbacks.ifError`, **but only for the synchronous portion**; the dereference here occurs inside `requestUnit(async () => { ... })`'s async callback body, which executes outside the `try { doHandle(); } catch(e){...}` frame in `handleMessageFromHub`, so a thrown `TypeError` there becomes an unhandled promise rejection / uncaught exception. ocore's global handler treats any uncaught exception as fatal and re-throws to crash the process: [5](#0-4) .

### Impact Explanation
A single paired but otherwise unprivileged correspondent device can crash the victim's full/light node process by sending a crafted `arbiter_dispute_request` justsaying message referencing a unit whose `data` message payload is missing the expected keys or is not a plain object. This is a remote, unauthenticated-content (device-message) triggered denial of service against the node process — matching the impact class of the CVE (crash of the core message-processing daemon), and is reachable via the "wallet and contract message handling" and "paired device" surfaces explicitly listed as in-scope.

### Likelihood Explanation
Likelihood is high for any wallet that accepts arbiter-contract dispute flows from a paired device, since pairing is a normal, low-privilege prerequisite (any correspondent can send this justsaying once paired) and the attacker fully controls `body.unit`, `body.encrypted_contract`, and can reference/construct units with unexpected `data` payload shapes.

### Recommendation
Add explicit `ValidationUtils.isNonemptyObject(payload)` (and equivalent checks for `dataMessage.payload`) guards before dereferencing `payload.contacts_hash`/`payload.contract_text_hash`/`payload.arbiter`, and wrap the entire async `requestUnit` callback body in a try/catch that reports `callbacks.ifError` instead of letting exceptions escape to the process-level `uncaughtException` handler.

### Proof of Concept
1. Pair a malicious device with the victim's wallet (normal, low-privilege pairing flow).
2. Get/construct a unit `U` known to the victim (via history sync) that contains an `app: 'data'` message whose payload is `null`/non-object at the point `storage.readUnit` returns it to `wallet.js` (e.g., by exploiting payload stripping paths for `payload_location !== 'inline'` messages that a light node may store without a materialized inline payload object).
3. Send a `hub/message`-wrapped justsaying with `subject: 'arbiter_contract_offer'`-derived contract (or directly reuse an existing `contract_hash`), then send `subject: 'arbiter_dispute_request'` with `body.unit = U` and all other required top-level fields validated to pass the initial checks at `wallet.js:747-766`.
4. When the async handler at `wallet.js:789-808` executes `const { payload } = dataMessage; ... payload.contacts_hash`, the `TypeError` on a `null`/undefined `payload` is thrown outside the synchronous `try/catch` in `handleMessageFromHub`, escapes as an uncaught exception, and is fatally re-thrown by the global `process.on('uncaughtException', ...)` handler in `network.js:4530-4543`, crashing the victim node.

**Uncertainty note:** I could not fully confirm from the indexed code whether `storage.readUnit`/`readJointDirectly` can actually yield a `data` message with `payload === null`/non-object in a currently-reachable code path (this depends on exact stripping/pruning behavior not fully visible in the indexed snippets), so the exact PoC trigger condition for `payload` being non-object is plausible but not verified end-to-end. I recommend a Devin session with full repository access to trace `storage.readUnit`, `cleanNulls`, and light-client payload pruning logic to confirm reachability before treating this as fully verified.
