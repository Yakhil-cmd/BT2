### Title
CCMenu API endpoint bypasses stack-scoping, letting a stack-scoped `ApiClient` token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` accessor used elsewhere in the API to enforce token/stack scoping, replacing it with an unscoped lookup. This breaks the trust binding "the stack a token authorizes" == "the stack the request actually touches," letting any valid `ApiClient` token — even one restricted to a single stack — read CCMenu status (`read:stack`) for every stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting accessor: [1](#0-0) 
`stacks` is restricted to `current_api_client.stack_id` when the authenticated `ApiClient` is stack-scoped, and `stack` resolves `params[:stack_id]` only within that restricted relation, via `Stack.from_param!`-style scoping (`stacks.from_param!`).

`CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model rather than through `current_api_client`'s scoped `stacks` relation. The controller only enforces the `read:stack` **permission** category via `require_permission :read, :stack`: [3](#0-2) 
but `check_permissions!` only validates that the client's `permissions` array contains `"read:stack"` — it does not check `stack_id` at all: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id (the stack the token authorizes)` == `stack (the stack the request touches)` — is violated: the controller derives `stack` from attacker-supplied `params[:stack_id]` unconditionally, independent of `current_api_client.stack_id`.

Authentication for this controller also accepts a `token` request/query parameter directly (`ApiClient.authenticate(params[:token])`): [5](#0-4) 
This is the token generated for narrowly-scoped read-only CCMenu clients, e.g. via `CCMenuUrlController`, which explicitly creates a `read:stack`-only, single-stack-scoped `ApiClient`: [6](#0-5) 
Such a token is meant to be shared externally (embedded in a CCMenu/CCTray URL for a single project's dashboard widget) precisely because it is supposed to be scoped to one stack.

### Impact Explanation
This is an unauthenticated-by-design token whose entire security model is "read-only, single stack," intended for third-party CI dashboard tools. Because `stack` bypasses `current_api_client`'s stack restriction, holding one such stack-scoped CCMenu token (which is routinely embedded in external tooling/URLs and thus more likely to leak) grants unauthorized read access to task streams/build status/deploy state for **every** stack managed by the Shipit instance — not just the one it was issued for. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity impact category: a credential scoped to reveal state for repo/stack A can be used to read state for repo/stack B, crossing the stack-authorization boundary the token system was designed to enforce.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token with the `read:stack` permission (no admin/team membership needed, and CCMenu tokens are specifically designed to be embedded in external URLs/tools, making them more exposed than typical Basic-Auth API credentials). The attacker needs to know or guess/enumerate another stack's `to_param` (slug), which is often predictable/public (`owner/repo/environment/branch`-derived). No additional privilege or session is required beyond the leaked/obtained token.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation exactly like `BaseController#stack` does (i.e. `stacks.from_param!(params[:stack_id])`), so a stack-scoped `ApiClient`'s `stack_id` is enforced consistently across all API controllers, including CCMenu.

### Proof of Concept
1. Create a stack-scoped CCMenu `ApiClient` for `stack_A` (as `CCMenuUrlController#client` does): `permissions: ['read:stack']`, `stack: stack_A`.
2. Obtain that client's `authentication_token`.
3. Send `GET /api/stacks/:stack_B_param/ccmenu.xml?token=<stack_A's token>` where `stack_B` is a different stack the client was never scoped to.
4. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` relation, the request succeeds and returns `stack_B`'s build/deploy status, even though the token's `stack_id` is `stack_A.id` — demonstrating the token-authorized-stack vs. stack-touched mismatch.
