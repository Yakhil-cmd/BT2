### Title
Stack-scoped API token can read build/deploy status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to bypass the stack-scoping enforced by `Shipit::Api::BaseController`, so an `ApiClient` token that is supposed to be authorized only for a single stack can be used to read the CCMenu (deploy status/build status) of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups through the `stacks` helper, which restricts the visible `Stack` set to the one referenced by `current_api_client.stack_id` when the API client is scoped to a stack: [1](#0-0) 

Every other API controller (e.g. `DeploysController`) relies on this scoped `stack` method, so a `read:stack`-only token that is bound to a specific `stack_id` (see the `here_come_the_walrus` fixture) can only resolve stacks it is authorized for: [2](#0-1) 

However, `CCMenuController` defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping method inherited from `BaseController`: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`; it never checks whether the specific stack being requested matches `current_api_client.stack_id`: [4](#0-3) 

This breaks the equality that should hold: `stack a token authorizes == stack it touches`. Before the (hypothetical) attacker-controlled request, `here_come_the_walrus`'s token is authorized only for the `shipit` stack (`stack_id` set in the fixture) and, through `stacks`, can only resolve that stack. After the request to `CCMenuController#show` with a different `stack_id` param, the same token resolves and returns data for an arbitrary stack, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

Additionally, `CCMenuController` allows the token to be supplied as a plain query-string parameter (`params[:token]`), which is designed for use in third-party CI dashboard tools/URLs and is more likely to leak/be embedded in bookmarks, third-party tools, or logs than an `Authorization` header: [5](#0-4) [6](#0-5) 

### Impact Explanation
This qualifies as "High - unauthenticated/unauthorized read of stack state, task streams or deploy output": a token deliberately scoped to a single stack (e.g., generated and handed out for a specific project's CI-status badge via `CCMenuUrlController`) can be used to read the last deploy/build status, running state, and lock state of any other stack in the Shipit instance, including ones the token holder was never granted access to. This crosses a repository/stack authorization boundary using a credential that was explicitly restricted at creation time.

### Likelihood Explanation
Likelihood is high: exploitation requires no special access beyond possession of any valid stack-scoped CCMenu token (which are routinely generated and distributed as URLs by `CCMenuUrlController#fetch` for embedding in third-party CI-status tools) and simply changing the `stack_id` path/query parameter of the request.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, scoped lookup instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures that when `current_api_client.stack_id` is set, only that stack can be resolved, consistent with how every other API controller enforces stack-level authorization.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack `shipit` with only `read:stack` permission (mirrors `here_come_the_walrus` fixture), e.g. via `CCMenuUrlController#fetch`, which creates such a client bound to `permissions: %w[read:stack]` and a specific stack: [7](#0-6) 
2. Take the resulting `token` and issue a GET request to `/api/<other_owner>/<other_repo>/<other_environment>/ccmenu.xml?token=<token>` for a stack the client was never scoped to.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is valid), `require_permission :read, :stack` passes (the token does carry `read:stack`), and `CCMenuController#stack` resolves the unrelated stack via `Stack.from_param!` (bypassing `stacks`), returning that stack's deploy/build status in the XML response — data the token was never authorized to view.
