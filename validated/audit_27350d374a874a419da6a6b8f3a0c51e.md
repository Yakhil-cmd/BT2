### Title
Github `status` webhook writes to commits in any repository/stack sharing a SHA, bypassing repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` purely by `sha`, with no restriction to the repository named in the webhook payload. Every other webhook handler that mutates state (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) goes through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any records. `StatusHandler` skips that scoping entirely, so the binding "the repository whose GitHub App/organization signed this webhook" == "the repository whose commit status gets written" is not enforced.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook using the webhook secret of `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the same payload's `repository.owner.login` field: [1](#0-0) 

That verification only proves the request was signed by the App/organization that owns the repository named in the payload. It says nothing about which `Commit` records in the Shipit database the handler is allowed to touch.

`StatusHandler#process`, however, ignores the `repository` field of the payload completely and matches on `sha` alone, against the entire `Commit` table (all stacks, all repositories): [2](#0-1) 

Compare this to the correctly-scoped handlers, which resolve the specific repository from the payload before querying: [3](#0-2) [4](#0-3) [5](#0-4) 

Because git commit SHAs are content-addressed (derived from tree, parent, author/committer, timestamps and message), an attacker who can trigger a legitimately-signed `status` webhook for *any* repository tracked by the same Shipit instance (e.g. their own repo, or a fork of a public target repo, both of which share the App installation's webhook secret for that organization) can craft a commit whose SHA matches an existing commit already tracked under a *different, unrelated* stack (their own fork of the victim repository naturally reproduces identical SHAs for identical history). They then have GitHub send (or, if the attacker controls a repo, cause) a `status` event referencing that SHA with an arbitrary `state`/`description`/`context`. `StatusHandler` will happily attach that status to every `Commit` row across the Shipit install sharing that SHA, including the commit belonging to the victim's stack: [6](#0-5) 

### Impact Explanation
Commit statuses drive Shipit's deploy/merge gating logic (`Commit#deployable?`, `MergeRequest#reject_unless_mergeable!`/`any_status_checks_missing?`/`any_status_checks_failed?`), which rely on `Status`/`CheckRun` records attached to a commit: [7](#0-6) [8](#0-7) 

By forging a `success` status for a SHA shared with a victim stack's commit, an attacker can make a commit appear CI-green (or CI-red to block a competitor's deploy) in a stack they have no legitimate access to, potentially enabling an unauthorized deploy or a merge-queue admission that should have been blocked. This is a cross-repository write of state that gates deploys/merges, matching the "unauthorized deploy" / "cross-repository writes" High/Critical impact bar.

### Likelihood Explanation
The attacker needs: (1) the ability to have a `status` webhook legitimately signed for some repository under an organization managed by the same Shipit instance (their own repo, or any repo they can push commits/CI statuses to within that org's installation), and (2) a commit whose SHA collides with one already tracked by the target stack. For public target repositories this is straightforward — commit SHAs are deterministic and reproducible by forking/replaying the exact same tree/parents/author/committer/timestamps/message, so an attacker can trivially manufacture a commit with an identical SHA in their own fork and then get GitHub (or their own CI) to emit a `status` webhook for it. No credentials belonging to Shipit or the victim are required beyond an ordinary GitHub account with a repo in the same GitHub App installation.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`), not a bare `Commit.where(sha: ...)` across the whole instance. For example, replace the global lookup with `stacks.flat_map(&:commits).where(sha: params.sha)` (or a `Commit.joins(:stack).where(stack: { repository_id: repository.id }, sha: params.sha)`), so a status webhook can only ever update commits under the repository it was actually signed for.

### Proof of Concept
1. Shipit instance manages two stacks: `victim-org/app` (target) and `attacker-org/app-fork` (a public fork of `victim-org/app`, or any repo under an org where the attacker has push/CI access and which shares a GitHub App installation with this Shipit instance).
2. Attacker forks `victim-org/app` and creates/pushes a commit with the exact same tree, parent, author, committer, message and timestamps as an existing commit `C` in `victim-org/app`'s tracked stack (reproducing the identical SHA `S`).
3. Attacker triggers (via their own CI, or a legitimately signed `status` API call/webhook they control for `attacker-org/app-fork`) a `status` event with `sha: S`, `state: "success"`, `context: "ci/required-check"`.
4. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s webhook secret and succeeds (it is a legitimately signed event for a repo the attacker controls).
5. `StatusHandler#process` executes `Commit.where(sha: S)`, which matches commit `C` in `victim-org/app`'s stack (not scoped to `attacker-org`), and calls `create_status_from_github!`, marking `C` as CI-passing in the victim's stack even though no such status was ever reported for `victim-org/app`.
6. This forged success status can satisfy `Commit#deployable?`/merge-queue CI requirements for the victim stack, enabling deploys/merges that should not have been allowed.
