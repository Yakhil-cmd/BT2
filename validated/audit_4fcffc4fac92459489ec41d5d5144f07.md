## Finding: Webhook signature is verified against a GitHub App keyed by `repository.owner.login`, but the write path uses `repository.full_name` — the two fields are never bound together

### Title
Webhook signature verification authenticates the organization named in `repository.owner.login`, while stack lookup/writes trust the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, then verifies the HMAC over the raw body using that org's secret. [1](#0-0)  Once the signature check passes, the actual write-side handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using `repository.full_name`, a completely different field from the one used to pick the verifying secret. [2](#0-1) [3](#0-2) 

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` `github:` keyed by org, as documented in `docs/setup.md`), each configured GitHub organization has its own `webhook_secret`. [4](#0-3)  `GitHubApp#verify_webhook_signature` performs a straightforward HMAC-SHA1 comparison of the raw POST body against the secret belonging to whichever organization was selected. [5](#0-4)  That selection is made by `WebhooksController#repository_owner`, which simply reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) straight out of the untrusted, attacker-suppliable JSON payload before any signature has been validated. [6](#0-5) 

Because a valid HMAC signature only proves "this body was signed by the secret of the org named in `repository.owner.login`," it proves nothing about the value of `repository.full_name`, which is the field actually used downstream to look up the `Repository`/`Stack` to act on: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` and `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)`. [2](#0-1)  `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack with the claimed branch. [3](#0-2) 

This is the same trust-binding class of bug as the reported issue: the value that was verified (`repository.owner.login`, checked against a signature) is not the value that is acted upon (`repository.full_name`, used to select the repository to write to). An attacker who controls (or has been granted, e.g., as an app installer/admin on) their *own* GitHub organization's Shipit App installation knows that organization's `webhook_secret` (or can otherwise produce a validly-signed payload for their own org, e.g. via a real webhook delivery from a repo they own in that org) can set `repository.owner.login` to their own org (so the signature check passes using their own secret) while setting `repository.full_name` to `some-other-org/some-other-repo` that is configured as a Shipit stack under a different, victim organization. The webhook signature verification will succeed (it only checks the org that they legitimately control), yet the handler will act on the victim's repository/stack, e.g. triggering `sync_github`, injecting commits/statuses, or (via other handlers such as `MembershipHandler`) manipulating team membership records tied to a different org's stacks.

### Impact Explanation
This breaks the intended equality `organization authenticated by signature == repository written by handlers`. In the default single-org configuration, `repository.owner.login` and `repository.full_name`'s owner segment normally coincide, masking the issue. But per the documented multi-org support, the two are independent lookups, and the controller never cross-checks that the org used to verify the signature actually owns the repository named in the payload. The practical impact is triggering unauthorized `GithubSyncJob`/`sync_github` calls, and other webhook-driven side effects (e.g., membership/team changes in `MembershipHandler`, PR-label driven review-stack behavior) against a target organization's repository, without possessing that target organization's `webhook_secret`. This maps to a cross-repository write / unauthorized action on a stack, crossing an organizational trust boundary that the signature check is supposed to enforce.

### Likelihood Explanation
The precondition is that the shipit instance is configured with multiple GitHub organizations (a documented, supported configuration) and that the attacker has legitimate control over at least one of those organizations' webhook secret (i.e., they administer their own GitHub org/App installation that is also configured on the same Shipit instance). Given that precondition, forging the JSON body's `repository.full_name` field is trivial since HMAC verification never inspects it for a match to the signing org. No session, API token, or the victim org's secret is required.

### Recommendation
After signature verification passes, cross-validate that `repository.owner.login` (or `organization.login`) — the identity whose secret verified the signature — matches the owner portion of `repository.full_name` before dispatching to handlers. Reject (422) any payload where these disagree.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-attacker` (attacker-controlled webhook secret, known to attacker) and `org-victim` (has a Shipit stack for `org-victim/target-repo`).
2. Attacker crafts a `push` webhook JSON body:
   - `repository.owner.login = "org-attacker"`
   - `repository.full_name = "org-victim/target-repo"`
   - `ref = "refs/heads/main"`, `after = "<attacker-chosen sha>"`
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-attacker's webhook_secret, body)`.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "org-attacker")`, verifies successfully with the attacker's own secret. [7](#0-6) 
6. `PushHandler` resolves `repository_name` from `repository.full_name` = `"org-victim/target-repo"`, finds the victim's stack, and calls `sync_github(expected_head_sha: ...)` on it — a write to a repository/org the attacker never proved control over. [3](#0-2)

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
