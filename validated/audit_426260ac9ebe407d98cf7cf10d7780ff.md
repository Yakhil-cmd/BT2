## Title
AA can receive an indivisible (NFT-like) asset as balance, but can never send it back — permanently locked funds - (File: aa_composer.js)

## Summary
An Autonomous Agent (AA) address can receive payments in a `fixed_denominations` asset (ocore's indivisible-asset type, functionally analogous to an NFT: a single non-fungible unit of a given denomination) exactly like it can receive `base` bytes or divisible assets. The trigger balance is credited normally, but `aa_composer.js`'s response-composition logic (`sendUnit`) unconditionally strips out any outgoing `payment` message that uses a `fixed_denominations` asset before the response unit is built and sent. This is the exact analog of the OpenQ report: the AA "vault" can accept the NFT-equivalent deposit, but the AA logic has no way to ever pay it back out, permanently freezing it.

## Finding Description
When any unit pays a fixed-denomination (indivisible) asset to an AA address, `getTrigger()` records it in `trigger.outputs[asset]` with no restriction on asset type [1](#0-0) , and `validateAATrigger()` in `validation.js` likewise does not filter by asset type when detecting AA triggers [2](#0-1) . `updateInitialAABalances()` then credits the AA's `aa_balances` table for that asset regardless of whether it is divisible or fixed-denomination [3](#0-2) .

However, when the AA script attempts to respond with a `payment` message that spends this same balance (e.g., forwarding the "NFT" to a claimant address), `sendUnit()`'s per-message asset processing explicitly skips completion for `fixed_denominations` assets ("will skip it later") [4](#0-3) , and later unconditionally filters ALL such payment messages out of the final message list before the response unit is constructed:
```
messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });
``` [5](#0-4) 

If this filtered-out payment was the only message (or the only one with outputs), the code proceeds to `handleSuccessfulEmptyResponseUnit(null)` — i.e., it treats the trigger as successfully handled, executes state updates, and silently "eats" the asset instead of bouncing with an error [5](#0-4) . There is no oscript-level or core-level path by which an AA can ever construct a valid outgoing `payment` message for a `fixed_denominations` asset — this stripping happens on every single AA response, always, for any AA definition. Contrast this with private assets, which cause an explicit bounce (`"sending private asset from AA"`) rather than silent success [6](#0-5) .

## Impact Explanation
Once an AA has received a `fixed_denominations` asset (any indivisible/NFT-like asset), those funds are permanently and irrecoverably locked at the AA address. The AA's internal balance bookkeeping (`aa_balances`) still reflects the deposit, and the AA author may write logic intending to forward, refund, or pay out that asset (e.g., a bounty/escrow AA that is deposited an indivisible collectible as a reward), but the core response-composition code silently drops every such payment message before the unit is built. This matches the "AA fund loss or freezing" impact category: any AA-based application (vaults, escrows, bounty/reward AAs, marketplaces) that accepts indivisible assets as deposits will unconditionally freeze them forever, with no error surfaced to the depositor or the AA author at deposit time.

## Likelihood Explanation
This is trivially and deterministically reachable by any unprivileged unit poster: simply send a payment of a `fixed_denominations` asset to any AA address that is not designed to explicitly reject such deposits (most existing AA templates do not special-case fixed-denomination assets, since oscript documentation and templates focus on divisible/base assets). No special privileges, timing, or race conditions are required — the bug fires on every attempt by any AA to pay out a fixed-denomination asset, not just an edge case.

## Recommendation
Either:
1. Reject fixed-denomination asset deposits to AA addresses at the trigger/validation level (`validateAATrigger` in `validation.js`, or `getTrigger`/`updateInitialAABalances` in `aa_composer.js`), bouncing the triggering unit with a clear error instead of silently crediting a balance that can never be spent; or
2. Implement genuine support for indivisible-asset outputs in AA response composition (`sendUnit`/`completePaymentPayload` in `aa_composer.js`) so that AAs can actually construct and sign valid payment messages for `fixed_denominations` assets, mirroring how `indivisible_asset.js` composes such payments for regular wallets.

## Proof of Concept
1. Deploy any AA whose response includes a `payment` message spending `trigger.output[[asset=<indivisible_asset>]]` back to `trigger.address` (e.g., a simple "echo the deposit" AA).
2. Define (or use an existing) asset with `fixed_denominations: true`.
3. Post a unit paying units of that indivisible asset to the AA address, invoking the AA.
4. Observe in `aa_composer.js`:
   - `updateInitialAABalances` credits the AA's balance for the fixed-denomination asset [7](#0-6) .
   - `sendUnit` skips completing the outgoing payment message for that asset and later filters it out entirely [4](#0-3) , [5](#0-4) .
   - If it was the only message, `handleSuccessfulEmptyResponseUnit(null)` fires — the trigger unit is accepted as successfully handled, no bounce/error is raised, and the deposited indivisible-asset balance remains stuck at the AA address with no way to withdraw it in any subsequent trigger.
