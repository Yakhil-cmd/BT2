### Title
Webhook signature verification keys off `repository.owner.login` while event routing keys off `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate an inbound webhook against using `repository.owner.login` (falling back to `organization.login`), but the handler layer that actually resolves which `Stack`/`Repository` the event acts on uses a *different* field from the same JSON body: `repository.full_name`. Because the HMAC only proves "this body was signed with organization X's secret," not "the `repository.full_name` in this body belongs to organization X," a party who knows one onboarded organization's `webhook_secret` on a multi-tenant Shipit instance can forge a webhook body whose `repository.owner.login` names their own organization (to pass signature verification) while `repository.full_name` names a completely different, victim-tracked repository (to control what gets mutated).

### Finding Description
`verify_signature` computes the signing organization purely from payload content, independent of the actual signature check target used downstream: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization app config (and its `webhook_secret`) purely from `repository.owner.login` / `organization.login`, and `verify_webhook_signature` only proves the raw body was HMAC-signed with *that* organization's secret: [3](#0-2) 

Once the signature check passes, `create` dispatches the entire raw payload to the matching event handler: [4](#0-3) 

Every repository-scoped handler (`PushHandler`, `StatusHandler`, pull-request handlers, `CheckSuiteHandler`, etc.) inherits `Handler#stacks`, which resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, with no cross-check against the field used for signature routing: [5](#0-4) 

`PushHandler` uses that repository binding to trigger a GitHub sync on the resolved stack: [6](#0-5) 

`StatusHandler` writes a commit status straight from attacker-controlled `sha`/`state`/`context` fields onto any `Commit` matching that SHA, regardless of which organization it belongs to: [7](#0-6) 

This breaks the intended binding **organization that authenticated (`repository.owner.login`/`organization.login`, used to pick the `webhook_secret`) == repository that is written (`repository.full_name`, used to pick the `Stack`/`Commit` mutated)**. Nothing in `WebhooksController` or `Handler` enforces that these two values refer to the same repository/organization; they are two independent reads of the same untrusted, attacker-supplied JSON body.

### Impact Explanation
On a Shipit deployment tracking repositories across multiple GitHub organizations (a supported, documented configuration since `Shipit.github(organization:)` is looked up per-org), anyone who knows the `webhook_secret` configured for *any one* onboarded organization can forge signed events that mutate state belonging to *any other* onboarded organization's stacks: forcing `GithubSyncJob` runs, writing arbitrary commit statuses (`StatusHandler`) that can flip a commit's deployability/CI gating, or driving pull-request/check-suite side effects tied to review stacks. Forged commit statuses in particular can be used to make an otherwise-blocked commit appear "success" for status checks Shipit gates deploys on, contributing to an unauthorized deploy path. This is a cross-repository / cross-organization write achieved purely by exploiting a mismatch between the field used for authentication and the field used for authorization of the write target — matching the "organization that authenticated vs. repository that is written" trust binding.

### Likelihood Explanation
Requires only knowledge of one organization's webhook secret in a multi-org Shipit instance (no access to the victim repository, no Shipit session, no GitHub App key, no privileged Shipit account) and the ability to POST a crafted, correctly-HMAC-signed JSON body to the public `/webhooks` endpoint (which accepts unauthenticated GitHub-style POSTs by design, per `WebhooksController#create`). No other in-engine defense checks that `repository.owner.login` and `repository.full_name` are consistent.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, derive both the signature-verification organization and the target-repository resolution from the *same*, single field (e.g., always derive the organization from `repository.full_name`'s owner segment, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching), rejecting the request if they diverge.

### Proof of Concept
1. Attacker is onboarded on the Shipit instance as organization `attacker-org`, with `webhook_secret` `S` configured for it in `Shipit.github_apps`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` and `X-Github-Event: push`, then `POST`s to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret` (`S`), and the signature validates successfully.
5. `PushHandler#process` resolves `stacks` via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack — despite the request only ever proving knowledge of `attacker-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
