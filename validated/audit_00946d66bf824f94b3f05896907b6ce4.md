### Title
Unsynchronized concurrent mutation of the unstable-unit cache races the global write lock, mirroring the netdev watchdog tracker race - ([File: storage.js])

### Summary
`storage.archiveJointAndDescendants()` mutates the same shared in-memory unit-tracking structures (`assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`) that `writer.saveJoint()` and `main_chain.markMcIndexStable()` mutate, but unlike those functions it never acquires the global `mutex.lock(["write"])` before doing so.

### Finding Description
The CVE's root cause is that two independent code paths (`netif_carrier_on()`/timer-driven `dev_watchdog()`) mutated the same reference-tracked pointer (`dev->watchdog_dev_tracker`) without a shared lock, so one path could free/overwrite state the other was using, corrupting the tracker's internal list.

`ocore` has the same structural pattern around its core unstable-unit bookkeeping. All of the "critical path" mutators of `storage.assocUnstableUnits` / `storage.assocBestChildren` / `storage.assocStableUnits` — which record parent/child relationships and free/stability status for every unit posted to the DAG — take the global `["write"]` mutex before touching them:

- `writer.saveJoint()` acquires the lock at the very top: [1](#0-0) , then later writes directly into `storage.assocUnstableUnits[objUnit.unit]` and pushes into `storage.assocBestChildren[...]`: [2](#0-1) .
- `storage.shrinkCache()` explicitly takes the same lock before deleting entries from these maps: [3](#0-2) [4](#0-3) .

However `storage.archiveJointAndDescendants()` walks the descendant tree, deletes DB rows, and then directly calls `forgetUnit()` / `fixIsFreeAfterForgettingUnit()` — which mutate `assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, `assocKnownUnits`, `assocCachedUnits`, etc. — entirely inside a plain `db.executeInTransaction()` callback, with **no** `mutex.lock(["write"])` around it: [5](#0-4) 

`forgetUnit()` itself performs unsynchronized in-place list surgery (`_.pull(assocBestChildren[parent_unit], assocUnstableUnits[unit])`) that is directly analogous to `ref_tracker_free()`'s `list_move_tail`/`list_del` operation in the CVE: [6](#0-5) 

If `archiveJointAndDescendants()` runs concurrently with `writer.saveJoint()` (which is actively holding the `["write"]` lock while it is, e.g., pushing a new child into `assocBestChildren[my_best_parent_unit]` or setting `assocUnstableUnits[objUnit.unit]`), the archiving path can read/delete/mutate the very objects the writer is simultaneously building, in the same pattern as the kernel bug: one path assumes exclusive ownership of the tracked structure while the other mutates it unguarded.

### Impact Explanation
Corruption of `assocUnstableUnits` / `assocBestChildren` can desynchronize the in-memory DAG state from the DB state. Because `main_chain.js` and `writer.js` rely on these caches (rather than re-querying the DB) to determine best parents, main-chain index propagation, and stabilization (`markMcIndexStable` iterates `storage.assocUnstableUnits`), corruption here can lead to nodes disagreeing on stabilization/validity of units, or crashing/throwing (e.g., `forgetUnit()`'s own assertion `"trying to forget stable unit"`), which is consistent with the "node disagreement on validity or stability" / "network unable to confirm new units" outcome classes.

### Likelihood Explanation
`archiveJointAndDescendants()` is reachable from `light_wallet.js`'s periodic `archiveDoublespendUnits()` (daily timer, gated on `conf.bLight`) and from `network.js` in the pruned-final-bad recovery flow, both of which can run concurrently with ordinary unit posting/writing (`writer.saveJoint`) which happens continuously as units are received. No malicious actor cooperation beyond ordinary unit posting is needed to create the race window; it only requires normal concurrent activity (a unit being written while the archiving path is running). This mirrors the kernel bug's likelihood profile: a race window between two paths that is exercised under ordinary, non-adversarial concurrency.

### Recommendation
Wrap `archiveJointAndDescendants()` (and any other direct caller of `forgetUnit()`/`fixIsFreeAfterForgettingUnit()` outside of `writer.saveJoint`) in `mutex.lock(["write"], ...)` before mutating `assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, and related caches, exactly as `shrinkCache()` and `writer.saveJoint()` already do, so that all mutators of this shared unstable-unit state serialize on the same lock.

### Proof of Concept
Conceptual (cannot be dynamically executed in ask-only mode):
1. A light client has a unit sitting unstable for >24h; the vendor reports `joint_not_found`, triggering `archiveDoublespendUnits()` → `storage.archiveJointAndDescendantsIfExists(unit)` → `archiveJointAndDescendants()` (no write lock).
2. Concurrently, a new unit referencing that same parent/descendant chain arrives and is processed by `writer.saveJoint()`, which holds `mutex.lock(["write"])` and is actively pushing into `storage.assocBestChildren[my_best_parent_unit]` / setting `storage.assocUnstableUnits[objUnit.unit]`.
3. Because `archiveJointAndDescendants()` does not hold the same lock, its `forgetUnit()` call can delete `assocUnstableUnits[unit]` / mutate `assocBestChildren[parent_unit]` while `writer.saveJoint()` is mid-mutation of the same maps, producing a torn/inconsistent state (e.g. `assocBestChildren[parent_unit]` containing a stale reference to a just-deleted `assocUnstableUnits` entry, or `forgetUnit()` throwing its own consistency assertion), analogous to the `list_del corruption` crash triggered by the unsynchronized `netdev_watchdog_up()`/`dev_watchdog()` race in the CVE.
