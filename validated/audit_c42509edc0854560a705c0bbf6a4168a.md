### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC secret) to check the inbound webhook signature against using one identifier taken from the payload, while every downstream event handler resolves the repository to write state to using a *different* identifier taken from the same payload. Because GitHub Enterprise/multi-org Shipit deployments configure the webhook secret per organization and treat a missing secret as "no verification required," an attacker who can trigger (or simply POST to) a webhook for an organization with no configured `webhook_secret` can supply a payload whose `repository.full_name` points at an entirely different (victim) organization/repository, and have it processed as if it were verified.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to pick the signing secret as: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) and is used to fetch `Shipit.github(organization: repository_owner)`, whose per-org `webhook_secret` gates HMAC verification: [3](#0-2) [4](#0-3) 

Crucially, `verify_webhook_signature` short-circuits to `true` when the resolved app has no configured secret (`return true unless webhook_secret`). This means any organization onboarded to a multi-tenant Shipit instance without a `webhook_secret` set effectively disables signature verification for any payload whose `repository.owner.login` (or `organization.login`) resolves to it.

Once verification passes, the actual event dispatch and repository resolution never re-checks `repository.owner.login`. Instead, every handler resolves the target repository (and therefore the stacks that get mutated) from a completely different field: [5](#0-4) [6](#0-5) 

So the binding that is actually verified is:
`verified_organization == payload["repository"]["owner"]["login"] (or payload["organization"]["login"])`

while the binding that is actually acted upon by every handler is:
`acted_repository == payload["repository"]["full_name"]`

These two fields are never required to agree. `repository.owner.login`/`organization.login` and `repository.full_name` are independent JSON fields in the raw, attacker-controlled POST body (the controller does `JSON.parse(request.raw_post)` with no schema/consistency constraint between them): [7](#0-6) 

### Impact Explanation
If a Shipit deployment is multi-tenant (multiple GitHub organizations configured, each potentially with its own `webhook_secret` — a documented supported configuration, see `test/dummy/config/secrets_double_github_app.yml`) and at least one configured organization has no `webhook_secret` set, an attacker can send a forged webhook whose `repository.owner.login` names the unsecured organization but whose `repository.full_name` names a victim repository belonging to a different, secured organization. `verify_signature` will pass (secret absent ⇒ auto-verified), while every handler (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) resolves and mutates state for the victim repository named in `repository.full_name`. This allows spoofed commit statuses, forged `pull_request`/`membership` events, and manipulation of stacks/commits belonging to a repository the attacker does not control — an authentication-bypass on a security boundary the engine claims to enforce (`X-Hub-Signature` verification), impacting a repository outside the attacker's authorized scope.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization without a `webhook_secret`. Both conditions are plausible/documented (the engine explicitly supports per-organization `github_app` configs and treats `webhook_secret` as optional/`.presence`-guarded), but they depend on operator configuration rather than being universally true of every deployment. No repository write access, API token, or session is needed by the attacker — only the ability to POST to the public `/webhooks` endpoint, so this crosses the intended trust boundary of an "unprivileged attacker."

### Recommendation
Make the field used for signature-secret selection and the field used for repository resolution the same, and require they agree: verify that `repository.full_name`'s owner segment matches the organization whose secret validated the signature (or vice versa), and reject the webhook otherwise. Additionally, do not silently treat a missing per-organization `webhook_secret` as "verification not required" — require an explicit, safe opt-out or treat missing secrets as a hard failure in multi-organization configurations.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`/`config/shipit.yml`: `org-unsecured` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`), each with its own repositories/stacks — a supported configuration per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a POST to `/webhooks` with header `X-Github-Event: push` (or `membership`, `pull_request`, etc.) and body:
   ```json
   {
     "repository": { "owner": { "login": "org-unsecured" }, "full_name": "victim-org/victim-repo" },
     "ref": "refs/heads/master",
     "..." : "..."
   }
   ```
3. `WebhooksController#verify_signature` computes `repository_owner = "org-unsecured"`, loads that org's `GitHubApp`, finds `webhook_secret` blank, and returns `true` unconditionally at [8](#0-7) , regardless of the (missing/invalid) `X-Hub-Signature` header.
4. The request proceeds to `create`, and the relevant handler resolves `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` at [9](#0-8) , locating and mutating `victim-org/victim-repo`'s stacks/commits — despite the signature check never having validated anything against `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
