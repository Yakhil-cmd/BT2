### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` bypasses deploy authorization - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no check that the sha belongs to the repository that signed the incoming webhook, and applies the payload's status to every matching `Commit` row across the entire database. Because a git commit is content-addressed, an attacker who forks a public victim repo (`S2`) can import the exact same commit sha into their own, unrelated, correctly-configured Shipit stack (`S1`), then use their own legitimately-signed CI/status webhook to write a forged `success` status onto `S2`'s commit, which drives `S2` straight into an unattended deploy via `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery`, none of which perform any `require_permission!`/`authorized?` check.

### Finding Description
Broken binding: `commit.stack_id == <stack whose repository actually authenticated this webhook>` is never enforced; instead `Commit.where(sha: params.sha)` matches by `sha` alone. [1](#0-0) 

`WebhooksController#verify_signature` only proves that the sender knows the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`) — it proves *who signed*, not that the `sha` inside the payload belongs to that signer's own repository. [2](#0-1)  `GitHubApp#verify_webhook_signature` is a pure HMAC check against a per-organization secret, with zero knowledge of which commit shas actually belong to that org's repos. [3](#0-2) 

Exploit flow:
1. Attacker owns/administers a Shipit-tracked stack `S1` (any repo they legitimately control, under an org already configured in Shipit with a `webhook_secret`).
2. Attacker forks the public victim repo backing stack `S2`, which shares git objects with the upstream — so a specific victim commit sha is byte-identical and importable into `S1`'s own branch history. `GithubSyncJob`/`Commit.from_github` will create a `Commit` row for that same sha under `S1`.
3. Attacker triggers (or fabricates via their own repo's real GitHub Status API, which they have legitimate write access to as owner of `S1`) a `status` event for `S1`'s repo on that shared sha. GitHub (or the attacker, holding legitimate write/webhook rights only on `S1`) sends a **correctly signed** webhook to `POST /webhooks`, since it is validated against `S1`'s real, legitimately-owned secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns **both** the `S1` commit and the pre-existing `S2` `Commit` row for the identical sha (imported from `S2`'s own normal sync history). It calls `commit.create_status_from_github!(params)` on each, writing a forged `success` status onto `S2`'s commit. [4](#0-3) 
5. `Status#schedule_continuous_delivery` fires `commit.schedule_continuous_delivery`, which — now that the commit looks `deployable?` — enqueues `ContinuousDeliveryJob` for `S2`. [5](#0-4) [6](#0-5) 
6. `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` → `trigger_deploy(commit, Shipit.user, ...)` builds and enqueues a real `Deploy` for `S2`, entirely inside a background job with no controller, no `current_user`, no `require_permission!`/`authorized?` call anywhere in this chain. [7](#0-6) [8](#0-7) 

`Shipit.github_teams`/`require_permission!` only gate the human-facing `DeploysController` path; they are never consulted here, so the UI-side authorization gate is fully bypassed for `S2`.

### Impact Explanation
An attacker with no privilege on `S2` and no Shipit session/token can force a real `Deploy` (running actual deploy commands/scripts) on `S2` by forging a CI status through a repository they legitimately control. This is a payload for repository `S1` mutating stack/commit/deploy state of unrelated repository `S2`, satisfying the Critical "unauthorized deploy" and "one repository mutating another's stack/commit" categories. It is repeatable against any stack whose backing repository is public (or otherwise git-fetchable) and shares any known commit with an attacker-controlled fork/repo, and blast radius spans every stack sharing that GitHub organization's or any org's commit-sha space, since the lookup is entirely unscoped.

### Likelihood Explanation
Preconditions: attacker needs (a) some legitimately Shipit-tracked stack `S1` they control (which they can register for their own repo/fork through normal onboarding), and (b) the target `S2`'s repository to be public/fetchable so a specific victim commit sha can be reproduced verbatim in `S1`'s history. No Shipit secrets, sessions, or GitHub App keys are required — only ordinary write/webhook access to a repo the attacker already owns. This is inexpensive and fully repeatable per victim commit/stack.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to commits whose `stack.repository`/`github_repo_name` matches the webhook's `repository.full_name`/`repository.owner.login`, e.g. `Commit.joins(:stack).where(sha: params.sha, stack: { repository: repo_from_payload })`, rejecting or ignoring statuses for shas that don't belong to the reporting repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status from repo A cannot create a status on a commit belonging to repo B" do
  stack_a = shipit_stacks(:shipit)          # attacker-controlled stack
  stack_b = shipit_stacks(:cyclimse)        # victim stack, unrelated repo

  shared_sha = 'deadbeef' * 5
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'victim commit')
  stack_a.commits.create!(sha: shared_sha, message: 'same sha imported into attacker repo')

  params = Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: 'success', context: 'ci/attacker'
  )

  assert_no_difference -> { commit_b.statuses.count } do
    Webhooks::Handlers::StatusHandler.new.call(
      { 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
        'repository' => { 'full_name' => stack_a.repository, 'owner' => { 'login' => stack_a.repo_owner } } }
    )
  end
  # Currently FAILS: commit_b.statuses.count increases by 1, proving cross-repo forgery,
  # and no require_permission!/authorized? call occurs anywhere in the resulting
  # ContinuousDeliveryJob#perform -> Stack#trigger_continuous_delivery chain.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      return unless stack.continuous_deployment?

      # deployment window before proceeding.

      return if cached_deploy_spec.blank?

      end
