### Title
Unauthenticated cross-organization webhook spoofing — the GitHub organization used to verify a webhook's signature is never bound to the repository the webhook handlers act on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate a webhook against using `params.dig('repository', 'owner', 'login')`, a field taken from the raw, attacker-supplied JSON body of an unauthenticated `POST /webhooks` request. The handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, all `PullRequest::*Handler`s, etc.) instead look up the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`. Nothing enforces that the organization whose secret authenticated the request is the same organization whose repository/stack is mutated.

### Finding Description
`config/routes.rb` mounts `resources :webhooks, only: :create` with no session or `ApiClient` authentication — the only gate is `WebhooksController#verify_signature`: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GitHubApp#verify_webhook_signature` is a no-op when the resolved organization has no `webhook_secret` configured: [2](#0-1) 

`webhook_secret` is documented as **optional** per organization, including in multi-org setups (`docs/setup.md`, `config/secrets.development.example.yml`), so this is a supported, non-malicious configuration, not a misuse of the engine.

Meanwhile, every webhook handler determines *what to write* using a completely different JSON path: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because `repository.owner.login` (used to pick the verifying organization/secret) and `repository.full_name` (used to pick the target repository/stack) are two independent keys in the same attacker-controlled JSON body, an attacker can set them to different values. The equality that should hold — "the organization whose signature authenticated this request" == "the organization that owns the repository being written to" — is never checked. [4](#0-3) 

### Impact Explanation
In a multi-org Shipit deployment (explicitly supported: `docs/setup.md` "Using Multiple GitHub Applications", `test/dummy/config/secrets_double_github_app.yml`), if **any one** configured organization has no `webhook_secret` (allowed by design, `nil` is the documented default), an unauthenticated attacker can:
1. Set `repository.owner.login` to that unsecured organization's name, so `verify_signature` picks a `GitHubApp` whose `verify_webhook_secret` trivially returns `true`.
2. Set `repository.full_name` to any other organization's repository that is actually registered as a Shipit `Stack` (with a properly configured, secret-protected GitHub App).
3. Send a crafted `push`, `pull_request`, `status`, or `check_suite` payload.

This lets the attacker trigger `GithubSyncJob`/`stack.sync_github` (`PushHandler`), forge commit `status` events, or open/close/label pull requests to trigger review-stack provisioning/archival (`PullRequest::*Handler`s) — all against a repository/organization the attacker never authenticated for. Depending on stack configuration (`continuous_deployment`, CI-gated merge queue, required statuses), this can escalate to an unauthorized deploy or merge, matching the required "unauthorized deploy, rollback, or merge" impact bar.

### Likelihood Explanation
No credentials, tokens, sessions, or GitHub App private keys are required — `/webhooks` is completely unauthenticated apart from `verify_signature`. The only precondition is an operator running a multi-org configuration where at least one org omits `webhook_secret`, which the project's own documentation presents as a normal, optional setting rather than a misconfiguration. This is analogous to the referenced report: a binding (here, "authenticating organization" vs. "written repository") that is implicit at setup time and never re-validated, so an operationally reasonable but incomplete configuration silently breaks the trust boundary for all other configured organizations.

### Recommendation
After resolving `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `Repository.from_github_repo_name(...).owner`) and require it to match `repository_owner` before dispatching to handlers. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail fast at boot/config-load time) rather than silently allowing an unauthenticated bypass per-organization.

### Proof of Concept
Given a multi-org config where `OrgWithoutSecret` has no `webhook_secret` and `OrgWithSecret/target-repo` is a real Shipit stack:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, verify_webhook_signature short-circuits true

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "OrgWithSecret/target-repo"
  }
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally. `PushHandler#process` then resolves `Repository.from_github_repo_name("OrgWithSecret/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)`, causing Shipit to process an unauthenticated, forged push event for an organization the attacker never authenticated against.

(Note: I was unable to fully trace whether `sync_github` alone can trigger an actual deploy without an additional CI/status green light in this index snapshot — that final step of the deploy pipeline in `app/models/shipit/stack.rb` and `ContinuousDeliveryJob` would benefit from a deeper read via a full Devin session to confirm the exact conditions for automatic deployment versus just fetching/mirroring the ref.)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
