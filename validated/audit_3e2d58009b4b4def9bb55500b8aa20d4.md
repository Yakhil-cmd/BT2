### Title
Webhook organization used for signature verification is not bound to the repository the event handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook's HMAC against using `repository_owner`, a value read directly out of the untrusted JSON body. The event handlers that subsequently act on the payload (creating commits, updating commit statuses, syncing stacks, processing pull requests, etc.) resolve the target repository from other fields of that same untrusted body (e.g. `repository.full_name`). Because these two lookups are performed against independently-controlled JSON keys inside a single attacker-supplied payload, nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository actually being written to.

### Finding Description
`verify_signature` derives the organization used to fetch the `GithubApp`/secret purely from the request body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` and is used only to pick which configured org's `webhook_secret` verifies the HMAC via `Shipit.github(organization: repository_owner).verify_webhook_signature`, which is implemented as: [3](#0-2) 

`Shipit` deployments commonly configure multiple independent GitHub organizations, each with its own `webhook_secret`: [4](#0-3) 

After signature verification passes, the raw JSON `params` (the entire attacker-controlled body) is handed unmodified to the registered handlers for the event type, which independently locate the `Stack`/`Repository`/`Commit` to act on from other keys in that same body (e.g. `repository.full_name`, `sha`, `repository`/`organization` blocks used by push/status/check_suite/pull_request handlers): [5](#0-4) 

Because the HMAC covers the raw body bytes but the *choice of which secret to check it against* is itself taken from a field inside that same unauthenticated body, an attacker who legitimately controls one configured organization (and therefore knows/controls that organization's `webhook_secret`, e.g. because they administer their own org that has installed the Shipit GitHub App) can craft a payload where `repository.owner.login` names their own org (so the correct, known secret is selected and the HMAC validates), while other fields consumed by the actual event handler (`repository.full_name`, `sha`, PR data, etc.) name a completely different, victim-owned repository configured in the same multi-tenant Shipit instance. GitHub's real webhook deliveries always keep these fields consistent, but nothing in this engine enforces that consistency for a forged request — the verified identity ("attacker's org, because its secret validated") is never checked against the repository actually written to.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." An attacker with no access whatsoever to a victim stack/repository, but with legitimate control of any other org onboarded to the same Shipit instance, could forge `push`, `status`, `check_suite`, or `pull_request` events that pass signature verification and are then processed as if genuinely originating from the victim repository. Depending on which handler is targeted this enables: injecting fake `status`/`check_suite` success states so that a `Stack`'s `continuous_deployment` or `merge_queue` machinery believes CI passed and triggers an unauthorized deploy or merge, or manipulating pull-request/label state used by merge automation for the victim repo. This lands squarely in the specified Critical impact bucket ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that the attacker legitimately control (or have obtained webhook_secret knowledge for) any single organization already configured in the same multi-tenant Shipit deployment — no access, credentials, or privileges on the victim repository/stack are needed. Multi-organization configuration is a documented, first-class deployment pattern (`config/secrets.development.shopify.yml`), so this is not a deviation from how the engine is meant to be run.

### Recommendation
After signature verification, re-derive the organization strictly from the fields the event handler will actually act upon (e.g. `repository.full_name`'s owner segment, or the `Stack`/`Repository` resolved by the handler) and require it to equal the organization whose secret validated the signature; reject the webhook if they diverge.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in Shipit's `secrets.yml` with its own `webhook_secret` (known to the attacker as the org's GitHub App/webhook owner).
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook JSON body where `repository.owner.login` = `"attacker-org"` but `repository.full_name` = `"victim-org/victim-repo"` (and `sha` set to a commit in the victim's undeployed range).
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully validates the signature against the known secret.
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs the status handler against `params`, which resolves the target commit/stack via `repository.full_name` = `victim-org/victim-repo`, applying the forged status to the victim's commit and influencing its deploy/merge automation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
