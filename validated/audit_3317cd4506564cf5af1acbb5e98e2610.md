### Title
Cross-tenant CI status injection via unscoped `Commit.where(sha:)` lookup enables unauthorized `MergeRequest#merge!` for another stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/merge_request.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming GitHub `status` webhook to **every** `Commit` row that shares the reported `sha`, with no scoping to the stack/repository that the webhook's signature actually authenticated. Since commit SHAs are content-addressed and identical commits routinely exist across multiple repositories/stacks (forks, shared history, cherry-picks), an attacker who controls any other repository whose organization is registered with Shipit can push a `success` status for a SHA that also exists in a victim stack's queued `MergeRequest`, causing `ProcessMergeRequestsJob` to treat the victim PR as CI-green and call `MergeRequest#merge!`, which merges using the **victim's** `stack.github_api` / `GITHUB_TOKEN` and `stack.github_repo_name`.

### Finding Description
The binding that should hold is:

`organization/repository that produced a validly-signed webhook == repository/stack whose Commit row gets its CI state mutated`

This does not hold in the code.

`WebhooksController#verify_signature` verifies the signature using only the organization named in the attacker's own payload: [1](#0-0) 
It never checks that the specific `repository.full_name` in the payload matches the stack/commit being updated — it only proves "this event was really sent by GitHub for organization X."

`StatusHandler#process` then does: [2](#0-1) 
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is **not** scoped by `repository.full_name`, `stack_id`, or organization. It matches any `Commit` row in the entire database that has that sha, regardless of which stack/repository it belongs to. The DB index confirms multiple stacks can legitimately hold rows with the same `sha` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` indexes `(stack_id, sha)`, i.e., `sha` is not globally unique).

`create_status_from_github!` → `add_status` → `Status.replicate_from_github!` writes a `Status` for that commit, and if it transitions the commit to `pending`/`success` it enqueues `ProcessMergeRequestsJob`: [3](#0-2) 

`ProcessMergeRequestsJob#perform` then re-evaluates queued merge requests for the victim stack: [4](#0-3) 
calling `merge_request.all_status_checks_passed?`: [5](#0-4) 
which builds `StatusChecker` purely from `head.statuses_and_check_runs` — i.e., from whatever `Status` rows exist for that `head` commit, including the one just injected by the attacker's cross-tenant webhook.

If it passes, `merge!` runs using the victim stack's own credentials: [6](#0-5) 

**Exploit flow**: Getting an identical SHA in two different Shipit-tracked repositories does not require a cryptographic SHA-1 collision. It is a normal git property: forking a repository, cherry-picking, or sharing an initial/template commit preserves the exact SHA-1 of the commit object. An attacker who (a) has push/commit-status access to any repository whose owning GitHub organization has Shipit's app/webhook secret configured (e.g., another repo in the same org, or their own fork if that org is used), and (b) can get a commit with the identical SHA as the victim's queued PR's head (trivial via fork before divergence, or cherry-pick of the victim's unmerged commit into their own repo) can set a `success` status on that SHA in their own repo. GitHub delivers a legitimately signed webhook for the attacker's org/repo; `verify_signature` passes because it only checks organizational provenance, not which specific repository's commit is being touched; `StatusHandler` then blindly applies the status to the victim's `Commit` row too.

None of the existing guards prevent this: `verify_signature` authenticates the org, not the specific repo/commit; the `ExplicitParameters` schema on `StatusHandler` only validates payload shape (`sha`, `state`, etc.), not repo ownership; there is no `repository.full_name`/`stack_id` filter anywhere in the `Commit.where(sha:...)` call.

### Impact Explanation
A payload legitimately authenticated for one repository/organization mutates commit/CI state belonging to a different stack, and that mutated state is consumed to authorize `MergeRequest#merge!`, which performs a real GitHub API merge (`stack.github_api.merge_pull_request`) using the victim stack's own `GITHUB_TOKEN`/`github_repo_name`. This is an unauthorized merge of a PR whose real, required CI checks never passed — a direct hit on "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge" (Critical). It is repeatable against any stack/PR for which the attacker can obtain (fork/cherry-pick) an identical-SHA commit, and scales across all stacks sharing a GitHub organization with the attacker's controlled repository.

### Likelihood Explanation
Preconditions: (1) attacker needs write/status access to some repository whose GitHub organization is one Shipit has app credentials for (this can be the very same org as the victim if the deployment is multi-repo/multi-team within one org, or the attacker's own account/org if Shipit installs are organization-scoped and the attacker's fork's org matches); (2) attacker needs a commit with an identical SHA to the victim's PR head, achievable cheaply by forking before the PR diverges or cherry-picking the exact commit unmodified. No Shipit session, token, or secret is required — only ordinary GitHub actions (fork, commit, set a status via the Statuses API on a repo they control) plus a real GitHub-delivered webhook. This is inexpensive and repeatable, though it does depend on organizational/app-installation topology that determines which repositories share webhook verification scope with the victim.

### Recommendation
Scope the `StatusHandler` (and analogous handlers, e.g. `CheckSuiteHandler`) commit lookup to the reporting repository, not just `sha`. Resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')`, verify it matches the `stack` that owns the `Commit`, and only then apply `create_status_from_github!`. Concretely, change:
```ruby
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
```
to filter by `commit.stack.github_repo_name == params.dig('repository','full_name')` (or join through `Stack` on repo owner/name) before creating the status.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
    test "a status for one repository's sha does not merge another stack's PR" do
      victim_stack = shipit_stacks(:shipit)
      attacker_stack = shipit_stacks(:cyclimse) # different repo/org

      shared_sha = 'deadbeef' * 5

      victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
        committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'shared')
      attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
        committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'shared')

      merge_request = shipit_merge_requests(:shipit_pending) # queued MR whose head == victim_commit
      merge_request.update!(head: victim_commit)

      payload = OpenStruct.new(sha: shared_sha, state: 'success', description: nil,
        target_url: nil, context: 'ci/attacker', created_at: Time.now)

      # Simulates a validly-signed webhook for the ATTACKER's repo only
      Webhooks::Handlers::StatusHandler.new(payload).process

      refute victim_commit.reload.statuses.where(context: 'ci/attacker').empty?,
        "victim commit received a status from a webhook that authenticated a different repository"

      Shipit.github.api.expects(:merge_pull_request).with(
        victim_stack.github_repo_name, merge_request.number, anything, has_entries(sha: victim_commit.sha)
      ).returns(true)
      Shipit.github.api.stubs(:pull_requests).returns([])
      Shipit.github.api.stubs(:delete_branch).returns(true)

      ProcessMergeRequestsJob.new.perform(victim_stack)
      assert_predicate merge_request.reload, :merged?
    end
  end
end
```
This demonstrates: the equality "org that authenticated the webhook == repo whose PR gets merged" is false — `attacker_stack`'s status webhook (its own `webhook_secret`/org) causes `merge_pull_request` to be invoked for `victim_stack`.
