### Title
Emergency OP-list vote counting silently drops legitimate votes cast near the trigger window, and depends on non-deterministic local mempool state - ([File: main_chain.js])

### Summary
The reported Gitcoin issue is a "closing window locks out an otherwise-valid actor" bug class: a recipient who registers at the very end of a fixed window can never be reviewed because the review window and the action window are the same, non-extendable window. The direct analog in `ocore` is `countVotes()`'s emergency OP-list vote-counting path, where a vote cast shortly before the emergency-count trigger fires is unconditionally excluded by a fixed age filter, and — more importantly — the set of "unstable votes" considered is read from each node's own local, non-deterministic mempool state rather than from any DAG-derived deterministic source.

### Finding Description
When the main chain gets stuck (no MC advances) for `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days), `applyEmergencyOpListChange()` is invoked and calls `countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp)`: [1](#0-0) 

Inside `countVotes`, when `is_emergency` is set, unstable (not-yet-stable) `system_vote` messages for `op_list` are pulled via `getUnstableVotes()`: [2](#0-1) 

`getUnstableVotes()` iterates `storage.assocUnstableMessages`/`storage.assocUnstableUnits`, i.e., the *local node's in-memory view* of currently unstable units, and discards any vote whose age (`emergency_count_command_timestamp - timestamp`) is below `EMERGENCY_COUNT_MIN_VOTE_AGE` (1 hour): [3](#0-2) [4](#0-3) 

This produces two related problems, both structurally analogous to the reported issue ("can only be reviewed/counted during a narrow window, so late-but-legitimate action is lost"):

1. **Deadline exclusion**: A witness/voter who casts (or whose vote unit becomes visible) an `op_list` vote less than `EMERGENCY_COUNT_MIN_VOTE_AGE` before the emergency count fires has that vote permanently discarded from the emergency tally — exactly like a recipient who registers too close to the review deadline and is never reviewed. There is no extension or grace period; the vote is simply dropped from this one-shot count.

2. **Non-determinism across nodes**: Because the emergency vote count is not derived from a stable, chain-agreed snapshot but from each node's private, timing-dependent view of unstable units (`storage.assocUnstableMessages`), different full nodes can legitimately see different sets of "young" vs. "old enough" unstable votes at the moment they run `applyEmergencyOpListChange()`. Two nodes evaluating the *same* `main_chain_index - 1` emergency vote count can therefore compute different `ops` arrays and write different `op_list` values into `system_vars` via the `REPLACE INTO system_vars` at the end of `countVotes()`: [5](#0-4) 

Since `op_list` determines the witness set used for main-chain determination and unit validation going forward, a divergence here is not cosmetic — it can cause different nodes to disagree on which units/witness set is authoritative, i.e., a consensus split precisely in the recovery mechanism meant to unstick the network.

### Impact Explanation
This affects `node disagreement on validity or stability` and `a network unable to confirm new units` categories:
- The emergency mechanism only triggers when the network is *already* stuck (no MC progress for 3 days), so it is the network's last-resort recovery path. If the vote count used to select the new OP (witness) list is non-deterministic and time-window-dependent as shown, different nodes may adopt different OP lists, deepening the stall or causing a chain split rather than resolving it.
- Even absent a full network split, an honest voter's last-minute (but valid) vote is silently and permanently excluded from the one-shot emergency count with no path to be reconsidered, mirroring the exact "excellent recipient can never be reviewed" pattern from the source report.

### Likelihood Explanation
The emergency path only activates in the rare case of the main chain being stuck for 3+ days, so it is not triggered on a normal unit-posting path, but is reachable to any full node running the same client logic without needing a malicious actor — an honest voter or the natural relative-timestamp gap between vote propagation and the timeout being reached is sufficient to hit the age-filter drop, and normal network latency/mempool divergence is sufficient to hit the cross-node non-determinism. It requires the specific circumstance of the OP list emergency-change mechanism actually firing, which is infrequent by design.

### Recommendation
- Derive the emergency vote snapshot from a deterministic, replayable source (e.g., only consider unstable units whose relative order/timestamp is agreed via last-ball/MCI references, not local node-time-of-evaluation), so all full nodes compute the identical result for the same trigger conditions.
- Remove or redesign the `EMERGENCY_COUNT_MIN_VOTE_AGE` cutoff so that a vote is not unconditionally discarded merely because it was cast close to the count-trigger time; instead, freeze the eligible-vote set based on a chain-derived checkpoint rather than wall-clock proximity to `emergency_count_command_timestamp`.
- Add a mechanism to recount (or extend the window) if votes that were previously "too young" become eligible, mirroring adding a proper review/grace period after the action window as recommended in the source report.

### Proof of Concept
Not independently executable here without a running two-node ocore/witness testnet; the flow to reproduce is:
1. Force the main chain to stall past `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) on a private/dev network.
2. Have a witness broadcast a `system_vote` for `op_list` at a time such that, on Node A, it becomes visible/unstable more than `EMERGENCY_COUNT_MIN_VOTE_AGE` (1h) before `applyEmergencyOpListChange` runs, while on Node B (due to propagation delay) it becomes visible less than 1h before the same call.
3. Trigger `applyEmergencyOpListChange` on both nodes at the same `emergency_count_command_timestamp`; Node A includes the vote in `getUnstableVotes()`, Node B excludes it per the age check at [6](#0-5) .
4. Observe that the two nodes can compute different `ops` sets and write different `op_list` values into `system_vars`, demonstrating the consensus-divergence risk.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
