### Title
`StatusHandler#process` writes `Status` rows for commits in unrelated stacks matched only by `sha`, without repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter tying the lookup to the `repository.full_name` that authenticated the webhook. Every other handler in the same module uses the `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name).stacks`) to scope database writes to the repository named in the payload, but `StatusHandler` does not use it at all.

### Finding Description
Binding that should hold: `Status.where(commit_id: Commit.where(sha: params.sha, stack: <stacks belonging to repository_name>).ids).count == Status rows written`, i.e. writes must be limited to commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`.

Actual code: [1](#0-0) 

`process` never touches `repository_name` or `stacks`; it iterates `Commit.where(sha: params.sha)` globally, so the write count equals `Commit.where(sha:).count`, not `Commit.where(sha:, stack: {repository: repository_name}).count`. This is confirmed by comparing to the base `Handler` class, which already exposes exactly the scoping primitive that is missing here: [2](#0-1) 

`Commit#sha` is a content-addressed git SHA-1 that is independent of which repository/stack stores it. Identical commit SHAs legitimately occur across unrelated repositories/forks (shared fork history, or a commit constructed with `git commit-tree`/`git hash-object`/`git am` reproducing the exact tree/parent/author/committer/timestamp of a target commit). Shipit's `Commit` table is populated per-stack from each repository's own push/GitHub events, so the same SHA can end up as separate `Commit` rows belonging to N different stacks tracking N different repositories.

Exploit flow:
1. Attacker owns/controls a repository that is (or becomes) a tracked Shipit stack, so GitHub will deliver a validly-signed `status` webhook for events on that repository.
2. Attacker crafts or acquires a commit whose SHA collides with a commit already present in other unrelated stacks (fork-shared history, or a manually constructed identical commit object via git plumbing) and pushes it / gets GitHub to emit a `status` event referencing that SHA on their own repo.
3. Signature verification (`GitHubApp#verify_webhook_signature`) validates only that the request body was signed by GitHub — it says nothing about which SHAs are "owned" by the sending repository. The `ExplicitParameters` schema only validates types (`sha: String`, `state: String`, etc.), not repository/stack membership.
4. `StatusHandler#process` fans out: `Commit.where(sha: params.sha)` returns every `Commit` row across every stack with that SHA, and `create_status_from_github!(params)` writes a `Status` for each, mutating stacks that never authenticated this webhook (`Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`): [3](#0-2) [4](#0-3) 

Existing guards do not stop this: webhook signature verification authenticates the payload's origin repository but not the `sha`'s scope; `drop_unhandled_event`/`ExplicitParameters` only gate event type and field shape; there is no `stack`/`repository` predicate anywhere in `StatusHandler`, unlike the `PullRequest::*Handler` classes which consistently use `stacks`.

### Impact Explanation
A single signed webhook from a repository the attacker controls can cause `Status` writes (`state`, `description`, `target_url`, `context`) to be attached to commits belonging to other tenants' stacks. `add_status` further triggers `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` on the *victim* stack — meaning a forged/collided status can flip a victim commit from "pending"/"failure" to "success", which can unblock deploys or merges (`deployable?`, `schedule_continuous_delivery`, `schedule_merges`) on a stack the attacker never authenticated against. This matches "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy/merge" (Critical).

### Likelihood Explanation
Exploitation requires: (a) the attacker's own repository being registered as a Shipit-tracked stack so a genuinely GitHub-signed webhook is delivered for it, and (b) producing (or finding) a commit SHA that also exists in another tracked stack's `Commit` table — trivially true for shared history between a public upstream repo and any of its forks, and constructible via ordinary git plumbing (`git commit-tree` reproducing identical tree/parent/author/committer/date) without needing any Shipit or GitHub secret. No privileged Shipit role, session, or API token is required beyond controlling one already-tracked repository — a bar many self-serve Shipit deployments allow any org member to clear. Repeatable per SHA collision found; blast radius scales with however many stacks happen to have matching-SHA commits (e.g., all downstream forks of a popular tracked upstream).

### Recommendation
Scope `StatusHandler#process` to only the stacks whose repository matches the webhook's `repository.full_name`, mirroring the pattern used elsewhere in the module:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `Handler#stacks` helper, so a write can never cross repository boundaries regardless of SHA collisions.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (representative, no live GitHub)
test "process only creates statuses for commits belonging to the payload's repository" do
  colliding_sha = "a" * 40

  stack_a = shipit_stacks(:shipit) # repository X, authenticated by payload
  stack_b = create_stack!(repository_name: "other-org/unrelated-repo-1")
  stack_c = create_stack!(repository_name: "other-org/unrelated-repo-2")

  commit_a = stack_a.commits.create!(sha: colliding_sha, message: "a")
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: "b")
  commit_c = stack_c.commits.create!(sha: colliding_sha, message: "c")

  payload = {
    'repository' => { 'full_name' => stack_a.github_repo_name },
    'sha' => colliding_sha,
    'state' => 'success',
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding: writes must equal commits belonging to stack_a's repository only (1),
  # not Commit.where(sha: colliding_sha).count (3).
  assert_equal 1, Shipit::Status.where(commit_id: [commit_a.id, commit_b.id, commit_c.id]).count
  assert Shipit::Status.exists?(commit_id: commit_a.id)
  refute Shipit::Status.exists?(commit_id: commit_b.id)
  refute Shipit::Status.exists?(commit_id: commit_c.id)
end
```
With the current implementation this assertion fails: `Status.where(...).count == 3`, demonstrating the fan-out across unrelated, unauthenticated stacks.
