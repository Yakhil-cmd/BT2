### Title
Attacker-supplied non-commit tag target (`FETCH_HEAD^{}` peel) reaches `reset --soft` / `worktree add`, causing repeated sync failures - (File: main.go)

### Summary
`repoSync.SyncRepo` resolves the fetched ref via `git rev-parse FETCH_HEAD^{}` [1](#0-0) , which per git semantics only peels through tag objects until a non-tag object is reached — it does not guarantee the result is a commit. If an attacker pushes an annotated tag whose target is a tree or blob, `remoteHash` becomes that tree/blob's object id, which is then fed unchecked into `git reset --soft remoteHash --` and `git.createWorktree(ctx, remoteHash)` → `worktree add ... hash --no-checkout` [2](#0-1) [3](#0-2) .

### Finding Description
`git-sync` fetches an attacker-controllable ref (`git.ref`) via `git fetch` [4](#0-3) , then immediately resolves `FETCH_HEAD^{}` and trusts the result as a commit hash with no type validation:

```go
if output, _, err := git.Run(ctx, git.root, "rev-parse", "FETCH_HEAD^{}"); err != nil {
    return false, "", err
} else {
    remoteHash = strings.Trim(output, "\n")
}
``` [5](#0-4) 

Git's `^{}` suffix only dereferences through **tag** objects recursively until a non-tag object is found — it makes no guarantee that the terminal object is a commit. If the attacker pushes an annotated tag whose target is a tree or blob, `rev-parse FETCH_HEAD^{}` succeeds and returns that tree/blob's hash rather than erroring out, because the object exists in the object database and the `^{}` operator does not enforce "commit" typing (unlike `^{commit}`).

This `remoteHash` is then used, with no commit-type check, as the target of:
- `git reset --soft remoteHash --` [6](#0-5) 
- `git worktree add --force --detach <path> <hash> --no-checkout` inside `createWorktree` [7](#0-6) 
- worktree naming/leaf directory, via `git.worktreeFor(hash)` and `worktree.Hash()` which is just the path basename [8](#0-7) [9](#0-8) 

Both `git reset --soft` and `git worktree add` internally require the target to dereference to a commit object (via `lookup_commit_reference`), so when given a tree or blob hash they will fail with a fatal git error (e.g. "Could not parse object '<sha>'.") rather than silently succeeding. Because the failure happens at the `reset --soft` step, which runs before `createWorktree`, `SyncRepo` returns an error immediately and no new worktree, symlink update, or corrupted state is produced — the previously published symlink and worktree remain untouched.

### Impact Explanation
The practical effect is a **denial of update**, not data corruption or a worktree with a non-commit leaf name: `SyncRepo` returns an error every sync cycle for as long as the upstream ref resolves to this malicious tag, and the currently published content is never refreshed. This is a persistent "sync stall" for the affected ref — matching a degraded-service/DoS-style impact class — but it does not achieve the more severe outcomes hypothesized in the question (a worktree whose leaf name is not a commit hash, or a corrupted `reset --soft` state), because git's own object-type checks in `reset` and `worktree add` reject the non-commit hash before any filesystem side effects occur.

### Likelihood Explanation
Preconditions are minimal and match the described attacker model: push access (or ref/object control) to the repo git-sync fetches, and no special flags beyond a normal deployment. No `--filter=blob:none`-specific behavior is required — this reproduces with any partial or full clone since the object type problem is at the ref-resolution layer, not the transfer layer. The attack is trivially repeatable (attacker can leave the malicious tag in place indefinitely, causing every sync cycle to fail identically).

### Recommendation
Validate `remoteHash`'s object type immediately after resolving `FETCH_HEAD^{}` (e.g., `git cat-file -t` or `git rev-parse --verify FETCH_HEAD^{commit}`), and treat non-commit resolution as a fetch/sync error with a clear diagnostic rather than passing the raw hash on toward `reset`/`worktree add`. Using `^{commit}` instead of `^{}` in the `rev-parse` call would make git itself fail fast with a clearer error at the exact point of resolution.

### Proof of Concept
1. Create a bare repo; commit an initial commit on `main`.
2. Create a blob: `git hash-object -w README` → `<blob-sha>`.
3. Create an annotated tag pointing at the blob: `git tag -a badtag <blob-sha> -m "malicious"` (git allows annotated tags to target any object type).
4. Push `badtag` to the repo served to git-sync; configure git-sync with `--ref=badtag`.
5. Run the sync loop (or call `SyncRepo` directly in a unit test) and observe:
   - `git rev-parse FETCH_HEAD^{}` succeeds and prints `<blob-sha>`.
   - The subsequent `git reset --soft <blob-sha> --` call fails with a fatal git error.
   - `SyncRepo` returns a non-nil error on every cycle; the published symlink target remains unchanged across sync periods.

**Note:** I could not fully verify within this session whether the top-level sync loop treats repeated `SyncRepo` errors as fatal (process exit) or as a logged, retried failure (e.g., via `--max-sync-failures` or similar), since the relevant loop/exit-code logic was not fully retrieved before the tool budget was exhausted. This affects whether the "crash loop" framing (process exit/restart) or only a "stalled but running" framing applies; only the latter is confirmed by the code examined here.

func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
