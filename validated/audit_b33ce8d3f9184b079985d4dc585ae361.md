## Title
Cross-repository Commit/Status mutation via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` looks up commits solely by `sha`, without any scoping to the repository named in the webhook payload, and updates whatever `Commit` rows it finds regardless of which stack/repository they belong to. Since GitHub commit SHAs are content-addressed and not globally unique to a single GitHub repository (they can trivially collide across forks or for well-known objects like the empty tree), a `status` webhook that is cryptographically verified only for repo B can mutate a `Commit`/`Status` row that belongs to repo A's stack.

## Finding Description
The broken binding: `payload.dig('repository','full_name')` (the repo the webhook signature in `WebhooksController#verify_signature` was verified against) should equal the repository owning every `Commit` row mutated by the handler, but it does not.

Code path:
- `WebhooksController#create` parses the raw payload and dispatches to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, after `verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)` — this only proves the payload's *organization/owner* signed the payload, tied to repo B. [1](#0-0) 
- `Handler` base class exposes a `stacks` helper that properly scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`, and other handlers (e.g. pull_request handlers) use it. [2](#0-1) 
- `StatusHandler#process`, however, never calls `stacks` or filters by `repository_name`; it queries `Commit.where(sha: params.sha)` across the *entire* commits table and calls `commit.create_status_from_github!(params)` on every match. [3](#0-2) 
- `Commit#create_status_from_github!` -> `add_status` unconditionally writes a new `Status` row, recomputes `status`, and fires `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` and may call `stack.schedule_merges`, all keyed off the commit's own `stack`, not the webhook's repository. [4](#0-3) [5](#0-4) 

Exploit flow: an attacker who owns/controls repo B pushes a commit whose SHA collides with a commit already present in victim repo A's stack (e.g., cherry-picking or otherwise reproducing repo A's public commit content into repo B, or using the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`), then triggers a GitHub `status` event for repo B with `state: success`. GitHub signs this payload for repo B's owner; `verify_signature` passes because it is checking the correct owner for repo B. `StatusHandler#process` then updates *every* `Commit` row across all stacks that shares that SHA, including repo A's, writing a new `Status` row and potentially flipping `Status::Group` state, unblocking `deployable?`/`schedule_continuous_delivery` for repo A's stack.

None of the existing guards prevent this: `verify_signature` authenticates the payload only for the repository/organization named in it (repo B), it does not restrict which `Commit` rows the handler is permitted to touch; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of the payload, not repository scoping; there is no `stacks`/`repository_name` filter applied in this handler as there is in others.

## Impact Explanation
A cross-repository write: an attacker fully controlling repo B can inject fabricated CI status (`success`/`failure`) onto commits belonging to unrelated repo A's stack, without any relationship to or access on repo A. This can flip `Commit#status`/`Status::Group` state for repo A, affecting `deployable?`, `blocked?`, and `schedule_continuous_delivery`, potentially causing an unintended/unauthorized deploy path evaluation for repo A (continuous delivery is scheduled if `new_status.pending? || new_status.success?`). This is repeatable against any repository whose stack contains a commit with a SHA the attacker can reproduce (trivial for the universal empty-tree SHA, or any commit whose tree/content the attacker can replicate in their own repo). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

## Likelihood Explanation
Preconditions are attacker-controlled and cheap: own/create a GitHub repo, commit content that reproduces a target SHA (either use the universal empty-tree SHA, or cherry-pick a public commit from the target repo, which is often visible since Shipit-managed repos are typically public/CI-integrated), and configure a webhook (or use GitHub's native status webhook when connecting the attacker's own repo to any CI producing a `status` event) — GitHub happily emits and signs this payload for the attacker's own repository, no privileged access to repo A required. `stack.ignore_ci?` must be false for the state to matter for deployability, otherwise the write still occurs (Status row is created regardless) but has less deploy-relevant effect. The attack is fully repeatable and requires no secrets, no session, no API token.

## Recommendation
Scope `StatusHandler#process` to the payload's repository, mirroring other handlers: use `stacks` (i.e., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map(&:commits).where(sha: params.sha)`) instead of an unscoped `Commit.where(sha: params.sha)`, so only commits belonging to stacks tied to `payload.dig('repository','full_name')` can be mutated.

## Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not written here since it's out-of-scope path but describing the required assertions):
1. Create `stack_a` for repo `"org/repo-a"` and `stack_b` for repo `"org/repo-b"`.
2. Create `commit_a = stack_a.commits.create!(sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)` with an initial `Status::Group` state (e.g., pending/unknown).
3. Build a `status` webhook payload for repo B: `{ "sha" => "4b825dc642cb6eb9a060e54bf8d69288fbee4904", "state" => "success", "repository" => { "full_name" => "org/repo-b" }, ... }`.
4. Assert before: `commit_a.reload.status.state != "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert after: expected/fixed behavior is `commit_a.reload.status.state` remains unchanged (write did NOT cross repositories); current buggy behavior is that `commit_a.reload.status.state == "success"`, proving the cross-tenant write. [3](#0-2) [2](#0-1) [6](#0-5) [4](#0-3) [5](#0-4)

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
