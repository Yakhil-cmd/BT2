### Title
Unallowlisted PR-label-derived environment variables (e.g. `PYTHONPATH`) reach `Command#start`/`PTY.spawn` for review-stack tasks including rollback - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and that hash is inherited by every `TaskCommands`-derived executor (`RollbackCommands`, `DeployCommands`) that ultimately spawns processes via `Command#start`/`PTY.spawn`. Because label names come from `LabelCapturingHandler#capture_labels`, which persists label text verbatim from the webhook payload, a fork PR author who can label their own PR can force an arbitrary environment-variable *name* (such as `PYTHONPATH`) into every subsequent `Command` invocation for that review stack, including rollback steps.

### Finding Description
The broken binding is: `ReviewStack#env.keys` should be `⊆ {allowed stack env keys defined by Stack#env / deploy_spec}`, but in fact `ReviewStack#env.keys ⊇ pull_request.labels.map(&:upcase)` with no filter.

Trace:
- `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body, with only type-checking (`requires :labels, Array do requires :name, String end`), no content allowlist. [1](#0-0) [2](#0-1) 
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the base `Stack#env` hash with no key restriction. [3](#0-2) 
- `TaskCommands#env` merges `@stack.env` (i.e. `ReviewStack#env` for review stacks) into the task command environment. [4](#0-3) 
- `RollbackCommands#env` (used for the rollback task, which runs `deploy_spec.rollback_steps!`) calls `super` and inherits this same unfiltered environment. [5](#0-4) 
- `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH`, so any injected key (including `PYTHONPATH`, or even `PATH`) overrides the process defaults, and this exact hash is passed to `PTY.spawn`. [6](#0-5) 

**Important correction to the exploit claim as stated in the question**: the injected value is not an attacker-chosen module path. `label_name.upcase` becomes the *key*; the *value* is hardcoded to the literal string `"true"` (`labels[label_name.upcase] = "true"`). So an attacker who labels their PR `pythonpath` causes `PYTHONPATH=true` to reach the spawned process - not `PYTHONPATH=/attacker/evil/path`. A working RCE therefore additionally requires the attacker to have a file/directory literally named `true` inside their own fork's checked-out working tree (which they fully control, since `@task.working_directory` is the checked-out PR branch used by `TaskCommands#checkout`/`#clone`), combined with a step that resolves a module or executable name matching something the attacker placed under `./true/`. That is a plausible but conditional chain, not a direct "attacker supplies the path" primitive as the question describes.

Existing guards do not stop the key-injection itself: `ExplicitParameters` only validates types/presence of `labels[].name`, not content; there is no allowlist of "safe" env var names anywhere in `ReviewStack#env`, `Stack#env`, or `Command`; and `provisioning_behavior=prevent_with_label` only gates *whether the review stack is provisioned/deployed at all*, not what env keys `ReviewStack#env` is allowed to expose once it is running.

### Impact Explanation
Any fork PR author able to add a label to their own review-stack PR can inject arbitrary environment-variable **names** (not arbitrary values) into every command run for that stack, including `rollback.override`/task/deploy commands, because the merge chain `ReviewStack#env → TaskCommands#env → RollbackCommands#env → Command#unbundled_env → PTY.spawn` has no allowlist. This is limited to the affected review stack (repository/PR-scoped, not cross-tenant), and the practical severity depends on whether the attacker can also plant a matching-named file/directory in their own checked-out fork tree and whether the base shipit.yml's rollback/task steps perform relative-path-sensitive lookups (Python import, `PATH` resolution, etc.). As described with a fully attacker-controlled value, this would be Critical RCE; as actually implemented (value fixed to `"true"`), it is a narrower environment-poisoning/import-hijack primitive that needs an additional coincidental condition in the trusted step's own logic to escalate to code execution.

### Likelihood Explanation
Requires: repository configured with `provisioning_behavior: prevent_with_label`, a review stack already provisioned for the PR, and the attacker being able to apply a label to their own PR (per the question's threat model). Given only the fixed `"true"` value is injectable, likelihood of full RCE is low without further conditions (attacker's own file tree containing a `true`-named module/executable and a rollback/task step whose commands are sensitive to `PYTHONPATH`/`PATH` in a way that resolves against the working directory).

### Recommendation
In `app/models/shipit/review_stack.rb`, allowlist which label-derived keys are permitted (or namespace them, e.g. `LABEL_<NAME>`) instead of merging raw uppercased label names directly into the process environment, and explicitly reject names colliding with security-sensitive variables (`PATH`, `PYTHONPATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_*`, etc.) before they reach `Command#env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (illustrative)
test "labels cannot inject PYTHONPATH into command env" do
  stack = shipit_review_stacks(:review_stack) # or build one
  pr = stack.pull_request
  pr.update!(labels: ['pythonpath'])

  env = stack.env
  assert_nil env['PYTHONPATH'], "fork-controlled label should not set PYTHONPATH"
end
```
Actual current behavior (demonstrating the break): `stack.env['PYTHONPATH']` equals `"true"`, confirming `ReviewStack#env` merges the uppercased label into the environment with no allowlist [3](#0-2) , and that hash is what `Command#unbundled_env` passes to `PTY.spawn` [6](#0-5) . Note: the value is always the literal string `"true"`, not an attacker-supplied path, which the question's exploit description gets wrong; a full RCE demonstration would additionally require asserting that the attacker's own checked-out fork tree contains a `true`-named directory/file that a rollback/task step's command resolves against - this additional step was not verified in the available code/tests.
