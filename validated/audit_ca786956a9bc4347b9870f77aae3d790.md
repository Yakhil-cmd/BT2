### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, so a `status` webhook that is only cryptographically authenticated for the attacker's own repository can create a `Status` row on every `Commit` in every stack that happens to share that SHA. Combined with `Commit#deployable?` treating `ignore_ci: true` as an unconditional bypass of CI state, this allows an attacker who controls a repository (and its own valid webhook secret) to influence CI status on an unrelated victim stack that shares the same commit SHA.

### Finding Description
The broken binding: the code assumes `verified_repository_owner(payload) == repository.owner_of(commit)` for every `commit` touched by the handler. In reality:

- `WebhooksController#verify_signature` only proves the payload's HMAC matches the webhook secret of `repository_owner` derived from the payload itself [1](#0-0) , i.e. it authenticates "this payload came from the org/repo named in the payload," not "this payload may only affect that repo's data."
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is unscoped by repository or stack — it matches every `Commit` row across every stack with that SHA.
- The schema confirms `sha` is only unique per `(sha, stack_id)` pair, not globally: `add_index :commits, %i(sha stack_id), unique: true` [3](#0-2) . This means the same SHA can legitimately exist as separate `Commit` rows belonging to different stacks (e.g., a stack tracking a fork and a stack tracking the upstream/victim repo, which share identical git history and therefore identical content-addressed SHA1s for shared commits).
- `Status#after_create` calls `enable_ci_on_stack`, and `after_commit` calls `commit.schedule_continuous_delivery` [4](#0-3) , both scoped to `commit.stack` — the victim stack, not the attacker's.
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [5](#0-4) . When the victim stack has `ignore_ci: true`, CI state is irrelevant to deployability, so the primary amplification claimed by the question is moot for the *ship* path (an already-deployable commit doesn't need a forged status to become deployable). However, the forged status still (a) creates a `Status` record attributed to the victim stack that did not authenticate it, (b) flips `enable_ci_on_stack` for the victim stack, and (c) can flip a commit to `blocking?`/failing state for CI-checking stacks that share the SHA (e.g. a stack with `required_statuses`/`blocking_statuses` including `github-actions`), causing `Commit#blocked?` to return true for downstream commits via `stack.commits.reachable.newer_than(...).any?(&:blocking?)` [6](#0-5) , which blocks deploys on the victim stack. This is a genuine cross-tenant write, independent of `ignore_ci`.

Attacker request: control a repository (or fork) whose commit history shares a SHA with a victim's tracked stack (trivial via forking a public repo tracked by Shipit, since git SHA1s are computed from content and identical commits across fork/upstream have identical SHAs). Send `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` for the attacker's own repo's webhook secret, `repository.owner.login` = attacker's org, `sha` = the shared SHA, `context: github-actions`, `state: failure` (or `success`). This passes `verify_signature` (attacker's own secret) and `StatusHandler#process` writes a `Status` onto the victim's `Commit` row for that SHA.

None of the existing guards catch this: `verify_signature` only checks the payload's own claimed repo/org secret [1](#0-0) ; the `ExplicitParameters` schema for `StatusHandler` only validates types, not repository scoping [7](#0-6) ; there is no `repository.full_name` check anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker with a repository sharing a commit SHA with a victim stack (via fork of a public repo, a common Shipit deployment pattern) can write `Status` rows to the victim stack's commits without ever authenticating against the victim's webhook secret — "a payload for one repository mutating another's stack/commit," matching the Critical category in the rules. This can force CI state flips (`enable_ci_on_stack`), trigger `schedule_continuous_delivery`, and mark commits as `blocking?` on victim stacks that gate on `github-actions` or similar contexts, causing unauthorized blocking of deploys. The `ignore_ci: true` amplification claimed by the question does not add further impact beyond what already exists (an `ignore_ci` stack's deployability doesn't depend on CI status at all), but the core cross-tenant unscoped write is real and independent of that flag.

### Likelihood Explanation
Requires: (1) the victim repository/stack to be public or forkable so that identical git commits (and therefore identical SHAs) exist in a repo the attacker controls, and (2) the attacker's own repository to be registered with Shipit (or at least have a webhook configured pointing at the Shipit host) so `verify_signature` succeeds against their own secret. Both are low-cost/attacker-controlled — creating a fork and configuring a webhook against a self-owned repo is trivial and repeatable against any stack that shares commit history with an attacker-accessible repository.

### Recommendation
Scope `StatusHandler#process` (and similarly any handler using `Commit.where(sha: ...)` without repository scoping) to only the `Stack`/`Repository` derived from the authenticated payload, e.g. resolve `repository.full_name` from the verified payload and restrict the `Commit` lookup to stacks belonging to that repository before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new)
test "status for one repository cannot flip status on another stack's commit sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # different repository
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
                                                authored_at: Time.now, committer: shipit_users(:shipit),
                                                committed_at: Time.now, message: "shared")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
                                                    authored_at: Time.now, committer: shipit_users(:shipit),
                                                    committed_at: Time.now, message: "shared")

  # binding under test: only the attacker's own stack/commit should receive the status
  assert_equal attacker_commit.stack_id, attacker_stack.id
  refute_equal victim_commit.stack_id, attacker_commit.stack_id

  params = ExplicitParameters::Parameters.new(sha: shared_sha, state: "failure", context: "github-actions")
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  # FINDING: both commits receive the forged status, even though only attacker_stack's repo authenticated it
  assert victim_commit.statuses.reload.exists?(context: "github-actions", state: "failure")
  assert attacker_commit.statuses.reload.exists?(context: "github-actions", state: "failure")
end
```
This demonstrates the equality `commit.stack_id == authenticated_repository.stack_id` is violated: the victim's commit receives a status despite the request only being authenticated for the attacker's repository.
