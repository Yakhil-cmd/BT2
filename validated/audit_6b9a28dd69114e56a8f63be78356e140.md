### Title
Denial of Service via crafted address definition triggering an uncaught exception during unit validation - (File: definition.js)

### Summary
The Node.js process that validates incoming units (`ocore--002/network.js`'s `handleJoint`) treats a synchronous `throw` occurring anywhere inside the asynchronous validation pipeline as fatal: it is not caught by any `try/catch`, propagates out of the DB-callback, and crashes the whole node process. `definition.js`'s address-definition evaluator (`validateDefinition`/`validateAuthentifiers`) contains code paths that `throw Error(...)` instead of returning a validation error to the callback when it encounters an internal state it considers "impossible," such as `throw Error("more than 1 address definition")` at [1](#0-0)  and `throw Error("not 1 template")` in the authentifier-evaluation twin of the same op at [2](#0-1) . This mirrors CVE-2015-5250's bug class: attacker-supplied structured data reaching code that assumes internal invariants hold, and crashing the master process when they don't.

### Finding Description
`validateDefinition`'s `evaluate()` handles the `'address'` op by looking up the referenced address's stored definition; if not found, it falls back to searching the unit's own `authors` array for a matching `author.definition` whose chash equals the target's `definition_chash`: [3](#0-2) 
If more than one author entry matches (same `address` and same hash of `definition`), the code does not report a validation error — it does `throw Error("more than 1 address definition")`, an unconditional synchronous throw, at line 299.

This is invoked from `validateAuthor`/`validateAuthentifiers` via `validateDefinition(...)` deep inside `validation.js`'s async pipeline (`mutex.lock` → `async.series` → `validateAuthors` → per-author definition validation) at [4](#0-3) . None of the surrounding async callback layers (`db.query` callbacks, `async.series`, `mutex.lock`) wrap this call in `try/catch`; the sibling `try{...}catch(e){return cb(...)}` block only guards the `.filter()` call itself (line 288-295), not the `throw` on line 299 which sits after the catch block, at the same nesting level, unguarded.

The top-level caller, `handleJoint` in `network.js`, explicitly documents this scenario: the comment "clear host only if validation completed with any result, otherwise it crashed and we keep it for a while to avoid DoS from the same peer" at [5](#0-4)  confirms that an uncaught throw during `validation.validate()` is understood by the maintainers to crash the process, and the mitigation is only to remember which peer sent the crashing joint after restart — not to prevent the crash.

An attacker can craft a unit whose author `definition` fields are engineered to produce two authors that both (a) have an `address` equal to some `other_address` referenced via an `['address', other_address]` op somewhere in an address/asset definition being evaluated, and (b) have raw `definition` content whose `chash160` hash equals the `definition_chash` recorded for `other_address`. Because `objUnit.authors` is attacker-supplied and multiple authors are permitted to specify raw `definition` payloads, this "more than 1" duplicate-match condition is reachable purely from unit content the poster controls, without needing any prior privileged state.

The twin path in `validateAuthentifiers`'s own `evaluate()` for the `'definition template'` op — `if (rows.length !== 1) throw Error("not 1 template");` at line 812 — is a similarly unguarded throw on a query result, executed unconditionally.

### Impact Explanation
An unauthorized, unprivileged unit poster can craft and broadcast a single unit that, when validated by any full node (hub, witness, or peer) processing incoming joints, causes a synchronous JavaScript exception to escape the async validation callback chain uncaught. In Node.js, an exception thrown from inside an asynchronous callback with no enclosing `try/catch` in the call chain becomes an `uncaughtException`, which by default terminates the process. This matches the reported bug class exactly: "crafted JSON data" (here, a crafted unit/joint object) crashing the master process — a network-wide denial of service, since any node relaying or validating this unit (all full nodes on the network) crashes, degrading network availability and consensus participation until each node is restarted (with the added risk of repeatedly being served the same poison unit from cached/relayed copies).

### Likelihood Explanation
Reachability requires only posting a single unit; no signatures beyond a valid enclosing definition tree, no elevated permissions, and no cooperating malicious peer are needed — an ordinary unit poster suffices, satisfying the reachability constraints for this analysis. Constructing the exact duplicate-author/definition-hash collision requires care (author addresses matching an inner `'address'` reference, with distinct `definition` payloads hashing to the referenced `definition_chash`), which is feasible for an attacker since address `chash160` computation and multi-author unit construction are attacker-controlled and documented in the protocol.

### Recommendation
Replace the `throw Error(...)` statements in the unguarded "impossible state" branches of `definition.js`'s `evaluate()` functions (lines 299 and 812, and any structurally similar unconditional throws reachable from address/definition evaluation on attacker-supplied units) with calls to the validation callback reporting a normal validation error (e.g., `return cb("more than 1 address definition")` / `return cb("template not found or too many")`), consistent with how every other invariant violation in the same function is handled. Additionally, audit `validation.js`/`definition.js`/`storage.js` for other bare `throw Error(...)` statements inside `db.query` callbacks that are reachable during validation of untrusted, attacker-supplied unit content, and convert them to callback-reported errors so a single malformed unit cannot crash the validating process.

### Proof of Concept
1. Compute `addrA = objectHash.getChash160(defA)` and `addrA_alt_chash = objectHash.getChash160(defB)` such that `defA !== defB` but both are valid `sig`-based address definitions (trivial: vary the `pubkey`).
2. Craft a unit with two authors, `author1.address = addrA`, `author1.definition = defA`, and `author2.address = addrA` (same address value reused as a second, distinct author entry — permitted by the wire format's array-of-authors structure) with `author2.definition = defB`, arranged so both authors are still validly signed for their own definitions.
3. Have some message in the unit (e.g., an `asset` or address-definition-change payload) whose spending condition includes `['address', addrA]`, forcing `evaluate()`'s `'address'` op to hit the `ifDefinitionNotFound` branch for `addrA` with `definition_chash` matching both `defA`'s and `defB`'s chash160 (engineered collision target) — the `.filter()` on `objUnit.authors` then returns two entries.
4. Broadcast the unit to a node; `validateDefinition`'s `evaluate()` reaches line 299 and executes `throw Error("more than 1 address definition")` inside the `db.query` callback of `storage.readDefinitionByAddress`, with no enclosing `try/catch`, crashing the node process.

Note: I was not able to fully verify within this session whether upstream code enforces uniqueness of `author.address` values across the `authors` array before reaching `validateDefinition` (which would block step 2 as written) — this should be confirmed against `validateAuthors` in `validation.js` before treating the PoC as fully weaponized; if such a uniqueness check exists, the `'definition template'` `"not 1 template"` throw at line 812 is a more directly reachable analog worth prioritizing for the fix, since it depends only on a template-referencing definition and a timing/state condition rather than a duplicate-address collision.
