Found it: the binding that breaks is **organization authenticated (used to pick the signing secret) ≠ repository written (used to find/act on the `Stack`/`Team`)**.

### Title
Cross-organization webhook forgery — signature verified against `repository.owner.login`/`organization.login` while handlers act on unrelated `repository.full_name`/`organization.login` values not covered by that check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret to validate against from a field taken directly out of the *unverified* JSON body, then, once "verified", every handler blindly trusts other identity fields from that same body to decide what repository/team/stack to mutate.

### Finding Description
`verify_signature` picks the org used to look up the webhook secret straight from the payload: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . Handlers, however, independently pull the write-target identity out of the same untrusted body: `Handler#repository_name` reads `payload.dig('repository','full_name')` [3](#0-2) , and `MembershipHandler` reads `params.organization.login` to create/attribute a `Team` [4](#0-3) .

For events carrying both a `repository` and an `organization` key (e.g. `membership`), `verify_signature`'s `repository_owner` fallback prefers `repository.owner.login` over `organization.login` [1](#0-0) . If those two values differ within a single payload, the signature is validated against org A's secret (from `repository.owner.login`), while `MembershipHandler` trusts `organization.login` — a value never bound to the signature check — to decide which `Team.organization` to write. This is exactly the reported bug class: a field acted upon (`organization.login` for team writes) is never covered by the verification that "passed" (which validated a different field, `repository.owner.login`).

Additionally, per-organization webhook secrets mean the HMAC only proves "some app with a valid installation for org X sent this", not "the content fields describing target Y are trustworthy" — there is no re-validation that `repository.full_name`'s owner equals the org whose secret matched.

### Impact Explanation
Exploiting this requires the attacker to control (or have push/webhook access to) at least one GitHub organization/App installation already onboarded into this Shipit instance, and craft a payload where `repository.owner.login` (used for signing) differs from `organization.login` or `repository.full_name` (used for the write). That lets a legitimately-configured-but-attacker-controlled org forge writes (e.g. create/mutate a `Team` object under a different org's namespace, or trigger `sync_github` on a `Stack` belonging to a repository outside the authenticating org) it does not own. This crosses the "cross-repository writes" / authorization-escalation-into-`Shipit.github_teams` boundary called out as in-scope impact.

### Likelihood Explanation
Requires the instance to have more than one GitHub organization configured with webhook secrets (a normal Shipit-engine multi-org deployment, not a hypothetical mis-configuration) and requires the attacker to be able to deliver a webhook signed by one org's secret but describing another org's resource. This is a real but narrow condition — I could not fully confirm from static reading whether GitHub itself would ever deliver such a mixed-org payload for a real event (e.g., `membership` payloads are normally same-org for `repository`/`organization` fields), so exploitability depends on whether an attacker can control payload delivery outside GitHub's normal webhook dispatch (e.g., via a malicious/compromised GitHub App relay), which is a meaningful precondition I cannot verify with the tools available.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, standardize on a single canonical "authenticated organization" derived once, and have every handler (`MembershipHandler`, `PushHandler`, etc.) assert that any `organization.login` / `repository.owner.login` field referenced in the payload matches the organization whose secret validated the signature before performing any write.

### Proof of Concept
Not independently reproduced — this is a structural code-review finding based on: `webhooks_controller.rb`'s `repository_owner` fallback logic [1](#0-0)  versus `MembershipHandler`'s use of `params.organization.login` [4](#0-3) , and `Handler#repository_name` [3](#0-2) . A full PoC would require constructing a `membership` webhook payload with divergent `repository.owner.login` and `organization.login` values and confirming GitHub's webhook infrastructure (or a rogue delivering party) can actually produce such a payload signed by the org whose secret matches `repository.owner.login` — this last step could not be verified from the codebase alone.
