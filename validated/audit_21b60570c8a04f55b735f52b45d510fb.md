### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, allowing a token scoped to one stack to read status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method that `Shipit::Api::BaseController` uses to enforce that an `ApiClient` token can only reach the stack it is authorized for. The override resolves `params[:stack_id]` against **all** stacks instead of the stack-scoped collection, breaking the binding between "the stack a token authorizes" (`ApiClient#stack_id`) and "the stack the request actually touches".

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true`, and stack-scoped tokens are a first-class concept in the engine: `Shipit::Api::BaseController` enforces this scope in `stacks`/`stack`: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Any controller inheriting from `BaseController` and calling `stack` therefore only ever resolves a stack the caller's token is entitled to (`Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped).

`Shipit::Api::CCMenuController`, however, redefines both `authenticate_api_client` (to allow query-string token auth, appropriate for CCTray/CCMenu clients) and `stack`: [2](#0-1) 

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`stack` here calls `Stack.from_param!` directly on the `Stack` model — it never consults `stacks` or `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it does not check which stack the token is scoped to: [3](#0-2) 

As a result, any valid `ApiClient` token with `read:stack` permission — even one deliberately scoped to a single stack — can be used against `GET /api/stacks/:stack_id/ccmenu` for **any** `stack_id`, not just the one it was issued for.

### Impact Explanation
This breaks stack-level isolation for authenticated-but-restricted tokens: the equality that should hold is `stack_touched == stack(s) authorized by current_api_client.stack_id`, but for this endpoint `stack_touched = any Stack in the system`. An attacker holding a legitimately-issued, narrowly-scoped, read-only token (e.g., issued for a low-sensitivity public-facing stack) can enumerate `stack_id` values and pull CCMenu/CCTray XML for other stacks' latest deploy/rollback status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state), which is unauthorized read of stack/deploy state belonging to stacks the token was never granted. This matches the "unauthenticated/unauthorized read of stack state or deploy output" class of High severity issue.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token with the `read:stack` permission (the minimal, expected permission level for this exact endpoint) — no admin rights, no webhook secret, and no elevated permissions are needed. `stack_id` values are small sequential/param identifiers, making enumeration straightforward once a single valid token is obtained.

### Recommendation
Make `CCMenuController#stack` respect the token's stack scope, mirroring `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` can only resolve the stack it was created for, consistent with every other controller under `Shipit::Api::BaseController`.

### Proof of Concept
1. As an authorized Shipit user, create (or have created for you) an `ApiClient` scoped to a single stack (`stack_id` set, `permissions: ['read:stack']`) — this is the documented, intended low-privilege token type in this engine.
2. Note that `Stack.where(id: current_api_client.stack_id)` restricts this token everywhere else (e.g. `Api::StacksController#index`), as covered by the existing test: [4](#0-3) 
3. Send `GET /api/stacks/<other_stack_id>/ccmenu?token=<the_scoped_token>` for a *different* `stack_id` than the one the token is scoped to.
4. Observe the request succeeds (HTTP 200) and returns the other stack's CCMenu XML (name, `lastBuildStatus`, etc.), because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, bypassing the `current_api_client.stack_id` restriction that would otherwise apply.
