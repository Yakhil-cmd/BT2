Confirmed vulnerability: AA state-variable names are stored in the kvstore as delimiter-separated keys (`"st\n" + address + "\n" + var_name`), but unlike data-feed names, state-var names are **not** checked for embedded `\n` characters before being written or read.

### Title
AA State Variable Name Injection via Unvalidated Newline Characters in KV Storage Keys - (File: `formula/evaluation.js`)

### Summary
`oscript`'s `state_var_assignment` handler validates a dynamically computed state-var name only for length (`MAX_STATE_VAR_NAME_LENGTH`) and UTF-16 well-formedness (`isWellFormed()`), but never rejects the `\n` (newline) character, unlike the equivalent data-feed name check in `validation.js`/`aa_validation.js` which explicitly does `feed_name.indexOf('\n') >= 0`.

### Finding Description
`var_name` can be attacker-controlled: an AA can compute `var[expr] = value` where `expr` derives from `trigger.data` (fully controlled by whoever posts the triggering unit) or from another AA's response. The only checks applied are: [1](#0-0) 
No rejection of `\n` occurs, whereas the analogous, security-critical check exists for data-feed names: [2](#0-1) 
and again in AA definition validation: [3](#0-2) 
The unvalidated `var_name` is concatenated directly with `\n` delimiters into the kvstore key used for both writing and reading AA state: [4](#0-3) [5](#0-4) 
Range-scan readers such as `readAAStateVars` and `checkStorageSizes`/`initStorageSizes` parse keys back into `(address, var_name)` by naive index/substring splitting on the fixed 3-byte prefix and address length, assuming var_name is a single trailing segment: [6](#0-5) [7](#0-6) 
Because a var_name containing embedded `\n` sequences is accepted, an AA (driven by attacker-supplied trigger data) can craft state-variable keys whose byte layout collides with, or is misparsed relative to, keys generated for other logical variables/prefix ranges — the same class of bug as CVE-2022-4768 (unsanitized string used to build a structured/delimited record, "public_key_str ... leads to injection").

### Impact Explanation
This directly maps to the required impact classes:
- **Node disagreement / storage-size accounting corruption**: `checkStorageSizes` computes per-address storage size by parsing `var_name.length` from the byte offset after the address; a crafted `var_name` with `\n` changes what downstream code perceives as the variable name length versus what was charged during `updateStorageSize`, causing storage-size accounting divergence, and `checkStorageSizes` throws (`"storage size mismatch"`) — a self-inflicted denial-of-service/crash on nodes that run this integrity check, or persistent inconsistency between `aa_addresses.storage_size` (SQL) and the raw KV data.
- **AA fund loss/freezing**: `updateStorageSize` bills `var_name.length + newSize` against the AA's byte balance [8](#0-7) ; crafted long/structured `var_name` values distort the byte-balance vs. actual KV storage relationship used to gate whether an AA can respond, which can be leveraged to under/over-charge storage against an AA's balance.

### Likelihood Explanation
Reachable by any unprivileged unit poster: composing `trigger.data` with a string value containing `\n`, referenced by a target AA's own `var[$name] = ...` code (a common, supported oscript pattern), requires no special privileges and no cooperation beyond a normal AA that uses attacker-influenced field/variable names — likelihood is high given how directly the trigger flows into the vulnerable sink.

### Recommendation
Add the same explicit `\n`-rejection check used for data-feed names (`validation.js`/`aa_validation.js`) to the state-var-name validation path in `formula/evaluation.js` (and the corresponding validation logic in `formula/validation.js`), rejecting any `var_name` containing `\n` before it is used to build or parse kvstore keys.

### Proof of Concept
1. Deploy an AA whose `state` message does `var[trigger.data.name] = 1;` (a legitimate, common oscript pattern for dynamic state keys).
2. Post a trigger unit with `data: { name: "foo\nbar" }`.
3. The AA validation path only checks length/`isWellFormed()` — the newline passes — and `saveStateVars()` writes key `"st\n" + address + "\n" + "foo\nbar"` to the kvstore, corrupting the expected single-segment `var_name` invariant relied upon by `readAAStateVars`, `checkStorageSizes`, and `initStorageSizes`, which parse the key assuming no additional `\n` after the address.
