### Title
Cross-tenant webhook forgery via mismatched organization/repository fields in `WebhooksController#verify_signature` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit's multi-tenant GitHub App configuration (`Shipit.github(organization:)`) selects a per-organization `webhook_secret` based on one field of the inbound JSON payload (`repository.owner.login`, falling back to `organization.login`), but every downstream webhook handler acts on a *different* field of that same payload (`repository.full_name`) to resolve the `Repository`/`Stack` to mutate. Because HMAC verification only proves the payload was signed with the secret belonging to the organization named in `repository.owner.login`/`organization.login`, and does not cross-check that this organization is a prefix of `repository.full_name`, a tenant that legitimately owns one onboarded GitHub organization (and therefore legitimately knows/can generate valid signatures for its own configured `webhook_secret`) can craft a payload where the `owner.login`/`organization.login` field names their own org (to pass signature verification) while `repository.full_name` names a *different* organization's repository, causing handlers to archive/unarchive/create Review Stacks or otherwise mutate state belonging to a repository they do not own.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization exclusively from the payload itself: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-org config block (containing its own `webhook_secret`) via `github_app_config(organization)`: [2](#0-1) 

Once the signature check passes, `create` dispatches the *entire raw payload* to every registered handler for the event, with no further validation: [3](#0-2) 

Every pull-request handler (`OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `EditedHandler`) and the base `Handler` class independently resolve the target repository/stack from a *separate* field, `repository.full_name`: [4](#0-3) [5](#0-4) 

Nothing in the request path enforces the invariant `repository.owner.login == repository.full_name.split('/').first`. GitHub itself always keeps these consistent for genuine deliveries, but a tenant crafting a raw HTTP POST directly to Shipit's webhook endpoint controls every JSON field independently, subject only to producing a byte-correct HMAC-SHA256 signature over the whole body using *the secret for whichever organization they choose to declare in `owner.login`*.

This breaks the binding the report's bug class describes: **the organization whose credential (webhook_secret) authenticated the request** vs. **the repository whose state is actually written by the handlers**. Before the attacker's request, these two are supposed to be the same tenant's organization/repository; the controller only checks the former, the handler acts on the latter, and no code ties them together.

### Impact Explanation
An organization onboarded to a shared/multi-tenant Shipit instance (one that knows its own `webhook_secret`) can forge webhook events that are accepted as authentic for a different organization's repository. Depending on which handler is targeted, this permits unauthorized cross-repository state changes: archiving/unarchiving Review Stacks, creating Review Stacks (`ReviewStackAdapter#create!` in `review_stack_adapter.rb`), or updating pull-request metadata for a repository the attacker does not own. This is a cross-repository write performed without holding write access to, or a valid credential for, the victim repository/organization — aligning with the "cross-repository writes" high/critical impact class in scope.

### Likelihood Explanation
Exploitability depends entirely on the deployment being configured with more than one GitHub organization under `secrets.github` (multi-tenant `TOP_LEVEL_GH_KEYS` schema, see `github_organizations`/`github_app_config` in `lib/shipit.rb#190-200`), each with its own `webhook_secret`, and at least one of those organizations being controlled by an untrusted/lower-trust tenant. In a single-organization deployment (the more common `secrets.github` top-level schema) `github_default_organization` returns `nil` and the whole class of attack collapses, since there is only one secret and hence only one implicit "owner." I could not verify from the indexed files whether any officially documented/expected deployment actually runs multiple organizations with mutually distrusting owners sharing one Shipit instance — this is a configuration precondition I was not able to confirm or rule out with the available context.

### Recommendation
In `WebhooksController`, after verifying the signature, assert that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, have handlers resolve the repository using the already-authenticated `repository_owner` rather than re-parsing an unrelated payload field, so the field used for authorization and the field used for the mutation are the same value.

### Proof of Concept
1. Attacker's organization `attacker-org` is configured in Shipit as a tenant with its own `webhook_secret`.
2. Attacker computes `sig = HMAC-SHA256(webhook_secret_for_attacker_org, raw_body)` where `raw_body` is:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { "...": "...", "head": {"sha": "...", "ref": "attack"}, "user": {"login": "attacker"}, "assignees": [], "labels": [] },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: pull_request` and `X-Hub-Signature: sha1=<sig>` (or the algorithm accepted by `verify_webhook_signature`).
4. `verify_signature` computes `repository_owner => "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature matches — request passes.
5. `PullRequest::OpenedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, if provisioning conditions are met, creates/mutates a Review Stack for `victim-org/victim-repo`, which the attacker does not own or control.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
