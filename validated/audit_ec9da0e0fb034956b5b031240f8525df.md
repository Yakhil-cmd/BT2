**Rationale:** The advisory GHSA-735f-pc8j-v9w8 / CVE-2024-7254 is specific to the **Java** implementation of Protocol Buffers (`protobuf-java`, `protobuf-javalite`, `protobuf-kotlin`, and the JRuby gem `google-protobuf`), affecting Maven and RubyGems ecosystems only. `polkadot-sdk` is a Rust codebase and does not depend on `protobuf-java` or any of the affected Maven/RubyGems packages anywhere in its dependency tree.

The only protobuf usage found is in the Substrate networking layer, which compiles `.proto` schema files (e.g. `substrate/client/network/sync/src/schema/api.v1.proto`) using the Rust `prost` crate, a completely independent implementation not affected by this CVE. [1](#0-0) [2](#0-1) 

Separately, the codebase's own SCALE-codec recursive decoding paths (which are the closest architectural analog to "recursion during deserialization causing stack overflow") already have explicit depth/recursion guards in place, e.g. XCM's `DoubleEncoded` decoding tracks `nesting_count` against `RECURSION_LIMIT` and `MAX_XCM_DECODE_DEPTH` [3](#0-2) , XCM instruction decoding is bounded by `MAX_INSTRUCTIONS_TO_DECODE` and tested against deeply nested payloads [4](#0-3) , and `WrapperOpaque`/`WrapperKeepOpaque` decoding is bounded by `MAX_EXTRINSIC_DEPTH` [5](#0-4) . These mitigations were also reinforced by a targeted fix for recursive XCM decoding [6](#0-5) .

Given (1) the complete ecosystem/dependency mismatch (Java/Ruby library vs. Rust codebase with no such dependency), and (2) the task's explicit instruction to reject dependency-only findings and generic resource-exhaustion/oversized-input claims, there is no demonstrable Polkadot SDK analog for this specific advisory.
