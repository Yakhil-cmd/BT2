### Title
Assets requiring attestor approval (`spender_attested`) can permanently trap funds inside an Autonomous Agent when the depositor's attestation is revoked - ([File: aa_composer.js])

### Summary
Blueberry's report describes a blacklist-token scenario where a fixed refund address (the position owner) becomes unable to receive tokens back, permanently freezing the position. The analogous mechanism in ocore is the `spender_attested` asset flag: transfers/issues of such an asset are only valid if **every output address** is currently attested by the asset's attestor(s) (`validation.js`). If an Autonomous Agent (AA) holds a user's balance of a `spender_attested` asset (e.g. received as part of a trigger payment) and later needs to pay it back to that same user — either through the AA's own `payment` message logic or through the automatic bounce mechanism — the payment will permanently fail validation once the user's attestation is revoked, with no way for the AA or the user to redirect the funds to a different, still-attested address.

### Finding Description
When an asset is defined with `spender_attested: true`, `validatePaymentInputsAndOutputs` requires that all output addresses of any payment in that asset be attested at validation time: [1](#0-0) 

This check is unconditional and per-unit: it doesn't matter that the address was attested when the AA received the deposit — it must be attested again at the time of *every subsequent* payment out of that asset, including refunds.

Inside `aa_composer.js`, when an AA's evaluated response can't be completed (e.g. because a payment message fails a validation check like this one), the AA response is bounced via the `bounce()` function, which reconstructs a payment sending the (fee-adjusted) trigger outputs straight back to `trigger.address`: [2](#0-1) 

If this bounce-back payment itself fails unit validation (because `trigger.address`'s attestation has been revoked and the asset is `spender_attested`), the code path re-enters `bounce()`, but the `bBouncing` guard causes it to simply call `finish(null)` and swallow the failure silently: [3](#0-2) 

The same terminal failure mode applies to any deliberate `payment` message an AA author writes to send the attested asset back to a specific user address (e.g. a withdrawal/close-position style AA): `completePaymentPayload`/`validateAndSaveUnit` will reject the unit because the destination address is no longer attested, and there is no AA-level mechanism to designate an alternate, currently-attested recipient address for the same logical owner. [4](#0-3) 

Because the incoming trigger payment was already credited to the AA's balance at initialization (`updateInitialAABalances`), and the compensating outbound payment can never validate again once the user is de-attested, the balance is durably stuck inside the AA with no code path to move it out.

### Impact Explanation
Any AA-based application that custodies a `spender_attested` asset on behalf of individual depositors (vaults, order books, escrow/AMM-like contracts, staking or lending-style AAs) is exposed: once a user's attestation for that asset is revoked by the attestor (the on-chain equivalent of being "blacklisted"), that user's principal held by the AA becomes permanently unrecoverable — neither the AA's bounce mechanism nor a manually authored withdrawal message can produce a validatable output to that user, and there is no ownership-transfer or alternate-address mechanism in the oscript/AA framework to work around it. This is a concrete AA fund-freezing condition, matching the "AA fund loss or freezing" impact class.

### Likelihood Explanation
This is reachable by any ordinary participant: an unprivileged AA trigger sender who deposits a `spender_attested` asset into an AA, and whose attestation is subsequently revoked by the (legitimate) attestor for any reason (compliance, expiry, dispute). No special privilege over the AA or the attestor is required from the affected user's perspective — the freezing is a direct, deterministic consequence of the asset's declared attestation requirement combined with the AA's fixed-address bounce/payout logic.

### Recommendation
- Provide AA authors a documented pattern/primitive to redirect payouts of `spender_attested` assets to a currently attested address supplied by the user (rather than only `trigger.address`), and clearly document in AA-authoring guidance that outbound payments of attested assets must tolerate the destination becoming non-attested.
- Consider allowing the bounce mechanism to fall back to paying out in `base` value (or skip only the failing asset) instead of aborting the whole bounce silently when one asset's output fails the attestation check, so unrelated assets/bytes are not also stuck.
- At minimum, surface a distinguishable error/log signal instead of silently calling `finish(null)` when a second-level bounce fails validation, so wallets/users can detect stuck balances.

### Proof of Concept
1. Attestor A defines asset `X` with `spender_attested: true`, attestors `[A]`.
2. Attestor A attests user `U`'s address as eligible.
3. `U` sends a trigger payment of asset `X` to AA `Z`, which is designed to send `X` back to `trigger.address` on a subsequent request/withdrawal message (or would bounce it back on failure of the primary logic).
4. Attestor `A` revokes `U`'s attestation (asset attestor lists are dynamic; see `asset_attestors`/`checkAttestorList` handling in `validation.js`).
5. `U` sends a withdrawal trigger to `Z` (or `Z`'s primary logic bounces for an unrelated reason). The resulting `payment` message with `asset: X`, output address `U`, fails `validatePaymentInputsAndOutputs`'s attestation check (`validation.js:2632-2641`), causing the unit to fail validation in `validateAndSaveUnit` (`aa_composer.js:1800-1838`).
6. `bounce()` is invoked to return `X` to `trigger.address = U`; this bounce payment fails the same attestation check; since `bBouncing` is already `true`, `finish(null)` is called and the failure is swallowed (`aa_composer.js:909-945`).
7. AA `Z`'s balance retains `U`'s deposited amount of `X` indefinitely, with no supported path for `U` (or anyone) to extract it.
