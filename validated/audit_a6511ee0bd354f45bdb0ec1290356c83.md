## Title
Cross-repository status webhook forgery leads to unauthorized deploy via `StatusHandler`'s unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
The webhook signature check binds an incoming payload to *one* GitHub organization's secret, but the `status` event handler applies the payload's content to *any* commit in the entire database that matches the given SHA, with no check that the commit belongs to a repository owned by the organization whose secret was verified. An attacker who legitimately controls one Shipit-tracked GitHub organization (and therefore possesses that organization's own webhook secret) can forge a signed `status` webhook that injects a fabricated "success" CI status onto a commit belonging to a completely different, unrelated stack/repository, potentially triggering an unauthorized continuous deployment on that unrelated stack.

## Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the signature against using a field taken directly from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

This only proves the request was signed by whoever holds the webhook secret for `repository_owner` (i.e., one specific organization already onboarded into this Shipit instance). It says nothing about which repository the payload's other fields refer to.

`Shipit::Webhooks::Handlers::Handler` (the base class used by most handlers) does scope subsequent lookups to the repository named in the payload via `repository_name`/`stacks`: [3](#0-2) 

However, `StatusHandler#process` bypasses this scoping entirely and looks up commits globally by SHA alone: [4](#0-3) 

Because SHA-1 commit hashes are attacker-observable (visible in any public GitHub repo, PR, or Shipit UI) and are not scoped per-organization, any organization admin able to authenticate a webhook body with *their own* org's secret can name a SHA belonging to *another* org's stack. `Commit.where(sha: params.sha)` will match it and call `create_status_from_github!`, which persists a new `Status` and can trigger deploy-relevant side effects: [5](#0-4) [6](#0-5) [7](#0-6) 

If the targeted stack has continuous deployment enabled, `ContinuousDeliveryJob`/`trigger_continuous_delivery` will deploy the (still real, unmodified) commit as soon as it's marked deployable: [8](#0-7) 

The binding that is broken: **organization authenticated by the webhook signature (`repository_owner`, derived from `Shipit.github(organization: repository_owner)`) ≠ repository/stack whose `Commit` record is actually written (`Commit.where(sha: params.sha)`, unscoped)**.

## Impact Explanation
This lets an actor who only controls one onboarded, low-trust GitHub organization forge a "green" CI status for a commit in someone else's stack. Combined with continuous deployment, this can cause an **unauthorized deploy** to be triggered for a target the attacker has no legitimate relationship to — this maps directly to the Critical impact category ("an unauthorized deploy, rollback or merge"). Even absent continuous deployment, it corrupts commit/CI state (`deployable_status`, merge-request auto-merge scheduling via `schedule_merges`) for stacks the forger's credentials were never meant to authorize.

## Likelihood Explanation
Requires only knowledge of one legitimately-configured organization's webhook secret (something any org admin onboarded to a multi-org Shipit instance already has by design) plus a target commit SHA (public information on GitHub). No Shipit session, API token, or privileged account is required — the `/webhooks` endpoint is intentionally unauthenticated aside from the per-org signature check. This is a realistic "unprivileged attacker" scenario within the accepted analog boundary (organization authenticated vs. repository written).

## Recommendation
In `StatusHandler#process` (and any other handler that doesn't already scope via `Handler#stacks`), constrain the `Commit` lookup to commits belonging to stacks under the `repository_name`/`stacks` derived from the payload's `repository.full_name`, and cross-check that this repository's owning organization matches the `repository_owner` used to select the verifying webhook secret, rejecting the event otherwise.

## Proof of Concept
1. Attacker administers `attacker-org`, which is a legitimate GitHub organization onboarded into the shared Shipit instance, with its own `webhook_secret` configured under `Shipit.github(organization: 'attacker-org')`.
2. Attacker observes (via public GitHub) the SHA of the next commit awaiting deploy on `victim-org/victim-repo`'s continuously-deployed stack.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature` with `attacker-org`'s webhook secret (`Hook::DeliverySigner`-equivalent HMAC-SHA1) and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` and successfully verifies the signature using attacker-org's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit (owned by an unrelated org/stack), and calls `create_status_from_github!`, creating a `success` status.
7. If `victim-org/victim-repo`'s stack has `continuous_deployment: true`, `schedule_continuous_delivery` → `ContinuousDeliveryJob` deploys the commit — an unauthorized deploy triggered purely by forged webhook content signed with an unrelated organization's secret.
