### Title
Stack-scoped ApiClient token can read CCMenu status of any stack, bypassing token's stack binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single `Stack` via the `stack_id` column, and `Api::BaseController#stacks` is supposed to enforce that scope for every request: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `Api::CCMenuController`, however, overrides the `stack` accessor and loads the stack directly via `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping [2](#0-1) . A token that is only supposed to authorize reads for one stack can therefore be used to read CCMenu status for every stack in the installation.

### Finding Description
`Api::BaseController#stack` is meant to be the single point that binds a request's target `Stack` to the authenticated `ApiClient`'s authorized scope:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`Api::CCMenuController` redefines `stack` to skip the `stacks` scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The only authorization gate that remains is `require_permission :read, :stack`, which merely checks that `read:stack` is present in the `ApiClient#permissions` list — it never checks that the requested `stack_id` matches `current_api_client.stack_id` [5](#0-4) . This is exactly the "unchecked binding" bug class from the external report: the account/scope that is authenticated (`current_api_client.stack_id`) is never checked against the resource that is actually acted upon (`params[:stack_id]`).

The route `/api/stacks/*stack_id/ccmenu` is open to any `stack_id` path segment [6](#0-5) , and the fixture data shows this scoping is a real, intentional feature: `here_come_the_walrus` is created with `stack: shipit` and only `read:stack` permission [7](#0-6) , and the corresponding test explicitly verifies that such a scoped client only sees its own stack through the (correctly scoped) `StacksController#index` endpoint [8](#0-7) . `CCMenuController` has no equivalent test asserting this scoping, and the code path shows it does not enforce it.

### Impact Explanation
This breaks the binding: "stack a token authorises" (`current_api_client.stack_id`) versus "stack it touches" (`params[:stack_id]` in `CCMenuController#stack`). A holder of a narrowly-scoped, single-stack read-only `ApiClient` token — which is the least-privileged kind of API credential Shipit issues, and is even auto-generated and handed out via `CCMenuUrlController#fetch` for embedding in third-party CI dashboards [9](#0-8)  — can use that token to enumerate CCMenu status (build/deploy status, lock status, last build label/time) for every other stack in the Shipit installation, including private/unrelated repositories' deploy state, regardless of the token's intended single-stack scope. This is an authorization-scope escalation yielding unauthorized read of stack state.

### Likelihood Explanation
Likely, given that `CCMenuUrlController` actively mints and hands out exactly this class of token (single-stack, `read:stack`-only) to any authenticated Shipit user for the "CCMenu" integration URL feature, meaning such restricted tokens are a normal, expected artifact in real deployments, not a hypothetical edge case.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or update it to route through the scoped `stacks` helper from `Api::BaseController`) so the CCMenu endpoint resolves `params[:stack_id]` against `stacks` (i.e., `stacks.from_param!(params[:stack_id])`) rather than the unscoped `Stack` model, consistent with every other stack-scoped API endpoint.

### Proof of Concept
1. As an authenticated Shipit user, visit any stack's CCMenu integration URL feature, causing `CCMenuUrlController#fetch` to mint (or reuse) an `ApiClient` scoped to `stack: <StackA>` with only `read:stack` permission, and obtain its `authentication_token`.
2. Using that token via HTTP Basic auth, send `GET /api/stacks/<StackB-owner>/<StackB-repo>/<StackB-env>/ccmenu` for a different, unrelated `StackB`.
3. `authenticate_api_client` in `CCMenuController` successfully authenticates the token [10](#0-9) ; `require_permission :read, :stack` passes because `read:stack` is in the token's permission list; `stack` resolves `StackB` directly via `Stack.from_param!`, bypassing the `stack_id` scope check.
4. The response renders `StackB`'s CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.), even though the token was only ever authorized to read `StackA`.
