### Title
Bare carriage-return (`\r`) in workflow log lines bypasses `asciisanitizer` and `bufio.Scanner` line splitting, allowing terminal status-line spoofing - ([File: pkg/cmd/run/view/view.go])

### Summary
`copyLogWithLinePrefix` in `pkg/cmd/run/view/view.go` sanitizes each log stream with `asciisanitizer.Sanitizer` and then splits it with `bufio.NewScanner`'s default `ScanLines` split function before printing `prefix + scanner.Text() + "\n"` via `fmt.Fprintf`. Because `ScanLines` only splits on `\n` (stripping a trailing `\r\n`), a bare `\r` embedded in the middle of a log line is preserved verbatim inside the string returned by `scanner.Text()` and is written unmodified to the terminal.

### Finding Description [1](#0-0) 

`displayLogSegments` builds a `prefix` from the job name and step name and calls `copyLogWithLinePrefix(w, rc, prefix)` for each log segment fetched from the run's log archive/stream, which is attacker-influenced content when the workflow run belongs to a PR/fork the attacker controls (e.g. logs that echo a branch name, PR title, commit message, or any other attacker-supplied value into `echo`/build output).

`copyLogWithLinePrefix` wraps the raw log reader with `transform.NewReader(r, &asciisanitizer.Sanitizer{})` and then uses `bufio.NewScanner`, which by default uses `bufio.ScanLines`. `ScanLines` treats `\n` as the sole line terminator and only trims a *trailing* `\r` immediately preceding a `\n`; any `\r` that occurs elsewhere in the line (not immediately followed by `\n`) is left inside the token returned by `scanner.Text()`. `asciisanitizer` (from `cli/go-gh`) is designed to neutralize BOM/C1 control codes and dangerous escape sequences, but it treats `\r` as ordinary text content (it is a legitimate CRLF component), so it does not strip or escape it.

As a result, an attacker who can get a line such as:
```
"buildOK\rSUCCESS: All checks passed\n"
```
into the raw log stream will have that exact string (including the embedded `\r`) survive both the sanitizer transform and the scanner round-trip. `fmt.Fprintf(w, "%s%s\n", prefix, scanner.Text())` then writes `prefix` immediately followed by the attacker string to the victim's terminal. On any terminal emulator, the bare `\r` moves the cursor back to column 0 of the current line without clearing it, so the text following `\r` visually overwrites the `prefix` (job name/step name) and any preceding characters on that same terminal row, letting the attacker forge what appears to be a different job name or status text in the victim's `gh run view --log` output.

### Impact Explanation
This is a bypass of the CLI's own output-sanitization control that is explicitly intended to stop exactly this class of attack (see the design intent stated at `pkg/iostreams/untrusted.go` and `pkg/iostreams/iostreams.go`, where `asciisanitizer`/`Untrusted` wrapping exists specifically so "external content" cannot forge terminal display). Because the CR character is not neutralized, an attacker who controls PR/fork content that ends up echoed into workflow logs can visually spoof the job name or step name shown to a victim running `gh run view --log` (or `--job`), misrepresenting which job/step produced which output. This is a terminal-output-spoofing / display-forgery issue rather than code execution or credential exfiltration, so it does not independently rise to RCE, credential theft, file write, or verification bypass — it is a scoped output-integrity issue that could be used to make a malicious or failing log segment appear to belong to a different, seemingly-benign job.

### Likelihood Explanation
Feasible and repeatable: any workflow run whose job/step logs contain attacker-controlled text (fork PR title/branch name/commit message echoed by a workflow step, or output an attacker's code produces during CI) can include a raw `\r` byte. No special privileges beyond triggering/participating in a workflow run (e.g., opening a PR from a fork that a repo already runs CI against) are required, matching the stated precondition of "workflow run triggered by attacker-controlled PR/fork content."

### Recommendation
In `copyLogWithLinePrefix`, either:
- Strip or escape bare `\r` characters from `scanner.Text()` before writing (e.g., `strings.ReplaceAll(line, "\r", "")` or render it as `\r` literal via `%q`-style escaping), or
- Configure `asciisanitizer`/the scanner pipeline to treat `\r` as a line boundary as well (custom `SplitFunc` that also splits on bare `\r`), so partial-line content cannot be reprinted starting at column 0 mid-line.

### Proof of Concept
```go
func TestCopyLogWithLinePrefix_CRSpoofing(t *testing.T) {
	var buf bytes.Buffer
	logLine := "buildOK\rFAKE: All checks passed\n"
	err := copyLogWithLinePrefix(&buf, strings.NewReader(logLine), "job\tstep\t")
	require.NoError(t, err)

	out := buf.String()
	// Demonstrates the bare \r survives untouched in the emitted output,
	// which will overwrite "job\tstep\tbuildOK" on a real terminal.
	require.Contains(t, out, "\r")
	require.Contains(t, out, "job\tstep\tbuildOK\rFAKE: All checks passed\n")
}
```
Expected: the assertion passes, showing the raw `\r` is present in the final terminal-bound output, confirming the sanitizer/scanner pipeline does not neutralize mid-line carriage returns.

func displayLogSegments(w io.Writer, segments []logSegment) error {
	for _, segment := range segments {
		stepName := "UNKNOWN STEP"
		if segment.step != nil {
			stepName = segment.step.Name
		}

		rc, err := segment.fetcher.GetLog()
		if err != nil {
			return err
		}

		err = func() error {
			defer rc.Close()
			prefix := fmt.Sprintf("%s\t%s\t", segment.job.Name, stepName)
			if err := copyLogWithLinePrefix(w, rc, prefix); err != nil {
				return err
			}
			return nil
		}()

		if err != nil {
			return err
		}
	}

	return nil
}

func copyLogWithLinePrefix(w io.Writer, r io.Reader, prefix string) error {
	sanitized := transform.NewReader(r, &asciisanitizer.Sanitizer{})
	scanner := bufio.NewScanner(sanitized)
	for scanner.Scan() {
		fmt.Fprintf(w, "%s%s\n", prefix, scanner.Text())
	}
	return nil
}
