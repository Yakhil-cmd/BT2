### Title
`ERC20Transactor::withdraw_asset_with_surplus` credits the fixed requested amount instead of the ERC20 contract's actual received/transferred amount, allowing fee-on-transfer/non-standard ERC20 tokens to create phantom XCM asset backing - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
This is a Polkadot SDK analog of the reported Gearbox bug: the external report shows a contract assuming `transferFrom` moves exactly `amountIn`, ignoring that fee-charging ERC20 tokens can deliver less than requested, and recommends checking the actual resulting balance instead of the nominal amount. `ERC20Transactor` (used as an XCM `TransactAsset` for revive-based ERC20 assets on Asset Hub) has the identical pattern: it issues a Solidity `transfer(to, value)` call and, upon a `true` boolean return, unconditionally mints an `AssetsInHolding` credit equal to the requested `amount`, never verifying how much the checking/beneficiary account balance actually changed.

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the transactor calls the ERC20 contract's `transfer(checking_address, amount)` via `pallet_revive::Pallet::<T>::bare_call`, and on success: [2](#0-1) 

it unconditionally constructs `AssetsInHolding` with `Erc20Credit(amount)` — the value requested in the XCM `Asset`, not the amount actually received by `TransfersCheckingAccount`. The only check performed is that the ABI-decoded boolean return value is `true`; there is no post-call balance read of the checking account (e.g. via `IERC20::balanceOf`) to confirm `amount` tokens actually landed there.

The symmetric `deposit_asset_with_surplus` path has the same shape [3](#0-2) : it transfers `amount` from the checking account to the beneficiary and treats a `true` return as full success, again with no balance verification.

This is exactly the invariant violated in the report: for ERC20 tokens that deduct a fee/tax on `transfer`/`transferFrom` (fee-on-transfer tokens, common on EVM but now reachable in a FRAME/`pallet-revive` context since any deployed Solidity contract satisfying the `IERC20` interface and matched by `Matcher: MatchesFungibles<H160, u128>` can be registered as a foreign/ERC20 XCM asset), the checking account or beneficiary receives `amount - fee`, yet the runtime's XCM holding/accounting believes `amount` was moved. Since `Matcher` and asset registration determine which contracts are eligible, and any user can potentially get an ERC20 contract registered as a transactable asset (this depends on the asset registration governance/config, which I could not fully trace within tool budget), a token contract that behaves as fee-on-transfer would let a user's XCM program construct holding credits larger than the tokens actually escrowed in the checking account.

### Impact Explanation
If reachable with an attacker-deployed or attacker-influenced ERC20 asset, the XCM executor's internal holding accounting becomes decoupled from real on-chain ERC20 balances held in `TransfersCheckingAccount`. Downstream XCM instructions (`DepositAsset`, `BuyExecution`, further transfers) operate on the inflated `Erc20Credit` amount, which can let a withdrawal appear fully backed while the checking account is short by the fee amount — a form of unbacked/uncollateralized asset movement through the ERC20 bridge, potentially draining the checking account's real balance relative to what the ledger believes is held, or causing later legitimate withdrawals to fail/revert unexpectedly (denial of availability for other holders of the same wrapped asset).

### Likelihood Explanation
Requires: (1) an ERC20 contract with fee-on-transfer or otherwise non-standard `transfer` semantics being usable as a registered/matched XCM asset via `Matcher: MatchesFungibles`, and (2) that contract not reverting on the fee deduction (returns `true`). I was not able to fully confirm, within the available tool budget, whether asset registration for this transactor is permissionless (any user-deployed `pallet-revive` contract) or gated behind privileged asset-registration governance on Asset Hub — this materially affects likelihood and I could not verify the `Matcher`/registration configuration in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs` before running out of iterations.

### Recommendation
After the `transfer` call succeeds (boolean `true`, no revert), read back the actual token balance delta on `TransfersCheckingAccount` (withdraw path) or on the beneficiary (deposit path) via `IERC20::balanceOf`, and construct `Erc20Credit`/report the transferred amount using that measured delta rather than the originally requested `amount` — mirroring the report's recommendation to use the actual resulting balance instead of the nominal transfer amount.

### Proof of Concept
Not executed. A concrete PoC would require: deploying (via `pallet_revive`) a minimal `IERC20`-compatible contract that deducts a fee on `transfer` and returns `true`, registering/matching it through the runtime's `Matcher` for `ERC20Transactor`, and running a local integration test (in the style of `polkadot/xcm/pallet-xcm/src/tests/assets_transfer.rs`) that executes an XCM `WithdrawAsset` for that asset and asserts `TransfersCheckingAccount`'s real ERC20 balance is less than the `Erc20Credit` amount subsequently used in `DepositAsset`. This reproduction was not run; the finding is based on static code inspection of `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` only, and the asset-registration/permission gating for this transactor's `Matcher` was not fully verified.
