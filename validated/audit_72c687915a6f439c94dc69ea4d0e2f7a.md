## Analog Found

### Title
Insufficient "initial deposit" detection in shares-based AMM sample AA allows first-depositor fund loss - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled Uniswap-like market-maker AA template detects whether a deposit is the "first" one by checking raw asset/byte balances (`$asset_balance == 0 OR $bytes_balance == 0`) instead of checking whether share tokens (`var['mm_asset_outstanding']`) have actually been issued. An attacker can pre-poison the pool balances with a tiny, un-accounted donation so that neither balance is exactly `0` while `mm_asset_outstanding` is still `0`, forcing the legitimate first investor's share calculation down the ratio-based branch, which divides by the (still-zero) `mm_asset_outstanding` and mints `0` shares while the investor's real payment is absorbed permanently into the AA's balance.

### Finding Description
The AA's "invest in MM" case computes share issuance as: [1](#0-0) 

Any incoming payment to an AA address is a primary trigger and is unconditionally added to the AA's tracked balance in `updateInitialAABalances` before any `if`/case is evaluated: `trigger_opts.assocBalances[address][asset] = (...) + trigger.outputs[asset]`. [2](#0-1) 

If none of the AA's `cases` match a given trigger (e.g. because the amounts don't satisfy any `if` condition), the AA performs no state change and simply keeps the received funds — this "silently absorb funds with no matching case" behavior is a documented outcome of the engine (`handleSuccessfulEmptyResponseUnit`), and is even used intentionally in other samples ("silently accept coins" pattern): [3](#0-2) 

Exploit path:
1. Right after the "define share asset" case runs (so `$mm_asset` is set but `var['mm_asset_outstanding']` is still unset/`0`), the attacker sends a single unit to the AA with **both** a small amount of the underlying asset (`$asset`) **and** a small amount of base bytes that is `<= 1e5` (so `trigger.output[[asset=base]] > 1e5` is false) and no `trigger.data`.
2. None of the AA's cases match this trigger: "invest" fails the `>1e5` bytes check, "divest" requires `mm_asset` received, "exchange bytes to asset" fails the `>1e5` check, and "exchange asset to bytes" requires `var['mm_asset_outstanding']` to be truthy (it is `0`). No case is selected, so the funds are silently absorbed into the AA's balance with **no state update** — `mm_asset_outstanding` remains `0`, but both `balance[$asset]` and `balance[base]` are now nonzero.
3. When a legitimate user makes the real first investment (`trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0`), the code computes `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and `$bytes_balance = balance[base] - trigger.output[[asset=base]]`. Because of the attacker's dual donation in step 1, **both** are now nonzero, so `$asset_balance == 0 OR $bytes_balance == 0` is **false**, and the code takes the ratio-based branch instead of the "initial deposit" branch.
4. `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` — since `var['mm_asset_outstanding']` is still `0`, `$issue_amount` evaluates to `0` regardless of how much real value the legitimate investor deposits.
5. The state update then does `var['mm_asset_outstanding'] += $issue_amount` (`+= 0`), so outstanding shares remain permanently `0`. The victim's real deposit is now part of the AA's balance, but they received `0` shares of the `$mm_asset` token, and every future depositor faces the same broken zero-share state — permanent, unrecoverable loss of the victim's funds to the AA (nobody, including the attacker, can ever redeem this trapped value because `mm_asset_outstanding` is stuck at `0`, so `investor_share = mm_asset_amount / var['mm_asset_outstanding']` in the divest branch would itself divide by zero for anyone trying to claim shares that were never minted).

This is a direct analog of the Insurance Fund bug: both rely on a "supply == 0 → first-deposit shortcut" heuristic that is derived from raw balances rather than the actual share-supply state variable, letting an attacker desynchronize balance from supply via an un-accounted direct transfer before the real first depositor arrives.

### Impact Explanation
The legitimate first investor's real bytes/asset contribution is irrecoverably absorbed by the AA with zero shares minted in return — a permanent fund loss for any user who invests early in an AA built on this pattern, and it only takes a trivial-value attacker donation (bytes above dust threshold, e.g. tens of thousands of bytes, and 1 unit of the underlying asset) to trigger it. Because `test/samples/uniswap_like_market_maker.oscript` is a bundled reference template that Obyte AA authors commonly copy as a starting point for AMM-style AAs, any deployed AA that reuses this exact "initial deposit" balance-based heuristic inherits the flaw.

### Likelihood Explanation
Likelihood is high for any real deployment that adopts this template unmodified: it requires only an unprivileged unit poster with access to the AA address (public knowledge as soon as the AA is deployed and its share asset is defined) and a tiny amount of base bytes/asset — no special privileges, timing races against consensus, or large capital are needed. The attacker only needs to act before the very first legitimate investment is confirmed.

### Recommendation
Replace the balance-based "initial deposit" heuristic with a check on the actual outstanding-shares state variable, e.g. `if (!var['mm_asset_outstanding']) { $issue_amount = balance[base]; return; }`, so that donation of raw balances cannot desynchronize the "is this the first deposit" decision from the true share-supply state. More generally, any AA that mints shares proportional to `balance[asset]` ratios should key its "first deposit" branch off the internal share-supply counter it controls, not off raw `balance[...]` values that any unprivileged trigger sender can inflate via un-accounted transfers.

### Proof of Concept
1. Deploy the AA from `test/samples/uniswap_like_market_maker.oscript`; call it with `trigger.data.define` to set `$mm_asset` (uses `var['mm_asset']`), leaving `var['mm_asset_outstanding']` unset.
2. Attacker sends one unit to the AA address with a `payment` message carrying `1` unit of `$asset` and a `payment` message carrying `1000` bytes (below the `1e5` threshold used by the "invest"/"exchange bytes to asset" cases), and no `trigger.data`. None of the `cases` match (verify against `if` conditions in [4](#0-3) ); the unit is accepted with no state change, silently increasing `balance[$asset]` and `balance[base]`.
3. Victim sends a legitimate "invest" unit with `trigger.output[[asset=base]] = 200000` and `trigger.output[[asset=$asset]]` matching whatever ratio is now implied by the poisoned balances.
4. Observe: `$asset_balance` and `$bytes_balance` are both nonzero, so the code skips the initial-deposit branch (line 38 of the sample) and computes `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` = `round(x * 0)` = `0`.
5. Verify the state update at the end of the "invest" case sets `var['mm_asset_outstanding'] += 0`, leaving outstanding shares at `0` while the victim's bytes/asset remain locked in the AA's balance with no `$mm_asset` tokens issued to reclaim them.
