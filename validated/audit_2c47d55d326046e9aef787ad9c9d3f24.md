Confirmed: the unique index on `commits` is `(sha, stack_id)` — unique per stack, but **not unique on `sha` alone**, so multiple `Commit` rows belonging to different `Stack`/`Repository` records can legitimately share the same `sha` (e.g., forks sharing history). `StatusHandler#process` exploits exactly this by matching on `sha` with zero repository/stack scoping.

### Title
Global unscoped `Commit.where(sha:)` lookup lets any onboarded repo's `status` webhook mutate another repository's Commit/CommitChecks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` never calls `Handler#stacks` (which scopes by `repository_name`); it instead runs `Commit.where(sha: params.sha)` across the entire `commits` table and calls `create_status_from_github!` on every match, regardless of which repository the commit belongs to. Because the unique index on `commits` is `(sha, stack_id)` and not `sha` alone, two different `Stack`s (e.g., forks sharing history) can hold rows with identical `sha`, and a signed `status` event scoped to repo B will still mutate repo A's Commit row.

### Finding Description
Broken binding (explicit equality that the code should enforce but does not):
`Commit#stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row touched by `StatusHandler#process`.

Code path:
- `WebhooksController#verify_signature` only validates that the payload's `repository_owner` (org) matches a known GitHub App installation; it does not bind the payload to a specific `Repository`/`Stack` at all: [1](#0-0) .
- `Handler#stacks`/`Handler#repository_name` exist and correctly scope by `payload.dig('repository','full_name')`, and `CheckSuiteHandler` uses them properly, further narrowing to `stack.commits.where(sha:)` (safe, since `commits` `belongs_to :stack`): [2](#0-1) [3](#0-2) .
- `StatusHandler#process`, however, **does not call `stacks` or `repository_name` at all**; it queries `Commit.where(sha: params.sha)` directly and calls `commit.create_status_from_github!(params)` on every returned row: [4](#0-3) .
- The `commits` table's unique index is `(sha, stack_id)`, not `sha` alone, confirming the schema intentionally allows the same `sha` to exist under multiple stacks: [5](#0-4) .
- `create_status_from_github!` mutates real state: it appends a `Status`, recomputes `status`, and can emit `commit_status`/`deployable_status` hooks and trigger `stack.schedule_merges`, i.e., it can influence deployability/merge logic for the *victim* stack: [6](#0-5) [7](#0-6) .

Exploit flow: attacker controls (or pushes to) a repository that is legitimately onboarded to Shipit under an org with a valid GitHub App/webhook installation (so `verify_signature` passes for that org). They cause a `status` event to be emitted with `sha` equal to a commit shared with a different (victim) repository's stack — trivially true for forked repositories sharing common ancestor commits, which is exactly the scenario `Commit#identify_merge_request`/fork-based Stacks are designed around. Because `StatusHandler` never checks `repository_name`, the victim stack's `Commit` row for that shared `sha` gets its status/CommitChecks updated by data supplied in the attacker-controlled repo's webhook.

Existing guards do not stop this: `verify_signature` authenticates the *organization*, not the specific repository-to-commit binding; `ExplicitParameters` only validates payload shape, not scope; `drop_unhandled_event` only filters event type. None of these constrain `Commit.where(sha:)` to the authenticated repository.

By contrast, `CheckSuiteHandler` correctly scopes through `stacks` (by `repository_name`) and then `stack.commits` (by `stack_id`), so it is not vulnerable to this cross-repo issue — the broken binding is specific to `StatusHandler`.

### Impact Explanation
An attacker who controls (or has push/CI-trigger access to) one Shipit-onboarded repository can write to `Commit`/`CommitChecks`-related state (statuses, computed `state`) belonging to an unrelated `Stack`/repository whenever a `sha` collision exists (guaranteed for forks sharing history, and possible for any repos sharing common commits). This is a cross-repository record mutation not authenticated by the entity actually named in the webhook payload's `repository.full_name`, matching the "Critical: a payload for one repository mutating another's stack, commit... " category. It is repeatable against any repository pair sharing commit shas and could be used to falsely mark a victim commit as passing/failing CI, potentially influencing `schedule_continuous_delivery`/`schedule_merges` for the victim stack.

### Likelihood Explanation
Preconditions: attacker needs at least one repository already onboarded to Shipit (webhook/App installed) so `verify_signature` passes — this is a real but not exotic precondition, satisfied by any contributor/org member able to trigger a `status` webhook (via GitHub Actions, third-party CI, or the GitHub Commit Status API) on a repo covered by the installation, and a commit `sha` shared with the target stack (trivial for forks/branches sharing history). No secrets are needed; only ordinary GitHub repository interaction. This is straightforward and repeatable once the precondition is met.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring `PushHandler`/`CheckSuiteHandler`: replace `Commit.where(sha: params.sha)` with `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), ensuring only commits belonging to stacks under `repository_name` are updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "does not update commit status for a different repository's commit sharing the same sha" do
  stack_a = shipit_stacks(:shipit)              # repo A
  stack_b = shipit_stacks(:cyclimse)            # repo B, different repository
  shared_sha = "a" * 40

  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared ancestor")
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = payload_parsed(:status)
  payload["repository"]["full_name"] = stack_b.github_repo_name
  payload["sha"] = shared_sha
  payload["state"] = "success"

  assert_no_changes -> { commit_a.reload.status.state } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end

  assert_equal "success", commit_b.reload.status.state
end
```
Before the fix this test fails: `commit_a.status.state` changes even though the webhook's `repository.full_name` names stack B, proving `StatusHandler` mutates a `Commit` row outside the authenticated repository (`stack_a.repository.full_name != payload['repository']['full_name']`).
