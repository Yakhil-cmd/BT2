### Title
`migrate_from_blend` trusts a caller-supplied Blend pool address and pre-authorizes controller token transfers to it, letting a forged pool contract drain controller-held tokens — (File: contracts/controller/src/external/blend.rs)

### Summary
The external report is a failure to authenticate the remote endpoint: the code disables TLS peer verification, so any attacker on the path can impersonate the trusted API and read or tamper with the exchange. The on-chain analog is `migrate_from_blend`: the controller performs a privileged cross-contract call to a `blend_pool` address and, critically, pre-authorizes `token.transfer` calls that move **the controller's own funds** to that address — without authenticating that the address is a genuine Blend pool. An unprivileged attacker supplies a malicious contract posing as a Blend pool and receives real token transfers from the controller.

### Finding Description
`blend_repay_all` builds `REQ_REPAY` requests for each `(asset, max)` pair in caller-influenced `debt_caps`, then calls `authorize_repay_pulls`, which pushes `InvokerContractAuthEntry` entries authorizing `transfer(controller -> blend_pool, max)` on each debt token, and finally `guarded_submit` invokes `BlendPoolClient::new(env, blend_pool).submit(...)` on the attacker-chosen address [1](#0-0) . Neither function pins `blend_pool` to a stored registry, allowlist, or previously recorded address — the "peer" of this privileged channel is whatever address the caller supplied. The same unauthenticated-channel pattern appears in `blend_sweep_all`, which submits withdraw requests to the supplied pool [2](#0-1) . The `submit` result (`BlendPositions`) is explicitly discarded (`let _ =`), so no post-call identity or sanity check exists either [3](#0-2) . This mirrors `CURLOPT_SSL_VERIFYPEER = false`: the endpoint's identity is never verified before secrets-value-bearing traffic (signed token transfers) is sent to it.

### Impact Explanation
Theft of controller-held funds. The controller holds real token balances (unclaimed revenue, refund buffers, flash-position collateral pending deposit). `authorize_repay_pulls` grants the fake pool signed authorization to pull up to `max` of each listed asset [4](#0-3) . A malicious `blend_pool` contract simply invokes the authorized `transfer`s during `submit` and returns any `BlendPositions` (ignored by the caller). The attacker walks away with tokens up to the caps they declared — which the fake pool can make arbitrarily large since it also fabricates the position data driving those caps.

### Likelihood Explanation
Reachable by any unprivileged address: `migrate_from_blend` is permissionless (any Blend user may migrate), and the attacker fully controls both the `blend_pool` contract and the position state it reports, so the debt caps and the forged `submit` response are under attacker control. No timing, oracle, or liquidity preconditions apply beyond holding tokens in the controller. One caveat I could not fully verify within the available index context: whether `debt_caps` are bounded by an independently trusted source (e.g., a Blend registry lookup) inside `contracts/controller/src/strategies/migrate_blend.rs` before `blend_repay_all` runs. If the caps are derived only from the fake pool's response or caller arguments, the drain is bounded only by the controller's token balances.

### Recommendation
Authenticate the counterparty before authorizing transfers: pin `blend_pool` against a stored Blend pool registry/settlement record (e.g., a Blend-pool allowlist written at market config time, or the pool address recorded during position onboarding), and reject caller-supplied addresses that do not match. Additionally, derive `debt_caps` from trusted state (recorded Blend liabilities at snapshot time) rather than data returned by the untrusted contract, and validate the returned `BlendPositions` instead of discarding it.

### Proof of Concept
1. Attacker deploys `FakeBlend` exposing the `submit(from, spender, to, requests)` ABI. On invocation it calls `token.transfer(controller -> FakeBlend, cap)` for every `(asset, cap)` the attacker listed — these calls succeed because `authorize_repay_pulls` already pushed the signed auth entries [5](#0-4) . `FakeBlend` then returns a `BlendPositions` with fabricated collateral/supply and empty liabilities (discarded anyway).
2. Attacker calls controller `migrate_from_blend` with `blend_pool = FakeBlend` and debt caps equal to the controller's full balances of the listed debt assets.
3. `guarded_submit` invokes `FakeBlend.submit` under the flash guard; the forged pulls execute; the attacker's contract now holds the controller's tokens. Any subsequent failure cannot claw back the transfers.

pub(crate) fn blend_repay_all(
    env: &Env,
    blend_pool: &Address,
    from: &Address,
    debt_caps: &Vec<(Address, i128)>,
) {
    let mut requests: Vec<BlendRequest> = Vec::new(env);
    for (asset, max) in debt_caps.iter() {
        requests.push_back(BlendRequest {
            request_type: REQ_REPAY,
            address: asset,
            amount: max,
        });
    }
    authorize_repay_pulls(env, blend_pool, debt_caps);
    guarded_submit(env, blend_pool, from, &requests);
}

/// Submits with the controller as spender and recipient while holding the
/// flash-loan guard against reentry into guarded controller operations.
fn guarded_submit(env: &Env, blend_pool: &Address, from: &Address, requests: &Vec<BlendRequest>) {
    storage::with_flash_guard(env, || {
        let controller = env.current_contract_address();
        let _ =
            BlendPoolClient::new(env, blend_pool).submit(from, &controller, &controller, requests);
    });
}

fn authorize_repay_pulls(env: &Env, blend_pool: &Address, debt_caps: &Vec<(Address, i128)>) {
    if debt_caps.is_empty() {
        return;
    }
    let controller = env.current_contract_address();
    let mut entries: Vec<InvokerContractAuthEntry> = Vec::new(env);
    for (debt_asset, max) in debt_caps.iter() {
        entries.push_back(InvokerContractAuthEntry::Contract(SubContractInvocation {
            context: ContractContext {
                contract: debt_asset,
                fn_name: symbol_short!("transfer"),
                args: (controller.clone(), blend_pool.clone(), max).into_val(env),
            },
            sub_invocations: Vec::new(env),
        }));
    }
    env.authorize_as_current_contract(entries);
}
