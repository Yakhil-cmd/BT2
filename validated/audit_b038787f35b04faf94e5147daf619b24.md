### Title
Cross-organization webhook forgery via decoupled `repository.owner.login` (signature routing) and `repository.full_name` (target resolution) enables unauthorized review-stack provisioning — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the signature against using `params.dig('repository','owner','login')`, while every `pull_request` handler (e.g. `LabeledHandler`, `LabelCapturingHandler`, `OpenedHandler`) resolves the target `Repository`/`review_stacks` using the independent field `params.repository.full_name`. Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker who owns a legitimate Shipit-connected repo/org can sign a payload with their own valid webhook secret while pointing `repository.full_name` at a victim's repo, causing the victim's review stack to be provisioned/deployed with an attacker-chosen `pull_request.head.sha`.

### Finding Description
The broken binding: `verify_signature`'s `repository_owner` (`params.dig('repository','owner','login')`, used to pick `Shipit.github(organization: repository_owner)` and thus the webhook secret checked) MUST equal the owner encoded in `params.repository.full_name` (used by `Repository.from_github_repo_name` in every `pull_request` handler) — but nothing enforces this.

Code path:
- `WebhooksController#verify_signature` picks the app config purely from `repository.owner.login`: [1](#0-0)  and [2](#0-1) .
- `Shipit.github(organization:)` resolves a per-organization `GitHubApp` (and its distinct `webhook_secret`) from `secrets.github[organization]` in a multi-org deployment: [3](#0-2) .
- Every `pull_request` handler independently re-resolves the target `Repository` from `params.repository.full_name`, ignoring `repository.owner.login` entirely: `LabeledHandler#repository` [4](#0-3) , `LabelCapturingHandler#repository` [5](#0-4) , `OpenedHandler#repository`/`process` [6](#0-5) .
- The resolved `repository.review_stacks` scope is then mutated by `ReviewStackAdapter` (create/archive/unarchive) using attacker-supplied `pull_request` data (including `head.sha`): [7](#0-6) .

Attacker's exact request: POST `/webhooks` with `X-Github-Event: pull_request`, `X-Hub-Signature` computed with the attacker's own org's legitimate `webhook_secret` over a raw body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/repo"`, `action: "labeled"`, and `pull_request.labels` containing victim-org's configured `provisioning_label_name`.

Exploit flow: `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the signature against the attacker's own secret — which succeeds because the attacker legitimately controls that secret via their own onboarded repo/installation. The request passes signature verification. The `LabeledHandler` (and `LabelCapturingHandler` before it, per `Shipit::Webhooks.for_event`) then resolves `repository` via `Repository.from_github_repo_name("victim-org/repo")`, finds the real victim `Repository`, and calls `ReviewStackAdapter#find_or_create!`/`archive!`/`unarchive!` scoped to `victim.review_stacks`, using the attacker-supplied `pull_request.head.sha`.

Why existing guards fail: `drop_unhandled_event` and `check_if_ping` only gate on event type, not payload consistency. `verify_signature` never checks that the org used for signature verification matches the org embedded in `repository.full_name`. `ExplicitParameters` schemas in the handlers only validate types/presence (`requires :full_name, String`), not cross-field consistency with the value used upstream for authentication. `Repository.from_github_repo_name` performs a plain lookup with no ownership/org check tied back to the verified signer.

### Impact Explanation
An attacker with a legitimate but unprivileged GitHub org (e.g., their own fork/org connected to Shipit) can forge webhooks that mutate a completely different, unrelated repository's review stacks — creating (`find_or_create!`) or archiving/unarchiving stacks under `victim.review_stacks` and driving deploys using an attacker-chosen head SHA. This is a payload-for-one-repository mutating another repository's stack/task, meeting the Critical bar (unauthorized deploy triggered on a repository the request never authenticated against). The attack is repeatable against any repository configured in the same multi-org Shipit deployment, and blast radius spans every tenant/org sharing that Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, so `github_default_organization` is non-nil and `Shipit.github(organization: ...)` resolves per-org secrets — single-org deployments are not exploitable this way since only one secret exists regardless of payload content). The attacker needs a Shipit-onboarded repo/org of their own (to legitimately know/compute a valid webhook signature) and knowledge/guess of the victim's `provisioning_label_name` (often a documented convention like `"shipit"`), plus the victim repo having `review_stacks_enabled` and `provisioning_behavior_allow_with_label?`. Attacker cost is low: craft one JSON body and one HMAC signature with their own secret; fully repeatable per request.

### Recommendation
In `WebhooksController#verify_signature`, or in each `pull_request` handler, enforce that the organization whose secret verified the signature matches the organization embedded in `params.repository.full_name` (and/or `params.repository.owner.login`) before resolving/mutating any `Repository`/`review_stacks`; reject the webhook (422) on mismatch.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or a new `pull_request` handler test):
```ruby
test "cross-org repository.full_name is rejected even with a validly-signed attacker payload" do
  attacker_org = "attacker-org"
  victim_repo = shipit_repositories(:shipit) # e.g. owned by "shopify"
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: "allow_with_label", provisioning_label_name: "shipit")

  payload = pull_request_labeled_payload(
    repository_owner_login: attacker_org,          # what verify_signature uses
    repository_full_name: victim_repo.github_repo_name, # what the handler uses
    labels: ["shipit"],
    head_sha: "attacker-chosen-sha"
  ).to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, payload)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  assert_no_difference -> { victim_repo.review_stacks.count } do
    post :create, body: payload, as: :json
  end
  # Binding under test:
  # left  = organization used by verify_signature (params.repository.owner.login == "attacker-org")
  # right = organization owning the mutated repository (params.repository.full_name.split('/').first == victim_repo.owner)
  # Currently left != right yet the request is processed => vulnerability.
end
```
This test currently fails (a `ReviewStack`/`Stack` is created under the victim repository) because no code path checks `repository_owner == repository.full_name`'s owner segment.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
