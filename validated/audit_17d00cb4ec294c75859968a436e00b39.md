### Title
Cross-organization Team hijack in membership webhook removes a legitimate operator's team membership - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, an attacker-supplied integer, with no check that it belongs to `params.organization.login`. An attacker who owns any org onboarded to Shipit (and can therefore produce a validly-signed webhook for that org) can send a `membership`/`removed` event whose `team.id` matches the `github_id` of an unrelated, already-existing `Team` (e.g. one listed in `Shipit.github_teams`), causing that real team's membership with a named victim login to be deleted.

### Finding Description
The binding the code should preserve is: `Team.find(returned_team).organization == params.organization.login`. In practice `find_or_create_team!` does: [1](#0-0) 

`Team.find_or_create_by!(github_id: params.team.id)` matches purely on `github_id`; the `team.organization = params.organization.login` assignment only executes inside the `do |team| ... end` block, which ActiveRecord only runs when a **new** record is being created. If a `Team` row with that `github_id` already exists (created earlier from a genuine webhook belonging to a different, victim organization), the existing record is returned unchanged, and its `organization` attribute is never revalidated against the current payload's `params.organization.login`. So the equality is broken: the returned `Team` can belong to an organization different from the one whose signature was verified.

`verify_signature` in the controller only confirms the payload was signed with the secret of `params.organization.login` (attacker's own org, which the attacker legitimately controls): [2](#0-1) 
It never checks that `params.team.id` actually belongs to that organization on GitHub.

Exploit flow:
1. Attacker owns/administers `evil-org`, which is onboarded to Shipit (so `Shipit.github(organization: 'evil-org')` has a valid webhook secret the attacker also possesses because they configured the app on their own org).
2. Attacker crafts a `membership` event payload: `action: 'removed'`, `team: { id: <victim_team_github_id>, name/slug/url: arbitrary }`, `organization: { login: 'evil-org' }`, `member: { login: '<victim-operator-login>' }`, and signs it with `evil-org`'s real webhook secret, then POSTs to `/webhooks`.
3. `verify_signature` passes because the signature matches `evil-org`'s secret and `repository_owner` resolves to `evil-org`.
4. `MembershipHandler#process` calls `find_or_create_team!`, which finds the *existing* `Team` row whose `github_id == victim_team_github_id` (created earlier from the victim org's real events) — a team is returned that has nothing to do with `evil-org`.
5. `User.find_or_create_by_login!(params.member.login)` resolves/creates the victim operator's `User` record.
6. `team.members.delete(member)` deletes the `Membership` linking the operator to the real target `Team`, which may be one of `Shipit.github_teams`, silently revoking `authorized?` for that operator (`Shipit::User#authorized?` re-evaluates team membership).

No existing guard catches this: `ExplicitParameters` only checks types/presence of `team.id`/`organization.login`, not their correlation; `drop_unhandled_event` and `verify_signature` only gate on event type and signature validity for the *attacker's own* org; there is no model validation tying `Team#organization` to `Team#github_id` on lookup.

Note: the question's proposed mechanism ("two `Team` rows sharing the same local `id` due to a prior lookup bug") is not accurate — the primary key `id` is a unique DB column and cannot collide between rows. The actual flaw is in the `github_id`-only lookup (an IDOR-style cross-tenant object reference), which produces the same practical outcome the question describes (attacker names an arbitrary member login and deletes membership in an unrelated `Team`).

### Impact Explanation
An attacker who has onboarded any organization to Shipit can deauthorize an arbitrary Shipit operator from any `Team` whose GitHub `github_id` they know or can guess, by targeting `Shipit.github_teams` entries. Because `User#authorized?` is computed from live `teams` membership, this can strip a legitimate operator's authorization for the whole app (blocking their ability to deploy/approve), which is an "authorization state corruption" reachable purely via a self-owned, validly-signed webhook — no victim-org secret required. This is repeatable against any operator/team combination whose numeric `github_id` the attacker can obtain, across any number of tenants using the same Shipit instance (multi-org deployments share the `teams`/`users` tables).

### Likelihood Explanation
Preconditions: attacker must own/administer an org already configured with a Shipit-recognized GitHub App/webhook secret (a bar equivalent to "any org can install the Shipit GitHub App," which is typically self-service and low-cost); attacker must know the target `Team`'s GitHub-assigned `github_id` (a small sequential integer, not a secret, though not always trivially discoverable for private teams) and the victim operator's GitHub login (public information). No Shipit session, API token, or victim-org secret is needed. This is straightforward to script and repeat.

### Recommendation
In `find_or_create_team!`, verify (and re-validate on every event, not only creation) that the found `Team#organization` equals `params.organization.login`; if it doesn't match, reject the event (e.g., raise/log and no-op) instead of silently reusing the mismatched row. Additionally, scope the `find_or_create_by!` lookup on both `github_id` and `organization`, and add a uniqueness/consistency validation on `Team` for `(github_id, organization)`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "removed event from an unrelated org deletes membership on an existing team with matching github_id" do
  operator = shipit_users(:walrus) # a real Shipit operator
  victim_team = Team.create!(github_id: 999, organization: 'victim-org', name: 'Ops', slug: 'ops', api_url: 'https://x')
  Membership.create!(team: victim_team, user: operator)
  assert victim_team.members.include?(operator)

  payload = {
    action: 'removed',
    team: { id: 999, name: 'Ops', slug: 'ops', url: 'https://x' }, # same github_id, attacker-controlled
    organization: { login: 'evil-org' },                          # attacker's own, legitimately-signed org
    member: { login: operator.login }
  }.to_json

  MembershipHandler.new(JSON.parse(payload)).call

  assert_not victim_team.members.reload.include?(operator)
end
```
This demonstrates: `Team` returned by `find_or_create_team!` for `organization: 'evil-org'` equals the pre-existing `victim-org` team (binding broken), and the operator's membership is deleted without any check binding the mutated `Team`/`Membership` pair to the organization that actually authenticated the webhook.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
