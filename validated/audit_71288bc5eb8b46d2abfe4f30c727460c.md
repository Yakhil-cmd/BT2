### Title
Unchecked division by zero in `PoolState::token_price_x32` causes swap panic / DoS — ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`PoolState::token_price_x32` computes both token prices using raw Rust division (`/`) instead of `checked_div`, and is invoked on every `swap_base_input` / `swap_base_output` call via `get_swap_params`. If either token's "real" vault balance (vault amount minus unclaimed protocol/fund/creator fees) is zero, the division panics, matching the reported bug class of unvalidated-denominator division by zero (analogous to `QuantizedBatchNormWithGlobalNormalization` not validating its operand constraints before dividing).

### Finding Description
`token_price_x32` is defined as: [1](#0-0) 

Unlike the rest of the fee/curve math in this codebase, which consistently uses `checked_div`/`checked_mul` with `Option` propagation to avoid panics (e.g. in `curve/fees.rs` and `curve/constant_product.rs`), this function performs plain `/` division with no zero-check on `token_0_amount` or `token_1_amount`. A panic inside a Solana program aborts the transaction with a runtime error rather than returning a graceful `Result::Err`.

This function is called from `get_swap_params`, which is invoked directly in both swap entry points reachable by any unprivileged swapper: [2](#0-1) [3](#0-2) [4](#0-3) 

The `token_0_amount`/`token_1_amount` passed in come from `vault_amount_without_fee`, which subtracts accumulated (but unclaimed) protocol/fund/creator fees from the actual token vault balance: [5](#0-4) 

Because fees continually accrue as bookkeeping entries against the vault balance while the "tradable" liquidity on one side can be driven down by repeated swaps/withdrawals, it is possible for the real trading balance on one side of the pool (`token_0_amount` or `token_1_amount`) to reach exactly zero (or become zero as unclaimed fees approach the full vault balance) without tripping the `InsufficientVault` underflow check, since that check only guards against the balance going *negative*, not equal to zero. Once one side's amount is zero, any subsequent call into `get_swap_params` (i.e., any swap by any user) unconditionally divides by that zero value and panics.

### Impact Explanation
A panic in a Solana on-chain program instruction causes the transaction to fail, but more importantly this represents an on-chain divide-by-zero introduced by state that a normal, unprivileged sequence of swaps/withdrawals can create. Once the pool reaches this state, every future `swap_base_input`/`swap_base_output` call against that pool will unconditionally panic in `get_swap_params` before any of the safety guards (`require_gte!(constant_after, constant_before)`, slippage checks, etc.) are reached, permanently freezing the swap functionality for that pool (deposit/withdraw paths that don't call `token_price_x32` may still work, but the pool becomes unusable for trading). This matches "permanent freezing of user or LP funds" via the swap path.

### Likelihood Explanation
This requires reaching a pool state where one side's fee-adjusted vault balance is exactly zero, which is an edge condition depending on fee configuration and sequence of trades/withdrawals; it is not trivially triggerable in a single transaction under normal fee-rate configurations (fees are typically far smaller than the full vault balance). However, it is reachable through a legitimate, unprivileged sequence of trades/withdrawals without any privileged action, and the codebase's own convention elsewhere (checked arithmetic everywhere else in the fee/curve modules) shows this raw-division pattern is inconsistent and unguarded, which is the exact root-cause class flagged in the reference CVE (missing input-constraint validation before division).

### Recommendation
Replace the raw `/` operators in `token_price_x32` with `checked_div`, returning `ErrorCode::MathOverflow` (or a dedicated error) when either denominator is zero, consistent with the rest of the codebase's checked-arithmetic conventions in `curve/fees.rs` and `curve/constant_product.rs`.

### Proof of Concept
Conceptual trigger path (cannot be executed without a live cluster/test harness):
1. Create a pool and let it accrue trade/protocol/fund/creator fees on one side (`fees_token_0` or `fees_token_1`) over many swaps.
2. Drive down the real (fee-excluded) balance of that same side via `swap_base_input`/`swap_base_output`/`withdraw` until `vault_amount_without_fee` returns `0` for that side (this does not trip `InsufficientVault` since the check only rejects negative results, not zero).
3. Call `swap_base_input` or `swap_base_output` again; `get_swap_params` → `token_price_x32` executes `token_0_amount as u128 * Q32 as u128 / token_1_amount as u128` (or vice versa) with a zero denominator, causing the instruction to panic and abort, and permanently freezing further swaps on the pool.     pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
            token_0_amount as u128 * Q32 as u128 / token_1_amount as u128,
        ))
