### Title
Webhook signature verification is scoped to the wrong GitHub organization, allowing cross-repository commit-status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using `repository_owner`, a value read directly out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`). The handlers that actually act on the event (e.g. `StatusHandler`) do not consult that same field — `StatusHandler` matches purely by commit SHA across the entire database, and `PushHandler`/`Handler#stacks` resolve the target repository from a separate payload field, `payload.dig('repository', 'full_name')`. Because the field used to pick the *verifying* secret and the field(s) used to pick the *acted-upon* repository/commit are independent, uncorrelated values inside the same attacker-controlled JSON body, an operator of one legitimately-configured GitHub organization in a multi-org Shipit deployment can forge a correctly-signed webhook that manipulates state belonging to a completely different organization/repository.

### Finding Description
`Shipit.github(organization:)` supports hosting multiple independent GitHub Apps/organizations in a single Shipit instance (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications"), each with its own `webhook_secret`. [1](#0-0) 

The signature check picks the app/secret to verify against using a field taken straight from the unauthenticated request body: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` HMACs the request body with the org's `webhook_secret` and compares it to the provided signature: [4](#0-3) 

Once verification passes, the event is dispatched to a handler that resolves *what to act on* using a **different** field of the same payload. The generic base class resolves the stack from `repository.full_name`: [5](#0-4) 

`StatusHandler`, used for the `status` webhook event, goes even further and does not scope by repository/stack at all — it matches any `Commit` record in the entire database by SHA: [6](#0-5) 

`PushHandler` similarly resolves target stacks from `repository.full_name` (via `Handler#stacks`), a field wholly independent from `repository.owner.login` used for signature selection: [7](#0-6) 

The binding that should hold is: **organization that authenticated the webhook == organization whose repositories/commits are mutated by the webhook**. Because `repository.owner.login` (used for signature selection) and `repository.full_name` / bare commit SHA (used to select the mutated record) are both attacker-supplied and never cross-checked against each other, this binding is broken. An attacker who administers "OrgA" in a multi-org Shipit deployment (and therefore legitimately knows `OrgA`'s `webhook_secret`) can sign a payload with `OrgA`'s secret while setting `repository.full_name` (or, for `status` events, just the SHA) to point at "OrgB"'s repository/commit.

### Impact Explanation
This crosses an organization/repository trust boundary that the signature check is meant to enforce, i.e. exactly the type of binding break in the reference report (a check performed on one entity while the action is carried out on a different, uncovered entity). The most direct exploit path is via `status` events: `StatusHandler` writes a commit status for *any* `Commit` row matching the given SHA, with zero scoping to the verifying organization or its repositories. Since git commit SHAs are content-addressed, an attacker can trivially produce a commit with an identical SHA to a target commit in a victim repo they don't control (e.g. by cloning/forking the victim's public repository into their own attacker-owned org configured in the same Shipit instance), then forge a `status` webhook — validly signed with their own org's `webhook_secret` — that marks the victim commit as passing a required CI context. Required CI statuses (`ci.require` in `shipit.yml`) gate deploy readiness, so this can be used to force a commit that never actually passed CI to appear deployable/mergeable, i.e. contributes to an unauthorized deploy/merge condition. `push`-type events additionally let an attacker who authenticated as `OrgA` trigger `sync_github` processing against a stack that belongs to `OrgB`'s repository, since `Handler#stacks`/`PushHandler` resolve the target purely from `repository.full_name`.

### Likelihood Explanation
Exploitation requires the Shipit deployment to be configured with the multi-organization GitHub App layout (explicitly documented and supported), and requires the attacker to legitimately control at least one of the configured GitHub organizations/apps (a normal, unprivileged "tenant" of the shared Shipit instance, not a privileged Shipit user or someone with any Shipit credentials). No `ApiClient` token, Shipit session, or GitHub write access to the victim's repository is required — only the attacker's own org's webhook secret, which they own by construction, and a target commit SHA (obtainable by forking/cloning a public victim repo).

### Recommendation
Verify the webhook signature and select the org/app to verify against using the same trusted, correlated identifier used to pick the acted-upon repository/commit, and re-validate consistency between them. Concretely:
- In `WebhooksController`, after signature verification succeeds for organization `X`, ensure any repository referenced in the payload (`repository.full_name`, `repository.owner.login`, or any SHA-only lookup) actually belongs to organization `X` before dispatching to handlers.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits/stacks whose `Repository#owner` matches the verified organization, instead of matching bare SHA globally.
- In `Handler#stacks`/`PushHandler`, cross-check that `repository.owner.login` (verified org) matches the owner portion of `repository.full_name` before resolving stacks.

### Proof of Concept
Given a Shipit instance configured per `docs/setup.md`'s "Using Multiple Github Applications" section with `OrgA` (attacker-controlled) and `OrgB` (victim) both onboarded:

1. Attacker forks/clones `OrgB/victim-repo`'s public commit `SHA1` into their own `OrgA/attacker-repo` (identical content ⇒ identical SHA).
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s known `webhook_secret` over the JSON body:
```json
{
  "sha": "SHA1",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and the computed signature.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and succeeds because the signature matches `OrgA`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "SHA1")` and finds/updates the victim's `Commit` (belonging to `OrgB/victim-repo`) with a forged "success" status for `ci/required-check`, despite the attacker never having any credential or write access to `OrgB`.

Note: I was not able to inspect `Commit#create_status_from_github!` or the exact deploy-gating logic (`ci.require`) end-to-end within the tool budget, so the precise mechanics of how a forged status feeds into deploy/merge gating could not be fully traced in this session — this is stated as an area of uncertainty; a Devin session with full repo access should verify `app/models/shipit/commit.rb` (`create_status_from_github!`) and the deploy-readiness checks to confirm the exact downstream effect.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
