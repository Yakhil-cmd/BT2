### Title
Cross-tenant Status write via unscoped `sha` lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without checking that the commit's owning repository matches the webhook's verified `repository.owner.login`. An attacker who controls a GitHub org onboarded to Shipit (and thus possesses a valid, org-scoped webhook secret for their own repo) can send a `status` event referencing a `sha` that also exists as a commit row belonging to a different tenant's stack, causing a forged `Status` record to be written against that unrelated stack's commit.

### Finding Description
The required binding is: `commit.stack.repository.owner == payload.repository.owner.login` for every `Commit` mutated by a webhook (i.e., a payload verified for org A must only mutate rows belonging to org A). `StatusHandler#process` breaks this: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  with no repository/stack filter at all. Compare to the base `Handler` class, which exposes a `stacks` helper explicitly scoped by `Repository.from_github_repo_name(repository_name)` [2](#0-1)  — other handlers (e.g. push) use this scoping, but `StatusHandler` ignores it entirely.

`WebhooksController#verify_signature` only verifies that the payload was signed with the secret belonging to `repository_owner` (`params.dig('repository','owner','login')`) [3](#0-2) [4](#0-3) . This proves the payload is authentic for org A, but nothing downstream re-checks that the `sha` in the payload actually belongs to a commit under org A's repository — `StatusHandler` looks up `sha` engine-wide. A commit `sha` is a 40-hex-char SHA-1 of that commit's content, which is fully determined by tree/parent/author/committer/message data. Two different repositories will only share a `sha` if they share literal commit history (e.g., a shared upstream, a fork, cherry-picked/rebased commit, or copy-pasted commit content) — this is not something the attacker can freely choose per victim; it does require the sha to coincide with an existing victim commit.

Given such a coincidence (or attacker knowledge of a specific victim commit sha, e.g. from a public fork/rebase relationship), attacker-org sends `POST /webhooks` with header `X-Github-Event: status`, signed with attacker-org's own valid webhook secret, body `{"sha": "<shared-sha>", "state": "failure", "description": "...", "target_url": "...", "context": "attacker-controlled", "repository": {"owner": {"login": "attacker-org"}}}`. `verify_signature` passes because it only checks attacker-org's own secret. `StatusHandler.call` → `process` finds all `Commit` rows with that sha across every tenant and calls `create_status_from_github!` on each, writing an attacker-controlled `Status` (state/description/target_url/context) onto the victim's commit, potentially affecting `commit.state`, CI-gating logic, and triggering `ProcessMergeRequestsJob` for the victim's stack.

### Impact Explanation
Attacker-org can write a `Status` record with arbitrary `state`/`description`/`target_url`/`context` onto a commit belonging to an unrelated tenant's stack whenever a sha collision (deliberate history-sharing, fork, or knowledge of a victim's commit sha via shared upstream) exists. This can flip `commit.state` (e.g., forge a `success` status to make a bad commit appear deployable, or forge `failure` to block/disrupt a victim's deploy), and can trigger the victim's `ProcessMergeRequestsJob`. This is a payload from one repository mutating another's stack/commit, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: attacker must have their own repository onboarded with a valid Shipit webhook (any GitHub org can add a webhook to their own repo pointing at the shared Shipit host, which is standard multi-tenant use), and must know/control a `sha` value that also exists as a `Commit` row in a victim's stack. This is not trivially achievable against an arbitrary victim of the attacker's choosing (they cannot forge a sha for content they don't control the way they want), but is realistic in shared-fork / shared-upstream / vendored-dependency scenarios, or when an attacker can observe a victim's commit sha from public GitHub activity (PRs, pushes) and reproduce identical commit content in their own repo/fork to obtain the same sha, or simply cross-post the same commit into both repos. No Shipit session, API token, or secret compromise is required beyond the attacker's own legitimate webhook secret.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `stacks` resolves via `Repository.from_github_repo_name(repository_name)` as already implemented in `Handler`.

### Proof of Concept
Minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):
1. Create two `Stack`s in different repositories/orgs, `stack_a` (repo `org-a/repo`) and `stack_b` (repo `org-b/repo`).
2. Create a `Commit` under `stack_a` and a `Commit` under `stack_b` with the identical `sha` value (e.g., `"deadbeef" * 5`).
3. Build a `status` webhook payload with `sha` = shared sha, `repository.owner.login` = `"org-a"`, `repository.full_name` = `"org-a/repo"`.
4. Stub/verify signature for `org-a`'s secret (valid).
5. POST to `/webhooks` (or call `StatusHandler.call(payload)` directly).
6. Assert `commit_b.statuses.count` changed (binding broken): `assert_difference('stack_b_commit.reload.statuses.count', 1) { StatusHandler.call(payload) }`.
7. After fix, assert `stack_b_commit.reload.statuses.count` is unchanged while `stack_a_commit.reload.statuses.count` increments — i.e. `commit.stack.repository.full_name == payload['repository']['full_name']` holds for every mutated row.
