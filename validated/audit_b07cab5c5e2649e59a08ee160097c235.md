### Title
Webhook signature verification selects the GitHub App / secret using the unverified `repository.owner.login` field, decoupling the authenticated organization from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate the `X-Hub-Signature` against by reading `repository_owner` straight out of the still-unverified JSON body. The repository that handlers actually act on (`repository.full_name`, used by `Handler#repository_name`) is a separate, independently attacker-controlled field that is never cross-checked against the organization used for signature verification.

### Finding Description
`verify_signature` derives the signing organization from the raw payload before any authentication has occurred: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up the app config for whatever organization name is present in the body via `github_app_config`, and `GitHubApp#verify_webhook_signature` treats an **unconfigured `webhook_secret` as automatically valid**: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, the handler that actually performs the write/side effect (e.g. syncing a stack, creating commit statuses) resolves the target repository from a completely different, independently attacker-controlled field, with no tie back to `repository_owner`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

This breaks the intended trust binding: `organization whose signature is verified == organization owning the repository being written to`. In a multi-organization deployment (the documented `github: {OrgOne: {...}, OrgTwo: {...}}` layout), if **any one** configured organization has a blank `webhook_secret` (a configuration shown as a normal, supported option in the shipped example secrets files), that organization's blank secret causes `verify_webhook_signature` to unconditionally return `true`. An attacker can then set `repository.owner.login` to that blank-secret organization (satisfying `verify_signature`), while setting `repository.full_name` to the full name of a repository/stack belonging to any other organization actually tracked by Shipit. The webhook is accepted with no valid HMAC at all, yet it drives handlers (`PushHandler`, status handlers, etc.) against a repository outside the "authenticated" organization. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged, unauthenticated attacker (no Shipit session, no `ApiClient` token, no `webhook_secret` knowledge for the target org) can forge GitHub webhook events (`push`, `status`, `deployment_status`, `pull_request`, etc.) for any repository tracked by Shipit as long as the operator's multi-organization config contains one organization with an unset `webhook_secret`. Forged `push` events trigger `GithubSyncJob` against arbitrary stacks (`PushHandler#process`) [7](#0-6) , and forged `status`/`commit_status` events fabricate CI results tied to arbitrary commits, which can influence deploy/merge readiness decisions elsewhere in Shipit. This crosses the "cross-repository writes" / "unauthorized deploy or merge" impact bar because a spoofed event is not scoped to the organization whose credentials actually authenticated the request.

### Likelihood Explanation
Likelihood depends on an operator running Shipit in multi-organization mode with at least one organization configured with a blank `webhook_secret`. This is not a theoretical edge case: the engine's own shipped example secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show `webhook_secret:` left blank as a normal template value, and nothing in `github_app_config`/`GitHubApp#initialize` warns or refuses to boot when a secret is missing for one organization while others have one configured. Any operator who partially configures one organization (e.g., during onboarding) is exposed while other organizations remain "protected" only in appearance.

### Recommendation
- Verify the webhook signature using a secret resolved independently of any attacker-supplied body field, or cross-check that the resolved `repository_owner` used for signature verification matches the owning organization of the `repository.full_name` actually used by the event handler, rejecting mismatches.
- Do not treat a missing/blank `webhook_secret` as "signature verification passed"; instead fail closed (reject with 422) when a configured organization has no secret, or require every organization in a multi-org deployment to define a secret.
- Consider requiring `repository.owner.login` and `repository.full_name`'s owner segment to be identical before dispatching to handlers.

### Proof of Concept
1. Operator configures Shipit with two GitHub Apps: `OrgA` (properly configured with `webhook_secret: <strong-secret>`, and tracks a real stack `OrgA/critical-repo`), and `OrgB` (onboarding in progress, `webhook_secret:` left blank as shown in the shipped example configs).
2. Attacker sends `POST /webhooks` with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature: sha1=deadbeef` (or any/no value)
   - Body: `{"repository": {"owner": {"login": "OrgB"}, "full_name": "OrgA/critical-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`
3. `repository_owner` resolves to `"OrgB"`, so `Shipit.github(organization: "OrgB")` loads `OrgB`'s config, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`) — no valid HMAC ever required.
4. `WebhooksController#create` dispatches to `PushHandler`, whose `repository_name` is `payload.dig('repository', 'full_name')` = `"OrgA/critical-repo"`, so it enqueues `GithubSyncJob` against `OrgA`'s real stack, entirely bypassing `OrgA`'s configured secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
