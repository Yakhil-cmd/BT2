### Title
Market accrual overflow permanently freezes a large pool market - ([File: common/src/rates/simulate.rs])

### Summary
The permissionless `update_indexes` path forwards caller-selected markets to the pool’s accrual routine. [1](#0-0) [2](#0-1)  Each market load runs `interest::global_sync`, which calls `accrue_step` before committing the new timestamp. [3](#0-2) [4](#0-3)  `accrue_step` first unscales aggregate debt and supply with `scaled_to_original`, so an `i128` overflow aborts accrual before the new index can be committed. [5](#0-4) [6](#0-5) 

### Finding Description
`global_sync` processes all elapsed chunks and calls `mark_accrued` only after the loop completes, leaving `last_timestamp` unchanged if any chunk panics. [4](#0-3)  Inside each step, `borrowed × borrow_index` and `supplied × supply_index` are evaluated before the borrow index is updated or clamped. [5](#0-4)  Because cap validation only ensures that the configured token amount can be represented at admission time, it does not reserve headroom for later index multiplication. [7](#0-6)  Consequently, a sufficiently large market can cross the `i128` value boundary before reaching the index ceiling, after which the accrual call deterministically reverts. [8](#0-7) 

### Impact Explanation
Once the product exceeds `i128::MAX`, the overflowing `update_indexes` call reverts without advancing the market timestamp, so every subsequent accrual repeats the same failing computation. [9](#0-8)  The existing regression test demonstrates the terminal state: `update_indexes` raises `MathOverflow`, the borrow index remains below its cap, and withdrawal and repayment also fail because they accrue first. [10](#0-9)  This permanently freezes suppliers’ and borrowers’ funds in the affected market and prevents liquidation or repayment absent a code fix or migration. [11](#0-10) 

### Likelihood Explanation
An unprivileged borrower can put the market into the vulnerable state by supplying their own collateral and borrowing a large amount through the normal `supply`/`borrow` entrypoints. [12](#0-11)  After index growth makes either aggregate value unrepresentable, any unprivileged caller can trigger the freeze with `update_indexes(caller, [hub_asset])`. [13](#0-12)  The issue is conditional on a large listed book and sustained borrow interest, but it does not require malformed caps because the cap domain checks only representability of the amount being admitted. [7](#0-6) 

### Recommendation
- Use widened arithmetic, such as `I256`, for `scaled × index` aggregate-value calculations, or compute utilization without materializing the full product in `i128`.
- Alternatively, enforce aggregate supply and debt-share limits derived from `i128::MAX / MAX_INDEX`, so every admissible book remains representable at the maximum possible index.
- Add a recovery mechanism or accrual path that can safely process a market already beyond the `i128` value boundary.
- Add regression coverage asserting that `update_indexes`, `repay`, `withdraw`, and liquidation remain executable up to the configured index and cap boundaries.

### Proof of Concept
On a listed market with enough supplier liquidity and a separate collateral asset, one unprivileged attacker can run:

```rust
let big = HubAssetKey { hub_id, asset: big_asset };
let collateral = HubAssetKey { hub_id, asset: collateral_asset };

// Attacker-owned account.
let account = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral, enough_collateral)],
);

// Existing BIG liquidity is borrowed at high utilization.
controller.borrow(
    attacker,
    account,
    vec![(big.clone(), large_borrow_amount)],
    None,
);

// After ledger time advances far enough that
// borrowed_shares * borrow_index > i128::MAX:
controller.update_indexes(attacker, vec![big.clone()]);
```

For an 18-decimal asset, `1_000_000_000 * 10^18` base units produces approximately `1e36` scaled value at index `RAY`; a debt of `0.98e36` scaled shares overflows when the borrow index exceeds roughly `173.6 * RAY`. [6](#0-5)  The observed call sequence is `update_indexes` → `Cache::load` → `global_sync` → `accrue_step` → `scaled_to_original`, ending in `MathOverflow` before `mark_accrued` can persist progress. /// Returns the largest cap, in asset base units, whose ray-scaled form still
```rust
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
