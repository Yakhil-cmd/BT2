### Title
Webhook signature verification selects the signing organization from unauthenticated payload fields, letting a holder of one configured org's `webhook_secret` forge events for repositories/stacks belonging to a different org - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` picks *which* `webhook_secret` to verify the HMAC against by reading `repository_owner` straight out of the untrusted, not-yet-verified JSON body, while the handlers that actually act on the event (creating `Stack`/`Team`/`User` records, triggering `GithubSyncJob`, etc.) key off other, independently-controlled fields of that same body (`repository.full_name`, `organization.login`, `team.id`). This is the same class of bug as the Gondi `distribute()` finding: the field that is cryptographically bound/verified is not the same field the privileged action is executed on, so an attacker who legitimately possesses one tenant's secret can make the "verified" identity diverge from the identity actually acted upon.

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the app config to verify against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), *before* any signature check has succeeded. `Shipit.github(organization:)` looks up a distinct `webhook_secret`/app config per organization key, as documented for multi-org setups: [3](#0-2)  and exercised in `Shipit.github` / `github_app_config`: [4](#0-3) .

Once `verify_signature` succeeds (HMAC computed with whatever org's secret `repository_owner` happened to select), `create` blindly dispatches the **entire raw payload** to handlers: [5](#0-4) 

Handlers resolve the target `Stack`/`Repository` using a *different* field, `repository.full_name`, that was never part of the binding decision: [6](#0-5) 

Concretely: an attacker who runs (or has been given webhook access to) a small/low-privilege GitHub organization that is configured in Shipit's `github:` secrets (e.g. `OrgTwo` in the documented multi-app schema) knows/controls the `webhook_secret` for `OrgTwo`. They can craft a POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `OrgTwo` → so `verify_signature` selects `OrgTwo`'s app/secret, and the attacker can produce a valid `X-Hub-Signature` for that secret.
- `repository.full_name` = `OrgOne/some-other-repo` (a repository belonging to a *different*, higher-trust organization that also has a Stack configured in the same Shipit instance).

The signature check passes (it only validates that the request came from *someone* who knows `OrgTwo`'s secret), but the `push`/`status`/`check_suite` handler then acts on `OrgOne/some-other-repo`'s `Stack` because `Handler#stacks` keys off `repository.full_name`, not off the organization that was actually authenticated: [7](#0-6) , feeding e.g. `PushHandler#process` which queues `GithubSyncJob` with an attacker-chosen `expected_head_sha`: [8](#0-7) .

The equality that should hold but doesn't:
`organization whose secret authenticated the request == organization/repository the handler subsequently writes to`.
Before the attacker's request: verification org and acted-upon repository owner are implicitly assumed equal. After the crafted request: they can be made to diverge, because the field feeding `Shipit.github(organization:)` and the field feeding `Handler#stacks` are two independent, both attacker-supplied JSON keys with no cross-check between them.

### Impact Explanation
This does not (by itself) leak `GITHUB_TOKEN` or `github_access_token`, but it does let an attacker with only a benign/low-privilege GitHub org's webhook secret drive Shipit's internal deploy-pipeline state machine (commit ingestion, spec caching, deploy-spec cache invalidation, membership/team/user creation) for a `Stack` belonging to a completely different, more trusted repository/org that the attacker does not control on GitHub. Depending on which webhook events are wired (`push`, `status`, `check_suite`, `membership`), this can: force spurious `GithubSyncJob` runs with attacker-chosen `expected_head_sha`, fabricate commit statuses on someone else's tracked commits, or create/modify `Team`/`Membership` records tied to an arbitrary `organization.login` string (`MembershipHandler#find_or_create_team!` blindly sets `team.organization = params.organization.login`) which can influence `Shipit.github_teams` membership checks used for authorization (`User#authorized?`). This directly touches the "escalation into `Shipit.github_teams` authorization" and "unauthorized deploy/rollback" impact categories the rules call out as High/Critical, since forged `push`/status events can influence what Shipit considers deployable and can trigger sync/deploy-adjacent jobs against a stack the attacker's org has no legitimate relationship to.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with the multi-organization `github:` schema (explicitly documented and supported: `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker controlling/knowing the `webhook_secret` of *any one* of the configured organizations (e.g., they are a legitimate GitHub org admin for one of several orgs onboarded onto a shared Shipit instance, or run a low-value org that was added to a shared instance). No repository write access, no Shipit session, and no `ApiClient` token are needed — only knowledge of one tenant's webhook secret, which is a materially weaker privilege than write access to the target repository. This matches a realistic Shipit multi-tenant operating model (many orgs sharing one Shipit instance is the entire point of the "Using Multiple Github Applications" feature).

### Recommendation
Bind signature verification and payload processing to the *same* authenticated identity: after selecting `repository_owner`/`organization` to verify against, re-derive the resource to act on (`Repository.from_github_repo_name`) and require that its owner matches the organization whose secret validated the signature, rejecting (422) any event where `repository.full_name`'s owner differs from `repository_owner`/`organization.login` used for verification. Alternatively, since a `Repository`/`Stack` is already associated with a specific configured GitHub organization in multi-app mode, look up the expected organization from the resolved `Stack`/`Repository` record rather than trusting the payload for secret selection at all.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` config shown in `test/dummy/config/secrets_double_github_app.yml`/`docs/setup.md`, containing at least `OrgOne` (tracks a stack for `OrgOne/target-repo`) and `OrgTwo` (attacker knows `OrgTwo`'s `webhook_secret`).
2. Attacker builds a `push` payload: `{"ref": "refs/heads/master", "after": "<attacker-chosen-sha>", "repository": {"full_name": "OrgOne/target-repo", "owner": {"login": "OrgTwo"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgTwo_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')` (from `repository.owner.login`), the HMAC matches OrgTwo's secret, verification passes.
5. `create` dispatches to `PushHandler`, whose `stacks` (via `Handler#stacks`/`repository_name`) resolves `OrgOne/target-repo`'s `Stack`, and `sync_github(expected_head_sha: 'attacker-chosen-sha')` is enqueued for it — despite the request only having proven possession of `OrgTwo`'s secret, not any relationship to `OrgOne` or `target-repo`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
