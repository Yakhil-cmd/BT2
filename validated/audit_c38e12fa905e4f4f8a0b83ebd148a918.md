### Title
`Pallet::remote_proxy`/`remote_proxy_with_registered_proof` weight annotation does not scale with attacker-controlled `proof: Vec<Vec<u8>>` size, allowing under-charged PoV/compute consumption - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
The `#[pallet::weight]` annotations on `remote_proxy` and `remote_proxy_with_registered_proof` only add `WeightInfoOf::<T, I>::remote_proxy()` (a fixed constant from a benchmark that always uses a minimally-sized proof, `pallets/remote-proxy/src/benchmarking.rs`) plus the inner call's own `di.call_weight`. Neither weight function scales with the size of the caller-supplied `proof: Vec<Vec<u8>>`, even though `do_remote_proxy` feeds the entire `proof` into `sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` and `sp_trie::read_trie_value`, both of which do work proportional to the total byte size of `proof` (hashing and inserting every supplied node into the in-memory trie backend, regardless of whether that node is on the path to the target key).

### Finding Description
`Pallet::remote_proxy` (`pallets/remote-proxy/src/lib.rs:284-304`) and `Pallet::remote_proxy_with_registered_proof` (`:364-390`) compute their declared weight as:
```
let di = call.get_dispatch_info();
WeightInfoOf::<T, I>::remote_proxy()
    .saturating_add(T::DbWeight::get().reads_writes(1, 1))
    .saturating_add(di.call_weight)
```
`di.call_weight` is well-calibrated for the *inner* call because the inner call's own pallet is independently benchmarked for its own parameters. `WeightInfoOf::<T, I>::remote_proxy()`, however, is a single fixed weight value that is benchmarked in `pallets/remote-proxy/src/benchmarking.rs:48-71` using a proof generated by `T::RemoteProxy::create_remote_proxy_proof(...)`, i.e. a realistically small, minimal proof for one storage item. There is no `x`/linear component parameterized over proof length in the benchmark, and the weight formula in `lib.rs` never reads `proof`'s length to scale the charge.

Inside `do_remote_proxy` (`:405-455`), the full user-supplied `proof` is passed to `sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` and then `sp_trie::read_trie_value`. Building the in-memory trie DB hashes and inserts *every* node in `proof`, so its CPU cost is proportional to the sum of the byte lengths of all entries in the `Vec<Vec<u8>>`, not just the nodes actually needed to prove the target key. An attacker can pad `proof` with additional garbage/duplicate byte blobs up to the extrinsic/block length limit (e.g. a fraction of the ~5MB `RuntimeBlockLength` seen in `system-parachains/asset-hubs/asset-hub-kusama/src/lib.rs:171-178`) while the runtime still only charges the fixed `remote_proxy()` benchmark weight for that verification step.

No other check in the pallet bounds or scales the cost with `proof` size: there is no `MaxEncodedLen`/`BoundedVec` limit on the number or size of proof nodes beyond the generic extrinsic-length limit, and the length-based transaction fee (a separate fee dimension from `Weight`) does not correct the `ref_time`/PoV-weight budget that governs how much computation a block builder assumes an extrinsic will consume.

### Impact Explanation
Since the charged `Weight` for `remote_proxy`/`remote_proxy_with_registered_proof` under-represents the actual CPU work of trie-proof verification for maximally padded `proof` vectors, an attacker can submit multiple such extrinsics that consume more real execution time per unit of charged weight than intended. This breaks the invariant that "weight/fee charged must be proportional to actual resource consumption" and can let an attacker fill a disproportionate share of a block's real computation time relative to its accounted weight, degrading block production throughput and delaying inclusion of other users' extrinsics (including legitimate asset operations) queued in the same or subsequent blocks.

### Likelihood Explanation
Exploitation requires only a signed account able to submit `remote_proxy` (no special privilege), a low-declared-weight inner call (e.g. `frame_system::remark`), and a crafted `proof: Vec<Vec<u8>>` padded up to the extrinsic length limit. It does not require the proxy proof itself to be valid for a match — the trie-DB construction cost is paid before the "not found"/`InvalidProof` error is even returned, since `into_memory_db` and `read_trie_value` run before the `find(f)` match logic (`:418-454`). This makes the attack repeatable and cheap relative to the extra CPU it forces the runtime to spend, bounded only by the chain's `RuntimeBlockLength`/`max_extrinsic_size` limits.

### Recommendation
Parameterize `WeightInfoOf::<T, I>::remote_proxy()` (and the registered-proof variant) over the actual size of `proof` (e.g. total encoded length or node count) with a benchmark that measures worst-case trie-proof verification cost as a function of proof size, then charge `base_weight + per_byte_weight * proof.encoded_size()` in the `#[pallet::weight]` closure. Additionally consider bounding the maximum number/size of proof nodes accepted (e.g. via a `MaxProofSize`/`BoundedVec` config parameter) so the worst case is bounded and can be benchmarked precisely.

### Proof of Concept
Rust benchmark/fuzz test plan:
1. In a test harness using `pallets/remote-proxy/src/tests.rs`'s mock runtime, construct a valid minimal `RemoteProxyProof::RelayChain { proof, block }` as in `create_remote_proxy_proof`, then pad `proof` with additional large, unrelated (but valid `Vec<u8>`) byte blobs up to `T::MaxBlockLength`-derived size.
2. Measure actual wall-clock/instruction count of `Pallet::<T,I>::do_remote_proxy` (or the full extrinsic dispatch) for (a) the minimal proof and (b) the maximally padded proof.
3. Assert that the ratio of measured cost (b)/(a) is not reflected in `WeightInfoOf::<T,I>::remote_proxy()` — i.e., assert `measured_weight(b) > WeightInfoOf::<T,I>::remote_proxy()` while the declared weight charged by the runtime for both (a) and (b) is identical.
4. Expected assertion: charged weight for (a) == charged weight for (b), but `measured_execution_time(b) >> measured_execution_time(a)`, demonstrating the declared weight fails to bound worst-case observed weight as required by the invariant.
