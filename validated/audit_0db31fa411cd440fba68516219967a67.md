### Title
`socialize-debt` uses stale `index`/`lindex` because it skips the mandatory `accrue()` call, unlike every other vault-mutating entrypoint - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every state-mutating vault function that depends on the borrow index or liquidity index first calls `(try! (accrue))` to bring those indexes up to date before using them — `system-borrow`, `system-repay`, and `flashloan` all do this. `socialize-debt` is the one exception: it reads `index` and `lindex` directly from storage without a preceding `accrue()` call, then uses those potentially-stale values to compute how much bad debt to write off and how much to slash the liquidity index that determines every zToken holder's redemption value.

### Finding Description
In `v0-vault-usdc.clar` (and the equivalent `socialize-debt` in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`), compare: [1](#0-0) [2](#0-1) 

Both `system-borrow` and `system-repay` call `(try! (accrue))` before reading `index`/`principal-scaled`, guaranteeing the values reflect all interest accrued up to the current timestamp.

`socialize-debt`, however, reads `index`, `lindex`, `assets` and `total-borrowed` straight out of storage with **no accrual step**: [3](#0-2) 

`debt-reduction` (used to determine how much of `old-total-assets` is being wiped out) and `new-lindex` (which is written directly into storage and read by every future `redeem`/`convert-to-assets` call for every zToken holder) are both derived from a potentially stale `idx`/`current-lindex`/`old-total-assets`. If interest has accrued since the last `accrue()` call (i.e., market.clar or any caller does not accrue this specific vault in the same transaction right before invoking `socialize-debt`), `debt-reduction` under- or over-states the real bad debt relative to the vault's true total assets, so `new-lindex` is computed on the wrong denominator/numerator pair. This directly parallels the reported bug class: a value (`weeklyEmissions` there, `index`/`lindex` here) that must be freshly refreshed before being consumed in a downstream shared calculation, but whose refresh is not enforced by the function that consumes it — leaving correctness dependent on whatever the caller happened to do beforehand.

Unlike the BIMA report where only the claimant's own reward was affected, here the miscalculated `lindex` write-down is **socialized across every zToken holder of the vault** — the stale-index caller (a liquidator or the market contract acting on their behalf) determines, via an avoidable staleness bug, how much loss every other current and future zToken holder absorbs.

### Impact Explanation
`lindex` directly backs `convert-to-assets`/`redeem` pricing for every supplier in the vault. An incorrect write-down (too small) leaves bad debt un-recognized, permanently overstating the redeemable value of zTokens system-wide until enough interest naturally accrues to “catch up” — a temporary/permanent freezing or mispricing of other suppliers' funds, i.e., loss socialized onto users who took no action. This lands in the **High** impact bucket (temporary freezing of funds / theft of value shared among suppliers due to incorrect accounting), and in the worst case (index writes compound with subsequent normal accruals) it degrades protocol solvency of the vault's shares.

### Likelihood Explanation
Any transaction path that invokes `socialize-debt` without first triggering `accrue()` on that same vault in the same block will exhibit this — this is easy to trigger by construction because `socialize-debt` has no internal accrual safeguard (contrasted with every sibling mutating function, which does). Whether market.clar's actual liquidation/bad-debt flow always calls `accrue`/`accrue-and-cache` for the exact vault immediately before calling `vault-socialize-debt` could not be fully confirmed from the excerpts retrieved; this is the main remaining uncertainty.

### Recommendation
Add `(u (try! (accrue)))` as the first binding in `socialize-debt`'s `let`, exactly as done in `system-borrow`/`system-repay`/`flashloan`, so `index`/`lindex`/`assets`/`total-borrowed` are guaranteed fresh before the write-down math executes. Apply this fix to `socialize-debt` in `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`.

### Proof of Concept
1. Let a vault accrue significant unrealized interest since its `last-update` (e.g., pause `accrue` temporarily via `set-pause-states`, wait, then unpause without an intervening accrual — or simply have a block where no other vault operation has run).
2. Trigger a liquidation/bad-debt path that calls `vault-socialize-debt` for that vault directly (bypassing a fresh `accrue()` call), e.g. by an authorized caller invoking `socialize-debt` on the vault contract without a preceding `accrue` in the same transaction.
3. Observe `debt-reduction` and `new-lindex` computed in `socialize-debt` ( [4](#0-3) ) using the stale `idx`/`current-lindex`/`old-total-assets` instead of the values `accrue()` ( [5](#0-4)  shape, mirrored in v0-vault-usdc) would have produced.
4. Compare the resulting `lindex` (and hence `convert-to-assets` value for all zToken holders) against the value obtained if `accrue()` had been called immediately before `socialize-debt` — they diverge whenever unaccrued interest exists at call time, showing suppliers' redeemable balances are computed on an incorrect basis that was never their own doing.
