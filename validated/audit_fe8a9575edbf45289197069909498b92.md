### Title
Unprivileged third party can grief a victim's egroup via unauthorized full `repay` on-behalf-of, forcing an unfavorable egroup transition that makes the victim liquidatable - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`repay(ft, amount, on-behalf-of)` lets **any caller** fully repay a specific debt asset for **any account**, using the caller's own funds. When the repaid asset's scaled debt reaches zero, `v0-market-vault::debt-remove-scaled` clears the corresponding debt bit from the victim's bitmask, causing an implicit egroup transition. Unlike `collateral-add`, which explicitly guards against harmful egroup transitions with a capacity check (`future-capacity >= current-capacity`, `ERR-UNHEALTHY`), `repay` performs no equivalent check before or after mutating the mask.

### Finding Description
The bug-class hint concerns a privileged/permissioned actor triggering an early, irreversible state transition (revealing solutions) that blocks another party's expected action while the actor keeps the benefit of the victim's locked-in resources. The Zest analog: `repay` is a permissionless function that lets caller A write into victim B's debt position state via `on-behalf-of`, exactly as the trivia contract let one party force a state change affecting another party's ability to act.

Flow:
1. Victim B holds a diversified position across egroup E1 (e.g., sBTC collateral + USDC + USDH debt), which grants a favorable LTV for that specific asset combination.
2. Attacker A calls `market.repay(usdhFt, hugeAmount, some(B))`, using their own USDH to fully pay off B's USDH debt (`amount-to-repay` is capped by `max-repay-tokens`, so A only needs to supply exactly B's outstanding USDH debt).
3. Because `repaid-scaled-debt == account-scaled-debt` (`repaying-all` is `true`), `v0-market-vault::debt-remove-scaled` clears the USDH debt bit from B's mask.
4. B's mask now resolves to a different, narrower egroup (e.g., sBTC collateral + USDC-only debt), which may carry a lower `LTV-BORROW`/`LTV-LIQ-PARTIAL` for B's remaining USDC debt than the multi-asset egroup B was relying on.
5. `repay` performs no `is-healthy-with-mask` / capacity check on the resulting egroup transition (contrast with `collateral-add`'s explicit protection at [4](#0-3) ), so B's position can become instantly liquidatable purely as a side effect of A's unsolicited repayment.
6. A (or a colluding third party) can then call `liquidate` on B and collect the liquidation bonus, while B is deprived of the egroup they built their position around and loses collateral to the liquidation penalty they never opted into.

### Impact Explanation
This is a write to a stranger's position (`on-behalf-of`) that changes shared state (the position bitmask/egroup) consumed by health/liquidation logic, and it can push another user's healthy position into liquidation without their consent — theft of collateral value via the liquidation penalty extracted from B, i.e., a Temporary/permanent loss of funds for the victim (liquidation penalty applied against B's will) and profit opportunity for the attacker. This lands in the in-scope **High** impact category: theft via forced liquidation penalty extraction from an otherwise-healthy position, since attacker-triggered liquidation converts B's unclaimed collateral value into attacker profit that would not have existed absent the unsolicited `repay`.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to identify a borrower whose egroup depends on a specific multi-asset debt combination, and to have (or flash-borrow, if permitted elsewhere) the exact debt-asset amount needed to trigger `repaying-all`. No `flashloan` mechanics are needed for the core griefing since only the exact debt token amount is required as ordinary capital. The `on-behalf-of` parameter is unauthenticated with respect to consent — any account can be named.

### Recommendation
In `v0-4-market.clar::repay`, when `repaying-all` is true for a debt asset that would cause a mask/egroup transition, perform the same capacity/health validation used in `collateral-add`: resolve the future mask after removing the debt bit, compute `is-healthy-with-mask` (or the capacity formula) against the account's remaining collateral/debt, and reject the on-behalf-of repayment (or skip the mask-clearing egroup narrowing) if it would decrease the account's health/capacity below its current debt. Alternatively, restrict full on-behalf-of repayments that trigger egroup transitions to `contract-caller == account` unless the resulting egroup is validated safe.

### Proof of Concept
Conceptual reproduction (Clarinet/simnet, mirroring the existing `collateral-add.test.ts` / `egroup.test.ts` harness style):
1. Alice deposits sBTC collateral and borrows both USDC and USDH such that her position resolves to Egroup E1 (sBTC coll + USDC+USDH debt) with LTV 70%, at a debt level that would be unhealthy under the narrower Egroup E2 (sBTC coll + USDC-only debt, LTV 45%) — analogous to the `TEST 3`/`EG-01` scenarios already present in `local-testing/tests/flows/collateral/collateral-add.test.ts` and `local-testing/tests/security/egroup.test.ts` that construct exactly this kind of capacity delta.
2. Bob (attacker, no relationship to Alice) mints/holds enough USDH to cover Alice's full USDH debt and calls `market.repay(usdhFt, aliceUsdhDebtAmount, some(alice))`.
3. `debt-remove-scaled` clears Alice's USDH debt bit; Alice's mask now resolves to Egroup E2.
4. Assert Alice's position is now liquidatable under E2's `LTV-LIQ-PARTIAL` even though it was healthy under E1, and that `repay` did not revert despite this outcome (no `ERR-UNHEALTHY`-style check exists in `repay`, unlike in `collateral-add`).
5. Bob (or Charlie) calls `market.liquidate(alice, ...)` and receives the liquidation bonus. [5](#0-4)

(define-public (debt-remove-scaled (account principal) (scaled-amount uint) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-scaled-debt user-id asset-id scaled-amount)))
        (nmask (if (is-eq remaining u0)
                      (mask-update mask asset-id false false) ;; debt, remove
                      mask))
        (updated-entry (merge entry (refresh nmask))))

    (try! (check-impl-auth))
    (asserts! (not (get debt-remove states)) ERR-PAUSED)
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)
