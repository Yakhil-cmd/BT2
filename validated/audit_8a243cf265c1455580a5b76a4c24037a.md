### Title
Deregistered Bridge Operator's Votes Persist in `voteCounts`, Allowing Threshold Satisfaction With Revoked Authority — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from `operators[_operator]` and `operatorList`, but does **not** clear that operator's already-cast votes from `votes[VoteType.ValueTransfer][N].voteCounts[voteKey]`. A subsequently registered (or still-active) operator voting for the same nonce and parameters can push `voteCounts` to the threshold, executing a `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` that the owner intended to block by deregistering the first operator. The contract itself documents this in a comment but leaves it unmitigated.

---

### Finding Description

`BridgeOperator` maintains a nested mapping:

```
mapping(uint8 => mapping(uint64 => VotesData)) private votes;
```

where `VotesData` holds `voted[address] → bytes32` and `voteCounts[bytes32] → uint8`. [1](#0-0) 

When an operator calls `handleKLAYTransfer` (or the ERC-20/ERC-721 equivalents), `_voteValueTransfer` is invoked, which calls `_voteCommon`. `_voteCommon` increments `voteCounts[voteKey]` and returns `true` (triggering the transfer) when the count reaches `operatorThresholds[VoteType.ValueTransfer]`. [2](#0-1) 

`deregisterOperator` only flips `operators[_operator] = false` and removes the address from `operatorList`. It does **not** touch `votes[...][N].voted[_operator]` or `votes[...][N].voteCounts[voteKey]`: [3](#0-2) 

The code's own comment (lines 148–158) describes the exact exploit path:

> *"Note that outstanding votes by the deregistered operator are not revoked. … Operator A votes on nonce N → Owner deregisters A → Operator B votes on nonce N, thereby executing the request N. In this case the request was executed with A's vote after A is deregistered."*

Because `handleKLAYTransfer` guards entry with `onlyOperators` (checking `operators[msg.sender]`), the deregistered operator cannot cast a *new* vote — but their already-counted vote in `voteCounts` is permanent and invisible to the threshold check. [4](#0-3) 

The same flaw applies to `handleERC20Transfer` and `handleERC721Transfer` in `BridgeTransferERC20.sol` and `BridgeTransferERC721.sol`, and to configuration votes (`_voteConfiguration`) used by `setKLAYFee` / `setERC20Fee`. [5](#0-4) 

---

### Impact Explanation

When the threshold is satisfied using a deregistered operator's stale vote, `handleKLAYTransfer` executes:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [6](#0-5) 

This sends KAIA (or mints/transfers ERC-20/ERC-721 tokens) to the `_to` address encoded in the fraudulent vote. The corrupted state value is `votes[uint8(VoteType.ValueTransfer)][N].voteCounts[voteKey]`, which retains a count contribution from a revoked operator. The result is an **unauthorized transfer of bridged assets** (KAIA, ERC-20, ERC-721) to an attacker-controlled address, bypassing the owner's explicit revocation intent.

---

### Likelihood Explanation

The scenario requires:
1. At least one operator to be compromised (key leak, insider, or coercion) and to cast a vote for fraudulent transfer parameters before the owner reacts.
2. The owner to deregister that operator — the standard incident-response action — which the owner reasonably expects to neutralize the vote.
3. A second currently-registered operator to call the same handle function with the same fraudulent parameters (either also compromised, or tricked into believing the request is legitimate).

With threshold = 2 and two operators, a single compromised operator plus the owner's delayed deregistration window is sufficient. The comment's own framing ("The Owner shall recognize this issue and expect that operator deregistration takes some time to be fully effective") confirms this is a realistic operational scenario, not a theoretical one.

---

### Recommendation

In `deregisterOperator`, after removing the operator from `operators` and `operatorList`, iterate over all open `VotesData` entries for that operator and subtract their contribution from `voteCounts`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];

    // NEW: revoke all pending votes cast by this operator
    for (uint8 vt = 0; vt < uint8(VoteType.Max); vt++) {
        // Iterate over known open nonces or maintain a per-operator nonce list.
        // Simpler alternative: store a per-operator list of (voteType, nonce) pairs
        // and clear them here.
    }

    // existing operatorList removal ...
    emit OperatorDeregistered(_operator);
}
```

A simpler alternative is to maintain a `mapping(address => uint64[]) private operatorOpenNonces` that records every nonce an operator has voted on, enabling O(k) cleanup on deregistration. Alternatively, the threshold check in `_voteCommon` can be changed to re-validate that each voter in `vote.voters` is still a current operator before counting their vote — though this is more gas-intensive.

### Proof of Concept

Setup: Bridge deployed with operators `[A, B]`, `operatorThresholds[ValueTransfer] = 2`, bridge holds 1000 KAIA.

1. **Attacker compromises operator A's key.**
2. **Attacker (as A) calls** `handleKLAYTransfer(txHash, user, attacker, 1000, nonce=5, blk, "")`. `_voteCommon` records `votes[0][5].voted[A] = voteKey` and sets `votes[0][5].voteCounts[voteKey] = 1`. Threshold not yet met; function returns without transferring.
3. **Owner discovers A is compromised and calls** `deregisterOperator(A)`. `operators[A]` is deleted. `votes[0][5].voteCounts[voteKey]` remains `1`.
4. **Attacker (also controlling B, or B is coerced) calls** `handleKLAYTransfer(txHash, user, attacker, 1000, nonce=5, blk, "")` as B. `_voteCommon` increments `votes[0][5].voteCounts[voteKey]` to `2`. `2 >= threshold(2)` → returns `true`. `closedValueTransferVotes[5] = true`. 1000 KAIA is sent to `attacker`.

The owner's deregistration of A had zero effect on the outcome. The corrupted `voteCounts` value (`1` from a revoked operator) was the deciding contribution. [7](#0-6) [8](#0-7)

    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
