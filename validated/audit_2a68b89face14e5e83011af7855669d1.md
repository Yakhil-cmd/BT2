### Title
API token stack-scope bypass in `CCMenuController` allows unauthorized cross-stack read - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` can only interact with the single stack it is bound to, by resolving `stack` through the scoped `stacks` relation [1](#0-0) . `Shipit::Api::CCMenuController` overrides this private `stack` method and resolves it directly from the global `Stack` table using only the client-supplied `params[:stack_id]`, without any scoping to `current_api_client.stack_id` [2](#0-1) . This breaks the binding `stack a token authorises == stack a token touches`: a token that GitHub/Shipit issued scoped to stack A can be used to read the CI status (`ccmenu#show`) of any other stack B.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [3](#0-2) . The engine's intended enforcement of that scope lives in `BaseController#stacks`/`#stack`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every other API controller (e.g. `StacksController`, `MergeRequestsController`, `HooksController`) relies on this inherited `stack`/`stacks` helper, so a scoped client is confined to its own stack.

`CCMenuController`, however, redefines the private `stack` method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Because Ruby method resolution favors the subclass's redefinition, `show` (which calls `stack.deploys_and_rollbacks.last`) never goes through the `current_api_client.stack_id` scoping check [4](#0-3) . The `require_permission :read, :stack` before_action only checks that the client's permission list contains `read:stack` [5](#0-4) ; it does not verify which stack the permission applies to. Consequently, any valid, authenticated `ApiClient` token that has `read:stack` in its `permissions` — even one deliberately scoped to a single, low-sensitivity stack (see fixture `here_come_the_walrus`, scoped to `stack: shipit` [6](#0-5) ) — can supply an arbitrary `stack_id` in the CCMenu request path and read build/deploy status for a stack it was never authorized to touch.

This is the exact analog of the report's bug class: a value that is supposed to gate/constrain an operation (the "0.25%" bonus constant vs. the actual "0.025%" used) is silently replaced by a weaker/incorrect check — here the per-request stack-scope check is silently dropped for one controller, producing the binding mismatch `authorized_stack != accessed_stack`.

### Impact Explanation
This meets the High severity bar: "unauthenticated [scope-inconsistent] read of stack state" — specifically, cross-repository/cross-stack unauthorized read of deploy/task state via a legitimately-issued but scope-restricted API token, using an authentication mechanism the client never should have access outside its bound stack.

### Likelihood Explanation
Likelihood is high: any deployment that issues stack-scoped `ApiClient` tokens (a first-class, documented feature — e.g. the auto-created CCMenu client via `CCMenuUrlController#client`, `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)` [7](#0-6) ) is directly exposed to this bug the moment that token is used against `Api::CCMenuController` with a different `stack_id` parameter — no special privileges, secrets, or additional access are required beyond possessing one valid, narrowly-scoped token.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` and let it inherit `BaseController#stack`, so lookups always go through the scoped `stacks` relation:

```ruby
private

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

If a bespoke lookup is required, it must intersect with `stacks` (i.e. `stacks.from_param!(params[:stack_id])`) rather than querying `Stack` directly.

### Proof of Concept
1. Provision a scoped API client, e.g. fixture-equivalent: `ApiClient.create!(creator: some_user, name: 'scoped', stack: stack_a, permissions: ['read:stack'])`, so `current_api_client.stack_id == stack_a.id`.
2. As an attacker holding only that token (e.g. it was leaked/shared for read-only CCMenu polling of `stack_a`), issue:
   `GET /api/stacks/other_owner/other_repo/production/ccmenu?token=<scoped_token>`
3. `CCMenuController#authenticate_api_client` succeeds (token is valid) [8](#0-7) .
4. `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack`, regardless of which stack [5](#0-4) .
5. `stack` resolves via `Stack.from_param!(params[:stack_id])`, unconstrained by `current_api_client.stack_id`, returning `other_owner/other_repo/production` — a stack the token was never bound to [9](#0-8) .
6. `show` renders that unrelated stack's latest deploy/rollback status [4](#0-3) , confirming unauthorized cross-stack read.
