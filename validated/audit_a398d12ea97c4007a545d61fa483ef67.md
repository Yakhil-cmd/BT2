### Title
Webhook signature verified against organization login from the payload while handlers act on the (separately-controlled) `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the incoming `X-Hub-Signature` against using `repository_owner`, a value read directly out of the *unverified* JSON body (`params.dig('repository','owner','login')`). Once the signature check passes, every event handler (e.g. `PushHandler`, the `PullRequest::*Handler`s) instead resolves the target `Repository`/`Stack` using a different field from that same body: `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`. Nothing ties the `owner.login` value used for authentication to the `full_name` value used to select which repository is written to.

For example `PushHandler#process` finds stacks by `branch` scoped to `stacks` derived from `repository.full_name`, and calls `stack.sync_github(expected_head_sha:)`: [4](#0-3) 

The equality that should hold but doesn't: *the organization whose secret authenticated the request* == *the organization owning the repository that is actually written*. Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are two independent, attacker-suppliable fields inside the same unauthenticated JSON body, an attacker who can produce a validly-signed payload for **any one** configured organization (i.e., they know that organization's `webhook_secret`, per the multi-org config format in `config/secrets.development.example.yml`) can set `repository.full_name` to point at a **different** organization/repository already tracked by Shipit. The `PushHandler` and pull-request handlers would then archive/unarchive stacks, trigger `sync_github` and mutate `PullRequest`/review-stack state for that unrelated repository, purely on the strength of a signature that only proves knowledge of a different org's secret.

### Impact Explanation
This breaks the org-authenticated vs. repo-written binding explicitly called out as in-scope. Concretely it allows unauthorized manipulation of a victim stack's GitHub sync state, archiving/unarchiving of review stacks, and label/PR record tampering for a repository the attacker's own webhook secret was never meant to authorize — a cross-organization/cross-repository write, matching the Critical "cross-repository writes" impact bar in the rules.

### Likelihood Explanation
Exploitability is conditioned on Shipit being configured with the multi-organization `github:` secrets format (each org keyed with its own `webhook_secret`) and the attacker controlling (or having legitimately configured, in a shared/multi-tenant Shipit deployment) at least one of those organizations' GitHub App installations, i.e. knowing that org's own webhook secret. In a single-tenant deployment with one global `github:` block, all organizations resolve to the same `GitHubApp`/secret, so the class of attack still applies to that shared secret being reusable for cross-repo forgery, but does not require possession of a second, distinct secret. Given webhook secrets are configuration-time-known values (not per-request derived from the signed content), and nothing in `Handler` cross-checks `repository.owner.login` against `repository.full_name` before mutating state, likelihood is moderate wherever Shipit is used to track more than one organization/repository through the same `/webhooks` endpoint.

### Recommendation
Bind the field used for authorization selection to the field used for the actual mutation: after `verify_webhook_signature` succeeds, re-derive the affected `Repository` strictly from `repository.owner.login` (the same field that selected the signing organization) rather than trusting `repository.full_name` independently in `Handler#repository_name`, or explicitly assert `repository.full_name.owner == repository_owner` before dispatching to handlers. Consider embedding/verifying the organization identity as part of each handler's resolution path instead of trusting two independently-controlled JSON fields.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (attacker-controlled installation, secret known to attacker) and `org-b` (victim, tracked stacks/repos exist in Shipit).
2. Attacker computes a valid HMAC-SHA1 signature over a crafted JSON body using `org-a`'s known `webhook_secret`:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac using org-a secret>`.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, verifies successfully against the attacker-known secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, finds the victim's stacks on the `main` branch, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, mutating the victim's repository/stack state despite the signature never having proven anything about `org-b`.
