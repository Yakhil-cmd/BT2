### Title
Cross-tenant webhook signature confusion allows attacker-org secret to authorize `membership` events for a different organization's team - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#repository_owner` picks the organization used for signature verification from `params.dig('repository','owner','login')`, while `MembershipHandler#process` picks the organization it actually mutates from `params.organization.login`. An attacker who legitimately controls their own tenant (`attacker-org`) can craft a `membership` webhook body where `repository.owner.login = 'attacker-org'` but `organization.login = 'shopify'`, causing the request to be signed/verified with the attacker's own valid `webhook_secret` while the handler adds the attacker as a member of a real `shopify` `Team`.

### Finding Description
The broken binding is: `organization_that_signed_the_request == organization_whose_team_is_mutated`. Before tracing the code this should hold, i.e. `repository_owner` (used in `Shipit.github(organization: repository_owner)` for signature verification) must equal `params.organization.login` (used by `MembershipHandler` to resolve/create the `Team`). Tracing the code shows this does not hold.

`WebhooksController#verify_signature` computes the verifying org via `repository_owner`, which prefers `repository.owner.login` over `organization.login`: [1](#0-0) 

That same method is used to select the `GitHubApp` instance and secret used for HMAC verification: [2](#0-1) 

However, `MembershipHandler#process` and its `find_or_create_team!` helper never consult `repository.owner.login` — they use `params.organization.login` (and `params.team.id`) to find-or-create the `Team` and add the member: [3](#0-2) 

Attacker request: POST `/webhooks` with `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": {"id": <existing shopify team github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `X-Hub-Signature` computed from the attacker's own genuine `webhook_secret` for `attacker-org`.

Exploit flow: `verify_signature` calls `repository_owner` → returns `'attacker-org'` (repository key present) → `Shipit.github(organization: 'attacker-org')` → HMAC verifies successfully against the attacker's own secret → request passes. `MembershipHandler#process` then runs with `params.organization.login == 'shopify'`, calls `Team.find_or_create_by!(github_id: params.team.id)` which finds the pre-existing `shopify` team (block only executes on create, so it doesn't matter attacker doesn't know shopify's real team metadata beyond the `github_id`), and calls `team.add_member(User.find_or_create_by_login!('attacker'))`, which appends the membership: [4](#0-3) 

No existing guard prevents this: `drop_unhandled_event` only checks the event name is registered, `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `organization.login`, `team.id`, etc. — it never cross-checks against `repository.owner.login` or the org that verified the signature. `force_github_authentication`/`require_permission!` are session-auth concerns unrelated to the webhook path. Once the `Membership` row exists, `User#authorized?` becomes true if the mutated `shopify` team is in `Shipit.github_teams`: [5](#0-4) 

### Impact Explanation
An attacker who only controls their own legitimately-configured tenant (`attacker-org`) can grant themselves membership in an arbitrary pre-existing `Shipit::Team` belonging to a different, victim organization (`shopify`), purely by knowing/guessing that team's GitHub `id` (which is not secret — team IDs are visible via GitHub API/UI to many users, or via `lib/tasks/teams.rake`/oauth config). If that team is one of `Shipit.github_teams` (the set of teams that grant app-wide `authorized?` access), the attacker becomes an authorized Shipit user without ever presenting `shopify`'s webhook secret. This is a genuine cross-tenant authentication/authorization bypass — the signing organization and the mutated organization diverge — matching the "escalation into `Shipit.github_teams` authorization" / "unauthorized... payload for one repository mutating another's... team" Critical/High categories. The attack is repeatable for any team `github_id` and requires no interaction beyond a single crafted HTTP POST per membership grant/revoke.

### Likelihood Explanation
Preconditions: Shipit configured multi-org (`lib/shipit/github_app.rb` per-org secrets via `Shipit.github_app_config`), attacker legitimately controls one configured tenant (`attacker-org`) with their own valid `webhook_secret`, and the victim team's `github_id` is known or discoverable. The attacker needs no session, no API token, no `shopify` secret — only the ability to sign a payload with their own secret and POST it to `/webhooks`, both of which are within the stated attacker capabilities. This makes the attack low-cost and directly reproducible.

### Recommendation
In `MembershipHandler` (and any other handler that trusts `params.organization.login` or similar org fields for authorization-relevant mutations), require that the organization used to verify the webhook signature (`repository_owner` from `WebhooksController`) matches the organization referenced in the payload used to select/mutate the `Team`/`Repository`. Concretely, pass the verified `repository_owner` into the handler context and assert `params.organization.login.casecmp?(verified_organization)` before performing `Team.find_or_create_by!`/`add_member`, rejecting (422) on mismatch. More generally, `repository_owner` should not silently prefer a possibly-unrelated `repository.owner.login` over `organization.login` when both are present without validating they refer to the same tenant used for the actual mutation.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook signed by attacker-org cannot mutate shopify's team" do
  shopify_team = shipit_teams(:shopify_developers) # organization == 'shopify'

  payload = {
    action: 'added',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'shopify' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  attacker_secret = 'attacker-known-secret'
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)}"

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )
  Shipit.expects(:github).with(organization: 'shopify').never

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  attacker = User.find_by(login: 'attacker')
  assert shopify_team.members.include?(attacker), "attacker should NOT be a member of shopify's team via attacker-org's secret"

  Shipit.stubs(:github_teams).returns([shopify_team])
  assert attacker.authorized?, "attacker should NOT gain Shipit.github_teams authorization from a signature verified only against attacker-org"
end
```
Both assertions demonstrate the broken binding: the signature verified against `attacker-org` (side A) but the mutated/authorized entity is `shopify`'s team (side B) — A ≠ B.
