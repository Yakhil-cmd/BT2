## Analysis

This maps to the "GitHub identity versus the `User` bound to the session" binding category. The relevant equality that should hold is: **session presented after OAuth completion == session created for that OAuth completion** (i.e., no pre-existing, attacker-influenced session should be reused to carry a freshly authenticated identity). The `GithubAuthenticationController#callback` action violates this by writing the authenticated user's id directly into the *existing* session without first invalidating/regenerating it. [1](#0-0) 

Compare this to `logout`, which correctly calls `reset_session`: [2](#0-1) 

The authorization gate that later trusts `session[:user_id]` is `Shipit::Authentication#find_current_user`, which merely does `User.find_by(id: session[:user_id])` — it has no way to know whether the session carrying that id was created fresh at login time or reused from before: [3](#0-2) 

### Title
Session Fixation on OAuth Login - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` assigns `session[:user_id]` on top of whatever session already exists for the requesting browser, without calling `reset_session` beforehand. This is the textbook CWE-384 Session Fixation pattern: whoever controls the pre-authentication session (e.g., by getting their session identifier accepted by the victim's browser) inherits the authenticated identity once the victim completes the GitHub OAuth flow through that same session.

### Finding Description
On successful OAuth callback, the code does:
```ruby
session[:user_id] = sign_in_github(auth)
session[:authenticated] = true
```
with no `reset_session` call. If a session-identifying value can be fixed onto a victim's browser prior to login (for example, if the host application backs Rails sessions with a server-side store such as ActiveRecord/Redis session store, where the session key is transmitted as an opaque id rather than a self-contained signed value), then:
1. Attacker establishes/knows a session identifier.
2. Attacker gets that identifier accepted by the victim's browser (e.g., cookie planted via a sibling subdomain, or a session id transmitted in a link if such a store/config is used).
3. Victim authenticates through the `/github/auth/github/callback` flow using that same fixed session.
4. `session[:user_id]` is now the victim's id, but the underlying session was created/controlled by the attacker before authentication — the attacker's browser/session reference now carries the victim's authenticated identity.

The engine performs no `reset_session` at the privilege boundary (unauthenticated → authenticated), which is the standard mitigation for this class of bug. The engine also does not mandate a session store, so whether the concrete session_store configuration makes this exploitable is a host application decision — but the vulnerable code path is entirely within this engine's `GithubAuthenticationController`.

### Impact Explanation
Successful exploitation binds an attacker-controlled session to a legitimate user's authenticated identity, effectively giving the attacker persistent access to that user's Shipit session — including any deploy/rollback/merge actions the victim's `User` record is authorized for. This matches the rules' explicitly enumerated High-impact category: "session fixation / forced OAuth completion."

### Likelihood Explanation
Exploitability depends on the host application's session store configuration (a cookie-store-only deployment with strongly signed/encrypted cookies containing the user id reduces classic fixation risk, since there is no server-side session-id indirection to fix). However, the engine itself provides no defense-in-depth (`reset_session`) at the authentication boundary, so any deployment using a server-side session backend is directly exposed, and the missing safeguard is a code-level gap regardless of deployment specifics.

### Recommendation
Call `reset_session` (or equivalent session regeneration) in `GithubAuthenticationController#callback` before assigning `session[:user_id]`, mirroring the pattern already used in `logout`.

### Proof of Concept
1. Configure Shipit with a server-side session store (e.g., ActiveRecord session store) — a supported Rails configuration, not a deviation from documented engine usage.
2. Attacker obtains/fixes a session identifier and gets it set on the victim's browser (e.g., via a cookie-injection vector on a shared/parent domain).
3. Victim visits Shipit and completes GitHub OAuth login; `GithubAuthenticationController#callback` sets `session[:user_id] = <victim id>` on the fixed session without regenerating it.
4. Attacker, using the same known session identifier, is now recognized as the victim by `Shipit::Authentication#find_current_user` and can perform deploys/rollbacks/merges as that user.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
