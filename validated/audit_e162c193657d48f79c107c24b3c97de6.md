`ERC20Transactor` credits/debits XCM holding with the requested `amount` instead of the ERC20 contract's actual balance delta, breaking on fee-on-transfer/rebasing ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` is the XCM `TransactAsset` implementation that lets Asset Hub (and any `pallet-revive`-enabled chain) route XCM instructions (`WithdrawAsset`, `DepositAsset`, etc.) through arbitrary ERC20 smart contracts identified by an `AccountKey20` location. This is a direct structural analog of the Teller `CollateralEscrowV1`/`CollateralManager` bug class: the transactor calls the ERC20 `transfer()` ABI function and, on a `true` return value, unconditionally treats the *requested* `amount` as the actual amount moved — it never reads the token's `balanceOf` before/after the call to determine the real amount transferred.

### Finding Description
`withdraw_asset_with_surplus` (used for XCM `WithdrawAsset`) builds `IERC20::transferCall { to: checking_address, value: amount }` and calls it via `pallet_revive::Pallet::<T>::bare_call`. If the call succeeds and decodes to `true`, it returns: [1](#0-0) 
i.e. it constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the XCM holding register with the *originally requested* `amount`, not the actual number of tokens the ERC20 contract moved out of the user's balance.

`deposit_asset_with_surplus` (used for XCM `DepositAsset`) mirrors this on the other side: it transfers from the `TransfersCheckingAccount` to the beneficiary and, on `true`, simply returns `Ok(surplus)`: [2](#0-1) 
Again, success of the `transfer()` call is taken as proof that exactly `amount` tokens landed in the beneficiary's balance — no `balanceOf` check.

Any ERC20 contract deployed on `pallet-revive` (which is explicitly permitted — `AllowEVMBytecode = ConstBool<true>` and arbitrary user-deployed contracts are supported, e.g. tests instantiate custom `MyToken` contracts) that implements a fee-on-transfer, rebasing, or otherwise non-1:1 `transfer()` (deducting a fee/burn on every transfer while still returning `true`) will cause the XCM holding register's internal accounting of "ERC20 units held" to diverge from the real on-chain ERC20 balance moved. This is architecturally identical to the reported Teller bug: the caller trusts the parameter `amount` instead of measuring `balanceOf` delta across the external call.

The runtime wiring is real and reachable by an ordinary signed user with no privileged role:
- `AssetTransactors` in the Asset Hub Westend runtime includes `ERC20Transactor` alongside the fungible/fungibles transactors: [3](#0-2) 
- Any signed account can deploy an arbitrary ERC20 contract via `pallet_revive::instantiate`/`bare_instantiate` (`InstantiateOrigin = EnsureSigned<Self::AccountId>`), and then reference it by `AccountKey20` in a self-executed `pallet_xcm::execute` call, exactly as the existing test harness does: [4](#0-3) 

### Impact Explanation
Because `deposit_asset_with_surplus`/`withdraw_asset_with_surplus` never verify the ERC20's `balanceOf` delta, an attacker can deploy an ERC20 whose `transfer()` returns `true` but moves a different amount than requested (fee-on-transfer, or, more severely, a token that "transfers" 0 or an inflated amount while returning `true`). This can be exploited to:
- Desynchronize the XCM holding register accounting from the true ERC20 balance, allowing an attacker to make the XCM executor believe it holds more (or less) of the ERC20 than it truly controls in the checking account, enabling incorrect `DepositAsset`/`RefundSurplus` behavior and potential draining of the `ERC20TransfersCheckingAccount`'s real token balance versus what the executor thinks remains.
- Because the checking account is shared across all users of that ERC20 (`ERC20TransfersCheckingAccount::get()`), a discrepancy introduced by one malicious token/contract only affects XCM programs interacting with that specific malicious contract's holding entries, but the underlying accounting-invariant violation ("assume `amount` transferred == amount requested") is the same missing check as the reported report.

This is a Medium-severity issue (matching the original report's Medium severity): it does not directly let an attacker steal other users' unrelated assets, but it breaks the internal accounting invariant for any ERC20 with non-standard fee-like transfer semantics, which the code explicitly supports by allowing arbitrary user-deployed contracts as the pluggable "asset" backend for XCM.

### Likelihood Explanation
Likelihood is significant because:
- Contract deployment and XCM execution are fully permissionless (`EnsureSigned` origins), so any user can deploy a custom ERC20 and reference it via `AccountKey20` in `pallet_xcm::execute`.
- The pattern is proven reachable: existing test suite (`withdraw_and_deposit_erc20s`, `smart_contract_does_not_return_bool_fails`, `expensive_erc20_runs_out_of_gas`) demonstrates the exact call path exercised end-to-end with custom Solidity contracts compiled to PolkaVM/EVM bytecode and driven through `pallet_xcm::execute`.
- The only defenses currently coded are checking `did_revert()` and decoding the boolean return value — neither of which catches a fee-on-transfer token, since such tokens legitimately return `true` while moving less (or more) than `amount`.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the relevant account's `balanceOf` (via a `balanceOf` `bare_call`, or via `pallet_revive`'s `fungibles::Inspect::balance`) immediately before and after the `transferCall`, and use the observed delta as the amount credited/debited in `AssetsInHolding` / returned as consequence, instead of trusting the requested `amount` parameter — mirroring the standard "measure `balanceOf` delta" fix pattern used to defend against fee-on-transfer tokens.
