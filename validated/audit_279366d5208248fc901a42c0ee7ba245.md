### Title
Cross-stack forged status injection via sha-only lookup in `StatusHandler` bypasses `MergeRequest` CI gating and triggers unauthorized merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits by `sha` alone, with no scoping to the repository/organization that signed the incoming webhook. An attacker who legitimately owns any Shipit-connected repository (and therefore controls a valid webhook signature for *their own* organization) can send a `status` webhook whose `sha` matches a victim stack's `MergeRequest#head` commit (a shared/forked upstream commit) and whose `context` matches `deploy_spec.merge_request_required_statuses`, causing a `Status` row to be attached to the victim's `Commit`. This satisfies `MergeRequest::StatusChecker#success?`, defeats `reject_unless_mergeable!`, and lets `ProcessMergeRequestsJob` call `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` on the victim's real GitHub repo using the victim's credentials.

### Finding Description
The binding the security model relies on is: *the GitHub organization/repository that authenticated the webhook signature == the GitHub organization/repository that owns the `Commit` receiving the resulting `Status`*. This binding is broken.

`WebhooksController#verify_signature` picks the `GithubApp` (and thus the HMAC secret) to validate against based on the payload's own `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

This is correct for authenticating "a request signed by organization X", but the payload's `repository` field is otherwise unused for routing the effect of the event. `Shipit::Webhooks::Handlers::StatusHandler#process` then looks up commits **globally by `sha`**, with no filter on stack, repository, or organization: [3](#0-2) 

`Commit` rows are unique per `(stack_id, sha)` (not globally unique per `sha`), so two different stacks/tenants can each hold a `Commit` row with the identical `sha` (e.g., a widely-forked upstream commit that predates any tenant-specific change). When `commit.create_status_from_github!(params)` runs, the resulting `Status` is scoped to `commit.stack` — i.e., whichever stack that particular `Commit` row happens to belong to — not the stack/org that produced the signed webhook: [4](#0-3) 

So an attacker who owns a legitimate Shipit-registered repository/org (and thus a valid webhook secret for that org, satisfying `verify_signature`) can forge a `status` event with:
- `sha` = the shared upstream commit hash also present in the victim's `MergeRequest#head`,
- `context` = a value in the victim stack's `deploy_spec.merge_request_required_statuses`,
- `state` = `success`,
- `repository.owner.login` = the attacker's own org (so `verify_signature` passes with the attacker's own valid secret).

`StatusHandler` finds every `Commit` with that `sha` — including the victim's — and creates a `success` `Status` on it. `stack.schedule_merges` is then triggered: [5](#0-4) 

`ProcessMergeRequestsJob#perform` re-evaluates pending merge requests: [6](#0-5) 

`MergeRequest#reject_unless_mergeable!` relies on `StatusChecker` built from `head.statuses_and_check_runs` and `stack.cached_deploy_spec`; the forged status satisfies the required context so `any_status_checks_missing?`/`any_status_checks_failed?` both return false: [7](#0-6) 

`merge!` then calls the victim stack's own `github_api.merge_pull_request` (using the victim's GitHub App/token) against the victim's real repository: [8](#0-7) 

None of the existing guards catch this: `verify_signature` correctly authenticates "a request from organization X" but says nothing about which stack's data the request is allowed to mutate; `drop_unhandled_event` only filters by event type; `ExplicitParameters` (`StatusHandler.params`) only validates payload shape, not repository ownership; there is no `Repository`/`stack_id` cross-check between the authenticated org and the `Commit` rows being mutated.

### Impact Explanation
A payload that authenticates only for the attacker's own repository/org is used to write a `Status` record against, and ultimately trigger a merge on, a victim's stack and real GitHub repository, using the victim's `GITHUB_TOKEN`/GitHub App credentials — an unauthorized merge executed with another tenant's credentials. This is repeatable against any victim stack with `merge_queue_enabled: true` whose merge queue has a pending PR whose head sha the attacker can reproduce (trivial for shared upstream commits, e.g., before a tenant applies its own commit on top). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: the attacker needs (a) a Shipit-registered repository/org of their own with a working webhook secret (any onboarded, unprivileged tenant qualifies — this is exactly the population the prompt describes as "unprivileged"), (b) a victim stack with `merge_queue_enabled: true` and a pending `MergeRequest`, and (c) a head commit sha that is shared between the attacker's repo and the victim's (feasible for common upstream/base commits, vendored dependencies, or cherry-picks prior to divergence). No Shipit session, API token, or victim secrets are required — only the attacker's own legitimate webhook signature. This is a low-cost, repeatable attack per matching sha/context pair.

### Recommendation
Scope `StatusHandler#process` (and other webhook handlers that look up commits/PRs by sha or number) to the repository asserted in the webhook payload, not just by `sha`/`number` alone — e.g., resolve the `Stack`/`Repository` from `params.dig('repository', 'full_name')` first (already authenticated via `verify_signature`'s organization check plus a repository-level check), and restrict `Commit.where(sha:)` to that stack/repository's commits before writing statuses.

```ruby
# test/models/webhooks/status_handler_cross_stack_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossStackTest < ActiveSupport::TestCase
    test "a status webhook signed for the attacker's own repo cannot set status on a different stack's commit" do
      shared_sha = 'deadbeef' * 5

      victim_stack = shipit_stacks(:shipit) # repository X, GITHUB_TOKEN belongs to victim
      attacker_stack = Stack.create!(repository: Repository.create!(owner: 'attacker', name: 'repo'))

      victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
        committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared upstream commit")
      attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
        committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared upstream commit")

      merge_request = victim_stack.merge_requests.create!(number: 1, head: victim_commit, merge_status: 'pending')
      victim_stack.cached_deploy_spec.stubs(:merge_request_required_statuses).returns(['ci/attacker-controlled'])

      # Binding under test: identity(attacker's org signature) == write-access-to(victim_stack)? -> should be false
      assert_not_equal attacker_stack.id, victim_stack.id

      forged_params = ActionController::Parameters.new(
        sha: shared_sha, state: 'success', context: 'ci/attacker-controlled'
      ).permit!

      assert_difference -> { victim_commit.statuses.count }, 1 do
        Webhooks::Handlers::StatusHandler.new.call(forged_params.to_unsafe_h)
      end

      Shipit.stubs(:github).returns(stub(merge_pull_request: true))
      victim_stack.github_api.expects(:merge_pull_request).never # this SHOULD hold if fixed; currently it fires
      merge_request.reload
      refute merge_request.reject_unless_mergeable!
      assert merge_request.all_status_checks_passed?
    end
  end
end
```
The test demonstrates: (1) `StatusHandler` writes a `Status` on `victim_commit` from a payload that only authenticates the attacker's own organization, (2) `merge_request.all_status_checks_passed?` becomes true and `reject_unless_mergeable!` returns `false`, proving the CI gate is bypassed and `merge!` (and thus `github_api.merge_pull_request` against the victim's repository) becomes reachable.

```ruby
    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
```
