### Title
Cross-organization Team membership forgery via webhook signature/organization binding confusion in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using an attacker-controlled JSON field (`repository_owner`), and `MembershipHandler#find_or_create_team!` looks up the target `Team` purely by `github_id`, never checking that `params.organization.login` (the org whose secret verified the request) matches the `organization` already stored on that `Team` record. An organization owner who legitimately created and configured their own GitHub App/webhook secret (per the multi-org setup in `docs/setup.md`) can therefore forge a `membership` webhook that is correctly signed for their own org but names an arbitrary pre-existing `Team.github_id` belonging to a different organization, adding themselves (or anyone) as a member of that foreign team.

### Finding Description
The claimed binding is: **organization whose webhook_secret verified the payload (`O_attacker`) == organization that owns the `Team` being mutated (should be `O_victim`)**. This binding is never enforced.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) picks the verifying app via `Shipit.github(organization: repository_owner)`, where `repository_owner` (line 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')` — both values come straight from the unauthenticated request body. [1](#0-0) [2](#0-1) 
- Per `docs/setup.md`'s "Using Multiple Github Applications" section, each organization creates and configures its **own** GitHub App and its **own** `webhook_secret` in `config/secrets.yml`. This means the owner of `O_attacker` legitimately knows the `webhook_secret` used to verify webhooks whose `organization.login`/`repository.owner.login` is `O_attacker`. [3](#0-2) 
- `GitHubApp#verify_webhook_signature` is a pure HMAC-SHA1 check over the raw body using that org's secret — it validates only that the body was signed with `O_attacker`'s secret, it says nothing about the semantic content of the JSON (e.g., which `team.id` is embedded). [4](#0-3) 
- `MembershipHandler#find_or_create_team!` finds/creates a `Team` keyed **only** by `github_id`; the `organization = params.organization.login` assignment is inside the `find_or_create_by!` creation block, so it is applied only when the team doesn't already exist, and is never validated against an existing team's `organization`: [5](#0-4) 
- `MembershipHandler#process` then unconditionally calls `team.add_member(member)` / `team.members.delete(member)` on whatever `Team` was found, regardless of which org's secret verified the request: [6](#0-5) 

**Exploit flow:** Attacker owns `O_attacker`, has a genuine Shipit GitHub App with a webhook secret they configured/know for that org. They already know `O_victim`'s pre-existing team's `github_id` (e.g., from public GitHub team pages, prior legitimate memberships, or the "shopify_developers" example). They compute a valid `sha1=` HMAC over a crafted JSON body: `{"action":"added","organization":{"login":"O_attacker"},"team":{"id":<O_victim_team_github_id>,...},"member":{"login":"attacker-login"}}` and POST it to `/webhooks` with `X-Github-Event: membership`. `verify_signature` resolves `repository_owner` to `"O_attacker"`, fetches `O_attacker`'s app, and the HMAC validates successfully because the attacker legitimately holds that secret. `MembershipHandler#process` then finds the existing victim `Team` by `github_id` and adds the attacker as a member — with no check that `O_attacker == team.organization`.

**Why guards fail:** `verify_signature` only proves "this body was signed by someone who knows `O_attacker`'s secret" — it does not, and structurally cannot, constrain the semantic contents (`team.id`, `member.login`) of that body to `O_attacker`'s real data, because the attacker fully controls the raw bytes they sign. `ExplicitParameters` schema in `MembershipHandler` only enforces types/presence, not cross-organization consistency. No other guard (`drop_unhandled_event`, `force_github_authentication`, model validations) checks `team.organization` against the verifying org.

### Impact Explanation
A successful request grants the attacker (or any GitHub login they name in `member.login`) membership in a `Shipit::Team` record they do not own. If that team's `id` is included in `Shipit.github_teams` (the configured set of teams gating login authorization via `User#authorized?`), this is a direct escalation into Shipit's authorization boundary — an unprivileged attacker can grant themselves login/authorization rights meant to be restricted to `O_victim`'s real team members. [7](#0-6) 
This matches the "High – escalation into `Shipit.github_teams` authorization" impact category. The action is repeatable against any `Team.github_id` known to the attacker and is not limited to a single victim organization/team — any org whose team IDs are discoverable can be targeted, as long as the attacker's own org has a legitimately configured GitHub App in this multi-tenant Shipit deployment.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (per `docs/setup.md`'s multi-org config), (2) attacker owns/administers an org with its own registered GitHub App and knows its `webhook_secret` (which is the normal, expected state for a legitimate tenant, not a leaked secret), (3) a target `Team` record for `O_victim` must already exist in Shipit's DB (created by a prior legitimate `membership` webhook or admin action) with a `github_id` the attacker can learn (team IDs are visible via GitHub's API/UI to org members and sometimes externally). Given these ordinary preconditions, the attack costs a single crafted, self-signed HTTP POST and is trivially repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/validation by both `github_id` and `organization`, and reject/raise if an existing team's `organization` does not match `params.organization.login` (which itself should be cross-checked against the verified `repository_owner`/app organization used in `WebhooksController#verify_signature`, not merely trusted from the body). Consider passing the verified organization from the controller into the handler explicitly rather than re-reading it from the attacker-controlled payload.

### Proof of Concept
```ruby
test ":membership from org A cannot add a member to org B's existing team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  assert_equal 'shopify', victim_team.organization

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },       # verifying org != victim_team.organization
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  # Simulate that 'attacker-org' has its own valid, attacker-known webhook secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  assert_difference -> { victim_team.memberships.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  # Binding check: verifying org ('attacker-org') != team.organization ('shopify')
  refute_equal 'attacker-org', victim_team.reload.organization
  assert victim_team.members.exists?(login: 'attacker-login')
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
