### Title
Webhook signature verification is keyed to `repository.owner.login`/`organization.login` while every event handler acts on `repository.full_name` — allowing signature confusion in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the `X-Hub-Signature` against using the organization name pulled from the payload (`repository.owner.login`, or `organization.login` as fallback), but every downstream `Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack`/`Team` from a completely different field of the same payload (`repository.full_name`, or `organization.login` for membership events). These two payload fields are never cross-checked against each other.

### Finding Description
`WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-38) computes: [1](#0-0) 

```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

with `repository_owner` derived from: [2](#0-1) 

Critically, `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is explicitly documented/scaffolded as optional (`config/secrets.development.shopify.yml:9,18`, `docs/setup.md:30` "Webhook secret (optional)"), so multi-organization Shipit installations very plausibly have at least one configured org with a blank secret.

Meanwhile, every handler that actually mutates state resolves its target using an entirely different payload field — `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

and the `MembershipHandler`, which grants/revokes `Team` membership (directly feeding `User#authorized?` and thus `Shipit.github_teams` access control), keys off `organization.login` for team creation but processes an attacker-suppliable `member.login`: [5](#0-4) 

Because signature verification is scoped to whichever organization the attacker names in `repository.owner.login`/`organization.login`, and that organization's secret can be unset (`verify_webhook_signature` returns `true` for a blank secret), an attacker can craft a payload where the "authenticating" organization field points at an org configured without a secret while the "acted upon" field (`repository.full_name`, or the `membership` event's `team`/`member`) targets a different, sensitive organization/repository/team. The controller never checks that the two fields agree.

### Impact Explanation
This breaks the intended binding "organization that authenticated == organization/repository being written." Concretely:
- If any configured GitHub org lacks a `webhook_secret` (a documented, supported configuration), an unauthenticated attacker can forge `push`/`status`/`check_suite` events causing `GithubSyncJob`, status updates, or check-run refreshes for stacks belonging to a *different*, properly-secured organization/repository — because `Handler#repository_name` only reads `repository.full_name`, never the value that was checked in `verify_signature`.
- More seriously, a forged `membership` event lets an attacker call `MembershipHandler#process` to add an arbitrary GitHub login to any `Team`, since `Team#organization`/`params.team.id` and `params.member.login` are not constrained to match `repository_owner`. Because `User#authorized?` (app/models/shipit/user.rb:80-82) checks team membership against `Shipit.github_teams`, this is a path to authorization escalation into `Shipit.github_teams` for an account the attacker controls, satisfying the report's High-impact bar ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Exploitability depends entirely on the operator's configuration: it requires at least one organization entry in `Shipit.github`'s config to have a blank `webhook_secret` while other organizations/teams are in scope. This is not a hypothetical misconfiguration — the shipped example configs (`config/secrets.development.shopify.yml`, `template.rb`) leave `webhook_secret` blank by default, and the docs mark it "optional." Any install that follows the documented multi-org setup without setting every org's `webhook_secret` is exposed. I could not fully verify from the index whether real-world/default single-org deployments (the common case) are also affected, since single-org configs collapse `repository_owner` and the only configured org into the same value — the divergence only manifests when multiple orgs (or an org+unrelated repo) are configured within a single Shipit instance and at least one lacks a secret.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank in multi-organization configurations; either require every configured org to set a secret, or fail closed instead of returning `true`.
- Cross-validate that the organization used to select the verifying secret (`repository_owner`) matches the organization actually referenced by `repository.full_name` (and, for `membership` events, `organization.login`) before dispatching to handlers.
- Consider verifying the signature using a secret bound to the specific repository actually targeted, not one derived from an attacker-controlled field.

### Proof of Concept
1. Operator configures Shipit with two GitHub orgs, e.g. `OrgA` (no `webhook_secret` set, per the documented optional/blank default) and `OrgB` (properly configured with a `webhook_secret` and a `Shipit.github_teams` entry used for authorization).
2. Attacker POSTs directly to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, and a body:
```json
{
  "action": "added",
  "team": { "id": <OrgB team id>, "name": "OrgB Team", "slug": "orgb-team", "url": "https://example.com" },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header.
4. `MembershipHandler#process` runs unauthenticated, looks up/creates `Team` by `params.team.id` (OrgB's team) and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker membership in a team backing `Shipit.github_teams` for OrgB — bypassing `User#authorized?` for OrgB's Shipit instance without ever presenting a valid signature for OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
