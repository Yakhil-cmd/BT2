### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping, allowing any CCMenu token to read any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` defines a `stacks` scope that restricts lookups to `current_api_client.stack_id` when the client is stack-scoped, and a `stack` helper that uses this scope. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` model, completely bypassing the per-client stack restriction, so any valid `read:stack` CCMenu token can be replayed against arbitrary `stack_id` values to read any stack's latest deploy/rollback status.

### Finding Description
The binding that should hold is: `stack_touched_by_request == current_api_client.stack_id` (when the client is scoped to a single stack). In `Api::BaseController`: [1](#0-0) 

`stacks` restricts the queryable set to the client's own stack, and the default `stack` method uses that scope. However, `Api::CCMenuController` (used by `Api::CCMenuController#show`) redefines `stack` to bypass this scope entirely: [2](#0-1) 

`ApiClient#check_permissions!` (invoked via `require_permission :read, :stack`) only checks that the token has the `read:stack` string permission in its `permissions` array — it never checks `stack_id` against the requested `stack_id`: [3](#0-2) 

So `current_api_client.stack_id` (the stack the CCMenu token was minted for, via `CCMenuUrlController#client`, which creates an `ApiClient` scoped `belongs_to :stack`) is never compared against the `stack_id` param actually being loaded. This is a direct violation of the intended equality — the `stacks` scoping method exists precisely to enforce it for other controllers, but `CCMenuController` opts out of it.

Exploit flow: the attacker obtains their own legitimate `read:stack` token for stack A via `CCMenuUrlController#fetch` (a request they are entitled to make for their own stack). They then send `GET /api/stacks/:any_other_stack_id/ccmenu.xml?token=<their_token>` for stack B, C, D... (any `stack_id`/`owner/repo/env` accepted by `Stack.from_param!`). `authenticate_api_client` in `CCMenuController` only validates the token signature, not stack ownership, so the request succeeds and returns stack B's `deploys_and_rollbacks` data.

This is corroborated by the engine's own test suite: `"stacks with no deploys render correctly"` authenticates as `@client` (scoped/created for `@stack = shipit_stacks(:shipit)`) but then requests `stack_id: stack.to_param` for a brand-new, unrelated `Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), ...)` and asserts a `200` with real payload data — demonstrating that the token is not actually confined to the stack it was minted for: [4](#0-3) 

No other guard intervenes: `require_permission!` only checks the string permission, `Stack.from_param!` performs no ownership check, and `identify_user`/session logic is irrelevant to this API-token path.

### Impact Explanation
Any holder of a single `read:stack` CCMenu token (obtainable legitimately for one stack they have access to) can enumerate `Stack.all` and retrieve each stack's latest deploy/rollback status (build status, last build label/time, activity, web URL) for every stack in the instance, including private/internal repositories the attacker has no access to. This matches the "unauthenticated read of stack state" High-severity category, and because it is trivially repeatable across the entire `Stack` table with one token, the blast radius spans all tenants/stacks hosted by the Shipit instance.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to legitimately obtain one CCMenu token for any stack they can access (a normal, intended workflow via `CCMenuUrlController#fetch`). No secrets, no privileged role, and no GitHub access are required beyond that. The attack is a simple parameter substitution (`stack_id`) on an authenticated-but-unscoped endpoint, fully repeatable and scriptable.

### Recommendation
Change `Api::CCMenuController#stack` to use the same scoped lookup as the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely so it inherits `Api::BaseController#stack`/`#stacks`, ensuring `current_api_client.stack_id` (when present) restricts the queryable stacks.

### Proof of Concept
minitest (add to `test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped token cannot read another stack's ccmenu status" do
  scoped_client = ApiClient.create!(
    creator: @user, name: 'CCMenu Client', stack: @stack, permissions: %w[read:stack]
  )
  other_stack = shipit_stacks(:cyclimse) # a different fixture stack
  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }
  assert_response :forbidden # currently fails: returns 200 with other_stack's real deploy data
end
```
Assert on both sides: `scoped_client.stack_id == @stack.id` while the actually-returned `stack.id` in the rendered payload equals `other_stack.id` — proving the divergence from the intended binding `current_api_client.stack_id == requested_stack.id`.
