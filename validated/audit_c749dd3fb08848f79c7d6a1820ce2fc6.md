This confirms the mechanism. `Shipit.github(organization:)` at `lib/shipit.rb:170-181` looks up the per-organization config via `github_app_config`, and if that organization's config has no `webhook_secret`, the `GitHubApp` instance built for it will have `@webhook_secret = nil` (`lib/shipit/github_app.rb:44-51`). Then `verify_webhook_signature` unconditionally returns `true` when `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).

The controller selects which organization's app/secret to use for verification based on an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), while the handlers that actually mutate state key off a *different* field, `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`, and reused in `push_handler.rb`, `pull_request/*_handler.rb`). This is exactly the "organization that authenticated versus the repository that is written" binding named in the rules.### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is decoupled from the repository the handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using an org name read straight out of the *unauthenticated* JSON body, while the handlers that mutate stack state key off a *different* field of the same body. If any configured organization in a multi-org Shipit deployment has no `webhook_secret` set (a state the shipped config templates explicitly show as normal/default), signature verification for that organization is unconditionally skipped, and the resulting payload is then dispatched using `repository.full_name`, which can point at any other organization's repository/stack.

### Finding Description
`verify_signature` computes the organization used for verification purely from body content: [1](#0-0) [2](#0-1) 

```ruby

  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-org config and builds a `GitHubApp` keyed on that org name: [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that org's `webhook_secret` is blank: [4](#0-3)

  return true unless webhook_secret

Multiple config templates in this repo ship organizations with `webhook_secret: # nil` as a normal example value, i.e., an organization entry with no secret configured is not a fringe misconfiguration: [5](#0-4) [6](#0-5) 

After (bogus) verification succeeds, `create` dispatches the raw payload to handlers: [7](#0-6) 

Every handler resolves the repository/stack to act on from a *different* field, `repository.full_name`, not `repository.owner.login`/`organization.login`: [8](#0-7) [9](#0-8) 

The binding that should hold is:
`organization used to select/verify the webhook signature == organization that owns the repository the handler subsequently writes to`

An attacker can break this equality: craft a JSON body where `repository.owner.login` (or `organization.login`) names an org configured in Shipit with no `webhook_secret`, while `repository.full_name` names a *different*, fully-configured org/repo that has an active stack in this Shipit instance. `verify_signature` picks the no-secret org, signature check trivially passes regardless of the (attacker-supplied or absent) `X-Hub-Signature` header, and the handler then acts on the victim org's repository/stack using attacker-controlled body content (e.g., `PushHandler` triggers `GithubSyncJob` with an attacker-chosen `after` SHA against the real stack; `pull_request` handlers can archive/unarchive/provision review stacks; `StatusHandler` can inject forged commit statuses that gate continuous delivery).

### Impact Explanation
This crosses the "unauthorized deploy/rollback... or an organization that authenticated versus the repository that is written" trust boundary called out for this exercise: an unprivileged, unauthenticated network attacker (no `ApiClient` token, no `webhook_secret`, no GitHub App key) can forge state-changing GitHub events against a *different* organization's stacks than the one whose (absent) secret was used for "verification." Depending on the handler this can trigger unwanted syncs/deploy pipelines (`push` → `GithubSyncJob` → eventually `CacheDeploySpecJob`), forge CI status used by continuous delivery gating (`StatusHandler`), or archive/create/unarchive review stacks (`PullRequest::*Handler`). This satisfies the High-severity criterion "unauthorized deploy... " via forged CI/push signals feeding continuous delivery, and can escalate toward Critical if continuous delivery is enabled on the victim stack, since a forged `push`/`status` payload can drive an actual unauthorized deploy.

### Likelihood Explanation
Likelihood is contingent on operator configuration: it requires a multi-org Shipit deployment where at least one configured organization has a blank `webhook_secret`. This is not a hypothetical edge case — the engine's own shipped config templates (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) present `webhook_secret: # nil` as the documented default/example value for an org entry, and `docs/setup.md` describes multi-org config without mandating a secret per org. No credentials, tokens, or GitHub access of any kind are required from the attacker; only network reachability to `/github/webhooks` (or equivalent mounted path) and knowledge of any org name configured without a secret (which can be enumerated via the `422`/error responses of `verify_signature`, since `GithubOrganizationUnknown` vs. accepted-but-unverified organizations behave differently).

### Recommendation
- Fail closed: if a configured GitHub organization has no `webhook_secret`, reject/queue-for-review incoming webhooks for that organization instead of treating `verify_webhook_signature` as vacuously `true`.
- Bind verification and dispatch to the *same* identity: derive the organization used for secret lookup from the same field the handlers use to resolve the repository (`repository.full_name`'s owner segment), or explicitly cross-check `repository.owner.login`/`organization.login` against `repository.full_name`'s owner and reject on mismatch before dispatch.
- Require `webhook_secret` to be present for every organization entry at boot/config-validation time, refusing to start (or logging a hard warning) when any org's secret is missing in production.

### Proof of Concept
1. Deploy Shipit in multi-org mode with two organizations configured:
   - `OrgNoSecret` — `webhook_secret` left blank/nil.
   - `OrgVictim` — fully configured with a real webhook secret, GitHub App, and an active tracked stack, e.g. `OrgVictim/app`.
2. As an unauthenticated attacker, POST to the webhooks endpoint:
   - Header: `X-Github-Event: push`
   - Body:
     ```json
     {
       "ref": "refs/heads/main",
       "after": "<attacker-chosen-sha>",
       "repository": {
         "owner": { "login": "OrgNoSecret" },
         "full_name": "OrgVictim/app"
       }
     }
     ```
   - No valid `X-Hub-Signature` header is needed.
3. `repository_owner` resolves to `"OrgNoSecret"`, `Shipit.github(organization: "OrgNoSecret")` returns a `GitHubApp` with `webhook_secret == nil`, so `verify_webhook_signature` returns `true` unconditionally regardless of the signature header.
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name == "OrgVictim/app"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` against the real `OrgVictim` stack — a forged, unauthenticated event acted on the victim organization's stack, breaking the intended authentication↔repository binding.
