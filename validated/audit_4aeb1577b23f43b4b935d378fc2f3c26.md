### Title
`Api::CCMenuController` reads any stack's build status regardless of the `ApiClient`'s `stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` bypasses the stack-scoping mechanism that every other `Api::BaseController` subclass relies on, looking up `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])`. As a result, an `ApiClient` token that was intentionally restricted to a single stack (via `ApiClient#stack_id`) can be used to read CI/build status information for *any* stack in the installation, not just the one it was scoped to.

### Finding Description
`Api::BaseController` defines the scoping primitive that all other API controllers are expected to use to resolve a stack from a request: [1](#0-0) 
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This encodes the binding: *the set of stacks a token authorizes* (`current_api_client.stack_id`) must equal *the set of stacks any request from that token can touch*.

`Api::CCMenuController`, however, overrides `#stack` and resolves the stack directly against the global `Stack` relation, ignoring the token's `stack_id` scope entirely: [2](#0-1) 
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
The controller only guards the action with a generic permission check (`require_permission :read, :stack`), which merely verifies that `"read:stack"` is present in the token's `permissions` array via `ApiClient#check_permissions!`: [3](#0-2) 
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```
This check has no knowledge of *which* stack is being requested — it never consults `current_api_client.stack_id`. So any token carrying the `read:stack` permission, even one explicitly created scoped to Stack A (e.g. via `CCMenuUrlController`, which mints a token with `stack_id`-less permissions but is meant to be used against one specific stack's CCMenu URL: [4](#0-3) ), can be replayed with a different `params[:stack_id]` to read another stack's build state, provided that other token was also stack-scoped and possesses `read:stack`.

The equality that breaks is: *stack a token authorizes* (`current_api_client.stack_id`) ≠ *stack the request actually touches* (`params[:stack_id]` passed straight to `Stack.from_param!`).

Comparing with the sibling API controller `Api::StacksController`, which correctly uses the scoped helper — this confirms `CCMenuController` is the outlier: [5](#0-4) 

### Impact Explanation
This is a scope-escalation of a stack-restricted `ApiClient` token. A token that is supposed to be usable only against one stack's build status can be used to enumerate/read `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, and `activity` for arbitrary other stacks (including ones the token's creator/holder may not otherwise have visibility into), by simply supplying a different `stack_id` param on the CCMenu XML endpoint. This is an unauthorized cross-stack read of stack state, matching the "unauthenticated/unauthorized read of stack state" High-severity impact category.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token with `read:stack` permission (the normal, expected credential type created e.g. by `CCMenuUrlController#client` for exposing a single stack's CI badge) can trivially exploit this by changing the `stack_id` URL parameter — no additional secret, session, or elevated privilege is required beyond the token they were already issued. This mirrors the root cause of the referenced report: a check (`check_permissions!`) is performed against the wrong granularity (the generic "operation:scope" string) while the actual object acted upon (`Stack.from_param!(params[:stack_id])`) is resolved without re-validating against the token's specific authorization scope (`stack_id`).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController`, exactly as other API controllers do:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the binding so that a stack-scoped token can only resolve the stack it was issued for.

### Proof of Concept
1. Create (or observe the creation of, via `CCMenuUrlController`) an `ApiClient` scoped to Stack A: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, stack: stack_a, name: 'CCMenu Client')`, and obtain its `authentication_token`.
2. Send `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<stack_a_token>` (or via Basic Auth as in `ApiHelper#authenticate!`), substituting Stack B's identifier for `stack_id`.
3. Observe that `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (token has `read:stack`), and `stack` resolves to Stack B via `Stack.from_param!(params[:stack_id])` — returning Stack B's build status even though the token was only meant to authorize Stack A.

**Note on confidence:** I could not fully verify at what other call sites `Api::CCMenuController` tokens are exclusively created/distributed (e.g., whether operators always mint per-stack tokens for this endpoint in practice, versus reusing broader tokens), since that depends on deployment-specific token provisioning outside the indexed code. The core code-level scope-bypass in `stack` versus `stacks` is confirmed directly by inspecting `app/controllers/shipit/api/base_controller.rb` and `app/controllers/shipit/api/ccmenu_controller.rb`.
