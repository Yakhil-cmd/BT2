This confirms the pattern: `Api::StacksController#stack` uses the scoped `stacks.from_param!(params[:id])` (`app/controllers/shipit/api/stacks_controller.rb:87-89`), and `Api::TasksController` likewise relies on `BaseController#stack` which calls `stacks.from_param!` (`app/controllers/shipit/api/base_controller.rb:74-80`), where `stacks` filters by `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController#stack`, however, bypasses this entirely by calling `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), so a token created with `stack_id` set to Stack A still succeeds for any `stack_id` supplied in the URL.

### Title
Stack-scoped API tokens bypass their stack restriction in `CCMenuController`, allowing cross-stack deploy-status disclosure - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be scoped to a single stack via the `stack_id` column, and every other API endpoint (`Api::BaseController#stacks`/`#stack`, used by `Api::StacksController`, `Api::TasksController`, etc.) enforces this scope by filtering `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]`. `Api::CCMenuController` instead defines its own `stack` method that resolves `params[:stack_id]` against the full, unscoped `Stack` relation, so a token that is only supposed to authorize `read:stack` on one stack can be used to read the CCMenu/CI status of any stack in the installation.

### Finding Description
The security invariant elsewhere in the API is: `current_api_client.stack_id (if set) == stack.id (resolved from params)`. This is implemented once, centrally, in `Api::BaseController`: [1](#0-0) 
Every controller that inherits `stack`/`stacks` from `BaseController` (e.g. `Api::StacksController#stack`, `Api::TasksController#task`) is therefore bound to the client's `stack_id` scope: [2](#0-1) 

`Api::CCMenuController` overrides `stack` and resolves it against the global `Stack` collection instead of the scoped `stacks` collection: [3](#0-2) 

`require_permission :read, :stack` only checks the client's `permissions` array via `ApiClient#check_permissions!`, not which stack it is scoped to: [4](#0-3) 

So the equality that is supposed to hold — "the stack a token is authorized for" == "the stack the token's request actually touches" — is broken specifically in this one controller: a `read:stack`-permissioned client scoped to `stack_id = A` (`current_api_client.stack_id? == true`, restricting it to Stack A everywhere else) can call `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id = B` and successfully retrieve Stack B's CI/deploy status, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This is an authorization-scope escalation: a token that an operator intentionally restricted to one stack (e.g., to embed in a public CI badge for that project only) can be used to read the last build/deploy status, activity, and label of every other stack in the Shipit instance, including private or unrelated stacks the token holder was never meant to see. This matches the "escalation into … unauthenticated/unauthorized read of stack state" class of impact, since it defeats the per-stack authorization boundary that the rest of the API enforces.

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-permissioned API token can exploit this with a single unauthenticated (from the app's perspective, just token-authenticated) GET request by substituting a different `stack_id` in the URL — no special privilege beyond holding one legitimately-scoped token is required, and no additional secrets need to be guessed since stack identifiers are visible/enumerable slugs (`owner/repo/environment`).

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` collection instead of the raw `Stack` model, e.g. `stacks.from_param!(params[:stack_id])`, so a stack-scoped client is confined to its authorized stack just like every other API endpoint.

### Proof of Concept
1. Create (or use console/fixture as in `here_come_the_walrus`) an `ApiClient` with `permissions: ['read:stack']` and `stack: StackA`.
2. `GET /api/stacks/:stack_id_of_A/ccmenu.xml` with `Authorization: Basic base64(token)` — succeeds, returns Stack A's status (expected).
3. `GET /api/stacks/:stack_id_of_B/ccmenu.xml` with the same token — also succeeds and returns Stack B's status, even though `current_api_client.stack_id == StackA.id`, because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`.
