### Title
Attacker-controlled swap route can inject unauthorized token transfers into `swap_collateral` authorization - ([File: contracts/controller/src/strategies/swap_collateral.rs](contracts/controller/src/strategies/swap_collateral.rs))

### Summary
`swap_collateral` accepts an opaque caller-supplied `swap` payload and forwards it to the configured router without constraining which contracts the route may invoke. [1](#0-0)  A malicious route can place attacker-controlled code beneath the caller’s `swap_collateral` authorization and request an unrelated token transfer from the caller. [2](#0-1)  If the caller signs the simulated authorization tree, the injected transfer succeeds and can drain unrelated wallet tokens. [3](#0-2) 

### Finding Description
The public `swap_collateral` entrypoint takes `swap: Bytes` as an uninterpreted route payload. [1](#0-0)  The controller authenticates the caller and verifies account ownership, but those checks do not validate the contracts embedded in the route. [4](#0-3)  The controller then withdraws collateral and passes the raw payload through `withdraw_and_swap_from_supply`. [5](#0-4)  The swap helper invokes `router.execute_strategy(&controller, &amount_in, swap)` while merely guarding reentry and measuring token balances. [6](#0-5)  It verifies only the input spend and positive output receipt; it does not prevent route-selected code from making additional calls carrying the caller’s authorization context. [7](#0-6)  The included authorization-tree test demonstrates that simulation records a malicious pool’s `token.transfer(caller, attacker, amount)` as a child of the caller’s `swap_collateral` authorization. [8](#0-7) 

### Impact Explanation
An attacker can steal unrelated tokens held directly by the victim’s address, beyond the collateral amount intentionally routed through the strategy. [3](#0-2)  The injected transfer is not bounded by `amount`, the swap output, collateral risk checks, or the router’s measured input/output accounting. [7](#0-6)  This is theft of user funds because the route can select any token contract, victim address, recipient, and amount representable by the injected contract call. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious venue contract and encode a route that causes the router to invoke it during a victim’s swap. [10](#0-9)  The exploit requires the victim to submit or sign a transaction containing the malicious route and its resulting poisoned authorization tree, so wallet or client-side authorization inspection can prevent it. [11](#0-10)  However, ordinary transaction simulation mechanically includes the malicious child invocation in the authorization tree, making the signed result valid rather than rejected by the protocol. [12](#0-11) 

### Recommendation
Do not allow arbitrary opaque routes to execute under the caller’s strategy authorization. The router or controller-facing strategy format should constrain route venues to audited, allowlisted contracts and reject callback hops that can invoke arbitrary addresses; alternatively, execute swaps from an authorization boundary that cannot reuse the caller’s authorization tree. Clients should additionally reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` authorization containing child invocations other than the exact expected input-token transfer.

### Proof of Concept
The repository includes a runnable reproduction in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. Its router fixture invokes a route-selected `hop_pool`, and the malicious pool calls `token.transfer(victim, attacker, amount)`. [10](#0-9) [9](#0-8)  Simulation records the theft as a child of Alice’s `swap_collateral` authorization, and the enforced-auth test shows the transfer succeeds when that poisoned tree is signed. [13](#0-12) [3](#0-2)  The attacker can invoke this path through `Controller::swap_collateral(caller, account_id, current, amount, new, malicious_swap)`. [14](#0-13)

    };
