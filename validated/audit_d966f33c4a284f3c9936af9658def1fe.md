### Title
Session Fixation in GitHub OAuth Callback Allows Authenticated Session Hijack - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
The external report's root issue is a broken binding between an intended, verified state and the state an unprivileged actor can actually manipulate (share balance vs. transferable balance). The reachable analog in shipit-engine is the binding between "the GitHub identity that OmniAuth verifies" and "the session container that identity gets written into." `GithubAuthenticationController#callback` writes the freshly-authenticated user id into the *existing* session instead of rotating the session identifier first, so an attacker-established session survives login and becomes a fully authenticated session for the victim.

### Finding Description
`GithubAuthenticationController#callback` performs the entire GitHub OAuth handshake and then does: [1](#0-0) 

Note that `session[:user_id] = sign_in_github(auth)` is called directly, with no `reset_session` (or `session.regenerate_id`) beforehand. Compare this with `logout`, a few lines below, which does call `reset_session`: [2](#0-1) 

`sign_in_github` itself only resolves/creates the `User` record and stores the OAuth token — it never touches the session identifier: [3](#0-2) 

Downstream, `Shipit::Authentication#current_user` simply trusts whatever `session[:user_id]` holds: [4](#0-3) 

The equality the engine is supposed to guarantee is: `{GitHub identity verified by OmniAuth}` == `{User bound to the session id in the victim's browser}`. Because the session id (the Rails session cookie) is not rotated at the authentication boundary, an attacker who can plant a session id in the victim's browser before the victim completes GitHub OAuth (classic session-fixation precondition — e.g., cookie tossing from a sibling subdomain, or a URL that sets a session cookie via a redirect chain the app doesn't control) retains a session that becomes authenticated as soon as the victim logs in with GitHub. The identity check (GitHub) is sound; the session-binding step is not, so the two sides of the equality diverge.

### Impact Explanation
This maps to the High severity category explicitly listed as in-scope: "session fixation / forced OAuth completion." Once the attacker's pre-planted session id becomes authenticated as the victim, the attacker inherits the victim's full `Shipit::User` privileges in-app: triggering deploys/rollbacks on stacks the victim can access, viewing task output/streams, and any other action gated by `current_user`. This does not require any GitHub App private key, `webhook_secret`, `api_clients_secret`, or repository write access — it only requires the standard session-fixation precondition (planting a session cookie), which is a credential/authentication boundary crossing, not social engineering of the target's account credentials.

### Likelihood Explanation
Medium. Exploitation requires the attacker to get a session cookie accepted by the victim's browser scoped to the Shipit host before the victim completes the OAuth callback — a well-understood technique (e.g., cookie tossing from a subdomain sharing the parent domain, or an open redirect elsewhere on the same domain that sets a session cookie). No credentials, tokens, or GitHub App secrets are needed. The vulnerable code path (`callback` action, `app/controllers/shipit/github_authentication_controller.rb:7-21`) is always reachable since GitHub authentication is mandatory for the mounted engine (`force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb:8`).

### Recommendation
Call `reset_session` (or `session.regenerate_id`) in `GithubAuthenticationController#callback` immediately after `auth` is validated and before assigning `session[:user_id]`, mirroring what `logout` already does. This rotates the session identifier at the authentication boundary so any pre-existing (potentially attacker-controlled) session id is discarded, restoring the intended binding between "GitHub-verified identity" and "session the browser holds."

### Proof of Concept
1. Attacker plants a known session id/cookie in the victim's browser for the Shipit host (e.g., via subdomain cookie tossing or any mechanism that lets an unauthenticated party set a cookie scoped to the app's domain).
2. Victim visits the Shipit instance, is redirected to `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`), completes GitHub OAuth.
3. `GithubAuthenticationController#callback` runs `session[:user_id] = sign_in_github(auth)` on the *existing* (attacker-known) session — no `reset_session` occurs (`app/controllers/shipit/github_authentication_controller.rb:7-21`).
4. Attacker replays the same session id/cookie and is now recognized as the victim by `current_user` (`app/controllers/concerns/shipit/authentication.rb:36-42`), gaining the victim's deploy/rollback/API privileges within the engine.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
