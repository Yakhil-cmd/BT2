### Title
Permissionless asset "Freezer" can permanently DoS a `pallet-asset-conversion` liquidity pool and lock all LPs' funds - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion`'s `create_pool`/`add_liquidity` accept any `T::AssetKind` that satisfies the generic `Assets` trait, including ordinary `pallet-assets` assets that anyone can create permissionlessly. `pallet-assets` grants the asset creator (default "team") the `Freezer` role, which can call `freeze(origin, id, who)` on *any* account holding that asset — including the asset-conversion pool's PDA-like `pool_account`. Once the pool account is frozen for that asset, every operation that needs to move that specific asset **out of** the pool account (`remove_liquidity`, and any `swap_*` that outputs that asset) fails with `Error::Frozen`, while deposits (`add_liquidity`, swaps that add that asset into the pool) keep succeeding. This mirrors the SPL freeze-authority collateral bug: an attacker-controlled token with a live freeze authority is accepted as pool/collateral backing without any check, letting the attacker DoS withdrawals for any innocent liquidity provider who trusted the pool.

### Finding Description
- `pallet_assets::create` is a **permissionless** extrinsic (documented under "Permissionless Functions"): any signed account can create a new asset class by paying a deposit, and per `set_team`/default team assignment the creator becomes Owner/Issuer/Admin/**Freezer** of that asset. [1](#0-0) 
- The `Freezer` role can call `freeze(origin, id, who)` to set `AccountStatus::Frozen` on **any** account holding balance of that asset, with only `ensure!(origin == d.freezer, ...)` as the check — no restriction on `who` (e.g. no exemption for PDAs like liquidity-pool accounts): [2](#0-1) 
- Freezing an account blocks **transfers from** that account while still allowing transfers **into** it, confirmed by the existing unit test: [3](#0-2) 
- `pallet-asset-conversion::create_pool` is itself permissionless and accepts arbitrary `T::AssetKind` pairs without any check on the asset's freeze/admin configuration: [4](#0-3) 
- `do_add_liquidity` transfers both assets from the liquidity provider into `pool_account` (deposits succeed even if later the account gets frozen for withdrawal-blocking purposes), and mints LP tokens to the provider: [5](#0-4) 
- `do_remove_liquidity` and swap paths require `T::Assets::transfer(asset, &pool_account, withdraw_to, amount, Expendable)` — i.e., a transfer **from** `pool_account` — which fails with `Error::Frozen` once the asset's Freezer has frozen `pool_account`: [6](#0-5) 

Attack narrative (no privileged role required at any step):
1. Attacker (ordinary signed account) calls `pallet_assets::create` + `mint` to create asset `X`, becoming its Freezer/Admin — fully permissionless.
2. Attacker (or anyone) calls `AssetConversion::create_pool(Native, X)` — permissionless.
3. A victim LP calls `AssetConversion::add_liquidity(Native, X, ...)`, transferring both Native and `X` into `pool_account`, receiving LP tokens.
4. Attacker calls `pallet_assets::freeze(origin=attacker, id=X, who=pool_account)`. This succeeds because attacker is the legitimate Freezer of `X` and `pool_account` is just a normal token holder from `pallet-assets`' point of view.
5. Victim now cannot call `remove_liquidity` or any swap that would send asset `X` out of `pool_account` — every such call returns `Error::Frozen`. The victim's LP tokens (and the locked `X`/Native reserves) are stuck.

### Impact Explanation
Any user who provides liquidity to a pool backed by a non-privileged, permissionlessly-created `pallet-assets` asset can have their funds permanently locked by that asset's Freezer (frequently the pool's own creator/attacker), with no recourse — matching the "Medium: avoidable, rare, but real fund-locking harming innocent users" severity used in the original C4 report. Unlike the SPL case (where freeze authority is inherent to any SPL mint), here it is inherent to `pallet-assets`' asset model, and `pallet-asset-conversion` performs no validation that a candidate `AssetKind` has no such freeze capability (or that the pool account is exempted from freezing) before allowing pool creation/liquidity provisioning.

### Likelihood Explanation
Likelihood is non-trivial: creating an asset and becoming its own Freezer, then creating a pool for it and enticing/attracting liquidity providers (rug-pull style), is a simple, low-cost, fully permissionless sequence of extrinsics with no governance or privileged role needed. It requires the attacker to control the freezer key of the paired asset, which they trivially do since they created the asset themselves.

### Recommendation
- `pallet-asset-conversion::do_create_pool` should reject asset kinds whose freeze/admin authority is not `None`/burned, or require an explicit allow-list/governance approval for which `AssetKind`s can be paired into pools (similar to the recommendation in the referenced report: "ensure the collateral token does not have an active freeze authority... if it does, disable it").
- Alternatively, `pallet-assets` could exempt certain "system" accounts (e.g., an account registered as a `PoolLocator` pool address) from being frozen by ordinary asset Freezers, or provide a `Config`-level callback allowing `pallet-asset-conversion` to fail-fast/never rely on pallet-assets transfer semantics for pool accounts.
- At minimum, document/require that only "trusted" assets (e.g. sufficient/foreign assets under governance control) be paired in `AssetConversion` pools in production runtimes, and add integration tests exercising this frozen-pool-account scenario to prevent silent regressions.

### Proof of Concept
Failed guard identified: `Assets::freeze` only checks `origin == d.freezer` [2](#0-1) , with no exemption for asset-conversion pool accounts, and `do_remove_liquidity`/swap functions perform an unconditional `T::Assets::transfer(..., &pool_account, ..., Expendable)` that will surface `Error::Frozen` [6](#0-5) . The existing repository test suite already demonstrates the underlying "transfer from frozen account fails" behavior in isolation [3](#0-2) , but there is **no existing integration test in `substrate/frame/asset-conversion/src/tests.rs`** that combines asset creation → pool creation → liquidity provisioning → freezing the pool account → attempted `remove_liquidity`/swap, so I was not able to execute a full end-to-end reproduction within this session; a background Devin agent with Rust/cargo test access would be needed to write and run that integration test (`build_and_execute` style, chaining `Assets::create` → `Assets::mint` → `AssetConversion::create_pool` → `AssetConversion::add_liquidity` → `Assets::freeze(freezer, asset_id, pool_account)` → `assert_noop!(AssetConversion::remove_liquidity(...), pallet_assets::Error::Frozen)`) to conclusively confirm the DispatchError surfaces as expected through the `T::Assets` fungibles adapter used by `asset-conversion`.

		pub fn freeze(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Frozen;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Frozen { asset_id: id, who });
			Ok(())
		}

		/// Create a new liquidity pool.
		///
		/// **Warning**: The storage must be rolled back on error.
		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};

			let pool_info = PoolInfo { lp_token: lp_token.clone() };
			Pools::<T>::insert(pool_id.clone(), pool_info);

			Self::deposit_event(Event::PoolCreated {
				creator: creator.clone(),
				pool_id: pool_id.clone(),
				pool_account,
				lp_token,
			});

			if let Some(fee) = initial_fee {
				PoolFees::<T>::insert(&pool_id, fee);
				Self::deposit_event(Event::PoolFeeSet { pool_id: pool_id.clone(), fee });
			}

			Ok(pool_id)
