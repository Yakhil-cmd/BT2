Found a solid analog: the WlsETH bug is about a value used to *drive an operation* (`_value` in ETH) never being validated against the unit the contract actually tracks internally (shares), so the two diverge silently. In shipit-engine, the same class of bug exists in the webhook trust path: the field used to *authenticate* a webhook (`repository.owner.login`, used to pick the GitHub App/`webhook_secret`) is never checked against the field used to *decide what gets written* (`repository.full_name`, used to resolve the target `Repository`/`Stack`). These two fields live in the same attacker-supplied JSON body but are never bound to each other.

### Title
Webhook signature verifies the organization, but event handlers act on an unrelated `repository.full_name` - allowing cross-organization forgery of CI status and push events (WebhooksController#verify_signature)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) using `repository.owner.login` from the JSON body, then HMAC-verifies the *entire* raw body against that secret. Every webhook `Handler`, however, resolves the actual `Repository`/`Stack` to mutate using a completely different field of the same body: `repository.full_name`. Nothing ties these two fields together, so a party who legitimately knows (or configures) the webhook secret for *one* organization onboarded into a multi-org Shipit instance can forge a webhook whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` points at a repository belonging to a *different*, victim organization also configured in the same Shipit instance.

### Finding Description
- `verify_signature` picks the app/secret via `repository_owner`, computed only from `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 
- The signature check only proves "this raw body was HMAC'd with organization X's secret" — it says nothing about which repository the body claims to describe.
- Every handler resolves its target purely from `repository.full_name`, independent of the field used above: [3](#0-2) 
- `PushHandler`, for example, uses that resolution to invoke `stack.sync_github(expected_head_sha: params.after)` on whatever stacks match: [4](#0-3) 
- The `status` event handler (exercised in `test/controllers/webhooks_controller_test.rb`) similarly writes a `Status` record onto a commit found by repository/sha from the same body, independent of the org used to authenticate the request: [5](#0-4) 

Equality that should hold but is never enforced:
`org_that_signed(repository.owner.login) == org_that_owns(repository.full_name)`

Shipit's multi-organization support is explicit — the config format documents multiple orgs, each with its own `webhook_secret`, all mounted on the same `/webhooks` endpoint: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because the two fields are never cross-checked, an attacker who administers (or has been granted) the webhook secret for *any one* organization configured on a shared Shipit instance can forge webhooks that write into any *other* configured organization's repositories/stacks, without any legitimate relationship to that target repository:
- Forging a `push` event lets them trigger `sync_github`/`GithubSyncJob` against a victim stack.
- Forging a `status` event lets them inject a fake CI status (e.g., `success`) for an arbitrary commit sha in the victim repository. Since Shipit's own deploy gating (`Commit#deployable?`, `required_statuses`/`blocking_statuses` in `DeploySpec`) relies on locally stored `Status` rows populated by this same webhook path, this can make a commit that never actually passed CI on GitHub appear deployable in Shipit, enabling an **unauthorized deploy** of that commit — a Critical-severity outcome per the rules (unauthorized deploy).
- Forging `pull_request`/`membership`-class events could similarly manipulate review stacks, team membership records, or merge-status state belonging to the victim org, i.e., cross-repository/cross-organization writes.

This only matters in a genuine multi-tenant Shipit deployment (multiple orgs configured with distinct `webhook_secret`s, as the engine explicitly documents supporting), and requires the attacker to know/control a secret for at least one onboarded organization — not a Shipit session, `ApiClient` token, or the app's own GitHub credentials, so it does not fall under the excluded "requires a privileged Shipit credential" category.

### Likelihood Explanation
`/webhooks` is a public, unauthenticated POST endpoint by design (it must accept requests from GitHub), and the only gate is the HMAC signature check shown above. Any tenant/organization admin who is trusted only with their own org's webhook secret — a routine, low-privilege credential in a multi-org setup — can exploit this without any interaction with the victim organization, victim repository maintainers, or GitHub itself. The bug is a one-line logic gap (missing cross-field validation), not a complex chain, making it straightforward to trigger.

### Recommendation
After signature verification, assert that the organization embedded in `repository.full_name` (or `organization.login` for org-level events) matches the `repository_owner` that was used to select the verifying secret, and reject the webhook (422) if they differ. Equivalently, resolve the `Repository`/`Stack` using the same authenticated organization identity that selected the `webhook_secret`, rather than trusting an independent, unauthenticated field from the payload body.

### Proof of Concept
1. Configure (or compromise the webhook secret of) organization `attacker-org` in a multi-org Shipit instance that also hosts `victim-org`.
2. Craft a JSON body for a `status` (or `push`) event where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`, `sha` = a real, unmerged/unreviewed commit sha in `victim-org/victim-repo`
   - `state = "success"`, `context` = one of `victim-org/victim-repo`'s required statuses
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC (the attacker crafted the whole body and knows the secret) — see [1](#0-0) .
6. The `status` handler locates `victim-org/victim-repo`'s commit via `repository.full_name`/`sha` (independent of `attacker-org`) and creates a fabricated passing `Status`, which `Commit#deployable?`/`DeploySpec#required_statuses` will treat as legitimate CI evidence — enabling an unauthorized deploy of that commit in `victim-org`.

Note: I could not fully inspect `app/models/shipit/webhooks/handlers/membership_handler.rb` and other org-scoped handlers within the available tool budget; those may present additional, possibly more severe instances of the same missing organization/repository binding (e.g., team membership tampering) and warrant a follow-up review with full file access.
