### Title
Webhook signature verification is keyed by `repository.owner.login` while stack mutation is keyed by `repository.full_name`, letting an org without a configured `webhook_secret` be used to forge writes against any other org's repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using `repository.owner.login`, but `Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the target repository using the independent `repository.full_name` field from the same attacker-supplied JSON body. If any organization configured in `Shipit.github(organization:)` has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` (`return true unless webhook_secret`), so an attacker can name that org as `owner.login` while pointing `full_name` at an entirely different, secret-protected org's repository, bypassing that org's HMAC check.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`organization(secret used to verify bytes) == organization(owner of repository whose Stack/Commit/Team is mutated)`

- Left side is computed in `verify_signature`: `repository_owner = params.dig('repository','owner','login')`, then `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [1](#0-0) [2](#0-1) .
- `verify_webhook_signature` short-circuits to `true` with no signature check at all when the resolved org has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) .
- Right side is computed later, deep inside the handler, from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`, used to look up `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) .

Nothing in `create`, `verify_signature`, or `Handler#initialize`/`#process` cross-checks that `full_name`'s owner segment matches `owner.login`. The attacker's HTTP request is a single unauthenticated `POST /webhooks` with `X-Github-Event` set to a handled event (e.g. `push`, `status`, `pull_request`), body `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/private-repo"}, ...}`, and any/absent `X-Hub-Signature`. Since `org-a` has no `webhook_secret`, `verify_signature` passes regardless of signature content, and the handler then resolves and mutates `org-b`'s `Stack`/`Commit`/`Team` via `full_name`.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type is registered [5](#0-4) ; the `GithubOrganizationUnknown` rescue only fires when `owner.login` doesn't match *any* configured org, not when it matches a differently-secured one [6](#0-5) ; `ExplicitParameters` schemas in handlers validate shape, not cross-field consistency with the owner used for auth.

### Impact Explanation
An attacker who knows (or discovers) that some organization in the Shipit config has no `webhook_secret` can forge webhook events attributed to any other organization's repository by name, causing unauthenticated writes to that other org's `Stack`, `Commit`, or `Team` records (e.g. enqueuing `GithubSyncJob`, creating commit `Status`, creating/removing `Membership`/`Team` records, or triggering pull-request-label-driven handlers) — this is a cross-tenant mutation from a payload that authenticated as a different (unsecured) repository owner, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This is repeatable against any repository whose owner can be resolved via `Repository.from_github_repo_name`, as often as the attacker likes, with no session or credentials.

### Likelihood Explanation
This is entirely configuration-dependent: it requires at least one organization entry in `Shipit.github(organization:)` config to have no `webhook_secret` set. If every configured organization has a properly set `webhook_secret`, the HMAC check for that organization is enforced normally and the attack fails because the attacker does not know any org's real secret. Given that requirement, attacker cost is trivial (single crafted HTTP POST, no auth, no knowledge of any secret) and the exploit is fully repeatable.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository resolution: verify that `payload.dig('repository','full_name')`'s owner segment equals `repository_owner` before dispatching to handlers, and/or require `webhook_secret` to be present (fail closed rather than `return true`) for every configured organization, rejecting webhooks for orgs without one instead of treating missing secret as "verified."

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` style (conceptual, not to be placed in an out-of-scope file per rules, but describing the reproducible assertions):
1. Configure two orgs in test config: `org-a` with `webhook_secret: nil`, `org-b` with `webhook_secret: "real-secret"`.
2. Create a `Stack`/`Repository` fixture owned by `org-b` (`full_name: "org-b/private-repo"`).
3. POST `/webhooks` with `X-Github-Event: push`, no/garbage `X-Hub-Signature`, and body `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/private-repo"}, "after": "<sha>", "ref": "refs/heads/<branch>"}`.
4. Assert `response.status == 200` (not 422) — i.e., `Shipit.github(organization: "org-a").verify_webhook_signature` returned `true` unconditionally.
5. Assert `GithubSyncJob` was enqueued with `stack_id: org_b_stack.id` — proving org-b's stack was mutated without org-b's `webhook_secret` ever verifying the bytes, violating the binding `organization(secret verifier) == organization(repository owner mutated)`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
