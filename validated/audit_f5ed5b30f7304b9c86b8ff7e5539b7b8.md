### Title
Cross-repository `Status` creation via unscoped SHA lookup mutates unrelated stacks' `ci_enabled?` and deployability state - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by SHA (`Commit.where(sha: params.sha)`) with no repository binding, unlike every other webhook handler in the codebase which resolves `Repository.from_github_repo_name(params.repository.full_name)` before touching any stack. A `status` webhook that is genuinely signed for one GitHub repository (owned/controlled by the attacker) is applied to every `Commit` row across the entire Shipit installation sharing that SHA, including commits belonging to unrelated victim stacks, causing `Status#after_create :enable_ci_on_stack` to flip `victim_stack.enable_ci!` and altering `Commit#deployable?`/CI banner state for a repository that never authenticated the webhook.

### Finding Description
The broken binding: the equality that should hold is `verified_payload.repository.full_name == stack.repository.full_name` for every `Stack`/`Commit` mutated as a side effect of the webhook. This binding is violated because `StatusHandler` never reads `payload['repository']` at all.

Code path:
- `WebhooksController#create` verifies the HMAC signature only against the organization derived from the payload (`repository_owner`) via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) , then dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . This confirms the *sender* controls a real GitHub repository that has the app installed under some organization/app installation — it does not confirm the sender controls the repository whose stack ends up mutated.
- `Handler` base class defines a `stacks` helper scoped by `repository_name` [3](#0-2) , and most handlers (`PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, `EditedHandler`) explicitly require `repository.full_name` in their param schema and resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [4](#0-3) .
- `StatusHandler`'s param schema only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — it never requires or reads `repository` at all: [5](#0-4) .
- Its `process` method fetches commits solely by SHA, globally, across every stack in the database: [6](#0-5) .
- Each matching commit gets `create_status_from_github!` called, which calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [7](#0-6) .
- `Status#after_create :enable_ci_on_stack` then unconditionally runs `commit.stack.enable_ci!` for whichever stack owns that commit row [8](#0-7) , and `Stack#enable_ci!` writes to the stack's CI cache flag [9](#0-8) .

Exploit flow: SHAs are content-addressed but are commonly shared across repositories in ordinary situations (forks, shared upstream history, cherry-picked/rebased commits with identical author/committer/timestamp/tree, or repositories tracking the same upstream mirror). An attacker who owns a repository (call it `attacker/repo`) with the same GitHub App/organization installation as a `victim` stack can:
1. Ensure a commit with a SHA equal to a SHA already recorded in the `victim` stack's `Commit` table exists in `attacker/repo` (achievable in many real setups — shared history, forks, mirrors, or cherry-picks reproducing identical commit metadata).
2. Trigger GitHub to send a genuine, correctly signed `status` event for that SHA from `attacker/repo` (e.g., via the GitHub Statuses API on their own repo, or via any CI integration they control).
3. Shipit's `verify_signature` succeeds (it is a real, GitHub-signed webhook — just for the wrong repository relative to the mutated stack).
4. `StatusHandler#process` matches the shared SHA against `Commit.where(sha: ...)` across all stacks, and the victim stack's `Status` row is created, firing `enable_ci_on_stack` on the victim's `Stack`, and also affecting `Commit#deployable?` via `add_status`'s `deployable_status` hook emission and `stack.schedule_merges` triggering.

Existing guards do not stop this: `verify_signature` only authenticates the org/app installation of the *sender's own repo*, not a binding between the payload's repository and the specific stacks being mutated; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` has no `repository` field to bind against; there is no `stacks`/`repository_name` scoping used anywhere in `StatusHandler`.

### Impact Explanation
An attacker controlling any repository on the same Shipit installation (or any org whose webhook secret they can trigger legitimate deliveries for) can create `Status`/mutate `Stack#ci_enabled?`, `Commit` deployability signals, and trigger `deployable_status`/`commit_status` hook emissions and `ProcessMergeRequestsJob`/merge scheduling for a `victim` stack they do not own, purely by causing a same-SHA status event from their own repository. This is a write to another tenant's `Stack`/`Commit` state without that tenant's repository ever authenticating the specific payload — matching the "payload for one repository mutating another's stack/commit" Critical impact category. It is repeatable against any commit SHA the attacker can reproduce or that happens to coincide (forks/shared history make this a routine, not theoretical, occurrence in multi-repo/multi-org Shipit deployments).

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository with the GitHub App/webhook installed that they control, and (b) a commit SHA in that repository matching a SHA already present as a `Commit` for the victim's stack. Requirement (b) is trivially satisfied for the extremely common case of forked repositories, shared upstream mirrors, or cherry-picked commits with identical committer/author dates and messages — no cryptographic collision is required, only ordinary git history sharing. No Shipit secrets, sessions, or privileged roles are needed; the attacker only needs the ability to make GitHub emit a real status webhook for a repository they legitimately control. This is a low-cost, repeatable attack.

### Recommendation
Require and validate `repository.full_name` in `StatusHandler`'s (and `CheckRun` handler's, if similarly unscoped) parameter schema, and scope the commit lookup to the resolved `Repository`'s stacks (e.g., `Repository.from_github_repo_name(params.repository.full_name)&.stacks&.commits&.where(sha: params.sha)`), matching the pattern already used by `PullRequest::OpenedHandler`/`ClosedHandler`/etc., so that a `Status` can only be created against commits belonging to stacks whose repository matches the authenticated payload's repository.

### Proof of Concept
minitest plan (add to `test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
```ruby
test "cross-repo status forgery mutates an unrelated stack's ci_enabled? state" do
  attacker_stack = shipit_stacks(:shipit) # repository A
  victim_stack = shipit_stacks(:cyclimse) # different repository B
  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

  # Simulate the same SHA existing in both repositories' commit history
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  Rails.cache.clear
  refute victim_stack.reload.ci_enabled?

  # Binding under test, stated explicitly:
  # payload.repository.full_name (attacker's repo A) == victim_stack.repository.full_name (repo B) ? -> should be false, and must gate the mutation
  payload = { "sha" => shared_sha, "state" => "pending", "repository" => { "full_name" => attacker_stack.repository.full_name } }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Assert the equality was violated: victim's stack was mutated despite the payload's repository not matching it
  assert victim_stack.reload.ci_enabled?, "victim stack's ci_enabled? flipped due to a same-SHA webhook signed for an unrelated repository"
end
```
This demonstrates that `victim_stack.ci_enabled?` (and by extension `enable_ci_on_stack`) changes as a side effect of a `status` payload whose `repository.full_name` never matches `victim_stack`'s repository — proving the binding is broken with no live GitHub interaction required.
