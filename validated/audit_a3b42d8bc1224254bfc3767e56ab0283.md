### Title
Cross-repository CI status forgery via unscoped `StatusHandler` sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub organization derived from the payload (`repository.owner.login`) [1](#0-0) [2](#0-1) , but `Shipit::Webhooks::Handlers::StatusHandler`, which processes `status` events, never checks that the commit it writes to belongs to that same organization/repository — it looks the commit up by SHA alone, across the entire database. [3](#0-2) 

### Finding Description
The base `Handler` class exposes a `stacks`/`repository_name` helper that scopes processing to the repository named in the webhook payload (`payload.dig('repository', 'full_name')`), and `PushHandler` correctly uses it before acting. [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores this scoping entirely:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha: ...)` is a global, unscoped query across every stack/repository tracked by this Shipit instance — it does not filter on `repository_name`/`stacks` the way `PushHandler` does. The status update lands directly on whatever `Commit` row matches the SHA, using that commit's own `stack_id`. [6](#0-5) 

The binding that should hold — "the GitHub organization/repository whose webhook signature was verified" == "the repository whose commit status gets written" — is broken. `verify_signature` only proves the payload was genuinely delivered by GitHub for *some* organization/repository configured in `Shipit.github`; it says nothing about which repository the `sha` in the body actually belongs to. Since git commit SHAs are a function of tree/parents/author/committer/timestamps/message and not of the hosting repository, an attacker who controls (or forks) any repository under an org onboarded to this Shipit instance can reproduce a commit with an identical SHA to a commit tracked by a *different, unrelated* stack (e.g. by forking the public upstream of a privately-deployed fork, or by pushing byte-identical commit objects). GitHub will then deliver a genuinely-signed `status` webhook for the attacker's own repository/commit, `verify_signature` passes (it's a legitimate GitHub signature for an onboarded org), and `StatusHandler` applies the forged CI state to the victim stack's commit purely because the SHA matches.

### Impact Explanation
Commit status directly gates whether a commit is deployable/mergeable — `commit.create_status_from_github!` updates `commit.state`, which feeds required-status checks used to allow deploys and to trigger `ProcessMergeRequestsJob`/merge-queue processing. [6](#0-5)  By forging a `success` status for a colliding-SHA commit, an attacker can make a commit in a completely different, higher-trust stack appear CI-green, enabling an **unauthorized deploy** (or unblocking the merge queue) of a commit that never actually passed its own repository's CI. This matches the report's underlying bug class — a check performed against one scope (here, the authenticated organization/repository) being silently applied to a different scope (any commit in the database) — analogous to the Ethereum test-suite mismatch between the network version a test was written for and the version it actually executes against.

### Likelihood Explanation
Exploitation requires the attacker to control (or fork) at least one repository under an organization already onboarded to the target Shipit instance, and to produce a commit whose SHA matches one tracked in a victim stack. This is non-trivial for arbitrary targets but realistic for common scenarios: forks of the same upstream history, mirrored repos, or any setup where multiple repositories under the same GitHub org share commit history (a common pattern) will produce identical SHAs. No secret, session, or repository write access to the *victim* stack is needed — only the ability to have GitHub deliver a legitimately-signed webhook for *some* onboarded repository.

### Recommendation
`StatusHandler#process` (and any other handler that queries by SHA/global identifiers) must scope its lookup to the repository named in the webhook payload, mirroring `Handler#stacks`/`repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through the `Stack`/`Repository` resolved from `payload.dig('repository', 'full_name')` before applying the status.

### Proof of Concept
1. Attacker forks/creates a repository under a GitHub organization already configured in `Shipit.github` (any onboarded org).
2. Attacker crafts a commit object (tree, parents, author, committer, timestamps, message) byte-identical to a commit already tracked by a victim stack in a different, unrelated repository — producing an identical SHA.
3. Attacker sets a commit status (e.g. `success`) on that commit in their own repository via the GitHub API/UI.
4. GitHub delivers a genuinely HMAC-signed `status` webhook to `POST /webhooks` for the attacker's own org/repo; `verify_signature` passes because the signature is valid for that (attacker-accessible) organization. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit (same SHA, different repository), and calls `commit.create_status_from_github!(params)`, marking it as `success` in the victim stack. [3](#0-2) 
6. The victim commit now shows CI success it never earned, enabling deploy/merge in Shipit for that stack.
