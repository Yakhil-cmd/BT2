### Title
Signature verification keyed on unverified `repository.owner.login`/`organization.login` field allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then validates the raw body against that org's secret. Once verification passes, the event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) independently read `repository.full_name` from the very same unverified body to decide which `Stack`/`Repository`/`Commit` to act on. Nothing binds these two payload fields to each other.

### Finding Description
In a multi-organization Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), each GitHub organization configured under `github:` in `secrets.yml` has its own `webhook_secret`.

`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks the `GithubApp`/secret to check the signature against using a field taken from the body itself, before that body has been authenticated. The actual `verify_webhook_signature` implementation only checks the HMAC of the raw payload against the secret for the org resolved this way: [2](#0-1) 

Once the head(422) gate is passed, `WebhooksController#create` dispatches the *entire unverified body* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers pick the target repository/stack from a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`StatusHandler` uses this to write commit statuses on arbitrary commits by SHA (no repo-membership check at all — it matches on `sha` globally):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` similarly act only on `repository.full_name`/`stacks`, unrelated to `repository.owner.login`: [6](#0-5) [7](#0-6) 

**The broken binding, as an equality:**
`organization_that_authenticated (repository.owner.login used for HMAC-key selection) == organization_of_repository_written (repository.full_name used by handlers)`

Before the attacker acts: for legitimate GitHub-originated webhooks, `repository.owner.login` and the owner portion of `repository.full_name` are always the same value, because GitHub itself serializes both from the same underlying repository object — the equality holds by construction.

After the attacker's crafted request: an attacker who is a legitimate administrator of **their own** GitHub organization/App entry in Shipit's multi-org config (and therefore genuinely knows that org's `webhook_secret` — this is not a privileged Shipit credential, it's a value the org owner chooses when creating their own GitHub App) can sign a payload with their own secret while setting `repository.owner.login` = their own org (so the HMAC-key lookup and check pass) but `repository.full_name` = `"victim-org/victim-repo"` (an entirely different org/repo tracked by the same Shipit instance). The verified-org/written-repo equality is broken, and Shipit processes attacker-controlled data as if it originated from the victim repository.

### Impact Explanation
This is a cross-repository / cross-organization write achieved purely by crafting a JSON body and a valid HMAC over it using a secret the attacker legitimately possesses for an unrelated tenant. Concrete effects on a victim stack/repo the attacker has no access to:
- Forge arbitrary commit statuses via `StatusHandler`/`Commit#create_status_from_github!` for any commit `sha` present in the victim's database (status matching is global by `sha`, not scoped by repo) — this can flip a commit from blocked to `deployable?` and trigger `schedule_continuous_delivery`, potentially causing an **unauthorized deploy** of the victim stack.
- Trigger `stack.sync_github` on the victim stack via `PushHandler`, or `schedule_refresh_check_runs!` via `CheckSuiteHandler`, injecting attacker-timed events into victim pipelines.
This satisfies the Critical bar ("cross-repository writes" / "an unauthorized deploy") defined in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, first-class configuration) and that the attacker administers one of those orgs' GitHub Apps (hence knows its `webhook_secret`) while having no access to the victim org. No GitHub org admin privileges over the victim, no Shipit session, and no `ApiClient` token are required — only the ability to send an HTTP POST to `/webhooks` with a body they sign themselves and control the `repository.full_name` field of. This is a realistic and directly reachable path once multi-org hosting is in place.

### Recommendation
After selecting the `GithubApp` config and verifying the HMAC, re-validate that the field(s) the handlers will actually act on (`repository.full_name`'s owner, or `organization.login` for org-scoped events) match the organization whose secret validated the signature, e.g. compare `repository_owner` against the owner segment of `payload.dig('repository', 'full_name')` and reject on mismatch, or key the webhook secret lookup by the confirmed `full_name` owner rather than a separately-read `owner.login` field.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (secret known to the attacker, who created that GitHub App) and `victim-org` (tracks a stack for `victim-org/victim-repo`, unrelated secret unknown to attacker).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo tracked in Shipit>",
  "state": "success",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>` and sends it with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s `GithubApp`, and successfully verifies the signature against the attacker's own known secret — see `app/controllers/shipit/webhooks_controller.rb#L24-L30` and `lib/shipit/github_app.rb#L76-L83`.
5. `create` dispatches the raw body to `StatusHandler`, which looks up `Commit.where(sha: ...)` — matching the victim's commit regardless of org — and writes a forged `success` status for it, per `app/models/shipit/webhooks/handlers/status_handler.rb#L20-L24`, potentially unblocking/triggering deployment of the victim stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
