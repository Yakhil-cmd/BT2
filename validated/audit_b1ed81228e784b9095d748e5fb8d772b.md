## Analysis Result [1](#0-0)  overrides the stack-scoping helper inherited from [2](#0-1) , breaking the invariant that an `ApiClient` restricted to one stack can only touch that stack.

### Title
Stack-scoped API token can read any stack's CI status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces that an `ApiClient` with a `stack_id` set is confined to that single stack by scoping the `stacks` relation before resolving `params[:stack_id]`: `stacks.from_param!(params[:stack_id])` [2](#0-1) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing this scoping entirely [3](#0-2) .

### Finding Description
`ApiClient#check_permissions!` only checks that the generic permission string (e.g. `read:stack`) is present in the client's `permissions` list; it never checks which specific stack the client is scoped to [4](#0-3) . The actual per-stack authorization boundary is enforced only by the `stacks` helper method, which restricts the queryable stacks to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id` [5](#0-4) .

`CCMenuController` authenticates using a raw query-string `token` param (not requiring the standard basic-auth flow) [6](#0-5) , and resolves the target stack with the unscoped `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` used everywhere else (e.g. `StacksController`, `TasksController`) [7](#0-6) . Because `require_permission :read, :stack` only validates the permission string and not the stack binding, any token holding `read:stack` — even one deliberately scoped to a single stack (e.g. fixture `here_come_the_walrus`, scoped to `stack: shipit` [8](#0-7) ) — can pass an arbitrary `stack_id` in the URL and successfully read that unrelated stack's `deploys_and_rollbacks`, name, lock status, and build status via the CCMenu XML view.

This mirrors the reported bug class: a value that is authorized for one narrow scope (a token scoped to `stack_id` X) is silently used to act on/read an arbitrary different scope (stack Y) because a security check ("is this stack within the token's authorized scope?") that exists on the sibling code path is missing on this one.

### Impact Explanation
This is a cross-stack authorization bypass: an attacker in possession of any `read:stack`-permissioned API token — even one intentionally scoped by an admin to a single, low-sensitivity stack — can enumerate and read the deploy/lock/status state of every other stack in the Shipit instance via the CCMenu endpoint. This matches the "High - unauthenticated/unauthorized read of stack state" impact bucket, since the token was never authorized to view that stack's data.

### Likelihood Explanation
Exploitation only requires possession of any valid API client token with `read:stack` permission (which is routinely handed out, e.g. automatically created and scoped tokens via `CCMenuUrlController`) and knowledge/guessing of another stack's `repo_owner/repo_name/environment` identifier used in `Stack.from_param!`. No privileged access, GitHub credentials, or session is required beyond having one legitimate, narrowly-scoped API token.

### Recommendation
Change `CCMenuController#stack` to use the scoped helper, consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id` restrictions apply uniformly across all API controllers.

### Proof of Concept
1. Admin creates (or the system auto-creates via `CCMenuUrlController`) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
2. Attacker (or a party who legitimately holds this token for Stack A, e.g. an embedded CI widget) uses the token against Stack B's CCMenu endpoint:
   `GET /api/1/stacks/:owner/:repo/:env/cc_menu.xml?token=<stack-A-scoped-token>` where the path params identify Stack B.
3. `authenticate_api_client` succeeds (token is valid) [6](#0-5) ; `require_permission :read, :stack` passes because the token has `read:stack` regardless of which stack [4](#0-3) ; `stack` resolves Stack B unscoped [7](#0-6) .
4. Response renders Stack B's name, lock state, and latest build status/log link — data the token was never authorized to access.
