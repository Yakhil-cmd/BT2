```
if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
    return cb("sending private asset from AA");
``` [1](#0-0) 

However, nothing in `validation.js`'s `validatePayment`/`validatePaymentInputsAndOutputs` prevents a normal wallet user from sending a private asset payment *to* an AA address in the first place — private payments are validated the same way regardless of whether the receiving address is an AA. [2](#0-1) [3](#0-2) 

Once such a private-asset output lands on an AA address, the AA has no code path to ever move it back out: `sendUnit` unconditionally bounces/errors any attempt to include that asset in an outgoing payment message, and there's no alternative mechanism (no "receive"-style withdrawal, no special-cased forwarding) for private assets held by an AA. This mirrors the reported bug class: a `receive()`-style path lets funds in, but the withdrawal path structurally can't reach that class of asset — the AA's balance for that private asset is permanently stuck.

### Title
Private assets sent to an AA become permanently locked because AAs cannot send private-asset payments - (File: `aa_composer.js`)

### Summary
Obyte's Autonomous Agents (AAs) can receive payments in any asset, including private (hidden) assets, but the AA response-composition logic in `aa_composer.js` unconditionally refuses to build outgoing payment messages for private assets. There is no compensating mechanism for the AA (or anyone) to ever release such coins, so any private-asset balance credited to an AA address is stuck forever.

### Finding Description
When an AA processes a trigger and prepares its response messages in `sendUnit`, each payment message's asset is looked up, and if `objAsset.is_private` is true the composition is aborted with the error `"sending private asset from AA"`: [4](#0-3) 

This check exists because, as the inline comment states, an AA-authored unit containing a private-asset output would fail unit validation anyway "due to lack of spend_proofs" — AAs cannot produce the `spend_proofs`/blinding data required for private outputs since that data must be generated interactively between counterparties off-chain (see `private_payment.js`'s chain-validation logic, which expects hidden `output_hash`/`blinding` fields supplied by a real wallet, not an AA script) [5](#0-4) .

Meanwhile, nothing in unit/payment validation stops a wallet from sending a private asset to an AA address as an ordinary trigger output — `validatePayment` and `validatePaymentInputsAndOutputs` validate private outputs the same way for any recipient address, AA or not [6](#0-5) [3](#0-2) . The AA's balance bookkeeping (`aa_balances` table, updated in `updateFinalAABalances`) tracks this credited balance per asset regardless of asset type [7](#0-6) .

Because the AA composer can never emit a payment message for a private asset, once an AA's balance for that asset is positive, it is unconditionally and permanently unspendable by that AA — there is no bounce, no forwarding, and no alternate withdrawal path, analogous to the `MarginTrading.sol` bug where ETH could be received via `receive()` but never withdrawn because the withdraw logic only handled unwrapped WETH.

### Impact Explanation
Any private asset accidentally or deliberately sent to an AA address results in permanent loss of those funds — a concrete AA fund freezing/loss condition. Unlike a bounce for base-asset triggers (where insufficient/incompatible payments are refunded via `bounce()`), private-asset outputs are not distinguished from other outputs when credited to the AA, so users interacting with AAs that also handle private assets (or a user who mistakenly funds an AA with a private-asset transfer) have no recovery path.

### Likelihood Explanation
This can be triggered by any ordinary user (unprivileged) simply composing a private-asset payment whose output address is an AA address — a normal wallet operation, requiring no special privilege, hub or node compromise. AAs that are designed to work with private assets (or generic "accept any asset" AAs, several of which appear as sample scripts, e.g. `a_bank_without_percent.oscript`'s "silently accept coins" branch) are directly reachable by this issue [8](#0-7) .

### Recommendation
Either (a) reject private-asset outputs directed at AA addresses at the validation layer (in `validateAATrigger`/`validatePayment`) so such payments can never be composed/confirmed in the first place, or (b) provide AAs with a defined mechanism to safely dispose of private-asset balances (e.g., an automatic bounce-equivalent for private-asset outputs mirroring the existing bounce-fee refund logic in `bounce()`) so they are not silently absorbed into an unusable balance.

### Proof of Concept
1. Define/issue a private (`is_private: true`) asset.
2. From a normal wallet, send a valid private-asset payment (with correct `spend_proofs`, blinding, etc., per `indivisible_asset.js`'s private composition logic) to the address of any existing AA.
3. The payment validates normally per `validatePayment`/`validatePaymentInputsAndOutputs`, and the AA's `aa_balances` entry for that asset is credited via `updateFinalAABalances`.
4. Trigger the AA to attempt to send that private asset back out (or observe that no code path in any AA script/`sendUnit` execution can ever include that asset in an outgoing payment) — `sendUnit` will always short-circuit with `"sending private asset from AA"` for any payment message referencing that asset, and no other mechanism moves it out. The balance remains stuck in the AA forever.
