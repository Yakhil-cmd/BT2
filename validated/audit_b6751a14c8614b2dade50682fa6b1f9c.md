### Title
Prompt-injectable `gh pr create` flag injection via attacker-controlled diff/commit content in unrestricted `Bash(gh pr create:*)` allowlist - ([File: .claude/commands/commit-push-pr.md])

### Summary
The `/commit-push-pr` slash command grants `Bash(gh pr create:*)`, which only anchors on the literal prefix `gh pr create` and places no restriction on any flags/arguments that follow. Because the command's own instructions feed `git diff HEAD` and commit-message content directly into the LLM's PR-title/body generation step, an attacker who can get adversarial text into tracked file content or a commit message reachable by that diff can attempt to steer the model into appending flags such as `--repo`, `--base`, or other `gh` options to the executed `gh pr create` invocation, and the wildcard allowlist would not block it.

### Finding Description
`.claude/commands/commit-push-pr.md` defines: [1](#0-0) 
The frontmatter's `allowed-tools: ... Bash(gh pr create:*)` matches any Bash command whose argv starts with `gh pr create`, with the trailing `:*` permitting arbitrary further arguments — this is the intended, documented wildcard behavior of Claude Code's Bash permission matcher (`Bash(cmd:*)` allows the base command with any arguments), confirmed by changelog entries describing this exact matching semantic. The command's context block injects `git diff HEAD` (staged/unstaged changes) directly into the prompt that instructs the model to "Create a pull request using `gh pr create`" and to construct title/body based on "the above changes." If tracked file content or a commit message contains adversarial text (e.g., an embedded instruction like `--repo attacker/evil` or `--base malicious-branch`), that text becomes part of the model's context when it decides what literal `gh pr create ...` command string to execute via the Bash tool. Because the allowlist pattern imposes no flag-level restriction (unlike the flag-allowlisting approach used elsewhere in this same repo, e.g. `scripts/gh.sh`'s `ALLOWED_FLAGS` gate for other `gh` subcommands: [2](#0-1) ), there is no enforcement layer to stop an injected `--repo`/`--base` flag from being included in the actual executed command once the model is convinced to add it.

### Impact Explanation
If successful, this could redirect a PR to an attacker-controlled `--repo`, target an unintended `--base` branch, or otherwise alter the PR's destination/metadata — potentially exposing PR content (including diff/code) to a repo the attacker controls, or corrupting the intended review/merge target. Impact is scoped to the PR-creation step of this specific slash command and requires the model to actually comply with injected instructions embedded in diff/commit content; the allowlist itself provides no defense-in-depth against such flags once the model emits them.

### Likelihood Explanation
This depends entirely on prompt-injection succeeding against the model (i.e., the LLM must be convinced by content embedded in a diff or commit message to append unexpected flags to the `gh pr create` invocation it authors) — the `allowed-tools` wildcard was designed to allow flexible `gh pr create` usage and is not itself a "parsing trick" bypass of a narrower stated restriction. Feasibility is therefore gated by prompt-injection robustness of the underlying model rather than a deterministic parser flaw, making this an inconsistent-mitigation issue (present for `gh pr create` but explicitly hardened via flag allowlisting for other `gh` subcommands in `scripts/gh.sh`) rather than a guaranteed exploit.

### Recommendation
Apply the same flag-restriction pattern already used in `scripts/gh.sh` to `gh pr create` (e.g., a wrapper script or hook that whitelists only `--title`, `--body`, `--head` and hardcodes `--repo`/`--base` to the current repository/default branch, rejecting any other leading-dash tokens), and tighten `allowed-tools` in `.claude/commands/commit-push-pr.md` and `plugins/commit-commands/commands/commit-push-pr.md` to route through that wrapper instead of the unrestricted `Bash(gh pr create:*)` pattern.

### Proof of Concept
Integration/fuzz test plan: seed a repo file/commit message with adversarial strings (`"--repo=attacker/evil"`, `"--base=malicious"`, or free-text instructions attempting to redirect PR target) reachable via `git diff HEAD`; invoke `/commit-push-pr`; capture the literal Bash tool invocation string passed for `gh pr create`; assert that `--repo` and `--base` (or their absence) always resolve to the fixed, expected origin repo/default branch regardless of diff/commit content, and fail the test if any fuzzed value flows into the executed flag list.
