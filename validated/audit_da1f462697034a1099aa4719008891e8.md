### Title
`uint64`-to-`int64` Narrowing Cast in `consolidatedNode.Split()` Corrupts CN/CL Reward Distribution — (`kaiax/staking/staking_info.go`)

### Summary

`consolidatedNode.Split()` converts `uint64` staking amounts to `int64` via a direct cast before constructing `big.Int` weights. If either `StakingAmount` or `CLStakingAmount` exceeds `math.MaxInt64` (≈ 9.22 × 10¹⁸ KAIA), the cast silently wraps to a negative value, producing a negative or zero `totalAmount` denominator. This corrupts the proportional split of every block's staking reward between the CN reward address and the CL pool address.

### Finding Description

In `kaiax/staking/staking_info.go`, `consolidatedNode.Split()` is the sole function that divides a reward amount between a validator's CNStaking address and its consensus-liquidity pool:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    ...
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))              // ← uint64 → int64 cast
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // ← uint64 → int64 cast
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount  = clAmount.Div(clAmount, totalAmount)          // ← division by totalAmount
    cnAmount  := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `StakingAmount` (field of `consolidatedNode`) and `CLStakingAmount` (field of `CLStakingInfo`) are declared as `uint64`: [2](#0-1) [3](#0-2) 

`uint64` has a maximum of `18,446,744,073,709,551,615`, while `int64` has a maximum of `9,223,372,036,854,775,807`. Any value in the range `[math.MaxInt64+1, math.MaxUint64]` wraps to a negative `int64`, so `big.NewInt(int64(x))` produces a negative `*big.Int`.

`Split()` is called in three reward-critical paths:

1. `assignStakingRewardsFlex` — distributes staking rewards to each CN/CL pair under the Flex rule (Osaka+): [4](#0-3) 

2. `assignStakingRewards` — distributes staking rewards under the Kore/Prague rule: [5](#0-4) 

3. `specWithProposerAndFundsFlex` — splits the proposer's own minting reward between CN and CL: [6](#0-5) 

Additionally, `consolidateNodes()` accumulates `StakingAmount` with unchecked `uint64` addition across multiple staking contracts sharing the same reward address: [7](#0-6) 

And both `assignStakingRewardsFlex` and `assignStakingRewards` add `CLStakingAmount` to `StakingAmount` with unchecked `uint64` arithmetic: [8](#0-7) [9](#0-8) 

### Impact Explanation

When `c.StakingAmount > math.MaxInt64`:

- `cnAmountBig` becomes a large negative `*big.Int`.
- `totalAmount = cnAmountBig + clAmountBig` can be zero (panic: division by zero in `clAmount.Div`) or a wrong signed value.
- If non-zero but negative, `clAmount` is computed as a negative fraction of `amount`, and `cnAmount = amount − clAmount` becomes larger than `amount`, effectively stealing KAIA from the CL pool and over-crediting the CN reward address — or vice versa.
- Every block that calls `FinalizeState` while this condition holds distributes the wrong amounts to `cn.RewardAddr` and `cn.CLStakingInfo.CLPoolAddr`.

This is an unauthorized redistribution of KAIA between the CN reward address and the CL pool address — a direct asset-ownership impact on staking rewards.

### Likelihood Explanation

`StakingAmount` is stored in KAIA (not kei), obtained by dividing the on-chain balance by `params.KAIA` (1 × 10¹⁸): [10](#0-9) 

`math.MaxInt64` in KAIA units is ≈ 9.22 × 10⁹ KAIA. The current total supply of KAIA is far below this threshold, making the condition unlikely under normal network conditions. However:

- The minting amount is governance-controlled and can be raised.
- A validator consolidating many staking contracts (line 138) accumulates their `uint64` sums without overflow protection.
- The `CLStakingAmount` addition (lines 444, 502) is also unchecked.

The bug class is latent and becomes exploitable if the network's token economy evolves or if governance parameters are changed.

### Recommendation

Replace all `int64(c.StakingAmount)` and `int64(c.CLStakingInfo.CLStakingAmount)` casts with `new(big.Int).SetUint64(...)`:

```go
cnAmountBig = new(big.Int).SetUint64(c.StakingAmount)
clAmountBig = new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
```

Also guard the `uint64` accumulations in `consolidateNodes`, `assignStakingRewardsFlex`, and `assignStakingRewards` with overflow checks (e.g., using `math.SafeAdd`) or promote intermediate sums to `*big.Int` before accumulation.

### Proof of Concept

```go
// Construct a consolidatedNode whose StakingAmount exceeds math.MaxInt64
cn := consolidatedNode{
    StakingAmount: math.MaxInt64 + 1, // wraps to -9223372036854775808 when cast to int64
    CLStakingInfo: &CLStakingInfo{
        CLStakingAmount: 1,
    },
}

// Split a reward of 1000 kei
cnAmt, clAmt := cn.Split(big.NewInt(1000))
// totalAmount = big.NewInt(int64(math.MaxInt64+1)) + big.NewInt(1)
//             = big.NewInt(-9223372036854775808) + big.NewInt(1)
//             = big.NewInt(-9223372036854775807)  (negative denominator)
// clAmount = 1 * 1000 / (-9223372036854775807) = 0 (truncated toward zero)
// cnAmount = 1000 - 0 = 1000
// → CL pool receives 0 instead of its proportional share; CN takes all.
fmt.Println(cnAmt, clAmt) // 1000, 0  — CL pool is silently zeroed out
```

If instead `CLStakingAmount` is chosen to make `totalAmount` exactly zero, `Div` panics with a division-by-zero, halting block finalization on every honest node that processes the block.
