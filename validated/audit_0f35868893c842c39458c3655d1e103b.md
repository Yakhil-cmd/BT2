## Title
Cross-stack information disclosure via `Api::CCMenuController#stack` bypassing the ApiClient's stack-scope binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` binds an `ApiClient`'s authorization to a specific `Stack` when the client is stack-scoped: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and `#stack` resolves the requested stack through that scoped relation (`stacks.from_param!(...)`). [1](#0-0)  `Api::CCMenuController` overrides `#stack` and instead resolves it against the entire `Stack` table, unscoped by the token's authorized stack: `Stack.from_param!(params[:stack_id])`. [2](#0-1) 

### Finding Description
The equality that should hold is: `stack the token authorizes == stack the controller touches`. For a stack-scoped `ApiClient` (`stack_id` set), that equality holds in every other API controller that relies on the inherited `stack`/`stacks` helpers, because `stacks` filters to `Stack.where(id: current_api_client.stack_id)` before `from_param!` is applied. [1](#0-0) 

`CCMenuController` breaks this equality: it re-implements `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, ignoring `current_api_client.stack_id`. [3](#0-2)  The `require_permission :read, :stack` before_action only checks that the permission string `read:stack` is present in the client's `permissions` array via `check_permissions!`; it never checks which specific stack the permission applies to. [4](#0-3)  Consequently, a client scoped to one stack (e.g. fixture `here_come_the_walrus`, scoped to the `shipit` stack, with only `read:stack` permission) can query `/api/{other_stack}/ccmenu.xml` and read CI/deploy status for any stack in the installation, not just the one it was authorized for.

This is structurally the same class of bug as the reported issue: a security-relevant piece of state (the "authorized scope") is computed correctly in one place (`BaseController#stacks`) but the value actually acted upon in the code path that matters (`CCMenuController#stack`) is a different, broader value — the narrower/authorized scope is silently discarded rather than being consistently applied, exactly analogous to the DefaultStateManager bug where the correct incremental value was discarded in favor of the last raw value.

### Impact Explanation
This matches the rule's explicit binding category — "a stack a token authorises versus a stack it touches" — and the accepted High-impact category "unauthenticated read of stack state, task streams or deploy output": an attacker holding any valid, stack-scoped, read-only API token for one stack can read deploy/build status output (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity) for arbitrary other stacks in the Shipit instance, which they were never authorized to see. `authenticate_api_client` in `CCMenuController` also accepts the token via `params[:token]` in a query string rather than only via the `Authorization` header, widening exposure (tokens end up in logs/URLs), but the core cross-tenant read is the security-relevant break here.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that issues scoped, read-only API tokens to third parties (this is exactly the supported use case demonstrated by `CCMenuUrlController`, which mints a `read:stack`-only `ApiClient` scoped to a single stack and hands its token to users for CI status widgets). [5](#0-4)  Any holder of such a token — an unprivileged actor with legitimate, narrow access to one stack's CI status URL — can enumerate/guess other stack params and read their status with no further privilege.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` (or reimplement it using the inherited, authorization-scoped `stacks` relation) so that `stack` is always resolved via `stacks.from_param!(params[:stack_id])`, consistent with `Api::BaseController`. This ensures the stack actually touched by the controller is always constrained to the stack(s) the authenticated `ApiClient` is authorized for.

### Proof of Concept
1. Create a stack-scoped `ApiClient` limited to `stack_a` with permission `read:stack` only (as in fixture `here_come_the_walrus`, scoped to stack `shipit`). [6](#0-5) 
2. Using that client's `authentication_token`, request `GET /api/{stack_b}/ccmenu.xml` where `stack_b` is a different, unrelated stack the client was never granted access to (pass token via `Authorization: Basic` header, or via `?token=` per `CCMenuController#authenticate_api_client`). [7](#0-6) 
3. Observe that `require_permission :read, :stack` passes (the client does have `read:stack` in its `permissions` list) and `#stack` resolves `stack_b` directly against `Stack.from_param!`, bypassing the `current_api_client.stack_id` scoping that `Api::BaseController#stacks` would otherwise enforce. [3](#0-2) 
4. The response renders `stack_b`'s latest deploy/build status, which the token was not scoped to access — contrast with `Api::StacksController`/other API controllers where the same token would only ever see `stack_a`, as demonstrated by the test "an api client scoped to a stack will only see that one stack." [8](#0-7)
