### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the commit belongs to the repository named in the webhook payload. Combined with the fact that GitHub's webhook signature covers only the raw payload bytes signed with *some* configured organization's `webhook_secret` — not a binding between that organization and the `sha`/`repository` fields the handler actually acts on — an attacker who legitimately controls any GitHub org/repo wired into the same Shipit instance can forge a "success" CI status for a commit that lives in a completely different stack/repository they have no access to.

### Finding Description
`WebhooksController#verify_signature` derives which organization's secret to check against solely from `repository_owner`, itself read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')`), and only *after* that verifies the raw body HMAC against that org's secret: [1](#0-0) [2](#0-1) 

This proves the request body was signed with *some* organization's own secret — nothing else. Downstream, most handlers additionally scope their action to the repository named in the payload via `Handler#repository_name` / `#stacks`, which reads `repository.full_name`: [3](#0-2) 

`StatusHandler`, however, does not use this scoping at all — it looks up commits globally by `sha` and applies the reported state directly: [4](#0-3) 

There is no equality enforced between "organization/repository whose secret authenticated this webhook" and "repository that owns the commit being written to." Because git commit SHAs are computed only from tree/parent/author/committer/message content, an attacker who controls their own repository (and thus knows/owns a legitimately configured `webhook_secret` for their own org in a multi-org Shipit deployment, or simply has push access to any repo tracked by the instance) can fabricate a commit with identical metadata to reproduce the exact same SHA as a commit that is tracked under a victim's stack, then fire a `status` event from their own repository setting `state: "success"` and a `context` matching a required check name for that SHA. Shipit's `Commit.where(sha:)` lookup is not repository-scoped, so this forged status is attached to the victim's tracked commit.

Binding broken: `organization/repository that authenticated the webhook == repository that owns the commit being mutated`. Before the attack, only GitHub events genuinely originating for a given repository can set statuses on that repository's commits. After sending a crafted payload, an unrelated org's authenticated webhook can set the status of a commit belonging to a different, unrelated stack.

### Impact Explanation
A forged "success" status on a required check can satisfy CI-gating logic that Shipit's merge queue / deploy readiness checks rely on, resulting in an unauthorized deploy or merge decision on a repository the attacker does not control — matching the Critical impact category ("unauthorized deploy, rollback or merge"). This requires no access to the victim's `webhook_secret`, `GITHUB_TOKEN`, or repository — only the attacker's own legitimately configured webhook credentials for an entirely different, unrelated repository/org in the same Shipit instance.

### Likelihood Explanation
Exploitation requires the attacker to control at least one repository/org already integrated with the Shipit instance (a realistic scenario for any shared, multi-team, or multi-org Shipit deployment) and the ability to craft a commit with a colliding SHA to a target commit (achievable deterministically by reproducing identical tree/parent/author/committer/timestamp/message fields, which is trivial if the attacker can observe the victim's commit metadata via the public GitHub API). No cryptographic secret of the victim is needed.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up records solely by SHA) to the repository identified in the verified payload the same way `PushHandler`/`CheckSuiteHandler` do — e.g., restrict the `Commit` lookup to `stacks`/repositories that belong to the `repository_name` in the payload, and additionally verify that `repository.owner.login` (used to select the signing secret) is consistent with `repository.full_name`'s owner segment before trusting either field.

### Proof of Concept
1. Attacker registers/owns `attacker-org/sandbox-repo`, which is a legitimately configured GitHub App installation on this Shipit instance (their own `webhook_secret`).
2. Attacker creates a commit in `sandbox-repo` with the exact tree, parent, author, committer, and message of a target commit `abc123...` that is tracked by `victim-org/victim-repo`'s stack (obtained via GitHub's public API), reproducing the identical SHA.
3. Attacker sends a `status` webhook to `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`, and body:
   ```json
   {
     "sha": "abc123...",
     "state": "success",
     "context": "required-ci-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/sandbox-repo" }
   }
   ```
4. `WebhooksController#verify_signature` validates successfully because `repository_owner` resolves to `attacker-org` and the signature matches `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, matches the victim's tracked commit (unrelated to `attacker-org/sandbox-repo`), and records a "success" status on it, independent of which repository/org actually authenticated the request. [5](#0-4) [6](#0-5)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
