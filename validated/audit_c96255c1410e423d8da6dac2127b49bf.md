### Title
`liquidate-multi` silently swallows a `liquidate()` failure, letting collateral seizure and debt write-off persist without the matching bad-debt socialization - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` does not "bubble up" per-position failures the way the Penumbra fix requires for contribution-handler crashes; instead it swallows them as inert data. `liquidate-multi` is implemented as `(ok (map call-liquidate positions))` [1](#0-0) , and `call-liquidate` simply forwards the return value of `liquidate` without ever calling `try!`/`asserts!` on it [2](#0-1) . Because the top-level transaction (`liquidate-multi`) always returns `Ok`, Clarity's transaction-level atomicity commits every state change made across the whole call, including the ones already performed by an individual `liquidate()` invocation that later fails and returns `(err ...)`. That per-position error is only "seen" as data inside the returned list — never propagated with `try!` — so it never triggers a rollback.

### Finding Description
Inside `liquidate`, the order of operations is:
1. Repay debt in the vault (`vault-system-repay`), remove the borrower's scaled debt obligation (`debt-remove-scaled`), and transfer seized collateral to the liquidator (`collateral-remove`) — all executed and committed first. [3](#0-2) 
2. Only afterwards, if the position has no collateral left, does it attempt **bad-debt socialization** via `fold socialize-debt-asset ...`, followed by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [4](#0-3) .

`socialize-debt-asset` itself is the mechanism that writes off the uncovered ("bad") debt at the vault level — decreasing the vault's aggregate scaled debt/liquidity index (`vault-socialize-debt`, `vault-accrue`) so that the loss is spread across all suppliers of that vault [5](#0-4) .

If this socialization step fails (`asserts!` triggers the error branch), `liquidate` merely *returns* `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` as an ordinary Clarity response value — this is not a runtime abort (`unwrap-panic`/panic), so it does **not** unwind the state changes already committed earlier in the same call (steps performed at lines 1495-1512). When `liquidate` is invoked directly by a user, this err is caught by the caller's wallet/client and (in most flows) the caller can choose to retry, but critically — when invoked through `liquidate-multi`, the err is never checked: `call-liquidate` just returns whatever `liquidate` returned, `map` puts it in a list, and `liquidate-multi` wraps that list in `(ok ...)`. Since the *transaction as a whole* returns `Ok`, Stacks commits everything, including the token transfers and `debt-remove-scaled` write from the failed position — but not the corresponding vault-level write-down.

Net effect: the borrower's individual obligation is erased and the liquidator keeps the seized collateral, but the vault's aggregate outstanding debt is never decremented to reflect the actual, permanent shortfall. This creates a "ghost" scaled-debt balance in the vault that no principal will ever repay, inflating the computed `total-debt()` / share price relative to reality — a loss that is silently deferred onto whichever suppliers hold zTokens when the shortfall is eventually discovered (or never discovered), rather than being immediately and correctly socialized.

### Impact Explanation
This harms an unprivileged third party distinct from the caller: all suppliers/depositors of the affected vault. The liquidator (attacker/beneficiary) walks away with real collateral while the corresponding debt write-off — which should immediately and proportionally reduce every supplier's redeemable value — never executes. Later suppliers who redeem after the shortfall surfaces bear a disproportionate share of the loss, and in the worst case the vault becomes unable to honor withdrawals for the full recorded balance once the "ghost" debt fails to materialize as real repayment (protocol insolvency / permanent freezing of supplier funds). This lands in the Critical impact bucket ("permanent freezing of funds... or protocol insolvency").

### Likelihood Explanation
`liquidate-multi` is documented as deliberately choosing to not revert the whole batch on a single position's failure ("Failed liquidations return error codes but don't revert entire batch") [6](#0-5) , but the implementation goes further than intended: it doesn't just avoid reverting *other* positions in the batch, it fails to roll back the *already-executed side effects of the very position that errored*, because Clarity only fully reverts on genuine runtime aborts or when an error is propagated with `try!` all the way to the top-level function. Any legitimate failure mode of `socialize-debt-asset`/`vault-socialize-debt` (e.g., a vault pause toggled mid-block, an index-cache mismatch, or any other `unwrap!`-guarded condition returning an error) is sufficient to trigger this — no privileged action or exotic setup is required, only calling `liquidate-multi` on a position that ends up with zero remaining collateral.

### Recommendation
`liquidate-multi` (and `call-liquidate`) must propagate individual failures with `try!`/`asserts!` so that a socialization failure aborts the whole transaction (matching the Penumbra fix's principle of "correctly bubbling crashes upstream"), or `liquidate` itself must perform the debt-removal/collateral-transfer and the bad-debt socialization as a single atomic step that cannot succeed partially — e.g., compute and validate that socialization can succeed *before* removing the borrower's obligation and transferring collateral, or use `try!` on the socialization result before doing `debt-remove-scaled`/`collateral-remove`.

### Proof of Concept
1. Attacker (liquidator) identifies a position that, once liquidated, will have zero remaining collateral, requiring bad-debt socialization via `socialize-debt-asset`.
2. Attacker constructs conditions (or timing) such that the socialization step's underlying `vault-socialize-debt`/`vault-accrue` call fails (any of the `unwrap!` guards in `socialize-debt-asset` at [7](#0-6)  returning err), e.g. via a vault pause state or an accrual/index edge case.
3. Attacker calls `liquidate-multi` with this position (batched, even a batch of one).
4. `liquidate` executes `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` successfully (attacker/liquidator receives collateral, borrower's debt obligation is cleared), then hits the `asserts!` on `socialization-result` and returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
5. `call-liquidate` returns this err value unchanged; `liquidate-multi` still returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` — the transaction succeeds and all prior state changes commit.
6. Vault's `total-debt()`/index accounting retains the un-written-off scaled debt while the corresponding borrower obligation no longer exists anywhere — a permanent discrepancy that inflates share price until it manifests as an inability to fully redeem for later suppliers.

Note: I was unable to execute this in a live/simulated environment (no test harness access), so the exact triggering condition for `socialize-debt-asset`'s internal `unwrap!` failure could not be empirically confirmed beyond identifying the code paths that can return an error; this should be validated with the project's test suite (e.g., `local-testing/tests/`) before remediation.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
