### Title
Webhook signature verified against `repository.owner.login`, but stack/repository resolution trusts unrelated `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
This is the closest reachable analog to the "field acted on vs. field verified" trust-binding class from the report: Shipit's webhook signature check authenticates *which GitHub organization's secret* produced a payload, but the code that actually resolves which `Stack`/`Repository` to act on trusts a different, independently-controlled field from the same JSON body, without cross-checking that it belongs to the authenticated organization.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate against based on `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` selects the corresponding `webhook_secret` (Shipit explicitly supports one `webhook_secret` per GitHub organization when multiple GitHub Apps are configured): [3](#0-2) [4](#0-3) [5](#0-4) 

Once the HMAC is accepted, the raw JSON body is dispatched unmodified to the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`): [6](#0-5) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack` purely from `repository.full_name` in that same payload, via `Handler#repository_name` / `Handler#stacks`: [7](#0-6) 

Nowhere in `Handler` (or `PushHandler`) is `repository.full_name`'s owner segment cross-checked against `repository_owner` used for signature selection. Both `repository.owner.login` and `repository.full_name` are attacker-supplied fields inside the same signed body — the signature proves only that *someone who knows the secret for organization X* sent the request, not that the enclosed `repository.full_name` actually belongs to organization X.

### Impact Explanation
In a multi-GitHub-App deployment (explicitly documented and supported), each organization onboarded to the same Shipit instance has its own, independently-known `webhook_secret`. An organization admin/attacker who legitimately controls their own onboarded organization ("OrgB") knows OrgB's `webhook_secret` (they configured it) but has no privileges over a different onboarded organization's repositories ("OrgA"). Because `verify_signature` only binds the signature to `repository.owner.login`, and the handlers key off the unrelated `repository.full_name`, OrgB's admin can craft and correctly sign (with OrgB's own secret) a payload where `repository.owner.login = "OrgB"` (to select the secret they know) but `repository.full_name = "OrgA/target-repo"` (to target a stack that belongs to a different organization). This lets them:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha:)` against OrgA's stacks, forcing sync of arbitrary/attacker-chosen `after` SHAs into OrgA's commit history tracking.
- Inject fabricated CI `status` records for OrgA's commits via `StatusHandler`, potentially unblocking OrgA's merge queue or deploy gating logic (`required_statuses`/`blocking_statuses` in `deploy_spec`), since those checks trust `Commit#statuses` populated straight from this webhook.
- Forge `check_suite` events for OrgA repos.

This crosses the organization/repository trust boundary the report's bug-class targets ("an organization that authenticated versus the repository that is written"), and can lead to an unauthorized deploy/merge decision being influenced by a party with no authorization over the target repository — matching the engine's Critical/High impact bar (unauthorized deploy/merge via forged status/gating signals).

### Likelihood Explanation
Requires: (1) the host Shipit instance to be configured with multiple GitHub Apps/organizations sharing one webhooks endpoint (a documented, supported configuration, not a misconfiguration), and (2) the attacker to be a legitimate admin of one onboarded organization with no rights on another. No token, session, or repository write access to the *target* org is needed — only knowledge of their own org's webhook secret, which they inherently possess. This is a realistic, unprivileged-relative-to-target-repo scenario in any Shipit deployment onboarding multiple untrusted/separate organizations.

### Recommendation
After verifying the HMAC signature for `repository_owner`, re-derive the expected owner from `repository.full_name` (or `repository.owner.login` used consistently everywhere) and reject/short-circuit if it does not match the organization whose secret validated the signature. Concretely, in `Handler#repository_name`/`stacks`, or in `WebhooksController#verify_signature`, assert `repository.full_name.split('/').first == repository_owner` before dispatching to handlers, so the authenticated organization is cryptographically bound to the repository the handlers act upon.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps/orgs, `OrgA` (victim, has `Stack` `OrgA/target-repo`) and `OrgB` (attacker-controlled, legitimate `webhook_secret_B` known to the attacker).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgA/target-repo", "owner": { "login": "OrgB" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_B, body)` using their own legitimate `OrgB` secret.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgB"`, loads `Shipit.github(organization: "OrgB")`, and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "OrgA/target-repo"` — an org the attacker's signature never authenticated for — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on OrgA's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
