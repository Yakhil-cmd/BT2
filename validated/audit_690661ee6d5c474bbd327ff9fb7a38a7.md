### Title
`Status` webhook flips `blocked?`/`deployable?` for any stack sharing a SHA, regardless of authenticated repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without any filter on the repository that authenticated the webhook. Because `Commit#blocked?` and `#deployable?` derive from `stack.blocking_statuses`/`status`, a `success` status for `context: ci/integration` authenticated by attacker-controlled repo A is written onto any `Commit` row in the `commits` table that happens to share the same `sha`, including one belonging to victim stack B, flipping B's blocking/deployability state.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:
`commit.stack.repository == webhook.repository_owner/repository_name` for every `Commit` mutated by a given webhook. In `StatusHandler`, this equality is never enforced.

Code path:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches by `X-Github-Event` header to `Shipit::Webhooks.for_event(event)` handlers, calling `handler.call(params)` [1](#0-0) .
- `verify_signature` only checks that the payload's `X-Hub-Signature` matches the HMAC secret configured for `Shipit.github(organization: repository_owner)` — i.e., it authenticates that the payload came from GitHub for *that* organization/app, not that the `sha` inside the payload is scoped to *that* repository [2](#0-1) . Any repository owner who is a Shipit-enabled GitHub App/org member can legitimately sign and send arbitrary `status` payloads for their own repo, including an arbitrary `sha` value they choose (e.g. a SHA copied from a public commit that also happens to exist as a commit in victim stack B, or — more directly — any SHA collision across repos since `sha` is attacker-supplied plaintext in the JSON body, not derived from repo identity).
- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query has no `stack_id`/repository filter at all, unlike the base `Handler` class which does provide a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` [4](#0-3)  — `StatusHandler` simply never uses that helper.
- `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, writing a `Status` row tied to whatever `stack_id` the matched `Commit` belongs to [5](#0-4) .
- `Commit#blocked?` walks `stack.commits.reachable...any?(&:blocking?)` and `#deployable?` gates on `success? && !blocked?` [6](#0-5) , both driven purely by the `Status` rows just written. `add_status` also triggers `stack.schedule_merges` when the new status becomes `success`/`pending` [7](#0-6) , directly feeding continuous-delivery/merge logic for the victim stack.

Attacker request: a `status` event JSON body with `repository.owner.login`/`repository.full_name` set to a repo the attacker legitimately controls (so `verify_signature` passes), and `sha` set to a value that also exists as a `Commit.sha` row for victim stack B (any two Shipit-tracked stacks that ever share a commit SHA — e.g. shared submodule commits, cherry-picks, monorepo forks, or a git history graft — are affected), with `context: ci/integration`, `state: success`.

Existing guards do not stop this: `verify_signature` checks signer authenticity for the *sending* repo only, not `sha` ownership; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape; there is no `stacks`/`repository_name` scoping applied in `StatusHandler#process`.

### Impact Explanation
A payload authenticated for repository A writes a `Status` row against a `Commit`/`Stack` belonging to repository B, changing B's `blocked?`/`deployable?` state and potentially triggering `stack.schedule_merges` (continuous delivery) for B — this is a cross-tenant/cross-repository state mutation matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The attacker can repeat this against any stack/commit combination that shares a SHA with a repo they control, and the effect (forcing `ci/integration: success`) can force a blocked-then-shippable transition or, symmetrically, plant a blocking failure status to block a victim's deploys.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository (any account) onboarded to the same Shipit instance/GitHub App configuration so `verify_signature` succeeds for their own org, and a SHA value that collides with a `Commit` row already tracked for the victim stack. Cost is low — sending a signed webhook from one's own repo is normal usage; the only non-trivial requirement is a shared SHA, which naturally occurs with forked/cherry-picked/shared-history repositories tracked by the same Shipit install, or can be engineered by pushing a commit with an identical tree/parent/timestamp to reproduce a target SHA is impractical in general, but any repo pair with actual shared history (forks, submodule syncs, monorepo splits) makes this trivially repeatable.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the repository that authenticated the webhook, mirroring the `stacks`/`repository_name` helper already present in the base `Handler` class, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through `Stack`→`Repository` filtered by `repository_name` from the payload, instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest outline:
```ruby
test "success status for ci/integration on unrelated repo's SHA does not affect victim stack" do
  attacker_stack = shipit_stacks(:shipit) # repo A
  victim_stack   = shipit_stacks(:cyclimse) # repo B, blocking_statuses configured requiring ci/integration
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker's own commit")

  before = victim_commit.reload.blocked?

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/integration',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = victim_commit.reload.blocked?
  assert_equal before, after, "victim stack's blocked? must not change from attacker-authenticated repo's webhook"
end
```
This currently fails (state diverges) because `StatusHandler#process` matches `victim_commit` too via the bare `sha` lookup.
