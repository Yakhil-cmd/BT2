### Title
Signature verification org (`repository.owner.login`) is not cross-checked against the handler resolution org (`repository.full_name`), allowing a cross-tenant `stack.sync_github` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` derives the verification organization solely from `params.dig('repository','owner','login')` and validates the HMAC against that org's secret, but `Handler#stacks`/`Handler#repository_name` resolves the target `Repository` independently using `payload.dig('repository','full_name')`. Because these two unsigned/attacker-controlled fields are never cross-checked, an attacker who controls `org-attacker`'s webhook secret can sign a payload where `repository.owner.login = 'org-attacker'` (so verification passes) while `repository.full_name = 'org-victim/private-repo'` (so `PushHandler` mutates a stack belonging to a different tenant).

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`organization_whose_secret_verified_signature (derived from repository.owner.login)` == `organization_owning_the_repository_the_handler_mutates (derived from repository.full_name)`

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- If verification succeeds, `#create` parses the raw body and dispatches to handlers such as `PushHandler`. [3](#0-2) 
- `PushHandler#process` calls `stacks` (inherited from `Handler`), which resolves the repository via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature verification. [4](#0-3) [5](#0-4) 
- `Repository.from_github_repo_name` splits `owner/name` from `full_name` and looks up the `Repository` record purely by that string, with no reference back to `repository.owner.login`. [6](#0-5) 

Root cause: the controller-level authentication decision (which org's secret must match) and the handler-level target resolution (which org's repository/stack gets mutated) are computed from two independent, both attacker-supplied, JSON fields (`repository.owner.login` vs `repository.full_name`) with no consistency check between them.

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/private-repo"
  }
}
```
signed with `X-Hub-Signature` computed using `org-attacker`'s own known `webhook_secret` over this exact raw body.

Exploit flow: `verify_signature` resolves `repository_owner = "org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and successfully verifies the HMAC because the attacker legitimately owns that secret. `#create` then invokes `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("org-victim/private-repo")` — an entirely different tenant's repository — and calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack on that branch.

No existing guard prevents this: `verify_signature` only checks the HMAC against the org named in `repository.owner.login`; it never compares that org to the owner segment of `repository.full_name`. `drop_unhandled_event` and `ExplicitParameters` (`requires :ref`, `requires :after` in `PushHandler`) only validate presence/shape of fields, not cross-field consistency. `Repository.from_github_repo_name` performs no authorization check — it is a straightforward lookup by owner/name.

### Impact Explanation
An attacker who owns a Shipit-connected repository/organization (with a known `webhook_secret`) can force `Stack#sync_github` to run against any other tenant's stack whose repository they can name (`org-victim/private-repo`), as long as that Repository record exists in Shipit. This is a cross-repository/cross-tenant write triggered by a payload signed with the wrong org's secret relative to the actual mutation target — matching the "Critical: a payload for one repository mutating another's stack" category. The attack is repeatable against any repository/stack combination the attacker can guess or discover (repository full names are often public/predictable), and is not limited to a single push — every subsequent forged webhook can retrigger `sync_github` with attacker-chosen `expected_head_sha` values.

### Likelihood Explanation
Preconditions are exactly as stated by the attacker model: attacker must own an organization/repository already connected to this Shipit instance with a known `webhook_secret`, and must know or guess the full_name of an existing target Repository record (e.g., `org-victim/private-repo`) that has non-archived stacks. No Shipit session, API token, or victim secret is required. Constructing the HMAC is trivial since the attacker owns their own secret and can sign arbitrary bytes. This is a low-cost, fully repeatable attack requiring only knowledge of the target's repository name.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), cross-check that the organization used to verify the signature is the same as the organization referenced by every field the handler will use to resolve state — e.g., compare `params.dig('repository','owner','login')` against the owner segment of `params.dig('repository','full_name')` and reject (`head(422)`) on mismatch before dispatching to handlers. Alternatively, have `Handler#repository_name` derive the owner exclusively from the already-verified `repository_owner`, rather than trusting the unrelated `full_name` field, and validate that `full_name`'s owner segment matches.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb`:

```ruby
test "push with mismatched owner.login and full_name mutates a different tenant's stack" do
  # Repository 'org-victim/private-repo' with a stack exists in fixtures/factories.
  victim_repo = Shipit::Repository.create!(owner: 'org-victim', name: 'private-repo')
  victim_stack = shipit_stacks(:shipit) # or a factory stack owned by victim_repo
  victim_stack.update!(repository: victim_repo, branch: 'master')

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: {
      owner: { login: 'org-attacker' },
      full_name: 'org-victim/private-repo'
    }
  }.to_json

  # Stub verification so it succeeds only for org-attacker's secret (simulating attacker
  # legitimately signing with their own known secret).
  Shipit.github(organization: 'org-attacker').expects(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=attacker-computed-signature'

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeef')

  post :create, body: body, as: :json
  assert_response :ok
end
```
Assertions on both sides of the binding: `repository_owner` used for verification == `'org-attacker'` (verified via secret ownership) while the repository actually mutated == `'org-victim/private-repo'` (via `sync_github` expectation on `victim_stack`), demonstrating the two are not equal, yet the mutation still occurs.
