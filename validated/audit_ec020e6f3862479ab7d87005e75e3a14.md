Based on my investigation, I found a concrete analog in this repo's `gh skill install` upstream-redirect logic. `ParseRepoURL` uses `ghrepo.FromFullName`, which is not restricted to `SupportedHost = "github.com"`, and the recursive `installRun` call re-validates the host via `source.ValidateSupportedHost`, which accepts `*.ghe.com` tenancy hosts in addition to github.com — so this is not a full host-allowlist bypass, but the redirect is entirely driven by attacker-controlled content.

### Title
Skill install silently follows attacker-controlled repository redirect based on unauthenticated content in `SKILL.md` metadata - ([File: pkg/cmd/skills/install/install.go])

### Summary
`gh skill install` inspects the `github-repo` frontmatter field of a fetched `SKILL.md` file and, when it differs from the repository the user explicitly requested, treats it as an "upstream" and can redirect the entire install (files, tree SHA, ref) to that attacker-named repository — a target chosen solely by the content of the skill being installed, not by the user.

### Finding Description
`checkUpstreamProvenance` in `pkg/cmd/skills/install/install.go` fetches the `SKILL.md` blob for the skill the user asked to install and parses its YAML frontmatter for a `metadata.github-repo` key [1](#0-0) . If that value differs from the requested repo, the function treats it as "upstream" and, depending on flags/interactivity, returns a different `ghrepo.Interface` to install from [2](#0-1) . Back in `installRun`, this redirect target fully replaces `opts.repo`/`opts.SkillSource`, clears the pin/version, and recursively calls `installRun(opts)` to install from the new repo [3](#0-2) .

The redirect target string is parsed with `source.ParseRepoURL`, which only validates that the string is a syntactically valid `owner/repo` (via `ghrepo.FromFullName`) — it does not restrict the value to a known-good or previously-trusted host or repo [4](#0-3) . The only later check is `source.ValidateSupportedHost`, which is a hostname allowlist (`github.com` and `*.ghe.com` tenancy), not an ownership/repo trust check [5](#0-4) . This means any repository the attacker publishes on a supported host can nominate itself, via its own `SKILL.md` metadata, as a redirect target for the install pipeline.

When `--upstream` is explicitly passed, the redirect happens with no further confirmation [6](#0-5) . In non-interactive mode without `--upstream`, the tool stays on the re-publisher and only prints a notice [7](#0-6) . In interactive mode the user is shown a two-choice prompt naming both repos before any redirect [8](#0-7) .

### Impact Explanation
This mirrors the report's underlying bug class: an operation with real consequences (fetching and writing files from a repository, i.e., "deploying" untrusted content) is triggered based on a condition embedded in attacker-supplied data rather than the user's explicit, informed choice of target. Here, the "target" of a `gh skill install <repo>` invocation can be silently substituted for a different, attacker-named repository whenever `--upstream` is used, or the install proceeds from the original repo but the tool already displayed content sourced from the attacker's frontmatter. Because installed skills are unverified content that "may contain prompt injections, hidden instructions, or malicious scripts" (the tool's own disclaimer) [9](#0-8) , an attacker who controls the SKILL.md metadata of one repo can steer installs toward another repo of their choosing.

### Likelihood Explanation
Exploitation requires the user to run `gh skill install owner/repo skill --upstream`, or to accept the interactive redirect prompt after being shown the upstream repo name; a fully "silent" redirect without any user signal only occurs when `--upstream` is explicitly set. This is a real but flag-gated/consent-adjacent path rather than a fully automatic no-consent redirect (the CLI does show the target repo name before/at the point of redirect in most modes), which lowers exploitation likelihood.

### Recommendation
Require explicit user confirmation of the exact upstream owner/repo before redirecting, even when `--upstream` is passed (e.g., show the resolved target and require a `--yes`/confirm step), and consider binding upstream redirects to a repository trust anchor (e.g., only allow redirects to repos previously installed from, or require the user to pass the target repo explicitly) rather than trusting arbitrary `github-repo` frontmatter values.

### Proof of Concept
1. Publish a skill repository `attacker/bait-skills` containing a `SKILL.md` with `metadata.github-repo: https://github.com/attacker/evil-skills`.
2. Victim runs `gh skill install attacker/bait-skills some-skill --upstream`.
3. `checkUpstreamProvenance` detects the mismatch and immediately returns `attacker/evil-skills` as the redirect target [6](#0-5) .
4. `installRun` recurses with `opts.repo` replaced by `attacker/evil-skills`, discarding the originally requested pin/version [10](#0-9) , and installs whatever content that repository serves.

// ParseRepoURL parses a repository URL stored in skill metadata.
func ParseRepoURL(raw string) (ghrepo.Interface, error) {
	raw = strings.TrimSpace(raw)
	if raw == "" {
		return nil, fmt.Errorf("repository URL is empty")
	}

	repo, err := ghrepo.FromFullName(raw)
	if err != nil {
		return nil, fmt.Errorf("invalid repository URL %q: %w", raw, err)
	}

	return repo, nil
}

// ValidateSupportedHost rejects hosts that are not supported.
// Supported hosts are github.com and GHEC with data residency (*.ghe.com).
// GitHub Enterprise Server is not currently supported.
func ValidateSupportedHost(host string) error {
	host = normalizeHost(host)
	if host == "" {
		return fmt.Errorf("could not determine repository host")
	}
	if host == SupportedHost || ghauth.IsTenancy(host) {
		return nil
	}
	if ghauth.IsEnterprise(host) {
		return fmt.Errorf("GitHub Skills does not currently support GitHub Enterprise Server; got %s", host)
	}
	return fmt.Errorf("unsupported host for GitHub Skills: %s", host)
}
