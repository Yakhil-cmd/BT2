### Title
Attacker-created low-liquidity oscript AMM AA can be atomically manipulated within a single trigger unit to feed a false spot price to any dependent AA reading its `balance[]` - (File: formula/evaluation.js, aa_composer.js)

### Summary
Obyte allows anyone to permissionlessly define an Autonomous Agent (AA) implementing a constant-product AMM whose "price" is simply derived from its own live balances (`balance[$asset]`, `balance[base]`), as illustrated by the bundled `uniswap_like_market_maker.oscript` sample. Any other AA (e.g., a lending/collateral AA) that treats `balance[some_AA_address][asset]` as an external price oracle is exposed to the same class of risk described in the external report: an attacker can spin up a brand-new, self-funded, negligible-liquidity market-maker AA and, within one atomic multi-message trigger unit, distort its balance ratio and have a dependent AA consume that distorted "price" before anyone else can trade against (arbitrage) the pool.

### Finding Description
The `balance` operator in `formula/evaluation.js:1480-1528` lets any AA formula read the *current, in-flight* balance of *any* address, including another AA that is mid-way through processing the very same trigger unit's cascade. Obyte's secondary-trigger mechanism in `aa_composer.js:1702-1757` (`handleSecondaryTriggers`) processes every AA reachable from a single trigger unit's outputs synchronously, within the same MCI-stabilization pass (`main_chain.js:1691-1723`, `writer.js:724-737`), before the unit or any of its state effects are visible to the rest of the network. This means a single unit can:
1. Pay a small, attacker-chosen amount into an attacker-deployed, low-liquidity AMM AA (structured like `uniswap_like_market_maker.oscript`), which updates that AA's `balance[base]`/`balance[$asset]` ratio (its "spot price") via `$p = $asset_balance * $bytes_balance` style formulas.
2. In the same trigger unit, trigger a second, independent AA (e.g. a lending/collateral AA) whose formula reads `balance[attacker_amm_address][asset]` (or similar) to value collateral or determine loan terms.
3. Because both steps execute as part of one atomic secondary-trigger cascade with no intervening unit from any other party, there is no opportunity for a third party to arbitrage the AMM's price back before the dependent AA consumes it — mirroring the "cannot be arbed within one transaction" scenario in the original report.

This is architecturally analogous to the Paraspace/Uniswap V3 bug: the underlying primitive (`balance[]`) supplies an instantaneous, unweighted, fully attacker-controllable "price" with no minimum-liquidity or time-weighting safeguard, and Obyte's synchronous secondary-trigger execution model provides exactly the single-atomic-step guarantee that made the flash-loan-style attack effective in the original report.

### Impact Explanation
Any AA design (lending, collateralized stablecoin, insurance, etc.) that consumes `balance[]` of another, permissionlessly-creatable AMM-style AA as a price feed can be drained: the attacker inflates or deflates the apparent price during the atomic cascade, extracts an outsized loan/output from the dependent AA, and reverts the AMM's ratio afterward (or simply abandons the now-hollowed-out AMM), leaving the dependent AA under-collateralized. This can cause direct, unrecoverable fund loss in any AA built on top of ocore that follows this common, ocore-endorsed (per the bundled sample) design pattern.

### Likelihood Explanation
Likelihood is Medium: it requires a second, victim AA to actually use another AA's live `balance[]` as a price oracle rather than its own state — a design choice made by application/AA authors, not a bug purely in ocore's validation logic. However, since ocore's own bundled sample (`uniswap_like_market_maker.oscript`) demonstrates and popularizes exactly this "price = balance ratio" pattern for building DEX-style AAs, and nothing in `evaluation.js`'s `balance` opcode or `aa_composer.js`'s trigger-cascade logic warns against or restricts cross-AA balance reads as a price source, the underlying primitive is dangerous by default and likely to be reused unsafely by third-party AA developers.

### Recommendation
- Document prominently (and ideally warn at AA-validation time, `aa_validation.js`) that `balance[other_AA]` should never be treated as a manipulation-resistant price oracle, since it can be fully attacker-controlled and manipulated atomically within a single trigger-unit cascade.
- Encourage/require dependent AAs to use manipulation-resistant sources (posted `data_feed` values from trusted oracle addresses, or an AA's own accumulated/time-weighted state rather than another AA's instantaneous balance) when valuing collateral.
- Consider providing built-in primitives for TWAP-like or minimum-liquidity-checked price feeds so application-level AAs are not tempted to rely on raw `balance[]` ratios from other, arbitrarily-creatable AAs.

### Proof of Concept
1. Attacker defines and deploys `MM_AA`, a constant-product market-maker AA modeled directly on `test/samples/uniswap_like_market_maker.oscript:102-120`, seeded with only a small amount of `base` and `$asset` (e.g., 1 unit of `$asset` and a negligible amount of `base`), so it is fully attacker-controlled.
2. Attacker constructs a single unit with:
   - Message 1: payment to `MM_AA` that swaps a large trigger amount of `base` for `$asset` (per the "exchange bytes to asset" case), driving `balance[MM_AA][base]` / `balance[MM_AA][$asset]` far from any external market rate.
   - Message 2: payment to `Victim_Lending_AA`, whose formula includes something like `$price = balance[MM_AA][base] / balance[MM_AA][$asset]` (or equivalent) to value `$asset` collateral and compute a loan payout in `base`.
3. `aa_composer.js`'s `handleSecondaryTriggers` (`aa_composer.js:1702-1757`) processes both AA responses synchronously within the same trigger-unit cascade (per `main_chain.js:1691-1723`), so `Victim_Lending_AA` reads the already-manipulated `MM_AA` balance before any other party's unit can arbitrage `MM_AA` back to a fair price.
