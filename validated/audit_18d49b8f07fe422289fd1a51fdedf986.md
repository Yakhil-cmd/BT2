### Title
Unauthenticated RPC Injection via Bridge P2P `ServiceChainCall` Message — (File: `node/sc/main_bridge_handler.go`)

### Summary
The main bridge's `handleCallMsg` function writes arbitrary P2P message payloads directly to the internal RPC server pipe without verifying the sender's authorization. The bridge peer handshake validates only `NetworkId` and `ProtocolVersion`, so any node that can reach the main bridge P2P port can inject arbitrary JSON-RPC calls into the parent-chain RPC server.

### Finding Description

In `node/sc/main_bridge_handler.go`, `handleCallMsg` (lines 86–102) handles the `ServiceChainCall` P2P message code by decoding the raw payload and writing it verbatim to `mbh.mainbridge.rpcConn` — the pipe to the main bridge's internal RPC server:

### Impact Explanation

Any node that can reach the main bridge P2P port, knows the `networkId`, and speaks the `servicechain/2` protocol can:

1. Connect and pass the handshake (no node-ID whitelist).
2. Send a `ServiceChainCall` message containing an arbitrary JSON-RPC payload.
3. Have that payload written to the main bridge's internal RPC pipe and executed by the parent-chain RPC server.

Depending on which RPC namespaces are exposed on that pipe (typically IPC-level, which includes `admin`, `debug`, and all other namespaces), the attacker can invoke methods such as `admin_addPeer`, `admin_removePeer`, `debug_*`, or any other method available on the parent-chain node — without holding any key or credential. This constitutes unauthorized privilege escalation over the bridge/parent-chain node's protected RPC surface.

### Likelihood Explanation

The main bridge P2P port is a network-accessible endpoint. The RLPx transport authenticates the peer's *identity* (node key) but the application layer imposes no whitelist. Any attacker who can generate a node key (trivial) and reach the port network-wise can exploit this. The `ServiceChainCall` message code is documented in the public protocol file.

### Recommendation

1. Maintain an explicit whitelist of authorized child-chain node IDs in the main bridge. Reject `ServiceChainCall` messages from peers whose node ID is not in the whitelist.
2. Alternatively, require the child-chain peer to prove ownership of a pre-registered address (e.g., via a signed challenge during handshake) before forwarding any RPC data.
3. At minimum, validate that the `chainID` received during the bridge handshake matches the configured child-chain ID before accepting privileged message codes.

### Proof of Concept

```
1. Attacker generates a fresh node key (any ECDSA key).
2. Attacker connects to the main bridge P2P port (publicly reachable).
3. Attacker completes the bridge handshake:
      ProtocolVersion = 2  (servicechain/2)
      NetworkId       = <parent chain network ID>   ← only checks performed
4. Attacker sends a P2P message with code ServiceChainCall (0x06)
   whose payload is a valid JSON-RPC request, e.g.:
      {"jsonrpc":"2.0","method":"admin_addPeer","params":["enode://attacker@..."],"id":1}
5. MainBridgeHandler.handleCallMsg() decodes the payload and writes it
   verbatim to mbh.mainbridge.rpcConn (the internal RPC pipe).
6. The parent-chain RPC server executes the call with no further
   authentication, returning the result to the attacker via
   ServiceChainResponse.
```

func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
	logger.Trace("mainbridge writes the rpc call message to rpc server", "msg.Size", msg.Size, "msg", msg)
	data := make([]byte, msg.Size)
	err := msg.Decode(&data)
	if err != nil {
		logger.Error("error in mainbridge message handler", "err", err)
		return err
	}

	// Write to RPC server pipe
	_, err = mbh.mainbridge.rpcConn.Write(data)
	if err != nil {
		logger.Error("failed to write to the rpc server pipe", "err", err)
		return err
	}
	return nil
}

	}
