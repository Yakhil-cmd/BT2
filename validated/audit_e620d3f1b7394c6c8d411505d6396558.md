### Title
CCMenu API endpoint bypasses stack-scoped ApiClient authorization, allowing read of any stack's state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` establishes a binding between what a stack-scoped `ApiClient` token is authorized to read and what stack data it can actually touch: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack, and the default `stack` method resolves the target stack through that scoped relation (`stacks.from_param!(params[:stack_id])`), as seen in `Shipit::Api::StacksController#stack`. `Shipit::Api::CCMenuController` overrides this and resolves the stack directly against the unscoped `Stack` model — `Stack.from_param!(params[:stack_id])` — breaking the equality `client.authorized_stack == stack_acted_on`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`CCMenuController` only enforces the coarse permission check `require_permission :read, :stack`, which verifies the `ApiClient` has the `read:stack` permission string but never checks *which* stack it is scoped to. [4](#0-3) 
The fine-grained restriction is supposed to come from `BaseController#stack`, which resolves the target through the `stacks` helper — itself filtered to `current_api_client.stack_id` for scoped clients. [1](#0-0) 
However, `CCMenuController` privately redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, entirely bypassing the `stacks` scoping method. [3](#0-2) 
This is exactly the same class of bug as the oracle report: a value (`stack_id`) that the token *authorizes* is checked at issuance/permission time, but the value actually *used* at data-access time is taken from an unchecked, attacker-controlled input (`params[:stack_id]`), so the two are never re-verified to match. `Shipit::CCMenuUrlController` is a normal, real-world source of such scoped tokens: it creates an `ApiClient` with `permissions: %w[read:stack]` bound to one specific stack for embedding in third-party CI dashboard tools. [5](#0-4) 

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-only `ApiClient` token (e.g. a CCMenu URL shared with a third-party CI status widget, an intern's dashboard integration, etc.) can query `/api/stacks/:stack_id/cc.xml` with an arbitrary `stack_id` for any stack in the Shipit instance — not just the one the token was issued for. The response leaks stack name, deploy activity, last build status/label/time, lock status, and `webUrl`, and is rendered via `render('shipit/ccmenu/project', ...)` using data pulled from `stack.deploys_and_rollbacks`. This is an unauthenticated (from the perspective of the target stack) read of stack state/deploy output across repository boundaries, matching the "High" impact bucket of "unauthenticated read of stack state, task streams or deploy output." [6](#0-5) 

### Likelihood Explanation
Likelihood is high: exploitation requires only a valid, low-privilege, single-stack-scoped `read:stack` token (which is the exact kind of token the engine's own `CCMenuUrlController` mints and is designed to be embedded in external tools/URLs) and changing one query parameter (`stack_id`). No signature bypass, timing race, or privileged access is needed — the scoping check is simply absent for this one controller. [7](#0-6) 

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` helper (i.e. `stacks.from_param!(params[:stack_id])`) exactly as `StacksController#stack` and the `BaseController` default do, so a stack-scoped `ApiClient` can never read data for a stack outside its `stack_id`. [2](#0-1) 

### Proof of Concept
1. As a legitimate user, visit `CCMenuUrlController#fetch` for `stack_id=stack-A`; the engine creates/reuses an `ApiClient` named "CCMenu Client" with `permissions: %w[read:stack]` and `stack: stack-A`, and returns a URL containing `?token=<authentication_token>`. [8](#0-7) 
2. Take that `token` (scoped only to `stack-A`) and call `GET /api/stacks/stack-B/cc.xml?token=<token>` instead.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (token validity is independent of stack scope), and `require_permission :read, :stack` passes because the client does have `read:stack` permission. [9](#0-8) 
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` to `stack-B` regardless of the client's `stack_id` binding to `stack-A`, and the controller renders `stack-B`'s deploy/build status in the XML response — data the token was never authorized to see. [10](#0-9)
