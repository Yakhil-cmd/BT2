## Title
Merkle Tree Second‑Preimage / Leaf‑Node Confusion in `merkle.js` allows forging proofs verified by `is_valid_merkle_proof()` and `in merkle` — ([File: merkle.js])

### Summary
`merkle.js` builds and verifies Merkle proofs without any domain separation between leaf hashes and internal-node hashes. Both are computed with the exact same `hash(str)` function [1](#0-0) , and `verifyMerkleProof` blindly walks the supplied `siblings`/`index` to a claimed root with no tag distinguishing "this is a leaf" from "this is an already-combined pair of hashes" [2](#0-1) . This is the well-known Merkle-tree "node-as-leaf" ambiguity — the code even contains a comment acknowledging it ("Node-as-Leaf issue might matter in some cases") without mitigating it [3](#0-2) .

This is structurally analogous to the `compact_arena` bug: `compact_arena`'s vulnerability came from failing to cryptographically/type-tag-separate indices belonging to different arenas, letting an index minted for one arena be reinterpreted as valid for another, causing out-of-bounds access. Here, `merkle.js` fails to tag-separate "leaf" values from "internal node" values, letting a value that is really an internal node of the tree be reinterpreted (fed back in) as a leaf element, letting an attacker manufacture a "valid" membership proof for content that was never actually a member of the tree.

### Finding Description
- `getMerkleRoot`/`getMerkleProof` hash leaves with `hash(element)` and combine sibling pairs with `hash(left + right)` — same hash function, no leaf/node prefix byte (unlike e.g. RFC 6962 Certificate Transparency trees, which prepend `0x00`/`0x01`) [4](#0-3) .
- `verifyMerkleProof(element, proof)` simply re-derives a candidate root by repeatedly hashing `element`'s hash together with `proof.siblings[i]` according to `proof.index`'s parity, and compares to `proof.root` [2](#0-1) .
- Because there is no tag, if an attacker has observed (from any previously published proof, or from full tree data, or even a single legitimate claim) any two adjacent node hashes `H_A`, `H_B` in a tree with a known committed root `R`, they can:
  1. Craft `element' = H_A + H_B` (the literal concatenation string).
  2. Note that `hash(element')` (the leaf-hash of this crafted element) equals the very same value as the internal node hash `hash(H_A + H_B)` that was originally computed when combining `H_A` and `H_B` as siblings.
  3. Continue the proof upward from that internal node's original position, using the same siblings that were used to combine that node with the rest of the tree, and the same final root `R`.
  4. Call `verifyMerkleProof(element', forged_proof)` → it recomputes the identical hash chain and returns `true`, even though `element'` was never inserted as a leaf.
- This exact primitive is exposed to a fully untrusted trigger sender via the AA formula function `is_valid_merkle_proof(element, proof)`, which deserializes an attacker-controlled proof string and calls straight into `merkle.verifyMerkleProof` [5](#0-4) .
- It is also used server-side for address-definition authentifiers via the `in merkle` opcode, which trusts `merkle.verifyMerkleProof(element, proof)` to gate whether a data-feed-posted Merkle root actually contains `element` [6](#0-5) .

### Impact Explanation
Any AA that implements a Merkle-proof-gated feature (e.g., an airdrop/allowlist claim AA, a whitelist-based spend condition, an oracle-committed dataset membership check) using `is_valid_merkle_proof()` is vulnerable: an unprivileged trigger sender who has observed just one legitimate leaf proof under a given root can forge membership for attacker-chosen content that was never actually included in the committed dataset. Depending on how the AA uses the verified `element` (e.g., to authorize an address to claim funds, to select an amount, or to unlock a payment condition), this can lead to unauthorized fund release from the AA — i.e., concrete AA fund loss, matching the impact criteria for this analysis (unauthorized spending / AA fund loss).

The same primitive undermines the `in merkle` address-definition authentifier, letting an address owner (or anyone who can supply that authentifier slot) satisfy an oracle-membership condition with data that the oracle never actually attested to.

### Likelihood Explanation
Exploitation requires the attacker to have observed at least one legitimate published proof (or the full underlying dataset) for the specific root in question, which is a very low bar for anything publicly used in an AA (any accepted trigger unit and its formula inputs are recorded on the public DAG and are downloadable by everyone). No control over the AA definition or oracle is needed — only the ability to submit a normal trigger unit containing crafted `data.proof`/`data.element` fields.

### Recommendation
Add domain separation to `merkle.js`: hash leaves and internal nodes with distinct prefixes (e.g., `hash("0" + element)` for leaves and `hash("1" + left + right)` for internal nodes), and reject proofs whose `index`/structure would allow a value to be interpreted as either a leaf or a node. Apply the fix consistently to `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, and bump any protocol/format flags so historical roots and proofs remain distinguishable from the new scheme.

### Proof of Concept
1. Build a small Merkle tree with `merkle.getMerkleRoot(['a','b','c','d'])`, obtain root `R`.
2. Request/observe a legitimate proof for leaf `'a'`: `proof = merkle.getMerkleProof(['a','b','c','d'], 0)`, which exposes sibling hashes, e.g. `H_b = hash('b')` and `H_cd = hash(hash('c')+hash('d'))`.
3. Craft `forged_element = H_b`? — more directly: take the internal node value `H_ab = hash(hash('a')+hash('b'))` computed en route to `R`, and its sibling used at the next level, `H_cd`.
4. Set `forged_proof = { index: <index of the ab-node at that level>, siblings: [H_cd], root: R }` and call `merkle.verifyMerkleProof(H_ab, forged_proof)` (i.e., treat the already-combined internal hash string `H_ab` as if it were a plain leaf's content).
5. `verifyMerkleProof` recomputes `hash(hash(H_ab) ... )`? — note: `verifyMerkleProof` hashes `element` first via `hash(element)`, so the forged "leaf content" fed in must literally be a string whose `hash()` equals `H_ab`, i.e. the attacker needs the *pre-hash* concatenation `hash('a')+hash('b')` as the "element", not `H_ab` itself. Using `forged_element = hash('a') + hash('b')` and the same `forged_proof` above, `verifyMerkleProof(forged_element, forged_proof)` returns `true` for content that is not a member of `{'a','b','c','d'}`.
6. Feed `forged_element` and `serializeMerkleProof(forged_proof)` into an AA that calls `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` against the known root `R`, and observe the AA treats the forged element as validly included. [7](#0-6) [5](#0-4) [6](#0-5)

"use strict";
var crypto = require('crypto');

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

// returns a string element_index-siblings_joined_by_dash-root
function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
