### Title
RAY value overflow during interest accrual permanently freezes a market — no repay, withdraw, or liquidate can execute - (File: common/src/rates/index.rs via contracts/pool/src/interest.rs)

### Summary
The MySQL Optimizer crash/hang bug class maps onto XOXNO Lending as a permanently-reverting arithmetic panic inside mandatory interest accrual. Every state-changing pool verb runs `global_sync` before mutating, and accrual computes the market's borrowed value as `scaled_debt × borrow_index` in the RAY (`i128`) domain. When that product exceeds `i128::MAX`, `accrue_step` panics with `MathOverflow`, and because accrual precedes every operation, the market becomes unrecoverable: repayments, withdrawals, liquidations, and bad-debt cleanup all revert. The borrow-index ceiling (`MAX_BORROW_INDEX_RAY = 10^36`) never engages because the value multiplication overflows first.

### Finding Description
`interest::global_sync` (`contracts/pool/src/interest.rs:20`) runs unconditionally inside `Cache::load`-based entrypoints, splitting elapsed time into chunks and calling `accrue_chunk`, which invokes `accrue_step` (`contracts/pool/src/interest.rs:39-53`). `accrue_step` computes accrued debt via `scaled_to_original` (scaled shares × index) with checked `i128`/`I256` arithmetic that raises `GenericError::MathOverflow` on an unrepresentable result (`common/src/math/fp.rs:12-16`, `docs/reference/formulas.md:20-24`).

The admitted arithmetic domain is documented in `docs/reference/formulas.md:421-437`: token-to-RAY input maximum is `i128::MAX / 10^(27-d)` (~170 billion whole tokens at 18 decimals), indexes start at RAY and are capped at 10^36, but "accrued position values and market totals must independently fit the RAY domain; valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates the full exploit end-to-end: an 18-decimal market seeded with 10^9 whole tokens at ~98% utilization on the XLM-style steep rate curve hits `MathOverflow` inside `update_indexes` while `borrow_index < MAX_BORROW_INDEX_RAY`, after which `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` — "the market is frozen: no repay, no withdraw, no liquidation."

The path is reachable by a single unprivileged address: `supply` (no price needed), `borrow` (with its own collateral in a second market), and the permissionless `update_indexes` (`docs/reference/endpoints.md:37`) are all in the allowed entrypoint set. The attacker does not need to trigger the final panic itself — once the book is oversized, ordinary time-based accrual crosses the cliff and every subsequent transaction on the market reverts.

### Impact Explanation
Permanent freezing of funds for all suppliers and borrowers in the affected market. Once `scaled_borrowed × borrow_index` overflows during `accrue_step`, `global_sync` panics before any verb's mutation phase, so: suppliers cannot `withdraw`, borrowers cannot `repay`, liquidators cannot `liquidate` positions whose risk depends on that market, `clean_bad_debt` cannot socialize losses, and `claim_revenue` cannot pay the accumulator. The freeze is unrecoverable — there is no admin verb that bypasses accrual or rewinds the index, so the market's token funds held by the pool are permanently locked. The panic persists across calls, matching the CVE's "frequently repeatable crash / complete DOS" shape, but with permanent rather than restartable effect.

### Likelihood Explanation
Medium. The attacker must supply a very large book (~10^9 whole units of a high-decimals token — feasible for large-supply assets) and drive utilization near the steep segment of the rate curve by borrowing most of it, both ordinary unprivileged operations within configured caps (caps admit up to the same ~170-billion-token domain). The condition then develops through normal interest accrual over an extended period at sustained high utilization — no privileged action, oracle manipulation, or timing race is required, and `update_indexes` lets anyone force accrual attempts. The likelihood is bounded by the capital required and by the need for sustained high utilization, but there is no code path that recovers the market once the cliff is crossed, and governance cannot retroactively shrink caps to save an already-oversized book.

### Recommendation
Cap the accrual arithmetic rather than letting it panic: in `accrue_step`/`scaled_to_original`, saturate the accrued value or clamp `borrow_index` at `MAX_BORROW_INDEX_RAY` *before* the value multiplication overflows, so accrual degrades gracefully (interest stops growing) instead of bricking the market. Alternatively, enforce a market-level value cap in `Cache`/spoke-usage accounting so that `borrowed × index` can never approach `i128::MAX` — the existing borrow/supply caps bound token inputs, not the grown RAY value, so a cap check against projected post-accrual value would need to be added in `guards` or `apply_entry` (`contracts/controller/src/spoke.rs`, exercised by the overflow test at `controller/tests/spoke.rs:286-313`).

### Proof of Concept
Adapted from `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Attacker seeds a whale book unprivileged:
let principal = BILLION * 10i128.pow(18);          // ~1e9 whole tokens
t.supply_raw(BOB, "BIG18", principal);             // attacker as supplier
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization

// Anyone (attacker or any keeper) pokes accrual each year:
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // -> MathOverflow
}

// Permanent freeze: all verbs accrue first and hit the same panic.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// borrow_index never reached MAX_BORROW_INDEX_RAY — the value cliff hit first.
```

Root cause: `accrue_chunk` → `accrue_step` multiplies scaled debt by the index in checked RAY arithmetic (`contracts/pool/src/interest.rs:39-53`); because `global_sync` precedes every market mutation (`contracts/pool/README.md:159-168`), the resulting `MathOverflow` panic permanently blocks all exit, repayment, liquidation, and cleanup paths for the market.
