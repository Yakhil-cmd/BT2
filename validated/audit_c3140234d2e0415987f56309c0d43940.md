### Title
Payment messages that mix an "issue" input with "transfer" inputs bypass the asset's `transfer_condition` entirely - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` decides which spending condition to enforce for an *entire* payment message using a single boolean `bIssue`, set once from the (at most one, first-position) issue input. When a payment message mixes an issue input together with transfer inputs, only `issue_condition` is evaluated and `transfer_condition` is skipped for the outputs actually being moved from existing (transferred) coins, exactly mirroring the reported analog: one privileged action path enforces the intended authorization ("removeFromOffice" gated by `onlyRole`) while the sibling action that produces the same economic effect ("transferFrom"/"safeTransferFrom") has no equivalent check.

### Finding Description
Asset definitions may independently define `issue_condition` and `transfer_condition` [1](#0-0) . These are meant to gate two different operations: minting new units of the asset vs. moving already-issued units between addresses.

In `validatePaymentInputsAndOutputs`, the loop over `payload.inputs` allows at most one `"issue"` input, which must be `input_index === 0`, and any subsequent inputs are `"transfer"` [2](#0-1) . The flag `bIssue` is set to `true` as soon as the issue input is processed [3](#0-2) , and it is never reset back to `false` for the remainder of the message even though later inputs are of type `"transfer"`.

After all inputs are processed, the code picks exactly one condition to check for the whole message:
```
var arrCondition = bIssue ? objAsset.issue_condition : objAsset.transfer_condition;
``` [4](#0-3) 

Because `bIssue` is a single flag for the entire payment rather than being evaluated per input, a message that contains one trivial issue input (index 0) plus one or more transfer inputs will have its `transfer_condition` completely skipped — only `issue_condition` (which may be absent/`null`, in which case the check is a no-op via `if (!arrCondition) return cb();`) is evaluated, even though the message also spends existing, previously-issued outputs that were supposed to be gated by `transfer_condition`.

Issuance by a non-definer is legitimately possible whenever `issued_by_definer_only` is `false`; the only structural restriction is that capped assets must be issued by the definer only [5](#0-4) , so an uncapped asset with `issued_by_definer_only: false` can be issued by anyone in arbitrary amounts, with no attached `issue_condition` requirement.

### Impact Explanation
An attacker holding (or having stolen/forwarded) a restricted output that is protected by an asset's `transfer_condition` (e.g. "only transferable to attested/whitelisted addresses", "only after some data-feed/oscript condition", etc.) can construct a single payment message that:
1. Issues a trivial extra amount of the same uncapped, non-definer-restricted asset as `input[0]` (type `"issue"`).
2. Adds the real, condition-protected coin as a subsequent `"transfer"` input.

Because `bIssue` becomes `true` for the whole message, `transfer_condition` is never evaluated for the transfer input, letting the attacker move funds to any address in violation of the asset issuer's transfer restrictions — effectively unauthorized spending/transfer of an asset whose owner explicitly restricted transferability. This is a concrete violation of asset transfer conditions defined at the protocol level, analogous to a council member being able to `transferFrom` an NFT with none of the governance checks that gate the equivalent privileged action.

### Likelihood Explanation
Any user can post ordinary units; no special privileges, hub cooperation, or malicious peer/node behavior are required. The only precondition is that the asset be uncapped and not restricted to definer-only issuance (a configuration choice the asset issuer controls, but one that is not documented as unsafe to combine with `transfer_condition`) or, if capped, that the attacker be (or have compromised) the definer's issuance path in a message that also carries transfer inputs. Given assets frequently combine `is_transferrable` + `transfer_condition` for access control while allowing open issuance for liquidity purposes, this is readily reachable by an ordinary unit poster.

### Recommendation
Evaluate `issue_condition` and `transfer_condition` independently, per input group, instead of using a single message-wide `bIssue` flag to pick one condition for the entire payment:
- Track whether the message actually contains transfer inputs separately from whether it contains an issue input.
- If it has an issue input, evaluate `issue_condition` for the "issue" segment; if it also (or instead) has transfer inputs, additionally evaluate `transfer_condition` for the value being moved by those transfer inputs.
- Do not allow a satisfied `issue_condition` to substitute for an unmet/absent `transfer_condition` check when transfer inputs are present in the same message.

### Proof of Concept
1. Definer creates asset `A` with `is_transferrable: true`, `fixed_denominations: false`, `issued_by_definer_only: false`, `cap` unset (uncapped), and a strict `transfer_condition` (e.g., requiring the recipient/sender to be attested by a specific attestor).
2. Attacker holds (or is the output owner of) a previously-issued output of asset `A` at address `X`, which they are not permitted to move per `transfer_condition`.
3. Attacker composes a single `payment` message for asset `A` with:
   - `inputs[0] = {type: "issue", amount: 1, serial_number: <unused>}` (legal since asset is uncapped and not definer-restricted).
   - `inputs[1] = {type: "transfer", unit: <src_unit>, message_index: <mi>, output_index: <oi>}` referencing the restricted output at `X`.
   - `outputs` balancing `total_input` (issued 1 + transferred amount) to any destination address the attacker wants, including addresses that would fail `transfer_condition`.
4. During validation, `bIssue` becomes `true` at `inputs[0]`, so `arrCondition = objAsset.issue_condition` is used for the whole message (`validation.js` lines 2643-2657); `transfer_condition` is never evaluated against the restricted transfer input, and the unit is accepted, moving the restricted coins to an address that should have been disallowed.
