## Analysis

The Ammplify bug's core pattern is: an unprivileged caller can force unwanted assets into a victim's fixed-size/limited resource (via an uncontrolled `recipient` parameter and unbounded, non-opt-in insertion into that quota), permanently blocking the victim's legitimate use of the protocol. The strongest reachable analog in `ocore--004` is in the AA payment-composition logic (`aa_composer.js`), where an AA's outgoing payments for a custom asset are assembled by consuming *all* unspent outputs of that asset sitting at the AA's own address, in a fixed non-amount-based order, with no per-loop cap on the number of inputs collected, and with no dust-amount filter for non-base assets (unlike the base-asset case, which is explicitly filtered for exactly this dust-attack reason).

### Title
Unbounded consumption of attacker-donated dust asset outputs can permanently DoS an AA's custom-asset payouts - (File: `aa_composer.js`)

### Summary
Any unprivileged wallet holding or able to issue a custom asset can send an unlimited number of tiny-amount outputs of that asset directly to a target AA's address. When the AA later needs to pay out that asset in response to a trigger, `aa_composer.js`'s `completePaymentPayload`/`iterateUnspentOutputs` consumes unspent outputs in deterministic `(main_chain_index, unit, output_index)` order rather than by size, and does so without any bound on the number of inputs collected [1](#0-0) . Because the base-asset case explicitly filters out dust outputs "to prevent dust attack: spamming the AA with very small outputs" [2](#0-1) , but the same filter is not applied when `asset` is a custom (non-base) asset [3](#0-2) , an attacker can flood an AA with worthless dust of a chosen custom asset that the AA's payout logic is forced to sweep up.

### Finding Description
`readStableOutputs`/`readUnstableOutputsSentByAAs` query all unspent outputs at the AA's address for the asset being paid, applying a minimum-amount dust filter only for the base asset (`asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE`) [4](#0-3) . `iterateUnspentOutputs` then walks every returned row and pushes it into `payload.inputs` until the target amount is reached, with no cap on the number of inputs consumed (contrast with the indivisible-asset picker, which explicitly stops at `constants.MAX_MESSAGES_PER_UNIT - 1`) [5](#0-4) . Any address (including an attacker's own) can send ordinary asset-payment outputs to the AA's address at any time — this requires no special privilege, matching the "unprivileged asset issuer" reachability in the rules. Crucially, the unit-level `MAX_INPUTS_PER_PAYMENT_MESSAGE` guard in validation is explicitly skipped for AA-generated units: `if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA) return callback("too many inputs");` [6](#0-5) . So the AA composer itself has no safety valve preventing it from assembling arbitrarily large input lists once dust has accumulated at its address for a non-base asset.

### Impact Explanation
Once enough dust outputs of a target custom asset accumulate at an AA's address (ordered before any legitimate larger output by main-chain sequence), the AA's attempt to pay out that asset will keep sweeping the dust first, inflating the resulting unit until it exceeds size/complexity limits (`MAX_UNIT_LENGTH`, `MAX_COMPLEXITY`) or oversize-fee/storage constraints, causing the response to bounce every time. This freezes the AA's ability to pay out that asset indefinitely — an AA fund-freezing DoS analogous to the Ammplify report's permanent blocking of Maker/Taker creation via quota-filling donations, reachable purely by an unprivileged unit poster sending ordinary payment outputs.

### Likelihood Explanation
Sending payment outputs to an arbitrary address (including an AA) is a normal, unprivileged operation available to any asset holder or issuer, and can be scripted/automated cheaply, similar to the original report's "low cost, easily automatable" attacker profile.

### Recommendation
Apply the same dust-amount filtering used for the base asset to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs`, and enforce an explicit cap on the number of inputs consumed per outgoing payment message (mirroring the `MAX_MESSAGES_PER_UNIT - 1` cap already used in `indivisible_asset.js`), regardless of whether the unit is AA-generated.

### Proof of Concept
1. Attacker repeatedly sends the AA's address tiny-amount outputs of a custom asset `X` (e.g., amount = 1 unit each), each in its own unit, well before any legitimate larger deposit of asset `X`.
2. A trigger later causes the AA to attempt paying out asset `X` to a legitimate user.
3. `readStableOutputs` returns the dust outputs first (deterministic ordering by `main_chain_index, unit, output_index`), and `iterateUnspentOutputs` consumes all of them into `payload.inputs` with no cap.
4. The resulting response unit becomes too large / too complex and fails validation/composition, causing the AA response to bounce repeatedly — permanently freezing the AA's ability to pay out asset `X`.
