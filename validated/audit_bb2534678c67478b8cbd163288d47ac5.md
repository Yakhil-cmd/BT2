### Title
Cross-tenant commit status forgery via webhook signature/target mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization named by the payload's own `repository.owner.login` (or `organization.login`) field, but the handler that actually writes data — `StatusHandler#process` — looks up the target `Commit` by a global, unscoped `sha` lookup with no relation to the organization/repository that was authenticated. This breaks the intended binding: `organization authenticated by signature == repository/stack actually mutated`.

### Finding Description
`verify_signature` in [1](#0-0)  selects the `GitHubApp` (and thus the webhook secret used to verify `X-Hub-Signature`) purely from the attacker-controlled `repository_owner` value: [2](#0-1) 

That value is read straight from the JSON body (`params.dig('repository', 'owner', 'login')`), which is fully attacker-supplied content in the POST request. `verify_webhook_signature` then just HMACs the raw body against that one organization's `webhook_secret`: [3](#0-2) .

Once the signature check passes, `create` dispatches to the registered handler for the event: [4](#0-3) .

For the `status` event, `StatusHandler#process` resolves the target row purely by `sha`, with no scoping to the organization/repository that was just verified: [5](#0-4) 

`Commit.where(sha: params.sha)` searches across **every** stack/repository/organization configured in the Shipit instance. In a multi-tenant deployment (explicitly supported and documented, see "Using Multiple Github Applications" in `docs/setup.md` and `lib/shipit.rb#github`/`#github_app_config`), each onboarded GitHub organization has its own `webhook_secret`, and each organization's legitimate operator is an "unprivileged" party with respect to every other tenant's stacks.

Because `verify_signature` only checks that the request signature matches *some org named in the payload*, and never asserts that this same org owns the `sha` (or repository) actually mutated by the handler, an org owner who legitimately knows only *their own* `webhook_secret` can:
1. Craft an arbitrary JSON body with `repository.owner.login` set to their own organization (to pass signature verification with their own secret), and
2. Set `sha` to the SHA of a commit belonging to a **different** tenant's stack (any commit sha, since the field is just a raw string match, not a proof of git object possession — the sha of a target commit is typically visible via Shipit's own UI/API or GitHub).
3. POST directly to `/webhooks` with a valid `X-Hub-Signature` computed from their own secret.

`StatusHandler` will then create/update a `Status` record on the victim's commit via `commit.create_status_from_github!(params)`, feeding attacker-controlled `state`/`description`/`context`/`created_at` fields [6](#0-5) .

### Impact Explanation
`Commit#create_status_from_github!` → `add_status` can transition the commit's aggregate CI state (e.g. to `success`), which is exactly the signal Shipit's merge queue and deploy safety checks rely on: it schedules `stack.schedule_merges` and can satisfy blocking-status/deploy gating logic [7](#0-6) . An attacker who only controls one tenant organization on a shared/multi-org Shipit instance can therefore forge a passing CI status on another tenant's commit, enabling that commit to be merged or deployed without ever actually passing CI/checks for that repository — an unauthorized merge/deploy crossing a tenant boundary the webhook signature was supposed to enforce.

### Likelihood Explanation
Requires only: (a) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration), and (b) the attacker legitimately owns/administers one of those onboarded organizations (and thus knows only their own `webhook_secret`, never the victim's). No privileged Shipit session, `ApiClient` token, or victim secret is needed — this is exactly the "organization that authenticated vs. repository/commit actually written" binding failure the review is looking for.

### Recommendation
In `StatusHandler` (and any other handler resolving records purely by GitHub-supplied identifiers such as `sha`), scope the lookup to the repository actually named in the same verified payload, e.g. restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository.github_repo_name`/`owner` matches the organization that was authenticated in `verify_signature`. More generally, `WebhooksController` should pass the verified organization down to handlers and have each handler assert that every entity it mutates belongs to that verified organization, rather than trusting repository/owner fields sourced from the unauthenticated parts of the JSON body.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (secret `S_A`) and `VictimOrg` (secret `S_V`), per `docs/setup.md` multi-org instructions.
2. As the legitimate admin of `AttackerOrg`, obtain a commit sha belonging to a `VictimOrg` stack (visible via Shipit's own commit list/API for that stack).
3. Build payload:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using `AttackerOrg`'s own known webhook secret.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: 'AttackerOrg')` and successfully verifies the signature against `S_A`.
7. `StatusHandler.process` runs `Commit.where(sha: '<victim_commit_sha>')`, finds the commit under `VictimOrg`'s stack, and calls `create_status_from_github!`, marking it `success` — potentially unblocking merge/deploy for `VictimOrg`'s stack despite the attacker never having any credential for `VictimOrg`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
