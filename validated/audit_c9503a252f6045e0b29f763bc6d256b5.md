### Title
Premature caching of unvalidated private-payment chains causes silent DoS on legitimate payments - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` in `wallet.js` marks a content-hashed `cache_key` for a set of private-payment chains as "handled" (`handledChainsCache[cache_key] = Date.now()`) as soon as the synchronous `async.eachSeries` loop over the chains completes — regardless of whether the actual per-chain validation (which can be asynchronous, via the `ifQueued` path) has finished or ultimately succeeded. Any later resend of byte-identical chains (same `cache_key`) is then short-circuited at the top of the function and unconditionally reported as `ifOk()` without ever being validated, analogous to the Next.js bug where an edge-case response was cached and then served to everyone regardless of correctness.

### Finding Description
`handlePrivatePaymentChains` computes a deterministic content hash of the whole chain set: [1](#0-0) 

If that key is already present in `handledChainsCache`, the function immediately emits `all_private_payments_handled` and calls `callbacks.ifOk()` without performing any validation of the (again-submitted) chains.

The cache is populated here: [2](#0-1) 

Key problems:
1. For each chain, `network.handleOnlinePrivatePayment` is invoked. When the light-client path can't validate immediately, it calls back via `ifQueued`, which merely registers an `eventBus.once(key, ...)` listener and calls `cb()` synchronously — the *real* asynchronous validation (`privatePayment.validateAndSavePrivatePaymentChain`, driven later from `handleSavedPrivatePayments` in `network.js`) has not completed yet: [3](#0-2) 
2. Because `cb()` returns immediately for the queued case, `async.eachSeries`'s final callback (`function(err){...}`) runs with `err === null` even though none of the queued chains have actually been proven valid yet.
3. At that point the code unconditionally executes `handledChainsCache[cache_key] = Date.now();` — poisoning the cache for this exact chain-set hash *before* the deferred validation outcome (`bValid` in the `eventBus.once(key, ...)` handler) is known.
4. If the deferred validation later fails (`ifError` in `handleSavedPrivatePayments`, which does `eventBus.emit(key, false)`), the `cancelAllKeys()` path removes the pending listeners but never clears `handledChainsCache[cache_key]`. The bad chain-set hash sticks in the cache for up to an hour (the cleanup interval): [4](#0-3) 
5. Consequently, if the exact same `arrChains` payload (same content hash) is retransmitted afterward — e.g., a legitimate resend by the hub/sender attempting to retry a payment that failed to reach the recipient the first time, or an attacker deliberately replaying the poisoned chain bytes — the second call to `handlePrivatePaymentChains` hits `handledChainsCache[cache_key]` and returns `ifOk()` and fires `all_private_payments_handled` immediately, **without validating or saving anything**, even though nothing was ever actually accepted.

### Impact Explanation
This is reachable by any private-payment counterparty (a paired device sending a `private_payments` message through the hub), which is an in-scope unprivileged surface (`case 'private_payments': ... handlePrivatePaymentChains(ws, body, from_address, callbacks);`): [5](#0-4) 

The impact is a denial-of-service on private payments: once a chain-set hash is poisoned (by a first attempt whose async validation later fails or by an attacker who deliberately triggers this timing window), any subsequent legitimate retransmission of that exact private-payment chain is acknowledged as "handled" but silently never validated/saved/forwarded. The recipient will never see the funds recorded, wallets relying on `all_private_payments_handled` events will believe the payment completed, and callers of `handlePrivatePaymentFile` (textcoin claiming) will get `cb(null, data)` as if successful: [6](#0-5) 
This can cause a payer to believe funds were delivered while the payee's wallet silently drops the payment — a node/wallet inability to confirm/record a legitimate private transfer, matching the "network unable to confirm new units/transactions" impact class.

### Likelihood Explanation
The race window exists on every call that goes through the `ifQueued` branch, which the code itself notes is "the most likest outcome for light clients." No cryptographic bypass or malicious peer collusion is required — an ordinary light wallet processing a private payment through the normal hub flow will exercise this code path, and the resulting cache entry is set deterministically before the deferred validation resolves. Any actor who can cause validation to be queued (any light-wallet counterparty) can trigger the premature caching; reproducing the failure/resend race to fully weaponize it needs some timing but requires no special privilege.

### Recommendation
Do not set `handledChainsCache[cache_key]` until every chain's underlying validation has actually completed successfully — i.e., move the cache write into `checkIfAllValidated()` (only once all `assocValidatedByKey` entries are confirmed `true`), and explicitly avoid writing to the cache (or delete any speculative entry) when `cancelAllKeys()` is invoked due to a failed deferred validation.

### Proof of Concept
1. From a paired light-wallet device, send a `private_payments` message via the hub containing a chain whose head unit is not yet known to the receiving wallet (`ifNew`/`ifKnownUnverified` in `handleOnlinePrivatePayment`), so the flow follows `savePrivatePayment()` → `callbacks.ifQueued()`.
2. `handlePrivatePaymentChains`'s `async.eachSeries` completes synchronously with `err === null` (since `ifQueued`'s `cb()` fires immediately), and `handledChainsCache[cache_key]` is set at line 1072 of `wallet.js`, before the real validation in `handleSavedPrivatePayments` (network.js) has run.
3. Arrange for the deferred validation to fail (e.g., the chain later proves to double-spend or fails `validateAndSavePrivatePaymentChain`), causing `eventBus.emit(key, false)` and `cancelAllKeys()` — the pending listeners are removed but `handledChainsCache[cache_key]` is never cleared.
4. Resend the exact same `chains` payload (identical JSON producing the same `objectHash.getBase64Hash(arrChains)`), e.g. a legitimate retry.
5. `handlePrivatePaymentChains` now hits the poisoned `handledChainsCache[cache_key]` entry at line 979 and immediately returns `ifOk()`/emits `all_private_payments_handled` without any validation, hashing, saving, or forwarding — the payment is silently dropped while appearing successful to the sender.
