### Title
Untrusted route pools can invoke arbitrary caller-authorized token transfers - (`contracts/swap-aggregator/src/execute/mod.rs`)

### Summary
A user-supplied `StrategySwap` route can name an arbitrary contract as a hop pool. The router invokes that address as the selected venue, allowing malicious pool code to request token transfers from the strategy caller while executing under the caller’s authorized `swap_collateral` transaction tree. If the victim signs the authorization tree produced by simulation, the malicious hop can steal unrelated wallet tokens while still returning enough swap output to satisfy the controller’s balance checks.

### Finding Description
`swap_collateral` accepts opaque `swap` bytes, withdraws collateral, and passes the payload to the configured router. [1](#0-0)  The controller authorizes only the exact input-token transfer from itself to the router, but does not constrain the pool addresses encoded in the route. [2](#0-1)  The router decodes caller-provided address and instruction registries, constructs each `SwapHop` from the route’s `pool`, `token_in`, and `token_out` indices, and dispatches the venue call. [3](#0-2) [4](#0-3) 

There is no validation that `hop.pool` is a recognized deployment for the selected venue. For example, the Soroswap adapter directly invokes `get_reserves` and `swap` on the route-controlled pool address. [5](#0-4)  Malicious code at that address can invoke `token.transfer(victim, attacker, amount)`; simulation records that transfer as a child of the victim’s controller authorization, and enforcement accepts it if the victim signs that tree. [6](#0-5) [7](#0-6) 

The controller’s post-router checks only require bounded input spend and positive measured output; they do not prevent the malicious pool from requesting an unrelated transfer under the caller’s authorization. [8](#0-7) 

### Impact Explanation
An attacker can steal arbitrary token balances from the transaction signer, including tokens unrelated to the lending markets or route. The theft is not limited to the collateral submitted to `swap_collateral`: the malicious pool can request a transfer of any token held by the victim, provided that transfer appears in the signed authorization tree. [9](#0-8) [10](#0-9) 

This is theft of user funds because the pool code executes inside a transaction the victim intended to be a collateral swap, and the malicious authorization request can be hidden among otherwise expected route authorization entries.

### Likelihood Explanation
The attacker only needs to cause the victim to submit a crafted route through `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`. The malicious pool must still satisfy the selected venue adapter’s invocation shape and ensure the router returns positive output, but the demonstrated path returns fair output while performing the unauthorized-looking transfer. [11](#0-10) [12](#0-11) 

Exploitation requires the victim to sign the expanded authorization tree. That matches a crafted-input phishing scenario: an interface or quote can produce a profitable-looking route whose simulation contains an additional token transfer, and a wallet or client that does not reject unexpected child authorizations will sign it. [13](#0-12) 

### Recommendation
Do not allow route bytes to select arbitrary pool addresses. Bind each encoded venue hop to an allowlisted or registry-verified pool address for that venue, and reject routes containing unapproved pool contracts before any external invocation. Independently, clients and wallets should simulate the final transaction and reject any authorization child other than the expected input transfer, but the router should not rely on clients to contain attacker-controlled external code.

### Proof of Concept
The repository’s adversarial test demonstrates the full flow:

1. Deploy a malicious contract with the pool interface expected by a route hop.
2. Configure it with `(victim, unrelated_wallet_token, attacker, amount)`.
3. Build a `swap_collateral` route whose hop-pool address is that malicious contract.
4. Have the victim hold supplied collateral and call `swap_collateral` with the route.
5. During simulation, the malicious pool calls `token.transfer(victim, attacker, amount)`, which is recorded under the victim’s `swap_collateral` authorization. [14](#0-13) [15](#0-14) 
6. If the victim signs that tree, the unrelated token is transferred to the attacker while the strategy still deposits the expected replacement collateral. [10](#0-9) [7](#0-6)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
