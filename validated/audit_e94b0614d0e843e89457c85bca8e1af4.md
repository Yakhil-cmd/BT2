### Title
Webhook signature scoping keyed on `repository.owner.login` while event routing keyed on `repository.full_name` allows cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate the inbound webhook signature against using `repository_owner`, a value read from `params.dig('repository','owner','login')` (or `organization.login`) inside the unauthenticated JSON body. Once verification "passes," `Shipit::Webhooks::Handlers::Handler#repository_name` resolves the actual DB `Repository`/`Stack` to act on using a *different* field of the same body: `payload.dig('repository','full_name')`. These two fields are never checked for consistency, and in the documented multi-organization configuration, each organization can independently have `webhook_secret` unset (`nil`), which `GitHubApp#verify_webhook_signature` treats as "always verified." ### Finding Description
The binding that should hold is: **organization whose signature check authenticated the request == organization that owns the repository actually written to**. This binding is broken because the two lookups read different, independently attacker-controlled fields of the same unauthenticated JSON payload:

- Signature/org selection: `repository_owner` = `params.dig('repository','owner','login')` (fallback `organization.login`), used to pick `Shipit.github(organization: repository_owner)` and thus which `webhook_secret` is used for HMAC verification. [5](#0-4) 

- Actual target resolution: `Handler#repository_name` = `payload.dig('repository','full_name')`, used by every handler (push, status, pull_request, etc.) via `Repository.from_github_repo_name(repository_name)` to look up the real `Repository`/`Stack` and act on it (sync commits, record CI statuses, capture PR labels, etc.). [3](#0-2) [6](#0-5) 

`Shipit.github` supports per-organization configuration (`github_app_config`), and the documented schema explicitly allows `webhook_secret` to be `nil` per organization: [7](#0-6) [8](#0-7) 

And `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [4](#0-3) 

Consequently, if *any* organization configured in a multi-org Shipit deployment has no `webhook_secret` (a documented, supported configuration), an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that unsecured organization's name so `verify_signature` unconditionally passes.
2. Set `repository.full_name` to `"<protected-org>/<real-repo>"`, a completely different, secret-protected organization's repository that Shipit tracks.
3. Send arbitrary event bodies (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) with these mismatched fields and have handlers act on the protected org's `Repository`/`Stack`/`Commit` records with no valid credential for that org at all.

This is a direct binding violation matching the rule's "an organization that authenticated versus the repository that is written" category.

### Impact Explanation
The most severe exploitable consequence is via `StatusHandler`, which trusts unauthenticated `state`/`context`/`target_url` fields to create commit statuses on arbitrary tracked commits once routed to the wrong org's repository: [9](#0-8) 

Since Shipit's merge queue and CI gating (`ci.require`) rely on GitHub commit statuses being trustworthy, an attacker able to forge success statuses on a protected repository's commits can unblock the merge queue and push commits toward an unauthorized deploy, without ever presenting a credential valid for that organization. `PushHandler` similarly triggers `stack.sync_github`, and other handlers (`pull_request`, `membership`, `check_suite`) mutate application state (creating users/teams, changing PR/merge state) for a repository the request was never authenticated against — an unauthorized cross-repository write.

### Likelihood Explanation
Exploitability is conditional but realistic: it requires (a) a multi-organization Shipit deployment (explicitly documented and supported: `docs/setup.md`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and (b) at least one configured organization with `webhook_secret` left blank — also explicitly shown as a supported, default-friendly configuration (`webhook_secret: # nil`) in the example secrets files. Given `webhook_secret` is optional in the documented schema, this is not a hypothetical edge case but a directly supported deployment shape, making likelihood moderate-to-high for any installation that onboards a low-trust or newly-configured organization alongside protected ones.

### Recommendation
- Verify the webhook signature using the *same* field that handlers use to resolve the target repository (`repository.full_name`'s owner segment), not a separately-read `repository.owner.login`/`organization.login` value.
- Reject webhooks where `repository.owner.login` and the owner segment parsed from `repository.full_name` do not match.
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank in a multi-org configuration; require an explicit, non-nil secret per organization, or fail closed instead of open (`return true unless webhook_secret` in `lib/shipit/github_app.rb` line 77 is fail-open and should be fail-closed, or at minimum documented/enforced only for genuinely single-tenant setups).

### Proof of Concept
1. Deploy Shipit with multi-org GitHub Apps: `OrgUnsecured` (no `webhook_secret` configured) and `OrgProtected` (repo `OrgProtected/critical-app` tracked by Shipit, `webhook_secret` set).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {
    "owner": { "login": "OrgUnsecured" },
    "full_name": "OrgProtected/critical-app"
  },
  "sha": "<known commit sha on OrgProtected/critical-app>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required, because `verify_signature` resolves `github_app = Shipit.github(organization: "OrgUnsecured")`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret).
3. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which resolves the commit via `sha` directly (not even repository-scoped) and calls `commit.create_status_from_github!`, injecting a forged "success" CI status on `OrgProtected`'s commit — despite never presenting any credential valid for `OrgProtected`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
