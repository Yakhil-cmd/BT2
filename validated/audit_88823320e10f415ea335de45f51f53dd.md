This confirms `run_stx_transfer(&sender.into(), &recipient.into(), transfered_ustx, ...)` is a direct STX balance debit/credit with `sender` taken verbatim from `TransferStxOp.sender`, which in turn is set to `pre_stx.output` at classification time. `PreStxOp::parse_from_tx` sets `output` to the first Bitcoin output address of the PreStxOp transaction — a value the creator of that transaction can set to **any** Bitcoin/StacksAddress hash160 they like, without needing to control the corresponding private key. There is no signature or ownership proof over the `output`/`sender` field anywhere in `PreStxOp` or `TransferStxOp`. However, this design is a fundamental, unpatched consensus rule and does not fall under the OUT-OF-SCOPE list (which is pox-2/3, tests, DoS, price assumptions, etc.), so it must be evaluated on its own merits. ### Title
Attacker-controlled `sender` in `PreStxOp`/`TransferStxOp` pairing allows theft of arbitrary STX balances - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Summary
`TransferStxOp.sender` is set from `PreStxOp.output`, which is parsed as the first Bitcoin output address of the PreStxOp transaction with no proof that the transaction's creator controls the corresponding private key. An attacker can therefore craft a PreStxOp whose first output encodes a victim's `StacksAddress`, and a follow-on TransferStxOp (which they alone sign, spending PreStxOp's second output) that sets `recipient` to themselves, moving the victim's on-chain STX balance to the attacker via `run_stx_transfer`.

### Finding Description
The equality that should hold is: **STX moved by the op == STX owned by the Bitcoin key(s) that authorized/signed the underlying Bitcoin transaction (AUTHORITY)**. This is broken because `sender` is populated purely from `pre_stx.output`, an arbitrary output address chosen by whoever crafts the `PreStxOp` Bitcoin transaction: `PreStxOp::parse_from_tx` takes `outputs.get(0)....address...try_into_stacks_address()` with no cryptographic tie to the transaction's signing keys [5](#0-4) . `stackslib/src/burnchains/burnchain.rs::classify_transaction` then takes `sender = &pre_stx.output` and calls `TransferStxOp::from_tx(block_header, burn_tx, sender)` [7](#0-6) , and `TransferStxOp::parse_from_tx` stores this untrusted value directly as `op.sender` [8](#0-7) . The only requirement to link the TransferStxOp to the PreStxOp is that its first input spends vout==1 of the PreStxOp transaction (`get_sender_txid`) [9](#0-8)  — that output (vout 1) is a *different* output than vout 0 (the "sender"/output field), so the attacker only needs to control the private key for spending vout 1, which they created themselves; vout 0 can be set to any address, including the victim's, since sending BTC to an address requires no proof of ownership of that destination. `TransferStxOp::check()` only rejects a zero amount or `sender == recipient` [3](#0-2) ; it performs no check that `sender` corresponds to any key the transaction's signer actually controls. Finally, `StacksChainState::process_transfer_ops` calls `run_stx_transfer(&sender.into(), &recipient.into(), transfered_ustx, ...)` [10](#0-9) , unconditionally moving `transfered_ustx` from the victim's Stacks account balance to the attacker's, entirely determined by Bitcoin-transaction fields the attacker fully controls.

**Exploit flow:** (1) Attacker crafts and broadcasts a Bitcoin `PreStxOp` transaction spending only their own BTC UTXOs, with output[0] = victim's StacksAddress-equivalent hash160 (the "sender"), output[1] = an address the attacker controls. (2) Attacker crafts and broadcasts a `TransferStxOp` Bitcoin transaction whose first input spends output[1] of the PreStxOp tx (proving control only over that spend, not over output[0]), with the op payload encoding `transfered_ustx` and `recipient` = attacker's Stacks address. (3) On the corresponding Stacks block, `process_transfer_ops` moves `transfered_ustx` from the victim's balance to the attacker's.

### Impact Explanation
This allows an attacker to steal any amount of STX from any Stacks address, as long as that address's balance covers `transfered_ustx` — a direct, repeatable theft of locked or liquid STX from arbitrary victims, matching the Critical severity category (direct theft of STX not authorized by its owner).

### Likelihood Explanation
The only precondition is that the attacker controls some BTC to fund two low-cost Bitcoin transactions (the PreStxOp and TransferStxOp); no interaction with the victim, no privileged role, and no dependency on stacking cycle phase or membership state is required. The attack is fully repeatable against any victim address with a nonzero STX balance and costs only Bitcoin transaction fees.

### Recommendation
Cryptographically bind `sender`/`output` to the entity that actually authorizes the PreStxOp/follow-on transaction — e.g., require `output` to equal the `StacksAddress` derived from the public key(s) that signed the transaction's first input (as is done for `apparent_sender`/`BurnchainSigner` elsewhere), and validate this during `PreStxOp`/`TransferStxOp` parsing rather than trusting the raw output address.

### Proof of Concept
Rust integration test (`stackslib` chainstate test or `stacks-node` integration test, modeled after existing `TransferStxOp` tests in `stackslib/src/chainstate/burn/operations/transfer_stx.rs` and `stacks-node/src/tests/epoch_21.rs`):
1. Set up a regtest chain with a funded "victim" Stacks account (`victim_addr`) with balance `V`, distinct from any address controlled by "attacker".
2. Attacker (controlling only their own BTC UTXOs) submits a `PreStxOp` Bitcoin transaction with output[0] = `victim_addr` (as legacy BTC address bytes) and output[1] = an address attacker controls.
3. Attacker submits a `TransferStxOp` Bitcoin transaction spending output[1] of the PreStxOp tx, with `recipient` = `attacker_addr`, `transfered_ustx = V`.
4. Mine the blocks so the ops are classified and `process_transfer_ops` runs.
5. Assert: victim's STX balance decreased by `V` (`victim_balance_after == victim_balance_before - V`) and attacker's STX balance increased by `V`, despite no transaction ever being signed by `victim_addr`'s private key — demonstrating the AUTHORITY equality is broken.
