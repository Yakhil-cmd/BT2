### Title
Unfunded `recapitalize` pays out pool custody without debiting the cash book, bricking withdrawals — (File: contracts/pool/src/lib.rs)

### Summary
The pool's `recapitalize` entrypoint transfers real token balance out of the pool to an arbitrary `payer` while the internal `cash` book is not debited to match. An unprivileged caller can invoke it (the controller exposes `recapitalize` as a permissionless path, and the pool's own test harness calls `client().recapitalize(...)` directly with a freshly generated payer). This leaves the book permanently overstating custody: the pool believes it is solvent, admits exits past its own liquidity guards, and every subsequent `withdraw` (and any other path settling against real balance) aborts inside the SAC transfer — a persistent denial of service on funds, the on-chain analog of CVE-2020-8618's attacker-crafted-input assertion-failure DoS.

### Finding Description
In `contracts/pool/src/lib.rs`, `recapitalize` is intended to cover bad debt "without minting shares": it moves tokens between the pool and the payer and adjusts accounting. The in-repo regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408` demonstrates the defect end-to-end:

1. A supplier deposits `10_000_000_000`; `cash == token.balance(pool)` holds.
2. `pool.recapitalize(hub(asset), payer, custody)` is called with `payer` a generated address and the full pool balance as the amount. Custody goes to zero, yet `state.cash >= deposit` still.
3. A subsequent `try_withdraw` passes both pool liquidity guards (`InsufficientLiquidity` and `PoolInsolvent` are explicitly asserted NOT to be the error) and fails only inside the SAC `transfer` with `BalanceError = 10` (insufficient balance). The receiver gets nothing and the book still overstates custody.

Unlike a fail-closed guard (which the rules exclude), the root cause is not a check firing — it is a check *not* firing: `require_reserves`/solvency guards read the corrupted `cash` book rather than actual token balance, so the crafted `recapitalize` input permanently poisons the accounting state that all later exits trust.

### Impact Explanation
Any address can drain the real token balance of a (hub, asset) market book while leaving `cash` claiming the funds exist. Suppliers' withdrawals then revert forever at the token transfer — funds are permanently frozen (the book still credits supply shares, so positions cannot be unwound), and the market cannot operate for lack of token custody. Borrow/flash/settle paths that rely on the book also report a solvent market that cannot pay.

### Likelihood Explanation
`recapitalize` is reachable by a single unprivileged address: it takes only `(hub_asset, payer, amount)`, requires no shares, no auth from the pool beneficiary, and no prior position. The attacker supplies nothing at risk; the only requirement is that the market holds balance. The panic the analog maps to (assertion failure aborting service) manifests as the SAC `BalanceError` abort on every withdrawal thereafter — a crafted-input-induced persistent failure, not a per-transaction revert.

### Recommendation
Inside `contracts/pool/src/lib.rs` `recapitalize`:
- Require the payer's `require_auth` or restrict the direction so recapitalize only ever pulls tokens *in* (measured via balance-delta receipt like the flash/settlement paths) rather than pushing custody out.
- After the transfer, reconcile `cash` against the actual post-transfer token balance and panic with `PoolInsolvent` if the book would exceed custody, so a bad recapitalize reverts atomically instead of persisting an overstated book.

### Proof of Concept
See `contracts/pool/tests/flows.rs:3408-3483` (`test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`), which exercises exactly this sequence:

```rust
// contracts/pool/tests/flows.rs:3432
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0, "custody is gone");
// book still claims >= deposit; withdraw passes pool guards then aborts
// in the SAC transfer with BalanceError = 10
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```

The test asserts the error is the SAC balance error and not `InsufficientLiquidity` or `PoolInsolvent`, proving the guards read the corrupted book — the DoS persists until governance/upgrade intervention.
