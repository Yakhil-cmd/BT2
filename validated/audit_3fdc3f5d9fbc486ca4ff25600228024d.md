### Title
Unchecked `address_definition_change` target allows a single, unconfirmed control transfer that can permanently lock an address's funds - (File: validation.js)

### Summary
The reported Solidity bug flags `Ownable.transferOwnership()` for accepting any non-zero address as the new owner in one step, with no verification that the nominee is a valid, controllable account, and recommends a zero-address check plus a two-step "propose/accept" pattern. Ocore's structural equivalent of address ownership transfer is the `address_definition_change` message, which lets the current controller of an address point it to a brand-new `definition_chash` in a single, irrevocable step. Like the Solidity pattern, the protocol only checks that the new value has the right *format*; it never verifies that anyone actually possesses (or will ever disclose) a definition hashing to that value.

### Finding Description
`address_definition_change` is validated in `validateInlinePayload()`. For the new controlling definition it only performs a format/length check: [1](#0-0) 

There is no check that `payload.definition_chash` corresponds to a definition anyone can produce a valid `evaluate`/signature for, no reachability check, and no acceptance step from whoever is supposed to control the new definition. The change is applied unilaterally by the current author and takes effect for all future units as soon as it is stable, exactly as `Swap.transferOwnership()` immediately overwrote `owner` with an unchecked value.

Downstream, once accepted, this new `definition_chash` is recorded and becomes the sole reference for future authentication of the address: [2](#0-1) 

Composer confirms the change is disclosed only lazily/optionally when a subsequent unit is signed with the new definition, never validated against the poster's real capability to sign with it at the time of the change: [3](#0-2) 

The `definition.js` validator that would normally check a full address definition template (signature schemes, thresholds, etc.) is bypassed for the `new_definition_chash` in `address_definition_change`; that string is checked with `isValidAddress`, i.e. only that it looks like a 160-bit chash: [4](#0-3) 

Because ocore's `isValidAddress` performs a checksum/format validity check but cannot know whether a matching definition JSON (and its associated private keys) actually exists, a single unprivileged unit poster who mistypes, miscomputes, or is tricked into using an unintended `definition_chash` (analogous to nominating an "uncontrolled EOA") will have their address's control transferred to a hash nobody can ever satisfy, permanently freezing every current and future output at that address (its base-currency balance, any assets, and its usability as a payer/trigger sender for AAs).

### Impact Explanation
This is the direct analog of losing `onlyOwner` control in the Solidity report: once the mis-set `address_definition_change` becomes stable, no future unit from that address can ever pass `validateAuthentifiers`/signature checks against a definition nobody can produce, permanently freezing all funds and AA-interaction capability tied to that address. This is a concrete "freezing of funds" outcome, matching the medium-severity bar (funds are not lost to an attacker, but become permanently unspendable/unrecoverable).

### Likelihood Explanation
Likelihood is comparable to the original report: it requires the address owner to make a mistake (bad chash, copy/paste of a template they don't fully control, or a compromised/malicious wallet UI suggesting an unverifiable chash), the same class of user error the C4 report calls out for `transferOwnership`. There is no protocol safeguard (no confirmation from a party proving control of the new definition, no fallback/rollback window) to catch this before it becomes final.

### Recommendation
Introduce a two-step confirmation analogous to `acceptOwnership()`: require the new definition to be disclosed and self-authenticated (e.g., a unit signed under the new definition referencing/confirming the pending change) before the change takes final effect for spending/authentication purposes, rather than making the switch effective on a single unilateral message. At minimum, warn/require an explicit acknowledgment at the wallet/composer layer (`composeDefinitionChangeJoint`) that the new `definition_chash` has been locally verified against a definition the user actually holds the keys for, and consider a protocol-level grace period during which the old definition can still countermand an unconfirmed change.

### Proof of Concept
1. Address `A` is controlled by definition `D1` (`sig` on key `K1`).
2. The address owner composes and posts a unit with message `{app: "address_definition_change", payload: {definition_chash: X}}` via `composeDefinitionChangeJoint` (`composer.js:85-87`), where `X` is a chash the owner does not actually hold matching keys for (e.g., transcription error, or a template hash they wrongly believe corresponds to a key they own).
3. `validateInlinePayload` (`validation.js:1719-1745`) accepts this because `X` passes `isValidAddress` format checks only — no proof of a matching definition/keys is required.
4. Once stable, `address_definition_changes`/`unit_authors.definition_chash` for `A` is updated to `X` (`writer.js:184-192`).
5. Any subsequent unit from `A` must supply a definition whose chash equals `X` and pass `validateAuthentifiers` — which nobody can do — permanently freezing all of `A`'s existing and incoming funds and blocking its use as an AA trigger sender. [5](#0-4)
