### Title
Webhook signature verified against `repository.owner.login` while handlers act on `repository.full_name`, allowing cross-organization/cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to authenticate an incoming webhook based on `repository.owner.login` (falling back to `organization.login`), but the HMAC signature only covers the raw JSON body as a bag of bytes—it does not bind that specific field to the rest of the payload in any Shipit-side re-validation. Once the signature check passes, every registered `Handler` (via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name` (`Handler#repository_name`), with no cross-check that `full_name`'s owner segment matches the `repository.owner.login` that was actually authenticated.

### Finding Description
`verify_signature` computes the authenticating organization as: [1](#0-0) [2](#0-1) 

```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This picks the correct per-organization `webhook_secret` (Shipit supports multiple GitHub App configurations, one per organization, as seen in `test/dummy/config/secrets_double_github_app.yml`) and HMAC-verifies the raw body against it via `GithubApp#verify_webhook_signature`.

Once verification succeeds, the *entire* raw payload (not just the fields used for verification) is dispatched unmodified to handlers in `WebhooksController#create`: [3](#0-2) 

Every handler resolves its target repository/stack from a **different** payload key: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers (e.g. `OpenedHandler#repository`) all key off `repository.full_name` to look up `Repository`/`Stack` records and act on them (`stack.sync_github`, `schedule_refresh_check_runs!`, `ReviewStackAdapter#find_or_create!`, etc.): [5](#0-4) [6](#0-5) [7](#0-6) 

Nowhere is `repository.owner.login` (the value used for authentication) checked against the owner segment of `repository.full_name` (the value used to select the write target). This is exactly the analog to the "convoluted `updateTo`" report's bug class: a value the verified signature is computed over (`repository.owner.login`) is not the same value the state-mutating logic actually acts on (`repository.full_name`), breaking the binding "organization that authenticated == repository that is written."

Any principal who controls (or is an admin of) **one** organization/GitHub App that is registered in this Shipit instance's `Shipit.github_apps` configuration—and therefore legitimately knows that organization's `webhook_secret`—can send a correctly-signed webhook whose `repository.owner.login`/`organization.login` names their own org (satisfying `verify_signature`) but whose `repository.full_name` names a repository belonging to a *different* organization also hosted on the same Shipit instance. Because handlers only trust `full_name`, this forges events (pushes triggering `sync_github`, PR-opened events provisioning review stacks, check-suite refresh triggers, etc.) against stacks/repositories the attacker does not own and was never authenticated for.

### Impact Explanation
This breaks the deployment-trust binding between the GitHub organization whose credentials authenticated the webhook and the repository/stack whose state is mutated. In a multi-organization Shipit deployment, an attacker who legitimately administers Org A (and thus its webhook secret) can forge webhook traffic that is processed as if it originated from Org B's repositories, causing unauthorized stack synchronization, review-stack provisioning, or check-run refresh actions on Org B's stacks—a cross-repository/cross-organization write performed without any authorization check tying the two fields together.

### Likelihood Explanation
Requires the attacker to control/administer at least one organization that is configured in the same Shipit instance's `github_apps`/`webhook_secret` config, and to know an existing target repository's `full_name` (typically public information). No repository write access, API token, or session on the target org is needed—only the ability to sign an arbitrary payload with credentials the attacker already legitimately possesses for their own org. This is realistic for shared/multi-tenant Shipit deployments serving several organizations under one host.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController#create`/`verify_signature`), require that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used for signature verification, and reject the webhook (422) on mismatch. Alternatively, resolve `stacks`/`Repository` scoped to the authenticated organization rather than trusting the payload's `full_name` in isolation.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App / `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, an admin of `attacker-org`, knows `attacker-org`'s `webhook_secret` (they configured it).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact body and POSTs it to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature, so the request proceeds.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack—an action never authenticated by `victim-org`.
