[1](#0-0) ### Title
Malicious flash-position receiver steals caller wallet assets through the signed authorization tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` accepts an arbitrary `receiver` contract and invokes it with the caller's address and caller-controlled `data`. [1](#0-0) [2](#0-1)  A malicious receiver can request additional authorization from `initiator`—for example, an unrelated token or position-NFT transfer—and Soroban records that request as a child of the caller's signed `flash_position` authorization.  If the caller signs the simulated tree, the unrelated transfer executes even though it is unnecessary for the flash-position settlement.

### Finding Description
The `receiver` parameter is an unconstrained contract address, and the controller invokes it inside the guarded flash-position flow. [1](#0-0) [3](#0-2)  The callback receives `initiator`, `account_id`, the debt asset, the received amount, the controller address, and the opaque callback payload, giving receiver-controlled code both execution and the victim address. [2](#0-1) 

The flash guard prevents reentry into protected protocol functions, but it does not prevent the receiver from calling unrelated token contracts. [4](#0-3)  The settlement baselines cover only declared collateral and refund assets; they do not bound or snapshot unrelated assets belonging to `caller`. [5](#0-4) 

Consequently, a receiver can satisfy the expected collateral transfer while also invoking `token.transfer(initiator, attacker, amount)` on an unrelated token.  Because the token's `transfer` requires `initiator` authorization, simulation adds that transfer beneath the caller's root authorization; signing the complete tree authorizes both the flash position and the theft. 

### Impact Explanation
A victim can lose unrelated wallet tokens or transferable position NFTs that were never inputs to the flash-position call.  The attacker can make the lending operation itself succeed by forwarding the borrowed proceeds or purchased collateral back to the controller, so the unrelated theft is not caught by collateral deltas, refund deltas, or final account risk checks. [4](#0-3)  This permits theft of user funds and potentially theft of the account represented by a transferable position NFT.

### Likelihood Explanation
The attack requires user interaction: the victim must submit a `flash_position` using the malicious receiver and sign the authorization tree containing the extra child transfer.  This is comparable to opening a malicious previewed file in the Theia advisory; normal-looking controller arguments do not reveal that the opaque callback will request unrelated authority. [1](#0-0)  Likelihood is bounded because a wallet or client that accurately displays and rejects unexpected child authorizations prevents the transfer.

### Recommendation
Treat the callback receiver as untrusted executable code rather than as a passive address. [2](#0-1)  Prefer a governance-approved receiver code-hash registry or a fixed audited callback adapter for production integrations.  Clients and wallets should simulate the transaction, decode the full authorization tree, and reject any child invocation that transfers tokens or NFTs from `caller` outside the expected protocol operation.  At minimum, document that any unexpected caller-auth child beneath `flash_position` invalidates the transaction.

### Proof of Concept
1. Deploy a malicious receiver implementing `execute_flash_position`.
2. Seed it with enough collateral, or let it swap the received debt proceeds, so it can satisfy the victim's declared positive collateral minimum.
3. Have its callback execute an unrelated transfer from `initiator` to the attacker, then send the expected collateral to the controller.
4. Convince the victim to call `flash_position(caller = victim, receiver = malicious_receiver, ...)`.
5. Simulation records the rogue token transfer as a child of the victim's `flash_position` authorization.
6. If the victim signs that tree, the lending operation succeeds and the unrelated wallet token is transferred to the attacker.

Example malicious callback logic:

```rust
pub fn execute_flash_position(
    env: Env,
    initiator: Address,
    _account_id: u64,
    debt_asset: Address,
    _amount: i128,
    _fee: i128,
    amount_received: i128,
    controller: Address,
    _data: Bytes,
) {
    // This becomes an unauthorized child under the victim's signed auth tree.
    token::Client::new(&env, &victim_wallet_token).transfer(
        &initiator,
        &attacker,
        &victim_wallet_balance,
    );

    // Make the flash-position accounting succeed.
    token::Client::new(&env, &declared_collateral).transfer(
        &env.current_contract_address(),
        &controller,
        &collateral_output,
    );

    let _ = (debt_asset, amount_received);
}
```

The decisive condition is the signed authorization tree, not whether the malicious receiver returns collateral.  Without the extra signed child transfer, the token invocation fails and rolls back; with it, both the legitimate-looking flash position and the wallet theft commit atomically.
