### Title
Cross-organization webhook forgery via mismatched signature-selection field and payload-consumption field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the inbound webhook against using the attacker-controlled `repository_owner` field taken from the *unverified* JSON body, while the handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler`) resolve the target `Stack`/`Commit` using a *different* field (`repository.full_name`, `sha`) from that same unverified body. Nothing enforces that these two fields refer to the same tenant, so a signature that is valid for organization A's secret can be attached to a payload whose "acted upon" data belongs to organization B.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
It picks the verification key via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the *unverified* JSON payload: [2](#0-1) 

`Shipit.github` resolves per-organization config from `secrets.github` (the documented multi-org schema explicitly supports one `webhook_secret` per organization, and marks it "optional"): [3](#0-2) 

Meanwhile, once `verify_signature` passes, `WebhooksController#create` parses the same raw body and dispatches it to handlers unchanged: [4](#0-3) 

Handlers resolve the actual `Stack`/`Repository` to act on using a **different** payload field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`PushHandler` and `StatusHandler` then mutate state (trigger a GitHub sync, or create a CI status on a real commit) purely from these attacker-suppliable fields: [7](#0-6) [8](#0-7) 

**The broken binding:** `organization authenticated (via repository_owner → webhook_secret lookup) == repository/stack written (via repository.full_name / sha, used by handlers)`. The HMAC signature only proves the request-body was signed by *some* configured organization's secret; it never binds that secret to the specific repository the handlers subsequently act on. An attacker who legitimately controls (or has been given) any single organization's Shipit webhook_secret — e.g. because they administer their own GitHub App installation pointed at the same shared Shipit instance, a normal and documented multi-org deployment pattern — can:
1. Compute a valid `X-Hub-Signature` using their own org's `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) in the JSON body to their own org, so `verify_signature` selects the secret they know and the check passes.
3. Set `repository.full_name` (and other handler-consumed fields such as `sha`) to point at a **victim** org/repo/commit tracked by the same Shipit instance.
4. The handler for the event (e.g. `push`, `status`, `check_suite`) executes against the victim's `Stack`/`Commit`, even though the attacker never possessed the victim org's secret and has no authorization over that repository.

This is structurally identical to the analog bug class: a "verified" credential/binding (org whose secret matches the signature) does not cover the field the code actually uses to decide what to act on (the target repository/commit), exactly mirroring how `MintableIncentivizedERC721.supportsInterface` claims compliance with an interface it never actually implements/checks.

### Impact Explanation
Depending on the event forged:
- `status` webhooks let the attacker call `Commit#create_status_from_github!` on any existing commit `sha` in the victim stack, which can fabricate a passing CI status. If the victim stack has `continuous_deployment` enabled and depends on that status context, this can help unlock/trigger an unauthorized deploy for a repository the attacker does not control — this reaches the "unauthorized deploy" Critical impact bucket.
- `push` webhooks can force `GithubSyncJob` to run for arbitrary tracked stacks (`Stack#sync_github`), and `check_suite`/`membership` handlers mutate other state (teams, check runs) for repositories/organizations outside the attacker's control.
- All of this is achievable without the victim's `webhook_secret`, GitHub App private key, or any Shipit session/ApiClient token — only knowledge of one (possibly the attacker's own) configured organization's `webhook_secret` in the same multi-tenant Shipit deployment.

### Likelihood Explanation
Requires a multi-organization `secrets.github` configuration (explicitly documented and supported) where the attacker legitimately administers/knows the secret for at least one configured organization sharing the instance with other, unrelated organizations/repos. This is a realistic operating mode for a shared, centrally-hosted Shipit instance serving several teams/orgs. No social engineering, TLS interception, stolen victim credentials, or privileged Shipit account is required — only the attacker's own legitimate org secret.

### Recommendation
Bind the signature-verification identity to the data the handlers act on: after selecting `webhook_secret` by `repository_owner`, re-validate that `repository.owner.login`/`organization.login` matches the owner segment actually used to resolve the target `Repository`/`Stack` (`repository.full_name`), and reject the webhook if they diverge. Alternatively, once the organization/app is resolved from a trusted source (e.g. from the installation id in a GitHub App-authenticated delivery, not from body content), verify that every repository referenced in the payload belongs to that same organization before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two organizations, `attacker-org` (secret `SECRET_A`, known to the attacker) and `victim-org` (secret `SECRET_B`, unknown to the attacker), both with stacks registered in the same instance.
2. Craft a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/critical-repo" },
  "sha": "<real sha of a commit on victim-org/critical-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, body)>`.
4. `POST /webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully against `SECRET_A`.
6. `StatusHandler#process` looks up `Commit.where(sha: ...)` — resolving the real commit on `victim-org/critical-repo` (unrelated to `attacker-org`) — and creates a forged passing status on it via `create_status_from_github!`, entirely outside the attacker's authorization scope, using a signature the attacker legitimately produced for their own organization.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
