### Title
`StatusHandler` writes commit CI status without checking that the commit belongs to the webhook-authenticated repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook by picking the GitHub organization's `webhook_secret` from a field inside the JSON body (`repository.owner.login` / `organization.login`) and verifying the HMAC over that same body. [1](#0-0)  That authentication only proves "this payload was sent by GitHub for organization X". Downstream, `Shipit::Webhooks::Handlers::StatusHandler#process` uses the `sha` field from the same payload to look up and mutate commit status records **globally**, with no check that the matched `Commit` actually belongs to a stack/repository owned by the authenticated organization:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

By contrast, `PushHandler` correctly scopes writes to the repository named in the payload via the shared `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)`: [3](#0-2) [4](#0-3) 

`StatusHandler` skips this scoping entirely, breaking the binding: *organization authenticated by the signature check* ≠ *repository (commit) actually written*.

### Finding Description
The `verify_signature` before_action selects the correct organization's secret from the payload and validates the HMAC-SHA1 signature against it, so the payload genuinely originates from GitHub for that organization's configured GitHub App/webhook. [5](#0-4)  This step never validates that the *content* fields the handler subsequently trusts are scoped to that same organization/repository.

`StatusHandler#process` then performs `Commit.where(sha: params.sha)` across the entire `commits` table (all stacks, all repositories, all organizations configured in this Shipit instance) and calls `commit.create_status_from_github!(params)` for every match. [2](#0-1)  `params.sha` is attacker-influenced content of the *signed* body (an unprivileged party can set it to any 40-character value), but it carries no cryptographic or referential link to the repository the signature was verified for.

Commit statuses drive both deploy gating (`Commit#deployable?`/CI hide-and-require logic) and the merge queue's `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` checks, which call `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)`. [6](#0-5)  If GitHub's Commit Status API is invoked to set a status for a `sha` that is valid in the sender's own repository context but happens to match a commit tracked by a *different* stack in the same Shipit deployment (e.g. shared history, vendored/forked commits, or any commit whose SHA the attacker can learn), the resulting webhook lets that unprivileged sender inject a passing (or failing) CI status onto a commit belonging to a stack/organization they were never authenticated for.

### Impact Explanation
Successful exploitation lets an attacker who only controls one organization onboarded to this Shipit instance forge a commit status for a commit under a different stack/organization. Because commit statuses gate `deployable?`/merge-queue checks, this can be used to mark an otherwise-blocked commit as CI-passing, enabling an unauthorized deploy or merge for a repository the attacker has no legitimate access to — matching the "unauthorized deploy, rollback, or merge" impact bucket.

### Likelihood Explanation
The attacker needs webhook delivery capability for at least one organization already configured in this Shipit instance (i.e. control of a repository whose events reach this Shipit engine) and knowledge of a target commit SHA in a different tracked stack — no Shipit session, ApiClient token, or GitHub App private key is required. The remaining difficulty (getting GitHub to deliver a `status` event referencing an arbitrary/foreign SHA) depends on external GitHub API behavior that this analysis could not fully verify from the engine code alone, so likelihood is assessed as medium rather than high.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload the same way `PushHandler` does, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or join through `Repository.from_github_repo_name(repository_name)`), so a commit status can only be applied to commits belonging to the organization/repository that the webhook signature was actually verified against.

### Proof of Concept
1. Attacker controls (or has webhook-triggering rights on) repository `attacker-org/attacker-repo`, which is configured as a Shipit-tracked stack with its own `webhook_secret`.
2. Attacker learns the SHA of a commit `deadbeef...` that is tracked by a different stack `victim-org/victim-repo` on the same Shipit instance (SHAs are not secret).
3. Attacker triggers (or crafts, via any means that produces a validly-signed `status` event for `attacker-org`) a `status` webhook payload: `{"sha": "deadbeef...", "state": "success", "context": "<required-ci-context>", "repository": {"owner": {"login": "attacker-org"}}, ...}`.
4. `WebhooksController#verify_signature` verifies the signature using `attacker-org`'s webhook secret — succeeds, because the payload really was delivered by GitHub for `attacker-org`. [1](#0-0) 
5. `StatusHandler#process` executes `Commit.where(sha: 'deadbeef...')`, which matches the commit belonging to `victim-org/victim-repo`, and records a passing CI status on it — with no check that `victim-org` has anything to do with the authenticated `attacker-org` webhook. [2](#0-1) 
6. That forged passing status can satisfy `required_statuses`/merge-queue checks on `victim-org/victim-repo`, enabling an unauthorized merge/deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
