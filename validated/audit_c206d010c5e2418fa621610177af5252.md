### Title
Missing minimum key-size enforcement for RSA public keys in `is_valid_sig`/`vrf_verify` oscript functions - ([File: signature.js])

### Summary
The `validateAndFormatPemPubKey()` function in `signature.js` enforces a fixed, algorithm-specific public-key length only for ECDSA curves, but performs **no minimum (or exact) key-size check at all for RSA keys**. This is directly analogous to CVE-2025-39889, where the Bluetooth L2CAP stack accepted an encryption key without verifying it met the required minimum key-size security parameter, silently downgrading cryptographic strength while reporting success.

### Finding Description
`validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix)` parses a DER-encoded SubjectPublicKeyInfo, determines the algorithm/curve OID, and then performs a key-length sanity check: [1](#0-0) 

This check is guarded by `objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA"`. For the RSA branch (`algo == 'RSA'`, OID `06092a864886f70d0101010500`), there is no corresponding length/modulus-size validation anywhere in the function: [2](#0-1) [3](#0-2) 

The only bound on RSA key material is an upper limit on the whole PEM content (`contentAloneB64.length > 736`, i.e. up to RSA-4096), used to cap parsing cost — not a lower bound: [4](#0-3) 

This function is reachable from the oscript functions `is_valid_sig()` and `vrf_verify()`, which are directly usable inside Autonomous Agent (AA) `getters`/`bounce`/`response` code, and their arguments (`message`/`seed`, `pem_key`, `sig`/`proof`) can all be sourced from `trigger.data`, i.e., fully attacker-controlled by any user posting a trigger to the AA: [5](#0-4) [6](#0-5) 

Both call sites pass `algo="any"` or `algo="RSA"` into `validateAndFormatPemPubKey`, so both are affected by the missing RSA size floor. Once `error` is null, `verifyMessageWithPemPubKey()` is invoked using Node's `crypto.createVerify('SHA256').verify()`, which will happily perform RSA verification with arbitrarily small (even single- or double-digit-bit) moduli: [7](#0-6) 

### Impact Explanation
An AA author who writes trust logic such as "accept this seed/message as authentic if it is signed under RSA key `pem_key`, and record/act on `pem_key` as a persistent identity/commitment" (e.g., for VRF-based lotteries, oracle attestations, or `is_valid_sig`-based external authorization schemes) relies on the runtime enforcing that an accepted `pem_key` provides adequate cryptographic security once validated. Because `validateAndFormatPemPubKey` performs zero minimum-size validation for RSA, a malicious trigger sender can submit a trivially small RSA modulus (e.g., a modulus that is easily factorable) as `pem_key`, compute the corresponding private key in negligible time by factoring, and then produce arbitrary valid `is_valid_sig`/`vrf_verify` signatures/proofs over content of their choosing. Any AA that stores or keys logic off a `pem_key` supplied in trigger data (rather than a fixed, hardcoded, adequately-sized key chosen by the AA author) as a durable identity/security anchor loses its unforgeability guarantee, which can be leveraged to manipulate VRF-driven randomness outcomes or forge externally-authenticated data that the AA uses to move funds — leading to AA fund loss or unfair fund distribution.

### Likelihood Explanation
Exploitation requires an AA that accepts an attacker-influenced `pem_key` and treats successful `is_valid_sig`/`vrf_verify` as a strong security property (a realistic and encouraged usage pattern for these primitives, e.g., VRF-based fairness schemes). No privileged access, node compromise, or network position is required — a single crafted trigger unit is sufficient.

### Recommendation
Add a minimum RSA modulus size check (e.g., reject moduli smaller than 2048 bits) in the RSA branch of `validateAndFormatPemPubKey`, mirroring the fixed-length check already applied to ECDSA curves at signature.js:180, so that no PEM key below an accepted security threshold can pass validation for `is_valid_sig` or `vrf_verify`.

### Proof of Concept
1. Generate a trivially small RSA key pair, e.g. `openssl genrsa 64 -out weak.pem` (or smaller if OpenSSL permits), and derive its public key.
2. Factor the tiny modulus (trivial for keys well under a few hundred bits) to recover the private key if not already known.
3. Sign an arbitrary message/seed with the weak private key.
4. Submit an AA trigger with `trigger.data = { message/seed, pem_key: <weak RSA public key PEM>, sig/proof: <forged signature> }` to an AA whose oscript uses `is_valid_sig(trigger.data.message, trigger.data.pem_key, trigger.data.sig)` or `vrf_verify(trigger.data.seed, trigger.data.proof, trigger.data.pem_key)` and subsequently trusts the outcome (e.g., stores `pem_key` as an authorized identity or uses the VRF output for a payout decision).
5. Observe that `validateAndFormatPemPubKey` accepts the weak key without error (no RSA-size floor at signature.js:180), and `verifyMessageWithPemPubKey` returns `true`, letting the attacker's forged data pass as cryptographically trustworthy.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
