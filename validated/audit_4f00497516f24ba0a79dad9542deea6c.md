### Title
Cross-stack CCMenu status disclosure via stack-scoped `ApiClient` token whose scope is never checked - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` tokens can be scoped to a single stack (`ApiClient#stack_id`), and `Shipit::Api::BaseController` is designed to enforce that scope on every request via its `stacks`/`stack` helpers. `Shipit::Api::CCMenuController` overrides `authenticate_api_client` and, more importantly, overrides `stack` to bypass the scoping entirely, resolving the target stack directly from the URL with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`. As a result, any valid token — even one deliberately restricted to a single stack for least privilege — can be used to read build/deploy status for any stack in the Shipit instance.

### Finding Description
The intended binding is: **the stack a token authorizes (`ApiClient#stack_id`) must equal the stack the token is used to touch (`params[:stack_id]` at the controller boundary)**. This is exactly the equality enforced in the base controller: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is confirmed to be the deliberate authorization model by `Shipit::Api::StacksController`, which also derives `stack` from the scoped `stacks` relation [2](#0-1) , and by the test asserting "an api client scoped to a stack will only see that one stack" [3](#0-2) .

`CCMenuController`, however, redefines `stack` to bypass the scope check entirely: [4](#0-3) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` [5](#0-4)  only calls `current_api_client.check_permissions!(operation, scope)` [6](#0-5) , which checks the *permission string* (`read:stack`) but never checks `stack_id` against the requested stack. Nothing in this controller checks whether `current_api_client.stack_id` (if set) matches the resolved `stack.id`.

Because `ApiClient#authentication_token` is a signed opaque token (`SimpleMessageVerifier`) that does not itself encode the stack scope in a checkable way at this call site, `ApiClient.authenticate(token)` only proves "this is a valid client," not "this client is authorized for this specific stack" — that check is supposed to happen in `stacks`/`stack`, and `CCMenuController` skips it.

### Impact Explanation
Any holder of a valid, even narrowly-scoped, API token (e.g., the `read:stack` "CCMenu Client" token minted per-user by `CCMenuUrlController` — note this one isn't stack-scoped either, but any stack-scoped token created via the `ApiClientsController` UI would be affected the same way) can query `/api/stacks/*stack_id/ccmenu` for any stack in the deployment, retrieving that stack's name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — data belonging to stacks/repositories the token was never meant to access. This is an escalation past the intended per-stack authorization boundary into cross-stack read of stack/build state, matching the "unauthenticated read of stack state" class of High-impact findings (the token is valid but not authorized for the target stack, i.e., the read is unauthorized for that resource).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires possession of *some* valid API token (any legitimately-scoped, low-privilege token suffices — there is no requirement that it be a global/unscoped admin token). Given that stack-scoped tokens are explicitly a supported least-privilege mechanism in the UI (`ApiClient belongs_to :stack, optional: true`), and tokens can be embedded in third-party CI dashboards/URLs (as `CCMenuUrlController` does), a token leaking or being intentionally minted with narrow scope is a realistic scenario the application's own design tries to guard against — but this controller silently defeats that guard.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the scoped `stacks` relation from `BaseController` instead of the unscoped `Stack.from_param!`:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Ensure `stacks` is reachable/works correctly given `authenticate_api_client` is overridden (it still sets `@current_api_client`, so `stacks` should function as in the base class). Add a regression test asserting that a token scoped to Stack A receives a 404/`RecordNotFound` when requesting `/api/stacks/<StackB path>/ccmenu`.

### Proof of Concept
1. As an authenticated Shipit user, create two stacks, `org/repo-a/production` and `org/repo-b/production`.
2. Via the `ApiClientsController` UI, create (or have an admin create) an `ApiClient` with `permissions: ['read:stack']` and `stack: repo-a-stack` (i.e., `current_api_client.stack_id?` is true, scoped to `repo-a`). Fixture `here_come_the_walrus` in the test suite demonstrates this exact configuration [7](#0-6) .
3. Obtain that client's `authentication_token`.
4. Send `GET /api/stacks/org/repo-b/production/ccmenu?token=<token>`.
5. Observe that `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning `repo-b`'s stack and rendering its CI/build status — despite the token being scoped only to `repo-a`. Compare with the equivalent request to `Api::StacksController#show` for `repo-b`, which correctly 404s because it uses the scoped `stacks.from_param!` helper.
