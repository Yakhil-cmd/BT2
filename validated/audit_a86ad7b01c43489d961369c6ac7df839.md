### Title
Cross-tenant `Status` injection via SHA-only commit lookup, bypassing repository/stack ownership check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no scoping to the repository that authenticated the webhook, unlike sibling handlers (e.g. `CheckSuiteHandler`) which correctly scope through `stacks` (derived from `Repository.from_github_repo_name(payload['repository']['full_name'])`). Since `Shipit::WebhooksController#verify_signature` only proves the request was signed by *some* organization's `webhook_secret` matching `repository_owner`, an attacker who legitimately controls a repository/organization onboarded to the same Shipit instance can emit a validly-signed `status` webhook whose `sha` matches a commit that also exists in a completely different (victim) stack, causing a `Status` row to be written with `stack_id: commit.stack_id` of the victim's stack.

### Finding Description
Intended binding: `write.stack_id == stack_owned_by(verified_repository.full_name)`, i.e. authorization to write `stack_id: commit.stack_id` should derive from the requester having proven control of that stack's own repository.

Actual code path:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`). This only proves the payload was signed by *the org named in the payload*, not that it corresponds to the specific `stack` whose commit will be mutated.
- `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a **global, unscoped** lookup across all `Commit` rows in the database — it never consults `stacks` (the `Repository.from_github_repo_name(repository_name)` scoping helper defined in the base `Handler` class, `app/models/shipit/webhooks/handlers/handler.rb:32-38`, and correctly used by `CheckSuiteHandler#process`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb:14`).
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) persists a new `Status` row with `stack_id: commit.stack_id` — the victim commit's real stack id.

Exploit flow: an attacker who owns/controls a repository under an organization already onboarded to this Shipit instance (so a genuine, correctly-signed `status` webhook can be produced for that org) forks or otherwise obtains a commit whose SHA1 is identical to a commit tracked in a victim's stack (git SHA1s are deterministic content hashes and are preserved across forks/cherry-picks with identical tree/parent/author/committer metadata). The attacker triggers (or directly POSTs, since only the signature and JSON body are checked, not TLS/session) a `status` event referencing that SHA. `verify_signature` accepts it because it is signed with the attacker's own org's secret. `StatusHandler#process` then matches the commit row belonging to the *victim's* stack purely by SHA and writes a `Status` scoped to `commit.stack_id`, which is the victim's stack, not any stack the attacker authenticated for.

Existing guards do not prevent this: `verify_signature` only authenticates "who signed this envelope", not "which stack/repository this envelope's contents may target"; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not scope; no `stacks`/`Repository#full_name` check is present in `StatusHandler`.

### Impact Explanation
An attacker who is a legitimate but low-privilege participant in one tenant/org's repository (or who otherwise controls any org already configured with a `webhook_secret` in this Shipit deployment) can inject fabricated CI `Status` records (`success`, `failure`, `error`, `pending`, arbitrary `description`/`target_url`) onto commits belonging to an unrelated victim's stack. Since `Commit#deployable?` and `Stack#continuous_deployment?`/`schedule_continuous_delivery` rely on aggregated status state, this can be used to force a victim commit into `success` state and trigger continuous deployment, or spoof `failure`/`error` states to block/gate the victim's deploy pipeline — a cross-tenant write mutating another stack's deploy-relevant state without ever holding that stack's credentials, matching the Critical category ("a payload for one repository mutating another's stack... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker must control at least one repository/org already registered with a `webhook_secret` in the Shipit instance (a normal, low-privilege situation for any onboarded org's contributor/forker), and must be able to produce or discover a commit SHA that coincides with one tracked by a victim stack — trivially achievable by forking the victim repository (SHA1 is preserved) and pushing/triggering a status event for that SHA from the fork, or crafting a request with any known SHA. No Shipit secrets, sessions, or API tokens are required. This is repeatable against any commit SHA the attacker can discover (e.g., via the victim's public GitHub history) and works for any number of victim stacks sharing that SHA.

### Recommendation
Scope `StatusHandler#process` (and any equivalent SHA-based lookups) to the commits reachable via `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), matching the pattern already used in `CheckSuiteHandler`, instead of a bare `Commit.where(sha: params.sha)` across the whole table.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s backed by two different `Repository`s (`full_name` "victim/repo" and "attacker/repo"), each with a `Shipit.github` config entry with its own `webhook_secret`.
2. Create a victim `Commit` (`stack: victim_stack`, `sha: SHARED_SHA`).
3. Build a `status` webhook payload with `sha: SHARED_SHA`, `repository.full_name: "attacker/repo"`, `repository.owner.login: "attacker"`, and sign it with `attacker`'s configured `webhook_secret` (i.e., a signature that only proves authenticity for `attacker/repo`).
4. `assert_difference -> { Status.where(stack_id: victim_stack.id).count }, 1 do post :create, body: payload, as: :json end`
5. Assert `response.status == 200`/`:ok` (request accepted) and that no `Status` was authenticated against `attacker_stack` — proving `Status.where(stack_id: victim_stack.id).count` incremented solely due to a webhook signed for the attacker's own organization, with no credential ever presented for `victim_stack`.
