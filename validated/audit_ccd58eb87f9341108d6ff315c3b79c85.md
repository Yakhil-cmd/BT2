### Title
Skill install silently redirects to an attacker-specified "upstream" repository based on unauthenticated frontmatter metadata - (File: pkg/cmd/skills/install/install.go)

### Summary
This is an analog of the reported bug class: trusting an attacker-controlled input (the freeze-authority-enabled token mint) without verifying an invariant, allowing the attacker to redirect/manipulate the intended trust target. In `gh skill install`, the equivalent untrusted "token" is the `github-repo` field embedded in a skill's `SKILL.md` frontmatter — content that lives inside the very (potentially malicious) repository the user is installing from — and it is used to redirect the entire install operation to a different, attacker-chosen repository without any independent verification.

### Finding Description
`checkUpstreamProvenance` in `pkg/cmd/skills/install/install.go` fetches `SKILL.md` from the repository the user asked to install from, parses its frontmatter, and reads a `github-repo` field: [1](#0-0) 

If that field differs from the current repo, the code treats it as evidence the skill was "re-published from an upstream source" and offers (or, in non-interactive mode with `--upstream`, automatically performs) a redirect of the entire installation to the repo named in that field: [2](#0-1) 

Back in `installRun`, when `checkUpstreamProvenance` returns a non-nil `upstreamRepo`, the code swaps `opts.repo` to the attacker-named repository and immediately recurses into `installRun` to install from it — with no additional validation that this "upstream" is legitimate, related to, or trusted relative to the originally specified repository: [3](#0-2) 

The only "authority" behind `github-repo` is a string embedded by the SKILL.md author — i.e., fully attacker-controlled content, analogous to the mint's freeze authority in the report: an untrusted, attacker-supplied property is trusted and acted upon by the protocol/tool without validating that it actually reflects a legitimate relationship.

### Impact Explanation
An attacker can publish a skill repository containing a `SKILL.md` with `github-repo` metadata pointing to any other repository (including one entirely controlled by the attacker, unrelated to the "original" skill). If a user runs `gh skill install attacker/repo --upstream` (non-interactive/CI use is explicitly supported and documented for this flag), the tool silently discards the user's chosen source and installs skill content from the attacker-designated target repo instead — which then gets written to disk as agent-skill instructions (already flagged elsewhere in the code as something that "may contain prompt injections, hidden instructions, or malicious scripts"): [4](#0-3) 

This can be used to smuggle a user into installing content from a completely different, attacker-nominated repository under the guise of "upstream provenance," bypassing the user's explicit repo selection. It does not achieve direct code execution by itself, but it undermines the integrity guarantee that "you get content from the repo you asked for," which is the core trust invariant the skill-install flow relies on.

### Likelihood Explanation
Requires the victim to pass `--upstream` (or interactively accept the redirect prompt) when installing a skill from an untrusted/attacker-published repository — a scenario explicitly supported by the CLI's own documented example for automation/non-interactive use. Interactive users are shown a warning and a choice, reducing likelihood in that mode; non-interactive/CI usage with `--upstream` set has no such safeguard.

### Recommendation
1. Do not allow `github-repo` frontmatter metadata from the source repo to unconditionally determine the install target. At minimum, cross-verify the claimed upstream by checking for reciprocal, cryptographically or API-verifiable linkage (e.g., a matching commit/tree SHA existing in both repos, or requiring the upstream metadata to be signed/verified) rather than trusting a plain string field.
2. In non-interactive mode, do not silently redirect installs even with `--upstream`; require explicit confirmation of the exact resolved owner/repo (print it and require an additional flag matching that value) before switching install targets.
3. Treat `github-repo` metadata purely as a display hint to the user, not as an actionable redirect target, unless independently corroborated.

### Proof of Concept
1. Attacker publishes `attacker/evil-skill` containing `skills/foo/SKILL.md` with frontmatter `github-repo: https://github.com/attacker/payload-skill`.
2. Victim, in a script or CI pipeline, runs:
   ```
   gh skill install attacker/evil-skill foo --upstream
   ```
3. `checkUpstreamProvenance` detects the mismatched `github-repo` metadata and returns `attacker/payload-skill` as the upstream repo (`pkg/cmd/skills/install/install.go:1337-1352`).
4. `installRun` swaps `opts.repo` to `attacker/payload-skill` and recurses, installing skill content chosen entirely by the attacker instead of from `attacker/evil-skill` (`pkg/cmd/skills/install/install.go:345-369`), with no verification that `payload-skill` has any real relationship to `evil-skill`.
