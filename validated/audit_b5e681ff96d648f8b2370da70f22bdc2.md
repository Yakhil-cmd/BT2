### Title
Vote weight for `system_vote_count` (op_list/threshold_size/tps params) is computed from live, un-snapshotted address balances, allowing flash-balance manipulation of system parameter votes - (File: main_chain.js)

### Summary
`countVotes()` in `main_chain.js` computes the weight of each cast `system_vote` by reading the voter's **current** confirmed balance at the moment the vote count is triggered, rather than a balance that was fixed/committed at the time the vote (or the `system_vote_count` trigger) was cast. Any unprivileged user can post a `system_vote_count` message at a time of their choosing, so an attacker can inflate their own address balance immediately before triggering the count and drain it immediately after, exactly mirroring the SALT "unstake to manipulate quorum" bug class: the parameter used to decide the outcome of a vote is re-evaluated at finalization time from a value the actor freely controls, instead of being fixed when the vote/trigger was created.

### Finding Description
`countVotes(conn, mci, subject, …)` is invoked once a `system_vote_count` trigger message becomes stable for a given `mci`: [1](#0-0) 

It then reads addresses that cast `system_votes` for the subject and computes their balance **at count time** with a live query over `outputs`/`units`: [2](#0-1) 

This balance is inserted into a temporary `voter_balances` table and used to weight both `op_list` votes and numeric parameter votes (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`): [3](#0-2) 

Crucially, the weight is the voter's balance *as it exists when the count actually executes*, not a balance fixed at the time the vote (`system_vote`) or the count-trigger (`system_vote_count`) unit was posted. A `system_vote_count` message can be posted by any address, unprivileged, at any time: [4](#0-3) [5](#0-4) 

Because the trigger is queued and executed on stabilization of a later MCI, an attacker controls both the timing of the trigger and, by moving bytes between their own addresses, the balance that will be read for weighting at that future point: [6](#0-5) 

This is the same root cause as the SALT bug: a decision (there: whether quorum is met; here: which value/OP-list wins the weighted vote) depends on a mutable, attacker-controlled quantity (there: `totalStaked`/voter stake; here: voter balance) that is *resolved at finalization time* instead of being snapshotted when the proposal/vote was created. The staker in SALT unstaked to shrink the denominator; here the voter can inflate the numerator (their own weight) right before triggering the count, then withdraw the funds afterward at no cost.

### Impact Explanation
`system_vote`/`countVotes` decides consensus-critical system parameters, including `op_list` (the list of Order Providers, i.e., analogous to witnesses used for main-chain stability determination) as well as `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` (fee/throughput parameters that affect fee validity and unit acceptance). A manipulated `op_list` outcome can shift control over main-chain stability/witnessing to addresses chosen by the attacker, and manipulated fee/TPS parameters can be used to bias validation of units network-wide. This can cause node disagreement on system-variable state or let a well-resourced (but not necessarily majority-holding) actor dictate consensus parameters — a Medium/High severity governance-integrity issue in a permissionless, unprivileged-poster-reachable path.

### Likelihood Explanation
The attack requires only that an actor (1) hold sufficient bytes to briefly consolidate into one voting address, (2) cast/refresh a `system_vote`, and (3) time-post an unprivileged `system_vote_count` trigger while the balance is inflated, then redistribute the funds afterward. No slashing, staking lock-up, or loss is incurred (only ordinary transaction fees), so the maneuver is essentially free and repeatable, similar to the zero-cost unstake/restake trick in the SALT report. The main constraint is that the attacker needs enough capital under their own control to sway a specific vote outcome at the moment of counting, but unlike a real stake-weighted system there is no commitment period preventing them from assembling that capital only momentarily.

### Recommendation
Snapshot voter balances (or, more robustly, a time-weighted/held-balance measure) at the time the vote (`system_vote`) is cast rather than re-reading live balances at `countVotes` execution time, or require the balance to have been held continuously since some minimum look-back window before the count executes rather than only "since_timestamp" windowing of the *vote*, which does nothing to prevent a fresh balance change on the voting address at the moment of counting. Alternatively, weight by a value that cannot be transiently inflated for free, such as balance integrated over time (coin-age) rather than instantaneous balance.

### Proof of Concept
Conceptual sequence (cannot be executed without a running network, but the code path is fully traced above):
1. Attacker holds bytes spread across several addresses they control; consolidates them into address `A`.
2. `A` posts a `system_vote` for `op_list` (or another subject) — accepted per `validation.js:1844-1859`.
3. `A` posts a `system_vote_count` trigger for the same subject — accepted unconditionally for any address per `uri.js:137-154` / composer support.
4. As soon as the MCI containing the trigger stabilizes, `main_chain.js`'s `saveUnstablePayloads` queues `subject` into `voteCountSubjects`, and after all `system_votes` for that MCI are recorded, `countVotes(conn, mci, subject)` runs and reads `A`'s balance live from `outputs`/`units` (main_chain.js:1757-1773), using it as `A`'s vote weight (main_chain.js:1850-1902).
5. Once the count is finalized and `system_vars` updated, `A` transfers the bytes back out to the original addresses — no funds are locked, slashed, or lost, and `A`'s momentary balance has already swung the vote result.
