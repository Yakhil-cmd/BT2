### Title
Per-recipient rounding in headers-commission share splitting allows supply inflation - ([File: headers_commission.js])

### Summary
`headers_commission.js` splits a unit's earned headers commission among multiple recipient addresses using independent `Math.round()` (or SQL `ROUND()`) operations on each recipient's percentage share, without renormalizing the sum back to the original commission amount. This is the same rounding-arithmetic flaw class described in the external report ("converting a token amount to shares and back… might lead to a higher amount than we started with"): each rounding operation can push a fractional share up, and because the roundings are independent, the sum of the rounded outputs can exceed the actual commission earned, minting extra bytes commission that becomes a spendable input.

### Finding Description
`earned_headers_commission_recipients` lets any unit author (even with a single author, since the "must specify" check in `validateHeadersCommissionRecipients` only forces its presence when `authors.length > 1`, but does not forbid it otherwise) declare a set of `(address, earned_headers_commission_share)` pairs whose shares must sum to exactly 100: [1](#0-0) 

When a unit wins the headers commission from a parent, the full amount is distributed among these recipients by rounding each recipient's fractional share independently, both in the SQL path and the in-memory/JS path: [2](#0-1) [3](#0-2) 

Because `Math.round()`/SQL `ROUND()` rounds each recipient's share separately with no compensating adjustment (e.g., giving the last recipient the remainder), the total distributed can be strictly greater than `full_amount`. For example, with shares `33/33/34` summing to 100 and `full_amount = 99`: `99*33/100 = 32.67 → 33`, `99*33/100 = 32.67 → 33`, `99*34/100 = 33.66 → 34`; total = `100`, one unit more than the `99` actually earned. An attacker who authors the winning child unit fully controls both the number of recipient addresses (all of which they can own) and their exact percentage split, and can therefore choose shares that maximize the rounding-up effect across all recipients for every unit they compose, repeatedly, over time.

The resulting inflated amounts are inserted directly into `headers_commission_contributions` and then aggregated into `headers_commission_outputs`: [4](#0-3) [5](#0-4) 

These `headers_commission_outputs` records are later spendable as a valid input type, so the extra amount is not just an accounting artifact — it becomes real, spendable bytes, i.e., an unbacked increase in the total spendable byte supply.

### Impact Explanation
This falls under "supply inflation," one of the accepted impact categories: a unit author can systematically cause the commission paid out to (self-controlled) recipient addresses to exceed the commission actually collected from the parent unit, minting bytes out of thin air. Repeated across many authored units, this creates a low-but-nonzero, systematically exploitable inflation channel with no economic cost beyond authoring ordinary units and controlling the winning-child selection race (which, per `getWinnerInfo`, is a hash-based lottery among candidate children rather than something the attacker fully controls — this reduces reliability of exploitation and is a mitigating factor, discussed below).

### Likelihood Explanation
Exploitation requires the attacker's unit to be selected as the "winner" child unit for a given parent by `getWinnerInfo` (a SHA1-hash tiebreak among candidate children when there is more than one), so the attacker cannot deterministically guarantee winning every time, only some fraction of attempts. This lowers likelihood versus a fully deterministic exploit, but since:
- posting many low-cost units is cheap,
- the attacker fully controls the recipient list and share split whenever their unit *does* win,
- and the per-unit gain, while small, is systematic and repeatable at scale,

the vulnerability is realistically and repeatedly reachable by an unprivileged unit author over time, which is why it is scored as Medium rather than High.

### Recommendation
Do not round each recipient's share independently. Instead, compute integer amounts that are guaranteed to sum exactly to `full_amount`, e.g., allocate `floor(full_amount * share / 100)` to each recipient and then distribute the remaining leftover units deterministically (e.g., to the recipient(s) with the largest fractional remainder, or entirely to a canonical last recipient by sort order), so the sum of all payouts can never exceed the original `full_amount`. Apply the same fix consistently to both the SQL (`ROUND(...)`) and in-memory JS (`Math.round(...)`) code paths in `headers_commission.js`, and audit `paid_witnessing.js` for the same pattern since it performs an analogous percentage-share split.

### Proof of Concept
1. Attacker composes a unit `U` (single author is sufficient) that declares `earned_headers_commission_recipients` = `[{addrA, share:33}, {addrB, share:33}, {addrC, share:34}]` (sum = 100, all addresses controlled by attacker), satisfying `validateHeadersCommissionRecipients`. [6](#0-5) 
2. Attacker arranges (or repeatedly attempts, relying on the hash lottery in `getWinnerInfo`) for `U` to be selected as the winning child unit of some parent unit `P` whose `headers_commission` (`full_amount`) is `99` bytes. [7](#0-6) 
3. `calcHeadersCommissions` computes, for `U`, per-recipient amounts: `round(99*33/100)=33`, `round(99*33/100)=33`, `round(99*34/100)=34`, inserting a total of `100` into `headers_commission_contributions`/`headers_commission_outputs` even though only `99` was actually earned from `P`. [2](#0-1) 
4. These `headers_commission_outputs` become valid, spendable inputs for the attacker's addresses, realizing a net gain of `1` byte beyond what was legitimately earned. Repeating this across many authored units compounds the inflation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

function getWinnerInfo(arrChildren){
	if (arrChildren.length === 1)
		return arrChildren[0];
	if (arrChildren.length === 0)
		throw Error("no children for hc");
	arrChildren.forEach(function(child){
		child.hash = crypto.createHash("sha1").update(child.child_unit + child.next_mc_unit, "utf8").digest("hex");
	});
	arrChildren.sort(function(a, b){ return ((a.hash < b.hash) ? -1 : 1); });
	return arrChildren[0];
}
