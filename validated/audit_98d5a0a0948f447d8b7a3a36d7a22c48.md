### Title
Git pathspec-magic injection via attacker-controlled filenames in `_diff_pathspec` lets an attacker suppress or widen the security-review diff - (File: plugins/security-guidance/hooks/gitutil.py)

### Summary
`_diff_pathspec` converts touched-file absolute paths into repo-relative strings and splices them, unescaped, after a single `"--"` separator into the `git diff` argv built by `get_git_diff`. Because `"--"` only stops option parsing and does **not** disable git's per-pathspec magic syntax (`:(exclude)…`, `:!…`, `:(glob)…`, etc.), a relpath whose value happens to start with `:` is interpreted by `git diff` as a pathspec-magic token rather than a literal filename.

### Finding Description
`_diff_pathspec(cwd, paths)` (plugins/security-guidance/hooks/gitutil.py, lines 70-88) does:
```python
r = os.path.relpath(os.path.realpath(p), cwd_abs)
...
rel.append(r)
...
return ["--"] + rel if rel else []
```
It performs no escaping, no `:(literal)` prefixing, and `GIT_CMD` (lines 25-29) does not set `--literal-pathspecs`. `get_git_diff` (lines 391-427) then builds:
```python
cmd = [*GIT_CMD, "diff", ..., baseline_sha] + [...] + pathspec
```
and runs it with `subprocess.run(cmd, ...)`.

Git's pathspec magic is recognized whenever a pathspec argument *itself* starts with `:` — this is unaffected by the preceding `--` separator, which only tells git's arg parser "everything after this is a pathspec/positional argument," not "everything after this is literal." If an attacker creates (or gets the agent to touch) a file whose *basename* is, e.g., `:(exclude)*` or `:!*` located directly at the repo root, then `os.path.relpath(...)` for that file yields exactly that string with the leading `:`, since nothing else is prefixed to it in the top-level case. When this string is placed among the other relpaths after `--`, git parses it as pathspec magic instead of a literal filename:
- `:(exclude)*` (or `:!*`) as one of several pathspecs makes git treat "everything except `*`" as the effective selection, which — combined with union semantics of multiple pathspecs — can suppress the other legitimately touched files from the diff output entirely.
- More narrowly, `:(exclude)<other-touched-relpath>` can be crafted to exclude a *specific* other touched file from the diff while still returning content for the attacker's own file, defeating the "diff must be restricted to touched paths" invariant in either direction (exclude sensitive files from review, or, depending on crafted magic like `:(glob)`, widen matching beyond the intended literal path).

Nothing in the code path validates or neutralizes a leading `:` in the relpath before it is spliced into the argv; the `"--"` separator is the only mitigation and it does not address this class of injection.

### Impact Explanation
This function feeds the diff that is sent to the security-review LLM prompt (`get_git_diff` → diff/parsing pipeline used by `security_reminder_hook.py`). A crafted-filename attack can cause modifications to sensitive/other files touched in the same turn to be silently dropped from the diff shown to the reviewer, defeating the security-guidance plugin's core invariant that the reviewed diff is restricted to (and inclusive of) the actually-touched paths. This is a trust-boundary/review-bypass bug in a security control, matching a "security control / detection bypass" class of impact rather than direct code execution.

### Likelihood Explanation
Preconditions: the attacker needs a file at repo top level whose basename begins with git pathspec magic characters (`:`, e.g. `:(exclude)*`), and the agent must subsequently "touch" (edit/write) that path so it enters the `paths` list passed into `get_git_diff`/`_diff_pathspec`. This is plausible in an unprivileged setting: a malicious repository can pre-seed such a file, or a prompt-injected instruction can induce the agent to create/edit a file with that name. No admin privilege, leaked keys, or maintainer trust is required — only ordinary repository content and normal agent file-edit flow. Feasibility depends on the exact call sites in `security_reminder_hook.py` that assemble the `paths` list (not fully confirmed from the excerpt reviewed), which determines whether attacker-named paths can reach `get_git_diff` unfiltered; this remains to be verified against that file's `compute_v2_review_set`/touched-path collection logic.

### Recommendation
Escape/neutralize pathspec magic when building `_diff_pathspec`'s relpaths — either invoke git with `--literal-pathspecs` (globally in `GIT_CMD`) or prefix every relpath with the `:(literal)` magic (e.g. `f":(literal){r}"`) before appending to `rel`, so arbitrary filenames can never be interpreted as pathspec magic regardless of their leading characters.

### Proof of Concept
Unit test (differential) in a temp git repo:
1. Create repo, commit baseline.
2. Create file literally named `:(exclude)secret.py` at repo root with sensitive content, and a second normal file `secret.py` also modified.
3. Call `get_git_diff(cwd, baseline_sha, paths=[os.path.join(cwd, ":(exclude)secret.py"), os.path.join(cwd, "secret.py")])`.
4. Assert the returned diff text contains changes for `secret.py` (or the maliciously-named file) as expected for a literal-path restriction, i.e. both files' changes appear.
5. Compare against a control run where the same content is passed through a pathspec-escaped/literal variant (e.g. manually prefixing `:(literal)`), and assert **set-equality** of files reported in both diffs.
6. Expected failure without the fix: the unescaped run's diff is missing `secret.py` (or is empty) because `:(exclude)secret.py`'s basename was interpreted as magic, demonstrating the invariant violation; the fixed (`:(literal)`-prefixed) version includes both files, showing the set mismatch.
