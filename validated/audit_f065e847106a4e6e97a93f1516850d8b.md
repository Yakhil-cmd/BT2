### Title
Cross-organization webhook spoofing: authenticated organization ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook's HMAC signature against based on an **unverified** field taken directly from the JSON payload (`repository.owner.login` or `organization.login`), rather than from any property tied to the actual signing key used by GitHub. In a multi-organization Shipit deployment (as documented in `docs/setup.md`, "Using Multiple Github Applications"), an attacker who controls one onboarded GitHub organization (and thus legitimately knows that organization's `webhook_secret`) can forge a signature that Shipit accepts, while embedding a different organization's/repository's `repository.full_name` in the body. Downstream handlers act on that unverified `full_name` to identify the `Stack`/`Commit` to mutate, breaking the binding: `organization authenticated by signature == repository whose data is written`.

### Finding Description
`verify_signature` computes `repository_owner` from the raw payload and uses it purely to select the `GitHub App` config/secret to validate against: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
and [2](#0-1) 

The signature is only checked against the HMAC secret belonging to `repository_owner`; it never binds the *content* of the payload (e.g., `repository.full_name`) to the organization whose secret validated it — `verify_webhook_signature` itself just does a raw HMAC compare against the whole raw body, but that body's `repository.full_name` can freely name a different org/repo than `repository.owner.login`: [3](#0-2) 

The event `create` action then dispatches the full (attacker-controlled) params to handlers: [4](#0-3) 

Handlers resolve the target `Stack`(s) using `repository.full_name` from that same untrusted payload, independent of `repository_owner`: [5](#0-4) 

For example, `PushHandler` uses `stacks` (scoped by that `full_name`) to trigger a GitHub sync against real branch/commit data: [6](#0-5) 

The `StatusHandler` is even less scoped — it looks up commits purely `by sha` with no repository/organization check at all before writing a `Status`: [7](#0-6) 

Because `Shipit` supports multiple GitHub Apps/organizations each with its own `webhook_secret` (per `docs/setup.md`), an attacker who is a legitimate collaborator/admin of one onboarded organization "attacker-org" knows that organization's real `webhook_secret` (it's configured by that org's own GitHub App admin, not secret to Shipit operators globally — the org's own webhook settings page shows/lets them set it). They can then craft an arbitrary payload body with `repository.owner.login = "attacker-org"` (or `organization.login`) so `verify_signature` selects and validates against the attacker-org's key, while setting `repository.full_name = "victim-org/victim-repo"` (or an arbitrary `sha`/branch) so downstream handlers mutate the victim's `Stack`, trigger a `GithubSyncJob`, or write a bogus commit `Status`.

### Impact Explanation
This breaks the deployment-trust binding "GitHub organization whose signature authenticated the webhook == repository/stack whose state is written." A user who is an admin of any single organization onboarded to a shared Shipit instance can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that write/modify state belonging to *other* organizations' stacks — e.g., forcing spurious `GithubSyncJob`s, injecting fabricated commit statuses that could unblock a deploy (`StatusHandler` writes statuses with no ownership check, feeding into `deployable?`/CI gating logic), or manipulating `Membership`/`Team` records tied to an org name they don't own. This can escalate into unauthorized deploy triggering paths gated on commit status, satisfying the High-impact bar (unauthenticated cross-boundary write into another org's stack state / bypass of CI gating used to authorize deploys).

### Likelihood Explanation
Requires the target Shipit instance to run in the documented multi-organization configuration and requires the attacker to control (or admin) at least one of the onboarded organizations — a materially lower bar than compromising the victim org or Shipit itself. No Shipit account, `ApiClient` token, or GitHub App private key is needed; only knowledge of one legitimate org's `webhook_secret`, which is set and visible to that org's own GitHub App administrators.

### Recommendation
Bind the payload's `repository.full_name` (and `organization.login` for org-scoped events) to the same organization that was used to select/verify the signature before dispatching to handlers — reject the webhook if `repository.owner.login`/`organization.login` used for `Shipit.github(organization:)` does not match the resolved `Stack`'s configured GitHub organization. Additionally, `StatusHandler#process` should validate that the `Commit`'s stack belongs to the organization/repository that was actually authenticated, not just match by `sha` globally.

### Proof of Concept
1. Onboard "attacker-org" to the shared Shipit instance per `docs/setup.md`'s multi-org config; obtain its `webhook_secret` (attacker is an org owner/admin who configured it).
2. Build payload:
```json
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<any sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, validates using the attacker's own secret — passes — while `PushHandler` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` and enqueues `GithubSyncJob` for the victim's stack. [8](#0-7) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
