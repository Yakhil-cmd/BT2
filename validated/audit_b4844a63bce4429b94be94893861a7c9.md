### Title
Predictable/attacker-grindable "randomness" via `number_from_seed()` in oscript (AA gambling contracts) - (File: formula/evaluation.js)

### Summary
oscript, the smart-contract language for Autonomous Agents (AAs), exposes a `number_from_seed(seed[, min, max])` primitive that AA authors use to generate pseudo-random numbers for lottery/dice/gambling-style AAs. The function is implemented as a pure, deterministic SHA-256 hash of a seed value, with no protocol-enforced binding to information that is unknown to the trigger sender at composition time. Because every input typically available to an oscript formula (`trigger.data`, `trigger.unit`, `trigger.address`, `timestamp`, state variables, `mc_unit`) is either fully chosen by the attacker or already known/computable by them before they decide whether to broadcast the triggering unit, an attacker can precompute the resulting "random" number off-chain for any candidate seed and only submit the trigger when the outcome favors them. This mirrors the EosRoyale incident, where the attacker precomputed the RNG output from public/previous-block data before committing a bet.

### Finding Description
`number_from_seed` is implemented in `formula/evaluation.js`: [1](#0-0) 

The seed is hashed with `crypto.createHash("sha256")`, and the first 16 hex chars of the digest are turned into a float in `[0,1)` (optionally scaled to `[min,max]`). This is a fully deterministic, publicly-computable function of the `seed` value with no VRF, no commit-reveal, and no dependency on data that is unpredictable to the party who decides whether to submit the triggering unit.

AA source code is public (definitions are stored on-chain and readable via `is_aa`/`definition[...]`), so any user can read a deployed gambling AA's oscript formula, see exactly what value(s) it treats as the "seed" (commonly `trigger.unit`, `trigger.data.*`, `trigger.address`, `timestamp`, or `response_unit`), simulate the SHA-256 computation locally for every candidate value, and only broadcast the unit whose resulting seed produces a winning outcome. Trigger content such as `trigger.data` is entirely attacker-supplied (validated only by `formula/validation.js`, not restricted in content), and `trigger.unit` is the hash of a unit the attacker composes and can iterate on (e.g., via unused fields, message ordering, or nonce-like additions to `data`) until a favorable hash is found — a classic hash-grinding/seed-grinding attack, analogous to attacker-controlled block-hash-based RNGs. [2](#0-1) [3](#0-2) 

Even where `response_unit` is used as a seed (as seen in test fixtures), because AA evaluation and message/state formulas are pure functions of already-known trigger content, address state, and the deterministic AA definition, a locally-run AA simulator lets the attacker predict the resulting `response_unit` hash and therefore the "random" outcome before ever broadcasting, since none of the mainstream oscript primitives combine the seed with future unpredictable network randomness (e.g., a delayed VRF output revealed only after commitment). The language does provide `vrf_verify` for verifying externally supplied VRF proofs, but this requires the AA author to correctly integrate an off-chain VRF service with a commit-reveal scheme; `number_from_seed` itself provides no such protection and its misuse is the natural/expected way most simple lottery AAs are written given the available primitives.

### Impact Explanation
Any AA that uses `number_from_seed()` seeded (directly or indirectly) by attacker-controlled or attacker-predictable inputs (trigger data, trigger unit hash, timestamp, response unit) to decide payouts can be biased by an unprivileged trigger sender to always "win," draining the AA's balance — a direct AA fund loss, exactly matching the impact category of the EosRoyale incident (theft of pooled funds via RNG prediction/manipulation).

### Likelihood Explanation
Likelihood is high for any deployed gambling/lottery AA built with this primitive: the attacker only needs read access to the public AA definition (always available on-chain) and the ability to run the same deterministic hash/oscript logic off-chain, which requires no special privilege — only the capacity to compose and, if needed, iterate over candidate trigger units before broadcasting, which is available to any wallet holder able to post units.

### Recommendation
- In `formula/evaluation.js`, discourage/flag `number_from_seed` usage where the seed depends solely on attacker-controlled/predictable values known before broadcast; provide safer built-ins/patterns (e.g., a native commit-reveal helper, or a mechanism binding the seed to unpredictable future data such as an as-yet-unknown MC unit content or a VRF output from an oracle revealed only after the trigger is locked in).
- Extend AA developer documentation/linting to explicitly warn that `trigger.unit`, `trigger.data`, `timestamp`, and `response_unit` are all attacker-predictable or attacker-chosen and must never be used alone as gambling seeds; recommend combining with a value from a trusted oracle's data feed posted strictly after the bet is placed, or a two-phase commit-reveal AA pattern.
- Consider adding protocol-level support (or a documented reference implementation) for delay/commit-reveal so seeds are only finalized after the trigger unit becomes irrevocably included and stable, removing the attacker's ability to grind or bail out.

### Proof of Concept
1. Attacker reads a deployed gambling AA's public definition and observes: `state: "{ $r = number_from_seed(trigger.unit, 0, 99); if ($r < 50) send prize; }"` (representative pattern).
2. Attacker composes candidate trigger units (varying an unused `data` field as a nonce) and, for each candidate, computes its unit hash `trigger.unit` locally exactly as `object_hash.getUnitHash` would.
3. For each candidate hash, attacker runs `sha256(candidate_unit_hash)` and applies the same scaling used in `number_from_seed` (`formula/evaluation.js` lines 1893-1917) to predict `$r` off-chain, at zero cost.
4. Attacker only broadcasts the specific candidate unit whose predicted `$r` results in a win, guaranteeing a payout every time and draining the AA's balance — reproducing the EosRoyale-style RNG-prediction theft.
