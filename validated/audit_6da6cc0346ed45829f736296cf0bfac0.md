### Title
Webhook signature verification is scoped to the wrong field, letting an org with no `webhook_secret` forge events for any other organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* organization's secret to verify the HMAC against using `repository_owner` (`params.dig('repository', 'owner', 'login')`), but every event `Handler` acts on the *different*, independently-attacker-controlled field `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (as shown by the supported config shape in `test/dummy/config/secrets_double_github_app.yml`), an organization configured with `webhook_secret: nil` causes `GitHubApp#verify_webhook_signature` to `return true unless webhook_secret`, i.e. signature checking is skipped entirely for that org. An attacker who can reach the public `/webhooks` endpoint can therefore craft a raw payload where `repository.owner.login` is the secret-less org (bypassing verification) while `repository.full_name` names a *different* organization's repository, and have that forged event processed against the victim org's stack.

### Finding Description
The signature check binds trust to `repository_owner`: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

But every concrete handler resolves the repository to act on from a *different* field of the same JSON body: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` and `repository.full_name` are two independent JSON fields; nothing ties them together cryptographically or logically before the handler acts. Signature verification itself is per-organization and is a no-op when that organization has no configured secret: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The engine explicitly supports multiple organizations, each with its own optional `webhook_secret`, resolved dynamically via `Shipit.github(organization:)` / `github_app_config`: [5](#0-4) 

and the docs/dummy fixtures confirm `webhook_secret` is optional and per-organization: [6](#0-5) 

The binding that should hold is: **organization that authenticated (the org whose secret validated the request) == organization that owns the repository being written (the repo the handler mutates)**. The code instead only enforces "some configured org's secret validated" and lets a completely separate `full_name` drive the write. Any tenant/org in the deployment configured without a `webhook_secret` (an explicitly documented, optional setting) becomes a skeleton key: pick that org as `repository.owner.login` to sail through `verify_signature` unauthenticated, then put any victim org/repo into `repository.full_name` to have the payload dispatched against that victim's stacks.

### Impact Explanation
This is an authentication-bypass primitive on the entire `/webhooks` surface for any stack tracked by the Shipit instance, not just the secret-less org's own repos. Concrete forgeable, unauthenticated effects include:
- `push` events driving `stack.sync_github(expected_head_sha:)` on an arbitrary victim stack via `PushHandler#process`, with an attacker-chosen `after` SHA [7](#0-6) .
- `status`/`check_suite` events writing fabricated commit/check statuses that CI-gate deploys and the merge queue for a repository the attacker does not own.
- `pull_request`/`membership` events mutating state (labels, team/user membership) for stacks outside the attacker's organization.

Because this can inject fabricated deployability signals (status/check state) that gate `Stack` deploy/merge decisions, it crosses into the "escalation into `Shipit.github_teams` authorization" / unauthenticated write territory that the rules treat as High/Critical, without requiring any Shipit session, API token, or GitHub credentials from the attacker — only that the deployment hosts ≥2 organizations and at least one lacks a `webhook_secret`.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization omits `webhook_secret` (an explicitly supported/optional field per `docs/setup.md` and the `secrets_double_github_app.yml` fixture). Given that, exploitation needs no credentials at all — just a raw HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and an `X-Github-Event` header; the `X-Hub-Signature` header can be omitted or arbitrary because verification short-circuits to `true`.

### Recommendation
- In `Handler#repository_name`, verify that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) matches the org used to select/verify the webhook signature (`repository_owner` in the controller) before resolving `Repository.from_github_repo_name`; reject on mismatch.
- Do not allow `verify_webhook_signature` to silently succeed (`return true unless webhook_secret`) for configured multi-org deployments; require every organization entry to have a non-blank `webhook_secret`, or fail closed if any org in a multi-org config is missing one.
- Additionally check that the resolved `Repository`'s stored `owner` matches `repository_owner` from the verified organization before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` (has `webhook_secret`) and `OrgTwo` (`webhook_secret: nil`), both installed on the same Shipit instance and both having stacks (e.g. `OrgOne/victim-repo` is tracked).
2. As an unauthenticated attacker, `POST /webhooks` with:
   - Header `X-Github-Event: push`
   - No/garbage `X-Hub-Signature`
   - Body: `{"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"OrgTwo"},"full_name":"OrgOne/victim-repo"}}`
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — the request passes.
4. `PushHandler` resolves `repository_name` as `OrgOne/victim-repo` (unrelated to `OrgTwo`) and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `OrgOne`'s stack, despite the request never being authenticated against `OrgOne`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
