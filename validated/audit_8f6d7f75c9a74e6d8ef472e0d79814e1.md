Based on my research, I found a valid analog vulnerability in ocore's asset attestation mechanism.

### Title
Asset definer can freeze/revoke already-distributed asset holdings by unilaterally updating the attestor list at any time - ([File: validation.js])

### Summary
The Sherlock report describes a vesting-escrow `revokeAll()` function where a privileged `owner` can seize `unclaimed()` tokens that rightfully belong to the recipient, with no check that the vesting/claim period has actually ended. The core issue is: **a privileged party retains unilateral, unbounded power over funds that should already belong to another party, with no protection once those funds have been legitimately earned/distributed.**

The analogous pattern exists in ocore's `spender_attested` asset feature. When an asset is created with `spender_attested: true`, only addresses on the definer's current attestor list are allowed to hold/spend that asset. Critically, this attestor list is checked dynamically at the *time of each spend*, not fixed at the time the tokens were received. The definer can call `asset_attestors` to update the list at any time, unilaterally removing a previously-attested address, which retroactively freezes that holder's already-received asset balance even though it was legitimately transferred/earned.

### Finding Description
When an asset has `spender_attested: true`, `validatePaymentInputsAndOutputs` checks that both output recipients and current input owners are on the live attestor list: [1](#0-0) [2](#0-1) 

The attestor list itself is fully controlled by the asset's `definer_address` and can be replaced at will, with no restriction tied to already-issued/held balances, and no requirement to preserve previously attested addresses: [3](#0-2) 

`readAsset`/`filterAttestedAddresses` always resolve the *latest* attestor list unit (as of `last_ball_mci`), so once the definer publishes a new `asset_attestors` message dropping an address, that address's existing balance in the asset becomes permanently unspendable going forward, even though the tokens were legitimately transferred to it earlier under the original attestor set: [4](#0-3) 

This mirrors the reported bug class exactly: the asset definer is the "owner"; the attested holder is the "vesting recipient"; the tokens already transferred are the "vested/unclaimed funds." There is no check analogous to "vesting has ended, no more revocation allowed" - the definer can revoke spending rights for previously-earned holdings at any point, indefinitely, exactly like the `revokeAll()` function lacking a check that vesting already concluded.

### Impact Explanation
Any holder who received a `spender_attested` asset legitimately (via the intended issuance/attestation process) can have their balance permanently frozen by the definer simply publishing an updated attestor list that excludes them. This is a direct AA/asset-holder fund freezing vector reachable by an ordinary asset issuer message - no privileged network role, node compromise, or off-chain access required. It is a first-class asset issuance/transfer condition abuse within the protocol's own consensus rules, causing genuine node-observable freezing of a user's funds (their outputs become permanently unspendable under valid consensus rules).

### Likelihood Explanation
Likelihood is high for any asset that opts into `spender_attested`. The mechanism is a core, intentionally exposed asset feature (used in `checkAttestorList`/`asset_attestors` messages), and the definer's ability to rewrite the attestor list is unrestricted and requires only a single, cheaply-postable unit. Any asset issuer acting maliciously (or simply careless/compromised) can trigger this at any time after distribution, with no coordination or race condition required.

### Recommendation
Introduce a rule preventing the definer from removing addresses from the attestor list that already hold a nonzero balance of the asset (or grandfather already-attested holders for spending purposes, even if removed from future issuance eligibility). Alternatively, snapshot the attestor list applicable to an output at the time it was created and validate spends against that historical list rather than the currently active list, so that legitimately distributed holdings cannot be retroactively frozen by later definer actions - similar to adding a "vesting has ended, no more revocation" guard in the reported Solidity bug.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Definer (or an issuance flow) transfers/issues tokens of asset `A` to address `X`. Validated successfully since `X` is attested: [1](#0-0) 
3. Later, definer posts a new `asset_attestors` message with `attestors: [Y]` (excluding `X`), validated via `validateAttestorListUpdate`: [3](#0-2) 
4. Address `X` now attempts to spend its previously-received, legitimate balance of asset `A`. Validation re-reads the live attestor list (excluding `X`) and rejects the spend: [5](#0-4) 
5. `X`'s funds are permanently frozen, mirroring the reported bug where an "owner" retroactively strips rights over already-earned/distributed funds.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
