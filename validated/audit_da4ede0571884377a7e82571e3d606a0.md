### Title
Malformed private-payment payload triggers double-processing and uncaught-exception crash in `handleSavedPrivatePayments` - (File: network.js)

### Summary
A private-payment counterparty can send a private payment chain (`arrPrivateElements`) whose head payload is structured so that `objectHash.getBase64Hash()` throws (e.g. contains a `null` value, a lone-surrogate/00-byte string, an empty array/object, or a non-finite number — all of which cause `getSourceString`/`getJsonSourceString` to `throw Error(...)`). `network.js`'s `handleSavedPrivatePayments()` catches that exception but fails to `return` from the `catch` block, so execution falls through and the same async iteration's `cb` is invoked twice (once via `deleteHandledPrivateChain()` in the catch block, and again via the full `privatePayment.validateAndSavePrivatePaymentChain()` path), while also proceeding to process a chain whose backing DB row was already deleted. This can throw uncaught exceptions (e.g. the various invariant `throw Error(...)` calls in `initPrivatePaymentValidationState`/`private_payment.js`/`writer.js` that assume "never happens" states) which propagate to `network.js`'s global `process.on('uncaughtException', ...)` handler, which explicitly does `throw err; // crash the process to avoid ending up in an inconsistent state`, killing the whole node.

### Finding Description
`handleSavedPrivatePayments()` iterates queued rows from `unhandled_private_payments` (populated by `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`, which accept private-payment JSON sent by any correspondent/peer) and for each row calls `validateAndSave()`: [1](#0-0) 

The `try { getBase64Hash(...) } catch (e) { ...; deleteHandledPrivateChain(row.unit, ..., cb); }` block has no `return` statement after handling the error. Execution therefore continues past the `catch` and immediately calls: [2](#0-1) 

with `json_payload_hash` left `undefined` (declared with `var` inside the `try`, hoisted). This means:
1. `cb` (the `async.each` iteratee callback) gets scheduled to be called twice — once by `deleteHandledPrivateChain`'s async DB callback, and again later by whichever of `ifOk`/`ifError`/`ifWaitingForChain` fires inside `privatePayment.validateAndSavePrivatePaymentChain`, which itself calls `deleteHandledPrivateChain(..., cb)` a second time: [3](#0-2) [4](#0-3) 

2. The chain is validated a second time against a row that the first branch already deleted from `unhandled_private_payments`, and validation itself performs direct queries and hard invariant checks (e.g. `if (rows.length > 1) throw Error("more than 1 message by index");`, `if (rows.length > 1) throw Error("more than one output "...)`) that are not designed to tolerate concurrent/duplicate processing of the same chain: [5](#0-4) [6](#0-5) 

Any of these thrown `Error`s is uncaught in this asynchronous DB-callback context and is caught only by the module-level handler: [7](#0-6) 

which deliberately re-throws to crash the node process ("crash the process to avoid ending up in an inconsistent state"). Since this handler exists specifically because the codebase relies on process death as a safety net for unexpected invariant violations, any attacker-reachable path that hits one of these "should never happen" throws is a genuine remote/local DoS, analogous to the reported Sandboxie bug where a malformed but unprivileged-reachable input causes a code path that was only exercised for well-formed data, crashing the whole component instead of being validated and rejected.

The attacker-controlled trigger is the private-payment payload itself: a private-payment counterparty (someone the wallet exchanges private payments with, or anyone who can get a private-payment JSON queued into `unhandled_private_payments` via `handleOnlinePrivatePayment`) fully controls `objHeadPrivateElement.payload`, and can shape it (e.g., insert `null`, non-finite numbers, or 00-byte-containing strings inside `outputs`/`inputs`/`asset` fields) to reliably make `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throw, entering the buggy fallthrough path.

### Impact Explanation
This lets an unprivileged private-payment counterparty crash the victim node/wallet process running `ocore`, a denial of service. Given the module-level `process.on('uncaughtException')` handler intentionally kills the process on any uncaught exception (rather than isolating the error), a reliably reachable malformed-payload trigger converts a local data-validation bug into a full node crash — matching the Medium severity DoS profile of the reported analog (crash triggerable by an untrusted, low-privileged input source, with no persistent state corruption but requiring restart of the node/wallet to restore service).

### Likelihood Explanation
High likelihood of reachability: any device/peer that can send a private payment to the victim (a normal wallet interaction) controls the payload content and can trivially craft a payload field that causes `getBase64Hash`/`getSourceString`/`getJsonSourceString` to throw (documented throw conditions: `null` values, `00`-byte strings, empty arrays/objects, non-finite numbers, lone-surrogate strings). No special privileges, mining power, or timing race is required — a single crafted private-payment message queued into `unhandled_private_payments` is enough to hit the missing-`return` bug on the next `handleSavedPrivatePayments()` invocation.

### Recommendation
Add a `return;` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave()` (network.js, around line 2476) so that a hash-computation failure short-circuits the function and does not fall through to `privatePayment.validateAndSavePrivatePaymentChain(...)`. Additionally, consider hardening `deleteHandledPrivateChain`/`validateAndSavePrivatePaymentChain` call sites against double-invocation of the iteratee `cb`, and converting the invariant `throw Error(...)` calls reachable from attacker-supplied private-payment data (e.g. in `initPrivatePaymentValidationState`, `private_payment.js`) into `callbacks.ifError(...)` paths where the offending data is genuinely attacker-controlled, rather than assumed-impossible database states.

### Proof of Concept
1. As a private-payment counterparty (paired device or peer), send a `private_payment` payload whose head element's `payload` field contains a value that makes `object_hash.getSourceString`/`getJsonSourceString` throw, e.g.:
   - an output or input object containing a `null` field value, or
   - a string field containing an embedded `\x00` byte, or
   - a numeric field set to `NaN`/`Infinity` (not directly JSON-serializable but reachable via internal object construction paths), or
   - an empty array/object in a field that `getSourceString` requires to be non-empty.
2. Ensure the payload otherwise satisfies `ValidationUtils.isNonemptyArray(arrPrivateElements)` and other superficial shape checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` so it is queued into `unhandled_private_payments`.
3. Wait for (or trigger) `handleSavedPrivatePayments()` to process the row. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside the `try`; the `catch` handles it but falls through, invoking `cb` twice and re-entering `privatePayment.validateAndSavePrivatePaymentChain` on an already-deleted row, which triggers one of the "impossible state" `throw Error(...)` invariants in `validation.js`/`private_payment.js`, propagating to the global `uncaughtException` handler in `network.js`, which re-throws and terminates the process.
