### Title
Organization used for webhook-signature verification is decoupled from the repository the payload is applied to, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. Once verification passes, the entire raw JSON body is handed to event handlers, which independently resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. These two payload paths are never checked for consistency, so an attacker who controls a legitimate webhook secret for one organization can forge a payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a victim organization's repository (to drive the actual write).

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks the app/secret to check the `X-Hub-Signature` against based on `repository_owner`, which is read straight out of the unauthenticated request body: [2](#0-1) 

After verification succeeds, `create` parses the same raw body and dispatches it, unmodified, to all handlers for the event: [3](#0-2) 

Handlers do not re-derive the target repository from `repository_owner`; instead the base `Handler` class resolves the stacks to act on via a different JSON path, `repository.full_name`: [4](#0-3) 

Because `repository_owner` (`repository.owner.login`) and `repository_name` (`repository.full_name`) are independent, attacker-controlled fields of the same untrusted JSON body, nothing binds the organization whose secret validated the signature to the organization/repository that handlers subsequently act on. The equality that should hold — "organization that authenticated" == "organization/repository that is written" — is not enforced anywhere in the request pipeline.

### Impact Explanation
An attacker who legitimately controls one onboarded GitHub organization (and therefore knows its `webhook_secret`, which is routinely exposed to repository/organization admins when configuring the GitHub App) can craft a webhook payload where:
- `repository.owner.login` (or `organization.login`) is set to their own organization, so `verify_signature` selects their own known secret and the HMAC check passes.
- `repository.full_name` is set to `victim-org/victim-repo`.

Handlers such as the push handler resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and then act on those stacks (e.g., enqueuing `GithubSyncJob`, updating commit statuses, or driving review-stack provisioning for `pull_request` events), even though the signature only proved the request came from a party who knows the attacker's own org secret, not the victim org's. This allows cross-repository state changes (sync jobs, commit statuses, review stack creation/label handling) attributed to a repository the attacker does not control, satisfying the "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate webhook sender for any one organization configured in this multi-tenant Shipit instance (i.e., they know or can trigger delivery of a validly-signed payload for their own org) and the ability to craft an arbitrary JSON body, which GitHub webhook redelivery/testing tools or a custom HTTP client both allow. No privileged Shipit account, session, or `ApiClient` token is needed — the attacker never authenticates to Shipit itself, only to the webhook endpoint using a secret they legitimately possess for their own org.

### Recommendation
Enforce that the field(s) used to select the verification secret and the field(s) used to resolve the target repository/stack are the same, single trusted source. Concretely, `Handler#repository_name` (and equivalents in per-event handlers) should be checked against the `repository_owner`/`organization` value that `verify_signature` used to pick the signing key, or the controller should derive both from one canonical path and reject payloads where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure two organizations in `secrets.github`, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (this is the documented multi-tenant setup, see `github_app_config` in `lib/shipit.rb`).
2. As a user with webhook access to `attacker-org` (their own onboarded org), craft a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-commit-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Sign the payload body with `attacker-org`'s known `webhook_secret` using HMAC-SHA1 and set it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` reads `repository_owner` as `attacker-org` from the payload, fetches `Shipit.github(organization: 'attacker-org')`, and the signature validates successfully.
5. `create` dispatches the parsed payload to the push handler, which calls `Handler#repository_name` → `payload.dig('repository', 'full_name')` → `"victim-org/victim-repo"`, resolving `victim-org/victim-repo`'s stacks and enqueuing sync/status-update jobs against them, despite the request never being authenticated as originating from `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
