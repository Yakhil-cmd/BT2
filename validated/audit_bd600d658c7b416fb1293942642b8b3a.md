### Title
Unauthenticated forged commit-status / push webhooks via mismatched organization used for signature verification vs. repository used for state writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the inbound webhook against using `repository.owner.login` (or `organization.login` as fallback), while every event `Handler` (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the actual `Repository`/`Stack` to write to using a **different** payload field, `repository.full_name`. Because the endpoint accepts a raw, unauthenticated JSON POST body and Shipit supports multiple independently configured GitHub organizations/Apps (each with its own, optional `webhook_secret`), an attacker can pick an organization whose `GithubApp` has no `webhook_secret` configured to trivially satisfy signature verification, while pointing `repository.full_name` at a completely different, secured organization's tracked repository.

### Finding Description
`verify_signature` looks up the org used for HMAC verification from attacker-controlled JSON, not from any cryptographically-bound field: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization — a legitimate, documented, optional setting: [3](#0-2) [4](#0-3) 

Multi-organization deployments are an explicitly supported configuration (see `test/dummy/config/secrets_double_github_app.yml`, where each org has its own, independently nullable `webhook_secret`).

Meanwhile, every default `Handler` resolves the actual `Repository`/`Stack` acted upon from a **different** field in the same payload — `repository.full_name` — completely independent of the field used above for org/secret selection: [5](#0-4) [6](#0-5) 

This breaks the binding: `organization authenticated (repository.owner.login used to pick the GithubApp/secret) == repository written (repository.full_name used to locate the Stack)`. Nothing in `verify_signature` or in `Handler#repository_name` enforces that `repository.owner.login` is a prefix of `repository.full_name`; they are simply two independent, attacker-supplied JSON fields.

Concretely, an unauthenticated attacker who knows (a) that a Shipit instance tracks a victim repository under organization `victim-org`, and (b) that the *same* Shipit instance is configured for at least one other GitHub organization `attacker-known-org` that has no `webhook_secret` set (an allowed, common configuration per the setup docs), can POST:
```json
{
  "repository": { "owner": { "login": "attacker-known-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "http://attacker.example"
}
```
with header `X-Github-Event: status` and any (or missing) `X-Hub-Signature`. `verify_signature` resolves `Shipit.github(organization: "attacker-known-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally, regardless of the signature supplied. `StatusHandler`/`Handler#stacks` then locate the real `victim-org/victim-repo` Stack via `full_name` and persist a forged `Status`.

### Impact Explanation
This crosses the "unauthorized deploy, rollback, or merge" boundary in the rules: forged commit statuses feed directly into deploy/merge decision logic — [7](#0-6) [8](#0-7) 
A forged `success` status for a required CI context on a victim's commit can make `Commit#deployable?` true and, for stacks with the merge queue enabled, satisfy `MergeRequest#any_status_checks_failed?`/`any_status_checks_missing?` checks that gate `MergeRequest#merge!`, leading to an unauthorized deploy or merge of a commit whose real CI never passed. The same organization-vs-repository mismatch also lets an attacker force `push`/`check_suite` handling (`GithubSyncJob`, `RefreshCheckRunsJob`) against arbitrary tracked stacks and can create/populate `Team`/`Membership` records via the `membership` handler for orgs whose webhook secret isn't set, indirectly touching `Shipit.github_teams` authorization data.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for more than one GitHub organization (documented supported use-case, see `secrets_double_github_app.yml`), and (2) at least one of those organizations to have `webhook_secret` left blank (documented as optional: "If you've set a webhook secret ... you should copy it here"). Given that `webhook_secret` is optional and easy to omit, and that the endpoint is public/unauthenticated by design (it must accept GitHub's webhooks), this is plausible in real multi-org deployments and requires no credentials, GitHub App keys, or session — only knowledge of the target repository's `full_name` and one org name with a missing secret.

### Recommendation
Do not select the verification organization from the same free-form payload fields used to resolve the target repository. Either:
- Bind webhook verification to the actual target repository (derive the org strictly from `repository.full_name`'s owner segment, and require that segment to match `repository.owner.login`), or
- Require `webhook_secret` to be mandatory for every configured organization (fail closed instead of `return true unless webhook_secret`), and reject any payload where `repository.owner.login` does not match the organization prefix of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit for two orgs: `victim-org` (webhook_secret set, tracks `victim-org/victim-repo`) and `attacker-known-org` (webhook_secret left blank, per documented-optional config).
2. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": {"owner": {"login": "attacker-known-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<real victim commit sha>",
  "state": "success",
  "context": "<required CI context>",
  "target_url": "http://x"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-known-org")` → `webhook_secret` blank → `verify_webhook_signature` returns `true` → request proceeds.
4. `StatusHandler` resolves the target stack via `repository.full_name = "victim-org/victim-repo"` and creates a forged `Status` for that commit, potentially unblocking deploy/merge for `victim-org/victim-repo` without ever presenting a valid signature for that organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
