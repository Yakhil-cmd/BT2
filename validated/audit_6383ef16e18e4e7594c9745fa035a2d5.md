### Title
Attacker-controlled repo bloat makes `fsck --connectivity-only` in `sanityCheckRepo`/`initRepo` exhaust the per-sync `--sync-timeout` budget, causing either permanent sync failure or destructive wipe of the published root - ([File: main.go])

### Summary
`sanityCheckRepo` runs `git fsck --no-progress --connectivity-only` on every sync iteration (via `initRepo`, called at the top of `SyncRepo`) inside the same `context.WithTimeout(..., *flSyncTimeout)` deadline used for the whole sync cycle. An attacker who can push commits/refs to the tracked repo can grow the total object graph large enough that `fsck` alone consumes the entire `--sync-timeout` budget, causing the underlying git process to be killed by context cancellation. That cancellation error is treated identically to a genuine corruption signal, so `initRepo` wipes the entire `--root` directory (`removeDirContents(git.root, ...)`) and reinitializes it, destroying the already-published worktree/symlink, and/or the sync repeatedly fails such that `cleanup()`'s `gc`/`reflog expire` (the only mechanism that would shrink the bloated repo) never runs because it is gated on a successful sync.

### Finding Description
The main loop creates one shared timeout budget per sync cycle: [1](#0-0) 

`SyncRepo` calls `initRepo(ctx)` first on every iteration. Once the repo directory exists (true after the first run), it takes the "already usable" branch and calls `sanityCheckRepo(ctx)`: [2](#0-1) 

`sanityCheckRepo` runs `fsck --connectivity-only` under that same `ctx`: [3](#0-2) 

`git.Run` executes via `exec` bound to `ctx`; if the context deadline is exceeded mid-fsck, the process is killed and `Run` returns a non-nil error, which `sanityCheckRepo` treats as "repo is bad" and returns `false` — with no distinction between "context canceled/timed out" and "genuinely corrupt repo." That `false` result causes `initRepo` to call `removeDirContents(git.root, ...)`, wiping the entire root volume (including the already-published worktree and symlink target) and re-running `git init`.

The cost of `fsck --connectivity-only` scales with the total number of reachable objects in the repo, which is directly attacker-controlled: an unprivileged pusher to the tracked ref can grow history size, add many refs/tags, or shape pathological commit/tree graphs to make full-graph connectivity checking arbitrarily expensive, without needing any operator-set flag beyond a normal `--sync-timeout`.

Separately, `cleanup()` — which runs `worktree prune`, `reflog expire --expire-unreachable=all --all`, and `gc`/`gc --aggressive` (the only step that can shrink/compact the bloated object store) — is only invoked after a successful `SyncRepo` call: [4](#0-3) [5](#0-4) 

If the fsck-dominated sync keeps failing (either failing outright on timeout, or "succeeding" only after the destructive wipe-and-reinit resets to an empty repo), `cleanup()`'s `gc` step to compact the repo either never runs or runs against a freshly emptied repo, so the attacker-inflated object graph is never remediated by normal operation — the failure is self-sustaining as long as the attacker keeps pushing.

`failCount`/`getMaxFailures()` defaults to unlimited retries, so the loop never exits; it simply retries forever without making progress, and `log.DeleteErrorFile()` is only called on the success path, so the readiness/error-file state reflects a persistent failure: [6](#0-5) 

### Impact Explanation
Two concrete, scoped impacts are reachable purely from repo content an unprivileged pusher controls:
1. **Permanent denial of updates**: repeated sync failures (context deadline exceeded during fsck) with unlimited retries and no successful `cleanup()`/`gc` to shrink the repo, matching the Kubernetes bug-bounty "persistent denial of service" class.
2. **Destructive data loss / integrity failure**: misclassification of a context-timeout as "corrupt repo" causes `initRepo` to `removeDirContents` on `git.root`, wiping the already-published worktree/symlink that downstream consumers are actively reading from the mounted `--root` volume — a more severe outcome than the question's "recovers without wiping already-published data" expectation.

### Likelihood Explanation
- No non-default flags are required; only a normal, documented `--sync-timeout` value and any `--git-gc` mode (the question's aggressive mode simply exacerbates budget pressure but is not required for the core fsck-timeout/wipe issue).
- The attacker only needs push access to the ref git-sync tracks (or ability to influence the object graph fetched), which is explicitly in the allowed unprivileged capability set.
- The condition is deterministically reproducible: any sufficiently large/pathological object graph will make `fsck --connectivity-only` scale past a fixed `--sync-timeout`; the attacker can keep growing the graph to guarantee this regardless of operator-chosen timeout.
- Because retries are unlimited by default (`getMaxFailures() < 0`), the failure state is stable and repeatable across restarts of the process (as long as the bloated `.git` history persists on disk or is re-fetched).

### Recommendation
- In `sanityCheckRepo`/`sanityCheckWorktree`, distinguish context-timeout/cancellation errors (`ctx.Err() != nil` or `errors.Is(err, context.DeadlineExceeded)`) from genuine git-reported corruption, and do NOT treat a timeout as "repo is corrupt" — instead log and retry rather than wiping `git.root`.
- Budget `fsck` and `gc` with their own sub-timeouts independent of (and smaller than) the overall `--sync-timeout`, so a slow connectivity check cannot consume the entire cycle or trigger destructive recovery logic.
- Run `cleanup()`/`gc` even on partial/failed syncs (or on a separate schedule) so a bloated repo can still be compacted instead of only compacting after a full successful sync.
- Consider making `fsck --connectivity-only` opt-out configurable or rate-limited (e.g., run it every N syncs) to bound its cost relative to `--sync-timeout`.

### Proof of Concept
Integration-test sketch (bash, local `file://` remote, mirroring `test_e2e.sh` conventions):
```bash
# 1. Create a local origin repo and push a pathologically large/deep object graph
#    (e.g., thousands of commits each touching many small blobs, or many refs)
#    to make `git fsck --connectivity-only` take longer than a small --sync-timeout.
git init "$REPO"
for i in $(seq 1 200000); do
  echo "$i" > "$REPO/f$i"
  git -C "$REPO" add "f$i"
done
git -C "$REPO" commit -qm "bloat"

# 2. Run git-sync once successfully with a generous timeout to populate $ROOT.
GIT_SYNC --one-time --repo="file://$REPO" --root="$ROOT" --link="link" --sync-timeout=600s

# 3. Re-run git-sync (not one-time) with a very small --sync-timeout so that
#    `fsck --connectivity-only` inside sanityCheckRepo cannot finish in time.
GIT_SYNC --repo="file://$REPO" --root="$ROOT" --link="link" \
  --sync-timeout=1s --period=2s --git-gc=aggressive &

# Expected (buggy) behavior to assert against:
#   - $ROOT/link and $ROOT/.git get deleted (removeDirContents triggered by
#     sanityCheckRepo returning false due to context deadline), even though
#     the previously published commit was valid and unrelated to real corruption.
#   - Sync never succeeds again while the bloated history persists, i.e.
#     $ROOT/link content stops updating (permanent denial of updates).

# Assertions:
assert_link_missing_or_reset "$ROOT/link"   # demonstrates destructive wipe
assert_sync_never_recovers_within_N_periods # demonstrates permanent DoS
```
A unit test can directly exercise the root cause by calling `sanityCheckRepo(ctx)` with a `ctx` whose deadline is already expired against a valid repo, and asserting it returns `false` purely due to `context.DeadlineExceeded`, then asserting `initRepo` proceeds to `removeDirContents` on a repo that was otherwise healthy.

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}

	if len(cleanupErrs) > 0 {
		return cleanupErrs
	}
	return nil
}
