### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC using `repository.owner.login` (or `organization.login`) from the JSON body, then hands the entire raw payload to `Shipit::Webhooks.for_event(event)` handlers. Those handlers look up the `Stack`/`Repository` to mutate using `repository.full_name`, a separate, independently-controlled field of the same signed payload. Because both fields are attacker-supplied JSON values inside the same signed body, an attacker who controls (or has webhook access to) one organization onboarded into this Shipit instance can produce a validly-signed payload where `repository.owner.login` equals their own org (so verification succeeds with their own org's secret) while `repository.full_name` names a stack belonging to a different, victim repository/organization.

### Finding Description
`verify_signature` computes `repository_owner` purely from the JSON body and uses it to select `Shipit.github(organization: repository_owner)`, whose `verify_webhook_signature` is then run against the raw body using that organization's `webhook_secret`. [4](#0-3) 

The equality that should hold is:
`organization whose secret authenticated the payload == organization owning the repository the handlers act on`

But the handlers never re-derive or cross-check the owner used for verification; they independently read `repository.full_name` to find the `Repository`/`Stack` row to mutate: [3](#0-2)  This is then used by, e.g., `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` [5](#0-4)  or `CheckSuiteHandler#process` to schedule check-run refreshes on commits of a resolved stack. [6](#0-5) 

Nothing ties `repository.owner.login` (used for signature/secret selection) to `repository.full_name` (used for the actual database lookup); they are two independently-controlled keys inside a single JSON body that is only integrity-protected as a whole blob, not field-by-field against a specific owner. As long as the outer HMAC validates (which it will, if the attacker signs with any organization's webhook secret they legitimately possess — e.g., their own onboarded org on a multi-tenant Shipit instance, or leaked/park secret), the body content, including `repository.full_name` naming an unrelated victim repository, is trusted.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary named in scope. Exploiting it lets an attacker who legitimately controls one onboarded organization's webhook secret forge events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that get routed to and act upon a **different** organization's `Stack`, e.g. triggering `sync_github` (refreshing commits/branch state), fabricating commit statuses via `StatusHandler`, or triggering `RefreshCheckRunsJob`/`schedule_refresh_check_runs!` for another org's stack. This is a cross-repository/cross-organization write performed without ever having credentials, GitHub App private key, or repository access for the victim organization. Severity is High/Critical depending on which handler is abused (e.g. anything that ultimately changes the "last deployed"/status/merge state or feeds into automatic deploy/merge decisions for the victim stack).

### Likelihood Explanation
Requires the attacker to have configured (or compromised) webhook credentials for at least one organization that this Shipit instance trusts — realistic on any multi-tenant/self-service Shipit deployment where organizations self-onboard GitHub Apps with their own `webhook_secret`. No privileged Shipit account, `ApiClient` token, or GitHub App private key for the victim is needed; only a valid signature for *any* onboarded org plus knowledge of the victim's `owner/repo` full name (public information).

### Recommendation
Bind signature verification to the exact repository being acted upon, not just its owner: after resolving `repository_name = payload.dig('repository', 'full_name')`, verify that its owner matches the same `repository_owner` used to select the signing secret, and reject the webhook if they don't match (or better, always require the full owner/name pair to belong to the exact GitHub App/organization installation the secret was scoped to, rather than trusting the payload's self-reported owner in isolation).

### Proof of Concept
1. Attacker administers `evilorg`, which is a legitimately onboarded GitHub App in this Shipit instance with its own `webhook_secret`.
2. Attacker crafts a `push` (or `status`/`check_suite`) JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "evilorg" },
       "full_name": "victimorg/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(evilorg_webhook_secret, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner == "evilorg"`, fetches `evilorg`'s `webhook_secret`, and the HMAC validates successfully. [4](#0-3) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#stacks` looks up `Repository.from_github_repo_name("victimorg/victim-repo")` and its stacks, then calls `sync_github(expected_head_sha: ...)` on `victimorg`'s stack — mutating state for a repository the attacker never had rights to.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
