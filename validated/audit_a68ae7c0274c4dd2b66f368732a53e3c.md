## Equality being validated

Claimed binding: `repository_owner` (= `params.dig('repository','owner','login')`, verified against `Shipit.github(organization: repository_owner).webhook_secret`) **==** organization that owns every row the invoked handler mutates.

Traced code:

- `Shipit::WebhooksController#verify_signature` derives the verifying organization solely from the top-level `repository.owner.login` (or `organization.login`) of the JSON body and checks the raw body's HMAC against that org's `webhook_secret`. [1](#0-0) 
- `Shipit::Webhooks::Handlers::StatusHandler#process` never references `repository` at all. Its param schema only requires `sha`, `state`, and optional fields — no `repository` block — and it resolves the target row purely by a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1) 

Compare this to `PushHandler`/`CheckSuiteHandler`, which correctly scope through `stacks` (derived from `payload.dig('repository','full_name')` in the base `Handler` class) before touching any row. `StatusHandler` has no equivalent scoping. [3](#0-2) [4](#0-3) 

Because git commit SHA1s are computed purely from commit content (tree, parent, author/committer, message/timestamp) and are independent of the repository/organization they're pushed to, the same SHA can legitimately exist in two unrelated Shipit-tracked stacks (e.g., via a public fork, or an attacker deliberately reproducing an identical commit object under their own org). `Commit.where(sha:)` does not disambiguate by owning repository/organization at all.

### Title
Cross-tenant commit status write via SHA-only lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the top-level `repository.owner.login`, but `StatusHandler#process` ignores the payload's `repository` entirely and updates whatever `Commit` row matches the attacker-supplied `sha`, with no check that the commit belongs to a stack under the verifying organization. An attacker who controls a repository under organization X (and thus can trigger genuine, X-signed `status` webhooks) can write a fabricated CI status onto a commit that actually belongs to organization Y's stack, as long as they can produce/reference a commit with the same SHA (e.g., forking Y's public repository into X, or reproducing identical commit content).

### Finding Description
The equality the system is supposed to preserve is: `repository_owner` used in `verify_signature` (org X, whose `webhook_secret` validated the HMAC) must equal the organization owning every `Stack`/`Commit` row the dispatched handler mutates. For the `status` event this equality is not held: `verify_signature` reads `params.dig('repository','owner','login')` [5](#0-4)  and verifies the raw body against `Shipit.github(organization: repository_owner)`'s secret [6](#0-5) , then `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler` with the full parsed body [7](#0-6) [8](#0-7) . `StatusHandler`'s `params` schema requires only `sha`/`state`/optional fields — no `repository` — and `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, a lookup across the entire `commits` table with no join/filter on the owning repository or organization. [2](#0-1)  Since `sha` is content-derived and not scoped per-org, a commit with the same SHA can exist under a stack belonging to a different organization Y (public fork, mirrored history, or an attacker deliberately reproducing an identical commit object), and X's own webhook will cause `commit.create_status_from_github!` to run against Y's row. `create_status_from_github!` calls `add_status`, which persists a new `Status`, emits hooks, and can invoke `stack.schedule_merges` when the new status is `pending`/`success`. [9](#0-8) [10](#0-9)  None of the listed guards intervene: `verify_signature` only checks the top-level org, `ExplicitParameters` for `StatusHandler` never declares/validates `repository`, and there is no `Repository.from_github_repo_name` scoping anywhere in this handler (contrast with `PushHandler`/`CheckSuiteHandler`, which do scope via `stacks`). [3](#0-2) 

### Impact Explanation
An attacker controlling any repository under organization X can write a `Status` row (and trigger downstream `deployable_status`/`commit_status` hooks and merge scheduling) onto a `Commit` owned by organization Y's stack, without ever authenticating against Y's webhook secret or holding any Shipit credential. This is a cross-tenant write matching the "payload for one repository mutating another's stack, commit, task or team" Critical category, and is repeatable against any commit SHA the attacker can reproduce or discover (trivial for forks of public repositories, which share identical git objects/SHAs with upstream).

### Likelihood Explanation
Preconditions: attacker owns/administers at least one repository registered as an X-owned Shipit stack (or can otherwise get a genuine `status` webhook fired from an X repo) and can identify or reproduce a target SHA also present in a Y-owned tracked stack — trivially satisfied for public repos/forks, which literally share commit objects. No Shipit secrets, sessions, or GitHub App keys are required; the attacker only needs to legitimately trigger a `status` event on their own GitHub repository (e.g., via their own CI integration). This is fully repeatable and requires no interaction from Y.

### Recommendation
Require and validate a `repository` block in `StatusHandler`'s `ExplicitParameters` schema, resolve the owning `Shipit::Repository` via `Repository.from_github_repo_name(params.repository.full_name)`, and scope the commit lookup to that repository's stacks (`repository.stacks.commits.where(sha: params.sha)`) instead of the unscoped `Commit.where(sha:)`, mirroring the pattern already used in `PushHandler`/`CheckSuiteHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not update a commit belonging to a different organization's stack" do
  # Y's stack/commit, unrelated to org X
  other_stack = shipit_stacks(:shipit) # repository owner "shopify" per fixtures
  victim_commit = shipit_commits(:first)
  victim_commit.update!(sha: "deadbeef00000000000000000000000000000000")

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "repository" => { "full_name" => "attacker-org/attacker-repo", "owner" => { "login" => "attacker-org" } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
Current behavior: this test fails, because `StatusHandler#process` matches on `sha` alone and creates a `Status` on `victim_commit` regardless of the payload's `repository` field — proving `repository_owner` (verified org) and the row's true owning organization are not bound together.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

        "status=#{status}"
      ].join(' '))
    end

        def process
          Commit.where(sha: params.sha).each do |commit|
