### Title
Bridge KLAY Push-Payment to Rejecting Recipient Permanently Locks Bridged Assets and Stalls Operator Queue — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the service-chain bridge uses a push-payment pattern: it sends KAIA to the caller-supplied `_to` address with a low-level call and then `require`s success. If `_to` is a contract that reverts on receive, the entire transaction reverts (including the nonce-state update), the bridge nonce never advances past that slot, and the Go-layer operator loop re-queues the stuck event ahead of every subsequent pending transfer, stalling the bridge indefinitely.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs the following sequence: [1](#0-0) 

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

The nonce-state writes (`handleNoncesToBlockNums`, `_updateHandleNonce`) appear before the transfer, but because the `require` is in the same transaction, a revert on the `call` rolls back **all** state changes. `lowerHandleNonce` is therefore never advanced past the stuck slot.

`_updateHandleNonce` advances `lowerHandleNonce` only when a contiguous run of nonces starting from `lowerHandleNonce` have been recorded in `handleNoncesToBlockNums`: [2](#0-1) 

Because the stuck nonce's entry is never written, `lowerHandleNonce` is permanently frozen.

On the Go side, `processingPendingRequestEvents` processes events in nonce order and, on any error from `handleRequestValueTransferEvent`, re-queues the failing event **and all events that follow it** before returning: [3](#0-2) 

When the Go binding calls `HandleKLAYTransfer` for the stuck nonce, gas estimation against the node fails (the simulated call reverts), so `bi.bridge.HandleKLAYTransfer` returns a non-nil error: [4](#0-3) 

The error propagates back to `processingPendingRequestEvents`, which re-queues the stuck event plus every subsequent pending event and exits. On the next scheduling tick the same stuck event is tried first, fails again, and the cycle repeats — permanently blocking all bridge transfers with a nonce higher than the stuck one.

The ERC20 path has the same structural flaw: `safeTransfer` to a blocklisted `_to` (e.g., a USDC-blocklisted address) reverts, rolls back the nonce update, and triggers the same operator-queue stall: [5](#0-4) 

---

### Impact Explanation

- **Bridged KAIA/ERC20 permanently locked**: the value deposited on the source chain for the stuck request can never be released because the counterpart bridge never records the handle.
- **Complete bridge DoS**: every transfer with a nonce higher than the stuck one is re-queued indefinitely; no subsequent user can complete a cross-chain transfer until the stuck nonce is resolved (which the current contract provides no mechanism to do).
- **Operator gas drain**: bridge operators pay gas for every failed estimation/submission attempt in the retry loop.

---

### Likelihood Explanation

Any user who initiates `requestKLAYTransfer` (or `requestERC20Transfer`) with a `_to` address that is a contract rejecting native value (or a blocklisted ERC20 recipient) triggers the condition. The attacker does not need special privileges — `requestKLAYTransfer` is a public payable function. A single malicious or mistaken request is sufficient to freeze the entire bridge operator queue. [6](#0-5) 

---

### Recommendation

1. **Decouple nonce advancement from asset delivery.** Record the nonce as handled unconditionally; if the push transfer fails, credit the amount to a per-recipient escrow mapping that the recipient can `withdraw` later (pull-payment pattern). This mirrors the fix suggested in the original Astaria report.

2. **Validate `_to` before accepting the request.** On the source chain, reject requests whose `_to` is a known non-payable contract, or require `_to` to be an EOA.

3. **Allow operators to skip irrecoverable nonces.** Add an owner-gated `skipHandleNonce(uint64 nonce)` that marks a nonce as handled with zero value, unblocking `lowerHandleNonce` advancement and the operator queue.

4. **Decouple operator retry logic from nonce ordering.** In `processingPendingRequestEvents`, log and skip a failing event rather than re-queuing it at the front of the queue, so that subsequent transfers are not blocked by a single stuck nonce. [7](#0-6) 

---

### Proof of Concept

1. Deploy a contract `Rejector` on the child chain whose `receive()` function always reverts.
2. On the parent chain, call `bridge.requestKLAYTransfer(rejector_address, value, "0x")` with `msg.value = value + fee`. This emits `RequestValueTransfer` with nonce N and locks `value` KAIA in the parent bridge.
3. The sub-bridge operator observes the event and calls `handleKLAYTransfer(..., rejector_address, value, N, ...)` on the child bridge. Gas estimation reverts; `bi.bridge.HandleKLAYTransfer` returns a non-nil error.
4. `processingPendingRequestEvents` re-queues nonce N and all higher-nonce events, then returns. On the next tick it retries N, fails again.
5. Any other user's pending transfer (nonce N+1, N+2, …) is permanently stuck in the re-queue. `lowerHandleNonce` on the child bridge never advances past N−1. The `value` KAIA on the parent bridge is unrecoverable.

			return
		}
