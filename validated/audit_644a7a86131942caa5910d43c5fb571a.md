### Title
Webhook signature is verified against an attacker-selectable organization while state mutation is scoped by an unrelated, unauthenticated repository field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body, but the handlers that actually mutate state (`Handler#repository_name`, `PushHandler`, and especially `StatusHandler`) resolve the object to write to using a *different* field (`repository.full_name`) or, in the case of `StatusHandler`, no repository scoping at all. In a multi-organization Shipit deployment this breaks the binding "organization that authenticated == repository that is written," letting any org that legitimately owns its own configured `webhook_secret` forge writes against stacks/commits belonging to a completely different organization on the same Shipit instance.

### Finding Description
`verify_signature` picks the verification key from the payload itself, then checks the *entire raw body* against that key: [1](#0-0) [2](#0-1) 

The org name used to pick the secret (`repository.owner.login` / `organization.login`) is just one JSON field inside the body being signed. Nothing ties that field to the other fields the handlers actually act on. Downstream, `Handler#repository_name` and `Handler#stacks` resolve the target `Repository`/`Stack` using a completely independent field, `repository.full_name`: [3](#0-2) 

Worse, `StatusHandler#process` does not scope by repository at all — it matches purely on commit `sha`, globally, across every stack in the installation: [4](#0-3) 

`PushHandler` similarly trusts `repository.full_name` from the body (via `stacks`) to select which stacks to sync, independent of which org's secret validated the signature: [5](#0-4) 

Shipit's documented multi-org configuration gives every configured organization its own independent GitHub App and `webhook_secret`: [6](#0-5) 

Because the HMAC only proves "this exact byte string was produced by whoever holds organization X's `webhook_secret`," and the signature-selection field (`repository.owner.login`/`organization.login`) is never cross-checked against the mutation-selection field (`repository.full_name` or bare `sha`), an org that legitimately controls its own `webhook_secret` (i.e., knows a valid key for `verify_signature`) can freely construct a payload naming itself in `repository.owner.login`/`organization.login` (to pass signature verification) while independently setting `repository.full_name` (for `push`/`check_suite`) — or simply guessing/observing a target commit `sha` (for `status`) — to point at another organization's stack. The equality that should hold, `organization authenticated == repository/stack written`, is broken.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact:
- `status` events are the most severe path: `StatusHandler` creates a `Status` for any `Commit` matching `params.sha`, with **no repository check whatsoever**. Any org onboarded to the same Shipit instance can forge a passing/failing CI status for a commit belonging to a completely unrelated organization's stack. Since commit statuses gate deployability in Shipit, this can be used to force required checks to pass and enable an unauthorized deploy of a victim stack.
- `push` events let a forging org trigger `stack.sync_github(expected_head_sha:)` for a victim's stack by naming it via `repository.full_name`, independent of the org whose secret actually signed the request.

This satisfies the required Critical bar ("an unauthorized deploy, rollback or merge") and does not require any GitHub session, `ApiClient` token, or privileged Shipit account — only possession of a `webhook_secret` that the attacker's own (unrelated, non-privileged with respect to the victim) organization legitimately owns in a multi-org configuration.

### Likelihood Explanation
Any Shipit operator who onboards more than one GitHub organization (a documented, supported configuration) exposes every one of those organizations' webhook signers to every stack in the shared Shipit instance, because the signature check and the state-mutation lookup key off different, uncorrelated fields of the same untrusted JSON body. No collusion, timing, or race condition is needed — a single crafted POST to `/webhooks` with a validly-computed HMAC for the attacker's own org is sufficient.

### Recommendation
- After `verify_signature` succeeds, re-derive the organization/repository that is authorized to act from the *verified* App/installation context (not from payload fields), and reject the request if `repository.owner.login`/`organization.login` does not match `repository.full_name`'s owner segment.
- Scope `StatusHandler#process` (and any other handler that doesn't already do so) by `Repository.from_github_repo_name(repository_name)` / `stacks`, exactly as `PushHandler` and `CheckSuiteHandler` do, instead of matching bare `sha` globally.
- Consider binding the webhook delivery's GitHub App installation ID (available from GitHub App context, not the JSON body) to the specific configured organization, rather than trusting a body field to select the verification secret.

### Proof of Concept
Assume a Shipit instance configured for two organizations, `attacker-org` (attacker legitimately administers this org and its `webhook_secret`, `S_attacker`) and `victim-org` (has an active stack tracking commit `abc123`).

1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)` — valid, since `verify_signature` looks up the secret for `repository_owner == "attacker-org"` [1](#0-0) , which the attacker legitimately knows.
3. POST to `/webhooks` with header `X-Github-Event: status`. Signature check passes.
4. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: 'abc123').each { |c| c.create_status_from_github!(params) }` [4](#0-3)  — with no check that `abc123` belongs to `attacker-org`'s repository — forging a `success` status on `victim-org`'s commit and potentially unblocking its deploy gate.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
