### Title
Cross-repository `status` webhook writes into a victim `Stack`'s CI-enabled cache via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commits to update purely by SHA, with no check that the SHA actually belongs to the repository that sent the webhook [1](#0-0) . Because git commit SHAs are content-addressed and identical between a repository and any fork that shares history, an attacker who owns a fork (or any repo sharing commits with the victim) can send a legitimately-signed `status` webhook that matches a `Commit` row belonging to an unrelated victim `Stack`, causing `Status#enable_ci_on_stack` to call `commit.stack.enable_ci!` on the victim's stack [2](#0-1) .

### Finding Description
The claimed binding is: `Status` row's `stack_id` and `enable_ci!` target `==` the `Stack` whose `repository.github_repo_name` genuinely generated the CI signal. The code never enforces this. `StatusHandler#process` does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is global across every `Stack` in the installation — it is not scoped by `params.repository` or by any relationship between the sending repo and `commit.stack`. `commit.create_status_from_github!(params)` (in `Commit`) then persists a `Status` using the commit's own `stack_id` (i.e. the victim's stack, since the `Commit` row already belongs to that stack), via `Status.replicate_from_github!(stack_id, github_status)` [3](#0-2) . Creation triggers `after_create :enable_ci_on_stack`, which unconditionally calls `commit.stack.enable_ci!` [2](#0-1) , and `Stack#enable_ci!` writes `true` to the stack's CI-enabled cache key with no re-validation of provenance [4](#0-3) .

Exploit flow: the attacker forks (or otherwise shares commit history with) the victim's repository. Commits that predate the fork have byte-identical SHAs in both repositories because git commit objects are content-addressed — this is not a hash collision, it is the literal same object. If the victim's `Stack` has a `Commit` row for one of those shared SHAs but has never received a genuine CI `status` for it (`ci_enabled?` false), the attacker installs/enables a `status`-emitting integration on their own fork (or a repo they control) and lets GitHub send a real, correctly-signed `status` webhook naming the attacker's own repository for that shared SHA. `WebhooksController` verifies the signature is authentic for *a* repository (the attacker's own, which the attacker legitimately controls), but `StatusHandler#process` never checks that the resolved `Commit`/`Stack` belongs to that same repository. The webhook therefore also matches the victim's `Commit` row and flips the victim `Stack`'s CI-enabled state.

Existing guards do not catch this: signature verification (`GitHubApp#verify_webhook_signature`) only proves the payload is authentic *for the repository named in the payload*, not that the resolved DB records belong to that repository; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repo ownership; there is no `stacks` scope check or repository-equality assertion anywhere in `StatusHandler` or `Status`.

### Impact Explanation
This is a payload from one repository mutating another repository's `Stack` record — explicitly listed as a Critical impact category. The write is limited to the CI-enabled cache flag (`Stack#ci_enabled?`), but this flag participates in deployment gating and CI-status derived logic (`branch_status`, `deployable?` semantics elsewhere depend on statuses existing). It is repeatable: any attacker who forks or otherwise shares commit ancestry with a target repo, and controls a `status`-emitting integration on their own copy, can flip the CI-enabled state on the victim stack for any shared ancestor commit, with no privilege on the victim repo, Shipit session, or secret required.

### Likelihood Explanation
Preconditions are realistic and cheap: any public/forkable repository, and the victim `Stack` must not yet have received a genuine CI status for a shared ancestor commit (a plausible window for freshly onboarded stacks or historical commits). The attacker needs no Shipit credentials — only the ability to fork the repo and trigger a `status` webhook from their own copy (e.g., via their own CI or a direct API call authenticated as their own GitHub identity/App installation on their fork). This requires no Shipit-side secret.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository that sent the webhook, e.g. filter to `commit.stack.repository.github_repo_name == params.repository.full_name` (or join through `Stack`/`Repository` in the query) before calling `create_status_from_github!`, rejecting/skipping any commit whose owning stack's repository does not match the webhook's asserted repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `victim_stack` with `repository` `victim/repo`, and a `Commit` `sha: "abc123"` under `victim_stack` with no `Status` rows. Assert `victim_stack.ci_enabled?` is `false`.
2. Create `attacker_stack` with `repository` `attacker/repo` (or simply construct params for a repo not associated with any stack) and build a `params` object for `StatusHandler` with `sha: "abc123"`, `state: "success"`, and `repository` referring to `attacker/repo`.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (or the equivalent handler entrypoint) with those params.
4. Assert `victim_stack.reload.ci_enabled?` is now `true`, and that a `Shipit::Status` row now exists with `stack_id: victim_stack.id`, despite the webhook never having named `victim/repo`.

Both sides of the binding — "the repo asserted in the webhook" vs. "the repo whose stack got `enable_ci!` called" — diverge before any fix, confirming the vulnerability.
