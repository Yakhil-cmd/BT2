### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name`, allowing a valid webhook secret from one GitHub organization to forge events for a different organization's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments, Shipit keeps a distinct `webhook_secret` per GitHub organization [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the incoming HMAC against using `repository_owner`, itself read straight out of the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . Once the signature check passes, `create` dispatches the very same parsed payload to handlers unmodified [4](#0-3) . Those handlers resolve which `Stack`/`Repository` to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [5](#0-4) , or `params.repository.full_name` in pull-request handlers [6](#0-5) . Nothing ever checks that `repository.owner.login` (the field the HMAC was resolved against) matches the owner encoded in `repository.full_name` (the field that actually selects the target repository/stack).

### Finding Description
The equality that should hold is:
`organization whose secret authenticated the signature == organization that owns the repository the payload will act upon`

Before verification, the controller trusts `repository.owner.login` from the still-unverified JSON body to pick which org's `GitHubApp`/`webhook_secret` to use for HMAC comparison [7](#0-6) . The signature (`X-Hub-Signature`) is a keyed HMAC over the raw body, so it does prove the sender knows *that organization's* secret and that the body hasn't been altered in transit — but it never proves internal self-consistency of the body's fields. Someone who legitimately controls (or has been issued) organization A's GitHub App and its `webhook_secret` — e.g. installed on their own org, a scenario the multi-org config explicitly supports (`secrets.github` keyed by org, see `github_app_config` at [8](#0-7) ) — can construct an arbitrary payload with `repository.owner.login = "orgA"` (so verification is done against orgA's secret) but `repository.full_name = "orgB/some-repo"` (so the handler resolves stacks belonging to organization B). Since they control the raw body, they sign it correctly with orgA's own secret, and `verify_webhook_signature` succeeds [9](#0-8) .

Downstream, `Handler#stacks` and every concrete handler (`PushHandler`, pull-request handlers, `LabeledHandler`, `ReviewStackAdapter`, etc.) key off `repository.full_name`/`repository`, not off the field used for signature selection, and `Repository.from_github_repo_name` does a straight DB lookup by parsed owner/name with no relation to which app authenticated the request [10](#0-9) . `PushHandler#process` will happily call `stack.sync_github` for a stack under the forged `full_name`, and `sync_github`/`GithubSyncJob` subsequently makes real GitHub API calls using `Shipit.github(organization: owner)` resolved from the *actual* stack's repository owner (org B) [11](#0-10) , not org A — meaning org A's forged, but validly-signed-by-orgA, webhook can trigger sync/build activity against org B's stacks without ever proving knowledge of org B's secret.

### Impact Explanation
This breaks the tenant isolation the per-organization `webhook_secret` is meant to provide: it is High severity, as it is an escalation allowing an unauthenticated-w.r.t.-target-org actor (one who only knows a different organization's webhook secret) to trigger `GithubSyncJob`/stack synchronization, commit `Status` creation (`StatusHandler` also has no owner binding, only `sha`, see [12](#0-11) ), review-stack archive/unarchive, and label capture actions against a repository/stack it is not entitled to influence, in a cross-repository/cross-organization manner without holding that organization's credentials.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations under `secrets.github` (documented, supported configuration, see `github_default_organization`/`github_organizations` at [13](#0-12) ), and (2) the attacker legitimately possesses one organization's own `webhook_secret` (e.g. as an admin of their own installed GitHub App, not a privileged Shipit account). No Shipit session, `ApiClient` token, or GitHub write access to the target repository is required — only crafting a raw POST to `/webhooks` with a mismatched `owner.login` vs. `full_name` and a correct HMAC for the org whose secret they hold.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from the same field the handlers use to select the target repository (`repository.full_name`'s owner segment) and reject the request (422) if it disagrees with `repository.owner.login`/`organization.login` used to pick the verifying secret. Alternatively, always resolve the verifying `GitHubApp` for a webhook from the owner segment of `repository.full_name` exclusively, and pass the already-resolved `Repository`/organization down to handlers instead of letting each handler re-parse `full_name` independently.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github = { orga: { webhook_secret: "orgAsecret", ... }, orgb: { webhook_secret: "orgBsecret", ... } }`, with a `Stack` whose `Repository` has `owner: "orgb"`.
2. As an actor who only knows `orgAsecret` (e.g., they administer the GitHub App installed for `orga`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgAsecret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner == "orga"`, calls `Shipit.github(organization: "orga")`, and the HMAC validates successfully against `orgAsecret` [2](#0-1) .
5. `create` dispatches to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository', 'full_name') == "orgb/target-repo"` [14](#0-13) , resolving stacks under `orgb` and enqueuing `GithubSyncJob`/`sync_github` against a repository the attacker never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
