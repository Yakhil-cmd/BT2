### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read the state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates a request using the `token` query parameter (an `ApiClient` authentication token) but then resolves the target stack directly from the URL via `Stack.from_param!(params[:stack_id])`, completely bypassing the stack scoping that every other API controller enforces through `BaseController#stacks`/`#stack`. This breaks the intended binding: *the stack a token is authorized for* must equal *the stack the request actually touches*.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting resolution of "which stacks can this API client see": [1](#0-0) 
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
An `ApiClient` can optionally be scoped to a single `stack` (`belongs_to :stack, optional: true`), and this is the mechanism the app uses to give a token access to only one stack instead of all stacks: [2](#0-1) 

`Api::CCMenuController`, however, overrides both the authentication and the stack lookup: [3](#0-2) 
```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
```
`stack` here resolves against `Stack.from_param!` (the whole `Stack` table), not against `stacks` (the client-scoped relation). `require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks that the string `"read:stack"` is present in the client's `permissions` array — it never checks `current_api_client.stack_id`: [4](#0-3) 

So the only two conditions to reach `show` are: (1) the token is a valid `ApiClient` signature, and (2) that client has the generic `read:stack` permission. Neither condition is tied to the specific `stack_id` in the URL.

**Equality that should hold:** `token.stack_id (authorized stack) == params[:stack_id] (stack touched)` whenever an `ApiClient` is created with a `stack` binding.
**What actually happens:** for the CCMenu action, the right-hand side is resolved independently of the left-hand side, so the equality is never enforced.

This is a direct analog of the reported bug class: the report's `ChildToken::resolveUser` verified the "signed" state (which locks belong to which user) before the mutation, but the mutation appended tokens in a way that broke the sequential ordering the read-path (`_unlockTokens`/`availableTokens`) relies on — an authorization/consistency invariant enforced elsewhere in the system was silently bypassed by one code path. Here, the stack-scoping invariant enforced by `BaseController#stack` is bypassed by the one controller (`CCMenuController`) that re-implements stack resolution instead of reusing the scoped helper.

### Impact Explanation
Per the rules, "unauthenticated read of stack state ... or deploy output" via escalation into stack scoping is a High-severity outcome. Concretely: an operator who is issued a stack-scoped `ApiClient` token (e.g., embedded in a CI dashboard, status-page widget, or third-party CCTray/CCMenu client for stack A) can use that same token to query `GET /api/stacks/:stack_id/ccmenu?token=...` for *any other stack* `B` in the Shipit instance, and receive `B`'s latest deploy/rollback id, status, and timestamp — data the token holder was never granted access to. This crosses the "stack a token authorises versus a stack it touches" boundary explicitly called out as in-scope.

### Likelihood Explanation
High likelihood for anyone already holding a legitimate, narrowly-scoped `ApiClient` token (a normal, low-privilege credential intentionally restricted to one stack). No repository write access, GitHub identity, or session is required — only the token, which is exactly the credential this endpoint is designed to accept via the `token` query parameter. The only variable input needed is the target stack's `stack_id` (owner/repo/env), which is not secret and is typically visible in URLs, dashboards, or predictable naming conventions.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`, as `BaseController` does), so that a stack-restricted `ApiClient` can only ever resolve a stack within `current_api_client.stack_id`.

### Proof of Concept
1. Create a stack-scoped `ApiClient`, e.g. as done in fixtures: an `ApiClient` with `stack: shipit` and permission `read:stack` (mirrors `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`): [5](#0-4) 
2. Obtain its `authentication_token` (`ApiClient#authentication_token`): [6](#0-5) 
3. Send `GET /api/stacks/<some-other-stack>/ccmenu?token=<token>` where `<some-other-stack>` is any stack other than `shipit`.
4. Observe the request succeeds (200 with XML `Project` info for the other stack) instead of failing, because `CCMenuController#stack` uses `Stack.from_param!` unconditionally rather than the client-scoped `stacks` collection used everywhere else in `Api::BaseController`.
