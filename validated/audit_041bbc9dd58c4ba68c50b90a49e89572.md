### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that the delivery was signed by the GitHub App/organization matching `params.dig('repository','owner','login')`, but `StatusHandler#process` never re-checks that binding when looking up the target commit — it queries `Commit.where(sha: params.sha)` across the entire `commits` table, with no `stack_id`/repository scope. An attacker who controls their own Shipit-registered organization (and thus its `webhook_secret`) can sign a `status` event referencing a commit sha that belongs to a different, victim organization's stack, and Shipit will write a status onto that victim's commit.

### Finding Description
The claimed invariant is: `organization_whose_webhook_secret_signed(request) == organization_that_owns(Commit.find_by(sha: params.sha).stack)`. This equality is enforced nowhere in the code path.

Path:
1. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the *attacker's own* `repository.owner.login` in the payload, and verifies the signature against that app's secret [1](#0-0) . This only proves "the attacker's own org signed this payload" — it says nothing about which commit sha the payload references being owned by that org.
2. `#create` dispatches unconditionally to `Shipit::Webhooks.for_event('status')`, i.e., `Handlers::StatusHandler` [2](#0-1) [3](#0-2) .
3. `StatusHandler#process` performs a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack scoping and no comparison against `repository_owner` [4](#0-3) .
4. `create_status_from_github!` writes into `statuses.replicate_from_github!(stack_id, github_status)` and triggers `add_status`, which can emit `Hook.emit(:deployable_status, ...)` and call `stack.schedule_merges` if the new status is `pending?` or `success?` [5](#0-4) [6](#0-5) .

Attacker request: register/own an organization in Shipit (any org with a valid `webhook_secret` the attacker controls, e.g. their own fork/org), obtain the sha of a commit belonging to a victim stack (git shas are public on GitHub — visible via commits, PRs, branch history), then POST a `status` webhook signed with the attacker's own secret, `X-Github-Event: status`, body `{"sha": "<victim_sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}`. Signature verification passes (attacker's own secret verifies their own payload), `drop_unhandled_event` passes because `status` has a registered handler, and `StatusHandler` matches the victim's commit row purely by sha, writing an attacker-controlled status onto it.

Existing guards do not stop this: `verify_signature` only authenticates the *sender*, not the *target record*; `drop_unhandled_event` only checks handler registration exists; the `ExplicitParameters` schema in `StatusHandler` validates types (`sha`, `state`, etc.) but not ownership; no model validation in `Commit`/`Status` ties `sha` back to a github App/org.

### Impact Explanation
This lets an unprivileged attacker forge a successful (or failing) CI status on a victim's commit in a stack they do not control, without any Shipit credentials beyond their own organization's webhook secret. If the victim stack has `continuous_deployment?` enabled and the commit is otherwise deployable, forging a `success` status can trigger `schedule_continuous_delivery` → `ContinuousDeliveryJob`, i.e., an unauthorized deploy of the victim's code. This is a cross-repository/stack mutation — a payload authenticated for one organization mutates another organization's commit/task state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs any GitHub App/organization registered with Shipit that they control (a normal, low-privilege setup for a self-service Shipit instance), and knowledge of a target commit sha (publicly discoverable on GitHub). No Shipit session, API token, or victim secrets are required. The attack is trivially repeatable against any sha the attacker can enumerate, across arbitrary victim stacks, at negligible cost (one signed HTTP POST per attempt).

### Recommendation
In `StatusHandler#process`, scope the commit lookup to commits belonging to stacks associated with `repository_owner` (and ideally the specific `repository.full_name`) derived from the verified webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, ... })`, mirroring the same repository binding that `verify_signature` establishes at the controller layer.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook from attacker org cannot mutate victim's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: '1' * 40, message: 'victim commit')

  # Simulate attacker's own org verified signature (controller-level check passes for attacker)
  Shipit::WebhooksController.any_instance.stubs(:verify_signature).returns(true)

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'attacker-org' } }
  }

  post shipit.github_webhooks_path,
       params: payload.to_json,
       headers: { 'X-Github-Event' => 'status', 'Content-Type' => 'application/json' }

  victim_commit.reload
  assert_equal 'success', victim_commit.status.state,
    "Attacker-signed webhook for attacker-org mutated victim_stack's commit status"
end
```
Assert on both sides of the binding: `organization_that_signed == 'attacker-org'` while `organization_that_owns(victim_commit.stack) == 'victim-org'`; the test demonstrates the status is written despite the mismatch, proving `StatusHandler` — not `WebhooksController` — is the vulnerable component.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
