### Title
Cross-tenant team membership escalation via `X-Hub-Signature`/team binding mismatch in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate a webhook based solely on `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . `MembershipHandler#find_or_create_team!` then looks up (or creates) a `Team` keyed only by `params.team.id` (GitHub's numeric team id), setting `organization`/other attributes only inside the `find_or_create_by!` block, which Rails only executes on record creation [2](#0-1) . Nothing ties the organization whose secret verified the signature to the organization owning the `Team` row that ends up mutated.

### Finding Description
The binding that should hold is: `organization_that_signed_the_webhook == Team#organization_of_the_row_mutated`. Concretely: `Shipit.github(organization: repository_owner)` (using `params['organization']['login']` == `'attacker-org'`) should equal the `organization` column of the `Team` row identified by `params['team']['id']`.

Trace:
1. Attacker installs their own GitHub App on `attacker-org` and has a valid `webhook_secret` for it (attacker owns this organization, this is legitimate/unprivileged setup, not a stolen secret).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: membership` and a body such as:
   ```json
   {
     "action": "added",
     "team": {"id": <victim-org's authorization team github_id>, "name": "x", "slug": "x", "url": "https://api.github.com/teams/x"},
     "organization": {"login": "attacker-org"},
     "member": {"login": "attacker-controlled-login"}
   }
   ```
3. `repository_owner` resolves to `"attacker-org"` [1](#0-0) , so `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates using the attacker's own, legitimately-known `webhook_secret` [3](#0-2) . This succeeds — no forged secret needed.
4. `MembershipHandler#find_or_create_team!` runs `Team.find_or_create_by!(github_id: params.team.id)`. If a `Team` row for that `github_id` already exists (e.g., it's one of the organization's teams already synced into `Shipit.github_teams`, which are populated from configured `oauth_teams` via `Shipit.github_teams` / `Team.find_or_create_by_handle`) [4](#0-3) [5](#0-4) , the block that assigns `team.organization = params.organization.login` is **not executed** — `find_or_create_by!` only runs the block on creation. The existing row's `organization` column (`victim-org`) is left untouched.
5. `process` then calls `team.add_member(member)` with a `User` for the attacker-supplied `member.login`, inserting a `Membership` row linking that user to the victim-org's team [6](#0-5) [7](#0-6) .
6. Because `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) , the injected user is now authorized in Shipit regardless of actual GitHub org membership.

No existing guard prevents this: `verify_signature` only checks the cryptographic signature against whichever organization the payload names in its top-level fields, it never checks that this organization matches the organization the nested `team`/`organization` object claims to belong to, nor the organization actually recorded on the `Team` row being mutated. The `ExplicitParameters` schema for `MembershipHandler` only validates types/presence, not cross-consistency between `repository_owner` and `params.organization.login`, nor does it verify the team id actually belongs to the claimed org via a GitHub API call.

### Impact Explanation
An attacker who controls only their own GitHub organization/App can add an arbitrary user (or their own account/login) as a member of a `Team` belonging to a completely different, victim organization that is listed in `Shipit.github_teams`. Since `User#authorized?` derives Shipit authorization from team membership, this is a direct escalation into `Shipit.github_teams` authorization — a High-severity, cross-tenant authorization bypass. It is repeatable against any victim organization/team whose numeric `github_id` the attacker can learn (team ids are not secret values comparable to `webhook_secret`s and can be observed via public GitHub API responses, prior webhook traffic, or simple enumeration).

### Likelihood Explanation
Preconditions: the Shipit instance must be configured in multi-organization mode (`secrets.github` keyed by organization) so `Shipit.github(organization:)` resolves per-org secrets, and the attacker must control an organization with its own installed GitHub App producing a valid signature — both attainable by any unprivileged GitHub user creating a free organization and installing a GitHub App on it. The only additional cost is learning the target team's numeric `github_id`, which is a low bar (GitHub API team ids are integers, often discoverable). Given this, the attack is cheap, requires no privileged credentials, and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other handler resolving GitHub entities by numeric id from webhook payloads), verify that the resolved/existing `Team#organization` matches the organization that verified the webhook signature (`repository_owner`/`params.organization.login`) before mutating membership; reject or no-op when they diverge. More generally, `WebhooksController#verify_signature` should pass the verified organization down to handlers, and handlers should refuse to mutate any resource whose `organization` (or repository owner) differs from the verified organization.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual, engine test dir)
test "does not let a webhook signed by one organization mutate a team belonging to another organization" do
  victim_team = Shipit.create(:team, organization: 'victim-org', github_id: 42)

  handler = Shipit::Webhooks::Handlers::MembershipHandler.new(
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'x', 'slug' => 'x', 'url' => 'https://api.github.com/teams/x' },
    'organization' => { 'login' => 'attacker-org' }, # mismatched org, signature verified under attacker-org
    'member' => { 'login' => 'attacker-login' }
  )

  handler.call

  victim_team.reload
  assert_equal 'victim-org', victim_team.organization # unchanged, proving find_or_create_by! didn't re-set it
  assert victim_team.members.exists?(login: 'attacker-login') # but attacker's user was still added
end
```
This demonstrates that `Team#organization` remains `victim-org` (the equality `signing_org == team.organization` is false: `attacker-org != victim-org`) while the membership mutation still succeeds, confirming the cross-tenant write.
