### Title
CCMenu API token authorized for one stack can read build/deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The "CCMenu" integration mints an `ApiClient` token intended to expose a single stack's CI status, but the token it issues is never bound to that stack, and the controller that consumes the token bypasses the engine's normal per-token stack scoping. This breaks the equality that should hold between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping via the `stacks`/`stack` helper methods: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` has one set, and `stack` looks up `params[:stack_id]` only within that restricted relation. This is the mechanism that is supposed to enforce "a stack a token authorises == a stack it touches."

`Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, fetching the stack directly from the unscoped `Stack.from_param!(params[:stack_id])`: [2](#0-1) 

Separately, the token used to authenticate to this endpoint is minted by `Shipit::CCMenuUrlController`, which creates (or reuses) a single `ApiClient` per user named `'CCMenu Client'` with `read:stack` permission, but never sets `stack_id` to scope it to the specific stack the URL was generated for: [3](#0-2) 

`ApiClient#check_permissions!` only checks the coarse `operation:scope` string (e.g. `read:stack`), never which stack the permission applies to: [4](#0-3) 

Because (a) the CCMenu client is never stack-scoped, and (b) even if it were, `CCMenuController#stack` ignores that scoping, a `token` value legitimately obtained from `CCMenuUrlController#fetch` for stack A can be replayed against `GET /api/*/stack-B/ccmenu.xml` for any other stack B in the Shipit instance, and it will render B's build status.

This is the direct analog of the reported bug class: `Core.vcon` (the source of truth for authorization) can diverge from `CoreRef._vcon` (the copy actually consulted at use-time). Here, `ApiClient#stack_id` (never set) is the source-of-truth scoping the docs/design imply ("URL for `stack.to_param`"), while `CCMenuController#stack` (fetched fresh from `params[:stack_id]`, unscoped) is the value actually acted upon — the two are never bound together, exactly the "stack a token authorises versus a stack it touches" mismatch the rules call out.

### Impact Explanation
This is an unauthenticated-boundary-crossing read: an attacker who obtains any one CCMenu token (e.g. a build-monitoring widget URL for a public stack, an unlisted/leaked CCMenu URL, or their own account's token for a stack they can legitimately see) can enumerate `stack_id` values and pull build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity) for stacks they have no read permission on, including private/internal stacks. Per the rules this rises to "High — unauthenticated read of stack state ... task streams or deploy output" once the intended per-stack scoping is defeated, since the effective authorization becomes "any stack in the Shipit instance" rather than the one stack the token was generated for.

### Likelihood Explanation
High likelihood: the CCMenu token is designed to be embedded in third-party CI dashboard tools and shared/URLs, making leakage plausible, and no further privilege beyond possessing that single token string is required to pivot to arbitrary stacks — just changing the `stack_id` route parameter.

### Recommendation
- Set `stack_id: stack.id` when creating the `ApiClient` in `CCMenuUrlController#client` so each CCMenu token is bound to the stack it was requested for.
- Fix `Shipit::Api::CCMenuController#stack` to use the inherited, scoped `stack`/`stacks` helper from `BaseController` (i.e., remove the override, or reimplement it via `stacks.from_param!(params[:stack_id])`) so a token's `stack_id` scope is actually enforced.
- Add a permission/ownership check that `current_api_client.stack_id` (when present) equals the requested stack before rendering.

### Proof of Concept
1. As `user`, visit stack A's overview page; `Shipit::CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` named `'CCMenu Client'` for `user` with permission `read:stack` and no `stack_id`, returning a URL like `.../api/*/stack-A/ccmenu.xml?token=<TOKEN>` [5](#0-4) .
2. Take `<TOKEN>` and replay it against a different stack's CCMenu endpoint: `GET /api/*/stack-B/ccmenu.xml?token=<TOKEN>`.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it's a valid `ApiClient`), and `#stack` resolves `stack-B` directly via `Stack.from_param!`, bypassing any `stack_id` scoping [6](#0-5) .
4. Response renders stack B's build/deploy status even though the token was only ever presented to the user in the context of stack A.

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
```
