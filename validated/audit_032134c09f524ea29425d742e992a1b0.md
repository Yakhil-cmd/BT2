### Title
Webhook signature is verified against the organization named in the payload while the Status handler applies the payload to any commit installation-wide, letting one authenticated GitHub organization forge CI status for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly out of the same untrusted JSON payload it is trying to authenticate. In a "multiple GitHub Applications" deployment (documented and supported by Shipit for exactly this purpose), each organization has its own independent `webhook_secret`. Nothing binds the organization whose secret validated the signature to the repository/commit that the resulting handler actually mutates. The `StatusHandler` in particular does not scope by repository at all — it looks up commits installation-wide by `sha`.

### Finding Description
`verify_signature` picks the signing secret to check against based on `repository_owner`, itself taken from the same payload being verified: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to whichever org's config (and `webhook_secret`) is looked up by that field, per the multi-app support: [3](#0-2)  and the documented multi-org secrets layout: [4](#0-3) .

Once the HMAC check passes (because it was checked against the secret of whichever organization is named by `repository.owner.login`/`organization.login` in the payload), the raw JSON is dispatched to handlers with no re-validation that the organization used for authentication matches the resource the handler subsequently acts on: [5](#0-4) 

Most handlers at least scope to `Repository.from_github_repo_name(repository_name)` (itself just another attacker-controlled field, `repository.full_name`, independent from `repository.owner.login`): [6](#0-5) 

But `StatusHandler` doesn't scope by repository/organization at all — it matches purely on commit `sha` across the entire Shipit installation: [7](#0-6) 

Applying a forged status calls `Commit#create_status_from_github!`, which records the attacker-chosen `state`/`context` and can flip the commit's deployable/mergeable status: [8](#0-7) [9](#0-8) 

This status is exactly what gates deploys and the merge queue via `ci.require`/`required_statuses`: [10](#0-9) [11](#0-10) [12](#0-11) 

**The equality binding that is broken:** the organization whose `webhook_secret` authenticated the request (`repository_owner` in the payload) is never required to equal the organization/repository whose commit status is written (looked up only by `sha`, with no repository/org filter at all in `StatusHandler`). Any tenant/org onboarded onto a multi-org Shipit instance — who legitimately possesses their own GitHub App's `webhook_secret` — can author an arbitrary raw POST body, sign it with their own secret, but populate `sha`/`state`/`context` for a commit sha belonging to a completely different organization's stack.

### Impact Explanation
A tenant of a multi-org Shipit deployment can forge a passing status (matching a `ci.require` context) for commits in stacks belonging to a different organization they have no access to. Since `Commit#deployable?`/`required_statuses` gate both the merge queue (`ProcessMergeRequestsJob`, triggered from `add_status` when state becomes `success`) and the deploy API's `require_ci` check, this can be used to force an unauthorized merge or unauthorized deploy of a commit that never actually passed the victim organization's real CI. This is a cross-organization authorization break, mapping to "unauthorized deploy, rollback or merge," which is Critical impact per the engine's threat model.

### Likelihood Explanation
The webhook endpoint is unauthenticated apart from the HMAC signature, and the flaw only requires the attacker to control one legitimate GitHub App/organization already wired into the Shipit instance (the documented supported "Using Multiple GitHub Applications" configuration) — no repository write access, GitHub App private key, or Shipit session/API token is needed. The only extra requirement (colliding a real commit `sha` between victim/attacker repos, or targeting a repo whose commits happen to be known) makes this a targeted rather than trivial-to-mass-exploit bug, but it is fully reachable by an unprivileged (relative to the victim org) attacker in any multi-tenant Shipit deployment.

### Recommendation
- Do not select the verification secret from an untrusted field of the same payload being verified; instead verify the signature against every configured organization's `webhook_secret` (or bind webhook URLs per-organization) before trusting any payload field.
- After signature verification, thread the authenticated organization through to handlers and require every handler (especially `StatusHandler`) to filter by `Repository.from_github_repo_name(repository_name)`/stack ownership matching the authenticated organization, not merely by `sha`.

### Proof of Concept
1. Operate/administer GitHub App "OrgA" on a multi-org Shipit instance, and know `webhook_secret` for OrgA (legitimate for that org).
2. Craft a raw JSON body: `X-Github-Event: status`, with `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` looks up and validates against OrgA's secret, but `sha` set to a commit sha from OrgB's tracked stack, `state: "success"`, `context` matching OrgB's `ci.require` context.
3. Sign the raw body with OrgA's `webhook_secret` and POST to `/webhooks`.
4. `WebhooksController#verify_signature` passes (OrgA's secret matches). `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds OrgB's commit by `sha` (no org/repo scoping) and records the forged "success" status, which can trigger `ProcessMergeRequestsJob` / satisfy `require_ci` for an unauthorized deploy on OrgB's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
