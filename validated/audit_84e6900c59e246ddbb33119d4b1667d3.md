### Title
Missing `review_stacks_enabled` guard on `prevent_with_label` disjunct in `OpenedHandler#provision?` allows unauthorized ReviewStack creation from a disabled repository - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` only ANDs `repository.review_stacks_enabled` with the first disjunct (`allow_all?`); due to Ruby's `&&`/`||` precedence, the second and third disjuncts (`allow_with_label?`/`prevent_with_label?`) are evaluated completely independently of `review_stacks_enabled`. A repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` will still have `provision?` return `true` for any unlabeled pull request, causing an unauthorized `ReviewStack` to be created and queued for provisioning off the attacker's fork branch.

### Finding Description
The claimed broken binding is: `review_stacks_enabled` (as gating disjunct 1) == `review_stacks_enabled` (as gating disjuncts 2/3). Tracing the code confirms they are NOT equal — disjuncts 2/3 have no dependency on it at all:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. For a repository with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label`, an "opened" PR webhook with no labels makes the third disjunct evaluate `true` regardless of `review_stacks_enabled`.

`process` then calls into `respond_to_pull_request_opened?` → `provision?` → true → invokes `ReviewStackAdapter#find_or_create!`: [2](#0-1) 

`find_or_create!` → `create!` builds the `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled fork branch) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

The attacker's exact request: open a pull request (from a forked repo the attacker owns) against the victim repository, with no labels, `pull_request.head.ref` pointing to the attacker's branch. The webhook is a normal GitHub-delivered "opened" event; `verify_signature` in `WebhooksController` validates the GitHub HMAC signature of the payload but does not — and cannot — validate the *semantic* correctness of `provision?`'s boolean logic, so it does not prevent this: [4](#0-3) 

Note the sibling handler `LabeledHandler#respond_to_label_change?` explicitly ANDs the whole behavior check with `repository.review_stacks_enabled`, showing the intended invariant and confirming `OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) diverges from it: [5](#0-4) [6](#0-5) 

Existing tests never exercise the combination `review_stacks_enabled: false` + `provisioning_behavior: :prevent_with_label`; the closest test, "create stacks for repos what prevent_with_label when label is absent," never sets `provisioning_enabled: false`: [7](#0-6) 

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against the target repository can force creation and provisioning of a `ReviewStack` on a repository whose owner explicitly disabled review stacks (`review_stacks_enabled: false`). The stack's `branch` is set directly from `pull_request.head.ref`, i.e., the attacker's own fork branch, and it is enqueued via `Shipit::ReviewStackProvisioningQueue.add`, feeding the provisioning pipeline (which builds/deploys based on the branch's `shipit.yml`). This is a write of a persisted record and a queued deploy/provisioning action for a repository that opted out and never authenticated this action — an unauthorized deploy/provisioning event using attacker-controlled code, matching the Critical "unauthorized deploy" impact category. It is repeatable against any repository configured this way and by any GitHub user able to open a PR against it (public repos, or private repos where the attacker otherwise has PR access).

### Likelihood Explanation
Preconditions are simply repository-level configuration choices (`review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label`) that an operator would reasonably pick believing review stacks are fully disabled. No secrets, tokens, or privileged roles are required — only the ability to open a pull request, which is the baseline capability defined for this attacker. The bug triggers automatically on every "opened" webhook meeting the condition, so it is fully repeatable and requires no race condition or timing tricks.

### Recommendation
Fix operator precedence/grouping so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`, which has the same unguarded disjuncts.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, using existing `configure_provisioning_behavior` helper):
```ruby
test "does not create stacks for repos with review stacks disabled even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []   # no label -> disjunct 3 true

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: `repository.review_stacks_enabled` is `false` (LHS) while the observed behavior (`provision?` truthiness, evidenced by a `ReviewStack` row being created and enqueued) is `true` (RHS) — proving they diverge. Running this against current code fails (`assert_no_difference` fails because a `Shipit::Stack` row is created), demonstrating the bug; the fixed `provision?` implementation makes it pass.
