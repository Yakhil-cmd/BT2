### Title
Cross-organization `Team` hijack via unvalidated `github_id` lookup in `find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, with no filter on `organization`, so a genuinely-signed `membership` webhook from a different, attacker-controlled GitHub organization that happens to (or is crafted to) reuse a `team.id` value can return and mutate a pre-existing `Team` row that belongs to another organization. This allows an attacker who legitimately owns/administers a GitHub organization configured in Shipit's multi-org GitHub App setup to add themselves (or any GitHub login) as a member of a `Team` belonging to a different tenant, escalating into that team's `Shipit.github_teams` authorization scope.

### Finding Description
The broken binding: the returned `Team.organization` should equal `params.organization.login` (the organization asserted in the signed payload), but the lookup `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end` [1](#0-0)  only assigns `team.organization = params.organization.login` inside the block that Active Record runs **only on creation**. If a `Team` row with that `github_id` already exists (created earlier for a different organization, e.g. via `Shipit.github_teams` seeding through `Team.find_or_create_by_handle`) [2](#0-1) [3](#0-2) , `find_or_create_by!` returns that existing row unchanged, and the handler proceeds to call `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , writing a `Membership` for the wrong, cross-tenant team.

However, signature verification is scoped per-organization: `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('organization', 'login')` and calls `github_app.verify_webhook_signature` using that specific organization's `webhook_secret` [5](#0-4) . This means the attacker can only produce a valid signature for a payload whose `organization.login` matches an organization for which they control (or have been given) the configured `webhook_secret` in Shipit's `secrets.github` config — i.e., an organization that a Shipit operator has already registered as a GitHub App installation/org in this deployment. Genuinely forging a signature for an arbitrary attacker-owned org requires that org to already be one of the app's configured installations with a secret only the Shipit operator/GitHub knows; a truly unprivileged internet attacker with no relationship to the Shipit deployment cannot mint a valid `X-Hub-Signature` for any organization, because `verify_webhook_signature` uses HMAC-SHA1 with the app's `webhook_secret`, which the attacker does not possess (`SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(...))`) [6](#0-5) .

The question's premise — "an unprivileged attacker send a genuinely-signed webhook from their own organization" — requires the attacker's organization to already be a legitimate, configured tenant in this Shipit instance (i.e., they possess that org's `webhook_secret`, meaning they are effectively a co-tenant operator, not an anonymous internet user). Once that precondition is granted, the `find_or_create_by!` bug is real: the lookup is genuinely github_id-only, with no organization filter, and the block does not re-validate `team.organization` on an existing record.

### Impact Explanation
If exploited, an attacker-org can add arbitrary GitHub logins as `members` of a `Team` belonging to a different organization in the same Shipit deployment, which is used for authorization checks against `Shipit.github_teams` (team-based access control) [7](#0-6) . This is a cross-tenant `Team`/`Membership` mutation not authenticated by the organization named in the same payload, matching the "payload for one repository mutating another's ... team" Critical category — but only within a Shipit deployment that already hosts multiple independently-configured, mutually distrusting GitHub organizations (multi-org `secrets.github` config), since only tenants of that specific configuration can produce a valid signature at all.

### Likelihood Explanation
Preconditions are stringent: (1) Shipit must be configured with multiple GitHub organizations under `secrets.github` (multi-tenant App config) [8](#0-7) ; (2) the attacker must control one of those already-configured, trusted organizations (possess its real `webhook_secret`) — this is not available to a generic unprivileged internet user or GitHub PR-opener as defined in scope, since minting a "genuinely-signed" webhook for any organization requires that organization's registered `webhook_secret`, which Shipit itself never discloses; (3) a colliding `github_id` between two teams from different organizations must exist, which is not attacker-controlled (`github_id` is GitHub's own team ID, assigned by GitHub, not chosen by the requester) — GitHub team IDs are globally unique across GitHub.com, so an attacker cannot force a collision with a victim's real team ID on shared github.com; this only becomes practically likely on GitHub Enterprise instances with independent ID spaces, or in a contrived test scenario.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
  end
end
```
Additionally, consider raising/rejecting if a `Team` with that `github_id` exists under a different `organization`, to surface a genuine ID collision as an error rather than silently reusing the record.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Create `shipit_teams(:shopify_developers)` fixture/record with `github_id: 999`, `organization: 'shopify'`.
2. Configure a second organization `'attacker-org'` in `secrets.github` for the test app with its own known `webhook_secret`.
3. Build a `membership` webhook payload: `{ action: 'added', team: { id: 999, name: 'x', slug: 'x', url: 'https://x' }, organization: { login: 'attacker-org' }, member: { login: 'evil-user' } }`.
4. Sign it with `attacker-org`'s real `webhook_secret` via `OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`.
5. POST to `/webhooks` with `X-Github-Event: membership` and the valid `X-Hub-Signature`.
6. Assert both sides of the binding: expected `team.organization == 'attacker-org'` (a new team) vs. actual `Shipit::Team.find_by(github_id: 999).organization == 'shopify'` and `shipit_teams(:shopify_developers).members.map(&:login)` now includes `'evil-user'` — demonstrating the payload from `attacker-org` mutated `shopify`'s team.

Note: this PoC still requires the test harness to grant the attacker a legitimate `webhook_secret` for a second configured organization, which is outside the "unprivileged internet attacker" threat model defined in the rules unless the deployment is genuinely multi-tenant with mutually distrusting orgs sharing one Shipit instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
