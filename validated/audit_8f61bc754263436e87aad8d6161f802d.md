Found a directly analogous pattern in `pallet-fast-unstake`. Both the entry action (`register_fast_unstake`) and the exit/reversal action (`deregister`) are gated by the exact same single toggle, `ErasToCheckPerBlock`. This mirrors the AI Arena root cause precisely: a single admin-controlled flag simultaneously halts the "opt-in" and "opt-out" paths, trapping funds committed while the feature was enabled.

### Title
`pallet-fast-unstake::deregister` is gated by the same `ErasToCheckPerBlock` toggle as `register_fast_unstake`, permanently locking a user's reserved deposit when the pallet is halted - (File: `substrate/frame/fast-unstake/src/lib.rs`)

### Summary
`pallet-fast-unstake` lets a signed, unprivileged staker opt in to fast-unstaking via `register_fast_unstake`, which reserves a `Deposit` and queues the stash. The reversal path, `deregister`, is meant to let a user who changes their mind reclaim that deposit and leave the queue. Both calls share the identical guard `ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed)`. `ErasToCheckPerBlock` can be (and, per the pallet's own defensive `halt()` logic, automatically is) set to `0`, which stops `on_idle` from processing the `Queue`/`Head` at all. Once that happens, a user who registered while the pallet was active can neither be processed out of the queue nor call `deregister` to exit, so their reserved `Deposit` becomes stuck with no available extrinsic path to release it.

### Finding Description
`register_fast_unstake` and `deregister` are defined with the same precondition: [1](#0-0) [2](#0-1) 

The `ErasToCheckPerBlock` storage item is documented as an on/off switch: "If set to 0, this pallet does absolutely nothing." [3](#0-2) 

The pallet even has a self-halt safety mechanism that forces this value to `0` on any unexpected internal error, explicitly calling this a "halt/disable": [4](#0-3) [5](#0-4) 

`do_on_idle` also early-returns and does nothing whenever `ErasToCheckPerBlock` is `0`, so once halted, the `Queue`/`Head` are never drained either: [6](#0-5) 

This is structurally the same defect as the referenced AI Arena finding: staking (`allowedStakingDuringRanked = true`) and unstaking share one boolean; turning it off (an otherwise legitimate admin action) blocks the exit path for users who already opted in. Here, `register_fast_unstake` (entry) and `deregister` (the only user-initiated exit besides pallet-driven processing) share one toggle (`ErasToCheckPerBlock != 0`); zeroing it (via `control()` by `ControlOrigin`, or automatically via `halt()`) blocks both the opt-in *and* the opt-out for users who are already queued, with no other extrinsic able to release their `Deposit`.

### Impact Explanation
While queued, `register_fast_unstake` has already fully unbonded and chilled the underlying stash within `pallet-staking`/`pallet-staking-async`, so the user's actual *stake* is not additionally at risk (it can be withdrawn via the normal staking `withdraw_unbonded` path once bonding duration elapses, independent of fast-unstake state). However, the `Deposit` reserved by `T::Currency::reserve` specifically for the fast-unstake registration: [7](#0-6) 
has no release path other than `deregister` or successful processing via `do_on_idle`, both of which are blocked once `ErasToCheckPerBlock == 0`. This is a locked-funds condition on the deposit for as long as the pallet remains halted, which can be indefinite if the halting error condition persists after `ControlOrigin` attempts to re-enable it.

### Likelihood Explanation
The pallet's own documented safety behavior deliberately zeroes `ErasToCheckPerBlock` on internal errors, and the `ControlOrigin` can also do so intentionally for operational reasons (e.g., to stop weight consumption). Any user with a registration in `Queue` at that moment is affected — no attacker action or privileged compromise is needed; a normal signed user simply loses access to a normal signed exit call as a side effect of a routine/defensive governance action.

### Recommendation
Decouple the `deregister` guard from `ErasToCheckPerBlock`. Allow signed stakers who are still in `Queue` (not yet in `Head`) to `deregister` and reclaim their `Deposit` regardless of whether the pallet is currently processing (`ErasToCheckPerBlock == 0`), mirroring the AI Arena recommendation that reversal of a previously permitted, user-initiated commitment should never be gated by the same switch used to admit new commitments.

### Proof of Concept
The existing test suite already reproduces the exact trapped state (only missing the observation that no path to unreserve then exists): [8](#0-7) 

Steps, using the existing mock/test harness in `substrate/frame/fast-unstake/src/tests.rs`:
1. `ErasToCheckPerBlock::<T>::put(1)` — pallet active.
2. `FastUnstake::register_fast_unstake(RuntimeOrigin::signed(1))` — succeeds; `Deposit` reserved, stash queued, this matches `register_works`/`deregister_works` test setup.
3. `ErasToCheckPerBlock::<T>::put(0)` — simulate `control()` by `ControlOrigin` or automatic `halt()`.
4. `FastUnstake::deregister(RuntimeOrigin::signed(1))` → fails with `Error::<T>::CallNotAllowed` (confirmed by the existing `deregister_disabled_fails` test).
5. Additionally assert `FastUnstake::on_idle(..., large_weight)` is a no-op while `ErasToCheckPerBlock == 0` (per `do_on_idle` early return), and that `Queue::<T>::get(1)` still shows the reserved `Deposit`, with `<T as Config>::Currency::reserved_balance(&1)` unchanged — demonstrating the deposit is stuck with no extrinsic capable of releasing it while the pallet remains halted.

This is a real code path reachable by any unprivileged signed account (`register_fast_unstake`/`deregister`), with the triggering condition (`ErasToCheckPerBlock -> 0`) being either an intended governance operation or the pallet's own documented defensive self-halt — not a privileged attacker action, consistent with how the original AI Arena Medium finding was scoped.
