### Title
`status` webhook writes `Status` records by bare SHA lookup with no repository scoping, allowing cross-tenant status forgery on a shared commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is a global, unscoped-by-repository query across the whole `commits` table. Any webhook sender whose signature validates for *some* organization (their own) can supply an arbitrary `sha` value in the JSON body; if that SHA also identifies a commit belonging to an unrelated victim stack (e.g., because the attacker forked the victim's public repository and shares its git history), the handler will create a `Status` row against the victim's `stack_id`, changing that commit's computed status for contexts like `deploy/production`.

### Finding Description
The broken binding is: `status.stack_id` (the tenant that a forged `failure`/`success` status is attributed to) should equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks` (the tenant that actually authenticated/owns the webhook). Instead:

- `WebhooksController#verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)` [1](#0-0)  — this only proves the payload was signed with the secret configured for the *organization named in the payload*, not that the `sha` inside the payload belongs to a commit under that organization/repository.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1)  — no filter on `repository_name`/`repository.full_name` at all, unlike every other handler in this engine (e.g. `PullRequest::OpenedHandler#repository`, `ClosedHandler#repository`) which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any records [3](#0-2) . The base `Handler` class even exposes a `stacks` helper scoped by `repository_name` [4](#0-3)  that `StatusHandler` simply never calls.
- `commit.create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) , and `Status.replicate_from_github!` writes the new row keyed to `commit.stack_id` — the victim's stack, not the attacker's [6](#0-5) .

Exploit flow: attacker owns (or controls webhook delivery for) some GitHub org/repo that is registered in this Shipit instance, and therefore knows/controls a webhook secret that will pass `verify_webhook_signature` for that org (this is per-organization, not per-commit) [7](#0-6) . The attacker forks the victim's public repository (or otherwise ensures a shared commit SHA), sends `POST /webhooks` with header `X-Github-Event: status`, `repository.owner.login` set to their own org (so the signature check passes), and body `{"sha": "<shared-sha>", "state": "failure", "context": "deploy/production", ...}`. `StatusHandler` matches that SHA across every stack in the installation, including the victim's, and creates a `Status(stack_id: victim_stack.id, context: "deploy/production", state: "failure")` on the victim's commit. This can flip `Commit#deployable?`/`Commit#blocked?` for the victim stack, and (via `state: "success"` instead) can force `stack.schedule_merges` on a commit that never actually passed the victim's real CI, per `Commit#add_status` [8](#0-7) .

None of the existing guards prevent this: `verify_signature` only authenticates an organization, not a commit-repository relationship; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate shape (`sha`, `state`, `context` are free-form strings) [9](#0-8) ; there is no `require_permission!`/`stacks` scoping check in this handler at all.

### Impact Explanation
A payload authenticated for one repository/organization can write a `Status` record attributed to a completely different tenant's stack, satisfying "a payload for one repository mutating another's stack, commit, task or team." Depending on the required-context configuration of the victim stack, this can force a required `deploy/production` context to `failure` (blocking deploys/merges) or to `success` (enabling `stack.schedule_merges`/`deployable?` to flip true on a commit that did not actually pass CI, i.e. unauthorized deploy/merge readiness). This is repeatable against any stack whose tracked repository shares a commit SHA with an attacker-controlled repo (trivial via forking any public repo the victim tracks), and the blast radius extends to every stack in the multi-tenant installation, matching the Critical "cross-tenant state manipulation" category.

### Likelihood Explanation
Preconditions: the attacker must control (own an org/repo registered in the target Shipit installation, i.e. one with a configured webhook secret they know) so their `status` webhook passes `verify_signature`; and a shared commit SHA between their controlled repo and the victim stack's repo, trivially obtained by forking the victim's public GitHub repository. No GitHub App private key, session, or `api_clients_secret` is required — the exploit is a plain unauthenticated `POST /webhooks` with a crafted body. This is realistic in any multi-tenant Shipit deployment where multiple orgs/forks are onboarded, and is repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the `repository`/`stacks` scoping already used by other handlers such as `PullRequest::OpenedHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status handler must not write a status for a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared")

  attacker_payload = {
    "sha" => shared_sha,
    "state" => "failure",
    "context" => "deploy/production",
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker-org" } }
  }

  before_status_count = victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  # Binding under test: status.stack_id (attacker's authenticated tenant) should equal
  # victim_commit.stack_id (the tenant actually addressed) -- expect NO new status created
  # because attacker's repository is not the victim's repository.
  assert_equal before_status_count, victim_commit.statuses.count,
    "a status webhook authenticated for attacker/unrelated-repo must not mutate victim_stack's commit"
end
```
This test currently fails against `StatusHandler#process`, because `Commit.where(sha: params.sha)` matches `victim_commit` regardless of the payload's `repository` field, demonstrating the cross-tenant write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
