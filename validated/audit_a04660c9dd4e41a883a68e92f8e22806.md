### Title
Membership webhook authorization escalation via unscoped `github_id` team lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the signing secret to validate a webhook using the `organization`/`repository.owner.login` field of the *payload itself*, but `MembershipHandler` then writes team membership using a *different, unvalidated* field (`team.id`) that is never checked to actually belong to that same organization. This breaks the binding: "organization whose secret authenticated the request" ≠ "team/organization actually written to the authorization table (`Shipit::Team` → `Shipit.github_teams`)".

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App (and thus which webhook secret) to verify against purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

For `membership` events there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — again attacker-controlled and only used to *choose the secret*, not to constrain what is subsequently written.

`MembershipHandler#process` then trusts a completely different, independently attacker-controlled field — `params.team.id` — to look up or create the `Team` record that is granted membership, without ever verifying that this GitHub team id truly belongs to the `organization.login` that was used to select the signing secret: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` matches globally on `github_id`, not scoped by organization. If a `Team` row already exists in Shipit's database for that `github_id` (e.g. it was previously synced from a legitimate, privileged organization listed in `Shipit.github_teams`), the forged event will find that *pre-existing* team and call `team.add_member(member)` on it, regardless of what organization the attacker put in the payload: [4](#0-3) 

Team membership in that table is exactly what gates application-wide authorization: [5](#0-4) [6](#0-5) 

The `/webhooks` endpoint requires no Shipit session or API token — only a valid `X-Hub-Signature` for *some* organization's webhook secret configured on the instance: [7](#0-6) 

Per `docs/setup.md`, each onboarded organization creates its own GitHub App and supplies its own webhook secret to the Shipit operators, so an org admin legitimately knows their *own* org's secret without holding any Shipit credential. Multi-org Shipit deployments are an explicit, supported configuration (see the dummy multi-app secrets fixture used in tests).

### Impact Explanation
An attacker who administers (or compromises) any single GitHub organization onboarded to a shared Shipit instance — and thus legitimately knows that organization's webhook secret — can forge a `membership` webhook signed with their own org's secret while setting `team.id` to the GitHub team id of a *different* organization's privileged team (one listed in `Shipit.github_teams`). If that team is already known to Shipit, the attacker can add an arbitrary `member.login` (including themselves) to it, escalating that user into `Shipit.github_teams` authorization and gaining access to the whole application (stacks, deploys, rollbacks) — matching the explicitly listed High-severity impact "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires the attacker to control (or compromise) at least one organization's GitHub App webhook secret already onboarded to the shared Shipit instance — a realistic scenario for any multi-tenant Shipit deployment serving several teams/orgs, none of which is a Shipit session, API client token, or GitHub App private key. It additionally requires the target privileged team's `github_id` to already exist as a `Team` row in Shipit (true for any team already used for authorization, since it must have received at least one prior legitimate `membership` webhook to exist). This is a plausible, low-friction attack path once multi-org deployment is in place.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` **and** the authenticated `organization.login`, and reject/ignore the event if an existing `Team` with that `github_id` belongs to a different `organization` than the one whose secret validated the signature. More generally, `WebhooksController#verify_signature` should pass the resolved/authenticated organization down to handlers so every downstream write can be asserted against it, rather than each handler independently trusting other payload fields.

### Proof of Concept
1. Shipit is deployed serving two organizations, `orgA` and `orgB`, each with its own GitHub App and webhook secret (as in `test/dummy/config/secrets_double_github_app.yml`).
2. `orgB` has a team `T` (github team id `999`) already synced into Shipit's `teams` table and listed in `Shipit.github_teams` for authorization.
3. Attacker legitimately administers `orgA` and therefore knows `orgA`'s webhook secret.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `orgA`'s secret, and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "T", "slug": "t", "url": "..." },
  "organization": { "login": "orgA" },
  "member": { "login": "attacker" }
}
```
5. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s GitHub App, and the signature validates successfully.
6. `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: 999)`, finds the pre-existing `orgB` team `T`, and `team.add_member(User.find_or_create_by_login!("attacker"))` adds the attacker to it.
7. Attacker logs into Shipit; `User#authorized?` now returns `true` because they belong to a team in `Shipit.github_teams`, granting full application access without ever being a member of `orgB` on GitHub.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
