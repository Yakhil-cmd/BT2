### Title
Cross-stack status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves commits purely by bare SHA with no repository or stack scoping, and applies the incoming GitHub status to every matching `Commit` row across the entire database. Since GitHub SHAs are content-addressed and identical commits legitimately exist in multiple `Shipit::Commit` rows (forks, mirrors, or multiple stacks/review-stacks tracking the same repository history), a webhook whose signature is validated only against the sending repository's/organization's webhook secret can flip required-status state (e.g. `ci/lint` `failure`) on a `Commit` belonging to a different, unrelated stack.

### Finding Description
The broken binding the code should enforce is: `status.repository == commit.stack.repository` (the status must only ever mutate a `Commit` that belongs to a stack backed by the exact repository that authenticated the webhook). The actual code does not encode this equality at all: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across every stack in the installation.

Signature verification in `WebhooksController#verify_signature` only proves the payload was signed by the GitHub App/organization matching `params.dig('repository','owner','login')`; it says nothing about which `Commit`/`Stack` rows the SHA is allowed to touch: [2](#0-1) 

Because `Shipit::Commit` rows are per-`stack` copies of GitHub commits (`belongs_to :stack`), the same underlying git commit (identical SHA, since SHAs are derived from content+history) can legitimately be recorded in more than one stack's `commits` table — e.g. a stack tracking `main` and a review stack auto-provisioned from a pull request that shares history with `main`, or multiple environment stacks on the same repository. `StatusHandler` walks *all* rows sharing that SHA and calls `create_status_from_github!` on each, which recomputes `deployable?`/`blocked?` via `add_status` and can trigger `stack.schedule_merges` and continuous-delivery scheduling: [3](#0-2) [4](#0-3) 

Exploit flow: with `review_stacks_enabled: true, allow_all` on `Shipit::Repository`, opening a pull request auto-provisions a review stack that executes `shipit.yml` from the PR branch (a separate, already-documented capability in this engine). Because that review stack shares commit ancestry (and therefore SHAs for shared commits) with the base repository/stack, a `status` event authenticated for the attacker's own fork/branch push can carry a `sha` that also matches a `Commit` row belonging to the victim's main (or another) stack for the same repository, letting the attacker set `context: ci/lint`, `state: failure` on that unrelated stack's commit and flip its `deployable?`/`blocked?` state, i.e. a payload authenticated for one context mutates another stack's required-status/deploy state — matching the "payload for one repository mutating another's stack, commit, task or team" Critical impact category. None of `verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler`, or model validations constrain the write to the authenticating repository/stack, because the query in `process` never references `repository_owner`, `params.dig('repository', ...)`, or any stack/repository foreign key at all.

### Impact Explanation
Any `Commit` row anywhere in the Shipit instance that shares a SHA with a commit legitimately signed for by *some* repository/org can have its status set by that unrelated party. Given `review_stacks_enabled true, allow_all`, review stacks are auto-provisioned for arbitrary external PRs and execute `shipit.yml`, so flipping the resolved status (e.g. from `ci/lint` failure to unblocked, or vice versa to block a legitimate deploy) can force or prevent a ship. This is repeatable for every commit SHA shared across stacks/forks and is not limited to a single victim stack — it applies to any stack whose commit history overlaps with an attacker-controlled repository, satisfying the Critical "unauthorized deploy" / "payload for one repository mutating another's stack" categories.

### Likelihood Explanation
Preconditions: the victim repository must have `review_stacks_enabled: true` with `allow_all` (or otherwise have multiple stacks/forks sharing commit history with attacker-reachable repositories), and GitHub must route a validly-signed `status` webhook for an attacker-owned or attacker-influenced repository whose commit history intersects the victim stack's. The attacker cost is low — opening a PR and pushing a commit/status is normal unprivileged GitHub activity — but the exploit requires the SHA collision to be a *real, shared commit* (fork/shared ancestry), not an arbitrary attacker-chosen SHA, since SHAs cannot be forged for content the attacker doesn't control. This makes it highly likely for the review-stack/base-stack sibling relationship described in the question (both tracking the same repository/ancestry) and plausible but conditional for cross-repository forks.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g. join through `Stack`/`Repository` using `params.dig('repository', 'full_name')` (or owner+name) so only commits belonging to stacks whose `Repository` matches the authenticating repository are updated: `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { name: repo_name, owner: repo_owner })`. Apply the same repository-scoping principle to any other handler that resolves records by bare SHA.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new):
1. Create `repository_a` and `repository_b` (fixtures), and `stack_a` on `repository_a`, `stack_b` (review stack, `review_stacks_enabled: true, allow_all`) on `repository_b`, where both stacks require `ci/lint`.
2. Create two `Commit` rows with the **same** `sha` (`"deadbeef..."`), one belonging to `stack_a`, one to `stack_b`, both currently `success`/deployable.
3. Build a `status` payload: `{ sha: "deadbeef...", context: "ci/lint", state: "failure", repository: { full_name: repository_b.full_name, owner: { login: repository_b.owner } } }` (i.e. authenticated only for `repository_b`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
5. Assert: `commit_b.reload.deployable?` is now `false` (expected — authenticated repo). Assert (bug): `commit_a.reload.deployable?` is **also** `false` even though the webhook was never signed for `repository_a` — i.e. `commit_a.stack.repository == repository_a` while the status came from `repository_b`, proving the binding `status.repository == commit.stack.repository` is violated.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
