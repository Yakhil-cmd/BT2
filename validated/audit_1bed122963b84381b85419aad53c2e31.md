### Title
Unsafe `uint64`→`int64` Narrowing Cast in `consolidatedNode.Split` Corrupts CN/CL Reward Distribution — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split` converts `uint64` staking amounts to `int64` via `big.NewInt(int64(c.StakingAmount))` without bounds checking. When either `StakingAmount` or `CLStakingAmount` exceeds `math.MaxInt64` (9,223,372,036 in KAIA units), the cast silently wraps to a negative value, producing a corrupted `totalAmount` denominator and therefore a wrong CN/CL reward split ratio. Every block where the affected validator is a staker or proposer distributes KAIA rewards to the wrong addresses.

---

### Finding Description

In `kaiax/staking/staking_info.go`, the `Split` function is responsible for proportionally dividing a reward `amount` between a validator's CNStaking address and its CLPool address:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }

    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))              // ← unsafe cast
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // ← unsafe cast
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)

    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are typed `uint64`: [2](#0-1) [3](#0-2) 

`uint64` has a maximum of `18,446,744,073,709,551,615`. `int64` has a maximum of `9,223,372,036,854,775,807`. Staking amounts are stored in KAIA units (divided by `params.KAIA = 1e18` at ingestion time): [4](#0-3) [5](#0-4) 

So the overflow threshold is **9,223,372,036 KAIA** staked by a single consolidated validator. Any value above this wraps to a negative `int64`, making `cnAmountBig` or `clAmountBig` negative. The resulting `totalAmount` denominator is then wrong (too small, zero, or negative), and the `clAmount = clAmountBig * amount / totalAmount` ratio is corrupted.

`Split` is called in three production reward paths:

1. `assignStakingRewards` (Kore/Prague path) — per-staker reward allocation: [6](#0-5) 

2. `assignStakingRewardsFlex` (Osaka/Flex path) — per-staker reward allocation: [7](#0-6) 

3. `specWithProposerAndFundsFlex` / `specWithProposerAndFunds` — proposer reward split: [8](#0-7) 

All three paths feed directly into `FinalizeState`, which writes the resulting balances to the state trie every block.

---

### Impact Explanation

When `StakingAmount` or `CLStakingAmount` exceeds `math.MaxInt64` in KAIA units, the `Split` ratio is computed from a corrupted denominator. Concretely:

- If `cnAmountBig` wraps negative and `clAmountBig` is positive, `totalAmount` is smaller than the true total, inflating `clAmount` beyond the actual reward — the CL pool receives more KAIA than it is entitled to, and the CN staking address receives less.
- If `totalAmount` becomes zero (both wrap to equal-magnitude negatives), the `Div` call panics, halting block finalization on all honest nodes — a consensus liveness failure.
- If `totalAmount` is negative, `clAmount` is negative, and `cnAmount = amount - clAmount` exceeds `amount`, crediting the CN address with more KAIA than the total reward.

In all non-panic cases, the `RewardSpec` records incorrect per-address amounts, and `FinalizeState` applies those incorrect balances to the state, permanently misallocating KAIA between the CN reward address and the CL pool address.

---

### Likelihood Explanation

The overflow threshold is **9,223,372,036 KAIA** for a single consolidated validator. The current total KAIA supply is well below this ceiling, making the condition practically unreachable today. However:

- The code contains no guard, assertion, or comment acknowledging this limit.
- The `uint64` type was chosen precisely to accommodate values up to ~18.4 billion KAIA, yet `Split` silently narrows to `int64`, halving the safe range.
- As the chain ages and staking concentrates, the gap narrows.
- The bug class (unsafe narrowing cast in a financial calculation) is a latent correctness defect regardless of current supply.

---

### Recommendation

Replace the narrowing `int64` cast with `new(big.Int).SetUint64(...)`:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }

    var (
        cnAmountBig = new(big.Int).SetUint64(c.StakingAmount)
        clAmountBig = new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )

    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount.Div(clAmount, totalAmount)

    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

This matches the pattern already used correctly everywhere else in the reward module, where `new(big.Int).SetUint64(...)` is the standard idiom for lifting `uint64` staking amounts into arbitrary-precision arithmetic.

### Proof of Concept

```
Given:
  c.StakingAmount           = 10_000_000_000  (10 billion KAIA, > math.MaxInt64 / 1e9)
  c.CLStakingInfo.CLStakingAmount = 5_000_000_000   (5 billion KAIA)
  amount (reward)           = 1_000_000_000_000_000_000 kei (1 KAIA)

Current code:
  cnAmountBig = big.NewInt(int64(10_000_000_000))
             = big.NewInt(-8_446_744_073)   // wraps: 10e9 - 2^63 mod 2^64 → negative
  clAmountBig = big.NewInt(int64(5_000_000_000))
             = big.NewInt(5_000_000_000)    // fits in int64
  totalAmount = -8_446_744_073 + 5_000_000_000 = -3_446_744_073  (negative!)

  clAmount = clAmountBig * amount / totalAmount
           = 5e9 * 1e18 / (-3.4e9)
           = -1_449_275_362_318_840_579 kei  (negative!)

  cnAmount = amount - clAmount
           = 1e18 - (-1.45e18)
           = 2_449_275_362_318_840_579 kei  (> total reward!)

Result: CN address credited with ~2.45 KAIA, CL pool debited ~1.45 KAIA,
        from a total reward of only 1 KAIA — permanent state corruption.
``` [9](#0-8)
