### Title
`PullRequest::OpenedHandler#provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` repositories auto-provision review stacks even when `review_stacks_enabled` is `false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` combines `review_stacks_enabled` with `provisioning_behavior_allow_all?` via `&&`, but ORs that against the `allow_with_label` and `prevent_with_label` clauses without also requiring `review_stacks_enabled`. Consequently, a repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` still auto-creates a `ReviewStack` whenever an attacker labels their own PR with the configured provisioning label, or with `prevent_with_label` whenever the attacker simply omits the label.

### Finding Description
Broken binding: the code's intent is `review_stacks_enabled == true` must gate all provisioning paths, but the actual code at [1](#0-0)  is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts are entirely independent of `review_stacks_enabled`.

Path: `process` calls `respond_to_pull_request_opened?` → `provision?` [2](#0-1) . If `provision?` is true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` builds a `ReviewStack` with `branch: params.pull_request.head.ref` taken directly from the webhook payload [3](#0-2) , then enqueues it via `ReviewStackProvisioningQueue.add(stack)`. `Repository#review_stacks` is a plain `has_many`, not filtered by the enabled flag [4](#0-3) , so nothing downstream re-checks `review_stacks_enabled`.

Attacker request: an unprivileged GitHub user forks the target repo, pushes a branch containing a malicious `shipit.yml`, opens a PR from that branch, and adds the label matching `repository.provisioning_label_name` (public/discoverable via repo settings UI) - or, for `prevent_with_label` repos, simply opens a PR without any label. GitHub then emits a standard `pull_request` "opened" webhook that the attacker does not need to forge (they own the PR).

Existing guards do not stop this: webhook signature verification only proves the payload came from GitHub, not that the repository opted into review stacks; `respond_to_pull_request_opened?` only checks `action == "opened"`; the `ExplicitParameters` schema only validates payload shape; none of these enforce `review_stacks_enabled`. The existing test suite's `allow_with_label` test does not set `review_stacks_enabled: false` (it defaults to `true` via `configure_provisioning_behavior`), so this specific divergence is untested [5](#0-4) .

### Impact Explanation
Once a `ReviewStack` is provisioned for the attacker's fork branch, standard Shipit machinery executes the deploy pipeline (`TaskCommands#perform` reading `shipit.yml` steps and spawning them via `Command#start`/`PTY.spawn`) against attacker-controlled source. This is RCE on the deploy host for any repository whose maintainer configured `provisioning_behavior` to `allow_with_label` or `prevent_with_label` but left (or intended to leave) `review_stacks_enabled` off — a plausible misconfiguration since the two settings are supposed to be independent toggles. It is repeatable per PR/per repository and affects any tenant repo with this specific combination of settings.

### Likelihood Explanation
Requires only: (1) a repository configured with `provisioning_behavior != allow_all` (`allow_with_label` or `prevent_with_label`) while `review_stacks_enabled` is `false`, and (2) attacker capability already assumed (open PR from own fork, label it). No secrets, tokens, or privileged roles are needed. This is a real logic bug reachable by any GitHub user able to open PRs against the target repo (public repos or repos where attacker is a collaborator).

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled? &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to any sibling handlers with the identical pattern (`labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`) if they replicate this logic.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1, confirming `repository.review_stacks_enabled == false` did not prevent stack creation, matching the vulnerable binding described.
