Based on my investigation, I found a concrete analog within the allowed scope: paired-device/wallet message handling that decrypts and deserializes attacker-controlled data before any size limit is enforced.

### Title
Unbounded Memory Allocation in Device Message Decryption Before Size Validation - (File: device.js)

### Summary
`device.js`'s handler for incoming hub messages (`handleJustsaying`, subject `hub/message`) and `network.js`'s `hub/deliver` handler validate only structural properties of an incoming `objDeviceMessage` (presence of fields, signature correctness, nesting depth/node count) but never bound the byte length of `encrypted_package.encrypted_message`, `iv`, or `authtag` before they are base64-decoded and fed into AES-GCM decryption and subsequent `JSON.parse`. An attacker who is (or claims to be, via the whitelisted `pairing` subject) a correspondent device can craft a single, non-nested device message with an arbitrarily large `encrypted_message` string and force the receiving wallet/hub to allocate memory proportional to the attacker-chosen size, with no upper bound enforced in the message-handling path itself.

### Finding Description
In `device.js`, the `hub/message` handler checks only for the presence of required fields and verifies the message hash/signature [1](#0-0) , but does not check the length of `objDeviceMessage.encrypted_package.encrypted_message` (or `iv`/`authtag`) anywhere before proceeding to decryption: [2](#0-1) 

`decryptPackage()` then unconditionally does:
```
var enc_buf = Buffer.from(objEncryptedPackage.encrypted_message, "base64");
```
and loops over `enc_buf` in 4096-byte chunks feeding an AES-GCM decipher, before parsing the decrypted plaintext with `JSON.parse`: [3](#0-2) 

None of these steps enforce any maximum size for `encrypted_message` prior to allocating `enc_buf` and the chunk buffers, or prior to the `JSON.parse` of the decrypted content.

The same unbounded field is reachable through the hub-side `hub/deliver` request handler in `network.js`. It checks for required fields and calls `isTooDeeplyNestedOrHasTooManyNodes(objDeviceMessage, 5, 100)`, which limits nesting depth and node *count*, not the length of any individual string value: [4](#0-3) 

The message is then persisted to `device_messages` (`LONGTEXT` column, effectively unbounded) and immediately re-broadcast in memory to the connected recipient if online: [5](#0-4) 

The only place a message-length ceiling exists (`ws.max_message_length`) is optional, hub-operator/client-negotiated, and used only to prune already-stored messages when serving the backlog (`sendStoredDeviceMessages` / `deleteOverlengthMessagesIfLimitIsSet`) — it is not enforced at ingestion time in `hub/deliver`, nor at all in the direct `hub/message` justsaying path used when a node is its own hub: [6](#0-5) 

This mirrors the Salvo advisory's root cause: a size-bearing payload (there: HTTP form body; here: `encrypted_message`) is read fully into memory / passed to a decode-and-parse pipeline (base64 decode → AES-GCM decrypt in chunks → `JSON.parse`) before any size cap is applied, and the only checks performed (field presence, signature, nesting depth/count) do not bound the byte size of the attacker-supplied string.

### Impact Explanation
A correspondent device (or any device whose `pairing` message is accepted, since `pairing` is explicitly whitelisted for non-correspondents) can send a single flat device message with a multi-hundred-megabyte or gigabyte `encrypted_message` field. On the receiving side (wallet acting as its own hub, or the wallet retrieving from its hub), this forces:
1. A base64 decode allocating a buffer proportional to input size.
2. Chunked but still full-size cumulative decryption via `Buffer.concat`.
3. `JSON.parse` of a large plaintext.

This can exhaust process memory and crash the wallet/light client process, denying it the ability to process legitimate payments, AA triggers it needs to track, or private-payment chains delivered via device messages — a concrete node/wallet availability impact directly analogous to the reported Salvo DoS.

### Likelihood Explanation
Reaching this path requires only being a paired correspondent (routine for any two wallets that have exchanged pairing codes) or using the `pairing` subject which is explicitly allowed from unknown, non-correspondent devices. No special privilege, network position, or protocol violation is needed — a single crafted `hub/message`/`hub/deliver` payload triggers the issue. Likelihood is high given the low bar to becoming a "correspondent" for this purpose.

### Recommendation
Enforce a strict maximum length (e.g., a small multiple of the realistic max plaintext size, such as tens of KB) on `objDeviceMessage.encrypted_package.encrypted_message` (and `iv`, `authtag`) immediately upon receipt in both `device.js`'s `hub/message` handler and `network.js`'s `hub/deliver` handler, before any base64 decoding, decryption, or persistence occurs — mirroring the size checks already applied to other unit/message payload types (e.g., `MAX_AA_STRING_LENGTH`, `MAX_UNIT_LENGTH` patterns in `constants.js`). Additionally, enforce `max_message_length`-style limits at ingestion time in `hub/deliver`, not only when pruning stored backlog.

### Proof of Concept
1. As device A, establish or spoof a pairing/correspondent relationship with victim device B (or send a `pairing`-subject message, which bypasses the correspondent check).
2. Construct `objDeviceMessage = { to: B, pubkey: A_pub, encrypted_package: { dh: {...valid ephemeral pubkeys...}, iv, authtag, encrypted_message: <base64 string of several hundred MB of random bytes> } }`.
3. Sign the message with A's permanent key so `ecdsaSig.verify` passes.
4. Send via `hub/deliver` (to a hub) or directly as `hub/message` justsaying if B is its own hub.
5. Observe B's process memory grow unbounded during `Buffer.from(..., 'base64')` / AES-GCM chunked decryption in `decryptPackage`, leading to OOM/crash — with no code path having rejected the message based on its size beforehand.

function sendStoredDeviceMessages(ws, device_address){

		var max_message_count = ws.max_message_count ? ws.max_message_count : 100;

			sendJustsaying(ws, 'hub/message_box_status', (rows.length === max_message_count) ? 'has_more' : 'empty');
		});
	});
