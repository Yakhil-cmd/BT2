### Title
Cosigner-supplied `shared_address`/`unit` fields are trusted verbatim in `arbiter_contract.store()` without any filter, letting a paired device redirect an arbiter contract to an attacker-controlled address - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.store()` copies the `shared_address` and `unit` fields straight out of an incoming, cosigner-supplied device message into the local `wallet_arbiter_contracts` row whenever `bFromCosigner` is true, with no validation that these values are legitimate for the contract. This mirrors the Camel-Knative flaw: a structured payload (`arbiter_contract_shared` body) is read and its fields are merged into an internal, trusted record without passing through the same validation ("filter") applied to the contract's other fields, and the resulting record later drives fund-moving/contract-completion logic.

### Finding Description
In `wallet.js`, the `arbiter_contract_shared` message handler validates only a subset of the contract fields (`title`, `text`, `creation_date`, `arbiter_address`, `me_is_payer`, `peer_pairing_code`, `amount`, addresses, hash), then calls `arbiter_contract.store(body, true)`: [1](#0-0) 

`store()` explicitly says contracts shared by cosigners are "trusted to reflect their true status," and when `bFromCosigner` is set it additionally injects `objContract.shared_address` and `objContract.unit` into the INSERT statement, taken directly from the attacker-controlled `body`/`objContract` object with no format or ownership check: [2](#0-1) 

Unlike the fields that are explicitly validated in the `arbiter_contract_shared`/`arbiter_contract_offer` handlers (address format, hash matching, date format, etc.), `shared_address` and `unit` are never checked before being persisted here. This is structurally identical to the Camel-Knative bug: the "binary" path (offer/update flows) filters/validates fields going into contract state via `setField()`'s explicit allow-list, while the "structured" path (`store()` from a cosigner) blanket-copies extra fields (`shared_address`, `unit`) straight from the untrusted payload into the same internal record without the equivalent filter.

Once `shared_address` is set on the contract row, it becomes the address other logic (`openDispute`, `appeal`, and payment/completion flows that reference `objContract.shared_address`/`objContract.unit`) treats as the multi-sig contract address holding/receiving funds for that arbiter contract. A malicious cosigner (a device already paired for a shared address, i.e., a "paired device" per the analog rules) can send an `arbiter_contract_shared` message with a `shared_address` value pointing to an address they control, or a `unit` value pointing to an unrelated unit, causing the local wallet to associate the contract's actual multisig/fund-holding address with an address chosen by the attacker.

### Impact Explanation
Because `shared_address` subsequently gates dispute/appeal API calls and is treated as the trusted multisig contract address for a specific arbiter contract, an attacker-controlled `shared_address` can misdirect subsequent flows that key off `objContract.shared_address` (e.g., dispute/appeal requests reference `objContract.arbiter_address`/`shared_address` context, and later signing/payment logic keys off `objContract.unit`/`shared_address` to determine the contract's on-chain state). This can cause fund loss or the victim's wallet trusting the wrong on-chain state for a contract, which is the same class of "internal-state confusion via unfiltered field injection" as the Camel-Knative CVE, reachable by a private-payment/paired-device counterparty (a "paired device" actor per the allowed threat model).

### Likelihood Explanation
This requires an already-paired cosigner device (a peer participant able to send `arbiter_contract_shared`/`arbiter_contract_update` messages), which is squarely inside the "paired device" actor scope. The attack requires no privileged access beyond being a legitimate contract cosigner, and the vulnerable code path (`store()` with `bFromCosigner=true`) is reached directly from the message handler with no additional validation, making exploitation straightforward for any malicious or compromised cosigner device.

### Recommendation
Validate `shared_address` (must be a syntactically valid address, and ideally re-derived/verified against the contract's known definition/signers) and `unit` (must reference a real unit that is provably tied to this contract, e.g., verified via `handleReceivedSigningUnit`/`handleReceivedSharedAddress` semantics) before persisting them in `store()`, mirroring the stricter checks already used in the `arbiter_contract_update`/`prosaic_contract_update` handlers for the `unit` and `shared_address` fields (status checks, `ValidationUtils.isValidAddress`, `ValidationUtils.isValidBase64` hash checks, and "already set" checks). Apply the same allow-list/validation discipline used in `setField()` to the fields accepted in `store()` from cosigners.

### Proof of Concept
1. Attacker device is a legitimate cosigner correspondent of the victim's wallet for some arbiter contract `hash`.
2. Attacker sends a `arbiter_contract_shared` device message reusing a legitimately-signed `title`/`text`/`creation_date`/`arbiter_address`/`amount`/hash (so `getHash()` validation in `wallet.js` passes) but with `shared_address` set to an address the attacker controls, and/or `unit` set to an arbitrary unit hash.
3. `wallet.js`'s `arbiter_contract_shared` handler does not check `shared_address`/`unit`, and calls `arbiter_contract.store(body, true)`.
4. `store()` at [3](#0-2)  inserts the attacker-chosen `shared_address` and `unit` into `wallet_arbiter_contracts`, and subsequent local logic that reads `objContract.shared_address`/`objContract.unit` operates on attacker-controlled values.

Note: I was not able to fully trace every downstream consumer of `objContract.shared_address`/`unit` (e.g., the exact `pay()`/`complete()` implementations) within the available index; a full Devin session with complete file access would be needed to confirm the exact fund-movement path and quantify the maximum impact precisely.

function store(objContract, bFromCosigner, cb) { // contracts shared by cosigners are trusted to reflect their true status
	const me_is_cosigner = bFromCosigner ? 1 : 0;
	const status = bFromCosigner ? (objContract.status || status_PENDING) : status_PENDING;
	var fields = "(hash, peer_address, peer_device_address, my_address, arbiter_address, me_is_payer, my_party_name, peer_party_name, amount, asset, is_incoming, creation_date, ttl, status, title, text, peer_pairing_code, peer_contact_info, my_pairing_code, my_contact_info, me_is_cosigner";
	var placeholders = "(?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?";
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, objContract.arbiter_address, objContract.me_is_payer ? 1 : 0, objContract.my_party_name, objContract.peer_party_name, objContract.amount, objContract.asset, 1, objContract.creation_date, objContract.ttl, status, objContract.title, objContract.text, objContract.peer_pairing_code, objContract.peer_contact_info, objContract.my_pairing_code, objContract.my_contact_info, me_is_cosigner];
	if (bFromCosigner) {
		if (objContract.shared_address) {
			fields += ", shared_address";
			placeholders += ", ?";
			values.push(objContract.shared_address);
		}
		if (objContract.unit) {
			fields += ", unit";
			placeholders += ", ?";
			values.push(objContract.unit);
		}
	}
	fields += ")";
	placeholders += ")";
	db.query("INSERT "+db.getIgnore()+" INTO wallet_arbiter_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb) {
			cb(res);
		}
	});
}
