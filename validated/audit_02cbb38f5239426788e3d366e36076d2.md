### Title
Hook Bypass via Fail-Open PreToolUse Error/Timeout Handling - (File: plugins/hookify/hooks/pretooluse.py)

### Summary

### Finding Description
The Taiko `Bridge.processMessage()` bug rewards the caller even when the guarded sub-operation (`_invokeMessageCall()`/`excessivelySafeCall()`) fails — an attacker can force that sub-call to fail (via the EIP-150 63/64-gas trick) while the outer function still completes "successfully" and pays out. The structural flaw is: *a security-critical sub-check can be forced to fail by an attacker-influenced resource constraint, and the surrounding logic treats that failure as if the check had passed (or simply ignores it), producing the privileged/rewarded outcome anyway.*

The `hookify` plugin's `PreToolUse` hook, `plugins/hookify/hooks/pretooluse.py`, implements the equivalent pattern for Claude Code's tool-approval trust boundary. This script is the enforcement point that is supposed to approve/deny tool calls (`Bash`, `Edit`, `Write`, `MultiEdit`) based on user-defined rules loaded by `load_rules()` and evaluated by `RuleEngine.evaluate_rules()` [1](#0-0) . Critically, any exception during rule loading or evaluation is caught and converted into an **allow** decision:

```
except Exception as e:
    # On any error, allow the operation and log
    error_output = {"systemMessage": f"Hookify error: {str(e)}"}
    print(json.dumps(error_output), file=sys.stdout)
finally:
    # ALWAYS exit 0 - never block operations due to hook errors
    sys.exit(0)
``` [2](#0-1) 

Independent of this internal catch-all, Claude Code's own hook contract reinforces the fail-open behavior at the framework level: hook exit code `2` is the only blocking signal; any other non-zero exit (e.g., a `timeout`-killed process, exit `124`) is classified as a "non-blocking error," and the tool call proceeds [3](#0-2) . The plugin's own `hooks.json` sets only a 10-second `timeout` on the `PreToolUse` hook [4](#0-3) , and the rule engine compiles attacker/config-influenced regex patterns via `re.compile(pattern, re.IGNORECASE)` for every `Condition` match against `tool_input` fields [5](#0-4) . A pathological regex (ReDoS) or any unexpected input shape that raises inside `_rule_matches`/`load_rules` therefore forces the sub-check ("does this Bash/Write/Edit call violate a blocking rule?") to fail — via either an uncaught exception (caught by the outer `except Exception`, exit 0) or a hang past the 10s timeout (killed, non-zero/non-2 exit, still treated as non-blocking by the harness) — and in both cases the tool call that should have been denied is **approved instead of denied**, exactly mirroring the Bridge pattern where a forced sub-call failure still yields the "success" payout.

### Impact Explanation
Any workflow relying on `hookify`'s `PreToolUse` rules to block dangerous `Bash`/`Write`/`Edit`/`MultiEdit` operations (e.g., blocking `rm -rf`, credential-file writes, path traversal) can be silently bypassed: an unprivileged actor who controls the tool input (e.g., a crafted file path, command string, or write content that triggers a regex-engine exception/hang, or any other exception in `evaluate_rules`/`load_rules`) causes the guard to fail open, letting an otherwise-blocked destructive or exfiltration-oriented tool call execute. This is a genuine trust-boundary/hook-bypass issue (unprivileged-user analog to a PreToolUse permission gate), not a mocked or peer/operator-only scenario.

### Likelihood Explanation
The fail-open `except Exception: ... exit(0)` is unconditional and by design ("ALWAYS exit 0 — never block operations due to hook errors"), so any bug, malformed rule file, or crafted input that raises inside rule loading/evaluation reliably bypasses blocking. Triggering the timeout path additionally requires an input that makes regex evaluation (or config loading) run past 10 seconds — plausible via ReDoS-style patterns in user-controlled tool inputs matched by `compile_regex`, though I was not able to fully inspect `config_loader.py`'s `Condition`/pattern-application logic in this session (tool access ended before I could open that file), so the exact regex construction and matched fields are not fully confirmed.

### Recommendation
- Change the exception handler in `plugins/hookify/hooks/pretooluse.py` to fail closed (deny or `ask`) for exceptions raised while evaluating rules that are configured as `block`, or at minimum surface a clear "hook failed — action not evaluated" warning that pauses the action rather than silently allowing it.
- Apply a regex execution timeout/length cap (or switch to a non-backtracking regex engine) in `compile_regex`/`_rule_matches` so a single pathological pattern cannot hang the whole hook.
- Treat hook timeout/non-zero-exit outcomes for hooks that exist specifically to block operations as "ask" rather than "allow" by default, since a silent timeout is indistinguishable from an attacker deliberately forcing resource exhaustion to evade the check.

### Proof of Concept
Conceptual PoC (not fully verified against `config_loader.py`, which I could not load in this session):
1. Install `hookify` with a blocking rule intended to deny dangerous `Bash` commands (e.g., matching `rm -rf`).
2. As the agent/attacker-controlled input, craft a `tool_input.command` string designed to cause catastrophic backtracking against the rule's regex (or any other input causing `RuleEngine.evaluate_rules`/`load_rules` to raise, e.g., malformed encoding, unexpected types) so that:
   - Rule evaluation raises an exception → caught by `except Exception` → `sys.exit(0)` → command is allowed [2](#0-1) , or
   - Rule evaluation exceeds the 10s `timeout` configured in `hooks.json` [6](#0-5) , causing the hook process to be killed; per the documented hook contract this is a non-blocking error and the tool call still proceeds [3](#0-2) .
3. The intended-to-be-blocked `Bash` command executes despite matching a `block` rule, confirming the fail-open bypass.

Note: I was unable to open `plugins/hookify/core/config_loader.py` before the session ended, so I cannot confirm the exact `Condition`/pattern fields an attacker would target to trigger the exception or ReDoS path; this should be verified directly against that file before treating the PoC as complete.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```

def compile_regex(pattern: str) -> re.Pattern:
    """Compile regex pattern with caching.

    Args:
        pattern: Regex pattern string

    Returns:
        Compiled regex pattern
    """
    return re.compile(pattern, re.IGNORECASE)
