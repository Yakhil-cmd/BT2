### Title
Webhook signature verification binds trust to `repository.owner.login`, but handlers act on the independent `repository.full_name` field, allowing cross-tenant repository/stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (one where `secrets.github` is keyed by organization, see `Shipit.github_app_config`), the webhook signature check authenticates the payload against the secret of the organization named in `repository.owner.login`, while every webhook `Handler` resolves the actual `Repository`/`Stack` to act on from the independent `repository.full_name` field. Because these two JSON fields are never cross-validated, an attacker who legitimately controls one tenant's GitHub App/webhook secret can forge a payload that is validly signed for their own organization but names a *different* organization's repository as the target, causing Shipit to perform stack/commit writes for a repository the attacker does not own.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret to check against using attacker-supplied JSON, not a fixed/authenticated source: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` looks up that organization's app config/secret via `github_app_config`: [3](#0-2) 

Once the signature is verified against *that* organization's secret, the raw payload is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`). Every handler determines which `Repository`/`Stack` records to mutate from a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of the repository resolved via `repository_name` (i.e. `full_name`), for the branch derived from `ref`: [5](#0-4) 

`CheckSuiteHandler` similarly acts on `stacks` (resolved from `full_name`) filtered only by `head_branch`/`head_sha`, both attacker-controlled: [6](#0-5) 

Because the raw HTTP body is a single JSON document entirely crafted by the attacker (they choose every field before signing it with the secret they legitimately hold for their own organization), nothing prevents `repository.owner.login` = "attacker-org" (used only to pick the verification secret) from diverging from `repository.full_name` = "victim-org/victim-repo" (used to pick the actual `Repository`/`Stack` acted upon). This breaks the intended binding: `organization authenticated == repository written`. The controller/handler pipeline instead enforces only `organization authenticated == organization named in one payload field`, while trusting a second, unrelated field for the actual write target.

### Impact Explanation
An attacker who is a legitimate administrator of *any* one GitHub organization/App configured in a shared, multi-tenant Shipit instance (i.e., they possess/know their own org's `webhook_secret`) can produce validly-signed webhook deliveries that cause Shipit to perform writes against a completely different organization's repositories and stacks that they have no relationship with:
- `push` events can force `Stack#sync_github` to run for another tenant's stack on an attacker-chosen branch/`expected_head_sha`, generating commit records and (depending on stack configuration such as `continuous_deployment`) downstream deploy scheduling for a repository the attacker does not control.
- `check_suite` events can force `schedule_refresh_check_runs!` on another tenant's commits.
- Team/user records can be manipulated cross-tenant via the `membership` handler using the same repository/owner field confusion pattern.

This is a cross-repository write triggered without authorization from the actual target repository's organization, satisfying the "cross-repository writes" Critical impact bar; depending on stack settings it can also lead to an unauthorized deploy trigger for another tenant.

### Likelihood Explanation
This requires the deployment to use the multi-organization `secrets.github` schema (keyed by org, per `Shipit.github_app_config`) hosting more than one tenant/repository owner behind the same Shipit instance — a supported and documented configuration. Any party who is a legitimate webhook-secret holder for one configured organization can exploit this without any Shipit credentials, without repository write access to the victim repo, and without a Shipit session or API token — matching the "unprivileged attacker" threat model required by scope.

### Recommendation
Bind the signature-verification organization to the same identity used to resolve the acted-upon repository. Concretely, `WebhooksController` should derive the organization strictly from `repository.full_name`'s owner segment (the same field `Handler#repository_name` uses), or better, look up the `Repository`/`Stack` first and verify the signature using the secret configured for that repository's known organization, rejecting the request if `repository.owner.login` and the owner segment of `repository.full_name` disagree.

### Proof of Concept
1. Deploy Shipit with a multi-org `secrets.github` config containing at least `org-a` (attacker-controlled GitHub App/webhook secret) and `org-b` (victim, e.g. hosting a stack for `org-b/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over this exact raw body (per `GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`).
4. POST to `/github/webhooks` with `X-Github-Event: push`. `WebhooksController#repository_owner` reads `"org-a"`, `Shipit.github(organization: "org-a")` succeeds and verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`), returning 200.
5. `PushHandler#process` resolves the target via `repository.full_name` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-23`) and calls `sync_github(expected_head_sha: params.after)` on `org-b`'s stacks — a write triggered against a repository the attacker never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
