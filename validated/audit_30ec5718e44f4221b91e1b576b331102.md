### Title
Cross-repository `schedule_merges`/hook trigger via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `sha` with no repository binding, so a genuinely signed `status` webhook for one Shipit-tracked repository will also update and fire hooks/`schedule_merges` for any other, unrelated stack that happens to have a `Commit` row with the same sha. Because `sha` is only unique per `(stack_id, sha)` and not globally, this is trivially triggerable whenever two tracked repositories share commit history (forks, templates, cherry-picks, shared bootstrap commits) — no hash collision engineering is required.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row that a `status` webhook is allowed to mutate. The actual code enforces no such binding: [1](#0-0) 

`process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it iterates every `Commit` row in the entire database matching that sha, with zero reference to `payload['repository']`. The base `Handler` class does compute a `repository_name`/`stacks` scoped helper [2](#0-1)  but `StatusHandler` never uses it.

`create_status_from_github!` → `add_status` then unconditionally fires `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` for whichever `commit.stack` owns that row: [3](#0-2) .

The DB schema only enforces sha uniqueness scoped to `stack_id` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same sha value is expected/allowed to exist across multiple unrelated stacks — e.g. any two repos bootstrapped from the same template will share an initial commit's sha (same tree, author, committer, message, timestamps → identical sha, no brute-force collision needed).

`verify_signature` in `WebhooksController` only checks that the payload's `X-Hub-Signature` matches the webhook secret configured for `repository_owner` (the org named in the payload itself): [4](#0-3) . This guard is legitimately satisfiable by the attacker: they only need a repository that Shipit already tracks as *some* stack (e.g. their own fork/org that was templated from, or itself, a tracked upstream project) and let real GitHub CI on that repo emit a real, correctly-signed `status` event for a commit sha that is shared with the unrelated victim stack. Signature verification authenticates "this event genuinely came from GitHub for org X" — it says nothing about which `Commit`/`Stack` rows the payload's sha is allowed to touch. `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not which stack it may affect.

Exploit flow:
1. Victim stack A tracks `victim-org/victim-repo`, seeded (e.g. via a company bootstrap template) with an initial commit `C` (identical tree/author/committer/message/timestamp across all templated repos) recorded as a `Commit` row with `sha == S`.
2. Attacker creates/owns `attacker-org/attacker-repo`, also bootstrapped from the same template, also tracked by Shipit as stack B, and also has a `Commit` row with the same `sha == S` (first-parent ancestor, not necessarily HEAD).
3. Attacker pushes a commit to their own repo/CI that causes GitHub to send a `status` webhook for `sha S` (this is a completely legitimate, correctly-signed webhook for stack B's org).
4. `StatusHandler#process` executes `Commit.where(sha: S)`, which returns **both** stack A's and stack B's `Commit` rows.
5. `create_status_from_github!` is invoked on stack A's row too, causing `add_status` to fire `Hook.emit(:commit_status/:deployable_status, stack: A, ...)` and `stack.schedule_merges` for **stack A**, the victim, despite the webhook never mentioning `victim-org/victim-repo`.

### Impact Explanation
An attacker who controls a repository that Shipit merely tracks as *any* stack can cause deploy-pipeline side effects (`schedule_merges`, `commit_status`/`deployable_status` hook emissions, and downstream automatic merges/deploys gated on commit status) on a completely unrelated victim stack, without ever authenticating against that victim's repository. This is a payload for one repository mutating another's stack/commit state — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The blast radius spans every stack pair that shares any commit sha (templated repos, forked repos, shared vendored commits), which in practice is common in organizations using bootstrap templates, and is repeatable on demand by the attacker simply re-pushing/re-running CI on their own tracked repo.

### Likelihood Explanation
Preconditions: (a) the attacker's own repository must be tracked by Shipit as a stack (a normal, non-privileged situation for org-wide Shipit deployments, review-stack/PR-based provisioning, or open templates), and (b) a victim stack must have a `Commit` row sharing a sha with the attacker's repo — realistic for any templated/forked codebase with identical bootstrap commits (identical tree + author + committer + timestamps produce identical git sha deterministically, no brute force needed). No secrets, sessions, or elevated GitHub permissions are required; the attacker only needs push/CI access to their own already-tracked repository. This is highly feasible and fully repeatable.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` by the repository that actually sent the webhook, e.g. restrict to commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')` (using the `stacks`/`repository_name` helper already present in `Handler`), rather than a bare global `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook for shared sha does not affect unrelated stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack(repository: create_repository(owner: 'attacker-org', name: 'attacker-repo'))

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' },
  }

  assert_no_enqueued_jobs only: ProcessMergeRequestsJob do
    # or: expect_no_hook(:deployable_status, stack: victim_stack) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute_equal 'success', victim_commit.reload.state,
    "victim stack's commit must not be updated by attacker repo's webhook"
end
```
This asserts the equality `commit.stack.repository.full_name == payload['repository']['full_name']` holds for every `Commit` mutated by `StatusHandler#process`; with current code this test fails because `victim_commit` is updated and `stack.schedule_merges`/hooks fire for `victim_stack`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
