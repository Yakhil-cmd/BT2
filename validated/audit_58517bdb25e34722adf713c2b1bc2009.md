### Title
AA logic using the `timestamp` builtin relies on unit-composer-controlled MC timestamp, allowing limited manipulation of time-gated financial logic - (File: aa_composer.js, validation.js)

### Summary
Autonomous Agents (AAs) can use the `timestamp` builtin in oscript to gate payments, price schedules, expiries, and milestone releases (e.g. ICO deadlines, blackswan/maturity checks, Dutch-auction-style decaying conditions). This value is not derived from an immutable, externally-verifiable clock — it is taken from the timestamp field of the last stable main-chain (MC) unit, a field that whoever composes that unit is free to set (bounded only by a small future-tolerance window), analogous to a miner setting `block.timestamp` in the reported EVM issue.

### Finding Description
When a trigger unit is processed, the AA composer builds the trigger context using the timestamp of the last (stable) MC unit rather than any tamper-evident consensus clock: [1](#0-0) 

For live/production trigger handling the same `objMcUnit` (with its `timestamp` field) is fed into `handleTrigger`, and this is the value bound to the `timestamp` keyword when AA oscript formulas are evaluated (confirmed by tests exercising the `timestamp` getter, which return `objLastStableMcUnitProps.timestamp`): [2](#0-1) 

The only consensus-level constraint on a unit's `timestamp` field is that it must be a positive integer and not more than a few seconds (`conf.max_seconds_into_the_future_to_accept`, default 5) ahead of the validating node's own clock — there is no check tying it to a strictly increasing sequence relative to previously stabilized MC units, nor any tighter bound preventing an author from setting it earlier than "true" time: [3](#0-2) 

The unit's timestamp is set by whoever composes it (`Math.round(Date.now() / 1000)` at compose time, or a caller-supplied value for light clients), i.e. by the unit's author/poster, not by any protocol-enforced oracle: [4](#0-3) 

AA authors are explicitly encouraged to use `timestamp` for time-boundary financial logic, as shown in the shipped sample templates that ship with ocore and are commonly copied as starting points for real AAs — e.g. deadline/expiry checks (`timestamp > $expiry_ts`) and maturity/blackswan gates (`timestamp < 1556668800`) that change payout logic and asset issuance/exchange rate rules depending on which side of the timestamp boundary the trigger lands on: [5](#0-4) [6](#0-5) 

Because the effective "current time" seen by the AA is the timestamp of whichever unit happens to be the last stable MC unit at the moment the trigger is processed, and that timestamp is chosen by an ordinary unit composer within a several-second tolerance window (and with no enforced monotonic/real-time linkage beyond that), a party racing to get their own unit onto the MC at the right moment can bias the effective `timestamp` seen by dependent AA logic near a boundary — mirroring the miner-manipulable `block.timestamp` pattern in the referenced report.

### Impact Explanation
Any AA that uses `timestamp` to gate a decision with financial consequences (expiry-triggered fund releases, price/rate boundaries, blackswan/maturity switches as in the sample templates) can have its outcome nudged across a boundary by an actor who controls the timestamp of the unit that becomes the qualifying last-stable-MC-unit for the trigger's processing. This can let a party claim a more favorable branch (e.g. avoid a "wait for maturity date" bounce, or trigger a milestone/expiry-based fund release slightly early/late), causing fund loss or unintended fund release for the AA and its counterparties.

### Likelihood Explanation
Likelihood is limited by the narrow manipulation window (a few seconds, bounded by `max_seconds_into_the_future_to_accept`) and by the fact that the attacker does not fully control which unit becomes the last stable MC unit at trigger-processing time — this depends on DAG/MC selection, not solely on the attacker's unit. Exploitation therefore requires the target boundary to fall within this narrow window and some favorable timing/network conditions, making this a lower-frequency but still real timing-manipulation vector for boundary-sensitive AA logic.

### Recommendation
- Avoid using wall-clock-like `timestamp` for security- or fund-critical boundary conditions in AA logic; prefer `mci` (main chain index), which increases deterministically and is not subject to the same few-second author-chosen slack, for ordering-sensitive decisions.
- Where real-world time is required, document that `timestamp` carries the same tolerance/manipulation caveats as `block.timestamp` on EVM chains, and encourage AA authors to build in a safety margin (e.g. checking `timestamp` against a threshold with a buffer larger than `max_seconds_into_the_future_to_accept`) rather than exact-boundary comparisons.
- Consider tightening validation to also reject timestamps that regress unreasonably relative to the previous MC unit's timestamp, reducing composer discretion.

### Proof of Concept
1. Deploy/observe an AA using a time-boundary condition analogous to the sample templates, e.g. `{ trigger.data.finish AND (trigger.address == $control_address OR timestamp > $expiry_ts) }` (`test/samples/ico_with_milestones.oscript:1964`) or `{ timestamp < 1556668800 ... }` (`test/samples/futures_contract.oscript:60,86`).
2. Near the boundary timestamp, compose and post a unit (payment or otherwise) with `timestamp` set to `Date.now()/1000` up to `+max_seconds_into_the_future_to_accept` seconds (`composer.js:360`, `validation.js:283-286`), attempting to get it selected as/near the last stable MC unit right as the trigger's context is built (`aa_composer.js:163-165`).
3. If successful, the AA's `timestamp` builtin evaluates using this attacker-influenced value, flipping the boundary condition (e.g., allowing/blocking milestone release, expiry finish, or exchange-rate branch) in the attacker's favor.
