### Title
Webhook `membership` events let any onboarded GitHub organization inject members into another organization's trusted `Team` record, bypassing `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
Shipit supports hosting multiple GitHub organizations from one instance, each with its own webhook secret [1](#0-0) . The webhook signature check correctly binds a payload to the organization named inside the payload itself [2](#0-1) , but the `membership` event handler looks up/creates the `Team` record purely by the GitHub-global `team.id`, never re-checking that the `organization` in the (verified) payload matches the `Team`'s stored `organization`. This lets an org that is legitimately onboarded to a shared Shipit instance impersonate GitHub's `membership` event for a *different*, more trusted organization's team, and add an arbitrary user to it, granting that user Shipit-wide authorization via `Shipit.github_teams`.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to verify the HMAC with, based on the organization named in the payload: [3](#0-2) 

For `membership` events, there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` [4](#0-3) . This is exactly the organization that owns the webhook secret used to sign the request, so signature verification is internally consistent — but it only proves "this payload was signed by *some* configured organization", not that the `team.id` inside the payload belongs to that same organization.

The `MembershipHandler` then does: [5](#0-4) 

`find_or_create_team!` looks the `Team` up (and, if missing, creates it) using only `github_id: params.team.id` — a GitHub-global numeric ID that says nothing about which organization sent the webhook. If a `Team` row already exists with that `github_id` (e.g. it was created earlier by the trusted org's own real GitHub membership events, or seeded via `Team.find_or_create_by_handle` from `Shipit.github_teams` [6](#0-5) ), the existing row is reused and its `organization` column is left untouched — it is never re-validated against `params.organization.login`.

`Team#add_member` then unconditionally appends the attacker-claimed member: [7](#0-6) 

Because `User.find_or_create_by_login!` resolves users globally (not scoped to any organization) [8](#0-7) , and `User#authorized?` only checks whether the user belongs to any `Team` matching `Shipit.github_teams` by row `id` (not by re-verifying organization) [9](#0-8) , adding a `Membership` row is sufficient to make an arbitrary user "authorized" for the whole Shipit instance: [10](#0-9) 

**Binding broken:** the organization that authenticated the webhook (verified via HMAC with that organization's own `webhook_secret`) is not equal to the organization actually authorized to mutate the `Team`/`Membership` rows that back `Shipit.github_teams`.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization, explicitly listed as a High-impact category. Any organization admin who legitimately installed the Shipit GitHub App for their own (lower-trust) organization in a multi-org Shipit deployment can grant any GitHub account (including their own) full access to the whole Shipit instance — all stacks, all organizations, deploys, rollbacks, merges — by forging a single `membership` webhook that only their own org's secret needs to sign.

### Likelihood Explanation
Requires:
1. A multi-org Shipit deployment (a documented, supported configuration [1](#0-0) ) where the attacker administers one of the onboarded, lower-trust organizations (and thus legitimately knows that organization's `webhook_secret`).
2. Knowledge of the target `Team`'s numeric GitHub `github_id` — a small sequential integer that is not treated as a secret by GitHub and is easy to obtain or guess for teams the attacker can see any information about.

No GitHub App private key, `ApiClient` token, or `webhook_secret` of the victim organization is required — only the attacker's own, already-known secret for their own onboarded org.

### Recommendation
- Scope the `Team` lookup by both `github_id` and `organization`, and verify that `params.organization.login` matches the `Team`'s `organization` before creating/reusing the record and before calling `add_member`/`members.delete`.
- Additionally, verify that the webhook's authenticating organization (`repository_owner`/`Shipit.github(organization:)`) matches `params.organization.login` used inside the handler, so a payload from org A can never mutate rows scoped to org B.
- Consider hard-scoping `Shipit.github_teams` membership checks to also require the `Team#organization` to be present in the configured `github_organizations` list matching the webhook that created/updated it.

### Proof of Concept
1. Deploy Shipit configured with two organizations: `trusted-org` (has `Shipit.github_teams` set to `trusted-org/admins`) and `attacker-org`, both with the GitHub App installed and their own `webhook_secret` known to their respective admins [1](#0-0) .
2. The `Team` row for `trusted-org/admins` already exists in Shipit's DB with `github_id = 555` (its real GitHub team ID), created either via `Shipit.github_teams` bootstrap or a legitimate prior membership sync [11](#0-10) .
3. Attacker, who administers `attacker-org` and knows `attacker-org`'s `webhook_secret`, sends a `membership` webhook to `/webhooks`:
   ```json
   {
     "action": "added",
     "team": { "id": 555, "name": "admins", "slug": "admins", "url": "https://api.github.com/..." },
     "organization": { "login": "attacker-org" },
     "member": { "login": "attacker-github-user" }
   }
   ```
   signed with HMAC-SHA1 using `attacker-org`'s real `webhook_secret`.
4. `WebhooksController#verify_signature` verifies successfully against `attacker-org`'s app/secret [12](#0-11) .
5. `MembershipHandler#find_or_create_team!` finds the existing `Team(github_id: 555)` (which is really `trusted-org/admins`) and `team.add_member(User.find_or_create_by_login!("attacker-github-user"))` [5](#0-4) .
6. `attacker-github-user` is now a member of the `Team` backing `Shipit.github_teams`; logging into Shipit as that user passes `current_user.authorized?` and grants full instance access [9](#0-8) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
