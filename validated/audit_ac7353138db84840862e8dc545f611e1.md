### Title
Cross-organization webhook forgery escalates into `Shipit.github_teams` authorization and cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook against using an *attacker-controlled JSON field* (`repository.owner.login`, falling back to `organization.login`), while the actual handlers that mutate state (team membership, stack/repository lookups) trust *other, independent* fields of the same unauthenticated JSON body (`organization.login`, `repository.full_name`). Because HMAC verification is a no-op whenever the selected organization has no `webhook_secret` configured — a state explicitly documented as optional/supported — nothing binds "the organization whose (absent) secret was used to authenticate the request" to "the organization/repository the handler actually writes to."

### Finding Description
`verify_signature` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` is a documented no-op when no `webhook_secret` is configured for that organization: [3](#0-2) 

`docs/setup.md` explicitly states the webhook secret is "optional": [4](#0-3) 

Once "verified" (trivially, because the chosen org has no secret), the request body is dispatched to handlers, which derive the *acted-upon* entity from **different** JSON fields than the ones used to select the verifying organization:

- `MembershipHandler` creates/updates a `Team` keyed by `params.team.id` (an ID an attacker can discover via GitHub's public API for any team) and adds an arbitrary attacker-supplied `member.login` to it, using `params.organization.login` only to set/find the team's org column — completely decoupled from any cryptographic binding to that org: [5](#0-4) 

- All repository-scoped handlers (`Handler#stacks`, and every `PullRequest::*Handler`) resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')`, a field never checked against `repository_owner` (the field used for signature-org selection): [6](#0-5) [7](#0-6) 

**Binding that is broken:** `organization` whose (possibly absent) `webhook_secret` authenticated the request `≠` `organization`/`repository` that the handler subsequently creates, joins, or archives. This is the same class of gap as the reported bug: two related values (`Whitelist.whitelistProduct` product vs. `OtokenFactory` collateral check) are validated independently instead of being cross-checked, letting the second check silently rely on state the first check never actually covered.

Concretely, an unprivileged attacker who knows (a) that at least one configured GitHub org in `secrets.yml` has a blank `webhook_secret` (a documented, supported configuration — see `docs/setup.md` line 30, and `config/secrets.development.shopify.yml` / `secrets_double_github_app.yml` which ship with `webhook_secret: # nil`), and (b) the numeric GitHub team ID of a `Shipit.github_teams` team (public/enumerable via the GitHub API for any org), can POST directly to `/webhooks` with `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "team": { "id": <known_team_id>, "name": "x", "slug": "x", "url": "https://x" },
  "organization": { "login": "<org-with-blank-webhook_secret>" },
  "member": { "login": "<attacker-github-login>" }
}
```
`verify_signature` calls `Shipit.github(organization: "<org-with-blank-webhook_secret>").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank, regardless of the actual `X-Hub-Signature` header. `MembershipHandler` then finds the existing `Team` by `team.id` and appends the attacker's GitHub login as a member.

### Impact Explanation
This grants unauthenticated escalation into `Shipit.github_teams` authorization: `User#authorized?` checks team membership against `Shipit.github_teams`, so an attacker added as a member of an authorized `Team` record becomes an authorized Shipit user once they complete GitHub OAuth login (an unprivileged, publicly available action), per: [8](#0-7) [9](#0-8) 

This is explicitly listed as a qualifying High-severity impact. The same organization/repository-field decoupling also lets the attacker forge `push`/`pull_request`/`status` events for stacks belonging to a *different, unrelated* repository than the (secret-less) organization used to pass verification, potentially injecting fake commit statuses or triggering stack syncs/archival for repositories they do not control — a cross-repository write.

### Likelihood Explanation
Requires no credentials, no session, and no GitHub write access — only knowledge of one multi-tenant Shipit deployment's org list (visible in `Shipit.github` config errors/UI) having at least one org with a blank `webhook_secret`, which the project's own documentation and shipped example configs (`config/secrets.development.shopify.yml`, `secrets_double_github_app.yml`) present as a normal, optional setup. Team IDs are discoverable via GitHub's public team APIs. The webhooks endpoint is intentionally public and unauthenticated by design (it must accept unauthenticated GitHub webhooks), so the only defense is the signature check, which this analysis shows is not actually bound to the entity being mutated.

### Recommendation
- Do not treat a missing `webhook_secret` as "verification passes"; require every configured GitHub App to have a non-blank `webhook_secret` in production, or reject events for any org without one.
- Cross-check that every identifying field used by handlers (`repository.full_name`, `organization.login`, `team.id`'s associated org) is consistent with the `repository_owner`/org actually used to verify the signature before processing the event.
- For `MembershipHandler`, verify that `params.organization.login` matches the organization already associated with `Team.find_by(github_id: params.team.id)` before mutating membership, rather than trusting the payload's `organization` field as authoritative provenance.

### Proof of Concept
1. Configure (or find) a Shipit deployment with two GitHub orgs in `secrets.yml`, where `OrgA` has a blank `webhook_secret` (per documented "optional" setup) and `OrgB` hosts a `Shipit.github_teams` team `Org/team` with known GitHub team id `T`.
2. Without any valid signature, POST to `/webhooks`:
   - Header `X-Github-Event: membership`
   - Body: `{"action":"added","team":{"id":T,"name":"n","slug":"s","url":"https://x"},"organization":{"login":"OrgA"},"member":{"login":"attacker-login"}}`
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank — request is accepted (see `test/controllers/webhooks_controller_test.rb` membership tests, which show membership events are processed with no signature stubbing beyond the general `verify_signature` stub).
4. `MembershipHandler` finds the existing `Team` with `github_id == T` (belonging to `OrgB`, unrelated to `OrgA`) and adds `attacker-login` as a member.
5. Attacker completes GitHub OAuth login with `attacker-login`; `User#authorized?` now returns true, granting full Shipit UI/API access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
```
