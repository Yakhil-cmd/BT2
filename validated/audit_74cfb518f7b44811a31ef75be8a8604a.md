### Title
Unauthenticated stack-existence oracle via forged `referrer` in `MergeStatusController#show` - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController#show` is exempted from `force_github_authentication` via `skip_authentication only: %i[check show]`, so `current_user.authorized?` (the `Shipit.github_teams` membership gate) is never evaluated for this action. An unauthenticated attacker can supply an arbitrary `params[:referrer]` value shaped like `https://github.com/<owner>/<repo>/pull/<n>`, which `ReferrerParser` uses to look up a `Stack` by `owner`/`name` with no ownership check, and the response body diverges depending on whether that stack exists.

### Finding Description
The broken binding: `authorized_repo(current_user) == referrer_parser.repo_owner/repo_name` is never asserted — the equality that should hold (only stacks the requester is authorized to view are returned) does not exist anywhere on this path.

Code path: request → `#show` (skip-authenticated) → `#stack` → `referrer_parser.repo_owner`/`repo_name` (parsed from `params[:referrer]`, no HTTP `Referer` header trust needed since the app reads `params[:referrer]` directly) → `Stack.where(repositories: { owner:, name: })...first` [1](#0-0) , [2](#0-1) .

`skip_authentication only: %i[check show]` calls `skip_before_action(:force_github_authentication, only: %i[check show])`, which removes the only guard that checks `current_user.authorized?` against `Shipit.github_teams` [3](#0-2) , [4](#0-3) .

In `#show`, once `stack` resolves to a truthy row, `current_user.logged_in?` is checked only to decide between `render('logged_out')` and `render(stack_status, ...)` — it never re-checks whether the stack exists or whether the anonymous caller should even learn that:
```
if stack
  return render('logged_out') unless current_user.logged_in?
  ...
else
  render(html: '')
end
``` [5](#0-4) 

So for an anonymous requester (no session cookie), the response is:
- `render('logged_out')` (HTTP 200, non-empty template) if a `Stack` matching the forged owner/name (and default `environment: 'production'`, or `params[:branch]`) exists,
- `render(html: '')` (HTTP 200, empty body) if `ReferrerParser` raises `ArgumentError` or no matching stack is found.

This response variance is a reliable unauthenticated oracle for stack existence, keyed purely off attacker-supplied `owner`/`name` strings, for any repository configured in this Shipit instance — including ones the attacker has no access to or isn't even the real owner of on GitHub (since `owner`/`name` are just matched against the local `Repository` table, not validated against actual GitHub permissions).

Existing guards that fail to stop this:
- `force_github_authentication` / `current_user.authorized?` — explicitly bypassed via `skip_authentication`.
- `stale?`/etag logic — only affects caching semantics of the authenticated path, not reached before the existence branch matters.
- `ReferrerParser`'s regex — validates format only, not repo ownership; it happily parses attacker-chosen owner/repo names [6](#0-5) .
- No `require_permission!`, `stacks` scope, or repository-ACL check exists anywhere in this controller.

### Impact Explanation
An unauthenticated attacker can repeatedly probe arbitrary `owner/name[/branch]` combinations against the Shipit instance and, from response-body/content differences (`'logged_out'` template vs empty body), learn whether a Shipit stack for that repository/branch exists. This is a confirmed unauthenticated information-disclosure primitive (stack existence, and indirectly which orgs/repos are onboarded to this Shipit instance) — matching the "High: unauthenticated read of stack state" category, though the disclosed content is limited to existence/onboarding status rather than full task/deploy output (the actual `stack_status` render is still gated behind `current_user.logged_in?`). Blast radius is cross-tenant: any repository configured on the shared Shipit instance can be probed by any anonymous internet user, with no session, token, or GitHub credential required.

### Likelihood Explanation
Attacker cost is trivial: a single unauthenticated HTTP GET to the `merge_status` route with a crafted `referrer`/`stack_id`-less query and a guessed or enumerated `owner`/`name` pair (e.g. from public GitHub org/repo names). No Shipit or GitHub secrets, no team membership, and no valid session are required — this is exactly within the stated attacker capability (unprivileged internet user sending HTTP requests to the Shipit host). The probe is fully repeatable and scriptable across arbitrary owner/name values.

### Recommendation
Do not allow `#show` to branch on stack existence for anonymous users before authorization is checked. Options:
1. Remove `show` from `skip_authentication` and instead let `force_github_authentication` run normally, deferring only the final "is this the right response" gating to view-level logic that doesn't leak existence.
2. If anonymous access to `show` must remain (e.g., for embeddable badges), make the response indistinguishable regardless of stack existence when `current_user` is not authorized/logged in — e.g., always `render('logged_out')` for anonymous requests (or always the same generic body), and only perform `ReferrerParser`/DB lookups after establishing the caller is authorized, or return a constant-time/constant-shape response for both existing and non-existing stacks.

### Proof of Concept
Minitest plan (`test/controllers/shipit/merge_status_controller_test.rb`-style, no live GitHub, no session cookie set):
```ruby
test "#show leaks stack existence to anonymous users via forged referrer" do
  stack = shipit_stacks(:shipit) # or create a Stack whose Repository owner/name is known
  # no login: do NOT call session[:user_id] = ...

  get merge_status_path(referrer: "https://github.com/#{stack.repository.owner}/#{stack.repository.name}/pull/1")
  assert_response :success
  existing_body = response.body

  get merge_status_path(referrer: "https://github.com/definitely-nonexistent-org-xyz/definitely-nonexistent-repo/pull/1")
  assert_response :success
  nonexistent_body = response.body

  refute_equal existing_body, nonexistent_body
  assert_equal "", nonexistent_body
  assert_match(/logged_out|log in/i, existing_body) # renders the 'logged_out' template only when stack exists
end
```
This demonstrates that, prior to any equality check like `current_user.authorized_for?(stack.repository)`, the response body for an unauthenticated caller already differs based purely on attacker-supplied `referrer` values, confirming the existence-disclosure vulnerability.

    class ReferrerParser
      URL_PATTERN = %r{\Ahttps://github\.com/([^/]+)/([^/]+)/pull/(\d+)}

      attr_reader :repo_owner, :repo_name, :pull_request_number

      def initialize(referrer)
        unless (match_info = URL_PATTERN.match(referrer.to_s))
          raise ArgumentError, "Invalid referrer: #{referrer.inspect}"
        end

        @repo_owner = match_info[1].downcase
        @repo_name = match_info[2].downcase
        @pull_request_number = match_info[3].to_i
      end
    end

      end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
