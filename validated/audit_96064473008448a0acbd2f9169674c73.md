## Title
Webhook authenticates the organization named in the payload, not the repository/commit the handler actually mutates — cross‑organization forgery of commit status and team membership - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the organization named inside the *unverified* JSON body (`repository.owner.login` / `organization.login`), then hands the *entire same, attacker‑controlled* body to handlers that act on a completely different key — a commit `sha` (for `status`) or a `team.id` (for `membership`) — without ever confirming those objects belong to the organization that was authenticated. This mirrors the M‑15 pattern: the check is bound to one identity (the authenticating org) while the effect is applied to a different, unchecked identity (the target repo/commit/team).

Once `verify_signature` passes, `create` forwards the raw, attacker‑supplied JSON to handlers unmodified: [5](#0-4) 

- `StatusHandler` looks up commits **purely by `sha`, with no repository/organization scoping at all**: [6](#0-5) 
- `MembershipHandler` resolves the target `Team` by `params.team.id` (only using `organization.login` on first creation) and adds the named member to it: [7](#0-6) 
- other handlers resolve the acted‑upon `Repository` via `params.repository.full_name`, an independent field from the one used for signature selection: [8](#0-7) 

Because the field used to select/verify the signing key (`repository.owner.login` / `organization.login`) is never cross‑checked against the field the handler actually mutates (`sha`, `team.id`, `repository.full_name`), an attacker who can get **any one** configured organization to pass `verify_signature` — trivially, by targeting an organization whose `webhook_secret` is left unset, a supported/documented configuration — can freely author the rest of the JSON body to reference commits, teams, or repositories belonging to a *different*, fully secured organization.

Binding that should hold but doesn't:
`authenticated_org(payload.repository.owner.login) == owning_org(payload.<acted_upon_entity>)`

### Impact Explanation
- Forging a `status` event lets an unauthenticated network attacker post an arbitrary commit status (`success`/`failure`, arbitrary `context`/`description`/`target_url`) for **any commit sha tracked by any stack on the instance**, regardless of which organization actually owns that repository. Since commit statuses drive Shipit's deployability/merge checks, this can be used to force a commit to appear "green" and enable an unauthorized deploy/merge/rollback.
- Forging a `membership` event with `action: added`, `team.id` set to an existing, already‑authorized team's GitHub id, and `member.login` set to the attacker's own GitHub login grants that user membership in a `Shipit.github_teams`‑authorized team, escalating them into full authenticated access via `User#authorized?`: [9](#0-8) 

Both outcomes match explicitly listed High/Critical impacts: escalation into `Shipit.github_teams` authorization, and an unauthorized deploy/merge/rollback.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it's the GitHub webhook receiver) and reachable by anyone. The only gate is `verify_signature`, which is fully satisfied for any organization configured without a `webhook_secret` — an explicitly optional, documented setting. No session, `ApiClient` token, or secret knowledge is required for that organization; the attacker only needs the target commit `sha` (often public, e.g. visible on GitHub or in the Shipit UI) or a target team's numeric GitHub id (also discoverable via GitHub's API/UI).

### Recommendation
Bind the signature‑verification identity to the entity being mutated:
- For `status`, require and validate `repository.full_name`/`owner.login` and only update commits belonging to that specific repository.
- For `membership`, verify `organization.login` matches the team's stored `organization` on every event (not just at creation) before adding/removing members.
- More generally, do not allow `webhook_secret`‑less organizations to authorize actions referencing entities (commits, teams, repositories) outside that same organization; consider making `webhook_secret` mandatory, or scoping every handler's target lookup by the authenticated organization.

### Proof of Concept
1. Configure (or find) a Shipit instance with two GitHub orgs, `OrgA` (no `webhook_secret` set) and `OrgB` (secret set, has a stack tracking commit `abc123` and is deploy-gated by CI status).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/unrelated-repo" }
}
```
No `X-Hub-Signature` needs to be valid because `Shipit.github(organization: "OrgA")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
3. `StatusHandler` executes `Commit.where(sha: "abc123").each { |c| c.create_status_from_github!(params) }`, creating a forged "success" status on `OrgB`'s commit — with no relation to `OrgA` at all — potentially unblocking a deploy that should have been gated by real CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
