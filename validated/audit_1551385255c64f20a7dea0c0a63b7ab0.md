### Title
Cross-organization `membership` webhooks let an attacker's own org grant `Shipit.github_teams` authorization by adding attacker's user to a victim team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by the GitHub-global `team.id`, never checking that the webhook's `organization.login` matches the team's stored `organization`. Combined with `WebhooksController#verify_signature`, which verifies the signature only against the org named in the attacker-controlled payload, an attacker who controls a webhook for *their own* configured org can add their own `Shipit::User` to a completely different org's `Team` record. Because `User#authorized?` and `force_github_authentication` grant access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, this write escalates the attacker into `Shipit.github_teams` authorization for a team they were never actually added to on GitHub.

### Finding Description
Broken binding, stated as an equality that the code fails to preserve:

`victim_team.organization` (as recorded when the team was created from GitHub, e.g. `"shopify"`) **should equal** the `organization.login` verified by the webhook signature that is allowed to mutate that team's `Membership` rows.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the signature using `Shipit.github(organization: repository_owner)` [2](#0-1) . `membership` events carry no `repository` key, so `repository_owner` is taken entirely from the attacker-supplied `organization.login` field — the attacker chooses which org's secret signs the request, and it can be their own configured org.
- `MembershipHandler#find_or_create_team!` then resolves the target `Team` via `Team.find_or_create_by!(github_id: params.team.id) { ... }` [3](#0-2) . The block that sets `team.organization = params.organization.login` only runs on creation; when the `github_id` already matches an existing (victim) `Team` row, that row is returned unmodified and the organization used for signing is never re-checked against `team.organization`.
- `process` then calls `team.add_member(member)` [4](#0-3) , creating a `Membership` between the attacker's `User` and the victim `Team`, purely because the attacker's own org's webhook secret validated the request.
- `User#teams` is `has_many :teams, through: :memberships` [5](#0-4) , so this new membership is immediately visible to authorization logic.
- `User#authorized?` grants access if `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , and `force_github_authentication` gates the entire application on this check [7](#0-6) .
- `Shipit.github_teams` is populated via `Team.find_or_create_by_handle` [8](#0-7) , whose id is exactly the `Team` row that `find_or_create_team!` matched by `github_id` — same row, so the attacker's forged membership satisfies the id filter directly.

None of the standard guards prevent this: `verify_signature` succeeds because it validates against the org the *attacker* named, not the org that owns the target team; the `ExplicitParameters` schema on `MembershipHandler` only validates presence/types of `team.id`, `organization.login`, `member.login`, not their mutual consistency; and there is no cross-check anywhere that the signing org equals `team.organization`.

### Impact Explanation
The attacker gains membership in a `Team` used for `Shipit.github_teams` authorization checks without ever legitimately belonging to that team on GitHub, letting them pass `force_github_authentication` and access every stack, deploy, task-stream, and any other `Shipit.github_teams`-gated resource on the shared Shipit instance. This is repeatable against any team whose numeric GitHub `team.id` the attacker can learn or brute-force (GitHub team ids are small sequential integers, discoverable via the GitHub API for teams the attacker can see, or simply guessed), and against any victim organization co-tenanted on the same Shipit deployment. This matches the "High - escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-tenant (serves more than one GitHub organization) with `Shipit.github_teams` configured to restrict access, and the attacker must control a webhook-emitting GitHub org that is itself a configured tenant of that Shipit instance (so `Shipit.github(organization: attacker_org)` resolves and signs successfully) — this matches the scenario explicitly assumed by the question ("after achieving the cross-org `Membership` write"). Given that precondition, the attacker's cost is a single crafted `POST /webhooks` request with `X-Github-Event: membership`, signed with their own org's webhook secret (which they legitimately possess), containing the victim's team `github_id`. This is fully repeatable and requires no GitHub API call to the victim org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the verified organization, and reject/no-op if an existing team's `organization` does not match the webhook's signing organization (which should be threaded through from `WebhooksController#verify_signature`'s `repository_owner`, not re-read from the untrusted payload). Additionally, `WebhooksController#verify_signature` should assert that `params.dig('organization','login')` (when used as `repository_owner`) matches the organization actually implicated by the event's substantive fields (e.g., the team being modified), rather than trusting the attacker-chosen value outright.

### Proof of Concept
Minitest plan (webhook controller / integration test), no live GitHub calls:
```ruby
test "membership webhook signed by attacker org cannot add member to a team belonging to a different org" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  attacker_login = 'attacker-user'

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # attacker's own configured org
    member: { login: attacker_login }
  }.to_json

  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)
  User.expects(:find_or_create_by_login!).with(attacker_login).returns(users(:attacker))

  post :create, body: payload, as: :json

  attacker = users(:attacker)
  # Binding under test: attacker.teams must NOT include victim_team without a legitimate
  # shopify-signed webhook ever having been verified.
  assert_not attacker.teams.reload.include?(victim_team)
end
```
Given the current implementation of `find_or_create_team!` (lookup by `github_id` only, no organization check), this assertion fails — `attacker.teams.include?(victim_team)` is `true`, confirming the escalation path into `Shipit.github_teams` authorization.
