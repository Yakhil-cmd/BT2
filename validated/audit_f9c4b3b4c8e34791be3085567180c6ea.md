### Title
Unhandled `throw Error` on duplicate-output race in private payment chain processing crashes the wallet process - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` performs an unguarded `throw Error(...)` inside a `db.query` callback when it finds more than one matching row for an incoming private-payment chain's head element. Because this throw happens inside an asynchronous callback with no surrounding try/catch (unlike the sibling error paths that call `callbacks.ifError`), it becomes an uncaught exception that can crash the whole node process — the same bug class as the Aztec fix, which stopped a contract-message handler from panicking on note-related messages it wasn't prepared to handle gracefully.

### Finding Description
When a private-payment counterparty (or the hub relaying a counterparty's message) sends a `private_payment`/`private_payments` message, it flows through `wallet.js:handlePrivatePaymentChains` → `network.js:handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`: [1](#0-0) 

That function queries the `outputs` table for the head element's `(unit, asset, message_index[, output_index])` and only guards against `rows.length > 1` with a hard `throw`, rather than routing it through `transaction_callbacks.ifError`: [2](#0-1) 

For divisible assets, the SQL intentionally omits the `output_index` filter (comment: "divisible outputs are never hidden individually … sql has no output_index filter"), so it can legitimately return multiple rows for the same `(unit, message_index)` once more than one output of that message has been separately revealed (e.g., recipient output and change output are handled as separate chains for divisible assets per `divisible_asset.js`'s "each chain consists of one element" model): [3](#0-2) 

A counterparty (or the hub) controls the timing and content of these `private_payment` messages. By sending overlapping/duplicate private-payment chains for the same unit/message_index concurrently (e.g., replaying the recipient chain twice, or sending recipient+change chains in a way that both resolve two output rows before the duplicate-check completes), the attacker can drive `rows.length` above 1 at the point this query resolves, hitting the `throw Error("more than one output ...")` path. Since this executes inside a `db.query` callback with no enclosing try/catch, it is an uncaught exception.

### Impact Explanation
An uncaught exception thrown from deep inside asynchronous DB-callback code is not caught by any of the surrounding `ifError` machinery (all sibling checks in the same function correctly call `callbacks.ifError`/`transaction_callbacks.ifError` and return — only this one case throws). Depending on whether a global `uncaughtException` handler is installed and how gracefully it degrades, this can crash the wallet process or leave it in a wedged state (open DB transaction/connection not released, since `conn.release()` inside `transaction_callbacks.ifOk/ifError` is never invoked before the throw propagates). Either outcome is a denial-of-service against the wallet/hub process reachable purely by sending crafted/duplicated private-payment messages — a node/wallet "unable to confirm new units" condition for that instance, matching the reachable-analog criteria (wallet/contract message handling).

### Likelihood Explanation
The trigger condition (receiving two private-payment chains for the same `unit`/`message_index` before the first one's row is fully "hidden"→"revealed" transition completes, or literally replaying the same chain) is achievable by any private-payment counterparty or a relaying hub, without needing any privileged access, key compromise, or protocol-breaking behavior — it only requires normal message-sending capability plus timing/duplication of already-valid payload structures. The comment in the code ("divisible outputs are never hidden individually … sql has no output_index filter") shows the developers were aware multiple rows are a normal occurrence for divisible assets, making the missing `ifError` handling a real gap rather than a purely theoretical one.

### Recommendation
Replace the `throw Error("more than one output "+sql+...)` with a call to `transaction_callbacks.ifError(...)` (and ensure the connection is rolled back and released, mirroring the rest of the function's error handling), so that malformed or duplicated/racy private-payment chains fail gracefully instead of crashing the process. Additionally, consider hardening the code path against concurrent processing of chains referencing the same `(unit, message_index)` (e.g., via a per-unit/message_index mutex) to prevent this race outright.

### Proof of Concept
1. Attacker (private-payment counterparty) sends a valid divisible-asset private payment chain to the victim wallet via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`, targeting a `unit`/`message_index` with two outputs (e.g., payment to victim + change to another address that is also being tracked/forwarded, or simply resend the same head element concurrently on two connections/threads such that both `db.query` calls in `validateAndSavePrivatePaymentChain` resolve after both output rows have been written).
2. Because the SQL for divisible assets does not filter by `output_index`, the second (or racing) invocation's `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` returns 2 rows.
3. `private_payment.js` line ~74-75 executes `throw Error("more than one output ...")` inside the `db.query` callback, which is not wrapped in try/catch anywhere in the call chain from `network.handleOnlinePrivatePayment`, causing an uncaught exception in the wallet/hub process. [4](#0-3)
