### Title
Cross-repository forgery of commit CI status via unscoped `StatusHandler` — organization authenticated for signature verification is not bound to the commit/repository the webhook payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against a specific GitHub App configuration selected solely by `repository.owner.login` (or `organization.login`) taken from the JSON body [1](#0-0) . That authenticated "organization" binding is never propagated into the handler that performs the mutation. `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits **globally by SHA**, with no repository/stack scoping whatsoever [2](#0-1) . This breaks the equality `organization_authenticated(payload) == repository_written(payload)`: the signature check authorizes a request for organization A, but the handler writes a `CommitStatus` onto any commit belonging to any repository/stack tracked by the entire Shipit install, including repositories owned by unrelated organizations B, C, etc.

### Finding Description
Signature verification resolves the relevant GitHub App/secret using only the `repository.owner.login` fallback to `organization.login` extracted from the raw, not-yet-verified body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

A per-organization `webhook_secret` is a normal, documented, optional configuration value — the shipped example config shows organizations configured with no secret at all (`webhook_secret: # nil`) [5](#0-4) . Any Shipit instance that hosts multiple GitHub organizations (a supported, documented topology) and has at least one organization without a configured secret provides an unauthenticated bypass for any request whose `repository.owner.login` (or `organization.login`) matches that unsecured organization.

Once past `verify_signature`, `WebhooksController#create` dispatches the parsed body directly to the registered handler for the event type:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

Most handlers correctly re-derive the target repository from `payload.dig('repository', 'full_name')` via the base `Handler#stacks` helper [7](#0-6)  — e.g. `PushHandler` scopes to `stacks.not_archived.where(branch:)` [8](#0-7) . `StatusHandler`, however, does not use `repository_name`/`stacks` at all; it resolves the target purely by commit SHA across the whole database:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Because `Commit` rows are shared across every `Stack`/`Repository` tracked by the Shipit instance, and the same 40-hex-character SHA can legitimately exist as a tracked commit under a different repository record (or an attacker who knows/guesses a target commit SHA that Shipit has already indexed for the victim stack), this handler will happily attach an attacker-supplied CI status (`state`, `context`, `description`, `target_url`, `created_at`) to that commit regardless of which organization's payload/signature check nominally authorized the request.

The equality broken, per the required binding classes, is:
`organization_authenticated_by_signature(repository.owner.login) != repository_of_commit_mutated(sha)`

### Impact Explanation
Shipit uses commit statuses to gate deploys: the `ci.require` configuration in `shipit.yml` blocks deploying a commit until required GitHub status contexts report success, and `Commit#deployable?` / the aggregate status stored via `create_status_from_github!` is what that gate consults. An attacker able to forge a `status` webhook event for any organization lacking (or with a known/misconfigured) `webhook_secret` can inject a fabricated "success" status for a required CI context onto a commit belonging to a *different* repository/stack, bypassing the CI-gate and enabling an **unauthorized deploy** of code that never actually passed CI — one of the explicitly qualifying Critical impacts (unauthorized deploy). This requires no session, no `ApiClient` token, no repository write access, and no possession of the victim organization's own webhook secret — only knowledge of an organization name configured on the instance without (or with a leaked, but non-webhook_secret specific) secret and the target commit SHA, which is typically public GitHub information.

### Likelihood Explanation
Likelihood depends on the operator's topology: this is exploitable whenever a Shipit instance hosts multiple GitHub organizations/apps (a first-class supported configuration, as shown in the shipped `secrets.*.yml` example with multiple org blocks) and at least one configured organization has no `webhook_secret` set — which the example configuration explicitly demonstrates as an accepted value (`nil`). Even where every organization has a secret configured, the same code proves a design defect: `StatusHandler` never checks that the authenticated organization matches the repository owning the target commit, so the class of vulnerability (authentication scoped to organization A, mutation applied without regard to which repository/stack owns the target row) is present in the code independent of any particular deployment's secret hygiene.

### Recommendation
- Bind the value used to select the verifying GitHub App/secret to the same value used by the handler to scope the mutation: `verify_signature` should re-derive `repository.full_name` (not just `owner.login`) and reject any event whose repository is not owned by the organization whose secret validated the signature.
- Fix `StatusHandler#process` to scope `Commit` lookups by the stack/repository derived from `payload.dig('repository', 'full_name')`, mirroring the pattern already used in `Handler#stacks` / `PushHandler`, instead of matching by SHA alone across the entire instance.
- Consider disallowing (or at minimum warning loudly and refusing signature bypass for) organizations configured without a `webhook_secret` when the instance manages more than one organization, since `verify_webhook_signature` currently treats an absent secret as an implicit "always trusted" organization.

### Proof of Concept
Given a Shipit instance configured with two organizations, `victim-org` (has stacks/commits tracked, secret configured normally) and `attacker-org` (configured on the same instance but with `webhook_secret: nil`, e.g. as shown in the sample config):

1. Attacker discovers/knows a commit SHA `deadbeef...` that Shipit has already recorded (e.g., it's the head of a branch on `victim-org/victim-repo` tracked by a `Stack` requiring a CI context named `ci/tests`).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # ignored because attacker-org has no webhook_secret
Body:
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/unrelated-repo" },
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "target_url": "http://example.com"
}
```
3. `verify_signature` computes `repository_owner == "attacker-org"`, loads `attacker-org`'s (secret-less) GitHub App config, and `verify_webhook_signature` returns `true` unconditionally [9](#0-8) .
4. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the commit that actually belongs to `victim-org/victim-repo`, and calls `create_status_from_github!`, writing a forged "success" status for the `ci/tests` context onto it — with zero relation to `attacker-org` [2](#0-1) .
5. If `victim-org/victim-repo`'s `shipit.yml` requires `ci/tests` before allowing deploy, this forged status can satisfy that requirement, enabling an unauthorized deploy of the commit.

Note: I was unable to directly inspect `Commit#create_status_from_github!` / `Commit#deployable?` implementation bodies within the indexed context (only reference counts were found), so the precise mechanics of how a forged status satisfies `ci.require` should be confirmed against `app/models/shipit/commit.rb` before remediation; the core authentication/authorization binding break in `WebhooksController#verify_signature` vs. `StatusHandler#process` is confirmed directly from the cited source.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
