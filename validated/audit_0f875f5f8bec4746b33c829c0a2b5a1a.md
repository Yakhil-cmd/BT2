### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-resolution helper with a version that skips the `ApiClient#stack_id` scoping check entirely, letting any valid token — even one deliberately restricted to a single stack — read build/deploy status for every stack in the Shipit instance.

### Finding Description
`Shipit::Api::BaseController` establishes the trust binding between an authenticated `ApiClient` and the stack(s) it is authorized to touch: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the client has a `stack_id`, and `stack` is derived from that scoped relation via `stacks.from_param!`. This is the binding: *"a stack a token authorizes" == "a stack it touches"*.

`Shipit::Api::CCMenuController` inherits from `BaseController` but redefines `stack` to bypass the scoped relation entirely: [2](#0-1) 

Here `stack` resolves via `Stack.from_param!(params[:stack_id])` — the global `Stack` relation, not the api-client-scoped `stacks` relation. The only enforcement is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only checks whether the string `"read:stack"` is present in the client's `permissions` array; it never consults `stack_id`. Consequently, `require_permission` cannot compensate for the missing scoping in `CCMenuController#stack`.

Fixtures show that stack-scoped clients are an expected, real-world configuration: [4](#0-3) 

`here_come_the_walrus` is created with `stack: shipit` and only `read:stack` permission, intended to only ever see the `shipit` stack (as verified elsewhere for the `Api::StacksController#index`, which is properly scoped via `stacks`). But when the same token is used against the `CCMenuController`, the `stack_id` restriction is silently dropped and `params[:stack_id]` in the URL is trusted directly against the unscoped `Stack` table.

This is structurally identical to the ENS bug class: an entity (`stack_id` on the `ApiClient`) is supposed to bind the authorized/verified resource ("the auction winner's deed") to the resource actually acted upon ("the ENS subnode"), but one code path (`CCMenuController#stack`) resolves the resource through a different, unverified reference (raw `params[:stack_id]`) instead of the authorized one.

### Impact Explanation
Any holder of a valid, deliberately narrow-scoped `ApiClient` token (e.g. a token meant only for CI status badges on one stack) can read deploy/build state — including `lastBuildStatus`, `lastBuildLabel`, activity, and lock status — for **every** stack managed by the Shipit instance, not just the one it was authorized for. This is an unauthorized read of stack state across tenants/stacks, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" defined for this exercise, since the binding between the authorized scope and the actually-touched resource is broken.

### Likelihood Explanation
High. Exploitation requires nothing more than possession of any valid API token with `read:stack` permission (even one intentionally scoped to a single stack) and knowledge or guessing of another stack's `to_param` (owner/repo/environment), which is often predictable or discoverable (e.g. via the public/team stack list). No secrets, GitHub credentials, or elevated privileges are required beyond an ordinary scoped token.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped relation, mirroring `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and delete the private `stack` override that reaches into the unscoped `Stack` model, so the `current_api_client.stack_id` binding is honored everywhere a stack is resolved from an API token.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack: stack_a` with permission `read:stack` (e.g. fixture `here_come_the_walrus`, scoped to `shipit`).
2. Authenticate to the API using this token (`Authorization: Basic <base64(token)>`).
3. Request `GET /api/stacks/<stack_a>/ccmenu.xml` — succeeds as expected.
4. Request `GET /api/stacks/<stack_b>/ccmenu.xml` for an unrelated stack the token was never granted access to.
5. Observe HTTP 200 with `stack_b`'s real `lastBuildStatus`/`lastBuildLabel`/activity data, confirming the `stack_id` scope on the `ApiClient` was not enforced by `CCMenuController`.
