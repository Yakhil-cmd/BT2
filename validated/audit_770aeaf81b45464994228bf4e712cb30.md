Confirmed: this vulnerability chain is real, and `PushHandler` is where it becomes exploitable.

### Title
Cross-org webhook signature verification allows attacker-forced `Stack#sync_github` with attacker-chosen `expected_head_sha` for a repository not owned by the verifying org - (File: app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature using the webhook secret of the org named in `repository.owner.login` [1](#0-0) [2](#0-1) , while `Handler#stacks` resolves the target repository using a *separate* field, `repository.full_name` [3](#0-2) . Because these two fields are independently attacker-controlled inside the same JSON body, an attacker who legitimately owns an org (and thus its `webhook_secret`) can craft a push payload where `repository.owner.login` is their own org (so the signature check passes) but `repository.full_name` names a victim org's repo, causing `PushHandler#process` to run `stack.sync_github(expected_head_sha: params.after)` against a stack the attacker's org does not own.

### Finding Description
The broken binding: `repository_owner_used_for_signature_verification == repository_owner_of_stack_being_mutated` must hold, i.e. `payload.dig('repository','owner','login')` (used in `Shipit.github(organization: repository_owner)` at `WebhooksController#verify_signature`, line 25 [4](#0-3) ) must equal the owner of the repository resolved via `payload.dig('repository','full_name')` in `Handler#repository_name`/`#stacks` [3](#0-2) .

These two values are read from independent JSON keys with no cross-check anywhere in the request lifecycle. `WebhooksController#create` parses the raw body once and hands the same hash to every handler after signature verification passes [5](#0-4) . Nothing re-derives or re-validates `repository.owner.login` against `repository.full_name`'s owner segment before `PushHandler#process` runs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [6](#0-5) .

Attacker exploit flow:
1. Attacker owns `attacker-org` on GitHub, which is registered in Shipit with its own legitimate `webhook_secret` (a precondition explicitly allowed by the rules: "any org whose webhook_secret they legitimately hold").
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and a body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen sha>"`.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [3](#0-2) [7](#0-6) , finds the victim's `master` stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for every matching non-archived stack [8](#0-7) .
5. `sync_github` (via `after_commit`/direct call) enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha`, which is used to detect/retry sync and drive commit reconciliation against the real GitHub state for the victim's repo [9](#0-8) .

Existing guards do not prevent this: `verify_signature` only proves the request was signed by *some* org's secret; `drop_unhandled_event` and `check_if_ping` are unrelated; `ExplicitParameters` schema on `PushHandler` only requires `ref`/`after` are present, it does not constrain repository ownership [10](#0-9) ; `Repository.from_github_repo_name` performs no authorization check tying the resolved repository back to the org that signed the request [7](#0-6) .

### Impact Explanation
Once `GithubSyncJob` runs with a forged `expected_head_sha` for a victim repository/stack, the victim stack's expected-head tracking and retry logic operate on attacker-controlled state [9](#0-8) . This is a payload for one repository (attacker's) mutating another repository's stack (victim's) — matching the Critical impact category defined in the rules ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any victim repository/stack combination as long as the attacker knows or guesses `full_name` and the target has a stack with a matching branch; the attacker needs only their own org's webhook secret, not the victim's.

### Likelihood Explanation
Preconditions: attacker must control at least one org registered in Shipit with a genuine `webhook_secret` (explicitly permitted by the rules as a legitimate attacker capability), and the victim must have a non-archived `Stack` for the targeted repository/branch. Attacker cost is low — one HTTP POST with a correctly signed but semantically mismatched body. No GitHub session, API token, or victim secret is required. This is directly reachable via the public `POST /webhooks` endpoint documented as mounted by the engine.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#stacks`, ensure the org used to verify the signature is the same org that owns the repository resolved for stack lookup: derive both from the same normalized source (e.g., always use `repository.full_name`'s owner segment for both signature verification and repository resolution, or explicitly assert `payload.dig('repository','owner','login').casecmp(repository.owner) == 0` before dispatching to handlers) and reject (422) on mismatch.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub — stub `verify_webhook_signature`):
```ruby
test "cross-org signed push payload mutates a stack in a different, unrelated organization" do
  victim_stack = shipit_stacks(:shipit) # owner "shopify", branch "master"

  body = JSON.parse(payload(:push_master))
  body["repository"]["owner"]["login"] = "attacker-org"      # used for signature org lookup
  body["repository"]["full_name"] = "shopify/shipit-engine"  # used for stack lookup
  body["ref"] = "refs/heads/master"
  body["after"] = "attacker0000000000000000000000000000attacker"

  request.headers['X-Github-Event'] = 'push'
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "attacker0000000000000000000000000000attacker"]) do
    post :create, body: body.to_json, as: :json
  end
  # Assert LHS (org whose secret verified) != RHS (org owning the mutated stack)
  assert_not_equal "attacker-org", victim_stack.repository.owner
end
```
This demonstrates the equality `repository_owner_used_for_signature == repository_owner_of_mutated_stack` is violated: signature is verified for `attacker-org`, but `GithubSyncJob`/`stack.sync_github` is invoked with an attacker-chosen `expected_head_sha` for the `shopify`-owned stack.
