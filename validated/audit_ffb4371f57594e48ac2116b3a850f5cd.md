### Title
Cross-organization commit-status forgery via webhook signature keyed on `repository.owner` while `StatusHandler` writes unscoped by repository - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the per-organization webhook secret used to validate an inbound webhook based on a field taken from the payload itself (`repository.owner.login`, falling back to `organization.login`), but the actual event handler that consumes the same payload for the `status` event, `Shipit::Webhooks::Handlers::StatusHandler`, updates commit state by matching **only on the commit SHA, with no repository, owner, or stack scoping at all**. This breaks the intended trust binding "organization whose secret authenticated this webhook" == "repository/stack that gets written," identically to the referenced finding's root cause: a value used to gate/authorize a downstream effect is not tied to (and not actually covered/enforced against) the effect it authorizes.

### Finding Description
`verify_signature` selects which org's `github_app`/secret to check the HMAC against using an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

Any party who legitimately controls a webhook secret for **one** organization registered in a multi-organization Shipit deployment (a normal, documented configuration, see `config/secrets.development.example.yml`'s "multiple Github applications for different Github organizations" example) can craft an arbitrary raw JSON body, sign it with that one known secret, and send it directly to the public `/github-notifications` webhook endpoint. The signature check only proves the bytes were signed with *some* org's secret — it never verifies that the content of the payload (e.g. the commit SHA being acted on) actually belongs to that organization's repositories.

`StatusHandler#process` then acts on the payload with no repository/owner scoping whatsoever: [3](#0-2) 

`Commit.where(sha: params.sha)` matches every `Commit` record across **every stack, repository, and organization** hosted on the same Shipit instance that happens to share that SHA value — SHAs are public information, visible in the target repository's Git history or the target stack's own Shipit UI. This contrasts with every other webhook handler in the engine, which correctly re-derives and scopes to a `Repository`/`Stack` via `Repository.from_github_repo_name(params.repository.full_name)` (see `push_handler.rb`, `opened_handler.rb`, `closed_handler.rb`, etc.) before mutating anything — `StatusHandler` is the outlier that drops this binding.

The broken equality is:
`organization whose webhook_secret verified this request` == `organization owning the repository/commit that gets mutated`

Before the attacker's request: this holds, because legitimate GitHub-originated `status` webhooks always carry `repository.owner.login` matching the actual commit's repository.
After the attacker's forged request: the left side is the attacker's own (low-trust) organization, while the right side can be **any** organization's commit whose SHA the attacker knows — a complete break of the binding.

### Impact Explanation
Commit statuses recorded via `Commit#create_status_from_github!` feed directly into Shipit's deploy/merge-gating logic (deployability checks surfaced through `commit_checks`/`deployable_status` hooks and the merge queue). By forging a `status` event signed with a webhook secret they legitimately hold for an unrelated, low-trust organization, an attacker can inject a fabricated "success" status onto a specific commit belonging to a completely different, higher-trust stack/repository on the same Shipit installation, which can make that commit appear deployable/mergeable when its real CI has not passed — i.e., it enables an unauthorized deploy or merge on a repository the attacker has no legitimate relationship with. This satisfies the "Critical - cross-repository writes / unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires only: (1) a valid webhook secret for one organization already configured in the shared Shipit instance (routine to obtain for anyone administering that org's GitHub App/webhook, not a Shipit credential, `ApiClient` token, or the target org's own secret), and (2) knowledge of the target commit's SHA, which is public. No Shipit session, no GitHub App private key of the target org, and no repository write access to the target repo are needed — matching the "unprivileged attacker" bar of the ruleset.

### Recommendation
In `StatusHandler` (and any other handler that could act cross-repository), scope the lookup by the repository identified from the payload's `repository`/`organization` field and cross-check it against `repository_owner`/the organization whose secret validated the signature, e.g. `commit.stack.repository.owner == repository_owner`, before mutating state. More generally, `verify_signature` should ensure the organization it authenticates against is provably the same organization whose data is subsequently written, not merely used to pick a secret out of an unauthenticated field.

### Proof of Concept
1. Shipit is configured with two organizations, `org-attacker` and `org-victim`, each with its own `github.webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker controls `org-attacker`'s webhook secret (e.g., they administer that org's GitHub App).
3. Attacker learns the SHA of a commit on a stack belonging to `org-victim` (public info).
4. Attacker POSTs to `/github-notifications` (or the configured webhook path) with `X-Github-Event: status`, body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "repository": { "owner": { "login": "org-attacker" } }
}
```
signed with `org-attacker`'s secret via `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner` to `org-attacker`, fetches `org-attacker`'s `github_app`, and the HMAC check passes since the attacker signed with the correct (attacker-owned) secret. [4](#0-3) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `org-victim` commit purely by SHA match, applying the forged `success` status to it, unaffected by the fact that the signature only vouched for `org-attacker`. [3](#0-2)
