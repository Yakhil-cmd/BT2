### Title
Missing upper bound on `count_coins` in asset denomination definitions allows floating-point precision-loss mismatch between declared `cap` and actual issuable supply - ([File: validation.js])

### Summary
`validateAssetDefinition` in `validation.js` computes `total_cap_from_denominations` by summing `denomInfo.count_coins * denomInfo.denomination` for every entry in `payload.denominations`, then requires this sum to equal the declared `payload.cap`. While `denomination` is (conditionally) bounded to `constants.MAX_CAP` and `cap` itself is always bounded to `MAX_CAP`, `count_coins` is validated only with `isPositiveInteger()` — there is no upper bound at all. This is directly analogous to the CVE-2020-22874 bug class: an integer-sizing/quantity value that is validated for "is a positive integer" but not for being within a safe/expected range, then used in a multiplication/summation that determines how a downstream buffer/quantity is sized — leading to silent overflow/precision loss and a mismatch between the value that was checked and the value that is actually used.

`isPositiveInteger` only checks that the value is a positive JS number that is an integer — it places no upper limit on `count_coins` (unlike `denomination` and `cap`, which are bounded to `constants.MAX_CAP = 9e15`, close to `Number.MAX_SAFE_INTEGER`). Because JavaScript numbers are IEEE-754 doubles, `count_coins * denomination` for large `count_coins` values (e.g. `1e20`, `1e50`, etc.) is computed with silent precision loss / rounding rather than throwing, and summing several such imprecise products via `+=` can, through crafted values, produce a `total_cap_from_denominations` that happens to equal any attacker-chosen `payload.cap` (which must itself be `<= MAX_CAP`) due to floating-point rounding collisions, even though the mathematically exact sum of `count_coins * denomination` is vastly different (much larger) than the declared cap.

The exact same identical pair of unvalidated fields (`count_coins`/`denomination`) is validated the same way in the AA-definition path in `aa_validation.js` (`validateDenominations`), which also only checks `isPositiveInteger(denomInfo.count_coins)`, with no upper bound, so both the unit-posting path and the AA-definition path are reachable by an unprivileged unit poster / AA author.

Later, at actual coin-issuance time, `indivisible_asset.js`'s `issueNextCoin` reads `denomination` and `count_coins` back from the `asset_denominations` table and computes `count_coins_to_issue * denomination` again to determine `issue_amount` for each output — using the same JS floating-point arithmetic. Because the issuance-side computation uses the same (lossy) arithmetic as the validation-side computation, a coordinated choice of `denomination`/`count_coins` values lets an attacker make the *declared* `cap` pass validation (matching the lossy sum) while the *real* mathemetical total of coins that will eventually be issuable across all denomination rows is arbitrarily larger than the stated cap, defeating the cap's supply-limiting guarantee for the asset.

### Impact Explanation
If the crafted definition is accepted (because `total_cap_from_denominations === payload.cap` in floating-point arithmetic despite gross precision loss), the asset is created with a small, "safe-looking" `cap`, but the sum of `count_coins × denomination` across its denomination rows is truly enormous. Since indivisible-asset issuance is per-denomination-row (`can_issue_condition = "max_issued_serial_number=0"` for capped assets, i.e. each denomination row can be issued once, up to `count_coins` coins of that denomination), the protocol has no other invariant preventing supply from growing far beyond the declared, user-visible `cap`. This is a supply-inflation vulnerability for indivisible (fixed-denomination) capped assets, matching the "supply inflation" impact criterion.

### Likelihood Explanation
Reachable directly by any unit poster who defines a new asset (`validateAssetDefinition` in `validation.js`) or by any AA author who defines an asset inside an AA definition (`aa_validation.js`). No privileged role, hub, or peer cooperation is required — a single crafted unit/AA definition triggers the vulnerable code path. The main uncertainty is whether a concrete `count_coins`/`denomination` pair can be constructed such that the exact IEEE-754 double sum collides with a legal `cap <= 9e15`; this requires careful numeric crafting but is a well-known class of floating-point exploitation (similar to "hash collision via rounding" issues) and is plausible given the complete absence of any upper bound on `count_coins`.

### Recommendation
Add an explicit upper bound check on `denomInfo.count_coins` (e.g., `count_coins <= constants.MAX_CAP / denomination`, checked with an overflow-safe method, or bound the product itself before adding) in both `validateAssetDefinition` (`validation.js`) and `validateDenominations` (`aa_validation.js`). Additionally, perform the cap-sum comparison using integer-safe arithmetic (e.g., BigInt or a "count_coins * denomination > MAX_CAP" check performed before accumulation) rather than raw JS floating-point multiplication/addition, and reject any denomination whose individual `count_coins * denomination` exceeds `constants.MAX_CAP`.

### Proof of Concept
Exact colliding numeric values were not able to be enumerated within the scope of this review (would require numerical search for a `count_coins`/`denomination` pair whose IEEE-754 double product/sum collides with a legal `cap ≤ 9e15`), but the vulnerable pattern is concretely demonstrated by the code:

```
denominations: [
  { denomination: 1, count_coins: <very large integer, unbounded, e.g. 1e20> }
]
```//

`isPositiveInteger(1e20)` returns `true` (no upper bound enforced), so this entry passes `validateAssetDefinition`'s per-field checks; `total_cap_from_denominations` is computed as `1 * 1e20 = 1e20` in floating point. By choosing multiple denomination rows whose individual products are each individually huge but whose *summed, rounded* floating-point result happens to equal a small legal `cap` value (≤ `9e15`), the asset definition passes the `payload.cap !== total_cap_from_denominations` check while the true intended/issuable supply across denomination rows is unbounded relative to the stated cap.
