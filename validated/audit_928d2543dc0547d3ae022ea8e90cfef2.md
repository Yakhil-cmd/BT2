### Title
StatusHandler#process applies GitHub status webhooks to any commit matching `sha` across all stacks/repositories, with no repository-scoping check - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)`, unlike every other webhook handler in the codebase (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`), which all resolve the target `stacks` via `Handler#stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`) before acting. This means a validly signed "status" webhook for *any* repository whose org has the Shipit GitHub App installed can write a `Status` onto a commit belonging to a completely different stack/repository, as long as the `sha` values coincide, and that status is then evaluated against `Commit#blocked?`/`deployable?` for the unrelated victim stack.

### Finding Description
The broken binding: `{commits mutated by a status webhook} == {commits belonging to the repository that the webhook signature authenticates}`. In reality it is `{commits mutated} == {all Commit rows in the entire Shipit database whose sha string equals params.sha}`, independent of which repository/organization originated the webhook.

Code path:
- `WebhooksController#create` dispatches the parsed JSON to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which selects the HMAC secret via `repository_owner = params.dig('repository','owner','login')` (attacker-supplied field inside the same signed payload) [1](#0-0) .
- Every other handler resolves the target stacks from `payload.dig('repository','full_name')` before acting: `Handler#stacks` [2](#0-1) ; e.g. `PushHandler#process` [3](#0-2)  and `CheckSuiteHandler#process` [4](#0-3)  both filter through `stacks...` before touching any commit.
- `StatusHandler#process` does not: it never requires/reads `repository` in its params schema and queries commits globally by sha: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! (params) }` [5](#0-4) .
- `Commit#create_status_from_github!` writes the new `Status` scoped to the commit's *own* `stack_id` (the victim's real stack), not anything derived from the webhook payload: `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [6](#0-5) .
- `Commit#blocked?` recomputes over `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` [7](#0-6) , and `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [8](#0-7) . A forged `success` for the specific blocking `context` on the oldest offending commit flips `blocking?` to false for that commit, which flips `blocked?` for every newer sibling in the same query, and `deployable?` for those commits accordingly (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [9](#0-8) .

Exploit flow: an attacker with legitimate write access to a repository whose GitHub org has the Shipit App installed can, via GitHub's real Statuses API on their own repo, create a status whose `sha` field is set to the (publicly discoverable) sha of a victim commit tracked in a different Shipit stack, using the exact blocking `context` string used by the victim (also discoverable from the victim's public status/CI page or `shipit.yml`). GitHub itself signs and delivers this webhook with the real secret for the attacker's own org, so `verify_signature` passes legitimately - no secret is guessed or bypassed. `StatusHandler#process` then applies it to the victim's commit purely by sha match, regardless of repository.

Why existing guards fail: `verify_signature` only authenticates *which organization's app* sent the webhook, not that the referenced `sha`/`context` actually belongs to a repository that org owns. `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate the shape of the payload (`sha`, `state`, `context`, etc.), not repository ownership - the schema doesn't even declare a `repository` field, unlike `PullRequest::OpenedHandler`, confirming the omission is structural, not merely unused input.

### Impact Explanation
A forged/legitimately-obtained status webhook from an attacker-controlled repository can mutate `Status` records - and thus `Commit#blocked?`/`deployable?` - for a commit and its entire undeployed sibling range belonging to a completely unrelated stack/repository/tenant on the same Shipit instance. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team." Downstream, this can unblock a deploy pipeline that legitimately has failing/missing required CI, enabling an unauthorized/unsafe deploy of the victim's stack if a human or continuous-deployment trigger acts on the now-falsely-green state. The blast radius is every stack hosted on the same Shipit instance, since the lookup is entirely un-scoped by repository - i.e., cross-tenant across the whole install, not limited to repos in the same GitHub org as the attacker (the attacker only needs their own org's app installation to get a validly-signed webhook accepted at all; the `sha` they choose can target any commit row in the database).

### Likelihood Explanation
Preconditions: (1) the attacker needs write/push access to at least one repository whose GitHub organization has the Shipit GitHub App installed (a normal, low-privilege capability for any contributor with push access to their own fork/repo in that org); (2) they need to know the victim's exact commit sha and the specific blocking context string, both of which are typically discoverable via the victim's public GitHub commit history and Shipit's own (often internally-visible) stack/status pages or `shipit.yml`; (3) GitHub's Statuses API must accept a `sha` value that is not part of the calling repository's own history (a documented quirk of GitHub's API, not something this analysis can independently verify with certainty from this codebase alone - flagged as an assumption). No Shipit secrets, sessions, or API tokens are required; the attacker never needs `webhook_secret`, `api_clients_secret`, or any GitHub App private key. This is repeatable at will against any stack/commit whose sha and context are known.

### Recommendation
Scope `StatusHandler#process` the same way as every other handler: require `repository.full_name` in the params schema, resolve `stacks` via `Handler#stacks`/`Repository.from_github_repo_name`, and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) before calling `create_status_from_github!`, so a status webhook can only ever mutate commits belonging to the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb`, no live GitHub):
```ruby
test "a status payload naming an unrelated repository must not mutate another stack's commit" do
  victim_stack = shipit_stacks(:shipit)          # e.g. repo "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)      # different repository entirely

  blocking_ctx = 'soc/compliance'
  victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => [blocking_ctx] }))

  oldest = victim_stack.commits.create!(sha: 'a' * 40, author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
  newer  = victim_stack.commits.create!(sha: 'b' * 40, author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
  oldest.statuses.create!(stack_id: victim_stack.id, state: 'failure', context: blocking_ctx)

  assert_predicate newer, :blocked?   # LHS of binding: victim's own commit is blocked pre-attack

  forged_payload = { 'sha' => oldest.sha, 'state' => 'success', 'context' => blocking_ctx,
                      'repository' => { 'full_name' => attacker_stack.repository.github_repo_name,
                                         'owner' => { 'login' => attacker_stack.repository.owner } } }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  refute_predicate newer.reload, :blocked?  # binding broken: attacker's payload flips victim's stack state
end
```
Assert the equality both ways: before the call, `newer.blocked? == true` (commits mutated belong only to `victim_stack`); after the forged call from `attacker_stack`'s payload, `newer.blocked? == false`, proving the set of mutated commits is not restricted to the webhook's own authenticated repository, i.e. the binding `{mutated commits} == {commits owned by repository in payload}` is false.
