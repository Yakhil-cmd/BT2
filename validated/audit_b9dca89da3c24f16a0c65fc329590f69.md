### Title
Cross-repo forged CI status chained into `Shipit::ProcessMergeRequestsJob` triggers an unauthorized merge decision - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` to any `Commit` matching a given `sha` without verifying that the `sha` belongs to the same repository that authenticated the webhook. Because `Commit#add_status` schedules `ProcessMergeRequestsJob` on success/pending transitions, and `MergeRequest#all_status_checks_passed?` reads directly off the commit's statuses, a forged "success" status delivered by an attacker-controlled repository (in an org already onboarded to this Shipit instance) can flip a victim stack's queued `MergeRequest` to mergeable and cause `merge!` to be invoked.

### Finding Description
**Broken binding:** `Status.stack_id` (and therefore the stack whose merge-queue is influenced) should equal the stack derived from `payload.dig('repository','full_name')` — the repository that GitHub authenticated the webhook for. Instead:

- `WebhooksController#verify_signature` authenticates only that the payload's `repository.owner.login` org has a valid HMAC signature for *that org's* `webhook_secret` [1](#0-0) . It says nothing about which specific commit/stack the payload is allowed to mutate.
- `Handler` (the base class every other handler uses) exposes a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` [2](#0-1) .
- `StatusHandler#process` does **not** use that scoping. It queries `Commit.where(sha: params.sha)` across the entire `commits` table (only indexed on `[stack_id, sha]`, not unique per `sha`, per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository the webhook payload claims to be from [3](#0-2) .
- `Status.after_commit :schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`/`add_status` calls `stack.schedule_merges if new_status.pending? || new_status.success?` [4](#0-3) , enqueuing `ProcessMergeRequestsJob` for the **victim's** stack (the stack owning the matched commit), not the attacker's.
- `ProcessMergeRequestsJob#perform` iterates `stack.merge_requests.to_be_merged`, calls `merge_request.all_status_checks_passed?`, and if true calls `merge_request.merge!` [5](#0-4) .
- `MergeRequest#all_status_checks_passed?` builds a `StatusChecker` from `head.statuses_and_check_runs` [6](#0-5)  — i.e., it directly reflects whatever `Status` rows exist on the head commit, including the forged one just written.
- `MergeRequest#merge!` then calls `stack.github_api.merge_pull_request(...)` using Shipit's own privileged GitHub App credentials for the victim's org [7](#0-6) .

**Exploit flow:** because Git commit SHAs are content-addressed and shared between a public repo and any fork of it, an attacker who forks (or otherwise controls) a repository within an org that already has Shipit's GitHub App installed can watch a victim's PR, note its head commit sha, and use the GitHub Statuses API (`POST /repos/{attacker}/{repo}/statuses/{sha}`) on their own repo/fork to create a `success` status for that exact sha. GitHub delivers a genuinely-signed `status` webhook to Shipit — signed with the org's real `webhook_secret`, so `verify_signature` passes — but the `repository` field in the payload is the attacker's repo, not the victim's. `StatusHandler#process` ignores that field entirely and applies the forged status to the victim's tracked `Commit`, activating the merge queue chain described above.

**Why existing guards fail:** `verify_signature` authenticates the org, not the specific repository-to-commit binding; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape (`sha`, `state`, etc.), not repository ownership of the sha; and unlike every other handler, `StatusHandler` bypasses the `Handler#stacks` repository-scoping helper.

### Impact Explanation
An attacker with write access to any repository within an org already onboarded to a given Shipit deployment can forge a CI "success" outcome for an arbitrary tracked commit in a *different* repository of that org, and drive that repository's merge queue to invoke a real `merge_pull_request` call using Shipit's privileged GitHub App token. This is "a payload for one repository mutating another's stack, commit... or an unauthorized merge," explicitly listed as Critical. The attack is repeatable against any repository/stack in the same org whose commit shas the attacker can predict (any public/forkable PR).

### Likelihood Explanation
Preconditions: (1) the target Shipit instance must have the GitHub App installed org-wide (a very common configuration, since `Shipit.github` config is keyed by organization, not repo) so webhooks from *any* repo in that org reach Shipit and are validly signed; (2) the attacker must be able to create/fork a repository within that org (many orgs allow member repo creation or public forking) and use the Statuses API on it (requires only push access to their own repo, not org admin); (3) a victim `MergeRequest` must be queued (`pending`) with CI otherwise satisfiable. No Shipit secret, session, or API token is needed. Cost is a single unauthenticated GitHub API call plus watching public PR activity — cheap and repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the requesting repository, mirroring every other handler's use of `Handler#stacks`, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or otherwise verify `commit.stack.repository` matches `payload.dig('repository','full_name')` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from an unrelated repository forges a status onto a victim commit and unlocks its merge queue" do
  victim_stack = shipit_stacks(:shipit) # e.g. github_repo_name == "shopify/shipit-engine"
  victim_commit = shipit_commits(:some_pending_head)
  merge_request = shipit_merge_requests(:pending_queued)
  merge_request.update!(head: victim_commit, merge_status: 'pending')

  refute merge_request.all_status_checks_passed?

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker-forged',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)
  end

  merge_request.reload
  assert merge_request.all_status_checks_passed?, "victim MergeRequest wrongly unlocked by a status from attacker-org/unrelated-repo"
end
```
Binding validated: `victim_commit.stack.repository.full_name` (`"shopify/shipit-engine"`) != `forged_payload['repository']['full_name']` (`"attacker-org/unrelated-repo"`), yet `commit.create_status_from_github!` and the subsequent `all_status_checks_passed?` proceed identically to a legitimate same-repo status, confirming the divergence.
