### Title
ERC20Transactor credits/debits the requested amount instead of the ERC20 contract's actual transferred amount, breaking on fee-on-transfer / non-standard ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (used by Asset Hub Westend's XCM configuration to let XCM `WithdrawAsset`/`DepositAsset` move Solidity ERC20 tokens deployed on `pallet_revive`) never verifies that the amount actually moved by the underlying ERC20 `transfer()` call matches the amount it credits into the XCM holding register (on withdraw) or the amount it instructs the checking account to send (on deposit). Because ERC20 contracts are fully attacker-controlled user code (any account can deploy arbitrary Solidity/bytecode via `pallet_revive::bare_instantiate`), a fee-on-transfer (or otherwise non-standard) ERC20 causes the same class of bug described in the BendDAO finding: the accounted amount and the real balance-transfer diverge, but here — unlike BendDAO's explicit `require` — there is *no* verification at all, so the mismatch propagates silently into the XCM holding/deposit machinery and results in deterministic failure/fund-lockup for that asset class rather than an explicit revert-with-message.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` ( [1](#0-0) ) withdraws tokens by calling the ERC20 contract's `transfer(checking_address, amount)` from the user's own account. It only checks whether the Solidity call reverted or whether the ABI-decoded boolean return was `true`; it never re-reads `balanceOf(checking_account)` before/after to measure what actually moved: [2](#0-1) 

On success it unconditionally credits the **requested** `amount` into the XCM holding register via `Erc20Credit(amount)` — a bespoke imbalance type that performs no runtime-level balance enforcement (its own doc comment states this explicitly): [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` takes the amount recorded in the XCM holding (which is whatever was credited on withdraw) and asks the checking account to `transfer(beneficiary, amount)` — again only checking revert/bool result, not verifying the checking account's real balance delta: [4](#0-3) 

If the ERC20 contract being transacted takes a transfer fee (or is a rebasing/reflection token that delivers less than the nominal `value`), then:
- On withdraw, the checking account's real ERC20 balance increases by `amount - fee`, but the XCM holding register is credited with the full `amount`.
- The XCM executor and any subsequent `DepositAsset` will operate on the inflated holding amount (`amount`), not the smaller amount actually received.
- On deposit, the transactor asks the checking account's contract to `transfer(beneficiary, amount)`, but the checking account's real balance for that asset is smaller than `amount` (further reduced by fees accumulated from earlier legitimate uses of the same fee-on-transfer token). This transfer either reverts due to insufficient balance (`return_value.did_revert()` or `is_success == false`) — producing `XcmError::FailedToTransactAsset`, mirroring the "keeps reverting" behavior of the original BendDAO finding — or, for tokens that don't revert on insufficient balance but instead silently transfer less, the shortfall is compounded across every future user of that token, permanently under-delivering to legitimate beneficiaries while the checking account's tracked/implied balance for that asset drifts inconsistent with its real on-chain ERC20 balance.

The reachable, attacker-controlled entry point is fully permissionless:
1. Any signed account can deploy an arbitrary ERC20 contract through `pallet_revive`'s permitted `instantiate`/`bare_instantiate` path (demonstrated in the repo's own test `withdraw_and_deposit_erc20s`, which deploys a `MyToken` contract and drives it through `pallet_xcm::execute`) — [5](#0-4) .
2. The attacker's contract can freely implement a fee-on-transfer `transfer()` (e.g. burn/skim a percentage on every transfer), since `pallet_revive` executes arbitrary bytecode with no restriction on token semantics.
3. Any signed account can then submit a normal `pallet_xcm::execute` (or `transfer_assets`) extrinsic referencing that ERC20 by its `AccountKey20` location, going through `ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` exactly as in the existing test.

No governance, privileged origin, malicious validator/collator, or forged inherent is required — this is a plain signed extrinsic combined with a self-deployed contract, satisfying the "real user entry" requirement.

### Impact Explanation
For any ERC20 asset with a transfer fee or non-1:1 transfer semantics that is used through `ERC20Transactor`:
- XCM messages moving that asset become unreliable/deterministically fail once the checking account's real balance for that asset falls behind the amounts the holding register believes it holds — a chain-level DoS specific to that asset (mirroring the original "keeps reverting" impact), and
- Because the checking account is a single shared pot per asset for *all* users of that ERC20 through XCM, a fee-on-transfer token used by multiple parties will progressively desynchronize the checking account's real balance from the sum of amounts credited to various XCM holdings, which can strand (temporarily or permanently) legitimately deposited ERC20 balances that are owed to good-faith beneficiaries.

This does not constitute unbacked issuance of the chain's native token or unauthorized dispatch, and it requires the affected ERC20 to itself implement non-standard transfer semantics; it is asset-scoped rather than protocol-wide. This most closely matches a **Medium** severity, consistent with how the original report was rated, since the affected functionality (XCM ERC20 transfers) becomes unusable/inconsistent for a whole (attacker choosable) class of tokens, but no direct theft of the chain's core assets/DOT/KSM issuance is demonstrated.

### Likelihood Explanation
Likelihood is high in the sense that deploying a fee-on-transfer ERC20 via `pallet_revive` requires no special privilege and is a normal, expected usage pattern for real-world tokens (fee-on-transfer tokens are common in the wild); the existing repo test suite already demonstrates the full withdraw/deposit ERC20 XCM path is reachable via a plain signed extrinsic. However, actually landing on Asset Hub's production `ERC20TransfersCheckingAccount` configuration and reproducing measurable value loss (versus just a failed/trapped instruction) needs the checking account's balance for the specific ERC20 to be exhausted, which depends on usage volume/order — this was not verified end-to-end against a running node.

### Recommendation
In `withdraw_asset_with_surplus`, read `balanceOf(checking_account)` before and after the `transfer` call (or use the ERC20's own `Transfer` event/return semantics where reliable) and credit the holding with the *actual* delta rather than the requested `amount`. In `deposit_asset_with_surplus`, use the same actual-delta measurement on the beneficiary's balance instead of trusting the boolean return value, and fail (returning the un-deposited remainder to holding, as the executor's existing "partial deposit failure" trap machinery supports) rather than assuming success. Alternatively, explicitly document (and, if desired, deny at asset-registration time) that `ERC20Transactor` only supports strictly-1:1, non-fee, non-rebasing ERC20 tokens, and add validation (e.g., a canary transfer/balance check at asset registration) to reject non-conforming contracts before they're wired into XCM.

### Proof of Concept
Not executed against a live node/test harness; the reasoning is based on static code inspection of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and the existing integration test `withdraw_and_deposit_erc20s` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`, which shows the exact reachable path (signed `pallet_xcm::execute` withdrawing/depositing a user-deployed ERC20 via `AccountKey20`). A concrete reproduction would:
1. Deploy a modified `MyToken`-style Solidity contract (as used in the existing test fixture) whose `transfer()` implementation burns/withholds e.g. 1% of `value` before crediting the recipient.
2. Fund the sender and the `ERC20TransfersCheckingAccount`, then submit the same `Xcm::builder()` sequence as `withdraw_and_deposit_erc20s` (`withdraw_asset` for the fee-on-transfer ERC20 + `deposit_asset` to a beneficiary).
3. Assert that `beneficiary_amount` (`<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary)`) is less than `erc20_transfer_amount`, or that the deposit instruction fails/traps once the checking account's real balance is insufficient to cover the full credited `amount` — demonstrating the accounting mismatch predicted above.

I was not able to execute this PoC in this environment (no code-execution access), so failed-guard / deployment evidence beyond the static code reading above is not available; this should be verified by a background agent with access to `cargo test -p asset-hub-westend-runtime` and the ability to compile a custom fee-on-transfer fixture contract.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

			target: "xcm::transactor::erc20::deposit",

		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());

			Some(inner) => inner,

		};

			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),

		// We do this using the solidity ERC20 interface.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
