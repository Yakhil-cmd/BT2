### Title
Cross-organization webhook signature confusion allows unauthenticated write to another organization's `PullRequest`/`Commit` records via `pull_request` `unassigned` events - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the signing secret using `repository.owner.login` while every handler, including `AssignedHandler`, resolves the affected repository/stack using the unrelated `repository.full_name` field. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no configured `webhook_secret`, an attacker can authenticate a forged webhook under a no-secret org while making it mutate a *different* org's stack data.

### Finding Description
The broken binding is the implicit assumption:
`repository_owner (used to select signing secret) == owner(repository.full_name) (used by handlers to resolve the mutated repository)`

In `verify_signature`: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
```
`repository_owner` is read from `params.dig('repository', 'owner', 'login')`: [2](#0-1) 

Yet `AssignedHandler` (and every other `pull_request` handler) resolves the repository from a completely different field, `params.repository.full_name`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally passes when the selected org has no secret configured: [4](#0-3) 

This is a documented, supported configuration in multi-org deployments — the repo's own example configs ship with `webhook_secret: # nil` per-org: [5](#0-4) [6](#0-5) 

Exploit flow: attacker crafts a `pull_request` webhook body with `action: "unassigned"`, sets `repository.owner.login` to `NoSecretOrg` (a Shipit-configured org with no `webhook_secret`), but sets `repository.full_name` to `VictimOrg/victim-repo` (the real, secret-protected org whose stack the attacker wants to hit). `verify_signature` calls `Shipit.github(organization: "NoSecretOrg")`, whose `verify_webhook_signature` returns `true` unconditionally — no valid HMAC, or even a well-formed `X-Hub-Signature` header value, is required for the request to pass. The request then reaches `WebhooksController#create`, which dispatches to `AssignedHandler`, which looks up the `Shipit::Repository`/`PullRequest` via `params.repository.full_name` = `VictimOrg/victim-repo`, and calls: [7](#0-6) 
`pull_request.update(github_pull_request: params.pull_request)` writes attacker-controlled `title`, `state`, `additions`, `deletions`, `assignees`, `labels`, and — via `github_pull_request=` — `head`, into the victim repository's `PullRequest` record: [8](#0-7) 
Critically, `head=` calls `find_or_create_commit_from_github_by_sha!`, which, for an unseen SHA, fetches that commit from the *victim's real GitHub repo* via `stack.github_api.commit` and persists a new `Commit` row for the victim's stack: [9](#0-8) 

No code checks that `repository.owner.login` matches the owner segment of `repository.full_name`; `drop_unhandled_event`, `ExplicitParameters` schema validation (which only requires `full_name` to be a String), and model validations do not enforce this equality either.

### Impact Explanation
This is an unauthenticated cross-tenant write: a request that authenticates against org A's (no-secret) signing key is used to mutate persisted state (`PullRequest`, and potentially newly created `Commit` rows) belonging to org B's stack, which the attacker never authenticated against. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Because `find_or_create_commit_from_github_by_sha!` fetches and registers arbitrary-but-real commits from the victim repo into the stack's commit history, and the target stack has `continuous_deployment` enabled, once that commit's CI/status is (or becomes) green, the existing `ContinuousDeliveryJob`/status-driven auto-deploy pipeline can pick it up as a deployable candidate — meaning this write is not merely cosmetic (assignee/labels) but can influence which commit the stack considers for automated deployment. I was not able to fully trace `ContinuousDeliveryJob`'s exact commit-selection logic (`app/jobs/shipit/continuous_delivery_job.rb`) within the remaining tool budget to confirm whether a `PullRequest`-linked `Commit` created this way is guaranteed to be treated as the branch head / deploy candidate, so the "auto-ship" amplification claim should be treated as plausible but not fully verified; the core cross-tenant unauthenticated write, however, is confirmed and is itself Critical-severity. The attack is repeatable against any stack whose owning org's repository owner differs from any no-secret-configured org known to Shipit, across arbitrary numbers of victim repositories in a single multi-org Shipit install.

### Likelihood Explanation
Preconditions: (1) the Shipit instance uses the multi-org GitHub config schema, and (2) at least one configured org has no `webhook_secret` (a state the shipped example/test configs actively demonstrate as normal), and (3) the victim stack/repository is a real, different org registered in the same instance. Given these — which are realistic operational states for multi-tenant Shipit deployments, not exotic edge cases — the attacker cost is a single crafted HTTP POST to `/webhooks` with no valid signature required at all (since `verify_webhook_signature` short-circuits `true`) and no GitHub, Shipit, or repository privileges. This is trivially repeatable and scriptable against every stack in the instance.

### Recommendation
In `WebhooksController#verify_signature`, derive the organization used for signature verification from the same field the handlers use to resolve the repository (`repository.full_name`'s owner segment, or equivalently validate `repository.owner.login == full_name.split('/').first`) and reject the request if they diverge. Additionally, `GitHubApp#verify_webhook_signature` returning `true` for a missing secret should, at minimum, log/alert loudly, and organizations without a configured secret should not be trusted to authenticate webhooks for other organizations' repositories under any circumstance.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.stubs(:secrets)` (or use `test/dummy/config/secrets_double_github_app.yml`) with two orgs: `NoSecretOrg` (`webhook_secret: nil`) and `VictimOrg` (`webhook_secret: "victim-secret"`).
2. Create `victim_repo = Shipit::Repository.create!(owner: 'VictimOrg', name: 'victim-repo')`, a `stack` on it with `continuous_deployment: true`, and a `Shipit::PullRequest` with `number: 42` belonging to that stack.
3. Build a `pull_request` JSON payload with `action: "unassigned"`, `number: 42`, `repository: { owner: { login: "NoSecretOrg" }, full_name: "VictimOrg/victim-repo" }`, and an attacker-chosen `pull_request.head.sha`/`assignees`/`title`.
4. `post shipit.webhooks_path, params: payload.to_json, headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => 'sha1=deadbeef', 'Content-Type' => 'application/json' }` (no valid HMAC).
5. Assert response is `200`/`:ok` (not `422`), proving `verify_signature` passed despite the signature being invalid for `VictimOrg`.
6. Assert `pull_request.reload.title` / `assignees` / `head` now reflect the attacker's payload — i.e., `assert_equal attacker_title, pull_request.reload.title` — demonstrating that a request authenticated (trivially) as `NoSecretOrg` mutated a `PullRequest` record belonging to `VictimOrg`'s stack, violating the invariant that "a `pull_request` event only affects the repository/stack whose secret authenticated it."

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
