### Title
Webhook signature verification authenticates by `repository.owner.login`, but handlers act on the unbound `repository.full_name` field, enabling cross-organization forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-organization Shipit deployment (`Shipit.github(organization:)` keyed by org, see `lib/shipit.rb`), the `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. However, once the signature check passes, the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, and subclasses like `StatusHandler`, `CheckSuiteHandler`, `PushHandler`) resolve the target `Stack`/`Repository`/`Commit` using a *different* field from the same payload: `repository.full_name`. Nothing binds these two fields together, so a signature valid for org A can carry a payload whose `repository.full_name` points at org B's repository.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` reads `repository.owner.login` (or falls back to `organization.login`). This determines *whose* `webhook_secret` authenticates the raw POST body [8](#0-7) [2](#0-1) .

`GitHubApp#verify_webhook_signature` only proves that the raw body was HMAC-signed with the secret associated with `repository_owner`'s GitHub App/org — it says nothing about which repository the payload's data should be applied to [7](#0-6) .

Every handler that actually mutates or reads Shipit state, however, keys off a *separate* JSON field, `repository.full_name`, via `Handler#repository_name`/`#stacks` [3](#0-2) , which is resolved into an ActiveRecord `Repository`/`Stack` scope by `Repository.from_github_repo_name` [6](#0-5) . Because `verify_signature` never asserts that `repository.owner.login == repository.full_name`'s owner segment, an attacker who legitimately controls their own GitHub organization ("org-A") — and therefore knows/configures its own `webhook_secret` in Shipit's multi-org `github:` config — can send a POST to `/webhooks` where:
- `X-Github-Event: status` (or `check_suite`, or `push`)
- `X-Hub-Signature` computed with org-A's own `webhook_secret` over the full raw body
- `repository.owner.login = "org-A"` (so `verify_signature` looks up and validates against org-A's secret — passes)
- `repository.full_name = "org-B/victim-repo"` (a repository the attacker does not own)

`verify_signature` passes because it only checked that org-A's secret matches, but `StatusHandler#process` / `CheckSuiteHandler#process` then act on commits/stacks belonging to `org-B/victim-repo`, entirely unrelated to the authenticating organization [4](#0-3) [5](#0-4) .

This breaks the trust binding "an organization that authenticated versus the repository that is written": the code implicitly assumes `repository.owner.login` used for auth and `repository.full_name` used for the write refer to the same repository, but nothing enforces this equality.

### Impact Explanation
Using the `status` event, an attacker can forge arbitrary commit statuses (`state`, `context`, `target_url`, `description`) against any commit SHA already known/tracked in a victim stack (`Commit.where(sha: params.sha)` in `StatusHandler#process`), which can flip a required CI status to `success` and unblock/trigger an unauthorized deploy or merge for a repository/organization the attacker does not control. Using `check_suite`, the attacker can force `RefreshCheckRunsJob` on a victim's commits. Using `push`, the attacker can trigger `GithubSyncJob`/`sync_github` against a victim stack. This satisfies the "unauthorized deploy" / "cross-repository writes" Critical impact bar, since data attributable to org-A's authenticated webhook is written into org-B's tracked repository state.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with the multi-organization `github:` schema (`lib/shipit.rb#github_app_config`, documented in `docs/setup.md`), and (2) the attacker's own organization ("org-A") to be one of the configured organizations with the app installed, so the attacker legitimately knows/controls org-A's `webhook_secret` (this is normal, unprivileged knowledge of their own app configuration, not a compromise of Shipit's own secrets). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only the ability to author a raw HTTP POST to the public `/webhooks` endpoint with a signature computed from a secret the attacker legitimately possesses for their own org.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the GitHub App/secret via `repository_owner`, cross-check that the same `repository_owner` matches the owner encoded in `repository.full_name` (and reject if they diverge) before dispatching to handlers. Alternatively, have handlers derive the repository/stack scope from the already-authenticated `repository_owner` rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (multi-org config as in `docs/setup.md`).
2. As the legitimate owner of `org-a`'s GitHub App, compute `sha1=HMAC(org-a_webhook_secret, body)` for a crafted body:
```json
{
  "sha": "<victim commit sha tracked under org-b/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully against the attacker's own secret.
5. `StatusHandler#process` finds `Commit.where(sha: ...)` under `org-b/victim-repo` (found via `full_name`, independent of `org-a`) and creates a forged "success" status, potentially satisfying `Stack` deploy/merge gating for a repository the attacker never authenticated for.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
