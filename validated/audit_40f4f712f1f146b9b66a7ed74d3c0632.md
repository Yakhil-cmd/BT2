### Title
CCMenu API endpoint uses an unscoped `Stack.from_param!` lookup, letting a stack-scoped ApiClient token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to call `Stack.from_param!(params[:stack_id])` directly, instead of using the stack-scoped lookup (`stacks.from_param!`) defined in `Shipit::Api::BaseController`. This breaks the trust binding "the stack a token authorises == the stack it touches."

### Finding Description
`Shipit::Api::BaseController` implements two levels of protection for stack-scoped `ApiClient` tokens:
1. `require_permission :read, :stack` / `:write, :stack` etc., which checks the token's `permissions` array via `ApiClient#check_permissions!`.
2. Stack scoping via `stacks`/`stack`: [1](#0-0) 
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
An `ApiClient` created with a `stack_id` (e.g. `here_come_the_walrus` fixture) is meant to be restricted to that single stack — `ApiClient#stack_id?` gates the `Stack.where(id: ...)` scope, and every controller that calls the inherited `stack` helper (e.g. `Api::DeploysController`, `Api::TasksController`, `Api::StacksController#show`) is correctly restricted to that one stack because `from_param!` is called on the pre-scoped `stacks` relation.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
`require_permission :read, :stack` still runs, but it only checks that the token has the `read:stack` permission string in its `permissions` array — it does not check which stack the token is bound to (that check lives entirely in the `stacks`/`stack` scoping helper that `CCMenuController` deliberately overrides). Because `Stack.from_param!` here queries the entire `Stack` table unconditionally, any token carrying `read:stack` — including one created via `Shipit::CCMenuUrlController#client`, which is minted with exactly `permissions: %w[read:stack]` and no `stack_id` restriction for the *requesting* stack's page, or any other stack-scoped token that happens to have `read:stack` — can be replayed against an arbitrary `stack_id` value and will resolve any stack in the installation, not just the one it was authorized/generated for.

This exactly mirrors the analog's bug class: a value that is *checked* (permission string `read:stack`) is disconnected from the value that is *actually authorized-and-enforced* (the specific `stack_id` binding), just as in the Notional bug where the amount authorized to be redeemed (`vaultShares`) was disconnected from the code path that enforced a nonzero-claim invariant.

### Impact Explanation
This is an unauthorized cross-stack read: a token that a user, hook, or CI system uses to fetch CCMenu status of one authorized stack can be used to enumerate/read the build/deploy status (latest deploy id, running/success/failure state, timestamps) of every other stack in the Shipit installation, including stacks belonging to different repositories/teams the token holder should not have visibility into. This matches the "unauthenticated (unauthorized) read of stack state" High-severity class in the rules (escalation into stack-level authorization is bypassed by any `read:stack`-scoped credential regardless of its intended `stack_id` binding).

### Likelihood Explanation
Likelihood is high for any deployment that issues `read:stack`-scoped tokens (which is a normal, documented feature — e.g., the CCMenu integration itself, via `Shipit::CCMenuUrlController#client`, mints exactly this permission set). No additional privilege, GitHub credential, or repository write access is needed beyond possession of any valid, minimally-scoped API token — this is well within the unprivileged-attacker footprint (a leaked or intentionally narrow-scoped CCMenu token is expected to be shared/embedded in CI dashboards).

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the inherited, properly scoped lookup instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
or simply remove the private `stack` override entirely so the `BaseController#stack` (which uses `stacks.from_param!`) is used. This restores the binding that `stack_id`-scoped tokens can only resolve the stack they were issued for.

### Proof of Concept
1. Create (or observe) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (this is exactly what `Shipit::CCMenuUrlController#client` produces for every visitor of a stack's CCMenu link): [3](#0-2) 
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
2. Using that token (`?token=<authentication_token>`), request `GET /api/stacks/B/ccmenu.xml` where `B` is a different stack the token was never scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping), the request succeeds and returns stack `B`'s deploy status, even though the token's `ApiClient#stack_id` field ties it to stack `A`.
4. Compare with `Api::StacksController#show` or `Api::DeploysController#index` using the same token against stack `B`: those correctly 404/403 because they use the inherited `stack`/`stacks` helpers that apply `Stack.where(id: current_api_client.stack_id)` scoping.
