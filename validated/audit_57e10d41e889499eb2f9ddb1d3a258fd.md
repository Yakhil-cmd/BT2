### Title
Webhook signature is verified against the payload's organization, but `StatusHandler`/`PushHandler` act on a different, unbound field of the same payload, allowing cross-organization commit-status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects **which GitHub App's webhook secret to use for HMAC verification** based on `repository_owner`, a field read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Once the signature checks out, the request is dispatched to handlers (`StatusHandler`, `PushHandler`, etc.) that act on **other, independent fields of the same payload** without re-checking that those fields belong to the organization whose secret was used to authenticate the request. In `StatusHandler` in particular, the target `Commit` is selected purely by `sha`, with no repository/organization scoping at all.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Shipit explicitly supports **multiple GitHub Apps, one per organization**, each with its own `webhook_secret` (`docs/setup.md`, "Using Multiple Github Applications"). The secret used to verify a given delivery is chosen dynamically from the attacker-controlled `repository_owner` field of the body being verified.

Once `verify_signature` passes, `WebhooksController#create` dispatches unconditionally:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

`StatusHandler#process` resolves its write target purely by commit SHA, with **no reference at all to `repository_owner` or `repository.full_name`**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

The equality the system implicitly assumes but never enforces:
`organization authenticated by verify_signature (repository_owner)` == `organization owning the Commit/Stack mutated by the handler`.

Because `repository_owner` and the field actually acted upon (`sha` for status events, `repository.full_name` for push events, resolved in `Handler#repository_name`) are both attacker-supplied fields of the *same* JSON body, an organization that legitimately owns a GitHub App installation on this Shipit instance (and therefore knows its own `webhook_secret`) can freely choose `repository_owner = "own-org"` (to pick its own secret and pass HMAC verification) while setting the SHA (or `repository.full_name`) to reference an entity belonging to a **different** organization/stack hosted on the same instance.

`Handler#repository_name`/`#stacks` show the same disconnect for push events:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Before the pull request/deployment: `verify_signature` and the handler's mutation target are both scoped, in the developer's intent, to the same organization — the one that owns the secret.
After a malicious sequence: `repository_owner` picks OrgA's secret (attacker's own, legitimately obtained), but `sha`/`repository.full_name` reference OrgB's commit/stack — the binding between "who authenticated" and "what got written" is broken.

### Impact Explanation
An attacker who administers their own onboarded GitHub organization on a multi-org Shipit deployment (a normal, unprivileged, documented configuration — `docs/setup.md` "Using Multiple Github Applications") can:
- Forge a `status` webhook, signed with their own org's `webhook_secret`, that creates a passing/green `Status` on a commit belonging to a **different organization's stack**. Since CI statuses (`commit.create_status_from_github!`) are used by Shipit to gate the merge queue and continuous deployment (`ci`/`review.checklist`/`merge` logic), this can make Shipit believe a foreign commit has passed CI it never actually ran, enabling an **unauthorized deploy or merge** of code the attacker does not control on the target org's repository. This matches the Critical bar: "cross-repository writes, or an unauthorized deploy, rollback or merge."
- Similarly abuse `push` to trigger `stack.sync_github` on a foreign stack (lower severity, but same broken binding).

### Likelihood Explanation
Requires only that the attacker legitimately controls one organization/GitHub App already installed and configured in the same multi-org Shipit instance — no privileged Shipit account, `ApiClient` token, or session is needed, since this path is entirely unauthenticated apart from the (attacker-known) webhook secret of their own org. Multi-org configuration is explicitly documented and supported, so this is a realistic deployment topology, not a hypothetical one.

### Recommendation
- Re-derive/re-validate the organization/repository actually referenced by each handler (`sha`'s owning `Stack`/`Repository`, or `repository.full_name`) against the same `repository_owner`/organization that was used to select the verifying secret, and reject mismatches.
- In `StatusHandler`, scope the `Commit` lookup by the stack's repository/organization, not by `sha` alone.
- Consider verifying against all configured webhook secrets is too aggressive; instead bind the authenticated organization to the resource being mutated end-to-end.

### Proof of Concept
1. Attacker administers "OrgA", which has a GitHub App installed on this Shipit instance with `webhook_secret = S_A` (per `docs/setup.md` multi-org config), a legitimate, unprivileged setup.
2. Attacker crafts a `status` event body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/whatever"},
  "sha": "<sha of a commit belonging to OrgB's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` — trivial since they own `S_A`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, verifies successfully against `S_A`. [5](#0-4) 
5. `StatusHandler#process` runs `Commit.where(sha: <OrgB's sha>)` and calls `create_status_from_github!`, writing a success status onto OrgB's commit despite the request never being authenticated for OrgB. [3](#0-2) 
6. If OrgB's merge queue/deploy gating relies on that CI context, the forged status can unblock an unauthorized merge/deploy for OrgB's stack.
