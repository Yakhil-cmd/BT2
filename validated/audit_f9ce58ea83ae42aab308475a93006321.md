Found the analog. `Shipit::Api::CCMenuController` overrides `authenticate_api_client` to authenticate purely by a `token` query parameter, and separately overrides `stack` to look the stack up unscoped via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping method (`BaseController#stacks`) used everywhere else in the API to enforce `current_api_client.stack_id?`.

### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`BaseController#stacks` is the enforcement point that binds an `ApiClient`'s authorized stack (`ApiClient#stack_id`) to the stacks it can act on: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . Every other API controller (`Api::DeploysController`, `Api::TasksController`, `Api::LocksController`, `Api::HooksController`, etc.) resolves the target `Stack` through this scoped `stack`/`stacks` helper defined in `BaseController` [2](#0-1) . `Api::CCMenuController`, however, defines its own private `stack` method that resolves the stack directly via `Stack.from_param!(params[:stack_id])`, with no reference to `current_api_client.stack_id` at all [3](#0-2) .

### Finding Description
The binding this breaks, expressed as an equality that should hold but doesn't:

`stack a token is authorized for` (`ApiClient#stack_id`) `== stack the request actually touches` (`params[:stack_id]` resolved by `Stack.from_param!`).

`ApiClient.stack_id` is meant to scope a client's token to a single stack — this is exactly how the app itself mints scoped tokens: `CcmenuController` (the session-authenticated, non-API controller) creates a stack-scoped `ApiClient` for a user and hands out a URL containing that client's `authentication_token`, intending the token to only ever be usable for that one stack's CCMenu feed. This is confirmed by the test suite: `":fetch creates a read only api client"` and `":fetch url includes api token on query string"` in `test/controllers/ccmenu_controller_test.rb`.

That minted token is then presented to `Api::CCMenuController#show`, which authenticates it via `ApiClient.authenticate(params[:token])` [4](#0-3)  — so far correct, the signature over the token is verified. But the controller then loads the target stack with `Stack.from_param!(params[:stack_id])` instead of the inherited `stacks.from_param!`/`stack` helper that all sibling API controllers use [3](#0-2) , and `require_permission :read, :stack` only checks the client's `permissions` array (e.g. `"read:stack"`), never the `stack_id` scope [5](#0-4) .

Consequently, a token that GitHub's Shopify org member believes/expects is bound to stack A (because it was minted for stack A's CCMenu URL) is honored by the controller for any `stack_id` supplied in the URL, as long as the token carries `read:stack` permission — which every CCMenu-issued token does by construction.

### Impact Explanation
This is an unauthenticated-scope-widening read: presenting a legitimately obtained, low-privilege, single-stack CCMenu token against a *different* `stack_id` yields that other stack's latest deploy/rollback status (`deploys_and_rollbacks.last`) rendered as XML, i.e. unauthorized read of stack/task state for stacks the token holder was never meant to see — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact category. It does not grant write access (the CCMenu client's permission set is read-only), but it defeats the intended per-stack isolation that `ApiClient.stack_id` exists to provide.

### Likelihood Explanation
High likelihood in any Shipit deployment that uses the CCMenu feature: obtaining one CCMenu URL (e.g. from a CI dashboard, a build monitor, or a leaked bookmark for one's own stack) is sufficient; the attacker only needs to substitute a different numeric/slug `stack_id` in the path — no privileged credentials, GitHub App keys, or session are required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Remove `Api::CCMenuController`'s custom `stack` override and use the inherited scoped `stacks`/`stack` resolution from `BaseController` so `current_api_client.stack_id` is enforced consistently, i.e. resolve via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`.

### Proof of Concept
1. As an authenticated user, visit any stack's CCMenu endpoint (`GET /stacks/:owner/:repo/:env/ccmenu.xml`) to have `Shipit::CcmenuUrlController#fetch` mint a stack-A-scoped `ApiClient` and return a URL of the form `.../api/.../ccmenu?token=<A-scoped-token>`.
2. Take that `token` value and issue `GET /api/stacks/<stack-B-id>/ccmenu?token=<A-scoped-token>` where stack B is an unrelated stack the attacker was never granted.
3. `Api::CCMenuController#authenticate_api_client` verifies the token signature successfully (it's a valid, unexpired `ApiClient` id), then `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stack_id` scope check, and `show` renders stack B's latest deploy/rollback status. # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
