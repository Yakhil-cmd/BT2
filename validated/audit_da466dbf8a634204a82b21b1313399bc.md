### Title
Capped-asset double issuance within a single AA-composed unit due to stale "already issued" check - (File: aa_composer.js)

### Summary
The `pokeTokens` bug class in the original report — two accrual code paths (`reset()` and `poke()`) each independently deciding "not yet accrued" and both crediting FLUX — has a structural analog in `aa_composer.js`'s `issueAsset()` routine used when an Autonomous Agent (AA) needs to self-issue units of a capped asset it defines. The guard that is supposed to enforce "issue only once for a capped asset" checks the `inputs` table in the database, which is not updated until the unit is fully composed and saved. If the AA's response unit requires more than one payment message denominated in the same capped asset (e.g., two separate `payment` messages that both fall short of funds and independently trigger `issueAsset()`), each invocation queries the same stale DB state and each concludes the asset "has not been issued yet," letting both proceed to add an `issue` input — inflating the capped asset's supply beyond its declared `cap`.

### Finding Description
`aa_composer.js` builds payment messages for an AA response via `completePaymentPayload()`. When the AA's own address doesn't have enough of `asset` to satisfy `target_amount`, and the asset is capped and issuable, the composer calls `issueAsset()`: [1](#0-0) 

The "already issued" guard is:
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
```
This check only sees `issue` inputs that are already persisted in the `inputs` table. The `input` object created by `addIssueInput()` is only pushed into the in-memory `payload.inputs` array of the *current* payment message and is **not written to the DB** until the whole unit is validated and saved via `validateAndSaveUnit()`, much later in the flow: [2](#0-1) 

If a single AA execution needs to build **more than one payment message in the same capped asset** — which can happen when an AA definition emits multiple `payment` messages for the same asset (e.g., paying two different sets of recipients, or paying recipients plus a fee/refund message) and the AA's existing balance is insufficient for both — `completePaymentPayload()`/`issueAsset()` is invoked once per message. Each invocation re-runs the identical `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` query against the database, which has not yet been updated by the sibling message's issuance (that issuance still lives only in the unsaved `payload.inputs` of the other message object). Consequently, both invocations see "not issued yet" and both call `addIssueInput(1)`, adding two `issue` inputs of `objAsset.cap` amount each for the same capped asset within one unit — doubling the capped asset's total supply the moment this unit is persisted.

This is functionally identical to the reported issue: two accrual/issuance code paths, gated by a check of pre-action state that does not account for a sibling action already scheduled (but not yet committed) within the same top-level operation, resulting in the guarded action executing twice.

### Impact Explanation
A capped asset's cap is a supply-inflation invariant enforced solely by this "issued only once" check. Doubling issuance within a single unit breaks that invariant permanently and irreversibly once the unit is stabilized, since `validation.js`'s divisible-issue double-spend check only prevents the *same* serial number/asset combination from being spent twice across *different* units — it does not prevent two issue inputs for the same capped asset serial number 1 occurring together in one unit's separate messages, because uniqueness is enforced per `(asset, denomination, address, serial_number)` key and both issuances would use `serial_number=1` for `objAsset.cap` capped assets, which validation.js requires: [3](#0-2) 

Two issue inputs with the same `(asset, serial_number=1)` in the same unit would in fact collide on `objValidationState.arrInputKeys`, so this exact "two issue inputs in one unit" scenario would likely be rejected by unit-level validation — **this is an important caveat**: `validation.js:2356-2359` tracks `arrInputKeys` per unit and would flag a duplicate `asset-denomination-address-serial_number` key. This significantly weakens (or may fully block) the practical exploitability of the analog as stated, and I was not able to fully verify within the available search budget whether AA-composed units always route through this same `arrInputKeys` collision check before being finalized, or whether some AA-specific fast path (`validateAndSaveUnit` calling `validation.validate`) exercises the identical code path guaranteeing the collision is caught.

### Likelihood Explanation
Low-to-Medium confidence. The vulnerable pattern (stale, DB-only "already issued" check not accounting for uncommitted in-memory state from a sibling operation in the same unit) is real and directly mirrors the reported bug class, but I could not conclusively confirm within this investigation that `completePaymentPayload()` is ever invoked twice for the same capped asset within a single AA response before unit validation is run, nor could I rule out that `validation.js`'s `arrInputKeys` duplicate check (which operates on `asset-denomination-address-serial_number`) would catch and reject the resulting duplicate issue inputs at validation time, which would neutralize the impact.

### Recommendation
Track already-issued capped assets in the AA composer's in-memory state (e.g., in `assetInfos[asset]` or `objValidationState`) as soon as `addIssueInput()` is called, rather than relying solely on a DB query of already-persisted `inputs` rows. This closes the window between "message added an issue input in memory" and "unit persisted to DB," ensuring a capped asset cannot be scheduled for issuance twice within the same unit-composition pass, independent of whether `validation.js`'s duplicate-key check would also catch it.

### Proof of Concept
Not independently reproduced; a concrete PoC would require crafting an AA definition with two `payment` messages denominated in the same capped, AA-issuable asset such that the AA's existing on-chain balance of that asset is insufficient to cover either message alone, forcing `issueAsset()` to run twice within a single trigger evaluation before the resulting unit is saved. This was not verified against the full test/validation pipeline due to tool-call limits; the caveat about `arrInputKeys` collision detection in `validation.js` (see Impact Explanation) should be resolved first to determine actual exploitability.
