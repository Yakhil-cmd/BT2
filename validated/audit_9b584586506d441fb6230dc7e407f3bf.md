## Analysis

The Sherlock H-6 bug class describes a "pause" mechanism that blocks the exit paths (`closeLoan`/`callLiquidation`) for positions that already exist, permanently trapping user funds with no way to unwind, even when unwinding (not new risk-taking) should always remain possible.

The analogous mechanism in `hirayap/ocore--008` is the `spender_attested` asset feature together with the `asset_attestors` message. When an asset is created with `spender_attested: true`, every payment (issue or transfer) requires the *sender's* address to be currently attested by one of the asset's attestors [1](#0-0) . Crucially, the attestor list used for this check is always the **single latest** list published by the definer — `readAsset` selects only the most recent `asset_attestors` unit (`ORDER BY level DESC LIMIT 1`), with no notion of "the list that was valid when I received these funds" [2](#0-1) . The definer can update this list at any time via a single-authored `asset_attestors` message that only requires being the asset's definer [3](#0-2) .

The per-input ownership check that enforces this is unconditional — it rejects the input if the owner address is not on the *current* attested list, regardless of what the output is trying to do (including sending funds back to the definer to "close" the position): [4](#0-3) 
The same unconditional check exists on the private/fixed-denomination code path [5](#0-4) , and again at issuance time [6](#0-5) .

Contrast this with the `is_transferrable` check just below it, which explicitly special-cases "sending back to the definer" as an always-allowed escape hatch [7](#0-6) . No equivalent escape hatch exists for `spender_attested` — there is no code path that lets a holder return/settle their existing coins to the definer once they fall off the attestor list, exactly mirroring the reported bug where `closeLoan`/`callLiquidation` were blocked by the same flag that governs new risk-taking.

### Title
Attestor-list rotation on `spender_attested` assets permanently freezes existing holders' funds with no exit path - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, every input's owner address is checked against only the *most recently published* attestor list (`storage.readAsset` / `filterAttestedAddresses`). Because the definer can freely republish the attestor list at any time via a single `asset_attestors` message, and because the spend check applies unconditionally to every payment — including one whose destination is the asset definer itself — a definer's routine attestor rotation (e.g. replacing a compromised attestor key, or narrowing eligible attestors) instantly and retroactively strips spendability from any holder who is not attested under the *new* list, with no way for them to move or return those funds.

### Finding Description
`readAsset` fetches attestors for a `spender_attested` asset by taking the single latest `asset_attestors` unit ordered by level/rowid, and uses only that list going forward [2](#0-1) . `validatePayment` and `validatePaymentInputsAndOutputs` gate every spend of the asset — issuance and transfer alike — on whether the current owner address appears in `arrAttestedAddresses`, computed from that single latest list [1](#0-0) [8](#0-7) . The `asset_attestors` update itself can be authored solely by the asset definer, with no requirement to preserve backward compatibility with previously-attested holders and no requirement to give notice or grace period [3](#0-2) .

Unlike the `is_transferrable=false` branch, which explicitly carves out "payment to the definer address" as a valid way to return funds regardless of other restrictions [7](#0-6) , the `spender_attested` ownership check has no analogous carve-out: it rejects the spend outright if the owner is not attested, irrespective of where the output goes [4](#0-3) . This is precisely the same shape of bug as H-6: a state flag (`collateralPaused`/attestor-list version) that is meant to gate *new* risk exposure ends up also blocking the *exit*/settlement path for holdings that already exist.

### Impact Explanation
Any holder of a `spender_attested` asset who is not on the definer's newest attestor list becomes permanently unable to move their existing coins — they cannot transfer them to anyone, and they cannot even send them back to the definer to "close out" their position. Since attestor-list updates are a normal, expected part of asset lifecycle management (key rotation, onboarding/offboarding of attestors, compliance changes), this can happen inadvertently to good-faith holders, freezing funds indefinitely with no code-level recovery path other than the definer/attestor proactively re-attesting every affected address.

### Likelihood Explanation
This requires no attacker at all — it is triggered by the asset definer performing an ordinary, permitted action (`asset_attestors` update) that the protocol explicitly supports. Any asset using `spender_attested` (a documented, first-class asset feature) is exposed the moment the attestor set changes in a way that excludes previously-valid holders (e.g. attestor key rotation), which is a realistic and likely operational event over an asset's lifetime.

### Recommendation
Provide an unconditional exit path for `spender_attested` assets analogous to the `is_transferrable` definer carve-out: allow a holder whose address is not currently attested to still send the funds back to the asset's `definer_address` without failing the "owner address is not attested" check in `validatePaymentInputsAndOutputs`/`validatePayment`. Additionally, consider evaluating attestation against the list that was current at the time the output was created (or providing a grace period) rather than unconditionally applying only the newest list to all historical outputs.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and attestor list `[X]`.
2. Attestor `X` attests address `H`. Holder `H` receives a transfer of asset `A` and successfully spends/holds it — validated via `objAsset.arrAttestedAddresses` derived from `[X]`'s attestation of `H` [9](#0-8) .
3. Definer publishes a new `asset_attestors` message setting the attestor list to `[Y]` (e.g., rotating away from a compromised key), which is accepted because the definer is the sole authorized author of this message [3](#0-2) .
4. `readAsset` now returns only `[Y]` as `arrAttestorAddresses` for asset `A` [2](#0-1) ; `H`'s old attestation from `X` is no longer counted by `filterAttestedAddresses`, since it filters `attestor_address IN (arrAttestorAddresses)` = `[Y]` only [9](#0-8) .
5. `H` attempts to spend their existing (already-owned) output of asset `A`, even by sending it back to the definer's address. `validatePaymentInputsAndOutputs` rejects it with "owner address is not attested" because the check is applied unconditionally regardless of destination [4](#0-3) .
6. `H`'s funds are now permanently frozen unless attestor `Y` proactively re-attests `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
