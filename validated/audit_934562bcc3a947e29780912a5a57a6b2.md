Cross-repository Commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a `status` webhook against the organization identified by `repository_owner`, which falls back to `params.dig('organization','login')` when the top-level `repository` key is absent. `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks either field: it performs `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match, so a correctly signed webhook from *any* configured GitHub App organization can write a status onto a commit belonging to a completely different repository/stack.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `organization named in the verified payload (repository_owner: params.dig('repository','owner','login') || params.dig('organization','login'))` == `organization owning the Repository/Stack that the matched Commit belongs to`.

- `WebhooksController#verify_signature` selects the GitHub App/webhook secret purely by `repository_owner`, with an explicit fallback to the `organization` sub-object when `repository` is omitted: [1](#0-0) [2](#0-1) 

- Once signature verification passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`: [3](#0-2) 

- `StatusHandler#process` looks up commits purely by `sha`, with no repository/organization filter whatsoever: [4](#0-3) 

This is inconsistent with every other handler in the codebase, all of which explicitly scope their writes to the repository named in the payload:
- `PushHandler` scopes via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [5](#0-4) [6](#0-5) 
- `CheckSuiteHandler` also uses `stacks.where(branch:)` before touching commits: [7](#0-6) 
- All `PullRequest::*Handler` classes resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)` before mutating anything: [8](#0-7) 

`StatusHandler` is the outlier: its `params` schema doesn't even declare `repository` or `organization` as required/accepted fields, so `ExplicitParameters` doesn't gate on it either: [9](#0-8) 

**Attacker request**: A minimal, correctly-signed (using the attacker's own legitimately configured Shipit GitHub App secret) `status` event payload:
```json
{ "organization": { "login": "attacker-org" }, "sha": "<victim commit sha>", "state": "success" }
```
`repository_owner` resolves to `"attacker-org"` via the fallback, `verify_signature` succeeds using the attacker's own app secret (a legitimate credential they hold for their own org), and `StatusHandler#process` writes a `Status` record onto the victim's `Commit` regardless of which repository/stack it actually belongs to.

Note that omitting `repository` and using the `organization` fallback is not strictly necessary — since `StatusHandler` never reads `repository` or `organization` at all, the same forgery works even when a normal `repository` object naming the attacker's own repo is included. The organization-fallback detail only demonstrates that no payload shape provides protection; the root cause is entirely inside `StatusHandler#process`, not in `verify_signature`.

No existing guard intercepts this: `drop_unhandled_event` only checks that a handler exists for the event type; `ExplicitParameters` only validates types/presence of `sha`/`state`/etc., not repository ownership; there is no `stacks`/`repository` scoping call anywhere in `StatusHandler`.

### Impact Explanation
Any organization onboarded as a legitimate Shipit GitHub App (an attacker's own organization, which they fully control and can configure to satisfy "preconditions") can create/mutate `Shipit::Status` records on commits belonging to *any other* tenant's stack, by simply guessing or discovering a target commit SHA (SHAs are often visible in PR/commit links, CI logs, or public repos). This directly affects Shipit's merge-queue logic: `Commit#create_status_from_github!` → `#add_status` can flip a foreign commit from failing/pending to `success`, which (per `add_status`) can trigger `stack.schedule_merges` and hooks (`commit_status`, `deployable_status`), potentially causing an unauthorized merge/deploy decision for a repository the attacker never authenticated against. This matches the "payload for one repository mutating another's stack/commit" Critical impact category. [10](#0-9) 

### Likelihood Explanation
Preconditions: attacker only needs one legitimately configured Shipit GitHub App organization (which they can set up themselves per this environment's rules) and knowledge of a target commit SHA — no session, API token, or GitHub secret of the victim is required. The attack is a single unauthenticated HTTP POST to `/webhooks` with a valid signature computed from the attacker's own webhook secret; it's trivially repeatable against arbitrary commits/SHAs across the entire Shipit installation.

### Recommendation
In `StatusHandler#process` (and its `params` schema), require and use the payload's `repository.full_name` (with the same fallback awareness as `verify_signature`) to resolve the owning `Repository`/`Stack` via `Repository.from_github_repo_name`, and scope the `Commit` lookup through that repository's stacks (e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })` or equivalent), mirroring the pattern used by `PushHandler`/`CheckSuiteHandler`, instead of the unscoped `Commit.where(sha: params.sha)`.
