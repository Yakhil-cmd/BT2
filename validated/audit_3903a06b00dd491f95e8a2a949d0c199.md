## Title
`initialize_with_permission` accepts an unchecked, non-signing `creator` account, allowing `pool_creator` to be set to a null/unrecoverable address and permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` takes `creator` as an `UncheckedAccount` that is never required to sign and never checked against `Pubkey::default()`. Its raw key is written straight into `PoolState.pool_creator` [1](#0-0) . Every downstream consumer of `pool_creator` assumes it is a valid, controllable address — exactly the `beneficiary`-must-not-be-null assumption from the Charta `DebtRegistry` report — but nothing enforces that here.

### Finding Description
- `creator` is declared as `/// CHECK: creator of pool` `pub creator: UncheckedAccount<'info>` with no `Signer`, no `address =`, and no non-default constraint [2](#0-1) .
- The `payer` (only gated by holding a `permission` PDA, not by controlling `creator`) is the only signer, and can supply **any** pubkey for `creator`, including `Pubkey::default()` or any other address it doesn't control [3](#0-2) .
- That arbitrary key is persisted as `pool_creator` in `PoolState::initialize` with `enable_creator_fee = true` [1](#0-0)  and `PoolState::initialize` sets `self.pool_creator = pool_creator.key();` without any validation [4](#0-3) .
- `CollectCreatorFee` (the privileged withdrawal path) requires `creator: Signer<'info>` constrained by `address = pool_state.load()?.pool_creator` [5](#0-4) . If `pool_creator` is `Pubkey::default()` or any address without a known private key, this instruction can never be signed for and becomes permanently unreachable.
- `CollectCreatorFeePermissionless` sidesteps the signer requirement and simply forwards accumulated `creator_fees_token_0/1` to an ATA owned by `pool_state.pool_creator` [6](#0-5) , but if that authority is an address nobody controls (e.g. the System Program's default pubkey), the tokens land in an ATA that can never be spent from — they are permanently locked, not just uncollectable via one path.
- The codebase already demonstrates the developers are aware of this exact class of bug and fix it elsewhere: `update_config.rs`'s `set_new_protocol_owner`/`set_new_fund_owner` explicitly call `require_keys_neq!(new_owner, Pubkey::default())` [7](#0-6) , but no equivalent check exists for `creator` in `initialize`/`initialize_with_permission`.

Trade fees routed into `creator_fees_token_0`/`creator_fees_token_1` originate from swappers' trades on the pool and are subtracted from the usable vault balance via `vault_amount_without_fee` [8](#0-7) , so this is real user-generated value at stake, not merely protocol bookkeeping.

### Impact Explanation
Any caller with a valid `permission` PDA (an otherwise unprivileged, permissioned pool creator) can create a pool where `pool_creator` is set to an address that nobody can sign for. All creator-fee revenue accrued from that pool's swappers becomes permanently frozen: `collect_creator_fee` can never be authorized, and `collect_creator_fee_permissionless` will lock the funds in an ATA with an uncontrollable authority. This is a permanent freezing of pool-derived user funds.

### Likelihood Explanation
Likelihood is moderate/high for anyone able to call `initialize_with_permission` — no special privilege over `creator`'s private key is needed, and the mistake could be made either accidentally (e.g., passing a placeholder/default account) or deliberately by a malicious permissioned creator to grief their own pool's fee stream or to build a pool that looks legitimate while silently discarding creator fees.

### Recommendation
Add an explicit check in `InitializeWithPermission` (and defensively in `Initialize`) rejecting `creator.key() == Pubkey::default()`, mirroring the `require_keys_neq!` pattern already used in `update_config.rs`'s `set_new_protocol_owner`/`set_new_fund_owner`. Consider additionally requiring `creator` to be a `Signer` (as already done in the un-permissioned `Initialize`) to prevent assigning fee rights to an address the payer does not control at all.

### Proof of Concept
1. Attacker obtains a `permission` PDA for their `payer` account (satisfying the `#[account(seeds = [PERMISSION_SEED, payer.key()])]` constraint) — this is the only gate on calling `initialize_with_permission`.
2. Attacker calls `initialize_with_permission`, passing `creator = Pubkey::default()` (or any address with no known private key) as the `creator` account; this account is never checked to be a signer nor non-default [2](#0-1) .
3. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()` [1](#0-0) , and `enable_creator_fee = true`.
4. Ordinary swappers trade against this pool, and creator-fee amounts accumulate in `creator_fees_token_0`/`creator_fees_token_1`.
5. `collect_creator_fee` can never succeed because no signer can satisfy `address = pool_state.load()?.pool_creator` for the default pubkey [5](#0-4) .
6. Anyone calling `collect_creator_fee_permissionless` moves the fee tokens into an ATA whose authority (`Pubkey::default()`) has no corresponding keypair, permanently locking these funds [9](#0-8) .

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
