### Title
Cross-organization team hijack via `membership` webhook - authentication bypass into `Shipit.github_teams` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used to verify the HMAC signature) solely by `repository_owner`, which for `membership` events falls back to `params.dig('organization', 'login')` — a value fully controlled by whoever sends the webhook. `MembershipHandler#find_or_create_team!` then looks up the `Team` purely by the attacker-supplied numeric `team.id` (`github_id`), never checking that the team's `organization` matches the organization whose secret verified the request, letting any GitHub org owner replay a self-signed `membership` webhook that mutates a `Team` belonging to a different, privileged organization.

### Finding Description
The broken binding is: `organization_whose_secret_verified_the_request == organization_owning_the_Team_row_being_mutated`. This must be false for the write to be illegitimate, but the code never enforces it.

- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` (lines 24-30) resolves `github_app = Shipit.github(organization: repository_owner)`, and `repository_owner` (lines 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')`. A `membership` payload has no `repository` key, so `repository_owner` becomes the attacker's own `organization.login` (`O_attacker`). `Shipit.github(organization:)` (`lib/shipit.rb` lines 170-181) looks up config/secret keyed by that exact organization name, so the signature is verified against `O_attacker`'s own `webhook_secret` — which the attacker controls since they own that organization. [1](#0-0) [2](#0-1) [3](#0-2) 
- `Shipit::Webhooks.for_event('membership')` dispatches to `Handlers::MembershipHandler`. [4](#0-3) 
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. Since `github_id` is a global (attacker-guessable/enumerable) numeric team id, if it already matches an existing privileged `Team` row (e.g., one in `Shipit.github_teams`), that existing row is returned unchanged — its `organization` attribute is not overwritten because the block only runs on creation. The handler never checks that `params.organization.login` equals the found team's `organization`. [5](#0-4) 
- `process` then executes `team.add_member(member)` for `action == 'added'`, inserting a `Membership` row for the attacker-named user into that privileged team. [6](#0-5) [7](#0-6) 
- `User#authorized?` grants access whenever the user's `teams` intersect `Shipit.github_teams` by id, with no organization cross-check either. [8](#0-7) 

No existing guard prevents this: `drop_unhandled_event` only checks the event is handled at all; `verify_signature` verifies a real signature, just against the wrong (attacker's own) secret because the org is attacker-chosen; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not organization identity; there's no `require_permission!` or stack/repository binding check on this webhook path at all, since it's org-scoped, not repository-scoped.

### Impact Explanation
A remote, unprivileged attacker who merely owns/administers any GitHub organization can add an arbitrary named GitHub login as a member of any pre-existing `Team` row in the Shipit database by guessing/enumerating its numeric `github_id`, without ever needing that team's real organization's `webhook_secret`. If the targeted team is one of `Shipit.github_teams`, the newly added user becomes `authorized?` for the whole Shipit instance — a full authentication/authorization bypass, matching the "escalation into `Shipit.github_teams` authorization" (High) / effectively enabling further Critical actions (deploys, rollbacks) once authorized. This is repeatable against any team id and any login string, is not scoped to any one repository, and affects the entire instance (not just the attacker's own org).

### Likelihood Explanation
Preconditions are low-cost: the attacker needs only a GitHub account (able to create/own an organization), an instance-reachable Shipit host with `POST /webhooks` enabled, and knowledge of the `github_id` of a privileged `Team` (numeric GitHub team ids are visible via GitHub API/UI and can also simply be brute-forced/incremented since they are global, sequential-ish integers). No Shipit credentials, sessions, or the target org's secret are required. The attack is a single unauthenticated HTTP POST and fully repeatable/scriptable.

### Recommendation
In `MembershipHandler`, verify that `params.organization.login` matches the `organization` already stored on the `Team` found by `github_id` before mutating membership (reject/log-and-drop otherwise, and never allow an existing team's `organization` to be silently reused for a mismatched org). Additionally, `WebhooksController#verify_signature` should not trust an attacker-chosen organization name for GitHub App selection when no repository is present; instead, cross-check that the resolved `github_app`'s organization actually corresponds to a `GithubHook::Organization` record configured for the `membership` event (as done via `Team#github_hooks`) before processing.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership webhook from unrelated org cannot hijack privileged team" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id known
  attacker_org = 'attacker-org' # configured with its own webhook_secret in test secrets

  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Membership.where(team: privileged_team).count } do
    post :create, body: payload, as: :json
  end
  # currently FAILS: a Membership for 'attacker' on privileged_team is created,
  # and User.find_by(login: 'attacker').authorized? becomes true
end
```
Binding assertion: before the fix, `organization_that_verified_signature ('attacker-org') != privileged_team.organization ('shopify')` yet the write still succeeds — demonstrating the missing check.
