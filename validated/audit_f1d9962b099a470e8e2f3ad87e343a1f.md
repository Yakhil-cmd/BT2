### Title
ReDoS in `_regex_match`/`compile_regex` via attacker-controlled rule `pattern` causes PreToolUse hook to hang and fail open - ([File: plugins/hookify/core/rule_engine.py])

### Summary
The `pattern` field of a hookify rule (loaded from `.claude/hookify.*.local.md`) is compiled with plain `re.compile()` and matched with `regex.search()` with no timeout, complexity limit, or safe-regex validation. A rule using a catastrophic-backtracking pattern (e.g. `(a+)+b`) matched against attacker-influenced `tool_input` text (e.g. `command`/`new_text`) will hang the hook process in CPU-bound backtracking, and since `pretooluse.py`'s hook-level timeout kill or crash never lets the block/deny decision be emitted, the tool call is allowed to proceed.

### Finding Description
`plugins/hookify/core/rule_engine.py`'s `compile_regex` (`re.compile(pattern, re.IGNORECASE)`, `plugins/hookify/core/rule_engine.py:14-24`) caches and compiles the `pattern` string taken verbatim from `Condition.pattern`, which is populated from the rule's YAML frontmatter `pattern`/`conditions[].pattern` field in `config_loader.py` (`Condition.from_dict`, `plugins/hookify/core/config_loader.py:22-29`, and `Rule.from_dict`, lines 45-84). These `.claude/hookify.*.local.md` files are ordinary repository content picked up by `load_rules()` (`plugins/hookify/core/config_loader.py:198-241`) with no validation of the regex's safety.

`_regex_match` (`plugins/hookify/core/rule_engine.py:256-273`) calls `regex.search(text)` directly with no timeout wrapper, no `signal.alarm`, and no use of a linear-time engine (e.g. the `regex` module's timeout parameter or RE2). The `text` argument is the tool's `command` (Bash) or `new_text`/`new_string` (Edit/Write/MultiEdit) field, extracted in `_extract_field` (`plugins/hookify/core/rule_engine.py:182-254`) directly from `tool_input`, which is attacker-influenceable content (e.g., a long adversarial string embedded in a file the model edits, or a crafted shell command).

Given a pattern like `(a+)+b` and an input of many `a` characters without a trailing `b` (e.g., `"a"*40`), Python's backtracking `re` engine exhibits exponential-time behavior, effectively hanging the process inside `regex.search()`. Because the hang occurs synchronously inside `re.search`, the `finally: sys.exit(0)` in `pretooluse.py` (`plugins/hookify/hooks/pretooluse.py:68-70`) is never reached from within this stuck call frame — the process itself stalls. Existing hook configuration (`plugins/hookify/hooks/hooks.json`) defines a per-hook execution timeout that Claude Code's host process is presumed to enforce; if the host kills the unresponsive PreToolUse hook process upon timeout, the design intent that the finally-block's `sys.exit(0)` "never blocks operations due to hook errors" produces an effective fail-open: the dangerous Bash/Edit tool call proceeds unchecked because no explicit `"permissionDecision": "deny"` was ever emitted before the hook was killed.

No check in `rule_engine.py` or `config_loader.py` validates regex complexity, limits pattern length, sandboxes matching with a timeout, or falls back to deny-on-timeout.

### Impact Explanation
This is a hook/guard bypass via denial-of-service: a rule intended to block a dangerous Bash command or file edit (e.g. `rm -rf`) can be neutralized because the regex evaluation itself never completes, and no deny decision is produced in time. Combined with the fail-open exit strategy in `pretooluse.py`, this allows dangerous, otherwise-blocked operations to execute — matching the "hook enforcement bypass" impact category (unauthorized command/file action proceeding despite an active blocking rule).

### Likelihood Explanation
Exploitation requires an attacker to get a `.claude/hookify.*.local.md` rule file with a catastrophic-backtracking `pattern` (or `conditions[].pattern`) into the repository — feasible via a malicious PR/commit if the project consumes hookify rules from repo content, or if the attacker already has write access to `.claude/`. It additionally requires the ability to trigger a Bash/Edit tool call whose `command`/`new_text` content can be shaped to trigger backtracking (e.g., a long run of a specific character), which is realistic in normal automation flows (long file contents, generated shell commands). The `lru_cache` on `compile_regex` doesn't mitigate this — the cost is in matching, not compiling. No detection or mitigation exists in the current code, making this reliably repeatable.

### Recommendation
- Enforce a hard timeout around regex matching in `_regex_match` (e.g., run `regex.search` in a subprocess/thread with `concurrent.futures` and a deadline, or use the third-party `regex` module's `timeout` parameter), and treat a timeout as a "deny" (or at least a warning) rather than silently allowing.
- Validate/sanitize rule patterns at load time (e.g., reject nested quantifiers or use a static ReDoS-pattern detector) in `config_loader.py`'s `Condition.from_dict`/`load_rule_file`.
- Consider switching to a linear-time regex engine (e.g., Google's `re2`) for user-supplied patterns.
- Change the hook's fail-safe behavior for PreToolUse so that inability to complete rule evaluation (timeout/crash) results in a deny or explicit warning rather than defaulting to allow, especially in `hooks.json`'s timeout-driven kill path.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_redos_pattern_hangs_or_times_out():
    rule = Rule(
        name="malicious-rule",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+b")],
        message="should block"
    )
    engine = RuleEngine()
    malicious_input = {
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 35}  # no trailing 'b'
    }
    start = time.monotonic()
    result = engine.evaluate_rules([rule], malicious_input)
    elapsed = time.monotonic() - start

    # Expected (fixed) behavior: bounded execution time, e.g. < 1 second,
    # and on timeout the rule should be treated as blocking/deny, not silently allowed.
    assert elapsed < 1.0, f"regex_match took {elapsed}s — ReDoS not mitigated"
```
Running this against the current implementation demonstrates unbounded (exponential) execution time as the `a` count increases (e.g. 30, 35, 40 chars), confirming no timeout/deny fallback exists, and that `pretooluse.py`'s `finally: sys.exit(0)` cannot execute until the pathological match completes — validating the hang/fail-open path described above.
