### Title
Cross-Organization Commit-Status/Sync Forgery via Unscoped Webhook Handlers - (File: `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature verification only proves that the sender knows the `webhook_secret` of the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field. The event-processing handlers, however, do not re-check that same organization when deciding which `Stack`/`Commit` records to mutate: `StatusHandler` looks up commits **globally by SHA only**, and the shared `Handler#stacks` helper resolves stacks purely from the unauthenticated `repository.full_name` string. This mirrors the IonZapper bug class: the entity that is cryptographically authenticated (the organization owning the secret) is not the entity actually acted upon (an arbitrary repository/commit elsewhere in the installation).

### Finding Description
`WebhooksController#verify_signature` selects the app config to verify against using a value taken straight from the JSON body: [1](#0-0) [2](#0-1) 

This only proves "the sender knows organization X's `webhook_secret`" — it says nothing about which repository/commit the payload's business fields refer to, because those other fields (`repository.full_name`, `sha`, etc.) are inside the same signed body and can be set to anything the secret-holder wants.

The event handlers then trust those unscoped fields without re-validating them against the authenticated organization:

- `Handler#stacks` resolves the target `Stack` purely from `repository.full_name` in the payload, with no relation to the org whose secret was verified: [3](#0-2) 

- `StatusHandler#process` is worse: it doesn't even use `repository` — it looks up **any** `Commit` row across the entire Shipit instance by `sha` alone and writes a status to it: [4](#0-3) 

- `PushHandler` and `CheckSuiteHandler` use the same unscoped `stacks` helper to trigger sync/refresh jobs for whatever stack matches `repository.full_name`: [5](#0-4) [6](#0-5) 

**Trust binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository_owner in payload)` ≠ `organization/repository actually written by the handler (repository.full_name or bare sha)`.

Before the analog: a webhook is only accepted if its HMAC matches the `webhook_secret` of the org named in `repository.owner.login`; the implicit assumption is that all state mutated by the event belongs to that same org. After: an attacker who controls (or has legitimately been granted) a GitHub App installation for **their own** organization — which Shipit also tracks, and for which they therefore hold a valid `webhook_secret` — can sign an arbitrary payload with their own secret while setting `repository.full_name` (or, for `status` events, simply `sha`) to values belonging to a **different** organization's repository/stack tracked by the same Shipit instance. `verify_signature` passes (correct org, correct secret), but the handler acts on a repository/commit outside that org.

### Impact Explanation
This is a cross-repository/cross-tenant write, an explicitly listed Critical impact:
- Forging commit statuses (`StatusHandler`) for a commit belonging to a repository the attacker doesn't own can flip `Commit#deployable?`-style CI gating used by deploy authorization flows (`require_ci` checks in `Shipit::Api::DeploysController#create`), enabling an unauthorized deploy of a victim's stack, or blocking legitimate deploys (denial of a specific deploy, not general DoS).
- Forging `push`/`check_suite` events for another org's tracked repository can trigger `Stack#sync_github`/check-run refresh jobs against that repository using the victim's own GitHub credentials, causing spurious commit ingestion or state changes on a stack the attacker does not control.

This satisfies the "cross-repository writes" / "unauthorized deploy" Critical criteria in the rules, without requiring a Shipit session, API token, or any privileged Shipit account — only that the attacker's own organization is one of the (possibly many) organizations configured with `Shipit.github(organization: ...)` webhook secrets on the same multi-tenant Shipit instance.

### Likelihood Explanation
Requires only that Shipit is configured to serve more than one GitHub organization (a documented and common deployment pattern, since `Shipit.github(organization:)` is looked up dynamically per webhook), and that the attacker administers a legitimate app installation for at least one of those organizations (unprivileged relative to the target org). No cryptographic break, no host compromise, and no Shipit account credentials are needed — only crafting a raw HTTP POST to `/webhooks` with a self-computed HMAC using the attacker's own known secret.

### Recommendation
Scope every handler's data access to the organization that was actually authenticated in `verify_signature`, not just to identifiers pulled from the unscoped payload body:
- Pass the verified `repository_owner`/organization down to each `Handler`, and filter `stacks`/`Commit` lookups by `Repository`s that belong to that organization (e.g., join through `Repository#owner` when resolving `repository_name`, and require `Commit`'s stack's repository owner to match in `StatusHandler`).
- Alternatively, verify that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) used in `verify_signature` matches the owner of the `Repository` record ultimately targeted by the handler before mutating any state.

### Proof of Concept
1. Attacker legitimately administers a GitHub App installation for `attacker-org`, which is configured in Shipit with `webhook_secret = S`. Shipit also tracks `victim-org/victim-repo` (a different org/app installation) as a `Stack`, and has a `Commit` row with `sha = "deadbeef..."` belonging to that stack.
2. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` for a crafted `status` event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "deadbeef...",           // belongs to victim-org/victim-repo
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake"
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and the computed signature.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully (attacker legitimately knows `S`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the victim's commit globally — and calls `create_status_from_github!`, forging a passing CI status on `victim-org/victim-repo`'s commit despite the attacker having no access to that organization at all, potentially unblocking `require_ci`-gated deploys for the victim stack.
