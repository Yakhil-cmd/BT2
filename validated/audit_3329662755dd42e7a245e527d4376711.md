### Title
Cross-repository forged CI status accepted for merge-queue decisions - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's originating repository (verified by `GithubApp#verify_webhook_signature`) matches the repository of the stack owning that commit. An attacker who controls any GitHub repository already tracked by the same Shipit instance can, by copying a victim commit's exact tree/parents/metadata into their own repo (making the sha identical) and then posting any status via their own repo's CI, get that status attached to the victim's `Commit` row and consumed by `MergeRequest#all_status_checks_passed?`.

### Finding Description
The binding the merge queue relies on is: `webhook_signing_org(payload) == organization_that_owns(commit.stack.repository)`. In reality, `StatusHandler` only enforces `webhook_signing_org(payload) == organization_that_owns(payload.repository)` (via `WebhooksController#verify_signature` calling `Shipit.github(organization: repository_owner)`), and then completely discards that repository binding: [1](#0-0) 

Unlike `Handler#stacks`, which scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, `StatusHandler#process` never calls `stacks` or checks `payload.dig('repository', 'full_name')` at all — it just does `Commit.where(sha: params.sha)` across the entire `commits` table, i.e. across every stack/repository/organization tracked by the instance: [2](#0-1) 

`Commit#create_status_from_github!` then writes the status onto that commit and triggers `add_status`, which calls `stack.schedule_merges` when the new status is pending or successful: [3](#0-2) [4](#0-3) 

`MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?` then evaluate `head.statuses_and_check_runs` (which now includes the forged status) using `stack.cached_deploy_spec` of the *victim* stack: [5](#0-4) 

`WebhooksController#verify_signature` only proves the webhook came from the organization named in the payload's own `repository.owner.login` — it says nothing about whether that organization/repo is the one that owns the `Commit` row being mutated: [6](#0-5) 

Given the stated precondition (victim's PR head sha is reproducible by the attacker — e.g. an identical commit object pushed into a repo the attacker controls, which is itself already onboarded to the same Shipit instance with a legitimate `webhook_secret`), the attacker can set any commit status (`success`, any context) on their own commit via their own repo's real GitHub integration. GitHub then sends a legitimately-signed `status` webhook for the attacker's own repository, which correctly passes `verify_signature`, but is then applied by `StatusHandler` to every `Commit` row sharing that sha — including the victim's, in a completely different stack/org.

None of the existing guards close this: `verify_signature` only authenticates the sender's own repo/org, not the target commit's stack; `StatusHandler` performs no repository-name comparison (unlike `PushHandler`/`CheckSuiteHandler`, which use `stacks`); and `Commit.where(sha: ...)` is a global, unscoped query.

### Impact Explanation
A forged `success` status (or removal of a `failure`/`pending` state via a synthetic success context) gets attached to a victim's merge-queue commit. Combined with `merge_queue_enabled` and `Shipit::Stack.schedule_merges` → `MergeRequest#reject_unless_mergeable!`, this allows a queued merge to proceed to `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` and merges the victim PR despite failing or missing CI. This is a payload from one repository (attacker's) mutating another repository's stack/commit/merge decision, and results in an unauthorized merge — matching the "Critical" category (payload for one repository mutating another's stack/commit, unauthorized merge). It is repeatable against any victim stack on the same Shipit instance, for any commit whose sha the attacker can reproduce.

### Likelihood Explanation
Requires: (1) the attacker's own repository already onboarded/tracked by the same Shipit deployment with a functioning webhook (a low bar — self-service repo onboarding is normal in Shipit deployments); (2) the ability to reproduce the exact victim commit sha in a repo they control (feasible only when the victim commit is a literal copy of a real commit object — e.g., a shared upstream/base commit, or a commit cherry-picked/pushed unchanged into the attacker's repo, which is a realistic and fairly common occurrence given git's deterministic hashing); (3) `merge_queue_enabled` on the victim stack. No Shipit secrets, sessions, or GitHub tokens are needed — only a normal, real GitHub status webhook from a repo the attacker legitimately administers.

### Recommendation
In `StatusHandler#process` (and any other sha-keyed handler), scope the `Commit` lookup by the stack's repository, not by sha alone — e.g. restrict to `stacks` derived from `payload.dig('repository', 'full_name')` (as `Handler#stacks` already does for other handlers) before matching by sha: `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. This re-establishes the binding that only a commit's own repository/organization can vouch for its CI status.

### Proof of Concept
```ruby
# test/models/merge_request_test.rb (conceptual addition)
test "a status forged via a different stack's webhook does not satisfy CI checks" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true
  attacker_stack = shipit_stacks(:cyclimse) # different repository/org

  shared_sha = "cafef00dcafef00dcafef00dcafef00dcafef00"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "PR head")
  merge_request = victim_stack.merge_requests.create!(number: 42, head: victim_commit)

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "copied commit")

  # Simulate StatusHandler#process being invoked by a genuinely-signed webhook
  # from the attacker's own (unrelated) repository/org.
  Shipit::Webhooks::Handlers::StatusHandler.call(
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_stack.repo_name, "owner" => { "login" => attacker_stack.repo_owner } }
  )

  merge_request.reload
  refute merge_request.all_status_checks_passed?, "victim MR should not see attacker-forged success"
  merge_request.reject_unless_mergeable!
  assert_equal "ci_missing", merge_request.rejection_reason
end
```
Currently `Commit.where(sha: params.sha)` matches both `victim_commit` and `attacker_commit`, so `victim_commit.statuses` gains the forged `success` status and the assertions above fail, demonstrating the cross-repository binding violation.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
