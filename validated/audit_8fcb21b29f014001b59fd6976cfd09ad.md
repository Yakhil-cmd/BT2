### Title
Webhook signature is verified against the wrong (or unconfigured) organization's secret, letting an attacker forge CI statuses / sync events for arbitrary repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, a value parsed straight out of the untrusted, attacker-controlled payload. The rest of the pipeline (event handlers) resolves the target `Stack`/`Repository`/`Commit` from other fields of that *same* payload (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all). Nothing binds "the organization whose secret validated this signature" to "the repository/commit that is actually mutated." When any organization in a multi-org install has no `webhook_secret` configured — an explicitly documented, supported, "optional" configuration — `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an unauthenticated caller submit a completely forged payload that is "verified" against that org while acting on any other org's stack or commit.

### Finding Description
`WebhooksController#repository_owner` is computed purely from the request body: [2](#0-1) 

This value selects the `GitHubApp` instance used to verify the signature: [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatic success: [4](#0-3) 

The webhook secret is documented as optional per-organization: [5](#0-4) , and multi-org configuration is a first-class, supported feature (`Shipit.github(organization:)`, `github_app_config`): [6](#0-5) .

Once verification passes (trivially, if the selected org has no secret), `WebhooksController#create` dispatches to handlers using the raw parsed JSON, not the verified org: [7](#0-6) 

Handlers resolve their target using unrelated payload fields:
- `Handler#stacks`/`#repository_name` uses `repository.full_name`: [8](#0-7) 
- `StatusHandler#process` does not scope by repository/stack at all — it queries `Commit.where(sha: params.sha)` globally and writes a status: [1](#0-0) 
- `CheckSuiteHandler#process` and `PushHandler#process` similarly act on whatever repository/branch the forged `full_name`/`ref` fields specify: [9](#0-8) [10](#0-9) 

**The broken binding (as an equality that should hold but doesn't):**
`organization whose secret validated X-Hub-Signature` == `organization owning the repository/commit the handler subsequently writes to`.

Before the attacker's request: this equality holds implicitly only because legitimate GitHub webhook deliveries have internally-consistent `repository.owner.login` and `repository.full_name` fields, and are signed with the secret of the actual installation that owns that repo.

After the attacker's request: an attacker POSTs a JSON body directly to `/webhooks` with `repository.owner.login` (or `organization.login`) set to an org configured with a blank `webhook_secret`, while setting `repository.full_name` (for push/check_suite) or `sha` (for status, which isn't even repo-scoped) to point at a completely unrelated victim stack/commit. `verify_signature` looks up the attacker-chosen org, finds no secret, and accepts the request unconditionally — no valid signature from the real, secret-holding organization is ever required.

### Impact Explanation
This lets an unauthenticated network attacker:
- Forge a `status` webhook event to write an arbitrary `success` CI status onto any commit in any stack in the Shipit instance (no repository binding exists at all in `StatusHandler`), which can satisfy `required_statuses`/`all_status_checks_passed?` checks that gate `MergeRequest#merge!` and deploy eligibility (`app/models/shipit/merge_request.rb`), resulting in an unauthorized merge or deploy proceeding on falsified CI evidence.
- Forge `push` and `check_suite` events to trigger `GithubSyncJob`/check-run refresh against arbitrary stacks, causing state to be resynced from attacker-implied data.

This satisfies the "Critical" bar of "an unauthorized deploy, rollback or merge" via forged/bypassed CI status, achieved purely by exploiting a documented, supported configuration gap (an org with no `webhook_secret`) combined with the engine's failure to bind signature-verification identity to the resource actually mutated.

### Likelihood Explanation
Requires only that at least one configured GitHub organization in the Shipit deployment has no `webhook_secret` set — explicitly presented as optional/acceptable in `docs/setup.md` and in the shipped `config/secrets.development.example.yml` template (`webhook_secret: # nil`). No authentication, API token, or repository write access is needed; the attacker sends a single unauthenticated HTTP POST to the public `/webhooks` endpoint. `StatusHandler`'s complete lack of repository scoping makes this maximally exploitable even in single-organization deployments where that one org's secret is unset.

### Recommendation
Bind the verified webhook identity to the mutated resource: after selecting the organization for signature verification, require that `repository.full_name`'s owner matches the verified `repository_owner`/organization, and reject the request otherwise. Additionally, scope `StatusHandler` (and any other handler) lookups to the repository/stack derived from the webhook payload rather than performing an unscoped `Commit.where(sha:)`. Treat a missing/blank `webhook_secret` as a hard misconfiguration warning rather than "auto-pass," or require an explicit signed opt-out.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` (real org with a real Shipit stack, e.g. `OrgA/victim-repo`) and `OrgB` (installed org, `webhook_secret` left blank per docs).
2. Attacker sends, without any signature or with `X-Hub-Signature` header absent:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim commit sha in OrgA/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/anything" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgB"`, loads `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` — no signature ever checked against `OrgA`'s real secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a fabricated `success` status onto the victim commit in `OrgA/victim-repo`, potentially unblocking an automated merge/deploy that depends on that CI context.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
