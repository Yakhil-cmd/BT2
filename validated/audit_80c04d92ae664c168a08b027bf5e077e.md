### Title
Cross-repository Status write via unscoped `Commit.where(sha:)` in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no repository/stack scoping, and `WebhooksController#verify_signature` only checks the webhook signature against the org named in the attacker-controlled payload (`repository.owner.login`), not against the actual owner of the commit being mutated. An attacker who controls a GitHub org configured in Shipit (i.e., a valid `webhook_secret`) can sign and send a `status` event naming their own repository but referencing a `sha` that happens to exist in an unrelated victim stack, causing a `Status` row to be created on the victim's `Commit`.

### Finding Description
The binding that should hold is: `organization_that_signed(payload) == organization_that_owns(Commit_matched_by(params.sha))`. Instead, the code only enforces `organization_that_signed(payload) == payload.dig('repository','owner','login')` via `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-30), where `repository_owner` (lines 59-62) is read straight from the same attacker-supplied JSON body that also carries `sha`. Nothing ties the `sha` field to that same repository.

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is global across all stacks/repositories — there is no `.where(stack: stacks)` or any join to the repository derived from the payload, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) which exists precisely for this purpose but is unused here: [2](#0-1) 

Exploit flow:
1. Attacker owns/controls GitHub org `attacker-org`, which is configured in Shipit with a legitimate `webhook_secret` (a normal, low-privilege prerequisite for any org wanting Shipit integration — no Shipit session or admin role required).
2. Attacker computes the HMAC signature for a JSON body using that secret.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}, "sha": "<victim_sha>", "state": "success", "description": "forged", "context": "ci/forged"}`.
4. `verify_signature` succeeds because the signature matches `attacker-org`'s secret and `repository_owner` resolves to `attacker-org` — the check only validates that the *claimed* owner in the payload matches the signer, it never validates that the `sha` truly belongs to that owner's repositories.
5. `StatusHandler#process` runs `Commit.where(sha: victim_sha)`, finds the victim's `Commit` row (owned by an entirely different stack/repository), and calls `commit.create_status_from_github!(params)`, writing an attacker-chosen `state`/`description`/`target_url`/`context` onto it.

Existing guards do not catch this: `verify_signature` validates only the payload/signature pairing for the *named* org, not sha ownership; `ExplicitParameters` schema in `StatusHandler.params` only validates types/presence of fields, not ownership; there is no `force_github_authentication`, `require_permission!`, or stack-scoping call anywhere in this handler.

### Impact Explanation
Any org with a configured `webhook_secret` can inject a fabricated `Status` (e.g., `state: 'success'`) onto a commit belonging to a completely different, victim stack, provided they can guess or discover a target commit SHA (SHAs are often public via GitHub UI/API, PR pages, etc., and are not secrets). Since Shipit's `Status::Group` and merge/deploy gating logic consume `Commit#statuses`, this can be used to spoof a passing CI status and help unblock a merge or deploy gated on that status for a repository the attacker does not own or control. This is a cross-repository/cross-tenant write and matches the "Critical" impact category: a payload for one repository mutating another's commit/stack state.

### Likelihood Explanation
Preconditions: attacker needs any org configured with a `webhook_secret` in the Shipit deployment (a normal/expected multi-tenant setup, not a privileged Shipit role) and knowledge of a target commit SHA (commonly discoverable, e.g. via public GitHub repos, PRs, or commit URLs). No Shipit session, API token, or GitHub App private key is required. The attack is a single signed HTTP POST and is fully repeatable against arbitrary SHAs across any tenant stack in the same Shipit instance, making it low-cost and highly feasible for any multi-tenant Shipit deployment.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository asserted in the payload, mirroring the `Handler#stacks` helper, e.g. `commit.stack.repository == Repository.from_github_repo_name(repository_name)` or restrict the query to `Commit.where(sha: params.sha, stack: stacks)` before calling `create_status_from_github!`. This should be applied to any handler doing sha-only lookups.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or via `test/controllers/webhooks_controller_test.rb` for full-path signature verification):
1. Create `stack_a` owned by `org-a` and `stack_b` owned by `org-b`, each with its own `webhook_secret`.
2. Create `commit_victim` under `stack_b` with `sha: "deadbeef..."`.
3. Build a `status` payload with `repository.owner.login == "org-a"`, `repository.full_name == "org-a/some-repo"`, `sha == commit_victim.sha`, `state == "success"`.
4. Sign the payload with `org-a`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
5. Assert the response is `200 OK` (signature accepted for org-a).
6. Assert `commit_victim.reload.statuses.last.state == "success"` — i.e., a `Status` row was created on `stack_b`'s commit despite the payload being signed only by `org-a`, proving `organization_that_signed(payload) == "org-a"` while `organization_that_owns(commit_victim.stack) == "org-b"`, violating the required equality.
