### Title
Cross-organization Team hijack via `MembershipHandler` — organization that authenticated the webhook is not bound to the `Team` record that gets mutated (`app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC validation directly from the payload's `organization`/`repository.owner` field, and validates the signature over the entire raw body [1](#0-0) . However, once a `membership` event passes that check, `MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the GitHub-global numeric `team.id`, and only assigns `team.organization` on first creation — it never re-verifies that `params.organization.login` (the org whose secret authenticated the request) matches the `organization` already stored on that `Team` record [2](#0-1) . This mirrors the reported bug class exactly: a value that gates access (`quote.maxBaseTokenAmount` / here, the authenticating organization) is checked once, but the actual mutated resource (`effectiveBaseTokenAmount` / here, the `Team` written to) is allowed to diverge from it without a revert.

### Finding Description
- `Shipit.github(organization: repository_owner)` picks the webhook secret keyed by the organization named in the payload itself, and `verify_webhook_signature` HMACs the full raw body against that secret [3](#0-2) . This proves only that *some* org config with a matching secret produced this exact payload — it does not scope which internal records that payload is allowed to touch.
- `MembershipHandler` requires `organization.login` and `team.id` in the payload [4](#0-3) , then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
Since GitHub team IDs are global (not scoped per organization), lookup by `github_id` alone means any *subsequent* `membership` event carrying that same numeric `team.id` will match the pre-existing `Team` row — regardless of what organization is named in that later event's payload. The block that sets `team.organization` only runs on the very first creation; it is never re-checked or re-verified on update.
- `team.add_member(member)` / `team.members.delete(member)` then mutates real membership on that (potentially privileged) `Team` [5](#0-4) .
- Deployments of Shipit that serve multiple organizations configure one `github:` entry (with its own `webhook_secret`) per organization, as shown in the setup docs and secrets templates [6](#0-5) . Each organization's operator legitimately knows only their own org's `webhook_secret`.

**Broken binding (equality that should hold but doesn't):**
`organization authenticated by the HMAC (params.organization.login validated against that org's webhook_secret) == organization of the Team record actually written (team.organization / team.github_id)`

Before the attack: Team #48 exists with `organization = "shopify"`, and is one of `Shipit.github_teams` used to grant application login access.
After the attack: an operator who only controls a *different*, unprivileged organization ("someothergithuborg") — and therefore only knows that org's `webhook_secret` — sends a correctly-signed `membership` event for their own org but with `team.id = 48` (the target's real GitHub team ID). `find_or_create_by!(github_id: 48)` matches the existing "shopify/developers" `Team`, and the attacker's chosen `member.login` is added to it, even though the signature only ever proved authenticity for "someothergithuborg".

### Impact Explanation
Team membership stored via `Shipit::Team` is what backs the `Shipit.github_teams` authorization gate used to admit users into the Shipit UI/API (login is restricted to members of configured GitHub teams). By forging a `membership` webhook signed only with a low-privilege organization's own webhook secret, but referencing the numeric `team.id` of a privileged team belonging to a different organization served by the same Shipit instance, an attacker can insert an arbitrary GitHub login into that privileged team's local membership record without ever being a real member of the target organization. This is a direct escalation into `Shipit.github_teams` authorization, matching the "High" impact bucket in scope (escalation into `Shipit.github_teams` authorization), and downstream can translate into unauthorized deploy/rollback/API-client-creation access once the attacker's account passes the team check.

### Likelihood Explanation
This requires: (1) a Shipit instance configured to serve more than one GitHub organization (an explicitly documented and supported configuration pattern — each org gets its own `webhook_secret` entry), (2) the attacker controlling one such lower-privileged organization already configured in the same Shipit instance (a realistic scenario for shared/SaaS-style Shipit deployments across teams or subsidiaries), and (3) knowledge of the target team's numeric GitHub `id`, which is disclosed by GitHub's API for any team the attacker can view (including public teams) and is also observable from prior legitimate `membership`/webhook traffic. No GitHub App private key, no Shipit session, and no privileged account on the target org are required — only control of one *other* onboarded organization's webhook secret, which the attacker inherently possesses if they administer that organization's app installation.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/update by both `github_id` and `organization`, and reject (or explicitly re-key) the event if an existing `Team` with that `github_id` has a different `organization` than `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_or_initialize_by(github_id: params.team.id)
  if team.persisted? && team.organization != params.organization.login
    raise ArgumentError, "Team #{params.team.id} organization mismatch"
  end
  team.github_team = params.team
  team.organization = params.organization.login
  team.save!
  team
end
```
More generally, `WebhooksController#verify_signature` should ensure the organization used to select the verifying secret is asserted to match every organization-scoped identifier acted upon later in the handler chain, rather than trusting downstream lookups keyed only by GitHub's global numeric IDs.

### Proof of Concept
1. Shipit instance is configured to serve two organizations, `shopify` (privileged, has `webhook_secret_A`, and `Shipit.github_teams` includes `shopify/developers`, GitHub team id `48`) and `someothergithuborg` (attacker-controlled, `webhook_secret_B`).
2. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_B, body)` where `body` is:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/48" },
  "organization": { "login": "someothergithuborg" },
  "member": { "login": "attacker-controlled-account" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: membership` and the above signature.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"someothergithuborg"` from the payload, fetches `webhook_secret_B`, and the HMAC validates successfully [7](#0-6) .
5. `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: 48)`, matches the pre-existing "shopify/developers" team, and `team.add_member(attacker-controlled-account)` executes [8](#0-7) .
6. `attacker-controlled-account` is now a member of `shopify/developers` inside Shipit's local `Team`/`Membership` tables, without ever belonging to the real `shopify` GitHub organization.

**Uncertainty / what I could not fully verify:** I could not open `app/models/shipit/team.rb`, `app/models/shipit/user.rb`, or `app/controllers/concerns/shipit/authentication.rb` in this session (ran out of tool calls) to confirm the exact mechanics of how `Team` membership is checked against `Shipit.github_teams` during login (e.g., whether it matches on `"org/slug"` handle or another field). The core broken binding — `Team` lookup by global `github_id` without re-validating `organization` against the authenticating org — is confirmed directly from `membership_handler.rb`; I recommend a Devin session or manual review of `app/models/shipit/team.rb` and `app/controllers/concerns/shipit/authentication.rb` to confirm the exact authorization-check code path before treating impact severity as final.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
