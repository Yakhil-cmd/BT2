### Title
Wallet Contract pays relayer fee unconditionally, before verifying the emulated transfer succeeded - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to emulate Ethereum EOAs / ERC-20 semantics on NEAR) pays out the relayer's fee via an independent, unconditional promise as soon as the transaction is parsed, without waiting for or checking whether the underlying emulated action (an `EOABaseTokenTransfer` or `ERC20Transfer`, i.e. an `ft_transfer` call) actually succeeds. This is the same root-cause class as the "fee-on-transfer token" bug: the contract's accounting assumes the value moved equals the intended amount instead of verifying the pre/post state (success) of the transfer before compensating for it.

### Finding Description
In `inner_rlp_execute`, once an `EOABaseTokenTransfer` or `ERC20Transfer` is parsed with a non-zero `fee`, the contract immediately creates a **separate** promise batch that transfers the fee to the relayer (`context.predecessor_account_id`), independent of the promise chain that will actually perform the transfer/`ft_transfer`: [1](#0-0) 

This `env::promise_batch_create` + `env::promise_batch_action_transfer` call is not `.then()`-chained to, or dependent on, the outcome of the action promise built later in the same function (the `ERC20Transfer` branch builds a multi-step `storage_balance_of` → `storage_deposit` → `ft_transfer` chain, and the `EOABaseTokenTransfer` branch builds an address-check chain): [2](#0-1) 

If the transfer chain later fails (e.g. `ft_transfer` panics due to insufficient token balance, the token contract rejects the call, `storage_balance_of`/`storage_deposit` fails, or the address-registrar lookup fails), the failure is only handled in `rlp_execute_callback`, which refunds the *caller's attached deposit* (`caller_deposit`) but has no knowledge of, and never claws back, the fee that was already sent to the relayer: [3](#0-2) 

The design intent (per the inline comment) is that "Relayers should also verify the fee before sending" - but this only protects relayers, not the wallet owner. The wallet's own NEAR balance is debited for the fee regardless of whether the intended ERC-20/base-token transfer actually completed, which is exactly the fee-on-transfer/rebasing-token failure mode: the contract credits/settles based on an assumed amount rather than the verified before/after balance or execution outcome.

### Impact Explanation
This causes an unauthorized balance change: the wallet contract's NEAR balance is drained to pay the relayer fee even when the corresponding emulated transfer never executes. Any submitted RLP-encoded transaction (reachable via `rlp_execute`, callable by anyone acting as predecessor/relayer) with a non-zero `fee` and a transfer that is destined to fail (e.g., insufficient token balance, non-existent/rejecting token contract, registrar mismatch) results in the wallet paying for a service that was not rendered. Repeated submissions amplify the loss.

### Likelihood Explanation
Likelihood is moderate-to-high: this does not require a malicious relayer with special privileges - the relayer only needs to relay a transaction whose emulated action will fail (which can be triggered by ordinary conditions, such as attempting an `ft_transfer` before the sender has a sufficient NEP-141 balance, or when the destination token contract behaves unexpectedly). Because the fee-transfer promise is unconditional and unlinked to the action's success, this is fully reachable from a normal unprivileged transaction submission path (`rlp_execute`), not a validator/node-only or mocked-only path.

### Recommendation
Chain the relayer fee-payment promise so it only executes after (and conditionally on) the success of the emulated action (e.g., attach it inside the `.then()` continuation together with, or after, `rlp_execute_callback`, and skip/refund it on `PromiseResult::Failed`). Alternatively, verify actual completion (e.g., check the `ft_transfer` promise result) before creating the fee-transfer batch action, mirroring the "check previous balance/after balance equals amount" recommendation for fee-on-transfer tokens.

### Proof of Concept
1. Deploy a Wallet Contract and fund it with NEAR and a NEP-141 balance below the amount intended to transfer.
2. Sign an Ethereum-style transaction (`Transaction2930`) with `to` = the NEP-141 token contract, `data` = `ERC20_TRANSFER_SELECTOR` + `(receiver, amount)`, and `gas_price` set so that the computed `fee` (per `NearToken` conversion in `try_emulation`) is non-zero.
3. Submit it via `rlp_execute` from a relayer account different from the wallet's own account id.
4. Observe: `inner_rlp_execute` immediately creates the refund promise crediting `fee` to the relayer's account, per [4](#0-3) .
5. The subsequent `storage_balance_of` → `ft_transfer` chain fails (because the wallet's NEP-141 balance is insufficient), triggering the `PromiseResult::Failed` branch in `rlp_execute_callback`, which only refunds `caller_deposit`, not the fee already paid to the relayer.
6. Result: relayer keeps the fee NEAR tokens despite the ERC-20 transfer never occurring, confirming the unconditional/unverified fee payout.
