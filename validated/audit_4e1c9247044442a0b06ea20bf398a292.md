### Title
Naive `'---'` substring split in `extract_frontmatter` lets a `pattern`/list value containing `---` truncate frontmatter and silently downgrade a `block` rule to `warn` (or corrupt its pattern) - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` locates the YAML frontmatter boundaries with `content.split('---', 2)`, which splits on the literal substring `---` anywhere in the text rather than on a line that is exactly `---`. If a rule's `pattern` (or any list/dict value) contains the three-character substring `---`, the split happens inside that value instead of at the real closing fence, truncating the parsed frontmatter and pushing the real closing `---` plus any following fields (e.g. `action: block`) into the message body. This causes fields after the injected `---` (such as `action`) to be silently dropped, defaulting `action` back to `warn` and truncating the `pattern` value itself.

### Finding Description
In [1](#0-0) , the function checks only that `content.startswith('---')` and then does `parts = content.split('---', 2)`, treating the first two occurrences of the substring `---` anywhere in the file as the frontmatter delimiters, regardless of whether they appear on their own line or embedded inside a YAML value.

Given a rule file such as:
```
---
name: block-x
enabled: true
event: bash
pattern: foo---bar
action: block
---
Blocked message
```
the second `---` encountered by `split` is the one embedded in `pattern: foo---bar`, not the intended closing fence. As a result:
- `parts[1]` (used as `frontmatter_text`) ends at `pattern: foo`, silently truncating the pattern value and dropping `action: block` (and anything after it) from the parsed frontmatter.
- `parts[2]` (used as the message body) becomes `bar\naction: block\n---\nBlocked message`, i.e., the real closing fence and the `action` field are now embedded as literal text in the message, not parsed as YAML.

When `Rule.from_dict` builds the `Rule` object ( [2](#0-1) ), the missing `action` key falls back to the default `action = "warn"` ( [3](#0-2) ), and the `pattern` used for matching is the truncated `"foo"` instead of `"foo---bar"`. There is no line-anchored delimiter check (e.g. `^---\s*$` on its own line), no escaping/quoting awareness, and no validation that the resulting frontmatter dict actually contains all expected keys before use — `load_rule_file` only checks that `frontmatter` is non-empty ( [4](#0-3) ), so the corrupted-but-non-empty frontmatter passes silently.

### Impact Explanation
This is a rule-integrity/parser-confusion bug in a component whose entire purpose is to enforce security policy (`action: block` is meant to prevent dangerous Bash/file operations per `RuleEngine`). If a `pattern` value legitimately or maliciously contains `---` (e.g., a pattern meant to match a compound shell command like `rm -rf / ---> danger`, or any regex/text with three consecutive dashes), the resulting rule silently loses its `block` semantics and reverts to `warn`, and/or the pattern is truncated so it may no longer match the intended dangerous input. This is a trust-boundary weakening: a rule the user intended to *block* dangerous operations can be silently downgraded to a no-op warning without any error being surfaced to the user (the file still "loads" because `frontmatter` is non-empty), undermining the enforcement guarantee the plugin advertises.

### Likelihood Explanation
Exploitability depends on how the malformed pattern gets into a rule file. Rule files are normally authored by the user directly or generated by the `/hookify` slash command's subagent, which explicitly analyzes conversation content (including tool outputs) to auto-derive `pattern` values ( [5](#0-4) ). If attacker-influenced text (e.g., content from a malicious repository file, issue/PR text, or tool output that the conversation-analysis subagent ingests) ends up verbatim in a generated `pattern`, and that text contains `---`, the corruption occurs automatically and silently on the very first parse — no special privileges are needed beyond getting attacker-influenced text into a rule's `pattern`/list value. This is a real, deterministic parser bug (not a crash, a silent semantic corruption) reproducible with a simple file 100% of the time whenever `---` appears in a value before the intended closing fence.

### Recommendation
Replace the substring `split('---', 2)` with a delimiter search that only matches `---` when it appears alone on its own line (e.g., `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or iterating line-by-line and only treating a line equal to `---` after stripping as a delimiter). Additionally, after parsing, validate that all frontmatter fields referenced by `Rule.from_dict` were actually captured (e.g., warn/error if `action` was requested via a nearby line but not found), and consider replacing the hand-rolled YAML parser with `yaml.safe_load` scoped strictly to the properly-delimited frontmatter block to eliminate this entire class of bug.

### Proof of Concept
Unit test to add to (or run against) `plugins/hookify/core/config_loader.py`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-x
enabled: true
event: bash
pattern: foo---bar
action: block
---
Blocked message
"""

frontmatter, message = extract_frontmatter(content)

# Expected (correct) behavior: pattern should be "foo---bar" and action "block"
assert frontmatter.get('pattern') == 'foo---bar', frontmatter.get('pattern')  # FAILS: actual value is "foo"
assert frontmatter.get('action') == 'block', frontmatter.get('action')        # FAILS: key missing entirely

rule = Rule.from_dict(frontmatter, message)
assert rule.action == 'block'   # FAILS: rule.action == "warn" (default), block enforcement silently lost
assert rule.pattern == 'foo---bar'  # FAILS: rule.pattern == "foo"
```
Expected result on the current implementation: both assertions on `action` and `pattern` fail, demonstrating that a rule authored as `action: block` with a `---`-containing pattern is silently converted into a `warn` rule with a truncated pattern.
