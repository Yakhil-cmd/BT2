## Confirmed Vulnerability

### Title
API token scoped to one stack can read CI status of any other stack via CCMenu - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper defined in `BaseController` with an unscoped lookup, breaking the binding between "the stack an `ApiClient` token is authorized for" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` implements scoping for all API endpoints: any `ApiClient` created with a `stack_id` is restricted to that single stack, enforced by `stacks`/`stack`: [1](#0-0) 

This is the mechanism that guarantees `stack_id? => Stack.where(id: current_api_client.stack_id)`, i.e. "the stack a token authorizes" equals "the stack a request can touch," for every controller that relies on the inherited `stack` method (e.g. `CommitsController`).

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving the stack directly from the `stack_id` request parameter with no reference to `current_api_client.stack_id`: [2](#0-1) 

The `show` action still declares `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission string — it never checks *which* stack the token is scoped to: [3](#0-2) [4](#0-3) 

Equality that should hold: `token.stack_id == request.stack_id` (enforced in `BaseController#stacks`). After the CCMenu override, this becomes: `token.stack_id` is never consulted at all — any stack ID can be substituted, so the equality is unconditionally broken for this controller.

### Impact Explanation
An `ApiClient` created with `stack_id` set to Stack A (e.g., issued to a single low-trust CI dashboard/integration for one project) can pass an arbitrary `stack_id` for Stack B and receive Stack B's deployment status, last build state/label/time, and lock state, since `CCMenuController#show` renders these fields from whatever `stack` resolves to: [5](#0-4) 

This is an unauthorized cross-stack read of task/deploy state, matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact category — the requester never had `deploy:stack`/`read:stack` authorization for the target stack, only for its own.

### Likelihood Explanation
Likelihood is Medium/High: any holder of a scoped `ApiClient` token (a routine, low-privilege credential type explicitly supported by this engine, e.g. via `CCMenuUrlController#client`) can trivially enumerate other stacks' numeric or slug identifiers and substitute them in the `stack_id` URL/query parameter — no additional exploit chain, timing, or privileged access is required. [6](#0-5) 

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it to delegate through `stacks.from_param!`) so it inherits the scoping behavior of `BaseController#stack`, guaranteeing that a token scoped to stack A cannot resolve any other stack.

### Proof of Concept
1. Create an `ApiClient` with `stack_id: A.id` and `permissions: ['read:stack']` (as done via `CCMenuUrlController#client` in normal usage).
2. Using that client's `authentication_token`, issue: `GET /api/stacks/:B_id/ccmenu?token=<token>` where `B` is a different stack the token was never scoped to.
3. Observe the response returns Stack B's `Project` XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) — despite `current_api_client.stack_id == A.id`, confirming `BaseController`'s scoping in `stacks`/`stack` (lines 74–80) is bypassed for this endpoint.
