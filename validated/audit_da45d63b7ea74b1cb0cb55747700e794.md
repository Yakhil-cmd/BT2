### Title
AA response unit is saved while its author-address validation lock is prematurely released - ([File: aa_composer.js])

### Summary
The Linux CVE fixes a bug where a refactor accidentally moved a call to `rvt_error_qp` outside the scope of `r_lock`, even though the function's contract (and a lockdep assertion) required that lock to still be held, creating a race window on shared queue-pair state. `ocore--019` has the same class of bug in `aa_composer.js`: the per-author-address validation lock (acquired by `mutex.lock(arrAuthorAddresses, ...)` inside `validation.js`) is released *before* the sensitive state-mutating operation (`writer.saveJoint`, which updates `aa_balances` and in-memory AA/unit caches) runs, unlike every other caller of the same validate→save pattern in the codebase.

### Finding Description
`validation.validate()` locks the unit's author addresses for the whole duration of validation and passes an `unlock` callback (`validation_unlock`) to `ifOk`, with the documented/implicit contract that the caller keeps holding this lock until the corresponding `writer.saveJoint` completes, because `saveJoint` mutates state (balances, caches, sequence/`is_stable` flags) keyed by those same addresses.

Every "normal" caller respects this:
- `network.js` `handleJoint`'s `ifOk` calls `validation_unlock()` only inside `writer.saveJoint`'s `onDone` callback: [1](#0-0) 
- `divisible_asset.js` and `indivisible_asset.js` `getSavingCallbacks().ifOk` also defer `validation_unlock()` until after `writer.saveJoint` finishes: [2](#0-1) [3](#0-2) 

But `aa_composer.js`'s `validateAndSaveUnit` (used to validate and save every AA-response unit produced by `handleTrigger`) calls `validation_unlock()` immediately, *before* `writer.saveJoint` runs, and only afterward flags `bUnderWriteLock = true` and invokes `writer.saveJoint`: [4](#0-3) 

This means the author-address lock protecting the AA's address is released while `writer.saveJoint` is still mutating `storage.assocUnstableUnits`, `storage.assocBestChildren`, AA balance caches, and DB rows for that address: [5](#0-4) [6](#0-5) 

Because the lock is released early, any other validation for a unit authored by the same address (e.g. a concurrently-dispatched AA trigger response for the same AA, or a dry-run trigger from `network.js`'s `ifOk` handler which runs under the unrelated `'handleJoint'` mutex and does not take the `'aa_triggers'` lock) can begin reading/mutating the same address's balance state via `mutex.lock(arrAuthorAddresses, ...)` in `validation.js` while the prior write is still in flight: [7](#0-6) [8](#0-7) 

This is structurally the same defect pattern as the CVE: a lock whose scope is documented/relied-upon to cover a state-mutating operation is dropped one step too early after a code change, opening a race window on data keyed by the same lock (there, `r_lock`/QP state; here, the author-address lock/AA balance & cache state).

### Impact Explanation
If two validations for the same AA address interleave because the address lock was released before the write completed, one validation can observe stale/partially-updated balance state (`aa_balances`, `storage.assocBalances`, `storage.assocUnstableUnits`) from the still-in-progress `writer.saveJoint`. This can let an AA response computation proceed against a balance snapshot that does not yet (or does not consistently) reflect a very recent debit/credit, opening the door to AA fund loss/freezing or double-crediting of AA-held funds — i.e., a concrete violation of AA balance-accounting invariants, not merely a performance/DoS issue.

### Likelihood Explanation
The race requires two validations against the *same* author address to be in flight concurrently while one is mid-write. Primary AA trigger processing is serialized by the `'aa_triggers'` mutex, which reduces likelihood for the main trigger-processing loop, but the dry-run trigger path (`aa_composer.dryRunPrimaryAATrigger`, invoked from `network.js` when handling an incoming payment-triggering unit) uses a separate DB connection and is not covered by the `'aa_triggers'` lock, so it can execute concurrently with real trigger processing for the same AA address. Triggering this reliably requires specific timing (posting a triggering unit while a prior trigger for the same AA is still being saved), so likelihood is moderate rather than trivial, but it is reachable by any unprivileged user simply by sending ordinary payments to an AA address.

### Recommendation
In `aa_composer.js`'s `validateAndSaveUnit`, defer the call to `validation_unlock()` until inside `writer.saveJoint`'s completion callback, matching the pattern used in `network.js`, `divisible_asset.js`, and `indivisible_asset.js`, so the author-address lock is held for the full duration of the state mutation: [4](#0-3) 

### Proof of Concept
1. Deploy an AA at address `A` whose triggers update `aa_balances` for `A` (e.g., accumulate a running balance across triggers).
2. Send unit `U1` that triggers AA `A`. `handleTrigger` → `validateAndSaveUnit` validates the AA-response unit, calls `validation_unlock()` immediately (releasing the lock on address `A`), then calls `writer.saveJoint` which begins mutating `aa_balances`/in-memory caches for `A`.
3. Before that `writer.saveJoint` call completes, send unit `U2` (a new payment to `A`) so that `network.js`'s `ifOk` branch triggers `aa_composer.dryRunPrimaryAATrigger` for the same address `A` (enabled via `conf.bDryRunNewTriggers`), which calls `validation.validate`/`mutex.lock([A], ...)` — this lock is free because it was already released in step 2, even though `U1`'s write to `A`'s balance has not finished.
4. The dry run (or, in variants without dry run, another legitimately concurrent code path touching the same address) observes a balance for `A` that is either pre- or mid-update from `U1`'s save, producing a validation/state result inconsistent with the final committed balance — demonstrating the missing-lock race and the potential for balance mis-accounting for AA `A`.
