Confirmed: `ApiClient` supports being scoped to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and the fixture `here_come_the_walrus` demonstrates a real client scoped to the `shipit` stack with only `read:stack` permission [2](#0-1) . `Api::BaseController#stacks` enforces this scope by intersecting with `current_api_client.stack_id` [3](#0-2) , and this scoping is explicitly relied upon and tested elsewhere ("an api client scoped to a stack will only see that one stack") [4](#0-3) .

### Title
Stack-scope bypass in Api::CCMenuController lets a stack-scoped ApiClient token read any other stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack` in a way that discards the stack-scoping enforced by `Api::BaseController`. A token that GitHub-app operators intentionally scope to a single stack (via `ApiClient#stack_id`) can be replayed against `/api/stacks/*stack_id/ccmenu` for any other stack, defeating the "read:stack" permission's intended scope binding.

### Finding Description
`Api::BaseController#stack` resolves the requested stack only from the client's authorized set: `stacks.from_param!(params[:stack_id])`, where `stacks` is `Stack.where(id: current_api_client.stack_id)` when the client is scoped [3](#0-2) . This is the binding: `ApiClient.stack_id` (the stack the token authorizes) == `stack_id` used to load the record.

`Api::CCMenuController` breaks this equality. It authenticates the client independently via a `token` query parameter, `ApiClient.authenticate(params[:token])` [5](#0-4) , and then resolves the requested resource with an unscoped lookup: `Stack.from_param!(params[:stack_id])` [6](#0-5) , instead of the scoped `stacks.from_param!` used by the base controller. `require_permission :read, :stack` only checks that the string `"read:stack"` is present in `current_api_client.permissions` via `ApiClient#check_permissions!` [7](#0-6)  — it never checks which specific stack the permission applies to. Consequently, the deployment-trust binding "the stack a token authorizes" (`ApiClient#stack_id`) diverges from "the stack the request actually touches" (`params[:stack_id]` loaded unscoped).

### Impact Explanation
An attacker holding any valid `ApiClient` token that includes `read:stack` — even one an administrator deliberately restricted to a single, low-sensitivity stack (e.g. handed out to an external CI badge/monitoring integration) — can call `/api/stacks/<any-other-stack>/ccmenu` and read that other stack's build/deploy state: last build status/label/time, lock reason, and activity [8](#0-7) . This is an unauthorized cross-stack read of deploy/task state using a token whose authorization was scoped to a different, specific stack — matching the "unauthenticated/unauthorized read of stack state" High-severity class, since the per-stack scoping restriction that the rest of the API enforces is silently bypassed for this endpoint.

### Likelihood Explanation
Likelihood is high for any deployment that uses `ApiClient#stack_id` scoping (a documented and tested feature) to hand out narrowly-scoped tokens: the only requirement is possessing one such valid, unprivileged, stack-scoped token and knowing (or guessing/enumerating) another stack's identifier — no additional privileges, secrets, or session are required beyond the token itself.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped `stacks` collection from `Api::BaseController` instead of `Stack.from_param!` directly, i.e. `stacks.from_param!(params[:stack_id])`, so `current_api_client.stack_id` scoping is enforced consistently across all API controllers, including this token-in-query-string variant.

### Proof of Concept
1. Admin creates (or the app creates, e.g. via `CCMenuUrlController`-style provisioning) an `ApiClient` scoped to Stack A: `permissions: ["read:stack"], stack: StackA`.
2. Attacker who obtains/possesses this token issues: `GET /api/stacks/<StackB-owner>/<StackB-name>/<env>/ccmenu?token=<TokenScopedToA>`.
3. `authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])` [5](#0-4) ; `require_permission :read, :stack` passes because the token has `"read:stack"` regardless of which stack [7](#0-6) ; `stack` resolves Stack B unrestricted by `current_api_client.stack_id` [6](#0-5) .
4. Response discloses Stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, etc. — data the token was never authorized to access.
