### Title
Cross-repository forged CI status via unscoped `Commit.where(sha:)` lookup enables unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization that signed the webhook, unlike `PushHandler` which scopes via `stacks.where(branch:)` against the verified repository. Because git commit SHAs are content-addressed and therefore reproducible across forks/mirrors of a public repository, any legitimately-onboarded-but-unrelated GitHub organization on the same Shipit instance can post a validly-signed `status` webhook for a SHA that also exists in a victim stack's commit table, and Shipit will apply that status to the victim's commit, potentially triggering `ContinuousDeliveryJob` to deploy it.

### Finding Description
Binding claimed broken, stated as an equality: for every `Status` row with `stack_id == S2.id` and `state == "success"`, `Status.context/target_url` provenance == "produced by CI that actually ran against `S2`'s own commit under `S2`'s own repository/organization". This binding is false in the code.

Path: `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches to `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`). `WebhooksController#verify_signature` (lines 24-49) calls `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`, line 61). This resolves and validates the signature against the `GitHubApp` instance configured for **whatever organization the attacker names in the payload** (`lib/shipit.rb:170-181,196-200`). If the attacker legitimately owns/administers *some* GitHub organization/repository already onboarded to the same Shipit instance (a normal, unprivileged tenant in a multi-org Shipit deployment, per `docs/setup.md` "Using Multiple Github Applications"), they know that org's own `webhook_secret` and can produce a perfectly valid `X-Hub-Signature` for that org — `verify_signature` passes.

Once inside `StatusHandler#process`:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-23`)
This query is **global across all stacks in the database** — it is not scoped by the stack, repository, or organization that was actually authenticated in `verify_signature`. The unique index is `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same `sha` value is expected/allowed to exist for multiple distinct stacks (forks/mirrors). Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes to `stacks.not_archived.where(branch:)` tied to the authenticated repository — `StatusHandler` has no equivalent repository/stack scoping.

`Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:365-386`) creates the `Status`, and if the new `state` is `success`, calls `stack.schedule_merges if new_status.pending? || new_status.success?` and (via `Deploy`/`Stack` state machine wiring, `app/models/shipit/stack.rb`, `app/models/shipit/deploy.rb:10`) schedules `ContinuousDeliveryJob`. `ContinuousDeliveryJob#perform` (`app/jobs/shipit/continuous_delivery_job.rb:10-21`) checks only `stack.continuous_deployment?`, schedule/occupied checks, then calls `stack.trigger_continuous_delivery`, which picks `next_commit_to_deploy` and deploys it — with `ignore_ci?` false, `deployable?` requires the forged `success` status, which the attacker just supplied.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with **their own org's** `webhook_secret`, and a JSON body `{"repository":{"owner":{"login":"attacker-org"}}, "sha": "<S2's commit sha>", "state": "success", ...}`. Repeated once per undeployed commit in S2, in order.

Why existing guards fail: `verify_signature` only proves the payload was signed by *some* configured org's secret — it never re-checks that the `sha` being mutated actually belongs to a commit under that same org/repository. `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, String; requires :state, String`) only validate shape, not ownership. There is no `Repository` full_name check, no stack ownership check, no `require_permission!`/`current_api_client` check (this is an unauthenticated webhook endpoint by design) that ties the `sha` lookup back to the authenticated repository.

### Impact Explanation
A payload correctly authenticated for one repository/organization can mutate `Commit`/`Status` state — and thereby trigger real deploy tasks (`Command`/`PTY.spawn` execution via `Deploy`/`Task`) — belonging to a completely different repository's stack, as long as SHAs coincide (trivially achievable via forking/mirroring a public repo, which preserves SHAs exactly). This matches the explicitly listed Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". The attacker can walk S2's entire undeployed commit range and, with `continuous_deployment?` true and `ignore_ci?` false, drive `ContinuousDeliveryJob` to actually deploy those commits to S2's production infrastructure — full unauthorized continuous deployment, repeatable for every future commit and for any stack sharing this Shipit instance whose SHA the attacker can reproduce.

### Likelihood Explanation
Preconditions: (1) Shipit instance hosts multiple GitHub organizations/repositories as tenants (a documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), or a single org where the attacker can still name any `repository.owner.login`; note that if Shipit is configured single-org and the attacker does not already control a valid onboarded org's `webhook_secret`, `verify_signature` will reject them, so the fully unauthenticated cross-org variant strictly requires a multi-tenant deployment where the attacker legitimately controls at least one onboarded org (still "unprivileged" w.r.t. the victim S2). (2) Victim stack S2 has `continuous_deployment? == true`, `ignore_ci? == false`. (3) Attacker can reproduce S2's commit SHAs by forking/mirroring the public repo. Given those, the attacker's cost per commit is one signed HTTP POST; the attack is fully repeatable and scriptable across S2's entire backlog with zero interaction with S2's maintainers or actual CI. This is a genuine bug in the engine's request-authorization logic (missing repository/stack scoping in `StatusHandler`), not a third-party/config issue, so it is in scope.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the verified webhook payload (mirroring `PushHandler`'s `stacks.where(...)` pattern), e.g. resolve `Repository.find_by(owner: repository_owner, name: repo_name)` and constrain `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`, rejecting/no-oping otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub, using stubs already present in that file):
1. Create two `GitHubApp`-backed orgs in `Shipit.github` config: `"attacker-org"` with known `webhook_secret_a`, and `"victim-org"` with `webhook_secret_v` (unknown to attacker in the test, but not needed since the attacker signs with their own).
2. Create `stack_v = shipit_stacks(...)` under `victim-org/repo`, with `continuous_deployment: true`, `ignore_ci: false`, and several undeployed `Commit` rows with real/reproducible SHAs (`sha_1..sha_n`), none of which have any `Status`.
3. For each `sha_i`, POST to `/webhooks` with `X-Github-Event: status`, body `{"repository":{"owner":{"login":"attacker-org"}}, "sha": sha_i, "state": "success"}`, and `X-Hub-Signature` computed with `webhook_secret_a` (i.e., signed as `attacker-org`, never touching `victim-org`'s secret).
4. Assert each request returns `:ok`, and `Commit.find_by(sha: sha_i, stack: stack_v).statuses.last.state == 'success'` — proving the binding "sha marked success for S2 == built against S2's own CI" is false, since S2's CI/webhook_secret was never involved.
5. Assert `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_v])` fires after the last commit's status update, and running `ContinuousDeliveryJob.new.perform(stack_v)` creates a `Deploy` for `stack_v` (`assert_difference "Deploy.count"`), demonstrating unauthorized production deployment of the victim stack driven entirely by attacker-signed traffic from an unrelated organization.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
