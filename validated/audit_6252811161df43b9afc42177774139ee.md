### Title
Cross-organization webhook signature confusion allows forged push/pull_request events for unrelated repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook against by reading an **unauthenticated** field from the same request body (`repository.owner.login`, falling back to `organization.login`), then uses that org's `webhook_secret` to verify `X-Hub-Signature` over the raw body. [1](#0-0)  Once the signature validates, the event handlers (e.g. `PushHandler`, pull-request handlers) resolve the target `Repository`/`Stack` using a *different* field from the same body — `repository.full_name` — via `Repository.from_github_repo_name`, with no cross-check that this repository actually belongs to the organization whose secret was used to authenticate the request. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
This is a direct analog of the reported `LibBytes.keccak` bug class: a value used to select/derive the "trusted" bound (there, `offset`/`length` bounding the hashed memory region; here, the *organization* whose secret is trusted for signature verification) is taken from attacker-controlled input without being checked against the value that is actually *acted upon* (there, `data.length`; here, `repository.full_name` used to look up and mutate a `Stack`).

Concretely:
- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` — both attacker-supplied JSON fields inside the raw POST body. [5](#0-4) 
- It then fetches the `GitHubApp`/secret for that `repository_owner` and verifies the signature against the *entire* raw body using that org's `webhook_secret`. [6](#0-5) 
- Because the HMAC covers the whole raw body, anyone who knows (or controls) the `webhook_secret` for **any one** organization configured in Shipit can craft a body where `repository.owner.login` equals that organization (so the correct secret is picked and the signature validates) while `repository.full_name` names a repository belonging to a **completely different** organization/stack.
- The handler layer trusts `repository.full_name` unconditionally to locate the `Repository`/`Stack` to act on (`Repository.from_github_repo_name(repository_name)`), with no comparison back to `repository_owner`. [2](#0-1) 
- For `push` events this drives `Stack#sync_github` / `GithubSyncJob`, which fetches commits from GitHub and appends them to the stack's commit history, potentially triggering downstream continuous-deployment/merge behavior for a stack the attacker does not own. [7](#0-6) [8](#0-7) 
- The `pull_request` family of handlers exhibits the same pattern: they parse `params.repository.full_name` from the body and use it to look up `Repository`/`PullRequest`/review stacks to archive, unarchive, label-capture, or provision, again without confirming that `full_name`'s owner matches the org whose secret signed the request. [9](#0-8) [10](#0-9) 

The broken binding, stated as an equality that the code implicitly (and wrongly) assumes but never enforces:
`organization authenticated by signature (repository.owner.login / organization.login)` ⇒ should equal ⇒ `organization of the repository whose Stack is written to (repository.full_name)`.

### Impact Explanation
An attacker who legitimately administers a GitHub App/webhook for **any** organization that has a Shipit `GitHubApp` configuration (and therefore knows that org's `webhook_secret` — this is normal, non-privileged knowledge for whoever configures that org's own webhook, not a Shipit credential) can forge signed webhook deliveries whose `repository.full_name` targets a stack belonging to an unrelated organization/repository also configured in the same Shipit instance. This can trigger unauthorized GitHub sync jobs, commit ingestion, PR-driven review-stack archiving/unarchiving/provisioning, or other stateful side effects on a repository the attacker does not control — i.e., cross-repository/cross-organization writes via a spoofed trust boundary, without needing an `ApiClient` token, session, or repository write access on GitHub itself.

### Likelihood Explanation
Requires the attacker to control a `webhook_secret` for *some* organization already configured in the Shipit instance (a low bar if Shipit is multi-tenant across orgs with different trust levels, since each org's admin can see/rotate their own secret) and to know that another organization's repository is tracked by the same Shipit instance (discoverable via the public Shipit UI/API for stacks). No GitHub-side compromise of the victim org is required.

### Recommendation
In `WebhooksController#verify_signature` / `Webhooks::Handlers::Handler`, after signature verification, assert that the repository/organization actually acted upon (`payload.dig('repository','full_name')`'s owner, or `payload.dig('repository','owner','login')`) matches the organization key used to select the `webhook_secret`, and reject the request (422) if they diverge. Equivalently, resolve `repository_owner` from the same field that handlers use to select the target repository, and never allow `organization.login` (from an org-level webhook, distinct from `repository.owner.login`) to authorize actions against a differently-owned `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `OrgA` and `OrgB`, each with their own `webhook_secret` in `config/secrets.yml` (as shown in `docs/setup.md`). [11](#0-10) 
2. Attacker administers `OrgA`'s own GitHub App/webhook and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"` from `repository.owner.login`, fetches `OrgA`'s `GitHubApp`, and the signature validates against `OrgA`'s secret. [1](#0-0) 
6. `PushHandler` is invoked with the full payload; it resolves the target repository via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, looks up `OrgB`'s stacks, and calls `stack.sync_github(expected_head_sha: ...)` — acting on `OrgB`'s stack despite the request only being authenticated for `OrgA`. [7](#0-6) [4](#0-3) 

Note: I could not fully trace whether `Stack#sync_github` alone (without additional deploy-trigger configuration such as continuous deployment) results in an actual unauthorized deploy versus just commit-ingestion; this would need to be confirmed in a live/staging environment, as I ran out of tool iterations to inspect `Stack#sync_github`'s full body and any auto-deploy hooks it may trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))

        end

          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
```
