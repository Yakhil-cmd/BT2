## Analysis

The Envoy CVE class is: a security decision is made using an imprecise string-matching primitive (raw substring/prefix comparison) instead of an exact, boundary-aware comparison, allowing an attacker-controlled value to be misclassified as matching/not-matching a rule it shouldn't.

The closest reachable analog in `ocore--009` is in the arbiter-contract dispute-request handler in `wallet.js`, where a **prefix check on signing paths** is used to decide whether a shared address's mutual definition was actually co-signed by both contract parties, without enforcing a path-segment boundary. [1](#0-0) 

### Title
Improper prefix matching of authentifier signing paths allows bypass of the "mutually signed" check in arbiter dispute requests - (File: wallet.js)

### Summary
`handleMessageFromHub`'s `arbiter_dispute_request` handler verifies that the shared address author of the referenced signing unit was actually signed by both contract parties by checking `signing_paths.find(p => p.startsWith('r.0.0'))` and `signing_paths.find(p => p.startsWith('r.0.1'))`. `startsWith` performs a raw substring/prefix comparison with no path-segment boundary check, exactly the bug class described in CVE-2019-18802 (Envoy compared `"header-value "` vs `"header-value"` as different strings, letting mismatched values slip past matchers). Here the inverse problem occurs: `"r.0.10"`, `"r.0.11"`, ... `"r.0.19"`, `"r.0.100"`, etc. are **siblings** of `"r.0.1"` (both are 3-segment paths that are children of node `"r.0"`), yet `"r.0.10".startsWith("r.0.1")` evaluates to `true`, causing the code to treat a completely different branch's authentifier as if it were the acceptor's (`r.0.1`) signature.

### Finding Description
The mutual-signing address definition created for arbiter contracts places the offeror's authentifier at path `r.0.0` and the acceptor's at path `r.0.1`, per `mutualPart[0]`/`mutualPart[1]` destructured a few lines later at [2](#0-1) . `arbiter_contract.js` supports attaching an arbitrary number of additional `cosigners` to the shared address definition (`createAndSend` serializes `objContract.cosigners` into the stored contract, [3](#0-2) ). If the underlying shared address definition contains 10 or more elements at the same tree level as the mutual `r.0.0`/`r.0.1` branches (achievable via extra cosigners or a crafted nested `and`/`or` array), a signature that is authenticated at path `r.0.10`, `r.0.11`, … will falsely satisfy `p.startsWith('r.0.1')`, even though it has nothing to do with the acceptor's branch.

Because `objUnit` here is a unit that has already passed full consensus/definition validation (fetched via `storage.readUnit` / `network.requestHistoryFor`), the *signature itself* is cryptographically legitimate — it's legitimately produced by some cosigner in the shared address. The bug is purely in the wallet's post-hoc heuristic that infers "the offeror and acceptor both consented" from prefix-matching authentifier path strings, which is not equivalent to "path is an ancestor of / equal to the authentifier path."

### Impact Explanation
An attacker who is one of the two contract parties (the "offeror", who legitimately signs at `r.0.0`) can craft/agree on a shared-address definition with ≥10 sibling branches at the level containing `r.0.1`, obtain any additional signature under one of the colliding sibling paths (e.g. `r.0.10`), and submit that unit as evidence to the arbstore for `arbiter_dispute_request`. The `isMutuallySigned` check will incorrectly pass, allowing a dispute to be raised and inserted (`arbiter_contract.insertDispute`) as if the contract were genuinely mutually signed by both the offeror and the real acceptor, even though the real acceptor's branch (`r.0.1` proper) was never signed. This can lead the arbiter to process and resolve a dispute — and potentially release/move contract funds — over a contract that lacks genuine two-party consent, i.e., unauthorized use of the arbiter fund-resolution flow. This is a wallet/contract message-handling authorization bypass, matching the scope's "wallet and contract message handling" category.

### Likelihood Explanation
Exploitation requires the attacker to control (or collude on) the shared address definition construction (feasible since one of the two parties composes/agrees to cosigners) and to get any authentifier signed at a colliding sibling path — not necessarily malicious cosigner, just enough branches to create the collision. This requires deliberate crafting of the contract definition ahead of time, so it is not trivially remote, but it is fully reachable by an unprivileged contract counterparty without server/node compromise, satisfying the "reachable by AA/contract counterparty" scope.

### Recommendation
Replace the `startsWith` prefix check with a boundary-aware path comparison, e.g. split both strings on `.` and compare exact path segments (`path === 'r.0.0' || path.startsWith('r.0.0.')`), or use the same authentifier-path prefix utility already used elsewhere in the codebase — `pathIncludesOneOfAuthentifiers` in `definition.js` — but fix that helper too, since it has the identical `substr(0, path.length) === path` boundary flaw: [4](#0-3) .

### Proof of Concept
1. Offeror composes an arbiter contract whose shared address definition places the offeror at `r.0.0`, the acceptor at `r.0.1`, and additionally includes 9+ more cosigner branches at the same array level (indices 2–10+), so that one of them resolves to authentifier path `r.0.10`.
2. Get the signing unit signed only by the offeror (`r.0.0`) and by cosigner #10 (`r.0.10`) — not by the actual acceptor.
3. Submit `arbiter_dispute_request` to the arbstore referencing this unit.
4. `signing_paths.find(p => p.startsWith('r.0.1'))` matches `"r.0.10"`, so `isMutuallySigned` is `true` and the dispute request passes validation despite the acceptor never having signed under `r.0.1`.
