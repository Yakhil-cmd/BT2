### Title
Integer overflow in `renderAllFiles` size-limit check allows attacker-controlled repository to bypass the 512KB rendering cap - ([File: pkg/cmd/skills/preview/preview.go])

### Summary
`gh skills preview` fetches files from an arbitrary, attacker-controlled repository/skill (identified by `owner`, `repoName`, and `opts.SkillName`) and imposes a `maxTotalBytes` (512KB) cap on how much content it will dump to the terminal, enforced by the check `totalBytes+f.Size > maxTotalBytes` at [1](#0-0) . The `f.Size` value for each `discovery.SkillFile` originates from the untrusted target repository's Git tree metadata, and the addition is done with plain (non-checked) integer arithmetic, directly mirroring the reported bug class: an attacker-influenced value participating in an unchecked arithmetic comparison that is meant to gate further, unbounded actions.

### Finding Description
In `renderAllFiles`, the loop over `extraFiles` (files belonging to a skill hosted in a repository that can be any GitHub repo the invoking user points `gh skills preview` at) enforces two guards: a max file count (`maxFiles = 20`) and a max cumulative byte budget (`maxTotalBytes = 512 * 1024`): [1](#0-0) 

The critical check is:
```go
if totalBytes+f.Size > maxTotalBytes {
    ...
    break
}
```
`f.Size` is populated from the file metadata (`SkillFile.Size`) returned by the GitHub Git Trees API for the repository being previewed — content that is fully attacker-controlled, since the attacker owns/controls the repository that a victim is asked to preview a skill from. This mirrors the report's root cause: an unchecked arithmetic operation on a value that a malicious actor can set to an extreme number, causing a comparison intended to bound behavior to evaluate incorrectly (there, `expiry - windowSize` underflowed to `2**256-1`; here, `totalBytes + f.Size` can overflow the signed integer range and wrap to a very large negative number).

Although Go's `int` is 64-bit on common platforms, `f.Size` is attacker-supplied and could be set to a value close to `math.MaxInt64` in the tree metadata. Because the addition is unchecked, `totalBytes + f.Size` can overflow into negative territory, making `totalBytes+f.Size > maxTotalBytes` false even though the "real" intended sum vastly exceeds the cap. This would let the size-limit guard be silently bypassed for every subsequent file, defeating the intended per-preview size guard (`renderAllFiles` continuing to fetch and print all remaining files regardless of the 512KB cap), similar in spirit to the interactive path (`renderInteractive`) which has no equivalent per-file limit at all.

### Impact Explanation
If the overflow is achieved, `gh skills preview` will continue calling `discovery.FetchBlob` for every remaining file in the attacker's repository and print all of that content to the user's terminal, bypassing the explicit 512KB safety cap that exists specifically to bound this. This is a resource-exhaustion / guard-bypass issue reachable purely by pointing `gh skills preview` at an attacker-controlled repository (an "attacker-published content" scenario), similar to the flagged bug class ("check bypass due to unchecked arithmetic on attacker-influenced values"). It does not, on its own, grant code execution or credential exfiltration, and its exploitability is bounded by the practical difficulty of an attacker actually producing a `Size` field near `MaxInt64` that the GitHub tree API and JSON decoder will accept and propagate unmangled, and by whatever OOM/output limits exist elsewhere in the terminal-output path [1](#0-0) .

### Likelihood Explanation
Moderate-to-low. The attacker fully controls the `Size` value returned in the tree metadata of their own repository, so triggering the arithmetic is trivial from a data-crafting perspective; the main uncertainty (which I could not fully verify due to index limits) is (a) the exact Go type of `SkillFile.Size` and how it's parsed from the GitHub API JSON (`int` vs `int64` vs `json.Number`), and (b) whether any intermediate validation clamps the value before it reaches this comparison. I was unable to fully inspect `internal/skills/discovery/discovery.go` for the `SkillFile` struct definition and the tree-parsing logic due to tool/iteration limits, so the exact overflow threshold and whether decoding would reject an out-of-range or malformed `size` field is unconfirmed.

### Recommendation
- Perform the size-limit comparison using overflow-safe arithmetic (e.g., check `f.Size < 0 || f.Size > maxTotalBytes-totalBytes` instead of `totalBytes+f.Size > maxTotalBytes`), or use `math/bits`-based overflow detection, or bound `f.Size` to a sane maximum (e.g., reject/clip any file whose reported size is negative or larger than `maxTotalBytes`) before it participates in the running total.
- Validate and clamp all size/length fields obtained from untrusted repository metadata immediately after decoding, rather than trusting them in later arithmetic.
- Apply the same treatment to `renderInteractive`, which currently has no equivalent size guard at all for fetched blobs.

### Proof of Concept
Conceptual (not run against a live environment, since I only have read access to source):
1. Attacker creates a public GitHub repository containing a `SKILL.md` and several additional files.
2. Attacker crafts the repository's Git tree so that one file's `size` metadata field is a value close to `math.MaxInt64` (or otherwise engineered so that `totalBytes + f.Size` wraps to a negative number in Go's signed 64-bit arithmetic).
3. Victim runs `gh skills preview <skill> --repo attacker/repo`.
4. In `renderAllFiles`, the check `totalBytes+f.Size > maxTotalBytes` [2](#0-1)  evaluates false due to the overflow, so the size-limit break never triggers.
5. `gh` proceeds to fetch and print every remaining file in the attacker's repository to the victim's terminal, exceeding the intended 512KB cap — a caveat given the unverified exact type/decoding behavior of `SkillFile.Size` noted above.
