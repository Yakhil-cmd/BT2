### Title
Permissionless `update_indexes` lets anyone force per-step reward truncation, diverting all supplier yield to protocol revenue - (File: `contracts/pool/src/interest.rs`, `common/src/rates/index.rs`)

### Summary
An unprivileged caller can invoke `Controller::update_indexes` every ledger (Soroban ledgers close ~every 5s), forcing `global_sync` to accrue interest in very small `delta_ms` steps. In each step, `update_supply_index` computes the new index as `floor((supplied·index + rewards)·RAY / supplied)`. When the per-step supplier reward is smaller than one atomic index unit per share (`rewards·RAY / supplied < 1`), the supply index does not move, so `supply_index_reward_shortfall` classifies the entire step's supplier reward as shortfall and books it — together with the reserve fee — as protocol revenue shares. Repeating this every ledger permanently redirects supplier yield to protocol revenue. This is the same bug class as the report: a callable-by-anyone accrual update whose per-token/per-share division truncates to zero.

### Finding Description
- `Controller::update_indexes` is an unprivileged entrypoint (it is in the reachable-entrypoint list and is invoked by the public keeper service in `services/keeper/src/stellar/invoke.rs` / `services/keeper/src/scheduler/tasks.rs`), which calls the pool and drives `interest::global_sync` (`contracts/pool/src/interest.rs:20-33`). Every user action (supply/borrow/withdraw/repay/liquidate) also triggers it.
- `accrue_step` (`common/src/rates/simulate.rs:51-94`) computes `supplier_rewards` via `calculate_supplier_rewards` and calls `update_supply_index`.
- `update_supply_index` (`common/src/rates/index.rs:29-45`) uses `mul_div_floor_saturating(new_value, RAY, supplied)` — a floor division over total supplied shares. If `rewards_increase` is small enough relative to `supplied`, `grown == old_index` and the index is unchanged.
- `supply_index_reward_shortfall` (`common/src/rates/index.rs:53-64`) then returns `rewards_increase − 0 = rewards_increase`, and `accrue_step` adds it to `protocol_reward`, minting `revenue_shares` to the protocol (`common/src/rates/simulate.rs:72-87`; `accrue_chunk` calls `cache.accrue_revenue` at `contracts/pool/src/interest.rs:52`).
- Making `delta_ms` tiny shrinks `accrued_interest` linearly (`borrowed · (index'−index)`), while `supplied` stays large, so the truncation condition `rewards·RAY < supplied·(1 index-unit)` is satisfiable on every ledger when total supply is large. Revenue shares minted each step also grow `supplied`, making subsequent truncation easier. The borrow index still grows (a multiplication, capped at `MAX_BORROW_INDEX_RAY`), so borrowers keep accruing debt — only the supplier side is starved.

### Impact Explanation
Total loss of supplier yield on affected markets for as long as the attacker keeps accrual steps below the truncation threshold: every unit of borrower interest net of nothing effectively lands in `revenue` shares instead of the supply index. This is theft/redirection of unclaimed yield (a Medium under the stated criteria). Suppliers' principal is not touched and withdrawals still work; no insolvency.

### Likelihood Explanation
No privilege needed — `update_indexes` only requires submitting a transaction each ledger, and even benign keeper cadence partially exhibits the effect. Feasibility scales with `supplied`: markets with large total supply (or low utilization/low rate) hit the truncation bound at longer intervals, so an attacker can trigger it less often. Caveat: cadence-dependent rounding and shortfall-to-revenue booking are partially documented design properties (ADR-0016 "does not eliminate … cadence dependence, or rounding error"; `contracts/pool/README.md:232-236`), which may reduce severity to Medium or lead the program to classify the rounding-by-design aspect out of scope; the specific exposure here is that an unprivileged caller can *choose* the worst-case cadence deterministically.

### Recommendation
- Gate `update_indexes` (or the pool accrual) with a minimum accrual interval, e.g. no-op `global_sync` when `elapsed_ms < MIN_ACCRUAL_DELTA_MS` chosen so per-step rewards reliably exceed one index unit.
- Alternatively carry forward undistributed rewards: keep an accumulator of `shortfall` that is only booked as revenue once it exceeds a threshold, otherwise re-add it to the next step's `supplier_rewards`.
- Or revert/skip supply-index update when `rewards > 0` but `grown == old_index`, leaving `last_timestamp` untouched so rewards accumulate until they clear the floor.

### Proof of Concept
1. Market state: `supplied = S` shares, `borrowed = B` shares, utilization > 0, borrow rate `r` annual, reserve factor `f`.
2. Attacker calls `controller.update_indexes` at timestamp `t0`; pool runs `global_sync`, sets `last_timestamp = t0`.
3. Wait one ledger (`Δ ≈ 5_000 ms`). Interest ≈ `B·index_borrow·r·Δ/year` (RAY). Supplier rewards `R = interest·(1−f)`.
4. Choose/confirm `R·RAY / S` floors to < 1 index unit — i.e. `R < S/1e27` in index terms. For large `S` this holds at 5s steps (e.g. `S ≈ 10⁶` RAY-scaled shares, low single-digit APR, small `B`: `R` per 5s is ~`10⁻⁴` of the threshold).
5. Attacker submits `update_indexes` in the same ledger. `update_supply_index` returns `old_index`; `supply_index_reward_shortfall` returns `R`; `accrue_revenue` mints `R/index'` revenue shares.
6. Repeat every ledger. Over the period, supply index grows only when the keeper's own cadence accidentally leaves a longer gap; all forced-step rewards accrue to `revenue`. Assert via `get_bulk_indexes`/views: `supply_index` flat while `borrow_index` rises and `revenue` grows — supplier claim (`shares·index`) shows zero interest for the window despite positive utilization and ongoing borrower interest.

I was unable to re-verify the exact auth decorator on `Controller::update_indexes` (search returned only call sites before the iteration limit), but the task rules list `update_indexes` among entrypoints reachable by an unprivileged address and it is invoked by an external keeper service, consistent with it being permissionless.
