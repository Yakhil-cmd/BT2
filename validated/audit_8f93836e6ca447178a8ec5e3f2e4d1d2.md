### Title
Fork-controlled pull-request label names become process environment variable keys (e.g. `PYTHONPATH`) for `ReviewStack` deploy commands - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash used to build task commands, with no allowlist against reserved/dangerous variable names. Because this hash flows unfiltered into `Command#unbundled_env` and then `PTY.spawn`, an unprivileged PR author can force arbitrary environment variable *names* — including `PYTHONPATH`, `RUBYOPT`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, etc. — to be set for every command Shipit runs for their review stack's deploy.

### Finding Description
The expected binding is: `Command#unbundled_env` for a stack's deploy/task steps should equal `BASE_ENV.merge(stack-and-task-controlled keys)`, where the key set is fixed and does not include attacker-chosen names. In reality:

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
```
Every label the PR author attaches to their own pull request becomes a hash key (uppercased), unconditionally merged with no allowlist or denylist. Labels are captured verbatim from webhook payloads by `LabelCapturingHandler#capture_labels`, so the label text is fully attacker-controlled (an unprivileged user can create labels on a repository they own/fork and open a PR against the target repo, or the label list arrives from `pull_request.labels` payload data mirrored from the webhook).
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `@stack.env` (i.e., this attacker-influenced hash for review stacks) into the environment used to construct every `Command.new(..., env:, ...)` for install/deploy/rollback steps.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the caller-supplied `@env` wins over `BASE_ENV`, so any reserved variable name present as a label overrides the sanitized base environment.
- This merged hash is passed straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at `lib/shipit/command.rb:92`.

No code in this path (`ReviewStack#env`, `Stack#env`, `TaskCommands#env`, `Command#initialize`/`#unbundled_env`) filters keys against a reserved list. `EnvironmentVariables#permit` (used elsewhere for stack/task custom env) is not invoked here — `ReviewStack#env` bypasses it entirely by writing straight into a plain hash. There is no `verify_signature` or authorization gap being exploited; the label value itself is legitimately attacker-supplied because they own the PR/label on their side of a fork-based review stack.

One important caveat verified in code: the injected value is always the literal string `"true"` (`labels[label_name.upcase] = "true"`), not an attacker-chosen path. The attacker controls the *variable name* but not its *value*. This still breaks the intended invariant ("no fork-controllable key such as `PYTHONPATH`"), and remains exploitable because the attacker also controls the git checkout content used as `chdir` for these commands (their own PR branch): they can create a directory or file literally named `true` inside their branch (e.g., `true/os.py` or similar), so that `PYTHONPATH=true` (interpreted as a path relative to `chdir`) causes a subsequent Python step invoked by the deploy spec to resolve imports from attacker-supplied code in that directory.

I was not able to locate a `deploy.variables` phase specifically named as such inside `app/models/shipit/deploy_spec.rb` in the indexed content (only README references to `deploy.variables` were found); the vulnerable env-merging happens generically for all commands built via `TaskCommands#env` for a `ReviewStack`, not a phase-specific code path I could directly confirm. This should be treated as an open uncertainty and re-verified by a Devin session with full file access before final triage.

### Impact Explanation
Any command executed for a `ReviewStack`'s task (dependency install steps, deploy steps, rollback steps) inherits an environment where the fork PR author fully controls which env variable *names* are forced to `"true"`, and fully controls the file system layout of the working directory used as `chdir`. Combined, this can be leveraged for local code/module hijacking (e.g., `PYTHONPATH=true` combined with a `true/` directory checked into the PR branch containing malicious `.py` files that shadow standard library or expected imports), which is a path toward command execution on the Shipit deploy host under the deploy task's privileges — matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" class, though the practical exploit chain requires that a step in the deploy definition performs an unqualified Python import while the working directory is attacker-influenced. This affects only review stacks for the target repository/PR (not cross-tenant by itself), since `pull_request.labels` are scoped to that stack's own PR.

### Likelihood Explanation
Requires: `provisioning_behavior=allow_with_label` (or any config path making `ReviewStack` process PR labels), a fork PR the attacker controls, and a deploy/task definition that performs a Python import (or similarly PATH/ENV-sensitive operation) without hardening against `PYTHONPATH`/similar variables. The attacker cost is trivial — open a PR, add a label, ensure a `true` (or similarly named) directory exists in the checkout. Feasibility of achieving full RCE depends on the exact deploy steps defined by the target repo's `shipit.yml`, which is a meaningful precondition not fully confirmed in this pass.

### Recommendation
In `ReviewStack#env`, do not merge raw uppercased label names as hash keys. Either: (1) prefix all label-derived keys with a fixed non-colliding namespace (e.g., `LABEL_<NAME>`) so they can never collide with real environment variables like `PYTHONPATH`, `LD_PRELOAD`, `RUBYOPT`, `PATH`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`; or (2) validate label-derived keys against a strict allowlist/denylist of reserved variable names before merging, rejecting or dropping any that match known-sensitive names.

```ruby
test "PR labels cannot inject reserved environment variable names" do

  pull_request = stack.pull_request
  pull_request.update!(labels: ["pythonpath"]) # attacker-controlled label, unprivileged

  env = stack.env

  # Binding under test: reserved/dangerous env var names must not be attacker-settable
  refute env.key?("PYTHONPATH"), "fork-controlled label leaked into PYTHONPATH env key"

test "Command spawned for review stack task does not receive attacker-forced PYTHONPATH" do
  stack = shipit_review_stacks(:review_stack)
  stack.pull_request.update!(labels: ["pythonpath"])
  task_commands = Shipit::TaskCommands.new(stack.deploys.last)

  command = Shipit::Command.new("python3 -c 'print(1)'", env: task_commands.env, chdir: Dir.tmpdir)

  assert_nil command.unbundled_env["PYTHONPATH"], "PYTHONPATH should not be attacker-settable via PR label"
end
```
Both assertions are expected to currently fail against `app/models/shipit/review_stack.rb:84-93`, demonstrating the divergence between the intended invariant (no fork-controllable reserved env key) and the actual merged environment.
