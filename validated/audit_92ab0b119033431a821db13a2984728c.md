### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App/org identified by the payload's `repository.owner.login` (or `organization.login`) field, but the `status` event handler (`Shipit::Webhooks::Handlers::StatusHandler`) never uses that `repository` field to scope which commit gets updated — it looks up commits purely by `sha`, globally, across every stack and every repository. This breaks the binding "organization that authenticated == repository that is written," matching the analog of the Hubble finding where a field used to pass one check (order provenance/price) is not the field actually acted upon (execution price).

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate the signature against solely from `repository_owner`, which is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

Once the signature check passes (i.e., the request is authenticated as coming from *some organization X* that owns the repository named in the payload), the full, attacker-controlled `params` blob is forwarded unchanged to every handler registered for the event: [3](#0-2) 

For the `status` event, `StatusHandler#process` only requires `sha`/`state`/etc. and never requires or validates the `repository` field at all, then updates **every** `Commit` row across the whole database matching that raw sha: [4](#0-3) 

Contrast this with other handlers in the same codebase (`CheckSuiteHandler`, the `PullRequest::*` handlers) which correctly scope their side effects through `stacks`/`repository`, derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [5](#0-4) [6](#0-5) [7](#0-6) 

So the equality that should hold — *(organization whose webhook secret authenticated the request) == (repository/stack whose commit is mutated)* — is never enforced for `status` events. The signature only proves "this request came from an app/org that owns *a* repository named in the payload"; it proves nothing about which `Commit` rows the handler will touch, because the handler ignores that field.

### Impact Explanation
Git commit SHAs are content-addressed and identical across forks/mirrors of the same history. Any GitHub organization/App installation that Shipit trusts (including one that legitimately owns some unrelated repository) can deliver a validly-signed `status` webhook whose `sha` matches a commit that also exists in a *different*, unrelated stack (e.g., an upstream repo that was forked, or any repo sharing common ancestor commits). Because `StatusHandler` performs `Commit.where(sha: params.sha)` with no repository/stack filter, this single legitimately-signed webhook will create/update a `CommitStatus` on commits belonging to a completely different repository/stack that the sending organization does not own.

Commit statuses are used by Shipit's `ci.require` deploy-gating checks (`Commit#deployable?`), meaning a party who can only trigger webhooks for their own (unrelated, trusted-by-Shipit) organization can forge a "success" status on a commit belonging to a different stack, defeating the CI-gate and enabling an unauthorized deploy — i.e., a cross-repository write leading to an unauthorized ship, which is in-scope Critical/High impact per the rules (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
This requires no privileged Shipit session, API token, `webhook_secret`, or GitHub App private key belonging to the *target* organization — only a webhook subscription belonging to *any* organization Shipit already trusts (which, per the setup docs, is routine: any team onboarded onto the same Shipit instance controls their own GitHub App/webhook config). SHA collisions across forked/mirrored repositories are common in real engineering organizations (monorepo forks, vendored branches, template repos), making this practically reachable rather than purely theoretical, and the code path (`StatusHandler`) is unconditionally reachable from the public `/webhooks` endpoint.

### Recommendation
`StatusHandler#process` must scope commit lookup/update to the repository identified by the authenticated `repository.owner.login`/`repository.full_name`, mirroring the `stacks`/`repository` scoping already used in `CheckSuiteHandler` and the `PullRequest::*` handlers, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently constrain the `Commit.where(sha: ...)` query with `.joins(stack: :repository).where(repositories: { id: repository.id })`, and make `repository.full_name` a required parameter so the binding between the authenticating organization and the mutated repository is enforced.

### Proof of Concept
1. Two stacks exist on the same Shipit instance: `orgA/upstream` (target, gated by `ci.require`) and `orgB/fork` (attacker-controlled fork of `orgA/upstream`, sharing a common ancestor commit `sha1`).
2. `orgB` has its own valid GitHub App/webhook secret registered with Shipit (a normal, legitimate configuration — no secrets stolen).
3. Attacker (who administers `orgB`'s GitHub App) sends a `status` webhook, correctly signed with `orgB`'s webhook secret, with body:
```json
{
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgB/fork" },
  "sha": "sha1",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `WebhooksController#verify_signature` verifies the signature using `Shipit.github(organization: "orgB")` and succeeds — `repository_owner` correctly resolves to `orgB`, which really did sign the request.
5. `StatusHandler#process` runs `Commit.where(sha: "sha1")`, which returns the `Commit` row belonging to `orgA/upstream` stack (because the same SHA exists there too), and marks it `success` for `ci/required-check`.
6. `orgA/upstream`'s commit is now marked CI-passing, satisfying `ci.require`, even though `orgA` never sent or signed this status and never intended to authorize a deploy for that commit.
