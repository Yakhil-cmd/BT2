## Title
Uncaught exception crash via inconsistent "definition template" validation in `validateAuthentifiers` — ([File: definition.js])

### Summary
The FreeRDP CVE describes a crash where a cleanup path assumes a decoded array is fully populated (matching the declared `cReaders` count) and dereferences `NULL` when a malformed/failed decode leaves it short. The direct analog in `hirayap/ocore--003` is in `definition.js`: the `'definition template'` operator is evaluated twice during authentifier validation — once by the graceful, error-returning `validateDefinition()` and once by the throwing `validateAuthentifiers()` — with **inconsistent handling of the same "row count mismatch" condition**. The second evaluator assumes the DB lookup for the referenced template always returns exactly one row, and `throw`s an unhandled `Error` if it doesn't, which is never caught anywhere in the call chain and crashes the whole node process via the global `uncaughtException` handler.

### Finding Description
`validateDefinition()` (used to pre-validate an address definition, e.g. when an address is first defined) handles a template row-count mismatch defensively: [1](#0-0) 

But `validateAuthentifiers()` (invoked on **every** unit signed by that address, re-validating the *same* definition each time — deliberately, per the comment) re-implements the identical query but throws an unguarded exception instead of returning a validation error: [2](#0-1) 

The comment above `validateAuthentifiers` explicitly documents that the address definition is intentionally re-evaluated on every unit, because inner/referenced state (redefinitions, complexity, stability, sequence) can change between validations: [3](#0-2) 

This is exactly the scenario the FreeRDP bug class targets: a value (the referenced unit's row count for `app='definition_template' AND +sequence='good' AND is_stable=1`) that was valid at the time of one check (`validateDefinition`, when the address/definition was first accepted) can differ at the time of a later check (`validateAuthentifiers`, on a subsequent unit spending from that address) if the referenced unit's `sequence` flips away from `'good'` (e.g. it becomes non-serial/void due to a later-resolved double-spend) or if concurrent validation of another unit changes stability state in between. The first path degrades gracefully; the second path throws.

`validateAuthentifiers` is reached from ordinary unit validation for **every posted unit**, via `validateAuthor` → `Definition.validateAuthentifiers`, which is invoked in the main `validate()` pipeline for all authors of any submitted unit: [4](#0-3) [5](#0-4) 

The `throw` occurs inside a `conn.query` callback, i.e., in a fresh stack frame with no enclosing `try/catch` anywhere up the async call chain, so it becomes a Node.js `uncaughtException`. The global handler for that event deliberately re-throws to crash the process: [6](#0-5) 

### Impact Explanation
Any node (full node, hub, or wallet) that validates a unit signed by an address whose definition contains a `'definition template'` reference can be crashed if the referenced template unit's row-count condition (`sequence='good' AND is_stable=1`) no longer holds exactly once at validation time — e.g., because the template unit's sequence changed to non-serial/void between the time the address definition was accepted and the time a later unit from that address is validated. This is a full process crash (denial of service against the validating node), matching "a network unable to confirm new units" if triggered against enough hubs/full nodes, and is directly analogous to the FreeRDP NULL-dereference-during-cleanup bug class: a count/array-length invariant that is assumed but not guaranteed at a later processing stage, hit via a code path that lacks the graceful error handling present in the sibling code path.

### Likelihood Explanation
Reaching `validateAuthentifiers` requires only posting an ordinary unit signed by an address that uses `'definition template'` in its definition — a normal, unprivileged feature (definition templates are commonly used for shared/multisig addresses). Triggering the mismatch requires the referenced template unit's stability/sequence state to differ between the two evaluations, which can occur legitimately through the normal double-spend/non-serial resolution process the codebase already supports, or through a race between concurrent unit validations that mutate `sequence`/`is_stable`. No cryptographic break or privileged access is needed; it exploits an ordinary consistency gap between two nearly-identical code paths.

### Recommendation
Make `validateAuthentifiers`'s `'definition template'` handling consistent with `validateDefinition`'s graceful handling: if `rows.length !== 1`, call `cb2(false)` (treat as authentifier check failure) instead of `throw Error("not 1 template")`, and wrap `JSON.parse`/`replaceInTemplate` there in the same defensive style already used in `validateDefinition`.

### Proof of Concept
1. Create address `A` whose definition is `['definition template', [unitX, {...}]]`, where `unitX` at definition time has exactly one stable, `sequence='good'`, `app='definition_template'` message — `validateDefinition` accepts it.
2. Later, cause `unitX` to become non-serial/void (e.g., via a resolved double-spend elsewhere in the DAG) so that the `SELECT ... WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1` query for `unitX` now returns 0 rows.
3. Post a new unit signed by address `A` referencing this state as `last_ball`. During validation, `validateAuthentifiers`'s `'definition template'` branch executes the same query, gets `rows.length === 0`, and executes `throw Error("not 1 template")` inside the `conn.query` callback.
4. The exception is uncaught, propagates to Node's `uncaughtException` handler in `network.js`, which logs and re-throws, crashing the process.
