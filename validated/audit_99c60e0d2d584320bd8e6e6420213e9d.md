### Title
`Shipit::WebhooksController#verify_signature` binds signature verification to the wrong (attacker-chosen) organization, allowing unsigned pushes to sync arbitrary repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`verify_signature` resolves the `GitHubApp` used to check `X-Hub-Signature` via `repository_owner`, which falls back to the attacker-controlled `organization.login` field when `repository.owner.login` is absent, while the actual mutation in `create` uses `repository.full_name` from the same JSON body. If any configured organization has no `webhook_secret`, `GitHubApp#verify_webhook_signature` vacuously returns `true`, letting an attacker "authenticate" as that organization while targeting a completely different repository.

### Finding Description
The broken binding: **organization that verified the signature bytes** (`Shipit.github(organization: repository_owner)`) **≠ organization owning the repository the handler mutates** (`repository.full_name` used inside `PushHandler`).

Code path:
- `repository_owner` reads `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  — an attacker who omits `repository.owner` and supplies only `organization.login` fully controls which `GitHubApp` is selected for verification.
- `verify_signature` uses that attacker-chosen org to fetch the app and check the signature [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) .
- On success, `create` parses the *same* body and dispatches to `PushHandler` using `repository.full_name` from the body — a field never checked against the verified organization [4](#0-3) .
- `PushHandler` resolves stacks via `Repository.from_github_repo_name(repository_name)` (i.e., `payload.dig('repository','full_name')`) and, for matching branches, calls `stack.sync_github` [5](#0-4) [6](#0-5) . The `PushHandler` params schema only requires `:ref` and `:after` — it performs no ownership/organization cross-check [7](#0-6) .

Attacker request: `POST /webhooks` with `X-Github-Event: push`, an arbitrary `X-Hub-Signature`, and body:
```json
{"repository":{"full_name":"OrgB/repo"}, "organization":{"login":"OrgC"}, "ref":"refs/heads/master", "after":"<sha>"}
```
(note: `repository.owner` is omitted so `repository_owner` falls back to `organization.login`).

Exploit flow: if `OrgC` is a configured GitHub App organization with no `webhook_secret` set, `verify_webhook_signature` returns `true` regardless of the garbage signature, the request passes with `head(:ok)`, and `PushHandler` triggers `GithubSyncJob`/`stack.sync_github` for stacks under `OrgB/repo` — an organization the attacker never authenticated against.

Existing guards do not stop this: `drop_unhandled_event` only filters unknown event types [8](#0-7) ; `ExplicitParameters` schemas for handlers validate types/presence, not organization ownership; there is no check anywhere that `repository_owner` (used for verification) equals the owner embedded in `repository.full_name` (used for mutation).

### Impact Explanation
Any repository under an organization that has misconfigured (blank) `webhook_secret` becomes a "skeleton key": an attacker who knows/guesses that org's login can forge a `push` (or any other) webhook targeting any other repository registered in Shipit, causing unauthorized `GithubSyncJob` enqueuing / stack sync against that repository's branch — a payload for one organization mutating another organization's stack, matching the "Critical: unauthorized deploy/mutation across tenants" category. This is repeatable per-request and scales to every repository configured in the Shipit install, as long as one org in the multi-org config lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (1) the multi-org GitHub App config schema (`Shipit.github(organization: ...)` keyed config, confirmed to be a supported/documented configuration, e.g. `test/dummy/config/secrets_double_github_app.yml` shows two orgs each with `webhook_secret: # nil`) [9](#0-8) ; (2) at least one configured org with an unset `webhook_secret`; (3) the attacker knows that org's login (organization names are generally public on GitHub). No secrets, sessions, or tokens are needed — a bare unauthenticated `POST /webhooks` suffices, so the attacker cost is a single HTTP request. This is a realistic and low-cost misconfiguration-triggered bypass, not a purely theoretical one, though it does depend on the operator having at least one org without a webhook secret in a multi-org deployment.

### Recommendation
Do not let `verify_webhook_signature` succeed vacuously based on an org resolved from attacker-influenced fallback fields when mixed multi-org configurations are in use. Specifically:
- In `Shipit.github_app_config`/`GitHubApp#initialize`, treat a missing `webhook_secret` as a hard misconfiguration (fail closed) rather than "verification disabled," at least whenever multiple organizations are configured.
- In `verify_signature`, resolve the verifying organization from `repository.full_name`'s owner segment (the value actually used by handlers) rather than allowing `organization.login` to silently substitute for it, or explicitly cross-check that the two agree before proceeding.
- Reject webhooks where `repository.owner.login` is absent but `repository.full_name` is present and its owner segment doesn't match `repository_owner`.

### Proof of Concept
```ruby
# test/lib/shipit/github_app_test.rb (conceptual addition)
test "verify_webhook_signature is vacuously true with no secret" do
  app = Shipit::GitHubApp.new('OrgC', {}) # no webhook_secret
  assert app.verify_webhook_signature(nil, '{"anything":"here"}')
  assert app.verify_webhook_signature('garbage', '{"anything":"here"}')
end

# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "cross-organization forged push syncs a different org's repository" do
  Shipit.stubs(:github).with(organization: 'OrgC').returns(
    Shipit::GitHubApp.new('OrgC', {}) # webhook_secret nil -> verification vacuous
  )

  body = {
    repository: { full_name: @stack.repository.github_repo_name }, # e.g. "OrgB/repo"
    organization: { login: 'OrgC' }, # no repository.owner present
    ref: "refs/heads/#{@stack.branch}",
    after: 'deadbeef'
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=not_a_real_signature'

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha: 'deadbeef']) do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Both sides of the claimed equality diverge in this PoC: verification is performed against `Shipit.github(organization: 'OrgC')` while the mutated resource belongs to `OrgB`'s repository — confirming the authorization-binding failure.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
