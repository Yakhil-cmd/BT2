### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while all event handlers dispatch on `repository.full_name` - organization/repository binding mismatch in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream event handler, however, resolves the `Repository`/`Stack` to act on using a completely different payload field: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (`Shipit.github(organization: ...)` supports per-org `webhook_secret`s), the field that authenticates the request and the field that determines which repository's data gets written are not the same field and are not cross-checked against each other.

### Finding Description [1](#0-0) 

`verify_signature` computes the org to verify against solely from `repository_owner`: [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This selects the `GitHubApp` instance (and its distinct `webhook_secret`) via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Meanwhile, every webhook handler (push, pull_request opened/closed/labeled/etc.) resolves which `Repository`/`Stack` record to mutate using `full_name`, not `owner.login`: [4](#0-3) [5](#0-4) 

Because the signature check and the repository-selection logic each read a *different* JSON field from the same payload, the equality the system implicitly relies on — "the organization whose secret verified this payload == the organization owning the repository being written to" — is never enforced. Shipit supports configuring multiple GitHub organizations, each with its own `app_id`/`webhook_secret`/`installation_id`: [6](#0-5) 

An operator running Shipit for organizations A and B, each with their own webhook_secret, exposes a scenario where a party who legitimately knows organization A's `webhook_secret` (e.g., because they administer the GitHub App for org A, which they are entitled to configure webhooks for) can craft a payload where `repository.owner.login` = `"org-a"` (so verification uses org A's secret, which they can correctly sign) but `repository.full_name` = `"org-b/victim-repo"`. `verify_signature` succeeds because it only checks org A's secret against the raw body; `Handler#stacks`/`#repository` then resolves and mutates org B's `Repository`/`Stack` records (triggering `sync_github`, archiving/unarchiving review stacks, updating pull request records, etc.) — a cross-organization write that the signing organization was never authorized to produce.

### Impact Explanation
This breaks the equality "the organization that authenticated the webhook == the organization whose repository is written," matching the required binding classes. If exploitable, it results in cross-repository/cross-organization writes (stack sync triggering, review-stack archive/unarchive, pull-request metadata mutation) originating from a different, unauthorized GitHub App/organization than the one Shipit believes signed the request. This maps to the "Critical: cross-repository writes" impact bucket.

### Likelihood Explanation
Likelihood is **low to moderate and configuration-dependent**: this analog only manifests in the (documented, supported) multi-organization configuration mode, where distinct `webhook_secret`s are configured per organization. In the common single-organization deployment (`github_default_organization` is `nil`), there is only one secret and this confusion collapses to a non-issue since any payload valid for the single secret is implicitly "for" the only configured org's repositories. I could not fully verify from the available in-scope code whether GitHub's webhook delivery/App model would even let a legitimately-configured App for org A deliver a payload whose `repository.full_name` names an org-B repo (GitHub Apps are installed per-org/repo and typically only receive webhooks for repos they're installed on) — this is a external/platform-level constraint outside `app/**` and `lib/shipit/**` that limits practical exploitability. Without confirming this platform behavior, I cannot assert this is trivially reachable by an "unprivileged attacker" as opposed to a party who already administers a GitHub App for one of the configured organizations.

### Recommendation
Make the field used for signature-org selection and the field used for repository resolution the same, or explicitly cross-validate them: after locating the `Repository`/`Stack` via `full_name`, confirm its owning organization matches `repository_owner` (the field used to select the verifying `webhook_secret`) before dispatching to handlers. Reject the payload if they diverge.

### Proof of Concept
Not independently verified end-to-end (would require a live multi-org Shipit deployment with two configured GitHub Apps/secrets to confirm GitHub's own delivery constraints do not prevent this). Conceptual PoC:
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret`.
2. As an entity possessing `org-a`'s `webhook_secret`, POST to `/webhooks` with `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
   signed with `org-a`'s secret.
3. `verify_signature` succeeds (uses `org-a`'s `GitHubApp`/secret). `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `sync_github(expected_head_sha: ...)` on its stacks — a write triggered by an entity only authenticated for `org-a`.

Given the residual uncertainty about whether GitHub Apps can actually deliver payloads naming a differently-owned `full_name` (a platform constraint outside this engine's code), I present this as the strongest in-scope analog but flag it as **not fully confirmed** as end-to-end exploitable purely within `app/**`/`lib/shipit/**`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
