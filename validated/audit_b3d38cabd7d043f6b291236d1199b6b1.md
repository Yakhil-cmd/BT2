### Title
Unprivileged PR label names propagate unfiltered into the deploy process environment, allowing `GEM_HOME` (and any other env var) override - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and that hash flows unmodified into `TaskCommands#env`, then into `Command#unbundled_env`, which is passed straight to `PTY.spawn`. An attacker who can open a PR and label it (e.g. with a label named `gem_home`) can therefore set `GEM_HOME=true` (or any other environment variable name) for every command executed during that review stack's deploy, including `deploy.variables`/dependency-installation steps.

### Finding Description
The broken binding is: **the set of environment variable keys injectable via PR labels should be ∅ (empty), but in practice it equals the full set of uppercased PR label names**.

Trace:
1. `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload with only a `String` type check, no name allowlist: [1](#0-0) .
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the base stack env with no key allowlist or blocklist: [2](#0-1) .
3. `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) into the env used to build every `Command` for `install_dependencies` and `perform` (the deploy steps, including `deploy.variables`-driven commands): [3](#0-2) .
4. `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`, so any key set via the PR label (e.g. `GEM_HOME`) overrides the base environment: [4](#0-3) .
5. `Command#start` passes this merged hash directly to `PTY.spawn`, so the child process (gem/bundler/deploy script) inherits the attacker-controlled `GEM_HOME`: [5](#0-4) .

The attacker's exact action: open a pull request from a fork against a repository configured with `provisioning_behavior: allow_with_label`, and attach a label literally named `gem_home` (or any other case-insensitive match of a sensitive variable such as `PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) to their own PR. GitHub emits a `pull_request` webhook with `action: labeled`; `LabelCapturingHandler` stores that label name on the associated `PullRequest` record; the next deploy/task run on that `ReviewStack` builds its environment through `ReviewStack#env`, injecting `GEM_HOME=true` (or any string, since the value is fixed to `"true"` but the key is fully attacker-chosen) into every spawned command for that deploy.

None of the existing guards intercept this: `verify_signature`/`GitHubApp#verify_webhook_signature` only validate that the webhook came from GitHub for that repo (an attacker's own fork/repo is a legitimate webhook source), the `ExplicitParameters` schema in `LabelCapturingHandler` only requires `labels[].name` to be a `String`, and there is no `EnvironmentVariables#permit`-style allowlist applied at the `ReviewStack#env`/`TaskCommands#env` layer — `filter_deploy_envs`/`filter_task_envs` in `DeploySpec` are only applied to the env hash supplied when a user explicitly triggers a task/deploy (`Stack#trigger_task`/`Stack#build_deploy`), not to the values merged in by `ReviewStack#env` during command execution.

### Impact Explanation
By controlling `GEM_HOME` (or `BUNDLE_GEMFILE`, `RUBYOPT`, `PATH`-adjacent variables that aren't stripped) for the entire lifetime of the review stack's deploy commands, an attacker can redirect Ruby's gem/bundler resolution to an attacker-populated gem tree, resulting in arbitrary code execution the next time any Ruby/Bundler command (dependency install steps, `deploy.variables`, custom deploy scripts) runs on the Shipit deploy host under that stack. This is Critical — RCE on the deploy host via `Command`/`PTY.spawn`, since the host process running the deploy commands is directly controlled by attacker-influenced environment. The blast radius is scoped to the fork's own review stack/repository (an unprivileged fork owner attacking their own review-stack deploy), but it demonstrates that PR labels are treated as a fully attacker-controlled, unfiltered environment-injection channel with no allowlist — the same pattern would allow overriding any other sensitive variable that influences command execution behavior.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior: allow_with_label` (or any config where review stacks are provisioned/deployed for fork PRs), which is a documented/supported Shipit feature. The attacker needs only the ability to open a PR and add a label to it — both actions available to any unprivileged GitHub user with a fork, requiring no Shipit credentials, no maintainer role, and no secrets. This is trivially repeatable on every PR/label event and costs nothing beyond opening/labeling a PR.

### Recommendation
Restrict `ReviewStack#env` to only merge a safe, prefixed, or explicitly allowlisted subset of label names (e.g., require a fixed prefix like `SHIPIT_LABEL_` and/or filter out any key that collides with reserved/sensitive environment variable names such as `GEM_HOME`, `BUNDLE_*`, `RUBYOPT`, `PATH`, `LD_PRELOAD`, etc.). Additionally, apply the same `filter_deploy_envs`/`filter_task_envs` allowlist mechanism used for user-supplied env at `Stack#trigger_task`/`build_deploy` to the environment computed by `TaskCommands#env` before it is handed to `Command.new`, so that no fork-controllable key can reach `Command#unbundled_env`/`PTY.spawn` unfiltered.

### Proof of Concept
```ruby
# test/lib/shipit/review_stack_env_injection_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
    test "GEM_HOME must not be injectable via a pull request label" do
      stack = shipit_fixtures(:shipit) # a Shipit::ReviewStack fixture with an associated pull_request
      pull_request = stack.pull_request
      pull_request.update!(labels: ['gem_home'])

      env = stack.env

      # Binding under test: fork-controllable label names must NOT be able to set GEM_HOME
      assert_not_equal 'true', env['GEM_HOME'],
        "PR label injected GEM_HOME into the review stack environment"

      # Confirm it reaches Command#unbundled_env / PTY.spawn input
      command = Shipit::Command.new('true', env: env, chdir: Dir.tmpdir)
      assert_not_equal 'true', command.unbundled_env['GEM_HOME']
    end
  end
end
```
This test builds the `deploy.variables`-equivalent environment through `ReviewStack#env` → `Command#unbundled_env`, injects `GEM_HOME` via an uppercased PR label name, and asserts the env value should not reach the spawned process — currently it does, confirming the vulnerability.
