### Title
Webhook signature is verified against the organization named in the payload while the event is applied to whatever repository `full_name` the same payload names — cross-tenant stack write ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` / `organization.login`). Once the HMAC checks out for *that* organization's secret, the whole payload — including a completely independent field, `repository.full_name` — is handed unchecked to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. `Handler#repository_name` (used by `PushHandler`) resolves the target `Stack` via `payload.dig('repository', 'full_name')`, not via `repository_owner`. Nothing enforces that `repository.full_name` starts with the organization that was actually used to authenticate the signature. This breaks the equality `authenticated_organization == organization_owning_written_repository`.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it only to pick the `GitHubApp`/secret: `github_app = Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 

- This design is explicit in the docs for multi-tenant use: each organization can register its **own** GitHub App with its **own** `app_id`/`installation_id`/`webhook_secret`, configured and known by that organization's own admins. [3](#0-2) [4](#0-3) 

- After signature verification succeeds, the *entire* raw JSON body (not just the verified organization) is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 

- `Handlers::Handler#stacks`/`#repository_name` resolve the target `Repository`/`Stack` using an entirely separate field, `repository.full_name`, with no cross-check against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

- `PushHandler#process` uses that resolved `stacks` to trigger a sync on whatever stack is found, passing an attacker-controlled `after` SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [7](#0-6) 

**Break-the-binding equality:** the engine implicitly assumes `repository.owner.login` (used to select and verify the signing secret) is bound to `repository.full_name` (used to select the `Stack` acted on). Nothing enforces `repository.full_name.split('/').first == repository.owner.login`. In a "Using Multiple Github Applications" deployment (the documented multi-org setup), an org (e.g. `OrgOne`) legitimately knows its own `webhook_secret` because it configured its own separate GitHub App. That org's operator can therefore compute a valid `X-Hub-Signature` for a payload of their own choosing, then set `repository.full_name` inside that payload to name a repository belonging to a *different* tenant, e.g. `OrgTwo/victim-repo`.

Before vs. after:
- Before the attack: `Shipit.github(organization: "OrgOne")` only ever authenticates and processes events for `OrgOne`'s own repositories.
- After the crafted request: signature verification passes for `OrgOne` (owner field = `OrgOne`), but `PushHandler` resolves and mutates the `Stack` belonging to `OrgTwo` (full_name field = `OrgTwo/victim-repo`), enqueuing `GithubSyncJob` for a stack the attacker has no relationship to.

### Impact Explanation
This lets a tenant that owns any organization/GitHub App integrated with a shared, multi-tenant Shipit instance forge push events attributed to another tenant's repository, causing `GithubSyncJob` to run against that other tenant's `Stack` with an attacker-chosen `expected_head_sha` and branch. `GithubSyncJob#perform` calls `stack.github_commits` (using the victim's own GitHub App/token to fetch commits, so the attacker cannot fabricate arbitrary commit content), but the attacker fully controls which branch is synced and which SHA is treated as `expected_head_sha`, and can force repeated syncs/`CacheDeploySpecJob` runs, spoofed `mark_as_accessible!`/`mark_as_inaccessible!` transitions, and repo-selection confusion across tenants — a cross-repository write triggered by an identity that never authenticated for that repository. Because the actual commit content fetched is bounded by real GitHub data for the victim repo, this does not directly leak `GITHUB_TOKEN`s or achieve RCE, but it is an unauthorized action on a repository/stack the caller was never authorized for, satisfying the "cross-repository writes / unauthorized deploy pipeline manipulation" bar for a multi-tenant deployment.

### Likelihood Explanation
Requires the Shipit instance to be configured in the documented multi-org mode (separate GitHub App per organization) — a real, supported deployment pattern, not a hypothetical. Any tenant with a legitimately configured GitHub App under that shared instance can trivially craft such a request: they know their own `webhook_secret`, and the only fields consumed for authorization are attacker-controlled JSON keys with no server-side cross-validation.

### Recommendation
After verifying the webhook signature, re-derive the authorized organization and enforce that `repository.full_name`'s owner segment (and/or `Repository#owner`) matches the `repository_owner`/`organization.login` value that was actually used to select the verifying secret. Reject the event (422) if they diverge, rather than trusting `full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
Given a Shipit instance configured with the multi-org github config (`OrgOne` and `OrgTwo`, each with their own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`), an attacker who administers `OrgOne`'s GitHub App (and thus knows `OrgOne`'s `webhook_secret`) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, body)>

{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
`verify_signature` resolves `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the HMAC validates successfully. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker was never authorized to touch, confirmed by [6](#0-5)  and [8](#0-7) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
