## Analysis

This is a genuine analog of the C4 finding: the sample/template AA contract `order_book_exchange.oscript` uses off-chain–signed order packages (via `is_valid_signed_package`) whose signed content does not bind to the specific AA address (`this_address`) that will execute the trade — exactly the missing-context-binding pattern from `updateProjectHash`.

Compare the two templates in the codebase:

- `payment_channels.oscript` explicitly protects against this class of bug: `trigger.data.sentByPeer.signed_message.channel != this_address` is checked before accepting a signed package. [1](#0-0) 

- `order_book_exchange.oscript`, however, verifies only the signer's identity and the order economics — it never checks that the order was signed *for this particular AA instance*: [2](#0-1) 

The anti-replay id is derived only from order content and is stored in **this AA's own** state (`var['executed_'||$id]`), which is per-address storage, not shared across AA instances. [3](#0-2) [4](#0-3) 

`is_valid_signed_package`/`validateSignedMessage` only check that the signature matches the claimed signer address and definition — they never require the signed message to reference the AA that is evaluating it. [5](#0-4) [6](#0-5) 

### Title
Off-chain signed orders lack AA-address binding, enabling cross-AA signature replay - (File: `test/samples/order_book_exchange.oscript`)

### Summary
The order-book-exchange AA template accepts user-signed order packages (`trigger.data.order1`/`order2`) validated only via `is_valid_signed_package(pkg, address)`. The signed payload (`sell_asset`, `buy_asset`, `sell_amount`, `price`, `address`, `last_ball_unit`) never includes the executing AA's own address (`this_address`), so the same signed order is valid input to *any* AA instance deployed from this template, not just the one the signer intended.

### Finding Description
`is_valid_signed_package` (and the underlying `signed_message.validateSignedMessage`) verifies only that the signature matches the definition/address of the claimed signer; it has no notion of which AA is consuming the package. [7](#0-6)  The order-book template relies solely on this check plus a per-AA "executed" flag computed purely from order content: [8](#0-7) . Because that flag is stored in each AA's own state vars, replaying the identical signed order at a *different* AA address (same template code, e.g. a second deployment, a fork, or any AA sharing this oscript logic) resets the replay-protection scope: the "already executed" check in AA #1 does not prevent execution of the same signed order in AA #2. This mirrors `Project.sol#updateProjectHash`, where `_data` lacked a project-address reference, letting a signature/nonce combination valid for one project be replayed on another project with the same builder/contractor and nonce.

### Impact Explanation
A user who signs an order intending to trade balance held in one order-book AA instance can have that exact signed order replayed against a different AA instance (same template) where they also hold balance, executing an unintended trade and moving/loss of their AA-held funds without a fresh authorization for that specific AA. This is unauthorized use of AA-held funds — an AA fund-loss condition — reachable by any unprivileged party who observes a previously broadcast signed order (orders are transmitted as trigger data in ordinary, publicly visible units).

### Likelihood Explanation
Likelihood depends on multiple identical/compatible order-book AAs existing that share the same asset pair and where the same trading address has deposited balance — plausible for a widely reused open-source AA template, and does not require any privileged access, just observing a previously posted signed order and re-submitting it as trigger data to another AA instance.

### Recommendation
Require the signed order message to include and bind to `this_address` (the executing AA's address), analogous to the `channel != this_address` check already present in `payment_channels.oscript`, e.g. add `if ($order1.aa_address != this_address OR $order2.aa_address != this_address) return false;` and have signers include `aa_address` in the signed content.

### Proof of Concept
1. Deploy two AAs, `AA1` and `AA2`, from the same `order_book_exchange.oscript` template.
2. User `U` deposits balance of asset `X` into both `AA1` and `AA2` (silently-accept-coins branch).
3. `U` signs an order package `order1 = {address: U, sell_asset: X, buy_asset: Y, sell_amount, price}` intending it to be filled against a counter-order in `AA1` only.
4. A counterparty (or `U` themself under duress/mistake) submits the same signed `order1`, paired with a matching `order2`, as a trigger to `AA2`.
5. `AA2` independently validates `is_valid_signed_package(order1, U)` — succeeds, since the signature says nothing about which AA it is for — and executes the trade against `U`'s balance in `AA2`, which `U` never authorized for that specific market/AA instance.
