### Title
Repository targeted by a webhook is not bound to the GitHub organization whose secret authenticated it, enabling cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using an *organization* value taken from the unauthenticated request body, then, once verification succeeds, hands the same body to per-event handlers that resolve the target `Stack`/`Repository` using a *different, independent* field of that body (`repository.full_name`). Nothing ties the two fields together, so a party who legitimately controls the GitHub App installation/webhook secret for one organization can forge a signed payload whose `repository.full_name` points at a repository belonging to a different organization, causing Shipit to act on that other repository's stacks.

### Finding Description
`verify_signature` picks the GitHub App config (and therefore the webhook secret) from `repository_owner`, computed as: [1](#0-0) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once `github_app.verify_webhook_signature` succeeds for that organization's secret over the whole raw body, the controller dispatches the parsed `params` unchanged to every registered handler for the event: [3](#0-2) 

Handlers resolve which `Stack`/`Repository` to mutate from a *separate* field of the same payload, `repository.full_name`, with no re-validation that this repository is owned by the organization whose secret produced the valid signature: [4](#0-3) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target repository/stack) are two unrelated JSON fields inside the same signed body, an attacker who legitimately owns/administers a GitHub organization's Shipit webhook (e.g. by installing the app on their own org/repo, which is a normal, unprivileged action) can:
1. Set `repository.owner.login` = their own org (so `verify_webhook_signature` succeeds using a secret they know), and
2. Set `repository.full_name` = `victim-org/victim-repo` (any repository already registered in Shipit),

then self-sign the payload and POST it to `/webhooks`. The signature check passes (secret matches attacker's org), but the handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, or the `PullRequest::*Handler`s) subsequently operates on the victim repository's stacks, e.g. calling `stack.sync_github(expected_head_sha:)` for arbitrary shas, updating commit statuses, or archiving/unarchiving `ReviewStack`s / mutating pull-request state for a repository the attacker does not control.

This is structurally identical to the Gearbox bug class: the check (webhook-secret verification keyed by `repository.owner.login`) and the effect (mutation keyed by `repository.full_name`) are performed on two different, uncorrelated fields, so a value that should have been implicitly bound together by validation is not — "an organization that authenticated versus the repository that is written."

### Impact Explanation
This breaks the trust boundary between GitHub organizations onboarded into the same Shipit instance. Any org/repo owner who has installed the Shipit GitHub App (an unprivileged, self-service action) can forge webhook events that mutate the state of stacks belonging to a completely different, unrelated repository/organization also hosted on the same Shipit instance — e.g., forcing `sync_github` to run against an attacker-chosen `expected_head_sha`, injecting fabricated commit statuses, or archiving/unarchiving review stacks and pull-request state for a victim repo. Depending on downstream automation (continuous delivery driven by commit status / sync state), this can influence what gets deployed for the victim stack, constituting an unauthorized write into another repository's Shipit-managed state — a cross-repository write across an organization trust boundary.

### Likelihood Explanation
Requires only that the attacker legitimately control (or install the Shipit GitHub App for) at least one organization already configured in the Shipit instance — no repository write access to the victim repo, no Shipit account, and no privileged Shipit credentials are needed. The forged payload is easy to construct since the two fields (`repository.owner.login` and `repository.full_name`) are ordinary, independently-controlled JSON keys in the GitHub webhook payload format.

### Recommendation
After `verify_signature` succeeds, re-derive/require that `params.dig('repository','owner','login')` (or `organization.login`) equals the owner portion of `params.dig('repository','full_name')` before dispatching to handlers, or better, look up the `Repository`/`Stack` via a scope that is explicitly filtered by the verified organization rather than trusting the payload's `repository.full_name` in isolation. Reject/short-circuit (422) when the two do not match.

### Proof of Concept
1. Attacker installs the Shipit GitHub App on organization `attacker-org` and configures a webhook secret `S` they know for it in `Shipit.github(organization: 'attacker-org')`.
2. Victim organization `victim-org/victim-repo` is already a Shipit stack on the same instance.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already reachable in victim repo>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app/secret, verifies successfully.
6. `Shipit::Webhooks::Handlers::PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a write the attacker was never authorized to trigger.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
