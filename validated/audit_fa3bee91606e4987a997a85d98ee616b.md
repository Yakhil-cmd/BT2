### Title
`pallet-psm` performs 1:1 mint/redeem swaps between internal and external stablecoins based only on decimal scaling, with no price oracle — analogous to the "1 USDC == 1 USD" assumption bug - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` (Peg Stability Module) is a new FRAME pallet [1](#0-0)  that lets any signed account swap between an "internal" stablecoin and approved "external" stablecoins (e.g. USDC, USDT) at a fixed 1:1 rate, adjusted only for decimal precision, never for actual market price. [2](#0-1)  This mirrors the Plaza Finance bug class: the protocol hardcodes an assumption that the external stablecoin is always worth exactly 1 unit of the internal (USD-pegged) asset, with no oracle-based deviation check.

### Finding Description
The `mint` extrinsic (callable by any signed account, permissionless, no privileged role required) converts a user-supplied `external_amount` of an approved external asset into the internal asset purely via `external_to_internal`, which only rescales for decimals — it contains no price/oracle input at all: [3](#0-2) 

`redeem` performs the symmetric inverse conversion via `internal_to_external`: [4](#0-3) 

Both dispatchables are reachable by any `Signed` origin with no governance/privileged prerequisite: [5](#0-4) [6](#0-5) 

The pallet's own documentation confirms the assumption that a fixed peg holds and that arbitrage (not oracle correction) is the only mechanism keeping the internal token's market price near $1: [7](#0-6) 

This is architecturally identical to the reported Plaza Finance issue: value is computed by assuming a stable 1:1 relationship between an external asset (USDC-like) and a USD-pegged internal unit, with only fixed minting/redemption fees (`Permill`, default 0.5%) as friction — no on-chain price feed is consulted to detect or react to a depeg of the external asset: [8](#0-7) 

Although a separate `pallet-oracle`/`pallet-asset-rate` exist in the same tree, `pallet-psm`'s `Config` trait does not reference either of them — its `mint`/`redeem` logic path never queries a price oracle: [9](#0-8) 

### Impact Explanation
If an approved external asset depegs below its intended $1 value (e.g. a real-world USDC depeg event as cited in the source report), any signed user can `mint` internal stablecoin at the stale 1:1 rate using the depegged (cheaper) external asset, extracting internal-asset value at a rate above the depegged external's real market worth, minus only the ~0.5% fee. This directly drains the PSM's reserve balance backing outstanding internal-asset debt (`PsmDebt`), degrading the internal asset's actual backing and creating unbacked-issuance risk for the internal stablecoin once the discrepancy is realized during redemptions by other holders — a Medium/High-severity integrity break of the peg mechanism, consistent with the referenced Sherlock finding's acknowledged-but-unmitigated status. Because `pallet-psm` is a generic pallet included in `kitchensink-runtime`/`asset-hub-westend-runtime` per the prdocs [10](#0-9) , any production runtime that enables it and approves a non-fully-collateral-checked stablecoin as `external_asset` inherits this exposure.

### Likelihood Explanation
Likelihood depends entirely on runtime configuration choices (which external assets are approved and whether any off-chain/governance monitoring exists to disable minting quickly via the circuit breaker). The pallet's own circuit-breaker (`CircuitBreakerLevel`) requires a privileged emergency-admin action to react after the fact [11](#0-10) ; there is no automatic on-chain safeguard, so exploitation is possible by any ordinary user during the window between a depeg event and manual circuit-breaker intervention. This matches the "protocol acknowledged" Medium severity of the original report rather than a guaranteed Critical, since it requires an external market event (depeg) as a precondition and a governance/oracle gap.

### Recommendation
Integrate `pallet-oracle` (or `pallet-asset-rate`) price feeds into `pallet-psm`'s `mint`/`redeem` paths to bound or reject swaps when the external asset's live market price deviates materially from its assumed $1 peg, or apply a price-based discount/haircut to `external_to_internal`/`internal_to_external` conversions instead of relying purely on decimal scaling and a static fee.

### Proof of Concept
Not executed. This is a design-level architectural analog identified via static code review of `substrate/frame/psm/src/lib.rs`; no local Rust/FRAME integration test was run in this session to empirically demonstrate reserve drain under an injected price divergence, since `pallet-psm` has no price-input hook to manipulate in the first place (that is precisely the finding: no oracle-based check exists to exploit or bypass). A concrete reproduction would require constructing a test runtime with `pallet-psm`, registering an external asset, and simulating a value divergence externally (e.g., via a companion AMM/oracle pallet) to show `mint`/`redeem` continuing at par — this was not performed here due to tool/iteration limits, and should be validated by a hands-on Devin session with full repository and test-harness access.

		/// Convert an amount denominated in external-asset units into internal units.
		///
		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
