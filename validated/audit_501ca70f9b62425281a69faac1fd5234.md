### Title
Webhook signature only authenticates `repository.owner.login`, not the `repository.full_name` actually acted on — cross-organization webhook confusion - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based solely on `params.dig('repository','owner','login')` (falling back to `organization.login`). Once the signature check passes, every registered `Shipit::Webhooks::Handlers::Handler` resolves the actual `Repository`/`Stack` to mutate using a completely different, unverified field: `payload.dig('repository', 'full_name')`. Nothing in the request-processing pipeline enforces that the owner used to select/verify the signing secret is the same owner encoded in `full_name`. This is the same class of bug as the reported finding: an admin/security boundary (which organization's key legitimizes the payload) is checked against one field, while the privileged state-mutating logic operates on a different, unchecked field of the same attacker-influenced payload.

### Finding Description
The signature-verification step: [1](#0-0) 

picks the GitHub App config via `Shipit.github(organization: repository_owner)` where: [2](#0-1) 

`repository_owner` only reads `repository.owner.login` / `organization.login`. This determines which per-organization `webhook_secret` HMAC is checked against `X-Hub-Signature`.

However, every handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target repository independently, using `payload.dig('repository', 'full_name')`: [3](#0-2) 

and `Repository.from_github_repo_name` simply splits that string into `owner/name` and looks up the DB record: [4](#0-3) 

There is no code path that cross-checks `repository.owner.login` (the field used to select the verifying secret) against the owner segment inside `repository.full_name` (the field the handler actually acts on). Since both fields live in the same JSON body that is HMAC-signed as a whole blob, a legitimate, valid signature normally implies both fields are consistent — but only if GitHub is the one generating the payload. If an entity that legitimately possesses (or leaks) one organization's `webhook_secret` (any organization onboarded into this Shipit instance) crafts a payload where `repository.owner.login` = their own org (so the correct secret/HMAC is chosen and verification passes) but `repository.full_name` = `other-org/some-repo`, the request will pass signature verification yet operate on a `Stack`/`Repository` belonging to a completely different organization that the attacker's key was never meant to authorize.

This mirrors exactly the reported bug class: an admin-configured trust boundary (`isAllowedForCollateral(mode, pool)` verified against one identity) is bypassed because the code that performs the sensitive state mutation (`syncCash`) trusts a different, unverified signal (raw token balance) instead of the checked one. Here, the "verified organization" (signing key owner) and the "repository actually written to" (`full_name`) are two different fields of the same payload, and only one of them is authenticated.

### Impact Explanation
An attacker who controls (or has leaked) the webhook secret for **any one** organization configured in this Shipit instance can forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc.) that are accepted as authentic for **any other organization's repository/stack** tracked by the same Shipit instance. Depending on handler, this can:
- Trigger `stack.sync_github(expected_head_sha: ...)` for another org's stack via `PushHandler`, forcing a resync to an attacker-chosen SHA context [5](#0-4) .
- Manipulate pull-request/review-stack state (`archive!`/`unarchive!`, label capture, merge status) for repositories the attacker does not own, via `LabeledHandler`/`UnlabeledHandler`/`LabelCapturingHandler` which resolve `repository` from `params.repository.full_name` alone [6](#0-5) .
- Inject `Status`/`CheckRun` updates for commits belonging to other organizations' stacks, influencing `deployable?`/CI-gating logic used by continuous delivery (`Commit#deployable?`) [7](#0-6) .

This crosses the "an unauthorized deploy/rollback" and "cross-repository writes" boundary described in the rules, since state belonging to a repository/organization the attacker's signing key was never scoped to can be mutated by spoofing the `full_name` field while satisfying signature verification with a different, legitimately-controlled organization key.

### Likelihood Explanation
This requires the attacker to already possess a valid `webhook_secret` for at least one organization onboarded to the Shipit instance (e.g. because they are a legitimate admin of that org's GitHub App integration, or the secret leaked). That is a real but bounded precondition — it is far short of needing access to the *target* organization/repository, which is the actual asset being protected. Because Shipit is explicitly designed to be a multi-tenant/multi-organization deployment tool (`Shipit.github(organization:)` supports per-org configuration and `GithubOrganizationUnknown` handling), this cross-tenant boundary is a first-class expected security property that the current code fails to enforce, making the likelihood non-trivial in any real multi-organization deployment.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), after verifying the HMAC, assert that `payload.dig('repository', 'owner', 'login')` (the identity used to select the signing secret) matches the owner segment parsed from `payload.dig('repository', 'full_name')`. Reject the request (422) if they differ. Centralize repository/organization resolution so handlers cannot independently trust `full_name` without this consistency check having been performed upstream.

### Proof of Concept
1. Attacker is a legitimate GitHub App admin for `org-attacker` (or has otherwise obtained `org-attacker`'s `webhook_secret` configured in Shipit's `secrets.yml`), and Shipit also tracks stacks for `org-victim/some-repo`.
2. Attacker builds a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/some-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `org-attacker`'s known `webhook_secret` over the raw JSON body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-attacker')` and successfully verifies the signature against `org-attacker`'s secret [8](#0-7) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('org-victim/some-repo')` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on `org-victim`'s stack, even though the signature only proved knowledge of `org-attacker`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
