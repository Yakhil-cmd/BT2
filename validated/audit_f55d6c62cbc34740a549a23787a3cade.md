### Title
Webhook signature verification selects the signing key from an unverified payload field, decoupling the authenticated GitHub organization from the repository the webhook is allowed to act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's webhook secret to validate the HMAC signature against by reading a field out of the *same, still-unauthenticated* request body. Because the field used to pick the key (`repository.owner.login`) is not the same field later used by handlers to resolve which `Repository`/`Stack` the event applies to (`repository.full_name`), an attacker who legitimately controls one configured GitHub organization (and therefore knows its real `webhook_secret`) can forge a signed payload that verifies correctly under their own org's secret while pointing the acted-upon repository at a completely different, victim organization's repository.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is extracted from `request.raw_post`, i.e. the very payload whose authenticity is being checked. `Shipit.github(organization:)` resolves to a `GitHubApp` instance configured per-organization (see the multi-org config layout in `docs/setup.md`/`config/secrets.development.example.yml`, where each org key has its own independent `webhook_secret`) [2](#0-1) . `verify_webhook_signature` then HMACs the raw body with *that org's* secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Because the HMAC covers the full raw body, an attacker who is a legitimate GitHub App owner/admin for *their own* configured organization ("org-attacker") knows that org's real `webhook_secret` and can sign an arbitrary JSON body with it. The equality the code implicitly, incorrectly assumes is:
`organization whose secret authenticated the request == organization/repository the handlers subsequently act on`

But nothing enforces this. The verification step only checks `repository.owner.login` (or `organization.login`) to select the key; it never re-validates that the *rest* of the payload (notably `repository.full_name`, which downstream handlers such as the push handler use to resolve the target `Repository`/`Stack`) actually belongs to that same organization. An attacker can therefore submit a body such as:
```json
{
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
signed with `org-attacker`'s real webhook secret. `verify_signature` succeeds (it only checked `org-attacker`'s key against the whole raw body, and the HMAC of course matches because the attacker computed it themselves), and the request is then dispatched to `Shipit::Webhooks.for_event(event)` handlers with the full attacker-controlled payload, including the victim's `full_name` [4](#0-3) .

This is the same trust-binding class flagged in the source report (a field acted upon that is never actually covered by the thing that is supposed to authenticate it) — here it manifests as "organization that authenticated" vs. "repository that is written."

### Impact Explanation
Handlers keyed on `repository.full_name` (e.g. push/status/check_suite handlers, as seen from the fixtures/tests referencing `Shipit::GithubHook::Repo` mapping to a specific `stack`) would process the forged event as if it legitimately originated from the victim repository, even though only the attacker's own organization's secret was checked. Depending on which webhook events are enabled, this can produce cross-repository writes such as: fabricated commit `status` entries on arbitrary commits of a victim stack, spoofed `push` events that queue `GithubSyncJob`/trigger continuous-deployment logic for a victim stack, or fabricated `check_suite` refreshes — none of which required any credential belonging to the victim organization. This crosses the "cross-repository writes / unauthorized deploy" bar because the write target (victim stack/repo state) is decided by an unauthenticated field, while only an unrelated organization's key was actually verified.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to be a legitimate app-owner/admin of at least one of those configured orgs (not the victim org) — i.e., no access to the victim's secrets, GitHub App, or Shipit account is needed. This satisfies "unprivileged attacker" relative to the victim, and the exploit is a single crafted HTTP POST to `/webhooks` with a valid signature computed from a secret the attacker already legitimately possesses.

### Recommendation
Do not let payload-controlled fields select the verification key. Either: verify the signature against every configured organization's secret and separately confirm that `repository.full_name`'s owner matches the org whose secret validated, or bind the signature-selection organization and the repository being acted upon by cross-checking `repository.owner.login == repository.full_name.split('/').first` before dispatch, rejecting mismatches. More robustly, resolve the target `Repository`/`Stack` first from trusted local records and then verify the signature using that resolved organization's secret, rather than trusting the org name embedded in the untrusted payload.

### Proof of Concept
1. Configure/observe a multi-org Shipit deployment where the attacker controls the GitHub App for `org-attacker` (knows its `webhook_secret`).
2. Craft a `push` (or `status`) webhook JSON body where `repository.owner.login = "org-attacker"` but `repository.full_name = "victim-org/victim-repo"` (a repo/stack tracked by Shipit under a different, unrelated organization).
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` and successfully verifies the signature (attacker signed it themselves) [5](#0-4) .
5. The event is dispatched to registered handlers with `full_name` pointing at `victim-org/victim-repo`, causing the handler to act on the victim's tracked stack/repository despite only the attacker's own organization's key ever being validated.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
