### Title
Cross-organization Team hijack in `MembershipHandler#find_or_create_team!` allows escalation into `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `params.team.id` (GitHub's numeric team ID), and only assigns `organization`/`github_team` attributes inside the `find_or_create_by!` block, which Rails only runs when a **new** record is being created. If a `Team` row with that `github_id` already exists (e.g., a team belonging to `victim-org` that is one of `Shipit.github_teams`), the organization is never checked, and the handler mutates that existing team's memberships in response to a webhook whose signature was verified against a completely different organization's `webhook_secret`.

### Finding Description
The broken binding: `organization_that_verified_signature (repository_owner via Shipit.github(organization: repository_owner))` should equal `organization_that_owns_the_mutated_Team (Team#organization for the record identified by params.team.id)`. These are never compared.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` [3](#0-2) [4](#0-3) . This only proves the request was signed by whichever GitHub App/`webhook_secret` corresponds to `repository_owner`.
2. `MembershipHandler#process` calls `find_or_create_team!` which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [5](#0-4) . The block only executes on record creation; if a `Team` with that `github_id` already exists, its `organization` column is left untouched, and no comparison is made between `params.organization.login` (or `repository_owner`) and the existing `team.organization`.
3. `team.add_member(member)` / `team.members.delete(member)` then mutates `Membership` rows on that pre-existing team regardless of which organization's key signed the request [6](#0-5) .

Precondition for exploitation: Shipit must be configured for multiple GitHub organizations (the documented multi-org config schema in `github_app_config`/`github_organizations`) [7](#0-6) , and the attacker must control one such configured organization ("attacker-org") with its own legitimate `webhook_secret`. This is a real supported deployment shape per `docs/setup.md`'s "Using Multiple Github Applications" section. Given that, `Shipit.github(organization: 'attacker-org')` succeeds and verifies signatures made with attacker-org's own secret — a fully valid signature, not a forged one. The attacker then crafts a `membership` payload with `team.id` equal to the `github_id` of an existing `Team` row that belongs to `victim-org` and is listed in `Shipit.github_teams` (an authorization-granting team). Because the ID lookup ignores organization, the handler updates that victim team's `Membership` records.

Existing guards do not stop this: `verify_signature` only proves *a* recognized organization signed the payload, not that it's the *same* organization whose Team is being touched; `ExplicitParameters` schema only validates types/presence of `team.id`, `organization.login`, etc., not cross-consistency [8](#0-7) ; there's no `Repository`/`Stack` scoping involved in this event at all.

### Impact Explanation
A single crafted, validly-signed `membership` webhook from attacker-org lets the attacker add an arbitrary GitHub login (including their own or an accomplice's) as a member of a `Team` row belonging to `victim-org`, provided that `Team.github_id` is already known/cached in Shipit's database and that team is in `Shipit.github_teams`. `User#authorized?` grants full access to the Shipit instance to any user in `teams` matching `Shipit.github_teams` [1](#0-0) , and `force_github_authentication` is the sole login/authorization gate for the entire app [2](#0-1) . This matches the High severity category: "escalation into `Shipit.github_teams` authorization." The attack is repeatable against any existing `Team` github_id known to the attacker and any member login they choose, and crosses tenant boundaries in any Shipit deployment configured for multiple organizations.

### Likelihood Explanation
Requires: (1) Shipit configured in the documented multi-organization mode with the attacker legitimately controlling one of the configured orgs (this is an operator decision, but is a documented, supported configuration — not a hypothetical one); (2) the victim's `Team.github_id` (a GitHub-assigned team ID) already present in Shipit's DB, which happens automatically once `Shipit.github_teams` is configured (it calls `Team.find_or_create_by_handle` for every configured OAuth team) [9](#0-8) ; (3) knowledge of that numeric ID, which is discoverable via GitHub's team API to any org member or in some cases via leaked webhook payloads. Attacker cost is low (one HTTP POST with a validly-signed body from their own org), and the action is repeatable at will.

### Recommendation
In `MembershipHandler#find_or_create_team!`, enforce that the found or created `Team#organization` matches the organization asserted by the verified webhook (`params.organization.login`, cross-checked against `repository_owner`); reject (or no-op) if they differ, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "organization mismatch" unless team.organization.casecmp?(params.organization.login)
  team
end
```
Additionally, `WebhooksController#verify_signature` should assert `repository_owner == params.dig('organization','login')` for membership-style events, or the handler should receive/verify the already-established `repository_owner` rather than trusting the payload's nested `organization.login` independently.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/membership_handler_test.rb` or similar under `test/`, not shown/created here per repo scope rules but described for the background engineer):
1. Create `Team` fixture `victim_team` with `organization: 'victim-org'`, `github_id: 555`.
2. Configure Shipit (secrets stub) with two orgs: `victim-org` and `attacker-org`, each with distinct `webhook_secret`.
3. Build a `membership` payload: `{ action: 'added', team: { id: 555, name: ..., slug: ..., url: ... }, organization: { login: 'attacker-org' }, member: { login: 'mallory' }, repository: { owner: { login: 'attacker-org' } } }`.
4. Sign it with `attacker-org`'s webhook secret (`X-Hub-Signature`), and POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert response is `:ok`.
6. Assert equality-before-and-after: `victim_team.reload.organization == 'victim-org'` (unchanged, confirming `find_or_create_by!` didn't run the create block) while `victim_team.members.map(&:login).include?('mallory')` is `true` — i.e., the organization column that "verified" the signature (`attacker-org`) differs from the organization column stored on the `Team` actually mutated (`victim-org`), proving the binding is broken.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
