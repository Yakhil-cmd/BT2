### Title
Unchecked RAY-value overflow can permanently freeze a saturated debt market - (File: common/src/rates/index.rs)

### Summary
Interest accrual computes total debt and total supply as `scaled_shares * index` before applying the index ceiling, so a sufficiently large market eventually overflows `i128`; because every pool mutation synchronizes interest first, repayments, withdrawals, liquidations, and explicit `update_indexes` calls all begin reverting permanently. [1](#0-0) [2](#0-1) 

### Finding Description
`update_borrow_index` multiplies the old index by the interest factor and only then clamps the result to `MAX_BORROW_INDEX_RAY`. [3](#0-2)  That index ceiling does not account for the market’s scaled-share total: `calculate_supplier_rewards` subsequently computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index`, while `update_supply_index` computes `supplied * old_index`. [4](#0-3) [1](#0-0) 

The multiplication itself is checked and panics on `i128` overflow rather than saturating or applying a value-aware cap. [5](#0-4) [6](#0-5)  The fixed index ceiling is `10^36` raw units, but the raw `i128` value ceiling is only about `1.70e38`, so a market with roughly `1e36` scaled borrowed units overflows once the borrow-index multiplier exceeds approximately 170, well before the fixed `10^9` index ceiling. [7](#0-6) 

All pool state transitions load the market through `synced_market`, which calls `interest::global_sync`, while the standalone `update_indexes` path calls the same accrual routine directly. [2](#0-1) [8](#0-7)  The integration test reproduces the cliff with a one-billion-unit, 18-decimal market at sustained 98% utilization and confirms that `update_indexes`, withdrawal, and repayment all fail with `MathOverflow` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Impact Explanation
Once the market reaches this state, later calls cannot bypass the overflow because the stored timestamp remains behind ledger time and each operation attempts the same unchecked scaled-value calculation first. [10](#0-9) [2](#0-1)  Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot settle the position through the normal controller paths, permanently freezing all funds represented by the market. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The attack requires a market and spoke configuration that permits a very large borrowable position, plus enough collateral to keep the debt position open at sustained high utilization. [13](#0-12)  An unprivileged address can nevertheless build the state using `supply` and `borrow`, then trigger accrual with permissionless `update_indexes`; no oracle dishonesty, leaked key, privileged call, or malformed token behavior is required. [14](#0-13) [15](#0-14)  The affected asset must admit enough raw units under its listed decimals and caps for `borrowed * borrow_index / RAY` to approach `i128::MAX`, which makes the issue market-size-dependent but reachable within the protocol’s admitted 0–18 decimal domain. [16](#0-15) 

### Recommendation
Apply a share-total-aware bound before computing accrued value, so `borrowed * new_borrow_index / RAY` and `supplied * new_supply_index / RAY` cannot exceed the `i128` domain. [4](#0-3) [1](#0-0)  A safer design would derive the effective index ceiling as `min(MAX_*_INDEX_RAY, floor(i128::MAX * RAY / scaled_total))`, clamp accrual to that value, and preserve a withdrawal/repayment path when the ceiling is reached. [7](#0-6)  Add a regression test that repeatedly accrues the reproduced whale-market state and proves withdrawals and repayments still execute after the effective ceiling engages. [9](#0-8) 

### Proof of Concept
1. On an 18-decimal borrowable market whose caps admit the size, call `supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])` to create and fund an account. [17](#0-16) 
2. Using a second collateral market, call `supply` with enough collateral and then `borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], None)`, matching the reproduced 98% utilization state. [18](#0-17) [13](#0-12) 
3. After enough accrual has elapsed for the borrow-index multiplier to exceed the raw-value headroom, call `update_indexes(caller, [BIG18])`. [15](#0-14) 
4. The call reaches `global_sync`, `accrue_step`, and the `borrowed * new_borrow_index` calculation, which panics with `MathOverflow`. [19](#0-18) [1](#0-0) 
5. Subsequent `withdraw`, `repay`, liquidation, and later `update_indexes` calls repeat the same synchronization and fail before their operation-specific logic can run. [2](#0-1) [20](#0-19)

    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {

    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
