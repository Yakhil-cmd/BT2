### Title
Unbounded `commission_bps` in `UpdateCommissionBps` vote instruction allows commission > 100% - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The external report describes `TokenBridgeBase.sol` fee setters that accept unbounded values with no upper-limit check. The equivalent pattern in agave is the `UpdateCommissionBps` vote-program instruction, which lets the vote account's authorized withdrawer set `inflation_rewards_commission_bps` / `block_revenue_commission_bps` to any `u16` value (0–65535) with no upper bound, even though basis points are conventionally capped at 10,000 (100%) elsewhere in the codebase.

### Finding Description
`update_commission_bps` sets the new commission value directly onto the vote state without validating that it is `<= 10_000`: [1](#0-0) 

The dispatcher in the vote processor forwards the raw `commission_bps` field from `VoteInstruction::UpdateCommissionBps` straight into this function, gated only by feature flags (`commission_rate_in_basis_points`, `delay_commission_updates`, and for `BlockRevenue` also `block_revenue_sharing`) — none of which bound the numeric value itself: [2](#0-1) 

Note that the codebase does contain a basis-points range check (`0..=10000`), but it exists only in the CLI-side input validator used for client-side argument parsing, not in the on-chain instruction handler: [3](#0-2) 

This means any authorized withdrawer (an unprivileged, non-validator-operator role — simply the holder of the withdraw-authority keypair for a vote account, which can be any staker/user) can submit `UpdateCommissionBps { commission_bps: 65535, .. }` directly via a transaction and have it accepted on-chain, since `update_commission_bps` performs no bounds check before storing the value: [4](#0-3) 

The stored `commission_bps` value is subsequently consumed during epoch-boundary reward distribution to compute the split between the vote account's commission and the delegators' share (basis-point math against a 10,000 denominator is used extensively in `runtime/src/inflation_rewards/mod.rs`). If `commission_bps` exceeds 10,000, the commission share of computed rewards would exceed the total reward pool for that vote account, corrupting the split between validator and staker portions.

### Impact Explanation
An out-of-range `commission_bps` (>10,000, i.e. >100%) breaks the fundamental invariant that commission + staker share == total rewards for a vote account. Depending on how the subtraction/split is implemented downstream in the reward-distribution path, this can result in delegators being misattributed reward amounts (receiving zero or corrupted rewards) at epoch boundary, since the "commission" fraction of the reward would legitimately exceed 100% of the total. This falls into the "misattributed or duplicated rewards" impact category for the accepted classes in this scan. I was not able to fully re-verify, within the remaining tool budget, whether the specific arithmetic in `runtime/src/inflation_rewards/mod.rs` uses saturating or checked operations that would prevent a panic/halt versus silently producing an incorrect split — this should be independently confirmed by tracing how `commission_bps` values are consumed in that reward-calculation module.

### Likelihood Explanation
High: the flaw is directly reachable by any holder of a vote account's withdraw-authority key (no validator/operator privilege required, no node compromise needed) via a single, ordinary `UpdateCommissionBps` instruction submitted to the cluster. It requires no race condition, no crafted snapshot, and is gated only by feature flags that are expected to be active on all recent clusters.

### Recommendation
Add a bounds check in `update_commission_bps` (analogous to the CLI's `is_valid_basis_points`) to reject `commission_bps > 10_000`, returning `InstructionError::InvalidInstructionData` for out-of-range values, before the value is written to vote state via `set_inflation_rewards_commission_bps` / `set_block_revenue_commission_bps`.

### Proof of Concept
1. Create/control a vote account and its authorized withdrawer keypair.
2. Submit a transaction containing `VoteInstruction::UpdateCommissionBps { commission_bps: 65535, kind: CommissionKind::InflationRewards }` signed by the authorized withdrawer.
3. Observe that `update_commission_bps` (`programs/vote/src/vote_state/mod.rs:827-859`) accepts and stores the value with no range validation, as confirmed by the existing unit test `test_update_commission_bps` which only exercises typical values (e.g., 500) and does not assert any upper-bound rejection: [5](#0-4) 
4. At the next epoch boundary, the vote account's reward split computation in `runtime/src/inflation_rewards/mod.rs` uses this out-of-range `commission_bps` in basis-point math, producing a commission fraction greater than 100% of the reward pool for that vote account.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

pub fn is_valid_basis_points<T>(basis_points: T) -> Result<(), String>
where
    T: AsRef<str> + Display,
{
    basis_points
        .as_ref()
        .parse::<u16>()
        .map_err(|e| {
            format!("Unable to parse input basis points, provided: {basis_points}, err: {e}")
        })
        .and_then(|v| {
            if v > 10000 {
                Err(format!(
                    "Basis points must be in range of 0 to 10000, provided: {v}"
                ))
            } else {
                Ok(())
            }
        })
}
