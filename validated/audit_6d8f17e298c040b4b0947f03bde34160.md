Based on my investigation, I found a real Polkadot SDK analog of the reported bug class (blind trust in ERC20 `transfer()` return-value compliance), located in the ERC20 XCM asset transactor. I was not able to fully verify two reachability preconditions with the tools available (see caveats below), so I present this with explicit uncertainty markers rather than as a fully proven exploit.

### Title
ERC20Transactor treats non-compliant `transfer()` return data as a hard failure, potentially desynchronizing real token balances from XCM `AssetsInHolding` accounting - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` invoke a Solidity-ABI `IERC20::transferCall` against a `pallet-revive` contract and unconditionally call `abi_decode_returns_validate` on the returned bytes, expecting a `bool`. This mirrors the exact bug class from the referenced report (Sublime `LenderPool.sol` assuming ERC20 `transfer()` always returns a bool, which breaks for USDT-style non-compliant tokens).

### Finding Description [1](#0-0) 
In `withdraw_asset_with_surplus`, a Solidity `transfer(to, value)` call is dispatched via `pallet_revive::Pallet::<T>::bare_call`. If the call does not revert, the code still requires the return payload to ABI-decode as a `bool`; if decoding fails it returns `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` even though the underlying call executed without reverting. [2](#0-1) 
The same pattern exists in `deposit_asset_with_surplus`: a successful (non-reverted) `transfer()` call whose return data fails `abi_decode_returns_validate` is treated as `Err((what, XcmError::FailedToTransactAsset(...)))`, i.e. as if the deposit never happened.

This is the direct analog of the C4 finding: the code assumes strict ERC20 return-value compliance (a `bool` must be ABI-encoded in the return data) for a token whose actual on-chain behavior may not honor that convention (e.g., a contract mimicking real-world USDT, which returns no data on success). Whether a non-reverting call's storage side effects (the underlying token balance already having moved) survive after this function returns `Err` up through the XCM executor is the crux of the impact, and I could not confirm this from the code I was able to inspect.

### Impact Explanation
If the underlying `bare_call` already committed the token balance movement (checking account credited on withdraw, or beneficiary credited on deposit) before the decode check runs, and that state is *not* rolled back when `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` return `Err`, then:
- On withdraw: tokens move to `TransfersCheckingAccount` on-chain, but no corresponding `AssetsInHolding` credit is created (the function returns `Err` instead of `Ok`), meaning the sender's tokens are debited in reality but not reflected in the XCM message's holding register — a real-balance-vs-accounting desync.
- On deposit: the beneficiary's real ERC20 balance increases, but the XCM executor is told the deposit failed and may re-trap the `what` holding (which still logically represents the same funds), risking double-accounting on any error/retry path.

I could not verify from the available code whether the XCM executor wraps these instruction-level calls in a storage-transactional layer that would automatically roll back the underlying contract's storage effects on an `Err` return (I found `transactional_process` used for instructions like `ExchangeAsset` and `PayFees`, per [3](#0-2) , but I did not confirm this wrapping applies to `WithdrawAsset`/`DepositAsset` calling into `ERC20Transactor`). This is the key unresolved question determining whether this is a genuine fund/accounting-integrity bug (High/Critical if unrolled) or a benign no-op DoS (Low, if fully rolled back).

### Likelihood Explanation
Likelihood also depends on an unverified precondition: whether the `Matcher`/asset-registration wiring that binds `ERC20Transactor` into a runtime's XCM config (e.g. `asset-hub-westend`) allows a non-privileged, unregistered/attacker-deployed contract address to be matched as a valid fungible asset, or whether only governance-registered contract addresses are ever routed through this transactor. I located the wiring reference in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs` but ran out of iterations before reading its contents to confirm registration permissions.

### Recommendation
- Do not treat an ABI-decode failure of the `transfer()` return data as unconditionally equivalent to "the transfer failed." Distinguish between "call reverted" (real failure) and "call succeeded but returned no/non-bool data" (ambiguous for non-standard tokens), and audit whether the latter case can leave on-chain token balances mutated while `AssetsInHolding` state diverges.
- Confirm whether XCM executor instruction dispatch for `WithdrawAsset`/`DepositAsset` is storage-transactional such that any `Err` return fully reverts the `bare_call`'s side effects; if not, wrap the ERC20 transactor's contract call + decode logic in an explicit transactional block so a decode failure cannot leave partial state changes.
- Restrict/allowlist which contract addresses can be matched by `Matcher` for this transactor (governance-only registration) if this is not already the case, to prevent unprivileged deployment of adversarial non-compliant ERC20 contracts targeting this path.

### Proof of Concept
No integration test was executed — I do not have terminal/execution access to build and run a Rust/FRAME reproduction in this session. Failed guards identified purely from static code reading: the `abi_decode_returns_validate` call at [4](#0-3)  and [5](#0-4)  is the sole gate distinguishing "successful non-reverted call" from "treated as XCM error," with no check for whether prior storage mutations were already committed. Deployment/registration evidence and transactional-rollback behavior of the surrounding XCM executor path remain unconfirmed — a background Devin session with repo/build access would be needed to (1) read `asset-hub-westend/src/xcm_config.rs` to confirm registration permissions for `ERC20Transactor`'s `Matcher`, (2) trace `xcm-executor/src/lib.rs`'s `WithdrawAsset`/`DepositAsset` instruction handlers for transactional wrapping, and (3) write a `pallet-revive` contract whose `transfer()` returns no data (USDT-style) and drive it through a real `WithdrawAsset`/`DepositAsset` XCM to observe whether the real token balance changes while `AssetsInHolding` does not.

/// We trigger an error via `ExchangeAsset` which uses `transactional_process` internally.
/// The mock has no `AssetExchanger`, so the exchange always fails. The assets taken from
/// holding for the exchange should be restored on failure.
#[test]
fn transactional_process_error_rolls_back_holding() {
	add_asset(SENDER, (Here, 100u128));

	let xcm = Xcm::<TestCall>(vec![
		WithdrawAsset((Here, 100u128).into()),
		// ExchangeAsset takes from holding and tries to exchange — fails because no
		// AssetExchanger is configured, which triggers rollback.
		ExchangeAsset {
			give: Wild(All),
			want: Assets::from(vec![(Parent, 50u128).into()]),
			maximal: true,
		},
	]);

	let (mut vm, _weight) = instantiate_executor(SENDER, xcm.clone());
	assert!(vm.bench_process(xcm).is_err());

	// Holding should be restored after the failed ExchangeAsset.
	assert_eq!(get_first_fungible(vm.holding()), Some((Here, 100u128).into()));
}
