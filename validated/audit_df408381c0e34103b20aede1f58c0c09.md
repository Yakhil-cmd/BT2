### Title
Cross-Repository Forged Webhooks via `repository.owner.login` vs `repository.full_name` Binding Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App used to verify the `X-Hub-Signature` HMAC based on `repository.owner.login` (or `organization.login`), but every event handler resolves the target `Stack`/`Repository` to act on using a completely different field of the same payload: `repository.full_name`. Nothing enforces that these two values agree, so a party who legitimately administers one configured GitHub organization (and therefore knows/holds that org's `webhook_secret`) can forge a signed webhook body whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` names a repository belonging to an entirely different org/stack tracked by the same Shipit instance.

`repository_name` comes from `payload.dig('repository', 'full_name')` — a distinct field from `repository.owner.login`/`organization.login` used for signature verification. `Repository.from_github_repo_name` simply splits this string into owner/name and looks the record up directly, with no cross-check against the verified organization: [4](#0-3) 

Since Shipit supports "Multiple Github Applications", each configured GitHub organization has its own `webhook_secret` in `secrets.yml`, and each org's App administrator can obtain/know that secret and POST directly to the public `/webhooks` endpoint (this endpoint has no session, IP, or additional binding requirement beyond the HMAC). Nothing in the code enforces that `repository.owner.login`/`organization.login` (the value bound by the signature) equals the owner segment of `repository.full_name` (the value that actually determines which `Repository`/`Stack` gets acted upon).

This is exactly the front-running/TOCTOU bug class from the reference report generalized to a deployment-trust binding break in the rules: **"an organization that authenticated versus the repository that is written."** Before an attack, for genuine GitHub-generated payloads these two fields are always consistent. An attacker who controls the webhook secret of *any one* configured organization can break that equality and forge events for repositories/orgs they do not own.

### Impact Explanation
This is a cross-repository write: an attacker who controls their own configured GitHub org's `webhook_secret` can forge:
- `push` events with `repository.full_name` set to a victim stack's repo, causing `PushHandler#process` to run `stack.sync_github(expected_head_sha:)` on a stack the attacker does not own [5](#0-4) , enqueuing `GithubSyncJob` for that stack.
- `status` events writing arbitrary CI status onto victim commits via `Commit#create_status_from_github!`, which can influence deploy safety checks [6](#0-5) .
- `check_suite` and `pull_request` events similarly resolved via the same unchecked `repository_name`/`stacks` helper, affecting review-stack provisioning and label-driven behaviors for repositories the forging party does not control.

This satisfies the required "cross-repository writes" Critical impact category since the attacker influences state (sync triggers, commit statuses) belonging to a stack/repository outside the organization whose credential they actually hold.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator/holder of the `webhook_secret` for at least one GitHub organization configured in a multi-org Shipit deployment (a realistic scenario for shared/multi-tenant Shipit instances documented in `docs/setup.md`'s "Using Multiple Github Applications" section). No GitHub App private key, `api_clients_secret`, or Shipit user session is needed — only a valid HMAC computed with an org they legitimately administer, and knowledge of a target repository's `full_name` (public information). This is a straightforward, code-verifiable path rather than a theoretical one.

### Recommendation
In `Handler#repository_name` (or centrally in `WebhooksController`), require that the resolved repository owner (parsed from `repository.full_name` or `repository.owner.login`) match the organization used for signature verification (`Shipit.github(organization: repository_owner)`). Reject the webhook if the owner segment of `repository.full_name` differs from `repository_owner`/`organization.login`, closing the gap between the field the signature covers-and-is-keyed-on and the field the handlers actually act upon.

### Proof of Concept
1. Shipit is configured with two GitHub orgs in `secrets.yml`: `attacker-org` (attacker is the App admin, knows `webhook_secret_A`) and `victim-org` (tracks a stack for `victim-org/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<malicious_sha_attacker_controls_in_victim_repo_history_or_arbitrary>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, body)` using their own known secret for `attacker-org`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (derived from `repository.owner.login`), and the signature verifies successfully because it was signed with `webhook_secret_A`.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')`, unrelated to `attacker-org`, and triggers `stack.sync_github` for the victim's stack — a forged cross-organization action authenticated by a credential the attacker legitimately controls only for a different organization.
