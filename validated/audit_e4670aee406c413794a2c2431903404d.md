### Title
Webhook signature verification does not bind the authenticated GitHub organization to the repository the payload acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a webhook against using `params.dig('repository', 'owner', 'login')`, but the handlers that actually act on the payload (`Repository`/`Stack` lookup, commit status creation, sync triggers) resolve the target repository from a *different, independently-controlled* field in the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two values together, so an attacker who legitimately knows (or controls) the `webhook_secret` for one configured GitHub organization can forge a signed webhook body whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a stack that belongs to a completely different organization/repository hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

It fetches the GitHub App config for `repository_owner`: [2](#0-1) 

and validates the raw body's HMAC against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Note also that if the resolved organization has no `webhook_secret` configured, verification is unconditionally skipped (`return true unless webhook_secret`), which further weakens the binding for any multi-org Shipit deployment where at least one org has an empty secret.

Once the signature check passes, the entire raw payload is dispatched to handlers: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`, a field completely independent of `repository_owner`: [5](#0-4) 

For example, `PushHandler#process` calls `stack.sync_github` for whatever stack matches that `full_name`: [6](#0-5) 

And `StatusHandler#process` writes a status to any commit matching the `sha` field, with no repository/org cross-check at all: [7](#0-6) 

The broken equality is: **organization whose secret authenticated the request (`repository_owner`) == organization/repository the handlers actually mutate (`repository.full_name` / commit `sha` lookup)**. The HMAC only proves "this exact byte sequence was signed with org X's secret" — it does not, and cannot, enforce that the semantic content of that byte sequence (which repository/commit it names) belongs to org X. Since these are two independently attacker-supplied JSON fields inside the same body, whoever can produce a validly-signed body for *any* configured organization can populate the `repository.full_name` / `sha` fields with values belonging to any other stack tracked by the same Shipit instance.

### Impact Explanation
An attacker who is a legitimate operator/owner of one organization onboarded to a shared, multi-org Shipit instance (and thus knows that org's `webhook_secret`, or exploits an org configured with a blank secret) can forge:
- `status` events to inject fake "success" statuses onto a victim organization's commits (`Commit#create_status_from_github!`), which can satisfy CI/required-status gating used by Shipit's deploy safety checks, leading to an **unauthorized deploy** of another team's stack.
- `push`/`check_suite` events to trigger `Stack#sync_github` or `RefreshCheckRunsJob` against a victim stack, manipulating its head SHA tracking and check-run state used to gate rollouts.

This crosses a repository/organization trust boundary without any Shipit session, API token, or GitHub write access to the victim repository — satisfying the Critical "unauthorized deploy" / cross-repository write class of impact.

### Likelihood Explanation
Requires the attacker to already have legitimate control of at least one GitHub organization/App installation registered on the shared Shipit instance (a realistic scenario for any multi-tenant Shipit deployment using the multi-org `github:` config shown in `docs/setup.md`/`config/secrets.development.shopify.yml`). No compromise of the victim org, no Shipit login, and no GitHub token for the victim's repo is required — only crafting a raw HTTP POST to `/webhooks` with a body signed by the attacker's own known secret.

### Recommendation
Cryptographically and logically bind the organization used for signature verification to the organization actually acted upon: after verifying the signature, re-derive the target `Repository`/`Stack` and assert that its owner/organization matches `repository_owner` (the value used to select the signing secret) before invoking any handler. Reject the webhook if they diverge. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank in a multi-org configuration — require every configured organization to have a non-empty secret.

### Proof of Concept
1. Shipit instance configured with two orgs in `github:` config: `org-a` (attacker-controlled, secret `S_A` known to attacker) and `org-b` (victim, owns stack `org-b/victim-repo`).
2. Attacker builds payload:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_A, body)` and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `org-a`, fetches `org-a`'s `GitHubApp`, and successfully validates the signature against `S_A`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches the victim's commit belonging to `org-b/victim-repo` — and calls `create_status_from_github!`, injecting a forged "success" status that can unblock deploy checks on the victim's stack, with no verification ever performed against `org-b`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
