### Title
Cross-organization webhook confusion allows unauthorized cross-repository writes via mismatched signature-selection vs. handler-routing fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC against using `repository_owner`, a field read straight out of the still-unverified JSON body [1](#0-0) , via `params.dig('repository', 'owner', 'login')` [2](#0-1) . Once the HMAC computed with that organization's secret validates against the raw body, the same raw body is handed unchanged to every registered handler [3](#0-2) , and each handler resolves the target `Repository`/`Stack` from a *different* field, `payload.dig('repository', 'full_name')` [4](#0-3) , used identically by `PushHandler`, `CheckSuiteHandler` and all the `PullRequest::*` handlers [5](#0-4) [6](#0-5) [7](#0-6) .

### Finding Description
Shipit supports hosting multiple independent GitHub organizations behind a single instance, each with its own `webhook_secret`, keyed by organization name in `config/secrets.yml` [8](#0-7) . `Shipit.github(organization:)` looks up the app/secret for a given org name and raises `GithubOrganizationUnknown` only if the name isn't configured at all [9](#0-8) .

The binding that should hold is:

`organization whose webhook_secret authenticated the signature == organization that owns the repository the handlers act on`

But the controller derives the *authenticating* organization from `repository.owner.login` (or `organization.login`) [2](#0-1) , while the handlers derive the *acted-upon* repository from the independent `repository.full_name` field [10](#0-9) . Nothing enforces that `repository.full_name` starts with `repository.owner.login`. Since the HMAC covers `request.raw_post` as a whole and is verified with the secret selected by the attacker-controlled `owner.login` value [1](#0-0) [11](#0-10) , an attacker who legitimately controls one configured organization (e.g. is an admin of `OrgTwo`, knows/owns `OrgTwo`'s `webhook_secret` because they installed and administer that GitHub App) can craft a payload where:
- `repository.owner.login = "OrgTwo"` (or `organization.login = "OrgTwo"`) — selects and validates against `OrgTwo`'s known secret.
- `repository.full_name = "OrgOne/victim-repo"` — is the field every handler actually uses to locate the `Repository`/`Stack` via `Repository.from_github_repo_name` [12](#0-11) .

The signed-and-valid webhook then drives `PushHandler` to enqueue a sync against `OrgOne`'s stack with an attacker-chosen `after` sha [13](#0-12) , or drives PR handlers to archive/unarchive review stacks, capture labels, or create review stacks belonging to `OrgOne` [14](#0-13) . This breaks the trust binding between "the organization whose credential authenticated the request" and "the repository the request is permitted to act on."

### Impact Explanation
This lets an attacker who administers one onboarded GitHub organization on a shared Shipit instance forge signed, "valid" webhook events for a completely different organization's repositories, triggering `GithubSyncJob` runs, review-stack archival/unarchival, and label capture against stacks they do not own — a cross-repository/cross-tenant write performed under a validated signature. It satisfies the Critical "cross-repository writes" bar since the write is not scoped to the org that actually produced the valid signature.

### Likelihood Explanation
This requires the deployment to use the multi-organization `github:` config layout (explicitly documented and tested, e.g. `test/dummy/config/secrets_double_github_app.yml`) [15](#0-14) , and requires the attacker to be a legitimate administrator/owner of at least one of the onboarded organizations (so they can read that org's own `webhook_secret` from their own GitHub App settings) — no privileged Shipit account or token is needed, only their own org's GitHub App credentials. Given multi-org hosting is a first-class supported/documented configuration, this is realistic wherever it's used.

### Recommendation
After `verify_signature` succeeds, re-derive and compare the organization implied by `repository.full_name` (or `organization.login`) against the organization whose secret matched, and reject the webhook (422) on mismatch. Alternatively, have handlers resolve `Repository` scoped to the authenticated organization rather than trusting `repository.full_name` on its own.

### Proof of Concept
1. Configure two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret`, per the documented multi-app schema [8](#0-7) .
2. As an admin of `OrgTwo`, obtain `OrgTwo`'s `webhook_secret` from your own GitHub App settings.
3. Craft a `push` event JSON body where `repository.owner.login = "OrgTwo"` but `repository.full_name = "OrgOne/victim-repo"`, `ref = "refs/heads/<target-branch>"`, `after = "<attacker-chosen sha>"`.
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgTwo_webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "OrgTwo")` (from step 3's `owner.login`), the HMAC validates, and `PushHandler#process` looks up `Repository.from_github_repo_name("OrgOne/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for `OrgOne`'s stack [13](#0-12) , despite the request never having been signed by anything belonging to `OrgOne`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
