### Title
Cross-stack read via `Api::CCMenuController#stack` bypassing `current_api_client.stack_id` scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController#stack` enforces token scoping via `stacks.from_param!(params[:stack_id])`, where `stacks` is filtered to `current_api_client.stack_id` when set. `Api::CCMenuController` overrides `#stack` with `Stack.from_param!(params[:stack_id])`, dropping that scoping entirely, so a token minted for stack A (with `stack_id` set) can read stack B's CCMenu XML.

### Finding Description
The invariant that should hold is: `stack.id ∈ stacks.pluck(:id)` where `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .

`Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, never referencing `stacks` or `current_api_client.stack_id` [2](#0-1) . This is the only subclass of `Api::BaseController` that overrides `#stack`; `Api::HooksController` and `Api::StacksController` rely on the inherited scoped implementation [3](#0-2) .

`check_permissions!` on `ApiClient` only checks the `permissions` array (e.g. `read:stack`) and never inspects `stack_id` [4](#0-3) , so `require_permission :read, :stack` in `CCMenuController` [5](#0-4)  does nothing to restore the missing scoping. `CCMenuUrlController#fetch` mints exactly this kind of token: it creates/reuses an `ApiClient` with `permissions: %w[read:stack]` (no `stack_id` restriction is even set here, but the vulnerability is general — any stack-scoped `ApiClient` row, however created, is affected) and builds a ccmenu URL with `token` in the query string [6](#0-5) .

Exploit flow: an attacker who holds a valid `ApiClient` authentication token whose `stack_id` column is set to stack A's id (e.g., issued as a stack-scoped credential) requests `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` with `stack_id` pointing at stack B. `Api::CCMenuController#authenticate_api_client` authenticates the token via `ApiClient.authenticate(params[:token])` [7](#0-6) , `check_permissions!` passes because `permissions` includes `read:stack`, and `#stack` resolves stack B directly via `Stack.from_param!`, bypassing the `Stack.where(id: current_api_client.stack_id)` filter that the base controller would have applied. The response renders stack B's name, activity, last build status/label/time and web URL [8](#0-7) .

### Impact Explanation
This is an unauthenticated-relative-to-scope read of another stack's build/deploy state (name, last build status, last build label, last build time, web URL) using a credential that should only be valid for one stack. It matches the "High - escalation ... unauthenticated read of stack state" category since a token scoped to stack A can read arbitrary stack B data by simply changing the URL parameter. It is fully repeatable against any stack in the installation since `Stack.from_param!` is unscoped and iterates over all stacks. It does not, on its own, permit writes, deploys, or credential exfiltration, limiting it to the read-disclosure tier rather than Critical.

### Likelihood Explanation
The only precondition is possession of any valid `ApiClient` token that has `permissions` including `read:stack` and a non-null `stack_id` (a "stack-scoped" token) — an artifact the system is explicitly designed to hand out for restricted, single-stack use (e.g., CCMenu integration tokens created by `CCMenuUrlController#fetch`, or any operator-issued scoped token). Given such a token, exploitation is a single unauthenticated-cost HTTP GET with a different `stack_id`; no GitHub secrets, sessions, or elevated Shipit privileges are required. The attack is trivially repeatable across every stack in the installation.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped lookup, e.g. `stacks.from_param!(params[:stack_id])`, so it respects `current_api_client.stack_id` exactly like every other `Api::BaseController` subclass.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read another stack via ccmenu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  scoped_client = ApiClient.create!(
    creator: @user,
    name: "Scoped Client",
    permissions: %w[read:stack],
    stack_id: stack_a.id,
  )

  # Binding under test: stack.id resolved in the action must be in
  # Stack.where(id: scoped_client.stack_id).pluck(:id) == [stack_a.id]
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  assert_response :not_found # expected if scoping were enforced
  # Current (vulnerable) behavior: assert_response :ok and body contains stack_b's name,
  # proving stack_b.id was returned even though it is not in the token's scoped stack set.
end
```
