### Title
Stale `assocCachedUnits` entry causes permanently unrequestable parent content, freezing units that spend outputs of locally-pruned/final-bad units - (File: `network.js`, `storage.js`)

### Summary
CVE-2018-12363 is a Firefox use-after-free where a mutation event moves a DOM node between documents, leaving the node with a dangling reference to the freed document. The reachable analog in `ocore--010` is not a memory-safety bug (JS is garbage collected) but a logically equivalent "stale-reference-to-freed-resource" bug: `storage.assocCachedUnits[unit]` (lightweight static props) can remain populated for a unit whose full content has been purged/pruned, so `isKnownUnit()` reports the unit as "known" even though the code that actually needs its full body (`bRequestPrunedContent` path) has no way to fetch it, because the request path is gated by the same stale cache.

### Finding Description
`storage.readStaticUnitProps()` lazily caches a minimal props record per unit in `assocCachedUnits` [1](#0-0) , and `storage.isKnownUnit()` treats presence in `assocCachedUnits` (or `assocKnownUnits`) as proof the unit is fully known [2](#0-1) . `joint_storage.checkIfNewUnit()` uses exactly this check to decide whether an incoming/needed unit must be (re-)requested from peers [3](#0-2) .

When a unit spends an output of a unit whose full joint content was already locally pruned (final-bad and stripped, or otherwise archived), `network.js`'s `ifNeedParentUnits` callback takes the `bRequestPrunedContent` branch: it stashes the dependent joint keyed by its own unit in RocksDB and records the missing parent(s) in `assocUnitsWaitingForPrunedContent`, then calls `requestJoints()` to fetch the missing content [4](#0-3) . The code explicitly documents the danger it is trying to work around: `requestNewMissingJoints` relies on `checkIfNewUnit()`, which "can say `ifKnown()` for a unit that only has stale props cached in `assocCachedUnits`, even though its full content is exactly what we are missing" [5](#0-4) .

`assocCachedUnits` entries are only cleared by `forgetUnit()` [6](#0-5)  or by the periodic `shrinkCache()` sweep [7](#0-6)  — neither of which is guaranteed to run, or to run in time, for every unit whose props were cached via `readStaticUnitProps` before its content was pruned (e.g. via `purgeUncoveredNonserialJoints` / `archiveJointAndDescendants`, which call `forgetUnit` but only for the specific unit set they process) [8](#0-7) [9](#0-8) . If any code path (e.g. earlier `readStaticUnitProps` lookups during ordinary validation/witness-list traversal, see `validation.js` witness handling calling `readStaticUnitProps`) populated `assocCachedUnits[missing_unit]` before that unit's row/content was stripped, the stale entry survives and `isKnownUnit(missing_unit)` returns `true` even though the joint body no longer exists in the KV store.

The result: `checkIfNewUnit()` answers `ifKnown()` for the missing parent, `requestNewMissingJoints`/`requestJoints` never actually re-fetches its content, and the dependent unit that is queued in `assocUnitsWaitingForPrunedContent` (and persisted under `'wj\n'+unit` in RocksDB) can never be completed/validated — it is stuck indefinitely, exactly as the in-code comment anticipated.

### Impact Explanation
An attacker (any unprivileged unit poster) can construct a payment that references an input from a unit they know is locally final-bad/pruned on some subset of nodes. On nodes where the parent's lightweight props happen to be cached but its content is pruned, the node can never validate the new unit because the missing-parent re-request is silently defeated by the stale "known" cache entry. This causes those nodes to permanently fail to confirm the unit, producing node-level disagreement about validity/processability of a legitimately postable unit and, if triggered broadly (e.g. via a crafted chain that many nodes cache-then-prune), a class of units the network cannot confirm — matching the "network unable to confirm new units" impact class. It does not directly cause double-spend or fund loss, so the severity is bounded by availability/consensus-liveness impact for the affected unit(s), consistent with a Medium/High-severity availability-of-validation bug rather than a spending/inflation bug.

### Likelihood Explanation
Likelihood is moderate: the bug requires the specific ordering where a unit's static props get cached (many code paths call `readStaticUnitProps`, e.g. witness-list/MC traversal in `validation.js` and `storage.js`) before its full content is pruned/archived, and requires the dependent spending unit to arrive after that. Because pruning is tied to the final-bad/uncovered-unit archival flow that runs automatically (`purgeUncoveredNonserialJointsUnderLock`), and static-props caching happens continuously during normal validation of any unit that touches the soon-to-be-pruned unit as an ancestor, this ordering is realistically reachable by a single crafted joint sequence from an ordinary poster, without needing a malicious peer/hub — it is a self-inflicted local-cache inconsistency triggered by ordinary validation combined with the pruning path.

### Recommendation
- Ensure every code path that removes/archives a unit's content (pruning, `generateQueriesToRemoveJoint`, `generateQueriesToVoidJoint`, `archiveJointAndDescendants`) also purges any `assocCachedUnits`/`assocCachedUnitAuthors`/`assocCachedUnitWitnesses`/`assocKnownUnits` entries for that unit, not only the units explicitly known to `forgetUnit()`'s caller set.
- Make `isKnownUnit()` / `checkIfNewUnit()` distinguish "we have cached lightweight props" from "we actually have the full joint content in the KV store," so `bRequestPrunedContent` requests cannot be short-circuited by a stale props cache.
- Add a lookup against `kvstore` (or a "has full content" flag) before answering `ifKnown()` when the caller specifically needs full content (as flagged by `bRequestPrunedContent`).

### Proof of Concept
1. Node A validates some ancestor unit `X` for unrelated reasons; this populates `storage.assocCachedUnits[X]` via `readStaticUnitProps` (e.g. through witness-list/MC traversal during validation of any other unit referencing `X`) [1](#0-0) .
2. `X` is later determined final-bad and its content is pruned via `purgeUncoveredNonserialJoints`, which calls `forgetUnit(X)` — but only if `X` is the exact unit selected by that pass's query; if `X`'s content is stripped through a different path that does not call `forgetUnit(X)` (or races with it), `assocCachedUnits[X]` remains populated.
3. An attacker posts unit `Y` that spends an output from `X`. On submission, validation reaches `ifNeedParentUnits(['X'], true)`, entering the `bRequestPrunedContent` branch in `network.js` [4](#0-3) , which calls `requestJoints(ws, ['X'])`.
4. Downstream, the joint-request logic calls `checkIfNewUnit('X', ...)`, which sees `storage.isKnownUnit('X') === true` (because `assocCachedUnits['X']` is still set) and returns `ifKnown()` instead of `ifNew()` [3](#0-2) , so no peer request for `X`'s full content is ever issued.
5. `Y` remains queued forever in `assocUnitsWaitingForPrunedContent['X']` and in RocksDB under `'wj\n'+Y` [10](#0-9) , never validated, never confirmed by this node.

Note: I was not able to fully trace every call site that populates `assocCachedUnits` versus every pruning code path in this session (index limits and iteration budget); a Devin session with full repo access would let a reviewer confirm the exact ordering/timing window and whether any existing cache-invalidation call (e.g., in `writer.js` or `archiving.js`) already covers this case in all pruning routes.

function checkIfNewUnit(unit, callbacks) {
