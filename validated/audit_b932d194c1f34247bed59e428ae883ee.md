### Title
Attacker-controlled `.gitmodules` submodule failure aborts the entire sync and can crash git-sync (persistent sync denial) - (File: main.go)

### Summary
`configureWorktree()` runs `git submodule update --init` as an unconditional step of preparing a newly fetched worktree whenever `--submodules` is not disabled. If this step fails, the error is propagated all the way up through `SyncRepo()`, which aborts the *entire* sync attempt for that ref/hash — even though the primary content (the files themselves) may already be checked out successfully. This mirrors the `ComplexRewarder.onReward()` pattern in the referenced report: a subordinate/optional operation (child rewarder / submodule update) failing causes the parent operation (`onReward` / `SyncRepo`) to revert entirely, denying the overall function to the consumer.

### Finding Description
In `configureWorktree()`, after the primary checkout (`git reset --hard`) succeeds, git-sync unconditionally attempts to update submodules if `git.submodules != submodulesOff` (the default is not off): [1](#0-0) 

Any failure in this call — e.g. because the pushed commit's `.gitmodules` references an unreachable, malformed, or intentionally-broken submodule URL/path — returns an error that is not distinguished from a fatal, unrecoverable failure. That error bubbles straight up out of `configureWorktree` into `SyncRepo`: [2](#0-1) 

`SyncRepo` itself has no exception handling to isolate the failure of this subordinate step from the rest of the sync — the whole function returns an error just as it would for a fundamental fetch/checkout failure: [3](#0-2) 

Back in the main loop, every `SyncRepo` error increments `failCount`, and with the default `--max-failures=0`, a single failure is enough to call `os.Exit(1)`, terminating the process entirely: [4](#0-3) 

Because the ref/commit hash that git-sync is tracking is attacker-controlled content (a branch/tag being synced), an attacker who can push a commit to the synced repo/ref can add or modify `.gitmodules` to point at a submodule URL that is unreachable, private, protocol-disallowed, or otherwise guaranteed to fail `git submodule update --init`. Since git-sync will re-fetch and re-attempt the same broken commit on every loop iteration (or on every pod restart in Kubernetes, since it keeps trying the same `--ref`), this is a durable, repeatable failure condition, not a one-off — it does not require any timing race or privileged operator behavior.

### Impact Explanation
This is a persistent sync denial: the sidecar can no longer publish the new (or any subsequent) commit via the `--link` symlink, exactly analogous to `withdraw()` reverting in the referenced report because a subordinate child operation failed. With `--max-failures` at its default (0), git-sync's process exits immediately on the very first sync attempt against the poisoned commit — in a Kubernetes sidecar deployment this manifests as a crash loop that never resolves on its own, since the underlying cause (the broken `.gitmodules` on the tracked ref) persists across restarts. Even with `--max-failures` set higher, the consumer application is denied any successful sync (and thus fresh content) for as long as the ref points at the poisoned commit, because the file-content success (checkout) is discarded/never published due to the submodule step failing before publish.

### Likelihood Explanation
Likelihood is high for any deployment where git-sync tracks a branch or ref in a repository to which an untrusted party can push (e.g., a public repo, a repo with permissive write access, or a mirrored/forked branch) and `--submodules` is left at its default (not disabled). No credentials, no race conditions, and no operator misconfiguration beyond "sync a branch that untrusted contributors can push to" are required.

### Recommendation
- Treat submodule initialization (and any other "child"/subordinate operations that are not essential for publishing the primary tree) as non-fatal: log the error and skip/continue rather than aborting the whole `SyncRepo()` call, or make the failure mode configurable.
- Alternatively, validate/sanitize submodule configuration (e.g., disallow submodules by default, or fail fast with a distinct, clearly-labeled "degraded" state) so operators can decide whether a submodule failure should block publishing.
- At minimum, avoid immediately exiting the process (`os.Exit(1)`) on the very first failure by default; ensure `--max-failures`'s default doesn't cause a single attacker-triggerable failure to kill the pod outright.

### Proof of Concept
1. Deploy git-sync with default flags against a repository/branch where an attacker can push commits (e.g., `--repo=<attacker-writable-repo>` `--submodules=recursive` or default) and default `--max-failures=0`.
2. Attacker pushes a commit to the tracked ref adding a `.gitmodules` entry pointing to a non-existent or unreachable URL (e.g., `url = https://invalid.example.invalid/x.git`).
3. On the next sync loop iteration, `git.fetch` succeeds, `git.createWorktree`/`configureWorktree`'s `reset --hard` succeeds, but `git submodule update --init` fails (main.go:1744) because the submodule URL is invalid.
4. `configureWorktree` returns the error, `SyncRepo` returns it up (main.go:1943-1945), `failCount` becomes 1, and since `getMaxFailures()` returns 0, git-sync logs "too many failures, aborting" and calls `os.Exit(1)` (main.go:1059-1061).
5. In Kubernetes, the sidecar container restarts and repeats the same failure indefinitely (crash loop) as long as the poisoned commit remains at the head of the tracked ref, denying consumers any synced content.
