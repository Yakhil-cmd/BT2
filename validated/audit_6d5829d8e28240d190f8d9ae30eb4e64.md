### Title
Global `handleJoint` lock held during synchronous AA trigger dry-run, blocking all unit validation network-wide - (File: network.js)

### Summary
`network.js`'s `handleJoint()` acquires the process-wide `mutex.lock(['handleJoint'], ...)` before validation, and this single global lock gates **all** incoming units, from any peer or any address. When `conf.bDryRunNewTriggers` is enabled, the `ifOk` callback performs `await aa_composer.dryRunPrimaryAATrigger(trigger, address, definition)` for every AA a posted unit's payment output addresses, **before** releasing the `handleJoint` lock (`unlock()` is only called after `writer.saveJoint` finishes). An attacker who posts a payment to an AA address controls which AA's oscript gets dry-run under this global lock, similarly to how libvirt's CVE-2019-20485 held its monitor job lock during a guest-agent query, blocking all other API calls.

### Finding Description
`handleJoint(ws, objJoint, bSaved, bPosted, callbacks)` wraps the entire validation/save flow in `mutex.lock(['handleJoint'], function(unlock){ ... })` [1](#0-0)  . This is a single, global key — not per-address — so it serializes ALL joint processing (units posted by any account, any AA, any peer) through one lock.

Inside `ifOk`, before the lock is released, the code executes:
```
if (conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers) {
    ...
    for (let { address, definition } of rows) {
        const trigger = aa_composer.getTrigger(objJoint.unit, address);
        await aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition));
    }
}
writer.saveJoint(objJoint, objValidationState, null, function(){
    validation_unlock();
    callbacks.ifOk();
    unlock();
    ...
});
``` [2](#0-1) 

Note `unlock()` for the global `handleJoint` mutex is only invoked in the `writer.saveJoint` completion callback, which runs strictly after the dry-run loop finishes. Any unit that triggers a primary AA response causes execution of the AA's oscript logic (`aa_composer.dryRunPrimaryAATrigger`) synchronously inside the globally-locked critical section. The duration of this dry run is fully attacker-influenced: an attacker who posts a unit targeting a computation-heavy/looping/recursive AA can make the dry run take much longer than typical validation, while every other unit submitted by any user in the network queues behind the single `handleJoint` mutex key (see `mutex.js` queuing model, where jobs sharing a locked key are queued and processed strictly after the lock is released) [3](#0-2) [4](#0-3) .

This mirrors the libvirt bug class exactly: a lock meant to protect a short critical section (validating/saving one joint) is instead held across an unbounded, externally-triggerable operation (running/simulating an AA's script), causing systemic API blockage for everyone else waiting on the same lock.

### Impact Explanation
Because `handleJoint` is a single global mutex key shared by every unit submitted to a full node (from posted transactions and from the network), holding it during an attacker-controlled AA dry run stalls processing of all other units — including unrelated payments, AA triggers, and stability advancement — network-wide for as long as the dry run executes. This is a "network unable to confirm new units" condition: while the lock is held, no other unit (regardless of author) can be validated or saved, delaying settlement and stability advancement for the whole network, not just the attacker's own address.

### Likelihood Explanation
Any unprivileged unit poster can trigger this by sending a payment to an AA address which they can also freely deploy/define beforehand with an oscript designed to be slow to dry-run (loops, expensive data-feed lookups, deep recursion via bounce/response chains) — no special privileges are required, only `conf.bDryRunNewTriggers` needs to be enabled (this is a legitimate configuration flag exercised in normal full-node deployments, not attacker-controlled, but not inherently disabled either). The condition is deterministic and repeatable: post-unit -> dry run under global lock -> block queue.

### Recommendation
- Release the `handleJoint` lock (or use a narrower, per-address/per-AA lock) before performing the dry run, or move the dry-run entirely outside of the `handleJoint` critical section since it does not need db-write exclusivity.
- Alternatively, gate the dry run behind a timeout/gas-style limit so that a pathological AA script cannot indefinitely extend the critical section.
- Consider decoupling `dryRunPrimaryAATrigger` execution from the synchronous `ifOk` path entirely (e.g., run it asynchronously/best-effort after `unlock()`), since its stated purpose is only to fail fast and it does not gate correctness of `writer.saveJoint`.

### Proof of Concept
1. Deploy an AA (`aa_addresses`) with an oscript function/handler containing a computationally expensive but valid loop (e.g., large iteration count over `data_feed` reads or repeated string operations) that is intentionally slow to execute even in dry-run mode.
2. Enable `conf.bDryRunNewTriggers` (a standard config toggle on full nodes) and ensure the node is not in light mode.
3. As an unprivileged user, post a normal payment unit whose output address is the malicious AA's address, causing `objValidationState.count_primary_aa_triggers` to be truthy.
4. On `ifOk`, the node calls `aa_composer.dryRunPrimaryAATrigger` for this AA before releasing the global `handleJoint` mutex (`network.js:1271-1294`).
5. Concurrently submit additional, unrelated valid units from other addresses/peers — observe they queue behind `handleJoint` in `mutex.js`'s `arrQueuedJobs` and are not validated/saved until the attacker's dry run completes, confirming network-wide unit-processing blockage for the duration of the attacker-chosen AA computation.
