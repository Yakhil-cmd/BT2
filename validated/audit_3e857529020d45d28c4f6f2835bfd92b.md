### Title
Session fixation in `Shipit::GithubAuthenticationController#callback` allows session hijacking - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`callback` writes `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true` into the current session without ever calling `reset_session`, unlike `logout`, which does call it. An attacker who can plant a known session identifier on a victim's browser before the victim completes the GitHub OAuth handshake ends up with that same session bound to the victim's authenticated `User` after `callback` runs.

### Finding Description
The broken binding is: `session.id (before GET /github/auth/github)` == `session.id (after callback sets session[:user_id])`. This should not hold across a privilege-elevation event (anonymous → authenticated), but in this code it does because `callback` never regenerates the session: [1](#0-0) 

Compare with `logout`, which correctly calls `reset_session`: [2](#0-1) 

Exploit flow: An attacker sends the victim a link/request that causes the victim's browser to hold a session cookie value known to the attacker (e.g., via a subdomain cookie-tossing vector, an open redirect, or simply by initiating `GET /github/auth/github` themselves and getting the victim to reuse that browser/cookie jar — any mechanism that fixes a known session id on the victim before login is sufficient, since Shipit performs no id rotation at any point in the authenticated flow). The victim then completes the real GitHub OAuth handshake (`GET /github/auth/github/callback` via omniauth). `sign_in_github` resolves/creates the `User` row for the victim's GitHub identity and returns its `id`, which `callback` stores directly into the fixed session: [3](#0-2)  and `sign_in_github`: [4](#0-3) 

Because the session identifier is unchanged, the attacker — who already knows/controls that identifier — can now present the same cookie value and be recognized as the victim by `current_user`/`find_current_user`: [5](#0-4) 

None of the existing guards prevent this: `force_github_authentication` only checks whether a user is present/authorized and does not detect or reject session reuse across the login boundary: [6](#0-5) 

`GithubAuthenticationController` inherits from `ActionController::Base` directly (not the app's authenticated base), so it isn't itself gated by `force_github_authentication`, and nothing else in the callback path rotates the session id.

### Impact Explanation
This is a full authentication-bypass / session-hijacking primitive: an attacker who fixes a session id can, after the victim authenticates through legitimate GitHub OAuth, use that same session to act as the victim across the entire Shipit UI/API surface reachable via cookie session (viewing stacks, triggering deploys/rollbacks, managing API clients, repositories, etc., subject to the victim's `User#authorized?`/team membership). This matches the "authentication bypass (forged webhook, session or API token accepted)" / "session fixation" categories called out as Critical/High in the rules. The attack is repeatable per victim and does not depend on the specific repository or stack being targeted — it compromises whichever Shipit-authenticated user can be lured into completing OAuth with a fixed session.

### Likelihood Explanation
The main precondition is the attacker's ability to place a known session cookie value in the victim's browser prior to OAuth completion. Rails' default cookie/session behavior and the complete absence of `reset_session` (or any `session.id`/renewal call) anywhere in `callback` means no rotation ever occurs on login, so any successful cookie-fixation vector (subdomain cookie tossing, response header injection, or simply having control of a shared browser/kiosk state) is sufficient — no Shipit or GitHub secrets are required, matching the attacker capability model in the rules.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before writing `session[:user_id]`/`session[:authenticated]`, mirroring what `logout` already does, so a new session identifier is issued upon successful authentication (standard session-fixation mitigation, e.g. OWASP guidance to regenerate the session ID at every privilege level change).

### Proof of Concept
minitest `ActionDispatch::IntegrationTest` plan (no live GitHub, using OmniAuth test mode / stubbed `request.env['omniauth.auth']`):
1. Perform an initial request to establish a session and capture the pre-login `session_id` (e.g. `session[:session_id]` or the raw cookie value) — call this `pre_id`.
2. Keep the same cookie jar (simulating attacker-planted cookie now shared with/known to the victim).
3. Stub `OmniAuth.config.mock_auth[:github]` with a fake `auth` hash and issue `get :callback` (or `get shipit.github_authentication_callback_path`) using that cookie jar.
4. After the request, read the session id again — call this `post_id`.
5. Assert `pre_id == post_id` reproduces the bug (session id unchanged across authentication) — i.e., assert the binding "`session.id` before login == `session.id` after `callback` sets `session[:user_id]`" holds, proving fixation.
6. Additionally assert `session[:user_id] == victim_user.id` to show the fixed session is now bound to the victim's `User` row.
7. As the fix verification, after adding `reset_session`, assert `pre_id != post_id`.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
