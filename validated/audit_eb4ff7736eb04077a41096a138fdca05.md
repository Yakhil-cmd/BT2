### Title
Webhook signature verification keys on attacker-controlled `repository.owner.login` while event processing keys on a different, unverified `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization GitHub App configurations, `WebhooksController#verify_signature` selects the webhook secret to validate against based on an org name taken directly from the unverified JSON body, while every event handler (`PushHandler`, `StatusHandler`, etc.) subsequently acts on a completely independent field, `repository.full_name`, taken from that same unverified body. An attacker who can produce a payload that authenticates against any configured organization lacking a `webhook_secret` (or one they otherwise control) can point `repository.full_name` at an unrelated, victim-owned repository/stack and have the event processed as if genuinely signed by GitHub for that repository.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the raw, unverified request body and uses it to pick which `GitHubApp`/secret to verify the signature with: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Meanwhile, the actual event handlers determine which `Stack`/`Repository` to mutate using a *different* field of the same unverified body, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) 

For example, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for every stack matching `repository.full_name`/branch: [5](#0-4) 

and `StatusHandler` writes a `Status` for any commit matching `params.sha`, again scoped only by whatever `Commit` rows already exist, not by the org used for signature verification: [6](#0-5) 

The binding this design implicitly assumes — "the organization whose secret authenticated this request" == "the repository/stack the event is applied to" — is never enforced. There is no cross-check that `repository.full_name`'s owner matches `repository_owner`/the org whose secret validated the signature. This is exactly the class of bug highlighted by the referenced RUSTSEC report: a value used to establish a trust decision (which key validates the message) is disjoint from the value the trusted action is actually performed on.

### Impact Explanation
If a Shipit installation runs in the multi-organization GitHub App mode (multiple orgs under `secrets.github`, selected via `Shipit.github_app_config(organization)`), and any one configured organization omits `webhook_secret` (a documented-optional field, and a plausible misconfiguration for a low-value/sandbox org), an unauthenticated attacker can:
1. Set `X-Github-Event: status` (or `push`/`check_suite`).
2. Set the JSON body's `repository.owner.login` (or `organization.login`) to the org lacking a secret, so `verify_webhook_signature` short-circuits to `true` regardless of the (attacker-supplied, arbitrary) `X-Hub-Signature` header.
3. Set `repository.full_name` to a victim's real, tracked repository (e.g. `victim-org/critical-repo`), and forge a `success` status for a commit SHA that is required by `ci.require` in that stack's `shipit.yml`.

This can flip a commit's CI gate to "success" without ever having write access to the victim repository, enabling an otherwise-blocked deploy/merge to proceed — matching the "unauthorized deploy" impact bucket. It requires no Shipit session, API token, or GitHub credentials, only knowledge that some configured org has no webhook secret.

### Likelihood Explanation
Exploitability depends entirely on the deployment having (a) multi-org GitHub App configuration enabled and (b) at least one configured organization without a `webhook_secret`. Single-org (legacy) installations are not affected because `Shipit.github(organization:)` ignores the caller-supplied `organization` argument when `github_default_organization` is `nil` and always uses the single top-level `secrets.github` config. I could not fully verify from the indexed code whether `webhook_secret` is enforced as mandatory per-organization in multi-org mode (`docs/setup.md` presents it as a normal, settable-but-not-obviously-mandated field), so likelihood is conditional on that operational configuration choice rather than a universal, unconditional flaw.

### Recommendation
- Enforce a hard failure (422/500) when `verify_webhook_signature` is called with a blank `webhook_secret` in multi-organization mode, rather than treating "no secret configured" as "always verified."
- After signature verification, cross-check that the organization used to select the verification key matches the owner embedded in `repository.full_name` (or `organization.login`) before dispatching to handlers.
- Consider requiring `webhook_secret` presence validation at configuration-load time for every organization entry under `secrets.github`.

### Proof of Concept
Conceptual (unverifiable end-to-end without a live multi-org secrets.yml, since the index doesn't show a deployed instance):
```
POST /github_webhook
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "org-without-secret" }, "full_name": "victim-org/critical-repo" },
  "sha": "<victim commit sha under required CI context>",
  "state": "success",
  "context": "ci/required-check"
}
```
`verify_signature` resolves `Shipit.github(organization: "org-without-secret")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), then `StatusHandler#process` writes a `success` `Status` against the matching commit in `victim-org/critical-repo`, regardless of the fabricated signature.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
