### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) authenticates an incoming GitHub `status` webhook against the GitHub App/webhook secret configured for the **organization that owns the payload's `repository`** field (`repository_owner`, line 59-61). That authentication only proves "this request was legitimately signed by GitHub for org X's repository." It does not, and cannot, bind the webhook to the specific commit SHA that gets mutated, because `StatusHandler#process` (lines 20-24) writes the status to **every** `Commit` row across the whole Shipit installation that matches `params.sha`, ignoring `repository`/`stack` entirely:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

### Finding Description
The binding that should hold is: *the organization/repository whose signature authenticated the webhook* == *the repository whose commit state is mutated*. `PushHandler` and the base `Handler` class correctly implement this binding — they resolve the target `Stack`/`Repository` through `payload.dig('repository', 'full_name')` (`Handler#repository_name`, line 36-38) before acting, so a push webhook can only affect stacks belonging to that same `repository.full_name`. `StatusHandler` breaks this binding: it never calls `repository_name`/`stacks` at all, and instead matches on `sha` alone, which is a value with no cryptographic or organizational relationship to the authenticating `repository.owner.login` used in `verify_signature`.

Git commit SHAs are content-addressed and can be duplicated/known-in-advance across unrelated repositories (e.g., a repository forked/imported into two different Shipit-tracked stacks under different orgs, cherry-picked commits, identical initial commits, or an attacker simply publishing a commit with a colliding SHA obtained by observing another tracked stack's commit history, which is often public). Once a `status` webhook is delivered from *any* GitHub App/organization configured in Shipit's `secrets.yml` (a legitimate, unprivileged installation the attacker controls, e.g. their own throwaway public repo), the payload only needs `sha` to match a `Commit` that exists in a completely different, unrelated stack tracked by the same Shipit instance. `verify_signature` will happily validate the signature (it is a fully legitimate signature, just for the wrong repository), and `StatusHandler` will write the forged state/description/target_url onto the victim stack's commit via `commit.create_status_from_github!(params)`.

### Impact Explanation
Commit statuses drive Shipit's deploy gating: CI `ci.require`/`ci.blocking` status checks (documented in `README.md` "CI" section) and the merge queue's `merge.require` checks gate whether a commit is deployable/mergeable. By forging a passing status (`state: "success"`) for an arbitrary required context on a victim stack's commit — from an organization that has no write access to the victim repository — an attacker can satisfy required CI checks for a commit that never actually passed CI, causing Shipit to consider it deployable and driving an unauthorized deploy/merge decision. This falls under the in-scope "unauthorized deploy" / cross-repository writes impact category, because the write (commit status creation) crosses a repository/organization trust boundary the webhook signature was supposed to enforce.

### Likelihood Explanation
The attacker only needs: (1) their own legitimate GitHub App installation/organization already configured in Shipit (a normal, unprivileged tenant of a multi-org Shipit deployment, as documented in `docs/setup.md` "Using Multiple Github Applications"), and (2) a commit SHA that also exists in the victim stack's `commits` table. No secrets, tokens, or privileged access to the victim repository are required — only knowledge of a target SHA, which is routinely public (GitHub commit history, PRs, forks). This is a plausible, config-supported scenario in any Shipit instance tracking more than one GitHub organization.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve the target stacks/commits via `repository_name`/`stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to that repository's stacks, rather than matching `sha` globally.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations, `victim-org` (tracks `victim-org/app`, stack has commit `abcd123` with a required CI context `ci/tests`) and `attacker-org` (attacker legitimately controls this org's repo and its GitHub App webhook secret).
2. Attacker creates a repository under `attacker-org` containing a commit with SHA `abcd123` (achievable via cherry-pick/fork/import of the public victim commit, or by finding any pre-existing collision such as a shared base commit).
3. Attacker triggers (or crafts, since they hold `attacker-org`'s webhook secret) a `status` webhook: `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login = attacker-org`, `sha = abcd123`, `state = success`, `context = ci/tests`, correctly signed with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature (it is genuinely signed by that org's app).
5. `StatusHandler#process` executes `Commit.where(sha: 'abcd123')`, which also returns the victim's commit row (same SHA, different stack/repository), and calls `create_status_from_github!` on it, marking the victim's required `ci/tests` context as `success` even though no code in `victim-org/app` was ever tested.
