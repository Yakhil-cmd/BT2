### Title
Webhook signature verification is keyed on `repository.owner.login`, but events act on the unauthenticated `repository.full_name`, letting any authenticated GitHub organization forge events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on `params.dig('repository','owner','login')` (falling back to `organization.login`), but the handlers that actually mutate application state (`StatusHandler`, `CheckSuiteHandler`, `PushHandler`, and the `PullRequest::*` handlers) resolve the target `Stack`/`Repository`/`Commit` using `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `Handler#stacks`. These are two independent, attacker-suppliable JSON fields inside the same raw body. In a multi-organization Shipit deployment (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`), the signature only proves "this body was signed with *some configured org's* secret" — it does not bind the signing org to the repository the handlers act on.

### Finding Description
The binding that should hold is:
`organization whose webhook_secret validated the signature == organization that owns the repository/stack being mutated`

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Meanwhile, `create` dispatches the entire raw `params` to handlers unchanged:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

The base `Handler` resolves the affected stacks purely from `repository.full_name`, independent of `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Because an attacker who administers a repository/GitHub App installation for **their own** organization (`OrgTwo`) legitimately knows `OrgTwo`'s `webhook_secret` (it's configured for their org's app), they can POST an arbitrary, self-crafted JSON body directly to `/webhooks`, setting:
- `repository.owner.login = "OrgTwo"` (or `organization.login = "OrgTwo"`) so `verify_signature` picks `OrgTwo`'s secret and the HMAC they compute themselves passes,
- `repository.full_name = "OrgOne/victim-repo"` — an entirely different, victim organization's repository that also happens to be configured on the same shared Shipit instance.

`StatusHandler` and `PullRequest::*` handlers trust payload fields directly (e.g. `commit.create_status_from_github!(params)` [5](#0-4) , and `CheckSuiteHandler` schedules check-run refreshes purely from `check_suite.head_sha`/`head_branch` matched against `stacks` derived from the forged `full_name` [6](#0-5) ), all without any GitHub API round-trip that would catch the mismatch. `PushHandler` similarly finds stacks via `repository_name` and enqueues `GithubSyncJob` for the victim's stack [7](#0-6) .

The webhook signature check treats any mismatch between the declared owner and the actual repository name as out of scope — it only verifies the body against the secret it looked up from the (attacker-controlled) owner field, then hands the whole unvalidated body to handlers that trust a different field.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, an attacker who legitimately controls one GitHub organization onboarded to a shared Shipit instance can:
- Force `StatusHandler` to write forged commit statuses onto commits of a victim's stack belonging to a different organization.
- Trigger `CheckSuiteHandler` to schedule check-run refreshes for a victim stack.
- Trigger `PushHandler`/`GithubSyncJob` sync cycles on a victim's stack (queue poisoning / unwanted resync), and archive/unarchive review stacks under `PullRequest::*` handlers for a repository they don't own (`Repository.from_github_repo_name(params.repository.full_name)` in `ReopenedHandler`/`UnlabeledHandler` etc. is resolved purely from the forged `full_name`) [8](#0-7) .

This does not directly leak `GITHUB_TOKEN` or achieve RCE, but it is a cross-organization/cross-repository write capability driven entirely by forged webhook payloads that bypass the organization-scoped trust the signature is meant to establish, satisfying the "cross-repository writes" high-impact criterion.

### Likelihood Explanation
Requires the Shipit deployment to host multiple GitHub organizations (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s multi-org schema) and requires the attacker to control (or have webhook-secret access to) at least one of those organizations' GitHub App installations. No GitHub session, API client token, or victim credentials are needed — only knowledge of one's own org's `webhook_secret`, which any org admin legitimately possesses. This is a realistic configuration for shared/central deploy platforms.

### Recommendation
Cross-check that the organization derived from `repository.owner.login`/`organization.login` (used to select the verification secret) matches the organization portion of `repository.full_name` before dispatching to handlers, and reject the request (422) on mismatch, in `WebhooksController#verify_signature`/`#create`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Onboard `OrgOne/victim-repo` as a Shipit stack.
3. As an attacker who is an admin of `OrgTwo` (and thus knows `OrgTwo`'s `webhook_secret`), craft a JSON body:
```json
{
  "action": "opened",
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
}
```
4. Sign the raw body with `OrgTwo`'s `webhook_secret` using HMAC-SHA1 exactly as `Hook::DeliverySigner`/`verify_webhook_signature` expect [9](#0-8) , and set `X-Hub-Signature`, `X-Github-Event: status`.
5. POST directly to `/webhooks`. `verify_signature` resolves `repository_owner => "OrgTwo"`, fetches `OrgTwo`'s secret, and the signature validates.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit belonging to `OrgOne/victim-repo` — and writes a forged commit status, even though the attacker never had access to `OrgOne`'s webhook secret or repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
