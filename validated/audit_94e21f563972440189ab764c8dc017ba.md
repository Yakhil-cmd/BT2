### Title
Push-webhook sync targets a repository never covered by the HMAC-authenticated organization field - (File: `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification from `repository_owner`, which is read out of the *unauthenticated* JSON body before the signature check runs, then later `Shipit::Webhooks::Handlers::Handler#repository_name` independently reads `repository.full_name` from that same body to decide which `Stack`/`Repository` gets synced/deployed. Nothing ties these two fields together.

### Finding Description
`verify_signature` derives the organization used to look up the GitHub App/webhook secret purely from the request body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler on the raw, already-parsed `params` hash, e.g. `PushHandler`: [3](#0-2) [4](#0-3) 

The handler base class resolves the target repository/stacks from a *different* field of the same payload, `repository.full_name`, with no cross-check against the `repository.owner.login` value that was used for signature verification: [5](#0-4) 

This mirrors the reported bug class exactly: `setZapConfig` updated `curvePool`/`token` (the field acted upon) without re-establishing the approval binding tied to those same fields, so the two pieces of related state silently diverged. Here, `repository_owner` (bound to the verified signature) and `repository.full_name` (bound to what stack is written to) are two independent fields drawn from the same unauthenticated JSON body, and the code never asserts `full_name.split('/').first == owner.login`. The equality that should hold and is not enforced is:

`organization authenticated by verify_webhook_signature == organization that owns the repository acted upon by the handler`

### Impact Explanation
If this equality can be broken, a webhook delivery cryptographically valid for one organization's webhook secret can be crafted to carry a `repository.full_name` pointing at a stack belonging to a different, unrelated repository/organization tracked by the same Shipit instance. Handlers like `PushHandler` would then enqueue `stack.sync_github(expected_head_sha: params.after)` against that unrelated repository/stack, and other handlers (`commit_status`, `check_suite`, `pull_request`, `membership`, etc.) resolve stacks/teams the same way through `Handler#stacks`/`#repository_name`. Depending on the specific handler this can update commit statuses, merge-queue state, or trigger `GithubSyncJob`/`RefreshCheckRunsJob` for a victim stack the sender does not actually control — an authorization-boundary violation across repositories in a multi-tenant Shipit deployment.

### Likelihood Explanation
Exploitability strictly depends on whether this specific Shipit deployment is multi-tenant, i.e., configured with more than one GitHub organization each holding its own distinct `webhook_secret` (per `Shipit.github(organization:)` / the app's GitHub-app config, which I could not fully inspect within the remaining tool budget — `lib/shipit.rb`'s exact `github_apps`/`webhook_secret` structure was not confirmed). If Shipit is configured as most documented deployments are — a single GitHub App/org integration, or one shared secret across all tracked organizations — there is no distinguishable "attacker org's secret" for the attacker to legitimately hold, and this analog does not cross a real trust boundary. I could not confirm from the available files whether per-organization distinct secrets are a supported, in-scope configuration, so likelihood is uncertain and depends on deployment topology that is outside what I could verify.

### Recommendation
In `Handler#repository_name` (and anywhere else a handler trusts a payload's repository/org identity), cross-validate that `payload.dig('repository', 'owner', 'login')` equals the organization segment of `payload.dig('repository', 'full_name')`, and reject/drop the event if they diverge, so the field used for signature verification and the field used to select the acted-upon repository can never disagree.

### Proof of Concept
Not independently verified end-to-end because I could not confirm within the remaining budget whether this Shipit installation supports genuinely distinct per-organization `webhook_secret`s (the exact `github_apps`/config shape in `lib/shipit.rb` was not fully read). Conceptually: an attacker who legitimately controls organization `attacker-org` (tracked by this Shipit instance, thus knows/derives a valid HMAC signature for it) sends a `push` webhook whose body sets `repository.owner.login = "attacker-org"` (so `verify_signature` selects and passes with `attacker-org`'s secret) but `repository.full_name = "victim-org/victim-repo"`. `PushHandler` then calls `Repository.from_github_repo_name("victim-org/victim-repo")` and syncs/queues jobs against the victim's stack.
