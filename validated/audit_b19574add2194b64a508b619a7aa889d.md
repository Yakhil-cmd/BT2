### Title
Webhook signature verified against attacker-chosen organization but events applied to any repository named in the payload - unauthorized cross-organization commit-status injection and deploy triggering ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON body. Every downstream webhook handler, however, resolves the actual `Repository`/`Stack`/`Commit` to act on using a *different* field of the same body — `repository.full_name` (or bare `sha` for status events) — without ever checking that it belongs to the organization whose secret validated the request. This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` when Shipit is configured for multiple GitHub Apps/organizations (a documented, supported configuration): [3](#0-2) [4](#0-3) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers. Those handlers never re-check `repository.owner.login`; instead they resolve the target repository via the independent `repository.full_name` field, e.g.:

- `PushHandler#process` finds stacks by `branch` for whatever `Repository`/`Stack` correlates to the push, ultimately triggering `sync_github` for that stack: [5](#0-4) 
- `StatusHandler#process` looks up commits purely by `sha` (no repo/org check at all) and calls `commit.create_status_from_github!`, writing a CI `Status` for that commit regardless of which org's secret validated the request: [6](#0-5) 
- Pull-request handlers resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)`, e.g. `ClosedHandler`, `OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `AssignedHandler`: [7](#0-6) 

Because `repository.owner.login`/`organization.login` (used for signature selection) and `repository.full_name` (used for the actual write) are two independent, unauthenticated JSON fields inside the same signed body, and the signature only proves "this body was signed by *some* configured org's secret" — not "this body's `full_name` belongs to that org" — an attacker who possesses (or has legitimately been issued) the `webhook_secret` for **any one** configured organization in a multi-org Shipit instance can forge a validly-signed payload with `repository.owner.login` set to their own org (so `verify_signature` picks their own known secret and succeeds) while `repository.full_name` (or `sha`) targets a stack/commit belonging to a completely different organization/repository that they have no access to.

This is the exact bug-class analog described in the report: an owner-verified/authenticated field ("organization that authenticated") diverges from the field actually acted on ("repository that is written"), because the two are never cross-checked, exactly as the empty-address-removal bug in the report allowed unremoved/unchecked entries in a security-relevant set to be acted upon inconsistently.

### Impact Explanation
Via `StatusHandler`, an attacker can inject a fabricated `success` CI status onto an arbitrary commit SHA of any stack tracked by the Shipit instance, without needing that repository's webhook secret at all — `StatusHandler` does zero repository/org validation, only matching by SHA. Injected `success` statuses drive `commit.create_status_from_github!` → `Status#enable_ci_on_stack` and `schedule_continuous_delivery`, which is the mechanism that unlocks deploy-eligibility / merge-queue progression for commits gated on CI (`Status`/`deployable_status` transitions). This can enable an unauthorized deploy of a commit in a repository the attacker does not control, meeting the "Critical – unauthorized deploy" bar. Additionally, `PushHandler` and pull-request handlers let a cross-org attacker trigger `GithubSyncJob`, archive/unarchive review stacks, and manipulate pull-request label-driven provisioning for repositories outside their authorized organization, causing unauthorized state changes on stacks they don't own.

### Likelihood Explanation
This requires the Shipit instance to be configured with multiple GitHub Apps/organizations (explicitly documented and supported, `docs/setup.md` "Using Multiple GitHub Applications"), and requires the attacker to possess a valid `webhook_secret` for at least one of the configured organizations (e.g., they administer that org's GitHub App, or the secret otherwise reaches them) — but zero credential for the target organization/repository. Given that the `StatusHandler` path performs no repository-owner check whatsoever (matches purely by commit SHA across the entire Shipit installation), likelihood is elevated: SHAs are often predictable/discoverable via public commit history, and no other binding exists to stop the cross-tenant write once any one organization's signature check passes.

### Recommendation
In `WebhooksController#verify_signature` / `#create`, after determining `repository_owner` and validating the signature, verify that every entity the dispatched handlers will act on (`repository.full_name`'s owner segment, and for `status` events the resolved `Commit#stack.repository`'s owner) matches the authenticated `repository_owner`/organization. Concretely: reject the webhook (422) if `params.dig('repository','full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`, and update `StatusHandler` to scope its `Commit.where(sha:)` lookup to commits whose `stack.repository.owner` matches the authenticated organization before creating a status.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As an attacker who only knows `OrgA`'s `webhook_secret` (e.g., because they administer `OrgA`'s GitHub App settings) but has no access to `OrgB`:
   - Craft a `status` event JSON body: `{"sha": "<sha of a commit belonging to an OrgB-owned stack>", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "OrgA"}}}`.
   - Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
   - POST to `/webhooks` with `X-Github-Event: status`.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
4. `Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the `Commit` purely by `sha` — belonging to `OrgB`'s stack — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto an `OrgB` commit despite the attacker never having any credential for `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
