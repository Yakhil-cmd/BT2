### Title
Cross-repository commit-SHA collision in `StatusHandler#process` triggers victim stack's `Hook.emit(:deployable_status, ...)` from an attacker-controlled webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no scoping to the repository that authenticated the incoming webhook. Because Git SHA is a function of tree/commit content and not of the repository name, an attacker can obtain a commit with an identical SHA to a commit already tracked in a victim's Shipit stack (e.g., by forking the victim's public repository) and deliver a signed status webhook for that SHA from their own repository, causing `Shipit::Commit#add_status` to invoke `Hook.emit(:deployable_status, stack, ...)` for the victim's stack.

### Finding Description
The broken binding is: `authenticated_repository.full_name == commit.stack.repository.full_name` is assumed but never checked.

- `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . This query is global across all `Commit` rows in the database — it is not scoped by `stack_id` or by the repository that the webhook payload claims to originate from.
- `Commit#create_status_from_github!` calls `add_status`, which appends the forged status, recomputes `new_status`, and — when `previous_status.simple_state != new_status.simple_state` — fires `Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))` using `self.stack`, i.e., whichever stack happens to own the matched `Commit` row [2](#0-1) .
- `Hook.emit` enqueues `EmitEventJob` and calls `deliver_internal_hooks`, and ultimately `Hook#deliver!` schedules `DeliverHookJob` to POST the payload to the stack's configured `delivery_url` (e.g., a Slack/webhook integration) [3](#0-2) .

Exploit flow: an attacker forks (or otherwise obtains) a repository containing a commit whose SHA is identical to a commit already ingested into a victim's Shipit stack (trivial via GitHub fork, since forking preserves SHAs exactly). The attacker sends (or triggers GitHub to send) a `status` webhook for that SHA from their own repository/installation. Nothing in `StatusHandler` or `Commit#create_status_from_github!` cross-checks that the webhook's repository matches `commit.stack.repository`; the `Commit.where(sha:)` lookup will match the victim's existing `Commit` row purely by SHA equality, and the victim stack's outbound `Hook` fires with attacker-supplied `state`/`description`/`target_url`/`context` content.

I was not able to fully trace `app/controllers/shipit/webhooks_controller.rb`'s signature-verification logic in this session (whether the HMAC secret is per-installation/per-repo or a single global GitHub App secret) due to tool-call exhaustion; this affects only the "attacker cost" side of the finding, not the core defect, which is unambiguous in `status_handler.rb` and `commit.rb`: there is no repository-identity check tying the webhook's authenticated source to the `Commit`/`Stack` being mutated.

### Impact Explanation
This lets a payload delivered under one repository's identity (or a repository the attacker owns/controls) trigger a write (`Status` record creation) and a side-effecting event (`Hook.emit(:deployable_status, victim_stack, ...)`) against a completely different tenant's stack — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The victim's configured outbound integrations (Slack notifications, custom webhooks that may themselves gate on `state`/`description`) receive attacker-influenced content purportedly about the victim's commit, and downstream automation reacting to `deployable_status` (e.g., auto-merge/auto-deploy hooks external to this engine) could act on forged state changes. This is repeatable against any victim stack whose tracked commit SHA the attacker can reproduce (any public fork target), and scales across tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: the victim stack must have already ingested the colliding commit (normal operation for any actively used stack), and must have a `Shipit::Hook` subscribed to `deployable_status` (a common configuration for Slack/webhook notifications). Obtaining a SHA-colliding commit is low-cost for public repositories (fork the victim repo). The remaining unresolved factor is exactly how `webhooks_controller.rb` authenticates/signs incoming status events (per-repo vs. global secret) — this determines whether the attacker needs to install a GitHub App on their own repo to get a validly-signed delivery, or whether some other authentication gap exists; this should be verified before finalizing severity, but the missing repository/stack scoping in `Commit.where(sha:)` is a standalone defect regardless.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other SHA-keyed handler) to the repository identified by the authenticated webhook payload, e.g., join through `stack.repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: authenticated_repository.id })`, or otherwise verify `commit.stack.github_repo_name == payload.repository.full_name` before calling `create_status_from_github!`. Apply the same repository-identity check pattern to any other handler that resolves records purely by SHA without tenant scoping.

```ruby
test "status webhook for a repository the attacker controls fires Hook for an unrelated victim stack sharing the same commit sha" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  # Simulate an attacker-controlled repository's status payload referencing
  # the *same* sha (e.g. via a fork with identical history).
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: victim_commit.sha,
    state: "failure",
    description: "forged by attacker",
    context: "attacker-ci"
  )

  Shipit::Hook.expects(:emit).with(:deployable_status, victim_stack, anything)

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process
end
```
Both sides of the intended binding — `authenticated_repository.full_name` (attacker's repo) vs. `victim_commit.stack.repository.full_name` (victim's repo) — are unequal, yet `Hook.emit(:deployable_status, victim_stack, ...)` still fires, because `StatusHandler#process` and `Commit#add_status` never compare them [1](#0-0) [4](#0-3) .
