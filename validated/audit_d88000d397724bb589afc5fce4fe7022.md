### Title
VT Recovery Loop Permanently Stalled by High-Volume Bridge Events in Fixed `filterLogsStride` — (File: `node/sc/vt_recovery.go`)

### Summary

The `retrievePendingEventsFrom` function in `node/sc/vt_recovery.go` queries bridge event logs in a hard-coded stride of 100 blocks (`filterLogsStride = uint64(100)`). If the `FilterRequestValueTransfer` or `FilterRequestValueTransferEncoded` call returns an error (e.g., because the 100-block window contains more than `GetLogsMaxItems = 10000` log entries), the function immediately returns `nil, err` without advancing the search window. Because `hint.blockNumber` is re-read from the bridge contract's `RecoveryBlockNumber` on every recovery tick and that value does not advance until a transfer is actually handled, every subsequent recovery attempt re-queries the same failing window. The result is a permanently stalled VT-recovery loop: pending cross-chain value transfers (KAIA, ERC20, ERC721) that were never handled remain locked in the bridge contract indefinitely.

---

### Finding Description

`filterLogsStride` and `maxPendingTxs` are package-level constants:

```go
// node/sc/vt_recovery.go
var (
    filterLogsStride = uint64(100)
    maxPendingTxs    = 1000
)
```

`retrievePendingEventsFrom` iterates over 100-block windows starting from `hint.blockNumber`:

```go
startBlkNum := hint.blockNumber
endBlkNum := startBlkNum + filterLogsStride

for startBlkNum <= curBlkNum {
    ...
    opts := &bind.FilterOpts{Start: startBlkNum, End: &endBlkNum}
    reqVTevIt, err := from.bridge.FilterRequestValueTransfer(opts, nil, nil, nil)
    if err != nil {
        return nil, err          // ← no retry, no window-halving, no skip
    }
    reqVTencodedDataIt, err := from.bridge.FilterRequestValueTransferEncoded(opts, nil, nil, nil)
    if err != nil {
        return nil, err          // ← same
    }
    ...
    startBlkNum = endBlkNum + 1
    endBlkNum = startBlkNum + filterLogsStride
}
```

`FilterRequestValueTransfer` ultimately calls `FilterLogs` on the contract backend. The Kaia filter layer enforces `GetLogsMaxItems = 10000` and `GetLogsDeadline = 10 s`. If either limit is exceeded the call returns an error.

The error propagates through `retrievePendingEvents → Recover`, where it is swallowed at trace level:

```go
// vtr.Start() goroutine
case <-ticker.C:
    if vtr.isRunning {
        if err := vtr.Recover(); err != nil {
            logger.Trace("value transfer recovery is failed", "err", err)
        }
    }
```

On the next tick `updateRecoveryHintFromTo` re-reads `RecoveryBlockNumber` from the bridge contract:

```go
hint.blockNumber, err = to.bridge.RecoveryBlockNumber(nil)
```

Because no transfer was handled (the recovery failed), `RecoveryBlockNumber` is unchanged, so `hint.blockNumber` stays at the same value. The next call to `retrievePendingEventsFrom` re-queries the identical failing window and fails again — indefinitely.

---

### Impact Explanation

Every `RequestValueTransfer` event that falls inside the saturated 100-block window is permanently skipped by the recovery mechanism. The corresponding KAIA, ERC20, or ERC721 tokens are locked inside the bridge contract with no automated path to release them. The primary subscription-based bridge path (`WatchRequestValueTransfer`) is unaffected for new transfers, but any transfer that was missed by the live subscription (e.g., during a node restart or connectivity gap) and falls in the saturated window will never be re-submitted. This constitutes a permanent loss of bridged assets for affected users until a manual operator intervention (code patch or config change) is applied.

---

### Likelihood Explanation

The Kaia service chain is designed for high-throughput dApp scenarios. An attacker (or even organic traffic) that submits more than ~100 `RequestValueTransfer` transactions per block for 100 consecutive blocks will saturate the 100-block window (10 000 log entries). Because bridge transfer transactions are permissionless (any address can call `requestValueTransfer`), the trigger is reachable by any unprivileged actor. The cost is bounded by gas fees for ~10 000 transactions, which is feasible for a motivated attacker. The failure is silent (trace-level log only) and self-reinforcing.

---

### Recommendation

1. **Adaptive window halving**: on a `FilterLogs` error, halve `filterLogsStride` and retry, similar to the fix recommended in the original Gravity Bridge report.
2. **Advance past unrecoverable windows**: if a window consistently fails after several retries, log a warning and advance `startBlkNum` past it so the loop does not stall permanently.
3. **Raise log level**: change `logger.Trace` to `logger.Warn` so operators are alerted when recovery fails.
4. **Configurable stride**: expose `filterLogsStride` as an operator-configurable parameter so it can be tuned for high-throughput chains.

---

### Proof of Concept

1. Deploy a service-chain bridge pair with VT recovery enabled (`VTRecovery: true`).
2. Submit > 10 000 `requestValueTransfer` transactions within any 100-block window on the child chain, ensuring the operator node misses the live subscription events (e.g., restart the node after the transactions are mined).
3. Observe that `valueTransferRecovery.Recover()` is called on each tick but `retrievePendingEventsFrom` returns an error on every call because `FilterRequestValueTransfer` exceeds `GetLogsMaxItems`.
4. Confirm that `hint.blockNumber` never advances (it stays at the value returned by `RecoveryBlockNumber`), so every subsequent tick re-queries the same failing window.
5. Confirm that the KAIA/ERC20/ERC721 tokens sent in step 2 remain locked in the bridge contract with no automated recovery path.
