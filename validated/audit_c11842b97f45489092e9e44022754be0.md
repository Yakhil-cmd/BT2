### Title
Webhook signature is verified against the wrong tenant's secret, letting a valid webhook sender inject CI status onto any commit across all tracked repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a request against using `params.dig('repository', 'owner', 'login')`, while the handlers that actually act on the payload (e.g. `StatusHandler`) select the target resource independently — in `StatusHandler`'s case with no repository scoping at all. This breaks the binding "organization whose secret authenticated the request == repository/commit that gets written," letting anyone who holds a valid `webhook_secret` for *any* one organization/app configured in the Shipit instance forge a signed request that mutates state (a CI `Status`) belonging to a commit in a completely different, unrelated repository.

### Finding Description
`Shipit.github` supports multiple GitHub App configurations, one per organization, each with its own `webhook_secret`: [1](#0-0) 

The webhook signature is verified using the secret picked from the payload's `repository.owner.login` field: [2](#0-1) [3](#0-2) 

This only proves the sender knows *some* organization's secret — the one named in `repository.owner.login`. It says nothing about which repository/commit the rest of the payload is allowed to touch. The generic handler base class instead resolves the target repository from the independent `repository.full_name` field: [4](#0-3) 

`StatusHandler`, which handles GitHub `status` events, goes further and does not use the repository at all — it looks up commits globally by SHA and writes a `Status` to whichever `Commit` row matches, with zero repository/organization scoping: [5](#0-4) 

An attacker who has a valid `webhook_secret` for **any** one organization tracked by the Shipit instance (e.g., their own org's GitHub App installation) can:
1. Read a public SHA belonging to a victim stack tracked by the same Shipit instance.
2. Craft a `status` event payload with `repository.owner.login` set to their own org (so `verify_signature` fetches and matches *their own* legitimate secret) and `sha` set to the victim's commit SHA, `state: 'success'`.
3. Sign the raw body with their own secret and POST it to `/github/webhooks`.

The signature passes because it is checked against the attacker's own valid secret/organization, but `StatusHandler#process` (`Commit.where(sha: params.sha)`) applies the fabricated green status to the victim's commit regardless of which organization it belongs to.

The equality this breaks: **organization authenticated (`repository.owner.login` used to select `webhook_secret`) == repository/commit actually mutated (`sha` lookup with no owner/org constraint)**. Before the attack, only GitHub, using the correct org's real secret, could report status for that org's commits. After, any organization admin/CI system with a legitimate but unrelated `webhook_secret` can inject arbitrary CI results for any commit tracked by the instance.

### Impact Explanation
A forged successful `Status` directly affects `Stack#deployable?` and `Stack#allows_merges?`, which gate whether a deploy can proceed or whether the merge queue will merge a PR: [6](#0-5) 

By injecting a fake green CI status for a victim's commit, the attacker can make an otherwise-blocked commit "deployable" or mergeable, resulting in an unauthorized deploy or merge on a stack/repository the attacker has no legitimate relationship with — a cross-tenant/cross-repository write and unauthorized deploy/merge, matching the Critical impact bar (unauthorized deploy or merge, cross-repository writes).

### Likelihood Explanation
Requires only: (a) the Shipit instance to be configured with more than one GitHub organization/app (a supported, documented configuration per `Shipit.github_organizations`/`github_app_config`), and (b) attacker possession of a legitimate `webhook_secret` for any one of those configured organizations (which is not a privileged Shipit credential — it's simply the shared secret of a GitHub App/organization webhook, obtainable by anyone administering that org's GitHub App). No Shipit session, API token, or GitHub write access to the victim repository is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the two fields together before trusting the payload: after `verify_signature` succeeds for organization X, reject the event (or reject in each handler) unless `payload.dig('repository', 'full_name')`'s owner equals X. Additionally, `StatusHandler` (and any handler that looks up records without going through `Handler#stacks`/`#repository_name`) should scope its lookup to commits belonging to the repository named in the payload, not to a bare, repository-agnostic `sha` match.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App) and knows a SHA of an undeployed/CI-pending commit on a `victim-org` stack (public repo commit list).
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
signed with `sha1=` HMAC using `attacker-org`'s real `webhook_secret`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own valid secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `Status(state: 'success')` on the victim's commit, with no check that it belongs to `attacker-org`.
6. The victim stack's `deployable?`/`allows_merges?` now reflect the forged green status, letting an unauthorized deploy or merge occur on a repository the attacker never had access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
        end
```
```ruby
      end
```
