### Title
Webhook signature verification selects the GitHub App/organization from an attacker-controlled payload field, decoupled from the repository the event actually acts on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (`docs/setup.md`, "Using Multiple Github Applications", where each org has its own `webhook_secret`), `WebhooksController#verify_signature` picks which organization's `GitHubApp`/`webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once that signature check passes, `WebhooksController#create` dispatches the same raw payload to the event handler, which resolves the repository/stack to act on from a *different* field of the same payload: `Handler#repository_name` = `payload.dig('repository', 'full_name')`. Nothing ties `repository.owner.login` (the field used to select the verifying secret) to `repository.full_name` (the field used to select the repository that is actually written to).

### Finding Description
This breaks the binding: `organization that authenticated == repository that is written`.

- Signature verification: `app/controllers/shipit/webhooks_controller.rb` lines 24-30 call `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`. [1](#0-0) 
- `repository_owner` is derived purely from the request body, not from any authenticated/routed context: [2](#0-1) 
- The event handler, however, determines which `Repository`/`Stack` the event applies to from a separate field of the very same body, `repository.full_name`: [3](#0-2) 
- Multi-org configuration, where each organization has its own distinct `webhook_secret`, is a documented, supported configuration: [4](#0-3) 

Because `verify_webhook_signature` only checks that *some* valid HMAC was produced with *some* org's secret (chosen by the attacker via `repository.owner.login`/`organization.login`), and the handler acts on an independent `repository.full_name` field, an attacker who legitimately knows (or has been issued) the `webhook_secret` for Org A can craft a payload where:
- `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`) → selects Org A's `GitHubApp`/secret for the HMAC check, which the attacker can compute correctly, and
- `repository.full_name` = `"org-b/victim-repo"` → causes the handler to act on Org B's repository/stack, which the attacker has no legitimate relationship with.

The signature check in `GitHubApp#verify_webhook_signature` only validates the HMAC over the raw body using the secret picked this way; it performs no validation that the signing organization matches the repository the payload claims to modify. [5](#0-4) 

For the `push` event this reaches `PushHandler`, which resolves stacks for `repository_name` (`Handler#repository_name`) and enqueues `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack/branch: [6](#0-5) 

This is directly analogous to the H1 report's bug class: a credential/authentication boundary (which org's secret validated the request) is checked against one identity, while the privileged action (which repository/stack is mutated) is performed against a *different, attacker-supplied* identity extracted from the same untrusted input — exactly the "organization that authenticated versus the repository that is written" binding called out in the rules.

### Impact Explanation
An attacker who controls (or has been issued) the webhook secret for one configured GitHub organization on a shared, multi-org Shipit instance can forge webhook deliveries that are processed as if they originated from a completely different organization's repository. Depending on the event handled (e.g. `push`, `status`, `check_suite`, `membership`, `pull_request`), this can trigger `GithubSyncJob` fetches/writes of commit data, status updates, or PR/merge-queue state changes against stacks belonging to a repository/organization the attacker is not authorized for — a cross-organization/cross-repository write inside the engine's own trust model, satisfying the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Requires (a) a Shipit deployment configured with multiple GitHub organizations/apps (a documented, supported configuration) and (b) the attacker knowing one org's `webhook_secret` — plausible for a webhook secret provisioned to a less-trusted org/team on a shared instance, mirroring the original report's premise of a lower-privileged principal escalating trust across a boundary the application assumes is aligned but does not verify. It does not require a Shipit session, admin access, or GitHub App private key.

### Recommendation
When resolving which `GitHubApp`/secret to verify a webhook against, cross-check that the resolved organization actually corresponds to the same organization referenced by `repository.full_name` (or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`) before dispatching to handlers. Alternatively, bind incoming webhooks to a specific organization via the URL route/config rather than deriving the verifying identity from attacker-controlled payload fields.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config), and create a stack for `org-b/victim-repo`.
2. As a holder of `org-a`'s `webhook_secret`, build a `push` payload body:
```json
{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen or known sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`), verifies successfully against `org-a`'s secret.
5. `PushHandler` resolves the target repository via `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"`, and enqueues `GithubSyncJob` for `org-b`'s stack, even though the request was never signed by `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
