### Title
AA trigger evaluation crash via double-completion of prematurely destroyed data-feed key stream - ([File: data_feeds.js])

### Summary
`dataFeedByAddressExists()` in `data_feeds.js` opens a RocksDB key-stream via `kvstore.createKeyStream()` to check `data_feed`/`in_data_feed` conditions used inside oscript/AA formulas. When a matching record is found before the relational range is exhausted, the code calls `stream.destroy()` and *synchronously* invokes the completion callback `onEnd()` itself, instead of waiting for the stream's own `'end'`/`'close'` event. [1](#0-0)  This is structurally identical to the Envoy OAuth2 bug class: an async I/O object (`stream`, analogous to Envoy's `AsyncClient`) is torn down while a completion path can still fire later and reach code (`onEnd`) that assumes the operation's lifetime has already ended.

### Finding Description
`dataFeedByAddressExists` sets up a leveldown/rocksdb key-stream and a `handleData`/`onEnd` pair: [2](#0-1) 
- `handleData` finds a satisfying record, sets `bFound = true`, calls `stream.destroy()`, and then immediately calls `onEnd()` itself (line 184-185).
- `onEnd()` is guarded by `bOnEndCalled` and explicitly `throw Error("second call of onEnd")` if invoked twice.
- The stream is also wired with `.on('end', onEnd)`.

`stream.destroy()` on a levelup/abstract-leveldown `ReadStream` does not synchronously stop the stream — it schedules asynchronous teardown of the underlying rocksdb iterator, and the stream can still emit its own `'end'` (or, depending on version, buffered `'data'`) event afterwards on a future tick, because destruction and event delivery race independently of the manual `onEnd()` call made by `handleData`. Since `onEnd()` was already invoked manually right after `destroy()`, the stream's own later `'end'` event fires the same `onEnd` handler a second time, hitting the `throw Error("second call of onEnd")` guard and crashing the process (unhandled exception since this callback is not inside a `try/catch` at the top of the call stack, e.g. it runs inside `handleAATriggers` → `handleTrigger` → oscript evaluation for `data_feed`/`in_data_feed`).

This code path is reached from ordinary oscript evaluation: [3](#0-2) [4](#0-3) 
Both `data_feed[[...]]` and `in_data_feed[[...]]` with a non-equality relation (`<`, `<=`, `>`, `>=`, `!=`) route through `dataFeedByAddressExists`/`readDataFeedByAddress`, which is the vulnerable premature-destroy path. Any AA definition can embed such a formula, and any unprivileged user can post a trigger unit to that AA (or an oracle address can simply post enough matching `data_feed` messages) to make the query match before stream exhaustion, hitting the race.

### Impact Explanation
When the double `onEnd()` throw fires, it happens deep inside AA trigger execution (`handlePrimaryAATrigger` → `handleTrigger`), which runs under the `aa_triggers` mutex while a SQL transaction (`conn`) and a RocksDB `batch` are open (BEGIN already issued, COMMIT and `batch.write` not yet issued). [5](#0-4)  A crash at this point during full-node processing of a *stable* trigger unit means the node cannot deterministically finish executing AA triggers for that unit: on restart, the SQL transaction rolls back but partial in-memory caches (`storage.assocStableUnits`, `assocUnstableMessages`, etc.) and/or the kvstore batch state may not perfectly reconcile depending on where exactly the crash lands, and every restart hits the exact same crash again on the same trigger since the request data is already stable and re-triggers deterministically — producing a stuck node that can never advance past this MCI, i.e. "a network unable to confirm new units" once enough nodes hit the identical crash, and disagreement between nodes that already processed the trigger vs. those that get stuck.

### Likelihood Explanation
Any user can define an AA using `data_feed[[...]]` or `in_data_feed[[...]]` with a relational operator, then arrange (as the oracle or simply by waiting for a normal oracle feed) for more than one qualifying `data_feed` message to exist for the referenced address/feed_name within the queried MCI range, and post a trigger to the AA. This is a normal, unprivileged interaction (AA definition + AA trigger sender), requiring no special network position, hub access, or peer trust — well within the reachable attack surface (oscript/AA trigger evaluation, data feeds).

### Recommendation
Do not manually invoke `onEnd()` from `handleData` after calling `stream.destroy()`. Instead:
- Set `bFound = true` and call `stream.destroy()`, but let the stream's own terminal event (`'close'`, or a single guaranteed `'end'`) call `onEnd()`, or
- Remove the `'end'` listener before/after calling `destroy()` and detach `handleData`, guaranteeing `onEnd` fires exactly once regardless of which path (manual early-exit vs. natural stream exhaustion) triggers it, e.g. by wrapping `onEnd` in an idempotent "call once" helper instead of throwing on double invocation.

### Proof of Concept
1. Define an AA whose oscript uses `in_data_feed[[oracles=..., feed_name="x", feed_value>0]]` (or `data_feed[[...]] ` with a relational operator).
2. Have the oracle post at least two `data_feed` messages for `feed_name="x"` with values satisfying the relation, within the min_mci/max_mci window that will be queried (e.g. two stable units with `x=5` and `x=10`).
3. Post a trigger unit to the AA so it becomes stable and is processed by `handleAATriggers`.
4. During evaluation, `dataFeedByAddressExists` (or `readDataFeedByAddress`, same pattern) finds the first satisfying key, calls `stream.destroy()` and manually invokes `onEnd()`; the underlying rocksdb iterator's asynchronous teardown subsequently fires the stream's own `'end'` event, invoking `onEnd()` a second time and hitting `throw Error("second call of onEnd")`, crashing the node process while mid-way through the AA trigger's DB transaction/batch.
