### Title
API scoping bypass allows a stack-restricted `ApiClient` token to read any stack's CI/CD status via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` bound to a single stack (`ApiClient#stack_id`) can only resolve stacks through the scoped `stacks` relation. `Shipit::Api::CCMenuController` overrides the `stack` lookup with an unscoped `Stack.from_param!` call, breaking that binding and letting a stack-scoped token read the CCMenu status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping primitive used by every API resource: [1](#0-0) 

`stacks` is deliberately restricted to `current_api_client.stack_id` when the authenticated client is bound to a specific stack, and `stack` (singular) is derived from that scoped relation, so `Stack.from_param!` can never resolve to a stack outside the client's authorization — this is the intended equality: `stack a token authorises == stack a token can touch`.

`Shipit::Api::CCMenuController` inherits from `BaseController` and only checks the *permission name* (`read:stack`), not the *scope*: [2](#0-1) 

But it overrides the `stack` accessor to bypass the scoped `stacks` relation entirely, resolving directly against the global `Stack` model: [3](#0-2) 

`Stack.from_param!` performs a global lookup with no scoping at all: [4](#0-3) 

`ApiClient` legitimately supports being bound to one stack (`belongs_to :stack, optional: true`), and this is a tested, intended authorization mechanism (`current_api_client.stack_id?`), exercised by the fixture `here_come_the_walrus` (`stack: shipit`) and the base controller's test suite ("an api client scoped to a stack will only see that one stack"): [5](#0-4) [6](#0-5) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, the `require_permission :read, :stack` check only verifies the client *has* the `read:stack` permission string — it never verifies the client is authorized for the *specific* `stack_id` in the request. The equality `stack the token authorises == stack the action touches` is broken specifically on this controller, while it holds everywhere else that uses the inherited `stack`/`stacks` helpers (`StacksController`, `DeploysController`, `RollbacksController`, `TasksController`, `HooksController`, etc., all of which call `stacks.from_param!`/`stack` from `BaseController`).

### Impact Explanation
An attacker holding any valid API token with the `read:stack` permission — even one deliberately restricted by an administrator to a single stack via `ApiClient#stack_id` — can query `GET /api/stacks/<owner>/<repo>/<environment>/ccmenu` for **any** stack in the Shipit installation, not just the one the token was scoped to. This discloses stack name, lock status, and latest build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`) for stacks the token holder has no authorization to see, which is exactly the "unauthorized read of stack state" scenario called out as a High-severity outcome: escalation past the `ApiClient`'s stack-scoping (an authorization boundary intentionally enforced by `BaseController#stacks`) to read state of stacks outside the token's authorized scope.

### Likelihood Explanation
Any consumer who is issued a stack-scoped API token (a supported, tested configuration) can trigger this with a single unauthenticated-scope GET request; no privileged access, secrets, or social engineering beyond possessing one legitimately-issued, narrowly-scoped token is required. The only prerequisite is a valid `ApiClient` credential with `read:stack` permission and any `stack_id`, which is the normal way third-party integrations (e.g., CCTray/CCMenu monitoring tools) are provisioned.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited, scoped `stacks` relation) so that CCMenu lookups go through `stacks.from_param!(params[:stack_id])` exactly like every other API controller, ensuring a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. As an administrator, create (e.g. via Rails console, matching the `here_come_the_walrus` fixture pattern) an `ApiClient` with `permissions: ['read:stack']` and `stack: <stack_A>`.
2. Using that client's `authentication_token`, issue:
   `GET /api/stacks/<owner>/<repo_B>/<environment_B>/ccmenu` (Basic auth with the token), where `repo_B/environment_B` is a **different** stack the token was never scoped to.
3. Observe that `Api::CCMenuController#show` renders the CCMenu XML for `stack_B` (its name, lock state, and latest deploy status) with a `200 OK`, even though `current_api_client.stack_id` only authorizes `stack_A` — confirming that `stack` bypasses the scoping enforced by `BaseController#stacks`/`#stack` used elsewhere in the API.
