### Title
Cross-repository forged `status` webhook can trigger unauthorized `MergeRequest#merge!` due to unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the *entire* database, with no check that the commit's stack/repository matches the webhook's own repository. An attacker who controls any Shipit-integrated repository (and can therefore produce a validly-signed webhook for their own org) can forge a `status` event naming a victim's PR head commit SHA (public information), causing the forged status to be attached to the victim's commit, `schedule_merges` to fire, and `ProcessMergeRequestsJob` to eventually call `merge_request.merge!` against the victim's real Shipit stack/GitHub credentials.

### Finding Description
The broken binding, stated as an equality that must hold but never does: `webhook_repository_owner (signature-verified org) == commit.stack.repository.owner` for the `Commit` object mutated by `StatusHandler#process`.

Trace:
1. `Shipit::WebhooksController#verify_signature` only checks that the payload's `repository.owner.login` matches an org whose webhook secret produced a valid HMAC — it verifies the attacker legitimately controls *that org*, nothing about which commits may be touched: [1](#0-0) .
2. `Shipit::Webhooks::Handlers::Handler` defines a `stacks` helper meant to scope handler logic to the repository named in the payload: [2](#0-1) . `StatusHandler#process`, however, never uses it — it queries `Commit.where(sha: params.sha)` globally: [3](#0-2) .
3. `create_status_from_github!` → `add_status` records the forged status and, on a `pending`/`success` transition, calls `stack.schedule_merges` — `stack` here is the *victim's* stack, derived solely from the matched `Commit`, not from the webhook's own repository: [4](#0-3) .
4. `Stack#schedule_merges` enqueues `ProcessMergeRequestsJob` for that victim stack: [5](#0-4) .
5. `ProcessMergeRequestsJob#perform` calls `merge_request.refresh!`, then checks `all_status_checks_passed?`, then `merge_request.merge!` — no hop re-verifies which org produced the triggering status: [6](#0-5) .
6. `all_status_checks_passed?` evaluates `StatusChecker` over `head.statuses_and_check_runs`, which includes the forged `Status` row permanently (persisted via `find_or_create_by!` in `Status.replicate_from_github!`): [7](#0-6) [8](#0-7) . `refresh!`'s call to `head.refresh_statuses!` fetches real GitHub statuses but never deletes stale/forged ones with unmatched contexts, so a forged status under a context GitHub hasn't (yet) reported leaves the check "passed": [9](#0-8) .
7. `merge!` then calls `stack.github_api.merge_pull_request(...)` using the **victim stack's** real GitHub App credentials against the **victim's** real PR: [10](#0-9) .

Root cause: `StatusHandler#process` never confirms the commit it mutates belongs to a stack whose repository matches the webhook's authenticated repository/org — the only scoping mechanism (`Handler#stacks`) exists in the base class but is unused here.

### Impact Explanation
An attacker who legitimately controls one Shipit-configured repository/org can, with a single forged webhook, poison the CI-status state of an arbitrary commit belonging to a *different, unrelated* tenant's stack, and trigger `ProcessMergeRequestsJob` to execute an unauthorized `merge_pull_request` call using that victim tenant's own GitHub credentials. This is a cross-tenant, payload-for-one-repository-mutates-another's-stack/commit scenario — matching the "unauthorized merge" Critical category. It is repeatable against any stack/commit whose SHA the attacker can learn (trivial for public repos, or any repo the attacker can read).

### Likelihood Explanation
Preconditions: the attacker must control at least one repository/org with a working Shipit webhook integration (a capability explicitly granted per the audit's threat model — "emit webhooks from a repository they own"). Beyond that, the attack requires only knowing the victim's target commit SHA (public GitHub data) and crafting a JSON `status` payload with a fabricated `repository.full_name`/`sha`/`state`. No secrets, tokens, or privileged roles of the victim org are needed. This is low-cost and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository asserted (and cryptographically confirmed) by the webhook, e.g. restrict to commits belonging to `stacks` (the `Handler#stacks` helper already scoped by `repository_name`) instead of a bare `Commit.where(sha: params.sha)` across the whole database.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_status_cross_repo_test.rb
require 'test_helper'

module Shipit
  class WebhooksCrossRepoForgeTest < ActionController::TestCase
    tests WebhooksController

    test "a status webhook signed for attacker's org cannot mutate a commit belonging to a different repository's stack" do
      victim_stack = shipit_stacks(:shipit) # repo e.g. "shopify/shipit-engine"
      victim_commit = shipit_commits(:first) # belongs to victim_stack
      victim_pr = victim_stack.merge_requests.create!(number: 42, head: victim_commit, state: 'pending')

      attacker_payload = {
        'sha' => victim_commit.sha,
        'state' => 'success',
        'context' => 'ci/forged',
        'created_at' => 10.years.from_now.to_s, # ensure it wins ordering
        'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
      }.to_json

      GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # attacker owns attacker-org's secret legitimately

      request.headers['X-Github-Event'] = 'status'

      assert_no_difference -> { victim_commit.stack_id } do
        assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack]) do
          post :create, body: attacker_payload, as: :json
        end
      end

      # BINDING CHECK: webhook org ("attacker-org") must equal victim_stack.repository owner ("shopify") for this mutation to be legitimate
      refute_equal 'attacker-org', victim_stack.repository.owner
      assert victim_commit.reload.statuses.exists?(context: 'ci/forged'), 'forged status was attached to a commit outside the webhook repository'
    end
  end
end
```
This demonstrates the equality `attacker-org == victim_stack.repository.owner` is false yet the forged status is still written, confirming the missing scope check in `StatusHandler#process`.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
