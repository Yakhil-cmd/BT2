The H2O exploit is a "weak randomness" bug class: the vulnerable contract derived its "random" outcome from fully predictable/observable on-chain values (`block.timestamp`, a pair address, and `blockhash`), so the attacker could pre-compute the result and only submit the profitable transaction (or retry until the check passed), turning a "random" mint decision into a fully controllable one.

## Analog in ocore

The closest reachable analog is `number_from_seed()` in oscript, the built-in "randomness" primitive available to AA authors, combined with the fact that **AA trigger execution is fully deterministic and can be dry-run by anyone before committing to posting the real unit**.

- `number_from_seed` is implemented in the formula evaluator as a pure `sha256`-derived deterministic function of whatever value(s) the AA author passes in — there is no on-chain entropy source at all: [1](#0-0) 
- The grammar/validation layer treats it as an ordinary function taking up to 3 arbitrary expression arguments (seed, optional min/max) — the AA author is free to seed it with predictable data such as `trigger.unit`, `trigger.address`, `timestamp`, `response_unit`, etc: [2](#0-1) [3](#0-2) 
- Crucially, ocore explicitly exposes a way to **simulate/dry-run an AA trigger without posting anything on-chain**, both internally and over the light-client protocol: `dryRunPrimaryAATrigger` executes the full AA logic (including any `number_from_seed` calls) against a caller-supplied trigger and returns the exact response, state changes and payment outputs: [4](#0-3) 
- This dry-run capability is reachable by any unprivileged client over the network protocol via `light/dry_run_aa`, which accepts an arbitrary trigger object (address, outputs, data) from the caller and returns the simulated AA response: [5](#0-4) 
- Because AA execution is fully deterministic given the trigger data known in advance (the trigger's own `unit`/`address`/`data`, and `timestamp`/`mci` of the last stable MC unit, all of which are either chosen by the sender or already public), any AA that uses `number_from_seed` with such predictable inputs to decide a probabilistic outcome (e.g., a lottery, gamble, or reward split) can have its outcome fully computed off-chain via `light/dry_run_aa` before the real triggering unit is posted. An attacker can dry-run the trigger repeatedly (varying `data`/`outputs`/timing) until a favorable outcome is predicted, then post only that specific unit — the exact "test-then-commit-only-if-profitable" pattern used in the H2O `_setRandomIn` loop.

Note that `vrf_verify` exists in the same module as a cryptographically sound alternative (verifiable, unpredictable randomness signed by an off-chain key), which underscores that `number_from_seed` alone provides no unpredictability guarantee and is unsafe for on-chain gambling/reward logic when seeded with attacker-visible/predictable data: [6](#0-5) 

### Title
Weak/Predictable Randomness via `number_from_seed` in AA Definitions Enabling Outcome Prediction and Selective Triggering - (File: formula/evaluation.js, aa_composer.js, network.js)

### Summary
AA authors can implement probabilistic logic (lotteries, reward splits, games) using the oscript `number_from_seed()` function. If the seed is derived from data that is known or chosen by the trigger sender before the triggering unit is finalized (e.g., `trigger.unit`, `trigger.data`, `timestamp`, `mci`, `response_unit`), the "random" outcome is not actually unpredictable. Combined with ocore's `light/dry_run_aa` network command, which lets any client fully simulate an AA's response to an arbitrary trigger without posting anything, an attacker can precompute the outcome for many candidate triggers and only submit the one unit that yields a favorable result — exactly mirroring the H2O exploit's use of a predictable PRNG that was checked before committing to the attack transaction.

### Finding Description
`number_from_seed` computes `sha256(seed)` and maps it deterministically into a number/range; it has no built-in entropy and depends entirely on whatever expression the AA author supplies as the seed (`formula/evaluation.js:1872-1918`). Common seed choices available to AA authors — `trigger.unit`, `trigger.address`, `trigger.data`, `timestamp`, `mci`, `response_unit` — are either fully controlled by the sender before posting, or are public/deterministic values of the last stable MC unit at dry-run time. Because `dryRunPrimaryAATrigger` (`aa_composer.js:272-306`) executes the AA logic exactly as it would run for real and is exposed unauthenticated via `light/dry_run_aa` (`network.js:3939-3963`), an attacker can iterate over candidate trigger contents/timing off-chain, observe the simulated `number_from_seed` outcome, and post a real unit only when the simulated result is favorable to them. This nullifies the intended randomness/fairness guarantee of any lottery-, game-, or reward-distribution AA that relies on `number_from_seed` seeded with such values.

### Impact Explanation
An AA that pays out funds based on a `number_from_seed`-derived "random" win/lose or split decision can be gamed to virtually guarantee a win for the attacker, resulting in unauthorized draining of the AA's balance/reserve to the attacker's advantage — directly analogous to the fund loss caused by the H2O weak-randomness mint. This is an AA fund loss risk (Medium/High depending on AA design and funds at stake), reachable purely by an unprivileged trigger sender crafting/dry-running trigger units.

### Likelihood Explanation
Likelihood is high for any AA that adopts this common/tempting pattern, since `number_from_seed` is a documented, easily-discoverable oscript primitive, and `light/dry_run_aa` is a standard, unauthenticated light-client RPC available to any wallet/attacker without needing to post real units or pay fees for failed attempts.

### Recommendation
- Do not seed `number_from_seed` with any value known to, or influenceable by, the trigger sender before the response is committed (avoid `trigger.*`, `timestamp`, `mci`, `response_unit`, or any state derivable from the current unstable DAG).
- Prefer `vrf_verify` with an unpredictable, provably-random seed generated and signed off-chain, or use a commit-reveal scheme spanning multiple stabilized units so the seed cannot be known at dry-run time.
- Consider restricting or rate-limiting `light/dry_run_aa` usage for AAs that use `number_from_seed`, or document/warn AA authors prominently against seeding with sender-controlled or dry-run-visible data.

### Proof of Concept
1. Deploy an AA whose logic is: `$r = number_from_seed(trigger.unit, 0, 1); if ($r == 1) { pay attacker_wins } else { pay AA_keeps }`.
2. Attacker crafts a candidate trigger (choosing `data`, output amounts, etc., which influence `trigger.unit`'s hash once assembled) and calls `light/dry_run_aa` (`network.js:3939`) repeatedly with slight variations (e.g., different `data` payloads or timestamps) until the simulated `dryRunPrimaryAATrigger` response shows `$r == 1`.
3. Attacker posts only the real unit matching the favorable simulated trigger, guaranteeing a win and draining the AA's reserved funds — the same "simulate first, submit only if profitable" strategy as `_setRandomIn` in the H2O PoC.
