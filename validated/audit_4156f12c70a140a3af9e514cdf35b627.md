### Title
A single bad/nonexistent asset in a multi-asset AA response payment causes the entire response unit to bounce, discarding all other legitimate payment messages - (File: `aa_composer.js`)

### Summary
`sendUnit()` in `aa_composer.js` builds an AA's response unit from a list of `messages`, iterating over them with `async.eachSeries` and, for each non-base payment message, loading the referenced asset via `storage.loadAssetWithListOfAttestedAuthors`. If that load fails, or if the asset is a private asset, the callback is invoked with an error, which immediately calls `bounce(err)` and aborts the **entire** response unit — including all other, unrelated payment messages for other assets/recipients that were already validated successfully.

### Finding Description
In `sendUnit`, each payment message's asset is resolved individually: [1](#0-0) 

If `storage.loadAssetWithListOfAttestedAuthors` returns an error (e.g., the asset does not exist, or fails some validity check) the per-message callback is `cb(err)`, and if the asset is a private asset it explicitly returns `cb("sending private asset from AA")`. Both propagate to the `async.eachSeries` final callback: [2](#0-1) 

which calls `bounce(err)` — a full rollback of the AA's response, restoring state vars/balances and returning only the trigger's own deposited outputs (not the intended payout) via the earlier `bounce()` implementation: [3](#0-2) 

This is the same bug class as the reported OpenQ issue: a loop over several independent asset payments is wrapped in a single all-or-nothing transaction, and one bad element (here, an asset reference that fails to resolve, or that is private) unconditionally aborts *all* the other, otherwise-valid payment messages in the same response — even though only one asset among several is problematic. Any AA whose oscript logic composes a response containing multiple `payment` messages for different assets (a common multi-asset settlement/distribution pattern, e.g. paying several depositors back in their respective deposited assets, or forwarding a batch of different asset payouts in one trigger) is exposed: an attacker only needs to get one bad asset reference included in that batch (e.g., by depositing/issuing a private asset the AA later tries to forward, or by supplying/triggering with an asset id that doesn't exist) to force the whole response to bounce.

### Impact Explanation
When this happens, the AA cannot deliver any of the payments in that trigger response — not just the one tied to the bad asset. Because AA execution is deterministic and the same trigger will hit the same failure every time it is reprocessed/retried with the same messages logic, this can make legitimate payouts to other, unrelated addresses permanently undeliverable through that code path (funds get stuck bounced back to the trigger sender rather than reaching the intended recipients), which is a fund-freezing/denial-of-service condition for an AA that batches multi-asset payments — matching the Sherlock report's "malicious/paused token blocks claiming for everyone in the batch" pattern.

### Likelihood Explanation
Reaching this requires an AA design that batches multiple asset payments (based on state/trigger data) into one response and where the asset used in one of the payment messages can be influenced by an unprivileged actor (e.g., a user-deposited asset, or an asset id taken from trigger data). This is a plausible and common AA pattern (multi-asset vaults, swap/distribution AAs), but it is design-dependent — it is not a defect in the core protocol validation itself, only in how `sendUnit`'s all-or-nothing loop composes AA-authored response units. It requires no privileged access: any address can define a private asset or reference a nonexistent asset id in trigger data.

### Recommendation
Do not let a single failing asset message abort the whole batch. Options:
- Validate/pre-check each payment message's asset (existence, `is_private`) before including it in `messages`, and skip or defer messages for assets that cannot be sent, rather than letting `sendUnit` bounce the entire unit on the first bad one.
- Alternatively, change `sendUnit`'s asset-resolution loop from `async.eachSeries` fail-fast semantics to a mode that drops/reports the offending message (similar to how `fixed_denominations` assets are already skipped) instead of erroring the whole batch, and let AA authors decide (via oscript) how to handle payments to invalid/private assets independently per message.

### Proof of Concept
1. Deploy an AA whose response logic composes multiple `payment` messages in a single trigger response, e.g. paying back several different assets to their respective owners in one unit (a multi-asset settlement pattern), where at least one asset id is derived from trigger data or state (attacker-influenced), as in `sendUnit`'s message-processing loop: [4](#0-3) 
2. Trigger the AA in a way that causes one of the resolved assets to be a private asset (or a non-existent asset id) - the loop at lines 1323-1330 will call `cb("sending private asset from AA")` or `cb(err)`.
3. Observe that `async.eachSeries`'s final callback receives that error and calls `bounce(err)` at [5](#0-4) , discarding all other payment messages that had already resolved successfully in the same batch, and the trigger's response is bounced instead of delivering the legitimate payouts.
