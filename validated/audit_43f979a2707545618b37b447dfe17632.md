### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App secret while the acted-upon repository is selected from the unrelated `repository.full_name` field, allowing cross-organization webhook forgery when any onboarded organization has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to validate a delivery against using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while every event handler (`Handler#stacks`, `PushHandler`, the `PullRequest::*` handlers) selects which `Repository`/`Stack` to act on using the completely separate `repository.full_name` field from the same body. Nothing binds these two fields together, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the organization's `webhook_secret` is blank. This lets a request "authenticated" as belonging to one (weakly configured) organization drive side effects against a repository/stack that actually belongs to a different, properly-secured organization.

Meanwhile, every handler resolves the target repository purely from `repository.full_name`, independent of whatever field was used for signature verification: [4](#0-3) [5](#0-4) 

The equality that should hold is: `organization whose secret verified the signature == organization owning the repository the handler acts on`. Because `repository.owner.login` (verification key) and `repository.full_name` (action target) are independent, unvalidated fields of the same JSON body, an attacker who can produce a payload that "verifies" (either because they know a valid secret for *some* onboarded org, or because that org has no `webhook_secret` configured — a state explicitly supported by the code and shown as the default in every shipped config template, e.g. `webhook_secret: # nil`) can set `repository.full_name` to point at a stack belonging to an entirely different organization. The handler code performs no comparison between the verified organization and the repository actually referenced.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out in scope. A forged `push` webhook processed this way calls `stack.sync_github(expected_head_sha: ...)` on an arbitrary stack chosen by the attacker, regardless of which organization the signature nominally verified against. Other events registered the same way (`status`, `check_suite`, `membership`, `pull_request` handlers) are equally reachable and can create commit statuses, mutate `PullRequest`/`ReviewStack` records (archive/unarchive, provisioning), or otherwise manipulate deploy-affecting state (e.g. commit deployability, review-stack archival) for repositories outside the organization whose credentials were actually used to authenticate the request. Because commit/status state feeds into deploy-eligibility and continuous-deployment scheduling elsewhere in the engine, this can cross an authorization boundary between organizations hosted on the same Shipit instance and influence which commits are considered deployable.

### Likelihood Explanation
No `ApiClient` token, session, or GitHub App private key is required — the `/webhooks` endpoint is unauthenticated by design and only gated by the per-organization HMAC check. The weak case (`webhook_secret` blank) is not a hypothetical misconfiguration outside the documented setup: it is the literal default in `docs/setup.md`'s schema description ("if you've set a webhook secret... you should copy it here") and in every shipped secrets template in this repository, and the engine's own code (`return true unless webhook_secret`) explicitly treats an absent secret as "verification passes." Any multi-organization Shipit deployment (a supported, documented configuration — see `secrets_double_github_app.yml`) where at least one organization has not set a webhook secret is exploitable by an unauthenticated network attacker.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive the verifying organization from `repository.full_name`'s owner segment (or otherwise reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`), and stop treating a blank `webhook_secret` as an implicit "verification passed" — require an explicit opt-out instead of a silent default-allow.

### Proof of Concept
1. Onboard two organizations to one Shipit instance: `WeakOrg` (no `webhook_secret` set, matching the shipped default templates) and `SecureOrg` (has a stack `SecureOrg/prod`, `webhook_secret` set to a real secret unknown to the attacker).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-present-in-SecureOrg/prod>",
  "repository": {
    "full_name": "SecureOrg/prod",
    "owner": { "login": "WeakOrg" }
  }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "WeakOrg").verify_webhook_signature(...)`, which returns `true` unconditionally because `WeakOrg` has no `webhook_secret`.
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("SecureOrg/prod")` and invokes `stack.sync_github(expected_head_sha: ...)` on `SecureOrg`'s stack — a side effect on `SecureOrg`'s deployment pipeline triggered without ever presenting a valid credential for `SecureOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
