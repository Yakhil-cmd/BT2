### Title
Cross-repo forged CI status via `StatusHandler#process` bypasses `require_ci` in `Shipit::Api::DeploysController#create` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` record for every `Commit` row that matches the webhook's `sha`, without restricting the search to the repository the webhook actually originated from. An attacker who owns a repository that shares a commit `sha` with a victim stack (e.g., a public fork or a shared upstream commit) can send a legitimately-signed GitHub status webhook for their own repo and have Shipit attach that forged status to the victim stack's own `Commit` record, making `commit.deployable?` return `true` for that commit even when the victim stack's own CI never ran or failed.

### Finding Description
The binding that should hold is: **`commit.deployable?` for victim/prod's `Commit` == a function solely of Status rows created from webhooks whose `repository.full_name` matches victim/prod's own repository**. This binding is violated.

- `Shipit::Webhooks::Handlers::Handler` defines a `stacks` helper that correctly scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, using the webhook payload's own repository field: [1](#0-0) 
- `StatusHandler#process`, however, does **not** use this scoping. It queries `Commit.where(sha: params.sha)` across the whole `commits` table, irrespective of which repository sent the webhook: [2](#0-1) 
- `Commit#create_status_from_github!` then creates the `Status` using the commit's *own* `stack_id` (the victim stack's id), not any id tied to the webhook's originating repository: [3](#0-2) 
- `Commit#deployable?` is computed purely from the commit's own `status` (all `statuses` + `check_runs` associated to that `Commit` row), which now includes the forged row: [4](#0-3) [5](#0-4) 
- `Shipit::Api::DeploysController#create` uses exactly this `commit.deployable?` to enforce `require_ci`: [6](#0-5) 

Exploit flow: the attacker owns/controls a GitHub repository (e.g., a public fork of victim/prod, or a repo that shares an ancestor commit) that is connected to Shipit as its own stack (with the attacker's own GitHub App installation/organization). They push or otherwise cause GitHub to emit a `status` webhook for a commit `sha` that also exists as a `Commit` row in victim/prod's stack (this happens automatically whenever victim/prod's stack has ingested that shared-history commit via its normal push/sync flow). GitHub signs this webhook legitimately for the attacker's own organization/installation, so `WebhooksController#verify_signature` (via `Shipit.github(organization: repository_owner).verify_webhook_signature`) passes — the signature check validates authenticity of *a* GitHub webhook for *that org*, but does not verify that the `sha`/commit referenced by the payload actually belongs to that org's repository. `StatusHandler#process` then writes a `success` `Status` scoped to the victim stack's `Commit`, so `commit.deployable?` becomes `true` on the victim's own stack.

An operator with legitimate (or even just their own, unprivileged) deploy permission on victim/prod then calls `POST /api/stacks/:id/deploys` with `require_ci: true`. The `param_error!(:require_ci, ...)` check reads the now-poisoned `commit.deployable?` and passes, so the deploy proceeds (`202 Accepted`) even though `require_ci: true` was supposed to prevent exactly this. This is not blocked by any existing guard: `verify_signature` only checks the signature belongs to the sending org, not that the sha/repo referenced in the payload is owned by that org; `drop_unhandled_event` doesn't apply to `status` events (they have a handler); `ExplicitParameters` schema in `StatusHandler` only validates types/presence, not repository ownership; and `require_permission!`/the `deploy` permission on `DeploysController` only checks the caller's authorization for the target stack, not the provenance of the CI status data.

### Impact Explanation
This allows an unauthorized deploy to proceed against `require_ci: true`'s explicit safety intent — the exact "Critical" category listed ("unauthorized deploy... proceed[ing]", and "a payload for one repository mutating another's stack[/]commit"). The blast radius is any stack whose commit history overlaps (shares a sha) with any GitHub repository reachable by an attacker (their own repo, a fork, or a repo sharing common ancestor commits with the victim). Because `Commit.where(sha:)` is global and unscoped, one forged status webhook writes a `Status` row directly onto the victim's own `Commit`/`Stack` association, defeating the CI safety net for that stack without needing any Shipit credentials, GitHub App private key, or `webhook_secret` belonging to the victim.

### Likelihood Explanation
Preconditions: (1) the attacker must control (or be able to trigger legitimate signed webhooks from) some GitHub repository that is itself registered as a Shipit stack, and (2) that repository must share at least one commit `sha` with the victim stack (trivially achievable by forking a public repo — fork commits retain identical SHAs as the upstream until diverged, or by cherry-picking/merging shared history). No secrets are needed; the attacker only needs their own legitimate GitHub webhook to fire (e.g., by pushing a status via GitHub's Status API to their own repo/commit, or by any action that causes GitHub to emit a `status` event referencing that shared sha). This is a low-cost, repeatable attack per shared sha and is feasible against any Shipit deployment that ingests commits from multiple related repositories/forks.

### Recommendation
Scope `StatusHandler#process` (and audit other handlers similarly) to only update commits belonging to stacks whose repository matches the webhook payload's `repository.full_name`, using the existing `stacks` helper from `Shipit::Webhooks::Handlers::Handler`, e.g. iterate `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from unrelated repo must not mark a victim stack's commit as deployable" do
  victim_stack = shipit_stacks(:shipit) # e.g. repo "shopify/shipit-engine"
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-fork' }, # not victim's repo
    'branches' => [{ 'name' => 'master' }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  refute_predicate victim_commit, :deployable?, "victim commit must not become deployable from an unrelated repo's status"
end
```
```ruby
# test/controllers/api/deploys_controller_test.rb (conceptual)
test "#create refuses require_ci: true deploy even if status was forged via cross-repo webhook" do
  shared_sha = @commit.sha
  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-fork' },
    'branches' => [{ 'name' => 'master' }]
  )

  assert_no_difference -> { @stack.deploys.count } do
    post :create, params: { stack_id: @stack.to_param, sha: shared_sha, require_ci: true }
  end
  assert_response :unprocessable_entity
  assert_json 'errors.require_ci', ["Commit is not deployable"]
end
```
Both assertions verify the equality claimed in the audit: `commit.deployable?` for the victim's own `Commit`/`Stack` must be computed solely from statuses whose originating webhook repository matches the victim's own repository, and currently it is not.
