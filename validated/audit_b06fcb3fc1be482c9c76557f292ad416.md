### Title
`ProxyType::NonTransfer` falsely declares itself a superset of `ProxyType::Auction`/`ProxyType::SudoBalances` in the Westend relay-chain runtime, allowing proxy privilege escalation via `add_proxy` - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
`pallet_proxy` authorizes nested `add_proxy`/`remove_proxy` calls solely via `ProxyType::is_superset`, not via `ProxyType::filter` (`substrate/frame/proxy/src/lib.rs:1004-1023`). In `polkadot/runtime/westend/src/lib.rs:1022-1030` the `is_superset` implementation contains a blanket rule `(ProxyType::NonTransfer, _) => true`, i.e. `NonTransfer` is declared a superset of *every* other proxy type, including `SudoBalances` and `Auction`. However, `NonTransfer`'s own `filter` (lines 954-982) does **not** admit every call that `SudoBalances` and `Auction` admit: it explicitly excludes the `Sudo` pallet ("Specifically omitting Sudo pallet") and explicitly excludes `paras_registrar::Call::swap` ("Specifically omitting Registrar `swap`"), while `SudoBalances` admits `Sudo::sudo{Balances(..)}` and `Auction` admits the whole `Registrar(..)` call family (including `swap`). This is exactly the bug class already fixed for AssetHub Westend in `prdoc/pr_12769.prdoc` ("`NonTransfer` proxy falsely claiming `Governance` containment") — but the fix and its regression test (`proxy_type_superset_relation_matches_call_filters` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2494-2516`) were only applied to the AssetHub Westend runtime, not to the Westend relay-chain runtime (nor to `substrate/frame/staking-async/runtimes/rc/src/lib.rs`, which has the identical `SudoBalances`/`Auction` omission pattern).

### Finding Description
`pallet_proxy::do_proxy` (`substrate/frame/proxy/src/lib.rs:994-1026`) installs a call filter on the inner dispatch that specifically re-authorizes nested proxy-management calls using `is_superset`, independent of `filter`: [1](#0-0) 
This means a delegate holding a `NonTransfer` proxy can call `Proxy::add_proxy` (which `NonTransfer::filter` admits, since it fully allows `RuntimeCall::Proxy(..)`) to register a brand-new, independent, top-level proxy of a *different* type for the delegator, as long as `NonTransfer.is_superset(new_type)` returns `true`. The check exists precisely to stop a limited proxy from minting itself a more powerful proxy — but the lattice declared in `is_superset` does not match what `filter` actually permits: [2](#0-1) 
- `SudoBalances::filter` admits `RuntimeCall::Sudo(pallet_sudo::Call::sudo{call: Balances(..)})`, a call `NonTransfer::filter` explicitly denies ("Specifically omitting Sudo pallet").
- `Auction::filter` admits `RuntimeCall::Registrar(..)` unconditionally (all variants, including `swap`), while `NonTransfer::filter` only admits `Registrar::register`/`deregister`/`reserve` and explicitly excludes `swap` ("Specifically omitting Registrar `swap`"). [3](#0-2) 

This is the identical root cause to the already-remediated advisory in this codebase: a lower-privileged, delegated actor (the `NonTransfer` proxy, analogous to Netmaker's "admin") can, through the update/assignment path (`add_proxy`, analogous to Netmaker's "user update" endpoint), grant a higher-privileged role (`SudoBalances`/`Auction`, analogous to "super-admin") to itself or an arbitrary account, because the code that is supposed to check "is the new role no more powerful than mine" (`is_superset`) is inconsistent with the actual permission set (`filter`).

### Impact Explanation
Any account holding only a `NonTransfer` proxy for a delegator can, without further authorization from the delegator:
1. Call `Proxy::add_proxy{ delegate: <attacker-controlled account>, proxy_type: Auction, delay: 0 }` through the existing `NonTransfer` proxy relationship. This succeeds because `is_superset(NonTransfer, Auction) == true`, and the resulting `Proxy::add_proxy` call itself is admitted by `NonTransfer::filter` (full `Proxy(..)` allowlist).
2. The newly created `Auction` proxy entry is a real, independent, top-level entry in `Proxies` storage for the delegator — not limited by the nested-call filter that was active during step 1.
3. Using this new `Auction` proxy directly (`Proxy::proxy` with `force_proxy_type: Auction`), the attacker can now dispatch `Registrar::swap` on behalf of the delegator — a call the delegator's original `NonTransfer` grant deliberately excluded.
4. The analogous path exists for `SudoBalances`, reaching `Sudo::sudo{Balances(..)}`, subject to the delegator's account actually being the configured `sudo` `Key` (this specific sub-case is unverified against Westend's live sudo-key configuration; `Auction`/`Registrar::swap` does not have this caveat and is unconditionally reachable).

This breaks the confidentiality/integrity guarantee that a `NonTransfer` proxy grant limits the delegate strictly to non-transfer, non-privileged actions — the delegate can silently escalate to `Auction`-level (parachain registrar/slot management) capability that the delegator never intended to grant.

### Likelihood Explanation
High for any delegator who has granted (or will grant) a `NonTransfer` proxy on the Westend relay chain — this is one of the most commonly used proxy types (`ProxyType::Any`/`NonTransfer` are the standard "convenience delegate" grants). No special privilege, governance action, or victim cooperation beyond the initial (routine) `add_proxy(NonTransfer)` grant is required from the attacker; the attacker is an ordinary signed account that received a limited delegation.

### Recommendation
Fix the `is_superset` lattice in `polkadot/runtime/westend/src/lib.rs` (and audit `substrate/frame/staking-async/runtimes/rc/src/lib.rs`, which has the same `SudoBalances`/`Auction` vs `NonTransfer` mismatch) so `NonTransfer` is only declared a superset of proxy types whose entire `filter` set is contained in `NonTransfer`'s `filter` set — remove `SudoBalances` and `Auction` from the blanket `(ProxyType::NonTransfer, _) => true` rule, matching the pattern used in the AssetHub Westend fix (`prdoc/pr_12769.prdoc`). Additionally, port the lattice-consistency regression test `proxy_type_superset_relation_matches_call_filters` (`cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2494-2516`) to the Westend relay runtime and to `staking-async` runtimes so this class of bug is caught automatically across all runtimes, not just AssetHub.

### Proof of Concept
Deployment evidence: `pallet_proxy` is wired into the Westend relay runtime with `ProxyType` as configured type [4](#0-3) , and `pallet_sudo`/`Auctions`/`Registrar` pallets are present [5](#0-4) . The `is_superset` gate used by `do_proxy` for nested `add_proxy` calls was confirmed at `substrate/frame/proxy/src/lib.rs:1004-1013`.

I was not able to execute an actual integration test in this session (read-only analysis tools only); no local Rust/FRAME repro was run. The `Registrar::swap` extrinsic's own internal origin/authorization logic (e.g., whether it further requires being the para manager) could not be located/verified in this pass (`paras_registrar` module path not resolved via glob search), so the concrete downstream effect of the `Auction` escalation depends on that pallet's internal checks and should be verified before treating this as fully weaponizable; the `SudoBalances`→`Sudo::sudo` path additionally depends on the delegator being the configured sudo `Key`, which was not confirmed for a live Westend deployment. The core claim — that `is_superset`'s declared lattice does not match `filter`'s actual permission set for `NonTransfer` vs. `SudoBalances`/`Auction` in this specific runtime file, unlike the already-patched AssetHub Westend runtime — is directly supported by the cited source lines.
