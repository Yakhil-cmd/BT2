### Title
`DepositDelegatorRewards` funds can become permanently frozen when a vote account has zero active delegated stake at reward-calculation time - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
SIMD-0123's `DepositDelegatorRewards` instruction lets *any unprivileged signer* transfer lamports into a vote account's balance and increment `pending_delegator_rewards`, a pool meant to be distributed to delegators proportional to stake at the next epoch boundary. This mirrors the reported WETH-staking bug: a reward pool accrues balance from an external, permissionless source before the "index" (here, `total_active_stake`) that gates payout is guaranteed to be non-zero.

### Finding Description
`deposit_delegator_rewards` performs a system transfer into the vote account and unconditionally increments `pending_delegator_rewards` via `add_pending_delegator_rewards`, with no check that the vote account currently has any active delegated stake: [1](#0-0) 

At epoch-boundary reward calculation, `calculate_block_reward` distributes `pending_delegator_rewards` to each stake account proportional to `stake / total_active_stake`, where `total_active_stake` comes from the `reward_epoch_delegated_stakes` snapshot for that vote account in the rewarded epoch: [2](#0-1) 

Critically, when `total_active_stake == 0` (no delegators exist yet, or the vote account currently has no active stake — e.g. a freshly created vote account, or one whose stake fully deactivated), the function returns `0` for every candidate stake account, so **no stake reward is derived from `pending_delegator_rewards` for that epoch**. This is exactly the reported pattern: an externally-fed reward balance (`_diff`/`balanceOf` in the Beedle report; `pending_delegator_rewards` here) accumulates while the proportional-payout denominator (`totalSupply` there; `total_active_stake` here) is zero, so contributions made during that window are never captured by the payout formula.

Compounding this, I found no code path that clears or reduces `pending_delegator_rewards` other than proportional distribution during `calculate_block_reward`/reward distribution. The `Withdraw` instruction is explicitly blocked from withdrawing lamports reserved for `pending_delegator_rewards`: [3](#0-2) 

Since `pending_delegator_rewards` is only ever incremented by `add_pending_delegator_rewards` (checked_add, no corresponding decrement path was found outside proportional distribution) and the vote account cannot withdraw lamports below that reserved amount, any deposit made while `total_active_stake` is zero is not converted into a distributable per-stake reward at that epoch boundary and the lamports remain locked in the vote account, unclaimable by the authorized withdrawer and never picked up by `calculate_block_reward`'s payout formula until (if ever) stake becomes active again — and even then, only *future* stake benefits, since the formula recomputes the split freshly each epoch based on current `stake`/`total_active_stake`, not a per-delegator observed baseline.

### Impact Explanation
Lamports deposited via the permissionless `DepositDelegatorRewards` instruction to a vote account with zero currently-active delegated stake are not captured by the block-reward distribution formula for that epoch and cannot be withdrawn (the `Withdraw` instruction reserves them). This constitutes a permanently/indefinitely frozen-funds condition analogous to the cited report — deposited value becomes unattributable and stuck in on-chain state, unavailable to either the depositor, the vote account's authorized withdrawer, or delegators.

### Likelihood Explanation
`DepositDelegatorRewards` requires only a signature from the source account transferring lamports and a valid V4 vote account — it is fully permissionless and can be triggered by any unprivileged user, including accidentally (e.g., automated commission/reward tooling depositing to a vote account before its stake has activated, or after full deactivation). Newly created vote accounts naturally start with zero active stake, making the zero-`total_active_stake` window a routine, not edge-case, occurrence.

### Recommendation
Either (a) reject `DepositDelegatorRewards` when the target vote account currently has zero effective/activating delegated stake, or (b) change `calculate_block_reward`/the epoch reward distribution to roll over undistributed `pending_delegator_rewards` correctly rather than silently returning `0` per stake account while leaving the vote account's `pending_delegator_rewards` field unchanged and lamports locked — ensuring the reserved amount is either distributable once stake exists or refundable to the original depositor.

### Proof of Concept
1. Create a new SIMD-0185 V4 vote account with no delegated stake yet (`total_active_stake` for it in `reward_epoch_delegated_stakes` is `0`).
2. Any signer calls `VoteInstruction::DepositDelegatorRewards { deposit: N }` targeting this vote account — succeeds per `deposit_delegator_rewards`, incrementing `pending_delegator_rewards` to `N` and transferring `N` lamports into the vote account.
3. At the next epoch boundary, `calculate_stake_rewards_and_commissions` calls `calculate_block_reward` for any stake delegated to this vote account; since `total_active_stake == 0` at the time snapshotted for the rewarded epoch, the function returns `0` — no stake reward is paid out of the `N` lamports.
4. Attempt to `Withdraw` the `N` lamports from the vote account: fails/limited, since `Withdraw` disallows withdrawing below the reserved `pending_delegator_rewards` amount (`programs/vote/src/vote_processor.rs` test `test_withdraw_pending_delegator_rewards`).
5. Result: the `N` lamports remain locked in the vote account, uncounted by the payout formula and unwithdrawable, with no on-chain path identified to reclaim or redistribute them.

Note: I was not able to fully trace whether a subsequent epoch (once `total_active_stake` becomes non-zero again) would correctly redistribute the *carried-forward* `pending_delegator_rewards`, or whether the formula's per-epoch recomputation means the originally "orphaned" contribution is diluted/never specifically attributed once new stake activates — this nuance would benefit from a Devin session with full repo/test access to trace `pending_delegator_rewards` end-to-end across multiple epoch-reward cycles.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
