### Title
`X-Shipit-User` header lets an authenticated `ApiClient` token impersonate an arbitrary `Shipit::User` unbound to any credential - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
The ERC4626Oracle bug is a decimals-binding mismatch: the oracle trusts a self-reported field (`token.decimals()`) as if it were the value that was actually validated (the underlying asset's real decimals), producing a wrong price. The analogous binding break in this engine is in `Shipit::Api::BaseController`: the request is authenticated via a signed `ApiClient` token (`ApiClient.authenticate`), but the `User` identity that Shipit subsequently *acts on* (`current_user`) is taken from the unsigned, client-supplied `X-Shipit-User` header, which is never covered by any credential or signature check.

### Finding Description
`authenticate_api_client` verifies only the bearer token against `ApiClient.message_verifier`, establishing `@current_api_client`: [1](#0-0) 

Separately, `current_user` is derived purely from the `X-Shipit-User` request header, matched case-insensitively against the `User` table, with no signature, no correlation to the authenticated `ApiClient`, and no restriction to users associated with that client: [2](#0-1) 

This is exactly the "authenticated principal A vs. acted-upon identity B" binding break the rules describe (GitHub identity vs. `User` bound to the session): the token authorizes *operations* (`read:stack`, `write:stack`, `deploy:stack`, etc. via `ApiClient#check_permissions!`), but the *actor* recorded/used for those operations is an attacker-chosen header value that was never authenticated. Any holder of a valid `ApiClient` token (even one scoped to a single stack with minimal permissions) can set `X-Shipit-User` to the login of any existing Shipit user — including privileged users — and have actions attributed to, or performed as, that user.

### Impact Explanation
`current_user` is consumed by state-changing controllers that use it as the actor for privileged operations — e.g. `Api::LocksController`, `Api::TasksController`, `Api::DeploysController`, `Api::RollbacksController`, `Api::ReleaseStatusesController`, and `Api::MergeRequestsController` all reference `current_user`. Using it as the recorded/effective author of a deploy, lock, or task run means an attacker with only a narrowly-scoped API token can impersonate any registered user (e.g. an admin or a bot with elevated trust) for auditing, authorization, or attribution purposes tied to that user — an escalation into the identity model that Shipit's permission and audit trail rely on. This aligns with a High-severity escalation (unauthorized action attribution / identity spoofing) rather than a full "unauthorized deploy" since the underlying `ApiClient.check_permissions!` scope check on operation/stack still applies — the break is specifically in the identity binding, not the permission-scope binding.

### Likelihood Explanation
Any party who has been issued an `ApiClient` token (a legitimate but potentially low-privilege client) can trivially exploit this by adding a single HTTP header to any API request — no additional secret, signature, or GitHub credential is required, and the header is read unconditionally whenever `current_user` is invoked in non-disabled-auth mode.

### Recommendation
Do not derive `current_user` from an arbitrary unauthenticated header. Either remove the `X-Shipit-User` impersonation path entirely for token-authenticated requests, or bind it cryptographically/contractually to the `ApiClient` (e.g., only allow it when the `ApiClient` itself is scoped/verified to act on behalf of that specific `creator`), and audit all controllers consuming `current_user` to ensure the identity is provably tied to the authenticated credential.

### Proof of Concept
1. Obtain any valid `ApiClient` token (e.g., one created with only `read:stack` or `deploy:stack` permission for a single stack).
2. Send an API request (e.g. to `Api::LocksController#create` or `Api::TasksController#create`) with header `X-Shipit-User: <victim_or_admin_login>`.
3. `identify_user` resolves `current_user` to that arbitrary `User` record without any verification: [3](#0-2) 
4. The resulting action (lock reason/author, task trigger author, etc.) is now attributed to/executed as the impersonated user, even though only the token — not that user's identity — was ever authenticated.

      def authenticate_api_client
        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
        return if @current_api_client

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end
