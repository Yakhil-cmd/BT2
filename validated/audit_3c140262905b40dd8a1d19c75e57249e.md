### Title
`initialize_with_permission` accepts an arbitrary, unverified `creator` account as `pool_creator`, permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The external report describes Mimo's `MIMOProxyRegistry`/`MIMOProxyFactory` failing to actually guarantee the "one owner - one proxy" invariant because critical ownership fields could be set/desynchronized without any validation of the real controlling party, and `deployFor()` let anyone assign a proxy "owner" without checks. The analogous flaw in this codebase is that `initialize_with_permission` records an arbitrary, completely unconstrained `creator` account as the immutable `pool_creator` for the pool, with no requirement that this account be a signer or otherwise prove control over the address.

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as an `UncheckedAccount` with no signer requirement, no `address =` constraint tying it to `payer`, and no relationship to the `permission` PDA (which is keyed only by `payer.key()`): [1](#0-0) [2](#0-1) 

This unchecked `creator.key()` is then written directly into `PoolState.pool_creator` via `pool_state.initialize(...)`, which becomes the immutable, authoritative "owner" record for creator-fee collection: [3](#0-2) [4](#0-3) 

Once set, `pool_creator` can never be changed (there is no ownership-transfer instruction), and it is the sole authority used everywhere creator fees are gated:
- `collect_creator_fee` requires `creator` to be a **Signer** matching `pool_state.pool_creator`: [5](#0-4) 
- `collect_creator_fee_permissionless` lets anyone trigger collection, but always routes the funds to an ATA owned by the fixed `pool_creator` address: [6](#0-5) [7](#0-6) 

Because `creator` is never validated as a signer at pool-creation time, a payer holding a valid `Permission` PDA (the only gate on this instruction) can supply any arbitrary pubkey as `creator` — including an address for which no private key is known/controlled (e.g. a randomly generated pubkey, a PDA of an unrelated program, or an address that is off the ed25519 curve). Just like the Mimo Registry recording an owner without verifying real control, this program records a `pool_creator` without ever confirming the designated party can actually sign for or claim the role.

### Impact Explanation
Accumulated creator fees (`pool_state.creator_fees_token_0` / `creator_fees_token_1`) are subtracted from the pool's usable vault balance in `vault_amount_without_fee`: [8](#0-7) 

If `pool_creator` is an address nobody controls, these accrued fees can never be collected by `collect_creator_fee` (requires the unreachable signer) and `collect_creator_fee_permissionless` only relocates them into an ATA owned by that same unreachable address — the funds are permanently locked out of circulation, a real, ongoing loss for the pool ecosystem (the LP/vault accounting permanently reserves and eventually strands these tokens). This satisfies the "permanent freezing of user or LP funds" impact bar, reachable via a single `initialize_with_permission` transaction with attacker-chosen `creator` data.

### Likelihood Explanation
Likelihood is bounded by the fact that `initialize_with_permission` can only be called by a `payer` who already holds a `Permission` account (admin-granted), so this is not callable by a fully unprivileged, arbitrary wallet. However, within the class of accounts allowed to create permissioned pools, this is trivially and always reachable — no special privileges beyond the `Permission` PDA are needed to choose an unrelated/uncontrolled `creator` value, and doing so requires no unusual conditions or races.

### Recommendation
Require `creator` to be a `Signer` in `InitializeWithPermission` (mirroring `Initialize`, where `creator` is `Signer<'info>`), or otherwise cryptographically prove that the designated `pool_creator` controls the address before it is permanently recorded in `PoolState`. Alternatively, add an explicit acceptance/claim step (analogous to Mimo's post-fix `claimOwnership`) so a two-phase handshake confirms the intended party can actually sign before fee-collection rights are locked to that address forever.

### Proof of Concept
1. Admin authorizes `payerA` by calling `create_permission_pda` for `payerA` (creating a `Permission` PDA keyed by `payerA`).
2. `payerA` calls `initialize_with_permission`, passing an attacker-chosen, unrelated pubkey `X` (for which no keypair is known) as the `creator` account — `X` is never required to sign.
3. `pool_state.pool_creator` is set to `X` in `PoolState::initialize` (`initialize_with_permission.rs:357-372`, `pool.rs:134-152`).
4. Swaps against the pool accrue `creator_fees_token_0/1` in `PoolState` (per `creator_fee_on`/`enable_creator_fee`).
5. Nobody can call `collect_creator_fee` (requires `X` to sign) and `collect_creator_fee_permissionless` only moves the fees into an ATA owned by `X`, which nobody can ever withdraw from — the funds are permanently frozen.
