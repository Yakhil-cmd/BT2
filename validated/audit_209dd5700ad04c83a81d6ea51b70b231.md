### Title
Merkle Tree Leaf/Node Hash Collision Enables Forged Inclusion Proofs - ([File: merkle.js])

### Summary
`merkle.js` computes both leaf hashes and internal-node hashes with the *same* undifferentiated hash function (`hash(x) = sha256(x)`), with no domain-separation prefix distinguishing "this is a leaf" from "this is an internal node." This is the exact bug class described in the external report — an ambiguous, under-specified hash preimage format that lets an attacker craft an input that is accepted as something it was never meant to represent. Here, an attacker can supply the raw concatenation of two known sibling hashes as a fake "leaf element," which hashes to the same value as the internal node computed from those two children, letting a forged Merkle inclusion proof pass verification for data that was never actually a member of the original set.

### Finding Description
`getMerkleRoot`/`getMerkleProof` hash leaves with `hash(element)` and combine internal nodes with `hash(left + right)`, both using the identical `hash()` function: [1](#0-0) 

`verifyMerkleProof` reproduces this same ambiguity when checking a proof — it hashes the caller-supplied `element` once, then repeatedly combines it with siblings using the same hash function, with no leaf/node domain tag: [2](#0-1) 

The code even flags this itself: `// Node-as-Leaf issue might matter in some cases`, at the top of `verifyMerkleProof`. [3](#0-2) 

Because leaves and internal nodes share one hash domain, if an attacker knows any two adjacent sibling hashes `h1, h2` in a published tree (siblings are revealed as plaintext strings in any legitimate proof, e.g. those posted via a data feed or shared to claimants), they can set `element = h1 + h2`. Then `hash(element)` equals exactly the internal node hash that the tree would have computed one level up from `h1`/`h2`. By supplying a proof whose `index`/`siblings` correspond to that internal node's position and continuing with the tree's remaining higher-level siblings, `verifyMerkleProof` will recompute the same root — even though `h1+h2` (the forged "element") was never one of the original `arrElements` fed into `getMerkleRoot`/`getMerkleProof`. This produces a fully valid, tree-root-matching proof for an unauthorized/fabricated element.

This primitive is exposed to unprivileged users in two reachable paths:
1. Address/asset spending condition `'in merkle'`, which lets a definition require a Merkle-root match against a data-feed oracle value, gated by a caller-supplied proof passed as an authentifier: [4](#0-3) 
2. The AA (Autonomous Agent) formula function `is_valid_merkle_proof(element, proof)`, callable directly from oscript/AA code using attacker/trigger-supplied `trigger.data` fields as `element` and `proof`: [5](#0-4) 

Both consumers pass raw user/trigger input straight into `merkle.verifyMerkleProof` without any leaf/node domain check, so the forgery described above is directly reachable by any address owner supplying an authentifier, or any AA trigger sender supplying `trigger.data`.

### Impact Explanation
Address definitions and AAs that use `in merkle` / `is_valid_merkle_proof` to gate fund release on membership in an oracle-published whitelist/allocation tree (a common pattern for airdrops, escrow releases, or reward/whitelist claims) can be tricked into accepting a forged "element" that was never part of the original data set. This is a genuine authorization bypass on a spending/AA condition, leading to unauthorized withdrawal of funds from a shared address or AA, i.e., concrete unauthorized spending / AA fund loss, matching the High-severity bar (funds released to a party never authorized in the underlying data set).

### Likelihood Explanation
Exploitation requires only observing sibling hashes from any single legitimate Merkle proof for the target tree — these are plaintext, non-secret, and routinely published (e.g., as a serialized proof shared with a legitimate claimant, or as part of a public data-feed value). No private keys, node privileges, or breaking of SHA-256 are required; only ordinary "malicious normal user abusing valid protocol flow" access is needed, which is the default reachable-attacker profile for this analysis.

### Recommendation
Introduce domain separation between leaf and internal-node hashing, e.g. prefix leaves with a distinct byte/tag (`hash("0" + element)`) and internal-node combination with another tag (`hash("1" + left + right)`), as done in RFC 6962 Certificate Transparency Merkle trees. Apply this consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js` so that no attacker-supplied string can ever be mistaken for (or collide with) an internal node's pre-image.

### Proof of Concept
1. Build a tree with `merkle.getMerkleRoot([a, b, c, d])`. Internal node `N = hash(hash(a) + hash(b))` is computed at the first combining level.
2. Obtain a legitimate proof for `a` (or `b`) — it reveals `hash(b)` (or `hash(a)`) as a sibling, and the remaining path to `root`.
3. From this, an attacker who additionally learns `hash(a)` and `hash(b)` (both are exposed in any single genuine proof for either leaf) sets `forged_element = hash(a) + hash(b)`.
4. Craft `forged_proof = { index: N's index at that level, siblings: [ the remaining siblings above N's level from the original tree ], root: root }`.
5. Call `merkle.verifyMerkleProof(forged_element, forged_proof)` (directly, or via `is_valid_merkle_proof(forged_element, forged_proof)` in an AA trigger, or as an `'in merkle'` authentifier in an address definition) — verification succeeds and returns `true`, even though `forged_element` (`hash(a)+hash(b)` as a raw string) was never one of the original elements `a, b, c, d` fed into the tree.
6. If an AA or address definition uses this to gate a payout to "whoever proves membership of `element = trigger.data.claim_id` in the whitelist root," the attacker satisfies the condition with a fabricated `claim_id` and drains funds intended for legitimate whitelist members.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
