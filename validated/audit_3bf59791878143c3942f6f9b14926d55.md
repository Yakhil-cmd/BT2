### Title
Webhook signature verification keys on `repository.owner.login`, but every event handler acts on the independently-attacker-controlled `repository.full_name` / `organization.login` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a direct analog of the `insertValidatorSet()` bug class: the code verifies (authenticates) one field of an inbound structure but then acts on a *different* field of the same structure that was never bound to that verification. In Shipit, `WebhooksController#verify_signature` selects the `GitHubApp`/HMAC secret to check the request against using `repository_owner` (derived from `payload.dig('repository','owner','login')`, falling back to `payload.dig('organization','login')`), but the event handlers that actually mutate state (`Handler#repository_name`, used by `PushHandler`, `PullRequest::*Handler`, etc.) look up the target `Repository`/`Stack` using a **separate, unvalidated** field: `payload.dig('repository','full_name')`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) 
using `repository_owner`: [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the `GitHubApp` config (and thus the `webhook_secret`) keyed by that owner login, and HMAC-verifies the raw body against it. This only proves "the sender knows organization X's webhook secret" — it does not prove anything about which repository the payload's `full_name` claims to represent.

Every default handler, however, resolves the repository to write to via `Handler#repository_name`, an entirely separate JSON path: [3](#0-2) 

For example `PushHandler#process` finds stacks by `repository_name` (i.e. `repository.full_name`) and calls `stack.sync_github`: [4](#0-3) 

Nothing in the request pipeline asserts `repository.full_name.split('/').first == repository.owner.login` (the field used for signature selection) or `== organization.login`. An attacker who legitimately controls (or has been granted) a GitHub App installation/webhook secret for **their own** organization, `attacker-org`, can send a webhook whose JSON body sets:
- `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against `attacker-org`'s real secret, which the attacker holds/can compute), and
- `repository.full_name = "victim-org/some-tracked-repo"` (an entirely different, Shipit-tracked repository/org)

`verify_signature` passes because the HMAC matches `attacker-org`'s secret and the *signature-checked* field (`repository.owner.login`) is internally consistent with that secret. The handler then acts on `repository.full_name`, which points at `victim-org`'s stack, with attacker-supplied `after` sha, `ref`, or (for other events) status/PR/team data.

This exactly mirrors the reported bug class: the value that is checked (validator power/pubkey in the original report; `repository.owner.login` here) is not the same value that is subsequently acted upon (insertion into the table; `repository.full_name`/`organization.login` used for writes here), so a party who is legitimately authorized/verified with respect to field A can smuggle in an arbitrary value in field B that the write path actually trusts.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." Concretely, an attacker holding a webhook secret for one org can:
- Force `GithubSyncJob`/`PushHandler` to trigger `stack.sync_github` for a *different* org's stack with an attacker-chosen `expected_head_sha`, causing spurious GitHub sync/commit-append flows against a repository the attacker does not control — this repository lookup and sync then uses `stack.github_api`/`Shipit.github(organization: <real owner>)`, so it still needs the real credentials for the target org to fetch data. This limits (but does not eliminate) the write impact for `PushHandler`, since actual commit content still comes from GitHub via `fetch_missing_commits`, not directly from the payload.
- For `MembershipHandler`, `params.organization.login` is used directly to set `team.organization`, and `Team.find_or_create_by!(github_id: ...)`/`team.add_member` mutate Team/Membership records; but here the `organization.login` field itself is what is used both to choose the webhook secret (via the `repository_owner` fallback) and to write — so this particular handler is actually consistent, unlike `PushHandler`/`PullRequest::*` handlers, which diverge to `repository.full_name`. This is a nuance and reduces confidence that this generalizes into an immediately game-changing write across all handlers.
- `StatusHandler` matches on `Commit.where(sha: params.sha)` globally (not scoped by stack/org at all), so any org holding any valid webhook secret can inject a `commit_status` for a commit sha belonging to a repo they don't own, as long as that sha coincidentally matches a commit tracked in any Shipit stack — this is a lower-severity data integrity issue (spoofed CI status), not a direct RCE/credential exposure/unauthorized deploy.

I could not fully verify, within the available time, whether any of these mismatches escalate to the report's required "Critical/High" bar (RCE, auth bypass, `GITHUB_TOKEN` exfiltration, cross-repo writes causing unauthorized deploy/merge/rollback, or SSRF with app credentials). The clearest concrete cross-tenant write is limited to triggering a `GithubSyncJob`/status write against another org's tracked repo/commit, which is a data-integrity/spoofing issue rather than a proven deploy, merge, or credential-exfiltration path.

### Likelihood Explanation
Exploitability requires the attacker to already hold a legitimate webhook secret for *some* organization configured in this Shipit instance (i.e., they administer a GitHub App installation pointed at this Shipit deployment for their own org/repo). That is a real but non-trivial precondition — it is not "no credential at all," but it is also not a privileged Shipit account, `ApiClient` token, or GitHub write access to the *victim* repository, so it does cross a meaningful trust boundary (one tenant's webhook credentials should not let it act on another tenant's tracked repository).

### Recommendation
Bind webhook signature verification to the exact repository/organization that the handler will act on:
- In `WebhooksController#verify_signature`, additionally assert that `payload.dig('repository','full_name')`'s owner segment (or `payload.dig('organization','login')` for org-level events) matches the `repository_owner` used to select the webhook secret, rejecting (422) on mismatch.
- In `Handler#repository_name`/each handler, cross-check the resolved repository's owner against the verified `repository_owner`/`organization.login` before performing any write, or thread the verified owner through to the handler and enforce it there rather than trusting `full_name` independently.
- Scope `StatusHandler`'s `Commit.where(sha: ...)` lookup by the verified repository/stack rather than a global sha search.

### Proof of Concept
Conceptual PoC (illustrating the field mismatch, not full HTTP tooling since I lack execution access in ask-only mode):
1. Register/hold the real `webhook_secret` for `attacker-org` in this Shipit instance's `github.yml`.
2. Craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/tracked-repo"
  }
}
```
3. Sign the raw body with `attacker-org`'s webhook secret and send it with header `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner => "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC matches → request is accepted.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/tracked-repo")` (from `Handler#repository_name`, reading `repository.full_name`), entirely bypassing any relationship to `attacker-org`, and enqueues a sync/`GithubSyncJob` against `victim-org`'s stack with the attacker's chosen `after` sha.
