### Title
Webhook signature verification selects the GitHub App config from unauthenticated payload fields, letting an attacker impersonate any organization that has no `webhook_secret` configured and forge events for arbitrary repositories/stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* per-organization GitHub App secret to verify the incoming webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the still-unverified JSON body, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

This is the same class of bug as the `Repository._removeContract()` finding: a value is used to make a security decision (which index / which org "owns" this event) even though that value comes from state the caller controls and hasn't been validated yet. In Shipit's multi-org mode (`Shipit.github_app_config`), each organization can have its own, independently-configured `webhook_secret`, and that field is explicitly documented and tested as optional (blank secret allowed). [3](#0-2) [4](#0-3) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank for the selected org: [5](#0-4) 

### Finding Description
The binding that should hold is: *organization that authenticated the webhook == organization that owns the repository the webhook event is applied to*. The controller breaks this equality:

1. `repository_owner` is derived from the raw, unauthenticated JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`).
2. `Shipit.github(organization: repository_owner)` looks up that organization's `GithubApp` config and calls `verify_webhook_signature`.
3. If the organization selected via that attacker-supplied field happens to have `webhook_secret` unset (a documented, tested, supported configuration — see `secrets_double_github_app.yml`'s `OrgTwo` with `webhook_secret: # nil`), verification trivially returns `true` for **any** payload content, with **no HMAC check performed at all**.
4. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then processes the same JSON body's `repository`/`sha`/`branches` fields to find and mutate the actual `Stack`/`Commit`/`Repository` records — objects that belong to whatever organization the attacker chose to put in the payload body, not necessarily the "authenticating" organization used in step 2.

Because `repository_owner` and the fields the handlers act on (commit sha, branch, repository full name) are both read from the same attacker-controlled JSON object *before* any cryptographic check ties them together, an attacker only needs to know that **one** configured organization in a multi-org Shipit deployment has no webhook secret. They can then set `repository.owner.login` (or `organization.login`) to that unsecured org for the purpose of passing `verify_signature`, while shaping the rest of the payload (e.g. `repository.full_name`, `sha`, `branches`) to target a stack belonging to a completely different, secret-protected organization tracked by the same Shipit instance.

### Impact Explanation
This allows an unprivileged attacker (anyone who can reach the public `/webhooks` endpoint) to forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events for repositories/stacks they do not control, as long as any other org on the instance is configured without a webhook secret. Depending on the target stack's configuration this enables:
- Forged `push` events causing `GithubSyncJob` to sync arbitrary refs into a stack not owned by the attacker (cross-repository/cross-stack writes).
- Forged `status`/`check_suite` events flipping commit status to "success", potentially unblocking `continuous_deployment` and triggering an unauthorized deploy.
- Forged `membership` events creating arbitrary `Team`/`User` records.

This matches the "Critical — cross-repository writes / unauthorized deploy" and "High — unauthenticated read/manipulation of stack state" categories in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (`Shipit.github_app_config` / `github_organizations`) and that at least one of them has an unset `webhook_secret` — a configuration explicitly documented as valid ("Webhook secret (optional)") and directly exercised in the engine's own multi-app secrets fixture. No credentials, session, or repository access are required from the attacker; only network access to the public `/webhooks` route.

### Recommendation
Do not select the verification organization from unauthenticated payload content when other, already-verified organizations exist on the same instance. Options:
- Verify the signature against **all** configured organizations' secrets and require at least one non-blank secret to match, rather than trusting attacker-supplied `repository.owner.login`/`organization.login` to pick the verifier.
- After signature verification succeeds for a given organization, cross-check that the `repository.owner.login` used for verification actually matches the `Repository`/`Stack` being mutated by the handler, rejecting the event otherwise.
- Disallow (or warn loudly) on blank `webhook_secret` for any organization in multi-org mode, since it undermines every other organization's protection at this endpoint.

### Proof of Concept
1. Deploy Shipit in multi-org mode with two orgs configured, e.g. per `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (has `webhook_secret`) and `OrgTwo` (`webhook_secret: nil`). [4](#0-3) 
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "OrgTwo" },
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/protected-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `repository_owner` to `"OrgTwo"` via `params.dig('repository', 'owner', 'login')`, calls `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is blank. [1](#0-0) [5](#0-4) 
4. The request proceeds to `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }`, which processes `full_name: "OrgOne/protected-repo"` and enqueues a sync job against `OrgOne`'s stack — despite `OrgOne` requiring a real webhook secret that the attacker never supplied or knew. [6](#0-5) 

Note: I was unable to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` and `status_handler.rb` in this session (tool errors prevented reading them) to confirm the exact field(s) used to resolve the target `Repository`/`Stack`; this should be verified directly before treating the PoC payload shape as final, though the controller-level signature-selection flaw itself is confirmed from `webhooks_controller.rb` and `github_app.rb`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
