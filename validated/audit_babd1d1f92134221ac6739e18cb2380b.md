### Title
Arbitrary environment variable injection into deploy-host `Command`/`PTY.spawn` via unprivileged pull-request label names (`allow_with_label`) - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment key with the value `"true"` into the stack's environment hash, with no allowlist of permitted key names. That environment is merged into `TaskCommands#env`, passed into `Command.new(..., env:)`, and ultimately merged into the process environment handed to `PTY.spawn` in `Command#start`, so a fork author can set arbitrary env var names (e.g. `PROMPT_COMMAND`, `BASH_ENV`, `ENV`, `RUBYOPT`, `GIT_SSH_COMMAND`) that influence commands run during the `dependencies.override`/install steps on the Shipit deploy host.

### Finding Description
The broken binding: the set of environment variable **names** reaching `PTY.spawn` for a `ReviewStack`'s deploy/dependency commands should equal `Stack#env.keys ∪ TaskCommands#env-defined keys ∪ allowlisted task env keys`, but in practice it equals that set **plus any uppercased pull-request label name the fork PR author chooses**, because `ReviewStack#env` applies no allowlist: [1](#0-0) 

This differs from `Stack#trigger_task`/`build_deploy`, where user-supplied `env` overrides are filtered through `definition.filter_envs` / `filter_deploy_envs` before being stored on the task: [2](#0-1) 

That filtering only applies to `@task.env` (explicit user-triggered overrides), not to `@stack.env`, which `TaskCommands#env` merges in unconditionally and unfiltered: [3](#0-2) 

The dependency/install step commands are built directly from this same `env`: [4](#0-3) 

`Command#initialize` stores this hash as `@env`, and `Command#unbundled_env` merges it directly over `BASE_ENV`/`PATH` with no key restriction, right before it is fed to `PTY.spawn` in `Command#start`: [5](#0-4) [6](#0-5) 

Exploit flow: an unprivileged GitHub user opens a fork PR against a repository whose `provisioning_behavior` is `allow_with_label` (so review stacks get created/deployed for fork PRs), and adds a label literally named `prompt_command` (case-insensitive; GitHub label names can be freely chosen by the PR author on their own fork/label set, and label names are captured verbatim from webhook payloads by `LabelCapturingHandler#capture_labels`). When the review stack's dependency-install phase runs, `TaskCommands#install_dependencies` builds `Command` objects whose `env` includes `PROMPT_COMMAND=true` sourced straight from that label, and that value reaches the process environment passed to `PTY.spawn`.

Why guards don't stop it: `verify_signature`/webhook auth only ensures the payload actually came from GitHub for that repo — it does not restrict what label names a PR author can choose on their own PR. `EnvironmentVariables#permit`/`filter_task_envs`/`filter_deploy_envs` restrict explicit user-submitted task env overrides but are never applied to `Stack#env`/`ReviewStack#env`. There is no allowlist of label names anywhere in `ReviewStack#env`.

### Impact Explanation
Any environment variable name (not just `PROMPT_COMMAND`) is injectable into the environment of every command Shipit runs for a review stack on the deploy host, including the `dependencies.override` install step and later deploy/rollback steps, since they all reuse `@stack.env`. Depending on what the `shipit.yml`/underlying tools do (bundler, rake, git, shell scripts), attacker-controlled variables such as `BASH_ENV`, `ENV`, `RUBYOPT`, `GIT_SSH_COMMAND`, or shell-prompt-related variables can be leveraged to execute attacker-chosen commands on the Shipit host as part of routine step execution — this lands in the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category. This is repeatable by any fork PR author against any repository configured with `allow_with_label` (or any provisioning behavior that provisions review stacks for unprivileged forks), and is not limited to a single repository — every review-stack-enabled repo using this provisioning mode is affected.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that provisions/deploys stacks for fork PRs (`allow_with_label` per the question, requiring the PR to carry a specific label — but the label name itself, not just its presence, is attacker-controlled text). The attacker only needs push access to their own fork and the ability to label their own PR (self-service on GitHub, no Shipit privileges needed). Cost is trivial — creating a label and opening a PR. It is fully repeatable and requires no secrets, sessions, or maintainer approval.

### Recommendation
Remove `ReviewStack#env`'s unrestricted label-to-env merge, or restrict it to a strict allowlist of safe, prefixed keys (e.g. only `LABEL_<name>` style keys that can never collide with security-sensitive variable names) and reject/skip any label name colliding with reserved/sensitive environment variable names (`PATH`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, etc.). Apply the same `filter_task_envs`/`EnvironmentVariables#permit`-style filtering used for task env overrides to this label-derived hash before it is merged into `Stack#env`.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`):
1. Build a `ReviewStack` with an associated `pull_request` whose `labels` include the string `"prompt_command"`.
2. Assert `review_stack.env["PROMPT_COMMAND"] == "true"` (demonstrates `ReviewStack#env` has no allowlist).
3. Build a `TaskCommands` for a task on that stack and call `install_dependencies`; for each returned `Command`, assert `command.env["PROMPT_COMMAND"] == "true"`.
4. Assert `command.unbundled_env["PROMPT_COMMAND"] == "true"`, showing the label-derived value reaches the exact hash passed to `PTY.spawn` in `Command#start`.
5. The binding under test: expected `Command#unbundled_env.keys ⊆ {system/env keys defined by Shipit code}` vs. actual `Command#unbundled_env.keys ⊇ {"PROMPT_COMMAND"}` sourced from an attacker-chosen PR label — the two sides diverge, proving the vulnerability.

      end

    end
