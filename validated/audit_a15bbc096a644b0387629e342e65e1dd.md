### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository actually mutated is taken from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
Shipit supports hosting multiple GitHub Apps/organizations, each with its own `webhook_secret` [1](#0-0) . When a webhook is received, `WebhooksController#verify_signature` picks *which* organization's secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, then verifies the signature using that organization's `Shipit.github(organization: repository_owner)` app [2](#0-1) [3](#0-2) . Once the signature check passes, every event handler resolves the target repository/stack using a *different*, independent field: `payload.dig('repository', 'full_name')` [4](#0-3) , e.g. `PushHandler#process` triggers `stack.sync_github` for every matching stack [5](#0-4) .

### Finding Description
The binding that should hold is:
`organization that authenticated the signature == organization that owns the repository being written to`

Instead the engine computes:
- LHS (what is cryptographically verified): the org selected via `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, whose `webhook_secret` is used to check `X-Hub-Signature` [6](#0-5) .
- RHS (what is actually acted upon): `payload.dig('repository', 'full_name')`, used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) to look up `Repository`/`Stack` records via `Repository.from_github_repo_name` [4](#0-3) .

These two JSON fields (`repository.owner.login` and `repository.full_name`) are never checked for consistency with each other, and both are entirely attacker-controlled body content, only the raw byte string as a whole is HMAC-signed - not the semantic linkage between "who authorized this" and "what this event claims to be about" at the org level. Since Shipit can be configured to serve multiple organizations, each with its own independently-known `webhook_secret` [7](#0-6) , an actor who legitimately administers (or has compromised) Org A's GitHub App/webhook config knows Org A's `webhook_secret` and can compute a valid HMAC for any payload of their choosing. By setting `repository.owner.login` (and/or `organization.login`) to `"OrgA"` while setting `repository.full_name` to `"OrgB/victim-repo"` (a stack hosted under a completely different, unrelated organization also configured on the same Shipit instance), the request passes `verify_signature` (because it is checked against OrgA's secret, which the attacker knows) and then is routed to and executed against OrgB's stack.

### Impact Explanation
This lets an attacker with legitimate control of one onboarded organization's webhook secret trigger deploy-relevant state changes on stacks belonging to a different organization it has no authorization over, e.g. forcing `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` for `OrgB` stacks [5](#0-4) , or manipulating `StatusHandler`/`CheckSuiteHandler` state which gates whether a commit is deployable, and `PullRequest` handlers that create/lock merge requests across arbitrary tracked repositories. This is a cross-organization/cross-repository write achieved purely by crossing the trust boundary between "which org's secret validated this webhook" and "which repository the payload claims to target," matching the required "cross-repository writes" impact bar.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control (or have compromised) at least one organization's GitHub App/webhook configuration already onboarded to the shared Shipit instance - this is exactly the kind of unprivileged-relative-to-other-tenants actor the rules target (an org boundary crossing, not a Shipit session/API token). Multi-organization hosting is an explicitly supported and tested configuration in this engine [8](#0-7) , so the precondition is realistic for any Shipit deployment serving more than one GitHub organization.

### Recommendation
Bind the signature verification to the same repository identity the handlers act on, not an independently-controlled field:
- Verify the webhook signature using the organization/app resolved from `repository.full_name`'s owner segment (or from a server-side lookup of the `Repository` record and its known parent app/org), rather than trusting the payload's `repository.owner.login`/`organization.login` in isolation.
- Additionally, after signature verification, assert that the authenticated organization matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
3. `OrgB` owns a Shipit-tracked stack, e.g. `OrgB/victim-repo`.
4. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
5. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)`.
6. `WebhooksController#verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully [6](#0-5) .
7. `PushHandler` is invoked with the full payload; `Handler#repository_name` reads `payload.dig('repository','full_name')` → `"OrgB/victim-repo"`, resolving `OrgB`'s stack and calling `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` [4](#0-3) [5](#0-4) , even though the signature was never verified against `OrgB`'s secret.
