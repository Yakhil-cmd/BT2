### Title
Cross-repository forged CI status via unscoped `Commit.where(sha:)` lookup, persisted permanently by `Commit#refresh_statuses!` - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/commit.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no scoping to the repository that sent the webhook, unlike every other handler (`PushHandler`, `PullRequest::*Handler`) which resolve `stacks`/`repository` from `payload['repository']['full_name']` before acting. Combined with `Commit#refresh_statuses!` only ever adding entries from GitHub's response and never deleting existing `Status` rows, a forged status attached to a victim's commit via a sha collision from an unrelated, attacker-owned repository is never purged.

### Finding Description
The broken invariant: `Commit#status` for victim commit `C` should equal only the states reported by `victim_stack.github_api.statuses(victim_stack.github_repo_name, C.sha)`. In practice it equals that set **union** any row ever inserted by `StatusHandler#process`, which is not scoped to `victim_stack` at all: [1](#0-0) 

Compare this to `PushHandler#process`, which resolves the sending repository first via `stacks` (derived from `Repository.from_github_repo_name(repository_name)`): [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks`/`repository`; it queries `Commit.where(sha: params.sha)` across the entire installation and calls `create_status_from_github!` on every match, regardless of which repository's webhook produced it: [4](#0-3) 

Signature verification only proves the payload came from *some* org whose GitHub App secret matches (`repository_owner` is read straight from the attacker-controlled JSON body and used to pick which org's secret to check against): [5](#0-4) 

It does not, and cannot, prove that the `sha` field belongs to a commit that actually lives in that organization's repository. Git commit hashes are computed only from public data (tree, parent(s), author, committer, message, timestamps), so an attacker who owns a repository (and thus can genuinely trigger a signed `status` webhook from GitHub for a real commit they create) can locally reconstruct a commit object with identical metadata to a target victim commit (whose metadata is publicly visible on GitHub) and obtain the *same* sha, without needing a cryptographic SHA-1 break. GitHub will then deliver a properly signed webhook naming that sha for the attacker's own repository.

Once the forged `Status` row is created for the victim's `Commit`, `Commit#refresh_statuses!` — invoked by the legitimate, scheduled `RefreshStatusesJob` — never removes it: [6](#0-5) 

`github_statuses.each { create_status_from_github! }` only inserts rows matching what GitHub currently reports; there is no corresponding deletion of `statuses` rows whose `context`/state no longer appear in the latest GitHub response. If the victim's real GitHub repository never reports a status for that exact sha (e.g., because the sha doesn't correspond to a commit that ever had CI run against it in the victim's repo, or 404s are tolerated), the forged row survives indefinitely and continues to be counted by `Commit#status`/`Commit#state`, which affects deployability gating (`deployable?`, `blocked?`): [7](#0-6) 

No existing guard prevents this: `verify_signature` only checks the HMAC against the org named in the payload, `drop_unhandled_event` only filters unregistered event types, and `ExplicitParameters` only validates the *shape* of the payload, not that `sha`/`repository` are consistent with each other.

### Impact Explanation
An attacker who owns any repository connected to the same Shipit instance can inject arbitrary, durable `success`/`failure`/`pending` `Status` rows onto commits belonging to a completely different stack/repository/tenant. Since `Commit#status`/`state` feed directly into `deployable?` and CI-gating logic used by deploy/merge automation, a forged `success` status can make an otherwise-not-CI-passing commit appear deployable, enabling an unauthorized deploy for a repository the attacker never authenticated against — this is "a payload for one repository mutating another's stack/commit... an unauthorized deploy," matching the Critical severity bucket. The corruption is not transient: it survives `RefreshStatusesJob` runs because the refresh path only adds, never deletes.

### Likelihood Explanation
Preconditions: the attacker must own a repository already connected as a Shipit stack (so a genuine, correctly signed webhook can be delivered for it), and must be able to reproduce a target commit's sha by duplicating its public git metadata (tree/parents/author/committer/message/timestamps) in a commit in their own repo — feasible for many real-world commits (e.g., templated "Initial commit", cherry-picked/rebased commits with preserved authorship/timestamps) without breaking SHA-1. No Shipit secrets, sessions, or maintainer status are required. This is repeatable against any known victim commit sha and any number of target stacks.

### Recommendation
Scope `StatusHandler#process` to the repository that produced the webhook, the same way `PushHandler`/`PullRequest::*Handler` do (e.g., filter through `stacks`/`Repository.from_github_repo_name(payload['repository']['full_name'])` before matching `Commit.where(sha:)`), so a status can only attach to commits belonging to stacks of that repository. Additionally, make `Commit#refresh_statuses!` reconcile (delete or invalidate) `Status` rows whose `context` is no longer present in the fresh GitHub response, rather than only inserting.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "StatusHandler attaches forged status to a commit in a different, unrelated repository" do
  victim_repo  = shipit_repositories(:victim)
  victim_stack = shipit_stacks(:victim_stack) # belongs to victim_repo
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  attacker_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "attacker/forged",
    "repository" => { "full_name" => "attacker/unrelated-repo" }, # not victim's repo
  }

  assert_difference "victim_commit.statuses.count", 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  assert_equal "success", victim_commit.reload.status.state
end

test "refresh_statuses! never clears the forged status" do
  Shipit.github.api.stubs(:statuses)
    .with(victim_stack.github_repo_name, victim_commit.sha, per_page: 100)
    .returns([]) # victim's real GitHub has no status for this sha

  assert_no_difference "victim_commit.statuses.count" do
    victim_commit.refresh_statuses!
  end

  assert_equal "success", victim_commit.reload.status.state # forged row still governs state
end
```
Binding checked: `victim_commit.status` should equal only states from `victim_stack.github_api.statuses(victim_stack.github_repo_name, victim_commit.sha)`; both tests show it instead equals `{attacker-forged status} ∪ {victim's real statuses}` even after a legitimate refresh, confirming the invariant is broken.
