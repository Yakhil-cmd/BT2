### Title
Cross-organization webhook forgery via mismatched signature-authenticated organization vs. acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to authenticate an inbound webhook based on `repository_owner`, a field parsed out of the untrusted JSON body, then hands the *same* parsed body to event handlers that independently re-derive the target repository from `repository.full_name` in that body. Nothing binds "the organization whose secret validated the signature" to "the repository the handler actually mutates," so a party who legitimately holds the `webhook_secret` for one configured GitHub organization (e.g. an org admin able to configure a custom webhook in `secrets.yml`'s per-org config) can forge a payload whose HMAC matches their own organization's secret while its `repository.full_name` field references a stack belonging to a completely different, unrelated organization/repository also hosted on the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and its `webhook_secret`) purely from `repository_owner`, itself just `params.dig('repository','owner','login')`, i.e., attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only proves that the raw body was HMAC-signed with *some* secret matching whichever organization `repository_owner` names — it never re-checks that other fields inside the same body (like `repository.full_name`) are consistent with that organization: [3](#0-2) 

Because the entire raw body is under a single HMAC, an attacker who knows Organization A's `webhook_secret` (multi-org installs keep a distinct secret per org in `secrets.github`) can compute a valid signature for a JSON body they fully control — including setting `repository.owner.login` to `"orgA"` (so the correct/known secret is selected) while setting `repository.full_name` to `"orgB/some-repo"` (an entirely different repository/org tracked by the same Shipit instance). Handlers resolve the acted-upon repository independently, via `repository_name`/`Repository.from_github_repo_name`, ignoring the value used for signature selection: [4](#0-3) 

This breaks the intended binding "organization that authenticated == organization owning the repository being written." Concretely, `PushHandler` uses only `params.ref`/`params.after` plus the handler's independently-resolved `stacks` (from `repository.full_name`) to enqueue a sync against a stack under Organization B, using a forged `after` SHA: [5](#0-4) 

That sync job fetches "missing commits" up to the `expected_head_sha` and, on transaction, appends git commits and (if the sync changed nothing else) recomputes/caches the deploy spec: [6](#0-5) 

If Org B's stack has `continuous_deployment: true`, appending new (attacker-influenced) commit records into that stack's reachable-commit list can feed the continuous-delivery scheduler, resulting in an unauthorized deploy being scheduled for a repository the attacker's own webhook secret was never meant to authorize: [7](#0-6) 

### Impact Explanation
This is an authentication-boundary break between "which credential validated this request" and "which repository/stack is mutated" — the same class of bug as the GodMode report, where the account authorized for one operation (fee/rent payer) was not the account actually mutated by the transfer. Here, the organization whose secret validated the HMAC is not the organization/repository actually written to. Consequences include triggering `GithubSyncJob` (and downstream `CacheDeploySpecJob`/continuous-deployment scheduling) against a stack belonging to a different, unrelated GitHub organization hosted on the same Shipit instance, and injecting forged `status` webhooks (`StatusHandler` matches purely by `Commit.where(sha: params.sha)` globally, with no organization scoping at all) that can flip CI status on arbitrary commits across all tracked repositories. This can lead to an unauthorized deploy being scheduled, satisfying the "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
Exploitability requires the attacker to already possess a valid `webhook_secret` for *at least one* organization configured in this multi-tenant Shipit instance (e.g., as a legitimate org owner able to configure Shipit's custom webhook for their own org). Given that precondition — which is a normal, intended-audience action rather than a privileged Shipit session/API token — the attacker can freely forge payloads for any *other* organization's repositories tracked by the same install, since nothing in `verify_signature` or the handlers cross-checks organization consistency.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the `GitHubApp` for `repository_owner`, verify that any `repository.full_name` (or `organization.login`) referenced elsewhere in the same payload is consistent with `repository_owner`/the authenticated organization before dispatching to handlers — reject payloads where the owner used for repository resolution disagrees with the owner used to select the signing secret.

### Proof of Concept
1. Shipit is configured with two GitHub organizations in `secrets.github`, `orgA` (secret `SA`) and `orgB` (secret `SB`), each with their own tracked repositories/stacks in the same Shipit instance.
2. Attacker is a legitimate admin of `orgA` and knows `SA` (e.g., configured a custom outgoing webhook in `orgA`'s GitHub App/webhook settings, or otherwise obtained `SA` for their own org).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SA, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "orgA")` (from `repository.owner.login`), verifies the signature against `SA`, succeeds.
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")`, matching the real Org B stack, and enqueues `GithubSyncJob` for it with the attacker-chosen `expected_head_sha`, despite the attacker never having been authenticated for Organization B.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
