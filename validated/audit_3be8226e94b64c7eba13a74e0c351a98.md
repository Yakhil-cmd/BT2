## Title
Webhook signature verification authenticates the sending organization but handlers act on an attacker-controlled `repository.full_name` field, enabling cross-organization writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, a value parsed straight out of the unauthenticated JSON body [1](#0-0) . Once the signature passes, every event handler acts on a *different* field of the same body — `repository.full_name` — to decide which `Stack`/`Repository` to mutate [2](#0-1) . Because Shipit supports hosting multiple independent GitHub organizations on one instance, each with its own `webhook_secret` [3](#0-2) , an attacker who legitimately administers Organization A's webhook secret can forge a request that authenticates as Organization A while its `repository.full_name` names a repository belonging to Organization B, causing Shipit to act on Organization B's stack.

### Finding Description
The verification flow is:
1. `verify_signature` reads `repository_owner` (from `repository.owner.login`, with fallback to `organization.login`) out of the raw JSON body and uses it to look up which GitHub App/org config (and therefore which `webhook_secret`) to check the signature against: [4](#0-3) .
2. `verify_webhook_signature` only proves that *some* known secret (the one belonging to `repository_owner`) produced the HMAC over the full raw body — it says nothing about which repository the payload's other fields describe: [5](#0-4) .
3. After the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that never re-read `repository_owner` — they instead resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`: [6](#0-5) . `Repository.from_github_repo_name` splits this string on `/` to find the owner/name independently of anything checked during signature verification: [7](#0-6) .

Nothing enforces `repository_owner == full_name.split('/').first`. Since an attacker who administers a legitimately-configured Organization A knows Organization A's real `webhook_secret` (they can set it themselves in their own GitHub App settings), they can POST directly to `/webhooks` with a self-crafted JSON body where `repository.owner.login = "OrgA"` (so the correct, known secret is used to compute a valid HMAC) but `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a different organization hosted on the same Shipit instance). The signature check passes because it only validates against Organization A's secret, and the handler then mutates Organization B's stack, e.g. `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for OrgB's stack using an attacker-chosen `after` SHA: [8](#0-7) . Pull-request/label handlers similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` and can archive/unarchive stacks or create review stacks for OrgB's repositories: [9](#0-8) [10](#0-9) .

This is the direct analog of the reported bug class: the borg-core report flags a condition-checking design where the value that is *verified* and the value that is *acted upon* can diverge due to reliance on an implicit, unenforced ordering/matching assumption. Here the equality that is silently assumed but never enforced is:

`repository_owner` (used to select/verify the signing secret) == owner segment of `repository.full_name` (used by every handler to select the mutated `Repository`/`Stack`).

### Impact Explanation
This breaks a deployment-trust binding across organization boundaries and enables **cross-repository writes** without ever having Organization B's credentials — an admin of any organization onboarded to the shared Shipit instance can trigger deploy-affecting sync jobs, archive/unarchive review stacks, or inject commit statuses against **any other organization's** stacks on the same instance. Per the stated impact rubric, cross-repository writes are Critical severity.

### Likelihood Explanation
Exploitability requires only knowledge of one's own organization's `webhook_secret` — something any org admin legitimately possesses when onboarding to a shared Shipit instance — plus knowledge of the target organization/repository name, which is generally public information (e.g., `OrgB/repo`). No Shipit session, `ApiClient` token, or GitHub App private key is needed, and the multi-org configuration this depends on is a documented, supported Shipit deployment mode [3](#0-2) .

### Recommendation
Enforce that the organization used to select/verify the webhook signature is the same organization that the payload's `repository.full_name` (or `repository.owner.login`) claims to belong to, independent of order-of-operations in the controller/handler pipeline — e.g., have `Handler#stacks`/`Repository.from_github_repo_name` cross-check against the verified `repository_owner`, and reject the event if they disagree, rather than trusting two unrelated fields of the same unauthenticated body for two different purposes.

### Proof of Concept
Assume a Shipit instance configured with two organizations, `OrgA` (attacker-administered) and `OrgB` (victim), per the documented multi-org `secrets.yml` schema.

1. Attacker knows `OrgA`'s `webhook_secret` (they configured it in their own GitHub App).
2. Attacker crafts a JSON body directly (bypassing GitHub):
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Attacker computes `signature = "sha1=" + HMAC-SHA1(OrgA_webhook_secret, raw_body)`.
4. Attacker `POST`s to `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: <signature>`.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature (it matches OrgA's real secret) [11](#0-10) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for OrgB's stack [8](#0-7) , an action the attacker has no legitimate authority to trigger on `OrgB`'s repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
