### Title
User-controlled swap routes can inject extra authorization requests and drain unrelated wallet assets - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts an opaque `swap` payload in `swap_collateral`, `swap_debt`, `multiply`, and related strategy entrypoints, then invokes the configured router while the account owner’s authorization is active. [1](#0-0)  A malicious route can cause route-selected code to request additional `caller` authorization inside the signed invocation tree, including a token transfer unrelated to the lending operation. [2](#0-1) 

### Finding Description
`swap_collateral` and `swap_debt` take caller-supplied `Bytes` without letting the controller understand or constrain the venues and contracts named by that payload. [3](#0-2)  Before router execution, `require_authorized_caller` creates a root authorization for the caller, while `authorize_transfer_as_current` grants the router only a single controller-owned input transfer. [4](#0-3) [5](#0-4)  Those controls protect the controller’s input, but they do not prevent route-controlled code below the router from adding a different `require_auth` request for the same caller. [6](#0-5) 

The harness demonstrates this exact authorization-tree injection: a rogue route hop calls `token.transfer(victim, attacker, amount)` for an unrelated wallet token while the router executes underneath `swap_collateral`. [7](#0-6)  If the victim signs the authorization tree produced by simulation, the host accepts the injected child invocation and moves the unrelated token. [8](#0-7) 

### Impact Explanation
A victim can lose wallet assets that are not listed by the lending protocol and are not part of the intended swap. The transaction still settles a valid strategy output, so the measured controller output and final account-risk checks do not stop the theft. [9](#0-8)  This is theft of user funds enabled by untrusted input reaching an authorization-bearing execution context, analogous to command injection.

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the resulting authorization tree. A wallet or client that treats simulation output as trustworthy can present only the legitimate-looking root strategy call while overlooking a malicious child transfer. The likelihood is therefore meaningful for off-chain route generation, but lower than an exploit executable without victim interaction.

### Recommendation
Constrain strategy routes to an allowlisted set of venue contracts and operations, or execute router strategies in an authorization context that cannot inherit or add caller sub-authorizations. At minimum, wallets and SDK helpers should reject any controller strategy authorization tree whose children differ from the expected token transfer(s). The current controller-side checks should also reject nonzero measured input plus unauthorized-auth behavior by bounding the router call to an explicit, declared route manifest.

### Proof of Concept
1. Victim supplies USDC and holds an unrelated token in the same wallet.
2. Attacker creates a swap payload whose hop address points to attacker-controlled code.
3. The malicious hop calls `token.transfer(victim, attacker, wallet_balance)` while the router is executing.
4. Victim calls `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_payload)`.
5. Simulation records the rogue token transfer as a child under the victim’s `swap_collateral` authorization. [10](#0-9) 
6. If the victim signs that tree, the swap succeeds and the unrelated token is transferred to the attacker; without the injected child, the host rejects the transfer. [11](#0-10)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
