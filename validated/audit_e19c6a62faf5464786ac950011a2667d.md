### Title
Debt-value overflow during interest accrual permanently freezes a market - (File: common/src/rates/index.rs)

### Summary
CVE-2020-35521 is a "crafted input forces an abort → denial of service" class. The analog in XOXNO Lending is a user-reachable arithmetic abort: every state-changing entrypoint runs `interest::global_sync` first, and accrual computes total debt as `borrowed * borrow_index` in `i128`/`RAY` space. When that product overflows `i128` the accrual panics with `MathOverflow`, and because accrual always runs before the mutation, the panic bricks every verb on that market — supply, borrow, withdraw, repay, liquidate, `clean_bad_debt` — permanently. A documented harness test confirms the cliff is reachable through ordinary `supply`/`borrow` calls and that the `MAX_BORROW_INDEX_RAY` cap never engages in time.

### Finding Description
`accrue_step` (driven by `global_sync` in `contracts/pool/src/interest.rs:20-53`) calls `calculate_supplier_rewards`, which computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)` (`common/src/rates/index.rs:80-81`). `Ray::mul` is the panicking half-up multiply-divide in `common/src/math/fp.rs`/`fp_core.rs` — it widens intermediates to `I256` but panics with `GenericError::MathOverflow` when the resulting quotient exceeds `i128`.

Scaled debt shares `borrowed` are normalized to RAY (shares ≈ `token_units * 10^(27-d)`), so for a high-decimals asset a large real deposit produces a huge `borrowed` value. On a steep rate curve at sustained ~98% utilization, `borrowed * borrow_index` exceeds `i128::MAX` while `borrow_index` is still far below `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`), so the cap cannot rescue the market. The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) demonstrates exactly this: after enough accrual, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` (error 33) — "no repay, no withdraw, no liquidation."

A single unprivileged attacker can reach the state:

1. `controller.supply(attacker, whale_amount)` of a high-decimals listed asset — inflates `borrowed`/`supplied` scaled shares toward the `i128` ceiling.
2. `controller.borrow(attacker, ~0.98 * supply)` against own collateral — sets utilization into the curve's steep segment.
3. Wait (or nudge with `update_indexes`, a public entrypoint) until accrual pushes `borrowed * borrow_index` past `i128::MAX`.

From that block forward, every call that loads the market cache aborts inside `global_sync` before any user logic runs.

### Impact Explanation
Permanent freezing of funds for every participant in that market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and `clean_bad_debt`/`recapitalize` also accrue first and hit the same panic. The debt keeps accruing conceptually but can never be settled; collateral backing other positions in the same position NFT/account that references this market is also impaired where liquidation depends on the frozen book. This is a protocol-level liveness failure with real funds locked, matching the accepted "permanent freezing of funds" impact — not a budget/memory or fail-closed-per-call DoS.

### Likelihood Explanation
Likelihood is capital-gated rather than technical: the attack needs a whale-scale position in a high-decimals asset (the harness uses ~10^27 raw units of an 18-decimal token at 98% utilization) and sustained high utilization long enough for compounded growth to hit the ceiling. The attacker also sacrifices their own position, so the motivation is griefing/sabotage rather than profit. The arithmetic path is deterministic — no oracle, timing, or third-party dependency — and the protocol's own test suite demonstrates it is reachable through the public `supply`/`borrow`/`update_indexes` entrypoints with no privileged access. Medium severity is appropriate: high impact, meaningful but plausible economic precondition.

### Recommendation
Make accrual never abort the market:

- In `calculate_supplier_rewards` (`common/src/rates/index.rs:80-83`), compute `new_total_debt`/`old_total_debt` with a saturating variant (as `update_supply_index` already does via `mul_div_floor_saturating` at line 41) and clamp `borrow_index` to a cap low enough that `borrowed * index` stays within `i128` — i.e., derive `MAX_BORROW_INDEX_RAY` (or a per-market dynamic cap `i128::MAX / borrowed`) so the index ceiling engages *before* the value ceiling.
- Alternatively, in `update_borrow_index`, cap the new index at `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` so `mul` can never overflow on the next accrual.
- Add a regression test asserting that once the cap binds, `repay`/`withdraw`/`liquidate` still succeed.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`: supply `10^9 * 10^18` units of an 18-decimal asset, borrow 98% of it via `borrow`, advance time; `try_update_indexes_for(["BIG18"])` eventually returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw_raw` / `try_repay` fail with the same error — the market is frozen.

Note on scope: this rests on the repo's own test documentation of the failure path plus the accrual arithmetic in `common/src/rates/index.rs`; I did not verify `Ray::mul`'s exact overflow threshold or `MAX_BORROW_INDEX_RAY`'s value beyond what the cited code shows.
