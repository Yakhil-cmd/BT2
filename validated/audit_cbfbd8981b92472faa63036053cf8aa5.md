### Title
Arbitrary directory deletion via attacker-crafted absolute `git.link` symlink target in `currentWorktree`/`removeWorktree` - ([File: main.go])

### Summary
`repoSync.currentWorktree()` reads the `git.link` symlink inside `--root` with `os.Readlink` and, when the target is an absolute path, returns it as a `worktree` value without validating that it resolves inside `--root`. `SyncRepo` subsequently passes this unchecked value to `removeWorktree`, which calls `os.RemoveAll` on it, so an attacker who can write to `--root` (an unprivileged co-mounted writer, per the stated scope) can redirect deletion to any directory reachable by the git-sync process.

### Finding Description
`currentWorktree()` performs `os.Readlink(git.link)` and branches on `filepath.IsAbs(target)`; when true it returns `worktree(target)` as-is, with no containment check against `r.root` and no validation that the leaf component looks like a git commit hash. `worktree.Hash()` simply takes the basename of this string, so any absolute target is accepted as a "current" worktree. `SyncRepo` compares this hash to the desired sync target and, on mismatch, calls `removeWorktree(ctx, currentWorktree)`, which ultimately performs `os.RemoveAll(worktree.Path())` on the attacker-supplied absolute path. Because the check for "is this a legitimate worktree" never verifies path containment under `--root`, the trust boundary is broken as soon as an attacker can replace the `git.link` symlink file itself (a plain filesystem write, not a flag/env/mount change).

### Impact Explanation
This matches the CONTENT_CONTAINMENT / PUBLISH_INTEGRITY impact class: an unprivileged process sharing the `--root` volume can cause git-sync to run `os.RemoveAll` against an arbitrary path outside `--root` (e.g., a shared emptyDir subpath used by a sidecar, or any directory the git-sync container's filesystem permissions allow), leading to data loss / denial of service for co-located workloads, not merely corruption of git-sync's own managed directory.

### Likelihood Explanation
Preconditions: attacker needs write access to `--root` as a non-root user, which is explicitly listed as in-scope ("read/tamper `--root` as non-root"). No non-default flags are required — the vulnerable code path is exercised on every normal sync cycle when `git.link` exists and its target hash doesn't match the desired sync target. This makes the issue directly and repeatably reachable via a simple filesystem-level tamper (delete/recreate `git.link` as `ln -s /path/outside/root git.link`) without needing to control flags, git refs, or HTTP endpoints.

### Recommendation
In `currentWorktree()`, after resolving the (possibly absolute) target, validate that it lies within `r.root` (e.g., via `filepath.Rel` + reject any result starting with `..`, or compare cleaned absolute prefixes) before treating it as a legitimate worktree. Additionally, validate that `worktree.Hash()` matches the expected git-hash pattern (`^[0-9a-f]{40}$`) before calling `removeWorktree`; if either check fails, treat the link as corrupt (log and remove/replace `git.link` itself) rather than passing the target to `os.RemoveAll`.

### Proof of Concept
Integration test sketch:
1. Initialize a git-sync `--root` directory and let a normal sync happen so `git.link` points to a legitimate worktree hash dir.
2. Create a sentinel directory `outside/sentinel` outside `--root` with a marker file.
3. Manually replace `--root/git.link` with `os.Symlink("<abs path to outside/sentinel>", root+"/git.link")`.
4. Trigger `SyncRepo` (with a remote commit hash different from the sentinel's basename so removal is attempted).
5. Assert that `outside/sentinel` still exists and its marker file is intact (i.e., `os.RemoveAll` was never invoked on any path outside `git.root`), and that git-sync instead logs/handles the link as invalid. [1](#0-0)
