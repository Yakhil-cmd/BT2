### Title
Unbounded in-memory response reads allow attacker-controlled content to exhaust `gh` memory - (multiple `io.ReadAll` sites)

### Summary
The external report describes a gRPC DoS pattern: the `mobilecoind-json` client sets a ~2 GB `max_receive_message_len`, allowing an attacker to force the client to buffer an unbounded amount of data in memory. The analogous pattern exists in the `gh` CLI's HTTP client code: several code paths read an entire HTTP response body into memory with `io.ReadAll(resp.Body)` with no size cap (no `io.LimitReader` / `http.MaxBytesReader` usage anywhere in the codebase), when the response body size is controlled by content an attacker can publish (a file in a public repository, a gist, or an attestation bundle URL).

### Finding Description
A repo-wide search found **no use of `io.LimitReader` or `http.MaxBytesReader`** anywhere in the codebase. Multiple HTTP response-reading paths call `io.ReadAll(resp.Body)` directly and load the full response into a `[]byte` before any further processing:

- `pkg/cmd/repo/read-file/http.go` — `fetchRawFile` fetches raw file bytes for a path in *any* repository the user points `gh repo read-file` at (including a public repository entirely controlled by an attacker) and does `return io.ReadAll(resp.Body)` with no cap. [1](#0-0) 
- `pkg/cmd/gist/shared/shared.go` — `GetRawGistFile` fetches the raw URL of a gist file (an attacker-authored, attacker-hosted-on-GitHub gist) and reads it fully into memory. [2](#0-1) 
- `pkg/cmd/attestation/api/client.go` — `getBundle` fetches an attestation bundle from a `safeurl.SafeURL` using `c.externalHttpClient`, explicitly documented as being for "non-GitHub hosts," and reads the entire body into memory before decompression/unmarshalling. [3](#0-2) 

The Contents-API-driven `fetchContent`/`fetchFile` path in `pkg/cmd/repo/read-file/http.go` also unconditionally buffers the whole JSON response. [4](#0-3) 

By contrast, release-asset and workflow-artifact downloads (`pkg/cmd/release/download/download.go`, `pkg/cmd/run/download/http.go`, `pkg/cmd/extension/http.go`) stream the body with `io.Copy` to a file/temp file rather than buffering in memory, so those are not equivalent to the reported bug class. [5](#0-4) [6](#0-5) 

### Impact Explanation
If an attacker publishes a very large file inside a public GitHub repository, a large gist, or hosts an oversized attestation bundle at a URL an attacker controls, a victim invoking `gh repo read-file`, `gh gist view <raw file>`, or `gh attestation verify` against that attacker-supplied content would have the entire body pulled into `gh`'s process memory in one allocation with no upper bound. This can exhaust the client machine's memory and crash the `gh` process (denial of service on the invoking user's workstation/CI runner), matching the report's DoS impact model applied to a client-side unpaginated buffer instead of a server-side gRPC receive buffer.

### Likelihood Explanation
Reachability requires an unprivileged remote attacker to get a victim to run one of these commands against attacker-controlled content: publish an oversized file in a public repo and get someone to run `gh repo read-file` on it, publish an oversized gist file, or (for the attestation path) supply a bundle URL that resolves to an oversized/slow-drip response from an attacker host. These are realistic "attacker-published content" scenarios reachable via normal `gh` commands without any privilege or MITM position, consistent with the rules of this analysis. I could not fully trace, within the available iterations, the exact call chain that determines where the `safeurl.SafeURL` passed into `getBundle` originates (whether it's always constrained to trusted Sigstore/TUF infrastructure or can be influenced by an attacker-crafted bundle/attestation), so the severity of that specific path is somewhat uncertain; the `read-file` and gist paths are more directly and clearly attacker-reachable.

### Recommendation
- **Short term:** Wrap response bodies with `io.LimitReader(resp.Body, maxBytes)` (or `http.MaxBytesReader` where applicable) before calling `io.ReadAll` in `fetchRawFile`, `fetchContent`, `GetRawGistFile`, and `getBundle`, choosing limits appropriate to expected content (e.g., GitHub's own ~100 MB file size cap, or a few MB for JSON/attestation-bundle responses), and return a clear error when the limit is exceeded rather than silently truncating.
- **Long term:** Establish a shared HTTP helper (e.g., in `api/http_client.go`) that enforces a default maximum response size for all non-streaming JSON/body reads across the codebase, so future call sites don't need to remember to add bounds individually; audit remaining `io.ReadAll(resp.Body)` call sites (e.g., `internal/codespaces/api/api.go`) for the same issue.

### Proof of Concept
1. Attacker creates a public GitHub repository containing a very large file (or a gist with a very large raw file).
2. Victim runs `gh repo read-file <path> --repo attacker/repo` (or `gh gist view <attacker-gist-id>` / views the raw file).
3. `fetchRawFile` (or `GetRawGistFile`) calls `io.ReadAll(resp.Body)` with no size limit, causing `gh` to allocate memory proportional to the attacker-chosen file size, exhausting available memory on the victim's machine. [7](#0-6)

// fetchRawFile retrieves the raw bytes of a file, used for files larger than the
// 1 MB inline content limit of the Contents API.
func fetchRawFile(httpClient *http.Client, repo ghrepo.Interface, filePath, ref string) ([]byte, error) {
	apiPath, err := contentsAPIPath(repo, filePath, ref)
	if err != nil {
		return nil, err
	}

	req, err := http.NewRequest("GET", apiPath.String(), nil)
	if err != nil {
		return nil, err
	}
	req.Header.Set("Accept", "application/vnd.github.raw")

	resp, err := httpClient.Do(req)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		return nil, api.HandleHTTPError(resp)
	}

	return io.ReadAll(resp.Body)
}

// GetRawGistFile fetches the full content of a gist file from its raw URL. The
// bytes are external content, so they are returned as iostreams.Untrusted to
// force callers to choose between sanitized display and raw round-tripping.
func GetRawGistFile(httpClient *http.Client, rawURL safeurl.SafeURL) (iostreams.Untrusted, error) {
	req, err := http.NewRequest("GET", rawURL.String(), nil)
	if err != nil {
		return iostreams.Untrusted{}, err
	}

	resp, err := httpClient.Do(req)
	if err != nil {
		return iostreams.Untrusted{}, err
	}

	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return iostreams.Untrusted{}, api.HandleHTTPError(resp)
	}

	body, err := io.ReadAll(resp.Body)

	if err != nil {
		return iostreams.Untrusted{}, err
	}

	return iostreams.NewUntrustedBytes(body), nil
}

func (w destinationWriter) Copy(name string, r io.Reader) (copyErr error) {
	fp := w.makePath(name)
	if fp == "-" {
		if w.allowEscapes {
			_, copyErr = io.Copy(w.stdout, r)
			return
		}
		copyErr = iostreams.CopyGuardedContent(w.stdout, r, w.isTTY)
		if binErr, ok := errors.AsType[iostreams.BinaryTerminalError](copyErr); ok {
			copyErr = fmt.Errorf("%w; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway", binErr)
		} else if errors.Is(copyErr, iostreams.ErrEscapeSequence) {
			copyErr = errors.New("the asset contains terminal escape sequences; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway")
		}
		return
	}
	if copyErr = w.check(fp); copyErr != nil {
		return
	}

	if dir := filepath.Dir(fp); dir != "." {
		if copyErr = os.MkdirAll(dir, 0755); copyErr != nil {
			return
		}
	}

	var f *os.File
	if f, copyErr = os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644); copyErr != nil {
		return
	}

	defer func() {
		if err := f.Close(); copyErr == nil && err != nil {
			copyErr = err
		}
	}()

	_, copyErr = io.Copy(f, r)
	return
