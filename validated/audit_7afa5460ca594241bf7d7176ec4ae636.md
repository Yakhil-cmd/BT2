## Analog Found

### Title
Cross-AA spot-price read via `balance[address][asset]` enables single-unit oracle manipulation of AMM-style AAs - (File: `formula/evaluation.js`)

### Summary
Oscript lets any AA formula read another address's live token balances with the two-argument form of `balance[]` (and `var[]`), evaluated against the *current* `aa_balances` state at the moment the trigger is processed. This is the ocore analog of Uniswap V2's `getAmountsOut`: any AA that computes a price from the instantaneous reserve ratio of an AMM-style AA (as ocore's own reference implementation `uniswap_like_market_maker.oscript` does) can have that ratio manipulated by an attacker within a single atomic unit/trigger chain, and a second, consumer AA that reads the manipulated ratio via `balance[mm_address][asset]` will act on the skewed price before any arbitrage can occur.

### Finding Description
The `balance`/`var` opcode in the formula evaluator explicitly supports querying another AA's address: [1](#0-0) 

`readBalance` pulls the value straight from `aa_balances`/`objValidationState.assocBalances`, i.e. the AA's real-time reserve balances, with no time-weighting or manipulation resistance: [2](#0-1) 

`formula/validation.js` confirms this two-argument form (`balance[aa_address][asset]`) is a documented, allowed feature for AAs (not an oversight): [3](#0-2) 

Ocore's own bundled example AA, the "Uniswap-like market maker," computes price purely from the current reserve ratio (`$p = $asset_balance * $bytes_balance`, `$amount = $asset_balance - $new_asset_balance`) with no TWAP or manipulation guard: [4](#0-3) 

Crucially, AA-to-AA composition inside a single top-level unit is fully synchronous and atomic: a primary trigger's response payment to another address immediately fires that address's AA as a "secondary trigger," processed in the same `handleTrigger` call chain, using the balances as they stand right after the first AA's state change: [5](#0-4) 

This means an attacker can construct one unit that (1) sends a large payment to the AMM-style AA to shift its `asset`/`base` reserve ratio, producing a response that (2) forwards funds to (or otherwise triggers) a second, "consumer" AA which reads the now-skewed ratio via `balance[mm_address][asset]` (e.g., to price collateral, mint a pegged asset, or settle a swap) — all resolved deterministically before any external arbitrageur has a chance to react, exactly mirroring the flash-loan-manipulated `getAmountsOut` pattern in the original report.

### Impact Explanation
Any production AA that uses another AA's live reserve ratio (via `balance[address][asset]`) as a price source for minting, collateral valuation, liquidation, or swap settlement can be driven to accept a manipulated price within one attacker-controlled unit, resulting in under-collateralized minting, unauthorized extraction of AA funds, or mispriced swaps — a direct fund-loss impact for the consumer AA and its other users.

### Likelihood Explanation
The primitive (`balance[address][asset]`) is a documented, unrestricted oscript feature reachable by any AA author, and can be triggered by any unprivileged unit poster who funds the attack unit. Ocore's own shipped sample (`uniswap_like_market_maker.oscript`) demonstrates the exact naive reserve-ratio pricing pattern that is vulnerable, making it a realistic template that AA authors are likely to copy or adapt. Exploitation requires only crafting a single unit with sequential payments to chain the manipulation and the consumer AA read — no privileged access or network-level attack needed.

### Recommendation
- Document prominently (and add lint/validation warnings) that `balance[aa_address][asset]` reflects an instantaneous, manipulable value and must never be used directly as a price oracle by other AAs without a TWAP or multi-block averaging mechanism.
- Consider providing/encouraging a built-in TWAP state-var pattern (e.g., cumulative price accumulators, as Uniswap V2 itself recommends) in reference AMM-style AA templates such as `uniswap_like_market_maker.oscript`, so that consuming AAs read a time-weighted value instead of the raw reserve ratio.
- Where feasible, expose a way to detect same-unit/same-chain composition (e.g., `trigger.initial_unit` correlation) so a consuming AA can refuse to price against an AMM AA that was touched earlier in the same trigger chain.

### Proof of Concept
1. Deploy an AMM-style AA modeled on `test/samples/uniswap_like_market_maker.oscript`, whose exchange price is `balance[asset]/balance[base]` at trigger time.
2. Deploy a "consumer" AA that reads `balance[mm_address][asset]` (or the equivalent ratio) directly in its formula to price an action (e.g., mint tokens proportional to the AMM's implied price).
3. Post a single unit whose messages: (a) pay a large amount of `base` to the AMM AA to shift its `asset`/`base` ratio; (b) forward the AMM AA's response payment to the consumer AA (secondary trigger), which reads the skewed `balance[mm_address][asset]` and mints/settles based on the manipulated ratio.
4. Because `handleSecondaryTriggers` processes both AAs synchronously within the same primary trigger's atomic transaction (`aa_composer.js` lines 1702-1757), the consumer AA never sees the pre-manipulation price, allowing the attacker to extract more value than the fair price would allow, all within one unit with no possibility of intervening arbitrage.
