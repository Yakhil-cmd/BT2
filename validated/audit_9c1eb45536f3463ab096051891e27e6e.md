### Title
Pre-fix AA auto-destroy asset balance desync between `aa_balances`/`balance[asset]` cache and spendable outputs - ([File: aa_composer.js])

### Summary
The OLPC/LABUBU exploit worked because a mutable token parameter caused a transfer to trigger an oversized, unaccounted burn that desynchronized the AMM pair's cached reserves from real balances, letting the attacker drain funds against stale state. In ocore, an analogous desync exists between an AA's cached balance ledger (`aa_balances` table / `objValidationState.assocBalances`, exposed to oscript via `balance[asset]`) and the set of outputs that are actually spendable for an `auto_destroy` asset whose definer is the AA itself.

### Finding Description
When an asset is defined with `auto_destroy: true` and `issued_by_definer_only`/definer = an AA address, any output of that asset sent to the definer (the AA) is treated by `validatePaymentInputsAndOutputs` as permanently destroyed — it can never be spent again (`validation.js` "this output was destroyed by sending it to definer address", `validation.js:2504`, `2430`).

However, `updateInitialAABalances` in `aa_composer.js` (lines 481-485, 502-511) unconditionally adds every asset received in `trigger.outputs` to `objValidationState.assocBalances[address][asset]`, and `insertAADefinitions`/`aa_balances` bookkeeping does the same — with no exception for auto-destroyed assets whose definer is the AA. This inflates the AA's cached `balance[asset]` value that oscript formulas read via `balance[asset]` (`formula/evaluation.js:1510-1528`, `readBalance`).

The actual spendable-output selection logic in `aa_composer.js` (`readStableOutputs` / `readUnstableOutputsSentByAAs`, lines 1140-1173) *does* correctly exclude auto-destroyed outputs sent to the definer — but only `mci >= constants.pemCurvesFixMci`:
```
if (asset && assetInfos[asset].auto_destroy && assetInfos[asset].definer_address === address && mci >= constants.pemCurvesFixMci)
    return handleRows([]);
```
Before `pemCurvesFixMci`, this exclusion did not exist, so the AA's cached balance (`balance[asset]`) and its actual spendable output set were consistent-looking on the surface but the destroyed output was still selectable as an input — meaning the AA logic, cap accounting, or a downstream payment amount calculated from `balance[asset]` could diverge from what could truly be issued/spent, exactly mirroring the OLPC bug class of "mutable/asset-specific burn semantics not reflected consistently in the cached balance figure used for further calculations."

### Impact Explanation
If exploited pre-fix (or if any residual code path still uses the cached `assocBalances`/`aa_balances` value for `auto_destroy` assets without the same MCI-gated exclusion — e.g., `readBalance` in `formula/evaluation.js` has no such exclusion at all, at any MCI), an AA that issues or accounts using `balance[asset]` for an auto-destroy asset can compute amounts based on a balance that includes destroyed/unspendable coins. This can lead to over-issuance approvals, incorrect change/output calculations, or bounced/stuck AA logic that assumes funds exist which cannot actually be spent — a form of AA fund accounting corruption (loss or freezing) directly analogous to the reserve-desync drain in OLPC/LABUBU.

### Likelihood Explanation
The `readBalance` formula path (`formula/evaluation.js:1510-1528`) that backs `balance[asset]` shows **no MCI-gated auto_destroy exclusion at all**, unlike the output-selection queries in `aa_composer.js`. Any unprivileged AA author can define an `auto_destroy` asset with itself as definer (a legitimate, currently-supported combination per `aa_validation.js:225-300` / `validation.js:2725-2827`), then send that asset to the AA and read `balance[asset]`, immediately exposing the inconsistency without requiring any special privilege or historical MCI window.

### Recommendation
Ensure `balance[asset]` (`readBalance` in `formula/evaluation.js`) and every other balance-cache write path (`updateInitialAABalances`, `insertAADefinitions`, `updateFinalAABalances`) apply the same auto_destroy/definer exclusion that `readStableOutputs`/`readUnstableOutputsSentByAAs` apply, unconditionally (not only post-`pemCurvesFixMci`), so that the cached balance an AA's oscript logic relies on always matches genuinely spendable funds.

### Proof of Concept
1. AA `X` defines an asset with `auto_destroy: true`, `issued_by_definer_only: true`, `is_transferrable: true`, definer address = `X` itself (permitted per `validateAssetDefinition`/`validateAADefinition`, no privileged party required).
2. Any user triggers `X`, causing `X` to send some of this asset back to itself (or receives it directly as `trigger.outputs`), which `validation.js` marks as destroyed (unspendable) per the auto_destroy/definer rule.
3. `X`'s balance cache (`aa_balances` / `assocBalances`) still shows the full amount as balance.
4. A subsequent AA response reads `balance[asset]` (`formula/evaluation.js` `readBalance`) and issues a payment/decision based on this inflated figure, while the actual spendable outputs are fewer — producing a payment-construction failure, unintended bounce, or (depending on the exact oscript logic) an inconsistency that can be leveraged to make the AA believe it holds more of the asset than it can actually pay out.

**Note on uncertainty:** I was not able to fully trace whether `pemCurvesFixMci` has already passed on the network this ocore snapshot targets, nor find a definitive commit message describing the original fix's full scope (the repo only shows a single "Initial commit" in its git history, so I could not review prior blame/commit context). The `formula/evaluation.js` `readBalance` path's lack of an auto_destroy exclusion appears to still be present in the current code regardless of MCI, which is the most concrete, currently-reachable part of this finding.
