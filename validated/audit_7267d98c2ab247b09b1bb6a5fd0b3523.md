### Title
Unauthenticated race between concurrent `light/dry_run_aa` requests and normal joint processing causes unsynchronized reset of in-memory DAG caches, leading to node disagreement on unit validity/stability - (File: network.js)

### Summary
The CVE describes a heap use-after-free in PJSIP's ICE session caused by a race between session-destruction and in-flight callbacks that still reference the freed session state. The analogous defect in `ocore` is a race between the destruction/rebuild of critical in-process caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocStableUnitsByMci`) and concurrent asynchronous callbacks (unit validation, writer, stabilization) that read and mutate those same caches without holding the mutex that is supposed to serialize all such access.

### Finding Description
`handleRequest` in `network.js` processes the `light/dry_run_aa` command sent by any unauthenticated light client: [1](#0-0) 

When `constants.COUNT_WITNESSES === 1` (single-witness networks, e.g. testnet or any custom single-witness deployment), after every dry run the handler unconditionally calls `storage.resetMemory(conn, onDone)` inside `db.executeInTransaction`, with **no mutex lock at all**:
```
if (constants.COUNT_WITNESSES === 1) { // the temp unit might have rebuilt the MC
    db.executeInTransaction(function (conn, onDone) {
        storage.resetMemory(conn, onDone);
    });
}
```
Compare this to every other place that legitimately mutates these same caches — `writer.saveJoint`, `main_chain.updateMainChain`/`advanceMcStability`, and cache initialization at startup (`initCaches`) — all of which first acquire `mutex.lock(["write"])` (or `handleJoint`) before touching the caches: [2](#0-1) 

`storage.resetMemory` is a multi-step asynchronous operation: it first deletes every key from `assocUnstableUnits`/`assocBestChildren`, then asynchronously repopulates them from the DB (`initUnstableUnits`), then does the same for `assocStableUnits`/`assocStableUnitsByMci`: [3](#0-2) 

Because JS is single-threaded but this is a multi-tick async sequence, any joint validation, `writer.saveJoint`, or main-chain stabilization callback that is scheduled to run on the event loop during that window will observe the caches in a transiently empty or partially-rebuilt state. These caches are read synchronously and unconditionally throughout the codebase (e.g. `handlePrimaryAATrigger` in `aa_composer.js` does `storage.assocStableUnits[unit]` and `throw`s if not found): [4](#0-3) 

and `determineIfStableInLaterUnitsAndUpdateStableMcFlag` in `main_chain.js` reads `storage.readUnitProps`/cached unit props to decide whether a unit is still on the main chain and to advance the stability point: [5](#0-4) 

If `resetMemory` clears `assocUnstableUnits`/`assocStableUnits` mid-flight of a legitimate `handleJoint`/`saveJoint`/stabilization sequence that is holding the `["write"]`/`["handleJoint"]` lock but relies on synchronous cache reads, the concurrent, unguarded `resetMemory` call can: (a) cause a hard crash via the `throw Error("...not found in cache")` path, effectively a remotely triggerable DoS against a single-witness/testnet full node servicing light clients; or (b) silently overwrite cache entries that were concurrently added by the in-flight save/stabilization with stale DB-read values, causing the node's in-memory view of "unstable"/"stable"/"best child" to diverge from what was just committed to the DB — i.e., node disagreement about unit validity/stability, and inconsistent AA trigger execution, because `aa_composer.handleAATriggers`/`insertAADefinitions` rely on the same caches being consistent with the DB state that triggered them.

Any unauthenticated light client can trigger this window repeatedly and cheaply by sending `light/dry_run_aa` requests (the address only needs to resolve to an existing AA; the trigger content is attacker-controlled and requires no funds or signature beyond basic validation done by `aa_composer.validateAATriggerObject`), racing it against the node's normal, concurrent unit-processing pipeline.

### Impact Explanation
This is reachable by an unprivileged peer (light client) sending unauthenticated `light/dry_run_aa` requests against a single-witness (`COUNT_WITNESSES===1`) full node — a configuration used on testnet and permitted for custom/private networks. The unsynchronized cache reset can (1) crash the node process via an uncaught `throw` inside async cache-lookup code reachable from AA trigger processing, denying service to the network's ability to confirm new units, and/or (2) desynchronize the node's cached view of unit stability/best-children from the DB, which feeds directly into AA trigger selection, main-chain stabilization, and balance accounting — creating a path to node disagreement on validity/stability and potential AA fund-accounting errors if the corrupted cache state is used before it is repaired on the next full DB round trip.

### Likelihood Explanation
Moderate-to-high on affected topologies: the request is fully unauthenticated and requires no special permission (any light client), and the race window is opened on every dry run when `COUNT_WITNESSES===1`. An attacker only needs to fire `light/dry_run_aa` requests in a tight loop while normal joint traffic (or other dry runs) is being processed by the node to reliably land in the multi-tick window between `resetUnstableUnits` clearing the cache and `initUnstableUnits` finishing its repopulation. On multi-witness mainnet-style deployments this specific trigger path does not fire, which limits blast radius to testnet/private single-witness networks, but the missing-mutex pattern itself is the root cause worth flagging.

### Recommendation
Wrap the `storage.resetMemory` call in `network.js`'s `light/dry_run_aa` handler with the same `mutex.lock(["write"])` (or `handleJoint`) discipline used by `writer.saveJoint`/`initCaches`/`main_chain` stabilization, so that cache resets can never interleave with in-flight validation, save, or stabilization callbacks. Alternatively, avoid clearing the live global caches altogether for dry-run purposes — perform the AA rebuild-check using a snapshot/copy of relevant cache entries scoped to the dry run, instead of mutating the shared `storage.assocUnstableUnits`/`assocStableUnits`/`assocBestChildren` singletons.

### Proof of Concept
1. Run a full node configured as the sole witness (`COUNT_WITNESSES === 1`, e.g. testnet).
2. As an unauthenticated light client, send a `light/dry_run_aa` request for any valid AA address, in a tight loop, from multiple concurrent connections.
3. Concurrently have another light/full client submit ordinary payment units to the same node so that `handleJoint`/`writer.saveJoint`/`main_chain.updateMainChain` are executing and reading/writing `storage.assocUnstableUnits`/`assocStableUnits`/`assocBestChildren` at the same time `storage.resetMemory` (triggered by the dry-run responses) is deleting and repopulating those same objects.
4. Observe either an uncaught exception/crash from a cache-lookup `throw` (e.g. in `aa_composer.js:104-106`-style guard code reachable through AA processing), or persisted logs showing state such as `assocStableUnits`/`assocBestChildren` entries reverted to stale DB-read values right after a legitimate `saveJoint`/stabilization added newer entries — demonstrating the cache desynchronization caused by the unsynchronized reset racing with the mutex-protected write path.
