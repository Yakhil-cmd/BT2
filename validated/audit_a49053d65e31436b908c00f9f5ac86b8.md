### Title
Ratio Manipulation via Front-Run Dust Deposit in Balance-Based AA Ratio Calculations - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bundled "Uniswap-like market maker" Autonomous Agent (AA) template computes investment/exchange ratios from the AA's *live* `balance[...]` at the moment a trigger unit is processed, rather than from a value the depositor could pin at the time they compose their transaction. Because Obyte processes triggers addressed to an AA in a strict, attacker-influenceable order, any unprivileged unit poster can submit a small ("dust") payment to the AA address that gets ordered ahead of a victim's pending investment trigger, shifting `balance[$asset]`/`balance[base]` and thus the ratio the victim's transaction is checked against. This mirrors the reported HedgeUnit `mint()` front-running bug: the victim's trigger either bounces (DoS/griefing) or executes on unexpectedly unfavorable terms.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript`, the "invest in MM" case computes: [1](#0-0) 

`$asset_balance` and `$bytes_balance` are derived by subtracting the *current* trigger's own contribution from the AA's live balance (`balance[$asset]`, `balance[base]`), which reflects every payment the AA has already received and processed up to that point — including from other triggers. `$current_ratio` and `$expected_asset_amount` are then computed from this live balance, and the trigger bounces with `'wrong ratio of amounts...'` if the depositor's own `trigger.output` doesn't exactly match what the (now-shifted) live balance implies.

The AA's balance is read from `objValidationState.assocBalances`, which is populated straight from the `aa_balances` table (or the in-memory equivalent for dry runs) at the moment each trigger is handled: [2](#0-1) 

Crucially, AA triggers destined for the same address are dequeued and executed in a fixed, unit-content-dependent order — `mci, level, aa_triggers.unit, address` — not in a way the original submitter controls or can lock in: [3](#0-2) 

Because any unprivileged party can post a payment unit to the AA's address, and that unit's trigger will be assigned a level/unit ordering that can precede a pending victim unit within the same or an earlier MCI, an attacker can deliberately place a small "donation"-style trigger (e.g., a tiny exchange or invest call) so that it stabilizes/executes before the victim's larger, already-broadcast investment transaction. The victim's `$expected_asset_amount`/ratio check, computed against pre-attack balances at composition time, no longer matches the AA's live balance when the trigger actually executes, causing the guard at line 45 to bounce the transaction.

### Impact Explanation
This is the same bug class as the reported HedgeUnit issue: a griefing/DoS vector with no direct fund loss to the attacker, but a targeted or arbitrary user's minting/investment transaction can be reliably forced to bounce (wasting their bounce fee) or made to receive an amount inconsistent with what they intended, because the ratio-determining logic trusts point-in-time balances instead of a value the caller can commit to in advance. Any AA built on this widely-referenced official template (or any bonding-curve/ratio AA following the same `balance[...]`-based pattern) inherits this weakness, affecting asset issuance/exchange logic reachable by any address that can send a payment to the AA.

### Likelihood Explanation
The attack cost is minimal — a single small-value unit sent to the AA's address, no privileged position needed. Any unprivileged unit poster who can observe a pending (not-yet-stable) investment/exchange unit targeting the same AA can attempt to get their own dust trigger ordered ahead of it, since trigger execution order depends on MCI/level/unit rather than mempool arrival time chosen by the victim.

### Recommendation
Avoid deriving critical ratios purely from the AA's live, on-the-fly balance read at trigger-execution time. Instead:
- Track explicit reserve/outstanding-supply state variables (e.g., `var['asset_reserve']`, `var['bytes_reserve']`) that are updated only by the AA's own state-change logic, rather than recomputing from `balance[...]` each time.
- Where a caller-specified expected ratio/amount must be honored, allow the AA to compute the output amount from the trigger's actual inputs rather than bouncing on any live-balance mismatch, or provide a slippage/tolerance parameter the caller can specify in `trigger.data`.

### Proof of Concept
1. AA `X` implements the market-maker pattern from `test/samples/uniswap_like_market_maker.oscript` (lines 33–48), holding asset `$asset` and base coins, with `var['mm_asset_outstanding']` tracking issued shares.
2. Alice composes and broadcasts a unit sending `base` and `$asset` to `X` sized to match the current known ratio, intending to invest.
3. Before Alice's unit stabilizes/executes as a trigger, Bob broadcasts his own small unit to `X` (e.g., a tiny "exchange asset to bytes" or "invest" trigger per lines 102–123 / 33–48) that gets ordered with an earlier `(mci, level, unit)` per the `ORDER BY` in `aa_composer.js` (lines 63-69).
4. Bob's trigger executes first, altering `balance[$asset]`/`balance[base]` (and possibly `var['mm_asset_outstanding']`).
5. Alice's trigger then executes with the new live balances; `$expected_asset_amount` computed inside her trigger no longer equals her `trigger.output[[asset=$asset]]`, so her transaction bounces per line 45's `bounce('wrong ratio of amounts...')`, denying her the intended investment (or, in variants without a strict equality check, changing the number of shares she is issued).
