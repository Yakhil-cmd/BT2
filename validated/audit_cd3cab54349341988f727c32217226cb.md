### Title
Cross-organization webhook forgery escalates into `Shipit.github_teams` authorization via `MembershipHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using an attacker-supplied field (`repository.owner.login`, falling back to `organization.login`) taken straight out of the unauthenticated request body, then hands the *entire, still-unverified* payload to event handlers that trust other attacker-supplied fields (e.g. `team.id`, `organization.login`, `member.login`) to mutate authorization-relevant records. In a multi-organization deployment, this lets an attacker who only needs to control (or exploit a secret-less) low-trust organization forge a `membership` event that adds an arbitrary GitHub login to a `Team` that is part of `Shipit.github_teams`, bypassing GitHub's real membership check entirely.

### Finding Description
`Shipit.github(organization:)` supports per-organization webhook secrets (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). The webhook secret is explicitly documented as **optional**: [1](#0-0) 

The signature check picks the app config purely from data embedded in the incoming JSON body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that particular organization has no configured `webhook_secret`: [3](#0-2) 

So the binding actually enforced is: *"the organization whose secret authenticated this request" == `params.dig('organization','login')` (attacker-controlled string, not cryptographically bound to anything else in the payload)*. The binding the rest of the pipeline needs is: *"the Team/organization actually mutated" == "the organization that legitimately owns that Team"*. These are never checked against each other.

`MembershipHandler` looks the `Team` up by `github_id` (a stable identifier that persists across events and organizations) and only uses the attacker-supplied `organization.login` on first creation; on any subsequent event it blindly adds/removes the attacker-chosen `member.login` from whatever `Team` already has that `github_id`: [4](#0-3) 

`Team#add_member` performs no verification against GitHub before persisting the membership: [5](#0-4) 

`Shipit.github_teams` (built from `oauth_teams` in each app's config) is exactly the set of teams `Authentication#force_github_authentication` uses to gate all engine access: [6](#0-5) 

### Impact Explanation
If any configured organization in a multi-org Shipit instance has no `webhook_secret` (an explicitly supported/documented configuration) — or if an attacker otherwise learns any one organization's webhook secret — that attacker can forge a `membership` webhook that is verified using that organization's (nil) secret while writing to a `Team` record belonging to a *different, privileged* organization (identified only by its numeric `github_id`, which can be recovered from GitHub's public API or from a previous legitimate webhook/log). This adds the attacker's own GitHub login as a member of a team in `Shipit.github_teams`. On the attacker's next OAuth login, `current_user.authorized?` succeeds, granting full authenticated access to the Shipit UI/session-based endpoints (deploys, rollbacks, stack management) without ever being a real member of the authorizing GitHub organization/team. This is an authentication/authorization-bypass escalation into `Shipit.github_teams`, matching the High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment (explicitly documented/supported feature), (b) at least one configured organization with no webhook secret, or knowledge of one organization's webhook secret, and (c) knowledge of the target `Team`'s GitHub `github_id` (obtainable via GitHub's public teams API for public orgs, or via prior webhook traffic/logs). No Shipit session, ApiClient token, or GitHub App private key is required — only network access to the public `/webhooks` endpoint. This is a realistic, unprivileged-attacker path analogous to the QuickAccManager bug: the verified identity (organization owning the secret) is not the identity actually acted upon (the Team/organization whose membership is mutated).

### Recommendation
- Re-derive the organization used for authorization decisions strictly from the `Team`'s already-stored `organization` (do not trust `params.organization.login` for lookups/writes on existing records), and reject `membership` events whose asserted `organization.login` does not match the `Team.organization` on file for that `github_id`.
- Cryptographically bind the verified webhook secret's organization to every field the handler is allowed to touch, rather than trusting attacker-supplied identifiers to select which trust boundary applies then trusting other attacker-supplied identifiers inside that boundary.
- Do not allow organizations to be configured without a webhook secret in any deployment that also configures `Shipit.github_teams`/OAuth authorization from another organization; make `webhook_secret` mandatory when multiple orgs are configured, or explicitly disable auth-relevant webhook handlers when a secret is absent.

### Proof of Concept
1. Deploy Shipit with `config/secrets.yml` configuring two organizations, e.g. `OrgAttacker` (no `webhook_secret`) and `OrgTrusted` (has `oauth.teams` referencing `OrgTrusted/developers`, which is part of `Shipit.github_teams`).
2. Team `OrgTrusted/developers` already exists in Shipit's database (created by a prior legitimate `membership` webhook), with a known `github_id` (discoverable via `GET https://api.github.com/orgs/OrgTrusted/teams` if public, or leaked from logs).
3. Attacker sends, without any valid signature (since `OrgAttacker` has no secret):
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <OrgTrusted_developers_github_id>, "name": "developers", "slug": "developers", "url": "x"},
  "organization": {"login": "OrgAttacker"},
  "member": {"login": "attacker-github-login"}
}
```
4. `verify_signature` resolves `repository_owner` = `"OrgAttacker"`, loads its `GitHubApp` (no secret), `verify_webhook_signature` returns `true` unconditionally — request proceeds.
5. `MembershipHandler#process` finds the existing `Team` by `github_id`, and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, adding the attacker to `OrgTrusted/developers`.
6. Attacker logs in via `/github/auth/github` with GitHub account `attacker-github-login`; `current_user.authorized?` now succeeds because the user is a member (in Shipit's DB) of a team in `Shipit.github_teams`, granting full application access.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
