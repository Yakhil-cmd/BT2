### Title
Silently ignored curator-fee transfer failure in `claim_child_bounty`/`claim_bounty` permanently strands funds and finalizes payout state - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-child-bounties::claim_child_bounty` and `pallet-bounties::claim_bounty` execute two sequential balance transfers (curator fee, then beneficiary payout) out of a bounty sub-account, but only guard the *first* transfer's outcome with `debug_assert!`, which is compiled to a no-op in release/production builds. [1](#0-0) [2](#0-1)  If the curator-fee transfer fails (e.g. the fee is below the Existential Deposit and the curator account does not yet exist), the extrinsic still proceeds to pay the beneficiary in full, emits success events, and irreversibly deletes the (child-)bounty record from storage - exactly the pattern described in the report: a failed `send`-equivalent is not checked/reverted, and the bookkeeping/state finalization proceeds as if it had succeeded, permanently losing the un-sent portion for the affected party.

### Finding Description
In `claim_child_bounty`:
```rust
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
debug_assert!(fee_transfer_result.is_ok());
let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
debug_assert!(payout_transfer_result.is_ok());
...
*maybe_child_bounty = None;
``` [3](#0-2) 

The identical pattern exists in `pallet-bounties::claim_bounty`:
```rust
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());
*maybe_bounty = None;
``` [4](#0-3) 

`debug_assert!` only executes in debug builds; in a production/release runtime it is a complete no-op, so the returned `DispatchResult` of `T::Currency::transfer` is discarded unconditionally. `pallet_balances`'s `transfer` implementation can fail with an existential-deposit error when the destination account does not already exist and the transferred amount is below the configured `ExistentialDeposit`. `claim_child_bounty` is callable by *any* signed account (`ensure_signed(origin)?`, no permission check on the caller), and the curator/beneficiary/fee values are set earlier by ordinary (non-privileged) calls to `propose_curator`/`accept_curator`/`award_child_bounty`. No malicious or privileged actor is required — a legitimate curator fee that happens to be smaller than the ED for an account that has never held a balance is enough to trigger the silent failure.

Contrast this with the already-fixed analog in `pallet-broker::do_claim_revenue`, where the same class of bug (revenue payout transfer failure discarded, entitlement removed regardless) was patched by propagating the transfer error with `?` so the whole extrinsic reverts and storage mutations are rolled back:
```rust
// The storage changes and the payment must both happen, or neither.
T::Currency::transfer(&Self::account_id(), &contribution.payee, payout, Expendable)?;
``` [5](#0-4) 
and by the fix documented in `pr_13040.prdoc`, "Return the error when the revenue payout to the payee fails, so the extrinsic reverts and the claimant keeps the entitlement. The pallet previously discarded this error and removed the entitlement without payment." [6](#0-5)  `pallet-bounties`/`pallet-child-bounties` were not given the equivalent fix and still rely on `debug_assert!`, which vanishes in release builds — unlike `pallet-broker`'s corrected `?`-propagation.

Once the transfer silently fails:
- The child-bounty (or bounty) record is unconditionally removed from storage (`*maybe_child_bounty = None;` / `*maybe_bounty = None;`), so there is no way to retry or reclaim the stranded curator fee.
- The curator deposit was already unreserved before the fee transfer is attempted, so the curator loses both the fee and any recourse.
- A `Claimed`/`BountyClaimed` event is still emitted, misleadingly signalling successful payout to off-chain observers/indexers.
- The `child_bounty_account`/`bounty_account` retains the un-transferred balance with no bookkeeping pointing to it, i.e., the funds become permanently orphaned/unreachable dust in a derived sub-account nobody tracks any more (comparable to the "stranded funds" pattern independently identified and fixed for `pallet-society` in PR 12590 [7](#0-6) ).

### Impact Explanation
This is a real fund-loss bug for a non-privileged party (the curator, and by extension the treasury-adjacent bounty economy), triggered by an ordinary user-facing mistake (setting a curator fee below the chain's ED) rather than by any malicious/privileged action. It matches the report's classification: the affected party (here, the curator whose fee transfer fails) permanently loses funds because the code assumes the transfer "should not fail" and only checks that assumption in a way that is stripped from production binaries. I assess this as Medium severity, consistent with the original report's classification and with Parity's own treatment of the closely related, already-patched `pallet-broker` and `pallet-society` issues, which were accepted as legitimate bugs worth a runtime-dev-facing fix (`prdoc` entries) though not marked as Critical/High theft or unbacked-issuance bugs.

### Likelihood Explanation
Likelihood is moderate: it requires a specific but plausible configuration — a curator-fee amount smaller than the runtime's `ExistentialDeposit` for a curator account that has never held a balance. This can arise from ordinary bounty proposals without any adversarial intent (fee is chosen by the bounty proposer/curator, not gated against ED), and the claim call itself is permissionless (`ensure_signed`), so any account can trigger the final claim once the state is set up. `debug_assert!` being compiled out in release builds means this silent failure is live on any production/mainnet runtime built in release mode (the default for all Polkadot/Substrate runtimes).

### Recommendation
Replace the `debug_assert!`-guarded transfers in `claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) with proper error propagation (`?`) inside a transactional context (e.g. `with_storage_layer`/`try_mutate`'s natural rollback), mirroring the fix already applied to `pallet-broker::do_claim_revenue` (PR 13040): if either transfer fails, the whole extrinsic should revert, leaving the bounty record and reserved/unreserved state unchanged so the claim can be retried once the underlying condition (e.g., ED) is resolved, instead of unconditionally deleting the record and losing the funds.
