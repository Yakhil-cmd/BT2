### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but handlers act on the unrelated `repository.full_name` field, allowing forged events when any configured GitHub App has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret is used to validate the inbound webhook HMAC based on `repository.owner.login` (falling back to `organization.login`), while every `Webhooks::Handlers::Handler` subclass resolves the repository/stacks it will mutate from a completely different JSON field, `repository.full_name`. These two fields are never cryptographically bound together outside of the whole-body HMAC, and `verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured — a state explicitly documented as optional. This breaks the binding: `organization authenticated == repository written`.

### Finding Description
`verify_signature` computes the organization used to fetch the verifying `GithubApp` purely from the JSON body itself: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

The setup docs and fixtures show `webhook_secret` is an explicitly supported "optional" configuration (`OrgTwo`'s config has `webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once the request passes (or is exempted from) signature verification, every handler dispatches on a *different* field — `repository.full_name` — to resolve which `Repository`/`Stack`s are mutated: [6](#0-5) 

For example, `PushHandler` forces a stack sync to an attacker-chosen `after` SHA for whatever stacks match the forged `full_name`/`ref`: [7](#0-6) 

And the `membership` event handler creates/removes `Team`/`Membership` records purely from attacker-supplied JSON, as shown by the tests exercising it without any repository field at all (using only `organization.login` for `repository_owner`): [8](#0-7) 

Binding broken: `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`, used only to pick which app's secret authenticates the request) `!=` `repository.full_name` (used by every handler to decide which repository/stacks/teams are actually written to). Nothing enforces that these two fields refer to the same repository/organization, and when the resolved organization has no secret configured, the check is skipped entirely, so an unprivileged, unauthenticated caller can submit any JSON body naming any `repository.full_name` and `organization.login` pair it likes.

### Impact Explanation
An unauthenticated attacker who knows (or guesses) that any one org configured in `Shipit.github_apps` has no `webhook_secret` can send a single unsigned `POST /webhooks` request that:
- Forces `GithubSyncJob`/`sync_github` on arbitrary stacks with an attacker-chosen `expected_head_sha` via `PushHandler`, potentially advancing continuous-deployment stacks to an arbitrary commit.
- Creates commit `Status` records for arbitrary commits/branches via `StatusHandler`.
- Creates/removes `Team` and `Membership` rows via the `membership` event handler, which is a direct escalation path into `Shipit.github_teams` authorization since team membership drives access control in `force_github_authentication`.
This satisfies the High-impact criterion "escalation into `Shipit.github_teams` authorization" and can contribute to an unauthorized ship on continuously-deployed stacks.

### Likelihood Explanation
The only precondition is that some organization registered in `Shipit.github_apps` has no `webhook_secret` set — a state the project's own setup docs mark as "optional," meaning it is a normal, supported deployment configuration rather than a misconfiguration outside the documented setup. No session, `ApiClient` token, or GitHub credentials are required; the request is a plain unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Bind the field used to select the verifying secret to the field acted upon by the handlers: verify the signature using the same repository/organization that `Handler#repository_name` resolves (`repository.full_name`'s owner), and reject requests where `repository.owner.login`/`organization.login` do not match the owner segment of `repository.full_name`. Additionally, avoid defaulting to unconditional acceptance when `webhook_secret` is blank — require an explicit "unauthenticated webhooks intentionally disabled for this org" opt-in rather than silently passing verification.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, e.g. `OrgTwo` with `webhook_secret: nil` (a supported configuration per `docs/setup.md`) and `OrgOne` with a real stack/repo under a different owner.
2. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "OrgTwo" },
  "repository": { "full_name": "orgone/critical-repo", "owner": { "login": "orgone" } },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `repository_owner` to `"orgone"` from the `repository.owner.login` field... but note the JSON here also lets the attacker independently control `organization.login` used as fallback when `repository` key is omitted (e.g. for `membership` events). Concretely, use the `membership` event, which has no `repository` object at all, so `repository_owner` resolves solely to `params.dig('organization','login')`, e.g. `"OrgTwo"` (no secret configured) while the created `Team`/`Membership` records are global and immediately usable for `Shipit.github_teams` checks:
```json
{
  "organization": { "login": "OrgTwo" },
  "team": { "id": 48, "name": "Attacker Team", "slug": "attacker-team", "url": "https://example.com" },
  "member": { "login": "attacker" },
  "action": "added"
}
```
4. `verify_webhook_signature` returns `true` unconditionally (no `webhook_secret` for `OrgTwo`), so `head(422)` is never triggered, and `MembershipHandler` (dispatched by `event`) creates the `Team`/`Membership` rows, granting the attacker's GitHub login membership recognized by Shipit's authorization checks.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
