### Title
KAIA Permanently Locked in Bridge When `_to` Recipient Contract Rejects Native Token Transfer — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` unconditionally requires that a low-level KLAY push to `_to` succeeds. If `_to` is a contract without a `receive()`/`fallback()` function (or one that explicitly reverts), the call always fails, the entire transaction reverts, the nonce is never consumed, and the bridged KAIA is permanently locked in the destination bridge contract with no recovery path.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs all state mutations — marking the request tx hash as handled, recording the nonce-to-block mapping, advancing `lowerHandleNonce`, and emitting `HandleValueTransfer` — before the external KLAY push:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // line 81
handleNoncesToBlockNums[_requestedNonce] = ...;    // line 83
_updateHandleNonce(_requestedNonce);               // line 84
emit HandleValueTransfer(...);                     // lines 86-96

(bool ok, ) = _to.call.value(_value)("");          // line 98
require(ok, "handleKLAYTransfer: transfer failed"); // line 99
```

Because Solidity reverts all state changes on a failed `require`, every mutation above is rolled back when `_to` rejects KLAY. The nonce is never permanently consumed, so operators can retry — but since `_to` is fixed by the original `RequestValueTransfer` event on the source chain and cannot be changed, every retry will fail identically. There is no admin escape hatch to redirect the stuck transfer or recover the locked KAIA.

The `_to` address originates from a user-controlled call on the source chain:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData)
    external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

Any user can supply a contract address for `_to`. Bridge operators relay the event faithfully; they have no authority to substitute a different recipient.

Secondary consequence: because `handleNoncesToBlockNums[N]` is always reverted to zero, `_updateHandleNonce` loop condition `handleNoncesToBlockNums[i] > 0` fails immediately at `i = N`, so `lowerHandleNonce` never advances past N and `recoveryBlockNumber` never advances past N's block. The value-transfer recovery daemon will perpetually re-scan from that stale block and re-attempt nonce N, creating an infinite retry loop.

---

### Impact Explanation

- **Permanent loss of bridged KAIA**: The `_value` KAIA deposited into the destination bridge contract can never be transferred to `_to` (which rejects it) and there is no mechanism to redirect or withdraw it. The funds are effectively burned.
- **`lowerHandleNonce` permanently stuck**: Storage for handled nonces is never cleaned up past N; `recoveryBlockNumber` is frozen.
- **Recovery daemon infinite loop**: The off-chain recovery process (`vt_recovery`) perpetually retries nonce N, wasting operator resources and potentially masking other recovery failures.

---

### Likelihood Explanation

Any unprivileged user on the source chain can trigger this by calling `requestKLAYTransfer` with `_to` set to a contract that has no payable fallback. This can happen accidentally (user confuses a contract address with an EOA) or deliberately (griefing). No special role or majority-validator collusion is required.

---

### Recommendation

1. **Pull-payment pattern**: Instead of pushing KLAY to `_to`, record the claimable amount in a mapping and let `_to` pull it. This is the standard mitigation for push-transfer DoS.
2. **Wrap-on-failure**: If the direct KLAY push fails, wrap the amount to WKLAY and transfer the ERC-20 token to `_to` instead (analogous to the WETH fallback pattern cited in the original report).
3. **Admin rescue function**: Add an `onlyOwner` function that can redirect a permanently-stuck nonce's KAIA to an alternative address, at minimum allowing recovery of locked funds.

---

### Proof of Concept

```solidity
// Deployed on the destination chain
contract KLAYRejecter {
    // No receive() or fallback() — all KLAY pushes revert
}

// On the source chain:
// 1. User calls:
bridge.requestKLAYTransfer{value: 10 ether}(
    address(klayRejecter),  // _to = contract that rejects KLAY
    10 ether,
    ""
);
// RequestValueTransfer(KLAY, user, klayRejecter, 0x0, 10e18, nonce=N, ...) emitted

// 2. Bridge operator relays to destination chain:
bridge.handleKLAYTransfer(
    requestTxHash, user, address(klayRejecter), 10e18, N, blockNum, ""
);
// → always reverts: "handleKLAYTransfer: transfer failed"

// 3. 10 KAIA is permanently locked in the destination bridge contract.
//    lowerHandleNonce stays at N forever.
//    recoveryBlockNumber never advances past N's block.
```
