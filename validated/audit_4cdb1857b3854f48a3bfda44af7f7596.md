### Title
Webhook signature verification is keyed on `repository.owner.login` while all mutations are keyed on `repository.full_name`, letting a forged payload authenticate against one org's (secretless) GitHub App while mutating another org's Stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the signature against using `params.dig('repository','owner','login')`, but every `pull_request` handler (e.g. `ClosedHandler`) resolves and mutates the target `Repository`/`Stack` using `params.repository.full_name` via `Repository.from_github_repo_name`. Both fields live in the same attacker-controlled JSON body, and nothing enforces that `full_name`'s owner segment matches `owner.login`. In a multi-organization Shipit installation where any configured org has no `webhook_secret` set, an attacker can set `repository.owner.login` to that secretless org and `repository.full_name` to a victim org's provisioned review-stack repo, causing the request to pass signature verification and archive the victim's Stack.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never checks:
`repository.owner.login (used to pick the verifying GitHub App/secret) == full_name.split('/').first (used to pick the mutated Repository/Stack)`.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) .
2. `Shipit.github` in a multi-org schema looks up `github_app_config(organization)` and builds a `GitHubApp` from whatever config is registered for that org name [3](#0-2) .
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank, without even checking the provided signature header [4](#0-3) .
4. Once verification passes, `Shipit::Webhooks.for_event('pull_request')` dispatches to `ClosedHandler`, which resolves the target repository from a completely different field, `params.repository.full_name`, via `Repository.from_github_repo_name` [5](#0-4) , and then calls `review_stack.archive!` [6](#0-5) .

Because `repository.owner.login` and `repository.full_name` are two independent strings inside the same attacker-supplied JSON body, and the controller/handlers never cross-check them, an attacker who knows the login of any Shipit-configured org whose `webhook_secret` is blank can put that org's login in `repository.owner.login` while pointing `repository.full_name` at a real, unrelated victim org's provisioned review-stack repository. `verify_signature` validates against the secretless org's (non-existent) secret and passes unconditionally; `ClosedHandler` then archives the victim org's Stack.

This differs from a normal single-organization Shipit install: there, `github_default_organization` is `nil`, so `Shipit.github` always uses the single top-level `secrets.github` config regardless of the `organization` argument passed in [7](#0-6) , and the one true secret must be known to forge a signature. The gap only opens in the documented multi-org configuration [8](#0-7) , where per-org secrets can independently be blank — a configuration Shipit itself supports and exercises in its own multi-app test fixture (`test/dummy/config/secrets_double_github_app.yml`, both orgs with `webhook_secret: # nil`).

Existing guards do not catch this: `drop_unhandled_event` only filters by event type, not payload consistency; `ExplicitParameters` schemas for `ClosedHandler` only require `repository.full_name` to be a `String` with no relation to `owner.login`; `Repository.from_github_repo_name` and the `Repository` validations only constrain the format of `owner`/`name`, not that they match the verifying org.

### Impact Explanation
An unauthenticated attacker (assuming a multi-org Shipit deployment with a secretless org) can cause the archiving of a review Stack belonging to a completely different, victim organization, without holding any Shipit or GitHub credential for that org. This is a "payload for one repository mutating another's stack" scenario as called out in the Critical impact bar, repeatable against any provisioned review stack whose PR number and repo full name the attacker can predict or brute-force, and it works identically for other `pull_request` handlers (`OpenedHandler`, `LabeledHandler`, etc.) that share the same `repository`/`full_name` resolution pattern, widening blast radius beyond just archiving.

### Likelihood Explanation
Exploitability is conditioned on:
- The Shipit instance being configured with the multi-organization GitHub App schema (documented and supported, not the default single-org setup).
- At least one configured org having a blank `webhook_secret` — a real but avoidable misconfiguration; Shipit's own fixtures demonstrate this exact shape is functional and testable.
- The attacker knowing the login of that secretless org (feasible if they are a member of it, or if it's discoverable/guessable) and the victim org's `full_name`/PR number for an existing review stack (observable from the victim's public repo activity).

Given those preconditions, the attack costs a single unauthenticated `POST /webhooks` with a crafted JSON body and an arbitrary/absent `X-Hub-Signature` header, and is fully repeatable.

### Recommendation
Bind signature verification and repository resolution to the same source of truth: after computing `repository` in the handler (via `full_name`), require that its `owner` matches the org whose secret verified the signature (or, conversely, have `verify_signature` derive the app from `repository.full_name`'s owner segment instead of the separate `repository.owner.login` field). Reject the webhook if the two disagree.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (conceptual, using the existing multi-app fixtures):
1. Configure Shipit with two orgs, `OrgOne` (a real/victim org owning a provisioned review stack) and `OrgTwo` (secretless, as in `test/dummy/config/secrets_double_github_app.yml`).
2. Create a review Stack for a repo under `OrgOne`, assert `stack.archived? == false`.
3. Build a `pull_request_closed` payload where `repository.owner.login = "OrgTwo"` but `repository.full_name = "OrgOne/<repo>"` and `pull_request.number` matches the existing stack's PR.
4. `POST :create` with `X-Github-Event: pull_request` and an arbitrary/blank `X-Hub-Signature` header.
5. Assert response is `:ok` (verification passed via `OrgTwo`'s blank secret) and assert `stack.reload.archived? == true`, proving a cross-org mutation of `OrgOne`'s Stack was performed using `OrgTwo`'s (non-)secret — i.e., the equality `owner.login == full_name.split('/').first` was violated and the mutation still succeeded.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      webhook_secret:
      private_key:
      oauth:
