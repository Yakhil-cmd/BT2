### Title
Unchecked `transferFrom` in ERC721 Bridge Allows Silent Failure, Enabling Free Cross-Chain Minting or Permanent Asset Loss - (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.sol` contains two bare `IERC721.transferFrom` calls whose return values are never checked and which are not wrapped in any safe-transfer helper. Unlike the ERC20 bridge — which explicitly imports `SafeERC20` and uses `safeTransfer`/`safeTransferFrom` throughout — the ERC721 bridge has no equivalent protection. For any registered non-standard ERC721 token whose `transferFrom` silently returns without reverting on failure, the deposit path emits a cross-chain request event and increments `requestNonce` without the bridge ever receiving the token, and the withdrawal path permanently consumes a handle nonce without delivering the token to the recipient.

---

### Finding Description

`BridgeTransferERC721` contains two unchecked `transferFrom` calls:

**Deposit path** — `requestERC721Transfer` (line 129):
```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [1](#0-0) 

If `transferFrom` silently fails (no revert, no return value checked), `_requestERC721Transfer` still executes: it emits `RequestValueTransferEncoded` and increments `requestNonce`. [2](#0-1) 

**Withdrawal path** — `handleERC721Transfer` (line 69):
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [3](#0-2) 

This executes **after** the nonce has already been updated and the `HandleValueTransfer` event emitted. A silent failure here permanently consumes the handle nonce with no delivery. [4](#0-3) 

**Contrast with ERC20 bridge**, which correctly uses `SafeERC20`: [5](#0-4) [6](#0-5) [7](#0-6) 

`BridgeFee.sol` also uses `safeTransfer` for all ERC20 fee payments: [8](#0-7) [9](#0-8) 

The `IERC721` interface declares `transferFrom` with no return value: [10](#0-9) 

Token registration is `onlyOwner`: [11](#0-10) 

---

### Impact Explanation

**Deposit path (primary impact):** For a registered non-standard ERC721 token whose `transferFrom` does not revert on failure, any unprivileged caller can invoke `requestERC721Transfer` without actually transferring the token to the bridge. The bridge emits the cross-chain event and increments `requestNonce`. Counterpart bridge operators, observing the event, will call `handleERC721Transfer` on the counterpart chain and mint or transfer an ERC721 to the attacker — an **unauthorized mint of a bridged asset** with no corresponding deposit.

**Withdrawal path (secondary impact):** If `transferFrom` silently fails during `handleERC721Transfer`, the handle nonce is permanently consumed (`_updateHandleNonce` already executed), the `HandleValueTransfer` event is already emitted, and the request tx hash is marked as handled. The recipient's ERC721 is **permanently lost** with no mechanism for retry, constituting **persistent corruption of bridge settlement state**.

---

### Likelihood Explanation

Requires a registered non-standard ERC721 token (one that does not revert on a failed `transferFrom`). Token registration is `onlyOwner`, so the precondition is either an inadvertently registered non-standard token or a token whose behavior changes post-registration. Once such a token is registered, the exploit is triggerable by any unprivileged user on the deposit path. The withdrawal path can be triggered by any bridge operator with a token that silently fails. The ERC20 bridge's explicit use of `SafeERC20` demonstrates that the developers were aware of this class of risk for ERC20 but did not apply equivalent protection to ERC721.

---

### Recommendation

1. Replace the bare `transferFrom` calls with `safeTransferFrom` (which reverts on failure) in both locations:

```solidity
// requestERC721Transfer (deposit)
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);

// handleERC721Transfer (withdrawal)
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

2. In `handleERC721Transfer`, move the `transferFrom`/`safeTransferFrom` call **before** updating the nonce and emitting the event, so a revert does not leave the nonce consumed with no delivery.

3. Alternatively, add a `require` around the call if a return-value-bearing variant is used.

---

### Proof of Concept

**Deposit path exploit:**

1. Deploy a non-standard ERC721 contract `MaliciousNFT` whose `transferFrom` does nothing (no revert, no state change) when the caller is not the owner or not approved.
2. Bridge owner calls `registerToken(maliciousNFT, counterpartNFT)` on the service-chain bridge.
3. Attacker calls `requestERC721Transfer(maliciousNFT, attackerOnMainChain, tokenId, "")`.
   - `IERC721(maliciousNFT).transferFrom(attacker, bridge, tokenId)` silently does nothing.
   - `_requestERC721Transfer` emits `RequestValueTransferEncoded` and increments `requestNonce`.
4. Counterpart bridge operators observe the event and call `handleERC721Transfer` on the main-chain bridge.
5. Main-chain bridge mints or transfers `counterpartNFT` token `tokenId` to the attacker.
6. Attacker receives a bridged ERC721 on the main chain without ever depositing anything on the service chain.

**Withdrawal path exploit:**

1. Same setup. Bridge holds no `tokenId` in lock mode (`modeMintBurn == false`).
2. Operators call `handleERC721Transfer` for a legitimate cross-chain request.
3. `IERC721(maliciousNFT).transferFrom(bridge, recipient, tokenId)` silently fails (bridge doesn't own the token).
4. Nonce is consumed, event emitted, request marked handled — recipient never receives the token and the request cannot be replayed.
