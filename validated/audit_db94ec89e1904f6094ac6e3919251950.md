Based on my research, I found a concrete Polkadot SDK analog of the CVE's underlying bug class: a role/permission hierarchy claiming a "superset" relationship without actually verifying that the superset's admitted-call set truly contains the subset's admitted-call set. In the CVE, `Role.toString()` was not overridden so a lower-privileged admin could add a "super administrator" because the code failed to distinguish role identity/containment correctly. The direct FRAME analog is `pallet_proxy`'s `InstanceFilter::is_superset`, which gates `add_proxy`/`remove_proxy` — exactly this class of bug was already found and fixed for `asset-hub-westend` (`NonTransfer` vs `Governance`, PR #12769), but the same *pattern* is still present, unfixed, in the relay-chain runtimes.

### Title
`ProxyType::is_superset` lattice violation lets a `NonTransfer` proxy self-grant an `Auction` proxy that can call `Registrar::swap`, which `NonTransfer` itself is explicitly denied - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
`pallet_proxy::do_proxy` authorizes `add_proxy`/`remove_proxy` solely via `T::ProxyType::is_superset`, without re-checking `InstanceFilter::filter` containment for the full call set of the target type. In `polkadot/runtime/westend/src/lib.rs`, `polkadot/runtime/rococo/src/lib.rs`, and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`, `ProxyType::is_superset` declares `(ProxyType::NonTransfer, _) => true` (i.e. `NonTransfer` is claimed to be a superset of every other proxy type, including `Auction`), while `ProxyType::filter` for `NonTransfer` explicitly excludes `paras_registrar::Call::swap` (comment: `// Specifically omitting Registrar \`swap\``) but `ProxyType::Auction`'s filter admits the entire `Registrar` pallet via a wildcard (`RuntimeCall::Registrar(..)` / `RuntimeCall::Registrar { .. }`), which includes `swap`.

### Finding Description
`pallet_proxy`'s privilege-escalation guard is: [1](#0-0) 

When a delegate account acts through the `proxy` extrinsic with `def.proxy_type = NonTransfer` and dispatches `Proxy::add_proxy { delegate: X, proxy_type: Auction, .. }`, the guard first checks `!def.proxy_type.is_superset(&Auction)`. Because `NonTransfer.is_superset(&Auction)` returns `true` (blanket rule), that guard does not deny the call, and execution falls through to `_ => def.proxy_type.filter(c)`, where `c` is the `Proxy::add_proxy` call itself (a `RuntimeCall::Proxy(..)` variant), which `NonTransfer`'s filter explicitly admits: [2](#0-1) 

So a `NonTransfer` proxy can successfully add an `Auction` proxy relationship for the account it proxies. The declared containment is false, however: [3](#0-2) 
`Auction`'s filter admits the entire `Registrar` pallet (`RuntimeCall::Registrar(..)`), which includes `paras_registrar::Call::swap`, a call that `NonTransfer`'s own filter explicitly, deliberately excludes (line 977 comment). `is_superset` is nonetheless declared blanket-true for `NonTransfer`: [4](#0-3) 

Once the `Auction` proxy exists, any account holding it (the original `NonTransfer` delegate itself, or an accomplice it names as `delegate` in `add_proxy`) can call `proxy(real, Some(Auction), Registrar::swap { .. })`, a call the `NonTransfer` type was never supposed to reach. This is structurally the same defect as the CVE: a role comparison (`is_superset`/`Role` ordering) that is used as the sole authorization gate for granting another role, but which does not actually verify that the granted role's capabilities are contained within the granter's own capabilities — enabling privilege escalation from a lower to a higher-privileged role.

This exact bug class (a proxy type falsely claiming superset containment via `is_superset` while its filter denies calls the "subset" admits) was already identified and fixed for `asset-hub-westend`'s `NonTransfer`/`Governance` pair: [5](#0-4) [6](#0-5) 
That fix, and its regression test, only cover the Asset Hub Westend runtime's `NonTransfer`/`Governance` edge: [7](#0-6) 
It did not address the analogous `NonTransfer`/`Auction` (Registrar `swap`) violation that remains in the relay-chain runtimes: [8](#0-7) [9](#0-8) 

### Impact Explanation
A `NonTransfer` proxy is intentionally a restricted, lower-trust delegation (it is granted, e.g., so a delegate can manage governance/utility/vesting-adjacent calls but not move funds or perform certain registrar operations). This bug lets such a delegate silently mint itself (or a colluding third account) an `Auction` proxy, which can then invoke `Registrar::swap` on behalf of the real account — a call `NonTransfer` was deliberately barred from reaching. `Registrar::swap` allows swapping two parachain/parathread registrations, an operation with direct consequences for parachain slot/lease ownership. Because the account under attack is the *proxy delegator* (the real account that granted the `NonTransfer` proxy), this is an unauthorized-dispatch/privilege-escalation issue reachable purely from a permitted, non-privileged signed extrinsic path (`Proxy::proxy` / `Proxy::add_proxy`), with no governance, root, or stolen-key prerequisite.

### Likelihood Explanation
The delegator must have granted a `NonTransfer` proxy to some account — this is a routine, expected use of `pallet_proxy` for a "broad but non-financial" delegation, not a privileged setup step. From there, the only actions required are two ordinary signed extrinsics (`proxy(add_proxy(Auction))` then `proxy(Registrar::swap)`), both fee-paying and within the delegate's own control. No validator/collator/governance/bridge cooperation is required. I was not able to fully confirm within the available tool budget whether `paras_registrar::swap` additionally requires the caller to be a specific para "manager" account matched between the two paras being swapped (which would narrow, but not eliminate, exploitability to cases where the real account is already a para manager); this should be verified against `polkadot/runtime/common/src/paras_registrar/mod.rs::swap` before finalizing severity.

### Recommendation
Apply the same fix pattern used for `asset-hub-westend`'s `NonTransfer`/`Governance` pair to the relay-chain `ProxyType::is_superset` implementations in `polkadot/runtime/westend/src/lib.rs`, `polkadot/runtime/rococo/src/lib.rs`, and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`: remove the blanket `(ProxyType::NonTransfer, _) => true` rule and replace it with an explicit, audited list of subsets whose `filter` is actually fully contained in `NonTransfer`'s `filter` (excluding `Auction`, since `Auction`'s wildcard `Registrar(..)` admits `swap`, which `NonTransfer` explicitly denies). Add a lattice-consistency test analogous to `proxy_type_superset_relation_matches_call_filters` (asset-hub-westend) for every runtime that defines a custom `ProxyType`, so any future edit that breaks `is_superset`/`filter` containment is caught automatically instead of relying on manual audit.

### Proof of Concept
Deployment evidence found in-repo:
- The vulnerable pattern (`is_superset` blanket claim contradicted by `filter` exclusion of `Registrar::swap`) is present and unaddressed in `polkadot/runtime/westend/src/lib.rs:954-1030`, `polkadot/runtime/rococo/src/lib.rs:918-1008`, and `substrate/frame/staking-async/runtimes/rc/src/lib.rs:1323-1419`.
- The identical bug class was already confirmed exploitable and fixed for the `NonTransfer`/`Governance` pair on `asset-hub-westend` (see `prdoc/pr_12769.prdoc` and the regression test `non_transfer_proxy_is_not_a_superset_of_governance` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2518-2559`), confirming this exact `pallet_proxy::do_proxy`/`is_superset` gate is a real, previously-exploitable authorization boundary in this codebase, not a theoretical one.

No local integration test was run against the westend/rococo/staking-async-rc runtimes to execute this specific `NonTransfer` → `Auction` → `Registrar::swap` chain end-to-end; this would require constructing `Proxy::add_proxy(Auction)` then `Proxy::proxy(Registrar::swap)` calls through those runtimes' mocks/integration harness and asserting the dispatch succeeds despite `NonTransfer`'s filter denying `swap` directly. I was also unable to fully verify `paras_registrar::swap`'s exact origin/manager-matching preconditions within the available tool budget — this should be confirmed before treating the finding as fully weaponized, though the `is_superset`/`filter` containment violation itself is definitively present in the cited code.

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
