### Title
Webhook signature is verified against `repository.owner.login`, but the repository actually acted upon is selected from the independent `repository.full_name` field — allowing cross-repository/cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, the actual event handlers (e.g. `PushHandler`) determine which repository/stack to mutate using a *different* field of the same attacker-suppliable JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing cross-checks that `repository.full_name`'s owner segment matches `repository.owner.login`, i.e. the organization whose secret authenticated the request.

### Finding Description
The `/webhooks` endpoint is a plain HTTP endpoint that accepts any POST body with a matching `X-Hub-Signature` header — it does not require a Shipit session, `ApiClient` token, or any prior authorization; it authenticates purely via a per-organization `webhook_secret` HMAC [1](#0-0) , resolved through `Shipit.github(organization: repository_owner)` and `GithubApp#verify_webhook_signature` [4](#0-3) .

Anyone who administers a GitHub App installed for *their own* organization (`OrgA`) legitimately knows/controls `OrgA`'s `webhook_secret`, configured per-organization in `secrets.yml` [5](#0-4) . That person is an unprivileged attacker with respect to any other organization (`OrgB`) hosted on the same shared Shipit instance.

The binding that should hold is:
`organization whose secret verified the signature (repository.owner.login)` == `repository that gets written to (repository.full_name)`

But these are two independent, unauthenticated-relative-to-each-other JSON fields inside the same signed raw body. The signature only proves "this exact byte string was signed with OrgA's secret" — it says nothing about internal consistency between `repository.owner.login` and `repository.full_name`. An attacker who owns `OrgA`'s secret can construct any JSON payload (not a real GitHub delivery) where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's `webhook_secret` and the HMAC computed over the full attacker-crafted body validates), and
- `repository.full_name` = `"OrgB/victim-repo"` (so `Handler#repository_name` / `Handler#stacks` resolves to a `Stack` belonging to `OrgB`) [3](#0-2) .

For the `push` event, `PushHandler#process` then finds all not-archived stacks on the victim repository/branch and calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , which enqueues `GithubSyncJob` to fetch and append commits up to an attacker-chosen `expected_head_sha`, and can trigger `CacheDeploySpecJob` re-caching of the deploy spec [7](#0-6) . This same class of mismatch is reachable for other handlers keyed off `params.repository.full_name` (pull request opened/reopened/label-capturing handlers) [8](#0-7) [9](#0-8) .

This exactly matches the class explicitly called out in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
By forging a push/pull_request-family webhook signed with a secret they legitimately control for their own org, an attacker can cause Shipit to sync and process arbitrary GitHub state (commits, SHAs, PR metadata) against a **different organization's repository/stack** that they have no access to. Where `continuous_deployment` is enabled on the target stack, syncing new/forged commit history via `GithubSyncJob` feeds directly into the deploy pipeline, potentially resulting in an unauthorized deploy of attacker-influenced state — one of the explicitly accepted "Critical/High" impacts (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Likelihood is medium: exploitation requires the attacker to control (or have administrative access to) at least one GitHub App/organization already configured in the shared Shipit instance's `secrets.yml` — a realistic scenario for any Shipit deployment hosting multiple organizations/tenants with distinct `webhook_secret`s, since none of those admins are meant to have any privilege over each other's repositories. No GitHub-side delivery is required; the attacker can POST directly to the `/webhooks` endpoint with a self-crafted, self-signed body.

### Recommendation
After parsing the payload, verify that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other repository identifiers used downstream by handlers) before dispatching to `Shipit::Webhooks.for_event(event)`. Reject the webhook (422) on mismatch. More robustly, have `WebhooksController#verify_signature` and `Handler#repository_name`/`#stacks` derive the organization/repository from the *same single, already-verified* field, rather than two independently attacker-controlled JSON paths.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App on the shared Shipit instance and knows `OrgA`'s configured `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and the signature validates against the crafted body [1](#0-0) .
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` lookup resolves `Repository.from_github_repo_name('OrgB/victim-repo')` [3](#0-2) , and `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` is triggered on `OrgB`'s stack — an org the attacker never had access to [6](#0-5) .

Note: I was not able to fully trace `Stack#sync_github`/`continuous_deployment` auto-deploy trigger logic in `app/models/shipit/stack.rb` within the available tool budget (only match counts were retrieved, not the method bodies), so the exact automatic-deploy consequence of a forged sync is inferred from `GithubSyncJob` and `continuous_deployment` scheduling (`Stack.schedule_continuous_delivery`) rather than directly confirmed line-by-line.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
