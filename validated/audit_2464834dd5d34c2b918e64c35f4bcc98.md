### Title
Unbounded decompression of attacker-published archives during `gh extension install`, `gh skill install`, `gh release download`, and `gh copilot install` enables a decompression-bomb DoS - ([File: internal/zip/zip.go])

### Summary
The Optimism report describes a bug class where an attacker-controlled input (batched, attacker-supplied compressed blobs) can be decompressed by a resource-constrained component with no size limits, exhausting memory and crashing/corrupting the process, which then has a systemic downstream effect (an unchallengeable/hijacked state). The general bug class is: *attacker-published compressed content is decompressed with no bound, in a normal client operation, leading to resource-exhaustion DoS.* In the `gh` CLI, several code paths decompress zip/tar.gz archives that originate from a third party (extension authors, skill authors, release publishers, or the `github/copilot-cli` release) with no cap on decompressed size or entry count, mirroring the same missing-resource-limit pattern.

### Finding Description
`internal/zip.ExtractZip` streams every zip entry directly to disk with `io.Copy(df, f)` [1](#0-0) , with no limit on the number of entries or the total/per-file decompressed size. This helper is reused by:
- `pkg/cmd/run/download/http.go:downloadArtifact`, which downloads a workflow-run artifact ZIP from the API and extracts it with `ghzip.ExtractZip(zipfile, destDir)` with no size cap [2](#0-1) .
- `pkg/cmd/copilot/copilot.go:extractZip`, used when installing the Copilot CLI binary [3](#0-2) .

Similarly, `pkg/cmd/copilot/copilot.go:extractTarGz`/`extractFile` decompress a gzip+tar stream from a GitHub release download and write each entry with an unrestricted `io.Copy(out, r)` [4](#0-3) . Both zip and tar.gz code paths only validate the *path* of each entry (to prevent traversal) — never the cumulative or per-entry *decompressed size*.

The extension installer (`pkg/cmd/extension/manager.go:installBin` → `downloadAsset`) and the release/asset download path (`pkg/cmd/release/download/download.go:downloadAsset`) similarly stream HTTP response bodies to disk based on attacker-controlled `Content-Length`/body size without an independent cap, and any archive content downloaded this way that is later extracted goes through the same unbounded `io.Copy`-based extraction routines.

In all these flows, the archive's origin is attacker-controlled content that reaches an unprivileged user running an ordinary `gh` command:
- `gh extension install owner/gh-extension` clones/downloads a repo owned by any GitHub user and (for binary extensions) extracts a release asset.
- `gh skill install owner/repo skill-name` fetches attacker-authored skill content from arbitrary repositories.
- `gh release download --archive=zip|tar.gz` downloads and (for `--archive`) does not decompress via `internal/zip`, but other release/run-artifact downloads route through `ghzip.ExtractZip`.
- `gh copilot install` downloads and extracts an archive from the `github/copilot-cli` releases (lower attacker control, but same missing-limit pattern).

This is structurally the same root cause the Optimism report calls out: a component that must process attacker-supplied compressed data has no resource ceiling, so a crafted, highly-compressible payload (a "zip/tar.gz bomb") causes disproportionate resource consumption relative to the compressed size the user/consumer expected to handle.

### Impact Explanation
A malicious extension or skill publisher (any unprivileged remote GitHub user can host a `gh-*`-named repository or an agent-skills repository) can craft a small, highly compressed zip/tar.gz archive that expands to many gigabytes when extracted. When a victim runs `gh extension install <owner>/<malicious-ext>` or `gh skill install <owner>/<repo> <skill>`, `gh` will decompress the archive without limit, filling the victim's disk and/or exhausting memory/CPU, denying service to the local machine (and potentially other processes competing for disk space). This matches the "DoS" assessed type in the source report and requires no privilege beyond publishing a public repository — an "unprivileged remote-attacker analog" fully within the allowed categories (downloads to disk / extension or skill install and execution).

### Likelihood Explanation
Likelihood is moderate: it requires a victim to actively choose to run `gh extension install`, `gh skill install`, or otherwise download/extract content from a repository controlled by an untrusted third party — which is an explicitly documented, normal, and encouraged workflow for `gh extension`/`gh skill` (the tool's own help text states "Extensions are not verified, signed, or endorsed by GitHub… you are trusting its publisher") [5](#0-4) . Since users are expected to install extensions/skills from arbitrary GitHub repos, an attacker merely needs to get a victim to install their extension/skill (e.g., via social engineering, a plausible-sounding name, or search listing) to trigger unbounded extraction.

### Recommendation
- Enforce a maximum decompressed size (and/or maximum entry count) in `internal/zip.ExtractZip` and in `pkg/cmd/copilot/copilot.go:extractTarGz`/`extractFile`, aborting extraction and returning an error once a configurable ceiling is exceeded (track cumulative bytes across all `io.Copy` calls, and reject archives with pathological compression ratios).
- Apply the same protection to `pkg/cmd/run/download/http.go:downloadArtifact` before/while extracting the ZIP.
- Consider bounding downloads themselves with `io.LimitReader`/`http.MaxBytesReader` in `downloadAsset` variants (`pkg/cmd/extension/http.go`, `pkg/cmd/release/download/download.go`) so a hostile server cannot stream unbounded compressed content in the first place.
- Surface a clear, actionable error to the user (e.g., "archive exceeds maximum allowed size") rather than allowing the process to silently exhaust disk/memory.

### Proof of Concept
Conceptual PoC (not executed, since this is a static/code-review-based analog rather than a runtime-verified exploit):
1. Attacker creates a public repository `attacker/gh-evil` following the `gh-<name>` extension naming convention, or an `agentskills`-style skills repo.
2. Attacker publishes a release asset (for a binary extension) or a repository script/skill payload that is a zip or tar.gz file consisting of a single file made of highly repetitive bytes (e.g., all zeros), compressing to a few KB but expanding to tens/hundreds of GB.
3. Victim runs `gh extension install attacker/gh-evil` (or `gh skill install attacker/repo evil-skill`).
4. `Manager.installBin` → `downloadAsset` downloads the small compressed asset, then extraction (`ghzip.ExtractZip` / `extractTarGz`) proceeds via unbounded `io.Copy`, writing an arbitrarily large decompressed payload to disk with no size check, exhausting the victim's disk space (and CPU while writing).

Note: I was not able to find any code path that imposes a decompressed-size or entry-count limit anywhere in the extraction routines (`internal/zip/zip.go`, `pkg/cmd/copilot/copilot.go`, `pkg/cmd/run/download/http.go`), which supports the conclusion that this gap is real rather than mitigated elsewhere in the codebase I was able to search.

func extractZip(path, destDir string) error {
	zipReader, err := zip.OpenReader(path)
	if err != nil {
		return fmt.Errorf("failed to open zip: %w", err)
	}
	defer zipReader.Close()

	absPath, err := safepaths.ParseAbsolute(destDir)
	if err != nil {
		return err
	}

	// As of the time of writing, ghzip.ExtractZip will safely skip files that
	// would result in path traversal. This is an issue for our use-case because
	// we want to error out before extracting if there's any such file.
	// To avoid breaking the shared ghzip.ExtractZip code that expects unsafe
	// paths to be ignored and no error produced, we pre-validate here,
	// producing an error if any such file is found.
	for _, f := range zipReader.File {
		_, err := absPath.Join(f.Name)
		if err != nil {
			return err
		}
	}

	if err := ghzip.ExtractZip(&zipReader.Reader, absPath); err != nil {
		return err
	}

	return nil
}

func extractTarGz(r io.Reader, destDir string) error {
	gzr, err := gzip.NewReader(r)
	if err != nil {
		return fmt.Errorf("failed to create gzip reader: %w", err)
	}
	defer gzr.Close()

	absDestDirPath, err := safepaths.ParseAbsolute(destDir)
	if err != nil {
		return err
	}

	tr := tar.NewReader(gzr)
	for {
		header, err := tr.Next()
		if err == io.EOF {
			break
		}
		if err != nil {
			return fmt.Errorf("failed to read tar: %w", err)
		}

		absFilePath, err := absDestDirPath.Join(header.Name)
		if err != nil {
			return err
		}
		target := absFilePath.String()

		if header.Typeflag == tar.TypeReg {
			if err := os.MkdirAll(filepath.Dir(target), 0755); err != nil {
				return fmt.Errorf("failed to create parent directory: %w", err)
			}
			if err := extractFile(target, os.FileMode(header.Mode)&0777, tr); err != nil {
				return err
			}
		}
	}
	return nil
}

// extractFile creates a file at target with the given mode and copies content from r.
func extractFile(target string, mode os.FileMode, r io.Reader) (err error) {
	out, err := os.OpenFile(target, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, mode)
	if err != nil {
		return fmt.Errorf("failed to create file: %w", err)
	}
	defer func() {
		if cerr := out.Close(); err == nil && cerr != nil {
			err = fmt.Errorf("failed to close file: %w", cerr)
		}
	}()
	if _, err := io.Copy(out, r); err != nil {
		return fmt.Errorf("failed to write file: %w", err)
	}
	return nil
}
