### Title
Webhook signature verification is bound to `repository.owner.login`, but repository dispatch is bound to `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the `X-Hub-Signature` HMAC based on `params.dig('repository', 'owner', 'login')`, but every downstream event `Handler` resolves the target `Stack`/`Repository` from a completely different, unauthenticated-by-that-check field: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so a webhook that is cryptographically valid for organization A can carry a `full_name` pointing at organization B's repository, letting a valid webhook signer for org A drive Shipit's webhook handlers against org B's stacks.

### Finding Description
`verify_signature` picks the app/secret purely from the owner login in the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a distinct config (and distinct `webhook_secret`) per organization: [3](#0-2) 

But `Handler#stacks`/`#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and all `PullRequest::*Handler` classes, resolve the repository to act on from `payload.dig('repository', 'full_name')` — not from `repository.owner.login`: [4](#0-3) [5](#0-4) 

The equality the engine implicitly (and incorrectly) assumes is:
`org(repository.owner.login used to select webhook_secret) == org(repository.full_name used to select the Stack that gets acted on)`

Nothing in `WebhooksController` or `Handler` enforces this. A payload can set `repository.owner.login = "org-a"` (so the signature is verified against org‑a's `webhook_secret`) while setting `repository.full_name = "org-b/victim-repo"` (so the handler resolves and mutates org‑b's `Stack` via `Repository.from_github_repo_name`). This breaks the "organization authenticated vs. repository written" trust binding described by the bug class, analogous to the Chainlink report's mismatch between the data actually validated and the data acted upon.

### Impact Explanation
Any actor who legitimately controls (or has compromised) the GitHub App/webhook secret of one organization already onboarded to a given Shipit deployment can forge webhooks that are accepted as authentic and then dispatch push/status/check_suite/pull_request/membership events against any other organization's stacks configured on that same Shipit instance. Depending on handler, this can trigger `GithubSyncJob` runs, review-stack provisioning/archival, membership/team mutation, or commit status writes on a completely different repository than the one whose secret actually signed the request — i.e., cross-repository/cross-organization state mutation without a valid signature for the targeted organization. This matches the "escalation into `Shipit.github_teams` authorization" / "unauthorized... task/streams" class of impact when the target is a differently-owned stack.

### Likelihood Explanation
Low-to-moderate: the attacker must control (or have compromised) a valid webhook secret for at least one organization already configured in the target Shipit instance — this is realistic in any multi-tenant Shipit deployment serving multiple GitHub orgs/teams, since `Shipit.github_app_config` explicitly supports per-organization secrets. No privileged Shipit session, `ApiClient` token, or GitHub App private key for the *victim* organization is required — only knowledge of one tenant's own webhook secret, which that tenant would consider unprivileged with respect to other tenants.

### Recommendation
Verify the webhook signature using the same organization/repository identity that the handler will actually act upon, and reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name` (or, better, always derive the signing organization strictly from `repository.full_name`, not from the separate `owner.login` sub-object). Additionally, after resolving the `Stack`/`Repository` in `Handler#stacks`, re-validate that the resolved repository's organization matches the organization whose secret validated the signature before performing any mutation.

### Proof of Concept
1. Attacker administers (or has compromised the webhook secret for) `org-a`, which is configured in this Shipit instance with its own `webhook_secret` via `Shipit.github_app_config('org-a')`.
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<arbitrary sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using org-a's known `webhook_secret` and POSTs to `/github/hooks` (the public webhook endpoint) with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the HMAC against org-a's secret — [1](#0-0)  — so the request passes.
5. `PushHandler#process` → `Handler#stacks` resolves `Repository.from_github_repo_name("org-b/victim-repo")` — [6](#0-5)  — and enqueues `sync_github` for org-b's stacks, even though the signature only ever proved knowledge of org-a's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
