### Title
Null pointer dereference (`msg.payload.outputs`) crashes full nodes with `bDryRunNewTriggers` enabled when a valid unit contains a non-inline "payment" message - ([File: network.js])

### Summary
`validation.js` allows a `"payment"` message to be validated as fully correct even when it carries no `payload` object at all (`payload_location: "none"` or `"uri"`). When such a unit also triggers an AA and the node runs with `conf.bDryRunNewTriggers` enabled, `network.js`'s `ifOk` handler blindly dereferences `msg.payload.outputs` for every message with `app === 'payment'`, including the payload-less one, throwing a `TypeError` that is never caught. This mirrors the CVE-2020-16599 pattern: a crafted, otherwise well-formed input causes an unchecked null/undefined access that crashes the process (denial of service), except here the trigger is a single posted unit rather than a crafted binary file.

### Finding Description
In `validation.js`, the payment-message content check only inspects `m.payload` when it is truthy, and unconditionally passes messages without a payload: [1](#0-0) 

This means a message such as `{app: "payment", payload_location: "none", payload_hash: "<valid-length hash>"}` (no `payload` field at all) is accepted as a valid message, because the payload-hash check for non-inline payloads simply `continue`s without requiring or validating any payload content: [2](#0-1) 

Meanwhile, `network.js`'s `handleJoint` → `ifOk` handler (triggered only after `validation.validate()` fully accepts the unit) does this, when the node has `conf.bDryRunNewTriggers` set, is not light, the unit is freshly posted (not part of a ball/catchup), and the unit contains at least one AA trigger: [3](#0-2) 

The `.filter(msg => msg.app === 'payment')` selects **all** payment messages, including a payload-less one, and then unconditionally accesses `msg.payload.outputs` for each — throwing `TypeError: Cannot read properties of undefined (reading 'outputs')` for the payload-less message.

This throw happens inside `ifOk: async function(objValidationState, validation_unlock){...}`: [4](#0-3) 

Since this async callback is invoked as a plain callback from `validation.validate()` (not awaited, no `.catch`), the thrown exception becomes an unhandled promise rejection. There is no `process.on('unhandledRejection', ...)` handler in production code (only in test files), so Node's default behavior for unhandled rejections applies, which in modern Node.js versions terminates the process — equivalent in effect to the explicit `process.on('uncaughtException', ...)` handler elsewhere in `network.js` that intentionally crashes the process to avoid inconsistent state: [5](#0-4) 

### Impact Explanation
Any single crafted (but validation-legal) unit posted to a full node that (a) is not light, (b) has `conf.bDryRunNewTriggers` enabled, and (c) has at least one output routed to an existing Autonomous Agent, can carry an additional benign-looking `"payment"` message with `payload_location: "none"` and no `payload`. This unit passes all of `validate()`'s checks, reaches the vulnerable dry-run code path, and crashes the node process with an unhandled `TypeError`. This is a concrete denial-of-service: "a network unable to confirm new units" if enough witnesses/full nodes run with this configuration, satisfying the required impact bar (node crash / unable to process units).

### Likelihood Explanation
The only precondition outside the attacker's control is the node operator's `bDryRunNewTriggers` config flag (used specifically to catch AA-trigger crashes proactively before they execute for real). Any node that enables this safety feature is directly exposed. The unit itself requires no special privileges — it is a normal payment unit posted by an unprivileged user, with one extra crafted "payment" message using `payload_location: "none"`, and an existing target AA address (trivial to satisfy on any live network with deployed AAs).

### Recommendation
In `network.js`, filter for payment messages that actually carry a payload before mapping `outputs`:
```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment' && msg.payload)
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
```
Additionally, consider tightening `validation.js`'s payment-message check at lines 245-255 so that a `"payment"` app message is always required to carry a `payload` (i.e., disallow `payload_location !== "inline"` for `app: "payment"` messages), and add a global `process.on('unhandledRejection', ...)` guard with proper logging/handling consistent with the existing `uncaughtException` handler, so that a single overlooked async throw does not silently take down the whole node.

### Proof of Concept
1. Run a full node with `conf.bDryRunNewTriggers = true` and `conf.bLight = false`.
2. Identify an existing AA address `AA_ADDR` on the network.
3. Compose and post a unit whose `messages` array contains:
   - message[0]: `{app: "payment", payload_location: "inline", payload: {outputs: [{address: AA_ADDR, amount: 1000}], inputs: [...] }, payload_hash: <correct hash>}` (a normal valid trigger to the AA).
   - message[1]: `{app: "payment", payload_location: "none", payload_hash: "<any 44-char valid base64 hash>"}` (no `payload` field).
4. This unit passes `validation.validate()` fully (per `validation.js:245-255`, the payload-less message is treated as valid).
5. Once `ifOk` fires in `network.js`, because `objValidationState.count_primary_aa_triggers > 0`, the code at `network.js:1271-1274` iterates both payment messages and throws `TypeError` on `msg.payload.outputs` for message[1].
6. The unhandled rejection terminates the node process.
