### Title
CCMenu Controller Bypasses ApiClient Stack Scoping, Allowing Stack-Scoped Tokens to Read Any Stack's Build Status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper defined in `Shipit::Api::BaseController` and, in doing so, drops the scoping that restricts a stack-scoped `ApiClient` token to only the single stack it was issued for. Any token with the `read:stack` permission — even one created and intended to be limited to one stack — can be used against this endpoint to read the deploy/build status of every stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting way to resolve the requested stack for an authenticated API client: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a specific stack (`current_api_client.stack_id?`), and only falls back to `Stack.all` for clients with no stack restriction (e.g. `UnlimitedApiClient` or a globally-scoped client). Every other API controller (`StacksController`, `TasksController`, `DeploysController`, etc.) inherits this `stack` method and therefore honours the per-token stack binding.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

Instead of calling the inherited `stacks.from_param!`, it calls `Stack.from_param!(params[:stack_id])` directly, i.e. it looks up the stack from the entire `Stack` table, ignoring `current_api_client.stack_id`. The only guard on the action is `require_permission :read, :stack`, which merely checks that the token's permission list contains the string `"read:stack"` — it does not check *which* stack that permission applies to: [3](#0-2) 

Equality that should hold but is broken:
`stack authorized by token (current_api_client.stack_id, when present)` == `stack actually touched by the action (params[:stack_id] resolved against Stack.all)`

Before the request: a stack-scoped token (e.g. fixture `here_come_the_walrus`, scoped to stack `shipit`, see `test/fixtures/shipit/api_clients.yml`) can only read state for stack `shipit` through every other controller.
After the request: the same token, hitting `GET /api/stacks/:stack_id/ccmenu.xml` with any other stack's `to_param`, receives that other stack's deploy status, last build label, and build time — data the token was never granted access to.

### Impact Explanation
This is an authorization-scope escalation: a legitimately issued, narrowly-scoped credential (intended by an administrator to expose CI status for one stack only, e.g. to an external CI status badge/aggregator) can be used to enumerate and read the deploy/build state of every stack managed by the Shipit instance, including stacks belonging to other teams/repositories. This falls under unauthorized read of stack state that a token was not authorized to touch.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token with the `read:stack` permission can trigger this by simply changing the `stack_id` path segment in the CCMenu XML request — no additional privilege, secret, or session is required beyond the token they already legitimately possess. The bypass is a straightforward one-line control-flow deviation (`Stack.from_param!` vs `stacks.from_param!`) with no other safeguard present.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it using the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id` binding, matching the behaviour of every other API controller.

### Proof of Concept
1. As an admin, create (or use) an `ApiClient` scoped to stack A (`stack_id` set) with permission `read:stack` (e.g. via `POST /stacks/A/ccmenu_url` or directly, matching fixture `here_come_the_walrus`).
2. Using that token's Basic-Auth credentials (`id--signature`), send: `GET /api/stacks/B/ccmenu.xml` where `B` is a different, unrelated stack the token was never scoped to.
3. Observe a `200 OK` response containing stack `B`'s CCMenu project XML (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token is only authorized (per its `stack_id`) to read stack `A`. [4](#0-3)
