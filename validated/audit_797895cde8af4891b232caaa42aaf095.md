### Title
L1 BTC lockup proofs in `register-for-bond` are not checked against the lockup's own maturity, letting a staker reuse an already-spendable (and potentially already-spent) Bitcoin lockup as bond collateral - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` / `get-l1-lockup-summary`, `stackslib/src/chainstate/stacks/boot/pox-5.clar:2032-2113`) only proves that a Bitcoin transaction with a matching P2WSH output/amount was once included in a given block header via a Merkle proof. It never checks the lockup's `unlock-burn-height` against the *current* Bitcoin height to confirm the timelock has not already matured, and there is no persistent, cross-call registry of consumed outpoints - only a per-call `seen-outpoints` accumulator scoped to a single `register-for-bond` fold.

### Finding Description
`register-for-bond` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:642-842`) computes `sats-total` via `verify-l1-lockups`, which folds over the caller-supplied lockup list using `get-l1-lockup-summary`/the accumulator function at `stackslib/src/chainstate/stacks/boot/pox-5.clar:2032-2113`. That function checks:
- `unlock-burn-height >= minimum-unlock-height` (a bond-specific minimum, not tied to "now")
- `unlock-burn-height < BITCOIN_LOCKTIME_THRESHOLD`
- the output script matches `construct-lockup-output-script`
- the output amount matches the claimed amount
- the outpoint hasn't been seen already **within this call** (`seen-outpoints`)
- the Merkle proof / block header are valid

None of these assert that the Bitcoin chain's current height is still below `unlock-burn-height`. Once that CLTV height passes, the `OP_IF ... OP_CHECKLOCKTIMEVERIFY` branch of the lockup script becomes spendable by `staker-unlock-bytes`, so the staker can withdraw the real BTC. Because the contract only verifies historical inclusion (not current UTXO status, which Clarity/Bitcoin-height oracles in this contract don't expose here), the exact same historical transaction/output/Merkle proof remains permanently valid to satisfy `verify-l1-lockups` for *any future* `register-for-bond` call, regardless of whether the BTC has since been spent.

There is also no map recording "this outpoint has already been used to back a bond" across separate transactions - `seen-outpoints` is a local accumulator, not persisted state (confirmed absent via search for any `l1-lockup-outpoints`/`used-outpoints` map in the contract).

### Impact Explanation
`sats-total` computed from an L1 proof gates `amount-ustx` sizing (`min-ustx-for-sats-amount`), the allowlist cap (`ERR_TOO_MUCH_SATS`), and `protocol-bonds-total-staked`, and it is recorded as the bond's `amount-sats` in `protocol-bond-memberships` (line ~791), which flows into signer weight / reward-eligibility accounting (`is-l1-lock: true` bonds skip sBTC custody transfer entirely - `roll-sbtc` moves `new-sbtc = u0` on the L1 path). If a staker can register (or re-register on a later, non-overlapping bond) using a lockup proof whose Bitcoin timelock has already matured and been withdrawn, the bond's declared `amount-sats` and associated signer/reward weight are backed by BTC that is no longer locked. This breaks the equality "signing weight / reward slots ≤ actually locked collateral," matching the in-scope High/Critical class: signing weight or reward slots exceeding locked value / sats credited by an L1 proof that were never (still) locked on Bitcoin.

### Likelihood Explanation
The attacker needs no privileged role - any allowlisted staker with a matured (or maturing) Bitcoin timelock output can exploit this simply by waiting past `unlock-burn-height`, withdrawing the real BTC on Bitcoin, and then submitting a fresh `register-for-bond` (for a subsequent, non-overlapping bond period, which the contract already permits as a "roll-over" or even as a fresh registration once any prior membership has ended) with the same historical proof. Building the required Merkle-proof/header data is already exercised by the repo's own integration tests (`stacks-node/src/tests/pox_5_integrations.rs`), showing the proof format is well understood and reusable; the only missing guard is a "not yet matured" / "not previously consumed" check.

### Recommendation
- Add an explicit check in `verify-l1-lockups`/`get-l1-lockup-summary` that the lockup's `unlock-burn-height` is still in the future relative to the current observed Bitcoin height (i.e., the CLTV has not matured), or otherwise obtain fresh proof that the UTXO is still unspent, before crediting `sats-total`.
- Persist consumed outpoints in a durable map (e.g. `l1-lockup-outpoints-used`) keyed by `{txid, output-index}` across all `register-for-bond` calls (not just within one call's fold), rejecting reuse with `ERR_DUPLICATE_LOCKUP_OUTPOINT` regardless of which staker or bond attempts it.

### Proof of Concept
1. Staker locks BTC into the timelocked P2WSH (`construct-lockup-output-script`) with `unlock-burn-height = H`, and submits `register-for-bond` for bond A with a valid Merkle proof - registration succeeds, `sats-total` credited.
2. Bond A completes/rolls over or ends; Bitcoin height advances past `H`. Staker spends the real BTC out of the P2WSH via `staker-unlock-bytes` (CLTV branch now unlocked).
3. Staker (now with the BTC no longer locked) calls `register-for-bond` again for a new bond B, resubmitting the *same* historical transaction/output/header/Merkle-proof tuple used in step 1.
4. `verify-l1-lockups`/`get-l1-lockup-summary` re-validates: script match ✓, amount match ✓, `unlock-burn-height >= minimum-unlock-height` for bond B ✓ (still the same fixed value from the original script), Merkle proof ✓, no *global* duplicate-outpoint state to reject reuse ✗ → `sats-total` is credited again for bond B even though the BTC is already spent/unlocked, giving bond B's membership `amount-sats` backing that no longer exists on Bitcoin.         (bond-index uint)
        (signer-manager <signer-manager-trait>)
        (amount-ustx uint)
        ;; Their BTC lockup info. If the response is `ok`, then
        ;; this is a list of outputs corresponding to their timelocks.
        ;; If the response is `err`, this is the amount of sBTC (in sats)
        ;; that they want to lock.
        (btc-lockup (response {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        }
            uint
        ))
        (signer-calldata (optional (buff 500)))
    )
    (let (
            (signer (contract-of signer-manager))
            ;; Compute the sats being staked for this bond.
            (sats-total (try! (match btc-lockup
                l1-lockups (verify-l1-lockups tx-sender bond-index l1-lockups)
                sbtc-amount (ok sbtc-amount)
            )))
            ;; Any bond the staker is currently a member of. Some value here
            ;; means this is a roll-over from an ending bond into a later one.
            (existing-membership (map-get? protocol-bond-memberships tx-sender))
            ;; sBTC currently custodied for the staker's existing bond (0 if
            ;; they have none, or if the existing bond is an L1 lock).
            (old-sbtc (get-staker-custodied-sbtc tx-sender))
            ;; sBTC this new bond needs custodied (0 on the L1 path).
            (new-sbtc (if (is-ok btc-lockup)
                u0
                sats-total
            ))
            ;; Any STX-only stake the staker has. Present means this
            ;; `register-for-bond` is a roll-over from an ending stx-only
            ;; stake into a bond.
            (existing-stake (map-get? staker-info tx-sender))
            (bond (unwrap! (map-get? protocol-bonds bond-index) ERR_BOND_NOT_FOUND))
            (allowance (unwrap!
                (map-get? protocol-bond-allowances {
                    staker: tx-sender,
                    bond-index: bond-index,
                })
                ERR_NOT_ALLOWLISTED
            ))
            (first-reward-cycle (bond-period-to-reward-cycle bond-index))
            (bond-start-height (bond-period-to-burn-height bond-index))
