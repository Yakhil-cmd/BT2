### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, allowing a stack-scoped token to read any stack's status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method in a way that bypasses the stack-scoping restriction enforced everywhere else in the API. An `ApiClient` token that is authorized (bound) to a single stack can be used to read the deploy status of *any* stack in the installation, not just the one it was issued for.

### Finding Description
`Shipit::Api::BaseController` restricts which stacks an `ApiClient` may act on via the `stacks` helper, which filters to `current_api_client.stack_id` when the client is scoped to a specific stack: [1](#0-0) 

Every other stack-scoped API controller (e.g. `StacksController`) resolves the requested stack through this scoped `stacks` relation, so a token whose `stack_id` is set to stack A cannot resolve/act on stack B — this is the binding: `ApiClient.stack_id` (the stack the token authorizes) must equal the stack the request actually touches.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves the parameter against **all** stacks: [2](#0-1) 

The `require_permission :read, :stack` check only validates that the token has the generic `read:stack` permission string (via `ApiClient#check_permissions!`): [3](#0-2) 

It never checks whether `stack_id` matches the requested stack — that check only exists inside the (bypassed) `stacks` scope. As a result, any client holding a token with `read:stack` permission, even one deliberately restricted to a single stack via the `stack:` association (as in the `here_come_the_walrus` fixture), can pass an arbitrary `stack_id` to `GET /api/stacks/:stack_id/cc_menu.xml` and receive the CC Menu XML — including `lastBuildStatus`, `lastBuildLabel`, `activity`, lock status — for a stack the token was never granted access to: [4](#0-3) 

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches": a token deliberately scoped to a single stack (a common pattern for handing out limited read-only credentials, e.g. to CI dashboards) is silently upgraded to read status information for every stack in the Shipit installation. This is an authorization-scope escape enabling unauthorized read of stack state across stack boundaries, matching the High-impact category "escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state[...]" pattern called out in the rules (here, a *scope-restricted* credential effectively becomes unrestricted read access).

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with the `read:stack` permission (regardless of whether it is scoped to a specific stack) and knowledge/guessing of another stack's `to_param` (repo/environment identifier, which is not secret). No privileged access, signing key, or session is needed beyond the token itself, which is exactly the kind of credential intentionally minted with limited scope (e.g. via `CCMenuUrlController`, which creates a `read:stack` client scoped to one stack).

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` collection instead of `Stack.from_param!` directly, i.e.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits the same `current_api_client.stack_id` restriction enforced by `BaseController`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A (`stack_id` set) with `permissions: ['read:stack']` (as in fixture `here_come_the_walrus`, scoped to `shipit`).
2. Using that client's `authentication_token`, issue: `GET /api/stacks/<Stack B's to_param>/cc_menu.xml?token=<token>` where Stack B is a different, unrelated stack (e.g. `cyclimse`, `soc`).
3. Observe the response returns HTTP 200 with Stack B's CC Menu XML (`lastBuildStatus`, `activity`, etc.), despite the token being authorized only for Stack A — confirmed by `CCMenuController#stack` at [5](#0-4)  never applying the `stacks` scope defined in [1](#0-0) .
