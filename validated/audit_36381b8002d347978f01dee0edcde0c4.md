### Title
CCMenuController#show reads arbitrary stack deploy history bypassing token's stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Every `Api::*Controller` subclass scopes stack lookups through `Api::BaseController#stacks`, which restricts results to `Stack.where(id: current_api_client.stack_id)` when the authenticating token is scoped to a specific stack. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping the `stacks` scope entirely, so a token scoped to one stack can read the deploy/rollback history of any other stack.

### Finding Description
The binding that must hold for every `Api::*Controller` is: `stack ∈ current_api_client-authorized set`, i.e. `stack == stacks.from_param!(params[:stack_id])` where `stacks` is defined in `app/controllers/shipit/api/base_controller.rb:74-76` as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. `Api::StacksController#stack` (app/controllers/shipit/api/stacks_controller.rb:87-89) correctly reuses this scoped `stacks.from_param!`.

`Api::CCMenuController` breaks the equality by redefining `#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) as `Stack.from_param!(params[:stack_id])` — an unscoped class-level lookup that ignores `current_api_client.stack_id` entirely. `#show` (lines 22-25) then calls `stack.deploys_and_rollbacks.last`, exposing deploy/rollback history for whatever stack the `stack_id` param names.

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which validates that the token's permission scope includes `:stack` reads — it does not verify that the *specific* stack being accessed matches `current_api_client.stack_id`. That ownership check only happens implicitly via the `stacks` scoped relation used by `stacks.from_param!`; `CCMenuController` never calls it, so no guard catches the divergence.

Attack: obtain (or otherwise possess) any valid `ApiClient` token that is scoped to stack A (`stack_id` set to A), then `GET /stacks/:owner/:repo/:env/cc_menu.xml?stack_id=<B>&token=<credentials>` (or via Basic Auth) where B is a private/internal stack not owned by that token. `Api::StacksController#show` would reject this with `Stack.from_param!` raising not-found because `stacks` excludes B, but `Api::CCMenuController#show` returns B's latest deploy/rollback status unauthorized.

### Impact Explanation
The attacker obtains unauthorized read access to another stack's deploy/rollback history (build/deploy status metadata) that is outside their token's authorized scope. This is a cross-tenant read of stack state, matching the "High - unauthorized read of stack state" impact category. It is fully repeatable against any stack ID reachable via the route, is not limited to one target, and requires no privileged credentials beyond a normal (even narrowly-scoped) API token.

### Likelihood Explanation
Precondition: possession of any valid `ApiClient` token scoped to some stack (a normal, low-privilege credential many integrations already hold, e.g. a CI status badge token). No GitHub secrets, webhook secrets, or session cookies are needed. The attacker only needs to guess or enumerate `stack_id`/repo-owner-name-environment identifiers, which are often predictable (repo name + branch/environment) or discoverable. Cost is a single HTTP GET request per target stack, fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, removing the private override entirely (or delegating to the inherited `BaseController#stack`) so it is bound by the same `current_api_client.stack_id` restriction as every other `Api::*Controller`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test 'show does not leak a stack outside the token stack_id scope' do
  owned_stack = shipit_stacks(:shipit)
  foreign_stack = shipit_stacks(:cyclid) # any stack not equal to owned_stack

  scoped_client = ApiClient.create!(permissions: %w[read], stack_id: owned_stack.id)

  # Api::StacksController correctly scopes and rejects the foreign stack
  authenticate_as(scoped_client)
  assert_raises(ActiveRecord::RecordNotFound) do
    get shipit.api_stack_path(foreign_stack)
  end

  # Api::CCMenuController ignores the scope and leaks the foreign stack
  get shipit.stack_cc_menu_path(
    foreign_stack.repository.owner, foreign_stack.repository.name, foreign_stack.environment,
    format: :xml, token: scoped_client.token
  )
  assert_response :success  # should be :not_found / :forbidden once fixed
end
```
This demonstrates the two controllers diverge on the exact same binding (`stack ∈ current_api_client-authorized set`) for the same token and foreign stack: `StacksController#show` enforces it via `stacks.from_param!` while `CCMenuController#show` does not, via `Stack.from_param!`.
