### Title
Webhook signature verification binds trust to an attacker-influenced `repository.owner.login`/`organization.login` field while stack/commit mutation logic trusts a different, unverified `repository.full_name`/`sha` field, allowing cross-organization forgery of push syncs and commit statuses - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, which is read directly from the unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Once the signature is accepted for that organization's secret, the raw JSON is handed to the event handlers, which act on a *different* field in the same unverified payload: `repository.full_name` (for stack selection) or `sha` (for global commit lookup), with no cross-check that the repository actually belongs to the organization that authenticated the request. [3](#0-2) [4](#0-3) 

### Finding Description
Shipit supports multi-organization GitHub configuration, where each organization has its own `webhook_secret` in `Shipit.github(organization:)`. The equality this design should enforce is:

`organization whose secret validated the signature == organization owning the repository/stack that gets mutated`

Before the signature is checked, the controller extracts `repository_owner` purely from the attacker-supplied body to decide *which* secret to verify against:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This only proves the requester knows the secret configured for *some* organization named in the payload — it does not prove the payload's other fields (`repository.full_name`, commit `sha`) genuinely belong to that organization. The endpoint accepts arbitrary raw HTTP POSTs (it is not restricted to GitHub's infrastructure), so anyone who knows one org's `webhook_secret` can freely craft the rest of the JSON body.

Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` resolves the target `Repository`/`Stack` purely from `payload.dig('repository','full_name')` — a value from the same unverified body, independent of `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github` for any `Stack` matching that `full_name`/branch, regardless of which organization's secret was used to authenticate the request. [6](#0-5) 

More severely, `StatusHandler#process` doesn't even scope by repository — it looks up commits **globally by `sha`** across the entire Shipit installation and writes an attacker-controlled CI status (`state`, `description`, `target_url`, `context`) onto every matching commit:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Similarly, `CheckSuiteHandler` scopes only to `stacks` derived from the same untrusted `repository.full_name`, and triggers `schedule_refresh_check_runs!` for any stack whose branch/sha match. [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate administrator of one small/low-value GitHub organization configured in Shipit (and thus knows or controls that organization's `webhook_secret`) can pass `verify_signature` while embedding a `sha` or `repository.full_name` that belongs to a completely different, higher-value organization/stack also hosted on the same Shipit instance. This allows:
- Forging a "success" commit status on an arbitrary commit SHA anywhere in the Shipit instance via `StatusHandler`, which can be used to satisfy deploy-gating checks (`Commit#create_status_from_github!`) and enable an unauthorized deploy, matching the "unauthorized deploy" impact criterion.
- Forcing `PushHandler`/`CheckSuiteHandler` to enqueue `GithubSyncJob`/`RefreshCheckRunsJob` for stacks/repositories the attacker does not control, causing cross-repository state changes/writes that were never authenticated for that repository's real organization.

This is a real cross-tenant boundary break specific to Shipit's own webhook trust model (organization-secret binding vs. repository-field trust), not a hypothetical or generic third-party issue.

### Likelihood Explanation
Requires the attacker to know a `webhook_secret` for at least one organization configured in the same Shipit instance (e.g., their own org, if Shipit is used as a shared multi-tenant deploy platform across several GitHub orgs/teams). No GitHub App private key, `ApiClient` token, or Shipit session is required — only a valid HMAC for one org's secret, which such an attacker legitimately possesses for their own organization's webhook. In any multi-organization Shipit deployment this is a plausible, low-effort attack path since the endpoint accepts arbitrary raw POSTs.

### Recommendation
- After resolving `repository_owner` and computing `stacks`/`Commit` lookups, verify that the resolved `Repository`'s owner/organization matches the `repository_owner` that was actually used to select the `webhook_secret` for signature verification.
- In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup to commits belonging to stacks/repositories owned by the authenticated organization, instead of a global sha lookup.
- In `Handler#stacks`, reject or ignore events where `Repository.from_github_repo_name(repository_name)`'s owner does not equal the verified `repository_owner`.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (attacker is an admin, knows its `webhook_secret`) and `victim-org` (has a Stack tracking `victim-org/critical-repo`, with commit `abc123` awaiting a required "ci" status check before deploy is allowed).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/critical-repo" },
  "sha": "abc123",
  "state": "success",
  "context": "ci",
  "description": "forged status"
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact raw body and POSTs it to `/github/webhooks` (or the mounted webhooks route) with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker-known secret. [8](#0-7) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds `Commit` `abc123` globally (belonging to `victim-org/critical-repo`) and writes the forged `success` status via `commit.create_status_from_github!(params)`, satisfying the CI gate for a deploy the attacker never had rights over. [4](#0-3)
