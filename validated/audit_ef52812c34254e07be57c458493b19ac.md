### Title
AAs can never send back fixed-denomination (indivisible) assets they receive, permanently trapping user funds - ([File: aa_composer.js])

### Summary
The Sherlock report describes a `receive()` function that accepts ETH but has no corresponding withdrawal path, permanently locking any Ether sent to it. The closest analog in ocore is at the protocol level: when an Autonomous Agent (AA) receives a payment in a **fixed-denomination (indivisible) asset**, the AA composer unconditionally strips out any outgoing `payment` message for that same asset before the response unit is built, so the AA can never forward, refund, or otherwise return that asset to anyone — including back to the sender who mistakenly sent it.

### Finding Description
When `handleTrigger()` builds an AA's response messages, each payment message's asset is looked up via `storage.loadAssetWithListOfAttestedAuthors`, and if the asset has `fixed_denominations` set, the composer simply defers processing without completing the payload: [1](#0-0) 

Immediately after all messages are processed, the composer performs a second filtering pass that **removes any payment message paying out a fixed-denomination asset entirely**, regardless of what the AA's oscript template intended to do with it: [2](#0-1) 

This means that no matter how the AA's `messages`/`state` logic is written — even if the author explicitly writes a `payment` message to refund `trigger.data.asset` back to `trigger.address` — that outgoing message is silently dropped by the core composer if the asset is indivisible (`fixed_denominations: true`). There is no way for an AA-level "withdraw" case to work around this, because the restriction is enforced by `aa_composer.js` itself before the response unit is finalized, not by the AA definition.

This is the direct ocore analog of the reported bug class: like the `receive()` payable function with no way to move funds back out, an AA is a "payable" address (any unprivileged unit poster/asset issuer can trigger it with a payment) that can accept an indivisible asset but core logic guarantees it can never emit a valid outgoing payment for that same asset.

### Impact Explanation
Any indivisible/fixed-denomination asset sent to an AA address becomes permanently and irrecoverably stuck at the AA balance, with no mechanism — not even bounce refunds, since `bounce()` in `aa_composer.js` composes payment messages for `trigger.outputs`, which for a fixed-denomination asset would be subject to the exact same filtering when the response unit is finalized. This is an AA fund-loss/freezing bug class explicitly listed as in-scope impact ("AA fund loss or freezing"). Since fixed-denomination assets are a first-class, protocol-supported asset type (see `test/samples/*.oscript` referencing `fixed_denominations`), and any asset issuer can create such an asset and any user/AA-trigger sender can send it to an AA, the attack surface is broad: a user (accidentally or an attacker griefing another party's AA) sending an indivisible asset to any AA permanently locks that value inside the AA with no possible recovery path, at any privilege level.

### Likelihood Explanation
Likelihood is high for accidental loss: any user or wallet UI that allows sending an indivisible asset payment to an AA address (which is a normal Obyte address, indistinguishable to a sender from a regular wallet address) will trigger this outcome. No special permissions or race conditions are needed — a single trigger unit carrying a fixed-denomination asset output to an AA is sufficient. AA authors cannot defend against this in oscript since the restriction is enforced unconditionally in the composer regardless of the AA definition.

### Recommendation
- At minimum, when an AA receives a fixed-denomination asset payment, bounce the trigger (refuse to accept it) rather than silently accepting the asset into the AA balance while making it permanently unspendable. This can be done by validating in `aa_composer.js`/`aa_validation.js` (or in `validateAATriggerObject`) that trigger outputs must not include fixed-denomination assets, causing such triggers to fail/bounce and return the funds via bounce-fee refund logic instead of accepting them into an address that can never move them again.
- Alternatively, extend `aa_composer.js` to allow limited egress of fixed-denomination assets from AAs (e.g., support the required indivisible-asset payment/spend-proof mechanics for AA-issued outgoing payments), so that AA templates that intend to forward/refund such assets can actually do so.

### Proof of Concept
1. Issue an asset with `fixed_denominations: true` (indivisible asset), as supported by `validateAssetDefinition` / test fixtures using `fixed_denominations`.
2. Deploy an AA whose `messages` include an unconditional case that, upon receiving `trigger.output[[asset=<indivisible_asset>]]`, emits a `payment` message paying the same amount of that asset back to `trigger.address` (a "withdraw"/refund case, analogous to `test/samples/order_book_exchange.oscript`'s "withdraw funds" case pattern but for an indivisible asset).
3. Post a trigger unit sending units of the indivisible asset to the AA address.
4. Observe in `aa_composer.js` (`handleTrigger` → the `async.eachSeries(messages, ...)` block) that `assetInfos[asset].fixed_denominations` is `true`, causing the payment message payload never to be completed (line 1327-1328), and then the final filter (line 1356) strips the payment message entirely from the composed response unit.
5. The response unit is generated without any payment refunding/forwarding the indivisible asset, while the AA's on-chain balance for that asset remains credited — the funds are stuck permanently with no code path in `aa_composer.js` capable of ever emitting a valid outgoing payment for a fixed-denomination asset from an AA.
