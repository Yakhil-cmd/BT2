### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository flip CI state for commits belonging to any other stack/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by bare SHA, with no check that the SHA belongs to the repository that produced the event. Because `Commit` rows are only unique per `(stack_id, sha)` and not globally, a legitimately-signed status event from repository A can flip the CI state (and thus `deployable?`) of an unrelated commit row belonging to repository B/stack B, ultimately enabling `stack.trigger_continuous_delivery` to ship code that repository B's own CI never approved.

### Finding Description
The broken invariant, stated as an equality that must hold but doesn't:
`commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` row mutated by a `status` event.

In `StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
this iterates over **every** `Commit` row in the entire database whose `sha` matches the payload, with zero reference to `params['repository']`. `Commit` `belongs_to :stack` [2](#0-1)  and is only unique per stack, so two different stacks (potentially backed by two entirely different GitHub repositories - e.g. a fork/upstream pair, a shared monorepo split into multiple Shipit stacks, or repositories that happen to share history) can each hold a `Commit` row with the identical `sha`.

`WebhooksController#verify_signature` only proves that the payload was genuinely signed by the GitHub App/organization named in `params['repository']['owner']['login']` (via `Shipit.github(organization: repository_owner)`), it never checks that the signing repository is the same repository that owns the matched `Commit`/`Stack`: [3](#0-2)  `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `requires :state`, `accepts :description/:target_url/:context`) likewise place no repository constraint on the handler. [4](#0-3) 

`create_status_from_github!` calls `add_status`, which persists the new status, and when the status transitions to `success`/`pending` it calls `stack.schedule_merges` and emits `deployable_status`/`commit_status` hooks: [5](#0-4) . `Commit#deployable?` is computed from this status (`success? && !blocked?`) [6](#0-5) , and `ContinuousDeliveryJob#perform` deploys whenever `stack.continuous_deployment?` and the stack is otherwise free, via `stack.trigger_continuous_delivery`: [7](#0-6) . Nothing in this chain re-validates which repository actually produced the status.

**Attack path**: an attacker who controls (or can push to/run CI on) any repository registered with Shipit under some GitHub organization/App can cause GitHub to emit a legitimately-signed `status` webhook (e.g., by wiring their own CI to post a `status` for a commit in their own repo, with `context`/`description`/`target_url` values of their choosing). If that commit's `sha` also exists as a `Commit` row for a different stack (shared history, fork/upstream, monorepo split, or simply reusing a known SHA that also exists elsewhere), the handler applies the attacker's `state`/`target_url`/`description` to that unrelated commit, marking it `success` in a repo/stack the attacker does not own and never authenticated against, which can trigger `trigger_continuous_delivery` for that other stack.

### Impact Explanation
This is a payload from one repository mutating another repository's commit/stack CI state, which can unblock or trigger an unauthorized deploy via `stack.trigger_continuous_delivery` - matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The blast radius spans any two stacks in the Shipit instance that ever share a commit SHA (a common occurrence for forks, upstream/downstream repos, or repos with common ancestor commits), not just repos in the same GitHub org as the attacker's signing repo.

### Likelihood Explanation
The attacker needs: (1) a repository already registered with Shipit and configured with a valid GitHub App/webhook secret for signing (this can be their own repo, satisfying "unprivileged" per the threat model — they only need to own/administer a repo that has Shipit wired to it, not the victim's repo), and (2) a commit SHA that also exists as a row in the victim stack (achievable via shared history, forked repos, or commit reuse). Given those, the attack is a single crafted/CI-driven `status` webhook and is fully repeatable against any matching SHA.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `check_suite`/`check_run` handlers if similarly unscoped) to commits whose owning stack's repository matches `params['repository']['full_name']` (or organization/repo id) from the verified payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.dig('repository', 'full_name') })`, rather than a bare global `sha` match.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or a new test if not already covering this):
1. Create `stack_a` bound to `Repository` `owner/repo-a`, and `stack_b` bound to `Repository` `owner/repo-b`.
2. Create `commit_a = shipit_commits(:...)` under `stack_a` with `sha = "deadbeef" * 5` and `commit_b` under `stack_b` with the **same** `sha`. Assert both currently have `state == "unknown"`/`deployable? == false`.
3. Build a `status` payload referencing `repository.full_name = "owner/repo-a"` and `sha = commit_a.sha`, `state: "success"`, `target_url: "http://attacker.example"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST through the controller with a valid signature for `owner/repo-a`).
5. Assert `commit_a.reload.state == "success"` (expected) **and** `commit_b.reload.state == "success"` / `commit_b.deployable?` becomes `true` even though the payload's `repository.full_name` was `"owner/repo-a"`, not `"owner/repo-b"` — proving `commit_b.stack.repository.full_name != payload['repository']['full_name']` yet the status was still applied, i.e., the equality binding is broken.
6. Optionally stub `Stack#trigger_continuous_delivery` on `stack_b` and assert it gets invoked/queued via `ContinuousDeliveryJob` as a result, demonstrating the deploy-triggering consequence.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      )

      ].join(' '))
    end
