## Analog Found

### Title
Unprivileged race to reveal a conflicting address definition can cause node disagreement / DoS on the affected address - (File: `validation.js`)

### Summary
The Allo report describes an unprotected, callable-once `initialize()` that any unprivileged actor can front-run to seize control of, or brick, a freshly deployed contract because there is no binding between the intended caller and the state-setting call. The closest reachable analog in `ocore` is the "first reveal wins" handling of address definitions: whoever's unit is first accepted into the DAG determines the definition recorded for an address, and a conflicting, near-simultaneous reveal by any other unprivileged unit author is explicitly flagged by the maintainers as capable of splitting nodes.

### Finding Description
When a unit's author includes an explicit `definition` field, `validateAuthor()` calls `validateDefinition()`, which looks up whether the address already has a stored/pending definition: [1](#0-0) 

- If nothing is found yet (`ifDefinitionNotFound`), the first unit whose definition hashes to the known `definition_chash` for that address "wins" and gets accepted — this is the legitimate case (definition_chash = address the first time it's used).
- If something is already found (`ifFound`), `handleDuplicateAddressDefinition()` is invoked, which currently unconditionally rejects the second, conflicting unit with `"duplicate definition of address ..."`, but leaves an explicit TODO acknowledging the race is unresolved: [2](#0-1) 

The comment `// todo: investigate if this can split the nodes` and `// in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition - the new definition will not be active yet` directly documents a scenario analogous to the Allo `initialize` front-run: an unprivileged unit poster can race the legitimate definition-revealing unit for an address (e.g. right after an `address_definition_change` is posted, or right when an address is first used) by broadcasting a conflicting unit that references/defines the same address. Because the outcome ("at most one of the balls will be declared good") depends on unit propagation/ordering rather than any binding authorization check, this is structurally the same class of bug as the reported issue: a state-initializing action lacking a caller-binding check, exploitable by whoever gets their unit accepted first or by racing a legitimate reveal.

The same "first reveal wins, no binding to an intended actor" pattern also appears in the generic definition lookup used when evaluating `['address', ...]` conditions inside other definitions/oscript conditions: [3](#0-2) 

### Impact Explanation
If two conflicting definitions for the same address are broadcast near-simultaneously (a legitimate reveal and a race by any other party who has independently learned of the pending change, e.g. via `address_definition_change` propagation), different nodes can end up disagreeing about which definition is authoritative before finality resolves it, per the maintainers' own "split the nodes" caveat. This maps to the required high-severity outcome category of "node disagreement on validity or stability" for the affected address, and until the fork is resolved, spends/authentications for that address may be rejected on some nodes and accepted on others (denial-of-service on that address's ability to transact), mirroring the Allo DoS impact.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an attacker to observe an in-flight `address_definition_change` (visible on the public DAG before stabilization) and quickly compose and broadcast a competing unit referencing the old/soon-to-be-superseded definition for the same address, similar to the resource/timing requirements described for the original Allo front-run (no funds needed, just network positioning/timing).

### Recommendation
Resolve the TODO in `handleDuplicateAddressDefinition()` (`validation.js:1486-1499`) with a deterministic, non-racy tie-breaking rule (e.g., always defer to the definition committed in the earliest-`main_chain_index`/best-parent unit, and require validators to reference that specific unit rather than accepting either of two unstable conflicting reveals as potentially "good"), and add a regression test that submits two competing definition-revealing units for the same address in quick succession to confirm that all nodes converge on the same outcome.

### Proof of Concept
1. Address `A` has its definition changed via `address_definition_change` to `new_chash`.
2. Before that unit stabilizes, party X (who is not the address owner and does not need any privileged role) constructs and submits their own unit referencing address `A` with a definition matching the *old* `definition_chash` (or a second unit racing to reveal a definition matching `new_chash` first).
3. Depending on propagation order, different nodes accept different reveals as `ifDefinitionNotFound`-first, hitting `handleDuplicateAddressDefinition()` on the losing branch for the conflicting unit — the exact scenario the code comment flags as a potential node split, analogous to the Allo `initialize` front-run causing inconsistent/unusable contract state.
