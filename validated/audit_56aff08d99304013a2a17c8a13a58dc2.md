## Title
Missing Enforcement of Minimum-Participation (Quorum) Threshold in System Parameter Voting (`countVotes`) - (File: `main_chain.js`)

## Summary
`countVotes()` in `main_chain.js` counts `system_vote` messages (posted by any address via a plain unit) to set global consensus/network parameters — `op_list` (order providers/witnesses), `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`. The function contains logic that is *intended* to expand the voting window until a minimum share of total supply (`SYSTEM_VOTE_MIN_SHARE`) has participated, but this check is never enforced as a hard gate: if the required participation share is never reached — even after scanning the entire voting history back to the very first vote — the code silently proceeds to apply the result computed from whatever (arbitrarily small) participation exists. [1](#0-0) 

## Finding Description
Any address can cast a `system_vote` unit; this is validated only for payload shape/value bounds, with no participation/supply checks at validation time. [2](#0-1) 

When an MCI stabilizes, `countVotes()` tallies votes weighted by each voter's stable-good BYTES balance and is supposed to require a minimum share of `TOTAL_WHITEBYTES` (`SYSTEM_VOTE_MIN_SHARE = 0.1`, i.e. 10%) to have voted before finalizing the result: [3](#0-2) 

The quorum logic is implemented as a "widen the window" loop:
```
let since_timestamp = mc_timestamp;
while (true) {
    since_timestamp -= 365 * 24 * 3600;
    if (since_timestamp <= activation_timestamp)
        break;
    const [{ total_balance }] = await conn.query(...); // sum of balances of addresses who voted since_timestamp
    if (total_balance >= constants.SYSTEM_VOTE_MIN_SHARE * constants.TOTAL_WHITEBYTES)
        break;
}
``` [1](#0-0) 

The loop only ever breaks in two ways: (1) the 10% share is reached, or (2) the window has been expanded all the way back to the timestamp of the very first vote ever cast for that subject (`activation_timestamp`). Critically, there is **no third branch that aborts/skips the vote count when case (2) occurs without reaching the 10% threshold**. Execution simply falls through to compute the result (median value for numeric subjects, top-`COUNT_WITNESSES` by balance for `op_list`) from whatever balance actually voted: [4](#0-3) 

The result is then written to `system_vars` and emitted to consumers (`storage.systemVars`) unconditionally — the same unconditional write happens for `op_list`: [5](#0-4) [6](#0-5) 

This is functionally the same root cause as the reported bug class: a quorum/participation constant is tracked and compared, but the comparison's negative outcome is never actually used to reject or ignore the vote — it is only used to decide whether to look further back in history. For subjects that rarely attract voters (e.g. `tps_fee_multiplier`, `tps_interval`, `threshold_size`, or even `op_list` on a low-activity network/devnet), the 10% share may never be reached across the entire vote history, yet the protocol will still adopt whatever value the small set of actual voters (weighted by held balance) produced.

## Impact Explanation
- `op_list` controls the set of order providers/witnesses used to determine main-chain stability; and the numeric subjects (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, `threshold_size`) directly control fee scaling and confirmation dynamics network-wide via `system_vars`.
- Because the intended 10%-of-supply quorum is not actually enforced, a small number of large-balance addresses (or even a single address with sufficient balance relative to the few other participants) can determine these protocol-wide parameters without meaningful, broad participation.
- Manipulating `tps_fee_multiplier`/`base_tps_fee`/`tps_interval` toward extreme (but individually-valid, per `validation.js` bounds) values can materially degrade the network's ability to confirm units economically, and manipulating `op_list` affects which addresses act as order providers for stability determination — both are high-impact governance/consensus effects.

## Likelihood Explanation
Reaching quorum requires no special privilege — any address that owns/holds bytes can post a `system_vote` unit, exactly as validated in `validation.js`. Low-attention subjects (esp. newly introduced numeric knobs, or `op_list` voting on lower-activity periods/subnets) are plausible real-world conditions where the 10% share is never reached, so the non-enforcement path in the loop at `main_chain.js:1807-1821` is a realistically reachable state, not merely a theoretical edge case.

## Recommendation
After the quorum-expansion loop, explicitly check whether the accumulated `total_balance` (or number of independent addresses of the voter set actually included) reached `SYSTEM_VOTE_MIN_SHARE * constants.TOTAL_WHITEBYTES`. If it does not, skip counting for that MCI/subject (retain the previous `system_vars` value) instead of silently finalizing a result derived from insufficient participation, mirroring the intent already expressed by `SYSTEM_VOTE_MIN_SHARE`.

## Proof of Concept
1. A protocol parameter subject (e.g. `tps_fee_multiplier`) is activated; only a handful of addresses (say two), holding a combined balance far under 10% of `TOTAL_WHITEBYTES`, ever cast a `system_vote` for that subject (`validation.js:1893-1907` allows any address to post this).
2. When `countVotes()` runs on stabilization, the while-loop at `main_chain.js:1807-1821` expands `since_timestamp` back to `activation_timestamp` (the first-ever vote for the subject) without ever satisfying `total_balance >= SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`, then exits the loop anyway.
3. `countVotes()` proceeds to compute the "majority" value using only the two low-balance voters' votes (`main_chain.js:1878-1902`) and unconditionally commits it to `system_vars` (`main_chain.js:1910`), changing a network-wide parameter despite ~0% actual quorum having been reached.
