### Title
CCMenu API endpoint scopes authentication to a stack-restricted `ApiClient` but never checks that scope against the requested stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` authenticates a request using a token that is designed to be permanently bound to a single stack (`ApiClient#stack_id`), but the controller's own `stack` lookup ignores that binding and resolves any stack ID supplied in the URL, breaking the equality "stack a token authorizes == stack it touches."

### Finding Description
`Shipit::CCMenuUrlController#client` creates (or reuses) a scoped `ApiClient` bound to one specific stack: [1](#0-0) 
That client is deliberately restricted with `permissions: %w[read:stack]` and `stack: <that stack>`, and its signed `authentication_token` is embedded in a CCTray URL intended to expose only that one stack's build status.

In the generic API base controller, stack lookups are always scoped through `stacks`, which filters by the authenticated client's bound stack when one is set: [2](#0-1) 

However, `Api::CCMenuController` overrides both `authenticate_api_client` (to accept the token from `params[:token]` instead of `Authorization`) and, critically, `stack`, resolving the stack directly against the entire table instead of the scoped `stacks` relation: [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks the permission string `"read:stack"` is present in the client's `permissions` array - it never compares `stack_id`: [4](#0-3) 

So the only enforcement that a CCMenu token is limited to "its" stack was supposed to come from the `stacks` scoping helper in `BaseController`, but `CCMenuController#stack` bypasses it entirely and calls `Stack.from_param!(params[:stack_id])` unconditionally. Any holder of a valid `here_come_the_walrus`-style scoped token (one legitimately obtained for stack A, e.g. by any teammate who visited stack A's page and hit `/ccmenu_url`) can substitute a different `stack_id` in the request path and read status for any stack in the installation, not just the one the token was scoped to.

### Impact Explanation
This is an unauthenticated-read escalation into stack state that a token was not supposed to expose: build/merge status (`lastBuildStatus`), running/build activity, latest deploy id (`lastBuildLabel`), and the stack's canonical URL for any stack, rendered via: [5](#0-4) 
This matches the "unauthorized read of stack state" High-severity class in scope: a token that authorizes reads of exactly one stack is usable to touch every other stack, cross-cutting the confinement the scoped `ApiClient` was designed to enforce. Compare with `Api::HooksController`, which correctly re-derives its scoping (`stack_id`) from the properly-scoped `stack` helper rather than bypassing it: [6](#0-5) 

### Likelihood Explanation
Any user with normal read access to at least one stack can trivially obtain a scoped CCMenu token for that stack via the standard UI flow (`CCMenuUrlController#fetch`), then reuse the same token with a different `stack_id` path segment to read other stacks' build state - no privileged access, GitHub credentials, or webhook secret is required beyond what an ordinary authenticated Shipit user already has for one stack.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `ApiClient#stack_id` binding is enforced consistently with the rest of the API surface.

### Proof of Concept
1. As a normal authenticated user with access only to `stack-a`, visit its page and trigger `GET /*stack_id/ccmenu` (routed to `CCMenuUrlController#fetch`) to mint a scoped token: this creates/reuses an `ApiClient` with `stack_id = stack-a.id`, `permissions = ["read:stack"]`, and returns a URL like `.../api/*stack_id/ccmenu?token=<TOKEN>`.
2. Take `<TOKEN>` and issue `GET /api/stack-b/ccmenu?token=<TOKEN>` for an unrelated `stack-b` the user has no legitimate access to.
3. `authenticate_api_client` accepts the token (valid signature via `ApiClient.authenticate`), `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack` (no stack-id check), and `stack` resolves `stack-b` directly via `Stack.from_param!(params[:stack_id])` - bypassing the `stacks` scoping that would have restricted it to `stack-a`. The response discloses `stack-b`'s build status, activity, and last deploy id.
