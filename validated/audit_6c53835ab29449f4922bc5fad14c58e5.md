Found it. `prosaic_contract.js`'s `handleReceivedSigningUnit` (unlike its sibling `arbiter_contract.js` version) confirms a contract's signing `unit` by checking only that the `unit`'s `data` message contains `payload.contract_text_hash === contract.hash`, but never validates that the shared-address author's authentifiers are actually a *mutual* signature from both parties. This is the same bug class as the reported "confirm without validating the identifying context matches the stored request" — here, a unit signed by only one party (attacker) can be accepted as final proof that a two-party prosaic contract was fully executed.

### Title
Prosaic contract signing-unit confirmation accepts non-mutually-signed unit as contract execution proof - (File: `prosaic_contract.js`)

### Summary
`handleReceivedSigningUnit` in `prosaic_contract.js` stores an incoming `unit` hash as the contract's final "signed" unit as soon as it finds a `data` message whose `payload.contract_text_hash` matches the contract hash and the `shared_address` is among the unit's authors. It never checks that both parties actually cosigned the unit (i.e., that `unit_authors.authentifiers` contains signatures for both signing paths `r.0` and `r.1` of the 2-of-2 `and` definition), unlike the equivalent `arbiter_contract.js` `handleReceivedSigningUnit`, which explicitly verifies `isMutuallySigned` via `signing_paths.find(p => p.startsWith('r.0.0')) && signing_paths.find(p => p.startsWith('r.0.1'))`.

### Finding Description
`prosaic_contract.js`'s shared address definition is a 2-of-2 `and` of `["address", offeror_address]` and `["address", acceptor_address]` (`deriveSharedAddress`, lines 114-138). Execution/acceptance of a prosaic contract is represented by a unit authored by the `shared_address` carrying a `data` message with `{contract_text_hash: contract.hash}`, set as the contract's `unit` field via `setField(contract.hash, "unit", unit)` (line 175): [1](#0-0) 

Compare this to the arbiter contract's version of the same function, which additionally requires: [2](#0-1) 

The prosaic contract path has no equivalent `isMutuallySigned` check. `unit_authors WHERE unit=? AND address=?` only proves the shared address participated as an author of some unit — a 2-of-2 `and` definition allows an incomplete/partial signature attempt to still be a syntactically valid "author" entry in an unconfirmed/invalid unit broadcast to the peer via the `prosaic_contract_update` device message (`wallet.js` case `'unit'`, lines 588-598), before validation of the full multisig actually completes on-chain. Because `handleReceivedSigningUnit` sets the contract's `unit`/status based purely on the presence of the `contract_text_hash` data message and shared-address authorship — not on verifying both cosigners' authentifier paths are present — a counterparty (or a malicious device message purporting to originate from the peer) can cause the local wallet to treat the contract as executed/signed prematurely, i.e., confirm contract completion without validating that the confirming unit actually carries the required cross-party (offeror+acceptor) authorization, mirroring the original report's core flaw: accepting a confirmation event without checking it truly matches/satisfies the expected authorization context of the stored request.

### Impact Explanation
A wallet can mark a prosaic contract as fully signed/executed (`unit` field populated, referenced in UI/wallet state as the executed contract) based on a unit that was never actually jointly authorized by both parties. Since prosaic contracts commonly gate fund releases from the shared address (`CHARGE_AMOUNT` deposits and subsequent payment logic reused across both contract types), a party could be misled into believing the counterparty's obligations were finalized/signed when the 2-of-2 authorization was never truly completed, leading to fund loss/freezing or the wallet acting on a false confirmation. This matches the "AA fund loss or freezing"/"unauthorized" impact category via the shared-address contract mechanism reachable directly from a peer device message.

### Likelihood Explanation
Likelihood is high for exploitation via any correspondent device able to send `prosaic_contract_update` messages once a contract is `accepted` and `shared_address` is set — the check is purely message-content-driven (`ValidationUtils.isValidBase64(body.value, ...)` in `wallet.js`) with no additional mutual-signature verification before invoking `handleReceivedSigningUnit`.

### Recommendation
Add the same mutual-signature check used in `arbiter_contract.js`'s `handleReceivedSigningUnit` to `prosaic_contract.js`'s version: after loading `author = objUnit.authors.find(a => a.address === contract.shared_address)`, verify `Object.keys(author.authentifiers)` contains authentifier paths for both `r.0` and `r.1` signing paths before calling `setField(contract.hash, "unit", unit)`.

### Proof of Concept
1. Two parties create a prosaic contract and derive the 2-of-2 shared address (`deriveSharedAddress`).
2. A malicious peer device sends a `prosaic_contract_update` message with `field: "unit"` referencing a unit where the shared address appears as an author (satisfying `SELECT 1 FROM unit_authors WHERE unit=? AND address=?`) and includes a `data` message with the correct `contract_text_hash`, but the authentifiers only cover the peer's own signing path (`r.0` or `r.1`), not both.
3. `handleReceivedSigningUnit` (`prosaic_contract.js:159-176`) finds the matching `unit_authors` row and matching `contract_text_hash`, and unconditionally calls `setField(contract.hash, "unit", unit)`, marking the contract as executed on the victim's wallet without verifying joint authorization — unlike `arbiter_contract.js`'s equivalent function which would reject this via its `isMutuallySigned` check.

```javascript
function handleReceivedSigningUnit(contract, unit, retry_count = 0) {
	db.query("SELECT 1 FROM unit_authors WHERE unit=? AND address=?", [unit, contract.shared_address], async function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`signing tx ${unit} not found in db after 10 retries, giving up`);
			console.log(`signing tx ${unit} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSigningUnit, 30000, contract, unit, retry_count + 1);
		}
		console.log(`signing tx ${unit} found in db, setting contract's unit`);
		const objUnit = await storage.readUnit(unit);
		const dataMessage = objUnit.messages.find(message => message.app === "data");
		if (!dataMessage)
			return console.log(`data message not found in purported prosaic signing unit ${unit}`);
		const { payload } = dataMessage;
		if (payload.contract_text_hash !== contract.hash)
			return console.log(`data message payload does not match contract ${contract.hash} in purported prosaic signing unit ${unit}`);
		setField(contract.hash, "unit", unit);
	});
```
