### Title
`Shipit::GitHubApp#verify_webhook_signature` fails open when `webhook_secret` is blank, letting any attacker forge webhooks for that organization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` immediately when the resolved organization's `webhook_secret` is blank, entirely skipping `SecureCompare.secure_compare`. Since `webhook_secret` is documented as optional and defaults to `nil`/blank in real configuration examples (and in the test dummy app itself), any org configured without a webhook secret accepts unsigned/arbitrarily-signed webhooks, and the attacker fully controls which org is targeted via the JSON payload.

### Finding Description
The claimed binding is: *"every org resolvable via `Shipit.github(organization:)` from attacker-controlled `repository_owner` has a non-blank `webhook_secret`."* This does not hold in general — it is false by default/config, not something guaranteed by the engine.

Code path:
- `Shipit::WebhooksController#verify_signature` resolves the GitHub App purely from attacker-supplied JSON: `github_app = Shipit.github(organization: repository_owner)`, where `repository_owner` reads `params.dig('repository', 'owner', 'login')` directly from the unauthenticated POST body. [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` looks up `github_app_config(organization)` from `secrets.github` by the attacker-supplied org name (case-insensitively) and constructs/caches a `GitHubApp` for it. [3](#0-2) 
- `GitHubApp#verify_webhook_signature` only reaches `SecureCompare.secure_compare(...)` when `webhook_secret` is present; otherwise it returns `true` unconditionally, before even checking the `X-Hub-Signature` header or algorithm: [4](#0-3) 

Root cause: the engine treats "no configured secret" as "trust everything" rather than "fail closed." This is not a hypothetical edge case — the setup docs explicitly say the webhook secret is "(optional)", the shipped example config files (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) all ship with `webhook_secret: # nil`, and the actual test dummy secrets file used across the test suite (`test/dummy/config/secrets.test.json`) sets `"webhook_secret": null`. [5](#0-4) [6](#0-5) 

Exploit flow: an internet attacker (no Shipit session, no secrets) POSTs to `/webhooks` with `X-Github-Event` set to a handled event (e.g. `push`, `status`) and a JSON body naming any organization that is configured in Shipit but has a blank `webhook_secret` (this covers both the "single org" default schema, e.g. the shipped test/dev configs, and any "newly-onboarded" org added under the multi-org schema before an operator fills in a secret). No `X-Hub-Signature` header, or any garbage value, is required — `verify_webhook_signature` returns `true` before ever parsing it. The request then reaches `WebhooksController#create`, which dispatches to `Shipit::Webhooks.for_event(event)` handlers exactly as if it were a legitimate signed GitHub delivery, e.g. enqueuing `GithubSyncJob` for a `push` event or writing a `Status` for a commit. [7](#0-6) 

Existing guards do not prevent this: `check_if_ping` and `drop_unhandled_event` only filter by event type, not authenticity; `verify_signature`'s only failure paths are an unverified signature (never reached when `webhook_secret` is blank) or `GithubOrganizationUnknown` (which only triggers for orgs absent from config, not orgs present but unsecured).

### Impact Explanation
For any organization configured in Shipit without a `webhook_secret` (the documented-optional, shipped-default state), an unauthenticated attacker can inject arbitrary forged webhook events (`push`, `status`, `check_suite`, `membership`, etc.) naming any repository/organization/branch/commit they choose in the JSON body. This can enqueue sync jobs, write commit statuses, or manipulate team membership for that org's stacks without ever possessing a real GitHub signature — an authentication bypass matching the Critical category ("forged webhook ... accepted"). Blast radius is scoped to organizations that lack a webhook secret, but is repeatable indefinitely and requires no attacker cost beyond an HTTP POST.

### Likelihood Explanation
Preconditions: the target Shipit installation must have at least one configured GitHub organization with a blank `webhook_secret`. This is not a rare or contrived state — it's the state shipped by the engine's own default/example configs and test fixtures, and is explicitly called out in `docs/setup.md` as optional, so real deployments that follow the documented quick-start or forget to set it (or are "newly onboarded" under the multi-org schema before secrets are filled in) are exposed. No attacker secrets or privileges are needed at all; the attack is a single unauthenticated POST.

### Recommendation
Change `GitHubApp#verify_webhook_signature` to fail closed when `webhook_secret` is blank instead of returning `true`, e.g. return `false` (or require operators to configure a mandatory, non-optional secret and refuse to boot/serve webhooks for an org without one). At minimum, log and reject unsigned webhooks rather than treating a missing secret as implicit trust.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "webhook is accepted without any valid signature when webhook_secret is blank" do
  # Binding under test: webhook_secret.present? == false for org 'shopify' in test/dummy secrets
  refute Shipit.github(organization: nil).send(:webhook_secret).present?

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=not-a-real-signature'
  body = JSON.parse(payload(:push_master)).to_json

  assert_enqueued_with(job: GithubSyncJob) do
    post :create, body:, as: :json
  end
  assert_response :ok # NOT :unprocessable_entity — SecureCompare.secure_compare was never invoked
end
```
This demonstrates the equality "webhook_secret present for attacker-resolved org" is false in the shipped test config, and that `verify_webhook_signature` short-circuits to `true`, letting the forged/garbage-signed webhook through to job enqueuing — the opposite of fail-closed.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
