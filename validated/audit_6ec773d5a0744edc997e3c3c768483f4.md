### Title
Overlapping `signing_request` events for multisig/multilateral signing can cause a confirmation dialog switch, leading to unauthorized signing of a malicious unit - (File: wallet.js)

### Summary
The Obyte wallet's device-message handler for the `"sign"` subject emits a `signing_request` event that the UI is expected to turn into a confirmation dialog [1](#0-0) . Because `signing_request` events for different units (potentially from different paired devices, i.e. cosigners in a shared/multisig address or counterparties in multilateral signing) are not ordered, deduplicated, or locked against each other by ocore itself, an attacker who is a cosigner or multilateral-signing counterparty can race a legitimate signing request with a malicious one so that the confirmation the user actually clicks approves the attacker's unit instead of the one the user intended to review — the same "last request wins / dialog gets silently swapped" bug class described in the Uniswap sidebar report.

### Finding Description
The `"sign"` case in `handleMessageFromHub` validates an incoming unsigned unit sent by a paired device (cosigner of a shared address, or counterparty of a multilateral/dumb-contract signing) and then, once `network.handleOnlineJoint` validates it, fires:
```
eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [1](#0-0) 

The code comment directly above this emit acknowledges the danger of overlapping confirmation requests, but only handles the case where multiple emits refer to the *same* unit:
```
// This event should trigger a confirmation dialog.
// If we merge coins from several addresses of the same wallet, we'll fire this event multiple times for the same unit.
// The event handler must lock the unit before displaying a confirmation dialog, then remember user's choice and apply it to all
// subsequent requests related to the same unit
``` [2](#0-1) 

Critically, ocore provides no serialization guarantee across *different* units/requests. The `"sign"` message is processed under `mutex.lock(["from_hub"], ...)` [3](#0-2) , but that mutex is released as soon as `callbacks.ifOk()`/`ifError()` fires — well before the actual `signing_request` event, which is deferred until the asynchronous `"validated-"+unit` event resolves [4](#0-3) . This means:
- A cosigner device (which any correspondent that is part of a shared/multisig address definition legitimately is) can send a benign-looking `sign` request for a transaction the user expects, quickly followed by a second `sign` request for a different, malicious unit spending from the same address.
- Both requests independently pass validation and independently fire `signing_request` at unpredictable, unsynchronized times, since each depends only on its own unit's validation completing.
- Because ocore never locks by *request* (only the comment suggests the UI should lock by *unit*, and only handles the identical-unit re-request case), nothing in the core prevents a second, unrelated `signing_request` from arriving and being surfaced to the user while they are in the process of confirming the first one.
- If the wallet UI (as in the Uniswap sidebar case) reuses a single confirmation surface for the most recent `signing_request`, the user's click intended for the honest transaction can end up approving—and producing a valid signature for—the attacker's unit instead.

This is architecturally identical to the reported bug class: a shared, single confirmation surface driven by an unordered stream of "the newest request replaces the current one" events, reachable by an unprivileged (from the wallet owner's perspective) but *authorized* correspondent — exactly matching the "paired device" reachability allowed by the rules.

### Impact Explanation
If exploited, a malicious cosigner or multilateral-signing counterparty can induce the victim to produce a valid authentifier/signature for a malicious unit (e.g., one that redirects shared-address funds to an attacker-controlled address, or approves an unfavorable multilateral contract) while believing they are confirming a different, legitimate transaction. Because the signature is cryptographically valid once produced, the resulting unit is fully spendable — this is concrete unauthorized spending from a shared/multisig address, satisfying the "unauthorized spending" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to already be a correspondent that is part of the address definition (a cosigner or multilateral counterparty) — a role explicitly permitted by the "paired device"/"private-payment counterparty" reachability rule — and to time a second `sign` request while the user has a pending confirmation for the first. This mirrors the report's own assessment ("hard to exploit because its timing must be precisely measured or guessed"), so likelihood is moderate: it doesn't require breaking any cryptography or bypassing validation, only racing two legitimately-triggered `signing_request` events, which any cosigner naturally has standing to send.

### Recommendation
- In ocore, associate each `signing_request` emission with a unique per-request identifier and require downstream handlers to process/queue signing requests in a strict order rather than allowing a newer request to preempt an older, unconfirmed one.
- Extend the unit-locking guidance in the comment at wallet.js so that a lock is held not just per-unit, but across the whole pending confirmation lifecycle for a given address, queuing new `signing_request` events from other units/addresses until the current one is resolved.
- Add an explicit "request queue depth" concept (as recommended in the source report) so the core can inform downstream UIs how many signing requests are outstanding, discouraging silent replacement of the currently displayed request.

### Proof of Concept
1. Set up a shared/multisig address with the victim and an attacker device as cosigners.
2. Attacker sends a legitimate-looking `sign` device message for unit A (a transaction the victim expects) to the victim's wallet, which triggers validation and (once validated) a `signing_request` event for unit A.
3. Immediately before the victim clicks "confirm," the attacker sends a second `sign` device message for unit B (spending shared funds to an attacker address) using the same shared address.
4. Because ocore does not serialize or queue `signing_request` events across different units, unit B's validation and `signing_request` emission can occur and be displayed by the UI in place of unit A while the victim clicks the confirmation button, causing the victim to sign unit B instead of unit A — see the emission and comment at [1](#0-0) .
