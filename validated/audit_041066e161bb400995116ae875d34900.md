### Title
Webhook signature verified against `repository.owner.login`, but the write is scoped by the untrusted `repository.full_name` field - allowing cross-organization commit-status/CI forgery ("Deploy Safe" bypass) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an incoming webhook against using `repository_owner`, taken from the still-unverified JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). But the actual database write performed by the handler that then processes the very same payload is scoped by a *different* field of the same untrusted body: `Handler#repository_name` (`payload.dig('repository', 'full_name')`), used to look up `Repository.from_github_repo_name` and thus the `Stack`s that get mutated. These two fields are never checked for consistency with each other.

### Finding Description
The route `POST /webhooks` (`config/routes.rb:14`) is public and unauthenticated by design; the only defense is the HMAC signature check in `WebhooksController#verify_signature`: [1](#0-0) 

That method picks the `GitHubApp` instance (and thus the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`: [2](#0-1) 

Crucially, in `lib/shipit/github_app.rb`, if the selected organization has no `webhook_secret` configured, verification is **unconditionally skipped**: [3](#0-2) 

Once the (possibly no-op) signature check passes, the raw JSON body is dispatched unchanged to the handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`). Every handler inherits from `Shipit::Webhooks::Handlers::Handler`, which determines the repository to act on using a *different* JSON key, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example, `StatusHandler` (handles the GitHub `status` event, i.e. CI/commit statuses that feed Shipit's `ci.require` deploy-safety checks) resolves target `Commit` records purely by `sha`, with no repository/stack ownership check at all beyond what `stacks`/`repository_name` implicitly provides via other handlers: [5](#0-4) 

`PushHandler` similarly resolves the target stacks via `Repository.from_github_repo_name(repository_name)` (i.e., from `repository.full_name`), not from `repository.owner.login`: [6](#0-5) [7](#0-6) 

**The binding being broken, as an equality:** `organization authenticated` (`repository.owner.login`/`organization.login`, used to pick the `webhook_secret`) must equal `repository written` (`repository.full_name`, used to pick the `Repository`/`Stack` acted upon). Nothing in the controller or in `Handler#repository_name` enforces this equality — they are read from two independent, fully attacker-controlled JSON fields in the same unauthenticated POST body.

### Impact Explanation
In a multi-organization Shipit deployment (`Shipit.github(organization: ...)`, `github_app_config`), an attacker who:
1. Knows (or controls) an organization configured in Shipit's `secrets.yml` with **no `webhook_secret` set** (or otherwise obtains/guesses a valid signature for any org, e.g. via a leaked secret for one org), and
2. Wants to affect a **different, secured** organization's stack,

can send a single POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to the unsecured/known org (so `verify_signature` passes trivially, since `verify_webhook_signature` returns `true` when `webhook_secret` is blank) while setting `repository.full_name` to the target victim org/repo that has real stacks configured. `Handler#repository_name` will resolve to the victim's `Repository`, and the handler will act on the victim's `Stack`s/`Commit`s — e.g., `PushHandler` triggering `Stack#sync_github`, or `StatusHandler` injecting a forged `commit_status` on the victim's commit. Forged commit statuses directly influence Shipit's deploy-safety mechanism (`ci.require` in `shipit.yml`), which gates whether a deploy is allowed to proceed — this can be used to mark a commit as CI-green when it is not, enabling an **unauthorized deploy** through the standard UI/API flow once the (bogus) CI gate is satisfied. This satisfies the report's Critical-tier impact bucket ("an unauthorized deploy") since the write is cross-organizational and driven purely by unauthenticated request data.

### Likelihood Explanation
This requires:
- A Shipit instance configured for multiple GitHub organizations (documented, supported feature: `docs/setup.md` "Using Multiple Github Applications").
- At least one configured organization lacking a `webhook_secret` (explicitly shown as an allowed/blank config value in every example, e.g. `config/secrets.development.example.yml:11`, `test/dummy/config/secrets_double_github_app.yml:7`), OR an attacker who has obtained any single org's webhook secret (much lower bar than compromising the target org's secret).
- No repository/GitHub-App-write-access requirement, no session, no API token — the webhook endpoint is designed to be reachable by anyone claiming to be GitHub.

Given that `webhook_secret` is optional per the documented config schema and Shipit explicitly supports it being unset, this is readily reachable without any privileged credential, satisfying the "unprivileged attacker" scope constraint.

### Recommendation
- In `Handler#repository_name`/`stacks`, cross-check that the resolved repository's `owner` matches the organization whose secret was used to authenticate the request (i.e., thread the verified `repository_owner`/organization through to the handler and assert `repository.full_name.split('/').first == authenticated_organization`).
- Do not allow `verify_webhook_signature` to silently accept unsigned webhooks for organizations with a blank `webhook_secret` when other organizations in the same install are configured with secrets; at minimum, warn/deny cross-tenant writes when signature verification was a no-op.
- Reject webhooks where `repository.owner.login` and the owner portion of `repository.full_name` disagree, before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `unsecured-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`, has a real `Stack` for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "unsecured-org" },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "unsecured-org" } },
  "sha": "<victim-repo commit sha awaiting CI>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header (or any value) is required, since `verify_webhook_signature` returns `true` when `unsecured-org`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the `Commit` by `sha` (global lookup, not scoped to `repository.full_name` at all in this handler) and records a fabricated successful `commit_status`, which can satisfy `ci.require` on `victim-org/victim-repo`'s stack and unlock deployment through the normal UI.

Note: I was unable to fully trace whether every downstream consumer of `commit_status`/`Commit` additionally re-scopes by repository elsewhere in `app/models/shipit/commit.rb` or `app/models/shipit/deploy.rb` (not indexed in this pass); a Devin session with full repository access should verify the exact `Commit`→`Stack` scoping chain to confirm no additional owner check exists there that would block this specific `StatusHandler` path, though the core signature/write binding mismatch in `WebhooksController` and `Handler#repository_name` is confirmed directly from the cited code.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
