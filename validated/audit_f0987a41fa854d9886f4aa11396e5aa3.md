### Title
Hardcoded NEP-141 Storage Deposit Amount in the Wallet Contract Breaks ERC-20 Transfer Emulation if `storage_amount_per_byte` Changes - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit account "Wallet Contract" hard-codes the amount of NEAR it attaches when registering an unregistered receiver with a NEP-141 token (`storage_deposit`). This constant is derived from the *current* value of the protocol-wide `storage_amount_per_byte` runtime parameter, baked directly into the wallet contract's WASM binary rather than being computed dynamically or read from governance-controlled config. Because `storage_amount_per_byte` is itself a governable runtime parameter that has changed historically, any future change invalidates the hard-coded constant for every eth-implicit account already deployed on the network, with no way to fix it short of a coordinated contract redeployment.

### Finding Description
`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` defines: [1](#0-0) 

The comment explains the rationale: rather than querying `storage_balance_bounds` on-chain, the contract hard-codes `1_250 * MICRO_NEAR` (i.e. `1.25 * 10^21` yoctoNEAR ≈ 0.00125 NEAR) as "the" NEP-141 storage deposit value, assuming this is what "essentially all tokens use."

This value is only correct because it equals `bytes_for_one_account_entry * storage_amount_per_byte`, where `storage_amount_per_byte` is a network-wide, governance-adjustable runtime parameter. The parameter has in fact changed across NEAR's history — the genesis mainnet config used `100000000000000000000` (`10^20`) yoctoNEAR/byte, while the current runtime-config snapshots use `10000000000000000000` (`10^19`): [2](#0-1) [3](#0-2) 

The hard-coded constant is used to fund the `storage_deposit` call whenever the wallet contract emulates an ERC-20 transfer (`EthEmulationKind::ERC20Transfer`) to a previously-unregistered receiver: [4](#0-3) 

Because the wallet contract's code is deployed once per eth-implicit account and is not meant to be redeployed or governed after deployment (it is the standard, immutable bytecode used across every eth-implicit account), if `storage_amount_per_byte` is later increased (as it has previously changed by 10x between genesis and later configs), every already-deployed wallet contract instance will attach an insufficient deposit relative to the actual `storage_balance_bounds.min` required by standard NEP-141 contracts.

### Impact Explanation
If the protocol-level `storage_amount_per_byte` increases relative to the value assumed when the wallet contract was compiled, the `storage_deposit` call issued on behalf of the user will underfund the receiver's registration. Standard NEP-141 implementations reject `storage_deposit` calls whose attached deposit is below `storage_balance_bounds.min`, causing that action — and consequently the chained `ft_transfer` action targeting the still-unregistered receiver — to fail. This breaks ERC-20 transfer emulation for all eth-implicit accounts network-wide for any unregistered receiver, with no governance lever to correct the now-stale constant except redeploying new wallet contract code (which does not retroactively fix already-deployed, already-relied-upon wallet accounts). This mirrors the reported bug class: a hard-coded, non-governable assumption about token/config pricing baked into deployed code becomes systemically wrong once the real economic parameter it depends on diverges, and — unlike the Solidity report's contracts — there is no governance function at all to adjust it after deployment.

### Likelihood Explanation
`storage_amount_per_byte` is a `RuntimeConfig` parameter that can be changed by protocol governance/upgrades (as evidenced by the genesis-to-current-snapshot discrepancy of 10x). The wallet contract, however, is fixed bytecode shared by every eth-implicit account on the network. Any future adjustment to this economic parameter — a normal, expected protocol governance action, not an attack — will silently desynchronize the hard-coded constant from the real requirement, affecting all existing wallet-contract instances at once.

### Recommendation
Avoid hard-coding the NEP-141 storage deposit amount. Either (a) query `storage_balance_bounds` on the target token contract before performing `storage_deposit` (accepting the extra cross-contract call), or (b) compute the deposit dynamically from the current `storage_amount_per_byte` protocol parameter (exposed to contracts, e.g. via a host function or genesis/config query) rather than baking a numeric constant into the contract binary, so that already-deployed wallet contracts remain correct as the protocol parameter evolves.

### Proof of Concept
1. Assume the network currently has `storage_amount_per_byte = 10_000_000_000_000_000_000` (10^19), matching the wallet contract's hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT = 1.25 * 10^21` yoctoNEAR (125 bytes worth).
2. Governance upgrades the protocol and raises `storage_amount_per_byte` to `100_000_000_000_000_000_000` (10^20), as has previously been the case at genesis (see `utils/mainnet-res/res/mainnet_genesis.json`).
3. A standard NEP-141 token contract, whose `storage_balance_bounds.min` is computed dynamically from the live `storage_amount_per_byte`, now requires `1.25 * 10^22` yoctoNEAR (10x the hard-coded amount) to register a new account.
4. A user submits an RLP-encoded ERC-20 `transfer` transaction through their eth-implicit `WalletContract` to a receiver who has never held that token.
5. `nep_141_storage_balance_callback` observes `storage_balance_of` returns `None` and issues `storage_deposit` funded only with the stale `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1x the now-required 10x amount): [5](#0-4) 
6. The token contract rejects the underfunded `storage_deposit`, so the chained `ft_transfer` action also fails because the receiver remains unregistered — breaking the transfer for every eth-implicit account on the network until every deployed wallet contract instance is somehow migrated.
