## Title
Payment `transfer_condition` Can Be Bypassed by Attaching an `issue` Input to the Same Payment Message - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` selects which asset-level spending condition to enforce — `issue_condition` or `transfer_condition` — using a single ternary keyed off whether *any* input in the payload happens to be an `issue` input, exactly the same "single boolean picks one of two mutually-exclusive checks for a multi-action message" pattern described in the reference report for `bucket_cdp/sources/vault.move`. Because one payment message is allowed to combine an `issue` input together with ordinary `transfer` inputs, an attacker can force the weaker (or entirely absent) `issue_condition` to be evaluated instead of the `transfer_condition` that was meant to gate the transfer of restricted coins.

### Finding Description
In `validatePayment()`, `bIssue` is computed once per message from the first input only: [1](#0-0) 

The comment above the input-processing loop explicitly confirms multiple input types are allowed together in one payment message: "max 1 issue must come first, then transfers, then hc, then witnessings": [2](#0-1) 

The `transfer` case is processed in the same loop right after `issue`, and both contribute to the same `total_input`/`total_output` balance for the message: [3](#0-2) 

After the loop finishes, exactly one condition is chosen based on the single, message-wide `bIssue` flag — not per-input: [4](#0-3) 

If `bIssue` is true, `transfer_condition` is never evaluated at all, regardless of how many restricted-address transfer inputs are also present in the same payload. If the asset issuer never defined an `issue_condition` (it's optional), `arrCondition` is `undefined` and the check is skipped entirely via `if (!arrCondition) return cb();`.

This mirrors the reported vault.move flaw precisely: an `if/else` (here a ternary) is used to gate two logically-independent operations that can both be present in a single request, so satisfying the "issue" branch's cheap condition suppresses the "transfer" branch's stricter condition, even though real transfers of value are still happening.

### Impact Explanation
Assets on Obyte can define a `transfer_condition` to restrict who may move coins (e.g., only to/from attested/whitelisted addresses, KYC-gated tokens, cosigned transfers, etc.), independent of `issue_condition`, `issued_by_definer_only`, or `cosigned_by_definer`. As long as `issued_by_definer_only` is not set (issuance is open, which is common — many assets restrict transfer but not issuance, or simply never set `issue_condition`), any author can add a minimal `issue` input (any positive amount is legal for uncapped assets) to the same payment message that also spends/transfers restricted coins from other addresses (as `transfer` inputs) they control. Because `bIssue` becomes `true`, the entire `transfer_condition` enforcement is skipped, letting the attacker move otherwise-restricted asset balances to arbitrary addresses. This is unauthorized spending / bypass of an asset's access-control policy — a supply/ownership integrity violation for any custom asset relying on `transfer_condition`.

### Likelihood Explanation
Trivially reachable by any unprivileged unit poster: they only need to author a `payment` message for a custom asset that (a) is not capped/`issued_by_definer_only`, and (b) defines a `transfer_condition` (with or without an `issue_condition`). No special privileges, mining power, or race conditions are required — a single, correctly-signed unit demonstrates the bypass.

### Recommendation
Replace the single ternary with independent, per-input-type enforcement: evaluate `issue_condition` whenever the payload contains an issue input, and independently evaluate `transfer_condition` whenever the payload contains one or more transfer inputs, in the same message:
```js
async.series([
    function(cb){
        if (!bIssue || !objAsset.issue_condition)
            return cb();
        Definition.evaluateAssetCondition(conn, payload.asset, objAsset.issue_condition, objUnit, objValidationState, ...);
    },
    function(cb){
        if (!bHaveTransfer || !objAsset.transfer_condition) // bHaveTransfer = any input with type "transfer"
            return cb();
        Definition.evaluateAssetCondition(conn, payload.asset, objAsset.transfer_condition, objUnit, objValidationState, ...);
    }
], callback);
```
This ensures a message combining issue and transfer inputs must satisfy both conditions independently, rather than allowing the cheaper branch to suppress enforcement of the other.

### Proof of Concept
1. Definer creates a divisible, uncapped custom asset with `issued_by_definer_only: false`, no `issue_condition`, and a strict `transfer_condition` (e.g., `['seen', {...attestation filter...}]`) intended to restrict who may receive transferred coins.
2. Attacker (who is not attested/whitelisted) already owns some units of this asset (received before or via any means) and wants to send them to an arbitrary, non-whitelisted address, which `transfer_condition` should forbid.
3. Attacker composes a single `payment` message for this asset whose `inputs` array starts with an `issue` input (index 0, any legal positive amount since the asset is uncapped) followed by a `transfer` input spending their own restricted coin, and whose `outputs` sum to `total_input` (issued + transferred amount) sent to the arbitrary target address.
4. In `validatePayment()`, `bIssue = (payload.inputs[0].type === "issue")` evaluates to `true`.
5. In `validatePaymentInputsAndOutputs()`, `arrCondition = bIssue ? objAsset.issue_condition : objAsset.transfer_condition` resolves to `objAsset.issue_condition`, which is `undefined`, so `if (!arrCondition) return cb();` skips all condition checking — the unit validates successfully despite violating `transfer_condition`.
