Based on my research, I found a strong structural analog to the OmniX "optimistic peer/destination assumption" bug in Sui's native bridge Move module, though I was unable to fully confirm one implementation detail (`send_token_internal`'s body) before running out of tool budget — I note that explicitly below.

### Title
Unvalidated `target_chain` in `bridge::send_token`/`send_token_v2` permits permanent locking of bridged funds - (File: crates/sui-framework/packages/bridge/sources/bridge.move)

### Summary
The Sui native bridge's outbound entry points, `send_token` and `send_token_v2`, accept an arbitrary `target_chain: u8` from any unprivileged caller and immediately lock the user's `Coin<T>` into the bridge's treasury/escrow via `send_token_internal`, without first validating that `target_chain` is a real, supported chain id or that `(inner.chain_id, target_chain)` forms a valid route. This mirrors the OmniXMultisender bug: the sending side optimistically assumes the destination is valid, while only the receiving/claim side enforces strict validation.

### Finding Description
`send_token<T>` [1](#0-0)  and `send_token_v2<T>` [2](#0-1)  take a caller-supplied `target_chain: u8` and only validate `target_address.length()` and that the token amount is non-zero, then call `inner.send_token_internal(target_chain, token, message)` which locks the coin and emits a `TokenDepositedEvent`/`TokenDepositedEventV2`. Neither function calls `chain_ids::assert_valid_chain_id(target_chain)` nor `chain_ids::is_valid_route`/`get_route(inner.chain_id, target_chain)` before committing the deposit.

By contrast, the claim/receive path in `claim_token` explicitly enforces `assert!(target_chain == inner.chain_id, EUnexpectedChainID)` and then calls `chain_ids::get_route(source_chain, target_chain)`, which aborts with `EInvalidBridgeRoute` if the (source, destination) pair is not one of the hardcoded `valid_routes()` [3](#0-2) [4](#0-3) . Other governance-message constructors (emergency op, blocklist, bridge-limit update, add-tokens) all call `assert_valid_chain_id` up front, as confirmed by dedicated abort tests [5](#0-4) , but the user-facing token-send path has no equivalent check on `target_chain` in the code I was able to inspect.

This is the same root-cause pattern as the reported bug: the entity that emits an outbound bridge request optimistically assumes the destination is valid/known, while the counterpart that consumes the request enforces strict validation — creating an asymmetry that can strand user funds.

### Impact Explanation
If a user (or a front-end bug/misconfiguration) calls `send_token`/`send_token_v2` with a `target_chain` that is not a supported `BridgeChainId` (e.g., an arbitrary `u8` value outside `{0,1,2,10,11,12}`) or with a valid chain id that does not form a registered route with the current chain (per `chain_ids::valid_routes()`), the deposited coin is already locked/escrowed in the bridge's `treasury` at the moment `send_token_internal` executes. The off-chain bridge committee would only sign approval for messages that can pass `chain_ids::get_route` on the receiving side; a message with an invalid route can never be claimed, since `claim_token` will abort on `get_route`. There is no visible on-chain mechanism in the inspected code for a sender to cancel a pending, permanently-unroutable deposit and reclaim their coin. This results in **permanent fund lock**, which is an explicitly listed High/Medium HackenProof impact for this scope.

### Likelihood Explanation
Likelihood is comparable to the original report's assessment: most users interact through a front-end that supplies correct `target_chain` values, making accidental misuse unlikely, but any integrator, script, or bridge SDK bug could trigger it, and there is no on-chain safety net once the coin has been locked.

### Recommendation
Add `chain_ids::assert_valid_chain_id(target_chain)` and `chain_ids::is_valid_route(inner.chain_id, target_chain)` checks (aborting on failure) at the top of `send_token` and `send_token_v2`, before any coin is moved into `send_token_internal`, mirroring the validation already performed in `claim_token`.

### Proof of Concept
1. Call `bridge::send_token<T>(bridge, target_chain = 99 /* not in {0,1,2,10,11,12} */, target_address, coin, ctx)`.
2. Observe that no assertion fires: `target_address.length()` and `token_amount > 0` pass, and `send_token_internal` locks the coin and increments the sequence number, emitting `TokenDepositedEvent { target_chain: 99, ... }`.
3. The bridge committee/node, upon observing this event, cannot produce a valid claim message because `claim_token`'s `chain_ids::get_route(source_chain, 99)` will abort with `EInvalidBridgeRoute` for any counterpart chain.
4. The user's coin remains locked in the bridge treasury indefinitely with no on-chain path to reclaim it.

**Caveat / uncertainty:** I was not able to fully retrieve and inspect the body of the private `send_token_internal` function within my tool budget to conclusively rule out that chain-id validation happens there rather than in `send_token`/`send_token_v2`. If `send_token_internal` (or a helper it calls) does perform `assert_valid_chain_id`/`is_valid_route` before locking the coin, this finding would be invalidated. I recommend a Devin session with full repo access specifically inspect `send_token_internal`'s complete implementation in `crates/sui-framework/packages/bridge/sources/bridge.move` to confirm or refute this before treating the finding as final.
