### Title
Cross-stack read via `Api::CCMenuController` bypasses the stack scope bound to an `ApiClient` token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` re-implements its own `stack` lookup instead of reusing `Api::BaseController#stack`, and in doing so drops the scoping that ties an `ApiClient` token to the single stack it was issued for. Any client holding a `read:stack`-permitted token — including one explicitly scoped to a single stack (`stack_id` set on the `ApiClient` record) — can read the CI/build status (`ccmenu`) of any other stack in the installation simply by supplying a different `stack_id` in the URL.

### Finding Description
`Api::BaseController` defines the authoritative binding between an authenticated `ApiClient` and the stacks it is allowed to act on: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` is derived from that restricted relation via `stacks.from_param!(params[:stack_id])`. This is the intended equality: `token.authorized_stack == stack_the_request_touches`.

`Api::CCMenuController`, however, overrides `stack` and `authenticate_api_client` and never applies this restriction: [2](#0-1) 

Its `stack` method calls `Stack.from_param!(params[:stack_id])` directly — bypassing `current_api_client.stack_id` entirely — while still only requiring the generic `read:stack` permission (`require_permission :read, :stack`), which `ApiClient#check_permissions!` validates purely against the `permissions` array, with no notion of which stack the permission applies to: [3](#0-2) 

So the binding that should hold — "the stack a token is authorised for" equals "the stack the request touches" — is broken specifically in this controller. `Api::BaseController#stack` enforces it; `Api::CCMenuController#stack` does not.

### Impact Explanation
An `ApiClient` created and scoped to a single stack (as the fixture `here_come_the_walrus` demonstrates, `stack: shipit`, `permissions: ['read:stack']`) is meant to only ever see that one stack, as proven by the existing test suite for other endpoints: [4](#0-3) 

But because `CCMenuController#stack` doesn't go through the `stacks` scoping, that same client's token can be replayed against `/api/stacks/*stack_id/ccmenu` for a completely different, unauthorized stack and successfully retrieve its build/deploy status (name, last build status, last build label, web URL, lock status), i.e. `render('shipit/ccmenu/project', locals: { stack:, deploy: latest_deploy })` in: [5](#0-4) 

This is an unauthenticated-for-that-resource read of stack state (build status, lock reason, activity) belonging to a repository/stack the token holder was never granted access to, matching the in-scope "unauthenticated read of stack state" High-impact category. It does not require any elevated credentials beyond a legitimately-issued, narrowly-scoped read token — exactly the kind of token an integrator would deploy to a low-trust consumer (e.g., a CI status badge/widget) believing it was constrained to one stack.

### Likelihood Explanation
Likelihood is fairly high for a possessor of any valid `read:stack` `ApiClient` token, scoped or not:
- No special privilege is needed beyond having a token with the generic `read:stack` permission bit.
- The stack ID is a simple, guessable/enumerable URL path segment (`owner/repo/environment`), not a secret.
- `CCMenuController` also supports authenticating purely via a `token` query-string parameter (`can authenticate with query string token`), which further widens where such tokens could leak/be embedded (e.g., in a CI dashboard URL), making exploitation via a leaked scoped token realistic.

### Recommendation
Have `Api::CCMenuController#stack` reuse the same stack-scoping logic as `Api::BaseController` (i.e., resolve through `stacks.from_param!(params[:stack_id])` rather than `Stack.from_param!`), so that a client whose `ApiClient#stack_id` is set can never resolve to a different stack, restoring the binding between the token's authorized stack and the stack actually served.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack A>.id` with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`).
2. Authenticate as that client (Basic Auth or `?token=`) against `GET /api/stacks/<owner>/<repoB>/<envB>/ccmenu`, where stack B is a different, unrelated stack.
3. Observe `200 OK` with `Api::CCMenuController#show` rendering stack B's CCMenu XML (name, lastBuildStatus, etc.), despite the client only being authorized for stack A — confirmed by contrasting with `Api::BaseController#stack`'s scoped behavior used by every other API controller (e.g., `Api::StacksController`, `Api::TasksController`), where the same scoped client cannot see stack B (`test/controllers/api/stacks_controller_test.rb:217-223`).

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
