### Title
Webhook signature verification keyed by attacker-controlled `repository.owner.login` allows an unconfigured/foreign org to authorize webhook events for any other org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report's bug class is: a value the system trusts as "verified" is not the same value the system actually acts on. In `WebhooksController`, the field used to select *which* GitHub App/secret verifies the request's signature (`repository.owner.login`) is different from the field the event `Handler` classes use to locate and mutate state (`repository.full_name`). Both fields come from the same unauthenticated-until-verified JSON body, and a multi-org deployment can have per-org `webhook_secret` configured or left blank, breaking the intended binding "organization authenticated == repository written."

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` used to check the HMAC signature strictly from the payload's `repository.owner.login` (with an `organization.login` fallback): [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-org config, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org has no `webhook_secret` configured: [3](#0-2) [4](#0-3) 

After (or without) verification, `Webhooks::Handlers::Handler#repository_name`/`#stacks` — used by every registered handler (`PushHandler`, pull-request handlers, etc.) — resolves the acted-upon repository from a **different** field of the same payload: `repository.full_name`: [5](#0-4) [6](#0-5) 

Because `verify_signature` and the handlers each read a different, independently-forgeable JSON field, an attacker who can produce one valid (or trivially bypassed) signature for organization A can supply a payload whose `repository.full_name` points at a completely different repository/org B that is registered as a `Stack` in this Shipit instance. In a multi-org config (`Shipit.github_organizations`/`github_app_config`), any org that has been onboarded with `webhook_secret: nil` (a documented, valid configuration — see `config/secrets.development.example.yml`) makes `verify_webhook_signature` return `true` for *any* signature, effectively authenticating the whole request while the acted-on repository is taken from an unrelated field: [7](#0-6) 

This is exactly the "organization authenticated versus the repository that is written" trust binding called out in scope: `verify_signature` proves `X-Hub-Signature` matches org A's secret (or that org A requires none), but `PushHandler#process`/`stacks` acts on `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, which can name org B's repository.

### Impact Explanation
An attacker with no GitHub credentials for the target repository can forge a `push` webhook: set `X-Github-Event: push`, `repository.owner.login` to an onboarded organization with no `webhook_secret` (or otherwise satisfy a cheaper signature check for org A), and `repository.full_name` to `victim-org/victim-repo`. The `PushHandler` will locate every non-archived `Stack` tracking that branch of the victim repository and call `stack.sync_github(expected_head_sha: params.after)`, driving `GithubSyncJob` with an attacker-chosen `expected_head_sha` and branch reference: [8](#0-7) 
This can desynchronize the stack's known commit history/HEAD used by continuous-deployment and deploy-eligibility logic for a repository the attacker never had write access to — an unauthorized, cross-repository state manipulation that can influence what gets deployed. The same handler-vs-verification-field split applies to all other webhook handlers (`pull_request`, `status`, `check_suite`, `membership`), widening the blast radius (e.g. forged `membership` events creating/asserting team/user records, forged `status`/`check_suite` events affecting merge/deploy gating) using only knowledge of one org's (possibly secret-less) webhook configuration.

### Likelihood Explanation
Requires (a) a multi-org Shipit deployment, and (b) at least one onboarded organization whose `webhook_secret` is left blank — a state the project's own example config treats as valid/normal (`webhook_secret: # nil`). Given that, no GitHub credentials, repository write access, or session are needed: the attacker only needs the HTTP endpoint (`POST /github/webhooks`, unauthenticated by design since it's meant to be called by GitHub) and knowledge of any other tracked repository's `full_name`, which is public information for public repos. This is a realistic operational misconfiguration risk in a codebase that explicitly supports "no secret" per org.

### Recommendation
Bind the verified signer to the acted-upon repository by construction:
1. Verify the signature using the GitHub App resolved from the same repository (`full_name`'s owner) that handlers will subsequently act on, not a possibly-different `owner.login` field, and reject if they disagree.
2. Treat "no `webhook_secret` configured" for an org as opt-in only for that org's own repositories — never as a blanket bypass usable for payloads referencing other orgs' repositories.
3. Have `Webhooks::Handlers::Handler` validate that the `Repository` resolved via `full_name` belongs to the same GitHub organization that `verify_signature` used to compute the signature, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (`webhook_secret` left blank/nil) and `orgB` (has a `Stack` tracking `orgB/victim-repo`, `webhook_secret` set to a real secret only GitHub knows).
2. POST to `/github/webhooks` with headers `X-Github-Event: push` and any `X-Hub-Signature` value (or omit correctness), and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")`; since `orgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the supplied signature (`lib/shipit/github_app.rb:76-83`).
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, mutating `orgB`'s stack state without any `orgB` credential or webhook secret ever being checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
