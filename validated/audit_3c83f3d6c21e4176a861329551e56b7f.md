### Title
Cross-organization repository resolution in webhook handlers via mismatch between `verify_signature`'s owner and `full_name`'s owner - ([File: app/models/shipit/repository.rb])

### Summary
`Repository.from_github_repo_name` (and every `pull_request` webhook handler that calls it) resolves a `Repository` purely from `params.repository.full_name`, with no check that this matches the organization whose credentials/secret verified the webhook. Because `WebhooksController#verify_signature` selects the signing organization from a *different* JSON field (`params.repository.owner.login`), a webhook whose signature check trivially passes for one configured GitHub App organization can carry a `repository.full_name` naming a repository belonging to a completely different organization, causing the handler to mutate/create state for that unrelated org's `Repository`/`Stack`.

### Finding Description
Binding claimed: `verified_organization == Repository#owner` for the row resolved by `from_github_repo_name`, where `verified_organization` is the org whose `webhook_secret` was used in `GitHubApp#verify_webhook_signature`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the org's `webhook_secret` is not configured (`return true unless webhook_secret`), which is a supported configuration shown in the repo's own multi-org fixture (`webhook_secret: # nil`). [2](#0-1) [3](#0-2) 
- Every `PullRequest::*Handler` (e.g. `OpenedHandler`) resolves the target repository from a *separate* JSON field, `params.repository.full_name`, via `Repository.from_github_repo_name`, which just does `find_by(owner:, name:)` with no reference back to the organization that was used for signature verification. [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used for signature routing) and `repository.full_name` (used for repository resolution) are independent, attacker-suppliable keys inside the same JSON body, an attacker can send a `pull_request` `opened` webhook where:
- `repository.owner.login = "orgA"` — a real organization configured in this Shipit instance that happens to have no `webhook_secret` set, so `verify_signature` passes for *any* signature/body.
- `repository.full_name = "orgB/target-repo"` — a different, real organization/repository with review stacks enabled.

`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#repository` then resolves `orgB`'s `Repository` row via `full_name` and, if `provisioning_behavior_allow_all?`/labels match, calls `ReviewStackAdapter#find_or_create!`, which creates a new `Stack` under `orgB`'s repository using entirely attacker-controlled `pull_request.head.ref`/`number`/labels. [6](#0-5) 

Existing guards do not prevent this: `verify_signature` only checks organization `orgA`'s secret (attacker doesn't need it if unset), `drop_unhandled_event` only checks the event type is handled, and the `ExplicitParameters` schema on `PullRequest::OpenedHandler` requires only `repository.full_name`, not `repository.owner.login`, so it never cross-validates the two fields. [7](#0-6) 

### Impact Explanation
An attacker who knows (or discovers) the name of any organization configured on the target Shipit instance without a `webhook_secret` can forge webhooks that are misattributed to that org for signature purposes, but that actually target and mutate a *different* organization's `Repository`/`Stack` records — creating review stacks, archiving/unarchiving stacks, and updating `PullRequest` records for a repository the attacker never authenticated against. This is a cross-tenant stack-creation/mutation bug matching "a payload for one repository mutating another's stack" (Critical). It is repeatable against any pair of (secret-less org, target org/repo) known to the attacker, and downstream stack creation can trigger provisioning/deploy commands built from attacker-controlled branch names and PR metadata, widening blast radius.

### Likelihood Explanation
Requires: (a) at least one organization configured on the Shipit instance without `webhook_secret` (a supported, non-default but real configuration seen in this repo's own fixtures/docs), and (b) knowledge of that org's name plus a target org/repo with review stacks enabled. No GitHub App private key, `webhook_secret`, session, or API token is required from the attacker — only the ability to POST to `/webhooks`, which is explicitly in-scope for the threat model. Feasibility is high if the precondition (a secret-less configured org) holds; if all configured orgs enforce `webhook_secret`, this path is not exploitable, since the attacker cannot forge a valid HMAC signature for any org and the divergence between `repository.owner.login` and `repository.full_name` can never bypass a real signature check.

### Recommendation
- In `Repository.from_github_repo_name` (or its callers in `Shipit::Webhooks::Handlers::Handler`), require the caller to pass the verified organization and assert it equals the resolved `Repository#owner`, rejecting mismatches.
- In `WebhooksController#verify_signature`, derive `repository_owner` consistently from the same field used later for repository resolution (`repository.full_name`'s owner segment), not a separate `repository.owner.login`/`organization.login` field, or require both to match.
- Strongly discourage/disallow unset `webhook_secret` in production; log/alert when an org's webhook signature check is a no-op.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "cross-org webhook: unsigned org's payload can target another org's repository" do
  # Configure Shipit.github so that :org_a has no webhook_secret (bypasses HMAC check)
  # and :org_b is a distinct configured org owning shipit_repositories(:org_b_repo)
  Shipit.stubs(:github).with(organization: 'org_a').returns(
    Shipit::GitHubApp.new('org_a', { webhook_secret: nil })
  )

  repo_b = shipit_repositories(:org_b_repo) # owner: "org_b", review_stacks_enabled: true, allow_all

  payload = {
    action: 'opened',
    number: 1,
    pull_request: {
      id: 1, number: 1, url: 'https://x', title: 't', state: 'open',
      additions: 1, deletions: 1,
      head: { sha: 'abc', ref: 'feature' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    repository: {
      owner: { login: 'org_a' },       # used by verify_signature -> no secret -> passes
      full_name: 'org_b/target-repo'   # used by from_github_repo_name -> resolves org_b's repo
    },
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary, ignored since org_a has no secret

  assert_difference -> { repo_b.review_stacks.count }, 1 do
    post :create, body: payload, as: :json
  end
  assert_response :ok
  # Assert equality that should hold but doesn't:
  # verified_organization ('org_a') != Repository resolved.owner ('org_b')
end
```
This demonstrates that `verified_organization` (`org_a`) and the `owner` of the `Repository` actually mutated (`org_b`) diverge, and a `ReviewStack` is created for `org_b` without any credential belonging to `org_b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
