### Title
Webhook signature verification is scoped to `repository.owner.login`, but event processing acts on the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The analog of the Mooniswap `_beforeTokenTransfer` bug — acting on a payload value that was never checked for consistency with the value the trust decision was actually made on — exists in `WebhooksController#verify_signature`. The HMAC signature check selects which GitHub App/secret to verify against using `repository.owner.login`, while every webhook handler that mutates state resolves the target `Repository`/`Stack` using the sibling field `repository.full_name`. These two fields are never cross-checked for equality.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` to validate the signature against based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`): [1](#0-0) [2](#0-1) 

Once the signature is accepted, `create` dispatches the raw parsed payload unchanged to the registered handlers: [3](#0-2) 

Every handler that identifies which `Repository`/`Stack` to mutate uses a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Nothing in the controller or in `Repository.from_github_repo_name` re-derives `owner` from `repository.owner.login` and asserts it equals the `owner` segment inside `repository.full_name`; the two are parsed from independent parts of the same untrusted JSON body. In the equality-of-bindings sense requested by the rules: the engine verifies `signature == HMAC(secret_for(repository.owner.login), raw_body)` but then executes `stack.sync_github(...)` for `Repository.from_github_repo_name(repository.full_name)` — i.e., the organization whose secret authenticated the request is not provably the organization/repository that is written.

This is architecturally analogous to Shopify's own multi-org deployment mode, documented in `config/secrets.development.example.yml`, where multiple GitHub organizations (each with its own `webhook_secret`) can be configured simultaneously: [7](#0-6) 

Because the raw POST body is fully attacker-controlled JSON before the signature is checked, and the two fields (`repository.owner.login` and `repository.full_name`) live at different JSON paths, a webhook sender that legitimately knows (or has leaked) one organization's `webhook_secret` could sign a payload whose `repository.owner.login` matches that organization (so `verify_signature` passes) while setting `repository.full_name` to `"other-org/other-repo"` for a **different** organization/stack tracked by this same Shipit instance. Handlers such as `PushHandler` would then act on the second organization's stack without ever validating a signature scoped to it.

### Impact Explanation
If exploitable, this allows an attacker who controls (or has been granted) a webhook secret for **one** organization/repository configured in a multi-org Shipit deployment to forge webhook events (e.g., `push`) that are processed as if originating from a **different** organization's repository, triggering `GithubSyncJob`/`stack.sync_github` and other state-changing webhook side effects (membership changes, pull-request/review-stack lifecycle changes) for a stack the attacker has no legitimate write access to. This crosses the "organization authenticated vs repository written" trust boundary described in scope, and can lead to unauthorized cross-repository state mutation, satisfying the High-impact bar of unauthenticated cross-stack mutation of task/stack state.

### Likelihood Explanation
Exploitability is contingent on Shipit being configured for **multiple** GitHub organizations sharing the same instance (the multi-org config shown in `config/secrets.development.example.yml`), and on the attacker possessing at least one valid `webhook_secret` for any one of those organizations (e.g., as a legitimate but lower-trust org admin, or via secret leakage of one org). This is a real, supported deployment topology, but it does require the attacker to already hold a webhook secret for some organization on the instance, which is a non-trivial precondition and narrows likelihood to a lower/medium tier compared to a fully unauthenticated bypass.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), after verifying the signature against the organization derived from `repository.owner.login`, assert that the `owner` segment of `repository.full_name` matches `repository.owner.login` (or `organization.login`) before dispatching to handlers; reject the request (HTTP 422) on mismatch. Equivalently, `Repository.from_github_repo_name` / `Handler#repository_name` could be tightened to require the caller to pass in the authenticated organization and refuse to resolve a repository whose owner differs from it.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (as supported by `config/secrets.development.example.yml`).
2. As holder of `org-a`'s `webhook_secret`, craft a `push` webhook JSON body where:
   - `repository.owner.login = "org-a"` (so `WebhooksController#repository_owner` resolves to `org-a`, and the HMAC signs cleanly with `org-a`'s secret).
   - `repository.full_name = "org-b/some-repo"` (a repository/stack tracked under `org-b`).
3. Sign the raw body with `org-a`'s `webhook_secret` and POST it to `/webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` passes because it only checks `org-a`'s secret against `repository.owner.login == "org-a"`.
5. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("org-b/some-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s stack, despite the request never being validated against `org-b`'s webhook secret.
