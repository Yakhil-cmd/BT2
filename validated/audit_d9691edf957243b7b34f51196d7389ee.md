### Title
Webhook signature verification selects the HMAC secret from query-string-controlled params while the processed payload comes from the signed body, letting an unauthenticated attacker pick a secret-less org and forge events for any other org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` is a public, unauthenticated endpoint (`ActionController::Base`, CSRF disabled, no `Shipit::Authentication`). [1](#0-0)  It decides *which* organization's `webhook_secret` to verify the HMAC against using `repository_owner`, which reads from the controller's Rails `params` object, not from the raw signed body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Rails builds `params` as `request_parameters.merge(query_parameters)`, so query-string keys silently override same-named body keys. Because `repository_owner` is read from `params` (query+body merged) while the actual event content dispatched to handlers is `JSON.parse(request.raw_post)` (the exact bytes the HMAC signs), an attacker who controls the request's query string can make `repository_owner` resolve to a *different* organization than the one whose data is in the signed/raw body - or to an organization with no `webhook_secret` configured at all.

`GitHubApp#verify_webhook_signature` treats an absent secret as "always valid":
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

and this is an explicitly supported, documented configuration (`webhook_secret: # nil` appears as valid example config for multi-organization setups). [4](#0-3) 

In multi-org mode, `Shipit.github(organization: repository_owner)` looks the org up by name and returns that org's dedicated `GitHubApp`/secret:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  ...
``` [5](#0-4) 

### Finding Description
The binding that must hold is:

`organization whose webhook_secret authenticated the request == organization/repository whose data is acted upon by the handler`

Before the attack, both values come from the same GitHub-signed JSON body, so this equality holds by construction.

After the attack, an attacker sends a raw POST directly to the public `/github/webhooks` endpoint with:
- `X-Github-Event: membership` (or `push`, `team`, etc.)
- A query string such as `?organization[login]=secretless-org` (an organization configured in `secrets.github` with a blank `webhook_secret`)
- A JSON body whose `organization`/`repository`/`team`/`member` fields target the *victim* organization/team/repository, with any (or no) `X-Hub-Signature` header.

`repository_owner` reads `params.dig('organization','login')`, which - due to Rails' query-over-body merge precedence - resolves to `secretless-org` from the query string, not the victim org embedded in the JSON body. `verify_webhook_signature` then short-circuits to `true` because `secretless-org`'s `webhook_secret` is blank. The controller then dispatches the *raw body* (targeting the victim org) to `Shipit::Webhooks` handlers, e.g. the `membership` handler that directly creates/deletes `Membership` rows from unverified payload data (confirmed by existing handler behavior). [6](#0-5) 

The `organization` used to authenticate is no longer the same as the `organization`/`repository` the processed payload writes to - the exact class of trust-binding break this scan targets (authenticated entity vs. entity written), reachable by a fully unprivileged, unauthenticated network attacker.

### Impact Explanation
Forging a `membership` event lets an attacker add an already-registered GitHub-authenticated user (themselves) to any `Team`, which is exactly the authorization gate checked by `User#authorized?` (`Shipit.github_teams`). [7](#0-6)  This is a direct escalation into `Shipit.github_teams` authorization - explicitly listed as a High-impact outcome. Forged `push`/`status`/`check_suite` events can also poison a stack's commit history/CI state and trigger `GithubSyncJob` for arbitrary tracked stacks. [8](#0-7) 

### Likelihood Explanation
The endpoint requires no session, no API token, and no repository access - it is reached over plain HTTP by anyone who can send a request to the Shipit host, which is a documented deployment requirement (the app must receive GitHub webhooks). The only precondition is that the Shipit instance is configured for multiple GitHub organizations with at least one organization having a blank `webhook_secret` - a configuration explicitly shown as valid/example in the engine's own multi-org config templates. [9](#0-8) 

### Recommendation
Derive `repository_owner` (and any value used to select the verification secret) exclusively from the parsed raw body (`JSON.parse(request.raw_post)`), never from `ActionController::Parameters`/query string. Additionally, consider rejecting webhook requests for organizations with a blank `webhook_secret` instead of treating them as always-valid, or require the resolved organization to match the actual signature-bearing body content strictly.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (real `webhook_secret`) and `attacker-org` (blank `webhook_secret`), per the documented multi-org schema. [10](#0-9) 
2. Send:
```
POST /github/webhooks?organization[login]=attacker-org HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{"action":"added","organization":{"login":"victim-org"},
 "team":{"id":1,"name":"Victim Team","slug":"victim-team"},
 "member":{"login":"attacker-github-login"}}
```
3. `repository_owner` resolves to `attacker-org` (from the query string) rather than `victim-org` (from the body); `verify_webhook_signature` returns `true` because `attacker-org.webhook_secret` is blank.
4. The unverified body is dispatched to the `membership` handler, which creates a `Membership` linking `attacker-github-login` to `Victim Team`, exactly as demonstrated for legitimate membership events in the test suite. [11](#0-10) 
5. If `Victim Team` is in `Shipit.github_teams`, the attacker's already-authenticated Shipit user (via normal OAuth login) now passes `User#authorized?` and gains full application access.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
