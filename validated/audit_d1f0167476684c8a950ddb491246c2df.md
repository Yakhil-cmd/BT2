## Finding

**Cross-organization webhook forgery via mismatched signing-org vs. write-target repository** — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The external report's bug class — "an entity is trusted to have performed an action (transferring WSX) but nothing checks that the value acted upon actually corresponds to what was verified" — maps to a real trust-binding gap in Shipit's webhook pipeline: **the GitHub organization used to verify a webhook's HMAC signature is not the same field used to determine which repository/stack the webhook payload is applied to.**

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` config (and therefore which `webhook_secret`) to verify the inbound signature against using a field read directly out of the unverified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `repository.owner.login`, falling back to `organization.login` — both attacker-controlled fields in the raw JSON body, read *before* any signature validation occurs.

Separately, once a handler runs, it determines *which Repository/Stack to write to* using an entirely different field of the same payload: [3](#0-2) 

`repository_name` is `repository.full_name` (`"owner/repo"`), never cross-checked against `repository_owner` used for signature verification.

`verify_webhook_signature` short-circuits entirely for any configured organization that has no `webhook_secret` set: [4](#0-3) 

`docs/setup.md` and the sample config explicitly document `webhook_secret` as **optional**, and multi-organization configuration is a first-class supported pattern (`Shipit.github(organization:)`), e.g.: [5](#0-4) 

**The break, stated as an equality that fails to hold:**
`organization used to select/pass signature verification` (`repository.owner.login` / `organization.login`) **≠** `organization/repository whose Stack rows are mutated` (`repository.full_name`).

In a Shipit deployment with ≥2 configured GitHub organizations where at least one has no `webhook_secret` (explicitly supported/documented), an attacker can:
1. Craft a payload with `repository.owner.login` = the unsecured org (or `organization.login` if no `repository` key is needed for that event), so `verify_webhook_signature` returns `true` unconditionally.
2. Set `repository.full_name` = `"<victim-org>/<victim-repo>"`, a different, secured organization's repository that is registered as a Shipit `Stack`.
3. Handlers such as `PushHandler` or `StatusHandler` resolve the target purely from `repository.full_name` via `Handler#stacks` / `Repository.from_github_repo_name`, then trigger writes: [6](#0-5) [7](#0-6) 

`PushHandler#process` calls `stack.sync_github(expected_head_sha:)`, which drives Shipit's deploy pipeline (commit sync, subsequently deploy eligibility) for the victim's stack, entirely without a valid signature for the victim organization.

### Impact Explanation
This allows an unprivileged network attacker (no Shipit session, no GitHub write access, no knowledge of the victim org's `webhook_secret`) to inject forged GitHub events (`push`, `status`, `check_suite`, etc.) that are applied to a *different, secured* organization's stacks — enabling unauthorized `github_sync`, forged commit statuses that feed into deployability checks, and potentially unauthorized deploy eligibility gating. This matches the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires the deployment to configure at least two GitHub organizations, with one intentionally left unsecured — a configuration explicitly permitted and shown in shipped sample configs and docs (`webhook_secret` marked optional). This is not a hypothetical misuse of the engine; it is the documented default posture for orgs that choose not to set a secret, combined with the engine's own code failing to bind the verified identity to the acted-upon identity.

### Recommendation
After `verify_signature` succeeds, re-derive `repository.full_name`'s owner and assert it matches the `repository_owner` (or `organization.login`) that was actually used to select the verifying `GitHubApp`/secret. Reject the webhook (422) on mismatch. Alternatively, require every configured GitHub organization to have a mandatory `webhook_secret`, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<any value>   # accepted because org "unsecured-org" has no webhook_secret

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist on victim repo>",
  "repository": {
    "owner": { "login": "unsecured-org" },   // used only for signature verification (bypassed)
    "full_name": "victim-org/victim-repo"    // used to select the Stack that gets sync_github'd
  }
}
```
`verify_signature` passes because `Shipit.github(organization: "unsecured-org")` has `webhook_secret` unset, but `PushHandler` operates on `victim-org/victim-repo`'s `Stack`. [1](#0-0) [3](#0-2) [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
