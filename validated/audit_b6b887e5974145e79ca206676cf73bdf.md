### Title
Organization-fallback signature selection is decoupled from `repository.full_name` used by `LabelCapturingHandler`, enabling cross-repository `PullRequest`/`Stack` writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using `repository_owner`, which falls back to the attacker-controlled `organization.login` field when `repository.owner.login` is absent. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler`, however, resolves the actual `Shipit::Repository`/`Stack`/`PullRequest` to mutate from the independently-attacker-controlled `repository.full_name` field. Because these two fields are never cross-checked, and `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization's `webhook_secret` is blank/unset, an attacker can pick a lenient/unsecured organization for signature selection while pointing `repository.full_name` at a completely different victim repository, causing the handler to overwrite that victim's `PullRequest.labels`.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner_of(repository.full_name)`, but nothing enforces this equality.

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , and is used only to pick the `GitHubApp` instance for signature verification: `Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization's config has no `webhook_secret` set: `return true unless webhook_secret` [3](#0-2) . The engine's own test fixtures show `webhook_secret: null` is a valid/normal configuration state [4](#0-3) .
- Separately, in the legacy/single-org config schema, `Shipit.github(organization:)` ignores the `organization` argument entirely and always returns the one globally configured `GitHubApp`: `if github_default_organization.nil? ... config = secrets.github` [5](#0-4) , meaning the value chosen for `repository_owner` has no bearing on which secret is checked in that (very common) deployment mode.
- `LabelCapturingHandler` never reads `repository_owner`/`organization.login`. It resolves the target repository purely from `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , then finds the matching review stack/`PullRequest` and, on `reopened` (`reopened_active_stack?`), persists attacker-controlled label names onto that `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [7](#0-6) .

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, a body with `action: "reopened"`, `organization.login` set to an organization known/guessed to have no `webhook_secret` (or, in single-org mode, any string at all since it's ignored), no `repository.owner.login`, and `repository.full_name` set to the victim's `"owner/repo"`. `repository_owner` resolves to the lenient organization, `verify_signature` passes trivially (blank-secret bypass or ignored-argument legacy path), and `LabelCapturingHandler` then loads and mutates the **victim's** `PullRequest` record because it only ever consulted `repository.full_name`.

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type exists a handler, not payload consistency; `ExplicitParameters` schema on `LabelCapturingHandler` only requires `repository.full_name` be present/a `String`, it does not require it to match any owner field; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant since `/webhooks` is unauthenticated by design; and `GithubOrganizationUnknown` (422) only triggers when the organization key is entirely absent from config, not when it exists with a blank secret.

### Impact Explanation
An attacker who controls (or merely knows) an organization entry in Shipit's GitHub config with a blank `webhook_secret` — or who operates against a single-org (legacy schema) Shipit instance where the `organization` parameter is ignored for secret selection — can forge arbitrary `pull_request` webhook bodies naming any victim `repository.full_name` and have `LabelCapturingHandler` overwrite that victim's `PullRequest.labels`, without ever authenticating against the victim repository's real secret. This is a cross-tenant write: a payload that authenticated (or bypassed authentication) as one organization mutates another organization's/repository's stack-linked `PullRequest` record. This is repeatable against any repository already imported into Shipit as a `Stack`/`ReviewStack`, satisfying the Critical bucket ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Feasibility hinges on at least one organization in the Shipit deployment's GitHub config lacking a `webhook_secret` (demonstrably a valid, non-error configuration state per the engine's own fixtures) or the deployment using the legacy single-org config schema (where the `organization` argument to `Shipit.github` is discarded regardless). Given that, the attacker needs zero credentials — no session, API token, GitHub App key, or webhook secret — only the ability to send an HTTP POST to `/webhooks` with attacker-chosen JSON and headers, which is explicitly in scope for an unprivileged internet attacker. The attack is fully repeatable against any repository name string.

### Recommendation
Cross-validate that the organization used for signature verification is the same organization that owns `repository.full_name` before dispatching to handlers (e.g., derive `repository_owner` from `repository.full_name`'s owner segment consistently, or require both fields to be present and equal). Additionally, treat a blank/missing `webhook_secret` for any configured organization as a hard misconfiguration (refuse to boot or reject all webhooks for that org) rather than silently bypassing verification, and make `Shipit.github` respect the passed `organization:` argument even in single-org/legacy mode, or reject payloads whose organization can't be unambiguously tied to the target repository.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative only — not to be placed under `test/` as a permanent change without following repo conventions):

```ruby
test "pull_request payload with mismatched organization/repository full_name mutates victim stack's PullRequest" do
  victim_stack = shipit_stacks(:shipit) # has repository.full_name == "shopify/shipit-engine"
  victim_pr = victim_stack.pull_request # existing PullRequest fixture, labels: []

  # Simulate an org with no webhook_secret configured (mirrors secrets.test.json: webhook_secret: null)
  request.headers['X-Github-Event'] = 'pull_request'

  forged_body = {
    action: 'reopened',
    number: victim_pr.number,
    pull_request: {
      id: 1, number: victim_pr.number, url: 'http://example.com', title: 'x', state: 'open',
      additions: 0, deletions: 0,
      head: { sha: 'deadbeef', ref: 'attacker-branch' },
      user: { login: 'attacker' },
      assignees: [],
      labels: [{ name: 'INJECTED_SECRET' }]
    },
    # No repository.owner.login -> repository_owner falls back to organization.login
    organization: { login: 'attacker-org' }, # config'd with blank webhook_secret
    repository: { full_name: victim_stack.repository.full_name }, # points at victim, independent of organization.login
    sender: { login: 'attacker' }
  }.to_json

  assert_equal 'attacker-org', JSON.parse(forged_body).dig('organization', 'login')
  assert_equal victim_stack.repository.full_name, JSON.parse(forged_body).dig('repository', 'full_name')
  refute_equal JSON.parse(forged_body).dig('organization', 'login'),
               JSON.parse(forged_body).dig('repository', 'full_name').split('/').first

  post :create, body: forged_body, as: :json

  assert_response :ok
  assert_equal ['INJECTED_SECRET'], victim_pr.reload.labels
end
```
Assert on both sides of the binding: before the request, `repository_owner` (`"attacker-org"`) != owner segment of `repository.full_name` (`"shopify"`), and the victim `PullRequest#labels` is unchanged; after the request, despite the mismatch, `verify_signature` still returns 200 and `victim_pr.labels` has been overwritten — proving the authenticated organization and the mutated repository are not the same tenant.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
