Found a genuine analog. `Shipit::Api::CCMenuController` overrides both the API-client authentication and the stack lookup in a way that decouples the stack an `ApiClient` token is authorized for from the stack whose data it actually returns.### Title
`Api::CCMenuController` lets a stack-scoped `ApiClient` token read the build status of any stack, not just the one it is authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The intended binding, enforced by `Shipit::Api::BaseController`, is: *the stack a client's token is authorized for* == *the stack whose resources the request touches*. This is implemented by `stacks`, which restricts the queryable set to `current_api_client.stack_id` when the token is stack-scoped, and by `stack`, which resolves `params[:stack_id]` only within that restricted set: [2](#0-1) 

Permission checking itself (`ApiClient#check_permissions!`) is stack-agnostic - it only checks whether the string `"read:stack"` (etc.) is present in the `permissions` array, it never inspects which stack is being accessed: [3](#0-2) 

So the *only* place the stack_id binding is actually enforced is the `stack`/`stacks` helper in `BaseController`.

`Api::CCMenuController` overrides that helper and drops the scoping: [4](#0-3) 

It resolves `stack` directly via `Stack.from_param!(params[:stack_id])` against the full `Stack` table, completely bypassing the `current_api_client.stack_id` restriction that `BaseController#stack` would have applied. The `require_permission :read, :stack` macro before the `show` action only calls `check_permissions!(:read, :stack)`, which - as shown above - never looks at `stack_id` either.

Before vs after equality broken:
- Intended invariant: `token.stack_id == params[:stack_id]` (when `token.stack_id` is present) for every resource served.
- Actual behavior in `CCMenuController#show`: `params[:stack_id]` can be **any** stack in the system regardless of `token.stack_id`, as long as the token has the generic `read:stack` permission.

### Impact Explanation
An attacker in possession of *any* valid, stack-scoped `ApiClient` token (e.g. a "CCMenu Client" token created via `CCMenuUrlController`, which is deliberately scoped to `permissions: %w[read:stack]` and handed to ordinary logged-in users for embedding in CI dashboards, see `app/controllers/shipit/ccmenu_url_controller.rb`) can use that token to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock state, etc., rendered via `shipit/ccmenu/project`) of **every stack in the Shipit instance**, not just the stack the token was created for. This is an authorization-scope escape: the credential's authorized resource set (one stack) does not match the resource set it can actually touch (all stacks), producing unauthenticated-for-that-resource read of stack state across repositories/teams the token holder may have no legitimate access to. This matches the "unauthenticated read of stack state" High-impact bucket in scope.

### Likelihood Explanation
Likelihood is high for anyone who already holds a legitimately-scoped, low-privilege `ApiClient` token (e.g. a CCMenu URL token, which by design is meant to only expose one stack's status and is often embedded in build-status widgets/dashboards, making it easier to leak than a full API credential). No additional authentication bypass or secret is required beyond a token that is intentionally scoped to `read:stack` on one stack - the vulnerability is purely in the controller's failure to reuse the stack-scoping helper that every other API controller relies on.

### Recommendation
In `Shipit::Api::CCMenuController`, do not bypass the inherited scoping. Replace the private `stack` method override with the base class's scoped lookup (i.e. remove the override and let `BaseController#stack` / `#stacks` apply the `current_api_client.stack_id` restriction), or explicitly re-check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering. Since `CCMenuController` also needs query-string token auth (unlike Basic Auth elsewhere), keep the custom `authenticate_api_client` override, but ensure the subsequent `stack` resolution goes through the same `stacks`-scoped helper as every other API controller.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for `stack_a` (`GET /:stack_id/ccmenu_url`), which creates/reuses an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_a` and returns a token via `authentication_token` [5](#0-4) .
2. Take that token (`token=<...>`) and issue: `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu.xml?token=<token>` where `stack_b` is a completely unrelated stack the token was never scoped to.
3. `authenticate_api_client` in `CCMenuController` successfully authenticates the token (`ApiClient.authenticate(params[:token])`) [6](#0-5) .
4. `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`, regardless of `stack_id` [3](#0-2) .
5. `stack` resolves `stack_b` directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stack_id` restriction, and the XML response for `stack_b`'s latest deploy/build status is rendered - even though the token was only ever authorized for `stack_a`.
