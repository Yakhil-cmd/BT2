### Title
`StatusHandler#process` updates `Commit`/`Status` rows by SHA with no repository scoping, allowing cross-repository status writes - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`PushHandler` and `CheckSuiteHandler` both call the private `stacks` helper (scoped via `Repository.from_github_repo_name(repository_name)`) before touching any `Stack`/`Commit`, but `StatusHandler#process` never calls `stacks` or `repository_name` at all. It instead runs `Commit.where(sha: params.sha)` against the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository's stack that `Commit` belongs to.

### Finding Description
The intended binding is: `Handler#stacks` (scoped by `payload['repository']['full_name']`) == the set of `Stack`s a given webhook payload is authorized to mutate, as enforced explicitly in `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { ... }`, app/models/shipit/webhooks/handlers/push_handler.rb:13-16) and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`, app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-15).

`StatusHandler#process` breaks this binding:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit` belongs to a `Stack` (`belongs_to :stack`, app/models/shipit/commit.rb:11), and `sha` is not scoped to be unique per repository in this query — `Commit.where(sha: params.sha)` matches any `Commit` row in the whole database sharing that SHA, across any stack/repository. `create_status_from_github!` then writes a `Status` row and triggers `Hook.emit(:commit_status, ...)`/`schedule_merges` side effects on that unrelated stack's commit (app/models/shipit/commit.rb:165-169, 366-386).

Because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, an attacker who owns repo A (already onboarded to Shipit, so `WebhooksController#verify_signature` — which validates only via `Shipit.github(organization: repository_owner)`, i.e. per-organization/App secret, not per-repository — succeeds for genuine GitHub-issued events) can cause GitHub to emit a real `status` event for a SHA that is also present as a `Commit` in a different repository/stack (repo B) that shares commit history (fork/mirror/monorepo split) or that the attacker otherwise obtains via a shared parent. That `status` payload is dispatched to `StatusHandler`, which finds and mutates the `Commit`/`Status` for repo B's stack with no verification that `repository_name` in the payload has anything to do with that stack.

Existing guards do not stop this:
- `verify_signature` only proves the payload came from GitHub for the claimed organization; it does not bind the payload's `repository_name` to the `Stack`s being mutated.
- `ExplicitParameters` schema in `StatusHandler` only validates shape of `sha`/`state`/etc., not repository ownership.
- `drop_unhandled_event`/`check_if_ping` are irrelevant to this authorization check.
- `Handler#stacks`/`repository_name` exist precisely to enforce this scoping but are simply never invoked in this subclass.

### Impact Explanation
A crafted or naturally-occurring status event for a shared SHA lets an attacker write `Status` rows and trigger `commit_status`/`deployable_status` hooks and `stack.schedule_merges` for a `Commit` belonging to a `Stack` outside the authenticated payload's own repository — a cross-repository write to `Commit`/`Status` state, matching the Critical "payload for one repository mutating another's stack/commit" impact category. This can influence CI-gated deploy eligibility (`deployable?`, `blocked?`) and continuous-delivery scheduling for a victim stack the attacker does not own, and is repeatable against any stack whose commits share SHAs with a repository the attacker controls (forks, mirrors, subtree/monorepo splits).

### Likelihood Explanation
Exploitation requires: (1) attacker owns/controls a repository already onboarded such that Shipit's GitHub App/webhook secret for that org is configured (consistent with the stated threat model — "emit webhooks from a repository they own"), and (2) a genuine SHA collision with a commit tracked by a victim stack, realistically achieved via forking/mirroring a repository whose commits are also tracked as a Shipit stack. This is a plausible, low-cost, repeatable scenario for any organization using Shipit across forked/mirrored repositories, and requires no secrets, sessions, or privileged roles — only a legitimate GitHub push/status event from an attacker-controlled repo.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve commits only within `stacks` (i.e., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) so a status payload can only mutate commits belonging to stacks of the repository named in that payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "#process does not update commits belonging to a different repository's stack" do
  repo_a = shipit_repositories(:shipit)          # attacker-controlled repo
  repo_b = create_repository(full_name: 'other-org/victim-repo')
  victim_stack = create_stack(repository: repo_b)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'shared history commit')

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo_a.github_repo_name }
  }

  assert_empty Shipit::Repository.from_github_repo_name(repo_a.github_repo_name).stacks.where(id: victim_stack.id)

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  assert_predicate victim_commit.reload.statuses, :empty?, "status handler must not mutate commits outside the payload repository's stacks"
end
```
This demonstrates that despite `repo_a`'s `stacks` relation (correctly) excluding `victim_stack`, `StatusHandler#process` still writes a `Status` onto `victim_commit`, proving the missing scoping.
