### Title
Fixed `--sync-timeout` Budget vs. Attacker-Controlled Repo Content Causes Persistent Sync Denial - (File: main.go)

### Summary
The IBC report describes a DoS pattern where a fixed, chain-local resource budget (gas limit) is applied uniformly to processing attacker-influenced payload content, so an attacker can craft content that reliably exceeds the budget on one side, forcing a timeout that permanently disables further progress (closing an `ORDERED` channel). `git-sync` has a structurally analogous pattern: a single fixed `--sync-timeout` (`context.WithTimeout`) is applied to the entire `SyncRepo` operation — fetch, reset, worktree creation, submodule update (potentially `--recursive`), and GC — regardless of how large or expensive the attacker-influenced upstream repository content is. Because a fetched ref's cost (blob size, submodule depth/count, tree size) is fully attacker-controlled once `--repo`/`--ref` point at a repository the attacker can push to, an attacker can make every sync attempt exceed the timeout deterministically, and by default (`--max-failures=0`) this causes `git-sync` to `os.Exit(1)` after the very first failure, producing persistent sync denial.

### Finding Description
The sync loop in `main.go` allocates one timeout context per sync attempt and passes it through the entire operation chain: [1](#0-0) 

That single `ctx` is used for `git fetch` (`fetch`), `git reset --soft`, `worktree add` (`createWorktree`), `git reset --hard` plus `git submodule update --init [--recursive]` (`configureWorktree`), and `cleanup` (GC/prune). None of these paths scale the timeout, nor is there any per-object size/complexity limit — the timeout is a single global constant regardless of how expensive the specific attacker-influenced ref is to process: [2](#0-1) [3](#0-2) 

When the command exceeds `ctx`'s deadline, `pkg/cmd` surfaces a `context.DeadlineExceeded` error rather than succeeding: [4](#0-3) 

Back in the sync loop, a single failed attempt increments `failCount`, and if `getMaxFailures()` (backed by `--max-failures`, default `0`) is `>= 0` and `failCount >= maxFails`, the process aborts entirely via `os.Exit(1)`: [5](#0-4) 

With the documented default of `--max-failures=0` ("the number of consecutive failures allowed before aborting"), a single timeout is enough to terminate the process: [6](#0-5) 

There is no mechanism to configure per-repo or per-content resource ceilings (equivalent to the reported recommendation of "different gas limits for different chains"), and submodule recursion (`--submodules recursive` is the default) further multiplies the amount of attacker-controlled work executed inside the same fixed timeout window: [7](#0-6) [8](#0-7) 

### Impact Explanation
This maps to the accepted "persistent sync denial" impact class. If an attacker with push access to the tracked upstream repository (or control over a submodule referenced by it) commits content whose processing (fetch + checkout + recursive submodule update + fsck/GC) reliably exceeds `--sync-timeout`, every sync attempt will fail identically. With the default `--max-failures=0`, `git-sync` exits after the first such failure; in restart-managed deployments (e.g., Kubernetes sidecar with `Always`/`OnFailure` restart policy) it will crash-loop indefinitely because restarting does not change the fact that the tracked ref is still oversized, so the mirrored content is never updated — a durable denial of service functionally equivalent to the ORDERED channel being permanently closed in the original report. Even with `--max-failures` raised or set to `-1` (retry forever), the sidecar would still never successfully sync the poisoned ref, permanently starving the consuming application container of updates.

### Likelihood Explanation
Moderate-to-high. It requires only push/commit authority (or control of a submodule dependency) over the specific repo/ref that an operator has configured `git-sync` to track — no privileged access to the `git-sync` deployment itself is needed, matching the "attacker-pushed commit" reachable path called out in the validation rules. The default configuration (`--max-failures=0`, `--submodules=recursive`) makes the failure mode occur on the very first affected sync with no extra flags required.

### Recommendation
- Do not `os.Exit` on a single `context.DeadlineExceeded` failure by default; distinguish timeout errors from other git failures and apply backoff/retry semantics that don't require operator opt-in via `--max-failures=-1`.
- Add configurable, independently-tunable sub-timeouts and/or size ceilings (e.g., max blob size, max tree size, max submodule depth/count) so a single oversized/attacker-crafted ref cannot exhaust the entire `--sync-timeout` budget for the whole `SyncRepo` pipeline, mirroring the reported recommendation of per-chain (here, per-repo) resource configuration.
- Emit clearer diagnostics distinguishing "content too large for configured timeout" from generic fetch/checkout errors, and document this failure mode (as the IBC vendor did) so operators can size `--sync-timeout` and submodule policy relative to trust in the upstream content.

### Proof of Concept
1. Deploy `git-sync` against an attacker-influenced repository (or one with a submodule the attacker controls) with default flags: `--repo=<attacker-influenced-repo> --root=/tmp/root --link=link` (default `--sync-timeout=120s`, `--max-failures=0`, `--submodules=recursive`).
2. Attacker pushes a commit whose tree/submodule graph is deliberately expensive to fetch/checkout (e.g., very large blobs, deeply nested/many recursive submodules) such that `fetch` + `configureWorktree` (`reset --hard` + `submodule update --init --recursive`) reliably takes longer than `--sync-timeout` on the git-sync sidecar's resource profile, referencing the timeout enforcement at: [9](#0-8) 
3. `git.SyncRepo(ctx, ...)` returns a `context.DeadlineExceeded`-wrapped error from `pkg/cmd/cmd.go`'s `runWithStdin`.
4. `failCount` becomes `1`; since default `--max-failures=0` satisfies `failCount >= maxFails`, `git-sync` logs "too many failures, aborting" and calls `os.Exit(1)`: [10](#0-9) 
5. In a Kubernetes sidecar deployment with an automatic restart policy, the container restarts and repeats steps 2–4 indefinitely because the poisoned ref is still the target, resulting in persistent denial of the sync function (the mounted volume is never updated with new content), analogous to a permanently closed `ORDERED` IBC channel blocking all future packets.

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
