### Title
Custom commission collector (SIMD-0232) can be rug-switched to redirect an already-earned epoch's inflation commission, bypassing the commission-rate delay protection - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
Agave's vote program lets a vote account's authorized withdrawer designate a "custom commission collector" (SIMD-0232) that receives the validator's inflation-reward commission instead of the vote account itself. While the *commission rate* is protected by a one-epoch delay so it cannot be changed retroactively to affect an already-in-progress epoch's payout, the *collector address* itself has no such delay and is resolved from the live vote-state at distribution time, not the delayed snapshot. This lets the withdraw authority redirect an entire epoch's already-earned commission to a new address at the last moment before distribution — the same "change-the-recipient-right-before-payout" pattern described in the referenced report.

### Finding Description
`update_commission_collector` lets the authorized withdrawer freely repoint `inflation_rewards_collector`/`block_revenue_collector` at any time, with no epoch-boundary restriction: [1](#0-0) 

Contrast this with `update_commission`, which enforces `is_commission_update_allowed` (i.e., commission-rate increases are disallowed in the second half of an epoch) specifically to prevent "commission rug pulls": [2](#0-1) 

At epoch-rewards distribution time, `redeem_delegation_rewards` deliberately fetches the **commission rate** from a delayed snapshot (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) specifically to delay the effect of commission changes by a full epoch: [3](#0-2) 

However, the **collector pubkey** that actually receives the commission lamports is read from the live, non-delayed `vote_state` (sourced from `distribution_epoch_vote_accounts`, i.e. state as of the end of the rewarded epoch / start of distribution): [4](#0-3) 

So the delay mechanism protects the *rate* used for computing rewards but not the *destination* of the payout. An authorized withdrawer can therefore let commission accrue all epoch under one collector (e.g. a shared revenue-splitting/staking-pool contract address configured as the "trusted" collector), then, right before end-of-epoch reward distribution is triggered by `distribute_reward_commissions`, call `UpdateCommissionCollector` to swap the collector to a personal wallet, capturing the entire epoch's commission that had already accrued under the old arrangement: [5](#0-4) 

This mirrors the reported bug class exactly: a privileged role (there: contract admin; here: vote-account authorized withdrawer) can retarget the recipient of already-accrued value immediately before it is paid out, with no cooldown/lock and no validation that a change is safe.

### Impact Explanation
Funds movement is diverted from the expected/previously-configured commission collector to an attacker-controlled address, with no consensus divergence but real economic loss to whoever relied on the previously set collector (e.g., a revenue-sharing counterparty or delegator pool that was told commission would flow to a specific collector account). Because the entire epoch's commission for a vote account can be substantial, this is a real transaction-triggered fund-diversion vector reachable purely by the vote account's authorized withdrawer signing a normal `UpdateCommissionCollector` instruction — no leader/operator/network privilege is required.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control the authorized withdrawer key of a vote account that has previously delegated its commission collector to a third party (e.g. a staking-pool/service arrangement), and to time the `UpdateCommissionCollector` transaction just before the epoch-boundary reward distribution. Since the withdrawer key is a normal signer (not requiring node/leader status) and the collector-change instruction has no timing restriction at all (unlike `update_commission`), the attack is straightforward to execute for anyone who already holds that authority and wants to defect from a revenue-sharing agreement.

### Recommendation
Apply the same delay semantics used for the commission rate (SIMD-0249) to the commission collector address: resolve `inflation_rewards_collector`/`block_revenue_collector` from the delayed snapshot (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) at distribution time in `redeem_delegation_rewards`, rather than from the live `distribution_epoch_vote_accounts` state, so a mid/end-of-epoch collector change only takes effect starting the following epoch, matching the intent that already-earned commission cannot be retroactively redirected.

### Proof of Concept
1. Vote account `V` is configured (via `UpdateCommissionCollector`, SIMD-0232) with `inflation_rewards_collector = SharedPoolAccount`.
2. Over epoch `N`, stake delegated to `V` earns inflation rewards; commission accrues based on `V`'s stake/credits throughout the epoch (this commission is only realized/paid at epoch-boundary distribution).
3. Near the end of epoch `N` (before `distribute_reward_commissions` runs for the epoch boundary), the authorized withdrawer of `V` submits an `UpdateCommissionCollector` transaction changing `inflation_rewards_collector` to `AttackerWallet` — this succeeds unconditionally per `update_commission_collector` (no rate-delay-style timing check applies to the collector, only to `update_commission`'s rate).
4. At epoch-boundary reward distribution, `redeem_delegation_rewards` computes the commission rate from the delayed snapshot (protecting the *rate*) but resolves `commission_pubkey` from the *current* `vote_state.inflation_rewards_collector()`, which is now `AttackerWallet`.
5. The entire epoch `N` commission — which accrued while the collector was `SharedPoolAccount` — is paid to `AttackerWallet` instead, per `distribute_reward_commissions`/`load_and_reward_commission_accounts`.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
