### Title
Reachable `throw Error` in oscript formula evaluator crashes the full node on attacker-controlled AA trigger data - ([File: formula/evaluation.js])

### Summary
The oscript formula evaluator in `formula/evaluation.js` uses a callback-driven `evaluate()` recursion that is supposed to convert every invalid or unexpected input into a soft `setFatalError()` (which safely bounces the AA trigger / rejects the formula via `callback`). However, several code paths inside `evaluate()` fall back to a raw synchronous `throw Error(...)` instead of `setFatalError()`, e.g. in the `ifelse` branch: `else if (typeof res === 'object') throw Error("test evaluated to object " + res);` at [1](#0-0) , and the catch-all `default: throw Error('unrecognized op '+op);` at [2](#0-1) , plus similar `throw Error` statements scattered through `evaluate()` (49 occurrences) such as unknown assignment operator handling [3](#0-2)  and unknown-type-of-value handling in `aa_composer.js`'s template `replace()` walker [4](#0-3) .

### Finding Description
`evaluate()` is invoked from `formulaParser.evaluate()` while processing an AA trigger's messages/state formulas, which are executed for every unprivileged unit posted with data/payment to an AA address (see `handleTrigger` → `evaluateAA` → `replace` → `formulaParser.evaluate` chain in `aa_composer.js` [5](#0-4)  and the trigger-driven unit validation/save flow at [6](#0-5) ). Any unhandled/unrecognized construct encountered mid-evaluation causes a synchronous JS exception that escapes the callback continuation chain because it is not routed through `setFatalError` (which is the only mechanism that safely aborts evaluation via callback without throwing). Since ocore is architected to intentionally crash the whole node process on any uncaught exception — `process.on('uncaughtException', ...) { ...; throw err; // crash the process to avoid ending up in an inconsistent state }` [7](#0-6)  — any reachable `throw Error` deep inside formula evaluation that isn't caught by an enclosing `try/catch` results in a full-node crash, not merely a rejected unit.

This mirrors the CVE-2021-2076 bug class: a high/attacker-controlled input path into the evaluator/optimizer that is "easily exploitable" and results in a repeatable crash/hang (complete DoS) rather than a data-integrity compromise.

### Impact Explanation
If an oscript formula (author-controlled AA code combined with attacker-controlled `trigger.data`/`trigger.output` values) can be steered into any of these `throw Error` branches, a single crafted unit sent to an AA is enough to crash every full node that processes/validates the trigger (during initial validation, `estimatePrimaryAATrigger` dry-runs, and secondary-trigger propagation), causing the network to become unable to process new units until nodes are restarted — a repeatable, network-wide denial of service, matching the "Impact" criteria (node disagreement on validity/availability, network unable to confirm new units).

### Likelihood Explanation
Likelihood depends on whether the specific `throw Error` branches are actually reachable given the surrounding guards (e.g., `isValidValue()` checks before the `ifelse` object-type branch, and the fact that the parser grammar controls which `op` values are ever produced). Based on the retrieved code, I could not fully confirm reachability of `formula/common.js`'s `isValidValue()` — I was not able to load its body in this session — so I cannot definitively prove that a plain-object `res` can slip through to line 1472, or that an "unrecognized op" can be produced by a valid-but-unusual formula/AST edge case. This is a **credible, medium-likelihood analog** that requires further code-flow confirmation (specifically the definition of `isValidValue` in `formula/common.js` and whether any caller of `formulaParser.evaluate` wraps calls in try/catch) before being escalated to a High severity confirmed finding.

### Recommendation
- Replace every raw `throw Error(...)` inside the callback-driven `evaluate()` function (and in `aa_composer.js`'s `replace()` walker) with `setFatalError(...)` so any invalid state is surfaced through the existing safe callback/rejection path instead of throwing.
- Audit `isValidValue()` in `formula/common.js` to ensure it truly excludes all values that would reach the `object`-typed `throw` branches.
- Add defensive `try/catch` around the top-level `evaluate()` invocation in `formulaParser.evaluate` (and within `handleTrigger`/`replace`) that converts any unexpected synchronous exception into a bounce/error response rather than letting it propagate to the global `uncaughtException` handler.
- Add fuzz/property tests targeting the oscript formula grammar to attempt to reach every `throw Error` line in `formula/evaluation.js` via crafted `trigger.data`, `trigger.output`, and state-var values.

### Proof of Concept
Not fully constructible without confirming `isValidValue()`'s exact allowed value set (unavailable in this session due to index limits on `formula/common.js`). Conceptually: define an AA whose `messages`/`state` formula contains an `if (...) {...} else {...}` construct whose test expression is engineered to still hold a raw JS object at the point checked in evaluation.js line 1470 (bypassing the `wrappedObject`/`isValidValue` normalization), then post a unit with `trigger.data`/`trigger.output` values chosen to drive the test expression into that state. If reachable, posting this one unit to the AA is sufficient to crash any full node that validates/executes the trigger.

**Note:** Because `formula/common.js` (specifically the `isValidValue` implementation) was not retrievable through the available search/index tools in this session, the exact reachability of the vulnerable `throw Error` branches could not be conclusively proven end-to-end. A Devin session with full repository/filesystem access would be needed to inspect `formula/common.js` directly, trace the AST/parser grammar for `op` values, and build a concrete PoC unit.
