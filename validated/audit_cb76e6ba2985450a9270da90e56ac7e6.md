### Title
Webhook payload processed without any signature-integrity guarantee when an organization has no `webhook_secret` configured, allowing unauthenticated forgery of commit CI status and pull-request state — ([File: lib/shipit/github_app.rb])

### Summary
The external report's root cause is that Shipit's curve-oracle stand-in — here, the webhook ingestion pipeline — trusts derived/summary data instead of verifying it against a cryptographically-anchored ground truth. In `Shipit::GitHubApp#verify_webhook_signature`, if an organization's `webhook_secret` is not configured, signature verification is skipped entirely and the request is treated as verified: [1](#0-0)  This breaks the binding that `WebhooksController` is supposed to enforce: *"organization that authenticated" == "payload that is trusted and acted upon."* When no secret exists, that equality collapses to "any payload for any repository is trusted," and every webhook handler (status, pull_request, membership, etc.) executes on entirely attacker-controlled data.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance for the organization named in the (unverified, attacker-supplied) `repository.owner.login`/`organization.login` field of the JSON body, and then asks that app to verify the HMAC signature: [2](#0-1)  `verify_webhook_signature` is the only checkpoint that binds the raw HTTP body to a legitimate GitHub App delivery. Its implementation is:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret

  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [1](#0-0) 

`return true unless webhook_secret` means: for any organization whose config omits `webhook_secret` (a state the engine itself supports — the config schema explicitly allows `webhook_secret: nil` per organization, as seen in the multi-org secrets template) [3](#0-2) , `verify_signature` unconditionally passes regardless of the actual `X-Hub-Signature` header or body content. The controller then dispatches the entirely-unauthenticated payload to every registered handler for that event type: [4](#0-3) 

The `status` (a.k.a. `:state`) handler persists attacker-supplied `state`, `context`, `description`, and `target_url` directly onto the matched commit's `Status` records, with no independent confirmation against GitHub: [5](#0-4)  Likewise `pull_request` handlers (`opened`, `closed`, `reopened`, `unlabeled`, `assigned`, `edited`) create/archive/unarchive review stacks purely from payload content matched only by `repository.full_name` and `number`, e.g.: [6](#0-5)  and `closed`: [7](#0-6) 

None of these downstream consumers re-derive the "ground truth" (an authenticated call back to the GitHub API) the way the LP-price report recommends checking real pool balances instead of a manipulable derived value (`get_virtual_price`). Shipit's status/PR state is accepted at face value from the webhook body whenever the signature check is a no-op.

### Impact Explanation
Commit `Status` rows written by the `status` handler are the authoritative signal Shipit's continuous-delivery/deploy-gating logic uses (`ci.require`, `deployable?`) to decide whether a commit is safe to auto-ship. An attacker who can post to `/webhooks` for an organization lacking a `webhook_secret` can forge a "success" status for any required CI context on any commit of a tracked repository/stack, causing Shipit to treat that commit as deployable and — for stacks with `continuous_deployment: true` — trigger an **unauthorized deploy**. This satisfies the Critical bar ("an unauthorized deploy, rollback or merge"). Even absent continuous deployment, forged pull_request events can create/archive review stacks and mutate merge-queue state without any legitimate GitHub-side action, corrupting the deployment-trust model for that repository.

### Likelihood Explanation
Likelihood is Medium: it requires only that one configured organization omit `webhook_secret` — a state the engine's own multi-org config schema explicitly supports (`webhook_secret: nil`) and the codebase treats as a first-class, intentional fallback (`return true unless webhook_secret`), not a hardening default. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only knowledge of the target's `/webhooks` endpoint, the tracked repository's owner/name, and a commit SHA (all public for open-source repos), which is achievable by a fully unprivileged actor.

### Recommendation
Do not silently accept unsigned webhooks. Either:
1. Require `webhook_secret` to be present for every configured organization at boot/initialization time (fail loudly instead of defaulting to `true`), or
2. If an organization is intentionally unsigned, restrict which event types/handlers may act on unsigned payloads (e.g., never allow unsigned payloads to write `Status` rows or mutate stack/review-stack state), or
3. For CI-critical operations (status writes gating deploys), re-verify against the GitHub API (fetch the actual combined status for the SHA) rather than trusting the webhook body verbatim — mirroring the recommendation in the LP-price report to use ground-truth balances instead of a derived/reported value.

### Proof of Concept
1. Configure (or find deployed) an organization entry in `secrets.github` whose `webhook_secret` key is `nil`/absent (a supported configuration per `config/secrets.development.shopify.yml`).
2. `POST /webhooks` with header `X-Github-Event: status` and a JSON body:
```json
{
  "sha": "<known deployed/tracked commit sha>",
  "state": "success",
  "context": "<the ci.require context for the target stack>",
  "target_url": "https://attacker.example/fake",
  "description": "forged",
  "repository": {"owner": {"login": "<org without webhook_secret>"}, "full_name": "<org>/<repo>"}
}
```
3. Because `webhook_secret` is blank for that org, `verify_webhook_signature` returns `true` unconditionally [8](#0-7) , so the request bypasses `head(422)` and reaches `Shipit::Webhooks.for_event('status')`, which creates a `Status` row on the commit exactly as demonstrated in the test suite [5](#0-4) .
4. If the target stack has `continuous_deployment: true` and this forged status satisfies the stack's `ci.require` context, the stack's continuous-delivery scheduler will consider the commit deployable and enqueue/trigger a deploy without any real CI having run — an unauthorized deploy driven entirely by unauthenticated input.
