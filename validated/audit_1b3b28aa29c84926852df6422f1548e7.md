### Title
Commit-status webhook forgery lets an unrelated GitHub organization fabricate CI status on any tracked stack's commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate a payload against using an attacker-controlled field (`repository.owner.login`, falling back to `organization.login`) taken from the *unverified* JSON body, before the HMAC check runs. `StatusHandler`, which processes the `status` event, then looks up the target `Commit` purely by `sha` with **no repository/stack scoping at all**. These two facts combine into a binding break: the identity that is cryptographically authenticated (the organization whose secret matched) is not the same entity whose data is written (any commit, in any tracked repository, matching an arbitrary `sha`).

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unauthenticated payload and uses it to pick the `github_app`/secret to verify against: [1](#0-0) [2](#0-1) 

Because Shipit supports configuring one `webhook_secret` per organization for multi-tenant setups, an attacker who legitimately administers *any* organization onboarded to this same Shipit instance (Org A) knows Org A's `webhook_secret`. They can send a `status` webhook whose `repository.owner.login`/`organization.login` is `"org-a"` (so the secret lookup and HMAC verification both succeed using a secret they legitimately possess), while every other field in the same signed payload — including the commit `sha` — is fully attacker-controlled, because the HMAC only proves "this body was signed with Org A's secret," not "this body only concerns Org A's data."

`StatusHandler#process` then updates state using only that attacker-controlled `sha`, with no scoping to the repository/organization that was authenticated: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped lookup across the entire `commits` table, so it can match a commit belonging to a completely different tracked stack (a different customer/organization) than the one whose secret authenticated the request. This breaks the binding: `organization that authenticated == repository that is written`.

The base `Handler` class does support scoping via `repository_name`/`stacks` (`payload.dig('repository','full_name')`): [4](#0-3) 
but `StatusHandler` never uses `stacks`/`repository_name` to constrain the `Commit` lookup, so the scoping mechanism that exists elsewhere in the codebase is bypassed entirely for this event type.

### Impact Explanation
By crafting a `status` webhook with `state: "success"` for a known commit `sha` (commit SHAs are public GitHub data, easily obtained from any public repo commit or PR) belonging to a victim stack hosted on the same Shipit instance, the attacker can inject a fabricated passing CI status via `commit.create_status_from_github!`. If that stack has required-status checks and continuous delivery/merge-queue enabled, a forged "success" status can satisfy CI gating and trigger an unauthorized deploy or an unauthorized pull-request merge for a repository the attacker has no access to — meeting the "unauthorized deploy, rollback, or merge" bar. This is only exploitable on multi-tenant installs where more than one organization/secret is configured (as documented in `config/secrets.development.example.yml`), and requires the attacker to control (or be a legitimate admin of) some other onboarded organization's webhook secret — not Shipit's own credentials.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment (explicitly supported and documented), (b) the attacker having legitimate control of at least one of the other configured organizations (a realistic scenario for a shared/SaaS-style Shipit instance serving multiple customers), and (c) knowledge of a target commit SHA (trivially public on GitHub). No Shipit session, API token, or GitHub App private key is needed — only the attacker's own organization's webhook secret, which they are entitled to know for their own org.

### Recommendation
In `verify_signature`, do not let the org used for secret selection be decoupled from the org whose data is subsequently modified: after verifying the signature, re-derive/re-validate the acting organization from the verified payload and pass it explicitly to handlers, or verify the payload against the secret of the organization that actually owns the target repository (looked up server-side from `Repository`, not from the payload). Additionally, scope `StatusHandler#process` (and any other handler using bare cross-cutting lookups) to commits belonging to repositories whose owning organization matches the authenticated organization, mirroring the `repository_name`/`stacks` pattern already used in `Handler`.

### Proof of Concept
1. Deploy Shipit with two organizations configured, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. As an admin of Org A (attacker-controlled), obtain Org A's `webhook_secret`.
3. Identify the SHA of a commit on Org B's tracked stack (public on GitHub).
4. POST to `/github/webhooks` with header `X-Github-Event: status`, body:
   ```json
   {
     "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"},
     "sha": "<org-b-commit-sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
5. Sign the raw body with Org A's `webhook_secret` and set `X-Hub-Signature` accordingly.
6. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's secret, and the signature validates.
7. `StatusHandler#process` executes `Commit.where(sha: "<org-b-commit-sha>")`, finds the Org B commit, and records a fabricated `"success"` status on it, potentially unblocking a deploy/merge on Org B's stack that Org A's attacker has no authorization over.
