### Title
StatusHandler creates Status rows for any Commit matching an attacker-chosen SHA without verifying repository ownership - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target `Commit` rows purely by `sha` (`Commit.where(sha: params.sha)`), never invoking `Handler#stacks`/`#repository_name` to scope by the repository that authenticated the webhook. Its `ExplicitParameters` schema also never declares `requires :repository`, so the `repository.full_name` field is entirely optional and unchecked, unlike every `PullRequest` handler.

### Finding Description
The broken binding: `repository_name` derived from the verified webhook payload (`payload.dig('repository','full_name')`, `Handler#repository_name` at `app/models/shipit/webhooks/handlers/handler.rb:36-38`) should equal the repository scope used to select rows mutated by the handler — for PullRequest handlers this holds via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (e.g. `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:49-53`), but `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never establishes this equality at all — it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository filter whatsoever.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) authenticates that the request is signed by *some* org's `webhook_secret` (resolved via `repository_owner`, which itself just reads `params.dig('repository','owner','login')`), but this only proves the attacker's own org secret matches — it does not bind the SHA in the payload to that org's repositories. Since `StatusHandler`'s params schema (`status_handler.rb:7-18`) only `requires :sha, :state` and never requires `:repository`, an attacker can send a `status` webhook signed with their own org's `webhook_secret`, containing an arbitrary or absent `repository` field, and any `sha` value. If that `sha` happens to match a `Commit` row in the DB belonging to a completely different stack/repository, a `Status` record is created on that unrelated stack via `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`), which further triggers `Hook.emit` for `:commit_status`/`:deployable_status` and `stack.schedule_merges` (`commit.rb:374-384`).

### Impact Explanation
This is a cross-repository write: an attacker with a valid webhook secret for any org (even their own throwaway org) can inject `Status` rows (state, description, target_url, context) onto Commits owned by stacks/repositories they don't control, provided they can predict or brute-force a valid SHA (git SHAs are 40 hex chars, not secret — they are visible in PRs, commit messages, GitHub UI, CI logs). Since `Status` creation feeds `deployable?`/`blocking?` logic and can trigger `stack.schedule_merges`, a forged "success" status could unblock or trigger a merge/continuous-deployment pathway for a stack the attacker has no relationship to. This matches "a payload for one repository mutating another's stack, commit, task" — Critical.

### Likelihood Explanation
Preconditions are minimal per the threat model: attacker needs only their own org with any valid `webhook_secret` registered as a `GithubHook` in the target Shipit instance, and a known SHA (SHAs are routinely public). No relationship to the real repository owner is required. This is trivially repeatable against arbitrary SHAs/stacks by simply changing the `sha` field in the POST body.

### Recommendation
In `StatusHandler`, add `requires :repository do requires :full_name, String end` to the params schema, and scope the commit lookup through `stacks`/`repository_name` (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), mirroring the pattern used by `PullRequest` handlers, so a `status` event can only mutate commits belonging to the repository that was cryptographically verified as the sender.
