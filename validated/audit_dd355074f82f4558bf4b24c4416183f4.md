### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on unrelated payload fields (`repository.full_name`, global `sha`) - cross-organization / cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to HMAC-verify a webhook delivery based on `repository.owner.login` (or `organization.login`) taken from the same attacker-suppliable JSON body it is about to validate. Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* raw payload to handlers that resolve the target `Repository`/`Stack`/`Commit` using **different, independently-controlled fields** of the same payload (`repository.full_name` in the generic `Handler`, or a completely unscoped, global `sha` lookup in `StatusHandler`). Nothing ties the org whose secret produced a valid signature to the repository that ends up being mutated.

### Finding Description
`verify_signature` computes the authenticating organization strictly from the payload itself: [1](#0-0) [2](#0-1) 

`github_app.verify_webhook_signature` only proves that the raw body's HMAC matches the `webhook_secret` configured for *that* organization (each org has its own independent secret, see `config/secrets.development.shopify.yml`): [3](#0-2) 

Once verified, the raw params are handed unmodified to the event handler: [4](#0-3) 

The base `Handler` class, however, resolves which `Repository`/`Stack` to operate on using `repository.full_name`, a field that is never checked against `repository.owner.login` (the field used for signature-org selection): [5](#0-4) 

Even more directly, `StatusHandler` doesn't scope by repository at all — it matches purely on a global `sha` across the entire `commits` table: [6](#0-5) 

This is the same class of bug as the reported swap issue: the binding used for **verification** (`repository.owner.login` → which secret validated the message) is never carried through to the value the **effectful action** uses (`repository.full_name` / global `sha`). Analogous to "trade executed with A2 while verification used A1's target price," here the delivery is authenticated as belonging to org A, but the write is performed against whatever repository/commit the payload names, which can belong to org B, C, etc. — any org onboarded to the same Shipit instance.

Concretely: an attacker who administers a GitHub App/webhook installed for *any one* of the organizations configured in this Shipit instance (i.e., possesses that org's `webhook_secret`) can sign an arbitrary JSON body with that secret while setting `repository.owner.login` to their own org (to pass `verify_signature`) and setting `repository.full_name` (for `push`/`check_suite`) or `sha` (for `status`) to reference a **different** organization's repository/commit. The webhook endpoint has no other authorization check — `verify_signature` is the sole gate — so the forged event is processed against the victim org's data.

### Impact Explanation
- Via `StatusHandler`, any org with a configured webhook secret can forge a commit status (state, context, description) for **any commit SHA in the entire database**, regardless of which repository/org it belongs to, since the lookup is `Commit.where(sha: params.sha)` with no repository scoping at all.
- Forged/spoofed CI statuses feed directly into deploy-gating logic (`commit.deployable?`/`require_ci` checks used by `Api::DeploysController#create`), enabling an attacker with control of one org's webhook secret to mark an arbitrary commit belonging to a different organization's stack as CI-passing, facilitating an **unauthorized deploy**.
- Via the generic `Handler#stacks`/`repository_name`, `PushHandler` and `CheckSuiteHandler` can trigger `sync_github`/`schedule_refresh_check_runs!` against any repository merely by naming it in `repository.full_name`, independent of the org that produced the valid signature.

This satisfies the Critical impact bucket: cross-repository writes / unauthorized deploy resulting from an authentication binding that does not carry through to the object actually mutated.

### Likelihood Explanation
Requires the attacker to control a GitHub App/webhook installation (and its `webhook_secret`) for at least one organization configured in the Shipit deployment — a routine, low-privilege position for any org onboarded onto a shared/multi-tenant Shipit instance (this is explicitly the scenario the rules flag as in-scope: "an organization that authenticated versus the repository that is written"). No GitHub repository write access, Shipit session, or `ApiClient` token is needed — only the ability to POST a crafted, self-signed payload to the public `/github/webhooks` endpoint.

### Recommendation
After verifying the HMAC signature for the org derived from `repository.owner.login`, re-validate that every repository/commit referenced elsewhere in the payload (`repository.full_name`, `sha`, `check_suite.head_sha`, etc.) actually belongs to that same verified organization before any handler is allowed to look up or mutate state. `Handler#repository_name`/`#stacks` and `StatusHandler#process` should scope lookups by the verified organization, not trust unrelated payload fields.

### Proof of Concept
1. Attacker is the administrator of `org-attacker`, which is configured in this Shipit instance with its own `webhook_secret` (a legitimate, low-privilege scenario for a multi-tenant Shipit deployment).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/anything" },
     "sha": "<victim commit sha belonging to org-victim/some-repo>",
     "state": "success",
     "context": "ci/tests",
     "description": "forged"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_org_attacker, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-attacker"`, looks up `org-attacker`'s app, and successfully verifies the signature — request passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no org/repository check, finds the victim's commit (belonging to `org-victim`), and calls `create_status_from_github!`, writing a forged CI status onto it. [6](#0-5) 
6. The victim's commit is now marked CI-passing, potentially allowing an unauthorized deploy through `Api::DeploysController#create`'s `require_ci`/`deployable?` gate.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
