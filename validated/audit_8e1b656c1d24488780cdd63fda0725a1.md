### Title
Webhook signature is validated against the organization derived from the payload, but the target repository/stack is resolved from a separate, unchecked payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub organizations (a documented, supported configuration), each organization has its own GitHub App and its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to use for HMAC validation based on `repository_owner`, taken from `params.dig('repository','owner','login')` (or `organization.login`) [2](#0-1) . However, every event `Handler` resolves the actual `Stack`/`Repository` to act on using a *different* field of the same JSON body: `payload.dig('repository','full_name')` [3](#0-2) . Nothing ties these two fields together, so a request whose HMAC is valid for organization A can still act on a repository belonging to organization B.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured organization [4](#0-3) , and the codebase explicitly supports and documents multiple independently-configured organizations sharing one Shipit instance [5](#0-4) [1](#0-0) .

`verify_signature` derives the organization used for HMAC verification solely from `repository_owner` (`repository.owner.login`, falling back to `organization.login`) inside the untrusted JSON body: [2](#0-1) 

Once the signature check passes, `WebhooksController#create` dispatches the full parsed payload to the registered `Handler` for the event [6](#0-5) . Every handler determines which `Stack`/`Repository` to mutate via `Handler#repository_name`/`#stacks`, which reads `payload.dig('repository', 'full_name')` — a field that is never cross-checked against the `repository_owner` value used to select the verifying secret: [3](#0-2) 

Concretely, this breaks the equality that should hold: `organization authenticated by webhook_secret == owner(repository acted upon)`. An attacker who controls (or is the admin of) a GitHub organization "OrgA" that is legitimately onboarded to this Shipit instance knows OrgA's `webhook_secret` (it is configured per-organization by that organization's own GitHub App setup, not a Shipit-instance-wide secret). That attacker can POST a forged JSON body directly to the `/webhooks` endpoint (this does not require any GitHub-side privileged action, just knowledge of the secret that GitHub itself would use to sign OrgA's real webhooks) where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up and verifies against OrgA's own `webhook_secret`, which the attacker controls/knows), and
- `repository.full_name` = `"OrgB/victim-repo"` (an entirely different, unrelated organization's repository already configured as a Shipit stack).

Because the whole raw body is HMAC'd with OrgA's secret and the attacker crafts the whole body, the signature check passes cleanly, while every downstream handler acts on `OrgB/victim-repo`'s stacks. This is demonstrated implicitly by the existing test suite, where `repository_owner` (used only for `Shipit.github(organization:)` lookup) and `repository.full_name` (used to resolve the acted-upon repository) are set completely independently in test fixtures [7](#0-6) [8](#0-7) .

Concrete impact via existing handlers acting on `OrgB`'s stack:
- `StatusHandler`/`push`/`check_suite` style handlers create `Status` records / trigger syncs for commits in `OrgB`'s stacks directly from attacker-controlled payload fields (state, description, target_url, context) as shown by the "`:state` create a Status for the specific commit" test, which persists CI status straight from payload content [9](#0-8) . A forged "success" status on a commit that never ran CI can defeat `shipit.yml` status-check gating and enable an unauthorized deploy of `OrgB`'s stack.
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any non-archived stack on the matched branch of `OrgB`'s repository [10](#0-9) .
- `PullRequest::LabeledHandler` archives/unarchives review stacks for `OrgB` based on attacker-supplied `pull_request.labels` [11](#0-10) .

### Impact Explanation
This crosses the organization-authentication boundary vs. repository-written boundary called out in scope: the credential (webhook secret) that authenticates as organization A is used to write/mutate state belonging to organization B's repositories and stacks configured on the same Shipit instance. Depending on which handler is abused, this can manipulate CI status used to gate deploys ("an unauthorized deploy") or manipulate review-stack provisioning state for a repository the attacker does not own — a cross-organization write achieved purely by knowing a webhook secret for an unrelated, legitimately-configured organization, not by compromising the victim organization at all.

### Likelihood Explanation
Exploitability requires only that the Shipit instance host multiple GitHub organizations (a documented, supported deployment topology) and that the attacker knows (or administers) the webhook configuration/secret for any one of those onboarded organizations — a normal, low-privilege capability relative to that org, but with no relationship to the victim organization. No GitHub write access, Shipit session, or `ApiClient` token is needed; only an HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses for their own org.

### Recommendation
`WebhooksController#verify_signature`/the `Handler` base class should require that the organization used to select and verify the `webhook_secret` matches the actual owner of `repository.full_name` used by handlers to resolve the target `Repository`/`Stack`. Concretely, derive both values from the same trusted field (e.g., always use `repository.full_name`'s owner segment for `Shipit.github(organization:)` lookup) or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker administers/knows `OrgA`'s `webhook_secret` (a secret only meaningful for authenticating OrgA's own webhook deliveries).
3. Attacker crafts a JSON body for a `status` (or `push`/`pull_request`) event:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates the signature successfully [12](#0-11) .
6. The dispatched handler resolves the target repository via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` [3](#0-2) , and writes a forged CI `Status` (or performs the handler's other side effects) against `OrgB`'s commit/stack — despite the request never being authenticated for `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
