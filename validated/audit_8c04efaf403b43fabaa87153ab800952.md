## Title
System Vote Weighting Uses Current Balance at Count Time Instead of Balance Held When the Vote Was Cast, Enabling Vote-Weight Manipulation - (File: main_chain.js)

### Summary
Obyte's on-chain governance mechanism (`system_vote` messages for `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) is analogous to the reported `GovernorBravoDelegate` issue: votes are counted using a balance snapshot that is decoupled from the time the vote was actually cast. Instead of locking in a voter's weight at the moment they vote (or at a fixed pre-vote block), `countVotes()` in [1](#0-0)  re-reads each voting address's *current* balance at the moment the vote tally runs (i.e. at MCI stabilization), regardless of when in the (potentially multi-year) voting window the address actually cast its `system_vote`.

### Finding Description
Any regular (non-AA) address can post a `system_vote` unit — validation only rejects AA authors and duplicate votes per unit, it does not restrict voting to witnesses/OPs: [2](#0-1) .

When a mci becomes stable and `system_vote_count` triggers tallying, `countVotes()` selects all distinct addresses that have *ever* voted on the subject, then computes their balance as of the tally time (current stable-good, unspent outputs), not as of the time they voted: [3](#0-2) 

The vote timeframe (`since_timestamp`) only decides *which votes count* (as a `(address, subject)` pair with a given timestamp); it does not bind the counted *balance* to the balance the address held at that vote's timestamp: [4](#0-3) 

The final aggregation for both `op_list` and numeric subjects then joins the vote/timestamp records with this current-balance snapshot: [5](#0-4) [6](#0-5) 

This is the exact bug class from the report: the contract (here, the network's countVotes routine) determines outcomes using a vote-weight value that is dynamic and can diverge from the value that was true when the vote was actually cast. In the GovernorBravo case this was `getPriorVotes` fetched at two different times; here it's the same address's balance fetched at tally time versus its balance at vote-casting time. Since balances can move freely between when a `system_vote` is posted and when the next `system_vote_count` stabilizes (which can be long after, given the vote window is allowed to expand across multiple years to reach `SYSTEM_VOTE_MIN_SHARE`), an address's recorded vote — cast at an earlier point with a small balance — will be weighted by whatever balance it holds at the moment of tallying, which an attacker fully controls by moving funds around.

### Impact Explanation
An attacker can cast a `system_vote` from many addresses while holding little to no balance, then concentrate/acquire the actual balance into one or more of those already-voted addresses only around the time counting occurs, thereby inflating the weight of stale votes without needing durable long-term ownership of the coins at the time of the decision. Because `system_vote` governs the operator (`op_list`)/witness set that underlies stabilization/consensus, and network parameters (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, `threshold_size`), a manipulated tally can shift control of the OP list to attacker-favored witnesses or tune fee parameters against honest participants, which is a governance-integrity impact on the whole network, not merely a resource-only issue.

### Likelihood Explanation
Likelihood is moderate: posting `system_vote` messages requires no privilege beyond being a normal address author (no AA restriction, no witness restriction), and the vote-count window logic explicitly stretches across long periods (expanding by 365-day increments) if voter participation share is low, which increases the opportunity for a voter to have its balance changed dramatically between casting the vote and the eventual tally at `main_chain.js` lines 1807-1821. Because the check is purely time-window-based on the vote, not balance-window-based, this is straightforward to exploit by shifting balances into already-voted addresses.

### Recommendation
Store and use the voter's balance at (or shortly before) the time each `system_vote` unit was posted/stabilized, rather than re-querying the address's balance at tally time. This could be done by snapshotting `balance` into the `system_votes` table when the vote is recorded (in `saveSystemVote`, `main_chain.js` around line 1619-1651) and using that stored value in `countVotes()`'s aggregation queries instead of joining against a freshly computed `voter_balances` table.

### Proof of Concept
1. Address A holds a negligible balance and posts a `system_vote` for `op_list` (or a numeric subject) early in the voting window; this vote is recorded in `system_votes` with A's identity and timestamp only — no balance is stored (`main_chain.js` lines 1619-1651).
2. Time passes; per the expanding window logic (`main_chain.js` lines 1807-1821), A's vote can remain "in scope" for up to several years if total voted share stays below `SYSTEM_VOTE_MIN_SHARE`.
3. Shortly before the mci that triggers `system_vote_count` stabilizes, the attacker transfers a large balance into address A (e.g., via a large purchase/temporary consolidation of funds).
4. `countVotes()` computes A's balance using the current stable-good, unspent-output query (`main_chain.js` lines 1757-1777) at tally time, attributing the full large balance to A's stale, low-conviction vote.
5. After the tally completes and `op_list`/parameter values are updated (`main_chain.js` lines 1863-1902), the attacker moves the funds elsewhere, having influenced the outcome without holding the stake during the actual decision period.

	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);
	if (is_emergency && subject !== "op_list")
		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};
	// Count all stable-good outputs that have no stable-good spender.
	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)
	for (let { address, balance } of bal_rows) {
		balances[address] = balance;
	}
