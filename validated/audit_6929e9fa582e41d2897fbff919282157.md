### Title
Partial bounce refund is silently dropped when a trigger carries multiple assets, permanently freezing funds inside the AA — (File: `aa_composer.js`)

### Summary
When an Autonomous Agent (AA) trigger fails and must be bounced, `aa_composer.js`'s `bounce()` function tries to refund every asset that was sent along with the trigger, minus the configured `bounce_fees`. If *any single asset* included in the trigger does not cover its own bounce fee, the function aborts the **entire** refund — including assets/bytes that were fully sufficient — and none of the funds are returned to the sender. Because the failed trigger also causes the AA's state changes to be rolled back, there is no state left that references these funds, so they remain stuck in the AA's balance with no built-in path to recover them, analogous to the reported Footium issue where a failed low-level `call` permanently locks native tokens with no recovery mechanism.

### Finding Description
`handleTrigger()` computes `bounce_fees` from the AA template (defaulting `base` to `constants.MIN_BYTES_BOUNCE_FEE`): [1](#0-0) 

For primary (non-secondary) triggers, before AA code is even evaluated, the composer checks that the base bytes are enough to cover `bounce_fees.base`, and for any other asset sent with the trigger, if `trigger.outputs[asset] < bounce_fees[asset]`, it immediately calls `bounce(...)`: [2](#0-1) 

The `bounce()` function is supposed to refund whatever was sent, minus the bounce fee, for every asset in `trigger.outputs`: [3](#0-2) 

The critical flaw is in the `for (var asset in trigger.outputs)` loop: if `fee > amount` for **any one** asset (i.e., that asset alone didn't cover its bounce fee), the function does `return finish(null)` — which aborts the loop immediately, discarding any refund `messages` that had already been queued for other assets/bytes that *did* have enough to be refunded: [4](#0-3) 

Concretely: a trigger unit sends base bytes B (with `B >= bounce_fees.base`) plus some custom asset X with `amount_X < bounce_fees[X]`. The early check at line 1856 catches this and calls `bounce('received X is not enough to cover bounce fees')`. Inside `bounce()`, when the loop reaches asset `base` first (if base sorts before X) it pushes a refund message for the bytes, but when it reaches asset X and finds `fee > amount`, it returns immediately via `finish(null)`, throwing away the already-queued bytes refund message as well. No response unit is ever created (`sendUnit` is never called), and `revert()`/`finish(null)` restores original state vars and balances, so no record exists that would let the AA later forward these funds back to the sender. The bytes and asset X are absorbed into the AA's on-DAG balance permanently, with no generic mechanism to reclaim them — mirroring the reported bug class where funds intended to be returned to a legitimate party become irretrievably stuck due to a failure path that isn't gracefully handled per-asset.

### Impact Explanation
This causes **AA fund loss/freezing** for legitimate senders: any user who sends a valid trigger to an AA along with any extra asset in an amount just under that asset's `bounce_fees` threshold will lose both that asset amount and all of the base bytes sent, even though the base bytes alone were sufficient to be bounced back. Given `bounce_fees` can be configured per-asset (or attackers can identify AAs with strict per-asset bounce fee requirements), this is a systematic and reproducible freezing of user funds inside the AA that neither the sender nor the AA definition can recover through this code path.

### Likelihood Explanation
Likelihood is moderate-to-high: any AA that defines `bounce_fees` for a non-base asset (a documented, normal AA feature) combined with any user mistakenly or intentionally sending an insufficient amount of that asset alongside adequate bytes will trigger this code path. No special privileges are required — this is reachable by any unprivileged unit poster sending a payment trigger to a public AA address.

### Recommendation
In `bounce()`, do not abort the whole refund when one asset's amount is insufficient to cover its fee. Instead, skip refunding only that specific under-funded asset (leaving it absorbed, as documented/intended) while still constructing and sending refund messages for all other assets/bytes that do have enough to cover their bounce fees, e.g. replace `return finish(null)` inside the loop with a `continue` (after deciding how to handle the insufficient asset), so partial refunds are not lost wholesale.

### Proof of Concept
1. Deploy an AA whose template sets `bounce_fees: { base: 10000, X: 1000 }` for some asset `X`, with normal response logic (e.g. `just_a_bouncer.oscript`-style AA as seen in `test/samples/just_a_bouncer.oscript`).
2. Post a trigger unit to this AA with a `payment` message sending `20000` bytes (well above `bounce_fees.base`) and a second `payment` message sending `500` units of asset `X` (below `bounce_fees.X = 1000`).
3. In `handleTrigger`, the pre-check at `aa_composer.js:1855-1858` detects `trigger.outputs.X (500) < bounce_fees.X (1000)` and calls `bounce('received X is not enough to cover bounce fees')`.
4. Inside `bounce()` (`aa_composer.js:909-945`), the loop over `trigger.outputs` processes `base` first, pushing a refund message of `20000 - 10000 = 10000` bytes to `trigger.address`; then it processes `X`, finds `fee(1000) > amount(500)`, and calls `return finish(null)` — discarding the already-queued base-bytes refund message.
5. `sendUnit` is never invoked; no response unit is created. The 20000 bytes and 500 units of X sent in the trigger remain part of the AA's balance permanently, with the sender unable to recover any of it (not even the bytes that were fully sufficient for a refund).
