### Title
RAY-valued market totals can overflow before the index cap, permanently freezing a market - (File: `common/src/rates/simulate.rs`)

### Summary
`Controller::update_indexes` is permissionless and calls the pool’s owner-gated `update_indexes`, which runs `interest::global_sync` for each requested `HubAssetKey`. [1](#0-0) [2](#0-1) [3](#0-2) 

Each accrual step converts scaled borrow and supply shares into their RAY-denominated values through `scaled_to_original`. [4](#0-3)  That conversion uses non-saturating fixed-point multiplication, which panics with `MathOverflow` when the resulting value does not fit in `i128`. [5](#0-4) [6](#0-5) 

Although the borrow and supply indexes are capped, the cap is applied only after the index multiplication, while the debt-value multiplication can already overflow during the next accrual step. [7](#0-6) [8](#0-7) 

### Finding Description
`accrue_step` first computes `borrowed_original` and `supplied_original` as `scaled * index`. [9](#0-8)  For a very large market, these products can exceed the maximum representable RAY value even though `borrow_index` and `supply_index` remain below `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`. [7](#0-6) [10](#0-9) 

Once the market reaches this boundary, the next call to `update_indexes` panics before `last_timestamp` advances, leaving the same overflowing interval in storage. [11](#0-10)  Every pool mutation uses `synced_market` or `load_leg`, both of which invoke `global_sync` before performing the operation. [12](#0-11)  Consequently, later `withdraw` and `repay` calls fail during accrual before they can burn shares or move cash. [13](#0-12) [14](#0-13) 

### Impact Explanation
This is permanent freezing of user funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, and liquidations or bad-debt processing cannot complete because all of those paths accrue the market first. [12](#0-11) [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The trigger requires a market whose scaled share totals are large enough that `scaled * index` exceeds `i128::MAX` before either index reaches its configured cap. [5](#0-4) [7](#0-6)  An unprivileged caller can create the exposure through ordinary `supply` and `borrow` when token supply, collateral value, liquidity, and configured caps permit it, then repeatedly call `update_indexes(caller, vec![hub_asset])` as time advances. [15](#0-14) [1](#0-0) 

The condition is economically extreme and depends on market scale and sustained utilization, so this is less likely than ordinary rounding or validation failures. [16](#0-15)  However, the attacker does not need governance access, leaked keys, oracle manipulation, or contract upgrades to execute the final freeze. [2](#0-1) 

### Recommendation
Bound the RAY-valued totals before converting them to `i128`, or make the utilization and interest split use saturating/widened arithmetic that cannot permanently poison accrual. [8](#0-7)  In particular, cap or clamp `borrowed * borrow_index` and `supplied * supply_index` to the protocol’s supported value domain before `calculate_supplier_rewards`, `utilization`, or `update_supply_index` consumes them. [10](#0-9) [17](#0-16) 

Add a regression path that reaches the market-value ceiling and then verifies `update_indexes`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` continue operating with deterministic bounded accounting. [3](#0-2) [12](#0-11) 

### Proof of Concept
1. In a listed hub/spoke market with sufficient token supply and caps, call `Controller::supply(caller, 0, spoke_id, vec![(hub_asset, principal)])` with a very large `principal`, then use the returned account to call `Controller::borrow(caller, account_id, vec![(hub_asset, debt)], None)` at high utilization. [15](#0-14) 
2. Let ledger time advance so the borrow index compounds toward the point where `borrowed * borrow_index` no longer fits in `i128`. [11](#0-10) [7](#0-6) 
3. Call the permissionless `Controller::update_indexes(caller, vec![hub_asset])`; the controller forwards the market to `LiquidityPool::update_indexes`, which invokes `global_sync`. [1](#0-0) [2](#0-1) [18](#0-17) 
4. `accrue_step` panics in `scaled_to_original` while computing `borrowed_original` or `supplied_original`, so the transaction reverts before `last_timestamp` is updated. [9](#0-8) [19](#0-18) 
5. A subsequent `withdraw` or `repay` repeats the same accrual through `load_leg` and reverts before share burning or cash accounting can execute. [20](#0-19) [13](#0-12) [14](#0-13)

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```
