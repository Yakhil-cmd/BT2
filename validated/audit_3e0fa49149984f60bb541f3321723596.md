### Title
Malformed/unrecognized secondary-trigger AA definition crashes shared AA-trigger queue via uncaught `throw Error` in `aa_composer.js`/`formula/evaluation.js` — ([File: aa_composer.js])

### Summary
`aa_composer.handleAATriggers()` is the single, globally shared entry point that processes *every* pending AA trigger across the whole network, in deterministic order, via `async.eachSeries`. This is the direct analog of `GaugeManager.distribute*()` iterating over all gauges: a single malformed/malicious element in the shared queue can throw synchronously and abort the loop for everyone, exactly like the CL-gauge bug halted reward distribution for all pools.

### Finding Description
`handleAATriggers()` reads *all* pending triggers system-wide and iterates them sequentially: [1](#0-0) 

For each row it does `var arrDefinition = JSON.parse(row.definition);` and calls `handlePrimaryAATrigger`, which calls `handleTrigger`. Any unhandled/synchronous `throw` reached while processing one trigger propagates out of the `async.eachSeries` iterator callback and becomes an uncaught exception in the surrounding Node.js process (there is no top-level try/catch around this call chain), because `handleTrigger`/`validateAndSaveUnit` deliberately convert several "should never happen" conditions into `throw Error(...)` instead of routing them through `bounce()`/`onDone(err)`: [2](#0-1) 

and inside the shared secondary-trigger recursion: [3](#0-2) 

The formula evaluator used by every AA (`formula/evaluation.js`) similarly throws hard, uncatchable `Error`s for "should never happen" branches such as `default: throw Error('unrecognized op '+op);` and `throw Error("test evaluated to object " + res);`, reached deep inside `evaluate()`'s recursive, callback-based execution of a *posted* AA's oscript: [4](#0-3) [5](#0-4) 

Because `aa_validation.js` and `formula/validation.js` are meant to guarantee that only well-formed ASTs/ops ever reach `evaluation.js`, any discrepancy between what validation accepts and what the evaluator supports (e.g., a new/edge-case AST shape, a value class not covered by `isValidValue`/`Decimal.isDecimal`/`wrappedObject` checks in a code path validation didn't anticipate) turns a single, unprivileged AA definition + a single unprivileged trigger-sender payment into a **process-crashing exception** that occurs *inside* the shared `handleAATriggers` loop — not inside an isolated per-AA sandbox with graceful error containment. Every other pending trigger in the same batch, and the `aa_triggers` queue itself (an `mci, unit, address` shared table), is left unprocessed until the node is manually restarted, since the row is only deleted from `aa_triggers` after successful completion of `handlePrimaryAATrigger`'s callback chain: [6](#0-5) 

This mirrors the root cause pattern in the reported bug: a shared, sequential distribution/processing routine trusts each queued unverified/adversarial item to fail gracefully (`bounce`), but some code paths bypass the graceful-failure convention and `throw` instead, so one bad item can brick the whole batch for everyone.

### Impact Explanation
If reachable, this is a Medium/High-severity liveness bug: any user can post a payment (unprivileged trigger sender) to any AA (potentially self-authored, unprivileged AA author) whose definition, while passing `aa_validation.js`/`formula/validation.js` at define-time, drives `evaluation.js` (or `aa_composer.js`) into one of the `throw Error(...)` "impossible state" branches at execution time. Because `handleAATriggers` is invoked synchronously from the core stabilization path (`main_chain.js` `stabilizeMci`/`markMcIndexStable`, `writer.js` `saveJoint`), an uncaught exception there halts:
- processing of all other pending AA triggers in the same and subsequent batches (queue never drains, `aa_triggers` table backs up),
- the node's ability to continue writing/stabilizing units that depend on AA trigger completion,
until an operator manually intervenes (restarts, or removes/patches the offending AA/trigger row) — i.e., "the network unable to confirm new units"/AA responses, network-wide, not just for the single malicious AA's counterparties.

### Likelihood Explanation
Likelihood depends on whether there truly exists a validation/evaluation mismatch reachable by an attacker-authored AA + unprivileged trigger. I could not fully enumerate every `throw Error` branch in `formula/evaluation.js` against every corresponding check in `formula/validation.js`/`aa_validation.js` within the available context to prove a concrete exploitable divergence (e.g., a specific AST shape that formula/validation.js accepts but evaluation.js's `switch` doesn't handle, or a value type that slips past `isValidValue`). The pattern itself — same-shaped surface as the reported issue (shared distribution/processing loop, "should never happen" `throw` instead of graceful error return) — is confirmed in the code, but proving a concrete PoC trigger AST requires deeper cross-referencing of `formula/validation.js` and `formula/evaluation.js` op tables than could be completed in this session.

### Recommendation
- Wrap the execution of `handleTrigger`/`evaluateAA`/`formulaParser.evaluate` invoked from `handleAATriggers` (aa_composer.js:59-150, 1841-1888) in defensive try/catch, converting any unexpected exception into a graceful `bounce()` for that single trigger (removing its row from `aa_triggers` and emitting a bounced response) rather than letting it escape the `async.eachSeries` iteration and crash/stall the shared queue.
- Audit all `throw Error(...)` sites in `formula/evaluation.js` and `aa_composer.js` reachable from attacker-controlled AA definitions/trigger data, and convert genuinely reachable ones (as opposed to true internal invariants unreachable from user input) into `setFatalError`/`bounce` paths.
- Add a regression/fuzz test that feeds `formula/validation.js`-accepted-but-edge-case ASTs into `formula/evaluation.js` to catch validation/evaluation divergence before it reaches production.

### Proof of Concept
Not fully constructible from the available index: a concrete AST/oscript snippet that passes `aa_validation.js`/`formula/validation.js` but causes `formula/evaluation.js` (or `aa_composer.js`) to hit one of the noted `throw Error(...)` branches during real trigger processing would be required to demonstrate the crash end-to-end; this was not confirmed within the scope of this analysis.
