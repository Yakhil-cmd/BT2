### Title
Session fixation on GitHub OAuth login — session identifier is never rotated after authentication - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` binds the authenticated GitHub identity to the current session by writing `session[:user_id]`, but it never calls `reset_session` (or otherwise rotates the session id) before doing so. `reset_session` is only invoked from the unrelated "stale credentials" branch of `force_github_authentication` and from `logout`. This breaks the intended binding "session identifier ↔ freshly authenticated GitHub identity", analogous to the PartyDAO bug where a later, authoritative event (`burn`→`mint`) blindly re-applied a previously recorded value instead of validating that the current binding should be replaced.

### Finding Description
The OAuth callback flow is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

`session[:user_id]` is written directly onto whatever session the browser presented when initiating the OAuth handshake. No `reset_session` call precedes this assignment, unlike `logout`, which does call it: [2](#0-1) 

The only other `reset_session` call in the engine is unrelated — it fires when an already-authenticated user's stored GitHub token is stale: [3](#0-2) 

Because the session cookie's identifier is never regenerated at the login boundary, a session id that existed *before* authentication (and that an attacker could have caused a victim's browser to adopt, e.g. via a cookie set on a shared parent domain, a response-splitting bug elsewhere, or any mechanism that plants a session cookie) remains valid and becomes bound to the victim's `User` record the moment the victim completes the GitHub OAuth flow. The attacker, who already knows that session id, can then use it to act as the authenticated victim through `current_user`/`find_current_user`: [4](#0-3) 

This is the "GitHub identity vs. the `User` bound to the session" binding: the equality that should hold after `callback` runs is `session_id (fresh, unpredictable) == User(authenticated_github_identity)`. Instead the code preserves `session_id (possibly attacker-known, pre-existing) == User(authenticated_github_identity)`.

### Impact Explanation
If an attacker can plant/fixate a session id in a victim's browser before the victim authenticates through `/github/auth/github`, the attacker inherits the victim's authenticated session after login, gaining full access to Shipit as that user (viewing stack state, deploy history/output, triggering deploys/rollbacks/locks the victim is authorized for, etc.). This matches the explicitly listed High-impact category "session fixation / forced OAuth completion."

### Likelihood Explanation
This is a real code defect (missing `reset_session` on the authentication path), but full exploitation additionally requires an external mechanism to fixate a chosen session id in the victim's browser (e.g., cookie tossing on a shared domain, another app on the same top-level domain setting the session cookie, or a proxy/cache issue). Shipit's own code does not provide such a vector, so likelihood depends on deployment/environment factors outside this engine. Within the engine's own boundary, the missing rotation is unconditional and reproducible for every login.

### Recommendation
Call `reset_session` (or otherwise regenerate the session id, e.g. via `request.session_options[:renew] = true` if using Rack session stores) at the start of `GithubAuthenticationController#callback`, before setting `session[:user_id]`/`session[:authenticated]`, so that no pre-existing session id can survive the authentication boundary:

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

### Proof of Concept
1. Attacker obtains/fixes a session cookie value `SID_A` in the victim's browser through some external means (out of scope of this engine, e.g. cookie planting on a shared domain).
2. Victim, still carrying cookie `SID_A`, visits `/github/auth/github` and completes the GitHub OAuth flow.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on the existing session `SID_A` without rotating it, per [5](#0-4) .
4. Attacker replays cookie `SID_A` against the Shipit instance; `find_current_user` resolves the victim's `User` from `session[:user_id]`, per [6](#0-5) , granting the attacker the victim's authenticated session.
