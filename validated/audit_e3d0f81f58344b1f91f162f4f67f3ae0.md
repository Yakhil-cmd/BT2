## Finding

### Title
Webhook signature is verified against the org named in an unverified payload field, while the event is executed against a different, unbound repository/commit — allowing cross-tenant status/event forgery — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the `GithubApp`/`webhook_secret` to validate a webhook against based on `repository_owner`, a value read straight out of the **unverified** JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the raw bytes are HMAC-validated against *that* org's secret, `WebhooksController#create` dispatches the full, attacker-controlled payload to handlers, which then decide *what to act on* using a **different field of the same untrusted payload** — `repository.full_name` for most handlers, or nothing at all in `StatusHandler`, which matches purely on `sha` across the whole install. ### Finding Description
This is the "organization authenticated versus the repository that is written" binding break called out in the prompt rules.

1. `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the JSON body (not yet authenticated):
`app/controllers/shipit/webhooks_controller.rb:24-30, 59-62`.
2. `verify_webhook_signature` only proves that the **entire raw body** was HMAC-signed with *that org's* `webhook_secret` — it never checks that the org used for verification is the same org/repo the payload subsequently claims to modify: `lib/shipit/github_app.rb:76-83`.
3. Once verified, `create` passes the *whole* parsed body, unmodified, to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — `app/controllers/shipit/webhooks_controller.rb:10-15`.
4. Handlers scope their side effects using a **different** field than the one used for signature verification:
   - `Handler#stacks` looks up `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, i.e. `full_name`, not `repository.owner.login`: `app/models/shipit/webhooks/handlers/handler.rb:32-38`.
   - `StatusHandler#process` is worse: it does `Commit.where(sha: params.sha)` with **no repository/organization scoping at all**, across the entire Shipit installation's commits table: `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.

Because a Shipit instance is commonly configured with multiple independent GitHub orgs, each with its own `webhook_secret` (see the multi-org `config/secrets.*.yml` layout: `somegithuborg` / `someothergithuborg`, each with a distinct `webhook_secret`) [5](#0-4) , a tenant who legitimately controls one onboarded org (and therefore legitimately knows/controls that org's own `webhook_secret`, e.g. because they configured the GitHub App for their own org) can:
- Set `repository.owner.login` (or `organization.login`) to **their own org**, so `verify_signature` picks their own org's `webhook_secret` and the HMAC check passes.
- Set every other field of the payload — `repository.full_name`, `sha`, `ref`, `check_suite.head_sha`, etc. — to reference a **victim org/repo/stack** that is also tracked by the same Shipit installation.

Since none of the handlers re-check that the org used for signature verification matches the repository/commit actually mutated, the attacker's self-signed webhook is accepted and acted upon against the victim's stack. `StatusHandler` is the most severe instance because it performs zero repository binding whatsoever: any commit sha known to the attacker (e.g. from public GitHub) in *any* stack tracked by the Shipit instance can have an arbitrary CI status (`success`/`failure`/`pending`) injected via `Commit#create_status_from_github!`, and `Status#after_create` calls `enable_ci_on_stack` and `schedule_continuous_delivery`, i.e. this can flip a stack's continuous-delivery/CI gating state. [6](#0-5) 

### Impact Explanation
This breaks the trust boundary between tenants of a single Shipit installation: possession of a webhook secret for org A should only ever authorize writes to org A's data, never org B's. By forging CI/check-suite/push statuses on a victim's commits, an attacker can manipulate a stack's mergeability/deployability gating (`Status`, `CheckSuiteHandler`, `PushHandler`) it does not control, which can enable an **unauthorized deploy** to proceed on the victim's stack once other conditions align (e.g., faking the required status context green). This matches the "High: escalation ... unauthorized deploy" impact bucket in the rules, since it is a cross-repository/cross-tenant write achieved purely by exploiting the mismatch between the credential used for authentication (organization) and the record actually mutated (repository/commit).

### Likelihood Explanation
Any Shipit deployment tracking more than one GitHub organization/app installation is affected by design — the vulnerable code path (`verify_signature` selecting the app by an unverified payload field, followed by handlers that key off unrelated fields of the same payload) is unconditional, requires no special GitHub permissions beyond what the attacker's own onboarded org already has, and needs only a single crafted HTTP POST to `/github/webhooks` with a valid signature for the attacker's own org.

### Recommendation
- After signature verification succeeds, re-derive the acting repository/org strictly from the same trusted context used for verification (i.e., the org whose secret validated the signature), and reject the webhook if `repository.owner.login`/`repository.full_name`'s owner does not match that org.
- In `Handler#stacks` and especially `StatusHandler#process`, scope lookups by the verified repository (owner + name), not solely by `sha`, `full_name`, or other payload-supplied identifiers that were never bound to the verifying secret.
- Consider embedding/checking the expected org identity as part of signature verification context rather than trusting `params.dig('repository','owner','login')` prior to verification.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `attacker-org` (attacker legitimately administers this org/app and knows its `webhook_secret`) and `victim-org` (unrelated tenant tracked by the same Shipit instance).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<sha of a real commit already known/tracked for a victim-org stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the HMAC matches → request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim-org's commit purely by `sha` with no ownership check, and calls `create_status_from_github!`, injecting a forged `success` status onto the victim's commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, `app/models/shipit/status.rb:16-33`), potentially unblocking or triggering continuous delivery for a stack the attacker does not control.
