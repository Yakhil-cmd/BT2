### Title
Address / cosigner enumeration via differentiated error responses in the "sign" device-message handler - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub` handler for the `"sign"` device message (reachable by any paired/correspondent device) calls `findAddress()` and returns distinctly different, information-leaking error strings depending on whether the requested address is known locally, known as a remote/cosigner address, a merkle-only path, or completely unknown. This mirrors the Vault LDAP user-enumeration bug class (CVE-2020-35177): an attacker-controlled but unprivileged peer (a paired device) can send crafted probe requests and, purely from the distinguishable error text/behavior, enumerate which addresses/paths are known to (or co-signed by) the victim wallet, without needing any secret material.

### Finding Description
The `"sign"` case in `handleMessageFromHub` (wallet.js) accepts a device message of the form `{address, signing_path, unsigned_unit}` from any correspondent device (`from_address`) [1](#0-0) . After basic structural validation, it calls `findAddress(body.address, body.signing_path, callbacks, ...)` and reacts differently for each outcome:

- `ifLocal`: address is one of *my* addresses — proceeds to `callbacks.ifOk()` and emits a `signing_request` event [2](#0-1) .
- `ifRemote`: address is a shared/multisig address whose signer lives on another device. If the requester (`from_address`) is not among `other_device_addresses`, it explicitly replies `"you are not listed as a cosigner for this address " + body.address` [3](#0-2) .
- `ifMerkle`: replies `"there is merkle proof at signing path " + body.signing_path` [4](#0-3) .
- `ifUnknownAddress`: replies `"not aware of address " + body.address + " but will see if I learn about it later"` [5](#0-4) .

`findAddress()` itself walks `my_addresses`, `shared_address_signing_paths`, and `peer_addresses` tables to decide which of these callbacks to invoke, effectively testing whether the address is a personal key, a member of a known shared/multisig address, a merkle-stub member, or unknown to the wallet at all [6](#0-5) .

Because each of these four outcomes yields a syntactically and semantically distinct response (`ifOk` vs. four different `ifError` strings, plus divergent side effects such as registering a one-time `new_address-<address>` listener only in the unknown case), a remote correspondent device can systematically probe arbitrary candidate addresses/signing paths against a target wallet and, purely from the response, determine:
1. Whether an address belongs to the target's wallet at all (`ifOk`/`ifLocal` vs `ifUnknownAddress`).
2. Whether an address is a shared/multisig address the target is a cosigner of, and whether the prober itself is a recognized cosigner (`ifRemote` "not listed as a cosigner" branch) — leaking membership/topology of the target's shared addresses.
3. Whether a given signing path resolves to a merkle-only branch of a shared-address definition.

This is a classic information-disclosure-via-differentiated-response bug, structurally analogous to the Vault LDAP enumeration flaw where different responses for "user exists" vs "user does not exist" allowed enumeration of valid usernames.

### Impact Explanation
An attacker who is (or becomes) a paired correspondent device of the target — a low-privilege relationship required only for normal wallet interoperability — can enumerate:
- Which addresses are controlled by the victim's wallet (personal addresses).
- Which addresses are shared/multisig addresses involving the victim, and the cosigner topology (device_address membership) of those shared addresses.

This does not by itself cause fund loss, but it discloses private wallet structure/topology (address ownership, multisig membership, and signing-path validity) to an unprivileged peer, which is directly analogous in bug class and severity tier to CWE-200/user-enumeration issues like the cited Vault advisory. It can be used as reconnaissance to target specific addresses for further social-engineering, contract, or multisig-cosigning attacks (e.g., crafting arbiter/multisig proposals against confirmed-real shared addresses instead of blindly guessing).

### Likelihood Explanation
Likelihood is high for any node that accepts device-pairing from semi-trusted or public correspondents (bots, marketplaces, arbiter services, etc.), since the `"sign"` message path performs no rate limiting or authorization check beyond being a paired device before branching into these four distinguishable outcomes; an attacker only needs to be an established correspondent and can send unlimited probe requests with candidate addresses/paths.

### Recommendation
Normalize the error responses for `ifRemote` (unauthorized cosigner), `ifMerkle`, and `ifUnknownAddress` to a single generic failure message (e.g., "cannot process signing request") that does not reveal which branch was taken, and avoid registering the `new_address-<address>` event listener (or any other observable side effect) differently based on address existence. Rate-limit or throttle `"sign"` requests per correspondent device to reduce probing throughput.

### Proof of Concept
1. Attacker device pairs with the victim device (normal correspondent pairing).
2. Attacker sends a `"sign"` device message with a guessed `address` A and an `unsigned_unit` whose `authors` includes A, plus an arbitrary `signing_path`.
3. Observe the reply:
   - `"not aware of address A but will see if I learn about it later"` → A is unknown to the victim wallet.
   - `"you are not listed as a cosigner for this address A"` → A is a real shared/multisig address (attacker learns existence + that attacker is not a legitimate cosigner).
   - `"there is merkle proof at signing path ..."` → the guessed signing_path corresponds to a merkle-hidden branch of a known shared address definition.
   - No error (proceeds to emit `signing_request`) → A is one of the victim's own addresses.
4. Repeating this for many candidate addresses lets the attacker map out which addresses belong to / are co-managed by the victim wallet, purely from differentiated device-message responses.

function findAddress(address, signing_path, callbacks, fallbackInfo){
	db.query(
		"SELECT wallet, account, is_change, address_index, full_approval_date, device_address \n\
		FROM my_addresses JOIN wallets USING(wallet) JOIN wallet_signing_paths USING(wallet) \n\
		WHERE address=? AND signing_path=?",
		[address, signing_path],
		async function(rows){
			if (rows.length > 1)
				throw Error("more than 1 address found");
			if (rows.length === 1){
				var row = rows[0];
				if (!row.full_approval_date)
					return callbacks.ifError("wallet of address "+address+" not approved");
				if (row.device_address !== device.getMyDeviceAddress()) {
					const other_rows = await db.query("SELECT DISTINCT device_address FROM wallet_signing_paths WHERE wallet=? AND device_address!=?", [row.wallet, row.device_address]);
					const other_device_addresses = other_rows.map(r => r.device_address);
					return callbacks.ifRemote(row.device_address, other_device_addresses);
				}
				var objAddress = {
					address: address,
					wallet: row.wallet,
					account: row.account,
					is_change: row.is_change,
					address_index: row.address_index
				};
				callbacks.ifLocal(objAddress);
				return;
			}
			const prefix = conf.storage === 'sqlite' ? "signing_path||'.'" : "CONCAT(signing_path, '.')";
			db.query(
			//	"SELECT address, device_address, member_signing_path FROM shared_address_signing_paths WHERE shared_address=? AND signing_path=?", 
				// look for a prefix of the requested signing_path
				"SELECT address, device_address, signing_path FROM shared_address_signing_paths \n\
				WHERE shared_address=? AND ( signing_path=? OR " + prefix + "=SUBSTR(?, 1, LENGTH(signing_path)+1) )", 
				[address, signing_path, signing_path],
				async function(sa_rows){
					if (sa_rows.length > 1)
						throw Error("more than 1 member address found for shared address "+address+" and signing path "+signing_path);
					if (sa_rows.length === 1) {
						var objSharedAddress = sa_rows[0];
						var relative_signing_path = 'r' + signing_path.substr(objSharedAddress.signing_path.length);
						var bLocal = (objSharedAddress.device_address === device.getMyDeviceAddress()); // local keys
						if (objSharedAddress.address === '') {
							return callbacks.ifMerkle(bLocal);
						} else if(objSharedAddress.address === 'secret') {
							return callbacks.ifSecret();
						}
						let newFallbackInfo = null;
						if (!bLocal) {
							newFallbackInfo = {};
							newFallbackInfo.device_address = objSharedAddress.device_address;
							const other_rows = await db.query("SELECT DISTINCT device_address FROM shared_address_signing_paths WHERE shared_address=? AND device_address!=?", [address, objSharedAddress.device_address]);
							newFallbackInfo.other_device_addresses = other_rows.map(r => r.device_address);
						}
						return findAddress(objSharedAddress.address, relative_signing_path, callbacks, newFallbackInfo);
					}
					db.query(
						"SELECT device_address, signing_paths FROM peer_addresses WHERE address=?", 
						[address],
						function(pa_rows) {
							if (pa_rows.length > 1)
								throw Error("more than 1 peer address found for address "+address);
							var candidate_addresses = [];
							for (var i = 0; i < pa_rows.length; i++) {
								var row = pa_rows[i];
								JSON.parse(row.signing_paths).forEach(function(signing_path_candidate){
									if (signing_path_candidate === signing_path)
										candidate_addresses.push(row.device_address);
								});
							}
							if (candidate_addresses.length > 1)
								throw Error("more than 1 candidate device address found for peer address "+address+" and signing path "+signing_path);
							if (candidate_addresses.length == 1)
								return callbacks.ifRemote(candidate_addresses[0], []);
							if (fallbackInfo)
								return callbacks.ifRemote(fallbackInfo.device_address, fallbackInfo.other_device_addresses);
							return callbacks.ifUnknownAddress();
						}
					);
				}
			);
		}
	);
}
