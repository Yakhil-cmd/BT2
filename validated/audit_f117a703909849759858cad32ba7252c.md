### Title
Webhook signature verification authenticates the payload's claimed organization, but handlers act on repositories/commits that are never checked against that organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery only against the GitHub organization named in the payload (`repository.owner.login` / `organization.login`), using that organization's own `webhook_secret`. The dispatched handlers, however, resolve the *target* repository/commit purely from other payload fields (`repository.full_name` for `PushHandler`, or a bare `sha` for `StatusHandler`) without ever re-checking that the resolved Stack/Commit actually belongs to the organization whose secret was used to sign the request. This breaks the equality "organization that authenticated == repository that is written," analogous to the UTB report's core flaw where a downstream code path executes privileged effects (`_swapAndExecute`) without re-validating the same instructions that the "front door" function (`swapAndExecute`) is required to validate.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and verifies the HMAC signature using the `webhook_secret` configured for *that* organization: [1](#0-0) [2](#0-1) 

Shipit supports multiple, independently configured GitHub organizations/apps in the same instance, each with its own `webhook_secret` (as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), i.e. a tenant that legitimately owns/administers their own GitHub App registration knows (or can rotate) their own org's `webhook_secret`. [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the raw JSON body to handlers, which independently re-parse the payload and act on whatever repository/commit identifiers are present, with no cross-check against the organization that was authenticated: [4](#0-3) 

- `Handler#stacks`/`#repository_name` resolve the target purely from `payload.dig('repository', 'full_name')`: [5](#0-4) 

- `PushHandler#process` triggers a GitHub sync for any non-archived stack on the resolved repository/branch: [6](#0-5) 

- `StatusHandler#process` is worse: it does not even use the repository at all - it looks up commits **globally by `sha`**, across every stack tracked by the Shipit instance, and writes a GitHub-status record for each match: [7](#0-6) [8](#0-7) 

Because the signature check in `verify_signature` only proves "the sender knows organization X's `webhook_secret`," but never constrains which repository/commit the handler is allowed to touch, a caller who legitimately controls organization X's webhook secret (e.g., a tenant admin in a multi-org Shipit deployment) can submit a directly-crafted HTTP POST (not routed through GitHub) whose body sets `repository.owner.login`/`organization.login` to X (to pass the signature check) while all other identifying fields (`repository.full_name`, `sha`, `branch`) point at a Stack/commit belonging to a different, unrelated organization Y.

### Impact Explanation
`Commit#deployable?` depends on `success?`, which is derived from `statuses`, which `StatusHandler` populates without any repository/ownership check: [9](#0-8) [10](#0-9) 

An attacker who is authenticated only as organization X can therefore inject a forged `success` status onto a commit belonging to organization Y's Stack, making that commit `deployable?` even though it never actually passed CI, and can additionally force `stack.sync_github` on Y's stacks via `PushHandler`. Since Shipit uses commit "green" status as one of the primary safety gates before allowing (including continuous, automatic) deploys (`schedule_continuous_delivery`), this is a cross-tenant integrity break that can lead to an unauthorized deploy of unreviewed/unverified code on a stack the attacker does not own - matching the Critical impact category "an unauthorized deploy." [11](#0-10) 

### Likelihood Explanation
This requires the attacker to legitimately control at least one GitHub organization/App configured in the same Shipit instance (i.e., know that org's own `webhook_secret`, which they administer themselves) - a realistic precondition in any multi-tenant Shipit deployment, and does not require any Shipit session, API token, or GitHub repository write access to a *victim* org. The forged POST is a plain HTTP request to the public `/webhooks` endpoint with attacker-controlled JSON, signed with a secret the attacker legitimately possesses.

### Recommendation
Bind the authenticated organization to the resolved target inside each handler (or centrally in the controller) before any write occurs: after computing `repository_owner` for signature verification, re-derive the repository owner from the *same* field the handler will use (`repository.full_name`'s owner segment) and reject if they don't match. For `StatusHandler` in particular, scope the `Commit.where(sha: params.sha)` lookup by the repository/stack resolved from the authenticated organization instead of a bare, global `sha` match.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-controlled GitHub App, attacker knows `webhook_secret_A`) and `orgB` (victim's tracked Stack, unrelated repo).
2. Attacker computes `HMAC-SHA1(webhook_secret_A, body)` over a crafted JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<sha of an unreviewed commit on orgB's stack>",
  "state": "success"
}
```
3. POST this body with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: status` to `/webhooks`.
4. `verify_signature` resolves `repository_owner` as `orgA`, validates the signature against `orgA`'s secret, and passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no owner/org check) and calls `create_status_from_github!`, marking the victim commit as `success` on orgB's Stack, potentially making it `deployable?` despite belonging to a different, unauthenticated organization.
