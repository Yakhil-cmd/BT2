This confirms the exploit chain: `Shipit.github_teams` maps `oauth.teams` config strings into `Team.find_or_create_by_handle` which stores an `organization` string keyed for authorization purposes, and `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. The `MembershipHandler` at [1](#0-0)  creates/updates team membership using `params.organization.login` and `params.team.id` taken straight from the unverified webhook body, and `find_or_create_team!` matches purely on `github_id`, so a forged membership event whose `team.id` matches an authorizing team's `github_id` will add an arbitrary `member.login` to that team via `User.find_or_create_by_login!`.

Now I have enough to write the analog finding.

### Title
Webhook signature is verified against an attacker-chosen organization while handlers act on an unverified `repository.full_name` / `team.id`, allowing forged GitHub events to reach any org/repo/team — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App secret of whichever organization is named inside the **unverified** JSON body itself (`repository.owner.login`, or `organization.login` as fallback), then hands the very same raw, unauthenticated body to handlers that trust a *different* field (`repository.full_name`, or `team.id`/`organization.login` for membership) to decide which Stack/Team to mutate. Because the field used to select the signing secret is never cross-checked against the field the handler actually acts on, and because a webhook secret can be legitimately blank for any configured organization, an attacker with no Shipit credentials can forge events that are "verified" under one (weakly- or un-secured) organization while being applied to a completely different, victim organization's repository or authorization team.

### Finding Description
`verify_signature` picks the `GitHubApp` instance — and thus the HMAC secret used to check `X-Hub-Signature` — using `repository_owner`, computed purely from the request body: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the org's `webhook_secret` is blank/unset — a configuration explicitly shown as valid/optional in the docs and dummy secrets: [4](#0-3) [5](#0-4) [6](#0-5) 

Multi-org installations are officially supported, keying `Shipit.github(organization:)` per-org config, each with its own (possibly blank) `webhook_secret`: [7](#0-6) 

Once `verify_signature` passes (using the secret associated with `repository.owner.login` / `organization.login`), `create` dispatches the **entire unmodified body** to handlers, none of which re-check that `repository_owner` matches the repository/team actually being mutated: [8](#0-7) 

- `PushHandler`/`Handler#stacks` resolves the target purely from `repository.full_name`, independent of the org used for signature verification: [9](#0-8) [10](#0-9) 

- `MembershipHandler` grants/revokes team membership keyed by `team.id` (GitHub team id) and `organization.login` from the same unverified body, with no linkage back to `repository_owner`: [1](#0-0) 

Authorization to use the whole application is gated on team membership: `User#authorized?` checks whether the user belongs to any of `Shipit.github_teams`, which are `Team` records addressable by `github_id`: [11](#0-10) [12](#0-11) 

**Binding broken:** the organization that authenticated the request (`repository_owner`, matched against a `webhook_secret` that may be blank) ≠ the repository/team the handler actually writes (`repository.full_name` / `team.id`, taken from the same unverified body). No code enforces that these two attacker-controlled fields refer to the same organization.

### Impact Explanation
An unprivileged internet attacker who knows (or exploits) any organization configured on the instance with a blank/absent `webhook_secret` — a state the project's own docs and templates present as valid — can:
1. Set `repository.owner.login` to that weakly-configured org so `verify_signature` passes trivially (`return true unless webhook_secret`).
2. Set `repository.full_name` to any other tracked repository/stack (belonging to a different, properly-secured organization) to trigger `PushHandler`/other handlers against it, e.g. forcing `stack.sync_github` on arbitrary stacks.
3. For the `membership` event, set `team.id` to the `github_id` of a `Team` referenced in `Shipit.github_teams` (the authorization gate for the whole application) and `member.login` to an attacker-controlled GitHub login, causing `MembershipHandler#process` to add that login to the authorizing team — granting the attacker login access to the entire Shipit instance (escalation into `Shipit.github_teams` authorization).

This matches the High-impact category of "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires only that at least one organization configured in `config/secrets.yml`'s multi-org `github` section have a blank `webhook_secret` (explicitly shown as acceptable/optional in `docs/setup.md` and the shipped example templates), or that the attacker otherwise knows a weaker org's secret. No Shipit session, API token, or GitHub write access is needed — only knowledge of the target org/repo/team names and, if any secret is set, that secret. Multi-org Shipit deployments are a documented, supported configuration, making this a realistic misconfiguration class rather than a purely theoretical one.

### Recommendation
Bind signature verification to the exact resource the handler will act on: derive the org used both for verification and for target resolution from a single trusted field, and require handlers to assert that `repository.full_name`'s owner (and `team`/`organization` for membership events) equals `repository_owner` before mutating any record. Additionally, require `webhook_secret` to be present for every configured organization (fail closed rather than `return true unless webhook_secret`), and consider rejecting membership/team mutations unless the org in the payload matches the org whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two orgs in `github`: `weak-org` (webhook_secret unset/blank) and `victim-org` (webhook_secret set, unknown to attacker), per the multi-org format in `docs/setup.md` lines 182-209.
2. POST to `/webhooks` with header `X-Github-Event: push` and NO valid `X-Hub-Signature` needed for `weak-org`. Body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" }
}
```
`verify_signature` resolves `repository_owner` = `weak-org`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret), so the request is accepted; `PushHandler` then resolves stacks via `repository.full_name = "victim-org/victim-repo"`, acting on the victim's stack.
3. For privilege escalation, POST `X-Github-Event: membership` with:
```json
{
  "action": "added",
  "team": { "id": <github_id of an authorizing Team>, "name": "x", "slug": "x", "url": "https://x" },
  "organization": { "login": "weak-org" },
  "member": { "login": "attacker-github-login" }
}
```
Signature check again passes trivially against `weak-org`; `MembershipHandler#find_or_create_team!` matches the existing authorizing `Team` by `github_id`, and `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` grants the attacker's GitHub login membership in the team gating `current_user.authorized?`, letting the attacker's GitHub account log in as an authorized Shipit user.
