### Title
Session Fixation on Login - `Shipit::GithubAuthenticationController#callback` never rotates the session ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated]` directly into the existing session without first calling `reset_session`, while `#logout` explicitly calls `reset_session`. This asymmetry allows any pre-existing (attacker-primed) session to survive the privilege transition at login, enabling classic session fixation.

### Finding Description
The broken binding is: **at the moment of privilege escalation (successful OAuth login), the session identifier/content before login must differ from the session identifier/content after login** — i.e. `session_before_callback != session_after_callback`. Tracing `app/controllers/shipit/github_authentication_controller.rb:7-21`, `#callback` does: [1](#0-0) 
It sets `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true` directly onto whatever session object already exists for that browser — no `reset_session` call. Contrast with `#logout`: [2](#0-1) 
which does call `reset_session`. The same asymmetry exists in `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-24`), which does call `reset_session` when forcing a re-login due to stale credentials, but the successful login path (`#callback`) that actually establishes a new authenticated identity never does. [3](#0-2) 

Root cause: the engine mounts `/github/auth/github/callback` (`config/routes.rb:70-75`) as the OAuth completion endpoint, and this endpoint is reachable without any prior authentication (it is the entry point that creates authentication), so any party who can get their session cookie loaded into a browser and then have that same browser complete the OAuth callback inherits whatever pre-existing session content was already present — this is textbook session fixation per OWASP guidance (regenerate session ID on authentication). [4](#0-3) 

None of the listed guards mitigate this: `force_github_authentication` only fires on subsequent requests and is not invoked for the callback controller itself since `GithubAuthenticationController` is a plain `ActionController::Base`, not including the `Authentication` concern.

### Impact Explanation
Session fixation on its own, in the cookie-store deployment used by this engine, means: if an attacker can inject/plant session state (or session id, depending on session store backend configured by the host app) before a victim authenticates, that planted session persists post-login. This matches the High severity category explicitly listed in scope ("session fixation / forced OAuth completion"). The scoped impact described in this question is only the confirmation of the root cause; it enables (per the question) a further chained attack via `MergeStatusController#enqueue` for unauthorized merges, but that chain is out of scope for this specific question — this question is scoped only to confirming the asymmetry itself.

### Likelihood Explanation
No special Shipit configuration is required; the divergence is unconditional in the code — `#callback` never calls `reset_session` under any config value. The only precondition is the generic session-fixation precondition (attacker can get a chosen session established in the victim's browser context, e.g., shared/kiosk browser, or a subdomain-cookie-scoping trick, depending on deployment) — access requirements for that priming step are outside this engine's code, but the root-cause bug (failure to rotate session at login) is unambiguously present and independent of deployment.

### Recommendation
Call `reset_session` at the very start of `#callback`, before setting any session keys, exactly as OWASP recommends and exactly as `#logout` and `force_github_authentication` already do elsewhere in the same file/concern:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```
Note `reset_session` clears `omniauth.origin`/`return_url`, so `return_url` must be captured before the reset (as shown).

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb (extend existing file)
test "#callback does not rotate the session (fixation)" do
  user = shipit_user
  # simulate a pre-existing/fixated session value
  session[:pre_existing] = 'attacker-planted-value'
  before_session_object_id = session.to_hash.dup

  mock_auth_hash(user) # existing helper in test file builds omniauth.auth
  get :callback

  # BROKEN BINDING: session content/object persists across login boundary
  assert_equal 'attacker-planted-value', session[:pre_existing]
  assert session[:user_id].present?
end

test "#logout resets the session" do
  Shipit::GithubAuthenticationController.any_instance.expects(:reset_session)
  get :logout
end
```
The first test demonstrates `session[:pre_existing]` (standing in for a fixated identifier/value) surviving through `#callback`, while the second confirms `#logout` does call `reset_session`, proving the asymmetry the question describes.
