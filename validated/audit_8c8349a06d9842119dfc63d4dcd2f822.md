### Title
Webhook Signature Selection Uses a Different Payload Field Than the One Used to Select the Target Repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`) taken from the untrusted JSON body, while the handler that actually performs writes (`Handler#repository_name`, used e.g. by `PushHandler`) reads a *different* field of the same body — `repository.full_name` — to decide which `Stack`/`Repository` to act on. Nothing binds these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the organization whose repository is mutated.

### Finding Description
`verify_signature` derives the org used to fetch the webhook secret purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same raw params to handlers such as `PushHandler`. Handlers resolve the *actual* repository/stack to mutate from a sibling field of the same body: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then triggers a git sync against every matching stack with an attacker-chosen commit SHA: [4](#0-3) 

Shipit explicitly supports a multi-tenant configuration where several independent GitHub organizations, each with its own `webhook_secret`, are configured on a single instance: [5](#0-4) 

The binding that should hold is: `organization whose webhook_secret authenticated the request == organization that owns the repository being written to`. Because the secret-selection field (`repository.owner.login` / `organization.login`) and the write-target field (`repository.full_name`) are independent, untrusted fields inside the same attacker-suppliable JSON body, an operator who legitimately possesses one onboarded organization's `webhook_secret` (their own org's credential — no theft required) can construct an arbitrary JSON body, set `repository.owner.login` to their own org (so the correct, known secret is selected and the HMAC validates), and set `repository.full_name` to a victim organization's repository that is also managed by the same shared Shipit instance. The request is POSTed directly to `/webhooks` (bypassing GitHub delivery entirely, since only the raw body and header need to match).

### Impact Explanation
This breaks a deployment-trust boundary between tenants of a shared Shipit instance: an org that only holds credentials for its own GitHub App can forge `push` events that resolve to a different org's `Stack` via `Repository.from_github_repo_name`, causing `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` to run against a repository/stack it does not own. For stacks with continuous deployment enabled, syncing an attacker-chosen commit as the new head can make Shipit consider it eligible for auto-deploy, i.e. an unauthorized deploy path on a victim's stack — one of the explicitly in-scope High/Critical impacts. Other handlers keying off the same asymmetry (e.g. `check_suite`, `status`) can similarly write commit/CI state onto a victim stack's commits.

### Likelihood Explanation
Requires the attacker to be a legitimate operator of at least one org configured in the same multi-tenant Shipit deployment (a documented, supported configuration), and to know their own org's `webhook_secret` — a credential every onboarded org naturally has. No GitHub token, session, or victim credential is needed; only a raw HTTP POST to the public `/webhooks` endpoint with a self-computed HMAC. This is realistic for shared/hosted Shipit deployments serving multiple external organizations.

### Recommendation
Bind the secret-selection identity to the same field used for authorization of the write target: derive `repository_owner` for secret selection from `repository.full_name`'s owner segment (or vice versa), and reject the webhook if `repository.owner.login`/`organization.login` and the owner segment of `repository.full_name` disagree. Alternatively, verify the signature per-installation using an installation identifier bound to the specific repository rather than an attacker-suppliable owner login string.

### Proof of Concept
1. Attacker legitimately administers GitHub org `attacker-org`, which is configured in this shared Shipit instance with `webhook_secret = S`.
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<malicious-sha-attacker-wants-synced>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"attacker-org"`, `Shipit.github(organization: "attacker-org")` loads secret `S`, signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (from `handler.rb:37`) and calls `stack.sync_github(expected_head_sha: "<malicious-sha>")` on the victim's stack — despite the request never having originated from, or been authenticated for, `victim-org`.
