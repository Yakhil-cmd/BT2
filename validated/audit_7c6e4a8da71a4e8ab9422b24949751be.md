This confirms the contrast: `CheckSuiteHandler#process` scopes strictly via `stacks.where(branch: ...)` (repository-derived) before touching commits, while `StatusHandler#process` does a global, repository-unscoped `Commit.where(sha: params.sha)` lookup. [1](#0-0) [2](#0-1) 

### Title
Repository-unscoped `Commit.where(sha:)` lookup lets cross-repository status webhooks mutate a victim stack's commit status - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` finds commits purely by `sha`, without ever consulting the payload's `repository` field or the `stacks` helper, so any org whose webhook signature verifies can write a `Status` for a commit belonging to a stack in a completely different, victim-owned repository, provided the sha matches (e.g. via a public fork sharing history with the upstream repo).

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a webhook handler. In `StatusHandler#process` this binding is never checked at all — `process` iterates `Commit.where(sha: params.sha)` across the entire `commits` table (all stacks, all repositories) and calls `commit.create_status_from_github!(params)` for every match. [2](#0-1)  `create_status_from_github!` writes a `Status` record scoped to `stack_id` via `statuses.replicate_from_github!(stack_id, github_status)` and triggers `Hook.emit(:commit_status, ...)` / `:deployable_status` and `stack.schedule_merges`, all keyed off whichever stack the matched commit happens to belong to. [3](#0-2) [4](#0-3) 

`ExplicitParameters.requires :repository` is irrelevant to this bug: even if `repository` were required and present in the payload, `process()` never reads it — the base `Handler#stacks`/`repository_name` helpers exist precisely for this scoping purpose and are used by `CheckSuiteHandler` (`stacks.where(branch: ...)` then `stack.commits.where(sha: ...)`) but `StatusHandler` bypasses them entirely. [5](#0-4) [1](#0-0)  So the "missing `requires :repository`" framing in the question is not the actual root cause — adding that requirement would not close the gap since the field still wouldn't be used to filter the `Commit` query.

`WebhooksController#verify_signature` only authenticates that the payload was signed by *some* known organization's secret (falling back to `organization.login` when `repository` is absent), it does not bind the signer's identity to the specific repository/stack whose commit gets mutated. [6](#0-5)  Because git commit SHAs are content-addressed and identical between a public repository and any fork of it, an attacker who owns a fork of a victim's public repository (with a Shipit stack configured on the fork, giving them a valid signature) can send a `status` webhook containing an upstream commit's `sha` with an arbitrary `state`/`description`, and it will match and mutate the `Commit` row belonging to the victim's stack, since the query has no repository/stack filter at all.

### Impact Explanation
This allows an unprivileged attacker to write a `Status` (and trigger `Hook.emit(:commit_status/:deployable_status)` and `stack.schedule_merges`) against a commit belonging to a stack they do not control, for any repository whose history overlaps with a repository the attacker controls (typically via forking). Forged "success" statuses can unblock `deployable?` checks and push a victim stack toward continuous deployment/merge scheduling; forged "failure"/"error" statuses can block legitimate deploys. This is a cross-tenant write (one repository's webhook mutating another repository's stack/commit state), matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the attacker needs their own repository (e.g., a public fork of the victim's repo) onboarded to the same Shipit instance with a working webhook signature (an unprivileged, self-serve action for any GitHub user who can fork+connect a repo they own), and a target commit sha that is shared between their repo and the victim's repo/stack — a scenario that's common and low-cost for any actively forked open-source project. No GitHub App secret, session, or maintainer role on the victim repo is needed. The attack is trivially repeatable per matching sha.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits by `sha` alone) through the same repository-derived `stacks` helper used elsewhere, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, and additionally require/validate the `repository.full_name` field in the params schema so the query is bound to the authenticated repository, not just the sha value.

### Proof of Concept
```ruby
test "StatusHandler mutates a commit belonging to a different repository's stack when sha matches" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'shared commit')

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-forged',
    # note: no 'repository' key referencing victim_stack's repo at all
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).process
  end

  assert_equal 'success', victim_commit.reload.status.state
end
```
This demonstrates the binding `commit.stack.repository.full_name == payload.dig('repository','full_name')` does not hold and is never checked: the status is written to `victim_commit`/`victim_stack` even though the payload names no repository at all.
