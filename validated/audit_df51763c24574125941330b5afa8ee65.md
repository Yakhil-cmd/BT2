### Title
Cross-organization commit-status forgery via unbound `StatusHandler` lookup breaks the "authenticated organization" ↔ "repository written" binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's inbound GitHub webhook signature verification is scoped per-organization (multi-tenant `github:` config), but `StatusHandler#process` applies the verified status payload to *any* commit in the entire database matched only by `sha`, without checking that the commit's repository/organization matches the organization whose webhook secret authenticated the request.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on an **unauthenticated** field read from the payload before verification: `repository_owner` (`params.dig('repository', 'owner', 'login')`), then verifies against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [1](#0-0) 

Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, configured under distinct top-level keys in `secrets.github`. [2](#0-1) [3](#0-2) 

Once the HMAC check passes for *that org's* secret, the raw JSON body is dispatched to the handler for the event type. For `status` events, `StatusHandler#process` looks up commits **globally by SHA only** — it never consults `repository.full_name`/`repository.owner.login` at all, and never restricts the query to stacks belonging to the authenticated organization:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Contrast this with other handlers (`PushHandler`, `PullRequest::*Handler`) which do scope their side effects to a specific repository via `Handler#repository_name`/`Repository.from_github_repo_name`. [5](#0-4) [6](#0-5) 

`Commit#create_status_from_github!` writes a new `Status` and re-evaluates the commit's deployability (`Commit#deployable?`, `Status::Group`), and if the state transitions it emits `deployable_status`/`commit_status` hooks and can schedule merges/continuous delivery: [7](#0-6) [8](#0-7) [9](#0-8) 

**Binding broken:** `organization authenticated by HMAC (repository.owner.login → webhook_secret)` **should equal** `organization/repository whose commit status is written (sha → Commit → stack → repository)`. In `StatusHandler` this equality is never checked — the only trust boundary crossing is "did *some* configured org's HMAC verify," not "does this SHA belong to that org's repositories."

### Impact Explanation
In the documented multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications"), each organization has its own GitHub App and its own `webhook_secret`, and the operator/admin who configures the GitHub App for "OrgOne" legitimately knows OrgOne's `webhook_secret` (they created/own that App and put the secret into Shipit's `secrets.yml`). That party is not trusted with respect to "OrgTwo"'s repositories. Because `StatusHandler` performs a global `Commit.where(sha:)` lookup, a request that authenticates as OrgOne can forge a `status` webhook (correctly HMAC-signed with OrgOne's secret) whose `sha` collides with a commit belonging to a stack under OrgTwo (or any other tenant). This lets an attacker who only controls one tenant's webhook secret mark an arbitrary commit in a different tenant's repository as `success`, satisfying `Commit#deployable?`/required-status checks and triggering `schedule_merges` / `ContinuousDeliveryJob` for a repository they have no legitimate access to — i.e., an unauthorized deploy/merge across the trust boundary between tenants. This matches the "High"/"Critical" impact bar (escalation into another repository's deploy authorization).

### Likelihood Explanation
Exploitation requires: (1) the instance is configured with the documented multi-organization `github:` config (an explicitly supported, documented feature), and (2) the attacker knows/controls the `webhook_secret` for at least one configured organization (e.g., they are the admin of that org's GitHub App, which is exactly the kind of "less-trusted org" scenario multi-tenancy is meant to isolate). Given that, forging a `status` event and guessing/observing a target SHA (SHAs are public on GitHub, e.g. via commits on a public repo or via the target stack's commit list in Shipit's own UI) is trivial — no other Shipit credentials, sessions, or API tokens are needed.

### Recommendation
Bind the authenticated organization to the data being written. `Handler` (and specifically `StatusHandler`, `CheckSuiteHandler`, `CheckRunHandler`, etc.) should scope lookups through the `repository.full_name`/`repository.owner.login` from the payload and verify that this repository's owning organization matches the organization used to authenticate the webhook (the one whose secret produced a valid HMAC), rejecting the event (or scoping `Commit.where(sha:)` to `stacks.where(repository: Repository.from_github_repo_name(repository_name))`) if the SHA's owning stack does not belong to that organization. This restores the same "org authenticated == org written" invariant that `PushHandler`/`PullRequest::*` already partially rely on via `repository_name`.

### Proof of Concept
1. Configure Shipit in multi-org mode with two tenants, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret` values (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker is the legitimate admin of `OrgOne`'s GitHub App and thus knows `OrgOne`'s `webhook_secret`. They have no access to `OrgTwo`.
3. Attacker observes (via GitHub's public API or the Shipit UI, which shows commit SHAs) that stack `OrgTwo/critical-app` has a pending/undeployed commit with SHA `abc123...` that is blocked by a required CI check.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
   ```json
   { "sha": "abc123...", "state": "success", "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/some-repo" } }
   ```
   signed with `X-Hub-Signature: sha1=<HMAC using OrgOne's webhook_secret>`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, and the HMAC verifies successfully (attacker used the correct, but wrongly-scoped, secret). [10](#0-9) 
6. `StatusHandler#process` runs `Commit.where(sha: "abc123...")` — finds the `OrgTwo` commit regardless of the authenticated org — and calls `create_status_from_github!`, marking it `success`. [4](#0-3) 
7. The commit in `OrgTwo/critical-app` becomes `deployable?` / triggers `schedule_merges`/`ContinuousDeliveryJob`, resulting in an unauthorized deploy or merge in a repository the attacker was never authorized to affect.

**Uncertainty:** I could not fully trace whether `ContinuousDeliveryJob`/`schedule_merges` unconditionally results in an actual deploy without further gating (e.g., branch protection, additional required statuses, or manual approval configured in `shipit.yml`) — this would need to be confirmed in a live/test environment, since `shipit.yml` step execution and CD gating logic live outside the files inspected here. The core cross-tenant write (forged commit status on an unauthorized repository/commit) is nonetheless directly demonstrated by the code paths cited above.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
