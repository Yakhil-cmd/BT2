## Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to validate a webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [1](#0-0) [2](#0-1)  However, once the signature is accepted, the actual event handlers resolve which `Stack`/`Repository` to act on using a *different* field: `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`. [3](#0-2)  These two fields are never checked for consistency with each other, so the organization whose secret authenticated the request is not necessarily the organization whose repository gets acted upon.

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications"). [4](#0-3)  `Shipit.github(organization: repository_owner)` looks up the app/secret keyed by `repository_owner`, and `verify_webhook_signature` HMAC-validates the raw body against that org's secret: [5](#0-4) .

Crucially, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that resolved organization (`return true unless webhook_secret`). [6](#0-5)  Combined with the fact that the *target* of the operation is read from a completely separate field (`repository.full_name`), an attacker who controls (or has installed the Shipit GitHub App on) one tracked organization — call it `orgA` — can post directly to `/webhooks` with:

- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) — selects `orgA`'s webhook secret/app for verification, which the attacker can compute/replay because they legitimately administer `orgA`, or because `orgA` has no `webhook_secret` configured at all (bypasses verification entirely).
- `repository.full_name = "orgB/target-repo"` — the value actually consumed by `Handler#repository_name`/`#stacks` to resolve the `Stack` to act on. [3](#0-2) 

This forged, `orgA`-signed payload is then dispatched to handlers exactly as if it were a legitimate `orgB` event: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack whose `Repository` matches `orgB/target-repo`, on the branch the attacker specifies. [7](#0-6)  `CheckSuiteHandler` and `StatusHandler` have the identical structural issue: they consume `params.check_suite.head_sha` / `params.sha` and target stacks resolved via the same `repository_name`/`stacks` helper, entirely independent of the authenticated org. [8](#0-7) [9](#0-8) 

This is a direct analog of the reported bug class: the quantity that is cryptographically bound/verified (`repository.owner.login`, driving the secret selection) is not the same quantity that downstream logic actually acts on (`repository.full_name`), exactly the "organization that authenticated versus the repository that is written" binding the task calls out.

### Impact Explanation
`GithubSyncJob`, enqueued by `PushHandler` via `stack.sync_github`, fetches commits from the real GitHub API for the resolved stack/org and appends them to the stack's commit history, and unlocks reverted commits: [10](#0-9) . Because Shipit's merge queue / continuous-deployment features act on this synced commit history, an attacker who is only a legitimate admin/installer of `orgA` (with no access to `orgB`) can force Shipit to sync/refresh state for `orgB`'s stacks on arbitrary branches, and forge `status`/`check_suite` completion signals for arbitrary commits in `orgB`'s repositories via `StatusHandler`/`CheckSuiteHandler`, which are inputs used elsewhere to gate merges/deploys. This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly listed as in-scope, and can escalate to unauthorized cross-repository state changes / merges depending on `orgB`'s CI-gated merge queue configuration.

### Likelihood Explanation
Exploitability only requires that the Shipit instance is configured for multiple GitHub organizations (an explicitly documented, supported configuration) and that the attacker legitimately controls one of them (or that one configured org lacks a `webhook_secret`, which `verify_webhook_signature` explicitly tolerates). No GitHub App private key, `ApiClient` token, or session is required — only the ability to POST to the public `/webhooks` endpoint with a body whose `repository.owner.login`/`organization.login` differs from `repository.full_name`'s owner.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, ensure the organization used to select/verify the webhook secret is derived from (and cross-checked against) the same repository identity (`repository.full_name`'s owner) that handlers use to resolve the target `Stack`/`Repository`. Reject any payload where `repository.owner.login` does not match the owner portion of `repository.full_name`. Also consider making `webhook_secret` mandatory (fail closed) rather than defaulting to `true` when absent.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (contains a tracked stack, e.g. `orgB/target-repo`), per `docs/setup.md`'s multi-org example. [4](#0-3) 
2. Compute `sha1=HMAC(orgA_webhook_secret, body)` over a JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `POST /webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner = "orgA"`, verifies successfully against `orgA`'s secret. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `repository.full_name = "orgB/target-repo"` [3](#0-2)  and enqueues `GithubSyncJob` for `orgB`'s stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated against `orgB`'s credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
