### Title
Signature verification uses `repository.owner.login` while handlers resolve the target repository from `repository.full_name`, letting an attacker's own webhook signature authorize actions against an unrelated victim repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the organization used to select the HMAC secret from `params.dig('repository','owner','login')` [1](#0-0)  while every downstream handler, including `LabeledHandler`, resolves the actual `Repository`/`Stack` to act on from the independent field `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [2](#0-1) . Because the attacker fully controls the raw JSON body and only needs to sign it with their own org's `webhook_secret`, these two fields can be set to different values, breaking the intended binding that "the organization whose secret verified the payload" equals "the organization whose stack gets mutated."

### Finding Description
The intended security invariant is: `organization_whose_secret_verified_payload == organization_owning_repository_acted_upon`. The code computes the left side from `repository.owner.login` [3](#0-2)  and `Shipit.github(organization: repository_owner)` to pick the per-org `webhook_secret` used in `GitHubApp#verify_webhook_signature` (a plain HMAC-SHA1 compare) [4](#0-3) . It computes the right side from an entirely separate JSON field, `repository.full_name`, in `Handler#repository_name`/`LabeledHandler#repository` [5](#0-4) [2](#0-1) . Nothing in `WebhooksController#create` or `Handler#initialize` cross-checks that the owner segment of `full_name` matches `repository.owner.login`.

An attacker who owns their own GitHub App/org (`attacker-org`, with a `webhook_secret` they legitimately know) can POST to `/webhooks` a `pull_request` "labeled" payload where `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` is selected and the HMAC computed with the attacker's own secret validates), but `repository.full_name = "victim-org/victim-repo"`. `verify_signature` passes because the signature is a valid HMAC of the raw body under the attacker's own known secret - the signature check never inspects `full_name`. `LabeledHandler#repository` then resolves the actual `victim-org/victim-repo` `Repository` record, and `respond_to_label_change?`/`pull_request_has_provisioning_label?` operate on that victim repository's `provisioning_behavior`/`provisioning_label_name`, potentially calling `stack.unarchive!` and routing through `ReviewStackAdapter` against `repository.review_stacks` [6](#0-5) , and further downstream `ReviewStackAdapter#unarchive!`/queueing provisioning for a stack the attacker never authenticated against.

None of the existing guards close this gap: `verify_signature` only proves the attacker knows *some* org's secret, not that that org owns the acted-upon repo; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schema only validates types/presence, not cross-field consistency; and `Repository.from_github_repo_name` performs a straightforward, un-scoped lookup by the untrusted `full_name` string.

### Impact Explanation
A payload authenticated for one repository/organization is used to mutate another organization's `Stack`/`ReviewStack` state - unarchiving and re-provisioning a review stack, and enqueuing `Shipit::ReviewStackProvisioningQueue.add` work for it - which the attacker's credentials never authorized. This matches the "Critical: a payload for one repository mutating another's stack... or an unauthorized deploy" category. Because any org that Shipit trusts (including a small/less-sensitive org the attacker legitimately owns) can be used as the signing identity while `full_name` freely names any tracked victim repository, this is repeatable against any repository/stack tracked by the Shipit instance, not limited to one tenant.

### Likelihood Explanation
Preconditions: the attacker must own or control a GitHub App/organization that is configured in this Shipit instance with its own `webhook_secret` (i.e., be a legitimate, even if low-privilege, tenant of the same Shipit deployment) - Shipit must be configured with the multi-organization `github_app_config` scheme rather than falling back to a single default org (`github_default_organization`). Given that precondition, the attack costs nothing more than crafting and POSTing a JSON body and computing one HMAC-SHA1 with a secret the attacker already knows; it is trivially repeatable and scriptable against arbitrary victim `full_name` values already tracked as `Repository` records with `review_stacks_enabled`.

### Recommendation
Bind the field used for signature-organization selection to the same field used for resolving the acted-upon repository. Concretely, in `Handler#initialize`/`WebhooksController#create`, require that `repository.owner.login` (used to pick the webhook secret) matches the owner segment parsed from `repository.full_name`, and reject the payload (422) on mismatch before dispatching to any handler. Alternatively, verify the signature using the organization derived from `full_name` exclusively rather than `owner.login`, so there is a single source of truth for "which org's secret must validate this payload."

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or a new `LabeledHandler` test), simulate:
1. Two orgs configured in `Shipit.stubs(:github)`/`github_app_config`: `attacker-org` (with a known `webhook_secret`) and `victim-org` (unrelated stack `victim_stack` with `review_stacks_enabled` and a `ReviewStack` matching a PR number).
2. Build a `pull_request`/`labeled` JSON payload with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, PR labeled with the victim's `provisioning_label_name`.
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(attacker-org's known `webhook_secret`, raw_body).
4. POST to `/webhooks` with that signature.
5. Assert `response.status == 200` (signature accepted) and assert `Shipit::ReviewStackProvisioningQueue.add` (or `stack.unarchive!`) was invoked for `victim_stack`, proving that a signature valid only for `attacker-org` triggered provisioning of `victim-org`'s stack - i.e., `organization_whose_secret_verified_payload ("attacker-org") != organization_owning_stack_that_gets_unarchived_and_provisioned ("victim-org")`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
