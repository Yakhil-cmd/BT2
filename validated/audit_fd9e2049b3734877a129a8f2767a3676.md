### Title
Webhook Organization/Secret Selection Is Decoupled From The Repository Acted On, Allowing Cross-Organization Deploy Triggering - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using the organization login taken from the request body itself, but the downstream event handlers select the target `Stack`/`Repository` to act on using a *different* field of the same, entirely attacker-controlled JSON body. Nothing binds these two fields together, so a party who legitimately controls the webhook secret for *any one* organization configured on the Shipit instance can forge a `push` payload that authenticates as their own org while targeting a `Stack` that belongs to a completely different organization/repository.

### Finding Description
`verify_signature` computes the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). `Shipit.github(organization: repository_owner)` picks the `GithubApp`/`webhook_secret` configured for that org (see the multi-org config documented in README.md, e.g. separate `webhook_secret` per organization). The signature is a valid HMAC over the full raw body computed with *that org's* secret — so anyone who knows one org's `webhook_secret` (i.e., legitimately controls that org's own GitHub App/webhook config) can produce a validly-signed payload for arbitrary JSON content, as long as `repository.owner.login` (or `organization.login`) in that JSON still names their own org.

However, once the signature passes, `WebhooksController#create` dispatches to handlers using an entirely separate field: [3](#0-2) 

Handlers such as `PushHandler` resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, not via `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used for secret selection) and `repository.full_name` (used for target-repository resolution) are independent JSON fields with no cross-check, an attacker can set `repository.owner.login = "their-own-org"` (to pass signature verification with a secret they legitimately hold) while setting `repository.full_name = "victim-org/victim-repo"` (to target a `Stack` they do not control). This breaks the binding: *organization that authenticated the request* ≠ *repository/stack that the request acts on*.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha:)` for every non-archived stack matching the target branch, which enqueues `GithubSyncJob` for the victim `Stack`'s real `stack_id`: [6](#0-5) 

This forces the victim stack to fetch its actual latest commits from GitHub (via `stack.github_api`, using the victim repo's real credentials/config) and, if the stack has continuous delivery enabled, can trigger an unauthorized deploy of the victim repository/branch — an action the attacker (who only controls a different organization's webhook secret) has no legitimate authority to invoke. This matches the "unauthorized deploy" impact category. Similar decoupling exists for other handlers keying off `repository.full_name` / `organization.login` (e.g., pull_request handlers), broadening the blast radius to any multi-tenant Shipit deployment where more than one GitHub App/organization is configured with distinct `webhook_secret`s.

### Likelihood Explanation
Exploitability is limited to Shipit deployments that configure multiple GitHub organizations under `Shipit.github(organization: ...)`, each with its own `webhook_secret` (a supported, documented configuration, per README.md's multi-org example). Within such a deployment, any org onboarded to the shared Shipit instance — who legitimately possesses only their own org's webhook secret — can exploit this to reach stacks belonging to other onboarded organizations. Likelihood is Medium: it requires a specific (but supported and documented) multi-tenant configuration, and the "attacker" is a legitimately onboarded but otherwise unprivileged organization relative to the victim organization's resources.

### Recommendation
Bind signature verification to the same identifier used for target resolution. Concretely: after resolving `stacks`/`repository` in each handler, verify that the resolved `Repository`'s owning organization matches the organization whose secret validated the signature (`repository_owner` computed in `verify_signature`), and reject the webhook otherwise. Alternatively, derive `repository_owner` from `repository.full_name`'s owner segment (the same field used by `Handler#repository_name`) rather than from the separate `repository.owner.login`/`organization.login` fields, so a single authoritative field governs both secret selection and target resolution.

### Proof of Concept
1. Attacker legitimately controls Organization A's GitHub App on the shared Shipit instance and therefore knows Organization A's `webhook_secret` (configured per `Shipit.github(organization: 'org-a')`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim head sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-webhook-secret, body)>` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "org-a"`, fetches Organization A's `GithubApp`, and the signature validates successfully.
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name') == "org-b/victim-repo"` [4](#0-3) , finds Organization B's `Stack`, and calls `stack.sync_github`, enqueuing `GithubSyncJob` for a stack the attacker does not own — forcing a sync/potential deploy of `org-b/victim-repo` despite the request only being authenticated for `org-a`.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
