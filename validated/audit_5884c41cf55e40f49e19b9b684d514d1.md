### Title
Position NFT `approve()` re-grant can be front run by the current approved operator to seize the entire lending account - (File: contracts/position-nft/src/contract.rs)

### Summary
The original report describes the classic allowance race: an owner's `approve()` that reduces/replaces an existing spender's power can be front run by that spender, who exercises the old authorization before the new one lands. XOXNO Lending has no fungible share token with an `approve` (RAY supply/debt shares are internal pool ledger state), so the class cannot land on pool tokens. It does land, with strictly worse impact, on `contracts/position-nft`, where `approve` grants a single operator the unconditional power to call `transfer_from` on a token whose id *is* the controller account id — so the approved operator holds the power to move the borrower's entire position (all collateral and debt) until `live_until_ledger`. An owner who tries to revoke or replace that approval by submitting a second `approve` can be front run exactly as in the reported bug, and the spender takes the whole account rather than a partial allowance.

### Finding Description
`PositionNft` exposes the stock OpenZeppelin `NonFungibleToken` surface: `approve(approver, operator, token_id, live_until_ledger)`, `approve_for_all`, and `transfer_from(spender, from, to, token_id)` (contract.rs:131-133, and the pinned behavior in `contracts/position-nft/src/test.rs:135-158`). Per `scripts/permissionless_entrypoints.txt:112-113`, `transfer_from` needs only `spender.require_auth` plus being the owner, the live approved address, or an `approve_for_all` operator, and `approve` is limited to the holder or that holder's operator.

The race:

1. Owner O approves operator B for `token_id` N (account N), with `live_until_ledger` far in the future.
2. O later submits `approve(O, C, N, ...)` to replace B (or `approve` to a sentinel/zero to revoke).
3. B observes O's revocation transaction in flight and submits `transfer_from(B, O, B, N)` first. Since B's approval is still live and the transfer clears the per-token approval (test.rs:156-157), B's transaction succeeds.
4. O's `approve` then executes harmlessly against a token B already owns.

Token id == account id (contract.rs:1-2, 54-55), so `transfer_from` hands B control of the entire controller account: its supplied collateral, borrow positions, and delegate surface. The allowance race on a fungible token in the source report cost the delta between two allowances; here it costs the whole account.

### Impact Explanation
Theft of user funds: the front-running approved operator captures the victim's entire lending account — every collateral position and the ability to act on it — rather than an extra slice of allowance as in the ERC20 case. An unprivileged spender reaches it through only public entrypoints (`approve`, `transfer_from`).

### Likelihood Explanation
Requires a precondition: the owner must first grant a live approval to an operator who later proves malicious (e.g., a marketplace, delegate service, or compromised integration), and must then attempt to revoke or replace it rather than transferring the NFT to safety first. Front-running is feasible because Stellar/Soroban transactions are publicly visible before inclusion and `transfer_from` needs only the spender's own authorization. Given the magnitude of impact relative to the source report (whole account vs. partial allowance), this maps at least at the same Medium severity.

### Recommendation
Document that `approve`/`approve_for_all` on the position NFT confers immediate, total account control and should be treated as transferring the account; revocation via a second `approve` is not safe against a watching operator. Optionally add a `revoke`-style path or recommend owners transfer the token to a fresh address they control when an approval must be unwound, since `transfer_from` clears the approval atomically.

### Proof of Concept
```
1. O owns token_id N (controller account N holding collateral).
2. O calls position-nft.approve(O, B, N, live_until) — B is now the live operator.
3. O submits approve(O, C, N, live_until') to reassign the approval.
4. B sees step 3 pending, submits transfer_from(B, O, B, N); it lands first.
   - spender B is the live approved address -> auth passes
   - stock update moves owner to B and clears the approval
5. Step 3 executes on token now owned by B; B rejects it (approver is not owner/operator) or it is meaningless.
Result: B owns account N outright.
```

One caveat I could not fully verify: whether `docs/explanation/threat-model.md` explicitly accepts this operator-revocation race as a documented user-responsibility design choice — the grep showed multiple `approve` mentions there but I did not read the lines, and the pinned test at `test.rs:136-157` shows the stock OZ semantics are intentional. If the threat model documents it as accepted, this finding should be downgraded accordingly.
