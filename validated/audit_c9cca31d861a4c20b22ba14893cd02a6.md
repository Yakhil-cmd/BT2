### Title
Reachable assertion-style crash when validating a payment input that spends a stable output marked `temp-bad` - (File: `validation.js`)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a hard `throw Error(...)` that is executed on the normal unit-validation code path whenever a payment input references a source output that is stable (`main_chain_index <= last_ball_mci`) but whose `sequence` is `'temp-bad'`. This is the same bug class as CVE-2017-13750: a reachable "invariant must never happen" assertion/abort placed directly in the parsing/validation path of externally supplied data, which crashes the process instead of being handled as a normal validation error.

### Finding Description
Inside the per-input handling of `case "transfer"` in `validatePaymentInputsAndOutputs`, the code fetches the source output of a claimed input and inspects its `sequence` state: [1](#0-0) 

By design, `sequence` is expected to only ever be `'good'`, `'final-bad'`, or transiently `'temp-bad'` while a conflict is being resolved; once a unit becomes stable, its sequence must have resolved to either `'good'` or `'final-bad'` — `'temp-bad'` for a *stable* unit is treated by the developers as an impossible state, hence the `throw Error(...)` instead of `return cb(...)`. Unlike every other validation branch in this function, which returns a graceful error to the caller via `cb(...)`, this line throws inside a `conn.query` callback. This is an unhandled exception with respect to the outer `async` control flow (`checkForDoublespends`/`validatePaymentInputsAndOutputs` do not wrap this callback in try/catch), so it propagates up and crashes the Node.js process that is validating the unit.

The trigger is fully attacker-reachable: any unpaired user can post a unit whose `payload.inputs` contains a `"transfer"` input pointing (`unit`, `message_index`, `output_index`) at any existing output on the DAG. All the attacker needs to do is get the referenced output into a state where its `sequence` is `'temp-bad'` while it is also stable in the parents of the new unit — i.e., exploit the double-spend/non-serial resolution logic (`checkForDoublespends`, `main_chain.js` stabilization) to leave a `temp-bad` sequence value un-resolved past the stabilization point, then submit a spending unit that references it. No special privileges, hub access, or protocol-level compromise are needed — this is reachable purely through unit content that any node will validate upon receipt (`validateMessage` → `validatePaymentInputsAndOutputs`). [2](#0-1) 

### Impact Explanation
A successful trigger throws an uncaught exception during unit validation on every full node that processes the crafted unit, crashing the node process. Because unit validation happens on all nodes that receive/relay the unit (this is core DAG validation, not a single node's local state), an attacker can craft one unit that, once broadcast, crashes every honest node that attempts to validate it — a network-wide denial-of-service that prevents the network from confirming new units, matching the "network unable to confirm new units" impact class called out in scope.

### Likelihood Explanation
Reaching the `throw` requires the attacker to engineer a specific DAG state (a stable output whose `sequence` field is `'temp-bad'`), which in turn depends on the correctness of the double-spend/non-serial resolution logic in `main_chain.js` and `checkForDoublespends`. I was not able to fully verify, within the scope of this investigation, whether the current stabilization logic in `main_chain.js` can actually leave a `'temp-bad'` sequence on a unit that becomes stable (the intended invariant is that it cannot), so likelihood depends on whether that invariant can be violated by a crafted sequence of conflicting units. Regardless of how hard it is to reach, the presence of a raw `throw` (rather than a normal validation error) on this path is a code-quality/robustness issue directly analogous to the JasPer reachable-assertion CVE: if the invariant is ever violated (by a corner case in double-spend resolution, an edge case in light/hub interaction, or a future regression), the result is an unconditional process crash rather than unit rejection.

### Recommendation
Replace the `throw Error("spending a stable temp-bad output " + input.unit)` with a graceful `return cb("spending a stable temp-bad output " + input.unit)`, consistent with the handling of the `'final-bad'` case immediately below it. This converts an unrecoverable process-crashing invariant violation into an ordinary unit-rejection, eliminating the DoS vector regardless of whether the `temp-bad`-while-stable state is currently reachable. It would also be worth auditing `main_chain.js`'s stabilization logic to confirm the invariant that stable units cannot retain `sequence='temp-bad'`, and adding defensive handling (try/catch or `return cb(...)`) around other similar `throw Error(...)` statements in `validatePaymentInputsAndOutputs` (e.g., line 2451 `"more than 1 src output"`, line 2591 `calcFunc`'s `ifError`) that sit on data-dependent code paths reachable from externally supplied units.

### Proof of Concept
1. Attacker crafts a sequence of conflicting units targeting a specific output such that, due to a corner case in double-spend/non-serial resolution (`checkForDoublespends` in `validation.js` and stabilization in `main_chain.js`), an output remains marked `sequence='temp-bad'` in the `outputs`/`units` tables at the moment it becomes stable (`main_chain_index <= last_ball_mci`).
2. Attacker then posts a new unit with a `payment` message whose `payload.inputs` includes a `"transfer"` input with `{unit, message_index, output_index}` pointing at that output.
3. When any node validates this new unit, `validatePaymentInputsAndOutputs` executes the query at `validation.js:2443-2448`, finds `bStableInParents === true` and `src_output.sequence === 'temp-bad'`, and executes `throw Error("spending a stable temp-bad output " + input.unit)` at `validation.js:2458`, crashing the validating process instead of returning a normal validation error.
