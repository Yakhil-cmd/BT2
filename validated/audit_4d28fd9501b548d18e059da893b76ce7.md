### Title
Custom-Asset Dust Outputs Sent to an AA Address Are Never Filtered, Allowing an Unbounded UTXO Set That Blocks the AA From Ever Spending That Asset - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit()` → `completePaymentPayload()` selects the UTXOs an AA will spend to build a response payment by querying all unspent, unused outputs for the AA's address and iterating over them one by one until the target amount is reached. For the base (bytes) asset this query filters out "dust" outputs below `FULL_TRANSFER_INPUT_SIZE` to defend against exactly this class of attack, but for any custom (non-base) asset no such minimum-amount filter exists. Any unprivileged unit poster who can send a transferable custom asset to an AA's address can create an unbounded number of dust outputs of that asset. When the AA later needs to pay out that asset (e.g., as part of a refund/response), it must select coins from that unbounded set, and none of the size/robustness limits that normally protect a payment message from becoming arbitrarily large apply to AA-generated units.

### Finding Description
`readStableOutputs()` and `readUnstableOutputsSentByAAs()` in `aa_composer.js` build the SQL that selects the AA's spendable coins: [1](#0-0) [2](#0-1) 

Note the comment explaining the intended anti-dust mitigation and how it is implemented only for the base asset:
```
// byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond
```
The SQL condition is:
```
asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+"
```
When `asset` is a custom asset (non-`base`), the `AND amount>=FULL_TRANSFER_INPUT_SIZE` clause is entirely absent — there is no lower bound on the amount, and no `LIMIT`. Any dust-amount output of that asset sent to the AA's address is a candidate coin.

The rows returned are consumed one‑by‑one by `iterateUnspentOutputs()`, which unconditionally pushes every selected row into `payload.inputs`: [3](#0-2) 

Normally, `validatePaymentInputsAndOutputs()` in `validation.js` caps the number of inputs per payment message and the overall unit size — but both checks explicitly exempt AA-generated units: [4](#0-3) [5](#0-4) 

Because an attacker (an ordinary, unprivileged unit poster) can send arbitrarily many transferable-asset outputs of arbitrarily small amount to the AA's address, and the coin-selection query for that asset has no amount floor and no cap on the number of candidate rows examined, the number of inputs the AA must gather to satisfy a target amount of that asset is unbounded. This mirrors the reported bug class exactly: many small "deposits" (tiny asset outputs) accumulate at a target address, and any future operation requiring that target's balance to be spent (here, an AA response/refund of that asset) must loop through all of them, and the normal guard rails that would prevent the loop from becoming unbounded (max-inputs-per-message, max-unit-size) are bypassed specifically for AA units.

### Impact Explanation
This can permanently degrade or block an AA's ability to pay out a custom asset:
- The generated response unit's payload can grow to reference thousands of dust inputs, producing a unit whose size/commission calculations, hashing, and DB writes become extremely expensive, and which — because the size checks are skipped for AA units — is not rejected by `MAX_UNIT_LENGTH`/`MAX_INPUTS_PER_PAYMENT_MESSAGE` at the point of construction.
- If the AA is expected to refund/return that specific asset amount to users (a common oscript pattern, e.g. `payment` message paying back `trigger.output[[asset=$asset]]`), an attacker who front-runs the AA's balance with thousands of dust outputs of that asset can make every subsequent AA response involving that asset extremely resource-intensive or effectively force it into a state where it repeatedly fails/bounces (e.g., running out of bytes fees while iterating, per the very DoS mechanism the base-asset mitigation was designed to prevent) — this is a fund-freezing/DoS condition against AA logic that depends on spending or refunding that asset. This fits the "AA fund loss or freezing" and "network unable to confirm new units" impact categories (very large/expensive AA-generated units), matching the severity class of the reported bug (permanent inability to process refunds/claims due to unbounded per-deposit loop).

### Likelihood Explanation
Likelihood is high for AAs that hold/transfer custom, non-auto-destroyed, transferable assets and pay them back to users based on received amounts (a common bounce/refund/vault pattern seen throughout the AA test suite, e.g. sample oscripts computing `trigger.output[[asset=$asset]]` and paying it back). Any unprivileged party can issue/transfer such an asset (subject to normal asset issuance rules) and send unlimited small-amount outputs to the target AA address at negligible cost, since only the base-asset dust threshold is enforced. No special privilege beyond normal transaction posting is required.

### Recommendation
Apply an equivalent minimum-amount ("dust") filter for non-base assets in `readStableOutputs()`/`readUnstableOutputsSentByAAs()` in `aa_composer.js`, proportional to the fee cost of including that input (analogous to `FULL_TRANSFER_INPUT_SIZE` for bytes), or cap the number of asset inputs selected per response (e.g., via `LIMIT`) and fall back to bouncing/deferring if the target amount cannot be reached within that cap. Additionally, consider re-enabling `MAX_INPUTS_PER_PAYMENT_MESSAGE` and unit-size checks for AA-generated payment messages (or introducing an AA-specific bound) so a malicious accumulation of dust outputs cannot produce unbounded response units.

### Proof of Concept
1. Attacker issues/holds a transferable custom asset `X` (not auto-destroyed, not fixed-denomination) that is used by a target AA (the AA's oscript logic refunds/pays out `X` based on amounts it receives, a common pattern).
2. Attacker crafts and posts many units, each sending a tiny amount (e.g., 1 unit) of asset `X` to the AA's address — there is no per-address/per-asset cap on number of outputs a user can create.
3. When the AA is triggered and needs to build a payment message paying out asset `X` (e.g., in `completePaymentPayload` inside `sendUnit()`), `readStableOutputs()` runs a query with no lower-bound filter on `amount` for asset `X` and no `LIMIT`, returning all of the attacker's dust outputs as candidate inputs.
4. `iterateUnspentOutputs()` accumulates inputs from this unbounded set until `target_amount` is reached; because `objValidationState.bAA` bypasses `MAX_INPUTS_PER_PAYMENT_MESSAGE` and `MAX_UNIT_LENGTH` checks in `validation.js`, the resulting unit can carry an extremely large number of inputs, producing a very expensive/oversized AA response or causing the AA to fail (bounce) when trying to cover fees for such a large input set — reproducing the "block all refunds by adding many deposits" condition against the AA's custom-asset payout path.
