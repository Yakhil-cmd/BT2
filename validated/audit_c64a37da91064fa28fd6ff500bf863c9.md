The claim rests on an incorrect premise. `RandomnessConfig::fetch` in `aptos-move/aptos-vm-environment/src/prod_configs.rs` is defined but is not invoked anywhere along the `vm-validator` admission path (`AptosVM::validate_transaction`) or in the `AptosVM` execution path in this codebase — a repo-wide search for its call sites returns none. [1](#0-0) 

Even setting that aside, the actual `RequiredGasDeposit`/`AllowCustomMaxGasFlag` config update flow works exactly as intended: `set_for_next_epoch` buffers the new value via `config_buffer::upsert`, and only `on_new_epoch` (invoked from `reconfiguration_with_dkg::finish`, itself only reachable via privileged governance/framework signer) commits it into the resource that `RequiredGasDeposit::fetch_config`/`AllowCustomMaxGasFlag::fetch_config` read. [2](#0-1) [3](#0-2)  Any code path that fetches this config (via `OnChainConfig::fetch_config(state_view)`) simply reads whatever value exists in that `state_view` snapshot — this is the same pattern used for every other on-chain config (gas schedule, features, consensus config, etc.) throughout Aptos, and is not a bug specific to randomness config. [4](#0-3) 

Architecturally, `vm-validator`'s `validate_transaction` is a best-effort mempool admission filter operating on the latest checkpoint state view, while final enforcement of prologue/epilogue checks (sequence number, gas payment, expiry, chain-id, etc., in `transaction_validation.move`) happens authoritatively inside `AptosVM` execution against the state view of the block actually being executed. [5](#0-4) [6](#0-5)  If validator-time and execution-time state views straddle an epoch boundary, execution's checks remain authoritative and any mismatch is resolved deterministically at commit — this is inherent to every on-chain config used in transaction processing, not an admission-bypass. Even hypothetically, a stale gas-deposit-amount readout affects gas/deposit accounting economics, not sender, signer set, fee payer, sequence, expiry, chain-id, or domain binding, so it does not satisfy the Admission Impact Gate's required impact categories (unauthorized execution under wrong sender/signer, replay/expiry/domain-binding bypass, authenticator/approval-set confusion, or pre-validation mismatch causing an otherwise-failing transaction to commit under the wrong identity). No corruption of sender/signer/replay/domain guarantees results from this code.
