### Title
Naive comma-split inline-dict parser in `extract_frontmatter` corrupts `pattern` values containing commas/colons, silently neutering hookify guard rules - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter`'s inline-dict branch (`if ':' in item_text and ',' in item_text`) splits a `- field: ..., operator: ..., pattern: ...` list item on every comma before splitting each fragment on the first colon. Any `pattern` value that itself contains a comma (e.g. a regex quantifier like `{1,3}`) gets shredded into multiple spurious dict keys, truncating the real pattern that later becomes `Condition.pattern`.

### Finding Description
In `extract_frontmatter` (plugins/hookify/core/config_loader.py, lines 163-172), when a YAML list item is written inline (`- field: file_path, operator: regex_match, pattern: <regex>`), the parser does:
```python
if ':' in item_text and ',' in item_text:
    item_dict = {}
    for part in item_text.split(','):
        if ':' in part:
            k, v = part.split(':', 1)
            item_dict[k.strip()] = v.strip().strip('"').strip("'")
    current_list.append(item_dict)
``` [1](#0-0) 

This blindly splits `item_text` on every `,`, regardless of whether the comma is inside the `pattern` value. For a rule such as:
```
- field: file_path, operator: regex_match, pattern: \.(env|pem){1,2}:secret$
```
the split produces fragments `"field: file_path"`, `" operator: regex_match"`, `" pattern: \.(env|pem){1"`, `"2}:secret$"`. Each fragment containing a `:` is independently split into a key/value, so the resulting dict becomes `{field: file_path, operator: regex_match, pattern: "\.(env|pem){1", "2}": "secret$"}` - the intended pattern is truncated to `\.(env|pem){1` and a bogus extra key `2}` is injected and then discarded (since `Condition.from_dict` only reads `field`, `operator`, `pattern` via `data.get(...)`). [2](#0-1) 

This corrupted pattern then flows unchanged into `RuleEngine._check_condition` -> `_regex_match`, which compiles and matches against `field_value` with no validation that the reconstructed pattern matches the rule author's intent. [3](#0-2) 

Because hookify's own documentation and skill files openly recommend and demonstrate the inline single-line format for conditions, and rule files (`.claude/hookify.*.local.md`) are ordinary repository content that can be added or edited via a normal pull request, an attacker can submit a "security" rule (e.g., "block edits that add secrets/API keys to `.env` files") using an inline condition whose `pattern` regex happens to contain a comma. A reviewer inspecting the diff sees a plausible, correctly-worded regex, but the actual enforced pattern silently becomes a truncated/garbled regex due to this parser bug - either failing to match the dangerous input (false-negative bypass of the guard) or matching much more broadly (false-positive over-block/DoS of legitimate edits).

### Impact Explanation
This is a parser-differential bug: the pattern string a human reviews in the rule file is not the pattern string that actually gets enforced by `RuleEngine`. For a security-relevant guard rule (blocking edits to secret files, dangerous `rm -rf` commands with quantifiers, etc.), this can silently neuter the protection - the rule appears present and enabled but never blocks the operation it was meant to block, or blocks unrelated/all operations, undermining trust in hookify's deny/allow decisions. This matches "trust-boundary/guard bypass due to parser bug" style impact: a security control that looks correctly configured is rendered ineffective by a parsing defect reachable through ordinary rule-file content (including PR-supplied rule files).

### Likelihood Explanation
Preconditions are low-friction: the attacker only needs to get a `.claude/hookify.*.local.md` file with an inline `conditions` list entry whose `pattern` contains a comma (very plausible for regex quantifiers like `{1,3}`, alternations with counts, or comma-containing character classes) merged into the repo - either as a legitimate-looking security rule in a PR, or simply as a miscrafted rule by a well-meaning contributor. No special privilege is required beyond normal PR contribution rights, and the bug is deterministic (not timing- or race-dependent), making it fully repeatable once the trigger pattern is loaded via `load_rules`/`load_rule_file`.

### Recommendation
Replace the naive comma-split inline-dict parser with a proper key-aware split, e.g. split only on `, <key>:` boundaries using a regex that requires known keys (`field`, `operator`, `pattern`) as anchors, or simply disallow/deprecate the single-line inline-dict shorthand in favor of the multi-line `- field: ...\n  operator: ...\n  pattern: ...` format (which already parses correctly line-by-line). At minimum, add a round-trip validation in `Condition.from_dict`/`load_rule_file` that warns (or rejects the rule) when a reconstructed `pattern` fails to compile as valid regex or looks truncated, and add unit/fuzz tests asserting that `pattern` values containing `,`/`:` survive `extract_frontmatter` unchanged.

### Proof of Concept
Add a unit test in the hookify test suite (e.g. `plugins/hookify/tests/`) exercising `extract_frontmatter` directly:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-env-secrets
enabled: true
event: file
conditions:
  - field: file_path, operator: regex_match, pattern: \\.(env|pem){1,2}:secret$
---
Blocked: secret file edit detected!
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Expected: the pattern should be preserved intact
assert rule.conditions[0].pattern == r"\.(env|pem){1,2}:secret$"
# Actual (bug): pattern is truncated, e.g. "\.(env|pem){1"
```
Additionally, a fuzz test can generate random `pattern` strings containing `,` and `:` (e.g. regex quantifiers `{m,n}`, alternations, anchors), embed them into the single-line inline-dict `conditions` syntax, run them through `extract_frontmatter` + `Rule.from_dict`, and assert `reconstructed_pattern == original_pattern` for every generated case - demonstrating the parser corrupts the pattern whenever it contains a comma.
