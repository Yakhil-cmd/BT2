### Title
Extension update notifier prints attacker-controlled release Version/URL to the terminal without sanitizing ANSI/OSC control sequences - ([File: pkg/cmd/root/extension.go])

### Summary
`update.CheckForExtensionUpdate` populates `ReleaseInfo.Version` and `ReleaseInfo.URL` directly from `ext.LatestVersion()` and `ext.URL()`, which for git-based extensions are ultimately derived from the attacker-controlled remote repository's ref/tag metadata. `pkg/cmd/root/extension.go`'s `PostRun` writes these values straight into `stderr` via `fmt.Fprintf`/`cs.Cyan`/`cs.Yellow`, none of which strip terminal control bytes, so a malicious extension publisher can inject ANSI/OSC 8 escape sequences into the victim's terminal output.

### Finding Description
In `internal/update/update.go`, `CheckForExtensionUpdate` (lines 51-78) builds `releaseInfo := &ReleaseInfo{Version: ext.LatestVersion(), URL: ext.URL()}` [1](#0-0)  straight from the `extensions.Extension` interface values, with no sanitization applied. That `*ReleaseInfo` is passed through `checkForExtensionUpdate` in `pkg/cmd/root/extension.go` (lines 94-99) [2](#0-1)  and ultimately rendered in `PostRun`:

```go
fmt.Fprintf(stderr, "\n\n%s %s → %s\n",
    cs.Yellowf("A new release of %s is available:", ext.Name()),
    cs.Cyan(strings.TrimPrefix(ext.CurrentVersion(), "v")),
    cs.Cyan(strings.TrimPrefix(releaseInfo.Version, "v")))
...
fmt.Fprintf(stderr, "%s\n\n", cs.Yellow(releaseInfo.URL))
``` [3](#0-2) 

`cs.Cyan`/`cs.Yellow`/`cs.Yellowf` (in `pkg/iostreams/color.go`) only wrap text with `ansi.ColorFunc`-generated escape codes for coloring; they perform no stripping or escaping of embedded control characters in the input string [4](#0-3) . The `extensions.Extension` interface (`pkg/extensions/extension.go`, lines 18-29) exposes `URL()` and `LatestVersion()` as plain strings with no documented or enforced sanitization contract [5](#0-4) . For a git-extension, these values are populated from the GitHub API's release `tag_name`/`html_url` fields (as reflected by the `ReleaseInfo` JSON tags `tag_name`/`html_url` in `update.go` lines 27-31) [6](#0-5) , both of which an attacker fully controls by publishing their own release on their own extension repository (tag name and the resulting `html_url`, which GitHub constructs from the tag name). No host allowlist, safeurl validation, or output-sanitization step is applied to these two fields before they reach the terminal write.

### Impact Explanation
This enables terminal escape-sequence / OSC 8 hyperlink injection and potential terminal state manipulation (e.g., prompt spoofing, hidden/malicious hyperlink text, clearing scrollback, or overwriting displayed text) whenever the victim runs any `gh <extension>` command that triggers the extension update notifier. This maps to a low/output-injection class impact (terminal/UI spoofing) rather than remote code execution, since no shell interpretation of the string occurs — the vulnerability is limited to what a terminal emulator will render/execute in response to raw escape sequences (which can range from cosmetic corruption up to, in vulnerable terminal emulators, more serious consequences like clipboard manipulation via OSC 52 or hyperlink spoofing via OSC 8).

### Likelihood Explanation
Highly feasible and repeatable: the only precondition is that the victim installs the attacker's `gh` extension (a normal, expected use case for third-party extensions) and subsequently runs any command for that extension while an "update available" state exists (`ext.UpdateAvailable()` true and the 24-hour state-file check window elapsed). The attacker fully controls the content of their own repository's release tag name and the corresponding `html_url`, requiring no compromise of GitHub infrastructure.

### Recommendation
Sanitize `ReleaseInfo.Version` and `ReleaseInfo.URL` before writing them to the terminal — e.g., strip or escape all non-printable/control characters (particularly ESC `\x1b` and other C0/C1 control codes) in `pkg/cmd/root/extension.go` prior to the `fmt.Fprintf` calls, or add a shared sanitization helper invoked wherever untrusted release/extension metadata is rendered to `stdout`/`stderr`. Consider validating that `Version` matches an expected version-string pattern and that `URL` is a well-formed `https://` URL before printing it.

### Proof of Concept
```go
// pkg/cmd/root/extension_test.go (illustrative)
func TestExtensionUpdateNotice_SanitizesControlBytes(t *testing.T) {
    ios, _, _, stderr := iostreams.Test()
    ext := &extensions.ExtensionMock{
        NameFunc:           func() string { return "gh-evil" },
        CurrentVersionFunc: func() string { return "v1.0.0" },
        OwnerFunc:          func() string { return "attacker" },
        IsPinnedFunc:       func() bool { return false },
        IsLocalFunc:        func() bool { return false },
    }
    releaseInfo := &update.ReleaseInfo{
        Version: "v1.0.1\x1b[8m", // conceal-mode escape sequence
        URL:     "https://example.com/\x1b]8;;javascript:alert(1)\x07click\x1b]8;;\x07",
    }
    checkFn := func(em extensions.ExtensionManager, e extensions.Extension) (*update.ReleaseInfo, error) {
        return releaseInfo, nil
    }
    cmd := NewCmdExtension(ios, &extensions.ExtensionManagerMock{}, ext, checkFn)
    cmd.PreRun(cmd, nil)
    cmd.RunE(cmd, nil)
    cmd.PostRun(cmd, nil)

    out := stderr.String()
    if strings.Contains(out, "\x1b") {
        t.Fatalf("expected control bytes to be stripped, got raw output: %q", out)
    }
}
```
Expected (current, vulnerable) behavior: the test fails because raw `\x1b` bytes appear unmodified in `stderr`, confirming the injection reaches the terminal write path unsanitized.
