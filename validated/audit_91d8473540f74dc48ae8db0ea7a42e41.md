### Title
`OpenedHandler#provision?` / `ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled` when `provisioning_behavior` is `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` write `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...allow_with_label...) || (...prevent_with_label...)` without grouping parentheses, so Ruby's `&&`-before-`||` precedence only ANDs `review_stacks_enabled` with the `allow_all` branch. If `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, a stack can be created/unarchived purely from PR label state regardless of `review_stacks_enabled`. `LabeledHandler`/`UnlabeledHandler` gate correctly (`review_stacks_enabled && (archive? || unarchive?)`), so only the `opened`/`reopened` paths are affected.

### Finding Description
Binding claimed: `repository.review_stacks_enabled == true` must be a necessary condition for provisioning/unarchiving in every handler.

Code in [1](#0-0) :
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` has higher precedence than `||`, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed into the first disjunct. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `provision?` returns `true` purely from label presence/absence, independent of `review_stacks_enabled`. The identical pattern is duplicated in `ReopenedHandler#unarchive?` [2](#0-1) .

By contrast, `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` correctly gate the whole disjunction: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)` [3](#0-2)  and [4](#0-3) . Those two handlers' own `archive?`/`unarchive?` helpers do not reference `review_stacks_enabled` at all [5](#0-4) , so `review_stacks_enabled` correctly gates the entire outcome for `labeled`/`unlabeled` events. So only `OpenedHandler` and `ReopenedHandler` are exploitable.

Root cause is missing parentheses around the `review_stacks_enabled && ...` term intended to scope over the full `||` chain.

Regarding re-triggering after remediation: this bug is only reachable while `repository.provisioning_behavior` is `allow_with_label` or `prevent_with_label` on the target repository (an operator-configured value, not attacker-controlled). If an operator remediates by switching `provisioning_behavior` to `allow_all` while still leaving `review_stacks_enabled: false`, then in `provision?`/`unarchive?` the `allow_with_label?`/`prevent_with_label?` predicates become `false`, and the only remaining disjunct (`review_stacks_enabled && allow_all?`) is correctly `false && true = false`. So switching to `allow_all` without enabling `review_stacks_enabled` does close the gap for `OpenedHandler`/`ReopenedHandler` — the "different clause" bypass hypothesized in the question does not exist once `provisioning_behavior` is `allow_all`. The persistent-exploit condition requires the operator to leave (or revert to) `allow_with_label`/`prevent_with_label` while `review_stacks_enabled` stays `false`; in that state, `OpenedHandler`/`ReopenedHandler` remain exploitable via label toggling and PR reopen/open, while `LabeledHandler`/`UnlabeledHandler` remain correctly closed.

### Impact Explanation
While `provisioning_behavior` is `allow_with_label` or `prevent_with_label` and `review_stacks_enabled` is `false` (operator believes review stacks are disabled), any external contributor who can open a pull request against the affected repository and add/remove a label matching `provisioning_label_name` can cause `ReviewStackAdapter#find_or_create!`/`unarchive!` to run, creating a `ReviewStack` record, enqueueing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [6](#0-5) , which drives downstream provisioning/deploy automation for that repository/environment (`pr#{number}`) — an unauthorized deploy despite the operator's intended kill-switch. This affects only the repository whose `provisioning_behavior` is misconfigured; it does not cross-tenant to other repositories. Matches "Critical: unauthorized deploy" category, scoped to repositories in this specific configuration state.

### Likelihood Explanation
Requires the target repository to already have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator-chosen setting, common for review-stack workflows) with `review_stacks_enabled` currently `false`. Given that precondition, exploitation cost is trivial: open a PR and add/remove a label the attacker fully controls on their own PR, or close/reopen the PR — both are unprivileged actions available to any contributor who can open PRs on the repo. Fully repeatable per PR and across PRs as long as the misconfiguration (behavior set but flag disabled) persists.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` scopes the entire disjunction in both handlers, matching the `LabeledHandler`/`UnlabeledHandler` pattern:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_precedence_test.rb
test "provision? bypasses review_stacks_enabled=false when provisioning_behavior is allow_with_label" do
  repository = shipit_repositories(:shipit).tap do |r|
    r.update!(review_stacks_enabled: false, provisioning_behavior: :allow_with_label, provisioning_label_name: "deploy-preview")
  end

  params = build_pull_request_opened_params(
    repository_full_name: repository.full_name,
    labels: [{ name: "deploy-preview" }]
  )

  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)

  # Binding under test: review_stacks_enabled(false) must equal the actual gating outcome.
  assert_equal false, repository.review_stacks_enabled
  assert_difference -> { Shipit::ReviewStack.count }, 1 do
    handler.process
  end
  # Demonstrates provision? returned true despite review_stacks_enabled == false,
  # confirming the operator precedence bug.
end
```
