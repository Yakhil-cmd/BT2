### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while every handler acts on the independent, unauthenticated `repository.full_name` field — cross-organization commit-status/sync forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the JSON body itself, then verifies the signature over the raw payload with that secret. But once verification "passes," every registered webhook handler resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same attacker-controlled body: `repository.full_name`. Nothing binds these two fields to the same organization/repository. In a multi-organization Shipit deployment, a tenant that legitimately owns one organization's webhook secret can forge a payload whose `owner.login` matches their own org (so it passes signature verification with their own secret) while `full_name` points at a completely different, unrelated organization's repository. This breaks the trust binding: *the organization that authenticated ≠ the repository that is written*.

### Finding Description
Signature verification:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github.<org>.webhook_secret` — Shipit explicitly supports one shared instance serving multiple, independently-administered GitHub organizations, each with its own webhook secret set by that org's own admin: [2](#0-1) 

`verify_webhook_signature` merely checks `HMAC(secret_for(repository_owner), raw_post) == signature`: [3](#0-2) 

Crucially, the HMAC only proves the request body was signed by whoever holds `secret_for(repository_owner)` — it says nothing about which repository the payload's data actually targets. Once `head(422)` is *not* returned, `WebhooksController#create` dispatches the **entire raw payload** to all registered handlers regardless of which field was used for verification:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves the target repository from `repository.full_name`, not `repository.owner.login`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
`Repository.from_github_repo_name` splits this field directly and does a DB lookup with no relation to the org whose secret produced the signature: [6](#0-5) 

Two concrete handlers illustrate impact:

- `PushHandler` finds the stacks for `repository.full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` against that stack: [7](#0-6) 
- `StatusHandler` looks up commits purely by `sha` (global, cross-stack) and calls `commit.create_status_from_github!(params)` with attacker-supplied `state`/`context`/`description`: [8](#0-7) 

`create_status_from_github!` → `add_status` triggers `deployable_status` hooks and, when the stack has continuous delivery enabled, schedules a deploy once a commit transitions to a `success` state: [9](#0-8) 
`Commit#deployable?` treats a commit as deployable once it has a `success` status and isn't blocked: [10](#0-9) 

Because `Status#state`/`context`/`description` are taken verbatim from the forged payload with no cross-check against `repository_owner`, an attacker who legitimately administers Org A (and therefore legitimately knows Org A's own `webhook_secret`, since Shipit's own docs instruct admins to "keep it in clear on the side") can:
1. Set `repository.owner.login` (or `organization.login`) = `"org-a"` so `verify_signature` validates the HMAC using Org A's own secret (which the attacker holds).
2. Set `repository.full_name` = `"org-b/victim-repo"` and `sha` = a real commit SHA in Org B's stack.
3. Sign the raw body with Org A's secret and send the `status` (or `push`) webhook.

The controller verifies successfully (Org A's secret matches), then `StatusHandler` creates a forged `success` status on Org B's commit, and/or `PushHandler` triggers a sync of Org B's stack — despite the attacker having no credentials, GitHub App installation, or authorization on Org B whatsoever.

### Impact Explanation
This crosses exactly the boundary called out as in-scope: the organization whose credential authenticated the webhook is not enforced to be the same as the repository/stack the handler subsequently writes to. Concretely, this allows an unprivileged tenant of a shared, multi-org Shipit instance to:
- Forge CI/status data (`commit.create_status_from_github!`) for another organization's commits, directly bypassing required-status gating in `Commit#deployable?`, and
- Trigger `ContinuousDeliveryJob`/deploys on another organization's stack once continuous deployment is enabled (see `add_status` → `stack.schedule_merges` and `Status#schedule_continuous_delivery`).

This matches the "unauthorized deploy" impact category, since a status forgery can make an otherwise-blocked commit satisfy `deployable?` and be auto-deployed by continuous delivery on a stack the attacker has zero legitimate access to.

### Likelihood Explanation
Requires operating a real GitHub organization onboarded onto a multi-tenant Shipit installation (the multi-org config schema is a first-class, documented feature — see `config/secrets.development.example.yml` and `lib/shipit.rb#github_app_config`), and knowledge of that org's own webhook secret, which the org's own admin sets and therefore knows. No access to the victim org's secrets, GitHub App, or Shipit session is required — only the ability to send an arbitrary HTTP POST to `/webhooks` with a body/signature the attacker fully controls, which is unauthenticated by design (webhooks endpoint has no session).

### Recommendation
Bind the field used for signature-secret selection to the same field used for repository resolution. Concretely:
- Compute `repository_owner` and the repository/stack target from the **same** payload path (`repository.full_name`'s owner segment), and reject the webhook if `repository.owner.login` does not match the owner segment of `repository.full_name`.
- After verifying the signature, re-derive the organization from `repository.full_name` and confirm it matches the org whose secret validated the signature before dispatching to handlers.

### Proof of Concept
1. Attacker is the legitimate admin of GitHub org `org-a`, onboarded on a shared Shipit instance, and knows `secrets.github.org-a.webhook_secret` (call it `SECRET_A`).
2. Victim org `org-b` has a Stack tracking `org-b/victim-repo` with continuous deployment enabled and a required status context `ci/required`.
3. Attacker crafts:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `SECRET_A` [11](#0-10) .
6. `WebhooksController#create` dispatches to `StatusHandler`, which finds the commit by `sha` (global lookup, no org scoping) and creates a forged `success` status for context `ci/required` on `org-b`'s commit [12](#0-11) .
7. If that commit now satisfies `deployable?` and `org-b`'s stack has continuous deployment enabled, a deploy is scheduled without any action by `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
