### Title
Commit-status webhook writes are not scoped to the authenticating repository, enabling cross-repository CI-status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App belonging to the *organization named in the payload* (`repository.owner.login` / `organization.login`), but `StatusHandler#process` then applies the carried `sha`/`state` to **any** `Commit` row in the entire database that matches that SHA, with no check that the commit belongs to a stack of the repository/organization that was actually authenticated. This breaks the binding: `organization that authenticated == repository whose Commit is written`.

### Finding Description
`WebhooksController` selects the GitHub App/secret used to verify the signature purely from data embedded in the still-to-be-trusted payload: [1](#0-0) [2](#0-1) 

This only proves that *some* organization configured in Shipit (whichever org owns the `repository.owner.login`/`organization.login` value) sent a validly-signed payload — it does not prove which specific `Stack`/`Commit` the effects of that payload should be limited to.

`Handlers::StatusHandler`, however, applies the event to every commit sharing that SHA across the whole installation, independent of repository: [3](#0-2) 

Contrast this with `CheckSuiteHandler`, which correctly scopes matching to the stacks whose `branch` matches, before looking at commits: [4](#0-3) 

Because git commit SHAs are content-addressed (a function of tree, parents, author/committer identities and timestamps, and message) and not secret, an attacker who has legitimate write/webhook-triggering rights on *any* GitHub organization configured in Shipit (their own org, in a multi-org Shipit deployment as documented in `docs/setup.md`) can:
1. Observe a target commit's SHA in a different, unrelated stack (commit SHAs/branches are visible via the Shipit UI/API or the public GitHub repo itself).
2. Reproduce an object with the identical SHA in a repository under their own, authenticated organization (e.g. via `git commit-tree` replaying the same tree/parents/author/committer/timestamps — this only requires the original commit's metadata being public, not write access to the original repo).
3. Set a commit status on that commit in their own repo, causing GitHub to send Shipit a webhook that is *genuinely* signed with their own organization's `webhook_secret`.
4. `verify_signature` passes (signature is valid for the authenticated org), but `StatusHandler` writes the forged status onto the `Commit` record of the **unrelated target stack**, because the query is not scoped to the repository that was authenticated.

### Impact Explanation
Commit statuses are load-bearing for automated, unattended actions in Shipit:
- `MergeRequest#reject_unless_mergeable!` / `#any_status_checks_missing?` / `#any_status_checks_failed?` gate automatic merges on these very status rows: [5](#0-4) 
- `ci.require` in `shipit.yml` similarly blocks deploys pending required statuses.

An attacker who controls a different, authenticated organization/repository in the same Shipit installation can inject fabricated "success" statuses into a target stack they do not own, unblocking `ProcessMergeRequestsJob#perform` to auto-merge a pull request, or clearing a deploy gate — i.e., an unauthorized merge/deploy of code in a repository the attacker has no legitimate authorization over. This is a cross-repository write and satisfies the Critical bar ("cross-repository writes" / "unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is constrained mainly by the requirement that the attacker control at least one organization/GitHub App installation configured in the same Shipit instance (a realistic scenario for the documented multi-organization configuration in `docs/setup.md`), and by the practical difficulty of reproducing an identical commit SHA (feasible when the target commit's exact git object metadata — tree, parents, author/committer identity and timestamps, message — is public, which is common for public open-source target repos). No possession of the target organization's `webhook_secret`, no `ApiClient` token, and no GitHub App private key for the target org is required — only a legitimately signed webhook from any configured organization.

### Recommendation
Scope `StatusHandler` (and any other handler that writes based on payload-supplied identifiers such as `sha`) to the repository/organization that was actually authenticated by `verify_signature`, e.g. by joining through `Commit -> Stack -> Repository` and filtering on the repository owner/name asserted (and cryptographically verified) in the same payload, rather than matching bare `sha` globally. At minimum, restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` matches `params.dig('repository', 'full_name')`.

### Proof of Concept
Conceptual PoC (cannot be executed here, but demonstrates the code path):
1. Configure Shipit with two GitHub orgs, `victim-org` and `attacker-org`, each with their own `webhook_secret` (multi-org setup per `docs/setup.md`).
2. Stack `A` tracks `victim-org/app` and has a `Commit` with `sha = X` awaiting a required CI status (`ci.require`).
3. Attacker, who administers `attacker-org/anything`, replays commit `X`'s exact git object (same tree/parents/author/committer/message/timestamps) into `attacker-org/anything`, producing the identical SHA `X`.
4. Attacker sets a "success" commit status on that commit in `attacker-org/anything`. GitHub sends a `status` webhook to Shipit, signed with `attacker-org`'s `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org` from the payload and verifies successfully against `attacker-org`'s secret.
6. `StatusHandler#process` executes `Commit.where(sha: 'X')`, which matches stack `A`'s commit (belonging to `victim-org`), and records the forged "success" status on it — satisfying `victim-org/app`'s CI requirement despite the attacker having no access to `victim-org`.

      return reject!('merge_conflict') if merge_conflict?

      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?

    end

    end
