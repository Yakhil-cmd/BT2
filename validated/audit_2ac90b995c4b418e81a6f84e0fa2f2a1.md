### Title
Liquidity-drain griefing: a borrower can sandwich a supplier's `withdraw` between `borrow` and `repay` to make it revert — (File: contracts/pool/src/ops/withdraw.rs)

### Summary
Analogous to the Particle NFT-withdrawal grief, a supplier's `withdraw` reverts whenever pool `cash` drops below the requested amount. An unprivileged attacker who already holds a collateralized position can drain the pool's `cash` down to the liquidation buffer with `borrow`, causing the victim's pending `withdraw` to fail with `InsufficientLiquidity`, then `repay` the debt to restore liquidity. Because interest accrues in millisecond chunks, a borrow/repay executed in adjacent ledger transactions (or within the same accrual chunk) costs the attacker essentially only the transaction fees, while the victim's exit is blocked for as long as the attacker chooses to keep the funds borrowed.

### Finding Description
`withdraw::accounting` ends in `gate_and_debit`, which calls `cache.require_reserves(net_transfer)` — a strict `cash >= amount` check that panics with `CollateralError::InsufficientLiquidity` (withdraw.rs:112, cash.rs:15-21). `borrow::accounting` debits `cash` and transfers real tokens out via `borrow::apply` (borrow.rs:34, 47), limited only by `require_liquidation_buffer`, which forces `cash - draw >= LIQUIDATION_BUFFER_BPS * supplied` (guards.rs:39-47), and `require_utilization_below_max` (borrow.rs:78). Neither guard prevents driving `cash` arbitrarily close to the buffer floor.

So for any victim withdraw of amount `W`, an attacker with sufficient collateral on any market can call `borrow` for `cash - buffer - W + 1` (bounded by `max_utilization`), making the victim's next `withdraw` revert. The attacker then calls `repay` for the full debt; since accrual is chunked per millisecond and the borrow/repay can straddle a zero-delta interval, repay returns the principal in full with negligible interest. The attacker can repeat this indefinitely for the cost of ledger fees, or simply hold the borrow to keep the supplier's funds locked.

Unlike the flash-loan window — where all monetary entries are correctly blocked by `FLASH_LOAN_ONGOING` — the borrow/repay grief is cross-transaction, so the reentrancy guard does not help.

### Impact Explanation
Temporary freezing of supplier funds: the victim cannot withdraw while the attacker keeps the pool's cash below the requested amount, and any single retry can be front-run again. Funds are not stolen and become withdrawable once the attacker repays, matching a DoS / medium-severity profile.

### Likelihood Explanation
Low cost, high feasibility: requires only a healthy collateralized borrow position (any collateral asset suffices — `cash` is tracked per hub/market but the attacker can borrow the same asset the victim wants). The attacker recovers the principal on repay and pays at most one millisecond accrual chunk of interest. Constrained by `max_utilization` and the liquidation buffer, so it only works when the borrow can push `cash` below `W` — i.e., it can always block large withdrawals, and partial withdrawals below the post-drain cash still succeed.

### Recommendation
- Reserve a per-withdraw liquidity floor or allow partial withdrawals to proceed when the full amount exceeds `cash` (users can already request less, but there is no way to pin liquidity for a pending exit).
- Alternatively, charge a minimum interest/flash-style fee on borrows repaid within one accrual chunk so repeated griefing is not free.

### Proof of Concept
1. Alice supplies 100k USDC to `(hub, USDC)`. Pool `cash` = 100k; liquidation buffer = `LIQUIDATION_BUFFER_BPS` of supplied (guards.rs:39-46).
2. Attacker supplies large ETH collateral, then calls `controller.borrow` for ~99k USDC — allowed since `cash - draw >= reserved` and utilization stays under `max_utilization` (borrow.rs:63-78). `cash` drops to ~1k.
3. Alice calls `controller.withdraw` for 50k USDC → `require_reserves` panics with `InsufficientLiquidity` (cash.rs:15-21, withdraw.rs:112).
4. Attacker calls `controller.repay` for the full USDC debt; with zero elapsed accrual chunks the debt equals principal, so the attacker loses only ledger fees. `cash` is restored — and the attacker can repeat step 2 before each of Alice's retries.
