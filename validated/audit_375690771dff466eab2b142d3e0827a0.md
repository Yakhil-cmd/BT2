## Analog Found: Unauthenticated `InitializeNonceAccount` allows anyone to claim authority over an already-created (but uninitialized) nonce account

### Title
Front-running / unauthenticated initialization of nonce accounts via `SystemInstruction::InitializeNonceAccount` - (File: `programs/system/src/system_instruction.rs`, `programs/system/src/system_processor.rs`)

### Summary
The System Program's nonce-account initializer, `initialize_nonce_account`, performs **no signer check at all** on the nonce account (or on any related key) before transitioning it from `State::Uninitialized` to `State::Initialized`. Anyone who submits a transaction naming an already-created, rent-funded, uninitialized nonce account can become its `nonce_authority`, exactly analogous to the reported "front run initializer" bug class where `initialize()` is callable by any unprivileged caller.

### Finding Description
`initialize_nonce_account` only checks that the account is writable and that its current state is `Uninitialized`; it never verifies that the caller (or any signer in the transaction) is related to the account's creator/funder: [1](#0-0) 

The processor entry point for `SystemInstruction::InitializeNonceAccount` similarly does not add any additional signer requirement — it only checks the number of accounts and fetches sysvars before calling straight into the unguarded initializer: [2](#0-1) 

This stands in contrast to sibling nonce operations such as `AdvanceNonceAccount`, `WithdrawNonceAccount`, and `AuthorizeNonceAccount`, which all verify the current `nonce_authority` against the transaction's `signers` set before mutating state. `InitializeNonceAccount` is the one operation that sets the authority for the first time, yet has no signer gate at all — the exact "anyone can call the initializer" pattern from the report.

In the normal CLI flow, account creation and initialization are bundled atomically into a single transaction by `system_instruction::create_nonce_account`, so the two steps execute together and cannot be split apart by an outside party: [3](#0-2) 

However, nothing in the System Program enforces that atomicity. Any account that is: (a) owned by the System Program, (b) sized to `nonce::state::State::size()`, (c) rent-exempt, and (d) still `State::Uninitialized`, is a valid target for `InitializeNonceAccount` regardless of who created/funded it or who submits the initializing transaction. If a wallet, exchange, or protocol ever creates such an account in one transaction and initializes it in a later, separate transaction (a legitimate and common pattern, e.g. custom nonce-account bootstrapping, batch pre-funding, or account recovery flows), the pending initialize transaction is visible in the mempool and can be front-run by an unrelated party who simply submits their own `InitializeNonceAccount` instruction (with themselves as `nonce_authority`) referencing the same account address, requiring no signature tied to the account itself.

### Impact Explanation
Once the attacker's transaction lands first, the account moves to `State::Initialized` with the attacker's chosen key as `nonce_authority`. The legitimate initializer's subsequent transaction then fails with `InstructionError::InvalidAccountData` (state already initialized). The attacker, now holding sole authority, can:
- Call `WithdrawNonceAccount` and drain the account's lamports (including the rent-exempt balance deposited by the legitimate funder) to an address of their choosing, since withdrawal authorization is checked only against the (now attacker-controlled) `nonce_authority`.
- Call `AuthorizeNonceAccount`/`AdvanceNonceAccount` to fully control the durable-nonce mechanism for that account, enabling denial-of-service or further manipulation against anyone relying on that nonce.

This is a concrete unsigned fund-movement / unauthorized-control vector reachable from a single unprivileged submitted transaction.

### Likelihood Explanation
Exploitation requires only that account creation and initialization occur in separate transactions (rather than the atomic bundle produced by the standard CLI helper) and that the pending initialize transaction is observable before confirmation (i.e., typical mempool/front-running conditions). This is plausible for any custom tooling, program, or workflow that does not strictly follow the bundled `create_nonce_account` helper.

### Recommendation
Require that `InitializeNonceAccount` be authorized by a signer tied to the account's creation — for example, require the nonce account itself to be a signer on the initializing instruction (mirroring how `CreateAccount` already requires the new account to sign), so that only the party that controls the account's keypair (or that atomically created it) can set the initial `nonce_authority`.

### Proof of Concept
1. Victim creates and funds a rent-exempt System-owned account `N` sized to `nonce::state::State::size()` in transaction T1 (e.g., via `SystemInstruction::CreateAccount`), intending to initialize it with their own authority in a later transaction T2.
2. Attacker observes T2 (containing `SystemInstruction::InitializeNonceAccount(victim_authority)` targeting `N`) in the mempool before confirmation.
3. Attacker submits their own transaction T_attack containing `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting the same account `N`, paying a higher priority fee, requiring no signature from `N` or the victim.
4. T_attack lands first; `N` transitions to `State::Initialized` with `attacker_authority` as the nonce authority, per [4](#0-3) .
5. Victim's T2 now fails with `InstructionError::InvalidAccountData`.
6. Attacker calls `SystemInstruction::WithdrawNonceAccount` signed by `attacker_authority` to drain `N`'s lamports.

    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
