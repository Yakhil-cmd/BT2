### Title
Uncapped-cost `data_feed`/`in_data_feed` oracle-list scans allow resource-consumption DoS via AA trigger formulas - (File: `data_feeds.js`, `formula/validation.js`)

### Summary
An unprivileged AA-trigger sender can craft a `data_feed[[...]]` or `in_data_feed[[...]]` oscript expression with an arbitrarily long, colon-separated `oracles` address list. The formula's static "complexity" cost charged for this operation is a fixed constant (`1`), independent of the number of oracle addresses supplied, because the per-address cost accounting is explicitly disabled. At execution time, however, the cost of resolving the expression scales linearly (or worse) with the number of oracle addresses and with the size of the mempool of unstable units, mirroring the unbounded-scan pattern in the reported `recall_relevant_memories_to_working_memory` bug class (CWE-400, uncontrolled resource consumption from a search/recall routine with no cost cap tied to attacker-controlled input size).

### Finding Description
`formula/validation.js` computes the complexity of `data_feed`/`in_data_feed` expressions via `validateDataFeed`/`validateDataFeedExists`. Both explicitly comment out per-address cost accrual: [1](#0-0) [2](#0-1) 

The evaluator (`formula/validation.js` `evaluate`, case `'data_feed'`/`'in_data_feed'`) simply adds `result.complexity` (constant `1`) to the running total regardless of how many oracle addresses were parsed from the `oracles` string: [3](#0-2) 

At runtime, `formula/evaluation.js` splits `oracles` on `:` into `arrAddresses` with no length cap and passes the full array into `dataFeeds.readDataFeedValue` / `dataFeeds.dataFeedExists`: [4](#0-3) [5](#0-4) 

Inside `data_feeds.js`, `readDataFeedValue`/`dataFeedExists` iterate the whole `storage.assocUnstableMessages` map (i.e., every currently-unstable/unconfirmed unit network-wide) once per call, computing `_.intersection(arrAddresses, objUnit.author_addresses)` for each unstable unit — a cost proportional to `arrAddresses.length * number_of_unstable_units`: [6](#0-5) [7](#0-6) 

For the non-unstable branch, `readDataFeedValue`/`dataFeedExists` additionally run `async.eachSeries(arrAddresses, ...)`, opening one LevelDB range/stream scan per oracle address: [8](#0-7) [9](#0-8) 

Because the oscript grammar allows the `oracles` string to be built with `||` concatenation and there is no explicit maximum count of colon-separated addresses enforced anywhere in `validateDataFeed`/`validateDataFeedExists` (unlike other operators such as `search_param_list`, which caps `arrPairs.length` to 5, or `min`/`max`, capped to 30 arguments), an attacker can pack many addresses into the `oracles` field while the formula's charged complexity stays at `1`. This is analogous to the reported bug: a "recall" style function whose cost is driven by external input but whose accounting does not reflect that cost, letting an unprivileged caller trigger disproportionate resource consumption per unit of accepted "budget."

### Impact Explanation
Every AA trigger unit is subject to complexity/count_ops limits meant to bound execution cost so nodes can validate AA responses within predictable time. Because `data_feed`/`in_data_feed` cost accounting ignores oracle-list length, a single trigger (or a handful of triggers, each still within the nominal complexity budget) can force every full node — during both the light-weight "estimate" pass (`estimatePrimaryAATrigger` in `aa_composer.js`) and the real AA-trigger handling path (`handleTrigger`) — to perform O(n) work per data-feed lookup and O(n) separate LevelDB stream scans for the non-unstable path, multiplied by however many `data_feed`/`in_data_feed` operators are placed in the trigger formula. Repeated or chained (secondary-trigger) use amplifies this further. This degrades node responsiveness/validation throughput network-wide (a form of "network unable to confirm new units" impact under load), which is the kind of concrete availability harm the validation criteria call for, without requiring a malicious peer/hub — it is reachable purely from a normally-formed AA trigger unit that any unprivileged user can post.

### Likelihood Explanation
The `oracles` parameter accepts any string expression evaluated at runtime (`evaluate(params.oracles.value, ...)` in `formula/evaluation.js`), and validation only checks that each colon-separated segment is a valid address — it never bounds the number of segments. Crafting such a trigger requires no special privileges, keys, or node compromise — just posting a normal unit containing an AA-triggering payment plus the crafted formula, well within the reach of "an unprivileged unit poster / AA trigger sender" described in scope. The main friction is unit/message size limits, which still permit many tens to low hundreds of 32-byte addresses per `oracles` string, and multiple `data_feed`/`in_data_feed` calls could be composed in one formula to multiply the effect further (subject to overall complexity/op-count caps that do not account for this specific cost).

### Recommendation
- Restore/enable per-address complexity accounting for `data_feed`/`in_data_feed` (the commented-out `complexity += addresses.length` lines) in `formula/validation.js` (`validateDataFeed`, `validateDataFeedExists`), or explicitly cap the number of colon-separated oracle addresses (mirroring the existing 5/30-item caps used for `search_param_list` and `min`/`max`).
- Reject formulas whose `oracles` list is only known at runtime (dynamic) or bound their maximum length defensively in `formula/evaluation.js` before invoking `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`.
- In `data_feeds.js`, short-circuit/limit iteration over `storage.assocUnstableMessages` and the number of concurrent kvstore stream scans triggered per formula evaluation, independent of the complexity-budget fix, as defense in depth.

### Proof of Concept
1. Construct an AA whose triggers evaluate, e.g.:
   `in_data_feed[[oracles="ADDR1:ADDR2:...:ADDRn", feed_name='x', feed_value=1, min_mci=0]]`
   with `n` chosen as large as the unit/message payload size allows (colon-joined valid Obyte addresses, 32 bytes/44 base32 chars each).
2. Post ordinary payment+data units that trigger this AA from an unprivileged wallet — no special permissions needed, as shown by existing tests exercising `data_feed`/`in_data_feed` triggers, e.g. `test/formula.test.js:904-916` and `test/formulas_in_contracts.test.js:95-100` (which confirm complexity stays at `1` even with multiple oracle addresses via `"oracles=\"...\"||this_address"`).
3. Observe that `validateFormula` reports the same low fixed complexity (`1` per call) regardless of `n`, while `dataFeeds.dataFeedExists`/`readDataFeedValue` perform `O(n)` intersection checks against every unstable unit and/or `O(n)` separate LevelDB stream scans during actual AA-trigger handling in `handleTrigger`, at negligible relative "cost" charged to the attacker's trigger.
