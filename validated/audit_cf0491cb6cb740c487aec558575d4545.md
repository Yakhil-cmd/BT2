### Title
Webhook signature verified with the wrong organization's secret due to unauthenticated `repository_owner` lookup - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly out of the *unverified* JSON body, before the signature has been checked [1](#0-0) [2](#0-1) . Handlers then act on `params['repository']['full_name']`, a separate, still-unverified field of the same untrusted body [3](#0-2) . This is the same root-cause pattern as the reported EVM bug: a piece of untrusted data is used to select the "trust context" (which secret authenticates the payload / which address+data get executed), while a *different* untrusted field of the exact same payload is the one actually acted upon, with the two never bound together.

### Finding Description
In a multi-organization Shipit deployment (`Shipit.github_organizations`, `Shipit.github_app_config` in `lib/shipit.rb`), each org has its own `webhook_secret` [4](#0-3) . `verify_signature` picks the `GitHubApp` (and hence the secret to verify against) using:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`repository_owner` comes straight from the attacker-controlled request body, not from anything cryptographically authenticated yet. `verify_webhook_signature` then just checks that `HMAC(secret_for(repository_owner), raw_body) == signature` [6](#0-5) .

An attacker who legitimately owns (or administers a GitHub App on) **Org A** with `webhook_secret_A` knows that secret. They can send Shipit an event whose body claims `repository.owner.login = "OrgA"` (so verification is performed with `webhook_secret_A`, which they can correctly sign) while `repository.full_name` inside the same body is set to `"OrgB/some-repo"` — a repository belonging to a completely different organization tracked by the same Shipit instance. `verify_signature` only checks that `repository_owner` (`"OrgA"`) matches the signer; it never checks that `repository.full_name`'s owner is consistent with `repository_owner`. Downstream handlers such as `PushHandler`/`StatusHandler`/etc. resolve the target purely from `repository.full_name` [3](#0-2) [7](#0-6) , so the forged event is processed *as if it were an authentic event about `OrgB/some-repo`*.

This breaks exactly the trust binding called out in the rules: "an organization that authenticated versus the repository that is written." The organization whose secret validated the signature (`OrgA`) is not equal to the organization of the repository the handlers act on (`OrgB`).

### Impact Explanation
`PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for any not-archived stack on the target branch of the spoofed repo [8](#0-7) ; `check_suite`, `status`, and `pull_request` handlers similarly mutate commit CI status, unarchive/archive review stacks, and update pull-request metadata for stacks belonging to `OrgB`, entirely driven by attacker-supplied JSON, without OrgB ever having sent anything. Because CI status and "deployable" checks are the gate that continuous-deployment and one-click deploy rely on (`Commit#deployable?`, statuses used by `stack.build_deploy`), an attacker able to forge a `status`-event payload accepted under their own org's signature can flip a commit's status to green for an `OrgB` repo it does not own, and if continuous delivery is enabled this can lead to an **unauthorized deploy**. This satisfies the "unauthorized deploy" Critical-impact bar.

### Likelihood Explanation
Requires the target Shipit instance to host more than one GitHub organization (multi-tenant `secrets.github` config, as documented/supported by `Shipit.github_organizations`/`github_app_config`) and requires the attacker to control (or have created) a GitHub App/webhook_secret for at least one of the tenant orgs — i.e. they must be a legitimate webhook sender for *some* org on the instance, but not for the org whose repository they target. No repository write access, no Shipit session, and no `ApiClient` token are needed; only knowledge of one org's `webhook_secret`, which by design is only shared with that org's admins/GitHub App owner — an unprivileged attacker relative to the victim org.

### Recommendation
Bind the signature-verifying organization to the payload's actual repository owner before trusting any other field: derive `repository_owner` and the repository/organization acted upon from the same verified source, and reject the request if `params.dig('repository','full_name')`'s owner does not match the organization whose secret validated the HMAC. Concretely, re-derive the acting repository owner *after* signature verification succeeds, and assert it equals the `repository_owner` used to pick the verifying secret, mirroring how the Concrete team fixed the referenced bug by binding the executed target strictly to the verified/expected structure rather than trusting an unverified/mismatched field.

### Proof of Concept
1. Configure a Shipit instance with two orgs in `secrets.yml`: `OrgA` (`webhook_secret_A`, known to attacker) and `OrgB` (tracked repo `OrgB/victim-repo`, unknown secret).
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, raw_body)`.
4. POST to `/github/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` → succeeds (attacker knows `webhook_secret_A`) → `head(422)` is not triggered.
6. `Shipit::Webhooks.for_event('status')` handler runs `StatusHandler`, which resolves the commit/stack via `repository.full_name = "OrgB/victim-repo"` and marks the victim commit's `ci/required-check` status as `success`, even though the request was never signed by `OrgB`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
