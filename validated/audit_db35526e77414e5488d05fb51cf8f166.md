### Title
Webhook signature validated against `repository.owner.login`'s secret while all handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the `X-Hub-Signature` HMAC based on `params.dig('repository','owner','login')` (or `organization.login`), but every webhook handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the actual `Repository`/`Stack` to act on using `payload.dig('repository','full_name')`. These two payload fields are never cross-checked against each other, so the "organization that authenticated" and the "repository that is written" are not bound to the same value.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config (multi-tenant `github: { org1: {...}, org2: {...} }` schema) and instantiates a `GitHubApp` with that organization's own `webhook_secret`: [3](#0-2) 

Signature verification is then performed with that organization's secret over the raw body: [4](#0-3) 

Critically, `verify_webhook_signature` returns `true` unconditionally if that particular organization has no `webhook_secret` configured (`return true unless webhook_secret`) — a documented, supported configuration state (`webhook_secret: nil` in `config/secrets.development.example.yml`).

Meanwhile, every handler resolves the target repository from a *different* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

and `Repository.from_github_repo_name` simply splits that string on `/`: [8](#0-7) 

Because `repository.owner.login` and `repository.full_name`'s owner segment are independent JSON keys the controller/handler pipeline never reconciles, an attacker who can produce a payload with a *valid* signature for **some** configured organization (e.g., an org that is deliberately configured with `webhook_secret: nil`, or whose secret has otherwise leaked/been guessed) can set `repository.full_name` to point at an entirely different, victim organization's repository. The equality that should hold — "organization whose secret authenticated the request" == "organization whose repository is mutated" — is broken.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Exploiting it lets an unprivileged external attacker forge `push`, `pull_request`, `status`, `check_suite`, or `membership` events against a target stack/repository that belongs to a different, properly-secured GitHub organization, by piggy-backing on a weaker/misconfigured organization entry in the same Shipit instance's multi-tenant config. Depending on the handler triggered this can enqueue `GithubSyncJob` (syncing arbitrary attacker-controlled `expected_head_sha`), create/archive/unarchive review stacks, or manipulate team membership — an unauthorized effect on a repository/organization the attacker never proved control of via signature. This aligns with the High-impact bucket ("escalation into authorization"/"unauthenticated ... state" mutation) since it results in cross-tenant unauthorized writes without possessing the victim organization's actual `webhook_secret`.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment (`github: { orgA: {...}, orgB: {...} }`) where at least one organization has `webhook_secret` unset/blank (a supported, documented configuration — see `config/secrets.development.example.yml`), or where an attacker has obtained any one organization's secret; and (b) the ability to send an arbitrary HTTP POST to the public `/github/webhooks` endpoint (unauthenticated, no session or token required by design). No repository write access or privileged account is needed — only knowledge that some tenant org in the shared instance has a weak/missing secret. This is a realistic operational scenario for shared Shipit instances serving several GitHub orgs.

### Recommendation
In `WebhooksController`, after resolving `repository_owner` for signature verification, also derive the owner from `repository.full_name` (and from any other identifying fields used by handlers) and reject the request (422) if they don't match the authenticating organization. More robustly, verify the signature using the secret belonging to the organization that owns `repository.full_name`, not a caller-supplied `repository.owner.login`/`organization.login` field, and disallow relying on organizations configured with a blank `webhook_secret` when the instance has more than one org configured.

### Proof of Concept
Given a Shipit instance configured with two GitHub App orgs:
```yaml
github:
  weakorg:
    webhook_secret: null   # or leaked
  victimorg:
    webhook_secret: "s3cr3t-strong"
```
An attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "attackercontrolledsha",
  "repository": {
    "owner": { "login": "weakorg" },
    "full_name": "victimorg/protected-repo"
  }
}
```
`verify_signature` calls `Shipit.github(organization: "weakorg")`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header. `PushHandler#process` then resolves stacks via `Repository.from_github_repo_name("victimorg/protected-repo")` and enqueues `sync_github(expected_head_sha: "attackercontrolledsha")` against the victim organization's stack — despite the request never being authenticated by `victimorg`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
