### Title
Receipt size limit is validated at creation but the check is bypassed once `output_data_receivers`/return values are appended, letting oversized receipts propagate - (File: runtime/runtime/src/verifier.rs, runtime/runtime/src/congestion_control.rs)

### Summary
This is the closest reachable analog in nearcore to the Sherlock H-6 pattern ("slippage checked but never applied/enforced"). In `ShortLongSpell::_withdraw`, `param.sellSlippage` is validated against a maximum but the checked value is never actually applied to the swap execution path, so the protection is illusory. In nearcore, `validate_receipt()` computes and checks a receipt's serialized size against `limit_config.max_receipt_size` only in `ValidateReceiptMode::NewReceipt` mode [1](#0-0) , but this check is performed on the receipt object at one point in time. Fields such as `output_data_receivers` (added via `promise_return`/promise chaining) or large return values are appended to the receipt object after the size check has already passed, meaning the enforced limit is not actually applied to the final receipt that gets serialized, stored, and forwarded.

### Finding Description
`validate_receipt` is the single enforcement point for `max_receipt_size` on newly created receipts: [1](#0-0) 

The nearcore codebase itself documents that this check is not actually applied consistently to the object that ends up being sent/stored: the receipt can pass validation, then have `output_data_receivers` (or a large returned value producing an oversized data receipt) attached afterward, pushing it above `max_receipt_size` without the check being re-applied. This is called out explicitly in test comments referencing a known tracked bug (nearcore issue #12606): [2](#0-1) [3](#0-2) 

Downstream code in `try_forward` (congestion/bandwidth control) is written defensively around exactly this gap — it explicitly acknowledges that receipts above the size limit can exist in practice and "pretends" they are `max_receipt_size` to avoid them getting permanently stuck, rather than rejecting them: [4](#0-3) 

This is structurally identical to the reported bug class: a limit is computed/checked (`sellSlippage` checked against `maxSlippageOfClose`; receipt size checked against `max_receipt_size`), but the checked value/limit is not actually enforced on the object that is subsequently used/propagated (the swap execution ignores the slippage bound; the receipt's final serialized form ignores the size bound once more fields are appended).

### Impact Explanation
An oversized receipt that bypasses the intended `max_receipt_size` enforcement can:
- Exceed the size assumptions baked into `ChunkStateWitness` size budgeting (documented to target ~17MiB total, built from the assumption that no receipt exceeds `max_receipt_size`) [5](#0-4) , undermining witness-size guarantees relied on for chunk distribution.
- Interact with `outgoing_receipts_usual_size_limit` / `outgoing_receipts_big_size_limit` bandwidth accounting in ways the protocol did not intend, since `try_forward` has to special-case oversized receipts to prevent them getting permanently stuck in the outgoing buffer [6](#0-5) .
This is a resource-accounting/congestion-control integrity issue reachable purely from a submitted transaction that triggers a contract to build a promise chain with `promise_return` or a large returned value — no validator or node-operator privilege is required.

### Likelihood Explanation
High likelihood of reachability: any contract call that uses `promise_return` to attach `output_data_receivers` after the initial receipt has already been sized and validated, or that returns a value close to `max_receipt_size`, can trigger this gap deterministically. The nearcore team has already reproduced and tracked this exact scenario in dedicated regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) which assert the receipt exceeds the limit and yet is processed rather than rejected [7](#0-6) [8](#0-7) .

### Recommendation
Re-validate (or validate) receipt size against `limit_config.max_receipt_size` after all fields that can grow the receipt post-creation (`output_data_receivers`, promise-return data receipts) have been finalized, immediately before the receipt is committed/forwarded, rather than only at the point of initial construction. Alternatively, bound the size of `output_data_receivers` and returned values tightly enough at the point they are appended so the previously-validated size bound cannot be exceeded, closing the gap referenced by nearcore issue #12606.

### Proof of Concept
Existing first-party regression tests already demonstrate the bypass end-to-end: [7](#0-6) [8](#0-7) 
These call a contract method that builds a promise chain (`[A -then-> B]`, `A` doing `promise_return` to spawn `C`), where `C`'s receipt is sized at exactly `max_receipt_size` before `output_data_receivers` is appended, causing the final receipt to exceed the limit; the test asserts (`assert_oversized_receipt_occurred`) that such an oversized receipt does in fact appear on-chain, confirming the checked limit was not applied to the receipt actually persisted/forwarded.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
