### Title
Forged `pull_request` `opened` webhook via no-secret org mutates victim repository's review stack - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used to validate the HMAC purely from `repository.owner.login` (or `organization.login`) in the untrusted payload, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has no `webhook_secret`. The `pull_request` `OpenedHandler` then resolves the target repository independently from `params.repository.full_name`, so an attacker who controls an org with no configured secret can forge a signature-free request whose `repository.full_name` names a *different*, victim repository, causing the handler to create/mutate that victim's review stack.

### Finding Description
The broken binding the code implicitly assumes is:
`repository_owner` (used to pick the `GitHubApp`/secret for verification) `==` `params.repository.full_name`'s owning organization (the repository actually mutated by the handler).

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` [1](#0-0) , looks up `Shipit.github(organization: repository_owner)`, and calls `verify_webhook_signature` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret` [3](#0-2) . If the configured org (e.g. an attacker-registered/no-secret org) has a blank `webhook_secret`, any payload naming that org as `repository.owner.login` passes verification with no signature check at all.
3. `Webhooks.for_event('pull_request')` fans the parsed body out to all PR handlers, including `OpenedHandler` [4](#0-3) .
4. `OpenedHandler#repository` resolves the actual target repository from `params.repository.full_name` — a completely separate field from the one used for signature-org selection — via `Shipit::Repository.from_github_repo_name` [5](#0-4) .
5. If that repo has review stacks enabled and provisioning allows it, `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [6](#0-5) , creating/mutating a review stack under the named repository — regardless of which org's (secret-less) signature check passed.

Root cause: the org used to authenticate the webhook (`repository_owner`, from `repository.owner.login`) is never checked for equality against the org/repo the handler actually operates on (`repository.full_name`). Since these are two independently attacker-controlled JSON fields inside the same forged body, an attacker can set `repository.owner.login` to an org configured in Shipit with a blank `webhook_secret` (satisfying step 2 trivially) while setting `repository.full_name` to `victim-org/victim-repo` (satisfying step 4/5). No existing guard checks this: `verify_signature` never re-validates `repository.full_name` against `repository_owner`, and `OpenedHandler`'s `ExplicitParameters` schema only requires `repository.full_name` to be a `String` — it performs no ownership/authorization check [7](#0-6) .

### Impact Explanation
An attacker who has no Shipit credentials, and controls only a GitHub org that a Shipit operator has configured in `secrets.github` without a `webhook_secret`, can forge arbitrary `pull_request`/`opened` payloads naming any victim repository/org tracked by that same Shipit instance. This causes the victim repository's review-stack lifecycle (`find_or_create!`, subsequent close/reopen/label handlers) to be driven by attacker-supplied data — a cross-tenant/cross-repository state-manipulation matching the "Critical: payload for one repository mutating another's stack" category. The same flaw generically affects any `pull_request` sub-handler (`ClosedHandler`, `LabeledHandler`, etc.) since all resolve the target repo the same way from `repository.full_name`, independent of the org whose secret verified the request.

### Likelihood Explanation
This requires: (a) Shipit is configured with multiple GitHub orgs (multi-org `github_app_config` schema), (b) at least one configured org has no `webhook_secret` set, and (c) a victim repository/org with review stacks is also configured on the same Shipit instance. Given those preconditions — which are an operator configuration choice, not something the attacker controls — the exploit itself costs a single unauthenticated HTTP POST with a crafted JSON body and no valid signature, and is fully repeatable against any repository tracked by the instance.

### Recommendation
In `WebhooksController#verify_signature`, cross-validate that the owner/org used to select the webhook secret matches the owner of every repository referenced in the payload (e.g., require `params.dig('repository','owner','login')` to equal the org portion of `params.dig('repository','full_name')`, and reject if they diverge). Additionally, consider refusing to treat a blank `webhook_secret` as "verified" for organizations that also own repositories with review stacks enabled, or require all configured orgs to have non-blank secrets.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "forged pull_request opened via no-secret org mutates victim repo review stack" do
  # Precondition: configure Shipit with two orgs — "no-secret-org" (no webhook_secret)
  # and "victim-org" (owns @stack with review_stacks_enabled: true, provisioning_behavior_allow_all: true)
  Shipit.stubs(:github_app_config).with('no-secret-org').returns({}) # no webhook_secret -> verify returns true

  @request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature header set / signature omitted or garbage

  body = {
    action: 'opened',
    number: 99,
    pull_request: {
      id: 1, number: 99, url: 'https://api.github.com/x', title: 't', state: 'open',
      additions: 1, deletions: 0,
      head: { sha: 'a' * 40, ref: 'attacker-branch' },
      user: { login: 'attacker' },
      assignees: [],
      labels: []
    },
    repository: {
      owner: { login: 'no-secret-org' }, # used ONLY for signature-org selection
      full_name: 'victim-org/victim-repo' # actual target mutated by the handler
    },
    sender: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::ReviewStack.where(repository: victim_repository).count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Assert on both sides of the binding: `repository_owner` (`no-secret-org`, whose secret verified the request) must equal the org of `params.repository.full_name` (`victim-org`, whose stack was mutated) — the test demonstrates they diverge yet the mutation still occurs, proving the vulnerability. Note: exact fixture setup for multi-org `secrets.github` config and `victim_repository`/review-stack fixtures was not directly inspected in this session and would need to be confirmed against `test/fixtures` and `config/secrets` handling before running.
