### Title
Griefing via bypassing withdraw permanently desyncs `pool_state.lp_supply` from real LP circulating supply, permanently locking pool funds - (File: `programs/cp-swap/src/instructions/withdraw.rs`, `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState.lp_supply` is a manually-tracked mirror of the LP mint's circulating supply, updated only inside the program's `deposit`/`withdraw` instructions [1](#0-0) [2](#0-1) . Because the LP mint uses the standard `mint::authority = authority` (pool PDA) but token *burning* is authorized by the token-account owner (not the mint authority), any LP holder can call the SPL Token/Token-2022 `Burn` instruction directly on their own `owner_lp_token`/`creator_lp_token` account outside of this program, permanently destroying LP tokens without ever decrementing `pool_state.lp_supply`.

### Finding Description
`PoolState` stores `lp_supply` as an explicit field [3](#0-2) , only mutated by the program's own logic: incremented in `deposit` via `pool_state.lp_supply.checked_add(...)` before minting [4](#0-3) , and decremented in `withdraw` via `pool_state.lp_supply.checked_sub(lp_token_amount)` before calling `token_burn` [5](#0-4) .

The `Withdraw` accounts context only requires `token::authority = owner` on `owner_lp_token` [6](#0-5)  — it does not, and cannot, prevent the same owner from invoking the token program's `Burn` instruction directly against that same account outside of this program's instruction set, since SPL Token/Token-2022 authorizes `burn` based on token-account ownership, not on the mint authority (which here is the pool PDA `authority`, only used for `mint_to`/`burn` CPIs invoked by the program, see `token_burn`/`token_mint_to` in `utils/token.rs` [7](#0-6) ). Any holder can therefore reduce the real, on-chain circulating LP supply through a path that never touches `pool_state.lp_supply`, exactly mirroring the reported griefing pattern where a token's transfer-to-null path bypasses the tracked accounting variable.

Once this divergence occurs, it is permanent and irrecoverable: `pool_state.lp_supply` is never reconciled against the LP mint's actual `supply` field anywhere in the program.

### Impact Explanation
`lp_supply` is the sole denominator used in `CurveCalculator::lp_tokens_to_trading_tokens` for all subsequent withdrawals [8](#0-7) : `token_amount = floor(lp_token_amount * vault_amount / lp_supply)`. If the tracked `lp_supply` is permanently inflated relative to the real circulating LP supply (due to tokens burned outside `withdraw`), then the sum of all future legitimate withdrawals (bounded by the real, now-smaller circulating LP supply) will never be able to claim the full vault balance — a proportional share of vault funds becomes permanently stranded and unclaimable by any user, since no LP tokens exist to redeem it and `lp_supply` never self-corrects. This is a permanent, irrecoverable freezing of pool/LP funds, reachable by any unprivileged token holder in a single transaction using only the standard token program interface.

### Likelihood Explanation
Likelihood is high: burning one's own SPL/Token-2022 token account balance is a completely standard, permissionless operation requiring only account ownership — no special privilege, feature flag, or off-chain component is needed. Any liquidity provider (or a malicious actor who acquires a small amount of LP tokens) can trigger the divergence with a single `burn` instruction.

### Recommendation
Do not rely on a manually tracked `lp_supply` field that can diverge from the LP mint's actual on-chain supply. Either:
- Read `lp_mint.supply` directly wherever `pool_state.lp_supply` is currently used for share calculations instead of maintaining a separate counter, or
- Set the LP mint's authority such that only the program can ever decrease supply (not achievable for `burn`, since SPL Token always allows the token-account owner to burn), so option 1 (sourcing the divisor from the mint account itself) is the robust fix.

### Proof of Concept
1. Attacker (or any LP holder) deposits liquidity via `deposit`, receiving `lp_token_amount` LP tokens; `pool_state.lp_supply` is incremented accordingly [1](#0-0) .
2. Instead of calling this program's `withdraw` instruction, the attacker submits a standard SPL Token/Token-2022 `Burn` instruction directly against their own `owner_lp_token` account for some amount `X` (they are the token-account owner/authority, which is all `Burn` requires).
3. The LP mint's real `supply` decreases by `X`, but `pool_state.lp_supply` is untouched, since only `deposit`/`withdraw` in this program update it.
4. `pool_state.lp_supply` is now permanently `X` higher than the real circulating LP supply, with no code path anywhere in the program to reconcile it.
5. All subsequent `withdraw` calls compute `token_amount = floor(lp_token_amount * vault_amount / pool_state.lp_supply)` using the inflated denominator, so the sum of everything that can ever be legitimately withdrawn undershoots the true vault balance by a fraction proportional to `X`, permanently locking that portion of pool funds.
