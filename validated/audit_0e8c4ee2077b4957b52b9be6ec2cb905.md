### Title
StatusHandler#process writes GitHub commit statuses onto matched Commit records without ever validating the payload's `repository.full_name`, letting a webhook for a fabricated/unrelated repository mutate a victim stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)`, which uses the matched commit's own `stack_id` to write the status. Unlike the base `Handler` class's `stacks` helper (which scopes lookups via `Repository.from_github_repo_name(repository_name)`), `StatusHandler` never consults `payload['repository']['full_name']` at all, so the repository field is decorative for this handler.

### Finding Description
The broken binding, stated explicitly: `repository.full_name` (payload) == the repository whose stacks are consulted before writing the status. In `StatusHandler`, this equality never holds because the right-hand side is never computed.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-30) only checks that the HMAC signature matches the GitHub App registered for `repository_owner` (`params.dig('repository','owner','login')`). This proves the request came from *some* org Shipit trusts, not that the `sha` or the rest of the payload pertains to that org's repository. [1](#0-0) 
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw payload to `StatusHandler.call`. [2](#0-1) 
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a global, unscoped lookup across every stack/repository in the Shipit instance. [3](#0-2) 
- `Commit#create_status_from_github!` writes `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is read off the matched `Commit` record - i.e., the victim's real stack - never off the payload's repository. [4](#0-3) 
- Contrast with the base `Handler` class, which provides a `stacks` helper explicitly designed to scope any handler's work to `Repository.from_github_repo_name(repository_name)`; `StatusHandler` simply never calls it (grep across `app/models/shipit/webhooks/handlers/*.rb` shows only `check_suite_handler.rb` uses `stacks.`, `StatusHandler` does not). [5](#0-4) 

Attacker request: attacker controls (or creates) a GitHub org/repo, registers/receives a valid webhook for it (any org Shipit already trusts, satisfying `verify_signature`'s per-org signature check), and sends a `status` event with:
- `repository.full_name = 'nonexistent/nowhere'` (or any repo, real or fake - it's never dereferenced)
- `sha` = the real SHA of a commit belonging to a victim's stack (SHAs are frequently public - visible in a victim's public GitHub repo, PR, or even Shipit's own UI if it's used for public repos)
- `state`, `context`, `description`, `target_url` of the attacker's choosing.

Because `Repository.from_github_repo_name('nonexistent/nowhere')` is never called by `StatusHandler` (only by the unused `stacks` helper), the fabricated repository name causes no failure - the handler proceeds straight to `Commit.where(sha: ...)`, finds the victim's real `Commit` row (matched purely by `sha`, globally, with no stack/repository predicate), and writes an attacker-controlled `Status` onto it using the victim's real `stack_id`.

Existing guards checked and why they don't stop this:
- `verify_signature` / `GitHubApp#verify_webhook_signature`: validates only that the payload was signed by a trusted org's secret - it authenticates the sender's org, not the payload's repository or the SHA's ownership.
- `drop_unhandled_event`: irrelevant, `status` is a handled event.
- `ExplicitParameters` schema in `StatusHandler.params`: only validates presence/types of `sha`, `state`, etc. - never cross-checks `repository`.
- `Repository.from_github_repo_name`, `Stack` scoping, `subset`/`url` validators: never invoked by this handler at all.

### Impact Explanation
An attacker with a webhook secret for any single org they control can inject arbitrary GitHub commit statuses onto any other org/stack's commit in the same Shipit instance, as long as they know/guess a valid SHA. Since `Status` state feeds into `Commit#status`/`Stack#deployable?` and blocking/required status computations (`stack.blocking_statuses`, `commit.deployable?`), this can be used to mark a victim's commit as `"success"` to unblock/force a deploy path that depends on required CI status, or as `"failure"`/`"error"` to jam continuous delivery for a targeted victim stack. This is a cross-tenant write (one repository's webhook mutating another repository's stack/commit data) matching the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs a valid webhook secret for at least one org/app registration that Shipit already trusts (which they can obtain themselves, e.g., by installing the configured GitHub App on their own org/repo, per the attacker model - "a valid webhook_secret from any one org they control"), and the SHA of a commit in the target victim's stack (commonly discoverable via public GitHub history, PRs, or Shipit's own public UI). No Shipit session, API token, or team membership is required. This is fully repeatable against arbitrary stacks/commits, limited only by SHA knowledge, making it low-cost and highly feasible.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository claimed in the payload (mirroring the base `Handler#stacks` helper), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently restrict to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only be applied to a commit belonging to a stack whose repository matches `Repository.from_github_repo_name(payload['repository']['full_name'])`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub required):
1. Create a victim `Repository` (`victim/repo`) and `Stack`, and a `Commit` on that stack with a known `sha` (e.g. `"a" * 40`).
2. Do **not** create any `Repository` record for `nonexistent/nowhere` - assert `Shipit::Repository.from_github_repo_name('nonexistent/nowhere').nil?` is `true` (left side of the binding: repository consulted).
3. Build a payload: `{ 'sha' => victim_commit.sha, 'state' => 'success', 'context' => 'ci/attacker', 'repository' => { 'full_name' => 'nonexistent/nowhere' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as the question concerns the handler's own logic once dispatched).
5. Assert `victim_commit.reload.statuses.last.context == 'ci/attacker'` and `victim_commit.reload.statuses.last.state == 'success'` and `victim_commit.reload.statuses.last.stack_id == victim_stack.id` - proving the write happened despite the nonexistent repository, i.e. the binding "repository field present == repository consulted before write" is false (right side never computed, yet the write succeeds).
