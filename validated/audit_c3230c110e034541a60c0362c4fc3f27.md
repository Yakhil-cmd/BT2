### Title
Webhook signature is authenticated against one organization while the repository acted upon is taken from an unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to check the signature against based on an attacker-supplied payload field (`repository.owner.login` or `organization.login`), but the handler that actually executes (e.g. `PushHandler`) resolves the target repository from a *different* payload field (`repository.full_name`) that is never bound to the signature check. If any configured GitHub organization in the deployment has no `webhook_secret` set, signature verification is skipped entirely for that organization, letting an unprivileged attacker submit a webhook whose "authenticating organization" field points to the secret-less org while its "acted-upon repository" field points to an unrelated, privileged repository/stack.

### Finding Description
`verify_webhook_signature` short-circuits to `true` whenever no secret is configured for the organization determined by `repository_owner`: [1](#0-0) 

`repository_owner`, used only to pick which app/secret to check against, is read straight from the untrusted JSON body: [2](#0-1) 

After (bypassed) verification, the full raw JSON is dispatched unmodified to handlers: [3](#0-2) 

The base `Handler` (and thus every event handler, e.g. `PushHandler`) resolves the actual repository/stack to mutate from a separate field, `repository.full_name`, which was never involved in the authentication decision: [4](#0-3) 

`PushHandler` then calls `sync_github` with an attacker-chosen `expected_head_sha` on every non-archived stack matching that repository/branch: [5](#0-4) 

The broken equality is: `repository_owner` (organization whose secret authenticated the request) ≠ `payload.dig('repository','full_name')` (repository the handler actually writes to/syncs). Because `webhook_secret` is optional per-organization (`@webhook_secret = @config[:webhook_secret].presence`), a Shipit instance managing multiple GitHub organizations where at least one has no secret configured allows an attacker to set `repository.owner.login`/`organization.login` to that unsecured org (satisfying `verify_signature`) while setting `repository.full_name` to any other, fully-secured organization's repository that has stacks in Shipit. The handler never re-validates that the two fields agree.

### Impact Explanation
This lets an unprivileged external attacker forge GitHub webhook events (`push`, `status`, `commit_status`, `deployable_status`, `check_suite`, etc.) targeting a repository/stack belonging to a completely different, properly-secured organization, without ever knowing that organization's `webhook_secret`. Depending on which handler is invoked this can trigger `Stack#sync_github` with an attacker-chosen `expected_head_sha`, or forge commit/CI statuses that continuous-deployment logic relies on to gate auto-deploys, resulting in an unauthorized deploy/rollback trigger on a repository the attacker does not control. This matches the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment manage more than one GitHub organization and that at least one of them has no `webhook_secret` configured — a legitimate, documented, optional configuration (`docs/setup.md`, `lib/shipit/github_app.rb`) rather than a misuse of the engine. Any organization without a configured secret becomes a "skeleton key" for forging events against every other configured organization's repositories, since the field used to pick which secret to check is fully attacker-controlled and decoupled from the field the handlers actually act on.

### Recommendation
Bind signature verification to the same repository identity the handler will use: after selecting the `github_app` for verification, re-derive and cross-check that `payload.dig('repository','full_name')`'s owner matches the verified organization before dispatching to handlers. Additionally, consider making `webhook_secret` mandatory for all configured organizations, or, at minimum, refuse to process any event whose `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret`) and `OrgB` (has a `webhook_secret`, owns a stack `OrgB/app` tracked in Shipit).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/app", "owner": { "login": "OrgA" } }
}
```
using any/no `X-Hub-Signature` value.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for `OrgA`. [1](#0-0) 
4. `PushHandler` resolves `repository_name` as `"OrgB/app"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgB`'s stack, even though the request was never authenticated by `OrgB`'s secret. [4](#0-3) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
