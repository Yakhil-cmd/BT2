### Title
Cross-Organization / Cross-Repository Commit Status Forgery via Unbound Webhook Signature Verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using an **unverified** field taken from the JSON body itself, and that organization binding is never propagated to the handlers that actually mutate state. `StatusHandler` in particular looks up commits to update by `sha` alone, with **no repository or organization scoping at all**. This breaks the equality `organization that authenticated == repository/commit that is written`, letting an attacker whose payload passes signature verification for *any* configured organization forge commit statuses on commits belonging to a completely different, unrelated tracked repository/organization.

### Finding Description
`verify_signature` derives the org used for signature verification purely from attacker-controlled JSON: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Because `repository_owner` comes straight from the unverified body, the attacker chooses *which* configured organization's secret is used to validate the request. Per `docs/setup.md` and the shipped `secrets*.yml` examples, `webhook_secret` is explicitly optional per-organization; when it is blank, `GitHubApp#verify_webhook_signature` short-circuits to `true` for *any* signature: [2](#0-1) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

Once the request clears this org-selectable, org-scoped check, the actual event handlers process the *entire* payload without re-validating that the data inside belongs to the organization that was authenticated. Most handlers scope by `payload.dig('repository', 'full_name')`: [3](#0-2) 

but `StatusHandler`, used for the `status` event, does not scope by repository or organization at all — it matches solely on commit SHA across the entire Shipit database: [4](#0-3) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So the binding that should hold — `organization authenticated by signature == organization/repository whose commit is written` — is broken: `verify_signature` binds only to `repository.owner.login`/`organization.login` (chosen by the attacker among any org configured in `Shipit.github`), while `StatusHandler` writes to whatever commit row happens to share the given `sha`, irrespective of repository/org.

### Impact Explanation
An unprivileged attacker can forge a `status` webhook that is authenticated as organization A (e.g., one configured with no `webhook_secret`, an explicitly supported configuration) but that sets `state: "success"`/`failure` on a commit that actually belongs to organization B's tracked repository, as long as the SHA values collide (attacker can pick their own repository's commit SHA, or brute a short-SHA collision, or simply target org B's own known commit shas seen from GitHub's public API). Forged "success" statuses can satisfy `deployable_status` checks used by Shipit to gate whether a commit is safe to ship, enabling an **unauthorized deploy** against a repository the attacker never authenticated against. This matches the Critical impact category "an unauthorized deploy... rollback or merge."

### Likelihood Explanation
Exploitation requires no session, API token, or knowledge of any other organization's secret — only that the Shipit instance has at least one configured GitHub organization whose `webhook_secret` is unset (explicitly documented and shown as a valid/default configuration in `docs/setup.md` and `config/secrets.development.shopify.yml`), or that the attacker controls any org onboarded to the same multi-tenant Shipit instance (a documented supported setup — "Using Multiple Github Applications"). The `status` handler's complete lack of repository scoping makes this trivially reachable once past `verify_signature`.

### Recommendation
- Bind signature verification to the same repository/organization identifier that handlers use to select data to mutate (i.e., verify against `repository.full_name`'s owning org, not an independently-chosen field), and reject if they disagree.
- In `StatusHandler#process`, scope the `Commit` lookup by the commit's owning repository (derived from `payload.dig('repository','full_name')`) in addition to `sha`, matching the pattern used by other handlers via `Handler#repository_name`/`#stacks`.
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for events that mutate deploy-gating state; require a configured secret for any organization enabled in `Shipit.github`.

### Proof of Concept
1. Configure/observe a Shipit instance with at least two GitHub orgs in `Shipit.github`, where org `A` has no `webhook_secret` set (a documented, supported configuration) and org `B` (the victim) has tracked repositories/commits with deployable_status checks.
2. Find or predict a commit SHA that exists in Shipit for org `B`'s tracked repository (commit SHAs are public via GitHub).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-org-B-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "A" }, "full_name": "A/anything" },
  "organization": { "login": "A" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "A")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` for any/no signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds org B's commit purely by SHA, then calls `commit.create_status_from_github!(params)`, marking it `success` — with no relation to org A ever having write access to org B's repository.
