### Title
Cross-repository/cross-organization forged commit statuses via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` writes GitHub "status" webhook data to a `Commit` record by looking it up **only by SHA, globally across the whole database**, with no scoping to the repository/organization that the webhook signature was verified against. This breaks the trust binding "organization that authenticated the webhook == repository/stack the webhook is allowed to mutate."

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate against using a field taken from the **unverified** JSON body itself: [1](#0-0) [2](#0-1) 

That check only proves the request was signed by *some* configured organization's secret — it says nothing about which repository/stack the payload is allowed to touch. The base `Handler` class does provide a repository-scoping helper (`stacks`, using `payload.dig('repository', 'full_name')`): [3](#0-2) 

But `StatusHandler` never uses it. Instead it resolves the target purely by SHA against the entire `Commit` table: [4](#0-3) 

`Commit.create_status_from_github!` then creates a `Status` record with the attacker-controlled `state`/`description`/`context` for that commit, unconditionally: [5](#0-4) 

`Status` creation directly influences deployability logic and can enable CI on a stack: [6](#0-5) [7](#0-6) 

Additionally, `Shipit.github(organization:)` shows this engine explicitly supports **multiple GitHub organizations/apps in a single Shipit install** (multi-tenant secrets schema, as also seen in the test fixture `secrets_double_github_app.yml`): [8](#0-7) 

And critically, `verify_webhook_signature` treats an **unset webhook secret as automatically verified**: [9](#0-8) 

Given the setup docs list the webhook secret as *optional*: [10](#0-9) 

Putting these together: in a multi-org Shipit deployment (an explicitly supported and documented configuration), if any one of the configured organizations has no `webhook_secret` set (or an attacker otherwise knows/controls that org's secret because they administer that org's GitHub App), that attacker can send a completely unsigned/self-signed `status` webhook to the shared `/webhooks` endpoint naming `repository.owner.login` = their own org (satisfying `verify_signature`), but with an arbitrary `sha` value that actually belongs to a commit tracked under a **different** organization/stack entirely — because `StatusHandler` never checks that the commit's stack/repository matches the organization that was authenticated. `Commit.where(sha: params.sha)` has no organization or stack filter at all.

This exactly matches the reported bug class ("a payload field acted on but never covered by the verified signature" / "an organization that authenticated versus the repository that is written"): the field driving signature selection (`repository.owner.login`) is disjoint from the field(s) actually acted upon (`sha`, globally).

### Impact Explanation
An attacker who controls (or knows the secret for, or benefits from the secret being unset) any single organization configured on a shared Shipit instance can forge `success` (or any) CI statuses for commits belonging to **stacks/repositories under other organizations** they have no legitimate access to. Since `Commit#deployable?` and CI-gating (`stack.ignore_ci?`/`success?`) depend on these `Status` records, this can allow an unauthorized commit to be marked as CI-passed, unblocking it for deployment through Shipit's normal deploy UI/flow — an unauthorized-deploy-enabling primitive, satisfying the "High"/"unauthorized deploy" impact bar.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (an explicitly supported, documented configuration) where at least one configured org either has no `webhook_secret` set or whose secret the attacker can obtain by legitimately administering that org's own GitHub App (they don't need any privilege on the victim org/repo). Given `webhook_secret` is documented as optional and the multi-org schema is a first-class, tested feature (`test/dummy/config/secrets_double_github_app.yml`), this is a realistic misconfiguration/deployment scenario, not a purely theoretical one.

### Recommendation
`StatusHandler` (and any other handler that doesn't already use `Handler#stacks`) should scope its `Commit` lookup to the repository/stack derived from the webhook payload and confirm that repository belongs to the organization whose secret validated the signature, rather than doing a global, unscoped `Commit.where(sha:)` lookup. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank; a per-organization webhook secret should be mandatory, or unsigned webhooks should be rejected outright.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` (attacker-administered, `webhook_secret` unset) and `OrgB` (victim, has stacks/commits tracked).
2. Attacker finds a real commit SHA under an `OrgB` stack, e.g. via GitHub's public API/UI (`sha = <victim_sha>`).
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim_sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; since `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no valid signature needed.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim_sha>")`, finds the `OrgB` commit, and calls `create_status_from_github!`, creating a `success` `Status` for it — despite the request never being authenticated by anything associated with `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
