### Title
Unhandled division-by-zero / uncaught exception in TPS-fee validation when `earned_headers_commission_share` is 0 - ([File: validation.js])

### Summary
`validateTpsFee()` in `validation.js` computes a per-recipient `share` from the unit's `earned_headers_commission_recipients` list and, if that share is falsy (i.e. `0`), does not reject the unit gracefully through the normal callback-based error path — it instead performs a raw `throw Error(...)` from inside an `async` validation function that is invoked while processing an incoming, attacker-controlled unit. [1](#0-0) 

### Finding Description
`earned_headers_commission_recipients` is a unit field that lets a multi-authored unit's author(s) redirect their share of headers commission to another address, with `earned_headers_commission_share` stored as a plain `INT` percentage with no positivity constraint at the schema level: [2](#0-1) 

During validation of a v4+ unit, `validateTpsFee()` derives `share = recipients[address] / 100` for every recipient and, unlike the analogous ImageMagick `sRGBTransformImage()` colorspace flaw (division by zero triggering undefined behavior on crafted input), the ocore code path even acknowledges the danger by adding a guard — but the guard converts the bad-input case into an unhandled JS exception rather than a normal unit rejection:
```
const share = recipients[address] / 100;
if (!share)
    throw Error(`invalid share for address ${address}: ${share}`);
``` [3](#0-2) 

Because `validateTpsFee` is `async` and is invoked as part of the standard validation pipeline for every incoming unit, a `throw` here does not flow back through the `callback(err)` convention used everywhere else in `validation.js` to reject malformed units cleanly; it instead surfaces as a rejected promise / uncaught exception in the validation call chain. This is analogous to the CVE's "division by zero...triggers undefined behavior" — an attacker-supplied value (`earned_headers_commission_share = 0`) drives an arithmetic operation into a degenerate state that the surrounding code does not handle as a controlled failure.

The same unguarded division pattern appears again without even the `throw` guard in `storage.js`'s `getPaidTpsFee()`, which is used by `parent_composer.js` when picking parents / computing TPS fees for descendant units, and which divides `tps_fees_balance / share` with no zero-check at all: [4](#0-3) 

### Impact Explanation
`earned_headers_commission_recipients` is settable by any ordinary unit poster with multiple authors — no special privilege, hub, or peer role is required. If such a unit sets a recipient's `earned_headers_commission_share` to `0`, `validateTpsFee` throws instead of returning a controlled validation error. Since this code runs for every node validating the unit (as part of standard DAG unit acceptance), this can either crash the validating process (denial of service — "a network unable to confirm new units") or, if some outer wrapper silently swallows the exception, cause nodes to disagree on whether the unit is valid (some crash, some don't, or the promise rejection is not handled uniformly), which risks node disagreement on unit validity. Later, if such a zero-share unit is present in the DAG, `storage.js`'s unguarded `getPaidTpsFee` division can also propagate `Infinity`/`NaN` into TPS-fee bookkeeping used by `parent_composer.js` when other nodes/wallets try to compose descendant units, potentially impairing normal unit composition.

### Likelihood Explanation
Reaching this code path requires only: (1) a v4+-network unit, (2) multiple authors, and (3) an `earned_headers_commission_recipients` entry with `earned_headers_commission_share: 0`. No schema-level constraint prevents `0` as a percentage, and this is data any unprivileged unit author fully controls, so the precondition is trivial to construct.

### Recommendation
- In `validateTpsFee` (`validation.js`), replace the `throw Error(...)` with a normal `return callback("invalid earned_headers_commission_share for address " + address)` so malformed units are rejected through the standard validation-error path instead of raising an uncaught exception.
- Add explicit validation (in the message/field validator for `earned_headers_commission_recipients`) that `earned_headers_commission_share` must be a positive integer between 1 and 100, rejecting `0` or negative values at parse time before any downstream division is performed.
- Add the same zero-share guard to `storage.js`'s `getPaidTpsFee()` (and any other unguarded `recipients[address] / 100` division sites) to avoid propagating `Infinity`/`NaN` into TPS-fee accounting.

### Proof of Concept
1. Craft a multi-authored unit (mci ≥ `constants.v4UpgradeMci`) whose `earned_headers_commission_recipients` array includes an entry `{ address: <validAddress>, earned_headers_commission_share: 0 }`.
2. Broadcast/post the unit to a node.
3. During validation, `validateTpsFee` computes `share = 0/100 = 0` for that address and executes `throw Error(...)` instead of calling `callback(err)`, producing an unhandled exception/rejected promise in the unit-validation flow rather than a clean "unit rejected" response.

Note: I was not able to fully trace, within the available tool budget, whether an outer wrapper (e.g. `util.callbackify` or a top-level `try/catch` around the validation pipeline) intercepts this `throw` and converts it into a graceful rejection versus an actual process crash / unhandled rejection. Confirming the exact end-to-end behavior (crash vs. safely-caught exception) would require running the validation pipeline or reading the caller of `validateTpsFee` and the async/await error-handling wrapper in `validation.js`, which was not available in the indexed context I retrieved.
