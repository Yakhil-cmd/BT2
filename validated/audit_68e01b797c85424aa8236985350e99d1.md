### Title
Attestation-based `attested` definition condition and asset `spender_attested` gate accept permanently-persisted attestation records with no revocation path - (File: storage.js / definition.js)

### Summary
`Definition.evaluate` (`case 'attested'`) and asset payment validation (`validatePayment` → `storage.loadAssetWithListOfAttestedAuthors`) both authorize spending/actions based on the mere historical *existence* of an `attestation` unit issued by a trusted attestor, via `storage.filterAttestedAddresses`. The query only checks that some stable, sequence-good attestation unit from an authorized attestor exists before `last_ball_mci`; it never checks whether that specific attestation claim is still the attestor's current/valid claim. There is no on-chain mechanism the attestor can use to invalidate a previously issued attestation for a specific address (short of the address changing its definition, which is separately excluded). This mirrors CVE-2021-36372: an authorization artifact, once issued and persisted, remains usable by the holder even after the issuer intends to revoke it.

### Finding Description
`storage.filterAttestedAddresses` [1](#0-0)  is the sole gate used to determine whether an address is "attested" for purposes of:
- The oscript/definition primitive `['attested', [address, [attestor_addresses]]]`, evaluated in `definition.js`'s `evaluate` function: [2](#0-1) 
- Asset spending gated by `spender_attested`, via `loadAssetWithListOfAttestedAuthors` and `validatePayment`: [3](#0-2) [4](#0-3) 

The SQL used is:
```
SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit)
WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good'
  AND main_chain_index>IFNULL(
        (SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit)
         WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good'
         ORDER BY main_chain_index DESC LIMIT 1),
      0)
```
This is an "ever attested since the last definition change" check, not a "currently attested" check. The `address_definition_changes` sub-clause only invalidates old attestations if the address itself changes its signing definition (e.g., the address was recycled to a new owner) — it provides zero protection against the attestor themselves wanting to revoke a specific attestation claim (e.g., after discovering fraud, KYC failure, sanctions, compromised counterparty, etc.), because there is no "latest attestation wins" semantic and no revocation message type. Once an attestor has ever posted an `attestation` message for an address with a matching `attestor_address`, that single historical record is sufficient forever (as long as the address keeps the same definition), regardless of any subsequent attestor action.

Contrast this with other privilege/state primitives in the same file that explicitly use "latest state wins" semantics, e.g. `in data feed`/data feeds and `has definition change`, which are inherently designed around a single canonical latest value. Attestations have no analogous "latest" concept in the validation query — every historical positive attestation is an eternally valid credential.

This is directly analogous to the reported CVE: in Apache Ozone, a block token, once minted and persisted, could still be used by an authenticated holder even after the granting authority intended to revoke access, because the system checked token validity based on stored token material rather than current authorization state. Here, an `attested` grant, once persisted as an `attestation` unit, remains a valid credential for spending/definition-satisfaction forever, because the check is existence-based rather than state-based, and the protocol provides no mechanism to overwrite/expire it.

### Impact Explanation
Any asset issuer that sets `spender_attested: true` (e.g., KYC/AML-gated assets, regulated private assets) or any address/AA that uses `['attested', ...]` in its definition to gate control of funds is exposed:
- An attestor who legitimately attested an address (e.g., "verified KYC")  and later determines the attestation should be revoked (fraud discovered, sanctions, key compromise, contract violation) has no on-chain way to revoke it. The previously attested address can continue to spend or unlock funds indefinitely.
- For assets with `spender_attested`, this can enable unauthorized spending of a regulated/gated asset (fund loss/violation of the enforced business rule) by a party whose privilege was supposed to have been revoked.
- For AA/oscript definitions using `attested` as an authorization gate for AA-controlled funds or a shared/multisig address, the same permanently-valid credential can allow unauthorized fund control (AA fund loss / freezing bypass by an unauthorized party) after the party's trust was supposed to be revoked.

This is a Medium/High severity improper-privilege-management issue: it doesn't create a network-wide consensus split (all nodes evaluate the same, deterministic SQL and agree on validity), but it produces genuine unauthorized fund control by a party whose authorization was supposed to have ended — the exact impact class (concrete unauthorized spending / AA fund loss) required by the validation criteria.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (1) an asset or AA/shared-address definition that relies on `attested`/`spender_attested` for access control, and (2) an attestor that has issued at least one attestation for an address it later wants to revoke. This is a realistic and intended usage pattern for regulated/KYC-gated Obyte assets and AAs (attested-based authorization is a documented oscript feature), so any deployment relying on attestor-driven access revocation is silently vulnerable — the attestor may believe they can "unattest" someone by simply not reattesting or by posting a negative attestation, but the validation logic here never looks for a "negative"/latest record, it only requires any historical positive match.

### Recommendation
- Change `filterAttestedAddresses` to select the attestor's *latest* attestation record for a given (attestor_address, address) pair (ordered by `main_chain_index`/`level`, similar to the "latest wins" pattern already used elsewhere, e.g. `asset_attestors`) rather than treating any historical match as sufficient.
- Introduce an explicit `revoked` or boolean status field in the attestation payload/profile so an attestor can supersede a previous attestation with a newer, authoritative state, and make `filterAttestedAddresses` respect only the most recent record's status.
- Document clearly that `attested` is a "monotonic historical claim" primitive rather than a live authorization gate, if the semantics cannot be changed for backward-compatibility reasons, so asset/AA authors relying on it for revocable KYC/AML gating are aware of this limitation.

### Proof of Concept
1. Attestor A creates an asset `X` with `spender_attested: true` and lists itself in `asset_attestors`.
2. Attestor A posts an `attestation` unit for address `B` (`{address: B, profile: {...}}`), which becomes stable.
3. Address `B` receives asset `X` and is now permitted to spend it (`filterAttestedAddresses` returns B).
4. Attestor A later determines B should lose spending rights (e.g., B failed ongoing KYC checks) and wants to revoke B's attested status. There is no protocol message that removes/overrides the earlier attestation record while B's address definition (signing keys) remains unchanged.
5. B posts a `payment` message spending asset `X`. `validatePayment` → `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` still finds the original stable attestation unit satisfying `attestor_address IN(...) AND address IN(...) AND main_chain_index<=last_ball_mci AND is_stable=1`, and B's spend is validated as authorized [5](#0-4) , even though A intended to revoke access. [1](#0-0) [2](#0-1) [5](#0-4)
