### Title
Cross-repository status forgery via webhook signature/commit-lookup mismatch enables unauthorized continuous deployment - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App configured for the **organization named in the payload** (`repository.owner.login`, falling back to `organization.login`), then hands the raw, still-untrusted JSON `params` to every registered handler for the event. [1](#0-0) [2](#0-1)  For the `status` event, `StatusHandler#process` never re-checks that binding: it looks up commits **globally by SHA across every stack/repository in the installation** and writes a GitHub-supplied status onto whatever commit matches. [3](#0-2) 

### Finding Description
The signature check only proves the request was signed with the `webhook_secret` of *some* organization/GitHub App configured in `Shipit.secrets.github` — the organization is picked straight out of the attacker-influenced JSON body before any signature validation occurs:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` resolves the app config (and thus the `webhook_secret`) purely from this field, then `verify_webhook_signature` HMACs the *entire* raw body against that secret. [4](#0-3)  This is a legitimate multi-tenant design (documented in `docs/setup.md` "Using Multiple Github Applications") — Shipit can host many organizations, each with its own GitHub App/secret. [5](#0-4) 

However, once the signature is verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same untrusted body to handlers that make no attempt to confirm the *content* of the payload (the repository being written) matches the *organization* whose secret validated it. [6](#0-5) 

`StatusHandler` is the clearest break: its param schema requires only `sha` and `state` (no `repository` scoping at all), and `process` resolves the target purely by SHA:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

`Commit.where(sha:)` is a database-wide query with no `stack_id`/repository filter — a commit belonging to organization/repo B can be matched even though the request's signature was validated using organization A's secret. [8](#0-7) 

`create_status_from_github!` writes the forged status and, through `add_status`, re-evaluates the commit and can call `schedule_merges` / update deployability state. [9](#0-8)  If the affected commit's `state` becomes `success`, `Commit#deployable?` returns true (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), and `after_commit` hooks already scheduled `schedule_continuous_delivery`, which is re-evaluated whenever status changes:
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [10](#0-9) 

`ContinuousDeliveryJob#perform` proceeds to `stack.trigger_continuous_delivery` for the target stack whenever that stack has `continuous_deployment?` enabled and isn't occupied/blocked by a schedule. [11](#0-10) 

**Binding broken (as an equality):** `organization authenticated by verify_signature (payload.repository.owner.login / organization.login, checked against webhook_secret)` **should equal** `organization/repository that owns the commit written by StatusHandler (commit.stack.repository)`. Nothing in `WebhooksController` or `StatusHandler` enforces this equality — the commit lookup is entirely SHA-keyed and repository-agnostic.

### Impact Explanation
An operator of a low-value, unrelated tenant organization onboarded to the same shared Shipit instance (who legitimately possesses that org's own `webhook_secret`, e.g. as an admin of their own GitHub App integration) can POST a forged `status` webhook, signed with their own org's secret, but carrying the `sha` of a commit belonging to a completely different, higher-value tenant's stack (commit SHAs are public GitHub metadata, trivially discoverable). By setting `state: "success"`, they can mark an unreviewed/malicious commit on that other stack as CI-passing, and — if that stack has continuous deployment enabled — cause Shipit to automatically deploy it via `ContinuousDeliveryJob`/`stack.trigger_continuous_delivery`. This is an unauthorized deploy achieved purely by crossing a repository/organization trust boundary that the webhook signature was supposed to enforce, matching the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` of at least one organization configured in the shared Shipit instance's `secrets.yml` — plausible in any multi-tenant deployment where multiple, differently-trusted teams each administer their own GitHub App entry, since nothing in Shipit prevents a lower-trust tenant's credentials from writing to another tenant's data. No access to the victim organization's GitHub, repository, or Shipit account is needed; only the target commit SHA, which is public.

### Recommendation
In `StatusHandler` (and any other handler that resolves records independent of `payload['repository']`), scope the lookup to the repository identified by the same field used in `verify_signature`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: payload.dig('repository', 'full_name') })`, and reject/ignore the event if that repository does not belong to the authenticated organization. More generally, `WebhooksController` should pass the authenticated `repository_owner`/app identity down to handlers and have `Handler#stacks` (and any handler bypassing it) assert that the resolved repository's owner matches the organization whose secret validated the signature, rather than relying purely on the raw JSON body's internal consistency.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App in a shared Shipit deployment and knows `OrgA`'s configured `webhook_secret`.
2. Attacker identifies a commit SHA `S` belonging to `OrgB/high-value-repo`, a stack with `continuous_deployment: true`, whose HEAD commit is currently pending/failing CI.
3. Attacker crafts a JSON body:
```json
{"sha": "S", "state": "success", "repository": {"owner": {"login": "OrgA"}}}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and successfully verifies the signature (it is a valid HMAC for `OrgA`'s secret). [12](#0-11) 
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit under `OrgB/high-value-repo`, and calls `create_status_from_github!` with `state: "success"`, regardless of `OrgB` never having signed anything. [3](#0-2) 
7. If that commit becomes `deployable?` and the stack has continuous deployment enabled, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, which deploys the commit. [10](#0-9) [11](#0-10)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
