### Title
Cross-tenant `Membership` creation via unscoped `team.id` lookup in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` binds a webhook-verified `member.login` to a `Team` located solely by the numeric `github_id` from the payload, never checking that the `organization.login` used to verify the webhook signature matches the `organization` already stored on that `Team`. Since GitHub team IDs are global (not org-scoped) and `Shipit::User.find_or_create_by_login!` fetches/creates users through the non-organization-scoped `Shipit.github.api`, an attacker who owns any org with a configured `webhook_secret` can forge a signed `membership` event that injects an arbitrary attacker-controlled `User` into a victim organization's `Team` and its associated `Membership`.

### Finding Description
Broken binding: `verified_organization (from request signature) == team.organization (record mutated)` — this is never enforced.

Trace:
- `WebhooksController#verify_signature` resolves the signing app via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization','login')` for events with no `repository` key (as membership events have). [1](#0-0) 
- This only proves the request was signed with *some org's* `webhook_secret` — specifically the attacker's own org, which the attacker legitimately controls and can configure with a real `webhook_secret`.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. The lookup block (which sets `team.organization`) only executes on creation; if a `Team` with that `github_id` already exists (e.g., the victim's team, previously created via a legitimate webhook from the victim org), the existing record — with the victim's `organization` — is returned unchanged. [2](#0-1) 
- `User.find_or_create_by_login!(params.member.login)` fetches/creates the `User` via `Shipit.github.api.user(login)`, using the default (non-organization-scoped) GitHub App client — it is not bound to the attacker's org, the victim's org, or any tenant at all ("Users are global, any app can be used"). [3](#0-2) 
- `team.add_member(member)` unconditionally appends this new/global `User` to the victim `Team`'s `members`, creating a `Membership` row. [4](#0-3) [5](#0-4) 

No guard anywhere in this path compares `params.organization.login` (the tenant whose secret verified the request) against the `organization` already stored on the found `Team`. The only authentication is "did *any* org's secret sign this," not "does this org own this team."

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own configured `webhook_secret`, and body:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "x" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-controlled-login" }
}
```
Because `repository_owner` resolves to `"attacker-org"` (via the `organization.login` fallback), `verify_signature` succeeds using the attacker's own secret. `find_or_create_team!` then matches the victim's pre-existing `Team` by numeric `github_id` alone, and `attacker-controlled-login` is linked into it.

### Impact Explanation
A single forged webhook lets an attacker-controlled `Shipit::User` become a `Membership` on a victim's `Team`. If that `Team` is included in `Shipit.github_teams` (`lib/shipit.rb:256-258`), this directly satisfies `User#authorized?` [6](#0-5)  for the attacker's identity, escalating them into an authorized-user role for the Shipit instance without ever being a real member of the victim org on GitHub. This is repeatable against any `Team` whose numeric GitHub `github_id` the attacker can learn (team IDs appear in GitHub UI/API URLs and are not treated as secrets), and it is a genuinely cross-tenant mutation — one organization's verified webhook payload alters another organization's `Team`/`Membership` records.

### Likelihood Explanation
Requires: (1) the Shipit deployment configured in multi-organization mode (`secrets.github` keyed by org) so that `Shipit.github(organization:)` can resolve and verify a webhook using the attacker's own org's `webhook_secret`; (2) attacker owns/administers at least one such configured org (feasible — they only need to be a Shipit operator's "customer" org, not a privileged GitHub role in the victim org); (3) attacker knows or guesses the victim `Team`'s numeric `github_id`, and that team already exists as a `Shipit::Team` row (created by any prior legitimate membership webhook from the victim org). Given multi-tenant GitHub App setups and discoverable team IDs, this is realistically achievable and fully repeatable — each forged request can target any known team ID, at negligible cost, without any GitHub or Shipit secret belonging to the victim.

### Recommendation
In `MembershipHandler#find_or_create_team!`/`#process`, require that `params.organization.login` (case-insensitively) matches the found `Team#organization` before allowing `add_member`/`members.delete`; if it doesn't match, reject/drop the event instead of silently reusing the existing record. Additionally, scope `User.find_or_create_by_login!` calls originating from a membership webhook to the verified organization's `Shipit.github(organization:)` client rather than the global default, to avoid conflating identity resolution across tenants.

### Proof of Concept
Minitest plan (webhooks controller/model level, no live GitHub):
```ruby
test ":membership from org A cannot add a member to org B's team" do
  victim_team = shipit_teams(:some_victim_team) # organization: 'victim-org', github_id: 999
  attacker_org_secret = 'attacker-secret'
  # stub multi-org secrets so Shipit.github(organization: 'attacker-org') resolves with attacker_org_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', webhook_secret: attacker_org_secret)
  )

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'https://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' }
  }.to_json
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, payload)}"

  Shipit.github.api.expects(:user).with('mallory').returns(stub(id: 1, login: 'mallory', name: 'Mallory', email: nil, avatar_url: '', url: ''))

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: payload, as: :json
  end
  # Currently FAILS: members.count increases by 1, proving cross-tenant membership write.
end
```
Both sides of the equality — `params.organization.login` ("attacker-org") vs. `victim_team.organization` ("victim-org") — are unequal, yet the write proceeds, demonstrating the vulnerability. [2](#0-1)

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end

        end
