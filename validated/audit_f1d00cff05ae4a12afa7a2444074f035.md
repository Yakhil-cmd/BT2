### Title
Unvalidated pool-creator address in `initialize_with_permission` permanently freezes accrued creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission` accepts a `creator` account with no signer requirement, no `address` constraint, and no zero-address check. Its raw key is stored as `pool_creator` in `PoolState` at pool creation with no way to change it later, mirroring the report's `_setOwner`/`setWalletAddress` class of bug (accepting an attacker-controlled address, including the zero address, without validation).

### Finding Description
In `InitializeWithPermission`, `creator` is declared merely as:
```rust
/// CHECK: creator of pool
pub creator: UncheckedAccount<'info>,
``` [1](#0-0) 

There is no `require_keys_neq!(creator.key(), Pubkey::default())`, no signer check, and no `address =` constraint tying it to a known/trusted account. The raw, attacker-supplied key is then persisted permanently into the pool's state:
```rust
pool_state.initialize(
    ctx.bumps.authority,
    liquidity,
    open_time,
    ctx.accounts.creator.key(),
    ...
``` [2](#0-1) 

`pool_creator` subsequently gates both fee-collection paths:
- `collect_creator_fee` requires the `creator` account to be a `Signer` whose key equals `pool_state.load()?.pool_creator`. [3](#0-2) 
- `collect_creator_fee_permissionless` lets anyone trigger collection, but still creates the destination ATAs with `associated_token::authority = creator`, where `creator` is constrained only by `address = pool_state.load()?.pool_creator`. [4](#0-3) 

If `pool_creator` is set to `Pubkey::default()` (the System Program ID / "zero address", which has no corresponding private key), the permissioned path (`collect_creator_fee`) can never be satisfied because no one can produce a valid signature for that key, and the permissionless path will happily create an ATA owned by the zero address and transfer the accrued `creator_fees_token_0`/`creator_fees_token_1` into it — an ATA that no private key can ever control.

### Impact Explanation
Once creator fees are swept into an ATA owned by the zero address via `collect_creator_fee_permissionless`, or once they simply keep accumulating on-chain because `collect_creator_fee` can never be signed for, the accrued creator-fee funds become permanently unrecoverable — no account exists that can ever authorize spending from that ATA. This is a permanent freezing of real fee funds that would otherwise belong to the pool creator, satisfying the "permanent freezing of user funds" bar. The vulnerability is reachable purely through the unprivileged, in-scope `initialize_with_permission` instruction (the `payer` chooses the `creator` account with no constraint), consistent with the scope's inclusion of pool-creation instructions.

### Likelihood Explanation
Any caller of `initialize_with_permission` (which only requires holding a `Permission` PDA, not elevated protocol privilege) can pass `Pubkey::default()` (or any other unspendable/unowned address) as `creator`. This can occur either by attacker intent (griefing a pool's future fee stream) or by client-side mistake (as the original Celo report notes, "some clients may default to sending null parameters if none are specified"). No other guard in the codebase prevents or later corrects this value — there is no update-creator instruction found in the reviewed code.

### Recommendation
Add an explicit check in `InitializeWithPermission`'s account validation or in `initialize_with_permission()`:
```rust
require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default(), ErrorCode::InvalidInput);
```
Additionally consider requiring `creator` to be a `Signer` (or otherwise attested) so a pool cannot be created on behalf of an address that never agreed to be the fee recipient, matching the mitigation cLabs applied for `setWalletAddress`/`Proxy._setOwner` (explicit non-zero-address validation before persisting critical addresses).

### Proof of Concept
1. Attacker (or careless integrator) calls `initialize_with_permission` with `creator = Pubkey::default()` (the all-zero/System Program address), a valid `payer`, `amm_config`, and mint accounts.
2. The instruction succeeds: `create_pool` and `pool_state.initialize(...)` store `pool_creator = 11111111111111111111111111111111` with no validation. [2](#0-1) 
3. Swaps occur on the pool, accruing `creator_fees_token_0` / `creator_fees_token_1` in `PoolState`.
4. Anyone calls `collect_creator_fee_permissionless`, which creates ATAs with `associated_token::authority = creator` (the zero address) and transfers the accrued fees there. [5](#0-4) 
5. No one can ever sign for the zero address, so these tokens are permanently unrecoverable; alternatively, if permissionless collection is never called, `collect_creator_fee`'s `Signer` constraint against `pool_creator = 0x0` can never be satisfied by any real keypair, so the fees remain stuck in the vault forever.
