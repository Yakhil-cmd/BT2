### Title
Arbiter contract sharing to cosigners leaks peer's pairing secret and both parties' contact info - ([File: arbiter_contract.js])

### Summary
`shareContractToCosigners()` in `arbiter_contract.js` forwards the **entire** DB row of a `wallet_arbiter_contracts` record — obtained via `getByHash()` (a `SELECT *`) — to every cosigner device, with no field filtering. This is analogous to the OMERO.web issue (CVE-2021-21376): a page/message intended to convey only the necessary contract terms instead includes extra session/credential-like fields that the recipient has no legitimate need for.

### Finding Description
`getByHash()` performs `SELECT * FROM wallet_arbiter_contracts WHERE hash=?` [1](#0-0)  which returns every stored column, including `peer_pairing_code`, `my_pairing_code`, `my_contact_info`, and `peer_contact_info`.

`shareContractToCosigners()` sends this unfiltered object directly to each of "my" cosigners: [2](#0-1) 

Compare this with `createAndSend()`, which explicitly clones the contract and deletes the `cosigners` field before sending to the peer device — demonstrating that the codebase is aware unfiltered contract objects must be scrubbed before being sent to other parties, but this scrubbing was omitted for the cosigner-sharing path: [3](#0-2) 

The `peer_pairing_code` field is populated from the counterparty's `device_pubkey@hub#pairing_secret` string, set during `respond()`: [4](#0-3) 

This pairing code (`device_pubkey@hub#pairing_secret`) is the same value used elsewhere (`uri.js`, `device.js`) to permit a new device to pair with/impersonate correspondence for the owning device — i.e., it is a bearer-secret analogous to a session credential, not something that should be disclosed to unrelated third parties such as one's own multi-sig cosigners who are not party to the peer relationship.

`shareContractToCosigners()` is invoked from `respond()` upon accepting a contract and from `createSharedAddressAndPostUnit()`, sending the full contract (including the peer's pairing secret and both parties' contact info) to every device listed in `getAllMyCosigners()` — i.e., every cosigning device on "my" wallet, none of whom are otherwise entitled to the peer's pairing secret: [5](#0-4) [6](#0-5) 

### Impact Explanation
A cosigner device (which may be a less-trusted party in a multi-sig wallet setup — e.g., a second factor, a business partner, or a device with a different security posture) receives the counterparty's `pairing_secret`. If this pairing secret can be used to initiate device pairing/correspondence as the counterparty's device (per its use in `device.js`/`uri.js` pairing flow), a malicious or compromised cosigner could leverage the leaked secret to pair with or impersonate correspondence toward the peer device, enabling social-engineering or further message-injection attacks against the arbitration counterparty. At minimum, this is disclosure of contact information and pairing credentials to a party with no legitimate need for them, satisfying CWE-200 (Exposure of Sensitive Information).

This is a real information-disclosure defect but its escalation to unauthorized spending/double-spend/AA fund loss is not established by the code reviewed — the primary damage is credential/PII exposure to an unintended, if semi-trusted, party (cosigner). I was not able to fully confirm from the available code what concrete actions a party can take purely from possessing another device's pairing_secret (i.e., whether the hub enforces additional checks before completing pairing), so the severity should be treated as Medium rather than definitively High/Critical.

### Likelihood Explanation
This triggers automatically and unconditionally any time an arbiter contract using cosigner-controlled addresses is accepted and shared (`respond()` → `shareContractToCosigners()`, and `createSharedAddressAndPostUnit()` → `shareContractToCosigners()`). No attacker action is required beyond having any cosigning device on one side of a multi-sig arbiter contract — a normal, permitted participant in the protocol.

### Recommendation
In `shareContractToCosigners()`, clone the contract object and strip fields that are not relevant to cosigners' need to know (e.g., `peer_pairing_code`, `my_pairing_code`, `peer_contact_info`, `my_contact_info`) before calling `device.sendMessageToDevice`, mirroring the scrubbing already done for the peer object in `createAndSend()`. Only send the minimal fields cosigners need (hash, addresses, amount, asset, status, arbiter_address, title/text as needed to render a confirmation dialog).

### Proof of Concept
1. Party A creates an arbiter contract offer with cosigners on their multisig wallet, and Party B (peer) accepts, sending back their `my_pairing_code` (which becomes `objContract.peer_pairing_code` for A) in the `arbiter_contract_response` handler.
2. When A calls `respond()` (status "accepted") or `createSharedAddressAndPostUnit()`, `shareContractToCosigners(hash)` is invoked and sends the full contract row — including B's `peer_pairing_code` — to every device in `getAllMyCosigners(hash)`.
3. Any of A's cosigner devices now possesses B's device pairing secret, without B ever consenting to share it with them.

function shareContractToCosigners(hash) {
	getByHash(hash, function(objContract){
		getAllMyCosigners(hash, function(cosigners) {
			cosigners.forEach(function(device_address) {
				device.sendMessageToDevice(device_address, "arbiter_contract_shared", objContract);
			});
		});
	});
}
