### Title
Restricted-asset AAs and multi-recipient payments become permanently stuck when a single output address is unattested or fails the transfer condition - (File: `validation.js`, `aa_composer.js`)

### Summary
Obyte assets can be configured with `spender_attested: true` (only attested addresses may hold/receive the asset) or a `transfer_condition`/`issue_condition` (an arbitrary spend-condition expression). Both checks are evaluated **atomically across the entire output set of a single payment message**, not per output. If an AA (or any single-authored payment message) sends this restricted asset to several recipients in one message — which is exactly what `aa_composer.js`'s `mergeMessagesAndOutputs` does, merging all per-recipient payment outputs targeting the same asset into one payment message — then a single unattested/blacklisted-by-condition recipient invalidates the *entire* message and thus the *entire* unit, exactly like the USDC pause/blacklist bug blocking the whole `netAtPrice()`/`withdrawAuction()` call.

### Finding Description
`validatePaymentInputsAndOutputs()` collects all output addresses of the message into `arrOutputAddresses` and only after that runs a single all-or-nothing check: [1](#0-0) 
and a single evaluation of `transfer_condition`/`issue_condition` against the whole message: [2](#0-1) 

There is no way to drop just the offending output and still validate/send the rest — `callback(err)` fails the whole payment message, which fails the whole unit.

For AAs, this is materially worse than a plain wallet payment because `handleTrigger`'s `sendUnit()` explicitly **merges independent outputs to different addresses paying in the same asset into a single payment message**: [3](#0-2) 

So an AA doing batch distributions/netting/payouts of a restricted asset (`spender_attested` or with a `transfer_condition`) to N users in one trigger response will have its entire response bounced if even one recipient is not attested or fails the condition — the AA has no mechanism to skip that one output and still pay the others. This is structurally identical to `CrabNetting.sol`'s single blacklisted USDC recipient reverting the whole `netAtPrice()`/`withdrawAuction()` batch.

### Impact Explanation
An attacker (or anyone whose attestation status changes, e.g. an attestor revokes/never grants attestation, or intentionally structures themselves to fail a `transfer_condition`) who is queued as one of many recipients in an AA’s batched payout can force that AA response to bounce every time it tries to pay the whole batch. Because bounce logic in `aa_composer.js` only returns the *base-asset* trigger fee to the trigger address and does not retry with the bad recipient excluded, the AA can become stuck repeatedly failing to distribute the restricted asset to all its legitimate recipients — a fund-freezing condition affecting every other user batched with the attacker, not just the attacker. This matches the report's "unable to exclude one bad recipient" impact and can cause an AA to be functionally stuck for its core distribution logic.

### Likelihood Explanation
Requires the asset in use to have `spender_attested` or `transfer_condition`/`issue_condition` set (an asset-issuer decision) and an AA design that batches multiple recipients' outputs of that asset into a single trigger response — a natural pattern for netting, revenue-sharing, or reward-distribution AAs. Any user able to become a "recipient" in such a batch (e.g. by depositing/registering to be paid out later, analogous to `queueCrabForWithdrawal`) can then get themselves un-attested or intentionally violate the transfer condition to grief the batch. This requires no special privilege beyond being one of the payees.

### Recommendation
When an output fails `spender_attested`/`transfer_condition` checks in an AA-composed payment, the AA layer should exclude that specific output (returning its share to the AA's balance or bouncing only that portion) rather than failing the entire merged payment message, or `mergeMessagesAndOutputs`/`sendUnit` should pre-filter recipients against attestation/condition status before merging, so that one non-compliant recipient cannot block payment to the rest of the batch.

### Proof of Concept
1. Define an asset with `spender_attested: true` (or a `transfer_condition` requiring, e.g., `["in data feed", ...]`), issued/definable via an AA (`asset` message in `messages`), per `validateAssetDefinition` in `validation.js`.
2. Deploy an AA whose trigger handler pays out this asset to multiple addresses in one `payment` message (e.g., a distribution/netting AA), relying on `aa_composer.js`'s `mergeMessagesAndOutputs` to combine multiple recipients' outputs into one message.
3. Have one recipient revoke/never obtain the required attestation (or otherwise fail the `transfer_condition`), while other legitimate recipients remain valid and queued in the same distribution trigger.
4. Trigger the payout; `validatePaymentInputsAndOutputs` in `validation.js` (lines 2630-2658) fails the entire payment message because `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, causing `sendUnit`/`evaluateAA` to `bounce()` the whole response — no legitimate recipient in that batch receives their share, and the AA cannot selectively exclude the bad address on retry.

	// merges payment messages paying in the same asset into a single message,
	// and merges outputs paying in the same asset to the same address into a single output.
	// send-all outputs (amount === undefined) are left as they are and never merged with anything.
	// non-payment messages are left intact.
	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
