This confirms the vulnerability. Unlike `PushHandler`, which scopes its query through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`), `StatusHandler#process` queries `Commit.where(sha: params.sha)` directly with no repository/stack scoping at all.

### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table and writes a GitHub status to every matching row, with no check that the status's authenticating repository owns that commit. Any repository whose webhook is registered with Shipit can push a `security/scan` status for a SHA that happens to collide with a commit tracked by an unrelated victim stack, and if that stack has `blocking_statuses` configured to require `security/scan`, the forged status can flip `Commit#blocked?` and thus `deployable?` for the victim stack.

### Finding Description
The broken invariant is: *a status for context `security/scan` received on repository A's webhook should only affect commits belonging to stacks under repository A* — i.e. `status.commit.stack.repository == webhook.repository`. This does not hold in the code.

`app/models/shipit/webhooks/handlers/handler.rb` provides a `stacks` helper that scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) correctly uses this scope to restrict `find_each` to the authenticated repository's stacks. `StatusHandler`, however, does not use `stacks` at all: [1](#0-0) 

`Commit.where(sha: params.sha)` matches on the raw `sha` column, which is not namespaced by repository or stack — it is a global table across all repos hosted on the same Shipit instance. `Commit#create_status_from_github!` then unconditionally appends the forged status: [2](#0-1) 

`Commit#blocked?` consults `stack.blocking_statuses` and scans reachable commits for any with `blocking?` true: [3](#0-2)  and `deployable?` gates directly on `blocked?`: [4](#0-3) 

**Exploit flow:** An attacker who owns/controls a low-privilege repository (call it Attacker/repo) can send a webhook-signed `status` event for that repository (any repository with a registered webhook secret can send legitimately-signed events for itself — this requires no privilege on the victim). If the attacker crafts or discovers a commit SHA on their own repository (e.g., by copying an empty/base commit, cherry-picking, or via a fork sharing history) that coincides with a SHA already present in the victim stack's `commits` table (SHAs are frequently shared across forks, cherry-picked commits, or shared base branches), the attacker sends `state: success` (or `failure`) with `context: security/scan`. `StatusHandler` finds *every* `Commit` row with that SHA — including the victim's — and attaches the forged status to it, regardless of which repository authenticated the webhook.

Existing guards do not stop this: signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload came from *some* registered repository, not that it is authorized to write to the target commit; `ExplicitParameters` validates the shape of `sha`/`state`/`context`, not ownership; there is no `stacks`-based scoping call inside `StatusHandler#process` as there is in `PushHandler`.

### Impact Explanation
A forged `security/scan` status can flip `Commit#blocked?` for a victim stack whose `blocking_statuses` configuration requires that context, directly altering `deployable?` and, through `schedule_continuous_delivery`/`ContinuousDeliveryJob`, causing an unauthorized deploy to proceed or be blocked. This is a payload from one repository (that authenticated its own webhook) mutating another repository's/stack's commit and status records — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and enabling "an unauthorized deploy, rollback." The blast radius extends to any two stacks/repositories hosted on the same Shipit instance that ever share a commit SHA, and is repeatable per shared SHA per webhook send.

### Likelihood Explanation
Preconditions: the attacker needs a webhook registered for some repository they control on the Shipit instance (a normal, expected Shipit onboarding step, not a privileged action), the victim stack must have `blocking_statuses` configured with a context the attacker chooses to forge, and a shared commit SHA must exist between attacker and victim repos (achievable via forks, cherry-picks, shared upstream history, or simply targeting a commit the attacker can also reproduce, e.g. an empty commit with identical tree/parent/author/committer/timestamps — SHA1 collision-by-construction, not brute force). Attacker cost is low: one HTTP POST per attempt, fully automatable, and repeatable against any stack sharing a SHA.

### Recommendation
Scope `StatusHandler#process` through `stacks`/`repository_name` the same way `PushHandler` does: only update commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of the bare `Commit.where(sha: params.sha)`.

test "status from unrelated repository must not affect victim stack's blocked? state" do

    'repository' => { 'full_name' => attacker_repo.full_name },

  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
