## Analysis

The reported bug class is a **value used for a security-relevant decision (gamma) diverging from the value actually acted upon (price/quote)**, allowing an attacker to exploit the gap. The engine analog with the same shape — *a value used to select/authenticate diverging from the value the handler actually acts on* — is in the webhook signature pipeline.

### Title
Webhook signature verification keys off `repository.owner.login`, but every event handler trusts `repository.full_name` for the target repo - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify the HMAC against using `repository_owner`, taken straight out of the untrusted, attacker-suppliable JSON body: [1](#0-0) , [2](#0-1) . Every downstream event handler, however, resolves the actual target repository/stack from a *different* field of the same payload, `repository.full_name`: [3](#0-2) .

### Finding Description
`Shipit.github(organization: repository_owner)` picks a per-organization `GithubApp` config, and `verify_webhook_signature` deliberately no-ops when that organization's `webhook_secret` is blank: [4](#0-3) . `webhook_secret` is explicitly documented and shipped as **optional** per organization, including in multi-org setups: [5](#0-4) , and appears as `nil` in real config templates: [6](#0-5) .

Because `repository_owner` is read from the payload's `repository.owner.login`/`organization.login` and `repository_name` used by every handler is read from the independent `repository.full_name` field, an attacker forging a raw POST to `/webhooks` (no signature, no session, no API token required) can set:
- `repository.owner.login` (or `organization.login`) = an organization configured in Shipit **without** a `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally, bypassing authentication entirely.
- `repository.full_name` = `"victim-org/victim-repo"`, an entirely different, secret-protected organization/repository that Shipit tracks.

`Handler#stacks` (used by every handler, e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) resolves the target purely from `repository.full_name` [3](#0-2)  — it never re-checks that this repository belongs to the organization whose secret gated the request. The binding broken is: *organization that authenticated (`repository.owner.login`, gated by that org's `webhook_secret`) ≠ repository that is written (`repository.full_name`, used unconditionally by handlers)*.

This lets an unprivileged, unauthenticated attacker forge `push`, `status`, `check_suite`, `pull_request`, and `membership` events for any repository/stack Shipit manages, as long as at least one configured organization has no `webhook_secret` (an officially supported, documented configuration).

### Impact Explanation
Forged `push` events queue `GithubSyncJob`, and forged `status`/`check_suite` events can flip CI status on arbitrary commits for a targeted stack — directly influencing whether the merge queue (`ProcessMergeRequestsJob` → `MergeRequest#merge!`) considers a PR mergeable, i.e. it can push a stack toward an **unauthorized merge**, satisfying the Critical-impact bar ("cross-repository writes...or an unauthorized deploy, rollback or merge"). It also lets an attacker create arbitrary `Team`/`User`/`Membership` records via a forged `membership` event, since `MembershipHandler` similarly trusts payload data once the (misdirected) signature gate passes.

### Likelihood Explanation
Requires only that a Shipit deployment has ≥2 configured GitHub organizations and at least one without a `webhook_secret` — a state the project's own setup docs treat as normal/optional. No credentials, sessions, tokens, or GitHub write access are needed; the attacker only needs to know the endpoint (`/webhooks`, always public per `docs/setup.md`) and the name of the secret-less organization (discoverable via the multi-org secrets template pattern or by trial).

### Recommendation
Do not let payload-supplied fields determine which secret authenticates the request while a *different* payload field determines the target of the action. Concretely: after selecting `repository_owner` and verifying the signature, re-derive `repository_owner`/org from the same field the handlers use (`repository.full_name`'s owner segment), and reject if they differ; or better, verify the payload against the `webhook_secret` of the organization that owns `repository.full_name`, not `repository.owner.login`/`organization.login` read independently.

### Proof of Concept
1. Configure Shipit with two orgs in `config/secrets.yml`: `OrgA` (has `webhook_secret`, owns tracked `victim-repo`) and `OrgB` (no `webhook_secret`, per docs "optional").
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "OrgB" },
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgB")`; `verify_webhook_signature` returns `true` immediately because `OrgB`'s `webhook_secret` is nil — no `X-Hub-Signature` header is even required.
4. `PushHandler` (via `Handler#stacks`) resolves `Repository.from_github_repo_name("OrgA/victim-repo")` and processes the forged push against the real, secret-protected `OrgA` stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
