## Finding confirmed

The unique index is `add_index :commits, %i(sha stack_id), unique: true` [1](#0-0)  — uniqueness is enforced per `(sha, stack_id)` pair, **not** globally on `sha`. This means the same commit sha can legitimately exist as separate `Commit` rows belonging to different, unrelated stacks (e.g. two Shipit stacks tracking the same public repo, a fork with shared history, or any stack that happened to sync a commit with that sha).

### Title
`StatusHandler#process` writes a forged CI status to any stack sharing a commit sha, bypassing repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Handler` provides a `stacks` helper that scopes operations to the stack(s) belonging to the repository named in the verified webhook payload [2](#0-1) , but `StatusHandler#process` never uses it. Instead it looks up commits globally by `sha` across **all** stacks and calls `commit.create_status_from_github!(params)` on each, which unconditionally passes `stack_id` (the commit's own, pre-existing stack id) into `Status.replicate_from_github!` [3](#0-2) [4](#0-3) .

### Finding Description
Binding claimed: `stack_id` used in `Status.replicate_from_github!` == the stack whose repository is named in the verified webhook payload (`payload.dig('repository','full_name')`).

Actual code path for the `status` event:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [5](#0-4) 

This query is **not** scoped by `repository_name`/`stacks` at all — every other handler in the codebase (e.g. `PullRequest::OpenedHandler`, `ClosedHandler`) explicitly filters through `stacks` derived from `Repository.from_github_repo_name(repository_name)` [2](#0-1) , but `StatusHandler` omits this entirely. `create_status_from_github!` then uses `self.stack_id` (the id already stored on whatever `Commit` row matched the sha) with no comparison to `self.stack.repository` or to the webhook's `repository.full_name`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

Because the unique index on `commits` is `(sha, stack_id)` rather than `sha` alone [1](#0-0) , the same `sha` can exist as distinct rows for multiple, unrelated stacks (this happens whenever two Shipit stacks track repositories that share commit history — forks, mirrors, or repos that both received the same commit). `WebhooksController#verify_signature` only checks that the HMAC matches the secret configured for `repository_owner` in the payload [6](#0-5)  — it validates *who sent* the webhook, not that the *content* (sha) belongs to that sender's repository. Once signature verification passes for the attacker's own repository/org, `StatusHandler` will happily write a `Status` (`success`, `failure`, etc.) onto **any** stack whose commits table has a row with that sha, including stacks belonging to entirely different organizations. Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate the sender and the shape of the payload but do nothing to bind the `sha` to the sender's own repository.

### Impact Explanation
An attacker who controls a Shipit-registered repository (their own fork/org) can send a `status` webhook for a sha that also exists in another, uninvolved stack's commit history, and Shipit will create a `Status` row against that uninvolved stack for that commit. This can mark a victim stack's commit as `success`, satisfying `deployable?`/CI gating and enabling an unauthorized deploy, or as `failure`, blocking a legitimate release — a payload from one repository mutating another's stack/commit state. This matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the target stack's commits table must contain a `Commit` row with the same `sha` as one the attacker controls/knows (realistic for forked/mirrored public repos, which is a supported and common Shipit configuration), and the attacker's own repository/org must already be configured as a Shipit stack (so that `verify_signature`'s per-organization secret lookup succeeds). No Shipit session, API token or GitHub App secret is required beyond what the attacker already has for their own registered repo. This is repeatable for every shared sha and against every stack that happens to share history with the attacker's repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through `stacks` (as other handlers do) instead of a bare `Commit.where(sha:)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter by `stack_id: stacks.map(&:id)`. Additionally/alternatively, `Commit#create_status_from_github!` should assert `self.stack.repository.full_name == payload's repository full_name` before delegating to `Status.replicate_from_github!`.

### Proof of Concept
```ruby
test "status webhook cannot write a status to a stack from an unrelated repository sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)          # e.g. github repo "victim-org/app"
  attacker_stack = shipit_stacks(:cyclimse)       # attacker-controlled registered repo, e.g. "attacker/app"

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: payload, as: :json
  end
  # Currently FAILS: victim_commit.statuses.count increases by 1, proving the
  # forged status from attacker_stack's webhook was written onto victim_stack's commit.
end
```
