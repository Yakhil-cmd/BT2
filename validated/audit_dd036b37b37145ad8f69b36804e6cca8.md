## Analog Found

### Title
Webhook signature verification is keyed to the attacker-controlled `repository.owner.login` field while event processing trusts the attacker-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App config (and therefore which `webhook_secret`) to verify the HMAC signature against using a value read straight out of the unauthenticated JSON body, not from anything cryptographically bound to the request. If that organization has no `webhook_secret` configured, signature verification is skipped entirely, yet the same unauthenticated payload is then dispatched to handlers (push, status, check_suite, membership, etc.) that act on a *different* payload field — `repository.full_name` — to decide which `Stack`/`Repository`/`Team` to mutate.

### Finding Description
`verify_signature` picks the GitHub App/organization purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a field inside the raw, unverified `request.raw_post` at the time it's read (the signature hasn't been validated yet). This value is used only to look up which `GitHubApp` instance (and thus which `webhook_secret`) will be used to validate the signature: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset — a supported, documented configuration state (`webhook_secret: # nil` appears as a valid example value in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`).

This means: in any multi-org Shipit deployment (`Shipit.github(organization:)` supports a per-org config map, as shown in `docs/setup.md`), if *any one* configured organization is missing a `webhook_secret`, an attacker can craft a payload with `repository.owner.login` set to that unsecured organization to sail through `verify_signature` unauthenticated — while setting `repository.full_name` (and other event fields like `after`, `sha`, `state`) to reference an entirely different, unrelated repository/stack. Downstream handlers such as `PushHandler` act on `params.after`/branch to trigger `stack.sync_github(...)`, and other handlers create/delete `Team`/`Membership`/`Status` records, all keyed off payload fields that were never covered by (or matched against) the organization used for signature verification: [4](#0-3) [5](#0-4) 

This is exactly the binding the rules call out: *"an organization that authenticated versus the repository that is written"* — the org whose (absent) secret gated the check is not the repository/stack the handler subsequently writes to.

### Impact Explanation
An unauthenticated network attacker who can reach `/webhooks` can forge GitHub events (`push`, `status`, `check_suite`, `membership`) for repositories/stacks they do not own, as long as one organization in the Shipit install lacks a webhook secret. This can trigger `GithubSyncJob` to ingest attacker-chosen commit SHAs into a tracked stack's history, manipulate `Status`/`CheckRun` state used for merge-queue gating, or create/delete `Team`/`Membership` records — all without any GitHub credential. Depending on downstream trust in synced commit state for deploy/merge decisions, this can lead to an unauthorized deploy or merge decision being made on forged data, which maps to the "unauthorized deploy, rollback or merge" High/Critical impact bucket.

### Likelihood Explanation
Requires only that one configured organization omit `webhook_secret` — a state the project's own example configs and docs present as valid/normal (`webhook_secret: # nil`). No credentials, sessions, or GitHub App keys are needed; only network reachability to the public webhooks endpoint, which is the documented, expected exposure of this controller.

### Recommendation
Do not let an attacker-controlled field decide the trust boundary for signature verification. Either require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and/or after verifying the signature, re-validate that `repository.full_name` actually belongs to the same `repository_owner`/organization that was used to select the verifying secret before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with two GitHub orgs configured (`OrgOne` with a `webhook_secret`, `OrgTwo` with `webhook_secret: nil`), tracking a stack under `OrgOne/private-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/private-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) signature header.
4. `PushHandler#process` runs against `repository.full_name` = `OrgOne/private-repo`, enqueuing `GithubSyncJob` for that stack with the attacker-supplied `after` SHA — a fully forged, unauthenticated event against a repository owned by a *different* org than the one whose (missing) secret let the request through.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
