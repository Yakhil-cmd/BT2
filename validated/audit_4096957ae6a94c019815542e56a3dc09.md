### Title
Cross-repository status forgery flips `Stack#ci_enabled?` cache for arbitrary victim stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with a global, repository-unscoped `Commit.where(sha: params.sha)` query, unlike sibling handlers such as `CheckSuiteHandler` which scope through the `stacks` helper before touching commits. Any GitHub user who owns a repository that shares commit history with a victim's tracked repository (most simply, a public fork) can emit a genuinely GitHub-signed `status` webhook for their own repo that references a SHA also present in the victim stack's `commits` table, causing Shipit to create a `Status` on the victim's commit and flip `Rails.cache` at `Stack#ci_enabled_cache_key` for a stack the attacker never authenticated against.

### Finding Description
The claimed binding is: `actor authorized to call stack.enable_ci!` == `actor whose webhook signature verifies against stack.repository`'s own GitHub App/organization installation.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only checks that the payload's signature is valid for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-controlled JSON body (`app/controllers/shipit/webhooks_controller.rb:59-62`). This proves the payload came from GitHub for *some* org the attacker controls — it says nothing about which Shipit `Stack` the payload is allowed to affect. [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a table-wide lookup by `sha` with **no filter on `repository`, `full_name`, or stack** at all. [3](#0-2) 
- Contrast with `CheckSuiteHandler#process`, which scopes to `stacks.where(branch: …)` (repository-bound) before touching any commit — showing the engine's own convention is to scope by repository, which `StatusHandler` fails to do. [4](#0-3) 
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` creates a `Status` row bound to `commit.stack`, not to the requesting webhook's repository. [5](#0-4) 
- `Status.after_create :enable_ci_on_stack` unconditionally calls `commit.stack.enable_ci!`. [6](#0-5) 
- `Stack#enable_ci!` writes `true` to `Rails.cache` at `ci_enabled_cache_key` for that stack, with no re-check of who requested it. [7](#0-6) [8](#0-7) 

Exploit flow: attacker forks (or otherwise shares ancestor history with) the victim's public repository. Ancestor commits are content-addressed (git SHA-1 over tree+parents+metadata) and identical across the fork and upstream, so any commit synced into the victim's Shipit `commits` table before the fork diverged also exists, with the same SHA, in the attacker's own repository. The attacker's repository has (or the attacker installs) the same GitHub App/organization webhook credentials trusted by Shipit for their own account — a completely legitimate, GitHub-issued signature for the attacker's own repo. The attacker sends (or triggers GitHub to send, e.g. via a CI status update on their fork) a `status` event referencing that shared SHA. `verify_signature` passes because it validates against the attacker's own org. `StatusHandler#process` then matches the *victim's* `Commit` row (same `sha`, different `stack_id`) via the unscoped `Commit.where(sha:)` query, creates a `Status` on it, and fires `enable_ci!` on the victim's `Stack`, mutating `Rails.cache` for a party that never engaged the victim's own repository/app installation.

No existing guard closes this: `verify_signature` authenticates the org in the payload, not the stack being mutated; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
The write is a genuine cross-repository mutation of another tenant's Shipit state (`Stack#ci_enabled?` cache) triggered purely by a payload the victim's repository never sent — this matches the explicitly listed Critical category "a payload for one repository mutating another's stack." Beyond the cache flip, the same unscoped lookup also creates a persisted `Status` record on the victim's commit and fires the `commit_status`/`deployable_status` hooks and `schedule_continuous_delivery` for the victim stack (via `Commit#add_status`), meaning a forged status from an unrelated repo can influence the victim's deploy/merge pipeline logic (e.g., marking a commit's simple_state as success), not merely a cache boolean. This is repeatable against any victim stack whose commit history intersects (via fork or shared upstream) with a repository the attacker controls, and scales to many stacks since `Commit.where(sha:)` returns all matches across the whole install.

### Likelihood Explanation
Preconditions are attacker-cheap and realistic: own/control any GitHub repository with the Shipit GitHub App installed (a normal, unprivileged action many public-repo forks already satisfy or can trivially obtain), and identify a SHA shared with a tracked victim stack (any commit predating the fork point, which is common and enumerable via `git log`/GitHub API on the public fork). No Shipit secrets, sessions, or `Shipit.github_teams` membership are required — the signature the attacker relies on is a legitimate one for their own org. The main constraint is finding a shared SHA already present in the victim's `commits` table, which is straightforward for any forked or vendored repository and requires zero cryptographic collision-finding.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits purely by `sha`) to the repository asserted in the webhook payload, e.g. resolve the `Repository`/`Stack` from `params.repository.full_name` first (as `stacks`/`from_param!` do elsewhere) and restrict `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` before calling `create_status_from_github!`, mirroring the pattern already used in `CheckSuiteHandler`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (minitest, no live GitHub)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status for an unrelated repository must not enable CI on a victim stack" do
          victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
          victim_commit = shipit_commits(:first)
          victim_commit.update!(stack_id: victim_stack.id)

          # Precondition: attacker's repo shares this SHA (e.g. via fork), simulated directly here.
          shared_sha = victim_commit.sha

          # Binding under test, stated as an explicit equality:
          # actor allowed to call victim_stack.enable_ci! == actor authenticated by victim_stack.repository's own webhook secret
          assert_nil Rails.cache.read(victim_stack.send(:ci_enabled_cache_key)),
            "precondition: victim stack CI flag must start unset"

          forged_payload = ExplicitParameters::Parameters.new(
            sha: shared_sha,
            state: 'success',
            description: 'attacker-controlled',
            context: 'attacker-ci',
            branches: []
          )
          # Payload is "verified" only against the ATTACKER's own org/app secret upstream
          # (WebhooksController#verify_signature never checks it against victim_stack.repository).
          StatusHandler.new.process_with_params(forged_payload) rescue StatusHandler.new.process

          assert Rails.cache.read(victim_stack.send(:ci_enabled_cache_key)),
            "VULNERABLE: victim stack's ci_enabled cache flipped by a status the victim repository never authenticated"
        end
      end
    end
  end
end
```
Both sides of the equality diverge after the call: the actor who satisfied `verify_signature` was authenticated only for their own organization/repository, yet `victim_stack.ci_enabled_cache_key` (and a persisted `Status` on `victim_commit`) were mutated — confirming the binding is broken at `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.
