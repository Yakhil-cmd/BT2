### Title
CCMenu API token created without stack scope grants read access to build status of every stack, not just the requested one - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The CoreRouter report's root cause is a binding mismatch: the value the contract *trusts* (`expectedUnderlying`, computed before the operation) is never checked against the value the operation *actually* produces (`actualUnderlyingReceived`), so payouts drift from reality. The direct analog in shipit-engine is an authorization binding mismatch in the CCMenu token flow: the `ApiClient` a user is issued is intended to authorize read access to **one specific stack** (the one whose URL they requested), but the token that is actually minted, and the controller that consumes it, never encode or check that binding — the token ends up authorizing read access to **every stack** in the installation.

### Finding Description
`CCMenuUrlController#client` creates (or reuses) an `ApiClient` with only a coarse permission string, never binding it to the requested stack: [1](#0-0) 

Compare this to `Shipit::ApiClient`, which explicitly supports a `stack` association meant to scope a client to one stack: [2](#0-1) 

and to `Shipit::Api::BaseController`, which is the normal enforcement point: it computes the client's allowed stacks from `current_api_client.stack_id` and scopes lookups through that collection: [3](#0-2) 

`Api::CCMenuController` (the endpoint the minted token is actually used against) does not use this scoped `stack` method at all — it overrides it with an unscoped lookup keyed purely off the request's `stack_id` param, and swaps in a bespoke `authenticate_api_client` that trusts a `token` query parameter directly: [4](#0-3) 

Permission enforcement is done only via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`, a check that only inspects the *name* of the permission ("read:stack") against the client's `permissions` array — it never looks at `stack_id` at all: [5](#0-4) 

So the binding that should hold is:
`stack the token was issued for == stack the token can read`

Before the flow: a user viewing Stack A's settings clicks "Get CCMenu URL"; the intent, visible in the URL itself (`stack_id: stack.to_param`), is that the resulting token lets a CI-status tool read Stack A's build status only.

After the flow: the created `ApiClient` has `stack_id = nil` (never set) and permission `read:stack`. Because `Api::CCMenuController#stack` bypasses the `stacks`/`stack` scoping from `BaseController` entirely and just does `Stack.from_param!(params[:stack_id])`, the token is accepted for **any** `stack_id` supplied in the request, not just the one it was minted for. Even if the client model were later fixed to set `stack_id`, this specific controller still wouldn't enforce it, since it never consults `current_api_client.stack_id`.

The test suite confirms the token is created with default (unscoped) permissions and no stack binding is asserted anywhere: [6](#0-5) 

### Impact Explanation
This satisfies the "High" bar of "unauthenticated read of stack state" via a scope-authorization escalation: possession of a single CCMenu URL/token (which is commonly embedded in third-party CI dashboard tools, CCTray clients, browser history, logs, or shared configuration — i.e., a lower-trust artifact than a full session or admin API key) grants read access to build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of **every stack** hosted by that Shipit instance, including stacks the token holder was never meant to see (e.g., other teams'/other repositories' private deploy pipelines). This is a direct escalation beyond the authorization scope the token was created for (`Shipit.github_teams`-gated web access, per-repository visibility), reachable by any authenticated Shipit user who requests one CCMenu URL and then simply changes the `stack_id` in the request while reusing their own token — no repository write access, GitHub App key, or `api_clients_secret` needed.

### Likelihood Explanation
High. No special privileges are required beyond being a logged-in Shipit user able to view one stack's settings page (`CCMenuUrlController#fetch` only requires session auth, not per-stack write access). Once a `read:stack`-permissioned token is obtained, exploitation is a single unauthenticated-parameter-substitution API call (`GET /api/stacks/:other_stack_id/ccmenu.xml?token=...`), matching the CoreRouter analog's "no verification of the actual bound value" pattern exactly.

### Recommendation
- When creating the CCMenu `ApiClient`, bind it to the requested stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack)`.
- In `Api::CCMenuController`, remove the custom unscoped `stack` override and use the inherited, scoped `stack`/`stacks` method from `BaseController` so that `current_api_client.stack_id` (when present) is enforced against `params[:stack_id]`.
- Ensure `ApiClient#check_permissions!` (or a new check) validates the client's `stack_id` (if set) matches the stack being accessed, rather than relying purely on the string-based permission name.

### Proof of Concept
1. As User A (logged in, member of a permitted GitHub team), visit Stack A's settings and click "Get CCMenu URL" → `CCMenuUrlController#fetch` returns a URL like `https://shipit.example.com/api/stacks/org/repo/1/env/ccmenu.xml?token=T`, backed by an `ApiClient` with `permissions=["read:stack"]` and no `stack_id`.
2. Take token `T` and issue `GET /api/stacks/other-org/other-repo/2/env/ccmenu.xml?token=T` for Stack B, which the user was never granted a URL for.
3. `Api::CCMenuController#authenticate_api_client` authenticates via `ApiClient.authenticate(params[:token])`, succeeds; `require_permission :read, :stack` passes because the client has the `read:stack` string permission; `stack` resolves `Stack.from_param!(params[:stack_id])` for Stack B without checking any relationship between the token and Stack B.
4. Response 200 with Stack B's build/deploy status is returned, confirming cross-stack read access via a token that was only ever intended, and displayed to the user, as scoped to Stack A.
