### Title
Cross-organization Team-membership hijack via `github_id`-only lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` finds a `Team` solely by `params.team.id` and, on the "found" path, never re-validates that the found record's `organization` matches `params.organization.login` before calling `team.add_member(member)`. In a multi-organization Shipit deployment, an attacker who controls one legitimately-configured tenant organization (and therefore knows *that* organization's `webhook_secret`) can sign a `membership` webhook claiming their own organization while referencing another organization's already-existing `Team.github_id`, causing their own GitHub account to be added as a member of a `Team` record that belongs to a different, `Shipit.github_teams`-authorized organization.

### Finding Description
The broken binding: `team.organization == params.organization.login` is required before `add_member` runs, but it is never checked on the "found" branch.

Code path:
1. `WebhooksController#verify_signature` resolves the app used to check the HMAC signature via `repository_owner`, which for a `membership` event (no `repository` key in the payload) falls back to `params.dig('organization','login')` [2](#0-1) . This means the signature is validated against `Shipit.github(organization: attacker-org).verify_webhook_signature`, i.e., against the attacker's own tenant's `webhook_secret` — not the victim organization's.
2. `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }` [3](#0-2) . The block that sets `organization` and `github_team=` (name/slug/api_url) only executes when a **new** record is created. If a `Team` row with that `github_id` already exists (e.g., created earlier for `victim-org` via `Shipit.github_teams` sync, `rake teams:fetch`, or a prior legitimate membership webhook), `find_or_create_by!` simply returns that existing row untouched — `organization` is never re-checked against `params.organization.login`.
3. `process` then unconditionally calls `team.add_member(member)` on the returned (possibly victim-owned) `Team`, appending the attacker's `User` to `team.members` [4](#0-3) .
4. That same `Team` row is exactly what backs Shipit's own authorization: `Shipit.github_teams` resolves configured team handles into `Team` records [5](#0-4) , and `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , gating access via `force_github_authentication` [7](#0-6) .
5. Schema confirms there is no `github_id`-unique or `(organization, github_id)`-unique constraint — only `(organization, slug)` is unique [1](#0-0)  — so nothing in the DB layer prevents this cross-org collision either.

Attacker's request: attacker logs into Shipit via the normal GitHub OAuth flow as themselves (no secret required, becomes a `Shipit::User` with `login: 'attacker'`), then POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s `webhook_secret`, and body `{action: 'added', team: {id: <victim_team_github_id>, name:, slug:, url:}, organization: {login: 'attacker-org'}, member: {login: 'attacker'}}`.

Existing guards fail here because:
- `verify_signature` only proves the payload was signed by *some* configured org's key; it never checks that the `organization.login` in the payload corresponds to the org whose `Team` is being touched.
- `find_or_create_by!`'s block-only-on-create semantics mean the `organization` binding is only enforced at creation time, not on subsequent lookups.
- `ExplicitParameters` schema only validates types/presence, not cross-field consistency (`team.id` vs. `organization.login`).

### Impact Explanation
Escalation into `Shipit.github_teams` authorization: an attacker with no legitimate relationship to `victim-org` can grant themselves membership in a `Team` record that Shipit trusts for access control, flipping `User#authorized?` to `true` and passing `force_github_authentication`. This is repeatable against any `Team` whose `github_id` the attacker can learn (team IDs are visible via GitHub UI/API responses, cached webhooks, or other disclosure vectors) and works across tenant boundaries in any multi-organization Shipit deployment. Matches the "High" impact category: escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires: (a) Shipit configured for multiple GitHub organizations (the multi-app config shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), (b) attacker controls one of those configured organizations (or a GitHub App installed there) well enough to know/derive its `webhook_secret` and send webhooks from it, (c) a `Team` row for the victim org/team already exists with a `github_id` the attacker can supply. Given those preconditions (explicitly granted by the question), the attacker's cost is a single crafted, self-signed HTTP POST — cheap and repeatable for every target team whose `github_id` is known.

### Recommendation
In `find_or_create_team!`, re-validate that `team.organization == params.organization.login` on both the "found" and "created" paths, e.g., raise/reject if a `Team` matching `github_id` exists but its `organization` differs from `params.organization.login`, or scope the lookup by `(github_id, organization)` and enforce a DB-level unique index on that pair.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/membership_handler_test.rb`):
```ruby
test "membership event cannot hijack a team belonging to another organization" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'devs', name: 'Devs', api_url: 'https://example.com')
  attacker_payload = {
    action: 'added',
    team: { id: 999, name: 'Devs', slug: 'devs', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'
  post :create, body: attacker_payload.to_json, as: :json

  victim_team.reload
  attacker_user = Shipit::User.find_by(login: 'attacker')
  # Assert the binding held: team.organization ('victim-org') != params.organization.login ('attacker-org')
  refute_equal victim_team.organization, 'attacker-org'
  # Vulnerable behavior (should NOT happen after fix):
  refute victim_team.members.include?(attacker_user), "attacker must not gain membership in victim-org's team"
  refute Shipit.github_teams.include?(victim_team) && attacker_user&.authorized?
end
```
