### Title
Bad-debt wipeout clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing claims, so wiped suppliers keep a phantom claim paid by later depositors - (File: contracts/pool/src/interest.rs)

### Summary
The external report is a parsing underflow: a routine trusted a bounded quantity to be non-negative/nonzero and produced a residual where none should exist. The in-scope analog is in `apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:73-89`): when socialized bad debt meets or exceeds the total supplied value, the correct result is a zero index (every supplier claim is worthless), but the code floors the new index at `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`), i.e. it *raises* the index from 0 back to a positive value. Every scaled supply share in the market keeps a positive `unscale_supply_floor` claim that is no longer backed by anything — a manufactured residual value exactly like the one-byte under-read.

### Finding Description
`apply_bad_debt_to_supply_index` computes `reduction_factor = (total_supplied_value - capped_bad_debt) / total_supplied_value`, multiplies the supply index by it, then applies `new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` (`contracts/pool/src/interest.rs:80-88`). When `bad_debt >= total_supplied_value`, `reduction_factor` is 0, the mathematically correct index is 0, but the clamp restores it to `RAY/1000`. No share balances are touched, so all pre-wipeout `scaled_amount` supply positions retain `scaled * RAY/1000` of claim value.

This path is reachable by an unprivileged caller through `controller.liquidate` / `clean_bad_debt`, which issue `PoolSeizeEntry` with `side = AccountPositionType::Borrow` to the pool; `seize::apply` calls `interest::apply_bad_debt_to_supply_index` with `unscale_borrow_ceil_ray(position)` (`contracts/pool/src/ops/seize.rs:24-28`).

The only thing masking the payout is the cash check in `withdraw` (`require_reserves`). The repo's own test proves the drain end-to-end on a raw cache: after the clamp, `stranded = unscale_supply_floor(old_scaled) > 0`; a fresh supplier deposits `stranded`, and `resolve_withdrawal(i128::MAX, old_scaled)` pays `gross == fresh_cash` to the wiped position, leaving `cash < fresh_claim` (`contracts/pool/tests/interest.rs:372-427`).

### Impact Explanation
Theft of user funds / protocol insolvency. Once a market's debt book is fully socialized (bad debt ≥ total supplied value, e.g. after a severe collateral crash leaves all borrows unbacked), every wiped-out supplier retains a phantom claim of `scaled_amount * RAY/1000`. The next depositors into that market provide the cash; the wiped holders call `controller.withdraw` (or an attacker who held a wiped position does) and receive real tokens up to their stranded claim. The pool's cash falls below what it owes the fresh suppliers — funds are directly transferred from later depositors to holders of zero-value positions. The aggregate phantom liability is `total_supplied * RAY/1000` scaled, i.e. roughly 0.1% of the pre-wipeout supply book, claimable repeatedly as new cash arrives.

### Likelihood Explanation
Medium. The trigger requires a market to reach full socialization: bad debt at or above the entire supplied value. That is an extreme but legitimate market state — it needs no privileged action, no oracle manipulation beyond honest prices, and no leaked keys; any unprivileged account can drive `liquidate`/`clean_bad_debt` once positions are insolvent. After the wipeout, the theft needs only one fresh deposit into the (still listed) market, which is plausible because the pool keeps operating and the supply index floor makes the market look non-degenerate. The profit cap (~0.1% of wiped supply per cycle) limits per-event severity, consistent with Medium.

### Recommendation
When `remaining` computed at `contracts/pool/src/interest.rs:81` is zero, the index must not be re-inflated. Either:

- Set `supply_index` to the floor **and** treat all existing scaled supply as void: record a wipeout flag on the market so `resolve_withdrawal`/claim paths return 0 for positions created before the wipeout, or
- Track a wipeout epoch/generation on the market; positions stamped with an older epoch unscale to zero, and `calculate_scaled_supply`/`require_reserves` account only for post-epoch shares.

At minimum, document the invariant the code currently relies on: the clamp is only safe if nothing can ever fund cash again after full socialization — which `supply`, `recapitalize`, and incidental token transfers all contradict.

### Proof of Concept
1. Market M has suppliers with scaled shares `S` and borrowers; collateral crashes so liquidation leaves unpaid debt `D ≥ unscale_supply(S)`.
2. Anyone calls `controller.clean_bad_debt`/`liquidate`; pool `seize` (Borrow side) calls `apply_bad_debt_to_supply_index`, `reduction_factor = 0`, but `supply_index` becomes `SUPPLY_INDEX_FLOOR_RAW` instead of 0. `S` is untouched.
3. Victim calls `controller.supply` depositing `X` tokens into market M (`mint_supply` + `credit_cash(X)`).
4. Holder of wiped shares `S` calls `controller.withdraw(amount = 0)`; `resolve_withdrawal` unscales `S` at index `RAY/1000` to `stranded > 0`, `require_reserves` passes because the victim's `X` funded cash, and `transfer_out` pays `min(stranded, X)` of the victim's tokens to the wiped holder.
5. Victim's own claim now exceeds remaining pool cash — loss is realized.

This mirrors exactly the sequence pinned by `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` in `contracts/pool/tests/interest.rs:372-427`, executed through the production `seize` → `withdraw` path rather than raw cache seeding.

Caveat: I verified the clamp logic, the seize call chain, and the demonstrating test, but did not fully trace the controller-side `clean_bad_debt`/`withdraw` entrypoints and `require_reserves` implementation, so the exact gate set on step 4 is inferred from the test and `contracts/pool/src/ops/withdraw.rs` structure rather than read end-to-end.
