## #Vulnerability found for this question.

### Title
`StatusHandler#process` writes GitHub statuses to any `Shipit::Commit` sharing a SHA, regardless of which repository's webhook authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with a bare, repository-unscoped `Commit.where(sha: params.sha)` and applies the incoming GitHub `status` payload to every match. Because the `commits` table is only unique per `(stack_id, sha)` — not globally unique per SHA — any stack whose commit history happens to contain the same SHA as the attacker's repository (fork relationship, shared upstream history, cherry-pick, or coincidental content match) receives the attacker's status write, even though the attacker never authenticated for that stack's repository.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == { commits belonging to the repository that authenticated this webhook }`, but the actual query is `Commit.where(sha: params.sha) == { every commit row in the entire database with that SHA, across all stacks/repositories }`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-supplied payload (`params.dig('repository','owner','login')`, line 59-62). This only proves the payload was signed by the GitHub App configured for that organization; it does **not** bind the payload to a specific `Shipit::Commit` or `Shipit::Stack`.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
There is no filter on `repository`, `stack_id`, or `github_repo_name` — only the bare `sha`.
3. The `commits` table's uniqueness constraint is per `(stack_id, sha)` (migration `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique by `sha`. This means multiple `Shipit::Commit` rows belonging to different stacks/repositories can legitimately share the same SHA — this is the normal, expected case for forked repositories, shared monorepo history, or any two stacks that track overlapping git history.
4. `commit.create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, which mutates that commit's status state directly using the attacker-supplied `state`/`context` regardless of which repository actually sent the webhook.

Exploit flow: An attacker who owns/controls a repository (or fork) that shares a commit SHA with a victim's tracked stack (e.g., they forked the victim's public repo, or the victim's repo was itself forked from a common upstream) sends a real, validly-signed `status` webhook from their own repository with `context: shipit/checks`, `state: failure`, and `sha` equal to the shared commit. `verify_signature` passes because the signature is valid for the attacker's own organization/App installation. `StatusHandler#process` then finds and mutates the victim stack's `Commit` row with that same SHA, flipping the `shipit/checks` status to `failure` and altering that commit's deployability, even though the attacker's webhook never touched the victim's repository or stack.

Existing guards do not prevent this: `verify_signature` scopes only to "is this payload authentically signed for the claimed org," not "does this payload's repository match the commit/stack being written to." No handler re-validates `params.repository.full_name` (or equivalent) against `commit.stack.github_repo_name` before writing.

### Impact Explanation
An unprivileged attacker who owns any repository tracked by (or sharing commit history with) a Shipit instance can flip the `shipit/checks` (or any) status on a completely different, victim-owned stack's commit — turning a required check to `failure` (blocking merges/deploys) or forging it to `success` (bypassing a required check and enabling an unauthorized deploy/merge). This is a payload from one repository mutating another repository's stack/commit state, matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The attack is repeatable against any commit SHA collision and requires no privileges beyond controlling a repository/fork with shared history.

### Likelihood Explanation
Preconditions: the attacker needs a repository where they can trigger a genuinely GitHub-signed `status` webhook (trivially achievable by owning any repo/fork with the Shipit GitHub App/webhook installed, or via any GitHub App installation the attacker controls that shares the app-wide/org-wide webhook secret), and a commit SHA that also exists in a victim's Shipit-tracked stack. SHA collisions across stacks are common and not adversarial-only (forks, mirrors, shared upstream branches, cherry-picks with identical trees) — this significantly raises feasibility over a random hash-collision requirement. No Shipit session, API token, or team membership is needed. The attack is trivially repeatable (repeat the webhook with different SHAs/states).

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers, e.g. check-run handler) to the repository that authenticated the webhook, e.g. filter through `Stack` by matching `params.repository.full_name` (or `repository_owner`) against `stack.github_repo_name`/`repository_id`, rather than a bare `Commit.where(sha:)` across the whole table. Concretely: `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_owner: ..., repository_name: ... })` or equivalent scoping using the verified repository identity from the webhook payload.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create two stacks, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/fork`), each with a `Shipit::Commit` row sharing the same `sha` (simulating shared git history), where `victim_stack`'s deploy spec requires `shipit/checks`.
2. Assert precondition equality: `victim_commit.sha == attacker_commit.sha` and `victim_commit.stack_id != attacker_commit.stack_id`.
3. Build a `status` webhook payload with `sha: shared_sha, context: 'shipit/checks', state: 'failure', repository: { full_name: 'attacker/fork', owner: { login: 'attacker' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).call` (or process directly), bypassing only the outer signature check (already out of scope per rules — assume it validly signed for `attacker`).
5. Assert that `attacker_commit.reload.state == 'failure'` (expected, in-scope write) **and** that `victim_commit.reload.state == 'failure'` / `victim_commit.deployable? == false` even though the webhook's `repository.full_name` was `attacker/fork`, proving the write crossed tenant boundaries.
