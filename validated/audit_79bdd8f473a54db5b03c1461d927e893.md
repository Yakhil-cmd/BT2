## Title
Webhook signature validation selects the GitHub App/organization secret from an unverified payload field, letting an attacker who controls one configured organization's webhook secret forge status/push/check-run events for a **different** organization's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* organization's HMAC secret to verify the incoming GitHub webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted request body, then uses that same body's `repository.full_name` to decide *which* `Repository`/`Stack` records the event handlers mutate. These two payload fields are not cryptographically bound to each other by the signature check - the HMAC only proves "this body was signed with organization X's secret," not "the `repository.full_name` field in this body belongs to organization X."

### Finding Description
`before_action :verify_signature` resolves the signing secret using a value taken from the raw, attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (in multi-org deployments, each org has its own `app_id`/`installation_id`/`webhook_secret`): [3](#0-2) [4](#0-3) 

`verify_webhook_signature` simply HMAC-compares the raw body against whichever secret was selected: [5](#0-4) 

Once the signature passes, `WebhooksController#create` dispatches to handlers using the raw JSON body: [6](#0-5) 

Handlers determine *which* `Repository`/`Stack` to act on from a **different** field of the same body - `repository.full_name` - via `Handler#repository_name`/`#stacks`: [7](#0-6) 

For example `PushHandler#process` syncs/updates whichever stacks match that `full_name`, and `StatusHandler#process` writes a CI status onto any local `Commit` whose `sha` is in the payload, regardless of which org "owns" that commit: [8](#0-7) [9](#0-8) 

The binding that should hold but does not:
`organization whose secret authenticated the request == organization that owns the repository/stack the handler mutates`

Both `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target Stack/Repository) live inside the same signed byte stream, so an attacker who legitimately knows **any one** configured organization's webhook secret (e.g. an organization admin/team-member of "org-A" in a multi-tenant Shipit install, who is entitled to configure org-A's own GitHub App and therefore knows or controls org-A's `webhook_secret`) can craft an arbitrary JSON body where:
- `repository.owner.login` = `"org-A"` (so `verify_signature` selects org‑A's secret and the HMAC they compute with a secret they legitimately possess validates), and
- `repository.full_name` = `"org-B/victim-repo"` (an org they have no authority over)

and sign it correctly. The check only proves the sender knows org-A's secret; it does not prove org-A actually owns `org-B/victim-repo`.

### Impact Explanation
Depending on the event type this enables an unprivileged-relative-to-org-B attacker to:
- Forge `push` events to trigger `sync_github` on org-B's stacks, or
- Forge `status`/`check_suite` events to write fake passing CI statuses/check-runs onto org-B's commits.

Because Shipit's deploy safety logic gates deploys on commit/CI status (`Commit#deployable?`, review/CI checks referenced throughout the deploy flow), an attacker able to inject fabricated "success" statuses onto a target org's commits can push a commit through CI gating it would not otherwise pass, ultimately enabling an unauthorized deploy on a stack the attacker's actual organization does not own. This is a cross-organization write / potential unauthorized-deploy primitive, only reachable in the multi-organization `github:` config schema (single-org/global-secret deployments are not affected, since `Shipit.github` ignores the `organization:` argument entirely when only one org is configured).

### Likelihood Explanation
Requires: (1) the host application configured with the multi-organization `github:` schema documented in `config/secrets.development.example.yml`, and (2) the attacker legitimately possessing/controlling one configured organization's own webhook secret (a realistic scenario for a self-service or partner-onboarding Shipit deployment where different customer/business-unit orgs each register their own GitHub App). Given that constraint, exploitation is a single crafted HTTP request with a valid HMAC computed from the attacker's own org secret - no other privilege is needed.

### Recommendation
Do not derive the "which secret verifies this request" decision from a field of the same untrusted payload used later for authorization/routing. Instead:
- Bind webhook delivery to a per-organization/per-installation URL segment or GitHub App `installation_id` established out-of-band, or
- After verifying with the resolved secret, additionally re-verify that the `installation.id`/organization identified by the *trusted* channel matches the `repository.owner.login`/`full_name` the handlers will act on, rejecting the request if they diverge.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` config (`org-a`, `org-b`, each with distinct `webhook_secret`).
2. As a party who owns/administers `org-a`'s GitHub App (and thus knows `org-a`'s `webhook_secret`), build a JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<org-b commit sha>",
  "state": "success"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a secret, body)>`.
4. POST to `/webhooks` (Shipit's webhook endpoint) with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches org-a's config, and the HMAC validates.
6. `StatusHandler#process` runs, writing a forged status onto `org-b`'s commit (a repository the attacker does not administer), because the handler routes purely off `repository.full_name`/`sha`, unrelated to the org that authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
