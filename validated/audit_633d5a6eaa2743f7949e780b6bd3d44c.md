### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook processing - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` updates commit CI status by matching on the raw git SHA across the *entire* database, with no scoping to the repository/organization whose webhook signature was actually verified, unlike every other webhook handler.

### Finding Description
The webhook signature check picks the GitHub App configuration to verify against based on `repository_owner`, which is taken from the same payload being verified: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
This only proves the request was legitimately sent by GitHub for *some* org/repo that owns that installation's `webhook_secret` — it establishes `organization authenticated == organization X`, nothing about which `Stack`/`Commit` records may be mutated.

Every other bundled handler re-establishes the missing binding by scoping mutations to the repository named in the (now-verified) payload via the `stacks` helper:
- `PushHandler#process` scopes to `stacks.not_archived.where(branch:)` before touching anything. [2](#0-1) 
- `CheckSuiteHandler#process` scopes to `stacks.where(branch: ...)` before touching commits. [3](#0-2) 

`StatusHandler#process`, however, looks up commits **globally by SHA only**, with no `stacks`/repository filter at all: [4](#0-3) 

Because git commit SHAs are content-derived and reused across repositories that share history (forks, cherry-picks, subtree merges, mirrored/vendored commits, or simply an attacker who controls one onboarded repo cherry-picking/rebasing a commit that is byte-identical to one that already exists in a `Commit` record belonging to a different stack), the `sha` field in a validly-signed `status` webhook is never checked against the repository the signature actually authenticated. This breaks the equality that should hold: `organization authenticated by webhook_secret == repository whose Commit rows are mutated`. An attacker who legitimately owns/administers *any* repository that Shipit is configured to receive webhooks for (and therefore can trigger a genuinely GitHub-signed `status` event, e.g. by pushing a commit and having their own CI or a script post an arbitrary commit status through the GitHub API) can cause `Commit.where(sha: params.sha)` to match a `Commit` row belonging to a completely different, unrelated stack/organization, and inject a forged `state: "success"` status onto it.

### Impact Explanation
Commit statuses gate automated, unattended actions in Shipit:
- Merge-queue merges are gated by `all_status_checks_passed?`, which is driven by the commit's `statuses_and_check_runs`, and directly leads to `merge!` calling `stack.github_api.merge_pull_request` for that stack's repository. [5](#0-4) 
- Continuous delivery / deployability checks rely on the same commit status data (`commit.deployable?`), which downstream deploy triggers depend on.

Because `StatusHandler` never verifies that the commit being updated belongs to a stack whose repository/org matches the one the webhook signature was checked against, an attacker with control of one onboarded (but otherwise unprivileged w.r.t. the target) repository can forge a passing CI status on a commit belonging to a different repository's stack that happens to share the same SHA, potentially triggering an unauthorized automated merge or deploy on a stack/repository they have no write access to — a cross-repository/unauthorized-merge impact within the accepted Critical impact category.

### Likelihood Explanation
Exploitation requires: (1) Shipit configured to service multiple repositories/orgs (the common multi-tenant deployment documented in this engine), (2) the attacker controls at least one such onboarded repository enough to generate a real, signed `status` webhook event (trivial — any commit status posted through GitHub's own API for a repo the attacker administers triggers this webhook), and (3) a SHA collision with a commit that exists in another tracked stack (achievable deliberately via cherry-pick/rebase/fork history sharing, not a cryptographic hash collision). No `ApiClient` token, session, or `webhook_secret` knowledge is required — only ownership of one already-onboarded, GitHub-App-installed repository, which is a materially lower privilege than write access to the *victim* repository/stack.

### Recommendation
Scope `StatusHandler#process` (and any other handler operating on `Commit`/`Stack` records) through the same repository-scoped `stacks` helper used by `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` or equivalently filter `Commit.where(sha: params.sha)` by `stack_id: stacks.pluck(:id)` before creating the status, ensuring the mutated `Commit` always belongs to a stack whose repository matches the organization that the webhook signature was verified against.

### Proof of Concept
1. Shipit instance tracks Stack A (`org-victim/app`) and Stack B (`org-attacker/app`), both with GitHub App webhooks configured (multi-tenant setup).
2. Attacker controls `org-attacker/app`. They cherry-pick/rebase a commit from `org-victim/app`'s history into their own fork so that a commit with an identical SHA `abc123...` exists in both repositories (or simply wait for a shared upstream commit to appear in both, e.g. via a common vendored dependency commit).
3. Attacker uses their own repo's CI (or the GitHub API directly, since they own `org-attacker/app`) to POST a `status` event with `sha: abc123...`, `state: success`, `context: ci/required-check` for their own repository. GitHub signs this webhook with `org-attacker`'s legitimate `webhook_secret`.
4. `WebhooksController#verify_signature` verifies the signature successfully (it is a genuine GitHub webhook for `org-attacker`). [6](#0-5) 
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...').each { |commit| commit.create_status_from_github!(params) }`, which matches and updates the `Commit` row belonging to Stack A (`org-victim/app`), because the lookup is not scoped to the requesting org/repo. [4](#0-3) 
6. Stack A's merge queue or continuous-delivery job observes the now-"passing" status and merges/deploys the victim commit automatically, even though the attacker never had write access to `org-victim/app`.
