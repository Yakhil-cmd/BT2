### Title
Cross-repository CI status forgery via SHA-only commit lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
### Finding Description
The `WebhooksController` selects the GitHub App/webhook secret used to authenticate an incoming `status` webhook based on `repository.owner.login` (or the top-level `organization.login`) extracted from the payload: [1](#0-0) [2](#0-1) 

This authenticates that the request was signed by the GitHub App installed for that particular organization — i.e. it proves "this organization sent this event," nothing more. Once the signature check passes, the raw JSON body is dispatched to `Shipit::Webhooks.for_event(event)` handlers with no further re-validation of which repository/organization the payload claims to target: [3](#0-2) 

`StatusHandler#process`, however, resolves the target `Commit` **purely by SHA**, without any scoping to the repository or organization that was used to verify the signature: [4](#0-3) 

Commit SHAs are 40-hex-character git object ids that are unique per-repository but not globally namespaced to an organization — the `Commit` records across all `Stack`s/`Repository`s in the Shipit database share one table, and `Commit.where(sha: params.sha)` will match any commit in any repository/organization tracked by the Shipit instance that happens to have that SHA in its history (e.g. a shared vendored file, a cherry-picked commit, a rebase, or simply a SHA an attacker discovers via the public GitHub API for the target repo and can also produce as a commit inside their own repo/branch using techniques such as an empty commit crafted to collide, or more realistically because many organizations mirror/fork shared code so identical commits legitimately exist in multiple repos).

This breaks the trust binding the report describes: **the organization whose webhook secret authenticated the request ≠ the repository/commit that is actually written**. The `repository_owner` field is checked only to select a valid signing key; it is never used to constrain which `Commit` row `create_status_from_github!` is allowed to mutate.

### Impact Explanation
An attacker who controls (or has push access to) any single repository/organization that is legitimately configured as a GitHub App installation in the target Shipit instance (i.e. can generate genuinely-signed `status` webhooks for their own repo) can push/forge a commit with a SHA equal to a real commit SHA belonging to a *different* organization/repository tracked by the same Shipit instance, and send (via their own, legitimately signed, org's GitHub App) a `status` event with `state: "success"` for that SHA. `StatusHandler` will apply the status to the victim's `Commit`, which feeds directly into `Commit#deployable?` / `Commit#status`: [5](#0-4) 

and into continuous-delivery scheduling: [6](#0-5) 

If the victim stack has `ignore_ci?` unset but relies on this externally-fed status (or has continuous deployment enabled), a forged success status from an unrelated, attacker-influenced organization can make an otherwise-blocked commit `deployable?`, enabling an **unauthorized deploy** — matching the High severity bar in the rules ("escalation ... unauthorized deploy").

### Likelihood Explanation
Requires the attacker to control at least one GitHub organization/repo that is a legitimate, separate GitHub App installation on the same Shipit instance (a plausible multi-tenant setup, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section), and to produce/know a colliding SHA that also exists in the victim repository's tracked history. This is a real but non-trivial precondition — it does not require any Shipit session, API token, or the target org's own webhook secret, satisfying the "unprivileged attacker" bar, but the SHA-collision requirement lowers likelihood versus a pure signature-bypass bug.

### Recommendation
Scope the `Commit` lookup in `StatusHandler` (and any other handler resolving records purely by SHA) to the repository/organization asserted by the payload and verified by `WebhooksController#verify_signature`, e.g. `stacks.commits.where(sha: params.sha)` using the same `Handler#stacks`/`repository_name` helper already available in `Handler`, instead of a global `Commit.where(sha:)` scan.

### Proof of Concept
1. Configure Shipit with two GitHub App installations: `org-victim` (tracks `org-victim/app`, contains commit `abc123...` currently pending CI) and `org-attacker` (attacker-controlled, legitimately installed).
2. Attacker crafts a commit with SHA `abc123...` inside their own repository (feasible when the victim commit is small/empty, or via known collision/mirroring techniques) and pushes it, or simply replays a `status` payload for that SHA through their own legitimately-signed GitHub App webhook delivery, setting `state: "success"`.
3. `WebhooksController#verify_signature` validates the signature against `org-attacker`'s webhook secret successfully (`repository.owner.login == "org-attacker"`).
4. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, matches the victim's commit, and calls `commit.create_status_from_github!(params)`, marking the victim commit `success`.
5. If `org-victim/app`'s stack has continuous deployment enabled, `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, deploying the victim's commit without a legitimate CI status from `org-victim`.
