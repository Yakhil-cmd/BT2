### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while event handlers dispatch on the unrelated `repository.full_name` field, letting an attacker bypass verification for one tenant and act on another tenant's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
This is the same bug class as the Bond report: two computations that are supposed to represent "the same value" diverge, and the security-relevant one is weaker than the one used to act on state. Here, `WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC against using `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), but the handlers that actually mutate state (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, pull-request handlers, etc.) select the target `Repository`/`Stack` using the unrelated `repository.full_name` field of the same attacker-controlled JSON body. [1](#0-0) [2](#0-1) [3](#0-2) 

Additionally, `GitHubApp#verify_webhook_signature` treats an organization with **no configured `webhook_secret`** as automatically verified: `return true unless webhook_secret`. [4](#0-3) 

### Finding Description
The binding that should hold is: **organization whose signature is checked == organization/repository the handler acts on**. Instead:

- `verify_signature` picks the `GitHubApp` (and hence the secret used for HMAC verification) via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `repository.owner.login` (fallback `organization.login`) from the untrusted JSON body.
- The `create` action, once `verify_signature` passes, dispatches the full raw JSON body to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 
- Every handler resolves the actual target repository/stack independently, using `payload.dig('repository', 'full_name')`, not `repository.owner.login`. [3](#0-2) [6](#0-5) 

In a multi-tenant Shipit deployment (multiple GitHub Apps/organizations configured under `secrets.github`, as exercised by `test/dummy/config/secrets_double_github_app.yml`), each organization can have an independently configured (or unconfigured) `webhook_secret`. Because `verify_webhook_signature` returns `true` when no secret is configured for that organization, an attacker who knows (or guesses) that **any** onboarded organization has no `webhook_secret` set can craft a POST to `/webhooks` where:
- `repository.owner.login` (or `organization.login`) = the org with no configured secret → signature check is skipped entirely.
- `repository.full_name` = a *different*, security-relevant org/repo that is tracked by Shipit (e.g., `"critical-org/critical-repo"`).

The handler layer then acts on `critical-org/critical-repo` using the attacker's forged payload content, with no signature ever having been checked against the org that actually owns that repository. This breaks the "organization authenticated versus the repository that is written" binding explicitly called out in the rules.

### Impact Explanation
This allows an unauthenticated, unprivileged network attacker (no session, no `ApiClient` token, no GitHub credentials) to forge webhook events against any repository/stack tracked by the Shipit instance, as long as any tenant in the same instance lacks a `webhook_secret`. Concretely reachable, credential-free consequences:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for an arbitrary tracked stack, which can affect deploy/rollback eligibility and undeployed-commit computation for a stack the attacker does not control.
- `Handlers::MembershipHandler` (per `test/controllers/webhooks_controller_test.rb`) can create arbitrary `Team`/`User` records tied to the crafted `member`/`team` payload.
- PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) can archive/unarchive review stacks for any repository, purely from a forged `pull_request`/`repository.full_name` combination.

This crosses the "cross-repository writes" / "unauthorized deploy" bar defined for Critical/High impact, because state belonging to one organization's repository is mutated using an authentication check performed against a different, attacker-chosen organization's (secret-less) identity.

### Likelihood Explanation
Exploitability depends entirely on operational configuration: the Shipit instance must be multi-tenant (multiple GitHub App organizations configured under `secrets.github`) and at least one configured organization must have `webhook_secret` blank/unset. This is a supported, documented configuration in this engine (see `test/dummy/config/secrets_double_github_app.yml`, and the setup docs marking `webhook_secret` as "optional"). No repository write access, GitHub App keys, or Shipit session/token are needed by the attacker — only a plain HTTP POST to the public `/webhooks` endpoint. This qualifies as an unprivileged-attacker analog and does not require assuming the host misconfigured anything the engine doesn't itself support/document as optional.

### Recommendation
- Do not let `verify_signature` and the handlers derive the "acting organization/repository" from independent fields of the untrusted payload. Both should resolve the tenant/organization from the *same* canonical field (e.g., always derive from `repository.full_name`'s owner segment, or bind the resolved `Repository`/`Stack`'s actual persisted owner) before selecting which secret to verify against.
- Do not treat an organization lacking a `webhook_secret` as automatically verified; either require a configured secret for every tenant or, if a secret is genuinely absent by design, restrict such an organization's webhook events to only affect stacks that are already scoped to that exact organization (never allow cross-organization dispatch).
- After signature verification succeeds for organization `O`, defensively re-check inside handler dispatch that the repository resolved via `repository.full_name` actually belongs to organization `O` before performing any mutation.

### Proof of Concept
Given a Shipit deployment configured with two GitHub App organizations, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml` where `OrgOne` has `webhook_secret: nil` and `OrgTwo` is the real owner of a tracked repository `OrgTwo/critical-repo`:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/garbage, never checked)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgOne" },        // used by verify_signature -> no secret configured -> auto "verified"
    "full_name": "OrgTwo/critical-repo"     // used by PushHandler to locate the real target stack
  }
}
```

1. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")`; `verify_webhook_signature` returns `true` immediately because `OrgOne`'s `webhook_secret` is blank — no HMAC is actually validated. [4](#0-3) 
2. `create` dispatches the parsed body to `Handlers::PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/critical-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the real, unrelated `OrgTwo` stack. [7](#0-6) 

No credential belonging to `OrgTwo`, no Shipit session, and no valid signature was ever required to affect `OrgTwo/critical-repo`'s tracked state.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
