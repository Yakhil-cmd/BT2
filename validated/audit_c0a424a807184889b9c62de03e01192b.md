### Title
Stack-scoped API token can read CI/deploy status of any stack via CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper inherited from `Shipit::Api::BaseController` in a way that drops the tenant/stack scoping that the rest of the API enforces for stack-scoped `ApiClient` tokens, letting a token that is only supposed to authorize reads on one stack read the deploy state of any stack on the instance.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the token's authorized stack when the token is stack-restricted: [1](#0-0) 

This is the binding that every other API controller relies on: `stack a token authorises == stack it touches`, enforced via `stacks.from_param!(params[:stack_id])`, where `stacks` is `Stack.where(id: current_api_client.stack_id)` for a scoped client.

`CCMenuController`, however, defines its own private `stack` method that bypasses `stacks` entirely and resolves the id against the full `Stack` table: [2](#0-1) 

The controller still enforces `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that the string `"read:stack"` is present in the client's `permissions` array — it never checks `stack_id` at all: [3](#0-2) 

So the only place the "stack a token authorises" constraint is actually enforced anywhere in the API is inside `BaseController#stacks`/`#stack`, and `CCMenuController` explicitly re-implements `#stack` to skip it, using `Stack.from_param!(params[:stack_id])` unscoped.

The mismatch is exploitable because CCMenu tokens are routinely minted as stack-restricted-looking, single-purpose tokens: `CCMenuUrlController#client` creates (or reuses) a `read:stack`-only `ApiClient` per requesting user and hands its `authentication_token` back embedded in a URL containing the originating stack id: [4](#0-3) 

(Note: this particular helper does not set `stack:` on the created client, but the `ApiClient` model and `ApiClient::PERMISSIONS` explicitly support creating stack-scoped, `read:stack`-only tokens for exactly this CCMenu use case — see the `stack` association and permission set in `app/models/shipit/api_client.rb` and fixtures such as `here_come_the_walrus` which is `stack: shipit, permissions: [read:stack]`.) Any such token — whether minted through this controller or through the general `api_clients` UI/API with a `stack_id` set — authenticates against `ApiClient.authenticate` the same way in every API controller: [5](#0-4) 

Because `CCMenuController#show` calls the overridden, unscoped `#stack` to build the response: [6](#0-5) 

a holder of a stack-restricted `read:stack` token for stack A can simply pass a different `stack_id` in the URL (`GET /api/:other_stack_id/cctray.xml?token=<tokenA>`) and receive build/deploy status for stack B, C, ... — any stack in the instance — even though the token's `stack_id` binds it to stack A only. The equality that should hold, `current_api_client.stack_id == requested_stack.id` (when the client is stack-scoped), is never checked in this controller; only the coarse `read:stack` capability is checked.

### Impact Explanation
This is an authorization-scope escalation: possession of a narrowly-scoped, low-privilege token (issued for CI dashboard integration on a single stack) is upgraded into an unauthorized read of another stack's deploy/build state — `lastBuildStatus`, `activity` (building/sleeping), `lastBuildLabel` (deploy id), and `webUrl`, as rendered in `app/views/shipit/ccmenu/project.xml.builder`. This satisfies the High-impact category of "escalation into ... unauthorized read of stack state" because the token's intended authorization boundary (one stack) is silently bypassed for reads across the entire stack namespace, breaking the "stack a token authorises vs. stack it touches" binding.

### Likelihood Explanation
Likelihood is high for any holder of a valid, even minimally-privileged (`read:stack`, single-stack) `ApiClient` token: the attack requires only changing the `stack_id` path segment of a request that is otherwise fully authenticated with a legitimately obtained token, no additional secrets, and no interaction with other users. `ApiClient` tokens are routinely distributed to third-party CI dashboards/tools for exactly the CCMenu use case, making the scoped-token population realistic and the bypass trivially discoverable by testing the endpoint with a foreign `stack_id`.

### Recommendation
Remove `CCMenuController`'s private `#stack` override (and the equivalent one in `CCMenuUrlController` if applicable) and route all stack lookups through the scoped `BaseController#stacks`/`#stack` helpers (`stacks.from_param!(params[:stack_id])`) so that stack-restricted tokens can never resolve stacks outside their `stack_id`. Additionally, have `ApiClient#check_permissions!` (or a dedicated method) validate that `stack_id` is nil or equals the resource being accessed, so the invariant is enforced centrally rather than depending on every controller reimplementing scoping correctly.

### Proof of Concept
1. Create (or have created for you via `CCMenuUrlController`) a stack-scoped `ApiClient` with `stack_id = A.id` and `permissions = ["read:stack"]`; obtain its `authentication_token`.
2. Call `GET /api/<stack_B_param>/cctray.xml?token=<tokenA>` where stack B is a different, unrelated stack.
3. Observe that `CCMenuController#authenticate_api_client` succeeds (valid token) and `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table rather than `ApiClient` A's authorized scope, returning stack B's build/deploy status in the XML response — confirming the token, though scoped to stack A only, can read state for stack B.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
