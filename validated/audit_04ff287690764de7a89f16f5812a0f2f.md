### Title
Fork PR labels named `github_repo_owner`/`github_repo_name` override `GITHUB_REPO_OWNER`/`GITHUB_REPO_NAME` in `ReviewStack#env` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges a hash derived from `pull_request.labels` on top of `Stack#env`, and PR labels are taken verbatim (uppercased) from the GitHub webhook payload with no reserved-key filtering. A fork owner can label their own PR `github_repo_owner` or `github_repo_name`, causing the resulting `env['GITHUB_REPO_OWNER']`/`env['GITHUB_REPO_NAME']` to become the literal string `"true"` instead of `repository.owner`/`repository.name`.

### Finding Description
The intended binding is `ReviewStack#env['GITHUB_REPO_OWNER'] == repository.owner` and `ReviewStack#env['GITHUB_REPO_NAME'] == repository.name`, as established in `Stack#env`: [1](#0-0) 

`ReviewStack#env` overrides this by merging a label-derived hash *after* calling `super`, so any label whose upcased name collides with an existing key wins: [2](#0-1) 

Labels are populated directly from the GitHub API/webhook payload with no allowlist/blocklist and no escaping of reserved key names: [3](#0-2) 

`self.labels = github_pull_request.labels.map(&:name)` at line 48 takes attacker-controlled label text as-is. A repository/fork owner who can open a pull request against the tracked repo (this is the normal review-stack workflow — PRs from forks are what review stacks are for) can add a label literally named `github_repo_owner` (or `github_repo_name`, case-insensitive since it's upcased) to their own PR. When the corresponding webhook (`pull_request` labeled event) is processed, `PullRequest#labels` is updated with that value, and the next call to `ReviewStack#env` computes:

```
super['GITHUB_REPO_OWNER']            # => repository.owner
.merge('GITHUB_REPO_OWNER' => 'true') # from the label
# => env['GITHUB_REPO_OWNER'] == 'true' != repository.owner
```

None of the existing guards prevent this: webhook signature verification (`verify_signature`) only authenticates that the payload came from GitHub for *that* repository — it does not restrict label content, which is entirely under the control of anyone who can label a PR (including the PR author on their own fork-originating PR, or any collaborator with label permission). There is no `EnvironmentVariables#permit`-style filtering applied to the label-derived hash before merging into `env`; `filter_deploy_envs`/`filter_task_envs` filtering happens on separately-supplied deploy `env` params, not on `Stack#env`/`ReviewStack#env` itself, and is irrelevant here since `env` (this method) is read directly by `deploy_steps`/`Command#interpolate_environment_variables` and by `Stack#links` interpolation.

### Impact Explanation
Any `shipit.yml` deploy/rollback/task script that branches infrastructure targeting based on `$GITHUB_REPO_OWNER`/`$GITHUB_REPO_NAME` (a documented pattern) will operate against the wrong, attacker-chosen value (`"true"`) instead of the real repository identity. Depending on how the deploy script uses these variables (e.g., to select a target AWS account, Kubernetes namespace, or GitHub API calls), this can misdirect deploy-time actions run via `Command`/`PTY.spawn` for that stack. The attack is repeatable on every webhook-triggered `env` computation for any review stack the attacker's fork/PR is associated with, i.e., any repository configured with Shipit review stacks. This matches "a command running that should not" / infrastructure misdirection at deploy time.

### Likelihood Explanation
Low operational cost: the attacker only needs to be able to open a pull request against a repository with Shipit review stacks enabled and apply a label to it (label application typically requires write access on GitHub, but PR authors from forks with the "allow edits" pattern, or maintainers who accept externally-suggested labels via bots, can trigger this). No Shipit credentials, session, or GitHub secrets are needed — only the ability to label a PR that Shipit ingests via webhook. The bug is deterministic and works every time such a label is present.

### Recommendation
In `ReviewStack#env`, reverse the merge precedence so the base `Stack#env` values always win, or explicitly blocklist/strip reserved keys (`GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`, `DEPLOY_URL`) from the label-derived hash before merging, e.g.:
```ruby
def env
  return super unless pull_request.present?

  label_env = pull_request.labels.each_with_object({}) { |l, h| h[l.upcase] = "true" }
  label_env.merge(super) # base stack env takes precedence
end
```

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_override_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvOverrideTest < ActiveSupport::TestCase
    test "PR label cannot override GITHUB_REPO_OWNER in ReviewStack#env" do
      stack = shipit_stacks(:review_stack) # a Shipit::ReviewStack fixture with a repository
      pull_request = stack.pull_request || stack.create_pull_request!(...)
      pull_request.update!(labels: ['github_repo_owner'])

      refute_equal stack.repository.owner, stack.env['GITHUB_REPO_OWNER'],
        "Expected divergence: label overrides GITHUB_REPO_OWNER"
      assert_equal 'true', stack.env['GITHUB_REPO_OWNER']
    end
  end
end
```
This demonstrates `ReviewStack#env['GITHUB_REPO_OWNER'] != repository.owner` once a PR carries the `github_repo_owner` label, confirming the broken binding.
