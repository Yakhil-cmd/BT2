## Title
Webhook signature verification key selected from an unverified payload field, allowing cross-organization/cross-repository writes when any configured GitHub App organization has no `webhook_secret` set - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` picks *which* organization's secret to use for HMAC verification from a field inside the very payload it is trying to authenticate (`repository.owner.login`), while the downstream handlers select the `Repository`/`Stack` to mutate from a *different* field of the same payload (`repository.full_name`). These two fields are never checked for consistency, so the "organization that authenticated" is not bound to the "repository that is written" — the same equality-gap pattern described in the external report (`currentDelegate` vs `delegatee` never compared).

## Finding Description
`before_action :verify_signature` resolves the signing key like this: [1](#0-0) 

`repository_owner` is read straight out of the unauthenticated request body: [2](#0-1) 

The secret used is looked up per-organization in `GitHubApp`, and if that organization has no `webhook_secret` configured, verification is unconditionally skipped: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps/organizations with independent secrets, as shown in the multi-org fixture where each org can have its own (possibly blank) `webhook_secret`: [4](#0-3) 

Once `verify_signature` passes (for any reason, including the “no secret configured” bypass), `create` dispatches the *entire raw payload* to handlers keyed only by the HTTP header event type — it never re-checks that `repository.owner.login` matches anything: [5](#0-4) 

Handlers then resolve the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, with no cross-check against the organization used to select the signing key: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to pick the verification key) and `repository.full_name` (used to pick the repo/stack to act on) are independent, attacker-controlled JSON keys, an attacker who crafts a payload where `repository.owner.login` names an organization configured with no `webhook_secret` (or one whose secret the attacker knows/leaks), but sets `repository.full_name` to `"<other-org>/<repo>"`, can have the request accepted by `verify_signature` while `PushHandler#process` (or `StatusHandler`) operates on a completely different, protected organization's stack — e.g. forcing `stack.sync_github(expected_head_sha: params.after)` to an attacker-chosen SHA, or forging a commit `Status` used to gate continuous deployment.

## Impact Explanation
This breaks the trust boundary "organization that authenticated == repository that is written," letting an unprivileged network attacker with no Shipit credentials trigger unauthorized syncs/deploys or forge CI statuses for a stack belonging to an organization/App they were never authenticated against. This matches the High/Critical impact bar ("unauthorized deploy… or cross-repository writes").

## Likelihood Explanation
Exploitability is conditioned on the specific multi-organization deployment topology: it requires at least one configured GitHub App organization to have a blank/unset `webhook_secret` (a supported, documented configuration state, not a coding error, as shown by the example config files), which then lets an attacker forge payloads for a *different*, properly-secured organization by manipulating `repository.owner.login` independently of `repository.full_name`. This is a real code-level design gap (missing binding between the two fields), but its practical reach depends on the operator's specific multi-org `secrets.yml` configuration having at least one organization without a webhook secret — a condition I could not confirm is disallowed anywhere in `lib/shipit.rb` (my final grep for `Shipit.github`'s organization-selection logic and `GithubOrganizationUnknown` handling did not complete before the tool budget ran out, so I cannot fully confirm whether an org lookup miss always raises rather than falling back to a shared/default secret).

## Recommendation
In `WebhooksController#verify_signature`/`#create`, after verifying the signature, re-derive the organization actually referenced by the payload's `repository.full_name` (or `organization.login`) and require it to equal `repository_owner` before dispatching to handlers — i.e., explicitly check `repository_owner == full_name_owner` (the missing equality check, directly analogous to adding `currentDelegate != delegatee`). Additionally, treat a blank/missing `webhook_secret` for a configured organization as a hard misconfiguration (refuse to accept unsigned webhooks) rather than as an implicit "always verified" bypass in `GitHubApp#verify_webhook_signature`.

## Proof of Concept
1. Configure Shipit with two GitHub App organizations (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgSecure` (has a `webhook_secret`) and `OrgOpen` (no `webhook_secret`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgSecure/protected-repo" }
}
```
No `X-Hub-Signature` (or an arbitrary value) is required, since `Shipit.github(organization: "OrgOpen")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
3. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgSecure/protected-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, affecting the `OrgSecure` stack despite the request never being authenticated for `OrgSecure`.

Note: I was unable to fully verify the exact fallback behavior of `Shipit.github(organization:)`/`GithubOrganizationUnknown` in `lib/shipit.rb` before the tool budget was exhausted, so confirm that code path (particularly whether an unknown/blank-secret organization can be looked up at all in a given deployment) before treating this PoC as fully validated against a specific configuration.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
