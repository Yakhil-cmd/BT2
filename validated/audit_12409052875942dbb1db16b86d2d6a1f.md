### Title
AA payments can be permanently bricked by dust-flooding an AA address with many small outputs, since `too many inputs` validation is bypassed for AA-generated units - ([File: aa_composer.js])

### Summary
`sendUnit`/`completePaymentPayload` in `aa_composer.js` builds an AA's outgoing payment by iterating over *every* matching unspent output of the AA's address with no cap on the number of inputs collected, and `validatePaymentInputsAndOutputs` in `validation.js` explicitly skips the "too many inputs" limit for AA-generated payments (`objValidationState.bAA`). This mirrors the referenced OpenQ bug class: an unprivileged user can flood a target (there: `getLockedFunds`'s deposit loop; here: an AA address) with a large number of small, but individually valid, deposits, forcing a later payout/refund-style operation to iterate over all of them and eventually fail or produce a pathological unit, permanently freezing funds.

### Finding Description
`completePaymentPayload`/`iterateUnspentOutputs` reads unspent outputs of the AA address via `readStableOutputs`/`readUnstableOutputsSentByAAs`, which run unbounded `SELECT ... WHERE address=? ... output_id NOT IN(...)` queries with no `LIMIT`: [1](#0-0) [2](#0-1) 

`iterateUnspentOutputs` then unconditionally pushes every returned row into `payload.inputs` until the accumulated `total_amount` reaches the target, with no check on `payload.inputs.length` against `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`: [3](#0-2) 

The only anti-dust guard is a minimum per-output size filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) meant to keep each individual input "net positive," documented in the comment at: [4](#0-3) 
This only prevents outputs *below* that threshold; it does not limit the *number* of outputs just above the threshold that an attacker can create by sending many small payments to the AA address.

Critically, standard payment validation waives the input-count cap specifically for AA-authored units: [5](#0-4) 
`constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` is 128: [6](#0-5) 

Because the input-count validation is bypassed for AA units, the composer does not need to (and does not) stop at 128 inputs, but it will still be bound elsewhere: the resulting unit must satisfy `MAX_UNIT_LENGTH` (5,000,000 bytes) and `MAX_MESSAGES_PER_UNIT`. If enough dust outputs are required to reach the target payment amount, the constructed payment message/unit can grow arbitrarily, and the deterministic AA trigger-handling logic (run identically by every full node) must query and iterate the full, ever-growing set of unspent outputs each time the AA tries to pay out from its balance in that asset.

### Impact Explanation
An adversary who can freely send payments to a public AA address can:
- Send a very large number of small-but-valid outputs (just above the `FULL_TRANSFER_INPUT_SIZE` dust threshold) to the AA.
- Because the too-many-inputs check is disabled for AA units, the AA composer will keep collecting these dust inputs without ever refusing due to input count, growing the payment message/unit size and processing time per node on every attempt to pay out of that balance.
- If the accumulated payment message eventually cannot be constructed within `MAX_UNIT_LENGTH`/`MAX_MESSAGES_PER_UNIT`, the AA response unit will fail internal construction/validation, causing `bounce()` and inability to pay legitimate recipients from its own funds/balance in that asset — effectively freezing AA funds analogous to "bricking refunds." Even short of an outright failure, every node in the network must repeat the same expensive unbounded query/iteration deterministically on every trigger that spends this balance, which is a resource-exhaustion vector reachable purely by posting ordinary payment units to a public AA address (no elevated privileges required).

This matches the report's "Medium/High" impact classes of AA fund loss/freezing and a node's inability to reliably process a specific class of unit (AA responses tied to a dust-flooded balance).

### Likelihood Explanation
Likelihood is significant for AAs that are publicly funded/payable (e.g., accept incoming payments from arbitrary users and later distribute/refund a proportional share), because sending many small payments is cheap and requires no special permissions — only enough bytes to cover the dust threshold per output and normal network fees. The precondition is that the AA logic must eventually attempt to spend a balance largely composed of attacker-deposited dust, which is a common pattern (bounty/vault/payout AAs).

### Recommendation
- Enforce a maximum number of collected inputs (e.g., `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`) in `iterateUnspentOutputs`/`completePaymentPayload` regardless of the `bAA` validation exemption, and fail early/gracefully (or use `LIMIT` in `readStableOutputs`/`readUnstableOutputsSentByAAs`) instead of relying solely on the minimum-output-size dust filter.
- Reconsider removing or bounding the `!objValidationState.bAA` exemption from the "too many inputs" check in `validation.js` so AA-generated payments are subject to the same anti-spam ceiling as user payments, or introduce an AA-specific ceiling with a defined fallback (e.g., partial payout across multiple triggers) so dust flooding cannot indefinitely block a payout.
- Consider consolidating/sweeping small AA-owned outputs (a "coin selection" strategy preferring fewer, larger inputs, or periodic self-consolidation) to reduce the blast radius of dust attacks on AA balances.

### Proof of Concept
1. Deploy or identify a public AA that accepts payments from arbitrary addresses and, at a later state-var-triggered payout event, pays out its holdings (e.g., a proportional refund/payout AA).
2. As an attacker, submit many small payment units to the AA address, each output valued just above `FULL_TRANSFER_INPUT_SIZE` (currently used to filter dust) — e.g., thousands of tiny outputs, well within normal unit/payment limits since regular payments are still capped at `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`, but nothing prevents repeating this across many separate units.
3. Trigger the AA's payout logic. `completePaymentPayload` calls `readStableOutputs` (unbounded query, no `LIMIT`) and `iterateUnspentOutputs`, which will keep adding all these dust outputs as inputs without ever refusing due to input count (per [5](#0-4) 's `!objValidationState.bAA` exemption), since `iterateUnspentOutputs` ( [3](#0-2) ) has no such limit either.
4. Observe that the constructed payment message/unit grows proportionally to the number of dust outputs required to satisfy the payout amount; past a sufficient number of dust deposits, the resulting unit will exceed `MAX_UNIT_LENGTH`/`MAX_MESSAGES_PER_UNIT` or take excessive processing time on every full node evaluating the trigger, and the AA response either fails/bounces (freezing that payout) or imposes heavy uniform per-node cost.

Note: I was not able to fully trace every downstream failure path (e.g., exact `bounce()` behavior when the constructed unit exceeds `MAX_UNIT_LENGTH`) within the available context; a Devin session with full repository/test access would be needed to confirm the precise failure mode and quantify the exact threshold of dust outputs required to trigger unit-construction failure versus mere performance degradation.
