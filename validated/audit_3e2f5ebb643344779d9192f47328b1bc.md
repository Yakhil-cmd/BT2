### Title
Unbounded RAY-value accrual can permanently freeze an entire lending market - ([File: contracts/pool/src/interest.rs])

### Summary
A heavily utilized market whose scaled balances are near the admitted RAY/cap domain can reach an accrued value that no longer fits `i128`, even though each stored scaled balance and index remains within its individual bounds. Subsequent accrual raises `GenericError::MathOverflow`, and because ordinary repayments, withdrawals, liquidations, and index updates all synchronize the market first, the market becomes unusable until a code-level repair is deployed. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The spoke cap check compares `stored_scaled + delta_scaled` to the cap converted at the current index, but it does not reserve arithmetic room for the future value `scaled * index`. [4](#0-3)  Accrual repeatedly calls `accrue_step` and persists the resulting borrow and supply indexes, while utilization and subsequent conversions derive asset values through `scaled_to_original`. [5](#0-4) [6](#0-5)  An attacker can legitimately create an extremely large scaled position within the configured caps, borrow most of the market, and let debt accrual push `scaled * index` beyond the `i128` domain before the borrow-index ceiling engages. [7](#0-6)  The regression test reproduces that state with an 18-decimal market at the cap, 98% utilization, and a subsequent `update_indexes` failure. [8](#0-7) 

`update_indexes` is permissionless except for caller authorization, so any unprivileged caller can trigger the terminal accrual once the numerical precondition exists. [9](#0-8)  Unlike the parser assertion in the CVE, this is not merely a rejected malformed input: the failed conversion occurs during mandatory synchronization before normal state transitions. [1](#0-0) 

### Impact Explanation
Once the market reaches the RAY-value ceiling, repayments, withdrawals, liquidation settlement, revenue claims, and explicit index updates that touch that hub asset can fail at synchronization, permanently freezing the market's underlying funds absent an upgraded implementation or another privileged repair path. [3](#0-2)  This is a market-wide loss of availability, not only a failed attacker transaction. [10](#0-9) 

### Likelihood Explanation
The attack requires a listed market configured near the maximum admitted token/cap domain and enough collateral and borrowable liquidity to sustain very high utilization, so it is capital-intensive and depends on permissive market limits. [4](#0-3) [11](#0-10)  No privileged call, oracle manipulation, malformed route, or external-contract failure is needed to trigger the final arithmetic failure; any authorized caller can invoke `update_indexes`. [9](#0-8) 

### Recommendation
Bound admitted scaled supply and debt by a market-specific safety margin that guarantees `scaled * MAX_BORROW_INDEX_RAY` and accrued protocol-revenue combinations remain inside `i128`, rather than checking only the current-index cap. [12](#0-11)  Alternatively, make accrual clamp index or book growth before value conversion can overflow, while preserving conservative repayment accounting and emitting an explicit ceiling event. [13](#0-12) 

### Proof of Concept
For a market `BIG18` with 18 decimals and another collateral market `COL`, configure caps at the admitted maximum and permit high utilization; the attacker then executes:

```text
supply(attacker, 0, spoke_id, [(COL, collateral)])
supply(attacker, 0, spoke_id, [(BIG18, principal)])
borrow(attacker, account_id, [(BIG18, 98% of BIG18 liquidity)], attacker)
update_indexes(attacker, [BIG18])
```

After sufficient accrual, `update_indexes` returns `MathOverflow`; the same overflow then prevents the attacker or suppliers from successfully calling repay, withdraw, or liquidation paths for `BIG18`. [14](#0-13)  The test demonstrates this state reaches `MathOverflow` while the borrow index is still below its configured ceiling, proving that the cap does not prevent the value-domain failure. [15](#0-14)

/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);

        "the index cap did not engage before the value overflow"

    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
