### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup in status webhook handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook solely by `sha`, with no scoping to the repository/organization that the webhook's signature was verified against. Because the `commits` table only enforces uniqueness on the composite `(sha, stack_id)` and not on `sha` alone, an attacker who can trigger a legitimately-signed webhook from a repository they control can cause a `Status` row to be written against a completely unrelated victim `Stack` whenever that victim stack happens to contain a `Commit` with the same sha (e.g., a shared ancestor from a common upstream fork).

### Finding Description
The broken binding: the code path implicitly assumes `commit.stack_id == the stack whose repository owner/secret produced a valid X-Hub-Signature`, but in reality `commit.stack_id` is simply whatever stack happens to have a row with `sha == params.sha`, with no relationship to the org that authenticated the request.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) authenticates the *request* by looking up `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and checking the HMAC over the raw body. This proves only that the payload was sent by GitHub for **that named organization/app installation** — it says nothing about which `Commit`/`Stack` rows should be affected.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This queries **every** `Commit` row across **every** `Stack` matching the sha, with no filter on `params.repository.full_name` or on the organization that was just authenticated.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) does `find_or_create_by!(stack_id:, ...)` — writing a `Status` scoped to `commit.stack_id` for **each** matched commit, unconditionally.
- The database only enforces `add_index :commits, %i(sha stack_id), unique: true` (db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb) — sha is explicitly **not** unique across stacks, so multiple tenants legitimately end up with rows sharing a sha (e.g., both forked the same public upstream and Shipit's `GithubSyncJob`/`Commit.create_from_github!` recorded the shared ancestor commit in both stacks' `commits` tables).

Attacker flow: the attacker owns/administers a repository under a GitHub organization/App installation that Shipit is configured for (this can be their own org with its own `github_app` entry, or any org sharing the installation with the victim — the webhook is authenticated per-organization, not per-repository or per-stack). They create (or already have) a commit whose sha is identical to a commit that also exists in the victim's stack (trivial via a shared public upstream fork — git shas are content-addressed). Using ordinary, unprivileged GitHub API access to their own repo, they set a commit status on that sha (`POST /repos/{owner}/{repo}/statuses/{sha}`) — a completely normal action for an owner of a public/private repo. GitHub then sends a real, correctly HMAC-signed `status` webhook to Shipit naming the attacker's repository. `verify_signature` passes because the signature is genuine for that organization. `StatusHandler#process` then finds **both** the attacker's own commit row and the victim's commit row (identical sha, different `stack_id`), and writes a `Status` against the victim's `stack_id` even though the payload's `repository.full_name`/`state`/etc. never referenced the victim's stack and the request was never validated against the victim's org/secret.

None of the existing guards prevent this: `verify_signature` only checks organization-level HMAC (not per-repository or per-commit binding); `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `StatusHandler.params` only validates payload shape (`sha`, `state`, etc.), not repository ownership of the sha; there is no `force_github_authentication`, `User#authorized?`, or `stacks` scoping applied in the webhook path, since webhooks are unauthenticated-by-session by design and rely entirely on signature + repository binding — which is exactly the binding this code fails to enforce.

### Impact Explanation
A single legitimate, signed webhook for one repository writes a `Status` row for a stack belonging to a different tenant/organization that never validated the request. This matches the stated Critical category: "a payload for one repository mutating another's stack, commit, task or team." Concretely: `after_create :enable_ci_on_stack` (app/models/shipit/status.rb:18, :38-40) flips `ignore_ci` state on the victim's stack, and `after_commit :schedule_continuous_delivery` (status.rb:19, :42-44) can enqueue `ProcessMergeRequestsJob`/CD flows on the victim's stack based on attacker-chosen `state`/`description`/`context`/`target_url` values, potentially causing an unintended deploy-readiness transition (e.g., forging a `success` CI status for the shared commit, unblocking continuous deployment or merge-queue progression on the victim stack) despite the attacker never authenticating against the victim's organization. This is repeatable against any stack whose commit history shares a sha with any repository the attacker can write statuses to.

### Likelihood Explanation
Preconditions: (1) Shipit is configured with a webhook secret/App the attacker's own repository is covered by (either their own org's Shipit installation, or a shared installation with the victim), (2) the victim's stack contains a `Commit` row with a sha identical to one in a repository the attacker controls — realistic via a shared public upstream (fork lineage) or by the attacker deliberately reproducing exact commit metadata to get sha collision. No Shipit secrets, sessions, or GitHub App keys are needed by the attacker; they only need ordinary write access to a repo they own and the ability to set a commit status on it via the standard GitHub API — both are unprivileged, self-service actions. This is directly demonstrable and repeatable without live GitHub, by seeding two `Commit` fixtures with identical `sha` under different `stack_id`s and posting one `status` webhook.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository named in the (already-authenticated) payload, not just `sha` — e.g., resolve the target `Stack`(s) via `params.repository.full_name` (or the authenticated `repository_owner`) first, then look up `Commit.where(sha: params.sha, stack: stacks_for_that_repository)`, so that a Status can only be written for a stack whose repository matches the one whose signature was verified.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook only affects the commit for the authenticated repository, not other stacks sharing the sha" do
  attacker_stack = shipit_stacks(:shipit)               # authenticated org/repo
  victim_stack   = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo'), environment: 'production')

  shared_sha = 'deadbeef' * 5

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'shared ancestor')
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'shared ancestor')

  params = ExplicitParameters::Parameters.new(
    sha: shared_sha, state: 'success', description: 'forged', context: 'ci', created_at: Time.now.to_s
  )

  assert_difference -> { Shipit::Status.where(stack_id: victim_stack.id).count }, 1 do
    # Equality that SHOULD hold: only Status.where(stack_id: attacker_stack.id) should change,
    # since only attacker_stack's org/secret validated this webhook.
    Shipit::Webhooks::Handlers::StatusHandler.new.call(params)
  end
end
```
Both sides of the binding, stated explicitly: expected `written_stack_id == stack_id_whose_org_verified_signature (attacker_stack.id)`; actual `written_stack_id ∈ {attacker_stack.id, victim_stack.id}` — the equality fails, confirming the vulnerability.
