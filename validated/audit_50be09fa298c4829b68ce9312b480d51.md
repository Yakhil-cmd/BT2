### Title
Webhook signature verification selects the GitHub App secret from `repository.owner.login`, while every event handler resolves the target repository from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the secret used to validate the `X-Hub-Signature` HMAC from `repository.owner.login` (or `organization.login`), while `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, e.g. `PushHandler`, `CheckSuiteHandler`) resolves the actual `Stack`/`Repository` to act on from a *different* JSON field, `repository.full_name`. Nothing enforces that these two fields agree, so the field that authorizes the request (which secret proved validity) is not the field bound by that signature check to a specific repository.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is [2](#0-1) :
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
This value only determines **which configured GitHub App's `webhook_secret` is used to compute the HMAC**, per [3](#0-2) .

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied JSON to handlers such as `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc. Every one of these inherits `repository_name`/`stacks` from `Handler`, which reads a **different** field: [4](#0-3) :
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Shipit supports multiple GitHub Apps/organizations configured side by side, each with its own `webhook_secret`, exactly as documented in [5](#0-4) . An actor who legitimately controls one configured organization/app (e.g. installs their own GitHub App on their own org, a normal, unprivileged self-service action for that organization) possesses a valid `webhook_secret` for that org and can compute a correct HMAC for **any JSON body of their choosing**, since `X-Hub-Signature` only proves "this body was signed with organization X's secret" — it says nothing about which repository the body's content refers to. There is no requirement that `repository.owner.login` equals `repository.full_name`'s owner segment; GitHub's own webhook payloads always keep them consistent, but a forged POST to `/webhooks` does not have to.

This breaks exactly the "organization authenticated vs. repository written" binding: the equality `repository.owner.login (used to select validating secret) == owner-segment of repository.full_name (used to select the Stack that is mutated)` is never checked.

### Impact Explanation
Using the org-A secret, an attacker can submit a forged `push` event whose `repository.full_name` names a stack belonging to an unrelated, victim repository/org configured in the same Shipit instance. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on stacks matching that (attacker-chosen) repository/branch — this triggers a GitHub sync using Shipit's own GitHub credentials for the victim repository, independent of who actually owns/controls that repository on GitHub. Similarly `CheckSuiteHandler` can force `schedule_refresh_check_runs!` and `StatusHandler` can inject `create_status_from_github!` records tied to arbitrary commit SHAs application-wide (statuses are looked up by `sha` alone, with no repository scoping at all - `Commit.where(sha: params.sha)`), letting an attacker holding one org's webhook secret inject fabricated CI/CD statuses that other stacks/orgs rely on to gate deploys. This is a cross-repository/cross-organization write performed under one org's authentication credentials against another org's stack state, matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability requires the attacker to control at least one configured GitHub App/organization's `webhook_secret` in a multi-org Shipit deployment (a normal, unprivileged tenant of that Shipit instance, not requiring any Shipit session, API token, or private key exposure) and to know or guess a target repository's `full_name` and a commit SHA/branch of interest (both public/discoverable information for public repos). No `ApiClient` token, GitHub App private key, or webhook secret theft is needed beyond the secret the attacker already legitimately owns for their own org. This is realistic specifically in the documented multi-organization configuration (`docs/setup.md`), which is a first-class supported Shipit deployment mode.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after verifying the signature, assert that the organization used to select the verifying secret (`repository_owner`) matches the owner segment actually used to resolve the target repository (`repository.full_name`'s owner). Reject/`head(422)` the request if they differ. Alternatively, derive both the verification key and the target repository from the *same* single field (e.g., always use `repository.full_name`'s owner segment for `Shipit.github(organization: ...)`), eliminating the possibility of an inconsistent payload being accepted.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `victim-org`, each with its own `webhook_secret` (as in `docs/setup.md`'s multi-org example).
2. As an attacker who legitimately installed/administers the Shipit GitHub App for `org-a`, obtain `org-a`'s `webhook_secret` (a normal, unprivileged capability for that org's admin).
3. Craft a JSON payload for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "victim-org/prod-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, payload)>`.
5. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` resolves `repository_owner == "org-a"`, fetches `org-a`'s `GitHubApp`, and the HMAC validates successfully.
6. `PushHandler.call(params)` runs, resolving `stacks` via `Repository.from_github_repo_name("victim-org/prod-repo")`, and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack — an action triggered entirely by `org-a`'s credentials against `victim-org`'s repository state.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
