### Title
`ReopenedHandler#unarchive?` bypasses `review_stacks_enabled` via operator-precedence bug, allowing unauthorized ReviewStack creation on opted-out repositories - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` intends `repository.review_stacks_enabled` to gate all review-stack provisioning behavior, but due to Ruby operator precedence (`&&` binds tighter than `||`), the flag only gates the `allow_all` branch. Any PR author can close/reopen their own PR on a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` (no label present) to trigger unauthorized `ReviewStack` creation and provisioning-queue enqueue, even though the repository owner explicitly disabled review stacks.

### Finding Description
The intended binding is: stack provisioning only occurs when `repository.review_stacks_enabled == true`. The actual code at [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||`, this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` only gates the first disjunct; the `prevent_with_label` (and `allow_with_label`) branches are entirely independent of it. With `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` and no provisioning label present, `unarchive?` evaluates to `true` via the third disjunct.

`respond_to_pull_request_reopened?` ( [2](#0-1) ) only checks `params.action == "reopened" && unarchive?` — it never independently checks `review_stacks_enabled`, unlike the sibling `LabeledHandler`/`UnlabeledHandler`, which correctly AND the entire condition with `repository.review_stacks_enabled` at the top level: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)` [3](#0-2) . This inconsistency confirms the `Reopened`/`Opened` handlers have a logic bug rather than intended behavior, since `OpenedHandler#provision?` contains the identical flawed pattern [4](#0-3) .

Once `unarchive?` is true, `process` calls `stack.unarchive!` [5](#0-4) , which delegates to `ReviewStackAdapter#unarchive!`. Since no stack exists yet for a first-time PR, `stack.blank?` is true and it calls `create!`, which creates a `ReviewStack`, builds the `pull_request` association, and enqueues `Shipit::ReviewStackProvisioningQueue.add(stack)` [6](#0-5) .

**Attack path:** An attacker who opened (or has an existing) PR against a repository already registered in Shipit closes and then reopens their own PR on GitHub. GitHub emits a legitimately-signed `pull_request` `reopened` webhook (no forged signature needed — the attacker relies only on ordinary GitHub PR actions available to any PR author). `WebhooksController#verify_signature` [7](#0-6)  passes because the signature is genuine. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ReopenedHandler` among others [8](#0-7) . The `Repository` model has no validation coupling `review_stacks_enabled` and `provisioning_behavior` [9](#0-8) , so an operator can legitimately configure exactly this combination (e.g., intending to fully disable review stacks while leaving `provisioning_behavior` at a non-default value), and the flag is silently ignored by this handler.

### Impact Explanation
For a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`), an unprivileged PR author can still cause Shipit to create a `Shipit::ReviewStack` record, associate a `PullRequest`, and enqueue it via `Shipit::ReviewStackProvisioningQueue.add`, which drives downstream provisioning tasks. This is an unauthorized-write/unauthorized-provisioning-trigger against a tenant repository that opted out of the feature, matching the "unauthorized deploy" class of Critical impact. It is repeatable per repository/PR (close+reopen again after re-archival) and does not require any Shipit credentials — only ordinary GitHub PR-author actions.

### Likelihood Explanation
Preconditions: the target repository must already be registered with Shipit (`Shipit::Repository.from_github_repo_name` must resolve), have `review_stacks_enabled: false`, and `provisioning_behavior: prevent_with_label` (or `allow_with_label`) — a plausible, unvalidated configuration combination. The attacker only needs to be the author of a PR against that repository (closing/reopening one's own PR is possible without repository write access on GitHub) and needs no Shipit secrets, tokens, or team membership. This makes the exploit low-cost and fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, consistent with `LabeledHandler`/`UnlabeledHandler`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `OpenedHandler#provision?`, which has the identical bug.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does NOT create/unarchive a review stack for repos with review_stacks_enabled=false, prevent_with_label, no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::ReviewStack.count } do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before the fix, `repository.review_stacks_enabled` is `false` yet `Shipit::ReviewStack.count` increases and `Shipit::ReviewStackProvisioningQueue.add` is invoked (can be asserted with `Shipit::ReviewStackProvisioningQueue.expects(:add)` never called); after applying the recommended fix, `assert_no_difference` passes because `unarchive?` returns `false` when `review_stacks_enabled == false`, regardless of `provisioning_behavior`.

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do

              stack.unarchive!(*args, &block)
            end
          end

          end

          private

          def action
            params.action
          end

          def repo_name
            params.repository["full_name"]
          end

          def pr_number
            params.number
          end

                )
