### Title
Webhook signature check validates only `repository.owner.login`/`organization.login` while every event handler keys its writes off the independently-supplied `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/secret to verify the HMAC against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . However, every registered handler (`PushHandler`, `StatusHandler`, `PullRequest::*`) resolves the target `Repository`/`Stack`/`Commit` using a *different, independently-controlled* payload field: `payload.dig('repository','full_name')` in the base `Handler#repository_name` [3](#0-2) , or `Commit.where(sha: params.sha)` with no repository/org scoping at all in `StatusHandler#process` [4](#0-3) . There is no code path that enforces `repository.owner.login == repository.full_name`'s owner, or that the org whose secret verified the signature is the org that owns the repository/commit being acted upon.

### Finding Description
The binding that should hold is: **organization whose webhook secret verified the request == organization that owns the repository/commit being written**. This binding is broken because the two fields come from disjoint parts of the same attacker-controlled JSON body, and only one of them is covered by "verification" (and that verification itself is a no-op whenever the target org has no `webhook_secret` configured, since `GithubApp#verify_webhook_signature` explicitly `return true unless webhook_secret` [5](#0-4) ).

Shipit is explicitly designed to host multiple GitHub organizations/apps at once (`Shipit.github(organization:)`, multiple entries as shown in `secrets_double_github_app.yml` [6](#0-5) ). Any org configured without a `webhook_secret` (a supported, documented configuration - see the `null`/blank `webhook_secret` in `test/dummy/config/secrets.test.json` [7](#0-6) ) causes `verify_webhook_signature` to unconditionally return `true` for any payload whose `repository.owner.login` names that org - regardless of the actual `X-Hub-Signature` header.

An unauthenticated caller (no Shipit session, no `ApiClient` token) can POST directly to the public `/github/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) = the name of the org with a blank/nil `webhook_secret` → passes `verify_signature` trivially.
- `repository.full_name` = the full name of a **completely different, properly-secured** repository/organization tracked by the same Shipit instance.

Because `Handler#repository_name` uses `repository.full_name`, not `repository.owner.login` [3](#0-2) , the handler resolves and acts on stacks belonging to the *other* organization. `StatusHandler` is the sharpest example: it looks up commits purely `Commit.where(sha: params.sha)` with zero repository/org filtering at all [4](#0-3) , and directly persists attacker-supplied `state`/`description`/`target_url`/`context` via `create_status_from_github!`.

### Impact Explanation
Commit deploy-gating in Shipit is driven by `Commit#deployable?`, which requires `success? && !blocked?` based on the commit's `Status` records [8](#0-7) , and status transitions fire `deployable_status` hooks and `stack.schedule_merges` [9](#0-8) . By exploiting the org-binding gap, an unprivileged attacker who merely knows (a) that some org configured in this Shipit instance has no webhook secret and (b) the sha of a commit in a target stack, can forge a `status` webhook event that flips that commit's CI status to `success` for a repository they have no relationship to. This directly satisfies the "unauthorized deploy" criterion: a commit that never actually passed CI can become `deployable?`, enabling continuous deployment/merge-queue automation to deploy or merge it without any real CI success, GitHub write access, or Shipit credentials. This is a genuine deployment-trust binding break (organization that authenticated ≠ repository/commit that is written) reachable by a pure network POST to an unauthenticated public endpoint.

### Likelihood Explanation
Requires only: (1) knowledge that the operator has configured at least one GitHub org/app in Shipit without a `webhook_secret` — a supported and, per the test fixtures, seemingly common minimal-setup configuration — and (2) the target commit SHA, which is generally public (visible via GitHub, PR pages, or the Shipit UI itself). No GitHub webhook secret, no Shipit session or `ApiClient` token is needed. The attack is a single unauthenticated HTTP POST.

### Recommendation
Enforce that the organization used to select/verify the webhook signature must equal the owner encoded in `repository.full_name` (and in any other repository-identifying field the handler subsequently uses) before dispatching to handlers — i.e., derive a single canonical repository-owner from the verified payload and reject/ignore events where `repository.full_name`'s owner differs from `repository_owner`. Additionally, `StatusHandler` (and any handler resolving records without going through `Handler#stacks`) should scope its lookup by the verified repository, not merely by `sha`. Finally, `GithubApp#verify_webhook_signature` returning `true` when `webhook_secret` is blank should be reconsidered/require an explicit "trust" opt-in per org, since it allows unauthenticated writes for any org lacking a configured secret.

### Proof of Concept
1. Configure (or observe, as an attacker, e.g. via error/log disclosure or default docs) that org `victimless-org` is registered in `Shipit.github_apps` with `webhook_secret: nil` and org `real-target-org/target-repo` has an actively-deployed stack in the same Shipit instance with a `webhook_secret` configured.
2. Find a pending/failing commit `sha` on `real-target-org/target-repo` tracked by Shipit (public GitHub info).
3. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<target commit sha>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "victimless-org" }, "full_name": "real-target-org/target-repo" }
}
```
   No valid `X-Hub-Signature` is required, since `verify_webhook_signature` returns `true` because `victimless-org`'s `webhook_secret` is blank [5](#0-4) .
4. `WebhooksController#create` dispatches to `StatusHandler`, which finds `Commit.where(sha: ...)` (matching `target-repo`'s commit) and calls `create_status_from_github!`, injecting a fabricated `success` status [4](#0-3) .
5. The commit becomes `deployable?` on `real-target-org/target-repo`'s stack despite never having received a real, signed status from that org's GitHub App.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
