### Title
Router routes to unallowlisted, attacker-chosen pool and token addresses, letting a rogue hop contract execute arbitrary code beneath the victim's authorization tree and drain wallet funds - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap aggregator's `execute_strategy` accepts a `swap_xdr` payload whose `assets` registry supplies every pool and token address the router will call, and it keeps no allowlist of those addresses. `dispatch_hop` invokes `hop.pool` directly, so an attacker can point a hop at a malicious contract that performs a `token.transfer(victim, attacker, amount)` inside the route execution. Because the call happens below the caller's `require_auth` entry, the stolen transfer is recorded as a child of the victim's signed authorization tree and executes if the victim signs the simulated tree. This mirrors the SSRF bug class: a user-supplied destination is invoked server-side (contract-side) with ambient authority, and the "globally routable = safe" check is replaced by no check at all.

### Finding Description
`execute_strategy` pulls `total_in` under `sender.require_auth()` and then walks the instruction stream, dispatching each hop to `ctx.hop.pool` and `ctx.hop.token_in`/`token_out` taken from the payload's address registry — `venues::dispatch_hop` calls the venue adapter, which invokes `env.invoke_contract(&ctx.hop.pool, "swap", ...)` and `token::Client::new(&ctx.hop.token_in)` with no whitelist check on either address [1](#0-0) [2](#0-1) . The measured balance-delta checks (`received > 0`, `spent == amount_in`) bound only the routed tokens; they do not constrain what other code the named pool runs while on the stack below the sender's authorization. The threat model confirms there is no allowlist: "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount" [3](#0-2) . The same exposure exists on the composed path: the controller authorizes one exact input transfer to the router and calls `execute_strategy` with the caller-supplied `swap` bytes [4](#0-3) . The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree` proves the mechanism end-to-end: a `RogueHopPool` performing `token.transfer(alice, attacker, WALLET_BALANCE)` is recorded as a child of Alice's `swap_collateral` auth entry, and when signed, her wallet is drained while the swap itself settles normally [5](#0-4) .

### Impact Explanation
Theft of user funds, unbounded by the swap size: the rogue pool can transfer any token the victim holds for which a `transfer(victim, …)` appears under the signed auth tree — the recorded tree attaches it to the victim's entry and enforcing mode accepts it if signed. The victim's routed swap still succeeds with fair output, so the theft is invisible in the swap result itself. Any user of `execute_strategy`, `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` who signs a route crafted by an attacker (e.g., delivered through a compromised or malicious quote, or pasted routeXdr) loses arbitrary wallet tokens in the same transaction.

### Likelihood Explanation
Requires the victim to sign an authorization tree containing the malicious child transfer. An honest client that decodes the route and refuses unexpected children blocks it, and the threat model prescribes exactly that mitigation — but nothing on-chain enforces it, and the payload's packed 5-byte instruction format makes the rogue pool address non-obvious to a wallet UI that only shows `token_in`/`token_out`/`min_out`. A single unprivileged attacker can craft and distribute the malicious route at no cost. Reachable by any authenticated user through normal strategy entrypoints; severity High rather than Critical because exploitation needs victim signature on the poisoned tree.

### Recommendation
Enforce a venue/pool allowlist on-chain: require each `hop.pool` (and each `token_in`/`token_out` in the `assets` registry) to be either a whitelisted token or a pool address registered by the router admin, checked in `Program::decode`/`dispatch_hop` before any `invoke_contract`. Alternatively, constrain hop targets to a registry of adapter-verified pool addresses keyed by the token pair. Until then, the mitigation is purely client-side (decoding the auth tree and rejecting unexpected children), which the test suite demonstrates is the only thing standing between the route and wallet theft.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` [6](#0-5) : `RogueHopPool::swap` calls `token.transfer(victim, attacker, amount)` for an unlisted wallet token. The route names this contract as `hop_pool`; `swap_collateral` → controller `swap_tokens` → router `execute_strategy` → `dispatch_hop` → `invoke_contract(rogue_pool)`. Simulation records the stolen transfer as a sub-invocation of Alice's `swap_collateral` auth entry; when signed, `assert_eq!(wallet(alice), 0)` and `assert_eq!(wallet(attacker), WALLET_BALANCE)` while Alice's ETH supply still receives the fair output [7](#0-6) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
