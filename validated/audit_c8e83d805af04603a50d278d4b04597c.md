## Analog Found

### Title
Asset definer can retroactively change the attestor whitelist to invalidate or steer already-committed payments - (File: validation.js)

### Summary
Obyte (ocore) assets can be configured with `spender_attested: true`, which restricts who may send/receive the asset to addresses that a list of trusted **attestors** have vouched for. The list of attestors is not fixed at asset issuance — it is a live, mutable object that the asset **definer** can update at will via an `asset_attestors` message, with no delay, no notice, and no lock against outstanding payments. Because validation of any pending payment reads the *latest* attestor list available before `last_ball_mci` (i.e., at stabilization time, not at the time the payment was composed and broadcast), the definer can add or remove attestors after a counterparty has already composed and sent a payment relying on the attestor state at that moment. This mirrors the reported bug class exactly: an "owner" (here, the asset definer) can change the distribution of who is eligible to receive/spend value after a user has already committed funds, and can even single out one specific recipient to be the sole eligible party, defeating any implicit "fair" random or first-come allocation the application logic assumes.

### Finding Description
An asset's attestor list is set at issuance and can subsequently be replaced by the definer through the `asset_attestors` message, validated by `validateAttestorListUpdate`, which enforces only that the sender is the asset's definer and that the new attestor set is well-formed — there is no cooldown, no reference to pending transactions, and no restriction based on time or unit content: [1](#0-0) 

When any payment of that asset is validated (`validatePayment`), the code loads the asset via `storage.loadAssetWithListOfAttestedAuthors` / `readAsset`, which queries for the attestor-list unit with the **highest level/MCI** that is stable and precedes `last_ball_mci` — i.e., whatever the current, most recently updated list is at validation time, not whatever it was when the payer composed the transaction: [2](#0-1) [3](#0-2) 

The `asset_attestors` message can be posted at any time by the definer and takes effect for all future spends as soon as it stabilizes: [4](#0-3) 

Because there is no way for the payer to lock the eligibility conditions at the moment of "commit" (broadcasting the payment), a definer who observes a pending, not-yet-stable payment can:
1. Deregister the intended attestor entries that vouch for the counterparty (or the payer), causing the payment to fail final validation ("none of the authors is attested" / "some output addresses are not attested" in `validatePaymentInputsAndOutputs`), effectively freezing/burning the sender's already-broadcast funds since a private payment, once composed, cannot trivially be revised.
2. Register a completely different, definer-chosen address as the sole eligible attestor/recipient right before the transaction stabilizes, redirecting who benefits from a distribution scheme built on top of `spender_attested`, exactly as the original report describes an owner picking winners by manipulating the eligible ID set around the time of a purchase.

### Impact Explanation
This allows the definer of a `spender_attested` asset to unilaterally decide, after the fact, whether a specific user's already-signed and broadcast payment succeeds or is rejected, and to redirect who is treated as an eligible recipient for a shared pool of assets. In an application built on this primitive (e.g., a whitelist sale, allocation, or gated NFT-like distribution), this enables fund freezing for the counterparty (their committed payment becomes permanently unspendable/invalid) or lets the definer bypass any "fair" allocation logic entirely by controlling who is attested at the exact moment of finalization.

### Likelihood Explanation
Any address can issue such an asset and become its definer (this is a normal, permissionless asset-issuance feature), and any user can be induced to transact against it (e.g., in a marketplace/allocation dApp built on top). The definer needs no special privilege beyond being the asset's own definer, and the state change (`asset_attestors`) is a first-class, always-available message type with no timelock, making the manipulation trivially and repeatably reachable by simply racing a new `asset_attestors` unit against the counterparty's pending payment before it stabilizes.

### Recommendation
- Consider requiring a mandatory delay (analogous to the "delayed multisig" fix accepted for the original report) between an `asset_attestors` update and its effect on payment validation, so counterparties can observe upcoming changes before committing funds.
- Alternatively, allow payments to optionally reference/pin a specific attestor-list unit at composition time so that a subsequent change by the definer cannot retroactively invalidate or redirect an already-broadcast transaction.
- Document explicitly, as part of the asset/attestor trust model, that `spender_attested` grants the definer live, uncommitted-transaction-affecting control, so application authors don't build fairness-dependent logic (allocations, sales, etc.) on top of it without additional safeguards.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and an initial attestor list `[X]`, where `X` has attested address `S` (seller).
2. Buyer `B` composes and broadcasts a payment of asset `A` to `S`, relying on `S` currently being attested per the list `[X]`.
3. Before `B`'s payment unit becomes stable, `D` posts an `asset_attestors` message removing `X` (or replacing it with `[Y]` where `Y` has never attested `S`).
4. Once `D`'s update stabilizes and precedes `B`'s payment's `last_ball_mci`, `validatePayment` (via `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`) reports `S` as no longer attested; `B`'s payment fails final validation ("some output addresses are not attested"), freezing `B`'s already-committed funds, while `D` retained full discretion to decide the outcome after `B`'s commitment — mirroring the "owner changes distribution/picks winner after commit" pattern from the original report.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
