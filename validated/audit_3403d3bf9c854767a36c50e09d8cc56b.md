## Finding: Missing WebAuthn ceremony-type (`ClientDataType`) validation in `PartialAuthenticatorAssertionResponse::verify_arbitrary_msg`

### Title
Missing `ClientDataType` (ceremony-type) check in WebAuthn transaction authenticator verification - (File: `types/src/transaction/webauthn.rs`)

### Summary
The production WebAuthn signature-verification routine used for Aptos transaction authenticators deserializes `CollectedClientData` from the attacker-supplied `client_data_json`, but only checks the `challenge` field against the expected transaction hash and then verifies the raw ECDSA signature. It never inspects `CollectedClientData.ty`, so a `client_data_json` whose `type` is `webauthn.create` (registration) is accepted exactly the same as one whose type is `webauthn.get` (assertion).

### Finding Description
`PartialAuthenticatorAssertionResponse::verify_arbitrary_msg` is the function invoked when a `SingleKeyAuthenticator`/`AnySignature::WebAuthn` transaction authenticator is checked (via `AccountAuthenticator::verify` → `SingleKeyAuthenticator::verify` → this function), which is exactly the code path exercised by `signed_txn.check_signature()` before a transaction is admitted (`api/src/tests/webauthn_secp256r1_ecdsa.rs:135`).

The verification logic:
```
let collected_client_data: CollectedClientData =
    serde_json::from_slice(self.client_data_json.as_slice())?;
let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())...
challenge_bytes.as_slice().eq(message).then_some(())...?;
let verification_data = generate_verification_data(...);
match (&public_key, &self.signature) { ... signature.verify_arbitrary_msg(&verification_data, public_key) }
``` [1](#0-0) 

`collected_client_data.ty` (the `ClientDataType` enum, i.e. `Create` vs `Get`) is parsed into the struct but is never compared/asserted anywhere in this function, nor anywhere else in the file (the only other reference to `ty` is inside `collected_client_data_to_json_bytes`, which only re-serializes it, and does not validate it) [2](#0-1) . The genuine WebAuthn spec (§6.3.3, step 11) requires relying parties to check `clientDataJSON.type == "webauthn.get"` during assertion verification; this check is absent here.

The test helper in the repo confirms production code sets `ty: ClientDataType::Get` when constructing client data for transactions [3](#0-2) , but nothing in `verify_arbitrary_msg` enforces that this must be `Get` rather than `Create`.

### Impact Explanation
The signature is computed over `verification_data = authenticator_data || SHA256(client_data_json)` [4](#0-3) , so the `ty` field is cryptographically bound inside the signed material — an attacker without the private key cannot simply flip `ty` on an already-signed payload and still pass signature verification, because that would change `client_data_json` and therefore invalidate the ECDSA signature. This means the "otherwise valid challenge/signature" precondition in the exploit question can only occur if the legitimate keyholder's authenticator actually produced a raw assertion-style signature over `authenticator_data || SHA256(client_data_json{ty:"webauthn.create", challenge:<tx-hash>})`. Real WebAuthn "create" (registration) ceremonies produce an *attestation* object, not this raw signed-blob format, so it is not straightforward to obtain such a signature from a genuine passkey/authenticator in the wild. The missing check is a genuine code-level gap relative to spec (ceremony-type confusion), but demonstrating full exploitability requires an authenticator/environment that can be coerced into producing a registration-ceremony signature in the assertion wire-format Aptos expects — which is outside what this Rust code alone controls.

### Likelihood Explanation
Low-to-moderate: this is a real missing invariant in the code itself (confirmed by reading the full verification path), but it does not on its own let an unprivileged attacker without the private key rebind or replay a transaction, since the ceremony-type field is inside the SHA-256-hashed, signature-covered `client_data_json`. Exploitability depends on being able to coerce a legitimate signer's client/authenticator into signing a "create"-typed payload with the transaction hash as challenge — a client/browser-side condition not enforced or preventable purely from this Move/Rust admission code.

### Recommendation
Add an explicit check in `verify_arbitrary_msg` that `collected_client_data.ty == ClientDataType::Get`, rejecting the signature with `CryptoMaterialError::ValidationError` otherwise, matching WebAuthn §6.3.3 step 11's relying-party requirement.

### Proof of Concept
Modify the existing test helper `get_collected_client_data` in `api/src/tests/webauthn_secp256r1_ecdsa.rs` [5](#0-4)  to set `ty: ClientDataType::Create` instead of `ClientDataType::Get`, keep the challenge/signature construction identical (sign the resulting `client_data_json` with the real private key), and call `signed_txn.check_signature()` / `verify_arbitrary_msg`. Since no code path checks `ty`, verification succeeds despite the ceremony-type mismatch, which can be asserted directly in a unit test against `types/src/transaction/webauthn.rs`'s `verify_arbitrary_msg`.

    pub fn verify_arbitrary_msg(&self, message: &[u8], public_key: &AnyPublicKey) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        challenge_bytes
            .as_slice()
            .eq(message)
            .then_some(())
            .ok_or(CryptoMaterialError::ValidationError)?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
