### Title
Cross-stack CI status disclosure via `Api::CCMenuController#stack` bypassing `current_api_client.stack_id` scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` enforces per-client stack scoping through a private `stacks` method that restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and its `stack` method resolves `params[:stack_id]` through that scope. `Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, silently dropping the scoping boundary for the CC Menu CI-status endpoint.

### Finding Description
The claimed binding is: `stack_id` resolved in a controller action ∈ `current_api_client.stack_id`'s authorized set, i.e. for any stack-scoped `ApiClient` C with `C.stack_id = A`, resolving `params[:stack_id] = B` (B ≠ A) must fail.

In `Api::BaseController`: [1](#0-0) 
`stacks` restricts to the client's own stack when `stack_id?` is set, and `stack` resolves through that restricted relation, so `stacks.from_param!(params[:stack_id])` raises `ActiveRecord::RecordNotFound` for any stack outside the client's authorized set.

`Api::CCMenuController` overrides this private `stack` method: [2](#0-1) 
Since Ruby method resolution picks the subclass method, `Api::CCMenuController#show` (line 22-25) calls this overridden `stack`, which queries `Stack.from_param!` against the entire `Stack` table — the client-stack scope from the base class is never invoked.

The only remaining gate is `require_permission :read, :stack` (line 6), which triggers `check_permissions!`: [3](#0-2) 
This checks only whether the string `"read:stack"` is present in the client's `permissions` array — it performs no comparison against `stack_id` or the requested stack at all. So a client created via `Api::ApiClientsController` with `stack_id: A.id` and `permissions: ["read:stack"]` (a token meant to only ever see stack A) can supply any `stack_id` for stack B in the CC Menu request and successfully render B's CI status.

Existing guards (`authenticate_api_client`, `require_permission!`, model validations) all pass because none of them re-check stack scope; the base class's `stacks` scoping is the sole enforcement point and it is simply never reached from this controller.

### Impact Explanation
An attacker holding any `read:stack`-scoped API token — even one explicitly restricted by an operator to a single stack — can query `GET /api/stacks/:stack_id/cc.xml?token=...` for an arbitrary stack ID belonging to any other repository/stack in the same Shipit instance and receive that stack's CI/deploy status (project name, last build status/label/time, web URL) rendered in `shipit/ccmenu/project`. This is a cross-tenant authorization bypass of the one scoping mechanism `Api::BaseController#stacks` exists to provide, is fully repeatable against any stack id in the system, and constitutes unauthorized read of stack state across the authorization boundary an operator relies on when issuing stack-restricted tokens.

### Likelihood Explanation
Preconditions are minimal and match a normal, supported Shipit configuration: an operator issues a stack-scoped `ApiClient` (a common practice to limit blast radius of a leaked token) with `read:stack` permission. No GitHub secrets, webhook secrets, or session access are needed — only the legitimately issued token the attacker already holds for their own stack. The request is a single unauthenticated (aside from the token) GET with a trivial parameter change (`stack_id`), so cost is negligible and it is trivially repeatable against every stack in the installation.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it via the inherited `stacks.from_param!(params[:stack_id])`) so that CI-status lookups honor the same per-client stack scoping enforced by `Api::BaseController`.

### Proof of Concept
minitest plan (in `test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` (distinct stacks/repositories).
2. Create an `ApiClient` scoped to `stack_a`: `client = ApiClient.create!(creator: user, name: 'scoped', stack_id: stack_a.id, permissions: ['read:stack'])`.
3. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
4. Assert on the binding: expected (base-class behavior) `stacks.from_param!('stack_b')` should raise `ActiveRecord::RecordNotFound` → `assert_response :not_found`.
5. Actual behavior via `Api::CCMenuController#stack`: `assert_response :ok` and `assert_payload 'name', stack_b.to_param`, proving `stack_b`'s CI status is disclosed despite the client's `stack_id` being `stack_a.id`.
