### Title
Webhook signature verification is bound to `repository.owner.login`, but stack/action resolution is bound to a different, unverified `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
This is the same bug class as the report: a security decision (whether to trust/act on a request) is gated on one field, while the actual state-changing operation is driven by a *different* field of the same attacker-supplied payload that is never cross-checked against the first. In `AcrossSwapHandler`, the gate is `fillCompleted` while the amount acted upon (`amount`) is not re-validated against the total transfer intended. In Shipit, the gate is "does the HMAC signature match the secret for the organization named in `repository.owner.login`", while the object actually mutated (which `Stack`/`Repository` receives the event) is selected using `repository.full_name`, a sibling field in the very same JSON body that is never checked for consistency with `repository.owner.login`.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against, based on `repository_owner`:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [4](#0-3) 

Once the signature is accepted, `create` dispatches the same raw payload to handlers, all of which resolve the target `Repository`/`Stack` using a *different* field:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`Shipit.github(organization:)` supports fully independent multi-tenant configuration, each organization with its own `webhook_secret`, `app_id`, `private_key`, etc.:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [1](#0-0) 

The binding that should hold is: **organization authenticated (`repository.owner.login`) == repository written (`repository.full_name`'s owner segment)**. Nothing in `verify_signature` or in `Handler#repository_name` enforces this equality — the two fields are read independently from the same untrusted, attacker-constructed JSON body, exactly like `handleAcrossMessage` trusting `amount` without tying it to the fill state that was actually checked.

An attacker who legitimately controls a GitHub organization/app already registered with this multi-tenant Shipit instance (i.e., they know their own org's `webhook_secret`, having configured their own GitHub App/webhook themselves) can:
1. Construct an arbitrary JSON body with `repository.owner.login` set to *their own* org (so `Shipit.github(organization: ...)` picks their own known secret) but `repository.full_name` set to `"victim-org/victim-repo"` (any other org/repo already registered on the same Shipit instance).
2. Sign the raw body with their own known `webhook_secret` and POST it to the shared `/github/webhooks` endpoint.
3. `verify_signature` succeeds because it only checks the signature against their own org's secret, using `repository.owner.login`, which the attacker deliberately set to a value that matches secret they hold.
4. The event handler (e.g. `PushHandler`, `CheckSuiteHandler`) then acts on `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, i.e. the *victim's* stack, not the attacker's own.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" boundary explicitly called out as Critical. Depending on which handler processes the event, an attacker who owns one tenant on a shared Shipit instance can trigger actions against stacks belonging to a completely different, unrelated GitHub organization/repository that they have no access to — for example forcing `Stack#sync_github` to run with an attacker-chosen `expected_head_sha` via `PushHandler` [6](#0-5) , or triggering `RefreshCheckRunsJob` on arbitrary victim commits via `CheckSuiteHandler` [7](#0-6) . Since the merge queue and CI-gating logic in `MergeRequest`/`Stack` (`deployable?`, `reject_unless_mergeable!`) rely on status/commit state that these webhook handlers write [8](#0-7) , poisoning this state on a victim's stack can influence automated deploys/merges on repositories the attacker does not own.

### Likelihood Explanation
Requires the attacker to control at least one organization/app tenant already configured on a shared, multi-org Shipit deployment (a configuration explicitly supported and tested, per `secrets_double_github_app.yml`) [9](#0-8) . This does not require a Shipit session, `ApiClient` token, GitHub App private key theft, or any privileged account on the victim's org — only knowledge of the attacker's own legitimately-configured webhook secret, which they set up themselves. On single-tenant deployments (single global `secrets.github` config, no per-org keys) this is moot because `repository_owner` is unused for secret selection (`github_default_organization` returns `nil`) [10](#0-9) , so likelihood is confined to genuinely multi-tenant setups.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), assert that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (the field used to select the signing secret) before processing, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit in multi-org mode with `secrets.github: { OrgA: {webhook_secret: "secretA", ...}, OrgB: {...} }`, and register stacks for both `OrgA/repoA` and `OrgB/repoB`.
2. As the operator/owner of `OrgA` (who legitimately knows `secretA`), craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/repoB", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(secretA, raw_body)`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully using `secretA` [11](#0-10) .
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/repoB"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack [6](#0-5)  — an action the `OrgA` attacker was never authorized to trigger.
