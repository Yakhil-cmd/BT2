### Title
Webhook signature verification is scoped by an attacker-controlled organization field decoupled from the repository/team the event actually mutates, allowing unauthenticated forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on an attacker-supplied field in the unauthenticated request body (`repository.owner.login` / `organization.login`), while the event handlers that actually mutate state key off a *different* field in the same body (`repository.full_name`). Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured — an explicitly documented, supported configuration — an attacker can pick an organization slot with no secret to satisfy signature verification, then set `repository.full_name` (or `team`/`organization`/`member` fields for the `membership` event) to target any repository or team tracked by the Shipit instance. This breaks the equality: `organization used to authenticate the request == organization/repository the handler writes to`.

### Impact Explanation
An unauthenticated, unprivileged attacker who can reach the public `/webhooks` endpoint (no session, no `ApiClient` token, no repository access required — it is a bare `ActionController::Base` action with CSRF disabled) can:
1. Choose, as `repository.owner.login`/`organization.login`, any configured GitHub organization slot that has `webhook_secret` unset (a supported, common configuration shown in the shipped example secrets files) — signature check then passes unconditionally.
2. Set `X-Github-Event: membership` and craft `team`/`organization`/`member` fields naming a team handle that is present in `Shipit.github_teams` (the authorization allow-list) and a `member.login` equal to their own real GitHub login.
3. The handler creates the `Team`/`Membership` records, satisfying `User#authorized?` for that login.
4. The attacker then completes the real, legitimate GitHub OAuth flow with that same GitHub identity and is granted access as if they were a genuine member of the authorized team — an authorization-bypass escalation into `Shipit.github_teams`, one of the explicitly listed High-severity impacts.

The same decoupling also lets the attacker forge `push`/`status`/`check_suite` events against any tracked repository (by supplying its `full_name`) while authenticating the request under an unrelated, secret-less organization, causing unauthorized `GithubSyncJob` enqueues and forged commit statuses for stacks the attacker has no real access to.

### Likelihood Explanation
Requires only that the Shipit deployment define more than one GitHub App/organization entry (the documented multi-org configuration) and that at least one of them omits `webhook_secret` — a state the shipped example/secrets templates present as normal and valid. No credentials, tokens, or prior repository access are needed to reach or exploit the endpoint itself.

### Recommendation
- Verify the webhook signature using the secret associated with the *actual* target repository/organization (i.e., derive it from `repository.full_name`, not from a separately attacker-suppliable field), or require every configured organization to have a mandatory, non-blank `webhook_secret`.
- Reject webhooks whose `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`.
- Do not allow `verify_webhook_signature` to return `true` when no secret is configured; fail closed instead.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "org-with-no-webhook-secret" },
  "team": { "id": 999, "name": "Authorized Team", "slug": "authorized-team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" },
  "repository": { "full_name": "org-with-no-webhook-secret/whatever" }
}
```
* `verify_signature` resolves `Shipit.github(organization: "org-with-no-webhook-secret")`; since that entry's `webhook_secret` is blank, `verify_webhook_signature` returns `true` with no signature required (`lib/shipit/github_app.rb:76-83`).
* The `membership` handler creates the `authorized-team` team (if it matches an entry in `Shipit.github_teams`) and adds `attacker-github-login` as a member (behavior verified via `test/controllers/webhooks_controller_test.rb:129-165`).
* The attacker then logs in through the real GitHub OAuth flow as `attacker-github-login`; `User#authorized?` now returns `true`, granting them access gated by `Shipit.github_teams`.

Note: I could not locate the exact `membership` handler source file in the index (only its behavior via `webhooks_controller_test.rb`); its precise field-mapping should be confirmed directly in `app/models/shipit/webhooks/handlers/membership_handler.rb` (not returned by search) before remediation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
