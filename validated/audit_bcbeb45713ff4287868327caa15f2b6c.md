### Title
Organization-Scoped Webhook Signature Verification Does Not Bind to the Repository Acted Upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook using the GitHub App/secret configured for the organization taken from `repository.owner.login` (or the fallback `organization.login`), but the handlers that actually mutate state look up the target `Repository`/`Stack` using a *different* JSON field, `repository.full_name`. Because the HMAC signature only proves that the request was signed with the secret belonging to whichever organization's App the attacker controls (not that the `full_name` field matches that same organization), an attacker who controls one onboarded GitHub organization's webhook secret can craft a payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a different organization/repository, causing Shipit to act on a repository the attacker does not control.

### Finding Description
Signature verification is done here: [1](#0-0) 

The organization used to select which App/secret validates the signature is derived from: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp` instance, each configured with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the request passes this per-organization signature check, `create` dispatches the parsed JSON `params` to every registered handler for the event, unmodified: [5](#0-4) 

However, the handlers resolve the actual target `Repository` using `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

This is used directly by `PushHandler` (which triggers `stack.sync_github`): [7](#0-6) 

and by pull-request handlers that create/mutate review stacks based on `params.repository.full_name`: [8](#0-7) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being written to**. Because the signature only covers the raw payload bytes against one specific organization's secret, and the controller derives *which* secret to use from a field (`repository.owner.login`) that is independent from the field the handlers actually trust (`repository.full_name`), any org whose webhook secret is known (i.e., any organization onboarded to this Shipit instance, since the app owner/admin of that org's GitHub App knows/controls that secret) can produce a validly-signed payload whose `full_name` names a stack belonging to a *different* onboarded organization/repository.

Concretely, before/after the attack:
- Before: attacker's org "attacker-org" owns a GitHub App installation with webhook secret `S_attacker`. A legitimate `push`/`pull_request` webhook for "victim-org/victim-repo" is signed with `S_victim` and has `repository.owner.login == "victim-org"` and `repository.full_name == "victim-org/victim-repo"`.
- After: attacker crafts a JSON body with `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) but `repository.full_name = "victim-org/victim-repo"`, `ref`, `after`, etc. pointing at whatever they want synced/deployed. They sign the raw body with `S_attacker` (which they know) and send `X-Hub-Signature: sha1=...`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully because the signature matches `S_attacker` over that exact payload. The handler then acts on `victim-org/victim-repo` because it reads `full_name`, not `owner.login`.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," enabling an attacker who controls one onboarded organization's GitHub App/webhook secret to forge webhook events (e.g. `push`, `pull_request`) that Shipit will apply to a stack/repository belonging to a different organization. Depending on handler, this can force a `Stack#sync_github` on an unrelated repository (affecting deploy state/commit tracking) or create/manipulate review stacks (`PullRequest::ReviewStackAdapter`) for a repository the attacker does not own — a cross-repository write triggered without possessing that repository's own webhook credential.

### Likelihood Explanation
Exploitability requires the attacker to be an onboarded organization with a legitimately configured GitHub App/webhook secret in this multi-tenant Shipit instance — i.e., an "unprivileged" attacker relative to the *target* repository, but a party trusted for their *own* organization. Any Shipit deployment servicing more than one organization is affected, since `Shipit.github(organization:)`/`GithubApp` explicitly supports per-organization configuration and secrets and the controller derives the verifying org from attacker-controlled JSON. Because the fields used for verification and for dispatch diverge (`owner.login` vs `full_name`), no additional privilege beyond "own one onboarded org's webhook secret" is needed to name an arbitrary victim repository in `full_name`.

### Recommendation
Bind the verified organization to the repository actually acted upon: after verifying the signature, re-derive `repository_name`/target `Repository` from the same trusted context used for signature verification (e.g., require `repository.full_name`'s owner segment to equal `repository_owner`, or resolve the target repository via the verified organization's own repository list) and reject the webhook if they diverge. Alternatively, verify webhook signatures using a secret keyed by the exact `repository.full_name` (or the `Repository` record itself) rather than by `repository.owner.login`/`organization.login`, so the field trusted for authentication and the field trusted for mutation are the same value.

### Proof of Concept
1. Onboard Shipit to two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and webhook secret (`S_attacker`, `S_victim`) as supported by `Shipit.github(organization:)`.
2. Attacker builds a JSON payload for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` since they know `S_attacker`.
4. POST to `/webhooks` with headers `X-Github-Event: push` and the computed signature.
5. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which succeeds because the signature matches `S_attacker`.
6. `PushHandler#process` (or a pull-request handler) executes using `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, causing Shipit to run `stack.sync_github(expected_head_sha: params.after)` (or create/mutate a review stack) for `victim-org/victim-repo`, a repository the attacker does not own.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
