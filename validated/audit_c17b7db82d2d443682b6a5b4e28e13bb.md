### Title
Missing non-zero validation of EVM `target_address` in `bridge::send_token`/`send_token_v2` causes permanent, unrecoverable burning of bridged tokens - (File: crates/sui-framework/packages/bridge/sources/bridge.move)

### Summary
`bridge::bridge::send_token` and `send_token_v2` — the public, unprivileged entry points a Sui token holder calls to bridge assets to Ethereum — validate only the *length* of the destination EVM address (`target_address.length() == EVM_ADDRESS_LENGTH`) but never validate that the address is non-zero. The Sui-side coin is immediately burned/escrowed in the treasury before the destination is ever checked by anyone else, so a caller supplying the null EVM address `0x000...0` (a valid 20‑byte value) causes an unrecoverable loss of funds — the same missing-non-zero-address root cause described in the Linea `initialize`/`fallbackOperator` report, here applied to a value-bearing address rather than a config address.

Once the message is relayed and approved on the EVM side, `SuiBridge.sol`'s `transferBridgedTokensWithSignatures` decodes the same unchecked `recipientAddress` from the payload and forwards it directly to `_transferTokensFromVault` with no zero-address check either: [4](#0-3) 

For the mirror ETH→Sui direction, `bridgeERC20` also only validates the *length* of the Sui-side `recipientAddress`, not that it is non-zero: [5](#0-4) 

### Impact Explanation
This qualifies as "unintended permanent burning below the 10B cap" / permanent fund lock (High/Medium allowed impact): the bridged coin is unconditionally burned from Sui treasury supply the moment `send_token`/`send_token_v2` is called, before any recipient validation happens off-chain. If the destination is the null address (0x0…0), the corresponding minted/unlocked value on the EVM side is unrecoverably lost to `address(0)` (or, depending on committee/relay behavior, the transfer may simply never be honored, permanently locking the burned value with no path to recovery on either chain). This is triggerable entirely by an unprivileged, ordinary SUI/bridged-asset holder — no validator, admin, or governance quorum involvement is required, satisfying the attacker model constraints.

### Likelihood Explanation
High likelihood: `send_token`/`send_token_v2` are `public fun`s callable by any address holding a bridgeable coin type; no special permission or unusual gas cost is required. The zero-address value trivially satisfies the only enforced constraint (`length() == EVM_ADDRESS_LENGTH`), and the existing test (`test_execute_send_token`) demonstrates this exact input passes validation without any additional guard. This could occur accidentally (e.g., a wallet/dApp bug that defaults an unset address field to zero) or be triggered deliberately.

### Recommendation
Add an explicit non-zero validation for `target_address` (and, symmetrically, for `recipientAddress` in `SuiBridge.sol`'s `bridgeERC20` and `BridgeUtils.decodeTokenTransferPayload`/`transferBridgedTokensWithSignatures`) before burning/escrowing funds, e.g.:
```
assert!(target_address != x"0000000000000000000000000000000000000000", EInvalidEvmAddress);
```
This should be enforced both in `bridge.move::send_token`/`send_token_v2` prior to `send_token_internal` (before the burn) and in the corresponding EVM contracts prior to any vault transfer, closing the same class of missing-non-zero-address validation described in the referenced Linea finding.

### Proof of Concept
1. An ordinary Sui user holding a bridgeable coin `T` calls `bridge::send_token<T>(bridge, target_chain, x"0000000000000000000000000000000000000000", coin, ctx)`.
2. `assert!(target_address.length() == EVM_ADDRESS_LENGTH, ...)` passes because the zero address is exactly 20 bytes.
3. `send_token_internal` immediately calls `inner.treasury.burn(token)`, destroying the user's coin on Sui.
4. The bridge message with `target_address = 0x0` is committed and, once relayed and approved by the committee, `SuiBridge.sol::transferBridgedTokensWithSignatures` calls `_transferTokensFromVault(... , tokenTransferPayload.recipientAddress /* == address(0) */, ...)`, sending the equivalent ERC20 value to the null address with no revert.
5. Funds are burned on Sui and unrecoverable/misdirected on Ethereum — permanent loss, reproducible by the existing repo test `test_execute_send_token` in `crates/sui-framework/packages/bridge/tests/bridge_tests.move:260-268`, which already demonstrates the zero-address path succeeds without any guard.

public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}
