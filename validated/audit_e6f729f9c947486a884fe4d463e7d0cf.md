### Title
Cyclic address-definition graph in `validateAuthentifiers` causes unbounded recursion during signature verification - (File: definition.js)

### Summary
`definition.js` implements two separate recursive walkers over an address's spending-condition tree: `validateDefinition()`'s `evaluate()` (lines 103-619), which enforces `MAX_COMPLEXITY`/`MAX_OPS` limits, and `validateAuthentifiers()`'s own `evaluate()` (lines 648-854), which performs the actual authentifier/signature checking and recurses into nested addresses via the `'address'` op (line 774-799) with **no complexity, op-count, or visited-set tracking of its own**.

### Finding Description
When a definition contains `['address', other_address]`, both evaluators call `storage.readDefinitionByAddress()` to fetch `other_address`'s current definition and recurse into it (`definition.js:279-303` for `validateDefinition`, `definition.js:774-799` for `validateAuthentifiers`). Because an address is only a hash-commitment (chash) of its *own* top-level definition, not of the definitions of any addresses it references by `['address', X]`, address X's definition can be independently redefined at any later point (via a `definition_change` message controlled by X's owner) to reference back to the original address, or to a longer chain that eventually loops back. The code comment at `definition.js:1449-1452` explicitly acknowledges this risk: *"redefinition of a referenced address might introduce loops that will drive complexity to infinity"* — and the intended mitigation is that `validateAuthentifiers()` always calls `validateDefinition()` first (`definition.js:1454`) to bound the walk by `MAX_COMPLEXITY`/`MAX_OPS` before doing the actual (unbounded) authentifier walk.

This relies on `validateDefinition()`'s complexity accounting being a perfect proxy for the depth/branching of the second, authentifier-checking walk. Both walkers independently call `storage.readDefinitionByAddress()` for the *current* on-chain definition of the referenced address at validation time, so if the reference graph is mutated (via legitimate `definition_change` messages posted between the two evaluations, or race conditions across MCI progression) so that it contains a cycle by the time `validateAuthentifiers()` runs, the second walker has no independent depth or complexity limit of its own, no visited-address tracking, and will recurse until a stack overflow / resource exhaustion, or indefinitely if broken by async DB calls (each `'address'` step issues an async `conn.query` via `readDefinitionByAddress`, so a cycle becomes an unbounded chain of DB round-trips rather than a synchronous stack overflow, but is unbounded in wall time and resource consumption either way).

### Impact Explanation
An attacker who controls (or colludes across) two or more addresses can construct a `sig`-bearing definition tree with a nested `['address', X]` reference, and later redefine `X` (a normal, unprivileged `definition_change`/`author.definition` operation) to point back into the cycle. Any unit or signed message (light wallet `is_valid_signed_package`, `signed_message.js`) that must be validated against such an address definition will hit the unbounded `validateAuthentifiers` walk, causing excessive CPU/DB load or a crash of the validating node/witness while processing an ordinary unprivileged unit — a client-side/validator resource-exhaustion condition analogous to the ORAS cyclic-referrer bug.

### Likelihood Explanation
This requires the attacker to control the referenced address's definition update path and to time a redefinition so a cycle exists when `validateAuthentifiers` (not `validateDefinition`) walks the tree — the two functions are called from different code paths at different times (validation of the unit that spends from the address vs. validation of past states), so a strict guarantee that `validateDefinition`'s complexity check always precedes and matches the exact graph seen by `validateAuthentifiers` could not be fully confirmed from the available code; the codebase's own comment suggests the developers considered this attack surface non-trivial to close. However, `readDefinitionByAddress`'s exact caching/staleness semantics and whether `validateDefinition` is unconditionally re-run with the identical resolved graph on every `validateAuthentifiers` invocation could not be fully verified within the available index — this is an area requiring closer, full-file review (e.g., a live Devin session) to confirm whether the "re-validate every time" mitigation fully closes the gap or only narrows the window.

### Recommendation
Add an explicit cycle/depth guard (a `Set` of visited addresses passed through the recursion, or a hard recursion-depth counter) directly inside `validateAuthentifiers()`'s `evaluate()` for the `'address'` op, independent of whatever `validateDefinition()` computed, so the authentifier-checking walk itself cannot exceed a bounded number of nested address dereferences regardless of when/how the underlying definitions were last changed.

### Proof of Concept
Conceptual (not fully executable from the index alone): 
1. Address A is defined as `["address", B]` wrapping a `sig` at the leaf, with B's initial definition as a plain `sig`.
2. After A is established and referenced by outputs/authors, the owner of B posts a `definition_change` redefining B as `["address", A]`.
3. A unit or signed message authored by/spending A is submitted for validation, triggering `validateAuthentifiers(..., address=A, ...)` → `evaluate(['address', B])` → reads B's (new) definition → `evaluate(['address', A])` → reads A's definition → back to `['address', B]`, looping through repeated async `storage.readDefinitionByAddress` calls with no visited-set or depth cap in this function.
