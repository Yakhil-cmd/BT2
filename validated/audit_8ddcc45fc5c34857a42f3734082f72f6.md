### Title
Unscoped `status` webhook allows cross-repository CI-state injection - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` selects commits with a bare `Commit.where(sha: params.sha)`, with no filter on the repository that produced the webhook, unlike sibling handlers (`CheckSuiteHandler`, `PushHandler`) which scope through the `stacks` helper (itself derived from `payload.dig('repository', 'full_name')`). Any commit row in any tenant's stack that happens to share the SHA in the payload gets its GitHub status updated and can trigger continuous delivery for that tenant.

### Finding Description
The broken binding: the handler assumes `commit.sha == params.sha ⇒ commit belongs to repository == payload['repository']['full_name']`, but nothing in the code enforces the right-hand side.

Trace:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw JSON payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers.
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the payload is validly signed by GitHub for `repository_owner` — i.e., the *organization present in the attacker's own payload*. Since the attacker owns/controls that repository, they can legitimately obtain a validly-signed `status` webhook for their own repo. This check does nothing to prevent the payload's `sha` from referring to another tenant's commit.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  There is no `repository_name`/`stacks` scoping check here, unlike `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17, which restricts to `stacks.where(branch: ...)` before touching commits) or `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17, scoped via `stacks`).
- `Commit#create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) writes a new `Status` row, recomputes `status`, and — critically — calls `stack.schedule_merges` and, via the `after_commit`/state-change chain, `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287) enqueues `ContinuousDeliveryJob.perform_later(stack)` if `deployable? && stack.continuous_deployment? && stack.deployable?`.
- The `Commit` model has no `repository_id`; it is only tied to a repository indirectly via `belongs_to :stack`. Multiple unrelated tenants (different repositories, different owners) can end up with `Commit` rows sharing the same `sha` if a commit with identical tree/parents/metadata (e.g., an exact cherry-pick or empty-commit reproduction) is pushed into both repos and each repo's `PushHandler`/sync process creates a `Commit` row for it in its own stack.

Attacker exploit: attacker crafts (or reproduces) a commit whose SHA is identical to a target tenant's commit (achievable when full commit metadata — tree, parent, author/committer identities and timestamps, message — is known/reproducible, e.g. from a public source repo), pushes it to their own repo (generating a legitimate signed `push` webhook that creates an attacker-owned `Commit` row with that SHA), then sends (or has GitHub CI send) a `status` webhook for their own repo with `sha` = that SHA and `state: "success"`. `verify_signature` passes because it is a real, correctly-signed webhook for the attacker's own repository. `StatusHandler#process` then updates **every** `Commit` row across **all** tenants sharing that SHA, including the victim's, potentially flipping the victim commit to "success" and firing `ContinuousDeliveryJob` for the victim's stack.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate only that the request is a genuine GitHub webhook for the attacker's own organization/repo and that the payload shape is correct — none of them check that the resolved `Commit` rows actually belong to a stack tracking the repository named in the payload.

### Impact Explanation
A payload legitimately authenticated for one repository can mutate CI state (`Status`) and trigger `Continuous DeliveryJob` (deploy) for a completely different tenant's stack/commit, without that tenant's repository ever producing the status event. This matches the Critical criteria: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". Blast radius is any tenant whose commit SHA can be matched/collided by an attacker; repeatable per colliding SHA per request.

### Likelihood Explanation
Requires: (1) attacker controls a GitHub repo capable of emitting real, signed `status` webhooks (any GitHub user with a repo — low bar), and (2) attacker can produce/discover a commit whose SHA exactly matches a target's commit — feasible when the target's repository/commit metadata (tree, parent, author/committer name+email+timestamp, message) is public/knowable, e.g. via cherry-pick of a public commit or reproducing an empty commit with identical metadata. No Shipit credentials, sessions, or GitHub App secrets are needed. Feasibility is nontrivial (exact metadata reproduction) but demonstrated as the class of attack Immunefi rates Critical for this bug class, and is fully reproducible in a controlled minitest without live GitHub by directly seeding two `Commit` rows with the same `sha` in different stacks/repositories and invoking `StatusHandler.call`.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks of the repository that produced the webhook, mirroring `CheckSuiteHandler`/`PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (derived from `payload.dig('repository', 'full_name')`) in `Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38).

### Proof of Concept
minitest plan (no live GitHub):
1. Create two `Repository`/`Stack` pairs in different "repos" (`attacker/repo`, `victim/repo`).
2. Create a `Commit` with `sha: "deadbeef..."` under the victim's stack, status currently `pending`/`unknown`, `stack.continuous_deployment?` stubbed `true`, `stack.deployable?` stubbed `true`.
3. Create a second `Commit` with the *same* `sha` under the attacker's stack.
4. Build a `status` payload: `{ "sha" => "deadbeef...", "state" => "success", "context" => "ci", "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker" } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since signature check is orthogonal/already passes for attacker's own repo).
6. Assert: victim commit's `status.success?` becomes `true` and `ContinuousDeliveryJob` was enqueued for the **victim's** stack — proving the equality `commit.sha == params.sha ⇒ commit.stack.repository == payload.repository` is false, and that the victim's stack state changed as a result of a payload it never authenticated.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
