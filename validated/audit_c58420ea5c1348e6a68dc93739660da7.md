## Finding

### Title
Hookify tool matching only recognizes hardcoded tool names (Bash/Edit/Write/MultiEdit), allowing block rules to be silently bypassed via other tools (e.g. NotebookEdit, MCP tools) - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine.evaluate_rules` relies on `_rule_matches` → `_check_condition` → `_extract_field` to determine whether a rule's condition fires, but `_extract_field` only recognizes tool names literally equal to `'Bash'`, `'Write'`, `'Edit'`, or `'MultiEdit'`. The same hardcoded set is used upstream in `pretooluse.py`/`posttooluse.py` to pick an `event` bucket (`bash`/`file`) for `load_rules`. Any other tool that performs an equivalent dangerous action (e.g. Claude Code's built-in `NotebookEdit` tool, or any MCP tool such as `mcp__filesystem__write_file`) falls outside every recognized branch, so field extraction returns `None`, all conditions fail, and even a `block` rule that matches the intended pattern for Bash/Edit/Write never fires for that operation.

### Finding Description
`pretooluse.py` derives the rule-loading `event` purely from `tool_name`:
```python
if tool_name == 'Bash':
    event = 'bash'
elif tool_name in ['Edit', 'Write', 'MultiEdit']:
    event = 'file'
``` [1](#0-0) 

If `tool_name` is anything else (`NotebookEdit`, any `mcp__*` tool, or a future built-in tool), `event` stays `None`, so `load_rules(event=None)` loads *every* enabled rule regardless of its configured `event` [2](#0-1) . This alone is benign, but combined with `_extract_field`'s hardcoded dispatch it becomes a silent bypass:

```python
if tool_name == 'Bash':
    if field == 'command':
        return tool_input.get('command', '')
elif tool_name in ['Write', 'Edit']:
    ...
elif tool_name == 'MultiEdit':
    ...
return None
``` [3](#0-2) 

Because no branch exists for any other tool, `_extract_field` returns `None` for every configured field (`command`, `file_path`, `new_text`, etc.). In `_check_condition`, `field_value is None` immediately returns `False` [4](#0-3) , which propagates to `_rule_matches` returning `False` for every condition-based rule [5](#0-4) . `evaluate_rules` therefore finds no `blocking_rules` and returns `{}` (i.e., allow) even though a `block` rule with a matching pattern exists for that content [6](#0-5) .

`NotebookEdit` is confirmed as a real, recognized built-in Claude Code tool elsewhere in the repo (e.g. `plugins/security-guidance/hooks/hooks.json` and `security_reminder_hook.py` explicitly handle it), yet hookify never accounts for it, nor for any MCP-provided file/command tool. Since Hookify's own optional `tool_matcher` field is a plain exact/`|`-split string comparison (`_matches_tool`) [7](#0-6)  with no wildcard/regex-by-default and is rarely configured by rule authors (per the plugin's documented rule format which only exposes `event`/`pattern`/`conditions`), the effective enforcement surface for a "protective" block rule (e.g., blocking edits to `.env`, blocking `rm -rf`) is limited to exactly the tool names hardcoded in `_extract_field`.

An attacker who can influence which tool Claude selects to perform an action — via prompt injection in repository content, issue/PR text, or other ingested content that the agent reads — can steer the agent toward `NotebookEdit` or an installed MCP tool (e.g., a filesystem or git MCP server) to write to a protected file or run an equivalent dangerous mutation, and the Hookify block rule the maintainer relies on will not fire, because tool matching/field extraction only recognizes one fixed representation of "edit a file" or "run a command."

### Impact Explanation
A maintainer-authored `block` rule intended to reliably deny a dangerous operation (e.g., editing `.env`/credential files, or running destructive shell commands) can be silently bypassed whenever the equivalent action is carried out through a tool other than `Bash`/`Write`/`Edit`/`MultiEdit` — most notably `NotebookEdit` or any MCP-provided tool. This breaks the stated invariant that "a matching block rule must reliably deny the protected operation," enabling wrong-target file mutation, secret file tampering, or unintended command execution that the user believed was guarded, consistent with the Immunefi impact category "Cross-repo, cross-session, or wrong-target mutation with real security impact."

### Likelihood Explanation
This requires the victim to (a) have configured a Hookify `block` rule to protect a file/command class, and (b) be operating with an installed alternate tool (built-in `NotebookEdit`, or any MCP server) and be exposed to attacker-influenced content (repo files, PR/issue text) that can steer tool choice — a common and already-accepted agentic-injection vector. No admin/maintainer privilege, leaked credentials, or social engineering beyond ordinary prompt injection is needed, and the bug is deterministic and 100% reproducible once the alternate tool path is taken.

### Recommendation
Replace the hardcoded tool-name dispatch in `_extract_field` (and the `event` derivation in `pretooluse.py`/`posttooluse.py`) with a generic, tool-agnostic field-extraction strategy: extract `command`/`file_path`/`content`-like fields directly from `tool_input` keys present (already partially done at the top of `_extract_field` via `if field in tool_input`) rather than gating on an enumerated `tool_name` allowlist, and ensure `event` classification for `file`-type rules is based on capability (does `tool_input` contain `file_path`/`new_string`/`content`?) rather than a fixed tool name list, so that `NotebookEdit`, MCP tools, and any future built-in tool are covered by the same block rules as `Bash`/`Edit`/`Write`/`MultiEdit`.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules` directly:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-env-edit",
    enabled=True,
    event="file",
    action="block",
    conditions=[Condition(field="file_path", operator="regex_match", pattern=r"\.env$")],
    message="Blocked edit to .env file"
)
engine = RuleEngine()

# Baseline: Edit tool on .env is correctly blocked
edit_input = {"hook_event_name": "PreToolUse", "tool_name": "Edit",
              "tool_input": {"file_path": ".env", "new_string": "API_KEY=x"}}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Bypass: NotebookEdit (or any non-enumerated tool) writing to the same file_path is NOT blocked
notebook_input = {"hook_event_name": "PreToolUse", "tool_name": "NotebookEdit",
                   "tool_input": {"file_path": ".env", "new_source": "API_KEY=x"}}
result = engine.evaluate_rules([rule], notebook_input)
assert result == {}  # demonstrates block rule silently fails to fire
```
Expected assertion failure to fix: the second assertion should instead be a `deny` decision once field extraction is made tool-agnostic.

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
