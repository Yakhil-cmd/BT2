## Analog Found: Fail-open hook enforcement in the `hookify` plugin

The reported smart-contract bug is a case where an accounting/enforcement step is supposed to gate or record an action, but an exception in that step is swallowed (`try {} catch {}`), so the underlying action (fund transfer) proceeds as if the gate had succeeded, silently corrupting downstream state. The closest reachable analog in this repo is the `hookify` plugin's hook executors, which wrap all rule evaluation in a blanket `except Exception` that defaults to **allowing** the tool call whenever anything goes wrong in the enforcement path, with no signal to the user that their configured `block` rule did not actually run.

### Title
Fail-open exception handling in `hookify` hook executors silently bypasses configured `block` rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin lets a user (or a project's checked-in `.claude/hookify.*.local.md` files) define `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` rules with `action: block` intended to prevent dangerous operations (e.g., `rm -rf`, editing secrets). Every hook entry point wraps rule loading and evaluation in a broad `try/except Exception`, and on **any** exception — regardless of cause — returns a benign `systemMessage` and unconditionally `sys.exit(0)`, which Claude Code treats as "allow." This mirrors the audited pattern: an enforcement step that should have gated the action instead has its failure swallowed, and the gated action proceeds unimpeded.

### Finding Description
In `plugins/hookify/hooks/pretooluse.py`, the enforcement path is: [1](#0-0) 

Any exception raised while loading rules or evaluating them (JSON parsing of hook input, file I/O beyond what's already caught in `config_loader.py`, unexpected input shapes, etc.) is caught, converted into a purely informational `systemMessage`, and the hook exits `0` — which is the "no decision / allow" outcome for `PreToolUse`. This is duplicated identically across `posttooluse.py`, `stop.py`, and `userpromptsubmit.py`: [2](#0-1) [3](#0-2) 

The comments make the intent explicit — "ALWAYS exit 0 - never block operations due to hook errors" — so this is a *deliberate* fail-open design, not an accidental omission. That said, it produces the same externally observable effect as the Sherlock finding: a control that is supposed to record/gate an action (here, `action: block` on a matched rule) does not actually take effect when the control's own execution path throws, and the caller (Claude Code) proceeds with the tool call as though the rule engine had cleanly returned "no match." The user has no way to distinguish "no rule matched" from "rule evaluation crashed" unless they read the transcript's `systemMessage`, which is easy to miss and is not surfaced as a block/deny.

### Impact Explanation
For unprivileged users relying on `hookify` as a local defense-in-depth layer (e.g., a `block` rule against `rm -rf`, credential-file edits, or other destructive Bash/Edit operations), any runtime error in the rule pipeline (malformed hook JSON on stdin, an unexpected `tool_input` shape, an environment issue with `CLAUDE_PLUGIN_ROOT`/`sys.path`, etc.) silently disables that specific enforcement for the current tool call, and the dangerous operation executes normally. This is a hook-bypass / tool-authorization trust boundary: the security guarantee the user configured ("block command X") is not upheld, but nothing in the tool-call outcome tells them enforcement failed — closely paralleling how `totalPrincipalTokensRepaid`/`totalInterestCollected` silently fail to update while the underlying transfer still completes.

### Likelihood Explanation
Moderate-to-low by itself, since `config_loader.py`'s `load_rule_file`/`load_rules` already catch and isolate most per-file parsing errors, and `rule_engine.py`'s `_regex_match` catches `re.error`. However, the outer `except Exception` in every hook script exists specifically because the authors anticipated unhandled failure modes reaching this layer (unexpected `tool_input` structures, stdin decoding issues, etc.), and any future change to `rule_engine.py`/`config_loader.py` that introduces a new uncaught exception type will silently degrade to fail-open rather than fail-safe, with no test coverage visible enforcing block-on-error behavior.

### Recommendation
Distinguish "no rule matched" from "rule evaluation failed" in the hook's exit behavior. On unexpected exceptions in the enforcement path, prefer failing safe for `block`-configured rule sets (e.g., surface a `permissionDecision: "ask"` or a hard block with a clear `systemMessage` explaining that rule evaluation errored) rather than defaulting to full allow, and log these events prominently rather than only to a `systemMessage` that can be missed.

### Proof of Concept
Not applicable in the strict PoC sense (no privileged/malicious external actor required) — the condition is triggerable by any input that causes an exception inside `main()` of `pretooluse.py` after `load_rules`/`evaluate_rules` return, e.g. a hook JSON payload whose `tool_input` doesn't match the shapes handled by `_extract_field`, or any future code path that raises outside the already-caught `IOError/OSError/ValueError/...` cases in `config_loader.py`/`rule_engine.py`. In all such cases the observable behavior is: configured `action: block` rule does not fire, and the Bash/Edit/Write tool call proceeds normally.
