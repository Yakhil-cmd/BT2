### Title
Share-price manipulation in `uniswap_like_market_maker.oscript` liquidity/share issuance model allows first-depositor donation attack that shortchanges or freezes later liquidity providers - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` example AA shipped in the ocore repo implements a share-based liquidity-provider vault pattern (mint `mm_asset` shares proportional to deposit, redeem proportional to `mm_asset_outstanding`). The share-minting math for both the first deposit and subsequent deposits is directly analogous to the audited Biconomy `LiquidityProviders.sol` bug: an attacker can set an extreme share/asset ratio on the first deposit and then further skew it by directly donating funds to the AA's address outside of the "invest" case, causing later depositors' shares to round down to (near) zero or making required co-deposit amounts astronomically large, effectively freezing/griefing future liquidity providers and diluting or capturing their contributed value.

### Finding Description
The relevant logic: [1](#0-0) 

```
{ // invest in MM
    if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
            $issue_amount = balance[base];
            return;
        }
        $current_ratio = $asset_balance / $bytes_balance;
        $expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
        if ($expected_asset_amount != trigger.output[[asset=$asset]])
            bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
        $investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
        $issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
    }`,
```

This is structurally identical to the vulnerable Biconomy pattern:
- The first depositor sets `$issue_amount = balance[base]` with no minimum-liquidity lock or minimum share floor, exactly mirroring the unpatched `_increaseLiquidity()` mint-shares-1:1 behavior that WatchPug's report recommends fixing by locking part of the first mint.
- All later share issuance is computed as `round(investor_share_of_prev_balance * mm_asset_outstanding)`, i.e. `(deposit / pool_balance) * total_shares` — the same `sharesToTokenAmount`-style ratio math flagged in the report.
- Crucially, `balance[base]` and `balance[$asset]` reflect the AA's *raw on-chain balance*, which any unprivileged unit poster can inflate simply by sending a plain payment to the AA's address (a message that does not match the `invest`/`divest`/`exchange` cases is silently accepted into the AA's balance without affecting `mm_asset_outstanding`). This is the oscript analog of a "donation" attack: `balance[X]` in the trigger-evaluation context is attacker-controllable independent of share accounting.

By donating a large, disproportionate amount of `base` or `$asset` directly to the AA address before a victim's `invest` transaction is processed, an attacker can push `$bytes_balance` or `$asset_balance` to extreme values relative to `mm_asset_outstanding`. Because oscript's `round()` truncates to the nearest integer (in units of the asset denomination) and `Decimal` division is exact but truncation happens at `round()`, this can cause:
1. `$issue_amount` for a legitimate depositor to round to `0` while their bytes/asset are still consumed by the AA (fund loss / free capture of value by the attacker's shares), or
2. `$expected_asset_amount` to demand an amount of the paired asset that is impossible to match exactly (since the victim must supply exactly `$expected_asset_amount` or the transaction bounces), effectively freezing legitimate deposits (denial of the vault to new liquidity providers), mirroring the "future liquidityProviders unable to remove/addLiquidity" impact in the original report.

### Impact Explanation
Any unprivileged address can send a plain (non-matching) payment unit to the AA to inflate `balance[base]` or `balance[$asset]` without being subject to the "invest" case's ratio checks. Combined with a dust-sized genuine first "invest" call to set `mm_asset_outstanding` to a tiny number, this manipulates the share price. Victims who subsequently `invest` following the documented pattern either lose value (receive `0` or negligible shares for real funds transferred into the AA's balance) or cannot invest at all because the exact-match ratio check (`bounce('wrong ratio of amounts...')`) becomes unsatisfiable at reasonable amounts. This results in AA fund loss/misappropriation for depositors and freezing of the liquidity-provision function for the affected asset/pool, matching the accepted High-severity impact criteria (AA fund loss or freezing).

### Likelihood Explanation
The attack requires only:
- Being the first (or an early) depositor of a freshly deployed instance of this documented AA pattern (or any AA copying it, since it is shipped as a canonical oscript template for building AMM/market-maker style AAs), and
- The ability to send an ordinary payment unit to the AA's address (available to any unprivileged unit poster).

No special privileges, hub/node cooperation, or leaked keys are needed — only crafting and posting ordinary units/triggers, which is squarely within the reach of a normal AA trigger sender.

### Recommendation
Apply the same mitigation recommended in the original report to any oscript liquidity/share-vault pattern (including this reference example, since developers copy it):
- Do not derive share issuance purely from `balance[...]` values that any address can inflate via direct transfer; track deposited/invested totals in dedicated state vars (e.g. `var['total_invested_base']`, `var['total_invested_asset']`) instead of relying on `balance[base]`/`balance[$asset]` for share-price computation.
- On the first deposit, mint shares using a fixed scaling factor (e.g., multiply by a large constant) or lock a minimum number of shares permanently (unredeemable), so a dust first deposit cannot set an extreme share price.
- Reject investments where the computed `$issue_amount` would round to `0`, and consider rejecting withdrawal/investment paths that are excessively sensitive to `round()` truncation by using higher internal precision before rounding at the final step.

### Proof of Concept
1. Deployer defines the market maker AA with `$asset` (some XYZ asset) as in `test/samples/uniswap_like_market_maker.oscript`.
2. Attacker sends `trigger.data.define = true` to create `mm_asset`.
3. Attacker sends the smallest possible "invest" trigger: `100001` bytes + `1` unit of `$asset`. Since `$asset_balance == 0`, this hits the "initial deposit" branch: `$issue_amount = balance[base] = 100001`; `var['mm_asset_outstanding'] = 100001`.
4. Attacker sends a plain payment (not matching any case, e.g. no `trigger.data` and outputs only `base`) directly to the AA address for a huge amount, e.g. `1e15` bytes. This is accepted into `balance[base]` without touching `mm_asset_outstanding`.
5. Victim now tries to `invest` with a normal amount, e.g. `1e6` bytes plus the "expected" asset amount. `$bytes_balance` is now ~`1e15`, so `$investor_share_of_prev_balance = 1e6 / 1e15 ≈ 1e-9`, and `$issue_amount = round(1e-9 * 100001) = 0`.
6. Victim's payment message attempts to send `0` `mm_asset` shares (invalid/no-op payment) despite having transferred real bytes and asset into the AA's balance — the victim receives no shares for their real funds while the attacker's earlier dust deposit retains a disproportionately large claim once the pool balance is later spent down by another exchange/divest.
