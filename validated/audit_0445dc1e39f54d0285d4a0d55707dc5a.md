### Title
Reachable Assert-Style Throw in Private-Payment Duplicate Check Crashes the Node Before Legitimate Duplicate Handling - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain` in `private_payment.js` runs a "check if duplicate" query and then, before applying the actual duplicate-detection logic that gracefully treats a resend as `ifOk()`, it fires an unconditional `throw Error("more than one output "...)` whenever the query returns more than one matching row. This mirrors the reported Zebra bug class: an invariant assertion executes ahead of the correct, non-fatal duplicate/rejection path, and a value fully influenced by a counterparty (repeated private-payment elements) can make the assertion false, turning what should be a clean "duplicate, ignore" outcome into an uncaught exception.

### Finding Description
In `validateAndSavePrivatePaymentChain`, before validating and saving a private payment chain, the code performs a "duplicate" check: [1](#0-0) 

For divisible assets (`objAsset.fixed_denominations` is false), the SQL query has **no `output_index` filter**:
```
SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?
``` [2](#0-1) 

A single divisible-payment message legitimately produces multiple `outputs` rows for the same `(unit, asset, message_index)` (e.g. a payment to a recipient plus a change output back to the sender, or a multi-recipient payment), as acknowledged directly in the surrounding comment: "divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them" [3](#0-2) . Once a chain has already been validated and saved once (writing more than one output row for that message_index into the `outputs` table), any subsequent re-delivery of the *same* private-payment chain element — which is the intended, legitimate "duplicate" case this code is designed to detect and swallow via `bDuplicate` at lines 76-102 — causes the preceding `rows.length > 1` check at line 74 to fire first, throwing an uncaught `Error` instead of reaching the graceful duplicate-detection branch.

This is reachable from an unprivileged private-payment counterparty: `handleOnlinePrivatePayment` in `network.js` calls `privatePayment.validateAndSavePrivatePaymentChain` directly on attacker/counterparty-supplied `arrPrivateElements` once the associated unit is known [4](#0-3) , and `handlePrivatePaymentChains` in `wallet.js` forwards externally received `private_payments` device messages into the same code path via `network.handleOnlinePrivatePayment` [5](#0-4) . A counterparty can simply resend a previously-accepted divisible private-payment chain (or intentionally rebroadcast it) to trigger the multi-row condition.

The `throw` occurs synchronously inside a `db.query` result callback with no surrounding `try/catch` in this call chain (unlike, e.g., `wallet.js`'s `handleMessageFromHub`, which wraps `doHandle()` in `try/catch` for a different message class [6](#0-5) , this database-callback throw in `private_payment.js` is not shown to be caught anywhere in its call path). In Node.js, an uncaught exception raised from an asynchronous callback crashes the process, exactly as in the Zebra `assert_eq!` abort scenario — the difference being that here the "assertion" is not even a true invariant, since divisible outputs routinely produce more than one row for a message_index, making the crash trivially and repeatably triggerable rather than only in an edge case.

### Impact Explanation
Any correspondent/counterparty capable of sending (or resending) a private payment chain to a node can crash the entire `ocore`-based process (wallet/hub node), a liveness-denial impact analogous to the Zebra advisory. Because the code path is reached through `network.js`'s `handleOnlinePrivatePayment` and `wallet.js`'s `handlePrivatePaymentChains` (device-message-driven), no privileged access is required — this qualifies as an unprivileged private-payment counterparty vector.

### Likelihood Explanation
Likelihood is high and does not require complex chain manipulation: divisible private payments frequently produce more than one own-output row per message (recipient + change, or multiple outputs), so once a chain has been accepted once, a straightforward resend of the identical chain (which is an expected/benign occurrence handled explicitly by the surrounding `bDuplicate` logic) is enough to hit `rows.length > 1` and crash the node. No mining/consecutive-block control analog is needed here — a single retransmission suffices.

### Recommendation
Remove the `throw Error(...)` invariant check, or replace it with logic that correctly handles multiple pre-existing rows (as the subsequent `bDuplicate` code already attempts to do for divisible assets) instead of aborting. At minimum, wrap the duplicate-check query callback in a `try/catch` that routes failures through `transaction_callbacks.ifError(...)` rather than allowing an uncaught synchronous `throw` to propagate out of the database driver callback and crash the process.

### Proof of Concept
1. Sender and recipient are on divisible-asset private payment. Sender pays recipient a private divisible asset amount, producing (at least) two `outputs` rows for the sender's message (one to recipient, one change back to sender) — this is the normal divisible-asset flow reaching `validateAndSavePrivatePaymentChain` in `indivisible_asset.js`/`divisible_asset.js`'s `getSavingCallbacks` `preCommitCallback` [7](#0-6) .
2. After the chain has been validated and saved once (outputs rows for `(unit, asset, message_index)` now number ≥ 2), the recipient (or any correspondent who has the chain, e.g. via `forwardPrivateChainsToOtherMembersOfOutputAddresses`) resends the identical `arrPrivateElements` via a `private_payments` device message.
3. `wallet.js`'s `handlePrivatePaymentChains` → `network.js`'s `handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` is invoked again on the resent chain [8](#0-7) [4](#0-3) .
4. The duplicate-check `SELECT` at `private_payment.js:62-69` returns ≥ 2 rows for the divisible-asset message, hitting the `rows.length > 1` branch and executing `throw Error("more than one output "...)` at `private_payment.js:74-75`, which — being unhandled — crashes the node process.
