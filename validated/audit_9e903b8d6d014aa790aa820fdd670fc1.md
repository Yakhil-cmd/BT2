### Title
Attacker-controlled swap route injects arbitrary contract code beneath the caller's signed auth tree, enabling theft of the signer's wallet funds - (contracts/controller/src/strategies/swap.rs)

### Summary
The ABRT bug class is "untrusted input placed unvalidated into a privileged execution context." The Soroban analog is real here: the lending controller forwards caller-supplied route bytes (`swap` / `StrategySwap` XDR) to the swap aggregator, which `invoke_contract`s whatever pool address the payload names, with no venue/pool allowlist. Any `require_auth` inside that attacker-deployed contract is recorded by honest simulation as a child of the *caller's* `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` auth entry. If the victim signs the simulated tree (the normal wallet flow), the rogue pool can call `token.transfer(victim, attacker, victim_balance)` on any unrelated wallet token, and it executes. The theft is unbounded by the routed amount, the payload `min_out`, or the controller's final risk gate.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one input transfer to the router and then calls `router.execute_strategy(&controller, &amount_in, swap)`, treating the whole route as a black box measured only by balance deltas [1](#0-0) . The router's venue adapters `invoke_contract(&ctx.hop.pool, …)` on payload-named pool addresses with no allowlist (e.g. `contracts/swap-aggregator/src/venues/phoenix.rs:25`, `sushi.rs:50`, `comet.rs:30`); the threat model itself confirms "the router calls the pool and token addresses its payload names and keeps no allowlist of them" [2](#0-1) . Because the controller's strategy entrypoint holds the caller's `require_auth`, any nested `require_auth` the rogue pool triggers (e.g. `transfer(victim, …)`) is folded into the victim's recorded auth tree. The harness test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` demonstrates exactly this: a `RogueHopPool.swap` calling `token.transfer(alice, attacker, WALLET_BALANCE)` is recorded as a `sub_invocation` of Alice's `swap_collateral` auth entry, and after execution `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` [3](#0-2) . There is no on-chain check anywhere that the signed authorization tree contains only the expected input-transfer child.

### Impact Explanation
Theft of user funds, scaled to the victim's entire wallet across every token, not just the routed `amount_in`. The rogue hop pool is attacker-deployed code positioned by route bytes on the call stack directly below the victim's authorization — the exact privilege-escalation shape of the ABRT injection (attacker bytes → code executed under a more-privileged context). The protocol's mitigations all bound the wrong thing: the measured input spend, `min_out`, positive output, and post-swap health checks constrain the *swap legs*, but a `transfer` issued by the rogue pool against an unrelated wallet token executes under the signed tree before/independent of those checks [4](#0-3) .

### Likelihood Explanation
Any unprivileged address can craft a malicious `routeXdr` naming its own pool contract — no privileged role, leaked key, or protocol misconfiguration needed. The same exposure exists on the direct `execute_strategy` path for every swap user [5](#0-4) . Delivery is social: a phishing quote, compromised route source, or malicious front-end returns a route that simulates successfully (recording mode accepts it and even reports the fair output), and standard wallets sign the simulated auth tree without surfacing that a foreign `transfer` of unrelated funds is embedded in it. The harness proves simulation itself records the poisoned tree, so the attack survives the standard sign-what-you-simulate flow [6](#0-5) .

### Recommendation
Bound what route-driven code can request under the caller's authorization on-chain, not only in client guidance: (1) have the router/controller validate or pin hop pool addresses against a registry of deployed venue pools (the payload already carries registry indices — bind them to allowlisted addresses instead of raw addresses); and/or (2) where the Soroban host permits, scope the caller's `require_auth` so strategy entrypoints only authorize the single input `transfer` sub-invocation and reject additional children. Until on-chain binding exists, SDK/wallet integrations must decode the route and enforce that the signed auth tree contains exactly one child (`token_in.transfer`) for controller strategies and standalone router swaps, per `payload.md`'s authorization model [7](#0-6) .

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:

1. `UnlistedPoolRouter.execute_strategy` decodes the caller-supplied route and `invoke_contract`s `route.hop_pool.swap()` — standing in for the real router's unallowlisted `invoke_contract(&ctx.hop.pool, …)` venue dispatch [8](#0-7) .
2. `RogueHopPool.swap` (attacker-deployed, configured with `(victim, wallet_token, attacker, amount)`) calls `token.transfer(victim, attacker, WALLET_BALANCE)`, which triggers `victim.require_auth()` inside the rogue contract [9](#0-8) .
3. Alice calls `ctrl.swap_collateral(alice, account, USDC, amount_in, ETH, poisoned_route)`; simulation (recording auth mode) succeeds and returns a fair ETH output, while the recorded auth tree shows the stolen `transfer` as a child of Alice's `swap_collateral` entry [10](#0-9) .
4. Post-state assertion: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and Alice still received `FAIR_OUT_ETH` supply balance — the swap looked entirely normal while the entire unrelated wallet token balance was drained [11](#0-10) .

The same primitive reaches `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` routes, and standalone `execute_strategy` calls — anywhere caller-provided `StrategySwap`/route bytes are executed under the caller's auth.

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
```

```markdown
The only signature is the sender's. `execute_strategy` calls `sender.require_auth()`, and the sender's auth entry must cover the nested `token_in.transfer(sender, router, total_in)`; simulation produces that tree (`transaction.simulated = true` envelopes already carry it — `attach_simulated_transaction` copies the simulator's `auth` into the op — and `simulateTransaction` produces it for a locally built one). Do **not** `transfer` or `approve` tokens to the router beforehand: the router pulls the input itself, and tokens sent ahead of time are not credited.

Every venue call is self-authorized by the router with invoker-contract auth (`venues/auth.rs::authorize_as_current` → `env.authorize_as_current_contract`): Phoenix and Sushi (`HopContext::authorize_pool_pull`) and Aquarius (`aquarius/pool.rs::invoke_pool_swap`) register `token_in.transfer(router, pool, amount_in)` before the pool pulls; Comet registers `token_in.approve(router, pool, amount_in, expiry)`, then `swap_exact_amount_in` with a nested entry for the pool's `transfer_from`, then clears the allowance; Soroswap transfers from the router to the pool directly. None of these appear in the sender's auth tree.

A contract calling the router (the lending controller in `contracts/controller/src/strategies/swap.rs`, or your own) is the `sender`: it runs `authorize_transfer_as_current(token_in, self, router, amount_in)` (`common/src/token.rs`) immediately before `execute_strategy(self, amount_in, swap)` and measures its own balance deltas afterward (`RouterOverspend = 501`, `NoSwapOutput = 502` in `common/src/errors.rs`). Details in [composition.md](composition.md).
```
