This confirms the mechanism precisely: when a primary AA trigger sends a payment to any address that is itself an AA, `handleSecondaryTriggers` fires that AA as a "secondary trigger" [1](#0-0) . If the secondary AA's own logic causes it to bounce (e.g., it deliberately calls `bounce()`), the error propagates through `async.eachSeries`, and because the failing AA is secondary while the top-level trigger is primary, the code calls `revert()` on the *entire* primary AA response [2](#0-1) . `revert()` then rolls back all state changes and cache entries for every AA in the chain via `ROLLBACK TO SAVEPOINT initial_balances`, discards all accumulated responses, and finally calls `bounce()` on the primary trigger itself [3](#0-2) .

### Title
Malicious secondary-AA output address can force revert/bounce of any primary AA trigger that pays it - (File: aa_composer.js)

### Summary
Any user can post an AA definition whose logic unconditionally (or conditionally, at the attacker's discretion) calls `bounce()`. If a legitimate primary AA (e.g., an exchange, DEX, or any protocol that forwards payments to a user-supplied address) ever sends an output to that attacker-controlled address as part of normal operation, `ocore` automatically fires the malicious AA as a secondary trigger. The attacker's `bounce()` propagates as an error up through `handleSecondaryTriggers`, which unconditionally calls `revert()` on the primary (non-secondary) trigger, unwinding *all* state changes made by the entire chain of AAs and forcing the whole primary response to bounce.

### Finding Description
`handleSecondaryTriggers` looks up every output address of a just-executed AA response that is itself an AA address and invokes `handleTrigger` on it as a secondary trigger [4](#0-3) . The `async.eachSeries` callback treats *any* bounce coming from a secondary AA as fatal to the calling chain: if the AA that failed is itself non-secondary (i.e., the top of the chain), the code calls `revert(...)`, not merely `bounce(...)` [2](#0-1) .

`revert()` is destructive at the level of the entire primary trigger: it rolls back cached response state (`revertResponsesInCaches`), clears all `stateVars`, clears the write `batch`, and issues `ROLLBACK TO SAVEPOINT initial_balances` on the DB connection, discarding every state/balance change performed by every AA in the response chain, before ultimately calling `bounce(err)` on the primary trigger [5](#0-4) .

This means the attacker does not need to be an "author" of the primary trigger or interact with it directly at all — they only need to deploy an AA at an address that a victim protocol is later induced (by ordinary use, e.g. as a swap counterparty, payout recipient, referral address, etc.) to pay. Since AA outputs are frequently attacker/user-supplied addresses (trade counterparties, referral/beneficiary addresses, etc., depending on the calling protocol's design), a griefer can reliably cause the entire primary AA invocation to bounce by making their AA revert every time it's triggered — this is directly analogous to the reported Rubicon issue where a "maker" output receiver can be a contract that always reverts, aborting the reactor's fill and enabling selective, indefinite denial of service against any trade the griefer finds unfavorable, at the cost only of the griefer's own AA definition (near-zero cost) versus repeated loss of the honest trigger sender's bounce fee and wasted execution for the whole chain.

### Impact Explanation
This meets the High severity bar for "AA fund loss or freezing" and "a network unable to confirm new units [profitably/as-intended]": a single unprivileged party who can get their AA address included as an output recipient of any other AA can force that AA's entire response (and all downstream secondary AAs already executed in the chain) to bounce, at will and repeatedly, for any trigger they consider unfavorable. This can be used to griefer/DOS any AA-based protocol (DEX, exchange, aggregator, etc.) that pays out to third-party or counterparty-supplied addresses, since the attacker merely needs their address to appear once as an output of that protocol's AA logic.

### Likelihood Explanation
Likelihood is high: creating an AA with a `bounce()` call is trivial and requires no special privilege — any user can post an AA definition. Being included as an output-recipient address of another AA is a normal outcome for many practical AA designs (counterparties in swaps, arbitrary payout/beneficiary addresses, referral or fee-recipient addresses supplied at trigger time). No cooperation from the primary AA's author is needed beyond ordinary protocol usage that lets a third party's address become an output.

### Recommendation
Do not allow a bounce from a secondary AA to cause a `revert()` of the entire primary trigger's already-completed state changes. Instead, treat a bounced secondary AA the same way a bounced primary trigger is treated when funds are insufficient: keep it isolated (its own state/balance changes and the funds it received should simply not go through / be handled per-AA), without unwinding unrelated, already-successful, upstream AA state changes. Alternatively, require primary AAs to explicitly opt into "safe" forwarding patterns (e.g., detecting output addresses that are AAs) or provide a formula-level mechanism to check whether an output address is an AA before paying it, so honest AA authors can avoid or handle the failure mode without triggering a global revert.

### Proof of Concept
1. Attacker posts an AA definition whose `messages`/`bounce_logic` always calls `bounce("grief")` regardless of trigger content (analogous to the `remote_aa` pattern used in the existing test `calling a remote function that fails`, but instead reachable via a plain payment trigger) — see the existing bouncing pattern in `test/aa_composer.test.js` around the `less than bounce fees` test and `just_a_bouncer.oscript` for reference of a self-bouncing AA [6](#0-5) .
2. Attacker gets their address accepted as an output recipient by any victim primary AA (e.g., as a counterparty/beneficiary address in a swap or payout AA), which is ordinary usage of that protocol.
3. When the victim primary AA executes and pays the attacker's address, `handleSecondaryTriggers` invokes the attacker's AA as a secondary trigger [4](#0-3) .
4. The attacker's AA calls `bounce()`, which surfaces as `err` in the `async.eachSeries` callback; because the top-level trigger is primary, `revert(...)` is invoked [2](#0-1) .
5. `revert()` unwinds all state/balances for the entire chain and bounces the primary trigger [5](#0-4) , so the victim's otherwise-valid, profitable-to-execute operation is denied — repeatable at will by the attacker for any trigger routed to their address.
