### Title
Overflow in RAY index accrual permanently freezes an oversized lending market - (File: `common/src/rates/index.rs`)

### Summary
An attacker can create a very large, highly utilized market whose scaled debt or supply later overflows `i128` during interest accrual. The borrow index ceiling is applied to the index itself, not to the much larger `scaled shares * index` value, so the overflow occurs before the index reaches `MAX_BORROW_INDEX_RAY`. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller.update_indexes` is permissionless and forwards attacker-selected `HubAssetKey` values to `markets::update_indexes`. [3](#0-2)  The pool's `accrue` path loads each market and invokes `interest::global_sync`, which chunks elapsed time and calls `accrue_step` until the market is current. [4](#0-3) [5](#0-4) 

The shared index code then multiplies scaled debt by the old and new borrow indexes, and scaled supply by the supply index, using `Ray::mul`. [6](#0-5) [7](#0-6)  `Ray::mul` returns an `i128`-scaled result and panics with `MathOverflow` when the exact product exceeds the representable range. [8](#0-7) [9](#0-8) 

The index ceiling is `1e36` raw units, equivalent to approximately `1e9 * RAY`, while a market with roughly `1e36` raw scaled shares overflows total value once its index exceeds roughly `170 * RAY`. [2](#0-1) [10](#0-9)  Consequently, the configured index cap does not protect the total-value multiplication. [11](#0-10) 

### Impact Explanation
Once total debt or total supplied value would exceed `i128::MAX`, accrual panics before the market's `last_timestamp` is advanced. [12](#0-11) [13](#0-12)  Every later operation touching that market must accrue first, so the same panic repeatedly prevents withdrawal, repayment, liquidation, bad-debt handling, and further index updates for that market. [14](#0-13) [15](#0-14)  This permanently freezes supplier and borrower funds in the affected `(hub_id, asset)` market and can leave protocol revenue unclaimable through the normal pool path. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
A single unprivileged principal can fund the attack by creating accounts through `supply(caller, account_id = 0, spoke_id, assets)`, depositing the target asset and sufficient collateral, borrowing most of the target asset through `borrow`, and later invoking permissionless `update_indexes`. [18](#0-17) [3](#0-2)  The repository's regression test uses one billion tokens with 18 decimals and 98% utilization; at that scale, debt shares are approximately `9.8e35` raw RAY units, so an index above roughly 173× produces an unrepresentable debt value. [19](#0-18) [20](#0-19) 

The attack requires substantial token liquidity, a market configuration admitting sufficient supply and utilization, and enough ledger-time accrual for the index to cross the value ceiling. [21](#0-20)  Those prerequisites reduce likelihood, but they do not require privileged execution, leaked keys, token misbehavior, oracle dishonesty, or an off-chain failure once such a market exists. [18](#0-17) [22](#0-21) 

### Recommendation
Apply an index ceiling based on the market's scaled balances, not only `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`. [1](#0-0) [7](#0-6)  Before committing a new index, calculate the largest index satisfying `scaled * index <= i128::MAX`, clamp the proposed index to that bound, and ensure subsequent reward distribution uses the same bounded value. [23](#0-22) [24](#0-23)  Alternatively, retain intermediate totals in `I256` and implement an explicit saturation policy, but state transitions should still never leave a market whose next mandatory accrual necessarily panics. [25](#0-24) [26](#0-25)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
