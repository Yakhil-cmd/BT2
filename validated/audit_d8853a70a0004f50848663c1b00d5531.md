### Title
Contract-acceptance signature is bound only to `title`, not to the unique contract hash - allows a paired peer to replay a signature across different contracts (arbiter/prosaic contract) - (File: wallet.js)

### Summary
The Harpie bug was caused by a signature that omitted `chain.id`, so a signature valid in one context (chain) could be replayed in another. In ocore's `signed_message.js`/`wallet.js` implementation of contract acceptance (`prosaic_contract_response` and `arbiter_contract_response`), the signature produced by `signMessage()`/`respond()` only covers a `signed_message` field equal to the contract's `title` string, and the verifier only checks that `objSignedMessage.signed_message == objContract.title` — it never checks the contract's unique `hash` (which is derived from `title + text + creation_date`, see `prosaic_contract.js` `getHash()`). This is the same root-cause class: a missing unique/context-binding value in the signed payload allows the signature to be replayed in a different context than the one it was created for.

### Finding Description
`signMessage()` in [1](#0-0)  produces a signed package whose only application-specific content is the `signed_message` string supplied by the caller; for contract responses this is simply the contract `title` (`prosaic_contract.respond`/`arbiter_contract.respond` pass `signedMessageBase64` produced elsewhere from the title, and the verifying side compares against `objContract.title`).

On the receiving side, both `prosaic_contract_response` and `arbiter_contract_response` handlers in `wallet.js` validate the signed package like this: [2](#0-1) [3](#0-2) 

Note that the check is `objSignedMessage.signed_message != objContract.title` — it does **not** compare against `objContract.hash` (the value that uniquely identifies a specific contract, computed from title+text+creation_date in `prosaic_contract.getHash()`), nor does it embed `objContract.hash` into the signed payload at all. Because many contracts can legitimately share the same `title` (e.g., a template name like "NDA" or "Service Agreement"), a signature obtained for one contract instance with a given title is cryptographically indistinguishable from — and therefore fully replayable as — a valid "acceptance" of any other pending contract that happens to have the same title but different `text`/terms/`creation_date`.

This mirrors the Harpie report precisely: the signed artifact lacks a binding to the specific context (there, `chain.id`; here, the contract's unique `hash`), so a value that was validly produced for context A can be replayed by the same signer/attacker-controlled peer device against context B.

### Impact Explanation
A correspondent device (an in-scope "paired device" actor) that has previously received one genuinely signed acceptance message with title T from a user can:
1. Send (or induce, via `prosaic_contract.createAndSend`/`arbiter_contract` offer flow) a new contract offer with the same `title` T but different, more favorable `text` (dollar amounts, obligations, escrow terms, etc.).
2. Replay the old signed acceptance package as the `signed_message` in a new `prosaic_contract_response`/`arbiter_contract_response` for the new contract.
3. The victim's wallet accepts it as a valid "accepted" signature for the new, different contract terms because only the title is checked.

For `arbiter_contract`, accepted contracts lead to funding of a shared/escrow address and can trigger fund movement/dispute resolution flows, so this can result in the victim's software recording a fraudulent acceptance of contract terms it never actually agreed to, which is used to justify subsequent fund transfers to the shared address and dispute outcomes — a concrete fund-loss/fraud vector for the victim, driven entirely by a paired counterparty (no privileged access needed).

### Likelihood Explanation
Medium. It requires a malicious/compromised paired correspondent device (already an accepted, in-scope actor per the rules), and requires the victim to reuse the same contract title across time or offers (plausible for template-driven contract UIs). No modification to the network protocol or additional infrastructure is required — a single crafted `arbiter_contract_response`/`prosaic_contract_response` device message is sufficient, exactly analogous to a single malicious transaction replay in the original report.

### Recommendation
Bind the signature validation to the unique contract `hash` (or at minimum to `title + text + creation_date`) instead of `title` alone: sign and verify `objContract.hash` (or the full contract object) as the `signed_message`, so a signature produced for one specific contract instance cannot be replayed against a different contract that merely shares the same title. This is the direct analog of adding `chain.id` to the Harpie signature — add the unique-context identifier to what is signed and checked in `wallet.js`'s `prosaic_contract_response`/`arbiter_contract_response` handlers.

### Proof of Concept
1. Alice and Bob (paired devices) exchange a prosaic/arbiter contract offer titled `"Service Agreement"` with terms `text1` and Bob signs acceptance; the wallet computes `signMessage("Service Agreement", ...)` and sends `{hash: contract1.hash, status: "accepted", signed_message: sig1}`.
2. Alice's wallet verifies `sig1` via `signed_message.validateSignedMessage` and checks `sig1.signed_message === "Service Agreement"` — passes, contract1 accepted.
3. Later, Alice (acting maliciously, or a MITM-capable paired device) sends Bob a new offer, `contract2`, with the same title `"Service Agreement"` but altered `text2` (e.g., a much larger payment obligation), and hash `contract2.hash != contract1.hash`.
4. Alice replays the previously captured `sig1` (captured from contract1's response) as the `signed_message` in a manufactured `arbiter_contract_response`/`prosaic_contract_response` for `contract2`.
5. Bob's/Alice's own wallet code path in [4](#0-3)  re-validates: `signed_message.validateSignedMessage` succeeds (signature is cryptographically valid for the string "Service Agreement"), and `objSignedMessage.signed_message != objContract.title` is `false` (they match) — so `contract2` is marked `"accepted"` even though Bob never actually reviewed or agreed to `text2`.
