## Analysis

The reported class of bug is: a protocol assumes `amount_requested == amount_actually_moved` when interacting with an external ERC20 `transfer()` call, without checking `balanceOf` before/after — breaking accounting when the token is fee-on-transfer/deflationary/rebasing.

In this Polkadot SDK snapshot there is a direct, reachable analog in the XCM `TransactAsset` implementation that bridges ERC20 tokens deployed via `pallet-revive` into the XCM asset model.

### Title
XCM `ERC20Transactor` credits/debits the requested `amount` instead of the ERC20 contract's actual balance delta, breaking accounting for fee-on-transfer/deflationary/rebasing ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke `IERC20::transfer` on an arbitrary, permissionlessly-deployed `pallet-revive` contract and treat a `true` boolean return as proof that exactly `amount` tokens moved, crediting/debiting the XCM `AssetsInHolding` register with the requested `amount` rather than the contract's observed balance change. [1](#0-0) 

### Finding Description
`ERC20Transactor` is wired into `AssetHubWestend`'s `AssetTransactors` tuple, so it is reachable from any signed extrinsic that dispatches an XCM program containing `WithdrawAsset`/`DepositAsset` instructions for an ERC20 location (e.g. `pallet_xcm::execute`), as demonstrated by the existing test `withdraw_and_deposit_erc20s`. [2](#0-1) [3](#0-2) 

The matcher used, `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, treats **any** local `Location` consisting of a single `AccountKey20` junction as a valid ERC20 asset — i.e. any contract address a user deploys via `pallet-revive`'s permissionless `InstantiateOrigin = EnsureSigned<Self::AccountId>` automatically qualifies as an XCM-fungible asset, with no allow-list or registration step required. [4](#0-3) [5](#0-4) 

On `withdraw_asset_with_surplus` (holding side, e.g. locking user funds for a reserve transfer or local `deposit_asset`), the code:
1. Calls `asset_id.transfer(checking_account, amount)` via `pallet_revive::Pallet::bare_call`.
2. Decodes only the boolean ABI return value (`is_success`).
3. On `true`, unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the **requested** `amount`, never checking the checking account's `balanceOf` before/after the call. [6](#0-5) 

Symmetrically, `deposit_asset_with_surplus` sends the checking account's `transfer(beneficiary, amount)` and, on `true`, simply returns success — again with no balance-delta verification. [7](#0-6) 

Because a user fully controls the deployed contract's bytecode, they can implement `transfer()` to return `true` while moving less (deflationary/fee-on-transfer) or more (rebasing/inflationary) tokens than `value`. The runtime's XCM holding register — which downstream instructions (`DepositAsset`, `InitiateReserveWithdraw`, bridge/reserve transfers) treat as ground truth — becomes desynchronized from the ERC20 contract's real ledger. This is the exact "checked amount vs. actual balance delta" invariant violated in the referenced Trader Joe finding, now present at the FRAME/XCM boundary that bridges `pallet-revive` ERC20 contracts into the asset-transactor stack (a component that does not exist in the original report but is structurally identical: an XCM component that must, but does not, validate ERC20 balance deltas around `transfer`).

### Impact Explanation
An attacker deploys a deflationary ERC20 contract (e.g., burns 50% on every `transfer`, returns `true`) and executes an XCM program (via `PolkadotXcm::execute`, a permissionless signed-origin call) that:
1. `WithdrawAsset` of `amount` X of their deflationary token — the checking account actually only receives `X/2`, but the holding register is credited `X`.
2. Uses that inflated `X` holding to `DepositAsset`/`InitiateReserveWithdraw` to mint/credit a downstream representation (a local beneficiary, or a reserve-backed asset on another chain) for the full `X`.

This produces unbacked issuance: downstream ledgers record `X` as delivered/backed while the checking account, which is meant to fully back all such credited ERC20 value, is short by the deflationary loss. Later legitimate holders attempting to redeem their (real) ERC20-XCM balance via `deposit_asset_with_surplus` will find the checking account under-collateralized, causing transfer failures/fund lock for other users — an insolvency of the shared `ERC20TransfersCheckingAccount`. This matches the Medium severity of the source finding (accounting break/fund-lock via ERC20 economic assumptions), while also creating a path toward unbacked issuance when combined with cross-chain reserve transfers, which is normally treated as higher severity.

### Likelihood Explanation
Likelihood is high for the accounting break itself: `InstantiateOrigin = EnsureSigned<Self::AccountId>` lets any signed account deploy an arbitrary contract, and `IsLocalAccountKey20`/`ERC20Matcher` accept any such contract as an XCM asset with zero registration or governance gate. Triggering the mismatch requires only writing a standard-looking `IERC20` contract whose `transfer()` deviates from `value` while still returning `true` — well within `ERC20TransferGasLimit`'s budget. The escalation to cross-chain unbacked issuance additionally requires the destination side (reserve/bridge configuration) to trust the checking account's local reserve accounting, which is the documented design of `LocalReserve`/`RemoteReserve` XCM transfers.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the relevant account's `balanceOf` immediately before and after the `IERC20::transfer` call (or use the actual balance delta) instead of trusting the boolean return value and the requested `amount`. Credit/debit `AssetsInHolding` with the measured delta, and reject (fail the transactor) if the delta does not exactly equal the requested `amount`, mirroring the standard "check balance before/after" mitigation from the referenced report.

### Proof of Concept
No PoC was executed against a live network. The reachability and wiring are demonstrated by the existing repository test `withdraw_and_deposit_erc20s`, which uses the standard (non-deflationary) `MyToken` fixture and asserts `beneficiary_amount == erc20_transfer_amount` exactly — showing the code path and its implicit "no fee" assumption. [8](#0-7) 
A minimal reproduction would replace `MyToken` with a Solidity contract whose `_update`/`transfer` burns e.g. 50% of `value` on every transfer while still returning `true` (structurally similar to the `_update` hook already present in the repository's OpenZeppelin ERC20 fixture used for compilation), then run the same `withdraw_and_deposit_erc20s` flow and assert that `beneficiary_amount != erc20_transfer_amount` while `AssetsInHolding`/event logs still report the full amount as transferred. This was not executed in this session; a background engineering session with Rust/cargo access is needed to compile the malicious fixture and run the assertion, as noted below. [9](#0-8)

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));

				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();

		let beneficiary_amount =

		assert_eq!(beneficiary_amount, erc20_transfer_amount);

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;

    function _update(address from, address to, uint256 value) internal virtual {
        if (from == address(0)) {
            // Overflow check required: The rest of the code assumes that totalSupply never overflows
            _totalSupply += value;
        } else {
            uint256 fromBalance = _balances[from];
            if (fromBalance < value) {
                revert ERC20InsufficientBalance(from, fromBalance, value);
            }
            unchecked {
                // Overflow not possible: value <= fromBalance <= totalSupply.
                _balances[from] = fromBalance - value;
            }
        }

        if (to == address(0)) {
            unchecked {
                // Overflow not possible: value <= totalSupply or value <= fromBalance <= totalSupply.
                _totalSupply -= value;
            }
        } else {
            unchecked {
                // Overflow not possible: balance + value is at most totalSupply, which we know fits into a uint256.
                _balances[to] += value;
            }
        }

        emit Transfer(from, to, value);
    }
