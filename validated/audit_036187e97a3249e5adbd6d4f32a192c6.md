### Title
Webhook signing-organization / acted-upon-repository binding mismatch allows cross-organization webhook forgery in multi-org installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` [1](#0-0) . If that organization's app config has no `webhook_secret` set (a documented, supported "optional" configuration, e.g. as shown in `config/secrets.development.shopify.yml` with `webhook_secret: # nil`), `verify_webhook_signature` short-circuits to `true` for **any** payload, signed or not [2](#0-1) . The handler dispatched afterward (e.g. `PushHandler`) then resolves the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')` [3](#0-2) .

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.*.yml` supports multiple GitHub orgs, each with its own `webhook_secret`), the equality the app relies on is:

`organization whose webhook_secret authenticates the request == organization owning the repository the handler mutates`

This equality can be broken. `repository_owner` in the controller is derived from `repository.owner.login`, falling back to `organization.login` [1](#0-0) . Meanwhile, `Handler#stacks` resolves the affected `Stack` by `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [3](#0-2) . Both values come from the same JSON body, so an attacker who crafts the raw POST body fully controls both fields independently — there is no requirement that `repository.owner.login` matches the actual owner segment implied by `repository.full_name`.

If any one organization configured in `secrets.github` (multi-org schema) has `webhook_secret` unset/blank — which the setup docs and shipped `secrets.development.shopify.yml` example explicitly show as a valid, supported configuration (`webhook_secret: # nil`) [4](#0-3)  — then setting `repository.owner.login` to that unsigned organization's login causes `Shipit.github(organization: repository_owner)` to resolve a `GitHubApp` whose `verify_webhook_signature` unconditionally returns `true` (`return true unless webhook_secret`) [5](#0-4) . The request thus passes `before_action :verify_signature` with no signature at all, while `repository.full_name` in the *same* payload can point at a stack belonging to a *different*, signed organization. The `PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  for that unrelated stack, unauthenticated.

### Impact Explanation
This lets an unauthenticated network attacker forge webhook events (push, status, check_suite, membership, pull_request, etc.) against any stack/repository configured under a *different*, properly-signed GitHub organization, as long as at least one configured organization in the same install lacks a `webhook_secret`. Depending on the handler this can trigger unauthorized `GithubSyncJob` runs, spoofed commit `Status` records that influence merge-queue and deploy-safety decisions (`StatusHandler`), or fabricated `Team`/`User` membership records (`MembershipHandler`) — i.e., escalation into `Shipit.github_teams` authorization and unauthorized ship/merge decisions, matching the High-impact bar.

### Likelihood Explanation
Requires a multi-org Shipit installation (supported and documented feature) where at least one org's `webhook_secret` is unset — a state the project's own sample config demonstrates as normal/expected. No credentials, session, or ApiClient token are needed; only network access to the public `/webhooks` endpoint that must be reachable per the documented setup guide.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive the verifying organization/app from the resolved `Repository`/`Stack` (or require `repository.full_name`'s owner segment to match `repository.owner.login`) rather than trusting an attacker-controlled top-level field independently from the field handlers use to select the target stack. Alternatively, disallow/require `webhook_secret` for every configured organization when running multi-org, so no organization can act as a signature "bypass" for the others.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.github`: `OrgSigned` (has `webhook_secret` set) with a stack `OrgSigned/app`, and `OrgUnsigned` (no `webhook_secret`, e.g. as in the shipped sample config) [7](#0-6) .
2. POST to `/webhooks` with header `X-Github-Event: push`, no `X-Hub-Signature`, and a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgUnsigned" }, "full_name": "OrgSigned/app" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgUnsigned")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing) signature [2](#0-1) .
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgSigned/app")` [3](#0-2)  and triggers `stack.sync_github(expected_head_sha: ...)` for the *signed* org's stack — despite the request never being authenticated by that org's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
