### Title
Cross-tenant Status forgery via global SHA lookup in `StatusHandler#process` combined with secretless-org signature bypass - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)` with no repository/organization scoping, while webhook authenticity is verified against the organization named in the *inbound* payload's `repository.owner.login` via `Shipit.github(organization: repository_owner)`. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no `webhook_secret` configured, an attacker who controls (or names) a secretless GitHub organization can forge a `status` event whose `sha` matches a commit belonging to a completely different, victim organization's stack, and have Shipit accept and apply it as a legitimate status.

### Finding Description
The binding the code implicitly assumes is: `organization verifying the webhook (repository_owner in payload) == organization owning the Commit matched by sha`. This is never checked.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from the attacker-controlled payload (`params.dig('repository','owner','login')`, line 59-62) and does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` — i.e., for any organization configured without a `webhook_secret`, **every** payload passes regardless of the `X-Hub-Signature` header or its content.
- Once past this check, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw parsed JSON (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-23`) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query has no `stack_id`/`repository` filter at all; it matches any commit in the entire database sharing that sha, irrespective of which stack/organization/repository it belongs to. Note this differs from the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which *does* scope via `Repository.from_github_repo_name(repository_name)` — `StatusHandler` does not use that helper.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a new `Status` from the attacker-supplied `state`/`description`/`target_url`, and via `add_status` fires `Hook.emit(:deployable_status, ...)` and can call `stack.schedule_merges`, feeding directly into deployability/merge gating logic (`app/models/shipit/commit.rb:227-229, 379-384`).

Attacker's exact request: knowing/guessing a victim commit sha (commit shas are frequently public — visible via PR URLs, git history, CI logs, etc.), the attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   (irrelevant since org X has no secret)
{
  "repository": {"owner": {"login": "secretless-org-X"}, "full_name": "secretless-org-X/some-repo"},
  "sha": "<victim_sha_belonging_to_org_Y_stack>",
  "state": "success",
  "description": "forged",
  "context": "ci/attacker"
}
```
This passes `verify_signature` because `secretless-org-X` has no configured `webhook_secret`, then `StatusHandler` matches the victim's `Commit` row purely by sha and writes a new `Status` for it — despite the payload's `repository` object referring only to `secretless-org-X`, never to the victim's org/repo.

None of the listed guards prevent this: `verify_signature` checks the *wrong* organization (the one in the payload, not the one owning the resolved commit); `drop_unhandled_event` only checks event type presence; there is no `ExplicitParameters` validation tying `sha` to `repository`; `force_github_authentication`/`User#authorized?`/`require_permission!`/`stacks` scope are session/API-token constructs not used by the unauthenticated webhook path at all.

### Impact Explanation
An attacker who has (or names) any GitHub organization configured in Shipit without a `webhook_secret` can forge `Status` records (state/description/target_url) on arbitrary tracked commits belonging to *any other* organization's stack, as long as they know that commit's sha. This is a cross-tenant integrity violation: it directly manipulates `Commit#deployable?`/`blocked?` logic (`app/models/shipit/commit.rb:227-237`) and can trigger `stack.schedule_merges` and continuous-delivery hooks (`schedule_continuous_delivery`, line 281-287), potentially causing an unintended merge or deploy to proceed (or be blocked) for a repository the attacker never authenticated against. This matches "Critical — a payload for one repository mutating another's stack, commit ... or an unauthorized deploy/rollback/merge."

### Likelihood Explanation
Preconditions: (1) at least one organization onboarded to this Shipit instance is configured without a `webhook_secret` (a plausible/common misconfiguration, and the code explicitly supports it — `return true unless webhook_secret`); (2) attacker needs to know a target commit's sha, which is typically public (PR pages, git log, CI badges). No Shipit credentials, GitHub App keys, or webhook secrets of the *victim* org are required — only the ability to POST to `/webhooks` with an org name that has no secret configured. This is cheap, repeatable against arbitrary shas/stacks, and requires no interaction from the victim.

### Recommendation
Scope `StatusHandler#process` (and any similar handler) to the repository asserted by the verified payload, e.g. resolve commits only within `stacks` (as derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) rather than a bare global `Commit.where(sha: ...)`. Additionally, `GitHubApp#verify_webhook_signature` should not silently accept any payload when `webhook_secret` is blank for organizations that are supposed to be secured — at minimum, `StatusHandler` must never mutate a commit in stack/org A off of a signature verified for org B.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status handler mutates commit belonging to a different org than the one that authenticated the webhook" do
  victim_stack = shipit_stacks(:shipit) # belongs to org "shipit", has a webhook_secret configured
  victim_commit = victim_stack.commits.create!(sha: '0' * 40, message: 'victim commit')

  payload = {
    'repository' => { 'owner' => { 'login' => 'secretless-org-x' }, 'full_name' => 'secretless-org-x/some-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'attacker-forged',
    'context' => 'ci/attacker'
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  assert_equal 'attacker-forged', status.description
end
```
Binding equality to assert both sides: `payload['repository']['owner']['login'] ("secretless-org-x")` != `victim_stack.repository.owner ("shipit")`, yet the write succeeds — demonstrating the divergence is never checked. (Verification of `verify_webhook_signature` returning `true` for a secretless org can be independently confirmed against `lib/shipit/github_app.rb:76-83`, calling it directly with an org whose config lacks `webhook_secret`.)
