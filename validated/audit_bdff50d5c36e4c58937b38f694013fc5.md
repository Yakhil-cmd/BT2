### Title
Webhook signature verification is keyed on `repository.owner.login` while event handlers act on the unrelated `repository.full_name` field, allowing forged events for any stack once a single organization is misconfigured without a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to verify against using `repository.owner.login` (or `organization.login`) from the untrusted JSON payload, then `verify_webhook_signature` unconditionally treats the request as verified if that organization has no `webhook_secret` configured. The event is then dispatched to handlers that act on a completely different field of the same attacker-controlled payload — `repository.full_name` — to select the `Stack`/`Repository` to mutate. This breaks the intended binding "the organization whose secret authenticated the request equals the repository the handler writes to."

### Finding Description
`verify_signature` resolves the app config for HMAC verification purely from payload content: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured, which the sample config explicitly shows as a supported/valid state (`webhook_secret: # nil`): [3](#0-2) [4](#0-3) 

After (non-)verification, `create` dispatches the same raw JSON payload to handlers: [5](#0-4) 

But every handler resolves the target `Repository`/`Stack` from `repository.full_name`, a field never checked against, or tied to, `repository.owner.login`/the organization used for signature verification: [6](#0-5) 

Concretely, `PushHandler` triggers `stack.sync_github` and `StatusHandler` writes commit statuses using only `full_name`-derived stacks: [7](#0-6) [8](#0-7) 

Exploit path: if the Shipit deployment has more than one GitHub organization configured (a documented/supported multi-org setup per `config/secrets.development.shopify.yml`) and any one of them has `webhook_secret` left blank, an unprivileged external attacker can POST to `/webhooks` with:
- `X-Github-Event: push` (or `status`)
- JSON body where `repository.owner.login` = the org with no secret (so `verify_webhook_signature` returns `true` unconditionally, no valid signature required)
- `repository.full_name` = `victim-org/victim-repo`, an entirely different, real, tracked stack

Because `verify_signature`'s organization lookup and the handler's repository resolution use two different, independently attacker-controlled fields of the same JSON body, and only the former is what gates authentication, the attacker forges an authenticated-looking push/status event against a stack it has no legitimate relationship to.

### Impact Explanation
A forged `push` event causes `Stack#sync_github` to run for the victim repository, and a forged `status`/`commit_status` event lets the attacker inject arbitrary commit statuses. Depending on stack configuration (e.g., `continuous_deployment: true` plus required status checks), this can move a stack toward triggering an unauthorized deploy, since the write path is reached with no cryptographic proof tying the event to the actual repository being mutated. This satisfies the "unauthorized deploy" Critical/High impact category since it is a genuine authentication-binding break rather than a benign misconfiguration only affecting the misconfigured org's own repos.

### Likelihood Explanation
Requires no attacker privilege beyond network access to `/webhooks`. It does require that the deployment has configured at least one GitHub organization without a `webhook_secret` — an explicitly supported/documented configuration shape (`config/secrets.development.shopify.yml` shows `webhook_secret:` left blank as a normal template value), so this is a realistic operational state, not a hypothetical.

### Recommendation
Bind the signature-verification identity to the same repository that handlers act on: either restrict the organization used for `verify_webhook_signature` to be derived from and validated against `repository.full_name` (not just `owner.login`), or reject events for organizations with no configured `webhook_secret` instead of treating them as implicitly trusted, or scope handlers so they only ever operate on the repository/org that was actually verified.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `victim-org` (has `webhook_secret` set, has real stacks) and `empty-org` (no `webhook_secret`, per the template default).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "empty-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "empty-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header.
4. `PushHandler.call` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` on the victim's real stack — a write triggered by an unauthenticated, forged request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
