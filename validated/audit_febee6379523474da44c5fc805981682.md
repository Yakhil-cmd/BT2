### Title
Response/Message-handling Nil-style Crash via Unchecked `.payload` Access in `handleOnlinePrivatePayment` - ([File: network.js])

### Summary
`network.handleOnlinePrivatePayment` only checks that `arrPrivateElements` is a non-empty array before immediately accessing `arrPrivateElements[0].payload.denomination`, without ever checking that `arrPrivateElements[0].payload` exists. A single malformed `private_payment` message from any counterparty reaching this handler directly (not through the `wallet.js` `handlePrivatePaymentChains` pre-validation path) crashes the process with `TypeError: Cannot read properties of undefined (reading 'denomination')`.

### Finding Description
`handleOnlinePrivatePayment` is the function that processes an incoming private-payment chain element: [2](#0-1) 

The only guard is `ValidationUtils.isNonemptyArray(arrPrivateElements)`. Immediately after, `arrPrivateElements[0].payload.denomination` is evaluated. If the first (head) element of the array is a non-empty object that lacks a `payload` property (or has `payload: null`), `arrPrivateElements[0].payload` is `undefined`, and accessing `.denomination` on it throws an unhandled `TypeError`, crashing the process the same way the sipgo `res.To()` returning `nil` crashed on `.Params["tag"]`.

This function is registered as the direct handler for the peer-to-peer `justsaying` message type `'private_payment'`, which any correspondent device or wallet peer can send: [1](#0-0) 

Unlike the `wallet.js` `handlePrivatePaymentChains` path — which pre-validates every chain element with `isNonemptyObject(e.payload)` before forwarding to `network.handleOnlinePrivatePayment` [3](#0-2)  — a peer sending the raw `'private_payment'` justsaying message directly bypasses that validation and reaches the vulnerable line with attacker-controlled content.

### Impact Explanation
Any device/peer able to send a `private_payment` justsaying (a normal, unauthenticated wallet/device-messaging operation, analogous to sipgo accepting any SIP request without further gatekeeping) can crash the receiving node process, since Node.js `TypeError` exceptions thrown outside of a wrapped `try/catch` in a message-handling callback are typically fatal to the process (unhandled exception). This is a remotely triggerable denial of service on any node that processes this message type, matching the sipgo advisory's "single malformed message causes a crash affecting all normal operations" impact.

### Likelihood Explanation
Reaching this code only requires constructing an object with a non-empty `unit`/other cosmetic field but omitting `payload` (or setting it to `null`), then sending it as a `private_payment` justsaying to a target node — no valid signature, unit inclusion, or prior state is required, and the check occurs before any deeper validation (`validation.js`, asset checks, etc.) is ever reached.

### Recommendation
Add an explicit non-empty-object check for `arrPrivateElements[0].payload` (and ideally full structural validation matching what `wallet.js`'s `handlePrivatePaymentChains` already performs) at the very top of `handleOnlinePrivatePayment`, before any property is read off it, returning `callbacks.ifError(...)` instead of allowing the exception to propagate.

### Proof of Concept
1. Establish a peer/device WebSocket connection to a target ocore node (this is a standard, unauthenticated capability in the protocol).
2. Send a `justsaying` message of type `'private_payment'` with content `[{ "unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=" }]` — i.e., an array containing one non-empty object that has no `payload` field.
3. The receiving node's message router dispatches this content into `network.handleOnlinePrivatePayment(ws, arrPrivateElements, ...)`.
4. Execution reaches `arrPrivateElements[0].payload.denomination` at network.js:2382, throws `TypeError: Cannot read properties of undefined (reading 'denomination')`, and (absent a surrounding catch in the calling justsaying dispatcher) crashes the node process.
