### Title
Webhook signature verification is bound to the org derived from the payload's `repository.owner.login`/`organization.login`, but event handlers act on repositories/commits derived from separate, unchecked payload fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the **attacker-controlled JSON body itself**. Once the signature check passes, the dispatched `Handlers::Handler` subclasses resolve the actual target (`Repository`/`Stack`/`Commit`) from *different, independent* fields of the same body (`repository.full_name` for push events, and a completely unscoped global `Commit.where(sha:)` lookup for status events). There is no server-side enforcement that these fields are mutually consistent, so a party who legitimately controls the webhook secret for **one** onboarded GitHub organization on a shared Shipit instance can forge events that are processed as if they came from a **different** organization's repository.

### Finding Description
`verify_signature` is: [1](#0-0) 

with `repository_owner` computed as: [2](#0-1) 

This value is attacker-supplied JSON, used only to select *which* org's `webhook_secret` is used for `Shipit.github(organization: repository_owner).verify_webhook_signature`, per `GithubApp#verify_webhook_signature`: [3](#0-2) .

Meanwhile, the dispatched handlers derive the actual acted-upon resource from a separate field: [4](#0-3) 

`PushHandler` uses this `repository_name` (i.e. `repository.full_name`) to find the target stacks and force a sync to an attacker-chosen `expected_head_sha`: [5](#0-4) .

`StatusHandler` is worse: it does not consult repository scoping at all, and applies the forged CI status to **any** commit matching the given `sha` across the entire installation: [6](#0-5) .

Binding that is broken (as an equality that should hold but doesn't):
`organization_that_authenticated_the_request (repository.owner.login / organization.login, verified against that org's webhook_secret) == organization_whose_repository/commit_is_actually_written (repository.full_name used by PushHandler, or the completely unscoped commit sha used by StatusHandler)`.

Because Shipit is explicitly designed to host multiple GitHub organizations in one instance (see `config/secrets.development.shopify.yml`, listing `somegithuborg`/`someothergithuborg` each with their own `webhook_secret`) [7](#0-6) , this cross-org isolation assumption is exactly the trust boundary the signature check is supposed to enforce, and it does not.

### Impact Explanation
An attacker who legitimately administers **one** org's GitHub App installation on a shared Shipit deployment (an unprivileged actor with respect to any *other* onboarded org/stack) can:
- Forge a `status` webhook, signed with their own org's `webhook_secret`, that sets an arbitrary CI status/context (e.g. a required check listed in another stack's `ci.require`) to `success` for a commit `sha` belonging to a victim stack in a completely different organization, because `Commit.where(sha:)` in `StatusHandler` is global and unscoped by repository/org. If continuous deployment is enabled and relies on that required status, this can result in an **unauthorized deploy** of a commit that has not actually passed CI - matching the "Critical: unauthorized deploy" impact category.
- Forge a `push` webhook to force `GithubSyncJob` to run against a victim stack in another org (`stack.sync_github(expected_head_sha: ...)`), influencing which commit is treated as the branch head for that stack.

This is a direct analog of the reported issue's root cause: a verification step is bound to one field while the privileged action is bound to a different, unchecked field of the same untrusted payload.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately controls a GitHub App installation/webhook secret for **some** organization onboarded to the same shared Shipit instance - no theft of victim credentials, no `ApiClient` token, and no repository write access to the victim repo is required. This is squarely "unprivileged attacker breaks a deployment-trust binding," matching the rules' scope. The main precondition is a multi-tenant deployment (multiple orgs configured under `Shipit.github`), which the engine's own configuration/docs explicitly support and document.

### Recommendation
Enforce that the organization used to select/verify the webhook secret is the *same* organization actually acted upon by the handler for every event type:
- In `WebhooksController#verify_signature`, after verifying, re-derive `repository_owner` from the same field the handlers use (`repository.full_name`'s owner segment) and reject if it disagrees with the `organization.login` fallback.
- In `Handlers::Handler#stacks`/`StatusHandler#process`, scope commit/status lookups by the repository identified in the verified payload (e.g., `Commit.joins(:stack).merge(Repository.from_github_repo_name(repository_name).stacks).where(sha: params.sha)`) instead of a global, repository-unaware query.

### Proof of Concept
1. Attacker administers `attacker-org`'s GitHub App on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `status` event body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"},
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/circleci"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s own `webhook_secret` over the raw body, and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully (attacker signed with their own valid secret) - see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` - with no check that `victim-commit-sha` belongs to `attacker-org`'s repository. If that commit belongs to a stack in a different, victim organization, its CI status is now attacker-controlled.

Note: I could not further trace, within the remaining tool budget, the exact downstream code path in the continuous-deployment scheduler that consumes `Commit#create_status_from_github!` results to confirm the precise conditions under which this forged status causes an actual deploy trigger (e.g., how `ci.require`/`deployable?` gate scheduling) - this would need one more pass over `app/models/shipit/commit.rb` and the continuous delivery job to fully confirm the automatic-deploy trigger chain, though the required-status semantics are documented in `README.md:446-471`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
