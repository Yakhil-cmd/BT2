## Analysis Result



### Title
Asset Definer Can Freeze Holders' Funds by Revoking/Withholding Attestation on a `spender_attested` Asset - (File: validation.js, writer.js)

### Summary
An asset issuer (or an AA that defines such an asset) can create an asset with `spender_attested: true`. Unlike most asset attributes, which are fixed forever once the asset is defined, the attestor list is explicitly designed to be mutable after the asset exists and after users already hold balances of it. The definer can publish new `asset_attestors` messages at any later moment to add, withhold, or effectively remove attestation for arbitrary addresses, and every future transfer of the asset requires all output addresses to be currently attested. This gives the definer (an unprivileged network participant who created the asset — analogous to the "admin" in the original finding) unilateral, ongoing power to freeze any holder's funds in that asset with no on-chain constraint, timelock, or governance.

### Finding Description
When an asset is defined with `spender_attested: true`, the schema itself documents that the definer "must subsequently publish and update the list of trusted attestors": [1](#0-0) 

The `asset_attestors` message can be submitted by the definer at any time after asset creation, is validated with only cosmetic constraints (no rate-limit, no permanence, no minimum attestor guarantee), and only prevents more than one such update per single unit — not per asset over time: [2](#0-1) 

Every payment of that asset — at the time it's broadcast, not at the time the asset was created — is checked against the *current* attestor list, and if any output address of the transfer is not attested, the transfer is rejected outright: [3](#0-2) 

The attestation check at issue time is likewise controlled by the current list, not any list at initial acquisition time: [4](#0-3) 

For AA-defined assets, the same `spender_attested`/`attestors` fields can additionally be driven by dynamic oscript formulas evaluated against AA state variables under the AA author's control, further widening the AA author's discretion over who is "trusted" at any given moment: [5](#0-4) 

Because the attestor list check is re-evaluated at spend time using whatever list is current on the DAG (not the list that existed when the holder acquired the asset), a definer can:
1. Define an asset with `spender_attested: true` and initially attest a wide set of addresses so that ordinary users freely acquire/hold the asset.
2. Later post one or more `asset_attestors` units that drop specific holder addresses (or shrink the whole attestor list to only the definer's own addresses).
3. From that point forward, those holders' outputs of the asset can never satisfy `arrAttestedOutputAddresses.length === arrOutputAddresses.length`, so **any transfer to or from those addresses is permanently rejected by validation**, freezing their balance indefinitely — with no expiry, no dispute mechanism, and no way for the frozen party to self-remedy since only the definer can update the attestor list.

This is the direct ocore analogue of the C4 finding: a single reachable, unprivileged actor (the asset issuer, or an AA author acting through this asset feature) retains a live "important variable" (the attestor list) it can rewrite at will post-issuance to lock user funds, exactly the "admin can change important variables" class of centralization risk, mapped onto a primitive that any asset issuer — not a privileged node/hub operator — can exploit.

### Impact Explanation
Any holder of a `spender_attested` asset can have their balance of that asset permanently frozen at the sole discretion of the asset's definer, at any point after they've already acquired/held the asset. Because ocore's consensus rules enforce this check identically on every node, this is not a bug affecting a single victim's wallet — it's a network-wide, consensus-enforced freeze once the definer updates the attestor list, satisfying the "AA fund loss or freezing" acceptance bar. This is analogous to the original finding's concern that admin-controlled parameters can be weaponized post-hoc against users who already committed funds.

### Likelihood Explanation
High. No special privilege beyond being the asset's own definer is required — any user can define such an asset (directly or via an AA) and lure counterparties into holding it, then unilaterally revoke attestation. The mechanism is a documented, intended feature (per the SQL schema comment) rather than an edge case, so it is trivially reachable and requires no unusual conditions to trigger.

### Recommendation
- Consider snapshotting/pinning attestor eligibility at the time an output address received the asset (grandfathering existing holders) rather than re-checking against the live attestor list on every subsequent spend.
- Alternatively, require attestor-list changes to only add attestors, or to take effect only after a mandatory on-chain delay (a timelock analogous to what the C4 report recommended), so holders have a guaranteed window to exit before losing spendability.
- Document explicitly, at the wallet/UX level, that `spender_attested` assets carry this centralization/freeze risk so users can make informed decisions before accepting such assets.

### Proof of Concept
1. Definer address `D` posts an `asset` message defining asset `A` with `spender_attested: true`, `is_transferrable: true`, and an initial `attestors` list that includes address `H` [6](#0-5) .
2. `D` (as the initial attestor, or via a cooperating attestor) attests `H`, and `H` receives/holds a balance of asset `A` through normal transfers, each successfully validated because `H` is in `arrAttestedAddresses` [4](#0-3) .
3. `D` later posts a new `asset_attestors` unit for asset `A` with an attestor list that no longer includes `H` (or includes only `D`'s own addresses) [7](#0-6) .
4. `H` attempts to transfer asset `A` to any address (including back to themselves). `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses` against the now-current list, `H`'s output address is not attested, `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, and the unit is rejected network-wide [3](#0-2) .
5. `H`'s balance of asset `A` is now permanently frozen; only `D` retains any ability to move funds of this asset, entirely at their discretion.
