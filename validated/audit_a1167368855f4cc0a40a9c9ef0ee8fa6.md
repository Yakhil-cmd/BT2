### Title
CCMenu token created for a single stack silently authorizes reading every stack in the installation - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The external report's core bug class is that a value which is supposed to bound a privileged operation (`maxGasPrice`) is not actually the value enforced at execution time, allowing the "authorized" scope to diverge from the "touched" scope and drain funds. The direct analog in shipit-engine is `CCMenuUrlController#client`, which mints a persistent `ApiClient` token intended to expose the CCMenu/CCTray status of one specific stack, but never binds that token to the stack it was generated for. Any holder of that token can use it to read the state of every stack in the Shipit installation, not just the one whose URL they were given.

### Finding Description
`CCMenuUrlController#fetch` builds a shareable "CCMenu URL" for a given stack and embeds an `ApiClient` authentication token in it: [1](#0-0) 

The client is created with `permissions: %w[read:stack]` only - no `stack:` attribute is passed, so `ApiClient#stack_id` remains `nil` for this client: [2](#0-1) 

`Api::BaseController` uses that `stack_id` to scope which stacks a client may see: [3](#0-2) 

Because `stack_id?` is false for this client (a boolean generated from the `stack_id` column), `stacks` resolves to `Stack.all` - i.e. every stack in the installation, not the one that appeared in the CCMenu URL path (`/ccmenu/*stack_id`). The `Api::CCMenuController#show` action (mounted at `/api/stacks/*stack_id/ccmenu`) only checks `require_permission :read, :stack`, it does not check that the authenticated client's `stack_id` matches the requested `stack_id`: [4](#0-3) 

The token itself is a durable, non-expiring `SimpleMessageVerifier`-signed client id, and is embedded directly in a URL meant for external tools (CCMenu/CCTray build-status widgets, dashboards, browser extensions) that are frequently pasted into shared/public locations: [5](#0-4) 

The equality that should hold is:
`stack the token authorizes == stack the token actually touches`

Before the flaw: a CCMenu token generated for stack A is expected to only ever return status for stack A.
After exploiting the flaw: the same token, presented against `/api/stacks/*any_other_stack/ccmenu`, satisfies `require_permission :read, :stack` (because the permission check is a flat string match on `permissions`, not scoped by `stack_id`) and returns that other stack's status, because `stacks` falls back to `Stack.all` when `stack_id` is unset.

### Impact Explanation
This lets anyone who obtains a single CCMenu URL/token (e.g., pasted into a status dashboard, Slack channel, or personal desktop widget, all common uses of CCMenu integrations) enumerate and read the live deploy/CI/lock state of every stack managed by the Shipit instance, bypassing the per-stack access boundary the URL implies and bypassing the web session's `Shipit.github_teams` authorization entirely (the API `ApiClient` path never checks team membership, only the `permissions` array). This matches the in-scope "High" impact category: unauthenticated (from the perspective of the actual target stack; the holder never authenticated for that stack) read of stack state.

### Likelihood Explanation
Likelihood is significant: CCMenu URLs are specifically designed to be embedded in third-party tools/widgets outside Shipit's session-based access control, so leakage of one such URL is a realistic and even expected occurrence. No additional secrets, elevated privileges, or session access are needed beyond a token that was deliberately designed to be shared externally for a single stack.

### Recommendation
Set the `stack:` attribute when creating the CCMenu `ApiClient` (mirroring the pattern that should scope the token), e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack)`, and additionally have `Api::CCMenuController` (and any other stack-scoped controller relying solely on `require_permission`) explicitly verify that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering, so a per-stack token can never be replayed against a different stack.

### Proof of Concept
1. As an authenticated Shipit user, visit `stack_A`'s page and trigger the CCMenu URL generation (`GET /ccmenu/stack_A...`), obtaining a URL of the form `https://shipit.example.com/api/stacks/stack_A/ccmenu?token=<TOKEN>`.
2. Share/leak this URL (or just the token) as intended for CCMenu widget embedding.
3. Any party holding `<TOKEN>` requests `https://shipit.example.com/api/stacks/stack_B/ccmenu?token=<TOKEN>` for an unrelated `stack_B` they were never granted access to.
4. `Api::BaseController#authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client's `permissions` includes `read:stack`), and `stack` resolves via `stacks.from_param!` where `stacks == Stack.all` because `current_api_client.stack_id?` is false — `stack_B`'s CCMenu status (build/lock state) is returned, confirming cross-stack disclosure with a token meant for `stack_A` only.

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

module Shipit

        end

        end

          false
        end
      end

      def show

      private
