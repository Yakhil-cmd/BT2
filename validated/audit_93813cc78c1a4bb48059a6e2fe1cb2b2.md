### Title
Asset-metadata name spoofing allows any registry address to impersonate a well-known asset's ticker/name in the wallet UI - (File: wallet.js)

### Summary
Chrome's CVE-2019-13740 is a UI-spoofing bug where the sharing dialog rendered an untrusted origin as if it were a trusted one, letting an attacker misrepresent identity to the user. The closest reachable analog in `ocore` is in the asset-metadata mechanism (`readAssetMetadata`/`fetchAssetMetadata` in `wallet.js`), where the human-readable `name` shown to wallet users for an asset is supplied by an arbitrary, attacker-controllable "registry" address and is trusted without any mechanism that guarantees global uniqueness or a reliable disambiguating suffix, so two different assets from two different (attacker vs. legitimate) registries can be displayed under the identical name.

### Finding Description
`fetchAssetMetadata()` [1](#0-0)  requests `hub/get_asset_metadata` for an asset and receives `metadata_unit`, `registry_address`, and `suffix` directly from the hub/peer response. It validates only that `metadata_unit` is a well-formed hash and `registry_address` is a syntactically valid address — it does not verify that `registry_address` is the actual issuer of `asset`, nor that it is any kind of trusted/whitelisted registry [2](#0-1) .

It then reads the referenced unit and confirms only that the unit was authored by `registry_address` [3](#0-2) , extracts the `data` message whose `payload.asset === asset`, and stores `payload.name` (plus the hub-supplied `suffix`) into `asset_metadata` [4](#0-3) .

The DB schema enforces uniqueness only on `(name, registry_address)`, not on `name` alone [5](#0-4) , and the comment even documents that a `suffix` is supposed to be "added only if the same name is registered by different registries for different assets, equal to registry name" [6](#0-5) . However, that disambiguation logic is never computed locally by the wallet — the `suffix` is taken verbatim from the (attacker-controllable) hub response `response.suffix` [7](#0-6) [8](#0-7) , so a malicious registry can simply omit/blank the suffix, or choose any `name`, and the client will display it just like a genuine well-known asset's name, since `readAssetMetadata()` renders `row.suffix ? row.name+'.'+row.suffix : row.name` purely from stored (attacker-influenced) fields [9](#0-8) .

Because *any* address can act as a "registry" for *any* asset id (the code never checks that `registry_address` equals the asset's issuer, and `INSERT ... IGNORE` for non-"updatable" registries means whichever registry posts first for a given asset wins permanently, see `isUpdatableRegistry()` gating only a hardcoded `conf.updatableAssetRegistries` allow-list [10](#0-9) ), an attacker who is fast to register metadata for a target asset, or who registers their own worthless asset with a name string colliding with a well-known token, can make the wallet UI display an identical or confusingly similar "name" for two entirely different assets — this is the direct behavioral analog of Chrome's incorrect sharing UI that let a malicious page spoof a trusted domain.

### Impact Explanation
Wallet users typically identify assets by their short displayed `name` (e.g., a ticker) rather than the full 44-character asset hash. If an attacker can cause their unrelated/worthless asset to display under the same recognizable name as a legitimate, valuable asset (with no distinguishing suffix, since the suffix is attacker-supplied and not independently computed/verified), a user can be deceived into believing a payment request, invoice, or received output is denominated in the legitimate well-known asset when it is not. This can lead a private-payment counterparty to accept a worthless asset believing it is a valuable one, or to send funds intending to pay in a legitimate asset but interacting with the spoofed one — a concrete loss-of-funds/deception scenario reachable simply by any unprivileged party creating an asset and issuing a metadata-registration unit, i.e., normal wallet/asset-issuance functionality with no special privilege required.

### Likelihood Explanation
Any user of the network can issue a new asset and post a `data` app message declaring themselves the "registry" for that asset with a chosen `name`. No permission, coordination, or privileged/network position (hub, node, or peer compromise) is required — this is fully achievable by a single unprivileged asset issuer using standard oscript/ojson `data` messages, which is exactly the "asset issuance and transfer conditions" surface explicitly listed as in-scope. The only obstacle is racing to register the *same real* victim asset id (which is somewhat harder since asset ids are fixed by their genuine definitions), but trivially achievable when spoofing via a *new* attacker-issued asset that simply reuses the same display `name` under a different registry address with an empty/blank suffix.

### Recommendation
Do not trust the hub-supplied `suffix` as an authoritative disambiguator. When storing/displaying asset metadata, the wallet should locally detect name collisions across different `registry_address` values for the same `name` and deterministically compute/display a disambiguating suffix (e.g., derived from `registry_address` or a registry's own attested name) rather than accepting an attacker-controlled `suffix` field verbatim. Additionally, consider requiring/preferring metadata where `registry_address` matches a known/trusted registry list, and always surface the full asset hash (or a truncated but collision-resistant identifier) alongside the friendly `name` so users can distinguish look-alike assets, analogous to how browsers were hardened to always show the full/verified origin during sharing rather than a spoofable label.

### Proof of Concept
1. Attacker issues a new asset `A2` via a standard `asset` definition message (any unprivileged user can do this).
2. Attacker crafts and broadcasts a `data`-app unit authored by address `R_attacker`, with payload `{asset: A2, name: "USDT", decimals: 6}` — this is the "registry" unit.
3. Attacker runs (or is answered by) a hub that responds to `hub/get_asset_metadata` for `A2` with `{metadata_unit: <that unit>, registry_address: R_attacker, suffix: ""}` (no suffix).
4. Victim wallet calls `fetchAssetMetadata(A2, ...)` — passes all existing checks (`metadata_unit` well-formed, `registry_address` valid, unit author matches `registry_address`, `payload.name` present) in `wallet.js` [11](#0-10)  and stores `name: "USDT"` with no suffix in `asset_metadata`.
5. `readAssetMetadata()` subsequently displays asset `A2` to the user simply as `"USDT"` [9](#0-8) , indistinguishable in the UI from the legitimate USDT-equivalent asset registered by the real registry, enabling the attacker to trick a payment counterparty into treating `A2` as the trusted asset.

```javascript
function fetchAssetMetadata(asset, handleMetadata){
	device.requestFromHub('hub/get_asset_metadata', asset, function(err, response){
		if (err){
			if (err === 'no metadata')
				assocLastFailedAssetMetadataTimestamps[asset] = Date.now();
			return handleMetadata("error from get_asset_metadata "+asset+": "+err);
		}
		var metadata_unit = response.metadata_unit;
		var registry_address = response.registry_address;
		var suffix = response.suffix;
		if (!ValidationUtils.isStringOfLength(metadata_unit, constants.HASH_LENGTH))
			return handleMetadata("bad metadata_unit: "+metadata_unit);
		if (!ValidationUtils.isValidAddress(registry_address))
			return handleMetadata("bad registry_address: "+registry_address);
		var fetchMetadataUnit = conf.bLight 
			? function(onDone){
				network.requestProofsOfJointsIfNewOrUnstable([metadata_unit], onDone);
			}
			: function(onDone){
				onDone();
			};
		fetchMetadataUnit(function(err){
			if (err)
				return handleMetadata("fetchMetadataUnit failed: "+err);
			storage.readJoint(db, metadata_unit, {
				ifNotFound: function(){
					handleMetadata("metadata unit "+metadata_unit+" not found");
				},
				ifFound: function(objJoint){
					if (objJoint.unit.authors[0].address !== registry_address)
						return handleMetadata("registry address doesn't match: expected " + registry_address + ", got " + objJoint.unit.authors[0].address);
					objJoint.unit.messages.forEach(function(message){
						if (message.app !== 'data')
							return;
						var payload = message.payload;
						if (payload.asset !== asset)
							return;
						if (!payload.name)
							return handleMetadata("no name in asset metadata "+metadata_unit);
						var decimals = (payload.decimals !== undefined) ? parseInt(payload.decimals) : undefined;
						if (decimals !== undefined && !ValidationUtils.isNonnegativeInteger(decimals))
							return handleMetadata("bad decimals in asset metadata "+metadata_unit);
						var verb = isUpdatableRegistry(registry_address) ? "REPLACE" : "INSERT " + db.getIgnore();
						db.query(
							verb + " INTO asset_metadata (asset, metadata_unit, registry_address, suffix, name, decimals) \n\
							VALUES (?,?,?, ?,?,?)",
							[asset, metadata_unit, registry_address, suffix, payload.name, decimals],
							function(){
								var objMetadata = {
									metadata_unit: metadata_unit,
									suffix: suffix,
									decimals: decimals,
									name: payload.name
								};
								handleMetadata(null, objMetadata);
							}
						);
					});
```

```javascript
}
```
