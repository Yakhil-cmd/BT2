### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unverified `repository.full_name` — allows cross-repository event spoofing in a multi-org Shipit deployment - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from the payload itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw JSON body is dispatched unchanged to the event handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) 

Nothing ties `repository.full_name` back to `repository.owner.login` (the field that was actually authenticated by the HMAC check). In a Shipit installation configured with more than one GitHub App/organization (as documented in `config/secrets.development.shopify.yml`, each org has its own `webhook_secret`), an attacker who legitimately controls one configured organization's webhook secret (e.g., because they administer their own GitHub App entry that Shipit trusts) can sign a payload where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` resolves to *their* app and `verify_webhook_signature` succeeds with their own secret), while
- `repository.full_name` = `"victim-org/victim-repo"` (any other repository already registered in Shipit).

This breaks the binding: `organization authenticated by signature == organization whose repository is written to by the handler`. The equality that must hold is `repository_owner (verified) == repository.full_name.split('/').first (acted upon)`, but the code never enforces it.

### Impact Explanation
Exploiting this a `push` event lets the attacker trigger `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` on every not-archived stack of the victim repository matching the given branch — forcing a GitHub sync to an attacker-chosen `after` SHA. [5](#0-4) 
A `status` event lets the attacker inject a fabricated commit status (`state`, `description`, `context`) on any commit SHA already tracked by Shipit for the victim stack via `Commit#create_status_from_github!`. [6](#0-5) 
A `check_suite` event lets the attacker force `schedule_refresh_check_runs!` on victim commits. [7](#0-6) 

Since Shipit deployability/merge/deploy gating typically depends on commit statuses and check runs being green, an attacker who can forge a passing `status`/`check_suite` payload for a victim repository could get Shipit to treat an unreviewed commit as deployable/mergeable, i.e., an **unauthorized deploy/merge path**, which matches the required Critical/High impact bar (unauthorized deploy). This requires the deployment to be configured with more than one organization's GitHub App/webhook secret, which is the intended and documented multi-org configuration shape (`config/secrets.development.shopify.yml`), not a misconfiguration outside the engine's contract.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with ≥2 organizations (each with its own `webhook_secret`), and (2) the attacker to have legitimate control of one of those org's webhook delivery (i.e., be able to make GitHub deliver, or forge, a signed webhook for their own org — which is a standard capability of anyone administering that org's GitHub App, not a privileged Shipit credential). This is a realistic and commonly-deployed configuration for organizations running one Shipit instance across multiple GitHub orgs.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, enforce that the organization used to select the webhook secret matches the owner of `repository.full_name` (i.e., derive `repository_owner` strictly from `full_name.split('/').first` rather than trusting the separate `repository.owner.login`/`organization.login` field, or explicitly assert equality between the two before processing).

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `victim-org` (no webhook secret access to attacker) and `attacker-org` (attacker controls the app/secret).
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha already known/tracked>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the signature check passes (`verify_webhook_signature`). [1](#0-0) 
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, and calls `sync_github(expected_head_sha: ...)` on the victim's stacks, even though the signature was never verified against `victim-org`'s secret. [4](#0-3)
