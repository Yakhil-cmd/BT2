### Title
Attacker-controlled commit message overwrites `Commit#author` with an arbitrary victim identity - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` parses the free-text GitHub commit message for a `Merge-Requested-By: <login>` line and, if found, unconditionally attributes authorship of that commit to the named Shipit user via `find_or_create_by_login!`, with no check that the commit is an actual Shipit-generated merge commit or that the named user requested anything. Any commit fetched via `Commit.from_github`/`Commit.create_from_github!` — including ordinary commits pushed inside an attacker's own pull request — is subject to this parsing, so an attacker can forge the `author` of a recorded `Commit` to be any existing Shipit login.

### Finding Description
The broken binding: `Commit#author` (the identity recorded as having authored/requested the commit for audit/trust purposes) should equal the GitHub identity that authenticated the push/commit (`github_commit.commit.author`/`github_commit.author`), i.e. `Commit#author == github_commit.author`. Instead, `User.find_or_create_author_from_github_commit` lets `Commit#author == <arbitrary attacker-chosen login extracted from commit.commit.message>` whenever the message matches the pattern.

Code path:
- `app/models/shipit/user.rb:34-44` — `find_or_create_author_from_github_commit` matches `/^Merge-Requested-By: ([\w\-.]+)$/` against `github_commit.commit.message` (fully attacker-controlled free text) and, on match, calls `find_or_create_by_login!(match_info[1])`, returning that user as the commit's author without any further validation. [1](#0-0) 
- `Commit.from_github` calls this method directly to populate `author:` for any commit fetched from GitHub. [2](#0-1) 
- `Commit.from_github`/`create_from_github!` is reachable from `PullRequest#find_or_create_commit_from_github_by_sha!` (invoked when populating `github_pull_request=`, i.e. any PR sync/webhook processing for a PR the attacker opened) and from `MergeRequest#find_or_create_commit_from_github_by_sha!`. [3](#0-2) [4](#0-3) 

The `Merge-Requested-By` field is intended to be written only by Shipit itself when it performs a merge (`MergeRequest#merge_message`, used in `MergeRequest#merge!`), to attribute the resulting GitHub merge commit to the chatops/UI user who requested the merge. [5](#0-4) [6](#0-5)  However, nothing in `find_or_create_author_from_github_commit` restricts the match to commits actually produced by that merge flow (e.g. verifying the commit is the stored `merge_commit` for a `MergeRequest` with a matching `merge_requested_by`). Any commit — including a normal, non-merge commit the attacker pushes to their own branch/fork with the literal text `Merge-Requested-By: <victim-login>` in the commit message — is parsed identically once it reaches `Commit.from_github` through ordinary PR sync/webhook code paths. There is no signature verification tying the commit message content to any Shipit action; `find_or_create_by_login!` will happily create/fetch a `User` row and bind it as `author_id` on the `Commit`.

No existing guard (`verify_signature`, `ExplicitParameters`, `force_github_authentication`, model validations) checks this: the commit message is normal GitHub payload content, not a signed authorization artifact, and `find_or_create_by_login!` only checks the login exists on GitHub — it does not check the login is related to the actual pushing identity.

### Impact Explanation
An attacker can cause a `Shipit::Commit` row belonging to any tracked repository/stack to have `author_id` pointing at an arbitrary existing Shipit user (e.g., a maintainer), without that user taking any action. This corrupts an audit-trail/attribution field (`Commit#author`, exposed via `commit_serializer`, deploy summaries `app/views/shipit/deploys/_summary.html.erb`, and `deploy_requested_at`/`merge_request.merge_requested_by` linkage in `Commit#identify_merge_request`). The affected record is written for a repository that did authenticate the webhook/PR event (the attacker's own repo/PR), but the identity bound to it is not the identity that authenticated — this is an identity-binding integrity issue, not a cross-tenant/RCE/secret-exfiltration issue. It is repeatable against any repository tracked by Shipit and any known Shipit login the attacker can discover in the UI, but its scoped impact is limited to falsified authorship/attribution metadata; I found no code path where `Commit#author` alone is consulted for a privileged decision such as bypassing `require_permission!`, granting `Shipit.github_teams` membership, or authorizing a deploy/merge/rollback without other independent checks (deploys/merges still require the deploying user's own permissions via controller-level authorization, not the commit author field).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to open a PR (or push a commit) against a Shipit-tracked repository with a crafted commit message, and know an existing Shipit login (visible via the UI). No secrets, tokens, or elevated GitHub/Shipit permissions are required. The commit merely needs to be synced (via webhook-driven PR processing or merge-queue head/base commit fetch) to trigger `Commit.from_github`. This is low-cost and repeatable per commit/PR.

### Recommendation
Restrict the `Merge-Requested-By` parsing so it only applies to commits Shipit itself created via the merge flow: e.g., instead of parsing arbitrary commit message text in `User.find_or_create_author_from_github_commit`, attribute merge-commit authorship by looking up the `MergeRequest` for the PR (already resolved in `Commit#identify_merge_request` via `stack.merge_requests.find_by(number:)`) and using its `merge_requested_by` association directly, removing the free-text regex parse entirely from untrusted commit message content. If the free-text marker must be kept for backward compatibility, at minimum validate that the commit is a genuine merge commit produced by Shipit for a `MergeRequest` whose `merge_requested_by.login` matches the parsed value before trusting it.

### Proof of Concept
```ruby
# test/models/commits_test.rb (minitest)
test "from_github does not let an attacker-authored commit message forge authorship of another user" do
  victim = shipit_users(:walrus) # existing Shipit user, e.g. a maintainer

  github_commit = resource(
    sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
    commit: {
      author: { name: 'attacker', email: 'attacker@evil.example', date: Time.now.utc },
      committer: { name: 'attacker', email: 'attacker@evil.example', date: Time.now.utc },
      message: "Add malicious feature\n\nMerge-Requested-By: #{victim.login}\n"
    },
    author: nil,
    committer: nil
  )

  commit = Shipit::Commit.from_github(github_commit)

  # LHS: the identity that "authenticated" this action is the attacker (via commit.author/committer),
  # not `victim`.
  refute_equal victim.login, github_commit.commit.author.name

  # RHS: yet Commit#author is bound to the victim purely from attacker-controlled text.
  assert_equal victim.login, commit.author.login
end
```
This demonstrates the divergence: the party that authenticated the GitHub action (attacker's own commit) is not the party recorded as `Commit#author` (the victim), with nothing in the code reconciling the two.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end

    end
