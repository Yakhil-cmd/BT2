### Title
Webhook Signature Verification Uses `repository.owner.login` But Handlers Act On The Independent `repository.full_name` Field, Allowing Cross-Organization Webhook Forgery When Any Configured GitHub App Has No `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` config (and thus which `webhook_secret`) to verify the inbound signature against using `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request whenever that selected app's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 

Every webhook handler, however, determines which `Repository`/`Stack` to actually mutate using a *different* field of the same attacker-controlled body: `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `Handler#stacks`. [4](#0-3) 

Nothing cross-checks that `repository.owner.login` (the field that selected the signature-verification key) matches the owner segment embedded in `repository.full_name` (the field the handler actually trusts). This is the same class of bug as `SignatureValidator::setAllowlist`: the field that is verified (or, here, that selects the verification key) is not the field that is subsequently acted upon.

### Finding Description
The binding the engine is supposed to enforce is:
`organization whose secret authenticated the request == organization of the repository the handler mutates`

Before the fix this binding holds only by convention (both fields normally come from the same real GitHub payload). An attacker who can get a raw POST to `/github/auth/../webhooks` (or wherever `WebhooksController` is mounted) with an arbitrary JSON body can break it as soon as **any** GitHub App/organization configured in `Shipit.github_configs` has a blank `webhook_secret`. This is an explicitly supported configuration — the engine's own docs and generator template ship a `webhook_secret:` field intended to be optional, and the test fixtures include a second app entry with `webhook_secret: # nil` alongside a first app that does have a secret, confirming multi-org, mixed-secret deployments are a first-class supported case. [5](#0-4) [6](#0-5) 

Attack sequence:
1. Attacker crafts a webhook payload where `repository.owner.login` = `OrgWithoutSecret` (any org configured in this Shipit instance whose `webhook_secret` is nil/blank) — this makes `verify_signature` pick `Shipit.github(organization: 'OrgWithoutSecret')`, whose `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header sent. [1](#0-0) 
2. In the same payload, attacker sets `repository.full_name` = `TargetOrg/protected-repo`, the real, secret-protected repository they want to attack.
3. `create` dispatches to the matching handlers (`push`, `status`, `check_suite`, `pull_request`, etc.), all of which resolve the target `Repository`/`Stack` from `repository.full_name`, not from `repository.owner.login`. [7](#0-6) [4](#0-3) 

The attacker has thereby authenticated as `OrgWithoutSecret` but written state belonging to `TargetOrg`'s repository — exactly the "organization that authenticated versus the repository that is written" binding the scan is looking for.

### Impact Explanation
Once inside, the attacker can forge any handled GitHub event for a repository they do not control and have no real webhook secret for, e.g.:
- Forge `status` events to inject fabricated commit `Status` rows (state/context/target_url) for `TargetOrg`'s stack, which Shipit reads to gate deploy safety (CI status checks) — this can be used to make an otherwise-blocked commit look green and enable an unauthorized deploy through the normal UI/API flow.
- Forge `push` events to enqueue `GithubSyncJob` for `TargetOrg`'s stack, manipulating which commits Shipit believes are undeployed.
- Forge `pull_request`/`membership` events to affect merge-queue state, team membership records, etc. tied to `TargetOrg`.

This satisfies the "unauthorized deploy" / cross-repository-write impact bar, because it lets an attacker with no credentials for `TargetOrg` and no valid signature for `TargetOrg`'s webhook secret still make Shipit believe an event legitimately came from GitHub for that repository.

### Likelihood Explanation
Requires the operator's Shipit install to be configured for at least two GitHub organizations where at least one has no `webhook_secret` set — a state the engine's own docs/generator explicitly allow and the test fixtures explicitly exercise (`secrets_double_github_app.yml`). Any installation following the documented multi-org setup while leaving one app's webhook secret unset (e.g., a staging/sandbox GitHub App) exposes every other configured organization's repositories to this cross-organization forgery. No GitHub credentials, API tokens, or repository access are needed by the attacker.

### Recommendation
Do not let the signature-selection key and the handler's target-resolution key diverge:
- After a successful signature check, re-derive the "authenticated organization" from the verified payload and assert it matches the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers; reject (422) on mismatch.
- Alternatively, make `verify_webhook_signature` fail closed (return `false`, not `true`) when `webhook_secret` is blank for a configured organization, and require every configured GitHub App to have a non-blank `webhook_secret` at boot/config-validation time.

### Proof of Concept
Given a Shipit instance configured with two GitHub Apps: `SafeOrg` (no `webhook_secret`, as allowed by `test/dummy/config/secrets_double_github_app.yml`'s `OrgTwo`) and `TargetOrg` (has a `webhook_secret`, with a real Stack tracking `TargetOrg/protected-repo`):

```
POST /github/auth/github/../webhooks   (whatever path WebhooksController is mounted at)
X-Github-Event: status
X-Hub-Signature: sha1=anything-invalid

{
  "sha": "<head sha of protected-repo>",
  "state": "success",
  "target_url": "https://attacker.example.com",
  "context": "ci/required-check",
  "created_at": "...",
  "repository": {
    "full_name": "TargetOrg/protected-repo",
    "owner": { "login": "SafeOrg" }
  }
}
```

`repository_owner` resolves to `SafeOrg`, so `Shipit.github(organization: 'SafeOrg').verify_webhook_signature(...)` short-circuits to `true` because `SafeOrg` has no `webhook_secret` [8](#0-7) 
, even though the `X-Hub-Signature` header is garbage. The `status` handler then resolves the commit/stack from `repository.full_name = "TargetOrg/protected-repo"` [9](#0-8) 
and writes a forged successful `Status` for `TargetOrg`'s real, secret-protected repository — with no valid signature ever produced for `TargetOrg`.
