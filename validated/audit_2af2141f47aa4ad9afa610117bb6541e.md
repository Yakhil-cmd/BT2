### Title
`unit[hash]` Oscript Builtin Returns Unwrapped, Uncloned Host Object Reference Enabling Formula-Side Mutation of Shared Unit/Joint State - (File: `formula/evaluation.js`)

### Summary
The `unit` built-in in the oscript formula evaluator wraps the JS object returned by `storage.readJoint()` directly into a `wrappedObject` without performing the defensive `string_utils.cloneDeep()` copy that every other object-returning builtin in the same evaluator performs. This mirrors the vm2 CVE-2026-44000 root cause pattern: a value crossing from the "host" (node process object graph, including cached joint/unit data) into the "sandbox" (oscript formula execution reachable from an AA trigger sender) is delivered with its original identity intact instead of through a copy/proxy, so mutations performed inside the sandboxed formula write straight through to host state.

### Finding Description
Every branch in `evaluate()` that returns object data to the formula wraps a **cloned** copy:
- `trigger.data`/`params`: `cb(new wrappedObject(string_utils.cloneDeep(value)))` [1](#0-0) 
- `previous_aa_responses`: `cb(new wrappedObject(string_utils.cloneDeep(objValidationState.arrPreviousAAResponses)))` [2](#0-1) 
- `trigger.outputs`: `cb(new wrappedObject(string_utils.cloneDeep(trigger.outputs)))` [3](#0-2) 
- the two `unit[...]` fast paths that read from `objResponseUnit` / `arrPreviousAAResponses`: both use `string_utils.cloneDeep(...)` [4](#0-3) 

However, the third `unit[...]` path — the one that reads an already-stable unit via `storage.readJoint()` — wraps the object **without cloning**:
```
ifFound: function (objJoint, sequence) {
    var objUnit = objJoint.unit;
    ...
    objectHash.cleanNulls(objUnit);            // in-place mutation
    for (let m of objUnit.messages)
        if (m.app === "temp_data")
            delete m.payload.data;              // in-place mutation
    cb(new wrappedObject(objUnit));             // NOT cloned, unlike every sibling branch
}
``` [5](#0-4) 

Two things stand out:
1. The code already mutates `objUnit` in place (`cleanNulls`, `delete m.payload.data`) before wrapping it, which only makes sense if `objUnit` can be a long-lived/shared object (e.g., served by a joint/unit cache) rather than a throwaway per-call allocation — otherwise these in-place edits would be pointless busywork on a disposable object.
2. `wrappedObject` here holds `objUnit` by reference, and formula code that stores this wrapped object in a local variable can mutate its contents through the `local_var_assignment` selector path, which writes directly onto `.obj`:
```
assignByPath(locals[var_name].obj, arrKeys, res);
``` [6](#0-5) 

Because `.obj` is the same object instance returned by `storage.readJoint()` (not a clone), any oscript formula that does something like:
```
$u = unit[$some_unit_hash];
$u.messages[0].payload.outputs[0].amount = 999999999;
```
mutates the exact object that `storage.readJoint()` handed out — not a private copy. If that object is shared (returned again from an in-memory joint cache on a subsequent lookup, reused by a concurrent AA evaluation within the same batch, or reused across getter/trigger executions in the same validation pass), the mutation performed inside one formula evaluation becomes visible to any other code path that subsequently reads the "same" unit object, exactly as the vm2 report demonstrates write-through mutation of a host object exposed through `Promise.then()`.

This is the same bug class as the report: a value transitions from a "host"-controlled data source into "sandboxed" formula logic without the isolation boundary (deep copy / wrapping) that the rest of the same function consistently applies everywhere else.

### Impact Explanation
If the underlying `objUnit` returned by `storage.readJoint()` is ever reused (via caching, via being read again later in the same or another AA's evaluation within the same trigger-processing session, or via any other consumer holding a reference to the same joint object), a formula-triggered mutation could:
- Corrupt cached unit data read by subsequent formula evaluations or getters, causing different nodes to observe different data for the "same" unit depending on cache state timing — a direct **node disagreement on validity or stability** scenario, since AA/bounce determinism across the network requires byte-identical evaluation results for identical triggers.
- Allow a hostile AA author to design a formula that corrupts amounts/messages of a referenced historical unit as observed by later logic in the same evaluation pipeline, potentially influencing derived state-variable or response-unit computation that depends on `unit[...]` data, leading to incorrect AA outputs (fund loss/freezing) if that corrupted view feeds into payment or balance logic.

This satisfies the Medium/High bar of "node disagreement on validity or stability" or "AA fund loss," contingent on the object identity actually being shared/cached elsewhere in the runtime (see caveat below).

### Likelihood Explanation
Reachability is straightforward: any AA trigger sender or AA author can write a formula using the documented `unit[hash]` oscript operator, which is a standard, unprivileged, publicly documented AA feature — no special privilege is required. The missing `cloneDeep` is a clear, deterministic code-pattern deviation from every sibling branch in the same function, which raises confidence that it is an oversight rather than an intentional performance optimization. The main uncertainty is whether `storage.readJoint()`'s returned unit object is definitely backed by a shared/cached reference in this codebase revision — I was not able to inspect `storage.js`'s `readJoint`/joint-cache implementation in the available tool budget to conclusively confirm object reuse across calls, so the severity is contingent on that caching behavior, but the in-place `cleanNulls`/`delete payload.data` calls at lines 1611–1614 are strong circumstantial evidence that the authors already anticipated a shared, mutable object here.

### Recommendation
Apply the same defensive-copy discipline used everywhere else in `evaluate()`: change `cb(new wrappedObject(objUnit));` to `cb(new wrappedObject(string_utils.cloneDeep(objUnit)));` in the `storage.readJoint` `ifFound` callback of the `unit` case, so that formula-side mutations of the wrapped result can never write through to the underlying joint/unit object that `storage.readJoint()` returns. [7](#0-6) 

### Proof of Concept
```
// oscript formula reachable from any AA trigger:
$u = unit[$some_stable_unit_hash];       // wraps objUnit WITHOUT cloning (line 1615)
$u.messages[0].payload.outputs[0].amount = 999999999;  // mutates locals[$u].obj in place
                                          // via assignByPath (line 1284), which is the
                                          // same object instance storage.readJoint() returned
```
If `storage.readJoint()` serves the same in-memory object on a subsequent lookup (cache hit) — e.g., from a later formula evaluation, getter call, or a different AA processed in the same batch that also reads `unit[$some_stable_unit_hash]` — that later read observes the mutated `amount`, demonstrating write-through corruption of host-side unit data from within oscript formula execution, analogous to the vm2 PoC's host-object mutation via `hostPromise.then(v => { v.nested.x = 999; ... })`.
