### Title
Unprivileged stake-account mutation during the epoch-rewards distribution window can trigger a consensus-critical panic - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Partitioned epoch rewards are calculated once, at the epoch boundary, from a snapshot of `StakesCache`, but are *paid out* over many subsequent blocks. During that payout window, a stake account owner can send ordinary, unprivileged stake-program instructions (e.g. `Split`, `Merge`, `Deactivate`, `DelegateStake`) that mutate the same account's `Delegation::stake` in the live `StakesCache` before its reward partition is processed. When the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is inactive, `build_updated_stake_reward` assumes the live delegation value is still exactly the pre-reward snapshot value plus the calculated reward and enforces this with a hard `assert_eq!`. This is the exact "cached balance vs. actual dynamically-changed balance" mismatch described in the wibBTC/Curve report, applied to Solana's stake/reward accounting instead of an ERC‑20 rebasing token.

### Finding Description
Reward calculation snapshots stake delegations from `self.stakes_cache.stakes()` at the epoch boundary and stores the computed `PartitionedStakeReward` (containing the *expected* post-reward `Stake` and `stake_reward`) in `Bank::epoch_reward_status`: [1](#0-0) .

Distribution happens over multiple subsequent blocks; each block distributes one partition via `distribute_partitioned_epoch_rewards` → `store_stake_accounts_in_partition` → `build_updated_stake_reward`: [2](#0-1) .

`build_updated_stake_reward` re-fetches the *current, live* stake account from `stakes_cache_accounts` (not the value that existed at calculation time), then reconciles it with the pre-computed reward: [3](#0-2) 

When `adjust_delegations_for_rent` is false, the code does not compute a fresh delegation from the live account state; it simply asserts that the live `stake.delegation.stake` (fetched from `StakesCache` at distribution time) plus the previously-calculated `stake_reward` equals the delegation value that was computed during the earlier calculation phase:

Between the reward-calculation block and the block that processes this particular stake account's partition (which can be many blocks later — up to `slots_per_epoch / 10`, see `get_reward_distribution_num_blocks` at [4](#0-3) ), the stake account owner is free to submit ordinary stake-program instructions. No gating mechanism was found in the reward-distribution code path (`distribute_partitioned_epoch_rewards`, `get_reward_interval`, etc. — see [5](#0-4) ) that blocks stake instructions while a reward is pending for that account, unlike the calculation-time `StakesCache` which is a fixed, consistent snapshot. If the owner performs e.g. a `Split` (which reduces the source account's `delegation.stake` and creates a new account) or a `Redelegate`/`DelegateStake`, the live `delegation.stake` read here will differ from the value implicitly baked into `partitioned_stake_reward.inflation.stake` at calculation time, and `expected_delegation != new_stake.delegation.stake`, tripping the `assert_eq!`.

This mirrors the wibBTC finding precisely: the reward-distribution logic treats the calculation-time snapshot of stake delegation as if it were a static, Curve-pool-style cached "reserve" that only the reward-distribution code itself updates, but the underlying stake account's balance/delegation can change dynamically and automatically outside that flow (via ordinary user stake instructions), and there is no reconciliation ("sync") mechanism for the non-feature-gated code path.

### Impact Explanation
An `assert_eq!` failure panics the executing thread inside bank-freeze/replay processing for a slot. Because this occurs during normal block replay of a legitimately-signed, unprivileged user transaction (a stake-program instruction issued by the stake account's own authority), it can be triggered deterministically by any staker and will be hit by every validator that replays the same block, producing a cluster-wide panic/halt at (or shortly after) an epoch boundary rather than a single-node crash. This falls squarely in the "epoch-boundary halt" impact category.

### Likelihood Explanation
Likelihood depends on whether `relax_post_exec_min_balance_check` (the feature gating `adjust_delegations_for_rent`) is activated cluster-wide. Prior to its activation (or on any cluster/testnet where it is not yet active), any staker with a pending, not-yet-distributed inflation reward can trivially trigger this by issuing a `Split` or similar delegation-mutating instruction during the multi-block reward distribution window — this requires no special privileges, only a normal stake account and a wallet capable of signing stake-program instructions.

### Recommendation
- Remove the hard `assert_eq!` in the non-`adjust_delegations_for_rent` branch of `build_updated_stake_reward`; instead, recompute the post-reward delegation from the *live* account state (as the `adjust_delegations_for_rent` branch already does) rather than assuming the calculation-time delegation is still valid.
- Alternatively, disallow stake-program instructions that mutate `Delegation::stake` (e.g. `Split`, `Merge`, `DelegateStake`) for accounts with a pending, undistributed partitioned reward, mirroring the reconciliation approach BadgerDAO adopted for wibBTC (rate-aware pool logic) rather than assuming a static snapshot.
- Add fuzzing/property tests that interleave stake-mutating instructions with epoch-reward calculation/distribution across multiple blocks (not just the "extra lamports added" scenario already covered by `test_delegation_adjustment_at_distribution`) to ensure the non-feature-gated path is likewise robust.

### Proof of Concept
1. Create a stake account `S` delegated to vote account `V` with a rewardable stake.
2. Advance to an epoch boundary so that `S` receives a computed `PartitionedStakeReward` (as exercised by `test_rewards_computation_and_partitioned_distribution_multi_blocks`, [6](#0-5) ), landing in a partition that is not distributed in the very next block (i.e., `num_partitions > 1`).
3. In a subsequent block prior to `S`'s distribution partition (while `relax_post_exec_min_balance_check` is inactive), submit a normal `Split` instruction from `S`'s stake authority, reducing `S`'s on-chain `Delegation::stake`.
4. When `S`'s partition is later processed, `store_stake_accounts_in_partition` → `build_updated_stake_reward` fetches the now-reduced `Delegation::stake` from `StakesCache`, computes `expected_delegation = reduced_stake + stake_reward`, which no longer equals the calculation-time `new_stake.delegation.stake`, and the `assert_eq!` at [7](#0-6)  panics.

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    #[derive(Debug, PartialEq, Eq, Copy, Clone)]
    enum RewardInterval {
        /// the slot within the epoch is INSIDE the reward distribution interval
        InsideInterval,
        /// the slot within the epoch is OUTSIDE the reward distribution interval
        OutsideInterval,
    }

    impl Bank {
        /// Return `RewardInterval` enum for current bank
        fn get_reward_interval(&self) -> RewardInterval {
            if matches!(self.epoch_reward_status, EpochRewardStatus::Active(_)) {
                RewardInterval::InsideInterval
            } else {
                RewardInterval::OutsideInterval
            }
        }

        fn is_calculated(&self) -> bool {
            matches!(
                self.epoch_reward_status,
                EpochRewardStatus::Active(EpochRewardPhase::Calculation(_))
            )
        }

        fn is_partitioned(&self) -> bool {
            matches!(
                self.epoch_reward_status,
                EpochRewardStatus::Active(EpochRewardPhase::Distribution(_))
            )
        }

        fn get_epoch_rewards_from_cache(
            &self,
            parent_hash: &Hash,
        ) -> Option<Arc<PartitionedRewardsCalculation>> {
            self.epoch_rewards_calculation_cache
                .lock()
                .unwrap()
                .get(parent_hash)
                .cloned()
        }

        fn get_epoch_rewards_cache_len(&self) -> usize {
            self.epoch_rewards_calculation_cache.lock().unwrap().len()
        }
    }
