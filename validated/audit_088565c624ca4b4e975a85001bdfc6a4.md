### Title
Cross-stack CCMenu deploy status leak via stack-scoped API token replayed against arbitrary `stack_id` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates the token but resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the base `#stacks`-scoped lookup, so a `read:stack` token minted for Stack A via `CCMenuUrlController#fetch` can be replayed against `GET /api/stacks/:other_stack_id/ccmenu.xml` for Stack B and will render Stack B's deploy/rollback status.

### Finding Description
The intended binding is `stack.id == current_api_client.stack_id` — i.e., an `ApiClient` scoped to a specific stack (`current_api_client.stack_id?` true) must only ever resolve `stack` to that one stack. This is exactly what `Shipit::Api::BaseController#stacks`/`#stack` implement: [1](#0-0) 

However `Api::CCMenuController` overrides `#stack` and bypasses this scope entirely: [2](#0-1) 

Authentication (`authenticate_api_client`) only verifies the token's signature and existence, not stack scoping: [3](#0-2) 

The only permission check performed is `require_permission :read, :stack`, which delegates to `ApiClient#check_permissions!`, checking merely that the permission string `"read:stack"` is present in `permissions` — it never compares `current_api_client.stack_id` to the requested stack: [4](#0-3) 

So for a token minted with `permissions: %w[read:stack]` and a `stack_id` bound to Stack A (via `CCMenuUrlController#client`/`#fetch`): [5](#0-4) 

nothing in `Api::CCMenuController#show` restricts the resolved `stack` to Stack A; `Stack.from_param!(params[:stack_id])` will happily resolve Stack B if the attacker (who legitimately owns Stack A and obtained a valid token for it) supplies Stack B's id/slug in the URL: [6](#0-5) 

The base controller's `#stacks` scoping guard, which is the actual enforcement mechanism for per-stack `ApiClient` tokens elsewhere in the API, is simply never invoked for this endpoint because `CCMenuController` defines its own conflicting `#stack` method.

### Impact Explanation
An attacker who legitimately owns/administers Stack A can request a CCMenu token bound to Stack A, then reuse that authenticated token against `GET /api/stacks/:stack_id/ccmenu.xml` for any other stack ID/slug in the same Shipit instance, and receive that stack's latest deploy/rollback status (deploy id, status, ended_at, running state) in the response XML. This is a cross-tenant unauthorized read of another stack's task/deploy state, repeatable against every stack the attacker can guess/enumerate slugs for, matching the High severity category ("unauthenticated/unauthorized read of stack state, task streams or deploy output" across tenants — here escalated because it uses a token scoped to one stack to read another's private stack).

### Likelihood Explanation
The attacker needs no special privileges beyond being a normal Shipit user who can create/own at least one stack (a very low bar, and explicitly within the "unprivileged attacker" definition since they hold a valid session as a user, not an operator or team member). They call `CCMenuUrlController#fetch` for their own stack to legitimately mint a `read:stack` token, then simply substitute a different `stack_id` in the query when calling the API endpoint directly — no secrets, signing keys, or GitHub credentials required. This is trivially repeatable for any stack.

### Recommendation
Remove the overriding `#stack` method in `Api::CCMenuController` (or reimplement it to delegate through the base `#stacks` scope, e.g. `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens are constrained exactly as they are in every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack fixture
  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack: stack_a,
    permissions: %w[read:stack]
  )
  assert_equal stack_a.id, client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }, format: :xml

  # Binding under test: stack.id == current_api_client.stack_id
  # Expected (fixed):  response should be 403/404 because stack_b.id != client.stack_id
  # Actual (vulnerable): response is 200 rendering stack_b's deploy data
  assert_response :forbidden # currently fails: assert_response :ok is returned instead, leaking stack_b's XML
end
```
