### Title
Caller-controlled swap routes can escape the controller authorization boundary and steal unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-supplied opaque route bytes and execute them through the configured router inside the caller’s `require_auth` tree. Because a route can place attacker-controlled pool code on that call stack, the malicious hop can invoke an unrelated token’s `transfer(caller, attacker, amount)` as a nested authorization. If the victim signs the simulated authorization tree, the router’s measured-input/output checks still pass while the victim loses wallet tokens unrelated to the lending position.

### Finding Description
`Controller::swap_tokens` snapshots only the controller’s input and output balances, authorizes the controller’s exact input transfer to the configured router, invokes `execute_strategy`, and then verifies controller-side spend and output. These checks constrain the controller’s balances but do not constrain additional contract calls made by route-selected venue code under the caller’s authorization tree. [1](#0-0) 

The router decodes the payload’s `assets` registry and uses attacker-selected indexes as the hop’s `pool`, `token_in`, and `token_out` addresses. [2](#0-1)  Its venue dispatcher measures only the router’s hop input and output balances; it does not prevent the selected pool contract from performing unrelated calls while it is on the stack. [3](#0-2) 

The repository’s adversarial test demonstrates the escape: a payload-selected rogue pool invokes `token.transfer(victim, attacker, amount)` for an unrelated wallet token during the hop. [4](#0-3)  Recording-mode simulation attaches that transfer as a child of the victim’s `swap_collateral` authorization, and signing that tree executes the theft while still crediting the expected swap output. [5](#0-4) 

### Impact Explanation
This is theft of user funds outside the protocol-accounting boundary. The malicious pool can transfer any token for which the victim signs the induced child authorization, not merely the collateral amount routed through the strategy. The victim can lose an unrelated wallet balance while receiving economically valid swap output and retaining a solvent account. [6](#0-5) 

### Likelihood Explanation
An unprivileged attacker can deploy the rogue pool, construct route bytes naming it, and persuade a user or integrating wallet to submit one of the affected strategy calls. Simulation records the malicious nested transfer, so exploitation requires the victim or client to sign the expanded authorization tree rather than reject unexpected children; the checked-in test proves both the simulated tree and successful enforcing-mode execution when that tree is supplied. [7](#0-6) 

### Recommendation
Constrain route-selected pool/venue addresses to a governance-managed allowlist, or otherwise ensure strategy payloads can invoke only known-compatible venue contracts. Clients should additionally treat any `swap_*`, `multiply`, or `repay_debt_with_collateral` authorization tree containing unexpected child invocations as malicious, but contract-level venue admission is needed to prevent malicious code from entering the signed call stack. [8](#0-7) 

### Proof of Concept
1. Deploy a contract whose `swap` function calls `unrelated_token.transfer(victim, attacker, victim_balance)`.
2. Construct route bytes whose `assets` registry contains that contract as the hop pool, with the listed collateral token as input and a valid output token.
3. Have the victim invoke `swap_collateral(caller=victim, account_id, current=usdc_key, amount, new=eth_key, swap=route)`.
4. Simulation records an authorization tree containing both the expected controller call and `unrelated_token.transfer(victim, attacker, victim_balance)`.
5. If the victim signs that returned tree, the route can still return sufficient output to satisfy `verify_router_output`, while the unrelated token balance moves to the attacker. [9](#0-8)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
