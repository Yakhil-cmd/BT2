This scan surfaces a genuine binding break in `WebhooksController`: the field used to select which GitHub App secret authenticates the request (`repository.owner.login`) is different from the field every event handler actually uses to decide which repository/stack gets mutated (`repository.full_name`), and nothing ties the two together.

### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on an Independently-Controlled `repository.full_name` — Cross-Organization Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or the `organization` fallback) [1](#0-0) [2](#0-1) . Every registered event handler, however, resolves the target repository/stack from a completely separate JSON field, `payload.dig('repository', 'full_name')` [3](#0-2) , as also seen in `PushHandler` and the `pull_request` handlers [4](#0-3) [5](#0-4) . Nothing in the controller or handlers checks that `repository.owner.login` and the owner segment of `repository.full_name` are consistent.

### Finding Description
GitHub always keeps `repository.owner.login` and `repository.full_name` consistent, but Shipit builds the raw JSON body itself for the HMAC check — the controller does `JSON.parse(request.raw_post)` and computes the signature over the entire raw body [6](#0-5) , and `verify_webhook_signature` merely checks the HMAC matches the secret configured for whatever organization `repository_owner` names [7](#0-6) . `Shipit.github(organization:)` looks the app config up per-organization from `secrets.github`, and each configured organization has its own independent `webhook_secret` [8](#0-7) [9](#0-8) .

Because Shipit is multi-tenant (multiple orgs can be configured, each with its own app), an attacker who legitimately knows or controls a webhook secret for **one** configured organization (`OrgA`) — e.g. because they administer a GitHub App/webhook for a repo they own under `OrgA` — can construct an arbitrary JSON body where:
- `repository.owner.login = "OrgA"` (selects `OrgA`'s secret for HMAC verification), but
- `repository.full_name = "OrgB/some-repo"` (the field every handler actually uses to look up `Repository`/`Stack` records via `Repository.from_github_repo_name` [10](#0-9) ).

They sign that crafted body with `OrgA`'s secret. `verify_signature` passes because the signature does match `OrgA`'s secret over the exact bytes sent [1](#0-0) . The handler dispatch then runs against `repository.full_name`, i.e. against `OrgB`'s repository/stacks, which the attacker has no legitimate control over. The equality the engine implicitly assumes but never enforces is: `organization authenticating the webhook == owner(repository.full_name)`. Nothing in the request pipeline checks this.

Concretely, `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack in `OrgB` matching the forged branch [11](#0-10) , and `pull_request` handlers can create/update/archive review stacks and `PullRequest` records for `OrgB`'s repos based on entirely forged `pull_request` payload content [12](#0-11) .

### Impact Explanation
This allows cross-repository/cross-organization writes: an attacker with legitimate webhook-signing capability for one tenant organization can inject forged push/pull_request/status/check_suite events that mutate state (trigger sync jobs, create/close/archive review stacks, edit tracked pull request metadata, or influence deployability signals) for a completely different organization's repositories that they have no authorization over. This matches the "cross-repository writes" Critical-tier impact criterion, since it breaks the isolation boundary between tenants that the per-organization webhook secret is meant to enforce.

### Likelihood Explanation
Exploitation requires the attacker to already hold a valid webhook secret for at least one organization configured in the same Shipit instance — this is a real-world condition in any Shipit deployment that manages more than one GitHub organization/app (a documented, supported configuration per `secrets.development.shopify.yml`). Given that precondition, forging the JSON body is trivial (it's the attacker's own raw HTTP POST body), so likelihood is high once the multi-org precondition holds; the flaw is a straightforward missing-field-cross-check bug rather than a cryptographic weakness.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login` for org-level events) and assert it matches `repository_owner`/the organization whose secret validated the signature, rejecting the request (422) on mismatch. Alternatively, verify the signature against the secret keyed by the owner parsed from `repository.full_name` consistently with what handlers use, so there is a single canonical field driving both authentication and downstream repository resolution.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema).
2. As an attacker who controls `OrgA`'s webhook secret (e.g., because you administer a repo/App under `OrgA`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and validates the signature — it passes because the attacker signed with the correct secret for `OrgA` [13](#0-12) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and triggers `sync_github(expected_head_sha: ...)` on `OrgB`'s stack [14](#0-13) , despite the request never being authenticated for `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
