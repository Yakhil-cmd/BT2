### Title
Pairing-secret authorization code can be reused/raced before invalidation, letting a second device impersonate the intended peer - ([File: device.js])

### Summary
`handlePairingMessage()` in `device.js` implements the same "one-time authorization code" pattern that the Gitea advisory describes for OAuth2 codes: a `pairing_secret` is generated once, has an `expiry_date`, and is supposed to be consumed exactly once when a peer pairs with it. As in the Gitea bug, the check ("is the code still valid?") and the invalidation ("delete/consume the code") are not performed atomically, so the code can be redeemed more than once during the race window.

### Finding Description
`startWaitingForPairing()` creates a single-use `pairing_secret` and stores it with an `expiry_date`: [1](#0-0) 

When a `pairing` message arrives, `handlePairingMessage()` validates the payload and then performs a **SELECT-then-later-DELETE** sequence that is not wrapped in a transaction or protected by any lock: [2](#0-1) 

The sequence is:
1. `SELECT ... FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>NOW()` — checks the code is still valid.
2. `INSERT ... INTO correspondent_devices` and `UPDATE correspondent_devices SET is_confirmed=1...` — the code is "redeemed" by making the sender a trusted correspondent.
3. Only afterwards, `DELETE FROM pairing_secrets WHERE pairing_secret=?` — the code is invalidated, but only for non-permanent secrets, and only after the correspondent has already been created.

Because steps 1–2 can run for two different `pairing` messages (from two different device pubkeys / `from_address`) concurrently before step 3 completes for either of them, the same one-time `pairing_secret` can be consumed by more than one device. This mirrors exactly the CWE-294 root cause in the advisory: "does not consistently enforce ... single-use behavior during token exchange" — the validity check and the invalidation of the one-time code are decoupled, enabling a race-based reuse.

### Impact Explanation
`pairing_secret` is the sole authentication mechanism binding an out-of-band shared secret (e.g., a QR code/pairing link shown once) to permission to become a trusted `correspondent_devices` entry. Once paired, a device is treated as an authenticated peer for all subsequent device-message flows: shared/multisig address setup (`extended_pubkeys`, `wallet_signing_paths`, `pending_shared_addresses`), signing requests, and payment/asset message exchange, all of which are wallet/contract message handling paths that ultimately gate multi-signature spending. An attacker who obtains or races the one-time `pairing_secret` (e.g., by intercepting it, or by winning the race against the legitimate device while both attempt to consume it near-simultaneously) can insert themselves as an additional trusted correspondent for a wallet owner. In a shared/multisig wallet flow this lets the attacker be treated as a legitimate co-signer device, which can lead to unauthorized participation in address definition/signing exchanges and consequent fund loss or spend-authorization freezing for the wallet the pairing was meant to protect.

### Likelihood Explanation
Exploitation requires the attacker to know (or race for) the `pairing_secret` value and send a `pairing` message to the hub before the legitimate recipient's message is fully processed and the secret deleted — a narrow window, but one with no locking or transactional protection at all in `handlePairingMessage()`, unlike other one-time-use flows in the codebase (e.g., `mutex.lock(["private_write"], ...)` used elsewhere for double-spend protection in `validation.js`). No cryptographic secret beyond the pairing string itself is required, only network-observable timing.

### Recommendation
Make the check-and-consume of `pairing_secret` atomic: perform the `SELECT` and `DELETE`/consumption inside a single transaction (or use a `DELETE ... WHERE pairing_secret=? AND expiry_date>NOW()` and only proceed if it affected a row), and hold a mutex (similar to `mutex.lock(["private_write"], ...)` used elsewhere) around the whole redeem-and-insert-correspondent sequence in `handlePairingMessage()` in `device.js` so that a non-permanent `pairing_secret` cannot be consumed by more than one competing pairing message.

### Proof of Concept
1. Device A calls `startWaitingForPairing()`, producing a one-time `pairing_secret` (`device.js:765-776`) meant for Device B only.
2. Device A shares the secret with Device B out-of-band (e.g., QR code).
3. An attacker (Device X) that also learns the secret (e.g., by observing the QR/link, or simply racing against B) sends a `pairing` device message with the same `pairing_secret` at nearly the same time as Device B.
4. Both `handlePairingMessage()` invocations (`device.js:816-822`) run their `SELECT ... expiry_date>NOW()` check before either has reached the `DELETE FROM pairing_secrets` step at `device.js:835`.
5. Both B and X get inserted/confirmed as `correspondent_devices` (`device.js:824-832`), i.e., the single-use pairing code is redeemed twice — X is now treated as an authenticated paired device of A, and can subsequently participate in wallet/shared-address message flows meant only for B.
