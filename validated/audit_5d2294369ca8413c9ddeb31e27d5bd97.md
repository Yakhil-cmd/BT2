### Title
Anyone can force a Wasm contract with a live token allowance to the pool to pay a flash-loan fee — `flash_loan` pulls repayment from a caller-chosen `receiver` via `transfer_from` without the receiver's auth - (File: contracts/pool/src/ops/flash.rs)

### Summary
The controller's permissionless `flash_loan` accepts an arbitrary `receiver` address, and the pool collects principal + fee from that receiver via `token.transfer_from` gated only by an on-chain allowance check — never by the receiver's invocation auth. Any Wasm contract that holds an unexpired allowance to the pool (e.g., a flash receiver that approved more than needed, or whose allowance has a later `expiration_ledger`) can be nominated as `receiver` by a third party, forced to run its `execute_flash_loan` callback with attacker-controlled `data`, and debited the flash-loan fee.

### Finding Description
The PerpDepository bug class is: a public function takes an `account`-style parameter and pulls tokens from it using a pre-existing approval, so any caller can spend another party's approval. The direct analog exists here:

- `process_flash_loan` in `contracts/controller/src/strategies/flash_loan.rs` is permissionless: it calls `require_authorized_caller(env, caller)` for the *initiator* only, then passes a caller-supplied `receiver` to the pool (`pool_flash_loan_call(..., caller, receiver, amount, data)`). The only check on `receiver` is `require_wasm_receiver` — it must be a WASM contract, not that it consented.
- In `contracts/pool/src/ops/flash.rs`, `apply` pays `amount` to `receiver`, invokes `execute_flash_loan(initiator, asset, amount, fee, pool, data)` on it with fully attacker-chosen `data`, and `collect_repayment` pulls `amount + fee` back:
  - `assert_with_error!(asset.allowance(receiver, pool) >= terms.total_repayment, InvalidFlashloanRepay)`
  - `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)`

`transfer_from` spends `receiver`'s stored allowance; `receiver.require_auth()` is never required by the pool for the repayment. The receiver does receive the `amount` principal, so its net loss on an honest repayment path is the `fee` — but the allowance consumption, the forced callback execution with hostile `data`, and the fee are all inflicted by an unrelated third party.

### Impact Explanation
An attacker picks any WASM contract holding a live SEP-41 allowance to the pool and calls `controller::flash_loan(caller, hub_asset, amount, receiver = victim_contract, data)`. The pool debits `amount + fee` of the victim's allowance. The victim pays the flash-loan fee for a loan it never requested (fee is protocol revenue, retained by the pool), its allowance is burned, and its `execute_flash_loan` callback executes with arbitrary `data`/`initiator`, which can trigger whatever logic that contract implements (the documented SDK guidance already warns receivers must treat `data` as untrusted and gate the callback — a receiver that only checks the pool caller but trusts `data` can be further abused). This is theft of user funds (the fee) plus forced execution — same impact class as the source report.

### Likelihood Explanation
The precondition is a victim contract with an unexpired allowance to the pool ≥ `amount + fee`. The SDK's `approve_flash_repayment` uses short expirations, but nothing enforces that pattern: any integrating contract that approves with a longer `expiration_ledger`, over-approves, or has an allowance surviving a previously reverted/interrupted flow is exposed for the remainder of the allowance's lifetime. The attacker only needs `caller.require_auth` on themselves and sufficient pool liquidity for `amount`; the attack costs nothing beyond fees since principal returns. Reachable by a single unprivileged address through `controller::flash_loan`.

### Recommendation
Bind the repayment pull to consent obtained within the current call, or drop the allowance-based path:

- Prefer `receiver.require_auth()` (or require the receiver's auth tree to cover the repayment) instead of relying on a standing allowance, or have the pool accept the repayment via `transfer` from the receiver inside the callback (mirroring the measured-receipt pattern already used elsewhere), reverting if the balance check fails.
- If `transfer_from` is retained, at minimum pass the expected repayment and let the receiver explicitly authorize it, and document that receivers must set allowance expiration to the current ledger.
- Receivers should additionally verify `initiator`/`data` in `execute_flash_loan`, but the protocol-level fix is to not let a third party nominate a `receiver` whose only protection is a stale allowance.

### Proof of Concept
1. Contract V is a flash receiver that previously approved the pool: `usdc.approve(v, pool, X, far_future_ledger)` and its allowance is still live.
2. Attacker A calls `controller::flash_loan(caller = A, hub_asset = USDC-hub, amount = X - fee, receiver = V, data = arbitrary)`.
3. Controller `require_authorized_caller` auths only A; `require_wasm_receiver(V)` passes since V is a contract.
4. Pool `apply` transfers `amount` to V, calls `V.execute_flash_loan(A, usdc, amount, fee, pool, data)` — V's callback runs with A-controlled `data`.
5. `collect_repayment` checks `allowance(V, pool) >= amount + fee` (true, from V's stale approval) and executes `usdc.transfer_from(pool, V, pool, amount + fee)` — no auth from V.
6. V loses `fee` (kept as protocol revenue) plus allowance, and its callback was executed on A's terms. Repayment succeeds, so the whole transaction commits.

Relevant code: `contracts/controller/src/strategies/flash_loan.rs` lines 14–33 (caller-only auth, arbitrary `receiver`); `contracts/pool/src/ops/flash.rs` lines 60–67 (payout → callback → collect) and lines 166–179 (allowance-gated `transfer_from` with no receiver auth).
