### Title
System-parameter and OP-list vote weight can be inflated by transiently holding a large byte balance at the moment votes are counted - (File: main_chain.js)

### Summary
Ocore's on-chain governance for the Order Provider (OP/witness) list and system parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) weights each voter by their **current stable byte balance at the moment the vote tally runs**, not by a balance that was locked or held for any minimum period. Any unprivileged unit author can cast a `system_vote` cheaply, then arrange to receive a large, purely transient balance exactly when a `system_vote_count` stabilizes, and move the funds away immediately afterward. This mirrors the reported bug class: economic weight is granted based on momentary token possession instead of sustained stake, letting an attacker "jump the queue" of governance influence without bearing the cost of actually holding capital.

### Finding Description
`countVotes()` recomputes voter weight from scratch every time it runs, using each previously-registered voter's **current** balance: [1](#0-0) 

This balance query has no concept of "how long" the balance has been held, nor any snapshot tied to the timestamp of the individual vote — it simply sums whatever stable, unspent, non-private `base` outputs the address currently owns: [2](#0-1) 

The result is fed directly into the OP-list and numerical-parameter tallies: [3](#0-2) [4](#0-3) 

Casting a `system_vote` requires no minimum balance or holding period — validation only checks message shape, and once cast, the vote's `timestamp` (from when it was posted) is what determines eligibility in the rolling vote window, not the balance held at that time: [5](#0-4) 

Anyone (not just an AA) may also trigger `system_vote_count`, which is what causes `countVotes()` to run on the next MCI stabilization: [6](#0-5) [7](#0-6) 

`saveSystemVote` merely logs the vote and its timestamp when the unit becomes stable — it never records or checks the voter's balance at vote time: [8](#0-7) 

Because weight is derived from a **live** balance query rather than a balance frozen/committed at vote-cast time, an address that has previously cast a `system_vote` can massively inflate its counted weight by receiving a large payment in a unit that stabilizes together with (or just before) the MCI that runs the count, then spend those funds away right afterward. There is no equivalent of the sherlock report's "one full pool cycle" lockup here at all — the check is purely instantaneous, making the attack strictly easier than the original bug (no need to even simulate a flash-swap "return"; the attacker only needs the funds to be stable for however long stabilization normally takes, then can move them immediately once the count has happened).

### Impact Explanation
This directly maps to the "node disagreement on validity or stability" impact category: the OP list determines which addresses are witnesses used for stability/MC determination network-wide, and `threshold_size`/`tps_*` parameters govern fee economics and admission to the network. An attacker able to transiently amplify their voting balance can:
- Push a preferred (potentially malicious or colluding) address into the OP list, weakening the security assumptions the whole network relies on for stability computation.
- Skew `threshold_size`/`tps_fee` parameters that regulate network throughput and fee economics, without holding commensurate economic stake.

Unlike a legitimate large holder whose capital is genuinely at risk/locked in the network, the attacker's capital is available for reuse (e.g., double-used across multiple colluding voters) immediately after the count, since there is no cycle-like restriction forcing sustained ownership.

### Likelihood Explanation
Any unit author can reach this path with only a standard payment and a `system_vote`/`system_vote_count` message — no special privilege, AA access, or protocol dependency is required (`system_vote_count` explicitly can be sent by non-AA authors, per validation.js:1916-1917). The only friction is coordinating the timing of a large balance transfer with MCI stabilization and a `system_vote_count` trigger, both of which are entirely observable/controllable by the attacker (they can send their own `system_vote_count` unit right after arranging the balance transfer).

### Recommendation
Weight votes using the voter's balance **as of the time the vote (or the tally-triggering event) was cast/became stable**, e.g. by snapshotting and persisting the voter's balance in `system_votes`/`op_votes`/`numerical_votes` at the time the vote message stabilizes (similar to how `timestamp` is already stored), rather than re-querying the live balance every time `countVotes()` runs. Alternatively, require a minimum holding period (e.g., balance must have been held stable for N days prior to the count) before it can count toward vote weight, closing the same class of gap identified in the original report.

### Proof of Concept
1. Attacker address `A` casts a `system_vote` for `op_list` (or a numerical subject) — accepted with no balance requirement (validation.js:1844-1883).
2. Shortly before triggering (or observing an upcoming) `system_vote_count`, a colluding party sends a large `base` payment to `A` in a unit that will stabilize.
3. Attacker posts `system_vote_count` for the same subject (validation.js:1913-1923), which is processed at MCI stabilization (writer.js:639-645) and runs `countVotes()`.
4. `countVotes()` computes `A`'s weight from `A`'s **current** stable balance (main_chain.js:1751-1777), which includes the freshly received large payment, and this inflated weight is summed into the OP-list or numerical-parameter tally (main_chain.js:1850-1902).
5. Immediately after the count concludes, `A` spends the borrowed/received funds away (e.g., returns them to the colluding party), retaining the disproportionate influence already recorded in `system_vars`/`op_votes`.
