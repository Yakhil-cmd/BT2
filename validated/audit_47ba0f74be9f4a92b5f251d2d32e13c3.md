## Confirmed key facts

`verify_webhook_signature` returns `true` unconditionally when the org has no `webhook_secret` configured: `return true unless webhook_secret` at [1](#0-0) . `WebhooksController#verify_signature` resolves the org's `GitHubApp` via `Shipit.github(organization: repository_owner)`, where `repository_owner` for a `membership` event (no `repository` key in payload) falls back to `params.dig('organization', 'login')` — i.e., the attacker-controlled `organization.login` value: [2](#0-1) .

`MembershipHandler#find_or_create_team!` looks up the team purely by `github_id: params.team.id`, via `Team.find_or_create_by!`. The `organization:`/`github_team=` assignment only executes in the creation block, **not** when the team is found: [3](#0-2) . So if a `Team` row with that `github_id` already exists (created for a real, secret-protected org), the lookup returns that existing row regardless of what `organization.login` was in the current payload. `process` then calls `team.add_member(member)` unconditionally on the found team: [4](#0-3)  and [5](#0-4) .

## Where the exploit breaks down

The critical missing piece is: **how does the attacker learn/guess the victim Team's `github_id`, and how does this map to `Shipit.github_teams` authorization?**

- `github_id` is GitHub's own internal numeric team ID, not something derivable from the org name or slug. It is opaque, sequentially assigned by GitHub across all teams globally, and not exposed to an unprivileged outsider for a team they don't belong to and can't query (GitHub's team API requires org membership or admin rights to list/read team IDs for private orgs). This is a significant precondition the audit prompt simply assumes away ("team.id matches a github_id of a Team already linked") without a feasible mechanism for the attacker to discover it. Guessing correctly for an authorization-relevant org's specific team is not demonstrated as reproducible.
- Even if guessed, `Shipit.github_teams` is derived from `oauth[:teams]` config, matched by `handle` (`"#{organization}/#{slug}"`), not by raw `github_id` alone in isolation from `organization`/`slug` fields already stored on the row — the existing `Team` record's `organization`/`slug` are untouched by this attack (since the `find_or_create_by!` block doesn't run on find), so the record used for `User#authorized?`'s `teams.where(id: Shipit.github_teams.map(&:id))` check is the **real, correctly-attributed Team row** — its `id` (Shipit's own primary key) doesn't change, only its `members` association gains the attacker. This is exactly the escalation path described (attacker added as a `Membership` to a legitimately-mapped `Team`), which is real, but requires the attacker to already know the exact GitHub-side numeric `team.id` of a team that Shipit has linked into `Shipit.github_teams`.

## Assessment

The code-level flaw is real and verifiable: `find_or_create_by!(github_id:)` in `MembershipHandler#find_or_create_team!` does not re-verify or bind the found team's `organization` against the webhook's claimed `organization.login`/verified signature, and `verify_signature`'s secret selection is itself keyed off the attacker-supplied `organization.login`, meaning signature verification for a secret-less/attacker-owned org provides zero binding guarantee to which `Team` row gets mutated. Given `team.id` is the real, otherwise non-guessable GitHub team ID, and no other part of the payload is cross-checked (no re-verification that `params.organization.login` matches the found team's `organization`), this constitutes a genuine confused-deputy/IDOR: signature verification for org A is used to authorize a mutation scoped to org B's team, purely because both share HMAC-optional/no-secret status and the attacker supplies a numeric ID that happens to collide.

This matches the High severity category ("escalation into `Shipit.github_teams` authorization") described in the rules, and the code path (`find_or_create_by!` lookup-vs-create asymmetry, `repository_owner` fallback to attacker-controlled `organization.login`, `verify_webhook_signature`'s secret-less bypass) is concretely demonstrated in this engine's own files, not a theoretical gem defect.

### Title
Membership webhook team lookup by numeric `github_id` is not bound to the signature-verified organization, allowing cross-org team membership escalation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using the attacker-supplied `organization.login` from the `membership` payload, and treats a secret-less/unconfigured org as automatically verified. `MembershipHandler#process` then resolves the target `Team` solely by the attacker-supplied numeric `team.id` via `Team.find_or_create_by!(github_id:)`, which does not re-check that the found team's `organization` matches the org whose signature was actually verified, letting a webhook "verified" for org A add a member to a `Team` that legitimately belongs to org B.

### Finding Description
Broken binding: `organization_that_verified_signature == organization_owning_mutated_team` is assumed but never enforced.

- `verify_signature` computes `repository_owner` for a `membership` event as `params.dig('organization', 'login')` (no `repository` key present) and fetches `Shipit.github(organization: repository_owner)`: [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no configured `webhook_secret`: [1](#0-0) . So an attacker can pick an arbitrary/unconfigured `organization.login` (e.g., an org they control or one absent from Shipit's config) to trivially "pass" `verify_signature`.
- `MembershipHandler#find_or_create_team!` looks the `Team` up strictly by `github_id: params.team.id`; the `team.organization = params.organization.login` assignment only runs inside the `find_or_create_by!` creation block, so an existing `Team` (created earlier for a different, properly secured org) is returned unmodified: [3](#0-2) .
- `process` then unconditionally calls `team.add_member(member)`, appending the attacker's `User` to that team's `members`: [4](#0-3) , [5](#0-4) .

Attacker request: POST to `/webhooks` with header `X-Github-Event: membership`, no valid `X-Hub-Signature` for the victim org (none needed — org param is attacker's own, secret-less), body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},"member":{"login":"attacker-login"}}`.

Existing guards that fail to stop this: `verify_signature` only proves the payload was HMAC-signed for whatever org the attacker names, not for the org owning the target `team.id`; `drop_unhandled_event` and the `ExplicitParameters` schema don't perform any cross-field consistency check between `organization.login` and `team.id`'s true owner; there is no model validation tying `Team#organization` to a re-verified value on every webhook.

### Impact Explanation
If successful, the attacker's `User` row gains a `Membership` in a `Team` that is part of `Shipit.github_teams` (per config `oauth.teams`), causing `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) to return true for the attacker: [6](#0-5) . That grants the attacker full session access to the Shipit UI/API for that authorization boundary — deploys, rollbacks, stack management — without ever having been added to the real GitHub team, and without presenting a valid signature for the victim org. This matches the "High - escalation into `Shipit.github_teams` authorization" category. Repeatable against any `Team` whose numeric `github_id` the attacker can obtain.

### Likelihood Explanation
The primary blocker to real-world exploitability is discovering the correct `github_id` (GitHub's internal numeric team ID) for a target team that Shipit has already synced/created as a `Team` row and that is listed in `Shipit.github_teams`. This ID is not derivable from public information for teams the attacker isn't a member of, and GitHub does not expose it to outsiders for private teams. The audit prompt stipulates this as a given ("team.id matches a github_id of a Team already linked"), but no concrete disclosure path for that ID is demonstrated in this codebase, so full end-to-end exploitability from an unprivileged, zero-knowledge attacker is not established — the code-level binding gap itself, however, is real and independently verifiable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after finding an existing `Team` by `github_id`, verify that `team.organization == params.organization.login` (and that `repository_owner`/the org whose signature was verified equals `params.organization.login`); raise/reject the event if they diverge instead of silently mutating membership on an unrelated team.

  }

  assert_no_difference -> { Shipit::Team.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call
  end

  attacker = Shipit::User.find_by(login: 'attacker-login')
  # BROKEN BINDING: attacker added to victim_team despite never authenticating against 'victim-org'
  assert_includes victim_team.reload.members, attacker
end
