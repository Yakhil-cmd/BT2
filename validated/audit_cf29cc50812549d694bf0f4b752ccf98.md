This finding is confirmed: `WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to verify against based on an **unverified, attacker-controlled field of the very payload being verified**, then dispatches the *entire* payload (including a possibly different `repository`/`full_name`) to handlers that mutate state for that referenced repository.

### Title
Webhook signature verified against organization derived from unauthenticated payload, allowing cross-organization signature confusion - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the `webhook_secret` to check the `X-Hub-Signature` against by calling `repository_owner`, which reads `repository.owner.login` (or `organization.login`) straight out of the raw, not-yet-verified JSON body. In multi-organization deployments (`Shipit.github_organizations` / per-org `webhook_secret` in `github_app_config`), an attacker who is a legitimate, unprivileged member/webhook-integration of **one** configured organization (Org A, whose secret they can compute a valid HMAC with) can craft a payload whose `repository.owner.login` still resolves to Org A (so the secret used for verification matches and passes), while the `repository.full_name` / other payload fields used later by the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) reference a stack belonging to a **different** organization/repository (Org B) that Shipit also manages.

### Finding Description
The verification and dispatch flow is: [1](#0-0) [2](#0-1) [3](#0-2) 

`verify_signature` calls `Shipit.github(organization: repository_owner)`, and `repository_owner` is derived purely from `params` (parsed JSON body, not covered by any authenticated boundary at this point) via `params.dig('repository', 'owner', 'login')`. The HMAC itself (`verify_webhook_signature`) only proves that the raw body was signed with *some* configured org's `webhook_secret`; it does not re-check that the `repository`/`full_name` embedded in that same body actually belongs to the organization whose secret was used: [4](#0-3) 

Once `verified` is true, `create` blindly parses the body a second time and hands the whole thing to handlers keyed only by event type, not by verified organization: [1](#0-0) 

Handlers such as `PushHandler`/`StatusHandler` resolve the target `Stack`/`Commit` from `repository.full_name` in the payload, with no cross-check that this repository belongs to the organization identified in `repository_owner`. Because `github_app_config` looks configuration up by `organization.downcase` and each org can have a distinct `webhook_secret`, the org used to authenticate (`config[:webhook_secret]` for Org A) and the repository actually written to (any repo name embedded in `repository.full_name`) are two independent, attacker-controlled fields, only one of which participates in the HMAC-selection logic, while the actual mutated resource is selected from unauthenticated content of the same message. This breaks the binding: *organization that authenticated == repository that is written*.

### Impact Explanation
An attacker who legitimately controls (or has compromised) a webhook integration for one configured GitHub organization in a multi-org Shipit deployment can forge events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that pass signature verification under their own org's secret but whose embedded `repository`/`organization` fields reference stacks belonging to a different organization the same Shipit instance manages. Handlers like `GithubSyncJob` enqueue against `stack_id` resolved from that forged `full_name`, `MembershipHandler` can add/remove team memberships, and `StatusHandler` can inject fabricated commit statuses — all cross-organization writes performed without ever holding write access to the target repository. This is a cross-repository/cross-organization write achieved by exploiting a signature-selection vs. content-authorization mismatch, matching the High/Critical impact bar for "cross-repository writes" and "escalation into `Shipit.github_teams` authorization" via forged `membership` events.

### Likelihood Explanation
Exploitability requires: (a) the deployment configured with more than one GitHub organization (the per-org config path in `Shipit.github_app_config`), and (b) the attacker being a legitimate webhook sender (or having compromised the webhook secret) for at least one of the configured organizations — this is a realistic "malicious member of Org A abusing a valid webhook integration" scenario rather than a fully unauthenticated attack. Likelihood is moderate: it depends on multi-org configuration being in use, which is an explicitly supported configuration path (`github_organizations`, `TOP_LEVEL_GH_KEYS`) rather than a hypothetical one.

### Recommendation
After signature verification succeeds, re-validate that every organization-identifying field actually referenced by the payload (`repository.owner.login`, `organization.login`, `full_name` prefix) matches the organization whose secret was used to verify the signature, and reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret`, both managing stacks in Shipit.
2. As a holder of `org-a`'s webhook secret (e.g., a legitimate CI integration for org-a), craft a `push` payload with `repository.owner.login = "org-a"` (so `repository_owner` resolves to `org-a`, and `Shipit.github(organization: "org-a")`'s secret is used to verify), but `repository.full_name = "org-b/some-repo"`.
3. Sign the raw body with `org-a`'s `webhook_secret` and send it to `POST /webhooks` with header `X-Github-Event: push`.
4. `verify_signature` passes (secret matches `org-a`), then `create` dispatches to `PushHandler`, which resolves the target `Stack` from `repository.full_name = "org-b/some-repo"` and enqueues a `GithubSyncJob`/creates commits/statuses for `org-b`'s stack — a write to a repository/org the attacker never authenticated for.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
