### Title
Cross-organization webhook forgery via signature/target mismatch in multi-org GitHub App config - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, while the actual event handlers resolve the `Stack`/`Repository` to mutate using a *different* field from that same unauthenticated body: `repository.full_name`. In a multi-organization deployment (the officially documented/tested configuration), these two fields are never cross-checked, breaking the binding "organization whose secret authenticated the request == repository that is written."

### Finding Description
`Shipit::WebhooksController` validates every inbound webhook by looking up a per-organization `GitHubApp` and checking its `webhook_secret` against the request body: [1](#0-0) 

The organization used for that lookup comes straight from the JSON payload: [2](#0-1) 

`Shipit.github(organization: ...)` returns config-specific `GitHubApp` instances, each with its own `webhook_secret`, exactly as documented and tested for multi-org setups: [3](#0-2) [4](#0-3) 

Once the signature check passes for `repository_owner`, the raw JSON body is dispatched to handlers unmodified: [5](#0-4) 

Every handler, however, determines which `Repository`/`Stack` to act on using `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because `verify_signature` only authenticates the `owner.login`/`organization.login` field, and the actual write target is resolved from `full_name`, an attacker who legitimately controls one configured organization (e.g. they are an admin of "OrgA" in a multi-org Shipit instance, so they know OrgA's `webhook_secret`) can POST directly to `/github_webhooks` (the endpoint is public, not gated by any Shipit session) with a payload where `repository.owner.login = "OrgA"` (so the signature validates against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"` (any other repository/stack tracked by the same Shipit instance). The signature check never inspects `full_name`, so this forged cross-organization payload is accepted and routed to handlers that act on the victim repository's `Stack`.

### Impact Explanation
This is a cross-repository write: `PushHandler#process` will enqueue `sync_github(expected_head_sha: ...)` against a completely different organization's stack: [8](#0-7) 

and `StatusHandler#process` will forge a commit status on any commit sha of the attacker's choosing for that victim stack: [9](#0-8) 

Commit statuses are commonly used by Shipit to gate whether a commit is deployable/mergeable, so an attacker controlling one org's secret can inject fabricated green/red statuses or trigger sync jobs against another organization's repository state, without ever needing that victim organization's webhook secret, an `ApiClient` token, or repository write access on GitHub itself. This matches the "unauthorized deploy" / cross-repository writes impact bar.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator/operator of at least one organization already configured in the same multi-org Shipit instance (so they know that org's `webhook_secret`) — this is a realistic multi-tenant scenario that the engine explicitly supports and documents. No GitHub App private key, `api_clients_secret`, or Shipit session is needed; only knowledge of one org's webhook secret and the ability to send an HTTP POST to the public webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature`, additionally verify that the organization owner used to select the signing secret matches the owner embedded in `repository.full_name` (and `organization.login` where present), rejecting the request (422) on mismatch. Alternatively, have handlers resolve the target repository using the same field (`owner.login`) that was authenticated, rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `secrets_double_github_app.yml` pattern).
2. Attacker is an admin of `OrgA` and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/github_webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and enqueues a sync against OrgB's stack — a write the attacker was never authenticated to perform.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
