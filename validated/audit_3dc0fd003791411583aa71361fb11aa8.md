### Title
`WebhooksController#repository_owner` lets an attacker verify a `membership` webhook against a spoofed organization while `MembershipHandler` mutates the real target organization's `Team`/`Membership` data - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification from `params.dig('repository','owner','login') || params.dig('organization','login')`, but the `membership` event handler independently reads `params.organization.login` and `params.team.id` to create/mutate `Team` and `Membership` rows. An attacker who controls the full raw JSON body can supply a `repository.owner.login` pointing at an organization whose webhook secret is blank/known to them, while setting `organization.login`/`team` to the real target organization, breaking the binding "the organization whose secret verified the request == the organization whose records are mutated."

### Finding Description
The claimed binding is: `organization_that_verified_signature (params.dig('repository','owner','login') || params.dig('organization','login'))` **must equal** `organization_whose_records_are_mutated (params.organization.login used by MembershipHandler)`.

Code path:
- `WebhooksController#repository_owner` [1](#0-0)  computes the org used for signature verification purely from attacker-controlled JSON, preferring `repository.owner.login` over `organization.login`.
- `verify_signature` uses that value to pick the `GitHubApp` instance and validate `X-Hub-Signature` against its `webhook_secret` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` **returns `true` unconditionally when no `webhook_secret` is configured** for that organization: `return true unless webhook_secret` [3](#0-2) .
- Once verification passes, the controller forwards the **entire raw JSON payload** unmodified to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `MembershipHandler#process` / `#find_or_create_team!` never consult `repository.owner.login`; they trust `params.organization.login` and `params.team.id` to locate/create the `Team` and to add/remove `Membership` rows [5](#0-4) .

Exploit flow: attacker POSTs to `/webhooks` with `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-configured-org"}},
  "organization": {"login": "real-target-org"},
  "team": {"id": 123, "name": "Owners", "slug": "owners", "url": "https://api.github.com/..."},
  "member": {"login": "attacker-github-user"}
}
```
If `attacker-configured-org` is any organization present in Shipit's GitHub app config with no `webhook_secret` set (or one the attacker otherwise knows), `verify_webhook_signature` returns `true` without checking the actual HMAC, so any `X-Hub-Signature` value (or none) passes. The request is accepted and dispatched, and `MembershipHandler` creates/updates the `Team` for `real-target-org` and adds `attacker-github-user` as a member of that team's `github_id`. This grants the attacker's GitHub login membership rows inside Shipit's own `Team`/`Membership` tables for an organization they never authenticated against.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schema in `MembershipHandler.params` only validates presence/types, not that `organization.login` matches `repository.owner.login`; there is no cross-check anywhere in the codebase enforcing that the organization used for signature verification is the same one the handler writes to.

### Impact Explanation
A successful request lets an unprivileged attacker inject arbitrary `Team`/`Membership` rows for **any organization configured in Shipit**, as long as some other configured (or attacker-controlled) organization entry has a blank/known webhook secret. Since `Shipit.github_teams` authorization elsewhere in the app is driven from these `Team`/`Membership` records, this is an escalation path into `Shipit.github_teams`-gated authorization, and outright forges a webhook (authentication bypass on a per-payload basis), matching the Critical "authentication bypass (forged webhook ... accepted)" / "a payload for one repository mutating another's ... team" categories. The attack is repeatable against any organization's `Team` data without holding that organization's real webhook secret.

### Likelihood Explanation
The attacker needs no session, token, or real webhook secret. The only precondition is that the Shipit deployment has at least one configured GitHub organization entry with a blank/absent `webhook_secret` (or one the attacker can otherwise learn, e.g. a public/sandbox org), which the attacker references via `repository.owner.login`. Given `verify_webhook_signature` explicitly treats an absent secret as "always verified," this is a plausible and low-cost misconfiguration to exploit; the request is a single unauthenticated HTTP POST and can be repeated at will for different target organizations/teams.

### Recommendation
Do not derive the organization used for signature verification from attacker-controlled JSON fields that differ from the fields the handler actually mutates. Specifically:
- For `membership` (and any org-scoped event), verify the signature using the same field the handler consumes (`params.organization.login`), not `repository.owner.login`.
- After successful verification, assert equality between `repository_owner` and any `organization.login` present in the payload, and reject (422) on mismatch.
- Consider failing closed (422) rather than `true` in `GitHubApp#verify_webhook_signature` when `webhook_secret` is blank, unless that is an intentional opt-out documented and audited per-organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_membership_spoof_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerMembershipSpoofTest < ActionController::TestCase
    tests WebhooksController

    test "membership payload with mismatched repository.owner and organization mutates the real org's team" do
      payload = {
        action: 'added',
        repository: { owner: { login: 'weak-secret-org' } }, # attacker knows this org has no/blank webhook_secret
        organization: { login: 'victim-org' },                # real target org, distinct from repository.owner.login
        team: { id: 999, name: 'Owners', slug: 'owners', url: 'https://api.github.com/teams/999' },
        member: { login: 'attacker' }
      }.to_json

      # Simulate that 'weak-secret-org' has no configured webhook_secret so verification
      # always returns true, per GitHubApp#verify_webhook_signature.
      weak_app = Shipit::GitHubApp.new('weak-secret-org', {})
      Shipit.stubs(:github).with(organization: 'weak-secret-org').returns(weak_app)

      request.headers['X-Github-Event'] = 'membership'
      request.headers['X-Hub-Signature'] = 'sha1=totally-invalid-signature'

      assert_difference -> { Shipit::Team.where(organization: 'victim-org').count }, 1 do
        post :create, body: payload, as: :json
      end

      team = Shipit::Team.find_by(organization: 'victim-org', github_id: 999)
      assert team, "Expected a Team row created for the *victim-org*, not weak-secret-org"
      assert_includes team.members.map(&:login), 'attacker'

      # Binding check: the org that verified the signature ('weak-secret-org')
      # is NOT the org whose Team/Membership rows were mutated ('victim-org').
      refute_equal 'weak-secret-org', team.organization
      assert_equal 'victim-org', team.organization
    end
  end
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
