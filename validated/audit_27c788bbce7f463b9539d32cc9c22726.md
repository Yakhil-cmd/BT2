### Title
Cross-Organization Webhook Forgery via Signature/Routing Field Mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook's HMAC against using `repository_owner`, a field read directly out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`). Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the target `Stack`/`Repository` to mutate using a *different* field from the same body: `payload.dig('repository', 'full_name')`. Because the signature only proves "this body was HMAC-signed with organization X's `webhook_secret`," but never binds that organization to the `repository.full_name` the handlers act on, an attacker who legitimately controls (or has compromised) one configured organization's `webhook_secret` in a multi-tenant Shipit deployment can forge a payload whose `repository.owner.login` points to their own org (so it validates against their known secret) while `repository.full_name` points to a victim repository/stack hosted under a different, unrelated organization in the same Shipit instance.

### Finding Description
`Shipit.github(organization:)` in `lib/shipit.rb:170-181` looks up per-organization config (including `webhook_secret`) from `secrets.github`, which supports multiple organizations each with independent secrets, as shown by `config/secrets.development.shopify.yml:5-23` (`somegithuborg`, `someothergithuborg`, each with their own `webhook_secret`). [1](#0-0) 

In `app/controllers/shipit/webhooks_controller.rb`, `verify_signature` picks the app/secret using `repository_owner`, itself derived straight from the JSON body before any cryptographic check occurs: [2](#0-1) 

Once the signature validates (proving only that *some* known org's secret signed the raw body), `create` dispatches the entire parsed body to handlers: [3](#0-2) 

Every handler resolves its target `Stack` via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` — a completely different field than the one used for the secret lookup: [4](#0-3) 

For example, `PushHandler` uses `stacks` (bound to `repository.full_name`) to trigger `stack.sync_github`, which enqueues `GithubSyncJob` to pull new commits into that stack: [5](#0-4) 

**The broken binding, as an equality that must hold but doesn't:**
`organization whose secret authenticated the signature (repository.owner.login)` ≠ `repository/stack the handler actually writes to (repository.full_name)`.

Before the attack: an org's `webhook_secret` only ever authenticates webhooks whose `repository.full_name` genuinely belongs to that org, because real GitHub webhooks always keep `owner.login` and `full_name`'s prefix consistent. After the attack: an attacker with one org's `webhook_secret` (e.g., the org they legitimately administer, since Shipit is explicitly designed to host many independent organizations' repos as per `config/secrets.development.shopify.yml`) can construct `{"repository": {"owner": {"login": "own-org"}, "full_name": "victim-org/victim-repo"}, ...}`, sign it with their own secret, and have the app act on the victim's stack.

### Impact Explanation
This crosses the "cross-repository writes" threshold. Depending on the event forged:
- A crafted `push` payload (`ref`, `after` pointing at a real/malicious commit SHA on the victim repo) forces `GithubSyncJob` to sync commits into a victim `Stack` the attacker does not own, potentially injecting attacker-influenced commits into the deploy queue or triggering resyncs.
- A crafted `pull_request` `labeled`/`unlabeled`/`closed` payload can archive/unarchive or provision/deprovision review stacks belonging to a repository the attacker has no access to (`app/models/shipit/webhooks/handlers/pull_request/*_handler.rb`, all keyed on `params.repository.full_name`).
- A crafted `membership` event can create arbitrary `Team`/`User`/`Membership` records that feed into `Shipit.github_teams` authorization checks used by `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:26-30`), since `WebhooksController` never scopes membership handling to the org that signed the request.

This meets the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" bar.

### Likelihood Explanation
Exploitability requires the attacker to know at least one organization's `webhook_secret` configured on the same Shipit instance — this is realistic in the documented multi-tenant deployment model where each organization independently configures and could leak/rotate its own `webhook_secret`(`config/secrets.development.shopify.yml`), and no code anywhere cross-checks that `repository.owner.login`'s org matches the org owning `repository.full_name`. The bug is a direct structural analog to the reported `RewardsMath.sol` issue: a computation/verification step (HMAC signature check picking a per-epoch/per-org secret) is performed over one representative field while the actual effect is applied using unaccounted-for, independently-controllable data (repository.full_name) — exactly the "verified signature not covering payload field" pattern called out in scope.

### Recommendation
After verifying the HMAC, cross-check that `repository.full_name`'s owner segment matches the `repository_owner`/organization whose secret validated the signature (or, better, resolve the target `Repository`/`Stack` and confirm its configured organization equals the organization that authenticated the webhook) before dispatching to any handler.

### Proof of Concept
1. Attacker legitimately administers `own-org` on the shared Shipit instance and knows `own-org`'s `webhook_secret`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "own-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(own-org's webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'own-org')` → succeeds because the signature was signed with `own-org`'s real secret [6](#0-5) .
5. `PushHandler.process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [7](#0-6)  and enqueues `GithubSyncJob` against the victim stack, even though the attacker has no relationship to `victim-org`.
