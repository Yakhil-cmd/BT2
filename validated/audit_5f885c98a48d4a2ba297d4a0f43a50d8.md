### Title
EIP-7702 delegation in `pallet-revive` caches the delegate's `code_hash` at authorization time instead of resolving it at call time, so calls into a delegated EOA keep executing code that has since been replaced via `set_code` - ([File: substrate/frame/revive/src/storage.rs])

### Summary
`pallet-revive`'s EIP-7702 implementation snapshots the delegation target's `code_hash` into the delegating EOA's `AccountType::DelegatedEOA` entry when the authorization is processed, rather than re-reading the target's live code on every call. This is the exact bug class from the report: one code path (`InverterBeaconProxy_v1`/plain calls to the target address) always resolves the *current* implementation, while another path (`InverterTransparentUpgradeableProxy_v1`/`DelegatedEOA` calls) is permanently pinned to whatever implementation existed at the time the pointer was cached, so a legitimate change to "shut down"/replace the implementation does not propagate to callers going through the cached pointer.

### Finding Description
Any call to a target contract's own address resolves its code fresh from storage on every call, via `AccountInfo::<T>::load_contract_with_delegation(&address)`: [1](#0-0) 

By contrast, when an EOA delegates to a target via an EIP-7702 authorization, `set_delegation` reads the target's *current* `code_hash` once and copies it into the authority's own `ContractInfo`: [2](#0-1) [3](#0-2) 

The code itself documents this as a deliberate "spec deviation: code is resolved at delegation time, not at call time," explicitly noting that it stays inaccurate whenever the target's code changes after the snapshot was taken: [4](#0-3) 

The only sanctioned way to change an existing contract's code post-deployment is the privileged `set_code` dispatchable, which mutates `AccountInfoOf` for the target directly and has no awareness of, or mechanism to invalidate, any `DelegatedEOA` snapshot that points at the old `code_hash`: [5](#0-4) 

Because delegation holds an incremented refcount on the snapshotted `code_hash`, the old code is also guaranteed to remain in storage (undeletable) for as long as any EOA's stale delegation references it - mirroring the report's scenario where the "shut down" implementation cannot actually be removed/blocked because a cached pointer still depends on it.

When a call is made to a `DelegatedEOA` address, the frame construction loads the *snapshotted* `code_hash` (via the cached `contract_info`) rather than re-reading the current code at the target address, so the executed logic is whichever code existed at delegation time - not whatever code the target address currently holds: [6](#0-5) 

### Impact Explanation
If code deployed at a delegation target is later changed via `set_code` (e.g. because a vulnerability was found and it is "shut down"/replaced with a patched or empty implementation, analogous to `initiateBeaconShutdown`), any EOA that previously delegated to that address keeps running the *old* code on every subsequent call, indefinitely, until that EOA's owner proactively re-signs a fresh authorization. An attacker who knows of the vulnerability in the old code can continue to call the affected EOA directly and trigger the stale, vulnerable logic against that EOA's own storage/balance, exactly as in the original report where Bob's proxy kept using a shut-down implementation. This can result in continued exploitation of a "fixed" vulnerability, unauthorized state mutation, or fund loss in the delegated EOA's own context.

### Likelihood Explanation
Reaching the divergence requires no privileged role from the attacker: any account can hold an EIP-7702 delegation, and any account can call the delegated EOA's address afterward (`eth_call`/`eth_transact` are ordinary, permitted entry points). The state transition that produces the stale snapshot (`set_code` on the target) is root-gated, matching the original report's structure where a legitimate/expected privileged action (beacon shutdown) is the trigger, but the exploitation of the resulting divergence is fully unprivileged. This makes the bug reliably reproducible whenever a delegated target's code is replaced.

### Recommendation
Resolve the delegated EOA's executable code at call time by re-reading the current `code_hash`/`AccountInfoOf` of the delegation target on every call, instead of snapshotting it into the `DelegatedEOA` entry at authorization time (the same fix direction the report itself proposes for the beacon-proxy case, and the same fix already called out as a known follow-up in the code's own comments). At minimum, invalidate/refresh dependent `DelegatedEOA` snapshots whenever `set_code` changes a target's code, or refuse to serve calls into a delegated EOA when the cached `code_hash` no longer matches the target's live code.

### Proof of Concept
No PoC was executed - this analysis is based on static code reading only; no test harness was run and no execution results can be reported. The relevant existing (currently `#[ignore]`d) test class demonstrating this "snapshot-vs-call-time" deviation is `late_deploy_to_delegation_target_resolves_code`, which the maintainers themselves flag as reflecting the same root cause (snapshot vs. call-time resolution), though it covers late-*deployment* rather than late-*replacement* via `set_code`: [7](#0-6) 

To confirm exploitability precisely, a reproduction would need to: (1) instantiate a contract with vulnerable code C1, (2) have a victim EOA sign an EIP-7702 authorization delegating to C1, (3) use root `set_code` (or an authorized migration) to replace C1's code with patched code C2, (4) call the victim EOA directly and observe that C1's (old, vulnerable) logic still executes against the victim's storage/balance rather than C2's. This was not run in this session; it is a proposed reproduction path based on the confirmed code paths above, not a verified result.

	///
	/// The target's `code_hash` (and the resulting `ContractInfo`) is snapshotted from
	/// `AccountInfoOf::<T>::get(&target)` here, not looked up live on every call. This is
	/// stable when `target` is already a deployed contract: the only way to change a
	/// contract's code is via root `set_code`, so the snapshot stays accurate.
	///
	/// It is **not** spec-compliant when `target` is **empty** at delegation time and a

	/// possibly even in the same transaction as the delegation). Spec-compliant clients
	/// resolve code at call time, so a post-delegation deployment would "wake up" the
	/// delegation. Here, the snapshot stays at zero and the authority continues to
	/// behave like a no-code EOA. The niche but real case this breaks is a single EIP-7702
	/// transaction that calls a factory which deploys to the future target *and* delegates

		) -> DispatchResult {

			<AccountInfoOf<T>>::try_mutate(&dest, |account| {

					return Err(<Error<T>>::ContractNotFound.into());
				};

				let AccountType::Contract(ref mut contract) = account.account_type else {
					return Err(<Error<T>>::ContractNotFound.into());
				};

				<CodeInfo<T>>::increment_refcount(code_hash)?;
				let _ = <CodeInfo<T>>::decrement_refcount(contract.code_hash)?;
				contract.code_hash = code_hash;

				Ok(())
			})
		}

/// Snapshot-vs-call-time deviation: if code is deployed at the delegation target *after*
/// the authorization is processed, spec-compliant clients resolve the new code at call
/// time. Our snapshot-at-delegation model misses it. Same root cause as the chained-
/// delegation and precompile-target deviations; the proper fix is call-time resolution.
#[test]
#[ignore = "snapshot-vs-call-time deviation; fix is call-time resolution"]
fn late_deploy_to_delegation_target_resolves_code() {
	let (counter_code, _) = compile_module_with_type("Counter", FixtureType::Solc).unwrap();

	ExtBuilder::default().build().execute_with(|| {
		let _ = <<Test as Config>::Currency as Mutate<_>>::set_balance(&ALICE, 100_000_000);

		// Pre-compute the CREATE2 address where Counter *will* be deployed.
		let setup = DelegationTestSetup::new([0xDD; 32]);
		let salt = [0xEE; 32];
		let target = crate::address::create2(&ALICE_ADDR, &counter_code, &[], &salt);

		// Alice delegates to `target` while it still has no code.
		setup.authorize(target);
		assert!(AccountInfo::<Test>::is_delegated(&setup.signer.address));

		// Deploy Counter at the pre-computed address.
		let deployed = builder::bare_instantiate(Code::Upload(counter_code))
			.salt(Some(salt))
			.build_and_unwrap_contract();
		assert_eq!(deployed.addr, target);

		// Spec-correct: calling the authority should now execute Counter's code.
		let result = builder::bare_call(setup.signer.address)
			.data(Counter::setNumberCall { newNumber: 99u64 }.abi_encode())
			.build_and_unwrap_result();
		assert!(!result.did_revert(), "spec-correct: late-deployed target should execute");

		let read = builder::bare_call(setup.signer.address)
			.data(Counter::numberCall {}.abi_encode())
			.build_and_unwrap_result();
		assert_eq!(Counter::numberCall::abi_decode_returns(&read.data).unwrap(), 99u64);
	});
}
