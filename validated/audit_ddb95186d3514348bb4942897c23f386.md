### Title
Arbiter-contract shared address lets a single party unilaterally sweep any excess/leftover funds beyond the agreed contract amount - (File: arbiter_contract.js)

### Summary
The shared address definition generated for arbiter contracts uses an `["and", [["address", X], ["has", {what:"output", amount: contract.amount, address: Y}]]]` branch to let either the offeror or the acceptor spend from the shared address unilaterally once the required payment condition is met. Because Obyte's `has` operator only checks for the *existence* of one matching output and places no constraint on the total value moved or on other outputs in the same message, whichever party controls the active branch can move the *entire* balance of the shared address while paying the counterparty only the minimum required amount, keeping any surplus (overpayments, accidental/third‑party top-ups, or dust) for themselves without the other party's cosignature.

### Finding Description
`deriveSharedAddress()` builds an `["or", [...]]` definition for the arbiter-contract shared address [1](#0-0) . For public, non-fixed-denomination assets, the "payer alone" and "payee alone" branches are:

```
arrDefinition[1][1] = ["and", [
  ["address", offeror_address],
  ["has", {what:"output", asset, amount: <contract amount minus cut>, address: acceptor_address}]
]];
arrDefinition[1][2] = ["and", [
  ["address", acceptor_address],
  ["has", {what:"output", asset, amount: contract.amount, address: offeror_address}]
]];
``` [2](#0-1) 

The only extra safeguard added is a `not has input from other address` clause to prevent combining multiple identical contracts in one transaction [3](#0-2) ; it does not limit the *total* amount an authorized single party can withdraw from the shared address, nor does it require that the shared address's entire balance equal `contract.amount`.

Confirmed in `definition.js`, the `has`/`has one` operator only verifies that at least one output (or input) in the unit matches the given filter — it does not restrict any other outputs of the message [4](#0-3) , and the address-definition validator for `has` only validates the filter shape, not exclusivity of the total spent amount [5](#0-4) .

Consequently, if the shared address ever holds more base/asset value than exactly `contract.amount` (e.g., the payer mistakenly sends extra bytes/asset units to the shared address, a third party sends funds there, or multiple funding rounds occur), the single signing party whose `["address", X]` + `["has", ...]` branch is active can spend the whole address balance in one message: include one required output of the minimum contract amount to the counterparty, and route everything else to themselves as change, since the address definition's OR-branch does not require a second signature nor restrict the aggregate amount moved.

### Impact Explanation
This allows one of the two arbiter-contract counterparties (paired device peer, i.e. an unprivileged contract participant) to unilaterally divert funds beyond the agreed `contract.amount` from a shared address that is supposed to require mutual/arbiter-mediated settlement. This is unauthorized spending/fund loss for the other counterparty (or third party who mistakenly funded the address), matching a concrete "unauthorized spending" impact.

### Likelihood Explanation
Exploitation requires the shared address to hold funds exceeding `contract.amount` at the time of settlement, which can happen through operator/user error (overpayment), a third party sending to the address, or repeated funding attempts before completion — plausible scenarios in real usage of `arbiter_contract.js`'s `pay()`/`complete()` flow [6](#0-5) . No special privilege is needed beyond being one of the two contract parties, who is already an unprivileged, reachable actor (private-payment counterparty via paired device).

### Recommendation
Change the unilateral spending branches to enforce that the *entire* balance of the shared address is disposed of exactly according to the contract (e.g., replace the loose `has` output check with a `sum`/exact-balance check, or require that inputs equal `contract.amount` exactly and forbid extra outputs other than the mandated payee/arbstore outputs and a change output back to a jointly-controlled address), so that any surplus cannot be unilaterally appropriated by a single party.

### Proof of Concept
1. Alice (offeror, payer) and Bob (acceptor) create an arbiter contract for `contract.amount = 1,000,000` bytes; shared address `S` is derived per `deriveSharedAddress()` [7](#0-6) .
2. Alice funds `S` with 1,000,000 bytes via `pay()` [6](#0-5) , but due to a UI/user mistake or a second funding attempt, `S` ends up holding 1,300,000 bytes total.
3. Bob (or Alice, depending which OR-branch condition he/she is entitled to trigger) posts a unit spending from `S`, signed only with his own key, that includes exactly one output of 1,000,000 bytes to Alice's address (satisfying the `has` clause) and routes the remaining 300,000 bytes change to his own address.
4. This unit validates successfully because the address definition only checks `["address", Bob], ["has", {output amount:1,000,000 to Alice}]` — it does not check that the total consumed equals 1,000,000, so Bob unilaterally keeps the extra 300,000 bytes without Alice's cosignature or the arbiter's involvement.

function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});
			// listen for peer announce to withdraw funds
			storage.readAssetInfo(db, objContract.asset, function(assetInfo) {
				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});
}
