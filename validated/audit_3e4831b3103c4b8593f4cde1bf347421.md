### Title
Webhook signature verification key is selected from an unauthenticated payload field, decoupling the authenticating organization from the repository written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` chooses which GitHub organization's `webhook_secret` to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, not-yet-verified JSON body. Nothing ties the value used to select the signing secret to the value later used by the event handlers (e.g. `repository.full_name`) to identify which `Stack`/`Repository` record is mutated. An attacker who legitimately controls the webhook secret for one organization can forge a payload whose `owner.login` matches their own org (so the signature check passes) while embedding a different `full_name`/target repository that the handler acts on.

### Finding Description
The signature verification flow is: [1](#0-0) 

`repository_owner` is computed purely from the JSON body before the signature has been checked: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization webhook secret to verify against, and `verify_webhook_signature` performs an HMAC comparison keyed on whatever `webhook_app` was resolved: [3](#0-2) 

Once `head(422) unless verified` passes, `create` dispatches the *entire* raw payload to handlers such as `Handlers::PushHandler`, `Handlers::MembershipHandler`, etc.: [4](#0-3) 

Those handlers determine *which* repository/stack/team record to mutate independently, from other fields in the same payload (e.g. `repository.full_name`, `organization.login`, `team.id`) — fields that are never cross-checked against the `repository_owner` value used to pick the signing key. This breaks the binding: **organization authenticated (used to select `webhook_secret`) ≠ repository/organization actually written (used by the handler)**.

Because Shipit is designed to serve multiple GitHub organizations from one instance (each configured with its own `webhook_secret` under `Shipit.github(organization: ...)`), an attacker who administers/controls a webhook for organization `A` (and therefore possesses `A`'s `webhook_secret`, which is not privileged with respect to Shipit itself) can:
1. Craft a JSON body with `repository.owner.login = "A"` (or `organization.login = "A"`) so `verify_signature` resolves and validates against `A`'s known secret.
2. Set `repository.full_name` (or `team`/`organization` sub-objects consumed by the handler) to point at a different, victim repository/org `B` that is already registered in Shipit.
3. Sign the raw body with `A`'s secret and send it to the shared `/webhooks` endpoint.

The signature check succeeds (it only validates against `A`), yet the handler processes the payload as an event for `B`, triggering `GithubSyncJob`, membership changes, or check-run refreshes for a repository the attacker does not control.

### Impact Explanation
This allows an actor who only holds credentials for one tenant/organization onboarded to a shared Shipit instance to inject forged, "signed" GitHub events for a different organization/repository, causing unauthorized state changes (e.g. `GithubSyncJob` enqueued for another stack's commits, forged commit statuses, or fabricated team memberships that could later be used for `Shipit.github_teams` authorization escalation via `MembershipHandler`). This crosses a repository/organization trust boundary that Shipit is supposed to enforce per-tenant, matching the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact categories.

### Likelihood Explanation
Exploitability requires only that the attacker possess a legitimate webhook secret for *any one* organization configured on the shared Shipit instance — not privileged access to Shipit itself, not a GitHub App key, and not repository write access to the victim repository. Constructing a payload with mismatched `owner.login`/`full_name` fields is trivial since Shipit performs no cross-field consistency check before dispatching to handlers.

### Recommendation
Do not select the verification key from unauthenticated payload data alone, or, after verification, cross-check that every repository/organization identifier used by downstream handlers (`full_name`, `organization.login`, `team.organization`) is consistent with the organization whose secret validated the signature. Reject the webhook if these fields disagree.

### Proof of Concept
1. Shipit instance configured with two organizations, `A` and `B`, each with a distinct `webhook_secret`.
2. Attacker owns/administers organization `A`'s GitHub App/webhook config and thus knows `A`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with:
   ```json
   {
     "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>"
   }
   ```
   and `X-Hub-Signature: sha1=<HMAC(A_webhook_secret, body)>`.
4. `verify_signature` calls `Shipit.github(organization: "A")` (from `repository.owner.login`), verifies successfully against `A`'s secret.
5. `Handlers::PushHandler` processes the event using `repository.full_name = "B/victim-repo"`, enqueuing `GithubSyncJob` for stacks under `B`, even though the request was never authenticated for `B`. [5](#0-4)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
