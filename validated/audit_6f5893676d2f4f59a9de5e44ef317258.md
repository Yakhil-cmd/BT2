### Title
System-parameter vote weight is tallied from the address's balance *at count time* instead of at vote time, letting a poster inflate an old vote by funding the voting address afterward - ([File: main_chain.js])

### Summary
`countVotes()` in `main_chain.js` determines the outcome of consensus-critical system votes (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) by joining each voting address to its *current* stable balance at the moment of tallying, not the balance the address held when it actually cast the `system_vote` message. This is the same bug class as the Carapace `ProtectionPool.requestWithdraw` report: an eligibility/weight amount is derived from a balance snapshot that can be freely manipulated after the qualifying action was taken, by simply moving coins into the already-voted address.

### Finding Description
Any address can post a `system_vote` message (validated in `validation.js`, persisted via `writer.js` into `system_votes` plus `op_votes`/`numerical_votes`) specifying a `subject` and `value`. When an MCI stabilizes, `countVotes()` is invoked: [1](#0-0) 

It collects every address that has *ever* voted for the subject, then computes each address's balance using the current DB state — the balance held right now, at the time of counting — not the balance it held when the vote transaction was signed: [2](#0-1) 

That current balance is stored into a `voter_balances` temp table and is later summed per candidate/value: [3](#0-2) [4](#0-3) [5](#0-4) 

Because the weight is bound to the **address**, not to the specific coins that were owned when the vote was cast, a voter (or several colluding voters) can:
1. Cast a `system_vote` from address `A` while holding only a trivial balance (e.g. 1 byte), well within the multi-year lookback window (`since_timestamp`).
2. Later, while the vote is still "active" (within the lookback window, which can span years and is only shrunk to satisfy `SYSTEM_VOTE_MIN_SHARE`), transfer a large balance from other addresses (which never voted, or voted differently) into `A`.
3. When any subsequent MCI stabilizes and `countVotes()` runs, `A`'s vote for the old `value`/`op_address` is now weighted by the newly received, unrelated balance — inflating the tally for that option without any of the transferred-in funds' owners ever having authorized that specific vote with their present holdings.

This mirrors exactly the reported bug class: the protocol records an authorization (deposit/vote) tied to a balance check performed at a *different* time than when the balance is actually consumed for weight, and transfers between addresses can be used to move "voting power" into an address after the fact, inflating what should be a fixed, historically-committed weight.

### Impact Explanation
`op_list` determines the set of Order Providers (witnesses) used for building the main chain, and `threshold_size`/`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` are core consensus/fee parameters read directly into `storage.systemVars` and used network-wide (`system_vars` table, emitting `system_vars_updated`). Manipulating these tallies can:
- Change the accepted OP/witness list to attacker-favored addresses, undermining the security assumption that OPs are chosen by honest, currently-committed stake/vote weight.
- Skew fee/TPS parameters that govern whether units are considered valid/stable, causing different nodes to potentially disagree on validity/stability if the manipulation happens near a decision boundary, or degrade network throughput/availability.

This falls squarely into "node disagreement on validity or stability" / "network unable to confirm new units" impact categories, warranting a High severity classification, matching the original report's severity for the analogous pattern.

### Likelihood Explanation
The attack requires only ordinary, unprivileged unit-posting capability (a `system_vote` message and later a normal payment moving funds into the voting address) — no special permission, no OP/witness role, and no light-client/network-manipulation is needed. The lookback window (`since_timestamp`) can span multiple years and only shrinks once accumulated voted balance passes `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`, giving an attacker a large time window in which an old, cheap vote can be "recharged" with fresh balance. The mechanics of moving funds between one's own addresses are trivial and routinely available operations on ocore.

### Recommendation
Bind vote weight to the balance the address actually held at (or near) the time the `system_vote` was cast, rather than the balance at counting time — e.g., snapshot and store the balance in `system_votes`/`op_votes`/`numerical_votes` at vote-insertion time (similar to how `spend_proofs` bind an amount at issuance), and use that stored value in `countVotes()`'s `SUM(balance)` aggregation instead of re-reading the address's current balance. Alternatively, invalidate/require re-voting whenever a voting address's balance increases materially after the vote, so that only balance provably held continuously since the vote counts.

### Proof of Concept
1. Address `A` posts a `system_vote` unit voting `op_list` (or a numeric subject) for value `V`, while holding a negligible stable balance (e.g. 1 byte). This is accepted and inserted into `system_votes`/`op_votes` per `writer.js`.
2. Time passes (still inside the multi-year lookback window used in `main_chain.js` `countVotes()`).
3. The attacker sends a large stable payment from an unrelated, never-voted address `B` to `A`.
4. On the next MCI stabilization that triggers `countVotes()` for the subject, the query at `main_chain.js:1757-1773` computes `A`'s balance as the large amount just received from `B`, and the subsequent aggregation (`main_chain.js:1850-1858` or `1882-1899`) credits value `V` with that inflated weight — even though the funds from `B` were never used to actually authorize vote `V`.
5. Repeating this with several funded "sleeper" voting addresses lets an attacker swing `op_list`/`threshold_size`/fee-parameter outcomes using capital that was never committed to those votes at cast time.
