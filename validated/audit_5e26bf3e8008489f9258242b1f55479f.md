### Title
Attacker-chosen `earned_headers_commission_share` used as a divisor lets a unit poster manipulate TPS anti-spam fee accounting - (File: validation.js)

### Summary
`validateTpsFee` in `validation.js` divides an address's accumulated `tps_fees_balance` by a `share` value that is directly taken from the unit's `earned_headers_commission_recipients` field, a field an unprivileged unit author fully controls. Just as the SALTY `virtualRewardsToAdd` computation let a first depositor distort a rewards/shares ratio by choosing the denominator, here an attacker can choose an arbitrarily small `share` (as low as 1%) for an address, which massively amplifies the divisor-based `tps_fee` calculation used to gate acceptance of a unit, effectively bypassing the intended anti-spam fee requirement.

### Finding Description
`validateHeadersCommissionRecipients` only requires that the shares in `earned_headers_commission_recipients` be positive integers summing to 100; it does not require recipients to be unit authors, nor does it bound the minimum individual share above 1%: [1](#0-0) 

That same attacker-controlled `earned_headers_commission_recipients` list (converted via `storage.ehcr2assoc`/`storage.getTpsFeeRecipients`) is used in `validateTpsFee` to compute a `share` used as a divisor: [2](#0-1) 

Specifically:
```
const share = recipients[address] / 100;
...
const tps_fee = tps_fees_balance / share + objUnit.tps_fee;
```
Because `share` can be set to a tiny value like `0.01` (1%), the derived `tps_fee` value used both in the "sufficient funds" check and the `min_acceptable_tps_fee` comparison is amplified by up to 100x relative to what was actually paid in `objUnit.tps_fee` and the address's real accumulated `tps_fees_balance`. This mirrors the SALTY root cause: a per-transaction attacker-selected ratio is fed as a divisor into an accounting formula whose invariant assumes the ratio reflects a real, previously-established proportion — but here nothing enforces that the declared `share` matches any prior real contribution by that address, since the recipient need not even be an author of the unit.

The same amplified/attacker-chosen `share` value also feeds `storage.getPaidTpsFee` (used for future units built on top of this one) and `storage.updateTpsFees`, which distributes/accrues `tps_fees_balance` deltas proportionally to `share` at stabilization time: [3](#0-2) [4](#0-3) 

By choosing a low share for a target address that has previously accrued even a small positive `tps_fees_balance` credit, or by pre-seeding a credit and later citing a tiny share for the same address, the attacker inflates the computed `tps_fee` far beyond the real value paid for the current unit, satisfying both:
```
tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share   // easy to satisfy since share is tiny
...
tps_fee = tps_fees_balance / share + objUnit.tps_fee < min_acceptable_tps_fee  // hard to fail since division inflates tps_fee
```

### Impact Explanation
The TPS fee mechanism is Obyte's core anti-spam/congestion-pricing control that is supposed to make units pay proportionally more as network throughput increases, preventing flooding. By manipulating the `share` denominator, an unprivileged unit author can make the network accept units while paying far less real `tps_fee` than the network's throughput-based schedule requires. Under sustained abuse this defeats the purpose of the TPS fee (network unable to price/limit unit issuance fairly during high load), a "network unable to confirm new units" fairly / anti-spam-bypass class of impact.

### Likelihood Explanation
Reachable by any single unit poster: constructing `earned_headers_commission_recipients` with an arbitrary address and a minimal (1%) share, and then relying on that address already having (or being able to accumulate) even a small positive `tps_fees_balance`, is entirely within reach of an unprivileged actor with no special permissions, cosigners, or race conditions required. The only constraint is that `total_earned_headers_commission_share` sum to 100, which is trivially satisfiable (e.g., 1% + 99%).

### Recommendation
- Do not let the attacker-controlled `share` field act as an unconstrained divisor for the TPS-fee "credit" comparison. Either bound the minimum allowed `share` at a level that prevents multiplicative blow-up, or decouple `tps_fees_balance` accrual/consumption from the `earned_headers_commission_recipients` mechanism entirely.
- Consider requiring TPS-fee recipients to be restricted to the unit's own authors (as headers-commission recipients conceptually are), removing the ability to name arbitrary third-party addresses.
- Add an invariant check that the amplified `tps_fee` derived via division can never exceed some multiple of the actually-paid `objUnit.tps_fee`, closing the "cheap unit, big apparent fee" gap.

### Proof of Concept
Conceptual sequence (concrete DB/test harness needed to fully validate, since a live test wasn't runnable in this environment):
1. Post unit U1 (single author, address A) that overpays `tps_fee` relative to the local minimum, and declares `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 100}]` (or default single-author behavior). After stabilization, `storage.updateTpsFees` credits address A's `tps_fees_balance` with the positive surplus (`total_tps_fees_delta`), per: [5](#0-4) 
2. Post a later unit U2, authored by A (or any author), that sets `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 1}, {address: B, earned_headers_commission_share: 99}]` and pays a near-zero `objUnit.tps_fee`.
3. In `validateTpsFee`, for address A: `share = 1/100 = 0.01`; `tps_fee = tps_fees_balance / 0.01 + objUnit.tps_fee`, which is ~100x the real accrued balance, easily clearing `min_acceptable_tps_fee` and the "sufficient funds" check, even though the unit paid almost nothing: [6](#0-5) 
4. Repeat for subsequent units to keep passing the check cheaply, degrading the anti-spam guarantee that the TPS fee mechanism is meant to enforce.

Note: this analysis is based on static reading of `validation.js` and `storage.js`; due to index/documentation limits I was not able to run the actual validation/test suite to empirically confirm the exploit end-to-end (e.g., exact interplay with `getPaidTpsFee` for downstream units and `min_acceptable_tps_fee_multiplier`). A Devin session with full repo/test access would be needed to build and run a concrete PoC unit test confirming the bypass numerically.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

async function getPaidTpsFee(conn, unit) {
	if (unit === constants.GENESIS_UNIT)
		return 0;
	let objUnitProps = assocUnstableUnits[unit] || assocStableUnits[unit];
	if (!objUnitProps) {
		const objJoint = await readJoint(conn, unit);
		const objUnit = objJoint.unit;
		objUnitProps = {
			unit,
			author_addresses: objUnit.authors.map(a => a.address),
			assocEarnedHeadersCommissionRecipients: ehcr2assoc(objUnit.earned_headers_commission_recipients),
			tps_fee: objUnit.tps_fee || 0,
			last_ball_unit: objUnit.last_ball_unit,
		};
	}
	if (!("tps_fee" in objUnitProps))
		throw Error(`no tps_fee in props`);
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const recipients = getTpsFeeRecipients(objUnitProps.assocEarnedHeadersCommissionRecipients, objUnitProps.author_addresses);
	let min_tps_fee = Infinity;
	for (let address in recipients) {
		const share = recipients[address] / 100;
		const [row] = await conn.query("SELECT tps_fees_balance FROM tps_fees_balances WHERE address=? AND mci<=? ORDER BY mci DESC LIMIT 1", [address, last_ball_mci]);
		const tps_fees_balance = row ? row.tps_fees_balance : 0;
		const tps_fee = tps_fees_balance / share + objUnitProps.tps_fee;
		if (tps_fee < min_tps_fee)
			min_tps_fee = tps_fee;
	}
	return min_tps_fee;
