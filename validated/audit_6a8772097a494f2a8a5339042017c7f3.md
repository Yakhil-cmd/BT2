### Title
Missing Sender-Authorization Check in `handleNewSharedAddress` Allows Any Paired Device to Register Forged Multisig Address Definitions - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` processes the `"new_shared_address"` device message and persists a peer-supplied address definition and signer map into the local `shared_addresses` / `shared_address_signing_paths` tables. Unlike other message handlers in the same wallet-pairing protocol (e.g. `create_new_shared_address`, which calls `validateAddressDefinitionTemplate(..., from_address, ...)`), `handleNewSharedAddress` never receives or checks `from_address` at all. [1](#0-0) [2](#0-1) 

### Finding Description
The dispatcher in `wallet.js` routes the `"new_shared_address"` message straight to `walletDefinedByAddresses.handleNewSharedAddress(body, callbacks)` without passing `from_address`:
```js
case "new_shared_address":
    // {address: "BASE32", definition: [...], signers: {...}}
    walletDefinedByAddresses.handleNewSharedAddress(body, {
        ifError: callbacks.ifError,
        ifOk: function(){ callbacks.ifOk(); eventBus.emit('maybe_new_transactions'); }
    });
    break;
``` [1](#0-0) 

`handleNewSharedAddress` itself takes only `body, callbacks` — no sender identity — and performs these checks: definition chash matches `body.address`, every signer path resolves consistently against the definition, and (via `determineIfIncludesMeAndRewriteDeviceAddress`) that at least one of the referenced member addresses is one of *my* own `my_addresses`/`shared_addresses`. It never verifies that the message actually originated from a device that legitimately controls one of the other member addresses/paths in the definition:
```js
function handleNewSharedAddress(body, callbacks){
    ...
    determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
        if (err) return callbacks.ifError(err);
        validateAddressDefinition(body.definition, function(err){
            if (err) return callbacks.ifError(err);
            addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
        });
    });
}
``` [2](#0-1) 

Contrast this with the sibling flow `create_new_shared_address`, which explicitly threads `from_address` into `validateAddressDefinitionTemplate` and requires `arrDeviceAddresses.indexOf(from_address) !== -1` (sender must be a device referenced in the template): [3](#0-2) 

This is the same root-cause pattern as the phpMyFAQ IDOR: a privileged, identity-sensitive operation (persisting a shared/multisig address record and wiring signer routing for it) trusts a caller-supplied object (`body`) instead of verifying that the actor invoking the operation (`from_address`, analogous to the admin session in the report) is authorized to be one of the parties to that object.

Once accepted, `addNewSharedAddress` stores the record and — critically — `forwardNewSharedAddressToCosignersOfMyMemberAddresses` automatically re-broadcasts the (attacker-controlled) definition and signer map to all *other devices* that co-sign the victim's own member address, over the pairing channel, without any additional authorization gate: [4](#0-3) 

### Impact Explanation
Any device merely paired (correspondent) with the victim — not necessarily involved in any legitimate multisig setup — can craft a `new_shared_address` message naming one of the victim's real addresses as a member path and injecting arbitrary attacker-controlled signer/device-address entries for the remaining paths. Because `handleNewSharedAddress` accepts this without verifying that the sender is actually one of those referenced parties:
- The victim's wallet silently records a new "shared address" it did not agree to create, together with `shared_address_signing_paths` entries that route signing requests for that fabricated address to attacker-chosen `device_address` values.
- This poisoned record is then auto-forwarded (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`) to the victim's other cosigner devices sharing the referenced member address, propagating the forged multisig topology to legitimate cosigners' wallets as well.
- Subsequent signing flows (`"sign"` messages, see `findAddress`) consult `shared_address_signing_paths` to decide whether a signing key is local or must be routed to a remote `device_address`; a forged entry can misdirect the routing of signing requests/responses for that fabricated address to attacker-controlled devices, and can also be leveraged in the `sign`-remote proxy path to solicit signatures under conditions the legitimate cosigner never agreed to (e.g. presenting the attacker as a legitimate cosigner for what appears to be a multisig wallet the victim participates in).

This can lead to loss/misdirection of funds sent to what the victim believes is a properly co-owned multisig address, and to node/wallet disagreement about who the legitimate cosigners for an address are — satisfying the "unauthorized spending" / "node disagreement on validity" bar, reachable purely by a paired device sending a crafted message (in-scope actor).

### Likelihood Explanation
Likelihood is High: exploitation requires nothing more than being an existing correspondent (paired device) of the victim — a normal, low-privilege relationship in Obyte's wallet-pairing model (analogous to the "any authenticated admin" precondition in the original report) — and sending one crafted `new_shared_address` device message referencing the victim's real address. No cryptographic secret of the victim needs to be known; the attacker only needs the victim's own address (public information once paired/chatting) and freely chooses the rest of the definition/signers.

### Recommendation
Thread `from_address` into `handleNewSharedAddress` (mirroring `validateAddressDefinitionTemplate`) and reject the message unless `from_address` corresponds to one of the `device_address` values referenced in `body.signers` for a path other than the victim's own member address(es). Additionally, before calling `forwardNewSharedAddressToCosignersOfMyMemberAddresses`, re-validate that all `device_address` entries being forwarded are actually correspondents that were expected to participate (e.g. only forward records that were locally created via `create_new_shared_address`/approval flow, not ones learned passively from `new_shared_address`).

### Proof of Concept
1. Attacker device `D_A` is a normal correspondent (paired device) of victim `V`, who owns known address `V_ADDR` (learned e.g. from a payment request or chat).
2. `D_A` sends a `"new_shared_address"` message to `V`:
```json
{
  "address": "<chash160 of the crafted definition>",
  "definition": ["and", { "set": [
      ["address", "V_ADDR"],
      ["address", "ATTACKER_ADDR"]
  ]}],
  "signers": {
      "r.0": { "address": "V_ADDR", "device_address": "0V_DEVICE" },
      "r.1": { "address": "ATTACKER_ADDR", "device_address": "0ATTACKER_DEVICE" }
  }
}
```
3. `wallet.js` routes this straight to `handleNewSharedAddress(body, callbacks)` with no `from_address` check.
4. `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `V_ADDR` is in `V`'s `my_addresses`.
5. `addNewSharedAddress` persists the shared address and signing paths, and `forwardNewSharedAddressToCosignersOfMyMemberAddresses` propagates the record to any other cosigner devices of `V_ADDR`, all without `D_A` ever proving it legitimately controls `ATTACKER_ADDR`'s claimed role or that `V` agreed to this shared address.

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
