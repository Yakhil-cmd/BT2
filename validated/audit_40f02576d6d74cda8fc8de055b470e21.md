### Title
Webhook signature check authenticates the sending organization but not the repository the event mutates, allowing cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate an inbound webhook based on a payload field (`repository.owner.login`, falling back to `organization.login`), but no code ever checks that this organization matches the repository that the corresponding handler subsequently loads and mutates (`repository.full_name`). In a multi-organization Shipit deployment, this breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` picks the app config purely from attacker-controlled payload JSON: [1](#0-0) [2](#0-1) 

The HMAC is verified over the *entire raw body* using the secret for whichever organization `repository_owner` resolves to: [3](#0-2) 

Because the signature only proves "this body was signed by the org whose secret matches `repository_owner`," and Shipit explicitly supports multiple independent GitHub organizations each with their own App/`webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section), an operator/attacker who legitimately controls Organization A (and can therefore generate a validly-signed webhook delivery for Org A, e.g. by pushing to their own repo) can freely set every *other* field of the JSON body, including `repository.full_name`, to point at a stack belonging to a different, victim organization (Org B) also configured in the same Shipit instance.

Downstream, every handler resolves the target repository independently from that same attacker-controlled `repository.full_name` field, with no re-check against `repository_owner`/the authenticating org: [4](#0-3) 

For example `PushHandler` loads the stacks for `repository_name` and immediately triggers a git sync keyed off attacker-controlled `after`/`ref` values: [5](#0-4) 

Nowhere is `params.dig('repository','owner','login')` (used to select the signing secret) cross-checked against `params.dig('repository','full_name')`'s owner segment before the handler acts. The signature only proves body integrity/authenticity relative to *some* configured organization — it does not prove that organization is authorized to act on the specific repository named inside the body.

This exactly matches the report's root-cause pattern of "field acted on but not bound to the entity that authenticated the request": there, `readMint`'s snapped valuation (used for sizing/authorizing the surplus swap) diverged from `readRedemption`'s raw valuation (used for the safety check), because the two paths trusted different derivations of the same underlying data without reconciliation. Here, the org used to *authenticate* the webhook and the repository used to *act* diverge because both are independently read from the same attacker-supplied JSON with no mutual validation.

### Impact Explanation
This crosses a repository-write boundary: a party who only controls one organization's GitHub App installation (i.e., is legitimate for Org A) can force Shipit to process webhook events — and therefore repository syncs and any push/check/status-driven side effects — for stacks belonging to Org B, without ever having GitHub access to Org B. This matches the report's "Critical: cross-repository writes" impact category, since the deployment-trust binding (which organization's credentials authorize which repository's changes) is broken.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization (documented, supported feature), and (2) the attacker legitimately controlling at least one of those organizations (i.e., able to install a GitHub App/webhook there, or knowing that org's `webhook_secret`). Given multi-org support is an advertised configuration, this is a realistic misuse of a documented feature rather than a purely theoretical scenario, though it does require the operator to run a multi-tenant/multi-org Shipit deployment.

### Recommendation
After signature verification, cross-check that `repository_owner` (or `organization.login`) used to select the verifying app matches the owner segment of every repository referenced in the payload (`repository.full_name`, and any nested repository references) before dispatching to handlers. Reject the event (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret` values (per `docs/setup.md`, "Using Multiple Github Applications").
2. As an entity with legitimate webhook delivery capability for `org-a` (e.g., controlling `org-a/some-repo`), craft a JSON body:
```json
{
  "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Sign the raw body with `org-a`'s `webhook_secret` and send it to `/github/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `org-a`, fetches `Shipit.github(organization: 'org-a')`, and verifies successfully since the attacker signed correctly for `org-a`.
5. `PushHandler` (via `Handler#stacks`) resolves `repository_name` as `org-b/victim-repo` from the same payload and processes the event against Org B's stack — `stack.sync_github(expected_head_sha: ...)` runs for a repository the attacker was never authenticated for. [2](#0-1) [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
