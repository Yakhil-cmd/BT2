### Title
Unprivileged stake-account mutation during epoch-reward distribution can trigger a consensus-halting `assert_eq!` panic - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` contains a hard `assert_eq!` invariant check that compares a previously-calculated stake reward amount against the currently-observed stake delegation in `StakesCache`. Because the stake program does not gate user instructions on the epoch reward interval, and because reward distribution/recalculation is spread over multiple blocks or is redone after snapshot recalculation, a mismatch between the calculation-time and distribution-time delegation state can be produced by ordinary account activity, causing every validator that replays the block to panic identically.

### Finding Description
`build_updated_stake_reward` in `distribution.rs` has two branches depending on the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`): [1](#0-0) 

When `adjust_delegations_for_rent` is false, the code does not tolerate any divergence between the delegation value baked into the `PartitionedStakeReward` (computed earlier, at the calculation phase or during `recalculate_stake_rewards`) and the delegation currently found in `stakes_cache_accounts`:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, "stake reward delegation must be consistent with the updated stake account lamport balance");
``` [2](#0-1) 

This function is called from `store_stake_accounts_in_partition`, which is executed deterministically as part of normal bank-advancement logic (`distribute_epoch_rewards_in_partition` → `distribute_partitioned_epoch_rewards`), i.e., inside consensus-critical block replay, not behind any privileged/validator-only gate: [3](#0-2) 

The reward-distribution machinery spans multiple blocks (`num_partitions` blocks per `get_reward_distribution_num_blocks`), and can additionally be *recomputed* by `recalculate_partitioned_rewards_if_active`/`recalculate_stake_rewards`, which reads the live `StakesCache` at a possibly different point in time than when the original inflation reward was calculated: [4](#0-3) [5](#0-4) 

No search in the `programs/stake` processor turned up any check on `EpochRewardStatus`/reward interval; the reward-interval concept is entirely internal to `runtime/src/bank` and is not enforced against `StakeInstruction` (delegate/split/merge/deactivate/withdraw) processing. Consequently, an ordinary stake authority can submit stake-program transactions during the reward interval that change their own account's stored `Delegation::stake` (e.g., via `Split`, `Merge`, `DeactivateDelinquent`, or interactions that adjust the account through legitimate instructions), producing a `stakes_cache_accounts` entry whose `stake.delegation.stake` no longer matches what was assumed when the `PartitionedStakeReward` was computed. On the distribution/recalculation block, `build_updated_stake_reward`'s `assert_eq!` fires, and — because this code runs identically on every replaying validator — the whole cluster panics/halts at that slot. This is directly analogous to the LayerZero finding's root cause: an unprivileged party can supply input that a downstream handler cannot gracefully reject, and the protocol has no non-blocking/recoverable fallback (there is no "burn and skip" path here as there is in the `Err` branch of `build_updated_stake_reward` — the assert path is a hard panic, not a recoverable `DistributionError`).

### Impact Explanation
A panic inside the block-processing/rewards-distribution path is deterministically reproduced on every validator that replays or recalculates the same slot, producing a cluster-wide, epoch-boundary halt — the network cannot progress past the affected slot until the invariant violation is patched, exactly matching the "epoch-boundary halt" impact category. Unlike the sibling `Err(DistributionError::...)` cases in the same function (which gracefully burn the reward and continue), this specific branch is a hard `assert_eq!` with no recovery path, so once triggered it is unrecoverable without a code change/restart — analogous to the LayerZero channel being permanently blocked with "no way of resetting the queue."

### Likelihood Explanation
Likelihood depends on whether an unprivileged staker can actually cause `stake.delegation.stake` (as read from `StakesCache` at distribution/recalculation time) to diverge from the value assumed at calculation time, without going through the `adjust_delegations_for_rent` path. This requires further verification of exactly which stake-program instructions can execute during the reward interval and whether `StakesCache` updates from those instructions can hit this exact code path before the corresponding partition's distribution block is processed (particularly via the snapshot-restore/warp-triggered `recalculate_stake_rewards`, which is more clearly reachable since it recomputes against the live cache after an arbitrary window). I could not find any restriction in the stake program's instruction processor that would block ordinary stake instructions during the reward interval, but I was not able to fully trace every code path (e.g., precise conditions under which `stakes_cache_accounts.get(...)` can return a stake with a differing `delegation.stake` for indices already computed) within the remaining tool budget.

### Recommendation
- Replace the hard `assert_eq!` in `build_updated_stake_reward`'s non-rent-adjustment branch with a graceful `DistributionError` (mirroring `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState`) so that a delegation mismatch burns the affected reward and is logged instead of panicking the entire validator set.
- Audit `recalculate_stake_rewards`/`recalculate_partitioned_rewards_if_active` to ensure the invariant it depends on (identical delegation state between original calculation and recalculation) can never be violated by ordinary user-submitted stake instructions, or explicitly document/enforce that stake accounts are immutable for the entire reward interval.

### Proof of Concept
Not independently reproducible from static analysis alone within the given tool budget; a concrete PoC would require constructing a bank test (similar to the existing `test_recalculate_partitioned_rewards`/`test_distribute_with_increased_rent` tests) that: (1) computes `PartitionedStakeReward`s for a stake account, (2) mutates that same account's `Delegation::stake` via a legitimate stake-program instruction before the corresponding distribution/recalculation block executes, and (3) shows the `assert_eq!` in `build_updated_stake_reward` panics rather than returning a `DistributionError`.
