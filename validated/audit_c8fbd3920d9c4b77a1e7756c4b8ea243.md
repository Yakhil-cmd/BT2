### Title
Cross-repository commit-status forgery via global SHA lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using only the `repository.owner.login` (or `organization.login`) field of the payload [1](#0-0) [2](#0-1) . Once the signature is accepted, `StatusHandler#process` never re-checks that the commit being updated actually belongs to the repository/organization that authenticated the request — it looks up commits by SHA alone, across every stack in the database [3](#0-2) .

### Finding Description
This mirrors the report's bug class: a security decision (which value is "trusted") is bound to one piece of mutable/attacker-influenced state (the org that authenticates), while the actual state that gets mutated (which `Commit` row receives the new status) is selected by a different, unconstrained key (`sha`) with no cross-check back to the authenticating repository/organization.

Concretely:
- The webhook signature only proves that the request came from a GitHub App installation belonging to *some* organization the attacker controls or has push/status access to (e.g., their own fork or a small unrelated repository tracked by the same Shipit instance) — this authenticates the organization, not the repository being written.
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , matching purely on `sha` with no `stack_id`/repository scoping.
- Because forks share git history, an identical commit (same tree, parents, author/committer timestamps, and message) pushed to a fork has the exact same SHA as it does in the upstream repository. If both the fork and the upstream repository are tracked as Shipit stacks (a very common setup for the merge-queue/PR workflow this engine supports), an attacker who only has status-posting rights on their own fork can send a `status` webhook event that is authenticated for their fork's organization/app but is written onto the `Commit` record belonging to the unrelated upstream stack, because the lookup ignores which repository authenticated the request.

Binding broken (as an equality that should hold but doesn't):
`organization_that_authenticated_the_signature == repository_owning_the_commit_row_that_gets_written`

Before the attacker's request: the commit's status in the target (protected) stack reflects real CI results reported through the legitimate app installation for that repository.
After the attacker's request: the same commit row can be updated with a spoofed `state`/`context`/`target_url` sourced from a webhook that was only authenticated for a different, attacker-controlled repository.

### Impact Explanation
A forged "success" status on a shared commit can satisfy `required_statuses`/`blocking_statuses` checks used by `Commit#deployable?`, `Stack#deployable?`, and `MergeRequest#any_status_checks_missing?`/`#any_status_checks_failed?` (via `StatusChecker`) [4](#0-3) , which gate both continuous-deployment triggers (`Stack#trigger_continuous_delivery`) and merge-queue completion (`MergeRequest#merge!`). This can lead to an unauthorized deploy or an unauthorized merge of a commit that never had valid CI status on the protected repository — matching the "unauthorized deploy…or merge" High-impact category.

### Likelihood Explanation
Requires: (1) the target commit to exist identically (same SHA) in a repository the attacker controls or has status/write access to, and (2) that attacker-controlled repository to also be onboarded as a Shipit stack (or otherwise trigger a validly-signed `status` webhook). This is a realistic scenario for the fork + merge-queue / review-stack workflows this engine is built around, but it is conditional on the specific multi-repo/fork topology and on the attacker's repo being tracked, so likelihood is moderate rather than trivial.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous check-run/check-suite handlers) to commits belonging to the stack(s) whose repository matches the payload's `repository.full_name`/owner — the same organization that authenticated the webhook — rather than matching on `sha` alone across the entire database.

### Proof of Concept
Not independently executable from static analysis alone (requires a live multi-repo Shipit deployment with a fork tracked as a stack), but the mechanism is directly traceable in code:
1. Attacker forks the upstream repo (tracked by Shipit as `stack A`) into their own org, which is also tracked by Shipit as `stack B` (e.g. for review-stack/PR automation).
2. Attacker cherry-picks/pushes the exact target commit (same SHA) into their fork and posts (or has their own CI post) a `status` webhook with `state: success` for a required context, signed with their fork's own GitHub App secret.
3. `WebhooksController#verify_signature` validates the signature against the attacker's own organization's app [5](#0-4) .
4. `StatusHandler#process` finds the `Commit` row(s) with that SHA across all stacks, including the one belonging to upstream stack A, and writes the forged status onto it [3](#0-2) .
5. Stack A's `deployable?`/merge-queue checks now see the forged "success" status and may trigger a deploy or complete a merge for a commit that was never actually validated by upstream's own CI.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
