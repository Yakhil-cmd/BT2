### Title
Insecure oracle: `data_feed[[...]]` reads unstabilized/manipulable data-feed values from in-flight AA responses - ([File: data_feeds.js])

### Summary
The `data_feed` oscript operator, used by any AA to price assets, settle bets, or gate payments, can resolve to a value posted by an **unstable, not-yet-finalized AA response** in the same DAG round as the reading AA's own trigger. This mirrors the Inverse Finance root cause of "using insecure oracles to calculate prices": a value that can be freshly manipulated and consumed atomically, before any finality check can reject the manipulation, is fed directly into fund-moving logic.

### Finding Description
`readDataFeedValue()` in `data_feeds.js` is the function that resolves `data_feed[[...]]` for oscript formulas. When invoked with a truthy `unstable_opts` (which is exactly the `bAA` flag passed from `formula/evaluation.js`'s `case 'data_feed'`), it scans `storage.assocUnstableMessages` — i.e., messages belonging to units that are **still unstable / unconfirmed** — for `data_feed` messages authored by the requested oracle address(es): [1](#0-0) 

If exactly one candidate is found it is used immediately with `ifseveral='last'`; if several are found they are sorted by `latest_included_mc_index`/`level` and the highest one wins: [2](#0-1) 

This unstable-candidate lookup is wired in directly from formula evaluation: the caller passes `bAA` (true whenever the formula executes inside an AA) as the `unstable_opts` argument of `readDataFeedValue`: [3](#0-2) 

The consequence is that an AA's `data_feed[[...]]` read is not guaranteed to reflect a *stabilized, final* oracle observation. It can reflect a value posted by another AA's response unit that was produced **in the very same unstable batch** as the reading AA's own trigger — i.e., within one atomic wave of unit posting, exactly analogous to a flash-loan attacker manipulating a price source and consuming it within the same transaction before the chain/consensus can react.

An attacker who can trigger (or who authors) an "oracle-style" AA whose output value is influenced by attacker-controlled trigger parameters (e.g., an AA that reports a computed ratio, TWAP-less spot price, or any state-derived number as a `data_feed` message) can:
1. Send a trigger to the oracle AA that causes it to post a manipulated `data_feed` value as part of its (still unstable) response.
2. In the same DAG round (parents referencing the still-unstable oracle response, or simply racing before MC advances), trigger a second, dependent AA whose logic reads `data_feed[[oracles=<oracle AA address>, ...]]` to price a swap, loan collateral, payout, etc.
3. Because `readDataFeedValue` happily picks up the unstable candidate value produced in step 1, the dependent AA acts on the manipulated figure before it is ever confirmed/stabilized, and before any other participant or bot could react to it.

This is fundamentally the same bug class the report describes for Inverse Finance: relying on a spot/quotable value that an attacker can move in the very same atomic sequence that consumes it, with no confirmation delay or manipulation-resistance (e.g., TWAP, quorum of independent stable oracles) enforced by the platform.

### Impact Explanation
Any AA design that composes with another AA as a price/data source (a documented and encouraged pattern, see `remote_aa`/getters tests) inherits this atomicity risk. A victim AA that moves funds (e.g., an AMM, lending, or option/prediction contract such as `test/samples/option_contract.oscript`, which itself calls `data_feed[[...]]` to gate payouts) can be tricked into releasing funds based on a value that only existed for the duration of one unstable DAG round and was manufactured by the attacker's own trigger sequence. This can cause direct fund loss or fund freezing in the victim AA, matching the "AA fund loss" impact criterion.

### Likelihood Explanation
Exploitation requires: (a) a victim AA that reads a `data_feed` from another AA (or an oracle whose value an attacker can influence through composable AA calls) without additional freshness/majority/TWAP safeguards, and (b) the ability to sequence two triggers so both land in the same unstable window. Both AA-to-AA composition and rapid successive triggering are ordinary, permissionless, unprivileged capabilities available to any unit poster / AA trigger sender — no privileged network position, hub, or leaked key is needed. Likelihood is Medium-to-High for any deployed AA that follows the (encouraged) cross-AA oracle-composition pattern without additional protections.

### Recommendation
- For `data_feed` reads driven by AA logic, prefer stabilized, finalized values only (i.e., disable the unstable-candidate branch in `readDataFeedValue` for value-critical financial logic, or make its use explicit/opt-in with clear warnings), rather than defaulting to `unstable_opts = bAA`.
- Document clearly, and consider providing built-in oscript aggregation primitives (median/TWAP over multiple independent stabilized data points), rather than relying solely on `ifseveral='last'` over an unstable and attacker-influenceable candidate set.
- For AA templates intended as price oracles, encourage/require multi-block confirmation delay before a data-feed value can be consumed by dependent AAs.

### Proof of Concept
1. Deploy `OracleAA`, an AA whose formula computes and posts a `data_feed` value derived from trigger-supplied or otherwise attacker-influenceable state (e.g., a spot ratio of `trigger.output[[asset=X]]`/`balance[Y]`), as part of its response messages.
2. Deploy `VictimAA` whose logic includes `data_feed[[oracles='<OracleAA address>', feed_name='price']]` to price a swap/loan/payout to the trigger address.
3. Attacker sends unit U1 triggering `OracleAA` with parameters chosen to make it emit a favorable/incorrect price in its (still-unstable) response.
4. Before U1's chain stabilizes, attacker sends unit U2 triggering `VictimAA`; `readDataFeedValue` (data_feeds.js:211-273) picks up the unstable `data_feed` message from OracleAA's response to U1 because `bAA` is true for the AA-context evaluation (formula/evaluation.js:646).
5. `VictimAA` computes and sends its payout/swap output using the manipulated (unstable, non-final) price, resulting in a value transfer favorable to the attacker before the system ever confirms whether that price was legitimate.

	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
