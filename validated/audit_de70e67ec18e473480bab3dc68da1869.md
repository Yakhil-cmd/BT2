### Title
Cross-tenant status/event forgery via organization-derived webhook signature selection independent of the acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify an inbound webhook against using an organization identifier extracted from the *unverified* payload, while the event handlers (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`) act on a completely independent `repository`/`sha` field from that same unverified payload. There is no requirement that the organization whose secret validated the signature be the owner of the repository/commit actually written to.

### Finding Description
`verify_signature` computes the org to check the signature against as: [1](#0-0) [2](#0-1) 

`repository_owner` prefers `repository.owner.login`, but falls back to the top-level `organization.login` whenever `repository.owner` is absent from the JSON body the attacker controls. The signature is verified with `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e., against the `webhook_secret` configured for whichever org name appears in that field of the *attacker-supplied* body: [3](#0-2) 

After signature verification passes, the full, separately-parsed payload is dispatched to handlers unchanged: [4](#0-3) 

Handlers then act on fields of that same payload that are never re-checked against the org that authenticated the request:
- `StatusHandler` looks up commits **only by `sha`**, with no repository/org scoping at all: [5](#0-4) 
- `PushHandler`/`CheckSuiteHandler` resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`: [6](#0-5) 

Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` (as shown in the multi-org secrets example), an entity that legitimately administers the webhook for **its own** org (Org A) knows Org A's `webhook_secret`. That entity can craft an arbitrary JSON body where the `organization.login` (or a `repository.owner.login`) is "Org A" — satisfying signature verification — while the `repository.full_name` (for push/check_suite) or `sha` (for status) references a stack/commit belonging to a completely different, victim organization/repository (Org B). The engine never confirms that the authenticated organization equals the organization that owns the repository/commit being mutated.

This is the exact analog to the cited bug class: a value ("organization") is used to select/authorize (the webhook secret used to authenticate), while a *different* value in the same unverified structure ("repository"/`sha`) is the one actually acted upon/written — and the binding between the two is never enforced.

### Impact Explanation
Via the `status` event, an attacker who only controls their own org's webhook secret can create a `Shipit::Status` record for **any commit SHA in the entire Shipit instance**, regardless of which repository/org it belongs to, since `StatusHandler#process` filters solely by `Commit.where(sha: params.sha)` with no ownership check. Commit CI/status state feeds directly into `Commit#deployable?` (`success? && !blocked?`) and `Commit#blocked?`/merge-queue scheduling: [7](#0-6) [8](#0-7) 

Forging a "success" status for a victim commit can mark it deployable and trigger continuous delivery / unblock a deploy for a repository the attacker has no access to, which maps to the required "unauthorized deploy" impact criterion. Similarly, `PushHandler`/`CheckSuiteHandler` let the attacker trigger `sync_github`/`schedule_refresh_check_runs!` against a victim stack chosen independently of the authenticating org.

### Likelihood Explanation
Exploitability requires only that the attacker knows a `webhook_secret` configured for *some* organization on the same Shipit instance (i.e., they are a legitimate tenant of a multi-org Shipit deployment, not a privileged Shipit operator, GitHub App private-key holder, or holder of an `ApiClient`/session token). This is consistent with the "unprivileged attacker" boundary defined in scope, since no Shipit session, API token, or GitHub App credential is needed — only a webhook secret for one's own, unrelated org.

### Recommendation
Do not select the verification secret from the same unverified field that determines which resource is written. Instead:
1. Verify the signature using the union/all configured orgs (or require an explicit correlation) and then, after verifying, re-derive the acting org strictly from `repository.owner.login` (never falling back silently to a different top-level `organization` object for non-membership events).
2. In `StatusHandler`, `PushHandler`, and `CheckSuiteHandler`, require that the resolved `Repository`/`Stack`'s owning organization matches the organization whose secret validated the signature, rejecting the event otherwise.
3. Consider deriving `repository_owner` deterministically per event type instead of a generic fallback shared across all handlers.

### Proof of Concept
Preconditions: Shipit configured with two orgs, e.g. `orgA` (attacker-administered, webhook secret known to attacker) and `orgB` (victim, has a tracked repository/stack and existing commit with sha `deadbeef...`).

1. Attacker computes `X-Hub-Signature: sha1=<hmac>` using OrgA's `webhook_secret` over the raw body:
```json
{
  "organization": {"login": "orgA"},
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests"
}
```
2. POST to `/webhooks` with header `X-Github-Event: status` and the body above.
3. `repository_owner` resolves to `"orgA"` (no `repository.owner.login` present) → signature verifies against OrgA's secret → passes.
4. `Shipit::Webhooks::Handlers::StatusHandler.call(params)` executes `Commit.where(sha: "deadbeef...")` — the victim's commit in `orgB`'s repository — and calls `create_status_from_github!`, creating a forged "success" status for a commit the attacker does not control, independent of the organization that authenticated the request.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
