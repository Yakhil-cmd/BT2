### Title
Cross-org signature verification allows attacker's own valid webhook signature to mutate commit statuses belonging to a different organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App/secret associated with `repository.owner.login` taken from the *attacker-controlled* payload body, not from the `sha` being mutated. `StatusHandler#process` then updates `Commit.where(sha: params.sha)` globally, with no re-check that the `sha` actually belongs to a stack tied to the org that was just verified. An attacker who owns any registered GitHub org/repo in Shipit can therefore send a validly-signed `status` webhook naming a victim `sha` (learned from any public commit/PR in another org's repo) and mutate that commit's status, satisfying "payload for one repository mutating another's stack/commit."

### Finding Description
The broken binding: the code implicitly assumes `verified_org == owning_org(sha)`, but nothing enforces this equality.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login')` (attacker-supplied JSON body) and does `Shipit.github(organization: repository_owner)` to fetch that org's `webhook_secret`, then checks the HMAC signature against `request.raw_post` [1](#0-0)  and derives `repository_owner` purely from `params` [2](#0-1) .
- This only proves the request was signed with **org X's** secret where X == `repository.owner.login` from the same payload — it is a tautological check, not proof that the `sha` inside the payload belongs to org X's repositories/stacks.
- After verification, `create` dispatches the raw parsed JSON to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- `StatusHandler#process` looks up commits **globally by `sha` alone**, with no scoping to the repository/org that signed the request: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . The handler's `params` schema only requires `sha`, `state`, and optional fields — no repository/org field is validated or cross-checked [5](#0-4) .

Attacker flow: attacker registers/owns org X in Shipit's GitHub config (or any repo whose org has a Shipit `webhook_secret` the attacker can obtain by being a legitimate member of that org — trivial since Shipit supports many orgs, and the attacker only needs to be a normal, unprivileged member/owner of *some* onboarded org, not the victim's). Attacker crafts a `status` event JSON body with `repository.owner.login = "X"` (their own org) and `sha` = victim commit sha from org Y's repo (learned via any public GitHub API/webpage), signs it with org X's `webhook_secret` (which they control fully, since it's their own org's webhook), and POSTs to `/webhooks`. `verify_signature` succeeds (X's signature checked against X's secret — legitimately valid). `StatusHandler#process` then finds and mutates the `Commit` row matching `sha` regardless of which org it came from.

Guards checked and found insufficient: `check_if_ping`/`drop_unhandled_event` only gate on event type, not repository ownership. `ExplicitParameters` schema for `StatusHandler` validates only `sha`/`state`/etc., not repository identity. No `require_permission!`/`current_api_client` check exists in this controller (it's public, unauthenticated-by-secret only). No model-level validation cross-references `Commit#sha` uniqueness/ownership against the verified org.

### Impact Explanation
An attacker with control of one legitimate, low-privilege Shipit-registered organization can write forged commit statuses (state/description/target_url/context) onto ANY commit tracked by Shipit across ANY other organization's stacks, by merely knowing that commit's `sha` (public information). Since commit statuses can gate deploy checks (e.g., CI/required-status checks referenced by Shipit's deploy pipeline), this can be used to fake a "success" status on a victim's commit to unblock/trigger deploys, or fake a "failure"/"error" to block legitimate deploys — a cross-tenant integrity violation matching "a payload for one repository mutating another's stack/commit," rated Critical. This is repeatable for any `sha` and any number of victim orgs/stacks, since the only requirement is knowing the sha.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with at least one org besides the victim's that the attacker legitimately controls the webhook secret for (common in multi-tenant Shipit deployments, e.g., self-service org onboarding), and the attacker must know a target commit `sha` (public via GitHub). No Shipit session, API token, or special role is needed — purely a normal webhook POST with a self-controlled signature. Attacker cost is minimal: crafting one JSON payload and computing an HMAC-SHA1 with their own known secret. Fully repeatable and automatable against arbitrary shas/stacks.

### Recommendation
In `StatusHandler#process` (and other handlers doing global `sha`/`login`-based lookups), scope the lookup to commits/stacks whose repository matches the verified `repository_owner`/`repository.full_name` from the same payload, e.g. join through `Stack` → `Repository` and filter by `Repository#owner`/`full_name` equal to the value used in `verify_signature`, rejecting mismatches. More generally, `verify_signature` should pass down the verified organization to handlers, and handlers should assert `commit.stack.repository.owner == verified_org` before mutating.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`:
1. Create `stack_x` under org `"attacker-org"` (registered with a known `webhook_secret_x`) and `stack_y` under org `"victim-org"` (different `webhook_secret_y`), each with their own `Commit` (`commit_x.sha`, `commit_y.sha`).
2. Build a `status` webhook JSON body with `repository.owner.login = "attacker-org"` but `sha: commit_y.sha`, `state: "success"`.
3. Sign the raw JSON body with `webhook_secret_x` (org X's own secret) as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. Assert response is `200 OK` (signature verification succeeded — confirm `verify_signature` did not fail with `422`).
6. Assert `commit_y.reload.statuses` (or `commit_y.create_status_from_github!` side effects, e.g. state) now reflects the attacker-supplied status, even though the signing org was `"attacker-org"` and `commit_y` belongs to `"victim-org"`'s stack — proving `verified_org ("attacker-org") != owning_org(sha) ("victim-org")` yet the mutation still occurred.
