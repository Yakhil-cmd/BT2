### Title
Cross-repository commit-status forgery via global SHA lookup in `StatusHandler#process` enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by SHA (`Commit.where(sha: params.sha)`), with no check that the payload's `repository.full_name` matches the `github_repo_name` of the stack the matched commit belongs to. Webhook signature verification (`WebhooksController#verify_signature`) only authenticates the payload against the *organization owner*, not the specific repository, so a genuinely GitHub-signed status event for one repository can write a `Status` row onto a commit that actually belongs to a different repository's stack, and that forged status can flip `MergeRequest#all_status_checks_passed?` to true.

### Finding Description
The binding the code should enforce is: `params.dig('repository','full_name') == commit.stack.github_repo_name` for the commit being updated. This is never checked.

Path:
- `WebhooksController#verify_signature` [1](#0-0)  only verifies the HMAC against `Shipit.github(organization: repository_owner)`, i.e. it authenticates "this payload was really sent by GitHub for this organization," not "for this specific repository."
- `StatusHandler#process` then does a completely global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . It ignores `params['repository']` entirely.
- `Commit#create_status_from_github!` writes the new `Status` scoped to `commit.stack_id`, i.e. whatever stack this commit row already belongs to in Shipit's DB [3](#0-2) .
- `MergeRequest#all_status_checks_passed?` builds `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)` directly from `head.statuses_and_check_runs` (`statuses + check_runs`) [4](#0-3) , with no re-verification of which repository actually produced each status.
- `ProcessMergeRequestsJob#perform` calls `merge_request.refresh!` (pulls real GitHub statuses for the correct repo) then checks `all_status_checks_passed?` and calls `merge_request.merge!` [5](#0-4) . Crucially, `refresh_statuses!`/`refresh_check_runs!` only *add* statuses returned by the real GitHub API for that sha [6](#0-5) ; they never delete or invalidate a previously-inserted forged `Status` row. `Status::Group#initialize` deduplicates by `uniq(&:context)`, keeping the first occurrence in array order [7](#0-6) , so whether the forged row or the real (missing/pending) row wins for a given context is a function of association ordering, not authentication — the forged row is not guaranteed to be superseded.

Exploit flow: an attacker who controls Repo A (same GitHub organization/webhook-secret scope as target Repo B, e.g. any repo they can create or push to under that org) crafts a git commit in Repo A whose tree, parents, author/committer identities and timestamps are byte-identical to the public head commit of the target pending `MergeRequest` on Repo B — this reproduces the exact same SHA-1 without any hash-collision attack, since all inputs to `git commit` hashing are publicly visible for a public PR. The attacker then sets a commit status via the GitHub Status API on their own Repo A commit, with the `context` equal to the merge-required context and `state: success`. GitHub delivers a legitimately signed `status` webhook to Shipit for Repo A. `verify_signature` passes (it's really GitHub, really signed, for a known org). `StatusHandler#process` looks up `Commit.where(sha: ...)` and finds Repo B's tracked commit (already present because it's the head of a pending merge request), writing a `success` status scoped to Repo B's stack. On the next `ProcessMergeRequestsJob` run, `all_status_checks_passed?` can now return true and `merge_request.merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, ...)` for Repo B [8](#0-7) .

No existing guard checks this: `verify_signature` is organization-scoped, not repository-scoped; `StatusHandler`'s `ExplicitParameters` schema only validates types, not repository ownership; there is no `force_github_authentication`/`require_permission!` involved since this is an unauthenticated webhook endpoint by design.

### Impact Explanation
A payload authenticated for one repository (Repo A) can write a `Status` record onto a commit belonging to a different repository's stack (Repo B), and — combined with the merge queue's auto-merge flow — this can produce an unauthorized `merge_pull_request` call against Repo B, a repository the attacker does not control. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The blast radius is any pair of repositories sharing a Shipit-known organization/webhook configuration; it is repeatable per pending merge request whose head commit's exact content the attacker can reproduce (feasible for any public head commit).

### Likelihood Explanation
Preconditions: Repo B must have `merge_queue_enabled`, a pending `MergeRequest` with a still-unsatisfied required status context, and its head commit's git metadata must be publicly reconstructible (true for any public GitHub PR). The attacker needs a repository (Repo A) whose owner/organization is recognized by Shipit's `Shipit.github(organization:)` configuration (so `verify_signature` doesn't reject with `GithubOrganizationUnknown`) — this is satisfied whenever Repo A is in the same GitHub organization Shipit is installed for, which is a common multi-repo deployment. No Shipit secrets, session, or API token are needed; the only "cost" is crafting one Git commit with identical metadata and calling the GitHub Statuses API on a repo the attacker owns.

### Recommendation
In `StatusHandler#process` (and analogously in the `check_run`/`check_suite` handlers), scope the commit lookup by the payload's own repository, not just by SHA: join/filter through `Stack` on `params.dig('repository','full_name')` (or `owner/name`) and only call `create_status_from_github!` on commits whose `stack.github_repo_name` matches the repository that produced the webhook. Reject or ignore the event otherwise.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/jobs/process_merge_requests_job_test.rb`):
```ruby
test "status payload for repo A must not flip merge status for repo B's commit sharing the same sha" do
  stack_b = shipit_stacks(:shipit) # github_repo_name => "shopify/shipit-engine"
  merge_request = shipit_merge_requests(:pending_with_required_status) # head.sha == SHA
  required_context = merge_request.stack.cached_deploy_spec.merge_request_required_statuses.first

  refute merge_request.all_status_checks_passed?

  # Payload signed for a DIFFERENT repository (Repo A), same sha, required context, success
  params = ExplicitParameters::Params.new(
    sha: merge_request.head.sha,
    state: 'success',
    context: required_context
  )
  # repository.full_name in the raw webhook body is "attacker-org/repo-a", not stack_b.github_repo_name
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  merge_request.reload
  assert merge_request.all_status_checks_passed?, "forged cross-repo status incorrectly satisfied the check"

  Shipit.github.api.expects(:merge_pull_request).never # assert Repo B is NOT merged off an unrelated repo's status
  ProcessMergeRequestsJob.new.perform(stack_b)
end
```
This demonstrates: (a) `StatusHandler#process` writes the status onto `stack_b`'s commit with no repository binding check, and (b) `all_status_checks_passed?`/`ProcessMergeRequestsJob` acts on it, ultimately calling `merge_pull_request` for `stack_b.github_repo_name`, despite the originating webhook payload's `repository.full_name` differing from `stack_b`'s repo.
