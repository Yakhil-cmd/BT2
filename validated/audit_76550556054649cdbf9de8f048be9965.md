### Title
Unauthenticated GitHub webhook impersonation when an organization's `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` fails open when `webhook_secret` is blank/unset, mirroring the reported "unset critical address bypasses a required check" bug class. Because the organization used to select which `GitHubApp` config (and therefore which secret) validates a webhook is itself taken from the unverified request body, any organization configured without a `webhook_secret` allows an unauthenticated attacker to forge arbitrary GitHub webhook events for that organization's repositories.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to validate against using an attacker-supplied field from the JSON body, before any authenticity is established: [1](#0-0) [2](#0-1) 

The selected `GitHubApp` then verifies the signature with: [3](#0-2) 

`return true unless webhook_secret` means that for any organization whose configuration omits `webhook_secret` (an explicitly supported/nil value, as shown in the shipped config templates), signature verification is skipped entirely and `verified` is always `true`, regardless of the `X-Hub-Signature` header content: [4](#0-3) [5](#0-4) 

Once `verified` is true, the controller dispatches the entire attacker-controlled payload to all registered handlers for the claimed event type with no further authentication: [6](#0-5) 

This breaks the binding "an organization that authenticated == the repository/team that is written": the `repository_owner`/`organization.login` value used to pick a trust anchor is not itself cryptographically bound to anything when that anchor has no secret, so an attacker can claim to be any such organization.

### Impact Explanation
Handlers triggered from unauthenticated webhook payloads include state-mutating operations with no additional authorization check, e.g. the `membership` handler which creates/removes `Membership` and `Team` records purely from the JSON body: [7](#0-6) [8](#0-7) 

Because `User#authorized?` is gated purely on team membership synced from these webhooks: [9](#0-8) 

an attacker can forge a `membership` event to add an arbitrary GitHub login to a `Shipit.github_teams` team, escalating that account (once it authenticates via OAuth) into full application authorization. Additionally, forged `push`, `status`, `check_suite`, `pull_request`, and `merge` events can manipulate commit statuses, queue `GithubSyncJob`, and influence merge/deploy eligibility for stacks belonging to the impersonated organization — matching the "escalation into `Shipit.github_teams` authorization" and "unauthorized deploy/rollback/merge" impact tiers.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires at least one configured GitHub organization in `secrets.github` with `webhook_secret` unset (nil/blank). This is not a hypothetical edge case — the project's own shipped example configs (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`) explicitly show `webhook_secret:` as commented "# nil", indicating this is an accepted, easy-to-reach default/documented configuration rather than a misuse of undocumented internals. No credential, token, or session is required by the attacker — only knowledge of (or guessing of) an organization login lacking a webhook secret and the public `/webhooks` endpoint.

### Recommendation
- Make `verify_webhook_signature` fail closed: if `webhook_secret` is blank, treat the webhook as unverifiable and reject it (return `false`), rather than silently accepting all requests.
- Require `webhook_secret` presence at configuration-load time for every configured organization (raise at boot / `Shipit.github_app_config` validation) instead of allowing a silent fallback.
- Do not use a value taken from the unverified request body to select the verification secret before any part of the payload has been authenticated; if per-org secrets must be selected dynamically, verify the signature against all configured secrets rather than trusting the payload's claimed `organization`/`repository.owner`.

### Proof of Concept
1. Configure (or find already configured, as in the shipped example) an organization in `secrets.github` with `webhook_secret` left blank, e.g. `someothergithuborg`.
2. As an unauthenticated attacker, send:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=deadbeef   (arbitrary/invalid)
Content-Type: application/json

{
  "action": "added",
  "organization": {"login": "someothergithuborg"},
  "team": {"id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com"},
  "member": {"login": "attacker-controlled-login"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: "someothergithuborg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `MembershipHandler` processes the forged event and creates a `Membership` linking `attacker-controlled-login` to team `admins`, exactly as exercised in [10](#0-9)  — but here triggered by an attacker with no valid signature at all.
5. If `admins`/`Shipit.github_teams` grants dashboard authorization, the attacker's GitHub account (once it completes OAuth login) is now `authorized?` in Shipit, per [9](#0-8) .

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
