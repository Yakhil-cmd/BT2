### Title
Unauthenticated `membership` webhook forgery grants/revokes team membership when the target org has no `webhook_secret` - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization's config has a blank `webhook_secret`, so any org configured in Shipit without a webhook secret accepts arbitrary unsigned webhook bodies. Combined with `MembershipHandler`, an unprivileged attacker can forge a `membership` event to add or remove arbitrary GitHub users from Shipit `Team` records, which are read by `User#authorized?` for team-based authorization.

### Finding Description
The broken binding: "a webhook is trusted" should be equivalent to "the request HMAC matches `webhook_secret` configured for that organization." In practice the code implements: `verified = webhook_secret.blank? ? true : HMAC_matches`.

Code path:
1. `Shipit::WebhooksController#verify_signature` resolves the org from attacker-controlled JSON via `repository_owner` (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), then calls `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
2. `Shipit.github_app_config(organization)` looks up the per-org config by downcased key; if the org exists in `secrets.github` but its config has no `webhook_secret` key, `GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret`. [3](#0-2) 
3. Because `verified` is `true`, `head(422)` is not called, and `Shipit::WebhooksController#create` dispatches the raw attacker-controlled JSON to `Shipit::Webhooks.for_event('membership')`, invoking `MembershipHandler#process`. [4](#0-3) 
4. `MembershipHandler` finds/creates a `Team` keyed only by `params.team.id` (attacker-supplied integer) and a `User` keyed by `params.member.login` (attacker-supplied string, resolved via `Shipit.github.api.user(login)`), then adds/removes membership based on `params.action`. [5](#0-4) 
5. `User#authorized?` reads exactly these membership rows: `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, where `Shipit.github_teams` is derived from `github.oauth_teams` and resolved to `Team` records by handle via `Team.find_or_create_by_handle`. [6](#0-5) [7](#0-6) 

The attacker's forged request: `POST /webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<any known oauth-team github_id>,"name":..,"slug":..,"url":..},"organization":{"login":"<org-without-webhook_secret>"},"member":{"login":"<attacker-or-victim-github-login>"}}`. No `X-Hub-Signature` needed since it's ignored for that org.

Existing guards fail because:
- `drop_unhandled_event` only checks the event is registered (`membership` is registered), it does not check authenticity.
- `verify_signature`/`verify_webhook_signature` is the sole authenticity gate, and it is bypassed by design for orgs lacking `webhook_secret` — this is documented "backward compatibility"-style behavior but has no signature fallback, unlike a HMAC-required-by-default posture.
- `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not trust.
- `force_github_authentication`/`require_permission!` are session-based guards on the web UI, irrelevant to this unauthenticated webhook endpoint.

### Impact Explanation
Any org present in `secrets.github` that is misconfigured without `webhook_secret` becomes a free forgery target: unauthenticated requests can add arbitrary GitHub logins (including the attacker's own account) to any `Team` whose `github_id` is guessed/known, directly manipulating the membership rows consumed by `User#authorized?`. If that `Team` is one of `Shipit.github_teams` (the configured OAuth authorization teams), this is a direct authorization escalation into `Shipit.github_teams`, letting an attacker's own GitHub account authenticate via OAuth and pass `authorized?` checks it should not pass — matching the High/Critical impact category of "escalation into `Shipit.github_teams` authorization" / "authentication bypass." It is repeatable indefinitely and does not require any secret, token, or session.

### Likelihood Explanation
Preconditions: at least one organization entry in Shipit's `secrets.github` multi-org config must omit `webhook_secret` (a plausible, easy-to-make misconfiguration since the schema allows it and there is no validation forcing its presence). No other secret, session, or role is required by the attacker — cost is a single unauthenticated HTTP POST with a guessable/observable `team.id` and any target login. This is fully attacker-controlled and repeatable.

### Recommendation
Do not allow `verify_webhook_signature` to auto-succeed when `webhook_secret` is blank; instead treat a missing secret as a hard misconfiguration (raise/log and reject with 422, or refuse to boot/serve webhooks for that org) so every org has mandatory HMAC verification. Additionally, consider validating at config-load time that every entry in `secrets.github` (or the top-level config) has a non-blank `webhook_secret`.

### Proof of Concept
Minitest plan (webhooks_controller_test.rb style, under `test/`, no live GitHub):
1. Configure `Shipit.stub` (or seed `secrets.github`) with an org, e.g. `"acme"`, whose config hash has no `webhook_secret` key.
2. Assert precondition equality before: `Shipit.github(organization: "acme").verify_webhook_signature("sha1=bogus", "{}") == true` (i.e., signature check is already broken independent of the request).
3. `POST /webhooks` with `X-Github-Event: membership`, no `X-Hub-Signature` header (or a garbage one), and body:
   `{"action":"added","team":{"id":42,"name":"n","slug":"s","url":"u"},"organization":{"login":"acme"},"member":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`), and assert `Shipit::Team.find_by(github_id: 42).members.exists?(login: "attacker")` is `true` — i.e., a team-membership row was created/mutated purely from an unsigned, attacker-controlled body.
5. Assert the binding after: if that team is included in `Shipit.github_teams`, `User.find_by(login: "attacker").authorized?` flips from `false` to `true` solely due to the forged webhook.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
