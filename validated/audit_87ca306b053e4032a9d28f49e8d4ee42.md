### Title
Newline injection in OAuth `login` value flows unsanitized into `git credential approve` stdin, allowing wrong-host credential poisoning - ([File: pkg/cmd/auth/shared/gitcredentials/updater.go])

### Summary
`Updater.Update` builds the `git credential approve`/`reject` stdin with a raw `%s` interpolation of `username` inside a heredoc, with no validation that the value is free of `\n`/`\r` characters. The `username` value originates from the GitHub API's `viewer.login` field (via `authflow.AuthFlow` → `getViewer` → `api.CurrentLoginName`, or `shared.GetCurrentLogin`), which is attacker-controlled when the "host" is an enterprise/attacker-controlled endpoint the victim points `gh auth login`/`gh auth refresh` at.

### Finding Description
`refreshRun` (and `Login`) call `credentialFlow.Setup(hostname, username, password)` after storing `authedUser` returned by `opts.AuthFlow` [1](#0-0) . `AuthFlow` obtains this value by querying the target host's GraphQL API for `viewer.login` in `getViewer`, with no format/charset validation on the returned string [2](#0-1) . `GitCredentialFlow.Setup` forwards this value straight to `Updater.Update` when an existing (non-gh) credential helper is configured [3](#0-2) . `Updater.Update` then interpolates `hostname`, `username`, and `password` into a heredoc-built stdin buffer passed to `git credential approve` without any escaping or newline stripping [4](#0-3) .

Because the git-credential protocol is a plain `key=value\n` stream terminated by a blank line, any `\n` embedded in `username` lets the attacker inject arbitrary additional `key=value` lines (e.g. `host=github.com`) into the same credential-approve payload. Since git's credential-store/-cache/-osxkeychain helpers key entries by the last-seen `host`/`protocol` pair before the blank line, an attacker-controlled enterprise host can return a `viewer.login` value like `attacker\nhost=github.com\n` to make the victim's git credential helper persist the attacker's token under the unrelated `github.com` entry.

No code path sanitizes or rejects control characters in the login value before it reaches this stdin construction — `api.CurrentLoginName`/`GetCurrentLogin` simply decode the JSON/GraphQL string field, and `config.Config.Login` stores it as-is.

### Impact Explanation
This breaks the credential-confinement invariant between hosts: an attacker who controls (or can respond as) an enterprise GitHub host the victim adds via `gh auth login`/`gh auth refresh` can cause the victim's system git credential helper to store the attacker's crafted credential entry under `host=github.com` (or any other host string of the attacker's choosing). Subsequent, unrelated git operations against github.com could then present the attacker-controlled username/token, i.e., wrong-host credential routing/poisoning — matching the "authenticated request to attacker-controlled host" / credential-confinement bounty class.

### Likelihood Explanation
Requires: (1) victim interactively runs `gh auth login`/`gh auth refresh` against an attacker-controlled or compromised enterprise host, (2) victim has answered "yes" to configuring git with GitHub credentials, and (3) victim already has a non-gh git credential helper configured (e.g. osxkeychain/store) so the `Updater.Update` path (rather than `ConfigureOurs`) is taken. These are realistic conditions for anyone testing/using a GHES instance under attacker influence, and the exploit requires no MITM or elevated privileges — just a malicious GraphQL response for `viewer.login`.

### Recommendation
Reject or sanitize `username`/`password` values before constructing the git-credential protocol payload in `Updater.Update` — e.g. return an error if `hostname`, `username`, or `password` contain `\n`, `\r`, or `=`-line-breaking sequences, or use `git credential-store`'s recommended API (writing via `-` args rather than string interpolation) so no field can inject additional protocol lines.

### Proof of Concept
```go
package gitcredentials_test

import (
    "bytes"
    "testing"

    "github.com/cli/cli/v2/git"
    "github.com/cli/cli/v2/internal/run"
    "github.com/cli/cli/v2/pkg/cmd/auth/shared/gitcredentials"
    "github.com/stretchr/testify/require"
)

func TestUpdate_RejectsNewlineInjectionInUsername(t *testing.T) {
    cs, restoreRun := run.Stub()
    defer restoreRun(t)

    var capturedStdin string
    cs.Register(`git credential reject`, 0, "")
    cs.Register(`git credential approve`, 0, "", func(args []string) {})
    // capture stdin passed to approve via a custom exec stub if run.Stub supports stdin capture,
    // otherwise use git.Client with a fake CommandContext that records cmd.Stdin bytes.

    u := &gitcredentials.Updater{GitClient: &git.Client{GitPath: "git"}}
    maliciousUsername := "attacker\nhost=github.com\nprotocol=https"
    err := u.Update("example.com", maliciousUsername, "TOKEN")
    require.NoError(t, err)

    // Expected (fixed) behavior: Update should return an error for embedded
    // newlines in username, or the captured stdin should contain exactly
    // one `host=` line matching "example.com" and no extra `host=github.com` line.
    require.NotContains(t, capturedStdin, "host=github.com")
}
```
Expected assertion after remediation: `Update` errors out on control characters in `username`/`password`, or the captured `approveCmd.Stdin` buffer contains only the single intended `host=example.com` line with no attacker-injected `host=`/`protocol=` lines.

	// If there is no credential helper configured then we will set ourselves up as
