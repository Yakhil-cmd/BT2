Based on my research, I found a concrete structural analog to the reported bug class: a value used to authenticate a request is derived from one payload field, while a *different* field from the same, unverified payload is what actually gets acted upon — exactly the "organization that authenticated versus the repository that is written" binding called out in the rules.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` from the same unverified payload, allowing a valid signature from one organization to authorize writes against a stack belonging to a different repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification by reading `repository_owner` out of the raw JSON body itself, then, once verification "succeeds", the entire unmodified body is handed to the registered webhook handlers, which resolve the target `Stack`/`Commit`/`Repository` using other fields of that same body (e.g. branch, sha, full name). Because the field used to pick the verifying secret and the fields used to select the object being mutated are not cryptographically bound to each other, an attacker who can obtain (or is entitled to) the webhook secret for organization A can forge a payload that is verified as "from org A" while its repository-identifying fields point at a stack/repository under a different organization or repo.

### Finding Description
`verify_signature` computes:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it exclusively to pick the `github_app`/secret to validate the signature against:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [2](#0-1) 

After this check passes, `create` re-parses the same raw body and dispatches it, untouched, to all registered handlers for the event:
```
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers such as `PushHandler` and `StatusHandler` then use *other* fields of that same body — `ref`/`after`/branch for push, `sha`/`state` for status — to select which `Stack`/`Commit` to mutate: [4](#0-3) [5](#0-4) 

Shipit explicitly supports multiple GitHub organizations, each with its own independently configured `webhook_secret`: [6](#0-5) 

Equality that should hold but does not: `organization_that_signed(payload) == organization_that_owns(repository_acted_on(payload))`. Because both sides are read from the same attacker-controlled JSON body, and the signature only cryptographically covers "the bytes match some org's secret," not "the repository/branch/sha fields belong to that org," an attacker holding organization A's webhook secret can set `repository.owner.login = "org-a"` (so verification passes with org A's secret) while setting the rest of the payload (e.g. `ref`, `after`, `sha`, or a differently-cased `repository.full_name`) to reference a stack that actually belongs to organization B.

### Impact Explanation
If exploitable, this allows an attacker who legitimately controls one onboarded organization's webhook secret (a low-privilege, "unprivileged" position relative to any other tenant/org configured on the same Shipit instance) to trigger `sync_github`, commit-status creation, or merge-queue processing (`stack.schedule_merges`) against stacks belonging to a different, unrelated organization/repository. This is a cross-repository, cross-tenant write, matching the "cross-repository writes" Critical-impact category — an attacker can force spurious GitHub sync/merge/deploy-eligibility state changes on a repository they do not own or have any access to, purely through the shared `/webhooks` endpoint.

### Likelihood Explanation
Likelihood depends entirely on the deployment being multi-organization (multiple entries under `secrets.github`, each with a distinct `webhook_secret`), which the codebase explicitly supports (`github_organizations`, `github_app_config`). For a single-organization deployment (the documented/typical setup in `docs/setup.md`), this collapses to a non-issue because there is only one possible `repository_owner`/secret pair, so this analog's exploitability is conditional on operator configuration that I could not fully verify is common. I was also unable to fully inspect the base `Shipit::Webhooks::Handlers::Handler#stacks` scope (tool errors prevented reading `app/models/shipit/webhooks/handlers/handler.rb` in the final iteration), so I cannot confirm with certainty whether that scope re-derives/re-validates the repository from `full_name` independently of `owner.login`, or whether some other guard rejects owner/full_name mismatches before a handler mutates state. This is a material gap in verification.

### Recommendation
Bind the field used for signature verification to the same field(s) used by handlers to resolve the target object: derive the verifying organization from a value that is either (a) also used, unmodified, by every handler to scope its lookups, or (b) cross-checked so that `repository.full_name`'s owner segment must equal `repository.owner.login`/`organization.login` before any handler runs. Reject the webhook (422) on mismatch instead of merely picking a secret to check against.

### Proof of Concept
Conceptual PoC (pending confirmation of `Handler#stacks` internals):
1. Attacker onboards/controls org "attacker-org" on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `push` (or `status`) payload where `repository.owner.login = "attacker-org"` (so `repository_owner` resolves to attacker-org's `github_app`, and the HMAC computed with attacker-org's secret verifies), but sets the branch/sha/other repository-identifying fields to correspond to a stack belonging to `victim-org/victim-repo`.
3. POST to `/webhooks` with `X-Hub-Signature` computed using attacker-org's secret.
4. `verify_signature` passes (secret matches attacker-org). `PushHandler`/`StatusHandler` then act on the victim stack's data using the fields that were never covered by the (attacker-org-scoped) signature check.

This PoC's final step could not be fully confirmed against `Handler#stacks`'s actual query due to a tool failure in the last research iteration; a background engineer should verify that scope's implementation before treating this as fully confirmed exploitable.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
