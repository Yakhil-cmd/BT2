### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` — authenticated organization ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC `webhook_secret`) to verify a webhook against using `repository.owner.login` from the JSON body, while every webhook handler resolves the `Stack`/`Repository` to act on using the unrelated `repository.full_name` field from the *same* attacker-controlled body. These two fields are never cross-checked, so a valid signature only proves "this body was signed with organization A's secret" — it proves nothing about which repository the body's `full_name` field claims to target.

### Finding Description
`verify_signature` derives the signing organization purely from payload content, before the signature itself is checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with that organization's configured `webhook_secret`; it does not constrain any field inside the JSON: [3](#0-2) 

Multiple, independently configured organizations/GitHub Apps can be registered in the same Shipit instance, each with its own `webhook_secret`: [4](#0-3) 

After the signature check passes, every handler resolves the target `Stack`/`Repository` from `repository.full_name` — a completely different field from the one used to pick the verification key: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret signed the payload == organization that owns the repository named in the payload`. Nothing enforces this equality — `repository.owner.login` and `repository.full_name` are independent strings inside the same attacker-crafted JSON body. An entity that legitimately controls the webhook secret of *one* onboarded GitHub App (an ordinary, non-privileged relationship to that App's own settings — not a Shipit credential, session, or `webhook_secret` belonging to the victim) can forge a raw body where:
- `repository.owner.login = "orgA"` (their own org, so the correct HMAC key is selected and the signature verifies), and
- `repository.full_name = "victim-org/private-repo"` (an unrelated repository/stack tracked under a different organization on the same Shipit instance).

Because handlers never re-check that `full_name`'s owner matches the organization that produced the valid signature, the forged webhook is processed as if it legitimately originated from the victim organization.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding explicitly called out as in-scope. Concretely, the attacker can drive, for any stack backed by a repository under a *different* organization than the one whose secret they control:
- `PushHandler#process` → `stack.sync_github(expected_head_sha:)` on arbitrary stacks not belonging to their organization.
- `ReviewStackAdapter#archive!` / `unarchive!` / `find_or_create!` (via the pull_request handlers) → deprovisioning, archiving, unarchiving, or creating review-stack environments for a victim organization's repository, driven entirely by attacker-supplied `pull_request.head.ref` / `number` data.

This is a cross-repository/cross-organization write achieved purely by forging a signed payload, satisfying the "cross-repository writes" / "unauthorized deploy or rollback" impact bar.

### Likelihood Explanation
Exploitability requires only that the attacker control the webhook secret of *some* GitHub App organization already onboarded onto the shared Shipit instance (a normal capability for any org admin who installed their own App on that instance) and that a victim organization's repository is also tracked by the same instance — a realistic multi-tenant deployment as documented in `docs/setup.md`. No Shipit session, API token, or the victim's own `webhook_secret` is needed.

### Recommendation
After verifying the signature, re-derive the organization from `repository.full_name` (or `repository.owner.login` used consistently for both signature selection and repository lookup) and reject/short-circuit the request if the signing organization does not match the owner of the repository named in `full_name`. Alternatively, scope `Repository.from_github_repo_name` lookups to the verified organization instead of a global unscoped match.

### Proof of Concept
1. Register/administer a GitHub App for `orgA` on the shared Shipit instance and note its `webhook_secret`.
2. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orgA" }, "full_name": "victim-org/private-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` selects `orgA`'s app via `repository.owner.login`, the HMAC verifies successfully, and `PushHandler` resolves the stack via `repository.full_name = "victim-org/private-repo"`, triggering `sync_github` on a stack the attacker does not control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
