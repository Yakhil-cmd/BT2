### Title
`status` webhook handler applies commit statuses by SHA alone, breaking the organization-authenticated-vs-repository-written binding — cross-repository CI status forgery enabling unauthorized deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook only against the GitHub App/organization derived from the payload's own `repository.owner.login` (or `organization.login`) field, and validates the HMAC using that organization's `webhook_secret`. [1](#0-0)  Once the signature is accepted, the event handler dispatch (`Shipit::Webhooks.for_event`) hands the raw payload to `StatusHandler`, which resolves the target `Commit` purely by `sha`, with no cross-check that the commit's stack/repository actually belongs to the authenticated organization: [2](#0-1) 

Unlike `PushHandler`, which scopes affected stacks through `Repository.from_github_repo_name(repository_name)` before acting [3](#0-2)  and the shared `Handler#stacks`/`Handler#repository_name` helpers [4](#0-3) , `StatusHandler` never calls `stacks` or checks `repository_name` at all — it queries `Commit.where(sha: params.sha)` globally across every repository tracked by the Shipit instance and writes a status onto every match: [5](#0-4) 

### Finding Description
The equality that should hold is:

`organization authenticated by verify_signature (payload.repository.owner.login / webhook_secret)` == `repository whose Commit records are mutated by the handler`

`verify_signature` binds trust to the org named in the *signed* payload's `repository`/`organization` field [6](#0-5) . That is the only scope the HMAC verification (`GitHubApp#verify_webhook_signature`) actually covers [7](#0-6) . But `StatusHandler#process` never re-derives or re-checks that scope — it matches by `sha` alone against the entire `Commit` table, which spans all repositories/organizations onboarded to this Shipit instance [5](#0-4) .

A commit SHA is a 40-hex-character git object id that is not secret and, in the case of shared history (forked repos, vendored/mirrored repos, monorepos split across multiple tracked Shipit stacks, or simply by brute-forcing/guessing since collisions across independent commit histories are only cryptographically hard, not access-controlled), an attacker who legitimately controls *any* organization/repository already onboarded to the same Shipit instance can send a validly-signed `status` webhook (signed with their own org's real `webhook_secret`, or unsigned if that org never configured one — `verify_webhook_signature` returns `true` when `webhook_secret` is blank [8](#0-7) ) whose `repository.owner.login` names their own org, but whose `sha` value matches a commit that actually belongs to a *different* stack/repository controlled by a different organization. `Commit.where(sha:)` will still find and mutate that unrelated commit's status.

`Commit#create_status_from_github!` → `add_status` updates `statuses`, recomputes `status`, and — critically — calls `schedule_continuous_delivery`, which checks `deployable?` (true when `success?` and not blocked) and, if the target stack has `continuous_deployment?` enabled, enqueues `ContinuousDeliveryJob` to actually deploy: [9](#0-8) [10](#0-9) 

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding. An attacker who is a legitimate but unprivileged user of one onboarded GitHub organization/repository can forge `success` CI statuses onto commits belonging to an entirely different, unrelated organization's stack, without ever authenticating against that stack's GitHub App/webhook secret or holding any Shipit/API credentials for it. On a stack with `continuous_deployment?` enabled, this can trigger an **unauthorized deploy** — matching the Critical-impact criteria in the rules (unauthorized deploy/rollback triggered via a broken authentication/authorization boundary).

### Likelihood Explanation
Requires an unprivileged attacker to control (or have push/CI access to) at least one GitHub organization/repository that is already registered with the target Shipit instance, and to know or predict a target commit `sha` tracked by another stack on the same instance. This is plausible in multi-tenant Shipit deployments (a common deployment pattern — one Shipit instance serving many teams/orgs), and SHAs are frequently public (mirrored/forked repos, shared submodules, or simply observable via the target org's public GitHub activity/PRs). No repository write access, GitHub App private key, or Shipit session/API token is required — only participation as an onboarded (but otherwise unprivileged relative to the victim stack) GitHub org.

### Recommendation
`StatusHandler` (and any other handler that resolves records purely by content like `sha`) must scope its lookup through the payload's authenticated repository, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
so that a `Commit` is only updated when it belongs to a stack whose repository matches the `repository.full_name` in the same payload that was authenticated by `verify_signature`.

### Proof of Concept
1. Two independent teams onboard Shipit: `victim-org/victim-repo` (stack has `continuous_deployment: true`) and `attacker-org/attacker-repo` (attacker controls this org's GitHub App/webhook secret legitimately).
2. Attacker learns/predicts a commit SHA `S` currently tracked (and pending/failing) in `victim-org/victim-repo`'s Shipit stack — e.g. via public GitHub activity, a shared vendored dependency, or a repo fork with retained history.
3. Attacker POSTs to `/webhooks` a `status` event payload:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "full_name": "attacker-org/attacker-repo", "owner": { "login": "attacker-org" } }
}
```
signed with `attacker-org`'s real `webhook_secret` (`X-Hub-Signature`), and event header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and the signature verifies successfully since it was signed with that org's own secret. [1](#0-0) 
5. `StatusHandler.call(params)` runs `Commit.where(sha: 'S')`, which matches the commit in `victim-org/victim-repo`'s stack (since lookup ignores the `repository` field entirely), and calls `create_status_from_github!`, marking it `success`. [5](#0-4) 
6. If that commit becomes `deployable?` and the victim stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` enqueues an automatic deploy of `victim-org/victim-repo` triggered entirely by the attacker's forged webhook. [10](#0-9)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
