### Title
Webhook signature is verified against a webhook-secret selected from the unverified `repository.owner.login`, letting any org's valid webhook impersonate any other configured org's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* `GithubApp` (and thus which `webhook_secret`) to validate the signature against by reading `repository_owner` directly out of the **unverified** JSON body, then hands the entire (still same) raw payload to handlers that trust `payload.dig('repository', 'full_name')` to resolve the target `Stack`/`Repository`. The equality the engine implicitly relies on is: *`organization whose secret authenticated the signature == organization whose repository the webhook payload is acted on`.* Because the organization used to select the secret and the repository acted upon both come from the same attacker-controlled JSON body, this equality holds only incidentally, not because it's enforced.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
```
`repository_owner` is read straight from the JSON body before any cryptographic check: [2](#0-1) . `Shipit.github(organization:)` looks up a per-organization config/secret in `Rails.application.credentials.github` [3](#0-2) .

Downstream, `Handler#stacks` resolves the target `Stack` purely from `payload.dig('repository', 'full_name')` [4](#0-3) , with no re-check that this `full_name`'s owner matches the organization whose secret validated the signature.

Because Shipit is explicitly a multi-tenant, multi-organization deployment (`config/secrets.development.shopify.yml` shows multiple orgs each with their own `webhook_secret`, `app_id`, etc. [5](#0-4) ), a legitimate, validly-signed webhook from **Org A**'s GitHub App can carry a JSON body whose `repository.full_name` names a repository belonging to **Org B**, since neither the signature check nor the handler logic ties `full_name`'s owner segment to the organization that produced/verified the signature. GitHub's HMAC signature only proves "this payload was sent by someone holding Org A's `webhook_secret_A`" — it says nothing about which `repository` field values are semantically valid for that secret, and Shipit doesn't independently constrain them.

This mirrors the C4 report's bug class exactly: the code assumes a relationship between two values pulled from the same untrusted source (`latestSample` vs `priceTarget` in the original; `repository_owner` used-for-auth vs `repository.full_name` acted-upon here) without the trust boundary (secret verification / price computation) actually enforcing that relationship.

### Impact Explanation
If a Shipit deployment configures multiple organizations (as the `github:` multi-org config format explicitly supports), an actor who controls (or compromises) one organization's GitHub App/webhook delivery for Org A can forge push/status/pull_request/check_suite events referencing a repository under Org B, since:
- `push` handler triggers `GithubSyncJob` for any stack matching branch on the resolved repository [6](#0-5) , which re-syncs commits and can affect deploy state/spec caching for Org B's stack.
- `status`/`check_suite` handlers can inject fabricated CI state for Org B commits, which feeds directly into `MergeRequest#all_status_checks_passed?` and the auto-merge queue (`ProcessMergeRequestsJob` → `MergeRequest#merge!`) [7](#0-6) [8](#0-7) , potentially causing an unauthorized merge of a PR in Org B's repository by satisfying required-status checks with forged data from Org A's credentials.

This crosses the organizational trust boundary that Shipit's per-org `github:` config is meant to enforce and can lead to cross-repository effects and unauthorized merges — matching the Critical/High impact bar (cross-repository writes / unauthorized merge).

### Likelihood Explanation
Requires the target Shipit instance to be configured for **multiple** GitHub organizations (documented, supported configuration per `config/secrets.development.shopify.yml`/`docs/setup.md`), and requires the attacker to control a legitimate webhook secret for at least one of those organizations (e.g., they administer their own GitHub App installation registered with the same Shipit instance, or are a maintainer of one onboarded org). No `ApiClient` token, GitHub session, or repository write access to the victim org is needed — only the ability to send a signed webhook for their own org whose body impersonates a different org's repository name.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the organization strictly from the verified payload and require it to equal the organization used to select `github_app` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s owner must equal `repository_owner` / the app's configured organization key), rejecting the webhook otherwise. Equivalently, scope `Handler#stacks` lookups to `github_app.organization` rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who legitimately controls `org-a`'s GitHub App/webhook secret, construct a `push` (or `status`/`check_suite`) JSON payload where `repository.owner.login` = `org-a` (to pick `org-a`'s secret for verification) but `repository.full_name` = `org-b/some-repo`.
3. Sign the payload with `org-a`'s `webhook_secret` and POST it to `/webhooks`.
4. `verify_signature` selects `Shipit.github(organization: 'org-a')`, verifies successfully against `org-a`'s secret, and passes.
5. `Shipit::Webhooks.for_event(event)` dispatches to e.g. `PushHandler`, whose `stacks` resolves via `Repository.from_github_repo_name('org-b/some-repo')` [4](#0-3) , acting on `org-b`'s stack/commits despite the signature only proving possession of `org-a`'s secret.

    # Backward compatibility

    if github_default_organization.nil?

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

module Shipit
  class ProcessMergeRequestsJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :default

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
  end
end
