### Title
Membership webhook handler resolves teams by `github_id` alone, letting a signed request for one organization mutate membership of a `Team` belonging to a different organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the request is validly signed for *some* GitHub organization (resolved from `repository.owner.login` or, when absent, `organization.login`) [1](#0-0) [2](#0-1) . `MembershipHandler#find_or_create_team!` then looks up the target `Team` exclusively by the attacker-supplied numeric `team.id`, with no check that the found team's `organization` matches the verified/signing organization, and mutates that team's membership [3](#0-2) . A holder of a real webhook secret for their own org can therefore add an arbitrary GitHub login to any pre-existing `Team` record in the database (e.g. one used in `Shipit.github_teams` for access control), regardless of which organization that team belongs to.

### Finding Description
The claimed binding — `Team.organization == verified_organization` for every mutation performed by `MembershipHandler` — does **not** hold.

Path:
1. Attacker owns org `evilcorp`, which has a real `webhook_secret` configured in `Shipit.github(organization:)`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: membership`, a body with **no** `repository` key, `organization.login = "evilcorp"`, `team.id = <github_id of an existing, unrelated, privileged Team row>` (e.g. the team backing `Shipit.github_teams`), and `member.login = "attacker-login"` (or any login they want to grant/deny access to). The signature is computed correctly with `evilcorp`'s real secret.
3. `repository_owner` falls back to `params.dig('organization', 'login')` = `"evilcorp"` [2](#0-1) , so `verify_signature` calls `Shipit.github(organization: 'evilcorp')` and the HMAC check passes [1](#0-0) .
4. `MembershipHandler.call(params)` runs. It never touches `repository_name`/`stacks` (those are inherited but unused) [4](#0-3) . It resolves the team via `Team.find_or_create_by!(github_id: params.team.id) { |team| ... }` [5](#0-4) . Because `find_or_create_by!` first performs a `find_by(github_id: ...)`, if a `Team` with that `github_id` already exists (belonging to any organization, e.g. a legitimate `shopify/developers` team used for Shipit access control), it is returned unchanged — the block (which would set `team.organization`) only executes on record creation, so no organization check or overwrite occurs.
5. `member = User.find_or_create_by_login!(params.member.login)` creates/fetches a `User` purely from the attacker-supplied login string, with no verification that this GitHub user actually exists or consented.
6. `team.add_member(member)` (action `added`) creates a `Membership` row linking the arbitrary user to the arbitrary pre-existing team [6](#0-5) .

Why existing guards fail: `verify_signature` authenticates *that the sender controls webhook_secret for some org*, not *that the mutated resource belongs to that org* — there is no cross-check anywhere in `MembershipHandler` tying `params.organization.login`/the verified organization to `team.organization`. `ExplicitParameters` only validates types/presence, not authorization scope. `Handler#stacks`/`#repository_name` — the only repository-binding mechanism in the base class — are never invoked by `MembershipHandler`, confirmed by its `process` method.

This directly compromises Shipit's own access-control model: `Authentication#force_github_authentication` gates every UI action on `User#authorized?`, which checks membership in `Shipit.github_teams` [7](#0-6) , and those `Team`/`Membership` rows are exactly what this handler mutates without any org scoping.

### Impact Explanation
An attacker who legitimately owns any GitHub organization with a Shipit-configured `webhook_secret` can inject or remove `Membership` rows for **any** `Team` already present in Shipit's database, including teams listed in `Shipit.github_teams` that gate access to the whole Shipit UI (stacks, deploys, task triggers, API client creation). This is an authorization-boundary violation: a payload authenticated for organization A mutates authorization state belonging to organization B. It matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and can rise to Critical if the targeted team also governs deploy/merge permissions, since gaining membership can unlock deploy/rollback/merge actions gated behind `force_github_authentication`/`User#authorized?`. The attacker only needs to know the numeric `github_id` of the target team (visible via GitHub's team API/UI to anyone with appropriate read access, or guessable/enumerable since it's a small sequential integer), not any Shipit secret. The attack is repeatable against any team whose `github_id` is known and works identically for removing members (`action: 'removed'`), enabling denial of legitimate members' access as well.

### Likelihood Explanation
Preconditions are modest and squarely inside the "unprivileged internet attacker" threat model: the attacker needs (a) a real GitHub organization for which Shipit has a configured `webhook_secret` (trivial — many Shipit deployments allow self-service org onboarding or the attacker is a legitimate customer/org owner in a multi-tenant Shipit install), and (b) the numeric `github_id` of the target team, which is not a secret (returned by GitHub's public team APIs/UI to org members, and small integers are practically enumerable). No Shipit session, API token, or GitHub App private key is required. The exploit is a single crafted HTTP POST, fully reproducible offline.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` **and** the verified organization (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: verified_organization)`), and reject/no-op when an existing team with that `github_id` belongs to a different organization than the one that was cryptographically verified in `WebhooksController#verify_signature`. Pass the verified organization from the controller into the handler explicitly rather than trusting `params.organization.login`, and add an explicit equality assertion (`team.organization == verified_organization`) before performing `add_member`/`delete`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "membership webhook cannot mutate a team belonging to a different organization" do
  privileged_team = shipit_teams(:shopify_developers) # organization == "shopify"
  attacker_org = "evilcorp"

  GithubApp.any_instance.stubs(:webhook_secret).returns("evilcorp-secret")
  Shipit.stubs(:github).with(organization: attacker_org).returns(
    Shipit.github(organization: "shopify") # simulate a real, distinct GithubApp for evilcorp
  )
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature verified for evilcorp

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: {
      id: privileged_team.github_id, # spoofed: target = shopify's privileged team
      name: privileged_team.name,
      slug: privileged_team.slug,
      url: privileged_team.api_url
    },
    organization: { login: attacker_org }, # attacker's genuinely-owned org
    member: { login: 'attacker-controlled-login' }
    # NOTE: no 'repository' key at all
  }.to_json

  assert_difference -> { privileged_team.reload.members.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  refute_equal attacker_org, privileged_team.reload.organization
  assert_includes privileged_team.members.map(&:login), 'attacker-controlled-login'
end
```
Both sides of the claimed binding (`team.organization` vs. the organization that produced a valid signature) diverge after this request: the signature was verified for `evilcorp`, yet the mutated `Team#organization` remains `"shopify"` and gains an attacker-chosen member — proving the vulnerability.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
