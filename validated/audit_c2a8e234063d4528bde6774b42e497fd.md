### Title
`BUNDLE_GEMFILE` (and any other arbitrary env var) from a fork PR's `shipit.yml` `machine.environment` block reaches `PTY.spawn` unfiltered - (File: app/models/shipit/deploy_spec.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`DeploySpec#machine_env` returns the `machine.environment` section of `shipit.yml` verbatim, `TaskCommands#env` merges it directly into the environment hash used for every step of a deploy/rollback/dependencies task, and `Command#unbundled_env` places `@env` (the caller-supplied hash) as the last, highest-precedence layer over the sanitized `BASE_ENV` before calling `PTY.spawn`. Because the fork branch's `shipit.yml` is fully attacker-controlled on a `allow_with_label` review stack, an attacker can set `BUNDLE_GEMFILE` (or `RUBYOPT`, `LD_PRELOAD`, etc.) via `machine.environment` and have it injected into every subsequent bundler-invoking command executed by Shipit on the deploy host.

### Finding Description
The broken binding is: the environment variables handed to `PTY.spawn` during a task on a review stack should equal `Command::BASE_ENV` (Bundler's sanitized/clean environment) merged only with Shipit-controlled keys — never with keys sourced from the fork branch's `shipit.yml`. In practice:

- `DeploySpec#machine_env` at [1](#0-0)  returns `config('machine', 'environment') || {}` with no key allow-list, unlike `deploy_variables`/`filter_deploy_envs` which go through `EnvironmentVariables#permit`.
- `TaskCommands#env` merges this value, unfiltered, into the hash passed to every `Command.new` call for `install_dependencies` and `perform` (and hence `deploy_steps`, `rollback_steps`, `dependencies_steps`): [2](#0-1)  and [3](#0-2) .
- `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — `@env` (which now contains the attacker's `BUNDLE_GEMFILE`) is merged last, so it overrides the sanitized `BASE_ENV`: [4](#0-3) .
- `Command#start` passes this exact hash to `PTY.spawn`: [5](#0-4) .
- `DeploySpec::FileSystem` reads `shipit.yml` from the checked-out review-stack working directory (`app_dir`/branch checkout), i.e., the PR branch content, via `config_file_path`/`load_config`: [6](#0-5) . This file is fully attacker-controlled on the fork branch.

For `allow_with_label` repos, the `LabeledHandler`/`UnlabeledHandler` only gate whether a `ReviewStack` is provisioned/archived based on label presence — they do not sanitize or restrict the content of `shipit.yml` that will later be read from the checked-out branch: [7](#0-6) . No code path filters `machine.environment` keys against a deny-list (e.g., `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`, `PATH`) before it reaches `Command#unbundled_env`.

Exploit flow: an unprivileged GitHub user opens/labels a PR from their fork against a repository with `provisioning_behavior=allow_with_label` and review stacks enabled; their branch's `shipit.yml` includes:
```yaml
machine:
  environment:
    BUNDLE_GEMFILE: /path/to/attacker/Gemfile
```
When Shipit provisions/deploys the review stack, `TaskCommands#env` picks this up via `deploy_spec.machine_env`, and every subsequent step that shells out to `bundle` (e.g. dependency installation via `BundlerDiscovery`, or any deploy/rollback step invoking `bundle exec`) runs with `BUNDLE_GEMFILE` pointed at a file the attacker controls (that file could itself have been checked out as part of the same branch, or reference any path readable/creatable on the host). Ruby/Bundler evaluates the Gemfile as Ruby code, so arbitrary code executes on the Shipit deploy host as the Shipit service user.

Existing guards do not stop this: `filter_deploy_envs`/`filter_rollback_envs` only apply to `deploy.variables`/`rollback.variables`, not to `machine.environment`; there is no permit-list applied to `machine_env` anywhere in `DeploySpec`, `TaskCommands`, or `Command`.

### Impact Explanation
This is Critical — Remote Code Execution on the Shipit deploy host. Bundler evaluating an attacker-supplied `Gemfile` runs arbitrary Ruby code with the privileges of the Shipit worker process, matching the "Command/PTY.spawn RCE" category explicitly listed in scope. The blast radius is bounded to repositories where review stacks are enabled with `allow_with_label` (or similarly to `allow_all`, since the same `machine.environment` merge path applies to any fork-controlled branch config, not just labeled ones), but within such a repository any external contributor able to open a PR can trigger it repeatedly, once per deploy/rollback/dependency-install task executed against their branch.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that lets an unprivileged PR reach the deploy pipeline (`allow_with_label` requires only adding a label the PR author itself often can add, or a maintainer/bot adding it — the question's threat model assumes attacker can get the label applied or exploit `allow_all`). No secrets, tokens, or elevated GitHub permissions are needed — only the ability to open a PR from a fork and control its `shipit.yml`. This is low-cost and fully repeatable against any repository configured this way.

### Recommendation
Apply an explicit allow-list/deny-list to `DeploySpec#machine_env` (mirroring `EnvironmentVariables#permit` used for `deploy_variables`), rejecting or stripping security-sensitive keys such as `BUNDLE_GEMFILE`, `BUNDLE_PATH`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, and any other variable that can redirect interpreter/loader behavior, before it is merged in `TaskCommands#env`. Alternatively, merge `machine_env` before Shipit's own authoritative keys (e.g. `BUNDLE_PATH`) rather than last, and have `Command#unbundled_env` re-assert a small set of protected keys (`BUNDLE_GEMFILE`, `RUBYOPT`, etc.) after merging `@env`, so fork-controlled config can never override them.

### Proof of Concept
minitest plan (no live GitHub, no network):
1. Build a `Shipit::ReviewStack` fixture with `provisioning_behavior: allow_with_label`, checked out from a temp working directory containing a `shipit.yml`:
```yaml
machine:
  environment:
    BUNDLE_GEMFILE: /tmp/attacker_gemfile/Gemfile
```
2. Instantiate `Shipit::DeploySpec::FileSystem.new(working_dir, stack)` and assert:
```ruby
assert_equal({ "BUNDLE_GEMFILE" => "/tmp/attacker_gemfile/Gemfile" }, deploy_spec.machine_env)
```
3. Build `Shipit::TaskCommands.new(task)` for a task on that stack and assert the binding under test:
```ruby
env = task_commands.env
assert_equal "/tmp/attacker_gemfile/Gemfile", env["BUNDLE_GEMFILE"]
```
4. Construct `cmd = Shipit::Command.new("bundle", "exec", "true", env: env, chdir: dir)` and assert the value actually reaching `PTY.spawn`:
```ruby
spawned_env = cmd.unbundled_env
assert_equal "/tmp/attacker_gemfile/Gemfile", spawned_env["BUNDLE_GEMFILE"]
refute_equal Shipit::Command::BASE_ENV["BUNDLE_GEMFILE"], spawned_env["BUNDLE_GEMFILE"]
```
The equality in step 4 (`spawned_env["BUNDLE_GEMFILE"] == attacker value`, diverging from `BASE_ENV["BUNDLE_GEMFILE"]`, which is `nil`/unset per Bundler's clean env) demonstrates the fork-controlled key overriding the sanitized environment that reaches `PTY.spawn`, confirming the vulnerability with no live GitHub interaction required.
