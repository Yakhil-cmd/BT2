## Title
`Shipit::Webhooks::Handlers::StatusHandler#process` writes a forged commit status onto any organization's commit sharing the attacker's SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`WebhooksController#verify_signature` correctly authenticates a `status` webhook against the GitHub App configuration for the organization named in the payload's `repository.owner.login`. However, `StatusHandler#process` then looks up commits by `Commit.where(sha: params.sha)` with no scoping to that organization/repository, and calls `commit.create_status_from_github!(params)` on every matching row. If the same SHA exists under a different stack owned by a different organization (shared base commit, cherry-pick, or identical merge commit), that unrelated commit receives a fabricated status too.

## Finding Description
The binding that should hold is: `repository_owner_of_authenticated_webhook == owner_of_stack_for_every_Commit_row_matched_by(params.sha)`. This is never enforced.

- `WebhooksController#verify_signature` derives `repository_owner` from the payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and verifies the signature using `Shipit.github(organization: repository_owner)`, i.e. that organization's own `webhook_secret` [1](#0-0) [2](#0-1) . This step only proves the payload was signed by organization A's secret; it says nothing about which `Commit` rows exist for sha `X`.
- `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a completely global lookup across every stack/repository in the database, with no `stack_id`, `repository_id`, or owner filter [3](#0-2) .
- `Commit#create_status_from_github!` unconditionally creates a `Status` row tied to `stack_id` and fires `Hook.emit(:commit_status, ...)`/`:deployable_status` and can enqueue `ProcessMergeRequestsJob`, potentially unblocking a deploy on the affected stack [4](#0-3) [5](#0-4) .

Attacker flow: attacker controls organization A and has a legitimately configured `webhook_secret` for A (per `Shipit.github_app_config`, multi-org configs each carry their own `webhook_secret`) [6](#0-5) . They discover (or engineer, e.g. via a cherry-pick/rebase/merge producing an identical tree+parents+timestamps SHA, or simply by referencing a well-known shared base commit SHA that both A's and victim org B's repos have ingested) a SHA that also exists as a `Commit` row under a stack owned by B. The attacker POSTs `/webhooks` with `X-Github-Event: status`, `repository.owner.login` set to A, correctly HMAC-signed with A's secret, and `sha` set to the shared value. `verify_signature` passes because it only checks A's secret against A's payload. `StatusHandler#process` then matches and mutates **every** `Commit` row with that sha — including B's — writing a fabricated `state`/`description`/`target_url`/`context` status onto B's commit, potentially flipping B's commit to `success` and triggering `ProcessMergeRequestsJob`/continuous delivery on B's stack.

No existing guard closes this gap: `verify_signature` authenticates the sender's organization, not the target commit's owner; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler.params` only validates field types/presence, not ownership; there is no `Repository`/`Stack` scoping anywhere in the query.

## Impact Explanation
A payload authenticated for organization/repository A causes a database write (a `Status` record, plus associated hook emissions and possible job scheduling) against a `Commit`/`Stack` belonging to organization B — a payload for one repository mutating another's commit/stack, matching the Critical impact category explicitly listed. Blast radius spans every tenant on a shared Shipit instance whose commit history can collide on a SHA with an attacker-controlled repo (base commits, cherry-picks, identical merges are common in monorepo/mirrored-repo setups). The attack is fully repeatable: each additional signed `status` POST with the colliding SHA appends another forged status.

## Likelihood Explanation
Preconditions: attacker needs a valid, self-controlled organization/repo integrated with the same Shipit instance (i.e., their own low-security org with a configured `webhook_secret`) and knowledge of a SHA that both their commit history and the victim's contain. No privileged Shipit role, session, or victim secret is required. SHA collision across independent orgs is not guaranteed for arbitrary content, but is realistic in common scenarios (shared upstream/base commits, forked/mirrored repos, identical merge commits from bots) — and the attacker can actively try to create such collisions on their own side without touching the victim's repo. Cost is a single signed HTTP POST.

## Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository/organization that authenticated the webhook: join through `Stack`/`Repository` and filter `Commit.where(sha: params.sha)` by the `repository_owner`/repository `full_name` derived from the payload (the same value used in `verify_signature`), so only commits belonging to stacks of the authenticated repository can receive the status. Apply the same scoping pattern to other handlers that perform sha-only lookups if any exist.

## Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`:
1. Create two stacks belonging to two different repositories/organizations (`stack_a` under org "attacker-org", `stack_b` under org "victim-org"), each with a `GithubHook`/webhook secret configured for its own organization.
2. Create a `Commit` with an identical `sha` value ("deadbeef...") under both `stack_a` and `stack_b`.
3. Build a `status` event payload naming `repository.owner.login = "attacker-org"` and `sha = "deadbeef..."`, sign it with attacker-org's `webhook_secret` via `Hook::DeliverySigner`/HMAC as `verify_signature` expects.
4. POST to `/webhooks` with `X-Github-Event: status` and the correct `X-Hub-Signature`.
5. Assert response is `:ok` (signature verified for attacker-org).
6. Assert both `stack_a`'s commit **and** `stack_b`'s commit (`commit_b.reload.statuses.last`) now have the forged status — i.e., `commit_b.statuses.count` increased and `commit_b.statuses.last.state == payload_state`, proving the binding "authenticated organization == owner of every matched Commit" is violated (`stack_b`'s owning organization, "victim-org", never signed anything, yet its commit was mutated).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
