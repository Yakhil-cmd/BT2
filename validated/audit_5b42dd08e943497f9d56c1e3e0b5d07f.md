### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the organization named in the payload (`repository.owner.login`), using that organization's own configured `webhook_secret`. [1](#0-0)  That verification only proves the request was signed by *some* organization's GitHub App installation — it says nothing about which repository's commits the payload is entitled to mutate. `StatusHandler`, unlike every other handler, never re-establishes that binding: it looks up commits globally by SHA instead of scoping through the repository named in the payload. [2](#0-1) 

### Finding Description
The base `Handler` class exposes a `stacks` helper that scopes any lookup to the repository named in the webhook payload (`payload.dig('repository', 'full_name')`), and handlers like `PushHandler` correctly use it before touching any records. [3](#0-2) [4](#0-3) 

`StatusHandler`, however, resolves the target commit purely by SHA across the entire `commits` table, with no repository/organization scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The equality that `verify_signature` is meant to guarantee is:
`verified_organization(payload) == organization_owning(record_written_to)`

For `StatusHandler` this equality is broken. `verify_signature` proves only that the payload was signed with organization `O`'s webhook secret (obtained via `Shipit.github(organization: repository_owner)`), [5](#0-4)  but the `sha` field used by `StatusHandler` to select which `Commit` (and therefore which `Stack`/repository) to mutate is never checked against `O`. Any organization/repository that has the Shipit GitHub App installed can legitimately produce a validly-signed `status` webhook, then set `sha` to a commit SHA belonging to a completely unrelated victim stack. Because `Commit.where(sha:)` is unscoped, the forged status gets attached to the victim's commit via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses drive Shipit's CI-gating logic (`ci.require`, `merge_queue`, "deployable?" checks used by `build_deploy`/merge queue automation). An attacker who controls any single GitHub organization/repository onboarded to the same Shipit instance can forge a successful CI status (or any required check context) onto a commit belonging to a different repository/stack they have no access to, potentially unblocking an unauthorized deploy or merge for that victim stack. This is a cross-repository write and falls under the "Critical – cross-repository writes / unauthorized deploy, rollback or merge" impact category.

### Likelihood Explanation
The attacker only needs to control one organization/repo already integrated with the shared Shipit instance (a realistic multi-tenant deployment scenario, since `Shipit.github(organization:)` supports per-organization webhook secrets). Target commit SHAs are not secret — they are visible on GitHub (commits, PRs, pushes) — so crafting the payload requires no privileged access to the victim repository. No Shipit session, API token, or GitHub App private key is needed; the only requirement is the ability to produce (or replay) a webhook with a valid signature for the attacker's *own* organization.

### Recommendation
In `StatusHandler#process`, scope the commit lookup the same way `PushHandler` and other handlers do: resolve `stacks` from `repository_name` in the payload first, and restrict `Commit.where(sha:)` to commits belonging to those stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join), so a status can only ever be attached to a commit that belongs to the repository whose organization/secret actually signed the webhook.

### Proof of Concept
1. Attacker owns `org-attacker/repo-attacker`, which has the Shipit GitHub App installed (webhook secret `S_attacker` configured for `org-attacker`).
2. Attacker observes a public commit SHA `deadbeef...` belonging to victim stack `org-victim/repo-victim`, which requires a `ci/tests` status to be `success` before merge-queue/deploy proceeds.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "org-attacker" } }
}
```
4. Attacker signs it with `S_attacker` (their own legitimately-configured secret) and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` succeeds because it only checks the signature against `org-attacker`'s secret. [1](#0-0) 
6. `StatusHandler#process` finds the victim's `Commit` by SHA (no repository scoping) and marks it `success` for `ci/tests`, satisfying the victim stack's deploy/merge-gating checks. [2](#0-1)
