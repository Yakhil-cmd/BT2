## Title
Webhook signature authenticates the payload's declared organization but not the repository actually acted upon, enabling cross-repository writes — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

## Summary
This is a valid analog of the reported bug class ("a value is trusted based on a check that does not cover the exact value later used"). In the external report, `checkSuccess()` validates `returndata` but nothing enforces it is evaluated against the specific call it is meant to validate. In shipit-engine, the webhook signature check validates an HMAC over the raw request body using a secret selected by one field of that body (`repository.owner.login`), while the handlers that actually mutate state select the target `Repository`/`Stack` using a *different* field of the same body (`repository.full_name`). Nothing binds these two values together, so a validly-signed webhook for organization A can name a repository owned by organization B.

## Finding Description
`WebhooksController#verify_signature` picks which org's webhook secret to validate against using: [1](#0-0) 
It then verifies the HMAC over the raw JSON body with that org's secret via `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Once verified, the parsed body is dispatched to handlers unmodified: [3](#0-2) 

Every handler resolves the target repository/stack from a *different* field of the same JSON object — `repository.full_name` — not the field used for signature-secret selection: [4](#0-3) 

For example `PushHandler` uses this to load stacks and trigger a sync with an attacker-chosen commit SHA (`params.after`): [5](#0-4) 

Because Shipit supports a multi-organization configuration (`Shipit.github(organization:)`, keyed per-org secrets as shown in `config/secrets.development.example.yml`), an entity that legitimately administers a GitHub App/organization already onboarded to this Shipit instance knows that organization's `webhook_secret`. They can therefore POST a self-crafted JSON body where:
- `repository.owner.login` = their own organization (so `verify_signature` fetches their own known secret and the HMAC validates), while
- `repository.full_name` = a victim organization's repository (so `Handler#repository_name`/`#stacks` resolves to a different org's `Stack`).

The equality that should hold — `org authenticated by signature == org whose repository is written` — is broken: verification is keyed off `repository.owner.login`, but mutation is keyed off `repository.full_name`, and nothing cross-checks that the two agree.

## Impact Explanation
This allows a validly-authenticated party for organization A to forge `push`/`status`/`check_suite` events that are dispatched against organization B's stacks — an unauthorized cross-organization/cross-repository action performed through a signature that was never scoped to that repository. Concretely, `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on a victim's non-archived stacks matching the spoofed branch, using an attacker-supplied SHA, and `StatusHandler` will write fabricated commit statuses for arbitrary shas. This is a cross-repository write/unauthorized action carried out under the guise of another organization's trust boundary, satisfying the "cross-repository writes" impact tier.

## Likelihood Explanation
Exploitation requires the attacker to be a legitimate administrator of *some* org already configured in this Shipit instance's multi-org `github:` secrets map (`config/secrets.*.yml`), i.e., they possess a real webhook secret for their own org — no GitHub private key, `api_clients_secret`, or Shipit session is needed. In any multi-tenant Shipit deployment (the config format explicitly supports several orgs), this is a realistic, unprivileged-relative-to-other-tenants attack path, since the endpoint is public and only body-HMAC + org lookup gate it.

## Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, cross-validate that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the organization prefix of `repository.full_name` before dispatching to handlers, rejecting (422) any payload where these disagree.

## Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is configured in Shipit's `github:` secrets map with `webhook_secret: S`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `S` and sets `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `S`, and the HMAC validates successfully.
5. `PushHandler#process` resolves `repository_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `victim-org`'s stacks — an action the attacker was never authorized to trigger for that organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
