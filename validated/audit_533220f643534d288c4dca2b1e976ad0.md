### Title
Unauthenticated, unconfirmed AA definitions poison the shared `definitions` cache and get permanently persisted by light clients - ([File: network.js])

### Summary
The IBM Langflow CVE describes a shared, ownership-unaware cache that any authenticated but unprivileged caller can pollute, causing other users/flows to consume attacker-influenced cached data. The closest reachable analog in ocore is the `light/get_definition` request handler in `network.js`, which serves and caches **unconfirmed** AA definitions (definitions attached to units that are not yet stable/final) in a process-wide, unkeyed-by-finality cache, and which light clients (`aa_addresses.js`) then persist directly into their local `aa_addresses` table as if the definition were confirmed at genesis.

### Finding Description
`network.js` keeps a module-level cache: [1](#0-0) 

The `light/get_definition` handler answers by first checking this cache, and if not present, falls back to `storage.getUnconfirmedAADefinition(params)` — i.e. a definition that came from a unit that has not yet stabilized (posted by any unprivileged unit poster) — and then unconditionally stores whatever is returned into the shared cache with no expiry, no finality check, and no invalidation hook if the underlying unit is later voided/final-bad: [2](#0-1) 

Because the cache is keyed only by address and is process-global (shared across all connected light-client requesters), a single unprivileged AA-definition poster can cause the serving node to cache an as-yet-unconfirmed definition for that address. Every subsequent `light/get_definition` request for the same address — from any other, unrelated light wallet — is answered straight from this cache, without re-checking whether the originating unit ever became stable/good or turned out to be `final-bad`/non-serial.

Downstream, light wallets that consume this response do not treat it as provisional: `aa_addresses.js`'s `readAADefinitions()` takes the response, verifies only that its content-hash matches the requested address, and then inserts it directly into the local `aa_addresses` table as if it were confirmed at the genesis unit: [3](#0-2) 

This is the same bug class as the CVE: a shared cache is written and served using untrusted, not-yet-final data supplied by an unprivileged party, and downstream consumers (other users' "flows") treat the cached value as authoritative without validating its provenance/finality.

### Impact Explanation
Once a light wallet installs an unconfirmed AA definition as if it were permanently defined (`unit=GENESIS_UNIT, mci=0`), all later logic that depends on `aa_addresses` — bounce-fee checks in `checkAAOutputs()` (`aa_addresses.js`), formula `definition[addr]` lookups, and payment composition — will act on a definition whose backing unit may still fork, be voided, or never stabilize. This can cause a light wallet to:
- Compose and send a payment to what it believes is a specific AA (with specific bounce_fees/behavior) that either never comes into existence or ends up with a different final definition, resulting in funds sent to an address that does not behave as expected (fund loss/freezing analogous to the "AA fund loss or freezing" impact class).
- Persist a poisoned, unauthenticated cache entry (`definitions{}`) on the serving node that affects every other light client's view of that address, i.e., cross-user cache pollution driving disagreement between what the light client believes about an address and what the network eventually finalizes.

### Likelihood Explanation
Reaching this path only requires posting a normal AA-definition unit (any unprivileged unit poster can do this) and having any light client query `light/get_definition`/`readAADefinitions` for that address before the unit stabilizes — a routine occurrence, since light wallets frequently resolve AA definitions before composing payments. No hub/node malice is required; the vulnerable behavior is in the standard full-node response logic and the standard light-client caching logic.

### Recommendation
- Do not cache or persist AA/address definitions sourced from `storage.getUnconfirmedAADefinition` (or any unstable unit) as confirmed. Track a separate provisional cache with short TTL and explicit invalidation when the backing unit is voided/final-bad.
- In `aa_addresses.js`, do not write light-vendor-supplied definitions into `aa_addresses` with a fabricated `unit=GENESIS_UNIT, mci=0`; instead record the real source unit/mci and its confirmation status, and re-validate/evict when that status changes.
- In `network.js`'s `light/get_definition`, avoid populating the long-lived `definitions{}` cache with unconfirmed content, or tag cache entries with the confirmation state so stale/invalid entries are not served indefinitely.

### Proof of Concept
1. Attacker (unprivileged) posts a valid-looking AA-definition unit for a fresh address `A`, but arranges for it to eventually become non-serial/`final-bad` (e.g., via a conflicting parallel unit or address reuse pattern that the network resolves against it).
2. Before finalization, a victim light wallet calls `light/get_definition` for address `A` against a normal, honest full node.
3. The full node answers using `storage.getUnconfirmedAADefinition(A)` (network.js:3832-3838) and caches the result in `definitions[A]` with no finality marker.
4. Victim's `aa_addresses.js` `readAADefinitions()` inserts this into its local `aa_addresses` table as confirmed at genesis (aa_addresses.js:97-105).
5. The attacker's original unit is later rejected/voided by the network, but the victim's wallet, and the full node's cache for any other querying client, continue to treat `A` as a legitimately defined AA with the attacker-chosen `bounce_fees`/behavior indefinitely.

Note: I was not able to fully inspect the implementation body of `storage.getUnconfirmedAADefinition` (only its references) or definitively confirm whether any invalidation-on-final-bad hook exists elsewhere in the codebase that clears the `definitions{}` cache; this is a limitation of the available index and would benefit from a full-repository review (e.g., via a Devin session) to confirm there is no compensating invalidation path.
