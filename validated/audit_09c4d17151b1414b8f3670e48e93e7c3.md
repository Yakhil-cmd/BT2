## Title
StatusHandler#process mutates Commit rows for any SHA without repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
Every other webhook handler that mutates data scopes its query through `Handler#stacks` (which resolves `Repository.from_github_repo_name(repository_name)`), but `StatusHandler#process` queries `Commit.where(sha: params.sha)` directly, with no repository/stack scoping whatsoever. Any "status" webhook that authenticates for one repository (verified only at the organization level) can create a commit status on a `Commit` row belonging to any other stack/repository whose commit happens to share that SHA.

## Finding Description
The broken binding, stated as an equality that other handlers enforce but `StatusHandler` does not:
`repository_name (payload.dig('repository','full_name')) == stack.repository.full_name for every Commit row mutated by process`

`Handler#stacks`/`repository_name` establish this binding generically: [1](#0-0) 

`PushHandler#process` and `CheckSuiteHandler#process` both go through `stacks`, so any DB mutation is confined to stacks belonging to the repository named in the verified payload: [2](#0-1) [3](#0-2) 

`StatusHandler#process`, however, never calls `stacks` or `repository_name` at all; it queries the global `Commit` table by `sha` only: [4](#0-3) 

`Commit.where(sha:)` is a bare, unscoped table query, and `create_status_from_github!` writes a new `Status` row and fires hooks (`commit_status`, `deployable_status`) that can trigger merges/deploys via `stack.schedule_merges`: [5](#0-4) [6](#0-5) 

**Root cause / call path:** `WebhooksController#create` verifies the signature only at the organization level (`Shipit.github(organization: repository_owner)`), then dispatches the raw parsed JSON to every registered handler for the event with no further repository check: [7](#0-6) 

Because commit SHA-1 hashes are computed purely from commit content (tree, parents, author/committer, message, timestamps) and not from the repository they live in, identical commits (e.g., shared history from a fork, cherry-pick, or subtree) legitimately produce identical SHAs across repositories. Any repository within the same Shipit-configured GitHub organization (sharing one `webhook_secret`) can trigger GitHub's real Status API against a SHA that also exists as a `Commit` row belonging to a completely different stack/repository tracked by the same Shipit instance. `StatusHandler` will happily match and mutate that unrelated commit's status, because it never checks that the commit's `stack.repository.full_name` equals the payload's `repository.full_name`.

None of the existing guards prevent this: `verify_signature` only binds the payload to an organization, not to the specific repository referenced in it; the `ExplicitParameters` schema for `StatusHandler` doesn't even require a `repository` key; there's no model validation on `Commit` tying `sha` uniqueness to a stack in a way this handler respects.

## Impact Explanation
An attacker who controls (or has commit/status-posting rights on) any repository sharing the same Shipit-configured GitHub App/organization as a target stack can forge a commit status ("success", "failure", etc.) for a `Commit` belonging to an entirely unrelated stack, as long as a SHA collision (shared commit) exists. Since `add_status` fires `deployable_status`/`commit_status` hooks and calls `stack.schedule_merges` on success/pending transitions, this can trigger unauthorized merges or continuous deployments on a stack the attacker does not control - matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy... or merge." This is repeatable for every commit that is shared/duplicated across repositories in scope.

## Likelihood Explanation
Requires only: (1) the attacker's repository and the victim stack's repository share the same Shipit-configured GitHub organization/App installation (thus the same `webhook_secret` validated by `verify_signature`), and (2) a commit with an identical SHA exists in both repositories (trivially achievable via forking/sharing git history, cherry-picks, or subtree merges - no cryptographic SHA-1 collision needed). No Shipit credentials, sessions, or API tokens are needed; only the ability to emit a legitimate "status" webhook from a repository within the shared org, satisfying the stated precondition.

## Recommendation
Scope `StatusHandler#process` through `stacks`/`repository_name` like `PushHandler` and `CheckSuiteHandler`, e.g. restrict the query to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack: stacks)`, so a commit is only updated if it belongs to a stack under the repository named in the verified payload.

## Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
```ruby
test "process does not mutate commits belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "repository" => { "full_name" => "attacker-org/attacker-repo" }
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)
  handler.expects(:stacks).never

  assert_no_difference -> { victim_commit.statuses.count } do
    handler.process
  end
end
```
Assert on both sides of the binding: `payload.dig('repository','full_name') == "attacker-org/attacker-repo"` while `victim_commit.stack.repository.full_name == "shopify/shipit-engine"` - they differ, yet `Commit.where(sha:)` still finds and mutates `victim_commit`, proving the missing binding (the test above will currently fail on `assert_no_difference`, confirming the vulnerability).

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
