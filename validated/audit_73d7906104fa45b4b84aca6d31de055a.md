### Title
Cross-stack status contamination via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up every `Commit` row matching the incoming `sha` with no repository, branch, or stack filter, even though the handler's own parameter schema accepts `branches`. Because `Commit` records are per-`Stack` (each row has its own `stack_id`), the same SHA can legitimately exist as separate `Commit` rows in two different `Stack`s of the same `Repository` (e.g. `master` and `release` sharing history), and a single incoming status webhook writes a `Status` to *all* of them.

### Finding Description
The broken binding is: `commit.stack.branch` (and, more generally, `commit.stack_id`) implied by `params.branches[*].name` must equal the branch/stack the status is intended for — but the handler never enforces `commit.stack.branch == params.branches.map(&:name)` or any repository check.

Code path:
- `app/models/shipit/webhooks/handlers/status_handler.rb:15-24` declares `accepts :branches, Array do requires :name, String end` but `process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is unscoped even by `repository_name`, unlike the sibling `CheckSuiteHandler`, which correctly scopes via `stacks.where(branch: ...)` before touching commits: [2](#0-1) 

`Handler#stacks` shows the intended scoping helper (`Repository.from_github_repo_name(repository_name)&.stacks`) exists in the base class but `StatusHandler` doesn't use it at all: [3](#0-2) 

`create_status_from_github!` writes the status using the found commit's own `stack_id`, so once a wrong commit is matched, a real `Status` row is persisted for the wrong stack: [4](#0-3) 
`add_status` then fires `stack.schedule_merges` and hooks based on the new state: [5](#0-4) 

Existing guards do not close this gap: `verify_signature`/`drop_unhandled_event` in `WebhooksController` only validate that the webhook is genuinely from GitHub for the named `repository_owner`/organization — they say nothing about which `Stack`/branch inside that repository the status applies to. [6](#0-5) 
The `ExplicitParameters` schema accepts `branches` but the field is dead — never read in `process` — so it provides no actual disambiguation despite appearing to.

Attack flow: a `Repository` is tracked by two `Stack`s (`master` and `release`). Both stacks import overlapping commit history (a completely normal git situation — commits before the branch point, or any commit cherry-picked/present on both branches, are stored as separate `Commit` rows with the same `sha` but different `stack_id`). Any legitimate CI/status event GitHub emits for that repository — triggerable by any contributor able to push a branch or open a PR that runs CI against a shared-ancestor commit — arrives as a validly-signed `status` webhook naming only one branch in `branches`. `StatusHandler#process` ignores that field and updates the status of the matching commit in *both* stacks, potentially flipping the untouched stack's commit to `success`/`pending` and triggering `stack.schedule_merges` / continuous deployment on a stack the status was never intended for.

### Impact Explanation
A status event intended for one branch/stack of a repository can mark a commit as `success` in a sibling stack of the same `Repository`, which can trigger `schedule_merges` and continuous delivery/deploy flows on that other stack — i.e. "a payload for one [branch/stack] mutating another['s] stack, commit, task" and potentially causing an unauthorized deploy, matching the Critical severity bar. The blast radius is bounded to stacks sharing the same underlying `Repository`'s commit history (multiple branches/environments of one repo); it does not, by itself, extend to a *different* tenant's unrelated repository, since `Commit.where(sha:)` will only realistically collide across rows that share genuine git history (true cross-repository SHA collisions are computationally infeasible and out of scope).

### Likelihood Explanation
Preconditions are realistic and require no secrets: the target `Repository` must have at least two `Stack`s (common for multi-branch/multi-environment setups), and their commit histories must overlap (normal for branches sharing ancestors or long-lived release branches). The attacker only needs the ability to cause GitHub to emit a genuinely-signed `status` event for a shared commit — achievable via ordinary CI activity on a PR/branch, which is within the stated attacker capabilities. No forged signature, token, or privileged role is needed.

### Recommendation
Scope `StatusHandler#process` by repository and by the declared `branches` parameter, mirroring `CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)`, restrict to stacks whose `branch` is included in `params.branches.map(&:name)` (or, if `branches` is absent, at least restrict to `stacks.commits.where(sha:)` scoped to the repository), and only then call `create_status_from_github!` on the resulting commits.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "a status for one branch does not update commits belonging to a sibling stack" do
          repository = shipit_repositories(:shipit)
          stack_master = shipit_stacks(:shipit)          # branch: master
          stack_release = Stack.create!(repository:, environment: 'release-env', branch: 'release')

          shared_sha = 'deadbeef' * 5
          commit_master = stack_master.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
          commit_release = stack_release.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'branches' => [{ 'name' => 'release' }], # attacker only names 'release'
          }

          assert_difference -> { commit_master.reload.statuses.count }, 0, "master stack's commit must NOT be touched" do
            Shipit::Webhooks::Handlers::StatusHandler.call(payload)
          end
          # Demonstrates current (buggy) behavior: both get updated
          assert_equal 'success', commit_master.reload.state
          assert_equal 'success', commit_release.reload.state
        end
      end
    end
  end
end
```
The first assertion (`assert_difference ... 0`) is expected to FAIL against the current code, proving the binding `commit.stack.branch == params.branches.map(&:name)` is violated: `commit_master`, belonging to the `master` stack, still receives the status even though only `release` was named.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
