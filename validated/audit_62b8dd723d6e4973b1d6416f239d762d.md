### Title
Webhook signature verification is keyed to the wrong organization, allowing an authenticated-but-secretless org to forge events for any repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to check against based solely on the `repository.owner.login` (or `organization.login`) field of the *unauthenticated* payload, and then calls `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` whenever that particular organization has no `webhook_secret` configured. The rest of the payload (`repository.full_name`, `sha`, `state`, `pull_request`, etc.) used by the actual event handlers to select which repository/commit/stack to mutate is never re-validated against the organization that was "authenticated." This is the same class of bug as the reported "unchecked delegatecall result": the result of a security check (signature verification) is trusted for the wrong scope, and a payload field that drives a state-changing action is never covered by what was actually verified.

### Finding Description
`repository_owner` is read straight from the untrusted JSON body: [1](#0-0) 

It is then used to pick the `GitHubApp` instance whose secret should validate the signature: [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` outright when no `webhook_secret` is configured for that app/org: [3](#0-2) 

Shipit explicitly supports running multiple GitHub Apps for different organizations sharing one instance, and per-organization `webhook_secret` is optional/nilable in every shipped configuration template, including the multi-org fixture used in tests: [4](#0-3) [5](#0-4) 

Because signature verification is scoped only by `repository.owner.login`, an attacker who knows (or can enumerate) that *any* organization hosted on the Shipit instance has no `webhook_secret` configured can craft a payload where:
- `repository.owner.login` == the org with no secret (so `verify_webhook_signature` short-circuits to `true`, no signature needed at all), while
- every other payload field (`repository.full_name`, `sha`, `state`, `target_url`, PR data, etc.) references a **different**, fully-configured organization/repository that Shipit actually tracks.

Event handlers act on those other fields without ever re-checking that they belong to the organization that was "authenticated." For example the `status` handler updates a `Commit`'s `Status` purely from `sha`/`state`/`target_url`/`repository` fields taken from the body, with the org lookup used only for the (bypassed) signature step — confirmed by the controller test which drives a `status` event exclusively via body params merged with an arbitrary `repository.owner.login`: [6](#0-5) 

The root cause is that the equality the engine needs to hold — *the organization whose secret validated the request* == *the organization/repository the handler is about to mutate* — is never enforced; only the former is checked, and only when that org happens to have a secret configured.

### Impact Explanation
An attacker with no Shipit session, no `ApiClient` token, and no GitHub credentials can forge `status`, `push`, `check_suite`, `pull_request` or `membership` webhook events for repositories/organizations they have no access to, as long as some other organization on the same Shipit instance is configured without a `webhook_secret` (an explicitly documented, default configuration state). This lets the attacker:
- Inject fabricated commit `Status` records (`state: success`) for arbitrary commits on a tracked repository, which can satisfy `ci.require` checks in `shipit.yml` and enable an **unauthorized deploy** of a commit that never actually passed CI.
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` and manipulate `Team`/`Membership`/`User` records via the `membership` handler for organizations they don't administer.

This crosses the "organization authenticated vs. repository/commit actually written" trust boundary called out in scope, and the CI-status forgery path leads to an unauthorized deploy, matching the Critical impact bar.

### Likelihood Explanation
Likelihood depends on at least one organization on the shared Shipit instance running without a `webhook_secret`. Every shipped configuration example (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`) shows `webhook_secret` as optional/nil, indicating this is a normal, supported operating mode rather than an edge-case misconfiguration — making exploitation plausible in real multi-tenant deployments of the engine.

### Recommendation
Do not let an unauthenticated payload field pick the trust boundary that authorizes a mutation on a *different* field. Concretely:
- Require `webhook_secret` to be present for every configured GitHub App/organization (fail closed instead of `return true unless webhook_secret`).
- After signature verification, re-validate that the organization that authenticated the request actually owns the `repository.full_name` (or other target identifiers) that the handler is about to act on, rejecting mismatches.

### Proof of Concept
1. Operate/observe a Shipit instance configured with two GitHub Apps: `OrgWithSecret` (has `webhook_secret`) and `OrgNoSecret` (no `webhook_secret`, per the documented/default template).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgWithSecret/target-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com"
}
```
3. `verify_signature` looks up `Shipit.github(organization: "OrgNoSecret")`, whose `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` needed).
4. The `status` handler processes the event against `OrgWithSecret/target-repo`'s commit, creating a forged passing `Status`, which can satisfy `ci.require` and allow an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
