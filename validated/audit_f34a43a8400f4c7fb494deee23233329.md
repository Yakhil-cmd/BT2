### Title
CCMenu API token stack-scoping bypass allows reading any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by `BaseController` in a way that discards the stack-scoping enforced for every other API endpoint, allowing a token that was only meant to authorize access to one stack to read CI/build data for any stack.

### Finding Description
`Shipit::Api::BaseController` defines the trust boundary between an `ApiClient` token and the stacks it is allowed to touch: [1](#0-0) 
`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` only through that restricted relation, so a stack-scoped token can never resolve a `stack_id` param other than its own.

`CCMenuController`, however, redefines `stack` to bypass this relation entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the global `Stack` collection instead of going through `stacks`/`current_api_client.stack_id`. The `require_permission :read, :stack` check only validates that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, which is scope-agnostic and does not verify which stack the permission applies to: [3](#0-2) 

The scoped-token flow this breaks is exactly the one used by the built-in "CCMenu URL" feature: `CCMenuUrlController` mints an `ApiClient` bound to a single stack (`permissions: %w[read:stack]`, `stack: <that stack>` implicitly via the client's `stack_id`) intended to only ever authorize CCMenu reads of that one stack: [4](#0-3) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, that token can be replayed against `GET /api/:other_stack_id/cc.xml?token=...` (or via Basic auth) for any other stack in the installation, and the controller will render that other stack's CCMenu status.

### Impact Explanation
This breaks the "a stack a token authorizes versus a stack it touches" binding: a legitimately-issued, narrowly-scoped token (bound to `stack_id: A`) can be used to read build/deploy status (name, last build status/label/time, activity, lock state) of stack `B`, which the token holder was never granted access to. This is an authorization bypass yielding unauthenticated (relative to stack `B`) read of stack state, matching the High-impact category "escalation ... or unauthenticated read of stack state."

### Likelihood Explanation
Any holder of a stack-scoped CCMenu token (which is handed out to any user with read access to one stack, including via the self-service `CCMenuUrlController#fetch` endpoint) can trivially exploit this by substituting a different `stack_id` in the URL. No special privileges beyond having one legitimate, narrowly-scoped token are required.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve through the same scoped `stacks` relation used by `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so tokens bound to `current_api_client.stack_id` cannot resolve any other stack.

### Proof of Concept
1. As a user with read access only to stack `A`, visit stack `A` and trigger `GET /:stack_A/ccmenu_url` (`CCMenuUrlController#fetch`), obtaining a token scoped to stack `A` (`ApiClient` with `stack_id = A.id`, `permissions: ['read:stack']`).
2. Send `GET /api/:stack_B/cc.xml?token=<token>` for an arbitrary other stack `B` that the same user has no access to.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `CCMenuController#stack` resolves `stack_B` via `Stack.from_param!` (unscoped), and `require_permission :read, :stack` passes because the token simply carries `read:stack`.
4. The response renders stack `B`'s CCMenu XML (name, last build status/label/time), disclosing its state despite the token being minted only for stack `A`.
