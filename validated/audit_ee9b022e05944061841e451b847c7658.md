## Analog Found: Uncaught Length-Mismatch Exception in `chash.isChashValid()` — Remote DoS via any Attacker-Supplied Address String

### Title
Unhandled exception (crash / DoS) from base32/base64 decode-length mismatch in `isChashValid()` - (File: `chash.js`)

### Summary
`chash.isChashValid()` decodes an attacker-controlled 32- or 48-character string and then assumes, without validation, that the decoded byte buffer has *exactly* 160 or 288 bits. If the decoder returns a buffer of unexpected length (a class of bug directly analogous to the Liblouis CVE-2017-13743 buffer/length mismatch that crashed `_lou_showString()`), the length-mismatch is only guarded by a `throw`, not a graceful `return false`, and that `throw` sits **outside** the function's own `try/catch` block. `isChashValid()` backs `isValidChash()`/`isValidAddress()`, which are invoked throughout unit, AA, and device validation on attacker-supplied strings, giving an unprivileged unit poster a path to crash the validating node process.

### Finding Description
`isChashValid()` decodes the address-like string and only wraps the *decode* call in `try/catch`: [1](#0-0) 

The decoded buffer is then fed to `buffer2bin()` and `separateIntoCleanDataAndChecksum()`, which strictly require the bit-length to be exactly 160 or 288, and `throw Error(...)` otherwise — with no surrounding `try/catch`: [2](#0-1) 

The 32/48 character-length precondition is enforced by the caller before entering `isChashValid`: [3](#0-2) 

However, a fixed *string* length does not guarantee a fixed *decoded byte* length: the `thirty-two` base32 decoder (used for the 32-character/160-bit case) and Node's lenient `Buffer.from(str, 'base64')` (used for the 48-character/288-bit case) can both silently produce a decoded buffer shorter or longer than expected when the input contains characters outside the strict base32/base64 alphabet or malformed padding, rather than throwing. That mismatched buffer then reaches `buffer2bin()` → `separateIntoCleanDataAndChecksum()`, whose `len !== 160/288` branch throws an **uncaught** `Error`, because that check is outside the `try{}` in `isChashValid`.

`isValidAddress`/`isValidChash` is the standard address-validity check reachable from many attacker-controlled surfaces: unit outputs/authors during unit validation, AA trigger/definition addresses evaluated via oscript's `is_valid_address`/`is_aa`, and private-payment/device-pairing address fields, e.g.: [4](#0-3) [5](#0-4) 

Any of these validation call sites that do not themselves wrap the `isValidAddress` call in a `try/catch` will propagate the uncaught exception up the stack, crashing the Node process (unhandled exception → process exit), i.e. a remote denial of service triggerable by posting a single malformed unit/trigger/message containing a crafted 32- or 48-character pseudo-address string.

### Impact Explanation
An uncaught exception thrown deep inside core address-validation logic (used pervasively across unit validation, AA trigger evaluation, and wallet/device messaging) can crash the Node.js process handling the request. Because this validation runs on ordinary node/hub/wallet processes processing any newly received unit, AA trigger, or device message, a single crafted message from an unprivileged sender can take down a node — "a network unable to confirm new units" if hosts crash while validating/relaying, satisfying the required impact bar (network-availability DoS), analogous to the referenced Liblouis CVE's remote DoS.

### Likelihood Explanation
The precondition is only a fixed string length (32 or 48 characters) with characters that decode incorrectly under the base32/base64 decoder used — a straightforward, unauthenticated input to craft. `isValidAddress` is called on numerous attacker-supplied strings (unit author/output addresses, AA `is_valid_address`/`is_aa` oscript calls, wallet definition/pairing messages) with no guarantee that every caller wraps it defensively, making this readily reachable from posted units or AA triggers.

### Recommendation
- In `chash.isChashValid()`, wrap the entire body (not just the initial decode) in `try/catch`, or explicitly validate that the decoded buffer's byte length equals `chash_length/8` before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, returning `false` on mismatch instead of throwing.
- Audit all call sites of `isValidAddress`/`isValidChash`/`isChashValid` to ensure none can propagate an uncaught exception into request-handling code paths (unit validation, AA evaluation, device message handling).

### Proof of Concept
1. Construct a 32-character string that is not valid base32 per the `thirty-two` decoder's alphabet (e.g., containing lowercase letters or digits `0`,`1`,`8`,`9` which are outside RFC 4648 base32) but still satisfies `isStringOfLength(str, 32)`.
2. Pass this string as an address field reachable to an unprivileged actor, e.g. as `trigger.address`/an oscript `is_valid_address(...)` argument in an AA definition, or as an author/output address in a posted unit.
3. During validation, `isValidAddress` → `isValidChash` → `chash.isChashValid` decodes the malformed string; if the decoder returns a buffer whose bit-length is not exactly 160, `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")` outside the local `try/catch`, propagating as an uncaught exception in the caller's stack and crashing the process if not defensively caught upstream.

*(Note: full confirmation of the exact lenient-decoding behavior of the `thirty-two` npm package for out-of-alphabet input was not verifiable from the indexed files alone — this relies on the well-documented laxness of that library/Node's base64 decoder rather than on inspecting its source directly, since that dependency's source is not part of this codebase index.)*
