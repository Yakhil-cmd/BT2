## Finding

An `ApiClient` can be scoped to a single stack via its optional `stack_id` (`belongs_to :stack, optional: true`), and the base API controller enforces that scope by restricting the queryable `stacks` collection: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) , and the default `stack` accessor resolves through that scoped collection (`stacks.from_param!(params[:stack_id])`) [2](#0-1) .

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving directly against the global `Stack` relation: [3](#0-2) 

It only checks the generic `read:stack` permission via `require_permission :read, :stack` [4](#0-3) , which is enforced by `ApiClient#check_permissions!` and only tests whether the permission string is present in the client's `permissions` array — it never consults `stack_id` [5](#0-4) .

The controller also supports authenticating via a `token` query-string parameter (as exercised in tests) [6](#0-5) , making the endpoint trivially reachable with any valid, even narrowly-scoped, `ApiClient` token.

### Binding broken
`ApiClient.stack_id` (the stack a token is authorized for) ≠ `params[:stack_id]` (the stack whose state `CCMenuController#show` actually reads), because `stack` in this controller does not intersect with `stacks`.

### Impact
An `ApiClient` created and scoped to Stack A (`stack_id = A`, permission `read:stack` only) can use its own valid token to request `/api/1/cc/<OTHER_ORG>/<OTHER_REPO>/<OTHER_ENV>` for any Stack B it was never granted access to, and receive the CCTray XML containing that stack's name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`, derived from `stack.deploys_and_rollbacks.last` [7](#0-6) . This is an unauthorized cross-stack read of deploy/build state, which matches the "unauthenticated read of stack state, task streams or deploy output" High-severity category, since the token's authorization boundary (its `stack_id` scope) is not honored by this controller.

### Likelihood
High — no special privileges are required beyond possessing any single valid, narrowly-scoped `ApiClient` token (which is by design meant to be handed out with restricted, single-stack access, e.g. for CI dashboards); exploitation is a single unauthenticated-looking GET request differing only in the `stack_id` path/query parameter. ### Title
Cross-stack authorization bypass in `Api::CCMenuController` via unscoped `stack` lookup - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack directly through `Stack.from_param!`, bypassing the `stacks` scoping that all other API controllers use to enforce an `ApiClient`'s `stack_id` restriction, letting a stack-scoped token read any other stack's CCTray build/deploy state.

### Finding Description
`BaseController#stacks` restricts an `ApiClient` to its own `stack_id` when one is set: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` calls `stacks.from_param!(...)`. `CCMenuController` overrides `#stack` with `@stack ||= Stack.from_param!(params[:stack_id])`, dropping the `stacks` scoping entirely. The only remaining check, `require_permission :read, :stack`, verifies the permission string `read:stack` is present on the client but never compares against `stack_id`. Because `CCMenuController#authenticate_api_client` also accepts the token via `params[:token]`, this makes it easy to invoke with any valid client credential against an arbitrary `stack_id`.

### Impact Explanation
An attacker holding a legitimately-issued, narrowly-scoped `ApiClient` token (scoped to one stack, with only `read:stack` permission — a common low-privilege integration credential) can read build/deploy status information (`name`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for any other stack in the Shipit instance, violating the intended per-stack authorization boundary. This is an authorization bypass allowing unauthorized cross-stack read of deploy state.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` collection (as `BaseController#stack` does) instead of the unscoped `Stack.from_param!`, so the `ApiClient.stack_id` restriction is honored consistently across all API controllers.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id; obtain its `authentication_token`.
2. Send `GET /api/1/cc/<org_B>/<repo_B>/<environment_B>?token=<token>` where `org_B/repo_B/environment_B` identifies Stack B (any stack other than A).
3. Observe the endpoint returns Stack B's CCTray XML (`show` renders `stack.deploys_and_rollbacks.last`), even though the token is scoped to Stack A only, because `CCMenuController#stack` never checks `current_api_client.stack_id` against the requested stack.
