### Title
Predictable/self-chosen seeds let an AA trigger sender pre-compute and selectively discard `number_from_seed()` outcomes before ever broadcasting - ([File: formula/evaluation.js])

### Summary
Oscript exposes `number_from_seed()` as the built-in randomness primitive for AAs, and `vrf_verify()` as a VRF-signature checker whose actual random value must be derived by the AA author (typically by feeding the VRF proof/output into `number_from_seed`). In both cases, the entropy the AA logic ultimately consumes is only as unpredictable as the seed the trigger sender or oracle chooses to supply. If an AA is written to derive its "randomness" from data that is fully known to the trigger author *before* the triggering unit is posted (e.g. `trigger.unit`, `trigger.data`, `trigger.address`, or any static/predictable seed), the poster can compute the outcome off-chain, and simply choose not to broadcast the unit if the draw is unfavorable, repeating with a different nonce in `trigger.data` until a favorable draw is found. This mirrors the report's "re-roll the output until it's favorable" bug class, except it's even cheaper here: no chain-reorg or hashrate is required — grinding happens entirely off-chain before commitment, for free, and repeatable indefinitely.

### Finding Description
`number_from_seed` hashes a caller-supplied seed with SHA-256 and maps the digest to a number/int range: [1](#0-0) 

The seed can be constructed from any oscript-visible value, including `trigger.unit`, `trigger.data`, or `trigger.address`, all of which are fully determined and known by the trigger sender before the unit is ever hashed, signed, or broadcast — the unit hash `trigger.unit` is computed locally by the author's wallet from the unit's own content: [2](#0-1) 

Because `handleTrigger` builds the trigger object directly from the already-fully-formed unit (`trigger.unit = objUnit.unit`, `trigger.data = message.payload`) with no confirmation delay or additional entropy contributed after broadcast: [3](#0-2) 

an AA author (attacker) can locally simulate arbitrarily many candidate trigger units — varying `data` fields — computing `number_from_seed(...)` for each candidate exactly as the AA will, entirely offline, before ever broadcasting anything. Since nothing is committed to the DAG until the author chooses to post, there is no cost or on-chain trace for a discarded attempt (unlike the reported bug, which required the VRF request to already be on-chain and then reorg it away). The author simply posts only the trigger unit that yields the favorable random draw.

This is architecturally analogous to the External Report's core problem: a party who can observe/compute the "random" output before it's final can selectively act only when it's favorable to them, defeating the purpose of the randomness. Here the mechanism is grinding an off-chain candidate set rather than a chain reorg, but the end effect — an unprivileged unit poster biasing an AA lottery/gamble outcome in their own favor — is the same class of vulnerability, and it is reachable purely by an ordinary trigger sender posting units, matching the reachable-actor constraints (AA trigger sender).

Additionally, `vrf_verify` only validates a signature/proof against a PEM key; it does not itself enforce that the VRF was computed over an unpredictable/uncommitted seed, nor does it enforce any confirmation delay between when a VRF request seed becomes known and when its output is consumed by AA logic: [4](#0-3) . If AA authors design games using a seed the requester chooses (e.g., an arbitrary nonce), the same grinding attack applies before even needing valid VRF proofs, because the vulnerable pattern is in how the seed is chosen, not in the VRF-verification primitive itself.

### Impact Explanation
Any AA that implements gambling/lottery/random-payout logic using `number_from_seed()` fed by trigger-controlled values (unit hash, trigger data, timestamp under the poster's control, etc.) can be biased by the triggering party. This constitutes unauthorized extraction of AA funds (the attacker only submits triggers that are guaranteed or highly likely to win), i.e., "AA fund loss" for the AA's other participants / the AA's balance, which meets the required impact bar (concrete unauthorized fund drain from an AA). Because it requires no consensus power, no reorg, and no privileged role — only an ordinary trigger-posting user — the severity is High: any well-funded actor can exploit any game-style AA that misuses this pattern with zero marginal cost per attempt.

### Likelihood Explanation
Likelihood is High for any gambling/random-reward AA that (a) accepts arbitrary attacker-influenced `data` in the trigger and (b) folds trigger-controlled data (or any pre-computable value) into the seed passed to `number_from_seed`. Grinding candidate triggers off-chain is computationally trivial (SHA-256 evaluation), requires no network broadcast for failed attempts, and can be repeated without limit or cost until a favorable outcome is found. This is a foreseeable and common AA-authoring pitfall since oscript provides no built-in commit-reveal or confirmation-delay primitive to prevent it.

### Recommendation
- Do not allow the randomness seed of an AA lottery/gamble to be derived (directly or indirectly) from any value known to the trigger sender prior to broadcast (`trigger.unit`, `trigger.data`, `trigger.address`, freely-chosen nonces).
- Where genuine unpredictability is required, require a two-phase commit-reveal: the AA should snapshot state at a `stable` MCI or unit that postdates the trigger being finalized/immutable, i.e., use randomness sourced from state that only becomes fixed strictly after the trigger unit's contents are already locked in and cannot be discarded without cost (e.g., derive the seed from a subsequently posted, unrelated unit's hash/response unit hash the poster cannot control, combined with a mandatory minimum stabilization delay).
- Document and, where feasible, provide a built-in commit-reveal or delayed-VRF oscript primitive so AA developers are not left to invent their own (fragile) randomness schemes with `number_from_seed`.
- For `vrf_verify`-based designs, require that the seed committed to for the VRF request be independent of and unknowable to the requester at request time, and enforce a mandatory confirmation/stabilization window (analogous to the External Report's recommended mitigation) between seed commitment and consumption of the VRF output by AA logic.

### Proof of Concept
1. Deploy an AA that pays out based on `number_from_seed(trigger.unit)` (or `number_from_seed(trigger.data.nonce)`), e.g., "if number_from_seed(trigger.unit, 1, 100) > 50, AA pays 2x, otherwise trigger sender loses their stake."
2. Off-chain, attacker constructs many candidate trigger units, varying an inert field (e.g., an unused `data.nonce` value), computing the resulting `trigger.unit` hash for each candidate exactly as `getChash`/unit hashing would (mirrors `number_from_seed` logic in [5](#0-4) ).
3. Attacker evaluates `number_from_seed(candidate_unit_hash, 1, 100)` locally for each candidate and only signs+broadcasts the one unit whose seed produces a winning value; all other candidates are discarded with zero cost, since nothing was ever posted to the DAG.
4. Because `getTrigger()` derives `trigger.unit`/`trigger.data` verbatim from the already fully-formed, author-controlled unit before AA execution ( [3](#0-2) ), the AA's "random" outcome is deterministically known to the attacker before commitment, guaranteeing a win rate far above the intended odds and draining the AA's balance over repeated plays.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
