### Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
When Shipit is configured for multiple GitHub organizations (a documented setup, see `config/secrets.development.shopify.yml`), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, taken from the payload's `repository.owner.login` (falling back to `organization.login`). However, the event handlers (e.g. `PushHandler`) resolve which `Stack`/`Repository` to act on using a *different* field of the same payload, `repository.full_name`, via `Handler#repository_name`. Nothing binds these two fields together after signature verification, so the org whose secret authenticated the request is not the org whose repository actually gets written to.

and `PushHandler#process` uses that repository's stacks to trigger a GitHub sync with an attacker-supplied `after` SHA: [4](#0-3) 

This is analogous to the report's core flaw: a field that is acted upon (`callValueRefundAddress`/here `repository.full_name`) is never covered by the same trust check as the field that authorizes the action (`_sender`/here `repository.owner.login` used to pick the HMAC secret). In a multi-org Shipit deployment, an administrator of Organization C (who legitimately knows/controls C's `webhook_secret` because they administer C's GitHub App installation) can sign an arbitrary JSON body with C's secret while setting `repository.owner.login` (or `organization.login`) to `"C"` (so `verify_signature` picks C's secret and passes) but set `repository.full_name` to `"A/victim-repo"`, a repository belonging to unrelated Organization A also hosted on the same Shipit instance. The `PushHandler` will then look up `Repository.from_github_repo_name("A/victim-repo")` and call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on Organization A's stacks, none of which required any credential belonging to Organization A.

### Impact Explanation
This breaks the trust boundary between tenants (organizations) sharing one Shipit instance: possession of one organization's webhook secret should only authorize webhook actions for that organization's own repositories, not for another organization's stacks. An attacker who is a legitimate but low-privileged actor for Org C (able to see/administer C's GitHub App webhook config) can force GitHub sync operations, and depending on handler (`status`, `check_suite`, `membership`) potentially manipulate commit statuses, check-suite state, or team membership records tied to Org A's repositories/stacks — data that gates whether a commit is "deployable" and can subsequently be shipped. This is a cross-repository/cross-organization write achieved without any credential belonging to the victim organization, matching the required High/Critical impact bar (unauthorized state change feeding into deploy decisions across repository/organization boundaries).

### Likelihood Explanation
Requires the attacker to control (or be an admin of) at least one organization configured in the same multi-tenant Shipit instance — a legitimate, documented deployment pattern (`config/secrets.development.shopify.yml` explicitly shows the multi-org config schema). No GitHub App private key, Shipit session, or victim credentials are needed; only the attacker's own org's `webhook_secret`, which they are expected to possess.

### Recommendation
After computing `repository_owner` for signature selection, re-verify inside each handler (or centrally in `WebhooksController`) that the `repository.full_name` (and `organization.login` if present) actually belongs to the same organization whose secret validated the signature, rejecting the webhook otherwise. Alternatively, look up the `Repository`/`Stack` first and use *its* configured organization to select the webhook secret, so the field used for authorization and the field acted upon are the same.

### Proof of Concept
1. Shipit is configured with two organizations, `A` and `C`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema).
2. Attacker administers Org C's GitHub App installation and thus knows C's `webhook_secret`.
3. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha that exists in Org A's repo>",
  "repository": { "full_name": "A/victim-repo", "owner": { "login": "C" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(C_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner` → `"C"` (from `repository.owner.login`), fetches `Shipit.github(organization: "C")`, and the HMAC matches → request passes.
6. `Shipit::Webhooks::Handlers::PushHandler` resolves `repository_name` from `repository.full_name` → `"A/victim-repo"`, finds Org A's `Stack`s, and calls `stack.sync_github(expected_head_sha: params.after)`, an action on Org A's stack triggered purely with Org C's credentials.
