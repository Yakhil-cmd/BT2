### Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the independent, unchecked `repository.full_name` field, allowing cross-organization forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC `webhook_secret`) to verify a webhook against based solely on `repository.owner.login` (or `organization.login`) taken from the JSON payload. Every `Shipit::Webhooks::Handlers::Handler` subclass, however, locates the `Repository`/`Stack` to act on using a completely different, independently-attacker-controlled field: `repository.full_name`. Nothing in the code enforces that `repository.full_name` belongs to the same organization used to select the verification secret, so a party who legitimately controls a webhook secret for one organization's GitHub App installation can craft a signed payload whose `repository.full_name` points at a stack belonging to an entirely different, unrelated organization configured in the same Shipit instance, and have it processed as if it came from that organization.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
``` [1](#0-0) [2](#0-1) 

This picks a GitHub-App-specific `webhook_secret` (per Shipit's multi-org configuration, see `test/dummy/config/secrets_double_github_app.yml`'s `OrgOne`/`OrgTwo` sections) and validates the raw body's HMAC signature against it.

Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, and the `PullRequest::*Handler` classes. Every one of these inherits from `Shipit::Webhooks::Handlers::Handler`, which resolves the target repository as:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository.full_name` and `repository.owner.login` are two independent JSON keys in the same payload body. The signature covers the raw body bytes as a whole, so the *signature itself* is valid proof only that "whoever holds OrgA's `webhook_secret` produced this exact byte string" — it says nothing about which organization's stacks that byte string is entitled to reference. Because the controller uses `repository.owner.login` only to pick the verification key, and the handlers use `repository.full_name` only to pick the mutated resource, an attacker who legitimately possesses a valid webhook secret for OrgA (e.g., because they administer their own GitHub App installation of Shipit for OrgA) can freely set `repository.full_name` to `"OrgB/some-repo"` while keeping `repository.owner.login` as `"OrgA"`, sign the whole payload with OrgA's secret, and have it accepted and dispatched against OrgB's stacks.

Concretely:
- `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for any stack under the forged `full_name` and `ref`. [4](#0-3) 
- `CheckSuiteHandler` will force a check-runs refresh for arbitrary commits on the target stack. [5](#0-4) 
- `PullRequest::ClosedHandler` resolves `repository` purely from `params.repository.full_name` and calls `review_stack.archive!`, again scoped only by the forged full name. [6](#0-5) 

The `repository_owner == organization used to verify the payload` binding is checked, but the `repository_owner == owner(repository.full_name)` binding that the handlers implicitly rely on is never validated anywhere in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding described in the analog bug class. Any principal who legitimately holds a valid webhook secret for one org's Shipit-connected GitHub App installation (not a privileged Shipit account, GITHUB_TOKEN, or API token — just their own org's webhook secret, which by design many separate customer orgs each hold in a multi-tenant Shipit deployment) can forge webhook events that mutate state (`sync_github`, check-run refresh, review-stack archival, membership/team changes via `MembershipHandler`, etc.) for stacks/repositories belonging to a completely different organization hosted on the same Shipit instance. This is a cross-repository/cross-organization write achieved purely by manipulating an unauthenticated payload field, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability requires only that the attacker already control a valid webhook secret for some organization registered with the Shipit instance — a low bar in any multi-tenant deployment (Shipit explicitly supports multiple GitHub App configs, as evidenced by the `OrgOne`/`OrgTwo` fixture). No access to the target organization, no GitHub credentials for the target repo, and no privileged Shipit account are needed. This makes the analog directly analogous in class and severity to the referenced report's factory-address confusion: a check is performed against the wrong scoping key, silently permitting cross-boundary action.

### Recommendation
After signature verification succeeds, explicitly assert that `repository.owner.login` (the field used to select/verify the webhook secret) matches the owner segment of `repository.full_name` (the field the handlers use to resolve the target Repository/Stack) before dispatching to handlers. Reject the request (e.g., with 422) if they diverge. Equivalently, have `Handler#repository_name` be constrained to `"#{repository_owner}/#{repo}"` derived from the same trusted field used at verification time, rather than trusting `full_name` independently.

### Proof of Concept
1. Attacker administers their own GitHub App installation of Shipit for `OrgA` and thus legitimately knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha already present as a commit on target stack>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully because the attacker legitimately possesses `OrgA`'s secret. [1](#0-0) 
5. `PushHandler.call(params)` is invoked; `stacks` resolves via `Repository.from_github_repo_name("OrgB/victim-repo")`, which has nothing to do with `OrgA`, and `stack.sync_github(expected_head_sha: ...)` runs against `OrgB`'s stack. [3](#0-2) [4](#0-3)
