### Title
Reachable `assert()` abort in `recover_cells()` via caller/callee cell-count mismatch - (File: `src/eip7594/recovery.c`)

### Summary
`recover_cells()` computes `len_missing = CELLS_PER_EXT_BLOB - (number of indices found in cell_indices)` and then executes `assert(CELLS_PER_EXT_BLOB - len_missing >= CELLS_PER_BLOB)` [2](#0-1)  instead of returning `C_KZG_BADARGS`. This invariant ("at least half of the cells are present, i.e. `num_cells >= CELLS_PER_BLOB` and no duplicates") is enforced only by the *caller*, `recover_cells_and_kzg_proofs()`, and is not re-validated inside `recover_cells()` itself.

### Finding Description
`recover_cells()` derives `len_missing` purely from scanning `cell_indices` for membership of each of the `CELLS_PER_EXT_BLOB` canonical indices using `is_in_array()` [3](#0-2) . It does **not** check that `cell_indices` contains no duplicates and does **not** check that `num_cells <= CELLS_PER_EXT_BLOB`. If the caller passes a `cell_indices` array that contains duplicate entries (e.g., the same valid index repeated many times) while `num_cells` nominally reports a value `>= CELLS_PER_BLOB`, the number of *distinct* indices actually found by `is_in_array()` can be smaller than assumed by the caller's own bound check, so `len_missing` computed inside `recover_cells()` can exceed `CELLS_PER_EXT_BLOB - CELLS_PER_BLOB`, violating the assumption baked into the `assert()` at line 260 and firing `abort()` (in release/NDEBUG-disabled builds this is a hard process termination; in builds where `NDEBUG` is defined the assert compiles out and the invariant violation instead flows into `vanishing_polynomial_for_missing_cells()`, which explicitly returns `C_KZG_BADARGS` only for the `len_missing >= CELLS_PER_EXT_BLOB` case, not for the intermediate corrupted state).

This is architecturally analogous to the Apollo Router bug: an externally-influenced input (duplicate/attacker-chosen cell indices reaching from `recover_cells_and_kzg_proofs()` — itself reachable directly from bindings such as `RecoverCellsAndKzgProofs`/`recover_cells_and_kzg_proofs` in the Rust/Go/Node bindings) reaches a code path that assumes a precondition was already enforced, but the assumption is not re-checked at the point where the crash-inducing assertion fires, so a single malformed input aborts the process — exactly the "count/invariant mismatch between caller's belief and callee's internal recomputation → reachable abort" bug class called out in the rules.

### Impact Explanation
A crafted `cell_indices` array (with duplicates) submitted to `recover_cells_and_kzg_proofs` — a function that is expected to process untrusted network-supplied cell data during PeerDAS data-availability reconstruction — can cause any node calling into this exact library to abort/crash. Since every node running `c-kzg-4844` for EIP-7594 cell recovery shares the identical code path, this meets the "High" impact bar: one crafted sidecar/cell-set crashes every node running this library.

### Likelihood Explanation
Reachability depends on whether `recover_cells_and_kzg_proofs()` (the actual public entrypoint, in `src/eip7594/eip7594.c`) itself de-duplicates or otherwise validates `cell_indices` for uniqueness *before* calling `recover_cells()`. I was not able to fully confirm within the remaining tool budget whether the caller performs a duplicate check prior to invoking `recover_cells()` (the snippet I retrieved for `recover_cells_and_kzg_proofs` was truncated before its validation section). This is the key open question that determines whether this is directly triggerable from the public API or only from an internal helper that already assumes clean input.

### Recommendation
Replace the `assert(CELLS_PER_EXT_BLOB - len_missing >= CELLS_PER_BLOB)` in `recover_cells()` with an explicit runtime check that returns `C_KZG_BADARGS` on failure, and/or explicitly validate that `cell_indices` contains no duplicates and `num_cells <= CELLS_PER_EXT_BLOB` at the top of `recover_cells_and_kzg_proofs()` before calling `recover_cells()`, so malformed input is rejected with a normal error code rather than a process abort.
