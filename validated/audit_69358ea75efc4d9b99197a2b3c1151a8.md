### Title
Front-runnable, creator-independent PoolState PDA lets an attacker hijack a pending pool's creator-fee rights and initial price - (File: programs/cp-swap/src/instructions/initialize.rs)

### Summary
The `PoolState` account address that every unprivileged swapper/LP will interact with is a PDA whose seeds are only `[POOL_SEED, amm_config, token_0_mint, token_1_mint]` [1](#0-0) . The identity of the party who actually submits the `initialize` transaction (the `creator`) is not part of this address derivation, yet that same unbound "creator" identity is stored on-chain and given a permanent, exclusive, unrevocable privilege (`collect_creator_fee`). This mirrors the reported bug class: a resource's deterministic/pre-computable address omits a security-critical parameter (there: the entrypoint; here: the creator), so any party who observes the pending, not-yet-created address can race to finalize it with attacker-chosen privileged parameters while the address stays the same as what other participants expect.

### Finding Description
`initialize` and `initialize_with_permission` derive/validate the `pool_state` PDA purely from `amm_config`, `token_0_mint`, and `token_1_mint` [2](#0-1) . Both instructions are permissionless with respect to who may call them — `creator`/`payer` is simply `Signer<'info>` with no additional binding to the pool's identity [3](#0-2) .

During `initialize`, whichever caller wins the race becomes permanently recorded as `pool_creator` via `pool_state.initialize(... ctx.accounts.creator.key() ...)` [4](#0-3) . That stored `pool_creator` pubkey is later the sole authority allowed to withdraw all accumulated creator fees for the life of the pool, enforced only by an `address = pool_state.load()?.pool_creator` constraint [5](#0-4) . There is no mechanism to change or re-validate this address after creation.

Additionally, the same transaction that wins this race also fixes the pool's initial reserve ratio (`init_amount_0`, `init_amount_1`), because the pool's first liquidity/price is computed directly from whatever `token_0_vault`/`token_1_vault` balances the winning caller funds during `initialize` [6](#0-5) . Since the `pool_state` address is fully predictable ahead of time from public inputs (config + mint pair), any party can watch the mempool/public intent to create a given pool, and instead submit their own `initialize`/`initialize_with_permission` transaction first — with themselves as `creator` and with a self-chosen (skewed) initial ratio — landing at the exact same PDA the legitimate deployer expected to control.

This is the direct analog of the reported issue: the address (there, the counterfactual wallet; here, the `pool_state` PDA) does not bind the privileged parameter (there, `entryPoint`; here, `creator`/initial ratio) into its derivation, so an attacker can finalize the resource with their own privileged value while preserving the address other parties already trust/reference.

### Impact Explanation
Whoever wins the initialization race for a given `(amm_config, token_0_mint, token_1_mint)` PDA permanently and unilaterally captures:
1. All future creator-fee revenue from that pool via `collect_creator_fee`, an unauthorized privileged effect diverting fee-ledger accounting away from the intended/legitimate project creator [7](#0-6) .
2. Control over the pool's genesis price ratio, which can be set adversarially to disadvantage the first depositors/swappers who interact with the pool assuming a fair, intended initial price, enabling immediate arbitrage extraction against subsequent depositors.

Because `pool_creator` cannot be changed after creation, this is a permanent, unrecoverable privilege misallocation rather than a temporary griefing.

### Likelihood Explanation
Exploitation requires only observing a public, unconfirmed `initialize`/`initialize_with_permission` transaction (or independently knowing a project intends to launch a pool for a known mint pair/config) and submitting a competing transaction with higher priority fee/compute — a standard, low-cost Solana front-running technique requiring no special privileges, matching the "attacker-chosen accounts and data in a single submitted transaction" reachability bar.

### Recommendation
Bind the intended creator (and/or a caller-chosen unique salt/nonce) into the `pool_state` PDA seeds, or require an explicit, separately-authorized "claim creator" step that cannot be front-run — analogous to including the entry point in the wallet's salt in the original report. At minimum, require the amm-config administrator/governance to pre-register the intended `creator` for a given mint pair before `initialize` is called, and reject `initialize` calls whose `creator` does not match that pre-registration.

### Proof of Concept
1. Project team publishes intent (or broadcasts an unconfirmed transaction) to call `initialize` for `token_0_mint = A`, `token_1_mint = B`, `amm_config = C`, funding it with a fair `init_amount_0`/`init_amount_1` ratio.
2. Attacker computes the same deterministic `pool_state` PDA: `find_program_address([POOL_SEED, C, A, B])` [1](#0-0) .
3. Attacker submits their own `initialize` transaction for the same `(C, A, B)` with a higher fee, setting themselves as `creator` and choosing a skewed `init_amount_0`/`init_amount_1` ratio, landing before the legitimate transaction.
4. The legitimate transaction now fails (`create2`-equivalent: account already initialized) or is simply superseded; the attacker's transaction succeeds, and `pool_state.pool_creator` permanently equals the attacker [4](#0-3) .
5. Attacker subsequently calls `collect_creator_fee`, which passes the `address = pool_state.load()?.pool_creator` check exclusively for the attacker, diverting all creator-fee accrual away from the legitimate project indefinitely [5](#0-4) .

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```
