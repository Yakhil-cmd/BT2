Cross-tenant webhook forgery: `repository_owner` used for signature verification is independent of `repository.full_name` used for stack mutation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to check the HMAC using `params.dig('repository','owner','login')`, while `LabeledHandler#repository` (and every other `PullRequest` handler, plus the base `Handler#stacks`) resolves the target `Repository` using the independent field `params.repository.full_name`. Nothing in the request pipeline enforces that these two attacker-controlled JSON fields refer to the same tenant, so a webhook signed with one organization's `webhook_secret` can name and mutate a completely different organization's repository/stack.

### Finding Description
The broken binding, stated as an equality that the code must (but does not) enforce:

`organization_that_signed_the_body == owner(repository.full_name_used_by_the_handler)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` and verify `X-Hub-Signature` against `request.raw_post`. [1](#0-0) 
2. `Shipit.github(organization:)` looks up the webhook_secret purely by the `organization` string, with no further cross-checks. [2](#0-1) 
3. Once verified, `WebhooksController#create` dispatches the entire raw `params` hash (unchanged) to the registered handler for the event. [3](#0-2) 
4. `LabeledHandler#repository` resolves the target repository using a *different* field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [4](#0-3) 
5. `Repository.from_github_repo_name` simply splits `"owner/name"` and does a `find_by`, with no relation back to `repository_owner` from step 1. [5](#0-4) 
6. `LabeledHandler#handle` then calls `stack.archive!` / `stack.unarchive!` on the `ReviewStackAdapter` built from that resolved repository's `review_stacks`, mutating state that belongs to whatever repository was named in `full_name`. [6](#0-5) [7](#0-6) 

Exploit flow: In a multi-organization Shipit configuration (`secrets.yml` with distinct `github.<org>.webhook_secret` per organization, as documented), an attacker who legitimately administers `attacker-org` (and therefore knows/controls `webhook_secret` for that org's GitHub App installation) can `POST /webhooks` directly with a body such as:
```json
{
  "action": "labeled",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "pull_request": { ... "state": "open", "labels": [...] },
  "sender": { "login": "attacker" }
}
```
signed with `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker-org, raw_body)`. `verify_signature` uses `repository.owner.login` ("attacker-org") to pick the app/secret and succeeds. The handler then uses `repository.full_name` ("victim-org/victim-repo") to locate and mutate the victim's `ReviewStack` (`archive!`/`unarchive!`), which changes `archived_since` and triggers deprovisioning, all without any credential belonging to `victim-org`.

None of the existing guards prevent this: `verify_signature` never compares the org it used for verification against `repository.full_name`'s owner; `drop_unhandled_event` and `check_if_ping` are event-routing only; the `ExplicitParameters` schema in `LabeledHandler` only requires that `repository.full_name` be a `String`, it does not require or check `repository.owner.login` at all; there is no `Repository` validation tying a name/owner pair to a specific webhook-signing organization.

### Impact Explanation
A payload authenticated for one tenant (`attacker-org`) causes a write (`stack.archive!`/`unarchive!`, deprovisioning, provisioning-queue mutation) against a different tenant's (`victim-org`) `ReviewStack`, with no credential belonging to the victim. This matches the Critical category "a payload for one repository mutating another's stack." It is fully repeatable against any repository the attacker can name in `full_name` as long as they can produce a signature verified by *any* organization configured in the Shipit instance's multi-org secrets. Blast radius scales with the number of tenants sharing one Shipit deployment, since the vulnerability lets any one tenant with a valid `webhook_secret` forge mutations against every other tenant's repositories/stacks (also affects `UnlabeledHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, and the base `Handler#stacks`, which have the identical pattern).

### Likelihood Explanation
This requires: (a) the Shipit instance to be configured for multiple GitHub organizations (the documented multi-org `secrets.yml` schema with per-org `webhook_secret`), and (b) the attacker to legitimately control at least one of those organizations/installations (a realistic scenario for a shared/multi-tenant Shipit deployment serving several orgs/customers). Given that, the attacker's cost is trivial: craft one JSON body and one HMAC signature and send a direct HTTP POST to `/webhooks` — no GitHub relay is required since Shipit accepts any POST with a valid signature header. This is fully repeatable and requires no session, API token, or victim secret.

### Recommendation
In `WebhooksController#verify_signature`, and/or in each `PullRequest` handler's `repository` method, enforce that the organization used to select the signing `webhook_secret` matches the owner encoded in `params.repository.full_name` (reject the request, e.g. `head(422)`, if `repository.owner.login` and the owner segment of `repository.full_name` diverge). Additionally, `Repository.from_github_repo_name` (or its callers) should validate that the resolved repository's `owner` equals the verified `repository_owner` before performing any stack mutation.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style), requires multi-org `Shipit.github` stubbing:
```ruby
test "labeled webhook signed by attacker-org can mutate victim-org's review stack" do
  victim_repo  = shipit_repositories(:victim) # owner: "victim-org", name: "victim-repo"
  victim_stack = create_review_stack(repository: victim_repo, environment: "pr42")
  victim_stack.archive!(shipit_users(:someone)) # start archived
  refute victim_stack.archived_since.nil?

  attacker_secret = "attacker-secret"
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", webhook_secret: attacker_secret)
  )

  body = {
    action: "labeled",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "https://x", title: "t", state: "open",
      additions: 1, deletions: 1,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [] # configured to trigger unarchive!
    },
    repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, body)

  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  assert_changes -> { victim_stack.reload.archived_since }, from: victim_stack.archived_since, to: nil do
    post :create, body: body, as: :json
  end
end
```
Assertions on both sides of the binding: (1) `verify_signature` succeeded using `attacker-org`'s secret (verified organization = "attacker-org"); (2) the mutated record's owning organization from `repository.full_name` = "victim-org" — these two differ, proving the binding is broken, and the victim stack's `archived_since` changed as a direct result.
