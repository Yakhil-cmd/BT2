### Title
Webhook signature verification authenticates `repository.owner.login`, but handlers act on the unauthenticated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub Apps/organizations, each with its own `webhook_secret`, keyed by organization name (see `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github_app_config`). `WebhooksController#verify_signature` selects which app/secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). However, none of the downstream event handlers use that same `owner.login` field to decide what to act on — they instead resolve the target `Repository`/`Stack` using `repository.full_name` via `Repository.from_github_repo_name` in `Shipit::Webhooks::Handlers::Handler#repository_name` and in every `PullRequest` handler.

### Finding Description
`verify_signature` computes: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and validates the HMAC over the raw body using that organization's `webhook_secret`: [3](#0-2) 

The organization→config lookup is per-organization: [4](#0-3) 

But the actual object mutated by a webhook (the `Stack`/`Repository` to sync, archive, unarchive, label, etc.) is selected from `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

All pull-request handlers repeat this pattern, resolving the acted-upon repository from `params.repository.full_name`: [7](#0-6) [8](#0-7) 

The equality that should hold but doesn't: `organization used to select/verify the webhook_secret (repository.owner.login)` == `organization implied by the repository the handler actually writes to (repository.full_name.split('/').first)`. In a legitimate GitHub-originated payload these always match, but nothing in the code enforces it. Since `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields both covered by the same HMAC over the raw body, a party who possesses (or has been issued) a valid `webhook_secret` for **their own** organization "OrgTwo" — which is completely legitimate to hold, since each org's admin configures and knows their own webhook secret per `docs/setup.md`'s "Webhook secret" step — can sign an arbitrary payload where `repository.owner.login = "OrgTwo"` (selects and satisfies OrgTwo's HMAC secret) while `repository.full_name = "OrgOne/some-repo"` (a repository belonging to a completely different, unrelated organization/tenant configured in the same Shipit instance). `verify_signature` will succeed because it only checks OrgTwo's secret against `owner.login = OrgTwo`; the handler then locates and mutates `Repository`/`Stack` rows for `OrgOne/some-repo` via `from_github_repo_name`.

### Impact Explanation
This crosses the "cross-tenant" boundary the multi-org GitHub App feature is meant to enforce: an admin who legitimately controls one organization's Shipit-configured webhook secret can forge cross-repository writes into another organization's stacks — triggering `GithubSyncJob` (which pulls/deploys arbitrary refs into OrgOne's stack, `push` handler), or archiving/unarchiving/mutating OrgOne's `ReviewStack`s (`pull_request` handlers). This maps to "cross-repository writes" and "an unauthorized deploy" impact tiers, since `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` on stacks it should never be authorized to touch: [9](#0-8) 

### Likelihood Explanation
Requires the attacker to be a legitimate, non-privileged (relative to the *other* tenant) holder of one organization's own `webhook_secret` in a multi-org Shipit deployment — a realistic operator population for any shared Shipit instance hosting several organizations' repositories, and explicitly a supported configuration (`test/dummy/config/secrets_double_github_app.yml`). No access to OrgOne's secret, GitHub credentials, or session is needed.

### Recommendation
After selecting the app/secret via `repository_owner` and verifying the signature, additionally assert that `repository.full_name`'s owner segment equals the same `repository_owner`/organization used for verification (mirroring the Gnosis fix of checking `messageSourceChainId() == MIRROR_DOMAIN` in addition to sender identity) before dispatching to handlers, and consider passing the verified organization down into handlers so `Repository.from_github_repo_name` scoping can be constrained to it.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`), both configured to manage stacks (e.g., `OrgOne/private-repo` and `OrgTwo/public-repo`).
2. As the legitimate owner of `OrgTwo`'s app (knows `OrgTwo`'s `webhook_secret` only), craft a `push` webhook JSON body with `repository.owner.login = "OrgTwo"`, `repository.full_name = "OrgOne/private-repo"`, `ref = "refs/heads/master"`, `after = <attacker-chosen sha>`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "OrgTwo"`, fetches OrgTwo's app, verifies the signature successfully (`GitHubApp#verify_webhook_signature`).
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgOne/private-repo")` and enqueues `GithubSyncJob` for OrgOne's stack, causing it to sync/deploy an attacker-chosen `after` SHA — despite the attacker never possessing OrgOne's webhook secret or GitHub access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
