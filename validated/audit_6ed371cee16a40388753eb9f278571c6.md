### Title
Attacker-controlled `.gitmodules` submodule content causes a deterministic sync failure loop and permanent denial of publishing - (File: `main.go`)

### Summary
`configureWorktree` runs `git submodule update --init` (optionally `--recursive`) against the checked-out worktree whenever `--submodules` is enabled. The submodule URLs and `.gitmodules` file are untrusted content that comes from the synced repository itself — i.e., they are attacker-controlled if the attacker can push a commit or control the ref that git-sync tracks. If that submodule fetch/checkout step fails (unreachable/malicious submodule URL, or content deliberately crafted so the update always errors), `SyncRepo` returns an error without ever calling `syncHooks.beforePublish`/`publishSymlink`, so the new hash is never published. Because the default `--max-failures` is `0` ("any sync failure will terminate git-sync"), this failure crashes the process; upon restart the same hash is fetched again, the worktree is (re)created via `createWorktree`'s self-cleaning "wedge case" logic, and `configureWorktree` fails identically — producing an unrecoverable crash-loop for as long as that ref is targeted. This is structurally the same bug class as the report: a sub-step whose success depends on untrusted/attacker-influenced external content (`fundingSplitRecipient` vs. a submodule URL) is embedded, non-separable, inside the single all-or-nothing "finalize"/"publish" transaction, so its failure blocks the entire operation and denies legitimate consumers the ability to progress, with no fallback path.

### Finding Description
The relevant code path is in `configureWorktree`: [1](#0-0) 
which runs `git submodule update --init [--recursive]` on the freshly created worktree using submodule definitions taken directly from the synced commit (attacker-controlled if the attacker can push to the tracked repo/ref).

This call happens inside `SyncRepo`, before the symlink is ever updated: [2](#0-1) 
If `configureWorktree` returns an error, `SyncRepo` propagates it immediately (`return false, "", err`), and `beforePublish`/`publishSymlink`/`afterPublish` are never invoked — so the new hash is neither made "ready" nor published, exactly mirroring how `_finalize` in the Solidity report cannot complete voting-power update / party transfer if the embedded fee transfer reverts.

The outer sync loop treats this as a fatal, unrecoverable failure by default: [3](#0-2) 
and `--max-failures` defaults to `0`, meaning "any sync failure will terminate git-sync": [4](#0-3) 

Crucially, `createWorktree` is explicitly designed to always retry from scratch on the next attempt by deleting any partially-built worktree ("wedge case" comment), so the retry deterministically repeats the same failing submodule operation every single time: [5](#0-4) 

Because the `git reset --soft remoteHash` already happened before the worktree/submodule step runs, `currentHash` state in the repo directory is already advanced to the malicious commit before the failure occurs, so nothing about restarting the process changes the outcome — the same commit is fetched, the same submodule content is processed, and the same failure recurs.

### Impact Explanation
Under a typical Kubernetes sidecar deployment (the documented primary use case), a crash (`os.Exit(1)`) causes the pod/container to restart via the standard restart policy, and the persistent volume backing `--root` retains the advanced git state. This produces an infinite crash-loop: git-sync can never converge because the untrusted commit's submodule content will always be re-processed and always fail, and the symlink is never advanced. This satisfies the "persistent sync denial" impact category from the ruleset — an application relying on the sidecar to serve fresh content is permanently denied any newer revision, and depending on deployment (`--one-time`, init containers, `readinessFile`), it can also block application startup/readiness entirely, since `setRepoReady()` is only called on success.

### Likelihood Explanation
This requires `--submodules` to be enabled (not the default of `off`, per `submodulesMode`) and requires the attacker to have push/commit access to the tracked ref of the synced repository (e.g., untrusted external contributors, a compromised upstream mirror, or any workflow where git-sync tracks a branch not fully trusted). This is a realistic threat model for git-sync given its explicit design goal of syncing external/remote repositories, and no special git-sync configuration beyond enabling submodules is needed to be affected — likelihood is moderate, gated primarily on `--submodules != off`.

### Recommendation
- Decouple submodule/sparse-checkout configuration failures from the "must succeed before publish" path where feasible, or provide a bounded, isolated retry/skip mechanism (e.g., skip failing submodules and log, similar to the report's recommendation to separate the failing sub-step from the atomic operation) rather than failing the entire sync.
- Ensure `--max-failures`/`--init-max-failures` guidance explicitly warns operators that a default of `0` combined with `--submodules` on an untrusted repo can produce a permanent crash-loop, and consider treating persistent identical failures (same target hash) specially, e.g., by not re-advancing `currentHash`/HEAD via `git reset --soft` until the whole worktree+submodule configuration has fully succeeded, so at least the previously-published good state remains servable indefinitely without repeated destructive retries.
- Consider validating/sanitizing submodule URLs (e.g., disallowing `ext::`/other exotic transport helpers) as defense-in-depth, independent of this specific denial-of-service issue.

### Proof of Concept
1. Deploy git-sync with `--submodules=shallow` (or `recursive`) tracking a branch that an attacker (or low-privilege collaborator) can push to.
2. Attacker pushes a commit adding a `.gitmodules` entry pointing to a submodule URL that is guaranteed to fail (e.g., a non-existent host, or a URL requiring interactive auth that git-sync's non-interactive environment cannot satisfy).
3. git-sync's sync loop performs `fetch` → `reset --soft` to the new hash → `createWorktree` (succeeds) → `configureWorktree` → `git submodule update --init` fails.
4. `SyncRepo` returns an error before `beforePublish`/`publishSymlink` runs; with the default `--max-failures=0`, `main`'s loop logs "too many failures, aborting" and calls `os.Exit(1)`: [6](#0-5) 
5. On container restart (Kubernetes default `Always` restart policy), the same commit is present in `.git`, `currentHash` will match remote (or the worktree is nuked/recreated per the "wedge case" logic), and step 3 repeats identically — an unbounded crash-loop, with no new content ever published and (if this is the first sync) `setRepoReady()`/readiness never being reached.

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
