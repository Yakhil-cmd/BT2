### Title
Cross-tenant Status webhook write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no repository/stack filter, then calls `create_status_from_github!` on every matching row. Because `Commit.sha` has no uniqueness constraint scoped to `stack_id` [1](#0-0) , a single authenticated webhook for repository A can write `Status` rows into a `Commit` belonging to an unrelated stack/repository B whenever both happen to contain a commit with the same SHA.

### Finding Description
The broken binding: `authenticated_repository(webhook_payload.repository.full_name) == commit.stack.repository` should hold for every `Commit` row mutated by a given webhook request. In the actual code this equality is never checked.

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App belonging to `repository_owner` (the org in the payload) [2](#0-1) . It does not constrain which `Stack`/`Commit` rows the handler is allowed to touch.

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

Notably, the base `Handler` class provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) , but `StatusHandler#process` does not use it — it queries `Commit` globally across all stacks/repositories in the database, keyed only by `sha`.

`create_status_from_github!` then writes a `Status` row and triggers `add_status`, which recomputes `status`, emits `Hook.emit(:commit_status, ...)`/`:deployable_status`, and can call `stack.schedule_merges` [5](#0-4) [6](#0-5)  — i.e. it can affect CI-gated deploy/merge state for the victim stack.

Since `Commit` has no uniqueness validation on `sha` scoped to `stack_id`, two different stacks (tracking different repositories that share history, e.g. a fork relationship or a shared upstream branch prior to divergence) can legitimately contain rows with an identical `sha`. Once that precondition holds, a genuine, correctly-signed status webhook from repository A's GitHub App will iterate and mutate the commit row belonging to stack B as well, because the query has no `stack_id`/repository filter.

### Impact Explanation
A single authenticated webhook payload for one repository writes a `Status` record into another tenant's stack/commit, matching the "payload for one repository mutating another's stack, commit" Critical category. This can alter `deployable?`/`blocked?` computation for the victim stack (via `status`, `blocked?`, `deployable?` on `Commit`) and can trigger `stack.schedule_merges`, indirectly influencing continuous-delivery/merge behavior for a repository the attacker never authenticated against. This is repeatable against any pair of stacks that happen to share a commit SHA.

### Likelihood Explanation
This requires the precondition that two different stacks contain `Commit` rows with the identical `sha` — plausible in real deployments (fork tracking, shared base branches, monorepo splits) since `Commit.sha` uniqueness is not enforced at the database/model level per the reviewed model code. Given that precondition, the attacker only needs to legitimately trigger a correctly signed status webhook from their own authenticated repository (no special privilege beyond owning/controlling a repo with the app installed) — the code performs the cross-stack write automatically. I could not fully verify DB-level uniqueness constraints (in `db/schema.rb`/migrations, which are out of scope per the rules) that might additionally restrict this, so the exact likelihood depends on whether such a constraint exists outside the reviewed application code.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the authenticated repository, e.g. use the existing `stacks` helper: `Commit.where(sha: params.sha, stack: stacks)` (or join through `stack_id: stacks.pluck(:id)`), mirroring how other handlers should restrict writes to stacks belonging to `repository_name`. Additionally, verify that if a global sha-uniqueness invariant is not enforced across stacks, all sha-based lookups in webhook handlers are consistently repository-scoped.

### Proof of Concept
```ruby
test "status webhook does not update commits belonging to other stacks with same sha" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack(repository_url: "git://github.com/other-org/other-repo.git")

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared ancestor")
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.github_repo_owner } }
  }

  assert_difference -> { commit_a.statuses.count }, 1 do
    assert_difference -> { commit_b.statuses.count }, 1 do
      Shipit::Webhooks::Handlers::StatusHandler.call(payload)
    end
  end
  # Both sides of the equality change even though only stack_a's repository authenticated the webhook,
  # proving commit.stack.repository (stack_b) != authenticated_repository (stack_a) yet was mutated.
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
