### Title
Operator-precedence bug in `ReopenedHandler#unarchive?` allows re-provisioning of archived ReviewStacks when `review_stacks_enabled == false` - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` intends to require `repository.review_stacks_enabled == true` before any re-provisioning decision, but Ruby's `&&`/`||` precedence only binds `review_stacks_enabled` to the `provisioning_behavior_allow_all?` branch. The `allow_with_label` and `prevent_with_label` branches are unconditional disjuncts, so a repository with `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` still triggers `stack.unarchive!` on PR reopen. Note: the question's file header cites `app/controllers/shipit/ccmenu_url_controller.rb`, which is unrelated; the actual code and bug live in `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` must gate every disjunct of `unarchive?`. The actual code is: [1](#0-0) 

Due to `&&` binding tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed with the first disjunct. If `review_stacks_enabled == false` and `provisioning_behavior == allow_with_label` and the reopened PR carries the provisioning label, `unarchive?` still returns `true`, and `process` calls `stack.unarchive!`: [2](#0-1) 

`respond_to_pull_request_reopened?` only checks `params.action == "reopened"` and `unarchive?` — there is no separate check of `review_stacks_enabled` before invoking `stack.unarchive!`: [3](#0-2) 

The attacker's exact path: open a PR on a repository they control that has (or previously had) review stacks provisioned with `provisioning_behavior: allow_with_label`, attach the provisioning label to their own PR, get the review stack archived (e.g., by closing the PR while it existed, or after the operator later flips `review_stacks_enabled` to `false`), then close and reopen the PR (or send a forged/legitimate `pull_request` `reopened` webhook payload for their own repo). Because none of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema check `review_stacks_enabled` state — those guards only validate payload shape and webhook signature, not this authorization gate — the flawed boolean expression is the sole check, and it fails open for the `allow_with_label` and `prevent_with_label` branches regardless of `review_stacks_enabled`.

### Impact Explanation
This causes `stack.unarchive!` to run and re-provision/re-run steps for a ReviewStack on a repository whose `review_stacks_enabled` flag is `false` — a state that should disable all review-stack provisioning. Since the attacker owns the repository and controls the PR's branch/commits, this results in unauthorized re-execution of attacker-controlled steps (build/deploy-like tasks) that the operator explicitly intended to be disabled via `review_stacks_enabled: false`. This matches "an unauthorized deploy/rollback" style impact — re-provisioning triggers task execution outside the authorization boundary the operator configured. The blast radius is confined to the attacker's own repository/stack (no cross-tenant record mutation is demonstrated), but it is a real bypass of the review-stacks kill switch and is repeatable on every reopen event.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled` set to `false`, with an existing archived ReviewStack for the PR. Attacker cost is low — they only need to open/close/reopen their own PR and manage a label, actions any GitHub user with write access to their own repo can perform. This is fully self-service and repeatable each time the PR is reopened.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
1. Create a `Repository` with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label`.
2. Create an archived `Stack`/ReviewStack associated to a PR number, with the provisioning label present on the PR payload.
3. Build a `reopened` webhook payload for that PR/repo including the label in `pull_request.labels`.
4. Call `ReopenedHandler.new(payload).process`.
5. Assert `stack.reload.archived?` is `false` (bug reproduced) vs. the expected `true` (fix verifies `repository.review_stacks_enabled == false` blocks `unarchive!`).
