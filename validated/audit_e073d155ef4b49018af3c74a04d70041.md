### Title
Cross-Repository Commit Status Injection via `StatusHandler` Bypasses the Per-Organization Webhook Signature Binding — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` records by matching **only** the SHA supplied in the webhook payload, with no scoping to the repository that the request was signed for. Because `WebhooksController#verify_signature` only proves that a payload was signed by *some* organization's configured GitHub App (selected via `repository.owner.login`), and never confirms that the commits actually acted upon by the handler belong to that same organization/repository, an attacker who is a legitimate installer/admin of **any** GitHub App configured in this Shipit instance can forge a `status` webhook that is correctly signed with their own organization's secret, yet whose `sha` value matches a commit belonging to a completely different (victim) organization's stack. This lets them write a fabricated `success` CI status onto a commit they do not own, potentially unblocking `continuous_deployment` for the victim stack and triggering an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` to validate against using only `repository_owner` (derived from the payload's `repository.owner.login`, falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This only proves the request was HMAC-signed with the webhook secret belonging to *that particular organization's* configured GitHub App — a secret which is known to (or forgeable by) anyone who legitimately administers that org's own Shipit-connected GitHub App installation. It says nothing about which repository's data the payload is permitted to describe.

Once verified, the raw JSON is dispatched to handlers unmodified: [3](#0-2) 

Most handlers correctly re-derive the acted-upon `Repository`/`Stack` from the payload's own `repository.full_name` field via the shared `stacks` helper: [4](#0-3) 

However, `StatusHandler` does not use this scoping at all. It queries `Commit` globally by `sha`, independent of any repository field in the payload: [5](#0-4) 

The binding that should hold is: *organization that authenticated (signed the payload) == repository whose commits are written*. Instead, the actual binding enforced is: *organization that authenticated == any organization configured in this Shipit instance* while *repository written == any repository, anywhere in the instance, whose commit happens to share the attacker-chosen SHA*. An attacker controlling Org A's GitHub App can therefore sign a payload as Org A but target a commit SHA that belongs to Org B's stack (SHAs are public and easily discoverable via GitHub's API/UI), and `commit.create_status_from_github!` will write the forged status onto that foreign commit.

### Impact Explanation
A forged `success` status written to a foreign stack's commit can satisfy the CI-clearance conditions that gate deploy triggers. If the targeted stack has `continuous_deployment` enabled, `ContinuousDeliveryJob#perform` unconditionally checks `stack.continuous_deployment?`, deployment-schedule windows, and whether the stack is occupied — but relies on the commit/status data (which the attacker just poisoned) to decide the deployable head: [6](#0-5) 

This allows an attacker with no access to the victim's GitHub organization or repository to trigger an **unauthorized deploy** on the victim's stack — satisfying the "Critical: unauthorized deploy" impact tier. At minimum, even without continuous deployment, the attacker can pollute a foreign stack's commit status history displayed in the UI and consumed by other automation (e.g., `check_suite`/status-gated merges), an integrity break of state the app is trusted to report accurately from GitHub.

### Likelihood Explanation
The prerequisite is administering (or otherwise obtaining a webhook secret for) **any one** GitHub App organization configured in the multi-tenant Shipit deployment — a materially lower bar than compromising the victim organization, and explicitly anticipated by this engine's own multi-org support (`docs/setup.md`'s "Using Multiple GitHub Applications" section, `test/dummy/config/secrets_double_github_app.yml`). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only a raw HTTP POST to `/webhooks` with a validly HMAC-signed body. Commit SHAs are not secret. This is a straightforward, repeatable, unprivileged-relative-to-the-victim attack path.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the payload's own `repository.full_name` (i.e., reuse the `stacks`/`repository_name` helper already used by every other handler) instead of querying `Commit` by `sha` alone, e.g.:

```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

More generally, audit all webhook handlers to guarantee that the organization bound by `verify_signature` is always cross-checked against the repository/stack the handler subsequently mutates, so no handler can act cross-tenant purely because it omits the `repository_name` scoping that `Handler#stacks` provides.

### Proof of Concept
1. Attacker is a legitimate admin of `OrgA`, which has its own GitHub App configured in this Shipit instance (`config/secrets.yml` → `github.OrgA.webhook_secret`).
2. Attacker discovers a commit SHA `deadbeef...` belonging to `OrgB/victim-repo`'s stack (public GitHub data), where the stack has `continuous_deployment: true`.
3. Attacker crafts a `status` event payload:
   ```json
   { "sha": "deadbeef...", "state": "success", "context": "ci/tests", "created_at": "..." }
   ```
4. Attacker signs it with `OrgA`'s known webhook secret using HMAC-SHA1 and sends it to `POST /webhooks` with headers `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
5. `verify_signature` resolves `repository_owner` — for a bare `status` payload with no `repository` key, it falls back to `organization.login`; the attacker sets that to `"OrgA"`, so `Shipit.github(organization: "OrgA")` is used and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the commit under `OrgB/victim-repo`'s stack (unrelated to `OrgA`), and calls `create_status_from_github!`, writing a forged "success" CI status.
7. If `OrgB`'s stack's deploy gating depends on that status, `ContinuousDeliveryJob` may now trigger an unauthorized deploy of that commit.
