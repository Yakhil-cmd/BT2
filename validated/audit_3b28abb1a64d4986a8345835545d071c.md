### Title
Webhook signature verification org is chosen from unverified payload fields, decoupling the authenticated organization from the repository the handler writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, not-yet-verified JSON body. The actual event handlers (e.g. `PushHandler`, `StatusHandler`) locate the `Stack`/`Repository` to act on using a *different* field of the same payload — `repository.full_name`. Because both fields are attacker-controlled prior to verification, an attacker can pick an organization whose config has no `webhook_secret` set (an explicitly supported, documented default — `webhook_secret: # nil`) for the "owner" field used only for signature selection, while pointing `repository.full_name` at a different, protected stack. This breaks the equality: `organization authenticated == repository written`.

### Finding Description
`verify_signature` computes the verification target purely from payload content, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp`/config instance for that named org, and `verify_webhook_signature` is a no-op bypass when that org has no secret configured: [3](#0-2) 

The documented setup explicitly allows `webhook_secret` to be left blank per organization: [4](#0-3) 

Meanwhile, event handlers such as the push handler resolve the target `Stack`/`Repository` from `repository.full_name` in the same payload, independent of the `repository.owner.login`/`organization.login` value used to pick the verifying secret (confirmed by the webhook controller test asserting repository lookup keys off `repository.full_name`): [5](#0-4) 

Because `repository_owner` and `repository.full_name`'s owner segment are two independently attacker-supplied fields in the raw JSON body, they need not match. An attacker who knows (or can guess) that some organization in a multi-tenant Shipit deployment has no `webhook_secret` configured can craft a payload where:
- `repository.owner.login` = the org with no secret (verification always "passes" via the `return true unless webhook_secret` short-circuit)
- `repository.full_name` = `victim-org/protected-repo` (the actual target acted upon by the handler)

This decouples the "organization whose credential authenticated the request" from "the repository the handler writes to," which is exactly the confused-deputy/binding-mismatch pattern the esLBR report illustrates (an action taken on one piece of state while the enforcing check validated a different, staled/mismatched piece of state).

### Impact Explanation
A successful forgery lets an unauthenticated attacker inject GitHub events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against a protected stack without possessing that stack's webhook secret, GitHub App private key, or repository write access. Depending on handler:
- `push` events can enqueue `GithubSyncJob`, altering which commits Shipit believes exist/are deployable.
- `status`/`check_suite` events can fabricate passing CI/check-run results for a real commit, which feeds directly into `Commit#deployable?`, `MergeRequest#all_status_checks_passed?`, and continuous-deployment/auto-merge logic — potentially causing an **unauthorized deploy or merge** on the protected stack.
This matches the Critical-tier impact bucket ("cross-repository writes... an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability is contingent on a specific but supported and documented deployment shape: multiple GitHub organizations configured under `Shipit.github`, where at least one configured organization has no `webhook_secret` set (shown as the default/example value in the docs and example secrets file). Given that shape, the attack requires no credentials at all — just an HTTP POST to `/webhooks` with a crafted body and correct `X-Github-Event` header. Likelihood is therefore **medium**: it depends on operational configuration choices that the engine itself documents as valid, rather than a host misconfiguration outside the documented setup.

### Recommendation
Do not let `verify_signature` select the verification secret based on any part of the still-unverified payload that a handler will later trust for a *different* purpose. Concretely:
- Verify the signature using the `webhook_secret` bound to the actual target repository/stack (resolved the same way handlers resolve it — e.g. via `repository.full_name`), not a separately-read `owner`/`organization` field.
- Reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Consider making `webhook_secret` mandatory (or failing closed) for any organization configuration, removing the `return true unless webhook_secret` bypass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config: `orgA` (no `webhook_secret` set) and `orgB` (has `webhook_secret`, owns a real, protected stack `orgB/prod-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/prod-repo" },
  "sha": "<real sha on orgB/prod-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` computes `repository_owner = "orgA"`, fetches `orgA`'s `GithubApp` (no secret) → `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler` processes the event using `repository.full_name = "orgB/prod-repo"`, creating a fabricated successful `Status` on the real commit of the protected stack, without ever presenting `orgB`'s webhook secret. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
