### Title
Cross-repository sha collision in `StatusHandler#process` unblocks other tenants' blocking-status gate - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, unlike every other webhook handler in this codebase (`OpenedHandler`, `ClosedHandler`, `EditedHandler`, etc.), which all resolve a `repository` from `params.repository.full_name` before touching any record. A verified webhook for repository A can therefore create a `Status` on a `Commit` belonging to a completely unrelated stack/repository B whose commits happen to share the same sha (e.g. via a fork sharing git history), letting an attacker flip a blocking commit's state to `success` and unblock `Commit#blocked?` for all later commits in stack B.

### Finding Description
The broken binding: for any `Commit` row updated by the status webhook, `commit.stack.repository.full_name` should equal `payload['repository']['full_name']` (the repository named in the verified, signed payload). It does not.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha` only - there is no `.where(stack: stacks)` or any use of the `Handler#stacks`/`repository_name` helpers that every other handler in this engine uses to scope work to the repository named in the verified payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Compare with e.g. `PullRequest::ClosedHandler`, which resolves `repository` from `params.repository.full_name` and scopes all lookups (`review_stack`) to that repository before mutating anything [3](#0-2) .

`WebhooksController#verify_signature` only authenticates that the payload came from the GitHub App installation belonging to `repository_owner` (the org/user in the payload) - it proves the payload is genuinely from that repository's installation, not that the `sha` inside it is unique to that repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [4](#0-3) 

The dispatcher then hands the raw payload straight to `StatusHandler.call`:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Exploit flow: an attacker who owns/forks a repository that shares git history with the target stack B's tracked repository (so a specific commit sha is identical in both, which is a normal outcome of forking - git commit shas are deterministic over content and are not attacker-forgeable, but they are trivially *shared* by any fork of the upstream history) installs the Shipit GitHub App on their own repo/org (a normal, unprivileged self-service action) and sets a commit status via GitHub's API on their own repo for that shared sha with `state: success`. GitHub delivers a webhook signed by the attacker's own installation secret; `verify_signature` legitimately passes because it only checks that the payload matches *that org's* installation, not that the `sha` is scoped to that org's repositories. `StatusHandler#process` then finds and updates *every* `Commit` row across the entire database with that sha - including the row in stack B - via `Commit.where(sha: params.sha)`.

`Commit#blocked?` for later commits in stack B depends on whether any reachable, undeployed, older commit is `blocking?`:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [6](#0-5) 
and `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [7](#0-6) . Once the forged `success` status lands on the blocking commit in stack B, `blocking?` flips to false for it, so `blocked?` flips to false for every later commit, restoring `deployable?` and enabling `Stack#next_commit_to_deploy` / continuous delivery to deploy commits that were previously gated by stack B's own CI blocking-status requirement.

Existing guards do not stop this: `verify_signature` authenticates the org, not the sha-to-repo binding; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership of the sha; `drop_unhandled_event` only checks the event type is registered; there is no model-level uniqueness constraint tying `sha` to a single stack/repository.

### Impact Explanation
An unauthenticated-relative-to-stack-B attacker can, using only their own legitimately-authenticated GitHub App installation on an unrelated repository, write a `Status` record and mutate the deployability state of another tenant's stack, bypassing that tenant's CI blocking-status safety gate and enabling deployment of code that never passed its own required check. This is a cross-tenant write authorized by a payload scoped to a different repository - matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy." The attack is repeatable against any stack/commit whose sha is reachable in a repository the attacker can control commit history for (typically forks of the tracked upstream repo), and can be repeated for every future blocking commit as long as sha reuse across the fork lineage continues.

### Likelihood Explanation
Preconditions: the target stack must configure `blocking_statuses` (`ci.blocking` in `.shipit.yml`), and the attacker needs a repository (e.g. a fork) that shares at least one commit sha with the target's undeployed range, plus their own Shipit GitHub App installation (a normal, self-service, unprivileged step for any GitHub user on a public multi-tenant Shipit deployment). No Shipit secrets, sessions, or team membership are required. Feasibility is moderate-to-high in the common case of Shipit tracking a public/open-source repository with forks, and requires no cryptographic sha forgery - just sha reuse via natural git history sharing.

### Recommendation
Scope `StatusHandler#process` (and `Commit.where(sha: ...)`) to the repository named in the verified payload, mirroring the pattern used by every other handler: resolve `repository = Repository.from_github_repo_name(params.repository.full_name)` and restrict the commit lookup to `repository.stacks.commits.where(sha: params.sha)` (or equivalent join through `stack: :repository`), rejecting/ignoring any commit whose stack's repository does not match the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "cross-repo sha collision unblocks a different stack's blocking commit" do
  blocking_commit = shipit_commits(:soc_second)   # stack: soc, blocking_statuses configured
  blocked_commit   = shipit_commits(:soc_third)

  blocking_commit.statuses.delete_all
  assert_predicate blocking_commit, :pending?
  assert_predicate blocking_commit, :blocking?
  assert_predicate blocked_commit, :blocked?         # BEFORE: gated

  # Attacker's repo shares the same sha (e.g. a fork of soc's upstream repo)
  attacker_repo_full_name = "attacker/evil-fork"
  payload = {
    "sha" => blocking_commit.sha,
    "state" => "success",
    "context" => blocking_commit.stack.blocking_statuses.first,
    "repository" => { "full_name" => attacker_repo_full_name },
    "branches" => [{ "name" => "master" }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  blocking_commit.reload
  blocked_commit.reload
  assert_predicate blocking_commit, :success?
  refute_predicate blocking_commit, :blocking?
  refute_predicate blocked_commit, :blocked?         # AFTER: gate bypassed for stack `soc` by a payload scoped to `attacker/evil-fork`
end
```
This demonstrates the binding `commit.stack.repository.full_name == payload['repository']['full_name']` is false yet `StatusHandler#process` still writes the status, flipping `Commit#blocked?` for stack `soc`'s later commit.
