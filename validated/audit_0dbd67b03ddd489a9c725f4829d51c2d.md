### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (with a fallback to `organization.login`), but every webhook handler (`PushHandler`, `CheckSuiteHandler`, etc.) resolves the actual `Repository`/`Stack` to act on using the independent `repository.full_name` field. Because Shipit supports one webhook secret per GitHub organization, an attacker who legitimately controls a GitHub organization/repo configured in the same Shipit instance can produce a validly-signed payload for their own org while pointing `repository.full_name` at a stack belonging to a different, more privileged organization, causing Shipit to treat the forged event as authentic for that unrelated repository.

### Finding Description
The signature check picks the verification secret using the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — both attacker-supplied JSON fields, not cryptographically bound to anything else in the payload. `Shipit.github(organization: repository_owner)` then looks up a per-organization `GithubApp`/webhook secret (Shipit explicitly supports multiple orgs, each with its own `webhook_secret`, as documented in `test/dummy/config/secrets_double_github_app.yml`).

Once the signature is confirmed valid for *that* organization's secret, the raw params are dispatched unmodified to handlers: [3](#0-2) 

Every handler, however, determines *which repository/stack the event applies to* using a completely different, unchecked field: [4](#0-3) 

`Repository.from_github_repo_name` simply splits `owner/name` out of `repository.full_name` and looks up the DB record — with no comparison back to the `repository.owner.login` value that was used to select the verification secret: [5](#0-4) 

This breaks the intended equality: **organization that authenticated the request (`repository.owner.login` used to pick the secret) ≠ repository that is actually written to (`repository.full_name` used to pick the `Stack`)**. Nothing in `WebhooksController` or `Handler` enforces that `repository.full_name` must start with `repository_owner`.

### Impact Explanation
An attacker who controls (or has been granted a legitimate, low-privilege) GitHub organization/App integration that is separately configured in the same multi-tenant Shipit deployment can craft and correctly sign (using their own org's known webhook secret) a payload whose `repository.full_name` names a stack belonging to a different, unrelated, more sensitive organization. Concrete handler effects reachable this way:
- `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for a stack the attacker has no GitHub access to, forcing Shipit to sync/refresh an unrelated stack's git history on attacker-chosen `after` SHA claims. [6](#0-5) 
- `CheckSuiteHandler` will schedule check-run refreshes for commits on an unrelated stack. [7](#0-6) 

Because sync/check-run refresh can influence which commits are considered "green"/mergeable and eligible for continuous deployment on the target stack, this crosses the organization-authorization boundary that Shipit's per-org webhook secrets are meant to enforce, matching the "escalation into authorization scoping" class of impact.

### Likelihood Explanation
Requires the attacker to control one legitimately-configured (but otherwise unprivileged w.r.t. the target) GitHub organization/App entry in the same Shipit deployment — i.e., knowledge of that org's own webhook secret, which they hold legitimately as that org's owner. No access to the victim org, its secret, its repository, or a Shipit session/API token is required. This exactly mirrors the "low likelihood, high impact ⇒ Medium/High" characterization of the original report: the precondition (existing multi-org deployment) is uncommon, but once present the crossover is trivial and requires no privileged credential on the victim side.

### Recommendation
Bind the two fields together before dispatch: after `verify_signature` succeeds, assert that `repository.full_name` (or `repository.owner.login`) used by handlers is the same organization whose secret validated the HMAC, e.g. reject the request in `WebhooksController#verify_signature`/`#create` if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Alternatively, resolve the target `Repository` once in the controller using the already-authenticated `repository_owner`, and pass that resolved model to handlers instead of re-parsing `repository.full_name` independently inside `Handler#repository_name`.

### Proof of Concept
1. Shipit is deployed with a multi-org GitHub config (as in `test/dummy/config/secrets_double_github_app.yml`), containing `OrgAttacker` (attacker is the org owner/App installer) and `OrgVictim` (has a stack `victim-org/victim-repo` registered in Shipit).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": {"login": "OrgAttacker"},
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgAttacker_webhook_secret, body)` using the secret they legitimately hold for `OrgAttacker`, and sends it to `POST /github/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgAttacker"`, fetches `Shipit.github(organization: "OrgAttacker")`, and the signature validates successfully. [1](#0-0) 
5. `PushHandler.call(params)` is invoked; `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, resolving `OrgVictim`'s `Stack` and calling `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, even though the attacker has no relationship whatsoever with `OrgVictim`. [4](#0-3) [6](#0-5)
