### Title
CCMenu token minted for one stack silently authorises read access to every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token that the UI presents as being scoped to a single stack, but the underlying `ApiClient` record is never bound to that `stack_id`. Because `Api::CCMenuController` also bypasses the stack-scoping helper used elsewhere in the API, that same token grants read access to every stack in the installation, not just the one it was issued for. This is the shipit analog of the reported bug class: a credential/permission is authorised for one target (a specific stack) but is actually usable against a different target (any stack) - the same "authorized-for-X, executed-against-Y" mismatch as `transferFrom` being invoked with the wrong holder of the allowance.

### Finding Description
`CCMenuUrlController#client` mints (or reuses) a single, unscoped `ApiClient`: [1](#0-0) 

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

Note that no `stack_id` is set, even though the endpoint is reached per-stack (`/ccmenu/*stack_id`) and hands back a URL containing that stack's id plus the token: [2](#0-1) 

Elsewhere, `ApiClient#stack_id` is exactly the mechanism the engine uses to bind a token to a single stack - `Api::BaseController#stacks` enforces it: [3](#0-2) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

But `Api::CCMenuController` overrides `#stack` and completely skips this scoping, resolving the stack directly from client-supplied params instead of through the `current_api_client`-scoped collection: [4](#0-3) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only validates the flat `permissions` array (`read:stack`) via `ApiClient#check_permissions!`, and never checks whether the token is scoped to the specific `stack_id` in the request: [5](#0-4) 

The binding that should hold is:
`stack the token authorises (the one it was minted for) == stack the token can touch (via Api::CCMenuController#show)`

Because the `ApiClient` is created without `stack_id` and `Api::CCMenuController#stack` bypasses the scoped `stacks` collection, this equality is broken: the token authorised for stack A can be replayed against `stack_id` = B, C, D... for any stack, since `Stack.from_param!` performs no ownership check against `current_api_client`.

### Impact Explanation
Any holder of a single "CCMenu Client" token (obtained from the CCMenu URL generated for one stack - these URLs/tokens are designed for embedding in third-party CI-status dashboards/widgets, i.e. environments where leakage is likely) can enumerate and read the deploy/build status (`lastBuildStatus`, `activity`, `lastBuildTime`, `webUrl`, lock state) of every stack in the Shipit instance by simply varying `stack_id` in `GET /api/stacks/*stack_id/ccmenu`, regardless of which stack the token was actually issued for. This is an authorization-scope escalation of a token beyond its intended stack boundary, matching the "unauthorized read of stack state" category.

### Likelihood Explanation
No privileged access is required beyond obtaining one legitimately-issued CCMenu token (which any authenticated Shipit user with access to a single stack can mint via `CCMenuUrlController#fetch`, or which may leak through third-party CI dashboard tooling this feature is explicitly designed to feed). Once obtained, exploitation is a single unauthenticated-permission-scope HTTP GET with an arbitrary `stack_id` - no signature, secret, or additional credential is needed.

### Recommendation
- Persist the `stack_id` on the `ApiClient` created in `CCMenuUrlController#client` (mirroring the pattern already enforced by `Api::BaseController#stacks`), so each CCMenu token is bound to exactly the stack it was generated for.
- Remove the `Api::CCMenuController#stack` override, or make it go through the scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!` directly, so tokens scoped to a stack cannot be replayed against other stacks.

### Proof of Concept
1. As User A with access to `stack-A`, visit `stack-A`'s CCMenu URL (`GET /ccmenu/stack-A` → `CCMenuUrlController#fetch`), obtaining `{ ccmenu_url: ".../api/stacks/stack-A/ccmenu?token=<TOKEN>" }`.
2. Reuse `<TOKEN>` against a different stack the token was never issued for:
   `GET /api/stacks/stack-B/ccmenu?token=<TOKEN>`
3. Observe `200 OK` with `stack-B`'s build status/activity/lastBuildTime returned, because `Api::CCMenuController#stack` resolves `stack_id` directly from `Stack.from_param!` without checking `current_api_client.stack_id`, and the `ApiClient` created in step 1 never had `stack_id` set in the first place.
