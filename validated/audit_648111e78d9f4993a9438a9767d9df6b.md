### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while all event handlers act on `repository.full_name` — attacker-selectable org lets signature checks be bypassed for actions on any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects **which GitHub App config's secret** to use for HMAC verification based on `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . Every event handler, however, resolves the actual `Stack`/`Repository` to act on from a **different** JSON field, `repository.full_name` [3](#0-2) . These two fields are never cross-checked against each other, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever the selected organization has no `webhook_secret` configured [4](#0-3) . Since `webhook_secret` is explicitly documented/scaffolded as optional and defaults to `nil` in templates and multi-org example configs [5](#0-4) [6](#0-5) , this breaks the equality binding: `organization used to select verification secret` (from `repository.owner.login`) `== organization whose repository is actually mutated` (from `repository.full_name`).

### Finding Description
`verify_signature` uses the attacker-controlled `repository_owner` value purely to pick a `GitHubApp` instance/secret:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [7](#0-6) 

`repository_owner` is read straight from the JSON body, not from any authenticated context:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Meanwhile, the base `Handler#stacks` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers, etc.) resolves the target repository from `repository.full_name`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

An unauthenticated caller controls the entire raw POST body, so nothing stops `repository.owner.login` (used only for secret selection) from disagreeing with `repository.full_name` (used to select which stack is mutated). Combined with the fact that in a Shipit deployment with multiple configured GitHub organizations it is normal/documented for individual orgs to have `webhook_secret` left blank [8](#0-7) , and that `verify_webhook_signature` treats a blank secret as "always verified":
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

an attacker who knows (or picks) any configured organization key without a webhook secret can send a forged webhook payload where `repository.owner.login`/`organization.login` names that unsecured org (satisfying `verify_signature`), while `repository.full_name` names an entirely different, victim repository whose stacks are actually mutated by the handler.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding: signature verification authenticates against org A's key, but the write happens against org B's repository/stack. Concretely reachable unauthenticated writes on a victim stack include:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: ...)`, queuing `GithubSyncJob` for the victim stack [9](#0-8) .
- `StatusHandler#process` creates a `Status` record with an attacker-chosen `state` (e.g. `success`) for any existing commit sha in the victim stack's history via `commit.create_status_from_github!(params)` [10](#0-9) . Because `Status` creation schedules continuous delivery and merge processing (`schedule_continuous_delivery`, `stack.schedule_merges`) [11](#0-10) [12](#0-11) , and stacks with `continuous_deployment: true` auto-trigger a deploy once a commit's status becomes `success` [13](#0-12) , this path can be used to force/expedite an **unauthorized deploy** on a victim stack that uses continuous deployment, by faking a passing CI status for a commit — without ever presenting a valid signature for that victim organization.

This satisfies the report's "High" bar: escalation into unauthenticated write of stack/task state, and potentially into "unauthorized deploy" territory (Critical bar) for CD-enabled stacks.

### Likelihood Explanation
Requires: (1) the Shipit deployment configured for multiple GitHub organizations (a documented, supported feature [8](#0-7) ) where at least one configured organization key has no `webhook_secret` set (also documented as "optional") [5](#0-4) ; and (2) the victim repository/stack tracked under a different organization. Given `webhook_secret` is optional by design and default config templates ship with it blank, this is a realistic, low-effort misconfiguration an unprivileged internet attacker can exploit with a single crafted HTTP POST to `/webhooks`, no credentials required.

### Recommendation
Bind the signature-verification organization to the same field used for repository resolution, and reject when they diverge:
- Verify the webhook signature using the organization actually derived from `repository.full_name` (or reject the request if `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`).
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations that have write-capable stacks; require an explicit opt-in/warning, or enforce that a webhook secret is mandatory once any stack exists for that org.
- Alternatively, verify against every configured organization's secret (or the specific org owning the resolved `Repository`), not the attacker-suppliable `repository.owner.login` field.

### Proof of Concept
Given a `config/secrets.yml` with two orgs, e.g.:
```yaml
github:
  attacker-org:
    app_id: 1
    installation_id: 1
    webhook_secret: # nil - unset
  victim-org:
    app_id: 2
    installation_id: 2
    webhook_secret: s3cr3t
```
and a Shipit stack tracking `victim-org/victim-repo`, an unauthenticated attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, ignored because attacker-org has no secret

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<existing sha of a commit on victim stack>",
  "state": "success",
  "context": "ci/forged"
}
```
`verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature` header [4](#0-3) . `StatusHandler` then resolves the target commit/stack from `repository.full_name` = `"victim-org/victim-repo"` [3](#0-2)  and creates a forged `success` status on the victim stack, potentially triggering an unauthorized continuous deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
