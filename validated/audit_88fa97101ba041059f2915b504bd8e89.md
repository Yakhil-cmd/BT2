## Finding: MultiKey / MultiEd25519 authenticators allow a single private key to satisfy a k‑of‑n signature threshold via duplicate public key entries

### Title
Missing duplicate-public-key check in `MultiKey`/`MultiEd25519` construction lets a single signer satisfy the k-of-n admission threshold - (File: `types/src/transaction/authenticator.rs`, `aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move`)

### Summary
Aptos's native k-of-n signature schemes (`MultiKey`/`MultiKeyAuthenticator` and legacy `MultiEd25519`) verify signatures per bitmap *index*, not per distinct public key. Neither `MultiKey::new` nor the Move-side `multi_key::new_multi_key_from_single_keys` reject duplicate public keys in the key list. Because the bitmap only guarantees each *index* is used once, a public key that appears twice in the list can be "signed for" twice using the exact same signature bytes, letting one private-key holder alone satisfy a threshold that was intended to require `k` distinct approvers.

### Finding Description
`MultiKey::new` only checks count bounds, never uniqueness of public keys: [1](#0-0) 

The Move-side constructor used when rotating an account's auth key to a multi-key scheme has the same gap: [2](#0-1) 

`MultiKeyAuthenticator::new` only prevents a duplicate *bitmap index*, not a duplicate *public key* at two different indices: [3](#0-2) 

Verification (`MultiKeyAuthenticator::verify` / `to_single_key_authenticators`) independently checks each `(index, signature)` pair against `public_keys[idx]`, with no cross-index deduplication of the underlying key material: [4](#0-3) 

The existing unit test actually demonstrates the exact failure mode: a `MultiKey` is built with keys `[sender0_pub, sender1_pub, sender1_pub]` (index 1 and 2 are the *same* key) and threshold 2. Supplying the *same* `signature1` (from `sender1`'s private key alone) at indices 1 and 2 passes full transaction signature verification with `signed_txn.verify_signature().unwrap()`, without any participation of `sender0`: [5](#0-4) 

The legacy `MultiEd25519Signature::verify_arbitrary_msg` has the identical structural gap: it counts `bitmap` ones against `threshold`, and verifies each bit's slot against `public_key.public_keys[bitmap_index]`, with no rejection of duplicate public keys in the `MultiEd25519PublicKey`: [6](#0-5) 

This breaks the invariant that a k-of-n authenticator (used to admit/authorize a transaction as validly signed by the intended approval set) requires signatures from `k` *distinct* key holders. If a MultiKey/MultiEd25519 account is set up (e.g. via `rotate_authentication_key_from_public_key` / `rotate_authentication_key`, or account creation) with a repeated key entry — whether by wallet UI mistake, by a malicious co-owner who controls the key-list construction, or by a service that lets a user submit an arbitrary key list for a "k-of-n social recovery/approval" account — a single key holder who is duplicated into ≥`k` of the slots can single-handedly pass VM admission for that account's transactions, even though the design intent (as consumed by any protocol/dApp relying on that threshold) is that `k` distinct parties approved it.

### Impact Explanation
This is an authenticator/approval-set-confusion at the transaction admission boundary: the on-chain authentication-key derivation and signature verification (both consulted during mempool/VM validation) accept a signing material set that does not represent `k` distinct approvers, even though the account was nominally configured as a k-of-n scheme. Any downstream system (custodial/non-custodial hybrid wallets, social-recovery wallets, DAOs/guardians using native MultiKey instead of `multisig_account.move`) that relies on Aptos's native k-of-n primitive to enforce "at least `k` independent signers approved this transaction" can have that guarantee silently bypassed by one signer occupying multiple slots, resulting in unauthorized execution under the wrong effective signer set.

### Likelihood Explanation
Exploitability requires that a MultiKey/MultiEd25519 account be constructed with a duplicate key entry — which is entirely permitted by current validation (`MultiKey::new`, `multi_key::new_multi_key_from_single_keys`, `MultiEd25519PublicKey`/`check_and_get_threshold`), with no on-chain or client-side guard rejecting it. This can happen via innocuous wallet bugs (accidentally including the same key twice while building a "guardian list"), or deliberately by a party who has influence over the key list (e.g., a co-signer supplying their own key twice while claiming distinct "backup" slots) to later exercise sole control. Because the framework performs no uniqueness check anywhere in the stack (Rust `MultiKey`, Move `multi_key`, `MultiEd25519`), the bug is systemic rather than incidental.

### Recommendation
Reject duplicate public keys when constructing a `MultiKey`/`MultiEd25519PublicKey` (both in `types/src/transaction/authenticator.rs::MultiKey::new` and in `aptos_std::multi_key::new_multi_key_from_single_keys`, plus the corresponding `MultiEd25519PublicKey` constructors), so a k-of-n scheme provably requires `k` distinct keys. This should be enforced both at authentication-key derivation time (so an account cannot even be created/rotated into this state) and defensively during authenticator verification.

### Proof of Concept
The existing repo test already constitutes a PoC of the flaw (only the assertion/interpretation differs): build `MultiKey::new(vec![sender0_pub, sender1_pub, sender1_pub], 2)`, sign the transaction only with `sender1`'s key, submit that one signature at bitmap indices 1 and 2, and observe `SignedTransaction::verify_signature()` succeed with no participation from `sender0`: [7](#0-6)

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }

    fn verify_arbitrary_msg(
        &self,
        message: &[u8],
        public_key: &MultiEd25519PublicKey,
    ) -> Result<()> {
        // NOTE: Public keys need not be validated because we use ed25519_dalek's verify_strict,
        // which checks for small order public keys.
        match bitmap_last_set_bit(self.bitmap) {
            Some(last_bit) if (last_bit as usize) < public_key.public_keys.len() => (),
            _ => {
                return Err(anyhow!(
                    "{}",
                    CryptoMaterialError::BitVecError("Signature index is out of range".to_string())
                ))
            },
        };
        let num_ones_in_bitmap = bitmap_count_ones(self.bitmap);
        if num_ones_in_bitmap < public_key.threshold as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Not enough signatures to meet the threshold".to_string()
                )
            ));
        }
        if num_ones_in_bitmap != self.signatures.len() as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Bitmap ones and signatures count are not equal".to_string()
                )
            ));
        }
        let mut bitmap_index = 0;
        // TODO: Eventually switch to deterministic batch verification
        for sig in &self.signatures {
            while !bitmap_get_bit(self.bitmap, bitmap_index) {
                bitmap_index += 1;
            }
            let pk = public_key
                .public_keys
                .get(bitmap_index)
                .ok_or_else(|| anyhow::anyhow!("Public key index {bitmap_index} out of bounds"))?;
            sig.verify_arbitrary_msg(message, pk)?;
            bitmap_index += 1;
        }
        Ok(())
    }
