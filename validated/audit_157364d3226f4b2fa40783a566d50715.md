### Title
Unauthenticated front-run of `set-burnchain-parameters` allows an unprivileged caller to fix PoX-5's reward-cycle geometry before boot — ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
The external report's core bug class is "an initializer that should be privileged/one-shot is instead callable by anyone." In `pox-5.clar`, `set-burnchain-parameters` is exactly such a one-shot initializer: it is gated only by a `configured` boolean, with **no `contract-caller`/`tx-sender` authorization check**, unlike every other admin-mutating entrypoint in the same contract (`set-bond-admin`, `set-pause-admin`, `pause-rewards`, `setup-bond` all `asserts!` on a stored admin principal).

### Finding Description
`set-burnchain-parameters` sets `first-burnchain-block-height`, `pox-prepare-cycle-length`, `pox-reward-cycle-length`, `first-pox-5-reward-cycle`, and `first-bond-period-cycle` — the parameters that every reward-cycle/unlock-height computation in pox-5 (`burn-height-to-reward-cycle`, `reward-cycle-to-burn-height`, `bond-period-to-burn-height`, etc.) depends on: [1](#0-0) 

Compare this to the sibling admin functions in the same file, all of which check the caller against a stored principal before mutating state: [2](#0-1) [3](#0-2) 

`set-burnchain-parameters` has no such `asserts!`. The only guard is the `configured` data-var, which is `false` at contract deploy and only becomes `true` after the first successful call — so the "first caller wins," and that caller need not be any privileged account. Test helpers explicitly document that this function is meant to be called once by an admin/deployer at boot time, e.g.: [4](#0-3) 

but nothing in the contract itself enforces that only the deployer or boot-code principal can call it.

### Impact Explanation
If an unprivileged account races the legitimate setup transaction (or the deployment simply does not immediately call `set-burnchain-parameters` in the same block as boot), it can call this function first with attacker-chosen `first-burn-height`, `prepare-cycle-length`, `reward-cycle-length`, and `begin-pox5-reward-cycle` values. Because every unlock-height and reward-cycle boundary in pox-5 is derived from these parameters, a malicious configuration can:
- Shift the reward-cycle/prepare-cycle boundaries so that `unlock-burn-height` computed for existing/future `stack-stx`/`register-for-bond` calls resolves to the wrong height, permanently freezing STX beyond the staker's intended lock period or unlocking it earlier than agreed (breaking the "unlocked value that was never authorised" and "permanent freezing" equalities).
- Desynchronize pox-5's cycle math from the node's actual PoX-5 lock logic in `pox_lock_v5`/`pox_rollover_v5` (`pox-locking/src/pox_5.rs`), which trusts the contract's returned `unlock-burn-height` verbatim: [5](#0-4) 

Because `configured` can only be set once and there is no admin recovery path visible in this file, a bad initial configuration is not something a later `bond-admin` call can fix — it is baked in for the contract's lifetime, matching the report's "permanent" freezing/misconfiguration class rather than a transient issue.

### Likelihood Explanation
Exploitability depends entirely on whether the node's boot sequence issues `set-burnchain-parameters` atomically within the same block/transaction that deploys `pox-5` (as `sip-031`'s initialization is shown to do via a single synthetic boot transaction in `clarity.rs`), or whether there is a window where the contract is deployed and callable before that setup transaction lands. I could not fully confirm, within the tool budget, whether the stacks-node boot path (`stackslib/src/clarity_vm/clarity.rs`, which references `set_burnchain_parameters`/`set-burnchain-parameters` seven times) invokes this call atomically at boot in the same manner as SIP-031's mint, or as a separate, front-runnable transaction. Test helpers (`initPox5`/`initBootPox5` in `pox-5-helpers.ts`) call it as an ordinary `txOk` after deployment, which is at least evidence that in test/devnet contexts it is a separate, callable-by-anyone transaction.

### Recommendation
Add an authorization check to `set-burnchain-parameters` consistent with the rest of the contract's admin functions — e.g., restrict it to the boot-code principal (`is-eq contract-caller (as-contract tx-sender)` if invoked via a synthetic boot transaction) or to `bond-admin`/a dedicated "genesis admin" role — rather than relying solely on the `configured` one-shot flag, so that whichever caller happens to submit the first transaction cannot unilaterally fix the reward-cycle geometry for the entire contract's lifetime.

### Proof of Concept
Not independently confirmed as exploitable end-to-end because the boot-atomicity question above is unresolved with available tools. The concrete, verifiable root cause is:
1. `pox-5.clar` `set-burnchain-parameters` (lines 429–449) performs no `contract-caller`/`tx-sender` check, only the `configured` guard.
2. All sibling privileged setters (`set-bond-admin`, `set-pause-admin`, `pause-rewards`, `setup-bond`) do perform such a check against a stored admin principal (lines 451–532), confirming the omission on `set-burnchain-parameters` is inconsistent with the contract's own security model rather than an intentional public function.

If a Devin session with terminal/build access is available, the boot-atomicity question (whether `set-burnchain-parameters` is called in the same transaction as pox-5 deployment, analogous to the SIP-031 mint sequence in `clarity_vm/clarity.rs`) should be verified directly against `stackslib/src/clarity_vm/clarity.rs` and `chainstate/stacks/boot/mod.rs` to determine whether this is exploitable on a live/regtest node or is a devnet/testing-only concern.
