### Title
Regulated-coin `DenyCapV2` holder can permanently brick a coin type by enabling global pause and freezing/burning the cap - (File: crates/sui-framework/packages/sui-framework/sources/coin.move)

### Summary
The Biconomy finding is a class of bug where a role holding a "pause" capability can enable a pause and then permanently destroy/renounce its own capability, leaving the paused state irreversible even to the contract owner. Sui's native `sui::coin` deny-list v2 mechanism has the same shape: the `DenyCapV2<T>` capability can both enable a global pause and is itself a freely transferable/freezable object (`has key, store`), with no binding or backup authority (e.g. `TreasuryCap`) able to override or disable the pause once the cap is gone.

### Finding Description
`DenyCapV2<T>` is defined with `key, store` abilities and holds the `allow_global_pause` flag: [1](#0-0) 

Enabling and disabling the global pause both require a `&mut DenyCapV2<T>` reference — there is no alternate path (no `TreasuryCap`-based override, no owner escape hatch): [2](#0-1) 

Because `DenyCapV2<T>` has `store`, its holder can call the generic `transfer::public_freeze_object` on it (or transfer it to an unrecoverable/burn address) at any time — this is standard, unprivileged framework functionality available to any object with `store`, not a defect by itself. Once frozen, the object becomes permanently immutable, so no future transaction can ever obtain a `&mut DenyCapV2<T>` for it, and `deny_list_v2_disable_global_pause` can never succeed again for that coin type. This mirrors the Biconomy bug exactly: `pause()` + `renouncePauser()` (here: `deny_list_v2_enable_global_pause()` + `public_freeze_object(deny_cap)`) yields an irreversible frozen state with no admin recourse.

The regulatory model documentation confirms there is no separate authority: only the `DenyCapV2` bearer controls the global pause switch, and disabling it is the only way to restore token liquidity for holders: [3](#0-2) 

### Impact Explanation
Once global pause is enabled and the `DenyCapV2<T>` is frozen (or sent to an unrecoverable address), all addresses become permanently unable to use the regulated coin as a transaction input, and, from the next epoch, unable to receive it either. There is no code path — not `TreasuryCap`, not any governance object — that can clear the pause once the sole authorizing capability is gone. This is a **permanent fund lock** for every holder of that coin type, matching the allowed High-severity impact ("permanent fund lock, harmful smart-contract behavior").

### Likelihood Explanation
Any regulated-coin issuer (the package publisher who receives `DenyCapV2<T>` from `create_regulated_currency_v2`) can trigger this unilaterally with two ordinary, permissionless framework calls — `coin::deny_list_v2_enable_global_pause` and `transfer::public_freeze_object` — no special privilege beyond normal cap ownership is needed, matching the "package publisher" attacker model allowed by the scope. This can be done accidentally (e.g., mistakenly freezing the cap for storage/immutability reasons) or maliciously.

### Recommendation
Do not allow a "reversible-state" capability like `DenyCapV2` to be frozen or otherwise made permanently inaccessible while a pause is active. Options: (1) disallow calling `deny_list_v2_enable_global_pause` unless the cap is guaranteed to remain a mutable, owned object (hard to enforce on-chain); (2) provide a secondary "break-glass" authority (e.g., the `TreasuryCap` or a registry-based capability) that can force-disable the global pause even without the `DenyCapV2`; (3) document strongly (as already partially done) that `DenyCapV2` must never be frozen/burned, and consider adding an explicit runtime check/warning when `public_freeze_object` is called on this type — though a full fix likely needs a framework-level design change (e.g., decoupling "ability to pause" from "ability to unpause" and adding a fallback holder for the latter).

### Proof of Concept
1. Publisher creates a regulated coin via `coin::create_regulated_currency_v2`, receiving `DenyCapV2<T>{allow_global_pause: true}`.
2. Publisher calls `coin::deny_list_v2_enable_global_pause<T>(deny_list, &mut deny_cap, ctx)` — global pause active immediately for inputs, next epoch for receipt.
3. Publisher calls `sui::transfer::public_freeze_object(deny_cap)` (or sends `deny_cap` irrecoverably, e.g., to `@0x0`).
4. From this point, no transaction can obtain `&mut DenyCapV2<T>`, so `coin::deny_list_v2_disable_global_pause` can never be executed for `T` again.
5. Every existing and future holder of coin type `T` is permanently unable to use or receive it — full, irreversible fund lock for that coin, with no recovery path available to the `TreasuryCap` holder, protocol admins, or anyone else.

Note: I was not able to fully verify whether there is any framework-level guard (e.g., a lint or runtime check) that specifically blocks freezing a `DenyCapV2` object, since `transfer::public_freeze_object`'s full body wasn't retrieved before the tool budget ran out — this should be double-checked in a follow-up session to confirm no such protection already exists.

    deny_list: &mut DenyList,
    deny_cap: &mut DenyCapV2<T>,
    ctx: &mut TxContext,

    assert!(deny_cap.allow_global_pause, EGlobalPauseNotAllowed);

```text
### Global pause switch

Regulated coin objects include an `allow_global_pause` Boolean field. When set to `true`, the bearer of the `DenyCapV2` object for the coin type can use the `coin::deny_list_v2_enable_global_pause` function to pause coin activity indefinitely. Immediately upon the bearer initiating the pause, the network disallows the coin type as input for any transactions. At the start of the next epoch (epochs last approximately 24 hours), the network additionally disallows all addresses from receiving the coin type.

When the bearer of the `DenyCapV2` object for the coin type removes the pause using `coin::deny_list_v2_disable_global_pause`, the coins are immediately available to use again as transaction inputs. Addresses cannot receive the coin type, however, until the following epoch.

The global pause functionality does not affect the deny list for the coin. After clearing the pause for the coin, any addresses included in the deny list are still unable to interact with the coin.
```
