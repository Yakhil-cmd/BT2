### Title
Webhook authentication is keyed on `repository.owner.login`, but every handler routes and mutates state using the unrelated `repository.full_name` field, allowing a forged payload to act on a repository whose owner never authenticated the request - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [1](#0-0) [2](#0-1) 

However, `verify_webhook_signature` in `GithubApp` (`lib/shipit/github_app.rb`) unconditionally returns `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every webhook `Handler` determines which actual repository/stack to mutate using a completely different field, `repository.full_name`, which is never cross-checked against the `repository.owner.login`/organization used for authentication: [4](#0-3) 

This is the same bug class as the MagicLP report: a value that is checked ("`repository.owner.login`" as the authorization key) is decoupled from the value that is actually acted upon ("`repository.full_name`"), and an attacker can create/exploit an inconsistency between them.

### Finding Description
Shipit explicitly supports multiple GitHub organizations/Apps configured under `github:` in secrets, each with an independent `webhook_secret` (demonstrated by the fixture `test/dummy/config/secrets_double_github_app.yml`, where multiple orgs can each be configured, and `webhook_secret` may be left blank/`nil`): [5](#0-4) 

The intended binding is: **the organization whose secret validated the signature == the owner of the repository whose state is mutated by the payload**.

- The *authentication* side only ever inspects `repository.owner.login` (or `organization.login`) to select which org's `webhook_secret` to HMAC-verify against: [2](#0-1) 
- The *execution* side, in every `Handler` subclass, resolves the target `Repository`/`Stack` purely from `repository.full_name` (or `params.repository.full_name`), independent of whatever the verification step determined: [4](#0-3) [6](#0-5) 

Because `verify_webhook_signature` returns `true` with no cryptographic check at all whenever the resolved organization has a blank `webhook_secret`, an attacker who knows (or can guess/observe) that *any* organization configured in Shipit's `github:` secrets has no `webhook_secret` set can:
1. Set `repository.owner.login` (and/or `organization.login`) in the forged JSON body to that no-secret organization, so `verify_signature` resolves an `GithubApp` instance whose `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header value.
2. Set `repository.full_name` in the same JSON body to any *other* organization/repository that Shipit actually tracks (which may have stacks, review-stacks, continuous deployment enabled, etc.).
3. Send the forged payload; `verify_signature` passes (secret is blank), and the handler dispatched by `event` acts entirely on the attacker-chosen `repository.full_name`, oblivious to the fact that authentication was performed against an unrelated organization.

This breaks the equality `verified_organization == mutated_repository.owner` and gives an unauthenticated party write access to any handler's side effects for the real, secret-protected repository.

### Impact Explanation
Concretely reachable, unauthorized actions include:
- **Unauthorized deploy via forged `pull_request` events.** `ReviewStackAdapter#stack_attributes` builds a new `ReviewStack` using attacker-controlled `params.pull_request.head.ref` for the `repository.full_name` resolved from the forged payload, and `find_or_create!`/`unarchive!` immediately enqueue provisioning (which runs deploy tasks) for that review stack: [7](#0-6) [8](#0-7) 
This satisfies the "unauthorized deploy" impact category, since the attacker is not the owner of the real repository and never possessed its `webhook_secret`.
- **Forged commit status / push events** on the real repository's stacks, letting an attacker mark arbitrary commits as CI-passing (`status` event) or trigger `GithubSyncJob` (`push` event) purely by picking a different, secret-less org for the `owner.login` field while pointing `full_name` at the victim stack.

### Likelihood Explanation
Exploitability depends only on the deployment having at least one configured GitHub organization/App with a blank `webhook_secret` (a state the codebase explicitly supports and ships fixtures for) coexisting with at least one other organization with real stacks. No `ApiClient` token, no `webhook_secret`, no GitHub App private key, and no repository write access are required from the attacker — only knowledge that such a no-secret organization exists in the Shipit instance's configuration (which can often be inferred from setup docs or trial-and-error probing of `X-Hub-Signature` behavior/HTTP status codes).

### Recommendation
- Bind authentication to the exact repository being mutated, not just its owning organization: after resolving the organization from `repository.owner.login`, re-derive and assert that `repository.full_name`'s owner segment matches `repository.owner.login` (and reject mismatches) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for an organization that also has trusted repositories with real secrets configured elsewhere; either require `webhook_secret` for every configured organization or scope unauthenticated bypass strictly to organizations with zero associated repositories/stacks.
- Have `Handler#repository_name`/`Handler#stacks` consume the already-verified repository context from the controller rather than re-reading `repository.full_name` independently from the raw payload.

### Proof of Concept
1. Configure (or identify) a Shipit deployment with two organizations under `github:` secrets — e.g. `NoSecretOrg` (no `webhook_secret`) and `RealOrg` (owns tracked stacks with CI/deploy configured), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Craft a `pull_request` webhook JSON body:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": {
       "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
       "additions": 0, "deletions": 0,
       "head": { "sha": "deadbeef", "ref": "attacker-branch" },
       "user": { "login": "attacker" },
       "assignees": [], "labels": []
     },
     "repository": { "owner": { "login": "NoSecretOrg" }, "full_name": "RealOrg/victim-repo" },
     "organization": { "login": "NoSecretOrg" },
     "sender": { "login": "attacker" }
   }
   ```
3. Send `POST /github/webhooks` with header `X-Github-Event: pull_request` and any (even bogus) `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "NoSecretOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately, bypassing the signature check entirely.
5. `PullRequest::OpenedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name("RealOrg/victim-repo")` and, if review stacks are enabled, creates/provisions a review stack for `victim-repo` on branch `attacker-branch` — an unauthorized deploy triggered without ever presenting `RealOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
