### Title
Cleartext credential disclosure via `--verbose` command-argument logging when `--repo` embeds credentials - (File: pkg/cmd/cmd.go, main.go)

### Summary
git-sync's command runner logs the full, unredacted argv of every git invocation at `-v 5` (and stdout/stderr at `-v 6`), while the code elsewhere is careful to redact the repo URL specifically for other log lines via `redactURL()`. The `fetch` path passes `git.repo` directly as a positional argument into `git.Run(...)`, which is not redacted before being logged by `runWithStdin`. If a user configures `--repo`/`$GITSYNC_REPO` as an HTTPS URL with embedded `user:password` (a supported, "natural" auth mode per the README), raising verbosity to reproduce/diagnose sync issues (a commonly recommended troubleshooting step, directly analogous to setting `-v=4` on the vsphere cloud-provider in the reported CVE) will print the plaintext credential to the git-sync container's stderr logs.

### Finding Description
- `runWithStdin` builds a single loggable command string via `cmdForLog(command, args...)` from the **raw, unredacted** `args` slice and logs it at `V(5)`: [1](#0-0) 
- `fetch()` explicitly redacts the repo for its own log line (`redactURL(git.repo)`), demonstrating the developers know the repo URL can carry secrets, but the actual command executed is built with the **unredacted** `git.repo`: [2](#0-1) 
- That unredacted `args` slice (containing `git.repo`) is what gets passed down into `git.Run(ctx, git.root, args...)`, which flows into `runWithStdin`/`cmdForLog`, defeating the redaction applied to the sibling "fetching" log line.
- `logSafeFlags` only redacts `--repo` and `--credential`/`--password` when logging the **initial flag dump** at startup, not when they are used to build subsequent git command argv: [3](#0-2) 
- The README explicitly documents that "natural" access (URL like `https://user:pass@host/repo`) is a supported, if implicit, auth mode, and separately documents `-v 5` as "Log all executed commands": [4](#0-3) [5](#0-4) 

By contrast, the code base explicitly protects credentials passed via `--credential`/`--username`/`$GITSYNC_PASSWORD` because those are only ever placed on stdin for `git credential approve`/`fill` (never on argv), and stdin content is never logged by `runWithStdin`: [6](#0-5) 
The gap is specific to credentials embedded directly in the `--repo` URL, which end up on the git argv and are logged verbatim at elevated verbosity.

### Impact Explanation
This matches the reported bug class (Cleartext Storage/Disclosure of Sensitive Information via elevated log verbosity) directly: any principal with read access to the git-sync container's stdout/stderr (e.g., `kubectl logs`, a log-aggregation pipeline, or a sidecar with shared log volume) can recover the plaintext username/password embedded in `--repo` whenever `-v >= 5` is set — a verbosity level that is explicitly documented and recommended for diagnosing "all executed commands." This is a real credential-disclosure path reachable purely through supported configuration (no attacker-controlled repo content required), consistent with the "credential or token disclosure" acceptance criterion.

### Likelihood Explanation
Requires: (1) the operator configuring `--repo` with embedded basic-auth credentials rather than `--username`/`--password-file`/`--credential`/`--askpass-url` (all explicitly discouraged in favor of the safer options, implying the URL-embedded form is a known/legacy pattern many users still use for simplicity or with token-in-URL patterns e.g. `https://<token>@github.com/...`), and (2) `-v >= 5`. Both conditions are plausible in real deployments: verbose logging is a standard first troubleshooting step, and embedding a PAT/token in a git URL is a very common lightweight-auth idiom.

### Recommendation
Redact known-sensitive positional/URL arguments (repo URL, and any other args matching credential patterns) before they reach `cmdForLog`/`runWithStdin`, not just in the dedicated "fetching"/"syncing" log lines. Concretely, apply `redactURL()` to any argument in `args` that looks like a URL before constructing the loggable command string in `pkg/cmd/cmd.go`, or have `fetch()` build the args using a redaction-safe wrapper for logging purposes distinct from the actual exec argv.

### Proof of Concept
1. Run git-sync with a URL containing embedded credentials and elevated verbosity:
   ```
   git-sync --repo=https://myuser:supersecretpassword@github.com/org/repo.git \
            --root=/tmp/root --link=link -v 5
   ```
2. Observe git-sync's stderr/stdout logs (as captured by `kubectl logs` or the log driver): the "running command" log entry from `runWithStdin` (`pkg/cmd/cmd.go:65`) will contain `cmd: "git fetch https://myuser:supersecretpassword@github.com/org/repo.git ..."`, exposing the plaintext credential, even though the adjacent "fetching" log entry at `main.go:2003` correctly shows the redacted form.
