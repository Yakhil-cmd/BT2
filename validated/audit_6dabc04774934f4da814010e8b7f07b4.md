### Title
Webhook Organization/Repository Confusion Allows Cross-Repository Forgery of Commit Statuses and Push Events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to validate a signature against using `repository.owner.login` (or `organization.login`) from the untrusted JSON payload, while the handlers that actually act on the payload (e.g. `PushHandler`, and especially `StatusHandler`) key off a *different* field (`repository.full_name`) or, in the case of `StatusHandler`, off no repository field at all. Because the field used to pick the "authenticating organization" is never checked against the field(s) used to determine which repository/commit is mutated, a webhook that authenticates against one (unprotected) organization can be used to write state for a completely different, unrelated repository/stack.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a no-op (returns `true`) whenever that organization has no `webhook_secret` configured, which is explicitly an optional/nil configuration: [3](#0-2) 

Once past `verify_signature`, the actual event handler is invoked with the raw JSON payload: [4](#0-3) 

Handlers derive the repository/stack to act on from a *different* payload field, `repository.full_name`, decoupled from the `repository.owner.login` used for signature selection: [5](#0-4) [6](#0-5) 

Worse, `StatusHandler` does not scope by repository at all — it looks up any `Commit` in the entire database purely by `sha` and writes a status onto it: [7](#0-6) 

This breaks the intended binding:
`organization_verified(payload.repository.owner.login)` must equal `owner(repository_written = payload.repository.full_name)` — but no such check exists anywhere in the webhook pipeline.

### Impact Explanation
An unauthenticated, unprivileged attacker only needs one organization tracked by the Shipit instance to have no `webhook_secret` configured (an explicitly supported/optional configuration) — they need no secret, no App private key, and no Shipit account. By sending `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login` set to that unprotected organization, and `sha` set to a commit sha belonging to an entirely different (protected) organization's repository, the attacker can inject an arbitrary, fabricated commit status (`state`, `context`, `description`, `target_url`) onto that victim commit via `Commit#create_status_from_github!`. Since deploy gating relies on commit statuses (`required_statuses`/`blocking_statuses` in `DeploySpec`), this can be used to force a commit to appear CI-green and enable an otherwise-blocked, unauthorized deploy — a cross-repository write with no credential, matching the Critical/High bar (unauthorized deploy, cross-repository writes). The same organization/repository decoupling also lets an attacker trigger `PushHandler` → `stack.sync_github` for arbitrary tracked stacks belonging to other organizations by simply setting `repository.full_name` to the victim stack while authenticating as the unprotected organization.

### Likelihood Explanation
Any real-world multi-organization Shipit deployment where at least one configured GitHub App/org omits the (documented-as-optional) webhook secret is sufficient. No knowledge of any secret, token, or private key is required — only knowledge of a target commit sha (visible on GitHub) and the name of the unprotected organization/app installed in the same Shipit instance.

### Recommendation
Cross-validate the payload's `repository.full_name` owner against the organization used to select/verify the webhook signature in `WebhooksController#verify_signature`, rejecting mismatches. Additionally, `StatusHandler#process` should scope the `Commit` lookup by the repository resolved from the verified organization/`repository.full_name` (via `stacks`) instead of matching by `sha` alone across the entire installation.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `UnprotectedOrg` (no `webhook_secret`) and `VictimOrg` (has `webhook_secret`, tracks stack `VictimOrg/app`).
2. Obtain the sha of a real commit belonging to `VictimOrg/app` that is pending/failing CI (visible publicly on GitHub).
3. Send, without any signature header (or an arbitrary one):
```
POST /webhooks
X-Github-Event: status

{
  "repository": { "owner": { "login": "UnprotectedOrg" }, "full_name": "VictimOrg/app" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged by attacker"
}
```
4. `verify_signature` resolves `repository_owner` = `UnprotectedOrg`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged "success" status onto `VictimOrg/app`'s commit — potentially unblocking a deploy gated on that status, with zero credentials belonging to `VictimOrg`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
