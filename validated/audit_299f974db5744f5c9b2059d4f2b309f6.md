### Title
Missing duplicate-member check in `r of set` / `weighted and` allows one signature to satisfy multiple required slots - ([File: definition.js])

### Summary
`definition.js`'s `validateDefinition` accepts an `r of set` or `weighted and` address/asset-condition whose `set` array contains the *same* `sig` (or the same nested `address`) entry more than once, without ever checking for duplicates. At authentifier-verification time, `validateAuthentifiers` treats each set element as an independent slot keyed only by its own path (`r.0`, `r.1`, …) and does not deduplicate by pubkey/signer, so a single private key can satisfy two (or more) "independent" slots of the threshold with one signature copied to both authentifier paths. This is the same root-cause pattern as the reported Shardus bug: the check counts satisfied *slots/signatures* instead of counting distinct *signers*.

### Finding Description
`validateDefinition` (definition.js, `r of set` case) only checks structural constraints of the set: [1](#0-0) 
There is no check that the elements of `args.set` are distinct (e.g., that two `sig` entries do not reference the same `pubkey`, or that two `address` entries do not reference the same underlying address). The identical gap exists for `weighted and`: [2](#0-1) 

At verification time, `validateAuthentifiers`'s `r of set` handler independently evaluates every set element at its own path and simply counts how many evaluate true: [3](#0-2) 
The `sig` leaf looks up the authentifier purely by `path`, then verifies it against `pubkey` for the fixed `unit_hash_to_sign`: [4](#0-3) 

Because ECDSA signatures produced by ocore are deterministic per (message hash, private key) (`ecdsaSig.sign(text_to_sign, privKey)` in `signed_message.js`), if the *same* pubkey appears at two different `sig` slots of an `r of set`/`weighted and`, the *same* signature bytes will independently validate at both paths. The attacker only needs to place that identical signature string at both `r.i` and `r.j` authentifier paths to have both slots counted as satisfied, even though only one real signer/key participated. The same effect applies to a `["r of set", {..., set:[["address", A], ["address", A]]}]` construction, since the `address` op is likewise evaluated per-path with no cross-path signer deduplication.

This is not caught anywhere downstream: `arrUsedPaths.length !== Object.keys(assocAuthentifiers).length` in the final check only verifies that all supplied authentifier keys were consumed, not that the underlying signers are distinct: [5](#0-4) 

### Impact Explanation
An address (or asset spending-condition) definition of the form `["r of set", {required: N, set: [sig_A, sig_A, sig_B, ...]}]` (duplicate signer) *looks* like an N-of-M threshold requiring N independent authorizations, but can in fact be spent/authorized with fewer real independent signers than N — as low as `N - (duplicates-1)`. This directly undermines the guarantee that a definition's threshold reflects the number of independent signers required to authorize spending, which is the exact same "count signatures, not signers" flaw as the reported report. It is reachable purely through unit posting (an ordinary unprivileged user can define such an address and later present a unit whose authors/authentifiers exploit the duplicate slot), matching the required "unauthorized spending" / "AA definitions" impact category — e.g., a party who is supposed to require independent co-signature from a second key can be tricked (or can trick a naive verifier) into accepting a definition that appears to need 2 signers but only needs 1.

### Likelihood Explanation
Reaching this path requires only posting an ordinary address definition (via a normal unit) containing a set with a duplicated `sig`/`address` member, plus supplying identical authentifier bytes at the two corresponding paths of a later spending unit — both are actions available to any unprivileged unit poster with no special network privileges. The duplicate-slot condition is never rejected by `validateDefinition`, so this construction is fully accepted by the network today.

### Recommendation
In `validateDefinition`'s `r of set` and `weighted and` handling, reject sets that contain structurally identical elements (e.g., by comparing `JSON.stringify` of each `args.set[i]`, or specifically disallowing repeated `pubkey` values across `sig` leaves and repeated addresses across `address` ops within the same set/threshold construct). Additionally, in `validateAuthentifiers`, consider tracking which underlying signer (pubkey/address) has already been counted within a given threshold construct and refuse to count the same signer twice even if it appears at different paths.

### Proof of Concept
1. Create a definition: `["r of set", {required: 2, set: [["sig", {pubkey: P}], ["sig", {pubkey: P}]]}]` for a single key pair `(P, sk)`. This passes `validateDefinition` unmodified (no duplicate check).
2. Compute `unit_hash_to_sign` for a spending unit from this address.
3. Sign it once with `sk` to get `signature`.
4. Set `author.authentifiers = {"r.0": signature, "r.1": signature}`.
5. `validateAuthentifiers` evaluates `r.0` and `r.1` independently; both call `ecdsaSig.verify(unit_hash_to_sign, signature, P)`, which succeeds twice, yielding `count = 2 >= required(2)` — the unit is accepted as validly authorizing spend from a "2-signature" address using only one real signature/key.
