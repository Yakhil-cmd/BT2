### Title
Webhook signature verified against attacker-controlled organization while handlers act on an independently-controlled repository field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository_owner`, which is parsed straight out of the untrusted JSON payload (`repository.owner.login` or `organization.login`). Every webhook handler, however, resolves the `Repository`/`Stack` to mutate using an entirely separate JSON field, `repository.full_name`. Because HMAC verification is scoped to whichever organization's secret the attacker chooses via `repository.owner.login`, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows/controls that organization's genuine `webhook_secret` via their own installed GitHub App) can forge a payload whose `repository.full_name` names a *different* organization/repository's stack, sign it with their own organization's secret, and have it accepted as authentic for the victim's repository.

### Finding Description
`WebhooksController#verify_signature` computes the "owning" GitHub App as: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) keyed strictly by that `organization` string: [1](#0-0) 

Meanwhile, every event handler (`PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, etc.) determines *which* `Repository`/`Stack` to act on using the unrelated `repository.full_name` field of the same payload, via `Shipit::Webhooks::Handlers::Handler#repository_name` / `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

The signature verification therefore proves only "this payload was signed by whoever holds `webhook_secret` for organization X" — it says nothing about the repository the payload claims to update. The equality the engine implicitly (and incorrectly) assumes is:

`organization authenticated by HMAC == organization whose repository/stack is written by the handler`

That equality does not hold: nothing binds `repository.owner.login`/`organization.login` (used for signature selection) to `repository.full_name` (used for the actual state-changing action). A tenant who is a legitimate, non-malicious-looking GitHub org admin of *their own* onboarded org — and thus trivially able to generate validly-signed webhook deliveries using their own org's `webhook_secret` (e.g., by using GitHub's "Redeliver" feature, or simply POSTing directly with a body they HMAC-sign themselves using the secret they configured for their own App/organization) — can substitute `repository.full_name` with any other onboarded organization's `owner/repo` string and have handlers mutate stacks belonging to a completely different tenant.

This is exploitable to: fabricate `push` events to trigger `GithubSyncJob`/deploy pipeline actions against a victim's stack, fabricate `pull_request` events to open/close/archive review stacks, fabricate `status`/`check_suite` events to poison the victim's CI state that gates deploy, and fabricate `membership` events (creating users/teams). All of these ultimately influence what commits are considered deployable and can lead to an unauthorized deploy on a stack the attacker does not own.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact: an entity that is only authorized (via its own org's webhook secret) to speak for its own organization's webhooks can inject events that mutate state (commit statuses, PR/review-stack lifecycle, sync of undeployed commits) for a stack belonging to a different, victim organization that it has no legitimate relationship to. Forged `status`/`push` events can manipulate which commit is considered "green"/deployable on the victim stack, directly influencing the automated deploy pipeline (e.g., continuous deployment), which corresponds to an unauthorized deploy/rollback outcome.

### Likelihood Explanation
Requires: (1) the deployment uses the multi-organization `github:` config schema (each org has its own `webhook_secret`), and (2) the attacker is an admin of at least one onboarded organization (or otherwise possesses a valid `webhook_secret` for any one org, e.g. through App install access to their own repos). No access to the victim's secret, no session, no `ApiClient` token, and no privileged Shipit access is required — only a legitimate GitHub App install for the attacker's own organization, matching the "unprivileged attacker relative to the victim" bar in the rules. Given this is a documented, supported configuration (`docs/setup.md`, `README.md` multi-org example in `config/secrets.development.example.yml`), the precondition is realistic for any operator federating multiple GitHub orgs into one Shipit instance.

### Recommendation
Bind the two fields used from the payload: after computing `repository_owner` for signature-app selection, require that every downstream handler's resolved `repository.full_name` owner matches `repository_owner` (case-insensitively), rejecting (422) the webhook otherwise. Alternatively, verify the signature against *every* configured organization's secret is not sufficient either — the correct fix is to only trust `repository.full_name`'s owner segment as the source of truth for which `webhook_secret` to check, or to explicitly cross-validate `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers.

### Proof of Concept
1. Operator configures Shipit with two orgs, `acme` and `victim`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker is an admin of `acme` and therefore has (or can derive, e.g. via "Redeliver webhook" replay/edit tooling, or simply because they configured it) `acme`'s `webhook_secret`.
3. Attacker crafts a `push` (or `pull_request`, `status`) JSON payload where:
   - `repository.owner.login` = `"acme"` (so `WebhooksController#repository_owner` resolves to `acme`, and `Shipit.github(organization: "acme")` is used for verification)
   - `repository.full_name` = `"victim/production-app"` (the actual repo/stack the handler will look up via `Repository.from_github_repo_name`)
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(acme_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) succeeds because it's checked against `acme`'s genuine secret.
6. `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) resolves `stacks` via `repository_name` = `"victim/production-app"` and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — despite the request never being signed by `victim`'s GitHub App/organization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

  end
