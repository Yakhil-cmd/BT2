### Title
`ReopenedHandler#unarchive?` operator-precedence bug lets webhook re-provision archived review stacks even when `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` intends to gate all re-provisioning on `repository.review_stacks_enabled`, but Ruby operator precedence (`&&` binds tighter than `||`) makes the flag only apply to the `provisioning_behavior_allow_all?` branch, not to the `allow_with_label`/`prevent_with_label` branches. As a result, a `reopened` webhook can call `ReviewStackAdapter#unarchive!` → `Shipit::ReviewStackProvisioningQueue.add(stack)` + `stack.unarchive!` on a repository that has disabled review stacks entirely, as long as its `provisioning_behavior` is `allow_with_label` or `prevent_with_label` and the label condition matches.

### Finding Description
The binding that should hold is: `unarchive? == true` only when `repository.review_stacks_enabled == true` (mirroring the same gating that `LabeledHandler#respond_to_label_change?` correctly applies as a standalone top-level `&&` before the archive/unarchive disjunction, at [1](#0-0) ).

In `reopened_handler.rb`, the check is instead: [2](#0-1) 

Due to Ruby precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. The `review_stacks_enabled` term is scoped only to the first disjunct. If a repository has `review_stacks_enabled: false` but `provisioning_behavior` is `prevent_with_label` (a very common configuration since most PRs will not carry the provisioning label, making `!pull_request_has_provisioning_label?` true by default), `unarchive?` returns `true` regardless of `review_stacks_enabled`.

`process` then calls `stack.unarchive!` at [3](#0-2) , which resolves to `ReviewStackAdapter#unarchive!`: [4](#0-3) 
This method itself never checks `review_stacks_enabled` at all — it relies entirely on the caller's gate, which is broken as shown above. It unconditionally re-enqueues provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`) and calls `stack.unarchive!`, reviving a stack whose original creation may predate the repository disabling review stacks (e.g., an operator disabled review stacks specifically to stop a malicious/abusive PR's stack from being (re)provisioned).

Attacker flow: attacker opens a PR on their own repo/fork while review stacks are enabled and provisioning_behavior is `prevent_with_label` (the natural default absent explicit configuration to `allow_all`), gets a `ReviewStack` created and later archived (e.g., PR closed, or operator disables `review_stacks_enabled` and/or closes the PR to stop it). Attacker then reopens the PR (`action: "reopened"` webhook, which needs no signature bypass — this is a legitimate webhook from their own repo) without the provisioning label. `unarchive?` still evaluates `true` because of the precedence bug, triggering re-provisioning and re-execution of the stack's steps even though the repository owner disabled review stacks.

This is a genuine authorization-truth divergence: `review_stacks_enabled` is expected to gate all review-stack (re)provisioning uniformly, but for two of the three `provisioning_behavior` modes it is silently ignored on the `reopened` path (and identically on the `opened` path in `opened_handler.rb`, which has the same bug pattern, though that is a separate handler/method).

### Impact Explanation
An attacker who controls the label state and commit/branch content of a PR on a repository they own can force Shipit to re-provision and re-run attacker-controlled review-stack provisioning steps on that repository even after the repository owner/operator has explicitly disabled review stacks (`review_stacks_enabled: false`) to stop this. This is a repository-scoped authorization bypass causing an unauthorized deploy/provisioning action to execute, matching the Critical impact category ("a payload for one repository mutating another's stack... or an unauthorized deploy"). It only affects review stacks belonging to the attacker's own repository (blast radius bounded to that repo's review stacks), but it is fully repeatable by simply reopening the PR again after each unarchive/archive cycle.

### Likelihood Explanation
Preconditions: the target repository must have a `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (not `allow_all`) — a configuration entirely independent of `review_stacks_enabled` and plausible as the operator's chosen mitigation when disabling review stacks broadly. The attacker needs no privileges beyond opening/reopening a PR and controlling its labels/branch, both attacker-controlled per the threat model. No Shipit secrets, tokens, or GitHub App keys are required; the `reopened` webhook is a standard, legitimately-signed event from the attacker's own repository. This makes the bug highly feasible and repeatable.

### Recommendation
Fix the operator precedence in `ReopenedHandler#unarchive?` (and the equivalent `OpenedHandler#provision?`) so `repository.review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally, consider defensively re-checking `repository.review_stacks_enabled` inside `ReviewStackAdapter#unarchive!` itself so it cannot be invoked by any future caller without the guard.

3. Build a `reopened` webhook payload for PR number 1 with no provisioning label (`labels: []`) and dispatch it through `ReopenedHandler.new(...).process` (or the standard webhook entrypoint used in existing tests).
4. Assert the binding is violated: `repository.review_stacks_enabled` is `false`, yet `stack.reload.archived?` is `false` and `Shipit::ReviewStackProvisioningQueue` received the stack (e.g., assert a provisioning job/queue entry was added), proving `unarchive!` executed despite `review_stacks_enabled == false`.
5. Compare with the expected binding: assert that after the fix, with the same setup, `stack.reload.archived?` remains `true` and no provisioning queue entry is added.
