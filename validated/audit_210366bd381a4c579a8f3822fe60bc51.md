### Title
Repeated mutable/immutable object conversion via `wrappedObject`/`cloneDeep` in AA formula evaluation allows GC-pressure DoS during unit validation - (File: formula/evaluation.js)

### Summary
The protobuf textformat bug (CVE-2022-3509) is a DoS caused by repeatedly converting objects back-and-forth between mutable and immutable forms when parsing attacker-controlled input, producing long GC pauses. `ocore`'s oscript/AA formula evaluator has the same structural pattern: every object value flowing through the evaluator is represented as a `wrappedObject`, and essentially every operation that touches it (`local_var_assignment`, `state_var_assignment`, `array`, `dictionary`, `concat`, `map`/`filter`/`reduce`, `readVar`, `definition`, `unit`, `trigger.data`, `params`, `trigger.outputs`, `previous_aa_responses`) performs a full `string_utils.cloneDeep()` of the object before/after wrapping it, explicitly to avoid mutating a possibly-frozen/shared copy. This is acknowledged directly in the code as a known performance risk.

### Finding Description
`wrappedObject` instances hold a JS object (`.obj`) that can be shared/frozen; every time the evaluator needs to touch or mutate that data it clones it with `string_utils.cloneDeep()` and re-wraps it in a new `wrappedObject`. This happens on nearly every AA-language operator that touches an object value:

- `local_var_assignment` / `state_var_assignment`: clone-then-reassign on every mutation [1](#0-0) 
- `array` / `dictionary` literal construction: `cloneDeep` per element before checking size [2](#0-1) 
- `concat`: clones both operands unconditionally [3](#0-2) 
- `readVar` (state variable read, used by every state-var reference and getters): `copyIfObject` re-clones the object on every single read [4](#0-3) 
- `map`/`filter`/`reduce`: clones elements per iteration [5](#0-4) 

The authors themselves flag this as a known risk in a comment at the top of the file: *"todo: replace cloning with CoW (e.g. immutable.js) as cloning of large objects can be quite expensive multiplied by MAX_OPS and amplifiable via getters (which can also amplify other expensive ops)"* [6](#0-5) .

This is precisely the bug class in CVE-2022-3509: repeated conversion of the same logical data between a "shared/immutable" form (`wrappedObject.obj`, potentially frozen/shared with cached state) and a "mutable" form (freshly `cloneDeep`d plain object) on every touch, rather than doing it once. An attacker who can define/trigger an Autonomous Agent (any unprivileged unit poster can define an AA and any account can send a trigger to it) fully controls the oscript executed during validation of every node that processes the unit, including the size of the object state var and the number of read/mutate operations performed on it.

Size limits exist (`isTooBigObj`, `MAX_AA_STRING_LENGTH`, `MAX_STATE_VAR_VALUE_LENGTH`) [7](#0-6)  and operation counts are limited by `MAX_OPS`/complexity checks in `formula/validation.js`, but these limits bound *count* and *max size*, not the *cumulative cost* of repeatedly deep-cloning a near-maximum-size object on every one of up to `MAX_OPS` operations. Getters amplify this further because getter calls can themselves invoke nested formula evaluations that each perform their own `readVar`/clone cycle on the same state var, as called out directly in the code comment above.

### Impact Explanation
Every full node (and light-vendor node) that validates the unit or executes the AA trigger runs this same execution path deterministically, so a crafted AA (large object state var + as many state-var-touching/getter operations as `MAX_OPS`/complexity limits allow) causes every validating node to pay the same disproportionate CPU/GC cost simultaneously. This matches the "network unable to confirm new units in a timely manner" impact category: repeated deep-cloning of large objects, amplified via getters, degrades AA/unit validation throughput network-wide rather than crashing a single process, but it is a genuine resource-exhaustion vector reachable by an unprivileged AA author/trigger sender, analogous to the protobuf GC-pause DoS.

### Likelihood Explanation
Medium-High. No special privileges are needed — defining an AA and sending it a trigger with a data payload (or having the AA build up a large state-var object) is a normal, permissionless operation. The attacker fully controls the number of clone-triggering operations (bounded only by the existing `MAX_OPS`/complexity limits, which were designed to bound execution steps, not clone cost per step) and the size of the object being cloned (bounded by `MAX_AA_STRING_LENGTH`/`isTooBigObj`, which allow objects large enough to make repeated `cloneDeep` calls non-trivial). The known "todo" comment in the code confirms the maintainers are aware cloning cost is not properly bounded relative to op count and getter amplification.

### Recommendation
Adopt a copy-on-write (or reference-counted immutable) representation for `wrappedObject` (as the code's own TODO suggests, e.g. via `immutable.js`), so that reads do not require a full `cloneDeep`, and mutation only clones the minimal changed sub-path rather than the whole object. Alternatively, introduce an explicit cost accounting for object size × clone operations (similar to the existing complexity/`count_ops` model) so that the cumulative cost of repeated cloning of large objects is bounded regardless of how many discrete AA operations or getter calls are used to trigger it.

### Proof of Concept
1. Deploy an AA whose `init`/message code creates a large (near `isTooBigObj`/`MAX_AA_STRING_LENGTH` limit) object and stores it as a single object state var (e.g. via `state_var_assignment` with an object RHS) — see the object-clone path at `formula/evaluation.js:1327-1344`.
2. Define one or more `getters` (activated via `readGetterProps`, see `aa_validation.js:763-768`) that repeatedly read that state var (`readVar`, which clones the object on every call, `formula/evaluation.js:2807-2834`) and perform additional object operations on it (`concat`, `dictionary`, `map`/`filter`) up to the `MAX_OPS`/complexity ceiling enforced in `formula/validation.js`.
3. Send a trigger unit to the AA; every validating/executing node repeatedly `cloneDeep`s the large object once per touching operation, multiplying clone cost by op count and by getter nesting, producing outsized CPU/GC load during validation of a single unit relative to its declared complexity/op-count cost.
