The report's root cause is specific to `GoldfinchAdapter.sol`'s pattern of valuing an external LP token by subtracting a separately-tracked "redeemed principal" counter from a static "initial principal" value, allowing the value to stay inflated by simply never calling redeem. I searched the Polkadot SDK for structurally analogous patterns — valuation/pricing logic that relies on a separately-tracked redeemed/claimed counter rather than live state:

- `pallet-asset-conversion`'s `get_reserves` reads live pool account balances directly via `Self::get_balance`, not a cached "initial deposit minus redeemed" counter [1](#0-0) , and quote functions were hardened to check against `reducible_balance` at query time [2](#0-1) .
- `pallet-nomination-pools` values a member's stake via `points_to_balance`, which reads `T::StakeAdapter::active_stake` live at call time rather than a stored "initial bonded amount minus withdrawn" delta [3](#0-2) , and slashing/withdrawal accounting is applied directly against ledger state rather than a user-gameable redemption counter [4](#0-3) .

In both cases the FRAME design queries live, authoritative on-chain balances/stakes at valuation time instead of trusting a mutable "amount redeemed so far" field that the holder controls by choosing not to call a redeem function. There is no analogous "protection/insurance" contract in the Polkadot SDK that values a claim against an external LP-token-like asset using a self-reported redemption delta that a user could simply avoid updating to keep the valuation artificially high. No FRAME pallet, XCM component, or bridge module was found with this specific missing-check pattern (stale/inflated valuation via omitted redemption + subsequent double claim).
