### Title
`StatusHandler#process` writes GitHub statuses onto commits by SHA alone, with no repository binding to the signing webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, never filtering by the `repository.full_name` present in the same payload that was used to select the signing key. Any repository owner who can get GitHub to emit (or can otherwise produce) a validly-signed `status` webhook for a commit SHA that coincides with a SHA also tracked by a different stack (e.g. via a fork, which preserves identical commit SHAs) can write a `Status` row for that unrelated stack's commit, including "blocking" contexts that feed `Commit#blocked?`.

### Finding Description
The binding the question asks to verify is: *the repository that authorized a `blocking_statuses`-context status write == the repository that owns the stack whose `blocked?` gate it feeds*. Tracing the code shows this binding does **not** hold.

- `WebhooksController#verify_signature` only checks that the raw payload was HMAC-signed with the webhook secret belonging to `repository_owner` (derived from `payload.dig('repository', 'owner', ...)`), i.e. it authenticates "this payload was sent by GitHub for org X's repo." [1](#0-0) 
- The base `Handler` class does provide a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`), which other handlers (push, pull_request) use to scope their writes to the authorized repository. [2](#0-1) 
- `StatusHandler#process`, however, does **not** use `stacks` at all. It queries `Commit.where(sha: params.sha)` globally across the entire commits table and calls `create_status_from_github!` on every match: [3](#0-2) 
- `Status#blocking?` is evaluated purely from `state`/`context` of whatever `Status` rows exist on the commit, with no repository check: [4](#0-3) 
- `Commit#blocked?` walks `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`, i.e. it inspects intervening `Commit` rows belonging to `stack` and asks each for `blocking?`, which is driven by whatever `Status` rows are attached to that commit row - regardless of which webhook (and which repository's signing key) created them: [5](#0-4) 

Because commit SHAs are content-addressed, two different `Repository`/`Stack` records can legitimately share the same SHA for the same underlying commit (most commonly via a fork: an attacker forks the victim's public repository, and the forked commits retain byte-identical SHA1 IDs). If the attacker's fork is registered with a GitHub App installation the attacker controls (their own webhook secret for their own org), GitHub will produce a validly-signed `status` webhook whose `repository.full_name` is `attacker/repo` but whose `sha` is identical to a commit that Shipit also tracks under `victim/repo`'s stack. `verify_signature` passes (the signature genuinely matches the attacker's own org's secret for their own repo event). `StatusHandler#process` then ignores `repository.full_name` entirely and matches purely on `sha`, writing/updating a `Status` on **every** `Commit` row with that SHA - including the one that belongs to the victim's stack.

If that status has `context` equal to one of the victim stack's `blocking_statuses` and `state: 'success'`, `Status::Common#blocking?` (`!success? && commit.blocking_statuses.include?(context)`) becomes `false` for that commit, so `Commit#blocked?` on the victim's head commit can flip from `true` to `false`, unblocking a deploy gate using a payload the victim's repository never authorized.

None of the listed guards catch this: `verify_signature` authenticates the sender/org of the payload but not the target rows being mutated; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/`context` etc., not repository scoping; `drop_unhandled_event` is irrelevant (the event type is legitimately `status`); and `Handler#stacks`/`repository_name` exist but are simply never invoked by this particular handler's `process` method.

### Impact Explanation
The attacker gains the ability to write a `Status` record onto an arbitrary victim `Commit` for any commit SHA they can get their own signed webhook to reference (fork-preserved SHAs make this practical against any tenant tracking a public/forkable upstream). Flipping a blocking-context status to `success` clears `Commit#blocking?` for that intervening commit, clearing `Commit#blocked?`/`deployable?` for later commits in the victim stack, which can unblock an otherwise gated deploy - this is a payload from one repository mutating another repository's stack/commit state and enabling an unauthorized deploy path, matching the **Critical** category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any victim stack sharing a SHA with a repo the attacker controls (e.g., via forking), and requires no privileges beyond owning/controlling a GitHub repository and its App installation/webhook secret.

### Likelihood Explanation
Preconditions: the attacker needs a repository they control that (a) has a GitHub App installation configured in Shipit's `Shipit.github(organization: ...)` config so `verify_webhook_signature` succeeds for their own org, and (b) shares at least one commit SHA with a victim stack - trivially achievable by forking the victim's (or a shared upstream's) public repository. No Shipit session, API token, or GitHub secret of the victim is required. This is low-cost and repeatable: the attacker can trigger this whenever they want by creating a `status` event on their own fork for the shared commit.

### Recommendation
Scope `StatusHandler#process` to the authorized repository, mirroring the pattern used by other handlers via `Handler#stacks`. E.g., restrict the commit lookup to `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so that only commits belonging to stacks of the repository named in the signed payload can have a `Status` created/updated.

```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "a status webhook signed for repo A must not clear blocking? on repo B's shared-sha commit" do
          repo_a = Repository.create!(owner: 'attacker', name: 'repo')
          repo_b = Repository.create!(owner: 'victim', name: 'repo')

          stack_a = Stack.create!(repository: repo_a, environment: 'production', branch: 'master')
          stack_b = Stack.create!(repository: repo_b, environment: 'production', branch: 'master')

          shared_sha = 'a' * 40

          intervening_commit_a = stack_a.commits.create!(sha: shared_sha, author: AnonymousUser.new, authored_at: Time.now, committer: AnonymousUser.new, committed_at: Time.now, message: 'shared')
          intervening_commit_b = stack_b.commits.create!(sha: shared_sha, author: AnonymousUser.new, authored_at: Time.now, committer: AnonymousUser.new, committed_at: Time.now, message: 'shared')
          head_commit_b = stack_b.commits.create!(sha: 'b' * 40, author: AnonymousUser.new, authored_at: Time.now, committer: AnonymousUser.new, committed_at: Time.now, message: 'head')

          # victim's own blocking status: failing CI on the intervening commit
          intervening_commit_b.statuses.create!(stack: stack_b, state: 'pending', context: 'blocking-context')

          # Binding under test, BEFORE:
          assert_predicate intervening_commit_b, :blocking?
          assert_predicate head_commit_b, :blocked?

          # Attacker sends a status webhook, validly signed for repo A ('attacker/repo'),
          # referencing the SHA shared with repo B, marking the blocking context 'success'.
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'blocking-context',
            'branches' => [{ 'name' => 'master' }],
            'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } }
          }

          StatusHandler.call(payload)

          # Binding under test, AFTER: repo A's payload must NOT affect repo B's gate.
          refute_predicate intervening_commit_b.reload, :blocking?   # currently flips to false - VULNERABLE
          refute_predicate head_commit_b.reload, :blocked?           # currently flips to false - VULNERABLE
        end
      end
    end
  end
end
```
This test demonstrates that `StatusHandler#process`, by matching purely on `sha` without scoping to `stacks` derived from the payload's `repository.full_name`, allows a webhook validly signed for `attacker/repo` to clear `blocking?`/`blocked?` state on `victim/repo`'s stack.
