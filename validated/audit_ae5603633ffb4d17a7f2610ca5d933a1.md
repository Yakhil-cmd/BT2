### Title
Clickjacking via `X-Frame-Options: ALLOWALL` on `MergeStatusController#show`, weaponized by `SameSite=None` cookies, lets an attacker page force an authenticated victim into performing state-changing merge-queue actions - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController#show` unconditionally sets `response.headers['X-Frame-Options'] = 'ALLOWALL'` for every request, removing all native browser framing protection on a page that renders a live, session-authenticated "Add to merge queue" / "Remove from merge queue" form. When an operator opts into `SHIPIT_ENABLE_SAMESITE_NONE`, `Shipit::SameSiteCookieMiddleware` rewrites every `Set-Cookie` to append `SameSite=None`, which is what actually allows the victim's session cookie to be sent on the cross-site iframe request in the first place (with the default `Lax`, the cookie would not be attached to a third-party iframe embed). The combination lets an attacker's page iframe `https://shipit.example.com/merge_status?referrer=...&branch=...` and, via classic UI-redress/clickjacking, trick the victim into submitting the genuine (CSRF-token-valid) `enqueue`/`dequeue` form rendered inside the frame.

### Finding Description
The broken binding: `response.headers['X-Frame-Options']` should equal a framing-restrictive value (e.g. `SAMEORIGIN`/absent, relying on CSP `frame-ancestors`) for any page containing session-privileged, state-changing forms, but instead equals `'ALLOWALL'` unconditionally in `MergeStatusController#show`: [1](#0-0) 

`show` is authentication-skipped (`skip_authentication only: %i[check show]`) but still branches on `current_user.logged_in?` to decide whether to render the real merge-status/queue UI or a `logged_out` placeholder: [2](#0-1) [3](#0-2) 

When the stack is queue-eligible, the rendered partial embeds a real form pointing at the state-changing `enqueue`/`dequeue` routes, submitted via `PUT`/`DELETE`: [4](#0-3) [5](#0-4) 

`ShipitController` has `protect_from_forgery with: :exception` enabled, so this form carries a valid authenticity token — the attack does not need to (and does not) bypass CSRF; it relies on the victim genuinely submitting the real form rendered from the real origin, which is exactly what clickjacking does: [6](#0-5) 

The `SameSite=None` half of the precondition is real and necessary: `SameSiteCookieMiddleware#call` only fires when `Shipit.enable_samesite_middleware?` (`ENV['SHIPIT_ENABLE_SAMESITE_NONE']`) is set, and appends `SameSite=None` (plus `Secure`) to every cookie on TLS requests: [7](#0-6) [8](#0-7) [9](#0-8) 

Without this middleware active, default `Lax` cookies are not attached to third-party iframe GET/PUT requests, `current_user.logged_in?` would be false inside the frame, and only the harmless `logged_out` placeholder renders — so the two conditions genuinely compose into a working exploit chain, matching the audit's claimed binding.

Attacker request: attacker hosts `attacker.example.com` with `<iframe src="https://shipit.example.com/merge_status?referrer=https://github.com/OWNER/REPO/pull/N&branch=BRANCH">`, visually overlays it (opacity/position tricks) with a decoy UI, and lures the victim (who has an active Shipit session) into clicking where the real "Add to merge queue" button renders. Existing guards that would normally stop this class of attack do not apply here: `verify_signature`/webhook checks are irrelevant (this is a browser-session path, not a webhook), `force_github_authentication` only checks the session is valid and the user is authorized/team-member — it does not check the request's framing or `Origin`/`Sec-Fetch-Site` context, and CSRF protection is satisfied because the form and its token are genuinely rendered by Shipit for the logged-in victim.

### Impact Explanation
Successful exploitation causes an authenticated victim's browser to submit `PUT /merge_status/:stack_id/pull/:number` (or `DELETE`), invoking `MergeRequest.request_merge!(stack, params[:number], current_user)` attributed to the victim, for an attacker-chosen repository/branch/PR that the attacker fully controls via the `referrer` and `branch` query params: [10](#0-9) 
This is an unauthorized state change (queuing an arbitrary PR for merge) performed under the victim's identity without their intended consent, which can lead to code being merged/deployed that the victim never approved — matching the "unauthorized merge" Critical impact category. It is repeatable against any stack/repository tracked by the Shipit instance with `merge_queue_enabled`, is not confined to a single tenant, and each click yields one queue/dequeue action.

### Likelihood Explanation
This requires the operator to have explicitly opted into `SHIPIT_ENABLE_SAMESITE_NONE` (an env var not enabled by default) and to be serving over TLS — both stated as given preconditions in the question. Given those preconditions, attacker cost is low: no secrets, tokens, or privileged roles are needed, only luring a logged-in victim to a crafted page and a successful clickjacking interaction (which has real-world friction — the victim must be tricked into clicking the exact overlayed spot at least once per queue action, and must currently have a live Shipit session).

### Recommendation
Do not set `X-Frame-Options: ALLOWALL` unconditionally. If framing is required for the browser-extension integration, restrict it via a `Content-Security-Policy: frame-ancestors` allow-list scoped to the extension's known origin(s)/scheme rather than allowing arbitrary origins, and/or move the extension's consumption of this endpoint to a same-origin fetch (as the extension's own `frame.html` already appears designed to proxy content) instead of directly framing the authenticated page. Independently, `SameSiteCookieMiddleware` should not blanket-apply `SameSite=None` to the session cookie without pairing it with framing restrictions on any page containing state-changing forms.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb (add)
test "GET show sets X-Frame-Options to ALLOWALL, permitting framing" do
  get :show, params: { referrer: 'https://github.com/Shopify/shipit-engine/pull/42', branch: 'master' }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
end

# test/middleware/same_site_cookie_middleware_test.rb (add)
test "session cookie gets SameSite=None when enable_samesite_middleware? is true" do
  Shipit.stubs(:enable_samesite_middleware?).returns(true)
  env = env_for_url("https://test.com/")
  _status, headers, _body = middleware.call(env)
  session_cookie = headers['Set-Cookie'].split("\n").first
  assert_match(/SameSite=None/i, session_cookie)
end
```
Both assertions independently confirm the two halves of the claimed binding (`X-Frame-Options == 'ALLOWALL'` and `SameSite=None` appended under the stated precondition). A full clickjacking demonstration (actual cross-site framed click causing `enqueue`) requires browser automation and cannot be expressed purely in a Rails minitest without a live browser; the two assertions above are the reproducible, code-level proof of the composing conditions.

    def call(env)
      status, headers, body = @app.call(env)

      if headers && headers['Set-Cookie'] &&
         Rack::Request.new(env).ssl?

        set_cookies = headers['Set-Cookie'].split(COOKIE_SEPARATOR).compact
        set_cookies.map! do |cookie|
          cookie << '; Secure' if cookie !~ /;\s*secure/i
          cookie << '; SameSite=None' unless cookie.match?(/;\s*samesite=/i)
          cookie
        end

        headers['Set-Cookie'] = set_cookies.join(COOKIE_SEPARATOR)
      end
