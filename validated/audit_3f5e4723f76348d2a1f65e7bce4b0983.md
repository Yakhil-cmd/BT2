### Title
Webhook organization authentication is bound to `repository.owner.login`, but handlers act on `repository.full_name` — allows cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `repository.owner.login` (or `organization.login`) in the attacker-supplied JSON body. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every handler (e.g. `PushHandler`) to resolve the `Repository`/`Stack` to act on, reads a *different* field from the same body: `repository.full_name`. Because both fields live in the same attacker-controlled JSON payload, a legitimate holder of one organization's real `webhook_secret` can set `repository.owner.login` to their own org (so the signature validates) while setting `repository.full_name` to a different organization's repository, causing the handler to operate on a stack it was never authenticated for.

### Finding Description
`verify_signature` picks the secret via: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `installation_id`, `webhook_secret`, `private_key`) confirming this engine is designed to host multiple independent GitHub organizations on one instance: [3](#0-2) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, which resolve the target repository via a *different* JSON key: [4](#0-3) [5](#0-4) 

The equality that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization of the repository the handler mutates (repository.full_name)`

Before the attacker's request: signature verification and handler dispatch both implicitly assume `repository.owner.login` and `repository.full_name`'s owner segment refer to the same repository/org, because a genuine GitHub webhook always sets them consistently.

After the attacker's request: the attacker (who legitimately administers a GitHub App/webhook installation for `org-a` on this Shipit instance, and therefore genuinely knows `org-a`'s `webhook_secret`) crafts a raw POST body where:
- `repository.owner.login = "org-a"` → `verify_signature` resolves `Shipit.github(organization: "org-a")` and the HMAC computed with `org-a`'s real secret validates successfully.
- `repository.full_name = "org-b/target-repo"` → `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-b/target-repo")`, an org the attacker was never authenticated for.

The `PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s stacks, with `params.after` fully attacker-controlled, forcing a `GithubSyncJob` for a repository/organization the request was never authorized to touch.

### Impact Explanation
This breaks the authentication boundary between tenants on a single Shipit instance: any org (or anyone possessing one org's legitimate webhook secret) can trigger sync/status/pull-request-provisioning side effects against a completely different org's stacks, which is a cross-repository/cross-tenant write achieved purely by manipulating unauthenticated fields of the JSON payload. Depending on further processing this can drive unintended `GithubSyncJob` runs, forged commit-status creation (`StatusHandler`, which additionally doesn't scope by repository at all and matches purely by `sha`), or forged pull-request/review-stack lifecycle events (`archive!`/`unarchive!`, `find_or_create!`) against another organization's stacks — matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a valid `webhook_secret`/GitHub App installation for at least one organization configured on the shared Shipit instance (a realistic scenario for any multi-tenant Shipit deployment using `Shipit.github_organizations`). No repository write access, GITHUB_TOKEN, or `ApiClient` token is needed — only the ability to send an arbitrary POST to `/webhooks` with a correctly-signed body for their own org, which they control by definition.

### Recommendation
`verify_signature` and `repository_name`/handler dispatch must derive the authorizing organization and the acted-upon repository from the same, single source of truth in the payload (e.g., always use `repository.full_name`'s owner segment, or cross-check `repository.owner.login` against the resolved `Repository`'s organization before allowing any handler to act), rejecting the request if they disagree.

### Proof of Concept
1. Attacker legitimately administers Shipit's GitHub App integration for `org-a` and thus knows `org-a`'s `webhook_secret`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `org-a`'s real `webhook_secret` over the raw body.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-b/target-repo")` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `org-b`'s stack, despite the request never being authenticated for `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
