### Title
No vulnerability found: bridged XCM origin cannot be forged into local sibling `AssetHubLocation` - (File: system-parachains/bridge-hubs/bridge-hub-polkadot/src/bridge_to_kusama_config.rs, system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs)

### Summary
The premise of the question conflates two structurally distinct locations: the local sibling `AssetHubLocation` (`parents: 1, [Parachain(1000)]`) and the bridged reserve location `bridging::to_kusama::AssetHubKusama` (`parents: 2, [GlobalConsensus(Kusama), Parachain(1000)]`). `DescendOrigin` can only append junctions to the current origin's interior — it can never remove the leading `GlobalConsensus`/parents prefix that bridge infrastructure establishes for inbound bridged messages, so a bridged program can never collapse into the local `AssetHubLocation`.

### Finding Description
Messages exported from Kusama AssetHub arrive at BridgeHubPolkadot via `pallet_bridge_messages` configured with `MessageDispatch = XcmOverBridgeHubKusama` and `BlobDispatcher = FromKusamaMessageBlobDispatcher` [2](#0-1) . `FromKusamaMessageBlobDispatcher` is a `BridgeBlobDispatcher<XcmRouter, UniversalLocation, BridgePolkadotToKusamaMessagesPalletInstance>` [3](#0-2) . Per the standard `pallet_xcm_bridge_hub`/`xcm_builder` bridge dispatch flow, the bridge infrastructure — not the attacker's message content — establishes the message's universal origin by wrapping it with the bridge's `GlobalConsensus(Kusama)` prefix plus the sending sibling's `Parachain(AssetHubKusamaId)` junction, before routing it onward (e.g., to `AssetHubPolkadot` via `XcmRouter`). This yields an origin rooted at `Location { parents: 2, interior: [GlobalConsensus(Kusama), Parachain(1000), ...] }`, which is exactly `bridging::to_kusama::AssetHubKusama` [1](#0-0) . A `DescendOrigin` instruction inside the attacker-crafted inner program can only push additional junctions onto this already-established origin (narrowing it further into a sub-location like an account under the bridged Asset Hub), it cannot strip the `GlobalConsensus(Kusama)` prefix or change `parents` from 2 to 1. Therefore the resulting origin can never equal the local sibling `AssetHubLocation = Location::new(1, [Parachain(1000)])` used elsewhere as a system-parachain trust anchor. Furthermore, `AssetHubPolkadot`'s `IsReserve`/aliasing logic (`TrustedReserves`, `AliasOriginRootUsingFilter<bridging::to_kusama::AssetHubKusama, KusamaGlobalConsensus>`) is intentionally scoped to accept the bridged `(2, [GlobalConsensus(Kusama), Parachain(1000)])` origin as the trusted reserve for bridged KSM/foreign assets [4](#0-3)  — this is the correct, intended trust boundary for the bridge, not a confusion with the local `AssetHubLocation`.

### Impact Explanation
None. The scoped impact (privilege escalation by collapsing a bridged origin into the trusted local `AssetHubLocation`) does not occur, because XCM origin tracking through bridges is monotonic-descending: origins can only be narrowed (via `DescendOrigin`), never generalized or re-rooted, by instructions inside the message payload itself.

### Likelihood Explanation
Not applicable — no exploitable path exists. The claimed root cause (a "missing check" allowing origin collapse) is not present; `DescendOrigin`'s semantics in the XCM executor structurally prevent this, and no code in `bridge_common_config.rs` or `xcm_config.rs` treats the local `AssetHubLocation` as reachable from a bridged Kusama-origin message.

### Recommendation
No fix required for this specific claim. General good practice (already reflected in the codebase) is to keep bridged trust anchors (`bridging::to_kusama::AssetHubKusama`, parents=2) and local sibling trust anchors (`AssetHubLocation`, parents=1) as distinct, non-overlapping `Location` values, which is already the case.

### Proof of Concept
An `xcm-emulator` test could assert this invariant explicitly: construct an `ExportMessage` from Kusama AssetHub containing `DescendOrigin(Junctions::from([Parachain(1000)]))` (or any junction sequence) as the first instruction of the inner program, dispatch through the bridge to BridgeHubPolkadot/AssetHubPolkadot, and then assert (e.g., via a `Transact`/`QueryPallet`-style probe or a custom instruction that reports `Origin`) that the resulting effective origin always starts with `(2, [GlobalConsensus(Kusama), Parachain(1000), ...])` and is never equal to `Location::new(1, [Parachain(1000)])`. Given the semantics of `DescendOrigin` in `xcm-executor`, this assertion is expected to always hold, confirming no forgery path exists.
