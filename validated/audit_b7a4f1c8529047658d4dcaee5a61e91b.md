### Title
Cross-repository/cross-stack commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates every `Commit` row matching a bare SHA regardless of which repository sent the webhook, while every other handler in this engine derives a `stacks`/`Repository.from_github_repo_name(repository_name)` scope from `payload.dig('repository','full_name')` before touching any record. Because `Commit` is stored per-stack (`belongs_to :stack`) and the same SHA can legitimately exist in multiple stacks (forks/mirrors of the same upstream history, multiple environments tracking the same repo, shared ancestor commits), an attacker who can get one authenticated `status` webhook accepted for *their own* repository can write a fabricated CI state onto a commit belonging to an unrelated victim stack — including a production-environment stack that requires `ci/coverage`.

### Finding Description
The invariant that should hold is:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a webhook.

`Handler` (the base class) explicitly provides this scoping primitive: [1](#0-0) 

But `StatusHandler#process` never calls it. It resolves target commits solely by SHA, with no repository/stack filter at all: [2](#0-1) 

`Commit` records are stack-scoped (`belongs_to :stack`), so the same SHA can appear as separate `Commit` rows in unrelated stacks whenever a fork, mirror, or multiple stacks of the same repository (e.g. staging/production) synced the same underlying git history: [3](#0-2) 

`create_status_from_github!` then writes a `Status` tied to that commit's own `stack_id`, and `add_status` immediately triggers deployability re-evaluation and merge-queue scheduling based on the new status: [4](#0-3) [5](#0-4) 

Downstream, `Stack#deployable?`/`Commit#deployable?`/`Commit#blocked?` consult exactly this status data to permit or block deploys, and `required_statuses`/`blocking_statuses` (configured via `ci.require`/`ci.blocking` in `shipit.yml`) determine whether `ci/coverage` is load-bearing for the victim's production stack: [6](#0-5) [7](#0-6) 

Exploit flow: attacker owns/controls a repository already wired to Shipit (their own fork or a repository whose webhook is legitimately authenticated by whatever signature scheme Shipit uses for that hook). They send a `status` event with `context: ci/coverage`, `state: success` (or `failure`), and a `sha` that is shared with a victim's stack (identical git history via fork/mirror, or coincidentally present because multiple stacks track the same upstream repo). `StatusHandler#process` matches `Commit.where(sha: ...)` across every stack in the installation, not just the attacker's own repository's stacks, and applies the status to the victim's `Commit` row too. If the victim stack is the production environment requiring/blocking on `ci/coverage`, this flips its deployability, unblocking (or blocking) deploys/merges.

Existing guards do not prevent this: signature verification (whatever scheme Shipit uses) only proves the payload came from *a* repo whose secret the attacker holds/knows — it says nothing about which `Commit`/`Stack` the handler is allowed to mutate. `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership. No `Repository`/`Stack` scoping check exists in `StatusHandler` at all, unlike the `stacks` helper other handlers are expected to use.

### Impact Explanation
A payload authenticated for repository A can write a `Status` record onto a `Commit` belonging to stack/repository B, which `Stack`/`Commit` deployability logic then consumes to gate deploys, rollbacks, and merge-queue promotion. This is a payload for one repository mutating another's commit/stack state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius spans every stack in the Shipit installation that happens to contain a `Commit` row with a matching SHA (forks, mirrors, multi-environment stacks of the same repo), and is repeatable for any SHA/context combination the attacker chooses.

### Likelihood Explanation
Preconditions: the attacker needs a webhook accepted as authentic for at least one repository (their own fork or any repo they control that is registered with this Shipit instance), and a SHA that is also present as a `Commit` row in the victim's stack — realistic whenever the victim stack tracks a repository the attacker has forked/mirrored, or when the same upstream repo backs multiple stacks (e.g., staging and production). No Shipit session, API token, or GitHub team membership is required beyond controlling one already-onboarded repository's webhook. This is directly reachable through the unauthenticated `POST /webhooks` entrypoint and is deterministic/repeatable once a shared SHA is identified.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records by bare SHA) to the requesting repository, mirroring the `stacks` helper already defined on `Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` before any status is written.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories: `repo_a` (attacker-controlled) and `repo_b` (victim, `environment: 'production'`, `cached_deploy_spec` with `ci.require = ['ci/coverage']`).
2. Create `commit_a = repo_a.stack.commits.create!(sha: SHARED_SHA, ...)` and `commit_b = repo_b.stack.commits.create!(sha: SHARED_SHA, ...)` (no `ci/coverage` status yet on either — `refute commit_b.deployable?`).
3. Build a `status` payload: `{ repository: { full_name: repo_a.full_name }, sha: SHARED_SHA, state: 'success', context: 'ci/coverage' }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the broken binding: before, `commit_b.stack.repository.full_name != payload.dig('repository','full_name')`; after processing, assert `commit_b.reload.statuses.where(context: 'ci/coverage').exists?` is `true` and `commit_b.deployable?` flips to `true` (or the production stack becomes deployable), proving repo B's state was mutated by a payload authenticated only for repo A.
