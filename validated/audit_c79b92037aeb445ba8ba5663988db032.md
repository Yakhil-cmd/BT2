### Title
Missing Cosigner Authorization on Signing Requests Enables Unsolicited Signing Prompts for Any Wallet Address - (File: wallet.js)

### Summary
The `sign` device-message handler in `wallet.js` (case `"sign"`, invoked from `handleMessageFromHub`) is the ocore-wallet analog of the Open WebUI IDOR: it enforces "does this correspondent exist" but never verifies "is this correspondent actually authorized to request a signature for this specific address," exactly mirroring the reported pattern of checking coarse access (channel/correspondent-level) while skipping fine-grained ownership/authorization (message/cosigner-level) validation.

### Finding Description
When a paired device sends a `"sign"` message, `handleMessageFromHub` in `wallet.js` validates the message structure and payment/authors fields, then calls `findAddress(body.address, body.signing_path, callbacks)`. If `body.address` is any address whose keys live locally (a plain single-sig address or a member address of a shared/multisig address), `findAddress` invokes `ifLocal`. Inside `ifLocal`, the intended ownership check — verifying that `from_address` (the sender) is actually a cosigner device registered for that wallet/address — is explicitly commented out: [1](#0-0) 

This means `handleMessageFromHub` accepts a `"sign"` request from **any paired correspondent device**, not only from a device that is genuinely part of the shared-address definition (`extended_pubkeys`/`shared_address_signing_paths`). The handler then proceeds to hash the attacker-supplied unit and fires the `"signing_request"` event that drives the wallet's confirmation UI: [2](#0-1) 

By contrast, the `ifRemote` branch of the very same `findAddress` callback — used when the address's keys live on another device — does perform the correct ownership check before proxying the request: [3](#0-2) 

The asymmetry (checked in `ifRemote`, deliberately removed in `ifLocal`, per the comment "the commented check would make multilateral signing impossible") shows the control was consciously dropped to support a legitimate feature (multilateral/contract signing across unrelated addresses) but without reintroducing any authorization boundary — precisely the CWE-862 pattern in the source report: a broader/coarser check (device is a known correspondent) is substituted for the correct one (device is a legitimate cosigner of *this* address).

### Impact Explanation
Any device merely paired/correspondent with the victim (e.g., a chat contact, or a third party added during an unrelated prosaic/arbiter contract flow) can send a forged `"sign"` request for **any local address of the victim's wallet**, including plain single-sig addresses that have nothing to do with that correspondent. This triggers the wallet's `"signing_request"` confirmation dialog for an attacker-crafted unit (e.g., one spending the victim's own funds to an attacker-controlled address), impersonating a legitimate multisig-cosigning flow. Because the trust decision ("is this sender allowed to ask me to sign this address's data") is removed from ocore itself and pushed entirely onto the human user's judgment in the UI, this is a broken-access-control weakness in the core signing-request pathway that can facilitate unauthorized-spend attempts if the user is misled into approving (e.g., believing it's a routine cosigning request from a party they've dealt with before, such as an arbiter/contract correspondent).

### Likelihood Explanation
Exploitation requires only that the attacker be an existing paired correspondent of the victim device — a low bar in ocore's model, since pairing happens routinely for chat, contract negotiation (`prosaic_contract_offer`, `arbiter_contract_offer`), and other everyday wallet interactions accepted from non-strangers. No cryptographic secret or special privilege is needed to reach `ifLocal`; the attacker only needs to know one of the victim's addresses (easily learned from a shared multisig setup, a contract, or a payment they previously received).

### Recommendation
Restore and enable an authorization check inside the `ifLocal` branch analogous to the one already implemented in `ifRemote`: before calling `callbacks.ifOk()`/emitting `"signing_request"`, verify that `from_address` is a registered cosigner device for `body.address`'s wallet (via `extended_pubkeys`/`wallet_signing_paths` for wallet addresses, or `shared_address_signing_paths` for shared addresses) at the specific `signing_path`, rejecting the request with `callbacks.ifError("sender is not cosigner of this address")` otherwise. If "multilateral signing" (unrelated address, contract-style signing) must remain supported, gate it through an explicit, narrower allow-list (e.g., a flag tied to a known contract/shared-address record) instead of removing the ownership check for all local addresses.

### Proof of Concept
1. Device A (victim) and Device B (attacker) become correspondents through any normal pairing flow (e.g., B sends A a `prosaic_contract_offer` or simple chat pairing).
2. B crafts a `"sign"` message body: `{address: "<A's own single-sig address>", signing_path: "r", unsigned_unit: {authors: [{address: "<A's address>", authentifiers: {r: ""}}], messages: [{app:"payment", payload_location:"inline", payload:{asset:null, inputs:[...A's real unspent output...], outputs:[{address:"<B's address>", amount: <victim's balance>}]}}]}}` and sends it to A via `device.sendMessageToDevice`.
3. On A's device, `handleMessageFromHub` reaches case `"sign"`, passes all structural checks (address is valid, is among unit authors, payload hashes match), and `findAddress` resolves to `ifLocal` because A holds this address's keys locally.
4. Because the ownership check is commented out, A's wallet immediately fires `"signing_request"` for B's fabricated unit, exactly as if B were a legitimate cosigner — even though B has no relationship to this address at all — prompting A's UI with a spend request that, if approved, transfers A's funds to B.
