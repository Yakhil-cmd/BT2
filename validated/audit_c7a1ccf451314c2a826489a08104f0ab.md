This confirms the vulnerability: in a multi-organization Shipit deployment (`Shipit.secrets.github` keyed by organization, per `lib/shipit.rb:170-200`), the webhook signature is computed against a per-organization secret selected using an unauthenticated field, while the actual repository the event is applied to is selected using a *different* unauthenticated field from the same unverified payload.

### Title
Webhook signature verified against organization derived from unauthenticated payload field while event is dispatched to a different unauthenticated repository field, enabling cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the HMAC `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, a value read directly out of the still-unauthenticated JSON body. Handlers, however, resolve which `Repository`/`Stack` to act on using a *different* field of that same unauthenticated body, `payload.dig('repository', 'full_name')`. Because both fields are attacker-controlled and nothing binds them to each other, an attacker who legitimately possesses the `webhook_secret` for organization A (e.g. they administer a GitHub App installed on their own org/repo, so GitHub itself signs real webhooks with A's secret, or they otherwise learn A's secret) can craft a raw body where `repository.owner.login` = `A` (making signature verification pass with A's secret) but `repository.full_name` = `B/some-repo`, a repository under an unrelated organization B configured in the same Shipit instance. The signature check and the repository-resolution logic never cross-validate that these two fields agree.

### Finding Description
- Signature verification: `Shipit.github(organization: repository_owner)` is looked up before the signature is verified, and `repository_owner` comes straight from the untrusted payload: [1](#0-0) [2](#0-1) 
- Multi-tenant config resolution keys GitHub Apps (and their distinct `webhook_secret`s) by organization name pulled from the payload: [3](#0-2) 
- Once the signature check passes (using organization A's secret), the actual event dispatch resolves the target `Repository`/`Stack` using `repository.full_name`, a completely separate field of the same body, with no re-check that it belongs to organization A: [4](#0-3) 
- `PushHandler`, for example, triggers a repository sync (`stack.sync_github`) for whatever stacks match the branch of the resolved repository: [5](#0-4) 

The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository the handler acts on**. Because `repository_owner` (used for auth) and `repository.full_name` (used for dispatch) are independent, unauthenticated fields inside the same JSON body, this equality is never enforced, breaking the "organization that authenticated versus the repository that is written" trust boundary called out in the rules.

### Impact Explanation
This allows a party who only holds one organization's webhook secret to forge webhook events (push, status, check_suite, pull_request, membership, etc.) that are dispatched against a *different* organization's repositories/stacks configured on the same Shipit instance. Depending on handler, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit statuses, or manipulate `Membership`/`Team` records for a repository the attacker does not control — a cross-organization/cross-repository integrity violation, which maps to the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability requires the attacker to legitimately hold (or otherwise obtain) the `webhook_secret` of at least one organization configured in the multi-tenant `secrets.github` map — for example, by being the administrator of their own GitHub App installation registered on the same Shipit instance, which is a realistic and unprivileged-with-respect-to-other-tenants scenario in a shared/multi-org Shipit deployment. No access to the target organization B's secret, GitHub credentials, or Shipit session is required.

### Recommendation
Bind the two fields cryptographically or logically before dispatch: derive the organization used for signature verification and the organization implied by `repository.full_name` from the same trusted source, and reject the request (422) if they disagree. Alternatively, verify the signature against every configured organization's secret only up to the point of matching, and then re-derive `repository_owner` strictly from the *same* nested object (`repository.owner.login`) that is used to compute `repository.full_name`, asserting they are identical, rather than trusting two independently attacker-suppliable fields.

### Proof of Concept
1. Shipit is configured multi-tenant with two orgs in `secrets.github`: `org-a` (attacker's own GitHub App, secret known to attacker) and `org-b` (victim), per the schema in `lib/shipit.rb:196-200`.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'org-a')`, verifies the HMAC successfully with org-a's secret, and allows the request through.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('org-b/victim-repo')` via `payload.dig('repository', 'full_name')` and triggers `sync_github` on org B's stacks, even though the request was never authenticated for org B.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
