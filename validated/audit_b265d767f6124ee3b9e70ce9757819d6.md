### Title
Splitting a pending-reward stake account during the calculation→distribution window triggers `assert_eq!` panic in `build_updated_stake_reward`, halting the cluster - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` compares a stake's *current* on-chain delegation (`stake.delegation.stake`, read fresh from `stakes_cache_accounts` at distribution time) plus the calculation-time inflation reward against `new_stake.delegation.stake`, which is a *snapshot* of the delegation taken during the earlier calculation phase [1](#0-0) . When the feature `relax_post_exec_min_balance_check` (`adjust_delegations_for_rent`) is inactive, any divergence between these two values (e.g., because the staker legitimately shrank their own delegation via `Split` between reward calculation and reward distribution) trips `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)`, panicking the validator during a consensus-critical accounting path.

### Finding Description
`begin_partitioned_rewards` computes `PartitionedStakeReward`s (including each stake's post-reward `Stake`) once, at the start of the epoch, from a stakes-cache snapshot [2](#0-1) . Distribution of these pre-computed rewards is then spread over `REWARD_CALCULATION_NUM_BLOCKS` and multiple partition blocks, driven by `distribute_partitioned_epoch_rewards` / `store_stake_accounts_in_partition` [3](#0-2) .

For each stake, `build_updated_stake_reward` re-reads the account's *current* state from `stakes_cache_accounts` at the moment of distribution (which reflects all transactions processed since the reward calculation, including the staker's own) [4](#0-3) . It then, in the non-rent-adjusted branch, asserts that `stake.delegation.stake + partitioned_stake_reward.inflation.stake_reward == new_stake.delegation.stake`, where `new_stake` is the calculation-time snapshot baked into `partitioned_stake_reward.inflation.stake` [5](#0-4) .

Nothing in this window prevents the stake account's authority (its legitimate owner) from issuing a normal `Split`, `Merge`, `DelegateStake`, or `Redelegate` instruction against their own account, which mutates `delegation.stake` in the stakes cache in between calculation and distribution — no such freeze/lock mechanism was found in the reviewed reward-status code (`EpochRewardStatus`/`epoch_reward_status`) that blocks stake-program instructions during an active reward interval. Because the pre-computed `partitioned_stake_reward` retains the stale, pre-split delegation value, the live delegation value read at distribution time no longer matches, and the `assert_eq!` fires.

Since this is bank/consensus code executed identically by every validator while processing the block, the panic is deterministic and occurs on all nodes at the same block height, producing a network-wide halt rather than a localized crash.

### Impact Explanation
This is a validator-panic / epoch-boundary-halt bug reachable purely by a normal user manipulating their *own* stake account with instructions they are fully authorized to send (no victim account, no signer bypass needed). Because reward distribution is deterministic bank-processing logic executed by every validator, triggering the panic causes a synchronized crash/halt across the cluster — matching the "validator panic/halt or split-brain state divergence" bounty category referenced in the audit scope.

### Likelihood Explanation
- Preconditions: `relax_post_exec_min_balance_check` feature inactive (the `else` / assert branch is taken) [6](#0-5) ; attacker owns a delegated, reward-eligible stake account.
- The attacker can predict which block/partition their stake falls into via the deterministic partition hashing (`hash_rewards_into_partitions`, using `parent_blockhash`), so they can time a `Split` transaction to land after reward calculation but before their partition's distribution block.
- Requires only a single, ordinary system/stake instruction the attacker is authorized to send on their own account — no special privileges, keys, or cluster control.
- Repeatable at every epoch boundary as long as the feature gate remains disabled.

### Recommendation
- Make the non-rent-adjusted branch tolerant of legitimate delegation changes rather than asserting equality: recompute rewards using the delegation observed at distribution time (as `recalculate_partitioned_rewards_if_active` already does for snapshot-restore), or fall back gracefully (skip/burn like `DistributionError`) instead of panicking, when the on-chain delegation no longer matches the calculation-time snapshot.
- Alternatively, prevent stake-modifying instructions from changing `delegation.stake` for stake accounts with an already-computed pending reward until distribution completes (an explicit lock keyed off `EpochRewardStatus`).
- At minimum, convert this consensus-invariant check into a recoverable `DistributionError` (burn reward, log) instead of `assert_eq!`, consistent with the `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` error-handling pattern already used in this function.

### Proof of Concept
Integration test outline (using `program-test`/bank warp harness, similar to `program-test/tests/warp.rs`):
1. Create a bank with a single delegated stake account owned by keypair `staker`, with enough stake to receive a nonzero reward, and ensure `relax_post_exec_min_balance_check` feature is disabled.
2. Warp to the epoch boundary so `begin_partitioned_rewards` computes and snapshots `PartitionedStakeReward` for `staker`'s stake (verify `EpochRewardStatus::Active(EpochRewardPhase::Calculation(_))`).
3. Before the block that distributes `staker`'s partition, submit a `stake_instruction::split` (signed by `staker`'s stake/withdraw authority) to split off part of the delegation into a new stake account, reducing the original account's `delegation.stake`.
4. Advance the bank to the block height corresponding to `staker`'s reward partition (`distribution_starting_block_height + partition_index`) and call `store_stake_accounts_in_partition` (or step the bank via `new_from_parent`).
5. Expected (buggy) result: the process panics inside `build_updated_stake_reward` at the `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)` line.
6. Expected (fixed) result: the reward is either recomputed against the reduced delegation, gracefully dropped/burned via `DistributionError`, with no panic and no assertion failure, and capitalization/stake accounting remains internally consistent.
