### Title
MultiEdit field reconstruction inserts artificial whitespace, allowing dangerous-pattern block rules to be bypassed by splitting payloads across edits - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`_extract_field` reconstructs the MultiEdit "new_text"/"content" field by joining every `edits[].new_string` with a literal space (`' '.join(...)`), which does not reflect how MultiEdit actually applies edits to the target file (sequential in-place string replacement, no inserted separators). An attacker-controlled agent can split a blocked pattern (e.g. `eval(`, a hardcoded secret marker, etc.) across two or more `new_string` entries so the space-joined string used for rule evaluation never contains the contiguous pattern, while the edits are applied to file locations that are adjacent in the real file, producing the exact dangerous contiguous string on disk.

### Finding Description
`evaluate_rules` → `_rule_matches` → `_check_condition` calls `_extract_field(field, ...)` to obtain the text a regex/contains rule is evaluated against [1](#0-0) . For `tool_name == 'MultiEdit'` and `field in ['new_text', 'content']`, the engine builds the check string as `' '.join(e.get('new_string', '') for e in edits)` [2](#0-1) .

This join is a synthetic construct invented purely for rule-matching; it has no relationship to the actual semantics of the `MultiEdit` tool, which performs independent `old_string` → `new_string` replacements at their respective locations in the file, with no space or separator inserted between them. If two edits target locations that are textually adjacent in the file (e.g., placeholder tokens with no whitespace between them, or one edit whose `old_string` ends exactly where another edit's `old_string` begins), the resulting file content will contain the two `new_string` values concatenated directly, with **no space**, while the rule-checking code inserts a space between them.

Consequently, an attacker (or a compromised/malicious repo-provided instruction that gets an unprivileged agent to construct such a MultiEdit call) can split a blocked contiguous token — such as `eval(`, `child_process`, `os.system(`, an API-key-looking string, or an exfiltration snippet — into two `new_string` fragments (e.g., `"ev"`, `"al("`) so that:
- Neither individual `new_string` matches the block regex.
- The space-joined reconstruction (`"ev al("`) also does not match a regex expecting contiguous adjacency (e.g., `r'eval\('`).
- Yet the real file, after both edits are applied at adjacent positions, contains the literal contiguous string `eval(`.

No other validation step re-scans the final file content after MultiEdit's edits are actually applied — the block/allow decision is made entirely from this synthetically joined string, so the bypass is silent and the operation is permitted.

### Impact Explanation
This is a hook/guard bypass: a rule configured with `action: block` and a `field: new_text` (or `content`) condition targeting `MultiEdit` operations (e.g., to block dangerous code execution primitives or secret-writing patterns) can be evaded, allowing the agent to write dangerous or exfiltration-capable code into the repository despite an administrator-configured block rule intended to prevent exactly that. This matches a trust-boundary/guard-bypass class of impact: a security control that is supposed to be authoritative (hookify block rule) is defeated by a parser/tokenization differential between what is checked and what is actually written to disk.

### Likelihood Explanation
Feasibility is high and fully deterministic: the attacker only needs the ability to influence the `edits` array passed to the `MultiEdit` tool (e.g., via a manipulated prompt, a malicious instruction embedded in repository content that an agent follows, or a crafted PR/issue that induces the agent to perform such edits) — no elevated privilege is required, and it works purely through standard `MultiEdit` usage. Splitting a token into two adjacent `new_string` fragments that get inserted next to each other in the file is a normal pattern for edits to adjacent code regions (e.g., inserting into a line piecemeal), so this is easily reachable through ordinary automation flows without any social engineering assumptions beyond the required "attacker/agent uses MultiEdit tool with attacker-influenced edits array" precondition already given.

### Recommendation
Do not synthesize an artificial separator when reconstructing MultiEdit content for rule evaluation. Instead:
1. Join `new_string` values with an empty string (`''.join(...)`) rather than a space, since that is closer to how adjacent replacements can concatenate in the final file, or
2. Better: reconstruct the actual resulting file content (or a close approximation) by simulating the sequential `old_string`→`new_string` replacements against the current file content (reading the target file via `file_path`), then run rule regexes against that reconstructed content.
3. At minimum, document that `_extract_field`'s MultiEdit reconstruction is heuristic/approximate and not a full-file simulation, and additionally run all block rules keyed on `content`/`new_text` against the actual post-edit file state (e.g., in a `PostToolUse` hook) as a second, authoritative check, rather than relying solely on the pre-application heuristic string.

### Proof of Concept
Unit test added to `plugins/hookify/core/rule_engine.py` test area:

```python
def test_multiedit_split_payload_bypasses_block_rule():
    rule = Rule(
        name="block-eval",
        enabled=True,
        event="file",
        conditions=[Condition(field="new_text", operator="regex_match", pattern=r"eval\(")],
        message="Dangerous eval() detected!",
        action="block",
    )
    engine = RuleEngine()

    # Attacker splits "eval(" across two adjacent edits
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": "app.py",
            "edits": [
                {"old_string": "PLACEHOLDER_A", "new_string": "ev"},
                {"old_string": "PLACEHOLDER_B", "new_string": "al("},
            ],
        },
    }

    result = engine.evaluate_rules([rule], input_data)

    # Expected (secure) behavior: block, because the file will contain "eval(" once
    # PLACEHOLDER_A and PLACEHOLDER_B (adjacent in app.py, e.g. "PLACEHOLDER_APLACEHOLDER_B")
    # are replaced.
    # Actual behavior: result == {} (no block), because
    # _extract_field joins new_strings as "ev al(" which does not match r"eval\("
    assert result != {}, "Block rule was bypassed via split MultiEdit payload"
```

Expected outcome demonstrating the bug: the assertion fails against current code (`result == {}`), proving the block rule is silently bypassed even though the resulting file content (`"...PLACEHOLDER_APLACEHOLDER_B..."` → `"...eval(..."`) contains the blocked pattern contiguously.

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
