### Title
Webhook signature is verified against the org derived from an unverified field, letting an attacker with one org's `webhook_secret` write to another org's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, a value read out of the still-unverified JSON body itself (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The handlers that actually act on the payload (e.g. `PushHandler`) instead resolve the target `Repository`/`Stack` from a different field of the same payload: `repository.full_name`. Nothing ties the two fields together, so the "organization that authenticated" and the "repository that is written" can be made to diverge. [1](#0-0) 

### Finding Description
`verify_signature` picks a `GitHubApp` instance keyed by `repository_owner`, and verifies the raw POST body's `X-Hub-Signature` against that org's configured `webhook_secret`: [2](#0-1) [3](#0-2) 

Each organization mounted on this Shipit instance has its own independent `webhook_secret` in configuration (`config/secrets.development.shopify.yml` shows this per-org structure), and `Shipit.github(organization: ...)` looks the secret up purely by name: [4](#0-3) [5](#0-4) 

Once the signature check passes, `Handler#stacks` (used by e.g. `PushHandler`) resolves the target repository from `payload.dig('repository', 'full_name')`, a completely different field of the same payload, with no re-check that it belongs to the organization whose secret validated the signature: [6](#0-5) [7](#0-6) [8](#0-7) 

Because HMAC-SHA1 verification only proves "this payload was signed by whoever holds `webhook_secret` for `repository_owner`", and the attacker legitimately controls their own org's `webhook_secret` (they installed the GitHub App on their own org/repo), they can compute a valid signature themselves over an arbitrary JSON body. Nothing in `verify_signature` or in `PushHandler`/`Handler#stacks` requires `repository.owner.login` to match `repository.full_name`'s owner segment. This is the exact class of bug from the report: a field the code trusts for one purpose (`slurp`'s live fee / here, org selection for signature verification) is decoupled from the field that is actually acted upon (yield distribution / here, the repository whose stack gets synced), and an attacker who legitimately controls one side of that binding can manipulate the outcome for the other side.

### Impact Explanation
An attacker who owns/administers any organization/repository that has this same Shipit instance's GitHub App installed (a normal, unprivileged setup step for any tenant org) knows that org's `webhook_secret`. They can:
1. Set `repository.owner.login` (or `organization.login`) to their own org — so `verify_signature` picks their own known secret and the HMAC check passes.
2. Set `repository.full_name` to `victim-org/victim-repo`, and `ref`/`after` to a branch/SHA of their choosing.
3. POST this self-signed payload to `/webhooks`.

`PushHandler` will look up `Repository.from_github_repo_name('victim-org/victim-repo')` and call `stack.sync_github(expected_head_sha: ...)`, forcing a `GithubSyncJob` to run against the victim's stack using Shipit's own installation-scoped GitHub API credentials for `victim-org` (`stack.github_api`, `Shipit.github(organization: owner)` in `Repository#github_app`). This causes commit ingestion / deploy-spec caching to run against a stack the attacker does not own, using cross-organization data manipulation without ever holding credentials for `victim-org`. This crosses a repository/authorization boundary this engine is supposed to enforce per-organization webhook isolation, satisfying "cross-repository writes" impact. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Requires only that: (a) the deployment hosts multiple organizations/tenants on one Shipit instance (a documented, supported configuration — see `config/secrets.development.shopify.yml`), and (b) the attacker controls at least one legitimate org with the GitHub App installed (i.e., a normal unprivileged tenant, not a Shipit admin). No `ApiClient` token, no GitHub write access to the victim repo, and no interception is required — only knowledge of a secret the attacker legitimately possesses for their own org. This matches an "unprivileged attacker" analog per the scan rules.

### Recommendation
After verifying the HMAC, cross-check that the organization used to select `webhook_secret` (`repository_owner`) matches the owner segment of `repository.full_name` (and any other repository-identifying field used downstream) before dispatching to handlers. Alternatively, derive the org strictly from `repository.full_name`'s owner and reject payloads where `organization.login`/`repository.owner.login` disagree with it.

### Proof of Concept
1. Attacker owns org `attacker-org`, which has installed the Shipit GitHub App with a known `webhook_secret = S`.
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `sha1=HMAC_SHA1(S, raw_body)` and sets it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully since the attacker signed with their own real secret.
6. `PushHandler#process` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack — a stack the attacker has no legitimate access to. [11](#0-10) [12](#0-11)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
