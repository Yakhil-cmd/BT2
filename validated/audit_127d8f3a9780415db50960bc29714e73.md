### Title
`is_valid_signed_package()` validates off-chain signatures against a stale, signer-chosen historical address definition instead of the address's current definition - ([File: formula/evaluation.js])

### Summary
The Keycloak CVE is a bug class where an authorization check validates a presented token against the *identity's claimed/asserted state* instead of re-checking the identity's *current* status, letting a disabled principal still obtain valid credentials. The analogous condition in `ocore` exists in the `is_valid_signed_package()` oscript/formula operator used by AAs to verify off-chain-signed messages (payment channels, order books, etc.). The "as of" point used to look up the signer address's definition is taken from a `last_ball_unit` field embedded *inside the signed package itself* — a value fully controlled by whoever constructs the signed package (the "signer", who could be an attacker holding an old/superseded private key) — rather than being tied to the AA trigger's own, network-determined `last_ball_mci`.

### Finding Description
`is_valid_signed_package` is implemented in `evaluate()` under case `'is_valid_signed_package'`: [1](#0-0) 

It calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`, only checking afterwards that `last_ball_mci === null || last_ball_mci > mci` is false, i.e. that the referenced last-ball is on or before the AA's own evaluation MCI: [2](#0-1) 

Inside `validateSignedMessage`, when the signed package is "network aware" (has a `last_ball_unit`), the address's definition is looked up **as of that embedded `last_ball_unit`**, not as of the AA's real, current `mci`: [3](#0-2) 

Because `signedPackage` (and therefore `last_ball_unit`) is data supplied by the party constructing the off-chain message — normally a legitimate counterparty in a payment channel or order-book contract, but potentially an attacker who once held valid signing keys for that address — the signer can pick *any* older, still-stable `last_ball_unit` for which the address definition used to be valid. If the true address owner has since revoked/replaced that definition (e.g., a `sig` keyset compromise prompted a keychange to a new definition, analogous to "disabling" the old credential), the old definition is still accepted for signature verification as long as an older stable last-ball can be cited. Ordinary on-chain unit validation does not have this weakness because `objValidationState.last_ball_mci` there is derived from the real unit's own parents/graph position, not from attacker-supplied data: [4](#0-3) 

This is the direct structural analog of the Keycloak flaw: the check that is supposed to gate on the principal's *current* authorization state (current address definition / active keys) instead trusts an attacker-selectable historical snapshot embedded in the very credential being validated.

### Impact Explanation
AAs such as payment-channel and order-book contracts rely on `is_valid_signed_package(trigger.data.sentByPeer, address)` to authenticate off-chain signed state (balances, fills, cancellations) attributed to one of the fixed parties, as seen in the payment-channel sample: [5](#0-4) [6](#0-5) 

If a channel/order-book party rotates its address definition after key compromise (its intended remediation, analogous to "disabling" the compromised credential), an attacker who possesses the old, superseded private key can still forge a `signed_message` package, pick an old but still-stable `last_ball_unit` from before the redefinition, and have it accepted by `is_valid_signed_package()` inside the AA. This can be used to submit a stale/false channel-closing balance or fraud proof, causing the AA to pay out funds based on unauthorized, outdated signer data — a concrete AA fund-loss/mis-payment scenario reachable purely by a private-payment/off-chain counterparty crafting a message, with no privileged network position required.

### Likelihood Explanation
Exploitation requires only: (1) an address owner who has changed/rotated their address definition at some point (a supported, expected operation), (2) an attacker in possession of that address's superseded signing key (e.g., from an earlier compromise that motivated the keychange), and (3) the existence of a stable, pre-rotation `last_ball_unit` to cite — which will always exist for any address that has ever transacted before its keychange. No cooperation from witnesses/hub/network attackers is needed; the attacker only needs to compose an oscript message as an ordinary AA trigger sender/counterparty. This makes the likelihood moderate-to-high wherever contracts trust `is_valid_signed_package` for authorization decisions tied to a specific address's *current* key material.

### Recommendation
When validating a signed package through `is_valid_signed_package()`, do not allow the embedded `last_ball_unit` to select an arbitrary historical definition-lookup point for the target address. Instead, either (a) always resolve the signer's definition as of the AA's own current, trusted `mci` (the value already passed in as `mci` to `evaluate()`), rejecting any `author.definition` mismatch with the *current* on-chain definition of `evaluated_address`, or (b) additionally require that no subsequent address-definition change has occurred between the cited `last_ball_unit` and the current AA evaluation `mci`, returning `false` if the address has been redefined since. This closes the gap between "was valid once" and "is valid now," matching the semantics that on-chain unit validation already enforces via `objValidationState.last_ball_mci`.

### Proof of Concept
1. Address `A` uses definition `D1 = ["sig", {pubkey: P1}]`. `A` engages in a payment-channel AA (`test/samples/payment_channels.oscript`) with counterparty `B`, funding the channel and exchanging off-chain signed balance updates signed with `P1`.
2. `A`'s private key for `P1` is later compromised. `A` protects funds by posting a unit that changes its address definition to `D2 = ["sig", {pubkey: P2}]` (a normal `address_definition_change`). This unit becomes stable at MCI `M2`.
3. The attacker, holding the compromised `P1` key, crafts a new `signed_message` claiming a *favorable-to-attacker* channel balance/fraud proof, sets `authors[0] = {address: A, definition: D1, authentifiers: {r: sig_with_P1}}`, and sets `last_ball_unit` to any stable unit from *before* `M2` (still valid, e.g. `M1 < M2`).
4. The attacker (as `B`, or colluding with `B`) submits this `signed_message` as `trigger.data.sentByPeer` in a `fraud_proof`/`close` trigger to the AA.
5. Inside `validateSignedMessage`, `storage.readDefinitionByAddress(conn, A, M1, ...)` returns `D1` (still valid as of `M1`), so the signature verifies successfully via `Definition.validateAuthentifiers`, even though `A`'s *current* definition is `D2`. `is_valid_signed_package()` returns `true`, and the AA processes the (attacker-controlled) stale state, potentially paying out channel funds based on unauthorized/outdated signer data attributed to address `A` after its keys were supposed to be revoked.

*Note: this PoC traces the exact code paths (`formula/evaluation.js` `is_valid_signed_package`, `signed_message.js` `validateSignedMessage`/`validateOrReadDefinition`, `storage.readDefinitionByAddress`) but was not executed against a live node; confirming the exact database state transitions around `address_definition_changes` timing would benefit from a live/test-harness run in a full Devin session.*
