## Title
AA data-feed reads from unstable ("unconfirmed") units allow execution before finality, enabling node disagreement / fund loss on reorg-like sequence flips - (File: `data_feeds.js`)

### Summary
The ZetaChain finding is a "confirmation bypass": a privileged-but-not-fully-trusted actor (observer) can push external chain data into on-chain processing (`InboundTracker`) without waiting for the same finality/confirmation depth that the normal path (`ObserveTxIn`) enforces, so a later block reorg can invalidate the data after funds have already moved. The reachable analog in `ocore` is `readDataFeedValue`/`dataFeedExists` in `data_feeds.js`, which let an Autonomous Agent (AA) read oracle data-feed values from **unstable** units — i.e. units that have not yet reached DAG finality and can still be re-sequenced as `final-bad` — instead of only from stable, finalized units.

### Finding Description
`readDataFeedValue()` in `data_feeds.js` has an `unstable_opts` parameter. When set, it scans `storage.assocUnstableMessages` for `data_feed` messages authored by units that are not yet stable and treats their values as usable inputs to AA logic: [1](#0-0) 

Likewise `dataFeedExists()` scans the same in-memory `assocUnstableMessages`/`assocUnstableUnits` structures for AA-authored unstable data feed posts (`bAA` branch): [2](#0-1) 

This is invoked from the oscript/formula evaluator for the `data_feed` and `in_data_feed` operations used inside AA definitions: [3](#0-2) [4](#0-3) 

The critical difference from the normal, safe path is the same class of bug as in the ZetaChain report: elsewhere in the codebase, reading committed on-chain state is guarded by explicit stability checks (`is_stable=1`, `main_chain_index<=last_ball_mci`), e.g. in payment input validation: [5](#0-4) 
and in the `unit` formula op, which explicitly rejects units that are not yet stable relative to `mci`: [6](#0-5) 

But the unstable-data-feed path deliberately skips this and consults an in-memory, per-node, propagation-dependent set (`storage.assocUnstableMessages`), which is populated as soon as a unit is received/validated locally, before consensus on its final sequence (`good`/`final-bad`) is reached: [7](#0-6) 

Because unstable units can still be resequenced to `final-bad` (the DAG equivalent of a "reorg" invalidating a transaction) when a conflicting/double-spending unit is later included and stability advances, an AA that already fired and paid out based on the unstable value has "front-run" finality: nodes that had received the unstable oracle unit at trigger time may compute one outcome, while nodes that received a competing unit (or none yet) compute a different outcome or none at all, causing the same class of impact called out in the report — the network/nodes disagree on validity, and funds can be paid out based on data that later turns out to have been on a losing/nonserial branch.

### Impact Explanation
If an AA is written to react to unstable data feeds (a documented but dangerous capability), any oracle or a party that can get two conflicting `data_feed` posts to different sets of peers before stabilization can cause AAs on different nodes to consume different unstable values for the same feed_name in the same query window. This causes:
- Non-deterministic AA trigger execution — different full nodes computing different responses for the same trigger unit, which the DAG's design assumes cannot happen (deterministic replay is core to `ocore`'s consensus model), i.e. "node disagreement on validity."
- If the unstable oracle unit is later voided (marked `final-bad`, analogous to invalidation on reorg), an AA that already disbursed funds against that data cannot claw the funds back — a direct funds-loss/inconsistency comparable to the double-spend scenario in the original report.

This qualifies as Medium/High under the same reasoning code423n4 judges used for the original finding: it requires a data-feed poster/oracle to act adversarially or simply be unlucky with timing, and is not trivial, but the root cause (finality/confirmation bypass for otherwise-guarded logic) is structurally the same defect class.

### Likelihood Explanation
Exploiting this requires an AA that actually enables the unstable-read mode (via `unstable_opts`/`bAA`-driven `in data feed`/`data_feed` behavior) and an oracle/attacker able to author conflicting data-feed units and control which peers see which unit before stabilization — network-timing-dependent, similar to the "difficult to practically exploit" caveat noted by the original report's authors and judges. I was not able to fully trace, within the available tool budget, every caller-side guard that determines exactly when `bAA`/`unstable_opts` is enabled versus forced to the safe "stable-only" branch (`formula/evaluation.js`'s `bAA` variable derivation was only partially inspected), so there is uncertainty about how broadly reachable this unstable-read mode is from ordinary AA authors versus only for restricted internal use (e.g., estimation-only paths like `aa_composer.js`'s `estimatePrimaryAATrigger`, which explicitly says "before it gets stable" and rolls back without committing).

### Recommendation
- For any AA logic path that can produce committed, fund-affecting side effects (real trigger execution, not just estimation/`bAir` dry-runs), disallow reading `data_feed` values from unstable units; require `is_stable=1` and `main_chain_index<=last_ball_mci`, exactly as done for payment inputs.
- If unstable-data-feed reads must be supported for latency reasons, restrict them to non-fund-moving informational paths only (e.g., UI estimation), and ensure the execution price (state changes recorded on-chain) always re-derives from the stable value at actual stabilization time rather than trusting the propagation-order-dependent unstable snapshot.
- Share/align the finality-check logic between the "stable" and "unstable" data-feed lookup code paths (mirroring the ZetaChain recommendation to unify `InboundTracker` and `ObserveTxIn`), so any future oracle/data-feed consumer cannot accidentally bypass the stability guard that the rest of validation.js enforces.

### Proof of Concept
Not independently reproducible from static analysis alone; a full PoC would require:
1. Deploy an AA whose `in data feed`/`data_feed` reference is evaluated in a context that sets `bAA`/`unstable_opts` truthy (reachable from AA-to-AA trigger evaluation per `data_feeds.js:34-97` and `205-241`).
2. Have an oracle author two data-feed units with conflicting values as parents of diverging DAG tips, sent to different peers before either stabilizes.
3. Trigger the AA on each side; observe that responses computed by nodes that saw different unstable data-feed units diverge, and that once one of the oracle units is later resolved as `final-bad`, the AA response computed against it cannot be undone.

Given the tooling limits (no live network to run this), this PoC could not be executed to hard-confirm cross-node divergence; the claim rests on the code-level absence of the stability guard that is present everywhere else the DAG performs financially consequential reads.
