### Title
`validate-agent.sh` aborts via `set -e` on first `((error_count++))`, silently truncating agent security validation - ([File: plugins/plugin-dev/skills/agent-development/scripts/validate-agent.sh])

### Summary
`validate-agent.sh` runs under `set -euo pipefail` and uses `((error_count++))` / `((warning_count++))` to tally issues starting from `0`. Because `((expr))` returns the exit status of the arithmetic *result* (`0` result → exit status `1`), the very first increment when `error_count` is still `0` (e.g., triggered by a missing `name:` field at line 61-63) makes the command "fail," and `set -e` immediately terminates the script before any subsequent checks (model, color, tools, system prompt) execute.

### Finding Description
At [1](#0-0) , `set -euo pipefail` is enabled for the whole script. `error_count` and `warning_count` are initialized to `0` at [2](#0-1) . The first place they can be incremented is the `name:` check: [3](#0-2) .

In bash, `((expr))` evaluates `expr` as an arithmetic expression and returns exit status `1` if the resulting value is `0`, and `0` (success) otherwise — this is unrelated to whether the increment itself "succeeded." For a post-increment `((error_count++))` where `error_count` is `0` before the operation, the expression's value is the *pre-increment* value, `0`, so the command's exit status is `1`, even though `error_count` is correctly updated to `1` internally. Under `set -e`, any non-zero exit status from a simple command aborts the script immediately, unless it's part of a conditional (`if`, `&&`, `||`, `!`, etc.) — which `((error_count++))` here is not.

This means: an attacker who supplies an `agents/*.md` file (or any similarly structured markdown consumed by this validator) that is missing the `name:` frontmatter field causes the script to silently exit right after printing "❌ Missing required field: name" — before the `description`, `model`, `color`, `tools`, and `system_prompt` checks at lines 90-203 ever run. Because the script exits due to `set -e` (not via the intentional `exit 1` at line 216 after the summary banner), it also never prints the final `❌ Validation failed with N error(s) and M warning(s)` summary, making the truncation non-obvious to whoever inspects the output.

This script is invoked as part of the trusted validation workflow by the `plugin-validator` agent, which explicitly documents using `validate-agent.sh` to validate agent files including checking `tools` grants as part of its "Security Checks" step: [4](#0-3)  and [5](#0-4) . It's also referenced by `agent-creator.md` as the recommended validation step for newly generated/attacker-influenced agent files: [6](#0-5) .

### Impact Explanation
An attacker-crafted agent markdown file that is missing `name:` (or reaches any other first-hit `error_count`/`warning_count` increment starting at zero) causes `validate-agent.sh` to bail out early via an uncontrolled `set -e` exit rather than completing its full field-by-field audit. Any later, security-relevant issues in the same file — most importantly an unrestricted `tools:` grant, or a malicious/oversized `SYSTEM_PROMPT` — are never reported to the invoking agent (`plugin-validator` or `agent-creator`), which may then present a false "looks fine" or incomplete report to the user, undermining the "complete validation before trust decision" invariant. This is a validation-bypass / silent-truncation issue that can cause a human or agent operator to install or trust an agent definition with unreviewed, potentially dangerous configuration (e.g., full tool access) because the validator's output looked shorter/cleaner than actual, or because downstream automation checks `exit 0`/`exit 1` status codes that no longer correctly correlate with "all checks ran."

### Likelihood Explanation
This is fully deterministic and requires no special access: any file lacking a `name:` field (the very first field checked) reliably triggers the bug on every invocation, on any standard bash implementation where `((var++))` follows POSIX arithmetic evaluation exit-status semantics. The precondition (agent markdown file missing `name:`, reachable via ordinary repository content, plugin submission, or a generated file) is trivial to construct and does not require malicious intent to occur — even benign malformed files reproduce it. It is 100% reproducible.

### Recommendation
Avoid `set -e`-fragile arithmetic increments. Use one of:
- `error_count=$((error_count + 1))` (assignment form doesn't reflect the arithmetic result in its exit status the same fatal way, or better: always returns success as an assignment statement), or
- `: $((error_count++))` (prefix with `:` to force success), or
- Temporarily disable `-e` around counters, or
- Wrap increments as `((error_count++)) || true`.
Apply this fix to every `((error_count++))` and `((warning_count++))` call site in the script (lines 63, 70, 77, 80, 86, 95, 102, 105, 111, 117, 126, 136, 146, 156, 176, 183, 186, 192) to guarantee validation always runs to completion and the accurate summary/exit code is produced.

### Proof of Concept
Unit/integration test:
1. Create `agent-missing-name.md`:
```
---
description: "Use this agent when testing"
model: unknownmodel
color: unknowncolor
tools: ["*"]
---
short
```
2. Run `bash plugins/plugin-dev/skills/agent-development/scripts/validate-agent.sh agent-missing-name.md`.
3. Assert the output contains ALL of: `❌ Missing required field: name`, a `model:` check line (`⚠️ Unknown model...`), a `color:` check line (`⚠️ Unknown color...`), the `tools:` line, and the `Checking system prompt...` / summary banner (`━━━...`) plus the final `❌ Validation failed with N error(s) and M warning(s)` line.
4. Expected (buggy) behavior: script exits immediately after printing `❌ Missing required field: name`, with `$?` reflecting the raw `((error_count++))` failure — none of the later section headers or the final summary line appear. This confirms the truncation.
5. After applying the fix (e.g., `: $((error_count++))`), rerun and assert all expected lines are present and the script correctly reaches `exit 1` at line 216 with the accurate error/warning counts.
