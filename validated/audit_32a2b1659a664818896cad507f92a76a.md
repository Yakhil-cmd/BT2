## Confirmed multi-org deployment: `Shipit.github_organizations` returns `secrets.github.keys` — Shipit supports several independent GitHub orgs, each with its own `webhook_secret` [1](#0-0) , and each org's admin legitimately knows/configures that org's `webhook_secret` in GitHub's webhook UI.

### Title
Webhook signature is verified against the organization named in the payload, not against the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check the HMAC against using `repository_owner`, taken from `params.dig('repository','owner','login')` (falling back to `organization.login`). Every webhook `Handler`, however, resolves the target `Repository`/`Stack` from a *different* field of the same payload: `payload.dig('repository','full_name')` [2](#0-1) . Nothing ties these two fields together, so a valid signature for organization A does not guarantee the acted-upon repository belongs to organization A.

### Finding Description
- `verify_signature` does: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(header, raw_post)` [3](#0-2) .
- `repository_owner` reads `repository.owner.login` (or `organization.login`) from the untrusted, attacker-supplied JSON body [4](#0-3) .
- The signature check itself only proves the raw POST body was HMAC-signed with the secret configured for `Shipit.github(organization: <owner.login from body>)` — it does not bind that org identity to any other field of the body [5](#0-4) .
- After signature verification passes, `WebhooksController#create` dispatches the parsed body to `Shipit::Webhooks.for_event(event)` handlers, unmodified [6](#0-5) .
- Every handler (`PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, etc.) looks up the target repository/stack via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a field that is never cross-checked against `repository.owner.login` used for signature selection [2](#0-1) [7](#0-6) .
- `StatusHandler` is especially dangerous: it writes CI status directly from unauthenticated payload fields onto any commit matching the given SHA, with no call back to GitHub to confirm the status is real: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [8](#0-7) .

**The broken binding**: `organization that authenticated the request` (`repository.owner.login`, used only to pick a `webhook_secret`) is treated as equal to `organization owning the repository that the handler subsequently writes to` (`repository.full_name`'s owner segment), but the engine never enforces that equality.

### Impact Explanation
In a Shipit deployment onboarding multiple orgs (`Shipit.github_organizations`), an administrator of Org A — who legitimately possesses Org A's `webhook_secret` (it's visible to them in GitHub's own webhook settings UI, no Shipit privilege required beyond controlling one org's webhook) — can craft an arbitrary raw HTTP POST to `/github/webhooks` (or wherever mounted) with:
- `X-Github-Event: status`
- Body: `{"repository":{"owner":{"login":"org-a"},"full_name":"org-b/victim-repo"},"sha":"<real commit sha of org-b stack>","state":"success","context":"<required-ci-context>"}`
- `X-Hub-Signature`: HMAC-SHA1 of that body using Org A's secret.

`verify_signature` passes because it only validates against Org A's secret (matched via `repository.owner.login: "org-a"`), while the actual write targets Org B's tracked commit/stack via `repository.full_name`. This forges a passing CI status for a commit in a completely unrelated organization's repository, which the merge-queue (`MergeRequest#all_status_checks_passed?` / `StatusChecker`) or continuous-deployment logic uses to gate auto-merge and auto-deploy — i.e., it can produce an **unauthorized ship** (deploy/merge) driven by forged status data, satisfying the "unauthorized deploy, rollback or merge" High/Critical impact bar. The same organization/repository mismatch applies to `push`, `pull_request`, and `check_suite` events as well.

### Likelihood Explanation
Requires only that the attacker administers (or has once had access to configure) the webhook for any single onboarded GitHub organization in a multi-org Shipit install — a realistic scenario for organizations that let multiple teams/orgs self-service onboard repos to a shared Shipit instance. No Shipit account, `ApiClient` token, or GitHub App private key is needed; only knowledge of one org's `webhook_secret`, which that org's own admins possess by design. This is a plausible, unprivileged-relative-to-the-target-org attack.

### Recommendation
In `WebhooksController#verify_signature` / the `Handler` base class, after verifying the signature, re-derive the organization from `repository.full_name`'s owner segment and assert it matches `repository_owner` (the org whose secret validated the signature) before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Onboard two orgs in `secrets.github`: `org-a` (attacker-controlled/known secret) and `org-b` (victim, tracked stack with continuous deployment or merge-queue enabled).
2. Attacker POSTs to the webhooks endpoint:
   ```
   X-Github-Event: status
   X-Hub-Signature: sha1=<hmac-sha1(body, org_a_webhook_secret)>
   body: {"repository":{"owner":{"login":"org-a"},"full_name":"org-b/victim-repo"},
          "sha":"<sha of pending org-b commit>","state":"success","context":"required-ci"}
   ```
3. `verify_signature` selects `Shipit.github(organization: "org-a")`, verifies HMAC against `org-a`'s secret — passes.
4. `StatusHandler#process` runs `Commit.where(sha: ...).each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto the `org-b` commit [8](#0-7) .
5. If that context is required by `org-b`'s merge queue / continuous deployment, the forged status can unblock an automatic merge or deploy.

**Note on confidence**: I could not fully trace, within the available index, whether `StatusChecker`/merge-queue logic in this specific engine snapshot always re-verifies statuses against live GitHub data before merging (some code paths call `stack.github_api.pull_request` afterward, which could reconcile state) — a background Devin session with full repo access would be needed to confirm end-to-end exploitability of the auto-merge path versus only the CI-status write itself.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
