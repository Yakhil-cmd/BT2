### Title
Rounding of `earned_headers_commission_share` Percentages Allows Minting of Extra Bytes - (File: `headers_commission.js`)

### Summary
The reported bug class is a decimal/scale-conversion flaw where a fixed-point quantity is repeatedly divided/rounded without preserving the invariant that the parts must sum exactly to the whole, causing value to be created or lost. In `afiVault.sol` this happened when scaling assets vs. shares; in `ocore`, the analogous defect exists in the headers-commission distribution logic, where a fixed commission amount is split among multiple recipients by percentage and each share is independently rounded with `Math.round()`, without any check that the rounded parts sum back to the original amount.

### Finding Description
When a unit is included by the network and wins headers commission, the winning child unit's `earned_headers_commission_recipients` list (an array of `{address, earned_headers_commission_share}` where the shares are validated only to be positive integers summing to `100`) is used to split the fixed `full_amount` (the payer unit's `headers_commission`) among the recipients: [1](#0-0) 

```
var full_amount = assocWonAmounts[child_unit][payer_unit];
if (objUnit.assocEarnedHeadersCommissionRecipients) {
    for (var address in objUnit.assocEarnedHeadersCommissionRecipients) {
        var share = objUnit.assocEarnedHeadersCommissionRecipients[address];
        var amount = Math.round(full_amount * share / 100.0);
        arrValuesRAM.push("('"+payer_unit+"', '"+address+"', "+amount+")");
    };
}
```

The same rounding is repeated for the SQL/non-`bFaster` code path: [2](#0-1) 

Each recipient's share of the commission is rounded to the nearest integer **independently**, and the resulting per-recipient amounts are inserted directly into `headers_commission_contributions` and later summed into `headers_commission_outputs` without ever re-checking that `SUM(amount) === full_amount`. Because `Math.round` is applied to each fractional share separately, the sum of the rounded parts can exceed the original `full_amount` whenever the fractional remainders of the individual shares are all `>= 0.5`.

The only validation performed on `earned_headers_commission_recipients` is: [3](#0-2) 

which enforces that shares are positive integers, addresses are valid and sorted, and the percentages sum to exactly `100` — but it does **not** constrain how the shares are chosen relative to the eventual `full_amount`, nor does it require the recipient addresses to be authors of the unit. Any unit author can freely choose share percentages (e.g. `50/25/25`) that are guaranteed to produce a rounding surplus for *any* possible `full_amount` value that isn't a multiple of 4, and can list arbitrary addresses (including addresses they themselves control) as recipients.

### Impact Explanation
Headers commission represents a fixed, already-collected pool of bytes (the transfer/header fee paid by the parent unit). The distribution logic is supposed to merely reallocate this fixed pool among recipients, never create new value. By choosing share percentages such as `50, 25, 25` (sum = 100) an attacker who authors a multi-recipient `earned_headers_commission_recipients` list can force the sum of `Math.round(full_amount*share/100)` to exceed `full_amount`, e.g. for `full_amount = 3`: `round(1.5)=2, round(0.75)=1, round(0.75)=1` → total `4` instead of `3`. Every time a unit with such a crafted recipient list wins headers commission from a parent, up to a few extra bytes per event are minted out of thin air into `headers_commission_outputs`, which are directly spendable balances. This is a genuine (if per-instance small) supply-inflation bug: repeated over many units/parents, an attacker fully controlling the addresses in the recipient list can accumulate free bytes without any corresponding burn, in a way this ocore commit is silent about and never checks.

### Likelihood Explanation
This requires no special privilege: any address can author a unit and add a valid `earned_headers_commission_recipients` array (constrained only by `validateHeadersCommissionRecipients` in `validation.js`), then simply wait to win headers commission through the ordinary, unprivileged unit-inclusion/parent-selection process (`getWinnerInfo` random-hash based selection in `headers_commission.js`). No cooperation from witnesses, hubs, or other privileged actors is needed — an attacker who controls multiple addresses can list them all as recipients with rounding-favorable percentages and repeat the attack across many units over time.

### Recommendation
When distributing `full_amount` across `earned_headers_commission_recipients`, round all-but-the-last recipient normally and assign the last recipient `full_amount - sum(previous rounded amounts)` (or use a similar remainder-based allocation), so the sum of distributed amounts is always exactly `full_amount`. Apply this fix identically to both the in-RAM (`assocEarnedHeadersCommissionRecipients`) and SQL (`profit_distribution_rows`) code paths in `headers_commission.js`, and add a consistency assertion (already partially present as the `_.isEqual` sanity check between RAM and SQL results) that also verifies `SUM(computed amounts) === full_amount` for every payer/child pair.

### Proof of Concept
1. Attacker controls addresses `A1 < A2 < A3` (sorted, as required by validation).
2. Attacker authors (or co-authors) a unit and sets:
   `earned_headers_commission_recipients = [{address: A1, earned_headers_commission_share: 50}, {address: A2, earned_headers_commission_share: 25}, {address: A3, earned_headers_commission_share: 25}]`
   — this passes `validateHeadersCommissionRecipients` since the shares are positive integers summing to `100`.
3. The unit is included as a child that (probabilistically, via `getWinnerInfo`) wins headers commission from a parent whose `headers_commission` (i.e., `full_amount`) is not a multiple of 4 (e.g. `full_amount = 3`).
4. `calcHeadersCommissions` computes, for each recipient: `Math.round(3*50/100)=2`, `Math.round(3*25/100)=1`, `Math.round(3*25/100)=1`, totaling `4` instead of `3`.
5. `headers_commission_outputs` now credits the attacker's three addresses with a combined `1` extra byte relative to `full_amount`, spendable like any other confirmed balance — repeatable indefinitely across many won parent units to accumulate inflated bytes.

```javascript
function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
```
