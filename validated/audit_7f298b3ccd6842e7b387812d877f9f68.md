### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for the `allow_with_label`/`prevent_with_label` branches due to `&&`/`||` operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` with three provisioning-behavior checks using Ruby's default operator precedence, where `&&` binds tighter than `||`. As written, `review_stacks_enabled` is only ANDed into the `allow_all` disjunct; the `allow_with_label` and `prevent_with_label` disjuncts are independent of it, so disabling `review_stacks_enabled` does not disable those two behaviors.

### Finding Description
Binding claimed by the operator's intent: `repository.review_stacks_enabled == false` should imply `provision? == false` for all three `provisioning_behavior` values (`allow_all`, `allow_with_label`, `prevent_with_label`).

Actual code, [1](#0-0) :
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` has higher precedence than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `provisioning_behavior` is `prevent_with_label` (or `allow_with_label`), the truth of `provision?` depends only on the label check — `review_stacks_enabled` is never consulted. If an operator sets `review_stacks_enabled = false` intending to pause all dynamic review-stack provisioning for a repo configured with `prevent_with_label`, the third disjunct still evaluates to `true` for any PR lacking the provisioning label, and `respond_to_pull_request_opened?` returns `true`, causing `ReviewStackAdapter#find_or_create!` to run and provision a new `Stack`, [2](#0-1) .

The repo owner (attacker, per the threat model) triggers this simply by opening a pull request without the provisioning label on their own repository, which is normally already integrated with Shipit via a legitimate signed webhook — no secrets are needed for this step since it's the standard "opened" webhook flow from GitHub. None of the usual guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) address this because they validate webhook authenticity/shape, not the provisioning-behavior/`review_stacks_enabled` business logic, which is exactly where the flaw lives.

### Impact Explanation
A repository operator who disables `review_stacks_enabled` believing it globally halts automatic review-stack creation is wrong for repos using `allow_with_label` or `prevent_with_label`. The PR author (an unprivileged party who merely owns/contributes to the tracked repository) can still force `Shipit::Stack` creation and provisioning by opening (or leaving unlabeled) a pull request. Because review-stack provisioning executes repository-defined tasks/commands as part of provisioning and later deploy/rollback flows, this results in execution of attacker-influenced pipeline steps on a feature that the operator explicitly believed was disabled — a real "operator-disabled feature still executes attacker steps" scenario. This is repeatable per pull request and applies to every repository configured with `allow_with_label`/`prevent_with_label` plus `review_stacks_enabled = false`.

### Likelihood Explanation
Preconditions: the repository must already be registered in Shipit and set to `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?`, with `review_stacks_enabled` toggled off by an operator (a plausible, even likely, misconfiguration path since the settings UI presents `review_stacks_enabled` as a single master toggle, [3](#0-2) ). No attacker credentials, tokens, or secrets are required beyond normal PR-opening capability on the tracked repo. This is low-cost and fully repeatable.

### Recommendation
Add explicit parentheses (or refactor to an explicit early-return) so `review_stacks_enabled` gates all three behaviors, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In (out-of-scope for direct citation, but illustrative) `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not provision stacks for repos with prevent_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no provisioning label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before toggling, `repository.review_stacks_enabled` is `true` and `provision?` is `true` for an unlabeled PR; after setting `review_stacks_enabled = false`, `provision?` must also become `false` — currently it stays `true`, and `Shipit::Stack.count` increases, demonstrating the divergence.
