### Title
Cross-organization webhook forgery triggers unauthorized sync/deploy for a foreign stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects the GitHub App configuration (and thus the webhook secret) used to verify the HMAC signature based on the `repository.owner.login` field read from the *same* attacker-supplied JSON body it is about to validate, while the event handlers resolve the *actual* Stack/repository to act on using a different field, `repository.full_name`, from that same body. Nothing ties these two fields together, so a signature that is valid for organization A's webhook secret can carry a forged payload whose `repository.full_name` points at organization B's repository, letting the request act on B's stack under A's authentication.

### Finding Description
`verify_signature` picks the app config by: [1](#0-0) [2](#0-1) 

using `Shipit.github(organization: repository_owner)`, and verifies the HMAC over the whole raw body with that organization's `webhook_secret`: [3](#0-2) 

The `create` action then hands the parsed body to the registered handlers unchanged: [4](#0-3) 

Handlers resolve the target Stack(s) not via `repository.owner.login` but via `repository.full_name`: [5](#0-4) 

and act on it, e.g. `PushHandler` enqueues a sync for every matching stack: [6](#0-5) 

Because both `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the target stack) are attacker-controlled fields inside the same signed body, and the controller never asserts that `full_name` is owned by `repository_owner`, an attacker who legitimately controls a *different* organization configured on the same Shipit instance (per the documented multi-org `secrets.yml` layout: `github_app_config`/`TOP_LEVEL_GH_KEYS`) can compute a valid HMAC with their own org's `webhook_secret` over a body claiming `repository.owner.login = "org-A"` (their own org) but `repository.full_name = "org-B/target-repo"` (a victim org hosted on the same instance). Verification succeeds because it only checks the signature against org-A's secret and the raw body content — it never checks that `full_name`'s owner equals `repository_owner`. [7](#0-6) 

This breaks the binding "organization that authenticated" (org-A, via its own webhook secret) versus "repository that is written" (org-B's stack, selected via `full_name`), letting an attacker who is unprivileged with respect to org-B trigger handler logic (sync, review-stack creation/archival, label capture, status writes, etc.) against org-B's stacks.

### Impact Explanation
Any registered webhook handler can be invoked against a foreign organization's stack once its `full_name` is matched, e.g.:
- `PushHandler` enqueues `GithubSyncJob` for org-B stacks, which can trigger the ingestion of new upstream commits and, if `continuous_deployment` is enabled on org-B's stack, an automatic unauthorized deploy at a time chosen by the attacker.
- `PullRequest::OpenedHandler`/`ReviewStackAdapter` can create or archive org-B review stacks, provisioning/deprovisioning infrastructure without org-B's knowledge.
- `status`/`check_suite` handlers can inject fabricated CI status data for org-B commits, which downstream can gate or unblock deploys.

This matches the "unauthorized deploy" / "cross-repository writes" High/Critical category, since it lets a party with no privilege over org-B trigger state changes and deploy timing on org-B's stacks using only credentials legitimately belonging to org-A.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with the documented multi-organization `github:` block in `secrets.yml` (each top-level key is a distinct organization with its own `webhook_secret`), which is an explicitly supported and documented deployment mode. Any admin/operator of one of the configured organizations (an "unprivileged attacker" with respect to any other configured organization) can exploit this by directly POSTing a forged, self-signed payload to `/github/webhooks` — no GitHub session, App private key, or victim-org credentials are required.

### Recommendation
In `WebhooksController`, after verifying the signature, re-validate that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) used to select the signing key, and reject the request (422) if they diverge. Alternatively, have handlers derive the owning organization strictly from `repository_owner`/the app that verified the signature rather than trusting `repository.full_name` alone, and cross-check it against the `Repository`/`Stack`'s actual configured organization before dispatching.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `org-A` (attacker-controlled, webhook secret known to attacker) and `org-B` (victim, hosts a tracked stack `org-B/target-repo`).
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha already on org-B/target-repo's main branch>",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-A_webhook_secret, body)` themselves (they legitimately know org-A's secret).
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "org-A")` and verifies successfully against the attacker-controlled secret.
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `payload.dig('repository','full_name') == "org-B/target-repo"` and enqueues `GithubSyncJob` for org-B's stack — triggering sync/possible auto-deploy on a stack the attacker has no legitimate access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
