### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any other stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`stack_id` set) may only access that stack, by routing all stack lookups through `stacks`/`stack`, which filters by `current_api_client.stack_id`. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, looking up `Stack.from_param!(params[:stack_id])` directly, so any valid `read:stack` token — even one created for/limited to a specific stack — can read the build status of an arbitrary stack it was never authorized for.

### Finding Description
`BaseController#stack` is the scoping mechanism that binds a token's authorization to a specific stack: [1](#0-0) 

`current_api_client.stack_id?` restricts the `Stack` relation to the one stack the client was scoped to when it isn't a global client. This is the equality that should hold for every stack-scoped API action: `authorized_stack(token) == stack_touched(request)`.

`CCMenuController`, however, redefines `stack` independently of `BaseController`, discarding the `stacks` scoping: [2](#0-1) 

The action only enforces `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains `read:stack`: [3](#0-2) 

It never checks that `params[:stack_id]` matches `current_api_client.stack_id`. Since the route accepts an arbitrary `stack_id` path segment (`scope '/stacks/*stack_id' ... get '/ccmenu' => 'ccmenu#show'`), any stack identifier can be supplied: [4](#0-3) 

Before/after state of the binding:
- Before (intended invariant, enforced elsewhere e.g. `StacksController#show`): `stack == current_api_client.stack` when the client is scoped.
- After (in `CCMenuController#show`): `stack == params[:stack_id]` unconditionally, regardless of `current_api_client.stack_id`.

This is a direct structural analog of the "parallel measurement system" bug class in the referenced report: one code path (`BaseController#stack`) is the trusted authorization binding, while a second, independently-implemented path (`CCMenuController#stack`) performs the equivalent operation using a different, unverified input, breaking the binding between "stack a token authorizes" and "stack a request actually touches."

### Impact Explanation
An attacker who possesses (or is issued) any `ApiClient` token with `read:stack` permission — including one deliberately scoped to a single stack — can read the CI/build status (last build status/label/time, activity, `webUrl`) of every other stack in the Shipit instance by simply changing the `stack_id` in the URL. This is a cross-tenant/cross-repository authorization bypass: the token's scope binding (`stack_id`) is completely ignored by this endpoint. Per the engine's authorization model, this constitutes unauthorized read access to stack state that a token was not provisioned for, matching the "escalation into unauthorized read of stack state" High-impact category.

### Likelihood Explanation
Likelihood is high: it requires no special conditions beyond possessing any valid API token with the widely-granted `read:stack` permission (the default/most common permission, also used to auto-provision "CCMenu Client" tokens via `CCMenuUrlController`). No signature forgery, no privileged account, and no additional exploit chaining is needed — only changing a URL path segment.

### Recommendation
Remove the `stack` override in `CCMenuController`, or make it explicitly re-use the scoped lookup from `BaseController` (`stacks.from_param!(params[:stack_id])`) so the `current_api_client.stack_id` restriction is enforced consistently across all API controllers, closing the divergence between the two independent stack-resolution code paths.

### Proof of Concept
1. As an admin, create (or observe the auto-created) `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g. fixture `here_come_the_walrus`, as in `test/fixtures/shipit/api_clients.yml`).
2. Confirm the scoping is enforced elsewhere, e.g. via `Api::StacksController#index`, which returns only stack A (see test `"an api client scoped to a stack will only see that one stack"` in `test/controllers/api/stacks_controller_test.rb` lines 217-223).
3. Using the same token, call `GET /api/stacks/<owner_B>/<repo_B>/<env_B>/ccmenu` where stack B ≠ A.
4. Observe HTTP 200 with stack B's build status XML returned (`Api::CCMenuController#show` → `stack` → `Stack.from_param!(params[:stack_id])`), despite the token being scoped only to stack A — confirming the authorization bypass. [5](#0-4)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
