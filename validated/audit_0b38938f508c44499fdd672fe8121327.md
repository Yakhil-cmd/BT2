### Title
`Webhooks::Handlers::StatusHandler#process` resolves `Commit.where(sha:)` unscoped by repository/stack, letting a legitimately-signed status webhook from one stack's repository forge `deployable?` on commits belonging to any other stack tracking the same SHA, with `Commit#locked?` (default `false`) providing no protection - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no `stack_id`/repository scoping, then calls `commit.create_status_from_github!` on every match. Combined with `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`), a webhook that is validly signed for one organization/repository can flip `deployable?` to `true` on a commit belonging to a different stack, because the only local guard (`locked?`) defaults to `false` for every freshly tracked commit.

### Finding Description
Binding claimed broken: `commit.locked? == false` (default, per `Commit#lock`/`#unlock` at `app/models/shipit/commit.rb:338-354` and the absence of any other default-true lock path) AND `deployable? = !locked? && (stack.ignore_ci? || (success? && !blocked?))` at `app/models/shipit/commit.rb:227-229`. This equality holds: the audit is correct that `locked?` is `false` by default and is the only local condition in `deployable?` that could block a forged status.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) validates `X-Hub-Signature` against `Shipit.github(organization: repository_owner)`'s webhook secret. This confirms the payload came from GitHub for the *organization named in the payload* - it does **not** verify that the `sha` inside the payload belongs to the repository/stack the attacker controls, nor does it scope processing to a specific `Repository`/`Stack` record.
2. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a global, cross-stack, cross-repository lookup keyed only on `sha`, with `state`/`context`/`target_url` fully attacker-supplied in the payload for the org that signed the request.
4. `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`, `366-386`) persists a `Status` record and recomputes `status`, which feeds `success?`/`blocked?`/`deployable?`.
5. Because `locked?` defaults to `false` for every newly-tracked commit, and no other guard in `deployable?` checks which repository/stack originated the status, `deployable?` becomes `true` as soon as a `state: "success"` status for a matching `sha` lands - regardless of which repository's webhook produced it.

Why existing guards don't help: `verify_signature` authenticates "this payload came from GitHub for org X," not "this `sha` belongs to a commit tracked by a stack whose repository is X." `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, String` / `requires :state, String`) validate shape, not repository ownership. There is no `stack_id`/`repository` filter anywhere in `StatusHandler`.

Attacker exploit flow: the practically exploitable case is when the same GitHub repository is tracked by more than one Shipit `Stack` (a documented, common Shipit configuration - e.g., separate `staging`/`production` stacks against one repo, or forks sharing commit history/branches). An attacker who can push a branch or open a PR in that repository (per the attacker model) causes GitHub to emit a genuinely-signed `status` webhook (e.g. via their own CI check) referencing a `sha` that is also tracked as a `Commit` row under a *different* stack. Because the SHA is identical (same underlying git object shared across stacks/forks), `Commit.where(sha:)` matches both rows, and the forged/attacker-influenced `state` is written onto the other stack's commit, flipping its `deployable?` to `true` without that stack's own CI having produced a success status. True SHA-1 collision across *entirely unrelated* repositories is not practically feasible, so the exploit is bounded to stacks that share commit history/SHAs with the attacker-reachable repository.

### Impact Explanation
A forged/cross-tenant `Status` write lets an attacker mark a commit as `success` in a stack they do not own, causing `Commit#deployable?` to become `true` and, in turn, `schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) can enqueue `ContinuousDeliveryJob`, potentially triggering an unauthorized deploy in the victim stack if continuous deployment is enabled. This matches the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." The blast radius is limited to stacks that track a repository whose commit history/branches are reachable by the attacker (shared-repo, multi-stack, or fork scenarios), not arbitrary unrelated third-party repositories, since matching `sha` values across genuinely different repositories is not feasible.

### Likelihood Explanation
Preconditions: (1) the target repository must be tracked by more than one Shipit `Stack`, or share actual commit SHAs with a repository/branch the attacker controls (a realistic and common deployment topology, e.g., staging/production stacks on one repo); (2) the attacker needs the ability to cause GitHub to emit a `status` event for that SHA (e.g., via their own CI/Action running against their branch, or any status-producing integration on a repo they can push to). No Shipit secrets, sessions, or GitHub App keys are required — the webhook is genuinely signed by GitHub for the organization that owns the repository. Cost is low and the action is repeatable for every matching `sha`. This differs from a "misconfigured edge case" only in that it requires shared/tracked SHAs; standard multi-stack-per-repo setups satisfy this.

### Recommendation
Scope `StatusHandler#process` (and analogously `CheckSuiteHandler`) to commits belonging to stacks whose tracked repository matches `params.dig('repository', 'full_name')` (or organization/repo derived from the payload), e.g. `Commit.joins(:stack).merge(Stack.where(repository: repo)).where(sha: params.sha)`, instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/commit_test.rb` and `test/models/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Assert default-safety binding: `commit = shipit_commits(:first); assert_equal false, commit.locked?` (via fixture/schema default, no explicit lock call).
2. Create two `Stack` fixtures (`stack_a`, `stack_b`) each tracking a `Commit` with the identical `sha` value (simulating shared history / multi-stack-per-repo).
3. Ensure `stack_b`'s commit currently has `deployable? == false` (e.g., no successful status yet, `locked? == false`).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(sha: shared_sha, state: 'success', context: 'ci', target_url: nil, description: nil, created_at: Time.now.to_s).call` (bypassing the controller/signature layer, as the handler itself has no repository check).
5. Reload `stack_b`'s commit and assert `commit.deployable? == true`, demonstrating the cross-stack write succeeded purely because `locked?` was `false` by default and `StatusHandler` never checked which stack/repository the status belonged to.
