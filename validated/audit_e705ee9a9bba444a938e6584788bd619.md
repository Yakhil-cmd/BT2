### Title
Webhook signature verification uses `repository.owner.login` while event processing trusts `repository.full_name`, allowing a webhook "verified" against an organization with no `webhook_secret` to mutate a different, secret-protected organization's stack - (`app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check against using `repository_owner` (`params.dig('repository','owner','login')`), but the downstream `PushHandler` resolves the target `Stack` using `payload.dig('repository','full_name')` via `Handler#repository_name`. Because both values are read unauthenticated from the same attacker-supplied JSON body and are never cross-checked, an attacker can set `repository.owner.login` to any org configured with no `webhook_secret` (trivially "verified") while setting `repository.full_name` to `victim-org/victim-repo`, causing `stack.sync_github` to run for the victim stack with an attacker-chosen `after` SHA.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`organization_whose_secret_verified_signature (Shipit.github(organization: params.dig('repository','owner','login')))` == `organization_owning_the_mutated_stack (Repository.from_github_repo_name(payload.dig('repository','full_name')).owner)`

Code path:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository','owner','login')`, then calls `github_app.verify_webhook_signature(header, raw_post)`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved app's `webhook_secret` is blank - no HMAC comparison occurs at all. [3](#0-2) 
3. `#create` re-parses `request.raw_post` into a fresh `params` hash and dispatches to registered handlers for the event, passing the whole body. [4](#0-3) 
4. `Handler#repository_name` (used by `PushHandler` via `stacks`) reads `payload.dig('repository', 'full_name')` - a completely independent field from the one used in step 1 - to resolve the `Repository`/`Stack`. [5](#0-4) 
5. `PushHandler#process` finds non-archived stacks on that repository matching the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)`, with `after` fully attacker-controlled. [6](#0-5) 

Attacker's exact request: `POST /webhooks` with `X-Github-Event: push`, an arbitrary/garbage (or absent) `X-Hub-Signature`, and a JSON body where `repository.owner.login = "org-with-no-secret"` and `repository.full_name = "victim-org/victim-repo"`, plus `ref`/`after` set to the attacker's target branch/SHA. No knowledge of victim-org's secret, session, or API token is required.

Why existing guards fail: `drop_unhandled_event` only checks the event name is registered, not payload consistency. `verify_signature`'s only failure modes are an unknown organization (`GithubOrganizationUnknown`) or a mismatched signature when a secret exists for that organization - neither triggers here because `org-with-no-secret` is a known, configured organization with `webhook_secret` blank. `PushHandler`'s `ExplicitParameters` schema only requires `:ref` and `:after`; it performs no validation that `repository.owner.login` matches the owner of `repository.full_name`. No other code cross-checks these two fields.

### Impact Explanation
This is a cross-tenant authentication bypass: an event that was never cryptographically bound to `victim-org` triggers `Stack#sync_github` on `victim-org`'s real, secret-protected stack. This can move the stack's tracked HEAD to an attacker-chosen SHA, which can influence subsequent deploy/CI status and merge-queue behavior. It is repeatable against any repository/stack whose owning organization is configured in `Shipit.github_configuration`, as long as any other organization in the same install lacks a `webhook_secret` (a documented, non-default but plausible multi-org configuration - see `docs/setup.md`'s "Using Multiple Github Applications" section and `test/dummy/config/secrets_double_github_app.yml`, which both show `webhook_secret:` left blank per-org). This matches the specified Critical category: "a payload for one repository mutating another's stack."

### Likelihood Explanation
Requires: (a) a Shipit instance configured with multiple GitHub organizations (per-org config keyed by organization login), (b) at least one configured organization with no `webhook_secret` set, and (c) an existing `Stack` for the victim repository. Given those preconditions - which are operator misconfiguration but not attacker-controlled secrets - the attack costs a single unauthenticated HTTP POST with no valid signature, and is trivially repeatable against any tracked repository/branch in the install.

### Recommendation
Bind signature verification to the same repository/organization actually used for event processing: derive the organization used for both `verify_webhook_signature` and stack resolution from a single trusted source (e.g., resolve the `Repository`/owning organization from `full_name` first, then verify the signature using that organization's secret), and reject the webhook if `repository.owner.login` doesn't match the owner of `repository.full_name`. Do not treat "no secret configured for org X" as authorizing changes to unrelated org Y's stacks.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test "cross-org forged push cannot mutate a differently-owned stack" do
  # Precondition: configure two orgs, one with no webhook_secret
  Shipit.stubs(:github).with(organization: 'org-with-no-secret').returns(
    Shipit::GitHubApp.new('org-with-no-secret', { webhook_secret: nil })
  )

  victim_repo = shipit_repositories(:shipit) # owner: 'shopify', has an existing stack
  stack = victim_repo.stacks.first

  forged_payload = {
    ref: "refs/heads/#{stack.branch}",
    after: "deadbeefattackercontrolledsha",
    repository: {
      owner: { login: 'org-with-no-secret' },   # equality LHS: verified org
      full_name: victim_repo.github_repo_name    # equality RHS: mutated org's repo
    }
  }.to_json

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=garbage-or-absent'

  # Assert the two sides of the binding: verified org != mutated repo's owner
  assert_not_equal 'org-with-no-secret', victim_repo.owner

  Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeefattackercontrolledsha')

  post :create, body: forged_payload, as: :json
  assert_response :ok
end
```
This proves the request is accepted (`assert_response :ok`, no 422) and `sync_github` is invoked on `victim-org`'s stack with an attacker-chosen SHA despite the signature never being validated against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
