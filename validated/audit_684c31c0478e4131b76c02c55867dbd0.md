I have enough evidence to build the analog. The `remote_func_call`/getter mechanism in `formula/evaluation.js` (`callGetter`) is a well-documented, intentional cross-AA "callback" mechanism, and its test-confirmed behavior — that a `bounce()` call in a remote AA's getter propagates as a fatal error to the caller — is the exact analog to the Cooler `onRepay` revert DoS.

### Title
Attacker-Controlled Remote-AA Getter (or Secondary-AA Payment Recipient) Can Permanently Block a Caller AA's Operation via Forced Bounce - (File: formula/evaluation.js, aa_composer.js)

### Summary
Oscript AAs can invoke a "callback" on another, attacker-controlled AA in two ways: (1) a `remote_func_call`/`$addr.$getter()` call that is evaluated via `callGetter` in `formula/evaluation.js`, or (2) sending a payment to an address that happens to be an AA, which automatically triggers that AA as a "secondary trigger" in `aa_composer.js`. If the counterparty's AA address is chosen by an untrusted party (e.g., a "lender", price source, or payee AA address supplied as configuration/data to a legitimate AA, analogous to Cooler's `lender` address), that party can deploy an AA whose getter/definition unconditionally calls `bounce(...)`. This forces the entire calling AA's trigger to fail every time, exactly like Cooler's malicious `onRepay` reverting to block `repayLoan`.

### Finding Description
`callGetter` in `formula/evaluation.js` evaluates the remote AA's getters formula and the specific getter call, and propagates any error (including an explicit `bounce()` call inside the getter) back to the caller as a fatal error: [1](#0-0) [2](#0-1) 

This is invoked from both the map-style function call handling and the `remote_func_call` opcode handling, where any `err` from `callGetter` is turned into a fatal error for the calling AA's entire evaluation: [3](#0-2) [4](#0-3) 

A test in the codebase itself demonstrates that a remote getter calling `bounce("==5")` causes the calling AA's trigger to bounce with that exact error, confirming the callback can force-fail the caller unconditionally: [5](#0-4) [6](#0-5) 

A second, independent path exists through payments: `handleSecondaryTriggers` in `aa_composer.js` automatically invokes any AA that appears as a payment output address of the trigger AA's response unit. If that secondary AA bounces, the failure propagates up and causes the *entire* primary trigger (and any other secondary AAs already executed in the chain) to be rolled back via `revert()`: [7](#0-6) [8](#0-7) 

In both cases, an attacker who controls the address of a downstream AA (analogous to the Cooler `lender` contract address) can guarantee it always reverts/bounces, and thereby deterministically prevent a legitimate AA that references or pays that address from ever completing its intended state transition — e.g. an AA implementing a Cooler-like loan/escrow pattern that must call a getter on (or forward payment to) a lender-supplied AA address before recording a repayment or releasing collateral.

### Impact Explanation
Any AA design pattern in which one party supplies a counterparty AA address that is later called via `remote_func_call`/getter, or that receives a payment forwarded as part of the caller's response, is vulnerable to a permanent denial-of-service: the counterparty can force every trigger to that AA to bounce, freezing state changes and stranding whichever assets/logic depended on completing that operation (e.g., marking a loan repaid, releasing collateral, or completing a settlement). This matches the "AA fund loss or freezing" acceptance criterion — the borrower/user side of such a construction can never make the intended operation succeed, mirroring the "guaranteed default even with funds to repay" impact from the original Cooler report.

### Likelihood Explanation
This requires an AA author to build a contract that (a) resolves a callee/lender AA address from trigger data or state (attacker-influenceable) and (b) calls a getter on it or routes a payment through it as part of a required, atomic state transition — a common and encouraged oscript pattern (getters and chains of AAs are first-class, documented features). Any protocol built this way (lending, escrow, marketplaces) that lets a counterparty specify their own AA address for receiving funds/notifications is exposed, without any special network position or timing needed by the attacker — they only need to deploy a bouncing AA and get referenced/paid by the victim AA.

### Recommendation
- For `remote_func_call`/getter invocations, provide the calling AA formula the ability to catch/ignore a bounced remote-getter error (e.g., a `try`/error-capturing construct) instead of always propagating it as a fatal, chain-reverting error, so a single malicious counterparty cannot block the caller's own state transition.
- For automatically-triggered secondary AAs receiving payment, consider not silently reverting the entire primary chain when an attacker-controlled downstream AA bounces, or make it explicit/documented that atomic chains of AAs are inherently vulnerable to griefing by any counterparty AA in that chain — and encourage protocol authors to isolate calls to untrusted/counterparty-supplied AA addresses from mandatory, atomic completion of critical state changes (e.g., record intent first, then attempt best-effort forwarding in a way whose failure doesn't roll back the already-recorded completion).

### Proof of Concept
1. Deploy `malicious_aa` whose `getters` always execute `bounce("dos")` for any input (as in the test `calling a remote function that fails`, `test/aa_composer.test.js:1625-1712`).
2. Deploy `victim_aa`, modeled as a Cooler-style lending/escrow AA, whose repayment logic reads a counterparty ("lender") AA address from its own state (settable by the counterparty at loan creation, analogous to Cooler's `lender` field) and calls `${lender_address}.$onRepay(...)` via `remote_func_call` before updating state to mark the loan repaid.
3. Attacker sets `lender_address = malicious_aa` when originating/accepting the loan.
4. Borrower triggers `victim_aa` to repay; `victim_aa`'s `init`/state formula calls `malicious_aa.$onRepay(...)`, which unconditionally bounces per `callGetter`'s error propagation shown in `formula/evaluation.js:3331-3336` and `:3361-3365`.
5. `victim_aa`'s entire trigger bounces (as verified by the existing test at `test/aa_composer.test.js:1674-1677`), so the loan is never marked repaid, no matter how many times or how much the borrower pays — reproducing the "guaranteed default" impact from the original Cooler.sol report.
