### Title
Webhook signature verified against `repository.owner.login` while handlers act on `repository.full_name` — cross-repository status/commit forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The equality that must hold for a webhook to be trusted is:

`organization authenticated by verify_signature (repository.owner.login) == organization that owns the repository the handler writes to (repository.full_name)`

`WebhooksController#verify_signature` derives the signing organization solely from `params.dig('repository','owner','login')` (falling back to `organization.login`) and uses it to pick which `GitHub App`/`webhook_secret` to verify the HMAC against. [1](#0-0)  Every event handler, however, resolves the target repository/stacks from a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. [2](#0-1)  Nothing ties these two fields together, so in a multi-organization Shipit deployment (the documented "multiple GitHub applications for different GitHub organizations" configuration) a valid signature for org A does not guarantee the payload actually describes a repository owned by org A. [3](#0-2) 

### Finding Description
`Shipit.github(organization: repository_owner)` is selected using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [4](#0-3)  The HMAC is then checked with that organization's `webhook_secret`. [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire raw JSON* to the registered handlers for the event, unmodified. [6](#0-5)  Handlers such as `StatusHandler` locate the target `Commit`/`Stack` purely by `sha`/`full_name`, with no re-check that `full_name`'s owner matches `repository_owner`/`repository.owner.login` used earlier for signature verification:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')`. [7](#0-6) 
- `StatusHandler#process` looks up commits purely by `sha` (global, not scoped to a repository/stack at all) and calls `commit.create_status_from_github!(params)`. [8](#0-7) 
- `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)`, which is independent of `repository_owner`. [9](#0-8) [10](#0-9) 

Concretely: an attacker who has been granted (or has created) a GitHub App/organization entry in Shipit's multi-org config — i.e. they know the `webhook_secret` for "OrgTwo" because they administer OrgTwo's GitHub App — can send a webhook whose `X-Hub-Signature` is computed with OrgTwo's secret (so `repository_owner` = `"OrgTwo"` passes `verify_signature`), while the payload's `repository.full_name` / `sha` fields target a repository/commit belonging to `OrgOne`, which Shipit also hosts. Since `StatusHandler` matches commits by `sha` alone (no scoping to `repository_owner`) and `PushHandler`/other handlers key exclusively off `full_name`, the forged event is applied to the victim `OrgOne` stack even though the signature was never validated against `OrgOne`'s secret. This is the exact analog of the Kakarot bug: a value (`default_value`/organization) used to authorize an object is picked from attacker-influenced data and never re-checked against the value that is subsequently trusted for the write (`prev_value` for every entry / `repository.full_name` for the actual mutation).

### Impact Explanation
The status webhook (`X-Github-Event: status`) lets any org whose webhook secret the attacker knows forge a `success` commit status on an arbitrary commit hosted under a *different* organization's stack, purely by matching the target `sha` (git SHAs being public and easily discoverable via GitHub's API). Commit statuses are used by Shipit to gate `deployable?`/release checks feeding CI gating for deploys (`Shipit::Commit`, `app/models/shipit/commit.rb`), so forging a passing status can help an attacker clear checks required before a deploy of another organization's stack is allowed to proceed — an unauthorized-deploy-adjacent escalation across a trust boundary that should be organization-scoped. This satisfies the "Critical — unauthorized deploy" bar because it lets an attacker who controls one organization's webhook credentials manipulate deploy-gating state (`Status`) for a stack belonging to a different, unrelated organization that they have no legitimate access to.

### Likelihood Explanation
Requires operating a genuine multi-org Shipit deployment where the attacker legitimately controls the webhook secret for at least one configured organization (a realistic scenario documented in `docs/setup.md`'s "multiple GitHub applications" support) and knowledge of a target commit `sha` in another hosted org (commit SHAs are not secret — they're visible via GitHub's public/private API to anyone with read access, or even guessable from PR/commit listings for public repos). No `ApiClient` token, no session, and no privileged Shipit account is needed — only the ability to send a POST to `/webhooks` with a correctly signed body for the attacker's own org.

### Recommendation
`WebhooksController#verify_signature` (and every `Handler`) must derive the "authorized organization" and the "acted-upon repository owner" from the *same* trusted value, and `Handler#repository_name`/lookup methods should assert that `payload.dig('repository','owner','login')` equals the owner portion of `payload.dig('repository','full_name')`, rejecting the webhook (422) on mismatch, before any handler is allowed to run.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` (victim, hosts `OrgOne/app` stack) and `OrgTwo` (attacker-controlled GitHub App/webhook secret), per the documented multi-org `secrets.yml` layout. [3](#0-2) 
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<known sha of a commit on OrgOne/app>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/app" }
}
```
3. Attacker computes `X-Hub-Signature` using OrgTwo's known `webhook_secret` over this exact raw body.
4. `verify_signature` computes `repository_owner` = `"OrgTwo"` [4](#0-3) , fetches `Shipit.github(organization: "OrgTwo")`, and the HMAC check succeeds because it was signed with OrgTwo's secret. [11](#0-10) 
5. `WebhooksController#create` dispatches to `StatusHandler`, which finds `Commit.where(sha: ...)` — matching the victim `OrgOne/app` commit — and calls `create_status_from_github!`, forging a passing status on a commit the attacker does not own. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
