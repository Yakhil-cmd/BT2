### Title
Cross-organization Team hijack via `MembershipHandler` webhook enables privilege escalation into `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` by `github_id` alone, without verifying that the team's `organization` matches the organization whose webhook secret authenticated the request. An attacker who owns any GitHub organization with a Shipit-configured webhook secret can forge a `membership` event referencing a victim organization's privileged team ID and add themselves (or any GitHub login) as a member of that team.

### Finding Description
The broken binding is: `verifying_organization` (the org whose `webhook_secret` validated `X-Hub-Signature`) must equal `team.organization` (the org that owns the `Team` row being mutated). In `WebhooksController#verify_signature`, the organization used to select the `webhook_secret` is derived purely from the payload: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . For a `membership` event there is no `repository` key, so this resolves to `params.dig('organization', 'login')` — a value fully controlled by whoever sends the request, and the signature is checked against that same organization's own secret: `github_app = Shipit.github(organization: repository_owner); github_app.verify_webhook_signature(...)` [2](#0-1) . Because an attacker owns `org-attacker` and controls its real webhook secret, they can sign an arbitrary payload themselves and it will pass verification.

Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . `find_or_create_by!` first performs a `find_by(github_id: ...)`; if a `Team` row already exists with that `github_id` (belonging to `org-victim`), it is returned as-is — the `organization:` assignment inside the block only runs when a new record is created, so an existing victim team is never re-checked against `params.organization.login`. The handler then does `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , appending the attacker-controlled user to `team.members` via `Team#add_member` [5](#0-4) .

`Shipit.github_teams` is used in `User#authorized?` as `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so membership in a `Team` whose `id` is configured in `Shipit.github_teams` directly grants elevated authorization to a user who never had legitimate GitHub membership in `org-victim`'s team.

None of the existing guards prevent this: `verify_signature` only checks that *some* organization's secret matches the bytes, not that it's the *same* organization whose team is being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema on `MembershipHandler` only validate payload shape, not cross-org consistency; there is no model validation on `Team` tying `github_id` uniqueness/lookup to `organization`.

### Impact Explanation
An attacker who operates their own GitHub organization (with its own legitimately-configured Shipit `webhook_secret`) can grant themselves (or any arbitrary GitHub login) membership in any pre-existing `Shipit::Team` row by guessing/observing its `github_id`, including teams that are configured in `Shipit.github_teams` and thus grant elevated authorization (`User#authorized?`) across the whole Shipit instance — not scoped to a single repository or stack. This is a cross-tenant escalation: the attacker's own org's webhook credentials are used to mutate authorization data belonging to a different organization's team, matching the "High - escalation into `Shipit.github_teams` authorization" impact category. It is repeatable for any victim `github_id` and any attacker-chosen `member.login` as long as the attacker can guess/know the target team's numeric GitHub ID (these are sequential-ish, low-entropy, and often discoverable via GitHub's public API for the org's teams if the attacker can see team listings, or simply guessed since team IDs are small integers assigned by GitHub).

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a GitHub organization that has a legitimate Shipit webhook configured with a real `webhook_secret` (attacker doesn't need any Shipit secret — they configure their own org's webhook themselves since they own that org); (2) a `Shipit::Team` row already exists for the victim team (created previously via a legitimate `membership` webhook or via `Team.find_or_create_by_handle`); (3) attacker knows/guesses the victim team's GitHub numeric `id`. All of this is achievable by an "unprivileged" attacker per the threat model who can register their own GitHub org and emit real webhooks from it. The cost is low: one crafted HTTP POST to `/webhooks` with a valid HMAC-SHA1 signature computed with their own secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject (or explicitly reconcile) the case where an existing `Team` with that `github_id` belongs to a different `organization` than `params.organization.login`. E.g., use `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and raise/log if a `github_id` collision with a different organization is detected instead of silently accepting the found row. More generally, `WebhooksController#verify_signature` should validate that the organization embedded in the event payload used for team/membership mutations matches the organization whose secret validated the signature, rather than trusting an attacker-controlled field to select which secret to check against.

### Proof of Concept
```ruby
# test/models/webhooks/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook cannot hijack a team belonging to another organization" do
  victim_team = Team.create!(github_id: 4242, organization: 'org-victim', slug: 'deployers', name: 'Deployers', api_url: 'https://api.github.com/teams/4242')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 4242, 'name' => 'Deployers', 'slug' => 'deployers', 'url' => 'https://api.github.com/teams/4242' },
    'organization' => { 'login' => 'org-attacker' },
    'member' => { 'login' => 'attacker-login' },
  }

  # Signed with org-attacker's own real webhook secret (attacker controls org-attacker)
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: 'org-attacker').send(:webhook_secret), payload.to_json)}"

  post :create, body: payload.to_json, headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature }

  attacker_user = User.find_by(login: 'attacker-login')

  # Binding under test: verifying_organization ('org-attacker') should equal team.organization ('org-victim')
  assert_not_equal 'org-attacker', victim_team.reload.organization

  # Assert exploit did NOT occur (post-fix expectation)
  refute victim_team.members.include?(attacker_user), "attacker was added to a team owned by a different organization"
end
```
Before a fix, this test fails: the attacker user is added to `victim_team.members`, and if `victim_team.id` is in `Shipit.github_teams`, `attacker_user.authorized?` becomes `true` despite the attacker never having real GitHub membership in `org-victim`.
