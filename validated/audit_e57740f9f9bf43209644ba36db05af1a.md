### Title
Cross-organization webhook forgery via signature verification scoped to `repository.owner.login` while repository writes trust `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit.github(organization:)` supports independent per-organization GitHub App configs, each with its own optional `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [2](#0-1) . But the handlers that actually act on the payload (create stacks, sync commits, open review stacks, update statuses) resolve the target repository from a *different* field, `payload.dig('repository', 'full_name')` / `params.repository.full_name` [3](#0-2) [4](#0-3) . Nothing enforces that `repository.owner.login` (used to pick the verifying secret) matches the owner encoded in `repository.full_name` (used to pick the affected `Repository`/`Stack`).

### Finding Description
`GitHubApp#verify_webhook_signature` explicitly bypasses HMAC validation when the resolved organization has no `webhook_secret` configured: `return true unless webhook_secret` [5](#0-4) . Setting `webhook_secret` is documented as optional per organization ("Webhook secret (optional)") [6](#0-5) , and the test fixtures explicitly demonstrate multi-org installs where an org's `webhook_secret` is nil [7](#0-6) .

The binding that should hold: `organization authenticated (repository.owner.login used to select the verifying secret) == organization/repository actually written (repository.full_name used by the handler)`. Before the attacker's request, this binding trivially holds because GitHub always sends payloads where these two fields describe the same repository. After an attacker directly POSTs to `/webhooks` (no GitHub involved), the two fields are independently attacker-controlled JSON keys with no cross-check: `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) can be set to any org configured in Shipit with a blank `webhook_secret`, causing `verified = true` unconditionally, while `repository.full_name` in the same JSON body can name an entirely different, "secured" organization/repo that Shipit tracks.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out for this bug class. An unprivileged network attacker with no Shipit session, no `ApiClient` token, and no knowledge of any real `webhook_secret` can:
- Trigger `GithubSyncJob` for an arbitrary tracked stack via a forged `push` event (`Handlers::PushHandler`) causing commit/state changes.
- Create/close/reopen review stacks via `Handlers::PullRequest::*` handlers, or mutate labels/assignees.
- Inject fake commit statuses via `Handlers::StatusHandler`, which can gate deploy eligibility (`deployable_status`).
This is an unauthorized action against a stack the attacker was never authorized to touch, satisfying the "unauthorized deploy/rollback" class of High/Critical impact, provided at least one organization in the multi-org config has no `webhook_secret` set (a state the docs themselves present as normal/optional) while another organization it can target does have secured, sensitive stacks.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (a documented, supported configuration, confirmed by `secrets_double_github_app.yml`), and (2) at least one of those organizations left without a `webhook_secret` (also a documented "optional" setting). Given this is an explicitly supported and documented configuration shape rather than a misuse, likelihood is realistic for any multi-tenant Shipit install that doesn't uniformly enforce `webhook_secret` across all configured orgs.

### Recommendation
Do not let `repository_owner` (used purely to pick which secret to verify with) diverge from the actual repository/org the handler acts upon. Concretely:
- After signature verification, confirm the resolved `repository_owner`/`organization` matches the owner encoded in `repository.full_name` (and `organization.login` for org-level events) before dispatching to handlers.
- Reconsider allowing `webhook_secret` to be blank per organization when multiple organizations are configured; at minimum, require a secret whenever more than one organization is present in `secrets.github`.

### Proof of Concept
Given a Shipit config with `OrgA` (no `webhook_secret`) and `OrgB` (has a real `webhook_secret`, owns a sensitive stack), an attacker with no credentials sends:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already in OrgB repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/protected-repo"
  }
}
```
`repository_owner` resolves to `OrgA` [8](#0-7) , `Shipit.github(organization: "OrgA")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally without checking `X-Hub-Signature` [5](#0-4) . The request passes verification and is dispatched to `PushHandler`, which resolves the target stack via `payload.dig('repository', 'full_name')` = `"OrgB/protected-repo"` [3](#0-2) , enqueuing a `GithubSyncJob` against `OrgB`'s stack despite the attacker never possessing `OrgB`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
