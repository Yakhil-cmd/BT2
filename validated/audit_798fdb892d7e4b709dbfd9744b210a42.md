### Title
Blind SSRF-style forced outbound connection via attacker-controlled `device_hub` in pairing/device messages - ([File: device.js])

### Summary
`device.js`'s `handlePairingMessage()` and the `hub/message` correspondent-hub-update logic accept a `device_hub` string supplied by an unauthenticated remote party (anyone who sends a pairing request, or any already-paired device claiming a new home hub) and store it as the trusted "hub" for that correspondent. This value is later used unmodified to open outbound WebSocket connections from the victim node/wallet, mirroring the Chamilo SSRF pattern where attacker-supplied "link"/"social" URLs were used to make server-initiated requests without adequate destination restriction.

### Finding Description
When a pairing request arrives, `handlePairingMessage()` validates `json.device_hub` only for non-emptiness, length ≤200, and `network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub)`, then stores it directly as the correspondent's `hub` in `correspondent_devices` [1](#0-0) . The same lax pattern of validating a device-supplied hub string and persisting it as trusted routing information is repeated when an existing correspondent updates its home hub in the `hub/message` handler [2](#0-1) , in `addUnconfirmedCorrespondent`, `updateCorrespondentProps`, and `addIndirectCorrespondents` [3](#0-2) .

This `hub` value is later used as the target of an outbound network connection whenever the local node needs to deliver a message to that correspondent, with no additional destination filtering: `sendMessageToDevice`/`sendMessageToHub` read `hub` from the DB and pass it straight into `sendPreparedMessageToHub`, which calls `network.findOutboundPeerOrConnect(conf.WS_PROTOCOL+hub_host, ...)` [4](#0-3) [5](#0-4) . `findOutboundPeerOrConnect` unconditionally opens a WebSocket to whatever `url` is passed in [6](#0-5) , and `getHubWs`/`loginToHub`/`getWitnessesFromHub`/`requestFromHub` all connect to `my_device_hub`/hub values in the same unrestricted manner [7](#0-6) [8](#0-7) .

The only gate is `network.isValidWsUrl`, which (based on its usage pattern across the file — accepting any string that merely resembles a `ws://`/`wss://` host:port with allowed characters) is a syntactic check, not a destination-allowlist check: it does not appear to reject private/loopback/link-local IP ranges, non-standard ports, or internal hostnames. This is functionally analogous to Chamilo's SSRF: a remote unauthenticated party supplies a "link" (here, a hub hostname/IP) which is not restricted to an allowlist of legitimate hub hosts, and the target application (the ocore wallet/device layer) subsequently issues outbound network requests to that attacker-chosen address.

### Impact Explanation
Because any device that can send a pairing message (a `pairing` subject message is explicitly whitelisted even from unknown/non-correspondent senders per `arrSubjectsAllowedFromNoncorrespondents` [9](#0-8) ) can specify `device_hub`, an attacker can force a victim's ocore-based wallet/hub client to open outbound WebSocket connections to arbitrary internal or otherwise-unreachable hosts/ports (e.g., internal management APIs, cloud metadata endpoints, LAN services) whenever the victim tries to reply, exchange further messages, or process the reverse pairing secret. This is a blind SSRF primitive: the requester does not see the response content directly, but can use connection timing/errors (as with the CVE's blind SSRF in links/social tools) to port-scan internal networks or interact with internal services reachable only from the victim host. This does not directly cause double-spend or asset inflation, but it is a genuine network-reachable request-forgery bug reachable from an unauthenticated "paired device"/pairing message, matching the class of bug in the report.

### Likelihood Explanation
Likelihood is high for triggering the outbound connection: pairing messages are processed automatically without requiring the victim's explicit approval of the hub value (only pairing_secret validity is checked), and correspondent hub updates from already-known devices are applied automatically as part of normal message handling. No user interaction beyond having ocore's device layer running and reachable (e.g., paired at least once, or willing to accept pairing) is required.

### Recommendation
- Tighten `network.isValidWsUrl` (or add a dedicated check before persisting/using `device_hub`) to reject private, loopback, link-local, and other non-routable IP ranges/hostnames unless explicitly configured to allow them (e.g., for local/dev testing).
- Consider resolving and validating the hub host at connection time (DNS pinning / re-check after resolution) to avoid DNS-rebinding bypasses of any allowlist.
- Rate-limit and require stronger authentication before allowing a remote, unauthenticated pairing message to set/update the `hub` value used for later outbound requests, and log/alert on hub changes to unfamiliar or private-range hosts.

### Proof of Concept
1. Attacker (any party, not previously paired) crafts a pairing request via a paired-device-style message with `body.pairing_secret` matching a temporary or permanent pairing secret exposed by the victim, and sets `json.device_hub` to an internal address, e.g. `169.254.169.254:6668` or `127.0.0.1:6668` (formatted to pass the syntactic `isValidWsUrl` check).
2. Victim's `handlePairingMessage` accepts and stores this as `hub` for the new correspondent [10](#0-9) .
3. Any subsequent action causing the victim to message this correspondent (e.g., processing `reverse_pairing_secret`, sending a chat reply) triggers `sendMessageToHub`/`sendPreparedMessageToHub`, which calls `network.findOutboundPeerOrConnect(conf.WS_PROTOCOL + hub, ...)`, causing the victim node to open a WebSocket connection to the attacker-chosen internal address [4](#0-3) [6](#0-5) .
4. Attacker infers reachability/service presence on the internal target from connection success/failure/timing observed indirectly (e.g., via error events or timing side channels), constituting blind SSRF.

Note: I could not directly view the implementation body of `network.isValidWsUrl` in the indexed context (only its call sites), so the exact set of characters/formats it accepts (and whether it already blocks private ranges) could not be fully confirmed from the available index; verifying that function's full source is recommended before finalizing remediation.

		throw Error('no url');

		onOpen = function(){};
	if (!bStarted)
		return onOpen("[internal] network not started yet");
	url = url.toLowerCase();
	if (url.startsWith('wss://byteball.org'))
		url = url.replace(/^wss:\/\/byteball\.org/, 'wss://obyte.org');
	var ws = getOutboundPeerWsByUrl(url);
	if (ws)
		return onOpen(null, ws);
	// check if we are already connecting to the peer
	ws = assocConnectingOutboundWebsockets[url];
	if (ws){ // add second event handler
		breadcrumbs.add('already connecting to '+url);
		return eventBus.once('open-'+url, function secondOnOpen(err){
			console.log('second open '+url+", err="+err);
			if (err)
				return onOpen(err);

				onOpen(null, ws);

				onOpen('[internal] websocket already closed');
			}
		});
	}
	console.log("will connect to "+url);
	connectToPeer(url, onOpen, dontAddPeer);
}
