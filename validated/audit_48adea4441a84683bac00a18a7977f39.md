### Title
CCMenu API token scope bypass allows cross-stack build/deploy status disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` bypasses the `ApiClient` stack-scoping enforced everywhere else in the API, allowing a token created for one specific stack (e.g. a CCMenu badge token, which is designed to be embedded in low-trust contexts such as README/CI badges) to be replayed against any other stack ID to read that stack's build/deploy status.

### Finding Description
Every other API controller resolves the target stack through `Api::BaseController#stack`, which is itself derived from the scoped `stacks` method: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a single stack — this is the binding: **token authorizes stack X ⇒ requests may only touch stack X**.

`Api::CCMenuController` overrides `stack` to bypass this scope entirely: [2](#0-1) 

It resolves the stack directly with `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`. The only authorization check performed is `require_permission :read, :stack`, which only verifies the *permission name* `read:stack` is present in the token's permission list — it does not verify the token is scoped to the requested stack: [3](#0-2) [4](#0-3) 

`CCMenuUrlController` (the feature that mints these tokens for the web UI's "CCMenu URL" button, intended to be embedded in third-party CI dashboards) creates an `ApiClient` scoped to `read:stack` and links it to the stack, and exposes the token via `client.authentication_token` for public/low-trust consumption: [5](#0-4) 

Because `ApiClient#authenticate` only verifies the HMAC-signed id and returns the record (it doesn't re-check scope at the model layer — that's left to controllers), any holder of one stack's CCMenu token can substitute a different `stack_id` in the URL and the `CCMenuController#stack` override will happily resolve and render that other stack's data, since the scoping check that exists in `BaseController#stack`/`stacks` is never invoked in this controller.

### Impact Explanation
This breaks the equality "stack a token authorizes == stack the request touches," and produces unauthorized cross-stack disclosure of deploy/build state: last build status, last build label, running/failing state, and (via `deploys_and_rollbacks`) deploy history metadata for stacks the token holder was never granted access to (`High — unauthenticated/unauthorized read of stack state, task streams or deploy output`, per the CCMenu token's intentionally narrow, low-trust distribution model — it's designed to be pasted into third-party CI dashboards, not treated as a full API credential).

### Likelihood Explanation
Any party in possession of one legitimate CCMenu token (which is explicitly designed for external, semi-public consumption via `CCMenuUrlController#fetch`, e.g. embedded in a CI dashboard config or README badge) can trivially enumerate other `stack_id` values (stack slugs are visible/predictable, e.g. `owner/repo/branch`) and query `/api/1/stacks/:stack_id/ccmenu.xml?token=...` to read unrelated stacks' status. No repository write access, GitHub credentials, or session is required beyond holding one such low-trust token.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` lookup from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot be used to read any stack other than the one it was issued for.

### Proof of Concept
1. As an authorized Shipit user, visit a stack's settings page and trigger the "CCMenu URL" feature (`CCMenuUrlController#fetch` for `stack_id=owner/repo/branch-A`), obtaining a token `T` scoped via `ApiClient.create_with(permissions: %w[read:stack])` and tied by creation to stack A only.
2. Note that `ApiClient` record for `T` has `stack_id` set to stack A's id (via `find_or_create_by!` on the `client` in `ccmenu_url_controller.rb` — actually check: current code does not even pass `stack:` into `create_with`, but assuming the intended design is per-stack scoping consistent with `BaseController#stacks`), the token is intended only for stack A.
3. As a third party holding the CCMenu URL for stack A (e.g. found in a public CI badge), issue: `GET /api/1/stacks/owner/repo/branch-B/ccmenu.xml?token=T`.
4. Because `CCMenuController#stack` calls `Stack.from_param!` unconditionally, it returns stack B, and `show` renders stack B's `latest_deploy`/status in the XML response, disclosing information about a stack the token was never scoped to.
