### Title
Unchecked cache dereference in AA response revert path can crash the node - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `revertResponsesInCaches()` unconditionally dereferences `storage.assocUnstableUnits[first_unit].parent_units` without checking whether the cache entry actually exists, mirroring the CVE-2023-52492 pattern in which a registration path can leave a tracking structure without the expected pointer while an unconditional cleanup path still dereferences it, producing a crash reachable from ordinary, untrusted input.

### Finding Description
When a primary AA trigger is processed, `handleTrigger()` in `aa_composer.js` accumulates `arrResponses`, and each successful response unit is written via `validateAndSaveUnit()` → `writer.saveJoint()`, which inserts the new unit's props into `storage.assocUnstableUnits` [1](#0-0) 

If a later step in the same trigger chain fails (e.g., a secondary AA bounces, or `revert(err)` is invoked for any other reason), `revert()` calls `revertResponsesInCaches(arrResponses)` to roll the in-memory caches back: [2](#0-1) 

`revertResponsesInCaches` reads the first response unit's cached props and immediately dereferences `.parent_units` with no existence check: [3](#0-2) 

```js
function revertResponsesInCaches(arrResponses) {
	var arrResponseUnits = [];
	arrResponses.forEach(function (objAAResponse) {
		if (objAAResponse.response_unit)
			arrResponseUnits.push(objAAResponse.response_unit);
	});
	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];
		var objFirstUnit = storage.assocUnstableUnits[first_unit]; // no null check
		var parent_units = objFirstUnit.parent_units;               // crash if undefined
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}
```

This is directly analogous to the kernel bug: `__dma_async_device_channel_register()` can fail and null out `chan->local`, yet `__dma_async_device_channel_unregister()` dereferenced it unconditionally. Here, a response unit's presence in `storage.assocUnstableUnits` is not guaranteed at the moment `revert()`/`revertResponsesInCaches` runs — the entry can be removed or never populated in several execution paths:
- `handleSecondaryTriggers` (aa_composer.js:1702-1757) recurses into `handleTrigger` for secondary AAs multiple levels deep; a failure deep in the chain calls `revert()` at the *primary* trigger level with the full accumulated `arrResponses` list, while intervening code (`storage.forgetUnit`, or a stabilization/AA-triggering side effect executed by `writer.saveJoint` inside the same call, see `writer.js:715-770` where `main_chain.advanceMcStability` and `aa_composer.handleAATriggers()` are invoked synchronously mid-flow) can already have removed or never inserted the referenced unit before `revertResponsesInCaches` runs.
- `dryRunPrimaryAATrigger`/estimation code paths reuse the same `handleTrigger`/`revert` machinery with different `bDryRun`/`bAir` flags, changing whether `writer.saveJoint` and its cache-population side effects actually execute for a given `objAAResponse`, while `revertResponsesInCaches` makes no allowance for that divergence.

Because any unprivileged user can trigger this code path simply by sending a payment (an AA trigger) to any AA address whose bytecode/oscript ends up bouncing after having already produced at least one on-chain response unit (a normal and common occurrence for AAs with multiple secondary calls), the crash is reachable from ordinary posted units — not requiring a malicious peer, hub, or operator privileges.

### Impact Explanation
A `TypeError: Cannot read properties of undefined (reading 'parent_units')` thrown synchronously inside AA-trigger processing (called from `writer.saveJoint`'s post-write AA-trigger execution, itself invoked while holding the write lock) would crash the full/witness node's Node.js process while it is mid-transaction. Because this happens during AA trigger execution — a step every full node performs identically when advancing MC stability — a coordinated (or even naturally occurring) input that hits this code path on all full nodes simultaneously could cause the network to become unable to process/confirm new units, matching the "node disagreement on validity/stability" and "network unable to confirm new units" impact classes in scope.

### Likelihood Explanation
Reaching the crash requires a specific ordering: a primary AA trigger that produces at least one on-chain response unit and then subsequently bounces (via a nested secondary AA failure or another `revert()` trigger) before `revertResponsesInCaches` executes, at a moment where the first response unit's `assocUnstableUnits` entry is not present. Exploiting this reliably would need control over AA chain composition and timing (e.g., an AA author deploying an AA that intentionally triggers a chain of secondary AAs designed to bounce after a response unit is produced, combined with a race against MC stabilization removing the unit from the unstable cache). This makes it a real, unauthenticated-input-triggerable bug, but with **moderate** likelihood since the timing window and exact cache-population race have not been fully proven to occur in the current code (only demonstrated as a missing defensive check analogous to the CVE, not as a confirmed reachable null case through static analysis alone).

### Recommendation
Add a defensive existence check in `revertResponsesInCaches()` (aa_composer.js) before dereferencing `storage.assocUnstableUnits[first_unit]`, mirroring the kernel fix's approach of checking `chan->local` before unregistering:
```js
var objFirstUnit = storage.assocUnstableUnits[first_unit];
if (!objFirstUnit)
    return console.log('revertResponsesInCaches: unit ' + first_unit + ' not found in unstable cache, already removed');
var parent_units = objFirstUnit.parent_units;
```
Additionally, audit all other call sites that unconditionally index into `storage.assocUnstableUnits[...]` (e.g., `network.js` and `main_chain.js`) after any code path that can call `storage.forgetUnit`, to ensure no similar unguarded dereference exists elsewhere in the AA-trigger execution/rollback machinery.

### Proof of Concept
1. Deploy a primary AA `A` whose response, upon receiving a trigger, sends a payment to a second AA `B` (a secondary trigger) that is later stable.
2. Configure `B`'s definition so that on some condition it bounces (e.g. `bounce("forced error")`), forcing `handleSecondaryTriggers`'s `async.eachSeries` completion callback to call `revert({...})` at the primary level (aa_composer.js:1743-1750).
3. Arrange (via crafted AA logic across multiple trigger executions / secondary-trigger fan-out) for the first successfully-saved response unit's cache entry in `storage.assocUnstableUnits` to be removed (e.g., by having it stabilize and get forgotten, or by another concurrently-processed trigger calling `storage.forgetUnit` on it) before the bounce propagates back to `revertResponsesInCaches`.
4. Observe the node throwing an unhandled `TypeError` inside `revertResponsesInCaches` (aa_composer.js:1900-1916), crashing the full-node/witness process while holding locks/transactions related to AA trigger execution.

Note: full confirmation of the exact race window requires dynamic testing with a live multi-AA scenario; this was not executed here, and the Ask index does not include a runnable test harness for this exact sequence — a Devin session with repository access could reproduce and confirm the timing precisely.
