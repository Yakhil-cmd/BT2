### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while every handler mutates state keyed by the untrusted `repository.full_name` (or bare `sha`), letting anyone who owns a valid webhook secret for one organization forge events for repositories in a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the HMAC secret to validate against using only `repository_owner` derived from the payload, then hands the *same untrusted payload* to handlers that key their side effects off a different field (`repository.full_name`) or off no repository field at all (`sha`). No code cross-checks that the field used to select the verifying secret matches the field used to select the record being written. This breaks the trust binding "organization whose secret authenticated the request == repository that gets written."

### Finding Description
`verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret`) using only the owner login: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this to a per-organization config (secret, oauth, etc.) declared in `config/secrets.yml`, and it is legitimate for multiple, mutually untrusting organizations to be configured on a single Shipit instance (see `test/dummy/config/secrets_double_github_app.yml` showing `OrgOne`/`OrgTwo` each with their own `webhook_secret`): [3](#0-2) 

Once the signature is accepted, `create` re-dispatches the *raw, unvalidated* payload to handlers: [4](#0-3) 

But the handlers never re-derive or check `repository.owner.login`. Instead:
- `Handler#stacks`/`#repository_name` looks up the target `Repository`/`Stack` purely by `repository.full_name`: [5](#0-4) 
- `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup, with no relation at all to which organization's secret verified the request: [6](#0-5) 
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching that `full_name`/branch: [7](#0-6) 
- `StatusHandler#process` is even weaker: it matches commits by bare `sha` with **no repository scoping whatsoever**, so a validly-signed event from organization A can inject a commit status onto a commit belonging to organization B's repositories if the sha happens to exist there: [8](#0-7) 
- The `PullRequest::*` handlers (open/close/reopen/label) similarly resolve the acted-upon repository purely from `params.repository.full_name`, independent of the field used for signature verification: [9](#0-8) [10](#0-9) 

Equality that should hold but does not:
`organization_that_signed(payload) == organization_owning(repository_acted_upon(payload))`

Before the attack: for legitimate GitHub deliveries, `repository.owner.login` and `repository.full_name`'s owner segment are always consistent because GitHub itself generates both fields from the same repository object.
After the attack: an attacker who legitimately controls a GitHub App/webhook secret for *their own* organization (`attacker-org`, a valid, unprivileged-relative-to-other-tenants entity on a multi-org Shipit deployment) can freely construct a payload where `repository.owner.login = "attacker-org"` (so the signature check passes using the secret they know) while `repository.full_name = "victim-org/victim-repo"` (so the handler acts on a repository/stack they have no legitimate access to).

### Impact Explanation
This lets a tenant with valid webhook credentials for their own organization forge GitHub webhook deliveries that mutate state belonging to a different organization's repositories on the same Shipit instance:
- Force a `push` event to trigger `GithubSyncJob` / `stack.sync_github` against an arbitrary victim stack with an attacker-chosen `expected_head_sha`, influencing what Shipit considers the tip of the branch and continuous-deployment behavior.
- Inject fabricated commit `status` records (`create_status_from_github!`) for commits in a victim repository, which can flip deploy-safety checks (`Undeployed Commit#deploy_state`, `deploy_disallowed?`) from blocked to allowed, enabling an unauthorized deploy.
- Archive or fabricate `ReviewStack`s for a victim repository's pull requests via the `PullRequest::*` handlers.

Because commit-status manipulation can directly unblock a deploy path (`deploy_disallowed?`/`blocked?` gating in `UndeployedCommit`), this crosses into the "unauthorized deploy" impact bucket, which the rules classify as Critical/High.

### Likelihood Explanation
The precondition is that the Shipit instance hosts more than one organization (a documented, supported configuration - see `config/secrets.yml`/`secrets_double_github_app.yml` with independent per-org `webhook_secret`s) and that the attacker is a legitimate admin of one of those organizations' GitHub Apps (i.e., knows their own org's webhook secret, which is not privileged access to the *Shipit* application itself, only to their own tenant's GitHub App settings — exactly the "unprivileged attacker crossing an organization/repository trust boundary" scenario the rules target). No Shipit session, `ApiClient` token, or GitHub write access to the victim repo is required — only an HTTP POST to the public webhooks endpoint with a correctly-signed-for-attacker's-org, victim-repo-labeled payload.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after signature verification, re-validate that the repository/organization the handler is about to act on (`repository.full_name`'s owner segment, or `organization.login`) matches the exact organization key that was used to select the verifying `webhook_secret`. Reject (422) any payload where these differ, rather than trusting `repository.full_name` independently downstream in `Handler#repository_name`/`Repository.from_github_repo_name`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who administers the `attacker-org` GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`) payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature check passes (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `create` dispatches to `PushHandler`, whose `stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:30-38`, `app/models/shipit/repository.rb:53-56`), and `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` runs against the victim's stack — despite the request never being signed with `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
