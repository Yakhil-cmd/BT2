### Title
Unchecked exception in private-payment hash check leads to double-processing of an unvalidated private chain - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` computes a hash of a wallet/hub-supplied private-payment payload inside a `try` block and, on failure, does not `return` after handling the error — exactly the CVE‑2014‑9746 pattern of "not checking a return/exception status before continuing to use the (uninitialized) result." Execution falls through and the corrupted/uninitialized value is used, and the payment is still submitted to the validator.

### Finding Description
In the `validateAndSave` closure of `handleSavedPrivatePayments`, `json_payload_hash` is computed from attacker/peer-supplied `objHeadPrivateElement.payload`: [1](#0-0) 

If `objectHash.getBase64Hash()` throws (e.g., because the private-payment JSON stored in `unhandled_private_payments` contains a malformed/non-serializable structure — nulls, non-finite numbers, or other shapes that fail object-hash serialization), the `catch` block logs the error, notifies the peer, and calls `deleteHandledPrivateChain(..., cb)` — but it does **not** `return`. Control flow continues past the `catch` to the very next line, which references `json_payload_hash`, a variable that was declared but left `undefined` because its assignment never completed: [2](#0-1) 

Worse, execution proceeds to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very payload whose hash could not even be computed — i.e., the payload that should have been discarded is still handed to the real validation/persistence pipeline: [3](#0-2) 

This mirrors the FreeType bug class described in the report: a parse/compute step's failure indicator is not checked, so the caller proceeds to use an uninitialized value and continues processing attacker-controlled data as if the earlier step had succeeded.

### Impact Explanation
Two concrete consequences follow from the missing `return`:
1. **Double invocation of `cb` for the same `async.each` item**: `deleteHandledPrivateChain(..., cb)` is called once from inside the `catch`, and then `validateAndSavePrivatePaymentChain`'s `ifOk`/`ifError`/`ifWaitingForChain` handlers each call `deleteHandledPrivateChain(..., cb)` (or `cb()`) again. Calling the `async.each` iterator callback more than once causes undefined behavior in the async control flow (the completion callback of `async.each` — which unlocks the `saved_private` mutex and emits `new_my_transactions` — can run multiple times or prematurely), which can desynchronize the node's private-payment processing pipeline (mutex double-unlock, race with the next payment record, or events emitted for units that shouldn't be treated as new/validated yet).
2. **Continued validation/possible persistence of a payload that failed integrity computation**: instead of dropping the malformed private element, the node still calls the full `validateAndSavePrivatePaymentChain` path, meaning a private element that could not even produce a consistent hash may still be accepted into `ifOk`, be broadcast via `new_direct_private_chains`, or be recorded as belonging to a "new" unit — inconsistent with what a node that treats the hash‑failure as fatal would do.

Because private-payment processing feeds directly into how outputs are considered spent/linked in a private (indivisible/divisible) asset chain, a peer or hub that deliberately supplies a payload triggering `getBase64Hash` to throw (crafted nested/foreign-field payload) can drive this code path into inconsistent per-node behavior — some nodes may end up in a different acceptance/rejection or double-unlock state than others for the same private chain, i.e., node disagreement on the validity of a private payment.

### Likelihood Explanation
The `unhandled_private_payments` table is populated directly from private-payment messages received from peers or the hub (`private_payment_in_unit` messages), and the code assumes the JSON stored there parses to a well-formed object. An attacker who controls the private-payment JSON (a normal unprivileged peer relationship in this protocol, since private-payment chains are exchanged between wallets/hubs without prior trust) can supply a payload shape that `objectHash.getBase64Hash` rejects (throws), which is a realistic and reachable trigger for any node reprocessing `unhandled_private_payments` (this function runs periodically/on startup and on `new_direct_private_chains`/hub delivery), making the missing `return` easy to hit.

### Recommendation
Add a `return` (or restructure to `return cb()` / early-exit) immediately after the error handling in the `catch` block so that execution never falls through to use `json_payload_hash` or call `validateAndSavePrivatePaymentChain` on a payload whose hash could not be computed:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. Craft (or have a malicious hub/peer relay) a private-payment JSON whose `payload` is shaped so `object_hash.getBase64Hash()` throws — e.g., contains a value that `getJsonSourceString`/hashing utilities reject (non-finite number, disallowed nested type, or a shape that fails object-hash's schema assumptions).
2. Have this JSON stored under `unhandled_private_payments` (via the normal peer/hub private-payment delivery flow that inserts unhandled records for later processing).
3. Trigger `handleSavedPrivatePayments()` (invoked periodically / on wallet startup / on new private chain notifications).
4. Observe: the `catch` block runs and calls `deleteHandledPrivateChain(...)` with `cb`, but code continues to build `key` using `undefined` `json_payload_hash` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError` handlers invoke `deleteHandledPrivateChain(..., cb)`/`cb()` a second time for the same `async.each` iteration — producing a double-callback and continued processing of the payload that had already failed integrity hashing.
