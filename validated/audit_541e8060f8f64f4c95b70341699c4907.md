### Title
Cross-tenant `ReviewStack` provisioning via mismatched `repository.owner.login`/`repository.full_name` in forged `pull_request` webhook - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb, app/models/shipit/repository.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against using `params.dig('repository','owner','login')`, while `OpenedHandler#repository` resolves the actual `Repository` record to mutate using the independent field `params.repository.full_name`. [2](#0-1) [3](#0-2)  Because these two fields are never cross-validated, and because `GitHubApp#verify_webhook_signature` returns `true` when no `webhook_secret` is configured for the organization named in `owner.login`, [4](#0-3)  an attacker who controls (or registers) any GitHub org with no `webhook_secret` configured can forge a `pull_request` `opened` payload where `repository.owner.login` names that unprotected org but `repository.full_name` names an arbitrary victim repository, causing Shipit to provision/mutate a `ReviewStack` for the victim repository without ever authenticating against the victim's secret.

### Finding Description
The broken binding the code implicitly assumes is:
`params.repository.owner.login == owner_segment_of(params.repository.full_name)`

This is never enforced anywhere in the request path. Trace:

1. `WebhooksController#verify_signature` builds `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. [5](#0-4) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank for that organization's config. [4](#0-3)  An attacker only needs one configured (or default) org entry in `Shipit.secrets.github` with no `webhook_secret` set — this is an explicitly supported, documented configuration (`secrets.development.example.yml`, `secrets.development.shopify.yml`), so it is a realistic operator state, not a hypothetical.
3. Once signature verification passes, `WebhooksController#create` parses the same raw JSON and dispatches it to `OpenedHandler#process`. [6](#0-5) 
4. `OpenedHandler#repository` looks up the target `Repository` purely from `params.repository.full_name` via `Repository.from_github_repo_name`, which just splits the string on `/` and does a `find_by(owner:, name:)`. [1](#0-0)  Nothing compares this `owner` segment to the `repository.owner.login` used in step 1.
5. If `repository.review_stacks_enabled` and provisioning behavior conditions are met for that (attacker-named) victim repository, `ReviewStackAdapter#find_or_create!` provisions a new `ReviewStack` using `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"`, entirely attacker-controlled strings, and adds it to `ReviewStackProvisioningQueue`. [7](#0-6) 

The stated "amplification" via blocking_statuses is a red herring for this specific finding: `blocking_statuses`/`blocked?` only affect deploy gating logic on `Commit#blocked?`/`Stack#deployable?` after a stack already exists and has commits with statuses; [8](#0-7)  a forged `pull_request` `opened` event does not set or clear any commit status or `blocked?` state — it only provisions a `ReviewStack`. So the "forced status sets/clears blocked?" amplification claim in the prompt is not supported by `OpenedHandler`'s code path; that would require a separate forged `status` event, which is a different attack path not covered by this file/target.

Existing guards that fail to prevent this: `drop_unhandled_event` only checks the event type is handled, not payload consistency; [9](#0-8)  `ExplicitParameters` schema in `OpenedHandler.params` only requires field presence/type, not cross-field consistency; [10](#0-9)  and `Repository` model validations only constrain `owner`/`name` character format, not correspondence to the verified organization. [11](#0-10) 

### Impact Explanation
An attacker can cause Shipit to create a `ReviewStack` (a `Stack` subclass) record and enqueue provisioning for a `Repository` they never authenticated against, provided that repository has `review_stacks_enabled` with `provisioning_behavior_allow_all?` (or label-gated behavior satisfied by attacker-controlled label names in the same forged payload). This is a cross-repository/cross-tenant write: a payload nominally "authenticated" for org A (no-secret org) creates state for org B's repository. This matches the "Critical — a payload for one repository mutating another's stack" category in principle, but the actual mutation here is limited to `ReviewStack` provisioning (branch/environment attributes and enqueuing a provisioning job) — it does not directly cause an unauthorized deploy, merge, or rollback by itself, nor does it leak secrets. The severity therefore depends on what `ReviewStackProvisioningQueue`/provisioning does with attacker-controlled `branch` (e.g., running commands against that ref) — that downstream execution path is outside the two files in scope and not traced here.

### Likelihood Explanation
Preconditions: (1) Shipit configured with multiple GitHub orgs (`Shipit.secrets.github` keyed by org) where at least one org has no `webhook_secret` set — a documented, supported configuration; (2) the victim repository has review stacks enabled with a provisioning behavior the attacker can satisfy (`allow_all`, or label-based, which the attacker fully controls in the same forged payload's `pull_request.labels`). Attacker cost is a single unauthenticated `POST /webhooks` request with a crafted JSON body and correct `X-Github-Event: pull_request` header; no secrets, sessions, or tokens are required. It is repeatable against any repository the operator has onboarded, as long as the "victim" repository is enabled for review-stack provisioning — this is a meaningful but non-trivial precondition (single-org deployments with only one configured `webhook_secret`, which is the common case, are not exploitable this way since `repository_owner` and the target repo's actual owner will typically coincide when there is only one org in play; the primary risk applies to multi-org configurations, or single-org configurations where `webhook_secret` is left unset).

### Recommendation
In `Shipit::WebhooksController` or in `Repository.from_github_repo_name`, enforce that the `owner` segment of `params.repository.full_name` matches `params.dig('repository','owner','login')` before dispatching to handlers, and reject the request (422) on mismatch. Additionally, consider treating "no `webhook_secret` configured" as a hard misconfiguration warning rather than an automatic pass-through, or scope `Repository` lookups by the verified `repository_owner` rather than trusting `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "forged pull_request opened for no-secret org can provision a ReviewStack for a different repository" do
  # Precondition: multi-org secrets where 'no-secret-org' has no webhook_secret
  # and 'victim-org/victim-repo' is a distinct, review-stack-enabled repository with allow_all provisioning.
  repository = shipit_repositories(:victim_repo) # owner: 'victim-org', name: 'victim-repo'
  repository.update!(review_stacks_enabled: true, provisioning_behavior: 'allow_all')

  payload = {
    action: 'opened',
    number: 999,
    pull_request: {
      id: 1, number: 999, url: 'https://api.github.com/x', title: 'x', state: 'open',
      additions: 1, deletions: 1,
      head: { sha: 'a' * 40, ref: 'attacker/forged-branch' },
      user: { login: 'attacker' },
      assignees: [], labels: []
    },
    repository: {
      full_name: 'victim-org/victim-repo',   # target repo — different org
      owner: { login: 'no-secret-org' }      # org used ONLY for signature check
    },
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature needed: verify_webhook_signature returns true for 'no-secret-org'

  assert_difference -> { Shipit::ReviewStack.where(repository:).count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end
end
```
Binding to assert before/after: `params.repository.owner.login` ("no-secret-org") used for signature verification vs. owner segment of `params.repository.full_name` ("victim-org") used for the actual `Repository` record mutated — these differ, and the test shows the mismatch is not rejected, letting a `ReviewStack` be created for `victim-org/victim-repo` from a payload only "authenticated" for `no-secret-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
