### Title
Actor-permission bypass allows unauthorized draining of another account's gas key via `TransferToGasKey`/`WithdrawFromGasKey` actions - (`runtime/runtime/src/action_validation.rs`)

### Summary
`validate_transfer_to_gas_key_action` and `validate_withdraw_from_gas_key_action` only check that the `GasKeys` protocol feature is enabled; they perform no check that the receipt's `predecessor_id` (the actor) equals the `receiver_id`/`account_id` being mutated. Unlike the legacy privileged actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`), which are documented and enforced to require `predecessor_id == receiver_id`, the new `TransferToGasKey`/`WithdrawFromGasKey` actions were not added to that actor-permission gate, so any account can target another account's gas key through a `FunctionCall`-driven receipt.

### Finding Description
`validate_transfer_to_gas_key_action` in `runtime/runtime/src/action_validation.rs` only enforces the protocol-feature gate: [1](#0-0) 

This is invoked from the general action dispatcher in `validate_action_with_mode`, which treats `TransferToGasKey`/`WithdrawFromGasKey` the same as any unprivileged action (e.g. `Transfer`): [2](#0-1) 

The documented and previously-enforced invariant is that only actions where `predecessor_id == receiver_id` may mutate access-key/account-privileged state (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`): [3](#0-2) 

`TransferToGasKey` and `WithdrawFromGasKey` are new actions that mutate access-key state (`gas_key_info.balance`) and, for withdrawal, also mutate the target account's balance — yet they are absent from that actor-restricted list, and the execution functions themselves take no actor/predecessor check, only an `account_id` (the receiver) parameter: [4](#0-3) [5](#0-4) 

The dispatcher in `Runtime::apply_action` passes only `account_id` (the receiver) to these functions, not `actor_id`, unlike `DeleteAccount` which explicitly receives and is gated by `actor_id`: [6](#0-5) 

Exploit flow: an attacker calls a deployed contract (their own or any contract they control) which, inside `FunctionCall` execution, uses `promise_batch_create` to open a new receipt toward an **arbitrary** `receiver_id` (any account, including a victim's), since `promise_batch_create` performs no ownership check on the target account id: [7](#0-6) 

The contract then appends a `WithdrawFromGasKey` action (or `TransferToGasKey`) to that batch via `promise_batch_action_withdraw_from_gas_key`/`promise_batch_action_transfer_to_gas_key`. Because `validate_transfer_to_gas_key_action`/`validate_withdraw_from_gas_key_action` do not check `predecessor_id == receiver_id`, this receipt is accepted for execution against the victim's account, provided the attacker knows the victim's gas-key public key (which is discoverable via public RPC `view_access_key`/`view_access_key_list`). `action_withdraw_from_gas_key` then decreases the gas key's `balance` and increases the victim account's spendable `amount()` — an account-state mutation the victim's key never authorized, breaking the "only the account itself may mutate its own account record" invariant.

### Impact Explanation
This is an authorization-bypass on account state: an unprivileged attacker can force the liquidation of a victim's gas-key funded balance into the victim's main balance without any signature or predecessor match from the victim, at a time of the attacker's choosing. While the funds stay nominally in the victim's account (rather than the attacker's), this still constitutes unauthorized mutation of another account's protected state (violating the actor-permission invariant that the near protocol otherwise enforces for `DeployContract`/`Stake`/`AddKey`/`DeleteKey`/`DeleteAccount`), and it can be used to grief/disable relayer or meta-transaction infrastructure that depends on gas keys retaining a specific funded balance for automated fee payment, causing denial-of-service on gas-key-dependent workflows. This matches the NEAR bounty impact class of "unauthorized action on another account" / authorization bypass.

### Likelihood Explanation
- Requires only an unprivileged account: no validator/node-operator privileges needed.
- Requires the victim to have an existing gas key (a protocol feature intended for automated agents/relayers) whose public key is discoverable via standard RPC view calls.
- The exploit path (`FunctionCall` → `promise_batch_create` to arbitrary receiver → `promise_batch_action_withdraw_from_gas_key`) uses only documented host functions available to any deployed contract, making it fully reproducible and repeatable.

### Recommendation
Add `Action::TransferToGasKey` and `Action::WithdrawFromGasKey` to the actor-permission enforcement path (the same check that currently restricts `DeployContract`/`Stake`/`AddKey`/`DeleteKey`/`DeleteAccount` to `predecessor_id == receiver_id`), or add an explicit `actor_id == account_id` check inside `action_transfer_to_gas_key` / `action_withdraw_from_gas_key` in `runtime/runtime/src/access_keys.rs`, returning `ActionErrorKind::ActorNoPermission` otherwise.

### Proof of Concept
Add to `runtime/runtime/src/tests/apply.rs`:
1. Create account `alice` and add a gas key with `AccessKey::gas_key_full_access(n)`, then fund it via `TransferToGasKeyAction` from `alice` itself.
2. From a different account `bob`, deploy/execute a `FunctionCall`-based contract that uses `promise_batch_create(alice)` followed by `action_withdraw_from_gas_key` for `alice`'s gas key public key with some `amount`.
3. Apply the resulting receipts and assert:
   - The receipt executes successfully (no `ActionErrorKind::ActorNoPermission` is raised) even though `predecessor_id` (`bob`) != `account_id` (`alice`).
   - `alice`'s gas key `gas_key_info.balance` decreased by `amount` and `alice`'s account `amount()` increased by `amount`, with `bob` not needing (and not providing) `alice`'s signature.
   - Run under `cargo test -p node-runtime --features test_features` and additionally assert the balance checker (`check_balance`) and total gas accounting pass, confirming the state mutation is fully accepted by the runtime despite lacking authorization from `alice`.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

    pub fn promise_batch_create(
        &mut self,
        account_id_len: u64,
        account_id_ptr: u64,
    ) -> Result<u64> {
        self.result_state.gas_counter.pay_base(base)?;
        if self.context.is_view() {
            return Err(HostError::ProhibitedInView {
                method_name: "promise_batch_create".to_string(),
            }
            .into());
        }
        let account_id = self.read_and_parse_account_id(account_id_ptr, account_id_len)?;
        let sir = account_id == self.context.current_account_id;
        self.pay_gas_for_new_receipt(sir, &[])?;
        let new_receipt_idx = self.ext.create_action_receipt(vec![], account_id)?;

        self.checked_push_promise(Promise::Receipt(new_receipt_idx))
    }
