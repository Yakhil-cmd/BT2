### Title
Organization-based webhook signature verification is decoupled from the repository the `pull_request` handler mutates, allowing cross-repository record forgery and continuous-deployment amplification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner`, which falls back to `params.dig('organization', 'login')` when `repository.owner.login` is absent from the payload. `AssignedHandler`, however, resolves the target `Shipit::Repository`/`Stack` from the completely independent `params.repository.full_name` field, never re-checking it against the organization that was actually authenticated.

### Finding Description
The broken binding is: `repository_owner` (used to pick the `GitHubApp` / `webhook_secret` for HMAC verification) **should equal** the owner of `params.repository.full_name` (used by the handler to select the `Repository`/`Stack` to mutate). In this codebase, both values are independently attacker-controlled fields of the same untrusted JSON body, and nothing enforces their equality.

Path:
- `WebhooksController#repository_owner` (app/controllers/shipit/webhooks_controller.rb:59-62) computes `params.dig('repository','owner','login') || params.dig('organization','login')`. If the attacker simply omits `repository.owner.login`, this becomes `organization.login`, a field with no bearing on which repository the event is "about".
- `verify_signature` (lines 24-49) calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. In `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83), `return true unless webhook_secret` — if the app resolved for that organization has no configured `webhook_secret`, **any** payload/signature pair is accepted unconditionally.
- `AssignedHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69) resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a field that was never used or validated during signature verification.
- `AssignedHandler#process` (lines 41-45) looks up an existing `Shipit::PullRequest` by `number` scoped to that repository (lines 53-65) and calls `pull_request.update(github_pull_request: params.pull_request)`.
- `PullRequest#github_pull_request=` (app/models/shipit/pull_request.rb:36-50) sets `head` via `find_or_create_commit_from_github_by_sha!(sha)` (lines 52-61), which calls `stack.github_api.commit(stack.github_repo_name, sha)` and `stack.commits.create_from_github!` against the **real, victim** repository — using `stack.github_repo_name`, not any attacker-supplied name.
- New `Commit` records run `after_commit ... on: :create, :schedule_continuous_delivery` (app/models/shipit/commit.rb:24-25, 281-287), which enqueues `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?`.

Exploit flow: the attacker picks an organization known to Shipit's config whose `GitHubApp` has no `webhook_secret` set (a valid, code-supported state per line 77 of `github_app.rb`), sets `organization.login` to that organization's name in the payload, omits `repository.owner.login`, and sets `repository.full_name` to the victim's real, continuous_deployment-enabled repository. `verify_signature` authenticates against the lenient organization (trivially, since no secret is required) while the handler operates entirely on the victim repository resolved from `repository.full_name`. This satisfies `drop_unhandled_event` (action `pull_request`/`unassigned` is handled), passes `verify_signature`, and reaches `AssignedHandler`, causing a write to a `PullRequest` belonging to a repository/stack that never authenticated the request.

### Impact Explanation
This is a payload originating under one organization's authentication mutating another repository's persisted state — matching the Critical category "a payload for one repository mutating another's stack, commit, task." Concretely: an existing `PullRequest` record for the victim stack is overwritten with attacker-chosen `title`/`state`/`labels`/`assignees`/`head.sha`, and if the referenced `sha` corresponds to a commit reachable in the victim's real GitHub repo (e.g., from a PR the attacker legitimately opened against the victim repo from their own fork) a new `Commit` row is created for the victim stack. When the victim stack has `continuous_deployment` enabled (and CI/blocking-status conditions are met, e.g. `stack.ignore_ci?`), this new commit can trigger `ContinuousDeliveryJob`, resulting in an unauthorized deploy driven by an unauthenticated forged webhook. This is repeatable against any repository/stack whose `full_name` the attacker can guess or discover, independent of whether that repository's own webhook secret is ever known to the attacker.

### Likelihood Explanation
Exploitability strictly requires that some organization registered in Shipit's multi-org GitHub App configuration has no `webhook_secret` set — a state the code explicitly permits (`return true unless webhook_secret`). Given that condition, the attack costs a single crafted, unauthenticated HTTP POST to `/webhooks` with a correctly-shaped `pull_request` JSON body (`action: "unassigned"`, valid `pull_request`/`sender` sub-objects, `repository.full_name` set to the victim, `organization.login` set to the lenient org, `repository.owner` omitted). It is fully repeatable and requires no privileges on the victim repository beyond having at some point created a matching PR record (attainable by opening a real PR against the victim repo from a fork, which is within the stated attacker capabilities).

### Recommendation
Verify webhook signatures using the organization/owner derived from the *same* field the handlers use to select the target repository (`repository.full_name`'s owner), and require that field to be present — do not fall back silently to `organization.login` for signature-key selection when it can diverge from the repository actually acted upon. Additionally, treat a missing `webhook_secret` as a hard failure (reject the request) rather than an implicit "always verified" bypass, or require that every configured GitHub App have a non-blank `webhook_secret`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in the test `Shipit.github` provider: `"lenient-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create a `Shipit::Stack` for `victim-org/victim-repo` with `continuous_deployment: true` (and `ignore_ci?`/deploy conditions satisfied), plus an existing `Shipit::PullRequest` with `number: 42`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, body: `{"action":"unassigned","number":42,"pull_request":{... ,"head":{"sha": known_sha, "ref": "branch"}, ...},"repository":{"full_name":"victim-org/victim-repo"},"organization":{"login":"lenient-org"},"sender":{"login":"attacker"}}`, and an arbitrary/garbage `X-Hub-Signature`.
4. Assert response is `200`/`:ok` (verification passed) even though the signature does not match `victim-org`'s `webhook_secret`.
5. Assert `Shipit::PullRequest.find_by(number: 42, ...).reload.title/state/head` reflect the attacker's payload — i.e., `repository_owner` (`"lenient-org"`) ≠ owner of `repository.full_name` (`"victim-org"`), yet the victim's `PullRequest`/`Commit` was written, and (if deploy-eligible) `ContinuousDeliveryJob` was enqueued for the victim stack.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def github_pull_request=(github_pull_request)
      self.github_id = github_pull_request.id
      self.number = github_pull_request.number
      self.api_url = github_pull_request.url
      self.title = github_pull_request.title
      self.state = github_pull_request.state
      self.additions = github_pull_request.additions
      self.deletions = github_pull_request.deletions
      self.user = User.find_or_create_by_login!(github_pull_request.user.login)
      self.assignees = github_pull_request.assignees.map do |github_user|
        User.find_or_create_by_login!(github_user.login)
      end
      self.labels = github_pull_request.labels.map(&:name)
      self.head = find_or_create_commit_from_github_by_sha!(github_pull_request.head.sha)
    end

    def find_or_create_commit_from_github_by_sha!(sha)
      if commit = stack.commits.by_sha(sha)
        commit
      else
        github_commit = stack.github_api.commit(stack.github_repo_name, sha)
        stack.commits.create_from_github!(github_commit)
      end
    rescue ActiveRecord::RecordNotUnique
      retry
    end
