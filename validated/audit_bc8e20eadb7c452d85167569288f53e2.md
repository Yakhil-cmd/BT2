This confirms the mismatch: the signature verification key (`repository_owner`) is derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) in `WebhooksController#repository_owner`, while the actual repository acted upon by every handler is looked up via `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These are two independent, unauthenticated fields inside the same JSON body, read *before* any cryptographic check has passed. [1](#0-0)  selects the `GitHubApp` (and thus which `webhook_secret` to verify against) using `repository_owner`. [2](#0-1)  shows `repository_owner` is read straight out of the untrusted JSON body. [3](#0-2)  shows `verify_webhook_signature` unconditionally returns `true` when that org's `webhook_secret` is blank/unset — a supported, documented multi-org configuration shown in [4](#0-3) . Meanwhile every handler resolves the target `Stack`/`Repository` from a *different* field, `repository.full_name`, via [5](#0-4) .

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write) are independent, attacker-controlled strings in the same unauthenticated payload, an attacker can set `repository.owner.login` to an organization configured with no `webhook_secret` while setting `repository.full_name` to point at a stack belonging to a *different*, fully-secured organization. This breaks the binding "organization authenticated == repository written."

### Title
Webhook organization used for signature verification differs from the repository acted upon, allowing forged webhooks against unrelated repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to verify against based on `repository.owner.login` (or `organization.login`), while every `Webhooks::Handlers::Handler` subclass resolves the `Stack` to mutate using the independent `repository.full_name` field from the same unauthenticated JSON body.

### Finding Description
`verify_signature` computes `repository_owner` purely from the raw, unverified payload before any signature check occurs, then looks up `Shipit.github(organization: repository_owner)` to obtain the secret to verify with [6](#0-5) . If that organization's config has no `webhook_secret` set — a valid, documented configuration for multi-org Shipit deployments [4](#0-3)  — `verify_webhook_signature` returns `true` unconditionally regardless of the actual signature header [3](#0-2) .

After "verification" passes, the controller re-parses the same raw body and dispatches it to handlers [7](#0-6) , and the base `Handler` class resolves the acted-upon repository from `payload.dig('repository', 'full_name')` — a completely different JSON field than the one used to select the signing organization [5](#0-4) .

Nothing enforces that `repository.owner.login` matches the owner encoded in `repository.full_name`. An attacker who knows (or guesses) that any one configured GitHub organization in the Shipit instance has no `webhook_secret` configured can submit a forged, unsigned webhook whose `repository.owner.login`/`organization.login` names that unsecured org (satisfying `verify_signature`), while `repository.full_name` names an arbitrary stack belonging to a different, secured organization. The handler will act on that unrelated stack.

### Impact Explanation
Handlers triggered this way include `push` (queues `GithubSyncJob`, which fetches commits and mutates the stack's commit history) and `pull_request` handlers that create/close/label stacks. This allows an unauthenticated attacker to inject fabricated push/PR events (e.g., forging `after` SHA, PR state, labels) against a target stack they don't control, corrupting the stack's tracked commit/PR state and potentially triggering downstream automated actions (e.g., deploy-related state depending on branch tracking). This is not RCE or direct unauthorized deploy, but it is an authentication-boundary break: an org that authenticated (or trivially bypassed auth) is not the org whose repository is actually written.

### Likelihood Explanation
Requires the deployment to configure at least two GitHub organizations where at least one has no `webhook_secret` set — a state explicitly supported and shown in the shipped example config. An operator running Shipit for multiple orgs, with one org (e.g., an internal/test org) left unsecured, is plausible. The attack itself requires no credentials, no session, and no signature — just crafting a JSON body with mismatched `repository.owner.login` and `repository.full_name`.

### Recommendation
In `WebhooksController`, after computing `repository_owner` for secret selection, additionally verify that the owner segment of `repository.full_name` (and/or `organization.login`) matches `repository_owner` before dispatching to handlers, or require a non-empty `webhook_secret` for every configured organization (fail closed rather than treating a blank secret as "always trusted").

### Proof of Concept
1. Configure two orgs in `secrets.github`: `SecureOrg` (with a `webhook_secret`) and `OpenOrg` (with `webhook_secret` unset/nil), as supported by [4](#0-3) .
2. POST to `/github/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "organization": { "login": "OpenOrg" },
  "repository": { "full_name": "SecureOrg/target-stack", "owner": { "login": "OpenOrg" } },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `repository_owner` to `"OpenOrg"`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
4. `create` dispatches the payload to the `push` handler, which resolves the target stack from `repository.full_name` = `"SecureOrg/target-stack"` [9](#0-8) , enqueuing `GithubSyncJob` against `SecureOrg`'s stack despite no valid signature for `SecureOrg` ever being presented.
