### Title
CCMenu API endpoint bypasses per-stack scoping, allowing any `read:stack` token to view any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` scopes an `ApiClient`'s access to stacks by binding `current_api_client.stack_id` to the requested `params[:stack_id]` inside its `stack` helper. `Shipit::Api::CCMenuController` overrides this helper and resolves the stack directly from `Stack.from_param!(params[:stack_id])`, completely skipping the scope check, so a token that is only authorised for one stack can be used to read the CCMenu status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the intended trust boundary for an `ApiClient` token: if the token has a `stack_id`, it may only touch that one stack. [1](#0-0) 

`CCMenuController` requires only the coarse `read:stack` permission bit and then overrides `stack` to bypass the scoped `stacks` collection entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in the client's `permissions` array — it never checks `stack_id`: [3](#0-2) 

The only place `stack_id` scoping is actually enforced is the `stacks`/`stack` pair in `BaseController`, and `CCMenuController` is the one endpoint that redefines `stack` to skip it. This is exactly the trust binding break called out by the reported bug class: "a stack a token authorises" (the `ApiClient.stack_id` it was created with, e.g. fixture `here_come_the_walrus` which is scoped to the `shipit` stack) is broken by "a stack it touches" (any `stack_id` value supplied in the URL of `GET /api/stacks/:stack_id/ccmenu`).

Before the request: token `here_come_the_walrus` is authorised only for stack `shipit` (its `stack_id` column is set). After the request: the same token can fetch `GET /api/stacks/<any-other-stack>/ccmenu` and receive that other, unauthorised stack's data because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This grants "unauthenticated" (relative to the intended per-stack scope) read of stack state for stacks the token holder was never authorised for — matching the High-impact category "unauthenticated read of stack state, task streams or deploy output." The disclosed data (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, whether the stack is locked) can reveal private repository/branch names, CI health, and deploy activity for stacks outside a client's intended scope, including private or restricted stacks that other teams deliberately scoped their tokens away from.

### Likelihood Explanation
Likelihood is high for anyone already holding any valid, narrowly-scoped `read:stack` API token (a routine, low-privilege credential — e.g., the CCMenu token users generate for themselves via `CCMenuUrlController`, or any scoped client created through the `api_clients` UI). No additional privilege is needed: the attacker just changes the `stack_id` segment of the URL to a stack they were never granted access to. This requires no session, no admin rights, and no interaction from the victim.

### Recommendation
- Short term: Have `CCMenuController#stack` reuse the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a token's `stack_id` binding is enforced consistently across every controller.
- Long term: Centralize "stack scoping" as a single, mandatory concern (e.g., a `before_action` in `BaseController` that all subclasses must use to resolve `@stack`), and add a regression test per controller (mirroring the existing "an api client scoped to a stack will only see that one stack" test in `stacks_controller_test.rb`) to ensure any future controller cannot silently bypass the scope.

### Proof of Concept
1. As an admin, create/obtain an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to stack `org/repo-a/production` (mirrors fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`).
2. Using that token's Basic-Auth credentials, request:
   `GET /api/stacks/org/repo-b/production/ccmenu`
   (a stack the token was never scoped to).
3. Observe a `200 OK` XML CCMenu response describing `org/repo-b/production`'s latest build status/label/URL, even though the token is only authorised (per its `stack_id`) for `org/repo-a/production`. Compare with `GET /api/stacks/org/repo-b/production` (handled by `Shipit::Api::StacksController`, which uses the inherited scoped `stack` method) — that request correctly returns `404`/empty for out-of-scope stacks, demonstrating the inconsistency introduced by `CCMenuController`'s override.
