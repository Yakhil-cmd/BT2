### Title
Forged `pull_request` webhook signature verified against `repository.owner.login` while handler resolves state from an unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App/organization used to validate the HMAC signature from `repository.owner.login`, while `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#repository` independently re-derives the target repository from the unrelated `repository.full_name` field. Because these two attacker-controlled fields are never cross-checked, and because signature verification trivially passes for any organization configured without a `webhook_secret`, an attacker can make a webhook "verify" under a harmless no-secret org while the payload actually mutates a completely different, real, secret-protected org's `ReviewStack`.

### Finding Description
The broken binding: the equality `organization_that_verified_signature == organization_that_owns_the_mutated_repository` is assumed but never enforced.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to select the GitHub App config: `github_app = Shipit.github(organization: repository_owner)` then calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no configured secret: `return true unless webhook_secret` [3](#0-2) . So naming any Shipit-configured-but-secretless organization in `repository.owner.login` makes verification pass regardless of the actual `X-Hub-Signature` value.
- After verification, the raw parsed JSON (`params` in `create`, unrelated to the `repository_owner` used above) is dispatched to handlers untouched: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `OpenedHandler#repository` resolves the target repository purely from `params.repository.full_name`, with no reference to `repository.owner.login`: `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new` [5](#0-4) .
- If `respond_to_pull_request_opened?` is true (action is `"opened"` and the resolved repo's provisioning policy allows it) [6](#0-5) , `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [7](#0-6) , which — if no matching stack exists for `environment: "pr#{params.number}"` — creates one with `branch: params.pull_request.head.ref` and provisions it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [8](#0-7) .

Exploit flow: an attacker crafts a JSON body with `repository.owner.login = "no-secret-org"` (an org present in Shipit's `github:` config with `webhook_secret: nil`) and `repository.full_name = "victim-org/victim-repo"` (a real repository tracked by Shipit, belonging to a different, secret-protected org, with review stacks enabled and an `allow_all`/label-based provisioning policy). They set `X-Github-Event: pull_request`, `action: "opened"`, and any (even garbage) `X-Hub-Signature`, then POST to `/webhooks`. `verify_signature` resolves the GitHub App for `no-secret-org`, finds no `webhook_secret`, and returns `true` for any signature — request passes. The handler then resolves `victim-org/victim-repo` via `full_name` and creates/provisions a `ReviewStack` for that repo using attacker-supplied `pull_request.head.ref`/`head.sha`/labels, with no relationship to `no-secret-org` at all.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type exists in the handler registry [9](#0-8) ; `ExplicitParameters` schema in `OpenedHandler.params` only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name` [10](#0-9) ; and `Repository` model validators only constrain `owner`/`name` character sets, not which org's webhook validated the request [11](#0-10) .

### Impact Explanation
A payload nominally attributed to (and only cryptographically checked against) a harmless, attacker-influenced/no-secret organization can create and provision a `ReviewStack` for an entirely different organization's repository, using attacker-controlled branch ref, PR number/labels, and sender login (`Shipit::User.find_or_create_by_login!(params.sender["login"])` [12](#0-11) ). This is cross-tenant state manipulation: one repository/org's forged webhook mutates another, secret-protected org's stack records, matching the "Critical — payload for one repository mutating another's stack" category. Repeatable per PR number/org combination as long as one no-secret org exists in Shipit's multi-org `github:` config and the target repo has review stacks enabled with a permissive provisioning behavior.

### Likelihood Explanation
Requires the Shipit instance to run with a multi-organization `github:` config (documented feature, see `docs/setup.md` "Using Multiple Github Applications") where at least one configured organization has no `webhook_secret` set, and the target/victim repository has `review_stacks_enabled` with `provisioning_behavior_allow_all` (or label-based policy matching attacker-controlled labels). Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub-side secrets, sessions, or team memberships are needed.

### Recommendation
Enforce that the organization used to verify the signature is the same organization that owns the repository the handler acts on: derive `repository_owner` and the handler's repository lookup from the same trusted field, and/or after determining `repository.full_name` in the handler, assert `Repository.from_github_repo_name(full_name).owner == repository_owner_used_for_signature_verification` before processing. Alternatively, disallow organizations with a blank `webhook_secret` from validating webhooks for repositories belonging to other configured organizations, or require every configured organization to have a non-blank `webhook_secret` in multi-org deployments.

### Proof of Concept
Minitest plan (ActionDispatch::IntegrationTest or existing `WebhooksControllerTest` style):

```ruby
test "pull_request opened webhook verified under no-secret org can provision a ReviewStack for a different org's repo" do
  # Setup: two orgs configured in Shipit.secrets.github
  #   "no-secret-org" => { webhook_secret: nil, ... }
  #   "victim-org"    => { webhook_secret: "real-secret", ... }
  victim_repo = Repository.create!(owner: "victim-org", name: "victim-repo",
                                    provisioning_behavior: "allow_all")
  victim_repo.update!(review_stacks_enabled: true)

  payload = {
    action: "opened",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "https://api.github.com/x", title: "t",
      state: "open", additions: 1, deletions: 0,
      head: { sha: "deadbeef", ref: "attacker-branch" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: {
      full_name: "victim-org/victim-repo",   # points at victim org's repo
      owner: { login: "no-secret-org" }       # used ONLY for signature verification
    },
    sender: { login: "attacker" }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=garbage-not-a-real-signature'

  # Equality under test BEFORE: org verifying signature ("no-secret-org")
  #   != org owning mutated repo ("victim-org")
  assert_no_difference -> { ReviewStack.where(stack_type: nil).count } do
    # sanity baseline
  end

  post :create, body: payload, as: :json
  assert_response :ok

  # Equality under test AFTER: assert the write happened for victim-org
  # despite the verifying org being unrelated no-secret-org.
  review_stack = victim_repo.review_stacks.find_by(environment: "pr42")
  assert review_stack.present?, "ReviewStack should not have been created without valid signature for victim-org"
  assert_equal "attacker-branch", review_stack.branch
end
```

This demonstrates the two sides of the equality diverge: the signature-verifying organization (`no-secret-org`) is not the organization actually mutated (`victim-org`), yet the write succeeds.
