### Title
Immutable `bounce_fees` in AA definitions can become insufficient to cover growing network fees, causing bounced funds to become permanently stuck - (File: aa_composer.js)

### Summary
Just like `WormholeTransceiver`'s immutable `gasLimit` can become insufficient to cover the real, time-varying L2 execution cost, an Autonomous Agent's `bounce_fees` is fixed forever at AA-creation time (it is part of the AA definition, whose hash *is* the AA's address, so it can never be changed) while the actual cost of composing the bounce/response unit is variable and has grown over the protocol's history (headers/payload commission, `oversize_fee`, `tps_fee`). If `bounce_fees.base` (set once, based on the `MIN_BYTES_BOUNCE_FEE` in effect at creation time) is no longer enough to cover the real cost of sending a unit, the AA can silently fail to bounce, leaving funds sent to it permanently locked with no state change and no way to reclaim them.

### Finding Description
An AA's `bounce_fees` are validated once at definition time and can only be *raised* above `constants.MIN_BYTES_BOUNCE_FEE`, never changed afterward, because the AA address is `objectHash.getChash160(arrDefinition)` — any change to `bounce_fees` produces a different address: [1](#0-0) 

At trigger-handling time, `handleTrigger` reads this static value from the definition template and uses it as the sole gatekeeper for whether the AA can afford to compose a bounce/response unit: [2](#0-1) [3](#0-2) 

When execution fails for any reason, `bounce()` is invoked. It only proceeds to actually send a bounce message if `trigger.outputs.base >= bounce_fees.base`, and otherwise just silently finishes without sending anything, i.e. it does not try to compute the *actual* required amount, only the fixed historical constant: [4](#0-3) 

However, the real cost of building and sending a payment message from the AA (which is what `bounce_fees` is supposed to approximate) is not static — `sendUnit`/`completePaymentPayload` computes `target_amount` from `size`, `net_target_amount`, plus `getOversizeFee()` (introduced at `v4UpgradeMci`) and `tps_fee` (also introduced later), on top of `headers_commission` and `payload_commission`: [5](#0-4) 

If insufficient spendable outputs/funds exist to cover this dynamically-computed `target_amount`, coin selection fails outright: [6](#0-5) 

Because `bounce_fees` was fixed at AA-creation time using the smaller, older cost model (or a value the author judged "just enough" under network conditions at that time), and new fee dimensions (`oversize_fee`, `tps_fee`) were added by protocol upgrades afterward without any way to update `bounce_fees` for already-deployed AAs, an AA that used to be able to bounce leftover funds can permanently lose that ability once its `bounce_fees.base` no longer covers the true unit-composition cost under current network conditions.

### Impact Explanation
When this mismatch occurs:
1. `handleTrigger` still passes the initial check `trigger.outputs.base >= bounce_fees.base` (using the stale, too-low threshold), so the trigger is accepted and the AA attempts to execute.
2. If execution/evaluation errors and `bounce()` is invoked, or if a legitimate bounce message needs to be composed, `sendUnit` may find that available funds (bounded by what the trigger sent, since `bounce_fees.base` under-estimates what's truly needed) are insufficient to cover the current `target_amount` (which includes `oversize_fee`/`tps_fee` unaccounted for by the immutable `bounce_fees`), and `readStableOutputs`/`iterateUnspentOutputs` returns `cb('not enough funds for ... bytes')`.
3. This causes the whole response-unit composition for that trigger to fail. Since bounce fee validation guaranteed just enough by an outdated standard, the AA's balance can end up strictly less than what's required, and there is no other path to recover those funds — the AA logic and definition are immutable, so the underlying `bounce_fees` can never be corrected for already-deployed AAs.

This matches the "AA fund loss or freezing" impact class: funds sent to a deployed AA can become permanently unspendable/stuck because the immutable fee assumption baked into the AA definition no longer matches the true, evolving cost of sending a unit under current network rules.

### Likelihood Explanation
This requires no malicious actor — any AA author who set `bounce_fees.base` close to the `MIN_BYTES_BOUNCE_FEE` in effect at deployment time (which is the common/minimal-cost pattern encouraged, see `test/samples/*.oscript` and `test/aa.test.js` using `bounce_fees: { base: 10000 }`), combined with subsequent protocol-level fee increases (e.g., `oversize_fee` and `tps_fee`, both introduced at `constants.v4UpgradeMci` after many AAs were already deployed), is sufficient to trigger the scenario. Any ordinary unprivileged user sending a trigger with an amount just above the AA's static `bounce_fees.base` but below what's actually needed under current fee rules can cause the freezing condition.

### Recommendation
Do not rely purely on the static, immutable `bounce_fees.base` from the AA definition as the sole check for whether a bounce/response can be composed. Instead:
- Compute the actual minimal cost of a bounce unit dynamically (including current `oversize_fee` and `tps_fee` under the mci at the time of trigger) before deciding whether to bounce, and use `max(bounce_fees.base, actual_required_amount)` as the threshold.
- Alternatively, allow `bounce_fees` to be revisited/topped-up out of AA logic (e.g., permit the AA's own state/balance to subsidize the shortfall) so that growth in protocol fee overhead does not permanently strand funds sent to older AAs.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000 }` (the minimum allowed by `constants.MIN_BYTES_BOUNCE_FEE`) prior to `v4UpgradeMci`.
2. Advance the network state past `v4UpgradeMci` so that `oversize_fee`/`tps_fee` become part of `target_amount` computation in `completePaymentPayload` (`aa_composer.js:1083-1091`).
3. Send a trigger with `trigger.outputs.base` slightly above `10000` (satisfying `handleTrigger`'s `bounce_fees.base` check at line 1852) that causes the AA to fail evaluation and call `bounce()`.
4. Observe that `sendUnit`'s coin-selection (`aa_composer.js:1231-1232`) fails with `'not enough funds for ... bytes'` because the true required amount (including the new `oversize_fee`/`tps_fee`) exceeds what `bounce_fees.base` guaranteed, leaving the trigger's funds stuck at the AA address with no state change and no route to recovery.
