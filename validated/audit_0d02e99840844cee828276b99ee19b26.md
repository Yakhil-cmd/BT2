### Title
Webhook signature is validated against the payload's `repository.owner.login`/`organization.login`, while every event handler trusts a completely different, unverified field (`repository.full_name` or a global `sha` lookup) - allowing an onboarded low-trust GitHub organization to forge events for another tenant's stacks (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Once the signature is accepted, the actual event handlers (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) resolve the target `Stack`/`Commit` using an entirely different, independently attacker-controlled field: `payload.dig('repository','full_name')`, or in `StatusHandler`'s case no repository scoping at all. This breaks the equality "organization that authenticated == repository that is written," letting any tenant organization configured in `Shipit.github` forge webhook payloads that mutate or spoof state for a different organization's stacks.

### Finding Description
The signature check and the business-logic dispatch use disjoint trust anchors:

- `verify_signature` selects the app/secret to verify against via `repository_owner`: [1](#0-0) [2](#0-1) 

- Once `verified` is true (or false is ignored because `head(422)` doesn't halt the filter chain before `create` — the same `before_action` sequence merely renders a response but the request has already been routed to the matching handler set based on `X-Github-Event`), `Handler#stacks`/`#repository_name` resolves the target repository using a *different* JSON key, `repository.full_name`, which is never covered by the signature-organization lookup: [3](#0-2) 

- `PushHandler` and `CheckSuiteHandler` then act on stacks found via that unverified `repository_name`: [4](#0-3) [5](#0-4) 

- `StatusHandler` is worse: it does not scope by repository at all, just a global `sha` lookup across every `Commit` in the entire Shipit installation: [6](#0-5) 

Because `Shipit` supports multiple GitHub organizations/apps each with its own `webhook_secret` (`Shipit.github(organization:)` / `github_app_config`), a payload only needs a valid HMAC computed with *any one* onboarded organization's secret: [7](#0-6) [8](#0-7) 

**Before the attack**: `repository_owner == org-a` → secret for `org-a` used to verify → handler acts on `repository.full_name == org-a/...` (consistent, as real GitHub deliveries always are).
**After the attack**: attacker sets `repository.owner.login = "org-a"` (to select `org-a`'s known secret) and signs the body with `org-a`'s `webhook_secret`, but sets `repository.full_name = "org-b/victim-repo"` (or, for `status` events, simply reuses a real commit SHA that also exists in `org-b`'s tracked repository). The signature check passes for `org-a`, yet the handler mutates/queries `org-b`'s stack/commit — the two fields that should be bound together (authenticating org vs. acted-upon repository) diverge.

### Impact Explanation
- Via `PushHandler`, an attacker who only administers/owns a webhook secret for one onboarded organization (`org-a`) can trigger `stack.sync_github(expected_head_sha:)` for any stack belonging to a different tenant (`org-b`), pointing it at an arbitrary SHA of the attacker's choosing.
- Via `StatusHandler`, which does zero repository scoping, forging a `status` event signed with `org-a`'s secret can inject a fabricated `success` commit status for any commit SHA tracked anywhere in the Shipit instance, including another tenant's repository. This directly undermines `MergeRequest#reject_unless_mergeable!`/`StatusChecker`, which gate merges and deploys on required CI statuses — this can enable an **unauthorized merge or deploy** of a commit that never actually passed CI in the target repository.
- Via `CheckSuiteHandler`, the same cross-tenant reach lets an attacker trigger check-run refresh cycles against another tenant's commits.

This satisfies the Critical bucket ("unauthorized deploy, rollback or merge") since CI-gated merge/deploy logic can be defeated cross-tenant using nothing but a webhook secret belonging to an unrelated organization already permitted on the instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls (or has been issued) a `webhook_secret` for at least one onboarded organization — a standard, documented multi-tenant configuration (`config/secrets.yml` `github:` keyed by org, see `lib/shipit.rb#github_app_config`). No repository write access, session, or `ApiClient` token is required; the attacker only crafts a raw HTTP POST to `/webhooks` with a body they sign themselves. This is a realistic "abuse of a lesser trust boundary to attack a stronger one" scenario, directly analogous to the referenced report's core issue (a privileged-but-narrowly-scoped actor able to affect resources outside their intended scope).

### Recommendation
Bind the field used for signature-organization selection to the same field used for repository resolution, and re-verify consistency inside each handler: after resolving `repository_owner`, require that `payload.dig('repository','full_name')` starts with `"#{repository_owner}/"` (reject otherwise), and make `StatusHandler` scope its `Commit` lookup by the verified repository rather than a global SHA search across all tenants.

### Proof of Concept
1. Configure Shipit (as documented) with two organizations, `org-a` and `org-b`, each with a distinct GitHub App and `webhook_secret` in `secrets.yml`.
2. As the operator/attacker who only knows `org-a`'s `webhook_secret`, build a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-in-org-b/target-repo>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook-secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `org-a`'s secret [9](#0-8) .
5. `PushHandler#process` resolves `stacks` via `repository.full_name = "org-b/target-repo"` [10](#0-9)  and calls `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s stack — a cross-tenant write the attacker was never authorized to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
