### Title
Stack-Scoped API Token Can Read CCMenu Status For Any Stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` looks up the target stack via `Stack.from_param!(params[:stack_id])` instead of the stack-scoped `stacks.from_param!(params[:stack_id])` helper defined in `Api::BaseController`. Because of this, an `ApiClient` token that is scoped to a single stack (`api_client.stack_id`) can be used to read build/deploy status (`ccmenu.xml`) for any stack in the installation, not just the one it was authorized for.

### Finding Description
`Api::BaseController` implements the intended authorization binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` carries a `stack_id`, and `stack` performs the lookup through that restricted scope. This is the equality the engine relies on everywhere else: `current_api_client.stack_id == stack.id` (or the client is unscoped).

`Api::CCMenuController`, however, overrides `stack` and bypasses the scoped relation entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class rather than on `stacks`, so the `current_api_client.stack_id` restriction the base controller establishes is never applied. The controller only checks `require_permission :read, :stack` (i.e. that the `read:stack` permission bit is present), never that the requested `stack_id` matches the token's bound stack.

That the stack-scoping mechanism is a real, exercised authorization boundary (not dead code) is confirmed by the `StacksController` test suite, which validates that a stack-scoped client only ever sees its own stack through the properly-scoped `stacks`/`stack` helpers: [3](#0-2) 

This is the analog of the reported bug class: just as the vault's `totalAssets()`/withdrawal execution used a value (share/asset conversion) that was never bound to what the user actually authorized, `CCMenuController#stack` uses a value (`params[:stack_id]`) that is authorized/checked against `read:stack` but never bound to the specific `stack_id` the presented token was actually issued for.

### Impact Explanation
Any holder of a stack-scoped `ApiClient` token (`read:stack` permission, `stack_id` set to stack A) can supply an arbitrary `stack_id` in the URL and receive that other stack's CCMenu status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock state, etc.) rendered by `app/views/shipit/ccmenu/project` — data the token was never authorized to read. This is an authorization-scope escalation resulting in unauthenticated-relative-to-scope read of stack/deploy state across stack boundaries, matching the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" (here: read of state belonging to a stack outside the token's granted scope).

### Likelihood Explanation
Exploitation requires only possession of any valid, stack-scoped `ApiClient` token with the `read:stack` permission — no privileged account, GitHub credentials, or session is needed beyond the token itself, and the mistake (using `Stack` instead of `stacks`) is a straightforward one-line divergence from the pattern used everywhere else in `Api::BaseController`-derived controllers. This makes the bug reliably and trivially reachable by anyone who legitimately has such a scoped token for one stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation, matching every other controller derived from `Api::BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the binding `current_api_client.stack_id == stack.id` for scoped tokens.

### Proof of Concept
1. Obtain (or be issued) a stack-scoped `ApiClient` token whose `permissions` include `read:stack` and whose `stack_id` is set to Stack A only (this is the supported/tested configuration, cf. `test/controllers/api/stacks_controller_test.rb:217-223`).
2. Send:
   ```
   GET /api/stacks/<STACK_B_ID_OR_PARAM>/ccmenu.xml?token=<TOKEN_SCOPED_TO_STACK_A>
   ```
3. `authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves Stack B via `Stack.from_param!`, ignoring that the token's `stack_id` is A.
4. Response 200s with Stack B's CCMenu project status (name, lastBuildStatus, lastBuildLabel, webUrl), which the token was never authorized to access.

Note: I could not find, within in-scope engine code, a UI flow that lets an ordinary user self-provision a stack-scoped `ApiClient` (`ApiClientsController#create_params` only permits `:name` and `:permissions`); such scoped clients are created out-of-band (e.g. by an administrator/console) but are a supported and tested first-class feature of the authorization model, which is what this finding breaks.
