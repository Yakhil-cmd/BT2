### Title
Attacker-controlled `repository.owner.login` vs `repository.full_name` mismatch bypasses org-scoped webhook binding, allowing cross-org ReviewStack provisioning - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the signing organization from `params.dig('repository','owner','login')` and validates the HMAC against that organization's `webhook_secret`, but `PullRequest::OpenedHandler#repository` resolves the target `Repository` from the independent field `params.repository.full_name`. Because nothing enforces that these two fields refer to the same organization, an attacker who controls one integrated org's webhook secret can sign a payload whose `repository.owner.login` is their own org (passing signature verification) while `repository.full_name` names a victim org's repo, causing a `ReviewStack` to be provisioned against the victim repository using attacker-supplied PR data.

### Finding Description
The claimed binding is: `organization_that_authenticated_HMAC == owner(Repository.from_github_repo_name(params.repository.full_name))`.

- `verify_signature` in <cite repo="Ellentat/shipit-engine--022" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" /> computes `repository_owner` via <cite repo="Ellentat/shipit-engine--022" path="app/controllers/shipit/webhooks_controller.rb" start="59-62" /> reading `params.dig('repository', 'owner', 'login')` from the attacker-supplied JSON body, then verifies the HMAC signature using `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` (<cite repo="Ellentat/shipit-engine--022" path="lib/shipit/github_app.rb" start="76-83" />).
- Downstream, `PullRequest::OpenedHandler#repository` resolves the actual target repository from a *different* JSON field, `params.repository.full_name`: <cite repo="Ellentat/shipit-engine--022" path="app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb" start="50-54" />.
- `process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` when `respond_to_pull_request_opened?` (`action == "opened" && provision?`) is true: <cite repo="Ellentat/shipit-engine--022" path="app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb" start="41-46" /> and <cite repo="Ellentat/shipit-engine--022" path="app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb" start="60-70" />.
- Nothing in the request pipeline cross-checks that `repository.owner.login` (used for HMAC org resolution) matches the owner portion of `repository.full_name` (used to load the target `Repository`). The `ExplicitParameters` schema for this handler only requires `repository.full_name` to be a `String`; it does not require or validate `repository.owner.login` at all (<cite repo="Ellentat/shipit-engine--022" path="app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb" start="33-35" />).

Exploit flow: attacker who controls an org already registered with Shipit (has its own `webhook_secret`, per the app's per-org GitHub App config) sends `POST /webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, `pull_request.head.sha/ref` fully attacker-controlled, `action = "opened"`, signed with HMAC-SHA1 using the attacker org's own `webhook_secret`. `verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret, which the attacker legitimately possesses. The handler then loads `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` — the real victim repository — and, if that repo has `review_stacks_enabled` and `provisioning_behavior_allow_all`, provisions a `ReviewStack` scoped to the victim repo using attacker-supplied `pull_request` data.

None of the listed guards prevent this: `verify_signature` only authenticates that *some* org's secret matches the signature, not that the authenticated org matches the target repository named in the payload; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence, not cross-field consistency; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved in the webhook path at all.

### Impact Explanation
A successful request causes a `ReviewStack` record to be created/found for a repository that never authenticated the webhook, using attacker-controlled `pull_request.head.sha`/`ref`. Review stacks subsequently drive stack provisioning and deploy/command execution against that ref. This is a cross-tenant write: a payload signed by org A mutates org B's data/state, matching the "Critical" category ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). The attack is repeatable against any victim repository that has `review_stacks_enabled` with `provisioning_behavior_allow_all` (or the label-based behaviors, if attacker also controls PR label names), for as long as the attacker's own org remains registered with Shipit.

### Likelihood Explanation
Preconditions: (1) the attacker must control at least one organization/repo that is itself registered with this Shipit instance and possesses a valid `webhook_secret` for sending webhooks (this is the "unprivileged" bar defined in this audit — owning a repo that emits webhooks, not any Shipit role); (2) the victim repository must have `review_stacks_enabled` and a permissive `provisioning_behavior` (`allow_all`, or label-based behavior satisfiable via attacker-chosen label names). No GitHub or Shipit secrets belonging to the victim are required — only the attacker's own webhook secret and knowledge of the victim's `owner/repo` full name (public information). This is inexpensive and fully repeatable via direct HTTP POST to `/webhooks`, no live GitHub interaction needed.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler before acting), enforce that the organization whose secret validated the signature (`repository_owner`) matches the owner segment parsed from `params.dig('repository','full_name')` (and ideally also `params.dig('organization','login')` when present), rejecting the request with 422 on mismatch. Additionally, `PullRequest::OpenedHandler` (and sibling handlers) should not trust `repository.full_name` alone to resolve the target `Repository`; they should re-derive/validate the owner against the authenticated org context passed down from the controller.

### Proof of Concept
Minitest plan (webhooks_controller / opened_handler, no live GitHub):
1. Configure two orgs in `Shipit.github_config`/`Shipit.github`: `"attacker-org"` with `webhook_secret: "attacker-secret"`, and `"victim-org"` with `webhook_secret: "victim-secret"`.
2. Create `victim_repository = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")`.
3. Build a `pull_request` `opened` JSON payload where:
   - `payload["repository"]["owner"]["login"] = "attacker-org"`
   - `payload["repository"]["full_name"] = "victim-org/victim-repo"`
   - `payload["pull_request"]["head"]["sha"]/["ref"]` = attacker-controlled values.
4. Sign the raw JSON body with HMAC-SHA1 using `"attacker-secret"`, set as `X-Hub-Signature` header, and `X-Github-Event: pull_request`.
5. POST to `/webhooks`.
6. Assert response is `200 OK` (not `422`), and assert `Shipit::ReviewStack.where(repository: victim_repository)` gained a new row whose `pull_request.head.sha` equals the attacker-supplied SHA — proving org A's signature caused a write scoped to org B's repository.
7. Contrast assertion: before the fix, `repository_owner` (`"attacker-org"`) != owner of `Repository.from_github_repo_name(payload["repository"]["full_name"])` (`"victim-org"`), yet the request succeeds — demonstrating the broken binding.
