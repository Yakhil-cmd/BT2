This is confirmed to be a genuine finding in this engine: the `membership` webhook handler creates/links `Team` and `User` authorization state entirely from attacker-suppliable payload content, and its authenticity is gated only by an *optional*, per-organization `webhook_secret`.

### Title
Unauthenticated forgeable `membership` webhook grants GitHub-team authorization when `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` looks up the `GitHubApp` for the payload's claimed organization and calls `verify_webhook_signature`, but `GitHubApp#verify_webhook_signature` explicitly `return`s `true` unconditionally when `webhook_secret` is blank [1](#0-0) . `webhook_secret` is documented as optional for every configured GitHub App [2](#0-1) [3](#0-2) . When that documented-optional field is left blank, the binding "payload signed by the org's secret" collapses to "no signature required at all," so any unprivileged network client can POST a crafted `membership` event and have it processed as if it came from GitHub, directly creating `Team`/`User` records that back `Shipit.github_teams` authorization.

### Finding Description
The webhook pipeline is: `WebhooksController#create` parses the raw body and dispatches it, unmodified, to registered handlers after `verify_signature` passes [4](#0-3) . `verify_signature` resolves the app config purely from attacker-controlled JSON (`repository.owner.login` or `organization.login`) and asks that app to verify the HMAC [5](#0-4) [6](#0-5) .

`GitHubApp#verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

If the operator leaves `webhook_secret` blank for an organization (a state the shipped example config and setup docs explicitly present as valid: `webhook_secret: # nil`), every webhook for that organization is accepted with **no cryptographic check whatsoever** — the equality the engine is supposed to enforce (`HMAC(secret, raw_body) == X-Hub-Signature`) degrades to `true == true`.

Once accepted, the `membership` event is dispatched to `MembershipHandler#process`, which trusts the payload completely: it creates a `Team` keyed by attacker-chosen `team.id`/`team.slug`/`team.name`, resolves/creates a `User` from an attacker-chosen `member.login` (fetching that login's public GitHub profile), and — for `action: "added"` — calls `team.add_member(member)` [7](#0-6) . `Team` membership is exactly the authorization primitive gating deploy access: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) .

So an attacker who knows (a) that a target Shipit instance has an organization configured without `webhook_secret`, (b) the numeric `github_id`/`slug` of a `Shipit.github_teams`-authorized team, and (c) a target user's GitHub login, can forge a POST to `/webhooks` with `X-Github-Event: membership` and add that user (or a sock-puppet account they control if the target login is attacker's own GitHub account) to the authorized team — escalating that account into `Shipit.github_teams` authorization without ever touching a Shipit session, an `ApiClient` token, or GitHub's real webhook infrastructure.

### Impact Explanation
This directly matches the in-scope "High" impact category: escalation into `Shipit.github_teams` authorization. Team membership drives `User#authorized?`, which downstream code paths use to gate access to deploy-capable UI/actions. No `ApiClient` token, GitHub App private key, or Shipit session is required — only the optional `webhook_secret` being unset, which is a supported, documented configuration state of this engine's own code (`GitHubApp#verify_webhook_signature`), not a violation of the deployment contract.

### Likelihood Explanation
Medium-to-high in any deployment that leaves `webhook_secret` blank (explicitly presented as acceptable in `config/secrets.development.example.yml` and `docs/setup.md`). The attack requires only network access to the `/webhooks` endpoint (no auth) and knowledge of a valid team id/slug and a GitHub login — both are typically public (team slugs are visible in GitHub org UI/API to members, and GitHub logins are always public).

### Recommendation
1. Make `webhook_secret` mandatory rather than optional in `GitHubApp` — refuse to `verify_webhook_signature` (or refuse to construct the app) when the secret is missing, instead of silently returning `true`.
2. At minimum, log/alert loudly and disable state-mutating handlers (`membership`, `push`, etc.) when running with no configured `webhook_secret`.
3. Consider requiring corroboration between `repository_owner`/`organization.login` (used to select the signing secret) and the entity actually mutated by the handler, so a payload cannot claim one org's identity while mutating another org's data even when a secret is configured.

### Proof of Concept
Given a Shipit deployment with an organization configured under `secrets.yml` `github:` with no `webhook_secret` set (per the documented-optional example config):
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "organization": { "login": "targetorg" },
  "member": { "login": "attacker-controlled-login" }
}
```
No `X-Hub-Signature` header is required — `verify_webhook_signature` returns `true` because `webhook_secret` is blank [9](#0-8) . `MembershipHandler#process` creates/looks up `Team(github_id: 48)` and `User(login: "attacker-controlled-login")` and adds the member to the team [10](#0-9) , matching the behavior asserted in the engine's own tests (`test/controllers/webhooks_controller_test.rb` `":membership creates the mentioned team on the fly"` and `":membership creates the mentioned user on the fly"`) [11](#0-10) . If team `48` is listed in `Shipit.github_teams`, the attacker's GitHub account is now authorized.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
