## Title
Ambiguous delimiter-based encoding of contract fields in `arbiter_contract.getHash()` may allow hash-collision forgery of arbiter contract terms - (File: `arbiter_contract.js`)

### Summary
The Sherlock report describes a bug class where variable-length byte/string data is concatenated into a digest without an unambiguous, self-delimiting encoding (i.e., without first hashing or length-prefixing the variable field), letting an attacker construct different logical inputs that hash to the same digest. In `ocore`, `arbiter_contract.js` defines a fixed string delimiter, `exports.DELIMITER = "[|#|]"` [1](#0-0) , which is exported alongside a `getHash(objContract)` function used to hash together attacker/user-controlled string fields such as `title`, `text`, addresses, and party names [2](#0-1) .

### Finding Description
`createAndSend()` computes `objContract.hash = getHash(objContract)` over fields that include free-form strings supplied by the contract counterparty, such as `title`, `text`, `my_party_name`, `peer_party_name`, `amount`, `asset`, and addresses [3](#0-2) . Later, in `wallet.js`, the same hash is recomputed from peer-supplied `contractContent` (decrypted from a message controlled by the *counterparty*) via `arbiter_contract.getHash({...})` and compared against `body.contract_hash` to authenticate the dispute request content [4](#0-3) .

This is architecturally identical to the `TitlesGraph.checkSignature()` root cause: a digest is built by directly combining several variable-length fields. If `getHash()` joins these fields with the plain string delimiter `"[|#|]"` (as its export name and export location alongside `getHash` strongly suggest) rather than length-prefixing or independently hashing each field (the way `object_hash.js`'s `getSourceString` deliberately does, rejecting embedded `STRING_JOIN_CHAR` bytes to prevent exactly this ambiguity, see `string_utils.js` lines 17-21 [5](#0-4) ), then a counterparty who controls `title`/`text`/party-name values can inject the delimiter sequence itself into one field to shift bytes into an adjacent field. Two different `(title, text, party_name, ...)` tuples can then produce the same concatenated pre-image and thus the same hash, defeating the integrity check at `wallet.js` line 780 (`if (body.contract_hash !== expectedContractHash) return callbacks.ifError(...)`) and the analogous check on `payload.contract_text_hash` at line 806 [6](#0-5) .

**Important caveat / unresolved verification**: I was unable to retrieve the actual body of `getHash()` (and `getContactsHash()`) within the available tool budget — only its call sites and the `DELIMITER` constant were confirmed. It is possible `getHash()` actually calls `objectHash.getBase64Hash` (which the file already imports at line 7 [7](#0-6) ) using the safe `getSourceString`/`getJsonSourceString` encoding rather than the raw `DELIMITER`-joined string. Confirming the exact implementation of `getHash()` and `getContactsHash()` in `arbiter_contract.js` is required before treating this as a proven vulnerability rather than a suspected analog.

### Impact Explanation
If confirmed, a malicious arbiter-contract counterparty could get a victim to sign/pay against one set of contract terms (e.g., favorable price/party names) while later presenting a different `title`/`text`/party structure that hashes identically, manipulating arbiter dispute resolution (`arbiter_dispute_request` handling in `wallet.js`) — potentially causing incorrect fund release/freezing decisions by the arbiter, i.e., AA/wallet fund loss analogous to the "unauthorized spending" class required by scope.

### Likelihood Explanation
Likelihood depends entirely on whether `getHash()`/`getContactsHash()` use raw delimiter-joined string concatenation (vulnerable, matching the `TitlesGraph` bug class) or route through `object_hash.js`'s safe `getSourceString`/`getBase64Hash` (not vulnerable, since that function explicitly rejects embedded join-character bytes as shown in `string_utils.js`). This cannot be conclusively determined from the code segments retrieved.

### Recommendation
Verify `getHash()`/`getContactsHash()` implementations in `arbiter_contract.js`. If they concatenate fields with the raw `DELIMITER` string, switch to `objectHash.getBase64Hash`/`getSourceString`-style encoding (which type-prefixes and length-delimits every field and forbids embedding the join character), consistent with how `object_hash.js` already treats unit/message hashing, or alternatively hash each variable-length field independently before combining (mirroring the Sherlock report's fix of hashing `data` before including it in the digest).

### Proof of Concept
Not independently confirmed due to inability to view the `getHash()` function body; the PoC pattern would follow the Sherlock report's approach — craft two `{title, text, my_party_name, peer_party_name, ...}` tuples where one field ends with characters from `DELIMITER` and an adjacent field begins with the remainder, such that raw delimiter-joined concatenation of the two tuples yields identical byte strings and thus identical hashes.
