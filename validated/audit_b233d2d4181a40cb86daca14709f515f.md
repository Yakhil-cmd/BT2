### Title
`in merkle` / `is_valid_merkle_proof` accept forged Merkle inclusion proofs due to missing leaf/node domain separation - ([File: merkle.js])

### Summary
`merkle.js`'s `verifyMerkleProof`/`getMerkleProof` hash leaves and internal nodes with the exact same function (`sha256` over a plain string), with no prefix or other domain separation between "this is leaf data" and "this is a pair of child hashes." [1](#0-0) [2](#0-1)  This is the exact class of bug described in the report (a proof verifier that accepts a value/path pair that was never genuinely committed), except here it lives in ocore's own bridge-less Merkle-proof primitive rather than IAVL, and it is reachable by an ordinary unit poster/AA trigger sender rather than a bridge relayer.

### Finding Description
`verifyMerkleProof` reconstructs the claimed root as follows: [3](#0-2) 

```
var the_other_sibling = hash(element);
for (var i = 0; i < proof.siblings.length; i++) {
    if (index % 2 === 0)
        the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
    else
        the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
    index = Math.floor(index / 2);
}
return (the_other_sibling === proof.root);
```

The first line, `hash(element)`, is supposed to represent "hash of a genuine leaf." But every internal node in the tree is computed with `hash(leftChildHash + rightChildHash)` [4](#0-3)  — i.e. `hash(stringA + stringB)`. Since leaves are hashed as `hash(anyString)`, there is nothing that distinguishes a genuine leaf value from the concatenation of two already-known child hashes. The code even contains a developer comment acknowledging this: `// Node-as-Leaf issue might matter in some cases` [5](#0-4) , but no domain-separation prefix (à la RFC 6962's `0x00`/`0x01` leaf/node prefixes) was ever added.

Concretely: given any two sibling hashes `h0`, `h1` at some tree level (which are directly revealed as `proof.siblings` in any legitimate previous proof, or can be recomputed if the underlying leaf data is public/known), an attacker computes `n0 = hash(h0 + h1)` — this collides exactly with the real internal node hash at that position. The attacker then submits a forged "element" equal to the raw string `h0 + h1` together with an `index`/`siblings` array corresponding to `n0`'s position (skipping the actual leaf level). `verifyMerkleProof` will compute `hash(element) === hash(h0+h1) === n0`, then follow the remaining (genuine) sibling path up to the real, already-committed root, and return `true` — despite `h0+h1` never being a genuine leaf value that was part of the original committed set.

This directly affects two reachable, unprivileged call sites:
- The `'in merkle'` address-definition authentifier, used to gate spending/authentication on membership in an oracle-published Merkle root: `merkle.verifyMerkleProof(element, proof)` followed only by checking that `proof.root` matches a previously-published data feed value. [6](#0-5)  Since `element` (`args[2]`) is chosen by whoever authors the address definition, any address owner (including a non-member of the whitelist) can pick `element = h0+h1` for two hashes they can derive, and supply the corresponding forged proof/siblings as the authentifier, bypassing the intended "is a member of this committed set" check entirely.
- `is_valid_merkle_proof(element, proof)` in the oscript/AA formula evaluator, directly delegating to the same `merkle.verifyMerkleProof`. [7](#0-6)  An AA that uses this opcode to check trigger-supplied data against a committed Merkle root (e.g., a whitelist or allocation table) can be tricked by a malicious trigger sender into treating a non-member/forged value as a valid member, if the sender can derive two sibling hashes of the real tree.

### Impact Explanation
Because both `'in merkle'` (address authentication) and `is_valid_merkle_proof` (AA logic) are core, general-purpose primitives exposed to unprivileged actors (any unit poster defining an address, any AA trigger sender), a forged-proof acceptance directly translates into:
- Unauthorized spending from an address whose definition uses `'in merkle'` to restrict signers/authentication to a committed whitelist, since a non-member can forge inclusion.
- AA fund loss/incorrect state transitions where AA logic relies on `is_valid_merkle_proof` to gate execution (e.g., claim/whitelist/airtable logic), since a trigger sender can forge membership for arbitrary data they choose.

This matches the required "concrete unauthorized spending" / "AA fund loss" bar.

### Likelihood Explanation
Exploitation requires the attacker to know two sibling hashes of the target tree at some level. This is trivially satisfied whenever: (a) the tree's leaf data is public or partially known (e.g. a published whitelist), (b) the attacker previously received or observed any legitimate proof for a real member (siblings are handed out as plaintext in every proof), or (c) the attacker constructs their own address definition and simply picks the forged `element` string to match hashes they compute themselves from public data. No secret key material or race conditions are needed — it's a pure hash-construction flaw, so likelihood is high whenever these opcodes gate anything of value.

### Recommendation
- Domain-separate leaf and internal-node hashing, e.g. `hash("\x00" + element)` for leaves and `hash("\x01" + left + right)` for internal nodes (RFC 6962 style), in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js`. [8](#0-7) 
- Reject proofs whose reconstructed leaf-level input could plausibly be a valid pair of prior hash outputs (defense in depth), and add negative tests specifically constructing the `h0+h1`-as-leaf forgery to prevent regression.
- Audit all consumers (`'in merkle'` in `definition.js`, `is_valid_merkle_proof` in `formula/evaluation.js`) after the fix to ensure serialized proof format changes don't break backward compatibility/versioning (may need an MCI-gated upgrade similar to other protocol changes in this codebase).

### Proof of Concept
1. Build a 4-leaf tree with leaves `L0..L3`; let `h0=hash(L0)`, `h1=hash(L1)`, `n0=hash(h0+h1)`, `n1=hash(h2+h3)`, `root=hash(n0+n1)` — exactly as computed by `getMerkleRoot`. [2](#0-1) 
2. Obtain (or derive) `h0`, `h1`, and `n1` — trivially available from any legitimate proof for `L0` (`proof.siblings = [h1, n1]`) or from public leaf data. [9](#0-8) 
3. Construct a forged proof: `element' = h0 + h1`, `proof' = { index: 0, siblings: [n1], root }`.
4. Call `merkle.verifyMerkleProof(element', proof')`: `hash(element') === n0`, then `hash(n0 + n1) === root`, so the function returns `true`, even though `h0+h1` is not, and never was, a genuine committed leaf. [3](#0-2) 
5. Feed `element'`/`proof'` as the `'in merkle'` authentifier value for `args[2]`/`assocAuthentifiers[path]` in an address definition, or as arguments to `is_valid_merkle_proof` in an AA trigger — both accept the forged proof as valid inclusion against a genuinely published root. [6](#0-5) [7](#0-6)

	var arrHashes = arrElements.map(hash);

// returns a string element_index-siblings_joined_by_dash-root
function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes

			index = Math.floor(index / 2);

	}

		return false;
