### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the independent `repository.full_name` field, letting a payload aimed at one org's (unsecured) webhook config forge writes against a different org's tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate the inbound HMAC against using `repository_owner`, which is read straight from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Every actual event handler, however, resolves the target repository/stack from a *different* field of the same payload: `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

This is the same class of bug as the M-14 report: the entity that is authenticated (`repository.owner.login`, used to pick the signing key) is not the entity that is actually written to (`repository.full_name`, used to pick the Stack/Repository record).

### Finding Description
The binding that should hold is:
`organization whose secret verified the request == organization that owns the repository the handler mutates`

Because the org used for key selection and the repo used for the write come from two independently-attacker-controlled JSON keys inside the same raw body, this binding is not enforced by any code path - it only happens to hold when every `github_app` webhook secret is set to a real value AND the config only has one usable "weak" entry does not exist.

Multi-organization installs are an explicitly supported and documented configuration (`Shipit.github(organization:)`, `github_app_config`, `TOP_LEVEL_GH_KEYS`), where `secrets.github` is keyed by organization, each with its own `webhook_secret`. [5](#0-4) 

`GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatic success: `return true unless webhook_secret`. [6](#0-5) 

The setup docs and sample secrets files explicitly show `webhook_secret` as optional/nilable per organization. [7](#0-6) 

Consequently, if any one configured organization in a multi-org deployment has `webhook_secret` unset (a supported, documented state), an unauthenticated attacker can craft a payload where `repository.owner.login` (or `organization.login`) is set to that unsecured organization - satisfying `verify_signature` trivially - while `repository.full_name` is set to `"other-org/some-tracked-repo"`, a completely different, secured organization's repository that Shipit tracks as a `Stack`. `WebhooksController#verify_signature` never checks that the two fields refer to the same organization, and the downstream handler never re-validates against the org that was actually authenticated.

### Impact Explanation
Handlers act on the spoofed repository as if it were a legitimately verified GitHub webhook:
- `PushHandler#process` finds `Stack`s for the spoofed `repository.full_name`/branch and calls `stack.sync_github(expected_head_sha: ...)`, i.e. it drives synchronization of the target stack's tracked ref using attacker-supplied SHA/branch data. [8](#0-7) 
- `StatusHandler#process` writes fabricated CI status onto real commits of the spoofed repo's stacks via `commit.create_status_from_github!(params)`, which can flip a commit from "safe to deploy" to "green" for another organization's pipeline. [9](#0-8) 

Because status/CI checks are core deploy-gating signals in Shipit, forging them for a repository/organization the attacker was never authenticated against enables an unauthorized deploy (a listed Critical impact) - functionally equivalent to the audited bug's core harm: a verification boundary (org whose secret gated the request) diverging from the entity actually acted upon (a different org's repository).

### Likelihood Explanation
This requires only that a multi-org Shipit deployment leave `webhook_secret` blank for at least one configured organization - a state the code and official docs actively support and even ship as a template default (`webhook_secret: # nil`). No authenticated session, `ApiClient` token, or GitHub write access is needed; the attacker only needs to know the login of the unsecured organization (often public) and the `owner/name` of the victim repository already tracked as a Stack. This is a realistic, low-effort scenario for any operator running Shipit against several GitHub orgs where not every org's app has a webhook secret configured.

### Recommendation
Do not select the verification key from an unauthenticated field that differs from the field the handler will act on. Concretely:
- Derive `repository_owner` for signature verification from the same value later used as `repository_name` (`repository.full_name`'s owner segment), not from a separate/independent field, and require them to match.
- After successful signature verification, re-derive/assert that `payload.dig('repository', 'full_name')`'s owner equals the `repository_owner`/organization whose secret validated the signature, rejecting (422) any mismatch.
- Treat "no webhook_secret configured" as an explicit opt-in rather than a silent bypass - e.g., warn/alert loudly or require an explicit `allow_unsigned: true` flag per organization, since `return true unless webhook_secret` currently makes any org with a blank secret a skeleton key for the signature check.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (a real repository, e.g. `orgB/prod-app`, tracked as a `Stack`).
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/prod-app" },
  "sha": "<real deployed sha of orgB/prod-app>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` computes `repository_owner = "orgA"`, calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
4. `StatusHandler` then resolves `stacks`/`Commit.where(sha: ...)` using `repository.full_name = "orgB/prod-app"` and writes a forged success status onto `orgB`'s commit, potentially unblocking an otherwise-gated deploy - despite the request never being verified against `orgB`'s (properly configured) webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
