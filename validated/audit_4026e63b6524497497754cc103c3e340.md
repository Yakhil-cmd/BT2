### Title
Attacker-controlled `machine.environment.PATH` in a review-stack `shipit.yml` overrides the sanitized `PATH` in `Command#unbundled_env`, causing bare-command RCE - (File: `lib/shipit/command.rb`, `lib/shipit/task_commands.rb`)

### Summary
`Command#unbundled_env` builds a safe `PATH` and then unconditionally merges the task/stack/deploy-spec environment hash on top of it, so any environment source that sets a `PATH` key silently replaces the safe value. `TaskCommands#env` merges `deploy_spec.machine_env`, which is read from the `shipit.yml` of the *commit currently checked out for the task* — for a Review Stack this is the fork PR's own branch, which is fully attacker-controlled when `provisioning_behavior=prevent_with_label` and the attacker simply avoids adding the opt-out label.

### Finding Description
The broken binding: for every spawned deploy/task process, the equality that must hold is
`PTY.spawn` env `PATH == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (the sanitized, operator-controlled PATH),
but the actual code produces
`PTY.spawn` env `PATH == @env['PATH']` whenever `@env` (the task command's merged environment) contains a `PATH` key, because: [1](#0-0) 

`unbundled_env` computes `BASE_ENV.merge('PATH' => safe_path).merge(@env.stringify_keys)` — the `@env` merge happens *last*, so a `PATH` entry in `@env` wins over the safe default.

`@env` is built by `TaskCommands#env`, which merges `deploy_spec.machine_env` (from `shipit.yml`'s `machine.environment`) directly into the environment with no key filtering: [2](#0-1) 

`deploy_spec.machine_env` is sourced from `config('machine', 'environment')` in the `DeploySpec`, populated by `DeploySpec::FileSystem` reading `shipit.yml` out of the task's checked-out working directory (i.e., the commit under deploy) — for a Review Stack task this is the PR branch's own file content: [3](#0-2) [4](#0-3) 

Under `provisioning_behavior=prevent_with_label`, `provision?` is true for **every** opened PR that does *not* carry the opt-out label — i.e., dynamic provisioning (and thus review-stack task execution against that commit) is reachable by default, unprivileged, unlabeled fork PRs: [5](#0-4) 

Once the review stack is provisioned and a deploy/task is executed, `DeployCommands#env`/`TaskCommands#perform` builds `Command.new(command_line, env:, chdir:)` for each `shipit.yml` step, and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir:)`: [6](#0-5) 

Existing guards do not stop this: `EnvironmentVariables#permit`/`sanitize_env_vars` is only invoked by `TaskDefinition#filter_envs`, used for the *custom task variables* input path (`app/models/shipit/task_definition.rb:63-65`), not for `deploy_spec.machine_env` merged inside `TaskCommands#env`. There is no denylist anywhere blocking a `PATH` key (or other dangerous keys such as `LD_PRELOAD`, `RUBYOPT`) from `machine.environment`. Because `shipit.yml`'s `deploy`/`dependencies` steps are typically bare command names (e.g., `bundle install`, `cap $ENVIRONMENT deploy`), a hijacked `PATH` prepending an attacker-writable directory (also supplied via the same repo checkout, e.g. `./bin`) causes the shell to resolve `bundle`/`cap`/etc. to an attacker-supplied executable, achieving code execution on the Shipit deploy host under the Shipit service account.

### Impact Explanation
An unprivileged fork PR author can, without any label or special permission (under `prevent_with_label`, simply not applying the opt-out label), have Shipit provision a Review Stack against their PR commit and run deploy/dependency steps whose environment's `PATH` is fully attacker-controlled via `shipit.yml`'s `machine.environment.PATH`. This overrides the safe `Shipit.shell_paths`-prefixed `PATH` in `Command#unbundled_env`, letting a bare command in any step resolve to an attacker binary — Remote Code Execution on the Shipit deploy host, matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category. This is repeatable per-PR/per-repository that has review stacks enabled with this provisioning behavior, and the blast radius covers whatever the deploy host process can reach (other stacks' git caches, `GITHUB_TOKEN`, secrets in `Shipit.env`, etc.), since the attacker fully controls process execution once spawned.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = true` with `provisioning_behavior = prevent_with_label` (a documented, supported, opt-out configuration) and no maintainer review gate before task execution begins. Attacker cost is minimal: fork the repo, open a PR without the opt-out label, include a `shipit.yml` with `machine.environment.PATH` set and an attacker binary placed at that resolved path within the repo checkout. No secrets, tokens, or privileged roles are required — this is exactly the unprivileged actor described in the rules.

### Recommendation
In `Command#unbundled_env` (`lib/shipit/command.rb`), compute the safe `PATH` *after* merging `@env`, or explicitly strip/ignore a `PATH` key from any caller-supplied environment (`.except('PATH')`) before merging, so the operator-controlled `Shipit.shell_paths`/`ENV['PATH']` value always wins. Additionally, apply an explicit denylist (at minimum `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`) to `deploy_spec.machine_env` before it is merged in `TaskCommands#env`, mirroring the `EnvironmentVariables#permit` allowlist pattern already used for task variables.

### Proof of Concept
minitest plan (`test/unit/command_test.rb` or `test/unit/task_commands_test.rb` style):
```ruby
test "unbundled_env does not allow caller-supplied env to override the safe PATH" do
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command = Shipit::Command.new('true', env: { 'PATH' => '/tmp/evil' }, chdir: '.')

  # Binding under test: the PATH reaching PTY.spawn must equal the safe PATH,
  # not the attacker-controlled value.
  assert_equal safe_path, command.unbundled_env['PATH']
  refute_equal '/tmp/evil', command.unbundled_env['PATH']
end

test "TaskCommands#env allows shipit.yml machine.environment to inject PATH" do
  deploy_spec_stub = stub(machine_env: { 'PATH' => '/tmp/evil' })
  commands = Shipit::DeployCommands.new(deploy)
  commands.stubs(:deploy_spec).returns(deploy_spec_stub)

  assert_equal '/tmp/evil', commands.env['PATH']
end
```
Both assertions currently fail against the safe binding (i.e., the PoC demonstrates `@env['PATH']` reaching `unbundled_env` unfiltered), confirming the vulnerability without any live GitHub interaction.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil

        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT

      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
