## Title
Arbiter Contract Hash Collision via Undelimited String Concatenation Allows Cross-Contract Escrow Data-Feed Key Reuse - (File: `arbiter_contract.js`)

## Summary
The reported NATS-Server bug class is "session/message hijacking via Client-ID malfeasance" — a client-supplied identifier that is not properly bound to the connection's actual identity lets an attacker claim another session's messages. The closest reachable analog in `ocore` is the `contract.hash` computed by `getHashSrc()` in `arbiter_contract.js`, which is used verbatim as the on-chain data-feed key (`"CONTRACT_" + hash` / `"CONTRACT_DONE_" + hash`) that authorizes fund release from a shared arbiter escrow address. Before `exports.NEW_HASH_DATE` ('2026-11-01') — which is still in the future relative to today (2026-09-15), so this is the code path presently in effect — this hash neither includes the parties' addresses nor uses a field delimiter, making the "session id" (the escrow key) forgeable/collidable by an unprivileged contract-offering peer.

## Finding Description
`getHashSrc()` computes the contract identifier that becomes the escrow condition key: [1](#0-0) 

For any contract whose `creation_date` is not after `NEW_HASH_DATE`, the hash source is:
```
[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")
```
Two problems compound here:
1. **No delimiter** between fields — the old branch uses `.join("")` instead of `exports.DELIMITER`, so field boundaries are ambiguous (e.g. `title="AB", text="CD"` yields the same source string as `title="A", text="BCD"`).
2. **No address binding** — unlike the new-format hash, the legacy hash never includes `payer_address`/`payee_address`, so contracts between entirely different parties with the same `title`, `text`, `creation_date`, party names, `arbiter_address`, `amount`, and `asset` collide by construction.

This `contract.hash` is then embedded directly into the oscript definition of the shared multisig escrow address in `deriveSharedAddress()`, as the data-feed key an arbiter (or, for private assets, either counterparty) posts to authorize release of funds: [2](#0-1) 

Because the key is only `"CONTRACT_" + contract.hash` (scoped by `arbiter_address`, not by the specific addresses involved), any second contract that a malicious counterparty (an ordinary, unprivileged contract-offering peer, reachable via `createAndSend`) constructs so that it hashes to the same value as an existing contract under the same arbiter will share the identical escrow-authorization key. This is a direct structural analog of "Client ID malfeasance": the identifier meant to scope a session/escrow ("Client ID" in MQTT, `contract.hash` here) is not cryptographically bound to the actual participants, so it can be reused/collided by an attacker to have data-feed decisions or completion markers "intended" for one contract's parties also unlock a different contract's shared address. [3](#0-2) 

## Impact Explanation
If a malicious peer constructs an arbiter contract whose hash collides with an existing, unrelated contract that shares the same arbiter, the escrow spending condition on the malicious peer's own shared address becomes satisfiable by a data feed (arbiter resolution, `CONTRACT_<hash>`) or self-reported completion (`CONTRACT_DONE_<hash>`, private assets) that was never intended for that contract. This can lead to unauthorized fund release from an arbiter/multisig escrow — i.e., unauthorized spending / fund confusion between two unrelated escrow agreements sharing an arbiter, which matches the "concrete unauthorized spending" / "AA-like fund loss" impact bar required by the validation rules. Because part of the collision (title/text) is fully attacker-controlled and only the timestamp field realistically constrains exact collision, exploitability is non-trivial but not purely theoretical, warranting Medium severity, consistent with the CVSS 6.5 of the source advisory.

## Likelihood Explanation
Reachable by any unprivileged wallet user who can propose an arbiter contract (`arbiter_contract.createAndSend`) to a counterparty using the same, publicly known arbiter address as a target contract. Exact collision requires matching `creation_date` (second-level granularity) in addition to attacker-chosen fields, which limits practical exploitation to a race/coincidence window or targeting contracts whose date is already known/predictable, making it Medium rather than High likelihood.

## Recommendation
Always use the delimited, address-bound hash (the branch currently gated behind `NEW_HASH_DATE`) unconditionally, rather than allowing a naive concatenation-without-delimiter, address-less path to remain in effect until 2026-11-01. Additionally, incorporate a full domain separator/salt (e.g., a random per-contract nonce or the full addresses of both parties plus device addresses) into the hash unconditionally so that no two distinct agreements under the same arbiter can ever produce the same escrow data-feed key.

## Proof of Concept
1. Attacker (Bob) observes/agrees an arbiter contract exists between Alice and Carol via arbiter `Arb1`, with known `title`, `text`, `creation_date` (to the second), `payer/payee` names, `amount`, and `asset`.
2. Bob calls `arbiter_contract.createAndSend()` with a contract that has the exact same `title+text` concatenation, `creation_date`, party names, `arbiter_address = Arb1`, `amount`, and `asset`, but sets his own `my_address`/`peer_address` for a different peer (Dave).
3. `getHash()` produces the same `contract.hash` as Alice/Carol's contract (pre-`NEW_HASH_DATE` branch, no delimiter, no address binding).
4. `deriveSharedAddress()` builds Bob/Dave's shared address with the oscript condition `["in data feed", [[Arb1], "CONTRACT_" + hash, "=", offeror_address]]`.
5. When `Arb1` later resolves the Alice/Carol dispute by posting a data feed `{"CONTRACT_<hash>": Alice_address}`, this same data-feed value also satisfies Bob/Dave's shared-address spending condition if `offeror_address` in Bob's contract was chosen to equal `Alice_address`, letting Bob's colliding escrow be released using an arbiter decision that was never about Bob's contract. function getHashSrc(contract) {
```javascript
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
```
