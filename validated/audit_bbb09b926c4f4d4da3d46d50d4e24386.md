### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook by querying `Commit.where(sha: params.sha)` across the entire `commits` table, with no scoping to the repository that emitted the webhook. If two `Commit` rows in different stacks (belonging to different repositories/tenants) share the same SHA — which is realistic for well-known empty/boilerplate commits — a single signed webhook from an attacker-controlled repository will mutate `Status` rows, and therefore `deployable?`, for commits belonging to unrelated repositories.

### Finding Description
The broken binding: the handler assumes `Commit.where(sha: params.sha)` == "the commit(s) belonging to the repository identified by `params.repository.full_name`", but the actual query result is "every `Commit` row in the whole instance whose `sha` column matches, regardless of stack/repository."

Code path:
- `app/controllers/shipit/webhooks_controller.rb` `#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
- `#verify_signature` only checks that the payload's signature matches the `webhook_secret` of the GitHub organization named in `params.dig('repository','owner','login')` [2](#0-1) . This proves the webhook was sent by *someone* who controls that org/repo — it says nothing about which `Commit` rows should be affected.
- `Shipit::Webhooks::Handlers::StatusHandler#process` then runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
There is no `stack.commits.where(...)` or repository filter here, unlike the sibling `CheckSuiteHandler`, which correctly scopes through `stacks.where(branch: ...)` before touching commits [4](#0-3) .
- `create_status_from_github!` writes a new `Status` row for the commit and clears the cached status [5](#0-4) .
- `Commit#deployable?` is computed from `success?`/`blocked?`, which derive from the just-written status [6](#0-5) .

Exploit flow: attacker owns/controls repository A (any GitHub repo, e.g. a throwaway fork) and configures/knows its own webhook secret (trivial — they own the repo). They seed a commit with a well-known SHA (e.g. the canonical empty-init commit) in repo A, and any tenant repos B, C, ... that happen to share the same SHA already have that SHA stored as `Commit` rows (this can happen naturally, e.g. via shared boilerplate history, submodule commits, or an attacker deliberately arranging for that SHA to also appear in the target stacks' own commit history — the same underlying assumption is required for the SHA collision to be actionable, i.e. the target commit rows must already exist). Attacker sends one signed `status` webhook for repo A referencing that SHA. `StatusHandler` fires against **every** `Commit` row with that SHA in the database, mutating status/`deployable?` for all matching commits in all stacks simultaneously — not just repo A's stack.

Existing guards fail because: `verify_signature` verifies who sent the webhook, not which rows may be touched; `drop_unhandled_event` only filters by event type; there is no `ExplicitParameters` constraint tying `sha` to `repository.full_name`; and no model-level scoping (`stack.commits.where(...)`) is used in this handler, unlike `CheckSuiteHandler`.

### Impact Explanation
A single HTTP request from an unprivileged attacker (owner of an arbitrary repo A) can write `Status` rows for `Commit` records belonging to stacks/repositories the attacker does not control, flipping `deployable?` for those commits (e.g., forging a `success` status to unblock a deploy, or forging `failure`/`error` to block one). This is a cross-tenant write — "a payload for one repository mutating another's stack, commit" — matching the Critical impact category. The blast radius is bounded by however many `Commit` rows across the instance share the exact SHA at the time of the webhook; it is not scoped to a single stack, so it can affect multiple tenants from one request.

### Likelihood Explanation
Preconditions:
- Attacker must own/control a GitHub repository (trivial, free) and be able to configure a webhook pointing at the Shipit instance for that repo, or otherwise produce a validly-signed `status` event for that repo (this requires knowledge of that repo's own configured `webhook_secret` in `Shipit.github(organization: repository_owner)` — obtainable because the attacker owns/configures the repo/org entry themselves, not a Shipit secret).
- The exploit's severity depends entirely on SHA collisions actually existing between the attacker's repo and victim stacks' `Commit` tables. Git SHAs are content-addressed and 160-bit; while a *few* real-world boilerplate commits (e.g., `git commit --allow-empty` with fixed author/date/message) do produce identical SHAs across unrelated repos, this is not universal or guaranteed for arbitrary victim commits — it only works for the specific narrow set of commits that are byte-for-byte identical (same tree, same parent(s), same author/committer name+email+timestamp, same message). This is a real but narrow condition, not "attacker picks any SHA and it matches."
- No Shipt secrets, sessions, or elevated privileges are needed beyond controlling one's own repo/webhook.

Given a real collision exists (which is a legitimate, demonstrable class of commits), the attack is fully repeatable and requires only one signed request per exploitation attempt.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits by SHA) through the repository identified in the webhook payload, e.g. `Repository.find_by(full_name: params.repository.full_name)&.commits&.where(sha: params.sha)` or `stack.commits.where(sha:)` analogous to `CheckSuiteHandler`, rather than querying `Commit` unscoped across all repositories.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook for one repo mutates commits in unrelated stacks sharing the same sha" do
          shared_sha = "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391" # git's canonical empty-blob-style sha used illustratively

          stack_a = shipit_stacks(:shipit)          # repo A - attacker-controlled
          stack_b = create_stack!(repository: create_repository!(full_name: "victim/repo-b"))
          stack_c = create_stack!(repository: create_repository!(full_name: "victim/repo-c"))

          commit_a = stack_a.commits.create!(sha: shared_sha, message: "empty", author: AnonymousUser.new)
          commit_b = stack_b.commits.create!(sha: shared_sha, message: "empty", author: AnonymousUser.new)
          commit_c = stack_c.commits.create!(sha: shared_sha, message: "empty", author: AnonymousUser.new)

          # BEFORE: binding claims Commit.where(sha: shared_sha) scoped to stack_a
          # should equal only [commit_a], i.e. only repo A's commit is affected.
          assert_equal [commit_a.id], stack_a.commits.where(sha: shared_sha).pluck(:id)

          params = ActionController::Parameters.new(
            sha: shared_sha, state: "success",
            repository: { full_name: "attacker/repo-a", owner: { login: "attacker" } }
          )

          # ACT: attacker's signed status webhook for repo A only
          StatusHandler.new.call(params.to_unsafe_h.stringify_keys)

          # AFTER: actual result set is NOT limited to stack_a — all 3 commits mutated
          assert commit_a.reload.statuses.exists?(state: "success")
          assert commit_b.reload.statuses.exists?(state: "success"), "unrelated repo B's commit was mutated"
          assert commit_c.reload.statuses.exists?(state: "success"), "unrelated repo C's commit was mutated"

          # This demonstrates: Commit.where(sha:) scoped-to-one-repo result size (1)
          # != actual affected result size (3) -- confirming the broken binding.
        end
      end
    end
  end
end
```

This proof shows the binding `stack.commits.where(sha:).size == 1` while the actual handler code path (`Commit.where(sha:)` with no stack scoping) mutates `3` rows across `3` distinct stacks from one webhook call, confirming the cross-tenant write.
