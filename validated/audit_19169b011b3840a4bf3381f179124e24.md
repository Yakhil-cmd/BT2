### Title
Webhook signature verification is bound to the wrong organization, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
### Finding Description
Shipit's multi-tenant webhook handling authenticates a GitHub webhook by looking up a per-organization secret using an **unauthenticated** field from the request body, then applies the resulting signature check as if it validated the entire payload — including a *different*, unauthenticated field that determines which repository/stack the event is actually applied to.

In `WebhooksController`, the signature check runs as a `before_action`, and the organization used to select the verification secret is derived directly from the JSON body before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and is used only to select which `Shipit.github(organization: ...)` app/secret pair to check the signature against: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization (`return true unless webhook_secret`). The setup documentation explicitly treats the webhook secret as **optional** per organization: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (or is skipped), the full, still-unverified JSON body is handed to every registered handler for the event: [6](#0-5) 

The value used to *select the verification key* (`repository.owner.login`) and the value used by handlers to *look up the target Stack/repository* (`repository.full_name`, read from the same attacker-supplied JSON body) are two independent fields with no cryptographic binding between them. Nothing forces the org whose secret validated the request to be the org that owns the repository the event is subsequently applied to.

This mirrors the oracle bug's root cause: a value used to gate a critical decision (`repository.owner.login` selecting the trust boundary) is disjoint from the value the system actually acts on (`repository.full_name` writing to a specific stack), and an attacker fully controls both, independently, in the same forged request.

### Impact Explanation
If a Shipit deployment manages multiple GitHub organizations (the documented and supported multi-org configuration) and at least one configured organization has no `webhook_secret` set (explicitly supported as "optional"), an attacker can craft a webhook payload where:
- `repository.owner.login` / `organization.login` = the organization with **no** secret (so `verify_webhook_signature` trivially returns `true`), and
- `repository.full_name` = a repository belonging to a **different**, privileged organization that Shipit also manages.

The request passes `verify_signature` (bypassed for the unsecured org) while the event handlers act on the victim organization's stack using the attacker-controlled body — enabling forged `push`, `status`, `check_suite`, `deployable_status`, etc. events. Depending on stack configuration (`ignore_ci`, continuous deployment, merge queue), this can flip commit status/deployable state and trigger an **unauthorized deploy or merge** on a repository the attacker never had signing credentials for.

### Likelihood Explanation
Requires no privileged credentials, no `ApiClient` token, and no GitHub write access — only knowledge that the target Shipit instance manages multiple orgs and that one has no webhook secret configured (a state the project's own docs present as a normal, optional setup path, not a misconfiguration outside the documented design).

### Recommendation
Do not select the verification secret from an unauthenticated payload field. Bind the signature check to the specific target repository/stack instead of the organization-derived app config, and reject events where the authenticated organization does not match the repository the payload claims to affect. Additionally, consider making `webhook_secret` mandatory (fail closed) rather than silently bypassing verification when absent.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-open` (no `webhook_secret`) and `org-secure` (has a `webhook_secret`), both with stacks registered.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "repository": { "full_name": "org-secure/victim-repo", "owner": { "login": "org-open" } }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-open")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of any (or missing) `X-Hub-Signature` header.
4. The status handler processes the event against `org-secure/victim-repo`, marking the attacker-chosen commit's status as `success` without ever presenting a valid signature for `org-secure`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
