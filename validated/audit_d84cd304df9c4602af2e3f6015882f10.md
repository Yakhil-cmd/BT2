### Title
`StatusHandler#process` matches commits globally by `sha` with no repository/organization scoping, letting a signed webhook from one org mutate commit rows belonging to any other org's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter tying the query to the repository/organization that signed the webhook. Since `Commit.sha` is not unique across the whole installation (any stack, for any repo/org, can contain a commit with any given sha, including via forks/rebases/cherry-picks), a legitimately signed webhook from `myorg` can mutate `Commit`/`Status` rows belonging to an unrelated org's stack whenever a sha collision exists.

### Finding Description
The claimed binding is: `{stacks owned by the org that signed the webhook} == {stacks whose Commit rows get create_status_from_github! called}`. Tracing the code shows this binding is violated.

- `WebhooksController#verify_signature` authenticates the webhook using `repository_owner` derived from the payload (`params.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) . This only proves the payload's `repository.owner.login`/HMAC secret matches `myorg` - it says nothing about which `Commit` rows may be touched.
- The base `Handler` class provides a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, derived from `payload.dig('repository','full_name')` [3](#0-2) . `StatusHandler`, however, does not use this `stacks` scope at all.
- `StatusHandler#process` instead queries `Commit.where(sha: params.sha)` across the **entire** `commits` table, with no `joins(:stack)` / `stack.repository` filter, and calls `commit.create_status_from_github!(params)` on every matching row regardless of which stack/repository/org owns it [4](#0-3) .
- `Commit#create_status_from_github!` performs a real write: it creates a `Status` record via `statuses.replicate_from_github!(stack_id, github_status)`, updates commit/stack `status` state, and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [5](#0-4) [6](#0-5) . A pending/success status on an unrelated org's commit can trigger merge scheduling logic for that org's stack.
- Nothing in `ExplicitParameters` schema, `drop_unhandled_event`, or model validations restricts the sha match to the signing org's repositories - the schema only validates the shape of `sha`/`state`/etc, not tenancy [7](#0-6) .

**Exploit flow**: An attacker with legitimate control of `myorg`'s GitHub repo (able to push commits/PRs, thus able to choose/force a sha to collide, e.g. via a rebase producing an identical tree+parent+author+timestamp+message, or more simply via naturally occurring cherry-picks/rebases across independently hosted forks that Shipit tracks as separate stacks) triggers a `status` event on `myorg/app`. GitHub signs it with `myorg`'s webhook secret. `verify_signature` passes because the payload's `repository.owner.login` is `myorg`. `StatusHandler#process` then matches **every** `Commit` row across the whole Shipit instance with that sha - including one belonging to `otherorg/other`'s stack - and calls `create_status_from_github!` on it, writing a `Status` row and potentially firing hooks/merge-scheduling for `otherorg`'s stack.

### Impact Explanation
A payload legitimately signed by one organization causes writes (`Status` creation, hook emission, and potential merge scheduling) on another, unrelated organization's `Commit`/`Stack` records. This is a cross-tenant mutation: "a payload for one repository mutating another's stack, commit, task or team," matching the Critical impact category. The blast radius extends to every unrelated stack in the same Shipit installation that happens to have a `Commit` with a colliding sha - this can affect CI-status-gated behavior (`deployable?`, `schedule_merges`) on stacks the attacker has no relationship with.

### Likelihood Explanation
This requires: (1) at least one commit sha collision between an org-controlled stack and a victim stack in the same Shipit deployment (git shas are 40 hex chars, so accidental collision across independent histories is not expected, but is achievable/likely in cases such as squash-merges, cherry-picks with identical author/committer/timestamp/message/tree, imported/forked histories, or shared upstream commits synced into multiple orgs' repos/stacks tracked as separate `Stack` rows); (2) the attacker only needs standard write access to their own GitHub repo to emit a `status` webhook - no Shipit credentials are needed. The attacker cost is low (any push/CI status update on their own repo) but the collision precondition is environment-dependent, so likelihood is moderate rather than trivial, though the code path itself is unconditionally reachable and unscoped for every signed status event.

### Recommendation
Scope `StatusHandler#process` to the repository that actually signed the request, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks under the repository named in the signed payload are mutated.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, following existing conventions):
1. Create three stacks: `stack_myorg_staging` and `stack_myorg_prod` (repository `myorg/app`), and `stack_otherorg` (repository `otherorg/other`).
2. Create a `Commit` with an identical `sha` (e.g. `"a" * 40`) under each of the three stacks.
3. Build a `status` payload with `repository.full_name = "myorg/app"`, `repository.owner.login = "myorg"`, and the shared `sha`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, since the binding under test is post-verification).
5. Assert (binding equality, before/after):
   - Before: `stack_otherorg.commits.find_by(sha: sha).statuses.count == 0`
   - After: expected (correct) = `stack_otherorg.commits.find_by(sha: sha).statuses.count == 0` (unchanged, not in `myorg`'s stack set)
   - Actual (current code): `stack_otherorg.commits.find_by(sha: sha).statuses.count == 1` -- proving the unrelated org's commit was mutated by `myorg`'s signed webhook, while `stack_myorg_staging` and `stack_myorg_prod` commits were correctly updated (superset violation confined to `otherorg`).
