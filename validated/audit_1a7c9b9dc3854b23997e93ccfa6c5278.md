## Analysis

The reported bug class is a **binding break between an authorized scope and the value actually consumed** — the surcharge computation trusted a derived value instead of the strictly verified one. The equivalent binding in shipit-engine is: `ApiClient#stack_id` (the stack a token is *authorized* for) must equal the stack a request actually *touches*. This binding is enforced centrally in `Api::BaseController` via the `stacks` scoping helper, but `Api::CCMenuController` bypasses it.

`Api::BaseController` scopes all stack lookups to the API client's own `stack_id` when one is set: [1](#0-0) 

Every other stack-scoped API controller resolves the stack through this `stacks` relation (e.g. `LocksController`, `StacksController#show`), so a token created with `stack: <A>` can never touch stack `B`. `ApiClient#check_permissions!` only checks that the string `"read:stack"` is present in the permission list — it never checks which stack is being accessed: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that loads directly from `params[:stack_id]` without going through the client-scoped `stacks` relation: [3](#0-2) 

This means: `ApiClient#stack_id == A` (the stack the token authorizes) but the endpoint permits `params[:stack_id] == B` (the stack it actually touches) — the same category of unenforced binding as the original report (value used ≠ value that should have been checked).

That a stack-scoped `read:stack` ApiClient is a real, supported credential is confirmed by the fixture and its associated test expectation: [4](#0-3) [5](#0-4) 

Route confirms the endpoint takes `stack_id` from the URL segment directly, matching `CCMenuController#stack`'s naive lookup: [6](#0-5) 

### Title
Stack-scoped ApiClient token authorization bypass in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` loads `Stack.from_param!(params[:stack_id])` directly instead of using the client-scoped `stacks` relation used by every other API controller, allowing a `read:stack` token that is bound to one specific stack to read deploy status/state for any other stack in the installation.

### Finding Description
`Api::BaseController` restricts stack visibility for a stack-bound `ApiClient` via `stacks`, which filters to `Stack.where(id: current_api_client.stack_id)` when the token has a `stack_id` [7](#0-6) . `Api::CCMenuController` overrides `stack` and instead resolves it unconditionally from `params[:stack_id]` via `Stack.from_param!` [8](#0-7) , completely skipping the per-token stack restriction. `require_permission :read, :stack` only validates that the string `"read:stack"` exists in the client's permission list [2](#0-1) ; it performs no per-object authorization. As a result, the equality that should hold — `token.stack_id == requested stack` — is never checked on this endpoint, exactly mirroring the original bug's core defect: a security-relevant value is trusted without being bound to the value that was actually authorized/verified.

### Impact Explanation
Any holder of a stack-scoped `read:stack` ApiClient token (e.g. a CI system or third party given restricted access to one repository/environment's deploy status) can enumerate/read deploy and rollback state (`stack.deploys_and_rollbacks.last`) for every other stack in the Shipit instance, including stacks belonging to unrelated teams or repositories, simply by changing `stack_id` in the URL. This is unauthenticated-relative-to-scope read of stack state, meeting the "High — unauthenticated read of stack state" bar since the token was never authorized for those stacks.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack` API token (no elevated privilege), and the attack is a single unauthenticated GET request with an attacker-chosen `stack_id` path segment — trivial to execute once a token scoped to any single stack is obtained.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same client-scoped relation used elsewhere, e.g. `stacks.from_param!(params[:stack_id])` (inherited from `BaseController`), instead of `Stack.from_param!(params[:stack_id])`, so a stack-bound token can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only (as modeled by the `here_come_the_walrus` fixture) [4](#0-3) .
2. Using that token's Basic-Auth credentials, send `GET /api/stacks/<owner_b>/<repo_b>/<env_b>/ccmenu` for Stack B (any other existing stack), per the route `scope '/stacks/*stack_id', ... get '/ccmenu' => 'ccmenu#show'` [6](#0-5) .
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes (permission string present) [9](#0-8) .
4. `stack` resolves Stack B directly from `params[:stack_id]`, bypassing the `stacks` scoping that would have restricted lookup to Stack A only [8](#0-7) .
5. Response renders Stack B's deploy/rollback status — data the token was never authorized to access.
