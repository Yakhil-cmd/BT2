## Finding [1](#0-0) 

### Title
Unauthenticated Re-submission of Cosigner Extended Pubkey Overwrites Already-Approved Multisig Wallet Key Material - (File: wallet_defined_by_keys.js)

### Summary
`addDeviceXPubKey()` is reachable from an unauthenticated `my_xpubkey` device message that ocore explicitly whitelists to be processed even from devices that are **not** paired/known correspondents, and it unconditionally overwrites a cosigner's `extended_pubkey`/`approval_date` with no check for whether the wallet was already approved or fully finalized, mirroring the hoppscotch onboarding-config bug class ("no auth guard + no already-completed check on an endpoint that overwrites security-critical configuration").

### Finding Description
The `my_xpubkey` subject is explicitly allowed from non-correspondent devices: [2](#0-1) 

and is routed straight into `walletDefinedByKeys.addDeviceXPubKey`: [3](#0-2) 

`addDeviceXPubKey` performs an `INSERT OR IGNORE` followed by an unconditional `UPDATE`, with no guard analogous to the `IS NULL` idempotency checks used elsewhere in the same file (`full_approval_date IS NULL`, `ready_date IS NULL`): [4](#0-3) [5](#0-4) 

Because `device_address` is derived cryptographically from the sender's own device pubkey (`from_address = objectHash.getDeviceAddress(device_pubkey)`), an attacker can only rewrite the `extended_pubkey` row keyed to their **own** device_address — but crucially there is no restriction preventing them from doing this repeatedly, at any time, including long after `approval_date` and even `full_approval_date`/`ready_date` were already set for the wallet. Each cosigning device keeps its own local copy of every other member's `extended_pubkey` (populated via `sendMyXPubKey`), and `deriveAddress()` deterministically recomputes the shared multisig address locally from whatever pubkeys currently sit in the local `extended_pubkeys` table: [6](#0-5) 

A device that was ever a legitimate cosigner (even one later removed/unpaired, since `my_xpubkey` bypasses the correspondent check) can send a fresh, unsolicited `my_xpubkey` message at any later time, silently changing the pubkey it contributes to the shared wallet definition on the receiving node — with no re-approval, no consensus among cosigners, and no signal that the wallet configuration changed. This exactly parallels the hoppscotch flaw: a state-changing operation intended for one-time bootstrap ("cosigner submits their pubkey") is left reachable and idempotency-free after the flow has already been completed.

### Impact Explanation
Once one cosigner's node accepts a stale/attacker-supplied re-submission, that node's locally computed shared multisig address for future indices diverges from what the other cosigners believe is correct (they still hold the older pubkey in their own local tables). This is a node-disagreement / fund-freezing scenario: funds sent to the address derived on the affected node may not be recognized or spendable by the rest of the group using their original definition, and vice versa — directly matching the accepted impact class "node disagreement on validity/stability" or "AA/wallet fund loss or freezing" for a shared-wallet (contract-like) construct.

### Likelihood Explanation
The message path (`hub/message` → `handle_message_from_hub` → `my_xpubkey`) requires no pairing and no prior authentication beyond knowing the target device's pubkey/hub and the `wallet` id (learned during normal wallet setup broadcast, or by any device that was once part of the cosigner set). No signature over "this is the final key" or approval-state check exists to prevent replay/overwrite, making exploitation straightforward for any former or current cosigning device.

### Recommendation
Add an idempotency/state guard to `addDeviceXPubKey` (and `handleNotificationThatWalletFullyApproved`) analogous to the `... IS NULL` guards used in `checkAndFullyApproveWallet`/`checkAndFinalizeWallet`, e.g. only allow the `UPDATE ... SET extended_pubkey=...` when `approval_date IS NULL`, and require explicit user/group re-confirmation for any subsequent key rotation of an already-approved wallet member.

### Proof of Concept
1. Device A creates a 2-of-2 multisig wallet with Device B; both approve and the wallet becomes fully approved (`full_approval_date` set) — see `checkAndFullyApproveWallet`.
2. Later, Device B (or any device sharing B's registered device_address/pubkey) sends an unsolicited `my_xpubkey` hub message for the same `wallet` id with a different `xPubKey`.
3. Device A processes it via the non-correspondent-whitelisted path (`arrSubjectsAllowedFromNoncorrespondents`) and calls `addDeviceXPubKey`, which unconditionally overwrites B's `extended_pubkey` in A's local `extended_pubkeys` table — with no check that the wallet was already fully approved.
4. Subsequent `deriveAddress()` calls on A now compute a different shared address than what B (and any other cosigner who didn't receive the update) still believes is correct, causing wallet address disagreement between cosigners.

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()],

							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet

								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

function deriveAddress(wallet, is_change, address_index, handleNewAddress){
	db.query("SELECT definition_template, full_approval_date FROM wallets WHERE wallet=?", [wallet], function(wallet_rows){
		if (wallet_rows.length === 0)
			throw Error("wallet not found: "+wallet+", is_change="+is_change+", index="+address_index);
		if (!wallet_rows[0].full_approval_date)
			throw Error("wallet not fully approved yet: "+wallet);
		var arrDefinitionTemplate = JSON.parse(wallet_rows[0].definition_template);
		db.query(
			"SELECT device_address, extended_pubkey FROM extended_pubkeys WHERE wallet=?", 
			[wallet], 
			function(rows){
				if (rows.length === 0)
					throw Error("no extended pubkeys in wallet "+wallet);
				var path = "m/"+is_change+"/"+address_index;
				var params = {};
				rows.forEach(function(row){
					if (!row.extended_pubkey)
						throw Error("no extended_pubkey for wallet "+wallet);
					params['pubkey@'+row.device_address] = derivePubkey(row.extended_pubkey, path);
					console.log('pubkey for wallet '+wallet+' path '+path+' device '+row.device_address+' xpub '+row.extended_pubkey+': '+params['pubkey@'+row.device_address]);
				});
				var arrDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);
				var address = objectHash.getChash160(arrDefinition);
				handleNewAddress(address, arrDefinition);
			}
		);
	});
}
