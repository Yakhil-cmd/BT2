### Title
Missing cosigner permission check in `wallet.js`'s "sign" device-message handler allows an unauthorized paired device to trigger local signing of arbitrary units/messages - ([File: wallet.js])

### Summary
The Jenkins Docker Plugin advisory (CVE-2019-10341) describes a missing permission check that let a low-privilege, already-authenticated principal invoke a privileged action (`doTestConnection`) using attacker-supplied parameters (URL + credentials ID), exfiltrating secrets that principal should not have been able to access. The structurally equivalent flaw in `ocore` is the disabled cosigner-membership check in the `"sign"` device-message handler in `wallet.js`, reachable from any paired device (a correspondent), which is exactly one of the actor classes explicitly in scope for this analysis.

### Finding Description
In `handleMessageFromHub`'s `"sign"` case, when `findAddress` resolves the requested address to a **local** address, the code is supposed to verify that the device sending the sign request (`from_address`) is actually a registered cosigner of that address/wallet before proceeding. That check is present and enforced in the `ifRemote` branch (`if (!other_device_addresses.includes(from_address)) return callbacks.ifError("you are not listed as a cosigner...")`), but the equivalent check for the `ifLocal` branch has been explicitly commented out: [1](#0-0)

Because of this asymmetry, **any correspondent device** that is merely paired with the victim's device (an untrusted, low-privilege relationship analogous to a Jenkins "Overall/Read" user) can send a `"sign"` message referencing:
- any local address the victim device controls (own wallet address, shared address, or an address in another wallet the device is party to), and
- an arbitrary `signing_path`, and
- an arbitrary `unsigned_unit` payload — either a full unit with `messages` (payment) or a `signed_message` (line 340–349, where no unit validation via `network.handleOnlineJoint` is even performed) —

without the software ever verifying that this sender is one of the legitimate cosigners of the referenced address (`wallet_signing_paths`/`extended_pubkeys` membership check as done elsewhere, e.g. `wallet_defined_by_keys.js`).

Successfully passing `findAddress`'s structural checks (the address must merely exist locally, in `my_addresses`, `shared_addresses`, or `peer_addresses`) is sufficient to reach `callbacks.ifOk()` and cause the victim device to emit a `"signing_request"` event for the crafted unit/message, i.e., to enter the signing flow using the local wallet's own key material for that address/path.

### Impact Explanation
This is a missing authorization check (CWE-862) matching the reported bug class: an entity with only a low level of trust (a paired correspondent, not a verified wallet cosigner) can invoke a privileged wallet operation — requesting the device to sign with its own keys — for any address/wallet it happens to know about, bypassing the intended cosigner-membership boundary that the (removed) SQL check was meant to enforce. Depending on how the host application wires the `"signing_request"` event (e.g., automated/headless wallets, bots, or exchange integrations that auto-approve requests from known correspondents without re-verifying cosigner membership), this can result in the device signing and broadcasting transactions that move funds from a shared/multisig address to attacker-chosen outputs, or producing valid signed messages/authentications on the victim's behalf — i.e., unauthorized spending or unauthorized authentication using the victim's private keys, exactly the class of impact the report criteria call for.

Even where a UI confirmation step exists, the missing check removes a fundamental server-side trust boundary: the wallet cannot itself distinguish "signing request from a legitimate cosigner of this shared address" from "signing request from an arbitrary paired device," pushing all security onto human judgment and defeating defense-in-depth for a multisig/shared-address security model.

### Likelihood Explanation
Reachability is high: pairing with a device is a routine, low-friction operation (via URI/QR pairing, `handlePairingMessage` in `device.js`), and any correspondent can subsequently send this `"sign"` justsaying message. No wallet-specific membership or capability is required to send it — only the address needs to be one the victim device recognizes as local, which is knowable/guessable in shared-address and multi-device wallet setups where the address is shared with counterparties for other purposes (e.g., contracts, shared wallets, arbiter/prosaic contracts). The comment left in the code ("the commented check would make multilateral signing impossible") confirms this is a known, intentional removal rather than an oversight not previously considered, increasing confidence that the missing check is exploitable as described.

### Recommendation
Restore an equivalent authorization check in the `ifLocal` branch of the `"sign"` handler, verifying that `from_address` is a legitimate cosigner/member entitled to request signing for `body.address` at `body.signing_path` (e.g., checking `wallet_signing_paths`/`extended_pubkeys` for wallet-defined-by-keys addresses, and `shared_address_signing_paths` for shared addresses), mirroring the check already implemented in the `ifRemote` branch. If multilateral signing genuinely requires accepting requests from non-cosigner devices for "message-only" signing, that case should be explicitly and narrowly scoped (e.g., only for `signed_message`, never for payment-unit `messages` that can move funds), and the UI/eventBus consumer should be given enough information to reliably indicate to the user whether the requester is a known cosigner of that specific address.

### Proof of Concept
1. Attacker device pairs with the victim's wallet device (standard pairing flow) so `correspondent_devices` contains the attacker as a known correspondent — no privileged relationship is required.
2. Attacker sends a device justsaying message with `subject: "sign"` and body:
```
{
  address: "<victim's local shared/multisig address, known to attacker e.g. via a prior contract>",
  signing_path: "r.1",
  unsigned_unit: {
    version: <current version>,
    authors: [{ address: "<that address>", authentifiers: { "r.1": "<placeholder>" } }],
    messages: [ /* payment message moving victim funds to attacker-controlled output */ ]
  }
}
```
3. On the victim device, `handleMessageFromHub` routes to case `"sign"`, `findAddress` resolves `ifLocal` (the address is locally known), and — because the cosigner-membership check is commented out — `callbacks.ifOk()` is returned and a `"signing_request"` event is emitted for the attacker-crafted unit, entering the local signing pipeline using the victim's key for that address/path, despite the attacker never having been a legitimate cosigner of it.
