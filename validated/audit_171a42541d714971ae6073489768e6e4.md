### Title
Tokens transferred directly to the Controller are never credited and are permanently stuck - (File: contracts/controller/src/payments.rs)

### Summary
Mirroring the Notional finding, XOXNO Lending's controller and pool never credit tokens by reading absolute balances — every crediting path measures the *delta* inside its own call (`snapshot` → action → `balance_delta_since`). Any token pushed to the controller or pool outside a measured window is invisible to all accounting, and neither contract exposes any sweep, rescue, or skim entrypoint, so those tokens are permanently locked.

### Finding Description
All custody accounting is delta-scoped:

- `transfer_amount_measured` credits only `post - pre` of a single transfer (`common/src/token.rs:16-31`).
- `balance_delta_since` / `snapshot_balances` in `contracts/controller/src/payments.rs:10-52` measure receipts only within one operation; `refund_controller_balance_delta` refunds only the delta *since that operation's snapshot*.
- Strategy legs (`contracts/controller/src/strategies/legs.rs:84-109`, `strategies/flash_position.rs:258-295`, `strategies/swap.rs:29-55`) snapshot controller balances at call start, so a pre-existing balance is never touched.
- The pool's cash book (`get_reserves`) is internal ledger state, fully decoupled from the token balance; every outflow (`withdraw`, `borrow`, `flash_loan` payout, `claim_revenue` paying `min(cash, revenue)` at `contracts/pool/src/lib.rs:250`, `recapitalize` capping at `backing_shortfall`) is driven by the book, not the balance.
- `flash_position` explicitly leaves any non-declared callback receipt "uncredited" (INV-STRAT-04; `skills/xoxno-lending-contracts/flash-loans.md:134`).
- Neither `contracts/controller/src/lib.rs` nor `contracts/pool/src/lib.rs` exposes any sweep/recover/skim function; all pool mutators are `#[only_owner]` legs driven by the controller.

An unprivileged address can reach this via:
1. `token.transfer(user, controller, amount)` — direct transfer; the tokens sit forever (the test at `tests/test-harness/tests/controller/outbound_transfer_measurement.rs:124-151` confirms controller dust is intentionally untouched by `claim_revenue`).
2. `token.transfer(user, pool, amount)` — inflates pool balance above cash + revenue + debt-backing; no path distributes the surplus.
3. `flash_position(..., receiver, data, collaterals, refund_assets)` — any token the receiver returns that is not declared in `collaterals` or `refund_assets` remains on the controller, neither deposited nor refunded.

### Impact Explanation
Permanent freezing of funds. Tokens sent directly to the pool or controller, or returned undeclared in a `flash_position` callback, are locked forever with no recovery path — the delta-measured settlement that protects the protocol equally guarantees stray balances can never be claimed. Unlike vaults with a `sweep`/`skim`, there is no owner or governance escape hatch here either, so even accidental transfers are unrecoverable.

### Likelihood Explanation
Medium. The pool/controller addresses are publicly known (`get_pool_address`), SAC token transfers are unrestricted, and `flash_position` receivers legitimately send tokens to the controller via plain `token.transfer` — a receiver returning an undeclared or over-sent asset strands it. Direct "fat-finger" transfers to contract addresses are a recurring real-world occurrence.

### Recommendation
Add a recovery path: e.g., an owner/permissionless `rescue(asset, to)` on the controller that pays out `balance(asset)` for assets it does not custody, and on the pool pays out `balance - (cash obligations + revenue claimable)`; alternatively, have `flash_position` treat every positive undeclared delta as refundable to the caller, and document that direct transfers are unrecoverable. At minimum, emit an off-chain warning that stray balances cannot be recovered.

### Proof of Concept
```rust
// Unprivileged user sends tokens straight to the controller.
let tok = token::Client::new(&env, &usdc);
tok.transfer(&alice, &controller_addr, &1_000_000);

// Every entrypoint ignores it: no crediting op snapshots before the
// transfer, so balance_delta_since only ever sees deltas inside its own call.
// `claim_revenue` pays min(cash_book, revenue) from the pool and forwards only
// the measured receipt — controller dust is explicitly left intact
// (test: claim_revenue_forwards_the_measured_amount_and_leaves_controller_dust_intact).
assert_eq!(tok.balance(&controller_addr), 1_000_000); // stuck forever

// Pool variant: donation inflates balance beyond the cash book; no sweep exists.
tok.transfer(&alice, &pool_addr, &1_000_000); // permanently locked
// recapitalize credits only up to backing_shortfall and refunds the rest to payer.
```

Caveat: the `flash_position` uncredited-receipt behavior is documented in INV-STRAT-04 and the SDK docs, which may be judged a deliberate design choice; the absence of any sweep on the pool/controller for *external* direct transfers is the part that has no documented justification.
