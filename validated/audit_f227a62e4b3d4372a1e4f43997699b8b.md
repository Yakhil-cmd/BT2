### Title
Cross-repository Status forgery via unscoped SHA lookup triggers unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commit to update by a global, repository-unscoped `Commit.where(sha: params.sha)` query, instead of scoping to the repository named in the webhook payload the way the base `Handler#stacks` helper does. Because a Commit's `stack_id` is fixed at creation (from the legitimate sync of the *owning* repository), a `status` webhook that is authentically signed for the attacker's own repository can write a `Status` row against a completely different (victim) stack whenever the two repositories share a commit SHA (e.g., via fork ancestry), and that write triggers `ContinuousDeliveryJob` against the victim's stack.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce:
`commit.stack.repository.full_name` (the repository that owns the `Commit` row matched by `params.sha`) **must equal** `payload.dig('repository', 'full_name')` (the repository the attacker's verified webhook claims to be from). The code never checks this.

Path:
- `WebhooksController#create` verifies the signature only against `repository_owner` derived from the attacker's *own* payload (`app/controllers/shipit/webhooks_controller.rb:24-30, 59-62`), which proves the request genuinely originated from GitHub for the attacker's repo/org — it says nothing about which `Commit`/`Stack` the handler is allowed to mutate.
- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This is a global lookup with no repository filter, unlike the pattern established in the base `Handler` class, which correctly scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 
- `create_status_from_github!` writes the status using the **commit's own** `stack_id` (set when the commit was originally synced from its real owning repository), via `statuses.replicate_from_github!(stack_id, github_status)`: [3](#0-2) 
- `Status` fires `after_commit :schedule_continuous_delivery, :broadcast_update, on: :create`, calling `commit.schedule_continuous_delivery`: [4](#0-3) 
- `ContinuousDeliveryJob#perform(stack)` — where `stack` is the commit's real (victim) stack, not anything derived from the attacker's payload — proceeds if `stack.continuous_deployment?`, no restrictive `continuous_delivery_schedule`, and not `occupied?`, then calls `stack.trigger_continuous_delivery`: [5](#0-4) 

Attacker's exact request: a genuine GitHub `status` webhook event (`X-Github-Event: status`) emitted by GitHub for the attacker's own repository/fork, with a `sha` value equal to an ancestor commit shared between the attacker's fork and the victim's repository (guaranteed to exist and be identical because SHAs are content-addressed and forks retain unmodified pre-divergence commit hashes), and `state: "success"`. This payload is legitimately signed by GitHub for the attacker's own org, so `verify_signature` passes.

Existing guards fail because: `verify_signature` only authenticates *sender identity for their own repo*, not *target authorization for the resource being mutated*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of `sha`/`state`, not repository ownership; and there is no `stacks`/repository-scoped filter applied in `StatusHandler#process`, in contrast to other handlers that use the base class's `stacks` helper.

### Impact Explanation
The attacker, using only a webhook triggered from a repository they own, can write a `Status` record against a victim's `Stack` and cause `ContinuousDeliveryJob` to run `stack.trigger_continuous_delivery` for that victim stack — ultimately building and enqueuing a `Deploy`/`Task` that executes shell commands via `Command`/`PTY.spawn` with the deploy environment (including `GITHUB_TOKEN`) for a repository the attacker never had write access to. This is a payload for one repository mutating another's stack/commit and resulting in an unauthorized deploy — Critical severity. It is repeatable against any victim stack that (a) has `continuous_deployment?` enabled, (b) is not occupied, (c) has no restrictive schedule, and (d) shares at least one commit SHA with a repository the attacker controls (trivially true for any fork relationship, including public forks of open-source victim repos).

### Likelihood Explanation
Preconditions are realistic and cheap for the attacker: own or control any repository with a shared git history with the victim (e.g., a public fork), have that repository's Shipit-integrated webhook fire a `status` event (attacker can set commit statuses on their own repo/fork via the GitHub API on their own account, no victim credentials needed), and target a victim stack with continuous deployment enabled and idle. No Shipit secrets, sessions, or GitHub App keys are required — only the attacker's own legitimate GitHub webhook delivery. This is fully repeatable and requires no live GitHub interaction to prove (the sha collision and resulting `Commit` record can be constructed directly in a test fixture).

### Recommendation
Scope `StatusHandler#process` (and any other handler doing an unscoped model lookup by SHA) to the repository named in the payload, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that a `Status` can only be created for commits belonging to stacks of the repository the verified webhook actually originated from.

### Proof of Concept
minitest plan (no live GitHub, `perform_enqueued_jobs`):
1. Fixtures: create `victim_repo`/`victim_stack` with `continuous_deployment: true`, not occupied, no schedule; create `attacker_repo` (a different `Repository`, different `full_name`) with no association to `victim_stack`.
2. Create a `Commit` with a fixed `sha` (e.g. `"deadbeef" * 5`) belonging to `victim_stack` (simulating a shared ancestor commit already synced from the victim's real repo).
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name` is `attacker_repo`'s full name (asserting `payload.dig('repository','full_name') != victim_repo.full_name`), `sha` equal to the shared SHA, `state: 'success'`, stubbing `verify_signature` to return true (simulating a genuinely-signed attacker webhook).
4. Assertions (both sides of the equality, before/after):
   - Before: `assert_not_equal attacker_repo.full_name, victim_stack.repository.full_name` (binding mismatch stated).
   - `assert_difference('Shipit::Status.count', 1) { post :create, ... }` and `assert_equal victim_stack.id, Shipit::Status.last.stack_id` — proving the write landed on the victim stack despite the attacker-scoped payload.
   - `perform_enqueued_jobs` around the POST and `assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack])`, then assert a `Shipit::Deploy` was created for `victim_stack` and `Shipit::PerformTaskJob` was enqueued for it — demonstrating the full unauthorized deploy chain triggered solely by the attacker's own webhook.
