### Title
Webhook signature verifies only the attacker's own organization while handlers act on a different organization's repository from the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret is used to authenticate a webhook based solely on `repository.owner.login` (or `organization.login`) taken from the attacker-controlled JSON body, but the webhook handlers that subsequently act on the payload resolve the target `Stack`/`Repository` from a completely different field in the same body — `repository.full_name`. Nothing binds these two fields together, so a party who legitimately controls one organization hosted on a multi-tenant Shipit instance can forge a payload whose `repository.owner.login` matches their own org (so it passes signature verification with a secret they know) while `repository.full_name` points at a victim organization's repository/stack also hosted on the same instance.

### Finding Description
`Shipit::WebhooksController#verify_signature` fetches the GitHub App config for `repository_owner`, computed as: [1](#0-0) 
and verifies the `X-Hub-Signature` header against that organization's `webhook_secret`: [2](#0-1) 

Once verified, the raw parsed JSON `params` is handed unmodified to every registered handler for the event: [3](#0-2) 

Handlers resolve which `Stack`/`Repository` to operate on using a *different* field of the same payload — `repository.full_name` — with no re-check that it belongs to the organization whose secret validated the signature: [4](#0-3) 

For example, `PushHandler#process` uses `stacks` (scoped via `repository_name`/`full_name`) to trigger `stack.sync_github`: [5](#0-4) 

Because `Shipit.github(organization:)` supports distinct per-organization configuration (raising `GithubOrganizationUnknown` for unconfigured orgs), this engine is designed to host multiple organizations with independent GitHub App credentials/`webhook_secret`s on one instance: [6](#0-5) 

The trust binding that should hold is: *organization whose secret authenticated the request* == *organization whose repository is acted upon*. The code instead evaluates: `verify_signature` uses `payload['repository']['owner']['login']`, while `Handler#repository_name` uses `payload['repository']['full_name']`. An attacker who administers "orgA" (and therefore knows/controls orgA's `webhook_secret`, having configured the webhook themselves) can submit:

```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<victim-repo real sha>"
}
```

signed with `orgA`'s secret. `verify_signature` passes because `repository.owner.login == "orgA"`. The `PushHandler` (or `status`/`check_suite`/`membership`/`pull_request` handlers) then look up stacks via `repository.full_name == "orgB/victim-repo"`, acting on a Stack that belongs to a different, unrelated organization the attacker never authenticated for.

### Impact Explanation
This breaks the equality `organization that authenticated == repository that is written`, letting an attacker with control of any one organization onboarded to a shared Shipit instance drive webhook-triggered actions against any other organization's stacks whose repository full name they can guess/observe (repo names are not secret). Concretely reachable handler actions include: forcing `GithubSyncJob`/status refresh on a victim stack, injecting arbitrary CI `Status` records (`state`, `target_url`, `context`, `description`) for a victim commit via the `status` handler, archiving/creating/unarchiving `ReviewStack`s via the `pull_request` handlers, and mutating `Team`/`Membership` records via the `membership` handler — all without the `webhook_secret`, GitHub App credentials, or any privileged account belonging to the victim organization. Forged CI/commit status on a required check can influence deploy/merge gating decisions made by legitimate operators of the victim stack, which aligns with the "unauthorized deploy/merge" and "authorization escalation" impact tiers.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately control one organization/app installation hosted on the same multi-tenant Shipit instance (something the engine explicitly supports via `Shipit.github(organization:)`/`GithubOrganizationUnknown`), and that they can guess or discover the `owner/name` of a target repository on the instance — no access to the victim's secret, GitHub token, or Shipit session is needed. This is a realistic configuration for any shared/hosted Shipit deployment serving several GitHub organizations.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), cross-check that `repository.full_name`'s owner segment matches the organization whose secret validated the signature (i.e., derive `repository_owner` and enforce it equals the owner portion of `repository.full_name` before dispatching to handlers), rejecting mismatched payloads with `422`.

### Proof of Concept
1. Onboard/administer "orgA" on a shared Shipit instance; note its GitHub App webhook secret `S_A` (attacker knows this because they configured it).
2. Craft a push-event JSON body where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"` (a stack belonging to a different tenant on the same instance), with `ref`/`after` pointing at a real commit on `orgB/victim-repo`.
3. Compute `X-Hub-Signature: sha1=<hmac(S_A, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` succeeds because it only checks `repository.owner.login == "orgA"` against `S_A`.
5. `PushHandler` resolves stacks via `repository.full_name == "orgB/victim-repo"` (app/models/shipit/webhooks/handlers/handler.rb:36-38) and triggers `stack.sync_github` for the victim's stack — an action the attacker was never authorized to perform on `orgB`.
