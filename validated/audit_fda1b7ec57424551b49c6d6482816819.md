Based on the investigation, I found the closest analog in ocore: the `spender_attested` asset attestor-list mechanism, which resolves to the exact same root-cause pattern as the vectorx bug — a mutable, definer-controlled "trusted validator" reference where only the *single latest* version is authoritative, silently invalidating everything anchored to previous versions.

### Title
Attestor list update for `spender_attested` assets invalidates historical attestations, freezing legitimate holders' funds - (File: `storage.js`)

### Summary
`readAsset()`/`filterAttestedAddresses()` in `storage.js` only ever recognize the **single latest** `asset_attestors` list published for an asset. The `attestations` table itself is checked against `attestor_address IN (?)` using `objAsset.arrAttestorAddresses`, which is always the most recent list, exactly as vectorx's `receiveMessage`/`receiveETH` only accepted proofs from the currently-configured vectorx contract. Once the asset definer publishes a new `asset_attestors` list (an ordinary, permissionless-to-the-definer, unprivileged action reachable by posting a normal unit), attestations issued by attestors who are no longer on the new list stop counting, even though those attestations were valid and relied upon when the coins were acquired.

### Finding Description
For a `spender_attested` asset, `storage.readAsset()` resolves `objAsset.arrAttestorAddresses` by finding the newest `asset_attestors` unit only: [1](#0-0) 

`filterAttestedAddresses()` then checks the `attestations` table only against this single, current attestor list: [2](#0-1) 

This `arrAttestedAddresses`/`arrAttestorAddresses` result is used to gate every spend of the asset — both the input owner check and the output recipient check — in `validatePaymentInputsAndOutputs`: [3](#0-2) [4](#0-3) [5](#0-4) 

The attestor list itself can be freely updated by the asset definer at any time via the `asset_attestors` message, with no restriction requiring old attestors to remain valid or requiring re-attestation of already-attested holders: [6](#0-5) 

Once a definer posts a new `asset_attestors` list that drops a previously-trusted attestor, any address whose only attestation came from the now-removed attestor becomes permanently unable to pass `spender_attested` checks — it can neither be an input owner, an output recipient, nor an issuer for that asset — for coins it legitimately holds. This mirrors exactly the vectorx bug class: a mutable single "current" trusted validator reference that silently discards everything anchored to earlier versions of itself, with no mechanism to re-validate or "carry forward" historical trust.

### Impact Explanation
Coin holders whose attestation predates an attestor-list change can have their `spender_attested` asset balances permanently frozen — they cannot spend, transfer, or receive further payments of that asset, because `validatePaymentInputsAndOutputs` will reject both the spending input ("owner address is not attested") and any output to them ("some output addresses are not attested"). This is an AA/asset-holder fund freezing condition triggered entirely by the definer posting an ordinary, otherwise-legitimate `asset_attestors` unit — no malicious node, hub, or p2p behavior is required, and it is directly reachable by any asset holder/definer through normal unit posting.

### Likelihood Explanation
Attestor-list rotation is an intended, documented feature of `spender_attested` assets (attestors are expected to be updated over time, per the schema comment "must subsequently publish and update the list of trusted attestors"). Any definer who rotates attestors for routine reasons (attestor retirement, key compromise, policy change) will, by design of the current lookup logic, immediately and silently strand every holder attested only by the removed attestor. This requires no adversarial intent — it is a natural consequence of routine attestor management, making the freezing scenario highly likely to occur in practice.

### Recommendation
Instead of only recognizing the single latest attestor list, `readAsset()`/`filterAttestedAddresses()` should treat an address as attested if it holds a valid attestation from *any* attestor that was trusted at the time the attestation was issued (i.e., historical membership should remain valid unless explicitly revoked), or the protocol should require attestor-list changes to preserve backward compatibility for already-attested addresses (e.g., an explicit re-attestation grace period, or falling back through the full history of attestor lists rather than only the newest one).

### Proof of Concept
1. Definer creates a `spender_attested` asset with `attestors: [A1]` (`validateAssetDefinition`, `checkAttestorList`).
2. Attestor `A1` posts an `attestation` for `holder` (address `H`), recorded in the `attestations` table.
3. `H` receives/holds units of the asset; `loadAssetWithListOfAttestedAuthors` confirms `H` is attested via `filterAttestedAddresses`, since `A1` is in `objAsset.arrAttestorAddresses`.
4. Definer posts an `asset_attestors` update: `attestors: [A2]` (dropping `A1`), which is permitted by `validateAttestorListUpdate` with no check on existing attestees.
5. `storage.readAsset` now resolves `arrAttestorAddresses = [A2]` only (`storage.js:1924-1930`).
6. `H` attempts to spend the asset. `filterAttestedAddresses` queries `attestations` with `attestor_address IN (A2)` — `H`'s attestation from `A1` no longer matches, so `H` is excluded from `arrAttestedAddresses`.
7. `validatePaymentInputsAndOutputs` rejects the spend with "owner address is not attested", permanently freezing `H`'s balance unless `A2` (or whichever attestor is currently active) re-attests `H`, which `H` may have no ability to obtain.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
