### Title
Unbounded unit size for AA-generated response units once `pemCurvesFixMci` is reached — no `MAX_UNIT_LENGTH` cap enforced - ([File: validation.js])

### Summary
The Squid CVE-2023-5824 bug class is: a size limit that is supposed to bound a data structure is applied inconsistently, so an oversized object can still be produced/accepted and later processed (parsed/hashed/stored) by every worker, causing stalls/crashes. In `ocore`, the `MAX_UNIT_LENGTH` cap that is supposed to bound the size of every unit (`headers_commission + payload_commission <= constants.MAX_UNIT_LENGTH`) is explicitly skipped for AA-generated units, and only conditionally re-enforced for AAs before the `pemCurvesFixMci` upgrade point. After that mci, no unit-size ceiling exists at all for AA response units — the only mitigation is an economic "oversize fee," not a hard limit.

### Finding Description
In `validate()`, the general unit-size check excludes AA units unconditionally: [1](#0-0) 

The only other place a size cap is applied to AA units is in `validateParents()`, and it is explicitly scoped to before the `pemCurvesFixMci` upgrade: [2](#0-1) 

After `last_ball_mci >= constants.pemCurvesFixMci`, this is the entire treatment of AA unit size — it computes an `oversize_fee` (a smoothly increasing but *unbounded* economic cost) instead of rejecting the unit outright: [3](#0-2) [4](#0-3) 

The AA composer itself relies on this same unbounded-fee logic instead of a hard cap when building the response unit and deciding how many outputs/messages/state to include (`sendUnit`/`completePaymentPayload` in `aa_composer.js`): [5](#0-4) [6](#0-5) 

So structurally, a "unit too large" rejection for AA units exists only pre-`pemCurvesFixMci`; post-upgrade the exponential `oversize_fee` (`Math.ceil(size * (exp(size/threshold_size - 1) - 1))`) is the sole gate. Since the fee is paid from the AA's own balance (and grows without an upper bound in the size variable), the *validation logic* has no numeric ceiling on `headers_commission + payload_commission` for AA units anymore — this mirrors the Squid flaw where a limit meant to be enforced universally ("before caching") ends up not applying in an important code path ("after retrieval from cache"), letting an oversized object slip through into processing paths that assume bounded size.

Per-field limits do exist (`MAX_AA_STRING_LENGTH`=4096, `MAX_STATE_VAR_VALUE_LENGTH`=1024, `MAX_MESSAGES_PER_UNIT`=128, `MAX_DATA_FEEDS_PER_MESSAGE`=1024, `MAX_OPS`=2000, `isTooDeeplyNestedOrHasTooManyNodes` nodesLimit=10000) as seen in `constants.js`: [7](#0-6) 
and in `string_utils.js`: [8](#0-7) 
but none of these per-field/per-message limits combine into an enforced whole-unit byte-size cap (`MAX_UNIT_LENGTH`, default 5 MB) for AA response units post-`pemCurvesFixMci`; an AA can compose many large messages/outputs (up to `MAX_MESSAGES_PER_UNIT` messages, each with up to `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`/`MAX_DATA_FEEDS_PER_MESSAGE` items, each item near the individual string/value caps) whose aggregate size can exceed `MAX_UNIT_LENGTH` many times over, as long as the triggering AA has enough balance to pay the resulting `oversize_fee`.

I was unable to determine from the available index snippets the exact numeric value assigned to `constants.pemCurvesFixMci` (whether it has already activated on mainnet); the grep only located references, not the defining line content, so I cannot confirm with certainty whether this bypass is already live on mainnet or scheduled for a future mci. This should be verified directly in `constants.js` in a full checkout.

### Impact Explanation
Every full node must download, hash, and store units it receives, including AA-generated response units. If `MAX_UNIT_LENGTH` is not enforced for these units past `pemCurvesFixMci`, a well-funded AA (or an attacker who funds a malicious AA with a trigger they control) can cause the AA to emit response units of essentially unbounded size (limited only by the composing node's own message/array/complexity sub-limits, which can still combine into units many times larger than `MAX_UNIT_LENGTH`). Because oversized units are still valid per consensus rules, every honest node must accept, hash, and store them — this is a network-wide processing/storage cost imposed by a single trigger poster, potentially causing memory/CPU stalls in the unit processing pipeline (validation, hashing, DB writes) analogous to Squid's crash/stall from oversized cached headers. This can degrade the network's ability to process new units in a timely manner (a DoS on unit confirmation throughput), which fits the "network unable to confirm new units" impact category.

### Likelihood Explanation
Exploitation requires an attacker to control (or fund) an AA whose formula, when triggered, produces enough messages/outputs/state changes to build a large response unit, and to ensure the AA holds sufficient balance to cover the (exponentially growing) `oversize_fee`. This is achievable by a single trigger sender deploying their own AA with permissive logic (fully in scope: "AA definitions and triggers" / "oscript evaluation"), and does not require a malicious peer, hub, or protocol-level attack — only crafting an AA and a trigger with the funds to pay fees. The bottleneck is the cost of the oversize fee itself, which does deter arbitrarily large units economically, but does not structurally cap them, so a sufficiently funded attacker (or one exploiting bounced/self-funding loops) can still produce units far larger than the network-wide `MAX_UNIT_LENGTH` intended for ordinary units.

### Recommendation
- Re-apply an absolute `MAX_UNIT_LENGTH` (or a distinct, explicit AA-specific hard ceiling) to AA-generated units unconditionally, regardless of `pemCurvesFixMci`, in both `validation.js` (`validate()` and `validateParents()`) and in `aa_composer.js` when composing the response unit, instead of relying solely on the exponential oversize fee as a deterrent.
- If the intent of `pemCurvesFixMci` was to allow AAs to build larger units in exchange for a proportionally larger fee, cap the maximum size multiplier so the fee-based mechanism cannot be used to bypass an effectively unbounded unit size — e.g., enforce `size <= N * MAX_UNIT_LENGTH` for some fixed small `N`, in addition to charging `getOversizeFee`.
- Add regression tests asserting that AA response units generated at/after `pemCurvesFixMci` are rejected once they exceed a defined absolute size ceiling, verifying parity with the non-AA `MAX_UNIT_LENGTH` check at `validation.js:267`.

### Proof of Concept
1. Deploy an AA whose formula (post `pemCurvesFixMci` mci) generates, on trigger, close to the maximum allowed per-field constructs — e.g. `MAX_MESSAGES_PER_UNIT` (128) payment/data_feed messages, each populated with up to `MAX_DATA_FEEDS_PER_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE` entries near their individual size limits (`MAX_DATA_FEED_VALUE_LENGTH`=64, `MAX_AA_STRING_LENGTH`=4096 for computed strings), such that the combined `headers_commission + payload_commission` well exceeds `constants.MAX_UNIT_LENGTH` (5e6 by default).
2. Fund the AA sufficiently (via prior triggers or `bounce_fees`) to cover the resulting `storage.getOversizeFee(objUnit, last_ball_mci, true)` computed in `aa_composer.js:1400`.
3. Send a trigger to the AA. `handleTrigger`/`sendUnit` composes the oversized response unit, computes `oversize_fee`, and calls `validateAndSaveUnit`.
4. In `validation.js`, the general size check at line 267 is skipped because `bAA` is true, and the AA-specific check at line 744 is skipped because `last_ball_mci >= constants.pemCurvesFixMci`. The unit passes validation as long as the `oversize_fee` matches `storage.getOversizeFee()`'s output, and is then broadcast and must be processed/stored by every node on the network, imposing outsized processing costs disproportionate to the `MAX_UNIT_LENGTH` design intent.

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}

function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
