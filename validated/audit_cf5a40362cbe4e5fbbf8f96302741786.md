### Title
Webhook signature verification is scoped by `repository.owner.login`/`organization.login` while every event handler acts on the independent, unverified `repository.full_name` field, allowing cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. But every webhook handler (`Handler#stacks`, and the `pull_request` handlers) resolves the target `Repository`/`Stack` using a completely different, independently-attacker-controlled field: `payload.dig('repository', 'full_name')`. Nothing ties `repository.full_name` back to `repository.owner.login`/`organization.login`, so the field that is authenticated (which org's secret signed the payload) is not the field that is acted on (which repository gets mutated).

### Finding Description
`WebhooksController#verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization: ...)` returns a per-organization `GithubApp` config (`lib/shipit/github_app.rb:44-57`) with its own `webhook_secret`. `verify_webhook_signature` (lines 76-83) then HMACs the *entire raw request body* with that org's secret and compares it to the `X-Hub-Signature` header.

Shipit explicitly supports multiple GitHub organizations, each with its own App and `webhook_secret` (see `config/secrets.development.shopify.yml` and `docs/setup.md`). Nothing in the engine restricts webhook delivery to only the GitHub org that configured it — the controller trusts whatever secret matches the org named in the payload.

Once the signature passes, `WebhooksController#create` dispatches the full, attacker-supplied JSON to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). Every handler resolves its target repository via `Handler#repository_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
```
(`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and the `pull_request` handlers do the same with `params.repository.full_name` (e.g. `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`).

`repository.full_name` and `repository.owner.login`/`organization.login` are two independent JSON fields inside the same signed payload — GitHub itself keeps them consistent, but Shipit does not enforce that consistency; it merely trusts that whoever crafted the JSON kept them in sync. An attacker who legitimately controls (or has been granted) their own GitHub App integration/organization in this Shipit instance — e.g. "attacker-org", with a valid `webhook_secret` they know — can craft an arbitrary JSON body where:
- `repository.owner.login` = `"attacker-org"` (or `organization.login` = `"attacker-org"`) — used only to pick which secret to check the signature against,
- `repository.full_name` = `"victim-org/some-repo"` — used by every handler to look up the actual `Repository`/`Stack` to mutate.

They sign the whole body with `attacker-org`'s own known `webhook_secret`. `verify_signature` computes `Shipit.github(organization: 'attacker-org')` and validates successfully, because the HMAC matches for the secret actually used to sign it. The request is accepted and forwarded to handlers operating on `victim-org/some-repo`.

This breaks the binding: **organization authenticated by the signature check == repository actually written to by the handler**. The equality that should hold is `repository_owner used for signature verification == owner(repository.full_name) acted on by handlers`, but no such check exists anywhere in `WebhooksController` or `Handler`.

### Impact Explanation
Depending on the event type dispatched, this allows an attacker who onboards (or compromises) any single GitHub organization configured in this Shipit instance to forge webhook events against stacks belonging to *any other* organization/repository also configured in the same Shipit instance:
- `push` (`PushHandler`) triggers `stack.sync_github(expected_head_sha:)` on victim stacks, forcing state sync using an attacker-chosen `after` SHA/ref for a repository the attacker does not own.
- `status` (`StatusHandler`) writes fabricated CI `Commit` statuses (`state`, `context`, `target_url`) onto victim commits (`Commit#create_status_from_github!`), which can be used to force a required status to "success" and unblock deploys or merges that depend on required checks.
- `check_suite` triggers `schedule_refresh_check_runs!` on victim stack commits.
- `pull_request` handlers (`opened`, `closed`, `labeled`, etc.) mutate victim `ReviewStack`s (archive/create/label) based on attacker-supplied pull request payload for `victim-org/some-repo`.

This is a cross-organization/cross-repository write primitive achieved purely by forging a JSON payload and signing it with a secret the attacker legitimately possesses for their own org — no access to the victim repository, victim webhook secret, or any Shipit session/API token is required. This matches the "cross-repository writes" and, via forged status checks, "unauthorized deploy/merge" impact category.

### Likelihood Explanation
Likelihood is High in any Shipit deployment that hosts more than one GitHub organization behind a single Shipit instance (a configuration explicitly documented and supported — see the multi-org example in `config/secrets.development.shopify.yml` and `docs/setup.md`'s per-org `github:` hash). Any org owner/admin with a legitimate GitHub App + webhook secret for their own org (an "unprivileged attacker" relative to other orgs on the same Shipit instance) can exploit this with a single crafted HTTP POST to `/webhooks`; no other credentials, sessions, or bypass techniques are needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to select/verify the webhook secret matches the owner of `repository.full_name` that handlers will act on. Concretely:
- After computing `repository_owner`, also derive the owner portion of `payload.dig('repository', 'full_name')` and reject the request (422) if it doesn't case-insensitively match `repository_owner`.
- Alternatively, pass the verified `repository_owner`/organization into each `Handler` and have `Handler#stacks`/`#repository` scope lookups to `Repository.where(owner: verified_owner)` rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Configure Shipit with two orgs, each with distinct `webhook_secret`s, per the documented multi-org config (`config/secrets.development.shopify.yml`):
   - `attacker-org` → secret `S_A` (known to the attacker, e.g. because they administer their own GitHub App installation on this Shipit instance).
   - `victim-org` → secret `S_V` (unknown to the attacker), owning stack `victim-org/some-repo`.
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "victim-org/some-repo", "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(S_A, body)>` and send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<...>
```
4. `WebhooksController#verify_signature` computes `repository_owner` = `"attacker-org"` (from `repository.owner.login`), fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies against `S_A` — passing, since the attacker signed with their own known secret.
5. `PushHandler#process` resolves `repository_name` from `payload.dig('repository','full_name')` = `"victim-org/some-repo"`, finds the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, mutating state on a repository the attacker never authenticated for.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
