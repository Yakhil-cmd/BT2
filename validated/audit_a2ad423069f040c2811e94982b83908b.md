### Title
Asset definer can permanently freeze already-received `spender_attested` asset funds by updating the attestor list - (File: `validation.js`)

### Summary
`ValidatorService`'s bug class ("disabling a validator does not release the funds already delegated to it, locking them for the delegation period") maps onto ocore's `spender_attested` asset mechanism. An asset definer (an unprivileged, ordinary posting party from ocore's perspective — anyone can define a `spender_attested` asset) can change the trusted attestor list for that asset at any time via an `asset_attestors` message. Because the "is this address attested" check is re-evaluated *at spend time* against the *current* attestor list rather than the attestor list that was valid when the funds were received, removing/replacing an attestor retroactively strips previously-attested holders of their spend eligibility, permanently freezing whatever asset balance they already hold, with no way to recover it.

### Finding Description
When an asset is created with `spender_attested: true`, every payment (issue or transfer) requires that:
- the owner address of each input be currently attested by one of the asset's trusted attestors, and
- the output addresses be currently attested too.

This is enforced in `validation.js`'s `validatePaymentInputsAndOutputs`, e.g. on the input side: [1](#0-0) 

and on the output side: [2](#0-1) 

The set of attestors is not immutable: the asset definer can update it at any later time with an `asset_attestors` message, validated by `validateAttestorListUpdate`, which only checks that the sender is the asset's `definer_address` — no protection is given to addresses that already hold balances under the old attestor list: [3](#0-2) 

The "attested" status used at spend time is derived from `arrAttestedAddresses`, which is computed by looking up attestations issued by the *current* attestor list at `last_ball_mci` (`storage.loadAssetWithListOfAttestedAuthors` / `filterAttestedAddresses`), not by the attestor list in effect when the address received its funds. Consequently, if the definer removes an attestor (analogous to `disableValidator`) that previously attested a given holder, and no other current attestor has attested that holder, the holder's existing asset balance instantly becomes unspendable — it cannot be transferred, cannot be sent back to the definer, and (if `auto_destroy` is not achievable because the address can't even construct a valid transfer to the definer) is permanently stuck, exactly like the delegated funds still bound to a disabled validator.

This is structurally identical to the reported bug class: a privileged party's routine, otherwise-legitimate management action ("disable an entity that funds are bound to") retroactively invalidates the spend eligibility of funds that were already validly held before the change, with the protocol offering no automatic release, refund, or grace mechanism.

### Impact Explanation
Any holder of a `spender_attested` asset can have their entire balance of that asset permanently frozen the moment the asset definer edits the attestor list, even though the holder did nothing wrong and their funds were validly received under the rules in effect at the time. Because assets can be freely created by anyone (`test/samples` show attestor-gated tokens are a normal supported feature, e.g. ICO/AA-issued tokens with `spender_attested`), this is a realistic, reachable path for any unprivileged asset holder participating in such a token economy. The result is fund freezing/loss of access for arbitrary users, which fits the "AA fund loss or freezing" / "unauthorized... spending" impact classes.

### Likelihood Explanation
Likelihood is Medium: it requires the asset's definer to actually publish an `asset_attestors` update that drops or changes attestors (a normal, expected asset-management action, not an exploit of a coding flaw), but once that happens, the freezing of existing holders' balances is deterministic and unavoidable under current validation logic. No additional attacker action is needed — the affected holder cannot do anything to unfreeze the funds.

### Recommendation
Evaluate `spender_attested` eligibility for a *spend* based on the attestor list (and attestation) that was valid when the input funds were *received*, or provide a grandfathering/grace mechanism so that removing an attestor does not retroactively invalidate the spend rights of addresses that were legitimately attested when they acquired the balance. Alternatively, require the definer to also provide an explicit unlock/refund path (e.g., always allow a transfer back to `definer_address` regardless of current attestor status) so that funds are never permanently stranded when the attestor list changes.

### Proof of Concept
1. Definer creates an asset with `spender_attested: true` and attestor A in the initial attestor list (`assetAttestors`/`asset` message, validated in `validateAssetDefinition`, `validation.js:2725-2827`).
2. Attestor A attests address H (an ordinary user). H receives a payment of the asset (valid at that time because H is attested by A, per `validation.js:2504-2507`, `2630-2641`).
3. Definer later posts an `asset_attestors` update removing A from the attestor list (`validation.js:2829-2848`, only requires `objUnit.authors[0].address === objAsset.definer_address`).
4. H now attempts to spend/transfer the previously received balance. `storage.loadAssetWithListOfAttestedAuthors` recomputes `arrAttestedAddresses` using the new attestor list; H is no longer in it.
5. Any payment from H is rejected at `validation.js:2506` ("owner address is not attested"), and H's funds remain permanently locked in the asset, with no code path to recover them.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
