### Title
Unbounded access-key/gas-key iteration in `DeleteAccount` is not gas-metered, allowing underpriced/DoS-prone account deletion analogous to `VotingEscrow.MAX_DELEGATES` - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
The Sherlock report describes `VotingEscrow.MAX_DELEGATES`: a hardcoded bound intended to keep the cost of a mandatory loop (`_moveTokenDelegates`) safe, but the bound does not actually keep the real gas cost of that loop under the chain's block gas limit, so a victim's mandatory action (`withdraw`) can be permanently un-executable, locking funds. `nearcore`'s `DeleteAccountAction` handling has the same shape of bug: the guard meant to bound the cost of removing an account (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`) bounds *storage bytes*, not the *number of access keys / gas-key nonces* that must be iterated and deleted one-by-one in `remove_account`, and the gas fee charged to the caller for the action is a fixed, count-independent `delete_account_cost` fee rather than a fee that scales with the amount of trie iteration/removal work actually performed.

### Finding Description
`action_delete_account` gates itself only on the account's total storage usage: [1](#0-0) 

It never checks (or charges for) the *number* of access keys or gas-key nonces attached to the account. The actual removal work is performed by `remove_account`, which iterates the full trie prefix of access keys and, for every gas key, every nonce entry, building a `keys_to_remove` vector and removing each one individually: [2](#0-1) 

The compute cost of this iteration is only added to `result.compute_usage` *after* the fact, via `storage_removes_compute`, and is used purely for accounting/telemetry (chunk-level compute budgeting), not to gate whether the action itself is allowed to proceed or to determine the gas actually deducted from the payer: [3](#0-2) 

Meanwhile the fee model (`docs/RuntimeSpec/Fees/Fees.md`) documents that `DeleteAccount` is priced with a single fixed base fee (`delete_account_cost`) independent of how many access keys/gas keys exist on the account: [4](#0-3) 

This is structurally identical to the `MAX_DELEGATES` bug class: a hardcoded/derived cap (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`, a byte-size bound) is used as a proxy to bound the cost of an unavoidable iterative cleanup loop, but the actual cost driver is the *count* of access-key/gas-key trie entries, which is only loosely correlated with storage bytes (many small access keys/gas-key nonce entries can fit under the storage-usage cap while still requiring a large number of individual trie lookups/removals). Because the fee charged is fixed and the compute is only tallied for informational/chunk-budget purposes rather than being pre-validated against a hard per-receipt limit before the work is done, the account owner (or anyone crafting a receipt targeting the account, e.g. via a relayed `DeleteAccount` from a contract) pays a constant price for `O(n)` work, where `n` (number of access keys / gas-key nonces) can be pushed close to whatever the storage-usage cap allows.

### Impact Explanation
This falls into the "free or underpriced execution" and "storage staking / gas accounting" categories called out as acceptable impacts. An account with a byte-budget's worth of gas keys/access keys packed as many small nonce records (`AccessKey::NONCE_VALUE_LEN` entries) instead of one full-access key can force `remove_account` to perform disproportionately more trie iteration/removal operations relative to what `delete_account_cost` reimburses the network for, i.e., the payer of `DeleteAccount` is not charged proportionally to the actual work of removing many keys, meaning validators do computation nodes are not compensated for, and — depending on how large `MAX_ACCOUNT_DELETION_STORAGE_USAGE` is relative to per-key overhead — the accumulated compute added post-hoc could contribute to exceeding intended per-chunk compute headroom without having been priced/validated up front, which is a form of underpriced/unmetered execution. In the worst framing (mirroring the original report), if the number of removable entries a user can accumulate under the byte cap is large enough, this could make deletion of that account disproportionately expensive for the network relative to what was paid, a resource-accounting mismatch of the same character as the `MAX_DELEGATES` issue (bound chosen on the wrong dimension — bytes instead of entry count).

### Likelihood Explanation
Reaching this path requires only an ordinary `DeleteAccount` action submitted by an unprivileged account (the account owner or beneficiary-controlled receipt), which is fully reachable from a signed transaction — no validator or node-privilege is required. Constructing an account with many gas keys/nonces under the byte-usage cap requires paying the normal storage staking deposit for each entry, so the attack is “self-funded” but not otherwise gated; there is no explicit limit on the *count* of access keys/gas keys, only on aggregate storage bytes.

### Recommendation
Bound `DeleteAccount`'s free-cleanup work directly by the *number* of access-key and gas-key-nonce entries (and/or contract-data entries) removed, not solely by aggregate storage-usage bytes, and either (a) charge `delete_account_cost` proportionally to `remove_result.gas_key_nonce_count` / access-key count actually removed, or (b) reject deletion (as is already partially done via `DeleteAccountWithLargeState`) once the entry count exceeds a limit calibrated to the real per-entry removal/compute cost rather than to storage bytes alone.

### Proof of Concept
Not independently reproduced in this pass (read-only investigation only); the conceptual PoC mirrors the Sherlock POC: create an account, add the maximum number of access keys/gas-key nonce records that fit under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` bytes (using minimal-size gas-key nonce entries to maximize entry count per byte), then submit `DeleteAccountAction` and observe that `remove_account`'s iteration cost (visible via `result.compute_usage`, as exercised in `test_delete_account_removes_gas_keys` / `test_delete_account_burns_gas_key_balances`) scales with entry count while the actual `delete_account_cost` fee charged remains fixed, confirming the fee/work mismatch: [5](#0-4)

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
