### Title
Pool-held Aquarius LP collateral accrues venue rewards that can never be claimed — permanent freezing of unclaimed yield - (File: contracts/pool/src/lib.rs)

### Summary
XOXNO Lending accepts Aquarius LP tokens as collateral assets in pool markets. The LP position's holder is the pool contract itself, so any venue rewards (Aquarius gauge/reward distributions) accrue to the pool address. The pool exposes no entrypoint to claim, harvest, or forward those rewards, and reward claims that require the holder's authorization can never execute because the pool has no path to authorize an arbitrary external call. Yield belonging to LP-collateral suppliers is permanently frozen at the reward contract.

### Finding Description
The pool's mutator surface is limited to lending operations (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `seize_positions`, `flash_loan`, `update_indexes`, `claim_revenue`, `recapitalize`, admin/params), all delegating to `ops/` modules — none of which issues an authorized outward call to a rewards contract. [1](#0-0)  `claim_revenue` only burns internal revenue shares and transfers the market's own underlying cash to the owner; it cannot touch a third-party reward token or invoke an external claim. [2](#0-1) 

The project's own threat model confirms both halves of the bug:

- "Aquarius LP collateral earns venue rewards for its holder, which is the pool. The pool has no entrypoint to claim or forward them."
- "Gauge rewards need the pool's authorization and therefore cannot be claimed at all." [3](#0-2) 

This is the exact analog of AaveV2Plugin missing a liquidity-mining claim: a contract that accrues external incentive yield on assets it custodies, with no function to collect it.

### Impact Explanation
Permanently frozen unclaimed yield. For any market whose collateral asset is an Aquarius LP token, all gauge rewards attributable to the pool's LP balance are unclaimable forever — the reward contract requires `require_auth` from the pool address and the pool can never produce it. This is strictly worse than the source M-01 (where a plugin upgrade or rescue could recover rewards): absent a contract upgrade, the yield is irrecoverable. LP-token rewards are frequently a material share of total LP yield, so LP-collateral suppliers lose a significant yield component relative to holding the LP directly.

### Likelihood Explanation
Certain for any listed market using Aquarius LP tokens as the market asset — Aquarius LP collateral is an explicitly supported configuration per the threat model. Reward accrual is automatic and ongoing; no attacker action or edge condition is required. The loss scales with LP collateral TVL and reward emission rates.

### Recommendation
Add an owner/governance-gated generic claim mechanism on the pool (or controller→pool path) that can invoke a whitelisted reward contract's claim function with the pool's authorization, measure the received reward tokens by balance delta, and credit them — either by swapping to the market asset and booking as `accrue_revenue`, or by transferring to the accumulator via the existing `claim_revenue` pipeline. Alternatively, distribute claimed rewards to LP-collateral suppliers pro-rata via the supply index.

### Proof of Concept
1. Governance creates a pool market whose `asset` is an Aquarius LP token (supported configuration; Aquarius LP fair value is handled by the pricing layer per the threat model's constant-product/stable LP valuation).
2. Users call `controller.supply`, transferring LP tokens into pool custody; the pool address becomes the LP holder.
3. Time passes; the Aquarius gauge accrues rewards attributable to the pool's LP balance.
4. Any user or keeper attempts to realize the rewards: gauge `claim` requires the holder's `require_auth`, which only a pool-originated sub-invocation could satisfy — and no pool entrypoint performs such a call (`claim_revenue` only calls `cache.transfer_out` of the market's own asset to the owner). [4](#0-3) 
5. Result: rewards accumulate at the gauge indefinitely; `token::balance` of the reward token at the pool stays zero, and no in-scope entrypoint can ever move them — confirmed by the threat model's statement that gauge rewards "cannot be claimed at all." [3](#0-2) 

Note: this limitation is acknowledged in `docs/explanation/threat-model.md` as forgone yield, which may weigh on whether the project treats it as an accepted design trade-off; the yield-freezing impact itself is nonetheless real and user-affecting.

pub(crate) fn apply(env: &Env, hub_asset: HubAssetKey) -> PoolAmountMutation {
    let outcome = accounting(env, hub_asset);

    if outcome.mutation.actual_amount != 0 {
        let owner = ownable::get_owner(env)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::OwnerNotSet));
        outcome
            .cache
            .transfer_out(&owner, outcome.mutation.actual_amount);
    }

    events::emit_market_state(env, outcome.cache.snapshot());
    outcome.mutation
}

pub(crate) fn accounting(env: &Env, hub_asset: HubAssetKey) -> RevenueOutcome {
    let mut cache = ops::renewed_market(env, &hub_asset);

    let net_transfer = cache.burn_claimable_revenue();

    guards::require_utilization_below_max(env, &cache);
    guards::require_supply_for_debt(env, &cache);
    cache.debit_cash(net_transfer);

    cache.commit();
    RevenueOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: net_transfer,
        },
    }
}
