### Title
Cross-repository forged commit status via `status` webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the *organization that owns the request* (derived from the payload's `repository.owner.login`), but `StatusHandler#process` writes a `Status` to **any** `Commit` in the entire database matching `params.sha`, without ever checking that the commit belongs to a repository owned by that authenticated organization. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to check with `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the untrusted payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [1](#0-0) [2](#0-1) 

This only proves the request came from *some* organization/repository that Shipit has a configured `webhook_secret` for — it says nothing about which repository/commit the payload is allowed to mutate.

Other event handlers correctly re-scope their side effects to the specific repository named in the (now-authenticated) payload, via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 
e.g. `PushHandler#process` and `CheckSuiteHandler#process` both operate through `stacks`, so a webhook that's valid for org/repo A can only touch stacks belonging to repo A: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does **not** use `stacks`/`repository_name` at all — it looks up commits globally by `sha` alone and writes a status onto whatever it finds: [6](#0-5) 

Since a `status` event's `sha`/`state`/`context` are the exact fields verified by the signature for the *sender's own repository*, but the code that consumes them looks up commits with no repository filter, any organization/repository configured in this multi-tenant Shipit instance can push a `status` webhook whose `sha` matches a commit belonging to a completely different stack/repository, and Shipit will happily attach that forged status to the victim's commit. This mirrors the original report's pattern precisely: one code path enforces a check ("is this the right principal") while a sibling code path performs the actual write and skips reasserting that check ("does the record I'm mutating actually belong to that principal") — exactly like `disableCollateral` revoking roles without updating `collateralActive`, letting the two pieces of state diverge and be exploited.

### Impact Explanation
`Status` records created here feed into `StatusChecker`, which gates whether a commit passes CI/merge/deploy requirements (`all_status_checks_passed?`, `any_status_checks_failed?`, `any_status_checks_missing?`) used by `MergeRequest#reject_unless_mergeable!`/`merge!`: [7](#0-6) 
An attacker who controls (or has webhook rights on) any repository/organization already configured in the Shipit instance can forge a passing status for a commit sha belonging to an unrelated victim stack, artificially satisfying required CI checks and enabling an **unauthorized deploy or merge** of that commit — one of the explicitly accepted Critical impacts.

### Likelihood Explanation
Exploitation requires the attacker to have a repository/organization that is already configured in this Shipit instance with a distinct webhook secret (a legitimate, low-privilege tenant of the same multi-org Shipit deployment), and to know or guess a commit SHA present in the victim stack (SHAs of merged/public commits are routinely public, e.g. visible on GitHub or in the Shipit UI itself). No access to the victim's GitHub repo, Shipit session, or `webhook_secret` is needed — only a signature valid for the attacker's *own* configured org, which they legitimately control. This is a realistic, unprivileged-attacker path within the documented multi-tenant deployment model.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already use `Handler#stacks`) to only update commits that belong to the repository named in the authenticated payload, e.g. filter through `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join through `Repository.from_github_repo_name(repository_name)`), rather than a bare global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker controls (or is a collaborator with webhook rights on) `attacker-org/attacker-repo`, which is already registered in this Shipit deployment with its own `webhook_secret` in `Shipit.github(organization: 'attacker-org')`.
2. Attacker finds a commit `sha` belonging to `victim-org/victim-repo`'s stack that is currently missing/failing a required CI status (e.g. via the public GitHub commit page or the Shipit UI).
3. Attacker sends a `status` webhook POST to `/github/webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature` computed with `attacker-org`'s webhook secret
   - Body: `{"sha": "<victim commit sha>", "state": "success", "context": "<required-context>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}}`
4. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies the signature successfully against `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — unscoped by repository — finds the victim's commit and calls `commit.create_status_from_github!(params)`, creating a forged "success" status on the victim's commit.
6. The victim stack's merge queue/deploy gating now sees the required status as passing, enabling an unauthorized merge/deploy.
