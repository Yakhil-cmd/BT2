This confirms the full write path: `archive!` finds the stack via `scope.find_by(environment:)` where `scope` is `repository.review_stacks` (scoped to the repository resolved from `full_name`), then calls `stack.deprovision` and `stack.archive!(user, ...)`, a real, irreversible mutation of B's stack.

### Title
Webhook signature verified against `repository.owner.login` while all resource resolution uses attacker-controlled `repository.full_name`, allowing cross-organization stack archival - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the signing organization/secret using `params.dig('repository','owner','login')`, but every handler (e.g. `ClosedHandler#repository`) resolves the target repository using the independent, also attacker-controlled `params.dig('repository','full_name')` field. When an organization is configured without a `webhook_secret`, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, so an unauthenticated POST naming that organization as `owner.login` but naming a *different* organization's repo in `full_name` passes signature verification and drives the handler to mutate the other organization's `ReviewStack`.

### Finding Description
The binding the code implicitly assumes is: `repository_owner (used to select the verifying webhook_secret) == owner(full_name) (the repository actually mutated by the handler)`. This does not hold, because the two fields are read independently from the same untrusted JSON body with no cross-check.

- `verify_signature` selects the app/secret via `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository', 'owner', 'login')` <cite repo="Ellentat/shipit-engine--007" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" />.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank/unset for that org: `return true unless webhook_secret` [1](#0-0) .
- `#create` then re-parses the raw body and dispatches to handlers using the same payload [2](#0-1) .
- `ClosedHandler#repository` (and every other PR handler / `Handler#repository_name`) resolves the acted-upon repository from `params.repository.full_name` / `payload.dig('repository','full_name')` — a completely different JSON field, never compared against `owner.login` [3](#0-2) [4](#0-3) .
- `ReviewStackAdapter#archive!` then finds the stack by `environment` ("pr<N>") scoped to that resolved repository's `review_stacks`, and calls `stack.deprovision` and `stack.archive!(user, ...)` — a genuine irreversible write [5](#0-4) .

Given the precondition that organization A's `github_apps` config entry has no `webhook_secret` (a supported, documented configuration — see the multi-org example fixture using `webhook_secret: # nil` for both orgs [6](#0-5)  and the setup docs showing `webhook_secret:` as optional/blank [7](#0-6) ), an attacker can send any unsigned body naming `owner.login: 'A'` while naming `full_name: 'B/target-repo'`, and the request passes `verify_signature` vacuously, then archives B's live review stack.

No other guard intervenes: `drop_unhandled_event` only checks the event name is handled, `ExplicitParameters` schema only validates types/presence of `full_name`, `action`, etc., not cross-consistency with `owner.login`, and there is no comparison anywhere between `repository_owner` and `repository.full_name`'s owner segment.

### Impact Explanation
An unauthenticated, unprivileged internet client can archive/deprovision a live `Shipit::ReviewStack` belonging to an organization/repository they have no relationship to, as long as any *other* configured organization in `Shipit.github_apps` lacks a `webhook_secret`. This is a cross-tenant write triggered by a payload that was never authenticated by the victim organization's credentials, matching the "Critical: a payload for one repository mutating another's stack" category. It is repeatable against any repository/environment combination as long as the attacker can guess or know its `full_name` and PR number (both are typically public/discoverable via GitHub), and against any number of stacks in one request loop.

### Likelihood Explanation
Requires: (1) at least one organization entry in `Shipit.github_apps` without a `webhook_secret` configured (documented as optional/supported, and even used in this repo's own test fixtures for multiple orgs), and (2) a live `ReviewStack` for the target repo with a guessable `environment` (`pr<N>`). No secrets, sessions, tokens, or GitHub write access to the victim repo are required — only knowledge of the victim's `full_name` and PR number, both public. Attacker cost is a single crafted HTTP POST.

### Recommendation
In `verify_signature`, derive the signing organization consistently with the resource the request will act on (e.g., require `owner.login` to match the owner segment of `repository.full_name`, or resolve `repository_owner` solely from `full_name`), and reject the request (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to vacuously succeed for organizations without a configured secret unless that is an explicit, intentional opt-out.

### Proof of Concept
Minitest integration test in `test/controllers/webhooks_controller_test.rb`:
1. Stub `Shipit.github_apps`/config so organization `orga` has no `webhook_secret` (mirrors `secrets_double_github_app.yml`).
2. Create fixtures: `Shipit::Repository` for `orgb/target-repo` with a live `Shipit::ReviewStack` at `environment: "pr7"`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and body `{"action":"closed","number":7,"pull_request":{...},"repository":{"owner":{"login":"orga"},"full_name":"orgb/target-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `:ok` (not `:unprocessable_entity`).
5. Assert `Shipit::ReviewStack` for `orgb/target-repo` `pr7` is now archived: `assert stack.reload.archived?`.
6. This demonstrates `repository_owner ("orga") != full_name owner ("orgb")` yet the write to `orgb`'s stack succeeds.
