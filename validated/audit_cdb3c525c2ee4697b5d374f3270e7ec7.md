### Title
Attacker-supplied route pool joins the caller's `require_auth` tree and drains wallet tokens beyond the routed input - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The `coffescript` report is the "malicious dependency" class: victim pulls in a package that looks like a swap route but executes attacker code that steals credentials/funds beyond the operation's declared scope. The on-chain analog exists in XOXNO Lending's strategy paths (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`): the caller supplies a `StrategySwap` XDR whose hops name arbitrary, unallowlisted pool addresses. The router invokes each `hop.pool`, and a rogue pool contract can call `token.transfer(victim, attacker, amount)` — Soroban folds that `require_auth` into the victim's root authorization tree created by the controller's `caller.require_auth()`. If the victim signs the simulated tree (which wallet UX actively encourages), the transfer executes, stealing wallet funds the swap never declared.

### Finding Description
`swap_tokens` authorizes only one exact input transfer to the router (`authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in)`), then calls `router.execute_strategy(&controller, &amount_in, swap)` with the fully caller-supplied `swap` payload [1](#0-0) . Neither the controller nor the router keep a pool allowlist — `dispatch_hop` invokes whatever `hop.pool` the payload names [2](#0-1) . The repo's own harness demonstrates the attack: a `RogueHopPool.swap()` performing `token.transfer(&victim, &to, &amount)` succeeds when nested under a `RootAuthEntry` that does `caller.require_auth()` — the unauthorized transfer joins the caller's signed auth tree [3](#0-2) . The threat model concedes: "a route can put third-party code on the call stack below the caller's authorization … The loss is then the caller's wallet, not the routed amount" [4](#0-3) . The balance-delta and overspend checks in `swap_tokens` only police the controller's own balances — they cannot bound a transfer debited from the caller's account.

### Impact Explanation
Theft of user funds: any token in the victim's wallet (unrelated to the swap's `token_in`/`amount_in`) can be transferred to the attacker. Like `coffescript` exfiltrating SSH keys and bash history rather than the package's declared function, the malicious hop exfiltrates wallet assets rather than just consuming the swap input.

### Likelihood Explanation
A single unprivileged address can reach this via `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`, all of which take a caller-supplied `StrategySwap`. The practical vector mirrors the advisory: routes are produced off-chain (quote server/SDK `routeXdr`), so the "package" the user embeds is opaque bytes; the victim sees one seemingly-fair swap and signs the auth tree simulation produces — which already contains the rogue transfer. Exploitation requires the victim to sign the poisoned tree, so likelihood is gated by client-side XDR decoding hygiene, not by any contract check.

### Recommendation
- Controller/router: cap the exposure by having the router only self-authorize venue pulls (`authorize_as_current_contract`) and reject any hop `pool` that is not a known venue deployment, or pin expected pool contract hashes per venue.
- Document/enforce that integrators must reject any simulated authorization tree where `caller.require_auth` has children beyond the single `token_in.transfer(caller → router, total_in)` (the exact rule stated in `threat-model.md`).
- Surface a machine-readable route hash so wallets can display exactly which contracts the transaction will invoke.

### Proof of Concept
1. Attacker deploys `RogueHopPool` (constructor stores `victim`, `token`, `to`, `amount`; `swap()` calls `token.transfer(victim, to, amount)`) — as in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` [5](#0-4) .
2. Attacker serves a route XDR for a victim's `repay_debt_with_collateral` whose single hop is `(venue=Phoenix-shape, pool=RogueHopPool, token_in=USDC, token_out=XLM)`; the payload's declared pool is attacker code.
3. Victim's client simulates the transaction. The auth tree now contains the expected `USDC.transfer(victim → controller)` plus the rogue `XLM.transfer(victim → attacker, ALL)`. The victim signs.
4. The rogue `swap` runs on the call stack under the controller→router→pool chain; the token contract's `from.require_auth()` resolves against the victim's signed tree, and the wallet drain executes while the swap's measured balance deltas still pass (`in_after <= in_before`, positive `received`) [6](#0-5) .

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
