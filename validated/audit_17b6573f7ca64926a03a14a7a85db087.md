Based on extensive research, I found a structurally analogous "pause bypass" pattern in the Polkadot SDK, though with an important difference in severity from the original Arrakis report (self-liquidity-removal is not theft of a third party's funds). I present it with full caveats.

### Title
Pausing `AssetConversion::remove_liquidity` via `pallet-tx-pause`/call-filter does not stop equivalent LP-token burn and asset withdrawal executed through the `pallet-revive` `AssetConversion` precompile - (File: `substrate/frame/asset-conversion/precompiles/src/lib.rs`)

### Summary
`pallet_asset_conversion` exposes liquidity removal through two different code paths that produce the identical state change (burn LP tokens, transfer back underlying reserves): the ordinary dispatchable extrinsic `Pallet::remove_liquidity` [1](#0-0)  and the `MutateLiquidity::remove_liquidity` trait method, which is invoked directly (not via `RuntimeCall` dispatch) by the `pallet-revive` Solidity-style precompile `IAssetConversion::removeLiquidity` [2](#0-1) . A chain operator using `pallet-tx-pause` (or a call-filter based safe mode) to pause the `AssetConversion`/`remove_liquidity` extrinsic during an incident only affects dispatch of the top-level `RuntimeCall::AssetConversion(Call::remove_liquidity{..})` variant, because `TxPause`'s `Contains` implementation matches on the pallet/call name of the outer dispatched call [3](#0-2) . The precompile call is dispatched as `RuntimeCall::Revive(Call::call{..})` — its pallet/call name is `"Revive"/"call"`, not `"AssetConversion"/"remove_liquidity"` — so the filter never inspects it, and the internal Rust call `<Pallet<Runtime> as MutateLiquidity<_>>::remove_liquidity(...)` executes and burns LP tokens / releases reserves regardless of the pause.

### Finding Description
`do_remove_liquidity` burns the caller's LP tokens via `T::PoolAssets::burn_from` and transfers back the underlying assets from the pool account [4](#0-3) . Both the pallet's own dispatchable and the trait-level `MutateLiquidity::remove_liquidity` implementation route to this same function [5](#0-4) . The `pallet-revive` precompile is reachable by any signed account (no privileged role) that calls a Solidity contract at the fixed precompile address, decodes `removeLiquidity(...)`, and forwards straight into `MutateLiquidity::remove_liquidity` [6](#0-5) . This call never passes through `frame_system`'s `BaseCallFilter`/`TxPause` check for `AssetConversion::remove_liquidity`, because that filter operates purely on the pallet/call name of the *outer* dispatched extrinsic (`Revive::call`), as implemented in `Pallet::<T>::contains` [3](#0-2) . This mirrors the Arrakis pattern exactly: pausing one named entry point (`ArrakisV2Router::removeLiquidity` / `AssetConversion::remove_liquidity`) does not prevent an equivalent, unguarded internal call (`ArrakisV2.burn()` / `MutateLiquidity::remove_liquidity` via the precompile) that produces the same effect.

### Impact Explanation
Unlike the Arrakis case, calling `remove_liquidity` only lets a user redeem *their own* LP tokens for their proportional share of reserves — it is not third-party fund theft. The real impact is defeating an operator's incident-response control: if `AssetConversion::remove_liquidity` is paused specifically to freeze withdrawals during a live accounting/reserve-calculation bug in `do_remove_liquidity`, an attacker or any user can still trigger the exact same vulnerable code path through the revive precompile, fully bypassing the pause. This downgrades the severity relative to the original High-severity theft report, since no cross-user drain occurs purely from the bypass itself — the risk is contingent on there being an additional live bug in `do_remove_liquidity`/reserve math that the pause was meant to contain.

### Likelihood Explanation
Likelihood depends on whether a given runtime deployment (a) enables `pallet-revive` with the `AssetConversion` precompile registered, and (b) simultaneously relies on `pallet-tx-pause`/a call-name-based filter to pause `AssetConversion::remove_liquidity` as an incident-response measure. I confirmed `pallet_asset_conversion::Config` and `pallet_tx_pause::Config` are both configured in `substrate/bin/node/runtime/src/lib.rs`, but I was **not able to fully confirm within the available searches** whether that specific runtime's `pallet_revive::Config::Precompiles` list actually includes the `AssetConversion` precompile (I found references to both but ran out of iterations to inspect the precompile-list wiring directly). This is a material verification gap.

### Recommendation
Any call-name-based pause/filter mechanism (tx-pause, safe-mode allow/deny lists) intended to freeze a pallet's dispatchable must also account for equivalent code paths reachable through other pallets that invoke the same underlying trait methods directly (e.g., `MutateLiquidity`, or other `fungible`/`fungibles` trait methods called from `pallet-revive` precompiles). Either gate `MutateLiquidity::remove_liquidity` (and analogous trait-level mutators) on the same pause state via a shared `TransactionPause`-aware guard, or ensure any precompile/host function that forwards into a pauseable pallet re-checks `TxPause::is_paused` for the underlying logical operation before proceeding.

### Proof of Concept
Not executed. This finding is derived from static code-path analysis: `substrate/frame/asset-conversion/src/lib.rs:495-517` (dispatchable), `substrate/frame/asset-conversion/src/liquidity.rs:118-137` (trait impl reused by non-extrinsic callers), `substrate/frame/asset-conversion/precompiles/src/lib.rs:462-484` (precompile bypass entry point), and `substrate/frame/tx-pause/src/lib.rs:279-288` (filter operates on outer call name only). No local Rust/FRAME integration test was run to demonstrate the pause bypass end-to-end, and the exact production runtime wiring (precompile registration alongside tx-pause) was not fully verified due to remaining tool-call budget — a Devin session with full repo access would be needed to confirm the precompile list for a concrete runtime and to write an integration test that (1) pauses `AssetConversion::remove_liquidity` via `pallet-tx-pause`, (2) asserts the dispatchable now fails, and (3) asserts a `pallet-revive` contract call into the `AssetConversion` precompile's `removeLiquidity` still succeeds and burns LP tokens / releases reserves.
