### Title
Unhandled exception in `handleJoint`-locked async callback leaves the mutex permanently held, halting all unit validation - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` in `main_chain.js` acquires the global `"handleJoint"` mutex via `mutex.lock(["handleJoint"], ...)` and then, inside the callback, calls `storage.readUnitProps(db, earlier_unit, async function(objEarlierUnitProps){...})` with an `async` function as the callback [1](#0-0) . If `objEarlierUnitProps.is_on_main_chain` is falsy, the function does `throw Error("earlier unit is no longer on main chain")` [2](#0-1) . Because this callback is an `async function` invoked as a plain callback (not awaited or wrapped in try/catch by the caller `storage.readUnitProps`), the thrown error becomes an unhandled promise rejection, and — critically — `unlock()` is never called on that code path. This mirrors CVE-2020-12658's root cause in gssproxy: a lock (`cond_mutex` there, the `"handleJoint"` mutex here) is not released before the executing context exits abnormally.

### Finding Description
The `mutex.js` implementation is a cooperative, key-based async lock used throughout the codebase to serialize critical sections such as unit validation and writing (`network.js:1166`, `composer.js:735`, `joint_storage.js:220-227`) [3](#0-2) . Locks are only released when the `unlock` callback supplied by `mutex.exec` is invoked; `handleQueue()` only re-evaluates queued jobs after `release(arrKeys)` runs [4](#0-3) .

In `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, once a "handleJoint" lock is acquired, `storage.readLastStableMcIndex` is queried and then `storage.readUnitProps(db, earlier_unit, async function(objEarlierUnitProps){...})` is invoked with an async function as its result callback [1](#0-0) . Every other exit branch in that async callback calls `unlock()` explicitly (e.g. line 1223, line 1235), but the `throw Error(...)` on line 1220 bypasses all of them — the thrown exception simply rejects the promise returned by the async function, which nobody consumes or catches. The `"handleJoint"` lock therefore stays held forever (`arrLockedKeyArrays` never has that entry removed), and every subsequent unit posted to the node that requires the `"handleJoint"` lock (i.e., essentially all unit validation, per `network.js:1166` `mutex.lock(['handleJoint'], ...)`) is queued indefinitely and never processed.

This is functionally the same defect class as CVE-2020-12658: a lock acquired on a legitimate/expected code path is not released when the routine exits through an unanticipated/abnormal path (a `throw` in gssproxy's worker-exit path vs. an unhandled async rejection in the ocore lock-holding callback).

### Impact Explanation
Any node that reaches this `throw` while holding the `"handleJoint"` mutex will permanently stop validating new units, because all future validations queue behind the stuck lock via `mutex.lock(['handleJoint'], ...)` in `network.js:1166` [5](#0-4) . This satisfies the "network unable to confirm new units" impact bar: the affected node stalls indefinitely and cannot process or relay new joints, effectively partitioning it from the rest of the network's confirmation flow until manually restarted.

### Likelihood Explanation
The condition `!objEarlierUnitProps.is_on_main_chain` is reached only when `determineIfStableInLaterUnits` first reports the `earlier_unit` as stable-in-parents (`handleResult(bStable, true)` at line 1202) while the unit's on-main-chain status has since changed by the time the `"handleJoint"` lock is granted and `readUnitProps` resolves [6](#0-5) . This is a race/reorg-timing condition triggered by the ordinary flow of units being posted and processed (single unprivileged unit posters continuously feeding units causes stability recalculation to run repeatedly), not by a specially crafted malicious payload alone — it requires a specific interleaving of unit arrival and main-chain movement while a stability-advance is in flight. I was not able to fully verify from the available code how deterministically an attacker-controlled unit sequence could force this exact race, since the full call chain from `validation.js` into `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (and the exact conditions that flip `is_on_main_chain` between the check and the lock acquisition) was not completely traced in the time available.

### Recommendation
Wrap the async callback passed to `storage.readUnitProps` in `main_chain.js` in a try/catch (or use `.catch()` on the returned promise) that guarantees `unlock()` is called before any exception is allowed to propagate. Alternatively, replace `throw Error(...)` with an explicit `unlock(); return console.log(...)`/`return handleError(...)` pattern consistent with the other exit branches in that function, so no code path inside a `mutex.lock` critical section can exit without releasing the lock.

### Proof of Concept
Not able to construct a concrete unit-posting sequence with full confidence without deeper tracing of `validation.js`'s call into `determineIfStableInLaterUnitsAndUpdateStableMcFlag` and the exact timing window needed to make `objEarlierUnitProps.is_on_main_chain` false between the initial stability check and the `readUnitProps` callback firing under the `"handleJoint"` lock. Conceptually: an attacker submits units in a pattern that causes `determineIfStableInLaterUnits` to report `earlier_unit` stable (line 1202), then, before the queued `"handleJoint"` lock is granted and `readUnitProps` resolves, posts/causes a reorg-like main-chain change so that `earlier_unit` is no longer on the main chain, hitting the `throw` at line 1220 and permanently wedging the `"handleJoint"` mutex.
