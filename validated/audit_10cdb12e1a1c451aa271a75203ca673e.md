## Title
Multisig transaction payload-mismatch check is feature-flag-gated, allowing execution of a different payload than what owners approved - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

## Summary
`multisig_account::validate_multisig_transaction` — the function the VM calls during mempool admission and transaction-prologue execution for `MultisigTransaction`s — only checks that the payload supplied at execution time matches the full payload that owners voted to approve when the feature `abort_if_multisig_payload_mismatch_enabled` is turned on. When that flag is off, an executing owner can submit a `SignedTransaction` whose entry-function/script payload differs from the payload that was actually voted on by the other owners, and admission will not reject it.

## Finding Description
`validate_multisig_transaction` is documented as being invoked both during mempool validation and as the first step of transaction execution: [1](#0-0) 

For a `MultisigTransaction` created with the full payload stored on chain (`create_transaction`, `transaction.payload.is_some()`), the check that the submitted execution payload matches what was approved is conditioned on a feature flag: [2](#0-1) 

```move
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(
        payload == *stored_payload,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
    );
}
```

Only the `payload_hash` case (transactions created via `create_transaction_with_hash`) is checked unconditionally: [3](#0-2) 

The `payload` value passed into `validate_multisig_transaction` is derived from the caller-supplied `TransactionExecutableRef` in the actual `SignedTransaction` being submitted, not from the on-chain vote record: [4](#0-3) 

This is exactly analogous to the reported Buffer bug: the admission/resolution step (`resolveQueuedTrades` there, `validate_multisig_transaction` here) is supposed to bind the thing being executed to the thing that was originally queued/approved, but the binding check is optional/skippable — in Buffer's case there was simply no check at all; here the check exists but is gated by a feature flag that (by its very name, "abort_if_..._enabled") indicates the mismatch was not enforced before this flag existed and is not enforced when it is disabled.

The consequence: any owner who has already accumulated the required number of approvals for a `MultisigTransaction` with full payload `A` stored on-chain can, instead of executing `A`, submit an execution transaction whose entry-function payload is `B` (some entirely different call, e.g. transferring funds to themselves, changing owners, or calling an arbitrary entry function on behalf of the multisig account). If `abort_if_multisig_payload_mismatch_enabled` is off, `validate_multisig_transaction` does not reject this at either mempool admission or prologue execution time, and the transaction proceeds to the execution phase in `AptosVM::execute_multisig_transaction`, which fetches "the next transaction payload" using the caller-provided payload as an input: [5](#0-4) 

I was not able to fully inspect the body of `multisig_account::get_next_transaction_payload` (the function actually invoked to determine what gets executed) within the available context, so I cannot state with 100% certainty whether it *always* falls back to the caller-supplied payload when the stored payload check is skipped, or whether it independently re-enforces the stored payload regardless of the prologue's gated check. This is the one remaining piece needed for full end-to-end proof and should be verified directly in a Devin session before treating this as conclusively exploitable.

## Impact Explanation
If `get_next_transaction_payload` allows the caller-provided payload to be used when the mismatch check is skipped, this breaks the core multisig approval-set invariant: the payload that N-of-M owners approved is not the payload that gets executed as the multisig account (a form of "approval validation accepting the wrong approval set," directly matching the admission-pivot criteria). This would let a single executing owner impersonate the full quorum's intent and execute arbitrary entry functions/scripts as the multisig account (fund transfers, owner/threshold changes, etc.), which is Critical severity for any multisig account relying on the "full payload stored on-chain" flow while the flag is disabled.

## Likelihood Explanation
Likelihood is contingent on the on-chain state of the `abort_if_multisig_payload_mismatch_enabled` feature flag (a governance-controlled feature). The mere existence of this flag as a distinct, nameable feature strongly suggests there was a period — and there may still be environments/testnets/other deployments — where it is disabled by default, meaning the mismatch enforcement is opt-in rather than baked into the core admission logic. Because this is a feature-flag-gated core invariant rather than an unconditional check, it also represents fragile design: any regression or misconfiguration that leaves the flag off silently reintroduces the vulnerability.

## Recommendation
Make the "provided payload must match stored payload" and "payload hash must match" checks unconditional, non-feature-gated invariants in `validate_multisig_transaction` (and confirm `get_next_transaction_payload` also unconditionally uses/derives from the stored payload, never a caller-supplied override) — mirroring the reported fix in the external report of binding execution strictly to the originally-approved/queued state rather than trusting a value the executor supplies out-of-band.

## Proof of Concept
Full end-to-end reproduction requires confirming `get_next_transaction_payload`'s exact fallback behavior, which I could not retrieve in this session. Conceptually:
1. Owner A creates a multisig transaction with `create_transaction` storing full payload `A` (e.g., `transfer(recipient=A, amount=X)`).
2. Owners vote/approve until quorum (`num_signatures_required`) is met for this transaction id.
3. With `abort_if_multisig_payload_mismatch_enabled` disabled, executing owner submits a `MultisigTransaction` execution transaction whose actual `TransactionExecutableRef` is payload `B` (e.g., `transfer(recipient=attacker, amount=Y)`), not `A`.
4. `validate_multisig_transaction`'s payload-match branch is skipped (flag off), admission passes.
5. If `execute_multisig_transaction` → `get_next_transaction_payload` executes `B` instead of `A`, funds/permissions intended for `A` are diverted per `B`, bypassing the other owners' approval of `A`.

Given the unresolved verification gap on step 5, I recommend a Devin session inspect `get_next_transaction_payload` in `aptos-move/framework/aptos-framework/sources/multisig_account.move` directly to confirm or refute this path before treating it as a confirmed, exploitable vulnerability.
