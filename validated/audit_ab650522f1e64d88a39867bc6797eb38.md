### Title
Unvalidated swap routes can inject arbitrary caller-authorized token transfers - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
High: caller-controlled `swap` bytes are forwarded through strategy execution while the caller’s root authorization remains active. A route-selected contract can add an unrelated `token.transfer(caller, attacker, amount)` beneath that authorization; if the simulated authorization tree is signed, the transfer succeeds while the swap still satisfies the controller’s measured-output checks.

### Finding Description
`swap_collateral` accepts the route as opaque `Bytes` and requires only caller authentication plus owner-or-delegate rights for the target account. [1](#0-0) [2](#0-1) 

The strategy withdraws collateral and passes the same opaque payload into `swap_tokens_or_passthrough`, which reaches `swap_tokens`. [3](#0-2) [4](#0-3) 

`swap_tokens` narrowly authorizes one controller-to-router input transfer, but then forwards the caller-supplied payload to the configured router. [5](#0-4)  Its subsequent checks measure only the controller’s input spend, leftover input, and output-token balance delta; they do not constrain which contracts the payload causes to run or which additional caller-authorized calls occur below the root invocation. [6](#0-5) [7](#0-6) 

The authorization bypass is demonstrated by the route-injection test: a router calls the payload-selected pool, and that pool calls `token.transfer(victim, attacker, amount)`. [8](#0-7) [9](#0-8)  Simulation records the injected transfer as a sub-invocation of the victim’s `swap_collateral` authorization, and enforcing mode executes it when the returned tree is signed. [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker can drain unrelated tokens held in the victim’s wallet while still delivering sufficient swap output for the controller’s checks and final account validation. [12](#0-11)  This is theft of user funds beyond the routed collateral: the injected transfer may target any token whose `transfer` requires the victim’s authorization and is included in the signed tree. [9](#0-8) 

The same class applies to every caller-controlled strategy route that reaches `swap_tokens`, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [13](#0-12) [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The attacker can deploy the malicious route contract and supply the poisoned route without privileges, but exploitation requires the account owner or delegate to sign the poisoned authorization tree produced by simulation. [16](#0-15) [17](#0-16)  The route remains externally plausible because it can return a valid output amount, so the controller’s balance-delta and solvency checks do not identify the injected wallet transfer. [6](#0-5) [18](#0-17) 

### Recommendation
Restrict route execution to governance- or router-approved venue contracts rather than allowing payload-selected contract addresses to run beneath the caller’s authorization. At the integration layer, reject a controller-strategy authorization tree containing any unexpected child invocation; the expected controller strategy should not need an unrelated token transfer under the caller’s root authorization. [19](#0-18)  The measured-input/output checks should remain, but they are not a substitute for constraining executable route targets. [20](#0-19) 

### Proof of Concept
1. A debt-free victim holds supplied USDC and an unrelated wallet token, while the attacker deploys a pool contract initialized with `(victim, wallet_token, attacker, amount)`. [21](#0-20) 
2. The malicious contract’s `swap` function transfers the victim’s wallet token to the attacker. [9](#0-8) 
3. The victim invokes `swap_collateral(caller=victim, account_id, current=USDC, amount=50_000_000_000, new=ETH, swap=poisoned_route)`. [22](#0-21) 
4. Simulation records the wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [10](#0-9) 
5. Signing and submitting that tree produces the expected ETH supply while reducing the victim’s unrelated wallet-token balance to zero and crediting the attacker. [12](#0-11) [23](#0-22)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
