### Title
Verifier-selector/data-selector divergence lets a webhook signed for one GitHub org mutate a `PullRequest` under an unrelated stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to check the HMAC signature using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent. `EditedHandler`, however, resolves the `Repository`/`Stack`/`PullRequest` to mutate entirely from the independent `params.repository.full_name` field. Because these two fields are not cross-checked, a webhook can be signature-verified against one GitHub organization's secret while its side effects apply to a completely different, unrelated repository/stack.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`organization_used_for_signature_verification (repository_owner) == organization_that_owns(params.repository.full_name)`.

Code path:
- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , and used to select the `GitHubApp` (and hence the webhook secret) via `Shipit.github(organization: repository_owner)` before calling `verify_webhook_signature` [2](#0-1) .
- `EditedHandler` resolves the target `Repository` purely from `params.repository.full_name`, an independently attacker-controlled field, unrelated to `repository_owner` [3](#0-2) , and then looks up and updates the matching `PullRequest` [4](#0-3) .
- `verify_webhook_signature` returns `true` unconditionally if the resolved org has no configured `webhook_secret` [5](#0-4) , making any org lacking a secret (or any org whose secret the attacker knows because they administer it in a multi-org Shipit deployment) a "lenient verifier."

Exploit request: an attacker who controls (or knows the secret for) some GitHub org "orgA" configured in this Shipit instance sends `POST /webhooks` with header `X-Github-Event: pull_request`, a body with `organization.login = "orgA"` and no `repository.owner.login`, but `repository.full_name = "victim-org/production-repo"` and `action: "edited"`. `repository_owner` resolves to `"orgA"`, the signature check passes using orgA's (possibly absent) secret, but `EditedHandler` looks up and updates the `PullRequest` belonging to `victim-org/production-repo`.

Existing guards do not close this gap: `drop_unhandled_event` and `check_if_ping` are unrelated; `verify_signature` only checks the byte-for-byte HMAC against the org selected by `repository_owner`, it never compares that org to `params.repository.full_name`'s owner; `EditedHandler`'s `ExplicitParameters` schema requires `repository.full_name` to be present but does not require `repository.owner.login`, nor does it require the two to match.

### Impact Explanation
The concrete, code-supported effect of `EditedHandler#process` is limited to `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5)  — i.e., overwriting the JSON metadata blob (title, state, additions/deletions, head sha/ref, assignees, labels) of an existing `PullRequest` record for a repository that did not authenticate the request. This is a genuine violation of tenant isolation ("a payload for one repository mutating another's stack/record") and matches the Critical example category in the rules, but nothing in `EditedHandler` triggers a `Command`/`PTY.spawn`, deploy, rollback, or merge — the "production environment" characteristic of the target stack does not amplify this handler's effect beyond metadata corruption. The claim of "Unauthorized deploy/rollback/merge of attacker-controlled code" is not supported by this handler's code; that broader claim would require chaining into a different handler (e.g., one that triggers deploys from PR state), which is out of scope for `EditedHandler`.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization and for at least one of them to either (a) have no `webhook_secret` configured, or (b) have a secret known/controlled by the attacker (e.g., an org the attacker administers in a multi-tenant Shipit deployment). Given that requirement, the attacker cost is a single crafted, unauthenticated HTTP POST with no GitHub/Shipit secrets required for the "lenient" org, and the record-corruption effect is repeatable against any tracked repository/stack by number.

### Recommendation
In `WebhooksController#verify_signature`, do not select the verification org independently of the data the handler will act on. Require that `repository.owner.login` be present for handlers that operate on `repository.full_name`, and reject the payload if `repository.owner.login` (when present) does not match the owner encoded in `repository.full_name`. Do not allow organizations with no `webhook_secret` configured to short-circuit verification (`verify_webhook_signature` returning `true` when `webhook_secret` is blank in `lib/shipit/github_app.rb`); require a secret for all configured organizations.

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb`:
1. Stub two configured orgs: `"lenient-org"` (no `webhook_secret`) and `"victim-org"` (has a `webhook_secret`, victim's `production` stack/repo lives under it).
2. Create a `Shipit::PullRequest` fixture attached to a stack whose `Repository#full_name == "victim-org/production-repo"` and stack `environment == "production"`.
3. Build a `pull_request` `action=edited` payload with `organization: { login: "lenient-org" }`, no `repository.owner.login`, `repository.full_name = "victim-org/production-repo"`, `number` matching the fixture PR, and a forged `pull_request.title`.
4. POST to `/webhooks` with header `X-Github-Event: pull_request` and no valid signature for `victim-org` (any signature, since `lenient-org` has no secret).
5. Assert response is `200 OK` (not `422`), i.e. `repository_owner` resolved to `"lenient-org"` and verification passed.
6. Assert the fixture `PullRequest#github_pull_request['title']` (and other fields) was overwritten with the attacker's forged title — proving the record for `victim-org`'s production stack was mutated despite the signature only having been checked against `lenient-org`'s (or a nonexistent) secret. Equality to test: `repository_owner used in verify_signature ("lenient-org") != owner(params.repository.full_name) ("victim-org")`, yet the write still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
