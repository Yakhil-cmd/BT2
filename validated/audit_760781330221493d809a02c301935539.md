### Title
Organization authenticated by webhook signature is decoupled from the repository/stack acted on by webhook handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read straight out of the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). All downstream event handlers, however, resolve the `Stack`/`Repository` to act on using a *different* field of the same payload: `repository.full_name` [1](#0-0) . Nothing binds these two fields together, so a validly-signed webhook (signed with the secret of an organization the attacker legitimately controls) can carry a `repository.full_name` pointing at a stack belonging to a completely different, victim organization.

### Finding Description
`verify_signature` picks the GitHub App config purely off attacker-supplied JSON: [2](#0-1) [3](#0-2) 

The signature check only proves that *some* configured organization's registered GitHub App produced the raw body (using the secret selected by `repository_owner`). It never checks that the `owner` field matches the `full_name`'s owner, nor that the resolved organization is the same one whose stacks are subsequently mutated.

Every webhook `Handler` subclass, though, resolves the stack scope from a different payload key entirely: [4](#0-3) 

For example `PushHandler` finds stacks by `full_name` and branch and calls `stack.sync_github`: [5](#0-4) 

More severely, the `status` webhook writes a `Status` object directly from attacker-controlled fields of the payload (`state`, `description`, `target_url`, `context`), with no round-trip to the GitHub API to corroborate them, as shown by the existing test: [6](#0-5) 

Because the trust boundary "which organization's secret authenticated this request" (via `repository_owner`) is never tied to "which repository/stack is written to" (via `repository.full_name`), an attacker who legitimately controls one configured organization (e.g., they own a `somegithuborg` GitHub App installation, as shown supported by multi-org configs such as `test/dummy/config/secrets_double_github_app.yml`) can:

1. Know or compute a valid `X-Hub-Signature` using their own organization's `webhook_secret` over a raw JSON body they fully control.
2. Set `repository.owner.login` (or `organization.login`) in that body to their own org so `Shipit.github(organization: repository_owner)` picks their own app/secret and the signature check passes.
3. Set `repository.full_name` in the very same body to `victim-org/victim-repo`, which the `Handler` base class uses to look up `Repository.from_github_repo_name` / `stacks`.
4. Have the handler act on the victim's stack — e.g. force a `sync_github` call, or, worse, forge a `status` event that writes a fake green CI status (`state: "success"`, arbitrary `context`) for a specific commit SHA on the victim's stack.

This breaks the binding: `organization that authenticated == repository that is written`.

### Impact Explanation
A forged CI status on a commit the attacker doesn't own can satisfy `ci.require` gating configured in the victim stack's `shipit.yml`, which Shipit uses to decide whether a commit is eligible to deploy. This can lead to an **unauthorized deploy** of a commit that never actually passed CI, satisfying the "unauthorized deploy" impact criterion. It requires only that the attacker control (or have push/webhook access to) one organization already configured in this Shipit instance — not the victim's organization, no privileged Shipit account, no `ApiClient` token, and no compromise of the victim's `webhook_secret`.

### Likelihood Explanation
Any Shipit deployment that serves more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` showing multiple orgs under one `github:` key) is exposed. The attacker only needs legitimate, unprivileged control of a repository/webhook in *any one* of the configured organizations to forge a signature that Shipit will accept while targeting a different organization's stacks — no credential theft or session is required.

### Recommendation
In `WebhooksController#verify_signature`, cross-check that `repository.owner.login`/`organization.login` (the field used to select the verifying app/secret) matches the owner embedded in `repository.full_name` before proceeding, and reject the request otherwise. Additionally, `Handler#repository_name` (and all handlers such as `StatusHandler`) should re-derive the owning organization from the same value used to authenticate the payload, not trust an independent field for stack resolution.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, `AttackerOrg` (attacker-controlled) and `VictimOrg` (hosts a tracked stack `VictimOrg/victim-repo`), similar to `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "https://attacker.example.com",
     "repository": { "full_name": "VictimOrg/victim-repo", "owner": { "login": "AttackerOrg" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)` — a secret they legitimately know from their own org's GitHub App.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and successfully verifies the signature (per `lib/shipit/github_app.rb#verify_webhook_signature`) [7](#0-6) .
6. `StatusHandler` (via `Handler#repository_name`) resolves `VictimOrg/victim-repo`'s stack and writes a forged "success" status for the specified commit, potentially satisfying that stack's `ci.require` gate for deployment — despite the request never being authenticated by `VictimOrg`'s own webhook secret.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
