### Title
Bundling multiple independent AA payment messages into one all-or-nothing response unit causes a single dust/insufficient-funds failure to permanently bounce and strand otherwise-payable rewards - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit`/`completePaymentPayload` logic composes *all* payment messages of a trigger response into a single unit and treats the whole unit as atomic: if any single payment message cannot be funded (e.g., because the AA's byte balance is fragmented into dust outputs below `FULL_TRANSFER_INPUT_SIZE`, or an asset issuance step fails), the entire response — including unrelated, independently payable messages — is discarded via `bounce()`. This mirrors the Tokemak M-4 pattern where staking a too-small TOKE reward reverted the whole reward-claim transaction and stranded an otherwise-claimable, unrelated DAI reward.

### Finding Description
When an AA trigger produces multiple payment messages (e.g., a base-currency change/fee payment plus an independent custom-asset reward payment to the same user), `sendUnit` iterates over `messages` and calls `completePaymentPayload` for each non-base asset first, then for the base payment last [1](#0-0) . Coin selection for the base ("bytes") payment explicitly skips outputs smaller than `FULL_TRANSFER_INPUT_SIZE` to avoid "dust attacks": `AND amount>=" + FULL_TRANSFER_INPUT_SIZE` [2](#0-1) . If the AA's spendable byte balance is composed entirely (or mostly) of such small/dust outputs, `readStableOutputs`/`readUnstableOutputsSentByAAs` will not find enough qualifying inputs even though the AA's nominal balance is sufficient to cover the requested amount, and the code falls through to `return cb('not enough funds for ' + target_amount + ' bytes')` [3](#0-2) .

That `cb(err)` propagates through the `async.eachSeries` callback and is converted directly into `bounce(err)` [4](#0-3) . Bouncing discards **all** messages composed for that trigger, not just the one that failed — including any independent custom-asset payment message that would have succeeded on its own (analogous to the DAI extra-reward in the Tokemak report, which is stuck because the unrelated TOKE main-reward stake reverts the entire claim). The same all-or-nothing bounce behavior also applies to `issueAsset` failures ("not enough funds for X of asset Y") and to the aggregate negative-balance check across messages [5](#0-4) .

Because AAs commonly merge/pay multiple messages per trigger response (see `mergeMessagesAndOutputs`, which explicitly groups multiple payment messages into per-asset messages within one unit) [6](#0-5) , any AA author who writes an `oscript`/`ojson` definition emitting several `payment` messages in one case (a common, unprivileged, user-reachable pattern, as shown by shipped sample AAs like `fundraising_proxy.oscript` and `51_attack_game.oscript` that emit multiple payment messages per branch) is exposed to this atomicity trap: a dust/insufficient-balance condition on one payment silently blocks payout of the other, unrelated payment, on every subsequent trigger attempt, because the dust condition does not resolve itself (dust outputs remain excluded from selection indefinitely and the trigger fee itself typically also lands as dust).

### Impact Explanation
Users/AA balance holders can have funds become permanently unclaimable/stuck: a legitimate, independently payable reward or refund message bundled with another payment that cannot be funded (due to `FULL_TRANSFER_INPUT_SIZE` dust exclusion or an asset-issuance failure) never gets paid, because the whole AA response bounces every time the trigger is resent, with no way for the trigger sender to separate the payments. This is an AA fund-freezing condition reachable purely by normal trigger senders/AA authors, without any privileged or malicious-peer behavior — it matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an AA definition that bundles multiple independent payment messages in one response (a supported, common, and even sample-documented pattern in this codebase), and (b) the AA's byte balance becoming fragmented into small (dust) outputs below `FULL_TRANSFER_INPUT_SIZE`, which can happen naturally over time from many small trigger fees or intentionally via a dust-flooding trigger sender. Once that state is reached, every subsequent trigger response bundling that payment with another payment bounces, so the condition is easy to trigger and hard to self-heal without protocol- or AA-author-level mitigation.

### Recommendation
Avoid making the entire multi-message AA response atomic with respect to fundability of unrelated payment messages:
- When a payment message cannot be funded due to insufficient (non-dust) inputs, consider partially satisfying independent messages rather than bouncing the whole response, or clearly document/require AA authors to separate independently-fundable payments across different trigger-processing steps/state so a stuck payment cannot block others.
- Alternatively, provide AA authors a way to detect/consolidate dust (e.g., an oscript primitive to merge small outputs) before attempting a payment that depends on aggregate balance, so dust fragmentation cannot indefinitely block payouts.
- At minimum, ensure `bounce()` clearly signals to the trigger sender (and available via `response.error`) that the failure is due to dust/fundability so operators can proactively consolidate the AA's outputs, and consider auto-consolidating dust outputs whenever the AA composes a base-payment message and has any spare capacity to do so.

### Proof of Concept
1. Deploy an AA whose response, for a given trigger case, emits two `payment` messages in the same response: (a) a small base ("bytes") payment/refund to address X, and (b) an independent custom-asset payment (e.g., previously issued token) to address X, similar to the pattern used in `fundraising_proxy.oscript`/`51_attack_game.oscript` which emit multiple payment messages per case [7](#0-6) .
2. Arrange (via many small prior trigger payments/fees) for the AA's byte balance to consist entirely of outputs smaller than `FULL_TRANSFER_INPUT_SIZE`, so `readStableOutputs` finds no eligible inputs [2](#0-1) .
3. Send a trigger that satisfies the `if` condition for case (b) (custom-asset payout), causing the AA to also emit the base payment message (a).
4. Observe that `completePaymentPayload` for the base message returns `'not enough funds for ... bytes'` [8](#0-7) , which is escalated to `bounce(err)` [4](#0-3) , discarding the entire response — including the custom-asset payout that would have succeeded independently — with the payout stuck on every retry as long as the dust condition persists.

			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
