Confirmed vulnerability. The multi-org configuration (`docs/setup.md:182-209`, `config/secrets.development.shopify.yml`) means a Shipit deployment tracking repositories across multiple GitHub organizations has a separate `webhook_secret` per org, keyed by the payload's `repository.owner.login` (or `organization.login`) field. But the code path that decides *which repository/stack is mutated* uses a completely different field: `repository.full_name`.

### Title
Webhook signature verified against `repository.owner.login`, but repository actions execute on unchecked `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature with by reading `repository.owner.login` (falling back to `organization.login`) from the **attacker-supplied JSON body**. [1](#0-0) [2](#0-1)  Once the signature check passes, every registered handler resolves the target `Repository`/`Stack` using a **different** field of the same body — `repository.full_name` — via `Webhooks::Handlers::Handler#repository_name`/`#stacks`. [3](#0-2) 

### Finding Description
Shipit explicitly supports hosting multiple GitHub Apps for multiple organizations, each with its own `webhook_secret`, selected via `Shipit.github(organization:)` / `Shipit.github_app_config` [4](#0-3) , as documented in `docs/setup.md` "Using Multiple Github Applications" [5](#0-4) .

The signature-verification binding is: `verified_org == payload["repository"]["owner"]["login"]`. The action-binding used afterward is: `acted_repository == payload["repository"]["full_name"]`. Because both values come from the **same unauthenticated JSON body** and are never cross-validated against each other, an attacker who legitimately controls a webhook endpoint/secret for **their own** GitHub organization (`OrgAttacker`, which they can freely configure as an installer of their own GitHub App under Shipit) can craft a payload where:
- `repository.owner.login = "OrgAttacker"` (so the HMAC is computed/verified with `OrgAttacker`'s known `webhook_secret`)
- `repository.full_name = "OrgVictim/victim-repo"` (a completely unrelated org/repo tracked by the same Shipit instance under a different stack)

`verify_signature` passes because the signature genuinely matches `OrgAttacker`'s secret, but `PushHandler`/`StatusHandler`/etc. then act on `OrgVictim/victim-repo`'s stack, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  or updating commit statuses for a commit belonging to a stack the attacker has no legitimate GitHub access to.

### Impact Explanation
This breaks the intended equality: "the organization whose secret authenticated the request" must equal "the repository whose state gets mutated." For `push` events this can force a spoofed `sync_github` job (fetching/ref-updates) against a victim org's stack; for `status`/`check_suite` events it can forge CI status/check results Shipit consults for merge/deploy safety-checks (`Handlers::StatusHandler`, `Handlers::CheckSuiteHandler`), potentially unblocking or misleading downstream deploy/merge decisions on a repository the attacker does not own. This crosses a cross-repository/cross-organization trust boundary using only credentials the attacker legitimately possesses for their own org.

### Likelihood Explanation
Requires only that (a) the Shipit deployment is configured with multiple GitHub organizations (a documented, supported configuration), and (b) the attacker controls at least one of those organizations' GitHub Apps (their own webhook secret) while also being aware of another repository/stack name tracked by the same instance. `repository.full_name` values are frequently discoverable from Shipit's own UI/API listing stacks. No privileged Shipit account, session, or token is needed — only the ability to set the webhook secret used to sign their own crafted POST to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature`, and/or in `Webhooks::Handlers::Handler`, cross-validate that the organization used to select the `webhook_secret` matches the organization portion of `repository.full_name` (and `organization.login` when present) before dispatching to handlers — i.e. reject the payload if `repository.owner.login`/`organization.login` != the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker configures/owns a GitHub App installed on `OrgAttacker`, giving them `webhook_secret_A` (a legitimate configuration in Shipit's multi-org mode).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `webhook_secret_A` (their own known secret) over the raw body and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and successfully verifies the signature against `webhook_secret_A`. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgVictim/victim-repo")` and triggers `stack.sync_github` on the victim's stack, even though the attacker has no GitHub authorization over `OrgVictim`. [6](#0-5)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
