# Multisig approval validation does not bind the executed payload to the approved payload when `abort_if_multisig_payload_mismatch` is disabled

### Summary

The Zeta report's core defect is that a value that is supposed to be *bound and enforced at admission time* (the gas limit used for fee calculation) is instead silently allowed to diverge from the value actually used at execution, letting a caller under-pay relative to what will really be executed. The Aptos-native analog exists in the multisig-transaction admission path: `validate_multisig_transaction`, the VM-prologue check for multisig cctx-equivalents, only enforces that the *executed* payload matches the *approved* payload when the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. When that flag is off, an owner who has accumulated quorum approval for one payload (`A`) can submit a transaction whose actual executable entry function is a completely different payload (`B`), and admission (the prologue) will not reject it — the wrong, unapproved payload will be committed under the multisig account's signer.

### Finding Description

`validate_multisig_transaction` is documented as being invoked by the VM prologue, i.e. it is an admission-boundary check, "invoked during mempool transaction validation and as the first step of transaction execution": [1](#0-0) 

When a multisig transaction was created with the full payload stored on chain (via `create_transaction`, which sets `payload_hash: option::none()` and `payload: option::some(payload)`), the on-chain payload/hash check is only performed conditionally: [2](#0-1) 

Concretely:
- `transaction.payload_hash.is_some()` is `false` in this path, so the hash-match assertion is skipped entirely.
- The only remaining safeguard — asserting `payload == *stored_payload` — is gated behind `features::abort_if_multisig_payload_mismatch_enabled()` *and* requires the caller-provided `payload` to be non-empty.

The `payload` argument passed into this Move function is derived, on the Rust/VM side, from the **executor's own submitted transaction**, not from the on-chain stored payload: [3](#0-2) 

After the prologue (`run_multisig_prologue`) succeeds, the VM proceeds to execute the entry function that the submitting owner actually put in their `SignedTransaction` — it does not re-fetch and substitute the stored `transaction.payload` for dispatch. Consequently, if `abort_if_multisig_payload_mismatch_enabled` is disabled, quorum approval collected for payload `A` (visible to and voted on by the owners) can be "spent" to execute an arbitrary, unapproved payload `B` submitted by any owner able to reach quorum, because nothing at admission time binds the dispatched call to the payload that was actually voted on.

This is distinct from the hash-committed flow (`create_transaction_with_hash`), where `payload_hash.is_some()` forces an unconditional `sha3_256(payload) == *payload_hash` check — that path is safe. The vulnerability is isolated to the full-payload-on-chain path guarded only by the feature flag.

### Impact Explanation

This breaks the "approval validation accepting the wrong approval set" invariant explicitly called out in the admission gate: the multisig owners' signatures/approvals are recorded against payload `A`, but the state transition that is actually admitted and committed executes payload `B`. Since the multisig account signer is used to execute `B`, this is effectively unauthorized execution under the multisig account's identity/signer set — funds can be moved, permissions changed, or arbitrary entry functions invoked without genuine quorum approval for that specific action. This is a critical-severity confusion between "what was approved" and "what gets executed," directly analogous to the underlying flaw class in the external report (a value trusted at approval/admission time is not the value actually enforced at execution time).

### Likelihood Explanation

The likelihood is conditional entirely on the state of `features::abort_if_multisig_payload_mismatch_enabled()`. If this flag is disabled on a given network (e.g., prior to activation, or if intentionally left off for compatibility), any account owner who is already an approved participant of the multisig (i.e., an "insider" with legitimate voting rights but not sole quorum control) can exploit this without any additional privilege — they simply craft their execution transaction to carry a different entry function than the one that was actually voted on. No cryptographic bypass or governance action is required beyond normal multisig usage; the caller here is not a "privileged governance/admin" actor performing an intended admin action but an unprivileged-relative-to-the-approved-payload owner exploiting a validation gap in the standard execute-flow.

### Recommendation

Make the payload-match check unconditional (not gated behind `abort_if_multisig_payload_mismatch_enabled`) whenever `transaction.payload.is_some()`, regardless of whether the caller-provided payload is empty. If an empty/omitted payload must be supported for UX reasons, resolve the entry function to execute from the *stored* `transaction.payload` rather than trusting the executor-supplied payload, so admission and execution always operate on the same, quorum-approved payload.

### Proof of Concept

1. Owner A calls `create_transaction(owner_A, multisig_account, payload_A)` where `payload_A` encodes a benign entry function (e.g., a small transfer). This stores `payload = Some(payload_A)`, `payload_hash = None`.
2. Owner B calls `approve_transaction(owner_B, multisig_account, seq)`, reaching the `num_signatures_required` quorum for `payload_A` (both owners implicitly/explicitly approve based on `payload_A` as displayed to them).
3. On a network/build where `features::abort_if_multisig_payload_mismatch_enabled()` is disabled, Owner A (or any owner able to submit the execution transaction) submits a `SignedTransaction` whose actual `TransactionExecutableRef::EntryFunction` encodes a different, more damaging entry function `payload_B` (e.g., draining a resource controlled by the multisig account), targeting the same `multisig_account` and `sequence_number`.
4. `run_multisig_prologue` computes `provided_payload = bcs(payload_B)` and calls `validate_multisig_transaction(owner, multisig_account, payload_B)`.
5. Inside `validate_multisig_transaction`: `transaction.payload_hash.is_some()` is false (skip), and the match-check branch is skipped because the feature is disabled — no assertion ever compares `payload_B` to the stored `payload_A`.
6. Admission succeeds; the VM then executes `payload_B` under the multisig account's signer, even though only `payload_A` ever received quorum approval.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
```
