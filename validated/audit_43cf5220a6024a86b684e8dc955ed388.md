### Title
Headers-commission split among multiple `earned_headers_commission_recipients` can over-distribute commission beyond the payer's actual fee via independent per-recipient rounding - (File: `headers_commission.js`, `validation.js`)

### Summary
The reported bug class is a rounding/remainder-accounting error: a shared pool of value is split among multiple claimants using per-claimant rounding without reconciling the rounded amounts against the real total, so the sum of distributed shares can exceed the actual balance available. In `ocore`, the analogous mechanism is the header-commission ("hc") redistribution among `earned_headers_commission_recipients`: each recipient's share of a single `headers_commission` amount is rounded independently with `Math.round()`, and nothing forces the sum of the rounded per-recipient amounts to equal the original commission amount.

### Finding Description
Any multi-authored unit can declare `earned_headers_commission_recipients`, an array of `{address, earned_headers_commission_share}` whose shares are validated only to sum to exactly 100 (percent) - not that the resulting rounded amounts sum to the original commission: [1](#0-0) 

When a unit wins headers commission from a parent, `calcHeadersCommissions()` computes the payer's `full_amount` (the parent's `headers_commission`) and then splits it per recipient by `Math.round(full_amount * share / 100.0)`, independently for each recipient: [2](#0-1) 

The MySQL code path performs the equivalent split with SQL `ROUND()`: [3](#0-2) 

Because each recipient's amount is rounded independently (not via a "distribute remainder to last recipient" or largest-remainder method), and `Math.round` rounds `.5` away from zero, splitting an odd `full_amount` across recipients with shares that produce `.5` fractions causes every recipient's rounded amount to be rounded *up* simultaneously. For example, `full_amount = 3` split 50/50 between two recipients: each recipient's exact share is `1.5`, and `Math.round(1.5) = 2` for both, so `2 + 2 = 4` is inserted into `headers_commission_contributions`/`headers_commission_outputs`, one unit more than the `full_amount` of `3` that was actually reserved as commission when the parent unit was created.

These summed amounts are inserted directly into `headers_commission_outputs` without any transfer from an existing balance: [4](#0-3) 

and are later spendable as ordinary `headers_commission` inputs, validated by `calcEarnings`/`validatePaymentInputsAndOutputs`: [5](#0-4) 

This exactly mirrors the reported bug class: an accounting value meant to reflect an exact, conserved share of a fixed pool is instead computed via independent unreconciled rounding, so the total credited to claimants can exceed the true underlying amount.

### Impact Explanation
The over-rounded amount is new spendable base-asset value that was never deducted from anyone's balance - it is fabricated purely by the rounding split. This constitutes a form of controlled supply inflation of the base asset (bytes), reachable by any unprivileged user who posts a multi-authored unit with a crafted `earned_headers_commission_recipients` list and shares chosen to force simultaneous upward rounding (e.g. all recipients' exact shares end in `.5`). While the amount created per occurrence is small (bounded by roughly `(n-1)/2` units per winning unit, where `n` is the number of recipients), it is systematically triggerable and repeatable across many units/mcis, allowing gradual, deterministic inflation of total circulating supply outside of the protocol's issuance rules.

### Likelihood Explanation
Likelihood is moderate-to-high: constructing a multi-authored unit with `earned_headers_commission_recipients` is a standard, unprivileged operation (`composer.js` already supports it), and the attacker fully controls the `earned_headers_commission_share` values (only constrained to sum to 100 and be positive integers) and can also influence whether their unit wins the headers-commission race for a given parent (deterministically, via the SHA1-based winner selection over children). Reliably obtaining commission wins requires only running enough addresses/nodes as unit authors, which is within reach of any actor with modest resources.

### Recommendation
Reconcile per-recipient rounding against the total commission before inserting rows, e.g. compute all shares' floor values first, then distribute the residual remainder (`full_amount - sum(floors)`) to specific recipients deterministically (largest-remainder method), so `sum(distributed amounts) === full_amount` is enforced by code rather than assumed. Apply this both in the JS in-memory path and in the MySQL `ROUND()` based SQL path in `headers_commission.js`.

### Proof of Concept
1. Create a unit `A` (parent) that will pay `headers_commission = 3` (a value achievable by controlling unit header size).
2. Create a multi-authored child unit `B` (2 authors) that becomes the SHA1-winning child of `A` for headers commission (`getWinnerInfo` in `headers_commission.js`), with:
   ```json
   "earned_headers_commission_recipients": [
     { "address": "ADDR1", "earned_headers_commission_share": 50 },
     { "address": "ADDR2", "earned_headers_commission_share": 50 }
   ]
   ```
3. When `calcHeadersCommissions()` runs after `A`/`B` stabilize, for `full_amount = 3` and `share = 50`, each recipient gets `Math.round(3 * 50 / 100.0) = Math.round(1.5) = 2`.
4. `headers_commission_contributions` receives two rows of `amount = 2` each (total `4`), and `headers_commission_outputs` sums to `4` for that mci — one unit more than the `3` that was actually reserved as `headers_commission` by unit `A`.
5. Both `ADDR1` and `ADDR2` can later spend their `2`-unit outputs as valid `headers_commission` inputs (`validation.js` lines 2579-2599), for a total of `4` spent from an original `3`-unit fee, demonstrating fabricated supply.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
