### Title
NULL/undefined pointer dereference in `handleOnlinePrivatePayment` crashes the node on a malformed private-payment message - (File: network.js)

### Summary
`network.js:handleOnlinePrivatePayment` (invoked whenever a wallet counterparty or hub-relayed peer sends a `private_payment` justsaying/chain) dereferences `arrPrivateElements[0].payload.denomination` before ever verifying that `.payload` exists. Any device or peer that sends a private-payment chain whose head element omits `payload` triggers an uncaught `TypeError`, which is escalated by the global `uncaughtException` handler into a process crash — directly analogous to the CVE-2018-10773 NULL-pointer dereference in `bibutils`' `addsn`, where a missing/short field is dereferenced without a prior existence check, causing an application crash.

### Finding Description
`handleOnlinePrivatePayment` is the entry point used to accept private (indivisible/divisible asset) payment chains received either directly from a peer/wallet counterparty or forwarded via a hub: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");

	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```

The only check performed is that `arrPrivateElements` is a non-empty array of *something*. `arrPrivateElements[0]` is not required to be a non-empty object, and in particular there is no check that `.payload` exists before `arrPrivateElements[0].payload.denomination` is accessed. If `payload` is `undefined` (or `arrPrivateElements[0]` itself lacks the field, e.g. `{unit: "..."}`), the line throws `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This is exactly the same bug class as CVE-2018-10773: a required substructure (in bibutils, the serial-number field; here, the `payload` object) is dereferenced without a presence check, and the resulting NULL/undefined dereference crashes the process handling attacker-controlled input.

Contrast this with the sibling validation code that is reached later in the same call chain and *does* perform the check correctly, confirming that the missing check in `handleOnlinePrivatePayment` is an oversight rather than an implicit invariant:
- `indivisible_asset.js:parsePrivatePaymentChain` checks `!objPrivateElement.payload || !objPrivateElement.payload.inputs || ...` before use [2](#0-1) 
- `private_payment.js:validateAndSavePrivatePaymentChain` checks `!headElement.payload` before use [3](#0-2) 

`handleOnlinePrivatePayment`, however, runs *before* either of these safer functions and crashes first.

The uncaught exception is not contained: any exception thrown while processing an incoming message in `onWebsocketMessage`/`handleJustsaying`/`handleRequest` is not wrapped in a try/catch for this code path, so it propagates to Node's process-level handler, which deliberately re-throws to kill the process: [4](#0-3) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

The path is reachable both from a wallet counterparty sending a private payment via wallet.js `handlePrivatePaymentChains`/`network.handleOnlinePrivatePayment` [5](#0-4) , and from any hub-relayed/peer-forwarded `private_payment` justsaying handled in network.js — i.e., an unprivileged private-payment counterparty (a normal wallet feature, no special privileges required) can trigger it.

### Impact Explanation
A crafted private-payment message with a head element that omits the `payload` field (or is otherwise malformed enough to make `payload` undefined) crashes the full node process that receives it. Because the crash occurs in the core message-handling path of `network.js` and is deliberately turned into a process-terminating exception, this is a straightforward, reliable, remotely-triggerable denial-of-service against any wallet/node that accepts private payments from a counterparty (which is a routine wallet interaction, not a privileged operation). Repeated against witnesses/hubs or user wallets, this can be used to keep target nodes offline, preventing them from validating/relaying/confirming units — i.e., "a network unable to confirm new units" for the affected node(s).

### Likelihood Explanation
High. No signature check, asset lookup, or other gating happens before the vulnerable line — only `isNonemptyArray(arrPrivateElements)` is checked. Any device paired with the victim (or any hub operator relaying a `private_payment` justsaying) can send a single malformed chain element to trigger the crash deterministically, with no race conditions or preconditions beyond having an active pairing/connection, which is the normal state for private-payment counterparties.

### Recommendation
In `handleOnlinePrivatePayment` (network.js), validate the shape of `arrPrivateElements[0]` before touching nested fields, mirroring the checks already used downstream in `indivisible_asset.js`/`private_payment.js`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0]) || !ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("invalid private payment element");
```
More broadly, audit all `arrPrivateElements[i].payload.*` and `arrPrivateElements[i].output*` accesses on the network-message-handling path for the same missing-field pattern, and wrap message-handling entry points in try/catch that reports a validation error instead of allowing exceptions to reach the global `uncaughtException` crash handler for attacker-controlled input.

### Proof of Concept
1. Pair two wallets/devices normally (attacker device is a legitimate private-payment counterparty of the victim).
2. Attacker sends a `private_payments` message (subject `private_payments`, handled by `wallet.js`'s `handlePrivatePaymentChains`) with `body.chains = [[{ unit: "<any 44-char base64 unit>", message_index: 0 }]]` — i.e., a chain whose sole/head element has no `payload` field. (`handlePrivatePaymentChains`'s own array-shape check only validates array/object non-emptiness of `chains`/elements, not that `payload` exists on the head element before `network.handleOnlinePrivatePayment` runs — verify against the exact guard in `wallet.js:955-972` for the current build.)
3. This reaches `network.handleOnlinePrivatePayment(ws, arrPrivateElements, ...)`, executing `arrPrivateElements[0].payload.denomination` where `payload` is `undefined`.
4. The resulting `TypeError` is uncaught, hits `process.on('uncaughtException', ...)` in `network.js:4530-4543`, and the victim's node process crashes/exits.
