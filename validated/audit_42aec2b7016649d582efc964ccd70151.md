### Title
Webhook signature authenticates the sending organization but not the target repository, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a delivery against using a field taken directly from the untrusted payload body, then only checks the HMAC of the raw body against that org's secret. It never verifies that the organization which supplied a valid secret actually owns the repository the payload claims to target. Any principal who controls a GitHub organization configured in this Shipit instance (multi-org deployments are a documented, supported configuration) can self-sign a fabricated payload and point it at a stack belonging to a *different* organization, exactly mirroring the reported bug class: a value trusted and acted upon (the repository/ref/SHA to sync) is not actually covered/bound by the verification step (the org-secret check) that is supposed to authorize it.

### Finding Description
`verify_signature` computes `repository_owner` from the JSON body itself: [1](#0-0) 
and uses it purely to select which `Shipit.github(organization:)` config/secret to HMAC-verify the raw body against: [2](#0-1) 

`verify_webhook_signature` only proves that *some* configured organization's secret matches the body's HMAC: [3](#0-2) 

Every event handler then resolves the actual `Stack`/`Repository` to operate on from a separate field in the same body, `repository.full_name`, with no cross-check against the organization that was authenticated: [4](#0-3) 

`PushHandler` then trusts attacker-controlled `ref`/`after` to sync a stack under that resolved repository to an arbitrary commit: [5](#0-4) 

Shipit explicitly documents running with multiple independently-configured GitHub organizations/secrets in the same instance: [6](#0-5) 

The binding that should hold is: `organization authenticated by webhook_secret == organization owning repository.full_name acted upon`. Before a malicious delivery, this holds naturally because GitHub itself always sends consistent `repository`/`owner` data. After an attacker who administers any one configured org crafts and signs their own payload with their own valid secret, `repository_owner` (used for auth) and `repository.full_name` (used for the actual stack lookup) can diverge arbitrarily, breaking the binding.

### Impact Explanation
An attacker who controls any GitHub organization onboarded to this Shipit instance — with no Shipit account, `ApiClient` token, or write access to the target repository — can forge `push`, `status`, or `check_suite` deliveries that are validated as authentic (because they are correctly HMAC-signed with the attacker's own legitimately-configured secret) yet target stacks belonging to an unrelated organization's repositories tracked by the same instance. This can drive `GithubSyncJob`/`stack.sync_github` to move a stack's head to an attacker-chosen SHA, or falsify CI/check-suite state used to gate deploys, leading toward an unauthorized deploy/rollback decision on a repository the attacker does not own — matching the High-impact category "escalation ... unauthenticated read of stack state ... or an unauthorized deploy."

### Likelihood Explanation
Requires only that the attacker administer/control one GitHub organization already configured in the shared Shipit instance's `secrets.yml` (a supported, documented multi-tenant setup), and no repository write access, Shipit session, or API token — squarely within the "unprivileged attacker" threat model defined by the rules.

### Recommendation
In `verify_signature`, after computing a verified organization from the secret check, re-derive/validate that `payload.dig('repository', 'full_name')`'s owner matches the authenticated organization (or that the resolved `Repository`/`Stack` belongs to that organization) before dispatching to handlers, rather than trusting `full_name` unconditionally in `Handler#stacks`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `victim-org` (owns tracked stack `victim-org/private-repo`) and `attacker-org` (attacker is an admin, with their own legitimate `webhook_secret`).
2. Attacker crafts a `push` JSON payload: `{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"full_name": "victim-org/private-repo", "owner": {"login": "attacker-org"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the HMAC matches → request passes.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/private-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, despite the request never being authenticated by `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
