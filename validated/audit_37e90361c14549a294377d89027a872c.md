### Title
Webhook Signature Verification Uses Attacker-Controlled Organization Field While Event Handlers Trust a Different Repository Field, Enabling Cross-Organization Webhook Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`). All downstream event handlers, however, resolve the target repository/stack using a *different* field of the same unverified body: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (a documented, first-class configuration, see `docs/setup.md` and `config/secrets.development.shopify.yml`), these two fields are never checked against each other, so a signature that is valid for organization A can be attached to a payload whose `repository.full_name` points at organization B's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
It picks the `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
`verify_webhook_signature` then just HMACs the raw body with that organization's secret: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the *same untrusted params* to handlers: [4](#0-3) 
All handlers (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, a completely separate field from the one used for signature routing: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `Shipit` explicitly supports hosting several independent GitHub organizations, each with its own `webhook_secret`, from one shared instance:

the binding that should hold is: *`repository.owner.login` (the org whose secret verified the payload) == the organization that owns `repository.full_name` (the repository the handler acts on)*. Nothing in the controller or in `Repository.from_github_repo_name` enforces this equality; `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled strings within the same signed body.

### Impact Explanation
Any party who legitimately administers (or otherwise knows the `webhook_secret` of) one tenant organization configured on a shared Shipit instance — an "unprivileged attacker" with respect to every *other* tenant — can craft an arbitrary JSON body, set `repository.owner.login` to their own organization (so `Shipit.github(organization: repository_owner)` picks the secret they know), sign it correctly with that secret, but set `repository.full_name` to `victim-org/victim-repo`. The forged, "verified" webhook is then processed as if it genuinely originated from GitHub for the victim repository. Depending on event type this allows:
- Forged `status` events (`StatusHandler`) writing fabricated CI statuses on a victim stack's commits, which is exactly the signal `ci.require`/CI gating relies on to allow deploys — a path toward an unauthorized deploy.
- Forged `push` events (`PushHandler`) triggering `GithubSyncJob` against a victim stack.
- Forged `pull_request`/`membership` events mutating state (labels, review-stack archive/unarchive, team/membership records) for organizations the attacker has no legitimate access to.

This is a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the acted-upon resource — squarely in the "authenticated organization vs. repository written" binding-break category and within the stated impact bar (cross-repository writes / path to unauthorized deploy).

### Likelihood Explanation
Requires only knowledge of a valid `webhook_secret` for *any one* organization hosted on the shared instance (something each tenant's own GitHub App owner necessarily knows, since they configure it themselves per `docs/setup.md`), plus the ability to send an unauthenticated HTTP POST to the public `/webhooks` endpoint. No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required. This is realistic wherever the multi-org configuration shown in `config/secrets.development.shopify.yml` is used.

### Recommendation
After verifying the signature, cross-check that the organization used to select the secret (`repository_owner`) actually owns the repository referenced by `repository.full_name` (and by extension the `Stack`/`Repository` record the handler will act on) before dispatching to handlers — reject the request if they don't match. Alternatively, derive the signing organization strictly from the resolved `Repository` record's `owner`, not from an independent, unverified payload field.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an administrator of `orgA` (who legitimately knows `orgA`'s `webhook_secret`, e.g. because you set up its GitHub App per `docs/setup.md`), build a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. In `verify_signature`, `repository_owner` resolves to `"orgA"`, `Shipit.github(organization: "orgA")` returns `orgA`'s app, and the signature checks out against the known `orgA` secret — the request passes verification.
6. `PushHandler#process` then resolves the target stacks via `Repository.from_github_repo_name("orgB/victim-repo")`, and `GithubSyncJob`/subsequent processing is triggered for `orgB`'s stack, despite the attacker having no access to `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
