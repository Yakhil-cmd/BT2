### Title
`provision?` operator-precedence bug admits `prevent_with_label` PRs when `review_stacks_enabled` is false - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` ORs three clauses, but `review_stacks_enabled` is `&&`-bound only to the first (`allow_all`) clause due to Ruby operator precedence, so it does not gate the `prevent_with_label` clause at all. An attacker who opens an unlabeled PR against a repository configured with `provisioning_behavior :prevent_with_label` gets a `ReviewStack` provisioned and its `shipit.yml` executed via `PTY.spawn`, even though the repository never enabled review stacks.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled (false) == the value provision? requires to admit this PR`. Tracing `provision?`: [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The third disjunct — the exact scenario in the question (`prevent_with_label?` true, no label) — is never conditioned on `review_stacks_enabled`. With `review_stacks_enabled == false`, `provisioning_behavior_prevent_with_label? == true`, and `pull_request_has_provisioning_label? == false`, the whole expression evaluates to `true` regardless of the disabled flag. The two sides of the binding therefore diverge: `review_stacks_enabled` is `false`, but `provision?` behaves as if it were `true` for this configuration.

`respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?`, so `process` proceeds unconditionally to: [2](#0-1) 

which calls `ReviewStackAdapter#find_or_create!` → `#create!`, creating a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled) and queuing it for provisioning: [3](#0-2) 

Nothing upstream blocks this: the webhook route validates the GitHub signature and dispatches by event type, but performs no repository-level authorization check tied to `review_stacks_enabled` before invoking the handler — that check is `provision?`'s sole job, and it's broken. Model validations on `Repository`/`Stack` do not constrain `branch` to any allow-list, so an attacker-named branch is accepted verbatim, and provisioning subsequently spawns processes running the deploy spec fetched from that branch, reaching `PTY.spawn` in `lib/shipit/command.rb`.

### Impact Explanation
For any repository owner who has configured `provisioning_behavior :prevent_with_label` (a legitimate, documented behavior) but has not opted into review stacks (`review_stacks_enabled == false`), an unprivileged attacker who can open a pull request (including from a fork) can force creation and provisioning of a `Shipit::ReviewStack` whose branch and deploy spec are entirely attacker-controlled. This leads to command execution on the deploy host via `Command`/`PTY.spawn`, matching the Critical impact category (RCE via `PTY.spawn`) for a repository that never authorized the review-stacks feature. It is repeatable against any repository matching this configuration, and each PR opened creates a new provisioned stack/environment.

### Likelihood Explanation
Preconditions are: `repository.provisioning_behavior == "prevent_with_label"` and `repository.review_stacks_enabled == false` — a plausible, even likely, configuration for operators who set a provisioning label policy before formally enabling review stacks, or who believe `review_stacks_enabled: false` fully disables the feature. No secrets, tokens, or privileged roles are needed; the attacker only needs to open a PR without the provisioning label (the default state — simply don't add the label). This is trivially and repeatably exploitable once the configuration exists.

### Recommendation
Fix operator precedence in `provision?` so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
