The Ghost CVE describes an HTTP path-traversal vulnerability in a web server's static-asset middleware (`frontend/web/middleware/static-theme.js`), triggered by an unauthenticated HTTP request with `..` path segments. This bug class requires an HTTP-facing file-serving component that resolves attacker-controlled path segments against a filesystem root without normalization.

Polkadot SDK's file-path-handling code (e.g., worker directory management, keystore file paths, WASM override scraping, sysinfo file reads, RPC server middleware) is not reachable via a real user entry point as defined by the report's threat model — a signed extrinsic, a contract call, an XCM message, or a public proof submission. All the file-path operations I found are either:
- Node/administrator-controlled configuration (`--node-key-file`, `--base-path`, `wasm_override` directory, keystore path) set by the node operator, not an unprivileged network attacker [1](#0-0) [2](#0-1) [3](#0-2) 
- Internal sandbox path construction for PVF workers, not exposed to any external/runtime input [4](#0-3) 
- JSON-RPC server middleware that operates on RPC method dispatch, not filesystem paths derived from request URLs [5](#0-4) 

None of these constitute a runtime-level extrinsic, XCM, or contract entry point that lets an unprivileged attacker supply a path segment consumed in filesystem access, which is the essential attacker-controlled-input requirement from the Ghost advisory. There is no FRAME pallet, XCM executor, or contracts/revive code path that takes user-supplied strings and resolves them against a local filesystem root for serving content back to the caller. This bug class (HTTP static-asset directory traversal) has no demonstrable analog in the Polkadot SDK's runtime/consensus-critical code reachable by an ordinary user.
