## Analysis

The Solidity report concerns `CollateralEscrowV1.sol`'s `depositAsset`, which records the caller-supplied `_amount` as the ledger balance instead of measuring the actual balance delta after `transferFrom`, so a fee-on-transfer token silently desyncs recorded vs. real balances and later withdrawals get stuck.

The Polkadot SDK's own token primitives (`pallet-assets`, `pallet-balances`, the `fungible`/`fungibles` `Mutate`/`Hold` traits) are immune to this bug class by construction: `decrease_balance`/`increase_balance`/`transfer_and_hold`/`transfer_on_hold` all return the *actual* amount moved and callers use that returned value for bookkeeping [1](#0-0) , [2](#0-1) . There is, however, one concrete analog where a caller-declared amount is trusted without verifying it against a resulting balance delta: `ERC20Transactor`, the XCM `TransactAsset` implementation used to move ERC20 tokens deployed on `pallet-revive` between XCM `Location`s such as `AssetHubWestend`.

### Title
ERC20Transactor records `amount` as XCM asset credit without verifying the actual balance moved, allowing fee-on-transfer / non-standard ERC20 tokens to desync XCM holding accounting - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls an arbitrary Revive-deployed ERC20 contract's `transfer(to, amount)` and, on a `true` boolean return, unconditionally credits `AssetsInHolding` with the requested `amount` [3](#0-2) . It never reads the checking account's post-transfer balance to confirm `amount` tokens actually arrived. `deposit_asset_with_surplus` mirrors this: it transfers the recorded `amount` out of the checking account to the beneficiary, again trusting the boolean return value rather than the observed balance change [4](#0-3) . Any ERC20 contract address referenced via an `AccountKey20` XCM `Location` is matched and processed with no separate registration/allow-listing step, as demonstrated by the integration test that deploys an arbitrary `MyToken` ERC20 and immediately uses its address in a `withdraw_asset`/`deposit_asset` XCM program [5](#0-4) .

### Finding Description
The invariant violated is: *the amount of an asset recorded as held/transferred in the XCM executor's `AssetsInHolding` must equal the amount actually moved in the underlying ledger.* `ERC20Transactor` breaks this invariant because it derives the recorded amount purely from the `Asset` value declared in the XCM instruction (via `Matcher::matches_fungibles`), not from measuring the ERC20 contract's balance before/after the `transfer` call [6](#0-5) .

Standard ERC20 contracts that implement transfer fees, rebasing, or any deduction on `transfer` (a widely used and legitimate token pattern, exactly the class flagged in the original report) will move less than `amount` to the `TransfersCheckingAccount`, yet the XCM executor's internal ledger (`Erc20Credit(amount)`) still reflects the full requested `amount`. Because `Erc20Credit`'s accounting methods (`saturating_take`, `saturating_subsume`) operate purely on this untrusted numeric value, not on real contract state, later `DepositAsset` instructions in the same XCM program will attempt to move the (inflated) recorded `amount` out of the checking account, exceeding what the checking account actually holds for that token.

The reachable entry point is a signed extrinsic: any account can call `pallet_xcm::execute` (or a reserve-transfer entrypoint that ends up calling `ERC20Transactor`) with a `WithdrawAsset`/`DepositAsset` program referencing an `AccountKey20` location pointing at any deployed Revive contract — no privileged role or registry entry is required, as shown by the test harness constructing and using an arbitrary ERC20 contract address inline [7](#0-6) .

### Impact Explanation
For a legitimate (non-malicious) fee-on-transfer ERC20 token used through XCM: after `WithdrawAsset` under-funds the checking account relative to the recorded credit, the subsequent `DepositAsset` instruction's `IERC20::transfer` call from the checking account will fail (insufficient real balance) even though the XCM executor believed it held enough. This causes the instruction to error and the mismatched `AssetsInHolding` value to be trapped via the standard asset-trap mechanism, at a *phantom* amount larger than the real tokens actually resident in the checking account — i.e., real user funds become effectively unrecoverable/stuck at their nominal (pre-fee) value, matching the "funds stuck at withdraw" impact of the original report. This is a Medium-severity accounting desync affecting real user funds without any privileged action, matching Sherlock's severity classification for the original issue.

### Likelihood Explanation
Likelihood depends entirely on whether the runtime configuring `ERC20Transactor`'s `Matcher` permits arbitrary/unregistered ERC20 contracts as valid XCM fungible assets. The Asset Hub Westend test suite demonstrates exactly this permissive configuration (an inline-deployed contract address is used immediately without any prior registration call) [8](#0-7) . I was not able to fully inspect `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs` (the concrete `Matcher`/`ERC20TransfersCheckingAccount` wiring) within the remaining tool budget to confirm there is no additional allow-list gate in the live runtime configuration beyond what the test exercises; this is the main open uncertainty.

### Recommendation
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should measure the checking/beneficiary account's ERC20 `balanceOf` before and after the `transfer` call (or use `transferFrom`/return-value-plus-balance-diff patterns) and credit/debit `AssetsInHolding` with the *actual* observed delta rather than the requested `amount`, consistent with how `pallet-assets`/`fungible` traits already return actual transferred amounts elsewhere in the codebase.

### Proof of Concept
I was not able to execute a live reproduction within the available tool budget (no terminal/execution access in this ask-only session). The evidence assembled is: (1) the vulnerable code paths crediting `amount` unconditionally on a boolean-success `transfer` call [9](#0-8) ; (2) the existing integration test proving arbitrary Revive-deployed contracts are directly usable as XCM fungible assets with no registration step [8](#0-7) . A concrete PoC would need to: deploy a standard fee-on-transfer ERC20 fixture (e.g., a token that burns 1% per `transfer`), run the same `withdraw_and_deposit_erc20s`-style XCM program, and assert that the beneficiary's received amount is less than `erc20_transfer_amount` while `AssetsInHolding`/trap accounting still reflects the full requested amount — this reproduction was not executed and its pass/fail status is unverified.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
