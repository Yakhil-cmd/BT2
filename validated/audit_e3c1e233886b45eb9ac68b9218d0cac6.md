### Title
`BridgeTransferKLAY` Fallback Function Uses `msg.sender` as Counterpart-Chain Recipient, Permanently Locking KLAY When Called by a Contract — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The fallback function of `BridgeTransferKLAY` unconditionally passes `msg.sender` as the `_to` (recipient) address on the counterpart chain. When a contract (e.g., a multisig wallet) sends KLAY directly to the bridge, the KLAY is bridged to the same address on the counterpart chain. Because contract addresses are deployment-deterministic and not backed by a private key, and because the contract almost certainly does not exist at that address on the counterpart chain, the bridged KLAY is permanently inaccessible.

---

### Finding Description

`BridgeTransferKLAY.sol` exposes a payable fallback function:

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [1](#0-0) 

This calls `_requestKLAYTransfer` with `_to = msg.sender`, which emits a `RequestValueTransfer` event with `to = msg.sender`:

```solidity
emit RequestValueTransfer(
    TokenType.KLAY,
    msg.sender,
    _to,          // <-- msg.sender, the calling contract's address
    address(0),
    msg.value.sub(_feeLimit),
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

The bridge operators on the counterpart chain observe this event and call `handleKLAYTransfer`, which delivers KLAY to `_to` via a low-level call:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [3](#0-2) 

The Go-layer bridge manager confirms this flow — it passes `ev.GetTo()` (which is the original `msg.sender`) directly into `HandleKLAYTransfer`: [4](#0-3) 

If `msg.sender` is a contract on the source chain, its address on the counterpart chain is either:
1. An empty account (no code deployed there) — KLAY is sent there and permanently inaccessible because no private key exists for a contract-derived address.
2. A different contract with no KLAY withdrawal mechanism — KLAY is trapped.

The `requestKLAYTransfer(address _to, ...)` function does not have this problem because the caller explicitly specifies `_to`. The vulnerability is exclusive to the fallback, which silently substitutes `msg.sender` for `_to` with no warning or guard.

---

### Impact Explanation

Bridged KLAY is permanently locked at an uncontrollable address on the counterpart chain. This is an **unauthorized loss of bridged assets** — the user's KLAY leaves the source chain bridge and arrives at an address nobody can spend from. The KLAY is neither recoverable by the user nor by the bridge operators (the handle nonce is consumed, so the transfer cannot be replayed).

---

### Likelihood Explanation

Contracts routinely interact with bridges by sending native tokens directly (the fallback is the standard ERC-20-style "just send ETH/KLAY" UX). Multisig wallets (Gnosis Safe, etc.) are the most common example and are widely used by DAOs, protocols, and institutional holders. The bridge documentation does not warn against contract callers. Likelihood is **medium-high**.

---

### Recommendation

Remove the implicit `msg.sender`-as-recipient behavior from the fallback. Either:

1. **Remove the fallback entirely** and require callers to use `requestKLAYTransfer(address _to, ...)` where `_to` is always explicit.
2. **Revert in the fallback if `msg.sender` is a contract**, e.g.:
   ```solidity
   function () external payable {
       require(msg.sender == tx.origin, "contracts must use requestKLAYTransfer");
       _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
   }
   ```
3. **Add a `_to` parameter to the fallback** (not possible in Solidity 0.5.x for a true fallback, so option 1 or 2 is preferred).

---

### Proof of Concept

1. Alice's DAO uses a Gnosis Safe multisig at address `0xABCD...` on the service chain.
2. The DAO sends 100 KLAY to the `BridgeTransferKLAY` contract address directly (triggering the fallback).
3. The fallback calls `_requestKLAYTransfer(0xABCD..., feeOfKLAY, "")`, emitting `RequestValueTransfer` with `to = 0xABCD...`.
4. Bridge operators observe the event and call `handleKLAYTransfer(..., _to=0xABCD..., _value=100 KLAY)` on the parent chain bridge.
5. `(bool ok,) = 0xABCD....call.value(100 KLAY)("")` succeeds — KLAY is deposited at `0xABCD...` on the parent chain.
6. No Gnosis Safe exists at `0xABCD...` on the parent chain (different deployment history). The address is an empty account. Nobody holds the private key for `0xABCD...`. The 100 KLAY is permanently inaccessible.
