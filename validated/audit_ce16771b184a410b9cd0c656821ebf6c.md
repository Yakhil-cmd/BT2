### Title
Webhook signature verification binds to a different organization than the repository the payload's handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the `X-Hub-Signature` HMAC against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). However, the handlers that subsequently act on the verified payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, and `StatusHandler`) select the actual repository/commit target using a *different* field of the same payload: `payload.dig('repository', 'full_name')` for most handlers, or no repository scoping at all for `StatusHandler`. Nothing enforces that the organization used to select the verifying secret is the same organization whose repository/commits get written to.

### Finding Description
This is the same bug class as the TWAP report: a verification step covers one piece of state (`pastLiquidityWeights[i]`/`_totalLiquidityWeight` in the analog; here, the "verified organization") while a different piece of state that participates in the actual effect (`pastLiquidityEvaluation` in the analog; here, the repository actually written to) is populated independently and never checked for consistency with the verified value.

Concretely:
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` calls `Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and verifies the raw HMAC body against that org's configured `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) instead resolve the target via `payload.dig('repository', 'full_name')`, an entirely separate JSON field within the same payload that is never cross-checked against `repository.owner.login`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) is even weaker: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no repository scoping at all** — any commit sha across the entire Shipit instance matching `params.sha` gets a status created, regardless of which organization's secret was used to authenticate the request.

In a documented multi-tenant Shipit deployment (`docs/setup.md:181-216`, "Using Multiple Github Applications"), each GitHub organization is configured with its own `webhook_secret` known to whoever set up that org's GitHub App. An org owner/administrator for "org A" (an unprivileged party with respect to "org B") legitimately knows org A's `webhook_secret`. They can therefore produce a validly-signed webhook body (HMAC verified successfully because `verify_signature` picks org A's secret via `repository.owner.login: "orgA"`), while crafting `repository.full_name` (or, for status events, simply any `sha` value) to reference org B's stacks/commits, which they have no legitimate access to.

### Impact Explanation
This breaks the trust boundary `verified_organization == repository/commit acted upon`. Its most severe expression is via `StatusHandler`: an attacker who controls only their own org's webhook secret can forge a `status` webhook (signed with their own org's secret) with an arbitrary `sha` belonging to any other tenant's repository, causing `Commit#create_status_from_github!` to record an arbitrary CI status (e.g., forging a "success" status) for a commit they don't own. Since commit statuses commonly gate deployability/merge checks in Shipit, this can enable an unauthorized deploy or merge of an attacker-chosen commit in a victim's stack that they have no repository access to — matching the required Critical impact of "an unauthorized deploy, rollback or merge" via a broken authentication binding. `PushHandler`/`CheckSuiteHandler`/pull-request handlers are also reachable this way (their target repo is chosen from `repository.full_name`, unbound from the verified org), letting a same-instance but different-tenant attacker trigger `stack.sync_github`, unarchive review stacks, or refresh check runs against a target stack they don't own.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations, each with the engine's own app installed (a documented, supported configuration), and requires the attacker to be a legitimate administrator/owner of at least one such configured organization (so they know that org's `webhook_secret`) while targeting a different tenant's repository on the same instance — no access to the victim org's secret, GitHub token, or Shipit session is needed. This is a realistic scenario for shared/multi-tenant Shipit deployments.

### Recommendation
Bind the verified organization to the actual write target: in `WebhooksController#verify_signature`, derive `repository_owner` and pass it (or the verified org) down to the handler dispatch, and have `Shipit::Webhooks::Handlers::Handler#repository_name` (and `StatusHandler#process`) validate that `payload.dig('repository', 'owner', 'login')` matches `payload.dig('repository', 'full_name').split('/').first`, and additionally scope `StatusHandler`'s `Commit.where(sha: ...)` lookup to commits belonging to repositories owned by the verified organization, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit for two orgs per `docs/setup.md`'s multi-org setup: `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, has a Shipit stack tracking commit `abc123`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` — a signature they can legitimately produce since they own `orgA`'s app.
4. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and successfully verifies the signature.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) runs `Commit.where(sha: "abc123")`, finds the victim's commit belonging to `orgB`, and calls `create_status_from_github!`, forging a "success" status on a commit the attacker never had access to — potentially unlocking deploy/merge gating for that commit in `orgB`'s stack.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
