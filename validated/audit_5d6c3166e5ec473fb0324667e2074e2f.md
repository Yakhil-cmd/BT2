### Title
CCMenu client token is created without a `stack_id`, making it valid for reading ALL stacks instead of only the one the URL was generated for - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints (or reuses) a single `ApiClient` per user via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, and never sets `stack_id` on that record. Because `Api::BaseController#stacks` only restricts to a single stack when `current_api_client.stack_id?` is true, this client's token is unscoped and grants `read:stack` on every stack in the installation, not just the stack the URL was generated for.

### Finding Description
The intended binding is: `token(stack A) == token(stack A)` and `token(stack A) ≠ usable-for(stack B)`. In practice:

- `client` is looked up by `creator` + `name` only, with no `stack_id`, so a second call to `fetch` for stack B returns the *same* `ApiClient` record and thus the *same* `authentication_token` as stack A: [1](#0-0) 
- Even on the very first call, the created `ApiClient` has `stack_id: nil` because it is never assigned, only `permissions: %w[read:stack]` is set: [2](#0-1) 
- `Api::CCMenuController#show` authenticates via `ApiClient.authenticate(params[:token])`, which just looks the client up by id via a signed message verifier — no stack binding is checked: [3](#0-2)  and `app/models/shipit/api_client.rb` `authenticate`/`authentication_token`: [4](#0-3) 
- The scoping that should limit the client to one stack lives in `Api::BaseController#stacks`, but it only applies a restriction when `stack_id?` is true; since it's `nil`, the resolved scope is `Stack.all`: [5](#0-4) 
- `require_permission :read, :stack` only checks the `permissions` array (`read:stack`), which is global, not stack-specific: [6](#0-5) [7](#0-6) 

So the CCMenu URL/token generated for stack A — which is designed to be shared with external CI status tools (a low-privilege, narrowly-scoped credential) — actually authorizes reading `Api::CCMenuController#show` for any stack in the Shipit instance. Whoever obtains a stack-A CCMenu token (e.g., pasted into a public CI dashboard, a common CCMenu use case) can query stack B, C, ... freely by changing `stack_id` in the URL, since the token carries no stack restriction at all.

None of the listed guards catch this: `authenticate_api_client` only verifies the token signature/lookup succeeds, `require_permission!` only checks the generic `read:stack` string, and the `stacks` scope fails open to `Stack.all` when `stack_id` is blank.

### Impact Explanation
An attacker who obtains one CCMenu URL (these are explicitly meant to be handed to third-party tools/dashboards, i.e., treated as shareable) gains read access to the status/state (`show` renders deploy/task state) of every stack in the Shipit installation, not just the one the URL was labeled for. This is a cross-tenant/cross-repository authorization escalation: unauthenticated read of stack state for arbitrary stacks, matching the "High - unauthenticated read of stack state" impact category. It is fully repeatable — a single leaked token works against every `stack_id` forever (tokens don't expire) and the leak surface is compounded because every subsequent CCMenu fetch by that same user reuses the identical global token.

### Likelihood Explanation
- Preconditions: a legitimate Shipit user must at least once visit stack settings and generate a CCMenu URL (a completely ordinary, low-privilege workflow the feature is designed for — CCMenu URLs are meant to be embedded in external build-monitor tools).
- No Shipit secrets, GitHub credentials, or session are required by the attacker; only possession of the URL, which by design leaves the Shipit trust boundary (pasted into third-party CI dashboards, config files, etc.).
- Attacker cost is trivial: change `stack_id` in the query path of a captured/leaked CCMenu URL.
- Fully repeatable against every stack_id value in the deployment.

### Recommendation
Set `stack_id` explicitly when creating/looking up the CCMenu `ApiClient`, scoping both the lookup and the record to the requested stack, e.g. `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, and ensure the `stacks` scope in `Api::BaseController` (and any other consumer) treats `stack_id.present?` as authoritative rather than optional, so a client without a stack cannot silently fall back to `Stack.all`.

### Proof of Concept
Minitest plan (extends existing `test/controllers/ccmenu_controller_test.rb` / adds to `test/controllers/api/ccmenu_controller_test.rb`):

```ruby
test "ccmenu token minted for stack A also grants access to stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack fixture
  user = shipit_users(:walrus)

  session[:user_id] = user.id
  get :fetch, params: { stack_id: stack_a.to_param }
  token_a = Rack::Utils.parse_nested_query(URI(JSON.parse(response.body)['ccmenu_url']).query)['token']

  get :fetch, params: { stack_id: stack_b.to_param }
  token_b = Rack::Utils.parse_nested_query(URI(JSON.parse(response.body)['ccmenu_url']).query)['token']

  # BROKEN BINDING: token(stack A) should NOT equal token(stack B)
  assert_equal token_a, token_b

  # Exploit: stack-A token used against stack B's CCMenuController succeeds
  get :show, params: { stack_id: stack_b.to_param, token: token_a }
  assert_response :ok # should be :forbidden/:unauthorized if properly scoped
end
```

Both assertions currently pass (identical tokens, and stack-A token authorizes stack B), confirming the vulnerability; a fix scoping `ApiClient` to `stack` would make `token_a != token_b` and the cross-stack request return `:forbidden`/`:not_found`.
