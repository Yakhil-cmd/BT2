### Title
Cross-organization commit-status forgery bypasses CI gating and triggers unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to verify a webhook's HMAC using only `repository.owner.login` (or `organization.login`) taken from the unauthenticated JSON body, while the handler that actually mutates state (`StatusHandler`) looks up the target `Commit` by a **globally unscoped** `sha` lookup that never re-checks which organization/repository that commit belongs to. This breaks the binding: *"organization that authenticated" (repository.owner.login) == "repository that is written" (the stack/repository owning the commit whose status gets created)*.

### Finding Description
- `WebhooksController#verify_signature` derives the signing organization solely from the request body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then verifies the HMAC using `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 

- In a multi-org Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications" and `Shipit.github_app_config`), each organization has its **own independent** `webhook_secret`, all installed on the same Shipit instance. [2](#0-1) 

- The signature check only proves the request was signed by *some* organization's app that is configured on this Shipit instance — the org named in `repository.owner.login`. It does **not** constrain any other field of the payload (e.g. `sha`, `state`, `context`) to belong to that same organization's repositories.

- `StatusHandler#process` then updates **any** commit in the entire database whose sha matches the payload's `sha`, without checking that the commit's stack/repository belongs to the organization that was used to authenticate the request:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

- `Commit#create_status_from_github!` persists the forged status and, via `add_status`, emits `deployable_status`/`commit_status` hooks and can immediately trigger continuous delivery:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
```
and `deployable?` gates purely on the aggregated status state (`success? && !blocked?`), while `schedule_continuous_delivery` fires `ContinuousDeliveryJob` as soon as a commit becomes deployable. [4](#0-3) [5](#0-4) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated via HMAC (repository.owner.login in the signed body)` == `organization/repository owning the Commit row actually mutated (looked up only by global sha, no owner/stack scoping)`

Before the attacker's request: commit statuses for stack A's commits can only be set via events signed with stack A's/organization A's own webhook secret.
After the attacker's request: an attacker who legitimately owns and installs their own GitHub App/organization (org B) on the shared Shipit instance — and therefore legitimately knows org B's `webhook_secret` — can send a `status` event payload where `repository.owner.login = "org-B"` (so the HMAC check passes using org B's secret) but `sha` is set to a commit SHA that exists in a stack belonging to an entirely different, unauthorized organization (org A, whose repositories/commits happen to share that SHA value known to the attacker, e.g. through public commit history, forks, or SHA collision within Shipit's own DB across orgs tracking the same upstream repo). Because `StatusHandler` never re-validates the commit's owning repository against the authenticated organization, the forged status is applied to org A's commit.

### Impact Explanation
This is a High severity confused-deputy issue: unauthenticated-for-that-repository writes into the CI/status/deploy-gating state of a *different* organization's stack. `deployable?` and continuous-deployment scheduling rely purely on aggregated status/check-run state (`success? && !blocked?`), so an attacker with only their own (unrelated, but Shipit-configured) org's webhook secret can inject a fabricated "success" status for a target commit they don't control, potentially triggering `ContinuousDeliveryJob`/unlocking a merge or deploy gate (`stack.schedule_merges`) for a stack/repository they have no legitimate access to. This escalates read/write authorization across organizational trust boundaries that the webhook signature verification is supposed to enforce, matching the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Requires the target Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`, "Using Multiple Github Applications") and requires the attacker to control one of those organizations' GitHub App (which they can legitimately do, e.g. by being a real, unprivileged member/owner of one of the configured orgs) plus knowledge of a target commit SHA belonging to another tracked stack. This is a narrower precondition than a single-org deployment, so likelihood is Medium, but it requires no privileged Shipit account, `ApiClient` token, or `webhook_secret` leakage from the victim organization — only legitimate possession of one's own org's secret, which is exactly the scenario the per-organization signature verification is meant to isolate.

### Recommendation
Scope the effect of every inbound webhook to the organization that was actually used to verify its signature:
- In `StatusHandler` (and similarly in `PushHandler`, pull-request handlers, `CheckSuiteHandler`, `MembershipHandler`), restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` matches the authenticated `repository_owner` used in `WebhooksController#verify_signature`.
- Alternatively, pass the verified `repository_owner`/organization down from the controller into each handler and assert `params.dig('repository', 'owner', 'login') == verified_organization` (and that the resolved `Repository`/`Stack` actually belongs to that organization) before performing any mutation.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (multi-org config as documented).
2. Attacker legitimately controls `org-b`'s GitHub App and therefore knows `org-b`'s `webhook_secret`.
3. Shipit tracks a stack under `org-a` containing a commit with sha `SHA_TARGET` (known to the attacker, e.g. from a public fork/mirror or previously observed via the UI/API).
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "SHA_TARGET",
  "state": "success",
  "repository": { "owner": { "login": "org-b" } }
}
```
signed with `X-Hub-Signature: sha1=<HMAC-SHA1(org-b webhook_secret, raw_body)>`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-b"`, fetches `Shipit.github(organization: "org-b")`, and successfully verifies the signature using org B's own legitimately-known secret.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: "SHA_TARGET")` — matching the commit that actually belongs to `org-a`'s stack — and calls `create_status_from_github!`, injecting a forged `success` status into org A's commit, potentially unblocking `deployable?`/triggering `ContinuousDeliveryJob` for org A's stack, despite the attacker never having proven any relationship to org A.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
