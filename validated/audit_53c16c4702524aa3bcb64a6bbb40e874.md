### Title
Malicious swap route can add an unauthorized token transfer to the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` and other routed controller strategies accept opaque `swap` bytes and forward them to the configured router while authorizing only the controller’s exact input-token transfer. Because route pool addresses are not restricted, a malicious venue can execute during the strategy and append an unrelated `token.transfer(victim, attacker, amount)` invocation beneath the victim’s signed authorization tree. If the victim signs that tree, the attacker can drain unrelated wallet tokens while the trade still returns valid output. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` requires the caller to own or control the account, verifies the requested amount, and invokes `withdraw_and_swap_from_supply` with caller-controlled route bytes. [3](#0-2)  The swap helper authorizes an exact transfer from the controller to the configured router and then executes the supplied route. [4](#0-3) 

The route can place attacker-controlled pool code beneath the caller’s authorization. That code may invoke an unrelated token transfer from the caller to the attacker; Soroban records that transfer as a child invocation, and it succeeds when the caller signs the containing tree. [2](#0-1)  The regression test demonstrates a rogue pool transferring an unrelated wallet token from Alice to the attacker during `swap_collateral`. [5](#0-4) 

The controller’s measured input/output checks do not limit this side effect because they only compare the controller’s `token_in` and `token_out` balances. [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary unrelated tokens from the caller’s wallet by embedding the theft in a route the caller is induced to sign. The stolen amount is not bounded by `amount_in`, the route minimum output, or the account’s final risk checks. [7](#0-6)  The proof test records Alice’s complete unrelated-wallet balance moving to the attacker while her lending account receives the expected swap output. [8](#0-7) 

### Likelihood Explanation
The attack requires the victim to submit or sign a malicious route and its resulting authorization tree, so it is not a pure on-chain front-run of an already fixed transaction. It is nevertheless reachable by an unprivileged attacker through user-supplied route bytes, because pools are not allowlisted and the protocol’s threat model confirms that direct `execute_strategy` users have the same exposure. [2](#0-1) 

### Recommendation
Restrict route execution so venue code cannot introduce caller-scoped token transfers outside the exact authorized route payment. At minimum, enforce an allowlist or registry of trusted venue contracts for production routes and reject any authorization tree containing child invocations other than the expected input-token transfer. Client-side validation mitigates signing risk but does not remove the contract-level exposure. [2](#0-1) 

### Proof of Concept
1. Alice owns a funded account and calls `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`. [9](#0-8) 
2. The controller authorizes only its exact input transfer to the configured router and executes `malicious_route`. [4](#0-3) 
3. The route names an attacker-controlled pool; during the swap, that pool calls `unrelated_token.transfer(alice, attacker, alice_balance)`. [5](#0-4) 
4. Simulation attaches the unrelated transfer as a child of Alice’s `swap_collateral` authorization; signing that tree drains Alice’s unrelated wallet balance while preserving the expected strategy result. [8](#0-7)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization

caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
