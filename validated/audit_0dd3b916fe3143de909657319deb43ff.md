### Title
Cross-organization webhook signature confusion allows forging CI status / push events for a repository not owned by the authenticating organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report describes a Solidity bug where `Treasury.sol` grants an `approve` allowance to an address for X tokens right before a `safeTransfer` of X tokens, allowing the receiver to pull the same X tokens a second time via `transferFrom` — i.e. the amount that was *approved* diverges from what was actually *intended to move*, because the two operations are not bound together. The same class of bug — two related fields treated as if they were bound together when they are not — exists in `shipit-engine`'s webhook signature verification: the GitHub organization whose secret is used to **authenticate** the payload is read from one JSON field, while the repository whose data is actually **acted upon** is read from a different, unrelated JSON field inside the same attacker-controlled body.

### Finding Description
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login` as fallback): [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves that the raw body was signed with *some* configured organization's secret — it does not bind that organization to any other field of the payload: [3](#0-2) 

Once verified, `WebhooksController#create` dispatches the entire, attacker-controlled `params` hash to the event handlers: [4](#0-3) 

However, every handler determines *which repository/stack to act on* using a completely different field — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [5](#0-4) 

`Repository.from_github_repo_name` resolves this field to an actual DB `Stack` without any check that its owner matches the organization whose secret validated the signature: [6](#0-5) 

Because the whole raw HTTP body is attacker-controlled JSON before being signed, and any organization onboarded to the Shipit instance (with its own `github.<org>.webhook_secret` configured in `secrets.yml`) can compute a valid signature for arbitrary content, an attacker who controls organization `X` (a legitimate GitHub App installation on the same Shipit instance) can craft a payload where:
- `repository.owner.login = "X"` → selected for signature verification, verified successfully with `X`'s own known `webhook_secret`.
- `repository.full_name = "victim-org/victim-repo"` → used by the handler to resolve and mutate a `Stack` belonging to a completely different organization.

This breaks the intended binding: **organization authenticated (`repository.owner.login`) == repository written (`repository.full_name`)**. Before the attack these two fields are supposed to always refer to the same GitHub repository (as GitHub itself would set them); after the attacker's crafted request, they refer to two different organizations entirely.

### Impact Explanation
Concretely, `StatusHandler#process` forges a CI `Commit::Status` for any commit belonging to the victim stack, by matching on `sha` alone regardless of owning org: [7](#0-6) 

`PushHandler#process` similarly triggers `stack.sync_github(expected_head_sha:)` for any branch of the victim's stack: [8](#0-7) 

Forged commit statuses can satisfy `ci.require` checks used by Shipit to gate deploy eligibility and continuous deployment, which can result in an unauthorized deploy being triggered on the victim's stack — matching the Critical-tier impact category ("an unauthorized deploy") called out in the rules. This requires no GitHub write access to the victim repository, no Shipit API token, and no Shipit session; the attacker only needs their own GitHub org (or organization login value they control) to be one of the organizations configured in this Shipit instance's `secrets.yml`, which is a standard, unprivileged multi-tenant setup for shipit-engine.

### Likelihood Explanation
Any Shipit deployment that serves more than one GitHub organization (a documented, supported configuration — see `secrets.development.shopify.yml`/`docs/setup.md` multi-org examples) is affected. Any org admin who can install/configure their own GitHub App entry (and thus knows their own `webhook_secret`) is, by definition, an "unprivileged attacker" with respect to every *other* org's/repo's stacks tracked by the same instance. Because the request only needs to reach the public `WebhooksController#create` endpoint with a crafted JSON body and no authentication beyond the attacker's own known secret, exploitation is straightforward once this multi-tenant condition holds.

### Recommendation
Bind organization identity to the repository being mutated: after selecting the webhook secret via `repository_owner`, re-validate that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve the target `Stack`/`Repository` via a lookup scoped to the authenticated organization) before dispatching to handlers. Reject the webhook if the two do not match.

### Proof of Concept
1. Configure the Shipit instance with two organizations in `secrets.yml`: `org-attacker` (installed by the attacker, who knows its `webhook_secret`) and `org-victim` (a legitimate stack tracked by Shipit) — a standard multi-tenant setup per `docs/setup.md`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha that Shipit is tracking>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(org-attacker's webhook_secret, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `org-attacker`, loads `org-attacker`'s `webhook_secret`, and verification succeeds [1](#0-0) .
5. `StatusHandler` resolves the target repository via `repository.full_name = "org-victim/victim-repo"` and writes a forged, "successful" CI status onto the victim's commit, without the attacker having any relationship to `org-victim`'s GitHub App or repository [7](#0-6) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
