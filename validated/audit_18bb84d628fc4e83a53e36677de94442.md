### Title
Cross-stack/cross-repo status forgery via unscoped `Commit.where(sha:)` lookup — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by `sha`, with no constraint that the webhook's originating repository matches the `Stack`/repository that owns the matched `Commit` row. Because `sha` is only unique per `(sha, stack_id)` and not globally, a webhook legitimately signed for one tenant's repository can write a `Status` (with any `state`, including `error`) onto a `Commit` belonging to a completely different tenant's `Stack`, directly steering that victim stack's `Stack#trigger_continuous_delivery` decision (`should_resume_continuous_delivery?`/`should_delay_continuous_delivery?`).

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`repository_owner_of(webhook payload that signs the request) == repository_owner_of(stack that owns the Commit record being mutated)`.

Path:
- `app/controllers/shipit/webhooks_controller.rb:24-49` (`verify_signature`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the JSON body (`params.dig('repository','owner','login')`, `webhooks_controller.rb:59-62`). In a multi-org deployment (`lib/shipit.rb:170-200`, `github_app_config`), each organization has its own `webhook_secret`. This step only proves the request was correctly signed *for the organization named in the payload* — it proves nothing about which `Commit`/`Stack` the payload's `sha` will end up touching.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a global lookup across **every** `Stack` in the instance. `Commit` rows are only unique on `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not on `sha` alone, so multiple stacks (different repos, or the same repo tracked as multiple stacks/environments, or a fork sharing history with an upstream repo) can each have a `Commit` row with an identical `sha`.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) create the `Status` using `stack_id` taken from the matched `Commit` (`self.stack_id`), not from the payload's repository. There is no check anywhere in this chain comparing the payload's `repository.full_name`/owner to `commit.stack.github_repo_name`.
- The new `Status` immediately affects `commit.state`/`deployable?`/`deploy_failed?`, which feeds `Stack#should_resume_continuous_delivery?` / `#should_delay_continuous_delivery?` (`app/models/shipit/stack.rb:701-713`), consumed by `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`), run automatically from `ContinuousDeliveryJob#perform` (`app/jobs/shipit/continuous_delivery_job.rb`).

Exploit flow: an attacker who administers any repository/org registered as its own tenant in this multi-org Shipit instance (a normal, unprivileged position for that org's own repo — they are not a maintainer or operator of the *victim's* stack) sets up their repo so that one of its commits shares a `sha` with a commit already tracked on the victim stack (trivially achieved via a fork of the victim's repo, since forked commits retain identical SHA-1 hashes with their upstream, requiring no cryptographic collision). The attacker then posts a commit status against that shared `sha` on their own repo via the ordinary GitHub UI/API (an action entirely within their rights over their own repository). GitHub genuinely signs and delivers the resulting `status` webhook using the attacker's own org's `webhook_secret`, which `verify_signature` accepts because it only checks that the signature matches the org named in the payload — the attacker's own org. `StatusHandler#process` then matches the *victim's* `Commit` row (same `sha`, different `stack_id`) and writes a forged `Status` (e.g. `state: error`) into the victim's stack, flipping `commit.deployable?`/`deploy_failed?` and thus `should_resume_continuous_delivery?`/`should_delay_continuous_delivery?` for a tenant the attacker never authenticated against.

None of the existing guards catch this: `verify_signature` authenticates "the org in the payload," not "the org that owns the matched commit/stack"; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates field types/presence, not repository binding; `force_github_authentication`/`User#authorized?`/`require_permission!`/`stacks` scope are irrelevant to webhook ingestion, which is unauthenticated by user session by design.

### Impact Explanation
A forged status from one tenant's own (legitimately owned) repository writes a `Status` record — and therefore alters CI/deploy-worthiness (`deployable?`, `deploy_failed?`) — for a `Commit` belonging to a different tenant's `Stack`. This can mask a real regression (forging `success`/resuming CD) or block/delay a legitimate deploy (forging `error`) on a victim stack, i.e. "a payload for one repository mutating another's stack/commit," matching the Critical category verbatim. It is repeatable against any victim stack for which the attacker can produce (or already possesses, via forking) a colliding `sha`, and scales across all tenants sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) attacker legitimately administers at least one repo/org tenant on the same multi-org Shipit instance (a normal condition for public/shared Shipit deployments, and per the question's own precondition "colliding sha reachable by attacker"); (2) a `sha` collision between attacker's repo and the victim stack's commit history — trivially satisfied by forking the victim's repository, no brute-forcing needed since forks share commit objects verbatim; (3) victim stack has `continuous_deployment: true`. No secrets, tokens, or privileged Shipit roles are needed beyond ordinary control of one's own GitHub repository plus (already-satisfied) tenant registration. Cost is low and the attack is repeatable at will.

### Recommendation
Scope the `StatusHandler` (and equivalently `check_suite`/check-run handlers) lookup to commits whose owning `Stack#github_repo_name` matches the webhook's `repository.full_name`/`repository.owner.login`, e.g. `Commit.where(sha: params.sha).joins(:stack).where(stack: { repository_owner: ..., repository_name: ... })`, rejecting or ignoring statuses whose repository does not match the stack that owns the candidate commit, instead of matching by `sha` alone across all tenants.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar):
```ruby
test "a status webhook from repo A must not mutate a commit belonging to stack B (different repo)" do
  victim_stack = shipit_stacks(:shipit)          # tracks victim/repo
  attacker_stack = shipit_stacks(:cyclimse)       # tracks attacker/other-repo, different repository_owner
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  before = victim_stack.should_resume_continuous_delivery?(victim_commit)  # baseline (equality LHS)
  # Attacker's own org sends a legitimately-signed status webhook for its own repo, but same sha
  Shipit::Webhooks::Handlers::StatusHandler.call(
    "sha" => shared_sha, "state" => "error",
    "repository" => { "owner" => { "login" => attacker_stack.repository_owner }, "full_name" => attacker_stack.github_repo_name }
  )

  victim_commit.reload
  after = victim_stack.should_resume_continuous_delivery?(victim_commit)   # actual RHS after forged webhook

  # Binding claims before == after (victim's decision unaffected by attacker's repo); assert it does not hold:
  refute_equal before, after
  assert_equal "error", victim_commit.status.state  # victim commit mutated by attacker's own-repo webhook
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
