### Title
Position NFT can be permanently frozen by transferring it to a contract that cannot authorize operations - (File: contracts/position-nft/src/contract.rs)

### Summary
`PositionNft` exposes the stock OpenZeppelin `transfer` / `transfer_from` entrypoints, which reassign `Owner(token_id)` to any `to` address with only the sender's authorization. On Soroban there is no receiver-capability check (no `onERC721Received` analogue and no `safe_transfer` variant): the destination is never asked to prove it can act. Because the token *is* the controller account (`account_id == token_id`, ownership resolved live via `owner_of`), sending it to a contract that cannot produce `require_auth` and cannot itself invoke `transfer` permanently locks the entire lending position — collateral, debt, and any accrued yield — with no rescue path.

### Finding Description
The OpenZeppelin `NonFungibleToken` implementation exported at `contract.rs:131-133` provides `transfer(from, to, token_id)` and `transfer_from(spender, from, to, token_id)`. Both only call `from.require_auth()` (or the spender's approval path); `to` is written verbatim into `NFTStorageKey::Owner(token_id)` by `Base::update`. Nothing validates that `to` is an address that can ever authorize a subsequent `transfer`, an `approve`, or any controller call.

The controller stores no owner cache: every owner-gated verb (`supply`, `borrow`, `withdraw`, `repay`, `migrate_from_blend`, `claim_revenue`, `update_account_threshold`, delegation, account deletion) resolves authority through `try_account_owner` → `owner_of(account_id)` and then requires that address's auth (`contracts/position-nft/README.md:5,29`). An account whose NFT sits on a contract without `__check_auth` — or on a contract that can sign but has no code path invoking `PositionNft::transfer` or the controller — can never authenticate again. `burn` is also unreachable because it is controller-only and is only invoked on account deletion flows that themselves require the owner (`contract.rs:88-95`).

This is the same class as the referenced `FootiumClub.safeMint` finding: a "normal-looking" token movement can strand the underlying asset on an incapable contract. Here it is strictly worse than an inert collectible — the NFT carries live collateral and debt.

### Impact Explanation
Permanent freezing of user funds. All collateral shares and any claimable revenue attached to the account become unreachable forever; the debt remains on the account, still accruing interest, and the position can still be liquidated by third parties while the "owner" contract can do nothing. No privileged or unprivileged recovery exists (`burn` cannot be reached without an owner-authorized emptying flow). This matches the accepted-impact category "permanent freezing of funds."

### Likelihood Explanation
Reachable by any unprivileged token holder or approved operator through `transfer`/`transfer_from` — both listed as standard entrypoints in the protocol's own interface (`contracts/position-nft/README.md:56-60`, exercised in `tests/integration/flows/nft.sh:33,45`). Triggering conditions are realistic rather than exotic: an approved marketplace/router contract that escrow-pulls the NFT via `transfer_from` but lacks a withdrawal path, a user who sets a multisig/smart-wallet or SAC address as recipient, or a flash-receiver/contract account transferring the token onward mid-callback (a flow the codebase itself supports, `tests/test-harness/tests/strategy/flash_position_callback_ownership_transfer.rs`). It requires a user/operator mistake in choosing `to`, but the protocol offers no guard against the most common version of that mistake, which is exactly why the ERC-721 `safeTransfer`/`_safeMint` convention exists.

### Recommendation
Add an allowlist or capability check on the receiving side, e.g.:

- Reject `transfer`/`transfer_from` when `to` is a contract address that is not a recognized position-aware contract (the pool, the controller, audited routers), or
- Provide a `safe_transfer` that invokes a receiver callback (`on_nft_received`-style interface) on `to` when `to` is a contract, reverting if the callback fails or returns an unexpected value, matching the spirit of ERC-721 `_checkOnERC721Received`.

At minimum, document the irreversibility and consider a controller-side rescue verb (governance-timelocked `force_transfer`) so a provably-bricked account is recoverable.

### Proof of Concept
Conceptual Soroban invocation sequence:

1. Alice supplies 10,000 USDC, creating `account_id = 7`; `PositionNft` mints token 7 to Alice (`controller.supply(caller=alice, account_id=0, ...)` → `PositionNft::mint`).
2. Alice (or an operator she approved via `approve`/`approve_for_all`) calls:
   `PositionNft::transfer(from=alice, to=<pool_contract or any contract without __check_auth/transfer path>, token_id=7)`.
   The call succeeds — only `from` auth is checked (`Base::update` in the OZ base, exported via `NonFungibleToken` at `contract.rs:131`).
3. `owner_of(7)` now returns the contract. Every subsequent `withdraw`, `repay`, `borrow`, `claim_revenue`, and even `PositionNft::transfer`/`approve` requires that contract's `require_auth`; a contract without `__check_auth` can never satisfy it, and even one with `__check_auth` can only act if its code contains a path that invokes these entrypoints.
4. Result: the 10,000 USDC collateral is permanently frozen; token 7 can never be moved, approved, or burned (burn needs the controller path that itself needs owner-authorized emptying). Debt continues accruing and the account remains liquidatable by anyone, payable to nobody reachable.
