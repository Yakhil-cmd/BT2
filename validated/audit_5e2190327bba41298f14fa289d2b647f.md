## Title
`in_data_feed`/`data_feed` oscript checks trust unstable AA data-feed units without verifying `sequence==='good'` - ([File: data_feeds.js])

### Summary
The Shopify report describes a gating condition (email confirmation) that is enforced in one code path but silently skipped in another path that consumes a token/reference produced by the first. The closest analog reachable by an unprivileged unit poster in ocore is in `dataFeeds.dataFeedExists()` [1](#0-0) , which is used to evaluate the `in data feed` / `in_data_feed` oscript conditions inside AA definitions and AA triggers [2](#0-1) [3](#0-2) . For the `bAA` branch, the function scans `storage.assocUnstableMessages`/`assocUnstableUnits` for a matching oracle data-feed message and returns `true` as soon as it finds a value match, filtering only on `latest_included_mc_index` and author address, but never checking `objUnit.sequence === 'good'`.

### Finding Description
Compare the two consumers of unstable data feeds:
- `readDataFeedValue()` (used for the `data_feed[...]` formula, i.e. reading a value) explicitly excludes non-good units: `if (objUnit.sequence !== 'good') continue;` [4](#0-3) .
- `dataFeedExists()` (used for the boolean `in_data_feed`/`in data feed` condition, which gates AA branching and address-definition authentication) has no such check in its `bAA` fast-path loop over unstable messages [5](#0-4) .

An oracle-posting (or any) unit that is temporarily included in the DAG but is on a losing/conflicting serial path (`sequence` = `temp-bad`, and ultimately possibly `final-bad`) is still visible in `storage.assocUnstableMessages` before stabilization. Because `dataFeedExists()` does not filter by `sequence`, an `in_data_feed` condition evaluated while the AA trigger is processed against still-unstable data (`bIncludeUnstableAAs`-style usage) can be satisfied by a data-feed message that will *never* become part of the finally accepted, "good" version of history — analogous to the Shopify flaw where an action (store creation) was permitted using state (an access token) that had not actually passed the required confirmation gate (email verification / sequence resolution).

### Impact Explanation
An AA whose logic branches on `in_data_feed` (e.g., "release funds only if oracle confirms X") could execute the funds-releasing branch based on a data-feed unit that subsequently resolves to `temp-bad`/`final-bad` and is discarded from the canonical history. Because AA execution is deterministic and part of consensus, if this bug causes different bots/nodes to observe different unstable states at trigger-processing time (e.g., depending on when exactly the trigger fires relative to the conflicting unit's own resolution), it can lead to nodes disagreeing on the AA's response unit and its outputs, or to release of AA-held funds under a condition that was never actually confirmed by an honest, sequence-valid oracle post. This falls under "AA fund loss/freezing" and "node disagreement on validity," matching the required Medium+ impact classes.

### Likelihood Explanation
Reachability requires only that an attacker (or a compromised/faulty oracle) posts a conflicting/double-spending data-feed unit from an oracle address that an AA already trusts, timed so that the unit is still unstable (`sequence` not yet resolved to bad) when the AA trigger evaluates `in_data_feed`. This is achievable by any unprivileged unit poster racing units against an oracle's normal data feed post, without needing any special privilege — the same posture as the external report's "unconfirmed user still reaching a privileged flow."

### Recommendation
Add the same `objUnit.sequence !== 'good'` filter used in `readDataFeedValue()` to the `bAA` fast-path loop in `dataFeedExists()`, ensuring `in_data_feed`/`in data feed` conditions only match unstable data-feed units that are on the currently winning ("good") sequence, consistent with how the value-reading counterpart already behaves.

### Proof of Concept
1. Deploy an AA with logic such as `if (in_data_feed[[oracles=$oracle, feed_name='approved', feed_value=1]]) { ... release funds ... }`.
2. Post two conflicting units both authored by `$oracle` in quick succession (double-spending some other input) — one containing `data_feed: {approved: 1}` and one not, so that one of them will resolve to `sequence='temp-bad'`/`final-bad`.
3. Trigger the AA while both units are still unstable and included via `latest_included_mc_index` within `[min_mci, max_mci]`.
4. `dataFeedExists()`'s `bAA` branch iterates `storage.assocUnstableMessages`, finds the `approved:1` message regardless of which of the two conflicting units it belongs to or whether that unit will ultimately be `good`, and returns `true`, causing the AA to release funds even though the oracle's approving unit may later be discarded as non-serial.

*Note: I was not able to fully trace every call site that sets `bIncludeUnstableAAs`/passes `bAA=true` into `dataFeedExists` (as opposed to `readDataFeedValue`) within `aa_composer.js` in the available index, so the exact trigger-time conditions under which `dataFeedExists`'s unstable-message fast path executes for a real AA trigger could not be fully confirmed from the indexed files; a full code review of `aa_composer.js` would be needed to verify the precise call path and timing window.*
