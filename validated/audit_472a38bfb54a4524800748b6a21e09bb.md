## Title
Webhook signature is verified against one GitHub organization while the state-changing action is performed against an unrelated repository named in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
The bug report describes a Deriverse binding failure where the value that determines execution (fallback slippage cap) is disconnected from the value the user actually authorized/expects. The analogous binding failure in Shipit is that `WebhooksController#verify_signature` selects *which* GitHub organization's `webhook_secret` to check the HMAC against using one payload field, while the actual database records mutated by the resulting handler are selected using a *different, independently attacker-controlled* field of the same payload. Nothing enforces that the two fields are consistent.

## Finding Description
`WebhooksController#verify_signature` derives the organization used for HMAC verification purely from the payload itself: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up the `webhook_secret` configured for that organization name and verifies `X-Hub-Signature` against the raw POST body using that secret [3](#0-2) .

Once the signature check passes, the event is dispatched to handlers that resolve the target repository/stack from a *different* JSON field, `repository.full_name`, with no re-check that it belongs to the organization used for verification: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits the string on `/` and looks up by owner/name with no cross-check against the signing organization: [6](#0-5) 

Because the whole raw body is HMAC-signed, the signature is cryptographically valid for whatever bytes are sent — but the protocol never establishes that `repository.owner.login` (or `organization.login`) must match the owner prefix of `repository.full_name`. Any party who legitimately holds a `webhook_secret` for **some** organization configured in `secrets.yml` (i.e., they administer their own low-privilege GitHub App/organization integrated with this Shipit instance) can craft an arbitrary payload where:
- `repository.owner.login` (or `organization.login`) = their own org (used only to pick which secret verifies the signature)
- `repository.full_name` = `"other-org/other-repo"` (used by the handler to select the actual `Stack`/`Repository` records to mutate)

This breaks the binding: *organization that authenticated (signs) the request* ≠ *repository whose stacks are written by `shipit.yml`/handler logic*.

## Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the forged `branch`/repository [5](#0-4) . Other handlers (`pull_request/*`, `status`, `check_suite`) similarly resolve `Repository`/`Stack`/`PullRequest` records purely from `repository.full_name` inside the same signed-but-uncorrelated payload, letting an attacker who controls one organization's webhook secret trigger sync/refresh/archive/unarchive state transitions on stacks belonging to a completely unrelated, higher-privilege repository they do not own — an authentication-binding bypass across repository/organization boundaries. This is a legitimate cross-repository "write" in the sense the rules define (state mutation such as forced re-sync, archiving/unarchiving review stacks, spurious commit statuses) performed against a repository the caller was never authorized to act on.

## Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for *some* organization configured on the instance — a realistic scenario for any multi-tenant or multi-org Shipit deployment (Shopify's own README documents per-organization `github.<org>.webhook_secret` entries), since organizations self-manage their own GitHub App webhook secret. No repository write access, GitHub App private key, or Shipit session/API token is required — only knowledge of one org's own webhook secret, which by design is meant to scope that org to its *own* repositories only.

## Recommendation
After verifying the HMAC signature, additionally verify that `repository.owner.login` (or `organization.login`) used to select the signing secret matches the owner segment of every repository reference acted on in the payload (e.g., `repository.full_name`) before dispatching to handlers. Reject the webhook (422) if they diverge.

## Proof of Concept
1. Configure `secrets.yml` with two orgs: `attacker-org` (webhook_secret known to the attacker, who administers it) and `victim-org` (a real, separate customer of the same Shipit instance).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-fake-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` and sends it as `X-Hub-Signature`, `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s secret, and the HMAC matches — request is accepted.
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: <attacker-chosen-fake-sha>)` on `victim-org`'s stacks — a state-changing action against a repository the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
