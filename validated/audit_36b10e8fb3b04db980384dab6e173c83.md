Found the critical mismatch: `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` — a field taken from the *unverified* raw payload, before the signature has been checked. The handlers, however (`Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`), locate the target `Repository`/`Stack` using a *different* payload field: `payload.dig('repository', 'full_name')`. Because `login` and `full_name` are independent, attacker-controlled strings in the same unsigned JSON body, an attacker can craft a payload where `repository.owner.login` names an org whose GitHub App has no `webhook_secret` configured (or one the attacker knows), while `repository.full_name` names a completely different org/repo that *does* have a secret and real stacks. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, so the signature check trivially passes for the org used to select the secret, yet the handler acts on the unrelated `full_name` target.

### Title
Webhook signature is verified against an organization derived from an unsigned payload field that differs from the field used to select the target repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to validate against using `params.dig('repository','owner','login')`, taken straight from the untrusted, not-yet-verified request body. All webhook handlers instead resolve the actual `Stack`/`Repository` to mutate using `payload.dig('repository','full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`). These two fields are never checked for consistency, and both come from the same attacker-supplied JSON before any cryptographic check occurs.

### Finding Description
`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` comes from the request body itself:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) short-circuits to `true` if that org's `webhook_secret` is blank. Meanwhile, every concrete handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc., via `Handler#stacks`/`Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves the mutated `Repository`/`Stack` from a *separate* field, `repository.full_name`. The binding the code implicitly assumes — "the org whose secret authenticated this request == the repo/org whose state is written" — is never enforced. Because both `repository.owner.login` and `repository.full_name` are attacker-controlled plaintext in the same unsigned body, an attacker can set `repository.owner.login` to any organization configured in `secrets.yml` with no `webhook_secret` (common in dev/staging configs, e.g. `test/dummy/config/secrets_double_github_app.yml` shows `webhook_secret: # nil` as a normal configuration shape) while setting `repository.full_name` to a fully different, secret-protected production org/repo. Signature verification trivially passes (secret blank ⇒ `true`), yet the handler that runs afterwards acts on the victim repository named in `full_name`.

### Impact Explanation
This breaks the authentication boundary of the webhook endpoint: an unauthenticated external caller can make Shipit act as if a legitimate signed GitHub webhook arrived for a protected repository's stack, by "borrowing" the identity of any less-protected/unconfigured organization known to the same Shipit instance. Depending on which handler event is sent, this enables state changes normally gated on GitHub-signed events for a repo the attacker does not control — e.g. `push` events trigger `Stack#sync_github`, and `status`/`check_suite` events feed into commit deployability/CI-gate state (`StatusHandler#process`, `CheckSuiteHandler`) that downstream code uses to decide whether a commit is safe to deploy. Forging these can manipulate the deployability signal used before an actual deploy is triggered by a legitimate user, which is a step in the "unauthorized deploy" trust chain (CI status is meant to gate deploys).

### Likelihood Explanation
Exploitation requires the attacker to know: (a) the routing endpoint (unauthenticated, public POST), (b) that some organization configured in the same Shipit deployment has `webhook_secret` unset or known, and (c) the target repo's `full_name`/branch. No GitHub credentials, ApiClient token, or repository write access are required — only knowledge of two org names, both discoverable from the Shipit instance itself (organization names appear in stack URLs) or a common convention such as leaving a rarely-used org unconfigured. This is a realistic multi-tenant misconfiguration risk rather than a purely theoretical one, since Shipit explicitly supports multiple GitHub orgs (`Shipit.github(organization:)`) sharing one webhook endpoint.

### Recommendation
Verify the webhook signature using the same repository/org context that the corresponding `Handler` will use to select the target (`repository.full_name`, not `repository.owner.login`), or better, validate that `repository.owner.login` is consistent with `repository.full_name`'s owner segment before using it to pick the signing secret. Additionally, do not treat a blank `webhook_secret` as an implicit "always verified" bypass for multi-tenant installations — require every configured organization used in production to have a non-blank secret, and fail closed (422) instead of `true` when a secret is missing for organizations known to host real stacks.

### Proof of Concept
1. Configure two orgs in `secrets.yml`: `AttackerOrg` (no `webhook_secret`) and `VictimOrg` (has a real, secret-protected `Stack` `victim-repo`, branch `main`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the real victim stack — despite the request never being signed by `VictimOrg`'s actual GitHub webhook secret.
