## Finding

### Title
Webhook signature verified against attacker-controlled organization while payload processing acts on an unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check the `X-Hub-Signature` against using an org name pulled from the raw JSON body itself (`repository.owner.login` or `organization.login`), while the actual event processing that follows resolves and mutates a completely different field of the same body (`repository.full_name`) to find the `Repository`/`Stack` to act on. Nothing binds these two fields together, so a request can be signed for one organization but processed against another organization's repository.

### Finding Description
`verify_signature` derives the organization used to pick the webhook secret purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

That organization name is fed into `Shipit.github(organization:)`, which (in multi-org mode) looks up a per-organization `webhook_secret` and calls `verify_webhook_signature(signature, raw_post)` — an HMAC check keyed to that secret: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` re-parses the same raw body and dispatches it to the event handler: [5](#0-4) 

`PushHandler` (and the base `Handler`) then resolve the target `Repository`/`Stack` using a *different* field of the body, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository/stack) are independent, unconstrained strings inside the same attacker-controlled JSON body, an operator of **their own** onboarded organization in a multi-organization Shipit deployment — who legitimately knows their own org's `webhook_secret` — can craft a payload where:
- `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) so `verify_signature` picks the secret they know and the HMAC check passes, and
- `repository.full_name = "victim-org/victim-repo"` so `PushHandler#stacks` resolves to a `Stack` belonging to a completely different, victim organization they have no relationship with.

This breaks the exact binding called out by the report's bug class: *"an organization that authenticated versus the repository that is written."* The equality that should hold — `organization-that-signed == organization-that-owns-the-mutated-repository` — is never checked anywhere in this flow.

### Impact Explanation
A forged push notification against an arbitrary victim `Stack` causes `Stack#sync_github` to enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha`: [8](#0-7) 
This forces an out-of-band sync/fetch of commits for a stack the attacker's organization has no legitimate relationship with. In a Shipit deployment with continuous deployment enabled on the victim stack, an unsolicited sync of new commits is exactly the trigger that starts an automatic deploy — meaning an attacker with no access to the victim repository or organization can force an unauthorized deploy cycle on it, satisfying the Critical "unauthorized deploy" bar. Even absent continuous deployment, this is at minimum a cross-tenant authorization boundary break: a signature scoped to organization A is being treated as authorization to mutate organization B's stack state.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately control one organization's GitHub App webhook secret in a multi-organization Shipit instance (the documented "Using Multiple Github Applications" setup) — no access to the victim org, its GitHub App, or its GitHub repository is needed. Both `repository.owner.login`/`organization.login` and `repository.full_name` are fully attacker-controlled body fields with no cross-validation, so crafting the mismatched payload is trivial once a valid secret for any org on the instance is known.

### Recommendation
After signature verification succeeds for organization `O`, require that the `Repository` resolved during event processing (`repository.full_name`'s owner segment) equals `O`, and reject the webhook otherwise. Alternatively, derive the repository/stack lookup itself from the same value used for signature-secret selection instead of a separately-parsed field.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `attacker-org` and `victim-org` both onboarded (each with its own GitHub App/`webhook_secret`), per `docs/setup.md`'s "Using Multiple Github Applications" section.
2. As the administrator of `attacker-org` (who legitimately knows only `attacker-org`'s `webhook_secret`), build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<arbitrary_sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s secret, and the signature verifies successfully.
5. `create` re-parses the body and `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")`, enqueuing `GithubSyncJob` against the victim's stack — despite the request never being signed by `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
