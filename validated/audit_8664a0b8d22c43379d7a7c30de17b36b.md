### Title
Signature verified against `repository.owner.login`'s org while the mutated stack is resolved from `repository.full_name` of a different org - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which org's `webhook_secret` to check the HMAC against using `repository_owner` (`params.dig('repository','owner','login')`), but `UnlabeledHandler#repository` resolves the actual `Shipit::Repository` (and thus the stack to archive/unarchive) via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. These two values are never checked for equality, so an attacker who controls a repo in an org configured with no `webhook_secret` (or a secret they know) can forge `repository.owner.login` to that org while setting `repository.full_name` to point at an entirely different, victim-owned repository/stack.

### Finding Description
The broken invariant, stated as an equality that must hold but doesn't:
`params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`

Neither `verify_signature` nor `UnlabeledHandler` enforces this.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`. `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) reads only `params.dig('repository', 'owner', 'login')`.
2. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` — i.e., if the selected org has no `webhook_secret` configured, *any* payload passes verification with no signature check at all. Even if it has a secret, the attacker (owning that org's repo) knows it and can compute a valid HMAC themselves.
3. Once the request passes `verify_signature`, `Shipit::Webhooks.for_event('pull_request')` dispatches to `UnlabeledHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb:41-45`), which never re-derives or checks `repository_owner`. Its `#repository` method (lines 59-63) instead does `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — resolving strictly from `full_name`, a value the attacker also fully controls in the JSON body.
4. `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) does a straight `find_by(owner:, name:)` lookup — it has no relation to whichever org authenticated the webhook.
5. `#stack` then builds a `ReviewStackAdapter` scoped to `repository.review_stacks` and calls `archive!`/`unarchive!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:23-50`), which mutate the victim repo's review stack — `stack.archive!`/`unarchive!` run with `user = Shipit::User.find_or_create_by_login!(params.sender['login'])`, itself attacker-controlled, and archiving/unarchiving triggers `deprovision`/re-provisioning via `Shipit::ReviewStackProvisioningQueue`, which drives deploy automation using the stack's configured `Shipit.user`/`bot_login` identity per the victim stack's Shipit config.

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "unlabeled",
  "number": 1,
  "pull_request": { ... "state": "open", "head": {"sha":"...", "ref":"attacker-branch"}, "user": {"login":"attacker"}, "assignees": [], "labels": [] },
  "repository": { "owner": {"login": "attacker-org-with-no-secret"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
No `X-Hub-Signature` is even needed if `attacker-org-with-no-secret` has no `webhook_secret` configured — `verify_webhook_signature` short-circuits to `true`.

Existing guards checked and found insufficient:
- `verify_signature` only authenticates that *some* configured org's secret matches; it never ties that org to the repository actually mutated.
- `drop_unhandled_event` only checks the event type is registered, not repository ownership.
- The `ExplicitParameters` schema (`params do ... end` in `UnlabeledHandler`) only validates shape/types of `repository.full_name`, `sender.login`, etc., not that they match `repository.owner.login`.
- `Repository.from_github_repo_name` and the `review_stacks` scope have no cross-check against the authenticating org.
- `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are all controller/API concerns for the authenticated web/API surface and are not invoked on this unauthenticated webhook path at all.

### Impact Explanation
An attacker who owns/controls any GitHub org (or repo) that is either configured in Shipit with no `webhook_secret`, or whose secret they know because they control the repo emitting the webhook, can forge a `pull_request`/`unlabeled` event that archives or unarchives an arbitrary victim review stack in a completely unrelated org's repository. Archiving deprovisions the stack (destructive); unarchiving re-queues provisioning, which runs deploy/provisioning tasks under the stack's configured bot identity (`Shipit.user`/`bot_login`) — i.e., a payload from one repository mutates and drives deploy automation for another repository's stack, which is one of the explicitly listed Critical categories ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). It is repeatable against any victim repository/stack whose owner/full_name the attacker knows, as many times as desired, from any org with a laxly-configured or attacker-known webhook secret.

### Likelihood Explanation
Preconditions: Shipit must be configured with the multi-org `github` schema (`github_app_config`/`github_organizations`) containing at least one org with no `webhook_secret` set (or one the attacker can otherwise learn, e.g., by owning that org and setting it themselves in a mixed single-tenant-per-org deployment), and a victim repository with `review_stacks_enabled` and a review stack for a matching `pr#{number}` environment. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body — no GitHub session, no Shipit account, no valid signature for the *victim* org is required. This is highly feasible and trivially repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler` base class), after resolving the repository from `params.repository.full_name`, assert that the resolved `Repository#owner` equals the `repository_owner` used to select the signing org, and reject (422) on mismatch. Alternatively, always resolve the target `Repository`/org from `full_name` first and use that same value both to pick the webhook secret and to load the stack, eliminating the two independent lookups.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.stubs(:secrets).returns` (or credentials fixture) with two orgs: `"attacker-org"` (no `webhook_secret`) and `"victim-org"` (with a `webhook_secret` the test never uses for signing).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_with_label")`.
3. Create a `Shipit::ReviewStack` for `victim_repo` with `environment: "pr1"`, unarchived, and assert `stack.archived? == false` (state before).
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body: `action: "unlabeled"`, `number: 1`, `pull_request.state: "open"`, `pull_request.labels: []`, `repository: {owner: {login: "attacker-org"}, full_name: "victim-org/victim-repo"}`, `sender.login: "attacker"`.
5. Assert response is `200`.
6. Reload the review stack and assert `stack.archived? == true` (state after) — proving a request "authenticated" via `attacker-org`'s (absent) secret archived `victim-org/victim-repo`'s review stack, violating `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`.
