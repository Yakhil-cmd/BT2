### Title
Missing Registered-Token Validation in `handleERC20Transfer` / `handleERC721Transfer` Allows Operators to Mint or Drain Arbitrary Tokens — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC20Transfer` and `handleERC721Transfer` in the Kaia service-chain bridge contracts accept a caller-supplied `_tokenAddress` without verifying it against the bridge's `registeredTokens` mapping. The outbound path (`_requestERC20Transfer` / `_requestERC721Transfer`) enforces `onlyRegisteredToken(_tokenAddress)`, but the inbound handle path carries no equivalent guard. A threshold of operators can therefore invoke the handle functions with any token address, causing the bridge to mint tokens from an unregistered contract (in `modeMintBurn` mode) or to transfer any ERC-20/ERC-721 tokens the bridge contract holds (in lock-and-release mode).

---

### Finding Description

`_requestERC20Transfer` (the outbound deposit path) is decorated with `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

`handleERC20Transfer` (the inbound settlement path) carries only `onlyOperators` and performs no token-registration check before executing the transfer or mint: [2](#0-1) 

The same asymmetry exists in `handleERC721Transfer`: [3](#0-2) 

The `registeredTokens` mapping is the on-chain source of truth that pairs a local token with its counterpart: [4](#0-3) 

The Go relay layer (`handleRequestValueTransferEvent`) does look up the counterpart token before calling `HandleERC20Transfer`, but this is an off-chain check that is not enforced by the contract itself: [5](#0-4) 

Any operator (or a set of operators meeting the configured threshold) can bypass the off-chain relay entirely and call `handleERC20Transfer` directly on-chain with an arbitrary `_tokenAddress`.

---

### Impact Explanation

**`modeMintBurn = true` (mint-and-burn bridges):**  
The bridge calls `ERC20Mintable(_tokenAddress).mint(_to, _value)` on the caller-supplied address. [6](#0-5) 
If the bridge has been granted the minter role on any token contract beyond the registered set (e.g., a second token that shares the same bridge for operational reasons, or a token whose minter role was not revoked after deregistration), operators can mint an unbounded amount of that token to any recipient.

**`modeMintBurn = false` (lock-and-release bridges):**  
The bridge calls `IERC20(_tokenAddress).safeTransfer(_to, _value)` on the caller-supplied address. [7](#0-6) 
Any ERC-20 balance held by the bridge contract — including tokens accidentally sent to it, previously deregistered tokens whose liquidity was not withdrawn, or KAIA-wrapped tokens — can be drained to an arbitrary address.

The same logic applies to `handleERC721Transfer` for NFT assets.

---

### Likelihood Explanation

Operators are semi-trusted automated relayers registered by the bridge owner. The threshold voting mechanism (`_voteValueTransfer`) requires multiple operators to agree, but it does not validate the token address — it only tracks whether a given nonce has been voted on: [8](#0-7) 

A single compromised operator key (if threshold = 1) or a colluding subset of operators (if threshold > 1) can exploit this without any user interaction. The operator set is small and fixed, making key compromise a realistic threat model for a bridge holding significant value.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guard already present on the outbound path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // <-- add this
{
    ...
}
```

Apply the same fix to `handleERC721Transfer`.

---

### Proof of Concept

1. Deploy a bridge in `modeMintBurn = true` mode with token `A` registered.
2. Deploy a second token `B` and grant the bridge its minter role (a realistic scenario when a token is deregistered but the minter role is not revoked, or when a second token shares the same bridge).
3. As an operator (threshold = 1), call:
   ```solidity
   bridge.handleERC20Transfer(
       bytes32(0),          // fake requestTxHash
       address(0),          // from
       attacker,            // to
       address(tokenB),     // _tokenAddress — NOT registered
       1_000_000e18,        // _value
       999,                 // fresh nonce
       0,
       ""
   );
   ```
4. `tokenB.mint(attacker, 1_000_000e18)` executes successfully because `handleERC20Transfer` never checks `registeredTokens[tokenB]`.
5. The attacker receives 1,000,000 `tokenB` tokens with no corresponding lock on the counterpart chain. [2](#0-1) [3](#0-2) [9](#0-8)
