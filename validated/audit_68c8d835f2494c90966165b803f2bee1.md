### Title
Missing cosigner authorization check on incoming "sign" requests for local addresses allows any paired device to obtain private-payment details and trigger signing prompts for wallets it does not co-sign - (File: wallet.js)

### Summary
Apache DolphinScheduler's flaw let an authenticated user reach alert-instance data tied to alert groups they had no permission to access, because the API returned associated child resources without verifying the requester's membership in the owning group. The analogous defect in ocore is in the `"sign"` message handler in `handleMessageFromHub` in `wallet.js`: when `findAddress` resolves the target address to `ifLocal` (i.e., the address is hosted directly on this device, not a shared/multi-device address), the code that would confirm the requesting device is actually a listed cosigner is explicitly commented out, so any paired device can submit a signing request for any local address and have its private payload and unsigned unit processed.

### Finding Description
In `wallet.js`, the `"sign"` case handles requests of the form `{address, signing_path, unsigned_unit, private_payloads}` sent by a remote paired device asking the local node to co-sign a unit [1](#0-0) . After validating the message shape and cryptographic hash consistency of any private payloads [2](#0-1) , the address is resolved with `findAddress(body.address, body.signing_path, callbacks)` [3](#0-2) .

For addresses that are members of a multi-device shared address, `findAddress`'s `ifRemote` result includes `other_device_addresses` (the list of legitimate cosigner devices), and the handler explicitly checks membership before proceeding: `if (!other_device_addresses.includes(from_address)) return callbacks.ifError("you are not listed as a cosigner for this address ...")` [4](#0-3) .

However, in the `ifLocal` branch — reached when `findAddress` determines the address's signing key lives directly on this device (`row.device_address === device.getMyDeviceAddress()`) [5](#0-4)  — the equivalent check is present only as commented-out code:
```

    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
``` [6](#0-5) 

Because this check is disabled, `handleMessageFromHub` proceeds to process the request from *any* correspondent device (`from_address`), not just devices that are actual cosigners of `body.address`, as long as `body.address` resolves to a wallet address hosted locally. The handler then:
1. Emits `signing_request` with `assocPrivatePayloads` — the decrypted private payment outputs/blinding factors sent by the requester — to the local UI/wallet layer [7](#0-6) , or
2. Validates and processes the caller-supplied `unsigned_unit` as an online joint via `network.handleOnlineJoint`, then emits `signing_request` again with the private payloads for user confirmation [8](#0-7) .

This is directly analogous to the DolphinScheduler flaw: the "child resource" (the local wallet address's signing capability, and the associated private-payment data submitted alongside the request) is accessed via a request that is only checked for basic well-formedness, not for the requester's actual membership/authorization relative to the owning resource (the wallet/address). The in-code comment confirms this was a deliberate but incomplete design tradeoff ("the commented check would make multilateral signing impossible"), rather than an intentional, safe design — no replacement authorization mechanism was substituted.

### Impact Explanation
Any device that is a correspondent (paired) with the victim's wallet — even one that is not a party to any shared/multisig address held on that device — can send `"sign"` requests referencing the victim's own local wallet addresses. This:
- Triggers signing-confirmation UI prompts (`signing_request` events) for units the attacker fully controls, which if the user approves (e.g., by habit, or via automated confirmation flows), causes the wallet to sign and potentially post attacker-crafted units, i.e., unauthorized spending from that address.
- Leaks private payment details: the attacker can supply `private_payloads` with fabricated but internally-consistent structure that gets validated and surfaced to the user/wallet backend, and via the `sign` code path (`objJoint`/`handleOnlineJoint`) the local node processes attacker-chosen unsigned unit content that references the victim's address as an author, exposing whether/how the victim's device reacts to the address, path, and confirms address ownership relationships to any correspondent regardless of authorization on that specific address.
- Because the CWE-200-style analog concerns unauthorized access rather than pure spend, the concrete risk here escalates to potential fund loss or freezing if a user is socially engineered to approve a "cosign" prompt for a transaction they didn't initiate, since the authorization gate that should have blocked non-cosigner devices from even reaching that prompt is missing.

### Likelihood Explanation
Exploitation requires only that the attacker's device is a correspondent (paired device) of the victim — a routine, low-privilege relationship in ocore's chat/wallet-pairing model, not requiring cosigner status on any specific address. The check that would prevent this (verifying the sender is a genuine cosigner of `body.address`) exists in code but is commented out, indicating this is a known, reachable, and easily triggerable gap rather than a purely theoretical one.

### Recommendation
Re-enable (and properly implement, compatible with multilateral signing use cases) an authorization check in the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is a legitimate cosigner/co-participant for `body.address` and `body.signing_path` before invoking `callbacks.ifOk()` and emitting `signing_request` or processing the unsigned unit. At minimum, distinguish between the "multisig same-address-multiple-devices" case (where the check makes sense against `wallet_signing_paths`/`extended_pubkeys`) and the "multilateral signing among different addresses" case (where a different validation, e.g., checking `from_address` appears among `objUnit.authors` or a corresponding contract, should be used) so that no case falls through with zero authorization checking.

### Proof of Concept
1. Device A pairs with victim Device B (ordinary correspondent pairing, not a cosigner relationship on any shared address).
2. Device A learns/derives one of Device B's local wallet addresses `ADDR` (e.g., from a prior chat, invoice, or history) and a plausible `signing_path` (e.g., `"r"`).
3. Device A sends a `"sign"` message to Device B via the hub:
   ```
   { address: ADDR, signing_path: "r", unsigned_unit: {...attacker-crafted unit with ADDR as author...} }
   ```
4. On Device B, `handleMessageFromHub` processes this: `findAddress(ADDR, "r", ...)` resolves via the `my_addresses`/`wallet_signing_paths` join since `ADDR` is local to B [9](#0-8) , invoking `ifLocal` without ever validating that Device A is entitled to request signing for `ADDR` [6](#0-5) .
5. Device B proceeds to validate the attacker-supplied joint (`network.handleOnlineJoint`) and emits a `signing_request` confirmation prompt to the user, or immediately forwards the request's private payload contents, despite Device A having no legitimate relationship to `ADDR`.
