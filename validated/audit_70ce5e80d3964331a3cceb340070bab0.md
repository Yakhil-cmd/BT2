### Title
Webhook signature verification is bypassable by selecting an unauthenticated organization, allowing forged commit-status webhooks that unlock deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate an incoming webhook against based on a field read straight out of the *unverified* JSON body (`repository.owner.login`), while the handlers that act on the payload (e.g. `StatusHandler`) use a completely different, also attacker-supplied field (`sha`) with no scoping to the organization that was "verified." Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever `webhook_secret` is blank for the selected organization, an attacker can pick any configured organization that has no `webhook_secret` set to make signature verification a no-op, then use the same request to forge a commit status for an arbitrary commit SHA belonging to any repository/stack in the Shipit instance.

### Finding Description
`verify_signature` derives the org used to fetch the verification secret purely from the request body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as "always verified": [3](#0-2) 

Multi-organization Shipit deployments are expected to configure a separate `github:` entry per organization, and it is explicitly documented/sampled that `webhook_secret` can be left unset for a given org: [4](#0-3) 

Because `repository_owner` is read from the same unauthenticated JSON body that is later used to pick the org whose secret validates the *entire* request, an attacker can set `repository.owner.login` to any org name that has no `webhook_secret` configured, which makes `verify_webhook_signature` return `true` unconditionally — no valid HMAC is required.

The payload is then dispatched to handlers keyed only by the `X-Github-Event` header, and `StatusHandler` acts on an attacker-controlled `sha` field with **no scoping to a repository or organization at all**: [5](#0-4) 

This breaks the binding: **organization authenticated (`repository.owner.login`, used to select the verification secret) ≠ resource acted upon (`sha`, resolved globally across all repositories/stacks via `Commit.where(sha: params.sha)`)**. The signature check authenticates one identity while the mutation is applied to a target entirely disconnected from that identity.

### Impact Explanation
A forged `status` webhook lets an unauthenticated attacker create arbitrary `CommitStatus` records (state `success`, arbitrary `context`/`description`) for any commit SHA tracked by any stack in the Shipit instance, as long as at least one configured GitHub organization in `Shipit.github_configs` lacks a `webhook_secret` (a state explicitly present in the shipped sample config). Commit statuses feed directly into Shipit's deploy-gating logic (`Commit`/`Stack` deployability checks), so this can be used to mark an otherwise-failing or unreviewed commit as CI-green, enabling an unauthorized deploy of that commit — matching the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Exploitation requires only an unauthenticated HTTP POST to the public webhooks endpoint; the attacker needs no token, no repository access, and no knowledge of any real webhook secret. The only precondition is that at least one org entry in the Shipit engine's GitHub config has no `webhook_secret` set — a documented, sample, and plausible real-world misconfiguration (setup docs and the Shopify sample config both show this as a valid/expected state), so the likelihood is non-trivial though contingent on that specific configuration state.

### Recommendation
- Require `webhook_secret` to be present for every configured organization and refuse to boot/serve webhooks for orgs missing one, instead of treating a blank secret as "always verified."
- Never use unauthenticated payload fields to select the verification key; if multi-tenant verification is required, verify against secrets for all configured organizations (or route by URL path segment established at hook-creation time) and require the resulting resolved organization to match the resource the handler is about to mutate.
- Scope `StatusHandler` (and other handlers) lookups (e.g. `Commit.where(sha:)`) to the repository resolved in `Handler#repository_name`/`#stacks`, not globally, so a payload cannot affect commits unrelated to the authenticated repository.

### Proof of Concept
1. Assume Shipit is configured with two GitHub orgs, `victim-org` (has `webhook_secret` set) and `test-org` (no `webhook_secret`, as in the sample config).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "test-org" }, "full_name": "test-org/anything" },
  "sha": "<commit sha belonging to victim-org's tracked stack>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged green build"
}
```
3. `verify_signature` looks up `Shipit.github(organization: "test-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature header.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit irrespective of `test-org` — and calls `create_status_from_github!`, injecting a fabricated passing CI status on the victim's commit, which can satisfy deploy-gating checks for an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit

          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do

          end
        end

        def process

          end
        end
      end
```
