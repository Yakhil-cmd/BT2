### Title
`repository.owner.login` used for signature org, `repository.full_name` used for repository resolution - webhook signature verified against wrong org, allowing cross-org forced sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org used to validate `X-Hub-Signature` solely from `payload.dig('repository', 'owner', 'login')` (via `repository_owner`), while the `push` handler (`Handler#stacks`/`Handler#repository_name`) resolves the target `Repository` solely from `payload.dig('repository', 'full_name')`. These two fields are never checked to be consistent, so an attacker can pick a no-secret (or attacker-controlled) org for the signature check while pointing `full_name` at a victim's repository, causing `PushHandler#process` to call `stack.sync_github` on the victim's stack.

### Finding Description
The broken binding is the implicit assumption:
`repository_owner (used to select the verifying webhook_secret) == owner_of(repository.full_name) (used to resolve the mutated Repository/Stack)`. Nothing in the code enforces this equality.

- `verify_signature` picks the app config via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) .
- `Shipit.github(organization:)` looks up `github_app_config(organization)` from `secrets.github`; if that org has no `webhook_secret` configured, `verify_webhook_signature` returns `true` unconditionally: `return true unless webhook_secret` [3](#0-2) [4](#0-3) .
- Once signature verification passes (trivially, because the chosen org has no secret), `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `process` uses `stacks`, which resolves the repository via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a field completely independent of `repository_owner` [5](#0-4) [6](#0-5) .
- Because `full_name` and `owner.login` are read from two independent, attacker-controlled JSON paths in the same forged payload, an attacker can set `repository.owner.login` to an org that has no `webhook_secret` configured (or one they otherwise control) and `repository.full_name` to `"victim-org/victim-repo"`. The signature check trivially passes for the "no-secret" org, and the handler then acts on the victim's stack, calling `stack.sync_github(expected_head_sha: params.after)`.
- No other guard intervenes: `check_if_ping` and `drop_unhandled_event` don't inspect these fields; `ExplicitParameters` (`PushHandler.params`) only validates `ref`/`after` are present, not that `full_name`'s owner matches `repository_owner`; there's no `Repository`/`Stack` validation tying incoming webhook org to the stored repo's owner at webhook-processing time.

### Impact Explanation
An unauthenticated attacker can force `GithubSyncJob`-equivalent behavior (`stack.sync_github`) against any tracked stack/repository in the Shipit instance, without ever satisfying that repository's actual `webhook_secret`, as long as any org in `secrets.github` lacks a webhook secret (or the attacker can otherwise get a signature to validate for an org they name). This is a cross-tenant mutation: a payload "verified" for org A causes state changes on org B's repository/stack, matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team." The blast radius spans every stack configured in the instance, and the attack is repeatable per request.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one organization in `Shipit.secrets.github` configured **without** a `webhook_secret` (common in multi-org/GitHub App setups where some orgs are added without a secret, or where `github_default_organization` fallback semantics apply). If such an org exists, the attacker's cost is a single unauthenticated HTTP POST to `/webhooks` with `X-Github-Event: push`, a JSON body naming that org as `repository.owner.login` and the victim repo as `repository.full_name`, and no valid `X-Hub-Signature` is even required. This requires no session, no API token, no GitHub secrets — fully within the unprivileged attacker model. The existing test suite (`test/controllers/webhooks_controller_test.rb`) does not test for this owner/full_name divergence, and the code has no cross-check that would prevent it.

### Recommendation
Verify webhook signatures and resolve the target repository using the same, single source of truth. Concretely: derive the owning organization used for `Shipit.github(organization:)` from the same `repository.full_name` (e.g., split `full_name.split('/').first`) that the handler uses to look up the `Repository`, or, after resolving the `Repository` via `full_name`, assert that its stored/owning organization matches `repository_owner` before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof sketch)
test ":push with mismatched owner/full_name forces sync on victim repo verified by unrelated org" do
  # Precondition: configure an org "attacker-org" in secrets.github with no webhook_secret
  Shipit.stubs(:secrets).returns(
    stub(github: { "attacker-org" => { app_id: 1, installation_id: 1, private_key: nil } }.with_indifferent_access)
  )

  victim_stack = shipit_stacks(:shipit) # owned by "shopify/shipit-engine" per fixtures
  request.headers['X-Github-Event'] = 'push'

  payload = JSON.parse(payload(:push_master))
  payload["repository"]["owner"]["login"] = "attacker-org"          # org with NO webhook_secret
  payload["repository"]["full_name"] = "shopify/shipit-engine"      # victim repo, different org
  payload["after"] = "attackercontrolledsha"

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "attackercontrolledsha"]) do
    post :create, body: payload.to_json, as: :json
  end
  # No X-Hub-Signature header set at all -- request still succeeds because
  # verify_webhook_signature short-circuits `return true unless webhook_secret`
  # for "attacker-org", which was never the owner of the mutated victim stack.
end
```
This demonstrates the equality `repository_owner == owner_of(full_name)` is false, yet the mutation (`sync_github`/`GithubSyncJob` enqueue) for the victim stack still occurs, confirming the vulnerability.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
