### Title
Any principal can register itself as a `signer-manager` and drain another staker's accrued rewards via `claim-staker-rewards-for-signer` without paying out sBTC - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`claim-staker-rewards-for-signer` in `pox-5.clar` is a public function intended to let a registered signer-manager contract "mark a staker as having claimed rewards" as part of its own reward-distribution bookkeeping. It computes the staker's currently-earned rewards via `settle-staker-rewards`, then unconditionally zeroes `staker-unclaimed-rewards-for-cycle` for `{reward-cycle, bond-index, signer: contract-caller, staker}` — but it never transfers any sBTC to the staker, and never checks that `contract-caller` is the staker's actual, currently-registered signer for that stake. [1](#0-0) 

### Finding Description
`claim-staker-rewards-for-signer` uses `contract-caller` as the "signer" identity with no validation step confirming that `contract-caller` is registered in `signers` for the given `staker`/`bond-index`, nor that it matches the staker's actual `protocol-bond-memberships`/`signer` assignment recorded elsewhere in the contract (e.g. in `update-bond-registration`, `stake`, etc., which use `signer-manager-validate-stake` with a real signer-manager trait binding, `stackslib/src/chainstate/stacks/boot/pox-5.clar:408-427`). By contrast, other privileged functions in this contract enforce ownership: `register-signer` checks `(is-eq contract-caller signer)` [2](#0-1)  and `grant-signer-key` checks `(is-eq contract-caller signer-manager)` [3](#0-2) .

`claim-staker-rewards-for-signer` has no analogous check tying `contract-caller` to the `staker` argument. Anyone can deploy a trivial contract, register it as a signer-manager via `grant-signer-key`/`register-signer` (a self-service, permissionless flow demonstrated in `contrib/core-contract-tests/contracts/signer-manager.clar:544-559` and `contrib/core-contract-tests/contracts/test-pox-5-signer.clar:26-38`), and then call `claim-staker-rewards-for-signer` passing an arbitrary victim `staker` principal and `reward-cycle`/`bond-index`. Because the map key includes `signer: contract-caller` (the attacker's own manager identity, not the staker's real signer), this call succeeds even though the attacker's signer never actually accrued that staker's stake, and it wipes the staker's `staker-unclaimed-rewards-for-cycle` entry to `u0` with no sBTC ever transferred.

This breaks the equality that "rewards recorded as claimed == rewards paid out to the staker." The staker's legitimately accrued sBTC reward entitlement, tracked in `settle-staker-rewards`/`staker-unclaimed-rewards-for-cycle`, is permanently zeroed out by an unrelated, unauthorized principal without any corresponding sBTC transfer — a permanent freezing/loss of an accrued sBTC reward.

### Impact Explanation
This matches the "Critical" bucket criteria in scope: permanent freezing of sBTC rewards belonging to a staker, and it is triggerable by any unprivileged account (no admin/bond/pause role or victim key required) — only a permissionless self-registered signer-manager contract, which is explicitly supported by the protocol design (`register-self` pattern shown in the core-contract-tests fixtures). Any staker whose accrued-but-unclaimed rewards can be targeted this way loses those rewards permanently since the state that gates future payout (`staker-unclaimed-rewards-for-cycle`) is reset to zero with no compensating mint/transfer.

### Likelihood Explanation
Likelihood is high: the attack requires only (1) deploying and self-registering an arbitrary signer-manager contract (a normal, unprivileged, permissionless action per the documented flow), and (2) knowing a victim staker's principal and the reward-cycle/bond-index they are staking in — both public on-chain information. No signature, admin role, or victim cooperation is required to invoke `claim-staker-rewards-for-signer` with an arbitrary `staker` argument.

### Recommendation
Add an authorization check in `claim-staker-rewards-for-signer` verifying that `contract-caller` is in fact the staker's currently-registered signer for the given cycle/bond-index (e.g., cross-check against `protocol-bond-memberships`/the staker's signer-assignment maps used elsewhere, analogous to the `is-eq contract-caller signer` checks used in `register-signer` and `grant-signer-key`), rejecting the call if the caller does not match the staker's real signer relationship.

### Proof of Concept
1. Attacker deploys `evil-signer-manager.clar` implementing the `signer-manager-trait` with a no-op `validate-stake!`.
2. Attacker self-registers it via a `register-self`-style flow: sign a `grant-signer-key` message with a fresh keypair, call `grant-signer-key` (passing `signer-manager = evil-signer-manager`), then `register-signer` — both succeed because they only check that `contract-caller == signer-manager` (the attacker's own contract), matching the pattern in `contrib/core-contract-tests/contracts/signer-manager.clar:544-559`.
3. Attacker's `evil-signer-manager` calls `(contract-call? .pox-5 claim-staker-rewards-for-signer VICTIM_STAKER reward-cycle bond-index)`.
4. `settle-staker-rewards` computes VICTIM_STAKER's real earned rewards for that cycle/bond, and `map-set staker-unclaimed-rewards-for-cycle {..., signer: contract-caller(evil-signer-manager), staker: VICTIM_STAKER} u0` executes successfully — no sBTC is transferred to VICTIM_STAKER, but their unclaimed-rewards entry is now zero, permanently precluding them from claiming those rewards through the legitimate signer path.

;; As a signer manager contract, mark a specific staker as having claimed
;; rewards. This is used to mutate internal rewards settlement state.
;;
;; This is only callable by the signer manager contract.
(define-public (claim-staker-rewards-for-signer
        (staker principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let ((rewards-info (settle-staker-rewards contract-caller reward-cycle bond-index staker)))
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))
        (map-set staker-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: contract-caller,
            staker: staker,
        }
            u0
        )
        (print {
            topic: "claim-staker-rewards-for-signer",
            signer-manager: contract-caller,
            staker: staker,
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            rewards-claimed: (get earned rewards-info),
        })
        (ok rewards-info)
    )
)
