### Title
Unscoped `Stack.from_param!` in CCMenu API controller leaks locked/private stack status across `ApiClient` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to call `Stack.from_param!(params[:stack_id])` directly on the model, bypassing the tenant-scoping that `Shipit::Api::BaseController#stack` normally applies via `stacks.from_param!`. Any valid `ApiClient` token with `read:stack` permission—regardless of its own `stack_id` scope—can therefore fetch the CCMenu XML status (including `merge_status` such as `locked`) of any other stack in the installation.

### Finding Description
The intended binding is: for a scoped `ApiClient`, `stack ∈ Stack.where(id: current_api_client.stack_id)`, i.e. `stack.id == current_api_client.stack_id` when the client is scoped. This is enforced generically in [1](#0-0)  where `stacks` filters by `current_api_client.stack_id?` before `from_param!` is called.

`CCMenuController`, however, redefines `stack` to skip that scoping entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains `"read:stack"` via `ApiClient#check_permissions!` [3](#0-2) ; it never checks whether the *specific stack* being accessed matches `current_api_client.stack_id`. That per-stack check only happens as a side effect of `BaseController#stacks` filtering the queryable set — logic this controller does not use.

The rendered view then discloses `stack.merge_status`, mapping `'locked'` to `lastBuildStatus: 'Failure'`: [4](#0-3) 

Exploit: an attacker holding (or possessing legitimately, from a different, unrelated integration) a token scoped to stack A (`ApiClient#stack_id == A`) sends `GET /api/stacks/B/ccmenu.xml?token=<tokenA>` where B is a different, locked/private stack. `authenticate_api_client` in the controller accepts the token from the query string [5](#0-4) , `require_permission!(:read, :stack)` passes because the token merely has `read:stack` globally, and `stack` resolves stack B unscoped, leaking B's lock state and last deploy timing/status in the XML response.

No existing guard (`require_permission!`, `Stack.from_param!`, or the view) checks stack-to-client ownership; the scoping is silently dropped by the controller's local override.

### Impact Explanation
This is an unauthenticated-for-that-resource / cross-tenant read of stack state: a token scoped to one stack can enumerate the lock/merge status and latest deploy/rollback metadata of any other stack in the Shipit instance, including private or explicitly locked stacks with operator-set lock reasons. This matches the High severity category ("unauthenticated read of stack state ... across tenants") since it lets a caller with narrow, legitimate authorization (or any leaked/rotated single-stack token) read state belonging to stacks outside its granted scope. It is fully repeatable — a simple `stack_id` change in the URL — against any stack ID in the system.

### Likelihood Explanation
Preconditions are minimal: the attacker needs any valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single, unrelated stack by an operator) and the numeric/param ID of the target stack. No GitHub secrets, webhook signatures, or session state are required — this is a straightforward authenticated-but-under-scoped HTTP GET. Given `ApiClient` tokens are commonly distributed to third-party integrations with the expectation that `stack_id` scoping is enforced, this is easy to trigger unintentionally as well as maliciously.

### Recommendation
Remove the local `stack` override in `CCMenuController` and use the scoped `stacks.from_param!` from `BaseController` (or explicitly verify `stack.id == current_api_client.stack_id` when `current_api_client.stack_id?` before rendering), so CCMenu respects the same per-client stack scoping as the rest of the API.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b`; lock `stack_b` with `stack_b.lock(reason: "maintenance")` so `stack_b.merge_status == 'locked'`.
2. Create an `ApiClient` with `stack_id: stack_a.id` and `permissions: ['read:stack']`; get its `authentication_token`.
3. `get shipit.api_stack_ccmenu_path(stack_b), params: { token: client.authentication_token }`.
4. Assert equality-of-binding failure: assert `response.status == 200` and the XML body contains `lastBuildStatus="Failure"` for `stack_b`'s project entry — i.e. assert `stack_b.merge_status == 'locked'` is exposed even though `client.stack_id != stack_b.id`, proving `stack ∈ Stack.where(id: current_api_client.stack_id)` does not hold.
5. Contrast with expected behavior: after the fix, the same request should return `403`/`404` instead of leaking `stack_b`'s status.
