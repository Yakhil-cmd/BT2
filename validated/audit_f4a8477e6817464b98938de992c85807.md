### Title
Cross-repository forgery of the Status webhook mutates victim stacks via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commits to update purely by SHA, with no join or filter against the repository named in the webhook payload. Any commit sharing that SHA in any stack — including a victim stack unrelated to the attacker's repository — receives a new `Status` record, whose `after_create :enable_ci_on_stack` callback unconditionally calls `commit.stack.enable_ci!` on the victim's stack.

### Finding Description
The broken binding, stated explicitly: `commit.stack` (mutated by the callback) must equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks` (the stack(s) legitimately owned by the repository that emitted the webhook). This equality is never checked or enforced.

Code path:
1. `WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event('status')`, which resolves to `StatusHandler`. [1](#0-0) 
2. `verify_signature` only authenticates that the sender knows the GitHub App/organization-level webhook secret for `repository_owner` (the payload's declared owner) — it never binds the SHA in `params.sha` to any specific repository or stack. [2](#0-1) 
3. `StatusHandler#process` looks up commits **globally by SHA only**, with no filter on repository/stack derived from the payload:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
4. `Commit#create_status_from_github!` creates a `Status` scoped to `stack_id` of whichever commit record was matched (which can belong to any stack, not the attacker's), via `add_status`/`statuses.replicate_from_github!`. [4](#0-3) 
5. `Status`'s `after_create :enable_ci_on_stack` callback fires unconditionally for every newly created status, mutating `commit.stack` — the victim's stack, not the attacker's:
```ruby
after_create :enable_ci_on_stack
...
def enable_ci_on_stack
  commit.stack.enable_ci!
end
``` [5](#0-4) 

Root cause: the handler trusts the SHA alone to select target commits, never validating that the resolved commit's `stack` corresponds to `Repository.from_github_repo_name(payload's repository)`. Any two repositories that happen to share a commit SHA (e.g., repositories created from the same template with identical author/committer/timestamp/tree producing an identical initial commit SHA, or any commit copied/cherry-picked verbatim between repos) let a webhook "for" one repository silently write a `Status` — and flip CI state — on a completely different stack.

Existing guards do not prevent this: `verify_signature` authenticates the org/app credential of the *claimed* repository owner, not a binding between that repository and the specific commit/stack being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate the shape of the payload (`sha`, `state`, etc.), not repository ownership of the matched `Commit` rows.

### Impact Explanation
A successful forgery causes `Status.create!` on a commit belonging to a stack the attacker does not own, which in turn calls `commit.stack.enable_ci!` on that victim stack — an unauthorized configuration mutation of a resource for a repository that never authenticated the request. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Beyond `enable_ci!`, the forged `Status` also triggers `schedule_continuous_delivery` and `broadcast_update` on the victim commit/stack, and (per `Commit#add_status`) can emit `commit_status`/`deployable_status` webhooks and enqueue `ProcessMergeRequestsJob`, all attributed to the victim's commit. The attack is repeatable against any stack whose commit table happens to contain a SHA the attacker can reproduce or discover.

### Likelihood Explanation
The attacker must: (a) control a repository whose organization/app is registered in Shipit's `github` webhook-secret configuration (so `verify_signature` succeeds for their own payload — they never need the victim's secret), and (b) know or engineer a SHA collision with a commit in the target stack's `commits` table. SHA collisions are practically achievable when repos are generated from identical templates (identical tree, author, committer, message, and timestamp yield an identical Git SHA1) — a low-cost, unprivileged, repeatable technique requiring no Shipit session, API token, or secret.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository declared in the webhook payload, e.g. resolve `Repository.from_github_repo_name(payload_repository_full_name)` and constrain `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` before calling `create_status_from_github!`, mirroring the binding that should hold: `commit.stack ∈ Repository.from_github_repo_name(payload_repo).stacks`.

### Proof of Concept
Minitest plan (model-level, no live GitHub):
```ruby
test "a status webhook for one repository's SHA must not mutate a different stack's CI state" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to victim stack
  # Simulate an attacker-controlled repository whose payload accidentally/deliberately
  # shares victim_commit.sha (SHA collision / templated repo)
  attacker_payload = OpenStruct.new(
    sha: victim_commit.sha,
    state: 'success',
    description: 'attacker-controlled',
    context: 'ci/attacker',
    target_url: 'http://attacker.example.com',
    created_at: Time.now,
    branches: []
  )

  victim_commit.stack.expects(:enable_ci!).never

  Shipit::Webhooks::Handlers::StatusHandler.new.process(attacker_payload)
end
```
Assert both sides of the binding: before the call, `victim_commit.stack != attacker_repository.stacks` (they are different records); after the call, `commit.stack.enable_ci!` must NOT have been invoked for `victim_commit.stack` unless `victim_commit.stack` is genuinely among `Repository.from_github_repo_name(attacker_payload_repo).stacks`. The `.expects(:enable_ci!).never` assertion fails against current code (proving the vulnerability) since `StatusHandler#process` matches purely by SHA and unconditionally calls `commit.create_status_from_github!`, firing `enable_ci_on_stack` regardless of which repository the payload names.
