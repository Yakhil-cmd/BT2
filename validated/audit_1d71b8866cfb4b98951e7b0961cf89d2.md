### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is looked up by `repository.full_name`, letting an attacker-signed payload mutate a victim org's `ReviewStack` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `params.dig('repository','owner','login')`, while `ReopenedHandler#repository` (and the base `Handler#stacks`) resolve the actual `Shipit::Repository`/`ReviewStack` scope using `params.repository.full_name` via `Repository.from_github_repo_name`. Because these two fields are independently attacker-controlled in the raw JSON body and are never checked against each other, an attacker who controls a legitimate GitHub org onboarded to this multi-tenant Shipit instance (and thus knows that org's real `webhook_secret`) can sign a payload as their own org while setting `repository.full_name` to a victim org's repo, causing `ReviewStackAdapter#unarchive! -> create!` to create and enqueue-for-provisioning a `ReviewStack` under the victim's repository with an attacker-chosen `branch`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`organization_verifying_signature (params.repository.owner.login)` **==** `organization_owning_the_mutated_repository (owner segment of params.repository.full_name)`

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` solely from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- Shipit supports per-organization GitHub App configs, each with its own independent `webhook_secret`, precisely so multiple GitHub orgs can share one Shipit instance. [3](#0-2) [4](#0-3) 
- Once signature verification passes (using the attacker's own org's genuine secret), `WebhooksController#create` dispatches the raw, still-attacker-controlled `params` to the `pull_request` handlers. [5](#0-4) 
- `ReopenedHandler#repository` resolves the repository purely from `params.repository.full_name`, independent of `owner.login`: [6](#0-5) 
- `Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` columns — no relationship at all to the `owner.login` value used for signature verification: [7](#0-6) 
- If `unarchive?` is true (victim repo has `review_stacks_enabled` + `provisioning_behavior_allow_all?`) and no `ReviewStack` matches the PR's environment, `ReviewStackAdapter#unarchive!` falls into the `stack.blank?` branch and calls `create!`, which calls `scope.create!(stack_attributes)` where `scope` is `repository.review_stacks` (the victim repository's association) and `branch: params.pull_request.head.ref` is taken verbatim from the unsigned-relative-to-target-org payload: [8](#0-7) [9](#0-8) 
- The created stack is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`, and provisioning later performs `git clone ... --branch @stack.branch` / `git fetch origin ... @stack.branch` through `StackCommands`, using the attacker-supplied branch string: [10](#0-9) [11](#0-10) 

None of the existing guards close this gap:
- `verify_signature` only checks the HMAC against the org named in `owner.login`; it never checks that `owner.login` matches the owner segment of `full_name`. [12](#0-11) 
- `ExplicitParameters` schema in `ReopenedHandler` only requires `repository.full_name` to be a `String`; it does not require or validate `repository.owner.login`, and the two are never cross-checked. [13](#0-12) 
- `drop_unhandled_event` and `check_if_ping` are unrelated to this binding.

The single-GitHub-app deployment mode (`github_default_organization.nil?`) is not exploitable this way since only one secret/org exists; the vulnerability requires the multi-org configuration (`github: {orgA: {...}, orgB: {...}}`), which is an explicitly documented and supported Shipit configuration.

### Impact Explanation
An attacker who legitimately owns/administers one GitHub organization onboarded to a shared, multi-tenant Shipit instance can forge webhook deliveries (using their own org's real secret, which they set themselves when configuring the webhook) that name a *different* onboarded organization's repository in the `repository.full_name` field. This causes Shipit to create a `Shipit::ReviewStack` (and its `PullRequest`) under the victim organization's `Repository` record with a fully attacker-chosen `branch`, and immediately enqueues it into `ReviewStackProvisioningQueue`. During provisioning, `StackCommands#fetch`/`#fetch_commit`/`git_clone` will run `git clone`/`git fetch` against the victim's real GitHub repo using the attacker-controlled `branch` argument shell-quoted into a `Command`. This is a cross-tenant record injection ("a payload for one repository mutating another's stack") and can be leveraged toward unauthorized provisioning/deploy activity against the victim repository. This matches the Critical category: unauthorized stack creation/mutation for a repository/org that never authenticated the request.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must be configured for multiple GitHub organizations (`github: {org1: {...}, org2: {...}}`), a documented, supported configuration; (2) the victim repository must have `review_stacks_enabled = true` and `provisioning_behavior_allow_all?` true (or `allow_with_label`/`prevent_with_label` satisfied); (3) the attacker must control at least one org's genuine webhook secret — trivial, since as owner/admin of their own onboarded org they set that secret themselves. Given these (realistic for any multi-tenant Shipit deployment), the attack is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable against any number of victim repositories/PR numbers, with no rate limiting or additional secret needed.

### Recommendation
In `WebhooksController#verify_signature` (or in the individual handlers before acting), enforce that the organization used to verify the signature equals the owner segment of `params.repository.full_name` (and of `params.repository.owner.login` when both are present), rejecting the webhook (422) on mismatch. Alternatively, resolve the `Repository`/`ReviewStack` scope using the same verified `repository_owner` value rather than trusting `full_name` independently in `Repository.from_github_repo_name` and `Handler#stacks`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style, combined with a controller-level test):

```ruby
test "org A's genuine signature must not let it create a ReviewStack for org B's repository" do
  victim_repo = shipit_repositories(:shipit) # owner: "shopify" (org B)
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = payload_parsed(:pull_request_reopened)
  payload["repository"]["owner"]["login"] = "attacker-org"      # org A - signer
  payload["repository"]["full_name"]      = "shopify/shipit-engine" # org B - victim, mismatched owner
  payload["pull_request"]["head"]["ref"]  = "attacker-controlled-branch"

  # Signature is verified only against attacker-org's own secret (organization = "attacker-org")
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    stub(verify_webhook_signature: true)
  )

  assert_difference -> { victim_repo.review_stacks.count }, 1 do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end

  created = victim_repo.review_stacks.last
  assert_equal "attacker-controlled-branch", created.branch
  assert created.awaiting_provision?, "expected stack to be queued for provisioning under victim repo"
end
```

Equality check both sides:
- Before: signer org = `"attacker-org"`, target repo owner = `"shopify"` → mismatch.
- After processing: `Shipit::ReviewStack.create!` was invoked with `scope = shopify_repository.review_stacks` and `branch = "attacker-controlled-branch"`, proving the mismatch was never rejected and the victim's tenant data was mutated using attacker-controlled input.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
