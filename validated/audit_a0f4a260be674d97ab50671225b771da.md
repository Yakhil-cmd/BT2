### Title
Case-sensitive/whitespace-sensitive exact-string comparison in `evaluate_rules` silently downgrades intended `block` rules to non-blocking `warn` rules, causing hook enforcement to fail open - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`Rule.from_dict` stores the raw `action` value straight from the parsed frontmatter with no normalization: `action=frontmatter.get('action', 'warn')` [1](#0-0) . `extract_frontmatter`'s hand-rolled YAML parser only lower-cases values that equal `true`/`false`; any other scalar (including `action`) is kept byte-for-byte after `strip()`/quote-stripping, with no case-folding and no comment stripping on a `key: value` line [2](#0-1) . `RuleEngine.evaluate_rules` then classifies a matched rule as blocking with a single exact string comparison `if rule.action == 'block':` — anything else (including `'Block'`, `'BLOCK'`, or `'block # nit'` produced by an inline YAML comment that the parser never strips) falls through to the `else` branch and is appended to `warning_rules` instead of `blocking_rules` [3](#0-2) . Because warning rules only add a `systemMessage` and never set `permissionDecision: deny` or `decision: block`, the tool call, file edit, or Stop event proceeds unimpeded even though the rule file visually declares an enforcement action [4](#0-3) . Note the "trailing whitespace" variant from the question does not apply since `value.strip()` at line 138 already removes it; the case-variant (`Block`) and inline-comment variant (`block # nit`) do reproduce.

### Impact Explanation
Any `.claude/hookify.*.local.md` rule file — which is ordinary, unprivileged repository content loaded by `load_rules`/`load_rule_file` and fed to every `PreToolUse`/`PostToolUse`/`Stop` hook [5](#0-4)  — that is authored or tampered with (e.g. via a pull request to a shared repo) with `action: Block`, `action: BLOCK`, or a trailing inline comment on the `action` line will be silently accepted by the parser but never enforced as a blocking rule. A reviewer or user who reads such a rule reasonably believes dangerous Bash commands, file edits, or Stop-event content are blocked; in reality they are only logged as a warning and the underlying tool call executes normally. This is a hook-enforcement fail-open bug: it defeats an intended repo-level guardrail against exactly the kinds of dangerous commands/file writes hookify exists to stop, without any error or indication to the user that enforcement silently degraded.

### Likelihood Explanation
Trivial to trigger and highly likely to occur unintentionally (case typos and inline comments are common in YAML-like files written by hand) and just as easily craftable deliberately by anyone who can add/modify a `.claude/hookify.*.local.md` file in a repository that will be used by Claude Code (e.g., a contributor submitting a rule file in a PR). No special privilege beyond normal repo-content contribution is required, and the bug is 100% reproducible given the exact-match code path.

### Recommendation
Normalize the `action` value at parse time or comparison time: e.g. in `Rule.from_dict`, do `action=str(frontmatter.get('action', 'warn')).strip().lower()`, and in `evaluate_rules` compare against the same normalized form. Additionally, strip inline `#` comments when parsing simple `key: value` lines in `extract_frontmatter` (consistent with comment-handling already done for whole lines), and consider validating `action` against an explicit allowed set (`{'warn', 'block'}`) with a loud warning/error on unrecognized values instead of silently treating anything non-`'block'` as `warn`.

### Proof of Concept
Unit test added to a suite exercising `config_loader.extract_frontmatter`/`Rule.from_dict` and `rule_engine.RuleEngine.evaluate_rules`:

```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

RULE_MD = """---
name: block-rm-rf
enabled: true
event: bash
action: Block
pattern: "rm -rf"
---

This should be BLOCKED, not just warned.
"""

def test_case_variant_action_is_not_enforced_as_block():
    fm, msg = extract_frontmatter(RULE_MD)
    rule = Rule.from_dict(fm, msg)
    assert rule.action == "Block"  # confirms no normalization happened

    engine = RuleEngine()
    result = engine.evaluate_rules(
        [rule],
        {
            "hook_event_name": "PreToolUse",
            "tool_name": "Bash",
            "tool_input": {"command": "rm -rf /important-data"},
        },
    )
    # BUG: expected the dangerous command to be denied, but it is only warned
    assert "hookSpecificOutput" not in result  # no permissionDecision: deny issued
    assert "systemMessage" in result  # falls into warning_rules instead
```
Expected (buggy) behavior: the assertions pass, demonstrating that a rule file explicitly declaring `action: Block` produces only a warning `systemMessage` and no `hookSpecificOutput` deny decision, so `rm -rf /important-data` is not blocked by PreToolUse enforcement despite the rule matching.
