### Title
Webhook signature is verified against the organization named in the payload, but the repository/stack that gets written is taken from a different, unbound field in the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` config (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body. Once that signature check passes, the very same payload is handed to event handlers (e.g. `PushHandler`) which look up the target `Repository`/`Stack` using an entirely different, uncorrelated field: `repository.full_name`. Nothing ties the “owner” used for authentication to the “full_name” used for the write, so a payload can be legitimately signed with organization A's secret while acting on organization B's stack.

### Finding Description
`verify_signature` picks the app config to check the signature with: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON payload the caller controls (`params.dig('repository', 'owner', 'login')`), and is used only to pick which org's `webhook_secret` verifies the signature via `github_app.verify_webhook_signature`.

Once verification succeeds, `create` dispatches the same payload to registered handlers: [3](#0-2) 

`Handler#repository_name`/`#stacks`, used by every handler including `PushHandler`, resolve the target `Repository`/`Stack` from a *different* field of the payload — `repository.full_name` — with no check that it belongs to the organization that was actually authenticated: [4](#0-3) 

`PushHandler#process` then acts on those stacks using an attacker-supplied `ref`/`after` (commit sha): [5](#0-4) 

Shipit is designed to host multiple organizations, each with its own `GitHubApp` configuration and its own distinct `webhook_secret` (confirmed by the multi-app test fixtures/tests): [6](#0-5) 

So the equality that should hold — `organization whose secret validated this request` == `organization that owns the repository being synced/deployed` — is never enforced. The payload field that authenticates the request (`repository.owner.login`) and the payload field that determines the write target (`repository.full_name`) are independent, attacker-controlled strings within the same signed blob.

### Impact Explanation
Any party who legitimately administers **one** organization onboarded to a multi-tenant Shipit instance (and therefore knows that organization's `webhook_secret`) can forge a `push` webhook payload where:
- `repository.owner.login` = their own organization (so `verify_signature` picks their own, genuinely-known secret and the HMAC check passes), and
- `repository.full_name` = any other organization's repository that is already onboarded as a Shipit `Stack`.

The signature will validate successfully, and `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` on the victim's `Stack` using an attacker-chosen `ref`/commit sha, even though the request was never authenticated as belonging to that victim organization. This is a cross-repository write: an attacker-controlled organization's credential is used to mutate the state (commits/until/since) of a completely different, unrelated tenant's stack, and if the victim stack has `continuous_deployment` enabled, this can lead to an unauthorized deploy/sync being triggered for a repository the attacker was never authorized to touch. This matches the “organization authenticated vs. repository written” binding explicitly called out as in-scope.

### Likelihood Explanation
Exploitability is bounded by the requirement that the attacker must be a legitimate administrator of at least one organization already onboarded to the shared Shipit instance (so they know a valid `webhook_secret`) — this is the intended "unprivileged" tenant in a multi-org Shipit deployment, not a privileged Shipit user/API-client. Given that constraint is met, forging the payload is trivial: no other secret, session, or credential is required, and the vulnerable code path (`verify_signature` → `create` → `PushHandler`) is reached on every webhook POST.

### Recommendation
Bind the field used to select/verify the webhook signature to the same field used to resolve the write target. Concretely, `WebhooksController#repository_owner` (used to choose the `GitHubApp`/secret) and `Handler#repository_name` (used to resolve `Repository`/`Stack`) should be derived from the same trusted value, and handlers should additionally assert that the resolved `Repository`'s owner matches the organization whose secret validated the request before acting on it.

### Proof of Concept
1. Attacker administers `evil-org`, onboarded to the shared Shipit instance with its own `GitHubApp` config and known `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "evil-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(evil-org webhook_secret, raw_body)>` and sends `POST /github/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"evil-org"`, fetches `Shipit.github(organization: "evil-org")`, and the HMAC check passes because the attacker legitimately knows `evil-org`'s secret.
5. `create` dispatches to `PushHandler`, which resolves the target via `repository.full_name = "victim-org/victim-repo"` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's `Stack`, even though the request was authenticated only for `evil-org`.

**Uncertainty note:** I could not fully trace `Shipit.github`'s organization-lookup implementation (`lib/shipit.rb`) or `Stack#sync_github`'s downstream effects (e.g., whether continuous deployment is auto-triggered) within the available tool budget; confirming the exact downstream blast radius (whether this alone can trigger an actual unauthorized deploy versus merely a bogus sync/resync attempt) would require reading `lib/shipit.rb` and `Stack#sync_github` in full, ideally in a live Devin session with complete file access.
