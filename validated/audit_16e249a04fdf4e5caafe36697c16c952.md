### Title
Cross-repository status forgery via SHA collision — `StatusHandler#process` writes statuses without repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack filter, unlike the `Handler` base class's `stacks` helper (which scopes by `payload.dig('repository','full_name')`) that other handlers (e.g. pull_request handlers) use. `verify_signature` in `WebhooksController` only proves the payload was signed by the sender repository's GitHub App secret; it never constrains which `Commit` records the handler is allowed to touch. Because git SHAs are content-addressed and identical commits (e.g., empty commits, cherry-picks, shared merge bases) can exist as `Commit` rows in multiple stacks/repositories that share history, a webhook authenticated for attacker-controlled repository A can create a `Status` on a `Commit` row that actually belongs to victim repository B's stack, as long as both stacks recorded a commit with that same `sha`.

### Finding Description
The broken binding: the system should enforce `status.repository == commit.stack.repository` for every `Status` created from a webhook, but `StatusHandler#process` enforces no such equality — it binds purely on `sha`, not on `(sha, repository)`.

Path: `POST /webhooks``WebhooksController#create` → `verify_signature` (authenticates that the payload signature matches the GitHub App for `repository_owner`, not that the `sha` belongs to that repository) → `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` → `StatusHandler.call(params)` → `StatusHandler#process`:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

Every `Commit` row across every stack/repository that shares this exact `sha` gets a new `Status` row via `commit.create_status_from_github!(params)` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) . This directly affects `Commit#blocked?` (via `stack.blocking_statuses` and `blocking?`) and `Commit#deployable?` [4](#0-3) , and can trigger `stack.schedule_merges` and `ContinuousDeliveryJob` via `add_status`/`schedule_continuous_delivery` [5](#0-4) [6](#0-5) .

Contrast with the base `Handler` class, which provides a `stacks` method specifically to scope by the reporting repository: `Repository.from_github_repo_name(repository_name)&.stacks` [7](#0-6) . `StatusHandler` does not use this scoping at all, unlike other handlers in the codebase.

Why guards fail: `verify_signature` authenticates the sender's identity as the owner of `repository_owner`/`repository.full_name` in the payload [2](#0-1) , but this says nothing about which `Commit` rows in the database correspond to that repository. Since `sha` is attacker-controlled and commits are looked up globally, an attacker who owns/controls a small repository can commit content whose SHA collides with a commit shared with (or previously observed in) a victim stack's history — e.g., an identical empty commit, a shared upstream commit that both repos have fetched, or a fork relationship — and then send a `status` event from their own (correctly signed) repository for that `sha` with `context: sonarqube`, `state: success`.

### Impact Explanation
If the victim stack has `blocking_statuses` configured requiring `sonarqube`, the forged `success` status for a shared/matching SHA can flip `Commit#blocking?` to false for that commit, changing `Commit#blocked?` for all newer undeployed commits in the victim stack [8](#0-7) , which changes `deployable?` and can unblock a deploy/merge (`stack.schedule_merges`, continuous delivery) that should have remained blocked. This is a payload from one repository mutating another repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius depends on SHA-collision availability across the fleet (shared forks/upstream mirrors increase likelihood), but the underlying missing-scoping bug is deterministic and repeatable for any pair of stacks that share a commit SHA.

### Likelihood Explanation
Preconditions: victim stack must have `blocking_statuses` configured to include the forged context (e.g., `sonarqube`); attacker must control/own a repository registered in Shipit (any developer can typically add their own repo/fork) and must find or engineer a `Commit` row shared by SHA with the victim stack (realistic in shared-fork/monorepo/mirrored-history setups, or when both stacks happen to import the same upstream commit). Attacker cost is a single signed webhook POST from their own repo — no privileged credentials needed beyond normal repository ownership. Fully repeatable per matching SHA.

### Recommendation
Scope `StatusHandler#process` to only the stacks/commits belonging to the reporting repository, using the same pattern as the base `Handler#stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, or add an explicit check `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (no live GitHub):
1. Create `repository_a` (attacker-owned, full_name `attacker/repo`) and `stack_a` with commit `commit_a` with `sha: "deadbeef..."`.
2. Create `repository_b` (victim) and `stack_b` with `blocking_statuses: ['sonarqube']`, a `commit_b` with the **same** `sha: "deadbeef..."`, and a newer undeployed `commit_b2`.
3. Assert baseline: `commit_b2.blocked?` is `true` (or `deployable?` is `false`) because no `sonarqube` success exists yet.
4. Build a `status` payload with `repository.full_name = 'attacker/repo'`, `sha: 'deadbeef...'`, `context: 'sonarqube'`, `state: 'success'`, and invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature, simulating a legitimately signed request from repo A).
5. Assert `commit_b.statuses.last.context == 'sonarqube'` and `commit_b.statuses.last.state == 'success'` even though the request only authenticated `attacker/repo`.
6. Assert `commit_b2.reload.blocked?` changed to `false` (or `deployable?` changed to `true`), demonstrating that repository B's stack state was mutated by a payload authenticated only for repository A.
