### Title
Missing Token-Lock Check in `handleERC20Transfer` / `handleERC721Transfer` Allows Locked-Token Transfers to Complete — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge enforces `onlyUnlockedToken` and `onlyRegisteredToken` guards on the **request** side of every ERC-20 and ERC-721 value transfer, but omits those same guards on the **handle** (completion) side. An owner who calls `lockToken` or `deregisterToken` to freeze a token on the destination bridge cannot prevent in-flight requests from being finalised by automated bridge operators, causing bridged assets to be transferred in violation of the owner's explicit freeze.

---

### Finding Description

`BridgeTokens.sol` exposes two owner-only controls:

* `lockToken(address _token)` — sets `lockedTokens[_token] = true` and emits `TokenLocked`. Its stated purpose is *"to prevent request token transferring."*
* `deregisterToken(address _token)` — removes the token from `registeredTokens` and clears `lockedTokens`. [1](#0-0) 

The **request** path enforces both guards via modifiers:

```solidity
function _requestERC20Transfer(...)
    internal
    onlyRegisteredToken(_tokenAddress)   // ← guard present
    onlyUnlockedToken(_tokenAddress)     // ← guard present
``` [2](#0-1) 

The **handle** path (called by bridge operators to finalise the transfer on the destination chain) has **neither guard**:

```solidity
function handleERC20Transfer(...)
    public
    onlyOperators          // only role check — no token-state check
{
    ...
    IERC20(_tokenAddress).safeTransfer(_to, _value);   // executes unconditionally
}
``` [3](#0-2) 

The identical omission exists in `BridgeTransferERC721.sol`:

```solidity
function handleERC721Transfer(...)
    public
    onlyOperators          // no onlyRegisteredToken / onlyUnlockedToken
{
    ...
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
}
``` [4](#0-3) 

---

### Impact Explanation

When the bridge owner locks a token on the **destination** bridge (e.g., in response to a security incident or a token contract upgrade), automated bridge operators that are already watching the source chain will continue to relay and call `handleERC20Transfer` / `handleERC721Transfer` for every pending `RequestValueTransfer` event. Because neither function checks `lockedTokens[_tokenAddress]` or `registeredTokens[_tokenAddress]`, the transfer executes and bridged ERC-20 / ERC-721 assets are moved to the recipient despite the owner's explicit freeze.

In `modeMintBurn` mode the impact is a **mint** of tokens that the owner intended to halt; in lock-and-release mode it is an **unauthorised transfer** of tokens held by the bridge contract. Both outcomes directly affect bridged assets. [5](#0-4) 

---

### Likelihood Explanation

Bridge operators in the Kaia service-chain architecture are automated relayers (`BridgeInfo.handleRequestValueTransferEvent`) that process every `RequestValueTransfer` event emitted on the counterpart chain without inspecting the current lock state of the destination bridge. [6](#0-5) 

The window between a `RequestValueTransfer` event being emitted on the source chain and the corresponding `handleERC20Transfer` call landing on the destination chain is non-zero (block confirmation latency). An owner who locks a token during this window cannot prevent the in-flight handle from completing.

---

### Recommendation

Add `onlyRegisteredToken` and `onlyUnlockedToken` modifiers to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guards already present on the request path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64  _requestedNonce,
    uint64  _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // add
    onlyUnlockedToken(_tokenAddress)     // add
{
```

Apply the same change to `handleERC721Transfer`. [7](#0-6) 

---

### Proof of Concept

1. Owner deploys a bridge pair (source chain Bridge A, destination chain Bridge B) with token `T` registered and unlocked on both sides.
2. User calls `requestERC20Transfer(T, recipient, 1000, 0, "")` on Bridge A. The call passes `onlyRegisteredToken` and `onlyUnlockedToken` on Bridge A. A `RequestValueTransfer` event is emitted with `requestNonce = N`.
3. Owner detects an anomaly and calls `lockToken(T)` on Bridge B. `lockedTokens[T]` is now `true` on Bridge B.
4. The automated bridge operator, watching Bridge A, picks up the event from step 2 and calls `handleERC20Transfer(txHash, from, recipient, T, 1000, N, blockNum, "")` on Bridge B.
5. `handleERC20Transfer` has no `onlyUnlockedToken` check. It passes `_lowerHandleNonceCheck`, votes through `_voteValueTransfer`, and executes `IERC20(T).safeTransfer(recipient, 1000)`.
6. 1 000 units of token `T` are transferred to `recipient` on Bridge B despite the owner's lock — the freeze is bypassed. [8](#0-7) [9](#0-8)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}
