Confirmed root cause: `Shipit::WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the HMAC secret) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — see [1](#0-0) . The signature is verified against `Shipit.github(organization: repository_owner)`'s `webhook_secret` [2](#0-1) . But once the signature is accepted, the event `payload` (the entire raw JSON body) is dispatched unmodified to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , and the base `Handler` resolves the stack to mutate using a **different field**, `payload.dig('repository', 'full_name')` [4](#0-3) , looked up via `Repository.from_github_repo_name` [5](#0-4) .

### Title
Webhook signature verifies `repository.owner.login`, but events mutate the stack identified by an unverified `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhook signature check authenticates the organization named in `repository.owner.login` (or `organization.login`), but the actual write target — the `Stack`/`Repository` acted upon by every handler — is selected from the independent `repository.full_name` field, which is never covered by the signature check binding.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload and fetches that organization's GitHub App config to verify `X-Hub-Signature` [6](#0-5) . This proves only that *some* org named `repository.owner.login` authorized the request (i.e., an attacker who legitimately owns/installs the GitHub App on `attacker-org/some-repo` and knows its `webhook_secret` can compute a valid signature for any payload body, since the secret is per-organization, not per-repository or per-payload-content).

Once verified, `create` hands the full JSON `params` to handlers unmodified [3](#0-2) . All handlers (`PushHandler`, `StatusHandler` via `Commit.where(sha:)`, pull-request handlers, etc.) resolve the target `Stack`/`Repository`/`Commit` from `repository.full_name` through `Handler#stacks` → `Repository.from_github_repo_name` [4](#0-3) . Nothing ties `repository.full_name` back to the organization that was actually verified (`repository.owner.login`); a payload can set them to different values.

This is the same trust-binding class as the reported bug (a control that gates on field A while a later, more consequential action reads unguarded field B): the equality that should hold is `verified_organization == owner_of(repository.full_name)`, but the code never enforces it.

### Impact Explanation
An attacker who runs their own GitHub organization/App installation (a completely unprivileged actor with respect to any *other* Shipit-tracked repository) can forge a webhook body where `repository.owner.login` is set to their own org (so the HMAC check passes using their own known secret) but `repository.full_name` is set to `victim-org/victim-repo`. This lets them:
- Inject a fake `push` payload that triggers `GithubSyncJob`/`sync_github` on the victim stack with an attacker-chosen `after` SHA, or
- Inject fake `status`/`check_suite` payloads that mark arbitrary commits on victim stacks as green CI, satisfying `deployable?`/merge-queue checks, or
- Trigger `membership`/`pull_request` handlers that mutate Teams, Users, or `MergeRequest` state tied to a repository the attacker does not control.

This is a cross-repository write achieved purely by controlling one's own webhook secret — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Medium-High for any Shipit instance configured with the documented multi-organization `github:` section (`config/secrets.yml` supports per-org `webhook_secret`s, see `docs/setup.md`), since any org owner in that list can forge cross-repo events. Exploitability depends on the target repository/stack already existing in Shipit's DB (`Repository.from_github_repo_name` returns nil otherwise) and on which event types have consequential side effects (status/push are the most impactful).

### Recommendation
After verifying the signature with the organization derived from `repository.owner.login`, re-validate that `repository.full_name`'s owner segment matches that same verified organization before dispatching to handlers (e.g., reject if `repository.full_name.split('/').first.downcase != repository_owner.downcase`), or have handlers exclusively derive both the signing organization and the target repository from the same, single trusted payload path.

### Proof of Concept
1. Attacker owns `attacker-org` with a Shipit GitHub App installed, and knows its `webhook_secret`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `X-Hub-Signature` is computed with `attacker-org`'s `webhook_secret` — `verify_signature` passes because it only checks `repository.owner.login` [2](#0-1) .
4. `PushHandler#process` resolves stacks via `repository.full_name` = `victim-org/victim-repo` [7](#0-6) [4](#0-3) , enqueuing `GithubSyncJob` for the victim's stack even though the attacker never authenticated as `victim-org`.

*Note: I was unable to fully trace whether `Shipit.github(organization:)`'s config lookup raises `GithubOrganizationUnknown` for organizations not present in `secrets.yml`, which would limit this to configurations that list multiple organizations. This limits the PoC to multi-org Shipit deployments; single-org deployments are not exploitable this way since the signature and full_name would necessarily belong to the same (only) configured org.*

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post

      head(422) unless verified

      Rails.logger.info([
