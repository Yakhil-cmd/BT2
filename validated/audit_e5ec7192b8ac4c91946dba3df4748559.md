## Title
Missing null check on `storage.assocStableUnits[trigger.unit]` allows an unprivileged unit poster to crash the node during AA-trigger execution - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` guards against a duplicate primary AA trigger by reading `storage.assocStableUnits[trigger.unit].count_aa_responses` without first checking that the cache entry exists: [1](#0-0) 

Elsewhere in the very same file, the developers explicitly guard against exactly this situation — a stable unit missing from `storage.assocStableUnits` — by throwing a controlled error only after an explicit `if (!objUnitProps)` check: [2](#0-1) 

The line at 1861 lacks that guard, so if `trigger.unit` is ever absent from `storage.assocStableUnits` at the moment `handleTrigger` runs for a primary (non-secondary, non-air) trigger, the property access `storage.assocStableUnits[trigger.unit].count_aa_responses` throws `TypeError: Cannot read properties of undefined`. This is analogous to CVE-2016-2391's root cause: a code path assumes a supporting data structure (there, the OHCI `eof_timer`; here, the in-memory stable-unit cache entry) is always initialized/present when a specific state is reached, and dereferences it without a null check, causing the process to crash.

### Finding Description
`handleTrigger()` is invoked for every AA trigger — i.e., for any unit an unprivileged user posts that pays to an AA address, once that unit's MCI is stabilized (`main_chain.js` → `handleAATriggers()` → `aa_composer.handlePrimaryAATrigger()` → `handleTrigger()`): [3](#0-2) 

Inside `handleTrigger`, for non-secondary triggers, the code checks whether the trigger unit has already produced AA responses (anti-double-trigger protection) by indexing directly into the `assocStableUnits` in-memory cache: [4](#0-3) 

`storage.assocStableUnits` is an in-process cache populated as units are stabilized (`main_chain.js`, `markMcIndexStable`), and entries can be evicted from memory over time (`storage.js` memory/cache reset and min-retrievable-MCI pruning routines). By contrast, `handlePrimaryAATrigger` (the normal caller of `handleTrigger`) explicitly checks for this exact possibility and throws a controlled error instead of crashing on unguarded dereference: [5](#0-4) 

The presence of this defensive check in one place, but not in the `handleTrigger` bounce-guard at line 1861, indicates the invariant "trigger.unit is always in `assocStableUnits`" is not reliably enforced across all call paths into `handleTrigger` (e.g., replayed/retried triggers from `aa_triggers` table rows processed after a restart, deferred stability advancement via `determineIfStableInLaterUnitsAndUpdateStableMcFlag`/`stabilizeMci`, or dry-run/AIR-adjacent code paths that reuse the same `handleTrigger` function with different `trigger_opts`). If any such path reaches line 1861 with `trigger.unit` no longer resident in the cache, the resulting uncaught `TypeError` will propagate out of the deeply nested async callback chain and crash the Node.js process, since there is no surrounding `try/catch` at this call site.

### Impact Explanation
A crash triggered here is not a local resource-exhaustion or benign error — it terminates the entire ocore process on any full node that executes AA triggers (i.e., every full/witness node processing the DAG, since AA-trigger execution is mandatory consensus-relevant work, not merely local bookkeeping). Because the crash happens mid-way through committing a stabilized MCI and its AA responses, repeated or simultaneous crashes across nodes create a scenario where the network can become unable to reliably confirm new units built on top of that AA response, matching the accepted impact category "network unable to confirm new units" / node disagreement risk if different nodes crash/restart at different points in the stabilization pipeline.

### Likelihood Explanation
The trigger condition (`trigger.unit` missing from `assocStableUnits` at trigger-execution time) is not attacker-controlled data validated by `validation.js`; it is an internal consistency assumption about cache freshness. Reaching it requires a specific but plausible interaction between AA-trigger scheduling/replay logic and cache lifecycle (e.g., following a restart with pending `aa_triggers` rows, or deep MCI-stabilization catch-up chains where multiple MCIs are stabilized in one pass before `assocStableUnits` bookkeeping catches up). I could not fully confirm from the available code excerpts whether current cache-population ordering (`markMcIndexStable` populates `assocStableUnits` synchronously before `finishMarkMcIndexStable()`/`handleAATriggers()` fires) makes this scenario unreachable in the common single-MCI-per-write case, so likelihood is assessed as plausible-but-unconfirmed for a specific reachable primitive, while the missing guard itself is a definite defect judged against the codebase's own explicit-null-check convention at line 104-106.

### Recommendation
Add the same defensive check used in `handlePrimaryAATrigger` before line 1861: verify `storage.assocStableUnits[trigger.unit]` exists, and if not, either fetch/hydrate the unit props from storage (`storage.readUnitProps`) or fail the trigger gracefully via `bounce()`/a controlled error rather than letting a raw property access throw.

### Proof of Concept
Not verifiable end-to-end without executing the full node stack; the concrete PoC is a code-path argument, not a demonstrated exploit:
1. Cause `trigger.unit` to be evicted from (or never present in) `storage.assocStableUnits` while an `aa_triggers` DB row still references it (e.g., simulate by directly calling `aa_composer.handleTrigger` with a `trigger.unit` value deleted from `storage.assocStableUnits` and `mci >= constants.pemCurvesFixMci`, `bSecondary=false`, `trigger_opts.bAir` falsy).
2. Observe that `storage.assocStableUnits[trigger.unit].count_aa_responses` throws `TypeError: Cannot read properties of undefined (reading 'count_aa_responses')`, uncaught by any surrounding handler, terminating the process — analogous to the QEMU OHCI NULL pointer dereference caused by referencing an `eof_timer` that was assumed, but not verified, to be initialized.
