### Title
`WebhooksController#verify_signature` authenticates against `organization.login` while `CheckSuiteHandler#process` writes based on `repository.full_name`, letting a no-secret org's webhook unlock refreshes on any other org's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using `repository.owner.login` with a fallback to `organization.login` [1](#0-0) , but `Handler#stacks`/`CheckSuiteHandler#process` scope which repository's stacks get mutated using `repository.full_name` from the very same payload [2](#0-1) . These two values are never checked for equality, so a payload can be "signed" (or unsigned) against one organization while its mutating effect lands on a completely different repository's stack.

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes `repository_owner (used for HMAC verification) == owner(repository.full_name) (used for the write in CheckSuiteHandler#process)`. Nothing in the code enforces this equality.

Trace:
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no configured `webhook_secret`: `return true unless webhook_secret` [4](#0-3) . `@webhook_secret` is `@config[:webhook_secret].presence`, i.e. optional per organization [5](#0-4) .
- If the payload omits `repository.owner.login` but includes `organization.login` naming an organization that is configured in Shipit but has no `webhook_secret` set, verification passes trivially with no HMAC check at all.
- `CheckSuiteHandler.call(params)` is then invoked and its `process` method resolves the actual mutation target independently, via `Handler#stacks`, using `payload.dig('repository','full_name')` - a field taken from the same untrusted body, decoupled from whatever was used for `repository_owner` [2](#0-1) .
- `CheckSuiteHandler#process` then looks up commits on that repository's stacks matching `head_sha`/`head_branch` and calls `schedule_refresh_check_runs!` on them [6](#0-5) .

Attacker request: `POST /webhooks` with header `X-Github-Event: check_suite` (any/no `X-Hub-Signature` value) and body:
```json
{
  "organization": {"login": "no-secret-org"},
  "repository": {"full_name": "victim-org/victim-repo"},
  "check_suite": {"head_sha": "<victim-commit-sha>", "head_branch": "<victim-branch>"}
}
```
`drop_unhandled_event` passes (check_suite is handled), `repository_owner` resolves to `"no-secret-org"` via the fallback, `Shipit.github(organization: "no-secret-org")` must resolve without raising `GithubOrganizationUnknown`, and `verify_webhook_signature` short-circuits to `true`. The handler then acts on `victim-org/victim-repo`'s stacks/commits, an organization/repository whose ownership was never authenticated in this request.

None of the existing guards catch this: `drop_unhandled_event` only filters by event type; `ExplicitParameters` schema for `CheckSuiteHandler` only requires `check_suite.head_sha`/`head_branch`, not repository/organization consistency; there is no `require_permission!`/session check on this unauthenticated webhook endpoint; and `verify_signature` never cross-checks the org it authenticated against the org implied by `repository.full_name`.

### Impact Explanation
An attacker who can get one Shipit-configured organization to have no `webhook_secret` (misconfiguration, but explicitly permitted by the optional `presence` check in `GitHubApp`) gains the ability to trigger `schedule_refresh_check_runs!` on commits belonging to any other organization/repository known to Shipit, by simply naming that other repository's `full_name` in the payload while authenticating (trivially, since no secret exists) against the unrelated organization. This is a cross-tenant write: a payload nominally scoped/verified for one repository mutates another repository's stack/commit state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any repository/commit combination known to the Shipit instance, for as long as the no-secret organization remains configured.

### Likelihood Explanation
This requires a specific precondition outside the attacker's control: at least one organization already configured in this Shipit instance's `github_organizations`/apps config must have no `webhook_secret` set. If that precondition holds, exploitation is trivial and free (no secrets, no session, no privileged role needed - just an HTTP POST). If no such organization exists in the deployment (i.e., every configured org enforces a webhook secret), the attack is not reachable, because `Shipit.github(organization: ...)` would raise `GithubOrganizationUnknown` for arbitrary attacker-chosen org names, and legitimately configured orgs would enforce HMAC verification. The vulnerability is therefore real and demonstrable in code, but its exploitability is conditional on this operator misconfiguration rather than solely attacker-controlled input.

### Recommendation
Do not derive the authentication organization and the mutation target from independent, un-cross-checked payload fields. Concretely: (1) after successfully resolving the repository/stack in each handler, verify that the resolved repository's owner matches the organization used for `verify_signature`; (2) do not allow `verify_webhook_signature` to silently return `true` when a configured organization lacks a secret - treat a missing `webhook_secret` for a known organization as a hard misconfiguration error (fail closed, not open); (3) prefer `repository.full_name`'s owner (not `organization.login`) as the sole source of truth for both signature verification and stack resolution, eliminating the fallback-to-different-field ambiguity.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_tenant_test.rb
require "test_helper"

module Shipit
  class WebhooksControllerCrossTenantTest < ActionController::TestCase
    tests WebhooksController

    setup do
      # Precondition: "no-secret-org" is configured in Shipit but has no webhook_secret.
      Shipit.stubs(:github).with(organization: "no-secret-org").returns(
        GitHubApp.new("no-secret-org", { app_id: 1, installation_id: 1 })
      )

      @stack = shipit_stacks(:shipit) # victim-org/victim-repo stack fixture
      @commit = @stack.commits.create!(sha: "f" * 40, branch: @stack.branch)
    end

    test "check_suite payload authenticated against org A mutates repo of org B" do
      payload = {
        organization: { login: "no-secret-org" },
        repository: { full_name: @stack.repository.full_name }, # no `owner` key
        check_suite: { head_sha: @commit.sha, head_branch: @stack.branch }
      }.to_json

      # binding under test: repository_owner used for verify_signature ("no-secret-org")
      # != owner(repository.full_name) used for the actual write (@stack.repository.owner)
      refute_equal "no-secret-org", @stack.repository.owner

      @request.headers["X-Github-Event"] = "check_suite"
      @request.headers["X-Hub-Signature"] = "sha1=not-a-real-signature"

      Commit.any_instance.expects(:schedule_refresh_check_runs!).once

      post :create, body: payload

      assert_response :ok
    end
  end
end
```
This demonstrates that verification succeeds against `"no-secret-org"` while the write (`schedule_refresh_check_runs!`) is dispatched against the victim commit/stack belonging to a different, never-authenticated organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
