### Title
Removing an address from an asset's attestor whitelist permanently freezes that address's already-held tokens - ([File: validation.js])

### Summary
For assets defined with `spender_attested: true`, transferring (including redeeming/moving) the asset requires the **sender/owner address** of the input being spent to currently be on the asset's attestor whitelist (`asset_attestors`), not just the recipient. Because the check is evaluated against the latest attestor list at validation time rather than the list in effect when the tokens were received, an address that legitimately held asset tokens can be de-whitelisted later (asset issuer publishes an `asset_attestors` update removing it), permanently freezing the tokens that address already owns — mirroring the reported UXDController bug class where removing an asset from a whitelist also blocks redemption of already-deposited/backing value.

### Finding Description
When validating a `payment` message for an asset with `spender_attested` enabled, the transfer branch in `validatePaymentInputsAndOutputs` requires the **owner address of the input being spent** to be in `objAsset.arrAttestedAddresses` (the current/latest attestor list as of `last_ball_mci`): [1](#0-0) 

The list itself is loaded from the latest `asset_attestors` unit that is stable before `last_ball_mci`, i.e., whoever last updated the attestor list fully replaces the set of "whitelisted" spenders: [2](#0-1) 

There is no separate "redeem" or "burn" path that bypasses this attestation check — `owner_address` (the sender of the coin being spent) is checked identically whether the destination is another user, the definer (redemption/auto-destroy), or oneself as change. Even the auto-destroy path back to the definer still requires the owner to be attested: [3](#0-2) 

Thus, exactly like the UXDController bug class — where removing an asset from `whitelistedAssets` blocks `_redeem` for users who already hold backing tokens — an asset issuer here can publish a new `asset_attestors` list (an `app: "asset_attestors"` message) that drops an address previously deemed attested. Any tokens that address already received while attested become permanently unspendable: it can no longer transfer them to anyone, including back to the definer to redeem/settle, because the spend-side check always evaluates against the *current* attestor list, not the list at the time the funds were received.

### Impact Explanation
This causes an irreversible fund freeze for legitimate asset holders. Once de-whitelisted, an address's asset balance is permanently locked in the DAG with no on-chain path to move or redeem it — not even a definer-directed burn/return, since the owner-side attestation check has no exception for that case. This is exactly the "AA/user fund freezing" class of impact called out in the validation rules (Medium severity): unauthorized asset issuers can trap user funds by unilaterally revoking attestation for any address, regardless of whether that address violated any rule, and regardless of the tokens already being legitimately held.

### Likelihood Explanation
Any asset defined with `spender_attested: true` (a supported, documented asset feature used for regulated/whitelisted assets) is affected. The asset issuer (definer) can trigger this at any time simply by publishing a new `asset_attestors` update message that omits a previously-attested address — a single unprivileged transaction from the definer, requiring no coordination with the affected address. This is a normal, reachable action within the intended asset feature set, not a contrived edge case.

### Recommendation
Decouple the "spend condition" whitelist from the "redeem" path for spender-attested assets. Specifically:
- Evaluate the attestation requirement for the *owner_address* using the attestor list in effect at the time the output was created (i.e., historically, based on when the source unit became stable), rather than re-checking against the latest list at spend time; or
- Provide an explicit exception allowing a currently-non-attested owner to send solely to the asset's `definer_address` (redemption/return), similar to how `is_transferrable` already carves out sending to the definer as an allowed case, so at minimum funds can always be redeemed even if new transfers to third parties are blocked.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, initial attestors `[X]`.
2. User X receives a payment of asset A (valid, since X is attested at the time).
3. Definer publishes a new `asset_attestors` message for asset A listing attestors `[Y]` only (X removed).
4. X attempts to transfer/redeem their held asset-A tokens (to anyone, including the definer for redemption).
5. Validation in `validatePaymentInputsAndOutputs` loads the asset via `storage.loadAssetWithListOfAttestedAuthors`, which resolves `arrAttestedAddresses` from the latest `asset_attestors` unit (now `[Y]`), and rejects the input because `owner_address` (X) is not in `arrAttestedAddresses`: [4](#0-3) 
6. X's asset-A balance is now permanently unspendable — confirming the freeze.
