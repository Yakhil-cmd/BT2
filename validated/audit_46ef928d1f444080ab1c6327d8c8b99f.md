## Confirmed vulnerability

`StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) breaks the binding: **organization authenticated by the webhook signature ≠ repository whose commit/status data is actually written.**

### Finding Description

The webhook signature check in `WebhooksController#verify_signature` selects which GitHub App/organization secret to validate against using only the `repository.owner.login` (or `organization.login`) field of the payload, and verifies the signature over the raw body with that org's secret: [1](#0-0) 

Every other default handler scopes its side effects to the repository named in the payload — e.g. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` before acting: [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never uses the `repository` field at all. Its `params` block only requires `sha` and `state`, and it writes a status to **every `Commit` row in the entire installation that shares that sha**, regardless of which repository/organization owns it: [4](#0-3) 

So the equality that should hold — "organization whose secret validated this request" == "repository/stack whose commit gets the status written" — is not enforced. The signature only proves the request came from *some* organization configured in `Shipit.github`; it does not prove that organization owns the commit identified by `sha`. Because git SHAs are content-addressed and frequently shared across forks/mirrors that are tracked by different Shipit stacks belonging to different organizations, a webhook validly signed by Organization A's secret can be used to write a fabricated commit status onto a commit that is actually tracked under Organization B's stack — as long as the same sha happens to exist in both.

`create_status_from_github!` → `add_status` then reacts to this forged status: it can flip the commit's simple state to `success`/`pending`, which triggers `stack.schedule_merges` and continuous-delivery scheduling for the *victim* stack: [5](#0-4) [6](#0-5) 

This is the direct analog of the report's "checksum/signature" bug class: the verified signature only binds the *sender's organization*, but the payload field actually acted upon (`sha`, which determines *which repository's data* is mutated) is never checked against that organization's repositories — exactly "an organization that authenticated versus the repository that is written."

### Impact Explanation

An unprivileged actor who can legitimately trigger a GitHub `status` webhook for **any** organization/repo configured in the same Shipit instance (e.g. a public-repo contributor whose CI posts commit statuses, requiring no Shipit secret) can inject arbitrary commit statuses (`state`, `context`, `description`, `target_url`) onto commits of a **different, unrelated stack**, as long as the sha coincides (common with forks, vendored/mirrored repos, or cherry-picked/rebased commits shared across repositories). This can:
- Mark CI as `success`/`pending` on a victim stack's commit, triggering `ProcessMergeRequestsJob`/continuous deployment (`stack.schedule_merges`), potentially causing an **unauthorized deploy or merge** on a stack the attacker has no relationship to.
- Poison the merge-queue status checks (`MergeRequest::StatusChecker`) used to gate automated merges: [7](#0-6) 

This satisfies the High-impact bar ("escalation into authorization... unauthorized deploy" class) without requiring the victim organization's `webhook_secret`, an `ApiClient` token, or repository write access — only a valid signature from *any one* configured organization is needed, which the attacker can obtain by legitimately interacting with their own (or any other tracked) repository's CI.

### Likelihood Explanation

Moderate. It requires: (1) a Shipit install tracking multiple stacks/organizations sharing the `github` webhook endpoint, and (2) a commit sha collision between the attacker-controlled repository and the victim stack's repository. Sha collisions are realistic in common setups — forked repositories, repositories mirrored into multiple orgs, or shared submodule/vendor commits — making this practically reachable in multi-tenant Shipit deployments, which the engine explicitly supports via the "Using Multiple GitHub Applications" configuration documented in `docs/setup.md`.

### Recommendation

`StatusHandler#process` (and any other handler that doesn't already scope through `stacks`) must require and verify the `repository` field from the payload and filter `Commit` lookups to the stacks/repositories owned by the organization that produced a verified signature, mirroring the pattern used in `PushHandler`/`Handler#stacks`. Additionally, verified webhook signatures should be tied not just to the request-level organization lookup but to an explicit check that the resolved commit's stack.repository actually belongs to that organization before any status is written.

### Proof of Concept

1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App/webhook secret (per the documented multi-org `github:` config).
2. Stack `org-b/victim-repo` tracks a commit with sha `abc123...` (e.g., because `victim-repo` is a fork of, or shares history with, `org-a/some-repo`).
3. As a normal (unprivileged) contributor to `org-a/some-repo`, trigger a legitimate `status` webhook event for commit `abc123...` with `state: success` (e.g. via a CI integration you control that posts a GitHub status) — this is signed by `org-a`'s webhook secret and passes `verify_signature` because `repository.owner.login == "org-a"`.
4. `WebhooksController#create` dispatches to `StatusHandler`, which executes `Commit.where(sha: "abc123...").each { |c| c.create_status_from_github!(params) }` — this matches and mutates the commit belonging to `org-b/victim-repo`'s stack, even though the request was never authenticated for `org-b`.
5. Observe `org-b`'s stack's commit status flip to `success`, and `ProcessMergeRequestsJob`/continuous delivery being scheduled on the victim stack.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
