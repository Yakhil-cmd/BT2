### Title
Webhook signature verification keys off `repository.owner.login` while event processing acts on `repository.full_name`, letting a payload spoof which org's secret is checked - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, the field used to select *which* organization's webhook secret validates a request (`repository.owner.login`) is not the same field used to determine *which* repository/stack the event is applied to (`repository.full_name`). An attacker who controls the raw JSON body of an unauthenticated webhook POST can decouple these two fields, causing the signature check to run against a different (weaker or unset) organization's secret while the event content still targets a stack belonging to another, properly-protected organization.

### Finding Description
`WebhooksController#verify_signature` derives the authenticating organization from the payload itself, before any signature has been validated: [1](#0-0) 

Specifically:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value is passed into `Shipit.github(organization: repository_owner)`, which in the documented multi-organization configuration (`secrets.github` keyed by org name, each with its own `webhook_secret`) selects a distinct `GitHubApp`/secret per organization: [2](#0-1) 

Meanwhile, event processing never looks at `repository.owner.login` again. Every `Handler` subclass resolves the target repository purely from `repository.full_name`: [3](#0-2) 

Both `repository.owner.login` and `repository.full_name` are independent keys inside the same attacker-supplied, pre-verification JSON body (`params = JSON.parse(request.raw_post)` happens in `create`, and `repository_owner` is read from the same unverified `params` in the `before_action`). Nothing enforces that `full_name`'s owner segment equals `owner.login`. This breaks the intended binding: *organization whose secret authenticated the request* == *repository being written to by the handler*.

`GitHubApp#verify_webhook_signature` further makes this a live issue whenever an organization has no `webhook_secret` configured (a supported configuration, see `webhook_secret: # nil` in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`): [4](#0-3) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

### Impact Explanation
An attacker who knows (or is not required to know, if unset) the webhook secret for **any** organization configured on the Shipit instance can craft a payload with `repository.owner.login` set to that weak/unsecured organization while `repository.full_name` points at a stack tracked under a different, properly-secured organization. The signature check in `verify_signature` passes (using the weak org's secret, or trivially if that org has no secret at all), yet `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches handlers that operate on the victim repository resolved via `full_name`. Depending on handler, this can:
- Force a `GithubSyncJob` (`PushHandler`) against the victim stack.
- Inject a fabricated commit status via `StatusHandler#process` (`commit.create_status_from_github!`) for a specific `sha`, which can flip CI status to "success" on a stack in the protected organization, satisfying `required_statuses` and enabling continuous deployment / merge-queue eligibility on a repository the attacker has no access to.

This crosses an authentication boundary equality (`authenticating org == acted-upon repository owner`) without requiring the target organization's own secret, potentially enabling an unauthorized deploy/merge path via forged CI status.

### Likelihood Explanation
This requires:
1. A Shipit instance configured with multiple GitHub organizations (a supported, documented configuration — not requiring undocumented mounting).
2. At least one configured organization with a missing or attacker-known `webhook_secret`.

Given multi-tenant Shipit setups are explicitly documented and exemplified (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`), and operators may reasonably leave a lower-stakes/test organization without a webhook secret, this is a plausible misconfiguration rather than a purely theoretical one. However, exploitation strength is bounded by handler capability (`StatusHandler` is the most actionable path found for driving toward an unauthorized deploy).

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) used to select the signing organization matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the request otherwise. Alternatively, resolve the target `Repository`/`Stack` using the same organization value that was used to verify the signature, rather than trusting `full_name` independently.

### Proof of Concept
Assume `secrets.github` configures `OrgWeak` (no `webhook_secret`) and `OrgStrong` (repo `OrgStrong/victim-repo` tracked as a stack with `required_statuses` gating deploys).

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any value):
```json
{
  "repository": {
    "owner": { "login": "OrgWeak" },
    "full_name": "OrgStrong/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
2. `WebhooksController#repository_owner` returns `"OrgWeak"`; `Shipit.github(organization: "OrgWeak")` yields a `GitHubApp` with `webhook_secret` nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the actual signature header.
3. `create` proceeds and `Shipit::Webhooks.for_event('status')` dispatches `StatusHandler`, which resolves the commit purely by `sha` (global, not scoped by repo) and calls `commit.create_status_from_github!(params)` — forging a passing CI status on the victim commit belonging to `OrgStrong/victim-repo`, without ever presenting `OrgStrong`'s webhook secret.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
