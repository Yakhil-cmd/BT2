### Title
Share-price manipulation via zero-balance "initial deposit" branch enables fund drain in the market-maker AA - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled Uniswap-like market-maker Autonomous Agent (`uniswap_like_market_maker.oscript`) computes new LP-share (`mm_asset`) issuance using an `OR` condition that treats a *momentary* zero balance of either side of the pool as a fresh "initial deposit," minting the *entire current byte balance* of the AA as shares to whoever triggers it at that instant — instead of a proportional amount of the actual deposit. This mirrors the Sonne Finance root cause: an internal exchange-rate/share computation that can be forced into an edge-case state by ordinary user-driven operations, letting one caller mint disproportionate claims on pooled funds and drain value from other depositors.

### Finding Description
In the "invest in MM" case: [1](#0-0) 

```
{ // invest in MM
    if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
            $issue_amount = balance[base];
            return;
        }
        ...
    }`,
    ...
}
```

`$asset_balance` and `$bytes_balance` represent the pool's pre-trigger balances (current on-chain `balance[...]` minus this trigger's own contribution). The `if` uses `OR`, so the "initial deposit" branch fires whenever **either** side is zero, not only when the pool has never been used. Because the AMM also allows draining one side of the pool entirely via the "exchange asset to bytes" / "exchange bytes to asset" branches (lines 102-145), it is trivial for legitimate trading activity (or an attacker) to bring `$asset_balance` to exactly 0 while `$bytes_balance` (and `var['mm_asset_outstanding']`, i.e., shares already owned by other investors) remains large and non-zero.

Once `$asset_balance == 0`, the very next "invest" trigger — even one contributing a negligible amount of bytes and asset — takes the branch that sets `$issue_amount = balance[base]`, i.e., **the AA's entire byte balance**, and mints that many `mm_asset` shares to the triggering address: [2](#0-1) 

```
messages: [
    { app: 'payment', payload: { asset: "{$mm_asset}", outputs: [{address: "{trigger.address}", amount: "{ $issue_amount }"}] } },
    { app: 'state', state: `{ var['mm_asset_outstanding'] += $issue_amount; }` },
]
```

This is analogous to the Compound-v2 "donation attack" root cause described in the report: an attacker manipulates the state (here, the pool's asset-side balance) into an edge condition so that the protocol's exchange-rate/share-minting formula (Sonne's `collateral factor`/exchange rate; here `$issue_amount`) produces a wildly incorrect, attacker-favorable result, at the expense of existing depositors/LPs.

### Impact Explanation
An attacker who forces (or opportunistically waits for) `$asset_balance == 0` can, with a single small AA trigger, mint LP shares equal to the AA's *entire byte balance* rather than a proportional share of their own deposit. Because `var['mm_asset_outstanding']` is incremented by this inflated `$issue_amount`, the attacker's shares become massively over-weighted relative to genuine LPs. They can then immediately "divest" (the case at lines 67-101) and claim a disproportionate fraction of both `base` and `$asset` balances held by the AA, draining value from other users' deposited funds — a concrete, unauthorized transfer of AA-held funds to the attacker (fund loss for other depositors), matching the "AA fund loss" impact category.

### Likelihood Explanation
Reaching `$asset_balance == 0` does not require any privileged access: any unprivileged address can post payments to the AA to swap out the entire asset-side balance via the existing "exchange asset to bytes" branch (especially easy on a lightly-used pool, or right after the pool is defined and has a small asset reserve), then immediately follow up with a minimal "invest" trigger. Both steps are ordinary AA triggers sent by any user, requiring no governance, no timelock exploitation, and no special permissions — directly analogous to how the Sonne attacker needed only to be the first to execute an already-public transaction.

### Recommendation
Change the "initial deposit" condition from `OR` to `AND` (or, better, gate strictly on `var['mm_asset_outstanding'] == 0`, which is the authoritative signal that no shares have ever been issued) so that the full-balance minting branch can only be taken exactly once, before any shares exist:
```
if (!var['mm_asset_outstanding']) { // true initial deposit
    $issue_amount = balance[base];
    return;
}
```
This prevents a transient zero balance on one side of the pool (reachable through normal trading) from being reinterpreted as a fresh, un-diluted initial deposit.

### Proof of Concept
1. AA is defined, `mm_asset` is created (case at lines 8-32), and one honest investor deposits, receiving `mm_asset_outstanding = N` shares proportional to `bytes_balance = B0`, `asset_balance = A0`.
2. Attacker drains the entire `$asset` side via the "exchange asset to bytes" case (lines 124-145), sending an amount of `$asset` such that `$new_bytes_balance` and remaining `$asset_balance` reach 0 (achievable since the formula allows swapping out all of one side, e.g., swapping `A0` worth of asset for close to all `bytes_balance`).
3. Immediately after, attacker sends a tiny "invest" trigger (`base > 1e5` and `asset > 0`, e.g., minimal required amounts). Since `$asset_balance == 0` at trigger time, the AA executes:
   `$issue_amount = balance[base]` — the *entire* current byte balance of the AA (which still includes the honest investor's residual byte value) — and mints that as `mm_asset` to the attacker, adding it fully to `mm_asset_outstanding`.
4. Attacker calls "divest" (lines 67-101) with their inflated `mm_asset` holding, receiving `investor_share * balance[$asset]` and `investor_share * balance[base]`, where `investor_share` is now dominated by the attacker's inflated share — extracting funds that rightfully belonged to the earlier honest investor.
