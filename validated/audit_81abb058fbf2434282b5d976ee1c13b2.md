### Title
Any single attacker-controlled commit permanently kills git-sync via the default `--max-failures=0` abort path - (File: main.go)

### Summary
`git-sync`'s main sync loop treats every `git.SyncRepo` failure as a strike against a configurable failure budget (`--max-failures`, default `0`). Because the default budget tolerates zero failures, a single deterministic git error caused by content in the very commit git-sync is told to track (e.g. a broken submodule reference, a colliding worktree path, or any other command that fails identically on every retry) causes git-sync to call `os.Exit(1)` and terminate the whole process, permanently halting synchronization for every consumer of that sidecar until an operator manually intervenes.

### Finding Description
The sync loop increments `failCount` on every error returned from `git.SyncRepo` and aborts the process once the effective failure limit is reached: [1](#0-0) 

By default `--max-failures` is `0`, meaning "any sync failure will terminate git-sync": [2](#0-1) 

`SyncRepo` performs a chain of git operations against whatever content is at the tracked `--ref` on every single loop iteration — `fetch`, `rev-parse`, `createWorktree` (`git worktree add`), `configureWorktree` (sparse-checkout apply, `reset --hard`, `git submodule update --init [--recursive]`), and `sanityCheckWorktree` (`git fsck`): [3](#0-2) [4](#0-3) 

Any of these operations failing deterministically for the commit currently at `--ref` (for example, a `.gitmodules` entry pointing to an unreachable/invalid submodule, or content that trips `git fsck --connectivity-only`) will fail identically on every retry, because the same broken hash is fetched and checked out each time. Since the default failure budget is `0`, the very first such failure trips the `os.Exit(1)` path in the main loop, unlike the withdrawal-queue analog where a single actor's action forces a shared protective mechanism (the queue) to activate for every other user — here a single attacker-influenced commit pushed to the tracked ref forces the shared sync process itself to terminate for every consumer relying on that `--link` symlink.

### Impact Explanation
Termination of the git-sync process is a persistent, total denial of the sync service (not merely a delay): the `--link` symlink stops updating, the HTTP readiness endpoint (`--http-bind`) stops reporting a healthy `200`, and in Kubernetes the sidecar container enters `CrashLoopBackOff`. Because git-sync re-fetches and re-attempts the exact same broken ref on restart, the container will continue to crash-loop indefinitely until an operator either reverts/fixes the offending commit upstream, changes `--ref`, or redeploys with a higher/negative `--max-failures`. This matches the "persistent sync denial" impact category.

### Likelihood Explanation
Any party with the ability to influence what commit is fetched at `--repo`/`--ref` (a contributor with push/PR-merge rights on the tracked branch, a compromised upstream account, or an attacker who can move a tracked tag/branch pointer) can trigger this with a single push — no special git-sync flags beyond defaults are required, since `--max-failures` defaults to `0`. This requires only content-level control of the tracked ref, which is exactly the "untrusted repo content" surface called out as in-scope.

### Recommendation
- Change the default `--max-failures` to a small positive retry budget (or require it be set explicitly) rather than `0`, so a single bad commit does not immediately kill the process.
- Distinguish between transient failures (network/timeout) and deterministic content failures (submodule/checkout/fsck errors on the same hash) — for the latter, keep serving the last-known-good `--link` target and surface an alert/metric instead of exiting the process.
- Document and encourage operators to run with `--max-failures=-1` (or a bounded retry count) in production so a single malicious/broken commit cannot force a full outage of the sidecar.

### Proof of Concept
1. Point git-sync at a repository/ref where an attacker (a branch contributor) can push a commit, using default flags (`--max-failures` unset, i.e. `0`):
   ```
   git-sync --repo=<repo> --ref=<tracked-branch> --root=/tmp/root --link=link
   ```
2. Attacker pushes a commit to `<tracked-branch>` containing a `.gitmodules` entry referencing a submodule URL/commit that cannot be resolved (or any content that reliably fails `git submodule update --init --recursive` or `git fsck --connectivity-only`).
3. On the next poll, `git.SyncRepo` fails at `configureWorktree`/`sanityCheckWorktree` (main.go:1733-1747, 1858-1897), `failCount` becomes `1`, `getMaxFailures()` returns `0`, and the process calls `os.Exit(1)` at main.go:1061.
4. Because the same broken commit is fetched every retry, every subsequent restart of the container repeats the same failure, producing a permanent `CrashLoopBackOff` and a fully halted sync for that sidecar until an operator manually fixes the upstream ref or redeploys with a different `--max-failures`/`--ref`.

```go
// SyncRepo syncs the repository to the desired ref, publishes it via the link,
// and tries to clean up any detritus.  This function returns whether the
// current hash has changed and what the new hash is.
func (git *repoSync) SyncRepo(ctx context.Context, syncHooks syncHooks) (bool, string, error) {
	git.log.V(3).Info("syncing", "repo", redactURL(git.repo))

	if err := syncHooks.refreshCreds(ctx); err != nil {
		return false, "", fmt.Errorf("credential refresh failed: %w", err)
	}

	// Initialize the repo directory if needed.
	if err := git.initRepo(ctx); err != nil {
		return false, "", err
	}

	// Find out what we currently have synced, if anything.
	var currentWorktree worktree
	if wt, err := git.currentWorktree(); err != nil {
		return false, "", err
	} else {
		currentWorktree = wt
	}
	currentHash := currentWorktree.Hash()
	git.log.V(3).Info("current state", "hash", currentHash, "worktree", currentWorktree)

	// This should be very fast if we already have the hash we need. Parameters
	// like depth are set at fetch time.
	if err := git.fetch(ctx, git.ref); err != nil {
		return false, "", err
	}

	// Figure out what we got.  The ^{} syntax "peels" annotated tags to
	// their underlying commit hashes, but has no effect if we fetched a
	// branch, plain tag, or hash.
	var remoteHash string
	if output, _, err := git.Run(ctx, git.root, "rev-parse", "FETCH_HEAD^{}"); err != nil {
		return false, "", err
	} else {
		remoteHash = strings.Trim(output, "\n")
	}
```
