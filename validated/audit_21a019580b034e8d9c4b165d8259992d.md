### Title
Griefing DOS of `SystemInstruction::CreateAccount` via pre-funding target address with lamports - (File: `programs/system/src/system_processor.rs`)

### Summary
`system_processor::create_account` unconditionally rejects account creation if the destination account already holds any lamports (`to.get_lamports() > 0`), and any unprivileged party can add lamports to an arbitrary pubkey via a signed `SystemInstruction::Transfer` without the recipient's cooperation. An attacker who can predict a target address before it is created (e.g., a PDA, an ATA, or any deterministic account address used by a protocol/program) can transfer 1 lamport to it ahead of the legitimate creation transaction, permanently blocking that specific `CreateAccount` call with `SystemError::AccountAlreadyInUse` — the same "grief by inflating the observed balance/state used in a gating check" pattern described in the external report (there the check was `balanceOf(this) <= poolCeiling`; here it is `to.get_lamports() > 0`).

This check is reachable from any single signed transaction that includes a `CreateAccount` instruction targeting an address whose lamports balance an attacker previously inflated.

Crucially, lamports can be added to *any* account, including one that does not sign and has no special owner, via the ordinary `Transfer` path: [2](#0-1) 
`transfer_verified` only requires the *source* to sign and be data-empty; the destination is never checked for signature, ownership, or any relationship to the sender. This lets an attacker deterministically compute the future address of any PDA, ATA, or seed-derived account a victim program/protocol intends to create, and pre-fund it with a trivial amount of lamports before the legitimate `CreateAccount` transaction lands.

The agave codebase itself acknowledges this exact griefing class: it introduces a dedicated `create_account_allow_prefund` instruction (feature-gated by `create_account_allow_prefund` in `feature-set/src/lib.rs`) specifically to allow creation to succeed even when the destination was pre-funded: [3](#0-2) 
The existence and doc comment of this new instruction ("Create a new account without checking for 0 lamports... Intended for use where account has already had rent paid in whole or in part before creation") confirms the balance-based `AccountAlreadyInUse` gate in the original `create_account` path is a known griefing vector for legitimate account creation flows that still use the plain `CreateAccount` instruction (which remains the default path used by the vast majority of on-chain programs and clients, since adopting the new instruction requires explicit protocol-level migration and feature activation).

Unlike a rent-exempt/ownership check, this lamports-only gate has no relationship to whether the account is actually "in use" by any program — an externally donated 1-lamport balance is sufficient to trip it, with no way for the intended creator to reclaim or clear those lamports without already controlling the account (which they cannot, since creation is what would grant them control).

### Impact Explanation
This is a griefing/DOS vector, not a fund-theft vector: an attacker cannot steal funds or forge signatures, but can indefinitely block the creation of any specific derived/deterministic account address by any protocol or user relying on the plain `CreateAccount` system instruction (directly or via CPI, e.g. token account creation, PDA initialization in arbitrary programs, vanity/precomputed addresses for airdrops, etc.). Since account creation is foundational to almost all on-chain workflows, a single low-cost transaction (the cost of one lamport plus network fee) can permanently deny a specific address from ever being initialized through the standard path, mirroring the "Temporary DOS ... until protocol raises poolCeiling" impact in the reference report, except here there is no cheap remediation analogous to "raise the ceiling" — the victim must either abandon that specific address or migrate to the newer `create_account_allow_prefund` instruction (which requires the destination account owner/program to explicitly adopt it and requires the feature to be activated on the cluster).

### Likelihood Explanation
Likelihood is high for any workflow that predeterministically computes destination addresses before submission (PDAs with `create_program_address`/`find_program_address`, `create_with_seed` accounts, or any keypair generated off-chain and published/predictable ahead of the creation transaction). The attack requires only a single unprivileged, non-CPI, ordinary `Transfer` instruction targeting the known future address, which is trivially cheap (fee plus 1 lamport) and requires no special permissions, precompiles, or leader collusion.

### Recommendation
- For any protocol/program relying on `CreateAccount` for addresses that can be predicted or front-run (PDAs, seed-derived, or externally shared vanity addresses), migrate to `SystemInstruction::CreateAccountAllowPrefund` (already implemented in `programs/system/src/system_processor.rs`, gated by the `create_account_allow_prefund` feature) once the feature is active on the target cluster, since it performs the same allocate/assign/fund logic without the `lamports > 0` rejection.
- Alternatively, harden `create_account`'s "already in use" check so it distinguishes a merely lamport-funded account from one that is truly initialized (i.e., check data length and owner rather than lamports alone) for callers that cannot immediately migrate, mirroring how `create_account_allow_prefund` already treats prefunding as legitimate.

### Proof of Concept
1. Off-chain, an attacker computes a future account address the victim protocol will create — e.g., a PDA via `create_program_address(seeds, program_id)`, or a keypair whose pubkey has been published/precomputed for a deterministic user flow.
2. Attacker submits a signed `SystemInstruction::Transfer` of 1 lamport from their own funded account to that target address. `transfer_verified` succeeds because it only checks the signer/source, not the destination: [4](#0-3) 
3. The victim later submits the legitimate `SystemInstruction::CreateAccount` instruction targeting the same address (directly or via CPI from another program). The check in `create_account` observes `to.get_lamports() == 1 > 0` and returns `SystemError::AccountAlreadyInUse`, permanently failing that specific creation attempt: [5](#0-4) 
4. The victim protocol's operation depending on that account's creation is denied of service until they redesign around a different address or migrate to `CreateAccountAllowPrefund`.

Note: I was unable to fully verify how widely `create_account_allow_prefund` has been rolled out/activated across the cluster feature set, or enumerate every in-repo program that still relies on the plain `CreateAccount` CPI path for PDA/ATA-style flows; this would require deeper cross-repo/program-level review (e.g., `spl-token`, `spl-associated-token-account`) which is outside this repository's index coverage.

/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
