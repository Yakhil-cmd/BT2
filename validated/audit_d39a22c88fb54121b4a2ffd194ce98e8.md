### Title
`Commit#add_status`'s `already_deployed` check only gates `Hook.emit`, not the `Status` row write or `deployable?` state change - (`File: app/models/shipit/commit.rb`)

### Summary
`Commit#add_status` computes `already_deployed = deployed?` and uses it exclusively to skip two `Hook.emit` calls. The `Status` row creation (via `yield`) and the derived `deployable?` flip happen unconditionally before and independent of that check, and `stack.schedule_merges` is also called unconditionally. For an undeployed victim commit, `already_deployed` is `false`, so the guard never engages at all — every write path proceeds exactly as if the guard didn't exist.

### Finding Description
Binding as claimed: `already_deployed` guarding `Hook.emit` == guarding `Status` row creation/`deployable?` change. This is **false** — confirmed as two distinct code paths:

```ruby
# app/models/shipit/commit.rb:366-386
def add_status
  already_deployed = deployed?              # computed once, from stack.last_deployed_commit.id >= id

  previous_status = status
  yield                                       # <-- Status row written HERE, unconditionally
  reload
  new_status = status

  unless already_deployed
    payload = { commit: self, stack:, status: new_status.state }
    Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
  end

  if previous_status.simple_state != new_status.simple_state
    if !already_deployed && (!new_status.pending? || previous_status.unknown?)
      Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
    end
    stack.schedule_merges if new_status.pending? || new_status.success?   # <-- unconditional
  end
  new_status
end
``` [1](#0-0) 

`yield` invokes the caller's block — e.g. `create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` — which persists the `Status` record before `already_deployed` is even consulted: [2](#0-1) 

`deployable?` is a pure derived read of `success?`/`blocked?`/`locked?`, which reflects the just-created `Status` row; it is never referenced by `add_status`'s guard at all: [3](#0-2) 

`deployed?` itself is `stack.last_deployed_commit.id >= id`, so for an undeployed commit (`id` greater than the last deployed commit's `id`) this is `false` by definition: [4](#0-3) 

Consequently for undeployed commits `unless already_deployed` / `!already_deployed` conditions are both true, so `Hook.emit` fires too — the guard is entirely inert for exactly the class of commit ("undeployed") this question asks about. It only ever matters for already-deployed commits, where it suppresses re-emission of `commit_status`/`deployable_status` webhooks — it never prevents the `Status` row write, the `deployable?` flip, or `stack.schedule_merges`.

The reachable write path is `StatusHandler#process`, which matches commits **only by `sha`, with no stack/repository scoping**, then calls `commit.create_status_from_github!(params)`: [5](#0-4) 

`verify_signature` in `WebhooksController` validates the HMAC against the GitHub App configured for `repository_owner` from the payload, but does not verify that the commit `sha` in the payload actually belongs to that repository/stack: [6](#0-5) 

### Impact Explanation
This confirms that even the one partial mitigation present (`already_deployed`) provides no write-prevention: for any undeployed commit whose `sha` collides across stacks/forks, a status event correctly signed for the attacker's own organization still results in a real `Status` row being written against the victim's `Commit`, the victim commit's `deployable?` flipping to `true`, and `stack.schedule_merges` running for the victim's stack — all unaffected by `already_deployed`. This matches the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy/merge," contingent on the cross-repo `sha` match reachability established via `StatusHandler#process`'s lack of repo scoping.

### Likelihood Explanation
Requires only that the attacker's own repository/org is a legitimate Shipit-configured GitHub App installation (so `verify_signature` passes for their own payload) and that a commit `sha` collides with a `Commit` row belonging to a victim stack (e.g., forked repos sharing history, or a resent/replayed sha from a public commit). No Shipit session, API token, or victim secret is needed — only a validly signed webhook for the attacker's own org, which they control. This is repeatable per matching `sha`.

### Recommendation
Fix `StatusHandler#process` (and analogous handlers) to scope `Commit` lookup by the stack's repository (`stack.repository`/`full_name` derived from the payload's `repository` object), not by `sha` alone, so a signature valid for org/repo A can never write status against a commit belonging to stack B. The `already_deployed` check in `Commit#add_status` should not be relied upon as a security control — it is (and should remain documented as) a UX optimization to suppress redundant hook emission for historical/deployed commits.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual, no live GitHub)
test "add_status writes Status row and flips deployable? for an undeployed commit even though already_deployed is false" do
  stack = shipit_stacks(:shipit)
  commit = stack.commits.create!(sha: '0' * 40, message: 'test')
  # ensure victim commit is undeployed relative to last_deployed_commit
  assert_not commit.deployed?

  assert_difference -> { commit.statuses.count }, 1 do
    commit.create_status_from_github!(OpenStruct.new(
      context: 'ci', state: 'success', description: nil, target_url: nil, created_at: Time.now
    ))
  end
  commit.reload
  assert commit.deployable?, "deployable? flipped despite already_deployed being false — guard never applied here"
end
```
This demonstrates the `Status` row write and `deployable?` flip occur regardless of `already_deployed`, confirming the guard is Hook-emission-only and provides no protection for undeployed commits.
