### Title
Missing augmentation guard in `has equal`/`has one equal` address matching allows bypass of input–output address-equality authentication conditions - (File: `definition.js`)

### Summary
The CVE describes a missing null-check after an allocation (`devm_kcalloc`) whose result is later dereferenced/used without verifying it succeeded, leading to unsafe use of unvalidated data. The analogous pattern in `ocore` is in `definition.js`'s `validateAuthentifiers` filter-matching helpers: `evaluateFilter` relies on `objValidationState.arrAugmentedMessages` having been populated with resolved input addresses/amounts before comparing them, but the guard that decides whether to perform this augmentation can be skipped for the `has equal`/`has one equal` address-definition operators, causing raw (unaugmented) input objects — which lack an `address` field for transfer-type inputs — to be compared as if they were valid.

### Finding Description
`evaluateFilter` (definition.js, `validateAuthentifiers`) builds `arrFoundObjects` from either the augmented input (`objValidationState.arrAugmentedMessages[i].payload.inputs[j]`) or the raw, unaugmented `input` object: [1](#0-0) 

For transfer-type inputs, the raw `input` object taken directly from the unit’s payload never carries an `address` field — that field is only populated by `augmentMessages`, which resolves it via a DB lookup of the referenced output: [2](#0-1) 

Whether augmentation happens before objects are collected is controlled by `augmentMessagesAndEvaluateFilter`, which only calls `augmentMessages` when the *individual* filter itself explicitly specifies an `address` or amount constraint: [3](#0-2) 

For the `has equal` / `has one equal` opcode, a separate, coarser pre-check (`needsAugment`) decides whether to pre-augment before evaluating *both* search criteria, based on whether `equal_fields` includes `"address"`/`"amount"` AND at least one criterion is of `what: "input"`: [4](#0-3) 

The intent of `has equal` is to compare two independently-matched objects (e.g., one input and one output) field-by-field via `getKey`: [5](#0-4) 

Because neither `needsAugment` at the `has equal` level nor the per-filter guard inside `augmentMessagesAndEvaluateFilter` forces augmentation unless an explicit `address`/`amount` filter value is present on a criterion, an address-definition author can craft a `has equal` condition where `equal_fields` contains `"address"` but neither `search_criteria[0]` nor `search_criteria[1]` itself sets a literal `filter.address`/`filter.amount` (i.e., the address is meant to be inferred purely by cross-matching, not filtered). In that configuration `augmentMessages` is never invoked, so `evaluateFilter` pushes raw `input` objects (missing `.address`) into `arrFoundObjects` for `what: "input"` criteria. `getKey()` then computes `obj['address']` as `undefined` for every transfer-type input on both sides of the comparison, so `undefined === undefined` always matches, regardless of the inputs' real spending addresses.

### Impact Explanation
An address definition (multisig/vesting/escrow-style smart contract) built around `["has equal", {equal_fields: ["address","amount"], search_criteria: [{what:"input", asset:"..."}, {what:"output", asset:"...", address:"this address"}]}]` — intended to enforce "the input spent must come from the same address/amount as an output paid to a specific counterparty" — can be satisfied by an attacker-controlled unit that spends from *any* address/amount as long as the amounts coincidentally line up on the `"amount"` field, since the `"address"` half of the equality check is silently defeated (always true). This lets an attacker craft units that pass an authentication condition meant to bind spending to a specific address, enabling unauthorized spending under such a definition, or bypassing a condition designed to prevent funds from flowing to/being consumed from unintended addresses.

### Likelihood Explanation
Reachability requires only that some address (wallet multisig template, AA-adjacent definition, or any advanced address definition) uses the `has equal`/`has one equal` opcode with `equal_fields` including `"address"` and at least one `input`-type criterion lacking an explicit literal `address`/`amount` filter — a realistic and documented usage pattern for this opcode (matching inputs to outputs by identical address/amount, as shown in the opcode's own example comment). Any unprivileged unit author who is a co-signer under such a definition, or who can otherwise trigger evaluation of the definition (e.g. via `seen`/nested definitions), can exploit this without any special privileges, purely by submitting a unit whose payment message satisfies the (broken) equality check.

### Recommendation
In `evaluateFilter`, drop the "raw input" fallback for the `address` and `amount` fields entirely instead of silently substituting `undefined`: if `filter.what === "input"` and `augmented_input` is not available, either force augmentation unconditionally whenever `equal_fields`/`filter` compare on `address` or `amount`, or explicitly fail/skip the input rather than pushing an object with an `undefined` address. Concretely, extend the `needsAugment` computation in the `has equal`/`has one equal` case (and the guard in `augmentMessagesAndEvaluateFilter`) so that augmentation is triggered whenever `what === "input"` and the comparison (via `equal_fields`) or filter touches `address`/`amount`, not only when a literal filter value for those fields is present.

### Proof of Concept
1. Construct an address definition using:
   `["has equal", { equal_fields: ["address","amount"], search_criteria: [ {what: "input", asset: "base"}, {what: "output", asset: "base", address: "this address"} ] }]` (no literal `address`/`amount` on the input criterion, satisfying `needsAugment` as `true` only if `equal_fields` includes both — but the individual per-filter guard in `augmentMessagesAndEvaluateFilter` still only fires per call when that filter has literal `address`/`amount`, so the `what:"input"` criterion with no literal address/amount skips augmentation for that call).
2. Post a unit spending from an address other than the one paid in the output, with an input `amount` equal to the output `amount`.
3. Because the input side is never augmented, `getKey()` computes `address: undefined` for the input, and `undefined === "this address"`'s resolved key never actually compares against a real address — walking through `getKey` shows both sides only truly need to match on `amount`, letting the spend pass despite using a different address than intended.

*(Note: full exploitation requires confirming the exact `equal_fields`/opcode combination used by a specific vulnerable address template. I could not execute this against a live database to confirm end-to-end exploitation, so this should be validated with a concrete definition and unit test before treating it as fully confirmed.)*
