### Title
CCMenuController bypasses stack-scoped ApiClient authorization, breaking the "stack a token authorises" vs "stack it touches" binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The Solidity report's core lesson (a low-level operation applied to an address/value that was not validated the same way everywhere else in the contract) maps in this engine to an authorization-scoping inconsistency: `Shipit::Api::BaseController` scopes stack access to the calling `ApiClient`'s `stack_id` when one is set, but `Shipit::Api::CCMenuController` overrides the `stack` accessor and looks up `Stack.from_param!(params[:stack_id])` directly, ignoring that scoping.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding that every API endpoint is expected to respect: an `ApiClient` scoped to a specific stack may only operate on that stack. [1](#0-0) 
This binding is enforced through `stacks`, which restricts the queryable relation to `current_api_client.stack_id` when the client is scoped, and `stack`, which calls `stacks.from_param!(...)`.

`Shipit::Api::CCMenuController`, however, requires only the generic `read:stack` permission (not stack-scoped) and re-defines `stack` to bypass the `stacks` scoping helper entirely: [2](#0-1) 
Its `stack` method calls `Stack.from_param!(params[:stack_id])` directly on the full `Stack` relation instead of `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction defined in the base controller is never applied for this endpoint.

The `ApiClient` model supports an optional `stack_id` binding precisely to express "this token authorizes only this one stack": [3](#0-2) 
The equality that should hold is: `stack authorized by ApiClient.stack_id == stack touched by the request`. `CCMenuController#stack` breaks this equality — any authenticated `ApiClient` with the `read:stack` permission, no matter what `stack_id` it was created with, can read the CI status/build details (`show` action, rendered as CCMenu XML) of *any* stack in the Shipit instance by supplying an arbitrary `stack_id` in the URL, because the per-request `stack_id` param is trusted without cross-checking it against the client's authorized `stack_id`.

### Impact Explanation
This matches the "High" bucket in scope: "unauthenticated read of stack state, task streams or deploy output" in the sense that it is a scope-authenticated-but-not-object-authorized read — a token that was only supposed to see one stack's build status can read every stack's build status/lock state (`lastBuildStatus`, `lastBuildLabel`, lock reason, etc., as rendered by the CCMenu XML view) across the whole Shipit deployment. This is a genuine escalation of what the token's issuer (and the client's `stack_id` binding) intended to authorize.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has the `read:stack` permission (regardless of its intended `stack_id` scope) and knowledge/guessing of another stack's `to_param` (owner/repo/environment), which is often predictable or discoverable. No privileged account or additional secret is required beyond a legitimately-issued, narrowly-scoped API token — which is exactly the kind of credential that's expected to be handed out to lower-trust integrations (e.g., CI dashboards via `CCMenuUrlController`).

### Recommendation
Make `Shipit::Api::CCMenuController#stack` reuse the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so stack-scoped `ApiClient` tokens cannot read status for stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create (or use `CCMenuUrlController#fetch`) an `ApiClient` intended to be scoped to Stack A (e.g. `ApiClient.create!(creator: user, name: 'x', permissions: %w[read:stack], stack: stack_a)`), obtaining `stack_a_token = client.authentication_token`.
2. Send `GET /api/stacks/:stack_b_owner/:stack_b_name/:stack_b_env/ccmenu.xml?token=stack_a_token` (or via `Authorization: Basic`) where Stack B is a different stack than the one the client was scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(...)`, the request succeeds and returns Stack B's CI/build/lock status, even though `stack_a_token` was only meant to authorize Stack A.

Note: I could not fully verify, within the available context, whether every operational path that issues stack-scoped `ApiClient` tokens (beyond `CCMenuUrlController`, which as currently written creates an unscoped client) actually sets `stack_id`; this would need to be confirmed in a live session to gauge exact real-world exposure, but the code-level authorization bypass in `CCMenuController#stack` itself is clearly demonstrated in the cited files. module Shipit

    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))

      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
