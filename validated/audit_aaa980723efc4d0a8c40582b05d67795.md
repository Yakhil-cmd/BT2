The only AEAD usage in the codebase's production code is `substrate/primitives/statement-store/src/ecies.rs`, which relies on the RustCrypto `aes-gcm` crate's single-shot `Aead::decrypt()`/`Aead::encrypt()` trait methods [1](#0-0) , not OpenSSL's C `EVP_Cipher()` API. The CVE's root cause is specific to OpenSSL's internal one-shot cipher finalization path skipping the AEAD tag check for AES-OCB/ChaCha20-Poly1305 when the ciphertext length is zero; the Rust `aead` crate trait used here has no equivalent split init/update/finalize state machine with that quirk, and its `decrypt()` call always authenticates the tag as part of the same call regardless of ciphertext length. A grep of the repository shows `openssl` is referenced only in unrelated build scripts/docs/webrtc TLS code [2](#0-1) , not in any AEAD decrypt/verify logic, so the vulnerable OpenSSL code path is not present in this codebase at all. Additionally, `decrypt_x25519` is not reachable from any signed extrinsic, XCM message, or contract call boundary — it is a primitive used internally by the statement-store gossip/offchain messaging layer [3](#0-2) , and its test suite already demonstrates that malformed/forged inputs are rejected rather than silently accepted [4](#0-3) .

/// Decrypt with the given x25519 secret key.
pub fn decrypt_x25519(sk: &SecretKey, encrypted: &[u8]) -> Result<Vec<u8>, Error> {
	if encrypted.len() < PK_LEN + NONCE_LEN {
		return Err(Error::BadData);
	}
	let mut ephemeral_pk: [u8; PK_LEN] = Default::default();
	ephemeral_pk.copy_from_slice(&encrypted[0..PK_LEN]);
	let ephemeral_pk = PublicKey::from(ephemeral_pk);

	let shared_secret = sk.diffie_hellman(&ephemeral_pk);
	if !shared_secret.was_contributory() {
		return Err(Error::BadData);
	}
	let mut shared_secret = shared_secret.to_bytes().to_vec();
	shared_secret.extend_from_slice(ephemeral_pk.as_bytes());

	let aes_key = kdf(&shared_secret);

	let nonce = &encrypted[PK_LEN..PK_LEN + NONCE_LEN];
	aes_decrypt(&aes_key, &nonce, &encrypted[PK_LEN + NONCE_LEN..])
}
