## Analysis

The claimed binding — `deployable? consulted by DeploysController#create == deployable? based on the repository's own verified CI events` — is broken because `StatusHandler#process` resolves target commits purely by SHA with **no repository/stack scoping**, unlike the sibling `PushHandler`.

**The vulnerable code path:**

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This queries `Commit` across **all stacks/repositories** in the Shipit instance, matching only on `sha`. Contrast this with `PushHandler`, which correctly resolves the target via the payload's own repository:
```ruby
stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }
```
where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., strictly scoped to the repository named in the payload. [2](#0-1) [3](#0-2) 

The schema confirms `sha` is unique only per `(sha, stack_id)`, not globally — the same SHA can legitimately exist as separate `Commit` rows under different stacks (e.g., a shared base commit between an upstream repository's stack and a fork/PR-review stack). [4](#0-3) 

`create_status_from_github!` writes a `Status` row tied to `stack_id` and flips `commit.success?`: [5](#0-4) 

which feeds `deployable?`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

and this is exactly what `DeploysController#create` consults:
```ruby
param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?
``` [7](#0-6) 

**Signature verification does not close this gap.** `WebhooksController#verify_signature` selects which GitHub App/secret to validate against using the payload's own `repository.owner.login`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [8](#0-7) 

This only proves the request came from *some* GitHub organization/app Shipit trusts — it says nothing about which *stack/commit* the SHA in the body should be allowed to affect. Once past `verify_signature`, `StatusHandler#process` treats the SHA as globally authoritative across every tracked repository.

## Exploit path

Shipit supports "review stacks" that are auto-created for pull requests/forks (per `CHANGELOG.md`), each wired with its own legitimately signed GitHub App/webhook hookup for the attacker's own fork. An attacker who:
1. opens a PR from their own fork against a tracked repository (unprivileged, standard GitHub action), causing Shipit to create a review stack/hook for their fork, and
2. has a commit in their fork whose SHA is identical to a commit that also exists in the victim's primary stack (true whenever the fork hasn't diverged from that base commit — the common case for a PR's base/merge-base commit), and
3. sets any commit status (`state: success`) on that SHA via the normal GitHub status API against their own fork (a fully legitimate action on a repository they control),

causes GitHub to deliver a **correctly signed** `status` webhook to Shipit for the attacker's own repo/org. `StatusHandler#process` then updates **every** `Commit` row across **every stack** sharing that SHA — including the row belonging to the victim's unrelated, production stack — marking it `success`.

A later, fully legitimate `POST /api/stacks/:victim_stack_id/deploys` with `require_ci: true` from any authenticated API client now passes `commit.deployable?` for a commit that never received a real CI success from the victim repository's own configured CI, because the state was injected by an attacker-controlled repository.

## Impact

This is a cross-tenant payload-forging bug: a status event legitimately signed for repository A (attacker's fork) mutates commit/stack state for repository B (an unrelated victim stack), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and enabling an unauthorized deploy bypass of the `require_ci` safety gate. Repeatable against any commit whose SHA is shared between the attacker's tracked fork/review stack and the target stack (trivially true for common ancestor/base commits before a PR diverges).

## Uncertainty

I could not fully verify from the indexed code how "review stacks" are provisioned (their hook creation code wasn't located in this session), nor whether `Shipit.github_teams`/org-level installation constraints would prevent an attacker's fork from ever being wired with a valid signing secret in a given deployment. If review stacks are not enabled, or the operator only ever installs the GitHub App on their own single organization/repos (not attacker-controlled forks), the practical reachability of a validly-signed cross-repo webhook is reduced, though the underlying code defect (`Commit.where(sha:)` with no repository scoping in `StatusHandler#process`) remains present and would also be exploitable for any two same-instance stacks that happen to share commit history (e.g., a repo rename/re-tracking, or a mirrored repo). I recommend a Devin session with full repo access to inspect the review-stack creation flow (`app/models/shipit/stack.rb`, any `ReviewStack`-related job/controller) to confirm the exact provisioning trigger before treating this as fully proven end-to-end.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to the webhook's own repository, mirroring `PushHandler`'s use of `stacks` derived from `Repository.from_github_repo_name(repository_name)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a global `Commit.where(sha: params.sha)`.
