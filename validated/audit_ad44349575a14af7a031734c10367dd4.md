### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA alone, across the entire `commits` table, instead of scoping the lookup to the repository named in the verified webhook payload. Because `commits` are only unique per `(sha, stack_id)` pair rather than globally, an attacker who owns any GitHub organization/repo onboarded to Shipit can send a signed `status` webhook for a SHA that happens to also exist as a queued `MergeRequest` head commit in an unrelated victim stack, and Shipit will write a fabricated CI status onto the victim's `Commit` row.

### Finding Description
The binding that must hold is: `repository named in the verified webhook payload == repository whose Commit/MergeRequest row is mutated`. Every other handler enforces this via the base class helper `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` before touching any records: [1](#0-0) 

`StatusHandler#process`, however, never calls `stacks` and instead queries the global `Commit` table directly by `sha`: [2](#0-1) 

`Shipit::WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` GitHub App signed the request — it never re-checks that the `Commit` rows subsequently touched actually belong to that same organization/repo: [3](#0-2) 

The `commits` table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone, so identical SHAs across different stacks/repositories are a normal, expected condition in this schema (e.g., forks, cherry-picks, or a rebase that reproduces an identical tree/parent/timestamps): [4](#0-3) 

Exploit flow:
1. Attacker owns/administers a GitHub org `attacker-org` with a repository already added as a Shipit stack (or any repo whose GitHub App webhooks route through this Shipit instance).
2. Attacker crafts a commit in their own repo whose SHA equals the victim's queued `MergeRequest#head.sha` (achievable when the victim's PR/commit content — tree, parents, author/committer identities and timestamps, message — is public/known, e.g. after a rebase that reproduces byte-identical commit data).
3. Attacker triggers a `status` event on their own repo/commit with `state: success` (via GitHub, since a "status" event on a commit they own is entirely under their control), which GitHub signs with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature against `attacker-org` — this succeeds because it is genuinely from attacker's org.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches both the attacker's own commit row (if tracked) AND the victim's `Commit` row with the same SHA in a completely different stack. `commit.create_status_from_github!(params)` writes a `success` status onto the victim's row.
6. `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) re-evaluates via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` and now reflects the forged success status, allowing `reject_unless_mergeable!` to pass and the merge queue to proceed toward `merge!`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate only that the sender is a legitimate GitHub App for *some* organization and that the payload shape is correct — none of them constrain which `Commit`/`Stack` rows the handler is allowed to mutate. The repository-scoping pattern used by `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler`s via `stacks` is simply absent from `StatusHandler`.

### Impact Explanation
An attacker fully controlling one onboarded (or attacker's own) repository can inject a fabricated `success` status onto a commit belonging to an unrelated victim stack, which flips `MergeRequest#all_status_checks_passed?` to true without the victim's actual CI ever running. This is a cross-tenant write: a payload authenticated for repository A mutates state for repository B, directly enabling an unauthorized/CI-bypassed merge in the merge queue (`ProcessMergeRequestsJob` → `MergeRequest#merge!`). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: the victim stack must have `merge_queue_enabled` with a queued `MergeRequest` whose head commit SHA collides with a SHA the attacker can produce/control in their own repo. SHA collision is not a cryptographic-hash-break requirement — it only requires the attacker to reproduce identical commit metadata (tree, parents, author/committer name/email/timestamp, message), which is realistic when acting on public repository history (e.g., cherry-picking/rebasing an exact copy of the victim commit into an attacker-controlled repo they've onboarded to the same Shipit instance). Attacker cost is low: no Shipit credentials, no GitHub org compromise, only ownership of one legitimate repo/organization with a GitHub App webhook configured toward the Shipit instance. Repeatable against any repository sharing the Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the repository authenticated by the webhook, mirroring the `stacks` helper used elsewhere:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status can only be applied to `Commit` rows that belong to a stack under the repository named (and cryptographically verified) in the webhook payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook from an unrelated repository must not affect another stack's commit with the same sha" do
  victim_stack = shipit_stacks(:shipit) # repo shopify/shipit
  attacker_stack = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'attacker-org', name: 'attacker-repo'))

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_stack.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  merge_request = Shipit::MergeRequest.create!(stack: victim_stack, number: 1, head: victim_commit)

  refute_predicate merge_request.reload, :all_status_checks_passed? # baseline: false, no status yet

  # Simulate a webhook whose signature is verified for "attacker-org" only, but sha collides with victim's commit.
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true)

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding check: repository in verified payload ("attacker-org/attacker-repo")
  # must equal the repository whose MergeRequest state is affected ("shopify/shipit" victim stack).
  assert_equal 'attacker-org/attacker-repo', payload.dig('repository', 'full_name')
  assert_equal 'shopify/shipit', victim_stack.repository.full_name
  refute_equal payload.dig('repository', 'full_name'), victim_stack.repository.full_name

  # Yet the victim's commit/merge request was mutated:
  assert_predicate victim_commit.reload, :success?
  assert_predicate merge_request.reload, :all_status_checks_passed?
end
```
This demonstrates that despite the two repository names being unequal (attacker's vs victim's), the victim's `MergeRequest#all_status_checks_passed?` flips to `true`, confirming the broken binding at [2](#0-1) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
