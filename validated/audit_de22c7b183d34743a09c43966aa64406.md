### Title
Pull request label names (uppercased) are merged unfiltered into the process environment reaching `PTY.spawn` for review-stack deploys - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` takes every label name attached to the associated pull request, upcases it, and merges it directly into the environment hash used to build the deploy `Command`, with no key allowlist. Because pull request labels are attacker-controlled (a fork PR author can add any label to their own PR) and `LabelCapturingHandler` persists label names verbatim from the webhook payload, an attacker can set arbitrary environment variable names — including `GEM_HOME` — that survive all the way into `Command#unbundled_env` and `PTY.spawn`.

### Finding Description
The broken binding: `Command#unbundled_env` is expected to satisfy `unbundled_env.keys ⊆ BASE_ENV.keys ∪ {task/stack-defined keys}` (i.e., only Shipit-defined environment keys reach the spawned child process), but in practice `unbundled_env.keys ⊇ pull_request.labels.map(&:upcase)` for any review stack.

Trace:
1. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body's `pull_request.labels[].name`, with only a `String` type check in the `params` schema — no format/allowlist validation. [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into `super` (the base `Stack#env`) with no key filtering whatsoever. [2](#0-1) 
3. `TaskCommands#env` (used by `DeployCommands#env` for the `deploy.override` step) merges `@stack.env` — i.e., the `ReviewStack#env` result including the label-derived key — into the hash passed to `Command.new(command_line, env:, chdir: ...)`. [3](#0-2) 
4. `Command#unbundled_env` merges `@env.stringify_keys` (which contains the attacker's `GEM_HOME` key) over `BASE_ENV`, with the attacker's value taking precedence since it's merged last. [4](#0-3) 
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the attacker-controlled `GEM_HOME` is set for the actually spawned deploy process. [5](#0-4) 

Attacker request: open a pull request from a fork and attach a label literally named `gem_home` (any case) to their own PR — labeling one's own PR requires no Shipit privilege, only ownership of the fork/PR. This label is captured via the `pull_request` webhook (`labeled`/`opened`/`reopened` actions) by `LabelCapturingHandler`, persisted onto the `PullRequest#labels` array, then surfaces in `ReviewStack#env` as `"GEM_HOME" => "true"` on every subsequent task/deploy (including the `deploy.override` step defined in `shipit.yml`), overriding the trusted `BASE_ENV`/`Bundler.unbundled_env` value.

Why existing guards fail: `capture_labels?` (`opened_active_stack? || labeled_active_stack? || ...`) only gates *when* labels are captured, not *what* label names are allowed — there is no repository-owner/maintainer approval step, and no `EnvironmentVariables#permit`-style allowlist is applied to the env hash before it reaches `Command`. The `prevent_with_label` provisioning behavior only gates whether the review stack is provisioned/deployed at all — it says nothing about label content sanitization once the stack is deployed.

### Impact Explanation
An attacker who can open a PR and label it on their own fork can inject `GEM_HOME` (or `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD` if similarly named labels are used) into the environment of the `deploy.override` process on the Shipit deploy host for that review stack. If `GEM_HOME` points to an attacker-writable directory populated during an earlier step of the same PR's pipeline (e.g. via the review stack's own `install_dependencies`/`deploy.override` steps, which the attacker also controls via `shipit.yml` in their fork), gem resolution for subsequently invoked Ruby processes can be redirected to attacker-supplied gems, leading to code execution on the shared deploy host — a Critical RCE-class impact. This affects any repository using `ReviewStack`/`provisioning_behavior=prevent_with_label`, and is repeatable per PR/per label with no rate limiting.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`provisioning_behavior` configured, e.g. `prevent_with_label`) and expose a `deploy.override`/other steps in `shipit.yml`. The attacker only needs to be able to open a PR from a fork and label it — both are unprivileged, low-cost actions requiring no Shipit credentials, GitHub App keys, or webhook secret. This is fully repeatable and requires no timing race or social engineering.

### Recommendation
In `ReviewStack#env`, restrict pull-request-label-derived environment keys to a fixed, safe prefix/allowlist (e.g., require a `SHIPIT_` prefix, as some Shipit deployments already convention for label flags) and/or explicitly reject any key from the label-derived hash that collides with names present in `Command::BASE_ENV`/`ENV.keys` (`PATH`, `GEM_HOME`, `BUNDLE_*`, `RUBYOPT`, `LD_PRELOAD`, etc.) before merging into the stack's env. Additionally, `Command#unbundled_env` should not allow task/stack-supplied `env` to override a denylist of security-sensitive interpreter/loader variables.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual, minitest[prevent_with_label])
test "GEM_HOME injected via upcased PR label reaches Command#start's spawned env" do
  stack = shipit_stacks(:review_stack) # a Shipit::ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['gem_home']) # simulates LabelCapturingHandler#capture_labels persisting the label name verbatim

  env = stack.env
  assert_equal 'true', env['GEM_HOME'], "attacker-controlled label should not set GEM_HOME"
  # ^ demonstrates the broken binding: env['GEM_HOME'] should be absent/only Shipit-derived, but equals 'true'

  command = Shipit::Command.new('echo test', env:, chdir: Dir.mktmpdir)
  resolved_env = command.unbundled_env
  assert_equal 'true', resolved_env['GEM_HOME'], "attacker-controlled GEM_HOME reaches the spawned process env"
end
```
This confirms `env['GEM_HOME'] == 'true'` (attacker value) rather than the expected absence of any fork-controllable key in the process environment that `PTY.spawn` receives for the `deploy.override` step.

      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
