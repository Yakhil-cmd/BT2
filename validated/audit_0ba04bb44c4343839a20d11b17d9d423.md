This confirms the vulnerability. The critical detail: `verify_signature` uses `repository_owner` (parsed from `params.dig('repository', 'owner', 'login')`) to select which `GitHubApp` verifies the HMAC, while `Handler#stacks`/`repository_name` independently uses `payload.dig('repository', 'full_name')` to resolve the target `Repository`/`Stack`. Both fields come from the same attacker-supplied JSON body with no cross-validation between them.

### Title
Webhook signature verification is keyed on `repository.owner.login` while stack resolution uses an independently-controlled `repository.full_name`, allowing cross-tenant webhook forgery when any one configured org has a blank `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification based on `repository.owner.login`, but `Handler#stacks` (used by `PushHandler` and others) independently resolves the target `Stack` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. Because both values are read from the same attacker-controlled JSON body without cross-validation, an attacker can pick an owner login whose `GitHubApp` has no `webhook_secret` configured (`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank), while setting `repository.full_name` to any other configured organization's repository, causing that other org's `Stack` to be synced/mutated by an unauthenticated request.

### Finding Description
The broken binding: the question assumes `stack.repository`'s organization == the organization whose secret verified the HMAC. In fact, verification identity is derived from `repository_owner = params.dig('repository', 'owner', 'login')` [1](#0-0)  and used to fetch `github_app = Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(...)` [2](#0-1) . Separately, `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2)  and `Handler#stacks` calls `Repository.from_github_repo_name(repository_name)` to resolve the affected stacks [4](#0-3) . These are two independent JSON paths in the same attacker-supplied payload; nothing enforces `repository.owner.login == repository.full_name.split('/').first`.

Root cause: `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that org, `return true unless webhook_secret` [5](#0-4) . If org `A` is configured in `secrets.github` without a `webhook_secret` (a real and plausible operator misconfiguration for one tenant among many), any request claiming `repository.owner.login = "A"` passes signature verification trivially, regardless of the HMAC header sent.

Attacker's request: POST `/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/private-repo" },
  "ref": "refs/heads/master",
  "after": "<sha>"
}
```
`verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so verification passes unconditionally. `PushHandler#process` then calls `stacks` which resolves `Repository.from_github_repo_name("orgb/private-repo")` and finds `orgB`'s existing `Stack` row, then calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) , which enqueues `GithubSyncJob.perform_later(stack_id: id, ...)` [7](#0-6) . `GithubSyncJob#perform` then runs `@stack = Stack.find(params[:stack_id])` and fetches commits from GitHub for `orgB`'s stack, potentially creating commits and triggering `CacheDeploySpecJob` [8](#0-7) .

Why existing guards fail: `drop_unhandled_event` only checks the event type is registered, not payload consistency. `verify_signature`'s only defense is the HMAC check tied to `repository.owner.login`; it never checks `repository.full_name` matches that owner. `ExplicitParameters` schemas (e.g. `PushHandler.params`) only require `ref`/`after` fields to be present/typed — they don't constrain `repository.full_name` to belong to the verifying org. `Repository.from_github_repo_name` and `Stack` validations only validate format, not tenant ownership relative to the verifying signature.

### Impact Explanation
An unauthenticated attacker can force GitHub sync operations (fetching commits, creating `Commit` rows, potentially marking stacks accessible/inaccessible, triggering `CacheDeploySpecJob`) against any `Stack` belonging to any configured organization, as long as at least one other configured organization has no `webhook_secret`. This is a cross-tenant confused-deputy: payload for organization A's webhook (unverified) is used to affect organization B's stack — matching "a payload for one repository mutating another's stack" in the Critical impact category. This is repeatable per request and scales to every stack whose `full_name` the attacker knows (often discoverable, e.g. public repo names or via the `/stacks` listing UI).

### Likelihood Explanation
Requires: (1) `Shipit.github_apps`-equivalent multi-org config in `secrets.github` with more than one org configured, and (2) at least one configured org missing a `webhook_secret`. This is plausible in real deployments (e.g., an org added for testing/staging without a secret, or a legacy single-org migration edge case). No GitHub App private key, no Shipit session, and no API token are needed — only knowledge of the vulnerable org's login and the target repo's `full_name`. Attacker cost is a single crafted HTTP POST.

### Recommendation
Cross-validate that `repository.owner.login` (or its lowercase org) used for signature verification matches the organization implied by `repository.full_name` before resolving/mutating any `Stack`. Alternatively, derive the `stacks`/`repository_name` lookup exclusively from the same `repository_owner` value already authenticated in `verify_signature`, rather than independently re-reading `repository.full_name` from the payload. Also consider treating a missing `webhook_secret` for any one org as a configuration error that should fail closed (reject signature verification) rather than short-circuiting to `true`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Stub two orgs in `Shipit.github_apps`/`secrets.github`: `orgA` with `webhook_secret: nil`, `orgB` with `webhook_secret: "realsecret"`.
2. Create `shipit_repositories(:orgb_repo, owner: "orgb", name: "private-repo")` and an associated `Stack` for it, e.g. `shipit_stacks(:orgb_stack)`.
3. POST to `:create` with `X-Github-Event: push`, no `X-Hub-Signature` (or an arbitrary bogus one), and body:
   `{ "repository": { "owner": {"login": "orga"}, "full_name": "orgb/private-repo" }, "ref": "refs/heads/master", "after": "deadbeef" }`.
4. Assert `assert_enqueued_with(job: GithubSyncJob, args: [stack_id: orgb_stack.id, expected_head_sha: "deadbeef"])` — proving that a signature verified against `orgA` (no secret) is accepted to enqueue a sync job against `orgB`'s `Stack`, i.e., `stack.repository.owner ("orgb") != repository_owner used for verification ("orga")`.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
