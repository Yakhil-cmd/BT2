### Title
CCMenu API token issued for one stack grants read access to every stack in the installation - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to expose the CI/build status of a single stack via the public CCMenu XML format, but the token it creates is never scoped to that stack. `Api::CCMenuController` then resolves the requested stack directly from the URL parameter, bypassing the `ApiClient#stack_id` restriction that every other API controller enforces. The result: a token generated in the context of stack A can be replayed with a different `stack_id` to read the build/deploy status of any stack B on the installation.

### Finding Description
`CCMenuUrlController#client` creates (or reuses) an `ApiClient` scoped only by `permissions: %w[read:stack]`, with no `stack:` association: [1](#0-0) 

Because `stack` is never assigned, `ApiClient#stack_id` is `nil`, so this is a client-wide token, not a stack-scoped one, even though it is generated from and embedded in a URL for one particular stack: [2](#0-1) 

Normally, `Api::BaseController#stacks` would restrict an api client's visible stacks to `current_api_client.stack_id` when present: [3](#0-2) 

But `Api::CCMenuController` overrides `stack` and resolves it directly from `Stack.from_param!(params[:stack_id])`, never going through the `stacks` scoping helper at all: [4](#0-3) 

`ApiClient#check_permissions!` only checks the `read:stack` permission string, it does not check which stack the operation targets: [5](#0-4) 

So the binding that should hold — "the stack a token authorizes == the stack it can be used against" — is broken twice over: the token is minted unscoped, and the controller that consumes it doesn't scope stack lookup even for tokens that were scoped. An attacker who obtains one stack's CCMenu URL (these URLs are designed to be pasted into third-party CI dashboard/CCTray tools, IM channels, browser extensions, status boards, etc., i.e., treated as semi-public/low-sensitivity), can swap the `stack_id` segment of the URL for any other stack in the Shipit instance (`/api/stacks/*other_stack_id/ccmenu?token=<leaked-token>`) and get that other stack's build name, last build status, last build label, and web URL.

### Impact Explanation
This is an authorization/stack-scope escalation: a credential intended to authorize read access to one stack's status is usable to read the state of every stack hosted by the Shipit instance — "escalation into ... unauthenticated read of stack state" for stacks the token holder was never granted access to, matching the High-severity criteria for stack-authorization escalation.

### Likelihood Explanation
Likelihood is high given the intended distribution model of these URLs: CCMenu/CCTray-style status URLs are explicitly designed to be embedded in third-party tools and are commonly less carefully protected than a full API credential (they are treated as "just a status badge URL"). No privileged access is required beyond having obtained one such legitimately-issued URL for any single stack, and the `stack_id` in the path is fully attacker-controlled and requires no signature of its own (only the token component is signed).

### Recommendation
- In `CCMenuUrlController#client`, scope the `ApiClient` to the requested stack (`stack:` association) instead of creating a permission-only, unscoped client shared across all stacks the user requests.
- In `Api::CCMenuController#stack`, resolve the stack through the same `stacks` (scoped-by-`current_api_client.stack_id`) helper used in `Api::BaseController`, rather than calling `Stack.from_param!(params[:stack_id])` directly.
- Add a check that `current_api_client.stack_id` (if present) matches the requested `stack_id` before rendering.

### Proof of Concept
1. As an authenticated Shipit user, visit `GET /ccmenu/org/repo-A/production` (via `CCMenuUrlController#fetch`) to obtain `{"ccmenu_url": "https://shipit.example.com/api/stacks/org/repo-A/production/ccmenu?token=<TOKEN>"}`.
2. Take `<TOKEN>` and request `GET /api/stacks/org/OTHER-REPO/staging/ccmenu?token=<TOKEN>`.
3. Because `Api::CCMenuController#stack` looks the stack up unconditionally via `Stack.from_param!(params[:stack_id])` and the token itself is not stack-scoped, the request succeeds and returns `org/OTHER-REPO/staging`'s build name, status, and last build info, a stack the token was never intended to expose.
