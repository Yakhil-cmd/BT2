### Title
`StatusHandler#process` writes Status rows for arbitrary stacks by matching `sha` globally, without scoping to the webhook's own repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` across the *entire* database and calls `commit.create_status_from_github!(params)` on every match, rather than restricting to commits belonging to `stacks` (i.e., stacks of the repository named in the incoming webhook payload) as the base `Handler` class provides. Because git commit SHAs are content-addressed and publicly derivable, an attacker who controls a repository with a valid Shipit webhook secret can reconstruct a commit object with an identical SHA to a commit that belongs to a victim's stack, push it, fire a `status` webhook, and have Shipit attach an attacker-controlled `Status` (e.g. `state: success`) to the victim's stack's commit.

### Finding Description
The intended binding is: for every `Status` row created via the GitHub "status" webhook, `status.commit.stack.repository.full_name == payload['repository']['full_name']` — i.e., a status event from repository X can only ever write a Status onto a commit that belongs to a stack of repository X.

`Handler` provides exactly this scoping primitive: [1](#0-0) 
and other handlers (`push_handler`, `membership_handler`, `check_suite_handler`, the pull-request handlers) use `stacks` to scope their side effects to the repository named in the payload.

`StatusHandler#process` does not do this: [2](#0-1) 
It calls `Commit.where(sha: params.sha)` — a global, unscoped lookup across every stack/repository in the Shipit instance — and for every match calls `commit.create_status_from_github!(params)`, which writes the Status under that commit's own `stack_id`: [3](#0-2) [4](#0-3) 

Compare with the API-poll path `Commit#refresh_statuses!`, which is correctly scoped: it fetches statuses via `stack.github_api.statuses(github_repo_name, sha, ...)`, i.e., only statuses that GitHub itself reports for that stack's own repository/sha: [5](#0-4) 

Exploit flow:
1. Attacker controls a repository R that is already registered as a Shipit stack (so Shipit knows the correct webhook secret for R's GitHub App/organization, and `verify_signature` in `WebhooksController` will pass for genuine webhooks from R).
2. Attacker identifies a target commit SHA belonging to a victim stack V (public repos expose full commit metadata — tree, parents, author/committer name/email/timestamps, message — via the GitHub API/UI).
3. Attacker crafts a git commit object in R with byte-identical content (same tree, parent chain, author/committer info, message/timestamps) to reproduce the exact same SHA-1, and pushes it to R (or a branch of R).
4. GitHub fires a legitimate, correctly-signed `status`-type webhook event for repository R referencing that SHA (attacker can trigger this by posting a commit status via GitHub API on their own repo, or via CI integration on R).
5. `WebhooksController#verify_signature` succeeds — the signature is valid for R's organization, since it is a real, correctly signed webhook from GitHub for repository R.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's `Commit` row (belonging to stack V) purely because the shared SHA collides, and calls `create_status_from_github!(params)` on it — writing a Status row under `stack_id` = V's id, using the attacker-controlled `state`, `description`, `context`, `target_url` from the webhook body.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate that the webhook signature matches *some* organization/app secret and that the payload shape is well formed — none of them verify that the resolved `Commit` actually belongs to a stack of the repository that signed the webhook. The `stacks` scoping helper exists in `Handler` precisely to close this gap, but `StatusHandler` never calls it.

### Impact Explanation
A single attacker-controlled repository with a valid Shipit-registered webhook secret can inject fabricated CI status data (state, description, context, target_url) onto commits belonging to any other tenant's stack in the same Shipit instance, as long as they can reproduce a matching commit SHA. Since `Commit#deployable?` and `#blocked?` depend on status/context state (`success?`, `blocking?`), this can be used to forge a "success" status for a blocking CI context on a victim's commit, unblocking or enabling an unauthorized deploy for a repository/team the attacker does not control — a cross-tenant write matching "a payload for one repository mutating another's stack, commit... or an unauthorized deploy" (Critical).

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository already onboarded into the same Shipit instance with a correctly configured webhook (any user who owns/administers a repo tracked by the target Shipit deployment, e.g., in a multi-tenant/monorepo-hosting Shipit deployment), and (b) the ability to reconstruct an identical-SHA commit object for the target commit, which is mechanically straightforward given git's content-addressing and publicly visible commit metadata on GitHub, but requires the victim commit's exact metadata to be fully known/reproducible (feasible for public repos; harder, though not impossible, for private ones). This is a real, repeatable, per-request attack for any stack whose commit metadata the attacker can obtain, without needing any Shipit credential beyond control of one already-onboarded repository's push/webhook capability.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the webhook payload, mirroring the pattern used by other handlers, e.g. replace `Commit.where(sha: params.sha)` with a lookup restricted to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a status webhook can only ever write a `Status` onto a commit belonging to a stack of the repository that actually sent the webhook.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually, though `test/**` itself is out of scope for remediation, only for demonstrating the bug):
```ruby
test "status webhook for repo A can write a Status onto a commit belonging to stack for repo B" do
  stack_b = shipit_stacks(:shipit)              # belongs to repo B
  commit_b = stack_b.commits.create!(sha: "deadbeef" * 5, ...)

  payload = {
    "repository" => { "full_name" => "attacker/repo-a" }, # different repo entirely
    "sha" => commit_b.sha,
    "state" => "success",
    "context" => "ci/blocking-check",
  }

  assert_difference -> { Shipit::Status.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  status = commit_b.statuses.last
  assert_equal stack_b.id, status.stack_id
  # Binding check: status.commit.stack's repository should equal payload's repository, but does not.
  refute_equal "attacker/repo-a", commit_b.stack.repository.full_name
end
```
This demonstrates that `create_status_from_github!` is reachable and writes a `Status` for `stack_b` even though the payload's `repository.full_name` never matches `stack_b`'s repository and `stack_b.github_api.statuses` is never invoked — breaking the claimed binding, whereas `Commit#refresh_statuses!` only ever creates statuses after calling `stack.github_api.statuses(github_repo_name, sha, ...)` for that same stack's own repository.
