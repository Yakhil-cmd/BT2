### Title
`StatusHandler` writes commit CI statuses by SHA alone, letting any org authenticated by the webhook signature inject statuses onto commits owned by a different organization's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook is authenticated using an HMAC computed against the whole request body, keyed to the GitHub App/organization identified by `repository.owner.login` (or `organization.login`) in that same payload. That authentication step only proves "this request was signed by org X's webhook secret." However, `StatusHandler#process` never checks that the `sha` being updated actually belongs to a repository/stack owned by org X — it looks the commit up globally by SHA across the entire Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to validate against solely from the payload's `repository.owner.login`: [1](#0-0) 

Once that HMAC check passes, `WebhooksController#create` dispatches the raw JSON straight to the handler for the event type: [2](#0-1) 

For the `status` event, `StatusHandler#process` resolves the target purely from `params.sha`, with no scoping to the `repository` object present in the same payload: [3](#0-2) 

Contrast this with the base `Handler` class, which does provide a `repository_name`/`stacks` helper scoped to `payload.dig('repository', 'full_name')`, used by every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers): [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler` is the one exception: it does not `require :repository` in its param schema at all, and calls `Commit.where(sha: params.sha)` unconditionally, then writes a status via `create_status_from_github!`: [7](#0-6) 

This breaks the intended binding "organization authenticated == repository/stack written." A GitHub organization that legitimately owns a Shipit-configured GitHub App (i.e., is a valid `Shipit.github(organization:)` target, so it can produce a validly-signed `X-Hub-Signature`) can send a `status` webhook whose `repository.owner.login` is its own org (to pass signature verification) but whose `sha` field names a commit SHA belonging to a *different* stack/organization tracked by the same Shipit instance. Because `Commit.where(sha:)` has no repository/stack filter, the forged status is written onto that unrelated commit.

### Impact Explanation
Commit CI status directly gates deploy-worthiness. `Commit#deployable?` requires `success? && !blocked?`, and `blocked?`/deployability is computed from the stored statuses: [8](#0-7) 

`ci.require`/`ci.blocking` in `shipit.yml` determine `required_statuses`/`blocking_statuses` used to compute the commit's status group, and continuous delivery / merge-queue logic depends on this reaching `success`: [9](#0-8) 

By forging a `success` status for the required CI context on a target commit that belongs to a *victim* organization's stack, an attacker who controls a completely unrelated (but legitimately Shipit-integrated) GitHub organization can flip that commit into a deployable state it never legitimately reached, enabling an unauthorized/unintended deploy via Shipit's continuous-delivery machinery — this crosses the "unauthorized deploy" bar.

### Likelihood Explanation
Exploitation requires: (a) the attacker's own organization to be a real, Shipit-configured GitHub App/org (so the webhook signature check succeeds — this is not "requiring a Shipit session/API token," it only requires controlling any org onboarded to the same Shipit instance, which is common in multi-tenant `secrets.yml` deployments per `docs/setup.md`'s "Using Multiple Github Applications" section), and (b) knowledge of the exact 40-character SHA of the victim commit, which is typically public (visible via the target's public GitHub repo, or via Shipit's own public stack/commit UI/API). Given multi-org Shipit deployments are an explicitly documented and supported configuration, this is a realistic scenario, not merely theoretical.

### Recommendation
Scope `StatusHandler` the same way as every other handler: require `repository.full_name` in the params schema and restrict the `Commit` lookup to commits belonging to stacks under that repository (e.g., `stacks.commits.where(sha: params.sha)` or `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`), rejecting/ignoring statuses for shas that fall outside the authenticated repository's stacks.

### Proof of Concept
1. Attacker controls organization `attacker-org`, which is configured as a legitimate secondary GitHub App/org in the shared Shipit instance's `secrets.yml` (per the documented multi-org setup), giving them a valid `webhook_secret` for HMAC signing.
2. Attacker discovers/know a commit SHA `abc123...` belonging to `victim-org/victim-repo`'s stack tracked in the same Shipit instance (e.g., from the victim's public GitHub commit history, or Shipit's own UI).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker signs the raw body with `attacker-org`'s webhook secret and sends it to `/github/webhooks` (or the mounted webhook route) with `X-Github-Event: status` and the correct `X-Hub-Signature`.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and validates the signature successfully (it is genuinely signed by that org's secret).
6. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, finds the victim's commit (regardless of `attacker-org` having no relation to it), and calls `commit.create_status_from_github!(params)`, writing a forged `ci/circleci success` status onto the victim's commit — potentially satisfying `ci.require` and unblocking an unauthorized deploy for the victim's stack.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
