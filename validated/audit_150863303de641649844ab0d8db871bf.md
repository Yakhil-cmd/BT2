### Title
Prosaic Contract Hash Excludes Party Addresses, Enabling Front-Running/Hijack of Pending Private Payment Contracts - (File: prosaic_contract.js)

### Summary
`prosaic_contract.getHash()` computes the contract identifier solely from `title`, `text`, and `creation_date`, deliberately excluding the `my_address`/`peer_address` fields that identify the actual parties to the contract [1](#0-0) . Because this hash is used as the primary lookup/storage key for contracts (`prosaic_contracts.hash`) and insertion uses `INSERT IGNORE` semantics, a malicious paired device can pre-empt ("front run") a legitimate contract offer by sending its own offer with identical `title`/`text`/`creation_date` (producing the same hash) before the real counterparty's offer arrives. This is the same bug class as the reported OpenZeppelin Governor issue: an identifier that is deterministically derived from *content* only, without binding to the legitimate proposer/party, lets an attacker claim the identifier first and hijack the resource associated with it.

### Finding Description
`createAndSend()` and the `'prosaic_contract_offer'` handler in `wallet.js` accept a contract whose `hash` must equal `getHash(body)` (title + text + creation_date only) [2](#0-1) . On acceptance, the record is persisted via `store()`, which does `INSERT IGNORE INTO prosaic_contracts (hash, ...)`, keyed by `hash` [3](#0-2) . Since `hash` does not incorporate `my_address`/`peer_address`, two structurally distinct contracts — one from a legitimate counterparty and one crafted by an attacker with the exact same `title`, `text`, and `creation_date` but attacker-controlled addresses — collide on the same primary key.

Because `store()` silently ignores duplicate-key inserts, whichever offer with that hash is received *first* wins: subsequent lookups (`getByHash(hash)`, used throughout `respond()`, `handleReceivedSharedAddress()`, `handleReceivedSigningUnit()`) will always resolve to the first-stored row, i.e., potentially the attacker's addresses, not the legitimate counterparty's [4](#0-3) [5](#0-4) . If the victim device later interacts with that hash (e.g. accepting via `respond()` or completing the shared-address derivation flow), it will use the attacker's `peer_address`/`peer_device_address` embedded in the hijacked row instead of the intended counterparty's, because `deriveSharedAddress()` builds the definition purely from the stored contract's `my_address`/`peer_address` fields [6](#0-5) .

This mirrors the OZ Governor front-running flaw cited in the report: `proposalId` there was derived only from proposal content (targets/values/calldatas/descriptionHash), not the proposer, letting any observer submit an identical proposal first and seize control of that ID. Here, `prosaic_contract.hash` is derived only from `title`+`text`+`creation_date`, not the parties, letting a paired device seize control of that contract ID.

### Impact Explanation
If exploited, the victim's wallet ends up associating a chat/negotiation thread and eventual shared payment address with an attacker-controlled address instead of the intended counterparty, because `deriveSharedAddress()` and downstream signing/acceptance logic operate on whichever row occupies the colliding hash. This can lead to funds being committed to a shared address that gives the attacker a payer/payee role they were never negotiated for, i.e., loss/misdirection of funds in a private payment arrangement — squarely within the "unauthorized spending" / "AA/contract fund loss" impact category permitted by the rules.

### Likelihood Explanation
Exploitation requires the attacker to be a paired device correspondent of the victim (an allowed threat actor per the rules) and to learn or guess the exact `title`, `text`, and `creation_date` of a contract about to be offered to the victim (e.g., by observing pairing chat, or colluding with one party in a negotiation, or if titles/texts are templated/predictable) and race the real offer. Given no cryptographic binding to addresses in the hash and `INSERT IGNORE` semantics, once these conditions are met the collision and hijack are deterministic and require no additional privilege. Likelihood is Medium: it requires timing/knowledge of exact contract content but no special network position beyond being a paired device.

### Recommendation
Include the party addresses (`my_address`/`peer_address`, analogous to the OpenZeppelin patch requiring `proposer` in the id) in `getHash()`'s input, so contract hashes are unique per (title, text, creation_date, parties). Additionally, `store()`/the `prosaic_contract_offer` handler should reject an incoming offer whose hash already exists for a *different* pair of addresses rather than silently ignoring it, and any contract lookup used for signing/fund-related flows should re-verify that the retrieved row's addresses match the expected correspondent's device/address before proceeding.

### Proof of Concept
1. Alice's wallet is expected to negotiate a prosaic contract with Bob: title=`"T"`, text=`"X"`, creation_date=`"2026-01-01 00:00:00"`. `hash = getHash({title:"T", text:"X", creation_date:"2026-01-01 00:00:00"})` — independent of any address.
2. Mallory (a paired device of Alice) learns/guesses these three fields before Bob sends his real offer, and sends `prosaic_contract_offer` to Alice with the same `title`/`text`/`creation_date` but `my_address`/`peer_address` set to Mallory's own addresses, and `hash` computed to match `getHash()`.
3. Alice's `wallet.js` handler validates `body.hash === prosaic_contract.getHash(body)` (passes, since Mallory's fields match) and calls `prosaic_contract.store(body)`, inserting the row keyed by `hash` [7](#0-6) .
4. Bob's legitimate offer (same title/text/creation_date, hash collides) arrives afterward; `store()`'s `INSERT IGNORE` drops it silently, leaving Alice's `prosaic_contracts` row pointing at Mallory as `peer_address`/`peer_device_address` [3](#0-2) .
5. Any later action keyed by `hash` (accept/response, `deriveSharedAddress`, shared-address exchange) operates on Mallory's addresses instead of Bob's, redirecting the negotiated shared payment address to include Mallory as a controlling party [8](#0-7) .

function store(objContract, cb) {
	var fields = '(hash, peer_address, peer_device_address, my_address, is_incoming, creation_date, ttl, status, title, text';
	var placeholders = '(?, ?, ?, ?, ?, ?, ?, ?, ?, ?';
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, true, objContract.creation_date, objContract.ttl, objContract.status || status_PENDING, objContract.title, objContract.text];
	if (objContract.shared_address) {
		fields += ', shared_address';
		placeholders += ', ?';
		values.push(objContract.shared_address);
	}
	fields += ')';
	placeholders += ')';
	db.query("INSERT "+db.getIgnore()+" INTO prosaic_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb)
			cb(res);
	});
}

function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}

function deriveSharedAddress(contract, bOfferor) {
	const offeror_address = bOfferor ? contract.my_address : contract.peer_address;
	const acceptor_address = bOfferor ? contract.peer_address : contract.my_address;
	const offeror_device_address = bOfferor ? device.getMyDeviceAddress() : contract.peer_device_address;
	const acceptor_device_address = bOfferor ? contract.peer_device_address : device.getMyDeviceAddress();
	var arrDefinition =
		["and", [
			["address", offeror_address],
			["address", acceptor_address]
		]];

	var assocSignersByPath = {
		"r.0": {
			address: offeror_address,
			member_signing_path: "r",
			device_address: offeror_device_address
		},
		"r.1": {
			address: acceptor_address,
			member_signing_path: "r",
			device_address: acceptor_device_address
		},
	};
	return { arrDefinition, assocSignersByPath };
}

function handleReceivedSharedAddress(contract, shared_address, retry_count = 0) {
	console.log(`received shared address ${shared_address} for prosaic contract ${contract.hash} from peer`);
	db.query("SELECT 1 FROM shared_addresses WHERE shared_address=?", [shared_address], function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`shared address ${shared_address} not found in db after 10 retries, giving up`);
			console.log(`shared address ${shared_address} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSharedAddress, 30000, contract, shared_address, retry_count + 1);
		}
		console.log(`shared address ${shared_address} found in db, deriving shared address definition to verify it matches the received one`);
		const { arrDefinition } = deriveSharedAddress(contract, false);
		const expected_shared_address = objectHash.getChash160(arrDefinition);
		if (expected_shared_address !== shared_address)
			return console.log(`expected shared address ${expected_shared_address} does not match received from offeror ${shared_address}`, JSON.stringify(arrDefinition, null, 2));
		console.log(`shared address ${expected_shared_address} matches the received one, saving it to the contract`);
		setField(contract.hash, "shared_address", shared_address);
	});
}
