### Title
Membership webhook signature verified against attacker-controlled organization but mutates victim's `Team`/`Membership` records - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` prioritizes `params['repository']['owner']['login']` over `params['organization']['login']` when selecting which org's `webhook_secret` verifies a webhook [1](#0-0) . For `membership` events, `MembershipHandler#process`/`find_or_create_team!` instead trusts `params.organization.login` and `params.team.id` to locate/create the `Team` and mutate its membership [2](#0-1) . Because these two fields can diverge in a single payload, an attacker who controls a legitimately-configured org (with its own `webhook_secret`) can forge a signature that Shipit accepts, while pointing `organization`/`team` at a victim org/team, mutating its membership.

### Finding Description
Broken binding: the organization used to select the verifying `webhook_secret` (`repository_owner` → `Shipit.github(organization: repository_owner)`) is asserted to equal the organization whose `Team`/`Membership` rows are mutated (`params.organization.login`, `params.team.id`). These are never actually checked against each other.

Code path:
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)` [3](#0-2) .
2. `repository_owner` reads `params.dig('repository', 'owner', 'login')` first, falling back to `params.dig('organization', 'login')` only if `repository` is absent [1](#0-0) .
3. `Shipit.github(organization:)` looks up `github_app_config(organization)` and instantiates a `GitHubApp` scoped to that org's own configured `webhook_secret` [4](#0-3) .
4. `GitHubApp#verify_webhook_signature` performs an HMAC-SHA1 compare using that org's `webhook_secret` only [5](#0-4) .
5. Once verification passes (using `repository_owner`'s secret), `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process`, which uses `params.team.id`/`params.organization.login`/`params.member.login` — none of which are cross-checked against `repository_owner` — to find/create the `Team` and add/remove the `Membership` [2](#0-1) .

Attacker request: POST `/webhooks` with `X-Github-Event: membership`, body containing:
- `"repository": {"owner": {"login": "attacker-org"}}` (an extraneous key not normally present on membership events)
- `"organization": {"login": "victim-org"}`
- `"team": {"id": <victim's real team id present in Shipit.github_teams>, "name": ..., "slug": ..., "url": ...}`
- `"member": {"login": "attacker-or-accomplice-login"}`
- `"action": "added"`

Signed with `X-Hub-Signature` computed from attacker-org's own `webhook_secret`.

`repository_owner` returns `"attacker-org"` (step 2), verification succeeds against attacker-org's own secret (steps 3-4), then `MembershipHandler` mutates the `Team`/`Membership` identified by `victim-org`'s `team.id` (step 5) — a record the attacker never authenticated as owner of.

Existing guards do not catch this: `verify_signature` only checks the HMAC against whichever org `repository_owner` names, it never compares that org to `params.organization.login` used downstream [6](#0-5) . The `ExplicitParameters` schema in `MembershipHandler` only type-checks presence/shape of `team`, `organization`, `member`, not cross-field consistency with the verifying identity [7](#0-6) . `drop_unhandled_event` and `check_if_ping` are unrelated gating steps and do not address this.

### Impact Explanation
A successful forgery lets the attacker add or remove members of a victim `Team` whose `github_id`/handle is referenced in `Shipit.github_teams`, which is used for authorization decisions elsewhere in the app (`app/controllers/concerns/shipit/authentication.rb`, `app/models/shipit/user.rb`). This is a cross-organization authorization write driven by a payload verified under one tenant's identity but mutating another tenant's team data — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any victim team id known to the attacker (team ids/slugs are often discoverable) and is not limited to a single request.

### Likelihood Explanation
This requires Shipit to be configured in multi-organization mode (`secrets.github` keyed by org) and the attacker to control (or know the `webhook_secret` of) at least one configured org distinct from the victim org — this is the stated precondition. Given that precondition, the attacker only needs to craft one HTTP POST with a correctly computed HMAC using their own secret; no other credential or session is needed, and the victim's `team.id` must be known/guessable. This is a low-cost, deterministic, and repeatable exploitation once the precondition holds.

### Recommendation
In `MembershipHandler` (and other handlers keying off `params.organization`/`params.repository`), validate that `params.organization.login` (or `params.repository.owner.login` when present) matches the `repository_owner` value that was used to select the verifying `webhook_secret`, and reject/drop the event otherwise. Alternatively, change `repository_owner` to never let a `repository.owner.login` outrank `organization.login` on events that are not repository-scoped, and have each handler assert equality between the field(s) it consumes and the org that authenticated the request before performing any mutation.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, hypothetical since `test/**` is out of scope for fixing but valid for demonstrating):
1. Configure `secrets.github` with two orgs: `attacker-org` (`webhook_secret: "attacker-secret"`) and `victim-org` (`webhook_secret: "victim-secret"`), and create `Team.create!(github_id: 999, organization: "victim-org", ...)`.
2. Build a membership payload: `{"action"=>"added", "team"=>{"id"=>999,...}, "organization"=>{"login"=>"victim-org"}, "member"=>{"login"=>"attacker-login"}, "repository"=>{"owner"=>{"login"=>"attacker-org"}}}`.
3. Sign the raw JSON with HMAC-SHA1 using `"attacker-secret"` and set as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert response is `200 OK` (verification passed using `attacker-org`'s secret — i.e., `repository_owner == "attacker-org"` yet `Shipit::Team.find_by(github_id: 999).organization == "victim-org"` and the equality `repository_owner == mutated_team.organization` is false).
6. Assert `Team.find_by(github_id: 999).members.map(&:login)` now includes `"attacker-login"`, proving a payload authenticated under `attacker-org`'s secret mutated `victim-org`'s team membership.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
