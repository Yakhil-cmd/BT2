### Title
Webhook signature verification binds to `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing a self-registered GitHub organization to forge webhook events (e.g., commit statuses) for a different organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) pulled straight from the unauthenticated JSON body. Once the signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) instead resolves the target `Repository`/`Stack` using a *different* field of the same unauthenticated body: `repository.full_name`. Nothing ties these two fields together, so a payload can be self-consistent for the field used at authentication time while pointing at a completely different repository for the field used at write time.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the request body, and `Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/`webhook_secret` configured for that specific organization (Shipit explicitly supports multiple organizations, each with its own app/secret, as shown by the `secrets_double_github_app.yml` test fixture and per-organization `Hook`/`GithubHook` fixtures such as `shopify_membership`).

Once `verify_signature` succeeds, `create` dispatches to the registered handler for the event: [3](#0-2) 

Every handler resolves which `Repository`/`Stack` to mutate via `repository_name`, which reads a **separate** JSON key (`repository.full_name`), not `repository.owner.login`: [4](#0-3) 

Because `verify_signature` only authenticates that *some* configured organization's secret matches the request, and the write path trusts an unrelated field of the same attacker-supplied JSON to pick the target repository, an attacker who legitimately controls one Shipit-registered GitHub organization (and therefore genuinely knows that organization's `webhook_secret`, since they set it themselves on their own GitHub App/webhook) can sign a payload with their own secret while setting `repository.full_name` to any other organization/repository that also happens to be registered in the same Shipit instance. The binding that should hold — "organization whose secret authenticated the request" == "organization whose repository state gets written" — is broken.

### Impact Explanation
This breaks a credential/repository boundary: a signature valid for org A is used to authorize a write against org B's repository. Concretely, the `status` event handler creates a `Status` record directly from attacker-controlled payload fields (`sha`, `state`, `target_url`, `description`, `context`) for whatever commit/repository `repository.full_name` points to, as shown by the controller test: [5](#0-4) 

Commit statuses are used by Shipit to gate whether a commit is deployable. An attacker who controls only their own GitHub org/webhook secret can forge a passing CI status on a commit belonging to a repository/stack they do not administer, undermining the deploy-gating checks and enabling an unauthorized deploy of a commit that never actually passed CI — this is a cross-repository write and a path to an unauthorized deploy, matching the required High/Critical impact bar.

### Likelihood Explanation
The attacker only needs to be an administrator of any single organization that is legitimately registered with the Shipit instance (multi-org support is a documented, in-scope configuration, e.g. `test/dummy/config/secrets_double_github_app.yml`). No access to the target organization, no Shipit session, and no privileged Shipit account are required — only the ability to compute a valid HMAC-SHA1 signature with a secret the attacker legitimately possesses for their own org, then send a crafted payload with a mismatched `repository.full_name`.

### Recommendation
Bind the fields consistently: derive both `repository_owner` (used to select the verification secret) and the repository/stack lookup key from the same trusted identifier, and reject any payload where `repository.owner.login` does not match the owner segment of `repository.full_name`. Alternatively, after selecting the `GitHubApp` for `repository_owner`, additionally verify that the resolved `Repository`/`Stack` actually belongs to that same organization before invoking the handler.

### Proof of Concept
1. Attacker registers/administers Org A, which is configured in Shipit with its own `webhook_secret` (per `Shipit.github(organization: "org-a")`).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<target commit in org-b/some-repo>",
     "state": "success",
     "target_url": "https://ci.example.com/fake",
     "description": "forged",
     "context": "ci/forged",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/some-repo" }
   }
   ```
3. Attacker signs the raw body with Org A's known `webhook_secret` and sets `X-Hub-Signature` accordingly.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, looks up Org A's app, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler` (invoked via `Handler#repository_name` → `payload.dig('repository','full_name')` → `"org-b/some-repo"`) creates/updates a `Status` on `org-b`'s commit, as demonstrated by the existing test pattern in `test/controllers/webhooks_controller_test.rb:42-59`, even though the signature only proved possession of Org A's secret.
