This is exactly the pattern described: the webhook signature is verified against the GitHub App configured for the organization named in `repository_owner`/`organization.login` (an unverified field read *before* signature checking), while the data that actually gets written (which `Stack`/`Repository` is synced, which branch is pushed) is derived from a *different* field in the same unverified JSON body: `payload.dig('repository', 'full_name')` in `Handler#repository_name` [1](#0-0) .

### Title
Webhook organization used for signature verification is not bound to the repository used for write actions - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [2](#0-1) . Once the signature check passes, the full raw, unverified payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler then re-reads the repository to act on from a **different** field of that same unverified payload: `payload.dig('repository', 'full_name')` [4](#0-3) , which is looked up via `Repository.from_github_repo_name` and used, e.g., in `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) .

Because the field that authenticates the org (`repository.owner.login`/`organization.login`) is never cryptographically bound to the field that is acted upon (`repository.full_name`), an attacker who can produce a validly-signed payload for **any one** tenant organization configured in `Shipit.github` (for example, by being a legitimate collaborator/webhook operator for their own low-value org that is also configured in the multi-tenant Shipit instance) can craft a payload whose `repository.owner.login`/`organization.login` matches their own org (so it passes `verify_webhook_signature` with their own `webhook_secret`), but whose `repository.full_name` names an arbitrary other tenant's repository/stack. `WebhooksController` does not compare these two identities.

### Finding Description
The trust binding that should hold is:
`organization authenticated by verify_webhook_signature == organization/repository whose Stack is mutated by the handler`

Before/after an attacker's crafted delivery:
- Before: signature is HMAC-SHA1 of the raw body under `Shipit.github(organization: repository_owner).webhook_secret`; `repository_owner` is taken from the same untrusted body used to compute the HMAC, but is not itself signed as "the org that owns this repo" independently of `repository.full_name`.
- After: `verify_signature` succeeds because the HMAC matches the secret of *the attacker's own organization* (since they control that org's webhook delivery and know its secret, or they are simply relaying its own genuine webhooks with a forged repository object appended), while `PushHandler`/other handlers act on `payload.dig('repository','full_name')`, which can be set to `victim-org/victim-repo`.

Because `Handler#repository_name` and `WebhooksController#repository_owner` read from independent JSON paths (`repository.full_name` vs. `repository.owner.login`/`organization.login`), nothing enforces `repository.full_name.split('/').first == repository.owner.login`.

### Impact Explanation
If exploitable, this allows a signed request for org A's webhook to trigger `sync_github`, GitHub sync jobs, commit status creation, or (via `check_suite`/`status` handlers) other stack-mutating operations against a Stack belonging to org B, i.e. a cross-repository/cross-organization write triggered without the victim organization's webhook secret. This matches the "cross-repository writes" Critical impact bucket in principle. However, this requires the attacker to already control a legitimately-configured GitHub App/organization within the same Shipit deployment (i.e., have a valid `webhook_secret` for some org known to this Shipit instance) — this is not a fully unprivileged, credential-free path; it depends on the deployment hosting multiple organizations' apps and an attacker controlling one of them.

### Likelihood Explanation
Low-to-Medium. It requires: (1) a multi-tenant Shipit deployment configuring more than one GitHub organization/App, and (2) attacker control of a legitimate webhook secret for at least one of those configured orgs (e.g., by installing their own GitHub App entry, or if they are an admin of one of the smaller orgs onboarded to the shared Shipit instance). Absent multi-tenancy, this collapses to a no-op because `repository_owner` and `repository.full_name`'s owner are always the same for genuine GitHub-originated events, and the actor already controls their own repo.

### Recommendation
In `WebhooksController#verify_signature` and `Handler#repository_name`, enforce that the organization used to select the webhook secret is cryptographically tied to the repository being mutated: derive both from `repository.full_name` (single source of truth) and reject the payload if `repository.owner.login` does not match the derived owner, or better, look up the `Repository`/`Stack` matched by `repository.full_name` and re-verify that its `owner` matches the organization whose secret validated the signature before invoking any handler.

### Proof of Concept
Not independently verified end-to-end (would require exercising a live multi-tenant Shipit instance with two configured organizations and one attacker-controlled webhook secret); reasoning is based on static review of `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`. Conceptually:
1. Deployment configures `github: { org-a: {webhook_secret: SECRET_A}, org-b: {webhook_secret: SECRET_B} }`.
2. Attacker controls `org-a`'s webhook secret (e.g., is an admin of `org-a`, a legitimate low-privilege tenant).
3. Attacker POSTs to `/webhooks` a JSON body with `organization.login = "org-a"` / `repository.owner.login = "org-a"` (so `repository_owner` resolves to `org-a`) but `repository.full_name = "org-b/victim-repo"`, `ref = "refs/heads/main"`, signed with `SECRET_A`.

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

          stacks

        end

        end
      end
