### Title
Attacker Can Permanently Lock KAIA and Corrupt Bridge `lowerHandleNonce` via Revert-on-Receive Recipient in `handleKLAYTransfer` — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` sends KLAY to the caller-supplied `_to` address via a bare `.call.value()` and hard-reverts the entire transaction if the call fails. Because all state mutations — including the nonce accounting written by `_updateHandleNonce` — are inside the same atomic transaction, a revert rolls back every write. An attacker who controls `_to` (a contract with a togglable `receive()`) can make every operator attempt to settle their bridge request revert permanently, locking their KAIA in the source bridge and freezing `lowerHandleNonce` at the poisoned nonce forever.

---

### Finding Description

In `handleKLAYTransfer` the execution order is:

1. `_lowerHandleNonceCheck` — validates nonce is ≥ `lowerHandleNonce`
2. `_voteValueTransfer` — sets `closedValueTransferVotes[nonce] = true` once threshold is reached
3. `_setHandledRequestTxHash` — marks the source tx hash as handled
4. `handleNoncesToBlockNums[nonce] = blockNumber` — records block number
5. `_updateHandleNonce` — advances `lowerHandleNonce` and `recoveryBlockNumber`
6. `emit HandleValueTransfer`
7. `_to.call.value(_value)("")` — sends KLAY
8. `require(ok, "handleKLAYTransfer: transfer failed")` — **reverts everything above if step 7 fails** [1](#0-0) 

Because step 8 reverts the entire transaction, all writes from steps 2–5 are rolled back. `closedValueTransferVotes[nonce]` returns to `false`, `handleNoncesToBlockNums[nonce]` returns to 0, and `lowerHandleNonce` is unchanged. The operators can retry, but every retry will fail identically because `_to` always reverts on receive.

The vote-closing flag is set inside `_voteValueTransfer` before the transfer: [2](#0-1) 

Since the revert undoes `closedValueTransferVotes[nonce] = true`, operators can re-vote indefinitely — but the transfer will always fail, so the nonce is never consumed.

`_updateHandleNonce` advances `lowerHandleNonce` only through consecutive successfully-handled nonces: [3](#0-2) 

Because nonce N is never successfully handled, `lowerHandleNonce` is permanently stuck at N, and `recoveryBlockNumber` never advances past the block preceding the attacker's request.

---

### Impact Explanation

- **KAIA permanently locked**: The attacker's KAIA was deposited into the source bridge when `RequestValueTransfer` was emitted. The destination bridge can never settle nonce N, so those funds are irrecoverable.
- **Bridge nonce state permanently corrupted**: `lowerHandleNonce` is frozen at N. The bridge recovery daemon keeps replaying from `recoveryBlockNumber` (the block before N), wasting operator resources and preventing the bridge's accounting from ever advancing past the poisoned nonce.
- **Subsequent nonces can still be processed** (they pass `_lowerHandleNonceCheck` since `lowerHandleNonce ≤ _requestedNonce`), but `lowerHandleNonce` and `recoveryBlockNumber` never advance, breaking the bridge's settlement and recovery invariants permanently.

This matches the allowed impact gate: *unauthorized loss of bridged KAIA assets* and *persistent corruption of bridge state that breaks settlement*.

---

### Likelihood Explanation

Any user can call `requestKLAYTransfer` on the source chain and specify any address as `_to`, including a contract they control. No special privilege is required. The attacker only needs to:

1. Deploy a contract with a togglable `receive()` on the destination chain.
2. Submit a bridge request naming that contract as `_to`.
3. Toggle the contract to revert after the request is emitted.

This is a low-cost, unprivileged, one-time action.

---

### Recommendation

Do not revert the entire `handleKLAYTransfer` transaction when the KLAY push to `_to` fails. Instead, use a pull-payment (escrow) pattern: record the owed amount in a mapping and let the recipient withdraw it separately. This decouples nonce settlement from recipient behavior:

```solidity
mapping(address => uint256) public pendingWithdrawals;

function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    // ... nonce checks and updates ...
    pendingWithdrawals[_to] += _value;
    emit HandleValueTransfer(...);
}

function withdraw() external {
    uint256 amount = pendingWithdrawals[msg.sender];
    require(amount > 0);
    pendingWithdrawals[msg.sender] = 0;
    (bool ok,) = msg.sender.call.value(amount)("");
    require(ok, "withdraw failed");
}
```

Alternatively, wrap KLAY as WKLAY and transfer the wrapped token, which cannot revert on receive.

### Proof of Concept

```solidity
// Deployed on the destination chain by the attacker
contract MaliciousReceiver {
    bool public rejectKLAY = false;

    function toggle() external { rejectKLAY = !rejectKLAY; }

    receive() external payable {
        require(!rejectKLAY, "blocked");
    }
}
```

**Steps:**

1. Attacker deploys `MaliciousReceiver` on the destination chain with `rejectKLAY = false`.
2. Attacker calls `requestKLAYTransfer(maliciousReceiver, value, extraData)` on the source bridge, depositing KAIA. [4](#0-3) 
3. Source bridge emits `RequestValueTransfer` with `_to = maliciousReceiver` and increments `requestNonce`.
4. Attacker calls `maliciousReceiver.toggle()` — now `rejectKLAY = true`.
5. Bridge operators observe the event and call `handleKLAYTransfer(..., maliciousReceiver, value, nonce, ...)` on the destination bridge.
6. The call reaches line 98: `_to.call.value(_value)("")` — `MaliciousReceiver.receive()` reverts.
7. `require(ok, "handleKLAYTransfer: transfer failed")` causes the entire transaction to revert. [5](#0-4) 
8. All state writes (nonce update, vote closure, tx hash marking) are rolled back.
9. Operators retry indefinitely — every attempt reverts. `lowerHandleNonce` is permanently frozen at nonce N. The attacker's KAIA remains locked in the source bridge with no recovery path.
