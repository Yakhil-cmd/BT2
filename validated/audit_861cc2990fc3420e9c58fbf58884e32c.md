### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup advances foreign stack's continuous-deployment queue - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `params.sha`, with no scoping to the repository named in the webhook payload (`payload.dig('repository', 'full_name')`), unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). Because `Commit.sha` is only unique per `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` indexes `[stack_id, sha]`, not `sha` alone), and forked repositories share identical git object hashes for shared history, a legitimately GitHub-signed status webhook from an attacker-owned fork can write a `success` status onto a `Commit` row belonging to an entirely different stack/repository whenever the shas coincide.

### Finding Description
The claimed binding is: `payload.dig('repository', 'full_name')` (the repository that authenticates/owns the webhook) `== stack.repository.full_name` (the repository whose `UndeployedCommit` queue is being advanced by the resulting status write).

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's own `repository.owner.login`. This proves only that the payload was signed for *some* org GitHub knows about — it does **not** prove that the `sha`/target commit belongs to that repository.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
There is no call to the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which every other repo-scoped handler (`PushHandler`, `CheckSuiteHandler`) uses to filter by `Repository.from_github_repo_name(repository_name)`. `StatusHandler` is the outlier: it queries commits globally across every stack in the installation.
- `Commit` shas are only unique within a stack (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), so the same 40-character sha can legitimately exist as separate `Commit` rows in two different stacks — this is the normal, expected case for forked repositories, since forking preserves git object identity (the commit sha is a hash of tree/parents/author/message, unaffected by which remote hosts it).

Exploit flow:
1. Attacker forks the victim's public GitHub repository (or otherwise obtains/controls a repo sharing history with the victim's tracked branch), thereby creating, in their own fork, a commit with the identical sha as a commit sitting in the victim stack's `expected_to_be_deployed?` window (an `UndeployedCommit`).
2. Attacker points a CI system (or a manual authenticated GitHub Status API call) at their own fork to post a `status` event with `state: "success"` for that shared sha. GitHub signs and delivers this webhook exactly as it would any legitimate event for the attacker's own repository — no Shipit secret, session, or privileged role is needed, since the attacker is a legitimate owner/admin of their own fork.
3. `WebhooksController#verify_signature` validates the signature against the attacker's own organization (found via `payload.dig('repository','owner','login')`) and succeeds — this check only proves "this payload really came from GitHub for this org," not "this sha belongs to this org's repo."
4. `StatusHandler#process` ignores `payload['repository']` entirely and matches `Commit.where(sha: params.sha)`, hitting the victim's `Commit` row too, and calls `commit.create_status_from_github!(params)` on it.
5. The victim's `Commit#status` now reflects `success`. For an `UndeployedCommit` wrapping that commit in the victim's queue, `deployable?` (`app/models/shipit/commit.rb:227-229`, `!locked? && (stack.ignore_ci? || (success? && !blocked?))`) can flip to `true`, and `UndeployedCommit#deploy_disallowed?` (`app/models/shipit/undeployed_commit.rb:39-41`, `!deployable? || !stack.deployable?`) flips to `false`. If `stack.continuous_deployment` is enabled and the commit is within `expected_to_be_deployed?`'s window (`app/models/shipit/undeployed_commit.rb:47-53`), the victim stack's continuous-deployment loop will pick this commit as the next one to auto-deploy.

This exists precisely because `StatusHandler` fails to enforce the repository binding that every comparable handler enforces via the `stacks` scoping helper.

### Impact Explanation
An attacker who controls no Shipit credentials can trigger an unauthorized deploy on another tenant's continuous-deployment-enabled stack by exploiting a forked/shared-history commit and a legitimately-signed webhook from their own repository. This is a cross-tenant "payload for one repository mutating another's stack/commit," matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any repository whose commit history overlaps with a repo the attacker controls (most commonly via forking public repos, which is extremely common on GitHub), and the blast radius spans every stack tracking the same shared commit.

### Likelihood Explanation
Preconditions: victim repo must be forkable/public (or otherwise have shared commit history reachable by the attacker), victim stack must have `continuous_deployment` enabled and the shared commit must currently sit within the `expected_to_be_deployed?` window (i.e., be the next commit(s) queued). Cost to the attacker is low: fork the repo, push a status via GitHub's API/CI on the fork (no Shipit secret needed — GitHub signs the webhook using the app's shared secret, verified only against the sender's own org). This is fully repeatable and does not require guessing any secret or session, only knowledge of the commit sha, which is publicly visible.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, consistent with `PushHandler` and `CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures a status webhook can only mutate commits belonging to stacks whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` style, or extending `undeployed_commits_test.rb`):
```ruby
test "StatusHandler does not update commits belonging to a different repository sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, author: shipit_users(:codertocat))
  next_expected = victim_stack.next_expected_commit_to_deploy
  undeployed = UndeployedCommit.new(victim_commit, index: 0, next_expected_commit_to_deploy: next_expected)

  # Binding before: payload repository != victim repository
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-fork' },
  }
  refute_equal attacker_payload['repository']['full_name'], victim_stack.repository.full_name

  assert_predicate undeployed, :deploy_disallowed? # before: not deployable (no status)

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  assert_equal 'success', victim_commit.state # forged write landed on victim commit
  refute_predicate UndeployedCommit.new(victim_commit, index: 0, next_expected_commit_to_deploy: next_expected), :deploy_disallowed?
end
```
This demonstrates that a payload naming a foreign repository still mutates the victim stack's commit status and flips `deploy_disallowed?` to `false`, confirming the broken binding.
