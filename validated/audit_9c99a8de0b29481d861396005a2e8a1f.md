### Title
Unbounded `burnt_gas_reward` fraction can cause a chain-wide panic on `checked_sub().unwrap()` during function-call gas accounting - (File: `runtime/runtime/src/lib.rs`)

### Summary
The C4 finding describes an admin-settable fee that can be set above 100%, causing an unchecked subtraction (`reward` lowered by `fee`) to underflow and break the core `deposit` flow for every user, with no recovery path. Nearcore has a structurally identical pattern: the `burnt_gas_reward` fraction in `RuntimeFeesConfig`, which represents "percentage of burnt gas refunded to the receiving contract," is never validated to be `<= 1` (i.e. `<= 100%`) anywhere in the config-loading or genesis-validation code, yet it is used directly in an unchecked balance subtraction that is reached on every successful function-call receipt.

### Finding Description
`burnt_gas_reward` is a `Rational32` parameter of `RuntimeFeesConfig`, loaded from the protocol parameter tables (e.g. `core/parameters/res/runtime_configs/parameters.yaml`, protocol-version diff files such as `core/parameters/src/fixture_diff_0.yml`), parsed via `TryFrom<&ParameterValue> for Rational32` in [1](#0-0)  with no bound check on numerator vs denominator.

In `apply_action_receipt`, the reward is computed and subtracted from the amount of tokens burnt for the receipt: [2](#0-1) 

Specifically, `receiver_gas_reward` is computed as `gas_burnt_for_function_call * numerator / denominator` of `burnt_gas_reward`, converted to a balance as `receiver_reward`, and then:
```
tx_burnt_amount = tx_burnt_amount.checked_sub(receiver_reward).unwrap();
```
If `burnt_gas_reward`'s numerator exceeds its denominator (i.e. the "reward fraction" is set to more than 100%), `receiver_reward` can exceed `tx_burnt_amount`, causing the `checked_sub` to return `None` and the `.unwrap()` to panic.

By contrast, other `Rational32`-typed economic parameters in the genesis config are explicitly bounds-checked: `online_max_threshold`/`online_min_threshold` are validated to be `<= 1`, and `gas_price_adjustment_rate` is validated to be `< 1`, in `GenesisValidator::validate_processed_records`: [3](#0-2) 

No equivalent invariant exists for `burnt_gas_reward` (or `gas_refund_penalty`, which is used similarly) in either `genesis_validate.rs` or in `RuntimeConfig`/`ParameterTable` construction, so nothing in the codebase prevents this fraction from exceeding 1.

### Impact Explanation
This computation runs in `apply_action_receipt`, which is executed for every `FunctionCall` action receipt during normal chunk application — a path reachable by any unprivileged account submitting a transaction that includes a function call. If a future protocol-version parameter change (via the `runtime_configs/NN.yaml` diff mechanism) ever sets `burnt_gas_reward` above `1` (numerator > denominator), the `.unwrap()` panic in `runtime/runtime/src/lib.rs:999` would trigger deterministically on essentially any function-call receipt with non-zero burnt gas, crashing every node applying that chunk — a chain-wide halt, not an isolated single-shard or single-account failure. This is analogous to the reported impact ("breaking essential mechanics… impossible to recover from") but manifests as a node panic/chain stall rather than a reverted call.

### Likelihood Explanation
Likelihood is low under normal operation because `burnt_gas_reward` is only changed through protocol-version parameter diffs subject to review, and the current values (`3/10`) are safe. However, unlike the sibling `Rational32` fields (`online_max_threshold`, `gas_price_adjustment_rate`) that do have explicit `<= 1` invariant checks, there is no defense-in-depth validation for `burnt_gas_reward` (or `gas_refund_penalty`) to catch an accidental misconfiguration (e.g., a typo'd denominator in a `runtime_configs/NN.yaml` diff) before it reaches production, which is exactly the failure mode the original report warns about.

### Recommendation
Add an explicit invariant check — analogous to the existing `online_max_threshold`/`gas_price_adjustment_rate` checks in `core/chain-configs/src/genesis_validate.rs` — that validates `burnt_gas_reward.numer() <= burnt_gas_reward.denom()` (and similarly for `gas_refund_penalty`) either at parameter-table parse time (`core/parameters/src/parameter_table.rs`) or in `RuntimeConfig::new`/`try_from`, rejecting any configuration where the fraction exceeds `1`. Additionally, consider replacing the `.unwrap()` in `runtime/runtime/src/lib.rs:999` with a saturating subtraction or an explicit `IntegerOverflowError`/`RuntimeError` to avoid a hard panic even if an invalid value slips through.

### Proof of Concept
1. In a test or local protocol-parameter diff, set `burnt_gas_reward: { numerator: 11, denominator: 10 }` (110%) via the parameter table (mirroring how `fixture_diff_0.yml`/`fixture_diff_1.yml` demonstrate diffs are applied, see [4](#0-3) ).
2. Submit any transaction containing a `FunctionCall` action that burns gas on execution (e.g., the existing `test_apply_surplus_gas_for_function_call` scenario in [5](#0-4)  or the `contract_function_call_reward` helper in [6](#0-5) ).
3. During `apply_action_receipt`, `receiver_gas_reward` (and thus `receiver_reward`) will exceed `tx_burnt_amount`, causing `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` at `runtime/runtime/src/lib.rs:999` to panic, aborting chunk application on every node that applies this receipt.

/// The portion of the function call's burnt gas that is credited back to the
/// contract account as a reward (30% of wasm-burnt gas).
fn contract_function_call_reward(
    fee_helper: &FeeHelper,
    res: &FinalExecutionOutcomeView,
    method_name: &str,
    args_len: u64,
) -> Balance {
    let num_bytes = method_name.len() as u64 + args_len;
    let gas_burnt_for_function_call = res.receipts_outcome[0]
        .outcome
        .gas_burnt
        .checked_sub(fee_helper.function_call_exec_gas(num_bytes))
        .unwrap();
    fee_helper.gas_burnt_to_reward(gas_burnt_for_function_call)
}
