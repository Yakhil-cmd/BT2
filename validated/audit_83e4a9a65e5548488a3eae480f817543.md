## Title
`GIT_PROXY_COMMAND` (and any environment variable) injected via `machine.environment` in a fork's `shipit.yml` reaches `dependencies.override` command execution - (File: app/models/shipit/deploy_spec.rb)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` from the checked-out `shipit.yml` with no filtering or allow-list, unlike `deploy_variables`/`rollback_variables` which are passed through `EnvironmentVariables#permit`. `TaskCommands#env` merges this unfiltered hash into the environment used for every task, including `install_dependencies` (which runs `deploy_spec.dependencies_steps!`), and that env is forwarded to `Command#unbundled_env`, which merges it over `BASE_ENV` before `PTY.spawn` — allowing an attacker-controlled `GIT_PROXY_COMMAND` (or any other env var) to be injected into the process that runs `dependencies.override` steps.

### Finding Description
The broken binding: the invariant claimed is `dependencies.override step env ∩ fork-controlled keys = ∅`, but in practice `TaskCommands#env` = `super.merge(@stack.env).merge({...fixed keys...}).merge(deploy_spec.machine_env).merge(@task.env)` [1](#0-0)  where `deploy_spec.machine_env` is `config('machine', 'environment') || {}`, read verbatim from the repository's `shipit.yml` with zero filtering [2](#0-1) .

Contrast this with `deploy_variables`/`rollback_variables`, which are explicitly passed through `EnvironmentVariables#permit` via `filter_deploy_envs`/`filter_rollback_envs` [3](#0-2)  — no equivalent filtering exists for `machine.environment`.

`install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using this same unfiltered `env`, for each entry in `deploy_spec.dependencies_steps!` (i.e., `config('dependencies', 'override')`) [4](#0-3) [5](#0-4) .

`Command#initialize` stores `@env = env.transform_values { |v| v&.to_s }` [6](#0-5) , and `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [7](#0-6) , meaning any key in `@env` — including `GIT_PROXY_COMMAND` — overrides the base environment. `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [8](#0-7) .

The `shipit.yml` used to build the `DeploySpec::FileSystem` is read from the checked-out working directory of the task (`config_file_path` scans `shipit.yml`/`.shipit/shipit.yml` etc. under `@app_dir`) [9](#0-8) , which for a `ReviewStack` is checked out from the PR/fork branch content — i.e., attacker-controlled. `ReviewStack` itself adds no additional sanitization to `machine_env`/dependency steps; its only overrides are `env` (adding PR label flags) and provisioning state machine handling [10](#0-9) .

None of the standard guards (`filter_deploy_envs`, `filter_rollback_envs`, `EnvironmentVariables#permit`) apply to `machine_env`; those filters only cover `deploy`/`rollback` `variables`, not `machine.environment`. There is no allow-list restricting `GIT_PROXY_COMMAND`, `LD_PRELOAD`, or similar dangerous variable names from `machine.environment`.

### Impact Explanation
If the finding holds, an attacker who can get a `shipit.yml` with a `machine.environment` block checked out into a task's working directory (via a review-stack/fork branch under `prevent_with_label`, or any stack whose deploy spec is read from attacker-influenced content) can set `GIT_PROXY_COMMAND` (or `GIT_SSH_COMMAND`, `PATH`, etc.) so that any subsequent `git` invocation performed by that command (or a following one sharing the merged env) executes an attacker-named binary — Remote Code Execution on the Shipit deploy host. This is a Critical-class impact (RCE via `Command`/`PTY.spawn`) per the stated severity matrix. Blast radius is scoped to the repository/stack whose spec is used (the review stack's own working directory/container), but any deploy host process spawned with that env is compromised.

### Likelihood Explanation
I was not able to fully verify, within the available iterations, two preconditions central to this specific question:
1. Whether `dependencies.override` steps (as opposed to `deploy`/`review` steps) actually invoke `git` with `GIT_PROXY_COMMAND` honored (i.e., whether the injected env variable is actually consumed by a command git executes during `dependencies.override`, versus simply being present in the env unused).
2. Whether `prevent_with_label` provisioning behavior gates *provisioning* of the review stack container (requiring a maintainer label) in a way that would prevent an unprivileged fork's `shipit.yml` from ever being loaded/executed at all before a maintainer applies the label — I found references to `prevent_with_label` in `app/models/shipit/repository.rb` and the labeled/unlabeled webhook handlers but did not have iteration budget left to trace whether that gate blocks `DeploySpec::FileSystem` construction (and thus `machine_env`) prior to explicit maintainer approval.

Assuming the review stack is provisioned (whether automatically or after a label is applied by a maintainer, per `prevent_with_label` semantics), the fork PR author fully controls the `shipit.yml` content and therefore `machine.environment`, at zero cost beyond opening a PR from their own fork. The `dependencies.override` step is a standard, commonly-used deploy-spec feature, so the primitive is broadly repeatable across any repo enabling review stacks.

### Recommendation
Filter `machine.environment` through an explicit allow-list (or deny-list of dangerous variable names such as `GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `PATH`, `BUNDLE_*`) analogous to `EnvironmentVariables#permit` used for `deploy_variables`/`rollback_variables`, and apply the same filtering to `DeploySpec#machine_env` before it is merged into `TaskCommands#env`. Additionally, consider excluding `machine.environment` entirely from specs originating in unprivileged/fork contexts (e.g., review stacks prior to maintainer approval under `prevent_with_label`).

### Proof of Concept
Not fully constructible without confirming the two open preconditions above (whether git actually respects `GIT_PROXY_COMMAND` during a `dependencies.override` invocation in this codebase's test harness, and whether `prevent_with_label` gates spec loading). A minitest along the lines of building a `DeploySpec::FileSystem` from a fixture `shipit.yml` containing `machine: {environment: {GIT_PROXY_COMMAND: "..."}}`, calling `TaskCommands#install_dependencies`, and asserting `Command#unbundled_env['GIT_PROXY_COMMAND']` equals the injected value would demonstrate the `machine_env` -> `Command#env` propagation, but I could not verify this against the actual test suite in the remaining budget.

Given the unresolved preconditions, I cannot confirm this with the certainty required — the `machine_env` unfiltered-merge-into-`PTY.spawn` path is real and demonstrated in code, but exploitability specifically gated by `prevent_with_label` and specifically materializing as `GIT_PROXY_COMMAND` abuse during `dependencies.override` remains unverified.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
