Based on the ocore address-definition validation logic, there is a directly analogous "no maximum duration / no sanity bound on time parameter" issue.

### Title
Unbounded `timestamp`/`mci`/`age` values in address definitions can accidentally/irreversibly freeze funds - (File: definition.js)

### Summary
When `validateDefinition` evaluates a `timestamp`, `mci`, or `age` operator inside an address (or asset) spending-condition definition, it only checks that the relation is one of `=, >, <, >=, <=, !=` and that the compared value is a non-negative integer. There is no upper bound (or "reasonableness") check on the literal value, analogous to the missing max-duration/max-end-time check in the Sherlock finding for `StreamFactory`.

### Finding Description
In `definition.js`, the `evaluate()` function inside `validateDefinition` handles the `mci`, `age`, and `timestamp` ops: [1](#0-0) 
The only numeric constraint applied is `isNonnegativeInteger(value)`, with no ceiling relative to current time/mci or any "max in the future" guard. The same absence of bound-checking exists in the authentication-time evaluator that actually enforces these conditions against `last_ball_timestamp`/`last_ball_mci`: [2](#0-1) 
Because address definitions are permanent (the address = hash of the definition, and normal usage is to author it once and reuse), any single unprivileged unit poster can define an address whose only spending branch is gated by `["timestamp", ">", X]` (or `["mci", ">", X]` / `["age", ">", X]`) with an arbitrarily large `X` (e.g., far beyond any realistic future date/mci, even up to `Number.MAX_SAFE_INTEGER`-range values that still pass `isNonnegativeInteger`). Funds sent to such an address before that time/mci is reached cannot be spent by any authentifier, because the definition-evaluation layer (`validateAuthentifiers`) will simply return `false` for the `timestamp`/`mci` branch until the (possibly absurd) threshold is met.

This mirrors the nounDAO `StreamFactory` root cause precisely: the protocol validates that the relation/format is syntactically well-formed but does not bound the "duration" implied by the time value, so a legitimate (non-malicious) unit poster can inadvertently create a spending condition that locks funds for an impractically long or effectively infinite period.

### Impact Explanation
Any bytes/asset amount sent to an address (or held under an asset spending condition) whose branch structure depends on an unbounded `timestamp`/`mci`/`age` comparison can become permanently inaccessible if the chosen value is unreasonably large and there is no alternative unlock branch (e.g., no `or` with a plain `sig` fallback, or a payer-cancel path as streamer has). Unlike `StreamFactory`, ocore address definitions have no "canceled by payer" escape hatch once funds are deposited — the funds are frozen for as long as the (potentially absurd) time condition dictates, which given the lack of a max bound, could be effectively forever. This is a fund-freezing bug reachable purely by an ordinary unprivileged address definer/unit poster.

### Likelihood Explanation
Likely to occur accidentally (e.g., a wallet-composition tool, `definition_template`, or shared-address template generator computing a wrong/huge timestamp/mci due to a units bug — seconds vs. milliseconds, or an off-by-orders-of-magnitude value) rather than being deliberately malicious, exactly like the original finding, which classifies this as Medium severity: an honest mistake with no built-in protocol guardrail.

### Recommendation
Add a sanity ceiling in `validateDefinition`'s `mci`/`age`/`timestamp` case (and mirror it, if feasible, in the evaluation path) analogous to the fix recommended in the original report: reject values that are more than some maximum reasonable offset from `objValidationState.last_ball_mci`/`last_ball_timestamp` (e.g., a maximum number of years/blocks in the future), or at minimum, document/UI-warn wallet/template authors so they don't accidentally embed unreachable time conditions. Since existing well-formed contracts already rely on relative timestamps (see `test/samples/futures_contract.oscript` and `ico_with_milestones.oscript`), any bound should be generous but finite.

### Proof of Concept
1. An unprivileged user composes and posts a unit defining a new address (or a shared/multisig address template) with definition:
`["timestamp", ">", 99999999999]` (`isNonnegativeInteger` accepts this large epoch value, which is centuries in the future).
2. `validateDefinition` accepts it because it only checks relation validity and `isNonnegativeInteger` — see [1](#0-0) .
3. The user or a counterparty sends bytes/assets to this address.
4. At authentication time, `validateAuthentifiers`'s `timestamp` case compares against `objValidationState.last_ball_timestamp`, which will never reach the huge value in any realistic timeframe — see [3](#0-2) .
5. The funds are permanently unspendable, with no cancellation mechanism, unlike the referenced `StreamFactory` case.
