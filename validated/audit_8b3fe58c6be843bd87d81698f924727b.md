### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is never bound to the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the request signature against using `repository_owner`, read from the JSON body itself (`repository.owner.login`, falling back to `organization.login`). The event handlers, however, resolve the Stack/Team/Commit to mutate using a *different* JSON field — `repository.full_name` (in `Handler#repository_name`) or `organization.login` (in `MembershipHandler`) — with no check that these fields agree with the organization whose secret validated the signature. The signature therefore authenticates "some organization named in the body," not "the organization that owns the repository being written to."

### Finding Description
`verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and then calls `github_app.verify_webhook_signature`, where `repository_owner` is taken straight from the untrusted JSON payload: [2](#0-1) .

`GitHubApp#verify_webhook_signature` in [3](#0-2)  returns `true` unconditionally whenever that organization's configured `webhook_secret` is blank (`return true unless webhook_secret`). Per-organization `webhook_secret` is optional/nullable in every documented and templated configuration (`docs/setup.md`, `template.rb`, `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml` all show `webhook_secret:` with no enforced value), and Shipit explicitly supports multiple GitHub organizations sharing one instance (`Shipit.github_organizations`, `github_app_config`) as described in `docs/setup.md` "Using Multiple GitHub Applications".

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire attacker-controlled JSON body* to handlers: [4](#0-3) . Those handlers locate the target Stack via `repository.full_name`, not `repository.owner.login`: [5](#0-4) , e.g. `PushHandler#process` syncs any stack matching that repository/branch: [6](#0-5) , and `MembershipHandler#process` adds/removes users from a `Team` keyed by `organization.login`/`team.id`, which directly feeds `User#authorized?` and thus `Shipit.github_teams` gating: [7](#0-6) , [8](#0-7) .

The equality binding that should hold — "the organization whose secret verified this request" == "the organization/repository this request is allowed to mutate" — is never checked. An attacker only needs one organization in the multi-org config to have a blank `webhook_secret` (a documented, supported, non-default-enforced state) to obtain a universal forging oracle: craft any JSON body, set `repository.owner.login` (or `organization.login`) to the weakly-configured org so `verify_signature` trivially passes, and set `repository.full_name` / other identifying fields to point at a *different*, properly configured stack/team belonging to a different organization.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out in scope. Concretely, with one blank-secret organization configured anywhere in the deployment:
- `push` events can be forged for any tracked Stack, forcing `GithubSyncJob`/`stack.sync_github` to run against attacker-chosen `expected_head_sha`, corrupting the commit graph used to gate deploys.
- `status` events can be forged (`StatusHandler`) to inject fake commit statuses for arbitrary commits, which feed `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`, directly influencing the automatic merge queue (`stack.schedule_merges`) — a path to an **unauthorized merge**.
- `membership` events can be forged (`MembershipHandler`) to add an attacker-controlled GitHub login to any `Team`, and since `User#authorized?` checks membership against `Shipit.github_teams`, this is a direct **escalation into `Shipit.github_teams` authorization** — letting an unprivileged GitHub identity gain authenticated access to the Shipit UI/API.

These outcomes map to the in-scope Critical ("unauthorized deploy, rollback or merge") and High ("escalation into `Shipit.github_teams` authorization") impact categories.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires a multi-organization Shipit deployment where at least one configured organization has a blank/unset `webhook_secret`. This is not enforced against by any validation in the codebase I could find (`GitHubApp#initialize` merely does `@webhook_secret = @config[:webhook_secret].presence`, no presence validation anywhere), and the documented example configs all ship with blank `webhook_secret` by default, making this a plausible operational state rather than a contrived one. I was not able to find any startup-time check that rejects a blank `webhook_secret` for a configured organization, nor any code that cross-validates `repository.owner.login` against `repository.full_name` before dispatch — these are the two central facts supporting root cause, and I'm reasonably confident of them, but the actual attacker likelihood is coupled to a security-relevant misconfiguration (unset secret) that some deployments will avoid.

### Recommendation
1. In `WebhooksController#verify_signature`, after establishing the verifying organization, validate that all repository/organization identifiers used by any dispatched handler (`repository.full_name`, `organization.login`, `team.organization`) belong to that same verified organization before invoking handlers.
2. Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in production; either require `webhook_secret` for every configured GitHub App/organization, or fail closed (return `false`) instead of silently trusting unsigned payloads.
3. Consider deriving the "verifying organization" from Shipit's own stored mapping of repository → organization (e.g., via `Repository.from_github_repo_name`) rather than from attacker-supplied payload fields, so the value used for authentication and the value used for authorization are provably the same field.

### Proof of Concept
Preconditions: a Shipit instance configured with two GitHub organizations, e.g. `weak-org` (no `webhook_secret` set) and `victim-org` (properly configured, secret unknown to attacker), each per `docs/setup.md`'s "Using Multiple Github Applications" schema, with a Stack tracking `victim-org/victim-repo`.

```
POST /github/webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/garbage - not checked)
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999, "name": "Attacker Team", "slug": "attacker-team", "url": "https://example.com" },
  "organization": { "login": "weak-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" }
}
```

`repository_owner` resolves to `weak-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`. `MembershipHandler#process` then creates/uses `Team` #999 under organization `weak-org` and adds `attacker-github-login` as a member — and by repeating this with a `team.id` that matches (or is set to collide with) a `Team` actually referenced by `Shipit.github_teams` for `victim-org`, the attacker's GitHub identity becomes `authorized?` for the Shipit instance without ever touching `victim-org`'s real webhook secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
