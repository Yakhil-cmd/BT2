### Title
Ambient git credential-cache authority is reachable by attacker-controlled `--exechook-command` content synced from the remote repo - (File: `pkg/hook/exechook.go`, `main.go`)

### Summary
The reported "relayer could lose funds" issue is a case of an untrusted downstream execution context (`xReceive`) inheriting the ambient authority (`tx.origin`) of a trusted principal (the relayer), letting attacker-controlled code drain funds the relayer never intended to expose. `git-sync` has a structurally analogous pattern: the `--exechook-command` hook runs with the freshly-synced (attacker-influenceable) worktree as its current directory and inherits the full process environment, while git-sync globally configures a shared, ambient `git-credential-cache` daemon for authentication. Any local process that can reach that daemon's socket - including the exechook process, whose working directory and, if configured as a relative path, whose very executable content come from the synced repo - can retrieve the cached repo credentials without git-sync's involvement.

### Finding Description
When any authenticated mode is used (username/password, `--askpass-url`, `--credential`, or GitHub App), `SetupDefaultGitConfigs` sets `credential.helper` to `cache --timeout 3600` globally: [1](#0-0) . `git-credential-cache` stores credentials in a background daemon reachable over a local UNIX socket; any local process running as the same user can query it for a URL/host and receive back the username/password, independent of which component originally called `git credential approve`.

Separately, git-sync's exec-hook feature executes an operator-provided command with the synced worktree as its working directory, and passes through the entire process environment: [2](#0-1) . The worktree path handed to the hook is exactly the just-synced content of `--repo`: [3](#0-2) , and the documented contract explicitly says the command "executes with the synced repo as its working directory": [4](#0-3) .

This mirrors the report's structure precisely:
- Relayer ⇔ the git-sync process, which is the entity that legitimately holds/caches repo credentials via `CallAskPassURL`/`StoreCredentials` ( [5](#0-4) ) or GitHub App tokens ( [6](#0-5) ).
- `xReceive` with unreliable code ⇔ `--exechook-command`, commonly pointed at a script that lives inside the synced repository itself (a repo-relative path), so its content is whatever the last synced commit contains.
- `tx.origin`-style ambient authority ⇔ the shared `git-credential-cache` daemon socket, which does not scope access to "only the git-sync process" - it's ambient authority available to any co-located process, exactly like `tx.origin` being ambient rather than an explicit capability.

If an attacker with push access to the tracked ref of `--repo` (the same untrusted-content threat actor the rules call out) supplies/overwrites the file referenced by a repo-relative `--exechook-command`, their code executes after every sync with the git-sync process's ambient identity and can issue `git credential fill` (or read the daemon socket directly) to exfiltrate the cached username/password or short-lived GitHub App token for that repo (and potentially other repos whose credentials were cached in the same process/session, e.g., via `--credential` for submodules).

### Impact Explanation
Successful exploitation discloses git credentials (password, PAT, or GitHub App installation token) to an attacker who already has push access to the synced ref. This can escalate to a wider compromise where that credential is reused for other repos (`--credential` entries used for submodules), or allow the attacker to impersonate the git-sync identity toward other systems reachable with the leaked token, satisfying the "credential or token disclosure" impact bar.

### Likelihood Explanation
This requires specific preconditions/flags, similar to the original report needing relayers to use a non-isolated wallet: (1) an authenticated `--repo` (`--askpass-url`, `--credential`, `--username`/`--password-file`, or GitHub App flags) so `credential.helper cache` is configured; (2) `--exechook-command` set to a path that resolves into the synced worktree (a documented, common operator pattern since the hook's whole purpose is to act on synced content); and (3) attacker push access to the tracked branch/ref. Given these, the attack requires no additional git-sync bug beyond the documented behavior - it is a design gap in ambient-credential scoping analogous to the original finding, not a memory-safety or logic bug.

### Recommendation
- Do not rely on a shared ambient `git-credential-cache` daemon when hooks may execute untrusted, repo-sourced code; scope credentials so hook processes cannot query them (e.g., avoid `credential.helper=cache` in favor of narrowly-scoped, single-use credential injection, or run hooks in a separate credential-less environment/namespace).
- Document, as Connext did for relayers, that `--exechook-command` should reference an operator-controlled path outside the synced `--root`/worktree, never a path resolved from repo content, and that hook processes should be treated as running with the same trust level as arbitrary code from the remote repo.
- Consider clearing/filtering the hook's environment and denying it access to the credential-cache socket by default.

### Proof of Concept
1. Operator runs git-sync with an authenticated repo and a repo-relative exechook script:
   `git-sync --repo=https://github.com/victim/repo --root=/mnt/git --link=current --username=bot --password-file=/creds/pass --exechook-command=./ci/on-sync.sh`
2. Because `credential.helper` is globally set to `cache --timeout 3600` (`main.go` `SetupDefaultGitConfigs`), the bot's credentials for `https://github.com/victim/repo` are cached in the `git-credential-cache--daemon` socket after the first sync.
3. An attacker with push access to `victim/repo` commits a malicious `ci/on-sync.sh` that runs `git credential fill <<<"url=https://github.com/victim/repo"` (or talks to the cache socket directly) and POSTs the returned `username=`/`password=` to an attacker-controlled endpoint.
4. On the next sync, git-sync's exechook runner executes this file from the freshly checked-out worktree (`pkg/hook/exechook.go` `Do`), running with the full ambient environment and access to the local credential-cache socket, exfiltrating the bot's credentials without any git-sync code change or misuse beyond the documented `--exechook-command` feature.

// CallAskPassURL consults the specified URL looking for git credentials in the
// response.
//
// The expected URL callback output is below,
// see https://git-scm.com/docs/gitcredentials for more examples:
//
//	username=xxx@example.com
//	password=xxxyyyzzz
func (git *repoSync) CallAskPassURL(ctx context.Context) error {
	git.log.V(3).Info("calling auth URL to get credentials")

	var netClient = &http.Client{
		Timeout: time.Second * 1,
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}
	httpReq, err := http.NewRequestWithContext(ctx, http.MethodGet, git.authURL, nil)
	if err != nil {
		return fmt.Errorf("can't create auth request: %w", err)
	}
	resp, err := netClient.Do(httpReq)
	if err != nil {
		return fmt.Errorf("can't access auth URL: %w", err)
	}
	defer func() {
		_ = resp.Body.Close()
	}()
	if resp.StatusCode != http.StatusOK {
		errMessage, err := io.ReadAll(resp.Body)
		if err != nil {
			return fmt.Errorf("auth URL returned status %d, failed to read body: %w", resp.StatusCode, err)
		}
		return fmt.Errorf("auth URL returned status %d, body: %q", resp.StatusCode, string(errMessage))
	}
	authData, err := io.ReadAll(resp.Body)
	if err != nil {
		return fmt.Errorf("can't read auth response: %w", err)
	}

	username := ""
	password := ""
	for line := range strings.SplitSeq(string(authData), "\n") {
		keyValues := strings.SplitN(line, "=", 2)
		if len(keyValues) != 2 {
			continue
		}
		switch keyValues[0] {
		case "username":
			username = keyValues[1]
		case "password":
			password = keyValues[1]
		}
	}

	if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
		return err
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}

// Do runs exechook.command, implements Hook.Do.
func (h *Exechook) Do(ctx context.Context, hash string) error {
	ctx, cancel := context.WithTimeout(ctx, h.timeout)
	defer cancel()

	worktreePath := h.getWorktree(hash)

	env := os.Environ()
	env = append(env, envKV("GITSYNC_HASH", hash))

	h.log.V(0).Info("running exechook", "hash", hash, "command", h.command, "timeout", h.timeout)
	stdout, stderr, err := h.cmdrunner.Run(ctx, worktreePath, env, h.command, h.args...)
	if err == nil {
		h.log.V(1).Info("exechook succeeded", "hash", hash, "stdout", stdout, "stderr", stderr)
	}
	return err
}
