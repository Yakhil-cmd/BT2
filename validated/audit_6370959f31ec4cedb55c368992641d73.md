### Title
Webhook authentication is scoped to the org named in an attacker-controlled `repository.owner.login`/`organization.login` field, but write targets are chosen from the separate, equally attacker-controlled `repository.full_name`/`team.id`/`member.login` fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate an incoming webhook against based on `repository.owner.login` (falling back to `organization.login`) read straight out of the unauthenticated JSON body. `verify_webhook_signature` then returns `true` unconditionally whenever that org's configured `webhook_secret` is blank/nil. [1](#0-0) [2](#0-1)  Once "verified" (or trivially bypassed because that org has no secret configured — a state the engine's own example configs explicitly allow, e.g. `webhook_secret: # nil`), the actual event handlers act on completely different, independently attacker-controlled fields of the same payload: `repository.full_name` (used to resolve the `Stack`/`Repository` to write to) and, for the `membership` event, `team.id`/`organization.login`/`member.login` (used to create Teams/Users and mutate `Team` membership, the exact structure that backs `Shipit.github_teams` authorization). [3](#0-2) [4](#0-3) [5](#0-4)  The engine never checks that the org used to authenticate the request is the same org that owns the repository/team being mutated.

### Finding Description
The binding that should hold is: **org authenticated by signature == org whose repository/team is written**. It does not.

- `verify_signature` picks the GitHub App (and its `webhook_secret`) using `repository_owner`, itself derived purely from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`): [6](#0-5) 
- If that org's `webhook_secret` is blank, `GithubApp#verify_webhook_signature` short-circuits to `true`, skipping HMAC verification entirely: [2](#0-1) 
- Handlers never re-derive or cross-check the authenticating org against the entity they mutate. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a different JSON key than the one used for authentication — with no relation enforced between the two: [3](#0-2) 
- `PushHandler#process` uses that repository-derived `stacks` scope to invoke `stack.sync_github(expected_head_sha: params.after)`, an attacker-supplied SHA, for any stack under the (attacker-chosen) `repository.full_name`: [4](#0-3) 
- `MembershipHandler#process` is worse: it `find_or_create!`s a `Team` keyed by `params.team.id` and sets `team.organization = params.organization.login`, then adds/removes an arbitrary `params.member.login` user to/from that team's membership — entirely from body fields that were never covered by the org-scoped signature check that gated the request: [5](#0-4) 

Because `Team` membership is exactly the mechanism `Shipit.github_teams` authorization relies on (per `lib/shipit.rb` / `app/controllers/concerns/shipit/authentication.rb`), an attacker able to get any request past `verify_signature` for one org can create/repopulate a `Team` object and grant/revoke membership on it using attacker-chosen team IDs and organization strings, without the request ever being validated for that team's real organization.

### Impact Explanation
This breaks the equality "org authenticated == org/repo/team written," matching the required High-impact criterion of escalation into `Shipit.github_teams` authorization. It also allows unauthorized writes/syncs (`sync_github`, review-stack provisioning/archival) against stacks belonging to a repository never covered by the signature check, satisfying the cross-repository-writes style impact.

### Likelihood Explanation
Medium: the primary trigger (no `webhook_secret` configured for a given org) is an explicit, documented configuration state supported by the engine's own sample configs (`webhook_secret: # nil` in `config/secrets.development.shopify.yml`), not a hypothetical misconfiguration invented for this analog. Any deployment with a multi-org setup where at least one org has no secret (e.g., an org onboarded before secrets were provisioned) is fully exposed to unauthenticated forged webhooks that name a *different* org's repository/team.

### Recommendation
Bind repository/team identity to the authenticating context: after (or as part of) `verify_signature`, re-validate that `repository.full_name`'s owner (and, for `membership` events, `organization.login`) equals the `repository_owner`/org actually used to select and validate the webhook secret, rejecting the request otherwise. Additionally, treat a missing/blank `webhook_secret` as a configuration error to warn/alert on rather than silently trusting the payload (`return true unless webhook_secret` in `lib/shipit/github_app.rb` should not implicitly authenticate unsigned requests for multi-tenant installations).

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (no `webhook_secret` set) and `OrgB` (has a `webhook_secret`, tracks a real stack/repo and a `Team` used for `Shipit.github_teams` authorization).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://github.com/orgs/OrgB/teams/admins" },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. `repository_owner` resolves to `OrgA`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` with no HMAC check.
4. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 999) { |t| t.organization = "OrgA" }` and calls `team.add_member(User.find_or_create_by_login!("attacker-controlled-login"))` — but if `github_id: 999` already refers to `OrgB`'s real admin team (created by a prior legitimate webhook), the attacker instead adds themselves to `OrgB`'s existing team via `find_or_create_by!` matching the existing record, escalating into whatever authorization `Shipit.github_teams` grants that team — despite the request only ever being "authenticated" against `OrgA`.

**Note on confidence:** I could not fully trace the exact runtime wiring of `Shipit.github_teams` to `Team#add_member`/authorization checks within the remaining tool budget (only grep hit counts were retrieved for `lib/shipit.rb`, `app/models/shipit/user.rb`, and `app/controllers/concerns/shipit/authentication.rb`, not their contents), so the precise authorization consequence of team membership should be confirmed by reading those files directly.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else

          end
        end
