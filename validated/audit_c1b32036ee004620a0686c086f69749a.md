### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but events are processed against the org/repo derived from `repository.full_name` — allowing cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the `X-Hub-Signature` against using `repository_owner`, a field taken from the attacker-supplied JSON body itself. The event handlers, however, act on repositories/stacks looked up via a *different* field of the same untrusted body: `repository.full_name`. Because these two fields are never cross-checked against each other, and because `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (a documented, supported configuration), an attacker can forge a webhook payload that authenticates as one (unsecured) configured organization while acting on a stack belonging to an entirely different, secured organization.

### Finding Description
`verify_signature` picks the `GitHubApp` used to check the HMAC signature like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Note `repository_owner` and `repository.full_name` are two independent JSON fields in the same attacker-controlled raw body (they are not required to be consistent — GitHub itself would keep them consistent, but a forged request is not GitHub). The signature check only proves the request body as a whole was signed by *whatever secret belongs to `repository_owner`'s org* — it does not prove any relationship between that org and the org embedded in `repository.full_name`.

Once `verify_signature` passes, the raw payload is dispatched unchanged to handlers: [2](#0-1) 

Handlers such as `PushHandler` resolve the target `Stack`/`Repository` using `repository.full_name`, not `repository.owner.login`: [3](#0-2) [4](#0-3) 

Signature verification is a no-op if the org's `webhook_secret` is blank: [5](#0-4) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is explicitly documented as **optional** per organization, and Shipit supports multiple GitHub App configurations keyed by organization name: [6](#0-5) [7](#0-6) 

**Binding broken:** the organization whose secret authenticated the webhook ≠ the repository/organization whose `Stack` is written to as a result of the webhook.

**Attack:** In a multi-org Shipit instance (documented feature) where at least one configured org has no `webhook_secret` (documented as optional), an attacker POSTs to `/webhooks` with:
- `X-Github-Event: push`
- Body: `{"repository": {"owner": {"login": "<unsecured-org>"}, "full_name": "<victim-org>/<victim-repo>"}, "ref": "refs/heads/<branch>", "after": "<attacker-chosen-sha>"}`

`repository_owner` resolves to `<unsecured-org>` → `Shipit.github(organization: "<unsecured-org>").verify_webhook_signature` returns `true` unconditionally (no secret configured) → request is accepted → `PushHandler` looks up stacks for `<victim-org>/<victim-repo>` (a properly secured org/repo) and calls `stack.sync_github(expected_head_sha: params.after)`, forging a push event and driving the victim stack's sync/deploy machinery with attacker-chosen `after` SHA, with zero valid credentials for the victim organization.

### Impact Explanation
This lets an unprivileged external attacker forge GitHub events (push/status/check_suite/membership/etc.) attributed to a stack belonging to a fully-secured organization, without ever knowing that organization's `webhook_secret`, `GITHUB_TOKEN`, or having any repository access. Depending on stack configuration (continuous deployment enabled, branch targeting), this can drive `sync_github`/deploy triggering with an attacker-chosen commit SHA, i.e., an unauthorized deploy/rollback trigger on a repository the attacker does not control — meeting the Critical bar of "an unauthorized deploy" via a spoofed cross-organization event.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (a first-class, documented configuration), and (2) at least one configured org without a `webhook_secret` (documented as optional, so plausible in real deployments, e.g. a low-value/test org kept alongside a production org). Given those two documented/supported conditions, exploitation requires only crafting a JSON body and POSTing it — no credentials, no signing key, and no interaction with the victim org needed.

### Recommendation
Bind the authenticating organization to the acted-upon organization: derive both the signing org and the repository-lookup org from the *same*, single field (e.g. resolve the target `Repository`/`Stack` first, derive its owning organization from the engine's own DB record, and verify the signature against that organization's secret) rather than trusting `repository.owner.login` and `repository.full_name` as independently-controlled fields of the untrusted payload. Additionally, consider making `webhook_secret` mandatory (or requiring it to be set for at least one org before allowing multi-org configs), since an org without a secret effectively disables authentication for any payload claiming that org, which the current architecture allows to be leveraged against other orgs.

### Proof of Concept
Given `config/secrets.yml` with two orgs configured — `unsecured-org` (no `webhook_secret`) and `victim-org` (secret set, with a Stack tracking `victim-org/app`):

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature needed)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-present-in-victim-repo>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/app"
  }
}
```

`repository_owner` → `"unsecured-org"` → `verify_webhook_signature` returns `true` (no secret) → `PushHandler` resolves `Repository.from_github_repo_name("victim-org/app")` → matching `Stack`s call `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, forging a legitimate-looking push event for `victim-org/app` despite the attacker never possessing `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
