### Title
Attestor-gated ("spender_attested") assets can be permanently frozen with no recovery path - ([File: validation.js])

### Summary
The Sherlock report describes a pattern where a fund-moving primitive (`sweepNative`) performs a mandatory external check (`recipient.call{value}`) that can unconditionally fail depending on a third party's state, and once it fails there is no alternative code path to move the funds — they are permanently stuck. Ocore has a structurally analogous, unprivileged-reachable mechanism for `spender_attested` custom assets: every payment of such an asset requires that both the payer(s) and *all* output addresses be present in the current on-chain attestor-issued attestation list, and if that condition can never be satisfied again, the coins held at any address become permanently unspendable, with no fallback transfer path in the protocol.

### Finding Description
For assets defined with `spender_attested: true`, `validatePayment` in `validation.js` enforces that at least one author is attested and (for issuance) the issuer is attested: [1](#0-0) 

For divisible (and analogously indivisible) transfers, `validatePaymentInputsAndOutputs` additionally requires that **every output address** of the payment be attested at validation time, with no exception: [2](#0-1) 

The attestor list itself is asset-definer-controlled and can be updated at any later point via an `asset_attestors` message, checked once per unit: [3](#0-2) 

`storage.readAsset`/`loadAssetWithListOfAttestedAuthors` always look up only the **most recent** stable attestor list unit for the asset and re-derive `arrAttestedAddresses` from current on-chain attestations issued by that list, with no way to "grandfather" already-issued coins: [4](#0-3) [5](#0-4) 

Composer-side code paths that build payments (`divisible_asset.js`, `indivisible_asset.js`) perform the exact same unconditional check before even attempting to compose a transfer, and simply refuse to spend if `arrAttestedAddresses.length === 0`: [6](#0-5) [7](#0-6) 

There is no other function, admin override, sweep mechanism, or bypass anywhere in the payment/validation code to move a `spender_attested` asset's balance once the attestor(s) stop attesting the holder (or any intended recipient) — the check is a hard, unconditional gate exactly like the `require(success)` in `sweepNative()`, except here failure is permanent for the class of assets rather than a one-off revert.

### Impact Explanation
If the asset's designated attestor(s) revoke, fail to renew, or simply never (re-)attest a holder's address — which is entirely plausible since attestors are external, off-chain-controlled parties whose willingness to attest can change over time, expire, or be withdrawn — then any balance of that asset held at that address becomes permanently frozen. There is no way within ocore's transaction/validation model to move the funds out once this condition is unmet, matching the "funds may be locked with no way to move them out" impact class from the report. This can affect any holder of such an asset (a broad, unprivileged population, since anyone can receive spender_attested asset outputs), not just the definer.

### Likelihood Explanation
This is a design feature intentional to `spender_attested` assets (KYC/whitelisting-style assets), so it is reachable purely through normal use: any user who receives a spender_attested asset and is later dropped from (or never added to) the attestor's attestation set, or where the attestor(s) stop publishing attestations at all, will find their balance frozen forever with no on-chain recourse. No privileged access or malicious node/peer behavior is required to trigger the freeze — only normal receipt of a spender-attested asset combined with the attestor(s)' subsequent (or absent) attestation behavior.

### Recommendation
Provide a recovery mechanism for `spender_attested` assets, e.g.: allow the asset definer to unilaterally reassign/burn stuck balances via a definer-authorized transfer that bypasses the attestation check for the holder side, or add a timeout/escape-hatch condition (similar to arbiter dispute timeouts) allowing holders to reclaim/burn coins if no attestor has attested them within a defined window. At minimum, document this as an inherent risk of `spender_attested` assets so wallets/dApps can warn users before accepting such assets.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and an initial `attestors` list `[Attestor1]`.
2. `Attestor1` attests address `Alice` (via an `attestation` message), then Alice receives a payment output of asset `X`.
3. Later, the definer posts an `asset_attestors` update (allowed at any time per `validateAttestorListUpdate`/the `assocHasAssetAttestors` check in `validation.js`) replacing the attestor with `Attestor2`, or `Attestor1` simply stops publishing attestations for Alice.
4. Alice now tries to spend her `X` balance to any address. `loadAssetWithListOfAttestedAuthors` recomputes `arrAttestedAddresses` from the latest attestor list and finds Alice (and/or her intended recipient) not attested by the current attestor set.
5. `validatePayment`/`validatePaymentInputsAndOutputs` reject the transfer with `"none of the authors is attested"` or `"some output addresses are not attested"` — Alice's coins remain in her balance forever with no other path in the protocol to move them. [1](#0-0) [2](#0-1)

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
