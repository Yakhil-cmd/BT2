### Title
Membership webhook lets attacker forge `Team#organization` for an unrelated victim organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) used to authenticate a webhook using `params.dig('repository','owner','login')`, falling back to `organization.login` only when `repository` is absent from the payload. `MembershipHandler`'s `params` DSL never requires (or forbids) a `repository` key, and separately consumes `organization.login` to stamp `team.organization` in `find_or_create_team!`. Because these two lookups read different top-level keys of the same attacker-controlled JSON body, an attacker who can produce a validly-signed webhook for their own organization can set `repository.owner.login` to their own org (satisfying signature verification) while setting `organization.login` to an arbitrary victim organization string that gets persisted onto a newly created `Team` row.

### Finding Description
The binding that should hold is: `repository.owner.login` (the value `WebhooksController#repository_owner` uses to pick the verifying `GithubApp`) `==` `organization.login` (the value written into `team.organization`). This is never enforced.

Code path:
- `WebhooksController#repository_owner` [1](#0-0)  resolves the signing organization from `repository.owner.login`, only falling back to `organization.login` if `repository` is missing entirely.
- `verify_signature` uses that resolved value to fetch the `GithubApp` and validate `X-Hub-Signature` against its `webhook_secret` [2](#0-1) .
- `MembershipHandler`'s `params` schema requires `organization.login`, `team.id/name/slug/url`, and `member.login`, but has no requirement on (or cross-check against) `repository` [3](#0-2) .
- `find_or_create_team!` persists `team.organization = params.organization.login` unconditionally on first sight of a given `github_id` [4](#0-3) .

Attack: attacker controls (or administers the webhook configuration of) an org `attacker-org` that is a legitimately registered `GithubApp` in this Shipit instance, so GitHub-signed (or manually HMAC-signed, since the attacker knows/controls that org's `webhook_secret`) `membership` events for `attacker-org` are accepted. The attacker sends (or crafts) a `membership` webhook body containing:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "x", "slug": "x", "url": "http://x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
`verify_signature` resolves `repository_owner` to `attacker-org` and validates successfully using `attacker-org`'s secret. `MembershipHandler` then creates a `Team` with `github_id: 999999` and `organization: "victim-org"`, a label the attacker chose, unconnected to any org whose credentials actually verified the request. No existing guard (`ExplicitParameters` schema, `drop_unhandled_event`, model validations) checks that `organization.login` matches `repository.owner.login`.

### Impact Explanation
A `Team` row is written with an `organization` value the attacker fully controls, disconnected from the organization whose secret actually authenticated the request. Since `Team.find_or_create_by_handle` and related lookups key off `organization` + `slug` [4](#0-3) , this can poison team records used by authorization/lookups keyed by organization+slug, corrupting cross-tenant team scoping. This matches the Critical category "a payload for one repository mutating another's ... team," since a request verified for one organization results in a persisted record falsely attributed to a different organization. The action is repeatable for any `github_id` not already present, against any victim organization string the attacker chooses.

### Likelihood Explanation
Requires the attacker to control (or be able to trigger validly-signed webhooks for) at least one organization already registered as a `GithubApp` in the target Shipit instance — consistent with the stated threat model of "any GitHub user who can... emit webhooks from a repository they own." No Shipit session, API token, or victim-org secret is needed; the attacker only needs their own org's already-configured webhook integration. Crafting the divergent `repository`/`organization` payload is a normal HTTP POST to `/webhooks`, trivially repeatable.

### Recommendation
In `MembershipHandler` (or generically in `WebhooksController`), verify that `params.dig('repository','owner','login')` (or the value used by `repository_owner`) equals `organization.login` before trusting the latter, or simply derive `team.organization` from the already-verified `repository_owner`/organization context rather than from an independently attacker-suppliable payload field.

### Proof of Concept
Minitest (extending `test/controllers/webhooks_controller_test.rb` style, e.g. in `WebhooksControllerTest`):
```ruby
test ":membership rejects a repository/organization mismatch" do
  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  body = {
    action: 'added',
    team: { id: 424242, name: 'Forged', slug: 'forged', url: 'http://example.com' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'shopify' } } # org whose secret verified the request
  }.to_json

  assert_difference -> { Team.count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 424242)
  refute_equal 'shopify', team.organization       # org that actually authenticated the request
  assert_equal 'victim-org', team.organization    # attacker-chosen label persisted instead
end
```
This demonstrates that `repository.owner.login` (`"shopify"`, the verifying organization) and the persisted `team.organization` (`"victim-org"`) diverge, confirming the unenforced binding.
