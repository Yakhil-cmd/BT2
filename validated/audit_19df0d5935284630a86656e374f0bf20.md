### Title
`StatusHandler#process` mutates `Commit` rows across unrelated repositories by matching `sha` globally instead of scoping to the sending repository's `Stack` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository that sent the webhook, even though the base `Handler` class already provides a `stacks` helper scoped by `repository_name` (`payload.dig('repository', 'full_name')`) that this handler ignores. Any commit sharing a `sha` in a completely different, unrelated `Stack`/repository will have `create_status_from_github!` invoked on it using the attacker-controlled payload.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`org(WebhookApp verifying the signature) == org(every Commit mutated by StatusHandler#process)`

should always be true, but `StatusHandler#process` breaks it.

Code path:
1. `Shipit::WebhooksController#create` parses the raw payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` [1](#0-0)  — this correctly authenticates that the request came from Org X (the sender), but authentication only proves *who signed*, not *which commits may be touched*.
2. `Handler#initialize`/`.call` parse `params` via `ExplicitParameters` and invoke `process` [2](#0-1) . The base `Handler` class exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, derived from `payload.dig('repository', 'full_name')` [3](#0-2) , which is exactly the correct scoping mechanism other handlers (e.g., pull_request handlers) rely on.
3. `StatusHandler#process`, however, does not call `stacks` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) , a table-wide, cross-tenant query with no `stack_id`/repository filter whatsoever.

Root cause: the `StatusHandler`'s params schema doesn't even require/use `repository.full_name` for scoping (only `sha`, `state`, etc. are required/accepted) [5](#0-4) , and the query against `Commit` has no join/scope to `Stack`/`Repository`.

Attacker's exact request: attacker controls Org X's repository and thus can send a legitimately-signed `POST /webhooks` with `X-Github-Event: status`, body `{"repository": {"full_name": "orgX/repo", "owner": {"login": "orgX"}}, "sha": "deadbeef...", "state": "success", ...}`, signed with Org X's real `webhook_secret` (attacker owns that repo, so they legitimately have/trigger this webhook). If Org Y's stack also has a `Commit` row with the same `sha` (plausible for cherry-picks, empty commits, shared upstream history, or squashed merges), `StatusHandler#process` will call `create_status_from_github!` on Org Y's commit too, writing a `Status` record originated from Org X's payload into Org Y's `Stack`.

Existing guards evaluated and why they don't help: `verify_signature` only authenticates that Org X's secret was used (correct binding for "who sent this"), but does nothing to prevent the handler from touching rows belonging to other orgs [6](#0-5) ; `drop_unhandled_event` and `ExplicitParameters` schema only validate presence/shape of fields, not ownership; the `stacks`/`repository_name` scoping helper exists in `Handler` but is simply unused by `StatusHandler`.

### Impact Explanation
An attacker who owns/controls any GitHub repository wired to Shipit can, using only their own repo's legitimate webhook secret (no privilege escalation needed), write a `Shipit::Status` record onto a `Commit` belonging to an entirely different organization's `Stack`, as long as that commit's `sha` collides. This is a cross-tenant write into another org's data via a payload that org never authenticated ("a payload for one repository mutating another's stack, commit, task or team" — Critical per the provided severity rubric). Practically, `create_status_from_github!` affects commit status aggregation, which can influence deploy-readiness checks/CI gating decisions on Org Y's stack, and is repeatable against any repository configured on the same Shipit instance whenever a `sha` collision exists (which is realistic for forks of a shared upstream, cherry-picks, or empty commits reused across branches/orgs).

### Likelihood Explanation
Preconditions: two `Shipit::Stack`s from different orgs on the same Shipit instance, each with a `Commit` row sharing an identical `sha`. This is a realistic, not contrived, scenario (forks/cherry-picks/empty commits/shared upstream history commonly produce identical SHAs across independent repos). The attacker needs zero Shipit credentials — only their own repository's genuine webhook secret, which they inherently have as the owner/maintainer of that (attacker-controlled) repo. The attack is a single signed HTTP request and is trivially repeatable for any repository pair with a matching `sha`.

### Recommendation
Scope the lookup in `StatusHandler#process` to the sending repository's stacks, mirroring the pattern already available in `Handler#stacks`, e.g. query commits via `stacks.flat_map(&:commits)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (would live under `test/models/shipit/webhooks/handlers/status_handler_test.rb`, not included in this repo currently):
1. Create `stack_x` (org "orgx/repo") and `stack_y` (org "orgy/repo"), each with a `Commit` having identical `sha: "deadbeef" * 5`.
2. Build a payload: `{"repository" => {"full_name" => "orgx/repo", "owner" => {"login" => "orgx"}}, "sha" => "deadbeef"*5, "state" => "success"}`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert the binding both before and after:
   - Before: `commit_y.reload.status` (or associated `Status` count) is unset/baseline.
   - After: assert `commit_x.reload` has the new status (expected, correct) AND assert `commit_y.reload` has **no** new status/`Status` record (expected to hold, but currently fails because `create_status_from_github!` is invoked on `commit_y` too).
5. The test demonstrates `commit_y.statuses.count` changes after a webhook signed only by orgx's secret, proving the cross-tenant write.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
