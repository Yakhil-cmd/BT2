### Title
Webhook signature verification binds to `repository.owner.login`, but the handler dispatch binds to `repository.full_name` — cross-organization stack sync/deploy trigger - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to verify the HMAC against using `repository.owner.login` (falling back to `organization.login`) from the webhook JSON body. Once the signature check passes, `Handler#repository_name` — used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) to look up the `Stack`(s) to act on — reads a *different* field of the same untrusted JSON body: `repository.full_name`. These two fields are never cross-validated against each other, so the org whose secret authenticated the request is not the repository the handler actually writes to.

### Finding Description
In a Shipit instance configured for multiple GitHub organizations (the officially documented "Using Multiple Github Applications" setup, see `docs/setup.md:182-209` and `config/secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret`: [1](#0-0) 

The controller picks the app/secret to verify against purely from the payload's `repository.owner.login` / `organization.login`: [2](#0-1) [3](#0-2) 

After the signature check passes, `create` blindly dispatches the raw parsed body to the handlers: [4](#0-3) 

Every handler resolves the target `Stack`(s) via `Handler#repository_name`, which reads `repository.full_name` — a field never checked against `repository.owner.login`/`organization.login` used for the signature: [5](#0-4) 

`PushHandler` uses this to locate stacks and immediately trigger a GitHub sync (which, for stacks with `continuous_deployment` enabled, can lead to an automatic deploy of new commits): [6](#0-5) 

**Equality that should hold but doesn't:**
`organization_verified_by_signature (repository.owner.login) == organization_owning_the_repository_that_is_written (repository.full_name)`

An attacker who legitimately controls/installed the Shipit GitHub App on **Organization A** (and therefore legitimately knows Organization A's `webhook_secret`, without any elevated Shipit privilege, session, or API token) can craft a webhook POST body where:
- `repository.owner.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")` is selected, and the HMAC computed with OrgA's own secret verifies successfully), while
- `repository.full_name` = `"OrgB/victim-repo"` (a stack belonging to a completely unrelated tenant, Organization B, hosted on the same shared Shipit instance).

The signature check passes (it only validates that the byte stream was signed with OrgA's secret — it says nothing about which repository the payload claims to be about). The handler then acts on `OrgB/victim-repo`'s `Stack`, invoking `stack.sync_github(expected_head_sha: params.after)`, which can trigger commit sync and, for continuously-deployed stacks, an unauthorized deploy pipeline kick-off — entirely outside the trust boundary of Organization B, whose repository/webhook secret the attacker never possessed.

### Impact Explanation
This breaks the tenant isolation boundary between separately configured GitHub organizations on the same Shipit install: knowledge of one org's own webhook secret (not privileged w.r.t. Shipit, not a `GITHUB_TOKEN`, not an `ApiClient` token) is sufficient to make Shipit process attacker-controlled webhook events "as if" they came from a different organization's repository. Because `PushHandler`/`sync_github` can drive continuous-deployment sync/deploy triggering for that other org's stacks, this can result in an **unauthorized deploy** trigger against a repository the attacker has no authorization over — matching the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is high in any multi-tenant deployment following Shipit's own documented multi-org configuration: any org onboarded onto the shared instance automatically becomes a potential source of forged cross-org events, since the webhook endpoint and dispatch logic never re-validates that the authenticating organization matches the repository named in the payload. No repository write access, GitHub App private key, or Shipit session is required — only the attacker's own legitimately-provisioned webhook secret for their own org.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController#create` before dispatch), verify that the resolved repository's owner matches the organization/app that successfully verified the signature (i.e., cross-check `repository.full_name`'s owner segment, or `repository.owner.login`, against the `repository_owner` used in `verify_signature`) before allowing any handler to act on a `Stack`. Reject the event (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret`, both hosting stacks (per `docs/setup.md` multi-org setup).
2. As an attacker with legitimate knowledge of `OrgA`'s `webhook_secret` (e.g., an admin of OrgA's own GitHub App installation), craft a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(OrgA's `webhook_secret`, raw body).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds (signed with OrgA's real secret).
6. `PushHandler#process` resolves `stacks` via `Handler#repository_name` = `"OrgB/victim-repo"`, finds the real `OrgB` stacks, and calls `stack.sync_github(expected_head_sha: params.after)` — acting on Organization B's stack despite the request only ever having been authenticated against Organization A's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
