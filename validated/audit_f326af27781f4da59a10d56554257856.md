### Title
Any address becoming a secondary-AA trigger can force revert of an entire primary AA invocation, griefing/freezing payouts intended for other honest recipients - ([File: aa_composer.js])

### Summary
The External Report describes an EIP-777 `tokensReceived` hook whose control lies with the token recipient: because the hook is invoked as part of a multi-step, all-or-nothing process (the legacy REP migration), a single malicious holder can revert the hook and thereby block the whole batch process from ever completing. In `ocore`, the AA (Autonomous Agent) engine has a structurally identical hook mechanism: when a primary AA's response unit pays out to one or more addresses, any output address that happens to be a registered AA is automatically re-invoked as a "secondary trigger" [1](#0-0) . If that secondary AA bounces, the entire primary invocation — including balances and state updates destined for every other, unrelated output address in the same response — is rolled back via `revert()` [2](#0-1) [3](#0-2) .

### Finding Description
`handleSecondaryTriggers` collects all output addresses of a primary AA's response unit that are themselves registered AA addresses and re-invokes each of them in series as "secondary triggers" [4](#0-3) . Crucially, the semantics of a single secondary bounce are: if *any* secondary AA in the chain bounces, the whole primary trigger's effects — its state-variable updates, balance changes and payouts to *all* the other addresses in the same response — are reverted and rolled back to `SAVEPOINT initial_balances`, then the primary trigger itself bounces:
```
function (err) {
    if (err) {
        if (bSecondary) return bounce(err);
        return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
    }
    ...
}
``` [5](#0-4) 

`revert()` unconditionally discards all responses accumulated so far and rolls the DB connection back to the initial-balances savepoint before bouncing the whole trigger:
```
function revert(err) {
    ...
    arrResponses.splice(0, arrResponses.length);
    ...
    conn.query("ROLLBACK TO SAVEPOINT initial_balances", function () {
        bounce(err);
    });
}
``` [3](#0-2) 

An AA address is fully deterministic and permissionless to register (it is simply the chash160 of its own JSON definition posted in a `definition` message), so any unprivileged unit poster can pre-deploy an AA that always calls `bounce(...)` whenever invoked as a secondary trigger — as demonstrated by `test/samples/just_a_bouncer.oscript` and the `'calling a remote function that fails'` / `'chain of AAs'` test cases that already exercise this exact mechanism [6](#0-5) [7](#0-6) .

Consequently, any legitimate "distribution"-style AA (payroll, staking rewards, marketplace payout, lottery, DAO treasury disbursement, etc.) that pays multiple recipients from a single trigger response — where at least one recipient address is attacker-influenced or attacker-choosable (e.g., supplied via `trigger.data`, looked up from a stored participant list, or simply guessed/pre-registered ahead of time) — can have its entire payout batch reverted by that single malicious recipient AA, denying the payout and state update to every other, innocent recipient in the same invocation, indefinitely and repeatably.

### Impact Explanation
This matches the report's core failure mode: a callback/hook whose execution is controlled by an untrusted counterpart is embedded in a multi-party, all-or-nothing operation, allowing that counterpart to permanently block completion of the operation for everyone else. In `ocore` this manifests as AA fund freezing/denial of payout: a single malicious AA-controlled address can force perpetual reversion of a victim AA's state changes and outgoing payments intended for other, honest addresses, each time the operation is attempted — the victim AA's business logic (e.g., recurring payouts, escrow release, voting settlement) can never advance past the point where it must pay the malicious address, exactly analogous to the `isMigratingFromLegacy` flag that could never be cleared in the Augur report.

### Likelihood Explanation
Deploying an AA is fully permissionless and requires no privileged role; it is reachable by any unprivileged AA author/trigger sender. Any protocol design that fans out payments to a set of addresses that includes attacker-influenceable input (a common and encouraged AA composability pattern — remote/secondary triggers — documented and tested in this repo) is exposed. The behavior is deterministic and repeatable on every invocation, so the griefing is reliable, not probabilistic.

### Recommendation
Reconsider making a single secondary-AA bounce revert the *entire* primary invocation. Options include: isolating each secondary trigger's balance/state effects so a bounced secondary trigger only reverts its own leg of the composition and consumes its own bounce fee (already partially modeled by per-branch bounce-fee handling), rather than rolling back the whole primary trigger's independent payouts/state changes to unrelated addresses; or requiring AA authors to explicitly opt into "all-or-nothing" semantics with a documented, isolated payout pattern for cases where partial failure must not affect unrelated recipients.

### Proof of Concept
1. Deploy AA `M` (malicious) whose only logic on any trigger is `bounce("always fail")` (as in `test/samples/just_a_bouncer.oscript`).
2. Deploy AA `V` (victim, e.g., "payroll") that, in a single response to one trigger, pays out to `[honestAddr1, honestAddr2, M]` and also updates its own state (e.g., decrementing a payroll counter or marking recipients as paid) in the same response unit.
3. Send a trigger unit to `V` that causes it to construct exactly this multi-output payment.
4. `handleSecondaryTriggers` invokes `M` as a secondary trigger; `M` bounces; per `aa_composer.js:1743-1750` this raises `err`, which — since `bSecondary` is false for `V` — calls `revert()` (`aa_composer.js:1759-1783`), rolling back *all* of `V`'s state changes and rescinding payouts to `honestAddr1` and `honestAddr2` as well, even though those addresses did nothing wrong.
5. Repeating the trigger against `V` reproduces the same outcome every time, permanently preventing `V` from ever completing a payout round that includes `M` as a recipient.
