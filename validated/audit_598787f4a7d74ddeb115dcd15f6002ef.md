### Title
Unbounded private-payment chain length allows a counterparty to force unbounded per-element DAG-traversal loops in `handlePrivatePaymentChains` / `parsePrivatePaymentChain` - ([File: wallet.js], [File: indivisible_asset.js])

### Summary
`handlePrivatePaymentChains` in `wallet.js` and `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` in `network.js` accept an attacker-controlled array of private-payment chains (`body.chains`), each chain itself an array of "private elements" representing a full transfer history of a private/indivisible-asset coin. Neither function enforces any upper bound on the number of elements in a chain (`arrPrivateElements.length`) before processing it.

### Finding Description
`handlePrivatePaymentChains` [1](#0-0)  only validates that each chain element is a non-empty, well-formed object — it never checks `arrPrivateElements.length` against any maximum. It hands each chain to `network.handleOnlinePrivatePayment` [2](#0-1) , which likewise performs no bound check, and ultimately to `privatePayment.validateAndSavePrivatePaymentChain` [3](#0-2) , which dispatches to `indivisible_asset.validateAndSavePrivatePaymentChain` -> `parsePrivatePaymentChain` for indivisible (fixed-denomination) private assets.

`parsePrivatePaymentChain` walks the entire supplied chain with `async.forEachOfSeries`, and for **every** element performs a full `validatePrivatePayment` (spend-proof hash computation, DB lookups, `validation.validatePayment`) [4](#0-3) [5](#0-4) . There is no cap analogous to `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, `MAX_AUTHORS_PER_UNIT`, or the `foreach`/array-literal size caps enforced elsewhere in the codebase (e.g. `constants.MAX_COMPLEXITY`/`MAX_OPS` in `definition.js`, the `count > 100` limit in `formula/validation.js` `readCount`, or the `arrItems.length > 100` check for array literals in `formula/evaluation.js`). A counterparty (or a device pretending to be one, since the payload arrives over the device-message/hub channel before any authentication of "is this really my counterparty's payment") can construct a chain with an arbitrarily large number of elements and send it as `private_payments`/`sign` messages.

This mirrors the reported Knox `_redeemMax` bug class: an unbounded loop, driven entirely by attacker-supplied array length, executed synchronously inside a critical code path (wallet message handling / private-asset validation), with each iteration performing non-trivial work (hash computation + DB round trips).

### Impact Explanation
Processing an oversized chain ties up the event loop and DB connection pool for the duration of a single `async.forEachOfSeries` walk over an attacker-chosen number of elements, each with several sequential DB queries. Because `handlePrivatePaymentChains` is invoked directly from `handleMessageFromHub` for `private_payments` and `sign` subjects (reachable by any correspondent/counterparty sending a private payment or countersigning request), a malicious counterparty can degrade or stall a victim wallet's ability to validate/receive legitimate private payments, and in constrained environments (mobile wallets, light clients) can exhaust memory/CPU processing the JSON-encoded chain (`JSON.stringify(arrPrivateElements)` is also persisted to `unhandled_private_payments`). This is a resource-exhaustion / griefing vector against the wallet's private-payment pipeline, distinct from pure network-DoS since it is a logic-layer unbounded loop triggered by payload content, not by connection flooding.

### Likelihood Explanation
Any device that is a registered correspondent (a normal precondition for exchanging private payments) can trigger this by sending a `private_payments` message with a single, arbitrarily long chain array — no special privilege, no need to broadcast a unit to the DAG, and no complexity/ops accounting comparable to what protects AA formulas and address definitions. The barrier to constructing such a payload is low (it need not even be a valid/spendable chain; the loop cost is paid before final proof failure at the deepest element for indivisible-asset payments, and even earlier failures still consume DB round-trips for each element visited).

### Recommendation
Enforce an explicit maximum chain length (e.g., a `MAX_PRIVATE_CHAIN_LENGTH` constant, comparable to other array-size caps already used in `ocore` such as `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`) at the earliest validation point — in `handlePrivatePaymentChains` (`wallet.js`) and in `handleOnlinePrivatePayment` (`network.js`) — before any per-element processing occurs. Reject chains exceeding the cap immediately with `ifError`, and consider rate-limiting/cost-accounting by correspondent device for repeated large private-payment submissions.

### Proof of Concept
1. As a registered correspondent device, construct `body.chains = [arrPrivateElements]` where `arrPrivateElements` is a synthetically large array (e.g. tens of thousands of well-formed-but-invalid link elements chained together via matching `unit`/`message_index`/`output_index` fields) for an indivisible private asset.
2. Send this as a `private_payments` device message to the victim wallet (`wallet.js` -> `handlePrivatePaymentChains`).
3. Observe that `parsePrivatePaymentChain` (`indivisible_asset.js`) walks the full array via `async.forEachOfSeries`, issuing a DB query and hash computation per element, with no early length-based rejection — consuming CPU/DB resources proportional to attacker-chosen array length before any error is returned.

// arrPrivateElements is ordered in reverse chronological order
function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
