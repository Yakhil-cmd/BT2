### Title
Webhook Signature Selected by Attacker-Controlled Organization Field Diverges from Repository Field Used to Locate the Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read straight out of the unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field of the same payload, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. Nothing enforces that the owner segment of `full_name` matches `repository.owner.login`. This breaks the intended binding "organization whose secret authenticated the request == organization whose repository is written to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
selecting `github_app = Shipit.github(organization: repository_owner)` where [2](#0-1) 
`repository_owner` comes straight from the (as-yet unverified) JSON body. Only after that org-specific secret is chosen is the signature checked against `request.raw_post`.

Meanwhile every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) locates the target repository/stack via `Handler#repository_name`/`#stacks`: [3](#0-2) 
which reads `payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login` — and resolves it via `Repository.from_github_repo_name`: [4](#0-3) 

Shipit explicitly supports multiple GitHub Apps/organizations configured with independent `webhook_secret`s, as shown in the multi-org fixture: [5](#0-4) 

Because the whole raw JSON body is HMAC-signed, an attacker cannot simply edit the body of a legitimately-signed webhook after the fact. But an attacker who *is* a legitimate GitHub App/organization admin/collaborator for Organization A (and therefore knows Organization A's `webhook_secret`, e.g. because they configured it or have push access that lets them trigger real webhooks and thus learn/replay a valid signature computed with it) can craft an arbitrary JSON payload where:
- `repository.owner.login` (and/or `organization.login`) = `"OrgA"` → causes `verify_signature` to fetch and check against OrgA's secret, which the attacker can satisfy;
- `repository.full_name` = `"OrgB/some-target-repo"` → causes the handler to resolve and act on a `Stack` that belongs to an entirely different organization, OrgB, that the attacker has no relationship with.

`verify_signature` never checks that `repository_owner` matches the owner segment of `repository.full_name`, and `Handler#repository_name`/`#stacks` never re-validates which organization actually authenticated the request. The equality the design relies on — "the organization whose secret authenticated this payload" == "the repository/stack the payload is used to act on" — is never enforced in code, only assumed.

### Impact Explanation
Depending on which handler is targeted, this allows a holder of a valid webhook secret for their own (unrelated) GitHub organization to forge state for a stack under a different organization:
- Via `StatusHandler`, an attacker can inject arbitrary commit statuses (`create_status_from_github!`) for a real commit SHA in a foreign repository/stack, which (depending on the stack's CI-required configuration) can make an otherwise non-deployable commit `deployable?` and eligible for continuous deployment, i.e. **unauthorized deploy**.
- Via `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha: ...)` to run against a foreign stack.
- Via `CheckSuiteHandler`/`MembershipHandler`, similar cross-organization state confusion into `Shipit.github_teams` authorization or check-run state is possible.

This matches the "High" bucket described by the rules (escalation into stack state / unauthorized deploy triggers) since it lets an org-A-authenticated request mutate org-B's stack state.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one organization that is configured in the same multi-tenant Shipit instance as the victim organization — this is the realistic deployment scenario the `secrets_double_github_app.yml` fixture documents (multiple orgs sharing one Shipit instance). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only a webhook secret for any one configured organization, which is the exact credential the design intends attackers to be scoped to only their own org's data.

### Recommendation
In `verify_signature`, after selecting `github_app` and validating the signature, additionally assert that the owner used to pick the signing secret equals the owner segment parsed from `repository.full_name` (or `organization.login`) before dispatching to handlers, and reject (422) on mismatch. Alternatively, have `Handler#repository_name`/`#stacks` cross-check the authenticated organization (passed down from the controller) against the resolved `Repository#owner` and refuse to act if they differ.

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker has legitimate knowledge of `OrgA`'s webhook secret (e.g., they are an admin of the GitHub App installed on OrgA).
3. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<real sha of a commit in OrgB/target-stack-repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-stack-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "OrgA"`, fetches OrgA's app/secret, and the signature check passes.
6. `StatusHandler#process` runs `Commit.where(sha: ...)` — which matches commits belonging to `OrgB`'s stack — and calls `create_status_from_github!`, forging a CI status on a commit the attacker has no authority over, potentially unlocking continuous deployment for `OrgB`'s stack.
