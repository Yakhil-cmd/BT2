### Title
Cross-organization webhook signature confusion allows an attacker with a valid webhook secret for one configured GitHub organization to forge events acting on any other organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* webhook secret to use for HMAC verification from an unauthenticated field of the incoming JSON body (`repository.owner.login` / `organization.login`), while the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, `PushHandler`, the `PullRequest::*Handler`s) select *which repository/stack to mutate* from a different, independently-controlled field of the same body (`repository.full_name`). No code ever checks that the organization whose secret validated the signature actually matches the owner encoded in `repository.full_name`.

### Finding Description
In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications" section), each GitHub organization onboarded to the same Shipit instance has its own `app_id`/`webhook_secret` pair, held in `Shipit::GitHubApp` instances keyed by organization name.

`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` just checks the HMAC of the raw body against whatever `webhook_secret` was configured for that one organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

Once the signature is accepted, `create` dispatches the raw JSON body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers determine the target repository/stack from `repository.full_name`, not from `repository.owner.login`:
```ruby

`Repository.from_github_repo_name` simply splits `owner/name` from that field, with no relation to the field used for signature verification:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [6](#0-5) 

Because `verify_webhook_signature` HMACs the *entire* raw body, and the attacker controls both `repository.owner.login` (used for secret selection) and `repository.full_name` (used for the actual mutation) inside that same body, an org admin who legitimately possesses the webhook secret for **their own** organization ("OrgA") can craft a payload where:
- `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")`'s secret is selected and the signature — computed with that secret over the crafted body — passes), and
- `repository.full_name = "OrgB/some-repo"` (an entirely different, unaffiliated organization's repository tracked by the same Shipit instance).

The equality that should hold is:
`organization authenticated by verify_signature == organization that owns the repository/stack mutated by the handler`

but this binding is never enforced — the two are read from independent, attacker-controlled JSON paths in the same unauthenticated payload, only the raw bytes as a whole are HMAC-verified, not any specific consistency between fields.

### Impact Explanation
This breaks organization isolation in a multi-org Shipit deployment: an entity that only administers/owns "OrgA" (and therefore legitimately knows OrgA's GitHub App webhook secret) can trigger `push` events (`GithubSyncJob` → `sync_github`) or other webhook-driven actions (PR opened/closed/labeled handlers driving `ReviewStackAdapter#create!`/`archive!`/`unarchive!`) against stacks belonging to a completely different organization ("OrgB") that it has no GitHub permissions on. This can force syncs, spurious review-stack provisioning/deprovisioning, or archive/unarchive actions on OrgB's stacks — a cross-repository/cross-tenant write triggered purely by controlling an unrelated organization's own webhook secret, matching the "cross-repository writes" High/Critical impact category.

### Likelihood Explanation
Requires: (1) the Shipit deployment to be configured for multiple GitHub organizations (an explicitly documented supported configuration in `docs/setup.md`), and (2) the attacker to be an administrator of at least one of those onboarded organizations (thus legitimately knowing that org's own webhook secret — not the target's). No access to the target org's credentials, no GitHub App private key, and no Shipit session/API token is required. This is a realistic multi-tenant setup and the crafted request is trivial to construct (standard HMAC-SHA1 over a JSON body with an attacker-chosen `repository.full_name`).

### Recommendation
After signature verification, enforce that the organization used to select the webhook secret is the same organization referenced by every repository-identifying field consumed downstream (`repository.full_name`, `organization.login`, etc.). Concretely, in `WebhooksController#verify_signature`/`create`, extract the owner from `repository.full_name` as well and reject the request (422) if it doesn't match `repository_owner`/the app used for verification. Alternatively, have `Handler#repository_name` and all handlers use the already-verified `repository_owner` rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Deploy Shipit with two organizations configured, e.g. `OrgA` (webhook secret `secretA`, known to the OrgA GitHub App admin) and `OrgB` (webhook secret unknown to the attacker), both with repositories tracked as Shipit stacks (per `docs/setup.md` "Using Multiple Github Applications").
2. As the administrator of `OrgA`'s GitHub App, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` using the OrgA secret the attacker legitimately possesses.
4. POST this to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies successfully against `secretA`. `PushHandler#stacks` then resolves via `Repository.from_github_repo_name("OrgB/target-repo")`, matching `OrgB`'s stack, and enqueues `GithubSyncJob` for it — even though the attacker never authenticated against or controls `OrgB`.
