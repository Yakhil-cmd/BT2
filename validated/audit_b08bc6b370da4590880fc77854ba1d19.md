### Title
Overflow in interest accrual permanently freezes an oversized market - (File: common/src/rates/simulate.rs)

### Summary
A large market at sustained high utilization can make `borrowed * borrow_index` exceed `i128::MAX` before the borrow-index cap engages, causing `GenericError::MathOverflow` during accrual. [1](#0-0)  Because every pool mutation synchronizes the market before applying its leg, the overflow blocks subsequent repayments, withdrawals, liquidations, recapitalization, and index updates. [2](#0-1) 

### Finding Description
`accrue_step` unconditionally computes the current unscaled debt and supply through `scaled_to_original`, which calls `Ray::mul` and panics when the fixed-point result does not fit in `i128`. [3](#0-2) [4](#0-3) [5](#0-4)  The borrow index is capped only after this computation in `update_borrow_index`, so the cap does not prevent multiplication of the stored scaled debt by the already-large index. [6](#0-5)  A regression test demonstrates that a one-billion-token, 18-decimal market at 98% utilization reaches the `MathOverflow` cliff before `MAX_BORROW_INDEX_RAY`, and that both withdrawal and repayment subsequently fail. [7](#0-6) 

### Impact Explanation
Once the product exceeds the representable `Ray` domain, the transaction reverts without advancing `last_timestamp`, so every later call repeats the same overflowing accrual. [8](#0-7)  `synced_market` runs this accrual before generic market legs, while `withdraw`, `repay`, and `update_indexes` all route through synchronized market loading. [2](#0-1) [9](#0-8)  This permanently freezes the affected market’s supplied liquidity and outstanding debt, including other users’ funds, absent a privileged parameter change or contract upgrade. [10](#0-9) 

### Likelihood Explanation
The trigger requires an unusually large market, admitted caps, and sustained high utilization over an extended period, so it is not practical on ordinary positions. [11](#0-10)  However, no privileged action is required after the market configuration admits the amounts: an unprivileged account can reach it through `Controller::supply`, `Controller::borrow`, and `Controller::update_indexes`, and anyone can submit the accrual call that crosses the cliff. [12](#0-11) [13](#0-12)  The impact is severe because a failed accrual blocks both exits and debt remediation rather than merely denying one optional operation. [14](#0-13) 

### Recommendation
Enforce scaled supply and debt limits derived from the maximum possible indexes so `scaled * MAX_*_INDEX / RAY` remains below `i128::MAX`, or perform accrual in a wider type and saturate utilization/reward accounting safely. [15](#0-14)  The check should run in `borrow`/`supply` admission paths rather than relying on `MAX_BORROW_INDEX_RAY`, because the overflow occurs before index capping. [16](#0-15)  A defense-in-depth fallback should also bound accrual to the last safely representable index and allow repay/withdraw paths to proceed instead of reverting unconditionally. [2](#0-1) 

### Proof of Concept
The existing harness reproduces the issue by creating an 18-decimal market with lifted caps, supplying one billion whole tokens, borrowing 98% of it, advancing ledger time year by year, and invoking controller `update_indexes` until the accrual returns `MathOverflow`. [17](#0-16)  The same test then proves market-wide freezing by showing both a one-unit supplier withdrawal and a borrower repayment fail with the same error while the stored index remains below `MAX_BORROW_INDEX_RAY`. [18](#0-17)

/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {

        return Ray::from(MAX_BORROW_INDEX_RAY);
    }

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
