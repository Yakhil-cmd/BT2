### Title
KLAY Permanently Locked in Bridge When Recipient Contract Cannot Receive Native Tokens — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` delivers bridged KLAY to the recipient using a low-level `call.value()`. If the recipient `_to` is a contract without a payable `receive`/`fallback` function, the call reverts, the entire transaction reverts (including nonce accounting), and the KLAY is permanently locked in the bridge with no recovery path.

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` performs the following sequence:

1. Validates and records the nonce (`_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`)
2. Emits `HandleValueTransfer`
3. Attempts delivery: `(bool ok, ) = _to.call.value(_value)("");`
4. Requires success: `require(ok, "handleKLAYTransfer: transfer failed");` [1](#0-0) 

Because step 4 is a hard `require`, any failure in step 3 reverts the entire transaction — including all nonce state written in step 1. This means `handleNoncesToBlockNums[_requestedNonce]` remains `0` for the stuck nonce.

The `_updateHandleNonce` loop advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`: [2](#0-1) 

Because the stuck nonce's entry is never written (every attempt reverts), `lowerHandleNonce` is permanently blocked at that nonce. Every subsequent operator call to `handleKLAYTransfer` for this nonce will also revert. The KLAY remains in the bridge contract indefinitely with no admin rescue function.

### Impact Explanation

Bridged KAIA is permanently locked in the parent-chain (or child-chain) bridge contract. The affected amount equals the `_value` of the stuck transfer. Because `lowerHandleNonce` never advances past the stuck nonce, the nonce window accounting is also corrupted for the lifetime of the bridge pair, though subsequent nonces (>= stuck nonce) can still be handled individually since `_lowerHandleNonceCheck` only enforces a lower bound. [3](#0-2) 

### Likelihood Explanation

A user bridges KLAY to a destination address that is a contract without a payable fallback — for example, a multisig, a DAO treasury, or any contract deployed before adding a `receive()` function. The bridge accepts the request on the source chain without validating whether the destination can receive native tokens. This is the exact scenario described in M-16 (staking from a contract that cannot receive ERC721), transposed to native-token delivery. The likelihood is low-to-medium but non-negligible given that contract addresses are common bridge destinations.

### Recommendation

Replace the hard-revert pattern with a pull-based or escrow pattern: if `_to.call.value(_value)("")` fails, record the unclaimed amount in a mapping (e.g., `pendingWithdrawals[_to] += _value`) and still consume the nonce. Provide a separate `claimKLAY()` function that lets the recipient pull their funds. Alternatively, allow bridge operators to specify a fallback recipient address when the primary delivery fails, similar to how the original Olas fix replaced `safeTransferFrom` with `transferFrom`.

### Proof of Concept

1. Alice deploys a contract `Vault` on the parent chain with no `receive()` or `payable fallback()`.
2. Alice calls `requestKLAYTransfer(Vault_address, 1 ether, "0x")` on the child-chain bridge, sending 1 KLAY + fee.
3. The child-chain bridge emits `RequestValueTransfer` with `_to = Vault_address`.
4. Bridge operators observe the event and call `handleKLAYTransfer(..., Vault_address, 1 ether, ...)` on the parent-chain bridge.
5. Inside `handleKLAYTransfer`, `Vault_address.call.value(1 ether)("")` returns `ok = false` (Vault has no payable fallback).
6. `require(ok, "handleKLAYTransfer: transfer failed")` reverts the transaction.
7. All nonce state (`handleNoncesToBlockNums[nonce]`, `lowerHandleNonce`) is rolled back.
8. Every subsequent operator attempt to handle this nonce also reverts.
9. The 1 KLAY is permanently locked in the parent-chain bridge. `lowerHandleNonce` is stuck at this nonce forever. [4](#0-3) [5](#0-4)
