### Title
Unprivileged PR label names inject arbitrary env-var keys (including `GIT_CONFIG_GLOBAL`) into git subprocesses via `ReviewStack#env` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name — uppercased — as an environment-variable **key** into the process env used by `Commands`, with no allowlist, and `LabelCapturingHandler#capture_labels` persists PR label names verbatim from the webhook body. This env eventually reaches `Command#unbundled_env`, which is passed to `PTY.spawn`, meaning an attacker who can label their own fork's PR (`allow_all` review stacks) controls an env-var key such as `GIT_CONFIG_GLOBAL` for every git/shell subprocess `StackCommands` runs, including `fetch_deployed_revision`.

### Finding Description
The broken binding: `ReviewStack#env.keys` should be a bounded set of application-defined variables, but in fact `ReviewStack#env.keys ⊇ pull_request.labels.map(&:upcase)`, an attacker-controlled set.

Code path:
- `app/models/shipit/review_stack.rb:84-93` — `env` does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })`, with no key allowlist/denylist.
- `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102` — `capture_labels` does `pull_request.update!(labels: params.pull_request.labels.map(&:name))`, storing whatever label names arrive in the webhook payload (only schema-validated as `String`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:29-31`), and this handler runs for any repository with an existing `ReviewStack` (`allow_all` included, `test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb:40-50` shows `allow_all` stacks are auto-created and don't require `require_permission!`/maintainer approval).
- `lib/shipit/stack_commands.rb:13-15` — `StackCommands#env` does `super.merge(@stack.env)`, pulling in `ReviewStack#env`.
- `lib/shipit/stack_commands.rb:51-59` — `fetch_deployed_revision` builds `Command.new(command_line, env:, chdir: dir)` for each `fetch` step, passing the attacker-influenced `env`.
- `lib/shipit/command.rb:34` and `:103-105` — `Command#initialize` stores `@env`, and `unbundled_env` does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, so any key present in `@env` (including a forged `GIT_CONFIG_GLOBAL`) overrides `BASE_ENV`.
- `lib/shipit/command.rb:92` — `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` executes the subprocess with this merged environment.

Exploit flow: an attacker opens a PR from a fork against a repository with `provisioning_behavior = allow_all` and review stacks enabled, then adds a label literally named `git_config_global` (any case) to their own PR. The `labeled` webhook is processed by `LabelCapturingHandler`, which persists the label on the stack's `PullRequest` with no allowlist check. On the next `FetchDeployedRevisionJob` (or any other `StackCommands`/`TaskCommands` operation for that review stack), `ReviewStack#env` injects `"GIT_CONFIG_GLOBAL" => "true"` into the env passed to every `git`/shell command for that stack, which is then forwarded to `PTY.spawn`.

Existing guards do not catch this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub for *some* repository (any repo owner can trigger this on their own repo), `drop_unhandled_event` and the `ExplicitParameters` schema only validate types (`String`), not value/content restrictions, and there is no `EnvironmentVariables#permit`-style allowlist applied to `ReviewStack#env` (unlike `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`, which do call `EnvironmentVariables.with(env).permit(...)` — but that filtering is not applied to `StackCommands#fetch_deployed_revision`, which uses the raw merged `env` directly).

Caveat on exploit completeness: the value assigned for every injected key is hardcoded to the string `"true"` (`review_stack.rb:91`), not an attacker-chosen path. So while the attacker can force the *key* `GIT_CONFIG_GLOBAL` to exist with value `"true"`, they cannot supply an arbitrary file path via this label mechanism alone. Turning this into full RCE would additionally require git to resolve `"true"` as a relative path against the command's `chdir` and the attacker separately placing a file literally named `true` containing a malicious git config (e.g., `core.fsmonitor` or a credential helper) inside their fork's checked-out tree at that `chdir`. That second precondition (git's exact relative-path resolution behavior for `GIT_CONFIG_GLOBAL`, and whether the fork's working tree content is present at the right `chdir` when `fetch_deployed_revision`'s configured `fetch` steps run) is not established by the code inspected here and would need runtime/behavioral verification against a specific git version — it is not confirmed by this codebase alone.

### Impact Explanation
Confirmed, in-scope impact: an unprivileged fork PR author can inject arbitrary **environment-variable keys** (not just `GIT_CONFIG_GLOBAL`) into every git/shell subprocess `Commands` runs for their own review stack — this includes keys like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `LD_PRELOAD`-adjacent overrides that the app might rely on being absent, or any variable a later `fetch`/`rollback`/deploy step's shell interprets specially. This is a violation of the stated invariant ("git subprocesses inherit no fork-controllable variable"). Full RCE via `GIT_CONFIG_GLOBAL` specifically requires the additional unverified precondition above; if that holds, it constitutes Critical RCE on the deploy host, scoped to the attacker's own repository/stack (the injected env only applies to that `ReviewStack`'s commands, so it is not directly cross-tenant, but the deploy host process compromise from RCE would be).

### Likelihood Explanation
Preconditions: `Shipit::Repository.review_stacks_enabled = true` and `provisioning_behavior = allow_all` (or `allow_with_label`/`prevent_with_label` combined with an already-provisioned/active review stack) — a documented, supported configuration. Attacker cost is trivial: open a PR from a fork, add a label. No secrets, tokens, or team membership required. The env-key injection itself is reliably repeatable and directly demonstrated by existing tests (`test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/task_commands_test.rb:6-16`, `test/lib/shipit/deploy_commands_test.rb:6-15`), which already prove label names become environment variable keys/values. The full RCE chain's likelihood depends on the unverified git relative-path behavior.

### Recommendation
Apply an explicit allowlist/denylist to `ReviewStack#env` before merging label-derived keys — e.g., reuse `EnvironmentVariables.with(env).permit(deploy_variables)`-style filtering, or reject/strip label names that collide with reserved/sensitive environment variable names (anything matching `GIT_*`, `LD_*`, `PATH`, `HOME`, `BUNDLE_*`, etc.), and validate/normalize label names before persisting them in `LabelCapturingHandler#capture_labels`.
