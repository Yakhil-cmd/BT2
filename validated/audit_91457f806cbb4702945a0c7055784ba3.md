### Title
Unvalidated `creator` account in `initialize_with_permission` permanently locks pool creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission::creator` is declared as a completely unconstrained `UncheckedAccount` and is stored verbatim as `pool_state.pool_creator`, exactly mirroring the `reclaimContract()` pattern where an attacker-supplied field (`order.maker`) is used to derive the fund destination without validating that it corresponds to a real, controllable account.

### Finding Description
In `initialize_with_permission`, the `creator` field has no `address`, `constraint`, signer, or non-default-key check at all: [1](#0-0) 

The raw, unchecked pubkey is passed straight into `pool_state.initialize(...)` and persisted as `pool_creator`: [2](#0-1) 

`pool_creator` is later relied upon as the sole source of truth for where accumulated creator fees are paid out. `collect_creator_fee_permissionless` constrains its `creator` account only via `address = pool_state.load()?.pool_creator` (no signer requirement, since the instruction is intentionally permissionless) and then creates an ATA for that address and transfers the entire accumulated `creator_fees_token_0`/`creator_fees_token_1` balance to it: [3](#0-2) [4](#0-3) 

Because `creator` at pool-initialization time is never checked to be a real, spendable account (e.g. not `Pubkey::default()`/the System Program ID, not a closed/frozen account, not required to sign), a payer can set it to a fictitious value. Every swap thereafter accrues real user-paid `creator_fees_token_0/1` inside the pool vaults (tracked in `PoolState`) that are earmarked for this bogus `pool_creator`. When `collect_creator_fee_permissionless` is eventually (and can be by anyone) invoked, the funds are irreversibly transferred to an associated token account owned by that unusable address, exactly as in `reclaimContract()` where `bullAssetAmount` is transferred to `bull == address(0)`.

### Impact Explanation
The accumulated creator-fee portion of every swap through the pool (a real economic value skimmed from user trades, tracked in `PoolState.creator_fees_token_0/1`) becomes permanently unrecoverable once collected to the bogus `creator` address — no code path exists to correct `pool_creator` after initialization. This is a permanent loss/freezing of protocol-derived funds, matching the High-severity "reclaimContract" bug class of transferring assets to an unvalidated/unreachable destination.

### Likelihood Explanation
Any payer who is permitted to call `initialize_with_permission` (gated by the `Permission` PDA check) can trigger this at pool-creation time simply by supplying an arbitrary pubkey for `creator` — no special privilege beyond that gate, no cross-account collusion, and no unusual runtime conditions are required. `collect_creator_fee_permissionless` requires no signature from `creator`, so anyone can then finalize the loss by invoking it once fees accrue.

### Recommendation
Add an explicit constraint requiring `creator` to be non-default (`require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())`) and/or require `creator` to sign the transaction (as done in the un-permissioned `initialize` instruction where `creator` is a `Signer`), so the pool cannot be initialized with an uncontrollable fee-recipient address.

### Proof of Concept
1. Obtain a valid `Permission` PDA for `payer` (via `create_permission_pda`).
2. Call `initialize_with_permission` with `creator = Pubkey::default()` (or any other pubkey with no known private key) — no constraint rejects this.
3. Perform swaps against the resulting pool; `creator_fees_token_0/1` accumulate in `PoolState` as usual.
4. Call `collect_creator_fee_permissionless`; it creates an ATA for the bogus `creator` and transfers all accrued creator fees there, unrecoverable forever. [5](#0-4)
