### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets one repo's CI status flip merge gating for another stack's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook to every `Commit` row in the entire database that matches the given `sha`, with no filtering by `repository.full_name` or stack, unlike every other webhook handler in this engine. Because `commits` are only unique per `(sha, stack_id)` [1](#0-0) , two different stacks can legitimately hold a `Commit` row for the identical sha (e.g. shared ancestor commits between a repository and any fork/mirror of it also tracked by Shipit), and a validly-signed status webhook delivered for one repo's commit will silently mutate the CI status of the other stack's `Commit`, which is exactly the value `MergeRequest#all_status_checks_passed?` reads to decide mergeability.

### Finding Description
The broken binding: **"stack that authenticated/authorized this status webhook" == "stack whose Commit record gets the status written"**. This holds for every other handler but not for `StatusHandler`.

- `PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler` all resolve the target stacks through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any record, e.g. `Handler#stacks` [2](#0-1)  and `CheckSuiteHandler#process` [3](#0-2) .
- `StatusHandler`, however, doesn't even declare `repository` as a required parameter, and resolves target records purely by sha, globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `verify_signature` in `WebhooksController` only checks that the payload is validly signed for *the organization named in the payload's own `repository.owner.login`* [5](#0-4) . It proves the request truly came from GitHub for the attacker's own (organization-covered) repo — it proves nothing about which `Commit`/stack the status should be written to.
- `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` / `any_status_checks_missing?` all build a `StatusChecker` (a `Status::Group` subclass) directly from `head.statuses_and_check_runs` [6](#0-5) , and `Status::Group` has no concept of which repo/stack produced the status — it simply reads whatever rows are attached to that `Commit` [7](#0-6) .
- `ProcessMergeRequestsJob` calls `merge_request.all_status_checks_passed?` and, if true, immediately calls `merge_request.merge!` [8](#0-7) .

Exploit flow: the attacker owns (or contributes to) any repository that is under a GitHub organization/App installation Shipit already trusts (satisfying `verify_signature`'s per-org check) — this can be their own fork if the GitHub App/webhook is installed org-wide, a very common configuration. They open a pull request against the victim's stack whose `head` sha is a real commit already shared between the two repositories' git history (e.g., an unmodified ancestor commit from before the fork diverged, or any commit both repos happen to contain) — no SHA-1 break is required, only two `Commit` rows for different `stack_id`s that share the same `sha`. The attacker then triggers (or already has, via their own CI) a GitHub `status` event of `state: success` for that sha on their own repository. GitHub delivers a validly-signed webhook to Shipit. `StatusHandler` writes a `success` status onto **every** `Commit` row matching that sha, including the victim stack's `Commit`, even though the payload's repository field never referred to the victim's repo. `ProcessMergeRequestsJob` then sees `all_status_checks_passed?` return true for the victim's pending `MergeRequest` and proceeds to merge it.

Existing guards do not prevent this: `verify_signature` authenticates the *sender org*, not the *target stack*; `ExplicitParameters` schema for `StatusHandler` never requires or checks `repository`; there is no `stacks`/`Repository.from_github_repo_name` scoping call anywhere in `StatusHandler`.

### Impact Explanation
A GitHub status event legitimately signed for repository A can inject a `success`/`failure` status onto a `Commit` belonging to a completely unrelated stack B, as long as both stacks contain a `Commit` row with the same sha. For merge queues this directly satisfies `all_status_checks_passed?`, letting `ProcessMergeRequestsJob` call `MergeRequest#merge!`, which invokes `stack.github_api.merge_pull_request(...)` — an unauthorized GitHub merge performed using Shipit's own GitHub credentials against the victim repository. This is "a payload for one repository mutating another's stack/commit" and directly causes "an unauthorized deploy/merge", matching the Critical impact bucket. It is repeatable against any stack pair that shares a commit sha (a normal occurrence for forked/mirrored repositories tracked by the same Shipit instance) and requires no privileged Shipit role, secrets, or GitHub App keys.

### Likelihood Explanation
Preconditions: (1) the attacker needs a repository reachable by Shipit's webhook infrastructure for signature purposes (e.g. their own fork under an org whose GitHub App/webhook Shipit already trusts, or any repo where they can otherwise get GitHub to emit a validly signed `status` event) — attackers who fork within the same monitored GitHub organization satisfy this trivially; (2) a shared commit sha must exist between attacker's repo and the victim's stack — realistic for forks, since forking preserves history and Shipit ingests all reachable commits into the `commits` table per stack. No secrets, tokens, or team membership are required, and the flaw is purely a missing scoping check in code, making it fully reproducible.

### Recommendation
Scope `StatusHandler#process` (and `create_status_from_github!`) to only the `Commit`s that belong to stacks tracking the repository named in the webhook payload, mirroring the pattern used by `PushHandler`/`PullRequest::*Handler`/`CheckSuiteHandler` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), and require `repository.full_name` in the `StatusHandler` params schema so unscoped/legacy payloads are rejected rather than silently applied.

```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status event for repo A cannot mutate a commit belonging to stack B" do
  victim_stack = shipit_stacks(:shipit)          # tracks victim/repo
  attacker_stack = Stack.create!(repository: shipit_repositories(:attacker_fork), ...)

  shared_sha = "cafefeedcafefeedcafefeedcafefeedcafefeed"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  merge_request = MergeRequest.create!(stack: victim_stack, head: victim_commit, merge_status: 'pending', ...)
  refute merge_request.all_status_checks_passed?

  # Webhook payload only references the attacker's repo
  payload = {
    "sha" => shared_sha, "state" => "success", "context" => "ci/attacker",
    "repository" => { "full_name" => shipit_repositories(:attacker_fork).full_name, "owner" => { "login" => "attacker-org" } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding check: victim's Commit should NOT have been mutated by attacker repo's webhook
  assert_equal 'unknown', victim_commit.reload.status.state   # currently FAILS: becomes 'success'

  ProcessMergeRequestsJob.new.perform(victim_stack)
  refute_predicate merge_request.reload, :merged?             # currently FAILS: proceeds toward merge
end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
```
