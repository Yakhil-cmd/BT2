### Title
Unbounded integer multiplication in asset denomination cap validation - ([File: validation.js])

### Summary
`validateAssetDefinition()` sums `count_coins * denomination` for each entry in an attacker-controlled `denominations` array to build `total_cap_from_denominations`, which is then compared against the attacker-supplied `cap` field. Neither `denomInfo.count_coins` nor (in the pre-`pemCurvesFixMci` regime) `denomInfo.denomination` has any upper bound before the multiplication, so the product can exceed `Number.MAX_SAFE_INTEGER` (2^53−1), silently losing precision in JavaScript's double-precision arithmetic — the same class of bug as the kernel's `arg->vec_len * sizeof(struct page_region)` overflow in `pagemap_scan_get_args()`, where an unvalidated multiplicand feeds a security-relevant size/sum computation.

### Finding Description
In `validateAssetDefinition()`: [1](#0-0) 
`denomInfo.denomination` is checked only with `isPositiveInteger()` (any positive integer, no upper bound) and is capped by `MAX_CAP` only conditionally, gated behind `objValidationState.last_ball_mci >= constants.pemCurvesFixMci`: [2](#0-1) 
`denomInfo.count_coins` is validated solely by `isPositiveInteger()` — with no upper bound at all, at any MCI: [3](#0-2) [4](#0-3) 
The product `denomInfo.count_coins * denomInfo.denomination` is accumulated into `total_cap_from_denominations` without any bound or overflow check, then compared for exact equality against the attacker-declared `payload.cap`: [5](#0-4) 
Since `cap` itself is bounded to `MAX_CAP`, an attacker can choose a `count_coins`/`denomination` pair whose true mathematical product vastly exceeds `MAX_CAP` (and even `Number.MAX_SAFE_INTEGER`), causing IEEE-754 rounding in the summation. This lets the declared `denominations` structure and the declared `cap` diverge from their true arithmetic relationship while still satisfying the equality check that is meant to enforce "cap must exactly equal the sum of count_coins × denomination across all denominations."

### Impact Explanation
This check exists specifically to enforce that a fixed-denomination asset's total issuable supply (`cap`) is consistent with its declared per-denomination coin counts. An overflow/precision-loss bypass of this consistency check undermines the guarantee that the declared `cap` accurately reflects the sum of mintable denominations for private, fixed-denomination assets — the same asset class ocore treats as fully backed and auto-destroying. A mismatch between the enforced `cap` and the actual denomination structure is a supply-accounting integrity issue for asset issuance, analogous in class (unauthenticated numeric field feeding an unguarded multiplication used for a security decision) to the CVE's overflow, though I was not able to fully trace forward into the downstream issuance/spend code within the available context to confirm a concrete double-spend or unbounded minting outcome beyond this cap-consistency check being bypassable.

### Likelihood Explanation
Any unprivileged unit poster can submit an `asset` definition message with a `denominations` array; this path is reached during ordinary unit validation with no special privileges required, matching the "unprivileged unit poster" reachability requirement. The lack of any bound on `count_coins`, and the conditional (upgrade-gated) bound on `denomination`, make triggering the overflow straightforward to attempt.

### Recommendation
- Add an explicit upper bound on `denomInfo.count_coins` (e.g., `<= constants.MAX_CAP`), matching the treatment already given to `cap` and (post-fix) `denomination`.
- Perform the `count_coins * denomination` multiplication using an overflow-safe check (e.g., verify the product does not exceed `constants.MAX_CAP` before accumulating, or use BigInt arithmetic) rather than relying on unchecked floating-point multiplication.
- Remove the MCI-gating so `denomination > MAX_CAP` is always rejected, not only after `pemCurvesFixMci`.

### Proof of Concept
Construct an `asset` definition unit (single-authored, `fixed_denominations: true`) with:
```
denominations: [
  { denomination: 100000000, count_coins: 100000000 }  // product = 1e16, exceeds Number.MAX_SAFE_INTEGER (~9.007e15) and MAX_CAP
],
cap: <crafted value that ends up equal to the rounded, precision-lost total_cap_from_denominations>
```
Because `count_coins` has no upper-bound check at all [4](#0-3) , and the equality check at [6](#0-5)  relies on the raw floating-point sum, an attacker can find `count_coins`/`denomination`/`cap` combinations where the declared cap passes validation despite not being the true arithmetic sum of the denomination's coin count and value.
