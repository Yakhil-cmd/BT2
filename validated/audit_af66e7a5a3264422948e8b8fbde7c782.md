### Title
Webhook organization used for signature verification is never bound to the repository acted upon, allowing cross-organization webhook forgery in multi-tenant Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the request against using `repository.owner.login` (or `organization.login`) from the JSON body, while every event `Handler` resolves the target `Repository`/`Stack` using a completely different field, `repository.full_name`. Because these two fields are never checked for consistency, a payload can be signed with one organization's secret while acting on a repository belonging to a different organization.

### Finding Description
`verify_signature` picks the `GitHubApp` instance (and therefore the `webhook_secret` used for HMAC verification) via: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository','owner','login')` (falling back to `organization.login`). This is the *only* field authenticated by the signature check — the signature proves nothing more than "this body was produced/known by whoever holds the `webhook_secret` configured for that owner".

Once verification passes, `create` dispatches the raw, attacker-controlled JSON body to the registered handlers: [3](#0-2) 

Every handler resolves the affected `Repository`/`Stack` from a *different* field of the same body — `repository.full_name` — via the shared base class: [4](#0-3) 

For example, `PushHandler` uses that repository lookup to enqueue a sync against an attacker-chosen `after` SHA: [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are independent JSON keys that are never cross-checked, in a multi-organization deployment (`Shipit.github(organization:)`, as documented for the "Using Multiple Github Applications" setup) an attacker who legitimately controls a GitHub App/webhook secret for **their own** organization ("Org A") can send a POST directly to the public `/webhooks` endpoint with:
- `repository.owner.login = "OrgA"` and a valid `X-Hub-Signature` computed with Org A's `webhook_secret` (which the attacker owns/knows, since they configured Org A's GitHub App themselves), and
- `repository.full_name = "OrgB/victim-repo"` pointing at a repository/stack belonging to a completely different, unrelated organization ("Org B") that the attacker has no access to.

`verify_signature` succeeds (it only checked Org A's secret against the raw body, which the attacker legitimately produced), but `PushHandler` (or `StatusHandler`, `MembershipHandler`, etc.) then acts on Org B's stack, e.g. queuing `GithubSyncJob` to move Org B's stack pointer to an arbitrary, attacker-chosen `after` SHA, or synthesizing a fabricated commit `status`. This breaks the trust binding: *organization that authenticated the payload* ≠ *repository the payload's handlers write to*.

Before the attacker's request: Org B's stack state (deployed SHA, statuses) can only be changed by webhooks legitimately signed with Org B's own `webhook_secret`, or through the authenticated web UI/API. After the attacker's request: Org A's webhook credential is sufficient to mutate Org B's stack state, because the signature-check field and the repository-resolution field are decoupled.

### Impact Explanation
The `push` and `status` handlers can be triggered against a victim organization's stack using credentials the attacker legitimately controls for an unrelated org. If the victim stack has continuous deployment configured, forcing a `GithubSyncJob` to run with an attacker-chosen `after` SHA (via `PushHandler`) can move the "last deployed"/head pointer of the stack, and forged `status` events (`StatusHandler`) can fabricate CI status ("success") on arbitrary commits, which can unblock automatic/continuous deploys or merges gated on CI. This can lead to an unauthorized deploy of attacker-influenced state on a repository the attacker does not otherwise have write access to — satisfying the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
This requires a Shipit instance configured for multiple GitHub organizations (explicitly supported and documented), and requires the attacker to control (or know the `webhook_secret` of) at least one of the configured organizations — a scenario the docs explicitly anticipate ("Using Multiple Github Applications"). No GitHub-side webhook delivery is actually required since `/webhooks` is a public unauthenticated HTTP endpoint that accepts any signed body; the attacker can compute and send the forged request directly. This is a realistic misconfiguration/multi-tenancy scenario rather than a purely theoretical one.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository/stack resolution. Concretely, `Handler#repository_name` (and any handler resolving repositories) should verify that the resolved repository's owner matches the `repository.owner.login`/`organization.login` that was used in `verify_signature`, or `verify_signature` should independently re-derive the organization from `repository.full_name`'s owner segment and reject if it disagrees with `repository.owner.login`/`organization.login`. This closes the same class of gap as the Aave `priceOracleSentinel` check the report analogizes to: a value that gates the operation's authorization must be the same value the operation actually acts upon.

### Proof of Concept
1. Deploy Shipit configured with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature using `OrgA`'s secret.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `OrgB`'s stack — a mutation on `OrgB`'s stack driven entirely by `OrgA`'s credential.
