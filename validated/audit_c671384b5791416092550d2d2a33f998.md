### Title
Unbound bootstrap pairing codes let any secret holder gain full trusted-correspondent privileges regardless of the intended context - ([File: device.js])

### Summary
`handlePairingMessage()` in `device.js` grants a peer full, unrestricted "confirmed correspondent" status as soon as it presents any valid `pairing_secret` (single-use or the account-wide permanent one), without binding the secret to the role/scope/context under which it was originally issued and shared.

### Finding Description
Pairing codes in ocore are generated in two ways: a one-time secret via `startWaitingForPairing()` and a long-lived, reusable "permanent" secret via `getOrGeneratePermanentPairingInfo()` [1](#0-0) . The permanent secret is embedded verbatim into unrelated, narrowly-scoped protocol flows — e.g. it is attached as `my_pairing_code` inside arbiter-contract offers, contract responses, dispute filings, and appeals sent to arbiter/arbstore endpoints and contract counterparties [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

When any party (the intended recipient, an arbstore operator who received the JSON payload, or anyone the secret otherwise leaked to) later replays that same code in a `pairing` message, `handlePairingMessage()` performs only generic, secret-existence validation:

```
"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>...
``` [6](#0-5) 

There is no field in the `pairing_secrets` table recording *why* the code was issued, to *whom*, or for what *scope* of interaction — only `pairing_secret`, `is_permanent`, and `expiry_date` [7](#0-6) . Consequently, once the secret check passes, the presenter is unconditionally upgraded to a fully trusted device:

```
db.query("INSERT ... INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", ...);
db.query("UPDATE correspondent_devices SET is_confirmed=1, ... WHERE device_address=? AND is_confirmed=0", ...);
db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", ...);
``` [8](#0-7) 

This mirrors the GHSA-gg9v-mgcp-v6m7 root cause exactly: a bootstrap setup code (pairing secret) is not bound to the intended device role/scope (e.g. "arbiter-contract counterparty only"), so first use of a leaked/repurposed code grants the presenter the *full* correspondent role — identical privileges to a deliberately, individually paired wallet cosigner.

Because `correspondent_devices.is_confirmed=1` is the sole gate that `sendMessageToDevice()` checks before relaying protocol messages [9](#0-8) , a device that abused an out-of-scope pairing code is thereafter treated on par with any legitimately paired device for the full breadth of device-message handlers in `wallet.js`, including `create_new_wallet`, `create_new_shared_address`, `new_wallet_address`, and `sign` [10](#0-9) [11](#0-10) .

### Impact Explanation
Once trust is escalated, the attacker can drive `create_new_wallet` / `create_new_shared_address` flows toward the victim, and — because `determineIfIncludesMeAndRewriteDeviceAddress()` and `handleNewSharedAddress()` accept any signer/definition set that includes one of the victim's own addresses without verifying the counterparty was ever intended as a cosigner for that specific address family [12](#0-11)  — the victim's wallet can be induced into recording a shared/multisig address definition it did not knowingly negotiate. Combined with the `sign` handler's `ifRemote` proxy path, which only checks that the requester is *some* listed cosigner of the address (not that it holds the originally intended, scoped role) [13](#0-12) , an out-of-scope pairing can be leveraged toward unauthorized signing-request flows and fund-control confusion for addresses the attacker was never supposed to co-own. This is a real device-role privilege-escalation bug (CWE-269/648 analog) with reachable financial impact through the wallet/multisig protocol, though final exploitation still requires social engineering the victim's confirmation dialogs in some paths (e.g., `create_new_shared_address` still emits a UI confirmation event), which somewhat limits severity relative to the original CVSS 9.8 rating.

### Likelihood Explanation
Pairing secrets — especially the account-wide "permanent" one — are routinely transmitted in plaintext-adjacent contexts (arbiter contract JSON to `httpRequest` endpoints, contract offers/responses/disputes/appeals to counterparties) [4](#0-3) , all logged/relayed through third parties (arbstores) that were never meant to become fully-trusted paired devices. Any party who intercepts or is handed this reused secret can trigger `handlePairingMessage()` at any time before `expiry_date`, and the permanent variant never expires in practice (`'2038-01-01'`) [14](#0-13) . No user interaction beyond sending the pairing message is required to obtain the correspondent-trust upgrade itself.

### Recommendation
Bind pairing/bootstrap codes to the specific context/role they are issued for: store a scope/purpose (e.g. "arbiter-contract:<hash>") alongside `pairing_secret` in the `pairing_secrets` table, and only elevate a presenting device to the matching restricted role (not full unconditional `is_confirmed=1`/`is_blackhole=0` correspondent trust) unless the code was explicitly generated for open-ended pairing. Additionally, require that shared-address/wallet-creation and signing-proxy flows independently re-verify that a correspondent was authorized for that specific address/wallet by the user, rather than relying solely on `correspondent_devices.is_confirmed`.

### Proof of Concept
1. Alice creates an arbiter contract with Bob; her client calls `device.getOrGeneratePermanentPairingInfo()` and embeds `my_pairing_code = pubkey@hub#pairing_secret` into the contract payload sent to the arbstore and to Bob (`arbiter_contract.js` `createAndSend`/`respond`/`openDispute`/`appeal`).
2. The arbstore operator (or anyone who observes the JSON payload sent to `/api/dispute/new` or `/api/appeal/new`) extracts `my_pairing_code`.
3. That party sends a `pairing` message to Alice's hub using the extracted `pairing_secret`, invoking `handlePairingMessage()`.
4. `handlePairingMessage()` finds the secret in `pairing_secrets` (any purpose) and unconditionally sets `is_confirmed=1`, `is_blackhole=0` for the new correspondent — granting it the same trust as a deliberately paired wallet cosigner, with no scoping to "arbiter dispute participant only."
5. The now-trusted correspondent sends `create_new_wallet` / `create_new_shared_address` / `sign` messages to Alice's device, which are processed by the full wallet protocol handlers in `wallet.js`, despite Alice never intending this party to hold any wallet-cosigner role.

		});
