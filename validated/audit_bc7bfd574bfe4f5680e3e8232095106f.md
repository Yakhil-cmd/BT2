## Analysis Summary

I found a valid analog in `Shipit::WebhooksController`. The vulnerability class from the report ("an action is trusted/executed based on one piece of context while a different, unverified piece of context determines what gets acted upon") maps directly onto a split between the **organization whose secret authenticated the webhook request** and **the repository/stack that the payload actually causes writes to**.

### Title
Webhook signature verification is keyed on `repository.owner.login` while write-side handlers act on the unrelated `repository.full_name` field, allowing a foreign GitHub organization to forge writes against another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using only `repository.owner.login` (or `organization.login`) from the JSON body. Once the signature check passes, the actual mutation performed by the event handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) is resolved from `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name` / `Shipit::Repository.from_github_repo_name`). Nothing in the code enforces that the owner used to select the signing secret is the same owner encoded in `full_name`. In a multi-organization Shipit deployment (explicitly supported and documented under "Using Multiple GitHub Applications"), this breaks the equality: `organization_that_authenticated == organization_that_owns_written_repository`.

### Finding Description
In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

Whatever value is in `repository.owner.login` selects a `Shipit.github(organization:)` config entry, which supplies the `webhook_secret` used to HMAC-verify the raw body (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`). Since HMAC verification only proves "this body was signed by *some* configured org's secret," and an attacker who administers Org A's own GitHub App installation legitimately possesses Org A's `webhook_secret`, that attacker can compute a valid signature over **any body they craft**, including one whose `repository.owner.login` is `"OrgA"` (so the signature verifies) but whose `repository.full_name` is `"OrgB/victim-repo"`.

Every mutating handler resolves the target purely from `full_name`, independent of the owner used for authentication:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses exactly that `stacks` scope to enqueue a sync against arbitrary branches:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`Repository.from_github_repo_name` does a plain owner/name lookup with no cross-check against which secret authenticated the request:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

The multi-organization configuration model is explicitly supported and documented (`docs/setup.md`, "Using Multiple Github Applications"), and is exercised in tests (`test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`), confirming this is an intended, in-scope deployment topology rather than a misuse of the engine. [6](#0-5) 

### Impact Explanation
An attacker who owns/administers **any one** GitHub organization that has its own Shipit GitHub App installed on a shared multi-org Shipit instance can forge webhook payloads that:
- Trigger `GithubSyncJob` for stacks belonging to a completely different organization (`PushHandler`), forcing spec re-caching and commit ingestion using a spoofed `expected_head_sha`.
- Inject fake commit statuses (`StatusHandler`) for another org's commits, which can flip CI gating used to authorize deploys.
- Inject fake `check_suite` results (`CheckSuiteHandler`) similarly affecting deploy gating.
- Manipulate PR-driven review-stack lifecycle (`PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) for another org's repository, archiving/unarchiving or otherwise mutating review stacks that do not belong to the attacker.

Because these operations feed directly into what commits get considered "deployable" and what stacks get automatically synced/provisioned, this can enable an **unauthorized deploy-relevant state change or cross-repository write** against a stack the attacker has no legitimate access to — matching the required Critical impact bucket ("cross-repository writes … or an unauthorized deploy").

### Likelihood Explanation
The precondition (multiple GitHub orgs configured on one Shipit instance, each with its own App/secret) is a first-class, documented configuration, not a misconfiguration. Any attacker who is themselves an admin of one of the configured orgs — an "unprivileged" actor with respect to the victim org — can exploit this with a single crafted, self-signed HTTP POST to `/webhooks`; no stolen secrets, sessions, or GitHub App private keys are required, only the attacker's own legitimately-held webhook secret for their own org.

### Recommendation
Bind the authenticated organization to the resource being mutated: after `verify_signature` resolves `repository_owner` and validates the HMAC, re-derive the repository/organization from the same trusted field and reject the event if `repository.full_name`'s owner segment does not case-insensitively match `repository_owner` (or `organization.login`) used to select the signing key. Alternatively, look up `Repository.from_github_repo_name` scoped additionally by the verified organization, and drop/422 the event on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgVictim`, each with its own GitHub App and webhook secret (per `docs/setup.md`, "Using Multiple Github Applications").
2. As the (legitimate) administrator of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret`.
3. Craft a `push` event JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgVictim/target-repo"`
   - `ref = "refs/heads/<victim-branch>"`, `after = "<attacker-chosen-sha>"`
4. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature using `OrgA`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgVictim/target-repo")` and enqueues `GithubSyncJob` against `OrgVictim`'s stack with the attacker-supplied `expected_head_sha`, despite the attacker having no relationship whatsoever to `OrgVictim`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
