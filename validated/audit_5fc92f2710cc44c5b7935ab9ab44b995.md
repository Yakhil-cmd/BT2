### Title
`Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing a stack-scoped `read:stack` token to read any stack's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes stack lookup through the `stacks` helper, which restricts results to `current_api_client.stack_id` when the token is scoped to a specific stack. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing that restriction entirely, so the `require_permission :read, :stack` check (which only verifies the string `'read:stack'` is present in the token's permission list) grants access to any stack, not just the one the token was issued for.

### Finding Description
The claimed binding is: `check_permissions!(:read, :stack) == true` should imply `stack.id ∈ authorized_stacks(current_api_client)`, i.e. `stack.id == current_api_client.stack_id` (when the client is stack-scoped).

Tracing the code:
- `Api::BaseController#require_permission!` just calls `current_api_client.check_permissions!(operation, scope)` [1](#0-0) , and `ApiClient#check_permissions!` only checks `permissions.include?("#{operation}:#{scope}")` — a flat string membership check with no reference to any stack id at all [2](#0-1) .
- The actual tenant isolation is supposed to happen via `BaseController#stacks`/`#stack`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and only calls `.from_param!` on that restricted relation [3](#0-2) . `StacksController` correctly reuses this scoped `stacks.from_param!` [4](#0-3) .
- `Api::CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the class, ignoring `current_api_client.stack_id` entirely [5](#0-4) .

Order of evaluation: `before_action :authenticate_api_client` runs first, then the `require_permission :read, :stack` before_action runs `require_permission!(:read, :stack)`, which only checks the permission string against the token's flat `permissions` array — it does not reference `params[:stack_id]` or `stack` at all. Only afterward, inside `#show`, is `stack` resolved via the unscoped `Stack.from_param!` [6](#0-5) . So the permission gate passes purely based on the token holding `read:stack`, independent of which stack is ultimately loaded, and the loading itself is unscoped in this controller.

Exploit: an attacker holding a legitimately issued API token scoped to Stack A (`current_api_client.stack_id == A.id`, `permissions` includes `read:stack`) sends `GET /api/stacks/:B_stack_id/cc.xml` (ccmenu route) with `params[:stack_id]` set to Stack B's identifier. `require_permission!(:read, :stack)` succeeds (token has `read:stack`), then `stack` resolves to Stack B unchecked, and the client receives Stack B's deploy/rollback status in the CCMenu XML response.

None of the listed guards prevent this: `verify_signature`/webhook checks are irrelevant (this is a token-authenticated API endpoint), the `ExplicitParameters` schema doesn't declare/validate `stack_id` against the client's scope, and `require_permission!` as shown does not consult `stack` at all — it is exactly the flat, stack-identity-blind check the question describes, combined with the controller's unique bypass of the `stacks` scoping helper that every sibling controller uses.

### Impact Explanation
A stack-scoped API token issued for one repository/stack can read CCMenu status (latest deploy/rollback state, running status) of any other stack in the installation, including stacks belonging to unrelated repositories/tenants. This is an unauthenticated-for-that-resource read of stack state across a tenant boundary — matching the High severity category ("escalation into ... unauthenticated read of stack state, task streams or deploy output"). It is fully repeatable against any stack id by varying `params[:stack_id]`.

### Likelihood Explanation
Requires possession of any valid `ApiClient` token scoped to a specific stack with the `read:stack` permission (a routine, low-privilege token type intentionally issued to a single stack/repo integration). No GitHub secrets, admin access, or webhook secrets are needed — only a legitimately issued, narrowly-scoped API token, which is the normal grant given to CI/CD integrations. The attack is a single unauthenticated (relative to Stack B) GET request with an attacker-chosen `stack_id`, trivially repeatable.

### Recommendation
Remove `Api::CCMenuController#stack`'s custom override and use the inherited `stacks.from_param!(params[:stack_id])` (or otherwise filter through `current_api_client.stack_id`) so that stack resolution respects the same scoping as `BaseController`/`StacksController`.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` (different repositories).
2. Create an `ApiClient` with `stack_id: stack_a.id` and `permissions: ['read:stack']`.
3. Assert `client.check_permissions!(:read, :stack)` returns `true` (demonstrating the permission string is stack-identity-blind).
4. Perform `get shipit.api_stack_cc_url(stack_a, stack_b)`-style request: `get "/#{stack_b.repository.owner}/#{stack_b.repository.name}/#{stack_b.environment}/cc.xml", params: { token: client.authentication_token }`.
5. Assert response is `200 OK` and the returned XML corresponds to `stack_b` (e.g., contains `stack_b`'s latest deploy id / environment), proving cross-tenant read despite the token being scoped to `stack_a`.
6. Contrast with `StacksController#show` under the same client/stack_b combination, asserting it raises `ApiClient::InsufficientPermission`/404 due to `stacks.from_param!` scoping, showing the divergence is specific to `CCMenuController`.
