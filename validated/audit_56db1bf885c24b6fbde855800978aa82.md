### Title
Cross-organization `Team` row hijack via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `github_id`, without constraining the lookup to the organization named in the webhook payload. Any attacker who can get a `membership` webhook signature to verify for an organization they control can forge a `team.id` that collides with a pre-existing, privileged `Team` row belonging to a different organization, and thereby write `Membership` records into that foreign team.

### Finding Description
The intended binding is: `team.organization (persisted at row creation) == params.organization.login (verified sender of this event)`. This equality is never checked at lookup time.

`app/models/shipit/webhooks/handlers/membership_handler.rb`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 

`find_or_create_by!(github_id: ...)` performs `WHERE github_id = X`, and the `organization:` assignment in the block only runs on the creation branch — it is silently ignored on the find branch. Since `Team.github_id` is not unique per organization (schema only has a unique index on `[organization, slug]`, not on `github_id`) [2](#0-1) , any organization can send a `team.id` numerically colliding with another org's already-persisted `Team.github_id`.

Path from attacker input: `WebhooksController#create` dispatches raw JSON `params` to `MembershipHandler.call` after `verify_signature`, which authenticates only that the request was signed by *some* organization's webhook secret (`Shipit.github(organization: repository_owner)`, keyed off `params.dig('organization','login')` for membership events) [3](#0-2) [4](#0-3) . Signature verification is per-organization but says nothing about which `Team` rows that organization is entitled to touch — `GitHubApp#verify_webhook_signature` only proves "this org's configured secret signed this payload" [5](#0-4) . Once verified, `MembershipHandler#process` calls `find_or_create_team!` then mutates membership state (`team.add_member(member)` / `team.members.delete(member)`) on whatever `Team` row was returned [6](#0-5) .

Attacker exploit: control (or self-register) an organization `evil-org` with Shipit installed/configured (satisfying signature verification for that org only), then POST:
```json
{
  "action": "added",
  "team": { "id": <github_id of victim Team row>, "name": "x", "slug": "x", "url": "https://example.com" },
  "organization": { "login": "evil-org" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "evil-org" } }
}
```
signed with `evil-org`'s webhook secret. `find_or_create_team!` returns the pre-existing victim `Team` (e.g., `shipit_teams(:shopify_developers)`), and `add_member` inserts a `Membership` row binding the attacker's GitHub login to that privileged team — with no cross-check that `evil-org == team.organization`.

No existing guard prevents this: `verify_signature` only checks per-org HMAC, not per-team ownership; `ExplicitParameters` (`params do ... end` block) only validates payload shape/types, not organizational binding [7](#0-6) ; `drop_unhandled_event` is irrelevant since `membership` is a handled event.

### Impact Explanation
This is a High-severity finding: escalation into `Shipit.github_teams` authorization state. `Shipit.github_teams` builds its team-membership trust set via `Team.find_or_create_by_handle`, and `Team#members` (populated through `Membership`) is used elsewhere to determine which GitHub users are trusted for privileged operations gated on team membership [8](#0-7) [9](#0-8) . An attacker who controls any org onboarded to this Shipit instance can inject arbitrary GitHub users into a completely different, privileged organization's `Team`, without needing credentials, sessions, or maintainer status for the victim org. This is repeatable per known/guessable `github_id` values and requires no interaction from the victim organization.

### Likelihood Explanation
Preconditions: (1) a privileged `Team` row already persisted with a known `github_id` (GitHub team IDs are sequential/enumerable, and may be discoverable via public GitHub API for known org/team slugs); (2) the attacker's own organization is configured/onboarded in Shipit (or has no `webhook_secret` configured, in which case `verify_webhook_signature` returns `true` unconditionally — see `return true unless webhook_secret` [10](#0-9) ), giving the attacker a straightforward valid-signature path. Attacker cost is a single crafted HTTP POST; the action is fully repeatable and does not require any GitHub-side privileges beyond controlling their own org's Shipit webhook.

### Recommendation
Scope the lookup by both `github_id` and `organization`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
  end
end
```
Additionally consider adding a uniqueness validation/index on `github_id` scoped to `organization`, or fully qualifying lookups by `(organization, slug)` as `find_or_create_by_handle` already does.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` or equivalent):
```ruby
test "cross-organization team collision" do
  victim_team = Team.create!(github_id: 999, organization: "real-org", slug: "admins", name: "Admins", api_url: "https://example.com")

  payload = {
    "action" => "added",
    "team" => { "id" => 999, "name" => "Fake", "slug" => "fake", "url" => "https://example.com" },
    "organization" => { "login" => "evil-org" },
    "member" => { "login" => "attacker" }
  }

  assert_no_difference -> { Team.count } do
    assert_difference -> { Membership.count }, 1 do
      Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
    end
  end

  victim_team.reload
  assert_equal "real-org", victim_team.organization  # binding claimed intact...
  assert_includes victim_team.members.map(&:login), "attacker"  # ...but membership was written by evil-org's event
end
```
Assert before: `victim_team.organization == "real-org"` and `params.organization.login == "evil-org"` (mismatch). Assert after: the same `victim_team` row (not a new one) received the `attacker` membership, proving the organizational binding was never enforced on lookup.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
