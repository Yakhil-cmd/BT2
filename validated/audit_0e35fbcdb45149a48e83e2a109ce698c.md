### Title
Attacker-authored hookify regex rule causes ReDoS timeout that silently degrades a `block` rule into allow - ([File: plugins/hookify/core/rule_engine.py])

### Summary
A `.claude/hookify.*.local.md` rule's `pattern` field is compiled with `re.compile` and executed with `regex.search(text)` against fully attacker/agent-controlled fields (`command`, `new_string`, etc.) with no timeout, length cap, or catastrophic-backtracking protection. If the pattern is crafted for exponential backtracking (e.g. `(a+)+$`) and matched against adversarial input, `_regex_match` hangs, the whole `pretooluse.py` process exceeds its 10s hook timeout, and Claude Code's hook subprocess-timeout handling proceeds without ever receiving the `permissionDecision: deny` JSON response — meaning a `block` rule that should have fired never gets to run to completion.

### Finding Description
`compile_regex` in [1](#0-0)  compiles the rule's `pattern` string directly with no complexity/length limits, and `_regex_match` invokes `regex.search(text)` synchronously with no timeout guard: [2](#0-1) . The call path is `pretooluse.main` → `RuleEngine.evaluate_rules` → `_rule_matches` → `_check_condition` → `_regex_match` → `compile_regex(pattern).search(text)`, as shown in [3](#0-2)  and [4](#0-3) . The `pattern`/`command`/`new_string` values are both sourced entirely from repo content: rules are loaded from any `.claude/hookify.*.local.md` file discovered via `glob.glob` in `load_rules`, and the frontmatter `pattern` field is taken verbatim [5](#0-4) [6](#0-5) , while `command`/`new_string` are the live tool-call arguments passed into the hook by Claude Code (attacker-influenced when the agent is operating on repo-supplied instructions/content).

The hook's `hooks.json` sets a `"timeout": 10` for the `pretooluse.py` command [7](#0-6) . `pretooluse.py`'s `main()` wraps evaluation in `try/except/finally: sys.exit(0)` [8](#0-7) , but that `finally` only executes if the Python process itself resumes control flow — it does not run if the OS-level hook harness kills/times out the subprocess externally after 10 seconds while it's stuck inside `regex.search()`. In that scenario no JSON is emitted on stdout at all. This finding assumes (and cannot fully verify from this repo alone, since Claude Code's own hook-runner source is not present here) that Claude Code's documented behavior for a hook that fails to respond in time is to treat it as non-blocking/allow, which is the standard "hook error/timeout ⇒ do not block the agent" design also explicitly encoded in this hook's own error path (`except Exception: ... allow the operation`). Under that behavior, a catastrophic-backtracking `pattern` in a `block` rule is a reliable way to guarantee the rule never gets to return its `deny` decision — silently converting a designed "deny" into an effective "allow" for that tool call, defeating the "deny means deny" invariant.

### Impact Explanation
This is a guard/hook bypass: an attacker who can drop or influence a `.claude/hookify.*.local.md` rule file in the repository (e.g. via a PR, a repo template, or content the agent is told to check in) can neutralize dangerous-command/dangerous-edit blocking rules for any tool call whose `command`/`new_string` content can be steered into triggering the backtracking blowup. This maps to Claude Code's hook/guard-bypass impact category — enabling unauthorized Bash command execution or file edits that a properly functioning `block` rule was supposed to prevent.

### Likelihood Explanation
Feasibility is high in principle: authoring `.claude/hookify.*.local.md` files with a `pattern` such as `(a+)+$` or `(.*)*!` is trivial and requires no special privilege beyond being able to add a file to the working repo/checkout that Claude Code operates on (consistent with the stated precondition of "attacker can author a hookify rule"). Repeatability requires that some subsequent tool call's `command`/`new_string` contains attacker-influenceable text long enough to trigger exponential blowup against that pattern — feasible for `Bash command` or `Write/Edit new_string` fields that echo repo content or agent-generated text of nontrivial length. The main uncertainty (which I could not verify from this codebase alone) is the exact external behavior of the Claude Code hook runner on a killed/timed-out `PreToolUse` hook process — whether it truly defaults to "allow" or to "deny" is defined outside this repo, so the ultimate bypass depends on that undocumented-here behavior.

### Recommendation
- Enforce a hard per-match time budget for `_regex_match` (e.g., run `regex.search` in a worker with `signal.alarm`/thread + timeout, or use the `regex` module's timeout parameter, or a linear-time engine like `re2`), and treat a timeout as a match-failure that still allows the rule's `action` to be evaluated deterministically rather than being silently dropped.
- Add pattern validation/complexity screening when loading rules in `config_loader.load_rule_file` (reject nested-quantifier patterns like `(x+)+`, `(x*)*`, cap pattern length) before ever compiling untrusted `pattern` values.
- Cap the length of `text` passed to `regex.search` for defense in depth.
- Most importantly: change the PreToolUse hook contract so that a hook timeout/crash on a rule engine failure defaults to `deny` (fail-closed) for `block`-action rules, not fail-open, or have `pretooluse.py` emit a partial/aggregate decision as soon as any earlier rule matches, rather than evaluating all rules before returning.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
```python
import time, pytest
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_redos_pattern_does_not_hang_and_denies():
    rule = Rule(
        name="evil-block-rule",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
        message="blocked"
    )
    engine = RuleEngine()
    evil_command = "a" * 40 + "!"  # forces catastrophic backtracking, no match at end
    input_data = {"hook_event_name": "PreToolUse", "tool_name": "Bash",
                  "tool_input": {"command": evil_command}}

    start = time.time()
    result = engine.evaluate_rules([rule], input_data)
    elapsed = time.time() - start

    # Expected (currently failing): bounded execution time
    assert elapsed < 2.0, f"regex evaluation took {elapsed}s — ReDoS not mitigated"
    # Expected (currently failing/undefined): timeout must not silently allow
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Run this with `pytest --timeout=5` to demonstrate that current code hangs well past a reasonable bound (input length can be tuned upward, e.g. 30–50 chars, to demonstrate exponential blowup), confirming `_regex_match`/`compile_regex` have no backtracking protection and that a hung evaluation never reaches the `deny` branch in `evaluate_rules`.

```python
    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
```

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```
