### Title
Stale `pending_delegator_rewards` snapshot causes inconsistent/duplicated block-reward payouts to stake delegators during partitioned reward recalculation - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Sherlock report describes a lending-pool pattern where a shared pool's "assets per share" is computed from a value (liquidity index) that is not adjusted for realized bad debt, so early withdrawers redeem at full value while later withdrawers absorb the entire loss. The closest reachable analog in Agave is the SIMD-0123 delegator-rewards pool on vote accounts: a single deposited lamport pool (`pending_delegator_rewards`) is split pro-rata among many unprivileged stake-account holders (delegators) using a formula computed from a *live*, mutable field rather than a value frozen at the start of the calculation.

### Finding Description
`deposit_delegator_rewards` increases `VoteStateV4::pending_delegator_rewards` via `add_pending_delegator_rewards` [1](#0-0) [2](#0-1) . This field represents a pool of lamports that must be shared, proportionally by delegated stake, among every stake account delegated to that vote account, via `calculate_block_reward`: [3](#0-2) 

Note that `pending_delegator_rewards` is read from `distribution_epoch_vote_accounts`, i.e., the *current* vote-account state at the time of calculation/recalculation, not a value frozen at the reward epoch boundary. In contrast, the denominator (`total_active_stake`) is deliberately taken from a frozen `RewardEpochDelegatedStakes` snapshot specifically to avoid a denominator-skew bug — the associated regression test states this requirement explicitly: [4](#0-3) 

That test proves the developers already recognized and fixed the "later recipients get a different result than earlier recipients because the pool inputs moved during distribution" bug class for the *denominator*. However, the *numerator* (`pending_delegator_rewards`) is not similarly pinned to an epoch-boundary snapshot — it is read live from the vote account each time `calculate_block_reward` runs (including during `recalculate_stake_rewards`, which the same file shows is invoked after a partial distribution, e.g., following a snapshot restore mid-epoch) [5](#0-4) .

Crucially, I found no code path in `programs/vote` or `runtime/src/bank/partitioned_epoch_rewards` that decrements `pending_delegator_rewards` on the vote account as individual delegator portions (`block_reward`) are paid out via `store_stake_accounts_in_partition` / `build_updated_stake_reward` [6](#0-5) . `add_pending_delegator_rewards` (the only mutator besides deserialization) only ever increments the value [2](#0-1) .

Because the numerator used in the pro-rata split is not frozen and not reduced as portions are distributed, a "first mover" pattern analogous to H-7 can arise: if `pending_delegator_rewards` is mutated (e.g., a new `deposit_delegator_rewards` transfer lands, or the value is otherwise re-read) between when some delegators' `PartitionedStakeReward.block_reward` entries were originally computed and when a recalculation occurs for others (per `recalculate_stake_rewards`, which the codebase explicitly exercises for "partial distribution" scenarios), delegators processed in an earlier partition receive rewards computed against one pool-total, while delegators in a later partition (post-recalculation) receive rewards computed against a different, inconsistent pool-total — the exact "early withdrawer locks in a favorable rate, late withdrawer bears the mismatch" structural flaw described in H-7, here manifesting as reward-payout inconsistency/duplication rather than principal loss.

### Impact Explanation
This falls in the "misattributed or duplicated rewards" and "cross-node state divergence" categories called out as acceptable impact classes. If `pending_delegator_rewards` is not frozen at the epoch boundary the way the delegated-stake denominator explicitly is, a recalculation triggered mid-distribution (the exact scenario the existing regression test targets) can compute a different total lamport pool for the still-unpaid partition than what was implicitly assumed for the already-paid partition, producing an inconsistent/duplicated allocation of the same underlying deposited SOL across delegators, and potentially divergent outcomes between validators that recalculate at different points versus those that do not.

### Likelihood Explanation
This requires the specific, already-instrumented-for-testing condition of a partial distribution followed by recalculation (e.g., after a snapshot restore mid-epoch) combined with an intervening mutation of `pending_delegator_rewards` (a new `DepositDelegatorRewards` instruction, which is permissionless for anyone signing as the source account) before recalculation completes. This is a narrower trigger than the lending-pool original (which needs only ordinary bad debt), so likelihood is lower, and I was not able to fully confirm within tool budget whether any additional invariant elsewhere prevents this (e.g., whether `deposit_delegator_rewards` is disallowed during an active distribution window).

### Recommendation
Freeze `pending_delegator_rewards` (the numerator) into the same epoch-boundary snapshot structure (`RewardEpochDelegatedStakes` or an equivalent) that is already used for the denominator in `calculate_block_reward`, so that recalculation after partial distribution is guaranteed to use the identical pool total for every delegator, regardless of intervening deposits. Add a regression test mirroring `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` but for `pending_delegator_rewards` mutation between calculation and recalculation.

### Proof of Concept
I was unable to construct and verify an end-to-end PoC within the available tool budget; this assessment is based on static code review of `calculate_block_reward`, `recalculate_stake_rewards`, `deposit_delegator_rewards`, and the associated regression tests, which together show the denominator is explicitly pinned against this bug class while the numerator is not. Confirming exploitability would require verifying whether `DepositDelegatorRewards` can execute during an active `EpochRewardStatus::Active` distribution window on a live bank, which I could not confirm with the remaining searches.

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,
        );
        (stake_rewards, partition_indices)
    }

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
        }
