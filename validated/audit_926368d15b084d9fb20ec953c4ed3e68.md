### Title
Spender-attested asset can permanently freeze already-held balances when the attestor list is updated - ([File: validation.js])

### Summary
For assets defined with `spender_attested: true`, `ocore` re-checks a holder's attestation status **at the time of every spend**, not at the time the funds were received. The asset definer can publish a new `asset_attestors` message at any time to change the list of trusted attestors (or an attestor may simply stop re-attesting an address). Any address that already holds a balance of the asset but is not on the current attestor list becomes permanently unable to move that balance, exactly mirroring the reported bug class where a decreasing `perWalletLimit` blocks withdrawal of shares a holder already legitimately owns.

### Finding Description
When an asset has `spender_attested: true`, `readAsset`/`loadAssetWithListOfAttestedAuthors` load the **current, latest** attestor list for the asset (most recent `asset_attestors` unit) rather than the list that was in effect when the balance was received: [1](#0-0) 

During payment validation, both the transfer's *input owner* and every *output address* must be on this current attested list, or the unit is rejected: [2](#0-1) [3](#0-2) 

The attestor list itself is fully mutable after asset creation via the `asset_attestors` message, which the asset definer (or, for AA-issued assets, the AA) can post at will: [4](#0-3) [5](#0-4) 

Because the check is evaluated against the *latest* stable attestor-list unit rather than a snapshot at receipt time, a wallet that legitimately received asset tokens while attested can be locked out of spending them the moment the attestor list changes and that wallet's attestor is dropped (or simply the definer swaps attestors and stops re-attesting the holder). This is structurally identical to the `LMPVault` issue: a protocol-controlled parameter (`perWalletLimit` there, `arrAttestedAddresses`/attestor list here) is allowed to change after the fact, and the enforcement logic applies the *new* value even to holders whose balance was accumulated under the *old* value, with no grandfathering, freezing already-held funds rather than merely limiting future accumulation.

### Impact Explanation
An address (including an AA or external protocol/integration holding the attested asset as part of its accounting) that already holds a balance can have that balance permanently frozen — it cannot transfer, redeem, or otherwise move it, because every payment spending that output requires the owner address to be on the current attestor list. This is a fund-freezing condition reachable purely by the asset's own designer via a normal, no-privilege-escalation `asset_attestors` unit (an in-scope "asset issuer" action), with no way for the holder to work around it (similar to the walletLimit case, the holder cannot "downsize" the transfer to route around the check, since the check is on the *address*, not the amount).

### Likelihood Explanation
This requires the asset to be defined with `spender_attested: true` (an explicit opt-in feature) and for the definer to publish an `asset_attestors` update, or for an attestor to simply stop re-attesting the address (attestations must be periodically renewed relative to `address_definition_changes`, per the query in `filterAttestedAddresses`). Both scenarios are ordinary, permitted operations already exercised by the protocol's normal API (`aa_composer.js`/`asset_attestors` message), not attacker-privileged actions, making this readily reachable in any asset that uses attestation-gated transfers.

### Recommendation
Snapshot attestation status at the time each output is created (or otherwise grandfather previously-attested balances), rather than re-validating spender attestation against the *current* attestor list at every subsequent spend. At minimum, only apply the up-to-date attestor-list check to newly issued/received outputs, and allow holders to move out balances they already held under a previously valid attestor list, analogous to allowing withdrawals unaffected by a later-tightened limit.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and attestor list `[Attestor1]`.
2. `Attestor1` attests address `A`. `A` receives a payment of asset `X` (validated fine, since `A` is attested and passes `arrAttestedAddresses` check at receipt time — `validation.js:2506`, `validation.js:2632`).
3. Definer later posts an `asset_attestors` message removing `Attestor1` and adding `Attestor2` only (`aa_validation.js:338-352`, `validation.js:2033-2041`).
4. `storage.readAsset` now loads the *latest* attestor list `[Attestor2]` for asset `X` (`storage.js:1917-1946`).
5. `A` (attested only by `Attestor1`, not `Attestor2`) attempts to spend/transfer its previously received balance of `X`. Validation fails at `validation.js:2506-2507` ("owner address is not attested") and/or `validation.js:2632-2641` if `A` is also an output/change address — the unit is rejected and `A`'s balance is permanently stuck.
