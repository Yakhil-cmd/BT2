### Title
AAs permanently lock any fixed-denomination (indivisible) asset units they receive - (File: aa_composer.js)

### Summary
Any Autonomous Agent (AA) address can receive coins of an arbitrary asset as part of its `trigger.outputs`, and `aa_composer.js` faithfully credits that asset to the AA's `aa_balances` row. However, the same file's outbound-payment logic in `sendUnit()` explicitly refuses to build a valid payment message for assets whose definition has `fixed_denominations: true` (i.e. indivisible/textcoin-style assets): the code skips `completePaymentPayload` for such assets and later strips any surviving payment message referencing them out of the response unit. No other function in `aa_composer.js` provides an alternate path for an AA to move a fixed-denomination asset it holds. Consequently, once such an asset is sent to an AA, the funds are permanently stuck there, exactly analogous to BathBuddy's `receive()` accepting ETH with no corresponding withdrawal logic.

### Finding Description
When a unit triggers an AA, `updateInitialAABalances()` in `aa_composer.js` credits the AA's balance for every asset present in the trigger's outputs, with no restriction on asset type: [3](#0-2) . This applies uniformly to base bytes, divisible assets, and fixed-denomination (indivisible) assets.

When the AA's bytecode later tries to construct outgoing payment messages in `sendUnit()`, for any non-base asset it loads the asset properties and, if `objAsset.fixed_denominations` is true, it deliberately skips `completePaymentPayload` (which is what fills in `inputs`/`outputs`/change for the message) with the comment "will skip it later": [1](#0-0) . Later, after the per-message loop finishes, any payment message that references a fixed-denomination asset is filtered out of the final message list entirely: [2](#0-1) . If this filtering empties the message list, the AA silently "eats" the trigger and produces an empty response, per `handleSuccessfulEmptyResponseUnit`.

This means there is no code path in `aa_composer.js` by which an AA can ever spend/forward a fixed-denomination asset that it holds — regardless of what the AA's own oscript/ojson logic instructs it to do. The restriction is structural (protocol/composer-level), not a bug in any individual AA's bytecode. Supporting evidence that fixed-denomination payments require special, single-input construction that only the wallet-side composers (`indivisible_asset.js`) implement — never `aa_composer.js` — can be seen in the validator's own requirement that fixed-denomination payments have exactly one input: [4](#0-3) , a shape aa_composer.js's payment-completion logic never produces.

Because `validateAssetDefinition` only forbids an AA from being the definer of a fixed-denomination asset when `issued_by_definer_only` is `true`, an AA can legitimately be a valid recipient/participant with such assets: [5](#0-4) . Any user (an "unprivileged unit poster" per the analog rules) can freely send a fixed-denomination asset's units to any AA address as ordinary payment, since normal payment validation only cares about output address validity, not whether the destination is an AA.

### Impact Explanation
Once units of a fixed-denomination asset are sent to any AA address (whether by a user, another AA, or as designed forwarding logic within the AA's own bytecode), those units become permanently and unconditionally unspendable:
- The AA's internal `aa_balances` bookkeeping still shows the asset as available, misleading AA authors and users into believing it is recoverable via the AA's normal payment message mechanism.
- No bounce, no state variable manipulation, and no valid oscript payment message can ever release these coins, since `sendUnit()` unconditionally strips fixed-denomination payment messages before building the response unit.
- This causes permanent freezing of user funds inside the AA layer, matching the "AA fund loss or freezing" impact category, and is more severe than the original BathBuddy report because it applies to *every* AA on the network, not a single contract, and there is no way for even the AA author to fix already-locked funds after the fact (an AA's definition is immutable once deployed).

### Likelihood Explanation
Likelihood is high: any address holding a fixed-denomination/indivisible asset (a supported, first-class asset type in Obyte, used e.g. for private textcoins and NFT-like assets) can trigger any AA by sending it such an asset as an ordinary payment. No special privilege, malicious node, or protocol violation is required — it is a normal, validly-signed unit. AA authors who are unaware of this platform-level limitation may also unintentionally design AAs (e.g. escrow/marketplace AAs) that accept arbitrary asset types from `trigger.output[[asset!=base]]` without realizing that fixed-denomination assets can never be forwarded back out.

### Recommendation
Either:
1. Implement support in `aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` for constructing valid single-input fixed-denomination payment messages (mirroring the logic in `indivisible_asset.js`) so AAs can actually spend indivisible assets they hold, or
2. If supporting indivisible-asset payments from AAs is out of scope, proactively prevent the lock by rejecting/bouncing trigger units that pay a fixed-denomination asset to an AA address at the protocol/validation layer (rather than silently accepting and permanently trapping the funds), and clearly document this restriction so AA authors do not build logic (e.g. `trigger.output[[asset!=base]]`) that implicitly assumes AAs can forward any asset type.

### Proof of Concept
1. Issue a fixed-denomination asset (`fixed_denominations: true`) using `indivisible_asset.js`/wallet composer functionality.
2. Send a payment of that asset's coin(s) to any deployed AA address as `trigger` outputs (a normal, validly-signed payment unit — no AA cooperation required).
3. Observe that `updateInitialAABalances()` credits the asset to the AA's `aa_balances` row [6](#0-5) .
4. Have the AA's bytecode attempt to send that asset back out via a `payment` message referencing the fixed-denomination asset (e.g. `trigger.data.withdraw` forwarding pattern as in `test/samples/a_bank_without_percent.oscript`).
5. Observe in `sendUnit()` that the message is filtered out at [2](#0-1)  and the AA instead emits an empty response ("no messages after removing fixed denominations"), while the coins remain permanently recorded in `aa_balances` with no way to ever move them out.
