## Analog Found

### Title
Unsanitized Correspondent Device Name Allows Invisible-Character Identity Spoofing in Multi-Signature Cosigner Approval - (File: device.js)

### Summary
`handlePairingMessage()` in `device.js` sanitizes an attacker-controlled `device_name` field only by stripping HTML-like tags, without removing invisible/zero-width/format Unicode characters. This stored `name` is later displayed to the wallet owner as the human-readable identity of a paired device/correspondent in security-relevant flows such as shared (multisig) address cosigner confirmation, exactly mirroring the CVE-2022-1834 bug class where an invisible-character-padded display name lets an attacker impersonate a trusted identity that the user relies on to make a trust decision.

### Finding Description
When a new device pairs, `handlePairingMessage` receives `body.device_name` and sanitizes it with: [1](#0-0) 
```
var safe_device_name = body.device_name.replace(/<[^>]*>?/g, ''); // only strips HTML tags
db.query(
    "INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
    [from_address, device_pubkey, json.device_hub, safe_device_name],
```
The only validation performed on `body.device_name` prior to this is a non-empty-string and length check: [2](#0-1) 

No filtering is applied for zero-width spaces, Braille Pattern Blank (`U+2800`), bidirectional override characters, or other invisible/confusable Unicode code points. This is the same root cause as CVE-2022-1834: Thunderbird trusted a display string built from user-supplied text containing invisible padding, so the "true" spoofed identity was hidden from the human verifying it while the validated identity (the digital signature / device pubkey-derived `device_address`) differed from what was shown.

In ocore, the stored `name` (keyed only by `device_address`, itself derived from the pairing device's pubkey — an identity the attacker fully controls since they generate their own pairing key) is subsequently displayed wherever correspondents are looked up by name rather than by address, e.g.:
- `readSharedAddressPeers` / `readSharedAddressCosigners` in `wallet_defined_by_addresses.js`, used to show shared-address (multisig) cosigners to the user: [3](#0-2) 
- `readCosigners` in `wallet_defined_by_keys.js`, used to display multi-device wallet members: [4](#0-3) 
- `readCorrespondents` / `readCorrespondentsByDeviceAddresses` in `device.js`, the general contact list used across chat, payment requests, and shared-address creation dialogs: [5](#0-4) 

An attacker who pairs with the victim can choose a `device_name` string that starts with the exact name of an already-trusted correspondent (or a bank/service the user expects), followed by many invisible Unicode characters, then a short distinguishing suffix. Truncated or non-glyph-rendering UI surfaces will display what looks identical to the trusted contact's name, while the underlying `device_address` (and thus the cryptographic identity used for signing/authorization) is the attacker's own.

### Impact Explanation
Names stored via this unsanitized path are the sole human-facing signal used when a user is asked to approve adding a device as a cosigner to a shared/multisig address (`create_new_shared_address` / `approve_new_shared_address` flow in `wallet.js`) or to accept a peer/counterparty for a private/multisig payment. If the user is deceived into believing they are approving a shared address definition with a known, trusted cosigner when in fact they are adding the attacker's device, the attacker becomes a legitimate co-signer of that shared address. Depending on the definition template (e.g., `n-of-m`/threshold `and`/`or` conditions), this can lead to unauthorized spending from the shared funds (if the attacker's signature alone or in combination with a lower threshold suffices) or to the shared address becoming permanently unusable/frozen (if the attacker refuses to cosign, as spending requires cooperation of all listed signers). This satisfies the required concrete impact of unauthorized spending or AA/wallet fund freezing reachable from a single paired device's message.

### Likelihood Explanation
Pairing with a victim is explicitly designed to be initiated by any party holding a pairing secret/QR code that is often shared broadly (e.g., posted publicly by a bot or business to onboard new users), and `handlePairingMessage` accepts pairing attempts from unknown correspondents by design (`arrSubjectsAllowedFromNoncorrespondents` includes `"pairing"`): [6](#0-5) 
Crafting a spoofed name requires no cryptographic effort — only choosing a `device_name` string containing common invisible Unicode characters, which are not filtered by the existing `<[^>]*>?` HTML-tag regex.

### Recommendation
Sanitize `device_name` (and any other free-text identity field surfaced in trust decisions, such as correspondent name updates in `addUnconfirmedCorrespondent`/`updateCorrespondentProps`) by stripping or rejecting non-printable, zero-width, and bidirectional-control Unicode categories (e.g., `Cf`, `Cc`, `Zs` beyond a single ASCII space) in addition to HTML tags, and consider normalizing (NFKC) and collapsing consecutive whitespace/invisible runs before storing or displaying the name. Additionally, always display the underlying `device_address`/pairing code alongside the human-readable name in any confirmation dialog that grants signing authority (shared-address creation/approval), so users are not solely reliant on a spoofable display string.

### Proof of Concept
1. Attacker publishes/obtains a pairing secret for the victim's wallet device (a normal pairing flow, e.g., via a bot's public pairing link).
2. Attacker's device sends a `pairing` message with `body.device_name` = `"Alice"` + repeated `U+2800` (Braille Pattern Blank) or `U+200B` (zero-width space) characters + a short random suffix, totalling ≤100 chars.
3. `handlePairingMessage` strips only HTML tags via `body.device_name.replace(/<[^>]*>?/g, '')`, leaving the invisible padding intact, and stores it as `correspondent_devices.name` for the attacker's `device_address`.
4. Victim's wallet UI, when listing correspondents/cosigners (via `readCorrespondents`, `readCosigners`, `readSharedAddressCosigners`), renders the name; due to invisible characters and truncation in typical list UIs, it appears identical to the real "Alice" contact.
5. Victim initiates `create_new_shared_address`, selecting whom they believe is "Alice" as cosigner, and approves the resulting shared address definition, unknowingly granting the attacker's device address a signing role in the multisig wallet.
6. Attacker, now a legitimate signer per the on-chain address definition, can withhold cooperation (freezing funds) or, depending on threshold, co-sign transactions to redirect funds — both outside the victim's actual intent.

function readCosigners(wallet, handleCosigners){
	db.query(
		"SELECT extended_pubkeys.device_address, name, approval_date, extended_pubkey \n\
		FROM extended_pubkeys LEFT JOIN correspondent_devices USING(device_address) WHERE wallet=?", 
		[wallet], 
		function(rows){
			rows.forEach(function(row){
				if (row.device_address === device.getMyDeviceAddress()){
					if (row.name !== null)
						throw Error("found self in correspondents");
					row.me = true;
				}
				else if (row.name === null)
					throw Error("cosigner not found among correspondents, cosigner="+row.device_address+", my="+device.getMyDeviceAddress());
			});
			handleCosigners(rows);
		}
	);
}
