### Title
Scoped API token can read the build status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver to look up the stack directly from `Stack.from_param!(params[:stack_id])` instead of using the api-client-scoped `stacks` relation defined in `BaseController`. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack whose state is actually returned," letting a token scoped to one stack read the build status of any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the set of visible stacks to the one the current `ApiClient` is bound to when `stack_id` is set: [1](#0-0) 

Every other API controller (e.g. `Api::CommitsController`, `Api::OutputsController`, `Api::HooksController`, `Api::StacksController`) relies on this inherited `stack`/`stacks` method, so `require_permission :read, :stack` combined with `stacks.from_param!` correctly enforces that a scoped token can only touch the stack it was minted for.

`Api::CCMenuController`, however, redefines `stack` to bypass this scope entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

It never checks whether `current_api_client.stack_id` matches the requested `params[:stack_id]`. Since `CCMenuController#stack` calls `Stack.from_param!` directly (not `stacks.from_param!`), the permission check and the stack lookup are decoupled: any token with `read:stack` — even one created scoped to a single stack, such as the ones minted transparently by `CCMenuUrlController#client` — can supply an arbitrary `stack_id` and receive that stack's data. [4](#0-3) 

This is exactly the "stack a token authorises versus a stack it touches" trust binding: before the attacker's request, `token.stack_id == requested_stack.id` is assumed to hold because of `require_permission`; after hitting this endpoint with a foreign `stack_id`, the binding is violated and cross-stack data is returned.

### Impact Explanation
An attacker in possession of any valid scoped API token (e.g. a CCMenu token generated for one project, which is embedded in a URL and passed as a plain query-string parameter, per `CCMenuUrlController#fetch`) can enumerate `owner/repo/environment` stack identifiers and read the build status, last build label, and activity of every stack managed by the Shipit instance — not just the one the token was scoped to. This is an unauthenticated-for-that-resource read of stack state, matching the "High" impact bucket: unauthenticated read of stack state.

### Likelihood Explanation
Any holder of a scoped `read:stack` token can exploit this with a single unauthenticated-for-target GET request; no privileged access, secrets, or social engineering is required, only knowledge/guessing of another stack's `stack_id` path component (`owner/repo/environment`), which is not itself secret. `CCMenuUrlController` actively hands such tokens to any logged-in user by embedding them in query strings, increasing the population of tokens available to test this against other stacks.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the permission check and stack resolution use the same trust boundary as the rest of the API controllers.

### Proof of Concept
1. Obtain a scoped CCMenu token for `stack-a` via `GET /ccmenu/stack-a` (mints an `ApiClient` with `stack_id = stack-a.id`, permission `read:stack`), or use any other token scoped with `read:stack` to a single stack.
2. Send `GET /api/stacks/stack-b/ccmenu?token=<stack-a-scoped-token>` where `stack-b` is a different, unrelated stack.
3. `authenticate_api_client` accepts the token (valid signature), `require_permission :read, :stack` passes (token has `read:stack`), and `stack` resolves via `Stack.from_param!('stack-b')` — bypassing the `stacks` scope — returning `stack-b`'s build status XML despite the token only being authorized for `stack-a`.
