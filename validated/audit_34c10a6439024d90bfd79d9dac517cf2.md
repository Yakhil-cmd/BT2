### Title
Stack-scoped API token authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution method inherited from `Shipit::Api::BaseController` in a way that drops the stack scoping enforced for every other API token. A token minted with `stack_id` set (i.e., authorized to read only one specific stack) can be used to read CCMenu/build-status data for **any** stack, because the controller resolves the target stack directly from the request parameter instead of through the token-scoped relation.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding between an `ApiClient` token and the stacks it may act on: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the token is scoped, or `Stack.all` otherwise, and `stack` resolves the requested id only within that relation — this is the equality the engine is supposed to maintain: `stack the token authorizes == stack the request touches`.

`CCMenuController`, however, redefines `stack` to bypass this relation entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`Stack.from_param!` resolves against **all** stacks, with no reference to `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string — it never re-validates that the specific `stack_id` in the request matches the token's authorized stack. As a result, presenting a valid, correctly-signed token that was created with `stack_id` set to stack A (via `ApiClient.authenticate(params[:token])`, e.g. tokens generated by `CCMenuUrlController#client` or any stack-scoped `ApiClient` created by an admin through `ApiClientsController`) still passes `authenticate_api_client` and `require_permission!`, and then `stack` in `CCMenuController` happily loads and renders data for stack B if `params[:stack_id]` is set to B's slug.

### Impact Explanation
This is an unauthenticated-scope escalation: a party holding a token that was deliberately restricted to one stack (the intended trust boundary encoded in `ApiClient#stack_id`) can read build/deploy status (`stack.deploys_and_rollbacks.last`, lock state, deploy name/status) for any other stack in the Shipit instance, including private/internal stacks the token holder was never meant to see. This satisfies the "unauthenticated read of stack state … deploy output" High-severity criterion, since the token is not a global/all-stacks credential by construction, yet the endpoint treats it as one.

### Likelihood Explanation
Any holder of a stack-scoped API token (these tokens are routinely shared, e.g. embedded in the CCMenu XML URL distributed to CI dashboard tools, or issued to third-party integrations restricted to a single stack) can trivially exploit this by changing the `stack_id` path segment on the `GET /api/:owner/:repo/:env/ccmenu.xml?token=...` request. No privileged access or additional secrets are required beyond a single valid, narrowly-scoped token — likelihood is high given how easily CCMenu tokens circulate (they are designed to be embedded in third-party CI dashboard URLs, per `CCMenuUrlController`).

### Recommendation
`CCMenuController#stack` should resolve the target stack through the same token-scoped `stacks` relation used everywhere else in the API (i.e., `stacks.from_param!(params[:stack_id])`), so a token whose `ApiClient#stack_id` is set can never resolve a different stack.

### Proof of Concept
1. An admin creates a stack-scoped `ApiClient` (or the CCMenu URL flow issues one) with `stack_id` set to Stack A and permission `read:stack` (`app/controllers/shipit/ccmenu_url_controller.rb`, `app/models/shipit/api_client.rb`).
2. Attacker obtains this token (e.g. from a shared CCMenu dashboard URL for Stack A).
3. Attacker sends `GET /api/<other_owner>/<other_repo>/<other_env>/ccmenu.xml?token=<TOKEN>` where the path identifies Stack B, a stack the token was never scoped to.
4. `authenticate_api_client` succeeds (token is valid) → `require_permission!(:read, :stack)` succeeds (token has `read:stack`) → `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` and returns Stack B, bypassing the `current_api_client.stack_id` restriction that `BaseController#stacks` would have enforced.
5. Response renders Stack B's deploy/build status XML, disclosing state of a stack outside the token's authorized scope.
