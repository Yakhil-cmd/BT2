### Title
`ReopenedHandler#unarchive?` bypasses `repository.review_stacks_enabled` for `prevent_with_label`/`allow_with_label` repositories due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` intends `repository.review_stacks_enabled` to gate all review-stack provisioning behaviors, but Ruby's `&&`/`||` precedence only applies it to the `allow_all?` clause. When a repository has `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, reopening a labelless PR still triggers `ReviewStackAdapter#unarchive!`, creating/unarchiving a `Stack` and enqueuing it for provisioning.

### Finding Description
The intended binding is `repository.review_stacks_enabled == (gate applied to every provisioning_behavior branch of unarchive?)`. The actual code is: [1](#0-0) 

which Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. `review_stacks_enabled` is only ANDed into the first disjunct; the second and third disjuncts are evaluated independently of it.

Trace: with `review_stacks_enabled = false`, `provisioning_behavior = :prevent_with_label`, and no provisioning label on the PR:
- clause 1: `false && false` = `false` (allow_all? is false because behavior is prevent_with_label)
- clause 2: `false && ...` = `false` (allow_with_label? is false)
- clause 3: `true && !false` = `true` → overall `unarchive?` returns `true`

`respond_to_pull_request_reopened?` then calls `stack.unarchive!` via `ReviewStackAdapter#unarchive!`, which either unarchives an existing archived stack or, if none exists, calls `create!`, both paths enqueuing the stack in `Shipit::ReviewStackProvisioningQueue`: [2](#0-1) [3](#0-2) 

The identical structural bug exists in `OpenedHandler#provision?`: [4](#0-3) 

By contrast, `LabeledHandler`/`UnlabeledHandler` correctly gate on `review_stacks_enabled` at the caller level (`respond_to_label_change?`), outside of the `archive?`/`unarchive?` methods, and their internal predicates don't reference `review_stacks_enabled` at all: [5](#0-4) 

This confirms the design intent that `review_stacks_enabled` must gate the entire feature; `OpenedHandler` and `ReopenedHandler` fail to do so due to the misplaced precedence. No other guard (`verify_signature`, `ExplicitParameters`, model validations) checks this consistency — the webhook signature check only authenticates that the payload came from GitHub for that repository, it does not enforce the intended policy semantics of `review_stacks_enabled`.

The existing test suite exercises `prevent_with_label` with label absent, but always with the default `provisioning_enabled: true` in `configure_provisioning_behavior`, so the `review_stacks_enabled=false` divergence is untested: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any user who can close/reopen (or open) a pull request against a repository misconfigured this way (`review_stacks_enabled=false`, `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`) can force creation and enqueuing-for-provisioning of a `Shipit::ReviewStack` for their own PR, bypassing the operator's explicit "review stacks disabled" setting. The created stack's `branch` is the attacker's PR head ref. If the host application has registered a `ProvisioningHandler` that runs actual provisioning commands (the documented purpose of the feature) or the stack later proceeds through normal deploy/task flow, this results in execution of attacker-influenced configuration/commands that the repository owner explicitly intended to prevent by disabling `review_stacks_enabled`. The write stays within the same repository's `review_stacks` association, so it is not a cross-repository/cross-tenant mutation, but it is an unauthorized bypass of an administrator-configured kill switch, repeatable on every reopen/open event against any repository left in this inconsistent state.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled=false` combined with `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (not the default `allow_all`) — an inconsistent-but-plausible state (e.g., an operator temporarily disabling review stacks without resetting the behavior). Given that configuration, exploitation is trivial and free for the attacker: open/close/reopen their own PR, optionally omitting/adding a label, with zero authentication or privilege required beyond being able to interact with the repo's own PRs.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by explicitly grouping `review_stacks_enabled` around the entire expression, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style:
```ruby
test "does not provision/unarchive stacks when review_stacks_enabled is false, even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails because `Shipit::Stack.count` increases by one (`unarchive?` returns `true` despite `review_stacks_enabled == false`, both sides of the intended binding diverge).
