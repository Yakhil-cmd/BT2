### Title
Webhook signature verification authenticates the wrong side of the payload, letting one configured GitHub organization forge events for another organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. Every other part of the webhook processing pipeline — in particular `Handler#stacks`, which decides *which repository/stack gets mutated* — uses a different field from the very same JSON body, `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so in any Shipit deployment configured with multiple GitHub organizations (a documented and supported configuration), an attacker who legitimately controls one configured organization's webhook secret can forge a payload where `repository.owner.login` names their own organization (so the signature check passes using their own valid secret) while `repository.full_name` names a completely different, victim organization's repository (so the write-side logic acts on that unrelated repository).

### Finding Description
The signature check: [1](#0-0) 
resolves the GitHub App config with `Shipit.github(organization: repository_owner)` and verifies the raw request body against that org's `webhook_secret`: [2](#0-1) 

The actual repository/stack that gets acted upon is resolved independently, in `Handler#stacks` / `Handler#repository_name`: [3](#0-2) 

For example, the push handler blindly trusts this repository resolution to find and mutate stacks: [4](#0-3) 

Shipit explicitly supports hosting multiple independent GitHub organizations, each with its own `app_id`, `private_key`, and `webhook_secret`, as documented in the example secrets files: [5](#0-4) [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login)` **==** `organization/repository actually mutated by the handler (repository.full_name)`

Before the attack: for a legitimate webhook, both fields describe the same repository, so the signature owner and the mutated repository always coincide.

After the attack: an attacker who administers "OrgTwo" (their own tenant on the same Shipit instance) knows OrgTwo's `webhook_secret` (it is their own GitHub App's webhook secret, configured by them when they set up their organization's App installation). They send a raw POST to `/github/webhooks` with:
- `repository.owner.login = "OrgTwo"` (their own org — makes `verify_signature` pick OrgTwo's config and succeed, since they control the actual HMAC key)
- `repository.full_name = "OrgOne/victim-repo"` (the victim's repository, tracked under a different org on the same Shipit instance)

`verify_signature` passes because the signature is valid for OrgTwo's secret and the whole raw body (the check never inspects `full_name`). The handler then resolves the target purely from `full_name`, so `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, using an attacker-chosen `after` SHA and `ref`, which is exactly the trust-boundary crossing the analog report describes: the value that was authenticated (organization/secret) is not the value that gets acted on (target repository/stack).

### Impact Explanation
This lets an unprivileged operator of one tenant organization on a shared Shipit instance forge GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) attributed to and acted upon a different organization's repository that they do not control. Depending on the handler this can trigger unwanted `GithubSyncJob` runs, fabricate commit statuses, or manipulate membership/team records for a repository the attacker has no legitimate access to — a cross-repository write across an organizational trust boundary that the app is supposed to enforce via per-organization webhook secrets.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a documented, supported setup) and that the attacker controls (administers the App installation for) at least one of those organizations — no Shipit session, `ApiClient` token, or victim credentials are needed, and the `/github/webhooks` endpoint is deliberately unauthenticated apart from the signature check.

### Recommendation
After signature verification succeeds, re-derive/require that `repository.owner.login` (or the GitHub App installation that produced the valid signature) matches the organization owning `repository.full_name` before dispatching to handlers, or bind webhook verification to the installation ID rather than a client-supplied `owner.login` field, ensuring the authenticated organization and the mutated repository are always the same entity.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (victim, tracked stack `OrgOne/victim-repo`) and `OrgTwo` (attacker-administered), each with distinct `webhook_secret`s, per `test/dummy/config/secrets_double_github_app.yml`.
2. As the attacker (admin of OrgTwo's GitHub App), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "full_name": "OrgOne/victim-repo", "owner": { "login": "OrgTwo" } }
   }
   ```
3. Sign the raw body with OrgTwo's real `webhook_secret` and POST it to `/github/webhooks` with header `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` and successfully verifies the signature against OrgTwo's secret.
5. `PushHandler#process` resolves `stacks` from `repository.full_name` ("OrgOne/victim-repo"), finds OrgOne's real stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on a repository the attacker does not administer, despite having authenticated only as OrgTwo.

      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified
