This confirms a strong finding: the webhook signature verification is keyed off `repository_owner` (org login), but the actual write-target (which repository/commit gets acted upon) is determined independently from `payload.dig('repository', 'full_name')` inside each handler ` [1](#0-0) `, with no re-check that the acted-upon repository belongs to the same organization whose secret validated the signature ` [2](#0-1) `. In a multi-org deployment (`Shipit.github_organizations` / per-org `webhook_secret` config as documented) ` [3](#0-2) `, an attacker who controls one onboarded GitHub organization's webhook secret can forge a `status` event whose `repository.owner.login` matches their own org (so it authenticates) but whose `sha`/`state`/`context` target a commit belonging to a stack in a **different, victim** organization, since `StatusHandler` looks commits up globally by `sha` with no ownership/org check ` [4](#0-3) `. This lets the attacker write fake CI/commit statuses on a victim repository they don't own, which the `ci.require` deploy-safety check consumes to allow deploys.

### Title
Webhook signature verified for one GitHub organization but the event acts on any repository's commits — cross-organization forged commit status ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) ` [2](#0-1) `. Once the signature passes, the full raw JSON `params` is handed unmodified to every registered handler for the event ` [5](#0-4) `. Handlers, however, independently pick their own target repository from `payload.dig('repository', 'full_name')` (base `Handler#repository_name`, and per-handler `params.repository.full_name`), which is never cross-checked against the organization/owner login that determined the verifying secret ` [6](#0-5) `. Worse, `StatusHandler` doesn't even filter by repository — it looks up `Commit.where(sha: params.sha)` engine-wide and writes a GitHub commit status onto any matching commit, from any stack, in any organization ` [4](#0-3) `.

### Finding Description
This is the same trust-binding break as the reference report: a value is checked/authorized against one thing (the org whose `webhook_secret` matched) while the effectful write is performed using a different, unverified field from the same payload (the target commit/repository). Equality that should hold: `organization authenticated by signature == organization owning the repository/commit written`. The code breaks this because:
- Shipit supports multiple GitHub organizations, each with an independent `webhook_secret`, selected per-request via `Shipit.github(organization: repository_owner)` and `github_app_config` ` [3](#0-2) `.
- `verify_signature` only proves the request was signed by *some* configured org's secret — the one named in the payload's own `repository.owner.login`/`organization.login` field, which is attacker-controlled content, not a property of which secret was actually used.
- The handler that performs the actual side effect (`StatusHandler#process`) trusts `params.sha` alone to find the `Commit` to mutate, with zero repository/org scoping ` [4](#0-3) `.
- Consequently, an attacker who legitimately owns Org A (onboarded in Shipit with its own `webhook_secret`) can sign a `status` payload with `repository.owner.login: "org-a"` (or `organization.login: "org-a"`) — which authenticates using Org A's secret — while setting `sha` to a commit SHA belonging to Org B's (victim) repository/stack. `Commit.where(sha:)` will match Org B's commit and `commit.create_status_from_github!` will record an attacker-chosen `state`/`context`/`description` for it.

### Impact Explanation
Commit statuses recorded this way feed directly into Shipit's deploy-safety gating (`ci.require`), which blocks deploys unless required status contexts are green. By forging a "success" status for a required CI context on a victim commit the attacker doesn't control, the attacker can clear a CI gate that a legitimate reviewer/human relies on before deploying, enabling an effectively unauthorized deploy path once a privileged user (or continuous deployment) proceeds based on the falsified status. This crosses the "unauthorized deploy" impact bar defined for Critical findings, achieved purely by exploiting the org-vs-repository binding gap — no repository write access or Shipit session is required, only ownership of one unrelated onboarded GitHub organization.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported and documented, see `config/secrets.development.example.yml` multi-org example and `docs/setup.md`) where the attacker controls at least one onboarded, lower-trust organization and knows/derives a target commit SHA from a higher-trust org (commit SHAs are not secret — visible via GitHub itself, PRs, or Shipit's own UI). No social engineering, stolen credentials, or code execution needed — just crafting an HTTP request with a valid signature computed from a secret the attacker legitimately possesses for their own org.

### Recommendation
Bind the org used for signature verification to the org actually acted upon: after resolving the handler's target repository (`payload.dig('repository', 'full_name')`), verify that its owner matches `repository_owner`, or better, scope handler queries (e.g., `StatusHandler`) to only commits belonging to stacks whose `Repository#owner` equals the authenticated organization before writing any status/state.

### Proof of Concept
1. Shipit configured with two organizations, `org-a` (attacker-controlled, webhook installed with secret `S_A`) and `org-b` (victim, has a stack with required `ci.require: ["ci/build"]`).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim-org-b-commit-sha>",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` using their own org's secret and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies against `S_A` ` [7](#0-6) `.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim commit in `org-b`, and writes the forged `success` status for `ci/build`, satisfying `ci.require` for a deploy the attacker never had access to influence ` [4](#0-3) `.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

  end
