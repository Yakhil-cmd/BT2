### Title
Asset definer can front-run a spender's payment by updating the attestor list to retroactively freeze already-issued, spender-attested asset funds - (File: validation.js)

### Summary
The Sherlock report describes `BountyCore`/`OpenQV1` allowing the bounty issuer to unilaterally toggle `kycRequired`/`invoiceRequired`/`supportingDocumentsRequired` and front-run a claimant's transaction, causing the claimant's already-earned payment to be rejected. The equivalent unrestricted, single-party, real-time-mutable eligibility gate in ocore is the `spender_attested` attestor list of an asset: the asset definer can publish a new `asset_attestors` message at any time to redefine which addresses are allowed to hold/spend the asset, and this new list is applied retroactively to every future spend attempt, including spends of coins that were already legitimately issued/received before the list changed.

### Finding Description
When an asset is created with `spender_attested: true`, every subsequent transfer/issue of that asset requires both the input owner and output addresses to be in the "latest" attestor list, evaluated at spend-validation time: [1](#0-0) [2](#0-1) [3](#0-2) 

The attestor list itself is not fixed at asset-definition time; the definer can change it at any point via an `asset_attestors` message, which only requires that the asset requires attestors and that the author is the definer - there is no cooldown, no restriction preventing a change while other users' spends are pending, and no protection for already-issued balances: [4](#0-3) 

`storage.readAsset`/`filterAttestedAddresses` always resolve the attestor list to the single most-recent stable `asset_attestors` unit before `last_ball_mci`, so as soon as an updated list stabilizes, it governs every new spend, regardless of when the coins being spent were received: [5](#0-4) [6](#0-5) 

This mirrors the OpenQ pattern exactly: a privileged single party (the asset definer, analogous to the bounty issuer) can observe a pending spend by a counterparty (analogous to the claimant) in the DAG and race it with an `asset_attestors` update removing that counterparty's address, so that the counterparty's transfer of coins they already legitimately hold is rejected by validation once the new list becomes the "current" one, effectively freezing the counterparty's balance in that asset. The check happens at spend time rather than being fixed at the point the funds were earned/issued, exactly like `_eligibleToClaimAtomicBounty` re-evaluating `kycRequired` at claim time instead of at bounty-creation/completion time.

### Impact Explanation
A malicious or compromised asset definer can freeze arbitrary holders' balances of a `spender_attested` asset after the fact, by racing their spend transactions with attestor-list updates. Because the requirement is enforced on every subsequent spend (not just the issuance), users who received the asset in good faith, believing they were attested, can have their funds permanently locked with no recourse, since only the definer can restore the attestor list. This is an "AA/asset fund freezing" impact reachable by the asset issuer against any private-payment counterparty who holds the asset.

### Likelihood Explanation
The asset definer is inherently privileged only over their own asset's attestor list (as designed), but nothing prevents them from waiting for a spend to appear in the DAG (visible pre-stabilization) and racing it with an `asset_attestors` update, since attestor validation always uses the latest stable list rather than the list in effect when the coins were transferred to the victim. This requires only normal unit-posting capability by the definer and observation of the mempool/DAG, making it straightforward to execute against any targeted address.

### Recommendation
Bind the attestor eligibility check for a given spend to the attestor list that was in effect when the spender's input coins were received/issued (similar to how `address_definition_changes` are tracked relative to the attestation's own mci in `filterAttestedAddresses`), rather than always requiring the address to satisfy the *current* list at spend time. Alternatively, require a timelock/notice period before an `asset_attestors` update takes effect, so holders have a window to move already-received funds before new restrictions apply.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and initial attestors `[X]`. [7](#0-6) 
2. `D` issues/transfers units of `A` to address `U`, which is attested by `X` at that time; `U`'s balance validates fine per `validatePaymentInputsAndOutputs`. [8](#0-7) 
3. `U` later posts a payment spending those same coins of `A` to a third party.
4. `D` observes `U`'s unstable spend unit and races it with a new `asset_attestors` message removing `U`'s attestation (e.g., replacing attestor `X`'s scope or updating the list so `U` is no longer attested), authored solely by `D`: [9](#0-8) 
5. If `D`'s `asset_attestors` unit stabilizes with an mci at or before `U`'s spend's `last_ball_mci` window, `filterAttestedAddresses`/`readAsset` will use the new list, and `U`'s spend fails with "owner address is not attested", even though `U` legitimately held and was attested for the coins when received: [10](#0-9) 
6. `U`'s existing balance in asset `A` is now unspendable unless `D` chooses to restore `U` to the attestor list, at `D`'s sole discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],

			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
