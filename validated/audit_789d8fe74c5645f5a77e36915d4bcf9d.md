### Title
Stack-scoped API token can read build status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack (`stack_id` set), and `Api::BaseController` enforces that scope by resolving the target stack through the `stacks` collection, which is filtered to `current_api_client.stack_id` when present. `Api::CCMenuController` overrides the `stack` accessor and resolves it directly from `Stack.from_param!`, bypassing the scoping collection entirely, so a token authorized only for stack A can read CCMenu status data (build status, activity, last build label/time) of any other stack B.

### Finding Description
`Api::BaseController` defines the scoping primitives used by every other API controller: [1](#0-0) 

`stacks` is restricted to the client's authorized stack when `current_api_client.stack_id?` is true, and `stack` looks the requested id up through that scoped relation, so `Stack.from_param!` raises `RecordNotFound` for any stack outside the client's authorization - this is exactly the behaviour verified by the existing test "an api client scoped to a stack will only see that one stack" and mirrored correctly in `Api::StacksController#stack`: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that ignores the scoped `stacks` collection and resolves the model directly from the global `Stack` relation: [3](#0-2) 

The controller still calls `require_permission :read, :stack`, which only checks that the token carries the `read:stack` permission string - it never checks that the specific stack being requested is the one the token is bound to: [4](#0-3) 

So the binding that should hold - "the stack a token authorizes == the stack it touches" - is broken specifically in this controller. A token created via `CCMenuUrlController`, which explicitly mints stack-scoped tokens (`permissions: %w[read:stack]`, bound implicitly to a given stack workflow), or any token administratively scoped to a single stack (fixture `here_come_the_walrus`, `stack: shipit`, `permissions: ['read:stack']`) can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for a different `stack_id` and will succeed. [5](#0-4) 

### Impact Explanation
This is a High-severity authorization escalation: an attacker holding a stack-scoped API token (e.g. leaked via the `CCMenuUrlController#fetch` URL, which embeds the token in a query string) can read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, activity) of every stack in the Shipit instance, not just the one the token was issued for. This matches the "unauthenticated/unauthorized read of stack state" impact category, since the token's authorization is scoped by design but the controller fails to enforce that scope.

### Likelihood Explanation
Likelihood is high for anyone who already possesses a legitimately-scoped, low-privilege token: CCMenu tokens are routinely embedded in CI dashboard URLs (`CCMenuUrlController#fetch` builds and returns a URL containing `token=...` in cleartext), so exposure of one such token (e.g. via browser history, logs, or a shared dashboard) is a realistic scenario. Exploitation requires no code execution or additional privileges - just changing the `stack_id` path parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (as `Api::StacksController` does), e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This will cause `stacks.from_param!` to raise `RecordNotFound` (rendered as 404) for stacks outside the token's authorized scope, consistent with the rest of the API.

### Proof of Concept
1. Obtain (or create via `CCMenuUrlController#fetch`) an `ApiClient` token scoped to stack A (`stack_id` set, `permissions: ['read:stack']`).
2. Send `GET /api/stacks/<stack-B-id>/ccmenu.xml` with `Authorization: Basic <base64(token)>` (or `?token=<token>`), where stack B is a different, unauthorized stack.
3. Observe `200 OK` with stack B's CCMenu XML payload (name, lastBuildStatus, etc.), despite the token only authorizing stack A - confirmed by contrast with `Api::StacksController#show`, which correctly returns 404/not-found for the same cross-stack request pattern.
