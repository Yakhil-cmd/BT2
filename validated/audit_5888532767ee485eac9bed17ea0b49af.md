### Title
Aquarius LP collateral valuation reads live pool reserves, allowing same-transaction reserve skew to force liquidations - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The price aggregator derives the collateral value of Aquarius LP share tokens from the pool's *current* reserves (`get_reserves`) and total shares inside a single transaction. An unprivileged attacker can skew the reserves of an Aquarius pool with their own swap immediately before calling `liquidate`, depressing the reported LP price and pushing LP-collateralized positions below the liquidation threshold. This is the same class as the USSD `slot0` spot-price finding, mapped onto XOXNO's LP collateral pricing.

### Finding Description
`read` in `contracts/price-aggregator/src/providers/aquarius.rs` (lines 69-131) fetches `(reserve_a, reserve_b)` via `aquarius_pool_reserves_call` and `total_shares` via `aquarius_total_shares_call`, then computes:

- constant-product: `fair_lp_price_wad` = `2 * sqrt(value_a * value_b) / share_supply_wad` (`common/src/oracle/lp.rs` lines 57-87)
- stable: `fair_stable_lp_price_wad` = `D * min(price_a, price_b) / share_supply_wad` (`common/src/oracle/lp_stable.rs` lines 80-109)

Both formulas are "fair value" formulas, which prevents *upward* manipulation — but they still move *downward* when reserves are skewed. For a constant-product pool, `2*sqrt(va*vb)` is strictly less than the balanced value `va + vb`, and drops monotonically as the reserve ratio is pushed away from the true market ratio. For a stable pool, the solved invariant `D` shrinks as the pool becomes imbalanced. Since swaps on Aquarius are permissionless and Soroban executes cross-contract calls atomically, the manipulated reserve state is exactly what `get_reserves` returns inside the liquidation transaction.

LP tokens are registered as collateral-bearing markets (e.g., `XLMUSDC_LP`, `XLMAQUA_LP` in `configs/mainnet/markets.json` lines 1198-1230 and 1574-1590, each sourced from a single `AquariusLp`/`AquariusStableLp` source with `tolerance` ratios of 0). The controller consumes the aggregator's strict price for health-factor computation, so a depressed LP price directly lowers the HF of every position holding that LP collateral.

### Impact Explanation
Theft of user funds via unjust liquidation. An attacker holding no privileged role can drive the LP oracle price down far enough (within the wide configured sanity bands, e.g., XLMUSDC_LP `min_sanity_price_wad = 0.45e18` to `max_sanity_price_wad = 2.5e18`) to push a victim's health factor below 1, then call `liquidate` and seize collateral at the HF-based bonus. The cost is swap fees plus slippage on the skewing trade, partially recoverable by swapping back in the same transaction; the liquidation bonus is pure profit. With a flash-funded swap (the controller's own `flash_loan`/`flash_position` or an external source), capital requirements are minimal.

### Likelihood Explanation
Medium. Requires an Aquarius LP token used as collateral with sufficient open borrow positions, and a pool shallow enough that a profitable skew exists within the sanity band. `min_pool_value_wad` floors (e.g., 1e24 ≈ $1M pool value) mitigate dust pools but do not prevent reserve-ratio skew in a $1M pool. No access control, whitelist, or staleness check stands between the attacker's swap and the reserve read — the observations carry `timestamp` from the leg feeds, not from the pool read, so freshness checks never apply to the reserve component.

### Recommendation
Make the LP valuation insensitive to intra-transaction reserve manipulation:

- Read reserves with a time-weighted or lagged mechanism (e.g., Aquarius TWAP/cumulative reserves if available, or a min-over-window reserve cache), or
- Cross-check the computed LP price against a reserve-ratio-free bound: price the share as `supply_weighted_min` using each leg's oracle price and a governance-set invariant ratio, rejecting reads whose implied reserve ratio deviates beyond a tight band from a stored last-good ratio, or
- At minimum, add a `max deviation` check comparing the current reserve ratio against a persisted previous ratio updated with a cooldown, so a same-block skew is rejected.

### Proof of Concept
1. Victim supplies `XLMUSDC_LP` as collateral and borrows USDC; HF ≈ 1.05.
2. Attacker obtains a large amount of XLM via `flash_loan` (or own capital).
3. In one transaction: swap XLM→USDC on the Aquarius XLM/USDC pool, skewing reserves so `value_a >> value_b`.
4. `liquidate(victim)` → aggregator `read` → `aquarius_pool_reserves_call` returns skewed reserves → `fair_lp_price_wad` = `2*sqrt(va*vb)/shares` is materially below the true share value → victim HF < 1 → collateral seized with bonus.
5. Swap back to restore the pool and repay the flash loan; keep the liquidation bonus.
