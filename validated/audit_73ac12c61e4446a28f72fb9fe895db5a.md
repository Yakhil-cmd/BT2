### Title
Unauthenticated forgery of GitHub webhooks when `webhook_secret` is unset grants team-based authorization bypass - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats an absent/blank `webhook_secret` as "signature verified" instead of "cannot verify, reject," letting anyone POST arbitrary, unsigned webhook events to the public `/webhooks` endpoint and have them processed as authentic GitHub events.

### Finding Description
`WebhooksController#verify_signature` selects the app config for the organization named in the payload and delegates verification: `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [2](#0-1) . The implementation is:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

If the organization's `webhook_secret` config key is nil/blank — which the setup docs and templates present as an optional field (`webhook_secret:` left empty is a supported/shown configuration in `template.rb` and `test/dummy/config/secrets_double_github_app.yml:46`) — the method unconditionally returns `true`, i.e. "verified," rather than failing closed. The binding broken is: *organization that "signed" the webhook* (should always be cryptographically proven) vs. *organization the code treats as having signed it* (accepted with zero proof when the secret is unset). This is the same class of defect as the reported bug — a default/uninitialized sentinel (`nil` secret) that is silently accepted as a valid state instead of being rejected — applied to a security check instead of an array index.

With signature verification bypassed, an unauthenticated attacker can POST a forged `membership` event. `MembershipHandler#process` finds-or-creates a `Team`/`User` purely from attacker-supplied payload fields and calls `team.add_member(member)` with no cross-check against actual GitHub team membership [4](#0-3) . `User#authorized?` — the gate used by `force_github_authentication` for every controller action — trusts exactly this local `Membership` record: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) , and `force_github_authentication` calls it directly to decide access [5](#0-4) .

### Impact Explanation
An attacker with no credentials can forge a `membership` webhook that adds an arbitrary GitHub user (including one they already control an OAuth-authenticated session for) to a `Team` whose `github_id`/`handle` matches one of `Shipit.github_teams`. Once that `Membership` row exists, `authorized?` returns true for that user on their next real OAuth login, escalating them into the application's authorization boundary without ever having been a genuine member of an authorized GitHub team. This matches the listed High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires only that the deployed instance leaves `webhook_secret` unset for the targeted organization — a state the shipped templates/examples present as valid/optional (`template.rb`'s generated `secrets.yml` ships `webhook_secret:` blank by default, and the test fixture `test/dummy/config/secrets_double_github_app.yml` explicitly comments `webhook_secret: # nil`), so this is a realistic, easy-to-hit misconfiguration rather than a deliberate opt-out of a documented mandatory control. No authentication, token, or repository access is needed to exploit it — an unprivileged actor need only know the target's `/webhooks` URL and one existing GitHub team `id`/`slug` used in `Shipit.github_teams`.

### Recommendation
Fail closed: `verify_webhook_signature` should return `false` (or the controller should reject with `422`) when `webhook_secret` is blank, rather than treating an unset secret as an implicit pass. Additionally, `webhook_secret` should be enforced as a required configuration value at boot for every configured organization.

### Proof of Concept
1. Deploy Shipit with an organization config that omits `webhook_secret` (as shown as valid in `template.rb`'s generated secrets and `test/dummy/config/secrets_double_github_app.yml`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": {"id": <id-of-a-team-in-Shipit.github_teams>, "name": "T", "slug": "t", "url": "https://x"},
  "organization": {"login": "org"},
  "member": {"login": "attacker-github-login"}
}
```
3. `verify_signature` calls `verify_webhook_signature`, which returns `true` because `webhook_secret` is nil [6](#0-5) ; the request proceeds to `create`, and `MembershipHandler#process` creates/updates the `Membership` [4](#0-3) .
4. Attacker logs in via the normal GitHub OAuth flow as `attacker-github-login`; `User#authorized?` now returns `true` due to the forged `Membership`, granting full application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
