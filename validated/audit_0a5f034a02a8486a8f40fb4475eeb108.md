Based on my investigation, I found a concrete binding-break analogous to the report's access-control gap: the webhook signature-verification step selects which GitHub organization's secret to check against using a field from the *same unauthenticated request* that determines *which repository the handlers will act on*, and multi-org installations may leave some orgs' `webhook_secret` unset — causing `verify_webhook_signature` to trivially return `true`.

### Title
Webhook signature verification is keyed off an attacker-controlled organization field, allowing forged webhooks against any org with no configured `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives the GitHub organization used to look up the HMAC secret directly from the untrusted request body, rather than from a value that has already been cryptographically bound to a specific installation. Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever `webhook_secret` is blank, this creates the same class of trust-binding failure described in the analog report: a value used to authorize an action (which org's secret gates this webhook) is not equal to, and is not securely bound to, the value that the resulting handler logic actually acts on (which repository/stack gets synced, which team/membership gets created).

### Finding Description
`verify_signature` computes the organization to authenticate against purely from the JSON payload: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)` and then verifies the signature using that organization's `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that organization (`return true unless webhook_secret`). In multi-organization configurations (as shown in `config/secrets.development.shopify.yml`, where each org has its own `webhook_secret` that can be nil), this means: for *any* org configured without a `webhook_secret`, an attacker who knows (or guesses) that org's login can send a completely unsigned/forged webhook request, set `repository.owner.login` (or `organization.login`) to that unsecured org, and pass signature verification trivially — regardless of what `X-Hub-Signature` header (or lack thereof) is sent.

Once verification "passes", the handlers dispatched via `Shipit::Webhooks.for_event` operate on data pulled from the same forged payload, e.g. `PushHandler` resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) 

and `MembershipHandler` creates/mutates `Team` and `Membership` records straight from payload fields: [6](#0-5) 

The binding that should hold is: *the organization whose secret authorized this webhook* == *the organization/repository the webhook payload is permitted to mutate*. Because `repository_owner` is attacker-supplied and the "authorization" (secret check) can be a no-op for a misconfigured/legacy org while `repository.full_name` used by handlers is independently attacker-controlled within the same payload, this binding is not enforced by any single verified value — it is enforced only if every configured org happens to have a non-blank `webhook_secret`, which is not guaranteed by the code and is explicitly supported as an optional/nil value in the documented configuration.

### Impact Explanation
If any organization onboarded into Shipit's multi-org `github:` config lacks a `webhook_secret` (an explicitly supported configuration state, shown as `webhook_secret: # nil` in `config/secrets.development.shopify.yml` and `docs/setup.md`), an unauthenticated attacker can:
- Trigger `PushHandler`/`StatusHandler`/`CheckSuiteHandler` logic against arbitrary stacks by crafting `repository.full_name` for a target repo while setting `repository.owner.login` to the unsecured org, enqueuing `GithubSyncJob`/`RefreshCheckRunsJob` and influencing merge/deploy readiness signals used for automatic deploys.
- Forge `membership` events to create arbitrary GitHub teams and add/remove arbitrary users' memberships (`Team#add_member`, `Membership.delete`), which is a direct path to `Shipit.github_teams` authorization escalation — a listed High-severity impact — since team membership drives `User#authorized?`.

This satisfies the "escalation into `Shipit.github_teams` authorization" and "unauthorized deploy" impact classes required by the rules.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: exploitation requires at least one configured GitHub organization with a blank/unset `webhook_secret`. This is a supported, documented configuration (not a hypothetical), and the engine provides no enforcement that all orgs must have a secret configured, nor any warning/rejection when `webhook_secret` is absent — the code path silently treats "no secret" as "signature verified." Because the routing decision (which org's secret to check) is taken from the same untrusted payload later used to decide what gets mutated, the two are not equality-bound, which is the exact class of flaw the analog scan targets.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization (fail fast at boot/config-load time if any org is missing one), removing the "trivially verified" fallback in `GitHubApp#verify_webhook_signature`.
- Do not select the verification secret purely from unauthenticated payload fields without cross-checking that the resulting repository actually belongs to that same organization (validate `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before trusting either).
- Consider deriving `repository_owner` in a way that is validated against Shipit's own `Repository` records (owner is already tracked) before ever attempting signature verification with per-org secrets, so a forged payload naming an unrelated repository cannot ride on a different org's leniency.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, e.g. `securedorg` (has `webhook_secret: <secret>`) and `legacyorg` (has `webhook_secret: nil`), both installed and tracked by Shipit stacks/repositories.
2. Send a POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or an arbitrary bogus one), body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "legacyorg" },
  "member": { "login": "attacker-controlled-user" },
  "repository": { "owner": { "login": "legacyorg" }, "full_name": "securedorg/some-target-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "legacyorg")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` immediately without checking any HMAC — the request is accepted (`head(:ok)` never triggered by 422).
4. `MembershipHandler#process` runs unconditionally, creating/updating a `Team` and adding `attacker-controlled-user`'s membership, independent of `securedorg`'s real webhook secret — demonstrating cross-organization/cross-repository trust-binding failure exploitable without any credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
