Confirmed. This is a genuine, exploitable logic bug caused by Ruby operator precedence in `provision?`.

### Title
`provision?` fails to gate `prevent_with_label`/`allow_with_label` behaviors on `review_stacks_enabled`, allowing unauthorized review stack creation - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` intends to require `repository.review_stacks_enabled == true` before any stack is auto-provisioned from a pull request, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to gate only the `allow_all` branch. The `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, so a repository with review stacks disabled but `provisioning_behavior: prevent_with_label` will still auto-create and provision a `Shipit::ReviewStack` for any opened, unlabeled pull request.

### Finding Description
The broken binding: `repository.review_stacks_enabled == true` should be required for stack creation for **all** provisioning behaviors, but is actually only enforced as `(repository.review_stacks_enabled == true) == (allow_all branch gated)`; the other two branches have no such gate.

Code path:
- `respond_to_pull_request_opened?` calls `provision?` [1](#0-0) 
- `provision?` is parsed by Ruby as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`, since `&&` binds tighter than `||` [2](#0-1) 
- When `review_stacks_enabled == false` and `provisioning_behavior == 'prevent_with_label'`, and the PR carries no provisioning label, the third clause `(prevent_with_label? && !has_label?)` alone evaluates `true`, making `provision?` return `true` regardless of `review_stacks_enabled`.
- `process` then unconditionally calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, persisting a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled) and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) .

Attacker's exact request: fork the target repository, push a branch (name can be attacker-chosen, e.g. containing shell-like text since `branch` is stored as a plain string), open a PR with no labels. GitHub sends `pull_request` `opened` webhook with a validly signed payload (signed by GitHub, not the attacker's secret — signature verification passes because it's a legitimate GitHub-originated webhook for a repo the attacker can freely open PRs against). No forged signature or stolen secret is needed; the attacker only needs the ability to open a PR against a repository they don't otherwise control provisioning settings for.

Existing guards fail to stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` and `ExplicitParameters` schema validate the payload shape and origin, not the provisioning semantics; `respond_to_pull_request_opened?` delegates entirely to the broken `provision?`; there is no separate check re-verifying `review_stacks_enabled` before `ReviewStackAdapter#find_or_create!` runs. The existing test suite corroborates the gap: the test for `prevent_with_label` with an absent label never sets `review_stacks_enabled: false` [4](#0-3) , and the only test disabling provisioning uses `behavior: :allow_all` [5](#0-4) , so the `review_stacks_enabled == false` + `prevent_with_label` combination is untested and unguarded.

### Impact Explanation
An unauthorized `Shipit::ReviewStack` record is created and queued for provisioning on a repository whose owner explicitly left `review_stacks_enabled: false` — i.e., never opted in to running PR-triggered infrastructure. Provisioning a review stack ultimately drives deployment tooling to check out and execute the attacker's branch content (`shipit.yml`/build/deploy scripts) on the deploy host, which is unauthorized code execution against a repository configuration that intentionally disabled this feature. This is repeatable against any repository configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label`, for the label-present case) and `review_stacks_enabled: false`, by any GitHub user able to open a PR against that repo (including forks, depending on the org's fork PR policy). This matches the Critical category: unauthorized deploy/provisioning action performed for a repository that did not authorize it.

### Likelihood Explanation
Preconditions are configuration-only and plausible: a repository operator sets `provisioning_behavior` to `prevent_with_label` (or `allow_with_label`) while leaving `review_stacks_enabled` off (e.g., during a rollout, or as a deliberate "off" state distinct from the provisioning-behavior enum). No secrets, tokens, or elevated GitHub permissions are needed — only the ability to open a pull request, which is the normal contributor workflow this feature is designed to react to. The bug fires on every "opened" webhook meeting these conditions, making it fully repeatable and low-cost to trigger.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire disjunction, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix pattern check to any sibling logic that mixes `review_stacks_enabled` with the provisioning-behavior branches (e.g., `LabeledHandler`/`UnlabeledHandler`, which already correctly `&&`-chain `review_stacks_enabled` at the top level of `respond_to_label_change?` and should be used as the reference pattern) [6](#0-5) .

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (using existing `configure_provisioning_behavior` helper):
```ruby
test "does not create stacks when review_stacks_enabled is false even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # repository.review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no provisioning label present

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::ReviewStack.count` increases by 1 (bug reproduced — `review_stacks_enabled == false` does not prevent creation). After applying the parenthesization fix, the assertion passes with no difference, confirming `review_stacks_enabled == false` correctly blocks provisioning for all `provisioning_behavior` values, not just `allow_all`.
