### Title
`is_valid_sig` / `is_valid_signed_package` Provide No Built‑In Domain Separation, Enabling Cross‑AA/Cross‑Network Signature Replay - ([File: formula/evaluation.js], [File: signed_message.js], [File: object_hash.js])

### Summary
Obyte's oscript primitives `is_valid_sig` and `is_valid_signed_package` let an AA verify that a given address (or PEM key) signed an arbitrary caller‑supplied message. Just like the `Revolver.joinGame()` bug, the byte payload that gets hashed and verified contains no protocol‑level binding to "domain" data — no chain/network id, no reference to the specific AA address that is checking the signature (`trigger.address`/`address(this)` equivalent), and no session/round identifier. All of that must be manually embedded by the AA author inside the `message` (for `is_valid_sig`) or `signed_message` field (for `is_valid_signed_package`). Any AA that reproduces the exact pattern from the report — hashing only `(uid, user, parameter)`‑style data and trusting a backend/oracle address — inherits the same cross‑deployment/cross‑round replay weakness.

### Finding Description
`is_valid_sig(message, pem_key, sig)` in `formula/evaluation.js` verifies `evaluated_signature` against `evaluated_message` and `formatted_pem_key` with `signature.verifyMessageWithPemPubKey`, with no reference at all to `trigger.address`, `mci`, or the network. [1](#0-0) 

`is_valid_signed_package(signed_package, address)` delegates to `signed_message.validateSignedMessage`, which only confirms that `address` (chosen by the AA author) signed the `signed_message` field and that `authors[].definition` hashes to that address; the resulting `unit_hash_to_sign` is derived from `objectHash.getSignedPackageHashToSign`, which hashes only `signed_message`, `authors` (without authentifiers), `last_ball_unit`, `version`, and `timestamp` — nothing that ties the package to the specific AA that will consume it, nor to the network the unit lives on. [2](#0-1) [3](#0-2) [4](#0-3) 

Because address derivation in ocore (`getChash160`) is network‑agnostic — the same private key controls the same address on livenet and on any test/private network — a signature/signed package created for one deployment context is valid verbatim in another, exactly mirroring the `joinGame()` flaw where `keccak256(uid, msg.sender, cellId)` omitted `block.chainid`, `address(this)`, and `currentRoundId`.

### Impact Explanation
If two or more AAs (e.g., a testnet clone and a mainnet AA, or two rounds/instances of the same game-style AA) rely on the same trusted backend/oracle address and use `is_valid_sig`/`is_valid_signed_package` with a message payload that does not itself encode the consuming AA's address, asset, or round, an attacker can capture a legitimately issued signature/package from one AA (or an earlier round) and replay it against another AA that shares the same trusted signer address. This can unlock AA logic gated on "backend approved this action" (e.g., releasing funds, granting entries, unlocking a payout) that was never intended for that AA/round, leading to unauthorized fund release/loss for the AA relying on this pattern.

### Likelihood Explanation
Exploitation requires an AA author to write oscript in the same vulnerable style as the reported `Revolver.joinGame()` (signing only `(uid, address, param)`-type data without embedding `trigger.address`, `params.round`, or a nonce) and to reuse the same off-chain signer across multiple AAs/rounds/networks — a common and natural pattern for bot/oracle-gated AAs. Any unprivileged unit poster who can obtain or intercept a previously-issued signed message/package for that signer (e.g., from a public unit, another AA's trigger data, or a different network) can trigger the vulnerable AA with the replayed payload; ocore performs no automatic anti-replay/domain binding for these primitives.

### Recommendation
- Document and, where feasible, enforce that any oscript usage of `is_valid_sig`/`is_valid_signed_package` for authorization purposes must include an explicit domain-separation payload inside the signed message: at minimum `trigger.address` (the AA's own address), an application/version tag, and a monotonically increasing nonce/round identifier maintained in AA state.
- Consider extending `getSignedPackageHashToSign` (and the `is_valid_signed_package` calling convention) to optionally bind the hash to the verifying AA's address and to the network (e.g., genesis unit hash) so that off-chain signed packages are not trivially portable between AAs/networks by default.
- Add prominent guidance/lint warnings in AA development docs for the `is_valid_sig`/`is_valid_signed_package` primitives, similar to EIP-712 recommendations, so AA authors don't reproduce the exact anti-pattern seen in `Revolver.joinGame()`.

### Proof of Concept
1. Off-chain backend signs `message = uid + "|" + user_address + "|" + param` and delivers it to a user for AA "GameA" (round 1) via `is_valid_sig`/`is_valid_signed_package(trigger.data.package, backend_address)`.
2. The same backend address also backs AA "GameB" (a second round/deployment/testnet instance) with an identical oscript check `is_valid_signed_package(trigger.data.package, backend_address)` but no additional domain fields in the signed message.
3. An unprivileged user captures the signed package/signature from step 1 (visible on-chain as part of the trigger unit's `data`) and resubmits it unchanged as trigger data to "GameB".
4. Because neither `is_valid_sig` nor `is_valid_signed_package`/`validateSignedMessage` bind the signature to the specific AA address or round, "GameB" accepts the replayed authorization and executes the gated logic (e.g., credits an entry or releases funds) that the backend never intended for that deployment/round.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
