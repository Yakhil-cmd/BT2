### Title
MultiEdit `_extract_field` space-joins per-edit fragments, letting attackers bypass secret/pattern-matching hookify rules by splitting the payload across two `edits` entries - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`_extract_field` builds the `new_text`/`content` value for a `MultiEdit` tool call by doing `' '.join(e.get('new_string', '') for e in edits)`, inserting an artificial space between each edit's `new_string` fragment. Because the actual file produced by `MultiEdit` concatenates the edits' replacement text with no such separator (each edit is an independent string replace at its own location), an attacker can split a blocked token (e.g. `API_KEY`) across the boundary of two edits so the synthesized, space-joined string used for rule evaluation no longer matches `contains`/`regex_match` patterns that require adjacency, even though the resulting file on disk contains the unbroken secret/pattern.

### Finding Description
`RuleEngine._check_condition` calls `_extract_field(condition.field, ...)` and then evaluates the operator (`contains`, `regex_match`, etc.) against the returned string [1](#0-0) . For `MultiEdit`, `_extract_field` concatenates all edits' `new_string` values with `' '.join(...)` rather than `''.join(...)`: [2](#0-1) 

This concatenation is purely an artifact of the rule engine — it does not reflect how `MultiEdit` actually mutates the target file. Each entry in `edits` performs an independent string replacement at its own `old_string` location; there is no guarantee (or requirement) that a literal space separates the resulting text from adjacent edits, so the real post-edit file content can have the two fragments directly adjacent (e.g., `API_KEY=xxxx` written contiguously by two edits that each contribute half the token).

The plugin's own documented rule format explicitly relies on holistic matching against `new_text` for exactly this kind of secret-detection use case, e.g. the sensitive-files/API-key rules: [3](#0-2) [4](#0-3) 

An attacker (i.e., whatever content/instructions drive the agent to issue the `MultiEdit` tool call) can split a token like `API_KEY` so that one edit's `new_string` ends with `API_` and the next edit's `new_string` begins with `KEY=secretvalue`. `_extract_field` returns `"...API_ KEY=secretvalue..."` (space injected at the join point), which fails a `contains: API_KEY` or an adjacency-sensitive `regex_match` such as `(API_KEY|SECRET|TOKEN)\s*=\s*["']` check anchored without permissive whitespace before the token — the pattern is only evaluated against the artificially-spaced string, not the real resulting file text, so the rule silently fails to trigger even though the on-disk file will contain the unbroken sensitive pattern.

### Impact Explanation
This is a hook/guard-evasion bug: an author-configured `hookify` rule intended to block or warn on sensitive-file/secret edits (`field: new_text`, `operator: contains|regex_match`) can be bypassed purely by how the `MultiEdit` payload is chunked into `edits`, without needing any privilege escalation. The impact is a secret-leaking or otherwise guarded edit reaching disk undetected — the exact "hook enforcement bypass leading to unauthorized file mutation / secret disclosure" class of impact the Claude Code bounty program targets. Severity is bounded by the fact that it only defeats a locally author-configured guard rule (not a built-in Claude Code safety boundary), but it does defeat the specific protection the rule was written to provide.

### Likelihood Explanation
Requires only: (1) an existing hookify rule using `field: new_text` (or `content`) against `MultiEdit`, matching the plugin's own documented and recommended pattern, and (2) any code path that causes the agent to issue a `MultiEdit` call with the sensitive token split across the join boundary of two `edits` entries. No special permissions are needed to trigger this — it is a pure parsing/concatenation defect in `_extract_field`, so it is fully reproducible and deterministic once the edits are shaped this way.

### Recommendation
Change the `MultiEdit` concatenation in `_extract_field` from `' '.join(...)` to `''.join(...)` so the field used for rule matching mirrors how `new_string` fragments actually compose in the resulting file, removing the artificial separator that can desynchronize pattern matches from real file content. Additionally, consider evaluating rules against the *post-edit* file content (reconstructed from `old_string`/`new_string` application) rather than a naive join of `new_string` values, to also catch patterns that straddle unedited (`old_string`) regions.

### Proof of Concept
Unit test targeting `RuleEngine._extract_field` / `evaluate_rules`:
```python
def test_multiedit_split_bypasses_contains_rule():
    rule = Rule(
        name="warn-env-file-edits",
        enabled=True,
        event="file",
        action="warn",
        conditions=[
            Condition(field="file_path", operator="regex_match", pattern=r"\.env$"),
            Condition(field="new_text", operator="contains", pattern="API_KEY"),
        ],
        message="Sensitive key detected",
    )
    engine = RuleEngine()
    input_data = {
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": ".env",
            "edits": [
                {"old_string": "X1", "new_string": "API_"},
                {"old_string": "X2", "new_string": "KEY=supersecretvalue"},
            ],
        },
    }
    result = engine.evaluate_rules([rule], input_data)
    # BUG: extracted field is "API_ KEY=supersecretvalue" (space injected),
    # so `contains: API_KEY` fails to match even though the real .env file
    # will contain the contiguous "API_KEY=supersecretvalue" once both edits apply.
    assert result != {}, "Rule failed to trigger due to artificial space injected by ' '.join in _extract_field"
```
Expected (buggy) behavior today: `result == {}` (rule bypassed). After fixing to `''.join(...)`, the extracted field becomes `"API_KEY=supersecretvalue"`, the `contains` check matches, and `result` contains the warning message.
