### Title
Deploy trigger API does not enforce the `deploy_variables` environment whitelist before spawning shell commands - ([File: app/controllers/shipit/api/deploys_controller.rb])

### Summary
The external report's bug class is: a function is supposed to only use a bounded/whitelisted amount of a resource, but the enforcement of that bound is inconsistent across code paths, letting more than intended leak through. In Shipit, the equivalent binding is: **environment key *permitted* by `Stack#filter_deploy_envs`/`Stack#filter_rollback_envs` (the `deploy.variables`/`rollback.variables` whitelist from `shipit.yml`) must equal the environment key that is ultimately *spawned* into the deploy shell process by `Shipit::Command`**. This binding is enforced asymmetrically between the rollback and deploy trigger paths.

### Finding Description
`Api::RollbacksController#create` explicitly filters user-supplied `env` through the whitelist before use: [1](#0-0) 

`Api::TasksController#trigger` relies on `stack.trigger_task`, which is proven (by test) to reject env keys not present in the task's `variables` whitelist: [2](#0-1) 

However `Api::DeploysController#create` passes the raw, attacker-controlled `params.env` Hash straight through to `stack.trigger_deploy`, with no call to `stack.filter_deploy_envs` at the controller layer: [3](#0-2) 

The whitelist itself is defined by `Shipit::EnvironmentVariables#permit`, which raises `NotPermitted` for any key not in the `variable_definitions` (i.e. `deploy.variables` from `shipit.yml`): [4](#0-3) 

`Api::BaseController` rescues `EnvironmentVariables::NotPermitted` globally, which is the only place this constraint is supposed to be enforced for API-triggered actions: [5](#0-4) 

Whatever ends up on `Deploy#env` is merged, with the *highest* precedence, into the final process environment by `TaskCommands#env`, which is then handed to `Shipit::Command`: [6](#0-5) 

`Shipit::Command` merges that `@env` hash directly on top of the unbundled base environment and passes it to `PTY.spawn`, with no key restriction at that layer either: [7](#0-6) 

Because the equality "permitted env key == spawned env key" is only enforced by an explicit call to `filter_deploy_envs`/`filter_envs`, and the deploy-trigger controller path does not perform that call before storing `env` on the `Deploy` record, an unlisted/arbitrary environment variable name supplied via the API (e.g. `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `GIT_SSH_COMMAND`) can reach the spawned deploy process environment, letting the caller influence code executed by any Ruby/Bundler/Git invocation inside the deploy script — this is a well known env-var-to-code-execution primitive independent of `shipit.yml` script content.

### Impact Explanation
If confirmed that `Stack#trigger_deploy` does not itself call `filter_deploy_envs` before persisting `env` on the `Deploy`/`Task` record, an API client holding only the `deploy:stack` permission (intended to just let CI/CD trigger deploys of vetted `shipit.yml` steps) could inject unauthorised environment variables into the deploy host's process environment, achieving code execution on the deploy host — a Critical impact per the scoring rubric (RCE on the deploy host / unauthorized deploy behavior).

### Likelihood Explanation
Any client already holding a `deploy:stack` `ApiClient` token could exploit this without further privilege escalation, by simply setting `env` on the deploy-trigger request. This is a low-effort, high-impact escalation *if* the described gap is real.

### Recommendation
Confirm whether `Shipit::Stack#trigger_deploy` internally calls `filter_deploy_envs` on the `env:` keyword before creating the `Deploy` record. If it does not, apply the same explicit filtering pattern used in `Api::RollbacksController#create` (`stack.filter_rollback_envs(params.env)`) to `Api::DeploysController#create` (`stack.filter_deploy_envs(params.env)`), so that the permitted-variable whitelist is enforced uniformly for every trigger path (deploy, rollback, custom task) before the value is ever persisted or interpolated into a spawned command's environment.

### Proof of Concept
Not independently executable from static analysis alone — this requires confirming `Stack#trigger_deploy`'s implementation, which was not retrievable within the indexed context (the file `app/models/shipit/stack.rb` content beyond grep match counts was not available to me). **This is the key open uncertainty**: I found 8 references to `filter_deploy_envs`/`filter_rollback_envs`/`filter_envs` inside `app/models/shipit/stack.rb`, which is circumstantial evidence that `trigger_deploy` *may* already perform this filtering internally — in which case the asymmetry I observed at the controller layer would be harmless (defense-in-depth only, not a real gap). I could not confirm this either way with the tools available in this session.

**Recommendation before treating this as confirmed:** have a Devin session read `app/models/shipit/stack.rb` in full (specifically `trigger_deploy`, `trigger_task`, `build_deploy`) and `test/models/stack_test.rb`/`test/controllers/api/stacks_controller_test.rb` to determine definitively whether unwhitelisted `env` keys passed to `POST /api/stacks/:id/deploys` are rejected the same way they are for `POST /api/stacks/:id/tasks/:task_name` and rollbacks. If no such rejection exists for deploys, the finding above stands as described.
