### Title
i128 overflow in accrual (`scaled_to_original`) permanently freezes all funds in a whale-sized market — (File: common/src/rates/scaling.rs)

### Summary
The Ghostscript report is a buffer-overflow DoS: a memory-safety fault crashes the process. The analog in this codebase is an `i128` overflow in index-value arithmetic that traps during interest accrual. Because every state-changing entrypoint runs `global_sync` (accrual) first, once the total borrowed/supplied RAY value exceeds `i128::MAX`, every verb — `withdraw`, `repay`, `liquidate`, `update_indexes` — panics with `MathOverflow` before doing any work. The market is bricked forever: no unwind path exists because the failing multiplication happens inside the accrual preamble itself, and the `MAX_BORROW_INDEX_RAY` cap never engages because the value overflow triggers first.

### Finding Description
Accrual computes `total_borrowed = scaled_to_original(borrowed, borrow_index)` via `Ray::mul` → `mul_div_half_up`, which returns `None`/panics with `GenericError::MathOverflow` when `borrowed * borrow_index / RAY` does not fit `i128` (common/src/rates/scaling.rs:14-16, common/src/math/fp_core.rs:122-143). The borrow index is capped at `MAX_BORROW_INDEX_RAY` in `update_borrow_index` (common/src/rates/index.rs:13-19), but the cap is irrelevant: with a large enough scaled `borrowed` base, `borrowed * index / RAY` overflows at a much smaller index (value ceiling ≈ `i128::MAX` ≈ 170e12 RAY-units), long before the index cap is reached. The same applies to `update_supply_index` (`supplied.mul(old_index)` at index.rs:34) and `calculate_supplier_rewards` (`borrowed.mul(new_borrow_index)` at index.rs:80-81) — all inside `accrue_step`, invoked from `global_sync` (contracts/pool/src/interest.rs:20-53), which every pool op calls before touching balances.

### Impact Explanation
Permanent freezing of funds. Once `borrowed * borrow_index` crosses `i128::MAX`, `global_sync` panics on every subsequent call, so suppliers can never withdraw, borrowers can never repay, liquidators can never liquidate, and `update_indexes` itself fails — there is no administrative or user-level escape since accrual is the first thing each op does. All supplied tokens in that pool book are locked indefinitely. The codebase's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361) demonstrates exactly this: after sustained ~98% utilization on the steep XLM rate curve, `try_update_indexes`, `try_withdraw`, and `try_repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.

### Likelihood Explanation
Reachable by an unprivileged address but requires substantial capital and time. The attacker must (a) supply and borrow enough of an 18-decimal asset that scaled `borrowed` is within ~170x of the `i128::MAX` RAY ceiling, and (b) hold high utilization on a steep rate curve so the borrow index compounds toward the cliff (the test uses `lift_caps`, a privileged cap raise — without it, listing caps bound `borrowed` via `require_cap_within_asset_domain`, but the cap ceiling is defined as exactly the largest balance `Ray::from_asset` can represent, i.e. the same i128 boundary, so a max-cap market still reaches the cliff). Time-to-freeze depends on the rate curve; the test bounds it under 40 years. This is a griefing/lockup condition rather than something an attacker profits from directly, but the impact (irreversible freeze of an entire market's funds) is in-scope.

### Recommendation
Use saturating or explicit-cap arithmetic on the value side, not just the index side: e.g., clamp `borrowed`/`supplied` totals or compute accrual deltas via `mul_div_floor_saturating` and stop index growth when the unscaled value would exceed `i128::MAX` — the index cap already exists (`MAX_BORROW_INDEX_RAY`), but a *value* cap tied to the same bound would engage first. Alternatively, allow `repay`/`withdraw` to proceed on a saturating index path so user funds remain recoverable after the ceiling is hit.

### Proof of Concept
Already pinned by the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361): supply `BILLION * 10^18` BIG18 and borrow 98% of it, advance time on `xlm_curve`; `try_update_indexes` fails with `errors::MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and `try_withdraw_raw`/`try_repay` fail identically — the market is frozen.
