I found a concrete analog. In `handleSavedPrivatePayments` (`network.js:2443-2522`), the inner `validateAndSave` function catches a hash-calculation exception but does not `return` after handling it, causing execution to fall through to unrelated code that dereferences the same object again — and this whole path is reached with attacker/counterparty-controlled JSON originally accepted almost unvalidated in `handleOnlinePrivatePayment` (`network.js:2375-2441`) and stored verbatim into `unhandled_private_payments` before deep structural checks occur.

### Title
Malformed private-payment chain JSON causes unhandled exception and full node crash (DoS) - (File: network.js)

### Summary
`handleOnlinePrivatePayment` accepts a private-payment chain array from an unprivileged private-payment counterparty and only checks the head element's `unit`, `message_index`, and `output_index` shape before persisting the raw attacker-supplied JSON into the `unhandled_private_payments` table for later, asynchronous processing. [1](#0-0)  When the saved chain is later replayed by `handleSavedPrivatePayments`, the head element is read back and `objectHash.getBase64Hash(objHeadPrivateElement.payload, ...)` is invoked inside a `try/catch`, but the `catch` block does not `return` after handling the error, so execution falls through and continues to reference `objHeadPrivateElement.payload` / `objHeadPrivateElement.unit` again and calls `privatePayment.validateAndSavePrivatePaymentChain` a second time, on top of the already-processed error path. [2](#0-1) 

### Finding Description
The head element's `payload` field is attacker-controlled and only loosely validated at ingestion (`isNonemptyArray`, `unit`/`message_index`/`output_index` basic type checks) before being serialized to the DB. [3](#0-2)  Deep structural checks (e.g. `isNonemptyObject`/`isNonemptyString` on payload contents) only happen in the synchronous `handlePrivatePaymentChains` hub-forwarding path, which is a *different* call path from `handleSavedPrivatePayments`, used for light clients waiting on missing/unstable ancestor units before validation can proceed (`ifWaitingForChain`) — i.e., a chain can be persisted via `savePrivatePayment()` without ever going through the stricter shape check in `wallet.js`'s `handlePrivatePaymentChains`. [4](#0-3) [5](#0-4) 

Later, `handleSavedPrivatePayments` re-reads the row and calls `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`. If `payload` (or nested fields) is structured to make `getBase64Hash` throw (e.g. containing values not valid for the hash routine, or being `null`/non-object where a nested access is expected), the `catch` block logs the error and starts `deleteHandledPrivateChain(...)`, but control still falls through past the `catch` to the following lines that reference `objHeadPrivateElement.unit` and unconditionally call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again. [6](#0-5)  This causes double-invocation of `cb` in `async.each`, and more importantly, any exception thrown deeper inside `validateAndSavePrivatePaymentChain` (e.g. `private_payment.js` accessing `headElement.payload.asset`, `storage.readAsset` callback assuming `objAsset` is non-null, or `objAsset.fixed_denominations` checks) is not caught anywhere in this call chain. [7](#0-6)  An uncaught exception anywhere in this asynchronous chain is fatal: ocore installs a global `uncaughtException` handler that deliberately re-throws to crash the whole process ("crash the process to avoid ending up in an inconsistent state"). [8](#0-7) 

This mirrors the CVE-2020-19722 bug class: an unhandled failure condition on attacker-influenced data that is not defensively guarded, propagating into a crash of the whole process instead of a contained per-request error — the private-payment counterparty is exactly the kind of low-privilege, network-reachable actor the advisory's threat model targets (an author of a payment/trigger able to reach deep validation code with malformed structured data).

### Impact Explanation
A crash of the full-node/wallet process is a denial of service: the node stops relaying/validating/confirming units until it is restarted, and if this is triggered repeatedly by a malicious counterparty sending crafted private-payment chains, the node can be kept offline, unable to confirm new units, satisfying the "network unable to confirm new units" bar in the validation criteria.

### Likelihood Explanation
The path is reachable by any device paired as a private-payment counterparty simply by sending a private-payment chain that will later be re-processed via `handleSavedPrivatePayments` (e.g. a light-client waiting on a missing/unstable ancestor via `ifWaitingForChain`, or when the corresponding unit becomes known later and `handleSavedPrivatePayments` is invoked automatically). No wallet approval or special privilege is required beyond being a correspondent device able to send a `private_payments` message.

### Recommendation
- Add a `return` after the `catch` block in `handleSavedPrivatePayments`'s `validateAndSave` (`network.js` around line 2472-2477) so that once the hash calculation fails, the function does not continue to reference `objHeadPrivateElement` or double-invoke the validation/save logic and `cb`.
- Wrap the call to `privatePayment.validateAndSavePrivatePaymentChain` (and its downstream `storage.readAsset`/`getBase64Hash` calls) in defensive try/catch so any deep structural malformation of attacker-supplied private-payment JSON degrades to a per-chain error (`ifError`) instead of an uncaught exception that crashes the whole process.
- Perform the same deep structural validation used in `wallet.js`'s `handlePrivatePaymentChains` (`isNonemptyObject`/`isNonemptyString` checks on payload fields) at the point where chains are persisted in `handleOnlinePrivatePayment`/`savePrivatePayment`, before they are stored for later asynchronous replay.

### Proof of Concept
1. As a paired correspondent device (private-payment counterparty), craft a `private_payments` message whose chain's head element passes the shallow checks in `handleOnlinePrivatePayment` (`unit` is a valid-looking base64 string, `message_index`/`output_index` are valid integers) but whose `payload` is structured so that `objectHash.getBase64Hash` throws when invoked with `true` (bJsonBased) — e.g., a payload containing a value type unsupported by the hashing routine, or a deeply-recursive/self-referential-looking structure that the JSON round trip still allows.
2. Ensure the chain is queued via `ifWaitingForChain`/`savePrivatePayment` (e.g., light client not yet having ancestor units, or a not-yet-stable ancestor), so it lands in `unhandled_private_payments`.
3. Trigger `handleSavedPrivatePayments` for that unit (e.g., once the referenced unit becomes known, which the node does automatically).
4. Observe that the `catch` block runs but execution falls through to also call `privatePayment.validateAndSavePrivatePaymentChain` again; any exception thrown further down this call chain is uncaught and hits the global `uncaughtException` handler, which re-throws and crashes the node process.
