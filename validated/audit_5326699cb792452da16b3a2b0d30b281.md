### Title
Silent front-run of shared-address co-signer routing via `INSERT IGNORE` in `addNewSharedAddress()` - (File: wallet_defined_by_addresses.js)

### Summary
`addNewSharedAddress()` persists a new multi-signature ("shared") address and the `device_address` that each cosigner's signing key/private chain requests should be routed to, using `INSERT IGNORE`. Just like the reported `create()` proxy that keeps operating on a pre-existing (attacker-controlled) contract address instead of reverting, this function keeps "succeeding" even when a row for the same `(shared_address, signing_path)` already exists, silently discarding the legitimate mapping instead of failing or overwriting it.

### Finding Description
When members of a multi-sig ("shared") address exchange the finished definition, `handleNewSharedAddress()` validates only that the definition hashes to the claimed address and that declared signer addresses match paths derivable from the definition itself: [1](#0-0) 

It never checks whether `shared_address_signing_paths` already contains a conflicting row for the same `(shared_address, signing_path)` with a different `device_address` before calling `addNewSharedAddress()`: [2](#0-1) 

Both the `shared_addresses` and `shared_address_signing_paths` inserts use `INSERT ` + `db.getIgnore()`, and `shared_address_signing_paths` has a `PRIMARY KEY`/`UNIQUE KEY (shared_address, signing_path)`: [3](#0-2) 

Because the address itself (`shared_address = chash160(definition)`) is content-derived and thus tamper-resistant, an attacker cannot forge the address/definition. But the per-signing-path `device_address` binding — which decides which device the wallet contacts for signature requests and forwards private payment chains to — is **not** content-derived; it is simply whatever `device_address` arrives first for that `(shared_address, signing_path)`. A cosigner (a legitimate, paired counterparty of the multisig) can pre-send a `new_shared_address` message claiming to be the `device_address` for another member's signing path before the real device-to-address binding for that path propagates. Once that row exists, the subsequent (correct) `new_shared_address` message from the legitimate flow is silently ignored by `INSERT IGNORE`, exactly mirroring the reported bug class: the operation "continues" and reports success even though a pre-existing (and here, malicious) entry already occupies the slot, instead of detecting the conflict and rejecting it.

This routing table directly drives two security-sensitive flows:
1. **Signing-key discovery** — `findAddress()` resolves which device to request a signature from strictly from `shared_address_signing_paths.device_address`: [4](#0-3) 
2. **Private-chain forwarding** — private payment chains for the shared address are forwarded to devices taken from the very same table: [5](#0-4) 

If an attacker's device is locked in for another member's signing path, subsequent signing requests and private-payment forwarding for that member's path will be misdirected to the attacker instead of the legitimate cosigner, and the legitimate rebind attempt is a silent no-op.

### Impact Explanation
- **Freezing of funds**: If the attacker's device is unreachable/uncooperative for signature requests, the shared (multi-sig) address becomes unable to produce a valid signature for that path, permanently blocking spending from the multisig address.
- **Leak of private payment data**: `forwardPrivateChainsToOtherMembersOfAddresses()` sends private chain elements of confidential outputs to the device recorded in `shared_address_signing_paths`, so an attacker who wins this race receives private transaction data belonging to another member's path.
- No cryptographic control is bypassed for actual signing (the attacker still cannot forge a valid signature without the private key), but availability of funds and confidentiality of private payments for anyone using shared/multisig addresses can be broken — both explicitly in-scope impact categories (AA/shared-address fund freezing and leak of private payment chains).

### Likelihood Explanation
The attack requires the attacker to be a participant device already involved in creating the shared address (able to send a `new_shared_address` correspondent-device message), i.e., a "paired device" counterparty — an explicitly in-scope, unprivileged actor per the analog rules. Winning the race only requires sending the malicious binding before the legitimate flow reaches the same `(shared_address, signing_path)` insert, which is plausible since address creation for multisig wallets is a multi-round, multi-device handshake with no atomic ordering guarantee.

### Recommendation
- Replace the `INSERT IGNORE` semantics in `addNewSharedAddress()` for `shared_address_signing_paths` with logic that detects an existing row for `(shared_address, signing_path)` and either rejects the new/duplicate binding when it conflicts, or requires the binding be corroborated by data actually anchored to the address definition (e.g., only allow rebinding by the device that also proves control of that member address), instead of silently keeping whichever entry arrived first.
- Reject (rather than ignore) conflicting rows in `handleNewSharedAddress()`/`addNewSharedAddress()` and surface an explicit error so cosigners can detect and resolve address-binding conflicts before relying on the shared address.

### Proof of Concept
1. Alice, Bob, and Mallory (attacker, an actual cosigner in an "and"/"or" multisig definition) begin creating a shared address together.
2. Before Bob's legitimate device-address exchange for his signing path completes, Mallory sends her own `new_shared_address` message (device_address = Mallory's) for `shared_address = X`, `signing_path = "r.1"` (Bob's path), reaching `addNewSharedAddress()` first: [6](#0-5) .
3. Bob's legitimate `new_shared_address` message for the same `(X, "r.1")` arrives later; the `INSERT IGNORE` silently drops it because the primary key already exists.
4. Any future signing request or private-chain forward for `X`/`r.1` (via `findAddress()` and `forwardPrivateChainsToOtherMembersOfAddresses()`) is routed to Mallory's device instead of Bob's, either permanently stalling the multisig (fund freeze) or leaking private outputs meant for Bob to Mallory.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
