### Title
Asset attestor list can be reset by the definer, freezing funds of already-attested holders of `spender_attested` assets - (File: `validation.js`, `storage.js`)

### Summary
The `asset_attestors` message lets an asset's definer replace the entire attestor list for a `spender_attested` asset at any time, with no protection for addresses that already hold (or received) units of that asset and were validly attested under the *previous* list. Because spendability of a `spender_attested` asset is always checked against the *most recent* attestor list rather than the list that was in force when the coins were acquired, a definer who "resets" the list (even accidentally) can instantly and unilaterally freeze other users' coins — the same root cause as the reported `setToken` bug: a critical configuration value can be overwritten after user funds already depend on the old value, with no guard requiring the old value to be unset/empty or no funds committed first.

### Finding Description
`validateAttestorListUpdate` in `validation.js` only checks that the message is single-authored, the payload has no foreign fields, the asset actually requires attestation, and the sender is the asset's `definer_address`: [1](#0-0) 

There is no restriction such as "the attestor list can only be set once" or "attestors can only be edited while no coins have been issued/transferred yet" — unlike the `setToken` fix recommendation (`require(token == address(0) || totalStaking == 0)`), there is no analogous `require` here.

When an asset requires attestation, spendability is determined by `storage.readAsset` / `filterAttestedAddresses`, which always looks up the *latest* attestor-list unit for the asset (`ORDER BY level DESC LIMIT 1`), not the list active at the time an address was attested or received the asset: [2](#0-1) [3](#0-2) 

This latest list is then used in `validatePayment` to gate every subsequent spend of the asset — including spends of units acquired long before the attestor list was changed: [4](#0-3) 

Consequently, exactly like the `setToken` scenario:
- The definer sets attestor list A, and users receive/hold the asset after being attested by an attestor in A.
- The definer later posts a new `asset_attestors` message changing the list to B (dropping the attestors that had attested existing holders).
- Existing holders who were only attested under A can no longer prove `arrAttestedAddresses` membership under B and are immediately unable to spend their already-held units of the asset — their funds are locked until (and unless) they are re-attested under the new list.

### Impact Explanation
Holders of a `spender_attested` asset lose the ability to spend previously acquired, legitimately-held funds the moment the definer posts a new attestor list, with no requirement that the definer first ensure no funds are outstanding or that affected holders be re-attested. This is a direct freezing of user funds triggered by a single ordinary AA/asset message from a privileged-but-not-node-level actor (the asset definer), matching the "AA fund loss or freezing" acceptance criterion. It also affects AA-issued assets, since AAs can issue `asset_attestors` messages via `aaApps` in `aa_validation.js` [5](#0-4) , so a poorly designed or buggy AA could trigger the same freeze programmatically.

### Likelihood Explanation
Any asset definer (a role reachable without special network privileges — just create an asset with `spender_attested: true`) can trigger this by posting one `asset_attestors` unit, exactly as easily as the original `setToken` call. No stability/finality race or malicious-node behavior is required; it is purely a missing state-guard in `validateAttestorListUpdate`.

### Recommendation
Add a guard in `validateAttestorListUpdate` (and/or in `storage.readAsset`/`filterAttestedAddresses`) so that changing the attestor list cannot retroactively strip attestation from addresses that were already validly attested and hold units of the asset — for example, by keeping historical attestor-list validity per received/held output (attest-at-receipt-time semantics), or by requiring that no outstanding balance exists before an attestor-list change is accepted, analogous to the recommended `require(token == address(0) || totalStaking == 0)` check in the original report.

### Proof of Concept
1. Definer `D` issues asset `X` with `spender_attested: true` and initial attestors `[A1]`.
2. `A1` attests holder `H` (`attestation` message with `address: H`).
3. `H` receives units of `X` (payment validated per `validatePayment` in `validation.js`, requiring `H` to be in `arrAttestedAddresses` at issue/receive time) [4](#0-3) .
4. `D` posts `asset_attestors` message changing the attestor list to `[A2]` (dropping `A1`) — accepted because `validateAttestorListUpdate` performs no check on outstanding balances or existing attestations [1](#0-0) .
5. `H` attempts to spend previously received `X`. `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` now computes `arrAttestedAddresses` using the new list `[A2]`; since `H` was never attested by `A2`, the payment fails validation (`"none of the authors is attested"`) [6](#0-5) , freezing `H`'s funds until re-attested under the new list.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
