## Title
Missing `return` after `getBase64Hash` exception causes double-callback / re-validation of a private payment chain in `handleSavedPrivatePayments` - (File: `network.js`)

### Summary
In `network.js`'s `handleSavedPrivatePayments()`, the inner `validateAndSave` closure wraps `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` in a `try/catch`. On exception, the `catch` block already performs the terminal cleanup — it reports the error to the peer and calls `deleteHandledPrivateChain(..., cb)`, which invokes the `async.each` iteratee callback `cb` — but it does not `return`. Execution then falls through to compute `key` from the now-`undefined` `json_payload_hash` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the very same (already-failed) `arrPrivateElements`, whose `ifOk`/`ifError`/`ifWaitingForChain` branches all also call `cb()`. [1](#0-0) 

### Finding Description
`cb` is the per-item completion callback of the outer `async.each(rows, function(row, cb){...}, function(){ unlock(); ... })` that drives `handleSavedPrivatePayments`. [2](#0-1)  A malformed/oversized/circular `objHeadPrivateElement.payload` received in an incoming private payment (`private_payment` message, reachable by any device/peer sending a payment/private chain to a wallet) causes `objectHash.getBase64Hash` to throw. [3](#0-2)  The `catch` block already finalizes this row via `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which deletes the DB row and calls `cb()`. [4](#0-3)  Because there is no `return` statement after that call, control falls through the `catch` block and continues in the same synchronous stack to build `key` (using the now-undefined hash) and invoke `privatePayment.validateAndSavePrivatePaymentChain` a second time on the same chain, which will itself eventually call `cb()` again through one of `ifOk`, `ifError`, or `ifWaitingForChain`. [5](#0-4) 

This is structurally the same defect class as the reported kernel CVE: a resource/state-tracking value (`op_nents` in the kernel; here the "this item is done" callback state in `async.each`) is correctly finalized on one error path, but a missing reset/guard (`return`) lets the same state be acted upon again later, causing double completion of what should be a single, one-shot cleanup.

### Impact Explanation
Calling the `async.each` iteratee callback twice for the same row causes the outer completion counter to be satisfied prematurely, so the final callback (`unlock()` releasing the `"saved_private"` mutex key, plus `eventBus.emit("new_my_transactions", ...)`) can fire while other rows in the same batch are still being asynchronously validated/saved. [6](#0-5)  Because `"saved_private"` is meant to serialize processing of `unhandled_private_payments` across concurrent invocations (`lock(["saved_private"], ...)` / `lockOrSkip`), premature release lets a second, concurrent `handleSavedPrivatePayments()` pass (e.g., triggered by a new incoming unit or another `eventBus` event) run while the first pass's private-chain validation/save (which performs its own `BEGIN...COMMIT` transaction and output/`is_spent` mutation in `private_payment.js` / `indivisible_asset.js` / `divisible_asset.js`) is still in flight. [7](#0-6) [8](#0-7)  This can lead to concurrent, un-serialized mutation of private-asset spend state (`outputs.is_spent`, `spend_proofs`) for chains sharing dependent private outputs, risking inconsistent local acceptance of a private payment chain (double-processing/race on the same private output) — i.e., node disagreement on validity/stability of private payment chains and potential double-spend recognition of a private, otherwise-stable output, since the intended serialization guarantee is broken.

### Likelihood Explanation
The trigger requires only that a peer/device send a `private_payment` (or forwarded chain saved to `unhandled_private_payments`) whose head payload cannot be hashed by `objectHash.getBase64Hash` (e.g., contains a value that breaks the deterministic JSON/hash serialization, such as a circular reference, invalid type, or oversized structure) — an unprivileged, remote, single-message trigger fully within the threat model (private payment chain content controlled by an untrusted counterparty). [9](#0-8)  No special timing is needed to hit the code defect itself (the missing `return` always fires on that exception); reliably escalating it into an observable double-spend/race window depends on additional concurrent traffic, which lowers exploit reliability but not the presence of the flaw.

### Recommendation
Add a `return` immediately after `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);` inside the `catch` block in `validateAndSave` (network.js, `handleSavedPrivatePayments`), so the function does not fall through to compute `key` and re-invoke `privatePayment.validateAndSavePrivatePaymentChain` on the same failed chain. This mirrors the kernel fix pattern: perform the cleanup once and stop, rather than letting an already-finalized item flow into the normal-processing path a second time.

### Proof of Concept
1. As any device/peer, send a `private_payment` message (or a chain that ends up queued in `unhandled_private_payments`) whose head element's `payload` is crafted so that `objectHash.getBase64Hash(payload, true)` throws (e.g., a payload value type that `object_hash`'s canonical-JSON stringifier cannot handle).
2. When the target node's `handleSavedPrivatePayments()` processes this row, the `catch` block executes `deleteHandledPrivateChain(...)` (calls `cb()`), then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the same broken chain, which will independently invoke `cb()` a second time.
3. Observe (via added instrumentation/logging or async's "Callback was already called" style symptoms) that the per-row `cb` fires twice, causing the batch's completion handler (`unlock()` + `new_my_transactions` emission) to run before all rows finish, while a concurrently arriving new private-payment batch can start a second `handleSavedPrivatePayments()` pass under the same `"saved_private"` key that should have still been locked.
