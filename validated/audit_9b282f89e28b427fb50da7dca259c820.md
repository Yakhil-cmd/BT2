### Title
Tokens transferred directly to the Liquidity Pool or Controller are permanently stranded — no entrypoint can recover unbooked balances - ([File: contracts/pool/src/lib.rs])

### Summary
The Sentiment report concerns `receive()` accepting ETH with no user-accessible withdrawal path. The analog in XOXNO Lending is stronger than the original: any Soroban token can be `transfer`red directly to the `LiquidityPool` or `Controller` contract address. The pool keeps a cash accounting book strictly separate from its physical token balance, and every mutating entrypoint only moves funds against that book. There is no sweep, rescue, or skim entrypoint anywhere in the pool or controller — not even owner-gated — so directly donated tokens are permanently locked in the contract.

### Finding Description
The pool's accounting model explicitly separates booked cash from the physical balance: "The pool tracks cash in an accounting book… direct donations do not automatically increase booked cash" (docs/reference/architecture.md), and the threat model confirms "Direct donations do not rewrite those books" (docs/explanation/threat-model.md).

The complete set of pool entrypoints in `contracts/pool/src/lib.rs` is: `create_market`, `update_params`, `upgrade`, `supply`, `borrow`, `withdraw`, `repay`, `update_indexes`, `recapitalize`, `flash_loan`, `create_strategy`, `seize_positions`, `net_settle`, `claim_revenue`, plus views. Every token-moving function is gated by `#[only_owner]` (the controller) and debits a booked amount:

- `borrow`/`withdraw` transfer out only amounts debited from the market's cash book.
- `claim_revenue` pays `min(cash, revenue)` — capped by the book, so it can never touch the donation excess.
- `recapitalize` pulls tokens in, it never sends excess out.
- `flash_loan` enforces exact balance transitions around the payout/callback but does not skim the excess.

Unlike the swap-aggregator, which provides `sweep_balance` to recover non-fee balances (contracts/swap-aggregator/src/lib.rs), the pool and controller expose no equivalent. The repository's own test suite treats this as a known hazard — `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs` rejects `borrow`/`withdraw` with `to == pool || to == controller` precisely because "the controller holds funds no balance-delta measurement can ever claim." But that guard only covers protocol-initiated transfers; a raw `token.transfer(user, pool, amount)` by the user is still accepted by the token contract and lands in the same unrecoverable custody.

### Impact Explanation
Permanent freezing of funds. Any user who sends a supported asset (e.g., USDC, XLM SAC) directly to the pool or controller address — a common mistake since users routinely pre-fund contracts on Stellar — loses the tokens forever. The donation inflates the physical balance above the sum of all market cash books, and no code path, privileged or not, can move the excess out; only a WASM upgrade could introduce a recovery path. This is strictly worse than the original report, where at least `sweepTo()` existed.

### Likelihood Explanation
Requires user error (direct transfer instead of going through `controller.supply`), same likelihood profile as the original Medium finding. On Soroban the mistake is plausible because supplying looks like a token transfer from the user's perspective, and front-ends or manual invocations can target the pool address directly. No attacker action is needed.

### Recommendation
Add a skim/rescue entrypoint on the pool that computes `token.balance(pool) - sum(book cash over all markets sharing the token)` (tracked via a reserved counter like the swap-aggregator's `ReservedTotal`) and transfers only the unbooked excess to a recipient, gated to the owner or executed through a governance operation. Alternatively/additionally, document the pool and controller addresses as non-custodial in client tooling. For the controller, whose balance is otherwise always zero, a simple owner-gated sweep of any positive balance suffices.

### Proof of Concept
```rust
// Any unprivileged user; pool never recovers the tokens.
let token = token::Client::new(&env, &usdc_sac);
token.transfer(&user, &pool_address, &1_000_000);

// Booked cash is unchanged; every withdrawal path is capped by cash.
// pool.get_reserves(hub_asset) == before; no entrypoint can send the excess out.
// token.balance(&pool_address) == booked_cash_total + 1_000_000 forever.
```
This mirrors the existing donation assertion in `tests/test-harness/tests/pool_money_flow_audit.rs`, where `token.balance(&market.pool) == state.cash + other.cash + 7 * UNIT` persists with the `7 * UNIT` donation belonging to no market and no exit path.
