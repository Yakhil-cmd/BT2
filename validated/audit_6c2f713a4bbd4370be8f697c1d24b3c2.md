### Title
Unvalidated route-pool address lets arbitrary venue code append wallet-draining auth - ([File: contracts/swap-aggregator/src/execute/mod.rs])

### Summary
`execute_strategy` accepts caller-supplied `assets` and uses an indexed entry directly as the hop `pool`, without an allowlist or compatibility check. Venue adapters then invoke that address below the sender/controller authorization. A malicious pool can make unrelated `token.transfer(victim, attacker, amount)` calls that simulation records under the caller’s authorization tree; if that generated tree is signed, the attacker drains wallet assets unrelated to the swap.

### Finding Description
`execute_strategy` decodes attacker-controlled `swap_xdr` and runs the resulting `StrategyPayload`. [1](#0-0)  The payload’s `assets` vector is explicitly a registry of token, pool, and LP-token addresses. [2](#0-1)  Although `Program::validate` range-checks the pool index, it only ensures the index exists in `assets`; it does not ensure the resolved address is an approved venue contract. [3](#0-2) 

During execution, `execute_op` constructs `SwapHop` by taking `ctx.assets[op.idx_a]` as `pool`, then calls `venues::dispatch_hop`. [4](#0-3)  The dispatch layer invokes the selected venue adapter without checking the pool address. [5](#0-4)  For example, the Soroswap adapter calls `get_reserves` and `swap` on `ctx.hop.pool`, while Phoenix invokes `swap` on that same caller-selected address. [6](#0-5) [7](#0-6) 

This is analogous to the Koha issue: untrusted input dynamically selects a field/callee that is later interpreted as trusted code, and the missing allowlist is the root cause. Soroban authorization does not eliminate the issue because route-selected code runs in the transaction’s call tree; any token transfer that calls `victim.require_auth()` is attached to the victim’s simulated authorization tree and executes if that tree is signed. The repository’s harness demonstrates exactly this behavior. [8](#0-7) 

### Impact Explanation
An unprivileged attacker can deploy a contract that satisfies the selected venue adapter’s call sequence while additionally invoking `token.transfer(victim, attacker, amount)` for any token held by the victim. When the crafted route is simulated and the resulting poisoned auth tree is signed, the rogue transfer executes even though the intended strategy only authorized the lending operation and its expected input transfer. The test harness demonstrates the full theft outcome: Alice’s unrelated wallet token balance falls to zero and the attacker receives `WALLET_BALANCE`, while the swap itself still completes. [9](#0-8) 

The affected surface includes direct router `execute_strategy` calls and controller paths that forward user-provided `StrategySwap` bytes, including `swap_collateral`; the controller forwards `swap` to `router.execute_strategy` and only bounds the controller-held input amount. [10](#0-9)  This is theft of user funds beyond the declared trade input, not merely bad pricing, MEV, or poor route selection.

### Likelihood Explanation
Likelihood is medium. The attacker needs the victim or integrator to sign the exact authorization tree containing the malicious child transfer; an honest client that rejects unexpected children prevents execution. However, simulation necessarily returns that tree, the route bytes are opaque XDR to most users, and the malicious child can target an unrelated wallet token while the displayed pair and output still look economically correct. The test confirms that recording simulation produces the malicious child and that enforcing mode executes it once signed. [11](#0-10) 

### Recommendation
Maintain an on-chain governance-controlled pool/venue allowlist keyed by `(venue, pool)` and check each decoded hop before invocation. For externally supplied routes, do not treat the `assets` registry as proof that an address implements the expected venue interface. Additionally, constrain the authorization surface so venue calls cannot introduce unrelated sender-authorized transfers, and update clients to reject any auth-tree child other than the exact expected input transfer.

### Proof of Concept
1. Attacker deploys `RogueHopPool` configured with the victim address, an unrelated wallet-token address, attacker recipient, and amount. Its `swap` function invokes `wallet_token.transfer(victim, attacker, amount)`. [12](#0-11) 
2. Attacker constructs `swap_xdr` with the rogue contract address in `assets` and an instruction whose `idx_a` resolves to that address; this passes the existing index bounds checks because `idx_a < assets.len()`. [13](#0-12) 
3. Victim calls a strategy such as `swap_collateral`; the controller authorizes its bounded input transfer and invokes `execute_strategy`. [14](#0-13) 
4. The router dispatches to the rogue pool address selected by the payload. [15](#0-14) 
5. Simulation records `wallet_token.transfer(victim → attacker, amount)` as a child of the victim’s `swap_collateral` authorization. [16](#0-15) 
6. Signing that tree authorizes the unrelated transfer; the harness asserts the victim wallet balance becomes zero and the attacker receives the funds. [17](#0-16)

    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);

    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {

    s.try_swap_with_signed_tree(&benign, &[])
