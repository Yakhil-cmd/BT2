### Title
Unbounded growth of `system_votes` log makes `countVotes` permanently more expensive to run on every stabilization triggered by a cheap `system_vote_count` unit - ([File: main_chain.js])

### Summary
The external report describes a queue (`rolloverQueue`) that grows forever because entries are never delisted, so a permissionless processing function that must scan the whole queue becomes progressively more expensive and eventually uneconomical/unusable for anyone who has to pay for the iteration. The analogous pattern in `ocore` is the `system_votes` table together with `countVotes()` in `main_chain.js`: any address can cast a `system_vote` for cheap, the vote is appended forever to `system_votes` (a pure append-only log, "just a log of all votes, including overridden ones", never pruned), and `countVotes()` is triggered by any unprivileged unit that posts a `system_vote_count` message during main-chain stabilization.

### Finding Description
`system_votes` is documented and implemented as an append-only log of every vote ever cast, with no deletion path: [1](#0-0) 

Whenever a `system_vote_count` message becomes stable, `countVotes()` is invoked for the corresponding subject: [2](#0-1) 

`countVotes()` starts by loading **every distinct address that has ever voted for that subject**, with no expiry, no minimum balance requirement to remain listed, and no cap: [3](#0-2) 

It then builds a temporary table and inserts a row for every one of these addresses, and only afterward filters by balance/timeframe: [4](#0-3) 

Because `system_votes` rows are never deleted (`op_votes`/`numerical_votes` keep only the *latest* vote per address, but `system_votes` retains the full historical log), the set of `DISTINCT address` for a given subject only ever grows as more low-value/throwaway addresses cast a single cheap vote and never vote again. Since anyone can post a `system_vote` message from a fresh address for the cost of one ordinary unit, and `system_vote_count` (which triggers the expensive query) can likewise be posted by any unprivileged user, the cost of `countVotes()` grows monotonically and is paid by every full node on the network at every stabilization that includes such a trigger — this is functionally identical to the "rolloverQueue grows forever, and each new call has to scan/skip more dead entries" pattern from the Carousel report, except that here the growing set is scanned unconditionally rather than being partially skipped.

### Impact Explanation
`countVotes()` runs as part of `advanceMcStability` → `markMcIndexStable`, i.e., inside the consensus-critical main-chain stabilization path that every full node must execute to advance stability. An attacker who repeatedly posts single cheap `system_vote` units from disposable addresses (and periodically a `system_vote_count`) permanently inflates the size of the address list and temporary table that `countVotes()` must build on every subsequent vote count for that subject. Over time this:
- increases the mandatory per-node computation and DB I/O cost for stabilizing units carrying a `system_vote_count` message, degrading throughput for the whole network (a node unable to keep up with confirming new units), and
- is irreversible: there is no mechanism to delist stale/low-balance/never-repeating voters from `system_votes`, so the query set only grows, exactly mirroring the reported issue of an ever-growing unprocessable/un-prunable queue that a permissionless caller must pay to traverse.

This differs from the original report's "keeper economics" framing (where only the *reward* for the caller is destroyed) — here the growing cost is imposed on all consensus-processing nodes, which is a stronger network-availability concern.

### Likelihood Explanation
Likelihood is fairly high given ordinary economics: casting a `system_vote` and later a `system_vote_count` are cheap operations available to any unprivileged unit poster, with no explicit bound on the number of distinct addresses that can accumulate votes for the same subject. No special privilege, timing, or malicious-peer behavior is required — only the ability to post ordinary units, which fits within the reachable single-poster threat model.

### Recommendation
Bound the growth of the address set considered by `countVotes()`:
- Prune or age out `system_votes` rows for addresses that no longer hold any balance, or cap the number of retained votes per subject.
- Alternatively, restrict `countVotes()`'s address scan to addresses that currently satisfy a minimum balance/stake threshold before constructing the temporary table, rather than loading the full historical `DISTINCT address` set unconditionally.
- Consider rate-limiting or requiring a minimum bond for casting `system_vote`/`system_vote_count` to prevent cheap unbounded accumulation of dead voter records.

### Proof of Concept
Not directly reproducible without a live network/test harness; the growth pattern is evidenced structurally:
1. Repeatedly compose and broadcast `system_vote` units from freshly generated addresses (minimal balance to cover fees) for a fixed `subject`, using `composer.js`'s `composeContentJoint`-based helpers, each vote is persisted forever into `system_votes` ( [5](#0-4) ).
2. Post a `system_vote_count` unit; `countVotes()` executes `SELECT DISTINCT address FROM system_votes WHERE subject=?` ( [6](#0-5) ) whose result set size is proportional to the cumulative number of distinct addresses that have ever voted, not to the number of currently-relevant voters.
3. Repeating step 1 with new throwaway addresses before each `system_vote_count` shows the temporary `voter_balances` table and its `INSERT` statement ( [7](#0-6) ) growing without bound over time, imposing permanently increasing per-stabilization cost on all full nodes.
