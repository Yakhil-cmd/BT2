### Title
Cross-tenant stack archive/unarchive via org-key/full_name mismatch in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`), but `UnlabeledHandler`/`LabeledHandler` (via `LabelCapturingHandler`'s shared pattern) resolve the target `Repository`/`Stack` using the independent `repository.full_name` field, with no code anywhere cross-checking that these two values name the same organization.

### Finding Description
Binding claimed safe: verifying org `A = params.dig('repository','owner','login')` should equal repository-owning org `B = params.repository.full_name.split('/').first`.

Trace:
- `WebhooksController#verify_signature` [1](#0-0)  computes `repository_owner` from `params.dig('repository','owner','login')` [2](#0-1)  and uses it solely to pick which configured GitHub App/`webhook_secret` HMAC-validates the raw body.
- `UnlabeledHandler`'s `ExplicitParameters` schema only `requires :repository { requires :full_name, String }` — it never declares or validates `repository.owner.login` [3](#0-2) .
- `repository` in the handler is resolved purely from `params.repository.full_name` via `Repository.from_github_repo_name` [4](#0-3) , and `stack` is scoped to that repository's `review_stacks` [5](#0-4) .
- `archive?`/`unarchive?` are computed purely from attacker-supplied `pull_request.labels` compared against the resolved repository's `provisioning_label_name`/`provisioning_behavior` [6](#0-5) , then `handle` calls `stack.archive!`/`stack.unarchive!` [7](#0-6) .

`/webhooks` accepts a raw POST body from the internet; nothing restricts it to genuine GitHub redelivery, and the signature check is only an HMAC over the *entire raw body* keyed by whichever org name is embedded in `repository.owner.login`. An attacker who legitimately owns/administers a Shipit-integrated org "A" (and therefore knows A's `webhook_secret`, e.g. because they configured the multi-org `github:` block for their own org as shown in `docs/setup.md`) can construct a raw JSON body where `repository.owner.login = "A"` (so `verify_signature` uses A's key and succeeds) while `repository.full_name = "B/victim-repo"` (an unrelated tenant's real repository), sign it with A's secret, and POST it directly. `drop_unhandled_event`, `ExplicitParameters`, and `verify_signature` all pass because none of them ever compare `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
The forged request drives `Shipit::Webhooks::Handlers::PullRequest::UnlabeledHandler#process` (and identically `LabeledHandler`) to resolve and mutate org B's real `Stack`/`ReviewStack` — flipping `archive!`/`unarchive!` state, which also triggers `deprovision`/enqueue-for-provisioning side effects — despite the request only having been authenticated against org A's secret. This is a payload for one tenant (repository/org A) mutating another tenant's (org B) stack state, satisfying the Critical "payload for one repository mutating another's stack" criterion. It is fully repeatable against any repository/stack whose `full_name` the attacker knows, for any org sharing this Shipit instance.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (the documented multi-org `github:` config), (b) the attacker to legitimately control at least one of those orgs (a low, "unprivileged" bar — Shipit explicitly supports many independent orgs on one instance), and (c) `Shipit::Repository#review_stacks_enabled`/provisioning-label config on the victim repo. Given those, the attacker cost is a single crafted HTTP POST with a correctly computed HMAC using their own known secret — no guessing of victim secrets required. This is feasible and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after determining `repository_owner`, assert it matches the owner segment parsed from `repository.full_name` (and/or `organization.login`) before dispatching to handlers; reject with 422 on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "rejects webhook whose repository.full_name org differs from repository.owner.login org" do
  request.headers['X-Github-Event'] = 'pull_request'
  payload = payload_parsed(:pull_request_unlabeled)
  payload['repository']['owner']['login'] = 'org-a'          # verifying org
  payload['repository']['full_name']      = 'org-b/victim-repo' # resolved by handler
  raw = payload.to_json

  Shipit.github(organization: 'org-a').expects(:verify_webhook_signature).returns(true)
  # Precondition: org-b/victim-repo has an active, non-archived review stack
  stack = shipit_stacks(:review_stack) # owned by org-b

  assert_no_changes -> { stack.reload.archived_since } do
    post :create, body: raw, as: :json, headers: { 'X-Hub-Signature' => 'sha1=attacker-computed-with-org-a-secret' }
  end
end
```
Assert both sides of the binding: `payload['repository']['owner']['login']` ("org-a") must equal the org segment of `payload['repository']['full_name']` ("org-b") for the request to be accepted; currently they diverge and the stack still mutates.
