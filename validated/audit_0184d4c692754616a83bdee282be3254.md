### Title
Webhook signature verification is scoped to `repository.owner.login`, but every handler acts on the independent, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) used to validate `X-Hub-Signature` by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body. [1](#0-0)  Once the signature check for *that* organization passes, `create` hands the entire, attacker-controlled `params` hash to the event handlers. [2](#0-1)  Every handler, however, resolves the target `Repository`/`Stack` from a different field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks`. [3](#0-2)  Nothing ties `repository.owner.login` (the value the signature was verified against) to `repository.full_name` (the value that determines which stack actually gets mutated).

### Finding Description
This is the same class of bug as the ZIP report: a piece of the payload that drives execution (here, which repository/stack the handler acts on) is outside the boundary that was actually cryptographically checked (here, which organization's secret validated the signature).

- `repository_owner` is computed from the raw, unverified body before any signature check: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [4](#0-3) 
- That value selects the `GitHubApp` instance and hence the `webhook_secret` HMAC key used by `verify_webhook_signature`. [1](#0-0) [5](#0-4) 
- Setup documentation and the shipped config templates explicitly treat `webhook_secret` as optional and show it left blank (`webhook_secret: # nil`) for one or more organizations in a multi-org configuration. [6](#0-5) [7](#0-6) 
- `verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank: `return true unless webhook_secret`. [8](#0-7) 
- Every registered handler (`PushHandler`, `pull_request` handlers, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`) resolves the acted-upon repository purely from `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login`. [3](#0-2) [9](#0-8) 

Consequently, in any Shipit deployment configured for multiple GitHub organizations where at least one organization has no `webhook_secret` set (a state the docs present as a supported, optional configuration), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to the no-secret organization - `verify_signature` passes trivially, no signature required.
2. Put an arbitrary target `repository.full_name` (belonging to a *different*, real, secret-protected organization) in the same payload.
3. Because handlers only look at `repository.full_name`, the forged event is dispatched against the real organization's stacks. `PushHandler` will call `stack.sync_github(expected_head_sha:)` on the victim stack for any branch/SHA the attacker chooses, and `pull_request`/`check_suite` handlers will mutate `MergeRequest`/`Commit`/check-run state for that stack as well. [10](#0-9) [11](#0-10) 

The equality this breaks: `organization that authenticated the request` (`repository_owner` used to pick the `GitHubApp`/secret) MUST equal `repository whose state is written` (`repository.full_name` used by every `Handler`), but the code never enforces this — before vs. after the attacker's crafted webhook, the org used for HMAC selection and the repo actually mutated can be completely disjoint.

### Impact Explanation
This allows cross-repository/cross-organization writes without possessing the target organization's `webhook_secret` at all — only requiring that some organization in the multi-org config has no secret configured (a state the project's own docs mark "optional"). Effects include forcing `GithubSyncJob`/`sync_github` on a victim stack with attacker-chosen `expected_head_sha`, and manipulating pull-request/check-run/commit state used for merge-queue and deploy gating on a repository the attacker was never authenticated against. This matches the "cross-repository writes" / unauthorized state-changing action criterion.

### Likelihood Explanation
Requires a specific but explicitly-supported deployment shape: multi-organization Shipit config (`Shipit.github(organization:)` schema, documented in `docs/setup.md`) where at least one configured organization omits `webhook_secret`. Given the docs present `webhook_secret` as optional per-organization and show it blank in example templates, this is a plausible real-world misconfiguration rather than a purely theoretical one; no privileged credentials, session, or API token are needed by the attacker.

### Recommendation
Bind the field used to select the verification secret to the field the handlers actually act on: after verifying the signature, re-derive `repository_owner` (and reject if it disagrees with `repository.full_name`'s owner segment), or better, verify the signature against every configured organization whose repository could match `full_name`, and require the resolved `GitHubApp`/secret to correspond to the same repository owner used by `Handler#repository_name`. Additionally, do not allow `verify_webhook_signature` to auto-pass (`return true unless webhook_secret`) in any configuration where other organizations do have secrets configured, since that creates an unauthenticated bypass path shared with the rest of the payload's fields.

### Proof of Concept
Given a multi-org config such as:
```yaml
github:
  attacker-org:
    webhook_secret: # nil
  victim-org:
    webhook_secret: "real-secret"
```
An attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/production-repo" }
}
```
`repository_owner` resolves to `attacker-org`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank. [8](#0-7)  The request is dispatched to `PushHandler`, which resolves the target repository from `repository.full_name` ("victim-org/production-repo") and triggers `sync_github(expected_head_sha: "deadbeef")` on that stack — despite the request never being authenticated for `victim-org`. [3](#0-2) [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
