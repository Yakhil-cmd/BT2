### Title
User Funds Silently Lost to an AA When `data` Message Field Names Contain a Typo - (File: `aa_composer.js`)

### Summary
When a user calls an Autonomous Agent (AA) by posting a unit with a `payment` message plus a `data` message (the on-chain analog of Footium's `_message` parameter), the AA's oscript logic reads user-supplied field names from `trigger.data`. Ocore performs no semantic validation that the keys/values in `trigger.data` match what the AA definition expects — a missing or misspelled key simply evaluates to `false`/`none` in formulas rather than causing an error. If the AA's response messages are gated behind an `if` condition on such a field, a single typo causes the AA to fall into the "no messages after filtering" path, which keeps the received coins, sends no response, and still commits state changes, permanently swallowing the user's payment with no bounce/refund.

### Finding Description
An AA trigger is built from the first `data`-app message and the `payment`-app message(s) sent to the AA address: [1](#0-0) . Field validation of a `data` message only requires it be a non-empty object — there's no schema/key validation against what a specific AA expects: [2](#0-1)  and [3](#0-2) .

Inside oscript formula evaluation, `trigger.data.<key>` for a missing/mistyped key does not throw — it silently evaluates to `false` (or `none`/undefined depending on context), confirmed by test cases such as `trigger with missing key` and `otherwise false with trigger`: [4](#0-3) [5](#0-4) . The `trigger.data` opcode implementation itself just returns `false` when the referenced value is absent: [6](#0-5) .

Because AA authors commonly gate `if`/`case` conditions on `trigger.data.<field>`, a caller's typo (e.g. sending `{"actoin":"stake"}` instead of `{"action":"stake"}`) makes every conditional message branch evaluate false. When all `messages` are filtered out, `handleTrigger` takes the "eat the coins" path instead of bouncing: [7](#0-6) , confirmed by the `no messages` test where the trigger's bytes are consumed and no refund output is produced for the sender beyond whatever the AA's own unconditional logic pays out: [8](#0-7) . Unlike underpayment of `bounce_fees` (which is explicitly checked and triggers a `bounce`) [9](#0-8) , there is no protocol-level check that the semantic *content* of `trigger.data` matches any expected schema — this validation is left entirely to each AA's own oscript, and most AAs do not implement exhaustive input-shape checks/typo-tolerance.

### Impact Explanation
A user who mistypes a key/value in the `data` message when triggering an AA (analogous to Footium's `_message` parameter for `makePayment`) can have the AA silently consume the attached payment, perform no corrective bounce, and never deliver the intended feature/state change. This is a genuine, unauthorized-permanent loss of user funds reachable by any ordinary unit poster interacting with a published AA — not a peer/node/hub issue. Severity is Medium: it depends on user error (a typo) rather than an active exploit, but the loss is real, permanent, and not something the protocol protects against, matching the class and severity of the original Footium finding.

### Likelihood Explanation
Likelihood is Medium: this requires no attacker, only an unprivileged user making a common data-entry mistake (which is highly plausible, given AA data payloads are typically constructed in a wallet UI or by hand). It occurs across many existing and future AAs that branch on `trigger.data` fields without validating unrecognized/missing keys, since the oscript language itself normalizes "missing key" to `false` rather than raising an error to be caught by an AA-level "unknown field" guard.

### Recommendation
- Encourage/require AA authors to explicitly validate the full expected shape of `trigger.data` (e.g., using `require()`/`bounce()` on unrecognized or missing fields) so that malformed input triggers a `bounce`, refunding the sender their payment minus `bounce_fees`, instead of silently falling through to "no messages after filtering."
- Consider adding an oscript primitive/pattern (e.g. `trigger.data` "strict-keys" check) that AA templates can opt into to bounce automatically when `trigger.data` contains keys not in an expected allow-list, reducing user-error fund loss without changing the low-level `trigger.data` opcode semantics used elsewhere.
- At minimum, document prominently for AA/dApp developers that "no messages after filtering" swallows the trigger's payment and that any conditional branch reachable via `if` gated on `trigger.data` fields must be paired with an explicit bounce for unmatched/malformed input.

### Proof of Concept
1. Deploy an AA whose response is entirely gated by an `if` clause reading `trigger.data.action`, e.g.:
```js
{
  messages: [
    { if: "{trigger.data.action=='deposit'}", app: 'payment', payload: { asset: 'base', outputs: [{address:"{trigger.address}", amount:"{trigger.output[[asset=base]] - 1000}"}] } }
  ]
}
```
(mirrors the `no messages` unit test setup) [10](#0-9) .
2. A user intends to trigger the deposit branch but sends `data: {"actoin": "deposit"}` (typo) together with a payment output to the AA, as built by `getTrigger`: [1](#0-0) .
3. `trigger.data.action` evaluates to `false` (key doesn't exist) per the confirmed opcode/formula behavior: [6](#0-5) , so the `if` condition is false and the only message is filtered out.
4. `handleTrigger` reaches the `messages.length === 0` branch and calls `handleSuccessfulEmptyResponseUnit(null)` instead of bouncing: [7](#0-6) .
5. The user's payment to the AA is retained by the AA balance; no refund unit is produced, and no deposit is credited — funds are lost due solely to the unvalidated `data` message.
