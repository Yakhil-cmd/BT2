### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` / bare commit `sha` with no scoping check, allowing forged commit statuses on any repository - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on a field read out of the untrusted JSON body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (or `organization.login`). Shipit supports multiple GitHub Apps/organizations configured with independent `webhook_secret`s (see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). Because the signature only proves "this payload was signed with organization X's secret", and X is picked from a field *inside* the same attacker-controlled payload, an attacker who legitimately controls one configured organization (knows/owns that org's `webhook_secret`) can craft an arbitrary raw body, set `repository.owner.login` to their own org (so `verify_signature` selects their own valid secret and passes), while every other field in the body is unconstrained.

Downstream, the dispatched handlers never re-check that the rest of the payload actually belongs to that authenticated organization/repository: [3](#0-2) 

`Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a completely independent field from the one used for signature-organization selection. Worse, `StatusHandler` does not even use `repository_name`/`stacks` scoping at all; it matches purely by commit SHA across the entire installation: [4](#0-3) 

This is a broken equality: the organization whose secret authenticated the request (`repository.owner.login`) is never bound to the repository/commit that the handler actually writes to (`repository.full_name`, `sha`). `PushHandler`/`CheckSuiteHandler` at least filter through `Repository.from_github_repo_name(repository_name)`, but that name itself is attacker-supplied and unrelated to the org that produced a valid signature — so an attacker who controls org X's webhook secret can point `repository.full_name` at `victim-org/victim-repo` and have Shipit believe the push/check-suite/status event genuinely originated from GitHub for that repository.

### Impact Explanation
A `status` webhook forged this way lets an unprivileged holder of one organization's webhook credentials write arbitrary `CommitStatus` records (`state`, `context`, `description`, `target_url`) onto any commit SHA already known to Shipit, regardless of which organization/repository it belongs to (`Commit#create_status_from_github!`). Because Shipit uses commit statuses to satisfy `ci.require` gating in `shipit.yml` and to drive continuous deployment, this can be used to mark a victim stack's commit as CI-green and trigger an unauthorized deploy — matching the Critical "unauthorized deploy" impact class. It also lets an attacker forge `push`/`check_suite` events that cause `stack.sync_github` / check-run refresh to run against a victim repository the attacker does not own, since `repository_name` resolution is never cross-checked against the authenticating organization.

### Likelihood Explanation
Exploitation requires the attacker to control (or be a legitimate low-privilege member/owner of) at least one GitHub organization/App already configured in Shipit's `secrets.yml` — a realistic scenario for any multi-tenant Shipit deployment serving several GitHub orgs, since Shipit is explicitly designed to host multiple independent orgs with separate webhook secrets. No GitHub App private key, session, or `ApiClient` token is needed; only the ability to POST a crafted, self-signed body to the public `/github/webhooks` endpoint.

### Recommendation
After verifying the HMAC, re-derive the acting repository strictly from the same trusted source used for signature verification (or validate that `repository.full_name`'s owner equals the `repository_owner` used to pick the webhook secret) before any handler processes the payload. `StatusHandler` in particular should scope `Commit` lookups by the authenticated repository/stack rather than matching bare SHAs installation-wide.

### Proof of Concept
1. Register/control organization `attacker-org` in Shipit's `github` config, giving you its `webhook_secret`.
2. Build a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" },
  "sha": "<victim commit sha already tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "branches": [{"name": "master"}]
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and the signature validates (step in `lib/shipit/github_app.rb#verify_webhook_signature`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of `repository.full_name` — and calls `create_status_from_github!`, injecting a forged CI-passing status onto a repository/commit the attacker never authenticated for.
