### Title
Missing cross-call replay protection on L1 Bitcoin lockup outpoints allows double-crediting the same locked sats - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`validate-l1-lockup`, the fold step behind `verify-l1-lockups`, only prevents an outpoint from being counted twice *within a single call's list* via the `seen-outpoints` accumulator [1](#0-0) . There is no evidence in this contract that the same `{txid, output-index}` outpoint is recorded in a persistent map after being credited, so a staker can resubmit a proof for the exact same Bitcoin lockup output in a subsequent transaction (or across different `bond-index`/registration calls) and have the sats counted again.

### Finding Description
`verify-l1-lockups` seeds a fresh `seen-outpoints: (list)` accumulator for every call and folds `validate-l1-lockup` over the supplied `outputs` list (max 10 entries) [2](#0-1) . Inside the fold, the only duplicate-detection is `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)`, checked against the in-memory list built up during *this* fold, then appended to that same transient list [3](#0-2) , [4](#0-3) . The comment explicitly documents the scope as "tracks every (txid, output-index) pair already credited in this call" [5](#0-4) .

This is the same equality-violating pattern as the CVE: the check verifies identity against the wrong/insufficient scope (an ephemeral, call-local list instead of durable global state), while the side effect it gates — crediting sats toward the staker's bond/lockup sum — is applied to durable, long-lived contract state (the `sum` returned by `verify-l1-lockups`, which callers presumably use to credit sBTC/stacking weight). Because the sum returned by one call is not checked against a persisted "already-claimed outpoints" set, nothing stops the same Bitcoin UTXO's lockup proof from being replayed across multiple transactions (or within different bond periods/registrations), crediting the same locked-on-L1 sats more than once.

I was not able to locate, within the scope reachable in this session, a map such as `used-l1-outpoints` or similar persisted structure that `validate-l1-lockup` or its caller consults/writes to prevent cross-call reuse of an outpoint. If such a persistent map exists elsewhere in `pox-5.clar` and is checked before `verify-l1-lockups` is invoked (e.g., in `register-for-bond`), this finding would not hold; I could not confirm its presence or absence with certainty given the remaining budget, so this should be verified against the caller of `verify-l1-lockups`.

### Impact Explanation
If no persistent replay protection exists, an attacker can submit the same valid L1 lockup proof multiple times across separate `register-for-bond`/lockup-verification transactions to inflate their credited/summed sats without locking additional BTC — i.e., "sats credited by an L1 proof that were never locked on Bitcoin" (double-counting a commitment). This directly breaks the equality between BTC actually locked on L1 and sats credited within pox-5, which per the given impact rules is Critical (double-counting a commitment / unbacked crediting of value never locked).

### Likelihood Explanation
Likelihood is uncertain without confirming whether the caller path (e.g. `register-for-bond`) persists consumed outpoints elsewhere. Purely from the code visible in `validate-l1-lockup`/`verify-l1-lockups`, the guard is scoped to a single call, which is a straightforward, low-skill-requirement replay if no external persistence exists — the attacker only needs to resubmit an already-used, publicly visible Bitcoin transaction/merkle proof.

### Recommendation
Persist every credited outpoint in a durable Clarity map (e.g., `used-l1-lockup-outpoints`) keyed by `{txid, output-index}` (or a stronger identity incorporating `staker`/`bond-index` per the contract's intended semantics), check it in `validate-l1-lockup` in addition to the call-local `seen-outpoints`, and mark it used before/at the point sats are counted toward `sum`, so no outpoint can ever be credited more than once across the contract's lifetime.

### Proof of Concept
Conceptual (unverified against the full caller path due to session limits):
1. Attacker locks BTC to the pox-5 timelock script, producing a valid outpoint `(txid, output-index)`.
2. Attacker calls `register-for-bond`/the entry point that invokes `verify-l1-lockups` with a proof for that outpoint; sats are credited.
3. Attacker calls the same entry point again (new transaction, new bond registration, or a different `bond-index`) with the identical outpoint's proof. Since `seen-outpoints` is reinitialized per call, `is-none (index-of? seen-outpoints outpoint)` passes again, and the sats are credited a second time without any new BTC being locked.
