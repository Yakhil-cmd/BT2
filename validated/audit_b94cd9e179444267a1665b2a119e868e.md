### Title
Webhook signature verification is scoped to the wrong organization, allowing status/push forgery across repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner` (taken from `params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, and especially `StatusHandler`) use a completely different, unverified field: `payload.dig('repository', 'full_name')` for scoping, or in the case of `StatusHandler`, no repository scoping at all. The equality the code implicitly assumes — "the organization whose secret validated this signature" == "the repository/commit that gets mutated" — is never enforced.

### Finding Description
`verify_signature` in [1](#0-0)  picks the org-scoped `github_app` purely from `repository_owner`, and `GithubApp#verify_webhook_signature` has a bypass: `return true unless webhook_secret` [2](#0-1) . Per the setup docs, the webhook secret is explicitly optional ("Webhook secret (optional)") [3](#0-2) , so any organization configured without one accepts arbitrary, unsigned payloads as long as `repository.owner.login` (or `organization.login`) names that unsecured org — information that is public.

Once past `verify_signature`, the payload is dispatched to handlers keyed only by event type, with `handler.call(params)` on the raw JSON [4](#0-3) . None of the handlers re-check that `repository.owner.login` (the field that was verified) matches the repository/commit they operate on:

- The base `Handler` scopes by `payload.dig('repository', 'full_name')`, an independent field from `repository.owner.login`, with no cross-check between the two [5](#0-4) . `PushHandler` uses that scoping to call `stack.sync_github(expected_head_sha: params.after)` on any tracked stack whose `full_name` was named in the forged payload [6](#0-5) .
- `StatusHandler` doesn't even use repository scoping — it looks up `Commit.where(sha: params.sha)` globally across the entire Shipit install and writes a GitHub status onto it: `commit.create_status_from_github!(params)` [7](#0-6) .

`create_status_from_github!` persists the forged status [8](#0-7) , and `Commit#deployable?`/`schedule_continuous_delivery` read from that status to decide auto-deploy eligibility: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and continuous delivery is scheduled right after status changes trigger new commit creation or explicit refresh [9](#0-8) [10](#0-9) .

### Impact Explanation
An unprivileged, unauthenticated attacker who knows (a) the login of any GitHub organization configured in this Shipit instance without a `webhook_secret` (public information, discoverable simply by knowing which orgs are onboarded) and (b) the `full_name`/SHA of a commit belonging to a *different*, secured organization's tracked repository can:
- Forge a `push` event naming the secured repo's `full_name` to trigger `GithubSyncJob`/`sync_github` on it.
- Forge a `status` event with an arbitrary `sha` (globally, not scoped to any repository) to inject a fake "success" CI status onto any tracked commit in the whole installation, which can flip `deployable?` to true and trigger `ContinuousDeliveryJob` for stacks with continuous deployment enabled — resulting in an unauthorized deploy.

This crosses the "GitHub organization authenticated versus repository/commit written" trust binding and can produce a Critical-class impact (unauthorized deploy) per the scope rules, without requiring any Shipit session, API token, or the target organization's own webhook secret.

### Likelihood Explanation
Requires: (1) the target Shipit instance to have at least one configured GitHub organization without a webhook secret (explicitly documented as optional, so plausible in real deployments, especially single-org setups where operators skip it), and (2) knowledge of a target repository's `full_name` and a commit SHA (both easily obtainable from the public GitHub repo). No credentials, sessions, or private secrets are required for the org lacking a secret. Likelihood is moderate-to-high in default/loosely-configured environments and zero in installs where every configured org (single or multi-org) sets `webhook_secret`.

### Recommendation
Enforce that the field used for signature-verification scoping (`repository_owner`) is the same field the handler subsequently uses to scope its side effects:
- In `Handler#repository_name`/`stacks`, cross-check `payload.dig('repository','owner','login')` against the resolved `Repository`'s actual owner before acting.
- In `StatusHandler`, scope `Commit` lookups by the stack/repository resolved from the verified owner instead of a global `Commit.where(sha:)`.
- Consider making `webhook_secret` mandatory (remove the `return true unless webhook_secret` bypass, or fail closed) so an org can never be used as an "impersonation vector" for another org's repositories.

### Proof of Concept
1. Configure (or identify) an installation where org `unsecured-org` has no `webhook_secret` set, per `config/secrets*.yml` examples [11](#0-10) .
2. Send `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/whatever" },
  "sha": "<sha of a commit belonging to secured-org/target-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` is required to pass verification, because `verify_webhook_signature` short-circuits to `true` when `unsecured-org`'s `webhook_secret` is blank [12](#0-11) .
3. `StatusHandler#process` finds the commit purely by `sha` (no ownership check) and records the forged "success" status [7](#0-6) .
4. If `secured-org/target-repo`'s stack has `continuous_deployment: true` and this was the last required status, `Commit#deployable?` becomes true and `ContinuousDeliveryJob` is scheduled, resulting in an unauthorized deploy of attacker-chosen code.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
