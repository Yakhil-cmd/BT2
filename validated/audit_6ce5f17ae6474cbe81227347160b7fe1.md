### Title
Webhook signature verification is keyed to `repository.owner.login`, but event handlers act on the independent, unvalidated `repository.full_name` field - allowing forged cross-repository events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify a payload against based on `repository.owner.login` (or `organization.login`). However, the actual event handlers that mutate application state resolve the target `Stack`/`Repository` from a completely different, independently-controlled field of the same JSON body: `repository.full_name`. Nothing in the code enforces that these two fields refer to the same repository/organization, and signature verification silently no-ops (`return true unless webhook_secret`) whenever the resolved org's config has no `webhook_secret` configured - a state the documentation itself labels "optional."

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == organization/repository that the handler actually writes to**. This binding is broken across two files.

1. `verify_signature` picks the GitHub App config purely from a payload field, then checks the signature against the whole raw body using that org's secret: [1](#0-0) [2](#0-1) 

2. The actual secret-check logic fails open when no secret is configured for that org - a state explicitly presented as optional in the setup docs (`Webhook secret (optional)`): [3](#0-2) 

3. Once the request passes (either because a valid secret was actually used, or because it failed open due to a blank `webhook_secret` for the org resolved from `repository.owner.login`), the full raw JSON `params` is handed unmodified to every registered handler: [4](#0-3) 

4. Handlers resolve the *actual* target repository/stack from `repository.full_name` - a field that was never cross-checked against `repository.owner.login`/the org used for signature selection: [5](#0-4) 

5. That resolved stack is then acted on directly, e.g. `PushHandler` triggers a GitHub sync for any stack matching the branch of the named repo, and `StatusHandler` writes commit statuses for any commit with a matching sha, regardless of which repository/org it belongs to: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used only to pick a secret / decide whether to enforce one at all) and `repository.full_name` (used to pick the repository actually written to) are independent JSON fields with no cross-validation, an attacker who crafts a payload naming an organization with no `webhook_secret` configured for the `owner.login` field, while pointing `repository.full_name` at any other stack registered in the same Shipit installation, gets that forged event fully processed - identical in shape to the smart-contract bug where `verifyState` checks one representative slot/entry and treats the whole structure as consistent, letting an attacker manipulate an unchecked region (`foo`/`evaluatedCFrags`) that the check never actually covers.

### Impact Explanation
This is an unauthenticated, unprivileged write across repository/organization boundaries on a publicly reachable endpoint (`/webhooks` explicitly skips CSRF protection: `skip_before_action :verify_authenticity_token`). An attacker with zero credentials can trigger `stack.sync_github`, forge commit statuses, deployable/merge status changes, or membership changes for any stack registered in the Shipit instance, as long as any one configured GitHub org lacks a `webhook_secret` (a state the docs call optional and the shipped example/dev configs default to `nil`). This matches the "cross-repository writes" / "unauthorized deploy" Critical-impact criteria.

### Likelihood Explanation
Likelihood depends on deployment configuration: it is fully exploitable with no credentials whenever at least one configured GitHub App entry in `Shipit.github` has `webhook_secret` unset - which the setup docs and every shipped example config (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `secrets_double_github_app.yml`) present as the default/optional state. Multi-org installs (as explicitly supported and documented, see `secrets_double_github_app.yml`) increase the attack surface because a low-value org's missing secret can be used to forge events for a high-value org's repository/stack in the same instance.

### Recommendation
- After signature verification, re-derive the organization strictly from the verified `repository.owner.login`/`organization.login` and require that `repository.full_name`'s owner segment match it before dispatching to handlers; reject on mismatch.
- Do not allow `verify_webhook_signature` to fail open (return `true`) when `webhook_secret` is blank; either require a secret to be configured for every org before accepting webhooks, or explicitly scope unauthenticated orgs so they cannot act on stacks belonging to other repositories/orgs.
- Update `docs/setup.md` to state that omitting `webhook_secret` disables event-forgery protection for every stack in the installation, not just for that one organization.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgWithoutSecret` (no `webhook_secret`) and `OrgWithSecret` (has a `webhook_secret` and owns a real production stack), as supported by `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "OrgWithSecret/production-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without any HMAC check.
4. `PushHandler#process` resolves the target repository from `repository.full_name` = `"OrgWithSecret/production-repo"` via `Handler#repository_name`, finds the real stack, and triggers `stack.sync_github(expected_head_sha: "deadbeef")` - a forged sync/deploy trigger for a repository the attacker never had credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
