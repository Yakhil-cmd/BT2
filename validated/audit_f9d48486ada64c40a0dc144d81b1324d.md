## Title
Use-After-Free-style Race Condition in Unlocked AA Dry-Run Execution Corrupting Shared In-Memory Unit Caches - (File: `aa_composer.js`, `network.js`)

## Summary
CVE-2018-9422 is a Linux kernel use-after-free caused by `get_futex_key()` operating on a shared object without holding the lock that protects it against concurrent modification/release, letting another thread free/mutate the object mid-use. The analogous root cause exists in ocore's `light/dry_run_aa` RPC handler: it drives a **real, mutating execution** of an AA trigger (`aa_composer.dryRunPrimaryAATrigger`) through the ordinary `writer.saveJoint()` path — which inserts entries into the process-wide, unprotected in-memory caches `storage.assocUnstableUnits` / `storage.assocBestChildren` / `storage.assocStableUnits` — **without acquiring the `handleJoint`/`write` mutex** that every other codepath touching these caches relies on for exclusivity.

## Finding Description
`handleRequest()`'s `light/dry_run_aa` case is reachable by any connected peer (no `ws.bSubscribed` gate, unlike e.g. `catchup`) and simply calls straight into the AA engine: [1](#0-0) 

`dryRunPrimaryAATrigger()` takes its own DB connection and drives the full trigger-execution/response-unit-generation logic through `handleTrigger`, using the normal (non-estimation) code path that performs real inserts and mutates the shared caches, then rolls back only the DB transaction: [2](#0-1) 

Critically, neither `dryRunPrimaryAATrigger()` nor the real trigger executor `handlePrimaryAATrigger()` acquire the `handleJoint`/`write` mutex that guards `storage.assocUnstableUnits` elsewhere (e.g. unit validation/writing in `network.js`'s `handleJoint`, or MC stabilization in `main_chain.js`): [3](#0-2) [4](#0-3) 

Response units generated inside the dry run are added to `storage.assocUnstableUnits`/`assocBestChildren` via the ordinary `writer.saveJoint()` path and only cleaned up afterward by `revertResponsesInCaches()`: [5](#0-4) 

`storage.forgetUnit()` unconditionally dereferences `assocUnstableUnits[unit]` with no existence check: [6](#0-5) 

Because these caches are global, singleton JS objects shared by every unit-validation, AA-trigger and stabilization code path (`markMcIndexStable` deletes entries from the very same map during normal MC stabilization): [7](#0-6) 

an interleaving where a `light/dry_run_aa` request's cache insert/forget sequence overlaps (between Node.js event-loop callback boundaries) with real unit processing or MC stabilization touching the same unit/parent keys can cause `forgetUnit()` to be invoked on an already-deleted `assocUnstableUnits[unit]` entry (or vice versa: a legitimate unit being deleted after — or missing a — `_.pull` step performed against a since-forgotten dry-run object still referenced in `assocBestChildren`). This mirrors the futex bug's essence: an object reachable through a shared structure is freed/mutated by one path while still referenced/expected-present by another path that lacks the same lock.

## Impact Explanation
`forgetUnit()`'s unchecked `assocUnstableUnits[unit].parent_units` throws a `TypeError` when the entry is already gone, and this throw occurs deep inside async callback chains outside any `try/catch`, crashing the Node.js process. A single unauthenticated/light peer can trigger this by sending `light/dry_run_aa` for an existing AA while the node concurrently processes ordinary traffic (new units, AA trigger execution, MC stabilization) that touches the same shared unit-cache keys — resulting in denial of service that halts unit confirmation, i.e. "a network unable to confirm new units." Beyond the crash, silent corruption of `assocBestChildren`/`assocUnstableUnits` (entries pulled/deleted out of order) can desynchronize a node's view of free/best-parent state used in consensus-relevant computations (best-parent selection, `is_free` bookkeeping), risking disagreement on validity/stability between nodes that received the same units in different interleavings.

## Likelihood Explanation
No special privileges are required — `light/dry_run_aa` is served to any connected peer/light client with only address/trigger-shape validation, and dry runs against an existing AA whose logic causes an error/insufficient-storage-balance bounce are trivial to craft (any AA with a state/storage-size branch triggered by attacker-controlled trigger payload). Triggering the race merely requires timing the request against the node's normal, ongoing traffic (new units, background `aa_triggers` handling), which happens continuously on a live hub/full node, making repeated attempts practical.

## Recommendation
Serialize `dryRunPrimaryAATrigger()` (and `handlePrimaryAATrigger()`) with the same `handleJoint`/`write` mutex used by unit validation and MC stabilization before any mutation of `storage.assocUnstableUnits`/`assocBestChildren`/`assocStableUnits` is possible, or refactor dry-run estimation to operate purely on cloned/local state (as `estimatePrimaryAATrigger`'s `bAir` mode already does) instead of exercising the real `writer.saveJoint` write path. Additionally, make `storage.forgetUnit()` defensive against a missing/already-forgotten `assocUnstableUnits[unit]` entry instead of throwing.

## Proof of Concept
1. Deploy/target an AA whose invocation can be made to fail deep in execution (e.g., insufficient byte balance for `storage_size`, causing `revert()`), and repeatedly send it real trigger units so `handleAATriggers`/`handlePrimaryAATrigger` runs continuously in the background.
2. From an unauthenticated peer connection, flood `light/dry_run_aa` requests against the same AA address with a crafted trigger, causing `dryRunPrimaryAATrigger` → `handleTrigger` → `revert()` → `revertResponsesInCaches()` to run repeatedly and race with the concurrently running `handlePrimaryAATrigger`/`markMcIndexStable` cache mutations on `storage.assocUnstableUnits`.
3. Given enough interleavings, `storage.forgetUnit()` is invoked for a unit whose `assocUnstableUnits` entry was already removed by the concurrent legitimate path, throwing an uncaught `TypeError` inside the async callback chain and crashing the node process (verifiable via `node --stack-trace-limit` process exit logs referencing `forgetUnit`).
