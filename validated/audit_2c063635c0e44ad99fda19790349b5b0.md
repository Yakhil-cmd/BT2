### Title
Unbounded in-memory buffering of git command stdout/stderr enables memory-exhaustion DoS via attacker-controlled ref/verbose output - ([File: pkg/cmd/cmd.go])

### Summary
`runWithStdin` in `pkg/cmd/cmd.go` captures the entire stdout and stderr of every git subprocess (e.g. `git fetch ... --verbose`) into unbounded `bytes.Buffer` instances before returning them as strings. Since `fetch()` in `main.go` invokes `git fetch` with `--verbose` by default, an attacker who controls the content/refs of the synced repository can inflate the volume of verbose output git emits, and that entire output is buffered fully in git-sync's process memory with no cap.

### Finding Description
`Runner.Run`/`Runner.RunWithStdin` (`pkg/cmd/cmd.go:51-61`) delegate to `runWithStdin`, which sets `cmd.Stdout = outbuf` and `cmd.Stderr = errbuf` where both are plain `bytes.NewBuffer(nil)` with no size limit [1](#0-0) . After `cmd.Run()` completes, the buffers are converted to strings and returned/embedded in error messages [2](#0-1) . There is no streaming, truncation, or byte-limit anywhere in this path — the full output of any git invocation is materialized in Go heap memory (as both the raw buffer and the trimmed string), effectively at least doubling memory usage relative to output size before it can be freed.

`fetch()` in `main.go` builds its git fetch argument list including `--verbose`, so every fetch cycle by default requests verbose ref-update reporting from git, and that output flows through this same unbounded-buffer `Run` path.

An attacker who controls the source repository content (refs, branches, tags) can increase the volume of `--verbose` fetch output (e.g., by maintaining or repeatedly changing/pushing a very large number of refs), causing git itself to emit proportionally large stdout/stderr text that git-sync fully buffers in memory on every sync cycle.

### Impact Explanation
This maps to a resource-exhaustion / persistent-stall impact class: repeated invocation of `fetch()` against a repo with attacker-inflated verbose output can drive the git-sync container's memory usage up on every sync interval, eventually triggering an OOM kill by the container runtime/kubelet. Because git-sync re-fetches on every configured interval, this can recur indefinitely, producing a persistent CrashLoopBackOff / denial-of-service against the sync sidecar (and thus against consumers relying on the synced content), without any code execution or credential/secret exposure.

### Likelihood Explanation
Feasibility is constrained by scale: to produce output on the order of hundreds of megabytes to gigabytes via `--verbose` per-ref lines, the attacker-controlled repository would need an extremely large number of refs/branches (order of millions), which is costly to create and push, and the `git fetch` operation itself would take a correspondingly long time and consume significant network/CPU before the buffering issue dominates. No non-default git-sync flags are required (`--verbose` fetch is baked in), but the practical exploit requires the attacker to operate/control a git remote capable of serving an unusually large ref set, and git-sync's own network/CPU limits or `--sync-timeout` may interrupt the fetch before the buffer grows unbounded. This makes the attack technically possible but resource-intensive and comparatively low-likelihood in typical deployments.

### Recommendation
Replace the unbounded `bytes.Buffer` stdout/stderr capture in `runWithStdin` (`pkg/cmd/cmd.go`) with a bounded writer (e.g., an `io.Writer` that caps total bytes and discards/truncates beyond a configurable limit, appending a "output truncated" marker), or stream git command output directly to the process log instead of buffering it fully for return values. Additionally, consider making `--verbose` optional/rate-limited for fetch based on ref-count heuristics, or capping the number of refs processed per fetch.

### Proof of Concept
Unit-test approach for `pkg/cmd/cmd_test.go` (conceptual, since actual test file wasn't inspected):
1. Create a fake `command` (or a real git repo) whose invocation prints, say, 500MB of text to stdout (e.g., `yes` piped through `head -c 500000000` invoked via `Runner.Run`).
2. Call `Runner.Run(ctx, cwd, nil, "sh", "-c", "yes | head -c 500000000")`.
3. Monitor process RSS during the call; assert that memory usage grows proportionally to the printed output size (confirming full in-memory buffering with no cap), and that `Run` does not return until the entire output has been read into memory.
4. For the git-specific path, set up a local bare repo with a large number of refs (e.g., 100k+ lightweight tags) and invoke `git fetch --verbose` through `Runner.Run`, observing the returned stdout string length scaling linearly with ref count, confirming the unbounded buffering behavior described above.
