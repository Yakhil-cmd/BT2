### Title
Cross-repository status injection triggers unauthorized deploys via unscoped `Commit.where(sha:)` lookup - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook using only the git SHA, with no check that the SHA belongs to a stack tracking the repository named in the payload that was actually signature-verified. `WebhooksController#verify_signature` only proves the request was legitimately signed by *some* registered GitHub organization/app (selected via `repository_owner`, i.e., `params.dig('repository','owner','login')`); it never re-checks that this organization/repository matches the commit(s) the handler subsequently mutates.

### Finding Description
The broken binding: `verified_repository_owner (from payload, used only for HMAC key selection) == commit.stack.repository.owner` is assumed but never enforced.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the attacker-controlled JSON body (`app/controllers/shipit/webhooks_controller.rb:59-62`), and verifies the HMAC signature using that organization's `webhook_secret`. This only proves "this payload was signed by whoever owns the `webhook_secret` registered for the org named `attacker`'s repository owner" — it says nothing about which commit/stack the payload's `sha` should be allowed to affect.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries **all** `Commit` rows across **every stack in the installation** matching the raw `sha` string — there is no `stack_id`, `repository`, or `github_repo_name` filter tying the lookup back to the payload's `repository` field or to the organization used for signature verification.
3. `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:165-169, 366-386`) creates the `Status`, and since the state transitions to `success`, calls `stack.schedule_merges` and, via the `Status` model's `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) and `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), enqueues `ContinuousDeliveryJob.perform_later(stack)` if `commit.deployable? && stack.continuous_deployment? && stack.deployable?`.
4. `ContinuousDeliveryJob` calls `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy`, creating a real `Deploy` for the **victim's** stack — even though the HTTP request that triggered all of this was signed for, and about, `attacker/repo`.

Exploit: attacker who legitimately controls their own repo/org registered in Shipit (with a real `webhook_secret` for that org, as supported by Shipit's multi-organization GitHub App config, see `lib/shipit/github_app.rb:44-57` and `test/dummy/config/secrets_double_github_app.yml`) sends `POST /webhooks` with `X-Github-Event: status`, a validly-signed body for `attacker/repo`, but with `sha` set to the victim stack's pending commit SHA and `state: success`. Signature verification passes (it's genuinely signed, just for the wrong repo). `StatusHandler#process` finds the victim's `Commit` purely by matching SHA and applies the attacker-supplied status to it, flipping `deployable?` to true and triggering an unauthorized deploy.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) close this gap: `verify_signature` authenticates the *sender*, not the *target record*; the `ExplicitParameters` schema on `StatusHandler` only validates the shape of `sha`/`state`/etc., not that they refer to the sender's own repository; there is no model validation tying a `Status`'s `stack_id` to the `repository` field of the originating webhook.

### Impact Explanation
An attacker who legitimately controls one repository/organization registered in a Shipit installation can, purely from a webhook they sign themselves, write a `Status` record to and trigger an unauthorized `Deploy` for **any other stack in the same installation**, as long as they know (or can guess) that stack's pending commit SHA — information often visible via the target repo's public GitHub history/PRs or the Shipit stack UI itself. This is repeatable against arbitrary stacks/commits and constitutes "a payload for one repository mutating another's stack, commit, task... or an unauthorized deploy," matching the **Critical** severity category.

### Likelihood Explanation
Preconditions: the attacker must control at least one repository/org that is itself legitimately onboarded into the same Shipit instance (so they possess a real, valid `webhook_secret`), which is realistic in any multi-tenant Shipit deployment serving multiple teams/orgs. The victim stack must have `continuous_deployment: true` (a common CD configuration) and a pending un-successful commit whose SHA the attacker can discover. Attacker cost is a single crafted HTTP POST with correctly computed HMAC using their own secret — no privileged Shipit role, session, or victim secrets are required.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository asserted in the verified webhook payload (e.g., join through `stack` and compare `stack.repository_owner`/`stack.repository_name` — or `github_repo_name` — to `params.repository.full_name`), rejecting or ignoring statuses whose `sha` matches a commit belonging to a different repository than the one the signature was verified against. The same repository-binding check should be applied to other handlers that resolve records purely by SHA/branch without checking the authenticated repository (e.g., `PushHandler`, `CheckSuiteHandler`) to avoid analogous cross-tenant confusion.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status payload for one repository must not trigger a deploy on another stack's commit" do
          victim_stack = shipit_stacks(:shipit) # or any fixture stack with continuous_deployment: true
          victim_stack.update!(continuous_deployment: true)
          victim_commit = victim_stack.commits.last
          victim_commit.statuses.destroy_all
          refute victim_commit.reload.deployable?, "precondition: commit must not already be deployable"

          # Simulate attacker's webhook payload: signed for attacker/repo, but sha == victim's commit sha
          attacker_payload = ActionController::Parameters.new(
            sha: victim_commit.sha,
            state: 'success',
            description: 'forged',
            context: 'ci/attacker',
            created_at: Time.now.to_s,
            repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } }
          )

          assert_no_difference -> { Deploy.count } do
            StatusHandler.new.process(attacker_payload) # or however params object is constructed
          end
        end
      end
    end
  end
end
```
Equality asserted before: `params.repository.full_name` ("attacker/repo") != `victim_stack.repository.full_name` — should remain unequal after the request, i.e., the victim stack's `Deploy.count` must not change. Currently (per code trace above), `Commit.where(sha: params.sha)` ignores this inequality entirely and applies the status regardless, so `Deploy.count` for `victim_stack` increases — confirming the vulnerability.
