### Title
Webhook signature routing keyed on `repository.owner.login` while all event handlers act on the independent, unsigned `repository.full_name` field allows cross-repository forgery when any configured GitHub App has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The `previewMint()`/`mintWithSignature` bug is a case where a signature is checked against one value while a different, unbound value is actually used by the executing logic. The same class of bug exists in `WebhooksController`: the field used to pick *which* HMAC secret verifies the request (`repository.owner.login`) is completely independent from the field every event `Handler` actually uses to select the `Stack`/`Repository` to mutate (`repository.full_name`). Both fields live in the same attacker-controlled JSON body of an unauthenticated `POST /webhooks` request.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization (and therefore the webhook secret) to validate against using a value pulled from the untrusted JSON payload, before any signature has been verified: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GithubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as automatic success: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

Per `docs/setup.md`, `webhook_secret` is explicitly documented as **optional**, and Shipit officially supports multiple independently configured GitHub Apps/organizations (`Shipit.github_organizations`, `github_app_config`) [4](#0-3) [5](#0-4) .

Meanwhile, every actual event `Handler` (push, pull_request, status, etc.) resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, which is never consulted during signature routing: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are independent keys inside the same freely attacker-authored JSON body, and because `create` re-parses the full raw body without re-checking that these two fields agree [8](#0-7) , an attacker can pick `repository.owner.login` equal to any organization configured **without** a `webhook_secret` (an officially supported, documented configuration) so that `verify_webhook_signature` trivially returns `true`, while setting `repository.full_name` to the full name of a completely unrelated, existing `Stack`'s repository (e.g. one belonging to an org that *does* have a secret). The signature check never actually authenticates the organization/repository that is subsequently written.

### Impact Explanation
This breaks exactly the equality the rules define as in-scope: "an organization that authenticated versus the repository that is written." An unauthenticated, unprivileged internet attacker (no GitHub access, no `webhook_secret` knowledge) can forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events for any repository already tracked in Shipit, as long as at least one configured GitHub App/organization in the deployment has no `webhook_secret` set — a state explicitly documented as optional/supported. Consequences include triggering `stack.sync_github` for arbitrary Stacks, injecting forged commit `Status` records that gate CI-based deploy safety checks (`PushHandler`, `StatusHandler`), or creating/removing `Membership`/`Team` records — undermining deploy authorization decisions and potentially enabling an unauthorized deploy/rollback path (Critical/High per the given impact list) without ever touching `webhook_secret`, `api_clients_secret`, or any session/token.

### Likelihood Explanation
Any Shipit deployment using the documented "Multiple GitHub Applications" feature, or simply leaving the optional `webhook_secret` blank for one organization (as shown in the example config files in this repo) is affected. `/webhooks` is unauthenticated by design (it's meant to receive GitHub's calls), so the attack surface is directly internet-reachable with no credentials required.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository resolution: require that `repository.owner.login`/`organization.login` and the owner segment of `repository.full_name` match, and reject the request otherwise. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` on a missing `webhook_secret` when other organizations in the same deployment do have secrets configured — either require a secret whenever more than one GitHub App is configured, or ensure that unsigned-app payloads can only ever affect repositories that belong to that specific unsigned org.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `OrgA` (no `webhook_secret` set — supported per docs) and `OrgB` (has `webhook_secret` set, hosts a tracked `Stack` for `OrgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `create` re-parses the same body and dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [9](#0-8)  and triggers `stack.sync_github(expected_head_sha: ...)` on the `OrgB` stack — despite `OrgB`'s webhook secret never having been verified.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
