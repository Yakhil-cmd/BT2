### Title
Webhook `StatusHandler` applies status updates to commits across all repositories by SHA alone, triggering `Commit#schedule_continuous_delivery` for a victim stack from an attacker-named repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever filtering by the webhook's `repository.full_name`. Because git SHAs are not repository-scoped (identical commits are common across forks/mirrors of the same upstream history), a signed `status` webhook for `attacker/repoA` can update the status of a commit that belongs to `victim/repoB`'s stack, which then fires `Commit#schedule_continuous_delivery` and enqueues `ContinuousDeliveryJob.perform_later(stack)` for the victim's stack.

### Finding Description
The claimed binding is: `ContinuousDeliveryJob.perform_later(stack)`'s `stack` == the `stack` derived from `payload.dig('repository', 'full_name')`.

Tracing the code:
- `Shipit::WebhooksController#create` verifies the GitHub signature per `repository_owner` [1](#0-0)  then dispatches every matching handler with the raw parsed payload [2](#0-1) . This only proves the payload really came from GitHub for the org that owns the named repository - it says nothing about which stacks the payload is allowed to touch.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, derived from `payload.dig('repository', 'full_name')` [3](#0-2) .
- `StatusHandler#process`, however, ignores this helper entirely and instead does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . No repository or stack filter is applied - any commit row anywhere in the installation with a matching `sha` column is updated.
- `Commit#create_status_from_github!` -> `add_status` writes the new status via `statuses.replicate_from_github!(stack_id, github_status)`, using the *matched commit's own* `stack_id` [5](#0-4) .
- `after_commit :schedule_continuous_delivery` on new-commit creation (or via `RefreshStatusesJob`) then checks `deployable? && stack.continuous_deployment? && stack.deployable?` on `self.stack` (the victim stack, correctly bound via `belongs_to :stack`) and enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` for that stack [6](#0-5) .

So `Commit#schedule_continuous_delivery` itself binds correctly to its own `stack` (the FK is sound); the break is upstream in `StatusHandler#process`, which never checks that the commit's stack belongs to the repository named in the webhook. The attacker's exact request: send (or cause GitHub to send, e.g. via their own repo's CI reporting a commit status) a legitimately-signed `status` webhook for `attacker/repoA` naming a `sha` that is shared with a commit already present in `victim/repoB` (trivial when both repos share upstream history, e.g. forks, mirrors, or cherry-picked/rebased-without-modification commits). None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema check repository/stack ownership of the matched `Commit` rows - they only validate signature and payload shape, not the cross-repository SHA collision. `force_github_authentication`, `User#authorized?`, and `require_permission!` are not on the webhooks path at all.

### Impact Explanation
A single crafted/legitimate-looking status event for a repository the attacker fully controls can flip the status of, and enqueue a real continuous-deployment run for, a completely unrelated victim stack - matching the "unauthorized deploy" and "payload for one repository mutating another's stack, commit, task" Critical categories. This is repeatable against any stack in the installation whose commit history shares a SHA with any repository the attacker can push to or generate signed status events for, and generalizes across all tenants sharing one Shipit instance.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment?` and `stack.deployable?` true, and a shared/colliding commit SHA exists between attacker's own repository and the victim's tracked branch (common via forks/mirrors/rebase-preserving-SHA workflows). Attacker cost is low: they only need to produce a genuine signed webhook for a repo they own (e.g. by pushing/creating a commit status through GitHub's normal API on their own repository) - no Shipit credentials, session, or GitHub App secrets are needed.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks derived from the webhook's own repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `Handler#stacks` helper that already derives stack scope from `payload.dig('repository', 'full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook naming attacker/repoA must not trigger continuous delivery for victim/repoB" do
  shared_sha = "a" * 40

  attacker_stack = shipit_stacks(:shipit) # repo_name "attacker/repoA"
  victim_stack = shipit_stacks(:cyclimse) # repo_name "victim/repoB"
  victim_stack.update!(continuous_deployment: true, lock_reason: nil)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared")

  payload = {
    "repository" => { "full_name" => "attacker/repoA" },
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci",
  }

  ContinuousDeliveryJob.expects(:perform_later).with(victim_stack).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # demonstrate the actual (vulnerable) behavior fires anyway:
  # ContinuousDeliveryJob.expects(:perform_later).with(victim_stack)
  # Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  # victim_commit.reload -> status flipped to success though webhook named attacker/repoA
end
```
Equality to check: `payload.dig('repository','full_name') == "attacker/repoA"` vs. `ContinuousDeliveryJob.perform_later(stack).stack.repo_name == "victim/repoB"` - they diverge, proving the vulnerability.
