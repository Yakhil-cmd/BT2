### Title
Cross-Repository Commit Status Forgery via Unscoped SHA Lookup in Webhook Status Handler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook only against the organization derived from `repository.owner.login` in the payload [1](#0-0) , using that organization's `webhook_secret` (`GitHubApp#verify_webhook_signature`) [2](#0-1) . However, `Handlers::StatusHandler#process` never re-checks that binding: it resolves the target commit purely by `sha` across the entire `Commit` table, spanning every stack/repository/organization hosted on the Shipit instance, and then writes a GitHub status onto it [3](#0-2) . This breaks the equality `organization authenticated == repository written`: the signature only proves the payload originated from *some* configured organization, not that the `sha` belongs to that organization's repository. Every other default handler correctly scopes through `Handler#stacks`, which resolves via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) ; `StatusHandler` bypasses this scoping entirely.

### Finding Description
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the organization (`return true unless webhook_secret`) [5](#0-4) , and the setup documentation explicitly shows `webhook_secret` as an optional field that can be left blank [6](#0-5) . More generally, even where a valid `webhook_secret` exists, that secret only proves the sender knows the secret for *an* organization onboarded to the Shipit instance — not that the `sha` targeted in the payload belongs to a commit within that organization's repositories.

Once `verify_signature` passes, `WebhooksController#create` dispatches the parsed JSON straight to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler` [7](#0-6) . `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no `stack`/`repository` filter [3](#0-2) . `Commit#create_status_from_github!` writes the forged status directly into `statuses`, which recomputes `Commit#status`, `deployable?`, and triggers `stack.schedule_merges` if the new status is `success` [8](#0-7) [9](#0-8) . `deployable?` and merge-queue gating (`MergeRequest#all_status_checks_passed?`) both depend on this same `statuses` association [10](#0-9) [11](#0-10) .

Equality broken: **organization authenticated (via `repository_owner`/`webhook_secret`) ≠ repository whose commit is written (matched globally by `sha` with no stack/repo scoping)**.

### Impact Explanation
An attacker who can get any single valid (or secret-less) organization signature accepted by the shared webhook endpoint can forge a `success` (or any) CI status for a commit `sha` belonging to a completely unrelated stack/repository/organization also hosted on the same Shipit instance — as long as they know that target commit's SHA (commonly public information: visible in PRs, Git history, or the Shipit UI itself). This lets them:
- Satisfy `required_statuses`/`blocking_statuses` checks that gate deploys (`Commit#deployable?`) [10](#0-9) .
- Satisfy merge-queue gating (`MergeRequest#all_status_checks_passed?` / `any_status_checks_missing?`) [12](#0-11) , and trigger `stack.schedule_merges` [13](#0-12) , leading to an unauthorized `merge!` that calls the GitHub App's `merge_pull_request` on a repository the attacker has no legitimate write access to [14](#0-13) .

This qualifies as Critical: an unauthorized deploy/merge achieved with no Shipit session, no `ApiClient` token, and no legitimate access to the target repository/organization — only knowledge of the target commit's SHA and the ability to have any organization's webhook accepted by the shared endpoint.

### Likelihood Explanation
Moderate-to-high on any multi-tenant Shipit deployment (the documented, standard deployment shape supports multiple organizations under one `github:` config block, as shown in `config/secrets.development.shopify.yml`). The attacker needs: (1) at least one organization's signature to be accepted — trivially true for any org configured with a blank `webhook_secret`, which the docs present as a valid/normal configuration; and (2) the target commit SHA, which is routinely public. No Shipit credentials, GitHub App keys, or repository write access are required.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records by content fields alone) to the repository verified during signature validation — e.g. filter `Commit.where(sha: params.sha)` down to commits belonging to `stacks` (resolved via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, consistent with the base `Handler` class) before calling `create_status_from_github!`.

### Proof of Concept
1. Shipit instance configured with two organizations, `victim-org` (private, real webhook secret) and `attacker-org` (attacker controls the GitHub App/webhook config, e.g. leaves `webhook_secret` blank per the documented optional field).
2. Attacker learns the SHA of a commit `deadbeef...` in a `victim-org` stack that is currently blocked by a failing/missing required CI check (SHA is visible from the public PR/commit page or Shipit's own UI).
3. Attacker POSTs to the shared `/github/webhooks` endpoint with `X-Github-Event: status`, `repository.owner.login: "attacker-org"` (so `verify_signature` checks — and passes — against `attacker-org`'s secret/blank secret), and body `{ "sha": "deadbeef...", "state": "success", "context": "<required-context>" }`.
4. `StatusHandler#process` finds the commit purely by `sha` (ignoring that it belongs to `victim-org`) and creates a `success` status on it via `create_status_from_github!`.
5. The victim stack/commit now reports the required check as passing; `stack.schedule_merges` / continuous delivery is triggered, resulting in an unauthorized merge or deploy on `victim-org`'s repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
