## Title
`RewardState::calculate_reward()` aborts *all* Alpenglow per-slot vote-reward crediting/root-updates if a single reward-cert validator is missing from `reward_slot`'s epoch stakes - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
In Alpenglow's per-slot reward path, `calc_vote_rewards_update_vote_states()` computes and applies vote-credit rewards (and, when combined with a finalization cert, root-slot/vote updates) for a whole set of validators in a single call via `update_accounts()`. The per-validator work is done in a `for` loop, but any single validator's failure propagates with `?` out of the entire function, discarding the results already computed for every other validator in the same call — this mirrors the reported class of bug where distributing to a set of recipients reverts entirely because one recipient is invalid, instead of skipping just that one.

### Finding Description
`update_accounts()` iterates over all validators (either `reward_validators`, `signers`, or their union) and calls `state.update_account(&mut vote_state, &mut leader_reward)?` for each one: [1](#0-0) 

`RewardState::update_account()` calls `self.calculate_reward(...)?`, which looks up the validator's stake in `self.accounts` (the vote-accounts snapshot at `reward_slot`) and returns `RewardStateError::MissingRewardSlotValidator` if the validator isn't present there: [2](#0-1) [3](#0-2) 

Because the `for validator in validators` loop in `update_accounts()` uses `?` on this call instead of catching/skipping the error, a single validator missing from the `reward_slot` snapshot (e.g. a validator that was present in the reward certificate's validator set but had already deactivated its stake/closed or was otherwise absent from the `epoch_stakes` at `reward_slot`) causes the whole function to bail out with `Err`, discarding the in-progress `updated_accounts` map — including all correctly-computed credit updates for every other validator processed earlier in the loop, and skipping the leader-reward payout logic entirely (it's only reached after the loop completes).

This error is explicitly documented as fatal to block processing: [4](#0-3) 

It propagates up through `calc_vote_rewards_update_vote_states()` → `update_bank_with_footer_fields()` → `BankFooterError`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is architecturally analogous to the reported Solidity bug class: a batch operation over many independent recipients is designed to short-circuit entirely because one entry is invalid/missing, instead of processing the remaining valid entries (the intended, and demonstrably supported, error-tolerant pattern used elsewhere in the same reward system — e.g. `store_stake_accounts_in_partition()` and `RewardCommissionAccounts` calculation both catch per-account errors and continue/burn instead of aborting the whole batch): [8](#0-7) [9](#0-8) 

### Impact Explanation
If reached in production (i.e., if a validator can legitimately appear in a validated reward certificate's validator set while being absent from the `reward_slot` epoch-stakes vote-accounts snapshot — for example due to stake/vote-account closure or state divergence between cert construction and reward-slot processing), this causes `update_bank_with_footer_fields` (called during block/footer processing for every bank in the Alpenglow path) to return `Err`, which per the error doc comments "should cause the processing of the bank to fail." This would deny/lose vote credit rewards for every other validator being credited in that call (not just the missing one), and could cause replay/consensus divergence or a processing halt for the affected slot if different nodes disagree on whether the validator was present at `reward_slot` (e.g., due to fork/snapshot timing differences), which maps to the "epoch-boundary halt" / "cross-node state divergence" impact categories.

### Likelihood Explanation
I could not confirm, from the code available in the index, whether it is actually possible in practice for a validator entry to be present in `ValidatedRewardCert`'s validator set but absent from `reward_slot`'s `epoch_stakes` snapshot (this would depend on how `ValidatedRewardCert` validators are chosen/validated relative to `epoch_stakes_from_slot(reward_slot)`, code I was not able to fully trace with the available search results). If such certs are always guaranteed consistent with the epoch-stakes snapshot by construction/validation upstream, this path may be unreachable in normal operation, and the error would effectively function as a defensive invariant-violation check rather than an externally triggerable condition. This is a material gap that could not be verified with confidence.

### Recommendation
In `update_accounts()`, do not propagate `RewardStateError::MissingRewardSlotValidator` (and similarly recoverable per-validator errors) via `?` inside the per-validator loop. Instead, log the error, skip crediting that specific validator (similar to how `distribution.rs::store_stake_accounts_in_partition()` handles per-account `DistributionError`), and continue processing the remaining validators and the leader-reward payout. Reserve hard failure (`Err` propagation that aborts bank processing) only for genuinely block-wide fatal conditions (e.g. `MissingEpochStakes`, `MissingEpochInflationAccountState`, `GenesisCertNotFound`) that indicate the whole reward-slot dataset is unusable, not for a single validator's absence.

### Proof of Concept
Not independently reproducible from the available indexed code, since I could not confirm the upstream invariant about `ValidatedRewardCert` validator-set membership vs. `reward_slot` epoch-stakes membership. Conceptually: construct/inject a `ValidatedRewardCert` whose validator set includes a pubkey `V` that is a member of `reward_validators` but not present in `bank.epoch_stakes_from_slot(reward_slot).stakes().vote_accounts()` (e.g. `V`'s vote account or stake was removed by the time `reward_slot`'s epoch stakes were snapshotted), then call `calc_vote_rewards_update_vote_states()` with that cert containing multiple other legitimately-rewardable validators. `update_accounts()` will process earlier validators, then hit `V`, call `calculate_reward` → `Err(MissingRewardSlotValidator)`, and via the `?` at `vote_reward.rs:391/395` return `Err` for the whole call — as reflected in the existing test harness pattern (`calc_vote_rewards_update_vote_states(...).unwrap()`) at: [10](#0-9) 
where any single such mismatch would turn this `.unwrap()` into a panic in tests, and an `Err`/bank-processing failure in production.

                    reward_slot: self.reward_slot,

        Ok(validator_reward)

pub(super) fn calc_vote_rewards_update_vote_states(
    bank: &Bank,
    reward_cert: Option<ValidatedRewardCert>,
    final_cert_input: Option<(&HashSet<Pubkey>, Slot)>,
    block_producer_time_nanos: i64,
) -> Result<(), CalcVoteRewardUpdateVoteStatesError> {
    let Some(updated_accounts) = allocate_updated_accounts(bank, &reward_cert, &final_cert_input)?
    else {
        return Ok(());
    };
    let reward_state = match &reward_cert {
        Some(c) => Some(RewardState::try_new(
            bank,
            c.slot(),
            c.validators(),
            block_producer_time_nanos,
        )?),
        None => None,
    };
    let final_cert_state = final_cert_input.map(|(signers, final_slot)| {
        FinalCertState::new(bank, signers, final_slot, block_producer_time_nanos)
    });
    let vote_accounts = bank.vote_accounts();

    let updated_accounts = match (&reward_state, &final_cert_state) {
        (None, None) => return Ok(()),
        (Some(state), None) => update_accounts(
            &reward_state,
            &final_cert_state,
            &vote_accounts,
            updated_accounts,
            state.reward_validators.iter().cloned(),
        )?,
        (None, Some(state)) => update_accounts(
            &reward_state,
            &final_cert_state,
            &vote_accounts,
            updated_accounts,
            state.signers.iter().cloned(),
        )?,
        (Some(r_state), Some(f_state)) => update_accounts(
            &reward_state,
            &final_cert_state,
            &vote_accounts,
            updated_accounts,
            r_state.reward_validators.union(f_state.signers).cloned(),
        )?,
    };

    bank.store_accounts((bank.slot(), updated_accounts.as_slice()), None);
    Ok(())
}
