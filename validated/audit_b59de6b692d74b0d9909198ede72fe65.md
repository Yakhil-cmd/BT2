### Title
Terminal escape-sequence injection via unsanitized `bashToolArgs.Command` in `renderLogEntry` bash case - ([File: pkg/cmd/agent-task/shared/log.go])

### Summary
In `renderLogEntry`'s `"bash"` case, `v.Command` (from `bashToolArgs.Command`, decoded from the untrusted `tc.Function.Arguments` JSON string) is spliced into `contentWithCommand` via `fmt.Sprintf("$ %s\n%s", v.Command, choice.Delta.Content.String())` and then written to the terminal, without ever passing through the `iostreams.Untrusted` sanitization that the codebase otherwise uses for exactly this purpose.

### Finding Description
`bashToolArgs` is defined with a plain `string` `Command` field [1](#0-0) , unlike `choice.Delta.Content` and `choice.Delta.ReasoningText`, which are typed `iostreams.Untrusted` specifically so that any `fmt` print path automatically strips ANSI/control escape sequences before reaching the terminal [2](#0-1) [3](#0-2) .

`v.Command` is decoded from `tc.Function.Arguments`, which is arbitrary JSON emitted in the streamed chat-completion log from the Copilot agent-task backend [4](#0-3) . In the `"bash"` case it is embedded raw into a display string: [5](#0-4) 

This string is then passed to `renderFileContentAsMarkdown`, wrapped in a fenced code block, rendered by glamour, and finally written to the writer via `fmt.Fprint(w, rendered)` [6](#0-5) [7](#0-6) . Neither glamour's markdown rendering nor `renderFileContentAsMarkdown` strip raw control/escape bytes embedded in code-block content, so any ANSI/OSC sequence present in `v.Command` reaches the victim's terminal unmodified — exactly the class of bug the `Untrusted` type was introduced to prevent (per its own doc comment) for content originating outside the CLI.

An attacker who controls repository content that a Copilot coding agent task processes (e.g., a file, issue, or PR the agent is asked to act on) can attempt prompt injection to influence the agent into echoing attacker-chosen text — including raw escape bytes — into a bash tool call's `command` or `description` argument. Since that value flows to the CLI's terminal output unsanitized, this can be leveraged for terminal escape-sequence injection (e.g., OSC 52 clipboard write, cursor/screen manipulation to spoof output, terminal title spoofing) when the victim runs `gh agent-task view --follow` or similar.

Note the same gap applies to `bashToolArgs.Description`, which is passed to `renderToolCallTitle` and written via `fmt.Fprintf` without sanitization [8](#0-7) [9](#0-8) .

Note: this is a display-only path — there is no `os/exec` or shell invocation of `v.Command` anywhere in this file or its call sites, so this is not remote code execution; it is a terminal output/escape-injection issue.

### Impact Explanation
Concrete impact is terminal escape-sequence injection into the victim's terminal when viewing agent-task logs, which maps to GitHub's bounty impact class for terminal/output injection (spoofing, clipboard hijack via OSC 52, hidden/obscured malicious text designed to trick the user into running a follow-up command). This does not constitute direct code execution, credential exfiltration, or file write, since `v.Command` is never executed or written to disk — it's purely rendered to the terminal.

### Likelihood Explanation
Exploitability depends on: (1) the victim running `gh agent-task view`/`--follow` against a Copilot coding agent task, and (2) the attacker successfully getting the agent's own tool-call arguments to contain literal escape bytes (via prompt injection from repo content the agent processes). This second precondition is non-trivial and not fully within attacker control, since the LLM (not the attacker directly) authors the JSON tool-call arguments; feasibility depends on how faithfully the agent reproduces injected text verbatim in `command`/`description`. This is a real gap relative to the existing `Untrusted` sanitization pattern in the same file, but is a defense-in-depth gap rather than a directly attacker-scripted payload.

### Recommendation
Change `bashToolArgs.Command` and `bashToolArgs.Description` (and any other free-text tool-arg fields rendered to the terminal, e.g. `viewToolArgs.Path`, `createToolArgs.Path`, `strReplaceToolArgs.Path`) to `iostreams.Untrusted`, or explicitly sanitize them with the same ASCII-sanitizer transform before interpolating into `fmt.Sprintf`/`fmt.Fprintf` calls that reach the terminal writer `w`.

```go
func TestRenderLogEntry_BashCommandEscapeInjection(t *testing.T) {
    // Craft a chat-completion-chunk log entry whose bash tool call "command"
    // argument contains a raw ANSI/OSC escape sequence, e.g.:
    //   command = "echo hi\x1b]52;c;<base64-payload>\x07"
    entry := chatCompletionChunkEntry{
        Object: "chat.completion.chunk",
        Choices: []struct{ /* ... */ }{
            {
                Delta: struct{ /* ... */ }{
                    Content: iostreams.NewUntrusted("output"),
                    ToolCalls: []struct{ /* ... */ }{
                        {Function: struct{ Name, Arguments string }{
                            Name:      "bash",
                            Arguments: `{"command":"echo hi\u001b]52;c;cGF5bG9hZA==\u0007","description":""}`,
                        }},
                    },
                },
            },
        },
    }

    var buf bytes.Buffer
    io, _, _, _ := iostreams.Test()
    io.SetOut(&buf) // or wire renderLogEntry's w to buf

    _, err := renderLogEntry(entry, &buf, io)
    require.NoError(t, err)

    // Assert the raw OSC escape sequence is NOT present in output;
    // currently this assertion FAILS, demonstrating the injection.
    require.NotContains(t, buf.String(), "\x1b]52;c;")
}
```
Expected: with the current code, the raw escape sequence survives into `buf.String()` because `v.Command` bypasses `iostreams.Untrusted` sanitization, whereas after applying the recommended fix (typing `Command`/`Description` as `iostreams.Untrusted`), the sequence would be neutralized.

func renderMarkdownWithFormat(md string, w io.Writer, io *iostreams.IOStreams, formatFunc func(string) string) error {
	rendered, err := markdown.Render(md,
		markdown.WithTheme(io.TerminalTheme()),
		markdown.WithWrap(io.TerminalWidth()),
	)

	if err != nil {
		return fmt.Errorf("failed to render markdown: %w", err)
	}

	rendered = strings.TrimSpace(rendered)
	if formatFunc != nil {
		rendered = formatFunc(rendered)
	}

	fmt.Fprint(w, rendered)

	return nil
}

func renderFileContentAsMarkdown(path, content string, w io.Writer, io *iostreams.IOStreams) error {
	lang := filepath.Ext(filepath.ToSlash(path))

	if lang == ".md" {
		return renderRawMarkdown(content, w, io)
	}

	md := fmt.Sprintf("```%s\n%s\n```", lang, content)
	// Glamour adds leading newlines when content is only a code block,
	// so we only want to add a trailing newline.
	formatFunc := func(s string) string {
		return fmt.Sprintf("%s\n\n", s)
	}

	return renderMarkdownWithFormat(md, w, io, formatFunc)
}

// Untrusted wraps string content the application did not author: HTTP response
// bodies, file contents fetched from a remote, anything that originates outside
// the CLI. The raw bytes are unexported so the only ways out are the methods
// below.
//
// Untrusted satisfies fmt.Stringer, and String sanitizes, so any fmt print path
// (Fprint, Fprintf with %s or %v, Sprint) renders the content with ANSI escape
// sequences neutralized. The only way to reach the raw bytes is Raw, which is
// deliberately easy to grep for and is intended for non-terminal uses such as
// hashing, writing to a file, or piping to another program.
type Untrusted struct {
	raw string
}
