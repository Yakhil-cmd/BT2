### Title
Missing sanity checks in `validateAssetDefinition()` allow issuer-controlled, self-destructing/non-transferrable public assets that permanently strand user funds - (File: validation.js)

### Summary
`validateAssetDefinition()` (called on every unit that defines a new asset, reachable by any unprivileged unit poster) is directly analogous to the reported `xcall()` issue: an entry point that accepts several interdependent, security-critical boolean/address-like flags from an untrusted caller, but is missing exactly the sanity checks needed to prevent the combination of flags from causing permanent, unrecoverable loss of the funds moving through the resulting asset. The code even contains commented-out checks acknowledging the exact hazard ("definer is like black hole") that were never enabled.

### Finding Description
`validateAssetDefinition()` in [1](#0-0)  validates the fields of a new asset (`cap`, `is_private`, `is_transferrable`, `auto_destroy`, `fixed_denominations`, `issued_by_definer_only`, `cosigned_by_definer`, `spender_attested`, conditions, denominations) supplied entirely by the posting author (any wallet can post a `asset` message; AAs can also self-define assets via the `asset` message type, see [2](#0-1) ).

The function checks many interdependent combinations (e.g. capped assets must be `issued_by_definer_only`, private+divisible assets must be `auto_destroy` and non-transferrable, private assets can't have conditions after a certain mci), see [3](#0-2) . However, two checks that the developers themselves identified as necessary were left commented out and are never enforced: [4](#0-3) 

These comments state the exact failure modes:
- "definer is like black hole" — if an asset is issued by *anybody* (`issued_by_definer_only=false`) and marked `auto_destroy=true`, then coins issued by any random issuer that reach the auto-destroy sink under the writer's/transfer logic are effectively burned/lost, with no restriction that only the definer (who presumably understands the destroy semantics) is allowed to trigger it.
- "the entire issue should go to the definer" — if issued by anybody but not `is_transferrable`, non-definer-issued coins become permanently stuck at whichever address received them (since the transfer-condition logic in `validatePaymentInputsAndOutputs` only allows non-transferrable assets to move to/from the definer address, see [5](#0-4) ), with no path to recover them if the issuer is not the definer.

This is structurally identical to the reported bug class: the posting entity supplies flag/address-like values (`recovery`, `agent`, `destinationDomain`, `slippageTol` in the Connext report vs. `issued_by_definer_only`, `auto_destroy`, `is_transferrable` here) that combine to create silent, permanent fund loss, and the missing validation was known/flagged by the developers but not implemented.

### Impact Explanation
Any unprivileged unit poster can define a public (non-private) divisible asset with `issued_by_definer_only=false`, `auto_destroy=true`, `is_transferrable` set arbitrarily, and no cap. Anyone who subsequently issues or receives that asset can have their coins become irrecoverable: issuance/transfer interacts with the non-transferrable/auto-destroy semantics in a way that only the definer's address is exempted from the trap, while ordinary participants' funds sent through the asset are silently destroyed or permanently locked at an address they don't control. Because asset definitions are immutable once posted and widely advertised (e.g., via oscript/AA-driven token issuance), this is a supply-affecting, fund-loss issue at High severity — matching the severity class of the original report (funds sent to zero/lost, funds locked forever).

### Likelihood Explanation
Likelihood is Medium-High: creating such an asset requires no special privilege — any wallet, or any AA via a self-issued `asset` message, can define it in a single unit. The dangerous combination of flags passes all currently enforced checks in `validateAssetDefinition()`; only the two commented-out lines would have blocked it. An attacker (or an unwitting asset creator) can trivially trigger this, and unsuspecting counterparties transacting with the asset are the ones who lose funds.

### Recommendation
Re-enable and enforce the two commented-out checks in `validateAssetDefinition()`:
```
if (!payload.issued_by_definer_only && payload.auto_destroy)
    return callback("if issued by anybody, cannot auto-destroy");
if (!payload.issued_by_definer_only && !payload.is_transferrable)
    return callback("if issued by anybody, must be transferrable");
```
Apply the same checks in the AA-defined asset path (`aa_validation.js`, `case 'asset':` block at [2](#0-1) ) so AA-issued assets are subject to the same guarantee. Because this is a validation-rule tightening, it should be gated behind an upgrade MCI (consistent with the pattern used elsewhere in `validateAssetDefinition`, e.g. `noPrivateAssetsWithConditionsUpgradeMci`) to avoid breaking consensus on already-confirmed asset definitions.

### Proof of Concept
1. Post a unit with an `asset` message payload:
```json
{
  "cap": undefined,
  "is_private": false,
  "is_transferrable": false,
  "auto_destroy": true,
  "fixed_denominations": false,
  "issued_by_definer_only": false,
  "cosigned_by_definer": false,
  "spender_attested": false
}
```
2. This passes all current checks in `validateAssetDefinition()` (validation.js:2725-2827) since: it's not private (skips 2794-2801 branch checks), not capped (skips 2802-2803), and the two relevant guards (2805-2811) are disabled comments.
3. Any third party who is issued this asset (not the definer) and transacts it is subject to `is_transferrable=false` restrictions that only exempt the definer address (validation.js:2616-2629), and `auto_destroy=true` semantics that were never meant to apply to non-definer-controlled issuance — resulting in the third party's asset balance being unrecoverable/effectively destroyed, with no available path to move or reclaim it.
