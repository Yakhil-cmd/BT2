## Analysis

**Broken binding claimed:** `repository_named_in_payload == repository_owning(commit)`

**Trace of the actual code path:**

1. `WebhooksController#verify_signature` resolves which webhook secret to check against via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the attacker-controlled JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 

2. `Shipit.github(organization:)` only raises `GithubOrganizationUnknown` (→ HTTP 422) when the named organization has **no configured GitHub App entry** in `secrets.github` at all. [2](#0-1) 
If that organization *is* configured in Shipit (i.e., it is a legitimate org whose repos are tracked in Shipit), the request is verified using **that org's own `webhook_secret`** — a secret that org's own users could plausibly control if they can trigger a real GitHub webhook for one of their own repos, or if signature checking is bypassed entirely (`return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`). [3](#0-2) 

3. Once signature verification passes, `WebhooksController#create` dispatches to `StatusHandler#process`, which is genuinely unscoped:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
This query has no repository/stack filter whatsoever — it's a bare lookup by `sha` across the entire `commits` table, which can span many stacks/repos/orgs.

**Why this is a real, exploitable divergence, not just theoretical:** Git commit SHAs are content-addressed. If a victim's repository is public (or forkable) and an attacker forks it or creates a repository that shares history (e.g., forks upstream, or simply knows the sha of a public commit — SHAs are not secrets, they're visible on any public commit URL), the **same 40-character sha will exist verbatim in the attacker's own repository**. The attacker then:
- Owns a repository under an org that Shipit tracks (or triggers a webhook naming any org configured in Shipit's `secrets.github`), satisfying the signature check with legitimately-obtained-for-their-own-repo credentials (their own installed GitHub App / webhook config for their own org).
- Sends a `status` event whose `sha` equals the victim's tracked commit sha (identical due to shared git history) and whose `repository.full_name` is the attacker's own repo — this field is **never checked against the commit being mutated**.
- `Commit.where(sha: params.sha)` matches the victim's `Commit` row (owned by a completely different `Stack`/repository), and `create_status_from_github!` writes an attacker-chosen `state` (e.g., `"success"`) onto it.
- That status write can flip `Commit#status`/`simple_state`, firing `stack.schedule_merges` and enabling `Shipit::ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery` to deploy based on a forged "green" status, since `ContinuousDeliveryJob` only checks `continuous_deployment?`, schedule windows, and `occupied?` — it does not re-verify CI status authenticity beyond what's stored on the `Commit`. [5](#0-4) 

**Existing guards do not close this gap:**
- `verify_signature` binds the request to *an organization named in the payload*, not to the specific repository/stack owning the target commit — it authenticates "some webhook from org X" but never checks that org X is the actual owner of the commit being mutated.
- `drop_unhandled_event` / `ExplicitParameters` schema in `StatusHandler` only validate presence/type of `sha`, `state`, etc. — they do not enforce any repository binding.
- There is no `stacks.where(repository: ...)` scoping anywhere in `StatusHandler#process`, unlike `CheckSuiteHandler#process`, which *does* scope through `stacks.where(branch: ...)` before touching commits. [6](#0-5) 

This confirms the equality `repository_named_in_payload == repository_owning(commit)` is **not enforced** — `StatusHandler` trusts `sha` alone as sufficient identification of the target commit, which is unsafe given shas can collide across repositories that share history (forks) or can simply be known/guessed for any public commit.

### Title
Cross-repository CommitStatus forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit solely by `Commit.where(sha: params.sha)`, with no check that the webhook's `repository` field matches the repository actually owning that commit. An attacker who controls a repository whose commit history overlaps with (or a commit sha coincides with) a victim's tracked commit can send a `status` webhook — signed only with their own org's webhook secret — and write an arbitrary `CommitStatus` (e.g., `success`) onto the victim's commit, potentially triggering `Shipit::ContinuousDeliveryJob` to deploy.

### Finding Description
The broken binding is `repository_named_in_payload == repository_owning(commit)`. `WebhooksController#verify_signature` authenticates only that the payload came from *some* org configured in Shipit (via `repository_owner` read straight from the attacker-supplied JSON), not that this org owns the commit being mutated (`app/controllers/shipit/webhooks_controller.rb:24-62`). `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero repository scoping (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). Because git SHAs are derived from content and are not secrets (visible on any public commit page, and identical across forks that share history), an attacker who forks or otherwise obtains a repository sharing a commit sha with a victim's tracked stack can forge a `status` event naming their own repository while carrying the shared sha, and the handler will still write the status onto the victim's `Commit` row. `ContinuousDeliveryJob#perform` only checks `continuous_deployment?`, delivery-schedule windows, and `occupied?` before calling `stack.trigger_continuous_delivery`, so a forged "success" status can drive an unauthorized deploy.

### Impact Explanation
An attacker can inject a fabricated `CommitStatus` (arbitrary `state`, `description`, `context`, `target_url`) onto any commit whose sha they know/share, in any stack tracked by Shipit, regardless of which repository actually owns it. If that stack has continuous deployment enabled, this can cause `Shipit::ContinuousDeliveryJob` to ship a change based on forged green CI, and it also corrupts the commit's displayed CI state for legitimate maintainers. This is a payload for one repository mutating another's commit/stack, matching the Critical category (unauthorized deploy triggered off forged authorization/status).

### Likelihood Explanation
The attacker needs: (a) to control/register a repository under any org that Shipit already has configured (`secrets.github`), so their own webhook signs successfully — this is plausible for any Shipit org that allows self-service repo/webhook setup — and (b) a commit sha shared with or known for the victim's tracked commit, achievable trivially by forking a public victim repo (identical shas) or by simply knowing a public commit sha. No Shipit secrets, sessions, or privileged roles are required. The attack is repeatable against any commit sha the attacker can produce or learn.

### Recommendation
Scope `StatusHandler#process` (and generally, sha-based lookups) to the repository asserted by `verify_signature`/the payload: join through `Stack`/`Repository` matching `params.repository.full_name` (or the verified organization) before applying the status, e.g. only update commits whose `stack.repository` corresponds to the authenticated org, mirroring the branch/stack scoping already done in `CheckSuiteHandler#process`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not update commit belonging to a different repository than the payload claims" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "org-victim/repo"
  commit = shipit_commits(:first)
  commit.update!(sha: "deadbeef" * 5)
  assert_equal victim_stack.id, commit.stack_id

  forged_payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'org-attacker/other-repo', 'owner' => { 'login' => 'org-attacker' } }
  }

  assert_no_difference -> { commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_payload)
  end
end
```
Currently this assertion fails: `StatusHandler#process` writes the status regardless of `forged_payload['repository']['full_name']` not matching `victim_stack`'s repository, because `Commit.where(sha: params.sha)` performs no such check (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
