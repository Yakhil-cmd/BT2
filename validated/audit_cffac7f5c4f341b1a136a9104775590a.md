### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` allows cross-organization forgery of CI status via a legitimately-signed webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by matching `sha` across the entire database, without any scoping to the repository/organization whose webhook signature was verified. Every other webhook handler resolves records through `stacks`, which is scoped to the repository derived from the authenticated payload. This breaks the equality "organization that authenticated == repository that is written": the HMAC check in `Shipit::WebhooksController#verify_signature` only proves the payload came from *some* legitimately configured GitHub App/organization, but `StatusHandler` then writes to whatever commit (in whatever stack, in whatever organization) happens to share that 40-hex sha.

### Finding Description
`WebhooksController#verify_signature` verifies the payload's HMAC using the secret configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the (still-unverified-at-that-point) payload: [1](#0-0) [2](#0-1) 

This only proves the request genuinely came from GitHub for *that organization's* configured GitHub App. It says nothing about which repository/stack the enclosed `sha` belongs to. Handlers such as `PushHandler` and `CheckSuiteHandler` correctly narrow their writes through `stacks` (repository-scoped): [3](#0-2) [4](#0-3) 

`StatusHandler`, however, bypasses that scoping entirely and matches on `sha` globally: [5](#0-4) 

`create_status_from_github!` then persists the attacker-controlled `state`/`context`/`description` as a real `Status` on that commit: [6](#0-5) 

Because a git commit SHA is a content hash, the same SHA legitimately exists in a fork and its upstream before divergence. An attacker who owns a fork of the victim's public repository can push a genuine `POST /repos/{attacker}/{fork}/statuses/{sha}` via GitHub's normal API, targeting the shared ancestor commit sha, using nothing but their own write access to their own fork. GitHub delivers this as a real, correctly-signed `status` webhook to whichever GitHub App/org is installed and subscribed on the attacker's side. As long as that organization is *any* organization configured in this Shipit instance (Shipit explicitly supports multiple organizations, each with its own app/secret, per `docs/setup.md` and `config/secrets.development.example.yml`), the signature check passes using that organization's own secret, and `StatusHandler` writes the forged status onto the matching `Commit` row — which may belong to a completely different stack/organization/repository than the one that authenticated the webhook.

### Impact Explanation
The forged status is exactly the data `MergeRequest#any_status_checks_missing?`/`#any_status_checks_failed?` and `Commit#deployable?` rely on for merge-queue gating and continuous-deployment gating: [7](#0-6) [8](#0-7) 

By injecting a fabricated `success` status for a required CI context on a commit it does not actually own/control, an attacker can make Shipit believe CI has passed for a victim stack's commit, letting an unrelated pull request clear the merge queue (`MergeRequest#merge!`) or letting continuous delivery deploy a commit whose real CI checks never ran. This is a cross-repository/cross-organization write that leads to an unauthorized merge/deploy, satisfying the Critical impact bar.

### Likelihood Explanation
Requires: (1) the target Shipit instance hosting more than one GitHub organization/app config (a documented, supported deployment pattern), (2) the attacker controlling any GitHub App/org configured in that instance (trivial — attacker can register their own org/app if self-service onboarding exists, or simply owns a fork with an installed status-reporting integration), and (3) a shared commit SHA obtainable by forking the victim's public repository before divergence. All of these are achievable by an unprivileged external actor with no Shipit session, no `ApiClient` token, and no access to the victim's secrets — only ordinary GitHub fork/API access to their own repository.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by raw payload identifiers) through the same repository-derived `stacks`/`repository` resolution used by `PushHandler`/`CheckSuiteHandler`, e.g. restrict the `Commit` lookup to `stacks.joins(:commits).where(commits: { sha: params.sha })` (or equivalent), so a status can only be attached to a commit belonging to a stack whose repository matches the organization that authenticated the webhook.

### Proof of Concept
1. Attacker forks the victim's public repository (`victim-org/app`) to `attacker/app`. The fork initially shares identical commit objects/SHAs with `victim-org/app` (e.g. `sha = deadbeef...`).
2. Attacker (or any GitHub App/integration they control, installed on their own org and configured as a separate organization entry in the target Shipit's `secrets.yml`) calls the GitHub API: `POST /repos/attacker/app/statuses/deadbeef...` with `{"state":"success","context":"ci/required-check"}`.
3. GitHub sends a `status` webhook to Shipit, HMAC-signed with the attacker-controlled organization's `webhook_secret`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker")`, verifies successfully (their own valid secret).
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, which matches the identical commit under `victim-org/app`'s stack, and calls `create_status_from_github!`, writing a forged `success` status onto the victim's commit.
6. The victim stack's merge queue/deploy gating now treats that commit as CI-passed, even though no CI ran on `victim-org/app` for that commit through legitimate means.
