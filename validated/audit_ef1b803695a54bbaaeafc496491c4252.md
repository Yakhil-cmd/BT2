### Title
Missing Ownership Check on `reject_new_shared_address` Allows Any Correspondent to Delete Another Device's Pending Shared-Address Session - ([File: wallet.js])

### Summary
The `reject_new_shared_address` device-message handler in `wallet.js` deletes a pending multi-signature ("shared") address creation session identified only by `address_definition_template_chash`, without verifying that the sending device (`from_address`) is actually one of the cosigning devices participating in that pending session. This mirrors the reported NocoDB flaw where `McpTokenService` operations acted on a resource identified purely by its ID, without checking that the caller owned it.

### Finding Description
In the device-message dispatcher `handleMessageFromHub` in `wallet.js`, the `reject_new_shared_address` case only validates that the supplied hash is syntactically a valid address/c-hash, then immediately deletes the pending shared-address record: [1](#0-0) 

```
case "reject_new_shared_address":
    // {address_definition_template_chash: "BASE32"}
    if (!ValidationUtils.isValidAddress(body.address_definition_template_chash))
        return callbacks.ifError("invalid addr def c-hash");
    walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash);
    callbacks.ifOk();
    break;
```

`deletePendingSharedAddress` performs an unscoped delete keyed only by the chash, affecting **all** cosigners' pending state, not just the sender's own row: [2](#0-1) 

This is inconsistent with the sibling handler `approve_new_shared_address`, which correctly scopes its `UPDATE` by both the chash **and** `device_address=from_address` (`wallet_defined_by_addresses.js` `approvePendingSharedAddress`, lines 150-155), just as `ApiTokensService` correctly scoped by `fk_user_id` in the NocoDB report. The `reject` path omits this ownership/membership filter entirely — the exact CWE-639 pattern from the advisory (privileged-by-knowledge-of-ID rather than privileged-by-ownership).

Because `reject_new_shared_address` is not in the hub-level whitelist of subjects allowed from unknown/non-correspondent senders (`device.js`, `arrSubjectsAllowedFromNoncorrespondents`), the attacker must already be a paired correspondent device of the victim — but critically does **not** need to be one of the cosigners of the specific shared-address template being rejected. Any paired device that can learn or derive the `address_definition_template_chash` (a value that is itself only weakly protected, being a deterministic hash of the definition template and potentially observable/inferable from prior communication) can unilaterally cancel another set of devices' in-progress multisig wallet setup.

### Impact Explanation
An unauthorized paired device can destroy another user's (or group of users') in-progress multi-signature address creation state (`pending_shared_addresses` / `pending_shared_address_signing_paths`), causing denial of service to the legitimate cosigners who are trying to jointly establish a shared/multisig payment address. This blocks the intended custody setup and can be repeated indefinitely to prevent the shared address from ever being finalized, mirroring the DoS/"invalidating tokens" impact called out as the primary risk in the source advisory.

### Likelihood Explanation
Exploitation requires the attacker to be an already-paired correspondent device of the victim (a Creator/wallet-participant analog) and to know or guess the `address_definition_template_chash` value. Because pairing between devices is common in ocore's wallet workflows (e.g., cosigner setup, contract negotiation), and the chash is not treated as a secret, this is plausible in realistic multi-device wallet workflows, matching the "Limited... requires ... knowledge of target token ID" likelihood characterization in the original report.

### Recommendation
In `deletePendingSharedAddress` (or at the call site in `wallet.js`), require and pass `from_address`, and scope the deletion to rows where the sender is a recognized cosigner of that specific `definition_template_chash` (i.e., add a `WHERE definition_template_chash=? AND device_address=?` filter and only allow it to remove/cancel that device's own participation, or reject/no-op if the sender isn't part of the pending template), consistent with how `approvePendingSharedAddress` already scopes by `device_address`.

### Proof of Concept
1. Device A initiates a shared-address creation offer via `create_new_shared_address` involving Device B and Device C, producing a known `address_definition_template_chash`.
2. Malicious Device X, already paired with Device B (but not part of this particular shared-address definition), obtains the `address_definition_template_chash` (e.g., observed via device correspondence or replayed from Device B's own logs/leaks).
3. Device X sends `{"subject":"reject_new_shared_address","body":{"address_definition_template_chash":"<chash>"}}` to Device B.
4. Device B's `wallet.js` handler calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)` with no check that Device X was a party to the pending session, deleting the pending shared address rows for all legitimate cosigners (A, B, C), denying them the ability to complete the multisig address setup.
