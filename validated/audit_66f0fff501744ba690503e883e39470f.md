### Title
Commit-status webhook writes are scoped by SHA only, not by the repository whose secret authenticated the request, allowing cross-tenant forged CI status injection - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the `webhook_secret` of the organization derived from the payload (`repository.owner.login` / `organization.login`) [1](#0-0) [2](#0-1) . Once verified, the `status` event is dispatched to `StatusHandler`, which updates commit statuses using only the commit SHA, with no check that the SHA belongs to a stack/repository owned by the organization that produced the valid signature [3](#0-2) . This breaks the equality that should hold: `organization that authenticated the webhook == repository whose Commit records are written`.

### Finding Description
Other handlers in the same directory correctly scope their side effects to the repository named in the payload via `Handler#stacks`/`Repository.from_github_repo_name` (e.g. `PushHandler` filters `stacks` by the repository derived from `payload.dig('repository', 'full_name')` [4](#0-3) [5](#0-4) , and `PullRequest::OpenedHandler` resolves a specific `repository` before acting [6](#0-5) ).

`StatusHandler`, however, does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit` is a global table shared across every `Stack`/`Repository` tenant hosted by this Shipit instance; nothing here restricts the write to commits belonging to the repository that was actually used to select and validate the HMAC signature in `WebhooksController#verify_signature`. Since git commit SHAs are content-addressed, any actor who can push to a repository whose organization is configured in Shipit (and therefore can produce a genuinely-signed `status` webhook for that organization) can:
1. Fabricate a commit with the same tree/parent/author/committer metadata as a target commit belonging to a different, unrelated stack tracked by the same Shipit instance (producing an identical SHA), or exploit any pre-existing shared history (e.g., forks/mirrors) between the victim repository and one the attacker controls.
2. Use GitHub's ordinary commit-status API on their own (attacker-controlled) repository to set a status for that SHA, which GitHub will deliver as a legitimately-signed webhook to Shipit for the attacker's organization.
3. `WebhooksController#verify_signature` validates successfully because it is checking the attacker's own organization's secret, matching the attacker's own payload — the check passes.
4. `StatusHandler#process` then writes/updates the status for that SHA on `Commit.where(sha: params.sha)`, which matches the victim stack's commit too, injecting a forged CI status (e.g. `state: "success"`) into the target repository's commit history as tracked by Shipit.

### Impact Explanation
Commit statuses gate deploy and merge eligibility (`commit.deployable?`, `ci.require`, `MergeRequest#reject_unless_mergeable!`/`any_status_checks_failed?`). A forged "success" status injected onto a victim stack's commit from a completely different, attacker-authenticated organization can satisfy CI requirements it never actually met, enabling an unauthorized deploy or merge on a stack the attacker's organization does not own — a cross-tenant write with deploy-security consequences, matching the "cross-repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Exploitation requires the attacker to control (or have push/status-write access to) at least one repository whose organization is already configured with a `webhook_secret` in this Shipit instance, and either produce a colliding SHA (feasible via forks/shared history, or deliberately identical commit metadata against a known target commit) or otherwise obtain a SHA that also exists in a victim stack. This is a real, multi-tenant-only risk (single-tenant deployments are unaffected since there is only one organization/repository), and does not require compromising `webhook_secret`, `api_clients_secret`, or any GitHub App key — only ordinary GitHub write access to one already-connected repository plus knowledge/reproduction of a target commit.

### Recommendation
Scope `StatusHandler#process` (and audit `CheckSuiteHandler` and any other handler operating on `Commit`/`Repository` records) to only update commits that belong to the repository resolved from the *verified* webhook payload, e.g. `Repository.from_github_repo_name(payload.dig('repository', 'full_name')).stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret`, each hosting a stack (`org-a/repo-a` and `org-b/repo-b`).
2. As a user with push/status access to `org-a/repo-a`, create a commit with tree/parent/author/committer fields identical to a known commit `SHA` in `org-b/repo-b` (or leverage a fork sharing history), producing the same SHA in `repo-a`.
3. Use GitHub's Statuses API against `repo-a` to set `state: success` for that SHA; GitHub delivers a genuinely `sha1=`-signed `status` webhook (signed with `org-a`'s secret) to Shipit's `/webhooks` endpoint.
4. `WebhooksController#verify_signature` validates the signature against `org-a`'s configured secret and succeeds [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the commit belonging to `org-b/repo-b`, and records the forged "success" status on it [3](#0-2) , potentially unblocking a deploy/merge for `org-b`'s stack that the `org-a` attacker never had legitimate authority over.
