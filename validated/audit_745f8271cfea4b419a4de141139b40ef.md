### Title
Webhook signature verified against attacker's own organization secret while actioned repository is taken from an unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which HMAC secret) to validate the request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . All event handlers, however, resolve the actual `Repository`/`Stack` to operate on using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Handler#stacks` [2](#0-1) . Nothing enforces that `repository.owner.login` (the field bound to signature verification) matches the owner encoded in `repository.full_name` (the field bound to the write/action target).

### Finding Description
`Shipit.github(organization: repository_owner)` picks a per-organization `GitHubApp` instance and its own `webhook_secret` [3](#0-2) , then `verify_webhook_signature` HMACs the *entire* raw request body against that org's secret [4](#0-3) . Any user who has legitimately installed the GitHub App for **their own** organization on the Shipit instance knows/can trigger real, correctly-signed deliveries for that org, and can therefore construct an arbitrary JSON body (not just relay a genuine GitHub payload) that is valid HMAC-wise for their own org while embedding a different `repository.full_name`.

Every handler dispatched from `WebhooksController#create` (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) looks up the target repository purely from `repository.full_name` [2](#0-1)  and `Repository.from_github_repo_name` [5](#0-4) , never re-checking it against `repository.owner.login`. Concretely, `PushHandler` uses this to locate stacks by branch and immediately triggers `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  — for a stack belonging to an organization the attacker does not control and never proved ownership of, because the signature only proved ownership of `repository.owner.login`, not `repository.full_name`.

This is exactly the "organization that authenticated versus the repository that is written" binding break called out as in-scope: `repository_owner (signature) == repository.full_name.owner (action target)` is assumed but never asserted.

### Impact Explanation
Any org/repo owner already onboarded to the Shipit instance (an otherwise unprivileged actor relative to *other* tenants' repos) can forge webhook events that are processed as if they came from GitHub for a **different** tenant's repository/stack, since the per-organization webhook secret only proves the identity of `repository.owner.login`, not of `repository.full_name`. This lets an attacker drive `Handler` subclasses (e.g. `PushHandler`) against stacks they do not own, forcing out-of-band `sync_github` calls and other handler side effects with attacker-chosen `ref`/`after` values for repositories belonging to unrelated tenants on the same Shipit instance — a cross-repository action performed without the repository's own signature ever being satisfied.

### Likelihood Explanation
Requires only that the attacker control (or have installed) a legitimate GitHub App/organization already configured in this Shipit deployment — no `ApiClient` token, GitHub App private key, or repository write access to the *victim* repo is needed, matching the "unprivileged attacker" framing. Constructing the forged payload/signature is trivial once the attacker's own webhook secret is known (which it inherently is, since GitHub delivers it to installations of their own app, and Shipit computes the HMAC over the full body they fully control).

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, require that the owner used to select the signing `GitHubApp` (`repository_owner`) equals the owner embedded in `repository.full_name` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret` (`S_attacker`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` — valid, because `verify_signature` looks up `Shipit.github(organization: "attacker-org")` from `repository.owner.login` [7](#0-6)  and checks against `S_attacker`.
4. `WebhooksController#create` parses the same body and dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [8](#0-7)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [6](#0-5)  — despite the signature never having been checked against `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
