Based on my research, I found a strong analog to the GLPPriceOracle gas-exhaustion pattern in ocore's AA data feed lookup mechanism, which performs unbounded iteration over global unstable-unit state whose cost scales with total network activity rather than with attacker-controlled input.

### Title
AA `data_feed`/`in_data_feed` lookups iterate over all unstable network units, causing unbounded evaluation cost per trigger - (File: data_feeds.js)

### Summary
The `data_feed` and `in_data_feed` oscript operators, when evaluated in an AA context (`bAA=true`), first scan through **every currently unstable unit in the entire DAG** (`storage.assocUnstableMessages`) before falling back to the indexed KV-store lookup [1](#0-0) . This is directly analogous to `GlpManager.getPrice()` iterating over all whitelisted tokens: the cost of a single call grows with the size of external/global state (here, the number of unstable units network-wide) rather than with the caller-provided input, and this scan is triggered every time a posted AA trigger's formula uses `data_feed`/`in_data_feed`.

### Finding Description
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` both contain a branch guarded by `bAA` that loops over `storage.assocUnstableMessages` for every unit currently pending stabilization, checking `author_addresses`, `latest_included_mc_index` bounds, and message payloads for a matching feed name: [2](#0-1)  and the read-path equivalent [3](#0-2) .

These functions are invoked from formula evaluation whenever an AA's oscript uses `data_feed[[...]]` or `in_data_feed[[...]]`: [4](#0-3) [5](#0-4) . Every posted unit that triggers an AA causes the AA response to be recomputed by every full node validating/executing that AA, so this loop executes once per node per trigger that reaches such a data-feed expression.

Unlike ordinary complexity/ops accounting, which bounds cost by the *static* size of the formula (`MAX_COMPLEXITY`, `MAX_OPS` in `constants.js`) [6](#0-5) , the cost of this particular operation is **not bounded by formula complexity at all** — it is proportional to `Object.keys(storage.assocUnstableMessages).length`, a piece of global, attacker-influenceable network state that can grow arbitrarily as the number of not-yet-stable units increases (e.g., during high throughput, slow witnessing, or a burst of postings). An attacker does not need to grow this state via the AA itself; they only need to trigger the AA while the DAG has many pending unstable units, or flood the network with cheap units to inflate `assocUnstableUnits`/`assocUnstableMessages` and then send a trigger.

### Impact Explanation
Because every AA trigger causes each validating node (and the AA-response voting scheme) to redundantly perform this unbounded scan, an attacker who can (a) increase the number of unstable units network-wide and (b) post a trigger unit invoking `data_feed`/`in_data_feed`, can materially increase the per-unit validation/response-computation cost across the network. If this cost grows large enough relative to node processing budgets, it degrades throughput for AA execution broadly (a network-wide resource-exhaustion/DoS vector), which under the rules provided maps to "a network unable to confirm new units" in the worst case, or at minimum non-uniform latency/processing cost that is not accounted for by the formula's static complexity limits.

### Likelihood Explanation
Any unprivileged unit poster can trivially construct an AA trigger using `data_feed`/`in_data_feed` (these are common, widely-used oscript primitives, as shown throughout `test/formula.test.js`), and the number of unstable units is a natural, frequently-large quantity during normal network operation — no special privilege or malicious peer/node behavior is required to reach this code path, only a normal trigger unit. The severity depends on how large `assocUnstableMessages` can practically get, which I could not fully quantify from static analysis alone (it depends on runtime network conditions such as posting rate vs. stabilization rate).

### Recommendation
Bound the AA-context data-feed lookup by a fixed/limited number of scanned unstable units (or index `assocUnstableMessages` by author address so the lookup is O(matching addresses) rather than O(all unstable units)), and/or charge this operation's cost into the formula's complexity/ops accounting so that expensive scans are reflected in `MAX_COMPLEXITY`/`MAX_OPS` limits rather than being effectively free from the formula-cost perspective.

### Proof of Concept
1. Post many low-cost units to the network to inflate the count of currently-unstable units tracked in `storage.assocUnstableMessages` (this dictionary is populated as units are received but before they stabilize).
2. While this backlog is large, post a trigger unit to any AA whose oscript definition contains a `data_feed[[...]]` or `in_data_feed[[...]]` expression.
3. Observe that AA response computation for that trigger (and thus validation by every node processing it) performs a full iteration over the current `assocUnstableMessages` set [7](#0-6)  before returning, with cost scaling with the size of that global unstable-unit backlog rather than with the trigger's own content.
