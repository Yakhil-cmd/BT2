## Finding

### Title
Future-dated oracle price timestamp permanently poisons the shared `last-update` floor and can freeze price resolution for all market participants - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in the market contract accepts any price update whose reported timestamp is not older than a shared, per-feed monotonic floor (`last-update`), and it treats *future* timestamps as automatically "fresh" instead of rejecting them. Because that floor is stored in a map keyed only by `{type, ident}` and shared by every subsequent caller, one price update with a timestamp ahead of real time can permanently raise the floor, causing every later — otherwise valid — price update for that feed to be rejected as "too old," which blocks all pricing-dependent operations (borrow, withdraw, liquidate) for every user holding or borrowing that asset.

### Finding Description
`oracle-timestamp-fresh` computes the staleness delta as: [1](#0-0) 

```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When the reported price timestamp `ts` is *ahead* of `stacks-block-time`, `delta` is forced to `u0`, so the freshness check `(<= delta max-staleness)` always passes regardless of how far in the future `ts` is. There is no upper bound placed on `ts` relative to `stacks-block-time` — this exactly mirrors the referenced report's root cause of an unvalidated timestamp field with no upper bound.

`price-resolve` then unconditionally persists that unbounded, future-dated timestamp as the new monotonic floor for the feed: [2](#0-1) 

```
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

The `last-update` map is shared, single-entry-per-feed state: [3](#0-2) 

Once any single relayed update (whether from clock skew between the oracle publisher's attestation and the Stacks chain, or a manipulated relay payload) sets `last-update[key]` to a value ahead of the real current time, the `(>= ts prev)` monotonicity check in `oracle-timestamp-fresh` will reject every subsequent legitimately-timed price update for that feed until real time catches up to the poisoned floor. Because `price-resolve`/`price-multi-resolve` back every collateral/debt valuation in the market (used for borrow, withdraw, and liquidation health checks), this freezes those operations for **every** user with a position keyed to that asset — not just the party that submitted the bad update.

### Impact Explanation
This is a shared-state (`last-update` map) poisoning caused by one caller's transaction that is consumed by all other market participants' subsequent transactions requiring that price feed. The victims are any borrowers/depositors/liquidators using the affected asset who did not submit the bad update, and the harm (inability to borrow, withdraw, or be liquidated correctly because `ERR-ORACLE-INVARIANT` reverts price resolution) is a temporary freezing of funds tied to that asset until the poisoned floor is naturally passed by real time. This lands in the in-scope "High — temporary freezing of funds" impact class.

### Likelihood Explanation
The trigger condition only requires one price update timestamp to be reported ahead of `stacks-block-time` — which can occur from ordinary clock/attestation skew between the external price source and the Stacks chain, not just from a malicious actor forging data, making the condition plausible in normal operation, similar to how the original report's bug could be triggered by any proposer without needing to compromise cryptographic guarantees.

### Recommendation
`oracle-timestamp-fresh` should reject timestamps that are ahead of `stacks-block-time` (or bound them to a small allowed clock-skew tolerance) instead of collapsing the delta to `u0`, and `last-update` should never be advanced past `stacks-block-time` when persisting the monotonic floor in `price-resolve`.

### Proof of Concept
1. A price update for feed `{type, ident}` is relayed with `timestamp = stacks-block-time + N` (N seconds in the future), where `N` is larger than any subsequent real-time drift will close within an acceptable window.
2. `oracle-timestamp-fresh` computes `delta = u0` (since `ts > stacks-block-time`), so `(<= delta max-staleness)` is trivially true; `(>= ts prev)` also holds since it's the first/newer timestamp seen. The update is accepted.
3. `price-resolve` executes `(map-set last-update key timestamp)`, storing the future timestamp as the new floor.
4. On the next real block, a legitimately-timed update arrives with `timestamp' ≈ stacks-block-time'` (correct, `< stored future floor`). `oracle-timestamp-fresh` now returns `false` because `(>= ts prev)` fails (`timestamp' < prev`), so `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.
5. Every market operation needing this asset's price (borrow, withdraw, liquidation checks) now reverts for all users, not just the one whose transaction triggered the poisoned entry, until real time surpasses the poisoned floor.
