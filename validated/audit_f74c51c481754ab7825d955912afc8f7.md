### Title
Cross-repository status write via unscoped `Commit.where(sha:)` lookup breaks the "organization authenticated" vs "repository written" binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook against the GitHub App/organization derived from the payload's `repository.owner.login` [1](#0-0) . However, `StatusHandler#process` never scopes its write to that verified repository/organization: it looks up commits engine-wide by raw SHA and mutates whatever it finds. [2](#0-1) 

### Finding Description
Every other handler (`PushHandler`, the `PullRequest` handlers) derives its target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`#repository_name`, which ties the webhook's *authenticated* GitHub organization to the *specific* repository being written to. [3](#0-2) [4](#0-3) 

`StatusHandler`, by contrast, ignores `repository`/`full_name` entirely and queries `Commit.where(sha: params.sha)` across the whole `commits` table, iterating every match regardless of which stack/repository owns it, and calling `commit.create_status_from_github!(params)` on each: [2](#0-1) 

The equality that should hold — `organization authenticated by signature == organization owning the repository/commit written` — is broken here: the signature only proves "this event legitimately came from organization/App X for one of X's repos," but the write path applies the status update to any `Shipit::Commit` row anywhere in the database that shares the same `sha`, independent of stack/organization. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `add_status`, which can fire `deployable_status`/`commit_status` hooks and call `stack.schedule_merges` on that unrelated stack [5](#0-4) , and `Status#schedule_continuous_delivery` further calls `commit.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if that (unrelated) stack has `continuous_deployment?` and is `deployable?` [6](#0-5) [7](#0-6) .

### Impact Explanation
Two independently-configured organizations/GitHub Apps in a multi-org Shipit deployment (`Shipit.github(organization:)`, `github_app_config`) [8](#0-7)  each get their own `webhook_secret`, and each is only supposed to be able to affect its own repositories' commits. Because `StatusHandler` matches purely on `sha` with no repository/stack scoping, an attacker who legitimately controls a repository under Organization A (and can therefore push a commit and set an arbitrary CI status on it — both actions available to any repo admin via the GitHub API, not requiring any Shipit credential) can craft a commit whose SHA-1 collides with — or, more practically, is engineered to be byte-identical to (e.g., cross-forked history, or copied tree/parent/author/committer/timestamp metadata) — a commit that exists in an unrelated Organization B's stack tracked by the same Shipit instance. Sending a `success` status for that SHA from Organization A's properly-signed webhook will update the status of the identically-shaed commit belonging to Organization B's stack, potentially marking it deployable and, if that stack has `continuous_deployment` enabled, triggering an **unauthorized deploy** of Organization B's stack. This satisfies the "unauthorized deploy" High-impact category, since it escalates a legitimately-authenticated Organization-A webhook into effects on an entirely different repository/organization's deployment pipeline.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to produce (or find) a commit with an identical SHA-1 to a target commit in a different repository they don't control — a nontrivial but not impossible bar (e.g., shared history from forks/mirrors, or deliberately reproduced commit metadata for a public commit). The attacker does not need any Shipit-side credential, API token, or webhook secret — they only need write/admin access to their own repository under an organization independently registered with the same Shipit instance, which is a realistic multi-tenant scenario described in the engine's own `docs/setup.md` "Using Multiple GitHub Applications" configuration.

### Recommendation
Scope the `StatusHandler` lookup the same way `PushHandler` and the pull-request handlers do: resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` (via the existing `Handler#stacks`/`#repository_name`) and restrict `Commit.where(sha: params.sha)` to `stacks.commits` (or equivalently join through the resolved `Repository`), so a status update can never cross repository/organization boundaries regardless of SHA collisions.

### Proof of Concept
1. Configure Shipit in multi-org mode with two GitHub Apps/organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. `OrgB` has a Stack tracking a commit with `sha = S` that is deployable and has `continuous_deployment: true`.
3. Attacker, who administers a repo under `OrgA`, creates a commit in their own `OrgA` repo whose SHA is also `S` (e.g., by reproducing tree/parent/author/committer/timestamp of the public `OrgB` commit, or via a git history/fork collision), then sets a `status` event with `state: "success"` for that commit via the GitHub API on their own repo.
4. GitHub delivers the `status` webhook to Shipit, correctly signed with `OrgA`'s `webhook_secret`; `verify_signature` passes because it only checks that the payload was legitimately signed by `OrgA`.
5. `StatusHandler#process` runs `Commit.where(sha: 'S').each { |commit| commit.create_status_from_github!(params) }`, which updates the status of `OrgB`'s commit (same `sha`) even though the webhook was never signed by/for `OrgB`.
6. If this transitions `OrgB`'s commit into a deployable state, `stack.schedule_merges`/`ContinuousDeliveryJob` may fire for `OrgB`'s stack, resulting in an unauthorized deploy triggered by an `OrgA`-signed webhook.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
