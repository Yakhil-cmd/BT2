### Title
Cross-tenant Team/Membership mutation via `MembershipHandler#process` matching teams by `github_id` alone, ignoring the signature-verified organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature against the webhook secret of whichever organization the payload claims (`repository_owner`, which for `membership` events falls back to `params.organization.login`) [1](#0-0) [2](#0-1) . `MembershipHandler#find_or_create_team!` then looks up the target `Team` purely by the integer `github_id`, never checking that the team's `organization` matches the organization the request was actually verified for [3](#0-2) . An attacker who owns a legitimate, Shipit-registered GitHub organization (with their own valid `webhook_secret`) can therefore sign a `membership`/`removed` payload naming their own org but pointing `team.id` at a Shopify team's `github_id`, and `team.members.delete(member)` will delete a real `Membership` row belonging to that other tenant's team [4](#0-3) .

### Finding Description
The intended binding is: **verified_organization == team.organization** for every team mutated inside a webhook-triggered handler. This binding is broken.

- `verify_signature` calls `Shipit.github(organization: repository_owner)` and HMACs the raw body against that specific organization's `webhook_secret` [1](#0-0) . For a `membership` payload there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — a field fully controlled by whoever holds a valid Shipit-registered org and its secret [2](#0-1) . This means the signature check only proves "this request was signed by organization X's secret" — it says nothing about the `team.id` inside the body.
- `MembershipHandler#process` then resolves the team via `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`; the block that sets `team.organization = params.organization.login` only executes on **creation**, so if a `Team` row for that `github_id` already exists (created earlier for the real `shopify` org), it is returned unmodified — its `organization` is never checked against the payload's `organization.login` [3](#0-2) .
- `case params.action; when 'removed'; team.members.delete(member)` then deletes the `Membership` row joining that (shopify) team and the named `member`, regardless of which org actually signed the request [5](#0-4) .

**Attacker's exact request**: `POST /webhooks`, header `X-Github-Event: membership`, body:
```json
{
  "action": "removed",
  "team": {"id": <shopify_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "attacker-org"},
  "member": {"login": "<victim-shopify-engineer-login>"}
}
```
signed with `X-Hub-Signature` computed using `attacker-org`'s own registered webhook secret. `verify_signature` succeeds because it resolves and checks against `attacker-org`'s secret, which the attacker legitimately possesses [1](#0-0) . `find_or_create_team!` then matches the existing Shopify `Team` by `github_id` [3](#0-2) , `User.find_or_create_by_login!` resolves the real victim user [6](#0-5) , and `team.members.delete(member)` deletes their `Membership`. If that team is in `Shipit.github_teams`, `User#authorized?` — which checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — flips to `false` for the victim [7](#0-6) .

No existing guard prevents this: `verify_signature` only authenticates "a message from org X", `drop_unhandled_event` is irrelevant (membership is handled), there is no `ExplicitParameters` cross-check between `organization.login` and the resolved `team.organization`, and no model validation ties `Team#organization` to the request's verified tenant on lookup.

### Impact Explanation
An attacker who controls any Shipit-registered GitHub organization (their own, legitimately onboarded org with its own webhook secret) can, using only their own org's webhook secret, force-delete `Membership` rows for teams belonging to a completely different organization (e.g., `shopify`), as long as they can guess/discover the target team's numeric `github_id` (partially public/enumerable GitHub info). This denies a legitimate, currently-authorized engineer their Shipit access (`authorized?` becomes `false`), and is repeatable against any team `github_id` in `Shipit.github_teams` for any tenant the attacker can enumerate. The symmetric `added` branch (`team.add_member`) is even more severe, letting the attacker grant Shipit access/escalate into `Shipit.github_teams` authorization for an arbitrary GitHub login using only their own org's credentials — this matches the "payload for one repository/tenant mutating another's team" Critical category.

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) their own GitHub organization already configured as a tenant in Shipit (with a legitimate webhook and its own `webhook_secret`), and (b) the numeric `github_id` of the target team, obtainable via GitHub's team/org APIs or reconnaissance. No Shipit session, API token, or victim-org secret is required — only the attacker's own legitimately-issued webhook secret. This is a low-cost, fully repeatable HTTP request with no rate limiting or additional checks blocking it.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and analogous handlers), verify that the resolved `Team#organization` matches the webhook-verified organization (`params.organization.login` / `repository_owner`) before performing any mutation; reject or no-op (with logging) when they diverge, instead of blindly resolving by `github_id` alone.

### Proof of Concept
```ruby
test "membership 'removed' webhook cannot mutate another organization's team" do
  shopify_team = shipit_teams(:some_shopify_team) # github_id known, organization: 'shopify'
  victim = shipit_users(:some_shopify_engineer)
  shopify_team.add_member(victim)
  assert victim.authorized?

  payload = {
    action: 'removed',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: victim.login }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, payload)

  assert_no_difference('Shipit::Membership.count') do
    post shipit.webhooks_path, params: payload,
      headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }
  end

  assert victim.reload.authorized?, "victim's shopify membership must not be deletable via attacker-org's own secret"
end
```
Under current code, `assert_no_difference('Shipit::Membership.count')` fails (count decreases by 1) and `victim.authorized?` becomes `false`, proving the cross-tenant mutation.
