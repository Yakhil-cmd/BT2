### Title
Webhook signature check is keyed to an attacker-chosen organization while the handler acts on a different repository field of the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate against using `repository_owner`, a value read directly from the unauthenticated, attacker-supplied JSON payload. `GitHubApp#verify_webhook_signature` then unconditionally returns `true` when that organization has no `webhook_secret` configured. However, the actual repository/stack that gets mutated by the webhook handlers is resolved from a *different* field of the very same payload (`repository.full_name`), which is never checked against the organization used for signature verification. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the organization to authenticate against purely from the incoming JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` bypasses HMAC verification entirely whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every webhook handler resolves the repository/stack it actually acts on from a separate field of the same untrusted payload — `repository.full_name` — with no re-check that this repository belongs to the organization that was used for signature verification: [4](#0-3) [5](#0-4) 

In a multi-organization Shipit deployment (`Shipit.github(organization:)` resolving per-org config via `github_app_config`), each org can have its own `webhook_secret`, and the docs describe the secret as optional: [6](#0-5) 

Consequently, if *any one* configured organization ("Org A") has a blank/unset `webhook_secret`, an unauthenticated attacker can send a POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = "Org A" (used only to pick the verification key — bypassed because Org A has no secret), and
- `repository.full_name` = "Org B/some-repo" (the actual, unrelated, fully-configured stack the attacker wants to affect).

`verify_signature` looks up Org A's config, finds no `webhook_secret`, and returns `true` without ever checking a signature. `create` then dispatches the raw JSON to the matching handlers, which resolve the target `Stack`/`Repository` via `repository.full_name` = "Org B/some-repo" — completely disconnected from the organization that was "authenticated."

### Impact Explanation
This crosses the exact trust boundary the report's bug class targets: the entity that is checked (owner/organization used for HMAC secret selection) is not the entity that is acted upon (repository resolved by `full_name`). This allows cross-organization/cross-repository forged webhook events on stacks the attacker has no legitimate relationship with, e.g.:
- Forged `push` events causing `PushHandler` to invoke `stack.sync_github` on arbitrary target stacks, which can advance deploy state and interact with continuous delivery.
- Forged `pull_request`/`membership`/`status`/`check_suite` events manipulating merge queue state, team/user membership, or commit statuses for repositories the attacker does not control.

This matches "cross-repository writes / unauthorized deploy [state] triggering" from a party with no credential for the targeted organization.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires that the Shipit instance is configured for more than one GitHub organization/App (`Shipit.github_organizations` returning more than `[nil]`) and that at least one of those configured organizations has left `webhook_secret` blank (documented as "optional" in `docs/setup.md`). Under a single-organization/App configuration (the common case documented in the primary setup guide), `repository_owner` resolves to the same, single configured org, so this specific cross-org confusion does not apply, though the "verification bypassed if webhook_secret is blank" behavior remains a standing risk for that one org's own repositories.

### Recommendation
- After signature verification succeeds, verify that the organization/owner used to select the verification secret actually matches the owner of `repository.full_name` (or `organization.login`) that the dispatched handlers will act upon, rejecting the payload if they diverge.
- Do not silently return `true` from `verify_webhook_signature` when `webhook_secret` is blank for a given organization in multi-org configurations; either require a secret for all configured organizations or fail closed when handling events for repositories outside the currently-authenticated organization.

### Proof of Concept
1. Operate a Shipit instance configured with two organizations, `org-a` (no `webhook_secret` set) and `org-b` (fully configured, with an existing `Stack` for `org-b/target-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "org-b/target-repo",
    "owner": { "login": "org-a" }
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` without checking any signature.
4. `create` dispatches the payload to `PushHandler`, which resolves the stack via `repository.full_name` = `"org-b/target-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the `org-b` stack — despite no valid credential ever being presented for `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
