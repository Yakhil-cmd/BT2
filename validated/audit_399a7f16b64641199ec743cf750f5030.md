### Title
Unbounded private-payment chain processing in `handlePrivatePaymentChains` enables an endless data / resource exhaustion attack - (File: wallet.js)

### Summary
`wallet.handlePrivatePaymentChains()` (invoked when a paired device sends the `private_payment_chains` message) accepts an attacker-controlled array of chains (`body.chains`), where each chain is itself an attacker-controlled array of private-payment elements, without imposing any limit on the number of chains or the length of each chain. Every chain is walked and validated element-by-element (DB lookups, spend-proof checks, `graph.determineIfIncluded` ancestor checks) with no cap, mirroring the "endless data" resource-exhaustion pattern described in the Notation advisory (unbounded number of served items causing a DoS on the party that must process them).

### Finding Description
`handlePrivatePaymentChains` only validates the *shape* of each chain element (that it's a non-empty object with required fields), never the *size* of `arrChains` or of any individual chain: [1](#0-0) 

Each chain is then handed to `network.handleOnlinePrivatePayment`, which in turn calls `privatePayment.validateAndSavePrivatePaymentChain`, which for indivisible assets calls `parsePrivatePaymentChain` — an `async.forEachOfSeries` loop over the **entire attacker-supplied array**, with no maximum length check: [2](#0-1) 

For light wallets (the common deployment for paired-device correspondents), each element additionally triggers `graph.determineIfIncluded` and DB queries per `validatePrivatePayment` call: [3](#0-2) 

and light clients further fetch a full linkproof chain per unhandled chain via `updateLinkProofsOfPrivateChain` / `checkThatEachChainElementIncludesThePrevious`, which requests `light/get_link_proofs` and validates the entire chain of joints: [4](#0-3) [5](#0-4) 

None of these paths enforce a bound analogous to the anti-spam limits enforced elsewhere in the codebase (e.g. `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`): [6](#0-5) 

The only size guard found (`isTooDeeplyNestedOrHasTooManyNodes`, depth 5 / 100 nodes) is applied to raw device-message envelopes at the hub-delivery layer (`hub/deliver` in `network.js`), not to the semantic content of `private_payment_chains`, whose `chains` array can contain arbitrarily many chains each of arbitrary length up to whatever the transport/device-message size limits allow (which are themselves configurable per-hub, `max_message_length`), so a malicious correspondent/paired device can still submit a very large `chains` payload: [7](#0-6) 

### Impact Explanation
A malicious paired device (a correspondent the victim has whitelisted for private payments) can send a `private_payment_chains` message containing a very large number of chains, or chains with very many elements, forcing the victim's wallet to perform unbounded database queries, unbounded ancestor-inclusion graph traversals (`graph.determineIfIncluded`), and — for light wallets — unbounded remote-proof round trips per chain, all synchronously serialized via `async.eachSeries`/`async.forEachOfSeries`. This can pin the wallet's mutex-protected private-payment processing pipeline and exhaust CPU/DB/network resources, denying the victim's wallet the ability to process new private payments (and potentially other mutex-serialized operations), which matches the "unable to confirm/process" DoS class analogous to the Notation advisory.

### Likelihood Explanation
The attack requires the attacker to already be a "correspondent"/paired device of the victim (private-payment counterparty), which is a normal, expected relationship for using private-payment features — no privileged network position or key compromise is needed. Any correspondent can freely construct `body.chains` with an arbitrarily large array or arbitrarily long individual chains, since only object-shape validation is performed before the unbounded processing begins.

### Recommendation
Add explicit upper bounds (analogous to existing anti-spam constants) on:
- the number of chains accepted in a single `private_payment_chains` message (`arrChains.length`),
- the length of each individual chain (`arrPrivateElements.length`),

and reject/short-circuit messages exceeding these limits in `handlePrivatePaymentChains` (wallet.js) before any DB/network work is performed, and likewise in `parsePrivatePaymentChain` / `validateAndSavePrivatePaymentChain` (indivisible_asset.js, divisible_asset.js, private_payment.js) as defense in depth.

### Proof of Concept
1. Attacker device pairs with the victim wallet as a normal correspondent (standard pairing flow, no special privilege required).
2. Attacker sends a `private_payment_chains` device message with `body.chains` = an array of, e.g., tens of thousands of syntactically-valid-looking chains (or a smaller number of chains each with a very long fabricated element list satisfying the minimal per-element shape checks in `wallet.js:959-972`).
3. `handlePrivatePaymentChains` passes shape validation and begins `async.eachSeries` over all chains, invoking `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain`/`validatePrivatePayment` for every element of every chain, each doing DB queries and (for light clients) `graph.determineIfIncluded`/link-proof network round-trips.
4. The victim wallet's CPU, DB, and (for light clients) network request queue are consumed processing the attacker-controlled volume of data, delaying or blocking legitimate private-payment processing and other mutex-serialized wallet operations.

				return cb("no output in private element");

				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)

			});
		},

			if (err)
				return callbacks.ifError(err);

// Note that we are leaking to light vendor information about the full chain. 
// If the light vendor was a party to any previous transaction in this chain, he'll know how much we received.
function checkThatEachChainElementIncludesThePrevious(arrPrivateElements, handleResult){
	if (arrPrivateElements.length === 1) // an issue
		return handleResult(true);
	var arrUnits = arrPrivateElements.map(function(objPrivateElement){ return objPrivateElement.unit; });
	requestFromLightVendor('light/get_link_proofs', arrUnits, function(ws, request, response){
		if (!response || response.error)
			return handleResult(null); // undefined result
		var arrChain = response;
		if (!ValidationUtils.isNonemptyArray(arrChain))
			return handleResult(null); // undefined result
		light.processLinkProofs(arrUnits, arrChain, {
			ifError: function(err){
				console.log("linkproof validation failed: "+err);
			//	throw Error(err);
				handleResult(false);
			},
			ifOk: function(){
				console.log("linkproof validated ok");
				handleResult(true);
			}
		});
	});
}

// light only
function updateLinkProofsOfPrivateChain(arrPrivateElements, unit, message_index, output_index, onFailure, onSuccess){
	if (!conf.bLight)
		throw Error("not light but updateLinkProofsOfPrivateChain");
	if (!onFailure)
		onFailure = function(){};
	if (!onSuccess)
		onSuccess = function(){};
	checkThatEachChainElementIncludesThePrevious(arrPrivateElements, function(bLinked){
		if (bLinked === null)
			return onFailure();
		if (!bLinked)
			return deleteHandledPrivateChain(unit, message_index, output_index, onFailure);
		// the result cannot depend on output_index
		db.query("UPDATE unhandled_private_payments SET linked=1 WHERE unit=? AND message_index=?", [unit, message_index], function(){
			onSuccess();
		});
	});
}
