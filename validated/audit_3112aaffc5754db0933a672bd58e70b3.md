### Title
Self-servable `vrf_verify()` randomness in oscript/AA formulas allows the seed/proof generator to grind for a favorable outcome before ever submitting a unit - ([File: formula/evaluation.js])

### Summary
ocore exposes a VRF primitive to Autonomous Agent (AA) authors: `vrf_verify(seed, proof, pem_key)` [1](#0-0)  validates that `proof` is a valid RSA-PSS/PKCS1 signature of `seed` under `pem_key`, using `signature.verifyMessageWithPemPubKey` [2](#0-1) . The corresponding proof-generation helper `vrfGenerate(seed, privkey)` simply signs an arbitrary seed with an RSA private key [3](#0-2) . Nothing in the oscript grammar or evaluator restricts what `seed` may be - it is evaluated as an arbitrary expression [4](#0-3)  - and nothing binds the seed to any prior on-chain commitment (e.g. `trigger.unit`, `mc_unit`, or a previous AA response hash) that the caller can't control.

### Finding Description
This mirrors the reported LooksRare bug class: a party that both (a) controls/derives the "random" seed and (b) holds the VRF signing key can compute the VRF output completely off-chain, for as many candidate seeds as they like, and only ever broadcast the unit that encodes the favorable (seed, proof) pair. There is no request/commit step enforced by the protocol that fixes the seed *before* the VRF holder learns/chooses it, and no cost or on-chain penalty for computing extra candidates locally (RSA signing is cheap and never touches the network, unlike Chainlink's on-chain re-request which at least costs gas/LINK and is visible).

Any Obyte "game" AA built with this primitive - analogous to `Infiltration.sol`'s wound/heal outcome selection - typically works by having the trigger sender (or a paired "oracle" they control) supply a seed and matching VRF proof in `trigger.data`, and the AA's oscript computes the game outcome (e.g., via `number_from_seed`-style hashing of the verified seed, itself unrestricted at `formula/evaluation.js:1872-1919` [5](#0-4) ) as a function of that seed. If the identity supplying the seed is the same as (or colludes with) the identity holding the corresponding private key, they can:
1. Enumerate seeds locally (`seed_0, seed_1, ...`), sign each with `vrfGenerate`, and evaluate the resulting game outcome off-chain via a dry run or local re-implementation of the AA formula.
2. Only ever submit the one `(seed, proof)` combination whose outcome favors them.
3. If a submission would be unfavorable and the AA design allows the trigger to bounce (refunded minus a small bounce fee) rather than commit state, they get an even cheaper effective retry loop, structurally identical to the "wait 24h and re-request" abuse described in the source report - the party who ultimately benefits from the randomness controls when/whether the output is ever finalized on-chain.

Neither `formula/validation.js` nor `formula/evaluation.js` enforces that `seed` must derive from something outside the submitter's control (there is no special-casing of `vrf_verify`'s first argument the way there is for restricted pseudo-variables like `trigger.unit`/`mc_unit` in getters) [6](#0-5) .

### Impact Explanation
Any AA that implements a lottery/wager/PvP-style game using `vrf_verify` plus a self-supplied seed (a documented, supported usage pattern of this primitive) inherits a guaranteed-win/guaranteed-favorable-outcome exploit for whichever party can grind seeds against their own VRF key or collude with the key holder. This can drain AA-held funds (the equivalent of "always winning the game" against other honest participants who fund the pot), i.e. concrete unauthorized/asymmetric fund extraction from AA balances - matching the required impact bar (AA fund loss).

### Likelihood Explanation
Likelihood is high wherever an AA developer uses `vrf_verify` for gameplay outcomes with a self-supplied or colludable seed, since the primitive itself provides no protocol-level protection (no forced binding to a prior stable ball/unit hash, no request-then-reveal separation, no fee/penalty for local re-computation). This is a foundational, protocol-level gap rather than a single-contract bug, so every AA built on top of `vrf_verify` without independently re-deriving the binding is exposed by design.

### Recommendation
- Document (and ideally enforce at the oscript-validation layer) that `vrf_verify`'s `seed` argument must be bound to prior, already-stabilized DAG state that the VRF key holder cannot have foreseen before it existed (e.g., require the seed to equal or be derived from `trigger.unit`, `mc_unit`, or a previous AA response's unit hash, all of which are fixed at the time the seed-signing key holder would need to act).
- Consider adding a first-class "commit-then-reveal" AA pattern/helper: require a hash-commitment message to be posted and stabilized before the corresponding seed/proof can be accepted in a later trigger, closing the "grind-then-submit-only-the-winner" window entirely.
- At minimum, flag in the oscript validator any usage of `vrf_verify` where the seed is a `trigger.data` field or otherwise fully controlled by the same address supplying the proof, since this configuration is fundamentally unsafe for any outcome that affects value transfer.

### Proof of Concept
1. Deploy an AA that: reads `trigger.data.seed` and `trigger.data.proof`, calls `vrf_verify(trigger.data.seed, trigger.data.proof, <pubkey_of_operator>)`, and on success derives a game outcome via `number_from_seed(trigger.data.seed, 0, 1)` (win/lose), paying out from a shared pot on a win.
2. As the entity holding the RSA private key matching `<pubkey_of_operator>` (either the trigger sender themselves in a "self-oracle" design, or a colluding operator), off-chain and before ever broadcasting a unit: loop over candidate seed strings, call `signature.vrfGenerate(seed, privkey)` (as exercised in `test/pem_sig.test.js:2448-2456` [7](#0-6) ) to get `proof`, and locally recompute the same `number_from_seed` hash the AA would use.
3. Only broadcast the trigger unit containing the `(seed, proof)` pair that yields the winning outcome; discard all others without ever posting them or incurring any on-chain cost.
4. Repeat for every round of the game to guarantee winning every time, draining the AA's pot from other honest participants.

*Note: I could not find any concrete example AA definition in this repository (ocore is the protocol/node codebase, not an AA-template repo) that uses `vrf_verify` end-to-end for a game, so the exploit path is demonstrated against the primitive's documented/tested behavior rather than a specific shipped contract. If a specific vulnerable AA template exists elsewhere in this organization's repos, a Devin session with broader repo access would be needed to confirm the exact wiring.*
