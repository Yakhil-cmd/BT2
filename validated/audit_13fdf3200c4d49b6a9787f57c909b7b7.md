Based on my research, I found a close and concrete analog to the "missing transaction deadline" bug class inside the Obyte oscript/AA layer of this repository.

### Title
Order-book exchange AA executes signed orders without expiry validation, allowing stale-price fills - (File: `test/samples/order_book_exchange.oscript`)

### Summary
The order-book exchange autonomous agent (AA) template matches two off-chain signed orders (`order1`, `order2`) and executes a trade between them, but the `if` filter that validates the match explicitly skips expiry checking, as marked by the code comment `// to do check expiry`. This mirrors the `MeritDutchAuction.mint` issue: a user commits to a price at the moment they sign their order, but nothing in the AA logic prevents that order from being executed arbitrarily far in the future, at which point the market price for the assets involved may have moved drastically against the signer, causing loss of funds with no recourse.

### Finding Description
`order_book_exchange.oscript`'s "execute orders" case parses two signed order packages via `trigger.data.order1.signed_message` / `trigger.data.order2.signed_message`, validates asset compatibility, verifies signatures with `is_valid_signed_package`, checks against double-execution via `var['executed_' || $id]`, and validates partial fill/price-bound consistency between the two orders — but never checks any expiration/deadline field on either order before computing `$buy_amount1`/`$expected_buy_amount2` and mutating balances in the `state` block. [1](#0-0) 

Because the AA is a passive counterparty matcher (any unprivileged trigger sender can submit `order1`/`order2` to be matched, as long as they present two validly-signed packages, similar to a relayer/executor role), any third party who is holding a stale but still-validly-signed order from either counterparty can execute it at any later time, at the originally signed price, regardless of how much the relative asset values have since diverged. The signer of the stale order has no in-protocol way to invalidate their price commitment once signed, unless they manually withdraw all balance from the corresponding `var[$sell_key]` beforehand. [2](#0-1) 

This is functionally identical to the reported Solidity issue: a user's payment/commitment (the signed order, analogous to `msg.value` in `mint`) is locked to a price, and the eventual execution (mint / order match) can occur after significant time has passed with no deadline enforced, leading to execution at a price the user no longer intends to trade at.

### Impact Explanation
An order signer can suffer unauthorized loss of funds: their asset balance held in the AA (`var[$sell_key]`) can be swapped at a price that is no longer reflective of the market, since the only protections are double-spend prevention (`executed_` flags) and partial-fill accounting — not staleness. Because balances are custodied by the AA (via the "withdraw" and "silently accept coins" cases) and orders are bearer, off-chain signed messages, an old order can resurface and be executed by any relayer long after it should have expired, draining funds at a stale rate. This satisfies the "concrete unauthorized spending / fund loss" bar for a Medium-severity finding.

### Likelihood Explanation
Likelihood is dependent on typical usage patterns of such an order-book AA: order signers commonly assume unfilled orders lapse in relevance, and typical off-chain distributed order relaying (used to gather counterparties) can retain a signed order well past its intended validity, especially since the `last_ball_unit` field embedded in the order id is only used for uniqueness, not for expiry enforcement.

### Recommendation
Include an explicit expiry field (e.g., `expiry_ts` or `expiry_mci`) in the signed order payload, and validate it against `timestamp` (or `trigger.unit`'s MCI) in the AA's `if` filter before allowing a match, bouncing the trigger if either order has expired — implementing the very check the code's own comment (`// to do check expiry`) acknowledges is missing.

### Proof of Concept
1. Alice signs `order1` offering to sell asset A for asset B at price P, intending it to be valid only briefly (e.g., "good for 10 minutes").
2. The order is relayed off-chain but not executed immediately.
3. Days later, the price of A relative to B has moved substantially in Alice's disfavor.
4. Any party (Bob) who still holds Alice's validly-signed `order1` package can submit it paired with a fresh, favorable `order2` to the AA's "execute orders" case.
5. Because the `if` condition performs no expiry check [3](#0-2) , the AA executes the swap at Alice's original stale price, transferring value out of her `var[$sell_key1]` balance at a rate she never intended to honor at execution time.

```text
			{ // execute orders, order1 must be smaller or the same as order2; order2 is partially filled
				if: `{
					$order1 = trigger.data.order1.signed_message;
					$order2 = trigger.data.order2.signed_message;
					if (!$order1.sell_asset OR !$order2.sell_asset)
						return false;
					if ($order1.sell_asset != $order2.buy_asset OR $order1.buy_asset != $order2.sell_asset)
						return false;

					// to do check expiry

					$sell_key1 = 'balance_' || $order1.address || '_' || $order1.sell_asset;
					$sell_key2 = 'balance_' || $order2.address || '_' || $order2.sell_asset;

					$id1 = sha256($order1.address || $order1.sell_asset || $order1.buy_asset || $order1.sell_amount || $order1.price || trigger.data.order1.last_ball_unit);
					$id2 = sha256($order2.address || $order2.sell_asset || $order2.buy_asset || $order2.sell_amount || $order2.price || trigger.data.order2.last_ball_unit);

					if (var['executed_' || $id1] OR var['executed_' || $id2])
						return false;

					if (!is_valid_signed_package(trigger.data.order1, $order1.address)
						OR !is_valid_signed_package(trigger.data.order2, $order2.address))
						return false;

					$amount_left1 = var['amount_left_' || $id1] otherwise $order1.sell_amount;
					$amount_left2 = var['amount_left_' || $id2] otherwise $order2.sell_amount;

					if ($amount_left1 > var[$sell_key1] OR $amount_left2 > var[$sell_key2])
						return false;

					$buy_amount1 = round($amount_left1 * $order1.price);
					if ($buy_amount1 > $amount_left2) // order1 is not the smaller one
						return false;
					$expected_buy_amount2 = round($buy_amount1 * $order2.price);
					if ($expected_buy_amount2 > $amount_left1) // user2 doesn't like the price, he gets less than expects
						return false;

					true
				}`,
```
