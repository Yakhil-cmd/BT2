### Title
Webhook signature check is keyed to a payload-controlled organization while the acted-upon resource is a different, unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to authenticate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* request body, before any signature has been verified. [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the resolved organization's `webhook_secret` is blank/unset: [3](#0-2) 

The downstream handlers, however, do not resolve the target `Stack`/`Repository`/`Team` from `repository.owner.login`; they resolve it from a completely separate payload field, `repository.full_name` (or `organization.login` for org-scoped events like `membership`), with no cross-check against the organization used for signature verification: [4](#0-3) [5](#0-4) 

### Finding Description
This is the same class of bug as the Sandclock report: a check is performed against one field/binding ("is `sponsorAmount` within `totalUnderlying()`"), while the value actually acted upon (`totalShares`) is a different, unguarded state variable that an attacker can drive out of sync from what was verified. Here the equality that must hold is:

`organization authenticated by verify_signature (repository.owner.login / organization.login, matched against a configured webhook_secret)` == `organization/repository actually written to (repository.full_name used by Handler#stacks, or organization.login used by MembershipHandler#find_or_create_team!)`

In the multi-org configuration documented by Shipit itself (`docs/setup.md`, "Using Multiple Github Applications"), each org gets its own `github_app_config` and its own `webhook_secret`, looked up via `Shipit.github(organization: repository_owner)`: [6](#0-5) 

Every example/default secrets file in the repo ships this key commented out / nil (`webhook_secret: # nil`), and multi-org example configs mirror this for each org individually: [7](#0-6) [8](#0-7) 

If any one organization configured on a given Shipit instance is left with a blank `webhook_secret` (a state the project's own docs/config templates treat as normal/default), `verify_webhook_signature` unconditionally returns `true` for any request whose `repository_owner` resolves to that organization — regardless of what `X-Hub-Signature` header is sent, and regardless of the rest of the payload's content. [9](#0-8) 

Because `WebhooksController#create` then dispatches the *entire, attacker-controlled* JSON body to every registered handler for the event type, and those handlers key off `repository.full_name` (a field never covered by the check in `verify_signature`) to find the target `Stack`s/`Repository`, an attacker who merely knows that one org on the instance has no `webhook_secret` set can forge `repository.owner.login: "<no-secret-org>"` together with `repository.full_name: "<victim-org>/<victim-repo>"` and have the request processed as if it legitimately originated from GitHub for the victim repository. [10](#0-9) [11](#0-10) 

For org-scoped events such as `membership`, the same gap lets the attacker forge `organization.login: "<no-secret-org>"` while it is actually used, unmodified, as the `Team#organization` value and the team/member membership record created/removed — meaning an attacker can also directly manufacture memberships in any org name they choose (`find_or_create_team!` trusts `params.organization.login` completely, with no relationship to any authenticated identity): [12](#0-11) 

### Impact Explanation
- Forged `membership` events let the attacker create arbitrary `Team`/`Membership` rows tied to any organization string, which is the input to `Shipit.github_teams` / OAuth team-authorization checks elsewhere in the app — this is an escalation into `Shipit.github_teams` authorization (High per the rubric).
- Forged `push`/`status`/`check_suite`/`pull_request` events let the attacker drive stack state (sync jobs, commit statuses, review-stack lifecycle) for repositories/stacks they do not own, purely by knowing that some unrelated org on the instance has an unset `webhook_secret` — an unauthenticated write into stack state that the signature check was specifically supposed to gate.
- No `ApiClient` token, Shipit session, or GitHub App private key is required; the only precondition is one org configuration on the instance with `webhook_secret` blank, which is the value shown in every stock/example secrets file in this repo.

### Likelihood Explanation
Blank `webhook_secret` is not a hardened/hypothetical edge case here — it is literally the default/placeholder value in every checked-in example config (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), and the "Using Multiple Github Applications" documentation walks operators through adding additional orgs with their own (easily-left-blank) `webhook_secret`. Any Shipit instance onboarding a second, lower-priority organization without immediately wiring up its webhook secret is exposed. The attacker only needs to discover (or guess) the name of that under-configured organization — information often visible from the Shipit UI itself (stack list) or from public GitHub org membership.

### Recommendation
- Fail closed instead of open: `verify_webhook_signature` should reject the request (return `false`/422) when `webhook_secret` is not configured, rather than treating an absent secret as "trivially verified."
- Bind the identity used for signature verification to the identity used for handling: `Handler#stacks`/`MembershipHandler#find_or_create_team!` should be resolved from (or cross-checked against) the same `repository_owner`/organization value that `WebhooksController#verify_signature` authenticated, not an independent, unauthenticated payload field.
- Consider requiring `webhook_secret` to be present for every org in the multi-org config schema at boot/validation time, and warn/fail startup if any org's secret is empty.

### Proof of Concept
1. Operator configures Shipit with two orgs: `victim-org` (has stacks, `webhook_secret` set correctly) and `side-org` (added later, `webhook_secret` left blank as in the shipped example templates).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and any (or no) `X-Hub-Signature`, and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "side-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "side-org")`; because `side-org`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-78`), independent of the header and body.
4. `PushHandler#process` (via `Handler#stacks`, `repository_name` = `"victim-org/victim-repo"`) runs against the real victim stack, enqueuing `GithubSyncJob` for it — a write triggered by a request that was never actually signed for `victim-org`.
5. Analogous forged `membership` requests (`organization.login: "side-org"`) let the attacker create/modify `Team`/`Membership` records at will, since `find_or_create_team!` trusts `params.organization.login` unconditionally once the (trivially-bypassed) signature check passes.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
