### Title
Legacy simple-pattern rules with `event: all` silently never match Bash commands due to incorrect field inference - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` infers the condition field for legacy `pattern:`-based rules purely from the `event` value, mapping anything other than `bash`/`file` to `field='content'`. `event: all` rules therefore get `field='content'`, but `_extract_field` in `rule_engine.py` only populates `'content'` for `Write`/`Edit`/`MultiEdit` tools — never for `Bash`, which only exposes `command`. A rule authored as `event: all` with a dangerous Bash pattern (e.g. `rm -rf`) is thus a dead rule for Bash invocations.

### Finding Description
In `Rule.from_dict` (plugins/hookify/core/config_loader.py, lines 56-73), when a legacy `pattern` field is present without explicit `conditions`, the field is inferred as:
- `event == 'bash'` → `field = 'command'`
- `event == 'file'` → `field = 'new_text'`
- else (including `event: all`) → `field = 'content'` [1](#0-0) 

During evaluation, `RuleEngine._extract_field` (plugins/hookify/core/rule_engine.py, lines 182-254) resolves `'content'` only for tools `Write`/`Edit`/`MultiEdit`: [2](#0-1) 

For `tool_name == 'Bash'`, only `field == 'command'` is handled; there is no fallback that maps `'content'` to `'command'`. Since `'content'` is not a key of the Bash `tool_input` dict (which only has `command`), the `if field in tool_input` direct-lookup at the top of `_extract_field` also fails, and the function falls through to `return None` at line 254.

`_check_condition` (plugins/hookify/core/rule_engine.py, lines 144-160) treats a `None` field value as an automatic condition failure: [3](#0-2) 

Since `_rule_matches` requires all conditions to pass, a rule file such as:
```
---
name: block-rm
enabled: true
event: all
action: block
pattern: "rm -rf"
---
```
will never fire against a Bash `rm -rf` invocation, even though its author intended `event: all` to mean "match this pattern regardless of tool/event".

### Impact Explanation
This is a false-sense-of-security / hook-enforcement bypass: a deny/block rule that appears to be a universal catch-all silently never blocks dangerous Bash commands. If a user (or a template shared/distributed by an untrusted party, e.g. in a public repo or plugin marketplace) adopts such an `event: all` rule expecting it to guard against dangerous shell commands, `Bash` tool invocations matching the pattern will be allowed to execute unblocked, defeating the intended guardrail (`action: block`) enforced by `plugins/hookify`'s `PreToolUse` hook path via `evaluate_rules`.

### Likelihood Explanation
High feasibility and fully deterministic: any rule author who writes a legacy simple-`pattern` rule with `event: all` (a documented/plausible value per the `event` field comment `"bash", "file", "stop", "all", etc.`) targeting Bash commands hits this bug 100% of the time — no crafted malicious input is needed beyond an ordinary-looking rule file, which could be supplied via a shared template, documentation example, or plugin distribution.

### Recommendation
In `Rule.from_dict`, do not statically infer a single field from `event`. For `event == 'all'` (or any non-`bash`/`file` event intended to cover multiple tool types), either:
1. Emit multiple conditions (one per plausible field: `command`, `content`/`new_text`) combined with OR semantics, or
2. Change `_extract_field`/`_check_condition` to attempt matching the pattern against all relevant fields for the actual `tool_name` at evaluation time rather than a single field decided at parse time, or
3. Explicitly document/require that `event: all` simple-pattern rules only support fields common across tools (and validate/warn when the inferred field cannot be extracted for a given tool), so the dead-rule condition is surfaced instead of silently swallowed.

### Proof of Concept
Unit test in `rule_engine.py`/`config_loader.py` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

rule = Rule.from_dict(
    {"name": "block-rm", "enabled": True, "event": "all",
     "action": "block", "pattern": "rm -rf"},
    "Dangerous rm command blocked!"
)

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"}
})

# Expected (per author intent): result contains permissionDecision "deny"
assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
This assertion fails — `evaluate_rules` returns `{}` (no match), proving the rule never blocks the Bash command it was written to catch.
