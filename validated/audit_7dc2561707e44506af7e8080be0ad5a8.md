### Title
Cross-organization CI-status spoofing bypasses deploy authorization and triggers an unauthorized deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` binds HMAC verification to the **organization** named in the payload (`repository.owner.login` / `organization.login`), selecting that organization's `webhook_secret` to validate the signature [1](#0-0) . However, once the signature check passes, `StatusHandler#process` uses the payload's `sha` field to look up and mutate **any** commit in the entire database, with no check that the commit's stack/repository belongs to the organization that was actually authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This breaks the binding: `organization authenticated == repository/commit being written`.

### Finding Description
Signature verification (`Shipit::GitHubApp#verify_webhook_signature`) only proves that the raw payload was HMAC-signed with the `webhook_secret` configured for the organization identified in the payload's `repository.owner.login` (fallback `organization.login`) [3](#0-2) . In a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications"), each organization has its own independent `webhook_secret`. Any attacker who controls (or can configure) a webhook for **one** organization (`org-A`) in the Shipit instance can compute a valid HMAC signature over an arbitrary JSON body using `org-A`'s secret.

Unlike `PushHandler` and the `pull_request` handlers, which at least scope their queries by `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [4](#0-3) , `StatusHandler` performs **no repository/stack scoping whatsoever** — it matches on `sha` alone across the whole `Commit` table [5](#0-4) . Because the `status` field of `WebhooksController#repository_owner` is only used to pick *which secret to validate with*, and is never cross-checked against which commit/stack is actually mutated, an attacker owning `org-A`'s webhook secret can forge a `status` event naming a commit SHA belonging to a completely unrelated, victim stack/repository (`org-B`) and mark it `success`.

`Commit#create_status_from_github!` creates a `Status`, which triggers `Status#schedule_continuous_delivery` → `commit.schedule_continuous_delivery` and (via `Commit#add_status`) `stack.schedule_merges` [6](#0-5) [7](#0-6) . If the victim stack has `continuous_deployment` enabled, `ContinuousDeliveryJob`/`Stack#trigger_continuous_delivery` will pick this now-"passing-CI" commit as `next_commit_to_deploy` and call `trigger_deploy`, which executes the real `shipit.yml` deploy steps on the deploy host for that commit [8](#0-7) .

**Binding broken**: `organization authenticated via webhook_secret` ≠ `repository/stack whose commit-status (and consequent deploy trigger) is written`.

### Impact Explanation
This allows an unprivileged holder of a webhook secret for one organization/stack to force an unauthorized deploy (or unblock a merge queue via `schedule_merges`) on a stack belonging to a different, unrelated organization/repository configured in the same Shipit instance — as long as the attacker can guess or learn a commit SHA already known to Shipit (SHAs are routinely public in GitHub URLs, PR pages, commit statuses, etc.). This directly matches the "unauthorized deploy" Critical impact category, since it bypasses the CI-gating that continuous deployment relies on for a stack the attacker has no legitimate authority over.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented/supported), (2) attacker control of a webhook secret for at least one configured organization (a normal, low-privilege capability — e.g. any org admin who can register a GitHub App/webhook against Shipit), and (3) knowledge of a target commit SHA for a stack with `continuous_deployment` enabled. All are plausible in the documented deployment model; likelihood is moderate-to-high wherever multiple orgs share one Shipit instance.

### Recommendation
`StatusHandler` (and any other handler that trusts a payload field to select a record for mutation) must scope its lookups by the repository indicated in the payload, and that repository must be validated as belonging to the organization whose `webhook_secret` produced a valid signature — mirroring what `PushHandler`/`Handler#stacks` already do via `Repository.from_github_repo_name`. At minimum, `StatusHandler#process` should filter `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { full_name: payload.dig('repository', 'full_name') })` rather than matching bare `sha` across all stacks; additionally, `WebhooksController#verify_signature` should assert that the organization used to select the `webhook_secret` matches the owner of `repository.full_name` present in the same payload, closing the gap between "org authenticated" and "repository/commit acted upon".

### Proof of Concept
1. Shipit instance configured with two organizations, `org-A` (attacker-controlled webhook secret) and `org-B` (victim stack `victim/app` with `continuous_deployment: true`, undeployed commit `abc123` pending CI).
2. Attacker builds a JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-A/unrelated-repo" }
}
```
3. Attacker signs the raw body with `org-A`'s `webhook_secret` and sets `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: status`, then POSTs to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner` → `org-A`, fetches `org-A`'s `webhook_secret`, and the signature validates successfully [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the victim's commit in `victim/app` (unrelated to `org-A`), and creates a `success` status on it [2](#0-1) .
6. This schedules continuous delivery for the victim stack; if all required statuses are now satisfied, Shipit deploys commit `abc123` to production without any legitimate CI signal or authorization from `org-B`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
