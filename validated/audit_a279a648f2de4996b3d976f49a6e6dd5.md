### Title
Unsafe ERC721 `transferFrom` in `handleERC721Transfer` Permanently Locks Bridged NFTs Without Reverting — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC721Transfer` in `BridgeTransferERC721.sol` uses the bare `IERC721.transferFrom` instead of `safeTransferFrom` when delivering a bridged ERC721 token to the destination address. If the destination `_to` is a contract that does not implement the standard `IERC721Receiver` interface, the transfer executes without reverting, the bridge nonce is permanently consumed, and the `HandleValueTransfer` event is emitted — but the NFT is irreversibly locked inside the recipient contract with no recovery path.

---

### Finding Description

In `handleERC721Transfer`, the bridge first commits all protected state — the handled-request hash, the nonce mapping, and the lower/upper handle nonces — and emits `HandleValueTransfer`, then performs the actual token delivery:

```solidity
// State committed before transfer
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

// Delivery — no safeTransferFrom, no receiver check
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

The OpenZeppelin `ERC721.transferFrom` implementation does **not** call `_checkOnERC721Received`; it only verifies ownership/approval and moves the token. It will succeed and return without reverting even when `_to` is a contract that has no `onERC721Received` handler. [2](#0-1) 

By contrast, `safeTransferFrom` explicitly calls `_checkOnERC721Received` and reverts if the recipient contract does not return the magic selector: [3](#0-2) 

The ERC20 path in the same bridge correctly uses `SafeERC20.safeTransfer` for all deliveries: [4](#0-3) 

The ERC721 path has no equivalent protection.

---

### Impact Explanation

When `_to` is a contract without `IERC721Receiver`:

1. `transferFrom` succeeds — the NFT ownership record in the token contract is updated to `_to`.
2. The bridge's `lowerHandleNonce` / `upperHandleNonce` / `handleNoncesToBlockNums` are permanently updated; the nonce can never be re-used.
3. `HandleValueTransfer` is emitted; the off-chain bridge relayer marks the request as handled and will not retry it.
4. The NFT is permanently locked inside `_to` with no withdrawal mechanism.

The user who initiated the cross-chain transfer on the source chain has already had their token locked or burned there (via `requestERC721Transfer` / `onERC721Received`). The bridged asset is destroyed with no recourse. [5](#0-4) 

---

### Likelihood Explanation

The destination address `_to` is supplied by the end-user on the source chain and relayed verbatim by bridge operators. Any user who specifies a multisig wallet, a DAO treasury, a DeFi protocol contract, or any other contract that was not written to implement `IERC721Receiver` will trigger this path. This is a realistic and common scenario in production bridge usage. [6](#0-5) 

---

### Recommendation

Replace the bare `transferFrom` call in `handleERC721Transfer` with `safeTransferFrom`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

This causes the transaction to revert if `_to` cannot receive ERC721 tokens, preserving the bridge nonce and allowing operators to retry or refund the transfer. Note that the inbound path (`requestERC721Transfer` line 129) intentionally uses `transferFrom` because the bridge contract itself does not implement the standard `IERC721Receiver` interface (its `onERC721Received` has a non-standard signature); that call does not need to change. [7](#0-6) 

---

### Proof of Concept

1. Deploy a bridge in non-mintBurn mode with a registered ERC721 token.
2. Deploy a simple contract `Sink {}` with no `onERC721Received` implementation.
3. On the source chain, call `requestERC721Transfer(tokenAddr, sinkAddr, tokenId, "")`. The token is transferred to the bridge and a `RequestValueTransfer` event is emitted with `_to = sinkAddr`.
4. Bridge operators observe the event and call `handleERC721Transfer(txHash, from, sinkAddr, tokenAddr, tokenId, nonce, blockNum, "", "")`.
5. The call succeeds: `lowerHandleNonce` advances, `HandleValueTransfer` is emitted, and `IERC721(tokenAddr).ownerOf(tokenId)` returns `sinkAddr`.
6. The NFT is permanently locked in `Sink`. The bridge considers the transfer complete. The user has lost their NFT on both chains. [8](#0-7)
