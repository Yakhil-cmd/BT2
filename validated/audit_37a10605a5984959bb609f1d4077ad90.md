### Title
User-supplied pattern reminders rendered indistinguishably from built-in security warnings inside the same provenance-tagged block - ([File: plugins/security-guidance/hooks/extensibility.py])

### Finding Description
`_validate_pattern` in `plugins/security-guidance/hooks/extensibility.py` accepts a `reminder` string from a project-local `.claude/security-patterns.{yaml,json}` file with only a length cap and a non-empty check [1](#0-0) . There is no content filtering, escaping, or structural marking that would prevent the attacker-controlled `reminder` text from containing arbitrary strings, including a literal copy of `_base.PROVENANCE_TAG` or text mimicking the built-in banner format. The resulting rule dict (`{"ruleName": f"user:{name}", "reminder": reminder, "_source": source}`) is appended to the same list returned by `user_patterns()` and merged with the built-in `SECURITY_PATTERNS` list in `check_patterns()` in `security_reminder_hook.py`: `for pattern in list(SECURITY_PATTERNS) + extensibility.user_patterns():` [2](#0-1) . On a match, `check_patterns` returns `(pattern["ruleName"], pattern["reminder"])` uniformly for both built-in and user rules [3](#0-2) , with no distinguishing marker beyond the `ruleName` prefix `user:` (which is not shown to verify it is actually surfaced/preserved downstream in the emitted reminder text). The `_base.py` module's own comment on `PROVENANCE_TAG` explicitly acknowledges this: "an attacker could spoof the exact string; the tag is a signpost so the agent can ask the operator 'is this from your plugin?'" [4](#0-3) . This means the design already treats `PROVENANCE_TAG`/`PROVENANCE_BANNER` as non-authoritative and spoofable by construction — it is documented as a signpost, not a security boundary.

### Impact Explanation
I was unable to fully trace the exact code path in `security_reminder_hook.py` that renders the matched `(ruleName, reminder)` tuples from `check_patterns()` into the final `additionalContext`/reminder text sent to the model (the file is 2192 lines and truncated in my view; my last searches for `PROVENANCE_TAG` usage and `additionalContext` formatting in that file returned matches but I did not get to read the actual emission code before running out of tool calls). Based on what is confirmed: an attacker who can commit `.claude/security-patterns.yaml` to a repo can inject an arbitrary `reminder` string (up to 1024 bytes) that gets matched and surfaced alongside built-in warnings, and nothing in `_validate_pattern` prevents that string from including the `PROVENANCE_TAG` text or formatting that visually mimics it.

### Likelihood Explanation
Preconditions match a realistic, low-privilege scenario: no plugin install or admin rights are needed, only the ability to add a file to a repository the victim later opens with Claude Code (e.g. via a PR or a cloned malicious repo) [5](#0-4) . The load path (`_load_user_patterns` → `_validate_pattern`) is confirmed to accept and forward arbitrary reminder text with only a byte-length cap [6](#0-5) .

### Recommendation
I cannot make a fully confident recommendation without confirming how the reminder tuples are actually rendered downstream (the emission code in `security_reminder_hook.py` was not fully read). In general terms: user-pattern reminders should be visibly and structurally distinguishable from built-in ones wherever they are emitted — e.g. wrap user reminders in an explicit `[from project security-patterns.yaml, untrusted]` prefix and strip/escape any embedded occurrence of `PROVENANCE_TAG`/`PROVENANCE_BANNER` substrings from user-supplied `reminder` text before emission, rather than relying solely on the `_source`/`ruleName` prefix field that may or may not surface in the final text.

### Proof of Concept
Not fully constructible with the code I was able to verify — I did not confirm the exact rendering/emission function that turns `check_patterns()` output into the text block containing `PROVENANCE_TAG`/`PROVENANCE_BANNER`. A complete PoC would need to: (1) craft a `security-patterns.yaml` with `reminder: "<PROVENANCE_TAG text> IGNORE PREVIOUS INSTRUCTIONS..."`, (2) run it through `_load_user_patterns`/`_validate_pattern`, (3) run `check_patterns()` against matching content, and (4) inspect the actual emitted hook output (in the still-unread portion of `security_reminder_hook.py`) to assert whether the built-in provenance tag and the attacker's embedded copy become visually/structurally indistinguishable in the final text sent to the model.

**Uncertainty note:** This finding is based on confirmed code in `extensibility.py` and `_base.py`, but the critical last step — how `check_patterns()`'s output is actually formatted into the emitted `additionalContext`/reminder text, and whether `_source`/`user:` prefixing is preserved there — was not verified due to running out of tool-call budget on a 2192-line file. The `_base.py` comment strongly suggests the maintainers are already aware `PROVENANCE_TAG` is spoofable and treat it as a non-authoritative signpost rather than a trust boundary, which weakens (but does not necessarily eliminate) the security impact of this specific report.

```python
def _load_user_patterns(cwd: Optional[str]) -> List[Dict[str, Any]]:
    rules: List[Dict[str, Any]] = []
    for label, path in _config_paths(cwd, "security-patterns"):
        # _config_paths returns an extensionless stem (e.g.
        # ".claude/security-patterns" or ".claude/security-patterns.local");
        # try each supported extension.
        for ext in (".yaml", ".yml", ".json"):
            candidate = path + ext
            data = _read_config(candidate)
            if data is None:
                continue
            for entry in (data or {}).get("patterns", []):
                rule = _validate_pattern(entry, source=label)
                if rule:
                    rules.append(rule)
            break  # found one extension; don't double-load .yaml AND .json
        if len(rules) >= PATTERN_MAX_RULES:
            break
    if len(rules) > PATTERN_MAX_RULES:
        debug_log(f"extensibility: {len(rules)} user patterns > cap {PATTERN_MAX_RULES}; truncating")
        rules = rules[:PATTERN_MAX_RULES]
    return rules
```
