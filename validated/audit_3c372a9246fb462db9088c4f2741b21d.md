## Analog Found

### Title
Webhook signature verified against `repository.owner.login` but event handlers act on the unrelated `repository.full_name` field — cross-repository event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the direct analog of the CoinFabrik `PricingStrategy`/`FlatPricing` bug: the *documented/verification* binding uses one field of the payload while the *actual usage* binds to a different field. In `PricingStrategy` the interface promised `(weiRaised, tokensSold)` but the implementation consumed `(tokensSold, weiRaised)`. In Shipit, `WebhooksController#verify_signature` selects which GitHub App secret to check the HMAC against using `repository.owner.login` (or `organization.login`), while every event `Handler` resolves which `Stack`/`Repository` to mutate using the completely independent `repository.full_name` field [1](#0-0) [2](#0-1) [3](#0-2) .

### Finding Description
`Shipit` supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret` [4](#0-3) . `verify_signature` picks the secret to verify the HMAC with solely based on `repository_owner`, computed from `params.dig('repository','owner','login')` [2](#0-1) , and then calls `github_app.verify_webhook_signature(signature, request.raw_post)` [1](#0-0)  which is a pure HMAC-over-raw-body check, not tied to any specific field's content [5](#0-4) .

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire, attacker-controlled JSON body* to handlers [6](#0-5) . Every handler resolves the target `Stack` via `Handler#stacks`, which reads `repository_name = payload.dig('repository', 'full_name')` — a different sub-field than the one used for signature routing [3](#0-2) . `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers all use `repository.full_name` (or independently controlled sub-objects) to select which repository/commits to write to [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) .

**Binding that should hold:** `organization_that_signed(payload.repository.owner.login) == organization_that_owns(payload.repository.full_name)`.

Since the JSON body is entirely attacker-authored (an organization admin who legitimately owns a GitHub App integration and therefore legitimately knows *their own* `webhook_secret` can freely construct and POST any payload, not just relay a real GitHub event), nothing enforces that `repository.owner.login` and `repository.full_name` refer to the same repository. An attacker who administers *any* one organization configured in Shipit's multi-org `secrets.github` map can:
1. Set `repository.owner.login` = their own org login (so `verify_signature` fetches *their own* known `webhook_secret` and the HMAC check passes).
2. Set `repository.full_name` = `"victim-org/victim-repo"` — any repository/stack actually tracked by Shipit under a different org.
3. Compute the HMAC themselves using their own secret and POST to `/webhooks`.

Because `verify_webhook_signature` only checks that *some* valid HMAC exists for the org derived from `repository.owner.login`, and the handlers never re-check that `full_name` starts with that same owner login, the forged event is processed against the victim's stack.

### Impact Explanation
Concrete write actions reachable through this mismatch, before/after comparison:
- **Before (expected):** only GitHub, holding the secret for org X, can emit events that mutate stacks belonging to org X's repositories.
- **After (actual):** any tenant admin holding a valid `webhook_secret` for *any one* configured organization can emit fabricated events that mutate stacks/commits belonging to *any other* organization's tracked repository, because the routing field (`owner.login`) and the mutation-target field (`full_name`) are unbound.

Concretely reachable writes:
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` on victim commits matched purely by `sha`, letting the attacker inject arbitrary CI status (`state`, `context`, `description`) for any commit sha they guess/know, potentially manipulating whether a commit is considered "deployable" (CI green) and thus indirectly encouraging an unauthorized/incorrect ship decision [8](#0-7) .
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for the victim stack, forcing unscheduled re-sync activity against a stack the attacker does not own [11](#0-10) .
- `PullRequest::OpenedHandler` can create review stacks against the victim repository [12](#0-11) .

This crosses a repository/organization trust boundary that the multi-org webhook design explicitly intends to keep isolated (separate secrets per org), qualifying at minimum as a High-severity cross-tenant authorization escalation; the CI-status-forgery path toward influencing deploy decisions pushes it toward the "unauthorized deploy" Critical bucket depending on downstream deploy-safety checks that consume commit status.

### Likelihood Explanation
Requires only that Shipit is configured for multiple organizations (documented, supported feature — `docs/setup.md` and `lib/shipit.rb#github_app_config`) and that the attacker legitimately controls at least one of them (i.e., knows one org's `webhook_secret`, which is a normal, low-privilege, "unprivileged relative to other tenants" credential, not a GitHub App private key or Shipit `ApiClient` token). No GitHub write access to the victim repo, no Shipit session, and no privileged Shipit account are needed — only the ability to sign an HTTP POST with a secret the attacker is entitled to hold for their own org. This is directly analogous to the original bug: the swap is latent/harmless in a single-org deployment but becomes exploitable exactly when the "documented"/expected multi-argument (multi-field) binding is exercised, i.e., in multi-org installations.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, bind the same field used for authentication to the field used for mutation: after verifying the signature for `repository_owner`, require that `payload.dig('repository','full_name')` starts with `"#{repository_owner}/"` (or, for org-level events, that `organization.login == repository_owner`), rejecting the request otherwise. Alternatively, resolve the target `Stack`/`Repository` by an owner-scoped lookup (`Repository.where(owner: repository_owner, name: ...)`) rather than trusting the independently-supplied `full_name` string.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `attacker-org` (secret known to the attacker as its legitimate GitHub App owner) and `victim-org` (tracks a repo/stack the attacker does not control).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and sets `X-Github-Event: status`.
4. `verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")` [1](#0-0)  and the HMAC matches, so the request passes.
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` (victim's commit) and calls `create_status_from_github!`, writing a forged CI status onto the victim's repository despite the attacker never having proven control of `victim-org` [8](#0-7) .

**Uncertainty:** I could not fully trace `Commit#create_status_from_github!` or the exact downstream effect of a forged `status` event on deploy-eligibility logic (e.g., whether "deployable" checks strictly require it), since that model file was not indexed in this pass. This should be verified before finalizing severity as Critical vs. High. If the user needs the full contents of `app/models/shipit/commit.rb` or related deploy-safety logic, a Devin session with full repository access would be needed to confirm the exact downstream consequence.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
