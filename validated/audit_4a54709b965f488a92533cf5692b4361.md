### Title
`Shipit::DeploySpec::FileSystem#build_config` follows `inherit_from` path traversal outside `@app_dir`, merging arbitrary host YAML into the executed deploy spec - (File: app/models/shipit/deploy_spec/file_system.rb)

### Summary
`build_config` resolves the attacker-supplied `inherit_from` value with `path.dirname.join(...)` and then `read_config` loads it with `SafeYAML.load(path.read)` whenever `path.exist?`, with no check that the resolved path remains inside `@app_dir`. Because a PR author fully controls the `shipit.yml` checked out for their own review stack, they can set `inherit_from: ../../../some/host/file.yml` (or any relative traversal) to pull in and `deep_merge` the contents of any YAML-parseable file readable by the deploy-host process user into the spec used to build `deploy`, `machine.environment`, `review`, and `tasks` sections.

### Finding Description
The binding the question asserts should hold is: `resolved_inherit_from_path == path_within(@app_dir)`. Tracing the code shows this equality is never enforced: [1](#0-0) 

- `config_file_path` locates the checked-out `shipit.yml`/`shipit.<env>.yml` under `@app_dir` (`file(filename, root: true)` → `@app_dir.join(path)`), which is legitimate. [2](#0-1) [3](#0-2) 
- `load_config` reads that file and passes it to `build_config`. [4](#0-3) 
- `build_config` takes the value under the `inherit_from` key verbatim, joins it to `path.dirname` (a `Pathname#join` which honors `..` traversal and absolute paths), and if `inherits_from_path.exist?` calls `read_config(inherits_from_path)`, `deep_merge`s the result into `config_obj`, and recurses — with no re-check that the new `path` is still inside `@app_dir`. [5](#0-4) 
- `read_config` performs no containment check either — it simply does `SafeYAML.load(path.read) if path.exist?`. [6](#0-5) 

The existing test suite (`test/models/shipit/deploy_spec/file_system_test.rb`) exercises `inherit_from` chaining but only ever stubs `Pathname#exist?`/`#read_config` for files intended to sit alongside the checkout — it never verifies containment inside `@app_dir`, confirming there is no enforced guard here. [7](#0-6) 

Exploit flow: an unprivileged attacker opens a PR from their own fork/branch (a review stack is created per `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`/`ReviewStackAdapter`, using `params.pull_request.head.ref` as the stack's checked-out branch). [8](#0-7)  In that branch's `shipit.yml` the attacker sets `inherit_from: ../../../../some/known/yaml/file/on/host`. When the review stack is deployed/provisioned, `DeployCommands#steps` calls `deploy_spec.deploy_steps!`, which is backed by `DeploySpec::FileSystem#config` → `load_config` → `build_config`, so the merged (partially attacker-controlled, partially host-file-derived) config becomes the actual `deploy`/`machine.environment`/`review` values. [9](#0-8)  Those steps are turned into `Command` objects and ultimately executed via `PTY.spawn` on the deploy host. [10](#0-9) [11](#0-10) 

None of the standard guards apply here: `verify_signature`/webhook auth only gate whether the review stack is created at all, not what its own branch's `shipit.yml` may reference once checked out; `ExplicitParameters`, `force_github_authentication`, and `User#authorized?` are irrelevant to filesystem path resolution inside `FileSystem`; there is no `Repository`/`Stack` validator constraining `inherit_from` content since it is arbitrary YAML content inside the checkout, not a database column.

### Impact Explanation
Because `deep_merge` in `build_config` merges the inherited (outside) config as the base and the local (attacker's) config as override (`inherits_config_obj.deep_merge(config_obj)`), the attacker cannot simply overwrite legitimate host secrets values wholesale, but they can pull in any YAML-parseable file reachable from the deploy host's filesystem that the process user can read (other stacks' cached `shipit.yml`, credentials-shaped YAML, etc.) into fields such as `machine.environment`, `review.monitoring` (rendered as iframes/images on the deploy page), or `tasks`, causing arbitrary readable host file content to be merged into the executed/displayed spec for their own stack. Combined with the fact that an attacker already fully controls their own PR's `shipit.yml`, the additional capability here is host filesystem disclosure of YAML-shaped files outside the checkout root, which can surface secrets or configuration data belonging to unrelated stacks/tenants into the attacker's review stack's deploy output/environment — a cross-tenant information disclosure that fits the "exfiltration of deploy-time secrets" Critical category if such files exist and are readable by the deploy process.

### Likelihood Explanation
Preconditions are low: the attacker only needs review stacks enabled for the target repository with a provisioning behavior that doesn't require special privilege (`allow_all`, or `allow_with_label` where the attacker can add their own label) — exactly the review-stack creation path described as already achievable in prior findings. No Shipit credentials, GitHub secrets, or elevated GitHub permissions are required; the attacker only needs to author a `shipit.yml` in their own PR branch. The traversal itself is a single YAML key (`inherit_from: ../../...`), trivially repeatable per PR/branch, and the resulting merged config is used every time the stack's deploy spec is loaded (each deploy/task run against that review stack).

### Recommendation
In `build_config` (and/or `read_config`), after resolving `inherits_from_path`, canonicalize it (`inherits_from_path.expand_path`) and verify it is still a descendant of `@app_dir.expand_path` before treating it as existing/readable; if it falls outside, ignore the `inherit_from` value (or raise a `DeploySpec::Error`) instead of silently reading it.

### Proof of Concept
```ruby
# test/models/shipit/deploy_spec/file_system_test.rb
test '#load_config does not read files outside the checkout root via inherit_from traversal' do
  Dir.mktmpdir do |outside_dir|
    File.write(File.join(outside_dir, 'secret.yml'), "deploy:\n  override:\n    - cat /etc/shadow\n")

    Dir.mktmpdir do |app_dir|
      shipit_dir = File.join(app_dir, 'checkout')
      FileUtils.mkdir_p(shipit_dir)
      File.write(
        File.join(shipit_dir, 'shipit.yml'),
        "inherit_from: ../../#{File.basename(outside_dir)}/secret.yml\n"
      )

      stack = shipit_stacks(:shipit)
      deploy_spec = Shipit::DeploySpec::FileSystem.new(shipit_dir, stack)

      loaded_config = deploy_spec.send(:load_config)

      # BEFORE (broken binding): resolved path == expand_path(inherit_from) which is
      # NOT contained within shipit_dir, yet its content is merged in:
      refute Pathname.new(outside_dir).expand_path.to_s.start_with?(Pathname.new(shipit_dir).expand_path.to_s)
      # Vulnerable behavior asserted below should NOT happen after the fix:
      assert_not loaded_config.dig('deploy', 'override')&.include?('cat /etc/shadow'),
        'expected inherit_from traversal outside @app_dir to be rejected'
    end
  end
end
```

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
