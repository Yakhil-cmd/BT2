### Title
Unbounded decrement of shared `total_raised` state variable in `fundraising_proxy.oscript` can corrupt fundraising accounting and freeze/misroute contributor funds - (File: `test/samples/fundraising_proxy.oscript`)

### Summary
The `fundraising_proxy.oscript` reference AA tracks the total amount of bytes raised in the shared state variable `var['total_raised']`. Contributions increase it, and the "refund" case decreases it via `var['total_raised'] -= $amount;` where `$amount` is simply whatever amount of the transferable proxy share asset (`$asset`) the caller sends to the AA in that trigger — with no check that `$amount` does not exceed the current `var['total_raised']`. This is structurally the same bug class as `decreaseTotalLp` in `BLVaultManagerLido.sol`: a pooled/global accounting counter is decremented by a caller-supplied amount that is bounded only by what that caller happens to hold/send, not by the counter's own state, so it can be driven inconsistent (or negative) relative to reality.

### Finding Description
In `test/samples/fundraising_proxy.oscript`:
- On contribution, shares of the transferable, freely-tradable `$asset` are minted 1:1 (minus a small fee) to the contributor, and `var['total_raised']` is incremented by the same `$amount` [1](#0-0) .
- On refund, any holder of the `$asset` share token can trigger the AA by sending back `trigger.output[[asset=$asset]] > 0` of that asset. The AA computes `$amount = trigger.output[[asset=$asset]];`, pays back that many bytes, and unconditionally does `var['total_raised'] -= $amount;` — with no bound check against the current value of `var['total_raised']` and no check that the fundraising round is still `'open'` [2](#0-1) .

Because `$asset` is declared `is_transferrable: true` [3](#0-2) , shares can move freely between addresses outside the AA's knowledge (secondary transfers, aggregation from multiple contributors into one address, etc.), so the AA has no reliable way to ensure that a single "refund" request's `$amount` is properly bounded by the AA's own internal accounting of `total_raised`. This mirrors the audited `decreaseTotalLp` flaw where a vault-level LP total could be desynchronized from a user's actual entitlement because of externally/mistakenly transferred tokens, and the checked/unchecked decrement produced denial-of-service or accounting corruption for later, honest participants:
```
var['total_raised'] -= $amount;
```
There is no equivalent of the recommended `if (amount_ > totalLp) amount_ = totalLp;` clamp, nor a revert-based bound as in the original report — instead the value can silently go negative (or below the sum of remaining legitimate contributions), corrupting the `$missing_amount` / `$bDone` computation used to decide whether the fundraising target was reached and how much to forward to `$destination_aa` [4](#0-3) .

### Impact Explanation
`total_raised` directly drives:
- `$missing_amount = ceil((balance[$destination_aa][base] + $total_raised)*0.51) - ...` and `$bDone = ($total_raised > $missing_amount);` — i.e., whether/when the raised bytes get forwarded to the destination AA [4](#0-3) .
- The amount of bytes forwarded on completion: `outputs: [{address: "{$destination_aa}", amount: "{$total_raised}"}]` [5](#0-4) .

If `total_raised` is corrupted (driven negative or desynchronized from the AA's actual byte balance) by a refund that exceeds the tracked total, later legitimate contributors' funds can be miscalculated, forwarding to the destination AA can be triggered incorrectly (too early/too late or for the wrong amount), and subsequent honest refunds can fail because the arithmetic no longer reflects the AA's real balance — a fund-freezing/fund-misrouting outcome analogous to the "stuck deposit" impact in the original report.

### Likelihood Explanation
Reaching this requires only an unprivileged AA trigger sender holding (via receipt, purchase, or aggregation) more of the freely transferable `$asset` share token than corresponds to their own tracked share of `total_raised`, then sending it back in a refund trigger — no special privilege, front-running, or race condition is needed, only ordinary asset transfers that the asset's `is_transferrable: true` flag explicitly permits.

### Recommendation
Clamp the decrement so it can never drive the counter below zero or below what is actually owed, mirroring the audit's suggested fix pattern:
```
if ($amount > var['total_raised'])
    $amount = var['total_raised'];
var['total_raised'] -= $amount;
```
Additionally, consider gating the refund case on the round still being `'open'` (checking `var[$asset || '_status']`) so refunds cannot be processed after funds have already been forwarded to `$destination_aa`.

### Proof of Concept
1. Two independent users, Alice and Bob, each contribute 100,000 bytes; each receives ~98,000 units of `$asset` and `total_raised` becomes ~196,000.
2. Alice transfers her 98,000 `$asset` shares to Bob (allowed, since `is_transferrable: true`).
3. Bob now holds ~196,000 `$asset` shares and sends the full 196,000 back to the AA in one refund trigger: `$amount = 196000`, `var['total_raised'] -= 196000` → `total_raised = 0`.
4. Bob is refunded, but no check ensured this reflected only Bob's legitimate share; the AA's internal accounting (`total_raised = 0`) is now desynchronized from any subsequent contributions/state, corrupting the `$missing_amount`/`$bDone` logic for later contributors and any future rounds.
