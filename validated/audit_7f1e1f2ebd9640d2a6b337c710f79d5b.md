### Title
Webhook signature is verified against a GitHub organization derived from the payload, but the repository actually written to is derived from a different, unvalidated payload field — allowing cross-organization/cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the inbound HMAC signature against using `repository_owner`, which reads `repository.owner.login` (falling back to `organization.login`) from the **unauthenticated** JSON body. Once the signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name` and its subclasses) resolves the target `Repository`/`Stack` using a **different** field of the same unauthenticated body: `repository.full_name`. Because the field used to pick the verifying secret (`repository.owner.login`) and the field used to pick the entity that gets mutated (`repository.full_name`) are never cross-checked against each other, a request that is cryptographically valid for organization A's GitHub App can be crafted to act on a repository belonging to organization B.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This determines which per-organization `webhook_secret` (configured under `github.<org>.webhook_secret` for multi-org deployments, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) is used to HMAC-validate `request.raw_post`.

- Every handler that actually performs an action derives its target repository from a **separate** field:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
```
`PushHandler`, `StatusHandler`, and the `PullRequest::*Handler`s all resolve their target `Repository`/`Stack`/`PullRequest` via `params.repository.full_name`, not via `repository.owner.login`.

- `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON keys inside the same raw POST body. The HMAC signature only proves the payload was produced with the secret belonging to whichever organization `repository.owner.login` names — it says nothing about which repository `repository.full_name` names.

This is the same trust-binding class as the H-01 analog: the value used to authorize (`repository.owner.login`) and the value that is actually consumed/acted upon (`repository.full_name`) are not the same field, and nothing enforces that they must refer to the same repository/org.

### Impact Explanation
In a multi-GitHub-App Shipit deployment (an explicitly documented and supported configuration, `docs/setup.md:181-209`), each organization has its own `webhook_secret`. An actor who legitimately controls one onboarded organization's GitHub App (e.g. as an org owner able to view/rotate its own webhook secret, or simply by triggering real webhook deliveries from a repo they administer) can compute a valid HMAC for a payload where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` picks their own, valid `webhook_secret`), while
- `repository.full_name` = `"other-org/other-repo"` (a stack belonging to a completely different, unrelated tenant).

Because handlers key exclusively off `repository.full_name`, the forged, signature-valid request is dispatched against the victim organization's `Stack`:
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) calls `stack.sync_github(expected_head_sha: params.after)` on the victim stack, forcing a GitHub sync to an attacker-chosen SHA/branch state, which can influence undeployed-commit tracking and (for `continuous_deployment` stacks) trigger automatic deploys of attacker-chosen commits.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) is even less scoped: it looks up `Commit.where(sha: params.sha)` **globally, with no repository filter at all**, and calls `commit.create_status_from_github!(params)` — letting a holder of any organization's webhook secret forge CI/commit statuses for commits belonging to any repository tracked by the Shipit instance, which can flip `ignore_ci`/deployability gates and unlock a deploy that should have been blocked.
- The `PullRequest::*Handler`s can archive/unarchive/create review stacks belonging to unrelated repositories.

This crosses the "cross-repository writes" / "unauthorized deploy" impact bar: state belonging to one tenant's repository is mutated using signing material that only proves control of a different tenant.

### Likelihood Explanation
This requires the attacker to already control a legitimately configured GitHub organization/App on the same multi-tenant Shipit instance (i.e., be able to produce a validly-HMAC'd webhook body for their own org) — this is a real precondition but not privileged access to Shipit itself, no `ApiClient` token, and no access to the victim organization or its secrets. Given that Shipit explicitly supports and documents multi-organization deployments with distinct per-org secrets, this precondition is realistic for shared/hosted Shipit installs serving multiple orgs.

### Recommendation
Bind signature verification and repository resolution to the same field. Either:
- Verify the signature using the organization owning `repository.full_name` (not `repository.owner.login`/`organization.login`) and reject if `repository.owner.login` disagrees with the owner segment of `repository.full_name`, or
- After verification, re-derive `repository_name` strictly from the same identity that was authenticated, and reject events where `repository.full_name`'s owner segment doesn't match the authenticated organization.
- Additionally, scope `StatusHandler#process` lookups by repository (join through `Commit -> Stack -> Repository`) instead of a global `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` (attacker-controlled) and `OrgTwo` (victim), each with its own `webhook_secret`, and a `Stack` for `OrgTwo/victim-repo`.
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgOne_webhook_secret, raw_body)>` using `OrgOne`'s known/legitimate secret.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`) and validates successfully against `OrgOne`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a write to `OrgTwo`'s stack authorized only by proof of control over `OrgOne`.
