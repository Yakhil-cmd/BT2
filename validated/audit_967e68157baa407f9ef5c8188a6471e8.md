**Rationale:**

The `ShardedExecutorService::start` loop processes commands strictly sequentially and synchronously from `command_rx` via `receive_execute_command()`; it only proceeds to the next iteration after fully handling the current command, and `Stop` triggers an immediate `break` out of the loop, ending the thread [1](#0-0) . Since crossbeam channels preserve FIFO delivery order and there is a single consumer thread per shard, there is no possible interleaving where an `ExecuteSubBlocks` command is received and executed *after* a `Stop` has already been observed by that same loop — once `Stop` is matched, the loop exits and no further `recv()` calls occur.

More fundamentally, this component is part of the post-consensus, sharded block **execution** engine (parallel VM execution of an already-ordered, already-validated block across shards) — not the transaction **admission** boundary (mempool, vm-validator, authenticator/signature checks) that the review scope requires [2](#0-1) . Transactions entering `ExecuteSubBlocks` have already passed sender/signer/sequence/expiry/chain-id validation upstream; this code has no logic that binds sender, signer set, fee payer, or expiry decisions — it only dispatches pre-partitioned, pre-validated sub-blocks to worker threads and returns outputs [3](#0-2) . There is no unprivileged-input path here that could rebind sender/signer/expiry/replay guarantees, so it falls outside the Admission Impact Gate and Boundary Conditions defined for this review.

        trace!(

    fn execute_block(
        &self,
        state_view: Arc<S>,
        transactions: PartitionedTransactions,
        concurrency_level_per_shard: usize,
        onchain_config: BlockExecutorConfigFromOnchain,
    ) -> Result<ShardedExecutionOutput, VMStatus> {
        assert_eq!(transactions.num_shards(), self.num_shards());
        let (sub_blocks, global_txns) = transactions.into();
        for (i, sub_blocks_for_shard) in sub_blocks.into_iter().enumerate() {
            self.command_txs[i]
                .send(ExecutorShardCommand::ExecuteSubBlocks(
                    state_view.clone(),
                    sub_blocks_for_shard,
                    concurrency_level_per_shard,
                    onchain_config,
                ))
                .unwrap();
        }

        // This means that we are executing the global transactions concurrently with the individual shards but the
        // global transactions will be blocked for cross shard transaction results. This hopefully will help with
        // finishing the global transactions faster but we need to evaluate if this causes thread contention. If it
        // does, then we can simply move this call to the end of the function.
        let mut global_output = self.global_executor.execute_global_txns(
            global_txns,
            state_view.as_ref(),
            onchain_config,
        )?;

        let mut sharded_output = self.get_output_from_shards()?;

        sharded_aggregator_service::aggregate_and_update_total_supply(
            &mut sharded_output,
            &mut global_output,
            state_view.as_ref(),
            self.global_executor.get_executor_thread_pool(),
        );

        Ok(ShardedExecutionOutput::new(sharded_output, global_output))
    }
