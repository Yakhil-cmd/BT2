### Title
Unverified route hops can inject unauthorized wallet token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller bounds only its own input-token authorization and measures only `token_in`/`token_out` balances around `execute_strategy`; it does not constrain venue contracts invoked by the router or prevent those contracts from initiating additional `token.transfer(victim, attacker, amount)` calls under the victim’s authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
The advisory class is an integrity-check failure that lets injected messages execute as trusted input. In XOXNO, a strategy transaction carries an attacker-controlled route payload, while `swap_tokens` authorizes only the exact `token_in.transfer(controller, router, amount_in)` entry needed for the swap. [3](#0-2)  The contract then rejects controller input growth/overspend and requires positive measured output, but those checks do not inspect or bound other sub-invocations performed by route venues against the end user’s authority. [4](#0-3)  An attacker-deployed venue can therefore include a `token.transfer(victim_wallet, attacker, stolen_amount)` hop; simulation records it as a child of the caller’s `swap_collateral` authorization, and enforcement succeeds if that poisoned tree is signed. [5](#0-4) [6](#0-5) 

### Impact Explanation
A malicious route can steal tokens that are unrelated to the lending position and were never supplied to the protocol, including the victim’s whole balance of an arbitrary wallet token. [7](#0-6)  The regression test demonstrates that the route can still pay the expected fair output and update the victim’s collateral while transferring the victim’s entire unrelated wallet balance to the attacker. [8](#0-7)  This is theft of user funds.

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and place it in a submitted route because route venues are not allowlisted by the controller. [2](#0-1)  Reachable entrypoints include `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral`, all of which can execute user-provided router payloads for an account the caller controls. [9](#0-8)  Exploitation requires the victim or an integrating client to sign the expanded authorization tree; an honest wallet that rejects unexpected child invocations prevents the transfer, so the practical severity is Medium rather than higher. [10](#0-9) 

### Recommendation
Constrain execution so third-party route code cannot attach user-funded sub-invocations beneath the caller’s authorization. Prefer an execution model where the router receives only controller authorization and cannot resolve the original caller’s auth, or use a dedicated, revocable intermediary authority and prohibit venue calls that invoke user-funded token transfers. At minimum, the protocol should expose and enforce a canonical authorization-tree policy for every strategy route: legitimate controller strategies should contain only the expected controller invocation and no caller-funded child token transfer. [2](#0-1) 

### Proof of Concept
1. Alice owns controller account `account_id` with USDC collateral and holds `WALLET_BALANCE` of an unrelated token.
2. The attacker deploys a venue whose `swap` invokes `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`. [11](#0-10) 
3. The attacker supplies or causes Alice to use a route through that venue in `swap_collateral(caller = Alice, account_id, current = USDC, amount = SWAP_IN_USDC, new = ETH, swap = malicious_route)`. [12](#0-11) 
4. The controller authorizes only its own exact input transfer, calls the configured router, verifies input/output controller balance deltas, and does not reject the venue’s additional user transfer. [13](#0-12) 
5. Simulation records the malicious wallet transfer as a child of Alice’s `swap_collateral` authorization; if Alice signs that recorded tree, the transaction succeeds. [14](#0-13) 
6. Final state: Alice’s unrelated wallet-token balance is zero, the attacker receives `WALLET_BALANCE`, and Alice still receives the expected ETH collateral output. [15](#0-14)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
