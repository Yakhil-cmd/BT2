### Title
`pallet-nfts` pre-signed mint/attribute signatures lack chain domain separation, permitting cross-instance replay - ([File: substrate/frame/nfts/src/lib.rs])

### Summary
The `_checkSig` finding in HermezAuctionProtocol.sol describes a signature scheme with no domain separator (no contract address, no chainId), so a signature valid on one deployment/fork is also valid on another. The Polkadot SDK analog is `pallet_nfts::validate_signature` used by `mint_pre_signed` / `set_attributes_pre_signed`: the signed payload is `Encode::encode(&mint_data)` (or `PreSignedAttributes`), containing only `collection`, `item`, `attributes`, `metadata`, `only_account`, `deadline`, `mint_price` — no genesis hash, chain/instance identifier, or `pallet-nfts` instance discriminator.

### Finding Description
`mint_pre_signed` is a public, unprivileged, signed extrinsic [1](#0-0) . It verifies the signature over the raw SCALE-encoded `PreSignedMint` struct via `Self::validate_signature(&Encode::encode(&mint_data), &signature, &signer)` and then calls `do_mint_pre_signed`. The `PreSignedMint`/`PreSignedAttributes` payload types contain only pallet-local fields [2](#0-1) : `collection`, `item`, `attributes`, `metadata`, `only_account`, `deadline`, `mint_price` — no genesis hash, `spec_version`, or any value that is unique to a particular runtime/chain deployment.

`do_mint_pre_signed` only re-checks the deadline (block-number based, not chain-bound), `only_account`, and that `signer` currently holds the `Issuer` role on `collection` in the local pallet storage [3](#0-2) . There is nothing in the signed message or in the verification path binding the signature to a specific chain instance (genesis hash) or pallet instance.

This mirrors the reported invariant violation directly: the signature schema is the only authentication for the mint (the calling `origin` can be anyone), but the message signed has no domain separator, so the same signature is valid wherever an identical `(collection, item, ...)` tuple and `Issuer` role assignment exist — e.g., a forked/cloned chain (testnet snapshot, community fork, or any additional chain running the same runtime with the same collection id and issuer key) — unlike `frame_system`'s own signed-extrinsic authentication, which is protected end-to-end by `CheckGenesis`/`CheckSpecVersion`/`CheckTxVersion` extensions [4](#0-3) . `pallet-nfts`'s own off-chain signature scheme does not reuse or add an equivalent binding.

Other signature-checking pallets in this codebase were also reviewed for comparison:
- `pallet_verify_signature` binds the signature to the *entire inherited implication* of the transaction-extension pipeline (which, in a real extrinsic, includes `CheckGenesis`/`CheckSpecVersion` when present), so it inherits domain separation from the pipeline it is embedded in [5](#0-4) .
- `pallet_assets` precompiles' EIP-2612 `permit` explicitly implements EIP-712 domain separation with `chainId` and `verifyingContract` [6](#0-5) , and has a dedicated regression test proving cross-instance replay is rejected [7](#0-6) .
- `polkadot/runtime/common/src/purchase` also signs a bare `Statement` with no domain separator [8](#0-7) , but that signature is only consumed inside `create_account`, which requires a privileged `ValidityOrigin` to submit — so it does not meet the "no privileged prerequisite" requirement of this analysis and was excluded.

`pallet-nfts`'s `mint_pre_signed`/`set_attributes_pre_signed` is the one instance that is (a) reachable by an ordinary signed account with no privilege, and (b) has a signature scheme with no domain-separation field comparable to the reported bug.

### Impact Explanation
If the same runtime (and pallet-nfts config) is deployed twice with overlapping `(collection, item)` identifiers and the same `Issuer` account key exists on both (e.g., a permissionless community fork, or a test/staging chain cloned from production with the same genesis-derived accounts and collection ids), a pre-signed mint/attribute-approval authorized by the issuer on one chain can be replayed verbatim on the other chain, minting/approving items the issuer never intended to authorize there. This is analogous to the reported exploit ("Eve forks the protocol, gets Bob to sign on the fork, then replays on the original"), but the impact is bounded to the specific attacker-controlled/collection-scoped signature the issuer chose to produce — it does not grant unauthorized dispatch beyond what the issuer's signature already permits (mint a specific item to a specific/any account under `only_account`). This is a data-validation/replay gap rather than an unbounded issuance or authority bypass, since it still requires the issuer to have signed a message and requires the second deployment to contain the same collection id and issuer role assignment.

### Likelihood Explanation
Requires a scenario where the same runtime/pallet state (collection id, item id, issuer role) is legitimately or accidentally present on two chains/instances signing with the same key — most plausible with test-network clones of production chains or community forks reusing genesis state. It is not exploitable against a single canonical chain with no fork/clone, and I could not find and did not attempt to construct a concrete two-chain reproduction; this remains a design gap comparable to, but with narrower blast radius than, the reported EVM bug.

### Recommendation
Include a chain-specific domain separator (e.g., genesis hash and/or a pallet instance identifier) in the signed payload for `PreSignedMint`/`PreSignedAttributes`, mirroring what `pallet_assets` precompiles' `permit` already does with EIP-712 domain separation (`chainId` + `verifyingContract`) [6](#0-5) , so pre-signed approvals cannot be replayed across distinct chain deployments sharing the same collection/item identifiers.

### Proof of Concept
Not executed. This report is an analog assessment based on static code review; no local Rust/FRAME integration reproduction against two chain instances was run. The existing unit tests (`substrate/frame/nfts/src/tests.rs::validate_signature`, `pre_signed_mints_should_work`) confirm the signature only binds to the pallet-local `PreSignedMint` fields and demonstrate collection/deadline/only_account checks, but do not test cross-chain-instance replay, since the test harness operates within a single runtime instance [9](#0-8) . Constructing an actual two-instance reproduction (two independent `TestExternalities`/chains sharing collection id and issuer key, signature generated against one and replayed against the other) was not performed in this session.

	pub(crate) fn do_mint_pre_signed(
		mint_to: T::AccountId,
		mint_data: PreSignedMintOf<T, I>,
		signer: T::AccountId,
	) -> DispatchResult {
		let PreSignedMint {
			collection,
			item,
			attributes,
			metadata,
			deadline,
			only_account,
			mint_price,
		} = mint_data;
		let metadata = Self::construct_metadata(metadata)?;

		ensure!(
			attributes.len() <= T::MaxAttributesPerCall::get() as usize,
			Error::<T, I>::MaxAttributesLimitReached
		);
		if let Some(account) = only_account {
			ensure!(account == mint_to, Error::<T, I>::WrongOrigin);
		}

		let now = T::BlockNumberProvider::current_block_number();
		ensure!(deadline >= now, Error::<T, I>::DeadlineExpired);

		ensure!(
			Self::has_role(&collection, &signer, CollectionRole::Issuer),
			Error::<T, I>::NoPermission
		);

	fn verify_signature(who: &T::AccountId, signature: &[u8]) -> Result<(), DispatchError> {
		// sr25519 always expects a 64 byte signature.
		let signature: AnySignature = sr25519::Signature::try_from(signature)
			.map_err(|_| Error::<T>::InvalidSignature)?
			.into();

		// In Polkadot, the AccountId is always the same as the 32 byte public key.
		let account_bytes: [u8; 32] = account_to_bytes(who)?;
		let public_key = sr25519::Public::from_raw(account_bytes);

		let message = Statement::<T>::get();

		// Check if everything is good or not.
		match signature.verify(message.as_slice(), &public_key) {
			true => Ok(()),
			false => Err(Error::<T>::InvalidSignature)?,
		}
	}
