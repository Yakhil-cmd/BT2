### Title
Stack-scoped API token can read any stack's build/deploy status via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be created with a `stack_id`, which is meant to restrict that token to operating only on the associated stack. `Api::BaseController#stacks`/`#stack` enforce this restriction, but `Api::CCMenuController` overrides `#stack` to resolve the stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the per-token stack scope entirely. This lets a token that is authorized ("authorises") for exactly one stack instead "touch" (read the build/deploy status of) any stack in the installation.

### Finding Description
`Api::BaseController` defines the stack-scoping mechanism used by all other API endpoints: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

When an `ApiClient` has a `stack_id` set (`belongs_to :stack, optional: true` on `Shipit::ApiClient`), `#stacks` narrows the queryable set to that single stack, and `#stack` (used by `DeploysController`, `TasksController`, `StacksController#show/update/destroy`, etc.) resolves `params[:stack_id]` only within that scope — a request for a different stack raises `RecordNotFound`.

`Api::CCMenuController`, however, defines its own `#stack`: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

This resolves `params[:stack_id]` against `Stack.from_param!` directly, with no reference to `current_api_client.stack_id` at all. Authorization is only checked via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

`check_permissions!` only checks the coarse `read:stack` permission string — it has no notion of *which* stack, so it does not compensate for the missing scoping in `CCMenuController#stack`.

**The broken binding, stated as an equality that fails to hold:**

`stack a token authorises` (`ApiClient#stack_id`, enforced in `Api::BaseController#stacks`) ≠ `stack the request touches` (`Stack.from_param!(params[:stack_id])` in `Api::CCMenuController#stack`).

Before the PR/attack: a stack-scoped token (e.g. `here_come_the_walrus` fixture, which is scoped to the `shipit` stack) can only read/act on that one stack through every other endpoint that goes through `Api::BaseController#stack`.
After hitting `CCMenuController#show`: the same token, presenting any other `stack_id` in the URL, is granted a full XML render of that other stack's latest build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.), because the controller never consults `current_api_client.stack_id`.

This mirrors the reported bug class: a value that is supposed to be checked/negated/scoped against a trusted binding (here, the token's authorized stack) is instead used raw against attacker-supplied input (`params[:stack_id]`), silently widening the token's effective authorization.

### Impact Explanation
This is an authorization-scope escape: a legitimately-issued, narrowly-scoped `ApiClient` credential (e.g. issued to a third-party CI dashboard or status-check integration for one repository/stack) can be used to read the build/deploy status of every other stack in the Shipit instance, including stacks it was never granted access to. This matches the "High" impact bucket of "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" in spirit — it is a cross-stack unauthorized read of deploy/task status data via a credential explicitly scoped to a single stack. It does not achieve RCE or credential exfiltration, but it does break the confidentiality boundary that stack-scoped tokens are supposed to enforce.

### Likelihood Explanation
Any deployment of shipit-engine that issues stack-scoped `ApiClient` tokens (a documented, supported feature — `ApiClient belongs_to :stack, optional: true`) and relies on that scoping for confidentiality of build/deploy status is affected. Exploitation requires only possession of one valid stack-scoped token (which by design is meant to be a low-privilege credential) and knowledge/guessing of another stack's `stack_id` path (owner/repo/environment), which is not secret. No write access, no signature forgery, and no privileged account are required beyond the token itself.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped resolution from `Api::BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the controller-local override so it inherits the `current_api_client.stack_id` scoping enforced by `#stacks`/`#stack` in the base controller. Add a regression test asserting that a stack-scoped token receives `404`/`RecordNotFound` when requesting `ccmenu#show` for a stack outside its `stack_id`.

### Proof of Concept
1. Create/seed an `ApiClient` scoped to stack `shipit` with `permissions: ['read:stack']` and `stack_id` set to that stack's id (analogous to the `here_come_the_walrus` fixture in `test/fixtures/shipit/api_clients.yml`).
2. Confirm the scoping works elsewhere: `GET /api/stacks/rails/staging/staging` (a different stack) with this token via `StacksController#show` → `404 Not Found`, because `Api::BaseController#stack` calls `stacks.from_param!` and `stacks` is restricted to the token's `stack_id`.
3. Now call the CCMenu endpoint for that *same different stack*: `GET /api/stacks/rails/staging/staging/ccmenu` using the same stack-scoped token (Basic Auth or `?token=`).
4. Observe `200 OK` with the CCMenu XML payload (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.) for the `rails/staging` stack — a stack the token was never authorized for — because `Api::CCMenuController#stack` bypasses `current_api_client.stack_id` and resolves any `stack_id` via `Stack.from_param!` directly.
