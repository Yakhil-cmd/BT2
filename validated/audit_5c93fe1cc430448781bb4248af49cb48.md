### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository scoping, unlike sibling handlers (`PushHandler`, `PullRequest::*Handler`) which resolve the target via `Repository.from_github_repo_name(params.repository.full_name)` before touching any record. This lets a genuinely-signed GitHub `status` webhook for repository A write a `Status` (state/description/target_url/context) onto a `Commit` belonging to a completely different `Stack`/repository B, provided both repos share a commit SHA (a common situation for forks that share history with their upstream).

### Finding Description
The claimed binding — "description's authorizing repository == repository of the `hooks` it gets broadcast through" — is broken. `StatusHandler`'s params schema does not even declare/require a `repository` field [1](#0-0) , and `process` resolves commits purely by SHA across the entire `commits` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` [2](#0-1) . Compare this to `PushHandler`, which scopes work through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) before acting [3](#0-2) , and the base `Handler#stacks`/`#repository_name` helper that exists precisely for this purpose [4](#0-3) . `StatusHandler` simply never uses this scoping mechanism.

The controller-level `verify_signature` guard only proves the webhook was really sent by GitHub for the organization named in the payload's `repository.owner.login` (via `Shipit.github(organization: repository_owner).verify_webhook_signature`) [5](#0-4) ; it does not, and cannot, prove that the SHA in the payload belongs to that repository. Once the signature check passes for the attacker's own (legitimately onboarded) repository/fork, `StatusHandler` propagates the status to every `Commit` row with a matching `sha`, across all stacks in the database, via `commit.create_status_from_github!` → `Status.replicate_from_github!` [6](#0-5) [7](#0-6) .

`Status` creation fires `after_create`/`after_commit` callbacks (`enable_ci_on_stack`, `schedule_continuous_delivery`, `broadcast_update`) on the *victim's* commit/stack [8](#0-7) , and per `commits_test.rb`, this path fires `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` on `commit.stack`, delivering the attacker-chosen `description` to whatever outbound hooks the victim stack has configured [9](#0-8) .

**Attack**: attacker forks a public victim repository (an unprivileged action). Because forks share git object history with upstream up to the fork point, many commit SHAs are identical between the victim's tracked repo and the attacker's fork. Attacker sets up their own CI/integration on the fork to POST a `status` event for one of those shared SHAs, with an attacker-chosen `description`/`context`/`state`. This webhook is genuinely delivered/signed by GitHub for the attacker's own repo (satisfying `verify_signature`), but `StatusHandler` has no code path that checks the payload's `repository.full_name` against the commit's actual stack/repository before writing the `Status` and firing hooks.

### Impact Explanation
The victim's `Commit#status` can be mutated by an unrelated repository, changing `deployable?`/`blocked?` computations (`app/models/shipit/commit.rb:227-237`) and driving `ProcessMergeRequestsJob`/continuous delivery decisions, and the victim's own outbound webhook/Slack integrations (`hooks` association) broadcast attacker-chosen text as if it were the victim's own CI result. This matches the "payload for one repository mutating another's stack/commit" Critical category. Blast radius is bounded to stacks that happen to track commits sharing a SHA with a repository the attacker controls or can trigger CI on — most realistically forks of the same upstream project, which is a common real-world topology for open-source Shipit deployments.

### Likelihood Explanation
Preconditions: the attacker's repository/fork must be one for which Shipit's GitHub App is installed and webhook delivery/signing is configured (i.e., the org/app already onboarded), and the colliding SHA must actually exist as a `Commit` row in the victim `Stack`'s history (satisfied automatically for shared ancestor commits between a fork and its upstream, without needing an actual SHA-1 collision attack). This is inexpensive for an attacker who can fork a tracked repository and control a CI status on that fork — no secrets, sessions, or elevated GitHub permissions are required, only the ability to push/trigger a `status` event on a repo/commit they own. It is repeatable against any stack whose repository has forks with shared history.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`/`Handler#stacks`: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `commit.sha == params.sha AND commit.stack_id IN repository.stacks.ids` (or equivalently `Repository.from_github_repo_name(...).stacks.joins(:commits).where(commits: { sha: params.sha })`) instead of the bare `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (model/controller level, no live GitHub):
1. Create two stacks/repositories, `victim_stack` (repo `victim/app`) and `attacker_stack` (repo `attacker/app-fork`), each with a `Commit` sharing the same `sha` value (simulating a shared fork ancestor).
2. Add a `Hook` to `victim_stack` for `commit_status`/`deployable_status` events.
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.owner.login`/`full_name` corresponds to `attacker/app-fork` and body `{ sha: <shared_sha>, state: 'failure', description: '<attacker payload>', context: 'ci/attacker' }`, with `GithubHook#verify_signature` stubbed to `true` (representing a legitimately signed webhook for the attacker's own repo).
4. Assert: `victim_stack.commits.find_by(sha: shared_sha).statuses.last.description == '<attacker payload>'`, and assert `Hook.emit` fired on `victim_stack` with the attacker-controlled `description` (using `expect_hook_emit(commit, :deployable_status, ...)` as in `test/models/commits_test.rb:703-709`), proving cross-repository mutation of the victim's `Status`/hooks purely from a webhook authenticated for the attacker's own repository.
