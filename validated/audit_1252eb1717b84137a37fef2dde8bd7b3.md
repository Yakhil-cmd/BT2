### Title
Webhook signature check fails open when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub events - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` (i.e. "signature valid") whenever no `webhook_secret` is configured for the organization, instead of defaulting to "reject/unverified". Since Shipit's own example/documented secrets templates ship `webhook_secret: # nil` as the default value, any organization left with this default accepts arbitrary, unsigned webhook payloads as authentic GitHub events.

### Finding Description
The webhook authenticity boundary in Shipit is: `request came from GitHub` ⇔ `HMAC-SHA1 signature over the raw body verifies against the org's webhook_secret`. This is enforced in `WebhooksController#verify_signature`, which calls into `GitHubApp#verify_webhook_signature`: [1](#0-0) 

The actual verification logic is: [2](#0-1) 

`return true unless webhook_secret` means that when `@webhook_secret` (set from `@config[:webhook_secret].presence`, see `GitHubApp#initialize`) is blank, the method short-circuits to "verified", regardless of any signature header sent - or the complete absence of one. This is the same bug class as the reported `isLeverageEnabled` defect: a boolean/authorization gate that should fail-closed (default `false`/"unverified") instead fails-open (default `true`/"verified"), silently disabling the security check instead of requiring explicit configuration to enable trust.

Critically, this is not a hypothetical misconfiguration edge case — Shipit's own shipped templates present `webhook_secret: # nil` as the example/default value in every secrets file: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (vacuously), `WebhooksController#create` dispatches the raw, attacker-controlled JSON body straight to the registered handlers with no further authentication: [5](#0-4) 

The handler that resolves which `Stack`/`Repository` the event applies to trusts the `repository.full_name` field embedded in that same unauthenticated payload: [6](#0-5) 

For the `status` event specifically, `Handlers::StatusHandler` creates a `Status` record on the named commit from unauthenticated attacker input (state, context, etc.), which is exactly the signal Shipit's CI-gating and continuous-deployment logic uses to decide whether a commit is safe to deploy (`Commit#deployable?`, `Stack#next_commit_to_deploy` / `deployable_commits`). By forging a `success` status for an arbitrary commit, an unauthenticated attacker can flip a commit from "blocked/pending/failing" to "allowed", clearing the CI gate that both human operators and continuous-delivery rely on before shipping code — without ever authenticating to Shipit, GitHub, or holding any `ApiClient` token.

### Impact Explanation
This crosses the credential/authentication boundary described in the rules: it is an authentication-check binding (`verified` should equal `signature covers this exact payload with a real secret`) that instead defaults to `verified = true` whenever the operator uses the documented default (blank secret). The practical outcomes for any org configured this way:
- Unauthenticated forgery of GitHub webhook events (`push`, `status`, `pull_request`, `membership`, `check_suite`) processed as trusted GitHub input.
- Forged `status` events can mark arbitrary commits as CI-"successful", defeating the `ci.require`/`blocking` gating that governs `Commit#deployable?`, and can cause `ContinuousDeliveryJob`/`Stack#trigger_continuous_delivery` to automatically ship an untested/malicious commit — an unauthorized deploy, matching the Critical impact bar ("unauthorized deploy").
- Forged `membership`/`pull_request` events can also corrupt team membership records and review-stack state used elsewhere for authorization decisions (`Shipit.github_teams`), touching the High-impact bar as well.

### Likelihood Explanation
The webhook endpoint (`/github/webhooks` handled by `WebhooksController`) is unauthenticated by design (it must accept requests from GitHub before any signature is checked), so no session, `ApiClient` token, or repository write access is required — only network access to the Shipit instance. The only precondition is that the target organization's `github.webhook_secret` is left blank, which is exactly the value shown in the engine's own shipped secrets templates, making it a highly plausible real-world default rather than an exotic misconfiguration.

### Recommendation
Change `verify_webhook_signature` to fail closed: if no `webhook_secret` is configured, treat all requests as unverified (return `false`) rather than `true`, and require operators to explicitly opt out (e.g. via an explicit `disable_webhook_signature_verification` flag) if they intentionally want to run without payload authentication. Additionally, consider cross-checking the payload's `repository.full_name`/owner against the organization that was used to select the webhook secret, so a valid signature from org A cannot be replayed to affect a differently-named repository.

### Proof of Concept
1. Deploy Shipit with a GitHub app configured using the documented default, i.e. `github.webhook_secret` left blank (`webhook_secret: # nil`), as shown in `config/secrets.development.example.yml`.
2. As an unauthenticated attacker, send:
   ```
   POST /github/webhooks
   X-Github-Event: status
   Content-Type: application/json

   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "branches": [{"name": "master"}],
     "repository": {"owner": {"login": "<target-org>"}, "full_name": "<target-org>/<target-repo>"}
   }
   ```
   No `X-Hub-Signature` header is required.
3. `WebhooksController#verify_signature` calls `GitHubApp#verify_webhook_signature(nil, body)`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `Handlers::StatusHandler` processes the forged payload and creates a `success` `Status` on the targeted commit, clearing CI gating for that commit, potentially triggering an unauthorized continuous deployment.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
