### Title
Unbounded `eventBus` listener accumulation in arbiter-contract payment handler causes memory-leak DoS - ([File: arbiter_contract.js])

### Summary
CVE-2020-10593 describes a Tor bug where a circuit-padding state machine could be negotiated twice on the same circuit because the negotiation handler did not check for an already-existing machine before creating a new one, causing memory to leak with every repeated negotiation. The `new_my_transactions` handler in `arbiter_contract.js` has the same root-cause pattern: every time a payment-related event fires for a contract that is in the `accepted` state, a brand-new `arbiter_contract_update` listener is registered without checking whether an equivalent listener already exists for that contract, and the listener is only ever removed when a very specific follow-up event occurs.

### Finding Description
In the `new_my_transactions` handler, for every incoming unit that pays into a shared address tied to a contract whose status is `accepted`, the code unconditionally adds a new one-off listener: [1](#0-0) 

There is no de-duplication key/guard (e.g. "do I already have a `retryPaymentCheck` registered for `contract.hash`?") before calling `eventBus.on('arbiter_contract_update', ...)`. The listener is designed to self-remove only when a very specific pair of conditions is met later: `objContract.hash === contract.hash && field === 'unit'`: [2](#0-1) 

This is structurally identical to the Tor bug class: a per-object state/resource (here, an event listener tied to a contract) is created again and again without verifying that one was already negotiated/registered for the same object, and the resource is only released on a narrow terminal condition that a remote counterparty fully controls (whether/when they broadcast the signing unit).

### Impact Explanation
`new_my_transactions` fires on every unit that touches a locally-watched or owned address, which happens automatically for any output paid to the contract's `shared_address`. A private-payment counterparty (the peer side of an arbiter contract, who chose to leave the contract in `accepted` status — e.g., by delaying or never sending the final signed/cosigned unit) can cause the local wallet to receive multiple qualifying units to the shared address (e.g., by sending the required amount in several smaller outputs/units, or by having other parties pay into the same tracked shared address) while never sending the completing `unit` event. Each qualifying unit adds one more permanent `arbiter_contract_update` listener that is never cleaned up, since the specific `field === 'unit'` condition that removes it never fires. Over time this causes unbounded growth of the process's event listener list — an in-process memory leak — degrading the victim wallet/hub node and potentially triggering Node's `MaxListenersExceededWarning` performance degradation or eventual crash from memory exhaustion, i.e. a Denial of Service.

### Likelihood Explanation
The trigger requires an active arbiter-contract relationship with the victim (contract in `accepted` status) and the counterparty repeatedly causing "new_my_transactions" events that satisfy the SQL filter (payment to shared address, contract status `signed`/`accepted`, sequence good), which is entirely under attacker (payer/counterparty) control since they decide how many units/outputs to send and whether to ever complete the contract. No special privileges beyond being a contract counterparty are needed, matching the requested "private-payment counterparty" reach class. This makes exploitation straightforward, though the severity of the leak (bytes per listener closure) is modest per event, so a sustained attack requires many repeated qualifying transactions.

### Recommendation
Guard against duplicate listener registration per contract, e.g., track registered `retryPaymentCheck` state per `contract.hash` (a `Set`/map keyed by hash) and skip `eventBus.on(...)` if one is already pending; alternatively use `eventBus.once` combined with an existence check, or bound the number of outstanding listeners and log/reject beyond a threshold. Ensure the listener is also removed on contract cancellation/expiry/ttl timeout, not only on the specific `field === 'unit'` event, so a counterparty that never completes the contract cannot keep the listener (and its closure state) alive indefinitely.

### Proof of Concept
1. Attacker and victim wallet set up an arbiter contract; contract reaches `accepted` status on the victim's side (victim has received a payment-qualifying unit but not yet the completing signed `unit`).
2. Attacker (counterparty) sends N additional units to the contract's `shared_address` in a way that continues to satisfy the `new_my_transactions` SQL filter (status remains `accepted`, `sequence='good'`, amount sums keep matching).
3. Each of the N units causes another `eventBus.on('arbiter_contract_update', function retryPaymentCheck...)` registration at [2](#0-1)  that is never removed because the attacker never emits the completing `unit` field update.
4. Repeating this over time causes the victim process's listener count and associated closures to grow without bound, consuming increasing memory. [3](#0-2)
