### Title
Signature verification is bypassed for organizations without a `webhook_secret`, allowing unsigned webhook payloads to be processed against any repository referenced in the payload - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
Shipit's inbound webhook authentication binds the *cryptographic check* to the organization named in `repository.owner.login`, but the *write target* (the `Stack`/`Repository` that gets mutated) is resolved from the independent `repository.full_name` field of the same untrusted JSON body. When the organization selected for verification has no `webhook_secret` configured, `verify_webhook_signature` unconditionally returns `true`, so the binding between "organization that authenticated" and "repository that is written" collapses entirely for that request.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to check against using an attacker-controlled payload field, not anything derived from a validated source: [1](#0-0) [2](#0-1) 

The actual signature check, in `Shipit::GithubApp#verify_webhook_signature`, fails open when no secret is configured for that resolved organization: [3](#0-2) 

`return true unless webhook_secret` means any organization entry in `Shipit.github` config that has a blank/nil `webhook_secret` (a state the codebase's own shipped configuration templates treat as normal/expected) causes **all** webhooks whose `repository.owner.login` resolves to that organization to be accepted without any signature check at all — regardless of the `X-Hub-Signature` header content: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, the controller dispatches the entire raw payload to handlers keyed only by `X-Github-Event`: [6](#0-5) 

Handlers (e.g. the push handler, confirmed by test behaviour resolving `GithubSyncJob.perform_later(stack_id: @stack.id, ...)`) resolve the target `Stack`/`Repository` from `repository.full_name`, which is built from `owner + "/" + name` on the `Repository` model: [7](#0-6) [8](#0-7) 

Because `repository.owner.login` (used only to pick the verification secret) and `repository.full_name` (used to pick the write target) are two independently-settable keys inside the same forged JSON body, an attacker only needs the payload's `repository.owner.login` to match an organization configured without a `webhook_secret` (e.g. a staging/dev org present in the same multi-tenant `Shipit.github` config) to have the signature check pass unconditionally, while pointing `repository.full_name` at an entirely different, "secured" organization's repository whose stack actually gets mutated (e.g. triggering `GithubSyncJob`, commit-status updates, PR/merge-queue state changes, or membership/team writes for that other org).

**Equality that should hold, and is broken:**
`organization whose secret authenticated the request == organization that owns the repository/stack being written`

Before the attack: this equality trivially holds for legitimate GitHub-originated webhooks because GitHub itself keeps `repository.owner.login` and `repository.full_name` consistent and signs the whole body with the correct per-installation secret.

After the attacker's crafted request: `repository_owner` (verification key) = an org with no `webhook_secret` configured; `repository.full_name`'s owner = a different, targeted org/repo. `verify_webhook_signature` returns `true` unconditionally for the first org, so the equality is broken and the second org's stack is written to based on entirely unauthenticated attacker data.

### Impact Explanation
This crosses the "High" bar explicitly listed in the rules: unauthenticated write/mutation of stack state (commit statuses, PR/merge-queue transitions, team/membership creation, GithubSyncJob triggers) for a repository the attacker was never authorized to send events for, achieved purely by forging an unsigned HTTP request to the public webhook endpoint — no `ApiClient` token, GitHub App key, or repository write access required. In multi-organization Shipit deployments (the engine explicitly supports and ships example configs with several `Shipit.github` entries), one loosely-configured/staging organization with a blank `webhook_secret` becomes a skeleton key for forging events against every other configured organization's repositories.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires at least one organization entry in `Shipit.github` with `webhook_secret` unset alongside at least one other organization whose repositories are meant to be protected. This is a realistic and even encouraged pattern shown by the engine's own example configs (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.test.json`), where `webhook_secret: nil` is treated as a normal/supported value rather than being rejected — the vulnerability is a fail-open root-cause defect in the engine's own `verify_webhook_signature`, not a misuse of an undocumented feature.

### Recommendation
- Change `GithubApp#verify_webhook_signature` to fail closed: if `webhook_secret` is not configured for an organization, reject the webhook (return `false`) rather than treating it as automatically verified, at minimum outside of test/development environments.
- Bind the verification organization to the same value used to resolve the write target — i.e., re-derive/re-check `repository.full_name`'s owner against the same `repository_owner` used for `Shipit.github(organization:)` lookup, and reject if they diverge, so a single payload cannot mix an unauthenticated organization identity with a different repository's write path.

### Proof of Concept
1. Deploy Shipit with two organizations configured in `Shipit.github`: `trusted-org` (has a real `webhook_secret`) and `staging-org` (configured with `webhook_secret: nil`, as shown to be a supported configuration in `config/secrets.development.shopify.yml`).
2. As an unauthenticated attacker, POST to `/webhooks` with:
   - Header `X-Github-Event: push`
   - Body: `{"repository": {"owner": {"login": "staging-org"}, "full_name": "trusted-org/production-repo"}, "after": "<attacker-chosen-sha>", ...}`
   - No valid `X-Hub-Signature` header (or an arbitrary garbage value).
3. `verify_signature` resolves `Shipit.github(organization: "staging-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately (`lib/shipit/github_app.rb:77`), regardless of the header sent.
4. The push handler processes the payload using `repository.full_name` = `"trusted-org/production-repo"`, enqueuing `GithubSyncJob` (or equivalent commit-status/PR/membership handlers) against `trusted-org`'s real stack, entirely unauthenticated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
