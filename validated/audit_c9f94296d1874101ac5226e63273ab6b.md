### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while write-path handlers trust the unrelated `repository.full_name` field, allowing a different organization's webhook secret to author events for another org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-tenant configurations (`Shipit.github_organizations` with per-organization `webhook_secret`), `WebhooksController#verify_signature` selects the HMAC secret to validate the request using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  However, none of the event handlers that actually mutate state use `repository.owner.login` to resolve which `Repository`/`Stack` to act on — they use the independent field `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key configured in `secrets.github`. [5](#0-4)  The controller picks that organization strictly from `repository.owner.login` (or `organization.login`) in the untrusted JSON body, verifies the HMAC signature against that org's secret, and — critically — never re-checks that `repository.owner.login` is consistent with `repository.full_name`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Once the signature passes, `create` dispatches the full payload — including `repository.full_name` — to every registered handler for the event unmodified. [7](#0-6)  Handlers such as `PushHandler`, `PullRequest::ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, and `AssignedHandler` resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` / `params.repository.full_name`, with no cross-check against `repository.owner.login`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) [8](#0-7) [9](#0-8) 

This is structurally identical to the reported analog bug class: a value (`_amountForContract`/penalty) that the code accounts for under one accounting bucket (the surrogate's ownership, or here, "org A authenticated this webhook") is never bound/verified against the entity that is actually acted upon (the `BobStaking` contract balance, or here, "repository B whose Stack gets synced/archived/unarchived"). The binding the code implicitly assumes — `repository.owner.login == owner(repository.full_name)` — is never enforced, so:

`organization that authenticated the HMAC signature` ≠ `repository that the handler actually writes to`

Any org admin who is entitled to configure/know a webhook secret for **one** organization registered in Shipit (e.g., `orgA`) can forge a signed webhook whose `repository.owner.login` is `"orgA"` (satisfying signature verification) but whose `repository.full_name` is `"orgB/some-repo"` (a completely different, unrelated organization/repository also hosted on the same Shipit instance). The forged payload will pass signature verification using `orgA`'s secret and then be processed by handlers that act on `orgB/some-repo`.

### Impact Explanation
This crosses exactly the boundary called out as High severity in the rules: "escalation into `Shipit.github_teams` authorization" is not directly implicated, but this is a cross-repository/cross-organization write achieved purely by possessing credentials scoped to a different, unrelated tenant. Concretely:
- A crafted `push` event can trigger `stack.sync_github(expected_head_sha:)` on `orgB`'s stacks, forcing a `GithubSyncJob` for a branch/SHA the attacker chooses, for a repository the attacker doesn't own. [10](#0-9) 
- A crafted `pull_request` `closed`/`reopened`/`labeled`/`unlabeled` event can archive/unarchive review stacks belonging to `orgB`. [11](#0-10) [12](#0-11) 

These are unauthorized cross-tenant state changes triggered without holding any credential legitimately scoped to the target repository/organization — matching the "cross-repository writes" / "unauthorized deploy trigger via sync" impact bucket.

### Likelihood Explanation
Likelihood is High for any deployment that uses the multi-organization `secrets.github` schema (multiple keys under `github`, each with its own `webhook_secret`), which is an explicitly supported, documented configuration path (`Shipit.github_organizations`, `github_app_config`). [13](#0-12)  The only prerequisite is that the attacker legitimately knows one org's `webhook_secret` (e.g., they administer that org's GitHub App/webhook config) — no repository write access or Shipit session is required, satisfying the "unprivileged-attacker" framing since the attacker has no privilege over the *target* org/repository.

### Recommendation
In `WebhooksController#verify_signature` / `#create`, after verifying the signature, assert that `repository.owner.login` (or `organization.login`) is consistent with `repository.full_name`'s owner segment before dispatching to handlers, e.g.:
```ruby
def create
  params = JSON.parse(request.raw_post)
  claimed_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) and return if claimed_owner && repository_owner && claimed_owner.casecmp(repository_owner) != 0
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
Alternatively, resolve the target `Repository` using `repository_owner` (the value bound to the verified signature) rather than trusting `repository.full_name` independently in each handler.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing `orga: {webhook_secret: "secretA", ...}` and `orgb: {webhook_secret: "secretB", ...}`, each with a `Stack` registered for `orga/repo1` and `orgb/repo2` respectively.
2. As someone who legitimately knows `secretA` (e.g., an admin of `orga`'s GitHub App), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/repo2" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(secretA, raw_body) and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "orga")` and successfully verifies the signature against `secretA`. [1](#0-0) 
5. `PushHandler#process` resolves `Repository.from_github_repo_name("orgb/repo2")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on `orgb`'s stack, even though the request was never signed with `orgb`'s secret. [10](#0-9)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
