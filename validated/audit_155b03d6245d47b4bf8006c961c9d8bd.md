### Title
Webhook signature verification is scoped to the payload's claimed `repository.owner.login`, not to the repository actually acted upon, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on an attacker-controlled field taken from the *unverified* JSON body, and never checks that the organization used to validate the signature actually owns the repository the webhook subsequently mutates.

```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a blank/absent `webhook_secret` as automatic success, which the setup docs and example secrets files present as a normal, supported per-organization configuration option:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) [4](#0-3) 

Meanwhile, the actual repository/stack that a handler acts on is derived from a **different, independent** field of the same payload:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

and `PushHandler#process` uses that lookup to trigger a sync/deploy on the matched stack:

```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

The binding the engine implicitly relies on is:

`organization authenticated by verify_signature == owner of the repository written by the handler`

Nothing in the code enforces this equality. `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the Stack/Repository that gets mutated) are two independent, attacker-supplied JSON paths inside the same unauthenticated request body — the code only checks that *some* configured organization's secret validates the raw body, not that it is the organization that owns the repository being modified.

### Impact Explanation
In a documented multi-organization Shipit deployment (`secrets.github` keyed by multiple org names, each with its own optional `webhook_secret`, exactly as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), if even one configured organization has no `webhook_secret` set (which the docs list as "optional"), an unprivileged attacker who knows/guesses that organization's name can forge a webhook that:
- sets `repository.owner.login` (or `organization.login`) to the weakly-configured org, so `verify_webhook_signature` returns `true` unconditionally,
- sets `repository.full_name` to any tracked repository belonging to a *different*, fully-secured organization,
- sets an arbitrary `after` SHA.

`PushHandler` will look up the real stack by `repository.full_name` and call `stack.sync_github(expected_head_sha: ...)`, causing GitHub sync/deploy machinery to act on a repository the attacker never proved control of, entirely bypassing the intended per-organization HMAC protection. This is an unauthorized-deploy / cross-repository-write primitive achievable purely by crafting an HTTP request to the public `/webhooks` endpoint, with no session, `ApiClient` token, or GitHub credentials required.

### Likelihood Explanation
Requires: (1) the deployment to run in multi-org mode, and (2) at least one configured org to have a blank `webhook_secret` — both are officially supported/documented configurations, not a misuse of the engine outside its documented mounting. Given the docs explicitly mark `webhook_secret` as optional per organization, this is a realistic operational configuration, especially for lower-trust/test orgs in an otherwise multi-tenant Shipit installation. No credentials, session, or write access are needed to exploit it — only knowledge of the weakly-configured org's login.

### Recommendation
Bind the verified organization to the repository being acted upon: after selecting `github_app` via `repository_owner`, require that `repository_owner` matches the owner segment of `repository.full_name` before dispatching to handlers, and/or refuse `verify_webhook_signature` success paths (`return true unless webhook_secret`) when the engine is running in multi-organization mode, forcing every configured org to require a secret.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two orgs: `TrustedOrg` (has `webhook_secret` set, owns tracked stack `TrustedOrg/app`) and `WeakOrg` (no `webhook_secret`, per documented optional config).
2. POST to `/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "WeakOrg" }, "full_name": "TrustedOrg/app" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "WeakOrg")`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`) regardless of the bogus signature.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("TrustedOrg/app")` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `TrustedOrg`'s stack — an unauthorized action on a repository never authenticated by its own secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
