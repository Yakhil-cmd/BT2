### Title
Webhook signature verification is scoped to an attacker-supplied organization while the event is processed against an unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` used to validate the inbound HMAC based on `repository_owner`, a value parsed straight out of the untrusted JSON body, while the actual event handlers key off a different field of that same untrusted body (`repository.full_name`) to decide which `Stack`/`Repository` to act on. The two values are never checked for consistency, so an attacker can select a signature-verification organization that suits them (in particular, one with no `webhook_secret` configured, which the docs themselves show as a normal/default state) while pointing the operative `repository.full_name` at a completely different, unrelated, real repository/stack.

### Finding Description
`verify_signature` derives the verifying organization purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-controlled JSON fields, read before any signature has been confirmed. `Shipit.github(organization: repository_owner)` returns the `GithubApp` for that org and `verify_webhook_signature` is called against it: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the selected organization has no `webhook_secret` configured, signature verification is bypassed entirely and the request is treated as authenticated. The setup documentation itself shows `webhook_secret: # nil` as a normal per-organization configuration value in a multi-org setup: [4](#0-3) 

Meanwhile, once `verify_signature` passes, the actual event handlers never re-derive or re-check the organization — they locate the target `Stack`/`Repository` solely from `payload.dig('repository', 'full_name')`: [5](#0-4) 

This is used identically across `PushHandler` and every `PullRequest::*Handler` (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `edited_handler.rb`), all of which resolve the acted-upon repository via `params.repository.full_name`: [6](#0-5) [7](#0-6) 

Because `repository.owner.login`/`organization.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the repository acted upon) are independent, unrelated fields of the same attacker-supplied JSON body, nothing enforces `organization_verified(payload) == owner_of(payload.repository.full_name)`. An attacker who knows (a) the name of any GitHub organization configured on the Shipit instance that lacks a `webhook_secret`, and (b) the `owner/repo` full name of any real tracked repository (public information), can craft a payload where the `repository.owner`/`organization.login` matches the unsecured org (satisfying `verify_signature` trivially) while `repository.full_name` names the real, tracked repository under a different, properly secured organization.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written," matching the report's bug class (a check that should gate on the full/correct amount but instead gates on a lesser, attacker-influenced value). Concretely, an unauthenticated external attacker can forge:
- `push` events to make `PushHandler` enqueue `GithubSyncJob` with an attacker-chosen `after` SHA against a real stack's branch.
- `pull_request` `opened`/`labeled` events to make `ReviewStackAdapter.find_or_create!` provision a review stack for an attacker-chosen PR number/branch on a real repository, or `closed`/`unlabeled` events to archive an existing review stack.

Because review-stack provisioning executes the repository's `shipit.yml` provisioning steps, this can result in unauthorized deploy/provisioning actions being triggered on real, tracked repositories by a party who never had valid GitHub webhook credentials for that repository's organization — an unauthorized-deploy-class impact.

### Likelihood Explanation
Exploitability requires only (1) that the multi-org Shipit deployment includes at least one configured GitHub organization without a `webhook_secret` — a state the project's own documentation and dummy config present as a supported default — and (2) knowledge of a real tracked repository's `owner/name`, which is public GitHub information. No GitHub credentials, API tokens, or prior repository access are required; the attacker only needs to `POST` a crafted JSON body to the public `/webhooks` endpoint with a `X-Hub-Signature` header value that is simply ignored once the unsecured org's `webhook_secret` is nil.

### Recommendation
Bind signature verification to the same repository that will actually be acted upon: derive the verifying organization from the same authoritative field that handlers use (`repository.full_name`'s owner segment) rather than a separately-parsed `repository.owner.login`/`organization.login`, and require `Shipit.github(organization:)` to reject (422) rather than silently succeed when `webhook_secret` is unset for an organization that has one or more registered repositories/stacks. Additionally, handlers should verify that the resolved `Repository`'s organization matches the organization whose secret validated the request before taking action.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `OrgUnsecured` (no `webhook_secret`, as shown valid in `test/dummy/config/secrets_double_github_app.yml`) and `OrgSecured/real-repo` (a real tracked stack, secret unknown to attacker).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: pull_request
X-Hub-Signature: sha1=anything

{
  "action": "opened",
  "number": 1,
  "pull_request": { ... "head": {"sha": "...", "ref": "..."} ... },
  "repository": { "owner": {"login": "OrgUnsecured"}, "full_name": "OrgSecured/real-repo" },
  "organization": {"login": "OrgUnsecured"},
  "sender": {"login": "attacker"}
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgUnsecured")`; since that org's `webhook_secret` is nil, `verify_webhook_signature` returns `true` unconditionally, regardless of the bogus `X-Hub-Signature`.
4. `Shipit::Webhooks.for_event('pull_request').each { |handler| handler.call(params) }` runs `PullRequest::OpenedHandler`, which resolves the repository via `params.repository.full_name` ("OrgSecured/real-repo") and calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, provisioning a review stack for `OrgSecured/real-repo` — even though the attacker never authenticated against `OrgSecured`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
