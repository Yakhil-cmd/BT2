### Title
Any address paid by a state-changing AA can be a malicious secondary AA that force-reverts the entire primary transaction, allowing recipients to block liquidation/settlement processes - (File: aa_composer.js)

### Summary
This is the same bug class as Sherlock H-8: a state-changing operation (e.g. debt repayment, vault settlement, liquidation) sends funds to an address; if that address's owner can force the transfer to fail, they can block the entire state-changing operation, including any accompanying liquidation/penalty logic. In ocore, an AA that pays out funds to any address as part of a critical process (e.g. a lending/vault protocol's `settle()` or `liquidate()` bounce/payout logic) is vulnerable if the recipient address is itself an AA, because that recipient AA is automatically invoked as a "secondary trigger", and if it deliberately bounces, the **entire primary trigger chain, including all its state changes and payments, is rolled back**.

### Finding Description
When a primary AA sends a payment message whose output address is another AA, `handleSecondaryTriggers()` in `aa_composer.js` automatically invokes that recipient AA as a secondary trigger via `handleTrigger()` [1](#0-0) . If the secondary AA bounces (returns an error), the callback in `async.eachSeries` receives that error and calls `revert()` on the *entire primary chain*: `return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});` [2](#0-1) .

The `revert()` function then rolls back all state variables, balances and previously composed response units for the whole primary trigger (`ROLLBACK TO SAVEPOINT initial_balances`), and finally calls `bounce()` on the primary trigger itself: [3](#0-2) .

This means an attacker who controls (or deploys) the recipient address of any outbound payment from a lending/vault-style AA (for example, a debt-repayment refund, a liquidation payout, or a collateral return sent to `trigger.address`/`trigger.initial_address`) can make that address an AA whose logic unconditionally calls `bounce(...)` whenever it is triggered by that specific payment. Since receiving an output at an AA address always triggers a secondary AA execution (there is no way for the sending AA to "push" funds without invoking the recipient's code, analogous to a native ETH transfer invoking a fallback function in the reported bug), the attacker fully controls whether the settlement/liquidation succeeds or is entirely reverted, exactly as in the reported Solidity vulnerability where the vault owner could revert a native ETH refund to block `VaultAccount.repayAccountPrimeDebtAtSettlement`.

The existing test `chain of AAs` in `test/aa_composer.test.js` demonstrates the normal (non-malicious) propagation of secondary triggers and shared state across a payment chain [4](#0-3) , and `calling a remote function that fails` shows a secondary/remote AA call intentionally bouncing and the parent's evaluation being aborted with the propagated error [5](#0-4) , confirming that bounce errors from any address invoked in the payment/call chain currently propagate to abort the whole primary operation.

### Impact Explanation
Any ocore-based DeFi AA (lending, vault, options, futures, order-book, payment-channel-style protocols, several of which exist in this codebase's sample AAs such as `futures_contract.oscript`, `option_contract.oscript`, `order_book_exchange.oscript`) that pays funds back to `trigger.address` or `trigger.initial_address` as part of a mandatory, time-sensitive state transition (loan repayment, liquidation, margin call, closing of a payment channel) is exposed: if the borrower/counterparty deploys an AA at their receiving address that always bounces on that specific payment, the entire settlement/liquidation trigger reverts. This:
- Permanently prevents undercollateralized positions from being liquidated (funds freezing / bad debt accrual, analogous to the original report).
- Lets a user deterministically block a protocol operation they don't like (e.g. a forced channel closure or liquidation) as long as they control the recipient address, causing denial of a critical AA function and potential loss of funds for the protocol/other counterparty.

### Likelihood Explanation
High for any protocol AA that (a) is triggered directly by an untrusted address (borrower/counterparty), or (b) pays out to an address supplied/controlled by an untrusted party as part of a mandatory settlement flow. Deploying an "always-bounce" AA at a chosen address costs only the gas/bytes of AA deployment and requires no special privilege — any unprivileged trigger sender can do this, matching the "vault liquidations run by any caller / recipient controls own address" pattern from the original report.

### Recommendation
Protocol AAs performing critical, must-succeed settlement/liquidation logic should avoid making the success of that logic depend on a downstream payment to a potentially adversarial recipient AA succeeding. Options:
- Perform state changes (marking debt/position settled, updating balances) in a `state`/`var` update *before or independent of* the payment message, and design fallback accounting (e.g., an internal ledger the recipient can withdraw from later) so that a bounce in the payment leg does not roll back the settlement state.
- Where possible, use `bounce_fees` and defensive design so secondary-trigger failures don't propagate a `revert()` of the whole primary chain for critical liquidation paths — e.g., split payout into a separate trigger/AA call decoupled from the liquidation state transition, similar to Notional's fix of removing transfers from the settlement step entirely.

### Proof of Concept
1. Attacker deploys `evil_aa` defined as an AA whose only logic is `bounce('never accept payouts')` regardless of trigger contents.
2. Attacker interacts with a lending/vault protocol AA (e.g. one modeled like the sample AAs in this repo) using `evil_aa` as their `trigger.address`, opening a loan/position.
3. When the position becomes eligible for liquidation/settlement and anyone (a liquidator, or the protocol's own maturity-triggered flow) posts a trigger causing the protocol AA to send the collateral-return/refund payment message with `outputs: [{address: trigger.initial_address, amount: ...}]` targeting `evil_aa`,
4. `handleSecondaryTriggers()` invokes `evil_aa` as a secondary trigger, which immediately bounces [6](#0-5) .
5. The `async.eachSeries` callback receives this bounce error and calls `revert({message: "one of secondary AAs bounced with error: ", ...})` [2](#0-1) , which rolls back the whole liquidation/settlement trigger via `ROLLBACK TO SAVEPOINT initial_balances` and re-bounces the primary trigger [3](#0-2) .
6. The position remains un-liquidated indefinitely; the attacker can repeat this for every liquidation attempt, at negligible cost (only the bounce fee of the primary trigger, refunded to no one but consumed as protocol overhead), permanently blocking liquidation of their own undercollateralized position.
