### Title
Webhook signature check authenticates the wrong payload field, allowing repository/stack impersonation via `repository.owner.login` vs `repository.full_name` mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (via `repository_owner`), but the event handlers (e.g. `PushHandler`) act on `repository.full_name` (via `Handler#repository_name`) to resolve the `Repository`/`Stack` that gets mutated. These two payload fields are never checked for consistency.

### Finding Description
The webhook signature is computed over the entire raw request body using the secret belonging to the organization derived from `repository.owner.login` (or `organization.login` fallback): [1](#0-0) [2](#0-1) 

Verification itself is delegated to `GithubApp#verify_webhook_signature`, which returns `true` unconditionally whenever no `webhook_secret` is configured for the resolved organization: [3](#0-2) 

Once the request passes (or is skipped), `Shipit::Webhooks.for_event(event)` handlers process the *entire* raw JSON payload, and resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, a field completely independent from the one used to select the verifying secret: [4](#0-3) [5](#0-4) [6](#0-5) 

This is the same class of bug as the analog report: a binding is verified over one identifier (`repository.owner.login`, used to pick the authenticating organization/secret) while the effectful action is keyed off a different, unauthenticated identifier (`repository.full_name`, used to pick the `Stack` that is synced). Nothing in `verify_signature` or in `Handler#repository_name` cross-checks that `full_name`'s owner matches the authenticated `repository_owner`.

The most direct way this manifests concretely: if any organization configured in `Shipit.github_apps` (multi-org installs are supported, see `Shipit.github(organization:)`) has a blank/nil `webhook_secret` — a supported, documented configuration state shown in `config/secrets.development.shopify.yml`'s `webhook_secret: # nil` and in `docs/setup.md` — then `verify_webhook_signature` short-circuits to `true` for *any* unsigned request claiming that organization as `repository.owner.login`, regardless of `X-Hub-Signature`. An unauthenticated caller (the `WebhooksController` is a public, non-session, non-token endpoint: `skip_before_action :verify_authenticity_token`) can then set `repository.owner.login` to the unsecured organization while setting `repository.full_name` to point at any other stack's repository (belonging to an organization that *does* have a secret configured, i.e. a real, protected repo). The handler dispatch never re-validates that the two fields agree, so events like `push` will resolve and mutate the *real* target stack (e.g. trigger `stack.sync_github(expected_head_sha: ...)`) even though the authenticating organization has nothing to do with that stack.

### Impact Explanation
This crosses the "payload field acted on but never covered by the verified signature" binding described in the prompt: the equality that should hold is `authenticated(repository.owner.login) == acted_on(repository.full_name)`, and it is not enforced anywhere in `WebhooksController` or `Handler`. Where it is exploitable (an org with no `webhook_secret` configured), an unauthenticated party gains the ability to trigger GitHub-sync/state-changing webhook events against arbitrary stacks that belong to unrelated, secured organizations — an authentication-boundary bypass reachable without any Shipit session, `ApiClient` token, or repository write access, satisfying the High-impact bar ("escalation into authorization" / cross-organization state manipulation via an unauthenticated read/write of stack state).

### Likelihood Explanation
Exploitability is fully gated on deployment configuration: it requires the Shipit instance to have at least one organization entry in `Shipit.github_apps` with a blank `webhook_secret`, which is an explicitly supported and documented state (shown in the shipped example/dev config and `docs/setup.md`) rather than a code defect that manifests unconditionally. Whether any given production deployment has such an unsecured organization entry cannot be determined from the engine code alone — it depends on the host's configuration, which the rules direct me to treat with caution ("Reject analogs that depend on the host application not mounting the engine as documented"). I was not able to fully confirm from `docs/setup.md`/`template.rb` whether an empty `webhook_secret` is presented as a normal/supported option versus a discouraged placeholder, which limits my confidence in this being a pure code-level vulnerability versus a configuration risk.

### Recommendation
- Cross-validate that `repository.full_name`'s owner segment matches the `repository_owner` used for signature verification before dispatching to handlers, rather than trusting two independently-derived payload fields.
- Do not treat a missing `webhook_secret` as "verification passed"; instead, either require a secret for every configured organization or explicitly reject/flag unsigned requests for organizations without one, rather than silently returning `true` in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations: `unsecured-org` (no `webhook_secret`) and `secured-org` (has a `webhook_secret`, owns a real Stack).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and a body where `repository.owner.login = "unsecured-org"` but `repository.full_name = "secured-org/real-repo"`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — see `lib/shipit/github_app.rb` lines 76-83.
4. `PushHandler#process` then resolves `Repository.from_github_repo_name("secured-org/real-repo")` via `repository.full_name` and calls `stack.sync_github(expected_head_sha: ...)` on the real, secured stack — see `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38 and `app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17 — despite the request never being authenticated against `secured-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
