## Title
Global read-any-stack CCMenu token via unscoped `ApiClient` creation and unenforced `stack_id` binding - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` for the current user with `permissions: %w[read:stack]` but never sets `stack_id`, so the resulting `authentication_token` is not bound to the stack whose settings page generated it. Compounding this, `Shipit::Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` directly, never going through the `stacks` helper in `Shipit::Api::BaseController` that would otherwise restrict lookups to `current_api_client.stack_id`. As a result, any authenticated Shipit user's CCMenu token can read the deploy status of every stack on the instance.

### Finding Description
The claimed binding is: `client.stack_id == stack.id` (the stack for which the CCMenu URL was generated). This is never established, and even if it were, it would not be enforced.

- `CCMenuUrlController#client` builds the client with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [1](#0-0)  — `stack_id` is absent from both the lookup attributes and the `create_with` defaults, so the client's `stack_id` column is `nil` on creation and is never revisited on subsequent calls (`find_or_create_by!` will find the same client, still with `stack_id: nil`, for a different stack).
- `ApiClient#authenticate` simply resolves the record by verified id, with no scope check [2](#0-1) .
- `Shipit::Api::BaseController#stacks` is the intended enforcement point: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [3](#0-2) . When `stack_id` is nil, this falls back to `Stack.all` — already a bypass even if the base controller were used.
- Critically, `Shipit::Api::CCMenuController#stack` does not use `stacks.from_param!` at all; it uses `Stack.from_param!(params[:stack_id])` directly [4](#0-3) , bypassing the `stacks` scoping mechanism entirely regardless of `stack_id`. Only `require_permission :read, :stack` gates access [5](#0-4) , which only checks the permissions array (`read:stack`), never the target stack identity.

Exploit flow: an attacker (any Shipit user, unprivileged) visits `GET /stacks/:owner/:repo/:branch/cc_menu_url` for a repo they can view, obtaining a token via `fetch`. They then call `GET /api/stacks/<any-other-repo>/<any-branch>/cc_menu.xml?token=<token>`. `authenticate_api_client` in `CCMenuController` accepts the token via `ApiClient.authenticate(params[:token])` [6](#0-5) , permission check passes (`read:stack` is present), and `stack` resolves the unrelated stack by param with no `stack_id` restriction, returning its full deploy/build status.

No existing guard prevents this: `require_permission!` only checks permission names, not stack identity [7](#0-6) ; the `stacks` scoping helper that would apply `stack_id` restriction is bypassed in `CCMenuController`.

### Impact Explanation
Any user able to reach one stack's settings page (which, per `StacksController#settings`, requires only `load_stack` — no stack-specific authorization beyond whatever gates `current_user` reaching `settings` at all) can obtain a token that reads the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) of **every** stack on the Shipit instance, including private/internal ones the attacker has no legitimate access to. This is repeatable indefinitely (the token doesn't expire) and scales across all stacks/tenants on the instance — matching the "High: unauthenticated/unauthorized read of stack state" category, since a token scoped by design to one stack functions as a blanket read-any-stack credential.

### Likelihood Explanation
Preconditions are trivial: the attacker needs only a Shipit session and access to any single stack's settings/CCMenu URL page (a very low bar — a legitimate contributor to any one project). No secrets, GitHub credentials, or elevated roles are required. The attack is a single unauthenticated (session-less) HTTP GET with the leaked token as a query parameter, fully repeatable against arbitrary stacks.

### Recommendation
Set `stack_id: stack.id` when creating/looking up the `ApiClient` in `CCMenuUrlController#client` (scope `find_or_create_by!` on `stack` as well, or mint a distinct token per stack), and enforce the binding server-side by making `Shipit::Api::CCMenuController#stack` use the `stacks` scoping helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!` directly, so a client whose `stack_id` is set cannot resolve any other stack.

### Proof of Concept
Minitest plan (`test/controllers/ccmenu_url_controller_test.rb` + `test/controllers/api/ccmenu_controller_test.rb` style):
1. Create two stacks, `stack_a` and `stack_b`, and a signed-in `current_user`.
2. `GET /stacks/:stack_a.owner/:stack_a.repo/:stack_a.branch/cc_menu_url` as `current_user`; extract `token` from the JSON response's `ccmenu_url`.
3. Assert (binding check, should fail today): `ApiClient.find_by(creator: current_user, name: 'CCMenu Client').stack_id == stack_a.id` — currently `nil != stack_a.id`.
4. `GET /api/stacks/#{stack_b.to_param}/cc_menu.xml?token=#{token}` (no session, no Authorization header).
5. Assert `response.status == 200` and the XML body's `Project[name]` equals `stack_b.to_param`, proving a token minted for `stack_a` reads `stack_b`'s status. [8](#0-7) [9](#0-8)
