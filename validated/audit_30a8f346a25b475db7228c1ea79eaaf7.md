### Title
Full plaintext device messages are unconditionally written to console log, exposing pairing secrets, private textcoin mnemonics, contract offers, and other sensitive payloads - ([File: device.js])

### Summary
`decryptPackage()` in `device.js` unconditionally logs the entire decrypted content of every device message with `console.log("decrypted: "+decrypted_message)`, before any validation of the message subject or contents takes place. This is directly analogous to CVE-2024-9621 (Quarkus CXF), where SOAP payloads containing secrets were written to logs despite configuration intended to hide them — here, ocore's end-to-end-encrypted device-message channel is meant to keep its payload confidential, yet the decrypted plaintext is dumped to the application log unconditionally.

### Finding Description
Every device message a wallet/hub node receives passes through `decryptPackage()`: [1](#0-0) 
which decrypts the AES-GCM package and then does:
```
var decrypted_message = decrypted_message_buf.toString("utf8");
console.log("decrypted: "+decrypted_message);
``` [2](#0-1) 

This happens before the JSON is parsed or its `subject` is checked, so it applies to **all** message types that flow over the device-message channel, including:
- `pairing` messages containing `pairing_secret`/`reverse_pairing_secret` used to authorize a new correspondent [3](#0-2) 
- `sign` requests carrying `assocPrivatePayloads` (private-asset payloads) [4](#0-3) 
- `private_payments` messages carrying full private-asset payment chains, including blinding factors and amounts (`arrChains`) [5](#0-4) 
- `arbiter_dispute_request` messages containing another layer of encrypted contract content that is itself decrypted (and thus logged again) via `device.decryptPackage(body.encrypted_contract)` [6](#0-5) 
- Contract acceptance responses embedding the `pairing_secret` in `my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret` [7](#0-6) 

Because `pairing_secret` is the bearer credential that lets an unknown device add itself as a correspondent (`handlePairingMessage` accepts any device presenting a valid, unexpired `pairing_secret`) [8](#0-7) , and because private-asset chains carry the exact `blinding`/`amount`/`address` triples needed to construct a `spend_proof` and validate/spend an output [9](#0-8) , leaking this decrypted plaintext into logs is equivalent to leaking a password/secret that the encryption layer was explicitly designed to hide from anyone but the intended recipient.

Additional smaller log leaks compound the issue: the sender-side `createEncryptedPackage()` never logs plaintext (only `shared_secret.length`) [10](#0-9) , but the receiving side logs the full plaintext for every message, symmetrically defeating the encryption's confidentiality guarantee on the recipient node. `validatePrivatePayment()` in `indivisible_asset.js` separately logs the full spend-proof preimage (`asset, unit, message_index, output_index, address, amount, blinding`) via `console.log("validation spend proof: "+JSON.stringify({...}))` [11](#0-10) , and `validateAndSavePrivatePaymentChain()` logs the entire private-element chain including blinding factors via `console.log("saving private chain "+JSON.stringify(arrPrivateElements))` [12](#0-11) .

### Impact Explanation
Any node that stores or ships its process/application logs (a common practice for full nodes, hubs, or self-hosted headless wallets) persistently exposes:
- Pairing secrets for any correspondent that paired with, or was paired to, that device — enabling an attacker with log access to impersonate a correspondent device and receive messages/payments intended for the legitimate device address.
- Full private-asset payment chain data (`blinding`, `amount`, `address`, `output_hash`) for every private (indivisible/divisible-private) payment routed through or to the node, which is exactly the information required to reconstruct spend proofs and double-spend or front-run privacy-asset outputs before the legitimate recipient claims them.
- Signing requests bundled with `assocPrivatePayloads`, letting a log reader observe transaction details that were meant to be confidential end-to-end.

This satisfies the "concrete unauthorized spending ... or freezing" bar: an attacker with log read access (e.g., a compromised logging pipeline, misconfigured log aggregator, or shared hosting) gains the same capability as the intended message recipient, without needing to compromise the private key material itself.

### Likelihood Explanation
Exploitation requires the attacker to have read access to application logs (analogous to the original advisory's condition that "the attacker must have access to the application log"). This is a realistic condition for centrally-hosted hubs, bots, or wallets running with verbose/console logging enabled in production (a common default in Node.js deployments where `console.log` is piped to a file or a log-aggregation service). No special "SOAP logging" style opt-in is needed here — the log statement is unconditional in `decryptPackage`, which runs on the hot path of every incoming device message. This raises the practical likelihood relative to the original CXF bug, which required deliberate special configuration.

### Recommendation
- Remove or gate behind an explicit debug flag (disabled by default) the `console.log("decrypted: "+decrypted_message)` statement in `device.js`'s `decryptPackage`.
- Redact or omit sensitive fields (`pairing_secret`, `blinding`, `amount`, `private_payloads`, `assocPrivatePayloads`) before logging pairing, private-payment, and signing-related messages in `device.js`, `wallet.js`, `wallet_general.js`, `arbiter_contract.js`, and `indivisible_asset.js`.
- Audit all `console.log(JSON.stringify(...))` calls that touch device-message bodies or private payment chains and replace them with structured, secret-scrubbing loggers.

### Proof of Concept
1. Run an ocore-based hub/wallet node with default logging (stdout captured to a file, as is typical in production deployments).
2. Have a correspondent send a `pairing` message, a `private_payments` message (asset transfer with `blinding`/`amount`), or a `sign` request with `assocPrivatePayloads` to the node.
3. Observe that `device.js`'s `decryptPackage` prints the full decrypted JSON body — including `pairing_secret`, `blinding`, `amount`, and private payload contents — to the console/log file via the line `console.log("decrypted: "+decrypted_message)` [13](#0-12) .
4. An attacker who obtains read access to that log file can extract the pairing secret to impersonate the correspondent, or extract the private-payment blinding/amount data to reconstruct spend proofs for the private asset output, matching the `validateSpendProof`/`spend_proof` computation in `indivisible_asset.js` [14](#0-13) .
