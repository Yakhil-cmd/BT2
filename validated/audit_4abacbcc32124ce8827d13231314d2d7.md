Confirmed: `create!` performs no independent check of `review_stacks_enabled`; it relies entirely on `provision?` gating in the handler. This confirms the vulnerability path is exactly as described.### Title
`OpenedHandler#provision?` fails to gate `prevent_with_label`/`allow_with_label` behavior on `review_stacks_enabled` due to Ruby operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends `review_stacks_enabled` to gate all review-stack auto-provisioning, but due to `&&`/`||` operator precedence, `review_stacks_enabled` is only ANDed with the `allow_all?` clause. The `allow_with_label` and `prevent_with_label` clauses are evaluated unconditionally, so an unprivileged fork PR author can trigger `ReviewStack` creation on a repository whose operator explicitly disabled review stacks.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold whenever `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter#create!` runs for that repository. Tracing the code: [1](#0-0) 

```ruby
def process
  return unless respond_to_pull_request_opened?
  Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter
    .new(params, scope: repository.review_stacks).find_or_create!
end
...
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

In Ruby, `&&` has higher precedence than `||`, so this expression parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is scoped only to the first disjunct. The second and third disjuncts (the `allow_with_label` and `prevent_with_label` behaviors) evaluate independently of `review_stacks_enabled`. `ReviewStackAdapter#create!` itself performs no independent check of `review_stacks_enabled`: [2](#0-1) [3](#0-2) 

so the handler's `provision?` gate is the sole enforcement point, and it is broken.

Attacker request: an unprivileged GitHub user opens a pull request (`action: "opened"` webhook) against a repository configured with `review_stacks_enabled = false`, `provisioning_behavior = "prevent_with_label"`, `provisioning_label_name = "deploy-preview"`, and adds no label. `pull_request_has_provisioning_label?` is `false`, so the third disjunct `(prevent_with_label? && !has_label?)` is `true`, making `provision?` return `true` regardless of `review_stacks_enabled == false`. `process` then calls `ReviewStackAdapter#create!`, which creates a `Shipit::Stack` (via `scope.create!`), attaches the PR, and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` — leading to provisioning/deploy activity for a repository that opted out of review stacks entirely.

None of the existing guards intercept this: `respond_to_pull_request_opened?` only checks `params.action == "opened"`; `ExplicitParameters` schema validation only shapes the payload, it does not enforce business logic; and no model validation on `Repository` or `Stack` checks `review_stacks_enabled` at creation time. The existing test suite covers `prevent_with_label` with the default `provisioning_enabled: true` (see `test/models/.../opened_handler_test.rb` line 159-172, `configure_provisioning_behavior` defaults `provisioning_enabled: true`) and never exercises `provisioning_enabled: false` combined with `prevent_with_label`, so this gap is untested. The identical logic bug also exists verbatim in `unarchive?`/`archive?`-adjacent gating in `ReopenedHandler#unarchive?`, which has the same `&&`/`||` precedence issue: [6](#0-5) 

### Impact Explanation
An unauthenticated (from Shipit's perspective — this is only a webhook payload, not proven to originate from GitHub) or unprivileged GitHub fork author can force `Shipit::Stack`/`Shipit::ReviewStack` creation and enqueue it for provisioning (`Shipit::ReviewStackProvisioningQueue.add`) on a target repository whose operator explicitly disabled review stacks (`review_stacks_enabled = false`). This causes unauthorized resource provisioning and deploy pipeline activity — an unauthorized deploy path — for a repository that opted out, matching the Critical category of "unauthorized deploy... via a payload." The blast radius is scoped to repositories configured with `provisioning_behavior = prevent_with_label` (or `allow_with_label` with the label present) while `review_stacks_enabled = false`; it is repeatable per PR/repository matching that configuration.

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled = false` + `provisioning_behavior = prevent_with_label` (or `allow_with_label` with label applied), which is a plausible admin misconfiguration/intermediate state (e.g., an operator disables review stacks but leaves `provisioning_behavior` set from before). No attacker secrets are needed beyond the ability to open a PR (or send a crafted `opened` webhook payload, subject to whatever webhook signature verification gates the endpoint — not traced in this pass, but the handler-internal logic bug exists independent of that). The bug is deterministic and trivially reproducible once the repository is in the vulnerable configuration state.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `ReopenedHandler#unarchive?` which has the identical precedence bug.

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false even for prevent_with_label without the label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before fix, `Shipit::Stack.count` changes (violating `repository.review_stacks_enabled == false` implying no stack creation); after applying the recommended fix, the count stays unchanged, restoring the binding.
