### Title
Webhook signature check binds trust to the payload's `repository.owner.login`, but downstream handlers act on the independently attacker-controlled `repository.full_name` field, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a webhook's HMAC signature against using `repository_owner`, a value read out of the same untrusted JSON body being verified [1](#0-0) [2](#0-1) . Once the signature check passes, every registered `Handler` decides which `Repository`/`Stack` to mutate using a *different* field of the same JSON body, `repository.full_name`, via `Repository.from_github_repo_name(repository_name)` [3](#0-2) . Because HMAC-SHA1 verification with `webhook_secret` (`verify_webhook_signature`) is a symmetric-key check over the raw bytes [4](#0-3) , whoever knows *one* organization's `webhook_secret` can forge an entirely arbitrary payload, including a `repository.full_name` naming a completely different organization's repository, while keeping `repository.owner.login`/`organization.login` equal to their own org so the signature check passes with a secret they legitimately hold.

### Finding Description
This is the direct analog of the reported `transferERC20ToTreasury` bug: the report's flaw was checking a token's *identity* via one address field (`tokenAddress != assetTokenAddress`) while the actual balance-moving operation could be reached through another, equally valid address for the same underlying asset — i.e., the field verified and the field acted upon were not provably the same entity.

Here the same class of flaw appears in the webhook trust boundary:
- The field used to pick the verification secret is `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')` [2](#0-1) .
- The field used to determine which `Stack`/`Repository` is actually acted on by handlers is `repository.full_name`, read via `Handler#repository_name` [5](#0-4) .
- Both fields are read out of the *same* attacker-supplied `request.raw_post` JSON, and nothing in `verify_signature` cross-checks that `repository.full_name`'s owner segment matches `repository_owner` used to select the HMAC key [6](#0-5) .
- `verify_webhook_signature` is a plain symmetric HMAC comparison (`OpenSSL::HMAC.hexdigest` + `secure_compare`) over the full raw body [4](#0-3) , meaning anyone holding a given organization's `webhook_secret` can sign *any* byte sequence, not just legitimate GitHub-generated payloads for that org.

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository whose Stack is mutated`

But the engine only enforces:
`organization named in repository.owner.login (used to pick the secret) == organization whose secret validated the signature`

and separately, unconditionally:
`repository named in repository.full_name (chosen freely by whoever forged the body) == repository whose Stack receives the event`

Since `repository.owner.login` and `repository.full_name` are two independent JSON keys within the same attacker-controlled body, an attacker who legitimately possesses (or has compromised) organization A's `webhook_secret` — e.g. a member with admin access to the GitHub App/webhook config for org A, but with no privileges on org B — can set `repository.owner.login`/`organization.login` to `"OrgA"` (so the correct secret is selected and validation passes) while setting `repository.full_name` to `"OrgB/target-repo"` (so the event is dispatched against org B's `Stack`).

### Impact Explanation
This crosses an authentication boundary the engine intends to enforce: only the organization whose webhook secret matches should be able to affect that organization's stacks. By decoupling the "authenticated organization" field from the "affected repository" field, an attacker holding a single org's webhook secret can forge `push`, `status`, `check_suite`, `check_run`, or `pull_request` events against any other organization's `Stack` configured on the same Shipit instance. Depending on the target stack's configuration (e.g., `continuous_deployment: true`, or CI-status-driven deploy gating), a forged `push`/`status` event can enqueue `GithubSyncJob`/`RefreshCheckRunsJob` work and influence deployability/merge state on a repository the attacker has no legitimate relationship with — a cross-repository/cross-organization write and a step toward an unauthorized deploy, matching the Critical/High impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Low-to-moderate: it requires the attacker to hold (or have compromised) the `webhook_secret` for at least one organization already configured in the multi-tenant Shipit deployment — analogous to the original report's "malicious/compromised admin" precondition. Given that webhook secrets are typically held by whoever configures the GitHub App/webhook for an org (not by Shipit itself as a global secret), a single rogue or compromised org admin is sufficient; no Shipit session, `ApiClient` token, or GitHub App private key is required, since HMAC verification only checks the shared secret, not GitHub App identity/signature.

### Recommendation
Do not select the HMAC verification key from an attacker-controlled field that is decoupled from the field used to resolve the mutated resource. Concretely:
- After signature verification succeeds for organization `O` (chosen via `repository_owner`), require that the `repository.full_name`'s owner segment (and/or `organization.login`) used by `Handler#repository_name`/`stacks` also equals `O`, rejecting (422) any payload where they differ.
- Alternatively, resolve the webhook secret/org strictly from `repository.full_name`'s owner segment (the same field the handlers use to select the `Repository`), so there is only one canonical "owning organization" derived per request, instead of two independently-read fields that can diverge.

### Proof of Concept
1. Assume Shipit is configured for two organizations, `OrgA` and `OrgB`, each with its own GitHub App installation and `webhook_secret` (per `config/secrets.yml`, e.g. as shown in `docs/setup.md`).
2. Attacker legitimately holds `OrgA`'s `webhook_secret` (e.g., is an admin of OrgA's GitHub App configuration) but has no access to `OrgB`.
3. Attacker crafts a JSON body for a `push` event:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "after": "<arbitrary sha registered in OrgB's stack>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` succeeds because the attacker signed with the correct (OrgA) secret [7](#0-6) .
6. `Shipit::Webhooks.for_event('push')` handlers run and resolve `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")`, acting on `OrgB`'s stack despite the request only having been authenticated for `OrgA` [3](#0-2) .

Note: I could not fully inspect `Shipit.github(organization:)`'s implementation in `lib/shipit.rb` (only partial context was retrievable), so the exact per-organization secret-lookup mechanics are inferred from `docs/setup.md`'s multi-secret example and `GithubOrganizationUnknown` handling in `webhooks_controller.rb`; the core divergence between `repository_owner` (used for signature-key selection) and `repository.full_name` (used for resource resolution) is directly confirmed in code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
