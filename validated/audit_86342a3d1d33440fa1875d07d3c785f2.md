### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret` used to validate the HMAC signature) using `repository.owner.login` (falling back to `organization.login`), while every event `Handler` resolves the actual `Repository`/`Stack` to mutate using a completely different, attacker-controlled field: `repository.full_name`. In Shipit's supported multi-organization configuration, these two identities are never checked for consistency, so a payload can be "authenticated" against one organization's webhook secret while its effects are applied to a different organization's repository.

### Finding Description
The verification step is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

This selects a `GitHubApp` instance keyed by organization name, and its `verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

Shipit explicitly documents and tests a mode where multiple independent GitHub App configs (each with its own `app_id`/`installation_id`/`webhook_secret`) are addressed by organization name: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, the entire raw payload is dispatched to handlers keyed only by the `X-Github-Event` header, with no re-check of which organization/secret was used: [6](#0-5) 

Every handler then resolves the target `Repository`/`Stack` using `repository.full_name`, a field entirely independent from `repository.owner.login`/`organization.login` used for signature selection: [7](#0-6) [8](#0-7) 

The broken equality is:
`organization whose secret authenticated the request (repository.owner.login / organization.login)` **≠** `repository actually written to (repository.full_name)`

Nothing in `verify_signature` or in `Handler#repository_name` enforces that `repository.full_name.split('/').first == repository_owner`.

### Impact Explanation
An attacker who knows (or who exploits) an organization in the multi-org config with no `webhook_secret` set — or who otherwise obtains that org's secret — can craft an arbitrary webhook payload where:
- `repository.owner.login` (or `organization.login`) = the weak/known organization, used only to pass `verify_signature`.
- `repository.full_name` = `victim-org/victim-repo`, an entirely different, properly-secured organization's repository that Shipit tracks.

This is a cross-repository write: the request is "authenticated" for one organization but its side effects (creating `Status` rows via the status handler, triggering `GithubSyncJob`/deploy-eligibility recalculation via the push handler, creating `Team`/`Membership` records via the membership handler, etc.) are applied against a repository/stack belonging to a different, unrelated organization whose secret was never checked. Because commit "deployability" in Shipit is influenced by ingested CI/status webhook data, this can be leveraged to make an otherwise-unreviewed commit appear deployable and to trigger deploy-related jobs for a stack the attacker was never authorized to touch, directly matching the report's "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitation requires: (1) Shipit is configured with multiple GitHub App organizations (a documented, first-class configuration), and (2) at least one configured organization has a blank/unset `webhook_secret`, or the attacker otherwise knows/leaks that organization's secret. Given `webhook_secret: # nil` is shown as the default/example value in the multi-org documentation, misconfiguration of this kind is plausible in real deployments, and the `WebhooksController` endpoint is unauthenticated and internet-reachable by design (it must accept unauthenticated POSTs from GitHub).

### Recommendation
Bind the verified identity to the identity acted upon: after `verify_webhook_signature` succeeds for `repository_owner`, re-derive `repository_owner` from `repository.full_name` as well and reject the request (422) if the two disagree. Do not allow `verify_webhook_signature` to return `true` unconditionally when `webhook_secret` is blank in a multi-org configuration — either require every configured organization to set a `webhook_secret`, or scope handler execution strictly to the organization that was used to compute `repository_owner` in `verify_signature`, never trusting `repository.full_name`'s owner segment independently for routing.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, e.g. `OrgWeak` (no `webhook_secret`) and `VictimOrg` (properly configured, with real tracked stacks), per `docs/setup.md` multi-org format.
2. POST directly to `/webhooks` (no GitHub App relationship required) with:
   - Header `X-Github-Event: status`
   - Body: `{"repository": {"owner": {"login": "OrgWeak"}, "full_name": "VictimOrg/victim-repo"}, "sha": "<victim-commit-sha>", "state": "success", "context": "ci/forged", "description": "forged", "target_url": "http://attacker"}`
3. `verify_signature` calls `Shipit.github(organization: "OrgWeak")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/garbage) `X-Hub-Signature` header — request passes.
4. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`, which resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` and creates/updates a `Status` for the victim commit using attacker-supplied `state`/`context`/`description`, even though the request was never authenticated against `VictimOrg`'s secret.

Note: I could not fully trace the exact `Commit#deployable?`/continuous-delivery gating logic in `app/models/shipit/commit.rb` in this session (a tool-access issue occurred on the final read attempt), so the downstream "forged status → auto-deploy" chain is asserted based on Shipit's documented CI/status-gated deploy model but is not line-by-line verified here. The cross-organization write itself (forged `Status`/sync trigger against a repository never covered by the verified secret) is fully verified against the cited files.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
