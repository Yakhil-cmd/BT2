## Title
Unbounded Private-Payment Chains Persisted to Disk Before Size Validation Enables Storage-Exhaustion DoS - ([File: network.js])

### Summary
`network.handleOnlinePrivatePayment()` writes the full JSON of an attacker-supplied `arrPrivateElements` array into the `unhandled_private_payments` table as soon as light structural checks pass, *before* the heavier chain/asset validation (`privatePayment.validateAndSavePrivatePaymentChain`) ever runs. Like the Undertow flaw where a bare HTTP GET can force multipart content to be parsed and written to disk before the application logic ever inspects it, here an unprivileged private-payment counterparty (or hub-relayed device message) can force the node to persist arbitrarily large/duplicated payloads to disk before any real validation occurs, and the entry only gets validated when `handleSavedPrivatePayments()` later runs.

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` [1](#0-0)  only checks that `arrPrivateElements` is a non-empty array and that the head element's `unit`, `message_index`, `output_index` fields are well-formed: [2](#0-1) 

No limit is enforced on:
- the number of elements in `arrPrivateElements` (chain length),
- the size/nesting of each element's `payload` (`inputs`, `outputs`, `blinding`, etc.), or
- the total serialized size of `JSON.stringify(arrPrivateElements)` before it is inserted into the DB.

When the unit is unknown, not yet handled, or (for light clients) the chain has more than one element, the function immediately calls `savePrivatePayment()`, which persists the raw JSON to the `unhandled_private_payments` table: [3](#0-2) [4](#0-3) 

This is reached from `wallet.handlePrivatePaymentChains()`, which is the handler for the `private_payments` subject of an ordinary device message (reachable by any paired correspondent, i.e., a private-payment counterparty), for each chain in `body.chains` with only shape checks (non-empty strings/objects/arrays), no length or size caps: [5](#0-4) [6](#0-5) 

The actual validation — parsing the chain, checking asset/denomination consistency, verifying spend proofs, and rejecting malformed chains — happens only later in `privatePayment.validateAndSavePrivatePaymentChain()` / `indivisible_asset.parsePrivatePaymentChain()`, which is deferred (`ifWaitingForChain`) precisely in the cases where the row was already written to disk: [7](#0-6) [8](#0-7) 

Unlike unit/joint processing, which enforces `isTooDeeplyNestedOrHasTooManyNodes()` and `constants.MAX_UNIT_LENGTH` before persisting anything (see `validation.js` [9](#0-8) , `constants.js` [10](#0-9) ), the private-payment-chain code path applies none of these guards before the DB write. A malicious or compromised paired device (or a hub simply relaying attacker-controlled `private_payments` messages) can therefore repeatedly submit large/duplicated `chains` bodies, each causing an unbounded DB insert, filling disk space and increasing DB/query load with data that will ultimately fail validation.

### Impact Explanation
Repeated abuse fills the `unhandled_private_payments` table with large, mostly-invalid JSON blobs, consuming disk space and DB I/O on the victim's wallet/hub node. Because the record is only cleaned up after the deferred validation runs (and validation itself must first deserialize and reprocess this same oversized JSON), a moderate stream of such messages can produce a lasting resource-exhaustion condition consistent with CWE-770 — matching the "Denial of Service via premature parsing/storage before validation" class described in the Undertow advisory.

### Likelihood Explanation
Any paired device correspondent (or in the hub scenario, anyone routing `private_payments` messages through a hub the target trusts) can trigger this with a single crafted device message; no special privileges, race conditions, or existing on-chain unit are required beyond normal pairing. The check gate is trivial to satisfy (non-empty array/object/string checks only).

### Recommendation
Before persisting `arrPrivateElements` (or `body.chains`) to the database:
- Enforce a maximum chain length (e.g., similar in spirit to `MAX_MESSAGES_PER_UNIT`/`MAX_PARENTS_PER_UNIT`).
- Enforce a maximum serialized payload size per element and per chain (e.g., bounded by `MAX_UNIT_LENGTH` or a dedicated constant).
- Apply `isTooDeeplyNestedOrHasTooManyNodes()` (already used for units and `hub/deliver` device messages) to each private-payment element/payload before any DB write in `handleOnlinePrivatePayment` and `handlePrivatePaymentChains`.
- Consider deduplicating/rate-limiting `unhandled_private_payments` inserts per peer/device before validation.

### Proof of Concept
1. Pair a malicious device with the victim wallet (or control/compromise a hub that forwards `private_payments` messages).
2. Send a `private_payments` device message whose `body.chains` contains one or many chains, each with an oversized `payload` (very large `inputs`/`outputs` arrays or long `blinding` strings) that still satisfies the shallow shape checks in `handlePrivatePaymentChains`.
3. Observe that `network.handleOnlinePrivatePayment` inserts the full JSON into `unhandled_private_payments` via `savePrivatePayment()` before any chain/asset validation runs.
4. Repeat with many distinct `unit`/`message_index` combinations to bypass the `INSERT IGNORE` de-duplication, causing continual disk/DB growth until validation catches up and rejects the entries — by which time resources have already been consumed.

// arrPrivateElements is ordered in reverse chronological order
function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
