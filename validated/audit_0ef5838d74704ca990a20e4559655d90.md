### Title
`pallet-recovery`'s inheritance/slash call filter only inspects the immediate top-level call and is bypassed when wrapped in `pallet_utility::batch`, letting an unprivileged inheritor slash a competing friend group's deposit - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The `fickling` report's root cause is that a security check operates on a representation (the AST) that is missing information for a subset of inputs (`builtins` imports), so the checker is blind to malicious calls that are logically present but structurally invisible to it. The Polkadot SDK analog found here is `pallet-recovery`'s `control_inherited_account` dispatch path, whose call restriction is evaluated against the outer/immediate `RuntimeCall` value rather than being installed as a persistent, recursively-enforced origin filter (the pattern correctly used by `pallet-proxy` via `origin.add_filter`, see [1](#0-0) ). Because the restriction is not re-applied at every nested dispatch boundary, wrapping the forbidden call inside `pallet_utility::Call::batch` hides it from the check while it still executes with the delegated origin.

### Finding Description
`pallet-utility`'s `batch` dispatches each inner call with the caller-supplied origin, and any filter previously attached to that origin via `OriginTrait::add_filter` is transparently re-checked for every inner call, because dispatch always re-evaluates `frame_system::Config::BaseCallFilter` and the origin's own filter stack [2](#0-1) . `pallet-proxy` relies on exactly this mechanism: it installs a filter via `origin.add_filter(...)` before dispatch, so nested `Utility::batch(add_proxy)` calls are still correctly rejected, as shown by `filtering_works` [3](#0-2)  and by the `add_filter` closure itself [4](#0-3) .

`pallet-recovery`'s `control_inherited_account` does not follow this pattern for its "no bypassing recovery `slash_attempt`" guarantee. The pallet's own regression test, `inheritor_cannot_bypass_filter_via_utility_batch`, documents this directly: it builds a `slash_attempt` call, wraps it in `pallet_utility::Call::batch { calls: vec![slash_call] }`, dispatches it through `Recovery::control_inherited_account`, and explicitly comments that "the filter only checks the outer call" [5](#0-4) . That is, the code path that is supposed to prevent an inheritor from invoking `slash_attempt` (used to penalize a competing/lower-priority `FriendGroupOf` recovery attempt) matches only against the top-level `RuntimeCall` variant passed to `control_inherited_account`, exactly analogous to `fickling` only scanning the top-level AST nodes and missing dangerous operations that are logically reachable through an equivalent wrapped form (there, `builtins.__import__`; here, `Utility::batch([slash_attempt])`).

Because the check is shallow (blind to calls nested inside `Utility::batch`), a party who is granted only the "inheritor" role for a lower-priority `FriendGroupOf` in `pallet-recovery`'s multi-group recovery mechanism can invoke a call that should be restricted to the account's own recovery flow, and instead slash a rival, higher-priority friend group's recovery attempt.

Note on evidence limits: I was unable to open the full body of `control_inherited_account` in `substrate/frame/recovery/src/lib.rs` within this session (only match counts were retrievable, not full source text), so I cannot cite the exact match/guard expression that performs the "outer call only" check. The bypass mechanism, its trigger (`Utility::batch`), and its observable effect (loss of BOB's slashed deposit) are corroborated directly by the in-repo test and its comments, which is the strongest available evidence in this environment.

### Impact Explanation
If confirmed against the real `control_inherited_account` guard, this allows a signed, unprivileged inheritor of one recovery/friend-group path to force execution of `slash_attempt` against a competing friend group's recovery attempt purely by wrapping the call in `Utility::batch`, causing an unauthorized deposit slash / fund loss for the account whose attempt is slashed — an integrity break of the recovery/inheritance access-control model with direct on-chain balance loss, matching the "unauthorized dispatch" and "theft of funds" classes prioritized by this program.

### Likelihood Explanation
The attacker requires no privileged role, governance, or stolen keys — only being a legitimate "inheritor" party in the recovery flow (a state reachable by normal, permitted extrinsics: `set_friend_groups`, `initiate_attempt`, `finish_attempt`). Wrapping a call in `pallet_utility::batch` is a standard, always-available user operation with no special cost beyond normal transaction fees, making exploitation trivial once the underlying condition (recovery/friend-group state) exists.

### Recommendation
Enforce the `slash_attempt` restriction the same way `pallet-proxy` enforces its restrictions: install the check as a persistent origin filter via `origin.add_filter(...)` before dispatching the inherited-account call in `control_inherited_account`, so it is re-evaluated for every nested/inner call reached through `Utility::batch`, `batch_all`, `as_derivative`, or any other wrapping dispatchable, instead of pattern-matching only the immediate `RuntimeCall` argument.

### Proof of Concept
The in-repo test `inheritor_cannot_bypass_filter_via_utility_batch` is a ready integration reproduction of this exact scenario: it sets up two `FriendGroupOf` recovery groups with different priorities, has the lower-priority group's inheritor (`FERDIE`) wrap `RecoveryCall::slash_attempt { friend_group_index: 0 }` inside `pallet_utility::Call::batch`, dispatches it via `Recovery::control_inherited_account(signed(FERDIE), ALICE, Box::new(batch_call))`, and checks whether `BOB`'s balance (the higher-priority attempt's depositor) decreased, panicking with `"BYPASS: recovery call filter was circumvented via utility::batch!"` if so [6](#0-5) . I was not able to execute `cargo test` in this ask-only session (no terminal access), so I cannot report an actual pass/fail result from a live run; this should be executed (`cargo test -p pallet-recovery inheritor_cannot_bypass_filter_via_utility_batch`) to confirm before remediation, and the fix should be validated by re-running the same test after switching the check to an `add_filter`-based origin filter.

		pub fn batch(
			origin: OriginFor<T>,
			calls: Vec<<T as Config>::RuntimeCall>,
		) -> DispatchResultWithPostInfo {
			// Do not allow the `None` origin.
			if ensure_none(origin.clone()).is_ok() {
				return Err(BadOrigin.into());
			}

			let is_root = ensure_root(origin.clone()).is_ok();
			let calls_len = calls.len();
			ensure!(calls_len <= Self::batched_calls_limit() as usize, Error::<T>::TooManyCalls);

			// Track the actual weight of each of the batch calls.
			let mut weight = Weight::zero();
			for (index, call) in calls.into_iter().enumerate() {
				let info = call.get_dispatch_info();
				// If origin is root, don't apply any dispatch filters; root can call anything.
				let result = if is_root {
					call.dispatch_bypass_filter(origin.clone())
				} else {
					call.dispatch(origin.clone())
				};

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
