### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler acts on the repository derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC against using `params.dig('repository', 'owner', 'login')` (or `organization.login`). Every webhook handler, however, resolves the target `Repository`/`Stack` to act on using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because the HMAC only proves "this body was signed with organization X's secret," not "the repository this body claims to describe belongs to organization X," an operator who legitimately controls a Shipit-registered GitHub App/organization can forge a payload whose `owner.login` matches their own org (so it passes signature verification) while `full_name` points at a completely different, victim-owned repository tracked by the same Shipit instance.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the payload == organization/repository the handler acts on`

`verify_signature` computes the expected org this way: [1](#0-0) [2](#0-1) 

The signature check itself is a pure HMAC-over-raw-body check with the secret picked for that derived organization: [3](#0-2) 

Crucially, HMAC validity says nothing about the *content* consistency of the JSON body - it only proves the sender knew the secret associated with whatever `repository.owner.login`/`organization.login` value they put in the body. An attacker who runs their own GitHub organization/App installation registered in Shipit (`config/secrets.yml` supports multiple orgs, each with an independent `webhook_secret`) knows their own secret and can therefore sign *any* JSON body they want, including one where `repository.full_name` names a repository belonging to a different, victim organization also tracked by the same Shipit instance.

After signature verification passes, `create` parses the raw body again and dispatches it, unmodified, to the handlers: [4](#0-3) 

Every handler resolves the `Stack`/`Repository` it operates on via the base `Handler#stacks`/`#repository_name`, which reads `full_name`, not `owner.login`: [5](#0-4) 

For example, `PushHandler` uses that repository lookup to trigger a resync of the victim stack based on attacker-supplied `ref`/`after` (head sha) values: [6](#0-5) 

So the equality that should hold - "the org whose secret signed this payload" == "the org/repo whose stack is mutated by this payload" - is never checked. Only `owner.login` is bound to the cryptographic proof; `full_name` (used for every actual write) is unauthenticated relative to that proof.

### Impact Explanation
This breaks the trust boundary between separately-onboarded GitHub organizations sharing one Shipit instance. An attacker who legitimately controls one org's GitHub App installation (and hence its `webhook_secret`) can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are accepted as authentic for a victim organization's repositories/stacks, because the signature check never validates that `full_name`'s owner matches the org whose secret was used. Concretely this allows a cross-tenant/cross-repository write: forged `push` events cause `Stack#sync_github` to run for a victim's stack with attacker-chosen `expected_head_sha`, and forged `status`/`check_suite` events can fabricate green CI state for a victim's commit, which downstream deploy-gating logic (this engine's task/merge status logic) may trust. This lines up with the Critical/High categories of "cross-repository writes" and "escalation via forged status impacting an unauthorized deploy," since Shipit's own review/merge/deploy flows can be steered by GitHub commit statuses and Membership records for a repository the attacker does not own.

### Likelihood Explanation
Requires the attacker to be a legitimate, but lower-privileged, tenant of the same Shipit installation (i.e., they control at least one organization's GitHub App/webhook config configured in `secrets.github`, which is a normal multi-org Shipit deployment per `docs/setup.md`). No GitHub write access to the victim repo, no Shipit session, and no API token are needed - only the ability to send an HTTP POST to `/webhooks` with a body signed with an org secret the attacker legitimately owns. This is a straightforward analog of the reported bug: a field that determines "who is asserting this" (`owner.login`, akin to `tx.origin`) is decoupled from the field that determines "what is actually acted upon" (`full_name`, akin to the proxy's actual deployed state/owner).

### Recommendation
Verify that `repository.owner.login` (used to select the signing secret) is identical to the owner segment of `repository.full_name` (and `organization.login`, when present) before dispatching to handlers, and reject the webhook if they diverge. More robustly, resolve the target `Repository`/`Stack` using the same organization value that was cryptographically authenticated, rather than trusting the unauthenticated `full_name` field independently.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `attacker-org` (attacker controls the GitHub App, knows `webhook_secret_A`) and `victim-org` (tracked stack `victim-org/some-repo`, unrelated secret).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/some-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(webhook_secret_A, body)` and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `owner.login`) and the HMAC validates successfully against `webhook_secret_A`. [1](#0-0) 
5. `create` dispatches the same body to `PushHandler`, which resolves the target repository via `full_name` = `"victim-org/some-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, even though the signature only proved control of `attacker-org`'s secret.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
