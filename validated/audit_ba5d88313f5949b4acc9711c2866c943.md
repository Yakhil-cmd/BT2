### Title
`StatusHandler#process` writes GitHub statuses to any `Commit` matching a SHA with zero repository/branch scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha` via `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no check against the webhook's own `repository` payload or the `branches` field it parses. This lets a valid webhook for repository A write a `Status` (and trigger `add_status`, `Hook.emit`, and `schedule_merges`) on a `Commit` belonging to a completely different stack/repository B, if a SHA collision occurs.

### Finding Description
The broken binding is: `repository_name(payload) == stack.repository` for every `Commit` that receives a status write. In `StatusHandler`, this equality is never checked.

- `app/models/shipit/webhooks/handlers/status_handler.rb:7-18` declares `accepts :branches, Array do requires :name, String end`, but `process` (lines 20-24) never reads `params.branches`. [1](#0-0) 
- `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped `Commit` table query with no `stack_id`, no `Repository.from_github_repo_name(repository_name)` filter, and no branch filter. [2](#0-1) 
- Contrast with `PushHandler#process`, which scopes strictly to `stacks.not_archived.where(branch:)`, where `stacks` is derived from the payload's own `repository.full_name` via the base `Handler#stacks`/`#repository_name` helpers. [3](#0-2) [4](#0-3) 
- `Commit#create_status_from_github!` performs a real write (`statuses.replicate_from_github!`) and triggers `add_status`, which emits hooks and can call `stack.schedule_merges`, affecting the *victim* stack, not the attacker's. [5](#0-4) [6](#0-5) 

`WebhooksController#verify_signature` only proves the payload was signed by a GitHub App installation for `repository_owner` derived from the payload itself — it never restricts *which* commits inside Shipit that payload is allowed to affect. [7](#0-6) 
So an attacker who owns/controls a repository that has the Shipit GitHub App/webhook installed (a normal, unprivileged setup step available to any GitHub user for their own repo) can send a legitimately-signed `status` event for their own repository, naming an `sha` that happens to also exist as a `Commit.sha` in an unrelated stack/repository tracked by the same Shipit instance. Because SHAs are only 160-bit but externally attacker-influenced (e.g., via crafted commit content, or simply targeting known/observed SHAs from public repos already tracked in the target Shipit instance), and because `Commit.sha` is not additionally scoped to `stack_id` in this query, the status is written onto the unrelated commit's row, corrupting CI/status state used for deploy gating (`deployable?`, `blocked?`, `schedule_merges`) on a stack the attacker never authenticated against.

None of the listed guards prevent this: `verify_signature` only authenticates the sender for their own org, `ExplicitParameters` validates shape not scope, and there is no `require_permission!`/`stacks` filter anywhere in `StatusHandler`.

### Impact Explanation
A correctly-signed webhook for the attacker's own repository can create/replace a `Status` row on a `Commit` belonging to another tenant's stack, influencing that stack's `deployable?`/`blocked?` computation and potentially triggering `schedule_merges` for continuous delivery — this is "a payload for one repository mutating another's ... commit" per the Critical bucket. It is repeatable per SHA collision and requires no privilege beyond controlling a repository that has a webhook configured against the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs a repository with a valid webhook/App installation pointed at the target Shipit host (a step any GitHub user can do for a repo they own, and Shipit hosts commonly accept many orgs' installs), and a SHA collision between their own commit and a `Commit` row already ingested for an unrelated stack (feasible by targeting commits from public upstream/forked repositories that the target stack already tracks, since `sha` is copied verbatim from GitHub and not repository-namespaced within Shipit). No secrets are required. Likelihood is moderate-to-high in multi-tenant Shipit deployments that track forks/mirrors of the same upstream commits across different stacks.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`: resolve the target `Stack`(s) via `stacks` (built from the payload's own `repository.full_name`), and restrict the `Commit` lookup to `stacks.map(&:id)` (or `Commit.where(sha: params.sha, stack_id: stacks.ids)`), rejecting or ignoring commits that don't belong to a stack tied to the reporting repository.

### Proof of Concept
minitest plan (`test/models/webhooks/status_handler_test.rb` conceptually, out of scope to write here but described):
1. Create `stack_a` for repository `owner/repo-a` and `stack_b` for repository `owner/repo-b`.
2. Create `commit_b = create(:commit, stack: stack_b, sha: "deadbeef...")`.
3. Build a `status` payload with `repository.full_name = "owner/repo-a"`, `sha = commit_b.sha`, `branches: []` (empty, satisfying `accepts :branches`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_b.statuses.reload.count` increased and the new `Status#stack_id == stack_b.id` — i.e. a payload declaring `repository.full_name == "owner/repo-a"` produced a write where `Status.stack_id == stack_b.id`, proving `repository_name(payload) != stack.repository` yet the write succeeded.
6. Contrast with `PushHandler` test `':push does not enqueue a job if not the target branch'`, which asserts no `sync_github` call occurs when the branch doesn't match — showing `StatusHandler` has no equivalent gate at all.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
