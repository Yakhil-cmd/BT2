### Title
Cross-organization webhook forgery via `repository.owner.login`/`repository.full_name` binding mismatch enables unauthenticated CI-status and push-event injection - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), while the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::StatusHandler`, `PushHandler`, `CheckSuiteHandler`) resolve the target `Repository`/`Stack`/`Commit` from a *different* attacker-controlled field (`repository.full_name`, or in the `status` handler's case, only the raw commit `sha`, with no repository scoping at all). Because GitHub App webhook secrets are documented as optional per organization, and `GithubApp#verify_webhook_signature` treats a missing secret as automatically verified, an attacker who can address the request to any configured organization lacking a `webhook_secret` can forge events that are processed as if they came from a completely different, protected organization/repository.

### Finding Description
`verify_signature` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally passes when no secret is configured for that organization: [3](#0-2) 

The webhook secret is explicitly documented as optional, and Shipit supports multiple simultaneously-configured GitHub organizations, each with its own (possibly unset) secret: [4](#0-3) [5](#0-4) [6](#0-5) 

Once past `verify_signature`, dispatched handlers do not re-derive the repository from the same field used for authentication. The base `Handler` resolves the target stacks from `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

Most critically, `StatusHandler` doesn't even scope by repository at all — it matches purely on commit SHA across the entire `Commit` table: [8](#0-7) 

`Commit#create_status_from_github!` creates a `Status` record, which drives CI-gating and continuous-delivery scheduling: [9](#0-8) [10](#0-9) 

**Binding broken:** `organization authenticated (repository.owner.login used to pick the HMAC secret) == organization/repository actually written to (repository.full_name / bare commit sha used by handlers)`. Before the attack, these two values are guaranteed equal only because real GitHub servers keep them consistent; nothing in Shipit enforces this. After the attack, an attacker crafts a payload where `repository.owner.login` names an org configured *without* a webhook secret (satisfying `verify_signature` trivially, since `return true unless webhook_secret`), while the effective target (`full_name`, or simply a known commit `sha`) belongs to a stack under a *different*, properly-secret-protected organization.

### Impact Explanation
This allows an unauthenticated attacker to:
- Forge `status` webhooks that create arbitrary CI success/failure `Status` records for any commit SHA in the system (no repo/org check exists in `StatusHandler` at all), which feeds `deployable_status` gating and can trigger `schedule_continuous_delivery`, potentially causing an unauthorized deploy on stacks with `continuous_deployment` enabled by faking passing CI on a target commit.
- Forge `push` and `check_suite` webhooks against any tracked repository (by setting `repository.full_name` to the victim repo while authenticating as an org with no configured secret), causing `GithubSyncJob` re-syncs and `RefreshCheckRunsJob`s to run against arbitrary stacks, and (through the same signature-selection flaw) suppress the requirement that the request actually originated from that repository's real GitHub App installation.

This crosses the credential/authentication boundary between organizations and can lead to an unauthorized deploy (impact category: Critical), qualifying under the report's accepted impacts. The severity is conditioned on at least one configured organization having no `webhook_secret` set — which the project's own documentation and default templates present as a supported, optional configuration, not a misconfiguration.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that (a) supports multiple GitHub organizations (a documented, supported feature since 0.34.0) and (b) leaves the webhook secret unset for at least one of them (explicitly documented as "optional" in `docs/setup.md` and shown as `# nil` in the shipped example secrets file). No credentials, session, or `ApiClient` token are required — only network access to the public `/webhooks` endpoint and knowledge of a target commit SHA (obtainable from public GitHub history) or repository full name.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization/app in production, and fail closed (reject, not verify-as-true) when it is absent.
- Bind signature verification and payload handling to the same identity: after verifying the signature for the organization derived from `repository.owner.login`, re-validate that `repository.full_name`'s owner segment matches that same organization before handlers run.
- Scope `StatusHandler#process` (and any other handler) to the resolved `stacks`/repository, not to a bare, globally-unscoped commit SHA lookup.

### Proof of Concept
1. Deploy Shipit configured with two organizations: `victim-org` (has `webhook_secret` set, hosts a tracked stack with continuous deployment enabled) and `attacker-org` (configured, e.g. for a low-value integration, with `webhook_secret` left blank as permitted by the docs).
2. Obtain a commit SHA of an undeployed commit on a `victim-org` stack (visible publicly on GitHub or via Shipit's own UI).
3. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any arbitrary value), and JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/anything" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's real commit — and calls `create_status_from_github!`, injecting a forged "success" status that can satisfy CI-gating and trigger `schedule_continuous_delivery` on the victim stack, without ever having presented a valid signature for `victim-org`.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
