### Title
Webhook Signature Verified Against `repository.owner.login` But Handlers Act on an Independent, Unvalidated `repository.full_name` / Global `sha` Lookup - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with, using only `params.dig('repository','owner','login')` (or `organization.login`). Once the signature validates, the raw payload is handed unchanged to `Shipit::Webhooks.for_event(event)` handlers, which act on a *different* field — `repository.full_name` (or, for `status` events, a completely unscoped `sha`) — with no check that this acted-upon repository/commit actually belongs to the organization whose secret authenticated the request.

`PushHandler` uses this to enqueue a sync for any stack under that repo: [5](#0-4) 

`StatusHandler` is even less scoped: it doesn't consult `repository` at all, just a global `sha` lookup across every `Commit` in the whole Shipit instance: [6](#0-5) 

Shipit explicitly supports multiple GitHub Apps/organizations configured on one instance, each with its own `webhook_secret` (as demonstrated by the multi-org fixture): [7](#0-6) 

Because the signature check only proves "this request was signed with OrgA's secret" and never proves "the resource being mutated (`repository.full_name`, or the commit `sha`) belongs to OrgA," an actor who legitimately administers **their own** organization/GitHub App in the same Shipit instance can craft a raw JSON body where `repository.owner.login` = their own org (satisfies signature routing/verification with their own known secret) while `repository.full_name` (or `sha`) references a **different** organization's tracked stack/commit. The binding that should hold — `organization that authenticated == repository/commit that is written` — is never enforced.

### Impact Explanation
This breaks the authorization boundary between tenants of a multi-org Shipit deployment:
- Via a forged `status` webhook, an attacker (owner of Org A's own GitHub App/secret) can set an arbitrary CI status (e.g. `success`) on **any commit sha** belonging to Org B's stack — `Commit.where(sha: params.sha)` has no repository scoping at all. Combined with `Commit#deployable?` (`success? && !blocked?`) and `schedule_continuous_delivery` (`stack.continuous_deployment?`), this can make an otherwise CI-gated commit appear deployable and trigger an **unauthorized deploy** via continuous delivery for a stack the attacker does not own.
- Via a forged `push` webhook, an attacker can force `GithubSyncJob` to run against Org B's stack (`PushHandler#process` / `Handler#stacks`), causing Shipit to sync/act on Org B's repository state on the attacker's command.
- Membership/team handlers similarly act on data (`organization`, `team`, `member`) taken from the payload without verifying it matches the org whose secret validated the request, potentially affecting `Shipit.github_teams`-based authorization for a different org.

This satisfies the required "Critical: unauthorized deploy" / "High: escalation into `Shipit.github_teams` authorization" impact bar, achieved purely by an actor who controls their own org's GitHub App configuration in a shared, multi-tenant Shipit instance — no privileged access to the victim's org, no GitHub App private key, and no Shipit session/API token is required.

### Likelihood Explanation
Requires that the Shipit deployment host multiple organizations' GitHub Apps (a documented, supported configuration, per `secrets_double_github_app.yml`) and that the attacker legitimately controls one of those organizations' webhook secret (normal for any org onboarded to a shared instance). No knowledge of the victim org's secret, no GitHub token exfiltration, and no code execution is needed — only crafting an inconsistent JSON body, which is straightforward once the attacker has any valid secret for the routing org.

### Recommendation
Enforce the equality invariant explicitly: after selecting `github_app` via `repository_owner`, validate that every subsequent use of `repository.full_name` (in `Handler#repository_name`) and any `sha`-based lookups begins with (or is scoped to) `repository_owner`/that organization's repositories only. Concretely:
- In `Shipit::Webhooks::Handlers::Handler#repository_name`, reject/raise if `payload.dig('repository','owner','login')` does not match the resolved `Stack#repo_owner`, or better, pass the already-verified `repository_owner` down and require an exact match against `full_name`'s owner segment.
- In `StatusHandler`, scope the `Commit.where(sha:)` lookup to commits belonging to stacks whose `repository.owner` equals the verified organization.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (attacker-controlled) and `OrgB` (victim), each with distinct `webhook_secret`s, as supported by `Shipit.github(organization:)`.
2. Attacker, knowing only `OrgA`'s `webhook_secret` (which they legitimately administer), crafts a `status` event payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" },
  "sha": "<victim commit sha in OrgB's stack>",
  "state": "success"
}
```
3. Computes `X-Hub-Signature` using `OrgA`'s webhook secret over this raw body.
4. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "OrgA")` and successfully verifies the signature (attacker knows this secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since no repository check exists, it matches and updates the status of `OrgB`'s commit, potentially flipping `deployable?` to `true` and triggering `ContinuousDeliveryJob` for `OrgB`'s stack — an unauthorized deploy of a repository the attacker never had access to.
