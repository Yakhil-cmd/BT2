### Title
Malicious Proposer Can Omit `header.VRank` to Suppress Candidate Failure Reports, Artificially Lowering CFS and Enabling Unearned `ValActive` Status and KAIA Rewards — (`kaiax/vrank/impl/consensus.go`, `kaiax/vrank/impl/getter.go`)

---

### Summary

`VerifyHeader` unconditionally accepts `len(header.VRank) == 0` for any non-epoch block after the permissionless fork. A single malicious proposer of block N can therefore submit a block with a nil `VRank` even when candidates provably failed to respond during block N-1 consensus. Because `cfReport` also returns empty for nil `VRank`, the CP matrix receives no failure increments for those candidates on that block. The byzantine filter does not correct this — it is designed to discard inflated (highest) scores, not suppressed (zero) ones. Over an epoch, repeated suppression keeps CFS scores below `CfsThreshold`, causing `isPassVrankTest` to return `true` for candidates who should fail, allowing them to transition to `ValActive` and collect KAIA block rewards they should have forfeited.

---

### Finding Description

**Step 1 — `VerifyHeader` accepts nil VRank unconditionally for non-epoch blocks** [1](#0-0) 

The guard at lines 59–61 returns `nil` (success) the moment `len(header.VRank) == 0`, with no check of whether candidates actually failed. This is the only validation path for non-epoch blocks with empty VRank.

**Step 2 — `cfReport` mirrors the same silent-empty behavior** [2](#0-1) 

When `applyBlocksForCPMatrix` calls `cfReport(blockNum)` for a block whose `header.VRank` is nil, it receives an empty slice. No `cpMatrix.Increment` calls are made for that block.

**Step 3 — `applyBlocksForCPMatrix` records the proposer but skips all increments** [3](#0-2) 

`AddProposer` is always called (so the proposer is counted in `ProposerCount()`), but the `for _, candidate := range cfReport` loop body is never entered. The malicious proposer's column in the CP matrix stays at 0 for all candidates.

**Step 4 — The byzantine filter does not protect against suppression** [4](#0-3) 

The filter sorts scores ascending and removes the top-F (highest) entries. A malicious proposer who suppresses failures contributes a 0 to the sorted list — the lowest possible value. The filter therefore removes honest reporters' non-zero scores instead, making the suppression attack strictly more effective than if no filter existed.

**Step 5 — Suppressed CFS feeds `isPassVrankTest` at epoch-end** [5](#0-4) 

`isPassVrankTest` passes when `cfs < CfsThreshold`. If the malicious proposer has suppressed enough failures, the candidate's CFS stays below the threshold.

**Step 6 — Passing the VRank test gates `CandTesting → ValActive`** [6](#0-5) 

A candidate that passes the VRank test enters `competeOrDemote` and can reach `ValActive`; one that fails is demoted to `Registered`. `ValActive` validators receive KAIA block rewards.

### Impact Explanation

A single malicious proposer — any validator selected by the protocol — can suppress candidate failure reports for every block they propose during an epoch. The CP matrix permanently records 0 for those blocks (the committed header is immutable). At epoch-end, `GetCFS` replays the committed headers and produces an artificially low CFS for the colluding candidates. Those candidates pass `isPassVrankTest`, transition to `ValActive`, and receive KAIA block rewards they should have forfeited. This is unauthorized reward distribution affecting KAIA system-managed funds.

---

### Likelihood Explanation

Any validator that is legitimately selected as a proposer can execute this attack unilaterally. No majority collusion, privileged keys, or external service compromise is required. The proposer simply omits `header.VRank` (sets it to nil) when building the block. Honest validators call `VerifyHeader`, which accepts nil VRank, and sign the block. The suppression is permanent and undetectable on-chain.

---

### Recommendation

`VerifyHeader` must not treat `len(header.VRank) == 0` as unconditionally valid for non-epoch blocks. When `GetCandTesting(N-1)` returns a non-empty candidate set, the proposer is obligated to include a VRank field (even if the report is empty, it should be encoded as `RLPEncode([])` = `0xc0`, not nil). The verifier should reject a nil VRank when candidates exist for block N-1. Concretely:

- If `GetCandTesting(N-1)` is non-empty, require `len(header.VRank) > 0`.
- Alternatively, require the proposer to always encode the report (including an empty list as `0xc0`) so that nil and "no failures" are distinguishable.

This mirrors the epoch-start block's treatment, which requires an exact byte-for-byte match against the expected encoding.

### Proof of Concept

1. Start a permissionless-fork-enabled chain with at least one `CandTesting` candidate C1.
2. Arrange for C1 to provably fail to respond (e.g., drop all `VRankCandidate` messages from C1 at the network layer).
3. When the malicious proposer P builds block N (non-epoch), override `PrepareHeader` to set `header.VRank = nil` instead of calling `encodeCandidateFailureVRank`.
4. Submit the block. `VerifyHeader` returns nil; honest validators sign it.
5. At epoch-end, call `GetCFS(epochEnd - 1)`. Assert `cfs[C1]` is lower than it would be if VRank had been populated with C1's address.
6. Assert `isPassVrankTest(C1)` returns `true` and C1 transitions to `ValActive` instead of `Registered`. [1](#0-0) [2](#0-1) [3](#0-2) [6](#0-5)

func byzantineFilter(cpMatrix vrank.CPMatrix, F int) map[common.Address]uint64 {
	cfs := make(map[common.Address]uint64)
	for cand, reporterToScore := range cpMatrix {
		scores := slices.Collect(maps.Values(reporterToScore))
		slices.Sort(scores)
		if F >= len(scores) {
			// since `scores` contain non-zero scores only, F >= len(scores) can happen, in which case all scores are discarded.
			scores = nil
		} else {
			scores = scores[:len(scores)-F]
		}
