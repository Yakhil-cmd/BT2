### Title
Attacker-controlled `shipit.yml` step text can exfiltrate host process `ENV` secrets via `$VAR` fallback in `EnvironmentVariables#interpolate` - (File: lib/shipit/environment_variables.rb)

### Summary
`Shipit::EnvironmentVariables#interpolate` substitutes any `$VAR` token found in a command string using `@env.fetch(variable) { ENV[variable] }`, silently falling back to the Shipit server process's raw `ENV` when the variable is not present in the command's own allowlisted env hash. Because task `steps` text originates from the target repository's `shipit.yml` (attacker-controlled for Review Stacks on forked/attacker-owned PRs), an attacker can reference any host environment variable name by simply writing `$SOME_NAME` in a step, causing its value to be interpolated into the shell command and captured in task output.

### Finding Description
The broken binding: only variable names explicitly present in a command's `env` hash (populated from the operator-approved, whitelist-checked `env:` block via `EnvironmentVariables#permit`) should ever be substitutable in step text — i.e. `interpolatable_names == env.keys`. In reality, `interpolate` breaks this:

```ruby
# lib/shipit/environment_variables.rb:20-27
def interpolate(argument)
  return argument unless @env
  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
```

`@env.fetch(variable) { ENV[variable] }` means any `$NAME` token in `argument` (the raw step command string) that is not a key of `@env` is resolved against the Shipit server process's own `ENV` — the full host environment, not the sanitized/whitelisted stack env.

Call path: `Shipit::Command#interpolate_environment_variables` (lib/shipit/command.rb:51-55) wraps each argument with `EnvironmentVariables.with(env).interpolate(argument)`, and `interpolated_arguments` (line 81-83) is used both when spawning the process (`start`, line 92) and is what ends up in the task's log output. The `env` here is the `Command`'s own `@env`, built from the merged stack/task environment (`env.transform_values`, line 34) that has already passed through `EnvironmentVariables#permit`'s whitelist check for the `env:` hash — but `permit` only validates the **keys explicitly assigned via `env:`**, it never validates or restricts what names can appear as `$VAR` inside the **step text itself**. `sanitize_env_vars` (environment_variables.rb:35-44) has nothing to do with the interpolation fallback path.

Attack: an attacker who can get a `shipit.yml` reviewed/built for a Review Stack (their own fork/PR, since Review Stacks build the deploy spec from the PR branch) writes a step such as:
```yaml
deploy:
  override: ["echo $AWS_SECRET_ACCESS_KEY", "echo $SECRET_TOKEN"]
```
When an operator (or an automated Review-Stack trigger) runs the resulting task, `Command#start` interpolates `$AWS_SECRET_ACCESS_KEY` / `$SECRET_TOKEN` against the Shipit host's process `ENV` (since these names are not in the task's `env:` whitelist) and echoes them into the task's streamed output, which the attacker (as the stack's PR author, who can view Review Stack task logs) can read.

No existing guard intercepts this: `EnvironmentVariables#permit` is not invoked by `interpolate`; `Command#initialize` only sanitizes values passed in `env:` (`v&.to_s`), not the substitution fallback; there is no allowlist check inside `interpolate` at all.

### Impact Explanation
Any process-level secret sitting in the Shipit host's `ENV` (e.g. `AWS_SECRET_ACCESS_KEY`, `GITHUB_TOKEN` if exported as env var, deploy credentials, `SECRET_TOKEN`, database URLs, etc.) can be exfiltrated into a task's log output, which is readable by the PR author / stack viewer. This is repeatable per-request (any new step referencing a different variable name), across any repository with Review Stacks enabled that allows external contributions, matching the Critical category "exfiltration of ... deploy-time secrets ... via a fork-controlled `shipit.yml` step."

### Likelihood Explanation
Requires Review Stacks enabled and a `shipit.yml` that is built from attacker-controlled branches/PRs (a documented, supported Shipit feature) plus an operator/automation triggering the resulting task. No Shipit credentials, GitHub tokens, or elevated permissions are needed beyond opening a PR — attacker cost is minimal (just guessing/knowing the names of secrets typically exported into the deploy host's environment, e.g. common AWS/CI variable names). This is highly feasible and cheaply repeatable.

### Recommendation
Change `EnvironmentVariables#interpolate` to never fall back to the raw process `ENV`; only substitute variables explicitly present in the whitelisted `@env` hash, leaving unmatched `$VAR` tokens untouched (or raising) instead of silently pulling host secrets:
```ruby
def interpolate(argument)
  return argument unless @env
  argument.gsub(/(\$\w+)/) do |variable|
    name = variable.sub('$', '')
    @env.key?(name) ? Shellwords.escape(@env[name]) : variable
  end
end
```

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (illustrative)
test "interpolate leaks host ENV for unwhitelisted variable names" do
  ENV['SECRET_TOKEN'] = 'super-secret-value'
  command = Shipit::Command.new(
    ['echo $SECRET_TOKEN', {}],
    chdir: '.',
    env: { 'PATH' => '/usr/bin' } # SECRET_TOKEN intentionally NOT included
  )
  interpolated = command.interpolated_arguments.first
  assert_includes interpolated, 'super-secret-value'
ensure
  ENV.delete('SECRET_TOKEN')
end
```
Before the fix: assertion passes, proving host `ENV['SECRET_TOKEN']` leaks into the interpolated command/task output. After applying the recommended fix, the assertion should fail (the literal `$SECRET_TOKEN` token remains unexpanded). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
