### Title
Webhook signature verified against the organization named in the unsigned JSON body, not the repository the handler writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, not-yet-verified JSON body, then checks the `X-Hub-Signature` HMAC using that org's secret. Every downstream handler, however, resolves the target `Stack`/`Repository` from a *different* field of the same body — `repository.full_name` — via `Handler#repository_name` and `Repository.from_github_repo_name`. In a multi-organization Shipit deployment (`secrets.github` keyed by org, each with its own `webhook_secret`), an attacker who controls one onboarded organization's webhook secret can sign a payload where `repository.owner.login`/`organization.login` is their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a *different*, victim organization also configured on the same Shipit instance.

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` with that app's `webhook_secret` (`lib/shipit/github_app.rb:76-83`, `verify_webhook_signature`).
- Handlers never re-derive or check `repository.owner.login`; they use `Handler#repository_name` = `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) to find the affected repository/stacks: `Repository.from_github_repo_name(repository_name)&.stacks` (same file, line 33), and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) simply splits `"owner/name"` from that string and does a DB lookup — with no cross-check against `repository_owner`/the org that authenticated the signature.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) then calls `stack.sync_github(expected_head_sha: ...)` on whatever stacks match that `full_name`, which enqueues `GithubSyncJob` to fetch commits and update the stack's cached deploy spec/HEAD using the API client for the *stack's own owner* (`Repository#github_app` → `Shipit.github(organization: owner)`), independent of which org's secret validated the request.

The binding that should hold is: **organization whose `webhook_secret` authenticated the request == organization that owns the repository the handler acts on**. Because `repository_owner` (the field covered by/driving signature selection) and `repository.full_name` (the field the handlers actually consume) are two independent, both attacker-controlled JSON fields, that binding can be broken: an attacker who is a legitimate installer of the GitHub App for org A (and therefore knows or can trigger delivery signed with org A's `webhook_secret`) can forge `repository.full_name` to point at org B's repository, and the signature check will still pass because it was computed against org A's payload/secret pairing, not org B's.

### Impact Explanation
This can cause a cross-organization write: `GithubSyncJob`/`PushHandler` will ingest fabricated commit history (`expected_head_sha`) and recompute/cache the deploy spec for a stack belonging to an organization the attacker does not control, using data taken from a webhook whose signature was only ever validated against the attacker's own org. Downstream, `CacheDeploySpecJob`/`Stack#sync_github` update the stack's `cached_deploy_spec` and commit graph based on this forged event, which can influence which commit is deployed next or corrupt deployability of the victim's stack — a cross-repository write driven entirely by a spoofed signature-binding, matching the "Critical: cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the deployment to use the multi-organization `secrets.github` schema (`docs/setup.md`, `config/secrets.development.shopify.yml`) with more than one org onboarded to the same Shipit instance, and the attacker to be a legitimate member/admin able to trigger real webhook deliveries for at least one of those orgs (e.g., they own or administer org A, which is also configured in the same Shipit instance as victim org B). This is a narrower but realistic multi-tenant scenario, not requiring any privileged Shipit session, `ApiClient` token, or the GitHub App private key — only the ability to get GitHub to deliver a webhook for a repo they control, with a forged `full_name` field.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, after verifying the signature, assert that `repository.owner.login` (the org used to select the verifying secret) matches the owner segment of `repository.full_name` before dispatching to handlers; reject the webhook (422) on mismatch. Alternatively, derive both values from the same already-verified field and stop trusting `full_name` independently of the org used for signature verification.

### Proof of Concept
Conceptual PoC (multi-org config, orgs `evilcorp` and `victimcorp` both configured in `secrets.github`):
1. Attacker administers `evilcorp`'s GitHub App and knows/derives its `webhook_secret`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "evilcorp" }, "full_name": "victimcorp/secret-repo" }
}
```
3. `X-Hub-Signature` computed with `evilcorp`'s `webhook_secret` over this exact raw body.
4. `verify_signature` computes `repository_owner = "evilcorp"`, fetches `evilcorp`'s app, and the HMAC check passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victimcorp/secret-repo")`, matching a real stack owned by `victimcorp`, and enqueues `GithubSyncJob` for it with the attacker-chosen `expected_head_sha`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
