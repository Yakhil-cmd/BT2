### Title
Type-confusion crash in `in merkle` address-definition evaluation due to unvalidated authentifier type before `merkle.deserializeMerkleProof` - (File: definition.js)

### Summary
CVE-2017-11552 is a memory-management bug in `mpg321`/`libmad` where a caller passes attacker-controlled data into a decoder without properly validating/bounding it, producing memory corruption and a crash. The closest reachable analog in `ocore` is a **missing type validation** before untrusted, unit-supplied data is fed into a parser: the `in merkle` address-definition operator passes the raw authentifier value straight into `merkle.deserializeMerkleProof()` without first checking that it is a string, unlike the equivalent code path in `formula/evaluation.js` for AAs, which does perform this check.

### Finding Description
In `definition.js`, the `in merkle` spending-condition operator only checks that the authentifier is *truthy* before parsing it: [1](#0-0) 

```js
case 'in merkle':
    if (!assocAuthentifiers[path])
        return cb2(false);
    ...
    var serialized_proof = assocAuthentifiers[path];
    var proof = merkle.deserializeMerkleProof(serialized_proof);
```

`merkle.deserializeMerkleProof` assumes its argument is a string and calls `.split("-")` directly on it with no type guard: [2](#0-1) 

If `assocAuthentifiers[path]` is a truthy non-string value — e.g., a number, boolean `true`, an array, or a nested object, all of which are valid JSON types that could be placed as an "authentifier" value for this path in a posted unit — `serialized_proof.split` is not a function and the call throws a `TypeError` synchronously, unlike the well-guarded call site in `formula/evaluation.js`, which explicitly checks `typeof proof === 'string'` before invoking the same deserializer and wraps `verifyMerkleProof` in `try/catch`: [3](#0-2) 

By contrast, the `in merkle` branch in `definition.js` has no such type check and no surrounding `try/catch` for the `deserializeMerkleProof` call itself.

This mirrors the CVE's bug class: a caller (here, the address-definition evaluator) fails to validate/sanitize attacker-supplied data before handing it to a lower-level parsing routine (`deserializeMerkleProof`) that makes unchecked assumptions about the input's shape, resulting in an unhandled runtime fault triggered purely by malformed but structurally-valid unit content.

### Impact Explanation
An address can be defined with an `in merkle` spending condition (a normal, supported definition template). Any unit spending from such an address supplies the authentifier for that path. If the authentifier value is a non-string JSON type instead of a string, the synchronous `TypeError` thrown inside `deserializeMerkleProof` propagates up through `validateAuthentifiers`'s evaluation chain. Depending on whether this specific call is protected by an outer `try/catch` elsewhere in the authentifier-evaluation pipeline (which I was not able to conclusively confirm within the available search), this could either:
- be caught and simply reject the unit (low impact), or
- escape as an uncaught exception during unit validation, disrupting validation/synchronization for that unit across nodes.

Given the strict validation criteria requiring "node disagreement on validity/stability" or "a network unable to confirm new units," I flag this finding with an important caveat: I could not fully verify (within my remaining tool budget) whether the exception is caught by an enclosing handler higher in `validation.js`'s `validateAuthentifiers` call chain. Without confirming an actual escape to an uncaught state that crashes or hangs the validating process, the severity claim cannot be fully substantiated to the "Medium/High/Critical, concrete impact" bar required by the rules.

### Likelihood Explanation
Triggering the code path only requires: (1) an address definition containing an `in merkle` clause (a documented, supported spending-condition operator), and (2) a unit spending from that address where the corresponding authentifier is set to a non-string JSON value (e.g., `123`, `true`, `[]`, `{}`) instead of the expected serialized-proof string. Both are achievable by an ordinary unprivileged unit poster who controls their own address definition and the authentifiers in their own unit — no special privilege is required to reach this code.

### Recommendation
Add an explicit type check in `definition.js`'s `in merkle` handler before calling `merkle.deserializeMerkleProof`, mirroring the guard already present in `formula/evaluation.js`:
```js
if (typeof assocAuthentifiers[path] !== 'string')
    return cb2(false);
```
Additionally, harden `merkle.deserializeMerkleProof` itself to validate that its input is a string and wrap its body (and the `in merkle` call site in `definition.js`) in a `try/catch` that resolves to `cb2(false)` on error, consistent with how `merkle.verifyMerkleProof` already fails safe.

2. Compose a unit spending from this address where `authors[].authentifiers[path]` is set to a non-string JSON value, e.g. `123` or `{}`, instead of a serialized merkle-proof string (`"index-sibling1-sibling2-root"`).
3. Submit the unit for validation. `validateDefinition`'s `in merkle` branch passes this non-string value directly to `merkle.deserializeMerkleProof`, which calls `.split` on it, throwing a `TypeError`.

*Note: I was unable to conclusively confirm within available search depth whether an enclosing `try/catch` in `validation.js`/`definition.js`'s broader `validateAuthentifiers` flow ultimately absorbs this exception before it can crash or hang the validating process. This uncertainty should be resolved via a live/dynamic Devin session (e.g., running a local test with such a malformed unit) before treating this as a confirmed high-severity DoS.*
