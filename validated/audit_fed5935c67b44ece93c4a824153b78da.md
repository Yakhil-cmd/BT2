### Title
Route-selected venue contracts can graft arbitrary `token.transfer(victim → attacker)` calls into the victim's signed auth tree for controller strategy calls, draining wallet tokens unrelated to the position - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-supplied route bytes that pass through arbitrary, unallowlisted hop venues. Any contract invoked inside the route can call `victim.require_auth()` (e.g. via `token.transfer(victim, attacker, x)`), and Soroban recording mode attaches that call as a sub-invocation of the victim's root `swap_collateral` entry. If the victim signs the simulated tree — which wallet UIs surface only as opaque sub-invocations — the rogue transfer executes and steals any token in the victim's wallet, including assets the protocol never listed.

### Finding Description
The controller's swap helper forwards user-supplied `StrategySwap` bytes to the router inside a flash guard, authorizing only the controller's own exact input transfer (`authorize_transfer_as_current`, `common/src/token.rs:36-52`). The router then invokes whichever `hop_pool` addresses the route names; venue allowlisting does not exist by design. Because the human caller signed the root invocation with `caller.require_auth()` at the controller entrypoint, every nested `require_auth()` on that same address anywhere in the call tree — including inside an attacker-deployed "pool" contract — is folded into the caller's recorded auth tree during simulation and is honored in enforcing mode if signed.

The repository's own harness proves the mechanism end-to-end: `RogueHopPool::swap` performs `token.transfer(victim, attacker, WALLET_BALANCE)` on a token the protocol never listed; recording mode produces an auth tree where that transfer sits beneath Alice's `swap_collateral` entry (`simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry`), and enforcing mode moves Alice's entire wallet balance once the poisoned tree is signed (`enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer`) — the same test shows an honest route signature is refused, so detection depends entirely on the signer inspecting raw sub-invocation XDR. ### Impact Explanation
Theft of user funds at Medium severity: an unprivileged attacker who supplies or influences the route bytes (the same channel that produces every route — quote services, phishing payloads, front-end injection) can drain the victim's entire balance of any chosen token the moment the victim signs the simulated transaction. The stolen assets need not be posted to the protocol at all, so this is strictly worse than ordinary slippage/route-quality loss: it converts a signature meant to authorize one collateral swap into a blanket wallet grant, mirroring CVE-2024-4768's "popup makes it easier to trick a user into granting permissions" class.

### Likelihood Explanation
Requires victim interaction (signing a poisoned simulated tree) and a route traversing the attacker's venue — both plausible since routes are opaque bytes produced off-chain and venues are deliberately unallowlisted. No privileged access, leaked key, or protocol-state precondition is needed; the attacker only needs their contract address present in the route the victim submits. The protocol itself records and surfaces the rogue transfer rather than filtering it, so the exploit reliability is bounded by wallet/auth-tree UX, not by contract defenses.

### Recommendation
Restrict strategy routes to governance-allowlisted venues, or have the router pin `sender` such that only the router's own authorized token pulls (never `sender.require_auth()` re-entry from hop code) can appear in the caller's tree — e.g., execute hops through a per-call ephemeral vault address rather than the user's address, and reject any route that produces a `require_auth` on the caller inside venue code. At minimum, document and surface in signing UX that sub-invocations of strategy calls may touch unrelated wallet tokens.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: deploy `UnlistedPoolRouter` as the swap aggregator and `RogueHopPool` pre-loaded with `(victim = Alice, wallet_token, attacker, 77_770_000_000)`; call `swap_collateral(alice, account_id, USDC_key, 50_000_000_000, ETH_key, route_through_rogue_pool)`. Recording mode returns an auth tree with `transfer(alice → attacker, WALLET_BALANCE)` nested under `swap_collateral`; submitting the signed tree moves Alice's full unlisted-token balance to the attacker while her position swap completes normally.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
