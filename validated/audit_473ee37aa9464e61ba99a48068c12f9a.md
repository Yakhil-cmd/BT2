### Title
Asset definer can instantly revoke `spender_attested` status via `asset_attestors` update, retroactively invalidating in-flight payments from previously-attested addresses - ([File: validation.js])

### Summary
For assets with `spender_attested: true`, the attestor list is not append-only or time-locked — the asset definer can publish a new `asset_attestors` message at any time, and this instantly replaces the *entire* list of trusted attestors used to determine which addresses are currently "attested". Any address whose attestation is not renewed under the new list immediately loses its ability to spend the asset, even for payments that were perfectly valid and broadcast under the previous attestor list but are not yet included before `last_ball_mci`.

### Finding Description
The `asset_attestors` message lets an asset's definer replace the attestor list at will: [1](#0-0) 

Only the *most recent* attestor-list unit before `last_ball_mci` is used to compute the set of currently attested addresses — there is no notion of grandfathering addresses attested under an older, still-valid list: [2](#0-1) 

This attestor set directly gates payment validity: if the asset requires `spender_attested`, all authors (or the issuer) must be in the freshly computed `arrAttestedAddresses`, otherwise the entire payment message is rejected: [3](#0-2) 

Crucially, this authorization check is **not evaluated once at the moment the payment is created/signed** — it is re-evaluated deterministically based on `last_ball_mci` at validation time, similar to how `definition.js` explicitly documents that address definitions (and by extension any state used for authorization, including `attested` conditions) must be **re-validated every time** because referenced state can change out from under a previously-valid, in-flight unit: [4](#0-3) 

The `attested` opcode itself has the exact same "point-in-time" evaluation semantics for address-definition-based authorization: [5](#0-4) 

So the sequence is:
1. Address A is attested for asset X, and broadcasts a `payment` spending asset X to address B. The unit is valid according to the attestor list in effect at broadcast time.
2. Before this unit becomes final (before its `last_ball_mci` advances/stabilizes), the asset definer publishes a new `asset_attestors` message that drops A from the attestor list (this is fully at the definer's discretion, with no notice period, no minimum-attestor overlap requirement, no delay).
3. When A's payment unit is finally validated (as it must be, deterministically, using the latest attestor list before its `last_ball_mci`), `arrAttestedAddresses` no longer contains A, and `validatePayment` rejects it with `"none of the authors is attested"`.

This is the same bug class as the reported issue: a mutable, unprivileged-affecting configuration parameter (attestor list / liquidation threshold) is changed by a party other than the affected user, and the change is applied retroactively/immediately to already-in-flight, previously-valid state, instead of being deferred until affected positions/transactions have a chance to resolve under the old rules.

### Impact Explanation
An asset definer (a role many assets require for `spender_attested` and `issued_by_definer_only` configurations — legitimate, non-malicious use is expected) can unilaterally and instantly invalidate legitimate, already-broadcast transactions of otherwise-honest holders, without any of those holders having done anything wrong. Concretely:
- Users' pending payments (potentially with headers/payload commissions already paid) become permanently non-serial/invalid, freezing the payment attempt and burning the fees spent creating/broadcasting the unit.
- Because attestor-list changes and payment validation both key off `last_ball_mci`, an attacker (or negligent definer) can front-run known pending payments from a target address by revoking its attestation before the payment's last ball advances, effectively freezing that specific transaction at will.
- This is functionally a fund-freezing bug reachable by an asset issuer against unprivileged holders of that asset — falling under the allowed "asset issuance and transfer conditions" impact category (AA/asset fund freezing).

### Likelihood Explanation
Any asset defined with `spender_attested: true` is exposed; this is a standard, documented asset feature (used in `test/aa.test.js` and part of the core asset model), not an edge case. The `asset_attestors` message has no rate limit, delay, or overlap requirement with the previous list, so the definer can trigger this at any time. The condition requires the definer to act (maliciously or carelessly) to change the list while payments are in flight — but this is a normal, permitted, single-message action available at any block, and no other party needs to cooperate.

### Recommendation
When resolving `spender_attested` for validating a specific unit, do not simply take the single most-recent attestor list unit before `last_ball_mci`. Instead:
- Consider giving previously-attested addresses a grace period (e.g., honor the attestor list that was in effect at the time the unit's `last_ball_unit`/parents were chosen) before applying a new list, similar to how address-definition changes require pending changes to stabilize before taking effect.
- Alternatively, require that an `asset_attestors` update can only remove an address once any concurrently in-flight transactions from that address are no longer pending (or reject the update until it is safely in the past relative to open payments), or clearly document this as expected/accepted behavior with wallet-level warnings so senders don't rely on attestation remaining stable mid-flight.

### Proof of Concept
1. Definer creates asset X with `spender_attested: true` and an initial attestor list that attests address A (via `attestors` in the `asset` message, recorded in `asset_attestors`, see `writer.js` lines around asset attestor insertion).
2. A is attested; A broadcasts `payment` spending asset X to B. This unit passes `validatePayment` since A ∈ `arrAttestedAddresses` per `storage.readAsset`'s `addAttestorsIfNecessary` (storage.js:1911-1946).
3. Before A's unit's `last_ball_mci` advances past the point needed for finality, the definer sends a new `asset_attestors` message with an attestor list that no longer results in A being attested (e.g., removing/replacing the attestor that vouched for A).
4. At validation time (revalidation is mandatory, see `definition.js` lines 1449-1453 for the general principle applied to any referenced state), `validatePayment` (validation.js:2115-2123) now computes `arrAttestedAddresses` without A and rejects A's unit with `"none of the authors is attested"`, even though the unit was fully valid when it was created and broadcast.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
