### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits solely by `Commit.where(sha: params.sha)` without any repository/stack scoping, then calls `commit.create_status_from_github!(params)` which writes a `Status` row scoped to `commit.stack_id`. Because two different GitHub repositories (e.g., a public upstream repo and any fork of it) can legitimately share identical commit SHAs, an attacker controlling repo B (a fork of victim repo A) can trigger a `status` webhook from repo B that creates/updates a `Status` for the *same commit row already tracked under stack A*, with an attacker-chosen `context` and `state`.

### Finding Description
The broken binding: the equality that should hold is `(context, state) approved-by == (context, state) written-for stack A` where "approved-by" means GitHub's CI check run authority for repository A. Instead the code enforces only `sha(payload) == commit.sha` globally across the entire commits table, with no constraint that `payload.repository.full_name == commit.stack.repository.full_name`.

Path:
1. `WebhooksController#create` dispatches the parsed JSON to `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)` [2](#0-1) .
2. `verify_signature` only checks that the payload is properly signed for `repository_owner` (derived from the payload's own `repository`/`organization` field) — it does not check that the sha or stack referenced in the eventual database write belongs to that organization/repository [3](#0-2) .
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . Unlike `CheckSuiteHandler#process`, which scopes lookups through `stacks.where(branch: ...)` derived from `Handler#stacks` (itself derived from `payload.dig('repository','full_name')`) [4](#0-3) [5](#0-4) , `StatusHandler` never restricts by repository at all.
4. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , and `Status.replicate_from_github!` writes `state`, `description`, `target_url`, `context`, `created_at` directly from the attacker-controlled payload, scoped to `stack_id` taken from the *victim's* commit record, not from the attacker's payload [7](#0-6) .

Exploit flow: attacker forks victim's public repository A into their own account/repo B (sharing identical commit SHAs for all commits up to the fork point, and any cherry-pick/rebase they choose to replicate). Attacker owns repo B and can configure and trigger real `status` webhooks from GitHub for repo B (e.g., by wiring any CI integration or GitHub Action they control to set a commit status on their own fork with `context: 'ci/required'`, `state: 'success'`, `sha: <shared sha>`). GitHub signs and delivers this webhook using the credentials associated with repo B's owner/org; `verify_signature` passes because it only checks the payload's own claimed repository/organization, not that this repository actually owns the target commit. `StatusHandler` then finds the pre-existing `Commit` row for that sha under stack A (created when Shipit synced A) and writes a fabricated `success` status scoped to `stack_id` = A's stack.

Existing guards fail because: `verify_signature` validates *who signed*, not *what the sha/stack correspond to*; `ExplicitParameters` schema only validates types/presence of `sha`, `state`, `context`, not their relationship to the requesting repository; and `StatusHandler` is the only handler in this codebase that omits the `stacks`/repository-scoping pattern used everywhere else (`CheckSuiteHandler`, `PushHandler`).

### Impact Explanation
A forged `success` status for context `ci/required` is written against stack A's commit despite never having been approved by repository A's actual CI. This directly feeds `Stack#blocking_statuses`/`Commit#blocked?` and `Commit#deployable?` at `app/models/shipit/commit.rb:227-237`, which can flip `blocked?` to `false` and make a commit `deployable?`, enabling an unauthorized deploy of a stack the attacker has no permission over. This is a payload for one repository (B) mutating another repository's stack/commit state (A) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy."

### Likelihood Explanation
Preconditions: stack A must already have the target commit synced into Shipit's `commits` table (normal operation for any actively tracked branch/PR), and A must configure `required_statuses`/blocking status with a `context` name the attacker can learn (e.g., from A's public CI badge, public `shipit.yml`, or public commit-status API). The attacker needs a repo (fork of A, or any repo sharing the sha, e.g. via cherry-pick of a public commit) under a GitHub org/account whose webhook signature can be validated by `Shipit.github(organization: repository_owner)` — i.e., their own account/org must have the relevant GitHub App/webhook installed, which is standard for any public fork if Shipit's GitHub App is installed org-wide or if the target uses a shared webhook secret model. Cost is low: fork, replicate a target sha (or find an already-shared upstream commit), fire one webhook. Fully repeatable against any tracked commit shared between repos.

### Recommendation
Scope `StatusHandler#process` (and `Commit.create_status_from_github!`) to only apply statuses to commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')` — mirror the pattern already used in `CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, using `Handler#stacks`/`repository_name` instead of a bare `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, illustrative — actual file under `test/` to be authored by engineer):
1. Create `stack_a` for repo `"victim/a"` with `required_statuses` (or `blocking_statuses`) including `'ci/required'`.
2. Create a `Commit` under `stack_a` with `sha: 'deadbeef...'` (simulating shared fork history) and no existing status for `'ci/required'`.
3. Assert `commit.blocked?` (or `deployable?`) reflects the missing required status beforehand: `refute commit.deployable?` (or assert it's blocked pending the required context).
4. Build a `status` webhook payload with `repository.full_name = "attacker/b"`, `sha` equal to the same sha, `context: 'ci/required'`, `state: 'success'`.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(parsed_params)` directly (bypassing only the outer signature check, which is out of scope for this unit-level equality proof).
6. Assert a `Status` row was created with `stack_id: stack_a.id`, `context: 'ci/required'`, `state: 'success'` even though the payload's `repository.full_name` was `"attacker/b"` — i.e., assert `status.stack_id == stack_a.id` while `payload['repository']['full_name'] != stack_a.repository.full_name`, proving the binding `payload.repository == status.stack.repository` is violated.
7. Assert `commit.reload.deployable?` (or `blocked?` becomes `false`) now returns favorably, demonstrating the forged CI signal took effect for stack A.
