### Title
Webhook signature verification authenticates the payload's declared organization, not the repository it actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a webhook against using the `repository.owner.login` (or `organization.login`) field of the payload, but every event handler that actually performs writes (looks up a `Stack`/`Repository` and mutates it) keys off a *different* field, `repository.full_name`. Because these two fields are never checked against each other, an attacker who can produce a validly-signed payload for one organization configured in Shipit can freely set `repository.full_name` to point at a completely different organization's repository/stack.

### Finding Description
`verify_signature` derives the authenticating organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

It uses that value to select a `GitHubApp` (and thus a specific `webhook_secret`) via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Shipit explicitly documents and supports configuring **one GitHub App/webhook secret per organization** for multi-tenant deployments: [4](#0-3) [5](#0-4) 

However, once the signature check passes, every default handler (`PushHandler`, the `PullRequest::*` handlers, `Handler#stacks`) resolves *which repository/stack to act on* using an entirely separate field — `repository.full_name` — with no re-validation that this repository actually belongs to the organization that was authenticated: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

`GitHubApp#verify_webhook_signature` also short-circuits to `true` when the selected organization has no configured `webhook_secret` — a state the setup docs mark as "(optional)": [10](#0-9) [11](#0-10) 

**Equality broken:** the binding the app relies on is `organization authenticated by verify_signature (repository.owner.login / organization.login) == organization owning the repository the handlers act on (repository.full_name)`. Nothing enforces this equality; both fields live in the same JSON body but are consumed independently by two different code paths.

**Before the attack:** a legitimate delivery for org `A`'s repo has `repository.owner.login == "A"` and `repository.full_name == "A/repo"` — consistent, because GitHub itself fills in both from the same source event.

**Attack sequence:** In a multi-org Shipit deployment, if the attacker can produce a request whose HMAC validates for organization `A` (either because they hold `A`'s configured `webhook_secret`, e.g. as the tenant that set up that App/org integration, or because `A` was configured without a `webhook_secret` at all — a documented, valid, "optional" configuration — making `verify_webhook_signature` return `true` unconditionally for any payload naming `A`), they POST a fully attacker-crafted JSON body directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = `"A"` (to satisfy `verify_signature`)
- `repository.full_name` = `"B/victim-repo"` (an unrelated, victim tenant's repository that has stacks/review-stacks configured in the same Shipit instance)

`verify_signature` passes (checked only against `A`), and the handler then resolves `Repository.from_github_repo_name("B/victim-repo")` and acts on it — e.g. `PushHandler` enqueues `GithubSyncJob` for `B`'s stack, or `PullRequest::ClosedHandler`/`OpenedHandler`/`LabeledHandler` archive, unarchive, or provision review stacks belonging to `B` via `ReviewStackAdapter#create!`/`archive!`/`unarchive!`, which calls `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.deprovision`.

### Impact Explanation
This breaks a cross-tenant isolation boundary in multi-org Shipit deployments: forging events attributed to organization `B` while only authenticating as organization `A` allows spoofed push/PR lifecycle events to trigger unauthorized provisioning, archiving/unarchiving, and deprovisioning actions on another tenant's stacks — an unauthorized deploy/rollback-adjacent action performed on repositories the attacker does not control, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Likelihood is highest whenever any organization configured in a multi-org Shipit deployment has no `webhook_secret` set (an explicitly documented "optional" configuration state) — in that case the attack requires no credential of any kind, only knowledge that such an unsecured organization name exists. It is otherwise contingent on the attacker holding the (non-victim) webhook secret for at least one tenant organization, which is a lower bar than compromising the victim's own secret, `GITHUB_TOKEN`, or `api_clients_secret`.

### Recommendation
Bind the organization used for signature verification to the same field used for repository resolution: after selecting the GitHub App via `repository_owner`, verify that `repository.full_name`'s owner segment matches `repository_owner` (or resolve the app/secret from `repository.full_name` directly) before dispatching to handlers in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (`docs/setup.md`, "Using Multiple Github Applications") containing organization `A` (attacker-known secret or no secret configured) and victim organization `B` (has stacks/review-stacks configured).
2. Craft a JSON body:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "..." },
  "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Compute `X-Hub-Signature: sha1=...` using `A`'s webhook secret (or omit/mismatch it if `A` has no secret configured).
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. `WebhooksController#verify_signature` authenticates against org `A` and passes; `PullRequest::ClosedHandler` then resolves `Shipit::Repository.from_github_repo_name("B/victim-repo")` and calls `review_stack.archive!`, deprovisioning a stack belonging to organization `B` despite the request never having been authenticated for `B`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
