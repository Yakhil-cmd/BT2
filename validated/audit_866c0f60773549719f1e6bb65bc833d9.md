### Title
Attempt-Counter Reset via Partial Delivery Allows Malicious Peer to Stall Fast-Sync Indefinitely — (`datasync/downloader/statesync.go`)

---

### Summary

The `process` function in `stateSync` clears a peer's attempt record for every unfulfilled trie-node task whenever `len(req.response) > 0`, regardless of whether the delivered blob actually advanced sync. A malicious P2P peer can exploit this by delivering one unexpected or duplicate blob per round, keeping `len(req.response) > 0` true while making zero real progress, and having its attempt entry erased for all N−1 withheld tasks. The downstream safety check `len(task.attempts) >= npeers` is therefore permanently bypassed, and the tasks are re-queued for the same peer indefinitely.

---

### Finding Description

**Root cause — line 560:**

```go
if len(req.response) > 0 || req.timedOut() {
    delete(task.attempts, req.peer.id)
}
``` [1](#0-0) 

The condition tests `len(req.response) > 0`, not `successful > 0`. Any non-empty response — including one blob that returns `ErrNotRequested` or `ErrAlreadyProcessed` — satisfies the condition and wipes the peer's ID from `task.attempts` for every task it was assigned but did not deliver.

**Task assignment — lines 508, 513-514:**

When `fillTasks` assigns a task to a peer it stamps `t.attempts[req.peer.id]` and moves the task out of `s.trieTasks` into `req.trieTasks`. [2](#0-1) 

After `process` clears the stamp and re-queues the task at line 569, `fillTasks` sees no entry for the peer in `task.attempts` and happily re-assigns the same task to the same peer. [3](#0-2) 

**Safety valve is bypassed — lines 565-567:**

```go
if len(task.attempts) >= npeers {
    return successful, fmt.Errorf("trie node %s failed with all peers ...")
}
``` [4](#0-3) 

Because the peer's attempt is deleted at line 561 *before* this check, `len(task.attempts)` never reaches `npeers` for the malicious peer. The abort path is never taken.

**Stall detection does not fire — lines 381-399:**

The only peer-drop path in `loop` requires `req.timedOut()` (i.e., `req.response == nil`). [5](#0-4) 

Because the malicious peer always sends a response (even a single junk blob), `req.timedOut()` is `false` and the peer is never dropped.

---

### Impact Explanation

**Complete stall (single-peer or eclipse scenario):** With `npeers = 1`, the malicious peer delivers one blob whose hash is not in the pending set (`ErrNotRequested`). `successful` stays 0, `s.sched.Pending()` never decreases, yet `len(req.response) > 0` clears the attempt. The loop at line 362 (`for s.sched.Pending() > 0`) never exits. The node cannot commit the state root and cannot transition to full-sync or block processing. [6](#0-5) 

**Severe slowdown (multi-peer scenario):** With honest peers present, the malicious peer monopolizes a batch of tasks (up to its full capacity, e.g. 384 items) for each round. While those tasks are held in `req.trieTasks` they are absent from `s.trieTasks` and unavailable to honest peers. The malicious peer can respond faster than honest peers and re-acquire the same tasks every round, starving honest peers of work.

---

### Likelihood Explanation

The attacker only needs to establish a standard P2P connection to a node that is performing fast-sync (a normal, publicly reachable state). No privileged keys, governance access, or majority-validator collusion is required. Delivering a single previously-seen trie blob (or any blob whose keccak256 is not in the current pending set) is trivially achievable by any peer that has participated in any prior sync session.

---

### Recommendation

Replace the `len(req.response) > 0` guard with `successful > 0` so that attempt-clearing is only granted when the peer actually contributed a new, valid trie node:

```go
// Before (vulnerable):
if len(req.response) > 0 || req.timedOut() {
    delete(task.attempts, req.peer.id)
}

// After (fixed):
if successful > 0 || req.timedOut() {
    delete(task.attempts, req.peer.id)
}
```

This ensures that a peer delivering only unexpected or duplicate blobs accumulates attempts normally and is eventually excluded by the `len(task.attempts) >= npeers` guard.

### Proof of Concept

```
Setup:
  - Victim node in fast-sync mode, single connected peer = malicious peer M.
  - npeers = 1, s.sched.Pending() = K (e.g. 10 000 trie nodes).

Round 1:
  fillTasks assigns hashes [h1 … hN] to M.
  M responds with [blob_x] where keccak256(blob_x) ∉ pending set.
    → processNodeData returns ErrNotRequested; successful = 0.
    → len(req.response) = 1 > 0  →  delete(task.attempts, M.id) for h1…hN.
    → len(task.attempts) = 0 < 1 = npeers  →  no abort.
    → h1…hN re-queued in s.trieTasks.

Round 2: identical to Round 1.
…
Round ∞: s.sched.Pending() = K (unchanged). Loop never exits.
```

The victim node's fast-sync goroutine is permanently blocked inside `loop()`, preventing state-root commitment and any subsequent block execution.
