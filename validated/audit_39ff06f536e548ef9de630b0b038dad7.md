### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name` field, allowing cross-organization spoofed webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from the payload's `repository.owner.login` (falling back to `organization.login`). However, once the signature check passes, `create` dispatches the *entire raw payload* to `Shipit::Webhooks::Handlers::Handler` subclasses, which independently determine the target `Stack`/`Repository` using `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb#repository_name`). These two fields are never cross-checked against each other, so the field that authorizes the request (the org used to pick the secret) is decoupled from the field that is actually acted upon (the full repo name used to locate stacks).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does: [1](#0-0) 
It calls `Shipit.github(organization: repository_owner)` and verifies the signature with that org's configured secret. `repository_owner` is computed purely from attacker-controlled JSON: [2](#0-1) 

`GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Once verification passes, `create` forwards the *raw params* — not scoped to the verified organization — to every matching event handler: [4](#0-3) 

Handlers such as `PushHandler` and `StatusHandler` resolve the affected `Stack`s solely via `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the same class of bug as the referenced report: the value used to establish trust (`totalSupply()`/here, the org whose secret is checked) is not the same value that is actually acted upon (`points_`-derived index/here, `repository.full_name` used to locate the Stack). Shipit's documented multi-organization configuration (`config/secrets.development.example.yml:18-38`) explicitly supports per-organization `webhook_secret`s, meaning some configured organizations may legitimately have no secret while others do: [8](#0-7) 

**Binding broken:** `organization authenticated (repository.owner.login / organization.login, whose secret gated the request) ≠ repository written (repository.full_name, used by Handler#stacks to locate the Stack acted upon)`.

### Impact Explanation
An attacker who knows (or can guess) that any single organization in a multi-organization Shipit deployment has `webhook_secret` left blank (a supported, documented configuration) can submit an unsigned POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that unprotected org, while setting `repository.full_name` to any *other*, secret-protected organization's real repository. The signature check passes trivially (secret-less org), and the dispatched handler acts on the spoofed `full_name`, causing:
- Forced re-sync of a protected repository/stack via `PushHandler` → `stack.sync_github(expected_head_sha:)`, letting an attacker drive the HEAD SHA used for sync/deploy tracking on a repo they have no GitHub access to.
- Forgery of commit statuses on arbitrary commits via `StatusHandler#process` → `commit.create_status_from_github!`, which can flip `deployable_status`/`merge_status` checks used to gate deploys and merges.
- Similar cross-org spoofing is available to any handler keyed off `repository.full_name` (`check_suite_handler.rb`, `membership_handler.rb`, `pull_request/*`), since none of them validate that `repository.full_name`'s owner matches the `repository_owner`/secret used for verification.

This crosses an authentication boundary (attacker never proves possession of the target org's `webhook_secret`) and can influence deploy/merge gating logic on a repository the attacker was never authorized to write to — a cross-repository/cross-organization write via forged webhook events.

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least one configured organization has no `webhook_secret` (explicitly supported/documented as a valid nil configuration) while another organization's repositories are the actual target. This is a realistic operational pattern (e.g., an internal/low-risk org left unsecured for convenience while primary orgs are protected) rather than a misconfiguration of the whole app. No credentials, session, or GitHub access are required by the attacker — only knowledge of the target repository's `full_name` and any one unsecured org's `login`. If every configured org has a strong `webhook_secret`, the attack is blocked at `verify_signature`.

### Recommendation
Bind the two identifiers together instead of treating them independently:
- Require that `repository.full_name`'s owner segment match `repository_owner` (the value used to select the verifying `webhook_secret`) before dispatching to handlers, rejecting the request (422) on mismatch.
- Alternatively, resolve the target `Stack`/`Repository` using the same organization value that was authenticated, and reject payloads whose `repository.full_name` owner differs.
- Consider making `webhook_secret` mandatory for every configured organization (fail configuration validation instead of silently returning `true` from `verify_webhook_signature`) to remove the secret-less bypass entirely.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `org-unsecured` (no `webhook_secret`) and `org-protected` (with `webhook_secret`, owning `Stack` for `org-protected/critical-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "org-unsecured" },
    "full_name": "org-protected/critical-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-unsecured")`; `verify_webhook_signature` returns `true` unconditionally because `org-unsecured` has no `webhook_secret` (`lib/shipit/github_app.rb:77`).
4. `PushHandler#process` resolves `stacks` via `repository.full_name = "org-protected/critical-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the protected stack — despite the attacker never presenting a valid signature for `org-protected`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
