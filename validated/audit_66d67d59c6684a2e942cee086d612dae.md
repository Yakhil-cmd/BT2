## Title
Cross-repository Status write via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's `WebhooksController` correctly verifies a GitHub webhook's HMAC signature against the specific organization derived from the payload's `repository.owner.login` field before dispatching the event to a handler. [1](#0-0)  However, once dispatched, the `status` event handler does not re-apply that repository binding when performing its write: it looks up target `Commit` records purely by SHA, globally across the entire Shipit installation, instead of scoping the lookup to the repository the signature was actually verified for.

### Finding Description
The base `Handler` class defines a `stacks` helper that scopes lookups to the repository named in the payload: [2](#0-1) 

Every other default handler uses this scoping — `PushHandler` filters via `stacks.not_archived.where(branch:)`, and `CheckSuiteHandler` filters via `stacks.where(branch: ...)`: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, bypasses this repository scope entirely and queries commits by SHA alone, across all stacks/repositories tracked by the Shipit instance: [5](#0-4) 

The binding that should hold is: *the GitHub organization/repository whose webhook secret validated the signature* == *the repository whose commit gets a status written*. Before the fix, `WebhooksController#verify_signature` establishes the former by resolving `Shipit.github(organization: repository_owner)` and checking the HMAC over the raw payload. [6](#0-5)  After dispatch, `StatusHandler#process` ignores `repository_name`/`stacks` and writes a `Status` onto every `Commit` row in the database whose `sha` matches the payload's `sha`, regardless of which repository/stack that `Commit` actually belongs to. [7](#0-6)  Because git commit SHAs are shared across forks (any commit predating a fork point has an identical SHA1 in both the upstream repo and every fork/downstream repo), a legitimately-signed `status` webhook for one tracked repository can cause a status update on a `Commit` belonging to a completely different tracked repository/stack whose history happens to share that commit (e.g., an org's second repository that was forked from, or shares ancestry with, the first).

### Impact Explanation
This is a cross-repository write: an entity that only has the ability to trigger (or legitimately receives) a correctly-signed `status` webhook for Repository A can affect commit/CI status state recorded against a `Commit` that Shipit associates with Repository B's stack, as long as that specific commit SHA is shared between the two histories. Since Shipit's merge queue and deployability logic (`Commit#deployable?`, `MergeRequest#all_status_checks_passed?`) rely on `Status`/`CheckRun` records keyed to a `Commit`, this can pollute or forge CI status data for a repository/stack the sender does not otherwise control, potentially affecting merge/deploy decisions for that unrelated stack. This matches the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
The main constraint is the requirement for identical commit SHAs across two Shipit-tracked repositories, which occurs naturally whenever a tracked stack is a fork (or shares linear history) of another tracked stack/repository within the same or a related GitHub organization — a very plausible setup in monorepo-splitting, template-repo, or fork-based deployment workflows. No token, session, or elevated privilege beyond the ability to have GitHub deliver a validly-signed `status` event (i.e., normal CI/App activity on a repository already onboarded to Shipit) is required to trigger the mismatched write; the flaw is a code-level scoping gap, not a misconfiguration.

### Recommendation
Scope `StatusHandler#process` to the handler's own `stacks`/`repository_name` binding (as `PushHandler` and `CheckSuiteHandler` already do), e.g. restrict the `Commit` lookup to commits belonging to `stacks` (via their `stack_id`) rather than a bare global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure Shipit to track two stacks whose underlying git histories share ancestry (e.g. Repository A and its fork Repository B, both onboarded as separate Shipit stacks/repositories, potentially under different orgs/webhook secrets).
2. Identify a commit SHA that exists in both A's and B's history (any commit prior to the fork point).
3. From Repository A, produce (or let GitHub deliver) a validly-signed `status` webhook event referencing that shared SHA:
```json
{
  "sha": "<shared_commit_sha>",
  "state": "success",
  "context": "ci/example",
  "repository": { "owner": { "login": "org-that-owns-repo-A" } }
}
```
4. `WebhooksController#verify_signature` validates this against Org A's webhook secret and succeeds. [6](#0-5) 
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which matches and updates the `Commit` row belonging to Repository B's stack as well, even though the signature only proved authenticity for Repository A. [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
