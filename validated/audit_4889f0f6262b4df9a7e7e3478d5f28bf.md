### Title
`GitHubApp#verify_webhook_signature` unconditionally returns `true` for any organization configured without a `webhook_secret`, bypassing HMAC verification on `POST /webhooks` - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever `@webhook_secret` is blank, with no HMAC check performed at all. Since `WebhooksController#verify_signature` resolves the `GitHubApp` instance purely from the attacker-controlled `repository.owner.login` field in the POST body, any organization that is configured (intentionally or accidentally) without a `webhook_secret` allows unauthenticated, unsigned webhook payloads to reach `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Finding Description
The broken binding: for organization `org`, `verified` should equal `false` whenever `Shipit.github(organization: org)`'s underlying config has no real shared secret, but the code makes `verified == true` in that case.

Code path:
- `WebhooksController#verify_signature` at [1](#0-0)  resolves `github_app = Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the JSON body's `repository.owner.login` / `organization.login` field [2](#0-1) , entirely attacker-controlled with no authentication.
- `Shipit.github` looks up the org's config via `github_app_config`, which does not validate that a `webhook_secret` is present [3](#0-2) .
- `GitHubApp#verify_webhook_signature` short-circuits: `return true unless webhook_secret` [4](#0-3) . If `@webhook_secret` (set from `@config[:webhook_secret].presence` at initialization [5](#0-4) ) is `nil`, the method returns `true` regardless of the signature header or body content.
- On `verified == true`, `create` proceeds to parse the raw body and dispatch it to all registered handlers for the event: [6](#0-5) .

Root cause: the "no configuration = trust everyone" fallback in `verify_webhook_signature` was presumably intended only for local/dev setups with a single global GitHub App config (the legacy single-org schema), but it applies identically in the multi-org schema, where an attacker who knows or guesses that some org has no `webhook_secret` set can spoof that org's identity via the request body alone.

This is not a hypothetical misconfiguration: the repository's own test/dummy secrets fixtures for the multi-org schema (`test/dummy/config/secrets_double_github_app.yml`, orgs `OrgOne`/`OrgTwo`) and the JSON fixture (`test/dummy/config/secrets.test.json`) all define `webhook_secret: null` [7](#0-6) [8](#0-7) , demonstrating this is a real, reachable operational state, not merely a contrived edge case.

Existing guards do not prevent this:
- `drop_unhandled_event` only filters by event type presence of handlers, not by authenticity [9](#0-8) .
- `GithubOrganizationUnknown` handling only covers orgs entirely absent from config, not orgs present but lacking a secret [10](#0-9) .
- No model validation or `ExplicitParameters` schema enforces `webhook_secret` presence at config load time.

### Impact Explanation
An attacker who can send arbitrary HTTP requests to the Shipit host (no session, no token required) can forge webhooks for any organization whose config omits `webhook_secret`, causing legitimate-looking side effects to be triggered for that org/repository: e.g. `GithubSyncJob` enqueued for arbitrary commits/branches, commit `Status` records created, `Membership`/`Team` records created or deleted via `membership` events, and any other handler registered under `Shipit::Webhooks.handlers` for events like `push`, `status`, `check_suite`, `pull_request`, etc. (see handler dispatch at `app/controllers/shipit/webhooks_controller.rb:12` and handlers exercised in `test/controllers/webhooks_controller_test.rb`). This is authentication bypass on webhook ingestion — the request is treated as if it originated from GitHub's signed webhook delivery when it did not. It is repeatable against every organization sharing this misconfiguration and scales to the full blast radius of whatever the registered webhook handlers do (state mutation, job scheduling) for that org's stacks.

### Likelihood Explanation
The only precondition is that some configured GitHub organization has `webhook_secret` unset/blank — a state the repository's own fixture files show is a plausible operational default, and which an operator could easily leave unset by omission (e.g. copying a template, or not realizing it's required per-org in the multi-org schema). No secrets are needed by the attacker; only knowledge (or trial) of an org name lacking the secret, and the ability to send an HTTP POST to `/webhooks`. This is a low-cost, fully repeatable attack, matching the "authentication bypass (forged webhook)" impact category.

### Recommendation
Change `verify_webhook_signature` to fail closed instead of failing open when `webhook_secret` is blank: return `false` (or raise a configuration error) if no secret is configured, and require every configured organization's `webhook_secret` to be present and non-blank at load time (e.g. validate in `Shipit.github_app_config`/`GitHubApp#initialize`, raising if missing). At minimum, restrict the "return true unless webhook_secret" fallback to the legacy single-org schema path only, and never allow it in the multi-org lookup path driven by attacker-supplied `repository_owner`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "webhook signature bypass for org with blank webhook_secret" do
  Shipit.stubs(:github).with(organization: 'someothergithuborg').returns(
    Shipit::GitHubApp.new('someothergithuborg', {
      app_id: 42, installation_id: 43, webhook_secret: nil, private_key: nil
    })
  )

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeefdeadbeefdeadbeefdeadbeefdeadbeef' # garbage signature

  payload = JSON.parse(payload(:push_master))
  payload['repository']['owner']['login'] = 'someothergithuborg'
  expected_head_sha = payload['after']

  # side effect fires despite bogus signature -> proves bypass
  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha:]) do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```
Both sides of the binding before the fix: `verified` (actual) == `true`; expected `verified` == `false` for an org without a real secret — they diverge, confirming the vulnerability. After applying the recommended fix (fail closed), `verified` == `false` and the request returns `422` with no job enqueued, closing the gap.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
