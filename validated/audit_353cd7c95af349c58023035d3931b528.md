### Title
`MembershipHandler` mutates a `Team` looked up solely by `params.team.id` while `verify_signature` only authenticates the webhook's originating organization, letting any org with a legitimate Shipit GitHub App forge team membership for another organization's team - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the organization named in `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), both attacker-controlled JSON fields. `MembershipHandler#find_or_create_team!` then looks up/creates the mutated `Team` purely by `params.team.id` (an integer, unrelated to which secret verified the request), and `MembershipHandler#process` adds or removes `params.member.login` from that team. Nothing cross-checks that the organization whose secret verified the payload actually owns `team.id`.

### Finding Description
The binding the code should enforce is:
`resolved_github_app.organization == Team(github_id: params.team.id).organization`

Trace:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`. This only proves the raw body was signed with the secret configured for the organization named in the body's own `repository.owner.login`/`organization.login` field — a field the requester fully controls and which will legitimately be their own organization's name if they own a Shipit-App-installed org.
- `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) is a pure HMAC check against `@webhook_secret`, which is a per-organization secret (`GitHubApp` initialized with `organization`). It has no knowledge of, and does not validate, any other field in the body (e.g. `team.id`, `team.slug`, `organization.login` used later).
- `create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches the full, still-attacker-authored JSON body to `MembershipHandler#process`.
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The lookup key is `github_id` only; `organization` is only set in the creation block (i.e., only when no row exists yet). For any team already known to Shipit (the normal case for any org actively using team-gated authorization), the existing row — belonging to the real victim organization — is returned unchanged, and `params.organization.login` (which the attacker can freely set to their own org, e.g. to keep it internally consistent, or to anything since it's unused here) has no effect on which row is targeted.
- `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then calls `team.add_member(member)` (action `added`) or removes a member, mutating the victim's `Team#members` association based on `params.member.login`, another attacker-controlled field.

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own org's legitimate `webhook_secret`, and a JSON body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "x"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-controlled-account"}
}
```
Because `repository_owner` resolves to `attacker-org`, `verify_signature` passes using the attacker's own legitimate secret. `MembershipHandler` then looks up the victim's pre-existing `Team` row by `victim_team_github_id` and adds `attacker-controlled-account` as a member of that team.

Existing guards do not stop this: `drop_unhandled_event` only checks that a handler exists for the event type; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not cross-organization ownership; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` check in the webhook path (webhooks are inherently unauthenticated by session/token and rely entirely on HMAC signature scoping, which this flow fails to scope correctly).

### Impact Explanation
An attacker who legitimately controls any organization with Shipit's GitHub App installed can add an arbitrary GitHub login (including their own or a colluding account) as a member of any `Team` already known to Shipit, provided they know or can guess/discover that team's numeric `github_id`. If `Shipit.github_teams`/team membership gates deploy, merge, rollback, or stack authorization (`User#authorized?` and related checks elsewhere in the app rely on `Team#members`), this is a cross-tenant authorization escalation: a party with no privileges in the victim organization gains membership in a privileged team recognized by Shipit for that victim's stacks. This matches "escalation into `Shipit.github_teams` authorization" (High/Critical depending on how those teams gate deploy/merge actions) and is repeatable against any team whose `github_id` the attacker can determine, across arbitrary victim organizations, using only the attacker's own legitimate webhook secret.

### Likelihood Explanation
Preconditions: attacker owns/installs the Shipit GitHub App on any organization (a self-service, unprivileged action), and knows the victim's target `Team#github_id` (numeric GitHub team IDs are frequently discoverable — e.g., via the public GitHub API for orgs/teams the attacker can observe, via team `@mentions` in public repos, via prior legitimate webhook traffic, or by brute-forcing a modest ID space) and the `Team` already exists in Shipit's database (true for any actively used team-gated stack, since these rows are created the first time a legitimate membership event or the `teams.rake` task creates them). No Shipit or GitHub secret belonging to the victim is required. The attacker only needs their own org's genuine webhook secret, which they possess by design once the App is installed. This is a repeatable, low-cost attack requiring no special access.

### Recommendation
In `MembershipHandler#find_or_create_team!`, look up the `Team` by both `github_id` AND `organization` (or verify that `params.organization.login` matches the existing team's `organization` before mutating it, raising/dropping the event otherwise). Additionally, `WebhooksController#verify_signature` should validate that all organization-identifying fields in the payload (`team`'s owning org, `organization.login`, `repository.owner.login`) are mutually consistent with the organization whose secret verified the signature, rejecting events where they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "membership webhook signed by org A can mutate org B's team" do
  org_a_secret = 'secret-a'
  org_b_secret = 'secret-b'
  Shipit.stubs(:github).with(organization: 'org-a').returns(Shipit::GitHubApp.new('org-a', webhook_secret: org_a_secret))
  Shipit.stubs(:github).with(organization: 'org-b').returns(Shipit::GitHubApp.new('org-b', webhook_secret: org_b_secret))

  victim_team = shipit_teams(:shipit_committers) # belongs to org-b, github_id known
  attacker_login = 'attacker-account'

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'org-a' }, # attacker's own org, matches signing secret
    member: { login: attacker_login }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, payload)

  post :create, body: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok
  victim_team.reload
  assert_includes victim_team.members.map(&:login), attacker_login
  # Assert the mutated Team's organization is NOT the organization that signed the request
  assert_not_equal 'org-a', victim_team.organization
end
```
This demonstrates: signature verified using org-a's legitimate secret, yet the `Team` mutated (`victim_team`, `organization == 'org-b'`) diverges from the signing organization (`org-a`), confirming the broken binding.
