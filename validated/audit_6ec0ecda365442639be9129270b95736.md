### Title
Fee-on-Transfer ERC20 Token Accounting Discrepancy in ServiceChain Bridge Causes Last Withdrawer to Fail — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` from the caller via `safeTransferFrom`, but when the bridged token is a fee-on-transfer (FoT) ERC20, the bridge contract receives less than that nominal amount. The `RequestValueTransfer` event still records the full `_value`, which bridge operators relay to the counterpart chain's `handleERC20Transfer`. In lock/unlock mode the source-chain bridge therefore accumulates a growing token deficit with every deposit, and the last user to withdraw on the source side will have their `safeTransfer(_to, _value)` revert due to insufficient balance.

---

### Finding Description

**Deposit path — source chain (`requestERC20Transfer`):**

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

For a FoT token with rate `r`, the bridge receives `(_value + _feeLimit) × (1 − r)` instead of `_value + _feeLimit`. `_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange`, which transfers `fee` to `feeReceiver` and `feeLimit − fee` back to the caller — a total outflow of `feeLimit` from the bridge.

```solidity
// BridgeFee.sol lines 74-78
IERC20(_token).safeTransfer(feeReceiver, fee);
uint256 feeRefund = _feeLimit.sub(fee);
if (feeRefund > 0) {
    IERC20(_token).safeTransfer(from, feeRefund);
}
``` [2](#0-1) 

After fee payment and refund the bridge holds:

```
(_value + _feeLimit) × (1 − r) − feeLimit
= _value − (_value + _feeLimit) × r
```

This is strictly less than `_value`. The `RequestValueTransfer` event, however, records the full `_value`:

```solidity
// BridgeTransferERC20.sol lines 97-106
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress,
    _value,          // ← nominal, not actual received
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

**Withdrawal path — source chain (`handleERC20Transfer`, lock/unlock mode):**

When users bridge back, operators call `handleERC20Transfer` with the `_value` read from the event. In lock/unlock mode (`modeMintBurn == false`) the bridge attempts:

```solidity
// BridgeTransferERC20.sol line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

Because the bridge holds `_value − deficit` per prior deposit, after N deposits the cumulative shortfall is `N × (_value + _feeLimit) × r`. The N-th withdrawer's `safeTransfer` reverts, permanently locking their bridged assets.

---

### Impact Explanation

In lock/unlock mode with a FoT ERC20 token, the source-chain bridge contract accumulates a token deficit proportional to the FoT rate and the total bridged volume. The last user(s) attempting to withdraw on the source chain will receive a revert, permanently losing access to their bridged tokens. This is a direct loss of bridged assets held in a system-managed contract.

---

### Likelihood Explanation

The precondition is that bridge operators register a FoT ERC20 token. The bridge contracts impose no restriction on token type — `registerToken` accepts any address, and `SafeERC20` does not detect FoT behaviour. Once a FoT token is registered, every ordinary user call to `requestERC20Transfer` silently widens the deficit. No special attacker capability is required beyond being a normal bridge user.

---

### Recommendation

Measure the actual received amount by snapshotting the bridge's balance before and after the `safeTransferFrom` call, and use the delta as the canonical transfer value in the `RequestValueTransfer` event:

```solidity
function requestERC20Transfer(...) public {
    uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - before;
    // derive actual _value and _feeLimit from actualReceived, then proceed
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Alternatively, explicitly prohibit FoT tokens from being registered by verifying that a round-trip transfer returns the expected amount.

### Proof of Concept

**Setup:** FoT token with 1 % fee; bridge deployed in lock/unlock mode (`modeMintBurn = false`); token registered by operators.

**Step 1 — Alice deposits:**
- Alice calls `requestERC20Transfer` with `_value = 1000`, `_feeLimit = 100`.
- `safeTransferFrom` pulls 1100 tokens; bridge receives `1100 × 0.99 = 1089`.
- `_payERC20FeeAndRefundChange` pays `fee` and refund totalling 100; bridge balance = `1089 − 100 = 989`.
- `RequestValueTransfer` emits `valueOrTokenId = 1000`.

**Step 2 — Counterpart chain:**
- Operators call `handleERC20Transfer` with `_value = 1000`; counterpart bridge mints/transfers 1000 counterpart tokens to Alice.

**Step 3 — Alice bridges back:**
- Alice locks 1000 counterpart tokens on the counterpart chain.
- Operators call `handleERC20Transfer` on the source chain with `_value = 1000`.
- Source bridge attempts `safeTransfer(Alice, 1000)` but holds only 989 → **revert**.

Alice's 1000 tokens are permanently inaccessible. With multiple users the deficit compounds: after N deposits of `_value = 1000, _feeLimit = 100`, the bridge is short `N × 11` tokens, and the last `⌈N × 11 / 1000⌉` withdrawers fail.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
