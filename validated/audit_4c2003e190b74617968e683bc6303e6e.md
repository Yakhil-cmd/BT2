### Title
Webhook signature verification authenticates the sending GitHub organization but not the target repository/commit acted upon, enabling cross-tenant status/stack forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a webhook against based on a field taken from the *same, untrusted* JSON body (`repository.owner.login` or `organization.login`), then hands the entire parsed payload to event handlers that key their side effects off a *different* field of that same body (`repository.full_name`, or in the case of `StatusHandler`, only a bare commit `sha` with no repository scoping at all). In a Shipit deployment configured for multiple GitHub organizations (a supported configuration, see `test/dummy/config/secrets_double_github_app.yml`), this breaks the binding: `organization that authenticated == repository/commit that is written`.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) [2](#0-1) 

The org used to pick `Shipit.github(organization: repository_owner)` — and therefore the `webhook_secret` used to compute the HMAC — is read from `params.dig('repository', 'owner', 'login')` inside the very payload whose authenticity is being checked. Since `verify_webhook_signature` HMACs the *whole* raw body with that org's secret, an attacker who legitimately controls a GitHub App installation for *one* configured organization (e.g. "OrgTwo" in `test/dummy/config/secrets_double_github_app.yml`) can freely construct **any** JSON body, set `repository.owner.login` to their own org so the correct secret is selected, and sign it correctly with their own, legitimately-known secret.

Downstream handlers, however, do not re-validate that `repository.owner.login` (used for auth) matches the repository actually being mutated:

- The base `Handler` resolves the target stacks purely from `repository.full_name` in the payload, independent of the authenticated org: [3](#0-2) 
- `PushHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler` all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a value fully controlled by the payload, not cross-checked against the authenticating org — and then call state-changing actions (`stack.sync_github`, `stack.archive!`, `stack.unarchive!`, `ReviewStackAdapter#find_or_create!`). [4](#0-3) [5](#0-4) 
- `StatusHandler` is worse: it does no repository scoping whatsoever, matching purely on commit `sha` across the entire installation and writing a GitHub status onto whatever `Commit` row happens to have that sha: [6](#0-5) 

So the equality that should hold — *the organization whose secret validated this signature* == *the repository (and its commits) the handler is about to mutate* — is never checked. Only the raw bytes are authenticated against the wrong identity source (an attacker-controlled field), not the target resource identity.

### Impact Explanation
An attacker who administers **any** GitHub organization onboarded to a shared, multi-org Shipit instance (this is an explicitly supported topology per `test/dummy/config/secrets_double_github_app.yml` / `config/secrets.development.shopify.yml`) can forge `status` (and `push`/`pull_request`) webhook deliveries — signed with their own legitimately-possessed `webhook_secret` — that target commits/repositories belonging to a *different* tenant organization on the same Shipit instance:
- Forging a `status` event with `state: "success"` for an arbitrary commit `sha` belonging to another organization's repository can mark a commit `deployable?` even though it never actually passed CI on GitHub, since `StatusHandler` performs no repository check and `Commit#deployable?`/CI-gating logic (`ci.require` in `shipit.yml`) relies on locally stored `Status` rows. This can enable an **unauthorized deploy** of a commit that should have been blocked by CI requirements.
- Forging `pull_request` `opened`/`labeled`/`unlabeled`/`reopened` events for another org's `repository.full_name` can archive/unarchive or provision review stacks belonging to that other tenant.
- Forging `push` events can trigger `stack.sync_github(expected_head_sha:)` against another tenant's stack.

This is a cross-repository/cross-organization trust boundary break directly analogous to the reported bug class: the check that gates an action (`verify_signature`, analogous to the withdraw-time check) is evaluated against the wrong quantity (an attacker-supplied field) rather than the quantity actually protected against forgery (the target repository/commit identity).

### Likelihood Explanation
Exploitability requires only that the Shipit deployment services more than one GitHub organization with the shared webhooks endpoint (a documented, supported configuration) and that the attacker administers or otherwise legitimately controls a GitHub App installation for at least one of those organizations — no theft of another tenant's secret, no privileged Shipit account, and no GitHub App private key are required. This is a realistic multi-tenant SaaS-style deployment scenario.

### Recommendation
After verifying the HMAC signature, cross-check that the organization/owner used to select the `webhook_secret` matches the owner of `repository.full_name` (and, for `status` events, that the commit's stack/repository belongs to that same organization) before dispatching to handlers. `StatusHandler` in particular should scope its `Commit` lookup by the authenticated repository, not by a bare `sha` alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`). `OrgOne/victim-repo` has a stack tracked in Shipit with `ci.require` configured.
2. Attacker legitimately controls the GitHub App / webhook secret for `OrgTwo`.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<sha of an unreviewed commit on OrgOne/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, body)>` themselves and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches `OrgTwo`'s legitimate secret, and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to `OrgOne/victim-repo`, and calls `commit.create_status_from_github!(params)`, marking it as passing CI in Shipit even though `repository.full_name` in the forged payload names an unrelated repo the attacker controls.
7. `OrgOne`'s stack may now consider the commit deployable/mergeable despite never having received a genuine passing CI status from GitHub.
