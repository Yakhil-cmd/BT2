### Title
Cross-organization webhook impersonation via unbound `repository.owner.login` vs `repository.full_name` fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). However, the handlers that actually act on the payload (`PushHandler`, all `PullRequest::*Handler`s, etc.) resolve the target repository/stack independently from `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so the HMAC only proves "this body was signed with OrgA's secret" — it proves nothing about which repository the body claims to target.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where several distinct GitHub organizations, each with its own `webhook_secret`, are configured on one Shipit instance: [1](#0-0) 

`WebhooksController#verify_signature` picks the org/secret to verify against using `repository_owner`: [2](#0-1) [3](#0-2) 

Once signature verification passes, `create` dispatches the *entire raw payload* — unfiltered — to the registered handlers for the event: [4](#0-3) 

Those handlers resolve the actual target repository from a *different* field, `repository.full_name`, which is never compared to the `repository.owner.login`/`organization.login` value used for signature selection: [5](#0-4) 

For example, `PushHandler` uses this `stacks` lookup (backed by `Repository.from_github_repo_name(repository.full_name)`) to trigger a sync on any matching, non-archived stack: [6](#0-5) [7](#0-6) 

**Binding broken:** `organization authenticated by HMAC (repository.owner.login / organization.login)` ≠ `repository whose stacks are written to (repository.full_name)`.

Before the attack, a member of legitimate tenant "OrgA" (who knows or can trigger a genuinely-signed webhook using OrgA's `webhook_secret`, configured for OrgA in `secrets.github`) can only affect stacks belonging to repositories under OrgA. After the attack, that same OrgA member crafts a payload where `repository.owner.login` (or `organization.login`) = `"OrgA"` but `repository.full_name` = `"OrgB/victim-repo"`, signs the raw body with OrgA's own secret, and POSTs it. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully because the HMAC matches OrgA's own secret over the (attacker-controlled) body — nothing ties the signature to `OrgB/victim-repo`. The `PushHandler` (or PR handlers) then acts on `OrgB/victim-repo`'s stacks, a repository the attacker's org has no legitimate authority over.

### Impact Explanation
This is a cross-tenant / cross-repository write: an entity that authenticated as OrgA can force actions (e.g., `stack.sync_github`, which fetches and appends new commits and — depending on the stack's continuous-deployment configuration — can lead to automatic deploys, or triggers review-stack provisioning/archival via the PR handlers) on repositories/stacks belonging to a completely different, unrelated organization (OrgB) hosted on the same Shipit instance. This falls under the "cross-repository writes / unauthorized deploy" Critical impact bucket, since the org boundary that the webhook_secret is supposed to enforce is bypassed entirely for the purpose of picking *what gets acted on*.

### Likelihood Explanation
High for any deployment using Shipit's documented multi-organization GitHub App configuration (multiple keys under `secrets.github`, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). Any member of one tenant org who can obtain or generate a valid signature for their own org (which is by design, since they control that org's GitHub App/webhook_secret) can immediately exploit this — no additional credentials, session, or privilege on the target org are required.

### Recommendation
After signature verification, validate that the organization derived from the verified signature (`repository_owner`) actually matches the owner segment of `repository.full_name` used by the handlers (and by extension the `Repository`/`Stack` looked up). Reject the request (422) if they diverge, so that a signature valid for OrgA can never be used to act on a repository whose `full_name` claims to belong to OrgB.

### Proof of Concept
1. Shipit is configured with two tenants, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and OrgB owns a Stack for `OrgB/victim-repo`.
2. Attacker (a legitimate OrgA member/admin) builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` using OrgA's own secret (which they legitimately possess/control) and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<...>
```
4. `WebhooksController#verify_signature` computes `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates the signature successfully against OrgA's secret — `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `create` dispatches the full payload to `PushHandler`, which resolves the target via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), finds `OrgB`'s stack, and calls `stack.sync_github(expected_head_sha: ...)` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), an action the OrgA attacker was never authorized to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
