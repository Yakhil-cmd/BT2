## Root cause

This is exactly the "organization that authenticated versus the repository that is written" analog called out in the rules.

`WebhooksController#verify_signature` picks the GitHub App/webhook secret to verify against using the *owner* field of the payload, falling back to the top-level `organization` object: [1](#0-0) [2](#0-1) 

Meanwhile, the actual event handlers resolve the *target* repository/stack to act on using an entirely different field of the same JSON body — `repository.full_name` — with no cross-check that it belongs to the org whose secret validated the signature: [3](#0-2) 

Notably, `StatusHandler` doesn't even scope by repository/stack at all — it just matches on bare commit SHA globally: [4](#0-3) [5](#0-4) 

## Why this matters

In a multi-org Shipit deployment (documented, supported configuration), each GitHub organization has its own independent `webhook_secret`: [6](#0-5) [7](#0-6) 

An attacker who legitimately controls one onboarded org's GitHub App (and thus knows *that* org's own `webhook_secret`, which is not the victim's secret and not excluded by the "requires webhook_secret" rule since it's their own credential for their own org) can sign an arbitrary JSON body with their own secret while setting `repository.owner.login` to their own org (so `verify_signature` picks their own — correctly verifying — app/secret) but setting `repository.full_name` (or a bare `sha` for the `status` event) to reference a completely different, victim organization's repository/commit.

Because `verify_signature` only checks "was this payload signed by *someone's* configured secret," and the handlers never re-validate that the resolved `repository.full_name`/`sha` actually belongs to the org that signed it, the attacker can:

- Forge a `status` event for an arbitrary commit SHA belonging to a *victim* stack, injecting a fabricated CI status (`success`) via `Commit#create_status_from_github!` → `Status.replicate_from_github!`. This flips the commit's CI state and can unblock the merge queue / continuous-deployment gating for a stack the attacker has no legitimate access to (`ProcessMergeRequestsJob`/`schedule_continuous_delivery` are triggered on status creation).
- Forge `push`/`check_suite` events referencing a victim's `repository.full_name` to trigger `GithubSyncJob`/`RefreshCheckRunsJob` against that victim stack.

This breaks the trust boundary: authentication is anchored to "org A signed this," but the write/action target is taken from an unrelated, unverified field, letting one org's credential act on another org's stack. This can enable an unauthorized deploy (via forged CI success unlocking continuous delivery/merge queue) — matching the Critical/High impact bar ("unauthorized deploy" / "cross-repository writes").

## Limitation

I could not fully trace how far `stack.enable_ci!` / `ProcessMergeRequestsJob` propagates into an actual unattended deploy without an existing merge-queue/CD configuration on the victim stack — that data-flow (continuous_deployment / merge_queue settings) would need to be confirmed in a live session, and the exact GitHub webhook payload shape for `status` events (whether `repository` is always present) should be re-verified against real GitHub webhook samples before treating this as certain in all configurations.

### Title
Cross-organization forgery of commit CI status and sync webhooks via mismatched signature/target-repository binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook against using `repository.owner.login` (or `organization.login`), but the webhook handlers (`StatusHandler`, `Handler#stacks` used by `PushHandler`/`CheckSuiteHandler`/pull-request handlers) resolve which commit/stack to act on from unrelated payload fields (`sha`, `repository.full_name`) without checking they belong to the same organization whose secret validated the request.

### Finding Description
In a multi-org Shipit installation, each org has an independently configured `webhook_secret`. The signature check only proves "the request body was HMAC-signed by whichever org's secret matches `repository.owner.login`/`organization.login`" — it does not bind that org to the specific repository/commit the handlers subsequently operate on. `Handler#stacks` uses `repository.full_name` to find the target `Repository`/`Stack`, and `StatusHandler` uses a bare `sha` to match `Commit` records across the whole instance, with no re-validation against the org that produced the valid signature.

### Impact Explanation
An org onboarded to the shared Shipit instance (holder of their own legitimate `webhook_secret`) can forge a payload signed with their own secret (`repository.owner.login` = their own org) while setting `repository.full_name` or `sha` to target a victim org's stack/commit. This allows forging a `success` CI status on a victim's commit, unblocking merge-queue/continuous-deployment gating and potentially causing an unauthorized deploy, or forcing sync/refresh jobs against a victim's stack — a cross-organization write achieved without possessing the victim's own webhook secret.

### Likelihood Explanation
Requires the attacker to be an administrator of at least one legitimate org already onboarded to a multi-org Shipit deployment (a realistic scenario for shared/managed Shipit instances serving multiple GitHub orgs), and knowledge of GitHub webhook payload shapes, both readily available.

### Recommendation
After signature verification, re-derive the "authenticated organization" and enforce that every repository/stack/commit acted upon by a handler actually belongs to that same organization (e.g., pass the verified organization into `Handler.call` and have `Handler#stacks`/`StatusHandler` scope lookups by `Repository.owner == verified_organization`).

### Proof of Concept
1. Attacker controls Org A's Shipit GitHub App installation and its `webhook_secret`.
2. Attacker crafts a `status` event JSON body: `{"sha": "<victim-stack-commit-sha>", "state": "success", "repository": {"owner": {"login": "orga"}, "full_name": "orga/somerepo"}}`.
3. Attacker computes `X-Hub-Signature` using Org A's own `webhook_secret` over this body.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches Org A's `GitHubApp`, and successfully verifies the signature (it is genuinely signed by Org A's secret).
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally (not scoped to Org A) and calls `create_status_from_github!`, creating a forged `success` status on the victim commit belonging to an entirely different organization's stack, triggering `ProcessMergeRequestsJob`/continuous delivery on that victim stack.
