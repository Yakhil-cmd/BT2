### Title
Cross-Organization Webhook Confusion via Mismatched `repository.owner.login` and `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a signature against using `repository.owner.login` (falling back to `organization.login`) extracted from the untrusted JSON body itself. However, once the signature is accepted, every event `Handler` (e.g. `PushHandler`) resolves the target `Repository`/`Stack` to mutate using a *different* field from the same payload: `repository.full_name` [1](#0-0) . Nothing in the code enforces that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same repository/organization. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
The signature check is:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
and
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
``` [3](#0-2) 

This picks the `GithubApp` config (and its `webhook_secret`) for the organization named in the payload's `repository.owner.login`. The HMAC (`verify_webhook_signature`) is computed over the *entire* raw body using that organization's secret [4](#0-3) , so it does cryptographically bind the whole JSON body, including `full_name`, to that specific secret. But an attacker who legitimately administers (and knows the webhook secret for) their own onboarded organization "attacker-org" in this same Shipit instance can construct any JSON body they like — including one where `repository.owner.login = "attacker-org"` (so the correct, attacker-known secret is used to sign it) while `repository.full_name = "victim-org/victim-repo"` (pointing at a completely different, unrelated stack in the same Shipit deployment).

Once `verify_signature` passes, `Handler#stacks` looks up the repository/stack to act on using only `full_name`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

For `PushHandler`, this means an attacker with valid credentials for one organization's webhook can trigger `stack.sync_github(expected_head_sha: ...)` [5](#0-4)  against a `victim-org/victim-repo` stack that belongs to a completely different organization/customer boundary they were never granted access to, forcing that stack to sync to an attacker-chosen `after` SHA.

### Impact Explanation
This crosses a repository/organization trust boundary that the signature verification is nominally supposed to enforce: an actor who is only entitled to send authenticated webhooks for organization A can cause write-side effects (forced GitHub sync, membership/team churn via `MembershipHandler`, or PR/label state changes for repositories) against stacks belonging to organization B, purely by putting B's `full_name` in an A-signed payload. This matches the "cross-repository writes" impact class, since the effective object acted upon (`Stack`/`Repository` B) is disjoint from the object whose credential/secret authorized the request (organization A).

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate operator/admin of *some* organization already onboarded to the same Shipit deployment (i.e., knows or can rotate that org's `webhook_secret` in its own GitHub App/organization settings) — no access to the victim organization's secrets, tokens, or repository is required. In any multi-tenant Shipit deployment (multiple `Shipit.github(organization: ...)` configs), this is a low-effort forgery: craft a JSON body with mismatched `repository.owner.login` vs `repository.full_name`, sign it with the known secret, and POST to `/github/webhooks`.

### Recommendation
Do not select the verification secret from an attacker-controlled JSON field without cross-checking it against the object being mutated. Concretely:
- After parsing, verify that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` (and matches `organization.login` when present) before dispatching to any handler; reject on mismatch.
- Alternatively, resolve the target `Repository`/`Stack` using the same organization identity that produced a valid signature (`repository_owner`), not an independently attacker-suppliable `full_name` field, so the two can never diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App config/`webhook_secret` (`config.github_apps` / `Shipit.github`).
2. Attacker, an admin of `attacker-org`, knows `attacker-org`'s `webhook_secret` (it is configured on GitHub's webhook delivery settings for repos under their own control).
3. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, raw_body)>` and POSTs it to `WebhooksController#create` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully [3](#0-2) .
6. `PushHandler.call(params)` runs, resolving `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [1](#0-0)  and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [5](#0-4) , even though the attacker never authenticated as, nor holds any secret for, `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
