### Title
Headers/witnessing commissions redirected to an AA address are permanently frozen because AA balance accounting never includes `headers_commission_outputs`/`witnessing_outputs` - (File: aa_composer.js, validation.js)

### Summary
`earned_headers_commission_recipients` lets a unit's author redirect the unit's earned headers commission to an arbitrary valid address, with no restriction against that address being an Autonomous Agent (AA). The commission is credited to the recipient in `headers_commission_outputs` (and analogously `witnessing_outputs` for paid witnessing) tables, spendable only via `type:"headers_commission"`/`type:"witnessing"` payment inputs. AAs are explicitly disallowed from using these input types, and AA balance bookkeeping (`aa_balances` table / `balance[...]` formula) is derived solely from the `outputs` table, never from the commission tables. Consequently, bytes routed to an AA this way become permanently stuck: unspendable by the AA (blocked input type) and invisible to the AA's own balance accounting (missing from the aggregation), mirroring the BunniSupply defect where one aggregation path includes accrued fees and the parallel path silently drops them.

### Finding Description
1. `validateHeadersCommissionRecipients` in `validation.js` (lines 1101-1126) validates only the syntax/sum of `earned_headers_commission_recipients` — checksum validity of `recipient.address` and that shares total 100% — with no check that `recipient.address` is not an AA address: [1](#0-0) 

2. When a unit becomes the "winning" child for headers commission, `headers_commission.js`'s `calcHeadersCommissions` distributes the commission to whatever address is named as recipient (including an AA address) and inserts it into `headers_commission_outputs`: [2](#0-1) 

3. Base-asset payment inputs of type `headers_commission`/`witnessing` are categorically rejected when the spender is an AA: [3](#0-2) 

4. AA balance state (`aa_balances`, `objValidationState.assocBalances`, and the `balance[...]` formula primitive) is populated exclusively from the `outputs` table — never from `headers_commission_outputs`/`witnessing_outputs`: [4](#0-3) [5](#0-4) [6](#0-5) 

5. The invariant-checking routine `checkBalances` (used by nodes to sanity-check `aa_balances` vs actual outputs) also sums only the `outputs` table, so this silent loss is not detected as a consistency error either: [7](#0-6) 

This is structurally identical to the BunniSupply bug: two supposedly-equivalent totals (spendable/real holdings vs. the value used by downstream logic) diverge because one path omits an accrued-fee/commission component, and here that omission additionally makes the funds unrecoverable rather than merely under-reported.

### Impact Explanation
Any unpriviledged user composing and posting an ordinary unit can specify `earned_headers_commission_recipients` (mandatory syntax already supported for multi-authored units, and accepted even for single-authored ones per the allowed-fields list in the top-level unit validation) that names an AA address as recipient. If that unit ever wins the headers-commission race (a routine, permissionless DAG event — essentially any unit can become a "best child"), the AA permanently receives bytes it can never move: the AA's oscript logic cannot see this balance (its `balance[base]` formula and financial decisions ignore it), and the AA cannot construct a spending input of type `headers_commission`/`witnessing` even if it tried, because such input types are forbidden for AA-authored units. The same reasoning applies to `witnessing` commissions for witnesses. The result is genuine, irrecoverable "AA fund loss/freezing" — an attacker (or even an innocent user) can lock protocol bytes at any AA address at will, and this can also be weaponized to grief a specific financial AA by starving/confusing its balance-dependent formulas (e.g., AAs computing exchange rates or payouts from `balance[base]`) since the actual DB-visible spendable total at that address (real bytes sitting in `headers_commission_outputs`) is inconsistent with what the AA's own model believes it owns.

### Likelihood Explanation
The trigger requires no special privilege: composing a unit with `earned_headers_commission_recipients` pointing at a known AA address is a standard, permissionless wallet operation (`composer.js`/`writer.js` already handle this field generically), and headers-commission distribution to an arbitrary "winning" unit happens automatically and continuously as part of normal DAG stabilization (`main_chain.js` calls `calcHeadersCommissions` on every stabilized MCI). No race condition, no special timing, and no cooperation from the AA definer is needed — likelihood is high.

### Recommendation
In `validateHeadersCommissionRecipients` (and the analogous acceptance of `address` for `witnessing` inputs/recipients), reject any recipient address that is a registered AA address (query `aa_addresses`), mirroring the existing `checkNotAAs` pattern used elsewhere in `validation.js` for OP lists. Alternatively/additionally, extend AA balance accounting (`insertAADefinitions`, `updateInitialAABalances`/`updateFinalAABalances`, and the `balance[...]` formula primitive) to also aggregate `headers_commission_outputs` and `witnessing_outputs` for AA addresses, and allow AAs to spend such inputs so that, if ever received, the funds are not unconditionally frozen.

### Proof of Concept
1. User composes and signs an ordinary (non-AA) unit whose `payload.outputs`/messages are unrelated to any AA, but includes `earned_headers_commission_recipients: [{address: <AA_ADDRESS>, earned_headers_commission_share: 100}]` (valid checksum, single recipient, share = 100, so it passes `validateHeadersCommissionRecipients`).
2. The unit is broadcast and eventually stabilizes; if it is selected as the "winning" child of some parent unit during `calcHeadersCommissions` (`headers_commission.js`), the parent's headers commission is credited to `<AA_ADDRESS>` in `headers_commission_outputs`.
3. Verify: `aa_balances` for `<AA_ADDRESS>` (and `balance[base]` inside any of its formulas) never reflects this amount, because it's sourced only from `outputs`.
4. Attempt to have the AA construct any payment message with an input of `type: "headers_commission"` for that mci range — rejected by `validation.js` line 2531 (`objValidationState.bAA` guard) whenever the unit is AA-authored, and no other ocore code path lets an AA claim `headers_commission_outputs`. The bytes remain permanently locked at the AA address.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
