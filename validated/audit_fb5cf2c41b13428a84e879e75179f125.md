### Title
StatusHandler#process applies GitHub status payloads to any commit sharing a SHA across all stacks, without verifying the commit's repository matches the webhook's authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and writes attacker-controlled `description`/`target_url`/`context`/`state` strings from the webhook payload onto every matching commit, regardless of which stack/repository that commit belongs to. Unlike the base `Handler` class, which exposes a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)`), `StatusHandler` never uses it, so the binding "the repository that authenticated the webhook == the repository whose commit's status is mutated" is never enforced.

### Finding Description
The claimed binding, stated explicitly:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row updated by a `status` webhook.

Tracing the code:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to handlers for the event type after `verify_signature`, which validates the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e., it authenticates that the payload legitimately originated from GitHub for the org identified by `repository_owner` in the payload. [1](#0-0) [2](#0-1) 
- Verification only proves the payload came from GitHub for *some* repository/org identified inside the payload itself (`repository_owner`) — it never binds the payload content to a specific `Stack`/`Commit` scope.
- `StatusHandler#process` accepts `sha`, `state`, `description`, `target_url`, `context` with no allow-list/format validation beyond `String`, and then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This query is **global** — it is not scoped to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, unlike the `stacks`/`repository_name` helper defined on the base `Handler` class that other handlers (e.g. pull-request handlers) do use. [4](#0-3) 
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which persists the attacker-chosen `description`, `target_url`, `context` verbatim, keyed only by the commit's own `stack_id` (the victim stack, since the `Commit` row itself belongs to Stack A) — not by any repository check against the webhook's source. [5](#0-4) [6](#0-5) 
- `Commit#status` (used throughout the UI/API for CI status display) simply groups all `statuses`/`check_runs` on the commit, so any status row written this way is surfaced to Stack A's legitimate operators as if it were CI state for Stack A. [7](#0-6) 

Root cause: `StatusHandler` is the only handler among those inspected that ignores the repository-scoping helper (`stacks`) provided by the base class and instead resolves target `Commit` rows purely by `sha`, a value that is not unique per repository — SHA-1 commit hashes are shared across any repositories with common ancestry (forks, mirrors, subtree merges), and Shipit does not require the sha match to also match the repository. An attacker who owns a fork (or any repository sharing history/SHAs with the victim's repository) — a low-cost, unprivileged action — can trigger a legitimate, correctly-signed `status` webhook from that fork's own CI (or a self-hosted GitHub App/webhook on their own repo/org, which is verified via `Shipit.github(organization: repository_owner)` for *their own* org, not the victim's) carrying arbitrary `description`/`target_url`/`context` for a shared SHA, which Shipit will apply to the victim commit in Stack A.

None of the listed guards prevent this: `verify_signature` authenticates the sender's own org/repo, not the target stack; `drop_unhandled_event` only filters event types; the `ExplicitParameters` schema only validates types (`String`), not content or repo binding; there is no `require_permission!`/`stacks` scope check inside `StatusHandler#process` at all.

### Impact Explanation
An attacker with a repository sharing commit SHAs with a victim's Shipit-tracked repository (typical for forks) can write attacker-chosen `description`, `target_url`, and `context` strings into Status rows attached to the victim Stack A's commits. These are rendered to Stack A's legitimate operators in the Shipit UI/API as CI status detail (link/description/context), i.e., stored content injection sourced from an unrelated, unauthorized repository into a victim tenant's CI status display. This is a cross-tenant write: a payload from Repository B mutates a record (`Status`) tied to Stack A, which did not authenticate that webhook. This matches the "payload for one repository mutating another's stack/commit" Critical category, scoped specifically to the `Status` record (not to Task/Deploy execution) — the blast radius is limited to CI-status metadata display (`description`/`target_url`/`context`/`state`), not to command execution or secret exfiltration.

### Likelihood Explanation
Requires: (1) a `Stack` in the victim's Shipit instance tracking a repository that shares git history/SHAs with a repository the attacker controls (e.g., attacker forks the victim's repository — a normal, unprivileged GitHub action), and (2) the attacker's fork/org having its own valid webhook signing configuration recognized by `Shipit.github(organization: repository_owner)` (feasible if the attacker's fork lives under an org/user for which Shipit has any registered GitHub App/webhook secret, or if the attacker runs their own CI that posts a `status` for a SHA also present in the victim stack). Cost is low and the attack is repeatable for every shared SHA (e.g., every commit prior to the fork point, or common upstream commits), across arbitrary stacks that happen to share history with attacker-reachable repositories.

### Recommendation
Scope `StatusHandler#process` (and verify all other handlers) to only update commits belonging to the repository that authenticated the webhook, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks`/`repository_name` helper from the base `Handler` class, so the binding `commit.stack.repository == payload repository` is enforced before any `Status` row is written.

### Proof of Concept
Minitest plan (model-level, no live GitHub):
1. Create `repository_a` ("victim/repo") with `stack_a` and a `commit` with `sha: "deadbeef" * 5` belonging to `stack_a`.
2. Create `repository_b` ("attacker/fork") with `stack_b` and a `commit` with the **same** `sha` belonging to `stack_b` (simulating shared git history from a fork).
3. Build a `status` webhook payload with `repository.full_name = "attacker/fork"`, `sha` matching, and `description`/`target_url` set to attacker-chosen strings (e.g. `"PWNED"` / `"https://evil.example/x"`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as it's out of scope for the handler-level unit test).
5. Assert: `stack_a.commits.find_by(sha: sha).status.description == "PWNED"` and `.target_url == "https://evil.example/x"` — i.e., Stack A's commit, which belongs to `repository_a` (never involved in the webhook payload), now exposes the attacker-supplied content, proving `commit.stack.repository.full_name != payload.dig('repository','full_name')` while the write still succeeded.
