### Title
Cross-organization forged commit status via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController` authenticates a webhook only against the *organization* implied by the payload's `repository.owner.login` (or `organization.login`) field, using that organization's `webhook_secret` [1](#0-0) . Every other handler then re-derives the target repository/stack from the payload's `repository.full_name` before touching any data, e.g. `Handler#stacks` / `Handler#repository_name` [2](#0-1)  and `CheckSuiteHandler#process` [3](#0-2) . `StatusHandler`, however, ignores the `repository` field entirely and looks up commits **globally by SHA only**, across every repository tracked by the Shipit instance: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .

### Finding Description
The equality this engine relies on is: **organization that authenticated the webhook == repository/stack that gets written**. This holds for `PushHandler`, `CheckSuiteHandler`, and the pull-request handlers, which all scope their side effects through `Repository.from_github_repo_name(params.repository.full_name)` before mutating anything [5](#0-4) .

`StatusHandler` breaks this equality: it never consults `repository.full_name` and instead resolves the target purely by git SHA, which is a property of commit content, not of any particular repository or organization. Because SHA-1 identifiers for a commit are computed from its tree, parents, author/committer, message and timestamps — not from which GitHub repository hosts it — the *same* SHA can legitimately exist as a `Commit` row for two completely unrelated stacks tracked by the same Shipit instance (e.g., forked repositories, shared history, cherry-picked/rebased commits, or an attacker deliberately reproducing a target commit's exact tree+metadata in their own repository).

An attacker who is a legitimate admin of Organization A (with its own valid, properly signed GitHub webhook feed into this Shipit instance) can:
1. Discover or reproduce a commit SHA that also exists as a tracked `Commit` in an unrelated Organization B's stack (the SHA is public information visible in Shipit's UI/API for any stack).
2. Push a commit with an identical SHA in their own Organization A repository (trivial if the exact tree/parents/author/committer/message/timestamp are known — realistic for shared ancestry or content-only repos), triggering a real, GitHub-signed `status` webhook for Organization A.
3. `WebhooksController#verify_signature` succeeds because the signature is validated against Organization A's own webhook secret via `repository_owner` [6](#0-5) .
4. `StatusHandler#process` then applies the forged status to **any** `Commit` row in the entire database matching that SHA, including Organization B's commit, via `commit.create_status_from_github!(params)` — with attacker-controlled `state`, `context`, `description`, and `target_url` [7](#0-6) .

This is a cross-repository/cross-organization write: an actor authenticated only for Organization A's webhook feed is able to write CI/commit-status data onto Organization B's stack that they have no authorization over.

### Impact Explanation
Commit statuses in Shipit gate deploy eligibility (`deployable_status`, referenced as one of the `Hook::EVENTS` and used by stack deployability checks). Forging a `success` status onto a victim commit that legitimately has failing/pending CI can make an otherwise non-deployable commit appear deployable to Shipit's UI/automation, enabling an unauthorized deploy of that commit on the victim organization's stack — this falls squarely in the "Critical: cross-repository writes / unauthorized deploy" impact bucket. At minimum it is a cross-repository, cross-organization data write (forged CI status) performed by an actor with no authorization over the target repository.

### Likelihood Explanation
The precondition (attacker legitimately controls one organization/webhook feed on the shared Shipit instance and can produce/discover a colliding SHA with a target organization's tracked commit) is realistic in any multi-tenant Shipit deployment serving several organizations (as the engine explicitly supports via per-organization GitHub App configuration, see `test/dummy/config/secrets_double_github_app.yml`). No secrets, tokens, or elevated Shipit permissions are required beyond what the attacker already legitimately has for their own organization.

### Recommendation
`StatusHandler#process` must scope its `Commit` lookup by the repository identified in the payload (`params.repository.full_name`), the same way `PushHandler`/`CheckSuiteHandler`/the PR handlers do via `Handler#stacks` / `Repository.from_github_repo_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
and the `status` handler's `params` block should `require :repository { require :full_name, String }` as the other handlers do.

### Proof of Concept
1. Org A operates its own GitHub App integration with this shared Shipit instance and receives valid `status` webhooks signed with Org A's `webhook_secret`.
2. Attacker (an Org A admin) identifies a public commit SHA `S` that Shipit already tracks for Org B's stack (visible via Shipit UI/API).
3. Attacker reproduces a commit with identical SHA `S` in an Org A repository (feasible when tree/parents/metadata are reproducible, e.g. via shared history or content-identical commit crafting) and pushes it, or otherwise triggers GitHub to emit a `status` event for SHA `S` under Org A.
4. GitHub signs the webhook with Org A's `webhook_secret`; POST hits `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = "OrgA" and validates successfully against Org A's secret [6](#0-5) .
6. `StatusHandler#process` executes `Commit.where(sha: 'S')`, which returns Org B's `Commit` row too, and calls `create_status_from_github!` on it with attacker-supplied `state: 'success'`, writing a forged status onto Org B's stack despite the request only ever having been authenticated for Org A [4](#0-3) .
