### Title
Missing cosigner/ownership check lets any paired correspondent trigger a signing request for a local address — analog of CVE-2020-10689 - (File: wallet.js)

### Summary
CVE-2020-10689 describes Eclipse Che failing to restrict access to another user's workspace pod: an authenticated peer who merely knows an identifier (service name/namespace) can bypass the intended authorization proxy and reach a resource that should be restricted to its owner. The comparable bug class in `ocore` — "authenticated principal reaches another principal's protected resource because an ownership/authorization check was disabled or never enforced" — is present in the `"sign"` message handler in `wallet.js`, where the check that the requester is actually a cosigner of the target address was deliberately commented out.

### Finding Description
The `"sign"` subject handler in `handleMessageFromHub` (`wallet.js`) is reachable from any *paired correspondent device* (an "authenticated" peer in the device-messaging sense — it has completed device pairing/login, but is not necessarily a wallet cosigner). The handler resolves the target `body.address` via `findAddress()` and, in the `ifLocal` branch (the address is hosted on this device), immediately fires the `"signing_request"` event for the wallet UI to act on — without verifying that `from_address` is actually one of the address's registered signers: [1](#0-0) 

The code explicitly documents that the ownership check was intentionally removed: [2](#0-1) 

By contrast, the `ifRemote` branch (used for multi-device shared addresses) *does* enforce that the sender is one of the address's registered co-signer devices before forwarding/acting on a signing request: [3](#0-2) 

This asymmetry is the root cause: for any address whose full key material is hosted on the receiving device (`ifLocal`), the "proxy" check that should confirm the caller is authorized to request a signature over that address is missing, exactly analogous to Che's JWT proxy failing to confirm the caller owns the target pod. Any device that has been paired with the victim (a very low bar — a `pairing_secret` obtained once, or even a permanent pairing secret, see `handlePairingMessage` in `device.js`) can send a `"sign"` message naming an address it does not co-own and force `signing_request` to fire with attacker-controlled `objUnit`/outputs/amounts: [4](#0-3) 

### Impact Explanation
`signing_request` is the event the wallet UI/bot listens on to display a confirmation dialog (or, for automated/bot wallets and headless signers, to auto-sign) for spending from the local address. Because the sender-authorization check is disabled, any paired correspondent (not just a legitimate co-signer) can craft `body.unsigned_unit` with arbitrary outputs/amounts and force this dialog/flow to appear as if it were a legitimate signing coordination request from a real co-signer. For headless/automated wallets or bots that trust `signing_request` inputs based on the message reaching this point without an authorization failure, this can lead to unauthorized signing (loss of funds) or at minimum a spoofed/confusing signing flow that a user could be tricked into approving, since the code path deliberately skips the check needed to prove the sender is an authorized cosigner of the spending address.

### Likelihood Explanation
Reaching this code only requires: (1) pairing with the victim device — achievable via a normal (or, if the victim uses a permanent pairing secret, even simpler) pairing exchange handled by `handlePairingMessage`, and (2) sending a `"sign"` message naming any address the victim's wallet controls, which is knowable from any prior transaction/correspondence with that address. No cryptographic secret of the victim needs to be known — only the address, matching the CVE's requirement of "knowledge of the service name and namespace" being sufficient to reach the restricted resource.

### Recommendation
Re-enable (or otherwise restore) an authorization check in the `ifLocal` branch of the `"sign"` handler verifying that `from_address` is actually a registered co-signer/device for `body.address` and `body.signing_path` (e.g., via `wallet_signing_paths` or `shared_address_signing_paths`) before emitting `signing_request`. If multilateral signing intentionally needs support for correspondents that are not registered cosigners, gate that flow behind an explicit, narrower check (e.g., require the address to be part of a shared/multilateral definition and the correspondent be a party to that specific definition) rather than removing the check entirely.

### Proof of Concept
1. Attacker device pairs with victim's wallet device via `device.js`'s pairing exchange (`handlePairingMessage`), becoming a "correspondent."
2. Attacker learns (or already knows) `address` — a base32 address hosted locally on the victim's wallet (from a shared invoice, prior chat, or public unit history).
3. Attacker sends a device message: `{subject: "sign", body: {address: address, signing_path: "r", unsigned_unit: {authors: [{address}], messages: [...attacker-chosen outputs...]}}}`.
4. In `wallet.js`, `findAddress` resolves the address as local (`ifLocal`), and because the cosigner-ownership check (lines 336–338) is commented out, `callbacks.ifOk()` is called and `signing_request` is emitted with the attacker's crafted unit — despite the attacker never being verified as an authorized signer for that address.
