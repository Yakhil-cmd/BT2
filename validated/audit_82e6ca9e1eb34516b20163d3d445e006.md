### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but every event handler acts on the org/repo derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves which `Repository`/`Stack` to mutate using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together cryptographically or logically once the request reaches the handlers.

### Finding Description
`verify_signature` selects the HMAC secret to validate against solely from `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

Because Shipit supports multiple configured GitHub Apps/organizations (`Shipit.github(organization: ...)`), each with its own `webhook_secret` (see `config/secrets.*.yml` examples with `OrgOne`/`OrgTwo`, `somegithuborg`/`someothergithuborg`), an attacker who has legitimate control of one configured organization (e.g. as an admin of their own GitHub org/App installation, which the docs treat as an "unprivileged" setup action, not an authenticated Shipit session) knows that org's `webhook_secret` and can therefore compute a valid `X-Hub-Signature` for *any* raw JSON body of their choosing, as long as `repository.owner.login` in that body equals their own org name: [3](#0-2) 

Once signature verification passes, `WebhooksController#create` dispatches the entire attacker-controlled body to the registered handler(s): [4](#0-3) 

But the handlers never re-check `repository.owner.login`. Instead, the base `Handler` class and every subclass resolve the target `Repository`/`Stack` using `repository.full_name`, a sibling field inside the same attacker-controlled `repository` object that is not tied to `repository.owner.login` in any way at signature-verification time: [5](#0-4) [6](#0-5) 

This means the binding `verified_org(repository.owner.login) == acted_upon_repo(repository.full_name)` is never enforced. An attacker who legitimately owns/administers `orgA` (and therefore its `webhook_secret`) can craft a raw JSON body with `repository.owner.login = "orgA"` (so the signature check picks and passes `orgA`'s secret) while setting `repository.full_name = "victim-org/private-repo"` — a repository that Shipit has configured under a completely different organization/App/secret. The signature is computed over the raw body bytes as a whole, so the attacker (who fully controls the body since they know the secret used to sign it) can put any value they want in `full_name`.

Concretely:
- `PushHandler#process` calls `Repository.from_github_repo_name(repository_name)` (derived from `full_name`) and then `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch: [7](#0-6) 
- `PullRequest::ClosedHandler` (and the sibling opened/labeled/reopened/unlabeled handlers) resolve `repository` the same way and call `review_stack.archive!`/provisioning actions on whatever stack matches `full_name`: [8](#0-7) 
- `StatusHandler` matches commits purely by `sha` globally (no repo scoping at all), letting the attacker inject arbitrary CI status/build state for any commit sha they can guess/know, from anywhere: [9](#0-8) 

### Impact Explanation
This breaks the intended trust boundary between GitHub organizations configured in the same Shipit instance: an entity that only controls one org's webhook secret can forge events that are attributed to (and acted upon) a completely different org's repositories/stacks. Via `PushHandler`, this can force `Stack#sync_github` to run against an attacker-chosen `expected_head_sha` for a victim's stack, and other handlers can archive review stacks, or inject fabricated CI statuses on arbitrary commits. Depending on the deploy/merge automation wired to these state transitions (sync, statuses, review-stack lifecycle), this can lead to an unauthorized deploy/rollback/merge decision being made for a repository the attacker does not control — matching the "authenticated organization vs. repository actually written" trust-binding break called out in scope.

### Likelihood Explanation
Requires only that the attacker control one legitimately configured GitHub App organization on the same Shipit instance (multi-org deployments are explicitly documented/supported, see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), and that a target stack for a different organization exists on the same instance. No Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed — only knowledge of one's own org's `webhook_secret`, which the attacker set up themselves.

### Recommendation
In `WebhooksController#verify_signature`/`create`, and in `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, enforce that the organization used to select/verify the webhook secret matches the owner of the repository actually being acted upon (e.g., compare `repository.owner.login` against the owner portion of `repository.full_name`, and reject the payload if they differ instead of silently trusting `full_name`).

### Proof of Concept
1. Attacker creates/administers `orgA`'s GitHub App on the shared Shipit instance and thus knows `orgA`'s `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "orgA"`, loads `Shipit.github(organization: "orgA")`, verifies successfully.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/private-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, despite the request never being signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
