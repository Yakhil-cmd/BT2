### Title
AA Payment Messages for Fixed-Denomination (Indivisible) Assets Are Silently Dropped, Permanently Trapping Received Indivisible-Asset Funds in the AA - (File: aa_composer.js)

### Summary
`handleTrigger`'s `sendUnit` logic in `aa_composer.js` unconditionally strips out any outgoing `payment` message whose asset is `fixed_denominations` (an indivisible asset) before composing the AA's response unit. Any oscript logic that tries to forward, refund, or swap an indivisible asset that the AA received is silently discarded rather than failing the trigger, so the received coins are absorbed into the AA's balance with no code path that can ever spend them back out via a `payment` message.

### Finding Description
When an AA is triggered, `sendUnit` iterates over the messages produced by `evaluateAA` and, for asset payments, looks up the asset's properties: [1](#0-0) 

If `objAsset.fixed_denominations` is true, the message is simply passed through (`return cb()`) without ever calling `completePaymentPayload` to populate `inputs`. Later, after the first pass, all payment messages referencing a fixed-denominations asset are filtered out entirely: [2](#0-1) 

There is no analogous exemption anywhere for basic bytes or divisible assets — those go through `completePaymentPayload`, which selects UTXOs, builds `inputs`, and produces a valid spend. For fixed-denomination assets, that pipeline is never invoked, and the message is dropped instead of causing a bounce or an error. `handleSuccessfulEmptyResponseUnit` is invoked when no messages survive, meaning the trigger is accepted and any state changes are committed — the indivisible-asset coins the trigger sent to the AA remain in the AA's balance/address as `is_spent=0` outputs, but the AA can never construct a valid indivisible-asset payment to move them, because every attempt is filtered before the unit is even assembled.

This mirrors the reported bug class: a token type (indivisible/fixed-denomination asset) is accepted as valid "funding" of a contract-like entity (the AA) via the exact same generic asset-payment mechanism used for other assets (the equivalent of the implicit ERC20 whitelist check succeeding), but the payout code path assumes a different type of asset transfer and silently cannot execute the corresponding withdrawal (the equivalent of `safeTransfer` reverting on an NFT). The result is the same: funds that got into the contract cannot get back out, i.e., a DoS/freeze of a specific class of assets, triggered purely by an ordinary unprivileged unit author sending a payment to the AA and by the AA author writing (or being tricked into writing/using) an oscript payment message for that asset.

### Impact Explanation
Any indivisible asset sent to an AA address as part of a trigger, when the AA logic intends to forward, swap, or refund it via a `payment` message, is permanently and silently trapped:
- The AA never bounces, never errors, and never surfaces the failure to the sender or the AA author — the response unit is generated as if nothing was wrong, with `handleSuccessfulEmptyResponseUnit`/no payment message for that asset.
- Every subsequent attempt to send this class of asset out of the AA fails the same way, because the drop is unconditional on `fixed_denominations`, not on any parameter or fee condition that a user could work around.
- Any DeFi-style AA that is designed to accept and later relay an indivisible NFT-like asset (e.g., an escrow, marketplace, or asset-swap AA) loses those funds permanently the moment a user funds it with such an asset — a direct case of AA fund freezing/loss reachable by any unprivileged unit poster who simply sends the asset to the AA.

### Likelihood Explanation
This triggers deterministically, with no race condition or special permission needed. Any unprivileged wallet holding a fixed-denomination asset can send it to an AA address whose bounce_fees/logic expects to route or forward that asset. The condition only depends on the asset property `fixed_denominations` being true (this is set at asset-definition time and is visible/queryable, so exploitation or accidental triggering is trivial and reproducible on every trigger involving that asset).

### Recommendation
Do not silently drop payment messages for fixed-denomination assets. Either:
1. Implement full support for composing indivisible-asset payment payloads inside `sendUnit`/`completePaymentPayload` (selecting exact-denomination coins similar to `pickIndivisibleCoinsForAmount` in `indivisible_asset.js`), so AAs can actually forward such assets, or
2. If indivisible-asset payments from AAs remain unsupported by design, make the AA definition/validation stage (`aa_validation.js`, case `'payment'`) reject any static reference to a known fixed-denomination asset in an AA's `messages`, and bounce the trigger with an explicit error at runtime (instead of silently succeeding) whenever a `fixed_denominations` asset ends up in the outgoing message list, so senders are not misled into believing the AA can hold/relay/return such funds.

### Proof of Concept
1. Define an indivisible asset A with `fixed_denominations: true` (e.g., via an `asset` message with `denominations`).
2. Deploy an AA whose `messages` include a `payment` message forwarding whatever `asset` was received in the trigger back to `trigger.address` (a generic "echo"/relay AA), e.g.:
```
messages: [
  { app: 'payment', payload: { asset: "{trigger.data.asset}", outputs: [{ address: "{trigger.address}", amount: "{trigger.output[[asset=trigger.data.asset]]}" }] } }
]
```
3. Send a trigger unit that pays some units of asset A to the AA (an ordinary, unprivileged unit).
4. Observe in `sendUnit` (`aa_composer.js` lines 1323-1361) that the payment message for asset A is retained through the first pass (line 1327-1328, since `fixed_denominations` is true) but then filtered out entirely in the second pass (line 1356), causing `messages.length === 0` and a normal (non-bounced) response with no payment of asset A ever sent — `handleSuccessfulEmptyResponseUnit` fires and the trigger is treated as successfully processed.
5. Confirm on-chain that the asset A outputs sent by the user remain owned by the AA address (`is_spent=0`), and any further identical trigger repeats step 4 indefinitely — the asset can never be paid out of the AA via any `payment` message.
