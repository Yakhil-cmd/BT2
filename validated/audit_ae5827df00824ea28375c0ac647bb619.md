**Analysis:** The premise of the question doesn't hold up against the actual code. `BITMAP_NUM_OF_BYTES` is 4 bytes = 32 bits, and `MAX_NUM_OF_KEYS` is exactly 32 [1](#0-0) . Since bit indices in a 4-byte bitmap range from 0 to 31 inclusive (32 total positions), and `MAX_NUM_OF_KEYS = 32` means valid key indices are also 0 to 31, there is no "bit position >= MAX_NUM_OF_KEYS but within the 4-byte array" — the entire 32-bit bitmap space is exactly and fully covered by the valid key-index range. There's no spare/unchecked bit space to exploit.

Additionally, even setting aside the arithmetic identity, the actual verification path bounds-checks the bitmap against the real number of supplied public keys at authenticator-verification time, not just against `MAX_NUM_OF_KEYS`: `verify_arbitrary_msg` rejects the signature if the last set bit is `>= public_key.public_keys.len()` [2](#0-1) , and it also requires the number of one-bits to equal both the signature count and to meet the threshold [3](#0-2) . During signature verification, each bit position is mapped via `public_key.public_keys.get(bitmap_index)` with an explicit out-of-bounds check [4](#0-3) . So even a signature bitmap that passed `try_from`'s bounds/popcount checks [5](#0-4)  cannot desynchronize indices from the actual public-key vector at verification time — any bit beyond the real key count is rejected there.

Thus there is no unprivileged path where a bitmap set beyond `MAX_NUM_OF_KEYS` (or beyond the actual public key count) is silently accepted; both `try_from` and `verify_arbitrary_msg` converge on rejecting such inputs.
