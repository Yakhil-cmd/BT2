The premise doesn't hold up against the actual code. `feature_version` in `StandardGasMeter` is derived from the on-chain gas schedule / feature version, which is a network-wide governance-controlled parameter shared by all transactions at a given point in time — it is not something an unprivileged transaction sender can set or influence per-transaction. `charge_slh_dsa_sha2_128s` follows the exact same version-gating pattern already used elsewhere in the same function for `charge_keyless` (gated on `RELEASE_V1_12`) and `charge_encrypted_txn_decryption` (gated on `RELEASE_V1_45`) — this is the standard, intentional mechanism for rolling out new gas charges without breaking replay of historical transactions. [1](#0-0) 

There is also no "public-key-binding cost model" or "5x ed25519 surcharge" concept present anywhere in the codebase tied to SLH-DSA gas charging — the only cost parameter is a flat `slh_dsa_sha2_128s_base_cost` gated the same way. [2](#0-1) 

The current `LATEST_GAS_FEATURE_VERSION` is `RELEASE_V1_50` (54), well past `RELEASE_V1_41` (45), so on any live network the surcharge is always charged; a version below `RELEASE_V1_41` only ever applies during replay/verification of old historical transactions committed before that feature was activated, not to newly admitted transactions from an unprivileged sender today. [3](#0-2) 

Since the feature version isn't attacker-controlled input and this is consistent, intentional versioned-gas-charging design (not a sender/signer/replay/domain binding issue in admission), this does not meet the bar for the admission exploit gate.
