### Title
`is_valid_sig` / `is_valid_signed_package` oscript primitives allow front-running/replay of signed authorization messages by any AA trigger sender - (File: formula/evaluation.js)

### Summary
The AA (Autonomous Agent) oscript language exposes two primitives, `is_valid_sig` and `is_valid_signed_package`, that let an AA verify an off-chain (or previously broadcast) signature/authorization message. Neither primitive binds the verified authorization to the specific trigger unit, trigger sender, or a single use. This mirrors the `pullTokensWithPermit` class of bug in the external report: a signature meant to authorize a benefit for its holder can be extracted (from the mempool, from a public unit, or leaked by any other means) and "front-run" or replayed by any unrelated, unprivileged party who posts their own trigger to the same or a different AA before/instead of the intended user, redirecting the authorized funds/benefit to themselves.

### Finding Description
`is_valid_sig(message, pem_key, sig)` in [1](#0-0)  only checks that `sig` is a valid signature of `message` under `pem_key`. It performs no binding whatsoever to `trigger.address`, the AA address, or any nonce/expiry — the same `(message, pem_key, sig)` triple remains "valid" forever and can be supplied by anybody who has seen it.

`is_valid_signed_package(signed_package, address)` in [2](#0-1)  is slightly stronger (it uses `signed_message.validateSignedMessage`, which ties the signature to the full authors/definition of `address`, see [3](#0-2) ), but it still does not require that the trigger sender (`trigger.address`) equal the verified `address`, nor does it mark the package as consumed after first use. The `signed_package` object supplied to the formula is entirely attacker-controlled data (it comes from `trigger.data`), so any AA trigger sender can copy a `signed_package` they observed elsewhere (e.g., in someone else's pending unit in the mempool, or in an earlier accepted trigger on the DAG) and resubmit it in their own trigger.

Contrast this with the base protocol signature scheme: an ordinary unit authentifier (`Definition.validateAuthentifiers`, `case 'sig'` in [4](#0-3) ) signs `objValidationState.unit_hash_to_sign`, which covers the *entire* unit content (all messages, inputs, outputs) — so a signature can never be detached from the specific transaction it authorizes. `is_valid_sig`/`is_valid_signed_package`, by design, sign only an arbitrary application-level `message`/`signed_message`, decoupling the authorization from any specific recipient or single spend — exactly the same architectural gap that made BakerFi's `permit`-based token pull exploitable by front-running.

### Impact Explanation
Any AA that uses `is_valid_sig` or `is_valid_signed_package` to gate a payout, discount, claim, or state change based on "this address signed this message" — without independently checking `trigger.address == <signer_or_authorized_address>` and without recording the signature/package as spent in a state var — is vulnerable to an unprivileged third party observing the signed authorization and front-running the legitimate holder's trigger, or simply replaying it indefinitely to drain AA funds intended for someone else. Because the primitive itself provides no anti-replay or sender-binding guarantee, this is a systemic footgun in the oscript language baked into ocore, not an isolated user mistake — analogous to how BakerFi's router made permit signatures generally reusable by any caller.

### Likelihood Explanation
Reachable by any unprivileged unit/trigger sender: constructing a competing AA trigger with a copied `signed_package`/`(message, pem_key, sig)` tuple requires no special privilege, only observing a broadcast unit or previously stable data. Given how commonly `is_valid_signed_package`/`is_valid_sig` are used for oracle/attestation/claim patterns in AAs (as shown by the extensive test coverage in `test/formula.test.js` and `test/pem_sig.test.js`), the likelihood of vulnerable AA logic being deployed on top of this primitive is high.

### Recommendation
- Document and, where feasible, enforce in the primitive itself that `is_valid_signed_package`/`is_valid_sig` results should never be used to authorize a transfer without the AA also checking `trigger.address` equals the signing address (or an explicitly designated beneficiary) and marking the specific `signed_message`/`(message, sig)` pair as consumed in a state var to prevent replay.
- Consider adding a native "consumed signed package" registry (similar to a nonce) at the protocol/oscript level so AA authors are not required to manually implement replay protection for every signature-authorized payout.

### Proof of Concept
1. AA `X` is written to pay out funds to `trigger.address` if the trigger includes a `signed_package` for which `is_valid_signed_package(trigger.data.signed_package, "AUTHORIZED_ADDRESS")` is true (a common oracle/attestation/claim pattern).
2. The legitimate holder of `AUTHORIZED_ADDRESS`'s key composes and broadcasts a trigger containing this `signed_package` to claim their payout.
3. Before that unit becomes stable (or even after, since the primitive imposes no single-use restriction), an unrelated attacker copies the exact same `signed_package` value out of the broadcast/mempool or from the stable unit's data payload and submits their own trigger unit to AA `X` with `trigger.data.signed_package` set to the copied value.
4. `is_valid_signed_package` in [2](#0-1)  returns `true` for the attacker's trigger as well, since it only checks that the package is validly signed by `AUTHORIZED_ADDRESS`, not that `trigger.address` sent it. If AA `X` pays out to `trigger.address` (a very common oscript idiom, see `{trigger.address}` payment outputs in [5](#0-4) ), the attacker receives the funds intended for the legitimate signer.
