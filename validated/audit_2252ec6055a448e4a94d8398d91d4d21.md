### Title
AA's fixed-cap asset issuance can be permanently griefed by a front-run issue - ([File: aa_composer.js])

### Summary
`issueAsset()` in `aa_composer.js` lets an Autonomous Agent (AA) issue its own capped asset by checking, once, whether *any* `type='issue'` input already exists for that asset. If an unprivileged unit poster issues even a tiny amount of that same asset first, the AA's own issuance permanently fails, bricking any AA logic that depends on it (e.g., a "define token" trigger case). This mirrors the reported `launchGroupCoinToUniswapV3`/`createPool` griefing pattern: a one-shot creation call that reverts/bounces forever once front-run by anyone.

### Finding Description
When an AA response composes a payment that needs to issue units of a capped asset, `issueAsset()` guards against double issuance: [1](#0-0) 

```
function issueAsset(cb2) {
    var objAsset = assetInfos[asset];
    if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
        return cb2("not a definer");
    ...
    if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
        conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
            if (rows.length > 0) // already issued
                return cb2('already issued');
            addIssueInput(1);
        });
    }
    ...
}
```

The check is keyed purely on the existence of *any* row `inputs.type='issue' AND inputs.asset=asset` — it does not check that the issuer is the AA itself. The only gate against a third party issuing this asset is `objAsset.issued_by_definer_only`, a field that is set once, permanently, at asset-definition time via the `asset` message payload (see `writer.js` persisting `issued_by_definer_only` into the `assets` table) [2](#0-1) .

If the AA author defines the asset **without** setting `issued_by_definer_only: true` (many real-world AA templates in this very repo, e.g. `test/samples/create_an_asset.oscript`/others, and any developer who omits this flag), then *any* unprivileged unit poster can send a standard payment/issue message for that asset (a single "unit" with an `inputs: [{type:"issue", asset:<assetId>, amount:<anything>, serial_number:1}]`) before the AA is ever triggered to issue it. Ordinary asset "issue" inputs are validated generically in `validation.js`/`inputs.js` and are not restricted to the AA's own address unless `issued_by_definer_only` is set.

Once such a foreign `type='issue'` row exists for that asset, the AA's `issueAsset()` query in `aa_composer.js:1196` will always find `rows.length > 0` and return `cb2('already issued')`, which bounces the AA trigger permanently — there is no fallback path, no re-derivation, and no way for the AA to ever successfully issue its own capped token again. This is functionally identical to the `createPool`-once griefing bug: a single, permissionless, one-shot creation primitive that an attacker can call ahead of the legitimate/expected caller, permanently denying that legitimate caller (here, the AA) its own resource.

### Impact Explanation
Any AA that mints a fixed-supply asset (e.g., a token-generation-event AA, an ICO template, a wrapped-asset AA) as part of its normal operation is vulnerable if its author forgets (or a template omits) `issued_by_definer_only: true`. The AA becomes permanently unable to complete its intended token issuance path — bouncing forever with `already issued` — freezing that entire feature of the AA and any funds sent to trigger it (the trigger unit's payment gets bounced, and users lose the tx fee / cannot obtain the intended token). This is a fund-freezing / permanent denial-of-service condition on AA functionality reachable by any address that can post an ordinary unit, matching the required "AA fund loss or freezing" impact bucket.

### Likelihood Explanation
Likelihood is medium: it requires an AA developer to have configured a capped asset for AA-controlled issuance without `issued_by_definer_only: true`. Given the flag exists and is documented, defensive templates in this repo (`ico_with_milestones.oscript`) do set it, but the AA composer code itself does not enforce it as a hard invariant for capped assets — it merely comments "only our AA can issue" as an assumption, not an enforced guarantee. Any third-party AA author who overlooks this single boolean field creates an easily and cheaply exploitable griefing vector: the attacker only needs to post one minimal issue-input unit before the AA's first issuance trigger fires.

### Recommendation
In `aa_composer.js`'s `issueAsset()`, do not rely solely on `objAsset.issued_by_definer_only` at asset-definition time. For capped assets meant to be minted by the AA, additionally restrict/validate that the existing `type='issue'` row (if any) was authored by the AA's own address before treating it as "already issued", or better, require/enforce `issued_by_definer_only=true` (with `definer_address` equal to the AA address) as a mandatory precondition whenever an AA attempts to issue a capped asset, bouncing at issuance-scheduling time with a clear configuration error instead of silently allowing a spoofable one-shot resource to be front-run.

### Proof of Concept
1. An AA is deployed whose `init`/message logic defines an asset with `cap: N`, `is_transferrable: true`, but `issued_by_definer_only` left `false`/unset (a common oversight when copying oscript templates).
2. The AA is triggered once to post the `asset` definition message, producing `asset = response_unit`, but before the AA's own subsequent trigger that would post `inputs:[{type:'issue', amount:N, serial_number:1}]`.
3. An attacker crafts and posts a standalone unit from their own address that includes a payment message with `asset: <assetId>` and `inputs: [{type:"issue", amount:1, serial_number:1}]` (this is valid because `issued_by_definer_only` is false, so any address may issue).
4. When the AA is triggered to perform its intended issuance, `issueAsset()` runs `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` [3](#0-2) , finds the attacker's row, and returns `cb2('already issued')`, permanently bouncing that AA trigger case for the lifetime of the asset.
