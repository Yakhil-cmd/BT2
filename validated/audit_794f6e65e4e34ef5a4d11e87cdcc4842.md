### Title
Recovery pallet's `control_inherited_account` filter checks only the outer call type and can be bypassed by wrapping the restricted call in `pallet_utility::batch` - (File: substrate/frame/recovery/src/lib.rs)

### Summary
The CSVAgent CVE's root cause is a denylist-based sanitizer that only pattern-matches the *literal surface form* of user input (`import`, `eval`, `os.`, etc.) and misses an equivalent code-execution path (`pd.read_pickle`) that achieves the same effect without tripping any denied pattern. The structural analog in this Polkadot SDK checkout is a call-authorization check in `pallet-recovery`'s `control_inherited_account` that appears to inspect only the *outer* `RuntimeCall` variant passed by the caller, rather than using FRAME's standard origin-filter mechanism (`OriginTrait::add_filter`) that is re-evaluated on every nested dispatch. Wrapping the restricted call (`slash_attempt`) inside `pallet_utility::Call::batch` changes the outer call's discriminant to `Utility::batch`, which the outer check does not recognize as the restricted operation, while `pallet-utility`'s `batch` dispatches the inner call against the same origin, executing the restricted logic anyway.

### Finding Description
`pallet-proxy`'s and `pallet-utility`'s battle-tested pattern for restricting what a delegated/derivative account may do is to attach a filter closure to the `RuntimeOrigin` via `origin.add_filter(...)` [1](#0-0)  before dispatching the inner call. Because `pallet_utility::batch`/`batch_all`/`force_batch` dispatch each inner call with `call.dispatch(origin.clone())` [2](#0-1) , and dispatch re-checks the origin's attached filter for every call (including nested ones), this design correctly prevents filter bypass through `Utility::batch`, `as_derivative`, etc. — as proven exhaustively in `pallet-proxy`'s own `filtering_works` test [3](#0-2)  and in `pallet-safe-mode`/`pallet-tx-pause` tests confirming batch-wrapped calls are still filtered [4](#0-3) .

`pallet-recovery`'s `control_inherited_account` in this repository, however, has a dedicated adversarial regression test explicitly describing the opposite behavior: a lower-priority `inheritor` (`FERDIE`) wraps a `slash_attempt` call — which they should not be able to invoke directly against a rival friend group — inside `pallet_utility::Call::batch`, and the test comment states plainly that "the batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call" [5](#0-4) . This is the exact bug-class analog of the CSVAgent flaw: a security check pattern-matches the visible/outer shape of the attacker-supplied payload (a specific `RuntimeCall` variant / a specific Python token) instead of the origin-bound, recursively-enforced permission that FRAME's own filter mechanism provides, and an equivalent-effect wrapper (`Utility::batch` / `pd.read_pickle`) sails through untouched.

### Impact Explanation
If confirmed at the implementation level (i.e., the outer-call check in `control_inherited_account` truly gates on `RuntimeCall::Recovery(Call::slash_attempt{..})` pattern-matching rather than an origin filter), a non-privileged, lower-priority inheritor could force-slash a rival friend group's deposit/attempt that they have no standing to touch, causing unbacked loss of the victim's reserved/staked deposit — an integrity break in the inheritance-priority arbitration logic described in the pallet's own documentation (`substrate/frame/recovery/src/lib.rs:59-78`).

### Likelihood Explanation
Wrapping any call inside `pallet_utility::batch` is available to any signed account with no privileged role, and the attacker (`FERDIE`, an already-successful inheritor of a *different*, lower-priority friend group) requires no governance, no stolen keys, and no malicious relayer/collator involvement — matching the "no privileged role" constraint of the reachable-entry-point requirement.

### Recommendation
Replace any ad hoc pattern-matching on the outer `RuntimeCall` passed into `control_inherited_account` with an origin-level filter attached via `OriginTrait::add_filter`, mirroring `pallet-proxy::do_proxy`, so that the restriction is re-applied to every nested dispatch (including calls wrapped in `Utility::batch`/`batch_all`/`as_derivative`), not just the top-level call shape.

### Proof of Concept
The repository already contains a Rust integration test that constructs exactly this scenario and asserts (via `panic!`) that the slash must not succeed: `substrate/frame/recovery/src/tests.rs:1423-1477` (`inheritor_cannot_bypass_filter_via_utility_batch`). I was not able to execute this test in this session (no code-execution tool available) and could not locate/read the body of `control_inherited_account` and its associated filter/guard logic in `substrate/frame/recovery/src/lib.rs` within the remaining tool budget — only the module-level doc comments (lines 1-80) were retrieved before the iteration limit was reached. Consequently, **this finding is not fully verified**: it is possible the actual filter implementation already closes this gap (e.g., via a properly attached origin filter) and the test exists purely to guard against regression, in which case there is no live vulnerability. This should be confirmed by reading the full `control_inherited_account` implementation and running `cargo test -p pallet-recovery inheritor_cannot_bypass_filter_via_utility_batch` before treating this as a confirmed, reportable bug.

fn filtering_works() {
