### Title
`check_suite` (and all webhook) target resolution uses `repository.full_name` while signature auth uses `repository.owner.login`, letting an attacker impersonate any no-secret org to act on any victim repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) to verify against using `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , but `Handler#stacks`, which every event handler (including `CheckSuiteHandler`) uses to resolve the actual `Repository`/`Stack`/`Commit` records, looks up the repository independently via `payload.dig('repository','full_name')` [3](#0-2) . These two JSON fields are never cross-checked, so an attacker who controls a Shipit-registered org with no `webhook_secret` can set `repository.owner.login` to that org (passing verification unconditionally) while setting `repository.full_name` to the victim's repository, causing the handler to operate on the victim's real stacks/commits.

### Finding Description
The broken binding: `params.dig('repository','owner','login')` (used to select the verifying `GitHubApp`) is implicitly assumed to equal the owner segment of `params.dig('repository','full_name')` (used to resolve the target `Repository`). No code enforces this equality.

Path traced:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)` to fetch the appropriate `GitHubApp` config, then `verified = github_app.verify_webhook_signature(...)`. [4](#0-3) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present. [5](#0-4) 
3. If the attacker names their own (or any) Shipit-registered org that has `webhook_secret: # nil` in `secrets.yml` — a documented/example configuration in this codebase [6](#0-5)  — as `repository.owner.login`, verification always succeeds, regardless of any `X-Hub-Signature` header content.
4. `Shipit::Webhooks.for_event('check_suite')` dispatches to `Handlers::CheckSuiteHandler`, whose `params` schema only requires `check_suite.head_sha` and `check_suite.head_branch` — it does not require or validate `repository.full_name` against `repository.owner.login`. [7](#0-6) 
5. `CheckSuiteHandler#process` calls `stacks.where(branch: ...)`, and `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')` — a value fully independent of the one used for signature verification. [3](#0-2)  `Repository.from_github_repo_name` does an exact case-insensitive `owner`/`name` lookup. [8](#0-7) 
6. Consequently a payload with `repository.owner.login = "attacker-org"` (unverified/no-secret) and `repository.full_name = "victim-org/victim-repo"` passes signature verification under the attacker's org, then resolves and operates on the victim's real `Stack`/`Commit` records, invoking `commit.schedule_refresh_check_runs!` → `RefreshCheckRunsJob.perform_later(commit_id: id)` on the victim's commit. [9](#0-8) 

Existing guards do not prevent this: `verify_signature` only ties authentication to `repository.owner.login`, not to `repository.full_name`; `drop_unhandled_event` only checks the event name is registered; `ExplicitParameters` schema for `CheckSuiteHandler` validates only the shape of `check_suite`, not any repository consistency; there is no `Repository` full_name vs. owner-login binding check anywhere in the webhook path. This same decoupling affects every handler that relies on `Handler#stacks` (push, status, pull_request family), since all of them inherit the identical `stacks`/`repository_name` resolution while the controller-level auth uses a different, independently-controlled field.

### Impact Explanation
An attacker with only an unprivileged, self-registered (or otherwise no-`webhook_secret`) GitHub organization in Shipit's config can forge webhook events "verified" under their own tenant while targeting any other tenant's repository/stack/commit by simply setting `repository.full_name` to the victim's repo. For `check_suite`, this results in `RefreshCheckRunsJob` being enqueued and executed for the victim's commit using the *victim's* legitimate `GitHubApp`/`GITHUB_TOKEN` (since `Commit#refresh_check_runs!` uses `stack.github_api`, which is scoped to the real repository owner, not the attacker). This is unauthorized job scheduling for a repository the attacker did not authenticate against, satisfying "a payload for one repository mutating another's stack, commit ... state" — the broader concern is that this same auth/target decoupling generalizes to other handlers (`push`, `status`, `pull_request`) that also resolve `stacks` via `full_name`, meaning any handler logic that writes state (e.g., creating statuses, closing PR-linked review stacks, etc.) is reachable by the same forged-organization technique across arbitrary victim repositories. This is repeatable per request against any repository name the attacker can guess/observe via Shipit's public UI, matching a Critical cross-tenant authentication bypass.

### Likelihood Explanation
Preconditions: Shipit must have at least one registered GitHub organization with no `webhook_secret` configured — a state explicitly supported and documented as a valid configuration in this codebase (`webhook_secret: # nil` appears in `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) [10](#0-9) [11](#0-10) . The attacker needs no Shipit credentials, session, or GitHub write access to the victim repo — only knowledge of the victim's `full_name`, an existing branch name, and a commit sha, all visible through Shipit's own UI. The attack is a single unauthenticated `POST /webhooks` with `X-Github-Event: check_suite` and no valid signature required. This is trivially repeatable against any number of victim repositories/stacks as long as one no-secret org exists in the deployment.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that the owner segment of `repository.full_name` matches `repository.owner.login` (or better, derive the verifying organization strictly from the same `full_name` field used for target resolution) before processing. Alternatively, resolve the target `Repository` using the same `repository_owner` value used for signature verification, so a single field governs both authentication and data access, and reject requests where they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":check_suite from a no-secret organization can target another repository's commit" do
  victim_stack  = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first)
  victim_commit.update!(sha: "6d9278037b872fd9a6690523e411ecb3aa181355")
  victim_stack.update!(branch: "master")

  # Attacker's own org, registered but with webhook_secret: nil
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", { webhook_secret: nil })
  )

  request.headers['X-Github-Event'] = 'check_suite'
  body = {
    action: 'requested',
    repository: {
      full_name: victim_stack.repository.full_name, # victim repo, used for target resolution
      owner: { login: 'attacker-org' }               # attacker org, used for signature bypass
    },
    check_suite: {
      head_sha: victim_commit.sha,
      head_branch: victim_stack.branch
    }
  }.to_json

  assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: victim_commit.id]) do
    post :create, body:, as: :json
    assert_response :ok
  end
end
```
This demonstrates `schedule_refresh_check_runs!` firing on the victim's `Commit` despite the request being "verified" only under the attacker's own, secret-less organization — proving `repository_owner` (auth) and `repository.full_name` (target) are unbound.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
