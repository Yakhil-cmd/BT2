`StatusHandler#process` applies GitHub `status` webhooks to every `Commit` row sharing a sha, regardless of reporting repository, allowing cross-tenant `blocking_statuses` bypass - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no scoping to the repository that sent the webhook, unlike its sibling `CheckSuiteHandler`, which correctly scopes through `stacks` (repository-derived). Any commit sha that exists in more than one stack's `commits` table — most plausibly because two repositories share git ancestry (a fork of a tracked repo) — lets an attacker who owns/controls only their own fork flip the status of a commit belonging to an unrelated victim stack, clearing `Commit#blocked?` for that stack.

### Finding Description
The claimed binding — "the repository whose webhook flipped the blocking commit's state == the repository that owns the blocking policy being bypassed" — does not hold in this code.

`Shipit::Webhooks::Handlers::Handler` exposes a repository-scoped helper: [1](#0-0) 
which resolves `Repository.from_github_repo_name(payload['repository']['full_name'])` and its `stacks`. `CheckSuiteHandler` uses this correctly, scoping both by stack and by branch before touching any commit: [2](#0-1) 

`StatusHandler#process`, however, bypasses `stacks` entirely and queries the global `Commit` table by sha alone: [3](#0-2) 
It never reads `payload['repository']`/`repository_name`, so any `Commit` row anywhere in the database that happens to have `sha == params.sha` receives the forged status via `commit.create_status_from_github!(params)`.

`Commit#create_status_from_github!` and the underlying `Status.replicate_from_github!` also perform no repository/stack cross-check: [4](#0-3) [5](#0-4) 

`Commit#blocked?` and `Status::Common#blocking?` then derive their result purely from the stored `state`/`context` on that `Commit`'s statuses, with no notion of which repository last wrote them: [6](#0-5) [7](#0-6) 

**Why signature verification does not stop this:** `WebhooksController#verify_signature` only checks that the payload's HMAC matches the webhook secret for `Shipit.github(organization: repository_owner)`, i.e., that GitHub genuinely signed *some* event for *some* organization known to Shipit: [8](#0-7) 
It never checks that `repository.full_name` in the payload corresponds to the stack whose commit is about to be mutated. An attacker does not need the webhook secret at all — they only need a repository (their own fork of a tracked upstream, or any repo under an org that has the same GitHub App/integration installed) so that GitHub itself computes a valid signature for a real `status` event they trigger (e.g. via their own CI/Actions or the Statuses API on a commit they control).

**Exploit flow:**
1. Attacker forks (or otherwise obtains a repository sharing git history with) a repository tracked by an unrelated victim stack that has `blocking_statuses` configured (`ci.blocking` in `shipit.yml`).
2. Because forks share commit objects, an old ancestor commit with sha `X` — already ingested into the victim stack's `commits` table and currently the nearest undeployed commit with a failing/missing blocking status — also exists (same sha) in the attacker's fork.
3. Attacker triggers (or directly emits) a genuinely GitHub-signed `status` webhook from their own repository for sha `X` with `state: success` and `context` equal to the victim's blocking context.
4. `StatusHandler#process` matches `Commit.where(sha: X)`, which includes the victim stack's `Commit` row, and calls `create_status_from_github!` on it — with no check that the payload's `repository` matches that commit's stack.
5. `Commit#blocked?` for every newer undeployed commit on the victim stack now evaluates to `false`, and `deployable?`/`Stack#next_commit_to_deploy` unblock continuous delivery or the manual redeploy button.

### Impact Explanation
This lets a request/webhook attributable to one repository mutate the deploy-blocking state of an unrelated repository's stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and enabling "an unauthorized deploy." The attacker gains the ability to silence a victim's `ci.blocking` safety gate and cause an unauthorized deploy to proceed on infrastructure they do not control, with no privileges on the victim's stack, repository or Shipit instance. It is repeatable against any stack whose blocking commit's sha is shared with an attacker-controlled repository (forks are the common case), so the blast radius spans all tenants sharing git ancestry with attacker-accessible repos on the same Shipit instance.

### Likelihood Explanation
Preconditions: (a) victim stack configures `ci.blocking` in `shipit.yml`; (b) an undeployed blocking commit whose sha also exists in a repository the attacker can generate genuine webhooks from (typically via forking a repo tracked by Shipit, which is common in OSS/CD setups); (c) the attacker's repository is under an org/account for which the same GitHub App/integration is installed so a legitimate signature is produced by GitHub. No Shipit secrets, sessions, or `api_clients_secret` are needed — GitHub itself signs the webhook. This is directly exploitable with attacker capabilities explicitly allowed by the rules ("emit webhooks from a repository they own").

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` is scoped: resolve commits only through `stacks` (i.e., `Commit.where(stack: stacks, sha: params.sha)` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) so a status webhook can only mutate commits belonging to stacks of the repository named in that webhook's own payload.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, conceptually; actual location per repo conventions):
```ruby
test "status webhook from an unrelated repository must not affect commits on other stacks" do
  victim_stack = shipit_stacks(:soc) # has blocking_statuses configured
  blocking_commit = shipit_commits(:soc_second)
  blocking_commit.statuses.delete_all
  descendant = shipit_commits(:soc_third)

  assert_predicate blocking_commit, :blocked? # sanity: sha exists, blocking gate up... actually assert blocking_commit.blocking? true, descendant.blocked? true
  refute_predicate descendant, :deployable?

  # Simulate a genuinely-signed webhook whose repository.full_name is NOT the victim's repo,
  # but whose sha collides with blocking_commit.sha (shared ancestor / fork scenario)
  forged_payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => victim_stack.blocking_statuses.first,
    'repository' => { 'full_name' => 'attacker/unrelated-fork' }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  blocking_commit.reload
  descendant.reload

  refute_predicate blocking_commit, :blocking?   # BUG: flips to false though webhook came from unrelated repo
  assert_predicate descendant, :deployable?      # BUG: victim stack's block cleared by foreign webhook
end
```
Assert both sides of the binding: `forged_payload['repository']['full_name'] != victim_stack.repository.full_name`, yet `blocking_commit.blocked?`/`descendant.deployable?` still change state — demonstrating the missing repository check in `StatusHandler#process`.
