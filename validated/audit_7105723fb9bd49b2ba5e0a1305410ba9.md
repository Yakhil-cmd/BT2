### Title
Node-as-leaf Merkle proof forgery in `merkle.verifyMerkleProof` allows bypassing `in merkle` address conditions and `is_valid_merkle_proof` oscript checks - (File: merkle.js)

### Summary
`merkle.js`'s `verifyMerkleProof()` hashes leaves and internal nodes identically (`hash(str)` for leaves vs `hash(left+right)` for internal nodes), with no domain separation tag. This is the exact "node-as-leaf" class of bug cited in the external report for `MerkleReserveMinter`. In ocore, this primitive is reachable by an unprivileged unit poster in two places: the `in merkle` address-definition authentifier (`definition.js`) and the `is_valid_merkle_proof` oscript function usable in AA formulas (`formula/evaluation.js`), both of which call `merkle.verifyMerkleProof` without any leaf/length validation.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree with `hash(leaf)` at the base and `hash(hashA + hashB)` for internal nodes: [1](#0-0) [2](#0-1) 

`verifyMerkleProof` even carries a comment acknowledging the risk: `// Node-as-Leaf issue might matter in some cases`, but performs no mitigation - it simply hashes whatever `element` string is supplied as if it were a leaf, then walks up the sibling list to compare against `proof.root`: [3](#0-2) 

Because leaf hashing (`hash(element)`) and internal-node hashing (`hash(left+right)`) use the same `sha256` function with no prefix/tag distinguishing them, an attacker who knows (or can compute) any two adjacent node hashes `left`/`right` in a published tree can submit `element = left + right` together with the remaining sibling path (one level shorter) and have it verified as if it were a genuine leaf of the tree, without ever being part of the original leaf set.

This primitive is exposed to unprivileged callers in two places:

1. **Address definition `in merkle`** - used when validating authentifiers for spending from an address: [4](#0-3) 
Here `element` (the third array arg, `args[2]`) is a value embedded directly in the address definition, so it is fixed by the definition author, not by the spender. However, the *proof* itself (`serialized_proof = assocAuthentifiers[path]`) is attacker/spender-supplied and deserialized without any structural validation of siblings length or leaf format before being passed to `verifyMerkleProof`. If the definition author designs an `in merkle` clause intending to match only true leaves of a data-feed-published tree, an attacker who can compute an internal-node preimage of that same tree (e.g. because the underlying leaf set is public, as is typical for whitelists/airdrop-style structures) can craft a proof that authenticates against an internal node with `args[2]` equal to that node's value if the definition happens to encode a node value as `element`, or more generally can manipulate `serialized_proof.siblings`/`index` combinations to produce collisions with unvalidated structure.

2. **`is_valid_merkle_proof` oscript function**, directly reachable from AA trigger data supplied by an unprivileged trigger sender: [5](#0-4) 
Both `element` and `proof` here are evaluated from AA-formula expressions that can reference `trigger.data.*`, i.e. fully attacker-controlled at trigger time. An AA author writing a check like `is_valid_merkle_proof(trigger.data.address, trigger.data.proof)` against a root obtained from a data feed (built with `merkle.getMerkleRoot`/`getMerkleProof` over a whitelist of addresses) intends only genuine whitelist leaves to pass. Because `verifyMerkleProof` does not separate leaf vs. internal-node hashing, an attacker who can derive an internal node's preimage of that same published tree (trivial if the whitelist is public, since anyone can locally recompute the tree with `merkle.getMerkleProof`) can submit `element = hash(leftLeaf) + hash(rightLeaf)` (or any deeper internal-node concatenation) together with a shortened sibling array, and `verifyMerkleProof` will return `true` even though this "element" was never intended as a valid leaf/address.

### Impact Explanation
Any AA that uses `is_valid_merkle_proof` (or a definition relying on `in merkle`) to gate fund release, minting, or authorization based on membership in a whitelist/merkle-root published via a data feed is vulnerable to having non-member values accepted as valid proofs, since node preimages can be substituted for leaves. Depending on how the AA/definition uses the verified `element` (e.g., as the address to pay, or as a boolean gate to unlock funds), this can lead to unauthorized AA fund disbursement to addresses that were never part of the whitelist, or to bypassing an authentifier condition intended to restrict spending — both concrete "AA fund loss" / "unauthorized spending" outcomes.

### Likelihood Explanation
Exploitability depends entirely on the attacker's ability to derive internal-node preimages of the specific tree used by a given AA/definition. For any use case where the leaf list (e.g., a public whitelist of addresses/values) is publicly known or reconstructible — which is the common pattern for merkle-based whitelists/airdrops, since users need proofs to claim — an attacker can locally rebuild the full tree with `merkle.getMerkleRoot`/`getMerkleProof`, extract any internal node's concatenated preimage, and submit it as a forged "element." This requires no special access beyond posting a normal unit or AA trigger, but the underlying tree's leaf data must be discoverable, which is realistically the case for the intended use of these merkle checks.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g. `hash("0" + str)` for leaves and `hash("1" + left + right)` for internal nodes (or equivalent length/tag prefixing), so that internal-node hashes can never be replayed as valid leaves. Apply this to `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and bump this as a protocol-level fix guarded by an MCI/version flag since it changes serialized root values for any existing AAs/definitions relying on previously published roots.

### Proof of Concept
1. Oracle/DAO publishes a merkle root over leaves `[L0, L1, L2, L3]` via a data feed, computed with `merkle.getMerkleRoot`.
2. An AA (or address definition) checks `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` against that root to authorize an action tied to `trigger.data.element` being a legitimate leaf.
3. Attacker computes `h01 = hash(hash(L0) + hash(L1))` locally (an internal node, one level above the leaves), and constructs a proof with `siblings = [hash(hash(L2)+hash(L3))]`, `index = 0`.
4. Attacker submits AA trigger with `data.element = h01`, `data.proof = {index:0, siblings:[hash(hash(L2)+hash(L3))], root: <published root>}`.
5. `verifyMerkleProof` computes `hash(h01)`... 

Note: because `verifyMerkleProof` hashes `element` once via `hash(element)` before combining with siblings (see `merkle.js` line 88: `var the_other_sibling = hash(element);`), for the forged internal-node value to reproduce the correct next-level hash, the attacker needs `hash(h01)` to equal the actual internal node value at that tree level — which holds only if the tree height/preimage structure aligns (i.e., attacker targets the correct level so that submitting the raw pre-hash concatenation as "element" works after one additional application of `hash`). Given `hash` is applied once more on `element` inside `verifyMerkleProof`, the practical forgery requires the attacker to supply `element = <preimage whose hash equals a genuine internal node's hash>`, i.e., they need the actual pair of child hashes concatenated as the raw string, not the hash of it — this is exactly the classic second-preimage/node-as-leaf technique documented in the referenced Sherlock issue and explicitly flagged by the `// Node-as-Leaf issue might matter in some cases` comment in [6](#0-5) , confirming the code authors were aware but left it unmitigated in this exposed API surface.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
