### Title
`StatusHandler#process` writes GitHub statuses by `sha` alone, letting a webhook from any registered repository overwrite CI status for a commit belonging to a different stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` without ever checking that the webhook's `repository` field matches the commit's own stack/repository, unlike `PushHandler`, which scopes through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). This lets a `status` webhook that is validly signed for one GitHub organization/repository write an arbitrary state (`success`/`failure`/`pending`/`error`) for a commit that actually belongs to a completely different, unrelated stack, as long as the attacker knows/guesses the target commit's sha.

### Finding Description
The binding the question implies should hold is: **repository queried by `refresh_statuses!`** (`stack.github_repo_name`, from `Commit#refresh_statuses!` at [1](#0-0) ) **== repository whose webhook wrote the last `Status` for that commit**. Tracing the webhook path shows this binding is never enforced:

- `WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the HMAC signature against `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . This only proves the request was signed by *some* organization registered with Shipit (e.g., the attacker's own GitHub App installation on their own org/repo) - it does not prove the payload's `sha`/status data actually originates from that repository's CI.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 
This is a global, unscoped lookup by `sha` across every stack in the installation - it never calls the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that `PushHandler` uses to scope work to the repository named in the payload [5](#0-4) [6](#0-5) .
- `create_status_from_github!` then persists the status using `commit.stack_id` — i.e., the commit's real (victim) stack — regardless of which repository's signature validated the request: `statuses.replicate_from_github!(stack_id, github_status)` inside `add_status` [7](#0-6) .

Meanwhile, `Commit#refresh_statuses!` (used by `RefreshStatusesJob`) correctly scopes its GitHub API call to the commit's own stack repository: `stack.github_api.statuses(github_repo_name, sha, per_page: 100)` [1](#0-0) [8](#0-7) . Because both paths write into the same `Status::Group` for the commit and `Status.replicate_from_github!` uses `find_or_create_by!`, a subsequent unrelated-repo `StatusHandler` webhook for the same `sha` can create a new `Status` row that becomes the newest/most-favorable entry, immediately superseding whatever `refresh_statuses!` just wrote — with no verification that the second write came from the commit's actual repository.

### Impact Explanation
An attacker who controls any GitHub organization/repository that is registered with the same Shipit installation (a normal, low-privilege tenant in a multi-repo Shipit deployment) can forge a `status` webhook — validly signed with their own org's webhook secret — containing an arbitrary `sha` value and `state: "success"`. If that `sha` matches a commit that exists in a different, unrelated stack (shas of public commits/PR heads are visible to anyone with read access to that repo), `StatusHandler` will create a `success` Status scoped to the victim stack's `stack_id`. If the victim stack has `continuous_deployment` enabled, this can trigger an unauthorized deploy (`stack.schedule_merges`/CD scheduling happens off `add_status` transitions, per `Commit#add_status`) [9](#0-8) . This is a payload for one repository mutating another repository's commit/stack state and can cause an unauthorized deploy — matching the "Critical" impact category (cross-tenant state mutation / unauthorized deploy).

### Likelihood Explanation
Preconditions: Shipit must host multiple stacks/repositories (typical multi-tenant deployment) and the attacker must control at least one repository/org already onboarded to the same Shipit instance (a low bar — any developer with a personal fork/org connected via the GitHub App). The attacker needs the target commit's sha, which is generally public for any repo they can read. No Shipit session, API token, or webhook secret of the victim's org is required — only the attacker's own valid webhook signature for their own org. This is repeatable against any tracked commit/stack whose sha the attacker can learn, at arbitrarily low cost per request (a single crafted POST to `/webhooks`).

### Recommendation
Scope `StatusHandler#process` (and any other sha/commit-keyed handler) to the repository named in the webhook payload, mirroring `PushHandler`'s use of `stacks`/`Repository.from_github_repo_name`, e.g. restrict the commit lookup to `Commit.joins(:stack).merge(stacks).where(sha: params.sha)` so a status can only be applied to commits belonging to the repository that actually signed the webhook.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "cross-repo status webhook overwrites refresh_statuses! result for unrelated repo" do
  stack = shipit_stacks(:shipit)                 # e.g. repo "shopify/shipit-engine"
  commit = stack.commits.last

  # 1. refresh_statuses! is repo-correctly scoped and fails/returns nothing
  Shipit.github.api.expects(:statuses)
    .with(stack.github_repo_name, commit.sha, per_page: 100)
    .returns([])
  commit.refresh_statuses!
  assert_not commit.reload.status.success?

  # 2. Forged webhook payload signed for an UNRELATED repo, same sha
  unrelated_payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/forged',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(unrelated_payload)

  # 3. Binding broken: stack.github_repo_name != 'attacker/unrelated-repo',
  #    yet commit.status now reflects the forged, unrelated-repo payload.
  assert commit.reload.status.success?
end
```
This demonstrates that `StatusHandler` does not enforce `payload['repository']['full_name'] == commit.stack.github_repo_name`, allowing a signed-but-unrelated-repository webhook to overwrite the repository-correct result just produced by `refresh_statuses!`.

      new_status

# frozen_string_literal: true

module Shipit
  class RefreshStatusesJob < BackgroundJob
    queue_as :default

    def perform(params)
      if params[:commit_id]
        Commit.find(params[:commit_id]).refresh_statuses!
      else
        stack = Stack.find(params[:stack_id])
        stack.commits.order(id: :desc).limit(30).each(&:refresh_statuses!)
      end
    end
  end
```
