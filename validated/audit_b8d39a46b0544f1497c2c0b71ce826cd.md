## Analog Vulnerability Found

### Title
Missing cosigner-authorization check on local signing requests allows any paired device to solicit unauthorized signatures for shared multisig addresses - (File: wallet.js)

### Summary
The Bifrost bug (CVE-2022-39219) allowed a party that was authenticated as a member of a group (but with only read permission) to issue write requests, because the code trusted the authentication step alone instead of also enforcing per-action authorization. In `ocore`, `handleMessageFromHub`'s `"sign"` case has the same class of flaw: after a correspondent device is authenticated (i.e., it is a known/paired device), the code that services a signing request for a *locally held* private key never verifies that the requesting device is actually a listed cosigner of the target shared/multisig address. The equivalent check exists — and is enforced — for the "remote" proxy path, but was deliberately disabled for the "local" path.

### Finding Description
In `wallet.js`, `findAddress()` is used to resolve who should sign for a given `address`/`signing_path` pair [1](#0-0) . When the resolved signer key lives on the local device, `callbacks.ifLocal(objAddress)` is invoked; when it lives on another device, `callbacks.ifRemote(row.device_address, other_device_addresses)` is invoked together with the list of legitimate cosigners.

In the `"sign"` message handler:
- The `ifRemote` branch explicitly authorizes the caller against the list of cosigners before forwarding/proxying the request: `if (!other_device_addresses.includes(from_address)) return callbacks.ifError("you are not listed as a cosigner for this address ...")` [2](#0-1) .
- The `ifLocal` branch has no equivalent check. The authorization check that would validate the sender is a legitimate cosigner of *this* address was intentionally commented out, with a note that keeping it would "make multilateral signing impossible": [3](#0-2) .

As a result, any device that is merely a *known correspondent* (paired at all, for any purpose — chat, unrelated contract, etc.) can send a `"sign"` request naming an arbitrary `address`/`signing_path` that happens to resolve locally, and the node will proceed to emit a `signing_request` event (or, for `signed_message` requests, directly validate/process the request) without ever checking that the sender is one of the parties entitled to request a signature for that specific shared address/path [4](#0-3) . The device authentication (pairing) is treated as sufficient proof of authorization for any resource (any locally-held address), exactly mirroring the Bifrost flaw where authenticated-but-lower-privilege members could issue actions reserved for higher-privilege members.

### Impact Explanation
Multisig/shared addresses in ocore are designed so that only the specific cosigner devices listed in `shared_address_signing_paths` may request signatures for a given signing path [5](#0-4) . Because the local-signing path skips this authorization check, any paired correspondent (e.g., a counterpart in an unrelated chat, contract, or bot pairing) can:
- Trigger signing-confirmation prompts for any of the victim's shared addresses/paths, which in automated/bot deployments (headless wallets that auto-sign, or arbiter/prosaic contract flows) can lead to funds being signed away without the true cosigners' involvement.
- Abuse `signed_message` flows (where the "unsigned_unit" carries `signed_message` and is auto-approved via `eventBus.emit`) to obtain signatures over attacker-chosen content for addresses the attacker does not co-own, undermining the integrity of the multi-party signing protocol and potentially enabling unauthorized spending once enough co-signatures are otherwise obtained through social engineering of the automated flow.

### Likelihood Explanation
This is directly reachable by any device already paired with the victim for whatever legitimate reason (a very low bar — pairing is a one-time, non-privileged exchange, and correspondents are not scoped to any single shared address). No wallet-of-record status or actual cosigner membership is required to initiate the request; the check present for the remote-proxy path was deliberately removed for the local path, indicating the omission is a conscious design gap rather than an obscure edge case.

### Recommendation
Reinstate/extend the authorization check on the `ifLocal` branch of the `"sign"` handler in `wallet.js`: before honoring a locally-resolvable signing request, verify `from_address` is a member of the cosigner set for the specific `address`/`signing_path` (e.g., re-enable the previously commented `extended_pubkeys`/`shared_address_signing_paths` lookup), while still allowing legitimate multilateral-signing use cases where a different address in the same unit is being co-signed by an unrelated party. At minimum, the emitted `signing_request` event should carry an explicit "requesting device is/ is not an authorized cosigner of this address" flag so downstream consumers (headless bots in particular) do not blindly trust the request.

### Proof of Concept
1. Device A pairs with Device B for any pretext (chat, an unrelated prosaic contract, etc.) so that B becomes a "known correspondent" of A.
2. Device A holds an address (`wallet.my_addresses`) that is also a member of a shared/multisig address `S` that A co-owns with Device C (a real cosigner), signing path `r.0`.
3. Device B (not part of `S`'s cosigner set) sends A a device message with `subject: "sign"`, `body: {address: S, signing_path: "r.0", unsigned_unit: <attacker-crafted unit>}`.
4. `findAddress(S, "r.0", …)` resolves the underlying key to A's local device and calls `ifLocal` [6](#0-5) .
5. Because the `ifLocal` branch never checks whether `from_address` (B) is a member of `shared_address_signing_paths` for `S`, A proceeds to validate/process the unit and emit a `signing_request` — even though B has no legitimate authority over address `S` [3](#0-2) .
