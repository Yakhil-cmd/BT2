### Title
Operator-precedence bug in `provision?` lets `prevent_with_label`/`allow_with_label` repositories auto-provision review stacks even when `review_stacks_enabled == false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` in a way that only gates the `allow_all` branch with `repository.review_stacks_enabled`; the `allow_with_label` and `prevent_with_label` branches are evaluated unconditionally due to Ruby operator precedence. This lets an unprivileged PR author cause `ReviewStackAdapter#create!` to provision a review stack for a repository whose maintainer explicitly disabled review stacks (`review_stacks_enabled == false`).

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: for every provisioning behavior, `provision? == (repository.review_stacks_enabled && <behavior-specific condition>)`. In the code this only holds for `allow_all`: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, the expression parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The last two disjuncts never reference `review_stacks_enabled`. So with `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label`, an attacker who opens a PR with an empty `labels` array makes `pull_request_has_provisioning_label?` false, `!false` true, `provisioning_behavior_prevent_with_label?` true → `provision?` returns `true` regardless of `review_stacks_enabled`.

`respond_to_pull_request_opened?` then permits `process` to call `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which unconditionally executes `create!`, persisting a `ReviewStack`, its `PullRequest`, and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` - none of these methods re-check `review_stacks_enabled`: [2](#0-1) 

The attacker's exact action: open a pull request (from their own fork, or any branch they control) against the target repository with no labels attached. GitHub emits a legitimately-signed `pull_request.opened` webhook (the attacker needs no secrets - this is the normal GitHub flow for any contributor opening a PR against a repo that has the Shipit GitHub App/webhook installed). Existing guards (`ExplicitParameters` schema, signature verification, `drop_unhandled_event`) validate payload shape and webhook authenticity but do nothing to enforce the `review_stacks_enabled` gate for the `prevent_with_label`/`allow_with_label` branches - the bug is purely in the boolean expression's precedence, not in any auth/signature layer.

Note: `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` with the whole `(archive? || unarchive?)` expression, confirming the intended invariant and that `OpenedHandler#provision?` is the outlier: [3](#0-2) 

### Impact Explanation
Any unprivileged contributor able to open a pull request against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` (or `:allow_with_label`, via the mirrored path) can force Shipit to create a `Shipit::ReviewStack`/`Shipit::PullRequest` record and enqueue it in `Shipit::ReviewStackProvisioningQueue` for a repository that never opted into review-stack automation. This is a record written for a repository/feature that did not authorize it, and it feeds a provisioning queue that can subsequently perform real infrastructure actions (build/deploy) associated with that stack. This matches the "unauthorized deploy/task record created for a repository lacking the right" class of impact - repeatable on every PR the attacker opens (one stack per unique PR number/environment), scoped to any repository misconfigured this way (which the maintainer believed was safe because `review_stacks_enabled` was false).

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled == false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible/common configuration for repos still opting into label-based gating while review stacks are globally disabled). No secrets, tokens, or special GitHub permissions are needed - only the ability to open a PR (fork-and-PR is sufficient) and control the label set (simply not adding the label, or adding it, depending on branch). This is trivially repeatable against any repository matching that configuration.

### Recommendation
Add explicit parentheses/grouping so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for prevent_with_label repos when review stacks disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
With the current code, `Shipit::Stack.count` increases by 1, proving `provision?` returns `true` despite `review_stacks_enabled == false`, i.e. `provision? != (review_stacks_enabled && behavior_condition)`.
