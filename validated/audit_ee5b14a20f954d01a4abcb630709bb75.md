### Title
Webhook Signature Verified Against `repository.owner.login`, But Target Stack Resolved From Unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check the inbound webhook against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature is accepted, the actual event handler resolves which `Stack`/`Repository` to act on using a *different* payload field, `payload.dig('repository', 'full_name')`, with no check that this field's owner matches the organization whose secret validated the request.

### Finding Description
In a multi-organization Shipit deployment, `config/secrets.yml` can define a separate `github` entry (and separate `webhook_secret`) per GitHub organization [1](#0-0) . `Shipit.github(organization:)` looks up the app/secret for a given org name and raises `GithubOrganizationUnknown` only if that org key is entirely absent from config [2](#0-1) .

The controller picks the verification secret like this: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` only asserts that the raw body's HMAC matches the secret configured for that one organization name; it says nothing about which repository inside the body is the "real" target [5](#0-4) .

Once verification passes, `Webhooks.for_event(event)` handlers are invoked with the full parsed payload. Every stock handler (e.g. `PushHandler`) resolves the stacks to mutate via `Handler#stacks`, which reads `payload.dig('repository', 'full_name')` — a *different* JSON field than the one used to pick the verification secret — and does a direct DB lookup with no cross-check against `repository_owner`: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the same class of bug as the reported issue: two logically-related fields (the field a security check is performed against, and the field business logic actually acts on) are allowed to diverge because enforcing their equality was treated as an unnecessary implementation detail. Here: `verified_organization == params.repository.owner.login` is checked, but the code that mutates state trusts `params.repository.full_name` (owner-independent) without ever asserting `full_name.split('/').first == verified_organization`.

### Impact Explanation
Concretely exploiting this requires an attacker who can get GitHub to deliver (or can otherwise produce) a validly-signed payload for organization A — e.g. by having push access to any repository under an organization on which the Shipit GitHub App is installed — while controlling the `repository.full_name` field's owner segment to reference a *different* organization/repository (B) that is also configured in the same Shipit instance. Because the signature is HMAC'd over the entire raw body by GitHub itself using org A's `webhook_secret`, and the code's only cross-field consistency check is "does `repository.owner.login` equal itself" (tautological, since both are read from the same object in normal GitHub deliveries), there is no enforced binding preventing a crafted delivery (via a custom webhook target such as a repo's own webhook settings, or GHE webhook redelivery/proxy) where `repository.owner.login` says "org-A" but `repository.full_name` says "org-B/some-repo". In that case, org A's secret is used to authenticate the request, yet a `GithubSyncJob` / stack sync targeting org B's stack is triggered [8](#0-7) , causing Shipit to sync/advance commit state for a repository the requester has no legitimate relationship to. This can influence CI status resolution, undeployed-commit tracking, and downstream automatic/continuous deployment decisions for a stack the attacker does not control — an unauthorized cross-organization write into deploy-relevant state.

### Likelihood Explanation
This requires: (1) a multi-org Shipit configuration (each org has an independently issued `webhook_secret`), (2) the attacker having legitimate push/webhook-trigger capability on at least one configured organization, and (3) the ability to make the delivered JSON body's `repository.owner.login` and `repository.full_name` diverge — which is not achievable through GitHub's native webhook delivery for standard events (GitHub always populates both fields consistently from the same repository object), only through non-standard delivery paths (custom webhook endpoints/relays, GHE webhook redelivery tooling, or a compromised/malicious intermediary that resends a signed body with a doctored `full_name`). Given the signature covers the whole raw body, a straightforward replay/tamper by an unprivileged external attacker without control over org A's `webhook_secret` is not directly possible — this materially lowers likelihood versus a pure logic-only bypass, since HMAC integrity does prevent naive field-tampering by third parties. This is a design gap (missing explicit equality assertion) rather than a demonstrated, minimal-privilege remote exploit path in the current codebase.

### Recommendation
Enforce the `Stack.owner == verified_organization` invariant explicitly wherever `Handler#stacks` (and any other handler) resolves target repositories: derive `repository_name` in `Shipit::Webhooks::Handlers::Handler` from the already-verified `repository_owner`, or explicitly assert `payload.dig('repository','full_name').split('/').first == repository_owner` before performing any lookup/dispatch, rejecting the request otherwise.

### Proof of Concept
Not independently reproducible with genuine GitHub-delivered webhooks, since GitHub always sets `repository.owner.login` and `repository.full_name` consistently for a single repository, and `X-Hub-Signature` is computed over that consistent body by GitHub using the org's registered `webhook_secret`. Demonstrating an actual exploit would require access to a mechanism that can redeliver a validly-signed body with a tampered `repository.full_name` (e.g., a compromised webhook relay/proxy, or GHE's raw webhook redelivery API under attacker influence) — this falls outside what could be verified purely from the engine's own code in this repository, and no such path was found in-scope (`app/**`, `lib/shipit/**`, `config/routes.rb`).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
