## Finding: `TransactionAuthenticator::verify()` for `FeePayer` (and `MultiAgent`) never asserts that `secondary_signer_addresses.len() == secondary_signers.len()`

### Summary
`TransactionAuthenticator::verify()` for the `FeePayer` variant builds its list of authenticators to check (`to_verify`) purely from the *actual number of `AccountAuthenticator` entries supplied* in `secondary_signers`, and never cross-checks that count against the *declared* `secondary_signer_addresses` list length before returning `Ok(())`. [1](#0-0) 

### Finding Description
In the `FeePayer` match arm:
```rust
let mut to_verify = vec![sender];
let _ = secondary_signers
    .iter()
    .map(|signer| to_verify.push(signer))
    .collect::<Vec<_>>();
```
`to_verify` is populated by iterating `secondary_signers` — whatever length it happens to be — with no assertion that it equals `secondary_signer_addresses.len()`. [2](#0-1) 

The signing message itself (`RawTransactionWithData::new_fee_payer`) embeds the full `secondary_signer_addresses` vector (e.g. 3 addresses), but the loop that actually demands a cryptographic signature only walks `secondary_signers` (e.g. 1 authenticator). [3](#0-2) 

Concretely: if an attacker submits `secondary_signer_addresses = [A, B, C]` but `secondary_signers = [sig_for_sender_key]` (a single valid `AccountAuthenticator` the attacker legitimately controls, e.g. duplicating/reusing their own sender key material as the lone "secondary signer"), then:
- `to_verify` = `[sender, one_signer]`.
- The loop only ever demands a valid signature from those two entries plus `fee_payer_signer`.
- No signature is ever demanded for addresses `B` and `C` — they are simply never checked at all.
- `verify()` returns `Ok(())` as long as the entries that *are* present verify correctly, with zero cryptographic material ever produced for `B` and `C`.

The same structural gap exists in the `MultiAgent` arm, which iterates `secondary_signers` in a `for` loop without checking it against `secondary_signer_addresses.len()`. [4](#0-3) 

This confirms the proof-of-concept premise in the question: a `FeePayer` authenticator with 3 secondary addresses and 1 secondary signer does **not** fail closed inside `TransactionAuthenticator::verify()` — the function has no length-equality guard for this variant, and would return `Ok(())` if the (fewer) supplied authenticators verify.

### Uncertainty / what I could not fully confirm
I found evidence (via `grep_search`, unread in detail due to iteration limits) that `types/src/transaction/mod.rs` also references `secondary_signers.len()` in several places, which may implement an independent length-equality check (e.g. inside `SignedTransaction::check_signature()`) before or after `verify()` is invoked. I was not able to read that file's content to confirm whether such a check exists and whether it runs *before* `TransactionAuthenticator::verify()` is called in the mempool/VM admission path, which would neutralize this specific gap at a higher layer. Likewise, I did not get to inspect how `aptos-vm` constructs the Move `&signer` list for multi-agent/fee-payer entry functions (whether it uses `secondary_signer_addresses()` directly, or a zipped/truncated pairing with `secondary_signers`), which determines whether this authenticator-level gap actually propagates into signer-binding corruption at the VM/Move layer, or whether Move-side prologue checks (`transaction_validation.move`, which does reference `secondary_signer_addresses.len()`) catch and reject the mismatch before execution.

### Impact Explanation
If no upstream/downstream length check exists, this is a genuine signer-binding break: a transaction can declare additional "secondary signer" addresses that are never actually authenticated, while the authenticator as a whole still reports `Ok(())`. Depending on how the VM derives the `&signer` arguments passed into a multi-agent/fee-payer entry function, this could let a transaction execute as if additional accounts had consented (signed) when they did not, corrupting the sender/signer-set guarantee that admission is supposed to enforce, while gas is still correctly charged to a legitimate fee payer.

### Likelihood Explanation
Directly demonstrated in the code path cited (lines 179–224): no code exists in `TransactionAuthenticator::verify()` to reject a length mismatch. Whether this is currently exploitable end-to-end at admission depends on unverified guards elsewhere (`types/src/transaction/mod.rs`, `aptos-vm` signer construction, and the Move prologue's `secondary_signer_addresses.len()` assertions), which I could not confirm within the available iterations.

### Recommendation
Add an explicit guard at the top of both the `FeePayer` and `MultiAgent` verify arms:
```rust
ensure!(secondary_signer_addresses.len() == secondary_signers.len(), "secondary signer address/authenticator length mismatch");
```
This makes `TransactionAuthenticator::verify()` fail closed independently of any downstream Move-prologue or VM-side length checks, removing reliance on defense-in-depth layers that were not confirmed during this review.

### Proof of Concept
```rust
let sender = AccountAuthenticator::ed25519(sender_pk, sender_sig);
let fee_payer_signer = AccountAuthenticator::ed25519(fp_pk, fp_sig);
let one_secondary_signer = AccountAuthenticator::ed25519(sec_pk, sec_sig); // only 1 authenticator
let secondary_signer_addresses = vec![addr_a, addr_b, addr_c]; // 3 declared addresses

let authenticator = TransactionAuthenticator::fee_payer(
    sender,
    secondary_signer_addresses, // len 3
    vec![one_secondary_signer], // len 1  <-- mismatched
    fee_payer_address,
    fee_payer_signer,
);

// Expectation per admission guarantees: this MUST fail.
// Actual: authenticator.verify(&raw_txn) returns Ok(()) as long as
// sender, the single secondary signer, and fee_payer_signer verify —
// addr_b and addr_c are never checked at all.
assert!(authenticator.verify(&raw_txn).is_ok()); // demonstrates fail-open behavior in this function alone
```

            Self::FeePayer {
                sender,
                secondary_signer_addresses,
                secondary_signers,
                fee_payer_address,
                fee_payer_signer,
            } => {
                // In the fee payer model, the fee payer address can be optionally signed. We
                // realized when we designed the fee payer model, that we made it too restrictive
                // by requiring the signature over the fee payer address. So now we need to live in
                // a world where we support a multitude of different solutions. The modern approach
                // assumes that some may sign over the address and others will sign over the zero
                // address, so we verify both and only fail if the signature fails for either of
                // them. The legacy approach is to assume the address of the fee payer is signed
                // over.
                let mut to_verify = vec![sender];
                let _ = secondary_signers
                    .iter()
                    .map(|signer| to_verify.push(signer))
                    .collect::<Vec<_>>();

                let no_fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.clone().into_owned(),
                    secondary_signer_addresses.clone(),
                    AccountAddress::ZERO,
                );

                let mut remaining = to_verify
                    .iter()
                    .filter(|verifier| verifier.verify(&no_fee_payer_address_message).is_err())
                    .collect::<Vec<_>>();

                remaining.push(&fee_payer_signer);

                let fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.into_owned(),
                    secondary_signer_addresses.clone(),
                    *fee_payer_address,
                );

                for verifier in remaining {
                    verifier.verify(&fee_payer_address_message)?;
                }

                Ok(())
            },
