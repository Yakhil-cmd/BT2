### Title
Attacker-controlled hookify rule regex enables ReDoS causing PreToolUse hook to fail open on dangerous Bash/file operations - (File: plugins/hookify/core/rule_engine.py)

### Summary
`compile_regex()` compiles a rule's `pattern` field with no complexity/length guard and `_regex_match()` calls `.search()` with no execution timeout, so a repo-committed hookify rule file with a catastrophic-backtracking pattern (e.g. `(a+)+b`) combined with a moderately long `tool_input` value (Bash `command`, `file_path`, or file content) can hang the `PreToolUse` hook process. The plugin's own error-handling philosophy is explicitly fail-open, and the hook host enforces only a fixed timeout, so a hang results in the dangerous tool call proceeding without a `deny` decision.

### Finding Description
Rules are loaded by `load_rules()` via `glob.glob('.claude/hookify.*.local.md')` [1](#0-0) , which loads **any** matching file present in the working directory with no origin/trust check — including files checked into an untrusted cloned repository. `Rule.from_dict` turns the frontmatter `pattern` field (or a `conditions` list `pattern`) directly into a `Condition.pattern` used for `regex_match` [2](#0-1) .

At evaluation time, `evaluate_rules()` → `_rule_matches()` → `_check_condition()` calls `_regex_match(pattern, field_value)` for the `regex_match` operator [3](#0-2) . `_regex_match()` compiles the attacker-supplied pattern via the LRU-cached `compile_regex()` and calls `regex.search(text)` with no timeout or backtracking-limit protection [4](#0-3) . Python's `re` module is vulnerable to catastrophic backtracking on patterns like `(a+)+b` or `(a|aa)+b`; combined with an adversarial or even coincidentally long `tool_input.command`/`file_path`/`content` string, `.search()` can take exponential time.

`pretooluse.py` invokes `engine.evaluate_rules(rules, input_data)` synchronously with no internal timeout of its own [5](#0-4) . The script's own exception handling explicitly documents a fail-open design: "ALWAYS exit 0 - never block operations due to hook errors" [6](#0-5) . The hook is registered with a fixed `"timeout": 10` in `hooks.json` [7](#0-6) . If the process hangs past this timeout and is killed externally, no `hookSpecificOutput.permissionDecision: "deny"` is ever emitted — consistent with the plugin's own fail-open handling for internal errors — so the tool call is not blocked by this hook.

No length cap, timeout wrapper (e.g. `signal.alarm`, subprocess with hard kill returning deny), or regex-complexity validation exists anywhere in `rule_engine.py` or `config_loader.py` to prevent this.

### Impact Explanation
A malicious rule file committed to a shared/cloned repository (`.claude/hookify.evil.local.md`) that a victim opens with Claude Code causes the hookify `PreToolUse` guard to hang or be killed on timeout for any Bash/Edit/Write/MultiEdit call whose field value triggers the vulnerable regex. Because the plugin's design explicitly favors "never block on error," a hang or external timeout kill results in the dangerous operation (e.g. a rule meant to block `rm -rf`) silently going unenforced — a trust-boundary/deny-bypass in the exact "deny means deny" invariant the hookify plugin exists to provide.

### Likelihood Explanation
This requires only that a victim clone/open a repository containing an attacker-authored `.claude/hookify.*.local.md` rule file (no admin/maintainer privilege, no leaked secrets, no social engineering beyond normal repo consumption) [1](#0-0) . Writing a catastrophic-backtracking regex is trivial and well documented; long `command`/`content` fields are common and easily reachable via normal Bash usage. This is fully repeatable and deterministic given a fixed pattern/input length.

### Recommendation
- Reject or sanitize regex patterns from rule files (e.g. static analysis for nested quantifiers, or use a linear-time engine such as Google's `re2` via the `re2` binding, or Python's `regex` module with a timeout parameter).
- Wrap `_regex_match()`/`compile_regex().search()` with an enforced timeout (e.g. `signal.alarm`, or run matching in a subprocess/thread with a hard deadline) and treat a timeout as a match-failure that still allows other conditions to short-circuit — but critically, if a rule's `action == 'block'` and evaluation cannot complete, the engine should fail closed (deny) rather than the current fail-open default.
- Cap the length of evaluated field values before regex matching.
- Do not silently trust rule files found via `glob.glob` regardless of source; consider requiring an explicit allowlist/signature/approval step for hookify rule files loaded from within a repository.

### Proof of Concept
Unit/timing test in `plugins/hookify/core/rule_engine.py`'s test scope:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

rule = Rule(
    name="evil-redos",
    enabled=True,
    event="bash",
    action="block",
    conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+b")],
    message="blocked"
)

engine = RuleEngine()
malicious_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "a" * 40 + "!"}  # no trailing 'b' -> forces full backtracking
}

start = time.monotonic()
result = engine.evaluate_rules([rule], malicious_input)
elapsed = time.monotonic() - start

# Expected (secure) behavior: elapsed < some bounded threshold (e.g. 1s),
# OR result explicitly denies on timeout.
# Actual (vulnerable) behavior: elapsed grows exponentially with command length,
# exceeding the 10s hooks.json timeout well before ~50 'a' characters, and the
# call returns {} (allow) once killed/aborted rather than a deny decision.
assert elapsed < 1.0, f"ReDoS: evaluation took {elapsed}s, exceeding hook timeout budget"
```
Run with increasing lengths of `"a" * N` to demonstrate exponential growth and confirm that once the hook's external `timeout: 10` in `hooks.json` is exceeded, no `permissionDecision: deny` is produced and the tool call is not blocked.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
