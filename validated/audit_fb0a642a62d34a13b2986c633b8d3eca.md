Found the analog. The webhook signature verification and the payload's action target are bound to different fields of the same untrusted JSON body, and nothing forces them to agree.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while the handler acts on the independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) is used to validate the HMAC signature based on `params.dig('repository', 'owner', 'login')` (or `organization.login`) taken from the unverified JSON body. But `Handler#stacks`/`repository_name` — the code that decides which repository/stack the webhook event actually acts on — reads a *different* field, `payload.dig('repository', 'full_name')`, from the same body. Nothing ties these two fields together.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, not-yet-verified body and uses it purely to look up which per-organization `webhook_secret` to check the signature against: [1](#0-0) [2](#0-1) 

Once the signature check "passes" (i.e., the sender knows the secret for whatever organization `repository_owner` resolves to), the actual event handlers act on `repository.full_name`, resolved independently via `Repository.from_github_repo_name`: [3](#0-2) [4](#0-3) 

In a single-org configuration (`Shipit.github` returning one fixed `webhook_secret`), this is not exploitable, since the same secret is used regardless of the claimed owner. But `Shipit.github(organization:)` explicitly supports per-organization configuration (multiple GitHub Apps, each with its own `webhook_secret`), as documented: [5](#0-4) 

In that multi-org setup, the binding that should hold is: `organization whose secret authenticated the request == owner of the repository the handler acts on`. The code never enforces this equality — `repository_owner` (used only for secret lookup) and `repository.full_name` (used for the actual DB lookup and mutation) are two separately-controlled JSON paths in the same attacker-supplied body. An attacker who holds a valid `webhook_secret` for *any one* organization configured on the Shipit instance (e.g., because they legitimately administer App B, or that secret leaked) can craft a payload where `repository.owner.login`/`organization.login` says "org-B" (so the signature check uses org-B's secret and passes) while `repository.full_name` says `"org-A/private-repo"` (so the handler acts on a stack belonging to org-A). This breaks the equality: *organization that authenticated ≠ repository that is written*.

### Impact Explanation
Depending on which webhook event/handler is invoked, this can drive unauthorized writes against a Stack belonging to an organization the attacker was never authenticated for: e.g. `PushHandler` calling `stack.sync_github(expected_head_sha:)` on org-A's stack, `StatusHandler` writing commit statuses, `CheckSuiteHandler` triggering `RefreshCheckRunsJob`, or `MembershipHandler`/pull-request handlers mutating Teams, Memberships, or review-stack provisioning — all cross-organization/cross-repository state changes triggered by a webhook secret that was never meant to authorize actions on that repository. This matches the "cross-repository writes" / "unauthorized deploy" high-impact criteria, since `sync_github` can advance the head of undeployed commits and interact with the continuous-delivery pipeline.

### Likelihood Explanation
Requires the attacker to already control a valid `webhook_secret` for *some* organization configured on the Shipit instance (their own org's GitHub App), which is a realistic scenario for any Shipit deployment serving multiple organizations/tenants with distinct GitHub Apps as documented. No repository write access, session, or `ApiClient` token is needed — only crafting a raw HTTP POST to `/webhooks` with a forged JSON body and a correctly computed HMAC using the attacker's own known secret.

### Recommendation
Enforce that the organization used to resolve/verify the signature is the same organization that owns the repository the handler subsequently acts on. Concretely, derive `repository_owner` and the repository used by `Handler#stacks` from the same trusted field (e.g., always parse `repository.full_name` and split its owner segment for both the secret lookup and the stack lookup), and reject the webhook if `repository.owner.login`/`organization.login` disagrees with the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker controls (or has been issued) a legitimate `webhook_secret` for organization `evil-org`, one of several orgs configured under `Shipit.github`.
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "evil-org" },
    "full_name": "victim-org/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(evil-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'evil-org')` and successfully verifies the signature since the attacker used the correct secret for `evil-org`.
5. `PushHandler#process` (via `Handler#stacks`/`repository_name`) resolves `Repository.from_github_repo_name('victim-org/private-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on a stack the attacker was never authenticated to touch.
