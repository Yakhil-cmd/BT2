## Analog Assessment

I found a real Polkadot SDK analog to the reported "unchecked slippage" bug class in `pallet-asset-conversion` and its XCM integration, but with an important nuance: the pallet's own extrinsics and `Swap`/`SwapCredit` trait implementations *do* enforce `amount_out_min > 0` / `amount_in_max` sanity via `ensure!(amount_out_min > Zero::zero(), Error::<T>::ZeroAmount)` and `ProvidedMinimumNotSufficientForSwap`. [1](#0-0) [2](#0-1) 

However, one call site deliberately bypasses this protection: `SwapFirstAssetTrader::refund_weight` in `cumulus-primitives-utility` calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, which skips any minimum-output check. [3](#0-2) 

### Title
Unbounded slippage in `SwapFirstAssetTrader::refund_weight` XCM fee-refund swap - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader`, an `xcm_executor::traits::WeightTrader` implementation, swaps a user's non-native fee asset into the runtime's `Target` asset in `buy_weight` (with a `swap_tokens_for_exact_tokens` call, which does have an implicit minimum by construction), but when refunding unused weight in `refund_weight` it swaps the `Target` asset back into the original fee asset via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — passing `None` for `amount_out_min`, i.e. explicitly disabling slippage protection for that leg of the swap. [4](#0-3) 

### Finding Description
`SwapFirstAssetTrader` is wired into `xcm_executor::Config::Trader` on real parachain runtimes, e.g. Penpal and the staking-async parachain runtime (an Asset-Hub-style config), meaning any XCM message that includes a `BuyExecution`/`PayFees` instruction with a non-`Target` fungible asset will trigger this trader. [5](#0-4) [6](#0-5) 

Any account that submits an XCM program (via `pallet_xcm::execute`/`send`, or via a cross-chain transfer that lands and executes locally) with `BuyExecution` paid in a non-native, pool-eligible asset is an unprivileged, ordinary entry point — no governance, no forged inherents, no relayer collusion needed.

The flow is:
1. `buy_weight` withdraws the user's asset and calls `SwapCredit::swap_tokens_for_exact_tokens(..., fee)`, obtaining exactly `fee` of `Target` (this leg is not attacker-exploitable for output shortfall, since it's "exact out"). [7](#0-6) 
2. At the end of message execution, if less weight was actually consumed than bought, `refund_weight` extracts the unused portion of `Target` from `total_fee` and swaps it back into the user's original asset for eventual return to the holding/user, using `swap_exact_tokens_for_tokens` with `amount_out_min = None`. [8](#0-7) 

Because `amount_out_min` is `None`, the internal `do_swap_exact_credit_tokens_for_tokens`/pool math will accept *any* non-zero output, however small, from the constant-product pool — there is no protection ensuring the user gets back a fair amount of their original asset for the surplus `Target` refunded. This mirrors exactly the pattern flagged in the report: an `amountOutMinimum`/`amount_out_min`-style parameter that is silently `0`/`None` in one code path while the analogous "buy" path enforces a real bound.

### Impact Explanation
Since the swapped pool (native/`Target` vs. the fee asset) is a public, on-chain AMM (`pallet_asset_conversion`), an adversary observing the pending XCM execution (e.g., a collator/block author reordering transactions, or simply a bot racing the same block) can move the pool price against the refund swap and back, extracting the difference between fair value and the value actually returned to the user. Because the amount being swapped in `refund_weight` is bounded by unused weight fees (typically small relative to a full swap), the *proportional* loss for the affected user can still be significant, and repeated or targeted execution (e.g., against known heavy XCM senders) compounds the extractable value over time. This is a genuine value-leak from an unprivileged, permissionless path, matching a Medium-severity slippage/sandwich issue class.

### Likelihood Explanation
Likelihood is bounded by several practical factors that reduce, but do not eliminate, exploitability:
- It requires that the runtime configures `SwapFirstAssetTrader` in its `Trader` tuple (true for Penpal and the shown staking-async parachain runtime; Asset Hub Westend/Rococo currently also use `SwapFirstAssetTrader` per `pr_8376.prdoc`). [9](#0-8) 
- It requires the user to pay XCM execution fees with a non-Target asset and to overpay (buy more weight than is consumed), leaving a non-trivial refund amount to be swapped back — a common but not universal pattern (fee estimation is often generous to avoid `TooExpensive` failures).
- The attacker needs the ability to observe and act within the same block/finality window as the refund swap (front-running/sandwiching capability), which is a permissionless capability available to any block-producing or mempool-observing party but does depend on network/consensus timing assumptions that are outside strict on-chain guarantees.

### Recommendation
Do not pass `None` for `amount_out_min` in `SwapFirstAssetTrader::refund_weight`. Compute a minimum acceptable output — e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in this file for `quote_weight`) with a configurable slippage tolerance — and pass `Some(min_out)` to `SwapCredit::swap_exact_tokens_for_tokens`. If the quoted minimum cannot be met, either skip the refund swap (returning the un-refunded `Target` credit to the drop handler) rather than accepting an arbitrarily bad price, similar to the pattern already implemented in `do_swap_exact_tokens_for_tokens`'s `ProvidedMinimumNotSufficientForSwap` check. [10](#0-9) 

### Proof of Concept
I was not able to execute a runnable reproduction within this session (no filesystem/terminal access in ask-only mode). Evidence gathered supports the finding at the source level:
- The vulnerable call site: `cumulus/primitives/utility/src/lib.rs:540-544`, explicit `None` for `amount_out_min` in `refund_weight`.
- Contrast with the enforced path: `substrate/frame/asset-conversion/src/lib.rs:988-1002`, `1086-1096`, and the existing test `swap_should_not_work_if_too_much_slippage` (`substrate/frame/asset-conversion/src/tests.rs:1565-1613`) confirming the pallet *does* reject swaps failing to meet a minimum when one is supplied — showing the protection exists but is deliberately not used for the refund leg.
- Confirmed live wiring into real runtime configs: Penpal (`cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs:408-422`) and the staking-async parachain runtime (`substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs:404-427`), both configuring `SwapFirstAssetTrader` as an active `Trader`.

A full PoC would require a local FRAME/XCM integration test (using the existing `cumulus/primitives/utility/src/tests/swap_first.rs` harness or the Penpal/asset-hub emulated test suites) that: (1) sets up an AMM pool with the fee asset and `Target` asset, (2) executes an XCM `BuyExecution` overpaying in the fee asset, (3) between `buy_weight` and `refund_weight`, mutates the pool reserves (simulating a sandwich) via a direct `AssetConversion::swap_exact_tokens_for_tokens` call from a third-party account, and (4) asserts the refunded amount is worse than a fair-price quote would have produced. I did not run this reproduction; the recommendation above should be validated with such a test before treating this as fully proven in a live deployment context.
