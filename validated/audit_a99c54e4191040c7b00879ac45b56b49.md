### Title
Unbounded route contracts can poison the caller’s signed authorization tree and drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap_collateral.rs)

### Summary

`swap_collateral` accepts caller-controlled `swap` bytes, authenticates only the owner/delegate caller, and forwards the opaque route to the configured router. [1](#0-0) [2](#0-1)  Because the router’s venue adapters invoke pool addresses supplied by the route, a malicious pool can execute inside the transaction and request a token transfer from the victim. [3](#0-2)  The resulting authorization request appears as a child beneath the victim’s `swap_collateral` authorization, so a client that does not decode and compare every child invocation can induce the victim to sign a theft of arbitrary wallet tokens. [4](#0-3) 

### Finding Description

`swap_collateral` requires `caller` authorization and verifies that the caller owns or delegates `account_id`, but it does not bind the signed operation to a fixed venue contract. [5](#0-4)  The supplied `swap` argument is passed through `withdraw_and_swap_from_supply`, which reaches `swap_tokens` and then `router.execute_strategy(&controller, &amount_in, swap)`. [6](#0-5) [7](#0-6) 

The controller narrowly authorizes only the controller’s own input-token transfer to the router and uses measured input/output balances afterward. [8](#0-7)  Those checks bound loss of the routed collateral, but they do not prevent a route-selected contract from requesting the victim’s authorization for an unrelated token transfer deeper in the same call tree. [9](#0-8) 

The production Phoenix venue path demonstrates the dangerous shape: the payload-selected `hop.pool` receives a `swap` invocation, with no pool allowlist at this boundary. [3](#0-2)  A malicious contract can satisfy the route by pulling the authorized input and returning enough output, while also calling `wallet_token.transfer(victim, attacker, victim_balance)`. [10](#0-9)  Simulation records that transfer as a child invocation of the victim’s `swap_collateral` authorization tree. [11](#0-10) 

### Impact Explanation

A successful attack steals any token balance held directly by the victim, including tokens completely unrelated to the lending account, while still producing the expected collateral swap result. [12](#0-11)  The regression test demonstrates that signing the poisoned tree transfers the victim’s full unrelated wallet-token balance to the attacker. [13](#0-12) 

This is theft of user funds reachable through a permissionless account-owner action. [14](#0-13) 

### Likelihood Explanation

The attacker needs only a crafted route and a malicious contract compatible with the selected venue call convention; the victim must supply collateral and sign the presented transaction. [15](#0-14)  The malicious transfer is not part of the human-readable `swap_collateral` arguments and relies on simulation/wallet handling to expose it as an authorization child. [16](#0-15)  An honest route produces no such child entry, while an unsafe client or deceptive dApp can present the signed transaction as an ordinary collateral swap. [4](#0-3) 

### Recommendation

Constrain venue calls to governance-approved pool contracts or otherwise prevent attacker-selected contracts from executing inside a user-authorized strategy call. [17](#0-16)  At minimum, the router should maintain a venue/pool allowlist and reject any payload pool not explicitly approved for the selected venue. [18](#0-17) 

Clients must also decode the complete `StrategySwap` payload and the simulated authorization tree before signing, and reject `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or direct router calls containing any unexpected child invocation. [19](#0-18) 

### Proof of Concept

1. Victim supplies USDC collateral and owns an account, while holding `WALLET_BALANCE` of an unrelated token in their wallet. [20](#0-19) 
2. Attacker deploys a route-selected malicious “pool” storing `(victim, wallet_token, attacker, amount)` and, when invoked as a swap venue, calls `wallet_token.transfer(victim, attacker, amount)`. [21](#0-20) 
3. The crafted route returns enough output for the controller’s measured-output and final-risk checks to pass. [22](#0-21) [23](#0-22) 
4. The victim submits `swap_collateral(victim, account_id, USDC, amount, ETH, malicious_swap)`. [14](#0-13) 
5. Simulation records the unrelated wallet-token transfer as a child of the victim’s `swap_collateral` authorization entry. [11](#0-10) 
6. With an honest root-only authorization, the host rejects the malicious transfer; when the victim signs the simulation-produced poisoned tree, the attacker receives the full wallet-token balance while the collateral swap succeeds. [24](#0-23)

**File:** docs/explanation/threat-model.md (L144-165)
```markdown
Router swaps settle measured input/output changes. The controller grants
one exact input-transfer invocation, not a token allowance, and refunds
unspent input still held by the controller. The router checks its payload
minimum against output after fees but before payout; its own residuals
follow a capped admin-revenue policy. The controller requires positive
measured output and final account risk, not an independent slippage bound.
A compromised router may consume authorized input for dust output while the
final account passes its risk gates. Exposure is bounded by routed funds and
those gates, not by an independent controller slippage limit.

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
