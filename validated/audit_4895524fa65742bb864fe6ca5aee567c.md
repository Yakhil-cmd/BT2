### Title
Arbitrary environment variable injection into shell-interpreted `shipit.yml` steps via unsanitized PR label names in `ReviewStack#env` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable key with value `"true"`, with no allowlist, and `TaskCommands#env`/`DeployCommands#env` merge this unsanitized hash directly into the process environment used by `Command#start` for `PTY.spawn`. An attacker who can label their own PR (or trigger the `pull_request` webhook with arbitrary label names) can inject env vars such as `GIT_CONFIG_GLOBAL` into every shell-interpreted `shipit.yml` step for that stack, and by also controlling the checked-out repository content (a file literally named `true` containing a malicious `core.fsmonitor`/hook directive), achieve command execution on the deploy host when git runs in that working directory.

### Finding Description
The broken binding is: **the set of keys reaching `PTY.spawn`'s environment for a task/deploy step == the set of variable names explicitly whitelisted by `TaskDefinition#filter_envs` / `DeploySpec#filter_deploy_envs`**. This holds for user-API-supplied env (`EnvironmentVariables#permit` at [1](#0-0)  raises `NotPermitted` for unlisted keys, verified by `test/controllers/api/tasks_controller_test.rb` rejecting `DANGEROUS_VARIABLE`), but it does **not** hold for `ReviewStack#env`.

`ReviewStack#env` merges pull request labels directly, unsanitized, into the stack env: [2](#0-1) 

`TaskCommands#env` merges `@stack.env` (this unsanitized hash) into the final environment used to build each `Command`: [3](#0-2) 

That `env` is passed straight to `Command.new(command_line, env:, chdir:)` for every `shipit.yml` step (`perform`, `install_dependencies`), and `Command#unbundled_env` merges `@env.stringify_keys` with no filtering before `PTY.spawn`: [4](#0-3) 

Labels reach `PullRequest#labels` from the webhook body with no key restriction: [5](#0-4) 

**Exploit flow:** an unprivileged fork owner opens a PR against a repository with review stacks enabled, applies a label literally named `git_config_global` (or any case-insensitive variant), and pushes a commit adding a file named `true` at the repository root containing a malicious `[core] fsmonitor = ...` or hook directive. `LabelCapturingHandler#capture_labels` persists the label name verbatim. `ReviewStack#env` then sets `GIT_CONFIG_GLOBAL=true` for every subsequent task/deploy `Command`. Because the step's working directory (`chdir:`) is the checked-out PR content, git resolves the relative path `true` as its "global" config file and executes the attacker-defined hook/fsmonitor command the next time any git operation runs as part of the pipeline (checkout, clone, or a `shipit.yml` step invoking `git`).

**Why existing guards fail:** `EnvironmentVariables#permit` is only invoked for `@task.env`/deploy variables sourced from API params (`TaskDefinition#filter_envs`, `DeploySpec#filter_deploy_envs`), not for `Stack#env`/`ReviewStack#env`, which is merged unconditionally in `TaskCommands#env` and `DeployCommands#env`. The existing test suite (`test/lib/shipit/task_commands_test.rb`, `test/lib/shipit/deploy_commands_test.rb`, `test/models/shipit/review_stack_test.rb`) explicitly documents and asserts this unsanitized behavior as intended ("`#env` includes the stack's pull request labels").

### Impact Explanation
Any fork owner can inject arbitrary-named, attacker-chosen environment variable keys (value fixed to `"true"`) into every shell-interpreted step executed for their review stack, including install/dependency and deploy/task steps that invoke `git` or other tools sensitive to environment-variable-driven configuration (e.g., `GIT_CONFIG_GLOBAL`, potentially other tool-specific override variables). Combined with attacker-controlled repository content checked out into the step's working directory, this can result in Remote Code Execution on the Shipit deploy host, scoped to the review stack the attacker's own PR provisions — matching the Critical RCE class via `Command`/`PTY.spawn`.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with any `provisioning_behavior` (allow_all, allow_with_label, or prevent_with_label — the label-name-to-env mechanism is independent of the provisioning gate) and have a shell-interpreted `shipit.yml` task/deploy step that invokes git (very common: checkout/clone are always git commands). The attacker only needs the ability to open a PR on a repository they control (fork) and apply/receive a label with the desired name — no Shipit credentials, no GitHub App secrets, and no maintainer status are required. This is low-cost and repeatable against any repository with review stacks enabled.

### Recommendation
Sanitize `ReviewStack#env` (and any label-derived env merge in `Stack#env`) through an explicit allowlist analogous to `EnvironmentVariables#permit`, rejecting or dropping label-derived keys that match reserved/dangerous variable name patterns (e.g., `GIT_*`, `LD_*`, `BASH_ENV`, `PATH`, etc.), or better, namespace label-derived variables under a fixed prefix (e.g., `SHIPIT_LABEL_<NAME>`) so they can never collide with security-sensitive environment variable names.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing "#env includes the stack's pull request labels" test)
test "#env allows a PR label to inject a dangerous, security-sensitive variable name" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_config_global"]

  env = stack.env

  # Binding under test: env keys reaching Command/PTY.spawn should be limited to an
  # explicit whitelist (as enforced by EnvironmentVariables#permit for API-supplied env).
  # Actual: the fork-controlled label name reaches the env unfiltered.
  assert_equal "true", env["GIT_CONFIG_GLOBAL"]
end

# test/lib/shipit/task_commands_test.rb
test "#env propagates attacker-controlled GIT_CONFIG_GLOBAL from a PR label into the task/step env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_config_global"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["GIT_CONFIG_GLOBAL"]

  # Confirm it reaches the actual Command/PTY.spawn env used for shell-interpreted steps
  command = Shipit::TaskCommands.new(task).perform.first
  assert_equal "true", command.env["GIT_CONFIG_GLOBAL"]
end
```
This demonstrates the binding failure directly: `ReviewStack#env`/`TaskCommands#env` place a fork-controllable, security-sensitive key (`GIT_CONFIG_GLOBAL`) into the environment passed to `Command`, which `Command#unbundled_env`/`PTY.spawn` will hand to the shell-interpreted `shipit.yml` step process, with no allowlist filtering as exists for API-supplied task/deploy env variables.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
