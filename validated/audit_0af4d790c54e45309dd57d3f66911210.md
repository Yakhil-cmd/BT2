### Title
Missing `return` after error causes double invocation of the private-payment cleanup callback, leading to a crash-inducing double "unlock" - (File: network.js)

### Summary
`network.js`'s `handleSavedPrivatePayments()` processes private payment chains that were previously saved to `unhandled_private_payments` (data an unprivileged private-payment counterparty can cause to be persisted, e.g. via a private chain sent directly or through the hub). Inside the per-row `validateAndSave` closure, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` calls the row's cleanup routine `deleteHandledPrivateChain(..., cb)` in the `catch` block, but does **not** `return` afterward. Execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain()` on the same `arrPrivateElements`, whose `ifOk`/`ifError` handlers call `deleteHandledPrivateChain(..., cb)` a second time. This is the same bug shape as the reported x25 issue: an error path frees/finalizes a resource and returns an error code, but the caller does not realize this happened and finalizes the same resource again. [1](#0-0) 

### Finding Description
`validateAndSave` is defined as: [1](#0-0) 

- If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (`getBase64Hash` builds a source string via `getJsonSourceString`/`getSourceString` and hashes it — these source-string builders are known to throw on payload shapes they don't expect), the `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`. [2](#0-1) 
- Because there is no `return` in the `catch`, execution continues to build `key` (using the now-undefined `json_payload_hash`) and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time on the very same, already-cleaned-up element. [3](#0-2) 
- That second call's `ifOk`/`ifError` handlers each also call `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`. [4](#0-3) [5](#0-4) 
- `deleteHandledPrivateChain` deletes the DB row and then always invokes `cb()`: [6](#0-5) 

The net effect: for a single row of `async.each`, the item's `cb` is invoked **twice**. `handleSavedPrivatePayments` runs all rows under an `async.each(...)` whose final callback calls `unlock()` on the `"saved_private"` mutex lock: [7](#0-6) 

`async`'s `each` calls its final callback once all items' `cb`s have fired; a double-fired `cb` for one item can cause the final callback to run twice (once when the async library’s internal completed-count first reaches the total, and again — depending on internal bookkeeping/timing — from the duplicate signal), which calls `unlock()` twice on the same lock. `mutex.js`'s `unlock` explicitly guards against this and **throws** on a second call: [8](#0-7) 

```
proc(function unlock(unlock_msg) {
    if (!bLocked)
        throw Error("double unlock?");
    ...
```

This `throw` is not caught anywhere in this callback chain, and in Node.js an uncaught exception thrown from an asynchronous callback crashes the process.

### Impact Explanation
Any private-payment counterparty (or a paired device forwarding a private chain) can craft a private-element payload whose head element causes `objectHash.getBase64Hash` to throw when it is later processed from `unhandled_private_payments` (this table is populated straight from received/forwarded private payment JSON with no schema validation prior to this point — see `savePrivatePayment`/`ifNew` path feeding this table). Once such a malformed chain is queued and `handleSavedPrivatePayments` runs, the double-`cb()` / double-`unlock()` sequence throws `Error("double unlock?")`, crashing the node process that is hosting the wallet/hub. A node that repeatedly crashes cannot confirm new units, matching the "network unable to confirm new units" impact category permitted by scope. This is triggerable purely through the private-payment/paired-device message path reachable by an unprivileged private-payment counterparty, not through peer/network flooding.

### Likelihood Explanation
Reaching this code path only requires sending a private payment chain (directly to a peer or through the hub) whose head element's payload is shaped to make `getBase64Hash`/`getJsonSourceString`/`getSourceString` throw (these source-string builders are known in this codebase to reject payloads with unexpected value types by throwing). No signature bypass, no special privileges, and no race condition beyond normal chain delivery is required, making this readily reachable by any wallet counterparty that can send a private payment.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (network.js, around line 2476) so that execution does not fall through to `privatePayment.validateAndSavePrivatePaymentChain(...)` after the head element has already failed to hash and its row has already been cleaned up / `cb` already invoked. Additionally, consider hardening `mutex.js`'s double-unlock guard to `console.error`/`breadcrumbs` instead of `throw`, so a similar programming error elsewhere degrades gracefully rather than crashing the process, and consider validating private-payment payload shape before persisting to `unhandled_private_payments`.

### Proof of Concept
1. As a private-payment counterparty, construct a private-payment chain whose head element (`arrPrivateElements[0]`) has a `payload` object containing a field type that `getJsonSourceString`/`getSourceString` cannot serialize (these helpers throw for unsupported value types when building the canonical hash source string).
2. Send this chain to the target wallet/hub directly or via `light/post_private_payment` type flow so that it ends up persisted in `unhandled_private_payments` (via the `ifNew`/`savePrivatePayment` path in `network.js`, sibling to `handleSavedPrivatePayments`).
3. When `handleSavedPrivatePayments()` next runs (triggered periodically / on new stable joints), it reaches `validateAndSave()` for this row: `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws.
4. The `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` (1st `cb()` call) but does not return.
5. Execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifError` (or `ifOk`) handler calls `deleteHandledPrivateChain(...)` again (2nd `cb()` call).
6. The duplicate `cb()` signals cause `async.each`'s completion handler to invoke `unlock()` on the `"saved_private"` mutex lock twice; the second `unlock()` call hits `if (!bLocked) throw Error("double unlock?")` in `mutex.js`, crashing the node process. [9](#0-8) [10](#0-9)
