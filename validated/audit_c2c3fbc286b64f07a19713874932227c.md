## Title
Webhook `status` events bypass signature verification when `webhook_secret` is unset and forge cross-repository commit statuses that can trigger unauthorized deploys - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats an unconfigured `webhook_secret` as automatic success, and `StatusHandler` writes `Status` rows by matching a commit `sha` across the *entire* installation with no per-repository scoping. Combining these, an unauthenticated caller can post a forged GitHub `status` webhook that is accepted without any valid signature and that creates a `success` status for any commit SHA already known to Shipit, in any stack, regardless of which organization or repository actually owns that commit. Because commit status directly feeds `Commit#deployable?` and continuous-delivery scheduling, this can be used to unlock an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` resolves a `GitHubApp` from the *unverified* JSON body and then asks it to verify the HMAC signature: [1](#0-0) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that app/organization: [2](#0-1) 

`webhook_secret` is documented and shipped as optional (`# nil` in the setup docs and in `test/dummy/config/secrets.yml` / `secrets.test.json`), so a legitimately-configured Shipit installation can have it unset: [3](#0-2) [4](#0-3) 

When only a single GitHub app is configured (the common/default setup), `Shipit.github` ignores the caller-supplied organization entirely and always returns that one app: [5](#0-4) 

So for the common single-app configuration with no `webhook_secret`, **every** webhook request is accepted regardless of the `X-Hub-Signature` header or body content — the “authenticated organization” side of the intended binding (`request signed by org X` ⇒ `payload genuinely originates from org X`) collapses to “always true”.

On the write side, `StatusHandler` (which processes GitHub `status` events) looks up commits purely by SHA, with **no** repository/stack scoping at all: [6](#0-5) 

This differs from every other handler in the codebase, which resolve the target repository via `Repository.from_github_repo_name(params.repository.full_name)` before acting: [7](#0-6) [8](#0-7) 

`Commit#create_status_from_github!` then persists the payload's `state`/`description`/`target_url`/`context` verbatim as a `Status` row: [9](#0-8) [10](#0-9) 

The binding broken (equality form):
`organization_that_authenticated_the_request == organization_owning_the_repository/stack_that_is_written`
is violated because (a) “authenticated” degenerates to “always” when `webhook_secret` is nil, and (b) `StatusHandler` never checks any organization/repository at all — it writes to whichever stack happens to contain a commit with the attacker-chosen `sha`.

### Impact Explanation
Commit status state drives `Commit#deployable?` and `Stack#branch_status`/`merge_status`/continuous-delivery scheduling: [11](#0-10) [12](#0-11) 

`add_status` triggers `stack.schedule_merges` and deployable-status hooks whenever a status transitions to `success`: [13](#0-12) 

For any stack with `continuous_deployment` enabled, forging a `success` status for its pending commit (found simply by knowing/guessing its SHA, which is public GitHub information) can cause that commit to become deployable and be picked up by continuous delivery — an unauthorized deploy triggered without any valid credential, matching the Critical impact category ("an unauthorized deploy").

### Likelihood Explanation
No secret, session, or token is required by the attacker: they only need to send an unauthenticated POST to `/webhooks` with `X-Github-Event: status` and a body containing a `sha` that already exists in Shipit's `commits` table (visible via the public GitHub repo history) and `state: "success"`. The only precondition is that the resolved `GitHubApp` (default single-app config, or an org explicitly configured without `webhook_secret`) has no webhook secret set — a state the project's own documentation and shipped example configs treat as normal/optional, not a misconfiguration outside the engine's control.

### Recommendation
- Make `webhook_secret` mandatory (or fail closed) rather than treating its absence as automatic verification success in `GitHubApp#verify_webhook_signature`.
- Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository identified in `payload['repository']['full_name']`, matching the pattern used by `PushHandler`/`Handler#stacks`, instead of matching commits by SHA alone across the whole database.

### Proof of Concept
1. Deploy Shipit with the default/documented config (`github.webhook_secret` unset, as in `test/dummy/config/secrets.yml`).
2. Identify any public commit SHA already known to the Shipit instance for a stack with `continuous_deployment: true` (e.g., the current undeployed HEAD).
3. Send:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<target commit sha>",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://example.com",
  "repository": {"owner": {"login": "any-org"}}
}
```
No valid `X-Hub-Signature` is required; `verify_webhook_signature` returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` matches the commit purely by `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) and creates a `success` Status, potentially unlocking continuous delivery for that stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
