### Title
`provision?` grants review-stack provisioning when `review_stacks_enabled` is false - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` uses Ruby's operator precedence (`&&` binds tighter than `||`) so that only the `allow_all?` branch is gated by `repository.review_stacks_enabled`; the `allow_with_label?` and `prevent_with_label?` branches are not. A repository owner who sets `provisioning_behavior=:allow_with_label` but never enables review stacks is therefore still vulnerable to unauthenticated review-stack creation from any PR author who attaches the provisioning label to their own PR.

### Finding Description
The broken binding is: `repository.review_stacks_enabled == false` should imply `provision? == false` for every `provisioning_behavior`, but it does not.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `review_stacks_enabled=false` and `provisioning_behavior_allow_with_label?=true`, the second disjunct alone (`allow_with_label? && has_label?`) can make `provision?` return `true`, entirely bypassing the `review_stacks_enabled` flag. The same defective precedence pattern also exists in `ReopenedHandler#unarchive?` [2](#0-1) , but by contrast `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` across the whole `archive? || unarchive?` decision [3](#0-2) , confirming the intended semantics that `review_stacks_enabled` must gate all provisioning behaviors.

Attacker flow: attacker forks the target repo (or, since `provision?` fires on `params.action == "opened"` for any PR against the repo, simply opens a PR from a branch they control), applies the repository's configured provisioning label to their own PR (label application by a non-collaborator triggers the `labeled` webhook event but that's irrelevant here — the label just needs to be present in the `pull_request.opened` payload's `labels` array, e.g., if labels can be pre-set at PR creation, or a collaborator/bot applies it before this is exploited), and GitHub emits a `pull_request` `opened` webhook. `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?`, which returns `true` despite `review_stacks_enabled=false`. `ReviewStackAdapter#find_or_create!` then calls `create!`, building a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled) and `environment: "pr#{params.number}"` [4](#0-3) , then enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [5](#0-4) . This queued stack is later checked out and its `shipit.yml` executed by the deploy pipeline, giving the PR author code execution on the deploy host via a repository whose owner explicitly disabled review stacks.

No existing guard intercepts this: webhook signature verification only authenticates that GitHub sent the payload, not that the payload's semantics are safe; `ExplicitParameters` only validates shape, not business logic; and there is no model-level validation on `ReviewStack` enforcing `repository.review_stacks_enabled` at creation time.

### Impact Explanation
This is Critical: it results in RCE on the deploy host via `Command`/`PTY.spawn` executing attacker-controlled `shipit.yml` steps checked out from the attacker's PR branch, on a repository whose owner explicitly disabled review stacks. It is repeatable against any repository configured with `provisioning_behavior=:allow_with_label` and `review_stacks_enabled=false`.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled=false` and `provisioning_behavior_allow_with_label?=true`, and the attacker's PR carries the configured provisioning label. Attacker cost is low — opening a PR and getting the label applied to it (the label being present is the only external dependency); no Shipit credentials, session, or GitHub App secrets are required. This is fully attacker-triggerable via a standard GitHub webhook flow.

### Recommendation
Fix operator precedence in `provision?` (and the identical bug in `ReopenedHandler#unarchive?`) by explicitly requiring `repository.review_stacks_enabled` to gate the entire expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
1. Create a `Shipit::Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "deploy-me"`.
2. Build `params` for a `pull_request` `opened` event with `labels: [{ name: "deploy-me" }]`, `head.ref` set to an attacker-controlled branch name.
3. Assert before: `repository.review_stacks_enabled == false`.
4. Call `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process` (or trigger via the appropriate webhook dispatch entrypoint).
5. Assert `Shipit::ReviewStack.count` increased by 1, and the created stack's `branch` equals `params.pull_request.head.ref`, and `environment == "pr#{params.number}"` — demonstrating a stack was provisioned for a repository with `review_stacks_enabled == false`, proving the equality (`review_stacks_enabled == false` implies `provision? == false`) is violated.
