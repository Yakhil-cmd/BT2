### Title
Blackholed (deactivated) paired device is still treated as a trusted correspondent for incoming device messages - (File: `device.js`)

### Summary
When a user chooses to silently ignore an unpair request (`conf.bIgnoreUnpairRequests = true`), the wallet does not remove the correspondent device — it only flags it with `is_blackhole=1` in `correspondent_devices` [1](#0-0) . This mirrors the CI4MS pattern: a revocation flag (`active=0` / here `is_blackhole=1`) is written to storage, but the authorization gate that decides whether an incoming session/message is trusted never re-checks that flag.

### Finding Description
The hub-message dispatcher in `device.js` decides whether an incoming `hub/message` comes from a known, trusted correspondent purely by looking up `correspondent_devices` on `device_address`, without filtering out blackholed rows: [2](#0-1) 

```
// check that we know this device
db.query("SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?", [from_address], function(rows){
    if (rows.length > 0){
        ...
        handleMessage(rows[0].is_indirect);
    }
    else{ // correspondent not known
        ...
    }
});
```

`is_blackhole` is set exactly when a device is meant to be deactivated as a correspondent while keeping the row for record-keeping purposes: [1](#0-0) 

Because `rows.length > 0` is the only condition, a device with `is_blackhole=1` is still routed through `handleMessage()` → `eventBus.emit("handle_message_from_hub", ...)`, exactly as if it were a fully active correspondent. The commented-out `is_blackhole` re-check is never present in this query, so the deactivation flag is entirely decorative for this code path — analogous to the CI4MS commented-out `active` re-check.

### Impact Explanation
Once routed through as a "known" correspondent, the blackholed device can drive `handleMessageFromHub` in `wallet.js`, which processes many message subjects without any additional confirmation, e.g. `arbiter_contract_shared` (auto-stores a contract on receipt) [3](#0-2) , `new_shared_address` (creates a shared/multisig address definition), `object`/`text` (delivered straight to the app), and `sign` (creates a `signing_request` for local addresses) [4](#0-3) . A device the user believed was revoked can therefore keep injecting shared-address/contract state, spamming signing prompts, or otherwise interacting with the wallet as a trusted peer — a wallet/contract-message-handling trust-bypass, not merely a low-impact annoyance, since it can pollute wallet state used later for fund movement (e.g., bogus shared addresses/contracts).

### Likelihood Explanation
This is directly reachable by any device that was previously paired and later "blackholed" (a normal, user-initiated deactivation flow, `conf.bIgnoreUnpairRequests=true`). No malicious hub, peer, or node behavior is required — it is purely a paired-device message reaching the local wallet, matching the "paired device" reachable-actor scope. It only triggers when the operator has opted into `bIgnoreUnpairRequests`, but this is a documented, supported configuration `exports.bIgnoreUnpairRequests` [5](#0-4) , not an edge case.

### Recommendation
Add `AND is_blackhole=0` (or equivalent) to the `correspondent_devices` lookup in `device.js`'s `hub/message` handler so blackholed devices are treated as unknown/untrusted, or explicitly reject/ignore any message when `rows[0].is_blackhole===1` before calling `handleMessage()`.

### Proof of Concept
1. Pair device B with device A; A sets `conf.bIgnoreUnpairRequests=true`.
2. B sends `removed_paired_device` — A sets `is_blackhole=1` for B instead of deleting the correspondent record [6](#0-5) .
3. B (still knowing the pairing keys) continues sending `hub/message` traffic (e.g., `arbiter_contract_shared`, `new_shared_address`, `sign`) to A's hub.
4. A's `handleJustsaying('hub/message', ...)` in `device.js` finds a `correspondent_devices` row for B (ignoring `is_blackhole`) and dispatches the message through `handleMessageFromHub`, which processes it exactly as if B were still an active, trusted correspondent.
