### Title
Server-Side Request Forgery via attacker-controlled arbiter address in arbiter contract flow - (File: arbiter_contract.js)

### Summary
The arbiter-contract feature lets a private-payment counterparty (someone the wallet owner pairs with via a device message) send an `arbiter_contract_offer` that includes an arbitrary `arbiter_address` chosen by that counterparty. When the wallet owner later interacts with the contract (opening a dispute, appealing, or checking the appeal fee), the wallet asks its hub for the URL registered for that `arbiter_address` and then makes an outbound HTTP(S) request to whatever URL is returned, without validating that the URL points to a legitimate, expected arbstore host. A malicious counterparty can register/point an "arbiter address" they control at an internal or attacker-chosen endpoint, causing the victim wallet to make server-side HTTP requests to that endpoint, carrying contract data (titles, text, addresses, encrypted contract payload).

### Finding Description
The chain begins with `arbiter_contract.store()` [1](#0-0)  which persists an incoming `arbiter_contract_offer`/`arbiter_contract_shared` device message from a paired counterparty, including the peer-supplied `arbiter_address` field, with no validation against a whitelist of trusted arbiters.

Later, when the local wallet owner acts on the contract (dispute, appeal, or fee lookup), the code resolves the arbstore URL purely from the (attacker-influenced) `arbiter_address`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The URL is only checked for being a non-empty string in `arbiters.js`, not for scheme, host, or being an allow-listed arbstore: [6](#0-5) [7](#0-6) 

Once resolved, the wallet performs an outbound HTTP POST to that URL with contract data (title, text, addresses, encrypted contract payload for the arbiter) using the unrestricted `httpRequest` helper: [8](#0-7) 

This directly parallels the reported bug class: a `baseurl`-like value (here, the "arbstore url" tied to an attacker-chosen `arbiter_address`) flows unchecked into a network request function (`http.request`/`https.get`), enabling SSRF (CWE-918).

### Impact Explanation
An attacker who can pair with the victim's wallet and act as counterparty in an arbiter-contract negotiation can steer the victim wallet into sending authenticated-looking HTTP POST requests (with contract details, party names, addresses, and — for disputes — an encrypted contract payload) to any host/port the attacker chooses (e.g., internal admin interfaces, cloud metadata endpoints, or other local services reachable from the wallet's network). This can result in confidentiality loss (leaking contract/party data to attacker infrastructure) and potential interaction with internal-only services, matching CVSS C:L/I:L/A:L. It does not directly cause loss of funds by itself, but is a concrete network-reachable SSRF triggerable by an unprivileged private-payment counterparty via a device message, consistent with the required "Medium" severity class.

### Likelihood Explanation
The offer flow is reachable by any device the victim has paired with (a normal precondition for using arbiter contracts) — the attacker only needs to be a private-payment counterparty proposing a contract with a self-controlled `arbiter_address`/arbstore URL, then get the victim to open a dispute or appeal (which are user-initiated but expected/social-engineerable actions within the normal arbiter-contract workflow, e.g., attacker deliberately disputes their own contract to force the victim to escalate). No hub or node compromise is required.

### Recommendation
Validate any arbstore/arbiter URL obtained from the hub before use: enforce `https://`, deny private/loopback/link-local IP ranges (SSRF-safe resolution), and consider requiring wallets to only trust a curated/allow-listed set of arbstore hosts rather than trusting whatever a device-message-supplied `arbiter_address` resolves to. Apply the same checks in `arbiters.js` `requestInfoFromArbStore` and `arbiter_contract.js` `httpRequest`.

### Proof of Concept
1. Attacker device pairs with victim and sends `arbiter_contract_offer` (handled via `wallet.js`, stored via `arbiter_contract.js:store`, `arbiter_contract.js:91-116`) with `arbiter_address` set to an address the attacker controls and for which the attacker's own hub answers `hub/get_arbstore_url` with `http://169.254.169.254` (or another internal target).
2. Victim accepts the contract, pays, then attacker forces a dispute scenario; victim wallet calls `openDispute()` (`arbiter_contract.js:262-319`), which calls `device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, ...)` and then `httpRequest(url, "/api/dispute/new", dataJSON, ...)` (`arbiter_contract.js:377-409`), sending an HTTP POST containing contract details to the attacker-chosen internal URL.
3. The attacker's endpoint receives the request/data, or the request interacts with an unintended internal service, confirming SSRF.

Note: I could not verify the exact server-side handler that lets an arbiter register/set its `hub/get_arbstore_url` mapping (not found in the indexed files), so the precise mechanism by which an attacker "registers" an arbitrary arbstore URL for a self-chosen `arbiter_address` on their own hub is inferred from the client-side trust model rather than directly observed in this codebase; a Devin session with full repo/hub-code access would be needed to confirm that registration path exactly.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
