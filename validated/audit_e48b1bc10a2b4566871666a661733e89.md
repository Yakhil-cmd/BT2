### Title
AA payments in fixed-denomination (indivisible) assets are silently dropped, permanently trapping AA balances - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) tries to send a payment message denominated in a `fixed_denominations` (indivisible) asset, `aa_composer.js`'s `sendUnit` logic detects the asset type, explicitly skips completing the payload for it, and later filters the whole message out of the unit before it is ever built and saved. The AA's state formula has typically already executed as if the transfer happened, but no payment output is actually created, and there is no fallback path (analogous to the reported `withdrawOneCoinI`/`withdrawOneCoinU` WETH-wrap workaround) that lets the funds be recovered by any other message or means. This mirrors the root cause of the Curve report: a special-cased asset type that the "withdraw"-like payment-sending code cannot handle, resulting in funds becoming permanently stuck at the contract/AA address with no way for the affected party to reclaim them.

### Finding Description
In `aa_composer.js`, inside `handleTrigger`'s `sendUnit`, when the composer processes payment messages by asset: [1](#0-0) 

it loads the asset properties via `storage.loadAssetWithListOfAttestedAuthors`, and if `objAsset.fixed_denominations` is true, it returns early with `cb()` without calling `completePaymentPayload` and without adding any outputs — the comment says "will skip it later". Later in the pipeline, any payment message with a `fixed_denominations` asset payload is filtered out of `messages` entirely: [2](#0-1) 

If this filtering leaves zero messages, the composer treats it as a benign empty response (`handleSuccessfulEmptyResponseUnit`), i.e. the AA's state changes (already computed by the formula engine before `sendUnit` was invoked) are committed as though the send succeeded, while no payment output for that indivisible asset is ever produced. There is no code path anywhere in `aa_composer.js` that converts, wraps, or otherwise makes an indivisible-asset balance held by an AA sendable — unlike the Curve report's suggested fix of wrapping ETH into WETH so it becomes sweepable through a different, always-available mechanism. Once an indivisible asset accumulates in an AA's balance (e.g., via a payment input to the AA, `updateFinalAABalances`, `aa_balances` table update at [3](#0-2)  ), the AA has no code path capable of ever paying it back out, because every attempt to include it in a payment message is filtered before the unit is assembled.

### Impact Explanation
Any indivisible (fixed-denomination) asset sent to an AA address (deliberately, by mistake, or as part of a designed workflow such as an escrow/vault AA that is supposed to redistribute assets) becomes permanently unspendable by that AA. This is a fund-freezing bug at the AA level: the tokens are consensus-valid, correctly credited, and visible in `aa_balances`, but the composer's payment-message pipeline has no capability to emit an output for them, so they can never leave the AA. This is analogous in severity to the ETH-stuck class of bug in the report — non-recoverable loss of asset value for the depositor/asset holder, with no owner/administrative bypass in ocore's case (unlike the Curve report, where at least the contract owner could sweep the stuck ETH — here even that escape hatch does not exist for the AA).

### Likelihood Explanation
Likelihood is high for any AA logic that is designed to receive and redistribute assets generically (vaults, exchanges, bridges, or auction/lottery-style AAs) if the asset happens to be indivisible. Since indivisible/fixed-denomination assets are a first-class, commonly-used asset type in the Obyte ecosystem, any AA author who does not specifically special-case and reject indivisible assets on receipt will unintentionally create a black hole for that asset once received; the trigger is simply "send a fixed-denomination asset as a payment input to any generic AA that later attempts a payment output in the same asset."

### Recommendation
Either (a) explicitly reject/bounce receipt of `fixed_denominations` assets by AAs at trigger-validation time so they can never accumulate in an AA balance, or (b) implement a genuine send path for indivisible assets in `aa_composer.js`'s `sendUnit`/`completePaymentPayload`, analogous to how `indivisible_asset.js` composes indivisible-asset payments for regular wallets, so AAs can actually move fixed-denomination balances instead of having those payment messages silently dropped.

### Proof of Concept
Not independently reproducible with the available tools (no execution environment); the trace above is based on static code reading of `aa_composer.js` lines 1312-1330 and 1356-1361, confirming the "skip it later" / filter-out behavior for `fixed_denominations` assets with no compensating send path elsewhere in the file. A concrete PoC would need to: (1) issue a fixed-denomination asset, (2) send a unit paying that asset to an AA address whose `bounce_fees` are satisfied in base, (3) have the AA's `messages` template attempt to pay the same asset back out, and (4) observe that the resulting response unit contains no payment message for that asset while `aa_balances` still shows the asset credited to the AA, confirming the funds are stuck.
