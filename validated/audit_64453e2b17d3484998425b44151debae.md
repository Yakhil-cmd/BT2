### Title
Cross-organization webhook forgery — signature verified against `repository.owner.login`/`organization.login` while stack lookup trusts a different `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from the *same untrusted JSON body* as the rest of the payload: `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`. [1](#0-0)  Once the signature is accepted, every event handler determines which repository/stacks to act on from a **different** field of the same body, `repository.full_name`. [2](#0-1)  For `push` events this drives `Repository.from_github_repo_name(...).stacks` and triggers `stack.sync_github(expected_head_sha: params.after)`. [3](#0-2) 

### Finding Description
In Shipit's multi-organization GitHub App configuration (documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization has its own `webhook_secret`, and `Shipit.github(organization:)` picks the app/secret for a given org key. [4](#0-3)  The binding the engine relies on is: *the organization whose secret authenticated the signature == the organization whose repository is acted upon*. This binding is never enforced.

`verify_signature` looks up the org used for HMAC verification purely from attacker-controlled JSON fields (`repository.owner.login` / `organization.login`), not from any fact independently known to the app (e.g., a fixed per-endpoint org, or verifying against *every* configured org before falling back). [5](#0-4)  Meanwhile, the actual repository/stack the handler mutates comes from `repository.full_name`, an entirely separate field of the same payload that is not covered by any cross-check against `repository_owner`. [2](#0-1)  `Repository.from_github_repo_name` performs a plain lookup by owner/name split out of `full_name`, with no relation back to which org's secret validated the request. [6](#0-5) 

Consequently, a party who legitimately controls one tenant's webhook configuration (e.g., an admin of `OrgA`, who — as shown in `docs/setup.md`'s "Using Multiple Github Applications" section — configures their own org's GitHub App and therefore knows `OrgA`'s `webhook_secret`) can craft a signed payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's app/secret and the HMAC validates), and
- `repository.full_name` = `"OrgB/target-repo"` (a repository belonging to a completely different, unrelated tenant `OrgB`).

The signature check passes (it was computed correctly with `OrgA`'s secret over the raw body), but the `PushHandler` (and any other handler keying off `repository.full_name`) will locate and act on `OrgB`'s stacks. [3](#0-2) 

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding. A tenant admin with zero authorization on `OrgB` can forge a `push` webhook that Shipit accepts as authentic and then dispatches against `OrgB`'s stacks, causing `Stack#sync_github` to run with an attacker-chosen `expected_head_sha`, and — since `push` handling directly feeds continuously-deployed stacks — can trigger unauthorized deploy activity on a repository the attacker has no access to. This matches the "unauthorized deploy" / cross-repository-write impact class.

### Likelihood Explanation
Requires a Shipit installation configured with multiple GitHub-organization tenants (explicitly documented as a supported configuration), and requires the attacker to control the webhook secret of at least one of the configured organizations (their own tenant) — a credential they legitimately possess for their own org, not one they need to steal from the victim. No other authentication, session, or write access to the victim org/repository is needed; the only fields that need to differ are `repository.owner.login` (or `organization.login`) versus `repository.full_name` in the JSON body, which are fully attacker-controlled within their own signed request.

### Recommendation
Enforce that `repository.owner.login` (used to pick the verifying app/secret) equals the owner segment of `repository.full_name` (used for the actual stack lookup) before dispatching to handlers, e.g. compare `repository_owner` against `params.dig('repository', 'full_name')&.split('/')&.first` and reject on mismatch (`head(422)`). Alternatively, derive the target repository/stacks strictly from the same field/org that was cryptographically authenticated, never trusting a second independent field for authorization-relevant routing.

### Proof of Concept
1. Configure Shipit with the multi-org schema (`config/secrets.yml`) containing `OrgA` (attacker-administered, webhook secret known to attacker) and `OrgB` (victim, has a Shipit stack for `OrgB/target-repo` with continuous deployment enabled).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and the signature validates successfully. [7](#0-6) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgB/target-repo')` (through `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on `OrgB`'s stack, despite the request never being authenticated by `OrgB`'s credentials. [3](#0-2)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
