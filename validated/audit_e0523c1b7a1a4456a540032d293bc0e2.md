Confirmed: `Command#unbundled_env` (`lib/shipit/command.rb`) merges `@env` (which includes `machine_env`) *after* the sanitized `PATH`, so an attacker-controlled `PATH` key fully replaces the hardened `PATH`. Combined with `TaskCommands#env` merging `deploy_spec.machine_env` (sourced directly from the fork branch's `shipit.yml` for `ReviewStack`s), this gives fork PR authors control over `PATH` for spawned deploy processes.

### Title
Fork-controlled `machine.environment.PATH` overrides the sanitized `PATH` in `Command#unbundled_env`, enabling RCE via bare-command hijack - (File: `lib/shipit/command.rb`)

### Summary
`Shipit::Command#unbundled_env` builds the spawn environment as `BASE_ENV.merge('PATH' => safe_path).merge(@env.stringify_keys)`, so any key in `@env` — including `PATH` — silently overwrites the hardened `PATH` value. Because `TaskCommands#env` merges `deploy_spec.machine_env`, which comes verbatim from the `machine.environment` section of the `shipit.yml` checked out from the task's commit, an unprivileged fork PR author who gets a `ReviewStack` provisioned for their branch can set `PATH: ./bin:/usr/bin`, causing any bare command name later invoked in a deploy/task step to resolve to an attacker-supplied binary in the checked-out working directory.

### Finding Description
The broken binding is: **intended** `PTY.spawn(env, ...)['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every spawned Task, regardless of `shipit.yml` content, vs. **actual** `PTY.spawn(env, ...)['PATH'] == @env['PATH']` whenever `@env` (the merged task/deploy env) contains a `PATH` key.

Code path:
1. `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` verbatim [1](#0-0)  — this is loaded straight from the repository's `shipit.yml`, and for `FileSystem`-backed specs the raw `machine.environment` values are preserved rather than being replaced with `discover_machine_env` defaults (`discover_machine_env.merge(machine_env)`, with `machine_env` winning) [2](#0-1) .
2. `TaskCommands#env` merges `deploy_spec.machine_env` into the environment hash used to build every `Command` for install/deploy/rollback/task steps [3](#0-2) .
3. `Command#unbundled_env` computes the final spawn environment: `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` [4](#0-3) . Because `.merge(@env...)` is applied last, any `PATH` entry inside `@env` (originating from `machine.environment`) wins over the hardened path.
4. `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [5](#0-4) , so the child process — and every bare command name it invokes internally without an absolute path — is resolved using the attacker-controlled `PATH`.
5. For `ReviewStack`s, `shipit.yml` is read from the exact commit/branch tied to the PR (`stack.branch = params.pull_request.head.ref` set at creation time by `ReviewStackAdapter#stack_attributes`) [6](#0-5) , i.e., content fully controlled by the fork PR author, and `DeploySpec::FileSystem` loads that checked-out `shipit.yml` to compute `machine_env`.

An attacker opens a PR against a repository with review stacks enabled (Allow All, or Allow With Label + self-applied label since they can label their own PR), commits a `shipit.yml` containing:
```yaml
machine:
  environment:
    PATH: "./bin:/usr/bin"
```
and a `./bin/<some-bare-command-name>` script matching a command name used bare in any deploy/task step (their own `shipit.yml` steps, or built-in discovery steps like `bundle`, `npm`, etc., which are invoked without absolute paths). Once the review stack is provisioned and a task/deploy runs, `Command#unbundled_env` resolves `PATH` to the attacker value, and the attacker's binary executes on the deploy host with the Shipit worker's privileges.

Existing guards do not prevent this: there is no allow/deny-list on `machine.environment` keys (`EnvironmentVariables#permit` filters interpolation targets in argument strings, not which keys can be injected into the process environment), no validation on `DeploySpec#machine_env`, and `Command#unbundled_env`'s "safe" `PATH` merge occurs *before* the untrusted `@env` merge instead of after.

### Impact Explanation
This is Critical — Remote Code Execution on the Shipit deploy host. Any bare (non-absolute) command name executed by any step of the affected review stack's task (dependency install, deploy step, rollback step, or custom task step, including Shipit's own auto-discovered `bundle`/`npm`/etc. steps) can be hijacked to run attacker-supplied code with the privileges of the Shipit worker process. This is scoped per-repository (the fork PR only affects tasks running for stacks/tasks derived from that PR's branch/commit), but within that scope it is fully repeatable for every task run against the review stack (install_dependencies, deploy, rollback, custom tasks) as long as the poisoned `shipit.yml` is checked out.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that includes the attacker's PR (Allow All trivially qualifies; Allow/Prevent With Label can be satisfied by the attacker labeling their own PR, since they own it). The attacker needs no Shipit session, API token, or GitHub team membership — only the ability to open a PR from their own fork/branch, which is available to any GitHub user with fork/PR rights on a public repo using review stacks. Cost is minimal (a two-line `shipit.yml` change plus a malicious binary in the PR branch), and the exploit is deterministic and repeatable on every task run for that review stack.

### Recommendation
In `Command#unbundled_env`, compute the safe `PATH` last so it cannot be overridden by `@env`, or explicitly strip/ignore any `PATH` key from `@env` (and specifically from `DeploySpec#machine_env`) before merging into the spawn environment:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge(
    'PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  )
end
```
Additionally, consider disallowing `PATH` (and other security-sensitive variables like `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`) from being set via `machine.environment` in untrusted `shipit.yml` files, especially for `ReviewStack`s sourced from forks.

### Proof of Concept
minitest (`test/unit/command_test.rb` style):
```ruby
test "#unbundled_env does not allow @env to override the sanitized PATH" do
  malicious_path = "./bin:/usr/bin"
  command = Command.new('echo hi', env: { 'PATH' => malicious_path }, chdir: '.')

  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

  # This currently FAILS on unpatched code because the attacker-controlled
  # PATH ends up verbatim in the env passed to PTY.spawn.
  refute_equal malicious_path, command.unbundled_env['PATH']
  assert_equal safe_path, command.unbundled_env['PATH']
end
```
This demonstrates that `Command#unbundled_env` carries an attacker-supplied `PATH` verbatim into the hash that `PTY.spawn` receives, confirming the binding violation end-to-end from `DeploySpec#machine_env`/`TaskCommands#env` through `Command#unbundled_env`.
