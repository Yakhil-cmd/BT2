### Title
Unvalidated duplicate `asset` message attestors trigger an uncaught DB exception that crashes the node - (File: writer.js, mysql_pool.js)

### Summary
An unprivileged unit author can define an `asset` message whose `attestors` array contains duplicate addresses. `writer.js` inserts every entry from that array into the `asset_attestors` table without deduplication and without an `INSERT IGNORE`, while the MySQL connection wrapper is designed to throw on *any* SQL error, which kills the entire node process — the same "DML causes availability loss" bug class as CVE‑2016‑5609.

### Finding Description
When persisting a unit whose payload contains an `asset` message, `writer.js` iterates `asset.attestors` and issues one `INSERT INTO asset_attestors (unit, message_index, asset, attestor_address) VALUES(?,?,?,?)` per entry, with no `IGNORE` modifier and no in-code deduplication: [1](#0-0) 

Compare this to other insert loops in the same function, such as `unit_witnesses`/`witness_list_hashes` or `definitions`, which explicitly use `conn.getIgnore()` to tolerate constraint violations: [2](#0-1) 

If the underlying table enforces uniqueness on `(unit, message_index, asset, attestor_address)` (or an equivalent index), a crafted `asset` message with a repeated attestor address in the `attestors` array reaches this insert loop and produces a duplicate-key/constraint SQL error. The database layer is not designed to tolerate this: `mysql_pool.js` wraps every query so that *any* error thrown by the driver is re-thrown out of the callback instead of being handled — this is an explicit, acknowledged "hack to make all errors throw exception that would kill the program": [3](#0-2) [4](#0-3) 

Because `saveJoint` in `writer.js` runs under the global write mutex and is invoked for every unit that passes validation (including units posted by ordinary, unprivileged network participants), an attacker only needs to get a single crafted `asset` definition unit accepted by `validation.js` and then processed by the writer to hit the faulting `INSERT`: [5](#0-4) 

Nothing in the reachable validation path (`aa_validation.js`/`validation.js` message-type switch) was found to reject duplicate entries inside `asset.attestors` before the unit reaches `writer.js`, so the malformed-but-"valid" unit is queued for the same DML path that crashes on constraint violation.

### Impact Explanation
On any full/hub node running MySQL storage (the deployment mode `mysql_pool.js` targets), a single attacker-crafted unit can force an uncaught exception that terminates the node process while it is inside the global write-lock section of `saveJoint`. This is a direct availability impact: the node stops confirming/relaying units, and because the crash occurs mid-write, any nodes racing to apply the same DAG update could also disagree on what got committed if some had already partially applied dependent queries before the crash. This matches the "DML impacting availability" class described in CVE‑2016‑5609, translated to ocore's DAG/DB writer.

### Likelihood Explanation
The trigger requires only posting one ordinary unit with an `asset` message containing a duplicate address in `attestors` — no special privilege, hub cooperation, or timing race is needed. The bug is deterministic once the record reaches the writer, assuming the table has a uniqueness constraint on the combination used in the `INSERT`. This makes the likelihood high for any deployment using MySQL storage, though it is not exploitable against SQLite-backed light/full nodes that don't route through `mysql_pool.js`'s throw-on-error wrapper.

### Recommendation
- Deduplicate `asset.attestors` in `validation.js`/`aa_validation.js` before acceptance, rejecting units with repeated attestor addresses.
- Use `conn.getIgnore()` (as done elsewhere in `writer.js`) for the `asset_attestors` insert to make it resilient to duplicate entries.
- Reconsider the "throw on any DB error" design in `mysql_pool.js`; at minimum, differentiate expected constraint violations (which should be handled gracefully) from truly unexpected DB failures.

### Proof of Concept
1. Craft and post a unit containing an `asset` message where `payload.attestors` includes the same address twice, e.g. `attestors: ["ADDR1", "ADDR1"]`.
2. The unit passes `validation.js` message-type checks (no dedup enforced there).
3. `writer.saveJoint` executes the `asset_attestors` insert loop, issuing two `INSERT` statements with identical `(unit, message_index, asset, attestor_address)` keys.
4. If the table enforces uniqueness on that tuple, the second `INSERT` fails; `mysql_pool.js`'s query wrapper throws the error instead of passing it to a handled callback, crashing the node process.

**Note on confidence:** I was unable to directly confirm from the indexed schema files (`initial-db/byteball-mysql.sql`) whether `asset_attestors` carries an explicit uniqueness constraint on `(unit, message_index, asset, attestor_address)`, since the exact `CREATE TABLE asset_attestors` definition was not returned by search. The core, confirmed facts are: (a) the insert loop performs no deduplication and omits `IGNORE` unlike sibling inserts in the same function, and (b) `mysql_pool.js` is explicitly documented to convert any SQL error into a fatal thrown exception. If the schema does not enforce such a constraint, this specific PoC would not fault, though the general crash-on-any-DB-error design remains a systemic availability risk for any other insert path that can be driven into a constraint violation by unprivileged input.
