### Title
`handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` Can Execute Asset Transfers When Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge has an `isRunning` flag that the owner can set to `false` to halt all bridge operations. All three outbound request functions correctly enforce this flag. However, all three inbound handle functions — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — do not check `isRunning`, allowing operators to continue executing asset transfers (KAIA, ERC20, ERC721) to users even when the bridge is in a stopped state.

---

### Finding Description

`BridgeTransfer.sol` declares `bool public isRunning = true` and exposes `setRunningStatus(bool)` (owner-only) to halt the bridge. [1](#0-0) [2](#0-1) 

All three outbound (request) paths enforce this flag:

- `_requestKLAYTransfer`: `require(isRunning, "stopped bridge")` at line 108
- `_requestERC20Transfer`: `require(isRunning, "stopped bridge")` at line 88
- `_requestERC721Transfer`: `require(isRunning, "stopped bridge")` at line 85 [3](#0-2) [4](#0-3) [5](#0-4) 

However, all three inbound (handle) functions carry **no** `isRunning` check — only `onlyOperators` (and `nonReentrant` for KLAY):

```solidity
// BridgeTransferKLAY.sol L62-100
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    // ... transfers _value KLAY to _to
    (bool ok, ) = _to.call.value(_value)("");
}

// BridgeTransferERC20.sol L32-73
function handleERC20Transfer(...) public onlyOperators {
    // ... mints or safeTransfers ERC20 to _to
}

// BridgeTransferERC721.sol L29-71
function handleERC721Transfer(...) public onlyOperators {
    // ... mints or transferFrom ERC721 to _to
}
``` [6](#0-5) [7](#0-6) [8](#0-7)

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` to halt the bridge — the expected action during an incident — operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to push through inbound value transfers. In lock-mode (`modeMintBurn = false`) this drains KAIA or ERC20/ERC721 tokens held by the bridge contract to arbitrary `_to` addresses. In mint-burn mode it mints new tokens. Either path constitutes an unauthorized transfer or mint of bridged assets against the owner's explicit halt intent, matching the allowed impact gate.

Additionally, `_updateHandleNonce` advances `lowerHandleNonce` and `recoveryBlockNumber` as a side-effect of each handle call, permanently mutating bridge accounting state even while the bridge is supposed to be frozen. [9](#0-8) 

---

### Likelihood Explanation

Operators are registered by the owner (`registerOperator`, owner-only), so they are semi-trusted. However, the `deregisterOperator` function itself notes that outstanding votes by a deregistered operator are **not** revoked, meaning a previously-cast vote can still be consumed after deregistration. [10](#0-9) 

This means: even if the owner stops the bridge and immediately deregisters all operators, any operator vote already cast (but not yet threshold-reached) can be completed by a remaining operator, executing the transfer after the halt. The window is narrow but real. The primary scenario is operators acting in good faith but not realizing the bridge is stopped, or a compromised operator key acting during the halt window.

---

### Recommendation

Add `require(isRunning, "stopped bridge")` at the top of each handle function, consistent with the request-side enforcement:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
``` [11](#0-10) [12](#0-11) [13](#0-12)

### Proof of Concept

1. Owner deploys `Bridge` with `modeMintBurn = false` and funds it with 100 KAIA.
2. Owner registers operator `op`.
3. User on the child chain calls `requestKLAYTransfer` — a `RequestValueTransfer` event is emitted with `requestNonce = 0`.
4. Owner detects an incident and calls `setRunningStatus(false)`. Bridge is now stopped. `isRunning == false`.
5. Operator `op` calls `handleKLAYTransfer(txHash, from, victim, 100 ether, 0, blockNum, "")`.
6. The call succeeds — no `isRunning` check exists. The bridge sends 100 KAIA to `victim`, `lowerHandleNonce` advances, and `recoveryBlockNumber` is updated — all while the bridge is in a halted state.
7. The owner's emergency halt has been bypassed; bridge funds are transferred and accounting state is mutated. [14](#0-13) [15](#0-14)
