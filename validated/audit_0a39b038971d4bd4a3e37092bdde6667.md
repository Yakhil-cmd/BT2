### Title
Unverified webhook `membership` events let an attacker self-grant `Shipit.github_teams` membership - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` writes a `Membership` row purely from the webhook JSON body (`team.id`, `member.login`, `action`) with `team.add_member(member)`, never confirming via GitHub's API that the named user is actually a member of that team. Because `User#authorized?` grants Shipit access solely based on the presence of a matching `Membership` row, forging (or replaying under the pre-existing signature-verification gap) a `membership` `action:'added'` event is sufficient to grant an attacker's GitHub login authorization to Shipit.

### Finding Description
The broken binding is: `Membership(user_id, team_id) exists` should be equivalent to `GitHub API confirms member.login ∈ team.id`, but the code enforces `Membership(user_id, team_id) exists ⇐ payload.action == 'added'` with no GitHub cross-check.

Path: `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, gated only by `verify_signature` (line 6), which calls `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83). That method `return[s] true unless webhook_secret` — i.e., if no `webhook_secret` is configured for the organization, signature verification is a no-op and any payload is accepted as authentic.

Once past that gate, `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) does:
```ruby
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
case params.action
when 'added'
  team.add_member(member)
```
`Team#add_member` (app/models/shipit/team.rb:41-43) is `members.append(member) unless members.include?(member)` — a pure DB write. Contrast this with `Team#refresh_members!` (team.rb:45-51), which fetches `github_api.get(api_url).rels[:members]` from GitHub before updating `self.members`. `add_member` has no equivalent authoritative check.

`User#authorized?` (app/models/shipit/user.rb:80-82) is:
```ruby
@authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
```
So any `Membership` row referencing a team in `Shipit.github_teams` unlocks authorization, regardless of provenance.

Attacker request: a forged (or, if `webhook_secret` is unset for the org, simply unsigned) `POST /webhooks` with `X-Github-Event: membership` and body `{"action":"added","team":{"id":<id of a Shipit.github_teams team>,"name":"...","slug":"...","url":"..."},"organization":{"login":"..."},"member":{"login":"<attacker-login>"}}`. This creates/finds the `Team` and calls `find_or_create_by_login!` for the attacker's real GitHub login, then blindly appends them as a member — no `Octokit`/GitHub API call is made to confirm the claim, matching the described `MembershipHandler#process` behavior exactly.

Existing guards don't prevent this: `drop_unhandled_event` only checks that a handler exists for the event type; `ExplicitParameters` (`params do ... end` block) only validates JSON shape, not authenticity of the claimed membership; `force_github_authentication` and `require_permission!` operate on session-authenticated users, not on webhook-created `Membership` rows themselves.

### Impact Explanation
A successful forged `membership` webhook creates a durable `Membership` row tying the attacker's real GitHub login to a `Shipit.github_teams` team, which is read directly by `User#authorized?` to gate all Shipit session authorization. This is a direct escalation into `Shipit.github_teams` authorization (High category) and, combined with the ability to forge the initiating webhook, becomes a full authentication bypass into Shipit (Critical) since the attacker can then log in as an authorized Shipit user and perform deploys/rollbacks/merges. The attack is repeatable against any team id known/guessable and persists until manually removed from the `memberships` table.

### Likelihood Explanation
The precondition is the pre-existing webhook signature-verification gap (unsigned/misconfigured `webhook_secret`, or another forgery vector referenced as "the same gap") allowing an unauthenticated `POST /webhooks` to be accepted as genuine. Given that, the attacker needs only to know or discover the numeric GitHub team `id` of a team listed in `Shipit.github_teams` (discoverable via public GitHub org API) and their own GitHub login — no Shipit credentials, session, or GitHub secrets are required. The `MembershipHandler` code itself performs zero additional verification, so exploitation cost after the precondition is trivially low and fully repeatable for any organization/team combination configured in `Shipit.github_teams`.

### Recommendation
Do not trust webhook-reported membership changes as ground truth. On receiving a `membership` `added` event, call `Shipit.github(organization:).api` (e.g., `org_team_membership` or equivalent) to confirm the named user is actually a current member of the GitHub team before writing/keeping the `Membership` row — mirroring the approach already used in `Team#refresh_members!`. Alternatively, treat webhook membership events only as a signal to trigger `refresh_members!` (an authoritative GitHub API resync) rather than performing the mutation directly from payload data.

### Proof of Concept
```ruby
test "MembershipHandler#process trusts webhook payload without calling GitHub API" do
  organization_login = 'shopify'
  team = shipit_teams(:some_configured_team) # a Shipit.github_teams entry
  attacker_login = 'attacker'

  payload = {
    'action' => 'added',
    'team' => { 'id' => team.github_id, 'name' => team.name, 'slug' => team.slug, 'url' => team.api_url },
    'organization' => { 'login' => organization_login },
    'member' => { 'login' => attacker_login }
  }

  # No Octokit/HTTP expectation set up at all — proves no cross-check occurs.
  Shipit.github(organization: organization_login).api.expects(:org_teams).never
  Shipit.github(organization: organization_login).api.expects(:org_team_membership).never

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call

  attacker = Shipit::User.find_by!(login: attacker_login)
  assert team.members.include?(attacker), "attacker was added to team without any GitHub verification"
  assert attacker.authorized?, "attacker gained Shipit.github_teams authorization purely from an unverified webhook payload"
end
```
This demonstrates both sides of the equality diverge: `Membership(attacker, team) exists == true` while `GitHub API confirms attacker ∈ team == unknown/never checked`.
