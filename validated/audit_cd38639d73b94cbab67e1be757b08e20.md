### Title
Webhook signature verification uses an unverified payload field to select the per-organization secret, and silently accepts unsigned events when that organization has no `webhook_secret` configured, allowing commit-status forgery and unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate a payload against based on a field taken directly from that same, not-yet-verified payload (`repository.owner.login` / `organization.login`). It then calls `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally when that organization's `webhook_secret` is blank — a state explicitly documented as optional (`docs/setup.md`, `config/secrets.development.example.yml`). The binding the report's bug class targets — "a payload field acted on but never covered by the verified signature" — is broken here: the organization-selection field is read from the body before any cryptographic check occurs, and for any org configured without a secret, the entire signature check is a no-op.

### Finding Description [1](#0-0) 
`verify_signature` computes `repository_owner` straight from `params.dig('repository','owner','login')` (attacker-supplied JSON body) and uses it to look up the GitHub App config via `Shipit.github(organization: repository_owner)` [2](#0-1) . The resulting app's `verify_webhook_signature` is: [3](#0-2) 

`return true unless webhook_secret` means any organization deployed without a webhook secret accepts **any** POST to `/webhooks`, signed or not, as authentic. This is a supported configuration state, not a misconfiguration Shipit rejects: the setup docs list `webhook_secret` as "(optional)" [4](#0-3)  and the example secrets templates ship with `webhook_secret: # nil` for both single- and multi-org schemas [5](#0-4) .

Once past `verify_signature`, the `StatusHandler` writes GitHub commit-status fields (`state`, `description`, `target_url`, `context`) directly into `Commit#create_status_from_github!` without any server-side call back to the GitHub API to confirm they are real: [6](#0-5) [7](#0-6) 

A newly created `success` `Status` triggers `schedule_continuous_delivery`, which (combined with `Commit#deployable?` returning true once required CI is green) drives `Stack#trigger_continuous_delivery`/`trigger_deploy` for stacks with continuous delivery enabled [8](#0-7) [9](#0-8) .

The equality that should hold but doesn't:
`organization whose signature was cryptographically verified == organization/stack whose commit-status/state is written and acted upon (auto-deploy trigger)`.
For any Shipit deployment where at least one configured GitHub organization lacks a `webhook_secret` (an officially supported, documented setup), this equality collapses: the "verification" step is a no-op for that organization, yet the handler still writes trusted state (`Status`) and triggers deploy automation for whatever repository/stack the forged payload names.

### Impact Explanation
An unauthenticated network attacker (no Shipit session, no GitHub credentials, no `ApiClient` token) can POST directly to the public `/webhooks` endpoint with `X-Github-Event: status` and a JSON body naming any commit SHA tracked by Shipit under an organization configured without a `webhook_secret`. This fabricates a `success` CI status on that commit, satisfying `Commit#deployable?` and, for stacks with `continuous_deployment` enabled, causing Shipit to automatically trigger a deploy of attacker-chosen code that was never actually validated by real CI — an unauthorized deploy driven entirely by forged webhook data. This matches the report's "unauthorized deploy/rollback" Critical-impact category defined in scope.

### Likelihood Explanation
Likelihood depends on operational configuration: it is only exploitable for GitHub organizations configured in `config/secrets.yml` without a `webhook_secret`. Because the setup documentation and shipped example templates present the secret as optional and leave it blank by default, and because multi-org installations configure secrets per-organization independently (so one org can be secured while another is overlooked), this is a realistic operational-drift scenario rather than a purely theoretical one — an admin can correctly secure their primary org while forgetting a secondary org, and the vulnerability requires zero attacker privileges once that gap exists.

### Recommendation
- Do not select the verification secret from an unverified field of the same payload being verified; verification should not silently succeed for organizations lacking a secret. At minimum, require `webhook_secret` to be present for every configured organization and refuse (422) any event for organizations without one, rather than treating "no secret configured" as "always verified."
- Consider not trusting webhook `status`/`check_run` payload fields (`state`, `description`, `target_url`) directly; verify commit status/state via an authenticated call to the GitHub API using the app's own installation token before creating a `Status` record, rather than persisting attacker-suppliable JSON fields verbatim.

### Proof of Concept
1. Configure Shipit with two GitHub organizations per `docs/setup.md`'s multi-org schema; leave `webhook_secret` blank for `OrgB` (the documented default/optional state).
2. Identify a Shipit stack tracking a repository under `OrgB` with `continuous_deployment: true`, and note a pending/未-deployed commit `SHA`.
3. As an anonymous attacker, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "SHA",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/some-repo" }
}
```
No `X-Hub-Signature` header is required — `GitHubApp#verify_webhook_signature` returns `true` unconditionally per [10](#0-9)  because `OrgB` has no configured secret.
4. `StatusHandler#process` creates a `success` `Status` on the commit [6](#0-5) , `Commit#deployable?` becomes true, and `schedule_continuous_delivery` triggers an automatic deploy of the attacker-targeted commit.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "event=#{event}",

      ].join(' '))
    end
```

**File:** lib/shipit/github_app.rb (L76-83)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
