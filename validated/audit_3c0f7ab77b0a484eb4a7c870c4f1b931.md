### Title
Cross-organization webhook forgery lets an attacker's own org secret authorize writes against a victim org's stacks — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`), a field read out of the same untrusted JSON body it is about to authenticate. All downstream event handlers, however, resolve *which Shipit `Stack`/`Commit` to mutate* using a different field from that same body: `repository.full_name`. An attacker who legitimately owns/administers a GitHub organization that is configured in this Shipit instance (and therefore knows that org's `webhook_secret`) can sign a payload with their own secret while setting `repository.full_name` to point at a *different* organization's repository/stack tracked by the same Shipit instance, causing the engine to accept the signature and then act on the victim's data.

### Finding Description
The equality this analog breaks is: **the organization that authenticated the request ≠ the repository that the handler actually writes to.**

- `verify_signature` derives `repository_owner` from the payload and uses it purely to pick which app config/secret verifies the signature: [1](#0-0) [2](#0-1) 

- Once the signature check passes, the *entire raw payload* — including `repository.full_name`, which is never tied to the org used for verification — is handed unscoped to every registered handler: [3](#0-2) 

- The base `Handler` class (and every subclass such as `PushHandler`) resolves the target `Stack`/`Repository` using `repository.full_name`, a field completely independent of `repository.owner.login`: [4](#0-3) 

- `StatusHandler` is the most impactful case: it looks up commits **globally by `sha`** (not even scoped by stack/repository) and calls `create_status_from_github!`, which can flip a real commit's CI status to `success`: [5](#0-4) 

- `Status#schedule_continuous_delivery` fires on every new status and, if the owning stack has continuous deployment enabled, schedules `ContinuousDeliveryJob`, which will deploy the commit once it appears "deployable": [6](#0-5) [7](#0-6) [8](#0-7) 

Because Shipit is explicitly designed to serve multiple GitHub organizations from one `/webhooks` endpoint, each with its own `webhook_secret` (see multi-org secrets configuration), and because `repository.owner.login` (used to pick the secret) and `repository.full_name`/`sha` (used to pick the write target) are two independent, unauthenticated fields inside the same attacker-crafted body, an attacker who is a legitimate administrator of org A (and thus knows org A's `webhook_secret`) can forge a `status` (or `push`) event where `repository.owner.login = "org-a"` but the affected `sha`/`full_name` belong to org B's stack.

### Impact Explanation
This falls under the High-impact category "escalation into `Shipit.github_teams` authorization" is not directly hit, but it does hit "unauthorized deploy" — the rules' Critical impact bucket — because a forged `status` webhook signed with an attacker-controlled org secret can mark an arbitrary victim commit as `success`, and if that commit's stack has `continuous_deployment` enabled, this triggers an actual, unauthorized deploy of that commit via `ContinuousDeliveryJob`. Additionally it constitutes a cross-repository write: an org's webhook credential is used to mutate commit/status/stack state belonging to a different, unrelated repository/stack tracked by the same Shipit instance.

### Likelihood Explanation
Likelihood is limited to installations where multiple organizations share one Shipit deployment (a documented, supported configuration — see `config/secrets.development.shopify.yml` showing two orgs) and where the attacker legitimately controls (or has been granted) a GitHub App/webhook secret for at least one of those organizations. No repository write access, GitHub token, or Shipit session/ApiClient is required — only knowledge of one org's `webhook_secret`, which the rules permit as an unprivileged-attacker starting point since it is not itself a Shipit-issued credential like `api_clients_secret` or a session.

### Recommendation
Bind the field used for signature-secret selection to the same field used for authorization of the write target. Concretely: after verifying the signature with the app selected by `repository.owner.login`, re-validate that `repository.full_name`'s owner segment matches `repository.owner.login` (or the organization determined during verification) before dispatching to handlers, and have `StatusHandler` scope its `Commit.where(sha: ...)` lookup by the same verified organization/repository rather than a global, cross-tenant `sha` search.

### Proof of Concept
1. Shipit instance configured with two orgs, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per documented multi-org setup).
2. Attacker administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha belonging to org-b/some-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret [1](#0-0) .
6. `StatusHandler#process` finds the real commit by `sha` (regardless of organization) and creates a `success` status on it [9](#0-8) .
7. If `org-b`'s stack has continuous deployment enabled, this triggers an unauthorized deploy of the victim's commit via `ContinuousDeliveryJob`.
