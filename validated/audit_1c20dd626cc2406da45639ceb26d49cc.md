### Title
Cross-organization `Team` membership injection via `github_id`-only lookup in `MembershipHandler` bypasses org isolation, escalating into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` correctly verifies a `membership` webhook's signature against the `webhook_secret` of the organization named in the payload's `organization.login` field, but that same attacker-controlled `organization.login` is never re-checked when `MembershipHandler` mutates a `Team` row. [3](#0-2)  Because `find_or_create_team!` looks up `Team` solely by `github_id` (a value fully controlled by the attacker's JSON payload), an attacker who legitimately administers their own org `O_attacker` on a multi-tenant Shipit instance can target an existing `Team` row belonging to a different org `O_victim` and insert themselves as a member of it. [4](#0-3) 

### Finding Description
The broken binding is: `organization that verified the webhook signature (O_attacker)` == `organization owning the Team row that get mutated (should be O_attacker, but is actually O_victim)`.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the raw request body against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [5](#0-4)  For a `membership` event there is typically no `repository` key, so `repository_owner` resolves to the attacker-supplied `organization.login`. In a multi-org Shipit deployment (documented under "Using Multiple Github Applications"), each org has its own `webhook_secret` configured by that org's own admin, so an attacker who administers `O_attacker` legitimately knows `O_attacker`'s `webhook_secret` and can produce a valid signature for a payload whose `organization.login` is `"O_attacker"`. [6](#0-5) 
2. `WebhooksController#create` then dispatches the **entire raw parsed payload**, unfiltered, to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6) 
3. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. [8](#0-7)  The `github_id` is attacker-supplied. If it matches a pre-existing `Team` row for `O_victim`, `find_or_create_by!` returns that row and the `do |team| ... end` initialization block (which would set `team.organization`) is **not executed**, since the record already exists — the row keeps its true `organization = O_victim`.
4. `process` then does `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` (the attacker's own real GitHub login), creating a `Membership` row binding the attacker's `User` to the `O_victim`-owned `Team`. [9](#0-8) [10](#0-9) 
5. No code in this path validates that the target `Team`'s `organization` column matches the verified/signing organization, and the `ExplicitParameters` schema for `MembershipHandler` only requires field presence/types, not cross-field consistency. [11](#0-10) 
6. If that `Team`'s `id` is among `Shipit.github_teams.map(&:id)` (the set of teams configured for the default org's OAuth authorization), the attacker's user now satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?` and `authorized?` returns `true`, which is exactly the check gating the whole application via `force_github_authentication`. [2](#0-1) [1](#0-0) [12](#0-11) 

### Impact Explanation
An attacker legitimately controlling one tenant org on a shared/multi-org Shipit deployment can inject a `Membership` record binding their own real GitHub account to any `Team` row already present in Shipit's database, as long as they know or can guess that team's GitHub-side numeric `id`. If the targeted team is one referenced by `Shipit.github_teams` (the authorization gate), the attacker gains full authenticated access to the Shipit instance — every stack, deploy, rollback and merge action available to authorized users — without ever being a real member of the gating GitHub team or organization. This is a cross-tenant authorization escalation matching the "High - escalation into `Shipit.github_teams` authorization" category. It is repeatable indefinitely (each `added`/`removed` webhook can toggle membership) and the blast radius spans every tenant sharing the Shipit instance, since any tenant's webhook credentials can be used to write `Team`/`Membership` rows belonging to any other tenant.

### Likelihood Explanation
This requires: (a) the Shipit instance to be configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup) so that a webhook signed by `O_attacker`'s own secret is accepted; (b) a `Team` row for `O_victim` (or the default/gating org) to already exist in Shipit's database with a known/guessable `github_id`; and (c) that team to be one referenced in the gating org's `oauth.teams` config. Precondition (a) is a supported, documented configuration, not a misconfiguration. Precondition (b)'s difficulty depends on how discoverable GitHub team IDs are (e.g., via public team pages, prior membership, or brute force of small sequential IDs) — this is the main source of uncertainty and is not verifiable purely from this codebase. Given those preconditions, attacker cost is a single signed HTTP POST with no other secrets required.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that the resolved `Team#organization` matches the organization that was authenticated by `WebhooksController#verify_signature` (e.g., pass the verified organization into the handler and raise/drop the event if `team.organization != verified_organization`) before calling `team.add_member`/`team.members.delete`. Additionally, consider scoping the `Team.find_or_create_by!` lookup by `[github_id, organization]` rather than `github_id` alone, and/or having `WebhooksController` reject `membership`/other events whose payload's `organization.login` doesn't match the same value used for `repository_owner`/signature verification for every downstream field the handler reads.

### Proof of Concept
minitest plan (ActionDispatch::IntegrationTest / ActionController::TestCase, extending the pattern already used in `test/controllers/webhooks_controller_test.rb`):
1. Seed a multi-org secrets config with two orgs, `o_attacker` (attacker-known `webhook_secret`) and `o_victim`.
2. Seed a `Team` fixture: `organization: 'o_victim'`, `github_id: 99`, and ensure this team's `id` is included in the stubbed `Shipit.github_teams` (stub `Shipit.oauth_teams`/`github_teams` to include this team's handle).
3. Build payload: `{ action: 'added', team: { id: 99, name: 'Victim Team', slug: 'victim-team', url: '...' }, organization: { login: 'o_attacker' }, member: { login: 'attacker_login' } }`.
4. Compute `X-Hub-Signature` using `o_attacker`'s configured `webhook_secret` (known to the attacker) over the raw JSON body.
5. `POST /webhooks` with header `X-Github-Event: membership` and the signature header; assert `response.status == 200`.
6. Assert `Membership.exists?(team: Team.find_by(github_id: 99), user: User.find_by(login: 'attacker_login'))` is `true` — the binding equality `(signing org == mutated team's org)` is false (`o_attacker != o_victim`) yet the write succeeded.
7. Assert `User.find_by(login: 'attacker_login').authorized?` is `true`, demonstrating escalation into `Shipit.github_teams` authorization for an org the attacker never belonged to.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end

          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
