### Title
Unbounded `denomination` field in indivisible-asset payments can exceed DB column range, causing an unhandled DB error that crashes the node - ([File: validation.js])

### Summary
`validatePayment()` in `validation.js` requires `payload.denomination` to be a positive integer for fixed-denomination assets, but unlike `amount`, `cap`, and other numeric payload fields, it never bounds the value against `constants.MAX_CAP` or any range compatible with the storage schema. A malicious unit author can set an arbitrarily large `denomination` (e.g. > 2^31-1), which passes validation and is subsequently written into database columns (`outputs.denomination`, `inputs.denomination`, `asset_denominations.denomination`) that are declared as 32-bit `INT` in the MySQL/RocksDB schema.

### Finding Description
In `validatePayment()`: [1](#0-0) 
the only check applied to `payload.denomination` is `isPositiveInteger(payload.denomination)`, defined as any finite integer greater than zero with no upper bound: [2](#0-1) 

By contrast, every other numeric quantity that ends up in the same tables (`amount`, `cap`, `oversize_fee`, `tps_fee`, etc.) is explicitly capped, e.g. output amounts: [3](#0-2) 
and asset caps: [4](#0-3) 

The `denomination` value that passes this loose check is later persisted into `outputs.denomination`, `inputs.denomination` and `asset_denominations.denomination`, which are declared as 32-bit `INT` columns in the schema: [5](#0-4) [6](#0-5) 

This mirrors the PocketMine-MP bug class: a value accepted by a loose/"positive-integer" style check (analogous to the wide-range `TAG_Int`) is written unchecked into a structure/column whose real, narrower range (32-bit `INT`) is only enforced later, at a different layer, where the resulting failure is not a clean validation error but an unhandled exception from the storage layer.

### Impact Explanation
If a value outside the 32-bit signed `INT` range reaches an `INSERT`/`UPDATE` on a MySQL-backed node (hubs typically run MySQL), the query fails with an out-of-range error. `db.query` callbacks throughout `writer.js`/`validation.js` generally assume success and do not wrap this class of error, so the failure surfaces as an uncaught exception. ocore installs a handler that deliberately re-throws and crashes the process on any uncaught exception: [7](#0-6) 
A single successfully-relayed unit from any unprivileged peer could therefore crash a hub/full node processing it — a remote, unauthenticated denial-of-service against unit-processing nodes, consistent with the CVSS profile of the reference advisory (network-reachable, no privileges, availability impact).

### Likelihood Explanation
The `denomination` field is fully attacker-controlled in any `payment` message referencing a fixed-denomination asset, and the only gate before it is written to the database is `isPositiveInteger`, which every large integer trivially satisfies. No further sanity check (against `MAX_CAP`, `constants.MAX_...`, or column width) exists anywhere else in `validatePayment`/`validatePaymentInputsAndOutputs`. The main uncertainty is storage-backend dependent: SQLite (dynamic typing) would likely just store the oversized value without erroring, so the crash is specifically reachable on MySQL-backed installations (typically hubs), which is where the impact from a network-reachable DoS matters most.

### Recommendation
Add an explicit upper bound to the `denomination` check in `validatePayment` (and in `aa_validation.js`'s asset-denomination validation), e.g. requiring `payload.denomination <= constants.MAX_CAP` (or a dedicated `MAX_DENOMINATION` constant sized to fit the 32-bit `INT` columns), mirroring the bound already applied to `amount` and `cap`.

### Proof of Concept
1. Attacker composes and broadcasts a unit containing a `payment` message referencing a fixed-denomination asset, with `payload.denomination = 99999999999` (exceeds 2^31-1).
2. `validatePayment` accepts it because `isPositiveInteger(99999999999)` is `true`.
3. Once accepted, `writer.js` inserts the output/input rows containing this denomination into `outputs`/`inputs`/`asset_denominations`, which are declared `INT` in the MySQL schema.
4. On a MySQL-backed node, the `INSERT` fails with an out-of-range error; because this is not specially handled, it surfaces as an uncaught exception, triggering `process.on('uncaughtException')` and crashing the node process.
