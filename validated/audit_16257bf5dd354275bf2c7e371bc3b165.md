Confirmed: `Shipit::Api::StacksController#stack` correctly scopes via `stacks.from_param!` [1](#0-0)  (where `stacks` is restricted to `current_api_client.stack_id` when set) [2](#0-1) , but `Shipit::Api::CCMenuController#stack` bypasses this scoping entirely by calling `Stack.from_param!(params[:stack_id])` directly [3](#0-2) , while permission is checked only via `ApiClient#check_permissions!`, which validates the `read:stack`/`write:stack` string permission but never checks `stack_id` [4](#0-3) .

### Title
Stack-scoped ApiClient token can read any stack's build status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` created with a `stack_id` (a token deliberately scoped to a single stack, e.g. via the CCMenu "fetch URL" flow) can be used to read the CI/build status of **any** stack in the Shipit instance, not just the one it was scoped to, because `Api::CCMenuController#stack` does not apply the `stacks` scoping used everywhere else in the API.

### Finding Description
Shipit's API authorization model binds an `ApiClient` to two independent things: a list of string `permissions` (e.g. `read:stack`) and, optionally, a single `stack_id` that scopes the client to one stack [5](#0-4) . The intended binding is enforced in `Api::BaseController#stacks`, which restricts the visible stack collection to `Stack.where(id: current_api_client.stack_id)` when a `stack_id` is set [2](#0-1) , and controllers such as `Api::StacksController` correctly resolve the requested stack through this scoped collection: `stacks.from_param!(params[:id])` [1](#0-0) .

`Api::CCMenuController`, however, overrides `#stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The only authorization check performed before this is `require_permission :read, :stack` [6](#0-5) , which calls `ApiClient#check_permissions!(:read, :stack)`. That method only checks whether the string `"read:stack"` is present in the `permissions` array — it never inspects `stack_id` [4](#0-3) .

This breaks the binding: **the stack a token authorizes ≠ the stack it touches**. Any `ApiClient` token with `read:stack` permission — including one deliberately scoped to a single, low-sensitivity stack (this is exactly the pattern used by `CCMenuUrlController`, which auto-creates a `read:stack`-only client scoped to one stack for embedding in CI dashboard tools: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` [7](#0-6) ) — can be replayed against `/api/stacks/:stack_id/ccmenu.xml` with a *different* `stack_id` path segment and will successfully render that other stack's status.

### Impact Explanation
This is a read-only disclosure of stack build/deploy status (name, `lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) for stacks the token was never authorized to see, via `Api::CCMenuController#show` [8](#0-7) . This matches the "High - unauthenticated/unauthorized read of stack state" impact category, since it is a cross-stack read enabled purely by a scoping bypass rather than the credential's granted authorization.

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-only `ApiClient` token (the exact kind of low-privilege token the product intentionally hands out via the CCMenu "fetch URL" feature for embedding in third-party CI dashboard tools) can trivially trigger this by changing the `stack_id` segment of the request URL. No additional privilege or secret is required beyond possessing that one token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (as `Api::StacksController` does), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot address stacks outside its `stack_id`.

### Proof of Concept
1. Create (or have Shipit auto-create via `CCMenuUrlController#fetch`) an `ApiClient` scoped to stack A with permissions `["read:stack"]` and note its `authentication_token`.
2. As an attacker holding only that token, issue: `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu.xml?token=<token>` for stack B, a completely unrelated stack.
3. Observe HTTP 200 with stack B's CCTray XML (`lastBuildStatus`, `activity`, etc.), even though the token's `stack_id` only authorizes stack A — confirming the bypass of `Api::BaseController#stacks` scoping in `Api::CCMenuController#stack`.
