### Title
Stack-scoped API token authorization bypass in `Api::CCMenuController` — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` implements the security boundary that binds an `ApiClient` token to the stack(s) it was authorized for: `stacks` filters by `current_api_client.stack_id` when the token is stack-scoped, and `stack` resolves the requested `params[:stack_id]` only from that scoped relation. [1](#0-0) 

`Api::CCMenuController` overrides `stack` to bypass this scoping entirely, resolving the stack directly from the global `Stack` relation regardless of the authenticated token's `stack_id`: [2](#0-1) 

Stack-scoped tokens are a normal, unprivileged product feature: `CCMenuUrlController` mints one for the current user, scoped to a single stack, with `read:stack` permission, specifically so it can be embedded/shared for CI-status polling of that one stack: [3](#0-2) 

Because `CCMenuController#stack` ignores `current_api_client.stack_id` and directly calls `Stack.from_param!(params[:stack_id])`, an attacker who legitimately obtains (or is given) a CCMenu token scoped to stack A can supply any other `stack_id` in the URL and read deploy/rollback state for stack B — a stack the token was never authorized to touch. This breaks the binding: `stack the token authorizes` (A) ≠ `stack the token touches` (B, or any stack in the deployment).

The `require_permission :read, :stack` declaration on the controller only checks that the *permission string* `read:stack` is present on the token — it never checks *which* stack the permission applies to; that check is delegated entirely to the `stack` method, which this controller has broken. [4](#0-3) [5](#0-4) 

### Impact Explanation
This matches the "High" category: unauthenticated/unauthorized read of stack state and deploy output. A holder of any single stack-scoped `read:stack` token (e.g., one legitimately generated for a low-sensitivity stack via the CCMenu embed feature, or one leaked from a status badge/URL) can enumerate and read the latest deploy/rollback status (`stack.deploys_and_rollbacks.last`) of every other stack in the Shipit instance, including stacks they have no authorization for. This is a genuine authorization-scope escape rather than a design choice, since every sibling controller (`Api::StacksController`, `Api::TasksController`, `Api::DeploysController`, etc.) correctly uses the scoped `stack` method from `BaseController`.

### Likelihood Explanation
Likelihood is significant: CCMenu tokens are explicitly designed to be shared/embedded (CI status widgets), so they are more likely to leak than general API credentials, and exploitation requires only changing a URL parameter — no privilege escalation, cryptographic attack, or additional secrets are needed.

### Recommendation
Remove the custom `stack` override in `Api::CCMenuController` (and the equivalent one in `CCMenuUrlController` if a token is ever checked there) so it inherits `BaseController#stack`, which resolves the stack via the `stacks` method honoring `current_api_client.stack_id`. If `CCMenuController` needs `Stack.from_param!` semantics for unscoped/unlimited clients, it should still filter through `stacks` (i.e., `stacks.from_param!(params[:stack_id])`) rather than the raw `Stack` relation.

### Proof of Concept
1. A user requests a CCMenu URL for `stack_a` via `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` scoped to `stack_a` with `permissions: ['read:stack']` and returns a token embedded in a URL such as:
   `GET /api/stack_a/ccmenu.xml?token=<token-scoped-to-stack_a>`
2. An attacker who obtains this token (e.g., from a shared CI dashboard, GitHub README badge, or leaked link) sends:
   `GET /api/stack_b/ccmenu.xml?token=<token-scoped-to-stack_a>`
3. `authenticate_api_client` successfully authenticates the token (`ApiClient.authenticate` only validates the signed client id, not the requested stack).
4. `require_permission :read, :stack` passes because the token does have `read:stack` in its permission list.
5. `stack` calls `Stack.from_param!(params[:stack_id])` directly — ignoring `current_api_client.stack_id` — and loads `stack_b`.
6. The response renders `stack_b`'s latest deploy/rollback status, which the token was never authorized to access.
