### Title
Webhook signature is verified against the organization named in the untrusted payload, but handlers act on an independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` based on `repository_owner`, a value read straight out of the unauthenticated JSON body. The actual event handlers (`PushHandler`, `StatusHandler`, `Handler#stacks`, `PullRequest::*Handler`) instead key off a *different* field of the same untrusted body — `repository.full_name` — to decide which `Stack`/`Repository` is mutated. Nothing in the code enforces that these two attacker-supplied fields describe the same repository/organization, so the "organization that authenticated" and "the repository that is written" are not the same equality the code implicitly assumes.

### Finding Description
`verify_signature` computes the authenticating organization purely from payload content: [1](#0-0) [2](#0-1) 

It then fetches the `GitHubApp` for that organization and verifies the signature using that organization's `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever the resolved organization's `webhook_secret` is blank — a state the setup docs and example config explicitly treat as valid/optional (`webhook_secret: null`): [4](#0-3) 

Meanwhile, every downstream handler resolves the target `Stack`/`Repository` using `repository.full_name`, a completely independent field of the same JSON body: [5](#0-4) [6](#0-5) 

Because `repository_owner` (used to select the *authenticating* app/org) and `repository.full_name` (used to select the *acted-upon* repository) are two independently attacker-writable JSON fields, an attacker who knows any organization configured in Shipit with no `webhook_secret` (a documented/supported configuration for multi-org installs) can craft a payload where `repository.owner.login`/`organization.login` names that unsecured org — causing `verify_signature` to pass with **no signature at all** — while `repository.full_name` names a `Stack` belonging to an entirely different, secured organization. The handler then processes the event as if it were a legitimate, signed webhook for that other organization's repository.

This breaks the equality the endpoint is meant to enforce: `organization that authenticated == organization owning the repository being written`.

### Impact Explanation
Once this equality is broken, an unauthenticated remote attacker can inject fully-controlled webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`) against stacks belonging to organizations they have no relationship with:
- `PushHandler` triggers `GithubSyncJob` for the targeted stack, which fetches commits via the *stack's own* legitimate GitHub API credentials and can be used to force spurious/forged sync activity.
- `StatusHandler` creates a `CommitStatus` on an existing commit of the targeted stack from forged `state`/`context`/`description` data, which can influence CI-gated deploy decisions (`ci.require`) and downstream continuous-deployment automation.
- `MembershipHandler` creates arbitrary `Team`/`User` records tied to `organization.login`, independent of `repository.full_name`, since it uses a still different unauthenticated field.

This is a cross-repository/cross-organization write achieved without possessing any of the excluded credentials (no `webhook_secret`, no `ApiClient` token, no repository write access needed) — it only requires knowledge that some organization in a multi-org Shipit deployment has `webhook_secret: nil`, which the maintainers' own example config demonstrates is a supported state.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`config/secrets.yml` keyed by org, documented feature), and (2) at least one configured organization without a `webhook_secret` — an explicitly supported/no-op configuration per `docs/setup.md` ("Webhook secret (optional)") and `secrets.development.example.yml`. Given that condition, exploitation is trivial: a single unauthenticated POST to `/webhooks` with a crafted JSON body and no `X-Hub-Signature` header (or an ignored one). No GitHub credentials, sessions, or tokens are required.

### Recommendation
Do not use payload-controlled fields to select the verification key. Instead:
1. Resolve `repository.full_name` first, look up the owning `Repository`/organization from Shipit's own trusted configuration/DB, and use *that* organization to select the `GitHubApp` used for signature verification — never trust `repository.owner.login`/`organization.login` for this purpose.
2. After signature verification, re-derive the acted-upon repository from the same trusted mapping (not from `repository.full_name` alone) and reject the event if the signing organization does not own that repository.
3. Treat organizations configured with a blank `webhook_secret` as unverifiable and refuse to process events that could affect other organizations' stacks, or require a `webhook_secret` for any multi-org configuration.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (`webhook_secret: null`) and `org-b` (`webhook_secret: "s3cr3t"`), each installed on real GitHub orgs, with `org-b/target-repo` mapped to an existing `Stack` in Shipit.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
No `X-Hub-Signature` header is required to be valid, since `repository_owner` resolves to `org-a`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('org-b/target-repo')` — a repository belonging to the *secured* `org-b` — and enqueues `GithubSyncJob`/processes the forged event against `org-b`'s stack, despite the request never being signed by `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
