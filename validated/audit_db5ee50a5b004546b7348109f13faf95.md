### Title
Cross-organization webhook forgery via mismatched signature-verification identity and payload-derived repository identity - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub organization's `webhook_secret` to verify an inbound webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the same untrusted JSON body it is trying to authenticate. Downstream webhook handlers (`Push`, `Status`, `CheckSuite`, `PullRequest`, etc.) separately resolve the target `Repository`/`Stack` from `repository.full_name` in that same body. These two lookups are never cross-checked against each other.

### Finding Description
`verify_signature` computes the verifying `github_app` from `repository_owner`, which is extracted straight from the attacker-controlled raw POST body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization config (each org can have its own `webhook_secret`, as shown in the multi-org example config), so `HMAC(webhook_secret_of_org_X, raw_body)` is checked using whatever `org_X` value the payload itself claims: [3](#0-2) 

Once the signature check passes, `Shipit::Webhooks.for_event(event)` handlers process the *same* raw payload and independently resolve the actual repository/stack to act on via `repository.full_name` (confirmed by the push handler test asserting `GithubSyncJob` is enqueued for the stack matching the payload's `repository.full_name`): [4](#0-3) 

Because the attacker fully controls the raw JSON body (this is a synthetic HTTP request, not a GitHub-relayed one), nothing prevents `repository.owner.login` (used to pick the verification secret) from being a different organization than the one implied by `repository.full_name` (used to pick the mutated repository/stack). The equality the code implicitly — and wrongly — assumes is:
`organization authenticated by verify_signature == organization owning the repository the handler writes to`

This binding is never enforced. An operator/attacker who legitimately administers their own GitHub App/org configured in Shipit (and therefore knows their own org's `webhook_secret`) can sign a forged payload with their own secret while setting `repository.full_name` to `"victim-org/victim-repo"`. The signature check succeeds (it's checking data signed with the attacker's own known secret against the attacker's own claimed `repository_owner`), and the handler then processes push/status/check_suite/pull_request/membership events against the victim organization's stack — creating commits, changing commit statuses (`deployable?`), or fabricating `check_suite`/`pull_request` events that influence deploy eligibility and merge queue behavior for a repository the attacker was never authenticated for.

### Impact Explanation
This crosses the "Critical" bar: **cross-repository writes**. An attacker with only their own (unprivileged, self-controlled) org webhook credentials can inject fabricated GitHub events (commits, CI statuses, check-suite results, pull-request state changes) into another organization's Shipit-tracked repository/stack, without holding a Shipit session, ApiClient token, or the victim org's `webhook_secret`. Because `Commit#deployable?` and merge-queue logic are driven by statuses/check-suites recorded from webhooks, this can be leveraged to mark otherwise-undeployable commits as CI-green or to manipulate merge-queue state for a repository outside the attacker's control, ultimately affecting which commits are eligible for deploy.

### Likelihood Explanation
Requires a Shipit deployment configured with multiple GitHub organizations/apps (a documented, supported configuration per `config/secrets.development.example.yml`), and requires the attacker to control (or have configured) at least one such organization's GitHub App/webhook secret — which is a normal, unprivileged capability relative to the victim organization (they are not required to have any access to the victim org, Shipit account, or Shipit-issued token). This is a config-dependent but realistic multi-tenant scenario.

### Recommendation
Do not let the payload determine which secret verifies itself. Bind the webhook endpoint to a specific organization out-of-band (e.g., `/webhooks/:organization` route segment, or per-installation webhook secret tied to `X-GitHub-Hook-Installation-Target-ID`/`installation.id` header data validated against the configured installation), and after signature verification, assert that the repository/organization the handler is about to mutate (`repository.full_name`'s owner) matches the exact organization whose secret validated the request. Reject the webhook if these do not match.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret` (per the documented multi-org config format).
2. Attacker (who administers `org-attacker`'s GitHub App and thus knows its `webhook_secret`) crafts a `push` webhook JSON body where `repository.owner.login = "org-attacker"` but `repository.full_name = "org-victim/some-repo"`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-attacker_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` and successfully verifies the signature against the attacker's own known secret.
5. `Shipit::Webhooks.for_event('push')` handlers process the payload using `repository.full_name = "org-victim/some-repo"`, causing `GithubSyncJob`/commit creation to run against `org-victim`'s stack — a write the attacker was never authorized to make.
