### Title
Unsanitized pull request label names injected as environment variables reach `Command#start` via `ReviewStack#env` → `TaskCommands#env` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash returned to callers, with no key allowlist or denylist. Because `TaskCommands#env` merges `@stack.env` into the environment passed to `Command.new`, and `Command#unbundled_env` merges that hash on top of the process's base environment before `PTY.spawn`, an attacker who can set a label named `pythonpath` on their own fork PR can inject a `PYTHONPATH=true` (or any other similarly-named) environment variable into every `tasks.<name>.steps` command run for that review stack.

### Finding Description
The broken binding: the environment reaching `PTY.spawn` for a `tasks.<name>.steps` command should equal `BASE_ENV` merged only with values whose *keys* originate from trusted, allowlisted sources (task definition variables, stack config, deploy metadata) — not arbitrary attacker-chosen strings. That invariant is violated.

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
super.merge(
  pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
)
```
There is no filtering of `label_name` before it becomes a hash **key**. Any label the PR author applies (labels on a PR from their own fork can be created via arbitrary label names if the repo/label doesn't already exist, or via existing repo labels — for GitHub, adding a *new* label to a repository normally requires write access, but an attacker who owns the fork repository, or who names an *existing* label matching a target variable such as `pythonpath`, can achieve this; regardless, the code path performing no key sanitation is the root defect independent of how the label gets created).
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `@stack.env` (i.e., the `ReviewStack#env` result, including the label-derived keys) into the hash used for every command, including `tasks.<name>.steps` invoked from `perform`.
- `Command#initialize`/`#unbundled_env` (`lib/shipit/command.rb:31-34`, `103-105`) does `@env = env.transform_values { |v| v&.to_s }` and then `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, with no key allowlist — any key present in `@env`, including `PYTHONPATH`, is passed straight into `PTY.spawn` at `command.rb:92`.

Existing guards do not stop this: `verify_signature`/webhook signature checks validate that the payload legitimately originates from GitHub for the given repo, but they do not restrict the *content* of label names; `EnvironmentVariables#permit` and `filter_task_envs`/`filter_deploy_envs`/`Definition#filter_envs` are applied only to explicitly user-supplied task-trigger `env` params (`Stack#trigger_task`, `Stack#build_deploy`), not to `@stack.env`, which is unconditionally merged in `TaskCommands#env`. There is no allowlist anywhere on the label-derived keys.

### Impact Explanation
If a `tasks.<name>.steps` command in the repo's `shipit.yml` invokes a Python interpreter or a Python-based tool, an attacker-controlled `PYTHONPATH` (or `LD_PRELOAD`-style variables for other keys, depending on the target step's interpreter) prepended into the process environment can cause arbitrary attacker-supplied Python modules to be imported and executed on the Shipit deploy host — Remote Code Execution on the deploy host, matching the Critical impact class (RCE via `Command`/`PTY.spawn`). The blast radius is scoped to the specific review stack/repository whose `shipit.yml` and task steps use Python (or another env-var-hijackable interpreter), but any repository configured with `provisioning_behavior: allow_all` and a Python-based `tasks.<name>.steps` entry is exploitable by any contributor who can open a PR against it and label it.

### Likelihood Explanation
Preconditions: the target repository must run in review-stack mode with `provisioning_behavior: allow_all` (per the question's framing) and must define a `tasks.<name>.steps` task that shells out to an interpreter sensitive to the injected variable name (e.g., `python`). The attacker needs only the ability to open a pull request and apply/create a label on it — a low-cost, fully self-service action for anyone who can fork and PR, or trivially satisfied on repositories that already allow external labelling. No Shipit credentials, session, or API token are required. This is repeatable on every push/label event for the life of the PR.

### Recommendation
In `app/models/shipit/review_stack.rb`, do not merge raw uppercased label names as environment variable keys. At minimum:
- Apply an explicit allowlist/prefix convention for label-derived env vars (e.g., only `LABEL_<safe-token>` keys, or filter through `EnvironmentVariables#permit` with a fixed allowlist of accepted variable names).
- Reject/skip label names that collide with security-sensitive environment variable names (`PYTHONPATH`, `LD_PRELOAD`, `PATH`, `RUBYOPT`, `GEM_PATH`, `NODE_OPTIONS`, etc.), or better, hard-fail if a label name is not a valid identifier under a strict allowlist regex.
- Ensure `TaskCommands#env`/`Command#unbundled_env` cannot be overridden by keys not explicitly sanctioned by the deploy spec/task definition, independent of the source of `@stack.env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or lib/shipit/task_commands_test.rb)
test "PYTHONPATH label injects into tasks.<name>.steps command env reaching Command#start" do
  stack = shipit_stacks(:shipit) # a ReviewStack fixture with provisioning_behavior allow_all
  pull_request = stack.pull_request
  pull_request.update!(labels: ["pythonpath"]) # attacker-controlled label on their own fork PR

  # Binding under test, stated explicitly before tracing:
  # expected: stack.env.key?("PYTHONPATH") == false
  # actual:
  assert_equal "true", stack.env["PYTHONPATH"]

  task = shipit_tasks(:task_with_python_step) # references a tasks.<name>.steps definition
  task_commands = Shipit::TaskCommands.new(task)

  command = task_commands.perform.first
  # assert the tainted key reaches Command#unbundled_env / PTY.spawn input
  assert_equal "true", command.unbundled_env["PYTHONPATH"]
end
```
This demonstrates the equality `stack.env["PYTHONPATH"] == "true"` (attacker-controlled) propagating unchanged into `Command#unbundled_env`, which is exactly the hash passed to `PTY.spawn` in `Command#start` (`lib/shipit/command.rb:92`).
