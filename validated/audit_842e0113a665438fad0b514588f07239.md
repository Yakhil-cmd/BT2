## Analysis

**Analog identified: `validatePaymentInputsAndOutputs` in `validation.js` — mixing an `issue` input with `transfer` inputs in one payment message causes `transfer_condition` to be silently skipped.**

CVE-2023-39418 is a bug-class where a single combined command (`MERGE`, which behaves like `INSERT` + `UPDATE`) only enforces the policy meant for one of its sub-operations (`INSERT`) and fails to enforce the policy meant for the other (`UPDATE`/`SELECT`) on rows affected by that sub-operation. The ocore payment-validation code has the same shape of bug for asset spending conditions.

### Root cause

A single `payment` message for a non-base asset can legally contain **one `issue` input followed by `transfer` inputs** in the same message: the code only requires that "issue must come first" and that transfers precede headers-commission/witnessing inputs, it never forbids mixing issue and transfer input types in the same payload. [1](#0-0) [2](#0-1) [3](#0-2) 

After processing all inputs, the code decides which asset-level spending condition to enforce using a single boolean `bIssue` that is set to `true` if *any* input in the message is an `issue`: [4](#0-3) 

```js
var arrCondition = bIssue ? objAsset.issue_condition : objAsset.transfer_condition;
if (!arrCondition)
    return cb();
Definition.evaluateAssetCondition(...)
```

This is exactly the MERGE flaw pattern: when the payload contains **both** an issue (insert-like) and transfers of pre-existing outputs (update-like), only `issue_condition` is evaluated and `transfer_condition` is never checked at all for the transfer inputs present in the same message, even though those transfers are real spends of existing, possibly restricted, asset outputs.

### Why this matters

Asset issuers can define `transfer_condition` to restrict who may receive/transfer the asset (whitelists, attestation requirements, freeze logic, cosigning, etc.), while leaving `issue_condition` empty or permissive (very common — most assets are `issued_by_definer_only:false` or have a trivial issue condition). Because the ownership check (`output owner is not among authors`) only ensures the sender owns the coins, not that the recipient/transfer satisfies `transfer_condition`, an asset holder can attach a self-issuance of the same asset (even a tiny amount, if `issued_by_definer_only` is false and the asset is uncapped) to a payment message that also transfers their existing restricted-asset outputs. Because `bIssue` becomes `true`, `transfer_condition` is skipped entirely, letting the transfer of the pre-existing outputs bypass the issuer's transfer restrictions (e.g., send restricted/whitelisted tokens to an unattested/unauthorized address).

## Title
Mixed issue+transfer payment messages bypass `transfer_condition` enforcement - (File: validation.js)

## Summary
In `validatePaymentInputsAndOutputs`, the asset spending condition to enforce is chosen with a single `bIssue` flag that is `true` whenever the message contains any issue input, causing `transfer_condition` to be completely skipped for any transfer inputs bundled in the same payment message.

## Finding Description
`ocore` allows a single `payment` message to combine one `issue` input (of the asset) with `transfer` inputs spending the sender's pre-existing outputs of that same asset, as no code path forbids this combination. [2](#0-1) [3](#0-2) 

At the end of validation, the code determines which condition governs the whole message using `var arrCondition = bIssue ? objAsset.issue_condition : objAsset.transfer_condition;` [4](#0-3) . Because `bIssue` is a message-wide boolean set as soon as any issue input is seen (`bIssue = true;` at [5](#0-4) ), the presence of one issue input suppresses the enforcement of `transfer_condition` for all other, unrelated transfer inputs in the same message. This mirrors CVE-2023-39418: a combined operation checks the policy for one constituent action (issue/INSERT) but never checks the policy that should also apply to the other constituent action (transfer/UPDATE) present in the same operation.

## Impact Explanation
Asset definers rely on `transfer_condition` (validated the same way as `issue_condition` via `Definition.evaluateAssetCondition`, see `validateAssetDefinition` at [4](#0-3) ) to restrict transferability of an asset (e.g., recipient whitelists, attestation gates, cosigning requirements). Since the check only inspects ownership of the spent outputs (`output owner is not among authors`, [6](#0-5) ) and never revalidates `transfer_condition` when an issue input is also present, any holder of the restricted asset can smuggle their transfer past the issuer's transfer policy by piggybacking a trivial self-issue input in the same message (feasible whenever the asset is not `issued_by_definer_only` and uncapped, a common configuration). This is a concrete bypass of asset issuance/transfer conditions — unauthorized transfer of a restricted asset outside its intended access-control policy.

## Likelihood Explanation
Any address holding units of an affected asset can trigger this by constructing an ordinary unit with a `payment` message containing an `issue` input at index 0 followed by `transfer` inputs, requiring no privileged access, no AA, and no cooperation from other parties — reachable directly from a single posted unit.

## Recommendation
Evaluate both `issue_condition` and `transfer_condition` independently per input type present in the message (i.e., check `issue_condition` if `bIssue` is true AND check `transfer_condition` if there is at least one non-issue, asset-spending input), rather than selecting exactly one condition to evaluate for the whole message based on the single `bIssue` flag.

## Proof of Concept
1. Definer publishes an asset with `issued_by_definer_only:false`, no `cap`, permissive/absent `issue_condition`, and a restrictive `transfer_condition` (e.g., requiring the recipient to be attested).
2. Attacker (who legitimately holds units of this asset from a prior transfer) constructs a single unit with one `payment` message for this asset containing:
   - input 0: `type:"issue"`, a small `amount`, `serial_number` per rules.
   - input 1..n: `type:"transfer"` inputs spending the attacker's existing outputs of the asset.
   - outputs sending the transferred amount to an address that does **not** satisfy `transfer_condition` (e.g., unattested).
3. In `validatePaymentInputsAndOutputs`, `bIssue` becomes `true` because of input 0, so `arrCondition = objAsset.issue_condition` is evaluated instead of `objAsset.transfer_condition`; since `issue_condition` is permissive/absent, validation passes and the transfer to the disallowed address is accepted, bypassing the issuer's transfer restriction.
