### Title
Caller-supplied swap route lets a malicious pool contract join the caller's authorization tree and drain wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Analog of CVE-2023-0648 (dst-admin masterConsole command injection): attacker-controlled input reaches an arbitrary external invocation sink. Here the "command" is the `swap`/`route` bytes argument that `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `multiply` accept from any caller. `swap_tokens` forwards those bytes verbatim to the configured router after authorizing exactly one input transfer, and the router dispatches hops to whatever pool addresses the payload names — it keeps no venue/pool allowlist. A route naming an attacker-deployed "pool" causes arbitrary third-party code to run inside the victim's authorized call tree, and a token `transfer` that code issues from the caller is recorded as a child of the caller's own `require_auth` entry, so signing the simulated tree authorizes a wallet drain unrelated to the swap.

### Finding Description
`process_swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` all funnel into `swap_tokens` (`contracts/controller/src/strategies/swap.rs:13-55`). The only controller-side mitigations are: `authorize_transfer_as_current(token_in, controller, router, amount_in)` covering the controller's own input (line 34), measured input/output deltas (`RouterOverspend`, `NoSwapOutput`), and a positive-output check. None of these inspect or constrain the route contents — the payload's pool/token addresses are fully caller-supplied. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` pins the exploit: `UnlistedPoolRouter::execute_strategy` invokes `route.hop_pool.swap` (lines 39-47), a `RogueHopPool` whose `swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` (lines 62-71), and simulation records that stolen transfer as a child invocation under Alice's `swap_collateral` auth entry (lines 195-227). Because `sender.require_auth()` at the controller root produces an auth tree that honest simulation populates with every nested authorization the route triggers, a victim who signs the simulated tree authorizes the theft. The threat model (`docs/explanation/threat-model.md:154-165`) confirms the router "keeps no allowlist" of pool/token addresses and that neither the payload min-out nor the final risk gate bounds the loss — the loss is the caller's wallet, not the routed amount.

### Impact Explanation
Theft of user funds: any token balance in the victim's wallet (or any allowance/auth the rogue pool can provoke, e.g. NFT transfers, other contracts' auth-gated functions) can be moved to the attacker, entirely outside the swapped amount and the position's risk checks. Every unprivileged strategy entrypoint that takes route bytes is a carrier.

### Likelihood Explanation
Exploitation requires the victim to execute a strategy with attacker-crafted route bytes (e.g. a malicious/compromised quote server or a phishing route) and sign the resulting authorization tree. Wallets that surface nested auth children poorly, or users who sign without decoding, make this practical; the attack needs no privileged role and the on-chain code places no obstacle to it.

### Recommendation
Enforce a venue/pool allowlist or restrict route pool addresses to governance-registered venues before dispatch (in the router), and/or have the controller reject routes whose execution would create authorization children beyond the single expected input transfer — e.g. by exposing a simulatable dry-run or requiring the router to self-authorize all venue pulls via invoker-contract auth so a pool-initiated `transfer` from the caller cannot attach to the caller's tree. Clients must also decode and verify the signed auth tree.

### Proof of Concept
Pinned by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: Alice (debt-free, 10,000 USDC supplied, plus an unrelated `WALLET_BALANCE` of another token) calls `swap_collateral(account_id, USDC, SWAP_IN_USDC, ETH, route)` where `route` names `RogueHopPool`. The rogue pool's `swap` executes `wallet_token.transfer(alice → attacker, WALLET_BALANCE)`; the recording-mode test asserts the stolen transfer is recorded as a child of Alice's `swap_collateral` `AuthorizedInvocation`, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and Alice still receives the fair `FAIR_OUT_ETH` swap output — all risk gates pass while the wallet is drained.
