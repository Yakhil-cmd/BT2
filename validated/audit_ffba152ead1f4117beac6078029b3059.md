### Title
Unallowlisted swap venues can inject arbitrary token transfers into the sender's authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
High. A malicious route can name an attacker-controlled contract as a swap pool. During `execute_strategy`, the router calls that contract under the sender's authorization context, allowing it to request unrelated `token.transfer(sender, attacker, amount)` authorizations. If the victim signs the simulated authorization tree without detecting the extra child invocation, the malicious venue can drain wallet tokens unrelated to the swap.

### Finding Description
`execute_strategy` authenticates `sender`, decodes attacker-supplied `swap_xdr`, and executes each packed swap instruction. [1](#0-0) 

For a swap operation, the pool, input token, and output token are all loaded from the caller-controlled `assets` registry without checking the pool against an allowlist. [2](#0-1) 

The Aquarius adapter then calls the route-selected `pool` address through `get_tokens` and `swap`; the pool address is not restricted to a deployed Aquarius contract. [3](#0-2) 

Consequently, an attacker can encode an Aquarius hop whose `pool` is a malicious contract that returns crafted token metadata, pulls the router-authorized input, pays a conforming output to satisfy measured-output checks, and additionally invokes `token.transfer(victim, attacker, amount)` for any token the victim holds. Soroban simulation records that token transfer as a child of the sender's authorization, and it executes when the victim signs the poisoned tree. [4](#0-3) 

The same authorization shape exists when the malicious route is supplied through controller strategies such as `swap_collateral`, because the controller forwards the route bytes to the configured router. [5](#0-4) 

### Impact Explanation
The attacker can steal arbitrary token balances from the victim's wallet, including assets unrelated to the lending position or route input. The measured input/output checks protect only the routed amount and do not bound additional token transfers signed as children of the victim's authorization tree. [6](#0-5) 

The repository's own authorization test demonstrates that a rogue hop can transfer the victim's entire unrelated wallet balance to an attacker when the poisoned authorization tree is signed. [7](#0-6) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious pool contract and distribute a crafted `swap_xdr` payload through a malicious quote, UI, message, or phishing flow. The opaque route bytes and generated authorization tree make the extra token transfer easy to miss during signing, especially when wallets or clients do not prominently decode every nested invocation.

The attack requires the victim to submit and sign the poisoned route. It does not require privileged roles, leaked keys, a compromised router, or control of the victim's lending account.

### Recommendation
Do not allow route payloads to choose arbitrary venue contract addresses. Maintain an on-chain or governance-controlled registry of legitimate pool contracts for each venue, or constrain venue calls to pools whose identity was verified when the route was constructed by a trusted component.

At a minimum, reject route-selected pool addresses that are not known-valid deployments for the selected venue and display all simulated authorization children before signing. Clients should refuse any tree containing token transfers other than the expected route input pull.

### Proof of Concept
1. The attacker deploys a malicious contract exposing Aquarius-compatible `get_tokens` and `swap` methods.
2. The attacker creates a `StrategyPayload` for `execute_strategy(sender = victim, total_in = X, swap_xdr = malicious_route)` where the `assets` registry includes the malicious contract as the hop pool.
3. The malicious contract returns `[token_in, token_out]` from `get_tokens`, pulls the router's authorized `token_in`, returns enough `token_out` to satisfy `min_out`, and invokes `token::transfer(victim, attacker, victim_balance)` for another token held by the victim.
4. Simulation records the additional transfer beneath the victim's authorization entry.
5. The victim signs the presented authorization tree.
6. The swap settles normally, while the unrelated wallet token is transferred to the attacker.
