### Title
Unbounded decompression of OCI referrer layer enables memory-exhaustion (decompression bomb) during `gh attestation verify --bundle-from-oci` - ([File: pkg/cmd/attestation/artifact/oci/client.go])

### Summary
`LiveClient.GetAttestations` fetches attestation bundle layers from an OCI referrers manifest and reads the fully decompressed layer into memory with `io.ReadAll(layer0)` with no size limit before handing the bytes to `bundle.UnmarshalJSON`. Any attacker who can publish OCI referrers for a public image (which is unauthenticated by design) can supply a small compressed layer that decompresses to a very large buffer, causing unbounded memory allocation on the victim's machine when they run `gh attestation verify --bundle-from-oci`.

### Finding Description
In `pkg/cmd/attestation/artifact/oci/client.go`, `GetAttestations` iterates referrer manifests whose `ArtifactType` matches `application/vnd.dev.sigstore.bundle`: [1](#0-0) 
For each matching referrer, it opens the first layer with `layers[0].Uncompressed()` (which transparently gunzips the layer) and reads it fully into memory with no cap: [2](#0-1) 
There is no `io.LimitReader`, content-length pre-check, or maximum-size enforcement anywhere in this path, and a repo-wide search found no size-limiting pattern (`LimitReader`/`MaxBytesReader`) used for OCI artifact/bundle fetching. Because OCI referrers/artifacts for a public image can be published by any unprivileged party controlling that image/repository (e.g., pushing referrer manifests via the registry API using their own credentials, which is a normal, unprivileged registry operation, not requiring victim's or admin's rights), an attacker fully controls the compressed layer content and size ratio. A crafted gzip layer (e.g., few KB compressed) can decompress to gigabytes, and `io.ReadAll` will keep growing an in-memory buffer until it's fully read or the process is killed/OOMs, before ever reaching `bundle.UnmarshalJSON`.

### Impact Explanation
This is a memory-exhaustion / denial-of-service vector on the victim's local machine when running `gh attestation verify --bundle-from-oci` against an attacker-controlled or attacker-published referrer artifact. It matches the "Denial of service" impact class for a CLI tool: uncontrolled resource consumption crashes or hangs the invoking process. It does not by itself grant code execution or credential exfiltration; the enlarged-buffer-reaches-parser concern is speculative without a demonstrated parser bug in `sigstore-go`'s `bundle.UnmarshalJSON`, so the concrete, provable impact is scoped to memory/resource exhaustion.

### Likelihood Explanation
Feasible and repeatable: publishing an OCI referrer with a decompression-bomb layer requires only push access to some registry, and the victim triggers the fetch simply by running `gh attestation verify --bundle-from-oci` pointed at that image reference, which is an intentional, first-class supported gh feature (`pkg/cmd/attestation/verify/options.go`, `verify.go`). No special privileges, MITM, or leaked tokens are needed — the attacker just needs to publish a referrer artifact type by attester `application/vnd.dev.sigstore.bundle` for the digest the victim verifies.

### Recommendation
Wrap the uncompressed layer reader with a bounded reader (e.g., `io.LimitReader(layer0, maxBundleSize+1)`) and reject/error if the read reaches the limit, before calling `bundle.UnmarshalJSON`. Also consider checking the declared/compressed layer size against a sane bundle-size ceiling (sigstore bundles are typically small, well under a few MB) prior to decompression.

### Proof of Concept
Go test plan:
1. Stub `remote.Referrers`/`remote.Image`/`layers[0].Uncompressed` (as done via the existing mock infrastructure in `pkg/cmd/attestation/artifact/oci/mock_client.go`) to return an `io.ReadCloser` backed by a real `gzip.Writer` stream that repeatedly writes a repeating byte pattern (e.g., zeros) to produce a gzip stream that is a few KB compressed but expands to >1GB when decompressed (classic "zip/gzip bomb" construction).
2. Call `LiveClient.GetAttestations` (or a helper extracted for testing) with this mocked layer and assert that the process either returns a bounded-size error before completing `io.ReadAll`, or measure that memory usage grows unbounded/exceeds an expected cap, demonstrating the missing size guard.
3. Expected (fixed) behavior: an explicit "bundle too large" error returned quickly with bounded memory allocation; expected (current) behavior: `io.ReadAll` allocates and returns the full multi-hundred-MB/GB buffer, or the test harness OOMs.
