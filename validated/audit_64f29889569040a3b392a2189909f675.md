### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while the event handlers act on the independently-read `repository.full_name` field, allowing cross-tenant/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) is used to validate the HMAC signature by reading `repository.owner.login` (or `organization.login`) out of the **same JSON body** that is being verified. Once the signature check passes, `WebhooksController#create` hands the *entire raw payload* to the event handlers, which independently re-read `repository.full_name` (a different field of that same body) to decide which `Stack`/`Repository` record to mutate. Nothing cross-checks that the organization whose secret validated the request actually owns the repository the handler is about to act on. This is the exact bug class in the report: the field that is cryptographically authenticated (`repository.owner.login`) is not the field that the code acts on (`repository.full_name`).

### Finding Description
Signature selection/verification: [1](#0-0) [2](#0-1) 

Handler dispatch uses the raw JSON `params` for both event routing and the actual write target: [3](#0-2) 

Every handler looks up the repository/stack to mutate from `payload.dig('repository', 'full_name')`, a field never compared to the `repository_owner` value that was used to pick the verifying secret: [4](#0-3) 

Concrete write handlers built on top of this trust binding: [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting several independent GitHub App installations (one per tenant organization) on a single Shipit instance, each with its own `app_id`/`webhook_secret`, as documented and fixtured: [7](#0-6) [8](#0-7) 

The verification logic itself is a straightforward per-secret HMAC-SHA1 comparison — it authenticates the *bytes*, not any binding between the org and the repository named inside those bytes: [9](#0-8) 

**Equality broken:** the trust invariant Shipit relies on is `verifying_organization(repository.owner.login) == acted_upon_repository.owner(repository.full_name)`. Because a legitimate tenant organization ("OrgA") knows its own `webhook_secret` (it configured its own GitHub App per `docs/setup.md`), it can sign an arbitrary JSON body with that secret. As long as `repository.owner.login`/`organization.login` in that body says `"OrgA"` (so `Shipit.github(organization: repository_owner)` selects OrgA's secret and the signature validates), the `repository.full_name` field can name a repository belonging to any other tenant, e.g. `"OrgB/victim-repo"`. `Handler#repository_name` and `Repository.from_github_repo_name` never check that the org that authenticated the request actually owns that repository.

### Impact Explanation
A tenant organization onboarded onto a shared Shipit instance can forge webhook deliveries (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are cryptographically valid under its own secret but target `Stack`/`Repository`/`Commit` records belonging to a different tenant's repository. Concretely:
- `PushHandler` forces `stack.sync_github(expected_head_sha:)` on a victim's stacks for an attacker-chosen SHA [5](#0-4) .
- `StatusHandler` writes fabricated CI/commit statuses onto a victim's commits [6](#0-5) , which can influence deployability gating that legitimate deploys rely on.

This is a cross-repository write performed without the writing organization having any legitimate GitHub-side access (installation, collaborator, or team membership) to the victim repository — matching the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Any tenant organization that is a legitimate, unprivileged customer of a multi-org Shipit deployment (a documented, supported configuration) already possesses everything needed: knowledge of its own `webhook_secret` and the ability to send an arbitrary POST to the shared `/webhooks` endpoint with a body it fully controls and signs itself. No GitHub App private key, no Shipit session, and no access to the victim organization are required — only the attacker's own legitimately-provisioned webhook secret, which they are entitled to hold. This makes the attack straightforward to reproduce for anyone hosted on a shared instance.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the verifying secret (`repository_owner`) matches the organization portion of `repository.full_name` (and, ideally, that the App installation associated with that secret actually has installation access to that specific repository) before any handler is allowed to look up or mutate a `Repository`/`Stack`. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two tenant GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, an administrator of `OrgA`, knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` to `"OrgA"` [2](#0-1) , loads `OrgA`'s app, and the HMAC check passes because the attacker signed with the correct (their own) secret [9](#0-8) .
6. `PushHandler#process` resolves the target stacks via `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"` [4](#0-3)  and forces `sync_github(expected_head_sha: "<attacker chosen sha>")` on `OrgB`'s stacks, without `OrgA` ever having legitimate access to `OrgB/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
