### Title
Webhook signature check authenticates the payload's declared organization, not the repository the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner`, a value taken from the same untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the raw body is re-parsed and dispatched to event handlers that key off a *different* field of the same payload — `repository.full_name` — to determine which `Stack`/`Repository` to act on. Nothing ties `repository.owner.login` to `repository.full_name`, so the organization whose secret authorized the request is not the same binding as the repository that gets written to.

### Finding Description
`verify_signature` computes the org used to look up the webhook secret purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

```
repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [3](#0-2) 

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` config for that org, and `verify_webhook_signature` explicitly treats a missing `webhook_secret` as automatically verified:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [4](#0-3) 

Shipit's own setup docs show `webhook_secret` as an optional/nilable field per organization, confirming an org can legitimately be configured with no secret at all: [5](#0-4) 

After `head(422)` is (conditionally) sent, execution continues (no `return`) and `create` re-parses the raw body and dispatches to handlers with the **same JSON**, this time keyed by `repository.full_name`, a completely independent field: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is: `organization used to select/verify the webhook secret == organization owning the repository the handler mutates`. Instead, the code trusts `repository.owner.login` (or `organization.login`) for authentication and `repository.full_name` for the write target — two independent, attacker-supplied strings in the same unauthenticated JSON body. If any org configured in Shipit's `github` secrets has no `webhook_secret` set (an explicitly supported, documented configuration), an attacker can send a forged webhook whose `repository.owner.login`/`organization.login` names that secret-less org (satisfying `verify_signature`) while `repository.full_name` names an entirely different, secured stack/repository that the attacker wants to affect. The `PushHandler` will then locate that unrelated stack via `Repository.from_github_repo_name(repository_name)` and enqueue a `GithubSyncJob` with an attacker-controlled `expected_head_sha`, and other handlers (`status`, `check_suite`, `pull_request`) resolve their target the same way via `repository.full_name`.

### Impact Explanation
This breaks the trust boundary between "which org's secret authenticated this HTTP request" and "which repository/stack this request is allowed to mutate." Concretely, a `push` webhook forged this way causes `Stack#sync_github` to run against a victim stack with an attacker-chosen `expected_head_sha`/ref, without knowledge of that stack's real webhook secret — an unauthorized action against a repository the request was never actually authenticated for. Other handlers (`status`, `check_suite`, `membership`, `pull_request`) are reachable through the identical bypass and can create commit statuses, archive/unarchive review stacks, or add team memberships against the mismatched target. This aligns with the "unauthorized deploy/rollback trigger" / "escalation into authorization-relevant state" class of impact, since it lets an unauthenticated caller act on a repository never covered by the signature that was actually checked.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: a deployment must have at least one configured GitHub organization with `webhook_secret` left blank (a state the documentation explicitly presents as normal/optional) while other organizations in the same instance do have secrets configured and host the higher-value stacks. Single-org deployments using the documented single-org config format are not affected by the *organization*-name confusion since there is only one org to select, though the deeper issue — that authentication is decided from a field never cross-checked against the actual write target (`repository.full_name`) — remains structurally present. I could not fully verify from the index whether every Shipit instance in practice always sets a webhook secret for every org, so likelihood is conditional on that operational fact rather than proven universal.

### Recommendation
Do not derive the authentication scope and the mutation scope from independent, uncorrelated fields of the same unauthenticated payload. Specifically:
- Cross-validate that `repository.full_name`'s owner segment matches `repository.owner.login` (or `organization.login`) before dispatching to handlers, and reject mismatches.
- Do not treat a missing `webhook_secret` as "verified" (`return true unless webhook_secret`) for any organization that also hosts stacks with secrets configured elsewhere; require a secret to be present or fail closed if any other configured org has an active secret.
- Ensure `verify_signature` actually halts the request (`head(422)` currently doesn't `return`/`throw(:abort)`, so execution can continue into `create` even on failed logging paths) — add an explicit `return` after `head(422)`.

### Proof of Concept
Preconditions: Shipit configured with `github: { OrgA: { webhook_secret: nil, ... }, OrgB: { webhook_secret: "s3cr3t", ... } }` (multi-org config as documented), with a `Stack` for `OrgB/high-value-repo`.

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/high-value-repo",
    "owner": { "login": "OrgA" }
  }
}
```
No valid `X-Hub-Signature` is required.
2. `verify_signature` computes `repository_owner == "OrgA"`, looks up `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` returns `true` immediately because OrgA has no `webhook_secret` configured.
3. `create` re-parses the body and calls `Shipit::Webhooks::Handlers::PushHandler.call(params)`.
4. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("OrgB/high-value-repo")`, finds the real `OrgB` stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` for the victim stack — despite the request never being authenticated with `OrgB`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
