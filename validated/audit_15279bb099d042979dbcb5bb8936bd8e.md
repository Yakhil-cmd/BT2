Based on my investigation, I found a genuine analog to this CVE's bug class in the archived-content / pruned-joint caching mechanism, where a strong reference to "master" content is granted based on a check that predates a concurrent state change, and the consumer trusts stale cached content across an async boundary without re-verifying it is still authoritative.

### Title
Stale/unverified pruned-output cache trusted to reconstruct spend inputs during payment validation - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` in [1](#0-0)  falls back to `archiving.getCachedOutput()` (populated by `archiving.cachePrunedJoint()` in [2](#0-1) ) whenever a spent output's `address` column is empty because the source unit was already stripped (`final-bad`, pruned). The cached, in-memory copy of the pruned joint is trusted as if it were an authoritative DB-verified source of `address`/`amount`/`denomination`/`asset` for a spend being validated for a brand-new incoming unit, similar to how ctnetlink trusted `exp->master` without re-verifying/holding a reference under the correct lock while other code paths could tear down the master object.

### Finding Description
`updateMinRetrievableMciAfterStabilizingMci` strips (voids) old `final-bad` units' full content from the `outputs`/`units` tables once they fall below `min_retrievable_mci`, but keeps a full in-memory copy alive for a bounded TTL via `archiving.cachePrunedJoint(objJoint)` [3](#0-2)  purely "in case somebody still needs it" during the stripping race window. This cache is a global, TTL-based, un-locked JS object (`assocCachedPrunedJoints`) [4](#0-3) , expired periodically by `purgeExpiredCachedPrunedJoints` [5](#0-4) .

When any subsequently posted unit references an input whose source output row has since had its `address` column stripped (i.e., it was voided as `final-bad`), the payment-validation code path unconditionally accepts the cached pruned-joint content in lieu of the live database row: [1](#0-0) . There is no re-check that:
- the referenced message/output actually still corresponds to what the cache holds (the cache is looked up purely by `unit`/`message_index`/`output_index` coordinates supplied by the untrusted new unit, similar to the kernel bug trusting `exp->master` reached only through the attacker-influenced expectation object without re-validating);
- the cached copy hasn't been superseded by any authoritative state change since it was captured (there is no lock coordinating `cachePrunedJoint` writes against `getCachedOutput` reads, unlike the correct fix in the CVE which extends `nf_conntrack_expect_lock` around the entire access);
- the TTL race window (`PRUNED_JOINT_CACHE_TTL_ms = 60*60*1000`) does not silently swap between "trust the cache" and "reject the unit," which is nondeterministic across nodes validating the same unit at different wall-clock offsets from the strip event.

This is the same class of bug: a secondary object (in the kernel, the expectation; here, the archived-pruned-joint cache entry) is used to reach a "master" record (the master conntrack; here, the historical spent-output data) that has already been invalidated/removed from its authoritative store, and the code trusts it without holding a lock/consistency guarantee tying its lifetime and content correctness to the moment of use.

### Impact Explanation
Because nodes may have divergent local pruning/caching state and independent TTL expiry timing, two full nodes validating the exact same posted unit can reach different conclusions: one may accept the payment by trusting a locally-cached pruned joint, and another (whose cache entry already expired, or was never populated because it never independently pruned that unit) rejects the unit with `output being spent ... not found` [6](#0-5) . This produces node disagreement on unit validity for units spending previously-voided final-bad outputs, which can be triggered by any unprivileged unit poster crafting an input that targets a stripped/voided output coordinate. Divergent validity decisions across the network threaten consensus on which units are valid, a core DAG-stability guarantee.

### Likelihood Explanation
Reachable directly by posting a single ordinary unit whose `payment` message references an input `(unit, message_index, output_index)` pointing at a unit that is `final-bad` and has fallen below `min_retrievable_mci` (i.e., already voided/stripped). No special privileges, hub/peer trust, or multi-party coordination are required — this is exactly the "unprivileged unit poster" actor this analysis is scoped to accept. The only variable is the non-deterministic timing of `PRUNED_JOINT_CACHE_TTL_ms` expiry and whether the receiving node itself performed the pruning (and thus populated its own cache) versus a node that never pruned that particular unit and therefore never caches it at all.

### Recommendation
Do not treat `archiving.getCachedOutput()` as authoritative for validation decisions that must be network-wide deterministic. Either: (1) remove the pruned-joint cache fallback from `validatePaymentInputsAndOutputs` and instead require re-fetching the full joint content from peers/history when the local row has been stripped, ensuring all nodes converge on the same DB-backed authoritative record before accepting a spend; or (2) make the fallback deterministic and unit-hash-verified — require that the requested (unit, message_index, output_index) be checked against the joint's committed unit hash/ball before trusting any field from the cache, and disable the cache path entirely once TTL is not synchronized across the network (i.e., never use it as a basis for `ifOk`, only to serve historical reads to peers).

### Proof of Concept
1. Post/allow a unit `U1` with a `payment` output to be accepted, then get it marked `final-bad` (nonserial loser) and let it fall below `min_retrievable_mci` so `updateMinRetrievableMciAfterStabilizingMci` strips it and populates `assocCachedPrunedJoints[U1]` [7](#0-6) .
2. Immediately post a new unit `U2` whose payment input references `U1`'s now-stripped output coordinates.
3. On a node that still holds `U1` in `assocCachedPrunedJoints` (within the 1‑hour TTL), `validatePaymentInputsAndOutputs` reconstructs `src_output` from the cache and validation proceeds [1](#0-0) .
4. On a node whose cache entry has already expired (`purgeExpiredCachedPrunedJoints`) or that never independently pruned/cached `U1` (e.g., it received `U1` already stripped via catchup), the same `U2` is rejected with `"output being spent ... not found"`.
5. Result: `U2` is accepted as valid by some nodes and rejected by others — a concrete node disagreement on unit validity triggered purely by an unprivileged unit poster.

**File:** archiving.js (L7-19)
```javascript
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
```

```javascript
function purgeExpiredCachedPrunedJoints(){
	const now = Date.now();
	for (let unit in assocCachedPrunedJoints)
		if (assocCachedPrunedJoints[unit].expiry_ts < now)
			delete assocCachedPrunedJoints[unit];
}
setInterval(purgeExpiredCachedPrunedJoints, PRUNED_JOINT_CACHE_TTL_ms);
```
