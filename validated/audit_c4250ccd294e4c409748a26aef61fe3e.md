### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature is verified against the GitHub organization derived from the payload's `repository.owner.login` [1](#0-0) , but `StatusHandler#process` never re-checks that binding: it looks up every `Commit` in the entire database that shares the attacker-supplied `sha`, with no scoping to the repository/stack that was actually authenticated [2](#0-1) . This breaks the equality "organization that authenticated the webhook" == "repository/stack whose commit status is written".

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using `repository_owner`, computed from the payload itself (`params.dig('repository', 'owner', 'login')`) [3](#0-2) . This only proves the request was genuinely signed by *some* organization's GitHub App installation for the repository named in the payload — it says nothing about which `Commit` records the handler is allowed to mutate.

For the `status` event, `Handler#stacks` (which scopes lookups to `Repository.from_github_repo_name(repository_name)`) exists [4](#0-3)  and is correctly used by `CheckSuiteHandler` [5](#0-4)  and `PushHandler` [6](#0-5) . However, `StatusHandler` does not use `stacks` at all — it looks the commit up globally by `sha` only:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Since git commit hashes are content-addressed and not unique per repository, the same `sha` can legitimately exist in multiple `Stack`s tracked by the same Shipit instance (e.g. a fork of, or shared history with, another tracked repository). An attacker who owns/administers such a repository can:
1. Trigger a genuine, correctly-signed `status` webhook from their own org/repo (e.g. by calling GitHub's Statuses API on a commit that exists in their fork and also exists in a victim org's tracked stack).
2. `verify_signature` authenticates this webhook correctly for the attacker's own organization.
3. `StatusHandler` then updates `create_status_from_github!` on **every** `Commit` row across all stacks sharing that `sha`, including the victim's stack, which the attacker never had permission over.

### Impact Explanation
`Commit#deployable?` and `Stack#deployable?`/`branch_status`/CD triggering all rely on the commit's `status` state [7](#0-6) , and successful status transitions can enqueue merges/deploys (see `ProcessMergeRequestsJob` enqueued from `create_status_from_github!`, exercised in `commits_test.rb` around lines 763-777). By forging a `success` status on a shared `sha`, an attacker with no privileges on the victim organization can flip a victim commit into a deployable/mergeable state, causing an unauthorized deploy/merge decision — meeting the High/Critical "unauthorized deploy" impact criterion.

### Likelihood Explanation
Requires the attacker to control a repository (fork or shared-history repo) with a commit `sha` overlapping a stack tracked in the same Shipit instance, and to be able to legitimately create/update a commit status on that sha via the normal GitHub Statuses API (which they can do on any repo they administer). No Shipit credentials, API tokens, or webhook secrets belonging to the victim organization are needed. This is a realistic scenario for shared/forked open-source projects tracked as separate Shipit stacks.

### Recommendation
Scope `StatusHandler#process` to the repository/stacks authenticated by the webhook, mirroring `CheckSuiteHandler` and `PushHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` (or join `Commit` through `Stack`/`Repository` derived from `payload.dig('repository', 'full_name')`) instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Track two stacks in the same Shipit instance: victim org `V/repo` and attacker-controlled `A/fork`, where `A/fork` shares a commit `sha` with `V/repo` (e.g. a fork with unmerged upstream history, or a cherry-picked commit).
2. As the owner of `A/fork`, call GitHub's `POST /repos/A/fork/statuses/{sha}` with `state=success` for the shared `sha`.
3. GitHub sends a `status` webhook to Shipit, signed with `A`'s app/webhook secret; `repository.owner.login == "A"`, so `verify_signature` passes.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the commit row belonging to `V/repo`'s stack, and calls `create_status_from_github!`, changing that commit's state without any authorization from org `V`.
