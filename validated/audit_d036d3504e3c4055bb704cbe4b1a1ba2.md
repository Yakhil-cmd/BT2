### Title
Webhook signature verified against `repository.owner.login` while mutation targets `repository.full_name` — cross-organization stack sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner` (`params.dig('repository','owner','login')`), but the actual write path (`Handler#repository_name` → `Repository.from_github_repo_name` → `stack.sync_github`) uses `repository.full_name` from the same JSON body. These two fields are never cross-checked, so an attacker who controls a configured GitHub organization (or one with no `webhook_secret`) can forge `repository.owner.login` to their own org while setting `repository.full_name` to any victim repo/org, causing that victim's stack to be resynced from an attacker-chosen `after` sha.

### Finding Description
The broken binding: the org whose secret verifies the HMAC (`repository_owner` = `params.dig('repository','owner','login')`) must equal the org that owns the mutated repository (`repository.full_name.split('/').first`, used in `Repository.from_github_repo_name`). The code never enforces this equality.

Path:
1. `WebhooksController#create` parses `request.raw_post` as JSON with no schema binding `owner.login` to `full_name`'s prefix: [1](#0-0) 
2. `verify_signature` picks the `GitHubApp` using only `repository_owner`: [2](#0-1) 
3. `repository_owner` reads `params.dig('repository', 'owner', 'login')`: [3](#0-2) 
4. `GitHubApp#verify_webhook_signature` returns `true` unconditionally if no `webhook_secret` is configured for that org: [4](#0-3) 
5. On success, `PushHandler.call(params)` is invoked, and `Handler#repository_name` reads a completely different field, `payload.dig('repository', 'full_name')`: [5](#0-4) 
6. `Repository.from_github_repo_name` looks up the DB record purely from the `owner/name` parsed out of `full_name`, with no reference to `owner.login`: [6](#0-5) 
7. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack on the target branch: [7](#0-6) 

Exploit: attacker sends `POST /webhooks` with `X-Github-Event: push`, body `{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/prod-repo"},"ref":"refs/heads/main","after":"deadbeef"}`. If `attacker-org` is configured in `Shipit.github` (attacker's own org, which they control/install the app for) with no `webhook_secret` or a secret they know, step 4 returns `true` and the request passes signature verification entirely on the strength of `attacker-org`'s credentials/lack thereof — yet the mutation in step 6-7 operates on `victim-org/prod-repo`'s `Stack`, resyncing it via `GithubSyncJob` (which fetches commits with the app's real GitHub credentials and appends them, driving continuous deployment) with an attacker-supplied `expected_head_sha`.

Why existing guards fail: `drop_unhandled_event` only checks the event type exists in `Shipit::Webhooks.handlers`, not the payload's internal consistency. `ExplicitParameters::Parameters` schema on `PushHandler` only requires `:ref` and `:after` are present — it does not validate `repository.full_name` against `repository.owner.login`. `GithubOrganizationUnknown` is only raised if `attacker-org` itself isn't configured at all; since the attacker controls/uses their own valid, configured org, this exception path is never hit.

### Impact Explanation
An attacker who registers/controls any GitHub organization configured in the target Shipit instance's `Shipit.github` multi-org config (or an org with no secret) can trigger `GithubSyncJob` for an arbitrary victim `Stack` belonging to a completely different, unrelated organization, forcing it to fetch and append attacker-influenced commits and potentially drive continuous deployment/rollback for that stack. This is a cross-repository/cross-tenant write triggered by a payload whose provenance was never actually validated for the resource being mutated, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team". It is repeatable against every stack/repository known to the Shipit instance, for every push (and similarly for `status`, `check_suite`, `pull_request`, `membership` handlers, which all trust `repository.full_name` or `organization.login` independently of the field verified in `verify_signature`).

### Likelihood Explanation
This requires the Shipit instance to run in "multiple GitHub applications" mode (`Shipit.github` keyed by org) per `docs/setup.md`, and for the attacker to control at least one configured organization (e.g., their own org where they've installed a Shipit GitHub App with no or known `webhook_secret`) — a low bar since the attacker only needs to be a legitimate but unprivileged user of the platform for one org while targeting another org's stacks. In single-org deployments (`github_default_organization` returns `nil`), `Shipit.github` ignores the `organization:` argument entirely, so this specific divergence collapses (the same single secret is used regardless); the exploit is specific to multi-org configurations, which is an explicitly documented and supported configuration. [8](#0-7) 

### Recommendation
In `Handler#repository_name` / `Webhooks::Handlers::Handler`, or in `WebhooksController#verify_signature`, enforce that the organization used to verify the signature equals the owner segment of `repository.full_name` (and any `organization.login` present) before dispatching to handlers — reject the request with 422 if they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push webhook signed by one org cannot sync a stack owned by another org" do
  victim_stack = shipit_stacks(:shipit) # owner: "shopify", full_name "shopify/shipit-engine"
  Shipit.stubs(:github_default_organization).returns("attacker-org")
  Shipit.stubs(:github_app_config).with("attacker-org").returns({ webhook_secret: nil })

  body = {
    repository: { owner: { login: "attacker-org" }, full_name: victim_stack.repository.full_name },
    ref: "refs/heads/#{victim_stack.branch}",
    after: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
  }.to_json

  @request.headers['X-Github-Event'] = 'push'
  # no X-Hub-Signature needed: attacker-org has no webhook_secret configured

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"]) do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Assert both sides of the binding: `repository_owner` (`"attacker-org"`) used in `verify_signature` must equal the owner of the stack mutated (`victim_stack.repository.owner`, `"shopify"`); the test demonstrates they diverge and the sync job is enqueued anyway for the victim's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
