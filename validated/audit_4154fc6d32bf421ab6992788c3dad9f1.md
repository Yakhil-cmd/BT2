### Title
Cross-organization webhook forgery — signature validated against `repository.owner.login` but repository acted upon is taken from unchecked `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This engine supports hosting multiple GitHub organizations with independent webhook secrets via `Shipit.github_app_config` [1](#0-0)  and the multi-org secrets schema documented in `config/secrets.development.example.yml` [2](#0-1) . `WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the raw payload against based solely on `repository_owner`, a field read directly out of the untrusted, attacker-supplied JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . However, the event handlers that actually act on the payload (e.g. `PushHandler`) determine the target repository/stack from a **different** field, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`, the field the signature check keyed off.

### Finding Description
This mirrors the Securitize bug class: one code path (`swap()`) validated that the wallet belonged to the claimed investor before acting, while the sibling path (`buy()`) skipped that check, letting attackers substitute an unverified value. Here, the binding that should hold is:

`organization authenticated via HMAC (repository.owner.login)` == `repository actually written to (repository.full_name)`

but no code enforces this equality.

Concretely:
1. Shipit is configured with two (or more) GitHub Apps/organizations, e.g. `OrgA` and `OrgB`, each with its own `webhook_secret`, as supported by the multi-org config schema [6](#0-5) .
2. An attacker who legitimately possesses (or can trigger) `OrgA`'s webhook delivery — e.g. because they administer a repository under `OrgA`, or `OrgA`'s webhook secret has otherwise been exposed to them — can compute a valid HMAC-SHA1 signature over an arbitrary JSON body using `OrgA`'s secret.
3. The attacker crafts a payload where `repository.owner.login = "OrgA"` (so `verify_signature` picks `OrgA`'s `webhook_secret` and the signature validates) but `repository.full_name = "OrgB/some-repo"` (so `Handler#repository_name` / `Repository.from_github_repo_name` resolves to a stack that actually belongs to `OrgB`).
4. `verify_signature` passes because it only checks the HMAC against the org derived from the attacker-controlled `repository.owner.login` field [7](#0-6) , and the dispatched handler then blindly trusts `repository.full_name` to select the target `Repository`/`Stack`, with no cross-check against `repository.owner.login` or against the organization whose secret validated the request.

Before the attacker's request: `OrgA`'s webhook secret only authorizes events for repositories owned by `OrgA`.
After: the same secret is sufficient to trigger `PushHandler#process` (`GithubSyncJob`), pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), or other webhook-driven state changes against any stack under `OrgB`, `OrgC`, etc., that Shipit also hosts — an org the attacker has no relationship with.

### Impact Explanation
This crosses an authentication boundary the report's rule set explicitly calls out: "an organization that authenticated versus the repository that is written." An attacker with only one organization's webhook credentials can force webhook-triggered actions (e.g. `stack.sync_github`, review-stack archive/unarchive/provisioning via `ReviewStackAdapter`) against stacks belonging to a completely different, unrelated organization hosted on the same Shipit instance — effectively a cross-repository/cross-organization write triggered by forged webhook events, without ever needing that other organization's secret.

### Likelihood Explanation
Requires: (a) Shipit configured to host multiple organizations (a documented, supported configuration [2](#0-1) ), and (b) the attacker having legitimate access to trigger/forge a valid webhook for at least one hosted organization (e.g. as a collaborator/admin capable of receiving delivery or replaying it, or via a leaked secret for that one org). Given multi-tenant hosting is an explicit supported feature, this is a realistic configuration, though it does require compromise/possession of at least one org's webhook secret to exploit against the others.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to validate the signature matches the owner encoded in `repository.full_name` (and `organization.login` for org-level events) before dispatching to handlers — reject requests where these differ instead of trusting `repository.full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `test/dummy/config/secrets_double_github_app.yml`).
2. As an entity with access to `OrgA`'s webhook secret, compute `signature = HMAC-SHA1(OrgA_webhook_secret, body)` for:
```json
{
  "ref": "refs/heads/master",
  "after": "<arbitrary sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates. `PushHandler#process` then resolves `Repository.from_github_repo_name("OrgB/target-repo")` and syncs/deploys a stack under `OrgB`, despite the request only being authenticated against `OrgA`'s secret.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
