### Title
Unauthenticated webhook signature bypass when `webhook_secret` is unset leads to forged `membership` events and escalation into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` delegates HMAC verification to `GithubApp#verify_webhook_signature`, which short-circuits to `true` whenever no `webhook_secret` is configured for the organization named in the payload. Because Shipit's own documentation and sample configs (`config/secrets.development.shopify.yml`, `docs/setup.md`) present `webhook_secret` as optional ("If you've set a webhook secret during the App creation, you should copy it here"), any org onboarded without one accepts **completely unauthenticated** webhook POSTs. This breaks the trust binding "an organization that authenticated (its `X-Hub-Signature`) versus the repository/organization whose state the webhook handler writes." An unprivileged network attacker can POST a forged `membership` event and get themselves (or any GitHub login) added as a member of a `Team` that is included in `Shipit.github_teams`, which is the authorization gate checked by `User#authorized?`.

### Finding Description
`GithubApp#verify_webhook_signature` is defined as: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

`WebhooksController#verify_signature` picks the `GithubApp` instance to check against using data taken directly from the unauthenticated request body, *before* any signature is validated: [2](#0-1) 

`repository_owner` is derived purely from the payload (`params.dig('repository','owner','login') || params.dig('organization','login')`): [3](#0-2) 

If the org identified by that field has no `webhook_secret` configured (a state the docs/sample configs explicitly allow — see `docs/setup.md` lines 119, and `config/secrets.development.shopify.yml` showing `webhook_secret: # nil`), `verify_webhook_signature` unconditionally returns `true`, and the request proceeds to be dispatched to the real handlers with no cryptographic proof it originated from GitHub.

For the `membership` event, `MembershipHandler#process` trusts the payload's `team`, `organization`, and `member.login` fields to find-or-create a `Team` and add a `member` to it: [4](#0-3) 

Team membership directly controls authorization: `User#authorized?` checks whether the user belongs to a team present in `Shipit.github_teams`: [5](#0-4) 

and `Team#add_member` performs no additional GitHub-side verification before appending the membership record: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization whose signature was cryptographically verified` == `organization/team whose authorization state is mutated by the handler`.

When `webhook_secret` is absent for the org named in the (forged) payload, the left side of that equality is vacuously "verified" (bypassed), while the right side (team membership → `Shipit.github_teams` authorization) is fully attacker-controlled.

### Impact Explanation
This maps to the explicitly allowed High-severity outcome: "escalation into `Shipit.github_teams` authorization." An attacker who knows (or guesses) the `github_id`/`slug`/`organization` values of a team already listed in `Shipit.github_teams` (these are often public GitHub team metadata, or can be inferred/brute-forced since `Team.find_or_create_by!` keys only on `github_id`) can forge a `membership` `added` action naming any GitHub login as `member`. `MembershipHandler` will:
1. `find_or_create_by!` the `Team` row (or reuse an existing authorized team).
2. `User.find_or_create_by_login!(login)` — creating a `Shipit::User` record for an arbitrary login (this call itself makes an authenticated GitHub API call via `Shipit.github.api.user(login)`, but does not validate that the *attacker* controls that account).
3. `team.add_member(member)` — granting that user `authorized?` status without any real GitHub team membership.

Combined with the OAuth login flow (`GithubAuthenticationController#sign_in_github` / `User.find_or_create_from_github`), once a `User` row exists and is authorized via a forged membership, that GitHub identity can log in through the normal OAuth path and pass `Authentication#force_github_authentication`'s `authorized?` check, gaining access to protected stacks, deploys, and API client management pages that are otherwise gated to trusted GitHub teams.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: this is only exploitable for organizations that are onboarded to a multi-org Shipit deployment without a `webhook_secret` set, a configuration explicitly presented as normal/optional by the project's own setup documentation and sample secrets files rather than as a misconfiguration to avoid. In any deployment following the documented setup with an organization lacking a webhook secret, the check silently and totally disables authentication for that organization's webhook traffic, so likelihood is high wherever that documented option is used.

### Recommendation
- Treat a missing `webhook_secret` as a hard configuration error rather than an implicit "trust everything" bypass; `verify_webhook_signature` should fail closed (return `false`/raise) when `webhook_secret` is blank, or Shipit should refuse to boot/mount webhooks for an org without one.
- Decouple "which secret to verify with" from attacker-supplied payload fields: resolve the target organization from the verified GitHub App installation/delivery metadata (e.g., signed headers, installation ID) rather than `repository.owner.login` taken from the JSON body prior to verification.
- In `MembershipHandler` (and other handlers that mutate authorization-relevant state), add defense-in-depth by cross-checking the payload's `organization.login`/`team` against an actual GitHub API call before creating/mutating `Team`/`Membership` records, instead of trusting the webhook body outright once "verified."

### Proof of Concept
Preconditions: Shipit is configured for at least one organization (`OrgX`) that has `webhook_secret` unset (per documented optional configuration), and `Shipit.github_teams` includes a team known to belong to `OrgX` (its `github_id`/`slug`/`name` are typically discoverable via GitHub's public team/org pages or prior legitimate webhook traffic).

1. Attacker crafts a POST to `/webhooks` (no valid `X-Hub-Signature` needed) with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <authorized_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/..." },
  "organization": { "login": "OrgX" },
  "member": { "login": "attacker-github-login" }
}
```
2. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgX"` from the body (`app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `Shipit.github(organization: "OrgX")`, and calls `verify_webhook_signature`, which returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
3. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which creates/finds the authorized `Team` and appends `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`, `app/models/shipit/team.rb:41-43`).
4. Attacker completes normal GitHub OAuth login as `attacker-github-login`; `User#authorized?` now returns `true` because the forged `Membership` row satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?` (`app/models/shipit/user.rb:80-82`), granting access to Shipit's protected stack/deploy/API-client UI despite never actually belonging to the real GitHub team.

Note: I could not fully trace whether any additional runtime guard exists that forces `webhook_secret` presence at engine boot (outside `app/**`/`lib/shipit/**`); this analysis is based solely on the in-scope engine code paths reviewed above.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

      ].join(' '))
    end
```
