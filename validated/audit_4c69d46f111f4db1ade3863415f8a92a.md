### Title
AA `timestamp` builtin resolves to a unit-poster-controlled value, enabling MEV-style manipulation of time-dependent AA logic - ([File: formula/evaluation.js])

### Summary
The `timestamp` keyword available to Autonomous Agent (AA) formulas does not reflect independently-verified real time. It resolves to `objValidationState.last_ball_timestamp`, which in turn is set to the `timestamp` field of whichever unit happens to occupy the relevant main-chain index (MCI) at trigger-execution time. That field is chosen by the author of an ordinary, unprivileged unit, constrained only by "not less than the parent's timestamp" and "not more than `max_seconds_into_the_future_to_accept` (default 5s) ahead of real time." This is structurally identical to the reported `block.timestamp` MEV issue: a party with limited, bounded control over the "clock" value can bias any AA logic that keys interest, unlocks, auctions, or health/liquidation checks off `timestamp`.

### Finding Description
In `formula/evaluation.js`, the `timestamp` operator in oscript is defined as: [1](#0-0) 

`objValidationState.last_ball_timestamp` is populated in `aa_composer.js` when a trigger is actually handled (not merely dry-run/estimated), directly from `objMcUnit.timestamp`: [2](#0-1) 

`objMcUnit` is obtained via `readMcUnit(conn, mci, ...)` inside `handlePrimaryAATrigger`, i.e. it is the actual unit that sits on the main chain at the trigger's stabilized `mci`: [3](#0-2) 

The `timestamp` field of that unit is set by its author (an ordinary, unprivileged unit poster — not a witness-only privilege) when composing it, and it is only weakly constrained by validation:
- It must not be more than a few seconds (`conf.max_seconds_into_the_future_to_accept`, default 5) ahead of the validating node's own clock: [4](#0-3) 
- It must not decrease relative to any parent unit's timestamp, but there is no lower bound forcing it to advance — a poster may simply repeat (or minimally increment) a parent's timestamp: [5](#0-4) 

Because ordinary unit posting is permissionless and any unit can end up on the main chain (subject to normal DAG/witness consensus, not special privilege), an unprivileged actor who can influence which unit becomes the MC unit at a given MCI — or simply times/crafts their own unit to land there — has bounded discretion over the `timestamp` value that every AA trigger executing at that MCI will observe via the `timestamp` keyword. This mirrors the reported bug class: a party with limited timestamp-setting latitude can shift the observed "clock" forward (up to +5s) or effectively freeze it (repeat the parent's timestamp) to bias any AA logic built on `timestamp` for time-based calculations (e.g., interest accrual, vesting/unlock schedules, auction end-times, price decay, or health/margin checks analogous to JUSD's `tRate`).

### Impact Explanation
Any AA definition that uses the `timestamp` builtin for security- or economically-relevant time arithmetic (interest-rate accrual, collateral health checks, auction/vesting deadlines, price-decay curves) inherits this weak timestamp guarantee. An actor with the ability to get a unit onto the main chain at the relevant MCI can nudge the observed time backward (by not advancing it beyond the parent) or forward (up to 5 seconds), which can:
- Prevent a time-gated unlock or auction-close condition from triggering as expected (freezing time), or
- Prematurely satisfy a time-based condition (fast-forwarding within the 5s window), or
- Skew interest/decay accrual computed via `timestamp` differences within an AA's own state variables.
This falls under "AA fund loss or freezing" / manipulation of AA logic reachable purely by posting units and triggers — no privileged network role is required.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need to be a witness or a network operator, only an ordinary user able to post units, and the manipulation window is small (≤5 seconds forward, and only a "freeze" backward relative to the last observed timestamp). Exploitability therefore depends heavily on how sensitive a given AA's economic logic is to sub-multi-second timestamp drift and on how tightly the AA's trigger execution is coupled to a specific MCI/timestamp. For AAs with fine-grained per-second interest/decay formulas or tight auction windows, this bounded but real timestamp discretion is sufficient to produce a measurable, repeatable bias.

### Recommendation
- Avoid relying on `timestamp` (derived from `last_ball_timestamp`, itself sourced from an arbitrary unit author's self-reported clock) for security-critical time arithmetic in AA templates that ship as part of the platform's reference contracts or examples; where possible, use `mci`-based conditions (main-chain index) instead, since MCI advancement is a consensus-driven counter, not a self-reported value.
- Tighten `max_seconds_into_the_future_to_accept` and consider enforcing a minimum forward progress for timestamps (not just non-decrease) so that "freezing" the clock across many stabilized units becomes costlier/detectable.
- Document explicitly, in the oscript/AA authoring documentation, that `timestamp` provides only weak, bounded, unprivileged-user-influenced guarantees, and is not suitable as a precise oracle for time — analogous to Ethereum's guidance to avoid `block.timestamp` for anything requiring precision.

### Proof of Concept
Conceptual (root cause confirmed in code; full end-to-end DAG PoC requires a running network / Devin session to construct and stabilize competing units):
1. Deploy an AA whose formula uses `timestamp` for a time-sensitive computation, e.g. `var['unlock_ok'] = (timestamp - var['start_ts']) >= 86400;` (a 24h unlock condition).
2. As an ordinary (non-witness) unit author, compose consecutive units so that the unit which becomes the on-main-chain unit at the relevant MCI has its `timestamp` field set to the minimum allowed value (equal to its parent's timestamp) rather than the actual wall-clock time — validation only rejects a *decrease*, not a stall: [5](#0-4) 
3. When the AA trigger for that MCI executes, `objValidationState.last_ball_timestamp` (and hence the `timestamp` oscript keyword) reflects this attacker-influenced, stalled value rather than real elapsed time, delaying satisfaction of the `unlock_ok` condition beyond what real-world elapsed time would justify: [2](#0-1) [1](#0-0) 
4. Conversely, an author could set the timestamp up to `now + max_seconds_into_the_future_to_accept` to accelerate satisfaction of a time-based condition slightly ahead of real elapsed time.
