### Title
`PATH` injection via fork `shipit.yml` `machine.environment` overrides safe `PATH` in `Command#unbundled_env`, enabling RCE on the deploy host - ([File: lib/shipit/command.rb])

### Summary
`DeploySpec#machine_env` returns the `machine.environment` hash from `shipit.yml` verbatim, `TaskCommands#env` merges it (and later `@task.env`) into the environment passed to `Command.new`, and `Command#unbundled_env` merges `@env` (the task/deploy env) **on top of** the safe hardcoded `PATH` it builds from `Shipit.shell_paths`. Because a `PATH` key is never stripped anywhere in this chain, an unprivileged fork PR author can set `machine.environment.PATH` in the fork branch's `shipit.yml`, which — on a repo configured with `provisioning_behavior=allow_all` — is read directly from the review-stack's checked-out (attacker-controlled) branch and used for every subsequent task, including the `deploy.override` steps.

### Finding Description
The broken binding: `Command#unbundled_env` is supposed to guarantee `PATH == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every spawned process, but the actual value is `BASE_ENV.merge('PATH' => safe_path).merge(@env.stringify_keys)['PATH']`, i.e., `@env['PATH']` if present, not the safe value: [1](#0-0) 

`@env` is the env passed into `Command.new` from `TaskCommands#env`, which merges `deploy_spec.machine_env` (attacker-controlled) followed by `@task.env`: [2](#0-1) 

`DeploySpec#machine_env` returns `config('machine','environment')` with no filtering of dangerous keys like `PATH`: [3](#0-2) 

`DeploySpec::FileSystem` is instantiated against `@task.working_directory` — the checked-out review-stack branch, i.e., the fork branch content — so `config` (and thus `machine_env`) is read from the PR author's own `shipit.yml`: [4](#0-3) 

For a repository with `provisioning_behavior_allow_all?`, opening a PR from an unprivileged fork automatically creates a review stack with no maintainer approval or label required: [5](#0-4) 

`Command#start` then spawns the process with `unbundled_env`, so any process invoked by a bare command name in `deploy.override` (or `dependencies`, `rollback`, `tasks`, etc.) resolves against the attacker-controlled `PATH`: [6](#0-5) 

Exploit flow: attacker forks the repo, adds `machine: {environment: {PATH: "/tmp/evil:$PATH"}}` and a malicious binary named after a command used in `deploy.override` (e.g. `bundle`, `rake`, `cap`) at `/tmp/evil/<name>` to the branch, opens a PR. Shipit auto-provisions the review stack (`allow_all`), and any task run for that stack (deploy, rollback, dependency install, custom task) spawns commands with the attacker's `PATH` prepended, causing the attacker's binary to execute on the Shipit deploy host.

No existing guard intercepts this: `machine_env` has no key-based sanitization/denylist, `DeploySpec::FileSystem#cacheable_config` merges `discover_machine_env.merge(machine_env)` without excluding `PATH`, and `Command#unbundled_env` merges `@env` last, unconditionally.

### Impact Explanation
This is a Critical Remote Code Execution vector: an attacker who can merely open a pull request against a repository with `provisioning_behavior=allow_all` and review stacks enabled can force execution of an arbitrary binary on the Shipit deploy host under the Shipit process's privileges, potentially exfiltrating `GITHUB_TOKEN`, other stacks' secrets, or pivoting to other tenants sharing the same deploy host. It is fully repeatable per PR/commit and does not require any Shipit credentials, session, or maintainer interaction.

### Likelihood Explanation
Preconditions are modest: the target repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_all` (the documented, commonly recommended setting per `docs/review_stacks.md`), which is a normal deployment configuration, not a misconfiguration outside intended use. The attacker cost is trivial — a fork, a `shipit.yml` edit, and opening a PR, all doable by any GitHub user with no special access. This makes the attack highly feasible and cheap to repeat against any `allow_all` repository.

### Recommendation
Strip or deny-list dangerous environment keys (at minimum `PATH`, `BUNDLE_*`, `RUBYOPT`, `LD_PRELOAD`, `GEM_HOME`, etc.) from `DeploySpec#machine_env`/`TaskCommands#env` before merging into `Command`. Additionally, `Command#unbundled_env` should compute `PATH` last and unconditionally from `Shipit.shell_paths`/`ENV['PATH']`, ignoring any `PATH` supplied via `@env`, so task-supplied environments can never override the trusted execution path.

### Proof of Concept
```ruby
# test/unit/command_test.rb (or new test file)
test "unbundled_env does not allow attacker-supplied PATH override" do
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command = Shipit::Command.new('echo', 'hi', chdir: Dir.tmpdir, env: { 'PATH' => '/tmp/evil' })

  # Broken binding demonstrated: attacker-controlled PATH wins instead of safe_path
  assert_equal '/tmp/evil', command.unbundled_env['PATH']
  refute_equal safe_path, command.unbundled_env['PATH']
end

# test/lib/shipit/task_commands_test.rb - full chain via fork shipit.yml
test "#env propagates fork-controlled PATH from machine.environment into deploy.override spawn env" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  deploy_spec = stub(machine_env: { 'PATH' => '/tmp/evil:$PATH' }, directory: nil)
  commands = Shipit::TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  env = commands.env
  assert_equal '/tmp/evil:$PATH', env['PATH']

  command = Shipit::Command.new('some-tool', chdir: Dir.tmpdir, env:)
  assert_equal '/tmp/evil:$PATH', command.unbundled_env['PATH']
end
```
Both assertions demonstrate the invariant ("the `deploy.override` step inherits no fork-controllable key such as `PATH`") is violated: the fork-supplied `PATH` reaches the environment hash passed to `PTY.spawn` via `Command#unbundled_env`.
