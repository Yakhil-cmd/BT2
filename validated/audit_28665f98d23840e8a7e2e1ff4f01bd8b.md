### Title
Cross-organization commit-status forgery via unscoped SHA lookup breaks the authenticated-organization ↔ deployed-repository binding, enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to validate a request against based on an **unverified field of the same request body** (`repository.owner.login` / `organization.login`), and `StatusHandler` then applies the status to any `Commit` row in the entire database whose `sha` matches — with no check that the commit belongs to a stack/repository owned by the organization whose secret actually validated the signature. In a multi-GitHub-App Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), this lets the operator/administrator of any one onboarded GitHub organization forge a `status` webhook, valid under *their own* organization's `webhook_secret`, that injects a fake `success` CI status onto a commit belonging to a **different, unrelated** organization's stack on the same shared Shipit instance — potentially satisfying `ci.require`/`deployable?` and enabling an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App configuration (and therefore which `webhook_secret`) to validate the incoming signature against using a value taken from the still-unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config (`app_id`, `installation_id`, and crucially its own `webhook_secret`) when Shipit is configured with multiple GitHub Apps, one per organization — a first-class, documented deployment mode: [3](#0-2) [4](#0-3) 

Once the signature is validated against *some* organization's secret, `StatusHandler#process` applies the status to any commit anywhere in the database that matches the SHA, with no verification that the commit's stack/repository belongs to the organization that validated the request: [5](#0-4) 

Contrast this with `PushHandler`/`Handler#stacks`, which do scope by `repository.full_name`: [6](#0-5) 

`StatusHandler` bypasses this scoping entirely and queries `Commit` globally, breaking the equality that should hold: `organization that authenticated the request == organization owning the repository/commit being written`. Any operator who legitimately controls one onboarded organization's GitHub App (and therefore its `webhook_secret`) can produce a validly-signed webhook whose payload's `sha`, `state`, and `context` fields are attacker-chosen, and have it applied to a commit belonging to any other tenant organization sharing the same Shipit instance.

The forged status directly feeds `deployable?` gating logic used to permit deploys and continuous delivery: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker with knowledge of a legitimately-issued `webhook_secret` for one organization onboarded to a shared Shipit instance (i.e., an unprivileged party with respect to every *other* onboarded organization) can forge a `status` webhook that fakes a `success` CI state for a required/blocking status context on a commit belonging to a completely different organization's stack. This can satisfy `ci.require`/`ci.blocking` and make `Commit#deployable?` return true for a commit that never actually passed CI, enabling that commit to be deployed via the API (`DeploysController#create` with `require_ci: true`) or auto-shipped via continuous delivery — an unauthorized deploy of code that was never validated, matching the Critical-severity "unauthorized deploy" criterion.

### Likelihood Explanation
This requires: (1) Shipit configured with multiple GitHub Apps (a documented, supported multi-tenant configuration), and (2) the attacker possessing a valid `webhook_secret` for at least one onboarded organization — which they would legitimately have if they administer that org's own GitHub App integration. No repository write access, `ApiClient` token, or session compromise on the *target* organization is required, satisfying the "unprivileged-attacker" constraint since the attacker never needed any credential belonging to the victim organization. Likelihood is moderate: it depends on multi-org deployment and requires knowledge of the SHA of a target commit (typically public in the target repo's commit history).

### Recommendation
Scope `StatusHandler` (and any other webhook handler that doesn't already do so) to the repository/organization that authenticated the request: after `verify_signature` selects the GitHub App/organization, pass that organization identity into the handler and restrict the `Commit` lookup to commits whose `stack.repository` belongs to that same organization (mirroring the scoping already done in `Handler#repository_name`/`#stacks`). Reject the webhook if the payload's `repository.owner.login` does not match the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured per `docs/setup.md` with two GitHub Apps, one for `org-attacker` and one for `org-victim`, each with its own `webhook_secret`.
2. Attacker legitimately administers `org-attacker`'s GitHub App and therefore knows `org-attacker`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to org-victim/critical-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"` [2](#0-1) , loads `org-attacker`'s config, and validates the signature successfully (attacker knows this secret).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` [5](#0-4) , finds the commit under `org-victim/critical-repo`, and creates a `success` status for it — with no check that this commit belongs to `org-attacker`.
7. The forged `success` status can satisfy `ci.require`, making the `org-victim` commit `deployable?`, and can be deployed through the normal deploy flow.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
