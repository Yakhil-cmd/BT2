### Title
Caller-supplied swap route executes arbitrary attacker-deployed contract code under the victim's signed authorization tree, draining wallet funds - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The Salt advisory (CWE-340) is a "predictable/attacker-controlled path executed under the victim's privileges" bug: the pre-flight script location is guessable, so attacker code runs as the victim. The XOXNO Lending analog is the router hop dispatch. Every strategy verb that routes a swap (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) forwards user-supplied `swap_xdr` bytes to the router, and `dispatch_hop` invokes whatever `hop.pool` address the payload names with no allowlist. An attacker who gets a victim to sign a poisoned route places arbitrary contract code on the call stack *inside the victim's signed authorization tree*, where it can call `token.transfer(victim, attacker, amount)` on any wallet token.

### Finding Description
`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-40` dispatches on `hop.venue` but the venue adapters call `env.invoke_contract(&ctx.hop.pool, ...)` — the pool address comes verbatim from the caller's payload (e.g., `contracts/swap-aggregator/src/venues/phoenix.rs:23-25`, `contracts/swap-aggregator/src/venues/comet.rs:30-34`). There is no registry of approved pools or tokens in the hop path.

On the controller side, `swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` authorizes exactly one input transfer to the configured router and then calls `router.execute_strategy`. The caller (`caller` in `swap_collateral`/`swap_debt`/etc.) signs the controller entrypoint with its sub-invocation tree. When the router calls the payload-named pool, and that pool invokes `token::Client::transfer(victim, attacker, amount)`, that transfer requires `victim.require_auth()` — which resolves *against the victim's own signed tree*, appearing as a child of the victim's root authorization. The protocol's measured-output checks (`dispatch_hop` lines 42-56, `verify_router_output` in swap.rs:75-84) are all satisfied because the rogue pool can still deliver a fair swap output; the theft is orthogonal to swap accounting.

This is proven end-to-end by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-72,194-227`: `UnlistedPoolRouter` invokes `route.hop_pool`, `RogueHopPool::swap` transfers `WALLET_BALANCE` from `alice` to `attacker`, and the recorded auth tree shows the stolen transfer nested under Alice's signed `swap_collateral` invocation. After execution Alice's wallet balance is 0 and the attacker holds the funds. The same exposure exists on the direct `Router::execute_strategy` path (documented in `docs/explanation/threat-model.md:154-165`).

### Impact Explanation
Theft of user funds. Any token held in the victim's wallet — unrelated to the lending position — can be transferred to the attacker inside a transaction that still passes all protocol output and risk gates. The swap settles "correctly" (fair output, positive measured delta, solvent final account), so neither `dispatch_hop`'s `ZeroOutput`/`InvalidAmount` checks nor the controller's `RouterOverspend`/`NoSwapOutput` checks bound the loss; the stolen amount is unlimited wallet balance, not routed input.

### Likelihood Explanation
Medium. Exploitation requires victim interaction (matching the CVE's `UI:R`): the attacker must deliver a malicious `routeXdr` — e.g., through a compromised/malicious quote source or phishing frontend — and the victim must sign the resulting authorization tree. An honest simulation *does* record the theft transfer as a child of the caller's auth entry, so a wallet that fully decodes the tree can surface it; wallets/clients that display only the root invocation cannot. Any unprivileged attacker can deploy the rogue pool contract and construct the payload; no privileged access, no oracle manipulation, and no privileged entrypoint is involved.

### Recommendation
Enforce a venue/pool allowlist at dispatch time: `dispatch_hop` (or `Program::validate` in `contracts/swap-aggregator/src/program.rs`) should reject hops whose `hop.pool` is not a governance-registered venue contract, analogous to how Blend migration requires an approved pool (INV-STRAT-03). Alternatively or additionally, the router should assert that the hop pool made no token transfers from `sender`/other foreign addresses — e.g., restrict authorization so only `transfer_from(router, pool, amount_in)` on `token_in` is authorized beneath the hop call. Short of contract changes, the documented mitigation (clients decode routes and reject auth trees with unexpected children) should be enforced in the official SDK builders.

### Proof of Concept
```text
1. Attacker deploys RogueHopPool { fn swap() { token.transfer(victim, attacker, amount) } }
   (see tests/.../rogue_hop_pool_transfer_joins_caller_auth_tree.rs:51-72).
2. Attacker serves victim a route whose SwapHop { venue: Phoenix-like, pool: rogue_pool,
   token_in: USDC, token_out: ETH } inside swap_collateral's swap_xdr.
3. Victim signs controller.swap_collateral(...). Controller authorizes one
   transfer(controller -> router) and calls router.execute_strategy
   (contracts/controller/src/strategies/swap.rs:34-38).
4. Router's dispatch_hop invokes hop.pool.swap() (venues/mod.rs:34-40;
   phoenix.rs:23-25). The rogue pool's token.transfer(victim, attacker, N)
   resolves victim.require_auth() against the victim's signed tree and executes.
5. Router still pays fair ETH output; dispatch_hop's measured-delta checks pass
   (mod.rs:42-56), verify_router_output passes (swap.rs:75-84), victim's account
   is solvent — and the victim's unrelated wallet token is drained.
```

Note on scope: this exposure is described in `docs/explanation/threat-model.md:154-165` as a known hazard pushed to client-side route verification. It is reported here because the in-scope contract code contains no allowlist enforcement and the harness test demonstrates live theft of user funds through a reachable unprivileged path — whether the client-mitigation design makes this accepted risk versus a contract bug is a judgment call for the protocol.
