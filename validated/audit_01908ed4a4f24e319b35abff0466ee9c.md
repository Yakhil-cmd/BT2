### Title
Flash-loan-style balance manipulation via atomic AA call chains — ([File: aa_composer.js])

### Summary
An AA (Autonomous Agent) can read the *current, live* balance of any other AA address (`balance[address][asset]`) and the *current* state variable of any other AA (`var[address][name]`) while evaluating its response formulas. Because a single triggering unit can atomically chain through multiple dependent AAs (deposit → borrow/price-check → repay/withdraw, all within `handleTrigger`/`handleSecondaryTriggers`), an attacker can temporarily inflate an AA's on-chain balance (functionally a "flash loan") within the same atomic chain that a downstream AA uses to compute price, collateral ratio, or exchange rate, and then reverse it — all within one irreversible unit sequence, exactly mirroring the Lava flash-loan exploit pattern.

### Finding Description
`handleTrigger` in `aa_composer.js` processes a primary trigger and, when the AA's response sends funds to another AA address, automatically and atomically invokes `handleSecondaryTriggers`, which recursively calls `handleTrigger` for each downstream AA within the *same* database transaction/batch (`conn.query("BEGIN"...)` in `handlePrimaryAATrigger`, committed only once at the very end): [1](#0-0) 

Within formula evaluation, any AA can read another AA's *live* balance or state var via the `balance`/`var` operators, which query `objValidationState.assocBalances` (updated in real time as the chain executes) or fall back to the DB: [2](#0-1) 

This pattern is explicitly used in shipped/example AAs, e.g. `fundraising_proxy.oscript`, which computes a "missing amount" / completion threshold directly from `balance[$destination_aa][base]` of a different, live AA: [3](#0-2) 

And `updateFinalAABalances`/`updateInitialAABalances` show that `assocBalances` is mutated incrementally as each message/response is processed in the chain, before the whole unit is committed: [4](#0-3) [5](#0-4) 

The "chain of AAs" test confirms that a primary trigger can cascade through multiple AAs synchronously, with each AA's `balance[]`/`var[]` reads reflecting the intermediate (not yet stabilized) state of the chain: [6](#0-5) 

Because none of this state is finalized until the very end of the primary trigger's processing (single commit), any AA-based lending/AMM/pricing protocol built on ocore that uses `balance[other_aa][asset]` or `var[other_aa][name]` as an oracle/pricing input for collateral valuation, exchange rate, or debt calculations is exposed to the same class of attack that hit Lava: an attacker crafts one unit whose chain of AA calls (1) inflates a balance/state read by a downstream pricing AA, (2) borrows/mints/withdraws against the inflated valuation, and (3) unwinds — with the entire sequence succeeding or failing atomically as a single unit, with no cross-block time delay to allow the price to be independently verified.

### Impact Explanation
Any AA-based lending, margin, or AMM-style application deployed on ocore that derives price/collateral from another AA's live `balance[]`/`var[]` (a supported and documented oscript feature, as demonstrated by the shipped `fundraising_proxy.oscript` sample) can have its collateral/price computation manipulated within a single atomic trigger chain, enabling unauthorized draining of AA funds — directly analogous to the $340k Lava flash-loan loss. This is a fund-loss / AA fund-drain class of impact.

### Likelihood Explanation
Any unprivileged unit poster can trigger this by simply sending one unit with a payment to the target primary AA; the entire attack sequence (deposit, secondary AA calls, price read, withdraw) executes automatically within `handleSecondaryTriggers`/`handleTrigger` without further permission checks, and is fully reachable from a single posted trigger unit. The vulnerability is not in ocore's core validation logic itself, but the AA framework provides no atomicity-aware safeguard (e.g., time-weighted balance, reentrancy guard across chained AA calls) — the risk depends on individual AA authors correctly avoiding use of live cross-AA `balance[]`/`var[]` reads as unguarded price oracles, which the shipped sample code does not caution against.

### Recommendation
- Document prominently (and consider tooling/linting warnings) that `balance[address][asset]` and `var[address][name]` for addresses other than `this_address` reflect *live, mutable, intra-chain* state and must not be used as unguarded price/collateral oracles.
- Encourage/require AA design patterns that use externally-attested `data_feed` oracles (from independent, out-of-band posted units) for pricing rather than another AA's live balance for financial-sensitive computations.
- Consider adding an optional "read-only, pre-trigger" balance snapshot primitive that AA authors can rely on for price computations, distinct from the mutable in-chain `balance[]`.

### Proof of Concept
1. Deploy `AA_Lender`, a lending AA whose collateral value / exchange rate calculation reads `balance[AA_Pool][asset]` (analogous to `fundraising_proxy.oscript`'s `balance[$destination_aa][base]` pattern) to determine how much can be borrowed.
2. Deploy `AA_Attacker`-controlled trigger unit that:
   a. Sends a large payment to `AA_Pool` (temporarily inflating `AA_Pool`'s balance within the atomic chain, per `updateInitialAABalances`/`updateFinalAABalances` in `aa_composer.js:474-586`).
   b. Chains (via secondary trigger, `aa_composer.js:1702-1741`) into `AA_Lender`, which reads the now-inflated `balance[AA_Pool][asset]` and computes an inflated borrowing/withdrawal limit for the attacker.
   c. `AA_Lender` sends out the over-valued amount to the attacker in the same atomic unit chain.
   d. A final secondary trigger withdraws/reclaims the initial payment from `AA_Pool` back to the attacker, unwinding step (a) — all within the single committed unit/trigger chain, mirroring the flash-loan pattern from the Lava incident.
