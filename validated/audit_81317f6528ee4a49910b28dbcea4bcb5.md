Confirmed: `validateDivisiblePrivatePayment` in `divisible_asset.js` calls `validation.validatePayment` on `payload.inputs` that comes directly from an attacker-supplied private-payment element, **without** ever running the array-element sanity gate (`m.payload.inputs.every(i => isNonemptyObject(i) && ...)`) that exists only in the full-unit `validate()` path [1](#0-0) . That gate is what normally guarantees `payload.inputs[0]` is a non-empty object before `validatePayment` dereferences `.type` on it [2](#0-1) . Private payments enter through `validateDivisiblePrivatePayment` → `validation.initPrivatePaymentValidationState` → `validation.validatePayment`, bypassing that unit-level message gate entirely [3](#0-2) [4](#0-3) .

### Title
Unvalidated private-payment input elements cause NULL/undefined-property crash in `validatePayment` - (File: divisible_asset.js / validation.js)

### Summary
`validateDivisiblePrivatePayment()` only checks that `payload.inputs` is a non-empty array (`ValidationUtils.isNonemptyArray(payload.inputs)`), then forwards the payload straight to `validation.validatePayment()`, which immediately does `payload.inputs[0].type === "issue"`. Unlike the full-unit validation path in `validation.js`, which sanitizes every message's inputs with `isNonemptyObject(i)` before any input is used, the private-payment path has no equivalent element-level check. A malicious private-payment counterparty can supply `payload.inputs: [null]` (or any primitive) to make `payload.inputs[0].type` throw a `TypeError`, analogous to how HEVC's mishandled duplicate-first-slice detection let a NULL/absent first slice be dereferenced (CVE-2019-11338).

### Finding Description
- The generic unit validator normalizes and gates every payment message's inputs before they reach any code that dereferences fields on `input`: [1](#0-0) 
- `validatePayment()` (used for both public and private payments) accesses `payload.inputs[0].type` unconditionally as soon as an asset is resolved: [2](#0-1) 
- For private divisible-asset payments, the entry point is `validateDivisiblePrivatePayment()`, which validates only array-level shape (`isStringOfLength(payload.asset, ...)`, `isNonemptyArray(payload.inputs)`) — never that each element of `payload.inputs` is a non-empty object: [3](#0-2) 
- It then calls `validation.validatePayment` directly with the raw `payload`, so `payload.inputs[0]` is never sanitized: [4](#0-3) 
- The wider "no inputs"/"no outputs" gate for private payments in `private_payment.js` also only checks array-level presence and does not validate that each element is an object: [5](#0-4) 

If `payload.inputs[0]` is `null`, `payload.inputs[0].type` throws inside a nested asynchronous callback chain (`storage.loadAssetWithListOfAttestedAuthors` → `validatePayment` callback), which is not wrapped in a try/catch here, producing an unhandled exception that can crash the node process handling the private payment — the same class of "improper handling of a required leading element, leading to a dereference of an invalid/absent object" that the HEVC CVE describes for duplicate first slices.

### Impact Explanation
An unhandled exception thrown inside `validatePayment`'s asynchronous flow while processing a received private payment chain will propagate as an uncaught exception in that async context, crashing the receiving full node's process. Because private payments are routinely relayed and validated by counterparties' own nodes/wallets when receiving indivisible/divisible private assets, a malicious private-payment counterparty (a normal, unprivileged actor in an ordinary private transfer) can remotely crash the recipient's node, denying that node's ability to validate/confirm any further units until restarted — a node-disagreement/DoS impact within the private-payment/asset-transfer pipeline.

### Likelihood Explanation
Likelihood is high for any node/wallet that accepts private asset payments: the attacker only needs to construct a `payload.inputs` array whose first element is `null` (or a non-object primitive) and send it as a private-payment element to a counterparty. No special privileges, witness/OP status, or existing balance are required — this is reachable purely as the receiving side of a private payment.

### Recommendation
Add an explicit per-element object check for `payload.inputs` (and `payload.outputs`) at the very start of `validateDivisiblePrivatePayment()` / `validateAndSavePrivatePaymentChain()` (and the analogous indivisible-asset path), mirroring the `isNonemptyObject(i)` check already performed for full units in `validation.js` lines 245–255, before any field of `payload.inputs[0]` is dereferenced in `validatePayment()`. Alternatively, add a defensive `isNonemptyObject` check directly in `validatePayment()` before accessing `payload.inputs[0].type`.

### Proof of Concept
1. Attacker crafts a private-payment message chain (as sent via `private_payment.js`'s `validateAndSavePrivatePaymentChain`) for a divisible private asset where the head element's `payload.inputs` is `[null, {type:"transfer", unit:"...", message_index:0, output_index:0}]` and `payload.outputs` is a valid non-empty array.
2. Attacker sends this private payment to a victim (e.g., via wallet chat as normally done for private asset transfers).
3. Victim's node calls `private_payment.validateAndSavePrivatePaymentChain` → `divisible_asset.validateAndSaveDivisiblePrivatePayment` → `validateDivisiblePrivatePayment`, which only checks `isNonemptyArray(payload.inputs)` and forwards to `validation.validatePayment`.
4. `validation.validatePayment` executes `var bIssue = (payload.inputs[0].type === "issue");` on `payload.inputs[0] === null`, throwing `TypeError: Cannot read properties of null (reading 'type')` inside the async callback chain, crashing the victim's node process.
