### Title
Unauthenticated webhook forgery of commit statuses drives Shipit's merge queue to auto-merge unreviewed pull requests - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The QuailFinance report describes a binding failure where a privileged actor's action (`rotateLiquidity`) permanently gates a downstream state transition, with no fallback validation. The structurally equivalent binding in Shipit is: *the signature that is supposed to authenticate a webhook* versus *the payload fields (`sha`, `state`, `context`) that the engine actually acts on*. `WebhooksController#verify_signature` computes `verified = github_app.verify_webhook_signature(...)` [1](#0-0)  but `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [2](#0-1) .

### Finding Description
Every secrets template in this repo ships with `webhook_secret` commented out/`nil` by default (`config/secrets.development.shopify.yml`, `template.rb`, `test/dummy/config/secrets_double_github_app.yml`) and the setup docs describe it as merely "optional" [3](#0-2) . When `webhook_secret` is unset for an organization, the `X-Hub-Signature` header is never actually checked — the equality "signature verified == request authentic" collapses to "always true," so the payload fields consumed downstream are never covered by any cryptographic guarantee.

The `status` webhook event is dispatched straight into `StatusHandler#process`, which takes attacker-suppliable `sha`, `state`, `context`, `target_url` fields from the JSON body and persists them as a `Status` on any matching `Commit` row: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . These locally-stored `Status` records are exactly what `MergeRequest#all_status_checks_passed?` and `#any_status_checks_failed?` consult via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` [5](#0-4)  — there is no independent re-fetch of CI status from GitHub's API at merge time.

`ProcessMergeRequestsJob` walks pending merge requests, calls `refresh!` (which re-fetches only the PR object, not statuses), then gates purely on the locally-cached `all_status_checks_passed?` before calling `merge_request.merge!` [6](#0-5) . `MergeRequest#merge!` performs a real, credentialed write to GitHub: `stack.github_api.merge_pull_request(stack.github_repo_name, number, merge_message, sha: head.sha, ...)` [7](#0-6) , using the app's own installation token.

### Impact Explanation
An unauthenticated attacker who knows (or guesses) a repository name already tracked by Shipit can POST a forged `status` (or `check_suite`/`check_run`) event to `/webhooks` claiming the required CI contexts succeeded for the head SHA of an arbitrary open, queued pull request. Because signature verification is a no-op for any organization without a configured `webhook_secret`, this forged status is accepted and stored. The background merge-queue job then treats the PR as green and calls GitHub's merge API using Shipit's real, privileged `GITHUB_TOKEN`, producing an **unauthorized merge** into the tracked repository — satisfying the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This does not require compromising `webhook_secret`, an `ApiClient` token, a GitHub App private key, or any session — it requires only that the target Shipit deployment has not configured a per-organization `webhook_secret`, which is the state produced by following the shipped defaults/templates (`webhook_secret: # nil` appears in every example secrets file examined). The attacker additionally needs an open PR already registered in the stack's merge queue (`pending`), which is a normal, low-privilege state reachable by anyone who can open a PR against the tracked repo.

### Recommendation
- Require `webhook_secret` to be present and reject requests when it is missing, rather than defaulting to `verified = true`.
- At minimum, re-verify commit statuses/check-run results against GitHub's API immediately before `MergeRequest#merge!` rather than trusting webhook-cached `Status` rows exclusively.
- Consider signing/validating `check_suite`/`status` payload sha against the actual PR head fetched via the API before persisting.

### Proof of Concept
1. Target a Shipit instance whose organization config has no `webhook_secret` set (the documented/default configuration).
2. Attacker opens (or has) a PR against the tracked repo that has been queued for merge (`merge_status: pending`) but whose CI has not actually passed.
3. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: status
   Content-Type: application/json

   {"sha": "<PR head sha>", "state": "success", "context": "<required-ci-context>",
    "repository": {"owner": {"login": "<org>"}, "full_name": "<org>/<repo>"}}
   ```
   No `X-Hub-Signature` is required to pass verification since `verify_webhook_signature` returns `true` unconditionally for this org.
4. `StatusHandler` persists a `success` `Status` for that commit.
5. `ProcessMergeRequestsJob` (running on its normal schedule) sees `all_status_checks_passed?` return true and calls `merge_request.merge!`, causing Shipit to call `github_api.merge_pull_request` and merge the PR into the base branch using the app's real GitHub credentials — despite CI never actually passing.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
