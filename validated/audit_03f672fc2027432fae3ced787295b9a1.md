### Title
Hookify PreToolUse/PostToolUse hooks fail-open on import/parse errors, allowing dangerous Bash/Edit/Write/MultiEdit operations to bypass deny rules - (File: plugins/hookify/hooks/posttooluse.py, plugins/hookify/hooks/pretooluse.py)

### Summary
Both `pretooluse.py` and `posttooluse.py` explicitly catch `ImportError` and any generic `Exception` during hook execution, print a `systemMessage` describing the error, and then unconditionally `sys.exit(0)` without ever emitting a deny/block decision. This is fail-open-by-design behavior: any condition that triggers an import failure or an unhandled exception in `load_rules`/`RuleEngine.evaluate_rules` silently converts what should be a blocking rule evaluation into a no-op allow.

If `from hookify.core.config_loader import load_rules` or `from hookify.core.rule_engine import RuleEngine` raises `ImportError` (e.g., because `CLAUDE_PLUGIN_ROOT` is unset, the plugin directory structure differs, or `sys.path` manipulation fails to locate the module), the script prints a JSON `systemMessage` and exits 0 with no rule evaluation ever happening — meaning no deny decision can possibly be produced. Similarly, inside `main()`, any exception raised by `json.load(sys.stdin)` (malformed input JSON), `load_rules(event=event)` (a malformed or unreadable `.claude/hookify.*.local.md` rule file causing a parse error), or `engine.evaluate_rules(rules, input_data)` is caught generically, converted to a `systemMessage`, and the process still exits 0 — again bypassing any potential deny outcome for that specific tool invocation.

Because `event` classification (`bash` vs `file`) and rule loading both occur inside the single `try` block, a crafted rule file or malformed hook JSON that triggers a parsing exception anywhere in `load_rules`/`evaluate_rules` degrades the entire enforcement path to a benign informational message rather than a blocking response, for `Bash`, `Edit`, `Write`, and `MultiEdit` tool calls alike.

This satisfies the "fail open" pattern: instead of denying by default when the hook cannot confidently evaluate rules, it allows by default and merely reports the error as a system message.

### Impact Explanation
An attacker who can influence the `.claude/hookify.*.local.md` rule content, or trigger any transient error condition in the hook module resolution/import path or JSON parsing, causes the hook to silently allow the underlying `Bash`/`Edit`/`Write`/`MultiEdit` operation instead of enforcing configured deny rules. This maps to "Unauthorized local command execution that bypasses Claude Code approval or deny controls," since the invariant that "every dangerous tool must map to the intended rule set and be enforced" is broken whenever an exception path is hit.

### Likelihood Explanation
The fail-open behavior is deterministic and requires no special privilege — it triggers on any exception, including ordinary misconfiguration, malformed rule files, or environment issues (e.g., `CLAUDE_PLUGIN_ROOT` not set as expected in some execution contexts). This makes it a broad, reliably reproducible bypass rather than a narrow edge case: any state that produces an exception in the hook chain (which is easy to induce by crafting rule files or hook JSON) results in a full pass-through rather than a safe default-deny.

### Recommendation
Change the fail-safe posture: on `ImportError` or any exception during rule loading/evaluation for dangerous tool events (`Bash`, `Edit`, `Write`, `MultiEdit`), the hook should emit an explicit deny/block decision (e.g., `{"decision": "block", "systemMessage": ...}` or the equivalent Claude Code hook schema field) rather than allowing silently, or at minimum surface the failure through a mechanism that halts the action pending human review, instead of `sys.exit(0)` with only an informational message.

### Proof of Concept
1. Unit test `test_posttooluse_import_error_fails_open`: monkeypatch `sys.modules` to make `import hookify.core.config_loader` raise `ImportError`, invoke `posttooluse.main()` with stdin JSON `{"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}}`, capture stdout and exit code. Assert exit code is `0` and stdout JSON has no deny/block field — demonstrating the operation is allowed despite the import failure.
2. Unit test `test_posttooluse_rule_parse_error_fails_open`: create a malformed `.claude/hookify.bash.local.md` that raises an exception in `load_rules`, invoke `main()` with a `Bash` tool call that should have been denied by a valid rule, and assert the resulting JSON contains only `systemMessage` (no block/deny) and process exits `0`.
3. Invariant assertion for both tests: `assert "decision" not in result or result.get("decision") != "block"` on the error path, proving that errors silently downgrade a deny to an allow, in violation of the required invariant.

```python
def main():
    """Main entry point for PostToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type based on tool
        tool_name = input_data.get('tool_name', '')
        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
```
