This confirms the base `Handler` class has no cross-validation between `payload.dig('repository', ...)` and `params.organization.login` — each handler independently reads whatever fields it needs from the same raw payload without re-verifying them against the field that `verify_signature` actually checked.

## Title
Membership webhook team creation trusts `organization.login` never validated against the org whose secret authenticated the request - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb](app/models/shipit/webhooks/handlers/membership_handler.rb))

## Summary
`WebhooksController#verify_signature` authenticates a webhook using `repository_owner`, which is computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  — preferring the `repository` object when present. `MembershipHandler#find_or_create_team!`, however, sets `team.organization = params.organization.login`, a field never checked against `repository_owner` [2](#0-1) . An attacker who legitimately administers an org onboarded into this Shipit instance (and thus knows their own org's `webhook_secret`) can send a payload with `repository.owner.login = 'attacker-org'` (satisfying signature verification against `attacker-org`'s secret) while `organization.login = 'victim-org'`, causing a `Team` row bound to `victim-org` to be created/persisted from data never authenticated by `victim-org`.

## Finding Description
The broken binding: `verified_org (repository_owner used in Shipit.github(organization: repository_owner).verify_webhook_signature)` should equal `team.organization` written by `MembershipHandler`. In this code, `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , but `team.organization = params.organization.login` [2](#0-1) . These are two independent reads of attacker-supplied JSON; nothing in `MembershipHandler`, the base `Handler` class [3](#0-2) , or `ExplicitParameters` schema cross-checks them.

Real GitHub-delivered `membership` events don't include a top-level `repository` key (they're org-scoped), so in normal operation `repository_owner` falls back to `organization.login` and the two values naturally match. The attack requires the attacker to POST directly to `/webhooks` (which accepts arbitrary raw JSON per `WebhooksController#create` [4](#0-3) ) with a synthetic `repository.owner.login` field that real GitHub would never include for this event type, forcing `repository_owner` to resolve to the attacker's own org while `organization.login` claims to be the victim org.

`Team.find_or_create_by!(github_id: params.team.id)` then creates a brand-new row (since the attacker picks an unused `team.id`) with `organization: 'victim-org'` and attacker-chosen `slug`/`name` [2](#0-1) . Later, `Shipit.github_teams` resolves configured team handles via `Team.find_or_create_by_handle`, which does `find_by(organization:, slug:) || fetch_and_create_from_github(...)` [5](#0-4) . Because `find_by` matches on the plain string columns, it returns the attacker-forged row instead of ever hitting the GitHub API to fetch/verify the real team, poisoning the authorization set used to gate access (e.g., in `bin/rake teams:fetch` / `lib/tasks/teams.rake` [6](#0-5) ).

## Impact Explanation
The attacker plants a row in the shared `teams` table (unique index on `organization, slug` [7](#0-6) ) that will later be silently adopted as the authoritative record for `victim-org/slug` once an operator configures `Shipit.github_teams` to include that handle, instead of that lookup ever calling GitHub's API to fetch/verify the real team. This is a cross-tenant write: a payload authenticated only by `attacker-org`'s webhook secret mutates state keyed to `victim-org`, matching the "escalation into `Shipit.github_teams` authorization" / cross-repository-owner mutation category.

## Likelihood Explanation
Exploitation requires: (1) the attacker administers (or is a legitimate webhook sender for) at least one org already onboarded into this Shipit instance with a non-blank `webhook_secret` they legitimately know, (2) the target `team.id` (GitHub's numeric team ID, guessable/enumerable) is not already present as a `Team` row, and (3) the operator later configures or already has `victim-org/<slug>` in `Shipit.github_teams`. Given these preconditions the attack is a single crafted HTTP POST, fully repeatable for any org the attacker is onboarded for, against any team-id/slug/org string of the attacker's choosing.

## Recommendation
In `MembershipHandler#find_or_create_team!`, validate that `params.organization.login` matches the authenticated `repository_owner`/org that verified the webhook (e.g., pass the verified organization into the handler and assert equality before writing `team.organization`), rather than trusting a second, independently-read field from the same unauthenticated JSON body. More generally, `WebhooksController#verify_signature` should derive `repository_owner` consistently per event type and handlers should reuse that verified value rather than re-reading `organization.login`/`repository.owner.login` from `payload`.
