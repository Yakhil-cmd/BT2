### Title
Blind SSRF via unvalidated arbstore URL in arbiter contract flow - (File: `arbiter_contract.js`, `arbiters.js`)

### Summary
The arbiter-contract feature lets a wallet's counterparty nominate/accept an `arbiter_address` for a payment dispute-resolution flow. When the wallet later needs to talk to the arbiter's "ArbStore" service, it asks its own hub for the URL registered for that `arbiter_address` (`hub/get_arbstore_url`) and then performs an outbound HTTP(S) request directly to that URL with no scheme/host validation — mirroring the exact bug class in the reported advisory (a URL obtained from an untrusted party is trusted at "invocation time" without re-validating it as an internal/loopback/metadata address).

### Finding Description
Any party who can be nominated as an "arbiter" for a contract (an ordinary, unprivileged counterparty in a private payment/contract negotiation — same trust tier as a "private-payment counterparty") registers an arbitrary URL as their ArbStore endpoint with the hub. The victim wallet, upon needing to contact the arbiter, fetches this attacker-controlled string and issues a raw HTTP(S) request to it:

- `arbiters.js` `requestInfoFromArbStore(url, cb)` only checks `validationUtils.isNonemptyString(url)` before calling `http.get(url, ...)`: [1](#0-0) [2](#0-1) 

- `arbiter_contract.js` `httpRequest(host, path, data, cb)` builds request options straight from `url.parse(host)` with no scheme or host allow-list check, and is invoked from `openDispute`, `appeal`, and `getAppealFee` with the URL returned by `device.requestFromHub("hub/get_arbstore_url", ...)`: [3](#0-2) [4](#0-3) [5](#0-4) 

There is no code path that restricts the returned `url` to `https://`, rejects loopback/link-local/private-network hosts, or otherwise re-validates it the way `register_manual`/`call_tool` are supposed to in the advisory's fixed version. Because `arbiter_address` is a value supplied/negotiated during contract creation (`createAndSend`, `store`, `respond` in `arbiter_contract.js`), and any device can register itself as an "arbiter" whose hub-served URL is whatever it wants, a malicious counterparty can point the victim's wallet at `http://169.254.169.254`, `http://localhost:<port>`, or any internal address reachable from the victim's host.

### Impact Explanation
When the victim's wallet opens a dispute, files an appeal, or queries the appeal fee (`openDispute`, `appeal`, `getAppealFee`, or `arbiters.getInfo`/`getArbstoreInfo`), it sends an HTTP POST/GET containing contract metadata (encrypted contract package, pairing codes, contact info, asset/amount) to the attacker-chosen destination. This is a blind SSRF: it can be used to probe/reach internal-only services, and because the "arbstore" response is parsed as JSON and partially trusted (`info.address`, `info.cut`, `device_pub_key`), a response spoofed from an internal service could also feed malformed/attacker-influenced data back into wallet state (`wallet_arbiters`, in-memory `arbStoreInfos` cache). This matches the CWE-918 class in the advisory but is scoped to information-disclosure/probing rather than fund loss, so severity is capped at the same "Medium" tier as the original report.

### Likelihood Explanation
Reachable by an unprivileged remote counterparty simply by being proposed/accepted as `arbiter_address` in a normal arbiter-contract negotiation and registering a malicious ArbStore URL with a hub — no compromise of the hub, node, or network layer is required, and no special privilege is needed beyond acting as a normal contract participant.

### Recommendation
Introduce a single `ensure_secure_arbstore_url(url)`-style check (analogous to the advisory's fix) that: (1) requires `https://` scheme, and (2) resolves/validates the hostname is not loopback, link-local (169.254.0.0/16), or private-range, applied uniformly wherever an arbstore URL is used to make an outbound request — `arbiters.js` (`requestInfoFromArbStore`, `getInfo`, `getArbstoreInfo`) and `arbiter_contract.js` (`httpRequest`, and its callers `openDispute`, `appeal`, `getAppealFee`, `getArbstoreAddresses`). The check must be re-applied at each call site immediately before the request, not only once at registration time, to avoid the same discovery/invocation trust-boundary gap described in the advisory.

### Proof of Concept
1. Attacker device registers itself with its hub (`hub/get_arbstore_url`) returning `http://169.254.169.254` (or `http://127.0.0.1:6379`) as its arbstore URL for `arbiter_address = A`.
2. Attacker proposes/accepts a normal arbiter contract with the victim, naming `A` as `arbiter_address` (`createAndSend`/`respond` in `arbiter_contract.js`).
3. Victim later calls `arbiters.getInfo(A, cb)` or triggers `openDispute`/`appeal`/`getAppealFee` on the contract.
4. The victim's node resolves the URL via `device.requestFromHub("hub/get_arbstore_url", A, ...)` and issues `http.get`/`http.request` directly to the attacker-chosen internal address [1](#0-0) [6](#0-5) , exposing internal-network reachability/metadata to the attacker's chosen endpoint and returning whatever that internal service serves back into the wallet's dispute/appeal flow.

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
