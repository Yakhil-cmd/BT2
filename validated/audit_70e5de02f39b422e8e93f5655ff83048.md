### Title
Unscoped `Commit.where(sha:)` lookup lets a status webhook from one repository overwrite `buildkite/deploy` state on a same-SHA commit belonging to a different stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by `sha`, with no scoping to the repository/stack that the webhook was verified for. Because commit SHAs are shared across forks, mirrors, or multiple Shipit stacks pointed at overlapping history, an attacker who controls a repository that shares a commit with a victim's stack can send a validly-signed webhook from their own repo and have Shipit write a `Status` record onto the victim's stack for that shared commit, flipping `required?`/`blocking?`/`deployable?` state.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == { commits belonging to the webhook's originating repository }`, but in reality `Commit.where(sha: params.sha)` returns every `Commit` row across every `Stack` in the installation that happens to have that SHA [1](#0-0) .

`Shipit::WebhooksController#verify_signature` only authenticates that the payload was signed with the webhook secret configured for the organization named in the payload's own `repository.owner.login` (`Shipit.github(organization: repository_owner)`); it never checks which `Stack`/`Commit` rows the handler will subsequently touch [2](#0-1) . So any attacker who legitimately owns a repository/organization wired into Shipit (their own fork, mirror, or second stack) can produce a correctly-signed `status` event.

`StatusHandler#process` then iterates every `Commit` with that SHA and calls `commit.create_status_from_github!(params)` [1](#0-0) , which persists the status against `commit.stack_id` -- the *found* commit's own stack, not the stack that authenticated the webhook [3](#0-2) [4](#0-3) .

Exploit flow:
1. Attacker registers/owns a repository in Shipit (e.g. a fork of the victim's repo, or any repo sharing ancestor commits with the victim) and gets a `Stack` created for it, which ingests a `Commit` row for the shared SHA.
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, and body `{ sha: <shared_sha>, context: "buildkite/deploy", state: "failure", repository: { owner: { login: <attacker_org> } } }`.
3. `verify_signature` passes because it validates against the attacker's own org's secret [5](#0-4) .
4. `StatusHandler#process` finds both the attacker's own `Commit` and the victim's `Commit` sharing that SHA, and writes a `failure` status for `buildkite/deploy` onto the victim's stack via `replicate_from_github!(stack_id, ...)` [3](#0-2) .
5. If `buildkite/deploy` is in the victim stack's `ci.require`, `Status::Common#required?`/`#blocking?` now flags the victim's commit as blocking [6](#0-5) , and `Commit#deployable?` flips to `false` for the victim [7](#0-6) .

None of the existing guards prevent this: `verify_signature` binds to the payload's *claimed* org, not the *target* commit's stack; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/`context`, not ownership; there is no `require_permission!`/`stacks` scope check in this webhook path since it is intentionally unauthenticated (server-to-server GitHub webhook).

### Impact Explanation
A `failure` status write lands on a repository/stack that never authenticated the request that produced it -- a cross-tenant record mutation matching the Critical category "a payload for one repository mutating another's stack, commit". This can flip `deployable?`/merge eligibility for the victim's commit, blocking legitimate deploys or (depending on which context is spoofed) unblocking one by overwriting it with a `success` state. The blast radius is any stack/commit sharing a SHA with an attacker-controlled repository, which is realistic whenever forks, mirrors, or multiple environment-specific stacks track overlapping git history.

### Likelihood Explanation
Preconditions: the attacker needs a repository wired to Shipit (which, per the threat model, they can arrange as an unprivileged GitHub user by owning a repo/fork and having Shipit ingest it), and a SHA that is shared with the victim's stack (trivially true for shared ancestor commits between a fork and upstream, or between two stacks tracking the same underlying repository). No Shipit session, API token, or GitHub secret is required beyond the ability to have their own repository's webhook delivered and signed normally by GitHub. This is fully repeatable against any shared-history commit.

### Recommendation
Scope the lookup in `StatusHandler#process` (and the analogous `CheckRunHandler`, if present) to the repository/stack that the webhook was verified for, e.g. resolve the `Stack`/`Repository` from `params.dig('repository', ...)` (matching the same identity `verify_signature` authenticated) and filter `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` instead of matching on `sha` alone.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not write to a stack it did not authenticate" do
  shared_sha = "a" * 40

  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(ignore_ci: false)
  # victim requires buildkite/deploy
  victim_stack.cached_deploy_spec.update!(config: { ci: { require: ["buildkite/deploy"] } })
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")

  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:rails), environment: "attacker")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker owned fork commit")

  before_state = victim_commit.reload.deployable?
  assert before_state, "victim commit expected deployable before attack"

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: "failure", context: "buildkite/deploy"
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  after_state = victim_commit.reload.deployable?

  # Binding under test: victim_commit.deployable? before == after (should hold; currently fails)
  refute_equal before_state, after_state, "attacker-signed status for a different stack flipped the victim's deployable? state"
end
```
This demonstrates that a status event resolvable only via the attacker's own (unrelated) stack still mutates the victim stack's commit state, confirming the cross-repository write.
