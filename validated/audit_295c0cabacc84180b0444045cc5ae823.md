### Title
Improper invalidation of `outputs.is_spent` when a spending unit is propagated to `final-bad` permanently freezes the spent output - (File: main_chain.js)

### Summary
CVE-2018-12207 is a bug class about a hypervisor failing to properly invalidate a stale page-table entry after an update, letting a CPU act on the stale entry and causing host DoS. The reachable analog in ocore is in `main_chain.js`'s stabilization logic: when a unit that spent a stable output is later marked `final-bad` (either directly or via `propagateFinalBad`), only the `inputs.is_unique` marker and `sequence` field are invalidated — the corresponding `outputs.is_spent=1` flag set at write time is never rolled back to `0`. The output is left in a stale "spent" state forever, even though the spend that set it was invalidated. This causes the legitimate owner to permanently lose the ability to spend their own confirmed, un-double-spent funds — a fund-freezing analog to the improper-invalidation bug class.

### Finding Description
When a unit is written, for every `transfer` input it marks the referenced output as spent unconditionally: [1](#0-0) 

This `is_spent=1` update happens regardless of whether the spending unit will ultimately end up `good` or `final-bad` — `is_unique` is the only value conditioned on `objValidationState.sequence`: [2](#0-1) 

At stabilization time, `markMcIndexStable` in `main_chain.js` determines final sequencing. For units that lose the double-spend race (`findStableConflictingUnits`), it sets `sequence='final-bad'` and clears `inputs.is_unique`, but does **not** touch `outputs.is_spent` for the outputs that these final-bad units spent: [3](#0-2) 

The same omission exists in `propagateFinalBad`, which recursively marks all descendant spenders of a final-bad unit as `final-bad` and clears their `inputs.is_unique`, again without ever resetting `is_spent` on the outputs those descendants consumed: [4](#0-3) 

The only code path in the entire codebase that actually resets `is_spent` back to `0` for a spent output is `generateQueriesToUnspendOutputsSpentInArchivedUnit`, called from `generateQueriesToVoidJoint`/`generateQueriesToRemoveJoint` in `archiving.js`: [5](#0-4) 

That archiving path only runs when a unit is explicitly archived/pruned/voided (e.g. during catchup replays in `light.js`, or `tryRecoverPrunedContentOfFinalBadUnit` in `network.js`), not during the normal full-node stabilization flow in `main_chain.js` where a unit becomes `final-bad` in place while remaining in the `units`/`outputs` tables. This is exactly the "improper invalidation after an update" pattern from the CVE: the `is_spent` "entry" (analogous to a stale TLB/page-table entry) is written once and never invalidated when the underlying condition (a valid, unique spend) is retroactively falsified.

The project's own `tools/compare_vote_balances.js` documents this exact defect as a known, unresolved discrepancy class ("zombie-spent outputs"): [6](#0-5) [7](#0-6) 

### Impact Explanation
Every coin-selection path that funds a payment or an AA response requires `is_spent=0` (`inputs.js`, `indivisible_asset.js`, `balances.js`, `wallet.js`, `aa_composer.js`, `mc_outputs.js`). Once an output's `is_spent` flag is stuck at `1` due to a final-bad spender, the true, unspent, stable output becomes permanently unusable by its owner: it will never be selected as an input again, and its value is excluded from balance calculations that rely on `is_spent=0` while inputs.is_unique is null for the final-bad claimant, i.e. funds are unaccounted-for by anyone and irretrievably locked. This is an unprivileged-reachable fund-freezing bug: any user who posts (or has posted to them) two conflicting spends of the same output — a completely normal, permissionless action for any unit poster — can trigger it, either accidentally or by an attacker deliberately front-running a victim's own spend with a conflicting spend that will be resolved as `final-bad`.

### Likelihood Explanation
Double-spend attempts (two units spending the same output) are a routine, permissionless occurrence in DAG-based ledgers and are explicitly handled by `findStableConflictingUnits`/`propagateFinalBad`. Any user posting a spend, or any attacker racing a victim's spend with a conflicting one that is deterministically ordered as the loser, will cause the loser unit to become `final-bad` and permanently strand the spent output. No privileged role, malicious hub, or network-level position is required — a single unprivileged posted unit is sufficient. The bug is also self-reinforcing: `propagateFinalBad` walks the whole descendant chain of spenders, so the freezing can cascade to further outputs spent by intermediate units in the chain.

### Recommendation
When a unit is marked `final-bad` (both in the initial `findStableConflictingUnits` branch and in `propagateFinalBad`), enumerate its `transfer` inputs and reset `outputs.is_spent=0` for the corresponding `src_unit`/`src_message_index`/`src_output_index`, mirroring the logic already implemented in `archiving.js`'s `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit` (which correctly re-checks whether another `good` unit already claims the same output before unspending it, to avoid clobbering a legitimately spent output). Apply the same fix for `headers_commission`/`witnessing` input types via the analogous unspend logic in `archiving.js`. Add a regression test that posts a double-spend, lets the loser stabilize as `final-bad`, and asserts the original output's `is_spent` flag returns to `0` and is spendable again.

### Proof of Concept
1. Create address A with a stable, spendable output O (value V).
2. From A, post unit U1 spending O to address B.
3. Before U1 stabilizes, post a conflicting unit U2 (also authored/co-signed to be valid) that spends the same output O to address C, structured so that the DAG ordering/`findStableConflictingUnits` comparison makes U2 the winner (`good`) and U1 the loser (`final-bad`) — e.g., by making U2's unit hash sort first, matching the comment "the smallest original on the same MCI comes first and will become good, all others will become final-bad" in `main_chain.js`.
4. Wait for stabilization: `markMcIndexStable` sets U1's sequence to `final-bad` and clears `inputs.is_unique` for U1 (`main_chain.js` lines 1334-1350), but output O was already flagged `is_spent=1` by U1's write in `writer.js` (lines 378-383) and is never reset.
5. Verify: query `outputs` for O — `is_spent=1` even though the only claimant recognized as `good` is U2 (which spent a *different* output row if O was one of several inputs, or, if U1 and U2 both reference the same `src_unit/src_message_index/src_output_index`, then in the single-input case B's coin-selection code (`inputs.js`, `wallet.js`) will refuse to reuse O even though the ledger-recognized owner of the funds cannot recover them via A because `is_unique` was already consumed by U1's insert attempt) — demonstrating funds effectively stuck and inconsistent with `tools/compare_vote_balances.js`'s documented zombie-spent-output discrepancy.

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){
				conn.addQuery(
					arrQueries, 
					"UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?", 
					[row.src_unit, row.src_message_index, row.src_output_index]
				);
			});
			cb();
		}
	);
}
