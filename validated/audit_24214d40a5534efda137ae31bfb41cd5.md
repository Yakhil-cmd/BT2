### Title
Webhook `status` handler applies statuses to commits by SHA alone, letting any authenticated GitHub organization forge CI status for another organization's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to verify a payload against, but that verified identity is never propagated to (or checked by) the handler that actually mutates data. `StatusHandler#process` looks up commits by `sha` alone, with no repository/organization scoping, so a payload correctly signed with organization A's webhook secret can carry a `sha` that belongs to a commit in organization B's repository, and Shipit will apply the forged CI status to it.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-controlled JSON fields and uses it only to pick the HMAC key: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw parsed `params` (the entire JSON body, including any `repository`, `sha`, etc. fields) are dispatched unchanged to the handler: [3](#0-2) 

`StatusHandler#process` never re-derives or checks the repository the event claims to belong to - it matches commits by `sha` across the entire instance: [4](#0-3) 

Compare this with `Handler#stacks`/`#repository_name`, used by other handlers, which at least scope by `repository.full_name`: [5](#0-4) 

`StatusHandler` does not use this scoping at all — it is the field the signature is verified against (`repository.owner.login`) that is disconnected from the field the handler actually trusts (`sha`, with no `repository` cross-check whatsoever).

**Binding broken:** the organization whose secret authenticated the request (`repository_owner` in `verify_signature`) ≠ the repository/commit whose state is written (`Commit.where(sha: params.sha)` in `StatusHandler`). Shipit explicitly supports multiple GitHub organizations each with an independent `webhook_secret` (`lib/shipit/github_app.rb`, `docs/setup.md` "Using Multiple Github Applications"), so this is a real tenant boundary in this engine, not a theoretical one. [6](#0-5) 

### Impact Explanation
In a multi-organization Shipit deployment, an attacker who legitimately controls (or is a maintainer of) one configured GitHub organization can compute a valid `X-Hub-Signature` using that organization's own `webhook_secret`, then send a `status` event whose `sha` matches a commit belonging to a stack/repository owned by a *different* configured organization. `StatusHandler` will happily create a forged commit status (e.g. `state: success`, arbitrary `context`) on that unrelated commit, because it performs no ownership check. Since Shipit's deploy gating relies on commit statuses to determine whether a commit is deployable, this can be used to make an unreviewed/unverified commit in another organization's repository appear "green", enabling an unauthorized deploy - a Critical impact per the report's own success criteria.

### Likelihood Explanation
Requires only: (1) the target Shipit instance is configured with `config/secrets.yml` for more than one GitHub organization (documented, supported use case), and (2) the attacker controls one of those organizations' apps/webhook secret (i.e., is a legitimate but unprivileged tenant of the shared Shipit instance, not a Shipit admin or Shipit session holder). No `ApiClient` token, no `github_access_token`, and no Shipit session/UI access is needed - only an HTTP POST to `/github_webhooks` with a correctly computed HMAC for the attacker's own org.

### Recommendation
`StatusHandler` (and any other handler that trusts payload fields for lookups) must scope its query by the repository identified in the payload, and `WebhooksController#verify_signature` should assert that the organization used to verify the signature actually owns the repository referenced elsewhere in the same payload (e.g., compare `repository_owner` against `repository.full_name`'s owner, and have handlers filter by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (supported multi-org configuration).
2. Attacker computes `X-Hub-Signature` for a JSON body using `attacker-org`'s known `webhook_secret`:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"},
  "sha": "<victim commit sha belonging to victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. POST to `/github_webhooks` with header `X-Github-Event: status` and the computed signature.
4. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and verifies successfully against the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (no ownership check), and calls `commit.create_status_from_github!(params)`, marking the victim's commit `success` for `ci/required-check` even though the attacker never had access to `victim-org`.
