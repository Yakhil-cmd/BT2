### Title
Membership webhook `organization.login` is trusted for `Team#organization` while signature verification authenticates a different, attacker-controlled `repository.owner.login` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `webhook_secret` used to validate the HMAC signature based on `repository_owner`, which reads `params.dig('repository','owner','login')` and only falls back to `params.dig('organization','login')` when `repository` is absent. `MembershipHandler#find_or_create_team!` instead trusts `params.organization.login` unconditionally to set `Team#organization`. Because the attacker fully controls the raw JSON body posted to `/webhooks` and signs it with their own known `webhook_secret`, they can make `repository.owner.login` (the authenticating field) and `organization.login` (the field written to the DB) point to two different organizations.

### Finding Description
The broken binding is:
`repository_owner` (used to select `webhook_secret` in `Shipit.github(organization: repository_owner)`, `app/controllers/shipit/webhooks_controller.rb:25,59-62`) **should equal** `params.organization.login` (used to set `team.organization`, `app/models/shipit/webhooks/handlers/membership_handler.rb:41`), because both are meant to represent "the organization that authenticated this event."

Trace:
1. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches the corresponding `GitHubApp` via `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(header, raw_body)` which does a `secure_compare` of the HMAC-SHA1 of the raw body against `webhook_secret` for that organization (`lib/shipit/github_app.rb:76-83`).
2. If the attacker sets `params['repository']['owner']['login'] = 'attacker-org'` (an org they control and whose `webhook_secret` they know, since they administer that GitHub App/organization in Shipit's config) while setting `params['organization']['login'] = 'victim-org'`, `repository_owner` resolves to `'attacker-org'`, and the signature check passes because the attacker signs the raw body with their own known secret.
3. `MembershipHandler#process` → `find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) ignores `repository_owner` entirely and writes `team.organization = params.organization.login`, i.e., `'victim-org'`, then `team.add_member(User.find_or_create_by_login!(params.member.login))` adds an arbitrary GitHub login as a member of that Team.

No existing guard prevents this: `verify_signature` only checks the signature against whichever organization `repository_owner` names; it never checks that `repository_owner == params.organization.login`. `drop_unhandled_event` only filters unknown event types, not this divergence. The `ExplicitParameters` schema on `MembershipHandler` (`params do ... end`) only enforces types/presence, not cross-field consistency with `repository`.

### Impact Explanation
An attacker who controls a legitimate Shipit-registered GitHub organization/App (their own `attacker-org`) can craft a membership webhook payload that is validated using their own known secret but writes/modifies team membership for an arbitrary victim organization (`Team#organization`), via `Team.find_or_create_by!`/`team.add_member` in `app/models/shipit/webhooks/handlers/membership_handler.rb:23,28,38-43`. Since `Shipit.github_teams` is used for authorization elsewhere in the app, this allows escalation into authorization scoped to the victim org - adding themselves or any GitHub login as a team member for that org. This is repeatable against any organization name and is not limited to the attacker's own tenant, matching the High/Critical "escalation into `Shipit.github_teams` authorization" and "payload for one repository mutating another's stack/team" categories.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment where the attacker legitimately administers at least one configured GitHub App/organization with a known `webhook_secret`; (2) the ability to POST directly to `/webhooks` with a crafted JSON body and matching `X-Hub-Signature` header (trivial, no session or token required - `WebhooksController` has no authentication besides the signature check). The attacker does not need to compromise the victim org's secret at all - only their own. This is a low-cost, fully repeatable attack once the attacker onboards or controls one legitimate org in the same Shipit instance.

### Recommendation
In `find_or_create_team!` (and any other handler trusting `params.organization.login`), use the same authenticated `repository_owner` value computed by `WebhooksController` (e.g., pass it through to handlers, or re-derive it identically) instead of trusting `params.organization.login`. Alternatively, in `verify_signature`, reject the request (or refuse to dispatch) whenever `params.dig('repository','owner','login')` and `params.dig('organization','login')` are both present and differ, ensuring the field used for authentication and the field used for authorization writes are always the same value.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership event cannot bind a team to an organization that didn't authenticate the request" do
  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret) # known to attacker
  payload = {
    action: 'added',
    team: { id: 42, name: 'Test', slug: 'test', url: 'https://api.github.com/teams/42' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker-controlled-user' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)

  post shipit.webhooks_path, params: payload,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature,
                  'Content-Type' => 'application/json' }

  assert_response :ok
  team = Shipit::Team.find_by!(github_id: 42)
  # equality that should hold but doesn't:
  # repository_owner ('attacker-org') == team.organization
  assert_equal 'attacker-org', team.organization # FAILS: actual value is 'victim-org'
end
```
