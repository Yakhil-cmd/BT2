## Title
AA payment messages sending fixed-denomination (indivisible) assets are silently dropped, permanently freezing those asset funds inside the AA - (File: aa_composer.js)

### Summary
The reported bug class is a hard-coded assumption that only one sub-type of a dual-type asset system is supported (ERC721 vs ERC1155), so operations on the unsupported sub-type silently fail and the corresponding funds become unreachable. The same pattern exists in `ocore`'s Autonomous Agent (AA) engine: AA definitions are validated as if they can send payments in *any* asset, including indivisible (`fixed_denominations`) assets, but the trigger-execution code in `aa_composer.js` silently strips out every payment message that targets a `fixed_denominations` asset before the response unit is built, meaning the funds are never actually sent.

### Finding Description
An AA definition's `messages` array is validated by `aa_validation.js`'s `payment` case, which allows `asset` to be any valid asset identifier (or a formula), with no restriction excluding indivisible/fixed-denomination assets: [1](#0-0) 

However, when the trigger is actually handled at runtime in `aa_composer.js`, every payment message whose asset is `fixed_denominations` is marked to be filtered out ("will skip it later") instead of composed: [2](#0-1) 

The message is then unconditionally dropped in the second-pass filter: [3](#0-2) 

If, after this filtering, no messages remain, the trigger is treated as a "successful empty response" — the AA still consumes/updates state and balances for the trigger, but no output payment is ever produced: [4](#0-3) 

This mirrors the reported bug precisely: the code path only supports one asset "kind" (divisible/base assets) and simply discards operations for the other kind (indivisible, `fixed_denominations` assets) instead of executing them or explicitly rejecting/bouncing the trigger. Because the AA's `state` changes and internal balance accounting still occur even though the payment output for the indivisible asset was dropped, per the `bounce`/`sendDummyUnit` handling logic that deducts balances only for the messages that actually get composed: [5](#0-4) 

### Impact Explanation
Any AA that is designed to receive and forward/distribute an indivisible (fixed-denomination) asset — e.g., acting as an escrow, marketplace, or claim contract for capped/NFT-like coins — will never be able to deliver that asset to the intended recipient. The payment message is silently removed rather than causing the trigger to bounce, so the AA's state can advance (marking the transfer as "done" in its state vars) while the actual funds remain permanently stuck in the AA's balance with no code path capable of releasing them. This is a concrete AA fund freezing scenario: legitimate recipients lose access to assets they are entitled to, and the AA operator/definer has no way to recover them either, since the AA logic itself has no other route to move `fixed_denominations` assets out.

### Likelihood Explanation
This triggers deterministically any time an AA definition includes a `payment` message for an asset that turns out to have `fixed_denominations: true` and that message is reached during evaluation. Since `aa_validation.js` fully permits such definitions to be published (no rejection at AA definition time), an AA author does not receive any warning that this functionality is a no-op, and any user or another AA sending indivisible-asset funds to such an AA anticipating a forwarded/claimed payment will have those funds silently trapped. No malicious actor is required — a single legitimate AA author or trigger sender combination reliably reproduces the freeze.

### Recommendation
Either (a) reject AA definitions containing `payment` messages for `fixed_denominations` assets at validation time in `aa_validation.js`, explicitly disallowing this unsupported combination so authors get immediate feedback, or (b) implement proper support for composing indivisible-asset payments from AAs in `aa_composer.js` (mirroring the coin-picking logic used in `indivisible_asset.js`), and in the meantime cause the trigger to `bounce` (returning the received funds) rather than silently dropping the message and treating the trigger as successfully handled.

### Proof of Concept
1. Define (or have deployed) an indivisible asset `A` with `fixed_denominations: true`.
2. Publish an AA definition whose `messages` includes a `payment` message with `asset: A` and an output to some recipient address; this passes `aa_validation.js` validation without error since fixed-denomination assets aren't excluded there (`aa_validation.js` payment case, lines 123-135).
3. Send a trigger unit to the AA that also transfers some amount of asset `A` to the AA (and enough base bytes to satisfy `bounce_fees`).
4. During execution, `aa_composer.js`'s `sendUnit` loads asset info, finds `objAsset.fixed_denominations === true`, and skips completing that payment message (lines 1323-1328), then filters it out entirely in the second pass (lines 1356-1361).
5. If this was the only substantive message, `handleSuccessfulEmptyResponseUnit` is invoked — the trigger is recorded as handled/successful, AA state can be updated, but no output unit ever delivers asset `A` to the recipient; the received `A` funds remain in the AA's balance indefinitely with no code path to spend them out.
