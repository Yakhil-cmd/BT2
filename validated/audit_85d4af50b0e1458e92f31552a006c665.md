### Title
Cross-node stake-reward divergence when `recalculate_stake_rewards` recomputes `delegation_may_need_adjustment` from live account state instead of the original epoch-boundary snapshot - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`Bank::recalculate_stake_rewards`, invoked only after a validator restarts from a snapshot mid-epoch-reward-window, recomputes the partitioned stake reward set using the *current* live `StakesCache` lamport balances rather than the lamport balances that existed at the original epoch-boundary calculation. Because `delegation_may_need_adjustment` is a threshold decision based on `current_lamports`, an attacker who sends an ordinary 1-lamport system transfer to a not-yet-distributed stake account between the epoch boundary and a validator's restart can cause that account to be included/excluded from the reward-adjustment set differently than validators that never restarted and are using their in-memory cached calculation.

### Finding Description
The stake-reward "may this delegation need a rent adjustment" decision is `delegation_may_need_adjustment`, which compares `lamports_with_rewards.saturating_sub(minimum_lamports)` against the pre-existing delegation: [1](#0-0) 

It is fed `current_lamports = stake_account.lamports()`, read directly off whatever `StakeAccount` is passed in: [2](#0-1) 

and again through the normal (vote-account-present) path via `redeem_rewards`/`redeem_stake_rewards`: [3](#0-2) 

The original, once-per-epoch calculation (`calculate_rewards_for_partitioning` → `calculate_stake_rewards_and_commissions`) runs at the epoch-boundary block using the `StakesCache` as it exists at that exact slot, and its result (`all_stake_rewards`/`partition_indices`) is cached in `Bank::epoch_reward_status` and reused unchanged by every non-restarting validator for the rest of the multi-block distribution window.

`recalculate_stake_rewards`, however, is only exercised when a validator restarts from a snapshot and must reconstruct this in-memory `epoch_reward_status`. It re-derives its inputs from `self.stakes_cache.stakes()` — i.e., the *live*, current bank state at the restart slot, not a preserved snapshot of the epoch-boundary state: [4](#0-3) [5](#0-4) 

This is invoked from `initialize_after_snapshot_restore`: [6](#0-5) 

The existing regression tests only validate that recalculation reproduces the original result when (a) nothing has changed, or (b) an entry has already been *distributed* (paid), which is explicitly excluded from recalculation: [7](#0-6) 

Neither test covers the case where an undistributed stake account simply receives a plain lamport transfer (not a reward payout) between the epoch boundary and the restart point. Because the account is delegated, arbitrary lamports can be transferred into it via `system_instruction::transfer` without any signature or authorization from the stake account itself — anyone can fund any account.

If such a transfer nudges `current_lamports` across the `lamports_with_rewards.saturating_sub(minimum_lamports)` boundary computed in `delegation_may_need_adjustment`, the account is included in the reward-adjustment set on recalculation but was excluded (or vice versa) in the originally-cached calculation used by non-restarting peers. When `redeem_delegation_rewards`/`redeem_rewards` return `None`/`Err`, the filter step in `calculate_stake_rewards_and_commissions` drops the account from the partitioned reward set entirely: [8](#0-7) 

Because `PartitionedStakeReward` entries drive the actual account mutation at distribution time (`build_updated_stake_reward` writes `new_stake.delegation.stake` and adjusts the account for rent using `adjust_delegation_for_rent`), a stake account that's present in one validator's partitioned reward set but absent in another's will end up with a genuinely different `stake.delegation.stake` (or simply untouched vs. adjusted) after the distribution block executes: [9](#0-8) 

No signer, rent, epoch, or overflow guard prevents this: the arithmetic is all `saturating_*`, and the divergence stems purely from which lamport snapshot ("epoch-boundary" vs. "live-at-restart") is fed into the threshold comparison.

### Impact Explanation
This is a cross-node state-divergence bug in consensus-critical stake-reward accounting. A validator that restarts from a snapshot mid-epoch-reward-distribution window can compute and commit a different `stake.delegation.stake` for an affected account than validators that did not restart, at the exact same distribution block. Since bank state (and hence bank hash) must be bit-identical across all honest validators processing the same block sequence, this produces a bank-hash divergence / potential consensus halt — matching the "cross-node state divergence / epoch-boundary halt" bounty category.

### Likelihood Explanation
Preconditions are modest and fully within an unprivileged attacker's control: any stake account (their own or, in principle, any other undistributed delegated stake account) sitting near the `minimum_lamports` threshold, plus a single 1-lamport `system_instruction::transfer` sent into it sometime between the epoch boundary and a validator restart. Validator restarts from snapshot (upgrades, crashes, fast-restart operational procedures) are routine events in a live cluster, so the race window recurs naturally every epoch; the attacker does not need to control or predict the exact restart moment precisely — sending the nudging transfer early in the distribution window and leaving it in place suffices, since any restart occurring afterward but before that account's reward partition is distributed will observe the shifted balance.

### Recommendation
`recalculate_stake_rewards` must reproduce the exact same inputs the original epoch-boundary calculation used, not the live `StakesCache`. Persist (as part of `Bank::epoch_reward_status`/whatever is (re)serialized across restarts) the lamport balances (or the full `current_lamports`/`minimum_lamports` snapshot) that were used for each unresolved stake delegation at calculation time, and have `recalculate_stake_rewards` recompute `delegation_may_need_adjustment` from that frozen snapshot rather than from `self.stakes_cache.stakes()`'s current balances. Alternatively, defer the entire adjustment-eligibility decision to distribution time only (removing the calculation-time inclusion/exclusion gate) so that the final decision is always made against the single canonical distribution-block account state that all validators share.

### Proof of Concept
Extend `test_recalculate_stake_rewards`/the snapshot-restore test harness (`calculation.rs`, e.g. near `test_recalculate_stake_rewards` at line 2428 or the partial-distribution test around line 2681) with a new case:
1. Build a reward bank with a stake account whose lamports sit exactly at the `delegation_may_need_adjustment` boundary such that at the epoch-boundary calculation it is *excluded* (`redeem_delegation_rewards` returns `None`), matching `test_redeem_delegation_rewards_excludes_inactive_from_partition`'s style at line 1301.
2. Capture the original `all_stake_rewards` from `Bank::epoch_reward_status` (Calculation phase) and confirm the target stake pubkey is absent.
3. Before calling `recalculate_stake_rewards`, directly credit the stake account with `+1` lamport via `bank.store_account`/`checked_add_lamports` to simulate the attacker's system transfer landing in an intervening block.
4. Call `bank.recalculate_stake_rewards(&epoch_rewards_sysvar, &thread_pool)` and assert that the target stake pubkey is now present in the recalculated reward set (`enumerated_rewards_iter()`), proving divergence from the cached original set.
5. Assert `original_stake_rewards` (as would be used by a non-restarted node) and `recalculated_stake_rewards` (as used by a restarted node) disagree on membership/`inflation.stake` for the same `stake_pubkey`, demonstrating that distributing from each would produce different final `StakeStateV2` account bytes and thus different bank hashes for the same block.

pub(crate) fn delegation_may_need_adjustment(
    current_delegation: u64,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
    status: StakeActivationStatus,
) -> bool {
    if status.effective == 0 && status.activating == 0 {
        return false;
    }

    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    new_delegation != current_delegation
}

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,
        );
        (stake_rewards, partition_indices)
    }
