### Title
Webhook signature verified against attacker's own org but payload's `repository.full_name`/commit `sha` used to act on a different org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository','owner','login')` or `params.dig('organization','login')` in the *same, attacker-crafted* JSON body. The event handlers, however, decide which `Stack`/`Repository`/`Commit` to mutate using a *different* field of that same body — `repository.full_name` (`Handler#repository_name`) or a bare commit `sha` (`StatusHandler`) with no repository scoping at all. Nothing binds "the org whose secret validated this delivery" to "the repository/commit that gets acted upon."

### Finding Description
`verify_signature` resolves the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

It then verifies the raw body's HMAC against that organization's own `webhook_secret`: [3](#0-2) 

Once verification succeeds, `create` dispatches the whole payload to the registered handler for the event: [4](#0-3) 

But the handlers resolve the target `Stack` using a *different* field of the same payload — `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`StatusHandler` is worse: it does not scope by repository at all, only by commit `sha`, matching across every stack/repository tracked by this Shipit instance: [6](#0-5) 

`PushHandler` and `CheckSuiteHandler` use `stacks` (i.e. `repository.full_name`) to find the target and then trigger sync/deploy-gating actions: [7](#0-6) [8](#0-7) 

Shipit is explicitly designed to host multiple independent GitHub Apps/organizations in one instance, each with its own `webhook_secret`, as shown in the sample config: [9](#0-8) 

The binding that should hold is:
`organization used to select/verify the webhook_secret == organization that owns the repository/stack being mutated`

Because both values are read from the same untrusted payload without any cross-check, an attacker who legitimately administers **their own** organization's GitHub App/webhook_secret in this Shipit instance (a normal, unprivileged tenant of a multi-org install) can forge a delivery that:
- Sets `repository.owner.login` / `organization.login` = `attacker-org` (so `verify_signature` looks up and HMACs against a secret the attacker already knows), and
- Sets `repository.full_name` = `victim-org/victim-repo` (or, for `status` events, an arbitrary commit `sha` belonging to any tracked stack).

The signature check passes (it's a valid HMAC computed with the attacker's own known secret over a body the attacker fully controls), yet the handler acts on a repository/commit belonging to a different organization entirely — exactly the "organization that authenticated versus the repository that is written" trust-binding break.

### Impact Explanation
This allows an unprivileged webhook sender (owner of one tenant org in a multi-org Shipit install) to:
- Inject arbitrary commit `status` records for any commit sha tracked anywhere in the instance via `StatusHandler`, which can be used to satisfy status checks that gate deploys/merges for stacks belonging to other organizations.
- Trigger `sync_github`/`schedule_refresh_check_runs!` against other organizations' stacks via `PushHandler`/`CheckSuiteHandler`, forcing state changes cross-repository.
This crosses a cross-repository / cross-organization trust boundary and can influence deploy/merge gating decisions for repositories the attacker has no access to, matching the High-severity criteria (escalation across the intended authorization boundary of a stack/repository).

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple GitHub Apps/organizations (a documented, supported configuration), and requires the attacker to control one of those organizations' own `webhook_secret` (i.e., be a legitimate but unprivileged administrator of their own tenant app) — no privileged Shipit account, `ApiClient` token, or access to the victim org's secret is needed.

### Recommendation
After `verify_signature` succeeds, re-derive the trusted organization from the resolved `github_app`/`organization` used for verification and require that the target repository's owner (as looked up by `Handler#repository_name`) match that trusted organization before dispatching to a handler. Additionally, scope `StatusHandler` (and any other handler acting on bare `sha`) to commits belonging to stacks whose repository owner matches the verified organization, not merely by `sha`.

### Proof of Concept
1. Shipit instance configured with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` pattern), both tracking stacks.
2. Attacker knows `attacker-org`'s `webhook_secret` (they own that GitHub App).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status` and a body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. `X-Hub-Signature` is computed as `sha1=` HMAC(`attacker-org`'s webhook_secret, raw_post) — a value the attacker can compute themselves.
5. `verify_signature` picks `Shipit.github(organization: 'attacker-org')`, verifies successfully, and `StatusHandler#process` creates a `success` status for the victim's commit `sha`, regardless of which repository it actually belongs to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
