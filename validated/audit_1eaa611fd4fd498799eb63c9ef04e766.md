### Title
Uncaught exception in address-checksum validation on crafted addresses (`isChashValid`) - ([File: chash.js])

### Summary
`chash.js`'s `isChashValid()` is the c-hash/address-checksum verifier used everywhere an address string from untrusted, attacker-supplied data needs to be validated (payment outputs, author/definition-change addresses, AA trigger/definition addresses, asset issuer/attestor addresses, etc., via `validation_utils.isValidAddress`/`isValidChash`). Similar to how `lha_read_data_none()` in libarchive trusted a length derived from crafted header data and read out of the expected buffer, `isChashValid()` only wraps the *decode* step (`base32.decode`/`Buffer.from(..., 'base64')`) in a `try/catch`, but the subsequent length-dependent processing (`separateIntoCleanDataAndChecksum`) throws an uncaught `Error` when the decoded byte length does not correspond exactly to 160 or 288 bits. [1](#0-0) [2](#0-1) 

### Finding Description
`isChashValid(encoded)` first checks only the *string* length (32 or 48 characters), then decodes it as base32 or base64: [3](#0-2) 

The decode step is guarded by `try/catch`, but nothing guarantees the *decoded byte length* actually matches 20 bytes (160 bits) or 36 bytes (288 bits). Base64 decoding in particular can terminate early when a `=` padding character appears in a non-terminal position of the 48-character string, or can otherwise yield a buffer shorter/longer than 36 bytes for a maliciously crafted, but still 48-character-long, input. `buffer2bin()` then converts whatever the actual buffer length is into a bit string of `buf.length*8` bits, and `separateIntoCleanDataAndChecksum()` throws when that bit length is neither 160 nor 288: [2](#0-1) 

This throw is **outside** the `try/catch` block in `isChashValid()`, so it is not turned into a `return false`; it propagates as an uncaught exception. `isChashValid` is reached through `isValidChash`/`isValidAddress` in `validation_utils.js`: [4](#0-3) 

`isValidAddress` is called synchronously and unguarded from many attacker-reachable validation paths, e.g. payment output addresses inside `validate()`: [5](#0-4) 

as well as author addresses, AA definitions/triggers, attestation payloads, asset issuer/attestor lists, and definition-related checks throughout `validation.js`, `definition.js`, and `aa_validation.js`. None of these call sites wrap `isValidAddress` in a local `try/catch`, so a crafted address string that passes the length check but decodes to a mismatched byte length will throw synchronously during unit/AA-trigger/asset validation.

### Impact Explanation
An uncaught exception thrown during synchronous validation of an incoming unit (which any unprivileged peer can post) crashes the calling stack; depending on where it fires (e.g., inside the main `validate()` flow invoked for every incoming joint), this can crash or destabilize the node process handling unit/joint validation, matching the required impact class of "a network unable to confirm new units." Because the malformed value only needs to be a correctly-sized string (32 or 48 chars) with content chosen to make padding/invalid characters truncate the decode, this is trivially reachable by a single crafted unit, AA trigger, or asset definition containing such an "address."

### Likelihood Explanation
Reachability is high: address fields are validated on essentially every unit, AA trigger, and asset definition. Crafting a 48-character base64-like string containing an interior `=` character (or other characters that a given base64 decoder implementation treats specially) is straightforward and requires no privileged access — this is exactly analogous to how a "specially crafted lha archive" in the CVE triggers the parser's unchecked length assumption.

### Recommendation
Move the length-mismatch checks in `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData` inside `isChashValid`'s existing `try/catch`, or explicitly validate `chash.length` (byte length, not the encoded string length) against the expected 20/36 bytes before calling `buffer2bin`, returning `false` instead of throwing for any mismatch. Additionally, audit all callers of `isValidAddress`/`isValidChash` to ensure a thrown exception here cannot escape unit/AA/asset validation unhandled.

### Proof of Concept
1. Construct a 48-character string intended to be validated as a `chash288`/32-byte address, where byte 10 (for example) is `=` and the remaining characters are valid base64 alphabet characters, so `Buffer.from(str, 'base64')` decodes fewer than 36 bytes.
2. Place this string as the `address` of a payment output (or as an AA trigger `address`, or asset `attestors` entry) in a unit and post it to a node.
3. During `validate()` → `isValidAddress(o.address)` → `isChashValid()`, `separateIntoCleanDataAndChecksum` receives a bit string whose length is neither 160 nor 288 and throws `Error("bad length=...")`, which is not caught anywhere in the call chain, crashing/destabilizing the validating process.

function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);

	}

	var checksum = bin2buffer(separated.checksum);

}
