### Title
Cross-organization webhook signature confusion allows forging commit statuses (and other events) for arbitrary Shipit repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but the payload's `repository.full_name` field — which the actual event handlers use to resolve which `Stack`/`Repository` (or, for `status` events, no repository scoping at all) the payload writes to — is never covered by that verification. This is the same class of bug as the PoolTogether report: a value that determines the outcome of a privileged operation is decoupled from the value that was actually authenticated/signed.

### Finding Description
The webhook signature check picks the GitHub App/org (and thus its `webhook_secret`) purely from the org-login field embedded in the untrusted JSON body: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` additionally treats a blank `webhook_secret` as automatically valid: [3](#0-2) 

Once "verified", the full raw payload is dispatched to handlers unmodified: [4](#0-3) 

But the handlers resolve the target `Repository`/`Stack` from a *different* field, `repository.full_name`, which is not bound to the signing key used above: [5](#0-4) 

The `status` handler is the most severe case: it doesn't even scope by repository — it matches purely on `sha` across the entire `commits` table, i.e. across every stack/organization hosted by the Shipit instance: [6](#0-5) 

Equality that should hold but doesn't: `organization authenticated by signature (repository.owner.login / organization.login)` == `repository actually written by the handler (repository.full_name, or nothing at all for status)`. In a multi-tenant Shipit instance (multiple orgs configured under `Shipit.github`, as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who can produce a validly-signed payload for **any one** configured organization — including one whose `webhook_secret` is left blank, which is explicitly accepted as configuration (`webhook_secret: # nil`) — can set `repository.owner.login` to that org (to pass verification) while setting `repository.full_name`/`sha` to reference a *different* target organization's stack/commit.

### Impact Explanation
A forged `status` event lets an attacker mark an arbitrary commit `success` (`Commit#create_status_from_github!` → `Commit#deployable?`): [7](#0-6) 
Since `deployable?` gates continuous delivery (`schedule_continuous_delivery`) and manual "Deploy" eligibility, injecting a fake success status can make an unreviewed/malicious commit deployable, i.e. an unauthorized deploy — one of the explicitly in-scope Critical impacts. `check_suite` and `membership` handlers are similarly reachable with attacker-controlled `full_name`/`organization.login` values that need not match the org whose secret validated the request, extending this to spurious CI check triggers and forged team membership changes (an escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Requires no privileged Shipit account, API token, or the target's `webhook_secret`. It only requires (a) the Shipit instance being multi-tenant (multiple GitHub orgs configured, as the codebase's own sample configs demonstrate is a supported deployment mode) and (b) at least one configured org having a blank/unknown-to-attacker-mismatched `webhook_secret`, or the attacker controlling any one legitimately configured org's webhook secret (e.g. by registering their own GitHub App/org against the same Shipit instance, a normal, unprivileged onboarding action). Given webhook delivery is unauthenticated apart from this signature, and the request is a single unauthenticated HTTP POST, likelihood is High for instances hosting more than one organization.

### Recommendation
Bind the field used to select the verification secret to the same field(s) used by every handler to resolve state: verify the signature using the secret for the organization implied by `repository.full_name`'s owner (not a separately-provided `owner.login`), and make handlers reject/ignore events whose `repository.full_name`'s owner doesn't match the organization that produced a valid signature. Additionally, `status_handler.rb` must scope `Commit.where(sha:)` by the verified repository/stack rather than matching globally, and `verify_webhook_signature` should not implicitly succeed when `webhook_secret` is blank for a given org unless that is an explicit administrator opt-out.

### Proof of Concept
1. Shipit instance hosts two orgs: `AttackerOrg` (attacker knows/controls `webhook_secret`, or it is unset) and `VictimOrg/victim-repo` (a real Shipit stack with `webhook_secret` the attacker does not know).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
3. Attacker signs the raw body with `AttackerOrg`'s webhook secret (or sends no matching secret if `AttackerOrg.webhook_secret` is blank) and sets `X-Github-Event: status`, `X-Hub-Signature` accordingly.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` via `repository_owner`, verification passes.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which does `Commit.where(sha: params.sha)` — matching the victim's real commit regardless of `AttackerOrg`/`VictimOrg` mismatch — and calls `create_status_from_github!`, marking the victim commit `success`, potentially triggering continuous deployment of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
