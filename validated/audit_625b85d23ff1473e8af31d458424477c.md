### Title
Contract acceptance signature only binds the `title` string, not the full contract terms, allowing signature replay to forge acceptance of different contract terms - ([File: wallet.js])

### Summary
CVE-2024-49394 describes a mutt/neomutt flaw where a cryptographically signed email's `In-Reply-To` header is not covered by the signature, letting an attacker reuse a legitimately signed message to impersonate consent in a different context. The same "signature commits to too little context" bug class exists in ocore's prosaic/arbiter contract acceptance flow: the peer's cryptographic acceptance (`signed_message`) is checked only against `objContract.title`, not against a hash of the full contract terms (`text`, `amount`, `asset`, `arbiter_address`, `ttl`, `cosigners`), so a previously obtained signature over a given title string can be replayed to forge acceptance of an unrelated contract that reuses the same title but different substantive terms.

### Finding Description
In `wallet.js`, both the `prosaic_contract_response` handler and the `arbiter_contract_response` handler validate a peer's signed acceptance like this: [1](#0-0) [2](#0-1) 

In both cases, `signed_message.validateSignedMessage()` only proves that `author.address` (i.e. `objContract.peer_address`) cryptographically signed the `signed_message` string, and the handler additionally requires `objSignedMessage.signed_message != objContract.title` to fail — i.e. the *entire* semantic binding between the signature and "this specific contract" is the equality of the signed string with the contract's free-text `title` field.

Compare this to `prosaic_contract.getHash()`, which commits to `title + text + creation_date`: [3](#0-2) 
— i.e. the contract's identity/hash includes `text` and `creation_date`, but the acceptance signature check in `wallet.js` does not require the signed message to cover the contract hash or the `text`/`creation_date`/`amount`/`asset`/`arbiter_address` fields; it only requires the signed string to equal `title`.

For `arbiter_contract`, the situation is worse because real value is at stake: contracts carry `amount`, `asset`, `arbiter_address`, `me_is_payer`, `cosigners`, and eventually a `shared_address` used for escrow/settlement (`arbiter_contract.js` create/store functions at lines 21-116). Yet the only thing cryptographically bound in the "accepted" signature is the `title` string (`wallet.js` lines 932-935).

Because `title` is a short, attacker/offer-controlled free-text field, an attacker who is a paired correspondent (in-scope actor: "paired device") can:
1. Send contract offer #1 with `title = "Agreement A"` and innocuous `text`/`amount`, obtain the counterparty's legitimately signed acceptance (`signed_message == "Agreement A"`).
2. Later send a new offer #2 to the same or another counterparty relationship reusing `title = "Agreement A"` but with different, adversarial `text`, `amount`, `asset`, or `arbiter_address`.
3. Replay the old signature bytes as `body.signed_message` in the new `arbiter_contract_response`/`prosaic_contract_response`. `wallet.js` will accept it as valid because it only checks `signed_message === title`, and the check passes even though the counterparty never agreed to the new contract's actual terms.
4. The receiving node then treats the contract as `accepted` (`setField(objContract.hash, "status", body.status, ...)`), proceeds to derive a shared/escrow address and can move forward with committing funds under terms the peer never actually authorized.

This is the same root-cause pattern as the CVE: a signature is verified over a narrow, attacker-influenced field (`title`/`In-Reply-To`) while the security-relevant payload (`text`/full email body, `amount`/`asset`/`arbiter_address`) is left outside the signed scope, enabling replay/impersonation of consent.

### Impact Explanation
For `arbiter_contract`, forged "acceptance" of contract terms can lead directly to fund loss: the accepting party's counterparty (or an attacker controlling one paired device in the relationship) can make the protocol logic believe a peer agreed to specific `amount`/`asset`/`arbiter_address` terms it never signed for, which can result in an escrow/shared address being derived and payments being composed and sent based on unauthorized terms — a form of AA/contract fund-loss and unauthorized-spending analog reachable purely from a paired device message, matching the scope's "wallet and contract message handling" category. For `prosaic_contract`, impact is weaker (no direct funds) but still results in a legally/operationally meaningful accepted "signed" agreement whose text was never actually signed by the counterparty, i.e., a signature-impersonation vulnerability of Medium severity, consistent with the reported CVE's 5.3 (Medium) severity for spoofing/impersonation.

### Likelihood Explanation
Exploitation only requires being a paired correspondent (already a permitted actor for wallet/device messages) capable of creating two contract offers that intentionally reuse an identical `title` value while varying `text`/`amount`/`asset`, and capturing/replaying the previously obtained signature bytes for the shared title string. No cryptographic break is needed — this is a pure protocol/binding flaw, making exploitation straightforward once an attacker controls contract offer content (which senders/offerors normally do).

### Recommendation
Bind the acceptance signature to the full contract commitment rather than to the `title` alone: require `objSignedMessage.signed_message` to equal (or contain) `objContract.hash` (which already covers `title + text + creation_date` per `getHash()`), and for `arbiter_contract`, additionally include `amount`, `asset`, and `arbiter_address` in the value that must be signed/verified, so that a signature cannot be replayed across contracts that differ in substantive terms but share a title.

### Proof of Concept
1. Device A sends `arbiter_contract_offer` #1 to Device B with `title="Deal"`, `amount=1000`, `asset="base"`.
2. Device B accepts, producing `signed_message = "Deal"` signed by B's address (per `arbiter_contract.js` `respond()`).
3. Device A captures B's `signed_message`/signature bytes from the `arbiter_contract_response`.
4. Device A creates `arbiter_contract_offer` #2 with the same `title="Deal"` but `amount=100000`, `asset="different_asset"`.
5. Device A crafts an `arbiter_contract_response` for contract #2 reusing B's captured signature (still `signed_message == "Deal"`, still signed by B's address).
6. `wallet.js`'s check `objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title` (lines 932-935) passes, and the handler treats contract #2 as accepted by B even though B never agreed to the new amount/asset terms. 			return cb("contract is in non-applicable status");
		var send = function(authors, pairing_code) {
			var response = {hash: objContract.hash, status: status, signed_message: signedMessageBase64, my_contact_info: objContract.my_contact_info};
			if (authors) {
				response.authors = authors;
			}
			if (pairing_code) {

			}
			device.sendMessageToDevice(objContract.peer_device_address, "arbiter_contract_response", response);
