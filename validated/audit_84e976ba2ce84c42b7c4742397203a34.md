### Title
Cross-tenant Commit Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with a global `Commit.where(sha: params.sha)` lookup that has no relation to the organization whose webhook secret authenticated the request. `WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` matches a configured `Shipit.github(organization:)` app secret; it never checks that the org owning that secret actually owns the stack/repository of the commit(s) that get mutated.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`organization_that_signed_the_request (repository_owner used in Shipit.github(organization: repository_owner)) == commit.stack.repository.owner (the tenant whose data gets mutated)`

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` purely from the attacker-controlled JSON body (`params.dig('repository','owner','login')`, line 59-61) and looks up `Shipit.github(organization: repository_owner)` to verify the HMAC signature [1](#0-0) . In a multi-org deployment (`lib/shipit.rb` `github_app_config`/`github_organizations`, and documented in `docs/setup.md` "Using Multiple Github Applications") each organization has its own independent `webhook_secret` [2](#0-1) . This only proves the request was really sent by GitHub on behalf of the org named in the payload — it proves nothing about which commit rows may be touched.
2. `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [3](#0-2) 
This query is global across the `commits` table (the unique index added in `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` scopes uniqueness to `(stack_id, sha)`, not `sha` alone — confirming the schema allows the same sha to exist under many different stacks/orgs simultaneously). There is no filter such as `.joins(stack: :repository).where(repositories: { owner: repository_owner })`.
3. `Commit#create_status_from_github!` unconditionally writes the row: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) [5](#0-4) , which can flip `Commit#deployable?` since it depends on `status.success?`/`blocked?` [6](#0-5) .

Exploit flow: since a git commit's SHA is content-addressed (author, committer, timestamps, message, tree, parents), an attacker who owns `attacker/evil-repo` (e.g. a legitimate fork of `shopify/shipit-engine` onboarded as its own tenant/org in this multi-org Shipit instance) can retain or reproduce a commit object with an identical SHA to one already tracked under `shopify/shipit-engine`'s stack. The attacker then causes GitHub to deliver a genuine, correctly-signed `status` webhook for their own org/repo (e.g. by having their own CI post a status to their fork) referencing that shared sha. `verify_signature` passes because the payload's `repository.owner.login` is `attacker` and the signature matches `attacker`'s real webhook secret. `StatusHandler#process`'s unscoped `Commit.where(sha:)` then matches the commit row(s) belonging to **any** stack with that sha, including `shopify/shipit-engine`'s, and writes the attacker-controlled `state`/`description`/`context` onto it.

None of the existing guards catch this: `verify_signature` validates the claimed org, not the mutated resource's owning org; the `ExplicitParameters` schema in `StatusHandler.params` only validates payload shape (`sha`, `state`, etc.), not ownership; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` check on this unauthenticated webhook path (webhooks are inherently unauthenticated except for HMAC-per-org verification).

### Impact Explanation
A payload correctly authenticated for one tenant (`attacker`) mutates another tenant's (`shopify/shipit-engine`) `Commit`/`Status` records. This can flip `Commit#deployable?` from false to true (or vice versa) by injecting a fabricated `success` status or blocking status, potentially enabling an unauthorized deploy of a commit that never actually passed CI, or blocking a legitimate deploy (denial-of-service is out of scope, but the deploy-enabling direction is Critical: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). The attack is repeatable against any repository/stack whose commit history intersects with a repository controlled by the attacker (most straightforwardly, any public fork relationship), across every tenant sharing the same Shipit instance.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment where the attacker's own GitHub org/repo is a legitimately onboarded tenant (documented as a supported configuration), (b) the target repository/stack to share at least one commit SHA with a repo the attacker controls (trivially achievable via forking, since SHAs are content-derived and forks retain identical commit objects for unmodified history), and (c) the attacker's ability to get GitHub to deliver a real `status` webhook for their own repo (fully within an unprivileged GitHub repo owner's control, e.g. via their own CI integration). No Shipit secret, session, or API token is needed. This is low-cost and fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and similarly for other handlers using bare `Commit.where(sha:)`, e.g. `check_suite`) to the organization that authenticated the webhook, e.g. join through `stack.repository` and filter `owner: repository_owner`, or pass the verified `repository_owner`/`repository.full_name` into the handler and require it match `commit.stack.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, using `ActionDispatch::IntegrationTest`):
1. Create two `GithubHook`/org fixtures (e.g. `shopify` and `attacker`) each with a distinct real `webhook_secret` configured via `Shipit.stubs(:github)` or a `secrets_double_github_app.yml`-style config.
2. Create `stack_a` owned by `shopify/shipit-engine` with `commit_a` (`sha: 'deadbeef...'`), and `stack_b` owned by `attacker/evil-repo` with `commit_b` sharing the identical `sha: 'deadbeef...'`.
3. POST `/webhooks` with `X-Github-Event: status`, body `{"sha": "deadbeef...", "state": "success", "repository": {"owner": {"login": "attacker"}}}`, signed with `attacker`'s real secret (`X-Hub-Signature` computed via `OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)`).
4. Assert `response.status == 200`.
5. Assert `commit_a.statuses.reload.last.state == 'success'` even though the request's verifying organization (`repository_owner == 'attacker'`) does not equal `commit_a.stack.repository.owner` (`'shopify'`), proving the cross-tenant write:
```ruby
assert_equal 'attacker', repository_owner_from_payload
assert_equal 'shopify', commit_a.stack.repository.owner
assert_equal 'success', commit_a.reload.statuses.last.state  # written despite mismatch
```
