### Title
Webhook signing-organization is not bound to the repository/commit acted upon, allowing cross-tenant status/commit injection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on the `repository_owner` field read directly out of the same unauthenticated JSON body it's about to validate: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

The signature is thus proven only for the *organization named in `repository.owner.login`*, using that organization's own `webhook_secret` from the multi-tenant `github:` config. [3](#0-2) 

However, downstream handlers do **not** re-derive the acted-upon repository/stack from that same `repository.owner.login` field. `Handler#repository_name` uses a completely separate field, `repository.full_name`, to look up the target `Repository`/`Stack`: [4](#0-3) 

Worse, `StatusHandler#process` doesn't scope by repository at all — it looks up commits globally by `sha` across the entire Shipit instance and creates a GitHub status on every match: [5](#0-4) 

### Finding Description
The binding that should hold is:
`organization whose webhook_secret validated the signature == organization/repository whose data (commits, statuses, refs) is written`.

In this multi-tenant configuration (`Shipit.github(organization:)`, `github_app_config`), each onboarded GitHub organization has its own independent `webhook_secret`. [3](#0-2) 

A tenant that legitimately administers Organization A (and therefore legitimately knows Org A's `webhook_secret`, since they configure the same secret on both the GitHub App webhook settings and in Shipit's `secrets.yml` for their org) can craft an arbitrary raw JSON body, set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` looks up and validates against Org A's secret, and HMAC-sign it correctly — while setting every other payload field (`repository.full_name`, `sha`, `state`, `ref`, `after`, etc.) to reference a completely different, unrelated Organization B's repository/stack that they do not administer.

Because `verify_signature` never checks that `repository.owner.login` equals `repository.full_name`'s owner, and because `StatusHandler` doesn't scope by repository at all, this signed-but-mismatched payload is accepted and processed against Org B's data:
- `status` events create arbitrary `Commit::Status` rows for any matching `sha` in the whole instance, regardless of which org the signature was verified for. [6](#0-5) 
- `push`/`check_suite`/`pull_request` handlers resolve the target `Stack` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, a field disjoint from the one used to pick the verifying secret. [4](#0-3) [7](#0-6) 

This is the same class of defect as the external report: the value that is cryptographically verified (`repository_owner` → secret) is not the value that is actually consumed to determine which resource gets mutated (`repository.full_name` / bare `sha`) — an organization-authenticated-vs-repository-written mismatch.

### Impact Explanation
A tenant admin of one onboarded organization can forge webhook events that fabricate GitHub commit statuses (`success`/`failure`) for arbitrary commits belonging to a completely different organization's stacks they have no access to. Since commit status directly feeds `deployable?`/`schedule_merges` logic and continuous delivery scheduling, this can be used to mark an unreviewed or malicious commit "green" and trigger an unauthorized deploy/merge in a stack the attacker does not control — a cross-tenant, cross-repository write and unauthorized-deploy scenario, matching the Critical bar in scope.

### Likelihood Explanation
Requires the attacker to already be a legitimate, but only single-tenant, onboarded organization admin with a valid `webhook_secret` for their own org — no GitHub repository write access to the victim org, no Shipit session, and no other credential is needed. Since the secret is per-organization by design and the signature check does not bind the verified organization to the field the handlers actually consume, the attack is a straightforward payload-crafting exercise (no cryptographic break needed) as soon as multiple organizations are configured under one Shipit instance.

### Recommendation
In `WebhooksController#verify_signature`, after validating the signature, assert that the organization used to select the secret is the same organization referenced by every payload field the handlers will consume (`repository.full_name`'s owner, or reject mismatched `organization.login`/`repository.owner.login`). Additionally, `StatusHandler#process` should scope the `Commit` lookup by the repository resolved from the verified organization/`repository.full_name`, not by bare `sha` alone, mirroring the scoping already done by `PushHandler`/`Handler#stacks`.

### Proof of Concept
1. Attacker administers `OrgA`, onboarded in Shipit's multi-org `github:` config with `webhook_secret: SECRET_A`. They legitimately know `SECRET_A`.
2. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "sha": "<sha_of_unreviewed_commit_in_OrgB_stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `sha1=HMAC-SHA1(SECRET_A, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates the signature against `SECRET_A` — succeeds. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, applying `state: success` to the target commit in `OrgB`'s stack — with no check that this commit belongs to `OrgA`. [5](#0-4) 
6. If `OrgB`'s stack has continuous delivery enabled, the forged green status can trigger an automatic deploy of that commit.

Note: I was unable to fully verify `Commit#create_status_from_github!` and the exact `deployable?`/continuous-delivery gating logic in this session (the read calls for those files did not return before the iteration limit), so the final "auto-deploy" step of the chain is inferred from `Stack#trigger_continuous_delivery`/`schedule_merges` wiring seen in `app/models/shipit/stack.rb` rather than confirmed line-by-line in the status/commit model; a follow-up read of `app/models/shipit/commit.rb` and `app/models/shipit/commit_status.rb` (or equivalent) is recommended to confirm the exact deploy-triggering condition.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
