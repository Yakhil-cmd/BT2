### Title
Cross-tenant Team hijack via `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook only against the GitHub App configured for the organization named in the payload (`repository.owner.login` or, if absent, `organization.login`), which for this event is attacker-controlled. `MembershipHandler#find_or_create_team!` then looks up the `Team` record purely by `github_id`, with no check that the verified organization actually owns that `Team` row, so an attacker whose own org's signature verifies can mutate a `Team` belonging to a different organization.

### Finding Description
The broken binding is: `organization_that_signed_the_request` (derived from `repository_owner` used by `Shipit.github(organization: repository_owner)` in `verify_signature`) must equal `team.organization` (the tenant that owns the mutated `Team` row) before any membership mutation is allowed. The code never enforces this equality.

Path:
1. `app/controllers/shipit/webhooks_controller.rb:24-49` — `verify_signature` computes `repository_owner` via `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`), which for a `membership` event without a `repository` key falls back to `params.dig('organization', 'login')`. It then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. If the attacker sends `organization.login = 'attacker-org'` and that org has its own configured GitHub App/secret in Shipit's multi-tenant `github:` config (as in `test/dummy/config/secrets_double_github_app.yml`), the signature check passes legitimately against the attacker's own secret.
2. `Webhooks.for_event('membership')` dispatches to `Handlers::MembershipHandler` (`app/models/shipit/webhooks.rb:20`).
3. `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`) calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; team.github_team = params.team }`. Because `find_or_create_by!` first performs a `find_by(github_id: ...)`, if a `Team` row already exists (e.g., belonging to `shopify`, with `github_id` equal to the attacker-supplied `team.id`), that existing row is returned unmodified — the block (which would at least set `organization` on create) never runs, and no comparison between the pre-existing `team.organization` (`shopify`) and the verified `repository_owner`/`params.organization.login` (`attacker-org`) is performed anywhere.
4. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then calls `team.add_member(member)` for `action == 'added'`, where `member = User.find_or_create_by_login!(params.member.login)` — the attacker's own real GitHub login. This writes a `Membership` row linking the attacker's `User` to the `shopify`-owned `Team`.

No other guard intervenes: `drop_unhandled_event` only checks handler registration, the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence (not organization ownership), and `Team` has no validation tying `github_id` uniqueness to `organization` (the DB unique index is on `[organization, slug]`, not on `github_id`).

If `Shipit.github_teams` includes that same `Team` (precondition given), `User#authorized?` (`app/models/shipit/user.rb:80-82`) becomes true for the attacker's account (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), since the attacker is now a member of that team.

### Impact Explanation
The attacker, who controls only their own GitHub organization's signed webhooks, can write a `Membership` row that grants their own Shipit `User` record membership of a `Team` belonging to an entirely different, unrelated organization (`shopify`). If that `Team` is part of `Shipit.github_teams`, this directly flips `User#authorized?` to true for the attacker, granting them access to the whole Shipit instance (viewing stacks, deploying, etc.) despite never being a legitimate member of `shopify`'s GitHub org or team. This matches the "High - escalation into `Shipit.github_teams` authorization" category. It is repeatable against any `Team` row whose `github_id` the attacker can guess or enumerate (team IDs are small sequential integers on GitHub, easily discoverable or brute-forceable), and the blast radius spans all tenants configured on a multi-org Shipit deployment.

### Likelihood Explanation
Exploitation requires: (1) a Shipit deployment configured for multiple GitHub organizations, each with its own `github_app`/`webhook_secret` (a supported, documented configuration, e.g. `test/dummy/config/secrets_double_github_app.yml`); (2) the attacker owns/administers one of those configured organizations (or any org that Shipit is configured to trust, however minimal); (3) an existing `Team` row for the victim organization with a known `github_id`. Given these, the attack costs only a single crafted, self-signed HTTP POST to `/webhooks` — no secrets from the victim organization are needed. Likelihood is moderate-to-high in any multi-tenant Shipit deployment; it is not exploitable in the common single-org deployment since then the attacker would have no way to get their own webhook signature accepted at all.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and explicitly reject the payload (or short-circuit without mutation) when an existing `Team` with the given `github_id` has a different `organization` than `params.organization.login`. Also validate that `repository_owner`/`params.organization.login` used for signature verification matches the organization that will be mutated, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login.downcase
    raise ArgumentError, "Team #{params.team.id} organization mismatch"
  end
  team || Team.create!(github_team: params.team, organization: params.organization.login)
end
```
Additionally, consider adding a DB-level uniqueness constraint or validation ensuring `github_id` cannot be shared or reassigned across differing `organization` values.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (illustrative)
test "membership event cannot hijack a Team belonging to another organization" do
  victim_team = shipit_teams(:shopify_developers) # organization == 'shopify'
  Shipit.stubs(:github_teams).returns([victim_team])

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker_login' }
  }

  assert_equal 'shopify', victim_team.organization # binding LHS before

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  victim_team.reload
  attacker = Shipit::User.find_by(login: 'attacker_login')

  # Binding should hold: mutating org must equal team's owning org.
  # Vulnerable: it does not.
  assert_equal 'shopify', victim_team.organization # unchanged owning org
  refute_nil attacker
  assert_includes victim_team.members, attacker # membership was written by non-owning org
  assert attacker.authorized?, "attacker gains Shipit.github_teams authorization for 'shopify' team"
end
```
This test posts (or directly invokes the handler with) a payload whose `organization.login` differs from the pre-existing `Team#organization`, and asserts that a `Membership` is created and `User#authorized?` becomes true — demonstrating the cross-tenant authorization escalation.
