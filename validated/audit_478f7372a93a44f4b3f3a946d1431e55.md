### Title
`roll-sbtc` accepts a `(contract-call? ... transfer ...)` success without checking the returned boolean, allowing sBTC bond accounting to be inflated without a matching on-chain transfer - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`pox-5.clar`'s `roll-sbtc` helper moves the sBTC delta between a staker and the contract whenever a bond's committed sBTC amount changes, and updates `total-sbtc-staked` to reflect the new committed amount. The SIP-010 `transfer` call is wrapped only in `try!`, which unwraps a `(response bool uint)` and continues as long as the outer response is `(ok ...)` - it never asserts that the inner boolean is `true`.

### Finding Description
In `roll-sbtc`, when a staker increases their committed sBTC (`new-sbtc > old-sbtc`), the contract pulls the delta from the staker: [1](#0-0) 
and unconditionally increments `total-sbtc-staked` by `delta` regardless of the boolean payload of the `transfer` response - only the outer `(response bool uint)` being `ok` is checked via `try!`. The same pattern (no boolean check, only `try!`) is repeated in `transfer-from-reserve` and `transfer-stranded-rewards`: [2](#0-1) [3](#0-2) 

This is the direct Clarity analog of the H-01 report: in Solidity, `transferFrom` can return `false` on failure without reverting (EURS/BAT), and code that only checks "did the call not throw" rather than "did the boolean say success" is exploitable. In Clarity, a SIP-010-conformant `transfer` function may likewise return `(ok false)` for a failed transfer (e.g., insufficient balance, paused token, blocklist) instead of an `(err ...)`, since SIP-010 does not mandate that failures be represented as `err` - it only mandates a `(response bool uint)` shape. `try!` only inspects whether the response is `err` (aborting) or `ok` (continuing); it does not assert the boolean is `true`. Because `pox_5_sbtc_contract` is explicitly configurable per node on non-mainnet deployments (and mainnet's is fixed but still an externally-controlled contract), if the configured sBTC token ever returns `(ok false)` for a failed transfer, `roll-sbtc` would still bump `total-sbtc-staked` and the staker's per-cycle sBTC weighting up by `delta`, without any sBTC ever actually moving into the contract: [4](#0-3) 

### Impact Explanation
This breaks the equality that `total-sbtc-staked` (and the per-staker/per-signer sBTC-weighted stake used for signing weight / reward-slot calculations) must equal actual sBTC custodied by pox-5. If the boolean is silently ignored, a staker's committed sBTC can be inflated without a corresponding real transfer, letting them claim signing weight or reward slots exceeding the sBTC value they actually locked - matching the "signing weight or reward slots exceeding locked value" High-impact category.

### Likelihood Explanation
Exploitability is contingent on the actual deployed sBTC contract returning `(ok false)` instead of erring on failed transfers - which is not proven to be true of the canonical mainnet sBTC token (out of scope per the rules unless pox-5's own handling is the flaw). The root cause identified here is squarely in pox-5's `roll-sbtc`/`transfer-from-reserve`/`transfer-stranded-rewards` code: they do not defensively assert the boolean payload of the `transfer` call, unlike the ERC20 best practice of checking `success`. This is a real gap in pox-5's own code, but requires an sBTC-token-side "soft failure" (or a future/alternate sBTC token configuration on non-mainnet) to be triggered - a defensive-coding oversight, not a directly-provable exploit against the canonical sBTC contract as it exists today.

### Recommendation
Assert the boolean payload of every sBTC `transfer` call in `pox-5.clar` (`roll-sbtc`, `transfer-from-reserve`, `transfer-stranded-rewards`) instead of relying solely on `try!`, e.g. `(asserts! (try! (contract-call? ... transfer ...)) ERR_SBTC_TRANSFER_FAILED)`, so that a token returning `(ok false)` cannot silently pass as a successful transfer.

### Proof of Concept
1. Deploy (or configure via `pox_5_sbtc_contract`, on a non-mainnet chain-id) a SIP-010-conformant sBTC token whose `transfer` returns `(ok false)` instead of `(err ...)` when the caller's balance is insufficient (a legal SIP-010 implementation, analogous to EURS/BAT).
2. A staker with insufficient sBTC balance calls a bond-registration path that invokes `roll-sbtc` with `new-sbtc > old-sbtc = 0`.
3. `(try! (contract-call? sbtc-token transfer delta tx-sender current-contract none))` returns `(ok false)`; `try!` unwraps to `false` and continues. [1](#0-0) 
4. `total-sbtc-staked` and the staker's per-cycle sBTC-weighted shares are incremented by `delta`, even though no sBTC ever left the staker's wallet, inflating the staker's/signer's on-record sBTC commitment relative to actual custodied sBTC.

/// Set the configured PoX-5 sBTC token contract id. Call once during node
/// startup from the run-loop, with the value parsed out of `NodeConfig`.
pub fn set_pox_5_sbtc_contract(contract_id: Option<QualifiedContractIdentifier>) {
    *POX_5_SBTC_CONTRACT.write().unwrap() = contract_id;
}

pub fn pox_5_sbtc_contract(is_mainnet: bool) -> QualifiedContractIdentifier {
    if is_mainnet {
        return SBTC_TOKEN_MAINNET_CONTRACT_ID.clone();
    }
    let contract_id = POX_5_SBTC_CONTRACT.read().unwrap().clone();
    if let Some(contract_id) = contract_id {
        contract_id
    } else {
        SBTC_TOKEN_TESTNET_CONTRACT_ID.clone()
    }
}
