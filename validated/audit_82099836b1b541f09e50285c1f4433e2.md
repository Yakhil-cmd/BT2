### Title
System vote weight is calculated from the voter's current balance at count time, not the balance held while voting, letting an attacker rent balance to steer `op_list`/fee-parameter governance - (File: `main_chain.js`)

### Summary
`countVotes()` in `main_chain.js` determines the outcome of `system_vote` polls (which set `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) by weighting each voter's most-recent vote with that address's **current** stable-good balance at the moment the vote count is triggered, rather than the balance the address actually held while its vote was cast and remained outstanding. This mirrors the Alchemix `Voter.sol` bug class: a value used to compute a weighted outcome (bribe eligibility there, vote weight here) is snapshotted at a point in time decoupled from the actual window of participation, letting an attacker "rent" the qualifying state just before the snapshot is taken.

### Finding Description
A `system_vote` message only requires posting a unit from any address; it does not lock or require any balance at the time of voting [1](#0-0) . The vote is persisted with just `address`, `subject`, `value`, `timestamp` [2](#0-1) .

Any user can also post a `system_vote_count` message for a subject; validation only checks that the subject name is one of the known ones and that the message is not from an AA [3](#0-2) . Once such a message stabilizes, `countVotes()` runs for that subject [4](#0-3) .

`countVotes()` collects every address that has ever cast a `system_vote` for the subject, then computes each address's *current* stable-good balance: [5](#0-4) 

This balance table (`voter_balances`) is then joined against the historical vote records (filtered only by `timestamp>=since_timestamp`, the vote's original cast time) to compute weighted totals used to decide `op_list` or the numerical system variables: [6](#0-5) [7](#0-6) 

Because the weight is read at count time rather than being fixed to the balance actually held throughout the vote's active window, an attacker can:
1. Cast a `system_vote` from an address holding little or no balance (free, since votes aren't balance-gated).
2. Wait/observe until conditions are favorable, then transfer a large stable balance into that same voting address.
3. Immediately post (or wait for someone else to post) `system_vote_count`, causing `countVotes()` to stabilize and read the now-inflated balance, giving the stale vote outsized weight in the outcome.
4. Move the balance back out afterward — it was only needed to be a stable-good output at the moment the counting MCI stabilized, not throughout the vote.

This is structurally the same defect as the reported bug: the weighting checkpoint (`Voter.sol`'s bribe `balanceOf` from `Bribe.sol#withdraw()`) is taken at a time inconsistent with the actual participation window (`lastVoted`), letting the attacker claim/influence an outcome without holding the qualifying stake during the relevant period.

### Impact Explanation
`countVotes()` directly writes into `system_vars`, which governs `op_list` (order providers used for main-chain determination), `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` — core consensus and fee parameters [8](#0-7) . An attacker who can cheaply inflate momentary balance to swing these votes can install malicious/uncooperative order providers or push fee/threshold parameters to extremes, degrading the network's ability to reliably confirm and validate new units, which matches the "node disagreement on validity or stability / network unable to confirm new units" impact class.

### Likelihood Explanation
Casting a `system_vote` costs only the fee for a normal unit and requires no balance lock, and `system_vote_count` can be triggered by any unprivileged address [9](#0-8) . The only requirement is having enough capital, even momentarily, to be the majority-stake voter among those who bothered to vote for a subject; since votes for niche subjects (e.g., `tps_fee_multiplier`) may have few participants, temporarily concentrating balance is a low bar. The existence of `tools/compare_vote_balances.js`, built specifically to audit voter-balance computation discrepancies, indicates the project itself has already identified this balance-calculation logic as fragile/bug-prone [10](#0-9) .

### Recommendation
Snapshot each voter's balance at (or shortly after) the time their `system_vote` is cast and stored, rather than re-reading the address's current balance at count time; alternatively, require the vote weight to be the minimum balance held continuously from `system_votes.timestamp` through the counting MCI, so momentary balance transfers cannot inflate stale votes.

### Proof of Concept
Not directly executable from the codebase index alone (requires a running multi-node test harness to demonstrate the stabilization timing); conceptually:
1. Address A (near-zero balance) posts `system_vote` for `tps_fee_multiplier` with an extreme value.
2. Before any `system_vote_count` for that subject stabilizes, attacker transfers a very large stable balance into address A.
3. Attacker posts `system_vote_count` for `tps_fee_multiplier`; once it stabilizes, `countVotes()` reads A's balance from `outputs`/`units` at that moment [11](#0-10)  and weights A's stale vote by the inflated balance, potentially deciding the median value.
4. Attacker moves the balance out of A immediately after stabilization.
