### Title
Ambiguous unstable data-feed candidates cause an uncaught fatal error, freezing AA logic that reads instant oracle prices - ([File: data_feeds.js])

### Summary
BonqDAO was drained because Bonq's collateral valuation used Tellor's *instant*, undisputed price submission directly inside the same borrow/liquidate transaction, with no staleness or agreement check on which value to trust. The ocore analog is in the AA-oracle read path: when an AA formula evaluates `data_feed[[oracles=...]]` (or `in_data_feed[[...]]`), the value is read from `storage.assocUnstableMessages` — i.e., from units that are posted but **not yet stable** — via `readDataFeedValue()` in `data_feeds.js`. If more than one oracle unit (from the same set of `oracles` addresses referenced by the AA) posts a feed update for the same `feed_name` and both units land at the exact same DAG level with the same `latest_included_mc_index`, the code cannot deterministically order them and hits:

```js
throw Error("can't sort candidates "+a+" and "+b);
``` [1](#0-0) 

### Finding Description
`readDataFeedValue()` builds a list of oracle-posted candidates from currently unstable units authored by any of the `arrAddresses` referenced by the AA's `oracles=` parameter: [2](#0-1) 

When more than one candidate exists, it sorts them by `latest_included_mc_index` then by `level`, and — critically — only allows a tie-break "sort randomly" fallback when `bIncludeAllUnstable` is true (i.e., `unstable_opts === 'all_unstable'`). For the normal AA-oracle read path, `unstable_opts` is passed as the boolean `bAA` (not the string `'all_unstable'`), so `bIncludeAllUnstable` is `false`: [3](#0-2) 

If two units — each authored by one of the `oracles` addresses the AA trusts, each posting the same `feed_name` — are unstable at the same time and share the same `latest_included_mc_index` and the same `level` (a normal occurrence for sibling units built on the same parents), the sort comparator throws a synchronous `Error`. This is invoked from `formula/evaluation.js`'s `data_feed` opcode handler while an AA is computing its response to a trigger: [4](#0-3) 

This throw is not a formula-level "bad value" (`cb(false)`/`setFatalError`) that the AA engine gracefully bounces — it is a raw JS exception thrown from inside `Array.prototype.sort`'s comparator, propagating synchronously out of `readDataFeedValue`, unlike the rest of the codebase's convention of returning errors through callbacks. Any single unprivileged unit poster who controls (or colludes with) two of the addresses listed in an AA's `oracles=` string can trigger this condition by crafting two sibling data-feed-posting units at the same level, then sending a trigger to the AA that reads that feed — exactly mirroring the BonqDAO root cause of trusting an *instantaneous, unvalidated, single-round* oracle read with no tie-break/agreement protocol, except here the failure mode is a crash of the read path instead of a manipulable price.

### Impact Explanation
Any AA that relies on `data_feed[[oracles='addr1:addr2', feed_name=...]]` with multiple trusted oracle addresses (a common pattern recommended precisely to avoid single-oracle manipulation, as BonqDAO's post-mortem suggests moving to multi-source oracles) is exposed: an attacker who can post units from two of those addresses (e.g., because the AA owner's multi-oracle setup includes an address the attacker also controls, or a compromised/malicious oracle deliberately colludes with the attacker's own address which is also whitelisted) can force the read to throw whenever the AA processes a trigger during the unstable window. Since AA response computation aborts on this uncaught error, the trigger either bounces or fails outright, denying the AA's users their expected functionality (e.g., withdrawal/liquidation/mint logic gated on that price feed) for as long as the ambiguous unstable state persists — a fund-freezing condition on the specific AA, not a general network DoS.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control or collude with (at least) two of the oracle addresses an AA actually references, and to time two data-feed unit submissions so they land at an identical DAG level and identical `latest_included_mc_index` while unstable. This is achievable by a determined attacker building both units on the same set of parent units (a normal thing to do deliberately), then quickly sending the AA trigger before the feed units stabilize.

### Recommendation
In `readDataFeedValue()` (`data_feeds.js`), do not `throw` on ambiguous same-level, same-mci candidates when `bIncludeAllUnstable` is false; instead resolve the tie deterministically (e.g., by unit hash or by failing the read gracefully via `objResult.bAbortedBecauseOfSeveral = true`), mirroring the `ifseveral==='abort'` path so the AA formula can defensively branch instead of crashing.

### Proof of Concept
1. Deploy or reference an AA whose `oscript` calls `data_feed[[oracles='OracleA:OracleB', feed_name='PRICE']]` for critical logic (mint/borrow/liquidate), following the "use multiple oracles" mitigation.
2. Attacker controls addresses `OracleA` and `OracleB` (or colludes with an oracle operator).
3. Attacker crafts two units, one authored by `OracleA` and one by `OracleB`, both built on identical parent units so they share the same `level`, each containing a `data_feed` message with `feed_name: 'PRICE'` and any value, and broadcasts them together so both are included at the same `latest_included_mc_index` while still unstable.
4. Attacker (or anyone) sends a trigger unit to the AA before these two units stabilize.
5. During response computation, `evaluation.js`'s `data_feed` case calls `dataFeeds.readDataFeedValue(...)` → `arrCandidates` ends up with 2 entries with equal `latest_included_mc_index` and equal `level` → `arrCandidates.sort(...)` throws `Error("can't sort candidates ...")`, aborting the AA's response and freezing the intended action for the duration of the unstable window.
