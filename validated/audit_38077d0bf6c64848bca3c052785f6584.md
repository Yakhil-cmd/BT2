### Title
RAY value overflow during index accrual permanently freezes a high-utilization whale market - (File: common/src/rates/scaling.rs)

### Summary
Interest accrual can panic when a market’s scaled RAY balance multiplied by its index exceeds `i128::MAX`. The panic occurs before the borrow-index cap is reached, so every later operation that syncs the market fails with `MathOverflow`, permanently freezing withdrawals, repayments, liquidations, and subsequent index updates absent an upgrade. [1](#0-0) [2](#0-1) 

### Finding Description
`scaled_to_original` performs `scaled * index / RAY` through `Ray::mul`, which panics with `MathOverflow` when the result does not fit `i128`. `accrue_step` calls it on total borrowed and supplied shares before calculating utilization, so a sufficiently large market whose borrow or supply index has grown enough makes accrual fail. [3](#0-2) [4](#0-3) 

The controller exposes this through permissionless `update_indexes(caller, assets)`, while pool market operations call `global_sync` through `synced_market` before applying repayments, withdrawals, borrows, liquidations, or other mutations. Once the overflow threshold is crossed, those paths repeatedly hit the same panic before they can reduce the offending balances. [5](#0-4) [6](#0-5) 

The overflow can occur before `MAX_BORROW_INDEX_RAY` is reached because `update_borrow_index` caps the index only after multiplying it by the new interest factor, while utilization is calculated from the possibly overflowing unscaled value first. The repository’s regression test demonstrates a valid 18-decimal market at 98% utilization reaching this cliff while `borrow_index < MAX_BORROW_INDEX_RAY`. [7](#0-6) [8](#0-7) 

### Impact Explanation
All user funds and debt positions in the affected market become inaccessible through the intended controller paths. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot clear positions, keepers cannot update indexes, and revenue or recapitalization paths that accrue first also fail. This is permanent freezing of funds unless governance deploys a code upgrade. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The condition requires a very large high-decimal market, a configured cap large enough to admit it, and sustained high utilization on a steep borrow-rate curve. Those parameters are within the protocol’s permitted domain: cap validation only bounds the asset’s RAY representation to `i128`, while the demonstrated 175% APR stress curve is below the configured maximum-rate domain. An unprivileged actor can create the market state through ordinary `supply` and `borrow` calls and trigger the eventual failure through permissionless `update_indexes`; attacker capital requirements make this Medium rather than Critical or High. [11](#0-10) [12](#0-11) 

### Recommendation
Make the unscale calculations saturating or otherwise prevent the market from crossing the representable RAY-value boundary before the index cap. In particular, use a non-panicking conversion for utilization inputs, clamp utilization inputs to a defined maximum, or enforce a stricter market cap derived from the maximum permitted index and token decimals. Add a regression test proving that after the demonstrated state reaches the boundary, `update_indexes`, `repay`, `withdraw`, and liquidation do not all fail with `MathOverflow`. [13](#0-12) [14](#0-13) 

### Proof of Concept
A single unprivileged signer can create two owned accounts, supply the listed debt asset to one and sufficient listed collateral to the other, borrow the target asset at high utilization, then call `update_indexes` as ledger time advances:

```text
supply(caller, account_id=0, spoke_id, [(target_asset, 1_000_000_000 * 10^18)])
supply(caller, account_id=0, spoke_id, [(collateral_asset, sufficient_collateral)])
borrow(caller, collateral_account_id,
       [(target_asset, 980_000_000 * 10^18)], None)

repeat as ledger time advances:
    update_indexes(caller, [target_asset])
```

For an 18-decimal asset, `1e27` base units rescale to approximately `1e36` RAY shares; once an index exceeds roughly `i128::MAX / 1e36 ≈ 170`, the next accrual panics inside `scaled_to_original`. The existing test executes this scenario, observes `MathOverflow`, confirms the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, and confirms subsequent withdraw and repay attempts fail with the same error. [15](#0-14)

```rust
/// Converts a scaled `Ray` amount to its original (unscaled) value by
/// multiplying by `index`, rounding half up.
pub fn scaled_to_original(env: &Env, scaled: Ray, index: Ray) -> Ray {
    scaled.mul(env, index)
}

/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
