### Title
RAY total-value overflow permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
Severity: High. A sufficiently large market can be pushed past the representable `i128` RAY-value domain during permissionless index accrual, after which market operations that synchronize interest revert with `MathOverflow`. `Controller::update_indexes` is permissionless and forwards the caller-selected `HubAssetKey` list to the pool, while `accrue_step` computes `scaled_to_original(borrowed, borrow_index)` before applying the borrow-index ceiling. [1](#0-0) [2](#0-1) 

### Finding Description
`scaled_to_original` evaluates `scaled * index / RAY` through `Ray::mul`, and `mul_div_half_up` panics with `GenericError::MathOverflow` when the exact result does not fit in `i128`. [3](#0-2) [4](#0-3) [5](#0-4) 

`interest::global_sync` calls `accrue_step` for every elapsed accrual chunk, and every synced market operation loads the cache through `ops::synced_market` before performing its mutation. [6](#0-5) [7](#0-6) 

The configured asset cap only ensures that the initial token-to-RAY conversion fits in `i128`; `max_cap_for_decimals` permits an 18-decimal asset amount approaching `i128::MAX / 10^9`, whose scaled value is already close to `i128::MAX`. [8](#0-7) [9](#0-8) 

Once `borrowed` or `supplied` is large enough, ordinary index growth makes `scaled * index / RAY` unrepresentable before the fixed `MAX_BORROW_INDEX_RAY` ceiling can protect the multiplication in `calculate_supplier_rewards`. [10](#0-9) [11](#0-10) 

### Impact Explanation
The affected market becomes permanently frozen because `update_indexes`, withdrawal, repayment, borrowing, liquidation settlement, revenue processing, and other operations that accrue the market all execute the same overflowing multiplication and revert. [12](#0-11) [13](#0-12) 

Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot settle positions through the affected market, which constitutes permanent freezing of user funds absent a privileged contract upgrade. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
A single unprivileged caller can create one account that supplies the target asset and another account that supplies collateral and borrows the target asset, keeping utilization high while interest accrues. [16](#0-15) 

The caller can then invoke `update_indexes(caller, assets)` with `assets = [HubAssetKey { hub_id, asset }]`; no role or governance operation is required because the endpoint is explicitly permissionless and only requires caller authorization. [1](#0-0) [17](#0-16) 

Exploitability is conditional on the listed market's legitimate caps and asset supply permitting scaled totals close enough to `i128::MAX` that index growth crosses the multiplication boundary, but the code admits such caps and the repository's regression test demonstrates the resulting `MathOverflow` freeze. [9](#0-8) [18](#0-17) 

### Recommendation
Track a per-market representable-index ceiling for both `borrowed` and `supplied`, clamp accrual before any `scaled * index / RAY` evaluation, and stop interest accrual at that ceiling rather than reverting. Admission checks should also reject new supply or borrow shares whenever the resulting total cannot be represented at the applicable index ceiling. Add regression coverage showing that withdrawals, repayments, liquidations, and recapitalization remain executable after the ceiling is reached. [19](#0-18) [11](#0-10) 

### Proof of Concept
```text
target = HubAssetKey { hub_id, asset: asset_18_decimals };

// Same caller creates two accounts.
account_supply = supply(caller, 0, spoke_id, [(target, S)]);
account_borrow = supply(caller, 0, spoke_id, [(collateral_asset, C)]);
borrow(caller, account_borrow, [(target, B)], Some(caller));

// Keep the borrowed share large and let ledger time accrue repeatedly.
update_indexes(caller, [target]);

// After the representable RAY-value boundary is crossed:
update_indexes(caller, [target]);                 // MathOverflow
withdraw(caller, account_supply, [(target, 1)]); // MathOverflow
repay(caller, account_borrow, [(target, 1)]);    // MathOverflow
```

The existing test seeds a large 18-decimal market, repeatedly advances time and calls `update_indexes`, observes `MathOverflow` before `MAX_BORROW_INDEX_RAY`, and confirms that withdrawal and repayment hit the same overflow. [18](#0-17)

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
