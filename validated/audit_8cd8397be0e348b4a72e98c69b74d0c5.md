### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The zkASM ecrecover bug is a class of "the security check validates against the wrong scope/value than the one actually acted upon." In shipit-engine, the analogous flaw is in the GitHub `status` webhook handler: the webhook signature is verified against the GitHub organization/app that the *payload claims* to belong to, but the handler that processes the event never re-checks that the target commit actually belongs to a stack under that same repository. It performs a global, repository-unscoped lookup by commit SHA.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the signature against using the untrusted, not-yet-verified payload field `repository_owner`: [1](#0-0) [2](#0-1) 

Once the signature is validated for *that organization*, the raw payload is fanned out to all registered handlers for the event type: [3](#0-2) 

Most handlers correctly re-derive scope from the payload's `repository.full_name` before acting, via the base `Handler#stacks` helper: [4](#0-3) 
For example `PushHandler` scopes to `stacks.not_archived.where(branch:)` [5](#0-4)  and `CheckSuiteHandler` scopes to `stacks.where(branch: ...)` [6](#0-5) .

`StatusHandler`, however, ignores the `stacks` scoping entirely and looks up commits **globally by SHA across the whole installation**, then writes an attacker-controlled status onto every match: [7](#0-6) 

The `state`, `description`, `target_url`, `context`, and `created_at` fields are taken verbatim from the payload and persisted via `Commit#create_status_from_github!` → `Status.replicate_from_github!`: [8](#0-7) [9](#0-8) 

The broken binding, stated as an equality that should hold but does not:
`organization whose webhook_secret authenticated the request == repository/stack that the resulting Status write targets`

Because Git commit SHAs are content-addressed and preserved across forks, an attacker who forks a target public repository (or otherwise produces a repo sharing a commit SHA with a Shipit-tracked stack) can send a legitimate GitHub `status` webhook for their own fork, correctly signed with their own org's `webhook_secret` (this passes `verify_signature`, which only checks that *some* configured org's secret matches — it does not check that the org owns the *commit being modified*). `StatusHandler` then matches that SHA against `Commit.where(sha: ...)` with no repository/stack filter, and writes a forged status (e.g. `state: 'success'`, `context: '<required-context>'`) onto the victim stack's commit.

### Impact Explanation
A forged "success" status on a required CI context can flip a victim commit's `deployable?`/blocking state, since `required_statuses`/`blocking_statuses` from the victim stack's `shipit.yml` are evaluated using exactly these `Status` rows, and success statuses can trigger `ProcessMergeRequestsJob`/continuous delivery. This lets an attacker who controls no credentials for the victim organization — only a legitimate webhook signature for an unrelated org configured in the same multi-tenant Shipit instance — unblock or trigger an unauthorized deploy on a completely different organization's stack. This matches the accepted "unauthorized deploy" / cross-repository-write impact class.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub orgs (a documented, supported configuration in `docs/setup.md` / `config/secrets.development.example.yml`), (2) at least one commit SHA shared between an org the attacker controls and a victim stack's repository (trivially achievable by forking a public repo and pushing/triggering a `status` webhook on a shared ancestor commit), and (3) no other authentication is required — the attacker's own legitimate app installation produces a validly signed webhook. This is a realistic scenario for any Shipit deployment serving several GitHub organizations, which the project explicitly documents as a supported topology.

### Recommendation
Scope `StatusHandler#process` to the repository asserted by the payload before writing any status, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
i.e., replace the global `Commit.where(sha: params.sha)` with a lookup restricted to `stacks` (repository derived from `payload.dig('repository','full_name')`), so a status can never be attributed to a commit outside the repository that was actually authenticated for this webhook.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `victim-org` (tracking `victim-org/app`) and `attacker-org` (attacker controls the app/webhook secret for this org).
2. Attacker forks `victim-org/app` into `attacker-org/app`; shared ancestor commit `abc123...` exists in both, and is the commit currently pending deploy in the `victim-org/app` Shipit stack (missing a required `ci/checks` status).
3. Attacker triggers (or crafts, since they own the app secret) a `status` webhook from GitHub for `attacker-org/app` with body `{"sha":"abc123...","state":"success","context":"ci/checks","branches":[...]}`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, verifies against `attacker-org`'s `webhook_secret` — succeeds.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, matches the victim stack's commit row (no repository filter), and creates a `success` `Status` with `context: 'ci/checks'` on it.
6. The victim stack's commit now satisfies `required_statuses`, becoming deployable/eligible for continuous delivery — an unauthorized state change achieved without any credential belonging to `victim-org`.
