### Title
Status webhook events are applied to commits across all organizations regardless of which org's signature was verified - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / webhook secret used to validate an incoming webhook's HMAC signature based solely on the `repository.owner.login` (or `organization.login`) field taken from the *same untrusted payload* it is about to verify: `Shipit.github(organization: repository_owner)` [1](#0-0) , with `repository_owner` computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Shipit supports hosting multiple GitHub organizations, each with its own App/installation and webhook secret (hence the `GithubOrganizationUnknown` rescue branch) [3](#0-2) .

Once the signature is verified as belonging to *some* organization, the `status` event handler processes the payload without re-checking that the reported commit actually belongs to a repository under that same organization: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `Commit.where(sha:)` is a global, cross-tenant lookup with no scoping by `repository_name`/`stacks`, unlike the base `Handler` class's own `stacks` helper which *does* scope by `payload.dig('repository', 'full_name')` [5](#0-4)  but which `StatusHandler` never uses.

### Finding Description
This breaks the binding: **organization that authenticated == repository that is written**. The webhook signature only proves "this request was signed by organization X's webhook secret" (or, at minimum, that the payload's `repository.owner.login`/`organization.login` field, which is attacker-controlled content inside a signed body from a legitimate GitHub App install of organization X, matches X). It does not, and cannot, prove that the `sha` field inside the same payload corresponds to a commit that lives in a repository owned by X. `StatusHandler` never checks this: it looks up `Commit.where(sha: params.sha)` across the entire Shipit installation — potentially across every organization and repository ever synced into that Shipit instance — and blindly calls `commit.create_status_from_github!(params)` on whatever commit matches, writing attacker-chosen `state`, `context`, `description`, and `target_url` [6](#0-5) .

An attacker who legitimately controls their own GitHub organization/App installation that is configured in the same Shipit instance (a normal, unprivileged tenant of a multi-org Shipit deployment) can freely trigger `status` webhooks from their own repository with an arbitrary `sha` value copied from a *different* organization's public commit history, and a forged `state`/`context` of their choosing. Because `StatusHandler` performs no cross-tenant repository check, this forged status is attributed to the victim organization's commit.

### Impact Explanation
Commit statuses gate Shipit's deployability logic (CI checks, `deployable_status`, `merge_status`) which is used by `continuous_deployment`/merge-queue features to decide whether a commit is safe to auto-deploy or auto-merge [7](#0-6) . By injecting a forged "success" status for a required check context on a victim's commit in an unrelated organization/repository hosted by the same Shipit instance, an attacker can make Shipit believe CI has passed for that commit, potentially triggering an **unauthorized deploy** of a commit that never actually passed its real CI pipeline. This matches the Critical-impact category of "an unauthorized deploy" defined in scope.

### Likelihood Explanation
Requires: (1) a Shipit instance configured to serve multiple GitHub organizations (a documented, supported configuration — each org gets its own App/webhook secret, per the `GithubOrganizationUnknown` handling), and (2) the attacker to control one of those organizations' legitimate GitHub App webhook delivery (i.e., be a normal, valid tenant of the multi-tenant Shipit instance, not a privileged Shipit user/API-client). No Shipit session, API token, or GitHub App private key theft is required — the attacker uses their own organization's legitimately-issued webhook secret to sign a payload whose `sha` field references a foreign commit. The victim's commit `sha` is typically public (visible via GitHub) making the attack straightforward to mount.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the commit lookup to commits belonging to repositories owned by the verified organization/repository, e.g. reuse the base `Handler#stacks` scoping (`payload.dig('repository', 'full_name')`) to restrict `Commit.where(sha: params.sha)` to commits under the stacks of that specific repository, mirroring how `PushHandler` correctly scopes via `stacks` [8](#0-7) .

### Proof of Concept
1. Shipit is configured with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App installation and webhook secret, per `docs/setup.md`'s multi-org support.
2. Attacker legitimately controls `attacker-org`'s GitHub App / webhook delivery (they are a normal tenant, not a Shipit admin).
3. Attacker looks up a target commit SHA belonging to `victim-org/some-repo` that is pending/failing a required status check.
4. Attacker sends (or triggers via their own repo activity, crafting a synthetic status delivery) a `status` webhook payload signed with `attacker-org`'s webhook secret, with `repository.owner.login = "attacker-org"` (so it passes `verify_signature`) but `sha` set to the victim's commit SHA, `state: "success"`, and `context` matching the victim stack's required release-status context.
5. `WebhooksController#verify_signature` validates the signature successfully against `attacker-org`'s secret [1](#0-0) .
6. `StatusHandler#process` finds the victim's commit via the global `Commit.where(sha: params.sha)` lookup and writes the forged success status onto it [4](#0-3) , potentially unlocking continuous deployment/merge of that commit in `victim-org`.
