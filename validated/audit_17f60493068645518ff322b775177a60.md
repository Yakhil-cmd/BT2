### Title
Unreleased `handleJoint` mutex lock on unexpected `throw` in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` acquires the global `["handleJoint"]` mutex before reading unit properties and potentially advancing the stability point. On one code path it throws an `Error` instead of releasing the lock first, exactly mirroring the CVE-2022-49684 pattern where a refcounted/held resource (`of_find_node_by_name()`'s node reference) is not released before an early return/error path.

### Finding Description
Inside `determineIfStableInLaterUnitsAndUpdateStableMcFlag`, the `["handleJoint"]` mutex is locked at [1](#0-0) , and then `storage.readUnitProps` is used to check whether `earlier_unit` is still on the main chain: [2](#0-1) 

If `objEarlierUnitProps.is_on_main_chain` is falsy, the code executes `throw Error("earlier unit is no longer on main chain")` **without calling `unlock()`** first, unlike the adjacent branch a few lines below that correctly calls `unlock(...)` before returning. This is the same root-cause shape as the kernel bug: a resource (`node` refcount in the kernel; the `handleJoint` mutex here) is acquired, and an error/early-exit path fails to release it.

The `handleJoint` key is not a niche lock — it is the primary serialization mutex used across `network.js`, `validation.js`, and `composer.js` to serialize **all** unit validation and joint handling, e.g. in `handleJoint` for peer-submitted units [3](#0-2)  and in the composer's saving callbacks [4](#0-3) . `determineIfStableInLaterUnitsAndUpdateStableMcFlag` is itself invoked from within `validation.js` (advancing-stability logic) and `network.js`, meaning the vulnerable code path is reachable while processing a posted unit's parent-stability determination.

`earlier_unit` can become "no longer on main chain" because of an ordinary main-chain reorganization that occurs concurrently while this code is waiting to acquire the `handleJoint` lock (the comment at line 1205 explicitly acknowledges this race: "the stability point moved while we were waiting for the lock" is handled just a few lines later for a different condition, but the `!is_on_main_chain` condition is handled by an unconditional `throw` instead).

### Impact Explanation
Because `handleJoint` is the single global lock serializing acceptance of all new units network-wide (see `network.js` `mutex.lock(['handleJoint'], ...)`), a lock that is acquired but never released permanently blocks:
- All subsequent joint validation/handling (`handleJoint` in `network.js`).
- All base/divisible/indivisible-asset composing-and-saving flows (`composer.js`, `divisible_asset.js`, `indivisible_asset.js`), which also acquire `handleJoint`.

This results in the node becoming unable to confirm any new units — a total denial of new-unit processing on the affected node — which falls squarely into the accepted "network unable to confirm new units" impact category.

### Likelihood Explanation
The trigger condition requires a main-chain reorganization to happen concurrently with a call to `determineIfStableInLaterUnitsAndUpdateStableMcFlag` while it is waiting on the `handleJoint` lock — a race window that is a natural, adversarially-influenceable consequence of unit posting/witnessing activity that shifts the best-parent selection on the DAG. This makes the crash reachable from ordinary (or deliberately timed) unit posting by any peer, without needing any special privilege, though the exact timing window makes it probabilistic rather than trivially deterministic on each attempt.

### Recommendation
Release the mutex before throwing (or convert the condition into a normal `unlock()` + return, treating a unit falling off the main chain as an expected race outcome rather than a fatal error), e.g.:
```js
storage.readUnitProps(db, earlier_unit, async function(objEarlierUnitProps){
    if (!objEarlierUnitProps.is_on_main_chain)
        return unlock("earlier unit is no longer on main chain");
    ...
});
```
This mirrors the kernel fix pattern of always releasing the acquired resource on every exit path, including error paths.

### Proof of Concept
1. An attacker (or ordinary network activity) posts units causing frequent main-chain reorganizations near the current stability frontier.
2. `determineIfStableInLaterUnitsAndUpdateStableMcFlag` is invoked (via `validation.js`/`network.js`) for a unit whose parents make it a stability candidate.
3. It determines `bStable=true`, calls `handleResult` early, and proceeds to acquire the `["handleJoint"]` lock to advance the stability point.
4. While waiting for the lock, a MC reorg displaces `earlier_unit` from the main chain.
5. Once the lock is acquired, `storage.readUnitProps` reports `is_on_main_chain=0`, and the code throws without unlocking `handleJoint`.
6. `handleJoint` remains permanently locked; every subsequent call to `mutex.lock(['handleJoint'], ...)` in `network.js`/`composer.js`/asset-composer files queues indefinitely, halting acceptance of all new units on the node.

Note: I was not able to fully trace every call site of `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (in `validation.js`, `network.js`, `tools/update_stability.js`) within the available exploration budget to confirm whether any outer `try/catch` wraps this specific `async` inner function and could mitigate the lock leak (an uncaught exception inside an `async function` callback becomes an unhandled promise rejection rather than a synchronous throw bubbling to a catcher, which typically means the lock leak persists rather than being caught). This should be verified against Node.js version/unhandled-rejection behavior in the deployment environment.
