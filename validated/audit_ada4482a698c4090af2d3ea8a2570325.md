Confirmed: `check_permissions!` only checks operation:scope permission strings (e.g., `read:stack`), and never checks `current_api_client.stack_id` against the requested stack — the scoping to a single stack is enforced *only* by `stacks` (`Stack.where(id: current_api_client.stack_id)`) in `Shipit::Api::BaseController#stacks`/`#stack`. `CCMenuController#stack` bypasses this scoping entirely by calling `Stack.from_param!` directly on the unscoped `Stack` model.### Title
`Api::CCMenuController#stack` bypasses stack-scoped authorization by calling `Stack.from_param!` instead of `stacks.from_param!` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces per-`ApiClient` stack scoping via `#stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), which `#stack` then queries with `.from_param!`. `Shipit::Api::CCMenuController#stack` overrides this and calls `Stack.from_param!` on the unscoped `Stack` model directly, so a client whose token is restricted to `stack_a` can fetch the CCTray XML status (build/deploy state) of any other stack `stack_b` by simply changing `params[:stack_id]`.

### Finding Description
The binding that must hold is: for identical `current_api_client` (with `current_api_client.stack_id = stack_a.id`) and identical `params[:stack_id] = stack_b.to_param`, every `Api::BaseController` subclass's `#stack` must yield the same authorization outcome (`RecordNotFound` because `stack_b` is outside `stacks`).

- `app/controllers/shipit/api/base_controller.rb:74-80` defines the correct, scoped version:
  ```
  def stacks
    @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
  end
  def stack
    @stack ||= stacks.from_param!(params[:stack_id])
  end
  ``` [1](#0-0) 
- `Api::StacksController` does not override `#stack` in a way that removes scoping — it defines its own `#stack` using `stacks.from_param!(params[:id])`, which still routes through the scoped `#stacks` method, so it correctly 404s for out-of-scope stacks. [2](#0-1) 
- `Api::CCMenuController#stack` instead does:
  ```
  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
  ```
  which queries `Stack` directly with no scoping by `current_api_client.stack_id`. [3](#0-2) 

Root cause: `check_permissions!(operation, scope)` in `ApiClient` only validates the coarse `"#{operation}:#{scope}"` permission string (e.g. `read:stack`) against `permissions`; it never consults `current_api_client.stack_id`. [4](#0-3)  The only place that enforces per-token stack scoping is the `#stacks`/`#stack` pair in the base controller. Since `require_permission :read, :stack` on `CCMenuController` only checks the generic permission (present on essentially any stack-scoped token), and the controller's own `#stack` override skips the scoped `stacks` relation, an attacker holding a stack-scoped token for `stack_a` can request `GET /api/stacks/:owner/:repo_b/:env_b/ccmenu` for `stack_b` and receive its build status.

Existing guards checked: `force_github_authentication`, `verify_signature`, `ExplicitParameters` schema — none apply here (this is API-token auth, not webhook or session auth). `require_permission!` and `ApiClient#check_permissions!` do not check `stack_id`. Nothing else in the reachable path restores scoping for CCMenu.

### Impact Explanation
An attacker who possesses one legitimately-issued, stack-scoped `ApiClient` token (scoped to `stack_a`) can read the CI/deploy status of any other stack in the Shipit instance (arbitrary `owner/repo/environment`) via `Api::CCMenuController#show`, including latest deploy id, timestamp, running/failure state and lock status (`locked stacks show as failed` behavior confirms lock state leaks too — see `test/controllers/api/ccmenu_controller_test.rb:41-45`). This is an unauthenticated-for-that-resource read of stack state across tenant boundaries — matches the **High** severity category ("unauthenticated read of stack state ... across repositories"). It is repeatable for every stack in the instance simply by iterating `stack_id` values; it does not require any escalation of write/deploy permissions and does not leak GitHub credentials, so it does not reach the Critical bar.

### Likelihood Explanation
Preconditions: attacker needs one valid `ApiClient` token that is stack-scoped (`stack_id` set) with `read:stack` permission — a normal, low-privilege API client that a Shipit operator may hand out to a single team/repository for CCTray integration. Beyond possessing that one legitimate token, no other secrets are needed. The request is a single unauthenticated-scope-wise `GET` to a predictable URL (`/api/stacks/*stack_id/ccmenu`), fully repeatable, no rate limiting bypass or timing dependency required. This makes exploitation cheap and reliable once such a token exists, though it does require the attacker to already hold *some* Shipit API token (not a fully external/unprivileged internet attacker with zero credentials) — it's a privilege-scope-escape rather than a fully anonymous bypass.

### Recommendation
Remove the `#stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited scoped `stacks` relation):
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it is consistent with `BaseController#stack` and honors `current_api_client.stack_id` scoping.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (and a parallel case in `stacks_controller_test.rb` for comparison), add:
```ruby
test "a stack-scoped client cannot fetch ccmenu status for a different stack" do
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  @client.update!(stack_id: @stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: stack_b.to_param }
  assert_response :not_found # currently fails: returns 200 with stack_b's CI status
end
```
Paired assertion on `Api::StacksController` with the same `@client`/`stack_b` setup:
```ruby
get :show, params: { id: stack_b.to_param }
assert_response :not_found # passes today, proving divergence is CCMenuController-specific
```
