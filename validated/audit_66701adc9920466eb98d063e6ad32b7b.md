### Title
Unchecked scaled-value growth can permanently freeze all operations in an overlarge market - (File: common/src/rates/index.rs)

### Summary
`accrue_step` can make `borrowed * borrow_index` or `supplied * supply_index` exceed the `i128` RAY-value domain before the configured index ceiling is reached, causing every subsequent market operation to panic during mandatory interest accrual. [1](#0-0) [2](#0-1) 

### Finding Description
A single unprivileged address can create a target-market supply account with `Controller::supply(caller, account_id = 0, spoke_id, assets = [(hub_asset, supply_amount)])`, create or use a collateral account, submit `Controller::borrow(caller, account_id, borrows = [(hub_asset, debt_amount)], to = None)`, and later call `Controller::update_indexes(caller, assets = [hub_asset])`. [3](#0-2) [4](#0-3) 

The public controller path forwards the index update to the owner-gated pool entrypoint, so authorization of the unprivileged controller caller is sufficient to reach the accrual code. [5](#0-4) [6](#0-5) 

Every market leg loads the market through `ops::load_leg`, which calls `synced_market` and therefore `interest::global_sync` before performing the requested operation. [7](#0-6) [8](#0-7) 

During accrual, `calculate_supplier_rewards` multiplies the stored scaled debt by both the old and new borrow indexes, while `update_supply_index` multiplies scaled supply by the supply index and then adds rewards. [9](#0-8) [10](#0-9) 

`Ray::mul` delegates to `mul_div_half_up`, which panics with `MathOverflow` when the exact result cannot fit in `i128`; therefore the index cap does not protect the protocol when the scaled principal itself is large enough. [11](#0-10) [12](#0-11) 

### Impact Explanation
Once the stored scaled debt or supply crosses the representable-value threshold for the next index, every subsequent accrual recomputes the overflowing product before committing state, so the market cannot advance past the failure. [13](#0-12) [14](#0-13) 

Because repayment, withdrawal, borrowing, and supply all synchronize the same market first, users lose access to repayment and withdrawal paths and liquidators cannot use normal market legs to reduce the frozen debt. [15](#0-14) [16](#0-15) 

This is a permanent freezing of user funds and a market-level denial of service rather than a fail-closed oracle or resource-limit issue: the panic is caused by unrepresentable internal accounting state. [17](#0-16) [18](#0-17) 

### Likelihood Explanation
The demonstrated trigger requires an extremely large admitted market and sustained interest accrual, so it is conditional on protocol caps, available liquidity, and the market remaining active long enough for scaled-value growth to cross the `i128` boundary. [19](#0-18) 

The checked-in scenario reaches the failure before the borrow-index ceiling and then confirms that both withdrawal and repayment fail with `MathOverflow`, demonstrating that the condition is not merely theoretical. [20](#0-19) 

### Recommendation
Bound admitted scaled supply and scaled debt so their multiplication by the maximum possible index remains representable, or perform accrual value calculations in a wider representation and explicitly clamp state transitions before storing them. [2](#0-1) [9](#0-8) 

Market admission and cap updates should enforce a scaled-position limit derived from `i128::MAX * RAY / MAX_*_INDEX_RAY`, rather than only limiting token-unit caps and index values independently. [21](#0-20) [2](#0-1) 

### Proof of Concept
1. Let `TARGET` be a valid high-decimals hub asset and `COLLATERAL` another admitted asset under one spoke; the attacker controls both accounts. [3](#0-2) 
2. The attacker calls `Controller::supply(attacker, 0, spoke_id, [(TARGET, target_supply)])`, then supplies collateral and calls `Controller::borrow(attacker, collateral_account_id, [(TARGET, target_debt)], None)`. [22](#0-21) [23](#0-22) 
3. The attacker periodically calls `Controller::update_indexes(attacker, [TARGET])`; each call reaches `pool.update_indexes`, which runs `global_sync` and `accrue_step`. [4](#0-3) [8](#0-7) 
4. Once `TARGET.borrowed * TARGET.new_borrow_index` or `TARGET.supplied * TARGET.new_supply_index` no longer fits in `i128`, `update_indexes` reverts with `MathOverflow`. [14](#0-13) [24](#0-23) 
5. The same overflow then causes `Controller::repay(attacker, collateral_account_id, [(TARGET, 1)])` and `Controller::withdraw(attacker, supply_account_id, [(TARGET, 1)], None)` to revert before their repayment or withdrawal logic runs. [25](#0-24) [18](#0-17)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();

/// The division saturates at `i128::MAX` instead of panicking, so the cap check

pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
