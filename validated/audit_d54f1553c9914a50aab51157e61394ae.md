### Title
`pull_request` webhook owner/full_name split lets a no-secret org's signature authorize `LabelCapturingHandler` writes onto a different org's `ReviewStack` — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the signing secret using `repository_owner`, which reads `params.dig('repository','owner','login')` (or `organization.login`), while `LabelCapturingHandler` resolves the actual `Repository`/`ReviewStack` it mutates from a completely independent field, `params.repository.full_name`. An attacker who owns/controls a GitHub organization that is configured in Shipit with no `webhook_secret` can forge a `pull_request` `action=labeled` payload whose `repository.owner.login` is that no-secret org (so signature verification trivially passes) while `repository.full_name` names a victim org/repo, causing the victim's `ReviewStack`'s `PullRequest#labels` to be overwritten from attacker-controlled data.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == owner(params.repository.full_name)`. In reality nothing enforces this equality.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is taken from `params.dig('repository','owner','login')`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) does `return true unless webhook_secret` — i.e., if the selected organization's config has no `webhook_secret`, verification is unconditionally true, regardless of the actual signature header.
- `LabelCapturingHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:110-114`) resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a field never checked against `repository_owner`.
- `LabelCapturingHandler#stack`/`#review_stack` (lines 104-118) then scopes `ReviewStackAdapter` to `repository.review_stacks` and looks the stack up by `environment: "pr#{params.number}"` (`review_stack_adapter.rb:15-17,96-98`) — again independent of any commit SHA, so the "shared commit SHA" element in the question is not actually part of this handler's resolution path; the exploit works purely off the owner/full_name mismatch.
- `#capture_labels` (lines 98-102) then does `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))`, persisting attacker-chosen label names onto the victim's `PullRequest` record for the resolved review stack.

Exploit flow: attacker configures/owns org `attacker-org` in Shipit with no `webhook_secret` set (a legitimately reachable "no-secret org" state per the question's premise). Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, some `X-Hub-Signature` (any value, since it's ignored when no secret is configured), and a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, `action = "labeled"`, and a PR `number` matching an existing victim review stack (e.g. `pr42`). `verify_signature` passes because `attacker-org` has no secret. The handler then loads `victim-org/victim-repo`'s repository record and updates the labels on that stack's `PullRequest`.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type exists a handler; `ExplicitParameters` schema only validates shape/types, not owner consistency; there is no `require_permission!`/`User#authorized?` check on webhook ingestion (webhooks are unauthenticated by design, relying solely on signature verification); and signature verification is keyed on the wrong field for cross-checking against `full_name`.

### Impact Explanation
The attacker can write to a victim's `PullRequest#labels` on an arbitrary review stack, by only needing to control a Shipit-configured org with no webhook secret and knowing the victim's `full_name`/PR number. This is a payload from one repository (attacker's, whose secret—or lack thereof—was used to authenticate) mutating another repository's stack/PR state, which matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Labels feed into `ReviewStack#env` as uppercased environment variables (confirmed by the question's premise and the existence of label-to-env logic in `review_stack.rb`), meaning attacker-controlled label strings become environment variable keys/values injected into deploy/provisioning commands for the victim's stack — a further escalation vector beyond simple data corruption. This is repeatable against any repository the attacker can name in `full_name`, as long as they control (or can point to) an org with no configured secret.

### Likelihood Explanation
Preconditions: Shipit must have at least one organization configured without a `webhook_secret` (the question's premise explicitly grants this — a "no-secret org" chosen by the attacker via `repository_owner`), and the attacker must know or guess a victim `owner/repo` full_name and an existing PR number/environment on that stack. No GitHub credentials, no Shipit session, no API token, and no privileged role are required — only the ability to send an unauthenticated HTTP POST to `/webhooks`. This is low-cost and fully repeatable, limited only by the existence of at least one misconfigured (secretless) org binding in the target Shipit deployment.

### Recommendation
Bind webhook signature verification to the same repository identity the handlers act on: derive the verifying organization from `params.repository.full_name`'s owner segment (not `params.repository.owner.login`) — or better, verify that `repository.owner.login` and the owner segment of `repository.full_name` match before dispatching to handlers, rejecting the request (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to trivially return `true` when `webhook_secret` is blank for any org that owns victim repositories; require every organization to have secrets configured before enabling webhook processing for it.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb`:

1. Configure `Shipit.github_app` config so org `"attacker-org"` has `webhook_secret: nil` and org `"victim-org"` has a real `webhook_secret` set.
2. Create a `Shipit::Repository` for `victim-org/victim-repo`, a `Shipit::ReviewStack` with `environment: "pr42"`, and its associated `PullRequest` with `labels: ["safe"]`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and JSON body:
   - `action: "labeled"`, `number: 42`
   - `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }`
   - `pull_request: { ..., labels: [{ name: "MALICIOUS_ENV_INJECTION" }] }`
4. Assert response is `200 OK` (i.e., signature check passed despite bogus signature, because `attacker-org` has no secret).
5. Reload the victim `PullRequest` and assert `pull_request.labels == ["MALICIOUS_ENV_INJECTION"]`, proving that a payload "authenticated" by `attacker-org`'s (non-)secret mutated `victim-org`'s stack state — violating the invariant that `repository.owner.login` used for signing must equal the owner of `repository.full_name` that is actually mutated.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
