### Title
Session fixation on GitHub OAuth login due to missing session ID regeneration - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` establishes an authenticated session by writing `session[:user_id]` and `session[:authenticated] = true` directly onto whatever session already exists, without first calling `reset_session` (or otherwise rotating the session identifier). This breaks the binding between "the GitHub identity that completed OAuth" and "the session/session-store key that is subsequently trusted as authenticated," matching the report's requested equivalence class of "a GitHub identity versus the `User` bound to the session."

### Finding Description
The OAuth callback is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

`sign_in_github` resolves/creates the `User` from the verified OmniAuth payload and returns its `id`, which is then written into the *existing* session hash: [2](#0-1) 

`current_user` elsewhere is derived purely from `session[:user_id]`: [3](#0-2) 

There is no `reset_session` call anywhere in the authentication flow (`logout` does call it, but `callback` does not), so the identifier for the session established prior to login persists across the privilege transition from anonymous to authenticated. If the session store is anything other than a fully self-contained encrypted cookie (e.g. an ActiveRecord/Redis/cache-based session store, which Rails apps commonly switch to for scalability, and which this engine does not prevent or override), an attacker who can plant/know a pre-authentication session identifier in a victim's browser can have that same identifier become authenticated once the victim completes GitHub OAuth — a classic session fixation, one of the explicitly named High-impact classes ("session fixation / forced OAuth completion").

### Impact Explanation
If exploited, the attacker's pre-set session identifier becomes bound to the victim's authenticated GitHub identity after OAuth completes, letting the attacker use the same session to impersonate the victim inside Shipit (view stacks, trigger deploys/rollbacks, since `current_user` and the whole authorization layer depend solely on `session[:user_id]`). This is a direct authentication-boundary crossing, matching the required "session fixation / forced OAuth completion" High-severity class.

### Likelihood Explanation
Likelihood depends on the session store in use in production. Shipit ships with the standard Rails session middleware; the engine does not force `CookieStore` and does not perform any session ID rotation at login. Any deployment using a server-side session store (common for larger installations, or any store keyed by a session id transmitted via cookie without per-login rotation) is directly exploitable by a low-privilege, unauthenticated attacker who can set a cookie in the victim's browser (e.g., via a subdomain, a response header injection elsewhere, or simply sharing a link that sets the session cookie) and then wait for the victim to log in via the normal "Login with GitHub" flow. No repository write access, API token, or webhook secret is required — only inducing/observing a normal OAuth completion, which is squarely in scope per the rules (this is not a GitHub App/webhook/API-token/TLS/local-access dependency).

### Recommendation
Call `reset_session` (or otherwise regenerate the session identifier) in `GithubAuthenticationController#callback` immediately before/when writing `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `logout`. This severs any pre-authentication session identifier from the post-authentication session, closing the fixation window regardless of which session store the deployment uses.

### Proof of Concept
1. Attacker visits the Shipit instance unauthenticated, obtaining a valid (but anonymous) session cookie/identifier `S`.
2. Attacker, via any means that sets cookies in the victim's browser for the Shipit domain (e.g., a crafted link that first hits the app and issues cookie `S`, or a shared/kiosk browser), causes the victim's browser to carry session identifier `S`.
3. Victim clicks "Login with GitHub" and completes the OAuth flow legitimately.
4. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth); session[:authenticated] = true` without regenerating the session id — session `S` is now bound to the victim's authenticated `User`.
5. Attacker, still holding session identifier `S` (if the session store is server-side/shared, e.g. via a fixed session cookie value they set), now has an authenticated session as the victim and can perform any action `current_user` is authorized for (viewing stacks, deploying, etc.).

Note: I was unable to fully confirm from the indexed engine code alone which session store the shipped example/production configuration ultimately uses at runtime (the search only surfaced `test/dummy/config/initializers/session_store.rb`, a test-only dummy app config), so the exact exploitability depends on the host application's Rails session store configuration, which is outside the engine's own code but is a deployment choice the engine does not defend against.
