### Title
Webhook signature verified against `repository.owner.login`, but stack lookup and event processing use the unauthenticated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` against using `repository.owner.login` (falling back to `organization.login`), while the actual event processing (`Handler#stacks` / `Handler#repository_name`) resolves the target `Repository`/`Stack` using the independent `repository.full_name` field of the same JSON body. In a multi-organization Shipit deployment, these two fields identify different trust domains, and nothing enforces that `full_name`'s owner segment matches `owner.login`.

### Finding Description
`WebhooksController#verify_signature` picks the webhook secret like this: [1](#0-0) [2](#0-1) 

The organization used to look up `Shipit.github(organization:)` (and thus the `webhook_secret` used to verify the HMAC) comes from `repository.owner.login`.

But once the signature check passes, the raw JSON is dispatched to handlers unmodified: [3](#0-2) 

Handlers resolve the affected repository/stack using a *different* field, `repository.full_name`: [4](#0-3) 

`Repository.from_github_repo_name` splits this string on `/` to get owner and name and looks up the `Repository` record directly, independent of whatever organization was used for the signature check: [5](#0-4) 

In a single-organization Shipit install this is not exploitable, because GitHub itself guarantees `owner.login` and `full_name`'s owner segment are consistent for legitimately-delivered webhooks. However, Shipit explicitly supports **multiple GitHub organizations**, each with its own independently configured `webhook_secret` (see `docs/setup.md`, "Using Multiple Github Applications"). An attacker who administers (or has a GitHub App installed in) *any one* of the configured organizations knows that organization's `webhook_secret` and can freely craft an HMAC-valid POST to the shared, unauthenticated `/webhooks` endpoint with:
- `repository.owner.login` = the attacker's own org (so `verify_signature` selects the attacker's own known secret and the signature check passes), and
- `repository.full_name` = `"<victim-org>/<victim-repo>"` — any repository tracked as a Shipit `Stack` under a *different*, unrelated organization.

Because `verify_signature` never checks that `repository.owner.login` matches the owner segment of `repository.full_name`, and because `Handler#stacks`/`Handler#repository_name` trust `full_name` unconditionally, the attacker can forge `push`, `status`, `check_suite`, etc. events for a stack belonging to an organization they have no legitimate relationship with — using a signature computed with credentials they legitimately possess for their own, unrelated organization.

This is the exact "organization that authenticated versus the repository that is written" binding called out in scope: the equality `authenticated_organization == repository_being_acted_on` is not enforced.

### Impact Explanation
A forged `push` event is routed to `PushHandler`, which for every not-archived stack matching the branch calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` for the victim's real stack: [6](#0-5) 

This job fetches commits via the *victim's own* configured GitHub credentials (`stack.github_api`, which resolves through `Repository#github_app` using the real repository's `owner`, not the attacker's), and — for stacks with `continuous_deployment` enabled — this sync can trigger automatic deploy/rollback processing on a stack the attacker does not control and has no access to. This satisfies the required "unauthorized deploy or rollback" impact bar without the attacker ever holding a Shipit session, API token, or the victim organization's webhook secret — only signature material for an org that has nothing to do with the target stack.

Other event types (`status`, `check_suite`) can similarly be spoofed against arbitrary tracked repositories/commits, corrupting commit status state and CI gating decisions used to authorize deploys.

### Likelihood Explanation
Requires only: (1) the attacker administers or has installed a GitHub App for *any* organization configured in Shipit's multi-org `github:` secrets (a normal, low-privilege scenario in a shared/multi-tenant Shipit instance), and (2) that Shipit instance also tracks a stack belonging to a different organization. Given Shipit explicitly documents and supports multi-org configurations for this purpose (shared internal deploy tooling across many teams/orgs), this is a realistic deployment shape, and the `/webhooks` endpoint requires no session or authentication beyond the HMAC check that the attacker can satisfy with their own legitimate secret.

### Recommendation
In `WebhooksController#verify_signature`, after locating the GitHub App for `repository_owner`, additionally verify that the owner segment of `params.dig('repository', 'full_name')` (when present) matches `repository_owner` before proceeding; reject the request (422) on mismatch. Equivalently, have `Handler#repository_name` (and any other field consumed by handlers) authenticate against the same organization value that selected the signing secret, rather than trusting an independent field from the same payload.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org setup). Attacker legitimately knows `attacker-org`'s webhook secret because they administer that org's GitHub App/installation.
2. Shipit tracks `victim-org/victim-repo` as an active `Stack` with `continuous_deployment: true`.
3. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. an older already-merged sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<hmac computed with attacker-org secret>
```
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully with the attacker's own secret, and passes.
6. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for the real victim stack — despite the request never being signed by anything belonging to `victim-org`.
