### Title
`approve_for_all` operator grant persists across account lifecycle and lets a stale operator steal positions minted after the grant - (File: contracts/position-nft/src/contract.rs)

### Summary
The position NFT uses the stock OpenZeppelin `NonFungibleToken` approval model: `approve_for_all(owner, operator, live_until_ledger)` stores a grant keyed only by `(owner, operator)` and valid until `live_until_ledger`. Because `account_id == token_id` and every new controller account mints a fresh token id to the caller, an operator approved once can `transfer_from` any token the owner holds — including tokens minted after the grant was given — and then drain the collateral through `controller::withdraw`.

### Finding Description
This is the direct analog of the ERC1155 `isApprovedForAll` epoch bug. In Knox, claim tokens of later epochs were redeemable by a stale approved receiver. Here, approval is similarly not scoped to a specific token or point in time:

- `PositionNft` exports the unchanged OZ `NonFungibleToken` trait (`contracts/position-nft/src/contract.rs:131-133`), so `approve_for_all` is the stock implementation whose storage key is `ApprovalForAll(owner, operator)` — no token id, no epoch, only a ledger expiry.
- `mint` (`contract.rs:68-76`) mints a new sequential token id to `to` and never clears or re-checks operator grants; any address matching an existing `(to, operator)` grant is instantly authorized over the new token.
- `controller::supply(caller, 0, spoke_id, assets)` creates a new account owned by `caller`, which mints a fresh NFT id (`load_or_create_account`, `contracts/controller/src/account.rs:95-97`). Alice can therefore create an entirely new collateralized position without touching the NFT contract, and the grant still applies.
- Ownership is resolved live via `owner_of` (`try_account_owner`, `contracts/controller/src/storage/account.rs:35-44`), so once Bob `transfer_from`s the new token to himself he is the account owner and can call `withdraw`/`borrow` to arbitrary `to` recipients.

Concretely:
1. Alice approves Bob as operator (`approve_for_all`) intending he manage/move account id `M`.
2. Later, Alice calls `supply` with `account_id = 0`, which mints token `N` to Alice and deposits her collateral.
3. While `live_until_ledger` hasn't passed, Bob calls `transfer_from(Bob, Alice, Bob, N)` — the `(Alice, Bob)` grant authorizes it despite `N` not existing at grant time.
4. Bob calls `controller::withdraw(caller=Bob, account_id=N, ...)` — he is now `owner_of(N)` — and receives Alice's collateral.

The protocol acknowledges the asymmetry in its own docs ("Approval hands over the whole account", `contracts/position-nft/README.md:168-172`) but nothing scopes the grant to tokens existing at approval time.

### Impact Explanation
Theft of user funds. A single expired-intent operator can seize entire future lending positions (all collateral plus control of debt) with no further authorization from the victim, matching the Knox bug's impact shape exactly.

### Likelihood Explanation
`approve_for_all` is a standard wallet/marketplace interaction users routinely sign with long `live_until_ledger` values. Any user who ever granted an operator and later opens a new account (a normal `supply` flow) is exposed for the full grant duration. Requires only that the victim created the grant — no privileged access.

### Recommendation
If broad operator support must remain, document/enforce short `live_until_ledger` values and revoke grants before creating new accounts. Stronger: override `transfer_from`/mint paths so `approve_for_all` applies only to token ids existing at grant time (store a grant-time id counter snapshot and compare in `transfer_from`), or drop `approve_for_all` from the exported interface so only per-token `approve` (which is cleared on transfer, `contract.rs` test `approved_operator_can_transfer_and_approval_is_cleared`) is available.

### Proof of Concept
```rust
// env: PositionNft deployed with controller C; Alice, Bob are users.
// 1. Alice opens account M and grants Bob blanket operator rights.
let m = nft.mint(&alice); // via controller::supply(account_id = 0)
nft.approve_for_all(&alice, &bob, &(ledger + 100_000));

// Bob may legitimately move M; grant remains (approve_for_all is per-owner,
// not cleared by transfer).
nft.transfer_from(&bob, &alice, &bob, &m);
nft.transfer(&bob, &alice, &m); // return it; grant still live

// 2. Later Alice opens a NEW account N with collateral.
//    controller::supply(Alice, 0, spoke, assets) -> mint(N) to Alice.
let n = nft.mint(&alice); // controller-side mint during supply

// 3. Bob steals N using the stale (alice, bob) grant.
nft.transfer_from(&bob, &alice, &bob, &n);
assert_eq!(nft.owner_of(&n), bob);

// 4. Bob drains it: controller resolves owner_of(N) = Bob.
// controller::withdraw(caller=Bob, account_id=N, withdrawals=[(market, 0)], to=None)
// pays Bob Alice's collateral.
```

Key facts: grant storage is `NFTStorageKey::ApprovalForAll(owner, operator)` keyed without a token id (`contracts/position-nft/README.md:96`); mint does not invalidate prior grants (`contract.rs:68-76`); the controller trusts `owner_of` live (`storage/account.rs:35-44`) and gates `withdraw` on `require_owner_or_delegate` (`account.rs:130-140`).
