### Title
Cross-organization GitHub App token/endpoint confusion via thread-local client cache - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#api` memoizes the `Octokit::Client` in a bare `Thread.current[:github_client]` slot that is shared across *all* `GitHubApp` instances, even though Shipit explicitly supports multiple, independently configured GitHub organizations/apps (potentially pointing at different domains — `github.com` vs a GitHub Enterprise host) via `Shipit.github(organization:)`.

### Finding Description
`Shipit.github(organization:)` keeps one `GitHubApp` instance per organization, each with its own `@domain`, `app_id`, `installation_id`, and installation token: [1](#0-0) 

Each `GitHubApp` builds its Octokit client via `new_client`, which bakes in `api_endpoint`/`web_endpoint` at construction time based on that org's `domain`: [2](#0-1) 

But `#api` caches this client using a single, un-namespaced thread-local key, and on cache hit only mutates `access_token`, never the endpoint/middleware: [3](#0-2) 

Because job/worker threads are reused across requests for *different* stacks (and thus potentially different organizations — see `Stack#github_app` / `Stack#github_api`, which resolve a possibly-different `GitHubApp` per repository owner): [4](#0-3) 

the first `GitHubApp` instance to call `.api` on a given thread "wins" the endpoint/domain for the lifetime of that thread. Every subsequent `.api` call from a *different* organization's `GitHubApp` on that same thread reuses the first org's cached `Octokit::Client` object (same `web_endpoint`/`api_endpoint`, same Faraday middleware/cache store) and merely swaps in the second organization's freshly-fetched installation token via `client.access_token = token`.

The equality this breaks: **the organization whose credentials/domain the client was configured for ≠ the organization whose token is transmitted through it.** Concretely, if `OrgOne` uses `github.com` (default) and `OrgTwo` is configured with `domain: github.example.com` (GitHub Enterprise), a worker thread that first serves `OrgOne` and then `OrgTwo` (multi-org config is explicitly documented and tested — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) will send `OrgTwo`'s freshly minted installation access token to `github.com` (the endpoint baked in for `OrgOne`), not to `github.example.com`. This is a direct analog of the reported bug class: a shared, non-isolated per-call context (there `sdk.Context`, here the cached `Octokit::Client`/`Thread.current`) is reused across logically distinct execution contexts (there concurrent goroutines, here successive calls on a reused thread from different `GitHubApp`/organization instances), causing state (there the context, here the API endpoint) from one context to be combined with credentials from another.

### Impact Explanation
This causes a GitHub App installation access token for one organization to be exfiltrated to the wrong GitHub host/domain (an enterprise-scoped token sent to `github.com`, or vice versa) and causes API calls intended for one organization's repositories to actually execute against a different organization's GitHub instance while carrying the wrong org's token — a credential-exfiltration and cross-repository-write vector across the multi-tenant organization boundary that Shipit's own configuration model is supposed to isolate (`docs/setup.md` explicitly states "A Github application can only authenticate to the Github organization it's installed in").

### Likelihood Explanation
This requires no attacker privileges, tokens, or sessions — it is triggered purely by ordinary multi-tenant operation (webhooks, syncs, deploys) for two or more configured organizations being processed on the same reused Puma/Sidekiq thread, which is the normal steady-state of any Shipit deployment configured with `docs/setup.md`'s "Using Multiple Github Applications" schema.

### Recommendation
Namespace the thread-local (or better, instance-level) client cache by the `GitHubApp` instance/organization (e.g., `Thread.current[:github_clients] ||= {}; Thread.current[:github_clients][object_id] ||= new_client(...)`), or simply memoize the client per `GitHubApp` instance instead of per thread, so that endpoint, middleware, and token all originate from the same organization's configuration.

### Proof of Concept
1. Configure Shipit with two organizations as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` on default `github.com`, `OrgTwo` with `domain: github.example.com`.
2. On a worker thread, trigger any code path that calls `Shipit.github(organization: 'OrgOne').api` (e.g. `Stack#github_api` for a stack owned by `OrgOne`) — this builds and caches an `Octokit::Client` with `api_endpoint = 'https://github.com/'` in `Thread.current[:github_client]`.
3. On the *same* thread, trigger a call to `Shipit.github(organization: 'OrgTwo').api` (e.g. a `GithubSyncJob` for a stack owned by `OrgTwo`), per `lib/shipit/github_app.rb:63-67`.
4. Observe: the returned client still has `api_endpoint`/`web_endpoint` pointing at `github.com` (OrgOne's), but `access_token` has been overwritten with `OrgTwo`'s freshly fetched installation token — so `OrgTwo`'s credential is sent to `github.com` instead of `github.example.com`.

    # Backward compatibility

      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
