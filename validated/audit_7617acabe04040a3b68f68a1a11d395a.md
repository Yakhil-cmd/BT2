### Title
Membership webhook signature is verified against `repository.owner.login`/`organization.login`-as-fallback, but `Team#organization` is written from `params.organization.login` with no cross-check, letting an attacker's own org's signature authorize writing a `Team` row scoped to a victim org - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` picks the signing organization from `repository.owner.login` (or, only as a fallback when `repository` is absent, from `organization.login`) and uses it exclusively to select the `webhook_secret` for signature verification. `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to set `Team#organization` on create. These two reads of "organization" are never reconciled, so an attacker who owns `attacker-org` (and thus its `webhook_secret`) can forge a `membership` payload whose top-level `repository.owner.login` is `attacker-org` (making the signature check pass with the attacker's own secret) while the nested `organization.login` is `victim-org` (which is written verbatim into `Team#organization`).

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`organization used to verify the HMAC signature` (`params.dig('repository','owner','login')`, read in `WebhooksController#repository_owner`, `app/controllers/shipit/webhooks_controller.rb:59-62`) **should equal** `organization written to Team#organization` (`params.organization.login`, read in `MembershipHandler#find_or_create_team!`, `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`).

Code path:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that organization's `webhook_secret` (`lib/shipit.rb:170-181`, `Shipit.github`/`github_app_config`).
- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) returns `params.dig('repository','owner','login') || params.dig('organization','login')` — i.e. if a `repository` key with `owner.login` is present anywhere in the JSON body, it wins outright, regardless of what `organization.login` says.
- `MembershipHandler` (`app/models/shipit/webhooks/handlers/membership_handler.rb:7-21`) only declares/validates `action`, `team`, `organization`, `member` in its `ExplicitParameters` schema — it does not declare or consult a `repository` key at all, so an attacker-supplied `repository.owner.login` used purely to satisfy `verify_signature` is otherwise ignored by the handler.
- `find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) sets `team.organization = params.organization.login` on create — this is the second, independent read of "organization", sourced from a different JSON key than the one used for signing.

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with attacker-org's own `webhook_secret`, and a JSON body such as:
```json
{
  "action": "added",
  "team": { "id": 999999, "name": "x", "slug": "x", "url": "https://api.github.com/teams/999999" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-user" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
`repository_owner` returns `"attacker-org"` (the `repository.owner.login` branch, taking priority over the fallback), so `Shipit.github(organization: "attacker-org")` is selected and the signature check passes using a secret the attacker legitimately holds. `drop_unhandled_event` passes because `membership` has a registered handler. `MembershipHandler` then creates `Team.find_or_create_by!(github_id: 999999) { |team| team.organization = "victim-org"; ... }` and adds `attacker-user` as a member of that team — all authorized solely by attacker-org's signature.

Existing guards do not stop this: `verify_signature` only checks the raw HMAC against whichever org string `repository_owner` resolves to; it has no notion of "the org that should match the payload's business data." The `ExplicitParameters` schema in `MembershipHandler` validates presence/types of `organization.login` but has no field or check for `repository.owner.login`, so there is no cross-check between the field used for authentication and the field used for authorization/data-write. `GithubOrganizationUnknown` only guards against an org with no configured GitHub App at all — it does not fire here because `attacker-org` is validly configured.

### Impact Explanation
The attacker forges creation (or later resolution, since `find_or_create_by!` keys off `github_id`) of a `Team` row whose `organization` column is `"victim-org"`, entirely verified under the attacker's own org signature, and can add arbitrary GitHub logins (including their own) as members of that row via the `added` action. This is a real cross-tenant write: a payload signed by `attacker-org` mutates state scoped to `victim-org`. Two concrete downstream consequences follow from code already inspected:
- `Team#github_hooks` (`app/models/shipit/team.rb:10-15`) and `Team::REQUIRED_HOOKS` join `GithubHook::Organization` by the `organization` foreign/primary key, so a forged `Team` with `organization: "victim-org"` participates in lookups scoped by that column for any future legitimate `victim-org` webhook processing that relies on this join, corrupting/duplicating those hook records for an org the attacker doesn't control.
- `Shipit.github_teams` (`lib/shipit.rb:256-258`) computes privileged team membership via `Team.find_or_create_by_handle(handle)` (`app/models/shipit/team.rb:18-21`), which does `find_by(organization:, slug:)` **before** ever hitting the GitHub API. If the attacker predicts or knows a configured `oauth_teams` handle (e.g. `"victim-org/some-team"`), they can pre-forge a `Team` row with `organization: "victim-org"`, `slug: "some-team"`, and add themselves as a member entirely via this forged webhook — short-circuiting `find_or_create_by_handle` into returning the attacker-controlled row instead of fetching real membership from GitHub. This is a path toward unauthorized escalation into `Shipit.github_teams` authorization, matching the "High" severity category in scope.

This is repeatable against any org for which the attacker knows or guesses a `team.id`/handle, is not limited to a single request, and the attacker never needs `victim-org`'s `webhook_secret`.

### Likelihood Explanation
Preconditions: the attacker must run their own GitHub App/organization already configured in Shipit's multi-org `secrets.github` map (i.e. `attacker-org` is a legitimately onboarded org with its own `webhook_secret`), and must know or guess the target `victim-org`'s login string and, for the `github_teams` escalation, a configured `oauth_teams` handle/slug. All of this is attacker-controlled or low-cost to obtain (org names and OAuth team handles are typically not secret). No Shipit session, API token, or victim secret is required — only crafting an arbitrary JSON body and signing it with a secret the attacker legitimately possesses. This is cheap and fully repeatable.

### Recommendation
In `WebhooksController#repository_owner`/`verify_signature`, and in each handler that derives authorization-relevant data from `organization.login` (e.g. `MembershipHandler`), require that the organization used for signature verification and the organization used for any data write/authorization decision are the same value from the same trusted field, and reject the webhook if they diverge. Concretely: for `membership` events, drive both signing and `Team#organization` from a single canonical field (e.g. `params.dig('organization','login')` only, dropping the `repository.owner.login` precedence for this event type, or vice versa), and add an explicit equality assertion between them before processing.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Configure two orgs in test secrets: `attacker-org` with `webhook_secret_a`, `victim-org` with `webhook_secret_v` (attacker does not know `webhook_secret_v`).
2. Build a `membership` payload with `repository: { owner: { login: 'attacker-org' } }` and `organization: { login: 'victim-org' }`, `team: { id: 424242, name: 't', slug: 'forged', url: '...' }`, `member: { login: 'attacker-user' }`, `action: 'added'`.
3. Sign the raw body with `webhook_secret_a` and POST to `/webhooks` with `X-Github-Event: membership`.
4. Assert response is `200`/`204` (not `422`), proving `verify_signature` accepted an attacker-org-signed request.
5. Assert `Shipit::Team.find_by(github_id: 424242).organization == 'victim-org'` — proving the write landed under the victim's org despite being authenticated with the attacker's org secret, i.e. `repository.owner.login ("attacker-org") != params.organization.login ("victim-org")` yet both were accepted without cross-check.
6. Optionally assert the created team's `members` includes `User.find_by(login: 'attacker-user')`, and that `Shipit::Team.find_or_create_by_handle('victim-org/forged')` returns this same forged row instead of hitting the GitHub API.
