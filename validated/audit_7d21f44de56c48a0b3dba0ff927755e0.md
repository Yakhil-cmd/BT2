### Title
Webhook signature is verified against an organization derived from the payload while write actions are keyed off an unverified `repository.full_name`, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using an organization name pulled straight out of the untrusted JSON body, while every event handler that actually performs writes (enqueuing sync jobs, archiving/unarchiving review stacks, updating pull request state, etc.) resolves its target `Repository`/`Stack` from a *different* field of that same untrusted body (`repository.full_name`). Nothing ties these two fields together, so a caller who legitimately knows the webhook secret configured for one organization in a multi-tenant Shipit install can forge a signature that "authenticates" that organization while pointing all the actual side effects at an unrelated repository/stack belonging to a different organization.

### Finding Description
`WebhooksController` computes the organization used to look up the verification secret purely from request body content: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and is used to call `Shipit.github(organization: repository_owner)`, which in a multi-org deployment looks up a per-organization `webhook_secret` from `secrets.github[org]`: [3](#0-2) 

Once the signature check passes, `create` dispatches the parsed JSON body to the matching `Shipit::Webhooks::Handlers::Handler` subclasses: [4](#0-3) 

Every handler, however, resolves the repository/stack to act on from `payload.dig('repository', 'full_name')` — a sibling field of the payload that is never checked for consistency with the `repository.owner.login` value used for signature verification: [5](#0-4) [6](#0-5) 

The same pattern repeats in every pull-request handler, which independently re-derives `repository` from `params.repository.full_name` and then mutates state (`archive!`, `unarchive!`, `update`) on whatever `Stack`/`PullRequest` that resolves to: [7](#0-6) [8](#0-7) [9](#0-8) 

Because `repository.owner.login` and `repository.full_name` are ordinary JSON fields inside the same attacker-controlled HTTP body (the request is not a byte-for-byte relay of a GitHub-originated payload that a caller cannot construct — anyone who possesses the secret can build any JSON body and sign it), the two values can be made inconsistent: e.g. `repository.owner.login = "orgA"` (so `Shipit.github(organization: "orgA")`'s `webhook_secret` is the one checked and it passes) while `repository.full_name = "orgB/private-repo"` (an entirely different, unrelated stack registered under a different organization in the same Shipit instance).

This breaks the trust binding the engine intends: *the organization whose secret authenticated the request* == *the repository whose data gets written*. The rules explicitly call out this exact class of binding as in-scope ("an organization that authenticated versus the repository that is written").

### Impact Explanation
An attacker who legitimately controls the webhook integration/secret for one organization onboarded to a shared, multi-tenant Shipit instance (`Shipit.github_organizations` supports several orgs each with independent `webhook_secret`, per `lib/shipit.rb#github`/`#github_app_config`) can forge signed webhook deliveries that pass `verify_signature` under their own organization's identity but carry a `repository.full_name` pointing at a stack owned by a completely different, unrelated organization. Depending on the event type dispatched, this yields cross-repository/cross-tenant writes without any legitimate access to the target repository:
- `push` events enqueue `GithubSyncJob` for the victim stack.
- `pull_request` `opened`/`closed`/`reopened`/`labeled`/`unlabeled` events can create, archive, or unarchive review stacks belonging to the victim repository, and can overwrite stored PR state (`pull_request.update(github_pull_request: params.pull_request)`).
- `status`/`check_suite` events can inject fabricated commit statuses/check runs against a victim stack's commits, which can influence deploy-gating logic elsewhere in the engine.

This is a cross-repository write performed by an entity that authenticated as a different organization than the one it is modifying, matching the "Critical: cross-repository writes" impact bucket in scope.

### Likelihood Explanation
Requires the attacker to know a `webhook_secret` value configured for some organization in the Shipit deployment. In single-organization deployments this is an operator secret and out of scope for an unprivileged attacker; but the engine explicitly supports and documents multi-organization configuration (`TOP_LEVEL_GH_KEYS`, `github_app_config`, `secrets.github.keys`), where different organizations/teams onboarded to a shared Shipit instance may each be the ones who provision and therefore know their own `webhook_secret`. Any such tenant is "unprivileged" with respect to every other tenant's repositories, so the crossing of the trust boundary is real whenever more than one organization/secret is configured. No GitHub App private key, session, or `ApiClient` token is needed — only the HMAC secret for the attacker's own organization and network access to the `/webhooks` endpoint.

### Recommendation
Bind the two fields together: after (or as part of) `verify_signature`, re-derive the target repository/organization strictly from the value that was authenticated (`repository_owner`) and reject or ignore any handler processing where `payload.dig('repository', 'full_name')`'s owner segment does not match the organization whose secret verified the signature. Concretely, in `WebhooksController#verify_signature` (or in the base `Handler`), assert that `repository_name.split('/').first.downcase == repository_owner.downcase` before invoking any handler, and fail closed (422) otherwise.

### Proof of Concept
Assume a multi-org Shipit instance with two configured organizations, `orgA` (attacker-controlled, secret known to attacker) and `orgB` (victim, has a stack `orgB/victim-repo` registered).

1. Attacker builds a `pull_request` "opened" webhook body:
```json
{
  "action": "opened",
  "number": 42,
  "pull_request": { "...": "..." },
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" },
  "sender": { "login": "attacker" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` using the secret they legitimately possess for `orgA`.
3. `POST /webhooks` with header `X-Github-Event: pull_request`.
4. `WebhooksController#repository_owner` returns `"orga"`; `Shipit.github(organization: "orga")` returns orgA's `GitHubApp`, whose `verify_webhook_signature` succeeds (per `lib/shipit/github_app.rb#verify_webhook_signature`).
5. `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler`, whose `repository` method resolves `Repository.from_github_repo_name("orgb/victim-repo")` — a stack the attacker has no legitimate access to — and calls `ReviewStackAdapter#find_or_create!`, provisioning/mutating state on the victim's stack.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
