### Title
Unfunded `recapitalize` refunds drain the pool's entire token custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` op assumes the caller has already transferred `amount` tokens into the pool ("The controller transfers `amount` into the pool before this call"), but the pool never verifies that any funds actually arrived. It computes `refund = amount - min(amount, backing_shortfall)` and unconditionally transfers `refund` back to `payer`. When the market has no backing shortfall, `applied = 0` and the full declared `amount` is refunded — paid out of real supplier custody — even though the caller sent nothing. The pool's own test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates custody drained to zero while the cash book still reports solvency.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `accounting` (lines 44-67) computes:

```rust
let applied = amount.min(guards::backing_shortfall(&cache));
let refund = amount.checked_sub(applied)?;
cache.credit_cash(applied);
cache.commit();
```

`apply` (lines 26-38) then executes `outcome.cache.transfer_out(&payer, outcome.refund)` — a real token transfer out of the pool — with no balance check that the pool's token balance actually increased by `amount` beforehand. Unlike the flash-loan path, which takes a `pre_balance` snapshot and enforces `balance_after_payout` / `balance_after_repayment` equality (`contracts/pool/src/ops/flash.rs:106-120`, `terms`), recapitalize performs a purely *declared*-amount settlement: it trusts the caller's `amount` argument rather than measuring the balance delta. When `backing_shortfall == 0` (healthy market), a call with `amount = pool_balance` yields `applied = 0`, `refund = pool_balance`, and `transfer_out` sends the entire custody to `payer`.

The UAF analog: `fz_keep_key_storable` kept a stale reference alive and reused it; here the declared `amount` is a stale/unbacked claim on custody that is "kept" through accounting and then used to authorize a real transfer, divorced from the actual resource state.

### Impact Explanation
Theft of user funds and protocol insolvency. A single call drains the market's entire token balance to the attacker while `cash` book state is unchanged. Subsequent supplier withdrawals pass `require_reserves` (which reads the book, not the balance) and then fail inside the SAC transfer — permanent freezing of remaining claims, as proven by the assertions in `contracts/pool/tests/flows.rs:3430-3483` (`token.balance(&t.pool) == 0`, withdraw fails with SAC `BalanceError = 10`, book still overstating custody).

### Likelihood Explanation
Reachability depends on the pool's caller gate: `contracts/pool/tests/flows.rs:3432` invokes `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` directly with a freshly generated `payer` and no controller involvement or prefunding, indicating the entrypoint is not restricted to a pre-funded controller flow (or at most requires `payer.require_auth()`, which the attacker supplies). If a controller-auth gate exists on this entrypoint, the attack degrades — but `controller::recapitalize` routes through the funding path, so the vulnerability stands or falls on the pool's auth check; nothing in `recapitalize.rs` itself performs one, and no balance-delta check substitutes for it. Cost to the attacker is zero tokens.

### Recommendation
Measure settlement instead of trusting the declared amount: snapshot `token.balance(pool)` before crediting, require `balance_after >= balance_before + applied` before refunding, or only refund the measured excess (`received - applied`). Alternatively enforce the funding precondition by having the pool pull `amount` via `transfer_from` (as `collect_repayment` does for flash loans) rather than assuming a prior push.

### Proof of Concept
From `contracts/pool/tests/flows.rs:3408-3433`:

```rust
token_admin.mint(&t.pool, &deposit);
t.client().supply(&t.sup(0, deposit));           // real supplier liquidity
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody); // no transfer in
assert_eq!(token.balance(&t.pool), 0);           // all custody to payer
```

The supplier's subsequent withdraw clears `require_reserves` and fails in the SAC transfer, confirming the pool reports itself solvent while holding nothing.
