### Title
Unvalidated `arbiter_address` embedded as the trusted fund-release oracle in arbiter contracts - ([File: arbiter_contract.js])

### Summary
The bonding-token report shows a factory function that accepts a user-supplied `_router` address without validating it against a known/trusted list, letting the caller embed an attacker-controlled address as the component that will later control fund flow. The same pattern exists in ocore's arbiter-contract (escrow) feature: the `arbiter_address` supplied when creating an arbiter contract is never validated to be a legitimate address, let alone a genuine registered arbitrator, before it is persisted and later embedded into the shared multisig address definition that ultimately controls release of escrowed funds.

### Finding Description
`createAndSend` builds and stores a new arbiter contract straight from caller-supplied fields, including `arbiter_address`, with no address-format or legitimacy check at all: [1](#0-0) 

The same unchecked value is persisted when a contract is received from a peer via `store`: [2](#0-1) 

Later, `deriveSharedAddress` uses `contract.arbiter_address` directly as the oracle address inside the `in data feed` conditions of the shared (multisig escrow) address definition — this is the address whose signed `data_feed` message decides which party (offeror or acceptor) receives the escrowed funds: [3](#0-2) 

The only "check" performed on the arbiter address is `arbiters.getArbstoreInfo`, which merely asks the hub for a URL associated with that address and parses whatever info the URL returns — it does not authenticate that the address belongs to a trustworthy, independent arbitration service: [4](#0-3) 

Finally, dispute resolution trusts any unit authored by `contract.arbiter_address` unconditionally: [5](#0-4) 

This mirrors the reported bug class exactly: a critical, fund-controlling address parameter (`_router` in the report, `arbiter_address` here) is accepted from an unprivileged party (the contract "offeror", who is simply the counterparty proposing the private escrow deal — reachable without any special privilege) and is never checked against a trusted registry before being wired into the logic that moves funds.

### Impact Explanation
If the offeror (a normal counterparty in a private arbiter contract) sets `arbiter_address` to an address they themselves control (or an accomplice controls), and the counterparty proceeds to fund the resulting shared address (`createSharedAddressAndPostUnit` / `complete`), the "arbiter" can unilaterally post a `data_feed` unit naming themselves as winner via `parseWinnerFromUnit`, satisfying the `in data feed` branch of the shared-address definition and diverting the escrowed base/asset funds to the offeror instead of the honest counterparty. This is unauthorized fund loss for the honest party in the escrow, exactly analogous to draining ETH from token sales via a poisoned router.

### Likelihood Explanation
Likelihood is high: setting up such a contract requires no elevated privilege — any wallet user can propose an arbiter contract with any `arbiter_address` value, and there is no local validation (`isValidAddress`) or cross-check against a known/attested arbiter list anywhere in `createAndSend`, `store`, or `respond`. The victim's only real protection is inspecting the arbiter identity out-of-band (e.g., in the UI) before agreeing to a contract, which is a social/UX safeguard, not a code-enforced one.

### Recommendation
Validate `arbiter_address` at the point contracts are created/stored/accepted:
- Require `isValidAddress(objContract.arbiter_address)` in `createAndSend` and `store`.
- Before allowing an acceptor to sign/fund the derived shared address, require confirmation from `arbiters.getArbstoreInfo`/a genuine registry that `arbiter_address` corresponds to a known, previously-vetted arbitration service (e.g., pinned/allow-listed arbstore addresses, or attestation similar to `checkAttestorList` used for asset attestors in `validation.js`), rather than trusting whatever a hub lookup returns.
- Surface a clear warning/blocking check in the acceptance flow when the arbiter is unknown/unverified, so users cannot be silently steered into an escrow controlled by their counterparty.

### Proof of Concept
1. Attacker (as offeror) calls the arbiter-contract creation flow with `arbiter_address = <address I control>` — accepted without validation: [1](#0-0) 
2. Victim (as acceptor) accepts and signs; `createSharedAddressAndPostUnit`/`deriveSharedAddress` embeds the attacker's `arbiter_address` as the trusted `in data feed` oracle controlling fund release: [3](#0-2) 
3. Victim funds the shared address (`complete`/payment to `shared_address`).
4. Attacker, using the private key of `arbiter_address`, posts a `data_feed` unit with key `"CONTRACT_"+hash` naming themselves as winner, satisfying `parseWinnerFromUnit`'s only check (`objUnit.authors[0].address === contract.arbiter_address`): [5](#0-4) 
5. The shared-address definition's `in data feed` branch is satisfied, and the attacker can now spend the escrowed funds to themselves — unauthorized fund loss.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
