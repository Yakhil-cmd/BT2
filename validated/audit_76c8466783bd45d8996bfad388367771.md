### Title
Webhook signature is verified against `repository.owner.login`'s org secret while the handler trusts `repository.full_name` for a different org, enabling cross-tenant stack creation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used for HMAC verification based on `repository.owner.login` (or `organization.login`), whereas `OpenedHandler#process` (via `#repository`) resolves the target `Shipit::Repository` from the unrelated `repository.full_name` field. Because these two payload fields are never cross-checked, an attacker who controls an org configured in Shipit's multi-org `github` secrets (with a known `webhook_secret`) can sign a payload with their own secret while pointing `repository.full_name` at any other tracked repository, causing Shipit to provision a `ReviewStack` under the victim repository at an attacker-controlled ref.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`organization_used_for_signature_verification(repository_owner) == organization_owning(params.repository.full_name)` — **false**.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(signature_header, raw_body)`. [2](#0-1) 
2. `Shipit.github(organization:)` — in the multi-org configuration (`github_default_organization` present), it does `config = github_app_config(organization)` and builds a `GitHubApp` keyed strictly by that `organization` argument, using **that org's own `webhook_secret`**. [3](#0-2) 
3. `verify_webhook_signature` does a plain `SecureCompare.secure_compare(signature, HMAC-SHA1(webhook_secret, raw_body))` — it authenticates *that request came from someone who knows `attacker-org`'s secret*, nothing about which repository the payload claims to describe. [4](#0-3) 
4. Once verified, `WebhooksController#create` parses the raw body itself (`JSON.parse(request.raw_post)`) and dispatches to handlers, passing this independently-parsed hash. [5](#0-4) 
5. `Handler.call` → `new(payload).process`, where `@params = self.class.param_parser.parse!(payload)` only validates the shape declared by `OpenedHandler.params` — it requires `repository.full_name` as a `String` but never validates or compares `repository.owner.login`. [6](#0-5) [7](#0-6) 
6. `OpenedHandler#repository` calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, splitting on `/` and doing a plain `find_by(owner:, name:)` lookup with no relation whatsoever to which org authenticated the request. [8](#0-7) [9](#0-8) 
7. If `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` (attacker's stated precondition for `victim/prod-app`), `respond_to_pull_request_opened?` is true and `process` runs `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, provisioning a stack under `victim/prod-app`'s `review_stacks` association, checked out at the attacker's fully-controlled `pull_request.head.sha`/`ref`. [10](#0-9) 

**Attacker's exact request**: a direct `POST /webhooks` (no live GitHub interaction needed) with header `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=<HMAC using attacker-org's known webhook_secret over the raw body>`, and JSON body:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { "...": "attacker-controlled head.sha/ref, labels, etc." },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim/prod-app" },
  "sender": { "login": "attacker" }
}
```
`repository.owner.login` drives step 1-3 (signature acceptance using attacker-org's own secret); `repository.full_name` drives steps 5-7 (which tenant's repository/stacks get mutated). Nothing in the code ties these two together.

**Why existing guards fail**: `verify_signature` only proves "the sender knows *some* configured org's secret," not "the sender is authorized for the repository named in the payload." `drop_unhandled_event` and `check_if_ping` are unrelated gating on event type. The `ExplicitParameters` schema in `OpenedHandler.params` validates types/presence of `repository.full_name` but has no rule requiring it to be prefixed by `repository_owner`/`repository.owner.login`. `Repository#from_github_repo_name` and `Repository.owner`/`name` format validators only constrain what's already stored in the DB (lowercase alnum/`-_.`), they say nothing about which org authenticated the current request. There is no `force_github_authentication`, `require_permission!`, or `User#authorized?` check anywhere in this webhook path since webhooks are meant to be server-to-server, machine-authenticated by HMAC alone — and that HMAC binding is exactly what's broken.

### Impact Explanation
A payload that authenticates as belonging to `attacker-org` is used to mutate state (create a `Shipit::Repository`less lookup hit, `Shipit::ReviewStack`, `Shipit::PullRequest`, and queue provisioning/deploy tasks) scoped to an entirely different tenant's repository (`victim/prod-app`). This is a payload-for-one-repository-mutating-another's-stack scenario, matching the Critical severity bucket in the rules. The blast radius is any repository tracked by Shipit whose owning org has `review_stacks_enabled` and `provisioning_behavior_allow_all?` (or a guessable/known provisioning label), regardless of which org's app config the attacker used to sign the request — i.e., cross-tenant in any Shipit deployment using the multi-org `github:` secrets layout. It is fully repeatable: each request can provision (or, via the `ClosedHandler`/`LabeledHandler`, also archive/relabel) stacks under the victim repository indefinitely, and can drive a checkout/deploy of an attacker-chosen `head.sha`/`ref` into the victim repository's review stack.

### Likelihood Explanation
Requires: (a) the Shipit instance configured with the multi-org `github:` secrets layout (documented as the standard way to support multiple GitHub orgs — `docs/setup.md` "Using Multiple Github Applications"), (b) the attacker's own org present as one of those configured orgs with a `webhook_secret` they set/know (attacker fully controls setup of their own org's GitHub App and its webhook secret, so this is attacker-chosen, not a leaked secret), and (c) the victim repository already tracked with `review_stacks_enabled` + `provisioning_behavior_allow_all?` (a common permissive default for review-stack workflows). Attacker cost is a single crafted HTTP POST with a self-computed HMAC — no GitHub interaction, no privileged Shipit role, and no secrets beyond the attacker's own org's. This is fully repeatable and requires no timing/race conditions.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository`/`OpenedHandler#repository`), enforce that the organization whose secret validated the signature matches the org portion of `repository.full_name` (and/or `organization.login` for org-level events) before dispatching to any handler — e.g., reject with 422 if `repository_owner.casecmp?(params.repository.full_name.split('/').first)` is false. This closes the gap between the HMAC-authenticated identity and the repository the payload claims to describe.

test "cross-org payload authenticated by org A cannot create a stack under org B's repository" do
  # Arrange: multi-org secrets stubbed so 'attacker-org' and 'victim' are both configured,
  # each with its own distinct webhook_secret.
  Shipit.stubs(:github_default_organization).returns('attacker-org')
  attacker_app = Shipit::GitHubApp.new('attacker-org', webhook_secret: 'attacker-secret')
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_app)

  victim_repo = shipit_repositories(:victim) # owner: 'victim', name: 'prod-app'
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = payload_parsed(:pull_request_opened)
  payload['repository']['owner'] = { 'login' => 'attacker-org' } # signs as attacker-org
  payload['repository']['full_name'] = 'victim/prod-app'          # targets victim's repo
  body = payload.to_json
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)

  assert_no_difference -> { victim_repo.review_stacks.count } do
    post :create, body:, as: :json
  end

  # is created under victim_repo.review_stacks despite being signed by attacker-org.
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret
