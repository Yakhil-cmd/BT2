### Title
AccountKeyFail Sub-Key in RoleBased Slot Bypassed via Cross-Type Replacement in `CheckReplacable` — (`blockchain/types/accountkey/account_key.go`)

### Summary

`AccountKeyFail` placed in a `RoleFeePayer` slot of an `AccountKeyRoleBased` key is supposed to permanently prevent the account from acting as a fee payer. However, `CheckReplacable` only enforces `AccountKeyFail`'s immutability when the replacement key is the **same type** (`Fail → Fail`). When the replacement is a **different type** (e.g., `Fail → Public`), `CheckReplacable` skips `oldKey.CheckUpdatable` entirely and only validates the new key via `CheckInstallable`, which succeeds for any valid public key. This allows a holder of the `RoleAccountUpdate` key to overwrite the `AccountKeyFail` sub-key and re-enable fee-payer capability.

### Finding Description

`CheckReplacable` in `blockchain/types/accountkey/account_key.go` (lines 123–128):

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    return newKey.CheckInstallable(currentBlockNumber)
}
``` [1](#0-0) 

When `oldKey` is `AccountKeyFail` and `newKey` is `AccountKeyPublic`, the types differ, so the function calls only `newKey.CheckInstallable(...)`. `AccountKeyFail.CheckUpdatable` — which unconditionally returns `ErrAccountKeyFailNotUpdatable` — is never invoked. [2](#0-1) 

Inside `AccountKeyRoleBased.CheckUpdatable`, for each non-Nil slot in the new key that is within the bounds of the old key, the `default` branch calls `CheckReplacable((*a)[i], (*newKey)[i], ...)`: [3](#0-2) 

For slot i=2 (RoleFeePayer) with `(*a)[2] = AccountKeyFail` and `(*newKey)[2] = AccountKeyPublic`, `CheckReplacable` returns `nil`, so `CheckUpdatable` returns `nil`, so `TxInternalDataAccountUpdate.Validate` passes: [4](#0-3) 

`Execute` then calls `stateDB.UpdateKey`, which reaches `AccountKeyRoleBased.Update`. That method calls `CheckUpdatable` again (same result: passes), then overwrites slot 2: [5](#0-4) 

The `AccountKeyFail` in the `RoleFeePayer` slot is replaced by the attacker's `AccountKeyPublic` in the state trie.

### Impact Explanation

After the update, the account's `RoleFeePayer` slot holds a valid `AccountKeyPublic`. Any fee-delegated transaction (`TxTypeFeeDelegated*`) signed by the corresponding private key will pass fee-payer signature validation. The attacker can submit fee-delegated transactions that charge fees to this account, draining its KAIA balance. This constitutes an unauthorized fee charge affecting KAIA funds — a direct match to the allowed impact gate.

### Likelihood Explanation

The attacker must control the `RoleAccountUpdate` key of an account whose `RoleFeePayer` slot is `AccountKeyFail`. This is a self-controlled account scenario (the attacker holds the update key), but the `AccountKeyFail` in the fee-payer slot may have been set as a deliberate, supposedly permanent restriction (e.g., by a protocol, governance action, or prior key holder). The transaction is a standard `TxTypeAccountUpdate` submitted through the public RPC — no privileged access is required beyond holding the `RoleAccountUpdate` key.

### Recommendation

In `CheckReplacable`, add an explicit check that the old key is not `AccountKeyFail` (or more generally, that the old key permits replacement regardless of type mismatch):

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    // Even on type change, the old key must permit being replaced.
    if err := oldKey.CheckUpdatable(newKey, currentBlockNumber); err != nil {
        return err
    }
    return newKey.CheckInstallable(currentBlockNumber)
}
```

Alternatively, `AccountKeyFail.CheckUpdatable` could be made type-agnostic (it already ignores the `newKey` argument and always returns the error), so calling it unconditionally is safe and correct.

### Proof of Concept

1. Create account `A` with key `RoleBased[PublicKey_B, PublicKey_U, AccountKeyFail]`.
2. Construct a `TxTypeAccountUpdate` from `A` with `newKey = RoleBased[AccountKeyNil, AccountKeyNil, PublicKey_FP]`.
3. Sign with `PublicKey_U` (the `RoleAccountUpdate` key).
4. Submit via public RPC (`eth_sendRawTransaction` / `kaia_sendRawTransaction`).
5. Observe that `stateDB.GetKey(A)` now returns `RoleBased[PublicKey_B, PublicKey_U, PublicKey_FP]` — `AccountKeyFail` is gone.
6. Submit a fee-delegated value transfer with `A` as fee payer, signed by `PublicKey_FP`. Observe that fees are deducted from `A`'s balance, confirming the invariant is broken.
