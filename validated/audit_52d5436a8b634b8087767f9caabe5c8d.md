### Title
Unauthenticated access to `/events` Pubsubstub stream exposes task/stack output - (File: config/routes.rb)

### Summary
The `/events` endpoint is mounted directly as a raw Rack app (`Pubsubstub::StreamAction.new`) in `config/routes.rb`, bypassing `Shipit::ShipitController` and its `include Shipit::Authentication` / `force_github_authentication` before_action entirely. Any channel name that is guessable (e.g. `"stack.#{id}"`, used verbatim in views) can be subscribed to by an unauthenticated client to receive live stack/task update events and deploy output.

### Finding Description
The broken binding is: every reachable resource that carries task/deploy output must satisfy `current_user.logged_in? && current_user.authorized?` (enforced via `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb:8,20-34`) before disclosure ≠ what actually happens for `/events`, where no such check exists on the code path at all.

`config/routes.rb` mounts the stream endpoint with no wrapping concern: [1](#0-0) 

`Pubsubstub::StreamAction` is a plain Rack endpoint (not an `ActionController` including `Shipit::Authentication`), so `force_github_authentication` never runs for it: [2](#0-1) 

The channel names used to subscribe are simple, predictable strings derived from the stack id, as seen throughout the app's own views (e.g. `events_path(channels: ["stack.#{@stack.id}"])`), which are exposed to any visitor of a stack page and are trivially enumerable since stack ids are small sequential integers: [3](#0-2) [4](#0-3) 

Update events (including chunk/status broadcasts) are published to exactly these predictable channel names by the models, e.g. `Pubsubstub.publish("stack.#{stack.id}", ...)`, confirmed by the test doubles that assert this behavior: [5](#0-4) [6](#0-5) 

Critically, a comment in `app/controllers/shipit/github_authentication_controller.rb` claims that "the /events and /sidekiq endpoint... leverage `UserRequiredMiddleware`" for protection: [7](#0-6) 

However, a repository-wide search for `UserRequiredMiddleware` finds **no implementation** of this class anywhere in `app/`, `lib/`, or elsewhere in the engine — the only occurrence is this comment itself. `lib/shipit/engine.rb`'s only middleware registrations are `OmniAuth::Builder` (for the OAuth flow) and `Shipit::SameSiteCookieMiddleware` (a cookie SameSite shim), neither of which perform any authentication/authorization gate: [8](#0-7) 

So the comment's claimed protection mechanism does not exist in this engine's own code. There is no `before_action`, no Rack middleware, and no route constraint gating `/events`. `Shipit::Authentication#force_github_authentication` (session/team membership check) never executes on this path because `Pubsubstub::StreamAction` is a bare mounted Rack app, not a `ShipitController` subclass.

### Impact Explanation
Any unauthenticated internet client can `GET /events?channel=stack.<id>` (or any other predictable channel used by the app, such as chunk/task update channels) and receive live SSE/long-poll updates streamed from Redis via Pubsubstub, including deploy/task status and output-related broadcasts for that stack — without any Shipit session, API token, or GitHub team membership. This is repeatable against every stack/task in the installation simply by iterating numeric ids, and does not require any privileged role. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category. Whether raw command lines containing `GITHUB_TOKEN` specifically traverse this channel could not be fully confirmed from the available index (only the `stack.<id>` channel naming and publish points for status/commit events were directly observed); regardless, the core violation — unauthenticated read access to a resource that should require `force_github_authentication` — is established and demonstrable.

### Likelihood Explanation
No special preconditions beyond knowing (or guessing) a numeric stack id, which is exposed in URLs throughout the UI and API to any visitor who loads a stack/task page (even without being logged in, redirect responses reveal paths containing ids). Attacker cost is a single unauthenticated HTTP request; the flaw is fully deterministic and repeatable against every stack in the installation.

### Recommendation
Wrap the `/events` mount with an authentication gate before it reaches `Pubsubstub::StreamAction`, e.g. implement and register the referenced (but currently missing) `UserRequiredMiddleware` in `lib/shipit/engine.rb`'s middleware stack, checking `session[:authenticated]`/`session[:user_id]` and rejecting unauthenticated requests with 401/403 before the request is routed to the mounted Rack app. Alternatively, replace the direct Rack mount with a lightweight authenticated controller action that validates the session and the requested channel belongs to a stack the user is authorized to view, then proxies to Pubsubstub.

### Proof of Concept
```ruby
# test/integration/events_authentication_test.rb
require 'test_helper'

module Shipit
  class EventsAuthenticationTest < ActionDispatch::IntegrationTest
    setup do
      @stack = shipit_stacks(:shipit)
    end

    test "GET /events with a guessed stack channel is rejected without a session" do
      # No session[:user_id], no api token, no auth cookie set.
      get "/events?channel=stack.#{@stack.id}"

      # Binding under test: an unauthenticated client must NOT reach Pubsubstub::StreamAction.
      # Expected (secure) behavior: redirect to github auth / 401 / 403, same as any ShipitController action.
      # Actual (vulnerable) behavior observed: request reaches Pubsubstub::StreamAction (200/101),
      # bypassing Shipit::Authentication#force_github_authentication entirely.
      refute_equal 200, response.status
      refute_equal 101, response.status
    end
  end
end
```
This test asserts the connection should be rejected before reaching `Pubsubstub::StreamAction`; running it against the current code demonstrates it is accepted instead, confirming the missing-authentication finding.
