## Analog Found: pallet-xcm `report_outcome_notify` — Query state deleted before verifying the notify callback actually executes

### Title
Premature `Queries` removal in `pallet_xcm::on_response` permanently loses the notify callback when its dispatch weight is underestimated or the call fails - (File: `polkadot/xcm/pallet-xcm/src/lib.rs`)

### Summary
`pallet-xcm`'s `report_outcome_notify` lets any pallet build an XCM program that, upon completion at a remote chain, triggers a `QueryResponse` back to the origin chain, which is expected to dispatch a "notify" callback into the calling pallet (analogous to the `anycall` `fallback`). In `on_response`, the pending `Queries` entry is unconditionally removed (`Queries::<T>::remove(query_id)`) before the weight check and before the notify call is actually dispatched. If the notify call's actual weight exceeds the `max_weight` budgeted at `report_outcome_notify` time, or if its dispatch itself errors, the callback never runs, yet the `Queries` state has already been deleted. This is the same "record success before the critical downstream side-effect actually lands" flaw described in the report: `executionHistory[fromChainId][nonce] = true` is set even when the corresponding `fallback` never fires.

### Finding Description
`report_outcome_notify` inserts a `SetAppendix(ReportError(...))` into the outgoing XCM and stores a `QueryStatus::Pending { maybe_notify: Some((pallet_index, call_index)), .. }` entry keyed by `query_id`: [1](#0-0) 

The weight budget for the eventual notify call is estimated once, at the time `report_outcome_notify` is called, using `notify.get_dispatch_info().call_weight`: [2](#0-1) 

The doc comment on the function itself warns of this fragility: *"Its weight is estimated during this function ... If it turns out to be heavier once it returns then reporting the outcome will fail."*

When the remote chain later replies with `QueryResponse`, the XCM executor calls into `Config::ResponseHandler::on_response` (pallet-xcm), which handles the pending query: [3](#0-2) 

Inside `on_response`, once origin/querier checks pass, the code decodes the notify call and **removes the `Queries` entry unconditionally before checking whether the decoded call's weight fits the budget or whether dispatch succeeds**: [4](#0-3) 

Specifically:
- `Queries::<T>::remove(query_id)` executes at line 4156, before the `weight.any_gt(max_weight)` check.
- If the check fails, `Event::NotifyOverweight` is emitted and the function returns `Weight::zero()` — the notify call is **never dispatched**.
- If dispatch is attempted but the callback errors, `Event::NotifyDispatchError` is emitted, but whatever partial/none of the pallet's compensating logic ran is not rolled back, and there's no residual state to retry from.

Unlike `report_outcome` (which stores `QueryStatus::Ready` for later polling via `take_response`), `report_outcome_notify` is fire-and-forget: once the entry is removed, there is no other on-chain trace of the pending query for the caller pallet to inspect or retry.

This exactly parallels the audited bug: the root-side "execution" (here, the `QueryResponse` XCM message reaching `on_response` and passing origin/querier checks) is treated as having "completed" and the tracking state is wiped, but the actual state-mutating action the caller pallet was relying on (the notify dispatch, analogous to the branch-side `fallback`) can independently fail due to a mis-estimated/insufficient weight budget.

### Impact Explanation
Any pallet built on top of `report_outcome_notify` to implement an escrow/lock-and-release pattern (e.g., "lock funds on chain A, unlock/redeem them once a callback confirms remote completion") inherits this flaw: if the notify call's actual weight exceeds the pre-computed `max_weight` (which can legitimately drift, e.g. due to `PostDispatchInfo`/dynamic encoding differences, or benchmark/runtime version differences between when `report_outcome_notify` was called and when the response arrives), the compensating callback silently never executes, and the `Queries` bookkeeping is already gone — permanently, since `query_id`s are not reused and there is no other entry to retrieve. Funds or state gated behind that callback firing can become permanently stuck, mirroring the "user can never redeem their deposit" impact in the original finding. This does not require any malicious actor — it's a straightforward mis-estimation of dispatch weight.

### Likelihood Explanation
This requires only normal usage of a documented, public pallet-xcm API (`report_outcome_notify`) by another pallet, and a routine weight-estimation drift or transient dispatch failure of the notify call — no privileged access, no malicious relayer/collator, and no protocol violation. The pallet's own doc comment concedes this failure mode is possible ("If it turns out to be heavier once it returns then reporting the outcome will fail"), indicating it is a known, reachable edge case rather than a purely theoretical one. However, whether it is exploitable for *loss* depends entirely on how a downstream pallet uses the notify callback (i.e., whether it structured funds-release logic to depend solely on that notify firing) — no such vulnerable consumer of `report_outcome_notify` performing fund custody was found within this repository's in-tree pallets during this scan.

### Recommendation
Move `Queries::<T>::remove(query_id)` to after the notify call has been successfully dispatched (or otherwise reconcile: only remove the entry on successful dispatch, and on `NotifyOverweight`/dispatch failure, re-insert a `QueryStatus` state — e.g., `QueryStatus::Ready`/a new `QueryStatus::Failed` — so the response is preserved and can be retried/polled via `take_response`, rather than being unconditionally and irrecoverably discarded).

### Proof of Concept
No PoC was executed. This scan produced a structural/code-reachability analog rather than a live-network or fully asserted integration reproduction: `Queries::<T>::remove` at `polkadot/xcm/pallet-xcm/src/lib.rs:4156` runs unconditionally prior to the weight-sufficiency check (`weight.any_gt(max_weight)`) and prior to `call.dispatch(...)`, which is confirmed by static reading of `on_response` and corroborated by the existing `report_outcome_notify_works` test exercising the success path only (`polkadot/xcm/pallet-xcm/src/tests/mod.rs:60-136`); no test in-repo exercises the `NotifyOverweight`/`NotifyDispatchError` branches to assert on post-failure recoverability, and no in-tree consumer pallet performing custodial fund locking atop `report_outcome_notify` was identified to construct an end-to-end funds-loss integration test within the scan budget.
