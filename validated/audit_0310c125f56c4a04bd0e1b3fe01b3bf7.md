The reported bug is a Solidity/Uniswap-v3-specific fixed-point scaling defect in a hardcoded `sqrtPriceX96 / 2**12` shift inside a non-Polkadot-SDK contract (`GoodEntry`'s `poolMatchesOracle`). There is no directly analogous "pool price vs oracle price" comparison function in `polkadot-sdk` that reproduces this exact overflow pattern. The closest analogs are:

- `pallet-asset-conversion`'s `get_amount_out`/`get_amount_in`/`quote_price_*` functions, which use `T::HigherPrecisionBalance` and explicit `checked_mul`/`checked_div` at every step, returning `Error::<T>::Overflow` instead of silently overflowing or panicking. [1](#0-0) [2](#0-1) 
- `sp_arithmetic`'s `FixedPointNumber`/`FixedU128` sqrt and multiplication helpers, which use `checked_sqrt`, `checked_mul`, and `multiply_by_rational_with_rounding` to guard against overflow rather than doing raw bit-shift scaling. [3](#0-2) 
- `pallet-oracle` (Honzon), which is a permissioned data-feed pallet with no price-scaling/sqrt math comparable to the Uniswap `sqrtPriceX96` calculation. [4](#0-3) 

None of these use an unchecked, hardcoded bit-shift scale-down of an attacker/pool-supplied square-root price value the way the reported GoodEntry bug does; all arithmetic paths in these pallets go through `checked_*`/`saturating_*` operations that fail safely (returning `None`/`Error`) instead of silently overflowing. Since the underlying root cause (insufficient scale-down before squaring a raw `sqrtPriceX96`-like value) has no reachable analog in FRAME code guarded by checked arithmetic, there is no demonstrable Polkadot SDK equivalent of this finding.

			/// Compute the square root. If it overflows or is negative, then `None` is returned.
			pub const fn checked_sqrt(self) -> Option<Self> {
				if self.0 == 0 {
					return Some(Self(0));
				}
				if self.0 < 1 {
					return None;
				}
				let v = self.0 as u128;

				// Want x' = sqrt(x) where x = n/D and x' = n'/D (D is fixed)
				// Our preferred way is:
				//   sqrt(n/D) = sqrt(nD / D^2) = sqrt(nD)/sqrt(D^2) = sqrt(nD)/D
				//   ergo n' = sqrt(nD)
				// but this requires nD to fit into our type.
				// if nD doesn't fit then we can fall back on:
				//   sqrt(nD) = sqrt(n)*sqrt(D)
				// computing them individually and taking the product at the end. we will lose some
				// precision though.
				let maybe_vd = u128::checked_mul(v, $div);
				let r = if let Some(vd) = maybe_vd { sqrt(vd) } else { sqrt(v) * sqrt($div) };
				Some(Self(r as $inner_type))
			}
