### Title
Predictable Pseudo-Randomness via `number_from_seed()` Allows Trigger Senders to Grind AA Outcomes Before Posting - (File: `formula/evaluation.js`, `network.js`)

### Summary
Obyte's oscript exposes a `number_from_seed()` function that autonomous agents (AAs) use as their sole primitive for pseudo-random behavior (lotteries, games, random selection, etc.). The generated "randomness" is a deterministic `sha256` of caller-supplied seed material such as `trigger.data`, `trigger.unit`, or `timestamp` — all of which are fully known and/or chosen by the trigger sender *before* the unit is broadcast. Combined with the network's `light/dry_run_aa` RPC and the node's own `aa_composer.dryRunPrimaryAATrigger`, any unprivileged trigger sender can locally/remotely simulate the exact AA outcome for arbitrary candidate trigger content, iterate until a favorable "random" result is found, and only then post the single winning unit. This is the direct analog of the reported EVM bug where `block.timestamp`/user-controlled salts are used for pseudo-randomness and a caller can simulate results before deciding whether to submit the transaction.

### Finding Description
`number_from_seed(seed[, min[, max]])` computes `sha256(seed)` and maps the top 64 bits into `[0,1)` (or `[min,max]`), a fully deterministic hash-based PRF with no unpredictable/external entropy: [1](#0-0) 

Because this is a plain oscript function, an AA author has no other source of "true" randomness in the platform, and the natural and commonly-used seed material — `trigger.data`, `trigger.unit`, `timestamp`, `params`, etc. — is either directly composed by the trigger sender or bounded to a narrow window the sender controls:

- `trigger.data` is arbitrary attacker/user-supplied JSON in the unit's message payload; the trigger sender picks every value in it before signing/broadcasting the unit (evidenced throughout `test/aa_composer.test.js`, e.g. `trigger.data.x`, `trigger.data.aa`, salts, etc. used inside AA formulas): [2](#0-1) 
- `timestamp` is only loosely bounded — a unit's timestamp must be `>= parent's timestamp` and `<= now + max_seconds_into_the_future_to_accept` (default 5s), giving the composer a multi-second grinding window, and it is exposed to formulas as the `timestamp` keyword used directly in AA state formulas: [3](#0-2) [4](#0-3) 
- `trigger.unit` (the trigger's own unit hash) is computed locally by the composer from the unit's content before it is ever broadcast — the sender therefore knows this value with certainty prior to posting and can vary payload fields to steer it.

The critical amplifier is that the platform exposes a first-class facility to **simulate an AA response without posting**, both to full/light nodes over the wire and locally:

- `light/dry_run_aa` network request: any peer (light client) can submit an arbitrary `params.trigger` object and address and receive back the exact `arrResponses` (including any `number_from_seed`-derived outcomes, balances, state changes) *before ever broadcasting a real unit*: [5](#0-4) 
- `aa_composer.dryRunPrimaryAATrigger()` performs the full deterministic execution of the AA against a caller-supplied trigger, rolling back all DB/cache effects afterward, explicitly designed for pre-flight simulation: [6](#0-5) 

An attacker can therefore:
1. Compose a candidate trigger unit content (choosing `data` fields/salts and, within the allowed window, `timestamp`).
2. Call `light/dry_run_aa` (or run their own full node and call `dryRunPrimaryAATrigger` directly) with that exact trigger to see the deterministic `number_from_seed()`-derived outcome the AA would produce.
3. Repeat with different candidate data/timestamp values, at no cost (dry runs are rolled back, no fee, no chain footprint), until a favorable outcome is found.
4. Only then sign and broadcast the one winning unit as the real trigger.

This exactly mirrors the reported issue's attack pattern — simulate-then-commit against inputs the caller controls, with no economic cost to failed simulations (the report's own analogy to flashbots "revert-if-unfavorable, no-fee" grinding).

### Impact Explanation
Any AA built on top of `number_from_seed()` for meaningful randomness (lotteries, gambling AAs, item drops, chance-based games, random selection of counterparties, etc.) is fully predictable and grindable by its own trigger sender. This allows:
- Deterministic winning of chance-based payouts, draining AA balances (fund loss for other participants / the AA treasury).
- Manipulation of any "fair" random selection logic (e.g., random winner selection, random slashing/rewards) to always favor the attacker.
Since this affects fund distribution logic inside AAs reachable by any ordinary trigger sender, and can lead to concrete unauthorized extraction of AA funds, this is a Medium/High severity design flaw in the primitive the platform provides for this exact purpose, and it is worsened by the platform providing a zero-cost oracle (`light/dry_run_aa`) for grinding outcomes before commitment.

### Likelihood Explanation
Likelihood is high: `number_from_seed()` is the only randomness primitive documented/available in oscript, so any AA needing chance-based logic will use it, typically seeded from trigger-controlled data or timestamp for lack of any better source. The `light/dry_run_aa` command is unauthenticated and available to any connected peer, requiring no special privileges — making grinding trivial and free.

### Recommendation
- Discourage/disallow use of purely local/deterministic seeds (`trigger.data`, `trigger.unit`, `timestamp`, `params`) for `number_from_seed()` in security-sensitive AAs; document this risk prominently in the oscript reference for `number_from_seed`.
- Provide a genuinely unpredictable-at-request-time entropy source for AAs (e.g., derived from a future unit/ball hash not known to the trigger sender at composition time, or a data feed from a committed VRF oracle) rather than only hash-of-caller-supplied-seed.
- Consider restricting or rate-limiting `light/dry_run_aa` per requester/trigger-address combination, or requiring the dry run to use the *same* trigger.data/timestamp bounds enforced on-chain so that repeated grinding attempts are costlier (e.g., minimum interval between distinct dry-run attempts for the same address).
- At minimum, add prominent guidance/lint warnings when AA validation detects `number_from_seed()` being seeded (even indirectly) by `trigger.data`, `trigger.unit`, or `timestamp` without additional un-attacker-controlled entropy (e.g., a committed value from a prior, already-stable AA response).

### Proof of Concept
1. Deploy an AA whose state formula computes an outcome via, e.g., `number_from_seed(trigger.unit, 1, 100)` or `number_from_seed(trigger.data.salt, 1, 100)`, and pays out based on whether the number is below a threshold (a "coin flip" game), mirroring the reported pattern of `dRandomNumber`/`sRandomNumber` derived from user-influenced seeds and `block.timestamp` equivalents.
2. As the attacker/trigger sender, before broadcasting anything, repeatedly vary `data.salt` (and/or the timestamp within the accepted `now±5s`/`>=parent` window) and call the network command:
   ```
   { command: 'light/dry_run_aa', params: { address: <AA address>, trigger: { data: { salt: <candidate> }, outputs: {...} } } }
   ```
   handled in [5](#0-4) , which internally invokes [6](#0-5)  to compute the exact `number_from_seed()` outcome for that candidate — with no fee and no on-chain trace.
3. Once a candidate salt/timestamp yields a favorable payout, compose and broadcast the real trigger unit with those exact values; the resulting AA response deterministically reproduces the previously-simulated favorable outcome (verified by the same `number_from_seed` implementation in [7](#0-6) ).
4. Repeat indefinitely at zero cost per failed attempt, guaranteeing favorable draws systematically.
