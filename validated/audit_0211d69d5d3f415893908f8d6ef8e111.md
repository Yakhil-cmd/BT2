**Analysis:**

The file `hot_state_op_accumulator.rs` implements `BlockHotStateOpAccumulator`, an internal block-executor bookkeeping structure used during VM execution to decide which `StateKey`s should be promoted to "hot" state at block epilogue time. It has no connection to transaction admission, mempool, vm-validator, authenticator parsing, signer binding, sequence numbers, chain-id, expiry, or replay protection [1](#0-0) .

Additionally, the specific exploit mechanics described don't hold up against the code logic:

- `writes` is a monotonically growing set for the entire block — once a key is added via `self.writes.get_or_insert_owned(key)` on a write, it is never removed [2](#0-1) .
- Every subsequent read of that key, in any later transaction, is checked against `writes` first and skipped (`continue`) before it can be inserted into `to_make_hot` [3](#0-2) .

So a later re-read of a previously-written key cannot "re-insert it into `to_make_hot`" — the existing `written_keys_are_not_promoted` test already demonstrates this by reading key `2` again after it was written, and confirming it stays excluded from `get_keys_to_make_hot` [4](#0-3) . Extending that test with an additional read would not produce a different result, since the guard at line 63 is unconditional for the remainder of the block regardless of how many further reads occur.

This falls both outside the admission-boundary scope (no sender/signer/sequence/chain-id/replay implication) and does not demonstrate an actual logic flaw in the accumulator itself.

```rust
pub struct BlockHotStateOpAccumulator<Key> {
    /// Keys read but never written to across the entire block are to be made hot (or refreshed
    /// `hot_since_version` one is already hot but last refresh is far in the history) as the side
    /// effect of the block epilogue.
    ///
    /// Unordered: `StateKey`'s `Hash`/`Eq` use the precomputed key hash and `Arc` pointer
    /// equality, while `Ord` dereferences and compares key contents, so a per-read `BTreeSet`
    /// insert is comparatively costly. The deterministic order the epilogue needs is imposed
    /// once, when the cap is applied in `get_keys_to_make_hot`.
    to_make_hot: hashbrown::HashSet<Key>,
    /// Keep track of all the keys that are written to across the whole block, these keys are made
    /// hot (or have a refreshed `hot_since_version`) immediately at the version they got changed,
    /// so no need to issue separate HotStateOps to promote them to the hot state.
    writes: hashbrown::HashSet<Key>,
    /// To prevent the block epilogue from being too heavy.
    max_promotions_per_block: usize,
}
```

```rust
    fn written_keys_are_not_promoted() {
```
