### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-scoped token to read any stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to resolve the target stack directly from `Stack.from_param!`, instead of using the stack-scoped `stacks.from_param!` helper inherited from `BaseController`. This breaks the equality that `ApiClient#stack_id` is supposed to enforce: `stack a token authorizes == stack the token can touch`. A token created with a restrictive `stack_id` can still read the CI/deploy status of any other stack.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping for API clients that are bound to a single stack via `ApiClient#stack_id`: [1](#0-0) 

`stacks` restricts the queryable set to only the client's authorized stack when `stack_id` is set, and `stack` (the method every other API controller relies on) resolves the requested `params[:stack_id]` against that restricted set via `stacks.from_param!`.

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, not on the scoped `stacks` relation. The only authorization check applied is `require_permission :read, :stack`, which only checks that the `permissions` array on the `ApiClient` contains `"read:stack"` - it never validates that `params[:stack_id]` matches the client's own `stack_id`: [3](#0-2) 

Before/after framing of the binding that should hold and is broken:
- **Before (intended)**: `ApiClient(stack_id: A)` with `read:stack` permission → can only ever resolve `stack == A` for any endpoint, because `stack` is always derived from the `stacks` relation scoped by `current_api_client.stack_id`.
- **After (actual, in `CCMenuController`)**: the same `ApiClient(stack_id: A)` token, hitting `GET /api/stacks/:stack_id/ccmenu.xml` with `params[:stack_id] = B`, resolves `stack == B` because `CCMenuController#stack` bypasses the `stacks` scoping and queries `Stack.from_param!` unscoped.

Every other API controller (`Api::StacksController`, `Api::TasksController`, `Api::MergeRequestsController`, `Api::HooksController`) relies on `BaseController#stack`/`#stacks`, and the existing test suite confirms scoping is deliberate and enforced there: [4](#0-3) 

No equivalent test exists for `CCMenuController`, and the code path confirms scoping is absent for it.

### Impact Explanation
This is a cross-tenant/cross-repository authorization bypass: a legitimately issued `ApiClient` token that an operator deliberately scoped to a single stack (e.g., a CI/CD monitoring integration meant to see only its own project's build status) can instead read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) of every other stack managed by the Shipit instance, including stacks belonging to unrelated repositories/teams. This is an unauthorized read of stack state via a credential whose entire purpose was to be confined to one stack - matching the "stack a token authorizes vs stack it touches" trust binding explicitly called out as in-scope.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has `read:stack` permission and a non-null `stack_id` (a very common, intentionally-restricted configuration pattern, e.g. tokens auto-created by `CCMenuUrlController` for CCMenu integrations: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)`). No privilege escalation, no signature forgery, and no additional secret is needed - only changing the `stack_id` path/query parameter to a different stack's identifier. [5](#0-4) 

### Recommendation
Remove the `CCMenuController#stack` override and use the inherited, properly-scoped `BaseController#stack` method (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` can never resolve a stack outside of its authorized `stack_id`.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController#client`) an `ApiClient` scoped with `stack_id = stack_A.id` and `permissions = ["read:stack"]`, and hands the resulting `authentication_token` to an external CI dashboard for stack A only.
2. That token holder issues `GET /api/stacks/:stack_B_id/ccmenu.xml?token=<token>` where `stack_B` is a different, unrelated stack.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client has `read:stack`), and `stack` resolves `Stack.from_param!(params[:stack_id])` = `stack_B`, unscoped by the client's `stack_id`.
4. The response renders `stack_B`'s CI/deploy status (`lastBuildStatus`, lock state, activity, build label), which the token was never authorized to see.
