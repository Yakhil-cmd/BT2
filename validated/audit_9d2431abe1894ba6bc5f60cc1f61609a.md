### Title
Webhook signature verification org is decoupled from the processing target org, allowing cross-tenant stack mutation via a divergent `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret used to authenticate the request) using `repository.owner.login` / `organization.login`, but every event handler (`Shipit::Webhooks::Handlers::Handler#stacks`, and the `PullRequest::*Handler#repository` methods) resolves the actual `Repository`/`Stack` to mutate using the independent, attacker-controlled `repository.full_name` field from the same JSON body. Because these two fields are never compared, a webhook can be correctly signed/verified as belonging to one (attacker-controlled) GitHub org while its side effects are applied to a stack owned by a completely different org.

### Finding Description
The claimed binding is: `org key used to verify the webhook signature == org that owns the repository actually mutated by the handler`, i.e. `repository.owner.login (verification) == owner(repository.full_name) (processing)`.

Trace:
- `WebhooksController#verify_signature` picks the app/secret via `repository_owner`, which reads only `params.dig('repository','owner','login')` (fallback `organization.login`): [1](#0-0) [2](#0-1) 
- Once verification passes, `create` hands the raw, still attacker-controlled `params` hash to every handler for the event, with no re-derivation or cross-check against `repository_owner`: [3](#0-2) 
- Every handler resolves its target purely from `payload.dig('repository','full_name')`, via `Repository.from_github_repo_name`, with zero reference to the value used for signature verification: [4](#0-3) [5](#0-4) 
- `PushHandler#process`, for instance, enqueues a `GithubSyncJob`/`sync_github` for every non-archived stack of that resolved repository on the matching branch: [6](#0-5) 
- The existing test suite even demonstrates that `full_name` can be changed independently of `owner.login` and the request still succeeds - it just doesn't attempt to make them point at different, already-registered repositories owned by a different configured org: [7](#0-6) 

Root cause: `Shipit.github(organization:)` resolves the per-org `webhook_secret` purely from `repository.owner.login`/`organization.login`, using case-insensitive normalization on both the lookup key and configured keys: [8](#0-7) 
This normalization is internally consistent (it can't itself be used to make one org's name collide with a *different* configured org, since config keys are also downcased at load time), but it is irrelevant to the actual bug: nothing anywhere ties the org whose secret validated the HMAC to the org embedded in `repository.full_name` that the handlers subsequently operate on. `GithubOrganizationUnknown` only blocks the case where `repository.owner.login` itself is unconfigured; it says nothing about `full_name`'s owner.

Exploit flow (multi-tenant Shipit instance hosting both `attacker-org` and `victim-org`):
1. Attacker controls a repo/webhook under `attacker-org`, which is configured in `Shipit.githubs` with a webhook secret the attacker can compute (either because `attacker-org`'s webhook_secret is empty/known to them, or, more generally, because they can trigger GitHub to deliver a validly-signed webhook for their own org's repo).
2. Attacker crafts a payload with `repository.owner.login = "attacker-org"` (so `verify_signature` uses attacker-org's secret and passes) but `repository.full_name = "victim-org/victim-repo"` naming an existing stack belonging to `victim-org`.
3. Attacker POSTs this to `/webhooks` with a valid `X-Hub-Signature` computed against `attacker-org`'s secret.
4. `verify_signature` succeeds because it only checks `attacker-org`'s secret against the raw body.
5. `PushHandler` (or `CheckSuiteHandler`, or the `PullRequest::*` handlers) resolves `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the real victim `Stack`, and enqueues `GithubSyncJob`, refreshes check runs, or archives/unarchives/labels the victim's `ReviewStack` — none of which the attacker is authorized to touch.

Existing guards that do not prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that *some* configured org's secret matches the body; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schemas validate field types/presence, not cross-field consistency; `Repository` model validations (`owner`/`name` format) constrain the target repo's name shape but do not restrict which repo a given signing org may name in `full_name`.

### Impact Explanation
An unprivileged attacker who merely has push/webhook access to their own org's repo (or can otherwise get a validly-signed webhook delivered) can cause Shipit to process events — `GithubSyncJob` enqueue on push, check-run refresh, PR label capture, review-stack archive/unarchive/creation — against a **different tenant's** stack/repository, purely by choosing a divergent `repository.full_name`. This is a payload for one repository mutating another repository's stack, matching the Critical severity category explicitly listed in the rules. It is repeatable against any repository name known to the attacker across the whole Shipit instance, and the blast radius spans every org sharing this single Shipit deployment.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-org (`Shipit.githubs` configured with more than one organization) and the attacker must control (or be able to trigger validly-signed webhooks for) at least one of those orgs' repos — a low bar for any organization member. No Shipit session, API token, or GitHub App private key is required; the attacker only needs their own org's ability to emit a correctly-signed webhook and knowledge/guessing of a target `owner/repo` full name (often discoverable, e.g. from the public Shipit stack list).

### Recommendation
Enforce the equality binding explicitly: derive the processing-target org from `repository.full_name` (or `organization.login`) and require it to equal `repository_owner` used in `verify_signature` before dispatching to handlers; reject (422) any request where they diverge. Alternatively, resolve `Repository`/`Stack` scoped to the verified org only, e.g. by looking up `Repository.from_github_repo_name` and asserting `repository.owner == repository_owner.downcase` before calling any handler.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossOrgTest < ActionController::TestCase
    tests WebhooksController

    setup do
      @victim_stack = shipit_stacks(:shipit) # owned by repo "shopify/shipit-engine" per fixtures
      Shipit.stubs(:secrets).returns(
        ActiveSupport::OrderedOptions.new.tap do |s|
          s.github = {
            'attacker-org' => { webhook_secret: nil },
            'shopify' => { webhook_secret: nil }
          }
        end
      )
    end

    test "signature verified against attacker org does not authorize mutation of a different org's stack" do
      request.headers['X-Github-Event'] = 'push'

      payload = JSON.parse(payload(:push_master))
      payload['repository']['owner']['login'] = 'attacker-org'   # org used for signature verification
      payload['repository']['full_name'] = @victim_stack.repository.full_name # org actually mutated

      assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @victim_stack.id, expected_head_sha: payload['after']]) do
        post :create, body: payload.to_json, as: :json
      end
      assert_response :ok

      # Binding check: verification org != processing-target org, yet the request succeeded.
      verification_org = payload.dig('repository', 'owner', 'login')
      processing_org = @victim_stack.repository.owner
      refute_equal verification_org, processing_org
    end
  end
end
```
This demonstrates that `verify_signature`'s org (`attacker-org`) and the org whose stack is actually enqueued for sync (`shopify`, owner of `@victim_stack.repository`) diverge, while the request is still accepted and processed.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
