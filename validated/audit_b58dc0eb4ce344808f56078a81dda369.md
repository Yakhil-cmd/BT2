### Title
Arbiter contract shared-address definition never enforces the arbstore cut fee for private assets - (File: arbiter_contract.js)

### Summary
`deriveSharedAddress()` builds the `["or", [...]]` definition that authorizes spending from an arbiter-contract shared address. For non-private assets it hard-wires a `has output` clause that forces the payer to also pay `arbstoreInfo.cut` to the arbstore's address whenever `hasArbStoreCut` is true. For private assets, this same "complete" branch is built purely from `["address", ...]` + `["in data feed", ...]` conditions with no `has output` fee-enforcing clause at all, so the arbstore's cut is never charged.

### Finding Description
`deriveSharedAddress(hash, bOfferor, cb)` computes `hasArbStoreCut = arbstoreInfo.cut > 0` and builds two OR-branches representing the two ways the contract can be completed (offeror wins / acceptor wins). [2](#0-1) 

For non-private assets, both completion branches add a `has` condition requiring the amount actually paid to the counterpart be reduced by the arbstore cut, and (when `!isFixedDen && hasArbStoreCut`) an additional `has` requiring an output of exactly the cut amount to `arbstoreInfo.address`: [3](#0-2) 

For private assets, however, the same two completion branches are defined only as:
```
["and", [["address", offeror_address], ["in data feed", [[acceptor_address], "CONTRACT_DONE_" + hash, "=", offeror_address]]]]
["and", [["address", acceptor_address], ["in data feed", [[offeror_address], "CONTRACT_DONE_" + hash, "=", acceptor_address]]]]
``` [4](#0-3) 

This branch places no constraint whatsoever on where the shared address's private-asset outputs go or how much reaches whom — the only requirement is that the correct address posts a `CONTRACT_DONE_<hash>` data feed value equal to itself. Since private-asset spend conditions rely purely on this address+data-feed gate, the payer (offeror or acceptor, whichever the definition allows) can construct the settlement payment however they like, sending 100% of the contract amount to the winning party and 0% to the arbstore, i.e., completely bypassing the `arbstoreInfo.cut` fee that the arbstore is supposed to earn for mediating/hosting the contract. The `complete()` function used by the wallet client for private assets indeed only posts a `data_feed` message and performs no payment enforcing the cut at all: [5](#0-4) 

By contrast, for the public-asset path, `complete()` explicitly computes `peer_amount`/`arbstore_amount` from the on-chain shared-address definition and sends the cut to `objContract.arbstore_address`: [6](#0-5) 

This is directly analogous to the reported bug class: the same underlying economic operation (paying out escrowed contract funds to the winning party) can be executed through two different code paths, and the "fee" (the arbstore's cut, analogous to the swap fee on the borrower) is enforced on one path but silently skipped on the other. Any user can choose to fund an arbiter contract using a private asset instead of a public one, then use the escape hatch to withhold the arbstore's fee entirely.

### Impact Explanation
Any two counterparties creating an arbiter contract in a private (non-transferable-tracked, is_private) asset can jointly agree to settle the contract off the intended split, unilaterally denying the arbstore its configured `cut` fee while still relying on the arbiter's dispute-resolution/data-feed mechanism to unlock funds. This is a direct loss of expected protocol/service revenue for the arbstore operator (fee bypass), and it creates unfair/inconsistent economic treatment between users of public vs. private assets for the identical arbiter-contract product — the same class of unfairness flagged in the referenced report (fee charged on one path, not on the economically equivalent other path).

### Likelihood Explanation
This does not require any privileged role: any wallet user creating/accepting an arbiter contract funded in a private asset controls this path. Because is_private assets are a normal, user-creatable asset type, and the arbiter-contract feature is exposed to ordinary users/wallets, this is straightforwardly reachable, and the two counterparties are financially incentivized to omit the arbstore cut whenever the underlying asset is private.

### Recommendation
For private assets, the shared-address "complete" branches should also embed an enforceable cut requirement analogous to the public-asset `has output` clause — e.g., require a `spend_proof`/output condition (or a value posted via the private payment chain and cross-checked by the arbiter/arbstore) that guarantees the arbstore's `cut` portion of `contract.amount` is paid to `arbstoreInfo.address` before the definition authorizes release of the remaining funds to the winning party, mirroring the logic already used for non-private, non-fixed-denomination assets.

### Proof of Concept
1. Two users, Alice (offeror) and Bob (acceptor), create an arbiter contract for a private asset via `createAndSend`/`createSharedAddressAndPostUnit`, choosing an `arbiter_address` whose `arbstoreInfo.cut > 0`.
2. `deriveSharedAddress()` builds the shared-address definition, and since `assetInfo.is_private === true`, the completion branches are only `["address", X] AND ["in data feed", ..., "CONTRACT_DONE_<hash>", "=", X]` — no output-amount or cut enforcement is present. [4](#0-3) 
3. The dispute is resolved (or the contract completes normally) and the payer's wallet calls `complete()`; for the private-asset branch it only posts a `CONTRACT_DONE_<hash>` data feed value and performs the private payment itself, with no code path that computes or transfers `arbstoreInfo.cut` to `arbstoreInfo.address`. [7](#0-6) 
4. Because the definition never requires an output to the arbstore for private assets, the payer can send 100% of `contract.amount` to the winning counterpart and 0 to the arbstore — the fee is fully bypassed, whereas the equivalent public-asset settlement (same `complete()` function, `else` branch) is forced by the definition to pay the cut.
