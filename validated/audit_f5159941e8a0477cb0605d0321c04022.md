### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but handlers act on the unbound `repository.full_name` / commit `sha` fields — cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to check the HMAC against using `repository_owner`, then verifies the *entire raw body* against that secret. [1](#0-0)  However, the field that actually drives write-side behaviour in every downstream handler — `repository.full_name` (`Handler#repository_name`) — is a completely separate JSON field from `repository.owner.login`/`organization.login` used for the signature-org lookup, and is never cross-checked against it. [2](#0-1)  Worse, `StatusHandler` doesn't even use `repository_name` at all — it looks up commits globally by `sha` across the entire installation. [3](#0-2)  This is the same class of bug as the reported `CollateralLiquidityProvider` issue: a value that is trusted/acted upon (`repository.full_name`, `sha`) is disjoint from the value actually covered by the authorization check (the org whose secret signed the payload).

### Finding Description
Shipit supports multi-tenant GitHub App configuration where each organization has its own `webhook_secret`, `app_id`, etc., set in `config/secrets.yml`. [4](#0-3)  On webhook delivery, `verify_signature` computes `repository_owner` from the payload and fetches that organization's `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature(signature, raw_post)` on it. [5](#0-4)  `verify_webhook_signature` is a pure HMAC-SHA1 check of the raw body against that org's stored secret — it makes no claim about which repository the payload concerns beyond what's used to pick the secret. [6](#0-5) 

Once verified, `create` dispatches the parsed JSON straight to registered handlers for the event. [7](#0-6)  Handlers derive the target repository from `payload.dig('repository', 'full_name')`, [8](#0-7)  a field that is never compared to `repository_owner`/`organization.login` (the field the signature check keyed off). Anyone who legitimately controls (or knows) the `webhook_secret` for *one* configured organization — e.g., a self-service customer/tenant who sets up their own GitHub App/webhook per the documented multi-org setup [9](#0-8)  — can sign an arbitrary JSON body with that known secret while setting `repository.owner.login` to their own org (satisfying `verify_signature`) but `repository.full_name` to a target belonging to a *different* tenant/org configured on the same Shipit instance.

Concretely:
- `PushHandler#process` resolves `stacks` from `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` — the attacker's own valid signature drives a sync of an arbitrary victim stack/repo. [10](#0-9) 
- `StatusHandler#process` is even less scoped: it matches on `Commit.where(sha: params.sha)` with **no repository/org check at all**, so a validly-signed payload from any one configured org's secret can inject/forge a CI status (`state`, `context`, `target_url`) for any commit SHA in the entire installation, including commits belonging to a completely unrelated tenant's stack. [3](#0-2) 
- `MembershipHandler#process` similarly trusts `params.organization.login` inside the payload body to attribute team/organization membership without re-verifying it matches the org whose secret signed the request. [11](#0-10) 

This is the same binding failure as the report: the authorization check covers one field (`externalCollateralRedemption` caller / here, `repository.owner.login`) while a different, unchecked field (`_externalCollateralRedemption` value / here, `repository.full_name` or `sha`) is what actually gets acted upon.

### Impact Explanation
If deployment forges a CI "success" status for a commit belonging to a stack it doesn't own via `StatusHandler`, this can satisfy deploy-gating checks (`Commit#create_status_from_github!`/CheckRun logic that stacks/tasks rely on to permit deploys), potentially enabling an unauthorized deploy on another tenant's stack — matching the rules' Critical bucket ("unauthorized deploy, rollback or merge"). At minimum this is a cross-organization/cross-repository write, forging sync triggers and commit statuses for stacks outside the attacker's own configured organization, satisfying the High/Critical "cross-repository writes" criterion.

### Likelihood Explanation
Exploitability requires the attacker to possess a valid `webhook_secret` for *some* organization configured in the multi-tenant Shipit deployment (a normal, documented self-service setup step for onboarding a new org, not a privileged Shipit account, API token, or GitHub App private key). Given that, forging the payload is trivial: HMAC-SHA1 over an attacker-fully-controlled JSON body, since nothing in `verify_signature` or the handlers ties `repository.owner.login`/`organization.login` to `repository.full_name` or `sha`. This matches the "unprivileged attacker" analog criteria — no Shipit session, `ApiClient` token, or GitHub App private key for the *victim* org is needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), assert that the organization implied by `repository.full_name`'s owner (and any `organization.login` field used by handlers such as `MembershipHandler`) equals the `repository_owner` value that was used to select and verify the signing secret. Reject the webhook (422) if these do not match. Additionally, scope `StatusHandler#process` lookups by the resolved repository/stack, not by a bare global `Commit.where(sha:)` query.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (as in `docs/setup.md`'s multi-app setup).
2. Attacker legitimately controls `orgA`'s GitHub App/webhook and thus knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" },
  "sha": "<victim commit sha belonging to orgB's stack>",
  "state": "success",
  "context": "ci/forged"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` looks up `Shipit.github(organization: "orgA")` (from `repository.owner.login`) and validates successfully since the attacker used `orgA`'s real secret. [5](#0-4) 
6. `StatusHandler#process` finds `Commit.where(sha: "<victim sha>")` — belonging to `orgB` — and calls `create_status_from_github!`, injecting a forged CI status onto a commit the attacker never had access to. [3](#0-2)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
