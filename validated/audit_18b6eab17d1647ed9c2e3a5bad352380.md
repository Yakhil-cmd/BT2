### Title
Cross-organization commit-status forgery bypasses CI gating and enables unauthorized merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` binds an inbound webhook to a specific GitHub organization by looking up that organization's `webhook_secret` and verifying the HMAC signature against it [1](#0-0) . However, `StatusHandler#process`, which handles the `status` event, never re-checks that the commit it updates actually belongs to a repository owned by that same verified organization — it looks up commits globally by `sha` across the entire installation [2](#0-1) . This is the same class of bug as the Insurance Fund report: a value used to authorize/verify one entity (the organization whose secret validated the signature) is silently detached from the value that is actually acted upon (the specific commit/repository the mutation targets), letting an attacker who legitimately controls one tenant's webhook credentials forge state for a completely different tenant.

### Finding Description
Shipit is a multi-tenant engine: each GitHub organization configured in `Shipit.github` has its own `webhook_secret`, and Shipit manages stacks/commits for potentially many different organizations/repositories in the same installation (see `config/secrets.*.yml` samples with multiple orgs) [3](#0-2) .

The webhook signature check derives the organization solely from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`) and picks the corresponding `webhook_secret` to verify against: [1](#0-0) [4](#0-3) 

Because the attacker fully controls the raw request body before signing it with their own legitimately-provisioned secret, they can set `repository.owner.login` to their own organization (call it Org A, for which they hold a valid GitHub App/webhook secret with Shipit), so the signature check passes — while the semantically-relevant field for the `status` event, `sha`, is independent of `repository.owner.login`/`full_name` and is never cross-checked against the verified organization.

`StatusHandler#process` uses only `params.sha` to find target commits, with no scoping to the repository/organization that was authenticated: [2](#0-1) 

Compare this to `Handler#stacks`/`Handler#repository_name`, which do scope by `repository.full_name` [5](#0-4) , and to other handlers (`PushHandler`, pull-request handlers) that resolve a `Repository` via `Repository.from_github_repo_name(params.repository.full_name)` before acting [6](#0-5) [7](#0-6) . `StatusHandler` is the outlier: it neither declares nor uses `repository` at all, so any commit SHA that exists anywhere in the Shipit database — belonging to Organization B, whose secret the attacker never had — can have a fabricated CI status attached by an attacker who only holds Organization A's webhook secret.

The binding broken, stated as an equality that should hold but doesn't:
`organization whose webhook_secret verified the signature == organization owning the repository/commit the handler mutates`.

Before the attack: commit statuses for Org B's commits can only be set by webhooks correctly signed with Org B's `webhook_secret`.
After the attacker's forged request (signed with Org A's secret, body claiming `sha` of an Org B commit): a `Shipit::Status` row is created/updated for that Org B commit as if GitHub itself reported it [2](#0-1) .

### Impact Explanation
Commit statuses are load-bearing for Shipit's merge-queue and CI gating (`ci.require` in `shipit.yml`, documented in the README) — deploy/merge safety checks rely on `Commit`/`Status` records populated exactly by this webhook path. An attacker who administers or has compromised only their own low-value GitHub organization/webhook secret (Org A, in-scope trust boundary is "an organization that authenticated" — see rules) can forge a passing CI status for a targeted commit belonging to an entirely different, higher-value organization (Org B) managed by the same Shipit instance, without ever holding Org B's credentials. If Org B's merge queue is gated on `ci.require`/required statuses, this can make Shipit treat an unvetted or malicious commit as CI-green, enabling an unauthorized merge — squarely within the "Critical: … an unauthorized deploy, rollback or merge" impact category.

### Likelihood Explanation
The only prerequisite is that the attacker administers (or has compromised) any single GitHub organization/App that this Shipit instance trusts and has a webhook_secret for — a realistic scenario for shared/multi-tenant Shipit deployments serving several orgs, which the codebase explicitly supports (`config/secrets.*.yml` multi-org examples). No repository write access, no `ApiClient` token, and no privileged Shipit account are required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a body signed by a secret the attacker legitimately possesses for their own org. The target commit `sha` is discoverable (commits/PRs are typically public or knowable to any collaborator across orgs using the same Shipit instance).

### Recommendation
In `StatusHandler`, and any other handler that mutates state keyed only by `sha`/global identifiers, require and validate `repository.full_name` (or an equivalent field) against the repository/organization that was actually verified by `WebhooksController#verify_signature`, e.g. by resolving `Repository.from_github_repo_name(params.repository.full_name)` and scoping the `Commit.where(sha:)` lookup to `commit.stack.repository_id == repository.id` before creating/updating a status. More generally, `verify_signature` should pass the verified organization down to handlers, and every handler must scope its mutations to that organization/repository rather than trusting any repository-identifying field embedded elsewhere in the same payload.

### Proof of Concept
1. Attacker administers/controls Organization A, which has a Shipit-configured `webhook_secret_A` (legitimate, e.g. from having created their own GitHub App integration with this shared Shipit instance).
2. Attacker identifies the `sha` of a commit belonging to Stack/Repository in Organization B, also hosted on the same Shipit instance (e.g., from a public PR or leaked commit hash).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<org_b_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `webhook_secret_A` over this exact body and POSTs it to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `webhook_secret_A`, and the HMAC check passes [1](#0-0) .
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and finds the commit belonging to Organization B, then calls `create_status_from_github!` on it — recording a forged `"success"` status for a commit the attacker had no verified authority over [2](#0-1) .
7. If Organization B's stack has `ci.require` including `ci/required-check`, this forged status can satisfy the merge/deploy gating for that commit, enabling an unauthorized merge/deploy path.
