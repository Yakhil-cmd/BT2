### Title
Cross-organization Team hijack via `MembershipHandler#find_or_create_team!` ignores webhook provenance - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves an existing `Team` purely by GitHub's global numeric `github_id`, without checking that the `organization.login` in the payload matches the `Team#organization` already stored. Because `WebhooksController#verify_signature` authenticates a membership webhook using the org that appears in the payload itself (not the org that owns the target `Team`), an attacker who controls any one of the multiple configured GitHub organizations can sign a forged `membership` webhook that mutates a `Team` belonging to a different organization, adding an attacker-chosen GitHub login to it.

### Finding Description
The broken binding, stated as an equality that the code must but does not enforce:
`team.organization (the org that owns the Team row being mutated) == params['organization']['login'] (the org whose webhook_secret verified this specific request)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  . A `membership` payload has no `repository` key, so `repository_owner` is `params['organization']['login']` — the attacker's own org.
2. `Shipit.github(organization: repository_owner)` therefore resolves the attacker-owned org's `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker signed the body with that org's own `webhook_secret` [2](#0-1)  . This is legitimate multi-tenant routing, not a bug by itself.
3. `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }` [3](#0-2)  . On the **find** branch (an existing row with that `github_id`), the block populating `team.organization = params.organization.login` never runs — Rails only invokes it on create — so the pre-existing `Team#organization` is left untouched, but the record found is still whichever `Team` row has that `github_id`, irrespective of which organization's secret authenticated the request.
4. `team.add_member(User.find_or_create_by_login!(params.member.login))` then attaches the attacker-controlled GitHub login as a member of that `Team`, regardless of the org that actually owns it [4](#0-3)  .

Exploit request: `POST /webhooks` with `X-Github-Event: membership`, signed with the webhook secret of an org the attacker administers, body `{action:'added', team:{id:<github_id of an existing Team owned by a different org>, name:'x', slug:'x', url:'x'}, organization:{login:'attacker-owned-org'}, member:{login:'attacker-login'}}`.

Existing guards do not stop this: `verify_signature` only proves the request came from *some* configured org, not the org owning the target `Team`; `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organizational ownership [5](#0-4)  ; no controller/model code cross-checks `team.organization` against the authenticating org.

Why this matters beyond a mere data-integrity bug: `User#authorized?` and the login gate in `force_github_authentication` check membership in `Shipit.github_teams` purely by `Team#id`/membership, with no per-organization scoping [6](#0-5) [7](#0-6)  . `Shipit.github_teams` is built from `github.oauth_teams` (`Team.find_or_create_by_handle`), which can list teams belonging to organizations other than the "default" one used to compute it [8](#0-7)  . So if the target `Team` row is one referenced in `Shipit.github_teams`, the forged membership grants the attacker's GitHub login full Shipit access (login/authorization bypass), not just an unrelated data write.

### Impact Explanation
A single forged, self-signed webhook lets the attacker add an arbitrary GitHub login as a member of any pre-existing `Team` row identified only by its numeric GitHub team id, as long as it belongs to a different configured organization than the one whose secret they used. If that `Team` is part of `Shipit.github_teams`, this is a direct authentication/authorization bypass: the attacker's account becomes `authorized?` and gains full access to the Shipit deployment UI/API for stacks it does not own — matching the "escalation into `Shipit.github_teams` authorization" (High) category, and arguably Critical since it can grant broad application access across tenants that share one Shipit instance. The action is repeatable against any organization/team combination for which the attacker knows (or can enumerate) a numeric `github_id`.

### Likelihood Explanation
Requires: (1) a multi-organization `secrets.github` configuration (`lib/shipit.rb#github_app_config`), (2) attacker administers one configured org and thus knows its `webhook_secret`, (3) a `Team` row already exists for the target org/team's `github_id` (created e.g. via `lib/tasks/teams.rake` or a prior legitimate webhook). GitHub numeric team IDs are frequently discoverable (public API responses, team page metadata) for organizations the attacker can query, so this is operationally feasible and cheap — one crafted HTTP POST per exploitation attempt, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found `Team#organization` matches `params.organization.login` before performing any membership mutation (e.g., raise/drop the event if they differ, or scope the lookup with `find_or_create_by!(github_id:, organization: params.organization.login)`), so a webhook authenticated as org A can never mutate a `Team` belonging to org B.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Fixtures: `Team` `victim_team` with `organization: 'victim-org'`, `github_id: 999`; second org config `attacker-org` with its own `webhook_secret` in `secrets.github`.
2. Build membership payload: `{ action: 'added', team: { id: 999, name: 'x', slug: 'x', url: 'x' }, organization: { login: 'attacker-org' }, member: { login: 'attacker-login' } }`.
3. Sign with `attacker-org`'s webhook secret (`sha1=` HMAC), set `X-Github-Event: membership`.
4. POST to `/webhooks`; assert `response.status == 200`.
5. Assert `victim_team.organization == 'victim-org'` while `params['organization']['login'] == 'attacker-org'` (binding proven broken).
6. Assert `Shipit::Membership.exists?(team_id: victim_team.id, user: Shipit::User.find_by(login: 'attacker-login'))` is `true`.
7. Optionally stub `Shipit.github_teams` to include `victim_team` and assert `User.find_by(login: 'attacker-login').authorized?` becomes `true`, demonstrating the login-bypass consequence.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else

          end
        end

        end
