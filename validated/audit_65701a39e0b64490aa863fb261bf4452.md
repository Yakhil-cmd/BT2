### Title
Signature verification is keyed off an attacker-controlled organization field that is decoupled from the repository actually acted on, allowing cross-tenant webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, while the actual event processing (`Handler#stacks`/`repository_name`) resolves the target repository/stack from a *different* field of that same body: `repository.full_name`. Nothing binds these two fields together, so in a multi-organization Shipit installation an attacker who legitimately administers one tenant org can forge a webhook whose signature validates against their own org's secret while the payload's `repository.full_name` points at a different tenant's repository, causing Shipit to act on that other repository.

### Finding Description
`verify_signature` resolves the signing secret using data taken from the body itself: [1](#0-0) [2](#0-1) 

Once verified, `create` dispatches the same raw params to the matching handlers: [3](#0-2) 

Handlers determine which `Stack`/`Repository` to operate on from a *different* body field, `repository.full_name`: [4](#0-3) 

Shipit explicitly supports per-organization GitHub Apps/secrets, each with its own `webhook_secret`, selected via `Shipit.github(organization: ...)`: [5](#0-4) [6](#0-5) 

The trust binding that should hold is: `{organization whose secret authenticated the webhook} == {organization owning the repository the handler writes to}`. Because both the "authenticating owner" (`repository.owner.login`/`organization.login`) and the "acted-on repository" (`repository.full_name`) are independently attacker-supplied fields of the same JSON body, an attacker who legitimately controls Org A (and therefore knows Org A's `webhook_secret`, since they administer that GitHub App installation) can:
1. Set `repository.owner.login` (or `organization.login`) = `"OrgA"` so `verify_signature` selects Org A's secret, which the attacker can correctly HMAC-sign.
2. Set `repository.full_name` = `"OrgB/some-repo"` (a repository belonging to a different tenant, Org B, hosted on the same Shipit instance) so the handler's `stacks`/`repository_name` resolution targets Org B's stack instead.

This breaks the equality `{authenticated organization} == {repository written}`, exactly analogous to the report's `INSTR.store` counter vs. `getProposalMetadata` mapping mismatch: the value used to pick the "container" (secret/app) is not the same value used to select the record actually written.

### Impact Explanation
The concrete impact depends on which handler is invoked with the forged cross-tenant payload, but at least one handler directly demonstrates a state-changing, unauthorized cross-repository write: `StatusHandler` looks up commits purely `by sha` (globally, not scoped by the authenticating org) and creates a GitHub status/CI record on them: [7](#0-6) 

Because `Commit.where(sha: params.sha)` is unscoped to a particular repository, and the attacker only needs to guess/know a sha that exists in a victim stack (SHAs are public, e.g., visible via GitHub or through the target org's own public activity), an attacker administering Org A's app can inject a forged "success" status onto a commit belonging to Org B's stack, potentially satisfying CI-gating logic used by Shipit's merge-queue/mergeability checks for that unrelated stack — an unauthorized state change across a repository boundary the attacker does not control. Other handlers (`PushHandler`, `pull_request/*` handlers, `MembershipHandler`) are similarly reachable with a valid-but-mismatched-organization signature because none of them re-validate that `repository.full_name`'s owner matches the organization whose secret authenticated the request.

This satisfies the "cross-repository writes" / unauthorized-state-change class of impact called out in the rules, reachable without any Shipit session, `ApiClient` token, or GitHub App private key — only knowledge of a webhook secret the attacker legitimately possesses for their own tenant.

### Likelihood Explanation
This is only exploitable when Shipit is configured for **multiple GitHub organizations** sharing one webhook endpoint (the documented multi-org configuration in `docs/setup.md`). In that configuration, any tenant admin who legitimately owns one org's app (and thus its `webhook_secret`) can attack any other tenant on the same Shipit instance. This is a real, supported deployment topology, not a hypothetical misconfiguration, and requires no elevated Shipit-side credentials — only administrative access to one's own GitHub org's App/webhook settings, which is the level of trust a tenant is expected to have over their *own* repositories, not others'.

### Recommendation
After selecting the signing organization/secret in `verify_signature`, cross-check that the resolved organization matches the owner segment of `repository.full_name` (or `organization.login`) actually used later by the handlers, and reject the webhook if they differ. Alternatively, scope all record lookups in handlers (e.g., `StatusHandler`'s `Commit.where(sha: ...)`) to the repository/stack whose organization matches the one that authenticated the request, rather than trusting an unscoped or independently-supplied field from the same payload.

### Proof of Concept
1. Deploy Shipit with the multi-org configuration (`Shipit.github(organization: ...)`), with Org A and Org B both onboarded (per `docs/setup.md`, "Using Multiple Github Applications").
2. As the legitimate administrator of Org A's GitHub App, obtain Org A's `webhook_secret`.
3. Craft a `status` event JSON body:
   - `organization.login` / `repository.owner.login` = `"OrgA"`
   - `repository.full_name` = `"OrgB/victim-repo"`
   - `sha` = a known commit sha belonging to an `OrgB` stack, `state` = `"success"`, `context` = a required CI context for that stack.
4. Compute `X-Hub-Signature` using Org A's `webhook_secret` over the raw body and `POST` it to `/github/webhooks` (or the configured webhook route) with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` from the body, verifies the signature successfully (attacker knows this secret), and `StatusHandler#process` creates a status on the `OrgB` commit found via the unscoped `Commit.where(sha: params.sha)` query, demonstrating a write into `OrgB`'s data despite the request only being authenticated for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
