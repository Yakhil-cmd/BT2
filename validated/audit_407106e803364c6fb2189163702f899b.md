### Title
Unvalidated venue/pool and token addresses in swap payload let a rogue route contract pull arbitrary tokens from the caller's wallet under their own authorization - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The analog of "parametrization over arbitrary curves with no whitelist" is the swap-aggregator's parametrization over arbitrary contract addresses. Every hop's `pool`, `token_in`, and `token_out` are taken verbatim from the caller-supplied `assets` registry, and no venue allowlist or address validation exists anywhere in the dispatch path. A crafted `swap_xdr` can name an attacker-controlled "pool" contract that, during the hop, performs an additional `token.transfer(victim, attacker, amount)` on any token the victim holds. Because the call happens below the sender's `require_auth`, the transfer is recorded as a child of the sender's own authorization entry and executes if the sender signs the simulation-produced auth tree — stealing wallet funds unrelated to the routed amount.

### Finding Description
`execute_op` resolves hop parameters purely by index into the payload's `assets` vector, with no check that the pool is a real Aquarius/Comet/Phoenix/Soroswap/Sushi deployment or that the tokens are legitimate contracts: [1](#0-0) . `dispatch_hop` then invokes the venue adapter against `hop.pool`, whatever it is, and only validates balance deltas afterward [2](#0-1) . The measured-delta checks bound only the routed `amount_in`/`token_out` pair; they do nothing about side effects the pool contract performs on *other* tokens while it is on the call stack. The threat model documents exactly this exposure: the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [3](#0-2) . A dedicated harness test proves the host behavior: a `RogueHopPool` invoked as a route hop calls `token.transfer(victim, to, amount)` on an unrelated wallet token, and in enforcing mode that sub-invocation is accepted if included in the caller's signed auth tree [4](#0-3) . The same lack of validation applies on the controller path: `swap_tokens` forwards the user-supplied `StrategySwap` XDR unchanged after granting only the single input-transfer auth [5](#0-4)  — controller users are somewhat protected because the controller's invoker-contract auth covers only the one input transfer, but the standalone `execute_strategy` path signs with a real user key whose simulated auth tree legitimately contains children, making injected children hard to distinguish.

### Impact Explanation
Theft of user funds. An attacker who can get a victim to sign a swap whose route embeds a malicious hop pool drains arbitrary amounts of any SEP-41 token in the victim's wallet, far exceeding `total_in`. The `min_out` check, per-hop `ZeroOutput`/`InvalidAmount` measurement, residual caps, and controller-side `RouterOverspend`/`NoSwapOutput` gates all pass because the theft is orthogonal to the measured route flow.

### Likelihood Explanation
Requires the victim to submit/sign a malicious route — e.g., a compromised or malicious quote source, a phishing front-end, or a manipulated `routeXdr`. This is an unprivileged-attacker-reachable path (`execute_strategy` is permissionless and `sender` is the only signer), but it depends on social/signing success and on the victim's wallet accepting an auth tree with an unexpected child. The mitigation exists only off-chain (client-side payload verification), not in the contract. Medium-to-high likelihood; impact makes it High overall.

### Recommendation
Mirror the report's "small, well-tested whitelist" recommendation: maintain an on-chain registry of approved venue pool/token addresses (populated by the router owner), and reject any hop whose `pool` or token address is not registered. Alternatively, derive venue pools deterministically (e.g., call the known venue factory/router rather than a payload-supplied pool address) so the payload can only select pairs, not code. Short of that, enforce a strict invariant in the contract where feasible (e.g., reject hop tokens that are not part of the declared route chain end-to-end) and require clients to refuse any sender authorization tree containing children beyond the single `token_in` transfer.

### Proof of Concept
The repository already contains the proving fixture: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` deploys `UnlistedPoolRouter`/`RogueHopPool` doubles where the hop pool calls `token.transfer(victim_wallet_token, attacker, amount)` during `swap`, and shows the transfer is recorded under the caller's auth entry and executes once signed [6](#0-5) . Against the real router the equivalent is: build a `StrategyPayload` whose `assets` registry contains an attacker-deployed contract as a hop `pool` plus the victim's wallet token address; the rogue pool's swap function emits the extra `transfer`; the victim signs the simulation-produced auth tree (which now contains the injected child alongside the legitimate input transfer); the swap completes normally and pays out `min_out`, while the victim's unrelated tokens are moved to the attacker.

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
