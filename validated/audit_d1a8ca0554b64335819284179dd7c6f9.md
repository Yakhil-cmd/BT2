### Title
`CCMenuController#stack` overrides `BaseController`'s stack-scoping, allowing an `ApiClient` scoped to one stack to read the CCMenu XML of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController#stack` enforces the binding `stack ∈ stacks scoped by current_api_client.stack_id` via the `stacks` helper (`Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped). `CCMenuController` redefines `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping, regardless of whether authentication happened via `params[:token]` or the inherited HTTP Basic path.

### Finding Description
Binding that should hold: `stack.id == current_api_client.stack_id` (when `current_api_client.stack_id?` is true), enforced in `BaseController#stacks`/`#stack`: [1](#0-0) 

`CCMenuController` overrides `#stack` and does not use `stacks`/scoping at all: [2](#0-1) 

`CCMenuController#authenticate_api_client` tries `ApiClient.authenticate(params[:token])` first, and falls back to `super` (Basic Auth via `BaseController#authenticate_api_client`) when no query token is present or valid: [3](#0-2) [4](#0-3) 

Whichever path sets `current_api_client`, `#show` calls the overridden `#stack`, which loads `Stack.from_param!(params[:stack_id])` unconditionally: [5](#0-4) 

`require_permission :read, :stack` only checks the permission string list (`read:stack` present in `permissions`), it never checks that the requested stack matches `current_api_client.stack_id`: [6](#0-5) 

Attacker flow: hold an `ApiClient` token (e.g., fixture `here_come_the_walrus`, scoped to stack `shipit` with only `read:stack` permission) — send `GET /api/stacks/:other_stack_id/ccmenu.xml` with `Authorization: Basic <base64(token)>` and no `token` param. `ApiClient.authenticate(nil)` returns `nil`, `super` runs, Basic Auth succeeds and sets `current_api_client` to the walrus-scoped client, `require_permission!` passes since `read:stack` is present, and `#stack` resolves `params[:stack_id]` against the full `Stack` table with no ownership check, returning any stack's `deploys_and_rollbacks`.

Existing guards checked and confirmed insufficient:
- `require_permission!`/`check_permissions!` only validate the permission name, not stack ownership: [6](#0-5) 
- The `stacks` scoping that protects other controllers (confirmed by test "an api client scoped to a stack will only see that one stack" in `stacks_controller_test.rb`) is never invoked by `CCMenuController` because it defines its own `#stack`.
- `ApiClient.authenticate` itself has no stack check, it just verifies the signed token and loads the record: [7](#0-6) 

### Impact Explanation
An attacker holding any valid `ApiClient` token scoped to a single stack (permission `read:stack`) can retrieve the CCMenu status/deploy data — `deploys_and_rollbacks`, build status, last build label/time — for every other stack in the Shipit instance, including stacks belonging to repositories/tenants they have no authorization for. This is a cross-tenant read of stack/deploy state, repeatable for arbitrary `stack_id` values with a single authenticated (but improperly scoped) token, matching the High severity category "escalation... unauthenticated [out-of-scope] read of stack state ... or deploy output" since the client is authenticated but not authorized for the accessed stack.

### Likelihood Explanation
Preconditions: attacker must already possess a valid `ApiClient` token (any stack-scoped token with `read:stack`, which is the default/minimal permission most integrations are issued). No GitHub secrets, session, or admin access needed. Cost is a single HTTP GET with a known/guessed `stack_id` (stack slugs are visible in URLs/Shipit UI in many deployments). Fully repeatable against any number of stacks.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited scoped lookup instead of hitting `Stack` directly, e.g. use `stacks.from_param!(params[:stack_id])` (the same `stacks` helper `BaseController` defines) rather than `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "an api client scoped to stack A cannot read stack B's ccmenu data via basic auth" do
  authenticate!(:here_come_the_walrus) # scoped to shipit_stacks(:shipit)
  other_stack = shipit_stacks(:cyclimse) # or any other fixture stack

  get :show, params: { stack_id: other_stack.to_param }

  # Binding under test: stack.id == current_api_client.stack_id (here_come_the_walrus.stack_id == shipit.id)
  assert_not_equal shipit_api_clients(:here_come_the_walrus).stack_id, other_stack.id
  # Vulnerable behavior: request still succeeds and returns other_stack's data
  assert_response :ok
  assert_payload 'name', other_stack.to_param
end
```
This demonstrates the client scoped to `shipit` stack retrieving `other_stack`'s CCMenu/deploy data, confirming the scoping bypass regardless of the token-vs-basic-auth path.
