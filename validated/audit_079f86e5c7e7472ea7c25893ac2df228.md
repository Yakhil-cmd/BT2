### Title
Stale AA/definition cache in `network.js` `light/get_definition` allows serving an outdated address/AA definition after redefinition - (File: network.js)

### Summary
`network.js`'s `light/get_definition` handler caches definitions in an in-memory object `definitions[params]` keyed only by `definition_chash`/address, and once populated it is served forever without ever being invalidated when the underlying address is redefined or the AA is confirmed/changed. This mirrors the libcurl bug class: a piece of previously-established state (a cached "connection"/result) is reused for a request whose effective parameters have since changed, because the cache key/invalidation check omits a relevant condition (here, whether the definition is still the currently valid one, or whether an unconfirmed AA definition became final/changed).

### Finding Description
In the `light/get_definition` request handler: [1](#0-0) 
the code checks `if (definitions[params]) return sendResponse(ws, tag, definitions[params]);` before ever consulting the database again. The cache is populated from `storage.getUnconfirmedAADefinition(params)` when no row exists yet in `definitions`/`aa_addresses`: [2](#0-1) 
Unlike `readDefinitionByAddress`/`readDefinitionAtMci` in storage.js, which always take an explicit `max_mci` and re-derive the definition_chash from `address_definition_changes` for the requested MCI: [3](#0-2) 
this hub-side cache has no MCI dimension and no invalidation hook, so once a value is cached for a given `params` key it is returned unconditionally, regardless of whether:
- the definition later becomes stable/final and could differ from the `getUnconfirmedAADefinition` snapshot that was cached, or
- the address is later redefined via `address_definition_change` (address definition changes are only looked up freshly in `light/get_definition_for_address`, not in `light/get_definition`).

### Impact Explanation
A light client that requests `light/get_definition` for an address/AA before it is confirmed can receive a definition cached from an unconfirmed/transient state. If that AA or address definition is later withdrawn, replaced, or finalized differently (e.g., a fork resolves against a different candidate AA definition, or the address's definition changes), the hub keeps serving the stale cached definition to light clients indefinitely. A light wallet relying on this definition to construct/verify outputs, spending conditions or authentifiers for that address could build or accept transactions against the wrong (no-longer-valid) definition, leading to failed submissions or (for AA addresses) misrepresented AA logic being surfaced to the user — a disagreement between what the hub reports and what the network ultimately finalizes as valid.

### Likelihood Explanation
This is reachable by any unprivileged light client sending a `light/get_definition` request, with no special privileges needed. The likelihood of hitting the divergent-cache condition depends on timing (requesting the definition before it's confirmed, then having the network resolve to a different/removed definition afterward), which is a normal, attacker-triggerable race rather than a rare edge case, since AA addresses and address definitions are commonly created and can be affected by forks/removals before stabilization.

### Recommendation
Key the `definitions` cache by both the requested chash/address and the `max_mci` (or stability status) used to resolve it, mirroring `readDefinitionByAddress`'s `max_mci` parameterization, and invalidate/refresh cached entries once a formerly-unconfirmed AA definition becomes stable or an address definition change becomes stable, instead of caching indefinitely on first resolution.

### Proof of Concept
1. Post/announce a not-yet-stable AA definition (or an address that later undergoes `address_definition_change`) such that `storage.getUnconfirmedAADefinition(params)` returns a value.
2. As a light client, send `{"command":"light/get_definition","params":"<address_or_chash>"}` — the hub queries DB, finds nothing in `definitions`/`aa_addresses` yet, falls back to the unconfirmed definition, and caches it in `definitions[params]`. [4](#0-3) 
3. Have the network resolve differently (e.g., the AA never stabilizes with that exact definition, or the address is redefined via a stable `address_definition_change`).
4. Send the same `light/get_definition` request again — the hub returns the old cached value from step 2 without re-querying the DB, because `definitions[params]` is truthy, serving stale/incorrect definition data to the light client indefinitely.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}


// max_mci must be stable
function readDefinitionByAddress(conn, address, max_mci, callbacks){
	readDefinitionChashByAddress(conn, address, max_mci, function(definition_chash){
		readDefinitionAtMci(conn, definition_chash, max_mci, callbacks);
	});
}

// max_mci must be stable
function readDefinitionAtMci(conn, definition_chash, max_mci, callbacks){
	var sql = "SELECT definition FROM definitions CROSS JOIN unit_authors USING(definition_chash) CROSS JOIN units USING(unit) \n\
		WHERE definition_chash=? AND is_stable=1 AND sequence='good' AND main_chain_index<=?";
	var params = [definition_chash, max_mci];
	conn.query(sql, params, function(rows){
		if (rows.length === 0)
			return callbacks.ifDefinitionNotFound(definition_chash);
		callbacks.ifFound(JSON.parse(rows[0].definition));
	});
}
