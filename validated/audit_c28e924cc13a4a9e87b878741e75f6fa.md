### Title
Signature malleability in `verifyMessageWithSecp256k1PemPubKey` allows replay of signed AA-authorization messages bypassing `is_valid_sig`-based anti-replay checks - (File: signature.js)

### Summary
`signature.js` implements `is_valid_sig()` support for secp256k1 PEM-encoded keys via `verifyMessageWithSecp256k1PemPubKey`, which normalizes any supplied ECDSA signature to its canonical low-S form *before* verifying it against the message hash and pubkey. [1](#0-0)  Because ECDSA signatures `(r, s)` and `(r, n-s)` are both mathematically valid for the same message/pubkey, and the code accepts either representation (normalizing them to the same canonical form prior to verification), an attacker who observes one valid signature can trivially derive a second, byte-distinct signature that also verifies as true for the identical message and key. This is the same malleability root cause described in the external report (unnormalized ECDSA acceptance), reachable here through the `is_valid_sig()` oscript primitive used by Autonomous Agents (AAs) and by the general `verifyMessageWithPemPubKey` PEM signature path.

### Finding Description
`verifyMessageWithSecp256k1PemPubKey` extracts the raw/DER signature, imports it if necessary, and explicitly calls `ecdsa.signatureNormalize(rawCompact)` — forcing the signature into canonical form — before calling `ecdsa.ecdsaVerify(compactSig, hash, pubkey)`. [2](#0-1)  This function is reached from `formula/evaluation.js`'s `is_valid_sig` opcode handler, which is directly triggerable by any AA-trigger sender supplying `message`, `pem_key`, and `signature` as trigger data, evaluated during AA execution. [3](#0-2)  The opcode is validated as complexity-bounded and generally usable in AA formulas per `formula/validation.js`. [4](#0-3) 

Contrast this with the definition-level `sig` authentifier check used for standard address signing (`case 'sig'` in `definition.js`), which calls `ecdsaSig.verify()` directly without any normalization step — `ecdsa.ecdsaVerify` from the `secp256k1` npm package rejects non-canonical (high-S) signatures outright in that path. [5](#0-4)  The `sig`-authentifier path is therefore *not* malleable. However, the PEM secp256k1 path added specifically for the "PEM curves fix" (`bPostPemCurvesFix`) deliberately normalizes first, reintroducing malleability specifically for `is_valid_sig()`. [6](#0-5) 

Because oscript/AA authors commonly build off-chain signed messages (orders, permits, withdrawal authorizations, etc.) and use `var[]` state to record that a specific signature/message has already been "consumed" to prevent double-spending or replay (the pattern is visible with `is_valid_signed_package` + `var['executed_'||id]` idempotency keys in `test/samples/order_book_exchange.oscript`), [7](#0-6)  any AA design that uses `is_valid_sig()` similarly and keys its "already used"/"cancelled" tracking off the *raw signature bytes* (rather than off `(r, message, pubkey)` or a hash of only the canonical `r` and the message) can be bypassed: the attacker malleates `s -> n-s`, re-encodes it as a valid DER (or hex/base64) signature string, and resubmits it as trigger data. `verifyMessageWithSecp256k1PemPubKey` will normalize and accept it as valid even though the raw bytes differ from the one already recorded as "used."

### Impact Explanation
Any AA logic gating fund release, order execution, or state transitions on `is_valid_sig()` combined with signature-byte-based replay/cancellation tracking can be tricked into accepting a semantically identical but byte-different signature, defeating the intended one-time-use guarantee. This maps to the "AA fund loss" / "double-spend of a stable output"-class impact: a withdrawal, claim, or order-fill authorized once by a legitimate signer could be replayed a second time by anyone who has observed the original signature (which, once posted on-chain in a unit's trigger data, is public), draining AA balances or double-executing a state transition that was meant to be single-use.

### Likelihood Explanation
Medium. Exploitation requires (a) an AA author to have implemented signature-based idempotency/cancellation keyed on the raw signature string rather than a value derived from the canonical `r` component and message (a realistic and non-obvious pitfall given the platform's own documentation/samples showcase hash-of-message-based idempotency but signature.js exposes a malleable primitive to app authors), and (b) the attacker must have already observed a validly signed message (which is unavoidable, since posting the signature on-chain in a trigger is the normal way to use `is_valid_sig()`). No compromise of private keys or off-chain infrastructure is needed — any unprivileged AA-trigger sender can compute the malleated variant and re-post it.

### Recommendation
In `verifyMessageWithSecp256k1PemPubKey`, reject non-canonical (high-S) signatures instead of silently normalizing them, mirroring the strict behavior already used for the `sig` authentifier in `definition.js`. Concretely: after building `rawCompact`, compare it against `ecdsa.signatureNormalize(rawCompact)`; if they differ, return `false` (reject) rather than proceeding to verify the normalized copy. This restores a 1:1 mapping between a signer's action and a single valid signature encoding, closing the replay/malleability gap for `is_valid_sig()`.

### Proof of Concept
1. A signer signs a message with a secp256k1 EC private key via `signMessageWithEcPemPrivKey`, producing DER signature `sig1 = (r, s)`.
2. An AA is written (analogous to `order_book_exchange.oscript`'s pattern) to use `is_valid_sig(message, pem_key, trigger.data.signature)` to authorize a one-time withdrawal/claim, and records `var['used_' || trigger.data.signature] = true` to prevent replay.
3. The signer/attacker posts a unit with `trigger.data.signature = sig1`; the AA validates it, pays out, and marks `sig1` as used.
4. The attacker computes `sig2 = (r, n-s)` (the malleated counterpart, `n` = secp256k1 curve order) and re-encodes it as a valid DER/hex signature string.
5. The attacker posts a second trigger with `trigger.data.signature = sig2` for the same `message`/`pem_key`. Because `verifyMessageWithSecp256k1PemPubKey` normalizes before verifying, `is_valid_sig()` returns `true` again for `sig2`, and since `var['used_' || sig2]` was never set (only `var['used_' || sig1]` was), the AA treats this as a fresh, unused authorization and executes the payout/action a second time — demonstrating the double-spend/replay.

```javascript
function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;

			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);
```

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
```
