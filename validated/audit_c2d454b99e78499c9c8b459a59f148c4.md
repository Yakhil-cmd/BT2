### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table, with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` on every match. Unlike `PushHandler` (and other handlers that use the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)`), `StatusHandler` never consults `payload['repository']['full_name']`, so a legitimately signed webhook from one repository can overwrite CI status on a commit belonging to a completely different stack/repository that happens to share the same SHA.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `commit` mutated by `StatusHandler#process`. This equality is never checked.

Code path:
1. `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers for the `status` event after `verify_signature` succeeds [1](#0-0) . `verify_signature` only proves the payload was HMAC-signed by GitHub for `repository_owner` (the org/owner in the payload) — it says nothing about which specific `Commit` rows the payload is entitled to affect.
2. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query has no `stack_id`/repository filter at all, unlike `PushHandler#process`, which explicitly scopes via the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching any row [3](#0-2) [4](#0-3) .
3. `Commit#create_status_from_github!` writes the status and recomputes `status`/`deployable?` via `add_status`, which also triggers `stack.schedule_merges` [5](#0-4) [6](#0-5) . `deployable?` depends directly on the aggregated `status`, which is derived from `statuses`/`check_runs` including the just-injected forged context [7](#0-6) [8](#0-7) .

Exploit flow:
- Since git commit objects are content-addressed, an attacker can reproduce a target SHA in a repository they own by re-creating an identical git object (same tree, parent, author/committer, timestamps, message) using plumbing commands (`git hash-object`, `git mktree`, `git commit-tree`) sourced from the victim's public commit metadata (retrievable via GitHub's API). This is not a SHA-1 collision attack — it's simply replaying the same object bytes into a different repository, which is a well-known and easy occurrence (e.g., shared history between a fork and upstream, or manual reconstruction).
- The attacker then uses the GitHub Statuses API on their own repository (which they legitimately control) to set `context: codecov/project`, `state: failure` on that SHA.
- GitHub delivers a `status` webhook, correctly signed with the attacker-owned org's real webhook secret, so `verify_signature` passes legitimately — no secret is stolen or forged [9](#0-8) .
- `StatusHandler#process` finds the victim's `Commit` row (same `sha`, different `stack_id`) and writes the forged `codecov/project` failure status to it, changing that commit's `status`/`deployable?` if `codecov/project` is part of the victim stack's `ci.require`.

Existing guards fail to prevent this specifically because they validate payload authenticity and event routing, not commit ownership: `verify_signature` validates the org/repo the payload claims to be from, `drop_unhandled_event` only checks the event type is registered, and `ExplicitParameters` (`params do ... end`) only validates presence/type of `sha`, `state`, `context`, etc. — none of them enforce that the target `Commit` belongs to the repository that authenticated the webhook.

### Impact Explanation
A payload legitimately authenticated for one repository (the attacker's own) mutates commit/status state belonging to an unrelated stack/repository, directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, this can flip a victim commit's required-context status to `failure`, which (via `Commit#deployable?` and `Stack#blocking_statuses`) can block or unblock a deploy/merge decision the victim never authorized, and it also triggers `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` on the victim's stack. This is repeatable against any commit sha the attacker can reconstruct, and generalizes to any status context (not just `codecov/project`), across arbitrary stacks sharing a SHA.

### Likelihood Explanation
Preconditions: the attacker needs (1) a GitHub repository they control that is recognized by Shipit's configured GitHub App/org (so `verify_signature` succeeds for `repository_owner`), and (2) the ability to reconstruct or otherwise obtain a commit with the exact same SHA as a targeted victim commit (feasible when commit metadata is public, e.g., shared upstream history, forks, or manual git-object replication). No Shipit credentials, session, or GitHub App secret are required — the whole request path uses legitimate GitHub-signed events from the attacker's own repository. This is a low-cost, repeatable attack once a shared SHA is established.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by `sha` alone) to only the commits belonging to the repository that authenticated the webhook, mirroring the pattern already used by `Handler#stacks`/`PushHandler`, e.g.:
```ruby
def process
  stacks.find_each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or add a `where(stack_id: stacks.select(:id))` condition on the `Commit` lookup.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create two stacks `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`), with `victim_stack.cacheable_ci_requirements`/`ci.require` including `codecov/project`.
2. Create `victim_commit = Commit.create!(stack: victim_stack, sha: 'deadbeef' * 5, ...)` with an existing passing/pending status such that `victim_commit.deployable?` is currently `true` (or a known baseline).
3. Create `attacker_commit = Commit.create!(stack: attacker_stack, sha: victim_commit.sha, ...)` — same sha, different stack, simulating the reconstructed-SHA scenario.
4. Build a fake `status` payload: `{ 'sha' => victim_commit.sha, 'state' => 'failure', 'context' => 'codecov/project' }` and invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller/signature layer, consistent with test scope).
5. Assert before/after:
   - Before: `assert_equal true, victim_commit.deployable?` (or whatever the baseline state is) and `victim_commit.status.state != 'failure'`.
   - After: `victim_commit.reload`; `assert_equal 'failure', victim_commit.status.state` and `assert_equal false, victim_commit.deployable?`.
6. Assert the equality binding was violated: `refute_equal victim_commit.stack.repository&.full_name, 'attacker/repo'` while `victim_commit.statuses.last.context == 'codecov/project'` was written by a payload that never referenced `victim/repo`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
