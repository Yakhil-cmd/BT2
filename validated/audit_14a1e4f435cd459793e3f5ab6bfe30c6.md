### Title
Inconsistent case-sensitivity between `contains`/`starts_with`/`ends_with`/`equals` and `regex_match` operators allows dangerous-command block rules to be silently bypassed by case variation - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._check_condition` implements `contains`, `not_contains`, `starts_with`, `ends_with`, and `equals` as raw, case-sensitive Python string operations, while `_regex_match` compiles patterns with `re.IGNORECASE` via `compile_regex`. A blocking rule written with a non-regex operator (e.g. `contains: "rm -rf"`) will fail to match a functionally equivalent, case-varied dangerous command (e.g. `rm -RF`, which GNU coreutils accepts identically to `rm -rf`), while the same pattern expressed as `regex_match` would have caught it.

### Finding Description
`_check_condition` dispatches on `condition.operator`: [1](#0-0) 
Only the `regex_match` branch routes through `_regex_match` → `compile_regex`, which hardcodes `re.IGNORECASE`: [2](#0-1) 
The other operators (`contains`, `not_contains`, `starts_with`, `ends_with`, `equals`) perform direct, case-sensitive Python string comparisons against `field_value` (which comes straight from `tool_input['command']`/`tool_input['new_string']` via `_extract_field`, with no normalization, case-folding, or homoglyph handling) at lines 169–177.

A hookify rule author writing a block rule like:
```
conditions:
  - field: command
    operator: contains
    pattern: "rm -rf"
```
would fail to block `rm -RF /important/data` (a valid, equivalent GNU `rm` invocation using uppercase `-R`/`-F` short-option case that many users/attackers naturally use interchangeably) or any casing variant of the substring, because Python's `in` operator is case-sensitive. The identical intent expressed with `operator: regex_match, pattern: "rm -rf"` would match `rm -RF` due to `IGNORECASE`. This creates a parser differential purely based on which operator the rule author selected for otherwise semantically identical detection logic, with no documentation warning of the case-sensitivity gap.

### Impact Explanation
If a repository's `.claude/hookify.*.local.md` block rules (which gate `PreToolUse` Bash/Edit/Write execution via `evaluate_rules`) rely on `contains`/`starts_with`/`ends_with` for dangerous-command detection, a Claude Code agent instructed (e.g. via prompt injection from untrusted repo content or issue/PR text) to run a case-varied form of the blocked command bypasses the guard and executes an otherwise-blocked destructive Bash command or file mutation. This is a hook/guard bypass leading to unauthorized dangerous command execution, matching the "hook bypass leading to unauthorized command execution" bounty impact category.

### Likelihood Explanation
Exploitability depends entirely on the rule author's choice of operator in their own hookify config; only rules using `contains`/`starts_with`/`ends_with`/`equals` on case-sensitive patterns are affected, and only for inputs where a case-varied form remains functionally equivalent to the blocked action (e.g., GNU `rm -RF` vs `rm -rf`, or a `Write`/`Edit` payload matched via literal substring where case doesn't affect the underlying effect). This is a real, low-effort bypass for an attacker who can influence the command text (e.g. via prompt injection) once such a rule exists, but it is not universal—commands that are genuinely case-sensitive at the shell level (e.g., a literal binary named differently by case) would not execute successfully regardless of the rule engine's behavior.

### Recommendation
Normalize case-sensitivity consistently across all operators: either make `contains`/`not_contains`/`starts_with`/`ends_with`/`equals` case-insensitive by default (comparing lowercased `field_value`/`pattern`), or add an explicit `case_sensitive` flag to `Condition` defaulting to a documented, consistent behavior matching `regex_match`. At minimum, document the case-sensitivity gap in `plugins/hookify/skills/writing-rules/SKILL.md` so rule authors are not misled into false security assumptions when choosing operators for security-sensitive rules.

### Proof of Concept
Add a differential unit test in `plugins/hookify/core` test suite:
```python
from hookify.core.config_loader import Condition, Rule
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()
input_data = {
    "tool_name": "Bash",
    "tool_input": {"command": "rm -RF /tmp/important"}
}

contains_rule = Rule(name="r1", enabled=True, event="bash",
    conditions=[Condition(field="command", operator="contains", pattern="rm -rf")],
    action="block", message="blocked")

regex_rule = Rule(name="r2", enabled=True, event="bash",
    conditions=[Condition(field="command", operator="regex_match", pattern="rm -rf")],
    action="block", message="blocked")

result_contains = engine.evaluate_rules([contains_rule], input_data)
result_regex = engine.evaluate_rules([regex_rule], input_data)

assert result_regex != {}   # regex_match blocks it
assert result_contains == {}  # contains fails to block the equivalent command -> inconsistent/bypassed
```
Expected outcome demonstrating the bug: `result_regex` blocks (`hookSpecificOutput.permissionDecision == "deny"`) while `result_contains` returns `{}` (allowed), proving the operator-level differential bypass for the same attacker-supplied `rm -RF` command.
