### Title
Signature verification selects the org secret from `repository.owner.login`/`organization.login` while `ClosedHandler` (and other handlers) resolve the target repository/stack from the independent `repository.full_name` field, decoupling "who signed" from "what gets mutated" - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/secret to validate the HMAC using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent. `ClosedHandler` (and `ReviewStackAdapter`) instead resolve the stack to mutate from `params.repository.full_name`, a completely separate, independently attacker-controlled field. This is a real architectural decoupling, but exploiting it to bypass authentication additionally requires that the org resolved via `repository_owner` have no `webhook_secret` configured (`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank) — a precondition that is a deployment misconfiguration, not something guaranteed by this engine's code alone.

### Finding Description
The claimed broken binding, stated as an equality: `repository_owner_used_for_signing == organization_owning(params.repository.full_name)` is **not enforced** anywhere in the codebase.

- `WebhooksController#repository_owner` computes `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , and `verify_signature` uses this value to select the GitHub App config via `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `Shipit.github` looks the organization up in `secrets.github` (multi-org mode) and raises `GithubOrganizationUnknown` (→ HTTP 422) if that org key isn't configured at all [3](#0-2) . In single-org mode (`github_default_organization.nil?`), the `organization:` argument is ignored entirely and the same single config/secret is always used [4](#0-3) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present [5](#0-4) .
- `ClosedHandler#repository` resolves the target repo purely from `params.repository.full_name` [6](#0-5) , and `ReviewStackAdapter#stack`/`#archive!` locate and archive the `ReviewStack` by `environment` (`"pr#{number}"`) within that repository's scope [7](#0-6) .

Root cause: the field used to pick the *verifying secret* (`repository.owner.login` / `organization.login`) and the field used to pick the *mutated repository/stack* (`repository.full_name`) are independent JSON keys under attacker control in the same POST body, and no code path cross-checks that the owner implied by `repository.full_name` matches the `repository_owner` that authenticated the request.

However, this only becomes an authentication bypass if the attacker can produce a payload that passes `verify_signature`. Since Shipit is not receiving this from GitHub but is being posted directly by the attacker (`POST /webhooks`), the attacker fully controls the raw body and must therefore make `verify_webhook_signature` return `true`. That happens only if:
1. The resolved organization is a key configured in `secrets.github` (so `GithubOrganizationUnknown` isn't raised), **and**
2. That organization's `webhook_secret` is blank/unset (line 77 short-circuit), or the attacker already knows that org's `webhook_secret` (excluded by the rules).

No code in this engine prevents condition 2/misconfiguration; `verify_signature` treats "no secret configured" as implicit unconditional trust for that org, with no warning, no fallback secret, and no restriction tying the trusted org to the repository actually referenced inside the payload.

### Impact Explanation
If such a misconfigured org exists (multi-org GitHub App setup where one onboarded org has no `webhook_secret`), an attacker can send an unauthenticated `POST /webhooks` with `X-Github-Event: pull_request`, `organization.login` set to that unsecured org, and `repository.full_name` set to an arbitrary victim repository/stack with `blocking_statuses` configured. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ClosedHandler`, which calls `review_stack.archive!` on the victim's `ReviewStack`, deprovisioning and archiving a review stack that belongs to a different, unrelated repository — a payload for one repository mutating another's stack. This matches the "Critical: payload for one repository mutating another's stack" category. The blast radius is limited to organizations that Shipit operators have onboarded without a `webhook_secret`, and to their review-stack-enabled repos.

### Likelihood Explanation
Exploitation strictly requires an operator misconfiguration: at least one organization entry present in `secrets.github` with a blank `webhook_secret`, while other orgs (the victim's) are properly configured. The attacker needs no session, token, or secret — only knowledge of a valid, currently-onboarded-but-unsecured org name (which may be guessable/discoverable) and the victim's `owner/repo` full name (public information). Given the rules' constraint that the attacker holds no secrets, this path is only reachable through such a misconfigured tenant; there is no way demonstrated to bypass `verify_webhook_signature` when a `webhook_secret` is actually configured for the selected org, since HMAC-SHA1 cannot be forged without it. This makes the finding real but conditional on a specific, non-default configuration state rather than a universally exploitable code defect.

### Recommendation
- Reject webhook payloads where the organization implied by `repository.full_name`'s owner does not match the `repository_owner` used to select the verifying secret.
- Treat a missing/blank `webhook_secret` for a configured multi-org entry as a hard configuration error (fail closed / refuse to boot or reject all webhooks for that org) rather than implicitly trusting all payloads (`GitHubApp#verify_webhook_signature`, line 77).
- Log/alert when `webhook_secret` is blank for any organization in a multi-org deployment.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Stub `Shipit.secrets.github` to a multi-org hash with two orgs: `"victim-org"` (has `webhook_secret: "realsecret"`) and `"attacker-org"` (no `webhook_secret` key / blank).
2. Create a `Shipit::Stack`/`Shipit::ReviewStack` under `victim-org/victim-repo` with `blocking_statuses` configured (fixture), not archived.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` (or arbitrary garbage), body: `action: "closed"`, `number: <pr>`, `organization: { login: "attacker-org" }`, `repository: { full_name: "victim-org/victim-repo" }`, `pull_request: {...required fields...}`, `sender: { login: "attacker" }`.
4. Assert response is `:ok` (not `:unprocessable_entity`), i.e., `Shipit.github(organization: "attacker-org").verify_webhook_signature` returned `true` despite no valid signature — the left side of the equality (`repository_owner == "attacker-org"`) diverges from the right side (`victim-org`, the actual owner of the mutated repository).
5. Assert `victim_review_stack.reload.archived?` is `true` (or `deprovision`/`archive!` was invoked), proving cross-tenant state mutation authenticated by `attacker-org`'s (absent) secret against `victim-org`'s stack.

If step 4/5 fail under the given config (i.e., `victim-org` requires a real signature and `attacker-org` also enforces one once `webhook_secret` is present), no vulnerability is demonstrable — the exploit is contingent on the blank-secret misconfiguration described above.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
