### Title
Cross-organization repository confusion in webhook processing — organization used for signature verification is decoupled from the repository acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate an incoming webhook based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature is accepted, the *entire* raw payload is dispatched to handlers, which independently derive the target repository from a different field — `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing ties these two fields together, so a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at organization B's repo, causing Shipit to act on a stack it was never authorized to touch by that sender.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick the app/secret: `github_app = Shipit.github(organization: repository_owner)` then verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret`. [2](#0-1) 

If verification succeeds, the controller parses the full JSON body and fans it out unmodified to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  ...
``` [3](#0-2) 

Handlers, however, resolve the target repository/stack from a *different* JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` looks up the repository purely by the owner/name embedded in `full_name`, independent of `repository.owner.login` used for verification: [5](#0-4) 

Concretely, the equality the system is supposed to enforce is:
`organization authenticated (repository.owner.login → webhook_secret selection)` == `repository written (repository.full_name → Repository.from_github_repo_name)`.

Before the attacker's request: for genuine GitHub-originated webhooks, GitHub itself guarantees these two fields describe the same repository, so the equality holds. After an attacker-crafted request: since the attacker fully controls the JSON body (any subscriber to a Shipit-configured GitHub App/org — e.g. an admin of their own low-privilege organization A that is legitimately configured in `Shipit.github` — can compute a valid HMAC using organization A's real `webhook_secret`), they can set `repository.owner.login` (or `organization.login`) to `"orgA"` while setting `repository.full_name` to `"orgB/target-repo"`. The controller verifies the signature against orgA's secret (succeeds, since the attacker legitimately knows it), but the handler then acts on `orgB/target-repo`'s stacks — an organization/repository the attacker has no relationship to and no GitHub-side push/status/check access on.

Concrete write-capable handlers reachable this way:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the target branch of the spoofed repository, forcing a GitHub resync using Shipit's own `github_app` credentials scoped to the target org owner. [6](#0-5) 
- `CheckSuiteHandler#process` schedules `schedule_refresh_check_runs!` for commits on the spoofed repo's stacks. [7](#0-6) 
- `StatusHandler#process` creates commit statuses (`create_status_from_github!`) for any commit matching the attacker-chosen `sha`, without any repository-ownership check tying the commit back to the authenticated organization. [8](#0-7) 

This matches the report's bug class precisely: a value used for one authorization decision (which secret verifies the payload, i.e. "asset value of all LP tokens") is silently substituted for a different value in the actual state-changing operation (which repository gets written to, i.e. "amount actually withdrawn"), producing an outcome broader than what the verified binding should permit.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" boundary called out in scope, allowing a webhook that is legitimately signed for one (attacker-controlled) GitHub organization to trigger state-changing operations (sync, check-run refresh, commit status writes) against stacks belonging to a completely different organization/repository that Shipit also happens to host. This is an authorization-boundary break using only the sender's own legitimate webhook secret — no token, no `webhook_secret` for the victim org, no repository write access on the victim repo is required.

### Likelihood Explanation
Exploitability requires only that the attacker control a GitHub App/organization that is already configured in this Shipit instance's `Shipit.github` config (i.e., they are a legitimate, but unprivileged with respect to the victim, tenant of a multi-org Shipit deployment) and that the instance also hosts a stack for the victim org/repo. Given Shipit-engine's explicit multi-tenant design (`config/secrets.*.yml` supports multiple orgs under `github:`), this is a realistic deployment shape, making the likelihood of exploitation in a shared/multi-org instance moderate to high.

### Recommendation
When verifying and dispatching a webhook, the controller/handler layer should cross-check that `repository.owner.login` (the field used to select the verifying `webhook_secret`) matches `repository.full_name`'s owner segment (the field used to resolve the target `Repository`), rejecting the request (e.g., 422) on mismatch. More robustly, handlers should receive/verify the already-authenticated organization and refuse to act on any repository whose owner differs from it.

### Proof of Concept
1. Shipit instance is configured with two orgs in `Shipit.github`: `orgA` (attacker-controlled, attacker knows its real `webhook_secret`) and `orgB` (victim, hosts a Shipit stack e.g. `orgB/target-repo`).
2. Attacker crafts a JSON payload for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using the real secret for `orgA` (which they legitimately possess).
4. POST to `/webhooks` with `X-Github-Event: push` and the above signature.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and successfully verifies the signature.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `orgB`'s stack — a write-triggering action performed against a repository/organization the attacker does not own, achieved purely by mismatching two independent fields inside a single, correctly-signed-for-orgA payload.
