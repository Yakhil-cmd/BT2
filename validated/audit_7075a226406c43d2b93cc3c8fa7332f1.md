### Title
`WebhooksController#verify_signature` returns 200/204 without signature verification for orgs missing `webhook_secret`, leaking which orgs are unprotected - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly bypasses HMAC validation (`return true unless webhook_secret`) when an organization has no configured `webhook_secret`. Combined with `verify_signature` in `WebhooksController`, this produces a distinguishable status-code oracle (200/204 vs 422) that lets an unauthenticated attacker enumerate which configured GitHub orgs lack webhook protection, and — more importantly — once found, forge arbitrary webhook events for that org's repositories with a garbage signature.

### Finding Description
The claimed binding is: `verify_webhook_signature(signature, message) == true` should require `SecureCompare.secure_compare(signature_hmac, expected_hmac)`, for every organization configured in Shipit, regardless of whether that org has set `webhook_secret`.

Tracing the code:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` and does `head(422) unless verified` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever `@webhook_secret` is blank, i.e. `return true unless webhook_secret` [2](#0-1) .
- `repository_owner` is read directly and unauthenticated from the untrusted payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) .
- `Shipit.github(organization:)` looks up per-org config via `github_app_config(organization)` and raises `GithubOrganizationUnknown` (→422) only if the org isn't configured at all [4](#0-3) .

So the observable divergence is real: for a configured org with `webhook_secret` set and a garbage signature, the request gets `head(422)`; for a configured org with no `webhook_secret`, `verified` is `true` and the request proceeds to `create`, which dispatches to real handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) and returns `head(:ok)` [5](#0-4) . `check_if_ping`/`drop_unhandled_event` only short-circuit for the `ping` event or unregistered event types, they don't affect this divergence [6](#0-5) , [7](#0-6) .

Attacker request: `POST /webhooks` with header `X-Github-Event: status` (or `push`/`pull_request`), body `{"repository":{"owner":{"login":"<guessed-org>"}}, ...}`, and `X-Hub-Signature: sha1=garbage`. Response is `200 OK` for orgs without a `webhook_secret`, `422` for orgs that have one, and `422` for unknown orgs. This lets an attacker fingerprint the weak org.

However, this is not merely an oracle — it is a full authentication bypass: for the unprotected org, the attacker's forged webhook is processed as genuine by the real handlers (`push_handler.rb`, `status_handler.rb`, `pull_request/*_handler.rb`, etc.), meaning any repository under that org can have stacks/commits/tasks mutated with a forged payload, no secret required.

None of the listed guards prevent this: `ExplicitParameters` schemas validate payload shape, not authenticity; `drop_unhandled_event` only filters event types; there is no `force_github_authentication`/session check on this controller (it's a public webhook endpoint by design); model validations don't validate webhook provenance.

### Impact Explanation
For any org configured without a `webhook_secret` (a documented, plausible misconfiguration — e.g. an org added only for OAuth login), an unauthenticated attacker can: (1) fingerprint that org via the 200-vs-422 divergence, and (2) submit fully forged `push`/`status`/`pull_request` webhooks for any repository "belonging" to that org, since `repository_owner` and all downstream payload fields are attacker-controlled and unverified. This can drive real handler side effects (e.g., commit/status updates, review-stack provisioning, PR label/merge related state changes) for repositories the attacker does not control. This matches **Critical** — authentication bypass (forged webhook accepted) and a payload from an unauthenticated source mutating a repository's stack/commit/task state.

### Likelihood Explanation
Preconditions: at least one org configured in Shipit's `secrets.github` without a `webhook_secret` — a realistic, documented misconfiguration case per the question. Attacker cost is trivial: no credentials, tokens, or secrets are needed; only knowledge/guessing of an org name and a single HTTP POST. The oracle itself (status code divergence) is repeatable and free to probe across all configured orgs.

### Recommendation
- Fail closed instead of failing open: in `GitHubApp#verify_webhook_signature`, treat a missing `webhook_secret` as "verification not possible" and reject (`return false`) rather than `return true`, or refuse to construct a `GitHubApp` for webhook-receiving purposes without a secret.
- Make the controller's error responses uniform (e.g., always `422` with the same body/timing) regardless of whether the cause is "unknown org", "missing secret", or "bad signature", to remove the oracle.
- At configuration/boot time, validate that every org intended to receive webhooks has a `webhook_secret` configured, and log/alert on misconfigured orgs.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub calls, using existing dummy secrets fixtures):
1. Configure two orgs in `test/dummy` secrets: `org_with_secret` (has `webhook_secret: "shhh"`) and `org_without_secret` (no `webhook_secret` key), matching real deployment patterns (`test/dummy/config/secrets_double_github_app.yml`).
2. Test A: `POST /webhooks` with `X-Github-Event: status`, `X-Hub-Signature: sha1=deadbeef`, body `{"repository":{"owner":{"login":"org_with_secret"}}, ...}` → assert `response.status == 422`.
3. Test B: same request but `repository.owner.login == "org_without_secret"` → assert `response.status == 200` (or `204` if event unregistered), demonstrating `GitHubApp#verify_webhook_signature` returned `true` despite an invalid/garbage signature — i.e. `verified == true` even though `SecureCompare.secure_compare(...)` was never evaluated against attacker input.
4. Assert the divergence: `status_for(org_with_secret) != status_for(org_without_secret)`, proving the equality `verify_webhook_signature(bad_sig, payload) == secure_compare(...)` is broken specifically when `webhook_secret` is blank, and that this materializes as a forged event being accepted end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
