## Finding: Front-running bad-debt socialization to shift losses onto remaining vault depositors

### Title
Front-runnable `redeem()` allows a depositor to escape bad-debt socialization loss and shift it onto remaining suppliers - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
This is a variant of the H-12 "sandwich `accruePremiumAndExpireProtections()`" bug class. In Carapace, `deposit()`/`withdraw()` used a stale exchange rate that a discrete `accruePremiumAndExpireProtections()` call would jump, letting an attacker deposit before and withdraw after to capture value that should have accrued to all suppliers gradually. In Zest's vaults, the *interest*-accrual side of that vector is closed because `deposit`/`redeem` compute shares via `convert-to-shares-preview`/`convert-to-assets-preview`, which already fold in *pending, not-yet-applied* positive interest through `debt-preview`/`total-assets-preview` [1](#0-0) . However, the *negative* counterpart — bad-debt socialization triggered from `liquidate()` — is **not** previewed, so a depositor can watch a pending liquidation transaction that will trigger `socialize-debt` and front-run it with `redeem()`, exiting at the pre-loss exchange rate and shifting the entire write-down onto the depositors who remain.

### Finding Description
`redeem()` computes the payout using the currently stored `assets` variable and `convert-to-assets-preview`, which only accounts for *future positive* interest via `debt-preview`/`total-assets-preview`; it has no way to anticipate an in-flight `liquidate()` call that is about to socialize bad debt: [2](#0-1) 

Bad debt is realized only when `liquidate()` in the market contract finds no collateral left for a position, at which point it calls `socialize-debt-asset` → `vault-socialize-debt` on the underlying vault: [3](#0-2) [4](#0-3) 

`socialize-debt` in the vault directly reduces the vault's `assets` variable (and writes down `lindex`), which is exactly the balance that all other sToken/zToken holders' redemption value is computed from: [5](#0-4) 

Because `assets` is only mutated at the moment `liquidate()`'s transaction actually executes, any depositor who submits `redeem()` and gets it mined *before* that `liquidate()` transaction lands (e.g., via higher fee/priority, or simply racing a visible mempool transaction) redeems at the pre-write-down exchange rate. All depositors who do not (or cannot) react in time absorb a proportionally larger share of the bad debt than they should have, since the loss is now split among a smaller remaining pool of shares/assets.

### Impact Explanation
This is a shared-state ordering dependency between two unprivileged parties: the front-running depositor (attacker) and the remaining depositors (victims) of the same vault. The victims' redemption value is strictly worse with the attacker's front-run than without it, because the loss that should be split across all suppliers present at the time of the bad debt event is instead concentrated onto fewer remaining shares. This is a direct transfer of principal value from remaining suppliers to the escaping depositor — i.e., theft of user funds at rest, falling under the Critical impact class (and at minimum causes permanent loss/freezing of the socialized-loss share for remaining depositors beyond what they should have borne).

### Likelihood Explanation
Liquidations and their resulting bad-debt socialization are visible in the mempool before confirmation (the market contract itself notes liquidation ordering is a known front-running surface: "Prevents front-running attacks that prevent bad debt socialization" [6](#0-5) , showing the team was aware of liquidation-ordering front-running risk from the liquidator's side, but the vault's `redeem()` path remains unprotected for depositors seeking to escape the socialized loss). Any position that goes deeply underwater (collateral fully consumed) triggers this path, and STX-class chains have public, delay-able mempools, making this a realistically executable MEV strategy whenever a large bad-debt event is pending.

### Recommendation
- Preview pending bad debt / anticipated socialization in `convert-to-assets-preview`/`total-assets-preview` analogous to how positive interest is already previewed, so `redeem()` cannot exit at a stale, better-than-actual exchange rate.
- Alternatively, apply a withdrawal delay/queue (as recommended in the original H-12 report) so redemptions cannot be ordered ahead of a same-block bad-debt socialization event.
- Consider bundling/atomically enforcing that any pending liquidation affecting a vault's `assets` is applied before any `redeem()` in the same block is settled (e.g., an accrue-before-redeem style forced settlement of any queued write-downs).

### Proof of Concept
1. A borrower's position becomes eligible for full liquidation with no collateral remaining to cover debt (bad debt scenario).
2. A liquidator (or anyone) submits `liquidate()` on `v0-4-market.clar`, which will call `vault-socialize-debt` and reduce the affected vault's `assets` var, lowering the redemption value of that vault's tokens for all holders [3](#0-2) .
3. Bob, a depositor in that vault, observes the pending `liquidate()` transaction in the mempool and submits `redeem()` with a higher fee so it mines first.
4. Bob's `redeem()` executes using `convert-to-assets-preview` against the still-unreduced `assets` value, giving him full value with no share of the impending write-down [7](#0-6) .
5. `liquidate()` then executes, calling `socialize-debt`, which reduces `assets` for the (now smaller) remaining pool of shareholders, who collectively absorb Bob's escaped share of the loss [5](#0-4) .

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
