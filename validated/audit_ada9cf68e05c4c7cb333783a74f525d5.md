### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the actual write target is selected from a different field, `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`ASA-2025-004` is about acknowledgement bytes being deserialized twice for two different purposes (routing/validation vs. execution) with no guarantee that both deserializations agree, letting an attacker desynchronize verification from effect. Shipit's webhook pipeline has the analogous shape: the field used to select **which organization's secret authenticates the request** is not the same field used to select **which repository/stack the request acts on**.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC against using: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is passed to `Shipit.github(organization: repository_owner)`, which resolves an org-specific `webhook_secret` config: [2](#0-1)  and the signature check itself trivially returns `true` when that org has no `webhook_secret` configured: [3](#0-2) .

Once verification passes (or is trivially bypassed for a secret-less org), `create` re-parses the same raw body and dispatches it to handlers unchanged: [4](#0-3) . Every handler, however, determines the target Stack/repository from a *different* JSON field — `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process`, for example, uses these `stacks` to enqueue a sync against whatever `full_name` points to: [6](#0-5) .

Because verification keys off `repository.owner.login` (or the sibling `organization.login`) while the write acts on `repository.full_name`, a single JSON payload can supply an `owner.login`/`organization.login` that resolves to an org with no `webhook_secret` configured (auto-verified per the `return true unless webhook_secret` shortcut) alongside a `repository.full_name` pointing at a completely unrelated, secured repository/stack tracked by Shipit. The equality that should hold — *organization whose credential authenticated the request == organization that owns the repository being written to* — is broken: verification binds to `owner.login`, effects bind to `full_name`, and nothing cross-checks that they name the same tenant.

### Impact Explanation
If any GitHub App/organization entry in `secrets.github` is left without a `webhook_secret` (a supported, non-error configuration per `verify_webhook_signature`), an attacker who can reach the public `/webhooks` endpoint can forge a payload with that org's login in `repository.owner.login`/`organization.login` to pass verification unconditionally, then set `repository.full_name` to any other tracked repository. This lets an unauthenticated party trigger `stack.sync_github`, forged commit statuses (`StatusHandler`), or check-run/PR-driven actions (`push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, `pull_request/*`) against a repository/stack they do not control the GitHub webhook for — an unauthorized cross-repository write/trigger, matching the High-severity "escalation" / unauthorized-effect bar in scope.

### Likelihood Explanation
Exploitability is entirely conditional on operational configuration: it requires at least one configured organization/app entry with a blank `webhook_secret`, which `verify_webhook_signature` explicitly tolerates rather than rejects. In deployments where every configured org has a secret set, this path is not reachable by an unprivileged attacker, since forging the HMAC for the owning org still requires knowing that org's secret. This bounds likelihood to "possible if misconfigured" rather than "always exploitable," but the misconfiguration is not flagged or rejected anywhere in `GitHubApp#initialize`/`verify_webhook_signature`, so the engine itself provides no safety net.

### Recommendation
- In `Shipit::WebhooksController#verify_signature`/`repository_owner`, cross-check that the organization used to select the verifying secret actually matches the organization portion of `repository.full_name` (or reject payloads where they disagree) before dispatching to handlers.
- Remove the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`, or fail closed when an org is configured without a secret, so a secret-less org can never act as an "always verified" identity.
- Have `Handler#repository_name`/`stacks` re-derive the repository from the same identity used during signature verification rather than trusting an independent field.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `no-secret-org` (no `webhook_secret` set) and `victim-org` (tracked stack `victim-org/victim-repo`, has a secret).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "no-secret-org" },
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeef"
}
```
No `X-Hub-Signature` (or any junk value) is required.
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header — request passes.
4. `create` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name == "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's stack, entirely unauthenticated with respect to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
