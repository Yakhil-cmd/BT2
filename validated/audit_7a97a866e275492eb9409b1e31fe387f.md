### Title
`OpenedHandler#provision?` operator-precedence bug allows PR label to trigger review-stack provisioning even when `review_stacks_enabled` is `false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled` for every provisioning behavior, but Ruby's `&&`/`||` precedence only binds `review_stacks_enabled` to the `allow_all?` branch. As a result, an attacker who opens a PR and adds/keeps the provisioning label on a repository configured with `provisioning_behavior_allow_with_label?` can trigger `ReviewStackAdapter#find_or_create!` and subsequent provisioning even though `review_stacks_enabled` was never turned on.

### Finding Description
The broken binding, stated as an equality that the code is supposed to enforce but does not:

`provision? == (repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)))`

What the code actually computes, per Ruby operator precedence (`&&` binds tighter than `||`): [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` is only ANDed with the `allow_all?` term; the `allow_with_label?` and `prevent_with_label?` terms are evaluated independently of `review_stacks_enabled`. With `review_stacks_enabled == false` and `provisioning_behavior_allow_with_label? == true`, `provision?` still returns `true` whenever the PR carries the provisioning label — a condition fully controlled by the PR's own author.

Call path: `process` calls `respond_to_pull_request_opened?` (`params.action == "opened" && provision?`), and on success invokes `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates/finds a `ReviewStack` record and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add` (`enqueue_for_provisioning`). The queue worker (`ReviewStackProvisioningQueue#provision`) later calls `stack.provisioner.provision?` (defaults to `true` in `ProvisioningHandler::Base#provision?` unless overridden) and then `stack.provision`, driving the review-stack's task/deploy execution path (`Command`/`PTY.spawn`) exactly as if review stacks had been properly enabled by a maintainer. [2](#0-1) [3](#0-2) [4](#0-3) 

No existing guard rescues this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` itself, so the precedence bug propagates straight through. `pull_request_has_provisioning_label?` reads `pull_request_label_names` directly from the webhook payload's `labels`, which is attacker-controlled content of their own PR/webhook payload and is not cross-checked against any authorization decision beyond the (buggy) `provisioning_behavior_allow_with_label?` flag. `LabeledHandler#respond_to_label_change?`, by contrast, correctly ANDs `repository.review_stacks_enabled` as a standalone top-level condition, showing the intended invariant that `OpenedHandler#provision?` fails to implement consistently. [5](#0-4) 

### Impact Explanation
A repository whose maintainer configured `provisioning_behavior` to `allow_with_label` at some point — intending it to take effect only once review stacks are later enabled — instead has review-stack provisioning (and the ensuing task/deploy execution path) reachable purely by any PR author adding the provisioning label to their own PR, with no maintainer action to actually enable review stacks. This is an unauthorized-deploy-class issue: a record (the `ReviewStack`) is created and queued for provisioning for a repository configuration that never authorized this behavior (`review_stacks_enabled == false`), matching the Critical category ("payload... mutating another's stack... or an unauthorized deploy"). The blast radius is scoped to repositories with this specific latent config (`review_stacks_enabled: false`, `provisioning_behavior: allow_with_label` or `prevent_with_label`), but it is fully repeatable by any PR author against every such repository.

### Likelihood Explanation
Preconditions are narrow but plausible: a repository must have `provisioning_behavior_allow_with_label?` (or `prevent_with_label?`) set while `review_stacks_enabled` remains `false` — a realistic staged-rollout configuration ("set the behavior now, flip the enable flag later"). Attacker cost is minimal: open a PR and add/observe a label on it, both actions available to any contributor on their own PR with no Shipit privileges required. The bug is deterministic and repeatable on every matching repository.

### Recommendation
Fix operator precedence/grouping in `provision?` so `review_stacks_enabled` gates all branches, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`-style minitest:
1. Create a `Repository` with `review_stacks_enabled: false` and `provisioning_behavior: 'allow_with_label'`.
2. Build webhook `params` for `action: "opened"` with `pull_request.labels` containing `repository.provisioning_label_name`.
3. Assert, before tracing: expected binding `provision? == false` (since `review_stacks_enabled == false`).
4. Instantiate `OpenedHandler.new(params)` (or call `process`) and assert actual: `handler.send(:provision?) == true`, and that a `ReviewStack` record is created/enqueued (`Shipit::ReviewStack.exists?(...)` becomes true), demonstrating the two sides of the equality diverge and provisioning proceeds despite `review_stacks_enabled == false`.
