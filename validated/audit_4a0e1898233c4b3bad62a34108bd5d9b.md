### Title
CI Status Forgery Across Repositories via Organization-Scoped Webhook Signature Verification - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies inbound GitHub webhooks by picking an HMAC secret keyed on the organization named *inside the unverified payload* [1](#0-0) , but the `status` event handler that consumes that payload never checks which repository/organization the event actually belongs to — it matches and mutates commit CI status purely by SHA, globally across the whole installation [2](#0-1) . This breaks the binding "organization authenticated == repository written."

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the verification secret straight from the attacker-controlled JSON body: [3](#0-2) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
It then fetches `Shipit.github(organization: repository_owner)` and validates the `X-Hub-Signature` against that organization's `webhook_secret` [1](#0-0) . In the documented multi-tenant configuration, each GitHub organization has its own distinct GitHub App and its own `webhook_secret` [4](#0-3) , all of which POST to the *same* shared Shipit `/webhooks` endpoint.

Once the signature check passes for whichever organization the payload claims to represent, `Webhooks.for_event('status')` dispatches to `StatusHandler`: [5](#0-4) 
```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    ...
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Unlike other handlers (e.g. `PushHandler`, the `PullRequest::*` handlers), `StatusHandler` never calls `Handler#stacks`/`repository_name` to scope the operation to the repository named in `payload['repository']['full_name']` [6](#0-5) . It resolves and mutates commits purely by `sha`, across **every** stack/repository tracked by the Shipit instance. `create_status_from_github!` creates a `Status` record with attacker-supplied `state`, `description`, `target_url`, and `context` verbatim [7](#0-6) .

Because the signature only proves "this request came from an organization known to Shipit," not "this event pertains to the repository/commit being mutated," any organization admin who legitimately runs their own GitHub App pointed at the shared Shipit webhook endpoint can forge a `status` event carrying an arbitrary `sha` and `state: "success"`. If that SHA also exists in another organization's tracked repository (trivial for public/forked commits, since git SHAs are content-addressed and reproducible by anyone with read access to the target commit), the forged status is written onto the victim's commit.

### Impact Explanation
Commit CI status directly gates deploy eligibility (`deployable?`/CI checks referenced throughout `Stack`/`Commit`, e.g. `require_ci` handling seen in `test/controllers/api/deploys_controller_test.rb` lines 88-103). By forging a `success` status for a victim commit whose real CI has not passed, an attacker who controls a *different*, unrelated organization tenant on the same Shipit deployment can make that commit appear deployable, enabling an **unauthorized deploy** of a commit belonging to another organization/repository they have no access to. This satisfies the "unauthorized deploy" Critical-impact criterion, since it crosses the organization-authenticated vs. repository-written trust boundary.

### Likelihood Explanation
Exploitability requires only: (1) the target Shipit instance hosts multiple GitHub organizations/tenants sharing one webhook endpoint (an explicitly documented, supported configuration [8](#0-7) ), and (2) the attacker administers one of those organizations' GitHub Apps (so they legitimately know that org's `webhook_secret`, which is standard for any tenant onboarding). No repository write access, Shipit account, or GitHub token to the victim org is required — only knowledge of a target commit SHA, which is public/derivable information. This is a realistic, low-effort attack for any unprivileged-relative-to-victim tenant admin in a multi-org deployment.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope via `Handler#stacks`) should restrict its `Commit.where(sha: ...)` lookup to commits belonging to stacks under the repository named in the payload (`payload.dig('repository', 'full_name')`), and that repository's owner must be cross-checked against the organization whose secret validated the signature. In general, `repository_owner` (used to choose the verification key) and `repository.full_name`'s owner (used to determine what gets mutated) must be proven consistent before any write is performed.

### Proof of Concept
1. Shipit instance is configured for two independent GitHub orgs/tenants, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret`, both posting to the same `/webhooks` endpoint (per `docs/setup.md`, multi-org config).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that GitHub App) and knows/derives the SHA of a commit tracked under `victim-org`'s stack (e.g., the commit is public, or a fork produces an identical SHA).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches that org's secret, and the signature verifies successfully [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (owned by `victim-org`, unrelated to the authenticating organization), and creates a `success` `Status` on it [2](#0-1) , potentially unblocking an unauthorized deploy of that commit in `victim-org`'s stack.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
