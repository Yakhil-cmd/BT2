### Title
Api::CCMenuController bypasses the `ApiClient`-to-stack scope, letting a stack-scoped token read the build/deploy status of any other stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts which stacks an `ApiClient` may touch by intersecting all stack lookups with `current_api_client.stack_id`. `Shipit::Api::CCMenuController` overrides the `#stack` accessor and looks the stack up directly with `Stack.from_param!`, never going through the scoped `stacks` collection, breaking the "stack a token authorizes" vs. "stack a token touches" equality.

### Finding Description
In `app/controllers/shipit/api/base_controller.rb`, every controller is meant to resolve the target stack only from the set the client is allowed to see: [1](#0-0) 

`current_api_client.stack_id?` reflects the `stack_id` column set on an `ApiClient` record (see fixture `here_come_the_walrus`, which is scoped to a single stack): tokens created this way are meant to only ever operate on that one stack.

`Api::CCMenuController`, however, defines its own `#stack` method that completely ignores this scoping and resolves the stack directly from the global `Stack` collection: [2](#0-1) 

The controller only enforces `require_permission :read, :stack`, which checks that the token has the *permission string* `read:stack` in `ApiClient#permissions` [3](#0-2)  — it never checks that the token's `stack_id` matches the stack being requested. `ApiClient.authenticate` similarly only verifies the token's HMAC signature and looks up the client by id; it carries no per-request stack binding either [4](#0-3) .

This is exactly the class of vulnerability described in the source report: a value that is checked/authorized in one dimension (the `ApiClient`'s permission scope) is not equal to the value that is actually acted upon (the arbitrary `stack_id` route parameter), because the code path that resolves the object to act on (`CCMenuController#stack`) diverges from the code path that established the authorization boundary (`BaseController#stacks`/`#stack`).

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (`stack_id` set, `read:stack` permission granted for CI/monitoring integration use, e.g. CCTray/CruiseControl consumers) can be replayed against `GET /api/stacks/*stack_id/ccmenu` for any other stack in the Shipit instance. This discloses that other stack's current deploy/build status, whether a task is running, and the latest deploy id/end time — cross-stack read of stack and deploy state that the token was never meant to access. This matches the rules' High-severity bucket: "unauthenticated [outside-scope] read of stack state, task streams or deploy output" via a broken token-to-stack authorization binding.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token (the exact "least privilege" mechanism operators are told to use for CI dashboards) can trivially exploit this by substituting a different `stack_id` into the URL — no additional credentials, signature forging, or privileged access required. The `CCMenuController#authenticate_api_client` override even accepts the token via a `params[:token]` query string, which is how CI dashboard URLs are normally shared/embedded, increasing the chance of accidental as well as deliberate exposure.

### Recommendation
Remove the bespoke `#stack` implementation in `Api::CCMenuController` (and its `#authenticate_api_client` override, if kept for query-string auth) and route stack resolution through the same `stacks`/`stack` helpers defined in `Api::BaseController`, so `current_api_client.stack_id` is always intersected with the requested stack before use, consistent with every other API controller (`CommitsController`, `OutputsController`, `HooksController`, etc.).

### Proof of Concept
1. As an admin, create two stacks, `org/repo-a` and `org/repo-b`.
2. Create an `ApiClient` scoped to `repo-a` only (`stack: repo-a`, `permissions: [read:stack]`) — mirrors fixture `here_come_the_walrus`.
3. Authenticate with that client's token and call:
   `GET /api/stacks/org/repo-a/production/ccmenu?token=<token>`
   — succeeds as expected (in scope).
4. Using the same token, call:
   `GET /api/stacks/org/repo-b/production/ccmenu?token=<token>`
   — because `CCMenuController#stack` calls `Stack.from_param!` directly instead of `stacks.from_param!`, this request also succeeds and returns `repo-b`'s deploy/build status, even though the token's `stack_id` is `repo-a`'s id and `current_api_client.stack_id?` should have excluded `repo-b` entirely.
