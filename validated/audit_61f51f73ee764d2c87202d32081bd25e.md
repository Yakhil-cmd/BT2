### Title
Webhook signature verification is keyed to `repository.owner.login` while every event handler dispatches on `repository.full_name` (or nothing at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret validates the inbound HMAC using a payload field (`repository.owner.login`), but the handlers that consume the same payload act on a *different* payload field (`repository.full_name`) — or, in the case of `StatusHandler`, no repository field at all. The equality the design implicitly assumes — "the organization whose secret authenticated this request == the repository/commit the handler writes to" — is never enforced.

### Finding Description
`WebhooksController#verify_signature` picks the verifying GitHub App config purely from the attacker-supplied payload: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That org's config comes from `Shipit.github_app_config(organization)`, one entry among possibly several in `secrets.github` in a multi-tenant setup, and `verify_webhook_signature` explicitly no-ops when that org has no secret configured: [3](#0-2) 

Docs describe the webhook secret as *optional* per GitHub App: [4](#0-3)  and setup guide lists `Webhook secret (optional)` — this is a supported, documented deployment shape, not a misconfiguration outside scope.

Once "verified", the actual event handlers never re-check `repository_owner`. `Handler#stacks` derives the acted-upon repository from a *separate* payload field, `repository.full_name`: [5](#0-4) 

`Repository.from_github_repo_name` splits that string on `/` to look up ANY repository/owner tracked by the Shipit instance: [6](#0-5) 

`PushHandler` uses this to force `sync_github` on any stack under that repo/branch, driven entirely by attacker-controlled `ref`/`after`: [7](#0-6) 

Worse, `StatusHandler` doesn't even use `stacks`/`repository_name` — it matches by `sha` globally across the whole instance and materializes a CI `Status` from the payload as-is: [8](#0-7) [9](#0-8) 

Creating a `Status` triggers `schedule_continuous_delivery` on the commit and can flip `enable_ci_on_stack`, which feeds into automatic/continuous deployment eligibility for that commit's real stack: [10](#0-9) 

**Break-down of the binding**: verification is scoped to `organization = repository_owner (payload)`; the write/action is scoped to `repository = repository.full_name (payload)` for push/membership/pull_request handlers, and to `sha (payload, unscoped)` for status/check_suite handlers. There is no code path enforcing `repository_owner == owner(repository.full_name)`, nor any repository scoping at all in `StatusHandler`.

### Impact Explanation
In a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, as supported by `Shipit.github_app_config`), if even one configured organization omits its optional `webhook_secret`, an unauthenticated attacker can send a `push`/`status`/`membership` webhook whose `repository.owner.login` (or `organization.login`) names that unsecured org — passing `verify_signature` trivially — while setting `repository.full_name` to any other tracked repository, or for `status` events, an arbitrary real commit `sha` belonging to any stack in the whole instance, with no owner check at all. This lets the attacker:
- Fabricate a `success` CI status for a real commit on any stack, triggering `schedule_continuous_delivery` and enabling an unauthorized deploy through the continuous-deployment path, without ever touching that stack's own webhook secret.
- Force `GithubSyncJob` re-syncs for arbitrary stacks via forged `push` events.
- Manipulate team membership across organizations via `membership` events, since that handler is also driven by attacker-controlled `organization`/`team`/`member` payload fields once "authenticated" against an unrelated org.

This matches the report's underlying "trust boundary not equal to the boundary actually enforced" bug class (analogous to `GovDev.updateSolution`'s owner-check-but-unlimited-blast-radius pattern): a narrow authentication check (owner-scoped signature) gates an operation whose actual effect (arbitrary repo/commit write) is unscoped.

### Likelihood Explanation
Requires only (a) a multi-org Shipit deployment where at least one configured GitHub App has no webhook secret set (an explicitly documented, optional configuration) and (b) network access to the public `/webhooks` endpoint — no privileged credentials, tokens, or secrets are needed for the unsecured org. This is fully within the "unprivileged attacker" analog class the rules require (no `ApiClient` token, no `webhook_secret` of the *target* org, no session).

### Recommendation
Bind verification and action to the same identity: derive the authorizing organization strictly from the *looked-up* `Repository`/`Stack` record (i.e., verify against the secret of the organization that owns the resolved `repository.full_name`, not the attacker-supplied `repository.owner.login`), and require every handler (especially `StatusHandler`) to scope lookups by the verified repository rather than a global `sha` search. Additionally, consider making `webhook_secret` mandatory per configured organization rather than silently trusting unsigned requests when absent.

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two orgs, `secure-org` (has `webhook_secret`) and `insecure-org` (no `webhook_secret` set, per documented "optional" config).
2. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "sha": "<real sha of a commit belonging to secure-org/target-repo>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "insecure-org" }, "full_name": "insecure-org/whatever" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'insecure-org')`; `verify_webhook_signature` returns `true` unconditionally because `insecure-org` has no `webhook_secret` (`lib/shipit/github_app.rb:77`).
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — the real commit under `secure-org/target-repo` — and calls `commit.create_status_from_github!`, creating a `success` `Status` and scheduling continuous delivery for that stack, entirely bypassing `secure-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
