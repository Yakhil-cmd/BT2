[1](#0-0) ### Title
Permissionless accrual overflows debt valuation and permanently freezes a valid whale market - (File: common/src/rates/scaling.rs)

### Summary
A market can remain inside the configured token cap, utilization domain, and borrow-index ceiling while `scaled_amount * index / RAY` exceeds `i128::MAX`. Once that happens, `scaled_to_original` reverts with `MathOverflow` during accrual, so `update_indexes`, `withdraw`, and `repay` all fail and market funds become permanently frozen. [2](#0-1) [3](#0-2) 

### Finding Description
`max_cap_for_decimals` only ensures that converting the configured token-unit cap to RAY fits in `i128`; it does not account for later multiplication by an index that can grow up to `MAX_BORROW_INDEX_RAY = 1e9 RAY`. [4](#0-3) [5](#0-4) 

`scaled_to_original` delegates to `Ray::mul`, which returns `MathOverflow` when the representable quotient exceeds `i128::MAX`. [2](#0-1) [6](#0-5) [7](#0-6) 

Every mutation synchronizes the market before applying the operation, and `global_sync` repeatedly calls `accrue_step` on elapsed chunks. [8](#0-7) [9](#0-8) 

The public `update_indexes` controller entrypoint is permissionless for any authorized caller and forwards the supplied `Vec<HubAssetKey>` to the pool. [10](#0-9) [11](#0-10) 

The checked-in scenario creates an 18-decimal market at the accepted cap domain, supplies `BILLION * 10^18` base units, and borrows 98% of it. [12](#0-11) 

Repeated accrual then returns `MathOverflow` while the stored borrow index is still below `MAX_BORROW_INDEX_RAY`, proving that the value ceiling is reached before the documented index ceiling can clamp growth. [13](#0-12) 

### Impact Explanation
This is permanent freezing of user funds: after the first failed accrual, withdrawals and repayments hit the same `MathOverflow` because they accrue before mutating the position. [14](#0-13) 

Because ledger time continues to advance, later calls cannot route around the already-unrepresentable scaled valuation; the market remains unable to settle borrows, supplier claims, liquidation, or revenue without an out-of-band governance or upgrade path. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
The trigger requires an unusually large market operating near the accepted amount ceiling and sustained high utilization, so the practical likelihood is lower than an ordinary transaction-input bug. [17](#0-16) 

Those balances and rates are nevertheless inside the accepted configuration domain: the cap validator admits the tested cap, utilization can be configured at or above `RAY`, and the stored index remains below its explicit ceiling when the revert begins. [18](#0-17) [19](#0-18) 

This is a Medium-severity permanent-freeze issue: the impact is severe, but it depends on an extreme but valid market scale and sustained borrowing conditions. [3](#0-2) [14](#0-13) 

### Recommendation
Enforce a combined scaled-share/index domain rather than validating only the token-to-RAY conversion; total supply and debt shares must satisfy the maximum later valuation implied by `MAX_SUPPLY_INDEX_RAY` and `MAX_BORROW_INDEX_RAY` with headroom for accrued revenue. [20](#0-19) [5](#0-4) 

Alternatively, accrual must avoid materializing unrepresentable RAY totals: compute utilization and index transitions with widened `I256` ratios or saturating comparisons, and clamp the index before trying to return an `i128` total value. [2](#0-1) [21](#0-20) 

Document the true `(scaled_amount, index)` bound and add regression coverage for `supply`, `borrow`, `repay`, `withdraw`, `liquidate`, `claim_revenue`, and `update_indexes` at that boundary. [22](#0-21) [23](#0-22) 

### Proof of Concept
The repository already contains an executable scenario in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [24](#0-23) 

1. Create an 18-decimal `BIG18` market, lift its spoke caps to `max_cap_for_decimals(18)`, and configure nonrestrictive utilization. [25](#0-24) 
2. An unprivileged supplier calls `supply` for `BILLION * 10^18` `BIG18`, another user supplies collateral, and the borrower calls `borrow` for 98% of the `BIG18` principal. [17](#0-16) 
3. Any caller repeatedly invokes the public `update_indexes(caller, [HubAssetKey { hub_id, asset: BIG18 }])` entrypoint as ledger time advances. [10](#0-9) [26](#0-25) 
4. The call eventually reverts with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, proving the revert occurs before the index cap protects the calculation. [27](#0-26) 
5. Subsequent `withdraw` and `repay` calls also return `MathOverflow`, leaving the supplied funds and debt position frozen. [14](#0-13)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

**File:** docs/reference/formulas.md (L20-30)
```markdown
Protocol boundaries require non-negative amounts; `Ray`, `Wad` and `Bps`
constructors do not enforce that restriction themselves. Multiply-divide uses
an `i128` fast path or an exact `I256` intermediate. Unrepresentable results
raise `MathOverflow`, except at explicit saturating sites; zero divisors raise
`DivisionByZero`.

Half-up multiply-divide requires non-negative operands and a positive divisor.
Raw floor and ceiling multiply-divide also support signed quotients. Decimal
upscaling uses checked `i128` arithmetic. Downscaling and division by a positive
integer support the signed extremes; signed half-up downscaling rounds exact
halves away from zero.
```
