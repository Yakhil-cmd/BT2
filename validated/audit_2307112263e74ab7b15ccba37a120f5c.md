## Finding

### Title
Self/oracle data-feed griefing via `ifseveral='abort'` freezes AA logic that depends on data feeds - (File: data_feeds.js)

### Summary
The C4 finding shows that a permissionless function (`generateFLNQuote`) can be called twice in the same block to zero out a difference-based freshness check, permanently reverting `_ensurePriceStability` and blocking `migrate`/`stabilizeFlan`. The Obyte analog is in the oscript/AA `data_feed[[...]]` evaluator: when a feed reader uses `ifseveral='abort'`, any address that is entitled to post that feed (which, in common AA patterns, can be the AA trigger sender itself acting as a self-oracle, or any one member of a multi-address oracle list) can post two distinct values for the same `feed_name` inside the still-unstable window (`min_mci`..current `max_mci`). This deterministically forces `bAbortedBecauseOfSeveral = true`, causing every read of that feed to fail with `"several values found"`, bouncing the AA trigger and freezing any logic gated on that feed for as long as the poster keeps refreshing the value faster than the DAG stabilizes — exactly mirroring "posting twice per block prevents any [downstream operation]".

### Finding Description
`readDataFeedValue`/`readDataFeedByAddress` in `data_feeds.js` implement the read side of `data_feed[[...]]`: [1](#0-0) 

For a given `address` + `feed_name`, the query is restricted to `[min_mci, max_mci]` and, when `ifseveral==='abort'`, it fetches up to 2 matching records: [2](#0-1) 

If any two records for the same address+feed_name land inside that window, `objResult.bAbortedBecauseOfSeveral` is set `true`, and the read is treated as ambiguous. The same “abort if several” pattern is applied to the in-memory scan of unstable AA messages in `readDataFeedValue`: [3](#0-2) 

This propagates directly into oscript evaluation. `formula/evaluation.js`’s `data_feed` operator calls `dataFeeds.readDataFeedValue` and turns `bAbortedBecauseOfSeveral` into a fatal formula error: [4](#0-3) 

The same abort semantics exist for the `attestation[[...]]` operator as well: [5](#0-4) 

Just as in the Solidity bug, the freshness/ambiguity check depends only on *how many* records were posted inside a narrow, attacker-influenced window (`min_mci`..current `max_mci`), not on who posted them or with any economic disincentive. Any address that is authorized to write to that `feed_name` (which is frequently the AA trigger’s own address in "self-attested" AA patterns, or any single member of a decentralized/multi-oracle list configured in `oracles=addr1:addr2:...`) can post two differing values while the DAG is still unstable around that MCI window, which is trivial and cheap (no cryptoeconomic cost, unlike Behodler’s post-fix EYE-burn proposal).

### Impact Explanation
Any AA that gates fund release, state transition, or escrow settlement on `data_feed[[..., ifseveral='abort']]` (a pattern explicitly supported and tested, see `formula/validation.js` `validateDataFeed`) can be indefinitely denied service: the AA trigger will keep bouncing with `"several values found"` as long as the responsible poster refreshes the feed value inside the still-unstable window faster than the network advances main-chain stability past that MCI. This satisfies the "AA fund loss or freezing" impact category — funds intended to be released by a data-feed-gated condition remain frozen in the AA, and legitimate trigger senders relying on that feed cannot make progress, with no cost to the griefer beyond normal transaction fees.

### Likelihood Explanation
The bug requires no special privilege beyond being one of the addresses permitted to post the `feed_name` used by the AA — a pattern intentionally supported by oscript (`oracles=trigger.address` self-attestation, or any address included in a multi-oracle list). Test coverage in `test/formulas_in_contracts.test.js` (`'formula - ifseveral abort'`) and `test/formula.test.js` (`'attestation ifseveral abort'`) confirms the abort branch is a normal, reachable code path, not a theoretical edge case: [6](#0-5) 

Because posting two feed values inside one still-unstable window is cheap and requires no coordination beyond controlling one authorized oracle address, likelihood is High for any AA that adopts this common pattern.

### Recommendation
- For `ifseveral='abort'`, only count as "several" the records that are already stable (i.e. compare against `min(max_mci, last_stable_mci)`), so unstable in-flight duplicates from a single actor cannot manufacture ambiguity.
- Alternatively, deduplicate by `(address, mci)` and keep only the highest-mci record per address before evaluating "several", so that rapid re-posting by the same address cannot itself trigger the abort condition — only genuinely conflicting posts from *different* addresses within the window should.
- Document to AA authors that `ifseveral='abort'` against a frequently-updating or self-attested oracle is unsafe without a sufficiently large `min_mci`/stability margin, and encourage requiring the referenced feed's supplying unit to be *stable* before consumption.

### Proof of Concept
1. AA author writes state logic that releases funds when `data_feed[[oracles=X55..., feed_name='release', ifseveral='abort']]` becomes available (or uses `oracles=trigger.address` for self-attested unlocking).
2. The oracle/trigger-sender address posts a `data_feed` message with `release=1` in unit U1, then, before U1 stabilizes, posts another `data_feed` message with `release=2` (or any different value) for the same `feed_name` in unit U2, both landing inside the AA’s `[min_mci, max_mci]` read window (`data_feeds.js:307-316` / `data_feeds.js:211-254`).
3. Any trigger that evaluates the `data_feed[[...]]` expression during this window hits `bAbortedBecauseOfSeveral=true` and bounces with `"several values found"` (`formula/evaluation.js:646-663`).
4. Repeat step 2 every time the previous pair of posts is about to stabilize, keeping the window perpetually ambiguous and the AA logic perpetually bounced, freezing any funds/state gated on that feed.
