### Title
Webhook signature verification keys off `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, letting a valid signature from one GitHub App/organization authorize actions against another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which HMAC secret) to verify the webhook signature with based on `repository.owner.login` (or `organization.login`) taken from the JSON body itself. [1](#0-0) [2](#0-1)  Once the signature is accepted, every webhook `Handler` resolves the target `Repository`/`Stack` using a *different* field of the same payload, `repository.full_name`. [3](#0-2)  Shipit explicitly supports multiple GitHub Apps, one per organization, each with its own independent `webhook_secret`. [4](#0-3) 

### Finding Description
The trust binding that should hold is: *the organization whose secret validated the signature* == *the repository/organization whose stack is acted upon*. The engine breaks this equality:

- Signature verification uses `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`). [2](#0-1) 
- The signature itself only proves the sender knew the HMAC secret configured for whichever organization is named by that field — it says nothing about the other fields in the body being consistent with that organization.
- After the signature check passes, `Handler#stacks` looks up the affected `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, an entirely separate, unauthenticated-relative-to-the-chosen-secret field. [3](#0-2) 

In a deployment with multiple configured GitHub Apps/organizations (a supported and documented configuration [5](#0-4) ), an attacker who legitimately possesses (or can obtain, e.g. via a repo they control and its own delivered webhook secret) the webhook secret for **their own** organization ("OrgOne") can craft a payload where `repository.owner.login = "OrgOne"` (so the signature check picks and validates against OrgOne's secret) while `repository.full_name = "OrgTwo/victim-repo"` (a stack belonging to a completely different, unrelated organization). The controller only checks that the signature is valid *for the organization named in the payload*, never that the organization used for verification actually matches the repository/stack the handler subsequently mutates. This is precisely the "organization that authenticated versus the repository that is written" trust-binding class.

### Impact Explanation
Handlers triggered this way (`push`, `status`, `check_suite`, etc.) act on the victim organization's `Stack` — e.g. enqueuing `GithubSyncJob` for the victim stack, recording forged commit `Status` records, or updating check-run state — using only proof-of-possession of an unrelated organization's webhook secret. Depending on how commit/check statuses feed into Shipit's continuous-deployment gating, this can influence which commits are considered "green"/deployable on a stack the attacker has no authorization over, i.e. it crosses an organizational trust boundary the signature is meant to enforce. This maps to the "unauthorized deploy" / cross-repository-write category of impact defined for this exercise.

### Likelihood Explanation
Requires an unprivileged attacker to control at least one organization/repository with its own Shipit-configured GitHub App and webhook secret (a normal, supported multi-tenant Shipit setup), and to be able to fire a webhook event for that organization (installing the app on their own org and pushing/triggering events is enough — no privileged Shipit account, `ApiClient` token, or access to the victim's secrets is needed). Given multi-org configuration is explicitly documented/supported, this is plausible in real deployments that host stacks for more than one organization.

### Recommendation
When resolving the target repository/stack in `Shipit::Webhooks::Handlers::Handler#stacks`, verify that `repository.full_name`'s owner matches the `repository_owner`/`organization.login` value that was actually used to select and validate the webhook signature, and reject (or drop) the event otherwise. Equivalently, bind the verified organization to the lookup so a signature validated for org A can never resolve a stack belonging to org B.

### Proof of Concept
1. Attacker controls organization `OrgOne` with a Shipit GitHub App installed, secret `S1`.
2. Victim organization `OrgTwo` has a Shipit stack for `OrgTwo/victim-repo`, secret `S2` (unknown to attacker).
3. Attacker builds a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  ... push/status/check_suite fields referencing a commit on OrgTwo/victim-repo ...
}
```
4. Attacker signs the raw body with `S1` and sends it to `/webhooks` with header `X-Hub-Signature`.
5. `verify_signature` computes `Shipit.github(organization: "OrgOne")` and validates successfully against `S1`. [1](#0-0) 
6. The matching `Handler` (e.g. push) calls `Repository.from_github_repo_name("OrgTwo/victim-repo")` and mutates/enqueues jobs for the victim's stack. [3](#0-2) 

Note: I was not able to fully trace, within the available iterations, the downstream effect of forged `status`/`check_suite` events on continuous-deployment auto-deploy gating (i.e., whether this can be escalated all the way to an actual unauthorized `Deploy`); that would need to be confirmed by reading `app/models/shipit/webhooks/handlers/status_handler.rb`, `check_suite_handler.rb`, and the continuous-deployment scheduling code, which I did not get to inspect before running out of tool calls.
