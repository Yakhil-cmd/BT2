### Title
ServiceChain Bridge Sends Stale Genesis KIP71 Config Instead of Current Governance Parameters — (`node/sc/main_bridge_handler.go`)

### Summary

`handleServiceChainParentChainInfoRequestMsg` in the main bridge handler reads KIP71 fee parameters directly from the static genesis `ChainConfig` (`chainCfg.Governance.KIP71`) instead of the live governance module. After any governance vote updates a KIP71 parameter, the bridge continues advertising the original genesis values to the service chain, causing the service chain to compute incorrect gas prices for all bridge operator transactions on the parent chain.

### Finding Description

When the service chain requests parent chain info, the main bridge handler constructs a `parentChainInfo` response by reading KIP71 parameters directly from the immutable genesis `ChainConfig`: [1](#0-0) 

The `chainCfg` returned by `mbh.mainbridge.blockchain.Config()` is the static genesis configuration. It is never mutated when governance votes ratify changes to `kip71.lowerboundbasefee`, `kip71.upperboundbasefee`, `kip71.gastarget`, `kip71.maxblockgasusedforbasefee`, or `kip71.basefeedenominator`. The live values are stored exclusively inside the governance module (header governance or contract governance), accessible via `govModule.GetParamSet(blockNum)`.

All five KIP71 parameters are explicitly listed as mutable governance parameters: [2](#0-1) 

The correct current values are assembled by the governance module and exposed through `ParamSet.ToKip71Config()`: [3](#0-2) 

The service chain receives the stale `parentChainInfo` and immediately uses it in two ways: [4](#0-3) 

1. `sbh.remoteGasPrice = pcInfo.KIP71Config.UpperBoundBaseFee` — sets the gas price for every bridge operator transaction sent to the parent chain.
2. `sbh.subbridge.bridgeAccounts.SetParentKIP71Config(pcInfo.KIP71Config)` — stores the stale config for ongoing base-fee calculations.

The `parentChainInfo` struct that carries these values: [5](#0-4) 

### Impact Explanation

**Scenario A — Governance lowers `UpperBoundBaseFee`:**
The service chain continues using the old (higher) value as `remoteGasPrice`. Every bridge operator transaction overpays gas fees by the difference, draining KAIA from the bridge operator account. This is a direct, ongoing fee overcharge on system-managed bridge funds.

**Scenario B — Governance raises `UpperBoundBaseFee`:**
The service chain uses the old (lower) value as `remoteGasPrice`. Once the parent chain's actual base fee rises above the stale cap (which is now permitted), bridge operator transactions are rejected by the parent chain's txpool. Bridge value transfers stall: bridged assets remain locked on the service chain side and cannot be settled on the parent chain until the service chain reconnects and re-syncs the correct config.

**Scenario C — Governance changes `GasTarget` or `BaseFeeDenominator`:**
The service chain's stored `KIP71Config` is used to compute `NextMagmaBlockBaseFee` for its own base-fee tracking of the parent chain. Stale values produce an incorrect predicted base fee, compounding the gas-price mismatch over time.

- **Impact:** High — incorrect fee charge on bridge operator KAIA; potential bridge asset lock-up.
- **Likelihood:** Medium — any legitimate governance adjustment to KIP71 parameters (a normal, expected operation) silently triggers the bug for all connected service chains.

### Likelihood Explanation

KIP71 parameters are explicitly mutable governance parameters. On Mainnet and Kairos, the governing node can ratify changes unilaterally in `single` mode. The bug activates on the very next `parentChainInfoRequest` after any such ratification — no attacker action is required; a routine governance update suffices.

### Recommendation

Replace the static `chainCfg.Governance.KIP71` read with a live governance module query:

```go
// In handleServiceChainParentChainInfoRequestMsg:
// Before (stale genesis config):
chainCfg := mbh.mainbridge.blockchain.Config()
pcInfo := parentChainInfo{
    nonce,
    mbh.mainbridge.txPool.GasPrice().Uint64(),
    params.KIP71Config{
        LowerBoundBaseFee:         chainCfg.Governance.KIP71.LowerBoundBaseFee,
        UpperBoundBaseFee:         chainCfg.Governance.KIP71.UpperBoundBaseFee,
        GasTarget:                 chainCfg.Governance.KIP71.GasTarget,
        MaxBlockGasUsedForBaseFee: chainCfg.Governance.KIP71.MaxBlockGasUsedForBaseFee,
        BaseFeeDenominator:        chainCfg.Governance.KIP71.BaseFeeDenominator,
    },
    ...
}

// After (live governance parameters):
currentBlock := mbh.mainbridge.blockchain.CurrentBlock().NumberU64()
pset := mbh.mainbridge.govModule.GetParamSet(currentBlock)
kip71 := pset.ToKip71Config()
pcInfo := parentChainInfo{
    nonce,
    mbh.mainbridge.txPool.GasPrice().Uint64(),
    *kip71,
    ...
}
```

### Proof of Concept

1. Deploy a Kaia mainnet node with a connected service chain (main bridge + sub bridge).
2. Record the genesis `UpperBoundBaseFee` (default: 750 Gwei).
3. Submit a governance vote to lower `kip71.upperboundbasefee` to 400 Gwei and wait for ratification (one epoch).
4. Observe that `govModule.GetParamSet(N).UpperBoundBaseFee` returns 400 Gwei for blocks after the epoch boundary.
5. Trigger a `parentChainInfoRequest` from the service chain (happens automatically on reconnect or every `SyncRequestInterval` blocks).
6. Capture the `parentChainInfo` response: `KIP71Config.UpperBoundBaseFee` will still be 750 Gwei (genesis value).
7. Observe `remoteGasPrice` on the service chain set to 750 Gwei — 350 Gwei above the current parent chain cap — causing every bridge operator transaction to overpay fees by `350e9 * gasUsed` KAIA. [1](#0-0) [4](#0-3)
