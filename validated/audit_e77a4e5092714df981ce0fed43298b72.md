### Title
Rounding bias in headers-commission distribution to attacker-chosen `earned_headers_commission_recipients` allows minting extra bytes (supply inflation) - ([File: headers_commission.js])

### Summary
When a unit wins the headers-commission "lottery" for a parent unit, the fixed `headers_commission` fee amount owed by the payer is split among the addresses listed in the winning child unit's `earned_headers_commission_recipients` array. Each recipient's share is computed independently with `Math.round(full_amount * share / 100.0)` (or the SQL equivalent `ROUND(...)`). Because rounding is applied per-recipient and JavaScript's/MySQL's `round()` rounds ties up, the sum of the rounded per-recipient amounts can exceed the original `full_amount` that was actually deducted from the payer as a fee. An unprivileged unit poster fully controls both the number of recipients and their percentage shares (only constrained to sum to exactly 100), so this rounding bias can be deliberately engineered to mint extra bytes that were never paid by anyone — a direct analogue of the Lido "leaked remainder" bug, except inverted: instead of value being lost, value is created out of thin air.

### Finding Description
`validateHeadersCommissionRecipients` in [1](#0-0)  only checks that the recipient list is non-empty, sorted by address, has positive-integer shares, and that the shares sum to exactly 100. It does not limit the number of recipients, nor does it account for the fact that rounding is later performed independently per recipient.

The actual distribution happens in `calcHeadersCommissions` in `headers_commission.js`. Both the in-RAM code path and the SQL/DB code path compute each recipient's payout with an independent rounding of `full_amount * share / 100.0`: [2](#0-1) [3](#0-2) 
and the MySQL variant does the same with `ROUND(...)`: [4](#0-3) 

`full_amount` here is the fixed `headers_commission` fee that was already deducted from the payer's inputs (enforced by the balance check in `validatePaymentInputsAndOutputs`, [5](#0-4) ). Because each recipient's share is rounded independently rather than the total amount being conserved (e.g., via a running remainder/last-recipient-gets-remainder scheme), the *sum* of rounded per-recipient outputs inserted into `headers_commission_contributions`/`headers_commission_outputs` can be strictly greater than `full_amount`. Since the payer only ever paid `full_amount`, any recipient total above that is minted from nothing.

An attacker who authors (or co-authors) the unit that wins the headers-commission lottery (`getWinnerInfo`, [6](#0-5) ) can set `earned_headers_commission_recipients` to a list of many addresses they control with shares chosen so that `full_amount * share_i / 100` lands near `x.5` for as many recipients as possible, maximizing the aggregate rounding-up bias. Because the validation only requires the *shares* to sum to 100 (not the resulting rounded amounts), there is no floor/ceiling reconciliation and no cap on the number of recipients.

### Impact Explanation
This is a **supply inflation** bug: attacker-controlled addresses receive `headers_commission_outputs` credits summing to more bytes than were ever deducted from any payer. These credits become normal, spendable base-asset outputs once the corresponding units stabilize, permanently increasing the circulating byte supply beyond the protocol's intended fixed emission (`TOTAL_WHITEBYTES`, enforced only at genesis, see [7](#0-6) ). This is deterministic and identical across all full nodes (both the RAM and DB paths are cross-checked and must agree, [8](#0-7) ), so it does not cause a fork/consensus disagreement, but it does directly inflate the total spendable bytes in existence, which the report class explicitly treats as in-scope impact.

### Likelihood Explanation
Likelihood is **Medium-to-High** for repeated, low-magnitude gains and lower for large single-shot gains: winning the headers-commission lottery for a specific parent requires being (or controlling) the "best child" per the SHA1-based tie-break in `getWinnerInfo`, which an attacker cannot fully control, but which they can influence by posting many candidate children units and/or simply being the only serial descendant of a parent unit they control. Once a unit wins, the attacker has complete control over the recipient list and shares in that same unit, since `earned_headers_commission_recipients` is a field of the *winning child* unit, not of the payer. This makes the rounding-inflation trick reproducible on demand whenever the attacker manages to win a payout, and it can be repeated indefinitely over time, similar in spirit to the "leaked remainder accumulates" pattern described in the source report.

### Recommendation
Change the distribution logic so that recipient amounts are conserved exactly rather than rounded independently:
- Round the first `n-1` recipients normally, then assign the **last** recipient `full_amount - sum(previous rounded amounts)` so the total always equals exactly `full_amount` (same remedy the report's "alternative considerations" section recommends: compute all splits then let one recipient absorb the remainder).
- Alternatively, always round down (`Math.floor`) each recipient's share and send any leftover remainder to a deterministic fallback address (e.g., the payer or the first author), matching the resolution pattern used by Lido's PR #236 (residual sent to a fixed collector rather than freely distributed).
- Add a runtime invariant check in `calcHeadersCommissions` that asserts `sum(rounded amounts for a given full_amount) === full_amount`, throwing/rejecting if violated, to catch any future regression before contributions are written to `headers_commission_contributions`.
- Apply the identical fix to the MySQL `ROUND(...)`-based query at [4](#0-3)  to keep the two backends consistent.

### Proof of Concept
1. Attacker creates a multi-authored unit (or any unit type that supports `earned_headers_commission_recipients`) that becomes the winning child for some parent unit `P` with `headers_commission = 150`.
2. Attacker sets:
   ```
   earned_headers_commission_recipients: [
     { address: A1, earned_headers_commission_share: 1 },
     { address: A2, earned_headers_commission_share: 1 },
     ... // 100 distinct attacker-controlled addresses
     { address: A100, earned_headers_commission_share: 1 }
   ]
   ```
   (sum of shares = 100, satisfying `validateHeadersCommissionRecipients`).
3. For each recipient, `full_amount * share / 100 = 150 * 1 / 100 = 1.5`, and `Math.round(1.5) = 2` for every recipient (JS/MySQL `ROUND` both round `.5` up for positive numbers).
4. `calcHeadersCommissions` inserts `100 recipients * 2 bytes = 200` bytes total into `headers_commission_contributions`/`headers_commission_outputs`, even though the payer of unit `P` only paid `150` bytes as `headers_commission`.
5. Once these outputs stabilize, the attacker's 100 addresses can spend a combined 200 bytes that were never deducted from anyone — a net creation of 50 bytes (33% inflation of that single commission event), repeatable every time the attacker wins a headers-commission payout.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

function getWinnerInfo(arrChildren){
	if (arrChildren.length === 1)
		return arrChildren[0];
	if (arrChildren.length === 0)
		throw Error("no children for hc");
	arrChildren.forEach(function(child){
		child.hash = crypto.createHash("sha1").update(child.child_unit + child.next_mc_unit, "utf8").digest("hex");
	});
	arrChildren.sort(function(a, b){ return ((a.hash < b.hash) ? -1 : 1); });

}
