### Title
Webhook signature verification authenticates the GitHub organization named in `repository.owner.login`, but handlers act on the unrelated repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to check the HMAC against using `repository_owner`, a value read straight out of the attacker-supplied JSON body. The handlers that actually mutate state (create commit statuses, sync commits, archive/merge review stacks, etc.) instead resolve their target `Repository`/`Stack` from a different field of the same body, `repository.full_name`. Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured — a supported configuration explicitly shown in `docs/setup.md` and `config/secrets.development.shopify.yml` (`webhook_secret: # nil`) — an unauthenticated attacker can pick *which organization's check to satisfy* (the unsecured one) while pointing the payload at a completely different, secured victim repository that the handlers will act on.

### Finding Description
`verify_signature` derives the authenticating organization from the payload itself: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` bypasses HMAC comparison entirely when the resolved organization has no configured secret: [3](#0-2) 

In multi-organization mode, `Shipit.github(organization:)` picks the config keyed by that same attacker-controlled `organization`/`repository_owner` value: [4](#0-3) 

Meanwhile, every handler resolves the actual `Repository`/`Stack` it operates on from a *different* field, `repository.full_name`, with no cross-check against `repository_owner`: [5](#0-4) [6](#0-5) [7](#0-6) 

So the binding the design relies on — "the organization whose secret authenticated this request" == "the repository the handler is about to write to" — is never enforced. Both `repository.owner.login` (used for auth-organization selection) and `repository.full_name` (used to select the target `Stack`) are plain, unsigned-by-anything-but-the-same-secret fields inside the request body the attacker fully controls. If the Shipit instance hosts at least one GitHub organization configured with `webhook_secret: nil` (documented as valid in `docs/setup.md:181-209` and `config/secrets.development.shopify.yml:9,18`), an attacker who knows nothing about any real secret can:

1. Set `X-Github-Event: status` (or `push`, `pull_request`, etc.).
2. Set `repository.owner.login` to the name of the org with no secret — `verify_signature` selects that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/garbage) `X-Hub-Signature` header.
3. Set `repository.full_name` to `victim-org/victim-repo`, an entirely different, secured repository tracked by Shipit.
4. The `create` action re-parses the same body and dispatches it to handlers, which look up the victim stack purely via `repository.full_name` and act on it.

### Impact Explanation
Via the `status` event, `StatusHandler#process` calls `Commit#create_status_from_github!`, which can flip a victim commit's state to `success`, and `add_status` will trigger `stack.schedule_merges` and can drive continuous-deployment auto-deploys: [8](#0-7) 

This lets an attacker with no Shipit session, no `ApiClient` token, and no knowledge of the victim organization's `webhook_secret` forge CI status for arbitrary tracked commits in a completely different, unrelated organization, triggering an unauthorized deploy or merge on that victim's stack — satisfying the "unauthorized deploy, rollback or merge" Critical-impact category. The same cross-repository confusion applies to `push` (fake `GithubSyncJob` triggers) and `pull_request` handlers (`ReviewStackAdapter` archive/unarchive) that also resolve their target solely from `repository.full_name`.

### Likelihood Explanation
Requires only that the Shipit deployment configures at least one GitHub organization without a `webhook_secret` — an explicitly documented, supported setup, not a misconfiguration outside the engine's own contract. No credentials, session, or prior access are needed by the attacker; a single unauthenticated POST to `/github_hooks`/webhooks endpoint suffices.

### Recommendation
`verify_signature` (or the handlers) should require that the organization used to select the verifying `GitHubApp`/secret matches the owner implied by `repository.full_name` used later for stack resolution, and/or `GitHubApp#verify_webhook_signature` should not silently pass all requests through when `webhook_secret` is blank for one organization while other organizations in the same instance have secrets configured — cross-organization payload confusion should be rejected regardless of secret presence.

### Proof of Concept
1. Configure Shipit in multi-org mode with `orgA` having `webhook_secret: nil` and `orgB` (containing the real victim stack) having a real secret.
2. POST to the webhooks endpoint with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success"
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. The request passes `verify_signature`, and `StatusHandler` (resolved purely from `repository.full_name`) creates a `success` status on the victim commit, potentially triggering `stack.schedule_merges`/continuous deployment for `orgB/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
