### Title
Gist filenames printed via `opts.IO.Out` are not ANSI-sanitized, allowing terminal escape-sequence injection - ([File: pkg/cmd/gist/view/view.go])

### Summary
`viewRun` treats gist file *content* as untrusted by wrapping it in `iostreams.NewUntrusted` before printing, but gist *filenames* (also attacker-controlled, sourced from the same untrusted JSON API response) are printed as raw Go strings via `fmt.Fprintln(opts.IO.Out, fn)` and `fmt.Fprintf(opts.IO.Out, "%s\n\n", cs.Muted(fn))`. Since `opts.IO.Out` performs no sanitization (only `opts.IO.ContentOut` / the `Untrusted.String()` path does), a filename containing raw ANSI/OSC escape bytes reaches the victim's terminal unmodified.

### Finding Description
In `pkg/cmd/gist/view/view.go`, the `render` closure explicitly wraps file content with `iostreams.NewUntrusted(gf.Content)` [1](#0-0)  so that when it is eventually printed, `Untrusted.String()`'s automatic sanitization via `asciisanitizer.Sanitizer` neutralizes escape sequences [2](#0-1) .

By contrast, filenames are collected directly as map keys from `gist.Files` (plain `string`, populated straight from the JSON API response) and printed with no such wrapping:
- List mode: `fmt.Fprintln(opts.IO.Out, fn)` [3](#0-2) 
- Multi-file header: `fmt.Fprintf(opts.IO.Out, "%s\n\n", cs.Muted(fn))` [4](#0-3) 

`opts.IO.Out` is a raw `fileWriter` (a colorable-wrapped stdout) with no built-in sanitization; only `ContentOut` is documented and used as the sanitizing path for "external content (HTTP response bodies, gist files, etc.)" per its doc comment [5](#0-4) . Filenames never pass through `ContentOut` or `Untrusted`, so `cs.Muted(fn)` (a color-scheme helper) simply wraps the raw attacker string with SGR codes and prints it verbatim — any embedded ESC (0x1B) sequences or OSC-8 hyperlink payloads in the filename are emitted directly to the terminal.

This is a genuine inconsistency: the code comments and design intent (`Untrusted` type, `ContentOut`) explicitly acknowledge that gist content must be treated as untrusted and sanitized before reaching a terminal, but the same treatment was not applied to filenames, which are equally attacker-controlled (a GitHub gist owner fully controls their filenames).

### Impact Explanation
This enables terminal escape/OSC injection against a victim who runs `gh gist view <id>` or `gh gist view <id> --files` on an attacker-published gist. Depending on terminal emulator, this can be used for: hiding/spoofing output (e.g., faking success messages), OSC-8 hyperlink spoofing (rendering deceptive clickable text), title-bar manipulation, or in more advanced terminal-emulator bugs, more serious effects. This matches the "terminal escape sequence / output injection" impact class recognized in prior GitHub CLI security work (the same class the `Untrusted` content-sanitization mechanism was built to prevent).

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any GitHub user can create a public gist with a filename containing raw control bytes (subject to GitHub's own filename validation, which is unknown/unverified here — GitHub's gist API may reject or sanitize certain filename characters, which would reduce/eliminate practical exploitability). This is the main uncertainty: it is not verified from this codebase alone whether GitHub's gist filename validation permits ESC (0x1B) bytes in filenames returned by the API. Assuming such filenames can exist (e.g., via API-created gists bypassing UI validation, which is plausible but not confirmed here), any victim running `gh gist view` against that gist ID is affected with no other precondition.

### Recommendation
Wrap filenames in `iostreams.NewUntrusted` (or route through `opts.IO.ContentOut`) before printing, mirroring the treatment already given to `gf.Content`:
```go
fmt.Fprintln(opts.IO.Out, iostreams.NewUntrusted(fn))
...
fmt.Fprintf(opts.IO.Out, "%s\n\n", cs.Muted(iostreams.NewUntrusted(fn).String()))
```
so `fmt`'s `%s`/`Fprintln` path invokes `Untrusted.String()` sanitization uniformly for all attacker-influenced strings, not just file content.

### Proof of Concept
```go
func TestViewRun_FilenameEscapeSequenceInjection(t *testing.T) {
    reg := &httpmock.Registry{}
    defer reg.Verify(t)
    reg.Register(
        httpmock.REST("GET", "gists/1234"),
        httpmock.JSONResponse(map[string]interface{}{
            "id": "1234",
            "files": map[string]interface{}{
                "\x1b[31mevil\x1b[0m.txt": map[string]interface{}{
                    "filename": "\x1b[31mevil\x1b[0m.txt",
                    "content":  "hello",
                    "type":     "text/plain",
                },
                "b.txt": map[string]interface{}{
                    "filename": "b.txt",
                    "content":  "world",
                    "type":     "text/plain",
                },
            },
        }),
    )

    ios, _, stdout, _ := iostreams.Test()
    ios.SetStdoutTTY(true)
    opts := &ViewOptions{
        IO:         ios,
        Config:     testConfigFunc(),
        HttpClient: func() (*http.Client, error) { return &http.Client{Transport: reg}, nil },
        Selector:   "1234",
        ListFiles:  true,
    }

    err := viewRun(opts)
    require.NoError(t, err)
    require.NotContains(t, stdout.Bytes(), []byte{0x1b}, "raw ESC byte leaked into terminal output via filename")
}
```
Expected (current) result: the assertion fails — `stdout` contains raw `0x1B` bytes from the crafted filename, confirming the filename path bypasses sanitization while the equivalent content-based test (using `gf.Content`) passes due to `Untrusted` wrapping.

	}
	return sanitized
}
