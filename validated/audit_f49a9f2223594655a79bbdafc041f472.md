### Title
Scoped ApiClient token can read any stack's CI status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution method inherited from `Shipit::Api::BaseController` in a way that removes the enforcement of an `ApiClient`'s `stack_id` scope, letting a token that is only supposed to authorize reads for one stack be replayed with an arbitrary `stack_id` parameter to read build/deploy status for any stack.

### Finding Description
`Shipit::Api::BaseController` defines the authorization boundary that scopes a token to the stack it was created for: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client has one, and `stack` resolves `params[:stack_id]`/`params[:id]` only within that restricted relation. Every other API controller inherits this and is correctly scoped, e.g. `Shipit::Api::StacksController#stack` calls `stacks.from_param!(params[:id])`: [2](#0-1) 

However, `Shipit::Api::CCMenuController` redefines `stack` to bypass the `stacks` scoping relation entirely and resolve directly against the whole `Stack` table: [3](#0-2) 

The only check performed before rendering is a scope-name permission check (`read:stack`) via `require_permission`, not an identity check tying the token to a specific `Stack` record: [4](#0-3) [5](#0-4) 

The invariant that should hold is: `current_api_client.stack_id == accessed_stack.id` whenever `current_api_client.stack_id?` is true (exactly as `BaseController#stacks`/`#stack` enforce for every other endpoint). `CCMenuController#stack` breaks that equality by never consulting `current_api_client.stack_id`, so the "stack a token authorizes" and "the stack it actually touches" diverge — precisely the class of binding violation described in the flash-loan analog (an index/parameter accepted from the caller is never checked against the value the credential was actually scoped to).

This is not a theoretical gap: the normal, documented way to obtain a CCMenu token is `Shipit::CCMenuUrlController#fetch`, which creates (or reuses) a `read:stack`-scoped `ApiClient` tied to one specific stack via `find_or_create_by!` and embeds its `authentication_token` in a URL: [6](#0-5) 

Any holder of a legitimately-issued CCMenu URL/token for stack A can simply change the `stack_id` query parameter to stack B's identifier and read stack B's CI/deploy state, even though the `ApiClient` record backing that token has `stack_id` pinned to stack A and only `read:stack` permission (no cross-stack grant).

### Impact Explanation
This lets a credential explicitly scoped to a single stack read `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, `activity`, and lock state for any stack registered in the Shipit instance, including private/internal stacks the token holder was never granted visibility into. This matches the "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" class of High-severity impact called out in the rules: a token that is supposed to be confined to one stack's read scope is used to read arbitrary stacks' state without ever proving authorization for them.

### Likelihood Explanation
Exploitation requires only a single valid, narrowly-scoped CCMenu token (obtainable by any authenticated Shipit user for any stack they can view via `CCMenuUrlController#fetch`) and knowledge or guessing of another stack's `to_param` (which is typically `owner/repo/branch`-derived and often predictable/enumerable). No signature forgery, GitHub credentials, or elevated privileges are required — only a request with a modified `stack_id` query parameter against `Api::CCMenuController#show`. This makes the likelihood high relative to the flash-loan analog, since the "index" here (`stack_id`) is a plain, attacker-controlled URL parameter.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (and the analogous override risk in any future controller) and use the inherited `BaseController#stack`/`#stacks`, which enforces `current_api_client.stack_id` scoping:
```ruby
private

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
More generally, ensure any endpoint resolving a `Stack` (or other scoped resource) from a request parameter always routes through the scoped `stacks` relation rather than querying the model class directly, and add a regression test asserting that a stack-scoped `ApiClient` token cannot fetch CCMenu data for a different stack.

### Proof of Concept
1. As an authorized Shipit user, visit `CCMenuUrlController#fetch` for `stack_id=owner/repoA/main`. This creates/reuses an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and `stack_id` set to stack A's id, and returns a URL like:
   `GET /api/stacks/owner/repoA/main/ccmenu.xml?token=<TOKEN_A>`
   (see `Shipit::CCMenuUrlController#fetch` and `#client`) [7](#0-6) 
2. Identify (or guess) another stack's param, e.g. `owner/repoB/main`.
3. Send: `GET /api/stacks/owner/repoB/main/ccmenu.xml?token=<TOKEN_A>`.
4. `authenticate_api_client` authenticates `TOKEN_A` successfully (it's a valid token) [8](#0-7) ; `require_permission :read, :stack` passes because the client has `read:stack` in `permissions` [5](#0-4) ; and `stack` resolves stack B directly from `Stack.from_param!`, ignoring that `current_api_client.stack_id` points to stack A [9](#0-8) .
5. The response renders stack B's CCMenu XML (name, lastBuildStatus, lastBuildLabel, webUrl, etc.), which `TOKEN_A` was never authorized to view.

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
```
