### Title
Burnchain `PreStxOp`/`StackStxOp` sender identity is bound to an unauthenticated Bitcoin output, allowing an attacker to lock a victim's STX without any Stacks-side signature - (`File: stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` derives the future stacking `sender` purely from the Bitcoin address of output[0], which any Bitcoin transaction author can set to an arbitrary victim `StacksAddress` without proving control of it. `StackStxOp::get_sender_txid`/`parse_from_tx` then bind `stacked_ustx`, `num_cycles`, and `signer_key` from a *different*, attacker-controlled spend of vout=1, and `StackStxOp::check()` never validates that the resulting `sender` authorized anything.

### Finding Description
The claimed equality is: *STX locked by an applied burnchain stacking op == STX owned by the Stacks address whose private key actually authorized the lock (via the Bitcoin key that funds/broadcasts the op)*.

Tracing the code:
- `PreStxOp::parse_from_tx` takes `outputs.get(0)....address...try_into_stacks_address()` as `output` with no signature or key-ownership check on that recipient — sending BTC to any address requires no consent from the recipient. [1](#0-0) 
- `StackStxOp::get_sender_txid` only validates that the spending input references `vout == 1` of some prior transaction; it performs no check that the spender is related to the address recorded as `output` in that prior `PreStxOp`. [2](#0-1) 
- `StackStxOp::parse_from_tx` then simply clones the externally-supplied `sender` (looked up via the PreStxOp pairing in `burnchain.rs`) into the resulting op, together with attacker-chosen `stacked_ustx`, `num_cycles`, and `signer_key` parsed from the second transaction's `OP_RETURN` payload. [3](#0-2) 
- `StackStxOp::check()` validates only that `stacked_ustx > 0`, `num_cycles` is in range, and that `signer_key` (if present) is a well-formed secp256k1 key. It never checks that `sender` corresponds to the Bitcoin key that produced the StackStx-opcode transaction, nor any Stacks-side signature from `sender`. [4](#0-3) 

Root cause: the identity used to lock STX (`sender`) is bound to whichever Bitcoin address the PreStxOp's broadcaster chose for output[0] — which requires zero proof of key possession — while the operational parameters (amount, cycles, signer key) are supplied by whoever later spends vout=1, which can be an entirely unrelated party. There is no cryptographic link tying `sender`'s private key to authorization of the lock.

Exploit: the attacker (1) broadcasts a PreStx Bitcoin transaction with output[0] = victim's StacksAddress-mapped Bitcoin address and output[1] = an address the attacker controls; (2) spends output[1] in a StackStx-opcode transaction they sign themselves, embedding `stacked_ustx`, `num_cycles`, and a `signer_key` of their choosing. The node pairs these via the burnchain indexer, producing a `StackStxOp{ sender: victim, stacked_ustx, num_cycles, signer_key: attacker_key, ... }` which is fed into `run_contract_call(&sender.into(), ..., "stack-stx", ...)`, locking the victim's real STX balance under a signer key the victim never approved.

Existing guards fail: `check()` does not check sender authorization; `get_sender_txid` only enforces the vout index, not key continuity; nothing in the burnchain-op path requires a Stacks-level signature from `sender`. Whether the downstream pox-5 `stack-stx` Clarity function additionally verifies a `signer-sig` could not be fully confirmed in this session, but any such check only authorizes the *reward address/signer-key* pairing — it is signed by the attacker's own signer key over the attacker's chosen parameters and does not, and cannot, constitute consent from the victim `sender` whose balance is what actually gets locked.

### Impact Explanation
The victim's unlocked STX (up to their full spendable balance) is locked into PoX for `num_cycles` reward cycles without any signature or on-chain action from the victim, using a `reward_addr`/`signer_key` entirely of the attacker's choosing — enabling both permanent (until unlock height) freezing of the victim's funds and diversion of the associated PoX reward-slot/signing weight to the attacker. This matches the Critical category: permanent freezing of staked STX and an unsigned stacking action redirecting reward flow.

### Likelihood Explanation
Preconditions are attacker-cheap: only enough BTC to fund two low-value Bitcoin transactions with correctly formatted `OP_RETURN` payloads recognized by the Stacks burnchain indexer (`Opcodes::PreStx`, `Opcodes::StackStx`), and knowledge of the victim's public Stacks address (always public). No victim Bitcoin or Stacks signature is required, and the attack is repeatable against any address holding unlocked, unpaused STX at reward-cycle start, for as many reward cycles as the attacker cares to grief.

### Recommendation
Require cryptographic proof that the entity broadcasting the `StackStx`-opcode transaction (or the `PreStx` transaction) actually controls the private key corresponding to the `sender` StacksAddress before treating it as the stacking sender — e.g., require a Stacks-side signature from `sender` authorizing the specific `stacked_ustx`/`num_cycles`/`reward_addr` tuple, or deprecate/disable the legacy burn-op stacking path entirely in favor of the pox-5 Clarity `stack-stx` call, which is authenticated by the Stacks transaction's own `tx-sender`.

### Proof of Concept
Rust integration test (mirroring `stackslib/src/chainstate/burn/operations/stack_stx.rs` unit-test style plus `stackslib/src/chainstate/coordinator/tests.rs` harness):
1. Boot a regtest chainstate with a funded victim `StacksAddress` V holding `N` unlocked uSTX.
2. Construct and mine a `PreStxOp` Bitcoin transaction with `output[0].address = V` (attacker does not own V's key) and `output[1].address = attacker_addr` (attacker's own key).
3. Construct and mine a `StackStxOp` Bitcoin transaction whose sole input spends `vout=1` of the PreStx tx, signed only by the attacker's Bitcoin key, with `OP_RETURN` payload encoding `stacked_ustx = N`, `num_cycles = 1`, `signer_key = attacker_pubkey`.
4. Run the sortition/coordinator processing so `process_stacking_ops` executes `run_contract_call(&V.into(), None, ..., "stack-stx", ...)`.
5. Assert: `stx-account(V).locked == N` (victim's balance became locked) while asserting no Stacks transaction was ever signed by V's private key and no Bitcoin transaction input was ever signed by V — i.e., the locked-STX identity (`V`) and the identity that authorized/signed the operation (attacker) differ, proving the claimed equality is broken.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }

    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
