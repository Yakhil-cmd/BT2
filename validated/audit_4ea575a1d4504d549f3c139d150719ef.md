### Title
Webhook signature verification is bound to an attacker-chosen `repository.owner.login`, not the repository the handlers actually write to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) is used to validate an incoming webhook based on a field read out of the *unverified* JSON body (`repository.owner.login`, or `organization.login`). The rest of the pipeline (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then acts on the full, attacker-controlled `params`, including repository-identifying fields such as `repository.full_name`, which are never checked against the organization that was actually used to authenticate the request.

### Finding Description
`verify_signature` does: [1](#0-0) 
It picks the `github_app` purely from `repository_owner`: [2](#0-1) 
which is read straight out of the untrusted request body before any signature check occurs.

The signature check itself is delegated to `GithubApp#verify_webhook_signature`, which unconditionally returns `true` when that specific organization's `webhook_secret` is not configured: [3](#0-2) 

Meanwhile, the handlers that consume `params` (`create` action forwards the entire raw JSON, unfiltered, to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) resolve the actual repository/stack to mutate using other fields of the same payload (e.g. `repository.full_name`), independent of `repository.owner.login`. This is demonstrated by the existing test which mutates `full_name` alone while leaving the rest of the payload (including `owner.login`) untouched, confirming the two fields are read and used independently by downstream handlers: [4](#0-3) 

The security-relevant equality that must hold is:
`organization_used_to_select_verification_config (params.repository.owner.login)` == `organization_owning_the_repository_the_handlers_actually_write_to (params.repository.full_name's owner)`

Nothing in `verify_signature` or in `create` enforces this equality. The controller only ever validates the payload against the `webhook_secret` belonging to whatever organization is named in `repository.owner.login`/`organization.login` — a value fully controlled by whoever is sending the HTTP POST, since this endpoint is unauthenticated (`ActionController::Base`, no `Authentication` concern, no `ApiClient` requirement) and only gated by the signature check itself.

### Impact Explanation
For any organization present in `Shipit.github` multi-tenant configuration that does not have a `webhook_secret` set (an explicitly supported, documented configuration state, e.g. `webhook_secret: # nil` in `config/secrets.development.shopify.yml`), `verify_webhook_signature` short-circuits to `true` for *any* payload, regardless of its actual originator. Because the org used for that check (`repository.owner.login`) is decoupled from the repository fields the handlers act on (`repository.full_name`), an attacker who only needs to name an unconfigured/secret-less organization in `repository.owner.login` can supply arbitrary `repository.full_name`, `ref`, `after`, `sha`, `state`, etc. targeting a *different*, fully-configured, privileged organization/repository. This lets an unauthenticated caller:
- Forge `push` events (`GithubSyncJob`) to make Shipit sync arbitrary commits into a tracked stack for a repository it does not own.
- Forge `status`/`check_suite` events that flip commit statuses/check-runs used to gate whether a commit is deployable.
- Forge `pull_request` events that auto-create/provision review stacks for arbitrary repositories.
- Forge `membership` events to add/remove arbitrary GitHub logins from `Shipit.github_teams`-backed `Team`s, directly affecting `User#authorized?` and thus who can log in and operate Shipit.

This crosses the authorization boundary described in the rules ("escalation into `Shipit.github_teams` authorization") and can enable unauthorized deploy-gating changes and stack creation without any credential.

### Likelihood Explanation
Requires only: (a) the target Shipit deployment to configure more than one GitHub organization/app (a documented, supported multi-tenant pattern), and (b) at least one of those organizations to have no `webhook_secret` configured — a state the engine itself permits and silently treats as "always valid." No secrets, tokens, or privileged access are needed by the attacker; a single unauthenticated HTTP POST to the public webhooks endpoint is sufficient.

### Recommendation
- Require every configured GitHub organization to have a non-blank `webhook_secret`; refuse to boot, or reject all webhooks for, organizations without one, instead of treating a blank secret as "verified."
- After signature verification, assert that the organization/app whose secret validated the request equals the owner of the repository the payload/handlers will actually act upon (e.g. compare `repository_owner` used for verification against the owner embedded in `repository.full_name` before dispatching to handlers).

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `victim-org` (properly configured with a `webhook_secret`) and `open-org` (present in `Shipit.github` config but with `webhook_secret` left blank — as shown possible in `config/secrets.development.shopify.yml`).
2. POST to the mounted webhooks route (`config/routes.rb`) with:
   - Header `X-Github-Event: push`
   - Body:
     ```json
     {
       "repository": { "owner": { "login": "open-org" }, "full_name": "victim-org/private-repo" },
       "ref": "refs/heads/main",
       "after": "<attacker chosen sha>"
     }
     ```
   - No valid `X-Hub-Signature` needed.
3. `verify_signature` resolves `Shipit.github(organization: 'open-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately (`lib/shipit/github_app.rb:76-77`).
4. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs with the full payload; the push handler resolves and syncs `victim-org/private-repo` using Shipit's own GitHub credentials, even though the request was never actually signed by `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
