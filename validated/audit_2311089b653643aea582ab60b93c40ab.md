### Title
Cross-Repository Commit Status Forgery via Organization-Scoped Webhook Signature Bypass - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the signing secret to check against based on `repository_owner`, a value taken verbatim from the *inbound, attacker-supplied* JSON payload [1](#0-0) , and `GitHubApp#verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically verified (`return true unless webhook_secret`) [2](#0-1) . Because `webhook_secret` is documented as optional per organization [3](#0-2) , and Shipit supports multi-organization configuration where each org is a separate top-level key [4](#0-3) , an attacker who controls (or self-registers) *any* organization in the Shipit instance that has no `webhook_secret` set can send a webhook whose "verified organization" is their own throwaway org, while the payload body actually targets data belonging to a completely different, unrelated repository/stack.

### Finding Description
The equality the code is supposed to enforce is:
`organization whose signature was verified == repository/stack whose state is mutated by the payload`

This equality is broken in `Shipit::Webhooks::Handlers::StatusHandler`, which processes GitHub `status` events. It resolves the target purely by commit SHA, globally, with **no repository or organization scoping at all**:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Unlike other handlers that at least scope by `repository.full_name` via the base `Handler#repository_name`/`#stacks` helpers [6](#0-5) , `StatusHandler` never calls `stacks` — it queries `Commit` directly by `sha` across the entire database. Since the `verify_signature` before_action only checks the signature against whichever organization's secret corresponds to `repository.owner.login` in the *same forged payload* [7](#0-6) , an attacker can:

1. Register/control an organization in Shipit's `github` config that has no `webhook_secret` (a supported, documented configuration) [8](#0-7) .
2. Send a POST to `/github/webhooks` with `X-Github-Event: status`, `repository.owner.login` set to their own org (so `verify_webhook_signature` short-circuits to `true` without ever checking an HMAC) [2](#0-1) .
3. Set `sha` in the payload to the SHA of a commit that belongs to a *victim's* tracked stack/repository (commit SHAs of public repos are public information, and Shipit stores all commits, across all stacks, in one global `commits` table keyed only by `sha`).
4. `StatusHandler#process` finds that commit purely by SHA match and writes an attacker-controlled `state`, `description`, `target_url`, and `context` onto it via `commit.create_status_from_github!(params)` — with zero verification that this commit belongs to the organization whose signature was actually checked.

### Impact Explanation
Commit CI status directly feeds into deploy-safety logic: `deployable?`, `UndeployedCommit#deploy_state`, and `Stack#deployment_checks_passed?`/`ci_enabled?` all key off `Status`/`CheckRun` records associated with a commit [9](#0-8) [10](#0-9) . By forging a `success` status for a victim commit that in reality failed CI (or was never reviewed), an attacker with no privileges on the victim repository/stack can make an unreviewed or malicious commit appear "allowed"/deployable, potentially enabling that commit to be picked up by continuous deployment (`Stack.schedule_continuous_delivery`) or manually deployed by an operator who trusts the (forged) green status — resulting in an unauthorized deploy of unvetted code. This matches the Critical impact category "unauthorized deploy" defined in scope, since it stems from a genuine trust-boundary confusion: the organization whose credentials were checked is not the repository whose durable state (commit status) is written.

### Likelihood Explanation
No privileged credentials are required — only the ability to reach `POST /github/webhooks` (public endpoint) and knowledge of a target commit SHA (which is public GitHub data for any repo the attacker can view). The only precondition is that the Shipit deployment has at least one configured GitHub organization with no `webhook_secret`, which the setup docs explicitly present as valid/optional configuration, and which an attacker fully controls if they can get any organization/app of theirs onboarded (e.g., a shared/self-hosted Shipit instance serving multiple orgs, which the multi-org config format explicitly supports) [11](#0-10) .

### Recommendation
- In `StatusHandler` (and any other handler that doesn't scope through `stacks`/`repository_name`), require that the commit being updated belongs to a repository whose owner matches the organization that was actually authenticated in `verify_signature`, e.g. scope `Commit.where(sha: params.sha)` through `stacks`/`Repository.from_github_repo_name(repository_name)` as other handlers do [6](#0-5) .
- Do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank for multi-tenant/multi-organization configurations; either require a secret for every configured organization or otherwise refuse to trust unsigned payloads' embedded repository claims.
- Pass the authenticated organization from `verify_signature` into the handler dispatch so handlers can assert consistency between the verified org and the repository/commit they mutate.

### Proof of Concept
1. Configure Shipit with two organizations: `attacker-org` (no `webhook_secret`) and `victim-org` (with `webhook_secret`), as the multi-org schema supports [11](#0-10) .
2. Attacker sends:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # ignored, since attacker-org has no secret

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged"
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which returns `true` unconditionally since `attacker-org` has no `webhook_secret` [12](#0-11) .
4. `StatusHandler#process` finds the victim's commit by SHA (regardless of organization) and creates a forged `success` status on it [5](#0-4) , potentially satisfying `victim-org`'s deploy gating checks.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
