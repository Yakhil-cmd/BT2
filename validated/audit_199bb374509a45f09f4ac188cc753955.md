### Title

Chunked liquidations can round the protocol fee to zero - (File: contracts/controller/src/positions/liquidation/math.rs)

### Summary

`liquidate` computes a liquidation protocol fee for each collateral seizure leg, but `SeizeMode::Transfer` truncates that fee to token units and caps it by the realized excess. For very small seizure legs, the realized excess can round to zero, so the protocol receives no fee even though the liquidator receives collateral containing a fractional bonus. A liquidator can repeat sufficiently small liquidation legs instead of submitting one larger liquidation, accumulating the liquidation bonus while avoiding the configured protocol fee.

### Finding Description

The liquidation planner derives `base_ray`, `bonus_ray`, and `protocol_fee_ray` separately for each collateral asset in `calculate_seized_collateral`. The configured `liquidation_fees` rate is applied only to that leg’s fractional `bonus_ray` in `common::math::fp::Bps::apply_to_ray` [1](#0-0) [2](#0-1) .

For transfer-mode seizures, the protocol fee is converted to token units with `to_asset_floor`, raised to one unit only when the raw fee is positive but the conversion truncates to zero, and then capped by `realised_excess` [3](#0-2) . `realised_excess` is itself computed by subtracting the floored repayment principal from the whole-unit amount paid by the pool and truncating the result to token units [4](#0-3) .

Consequently, a leg whose gross seizure rounds down far enough to leave less than one token unit above its principal records `protocol_fee = 0`. This is not merely theoretical: the repository’s own liquidation-math test documents a seizure of `12.971` token units being truncated to `12`, leaving a realized excess below one token unit and therefore a protocol fee of zero [5](#0-4) .

Unlike `SeizeMode::Credit`, where the fee share is rounded up with `mul_div_ceil` and therefore cannot round a positive fractional fee to zero shares, the transfer-mode path can zero out the fee at the token-unit boundary [6](#0-5) .

### Impact Explanation

This is theft or loss of unclaimed protocol yield. An unprivileged liquidator can split a liquidation into multiple small legs whose realized excess is less than one token unit, causing each protocol fee to round to zero while still receiving the corresponding fractional liquidation bonus inside the seized collateral. Repeating the strategy over eligible collateral can aggregate to a material unpaid fee, particularly for low-decimal or low-value collateral where one token unit is economically meaningful.

The issue does not let the liquidator seize more collateral than the liquidation plan assigns. Instead, it prevents the configured `liquidation_fees` share of the liquidation bonus from reaching pool revenue.

### Likelihood Explanation

Likelihood is moderate to high whenever a position supports multiple collateral seizure legs and a liquidator can choose repayment sizes that produce sub-unit realized excess. Low-decimal assets make the condition easier because a larger economic amount can remain below one whole token unit. The rounding boundary is deterministic and depends only on the liquidation size, price, bonus, collateral index, and configured liquidation fee.

The attack does not require privileged access, oracle manipulation, or control of the victim. It does require an eligible liquidation and the ability to execute repeated partial liquidation calls without another liquidator completing the liquidation first.

### Recommendation

Preserve the protocol’s share of the fractional bonus instead of truncating it independently per transfer leg.

Possible approaches:

- Round the realized excess or final fee upward when `protocol_fee_ray > 0`, while still enforcing `protocol_fee <= capped_amount`.
- Carry the uncollected fractional protocol fee forward across liquidation legs or across liquidation calls, so chunking does not repeatedly discard it.
- Enforce a minimum liquidation or seizure amount that guarantees any positive bonus produces at least one token unit of protocol fee.
- Use a credit/share-based fee split where practical, since `split_seized_shares` already uses ceiling division for positive fee shares.

The implementation should avoid charging a fee when there is truly no realized bonus, but it should not allow the per-leg token-unit truncation to erase a positive fee entitlement.

### Proof of Concept

Consider a collateral asset with two token decimals, a configured positive `liquidation_fees` rate, and a liquidation leg whose ideal seizure is `100.999` token units:

1. `seizure_ray` is derived from the repayment and liquidation bonus.
2. `base_ray = floor(seizure_ray / (1 + bonus))`, leaving approximately `0.999` token units as the raw bonus.
3. `protocol_fee_ray` is positive because `liquidation_fees > 0` and `bonus_ray > 0`.
4. The whole-unit seizure floor returns `100` token units.
5. `realised_excess = floor(100 - base)` can be zero when the fractional remainder above `base_ray` is below one token unit.
6. `protocol_fee = min(max(1, floor(protocol_fee_ray)), realised_excess) = 0`.
7. The liquidator receives the `100`-unit seizure and effectively retains the entire fractional bonus encoded in that seizure.
8. Repeating similarly sized liquidation legs accumulates the bonus while each leg reports zero protocol fee.

This is consistent with the existing unit-test scenario where a `12.971`-unit seizure floors to `12` and a `0.1`-unit realized excess produces `protocol_fee = 0` [5](#0-4) .

/// Splits credit-mode shares with `fee = ceil(fee_rate * bonus_scaled)`.
/// The liquidator gets the exact remainder. Enforces bounds and
/// `seized_scaled == fee + liquidator` to prevent unbacked share creation.
pub(crate) fn split_seized_shares(
    env: &Env,
    seized_scaled: Ray,
    bonus_scaled: Ray,
    liquidation_fees_bps: u32,
) -> (Ray, Ray) {
    let fees = i128::from(liquidation_fees_bps);
    if seized_scaled < Ray::ZERO
        || bonus_scaled < Ray::ZERO
        || bonus_scaled > seized_scaled
        || fees >= BPS
    {
        panic_with_error!(env, GenericError::InternalError);
    }

    let fee_scaled = Ray::from(mul_div_ceil(env, bonus_scaled.raw(), fees, BPS));
    // Recheck the computed fee against the seizure; rates come from position stamps.
    if fee_scaled > seized_scaled {
        panic_with_error!(env, GenericError::InternalError);
    }

    let liquidator_scaled = seized_scaled.checked_sub(env, fee_scaled);
    if fee_scaled.checked_add(env, liquidator_scaled) != seized_scaled {
        panic_with_error!(env, GenericError::InternalError);
    }
    (fee_scaled, liquidator_scaled)
