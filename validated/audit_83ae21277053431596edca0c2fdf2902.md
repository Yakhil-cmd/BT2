### Title
Webhook signature verification is bypassed when the org selected for verification (derived from the unverified payload) has no `webhook_secret` configured, allowing unauthenticated forgery of GitHub events (push/status/check_suite/membership) that drive commit deployability and CI state - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and therefore which `webhook_secret`) to use for HMAC verification by reading `repository.owner.login` / `organization.login` directly out of the still-unverified JSON body. Combined with `GithubApp#verify_webhook_signature` short-circuiting to `true` whenever `webhook_secret` is blank, any organization configured in a multi-org Shipit install without a `webhook_secret` becomes a complete signature-verification bypass for that organization's webhooks - with no credential required at all.

### Finding Description
The controller flow is: [1](#0-0) 

`repository_owner` is computed straight from the raw request body before any authenticity check: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GithubApp` instance configured per-organization, and `verify_webhook_signature` unconditionally trusts the payload if that organization has no `webhook_secret` set: [3](#0-2) 

The engine's own documentation explicitly supports multiple GitHub App configs, one per organization, each with an **optional** `webhook_secret`: [4](#0-3) [5](#0-4) 

This breaks the intended binding "the organization whose credential authenticated the webhook == the organization whose repository state is mutated by the payload": the *selector* used to pick the verification secret is taken from the same untrusted body that the event handlers then act on. If any configured organization omits `webhook_secret` (an explicitly supported, documented configuration), an unauthenticated attacker can submit a forged `X-Github-Event: status` (or `push`, `check_suite`, `membership`) request with `repository.owner.login` set to that unsecured organization, and `verify_signature` will pass with **no signature at all**, because `head(422) unless verified` is the only enforcement and `verified` is forced `true`.

Once past `verify_signature`, `Shipit::Webhooks.for_event(event)` dispatches the fully attacker-controlled JSON to handlers such as `Handlers::StatusHandler`, `Handlers::PushHandler`, `Handlers::CheckSuiteHandler`, and `Handlers::MembershipHandler`: [6](#0-5) [7](#0-6) 

### Impact Explanation
A forged `status` webhook can mark an arbitrary commit as CI-green for a stack belonging to the unsecured organization. Stacks configured with `continuous_deployment` (README/docs) automatically trigger a deploy once a commit becomes "deployable," so this forged CI status can result in an **unauthorized deploy** with no session, API token, or GitHub credential of any kind - it only requires that one organization in the Shipit install lacks a `webhook_secret`, which is an explicitly documented, supported configuration (not a misconfiguration outside the engine's control). A forged `membership` webhook can also create arbitrary `Team`/`User` records under that organization, and forged `push`/`check_suite` events pollute commit/check-run state used for deploy gating.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (documented, supported feature), and (2) at least one of those organizations configured without `webhook_secret` (explicitly marked "optional" in the setup docs and example secrets file). Given this, exploitation requires nothing more than an HTTP POST to `/webhooks` with a crafted JSON body and the correct `X-Github-Event` header - no authentication, no token, no session. Likelihood is directly tied to operational configuration choices that the engine itself documents as valid, so it is realistically reachable in the wild.

### Recommendation
- Never derive the verification key from the unverified payload body. Verification should not depend on attacker-controlled fields at all, or the organization used for verification must be independently confirmed (e.g., matched against an installation/delivery ID from the request headers such as `X-GitHub-Hook-Installation-Target-ID`, not payload JSON).
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; instead, treat a missing configured secret as a hard failure (`head(422)`), or require `webhook_secret` to be mandatory for any organization in a multi-org configuration.
- Log and alert when webhook verification is skipped due to an absent secret, so operators are aware of the exposure.

### Proof of Concept
Given a `config/secrets.yml` with two orgs configured, e.g.:
```yaml
github:
  secured-org:
    app_id: 1
    webhook_secret: "s3cr3t"
  unsecured-org:
    app_id: 2
    # no webhook_secret set
```

An attacker (no auth) sends:
```
POST /webhooks
X-Github-Event: status

{
  "sha": "<victim commit sha in a stack under unsecured-org>",
  "state": "success",
  "branches": [{"name": "main"}],
  "repository": {
    "owner": {"login": "unsecured-org"},
    "full_name": "unsecured-org/some-repo"
  }
}
```
`repository_owner` resolves to `unsecured-org`, `Shipit.github(organization: 'unsecured-org')` has `webhook_secret` nil, so `verify_webhook_signature` returns `true` regardless of (or absent) `X-Hub-Signature`. `Handlers::StatusHandler` then processes the forged "success" status for the referenced commit, potentially triggering continuous deployment for that stack with no attacker credential of any kind.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
