### Title
Cross-tenant `Commit.where(sha:)` in `StatusHandler#process` mutates commit rows from unrelated stacks/repositories - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization that authenticated the webhook, so a validly-signed status event from one tenant's own GitHub organization can update `Status` records — and trigger downstream deploy scheduling — for `Commit` rows belonging to a completely different repository/stack that happens to share the same sha (e.g., a shared open-source ancestor commit between a victim's repo and an attacker-controlled fork). This can affect multiple `Stack`s (e.g., `staging` and `production`) simultaneously if both have a `Commit` row for that sha.

### Finding Description
The binding that should hold: **the set of `Stack`/`Commit` rows mutated by a status webhook == the `Stack`(s) that belong to the repository/organization that produced a validly-signed webhook** (i.e. `organization_that_signed == organization_owning_the_mutated_stack`). Instead, the actual binding is: **mutated rows == every `Commit` row across the entire database whose `sha` column matches `params.sha`**, regardless of `stack_id`/repository, because `Commit.where(sha: params.sha)` in `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:21-23`) is a global, unscoped lookup.

`WebhooksController#verify_signature` only proves that the payload was signed with the `webhook_secret` configured for the organization named in `params['repository']['owner']['login']` (`Shipit.github(organization: repository_owner)`, `lib/shipit.rb:170-181`); it says nothing about which `sha` or which `stack`/`repository` the event is actually allowed to affect. `StatusHandler` never re-checks `params.dig('repository', ...)` against the `Commit`'s owning `stack.repository`, so once signature verification passes for *any* configured organization, the handler will happily update any `Commit` row anywhere in the system that shares the reported sha — including rows belonging to `staging` and `production` `Stack`s of a totally different, victim-owned `Repository`, as long as both stacks happen to have ingested a commit with that same sha (realistic for forked/mirrored repos, since git SHA-1s are content-derived and identical for identical commit content).

Exploit flow: attacker registers/administers their own organization "attacker-org" as a legitimate tenant on the shared Shipit instance (with its own `webhook_secret`), forks or otherwise obtains a commit that shares a sha with a commit already tracked by the victim's `staging` and `production` `Stack`s, and sends (or has GitHub send, via a real status update on their own repo) a `status` event: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<shared sha>", "state": "success", ...}`, correctly signed with attacker-org's own secret. `verify_signature` passes because it only checks that attacker-org's secret matches. `StatusHandler#process` then runs `Commit.where(sha: "<shared sha>")`, which returns the victim's `staging` and `production` `Commit` rows (different `stack_id`s, same `Repository`) alongside the attacker's own, and calls `commit.create_status_from_github!(params)` on all of them, marking them `success` and (via `Commit#add_status` → `stack.schedule_merges`, and `Commit#schedule_continuous_delivery`) potentially triggering deploys on both victim environments in one request.

Existing guards do not catch this: `verify_signature` authenticates the organization, not the sha/repository being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema only validates field shapes, not ownership; there is no `stack`/`repository` scoping anywhere in `StatusHandler`.

### Impact Explanation
A validly-authenticated webhook from one tenant's own GitHub organization can write `Status` rows and drive continuous-deployment decisions for `Commit`/`Stack` rows owned by a completely unrelated `Repository`/tenant, matching "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." Because the lookup is by bare `sha` with no repository scoping, one forged/legitimate-but-misdirected event can simultaneously affect every `Stack` (e.g., both `staging` and `production`) that has ingested a `Commit` with that sha, not just one. This is repeatable against any sha collision the attacker can arrange, and the blast radius spans all stacks across all repositories sharing that commit history, not just one victim repository.

### Likelihood Explanation
Requires: (1) Shipit configured in multi-organization mode with multiple tenants (`github_default_organization` non-nil, `secrets.github` keyed by org) — a supported, non-exotic configuration; (2) attacker controls a registered organization on the same Shipit instance (their own GitHub App installation/secret, which they legitimately have as a tenant, not a secret stolen from the victim); (3) a genuine sha collision between the attacker-visible repo and the victim's tracked stacks, which occurs naturally for forks/mirrors of the same upstream history. Attacker cost is low once these preconditions hold (no special GitHub org privilege on the victim's side is needed), and the action is repeatable for every shared sha.

### Recommendation
Scope `Commit` lookups in `StatusHandler#process` (and analogous handlers) to the repository/stack indicated by the authenticated webhook's organization/repository — e.g., join through `stack.repository.owner`/`full_name` derived from `params['repository']` and require it to match before updating any `Commit`, instead of a bare `Commit.where(sha:)` across the whole table.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create one `Repository` with two `Stack`s (`staging`, `production`), each `continuous_deployment: true`.
2. Create two `Commit` rows with the identical `sha` "deadbeef", one per stack (`stack_id` differing).
3. Build `params` for `StatusHandler` with `sha: "deadbeef", state: "success"` and a `repository` payload pointing at an unrelated third-party org/repo (simulating the "attacker org" whose signature validly passed `verify_signature` upstream).
4. Call `StatusHandler.new.process(params)` directly (bypassing controller-level signature check, since that check is orthogonal — it only proves org authenticity, not sha/repo scoping).
5. Assert both `Commit` rows now have a `success` status: `assert commit_staging.reload.success?` and `assert commit_production.reload.success?`.
6. Assert both stacks' continuous-deployment path was invoked (e.g., stub/expect `ContinuousDeliveryJob.perform_later` called with each stack, or that `schedule_continuous_delivery` fired for both), demonstrating a single forged/misdirected webhook mutated and could deploy two independent environments of the same victim `Repository`.
