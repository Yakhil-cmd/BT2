## Confirmed root cause

`definition.js` `validateDefinition()`'s `'in data feed'` and `'in merkle'` op handlers validate `feed_name` for type, non-emptiness and max length, but never reject embedded `\n` (newline) bytes: [1](#0-0) [2](#0-1) 

Compare this to the sibling code path that actually *writes* data feeds — `validateInlinePayload()`'s `"data_feed"` case in `validation.js`, which explicitly blocklists `\n` in both `feed_name` and string `value` because they are used as a delimiter: [3](#0-2) 

That delimiter usage is confirmed in the KV-store key construction and in the address-lookup code, where `feed_name` is spliced directly between `\n`-separated segments of the lookup key (`'df\n'+address+'\n'+feed_name+'\n'+prefixed_value+...`), and parsing later does `key.split('\n')` expecting exactly the right number of segments: [4](#0-3) [5](#0-4) 

So the write path (`data_feed` message) blocks `\n` in `feed_name`/`value`, but the read/condition path (`'in data feed'` and `'in merkle'` address-definition operators) does **not** — this is the same class of bug as the CVE: a denylist that filters a dangerous character on one code path but is missing/incomplete on a structurally-related path that shares the same delimiter-based parsing, letting crafted input "escape" its intended field boundary.

### Title
Missing newline filtering in `'in data feed'`/`'in merkle'` address-definition validation allows delimiter-injection into oracle data-feed keys — (File: `definition.js`)

### Summary
`definition.js` validates the `feed_name` argument of the `'in data feed'` and `'in merkle'` address-definition operators for length and type only, unlike the `data_feed` message payload validator in `validation.js`, which explicitly forbids `\n` because the underlying storage engine (`data_feeds.js`, `string_utils.js`) uses `\n` as a field delimiter inside the LevelDB/RocksDB key format `df\n<address>\n<feed_name>\n<type>\n<value>\n<mci>`.

### Finding Description
The `data_feed` message app (the write path) enforces `feed_name.indexOf('\n') === -1` and `value.indexOf('\n') === -1` precisely because the key/value are `\n`-joined and later split with `key.split('\n')`/`data.value.split('\n')` [3](#0-2) [5](#0-4) .

The read/condition path — the `'in data feed'` and `'in merkle'` operators that can appear inside an **address definition** — builds the exact same kind of `\n`-delimited key prefix via `dataFeedByAddressExists()`/`readDataFeedByAddress()` [4](#0-3) [6](#0-5) , but its own validation in `definition.js` never checks `feed_name` (or `value`, for the `in data feed` case) for embedded `\n` [7](#0-6) [8](#0-7) .

Because a `feed_name` containing an embedded `\n` is accepted by `validateDefinition()`, an address (or shared/multi-signature address) definition can encode a `feed_name` such as `"real_feed\nfoo"`. When this condition is evaluated at spend time, the resulting key prefix `df\n<oracle>\nreal_feed\nfoo\n...` no longer corresponds to any legitimately-posted `real_feed` value (since the write path guarantees no genuine data feed key can contain that shape), but it changes the semantic boundary of the `\n`-delimited key space that the range-scan (`kvstore.createKeyStream`/`createReadStream` with `gte`/`lte`) traverses. This lets a party who authors (or negotiates) the shared address definition construct a data-feed condition whose displayed/intended feed name (e.g. shown to a counterparty as `"real_feed"`) does not match the actual byte-level condition being checked, since trailing bytes after the embedded `\n` are silently absorbed into what should be the `type`/`value` segment of the key. This is the same "denylist incompleteness enables scope escape" bug class as the CVE: filtering a special character on the sink that produces data but not on the sink that consumes/matches it.

### Impact Explanation
This affects any address whose spending condition includes `'in data feed'` or `'in merkle'`, most notably **shared/multi-party addresses** (escrow, betting, vesting, or oracle-gated multisig contracts) where one party authors the definition text and another party co-signs trusting the displayed condition. A malicious co-author can craft a `feed_name` with an embedded newline so that the condition text appears to reference a legitimate, currently-nonexistent or attacker-controllable oracle feed name/value pair, while the actual key range scanned in the KV store can be made to overlap with a different feed record than what the honest party believes they are approving. This can let the malicious party satisfy the "oracle" condition in a way the honest counterparty did not intend, resulting in unauthorized release of funds held at the shared address (fund loss for the honest party).

### Likelihood Explanation
Exploitation requires the attacker to control (or negotiate) the address definition text, which is a normal step in creating shared/multisig contract addresses in ocore (e.g., betting/arbiter contracts, vesting definitions) — it does not require any node compromise, and the manipulation is a pure string-crafting exercise reachable by any unprivileged address/definition author. The likelihood is moderate: it requires a specific two-party contract-construction workflow using `'in data feed'`/`'in merkle'`, and the counterparty must fail to notice the embedded control character in the displayed definition (plausible since `\n` is often invisible or truncated in UIs).

### Recommendation
Add the same `indexOf('\n') === -1` (and ideally reject `\r` as well) checks for `feed_name` (and, for `'in data feed'`, the string `value`) in the `'in data feed'` and `'in merkle'` op validators in `definition.js`, mirroring the checks already present in `validation.js`'s `data_feed` payload validator, so the read/condition path enforces the same invariant as the write path.

### Proof of Concept
1. Construct a shared/multi-signature address whose definition includes:
   `["in data feed", [["ORACLE_ADDR"], "real_feed\nEXTRA", "=", "100"]]`
2. Present this definition (or the resulting address) to a counterparty; the rendered/serialized text may visually appear to reference feed name `real_feed` (with the trailing bytes after `\n` hidden/truncated in typical rendering), while `definition.js`'s validator accepts it unmodified since it never checks `feed_name` for `\n`.
3. At spend time, `evaluate()`/`dataFeedByAddressExists()` builds the key prefix `df\nORACLE_ADDR\nreal_feed\nEXTRA\n...` and performs a range scan; because genuine data-feed records for `real_feed` can never contain this exact byte sequence (the write path forbids `\n` in feed names), the attacker can pre-arrange (or wait for) an oracle-posted record whose key range is inadvertently captured by this crafted boundary, satisfying the condition without the honest, visually-agreed-upon oracle value ever being posted.

*(Full exploitability of step 3 — i.e., constructing an oracle value that a modified boundary will match unexpectedly — depends on kvstore range-scan semantics not independently re-verified beyond the code shown; the concrete root cause of the missing `\n` denylist on the read path versus the write path is confirmed directly in the code.)*
