### Title
Missing reentrancy guard around external `signer-manager-validate-stake` call in `register-for-bond` allows state to be manipulated before bond accounting is committed - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` invokes an attacker-supplied contract (`signer-manager`, passed as a `<signer-manager-trait>` reference) via `signer-manager-validate-stake` *before* it settles rewards, rolls over custodied sBTC, and commits the staker's bond membership and share accounting. [1](#0-0)  Unlike every other state-mutating public function in this contract that talks to an untrusted `signer-manager`/token contract, `register-for-bond` does **not** call `validate-no-reentrancy` before or after that external call.

### Finding Description
The contract has an explicit, repeatedly-used reentrancy guard, `validate-no-reentrancy`, that is invoked in `claim-rewards`, `claim-staker-rewards-for-signer`, `unstake-sbtc`, `announce-l1-early-exit`, and `grant-signer-key` immediately around/after external `contract-call?`s to sBTC or signer-manager code: [2](#0-1) [3](#0-2) [4](#0-3) .

`register-for-bond`, however, calls `(try! (signer-manager-validate-stake signer-manager tx-sender bond-index u1 amount-ustx sats-total true signer-calldata))` — a call into caller-supplied contract code — *before* any of the following state-mutating steps run:
- `settle-rewards` / `settle-staker-rewards` (reward snapshot commit)
- `verify-bond-rollover-window`
- `roll-sbtc` (moves custodied sBTC — itself an external `contract-call?` to the sBTC token)
- `map-set protocol-bond-memberships`, `map-set protocol-bonds-total-staked`
- `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles` [5](#0-4) 

At the time `signer-manager-validate-stake` executes, `existing-membership`, `old-sbtc`, and `existing-stake` have already been captured as local `let` bindings from pre-call state, but none of the maps have been written yet. Because `signer-manager` is a trait reference supplied by `tx-sender` themselves, the staker can point it at a contract they control, and that contract's `validate-stake!` implementation runs with full ability to re-enter `pox-5` (e.g., call `register-for-bond` again for a different `bond-index`, or call `stake`, `stake-update`, `unstake-sbtc`) while the outer call's `protocol-bond-memberships`/`total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle` maps are still in their pre-transaction state. This is the exact checks-effects-interactions violation the external report describes (control handed to an interacting/attacker contract before internal accounting is finalized).

### Impact Explanation
If reentrant calls into `register-for-bond`/`stake`/`stake-update` succeed while `existing-membership`/`existing-stake` still read as `none` (because the outer call hasn't written them yet), a staker could register bond/share entries against multiple `bond-index`s or against `staker-info` state that the overlap checks (`bond-overlaps-new-position?`, `ERR_ALREADY_STAKED`, `ERR_ALREADY_REGISTERED`) are specifically designed to prevent. That would let a single staker's underlying committed STX/sBTC be double-counted into `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle`, inflating reward-earning shares without a matching increase in locked value — a double-counting of a commitment, which is a Critical-severity outcome under the stated impact criteria (double-counting a commitment or reward).

### Likelihood Explanation
Exploitability depends on two conditions I could not fully verify against the codebase within the available search budget:
1. Whether Stacks' pox-locking special-case handling (`pox-locking/src/pox_5.rs`, `handle_lockup_pox_v5`) fires for *nested* `contract-call?`s to `stake`/`register-for-bond` made from within another contract's execution (i.e., a reentrant call from `signer-manager`), or only for the outermost transaction-level call.
2. Whether the actual sBTC `ft-transfer?` inside `roll-sbtc` would fail on a reentrant second pull due to insufficient balance, which would bound the practical STX/sBTC that could be double-committed even if the map state can be manipulated.

Regardless of those two open questions, the structural issue — an external, attacker-controllable call preceding effects, with no reentrancy guard, in a function that every sibling function in the same file explicitly guards — is a clear deviation from the contract's own established safety pattern and directly matches the report's bug class.

### Recommendation
Add `(try! (validate-no-reentrancy))` immediately before or after the `signer-manager-validate-stake` call in `register-for-bond` (and audit `stake`, `stake-update`, `update-bond-registration` for the same gap), or move the external validation call to occur strictly after all local map-state (`protocol-bond-memberships`, `*-staked-for-cycle` maps, `staker-info`) has been committed, following the same checks-effects-interactions ordering already used in `claim-rewards` and `unstake-sbtc`.

### Proof of Concept
Conceptual sequence (exact reentrant call must be confirmed against pox-locking's nested-call handling, per the caveat above):
1. Attacker deploys a malicious contract `evil-signer-manager` implementing `signer-manager-trait`, whose `validate-stake!` callback calls back into `pox-5.register-for-bond` with a different `bond-index`.
2. Attacker calls `register-for-bond(bond-index=A, signer-manager=evil-signer-manager, ...)`. Execution reaches `(try! (signer-manager-validate-stake ...))` at [6](#0-5)  before `map-set protocol-bond-memberships` has run.
3. Inside that callback, `evil-signer-manager` re-enters `register-for-bond(bond-index=B, ...)` for the same `tx-sender`. Because `protocol-bond-memberships`/`staker-info` for the staker have not yet been written by the outer call, the overlap/`ERR_ALREADY_STAKED`/`ERR_ALREADY_REGISTERED` checks pass for the inner call too.
4. Both calls proceed to commit bond membership and per-cycle share maps, potentially crediting the staker's shares/rewards eligibility twice against a single locked-STX/sBTC commitment.
