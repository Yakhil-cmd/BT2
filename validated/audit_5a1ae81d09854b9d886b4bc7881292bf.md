### Title
RAY-value overflow in accrual permanently freezes a large market — (`common/src/rates/simulate.rs`)

### Summary
The integer-overflow class maps onto the protocol's RAY-scaled accrual math. Every compounding step revalues the whole book as `borrowed × borrow_index` and `supplied × supply_index` in `i128`. These products grow without bound: indexes compound up to `MAX_BORROW_INDEX_RAY = 10^36`, while `borrowed`/`supplied` are scaled shares whose magnitude is set by user deposits. When either product's half-up result exceeds `i128::MAX`, `mul_div_half_up` panics with `MathOverflow` inside `accrue_step`, and every state-changing entrypoint accrues first — so the entire market freezes permanently with all supplier and borrower funds locked.

### Finding Description
`contracts/pool/src/interest.rs::global_sync` runs `accrue_chunk` → `common/src/rates/simulate.rs::accrue_step` before any pool mutation. `accrue_step` unconditionally computes:

- `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` (line 60)
- `supplied_original = scaled_to_original(env, supplied, supply_index)` (line 61)

`scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), i.e., `mul_div_half_up(scaled, index, RAY)`. The `I256`-widened intermediate is exact, but the quotient itself must fit `i128` — `borrowed` is a RAY value (whole tokens × 10^27), and `borrow_index` multiplies it again by up to 10^9× (cap 10^36 raw / RAY). The borrow index only grows (`update_borrow_index` is monotone, capped at 10^36), so once `borrowed × borrow_index / RAY > i128::MAX` there is no path back: the panic is hit on the very first arithmetic of accrual, before any clamping.

Because every controller verb (supply, borrow, withdraw, repay, liquidate, clean_bad_debt, flash paths) routes through the pool, which calls `global_sync` first, all of them revert with `MathOverflow` for that market forever. Repayment cannot shrink `borrowed` because repayment itself accrues first and panics. The project's own stress test demonstrates this: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` shows `update_indexes`, `withdraw`, and `repay` all reverting with `MATH_OVERFLOW`, and confirms `borrow_index < MAX_BORROW_INDEX_RAY` — the value overflow preempts the index cap (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). `docs/reference/invariants.md` INV-IDX-01 acknowledges "Debt-value overflow can still revert accrual before that ceiling is reached," i.e., the freeze is a real reachable state, not a theoretical bound violation.

### Impact Explanation
Permanent freezing of funds: every supplier's deposit and every borrower's collateral backing the affected (hub, token) book becomes unrecoverable, and liquidations of underwater positions in that market become impossible, compounding insolvency risk. The freeze also blocks `clean_bad_debt`/`recapitalize`-style recovery on that market since they accrue first.

### Likelihood Explanation
An unprivileged attacker can reach the cliff without privileged calls: `update_indexes` is permissionless and performs the same accrual; the preconditions are only a sufficiently large book (the demonstrated cell uses ~10^9 whole 18-decimal tokens supplied, ~98% borrowed) and sustained high utilization on a steep rate curve so the index compounds ~170× before caps engage. Caps are validated at listing (`require_cap_within_asset_domain`) but `max_cap_for_decimals` permits billion-token-scale markets, and governance can set high caps legitimately. The capital and time requirements make opportunistic exploitation costly, but no privileged action is needed and a market can also drift into the cliff organically — utilization is value-based and uncompounded books drift upward over years. Severity: Medium.

### Recommendation
Make the overflow non-fatal: saturate (or clamp) the revaluation in `calculate_utilization`/`accrue_step` to `i128::MAX` rather than panicking, or scale down operands (e.g., compute utilization via `mul_div` on reduced-precision values) so accrual always completes. Additionally or alternatively, enforce a per-market cap on scaled totals such that `supplied × index` can never exceed `i128::MAX` before the index cap engages — i.e., derive supply/borrow caps from `i128::MAX / MAX_BORROW_INDEX_RAY` in RAY terms rather than only from token-decimal domains.

### Proof of Concept
Reproduced by the existing test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

```rust
let principal = BILLION * 10i128.pow(18);          // 1e9 BIG18 tokens
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
// advance time year-by-year; eventually:
t.try_update_indexes_for(&["BIG18"])               // Err(MATH_OVERFLOW)
t.try_withdraw_raw(BOB, "BIG18", 1)                // Err(MATH_OVERFLOW)
t.try_repay(ALICE, "BIG18", 1.0)                   // Err(MATH_OVERFLOW)
```

The panic originates at `common/src/rates/simulate.rs:60-61` (`scaled_to_original` → `mul_div_half_up` quotient > `i128::MAX`), before `update_borrow_index` can clamp at `MAX_BORROW_INDEX_RAY`.
