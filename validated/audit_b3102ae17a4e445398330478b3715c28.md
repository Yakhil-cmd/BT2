### Title
Webhook signature is verified against the organization named in the payload, but handlers act on repository/commit identifiers from that same untrusted payload without confirming they belong to the verified organization — enabling cross-tenant status/commit spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using an org name pulled straight out of the request body (`repository.owner.login`, falling back to `organization.login`), then only checks that this *one* field's implied secret matches the HMAC of the whole body. [1](#0-0) [2](#0-1) 

Downstream handlers, however, do not re-check that the organization used to select the secret is the same organization that owns the repository/commit being acted on. `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` load stacks purely from `payload.dig('repository', 'full_name')`, [3](#0-2) 
and `StatusHandler#process` is worse still — it doesn't consult repository ownership at all, it just does `Commit.where(sha: params.sha)` across the *entire* database and calls `create_status_from_github!` on every match. [4](#0-3) 

Because Shipit explicitly supports multiple GitHub organizations each with their own `app_id`/`webhook_secret` config (documented in `docs/setup.md`), [5](#0-4) 
an operator running such a multi-tenant instance creates exactly the situation the report's bug class targets: a field that is used to select/verify trust (`repository.owner.login`) is disconnected from the fields the code actually acts on (`repository.full_name`, `sha`).

### Finding Description
The binding that should hold is:
`organization whose secret validated the signature == organization owning the repository/commit the handler mutates`

Trace of the break:
1. `repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) from the JSON body and is used solely to pick which `GitHubApp`/webhook secret is used for HMAC verification via `Shipit.github(organization: repository_owner)`. [6](#0-5) 
2. The HMAC (`X-Hub-Signature`) only proves that *some* org's registered GitHub App produced this exact byte string — it says nothing about whether the `repository.full_name` or `sha` fields inside that same body actually belong to that org. Any tenant that operates their own GitHub App/organization pointed at the shared Shipit install can freely fabricate any JSON body (including `repository.full_name` or `sha` values referencing a completely different tenant's repository/commit) and have GitHub sign it validly for their own org's secret.
3. `Handler#stacks` resolves the target `Stack` purely via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — with no comparison back to the verified `repository_owner`. [7](#0-6) [8](#0-7) 
4. `StatusHandler#process` is the sharpest instance: it never even reads `repository` from the payload, it looks up commits globally by `sha` and writes a GitHub-status record onto whatever `Commit` (belonging to whatever `Stack`, whatever org) happens to have that SHA. [9](#0-8) 
5. `Commit#create_status_from_github!` → `add_status` directly influences `Commit#deployable?` (`success? && !blocked?`) and can trigger continuous delivery (`schedule_continuous_delivery`) for the victim stack. [10](#0-9) [11](#0-10) [12](#0-11) 

Before the attacker's request: victim stack's commit status is driven only by GitHub events genuinely signed by the victim org's own webhook secret.
After the attacker's request: an operator of *any other* onboarded org can push a `status` (or `push`/`pull_request`/`check_suite`) webhook, signed with their own org's secret, that references the victim's `sha`/`repository.full_name`, and Shipit will process it as if it came from the victim org — because nothing after signature verification re-checks organization identity.

### Impact Explanation
This breaks the "an organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Concretely, in a multi-org Shipit deployment:
- A `status` webhook forged this way can flip a required CI context to `success` on a victim commit it does not own, satisfying `ci.require` and `Commit#deployable?`, which can unblock/trigger continuous delivery and an unauthorized deploy of a repository the attacker has no legitimate access to. This matches the Critical bucket ("cross-repository writes, or an unauthorized deploy").
- `push`/`pull_request`/`check_suite` handlers resolve stacks purely by `repository.full_name` from the body as well, so the same class of forged-organization-but-arbitrary-repository payload can enqueue `GithubSyncJob`, refresh check runs, or manipulate pull-request-derived state for a victim's stack.

### Likelihood Explanation
This requires the operator to run Shipit with more than one configured GitHub organization (a documented, supported configuration) and requires the attacker to control one of those organizations' own GitHub App (i.e., they are a legitimate but semi-trusted tenant of the shared Shipit instance, not a fully privileged Shipit user/admin). No `ApiClient` token, no Shipit session, and no GitHub credentials for the victim org are needed — only ownership of *any one* onboarded org's webhook secret, which they legitimately possess for their own tenant. This is a realistic multi-tenant trust-boundary violation, not a theoretical one.

### Recommendation
After verifying the HMAC, cross-check that the organization actually owning the resolved `Repository`/`Stack` (or the `Commit`'s stack, in `StatusHandler`) matches `repository_owner` used for signature selection, and reject/drop the event otherwise. `StatusHandler` in particular should scope its `Commit` lookup to commits belonging to stacks whose repository owner equals the verified `repository_owner`, not a bare `Commit.where(sha: params.sha)` across all tenants.

### Proof of Concept
Setup: Shipit configured with two GitHub orgs, `AttackerOrg` and `VictimOrg`, per the documented multi-org `secrets.yml` schema. [5](#0-4) 

1. Attacker controls `AttackerOrg`'s GitHub App and therefore knows/controls its `webhook_secret`.
2. Attacker crafts (or has GitHub deliver, by triggering any event in their own org while embedding attacker-controlled JSON) a `status` event body:
```json
{
  "sha": "<victim_commit_sha_in_VictimOrg_repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
3. `verify_signature` computes `repository_owner` = `"AttackerOrg"`, fetches `AttackerOrg`'s `webhook_secret`, and the HMAC validates because the request genuinely came from `AttackerOrg`'s GitHub App. [6](#0-5) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `VictimOrg` commit purely by SHA (global lookup, no owner check), and calls `create_status_from_github!`, marking the victim's commit `success` for a required context. [4](#0-3) 
5. If `VictimOrg`'s stack has continuous delivery enabled and this was the last blocking status, `Commit#schedule_continuous_delivery` fires, resulting in an unauthorized deploy of `VictimOrg`'s stack triggered entirely by `AttackerOrg`. [11](#0-10)
