### Title
Unchecked Return Value on Raw `IERC721.transferFrom()` in Bridge Allows Unauthorized Cross-Chain Minting — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.requestERC721Transfer()` calls `IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId)` without verifying that the transfer actually succeeded. In non-`modeMintBurn` deployments, if a registered non-standard ERC721 token's `transferFrom` does not revert on failure (silently no-ops), the bridge emits `RequestValueTransferEncoded` and increments `requestNonce` even though no token was deposited. Counterpart-chain operators then legitimately handle the event and mint or release the token on the other chain, giving the caller an asset they never deposited.

---

### Finding Description

`BridgeTransferERC20` and `BridgeFee` both import and apply `SafeERC20` for every ERC-20 movement. [1](#0-0) [2](#0-1) 

`BridgeTransferERC721` imports no equivalent safety wrapper and makes two bare `transferFrom` calls:

**Line 129 — public entry point (the exploitable path):**
```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [3](#0-2) 

**Line 69 — operator-only handle path (loss-of-funds on delivery):**
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [4](#0-3) 

The ERC-721 standard requires `transferFrom` to throw on failure, but it does not mandate a boolean return value. Non-standard ERC-721 tokens that return `false` instead of reverting are a known class of deployed contracts. Because the interface declares the function as `returns ()`, Solidity silently discards any returned data; no ABI-decode revert occurs, and execution continues past the failed transfer.

In `_requestERC721Transfer`, the only guard that could catch the failure in `modeMintBurn` mode is the subsequent `ERC721Burnable.burn()` call (which would revert because the bridge never received the token). In **non-`modeMintBurn` mode** there is no such guard: the event is emitted and `requestNonce` is incremented unconditionally. [5](#0-4) 

---

### Impact Explanation

An attacker who controls or interacts with a registered non-standard ERC-721 token (one whose `transferFrom` silently no-ops on failure) can:

1. Call `requestERC721Transfer` for a `_tokenId` they do not own or have not approved.
2. The bridge's `transferFrom` call returns without reverting; the token stays with its real owner.
3. `RequestValueTransferEncoded` is emitted with a valid nonce; counterpart operators process it normally.
4. The attacker receives a freshly minted (or unlocked) ERC-721 on the counterpart chain at zero cost.

This is an **unauthorized mint of a bridged asset**, directly matching the allowed impact gate. The bridge's `requestNonce` is also permanently consumed, which can disrupt nonce-based recovery.

---

### Likelihood Explanation

- `requestERC721Transfer` is a public, permissionless function — no role check is required to call it.
- The only prerequisite is that the target token is registered (`onlyRegisteredToken` in `_requestERC721Transfer`). Token registration is controlled by the bridge owner, but once a non-standard token is registered the attack is open to any caller.
- Non-standard ERC-721 tokens that return `false` rather than reverting exist in production (analogous to USDT in the ERC-20 space).
- The vulnerability is limited to non-`modeMintBurn` bridge deployments; `modeMintBurn` deployments are incidentally protected by the downstream `burn()` revert.

---

### Recommendation

Replace both bare `transferFrom` calls with OpenZeppelin's `safeTransferFrom` (the ERC-721 variant that checks `onERC721Received` and reverts on failure), or add an explicit ownership check before and after the transfer:

```solidity
// requestERC721Transfer — line 129
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);

// handleERC721Transfer — line 69
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

Alternatively, assert ownership transfer by checking `ownerOf(_tokenId)` equals `address(this)` after the call, and revert if it does not.

---

### Proof of Concept

1. Deploy a non-standard ERC-721 token whose `transferFrom` emits a `Transfer` event but does **not** actually update `_tokenOwners` and does **not** revert (returns silently).
2. Register the token on a non-`modeMintBurn` bridge via `registerToken`.
3. Call `bridge.requestERC721Transfer(tokenAddr, attacker, tokenId, "0x")` from any EOA — no prior `approve` needed because the token's `transferFrom` is a no-op.
4. Observe that `RequestValueTransferEncoded` is emitted with a valid nonce and `requestNonce` increments.
5. On the counterpart chain, operators call `handleERC721Transfer`; the token is transferred (or minted) to the attacker's address.
6. The original token owner on the source chain still holds `tokenId`; the attacker now holds the bridged copy on the destination chain. [6](#0-5) [7](#0-6)

    // _requestERC721Transfer requests transfer ERC721 to _to on relative chain.
    function _requestERC721Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _tokenId,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        (bool success, bytes memory uri) = _tokenAddress.call(abi.encodePacked(ERC721Metadata(_tokenAddress).tokenURI.selector, abi.encode(_tokenId)));
        if (!success) {
            uri = "";
        }
        if (modeMintBurn) {
            ERC721Burnable(_tokenAddress).burn(_tokenId);
        }
        emit RequestValueTransferEncoded(
            TokenType.ERC721,
            _from,
            _to,
            _tokenAddress,
            _tokenId,
            requestNonce,
            0,
            _extraData,
            2,
            abi.encode(string(uri))
        );
        requestNonce++;
    }

```
