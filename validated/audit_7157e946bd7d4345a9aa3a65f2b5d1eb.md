## Title
Merkle tree in `merkle.js` lacks domain separation between leaf and internal-node hashes, enabling forged inclusion proofs consumed by `is_valid_merkle_proof` / `in merkle` - (File: merkle.js)

### Summary
`merkle.js` hashes leaves and internal nodes with the exact same function and no domain-separating prefix. A leaf hash is `hash(element)` and an internal node hash is `hash(child1 + child2)` — plain string concatenation of two children hashes, with nothing distinguishing "this is a leaf" from "this is an internal node." This is the classic Merkle "node-as-leaf" second-preimage weakness, and the codebase's own comment acknowledges it (`merkle.js` line 85: `// Node-as-Leaf issue might matter in some cases`). This directly maps to the reported bug class (missing domain separation / leaf-collision in a Merkle scheme used for on-chain proof verification).

### Finding Description

and `verifyMerkleProof` reconstructs the root the same way, hashing the caller-supplied `element` exactly like an internal node would be hashed: [2](#0-1) 

Because leaf-hashing and node-hashing use the identical `hash()` primitive with no distinguishing prefix (e.g. `0x00` for leaf / `0x01` for node), anyone who knows two sibling hash values one level below the root (`H1`, `H2`) of a genuinely published tree can compute `fakeElement = H1 + H2` and submit that as a "leaf" together with the sibling path from that internal level upward. `verifyMerkleProof` will faithfully hash `fakeElement` into the same internal-node value and walk it up to the same, genuine root — successfully "proving" inclusion of an element that was never part of the original data set.

This is directly reachable by an unprivileged AA trigger sender through the oscript `is_valid_merkle_proof` function, where both `element` and `proof` (including `proof.root`, `proof.siblings`, `proof.index`) are attacker-supplied trigger data: [3](#0-2) 

It is also reachable through the address-definition `in merkle` authentifier, where the element is fixed by the definition but the format-validation regex still permits base64 characters (`+`, `/`, `=`, alphanumerics), i.e. it does not reject a string shaped like a concatenation of two base64 hash digests: [4](#0-3) [5](#0-4) 

In both flows, `is_valid_merkle_proof`/`verifyMerkleProof` only checks that the supplied sibling chain reconstructs to a root — the AA/definition author separately compares that reconstructed root to a trusted value (typically a Merkle root published by an oracle via `data_feed[[...]]`, as seen in the codebase's own oscript examples of comparing computed values against oracle feeds). Since the underlying tree's data set (and hence its internal hashes) is generally public — a merkle-based whitelist/airdrop must publish the underlying elements for legitimate users to build their own proofs — an attacker can derive internal-node hash values and thereby forge inclusion for a synthetic "element" that never appears in the original committed list, while still validating against the oracle-published root.

### Impact Explanation
Any AA (autonomous agent) that uses `is_valid_merkle_proof` (or an address definition using `in merkle`) to gate an action — e.g. a merkle-based airdrop/whitelist AA that pays out to `trigger.data.element` or unlocks a state transition when `element` is proven a member — can be tricked into treating a forged, non-member string as a valid leaf. Depending on how the AA consumes `element` afterward (e.g. as a beneficiary identifier, amount, or unlock code), this can lead to unauthorized AA fund disbursement/loss or bypass of the intended whitelist/authorization gate, which are concrete AA-fund-loss/bypass impacts.

### Likelihood Explanation
Exploitation requires the underlying Merkle data set (or at least two revealed sibling hashes at some tree level) to be knowable to the attacker, which is normally the case for public whitelist/airdrop Merkle trees since the oracle must publish the list (or sibling proofs are shared with the legitimate leaf holders) for anyone to build a valid inclusion proof in the first place. No privileged access, malicious peer, or network condition is required — only a single crafted trigger unit from any wallet, which fits the "unprivileged AA trigger sender" threat model.

### Recommendation
Add domain separation to `merkle.js`'s hashing: prefix leaf hashing and internal-node hashing with distinct tags (e.g. `hash("\x00" + element)` for leaves and `hash("\x01" + child1 + child2)` for internal nodes), and re-verify/version this change carefully since it changes on-chain-verifiable hash values (would need a protocol upgrade / MCI-gated fix similar to other `bPostPemCurvesFix`-style upgrades already present in `formula/evaluation.js`).

### Proof of Concept
1. Oracle publishes Merkle root `R` over elements `[e0, e1, e2, e3, ...]` for a whitelist/airdrop, as computed by `merkle.getMerkleRoot`.
2. Attacker (who can see the full published list, as is required for legitimate users to build their own proofs) computes `H1 = hash(e0)`, `H2 = hash(e1)` and forms `fakeElement = H1 + H2` (plain string concatenation, same as `merkle.js` line 15/41 `hash(arrHashes[i] + arrHashes[hash2_index])`).
3. Attacker builds a forged proof object `{ index: <index of the (e0,e1) pair's parent node>, siblings: <the real siblings from that level up to the root>, root: R }`.
4. Attacker submits an AA trigger unit with `trigger.data.element = fakeElement` and `trigger.data.proof = <forged proof>`.
5. The AA formula `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` (`formula/evaluation.js` lines 1768-1807) returns `true`, and if the AA compares `trigger.data.proof.root == data_feed[[oracles=..., feed_name=...]]` this also succeeds because `root` is the genuine oracle-published `R`, even though `fakeElement` was never one of the committed elements `e0..en`. function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
