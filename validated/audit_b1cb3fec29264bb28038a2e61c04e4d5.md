### Title
Unbounded, un-partitioned epoch-boundary commission-account processing scales with attacker-created vote-account count, not real validator count - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`distribute_reward_commissions` and `store_commission_accounts_partitioned` process the entire set of reward-commission accounts (`RewardCommissionAccounts`/`RewardCommissionAccountsStorable`) in a single, un-partitioned block at the epoch boundary, unlike stake rewards which are spread over `num_partitions` blocks. The code explicitly documents an assumption that the number of distinct commission accounts M is "always significantly smaller than the number of delegations," but nothing enforces this — M is simply the count of distinct `commission_pubkey` values produced by `redeem_delegation_rewards`, one per distinct voter pubkey (or its designated collector) with an active, rewarded stake delegation.

### Finding Description
In `calculate_stake_rewards_and_commissions` (runtime/src/bank/partitioned_epoch_rewards/calculation.rs:780-938), each stake delegation is redeemed via `redeem_delegation_rewards`, which returns an `InflationRewardWithCommission` keyed by `commission_pubkey` — the vote account itself by default, or the vote account's configured commission collector when `custom_commission_collector` is active [1](#0-0) . These are accumulated into a `RewardCommissions` map whose size M is bounded only by the number of *distinct vote accounts* that receive nonzero rewards, with the code comment acknowledging this as an unenforced assumption: [2](#0-1) 

At distribution time, `distribute_reward_commissions` loads and rewards all M commission accounts in one pass (`load_and_reward_commission_accounts`), then calls `store_commission_accounts_partitioned`, which stores the *entire* `RewardCommissionAccounts` set to accounts DB in a single call with no partitioning across blocks, unlike `store_stake_accounts_in_partition` used for stake rewards: [3](#0-2) 

This all happens synchronously inside `begin_partitioned_rewards`, which itself runs entirely within `process_new_epoch` at the epoch-boundary block: [4](#0-3) [5](#0-4) 

An unprivileged user can create N distinct vote accounts (each satisfying the VAT-survival minimum balance, `minimum_vote_account_balance_for_vat` [6](#0-5) ), delegate the minimum stake to each (`get_minimum_delegation` = 1 SOL under the v5 stake program) [7](#0-6) , and thereby force N distinct `commission_pubkey` entries into `reward_commissions`, all processed and stored atomically in the single epoch-boundary block regardless of real validator count.

### Impact Explanation
This inflates single-block work (`load_and_reward_commission_accounts_us`, `store_commission_accounts_us` metrics) at the epoch boundary proportionally to attacker-created vote-account count rather than real validator count, since this work is not partitioned like stake rewards are. In the extreme, this could stall processing of the epoch-boundary block, matching the "validator stall on a single, atomic epoch-boundary block" impact category.

### Likelihood Explanation
Exploitability requires real, locked economic cost: each additional "fake commission node" costs the attacker roughly 1 SOL (minimum stake delegation) plus vote-account and stake-account rent-exemption reserves, and the VAT-survival threshold. This capital is not spent/burned — the attacker retains ownership and continues earning proportional stake rewards — but it must be committed and re-delegated every epoch to keep the vote account alive under VAT filtering. This makes the attack costly to scale to a magnitude sufficient to cause a meaningful stall (would require locking tens of thousands to millions of SOL to grow M into the range where per-account processing overhead becomes significant), which substantially reduces real-world feasibility compared to a "free" DoS, though the underlying architectural assumption (M ≪ N) is explicitly unenforced in code.

### Recommendation
Partition commission-account loading/storing across multiple distribution blocks the same way `store_stake_accounts_in_partition` partitions stake rewards, instead of processing the entire `RewardCommissionAccounts` set atomically in `store_commission_accounts_partitioned`/`load_and_reward_commission_accounts`. Alternatively, enforce/verify the assumed upper bound on distinct commission-collector count (e.g., by capping or rate-limiting per-epoch growth of unique reward-eligible vote accounts) so that a single user's newly created vote accounts cannot unboundedly inflate un-partitioned epoch-boundary work.

### Proof of Concept
Integration test plan (extends existing `test_store_commission_accounts_partitioned`/`test_rewards_computation` harnesses in `calculation.rs`):
1. Using `create_reward_bank_with_specific_stakes`-style helpers, create N (e.g., 10,000+) distinct vote accounts, each funded at `minimum_vote_account_balance_for_vat`, each with a unique keypair (optionally each also setting a unique `inflation_rewards_collector` via `UpdateCommissionCollector` to exercise `custom_commission_collector`).
2. Delegate `get_minimum_delegation()` lamports of stake from N distinct stake accounts, one to each vote account.
3. Advance to the epoch boundary and call `begin_partitioned_rewards` (as in `test_begin_partitioned_rewards_returns_total_capitalization_increase`), capturing `RewardsMetrics::store_commission_accounts_us` and `load_and_reward_commission_accounts_us`.
4. Assert that these metrics scale linearly (not sub-linearly/bounded) with N, and that this work is entirely contained within one block invocation of `distribute_reward_commissions`/`store_commission_accounts_partitioned` (no partition_index parameter, unlike `distribute_epoch_rewards_in_partition`), confirming the absence of any bound or partitioning mechanism relative to the number of real validators versus attacker-created vote accounts.
