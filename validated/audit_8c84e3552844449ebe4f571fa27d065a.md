## Analog Found

### Title
Uncaught Exception in `definition.js` Signature Evaluation Crashes the Node Instead of Rejecting the Invalid Unit — ([File: definition.js])

### Summary
The Reactor Netty advisory (CVE-2020-5403) describes a case where malformed input (a bad URI) causes an `URISyntaxException` that is not handled gracefully — instead of returning a proper `400 Bad Request`, the connection is torn down and the process misbehaves. The analogous class in ocore is: a malformed/unsatisfiable condition encountered while validating an already-signed unit's address definition causes the validator to `throw Error(...)` synchronously from inside an asynchronous `db.query` callback, instead of calling the error callback (`cb(...)`) that would gracefully reject the unit. Because this throw happens inside an async callback, it cannot be caught by the caller's control flow and propagates to the top-level `process.on('uncaughtException')` handler in `network.js`, which explicitly re-throws to crash the process: [1](#0-0) 

### Finding Description
`definition.js` contains two implementations of "evaluate an address definition tree":
- `validateDefinition()` — used when an address is *first defined* — handles the "definition template" op safely, returning a normal validation error via the callback if the referenced template unit can't be found or is ambiguous: [2](#0-1) 

- `validateAuthentifiers()` — used every time an *existing* address later signs a subsequent unit (i.e., normal signature/authentifier checking on every posted unit) — implements the same "definition template" op but with a bare `throw Error("not 1 template")` instead of an error callback, when the referenced template row count is not exactly 1: [3](#0-2) 

Since this code executes inside the `conn.query(...)` callback (asynchronous), the `throw` is not caught by any surrounding `try/catch` in `validateAuthor`/`validate()`. It bubbles up out of the SQL driver's callback dispatch and becomes an uncaught exception at the process level, which is caught only by the global handler in `network.js`, which deliberately re-throws to crash the process "to avoid ending up in an inconsistent state": [1](#0-0) 

This is the same bug class as CWE-755/CWE-20 in the advisory: an edge case in parsing/evaluating attacker-influenced structured input is not converted into a normal rejection path, but instead triggers an unhandled exceptional condition that terminates the connection/process.

### Impact Explanation
Any address whose definition contains a `['definition template', [unit, params]]` clause is revalidated via `validateAuthentifiers()` every single time that address signs a new unit (this is standard signature verification, run on every unit from that author, including units posted by ordinary unprivileged users). If the referenced `definition_template` unit's row lookup ever returns `!= 1` rows at validation time (e.g., the template unit is not yet present/stable in local storage — a state achievable during catch-up, hash-tree replay, syncing from a different last-ball_mci context, or if the query legitimately returns 0 rows because of reorg/instability differences between nodes), every node that processes that unit will crash instead of simply rejecting the single bad unit. This is a network-wide denial-of-validation/availability bug: a node that would otherwise return a normal `ifUnitError` becomes unable to continue processing, matching the "node disagreement on validity" / "network unable to confirm new units" impact class permitted by the rules. A single unprivileged unit poster who controls (or previously set up) an address using this definition op can reliably reproduce the crash condition on any full node that processes their unit under differing state.

### Likelihood Explanation
The "definition template" address-definition operator is a documented, user-accessible feature (any user can define their address using it), and `validateAuthentifiers()` is executed on the normal hot path of unit signature validation for every unit an address sends — not a rare corner case. The discrepancy between the safe handling in `validateDefinition()` (definition-time) and the unsafe `throw` in `validateAuthentifiers()` (signing-time) shows this is a genuine oversight rather than an intentional invariant, making it plausible to trigger under normal operational conditions such as catch-up, syncing at different tips, or minor timing/state differences between the several nodes validating the same unit.

### Recommendation
Replace `throw Error("not 1 template")` in `definition.js`'s `validateAuthentifiers()` "definition template" case with the same graceful error path used in `validateDefinition()`, i.e., invoke `cb2(false)` (or the appropriate error-signaling call for that function's error convention) when `rows.length !== 1`, so that a missing/ambiguous template unit results in a normal signature-verification failure instead of process termination. The `JSON.parse(template)` on the subsequent line should also be wrapped in a `try/catch` for the same reason, consistent with `validateDefinition()`'s handling of `replaceInTemplate`.

### Proof of Concept
1. Attacker's address `A` is defined using `['definition template', [T, {p:1}]]`, where `T` is a unit containing an `app: 'definition_template'` message. At the time `A` is first used (`validateDefinition` path), the lookup for `T` succeeds (1 row), so `A` is accepted as valid.
2. Later, address `A` signs and posts a new ordinary unit `U`. This triggers `validateAuthor` → `Definition.validateAuthentifiers` → `evaluate()` on `A`'s definition tree, hitting the `'definition template'` case in `definition.js` at lines 802-819.
3. If, due to a difference in local DB state (e.g., unit `T` not yet marked stable at this node, differing last_ball_mci, or catch-up sync ordering), the query `SELECT payload FROM messages JOIN units USING(unit) WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1` returns 0 (or >1) rows, the code executes `throw Error("not 1 template")` inside the `conn.query` callback.
4. This exception is not caught anywhere in the synchronous call chain (`validate()` in `validation.js` has no `try/catch` wrapping the async `db.query` callback chain), so it propagates to `process.on('uncaughtException')` in `network.js`, which logs it and then re-throws, crashing the node process.
5. Because different nodes may have slightly different local views of stability/sync progress when this unit propagates, an attacker can reliably cause a fleet-wide crash of full nodes processing unit `U`, contrasted with the intended behavior of simply rejecting `U` as invalid via `ifUnitError`.
