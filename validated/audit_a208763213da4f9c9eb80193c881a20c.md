### Title
Webhook signature check can be silently bypassed for organizations with no `webhook_secret`, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using an **attacker-controlled field from the same unauthenticated JSON body** (`repository.owner.login` or `organization.login`), then calls `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` when that organization's `webhook_secret` is blank/unset. Since `docs/setup.md` documents the webhook secret as **optional**, any Shipit installation using multi-organization GitHub App config (`Shipit.github(organization:)`) with at least one organization missing a secret allows an unauthenticated attacker to submit a completely forged webhook payload for that organization — including a `membership` event that creates `Team`/`Membership` records used by `User#authorized?` to gate application access.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the "authenticating" organization purely from the untrusted request body (`repository.owner.login` or `organization.login`): [2](#0-1) 

`GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb`: [3](#0-2) 
returns `true` immediately if `webhook_secret` is not present for that organization's config — i.e. no HMAC check is performed at all, and the payload is accepted regardless of content or the missing `X-Hub-Signature` header.

`lib/shipit.rb#github` resolves per-organization configuration keyed by the same attacker-supplied organization string: [4](#0-3) 

`docs/setup.md` explicitly documents the webhook secret as optional: [5](#0-4) 

This breaks the intended binding: **"organization that authenticated the webhook" == "organization whose data is trusted and acted upon."** If any configured organization has no secret set, the "authentication" step is a no-op for that organization, and every handler dispatched by `Shipit::Webhooks.for_event` — including `MembershipHandler`, which creates `Team` and `Membership` records — will process fully attacker-forged payloads for that organization's namespace.

`Membership`/`Team` records populated by the `membership` webhook feed directly into `User#authorized?`, which is the sole authorization gate for the whole application in `app/controllers/concerns/shipit/authentication.rb`: [6](#0-5) [7](#0-6) 

By forging a `membership` event ("action": "added", team belonging to `Shipit.github_teams`, member login = attacker's own Shipit login) against an organization lacking a webhook secret, an attacker can add themselves (or any known login) to a `Team` that `Shipit.github_teams` authorizes, satisfying `authorized?` and gaining full authenticated access to Shipit without any real GitHub team membership or valid GitHub credentials.

### Impact Explanation
This is an authentication-bypass / privilege-escalation into `Shipit.github_teams` authorization — one of the accepted High-severity impacts. It requires no GitHub credentials, no valid HMAC signature, and no prior session — only knowledge that an organization configured in `secrets.github` lacks a `webhook_secret` (a supported, documented configuration).

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: the risk only materializes for organizations configured without a `webhook_secret` in a multi-org `secrets.github` setup. Since the setup guide marks the secret as optional and does not warn about this consequence, misconfigured/negligent deployments are plausible, especially for secondary or newly-added organizations added later without updating secrets. This is a config-dependent but code-enabled flaw: the engine itself provides no compensating control (e.g. it does not require organizations to have a webhook secret, nor does it cross-check `repository`/`organization` identity against any other authenticated channel).

### Recommendation
- In `GitHubApp#verify_webhook_signature`, do not silently return `true` when `webhook_secret` is blank; instead fail closed (reject the webhook) unless the app explicitly opts into signature-less mode via a distinct, clearly-named configuration flag.
- Require `webhook_secret` to be present for every entry in `secrets.github` when using the multi-organization schema, and raise a startup/config error otherwise.
- Consider validating that the organization derived for signature selection (`repository_owner`) matches the organization embedded in `repository.full_name` before handlers execute, so a single compromised/misconfigured organization cannot influence unrelated repository data.

### Proof of Concept
1. Deploy Shipit with multi-organization GitHub App config in `secrets.github`, where organization `victim-org` has `webhook_secret` unset (permitted per `docs/setup.md`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Trusted Team", "slug": "trusted-team", "url": "..." },
  "member": { "login": "attacker-shipit-login" },
  "organization": { "login": "victim-org" }
}
```
3. `verify_signature` resolves `repository_owner` = `"victim-org"`, calls `Shipit.github(organization: "victim-org").verify_webhook_signature(...)`, which returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `MembershipHandler` processes the forged payload, creating/updating `Team` "trusted-team" and adding `attacker-shipit-login` as a member.
5. If `Shipit.github_teams` includes `victim-org/trusted-team`, the attacker's Shipit `User` record now satisfies `authorized?` (`app/models/shipit/user.rb:80-82`), granting full application access on their next GitHub OAuth login — bypassing the intended team-membership authorization check entirely.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
