Found a concrete analog: a scoped `ApiClient` token (one restricted to a single stack) can be used to read information about an *arbitrary other stack* through `Shipit::Api::CCMenuController`, because that controller bypasses the stack-scoping check that every other API controller relies on.

### Title
Stack-scoped ApiClient tokens can read any stack's build status via CCMenuController, bypassing token stack-scope binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the stack(s) it is allowed to touch: `stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves the requested `stack_id` param against that restricted relation. `Shipit::Api::CCMenuController` overrides `stack` to resolve directly against the unrestricted `Stack` relation, discarding the client's `stack_id` scope entirely, while still passing the generic `require_permission :read, :stack` check that only verifies the permission name, not the scope binding.

### Finding Description
`BaseController` defines the intended trust boundary as an equality: `current_api_client.stack_id == stack.id` (when the client is stack-scoped). [1](#0-0) 

`require_permission!`/`check_permissions!` only validate that the token carries the `read:stack` permission string — they never look at `stack_id`, so scope enforcement depends entirely on the `stacks`/`stack` helpers being used. [2](#0-1) [3](#0-2) 

`CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of going through the scoped `stacks` relation, so the `current_api_client.stack_id` restriction is never applied here: [4](#0-3) 

Before the request: the token is authorized only for `stack_id = A` (its own stack). After the request: `CCMenuController#show` returns build/deploy status for `stack_id = B`, any stack in the installation, because `stack` no longer filters by `current_api_client.stack_id`. The equality `token.stack_id == stack.id` that holds in every other API controller (`Shipit::Api::StacksController`, `LocksController`, `MergeRequestsController`, etc., which all use the inherited `stack`/`stacks` helpers) is broken specifically in `CCMenuController`.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: a token deliberately restricted to one stack (e.g. the `here_come_the_walrus` fixture scoped to `shipit`) can be replayed against `GET /api/stacks/:stack_id/ccmenu.xml` for any other stack to read its `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc. This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output" from a credential whose entire purpose is to be scoped to a single stack.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a normal, low-privilege credential intentionally minted to only see one stack, e.g. via `CCMenuUrlController#fetch` or manually via the admin UI) can trigger this simply by changing the `stack_id` path parameter — no additional secret, signature, or elevated permission is needed beyond the token they already legitimately hold for their own stack.

### Recommendation
Have `CCMenuController#stack` resolve through the scoped `stacks` relation (as `BaseController#stack` does) instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` binding is enforced consistently across all API controllers.

### Proof of Concept
1. Create (or have) a stack-scoped `ApiClient` with `stack_id` set to stack A and `permissions: ['read:stack']` (this is exactly how `here_come_the_walrus` / `CCMenuUrlController#client` tokens are minted). [5](#0-4) 
2. Using that token's `authentication_token` as the `token` query param, call `GET /api/stacks/<stack-B-param>/ccmenu.xml` for a different stack B that the client was never granted access to.
3. Observe `require_permission :read, :stack` passes (the token does have `read:stack`), and `CCMenuController#stack` returns stack B via `Stack.from_param!`, bypassing the `stacks` scoping used everywhere else, returning stack B's build/deploy status in the response body.
