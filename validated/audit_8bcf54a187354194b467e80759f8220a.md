### Title
Uncaught exception in `readDataFeedValue`'s sort comparator crashes the node when unstable AA data-feed candidates tie - ([File: data_feeds.js])

### Summary
`data_feeds.js` builds a list of unstable, not-yet-stable data-feed candidates when an AA formula evaluates `data_feed[[...]]`/`in_data_feed[[...]]` with an "unstable" option. When more than one candidate is found and they tie exactly on `latest_included_mc_index` and `level` (and `bIncludeAllUnstable` is false), the comparator passed to `Array.prototype.sort()` executes `throw Error("can't sort candidates ...")` synchronously inside the sort call, rather than returning an error through the callback chain used everywhere else in this code path.

### Finding Description
`readDataFeedValue()` collects unstable data-feed messages from `storage.assocUnstableMessages` authored by the oracle address(es) referenced in an AA's `data_feed[[...]]` expression: [1](#0-0) 

When several candidates are found and `ifseveral` is not `'abort'`, they are sorted to pick the most recent one. The comparator throws a plain `Error` (not routed through `handleResult`/`cb`) if two candidates cannot be strictly ordered by `latest_included_mc_index` and `level`: [2](#0-1) 

This throw happens synchronously from inside `[].sort()`, which is called synchronously inside the `data_feed`/`in_data_feed` opcode handling of the oscript formula evaluator (`formula/evaluation.js`), which itself runs synchronously inside `aa_composer.handleTrigger` → `evaluateAA`/`evaluate` during AA-trigger processing (`aa_composer.js`, e.g. `handleTrigger`/`evaluateAA` at lines 589-618, 1841-1888). None of these layers wrap formula evaluation in a `try/catch`; they use callback-passing style, expecting all failure paths to call back with an error rather than throw. An uncaught exception thrown synchronously from deep inside this callback chain propagates up through the event loop and is caught only by the top-level `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly rethrows to crash the process: [3](#0-2) 

Two unstable messages tie when they are authored by units with identical `latest_included_mc_index` and identical `level` — this is achievable by an ordinary user (an AA trigger sender, or the oracle addresses referenced by an AA) by posting two sibling units (same set of parents, thus same level and latest_included_mc_index) each carrying a `data_feed` message for the same `feed_name`/oracle address(es) that the target AA reads with the unstable option and a non-`'abort'` `ifseveral`. When the AA trigger causes evaluation of that `data_feed[[...]]` expression before either of the two units stabilizes, `readDataFeedValue` collects both as tied candidates and throws.

### Impact Explanation
Because the throw is not caught anywhere in the callback chain and is only intercepted by the network-level `uncaughtException` handler that intentionally rethrows to crash the process, any full node that evaluates the crafted AA trigger dies. Since AA trigger evaluation is deterministic and must be performed identically by every full node in order to reach agreement on AA responses/state, an attacker can craft a unit (trigger) that reliably crashes every full node that processes it — a network-wide denial of service preventing the network from confirming new units, directly matching the "hang or frequently repeatable crash (complete DOS)" impact of CVE-2021-2410.

### Likelihood Explanation
The trigger conditions are fully attacker-controlled and require no special privileges: post two sibling units carrying `data_feed` messages from the addresses referenced in a target AA's oscript, arrange for them to have identical `level`/`latest_included_mc_index` (trivial — same parents), and send a payment/trigger to the AA that reads that feed with `[unstable]` (or an equivalent unstable option) and a default (non-`'abort'`) `ifseveral`. This is a normal usage pattern for oracle-driven AAs, making the precondition realistic and easily reproducible by any user able to post units and control (or impersonate as) the oracle addresses an AA trusts, or by an AA author who designs their own AA to read feeds from addresses they control.

### Recommendation
Replace the `throw Error(...)` in the sort comparator in `readDataFeedValue` (data_feeds.js, around line 266) with a deterministic tie-break (e.g., fall back to comparing `unit` hash lexicographically, mirroring how `bIncludeAllUnstable` already breaks ties) instead of throwing, and/or wrap AA formula evaluation entry points (`aa_composer.handleTrigger`/`evaluateAA` and `formulaParser.evaluate`) in defensive `try/catch` that converts unexpected exceptions into a formula "fatal_error"/bounce rather than letting them propagate to `uncaughtException`.

### Proof of Concept
1. Deploy an AA whose oscript reads `data_feed[[oracles=ORACLE_ADDR, feed_name='x', ifseveral='last']]` (or omit `ifseveral`, using the default) with the `[unstable]`/`all_unstable` option, and includes it in the trigger's execution path.
2. As the oracle (or as any user able to post from `ORACLE_ADDR`, or if the AA is designed to read the feed from multiple untrusted addresses), post two sibling units U1 and U2 with identical parent sets (so their `level` and `latest_included_mc_index` match) that both post `data_feed` messages with `feed_name: 'x'` before either stabilizes.
3. Send a trigger unit to the AA before U1/U2 stabilize, causing `handleTrigger` → `evaluateAA` → formula evaluation of the `data_feed[[...]]` expression to call `dataFeeds.readDataFeedValue` with `bIncludeUnstableAAs=true`.
4. `arrCandidates` contains two tied entries; the comparator's `throw Error("can't sort candidates ...")` executes synchronously, propagating out of `Array.prototype.sort`, out of `evaluate`, and up to the top-level `uncaughtException` handler in `network.js`, which rethrows and crashes the node process. Every full node that processes this trigger the same way crashes identically.
