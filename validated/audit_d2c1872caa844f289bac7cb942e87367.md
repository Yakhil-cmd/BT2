## Analysis

The SQLBot CVE is a cross-tenant IDOR/authorization-bypass: an endpoint accepts an object reference (a data-source/schema ID) from a caller and operates on it without verifying that the caller is actually authorized to act on that object in its own tenant/workspace. The closest analog in `Camomtat/ocore--016` is in the wallet device-message handling for shared addresses, where a resource that includes "my address" is registered on behalf of the owner without validating that the requester went through the authorization/consent workflow that the protocol itself defines for that purpose.

### Title
Unauthenticated registration of shared-address definitions bypasses the approval workflow, allowing a paired device to bind a victim's address into an attacker-controlled spending condition - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress` (invoked directly from the `"new_shared_address"` device-message subject) inserts a new `shared_addresses`/`shared_address_signing_paths` record as soon as it can verify that *some* address inside the submitted definition belongs to the recipient's wallet. It never checks that the recipient actually participated in and approved that specific definition through the intended `create_new_shared_address` → `approve_new_shared_address` handshake.

### Finding Description
The protocol defines an explicit two-step consent flow for creating a shared (e.g., multisig) address:
1. `"create_new_shared_address"` — triggers a confirmation dialog for the user to approve participation [1](#0-0) 
2. `"approve_new_shared_address"` — records the user's explicit approval for a specific `definition_template_chash` [2](#0-1) 

However, the `"new_shared_address"` subject bypasses this entirely and calls `walletDefinedByAddresses.handleNewSharedAddress(body, …)` directly with no confirmation step: [3](#0-2) 

Inside `handleNewSharedAddress`, the only ownership-style check performed is `determineIfIncludesMeAndRewriteDeviceAddress`, which merely queries whether any address referenced in `body.signers` exists in `my_addresses` (or `shared_addresses`) — i.e., it treats "my address appears somewhere in the definition" as sufficient authorization to accept the whole definition and store it: [4](#0-3) [5](#0-4) 

`validateAddressDefinition` only checks generic structural validity of the definition (must contain a signature branch, complexity limits) via `Definition.validateDefinition`; it does not check whether the composition is an `"and"` (true multisig) or an `"or"` (single-key spend) condition: [6](#0-5) 

As a result, any paired correspondent device (an "unprivileged" peer, analogous to the low-privilege caller in the SQLBot IDOR) can:
1. Pick one of the victim's known addresses `V_ADDR`.
2. Build a definition such as `["or", [["address", V_ADDR], ["address", A_ADDR]]]`, where `A_ADDR` is attacker-controlled.
3. Compute `shared_address = chash160(definition)` and send a `"new_shared_address"` message referencing `V_ADDR` as one of the signers.
4. The victim's node silently accepts and stores this as a legitimate shared address it partially controls — without any UI confirmation, and without confirming this matches any `pending_shared_addresses` record the victim actually approved via the honest flow.

This is directly analogous to the reported bug class: a resource (the shared-address "ownership" record binding the victim's address into a new spending condition) is created/modified by an unauthorized party purely because the request references an object (address) the party doesn't actually control, with no verification that the acting party is entitled to bind that address into the new structure.

### Impact Explanation
If the victim (or the victim's automated tooling) is subsequently induced to fund the resulting `shared_address` — believing it to require joint authorization because it now appears among their known/controlled addresses — the attacker can unilaterally spend from it using the `"or"` branch, resulting in unauthorized spending/fund loss without the victim's cosigner participation. This mirrors the CVE's core impact: legitimate protections designed to gate access/modification to authorized owners are bypassed via direct object reference.

### Likelihood Explanation
The attack requires only an existing device pairing (no elevated privileges, no special node role), a single crafted message, and the address-composition logic already documented in the client. No cryptographic breaks are needed; only the missing binding between `"new_shared_address"` and a prior, user-approved `pending_shared_addresses` record must be exploited, which is a straightforward, unauthenticated protocol-level gap.

### Recommendation
`handleNewSharedAddress` should refuse to create a shared address unless there is a corresponding `pending_shared_addresses`/`pending_shared_address_signing_paths` record that the local user already approved (matching `definition_template_chash` and device_addresses), similar to what `approvePendingSharedAddress` already tracks. Alternatively, require explicit user confirmation before persisting any inbound `"new_shared_address"` message, exactly as is already done for `"create_new_shared_address"`.

### Proof of Concept
1. Pair attacker device `A` with victim device `V` (ordinary correspondent pairing).
2. `A` learns one of `V`'s addresses, `V_ADDR` (addresses are not secret).
3. `A` builds `definition = ["or", [["address", V_ADDR], ["address", A_ADDR]]]`, computes `shared_address = objectHash.getChash160(definition)`.
4. `A` sends device message `{subject: "new_shared_address", body: {address: shared_address, definition, signers: {"r.0": {address: V_ADDR}, "r.1": {address: A_ADDR}}}}`.
5. On `V`'s node, `handleMessageFromHub` routes to `walletDefinedByAddresses.handleNewSharedAddress`, which stores the shared address without any confirmation dialog, listing `V_ADDR` as a member. [3](#0-2) [5](#0-4) 
6. If `V` funds `shared_address`, `A` can spend it alone via the `"or"` branch, without `V`'s cooperation.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
