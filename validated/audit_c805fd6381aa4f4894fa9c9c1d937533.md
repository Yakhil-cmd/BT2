## Finding

### Title
Webhook signature verification binds to an attacker-chosen organization field instead of the repository actually mutated by the handler, enabling cross-organization Status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on an **unauthenticated field of the very payload it is about to verify** (`repository.owner.login`, or `organization.login` as fallback). Handlers that consume the payload, most notably `StatusHandler`, then act on data (a commit's SHA) that is **not scoped to that same organization at all**. This breaks the equality that should hold: `organization whose secret produced a valid signature == organization/repository whose state gets written`. In a multi-tenant Shipit deployment (explicitly supported and documented) an actor who legitimately controls one onboarded GitHub organization's webhook secret can forge a `status` webhook that writes CI status onto a commit belonging to a *different* organization's stack.

### Finding Description
`Shipit` supports multiple, independently configured GitHub Apps/organizations sharing one instance, each with its own `webhook_secret`: [1](#0-0) [2](#0-1) 

For every inbound webhook, `WebhooksController#verify_signature` picks the secret to verify against using a field taken directly from the **unverified** JSON body: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` looks up per-organization config and returns a `GitHubApp` whose `verify_webhook_signature` only checks that the raw body matches an HMAC computed with *that org's* secret: [5](#0-4) [6](#0-5) 

Nothing ties the organization used to select the secret to the resource the handler will actually mutate. `StatusHandler`, in particular, does not scope to a repository at all — it queries commits globally by SHA: [7](#0-6) 

Other handlers (e.g. `PushHandler`) do scope via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, but that `full_name` field is again just another attacker-controlled field of the same JSON body used to pick the signing org, so it can be set independently of `repository.owner.login`: [8](#0-7) [9](#0-8) 

This mirrors the reported bug class exactly: a security-relevant check (`onlyComptroller` / `verify_signature`) is bound to the wrong entity — a permission/identity that does not correspond to the object actually being written (`UserManager` state / a victim organization's `Commit`).

### Impact Explanation
Any actor who legitimately possesses (or has been issued) the `webhook_secret` for **one** organization configured in a multi-tenant Shipit instance can forge a valid `X-Hub-Signature` for a `status` event payload, because `verify_signature` only proves "a payload was signed with some known org's secret," not "this payload's target repository belongs to that org." Because `StatusHandler#process` resolves target commits with an unscoped `Commit.where(sha: params.sha)`, the forged event can create a `Status` (state, context, target_url) on any commit across **any stack in the instance**, including stacks that belong to completely unrelated GitHub organizations the attacker has no access to. Since Shipit uses commit statuses to determine `deployable?`/required-status gating for deploys and the merge queue, this is a cross-repository write of security-relevant state that can be used to fabricate a passing CI check and clear the path for an unauthorized deploy of a victim stack — matching the Critical-tier impact categories (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
This requires no Shipit session, API token, or GitHub App private key — only the `webhook_secret` of any single organization already onboarded to the same multi-tenant Shipit instance (a normal, low-privilege credential the attacker's own organization legitimately holds). Multi-organization configuration is a first-class, documented deployment mode, so this is a realistic configuration, not a hypothetical one.

### Recommendation
Bind signature verification to the resource actually mutated by the handler rather than to an attacker-supplied field: verify the payload's `repository.full_name` (or `organization.login` for org-scoped events) against the `Repository`/`Stack` records that already store which GitHub organization/App they belong to, and reject the webhook if the two disagree. Alternatively, scope every handler's queries (especially `StatusHandler`) to repositories that are provably associated with the organization whose secret validated the signature.

### Proof of Concept
1. Attacker operates (or was issued credentials for) `OrgA`, which is configured in the shared Shipit instance with its own `webhook_secret` (`secretA`), per the documented multi-org setup.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to VictimOrg/victim-repo stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully because it truly was signed with `secretA`. [10](#0-9) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with no repository/organization filter — writing a forged "success" status onto the victim's commit. [11](#0-10) 

**Note on completeness:** I could not execute this end-to-end in a live environment; the analysis is based on static review of `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/*`, `lib/shipit.rb`, and `lib/shipit/github_app.rb`. I was unable to inspect `Commit#create_status_from_github!` and `Commit#deployable?` in full within the available iterations to confirm the exact downstream gating logic that consumes forged statuses, though their names and usage in `params.require_ci` checks strongly indicate they drive deploy-eligibility decisions.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
