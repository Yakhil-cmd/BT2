## Confirmed vulnerability

### Title
Webhook signature verified against `repository.owner.login`, but events are applied to the stack identified by the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify a webhook against using `repository.owner.login` (or `organization.login`) taken from the request body. Once that check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` — used by `StatusHandler`, `PushHandler`, `CheckSuiteHandler`, etc. — looks up the target `Stack`/`Repository`/`Commit` using a *different* field from the same JSON body: `repository.full_name`. Nothing binds these two fields together.

### Finding Description [1](#0-0) 
selects the app config purely from `repository_owner`: [2](#0-1) 

`Shipit.github(organization: ...)` resolves a distinct, independently configured `webhook_secret` per organization when the engine is set up with multiple GitHub Apps, which is a documented and supported configuration: [3](#0-2) [4](#0-3) 

Once the HMAC check succeeds, `create` dispatches the entire raw JSON payload to handlers: [5](#0-4) 

Every handler resolves its target repository from `repository.full_name`, not from `repository.owner.login`: [6](#0-5) 

`StatusHandler` uses this to create/replicate a commit `Status` for whatever `sha` is supplied, sourced only from the commit table (not scoped to a particular repository/org at all beyond `full_name`‑derived stack lookup upstream via `Handler#stacks`): [7](#0-6) 

Because the entire request body is HMAC'd as one blob with `verify_webhook_signature`, an attacker cannot forge a signature without knowing *some* configured `webhook_secret`. But in the documented multi-org configuration, each GitHub organization admin is legitimately given their own `webhook_secret` (they configure/see it themselves in their own GitHub App settings) — a "keyholder" for Org A's secret can freely craft the JSON body and compute a valid HMAC over it themselves before sending it to the shared Shipit-engine endpoint. Nothing in `verify_signature` re-checks that `repository.full_name`'s owner matches `repository.owner.login`, and nothing in the handler layer re-derives the acting organization from the field that was actually verified.

This is the same trust-binding break as the CCIP bug class: the field that is cryptographically checked (`repository.owner.login`, used to pick the secret) is not the field that is subsequently acted upon (`repository.full_name`, used to find/act on the Stack). The equality the code implicitly assumes — `repository.owner.login == owner(repository.full_name)` — is never enforced.

### Impact Explanation
An administrator who legitimately controls a GitHub App/organization onboarded to this Shipit instance (and therefore knows that org's `webhook_secret`) can forge signed `status` (or `push`/`check_suite`) webhook events whose `repository.full_name` points at a *different* organization's repository/stack hosted on the same Shipit instance. Via `StatusHandler`, this lets them inject arbitrary commit `Status` records (`state`, `context`, `description`, `target_url`) for another org's commits/stacks: [8](#0-7) 
which can satisfy `ci.require`/`ci.blocking` requirements and enable/trigger continuous-delivery deploys of that other org's code: [9](#0-8) 

Falsely marking a required CI context as `success` can flip a commit from non-deployable to deployable and can trigger an automatic (continuous delivery) deploy of an unreviewed/unapproved commit on a stack belonging to a different organization than the one whose credentials were used — an unauthorized deploy crossing an organizational trust boundary, matching the "unauthorized deploy" High-impact category.

### Likelihood Explanation
This requires the Shipit instance to be configured with more than one GitHub organization/App (a documented, supported setup), and requires the attacker to be an admin/keyholder of one of those onboarded organizations (not an arbitrary unauthenticated internet attacker, but also not requiring any Shipit-specific credential such as `api_clients_secret` or a Shipit session/`ApiClient` token — only their own GitHub App's webhook secret, which they are handed by design). Given that cross-org isolation is the entire premise of a multi-tenant Shipit deployment, this is a realistic and moderately likely misuse path in any installation onboarding multiple, mutually-distrusting organizations.

### Recommendation
In `WebhooksController#verify_signature`/`create`, or in `Webhooks::Handlers::Handler`, cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` before dispatching to handlers, and reject the event (422) on mismatch.

### Proof of Concept
1. Shipit-engine is configured with two GitHub organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. `OrgA`'s administrator (who legitimately knows `OrgA`'s `webhook_secret` from their own GitHub App settings) crafts a `status` event JSON body with:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
   - `sha = <a commit sha belonging to an OrgB-owned stack>`, `state = "success"`, `context = "ci/required-context"`
3. They compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` themselves and POST to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` from `repository.owner.login`, verifies successfully against `OrgA`'s secret.
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (reachable via the OrgB stack, whose lookup elsewhere in the handler chain uses `repository.full_name`) and creates a `success` `Status` for the OrgB commit, satisfying `ci.require`, potentially triggering a continuous-delivery deploy on the OrgB stack — despite the request only being authenticated as belonging to OrgA.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
