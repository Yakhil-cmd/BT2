### Title
`Command#unbundled_env` lets attacker-controlled `machine_env` (from `shipit.yml`) override `PATH`, enabling binary hijack on the deploy host - (File: `lib/shipit/command.rb`)

### Summary
`Command#unbundled_env` builds the spawn environment by merging `BASE_ENV`, then the safe `PATH`, and finally `@env` last, so any `PATH` key present in `@env` silently overwrites the intended `PATH`. `@env` is populated in `TaskCommands#env` from `deploy_spec.machine_env`, which is read directly out of the deployed repository's `shipit.yml`, giving an attacker who controls that file control over the `PATH` used by every subsequent unqualified command (`git`, `bundle`, etc.) run by `PTY.spawn`.

### Finding Description
The binding that should hold is:
`Command#unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every `Command`, regardless of `@env`.

Instead, in [1](#0-0) , the method computes:
```
BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
```
`.merge(@env.stringify_keys)` is applied last, so any `'PATH'` key inside `@env` wins over the safe value, and this merged hash is passed straight to `PTY.spawn` in [2](#0-1) .

`@env` is not a fixed, trusted hash — it is built per task in [3](#0-2) , which merges, among other things, `.merge(deploy_spec.machine_env)`. `deploy_spec.machine_env` reads directly from the parsed `shipit.yml` config via `config('machine', 'environment')` in [4](#0-3) , and `DeploySpec::FileSystem` loads that config from the checked-out repository content (`@app_dir`/`load_config`), as seen in [5](#0-4) . There is no key filtering: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb`) is a distinct whitelist mechanism used for task-definition variables, not applied to `machine_env`, so nothing strips or rejects a `PATH` key placed under `machine: {environment: {PATH: ...}}` in `shipit.yml`.

Exploit flow: an attacker who can get their commit deployed (e.g. a PR merged to the tracked branch, or their own repository added as a Shipit stack) places in `shipit.yml`:
```yaml
machine:
  environment:
    PATH: "/tmp/evil:/usr/bin:/bin"
```
and also drops a malicious `git` (or `bundle`) executable at `/tmp/evil/git` in the deploy working directory via the same commit. On the next deploy, `TaskCommands#env` merges this into `@env`, `Command#unbundled_env` lets it clobber `PATH`, and `PTY.spawn` executes subsequent unqualified commands (`git ...`, `bundle ...`) using the attacker's `PATH`, causing the attacker's binary to run with the privileges of the Shipit deploy host process.

No existing guard intercepts this: `verify_signature`/webhook checks are irrelevant (this isn't a webhook path), `EnvironmentVariables#permit` isn't invoked on `machine_env`, and `Command` itself performs no key exclusion when merging `@env`.

### Impact Explanation
This is Critical: arbitrary command execution on the deploy host under the Shipit deploy process's privileges, achievable by manipulating `shipit.yml`/repo content within a single stack. Blast radius is bounded to the stack whose repository content is compromised, but that includes full RCE, exfiltration of any secrets available to the deploy process (e.g. `GITHUB_TOKEN`, deploy credentials), and could pivot further depending on host configuration.

### Likelihood Explanation
Requires the attacker's commit (containing a modified `shipit.yml` and a malicious "git"/"bundle" binary) to actually be checked out and deployed by Shipit — i.e., merged to the tracked branch or the attacker controls a repo already onboarded as a Shipit stack. For a repo whose Shipit stack tracks a protected branch, this needs a merge (not just an open PR), but for less-protected stacks/branches, an attacker who can push directly can trigger this without further privilege. Cost is low (just crafting `shipit.yml` + a script) and it's fully repeatable on every deploy of that stack.

### Recommendation
In `Command#unbundled_env`, compute `PATH` last so it cannot be overridden by `@env`:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")
end
```
Additionally, consider filtering/rejecting a `PATH` key from `deploy_spec.machine_env`/`@task.env` before it ever reaches `Command.new(..., env: ...)`, to fail loudly rather than silently drop attacker-supplied `PATH`.

### Proof of Concept
Add to `test/unit/command_test.rb`:
```ruby
test "#unbundled_env does not allow @env to override PATH" do
  command = Command.new('git status', env: { 'PATH' => '/tmp/evil:/usr/bin' }, chdir: '.')
  expected_prefix = Shipit.shell_paths.join(':')
  assert command.unbundled_env['PATH'].start_with?(expected_prefix),
    "expected PATH to start with #{expected_prefix}, got #{command.unbundled_env['PATH']}"
  refute command.unbundled_env['PATH'].start_with?('/tmp/evil'),
    "PATH was overridden by attacker-controlled env"
end
```
Currently this assertion fails because `unbundled_env['PATH']` equals `/tmp/evil:/usr/bin`, confirming the override.
