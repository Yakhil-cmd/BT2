### Title
Authorization Bypass via User-Controlled `wallet` Key in `my_xpubkey` Device Message — ([File: wallet_defined_by_keys.js])

### Summary
The `my_xpubkey` device-message handler accepts an attacker-supplied `wallet` identifier and inserts/updates an `extended_pubkeys` row for that wallet using only the sender's own `device_address`, without ever verifying that the sending device is one of the cosigners defined for that wallet. This mirrors the Liferay IDOR pattern (CWE-639): a caller-supplied key (`wallet`) is used to reach a record belonging to a scope (another user's/tenant's multisig wallet) that the caller was never authorized to join.

### Finding Description
`wallet.js` explicitly allows the `my_xpubkey` subject from **non-correspondents**: [1](#0-0) 

It performs only basic string-length checks and then forwards `body.wallet` (fully user-controlled) straight into `walletDefinedByKeys.addDeviceXPubKey`, using `from_address` (the sender's own device address, also attacker-controlled) as the cosigner key: [1](#0-0) 

`addDeviceXPubKey` performs no authorization check that `wallet` was ever offered to, or that `device_address` is part of, the wallet's `wallet_definition_template`/`wallet_signing_paths`. It simply does an `INSERT IGNORE` followed by an `UPDATE ... WHERE wallet=? AND device_address=?`: [2](#0-1) 

This is asymmetric with the sibling handler `create_new_wallet` (`handleOfferToCreateNewWallet`), which *does* validate the sender against the wallet definition template before accepting cosigner data: [3](#0-2) 

No equivalent `validateWalletDefinitionTemplate` (or membership) check exists in `addDeviceXPubKey`. The `wallet` id is simply `sha256(xPubKey)` (a deterministic, guessable/derivable value, not a secret) chosen at wallet-creation time: [4](#0-3) 

Because `wallet` acts as the sole "key" scoping the `extended_pubkeys` and downstream approval logic (`checkAndFullyApproveWallet` / `checkAndFinalizeWallet`), an unauthorized device can inject rows into another party's wallet state: [5](#0-4) 

The same missing-authorization pattern also affects `handleNotificationThatWalletFullyApproved` (subject `wallet_fully_approved`, also whitelisted for non-correspondents) and `cancel_new_wallet` (via `deleteWallet`), all keyed only by attacker-supplied `wallet`: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because the `UPDATE` in `addDeviceXPubKey` is scoped to `WHERE wallet=? AND device_address=?`, an attacker can only write rows keyed by their **own** device address — they cannot overwrite an existing legitimate cosigner's `extended_pubkey`. However, this still lets an unauthorized/unpaired device:
- Insert itself into the `extended_pubkeys` table of a wallet it was never invited to cosign, polluting local wallet state on the victim's node (denial-of-service / confusion of local multisig approval bookkeeping such as `checkAndFullyApproveWallet`/`checkAndFinalizeWallet`).
- Send a spoofed `cancel_new_wallet` for any `wallet` id it can compute/guess, causing `deleteWallet` to run — though this is gated by `approval_date IS NULL AND device_address` matching an existing member row, limiting effectiveness for wallets whose full definition the attacker doesn't already partially participate in.

I could not fully confirm within the available context whether this can be escalated further (e.g., into actual fund loss or supply/definition corruption) because I was unable to inspect `deriveAddress`/`recordAddress` in `wallet_defined_by_keys.js` (I ran out of iterations before reading them) to determine whether `extended_pubkeys` entries feed into real shared-address derivation independent of `wallet_signing_paths`. Based on what is visible, the primary confirmed effect is state pollution / approval-bookkeeping confusion for wallets the attacker is not a legitimate cosigner of, rather than a demonstrated unauthorized-spend or double-spend path.

### Likelihood Explanation
The `wallet` identifier is not secret — it's a deterministic hash of an xPubKey shared during wallet setup and can appear in various device messages, logs, or be derived by a participant/observer of any part of the multisig setup flow. The `my_xpubkey` and `wallet_fully_approved` subjects are explicitly whitelisted to be accepted from **non-correspondents** (`arrSubjectsAllowedFromNoncorrespondents`), meaning any device that can reach the hub can send this message without ever pairing with the target, significantly raising reachability compared to a typical authenticated-only threat model.

### Recommendation
In `addDeviceXPubKey`, `handleNotificationThatWalletFullyApproved`, and `deleteWallet`, verify that `device_address` (the sender) is actually one of the device addresses derived from the wallet's stored `definition_template` (i.e., reuse the same `validateWalletDefinitionTemplate`/membership check used in `handleOfferToCreateNewWallet`) before performing any INSERT/UPDATE/DELETE keyed by the attacker-supplied `wallet` value. Reject the message if the sender is not an expected cosigner for that wallet.

### Proof of Concept
1. Attacker device (not paired with victim, and not a cosigner of victim's wallet `W`) obtains/derives the `wallet` id `W = sha256(victim_xPubKey)` (e.g., overheard from a `create_new_wallet`/`my_xpubkey` message exchanged between victim and a real cosigner, or otherwise learned).
2. Attacker sends a device message to the victim's hub/device:
   `{"subject":"my_xpubkey","body":{"wallet": W, "my_xpubkey": "<attacker xpubkey>"}}`.
3. Because `my_xpubkey` is in `arrSubjectsAllowedFromNoncorrespondents` [1](#0-0) , the victim's node processes it without requiring the attacker to be a correspondent.
4. `walletDefinedByKeys.addDeviceXPubKey(W, attacker_device_address, attacker_xpubkey, ...)` runs with no check against `W`'s actual `wallet_definition_template`, inserting/updating a row in `extended_pubkeys` for `W` keyed by the attacker's device address [2](#0-1) .
5. This triggers `checkAndFullyApproveWallet(W, ...)` [5](#0-4) , altering the victim's local approval bookkeeping for a wallet the attacker was never invited to join.

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

function deleteWallet(wallet, rejector_device_address, onDone){
	db.query("SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?", [wallet, rejector_device_address], function(rows){
		if (rows.length === 0) // you are not a member device
			return onDone();
		if (rows[0].approval_date) // you've already approved this wallet, you can't change your mind
			return onDone();
		db.query("SELECT device_address FROM extended_pubkeys WHERE wallet=?", [wallet], function(rows){
			var arrMemberAddresses = rows.map(function(row){ return row.device_address; });
			var arrQueries = [];
			db.addQuery(arrQueries, "DELETE FROM extended_pubkeys WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallet_signing_paths WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallets WHERE wallet=?", [wallet]);
			// delete unused indirect correspondents
			db.addQuery(
				arrQueries, 
				"DELETE FROM correspondent_devices WHERE is_indirect=1 AND device_address IN(?) AND NOT EXISTS ( \n\
					SELECT * FROM extended_pubkeys WHERE extended_pubkeys.device_address=correspondent_devices.device_address \n\
				)", 
				[arrMemberAddresses]
			);
			async.series(arrQueries, function(){
				eventBus.emit('wallet_declined', wallet, rejector_device_address);
				onDone();
			});
		});
	});
}

function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[xPubKey, wallet, device_address],
				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}

				}
			);
		}
	);
}
