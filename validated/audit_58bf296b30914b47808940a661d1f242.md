### Title
API requests can impersonate any Shipit user via the unverified `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The external report's root cause is a trust binding that is asserted but never actually verified before it is acted upon: the SCW "pays" (transfers tokens) but the contract never checks whether the claim/credit that is later relied upon (settlement, refund) is tied to a verified, still-valid session. The same class of bug — *acting on an identity claim that was never cryptographically or session-verified* — exists in the Shipit API layer, where the acting `User` for privileged operations (deploy, rollback, lock, merge, task trigger/abort) is derived from a bare HTTP header (`X-Shipit-User`) instead of the authenticated principal bound to the request.

### Finding Description
`Shipit::Api::BaseController` authenticates the *caller* via a signed `ApiClient` token (HMAC-verified through `ApiClient.authenticate`/`SimpleMessageVerifier`): [1](#0-0) 

However, the `current_user` used for attribution and for driving privileged model methods is derived from a completely separate, unauthenticated code path: [2](#0-1) 

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

The binding being broken is: **`ApiClient` token authenticates the caller** ≠ **the `User` acted on behalf of for the operation**. `X-Shipit-User` is a client-supplied request header with no signature, no proof of GitHub identity, and no session tie — the engine's own signing mechanisms (`ApiClient#authentication_token`, `Hook::DeliverySigner`) are never applied to it. Any holder of a valid `ApiClient` token (even one scoped only to `deploy:stack`/`lock:stack`/`read:stack` permissions on a single stack) can set this header to the login of any `Shipit::User` row (e.g., an admin, a member of `Shipit.github_teams`, or a CI bot account) and have all resulting actions attributed to, and executed "as", that user.

This `current_user` is passed directly into privileged model operations:
- `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [4](#0-3) 
- `stack.lock(params.reason, current_user)` [5](#0-4) 
- `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [6](#0-5) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)` [7](#0-6) 

### Impact Explanation
This breaks the equality "authenticated principal == acting `User`", which is the same misbinding pattern flagged in the source report ("paid tokens" attributed to one identity, but the settlement/refund path trusts an unverified identity claim). Concretely, an `ApiClient` token — which is scoped only to specific permissions/stacks by design — can be used to impersonate *any* `User` record, including users that are members of `Shipit.github_teams` (the engine's authorization group used to gate the web UI, per `app/controllers/concerns/shipit/authentication.rb` and `app/models/shipit/user.rb#authorized?`). This lets a limited-permission API-client holder cause deploys, rollbacks, locks, task triggers/aborts, and PR-merge requests to be recorded and executed as an arbitrary, potentially highly-privileged user, undermining audit trails and any user-identity-based authorization or attribution used downstream (e.g., `SHIPIT_USER`/`GIT_COMMITTER_NAME` in deploy scripts, aborted_by tracking, merge attribution). This constitutes escalation into `Shipit.github_teams`-adjacent trust and an unauthorized-actor attribution on deploy/rollback/merge actions.

### Likelihood Explanation
High. Exploitation requires only possession of any valid `ApiClient` token (Basic Auth), which is the engine's normal, documented API authentication mechanism — no additional secret, TLS interception, or social engineering is needed. Setting an arbitrary header value is trivial for any HTTP client.

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity assertion for privileged operations. Either remove header-based user identification entirely and always attribute API-triggered actions to the `ApiClient`'s `creator` (which is already authenticated and bound to the token), or require any user-impersonation header to be additionally verified (e.g., signed the same way `ApiClient#authentication_token` is signed, or tied 1:1 to a specific `ApiClient` record) and constrained by the requesting client's own permissions/scope.

### Proof of Concept
1. Obtain (or be issued) an `ApiClient` with minimal permissions (e.g., `deploy:stack` scoped to one stack), as in `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus`.
2. Send `POST /api/stacks/:id/deploys` (or `/rollbacks`, `/locks`, `/tasks/:id/trigger`, `/merge_requests/:id`) with `Authorization: Basic <api_client_token>` and header `X-Shipit-User: <login-of-privileged-user>` (any existing `Shipit::User` login, e.g. an admin/team member).
3. `identify_user` resolves `current_user` to that arbitrary `User` record without any proof the caller controls that user's GitHub/session identity.
4. The resulting `Deploy`/`Task`/lock/merge record is created with `user`/`aborted_by`/`by` set to the impersonated user, as shown in `app/controllers/shipit/api/deploys_controller.rb`, `rollbacks_controller.rb`, `locks_controller.rb`, `tasks_controller.rb`, and `merge_requests_controller.rb`.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")

          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
