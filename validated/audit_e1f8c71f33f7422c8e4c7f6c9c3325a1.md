### Title
Missing cosigner verification when handling remote "sign" requests allows any paired device to solicit signatures on shared/multisig addresses - (File: wallet.js)

### Summary
The `withdraw_collateral` bug class is "an entry point meant to be restricted to a trusted caller performs a privileged fund-affecting action while trusting caller-supplied identity/address without verifying the actual caller's authorization." The closest reachable analog in this codebase is in the `"sign"` message handler of `handleMessageFromHub` in `wallet.js`, which processes signing requests received from *any paired device* for a locally-held address (used for multisig/shared addresses). The code that was supposed to verify the requester is actually a legitimate cosigner of that address has been explicitly disabled.

### Finding Description
In `wallet.js`, the `"sign"` case of `handleMessageFromHub` handles a signing request forwarded by a peer device for an address that resolves locally (`ifLocal`) in `findAddress`. This is used for multisig ("same address hosted on several devices") and multilateral signing use cases. [1](#0-0) 

The intended access-control check — verifying that `from_address` (the device that sent the `"sign"` request) is actually a registered cosigner of the target wallet (via `extended_pubkeys`/`wallet_signing_paths`) — is present in the code but **commented out**: [2](#0-1) 

The comment explicitly states the developers disabled this check on purpose ("the commented check would make multilateral signing impossible"), meaning `callbacks.ifOk()` is invoked and the `signing_request` event is emitted for **any** device that is paired with the wallet and can reach this code path with a `body.address` that matches a locally-held address and any crafted `unsigned_unit`, regardless of whether that device is actually a registered cosigner of the wallet/address.

By contrast, the sibling `ifRemote` branch (used when forwarding a request to another device) *does* perform this exact check before proceeding: [3](#0-2) 

This is a genuine asymmetry: for locally-hosted keys, arbitrary paired devices can trigger a signing_request/handleOnlineJoint flow for a crafted unit spending from the local address, whereas for remote forwarding the same authorization is enforced. The root cause mirrors the `withdraw_collateral` issue: the entry point trusts the caller-supplied `address`/unit content and skips verifying that the sender is authorized to act on that address, relying only on downstream application logic (UI confirmation) rather than protocol-level access control.

### Impact Explanation
For shared/multisig addresses, the security model depends on the requirement that a signature request only reaches the relevant device from a legitimate cosigner, so that any human or automated confirmation step is only shown for requests plausibly originating from another party to the multisig arrangement. With this check disabled, any device paired with the target device (an "unprivileged" peer with no cosigning rights over the address) can:
- Submit a fabricated `unsigned_unit` referencing the local address as an author,
- Reach `findAddress`'s `ifLocal` branch,
- Trigger `network.handleOnlineJoint`/the `signing_request` event for a unit it fully controls the content of (including payment outputs).

In automated/unattended signing setups (e.g., wallets that programmatically respond to `signing_request` for known multisig counterparties without further verifying the requester identity), this enables an unauthorized third party to solicit a signature and potentially assemble a fully-signed transaction that spends from the shared address without genuine cooperation of an authorized cosigner — undermining the m-of-n trust assumption of the shared address and enabling unauthorized spending of collectively-held funds.

### Likelihood Explanation
Exploitability requires: (1) the attacker's device is paired as a correspondent of the victim device (a low bar — pairing is a standard, low-privilege operation), and (2) the victim's `ifLocal` signing flow completes without further application-level filtering of the requester's identity. Given the code explicitly disabled the intended check and no other check inspects the identity of the requester for local, non-shared multisig-key signing, likelihood is Medium-to-High in any deployment where signing confirmation is automated or where the UI does not independently show which requester triggered the prompt in a way the user can meaningfully validate against the actual cosigner set.

### Recommendation
Restore (or reimplement in a way compatible with multilateral signing) the cosigner-verification check before emitting `signing_request`/proceeding to `network.handleOnlineJoint` in the `ifLocal` branch of the `"sign"` handler. At minimum, verify that `from_address` is a member of `arrDeviceAddresses`/`wallet_signing_paths` (or the equivalent shared-address cosigner set) for the target address/signing path before treating the request as legitimate, mirroring the check already performed in the `ifRemote` branch at wallet.js:377.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet device (standard, low-privilege pairing).
2. Attacker crafts an `unsigned_unit` whose `authors` array includes the victim's locally-hosted shared/multisig address, with payment outputs directing funds to an attacker-controlled address.
3. Attacker sends a `"sign"` message to the victim's device with `body.address` = victim's local member address, `body.signing_path` pointing at that address's local signing key, and `body.unsigned_unit` = the crafted unit.
4. `handleMessageFromHub` → `findAddress` resolves the address locally and calls `ifLocal`, which — because the cosigner check is commented out — proceeds directly to `callbacks.ifOk()` and emits `signing_request`/calls `network.handleOnlineJoint`, without verifying that the attacker's device is an actual cosigner of the shared address.
5. If the victim's signing flow (bot/automated wallet, or a UI that does not surface enough context to detect the spoofed cosigner) proceeds to sign, the attacker obtains a signature on their crafted unit, contributing to an unauthorized transaction spending from the shared address.
