### Title
`StatusHandler#process` writes a `Status` to any `Commit` matching `sha` without verifying it belongs to the payload's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)` and never calls the inherited `Handler#stacks` or `Handler#repository_name` helpers, so it never asserts `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`. Any signed `status` webhook whose `sha` happens to collide with a commit sha stored under a different tenant's `Stack`/`Repository` will create a `Status` row against that unrelated commit.

### Finding Description
The broken binding, stated explicitly: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — this equality is **never checked**.

Code path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, after `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) checks the HMAC using `Shipit.github(organization: repository_owner)`. This only proves the payload was signed by *some* org's `webhook_secret` — the org that owns `repository_owner` in the payload — not that it is tied to any particular `Stack`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This never touches `repository_name` (`payload.dig('repository', 'full_name')`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) or `stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), unlike every other multi-tenant handler in this codebase (e.g. `PullRequest::OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ClosedHandler`, `LabelCapturingHandler` all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting — `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`, `label_capturing_handler.rb:110-114`, etc.).
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`), which unconditionally `find_or_create_by!`s a `Status` scoped to that commit's own `stack_id` (`app/models/shipit/status.rb:24-33`) — completely independent of which repository/org actually sent the webhook.

Attacker's exact request: the attacker owns/controls a GitHub repository (their own org, with a legitimate `webhook_secret` configured on Shipit for that org). They fork or otherwise produce a repository whose HEAD commit shares an identical SHA with a commit already tracked by a victim `Stack` (git commit hashes are content-addressed, so un-rebased forked commits from a public upstream retain the exact same SHA as upstream). The attacker triggers (or fabricates, since the GitHub App on their org will sign whatever payload GitHub emits for their own repo, and the signature check only validates HMAC against the attacker's own org secret) a `status` webhook: `X-Github-Event: status`, `repository.full_name` = attacker's repo, `sha` = the shared/colliding SHA, `state` = e.g. `"success"`.

Exploit flow: `verify_signature` passes because the signature is checked against the attacker's own org's `webhook_secret` (`Shipit.github(organization: repository_owner)` resolves the attacker's org). `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`. `Commit.where(sha: params.sha)` matches the victim's `Commit` row (because the sha values collide across repos). `commit.create_status_from_github!(params)` creates a `Status` on the victim's stack, changing `commit.state`/`commit.deployable?`, and firing `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`) — potentially unblocking or triggering downstream continuous-delivery logic on a stack the attacker never authenticated for.

Existing guards do not close this: `verify_signature` authenticates the *sending organization*, not the *target commit's owning repository*; `ExplicitParameters` only validates the shape of `sha`/`state`/etc, not repository ownership; there is no `subset`/`format` validator tying `Status#stack_id` to the payload's `repository.full_name`.

### Impact Explanation
An attacker can write a `Status` record (state/description/target_url/context) attributed to a commit belonging to a `Stack`/`Repository` they do not own or control, without any Shipit credentials beyond a webhook secret for their own unrelated repo. This is a cross-repository mutation of another tenant's `Commit`/`Status` state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Because `Status` writes can flip `commit.state` (`Commit#state` delegates to `status`, `app/models/shipit/commit.rb:219`) and drive `deployable?` and `schedule_continuous_delivery`, this could influence auto-merge/auto-deploy decisions on the victim stack. The attack is repeatable against any commit sha the attacker can predict or reproduce (e.g., forking a public upstream repo tracked by a victim Shipit stack, which is a normal, low-cost action for any GitHub user).

### Likelihood Explanation
Preconditions: attacker needs a repository under their control with a webhook configured to Shipit and a valid `webhook_secret` for that org (routine, low-cost setup — many CI-enabled orgs onboard themselves), and a commit sha that is also present in the victim's `Stack`. The latter is highly feasible whenever the victim's tracked repository is public and forkable, since un-modified commits retain identical SHAs across forks — no privileged access or secrets of the victim/Shipit are required. Attacker cost is a single signed POST to `/webhooks`, fully repeatable.

### Recommendation
In `StatusHandler#process`, scope commit lookup to the payload's repository via the same pattern used elsewhere: resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) and restrict `Commit.where(sha: params.sha)` to commits whose `stack_id` is in that repository's stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or a `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), so a `Status` is only ever written for commits belonging to the repository that authenticated the webhook.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style) plan:
```ruby
test "status handler does not write a Status for a commit belonging to a different repository" do
  victim_repo  = shipit_repositories(:shipit) # owns victim_stack, e.g. "shopify/shipit-engine"
  victim_stack = victim_repo.stacks.first
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  assert_not_equal 'success', victim_commit.reload.state
end
```
Before the fix: `assert_no_difference` fails (a `Status` is created) and `victim_commit.reload.state` becomes `'success'`, proving `commit.stack.repository.full_name == payload.dig('repository','full_name')` is violated. After applying the recommended repository-scoping fix, both assertions hold. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
