### Title
Signing-organization / mutation-organization confusion in webhook processing allows cross-tenant `Team` writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` selects the GitHub App (and therefore the HMAC secret) used to verify a webhook based on `repository.owner.login`, falling back to `organization.login` only when `repository` is absent. Handlers such as `MembershipHandler` independently read `params.organization.login` to decide which organization's `Team` record to create/mutate, with no cross-check against the value used for signature verification, so a single crafted payload can be verified under one organization's key while writing data attributed to a completely different organization.

### Finding Description
The broken binding, stated explicitly:
`repository_owner` (used to pick the `GitHubApp`/HMAC secret in `verify_signature`) == `params.dig('organization','login')` (used by `MembershipHandler#find_or_create_team!` to set `team.organization`)

Code path:
- `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature`, which calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` prefers `repository.owner.login` and only falls back to `organization.login` when `repository` is missing: [2](#0-1) 
- `Shipit.github` looks up per-organization config and instantiates/caches a `GitHubApp` keyed by that organization, with its own `webhook_secret`: [3](#0-2) 
- `verify_webhook_signature` trivially returns `true` if no `webhook_secret` is configured for that organization: [4](#0-3) 
- `MembershipHandler` requires and trusts `params.organization.login` on its own, independent of `repository_owner`, and writes it into `team.organization`: [5](#0-4) [6](#0-5) 

Root cause: real GitHub `membership` events never include a `repository` key (the payload is org-scoped: `action`, `scope`, `member`, `team`, `organization`, `sender`). Because the controller merely parses attacker-supplied raw JSON and never validates that the top-level `repository` key legitimately belongs to the event type, an attacker can inject an arbitrary `repository.owner.login` into a `membership` payload purely to steer HMAC-key selection, while leaving a separate, unrelated `organization.login` for the handler to trust and persist.

Exploit: An attacker who knows (a) that Shipit hosts multiple GitHub organizations and (b) that one configured organization ("secretless-org") has no `webhook_secret` set (a realistic multi-tenant misconfiguration, or one they can probe for via the 422 vs success behavior) sends:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "secretless-org"}},
  "team": {"id": 1, "name": "n", "slug": "s", "url": "u"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker"}
}
```
with `X-Github-Event: membership`. `verify_signature` resolves `repository_owner` to `"secretless-org"`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request passes with no valid signature at all. `MembershipHandler` then proceeds to `find_or_create_team!`, writing `team.organization = "victim-org"` and adding `attacker` as a team member for `victim-org` — an organization never involved in the signature check.

Why existing guards fail: `drop_unhandled_event` only checks the event name is registered, not payload consistency; `verify_signature` never compares its selected `repository_owner` against any field the handler later trusts; `ExplicitParameters` (`Handler#params`) validates types/presence of `organization.login` but has no knowledge of, or cross-check against, `repository_owner`; there is no model-level validation forcing `Team#organization` to match the org used for verification.

### Impact Explanation
An attacker can create/mutate `Team` records (and add arbitrary members to teams) for an organization ("victim-org") that was never authenticated by the webhook signature at all — the signature check silently succeeded against an unrelated, secret-less org. This is a cross-tenant authorization bypass: a payload nominally scoped to one (attacker-influenced) organization mutates another tenant's data, matching the "payload for one repository mutating another's ... team" Critical impact category. It is repeatable against any organization name the attacker chooses for `organization.login`, for every webhook delivery, as long as one org in the deployment lacks a `webhook_secret` (or the attacker otherwise knows a valid secret for some org).

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one GitHub organization configured (`Shipit.github_organizations`) with no `webhook_secret` (or with a secret the attacker has learned by other means) for the multi-org config schema to be in effect at all — the single-app "backward compatibility" schema (`github_default_organization.nil?`) always uses `secrets.github` and ignores `repository_owner`, so this issue is specific to installations using per-organization GitHub Apps. Attacker cost is a single unauthenticated HTTP POST to `/webhooks` with a `X-Github-Event: membership` header and no valid `X-Hub-Signature` needed if the target-of-selection org has no secret; otherwise the attack requires a known secret, which is out of scope for an unprivileged attacker. Given the secret-less-org precondition, the attack is trivially repeatable and cheap.

### Recommendation
- Do not use `repository.owner.login` as a fallback source for org-scoped events (like `membership`, `organization`) that don't legitimately carry a `repository` object; select the verification key from a field appropriate to the event type, and reject payloads containing unexpected top-level keys for that event.
- After signature verification, require handlers to assert that any organization/repository identifiers they act on match the organization that was used to select the verifying `GitHubApp` (i.e., enforce `repository_owner == organization.login` when both are present, or make `MembershipHandler` receive/verify against the same resolved organization used in `verify_signature`).
- Treat a missing `webhook_secret` for a configured organization as a hard misconfiguration (raise/log loudly, or refuse to process events) rather than silently returning `verified = true`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest)
test "membership payload with divergent repository.owner and organization.login writes team.organization from the untrusted field, while HMAC verification passes under a different org" do
  # secretless-org has no webhook_secret configured in Shipit.github config
  Shipit.stubs(:github).with(organization: 'secretless-org').returns(
    Shipit::GitHubApp.new('secretless-org', {}) # no webhook_secret => verify_webhook_signature always true
  )

  payload = {
    action: 'added',
    repository: { owner: { login: 'secretless-org' } },
    organization: { login: 'victim-org' },
    team: { id: 1, name: 'Team', slug: 'team', url: 'https://api.github.com/teams/1' },
    member: { login: 'attacker' }
  }.to_json

  post :create, body: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => 'sha1=deadbeef' # arbitrary/invalid, irrelevant since secret is nil
  }

  assert_response :ok

  team = Shipit::Team.find_by(github_id: 1)
  refute_nil team
  # Binding broken: verification org ("secretless-org") != write org ("victim-org")
  assert_equal 'victim-org', team.organization
  refute_equal 'secretless-org', team.organization
end
```

```ruby
    # Backward compatibility

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
