### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-stack/cross-repository status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, a query scoped by nothing but the raw sha string, and never consults `params.dig('repository', 'full_name')` or any stack/repository identifier from the payload. Any commit row in the entire Shipit installation whose sha matches the attacker-supplied value gets a status written to it via `commit.create_status_from_github!(params)`, regardless of which repository the inbound webhook was actually generated for.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` is never asserted anywhere on this path, even though the write mutates `commit.statuses` (and, downstream, `commit.stack`'s deployability/CD state).

Code path:
- [1](#0-0)  — `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. There is no `.where(stack_id: ...)`, no `.merge(stacks)`, and `params.dig('repository', ...)` is never read.
- Contrast with the base class, which *does* provide a repository-scoped helper that `StatusHandler` simply doesn't use: [2](#0-1)  (`stacks` / `repository_name`).
- `create_status_from_github!` performs the actual write with no additional relationship check: [3](#0-2) .
- `verify_signature` in the controller only authenticates that the event genuinely originated from the organization named in `payload['repository']['owner']['login']` — it does not authenticate any relationship between that repository and the sha being reported: [4](#0-3) .
- `ExplicitParameters` only type-checks `sha`/`state`/etc., it doesn't cross-check `sha` against `repository`: [5](#0-4) .

Attacker flow: the attacker owns/controls some repository whose webhooks legitimately reach this Shipit instance (satisfying `verify_signature`'s org-secret check — a precondition, not a bypass). They cause a genuine, GitHub-signed `status` event to fire for that repository (e.g., by pushing a commit that CI marks with a status, or by using their own GitHub token to POST a commit status to their own repo). If the sha in that event happens to also exist as a `Commit` row belonging to an unrelated, private stack (which happens naturally with forks/mirrors of the same upstream history, or by deliberately cherry-picking/rebasing a publicly-known commit so the resulting git object is bit-for-bit identical), `StatusHandler` will locate and mutate that unrelated commit's status with zero verification that the reporting repository has anything to do with the victim stack.

Existing guards fail to close this gap because they operate at a different layer: `verify_signature` authenticates *who sent the webhook* (by organization), not *what the webhook's sha is allowed to modify*; and no model validation or `stacks` scoping is applied inside `StatusHandler`.

### Impact Explanation
A successful request causes `Status` records (and consequently deployability, blocking-status evaluation, and continuous-delivery scheduling via `add_status`/`schedule_continuous_delivery`) to be written for a commit belonging to a stack/repository that never authenticated or authorized the request. This is "a payload for one repository mutating another's stack, commit" — matching the Critical impact category. It is repeatable against any commit whose sha the attacker can learn or reproduce, and the blast radius spans every stack in the installation whose commits are reachable via legitimately-signed webhooks from any repository the attacker can trigger events on. [6](#0-5) 

### Likelihood Explanation
The attacker needs (a) a repository whose webhook signature will pass `verify_signature` (i.e., under an organization already configured/known to this Shipit instance) and (b) a sha that also exists in the victim's `Commit` table. Requirement (b) is not achievable by "brute-forcing/copying any random 40-char sha from an unrelated public repo" in general — SHA-1 git object identity is derived from tree/parent/author/message content, so an arbitrary externally-observed sha will not collide with an unrelated private stack's commit by chance. It is realistic specifically when the victim stack tracks the same code lineage as a repository the attacker can influence (forks, mirrors, monorepo/vendor imports, or a stack built from an upstream open-source project the attacker can also contribute to) — a real but narrower precondition than pure guessing. Given that precondition, the exploit is cheap and repeatable per matching sha.

### Recommendation
Scope the lookup in `StatusHandler#process` to the requesting repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `stacks`/`repository_name` helper already defined on `Handler`, so a status payload can only mutate commits belonging to stacks whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (no live GitHub calls, matching existing test patterns in `test/models/shipit/webhooks/handlers/`):
1. Create `stack_a` for repository `"attacker-org/repo-a"` and `stack_b` for repository `"victim-org/repo-b"`.
2. Create a `Commit` under `stack_b` with `sha: "f" * 40` (the "victim" commit) — do not create any commit with that sha under `stack_a`.
3. Build a webhook payload: `{ 'repository' => { 'full_name' => 'attacker-org/repo-a', 'owner' => { 'login' => 'attacker-org' } }, 'sha' => 'f' * 40, 'state' => 'success', 'context' => 'ci/attacker' }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `stack_b`'s commit `statuses.count` increased by 1 (equality `commit.stack.repository.full_name == payload['repository']['full_name']` is false, yet the write still happened), and assert `stack_a` has zero commits/statuses affected — proving the write crossed repository/stack boundaries with no authorization check.
