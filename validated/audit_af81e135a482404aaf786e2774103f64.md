### Title
Missing exponent-size guard in `e^x` branch of oscript evaluator allows unbounded `Decimal.exp()` calls - ([File: formula/evaluation.js])

### Summary
The oscript arithmetic evaluator applies an exponent-magnitude check before computing `pow`, but the special-cased "natural exponential" branch (`e^x`) bypasses this check entirely and calls `Decimal.exp()` on an attacker-controlled, unbounded value.

### Finding Description
In the `^` (power) operator handling in `evaluate()`, when the left operand equals the constant `e`, the code takes a special branch that calls `res.exp()` directly, with no bound placed on `res`: [1](#0-0) 

Contrast this with the general `pow` case immediately below it, which explicitly guards against overly large exponents before calling `prevV.pow(res)`: [2](#0-1) 

The guard `res.abs().gte(Number.MAX_SAFE_INTEGER)` was clearly added (and is exercised by the test `'222222222 ^ 222222222 infinity'` and `'2 ^ 9007199254740992'`) precisely to prevent overflow/DoS from oversized exponents in exponentiation — this is the same bug class as the referenced `pallet-revive` "exp overflow" fix. However, that same protection was never applied to the `e^x` special case just above it, even though `res` there can be any decimal value up to the configured `maxE`/`minE` bounds (`Decimal.set({ maxE: 308, minE: -324 })`, `precision: 15`): [3](#0-2) 

Any oscript formula (used inside AA definitions and evaluated for every triggering unit) that contains `e^X` with an arbitrarily large `X` reaches `Decimal.exp()` unguarded. Because oscript formulas are supplied by AA authors and executed against attacker-supplied trigger data, an unprivileged AA author (or an AA that reads trigger-controlled numeric data into an `e^...` expression) can force this code path with attacker-chosen magnitudes.

### Impact Explanation
Unbounded exponent computation in `Decimal.exp()` is a classic source of expensive/undefined-behavior arithmetic: extremely large exponents require internal Taylor-series/argument-reduction work whose cost scales with the exponent's magnitude, and can also generate extreme internal precision/exponent values before the library normalizes or rejects them. Depending on decimal.js's internal handling, this can produce either (a) significant/unbounded CPU consumption while validating/evaluating a single unit's AA trigger (since AA evaluation happens synchronously as part of consensus-critical validation), or (b) an uncaught internal error/exception if decimal.js throws for out-of-range results, which would abort validation of that unit inconsistently across nodes rather than deterministically rejecting it through `setFatalError`. Both outcomes affect the network's ability to consistently validate/confirm AA-triggering units, which is a shared, all-node-reachable code path (not just a light client or single node).

### Likelihood Explanation
The path is trivially reachable: any AA author can define an oscript formula containing `e^<expr>`, and any user can send a trigger unit whose data feeds a large numeric value into that expression. No special privileges are required beyond the ordinary ability to define and trigger AAs, which is explicitly in scope as "AA trigger sender" / "oscript evaluation."

### Recommendation
Apply the same exponent-magnitude bound used for the general `pow` path to the `e^x` branch before calling `.exp()`, e.g. reject (via `setFatalError`) when `res.abs()` exceeds a safe threshold (such as `Number.MAX_SAFE_INTEGER`, or better, a much smaller domain-appropriate bound given `maxE: 308`, since `e^x` overflows the representable double range far earlier than `2^x` does). This keeps the deterministic-rejection behavior consistent between the `pow` and `e^x` code paths.

### Proof of Concept
An AA (or oscript formula evaluated during unit validation) containing:
```
e^9007199254740992
```
or an even larger literal/derived value (up to the ~1e308 boundary allowed by `Decimal.set({maxE: 308})`) reaches: [4](#0-3) 
without ever hitting the `too large exponent` guard that the equivalent `pow` expression (`2^9007199254740992`, already covered by test at test/formula.test.js:245-249) is protected by.
