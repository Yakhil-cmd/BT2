### Title
Webhook signature verification selects a different GitHub App/organization secret than the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the webhook secret to validate against using an attacker-controlled JSON field (`repository.owner.login` / `organization.login`) read from the *unverified* request body, while the handlers that mutate state key off a different field (`repository.full_name`). In multi-organization installations, if any configured organization has no `webhook_secret`, an attacker can forge a payload whose `owner.login` points at that unsecured organization while `full_name` points at a victim stack belonging to a properly-secured organization, causing the request to be processed as authentic.

### Finding Description
`verify_signature` derives the GitHub App/organization used for signature verification purely from the JSON body, before that body has been authenticated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the per-organization config, and `verify_webhook_signature` explicitly no-ops when that organization has no configured secret: [3](#0-2) [4](#0-3) 

Once `head(422)` is skipped (secret absent → `verified == true`), `create` dispatches the entire attacker-supplied `params` to the matching event handler: [5](#0-4) 

But the handler resolves the *target* repository/stack from a **different** field than the one used to select the verification secret — `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because both `repository.owner.login` and `repository.full_name` are independently attacker-controlled fields in the un-authenticated JSON body, they need not agree. The binding that should hold is:

`organization whose secret authenticated the request == owner of the repository that gets mutated`

but nothing enforces this equality. This is the closest in-engine analog to the audit finding's root cause: a value trusted for one purpose (`initial_last_point.ts`, used for the block-slope math) silently diverges from the value that should have matched it (`last_point.ts`, mutated in the loop) because of an aliasing/consistency assumption that isn't actually enforced. Here, the "should be identical but isn't guaranteed" pair is `repository_owner` (drives which secret verifies the request) vs. `repository.full_name`'s owner segment (drives which stack/repository is acted upon).

### Impact Explanation
For example, `StatusHandler#process` sets a CI status on any tracked commit purely from the payload, with no additional authorization check: [8](#0-7) 

and `PushHandler#process` triggers a `GithubSyncJob` sync for any stack matching `full_name`/branch: [9](#0-8) 

If any organization configured in `secrets.github` (multi-app mode) lacks a `webhook_secret`, an unauthenticated attacker can name that organization in `repository.owner.login`/`organization.login` to trivially pass verification, while setting `repository.full_name` to any other tracked repository owned by a different, properly-secured organization. This lets an outsider forge `status`, `push`, `check_suite`, etc. events against a victim stack they have no access to — e.g. spoofing a passing CI status on an arbitrary commit, which downstream merge/deploy automation may treat as deployable/mergeable. This crosses a repository-write boundary without any credential for the targeted organization, matching the "unauthorized deploy/merge" and "unauthenticated read/write of stack state" impact classes.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires a multi-organization Shipit deployment (`secrets.github` keyed by organization) where at least one configured organization has no `webhook_secret` set — a state the code explicitly tolerates (`return true unless webhook_secret` in `verify_webhook_signature`), rather than rejecting as misconfiguration. Given webhook secrets are optional per the code path and setup docs don't uniformly mandate one per org, this is plausible in real deployments but not guaranteed — the engine itself does not enforce “documented” mandatory secrets for every org.

### Recommendation
- Require a non-blank `webhook_secret` for every configured GitHub organization (fail closed instead of `return true unless webhook_secret`).
- After signature verification succeeds, re-derive `repository_owner`/`organization` for authorization purposes from the *same* field the handler will use (`repository.full_name`'s owner segment / `organization.login`), and reject the request if the two disagree, instead of letting the handler act on an independently-controlled `full_name`.

### Proof of Concept
Preconditions: Shipit configured with `secrets.github: { orgA: { webhook_secret: <secret> }, orgB: { } }` (orgB has no secret), and stack `orgA/victim-repo` exists.

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # ignored, orgB has no webhook_secret

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgA/victim-repo", "owner": { "login": "orgB" } }
}
```

`verify_signature` calls `Shipit.github(organization: "orgB")` → `verify_webhook_signature` returns `true` unconditionally (no secret configured for `orgB`). `StatusHandler` then looks up commits by `sha` and marks them `success`, regardless that the request had nothing to do with `orgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
