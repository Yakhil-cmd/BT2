### Title
Cross-repository forged commit status via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to using only the raw commit `sha`, with no scoping to the repository/organization that the verified webhook payload came from. Because the `commits` table has a unique index on `["sha", "stack_id"]` (not on `sha` alone), the exact same SHA-1 commit object can legitimately exist under multiple stacks/repositories, allowing a webhook that is validly signed for the attacker's own repository to inject a forged status onto a victim's commit, satisfying `Shipit::MergeRequest::StatusChecker`/`#any_status_checks_missing?` and unblocking `#reject_unless_mergeable!`/`merge!`.

### Finding Description
The broken binding is: `repository_owner_of(verified_webhook_payload) == repository_owner_of(commit.stack)`. Tracing the code shows this is never enforced.

`WebhooksController#verify_signature` correctly authenticates the payload against the organization named in `params.dig('repository','owner','login')` [1](#0-0)  — so an attacker can only get a "verified" `status` webhook accepted if it is genuinely signed by GitHub for an organization/repo the attacker controls or can trigger (e.g. their own repo, or any repo/org onboarded onto the same Shipit instance).

Once verified, `StatusHandler#process` is invoked, and it does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is **not scoped by stack, repository, or the payload's `repository.full_name`/organization at all** — it matches by `sha` globally across every stack in the Shipit installation. The schema confirms multiple stacks can hold a commit row with the identical `sha` value, since the uniqueness constraint is `["sha", "stack_id"]`, not `sha` alone: [3](#0-2) .

`create_status_from_github!` then creates the `Status` scoped to `commit.stack_id` — i.e., whichever stack's `Commit` record matched, not the stack that actually owns the attacker's authenticated repository: [4](#0-3) , [5](#0-4) .

Exploit flow:
1. Victim's PR head commit SHA is public (visible via GitHub UI/API for the PR).
2. Attacker reproduces an identical git commit object (same tree, parent SHA, author/committer name+email+date, message) in a repository they control (e.g., by forking the victim repo before the divergence point, or replaying a shared ancestor commit), so the resulting SHA-1 is byte-identical to the victim's commit SHA. This is not a cryptographic SHA1 break — it is simply creating identical content, which naturally yields the identical hash, and is achievable whenever the relevant commit exists in shared/forked history or was ever imported into Shipit as a `Commit` row for another stack.
3. Attacker sets a `success` status for context `ci/very-important` on that SHA in their own repository via the GitHub API (an action they are fully authorized to do on their own repo).
4. GitHub sends a genuinely-signed `status` webhook to Shipit for the attacker's organization/repository.
5. `WebhooksController#verify_signature` passes because the signature really matches the attacker's org's `webhook_secret`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns the victim's `Commit` row (belonging to the victim's stack) purely because the SHA string matches, with no check that `params['repository']['full_name']`/`owner` corresponds to that commit's stack's repository.
7. `commit.create_status_from_github!(params)` creates a `Status` with state `success`, context `ci/very-important`, attached to the victim commit, scoped to the victim's `stack_id`.
8. `ProcessMergeRequestsJob` re-evaluates the merge request; `any_status_checks_missing?` (`app/models/shipit/merge_request.rb:204-206`) now returns `false` because `StatusChecker` sees the forged status satisfying `deploy_spec.merge_request_required_statuses`, so `reject_unless_mergeable!` (`app/models/shipit/merge_request.rb:155-162`) no longer rejects with `ci_missing`, and the PR proceeds toward `merge!`.

No existing guard prevents this: `verify_signature` only authenticates *which org sent this payload*, it does not bind the payload to the specific commit/stack being updated; `ExplicitParameters` in `StatusHandler.params` only validates types, not repository identity; there is no code anywhere that cross-checks `params['repository']` against `commit.stack.repository`.

### Impact Explanation
An attacker who controls any repository/organization onboarded to the same Shipit instance can, from a completely unrelated repository, inject a forged "success" (or any) commit status onto another tenant's commit/PR, bypassing that stack's required-CI merge gate and causing an unauthorized merge of a pull request whose real CI never ran. This is a cross-tenant authorization bypass: a payload legitimately authenticated for one repository mutates state (`Status`, and downstream `MergeRequest`/`merge!`) belonging to a different repository/stack. It matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized ... merge."

### Likelihood Explanation
Preconditions: the victim's `deploy_spec` must list the forgeable context under `merge_request_required_statuses`; the attacker needs any GitHub org/repo with a Shipit webhook installed (which could be their own onboarded repo, or any repo they can push commits/status to); and the attacker needs a commit SHA collision achievable purely by reproducing identical git commit content (trivially possible for shared/forked history commits, and always possible if the target commit is a genuinely shared ancestor). No Shipit secrets, sessions, or privileged roles are required — only ability to push to a repo they own and call the GitHub statuses API on it, both of which are explicitly in-scope attacker capabilities. This is repeatable against any repository sharing a base history with a target, or any commit whose exact content the attacker can reproduce.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the stack(s) whose repository matches the webhook payload's `repository.full_name`/`owner`+`name`, e.g. join through `Stack -> Repository` filtered by `params.dig('repository','full_name')`, instead of a bare global `Commit.where(sha:)`. Alternatively/additionally, enforce this at the `Commit` model or `Status.replicate_from_github!` layer by requiring the stack's `Repository` to match the incoming payload's repository identity before creating a `Status`.

### Proof of Concept
minitest (mirrors `test/models/merge_request_test.rb`'s `#reject_unless_mergeable! reject the PR if it has a missing required CI status`, but drives the status creation through `StatusHandler.call` with a payload whose `repository` does not match the PR's stack):

```ruby
test "#reject_unless_mergeable! is bypassed by a status webhook for an unrelated repository sharing the commit sha" do
  @pr.stack.cached_deploy_spec.stubs(:required_statuses).returns(['ci/very-important'])
  @pr.head.statuses.where(context: 'ci/very-important').delete_all

  # Precondition: gate is currently missing -> PR rejected
  assert_predicate @pr, :any_status_checks_missing?
  assert_equal true, @pr.reject_unless_mergeable!
  assert_predicate @pr, :rejected?
  assert_equal 'ci_missing', @pr.rejection_reason
  @pr.retry!

  # Attacker payload: repository does not own @pr.head, but sha matches
  forged_payload = {
    'sha' => @pr.head.sha,
    'state' => 'success',
    'context' => 'ci/very-important',
    'description' => 'forged',
    'target_url' => 'http://attacker.example.com',
    'created_at' => Time.now.utc.iso8601,
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  # Simulate signature verification already passed for attacker-org (their own valid secret)
  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  # Binding check: repository_owner_of(payload) == 'attacker-org' != repository_owner_of(@pr.stack)
  refute_equal 'attacker-org', @pr.stack.repository.owner

  @pr.head.reload
  refute_predicate @pr, :any_status_checks_missing? # BUG: forged status satisfies the gate
  assert_equal false, @pr.reject_unless_mergeable!    # BUG: no longer rejected, proceeds to merge
end
```
