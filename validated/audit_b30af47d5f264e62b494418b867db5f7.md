### Title
Cross-repository status webhook forgery via unscoped `Commit.where(sha:)` lookup bypasses CI gating for unrelated stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records for an incoming GitHub `status` webhook purely by `sha`, with no check that the webhook's `payload['repository']` matches the `stack.repository` that owns the matched commit. Because git commit SHAs are content-addressed and identical across forks/mirrors of a repository, an attacker who owns (or controls a GitHub App installation on) any repository sharing history with a victim's tracked repository can post/replicate a `success` status from their own repo and have it applied to the victim's commit, driving `Commit#status` to `success` and triggering `Stack#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger` for the victim's stack.

### Finding Description
The claimed binding is: `success? == (statuses were posted by a webhook whose payload.repository == stack.repository)`. This binding is broken.

`WebhooksController#verify_signature` only authenticates *which GitHub organization/App* sent the webhook (via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`), it never validates that the payload's `repository.full_name` corresponds to the `stack.repository` of the commit that will be mutated: [1](#0-0) [2](#0-1) 

The dispatched `StatusHandler` then resolves target commits with no repository scoping at all: [3](#0-2) 

`Commit.where(sha: params.sha)` matches **every** `Commit` record in the database with that SHA, across every stack/repository, not just commits belonging to the repository that actually emitted the webhook. `create_status_from_github!` then creates a `Status` and calls `add_status`, which fires `stack.schedule_merges` and, via the `after_commit` callback on `Status`, `Commit#schedule_continuous_delivery`: [4](#0-3) [5](#0-4) 

Root cause: the lookup key (`sha`) is not scoped to the repository that authenticated the request. Because git SHAs are computed from commit content (tree, parents, author, message, timestamps) independent of which repository hosts them, two repositories — e.g. a victim's public/private repo and any fork or independently created repo with byte-identical commit metadata — can share identical SHAs for different logical histories. An attacker who forks the victim's repository (or otherwise controls a repository that shares a commit SHA with the victim) and has the Shipit GitHub App (or a configured multi-tenant org) installed on their own fork can send a completely genuine, correctly-signed `status` webhook from their own repository for that shared SHA. `verify_signature` validates this webhook correctly (it *is* legitimately signed by GitHub for the attacker's own org/repo), so the request is accepted by Shipit as a whole. But since `status_handler.rb` never checks `payload['repository']` against the commit's actual `stack.repository`, the forged/attacker-controlled status is applied to the victim's identical-SHA commit in the victim's stack as well.

Existing guards do not prevent this:
- `verify_signature` authenticates the *sender org*, not the *target repository of the commit being mutated*.
- `drop_unhandled_event` / `check_if_ping` are irrelevant to this path.
- `ExplicitParameters` schema in `StatusHandler` only validates types (`sha`, `state`, etc.), not repository identity.
- No model-level uniqueness or scoping ties a `Commit`'s `sha` lookup to the requester's repository.

### Impact Explanation
A forged/legitimately-self-signed status from an attacker's own repository can flip `Commit#status` to `success` for a commit in a **victim's** stack, as long as that commit's SHA is shared (e.g., via fork). Because `deployable?` for continuous delivery relies on `success? && !blocked? && !locked?`, and the operator only locks commits they distrust (not realizing a shared-SHA commit can be gamed from an unrelated repo), this can cause `ContinuousDeliveryJob` to enqueue and `Stack#trigger` to deploy code the victim's own CI never actually validated. This is a cross-tenant/cross-repository forged authorization resulting in an unauthorized deploy — matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" Critical impact categories. The attack is repeatable against any victim stack whose repository has ever been forked (or otherwise shares commit history) with a repository the attacker controls or that is hosted under a Shipit-configured GitHub organization the attacker can push/install apps to.

### Likelihood Explanation
Preconditions: (1) a multi-tenant or public Shipit-GitHub-App configuration where the attacker can get a `status` webhook correctly signed for their own repository/org (e.g., installing a public GitHub App on their own fork, or being a member of a Shipit-configured org); (2) a victim stack tracking a repository from which the attacker can produce or find an identical-SHA commit (trivial via `git fork`, since GitHub forks preserve SHAs exactly, or by cherry-picking/rebasing a commit with identical tree/author/timestamp into another repo); (3) the victim's specific commit not being individually `locked?` and the stack having `continuous_deployment`/CI gating enabled with `ignore_ci?` false. Given forking is a normal, unprivileged GitHub action available to "any GitHub user," and the attacker fully controls when/what status to post on their own fork, this is highly feasible and repeatable at low cost.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `check_suite`/`check_run` handlers if they have the same pattern) to only commits belonging to stacks whose `repository` matches the webhook payload's `repository.full_name`, e.g.:
```ruby
def process
  Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload))
        .where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `repository_from_payload` is derived from the same `payload['repository']` structure and compared to `Repository#owner`/`#name` (or full name), never trusting the SHA alone as an implicit repository identifier.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status from an unrelated attacker repository must not affect a victim stack's commit with the same sha" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...) # undeployed, unlocked
  victim_stack.update!(continuous_deployment: true)

  request.headers['X-Github-Event'] = 'status'
  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    post :create, body: attacker_payload, as: :json
  end

  refute_equal 'success', victim_commit.reload.state
end
```
Both sides of the binding to assert explicitly:
- Before fix: `victim_commit.reload.state == 'success'` even though `payload['repository']['full_name'] != victim_stack.repository` — binding broken, `ContinuousDeliveryJob` enqueued for `victim_stack`.
- After fix: `victim_commit.reload.state != 'success'` and no `ContinuousDeliveryJob` enqueued for `victim_stack`, because the handler filters commits by matching `stack.repository == payload['repository']['full_name']`.
