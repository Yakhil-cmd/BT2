### Title
`is_valid_signed_package()` accepts a self-declared address definition and skips the on-chain current-definition (trust-policy) check when `last_ball_unit` is omitted, allowing signatures from a revoked/rotated key to be treated as valid - ([File: signed_message.js])

### Summary
The oscript/formula built-in `is_valid_signed_package(signed_package, address)` — used by AAs (e.g. payment-channel contracts) to authenticate off-chain messages sent by a specific counterparty address — has two verification modes depending on whether the caller-supplied package includes a `last_ball_unit` field. When it is present ("network-aware"), the verifier looks up the address's *actual, current* on-chain definition via `storage.readDefinitionByAddress` and enforces it. When it is absent, the verifier falls back to trusting the definition embedded directly in the package, checking only that `chash160(definition) === address`, without ever consulting the address's current registered definition or any `address_definition_change` history. This mirrors the SeaweedFS bug class: a "direct/bearer" verification path that authenticates the raw credential but never enforces the authoritative trust policy (the address's current definition) that the "proper" network-aware path enforces.

### Finding Description
`is_valid_signed_package` is implemented in `formula/evaluation.js` and delegates to `signed_message.validateSignedMessage`: [1](#0-0) 

Inside `validateSignedMessage`, whether the address's real definition is enforced depends entirely on `bNetworkAware = ("last_ball_unit" in objSignedMessage)`: [2](#0-1) 

When `bNetworkAware` is true, `validateOrReadDefinition` fetches the address's *current* definition from storage and, if one is already registered, explicitly rejects any caller-supplied definition (`"should not include definition"`) — i.e. it enforces the authoritative, up-to-date policy for that address: [3](#0-2) 

But when `last_ball_unit` is simply omitted, the function takes the `else` branch, which never queries storage for the address's real definition at all — it only checks that the *caller-supplied* definition hashes to the given address, then authenticates the signature against that self-supplied definition: [4](#0-3) 

Because Obyte addresses can be re-keyed over time via `address_definition_change` (the address stays the same but the authoritative signing definition changes), the *original* definition that first produced the address hash remains forever hash-consistent with that address, even after it has been superseded/revoked on-chain. The "no `last_ball_unit`" code path has no way to know a newer definition exists and will happily validate a signature made with an old, revoked key as if it were still authoritative for that address.

This built-in is explicitly designed for exactly this trust decision: authenticating a specific known counterparty address inside AA logic, e.g. in the sample payment-channel contract, where a "fraud proof" branch trusts whichever party is validated by `is_valid_signed_package`: [5](#0-4) 

The caller of `is_valid_signed_package` fully controls the shape of the object being validated (it typically comes from AA trigger `data`, i.e. attacker-controlled input), including whether to include `last_ball_unit`. Omitting it is sufficient to force the weak, non-authoritative verification path.

### Impact Explanation
Any AA that uses `is_valid_signed_package(pkg, address)` to authenticate messages from a specific, potentially re-keyed address (payment channels, order books, or any oscript pattern relying on "signed by trusted counterparty X") can be fooled into accepting a message signed with a key that the real owner of `address` has already revoked/rotated via `address_definition_change`. In a payment-channel-style AA this directly enables an attacker who once held (or later recovers/leaks) an old private key to forge channel-closing or fraud-proof messages "as" the legitimate counterparty after that counterparty believed they had secured the channel by rotating keys, resulting in unauthorized fund movement / loss for the honest party. This is a concrete AA fund-loss vector reachable purely by a trigger sender crafting the `data` payload of a trigger unit — no privileged access needed.

### Likelihood Explanation
Any wallet or user who ever changes their address definition (e.g. after suspecting key compromise, or as routine key rotation) while continuing to participate in an AA that authenticates them via `is_valid_signed_package` is exposed. Triggering the vulnerable path requires nothing more than omitting one optional field (`last_ball_unit`) from an attacker-crafted `signed_package` object that is otherwise a completely normal, spec-compliant construct (the field's absence is explicitly a supported, tested mode — see `test/formula.test.js` tests for `is_valid_signed_package` without `last_ball_unit`). This makes exploitation straightforward for anyone possessing an old/leaked private key for the target address.

### Recommendation
Require `last_ball_unit` (network-aware mode) for any `is_valid_signed_package` call that authenticates a pre-existing address identity, or otherwise always cross-check the caller-supplied definition against the address's most recent on-chain definition (honoring `address_definition_change`) regardless of whether `last_ball_unit` is present, so that revoked/rotated definitions can never again satisfy authentication for that address.

### Proof of Concept
1. Address `A` is created with initial definition `D0 = ["sig", {pubkey: P0}]`, so `chash160(D0) === A`.
2. `A`'s owner detects `P0` may be compromised and rotates to `D1 = ["sig", {pubkey: P1}]` via an `address_definition_change` message, updating `A`'s authoritative on-chain definition to `D1`.
3. An attacker who has `P0`'s private key crafts a `signed_package` object (no `last_ball_unit` field):
```json
{
  "signed_message": { "channel": "A", "period": 3, "amount_spent": 999999 },
  "authors": [{
    "address": "A",
    "definition": ["sig", {"pubkey": "P0"}],
    "authentifiers": { "r": "<signature made with P0>" }
  }]
}
```
4. Attacker submits this as `trigger.data.sentByPeer` to an AA (e.g. the payment-channel contract) that calls `is_valid_signed_package(trigger.data.sentByPeer, A)`.
5. Because `last_ball_unit` is absent, `validateSignedMessage` takes the non-network-aware branch (`signed_message.js:241-252`), verifies only that `chash160(D0) === A` and that the signature matches `D0`, and returns success — even though `A`'s real, current, authoritative definition is `D1` and `P0` has been revoked.
6. The AA treats the message as validly signed by `A` and executes the corresponding logic (e.g. releasing channel funds according to the forged state), causing fund loss.
