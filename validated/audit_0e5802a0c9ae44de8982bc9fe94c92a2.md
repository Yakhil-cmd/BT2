### Title
Webhook `organization` used for signature verification is not bound to the `repository` the handlers act on, enabling cross-organization webhook forgery when any onboarded org has no `webhook_secret` configured - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org config (and therefore which `webhook_secret`) to verify a webhook against using an **unverified** field taken straight from the JSON body, while the event handlers that actually perform writes select the target `Stack`/`Repository` using a **different, independently-controlled** field from the same unverified body. Because `GitHubApp#verify_webhook_signature` unconditionally accepts any payload when the selected org has no `webhook_secret` configured (a supported configuration), the two fields never have to agree, breaking the binding "organization authenticated == repository written."

### Finding Description
`WebhooksController#verify_signature` picks the org to authenticate against like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` (and thus which `webhook_secret` is used) comes straight from the request body, before any signature has been checked — it is entirely attacker-controlled. `GitHubApp#verify_webhook_signature` then does:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

If the organization named in the (still unverified) payload happens to be one that is configured in Shipit's multi-org `github:` config without a `webhook_secret` — which is an explicitly documented, supported configuration (`webhook_secret: # nil` in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets.yml`) — verification is bypassed unconditionally, and `head(422)` is never called.

Meanwhile, every event handler derives the actual write target from a **different** field of the same payload:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository.owner.login` (used for auth) and `repository.full_name` (used for the write target) are two independent JSON fields with no cross-validation. An attacker only needs to know that **some** org onboarded on the Shipit instance has no `webhook_secret` set; they can then set `repository.owner.login`/`organization.login` to that unsecured org while setting `repository.full_name` to any other org/repo tracked by the instance (e.g. `victim-org/victim-repo`), and the request will be accepted and dispatched to handlers acting on `victim-org/victim-repo`.

Concretely, for a forged `push` event, `PushHandler#process` will run:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 
which enqueues `GithubSyncJob` for the victim's stack, ingesting attacker-chosen commit SHAs as if they had really been pushed to the tracked branch — and if `continuous_deployment` is enabled on that stack, this can trigger an unauthorized deploy.

### Impact Explanation
This breaks the trust binding between "the organization whose credential authenticated the request" and "the repository/stack that is actually written to." An unauthenticated, unprivileged network attacker can:
- Forge webhook events (push, status, check_suite, membership, pull_request, etc.) attributed to any repository/organization tracked by the Shipit instance, as long as any other onboarded org lacks a `webhook_secret`.
- Cause `GithubSyncJob` to ingest attacker-controlled commit SHAs into a victim stack's history and, on stacks with `continuous_deployment` enabled, trigger an unauthorized deploy — matching the "unauthorized deploy" and "cross-repository writes" Critical/High impact categories.

The severity depends on operator configuration (at least one org without a `webhook_secret`), but this is an explicitly supported/documented setup, not a hypothetical misuse, and the vulnerable code path (`repository_owner` selection vs `repository_name` selection) is present regardless of configuration — it is only latent until one org's secret is unset.

### Likelihood Explanation
Requires no credentials, tokens, or privileged access — only knowledge (or a guess) that one org onboarded to a shared/multi-tenant Shipit instance has no `webhook_secret` configured, which is plausible in staging/dev/internal setups or partially-configured production multi-org deployments. The `/webhooks` endpoint is unauthenticated by design (it's meant to receive GitHub's calls), so the only barrier is the signature check this issue defeats.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the same field used by handlers to select the write target (e.g., always derive both from `repository.full_name`, or verify the signature using the config for the org that owns the repository actually being acted upon, not a caller-supplied org name). Additionally, do not allow signature verification to silently succeed (`return true unless webhook_secret`) for organizations with no secret unless that is an explicit, intentional opt-out; consider requiring `webhook_secret` for all configured organizations.

### Proof of Concept
1. Shipit is configured with two orgs: `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, e.g., left blank during setup), both with repositories tracked as stacks.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "secure-org/victim-repo",
    "owner": { "login": "open-org" }
  }
}
```
No valid `X-Hub-Signature` header is required.
3. `WebhooksController#verify_signature` computes `repository_owner` = `"open-org"`, loads `open-org`'s `GitHubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-83`.
4. `PushHandler` resolves `repository_name` = `"secure-org/victim-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` for `secure-org`'s stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated for `secure-org`.

Note: I was not able to fully trace, within the remaining tool budget, whether the `membership` event's downstream effect on `Team`/`Membership` records also feeds into OAuth login authorization (`oauth_teams` in `lib/shipit/github_app.rb`); if it does, this same forgery vector could additionally be leveraged for authentication bypass via team membership manipulation. This secondary claim is not confirmed with code and is not included in the impact assessment above.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
