### Title
Operator-precedence bug in `provision?` lets `review_stacks_enabled = false` be bypassed via `provisioning_behavior_prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the three `provisioning_behavior_*` checks using `&&`/`||` without parentheses around the whole `review_stacks_enabled` gate, so due to Ruby's operator precedence `&&` binds tighter than `||`. As a result, `review_stacks_enabled` only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of the flag.

### Finding Description
The binding the operator expects is `review_stacks_enabled == true` before any provisioning decision is made, i.e. `provision? => review_stacks_enabled && (allow_all? || (allow_with_label? && label) || (prevent_with_label? && !label))`. The actual code is: [1](#0-0) 

which Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. When a repository has `review_stacks_enabled = false` but `provisioning_behavior = prevent_with_label` (a plausible state if an operator flips the flag off without resetting the mode, or leaves the default mode in place), any newly opened pull request with no label — which is the default state of a PR an unprivileged contributor opens — satisfies `prevent_with_label? && !pull_request_has_provisioning_label?`, making `provision?` (and therefore `respond_to_pull_request_opened?`) return `true` regardless of the disabled flag.

`process` then calls `Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1)  to resolve the real, correctly-authenticated repository, and reaches `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [3](#0-2) , creating a `ReviewStack`/`Stack` row and queuing it for provisioning even though `review_stacks_enabled` is `false`.

No forged webhook is required: the webhook is a genuine GitHub `pull_request.opened` event, correctly signed, sent by GitHub itself when the attacker (an ordinary external contributor able to open a PR against the tracked repository) opens an unlabeled pull request. `verify_signature`/`drop_unhandled_event` in `WebhooksController` pass normally because the event is real and correctly signed for that organization [4](#0-3) ; they do nothing to validate the business-logic gate inside the handler. The same precedence pattern also exists in `ReopenedHandler#unarchive?` [5](#0-4) .

### Impact Explanation
For any tracked repository where `provisioning_behavior` is `prevent_with_label` (or, with attacker-controlled labels, `allow_with_label`) while `review_stacks_enabled` is `false`, an unprivileged contributor who can open a pull request causes Shipit to create a `Stack`/`ReviewStack` row scoped to that repository and enqueue it in the provisioning workflow, which drives real provisioning/deploy tasks on the deploy host. This is repeatable per pull request against any repository sharing this misconfiguration, and it silently defeats the operator's intended kill-switch (`review_stacks_enabled = false`) for that repository, resulting in unauthorized automatic deploy/provisioning activity.

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled = false` combined with `provisioning_behavior = prevent_with_label` (no attacker action needed to hit the label condition, since default PRs carry no labels) or `allow_with_label` if the attacker can also set the label. This is a real, not purely theoretical, operator-configuration state (e.g., disabling review-stack auto-provisioning temporarily while leaving the label-based mode set) and requires zero elevated attacker capability — only the ability to open a PR against a repository Shipit already tracks and receives webhooks for.

### Recommendation
Parenthesize the entire condition so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
test "does not create a stack when review_stacks_enabled is false even with prevent_with_label mode" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # default unlabeled PR

  handler = OpenedHandler.new(payload)
  assert handler.send(:respond_to_pull_request_opened?), "expected gate bypass to reproduce"

  assert_no_difference -> { Shipit::Stack.count } do
    handler.process
  end
end
```
With the current code, `respond_to_pull_request_opened?` returns `true` and the `assert_no_difference` fails because a stack is created, demonstrating `review_stacks_enabled == false` no longer implies `gate_enforced_before_stack_creation == true`.
