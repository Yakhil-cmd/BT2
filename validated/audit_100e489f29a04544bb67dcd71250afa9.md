### Title
CCMenu API token is not scoped to the stack it was generated for, allowing cross-stack disclosure of build status - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints a `read:stack` `ApiClient` token without binding it to the `stack` the URL was requested for, and `Api::CCMenuController#stack` looks up the target stack directly instead of scoping it via the client's own `stack_id` restriction. The result: a single long-lived token intended to expose the CI status of one stack can be replayed against the `cc_menu.xml` endpoint of any other stack in the installation.

### Finding Description
`ApiClient` supports per-token stack scoping via its `belongs_to :stack, optional: true` association [1](#0-0) , and `Api::BaseController` enforces that scoping for normal API requests: if `current_api_client.stack_id?` is set, the client can only see that one stack [2](#0-1) .

However, the CCMenu feature breaks this binding on both ends:

1. **Token minting**: `CCMenuUrlController#client` creates (or finds) the `ApiClient` using only `creator` and `name: 'CCMenu Client'` — it never sets `stack:` on the record, so `stack_id` remains `nil`:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [3](#0-2) 
Because `find_or_create_by!` matches on `creator` + `name` only, the *same* unscoped token is (re)used for every stack a given user requests a CCMenu URL for.

2. **Consumption**: `Api::CCMenuController` overrides the base controller's scoped `stack` helper with a direct, unscoped lookup:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 
This bypasses `BaseController#stacks`/`#stack`, which is the only place the `stack_id` restriction from item 1 would have been enforced [2](#0-1) . The only gate left is `require_permission :read, :stack` [5](#0-4) , which only checks that `read:stack` is present in `permissions` — it says nothing about *which* stack.

**Binding broken**: the stack a token is supposed to authorize (the one whose URL the user requested, `stack_id` at generation time) vs. the stack the token actually touches (any `stack_id` param supplied at request time to `/api/stacks/:stack_id/cc_menu.xml`). Before the attack: token is intended for stack A only. After: the identical token, unmodified, is accepted for stack B, C, … because `ApiClient#stack_id` was never set and `CCMenuController#stack` never checks it.

CCMenu tokens are explicitly designed to be embedded in unauthenticated third-party consumers (build radiators/status boards) via a bare query-string `token` parameter (`?token=...`), so this is a credential class expected to be handled outside a Shipit session/browser — an "unprivileged" holder of one leaked/observed URL gains read access to every other stack's build status.

### Impact Explanation
This matches the specified High-severity category: "unauthenticated read of stack state, task streams or deploy output." An attacker in possession of a single stack's CCMenu token (a value designed to be pasted into public, unauthenticated dashboards) can query `GET /api/stacks/:any_stack_id/cc_menu.xml?token=<leaked_token>` and obtain `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock status, etc. for arbitrary stacks in the Shipit instance, not just the one the token was generated for — a cross-stack information disclosure that the scoping mechanism (`ApiClient#stack_id`) was specifically built to prevent for other API clients.

### Likelihood Explanation
High. No special privileges are required beyond obtaining one legitimately-issued CCMenu URL/token (which by design is meant to be shared with low-trust display systems). The vulnerable code path is the default, unmodified controller behavior — no misconfiguration is needed. `ApiClient.authenticate` only validates the message-verifier signature and existence of the record [6](#0-5) ; it performs no stack-matching, so any valid CCMenu token trivially works against any stack ID.

### Recommendation
- In `CCMenuUrlController#client`, create/find the `ApiClient` scoped to the specific `stack` (e.g., `find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack:)`), so each stack gets its own bound token.
- In `Api::CCMenuController#stack`, restore the base `stacks`-scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so `current_api_client.stack_id` restriction is enforced exactly as it is for the rest of the API.

### Proof of Concept
1. As a logged-in user, request a CCMenu URL for stack A: `GET /stacks/A/ccmenu_url` → response includes `ccmenu_url` with an embedded `token` [7](#0-6) .
2. Note that the underlying `ApiClient` record has `stack_id: nil` and `permissions: ["read:stack"]` (verifiable via the test at [8](#0-7) , which shows the client is created with no stack binding).
3. Take the same `token` and request `GET /api/stacks/B/cc_menu.xml?token=<token>` for an unrelated stack B that the user never requested a CCMenu URL for.
4. Observe the response returns `200 OK` with stack B's build status data, because `CCMenuController#stack` resolves `params[:stack_id]` unconditionally [9](#0-8)  and `require_permission :read, :stack` only checks the permission string, not the stack identity.
