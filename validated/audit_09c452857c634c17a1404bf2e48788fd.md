### Title
Missing Staking Info Validation During FastSync Allows Any Peer to Poison the Staking Epoch DB — (`datasync/downloader/queue.go`)

### Summary
During FastSync, any registered P2P peer that is assigned a staking info fetch task can deliver a `P2PStakingInfo` with entirely fabricated `NodeIds` and `StakingAmounts`. The `validate` closure in `queue.DeliverStakingInfos` is an unimplemented TODO stub that unconditionally returns `nil`, so no content is checked against the block header's committed state root. The fabricated data is then written permanently to the staking epoch DB by `commitFastSyncData`.

### Finding Description

`queue.DeliverStakingInfos` in `datasync/downloader/queue.go` defines a `validate` closure that is a stub:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

Compare this to `DeliverBodies`, which verifies `DeriveTransactionsRoot(...) != header.TxHash`, and `DeliverReceipts`, which verifies `DeriveReceiptsRoot(...) != header.ReceiptHash`. Staking info has no equivalent check. [2](#0-1) [3](#0-2) 

The `reconstruct` closure blindly stores the attacker-supplied struct into the fetch result:

```go
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [4](#0-3) 

`commitFastSyncData` then writes it to the persistent staking DB using the attacker-controlled `BlockNum` field as the key:

```go
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [5](#0-4) 

The same unguarded write occurs in `commitPivotBlock`: [6](#0-5) 

The P2P entry point `handleStakingInfoMsg` performs no authentication beyond the peer being registered: [7](#0-6) 

The `deliver` function in `queue.go` does check that the peer has a pending request (`pendPool[id]`), which means the attacker must be assigned a staking info fetch task. However, any registered P2P peer is eligible to be assigned such tasks during FastSync via `ReserveStakingInfos` → `fetchParts` → `idlePeers`. [8](#0-7) 

The staking DB schema stores entries as `"stakingInfo" || Uint64LE(num) => JSON.Marshal(StakingInfo)`, and `GetStakingInfo` reads from this DB before falling back to state: [9](#0-8) 

### Impact Explanation

The staking DB entry at the poisoned `BlockNum` is used for:
- **Validator selection**: `NodeIds` and `StakingAmounts` determine the weighted-random proposer set for all blocks in the affected staking epoch.
- **Reward distribution**: `StakingAmounts` determine each validator's share of block rewards.

An attacker can inject arbitrary `NodeIds` (replacing legitimate validators with attacker-controlled addresses) and arbitrary `StakingAmounts` (skewing reward distribution). This constitutes unauthorized manipulation of reward distribution and validator authority over protected chain state.

The corruption is durable: `PutStakingInfoToDB` writes to the persistent key-value store, and `GetStakingInfo` will serve the poisoned entry from DB on every subsequent lookup for that epoch. [10](#0-9) 

Note: this path is only active before the Kaia hardfork. After the Kaia fork, `GetStakingInfo` derives staking info from the previous block's state and does not use the DB. [11](#0-10) 

### Likelihood Explanation

- The victim node must be in FastSync mode (a new node syncing from scratch, which is the normal bootstrap scenario).
- The attacker must be a connected P2P peer — any node can connect to a Kaia node's P2P port.
- The attacker must be assigned a staking info fetch task by the downloader's scheduler. Since any idle peer is eligible, a single malicious peer in the peer set is sufficient.
- No cryptographic key, governance privilege, or validator majority is required.

### Recommendation

Implement the missing validation in `queue.DeliverStakingInfos`. The staking info must be verified against the block header's committed state root by re-deriving the staking info from the state at the source block number and comparing it to the delivered data. Until this is implemented, the TODO stub should at minimum reject deliveries during FastSync or require the `BlockNum` field to match the requested header's number.

### Proof of Concept

1. Start a victim node in FastSync mode (`--syncmode fast`) with the WeightedRandom proposer policy.
2. Connect a malicious peer that serves valid headers/bodies/receipts but, when assigned a staking info fetch task, responds with a `stakingInfoPack` containing a `P2PStakingInfo` with fabricated `NodeIds` (attacker-controlled addresses) and `StakingAmounts`.
3. The malicious peer's response passes through `handleStakingInfoMsg` → `DeliverStakingInfos` → `queue.DeliverStakingInfos` with `validate` returning `nil`.
4. `commitFastSyncData` calls `PutStakingInfoToDB(fabricatedBlockNum, fabricatedStakingInfo)`.
5. After sync completes, call `GetStakingInfo(epochBlock)` — it returns the attacker-supplied validator set and staking amounts from DB.
6. All subsequent block proposals and reward distributions for that epoch use the poisoned data.

func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
