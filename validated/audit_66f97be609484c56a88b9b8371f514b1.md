### Title
Unvalidated route bytes let an attacker-named hop contract execute arbitrary code under the swapper's authorization tree — ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and `flash_position` all forward a fully caller-controlled `StrategySwap` byte payload to the configured router. The controller validates only the payload is non-empty and measures token deltas around the call; it never inspects which contract addresses the route will invoke. Inside the router, the payload's `assets` registry names the pool address each hop calls, with no allowlist. An attacker-deployed "pool" contract therefore runs arbitrary code mid-transaction, and any `token.transfer(victim, attacker, amount)` it issues is recorded by the Soroban host as a sub-invocation of the victim's own `swap_collateral` (or `execute_strategy`) authorization entry — executing if the victim signs that tree.

### Finding Description
The bug class in the report is a serialized payload smuggling an executable gadget past a detector. The analog here is the serialized `swap` route: opaque bytes that pass the controller's checks (`!swap.is_empty()` at `swap.rs:22`, measured-delta checks at `swap.rs:40-54`) while embedding a call to attacker code. `swap_tokens` authorizes only the exact input transfer (`authorize_transfer_as_current`, `swap.rs:34`) and forwards the bytes to `router.execute_strategy(&controller, &amount_in, swap)` at `swap.rs:37`. The router keeps no allowlist of pools or tokens (`docs/explanation/threat-model.md:154-165`): "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` pins the exact behavior: a `RogueHopPool` whose `swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` is recorded as a child of Alice's `swap_collateral` auth entry and drains her full balance of an unrelated, never-listed token while the swap itself settles normally (fair output credited, all risk gates pass).

### Impact Explanation
Theft of user funds: any token the victim holds — including tokens unrelated to the protocol — can be transferred to the attacker inside the victim's signed auth tree. The measured-delta guards and `RouterOverspend`/`NoSwapOutput` checks only bound the protocol-routed amounts; the rogue pool's `transfer` from the caller's wallet is outside all of them. The attack reaches the victim through every swap-bearing entrypoint (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position`) and through direct `execute_strategy` calls on the router.

### Likelihood Explanation
Requires the victim to sign an authorization tree containing the extra child `transfer`. Standard simulation records the tree silently; a user or dApp that does not decode the route bytes and inspect the simulated auth children signs it. The threat model documents this and prescribes client-side verification, which caps the severity at Medium — there is no contract-level mitigation, and exploitation needs a poisoned route plus an uninspected signature rather than a single unprivileged transaction.

### Recommendation
Constrain the dispatch surface so payload-named addresses cannot run arbitrary code beneath the caller's auth: maintain a governance-approved venue/pool registry in the router (or validate hop pool addresses against a known-good list in `program.rs` decode), or have the controller reject routes that would produce auth sub-invocations beyond the single input transfer by pre-simulating/verifying the auth tree. At minimum, surface the signed-tree-contains-foreign-transfer check as a protocol-invariant requirement on integrators.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is the working PoC: `RogueHopPool::swap` (lines 62-71) calls `token.transfer(alice → attacker, 77_770_000_000)`; `route_through_pool_stealing` embeds that contract as the hop pool; the test asserts the stolen transfer is recorded inside Alice's `swap_collateral` auth entry (lines 206-222), Alice's wallet is drained to 0, the attacker receives the full balance, and the swap still delivers fair ETH output (lines 224-226). Against the production router the same payload is a `StrategyPayload` whose `assets` registry places the rogue contract at the hop's pool index — the router's `dispatch_hop` invokes it directly.
