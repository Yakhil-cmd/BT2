### Title
Webhook signature is verified against `repository.owner.login`, but repository lookup uses the unrelated `repository.full_name` field, letting one org's webhook secret archive/deprovision another org's ReviewStack — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to validate a request against using `params.dig('repository','owner','login')`, while `ClosedHandler` (and other pull_request handlers) resolve the target `Repository`/`ReviewStack` using the independent `params.repository.full_name` field. Because these two JSON fields are never cross-checked against each other, an attacker who owns any Shipit-configured org (OrgA) can self-craft a `pull_request` `closed` payload whose `repository.owner.login` is `"OrgA"` (so it validates against OrgA's own `webhook_secret`) but whose `repository.full_name` is `"OrgB/protected-repo"` with a victim PR `number`, causing `ReviewStackAdapter#archive!` to deprovision and archive OrgB's live ReviewStack.

### Finding Description
The broken binding, stated as an equality that the code should enforce but doesn't:
`organization_used_to_verify_signature (params.repository.owner.login) == organization_whose_repository_is_mutated (owner parsed from params.repository.full_name)`

Trace:
1. `WebhooksController#verify_signature` computes the verifying org purely from the payload's `repository.owner.login` sub-field (with an `organization.login` fallback), never from `repository.full_name`: [1](#0-0) [2](#0-1) 
It then fetches `Shipit.github(organization: repository_owner)` and validates the raw body HMAC with that org's `webhook_secret`: [3](#0-2) 

2. Once verified, `create` dispatches the raw, attacker-controlled JSON `params` (unmodified) to all registered `pull_request` handlers, including `ClosedHandler`: [4](#0-3) 

3. `ClosedHandler#process` resolves `repository` strictly from `params.repository.full_name` — a completely separate JSON field from the one used for signature verification — and scopes the `ReviewStackAdapter` to that repository's `review_stacks`: [5](#0-4) 

4. `Repository.from_github_repo_name` parses the owner/name purely by splitting the string, with no validation that it matches the organization that authenticated the request: [6](#0-5) 

5. `ReviewStackAdapter#archive!` finds the stack by PR number (`environment: "pr#{params.number}"`) within the scope passed in, and unconditionally deprovisions/archives it: [7](#0-6) [8](#0-7) 

Attacker's exact request: a raw JSON body with
```
{"action":"closed","number":<OrgB PR#>,"repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/protected-repo"}, "pull_request": {...}, "sender": {"login": "attacker"}}
```
signed with `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` — a secret the attacker legitimately possesses because it belongs to their own org's GitHub App installation.

Existing guards do not prevent this: `verify_signature` only proves the payload was signed by *some* known org's secret, never that the *acted-upon* repository belongs to that org. `drop_unhandled_event` and `ExplicitParameters` schemas only validate types/presence of fields (`repository.full_name` as `String`), not cross-field consistency with `repository.owner.login`. `Repository.from_github_repo_name` performs no ownership/authorization check either. Nothing in the call chain (`verify_signature` → `create` → `ClosedHandler#process` → `ReviewStackAdapter#archive!`) ties the verified organization identity to the repository being mutated.

### Impact Explanation
An attacker controlling only their own Shipit-registered GitHub org (OrgA) can force `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!` to run against any other tenant organization's (OrgB's) actively-deploying `ReviewStack`, purely by naming OrgB's `repository.full_name` and the victim PR `number` in a self-signed payload. This is a cross-tenant, unauthorized mutation of another organization's stack/deploy environment — a denial of a legitimate deploy pipeline the victim never authorized. It is trivially repeatable against any repository/PR number combination and any org configured in Shipit's multi-org `github:` secrets, since nothing scopes the effect to the attacker's own org. This matches the "Critical" category: "a payload for one repository mutating another's stack."

### Likelihood Explanation
Preconditions: Shipit configured with multiple GitHub orgs (the documented multi-org `github:` secrets schema), attacker owns/administers at least one such org (OrgA) and thus legitimately knows OrgA's `webhook_secret`, and OrgB has an existing, non-archived `ReviewStack` for a guessable/observable PR number (PR numbers are sequential and often public). Attacker cost is minimal — one crafted HTTP POST to `/webhooks` with a valid HMAC computed from their own secret; no GitHub relay or MITM is needed since the endpoint accepts arbitrary self-crafted payloads, not just GitHub's real deliveries. Fully repeatable and scriptable against arbitrary victim orgs/PRs.

### Recommendation
Enforce that the organization used to select the webhook secret matches the organization that owns the mutated repository. Concretely:
- In `WebhooksController#verify_signature`, after resolving `repository_owner`, also derive the owner from `repository.full_name` (when present) and reject (422) if it disagrees with `repository.owner.login`/`organization.login`.
- In handlers (`ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.), pass the verified organization down (e.g., via a request-scoped attribute) and validate `repository.owner == verified_organization` before resolving `Repository.from_github_repo_name`, refusing to process otherwise.
- Alternatively/additionally, validate that `Repository#owner` matches the GitHub App's own organization (`Shipit.github(organization: owner)`) that produced the currently-verified signature, not merely an app config keyed by an attacker-supplied string.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), demonstrating both sides of the equality before/after the exploit:

```ruby
test "pull_request closed event signed by OrgA cannot archive OrgB's ReviewStack" do
  # Setup two orgs with distinct webhook secrets (multi-org secrets config)
  # OrgB has an active, non-archived ReviewStack for PR #99
  org_b_repo = shipit_repositories(:org_b_repo) # owner: "orgb"
  review_stack = create_review_stack(repository: org_b_repo, pr_number: 99)
  assert_not review_stack.archived?

  payload = {
    action: "closed",
    number: 99,
    pull_request: { id: 1, number: 99, url: "u", title: "t", state: "closed",
                     additions: 1, deletions: 1,
                     head: { sha: "abc", ref: "feature" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { owner: { login: "orga" }, full_name: "OrgB/protected-repo" },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_webhook_secret, payload)

  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  post :create, body: payload, as: :json

  # Assert the binding: verifying org (OrgA) != owning org (OrgB) -> should NOT mutate OrgB's stack
  assert_response :ok # currently succeeds and processes the event (vulnerable)
  assert_not review_stack.reload.archived?, "OrgB's ReviewStack must not be archived by a payload signed with OrgA's secret"
end
```
Without a fix, this test fails: `review_stack.reload.archived?` becomes `true`, proving the cross-tenant mutation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
