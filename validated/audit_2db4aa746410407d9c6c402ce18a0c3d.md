### Title
Unhandled `throw` in `validateAndSavePrivatePaymentChain` leaks a pooled DB connection and can crash the node on a crafted private payment - (File: private_payment.js)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` takes a DB connection from the pool, opens a transaction, and then runs a duplicate-check query. If more than one matching output row is found, the code executes a bare `throw Error(...)` instead of routing through `transaction_callbacks.ifError`/`ifOk`. This throw happens inside an asynchronous callback, so the connection acquired via `db.takeConnectionFromPool()` is never rolled back or released, and (depending on whether the process has a global handler) the exception can also crash the whole node process. This matches the CWE-404 "Improper Resource Shutdown or Release" bug class from the GoPistolet advisory: a resource (here, a pooled DB connection / open transaction) is not released when an error path is taken.

Every other completion path in this function goes through `transaction_callbacks.ifError` or `ifOk`, both of which issue a `ROLLBACK`/`COMMIT` and call `conn.release()` to return the connection to the pool (`sqlite_pool.js`/`mysql_pool.js` connection objects, see `sqlite_pool.js:74-82`). The `rows.length > 1` branch, however, bypasses this cleanup entirely and throws synchronously inside the query callback. The connection remains marked `bInUse = true` and stuck inside an open (uncommitted) transaction forever, and the exception propagates as an uncaught error in the event loop (there is no `try/catch` around this call chain, and this is a low-level module without a domain wrapper).

`validateAndSavePrivatePaymentChain` is reachable by any private-payment counterparty (a device that sends a private payment/chain to a wallet or hub):
- Directly, via `network.js` `handleOnlinePrivatePayment()` → `privatePayment.validateAndSavePrivatePaymentChain(...)` [2](#0-1) 
- Via `network.js` `handleSavedPrivatePayments()` for chains stored in `unhandled_private_payments` [3](#0-2) 
- Via `wallet.js` `handlePrivatePaymentChains()`, which validates chains received directly from another device over the private-payment protocol [4](#0-3) 

The duplicate-check SQL matches rows by `unit`, `asset`, `message_index` (and `output_index` for indivisible/fixed-denomination assets). Because the `outputs` table is populated as private payments/chains for the same unit are processed (e.g., a recipient chain and a change/cosigner chain for the same payment, or repeated resubmission with slightly different hidden/unhidden output fields), an attacker who controls a private payment counterparty can engineer more than one row to already exist for the same `(unit, asset, message_index[, output_index])` key before this check runs (e.g., by sending crafted or duplicated private elements/chains that get inserted through different code paths before the duplicate check executes), triggering the `rows.length > 1` branch.

### Impact Explanation
Reaching the `throw` branch:
1. Leaves the acquired connection permanently checked out of the pool (`bInUse` never reset, transaction never rolled back), which — if triggered repeatedly — exhausts the finite SQLite/MySQL connection pool (`MAX_CONNECTIONS` in `sqlite_pool.js`, `conf.database.max_connections` in `mysql_pool.js`), so the node can no longer take new connections to validate/write any further units, payments, or AA triggers, i.e., the node becomes unable to process the network — a denial of service.
2. If the process has no defensive `uncaughtException` handler around this particular code path, the thrown error can crash the entire ocore process, taking down the node/wallet/hub entirely.

Both outcomes match "a network unable to confirm new units" / node inoperability, which is in the accepted-impact list for this analog.

### Likelihood Explanation
The trigger condition (`rows.length > 1` matching rows for the same unit/asset/message_index/output_index) requires the attacker to get two output rows inserted for that key before the duplicate check runs — feasible for a counterparty who controls the exact sequencing/content of private chains sent to a victim's device (private payments are attacker-supplied JSON structures processed directly from `handlePrivatePaymentChains`/`handleOnlinePrivatePayment` with minimal structural validation before reaching this code). This does not require any privileged network position, hub cooperation, or malicious peer/node — it only requires being a private-payment counterparty, which is explicitly in scope. Reliability of hitting the exact race/ordering may vary, so likelihood is assessed as Medium.

### Recommendation
Replace the bare `throw` with a call into `transaction_callbacks.ifError(...)` so that the transaction is rolled back and the connection is released before surfacing the error to the caller:
```js
if (rows.length > 1)
    return transaction_callbacks.ifError("more than one output " + sql + ' ' + params.join(', '));
```
More generally, audit other `throw` statements inside connection-holding async callbacks in `private_payment.js`, `indivisible_asset.js`, and `divisible_asset.js` for the same pattern, and ensure every code path that acquires a connection via `db.takeConnectionFromPool()` guarantees `conn.release()` (e.g., via `try/finally`-style wrapper or consistently routing all errors through the existing `ifError`/`ifOk` cleanup callbacks).

### Proof of Concept
1. As a private-payment counterparty (attacker device), send a private payment/chain (`handlePrivatePaymentChains` via `wallet.js`, or `handleOnlinePrivatePayment` via `network.js`) for a given `unit`/`asset`/`message_index` (and `output_index` for a fixed-denomination asset).
2. Cause two separate insertions into the `outputs` table for that same `(unit, asset, message_index[, output_index])` key prior to the duplicate check — e.g., by concurrently/sequentially delivering a recipient chain and a cosigner/change chain that both populate the same output row key, or by resending the private element with variations that still satisfy the SQL match criteria while a previous insert is still pending validation.
3. When `validateAndSavePrivatePaymentChain` runs its duplicate check (`private_payment.js:70-75`) and finds `rows.length > 1`, it throws, leaking the connection checked out at `private_payment.js:45` (never rolled back or released) and potentially crashing the process if uncaught.
4. Repeating this against a victim's wallet/hub node exhausts the DB connection pool over time, preventing the node from validating/saving any further units or payments.
