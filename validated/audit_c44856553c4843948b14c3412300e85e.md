### Title
Webhook signature is verified against the GitHub App secret of an attacker-chosen organization, but the event handlers act on a repository named independently in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App's `webhook_secret` to validate a webhook against by reading an unauthenticated field from the payload itself, then, once that check passes, the event handlers act on a *different* payload field (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. On a Shipit instance configured with multiple GitHub organizations (`docs/setup.md` "Using Multiple Github Applications"), the field used to select the verifying secret and the field used to select the target repository are not cryptographically bound to each other, only the raw body as a whole is HMAC'd. An administrator of one configured GitHub App (their own org) can therefore forge webhook payloads that pass signature verification but are processed as events for a different organization's repository/stack in the same Shipit deployment.

### Finding Description
`verify_signature` selects the `GithubApp` (and hence the `webhook_secret` used for HMAC verification) using: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the JSON body (`repository.owner.login`, falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` returns the `GithubApp` instance configured under that organization's key in `config/secrets.yml` (see the multi-org config shape in `docs/setup.md`, e.g. `somegithuborg` / `someothergithuborg`), each with its own independent `webhook_secret`: [3](#0-2) 

Once the HMAC check passes, control passes to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler` and `StatusHandler`, which resolve the *target* repository/stack from a completely different field of the same payload, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the whole raw body is HMAC'd with a *secret keyed by an org name taken from that same body*, nothing prevents `repository.owner.login` (used to pick the verifying secret) from being a different organization than `repository.full_name` (used to pick the mutated `Stack`/`Repository`). The binding that should hold is:

`organization whose secret signed the request == organization owning the repository the handlers act on`

but the code only enforces:

`HMAC(raw_body, secret_of(payload["repository"]["owner"]["login"])) == signature`

with no constraint tying `payload["repository"]["owner"]["login"]` to `payload["repository"]["full_name"]`. An attacker who administers a GitHub App for `OrgA` (and therefore legitimately knows `OrgA`'s `webhook_secret`, since GitHub App owners set/see this value themselves) can craft `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo"}, ...}`, sign it with `OrgA`'s secret, and have it accepted as if it came from GitHub for `OrgB/target-repo`.

### Impact Explanation
With `PushHandler`, the forged event triggers `stack.sync_github(expected_head_sha: ...)` for any stack of `OrgB/target-repo`, i.e. an unprivileged-in-`OrgB` attacker can force a resync to an attacker-chosen SHA. With `StatusHandler`, the attacker can inject arbitrary commit statuses (`state`, `context`, `target_url`, `description`) for commits belonging to `OrgB`'s stacks via `Commit#create_status_from_github!`. Since commit/check statuses commonly gate whether a commit is "deployable" (merge/deploy eligibility in Shipit's UI and API), this lets an attacker with no relationship to `OrgB` other than knowledge of `OrgA`'s webhook secret fabricate green CI signals or force syncs against `OrgB`'s repositories — a cross-organization write achieved purely by exploiting the confused-deputy binding, without ever holding an `ApiClient` token, a Shipit session, or GitHub write access to `OrgB`. This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar, since fabricated commit statuses directly influence deploy eligibility decisions elsewhere in the engine.

### Likelihood Explanation
This requires a Shipit installation configured with more than one GitHub organization (an explicitly documented, supported configuration in `docs/setup.md`), and the attacker must be someone who legitimately administers one of those GitHub Apps (thus knows that org's `webhook_secret`) but is not authorized on the target org. This is a realistic multi-tenant scenario (e.g., a shared internal Shipit instance serving several business units/orgs, each running their own GitHub App). No GitHub write access, Shipit session, or API token is required — only the webhook secret of any one configured org and the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Do not use an untrusted, attacker-suppliable field of the payload to select the verifying secret and then trust an unrelated field of the same payload for authorization decisions. Concretely:
- Require that `repository.owner.login` (or `organization.login`) used for signature verification match the owner encoded in `repository.full_name` before dispatching to handlers; reject the webhook otherwise.
- Alternatively, attempt verification against all configured `webhook_secret`s and only accept the payload if the *matching* organization equals the owner of `repository.full_name`, closing the gap between "who authenticated" and "whose repository is written."

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with independent `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. As the administrator of `OrgA`'s GitHub App (a normal, unprivileged position with respect to `OrgB`), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, verifies successfully against `OrgA`'s secret [1](#0-0) .
5. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `"OrgB/target-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack [5](#0-4)  — despite the request never being signed by `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
