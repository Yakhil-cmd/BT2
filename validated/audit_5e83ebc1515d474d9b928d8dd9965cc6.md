## Analysis

The Kyber Router.sol bug is fundamentally a "hash-collision undermines an identity check" issue: an address computed as `hash(inputs)` is trusted as an authorization/ownership proof without further validation, and the *effective* collision resistance of that hash is lower than its nominal bit-length suggests.

`ocore`'s own address scheme (`chash.js`, used everywhere identity/ownership is proven by hash match — `validation.js`'s `validateDefinition`, `signed_message.js`, `wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js`, AA addresses, etc.) has exactly this property, and it is *worse* than the nominal 160-bit encoding suggests.

### Title
Obyte "chash" addresses have only 128 bits of real collision resistance, not 160, enabling first-use address hijacking - (File: chash.js)

### Summary
`getChash160()` in `chash.js` derives every ocore address from a RIPEMD160 hash, but discards 32 of its 160 bits and replaces them with a "checksum" that is itself a deterministic function of the remaining 128 bits, contributing zero independent entropy. Consequently, every 32-character ocore address (`sig`, multisig, shared, and AA addresses) is really only backed by 128 bits of hash security, not 160. Because ocore's core validation logic (`validation.js`) accepts the *first* definition array whose `getChash160()` output matches an address as the permanent, authoritative owner of that address (analogous to Router.sol trusting `msg.sender == computeAddress(...)` without checking the factory), an attacker who can find a collision between a self-controlled `sig` definition and an already-funded address can permanently bind their own key as the address's owner and steal all funds ever sent to it.

### Finding Description
`chash.js#getChash` (lines 122-142):
```js
var hash = crypto.createHash("ripemd160").update(data, "utf8").digest(); // 160 bits
var truncated_hash = hash.slice(4); // drop first 4 bytes -> only 128 bits remain
var checksum = getChecksum(truncated_hash); // checksum = sha256(truncated_hash) picks 4 bytes
var binChash = mixChecksumIntoCleanData(binCleanData, binChecksum); // interleave 128+32 bits -> 160-bit encoded string
``` [1](#0-0) 

The `checksum` is fully determined by `truncated_hash` via `getChecksum()`, so it is not additional secret entropy — it exists purely for error-detection (like a CRC), not for security: [2](#0-1) 

The final base32-encoded 32-character address therefore only encodes 128 bits of unpredictable hash output, even though it looks like a full 160-bit RIPEMD160 hash (unlike Bitcoin's Base58Check, which appends an independent 4-byte checksum *after* a full, untruncated 160-bit HASH160 and therefore keeps full 160-bit security).

This weakened hash is then relied upon as the sole ownership/authorization proof for an address the very first time it is used, exactly like Router.sol trusting a hash-derived address as a valid pool without checking the factory:
```js
storage.readDefinitionByAddress(conn, objAuthor.address, objValidationState.last_ball_mci, {
    ifDefinitionNotFound: function(definition_chash){ // first use of the definition_chash (=address)
        if (objectHash.getChash160(arrAddressDefinition) !== definition_chash)
            return callback("wrong definition: ...");
        callback();
    },
    ...
``` [3](#0-2) 

Once an address's definition_chash has never been bound (i.e., an address received funds but has never authored a unit), whoever is first to post a unit with *any* definition array (e.g., a trivial `['sig', {pubkey: attacker_pubkey}]`) that hashes via `getChash160` to that address becomes the permanently-authoritative signer of that address. The same "trust the hash, no additional binding" pattern is used across `wallet_defined_by_addresses.js` (`handleNewSharedAddress`) and `signed_message.js` (`validateOrReadDefinition`), so any address that has received value but not yet revealed/used its real definition is exposed. ### Impact Explanation
Because the collision space is only 2^128 (not 2^160), the birthday-bound attack value is `k = sqrt(2·2^128) ≈ 2^64.5`, dramatically lower than the ≈2^81 hashes calculated in the Kyber Router report (which Sherlock still accepted as a valid Medium). A 2^64-class collision search is already demonstrated feasible in the real world for comparably-sized hash outputs (e.g., Google's 2017 SHA-1 collision at ~2^63.1 operations), and will only get cheaper over time as noted extensively in the referenced discussion. A successful attacker can:
- Permanently seize control of any address that has received (or will receive) funds before its owner has ever authored a unit from it (a common state for cold/rarely-used deposit addresses, since ocore, like Bitcoin, lets you receive funds to an address whose definition has never been posted on-chain).
- Drain all funds ever sent to that address, and permanently deny the legitimate owner the ability to ever use it (once the definition_chash is bound to the attacker's definition, `handleDuplicateAddressDefinition` will reject the true owner's definition as a mismatch).
This is unauthorized-fund theft with material loss, matching the "concrete unauthorized spending" bar.

### Likelihood Explanation
This requires substantial (but not physically or economically absurd) targeted compute, similar to the Kyber case, but is *more* likely to be exploited sooner because the real security margin (128 bits) is far below what address holders and downstream integrators assume (160 bits, since the encoded chash is 160 bits long). As with the Kyber M-2 finding accepted by Sherlock as Medium, compute/storage cost trends downward every year while the vulnerable class of addresses (any address that has received value but never spent) is unboundedly large and grows over time, and `chash.js` is an unfixable, foundational, core protocol component (changing it is a hard fork).

### Recommendation
Stop discarding hash bits to make room for a derived checksum. Either:
- Use the full 160-bit RIPEMD160 output as the "clean data" and append an independently-keyed or externally-appended checksum (as Bitcoin's Base58Check does), rather than slicing off bytes from the hash and mixing in a checksum computed from the remainder, or
- Move to a wider hash function (e.g., use the full un-truncated hash, or increase to a 256-bit hash) for address derivation so that even after reserving bits for a checksum, at least 128+ bits of independent, unpredictable hash output remain.

### Proof of Concept
1. Victim address `A = chash160(D_victim)` for some as-yet-unrevealed definition `D_victim` (e.g., a fresh `sig` address that has only received payments, never authored a unit).
2. Attacker enumerates `2^64`–`2^65` candidate `sig` definitions of the form `['sig', {pubkey: P_i}]` for freshly generated keypairs `P_i`, computing `chash160(['sig', {pubkey: P_i}])` for each, until one matches `A` (birthday-bound search over the effective 128-bit space, per `chash.js#getChash`'s truncation of RIPEMD160 to 128 real bits at line 127 `hash.slice(4)`).
3. Attacker submits a unit authored by address `A`, with `author.definition = ['sig', {pubkey: P_match}]` and a valid signature under `P_match`'s private key.
4. `validation.js#validateDefinition`'s `ifDefinitionNotFound` branch checks only `getChash160(arrAddressDefinition) === definition_chash`, which now passes for the attacker's definition since it collides with `A`. [6](#0-5) 
5. The unit is accepted; address `A` is now permanently bound to the attacker's key, and the attacker can spend any/all outputs previously sent to `A`.
