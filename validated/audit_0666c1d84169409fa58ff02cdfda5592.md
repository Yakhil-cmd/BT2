### Title
Cross-Repository Commit Status Forgery via Unscoped `Commit` Lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController` verifies an inbound GitHub webhook's signature using the secret configured for the **organization named in the payload** (`repository.owner.login`), then dispatches the same payload to an event handler. For `push` and `check_suite` events, the handler correctly scopes its writes to `Repository.from_github_repo_name(repository_name)` — i.e., the repository that was actually authenticated. `StatusHandler`, however, looks up commits solely by `sha` across the *entire* `Commit` table, with no repository/organization scoping at all, breaking the binding between "organization whose secret authenticated the request" and "repository whose state is written."

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the payload and verifies the raw body against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

Once verified, the raw params are handed to the registered handler for the event, unmodified: [3](#0-2) 

The base `Handler` class exposes a helper that correctly scopes lookups to the repository named in the (now-verified) payload: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` use this `stacks` helper, so their writes are confined to stacks belonging to `repository.full_name` from the same authenticated payload: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, bypasses `repository_name`/`stacks` entirely and resolves target rows purely by commit SHA, globally: [7](#0-6) 

This means the only binding actually enforced end-to-end is "signature valid for organization X," while the effect applied is "write a commit status onto whichever `Commit` row anywhere in the database happens to share that SHA" — which may belong to a stack under a completely different, unrelated repository/organization than X. This is the same class of bug as the report: a check is performed against one value (the org that signed the payload) while the actual effect (which commit/repository record gets mutated) is determined by a field that was never bound to that check.

### Impact Explanation
An attacker who can trigger a genuinely GitHub-signed `status` webhook for *any* organization/repository configured in this Shipit instance (e.g., their own tracked repository, via a CI integration they control) can set `sha` to a commit SHA that also exists as a `Commit` row belonging to a different, unrelated stack (e.g., forked/mirrored repositories, monorepos split across multiple tracked stacks, or shared base commits). `StatusHandler` will apply the forged status to that unrelated commit via `Commit#create_status_from_github!`, regardless of which organization's secret validated the request. Because commit statuses gate `ci.require`/deployability and continuous delivery triggers, this can be used to force a "success" status onto a commit in a stack the attacker does not control, enabling an unauthorized deploy/continuous-delivery trigger for that stack — crossing a repository trust boundary that the webhook signature was supposed to enforce.

### Likelihood Explanation
Exploitability requires the attacker to control at least one repository/organization onboarded to the same Shipit instance (to legitimately trigger a signed `status` webhook) and for a target commit SHA to also exist as a tracked `Commit` in another stack (common with forks, mirrors, or shared history across multiple tracked repos of the same upstream project). This is a real but narrower precondition than a fully unauthenticated attack, so likelihood is moderate rather than trivial.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the verified payload, consistent with `PushHandler`/`CheckSuiteHandler`, e.g. via `stacks.flat_map(&:commits).where(sha: params.sha)` or by joining through `Repository.from_github_repo_name(repository_name)` before filtering by SHA, so a commit status can never be applied outside the repository that the webhook signature actually authenticated.

### Proof of Concept
1. Shipit is configured with multiple GitHub organizations/apps, each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`).
2. Attacker controls repository `attacker-org/repo`, tracked as a Shipit stack, and can trigger a genuine `status` webhook (e.g., via their own CI) with an arbitrary `sha`.
3. Attacker sets `sha` equal to a commit that is also stored as a `Commit` row for stack `victim-org/repo` (shared commit history, e.g., a shared upstream commit present in both a fork and the original).
4. `WebhooksController#verify_signature` validates the signature against `attacker-org`'s secret — verification succeeds because the payload's `repository.owner.login` is `attacker-org` and it is genuinely signed.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter, matches the commit belonging to `victim-org/repo`, and calls `create_status_from_github!`, forging a CI status on a repository the attacker never authenticated against.
