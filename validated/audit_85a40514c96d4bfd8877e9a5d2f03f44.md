### Title
Asset definer can front-run pending attestation-gated payouts by instantly swapping the `asset_attestors` list - (File: validation.js)

### Summary
Assets with `spender_attested: true` gate every payment/issue by checking whether the output/issuer addresses are currently attested by an address on the asset's *trusted attestor* list. This trusted attestor list is set at asset creation and can be changed at any time via an `asset_attestors` message, with the only requirement being that the author is the asset's `definer_address`. There is no cooldown, no restriction tied to already-pending spends, and no snapshot binding a specific attestation to the attestor-list state at the time it was granted.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment (`validatePayment` → `validatePaymentInputsAndOutputs`) must have its output addresses currently attested by one of the addresses in `objAsset.arrAttestorAddresses`: [1](#0-0) 

The attestor list itself is not fixed — it is looked up dynamically as "the latest attestor list before last_ball_mci" every time an asset is read: [2](#0-1) 

Updating this trusted attestor list is trivially permitted for the asset definer at any time, with no timing or state restrictions beyond checking authorship and a valid attestor array: [3](#0-2) 

This is directly analogous to the reported `OngoingBountyV1.setPayout` issue: a privileged party (there, the bounty owner; here, the asset `definer_address`, e.g. a "bounty"/reward-token issuer) can unilaterally and instantly change a parameter that determines whether a specific contributor's pending payout is valid, with no restriction on timing relative to contributors' in-flight claims. A contributor who was attested (eligible) and who composes/broadcasts a payment (claim) of the attestation-gated asset can be front-run: the definer observes the pending claim (e.g., in the network/mempool) and immediately posts a new `asset_attestors` message dropping/rotating the attestor address that vouched for the contributor. Because the check in `validatePaymentInputsAndOutputs`/`validatePayment` re-evaluates attestation status against the *current* (latest, most-recently-confirmed-before-last-ball) attestor list rather than the state at time the contributor was originally attested, the contributor's previously-valid, already-signed claim unit becomes invalid once the attacker's `asset_attestors` update is included with an mci at or before the claim's `last_ball_mci`.

### Impact Explanation
A malicious or self-interested asset definer (analogous to a "bounty owner") can retroactively invalidate a contributor's legitimately-attested eligibility right before their payout/claim confirms, causing the honest contributor's unit to be rejected ("some output addresses are not attested" / "none of the authors is attested"), wasting the contributor's transaction fees and denying them the promised payout while giving the definer full unilateral control over who ultimately gets paid. This matches the Medium-severity impact class of the source report: privileged party can cheat a counterparty out of an expected payout via an unrestricted last-moment parameter change.

### Likelihood Explanation
The `asset_attestors` message has no cooldown, no reference to any specific asset spend, and only requires authorship by the definer — this makes the front-run trivially and repeatedly executable by any asset issuer who wants to grief or selectively deny specific contributors, and is entirely within the reach of an unprivileged issuer/attestor role interacting with the asset issuance/attestation mechanism (no p2p, node, or operator privilege required).

### Recommendation
Bind attestation eligibility checks to a stable historical point (e.g., require the attestation to have been valid at the mci the contributor's spend was created/signed, or require a minimum delay/timelock before an `asset_attestors` update takes effect) so that a definer cannot retroactively invalidate a contributor's already-obtained, valid attestation for a specific pending spend.

### Proof of Concept
1. Definer creates an asset `spender_attested: true` with attestor oracle `A`. [4](#0-3) 
2. Oracle `A` attests contributor `C`'s address as eligible.
3. `C` composes/broadcasts a payment of the asset to their own (attested) address as their bounty payout.
4. Definer sees the pending payment and immediately posts a new `asset_attestors` message removing `A` (or replacing with an oracle that will never attest `C`). [3](#0-2) 
5. If the definer's update unit stabilizes with mci ≤ the `last_ball_mci` that ends up being used to validate `C`'s payment, `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` will no longer find `C`'s address attested by the (now-current) attestor list, and `C`'s claim fails validation, cheating `C` out of the payout. [2](#0-1)

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
