### Title
Nested AA definitions embedded in `definition` messages skip full recursive `validateAADefinition` checks - ([File: aa_validation.js])

### Summary
When an Autonomous Agent (AA) posts a `definition` message (i.e., an AA response creates/registers a nested AA), the payload's inner `["autonomous agent", {...}]` definition is validated only shallowly, and the original recursive call into `validateAADefinition` for the nested definition has been commented out. This mirrors the Deno bug class where a dynamically loaded module's own (transitively imported) resources bypass the permission/validation checks that are otherwise enforced on top-level imports.

### Finding Description
`validateAADefinition()` in `aa_validation.js` recursively walks an AA's payload structure and, for `case 'definition'` (an AA definition embedded as a message payload), only performs shallow structural checks: [1](#0-0) 

It checks that `payload.definition` is a 2-element array, that `payload.definition[0] === 'autonomous agent'`, and that `payload.definition[1]` is a non-empty object (or, post `aa2UpgradeMci`, that it may be a formula). It does **not** recursively invoke `validateAADefinition` on `payload.definition` itself — the line that would do so is explicitly commented out with the note "interrupt the call stack to protect against deep nesting": [2](#0-1) 

By contrast, a genuinely top-level AA definition (one posted directly as a `definition` message on a unit, or the base AA definition validated via `tools/validate_aa_definitions.js`/`validation.js`) is fully validated by `validateAADefinition`, which enforces the oscript op whitelist, formula validity, getters complexity budget (`complexity > 0` check on getters), `MAX_DEPTH`, and other structural/semantic constraints throughout the whole tree (see the getters-complexity enforcement and depth-limited recursive `validate()`): [3](#0-2) 

Because the nested/child AA definition embedded inside a `definition` message payload never goes through this full recursive `validate()`/`validateFormula()` pipeline, an unprivileged unit poster (or an AA author whose AA emits such a message in a response) can embed a nested AA definition object whose internal formulas/oscript were never checked for the same complexity limits, whitelisted operations, or structural correctness that are mandatory for any other AA definition in the system.

### Impact Explanation
If nodes accept and register a child AA definition that was never fully validated the way ordinary top-level AA definitions are, that AA can end up in a state that other parts of the codebase (formula evaluation, complexity accounting, `getGettersFromLocals`, remote getter calls) assume is impossible for a "validated" AA. This can produce inconsistent behavior at execution time between nodes (e.g., depending on when/whether a node re-validates vs. trusts the stored definition), which maps to node disagreement on validity/stability of units that trigger or reference the nested AA, or to an AA getting stuck/unusable (fund freezing) if its unchecked definition later fails unexpectedly during trigger processing.

### Likelihood Explanation
Reaching this code path only requires posting/triggering an AA that emits a `definition` message with a crafted `payload.definition` — well within reach of an ordinary unprivileged unit poster or AA trigger sender, with no special privileges needed. This matches the reachability constraints of the target bug class (single posted unit/trigger reaching validation logic).

### Recommendation
Restore full recursive validation of nested AA definitions: re-enable a bounded recursive call into `validateAADefinition` (or an equivalent full validator, guarded by `setImmediate`/depth-limits to avoid stack blowup, similar to the commented-out line) for `payload.definition` in the `case 'definition'` branch, so nested AA definitions receive the same complexity, op-whitelist, and formula validation as top-level AA definitions before being accepted as valid.

### Proof of Concept
I could not fully trace, within the available iterations, how a registered-but-shallowly-validated nested AA definition is subsequently consumed at execution time (e.g., in `aa_composer.js`) to confirm whether a concrete double-spend/fund-loss/consensus-fork can be triggered end-to-end; this would need to be confirmed against `aa_composer.js`'s handling of `definition` messages and whether it re-validates or trusts the stored definition before execution. Given index limits, a full trace of `aa_composer.js`'s definition-message handling was not completed — this should be verified in a full Devin session with complete file access before treating this as fully proven versus a partially-mitigated validation gap.
