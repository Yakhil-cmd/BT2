### Title
Command interpolation falls back to the deploy host's real process environment, breaking the "permitted env keys" vs "env keys spawned into the command" binding - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#permit` enforces a strict whitelist binding *the env keys a user is allowed to set* to *the env keys that get spawned with a task/deploy*. However, a second code path, `EnvironmentVariables#interpolate` (used by `Command#interpolate_environment_variables` to expand `$VAR` references inside `shipit.yml` step arguments), does not respect that same whitelist: when a referenced variable name is absent from the permitted/task `@env`, it silently falls back to the Shipit application process's own `ENV`, and the resolved value is spliced directly into the spawned command line and streamed back as task output.

### Finding Description
`TaskDefinition#filter_envs` binds "permitted variables" (`variables_with_defaults`/whitelist declared in `shipit.yml`) to the actual env passed into `Task`/`Deploy` records: [1](#0-0) 

`EnvironmentVariables#permit` is the enforcement point for that binding — any key not in `variable_definitions` raises `NotPermitted`: [2](#0-1) [3](#0-2) 

But the *same class* also exposes `interpolate`, used when a command's `shipit.yml` step string references `$VARIABLE`. Unlike `permit`, it does **not** raise on an unknown/unpermitted variable — it instead reads straight from the real OS environment of the Shipit worker/web process: [4](#0-3) 

This is invoked from `Command#interpolate_environment_variables`/`#interpolated_arguments`, which builds the argv actually passed to `PTY.spawn`: [5](#0-4) [6](#0-5) 

So the equality the design intends is:
`{keys permitted by TaskDefinition#filter_envs} == {keys usable inside a shipit.yml step}`

but the actual behavior is:
`{keys permitted by TaskDefinition#filter_envs} ⊂ {keys resolvable inside a shipit.yml step}` (superset includes the full deploy-host process `ENV`).

Any `shipit.yml` step (custom task, deploy step, review-app step, etc.) that references `$SOME_HOST_SECRET` — a name that is *not* declared as a task variable and therefore never goes through the whitelist/validation — will have that variable resolved from the real process environment of the Shipit server (e.g. `SECRET_KEY_BASE`, `REDIS_URL`, `DATABASE_URL`, injected CI/host credentials, etc., anything present in the Rails process's `ENV`) and injected into the argv of the spawned subprocess, whose stdout/stderr is then streamed to the task output page.

### Impact Explanation
Task/deploy output is visible to any authenticated user with `read:stack` (an unprivileged, non-admin permission per `app/controllers/shipit/api/*`). If a `shipit.yml` step references an env-var name that happens to collide with a real environment variable configured on the Shipit host (which is very plausible for common names like `PATH`, `HOME`, `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, etc.), the value gets echoed into command output and exposed to any user who can view that stack's task page — an unintended disclosure of host/application secrets that were never meant to cross the trust boundary between "declared task variables" and "actual process environment." This matches the Impact criteria of credential exfiltration.

### Likelihood Explanation
This requires only normal, pre-existing configuration capability: whoever authors a `shipit.yml` (deploy/task step definitions, which is a routine, low-privilege repository content change rather than a privileged Shipit action) can reference `$ANY_NAME` in a step's arguments. No malicious "attacker-controlled webhook forgery" or credential theft is needed to trigger the fallback — it happens implicitly whenever a referenced name isn't part of the declared, whitelisted `variables:` list, which is easy to happen accidentally (typo in a variable name) or deliberately. Given `test/unit/environment_variables_test.rb` only tests `permit`, not `interpolate`'s fallback behavior, the gap looks unintentional and untested.

### Recommendation
- Make `EnvironmentVariables#interpolate` fail closed like `#permit`: raise `NotPermitted` (or leave the literal `$VAR` un-substituted) when the variable is not present in the sanitized/permitted `@env`, instead of falling back to `ENV[variable]`.
- Audit `Command#unbundled_env`/`BASE_ENV` construction as well, to confirm the spawned subprocess doesn't otherwise inherit sensitive parent-process variables beyond `PATH`.
- Add regression tests asserting that `interpolate` cannot read arbitrary host environment variables.

### Proof of Concept
1. In a stack's `shipit.yml`, add a custom task whose step references an environment variable name that is not declared under that task's `variables:` list, e.g.:
```yaml
tasks:
  leak:
    action: "Leak"
    steps:
      - "echo $SECRET_KEY_BASE"
```
2. Any user with `deploy:stack`/task-trigger rights (a normal, unprivileged Shipit user) triggers the `leak` task via the tasks controller (`app/controllers/shipit/tasks_controller.rb`).
3. `TaskDefinition#filter_envs` validates only the explicitly provided `env` params against the whitelist (`lib/shipit/environment_variables.rb#permit`); `SECRET_KEY_BASE` is never in that whitelist and never rejected because it isn't user-supplied — it's referenced only inside the step text.
4. When the task runs, `Command#interpolated_arguments` calls `EnvironmentVariables#interpolate`, which does not find `SECRET_KEY_BASE` in the sanitized `@env` and falls back to `ENV['SECRET_KEY_BASE']` — the real value configured on the Shipit host process — substituting it into the command line.
5. The resulting `echo` output containing the real secret is streamed to the task page (`app/controllers/shipit/tasks_controller.rb#tail`), visible to any user who can view that stack's tasks.

**Note on certainty:** I was not able to run this end-to-end (no execution environment available in this ask-only session) to directly observe leaked values, so this is a static-analysis-based finding derived from tracing `interpolate`'s fallback to `ENV[variable]` versus `permit`'s strict whitelist rejection; the actual exploitability also depends on which process env vars are present on a given deployment's Shipit host and are not already deliberately exposed via `Shipit.env`/`machine.environment`.

```ruby
    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
```

```ruby
    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
```
