### Title
Webhook signature verification is scoped to `repository.owner.login`, but write actions are dispatched using the unrelated `repository.full_name` field, allowing cross-repository/cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, read from the payload field `repository.owner.login`. [1](#0-0) [2](#0-1)  However, once the signature check passes, every `Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to act on using a completely different payload field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`. [3](#0-2)  Nothing ties the organization whose secret validated the request to the repository that the handler subsequently mutates.

### Finding Description
The binding that should hold is: **organization whose webhook secret authenticated the request == organization owning the repository being written to**. The code breaks this equality because these are two independent lookups into the same JSON body, and only one of them is covered by the "trust" the signature is supposed to establish:

- `verify_signature` builds `Shipit.github(organization: repository_owner)` from `repository.owner.login` and calls `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `GithubApp#verify_webhook_signature` explicitly **returns `true` unconditionally when `webhook_secret` is blank**: `return true unless webhook_secret`. [4](#0-3)  The webhook secret is documented as optional (`webhook_secret: # nil`) in the setup docs and example secrets file. [5](#0-4) 
- After the (possibly no-op) signature check passes, `WebhooksController#create` dispatches the raw parsed payload to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [6](#0-5) 
- Every handler (e.g. `PushHandler`) resolves the target stacks purely from `payload.dig('repository', 'full_name')`, independent of whatever `repository.owner.login` was used to select the verifying app/secret. [3](#0-2) [7](#0-6) 

Concretely, in a Shipit instance configured with the documented multi-organization `github:` hash (one entry per GitHub org, each with its own `webhook_secret`), an attacker who is only authorized to send webhooks for `org-attacker` (e.g. because `org-attacker`'s entry has no `webhook_secret` configured, which is explicitly supported/blank-tolerant) can:

1. Set `repository.owner.login = "org-attacker"` so `verify_signature` selects `org-attacker`'s (blank) secret and trivially passes.
2. Set `repository.full_name = "org-victim/some-repo"` (any repository actually tracked by the Shipit instance) so the dispatched handler acts on a stack that has nothing to do with `org-attacker`.

Because the signature check and the write-target resolution consult two unrelated fields of the same untrusted JSON body, "authenticated as org A" never actually constrains "writes happen to org A's repositories."

### Impact Explanation
This is a cross-repository/cross-organization write primitive driven entirely by an unprivileged party who is legitimate only for one (weakly-configured) organization's webhook endpoint. Depending on which handler fires, this can:
- Trigger `Stack#sync_github` for a victim repository via `PushHandler`, forcing spurious commit ingestion/CI-status noise. [7](#0-6) 
- Manipulate `pull_request` handlers (`opened`, `closed`, `labeled`, etc.) that also resolve their target via `Repository.from_github_repo_name(repository_name)`, potentially influencing merge-queue/review-stack state for a repository the attacker does not own.
- Create/modify `Team`/`Membership` records via the `membership` handler for organizations the attacker was never a member of, since that handler is likewise driven by payload content rather than the authenticating organization.

This satisfies the "cross-repository writes" / "unauthorized deploy, rollback, or merge" Critical bar, since it is a genuine deployment-trust binding violation: the organization that authenticated is not the repository being written.

### Likelihood Explanation
The precondition is that the deployment uses the documented multi-organization GitHub configuration (`config/secrets.yml` with a nested `github:` hash keyed by org) and that at least one configured organization either has no `webhook_secret` set (explicitly supported as blank/optional) or the attacker otherwise knows/controls that organization's secret while a *different* organization's repository is also tracked by the same Shipit instance. This is a realistic deployment shape for organizations centralizing Shipit across multiple GitHub orgs, and requires no privileged Shipit session, API token, or GitHub App key — only the ability to POST to the public `/webhooks` endpoint, which is unauthenticated by design.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature matches the organization embedded in `repository.full_name` (and `organization.login`) before invoking handlers — reject the request if they diverge. Additionally, consider requiring `webhook_secret` to be present for every configured organization (removing the blank-secret bypass in `GithubApp#verify_webhook_signature`), or at minimum log/alert when an organization is configured without a secret.

### Proof of Concept
1. Configure Shipit with two orgs in `github:`: `org-attacker` (no `webhook_secret`) and `org-victim` (repository `org-victim/app` tracked by a `Stack`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/app"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-attacker")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header sent. [8](#0-7) 
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("org-victim/app")` and calls `sync_github` on `org-victim`'s stack — a write action against a repository/organization the attacker never authenticated for. [3](#0-2)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
