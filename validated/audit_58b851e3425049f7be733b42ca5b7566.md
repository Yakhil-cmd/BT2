## Analysis

The Trader Joe bug class here is: **a value the code trusts/enforces (checked/signed field) diverges from the value the code actually acts on**. The strongest analog in shipit-engine is in the webhook verification pipeline: the *organization used to select/verify the signing secret* is a different payload field than the *repository the handler subsequently writes to*.

### Root cause

`WebhooksController#verify_signature` derives the organization used to pick the GitHub App / webhook secret from one payload field: [1](#0-0) 

Specifically: [2](#0-1) 

That value is fed into `Shipit.github(organization: repository_owner)`, and the resulting app's `verify_webhook_signature` is used to accept/reject the request: [3](#0-2) 

Note `return true unless webhook_secret` — if the selected organization has no `webhook_secret` configured (an explicitly documented, optional setting), signature verification is a no-op and **any** payload/signature combination is accepted.

Meanwhile, every actual event handler resolves the target `Repository`/`Stack` from a *different* field of the same JSON body — `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

e.g. `PushHandler` triggers a GitHub sync for stacks matched that way: [5](#0-4) 

Pull-request handlers behave the same way: [6](#0-5) 

The multi-organization configuration, including the ability to leave `webhook_secret` empty per org, is a documented and supported deployment mode: [7](#0-6) [8](#0-7) 

### The broken binding

`organization authenticated (repository.owner.login → webhook_secret lookup) == repository written (repository.full_name → Stack/Repository lookup)` — this equality is never enforced. An attacker can set `repository.owner.login` to any configured organization that happens to have `webhook_secret` unset (bypassing signature verification entirely per the `return true unless webhook_secret` short-circuit), while setting `repository.full_name` to point at a completely different, properly-secured repository/stack tracked by Shipit. The handler dispatch only looks at `full_name`, so the forged, unsigned payload is processed as if it legitimately originated from GitHub for that other repository.

This lets an unauthenticated network attacker forge `push`, `pull_request`, `status`, `check_run`/`check_suite`, and `membership` webhook events against any repository/stack tracked by the instance — triggering GitHub syncs, review-stack provisioning/archival, commit status writes, and team membership changes — without ever possessing the secured org's `webhook_secret`, purely by exploiting the mismatch between the field used for authentication and the field used for authorization/action targeting.

### Title
Webhook signature verification keys off `repository.owner.login` while every handler acts on the independent `repository.full_name` field, letting an unconfigured-secret organization be used to forge events for any other tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a request against using `repository.owner.login` (or `organization.login`), but the event handlers that actually mutate state resolve their target `Repository`/`Stack` using the separate `repository.full_name` field. If any configured organization has no `webhook_secret` set (an officially supported configuration), the signature check becomes a no-op for payloads claiming that org, while the acted-upon repository can be forged to point anywhere else Shipit tracks.

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted, not-yet-verified body and uses it to fetch a `GitHubApp` instance whose `verify_webhook_signature` gates the request:
- `app/controllers/shipit/webhooks_controller.rb:24-49,59-62`
- `lib/shipit/github_app.rb:76-83` (`return true unless webhook_secret`)

Handlers never re-check `repository.owner.login`; they resolve their operating scope purely from `repository.full_name`:
- `app/models/shipit/webhooks/handlers/handler.rb:32-38`
- `app/models/shipit/webhooks/handlers/push_handler.rb:6-17`
- `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54` (and the other PR handlers)

Because these are two independent JSON fields in the same attacker-controlled body, a payload can claim ownership by an organization with no secret configured (bypassing verification) while directing the handler logic at a repository belonging to a different, secured organization.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out as a valid analog class. An unauthenticated attacker can forge webhook events (`push`, `pull_request`, `status`/`commit_status`, `check_run`/`check_suite`, `membership`) against any repository/stack tracked by the Shipit instance, as long as one configured organization in `secrets.github` lacks a `webhook_secret` — causing unauthorized GitHub syncs, review-stack creation/archival, commit status writes that can influence merge/deploy gating, and team membership churn, all without the secured organization's secret. This can escalate into unauthorized state changes on stacks (`Shipit.github_teams`-adjacent authorization surfaces, forged commit statuses feeding deploy/merge decisions), matching the High-impact category.

### Likelihood Explanation
Requires no credentials, sessions, or tokens — only an HTTP POST to `/webhooks` — and only requires that the deployment uses the multi-org config schema with at least one org's `webhook_secret` left blank, which is explicitly presented as a valid, documented option (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, `docs/setup.md`). This is a realistic operational configuration, not a misconfiguration outside the documented setup.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: verify against the secret/app that owns `repository.full_name`'s organization (not a possibly-different `repository.owner.login`/`organization.login`), and reject requests where an organization has no `webhook_secret` configured (fail closed instead of `return true unless webhook_secret`). Optionally, cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatch.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.github`: `OrgA` (has a real repo/stack tracked in Shipit, `webhook_secret` set) and `OrgB` (`webhook_secret: nil`, per the documented optional setting).
2. POST to `/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, with body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "full_name": "OrgA/tracked-repo", "owner": { "login": "OrgB" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgB")` → `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` nil for OrgB), so the request passes verification regardless of the signature header.
4. `PushHandler#process` resolves stacks via `repository.full_name` = `"OrgA/tracked-repo"` and triggers `stack.sync_github(expected_head_sha: params.after)` for OrgA's stack — an action normally gated by OrgA's (configured) webhook secret — without ever presenting OrgA's secret.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
