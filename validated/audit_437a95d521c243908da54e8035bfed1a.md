### Title
Attacker-controlled `repository.owner.login` selects the webhook signing secret used to verify a payload whose `repository.full_name` targets a different, unrelated stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to verify the HMAC signature against using a field read straight out of the *unauthenticated* JSON body, while the code path that actually mutates state (`PushHandler`, and other handlers) reads a *different* field of the same untrusted body to decide which `Repository`/`Stack` to act on. Nothing binds "the organization whose secret validated this request" to "the repository the handler subsequently writes to."

### Finding Description
`verify_signature` computes the org used for verification purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — both are attacker-supplied JSON fields with no cryptographic backing at the point they are read, since signature verification hasn't happened yet.

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` configured for that org, and verification is performed with that org's secret: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank/`nil` for the selected org — i.e. verification is a no-op for any org configured without a webhook secret (a supported, non-default configuration shown in `config/secrets.development.example.yml` and `docs/setup.md`, where `webhook_secret:` may be left blank).

Once `verify_signature` passes (either because the real signature matched, or because the attacker aimed the request at an org with no secret configured), `WebhooksController#create` dispatches to the registered handler for the event, passing the *entire raw payload* unchanged: [4](#0-3) 

The handler then independently re-reads the payload to determine which repository/stacks to mutate, via `repository.full_name` — a field that was never involved in the signature-org lookup used to authorize the request: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose secret validated the HMAC` == `owner of the repository the handler subsequently mutates`

But nothing enforces this equality: `repository_owner` (used to select the verifying secret) and `repository.full_name` (used to select the target `Stack`) are two independently attacker-controlled fields inside the same JSON body. An attacker can set `repository.owner.login` to an organization that Shipit has configured with `webhook_secret: nil` (or otherwise easy to satisfy), while setting `repository.full_name` to `"victim-org/victim-repo"` — a completely different, legitimately-tracked stack. `Repository.from_github_repo_name(repository_name)` will resolve to the victim stack and `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on it, all without the victim organization's webhook secret ever being checked.

### Impact Explanation
This allows an unauthenticated actor to forge push/status/pull_request/check_suite events for any stack tracked by the Shipit instance, as long as they can find (or are themselves) an org configured in `Shipit.github` without (or with a weak) `webhook_secret`. Effects vary by handler but include forcing `GithubSyncJob` re-sync with an attacker-chosen `expected_head_sha`, injecting fabricated commit statuses/check runs, and fabricating pull_request lifecycle events (open/close/label) against a stack whose repository is entirely unrelated to the "verifying" organization. Because `sync_github` and merge-queue/status logic feed directly into what Shipit considers deployable, this is a path to influencing deploy/rollback/merge decisions for a repository the attacker does not control and was never authenticated against — an unauthorized-deploy-adjacent authentication-bypass class issue, satisfying the "authentication bypass" / "unauthorized deploy" impact bar when the target org has no (or a guessable) webhook secret.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: it requires at least one org registered in `Shipit.github` with a blank/absent `webhook_secret`, or the attacker being able to guess/obtain a low-value org's secret (e.g., a sandbox/test org configured on the same Shipit instance as production stacks). The documentation and example configs (`config/secrets.development.example.yml`) explicitly show `webhook_secret` as optional/nilable, so this is not a purely theoretical operator error — the code deliberately supports "no secret" orgs via `return true unless webhook_secret`. Given that the org-selection field and the repository-target field are simply two different keys of the same unauthenticated JSON body, exploitation requires no privileged access — only knowledge of a misconfigured (secret-less) org name and the target repo's `owner/name`.

### Recommendation
Bind the field used to select the verifying secret to the field used to select the mutation target: verify the signature using the GitHub App corresponding to `repository.full_name`'s owner (not a possibly-different `organization`/`repository.owner.login` value), and reject payloads where these two fields disagree. Additionally, do not silently treat a blank `webhook_secret` as "verification passes" — require an explicit `Shipit.disable_webhook_signature_verification` style flag scoped per-installation instead of an implicit bypass whenever a secret is unset, and log/alert when a webhook is accepted without secret verification.

### Proof of Concept
1. Configure (or find) an org, e.g. `no-secret-org`, in Shipit's GitHub config with `webhook_secret: nil` (a supported configuration per `config/secrets.development.example.yml`).
2. Ensure a legitimate stack exists for `victim-org/victim-repo` (tracked separately, with its own, secret-protected GitHub App config).
3. POST to `/github/auth/github`'s sibling webhook endpoint with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
4. `verify_signature` resolves `repository_owner = "no-secret-org"`, fetches its `GitHubApp` (secret-less), and `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) regardless of the (even absent) `X-Hub-Signature` header.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name = "victim-org/victim-repo"` (`handler.rb:36-38`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim stack — a write triggered without ever validating any signature tied to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
