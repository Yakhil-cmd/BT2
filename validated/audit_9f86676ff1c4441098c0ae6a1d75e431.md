### Title
Unbounded per-MCI AA-trigger backlog causes serialized processing that blocks new-unit writes - (File: main_chain.js, aa_composer.js, writer.js)

### Summary
`markMcIndexStable()`'s inner `handleAATriggers()` (main_chain.js:1691-1723) collects, with no cap, every unit in the just-stabilized MCI that pays to a known AA address, inserts them all into `aa_triggers`, and signals the caller to run `aa_composer.handleAATriggers()`. That function (aa_composer.js:59-89) pulls **all** pending rows from `aa_triggers` and processes them strictly sequentially with `async.eachSeries`, each iteration opening its own DB connection/transaction (`handlePrimaryAATrigger`, aa_composer.js:91-150). Crucially, this entire sequential pass is awaited from inside `writer.saveJoint()` (writer.js:724-727, 754-758) while the global `write` mutex is still held (acquired at writer.js:34, released at writer.js:776), so no other unit — from any user — can be validated/saved until the whole AA-trigger backlog for that MCI has finished executing.

### Finding Description
An unprivileged unit poster can send ordinary payment units (paying only the required TPS fee, no special privilege) with tiny outputs addressed to one or more existing AA addresses. Each unit is limited to a single primary AA trigger by `validateAATrigger` [1](#0-0) , but nothing caps how many such units the attacker may post within one MCI, nor how many distinct AA addresses/units can accumulate as triggers in that MCI. When the MCI stabilizes, `markMcIndexStable`'s `handleAATriggers()` selects every matching `(unit, address)` pair for that MCI with an unbounded query and inserts them all into the `aa_triggers` table [2](#0-1) .

The actual execution of these triggers happens in `aa_composer.handleAATriggers()`, which loads the whole `aa_triggers` set and iterates it with `async.eachSeries`, invoking `handlePrimaryAATrigger` once per trigger — each call takes its own connection, begins a transaction, evaluates the AA formula, and commits [3](#0-2) [4](#0-3) . This call is awaited synchronously from `writer.saveJoint()`: [5](#0-4) 

and again for any further MCIs stabilized in the same write [6](#0-5) . All of this happens while the `write` mutex taken at the very start of `saveJoint()` is still held [7](#0-6) , and is only released after the entire AA-trigger backlog finishes [8](#0-7) . Since every unit save (by any peer) goes through `writer.saveJoint()` and must first acquire this same `write` lock, an inflated per-MCI AA-trigger backlog directly serializes and delays the write path for the whole node, exactly analogous to the referenced report's pattern of an attacker cheaply inflating a per-entity list that is later iterated in full by a critical function.

### Impact Explanation
While a single AA trigger is processed, the node cannot commit any other unit (from any user), because `saveJoint()` holds the `write` mutex for the duration of the entire trigger backlog. An attacker who spends a modest, predictable amount in TPS/transfer fees to post many low-value payments to AA addresses within one MCI can force the node to serially execute a correspondingly large batch of AA triggers (each with its own formula evaluation, DB transaction and commit) before the mutex is released, delaying acceptance/propagation of all other users' units for that duration. This matches the "network unable to confirm new units" impact class for the affected node during the backlog processing window.

### Likelihood Explanation
The TPS fee mechanism raises the cost of unit spam as network usage increases, but it does not impose any hard cap on the number of distinct low-value payments to AA addresses that can be included within a single MCI, nor any limit on the size of the `aa_triggers` batch computed per MCI. An attacker only needs ordinary wallet functionality (posting payments to well-known AA addresses) and is willing to pay linearly scaling fees, which is a modest cost compared with stalling the write path of a node for the whole serial-execution duration.

### Recommendation
Bound the number of AA triggers executed per MCI/per write (e.g., cap and defer excess to subsequent processing passes), and/or move `aa_composer.handleAATriggers()` execution outside the `write` mutex critical section so unrelated unit writes are not blocked while a large trigger backlog is processed. Consider parallelizing/batching trigger execution where the formulas do not have interdependencies, and revisit TPS-fee weighting so it scales more than linearly with the number of AA triggers targeted within a single MCI.

### Proof of Concept
1. Deploy/identify an existing AA address `A` on the network.
2. From an unprivileged wallet, repeatedly compose and post many minimal payment units, each sending a small amount to `A`, all landing within the same not-yet-stable MCI window (paying the applicable TPS fee each time).
3. Once that MCI stabilizes, `markMcIndexStable`'s `handleAATriggers()` will select every one of these units as an AA trigger with no upper bound and enqueue them in `aa_triggers` [9](#0-8) .
4. `writer.saveJoint()` will then `await aa_composer.handleAATriggers()` while still holding the `write` mutex [7](#0-6) [5](#0-4) , and `aa_composer.handleAATriggers()` will process the whole inflated batch serially via `async.eachSeries` [10](#0-9) , measurably delaying every other unit's commit until the batch completes.
