### Title
`Team.find_or_create_by!(github_id: params.team.id)` never re-checks `team.organization == params.organization.login` on find, letting a webhook from one GitHub organization mutate team membership for a `Team` belonging to a different organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` only assigns `team.organization = params.organization.login` inside the `find_or_create_by!` block, which Rails only executes when the record is *created*, not when an existing row is *found* by `github_id`. `MembershipHandler#process` then calls `team.add_member(member)` / `team.members.delete(member)` unconditionally, with no comparison between the persisted `team.organization` and the organization claimed in the current webhook payload.

### Finding Description
The broken binding is: for any subsequent membership webhook processed for a given `github_id`, `Team.find_by(github_id: params.team.id).organization` must equal `params.organization.login` before `add_member`/`members.delete` is trusted. That equality is never checked.

Code path:
- `find_or_create_team!` at [1](#0-0)  only sets `team.organization` inside the block passed to `find_or_create_by!`, which ActiveRecord skips when a row with the given `github_id` already exists.
- `process` at [2](#0-1)  calls `team.add_member(member)`/`team.members.delete(member)` with no check that `team.organization` matches `params.organization.login`.
- `WebhooksController#verify_signature` selects the GitHub App/secret to validate the signature based on the **payload's own** `organization.login` (via `repository_owner`, which falls back to `params.dig('organization','login')` for org-level events like `membership`), not based on the team's stored organization: [3](#0-2)  and [4](#0-3) .

Because signature verification is keyed off the attacker-claimed organization rather than the team's true organization, an attacker who administers their own GitHub organization onboarded into this same Shipit instance (multi-tenant install) knows that organization's own `webhook_secret` and can produce a validly-signed `membership` event whose `team.id` equals the numeric GitHub team ID of a team that actually belongs to a different, unrelated organization already in Shipit's database (e.g. one referenced by `Shipit.github_teams`). `Team.find_or_create_by!(github_id: ...)` finds that pre-existing row, skips the `organization=` assignment (leaving the stored value, e.g. `'shopify'`, untouched), and `team.add_member(member)` runs anyway - `member` being `User.find_or_create_by_login!(params.member.login)`, which fetches and locally materializes *any* GitHub login the attacker names via the global GitHub App client [5](#0-4) .

No other guard intercepts this: `drop_unhandled_event` only filters unhandled event types, the `ExplicitParameters` schema only validates shape/types of `team`/`organization`/`member`, and there is no model validation on `Team#organization` tying it to `github_id` immutably [6](#0-5) .

### Impact Explanation
`User#authorized?` grants Shipit access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) . If the targeted `Team` row's `id` is one of `Shipit.github_teams`, silently adding an attacker-chosen `User` as a member of that `Team` via a cross-organization webhook escalates that user into Shipit's privileged-team authorization without ever being a real member of the corresponding GitHub team. This is repeatable against any team `github_id` the attacker can guess or discover, for any organization already onboarded into the same Shipit instance, matching the High severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Exploitation requires the attacker to control (or administer) at least one GitHub organization that is already configured in this Shipit instance (multi-tenant deployment), so they know that organization's `webhook_secret` and can produce a validly-signed payload. `Shipit.github(organization:)` raises `GithubOrganizationUnknown` for organizations not configured at all, so a fully arbitrary/unregistered "attacker-org" cannot pass signature verification. Given a multi-tenant install (common for this engine, which supports many orgs/repos per instance), the attacker's own legitimate onboarding is sufficient; no Shipit session, API token, or GitHub App private key of another tenant is needed. The remaining requirement - guessing/discovering a target team's numeric GitHub `github_id` - is feasible since team IDs are visible via GitHub's team API/URLs to team members or via prior reconnaissance.

### Recommendation
In `find_or_create_team!`, after fetching/creating the team, always verify `team.organization == params.organization.login` (and ideally that `repository_owner`/signature-verified organization matches too) before proceeding, and raise/drop the event on mismatch instead of silently proceeding to `add_member`/`members.delete`.

### Proof of Concept
1. Fixture: create `shipit_teams` row with `github_id: 4242, organization: 'shopify', slug: 'legit-team'`, and configure it as a member of `Shipit.github_teams`.
2. Configure two orgs in `Shipit.github` config for the test: `shopify` (secret `S1`) and `attacker-org` (secret `S2`, attacker-controlled).
3. POST to `/webhooks` with header `X-Github-Event: membership`, signed with `S2`, and body:
   ```json
   { "action": "added",
     "team": { "id": 4242, "name": "legit-team", "slug": "legit-team", "url": "..." },
     "organization": { "login": "attacker-org" },
     "member": { "login": "attacker-login" } }
   ```
4. Assert response is `200 OK` (signature accepted for `attacker-org`).
5. Assert `Shipit::Team.find_by(github_id: 4242).organization == 'shopify'` (unchanged, proving the update never ran).
6. Assert `Shipit::Membership.exists?(team_id: team.id, user_id: User.find_by(login: 'attacker-login').id)` is `true` - proving membership was granted despite the organization mismatch.
7. Assert `User.find_by(login: 'attacker-login').authorized?` is `true` if the team is in `Shipit.github_teams`, demonstrating the authorization escalation.

# frozen_string_literal: true

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end

    def refresh_members!
      github_api = Shipit.github(organization:).api
      github_members = Shipit::OctokitIterator.new(github_api.get(api_url).rels[:members])
      members = github_members.map { |u| User.find_or_create_from_github(u) }
      self.members = members
      save!
    end

    def github_team=(github_team)
      self.name = github_team.name
      self.slug = github_team.slug
      self.api_url = github_team.url
      self.github_id = github_team.id
    end
  end
