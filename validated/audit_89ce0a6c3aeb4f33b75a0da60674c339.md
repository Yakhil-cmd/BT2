Based on my investigation, I found a genuine analog to the CVE's bug class (an internal structure reset in one place while a related structure retains a stale reference, later misused) in the AA (Autonomous Agent) trigger-execution/rollback path.

### Title
Stale in-memory unit-props cache after AA chain `ROLLBACK TO SAVEPOINT` causes DB/cache desync on `latest_included_mc_index` and stability state - (File: `aa_composer.js`, `main_chain.js`, `writer.js`)

### Summary
When a primary AA trigger dispatches a chain of secondary AA responses, each response unit is written through `writer.saveJoint()`, which synchronously mutates shared in-memory unit-props objects (`storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`) as part of `main_chain.updateMainChain()` — in the *same* SQL transaction used for the whole AA chain. If a later secondary AA in the chain bounces, `aa_composer.js`'s `revert()` rolls back only the SQL side via `ROLLBACK TO SAVEPOINT initial_balances`; it does **not** undo the direct, synchronous mutations already made to shared unit-props objects in memory. This mirrors the CVE's pattern: one internal structure is torn down/reset (SQL rolled back) while a related, previously-populated structure (in-memory cache) is never reconciled and is later trusted as-is.

### Finding Description
`aa_composer.js`'s `revert()` is invoked whenever any secondary AA in a trigger chain fails after earlier secondary/primary AA response units were already saved: [1](#0-0) 

`revert()` calls `revertResponsesInCaches()`, which only forgets the AA **response units themselves** (and fixes `is_free` on their direct parents): [2](#0-1) 

It then issues `conn.query("ROLLBACK TO SAVEPOINT initial_balances", ...)` — a purely SQL-level undo: [3](#0-2) 

However, each AA response unit written earlier in the same chain went through `writer.saveJoint()`, which **immediately** (before any COMMIT/ROLLBACK decision) mutates the live cache objects and, as part of `arrOps`, invokes `main_chain.updateMainChain()`: [4](#0-3) 

`updateMainChain()`'s `calcLIMCIs()` recalculates `latest_included_mc_index` for affected units and writes it **directly onto the shared props object** retrieved from `storage.assocUnstableUnits` (not a copy): [5](#0-4) 

The corresponding SQL update (`UPDATE units SET latest_included_mc_index=?`) is undone by the later `ROLLBACK TO SAVEPOINT`, but the in-memory field mutation on the shared props object in `assocUnstableUnits` is **not** reverted — there is no code path that restores it. `markMcIndexStable()` similarly moves objects between `assocUnstableUnits`/`assocStableUnits` and mutates `is_stable` in place: [6](#0-5) 

Downstream, other core paths trust these cached objects directly without re-verifying against the database, e.g. the `conf.bFaster` fast path in `readPropsOfUnits`: [7](#0-6) 

Once the AA response chain reverts, the node is left holding unit-props objects whose `latest_included_mc_index`/`is_stable` reflect a state that was never actually committed to the database — the classic pattern of "reset one structure, but a related structure retains the stale, already-freed/invalidated state," directly analogous to the curl UAF (reset invalidates internal pointer state, cleanup still dereferences it).

### Impact Explanation
`latest_included_mc_index` and unit stability are core consensus inputs used throughout `graph.js`/`main_chain.js` (e.g., `determineIfIncluded`, stability/witness-level determination). A permanently desynced cache (in-memory value diverging from the authoritative DB state after rollback) can cause the affected node to compute different inclusion/stability/validity results than peers using fresh DB state — i.e., node disagreement on validity or stability, and potentially incorrect acceptance/rejection of units depending on the corrupted cached field, persisting until the node restarts or the unit is purged from cache.

### Likelihood Explanation
Reachable by any unprivileged user who can post a payment/trigger to an AA that calls one or more secondary AAs, provided one of the later secondary AAs in the chain can be made to bounce (e.g., insufficient balance, formula error) after at least one earlier response unit in the same chain caused `updateMainChain()` to touch `latest_included_mc_index` of sibling/parent units. This does not require any special privileges — only ordinary AA trigger composition — making the trigger conditions realistic, though the precise timing (an earlier unit in the chain causing LIMCI recalculation on units unrelated to itself, followed by a later bounce) requires a somewhat specific AA chain topology.

### Recommendation
In `aa_composer.js`'s `revert()`, when rolling back to the savepoint, also revert any in-memory unit-props mutations performed by `main_chain.updateMainChain()`/`calcLIMCIs()`/`markMcIndexStable()` for units touched during the AA chain — e.g., by snapshotting affected unit-props (`latest_included_mc_index`, `is_stable`, membership in `assocStableUnits`/`assocUnstableUnits`) before dispatching secondary triggers and restoring them on `revert()`, or by calling `storage.resetMemory()` (as `writer.js`'s own error path already does at [8](#0-7) ) instead of a bare SQL `ROLLBACK TO SAVEPOINT` whenever any unit was written during the reverted chain.

### Proof of Concept
1. Deploy a primary AA `P` whose trigger message set, upon receiving a payment, sends outputs to a secondary AA `S1` (which will succeed and post a response unit) and then to a secondary AA `S2` (which is designed to bounce, e.g., by referencing an invalid state/asset condition).
2. Ensure `S1`'s response unit inclusion causes `writer.saveJoint()`'s `main_chain.updateMainChain()` to recompute `latest_included_mc_index` for at least one other still-unstable unit already present in `storage.assocUnstableUnits` (achievable by crafting DAG timing so `calcLIMCIs` updates a sibling unit's LIMCI as a side effect of adding `S1`'s unit).
3. Post the trigger to `P`. `S1`'s response gets written (mutating the sibling unit's cached `latest_included_mc_index` in place) and then `S2` bounces, causing `aa_composer.js`'s `revert()` to run `ROLLBACK TO SAVEPOINT initial_balances`.
4. Inspect `storage.assocUnstableUnits[<sibling_unit>].latest_included_mc_index` in the running node versus the value in the `units` table after rollback — they diverge, and the node continues to use the stale in-memory value for subsequent validation via the `conf.bFaster` cache-trusting path in `storage.readPropsOfUnits`.
