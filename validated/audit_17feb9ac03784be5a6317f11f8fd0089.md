### Title
Missing dust-output filter for non-base asset payments lets an attacker inflate AA response units, causing byte-fee loss and freezing of an AA's asset payouts - ([File: aa_composer.js])

### Summary
The `liquidity_lockbox` bug is a griefing pattern where an attacker opens many minimum-liquidity positions with no floor, forcing the victim to unwind them one by one at disproportionate cost. Obyte's `aa_composer.js` already recognizes and mitigates this exact class of attack for base-byte outputs sent to an AA, but the identical dust-filter is missing for custom-asset outputs, leaving AAs that hold/pay out assets exposed to the same griefing pattern.

### Finding Description
When an AA composes a payment in a given asset (in `completePaymentPayload`), it selects the AA's own unspent outputs of that asset via `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) 

The comment explicitly documents the threat model: "*byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond*" — but the actual `WHERE` clause only applies the `amount>=FULL_TRANSFER_INPUT_SIZE` filter **when `asset` is null** (i.e. for base bytes). For any custom asset, the query has no minimum-amount filter at all, and likewise has no `LIMIT` clause, so `iterateUnspentOutputs()` will happily walk through every dust output the attacker deposited: [2](#0-1) [3](#0-2) 

Normally, an oversized payment message would be caught by the "too many inputs" check in `validatePaymentInputsAndOutputs`, but that check is explicitly skipped for AA-generated units: [4](#0-3) 

Because the check is bypassed for AA responses (`objValidationState.bAA` is true), an AA can be forced to build a payment message with an unbounded number of asset inputs. The overall unit size (including this bloated asset-payment message) then feeds directly into the AA's oversize-fee computation whenever the AA also composes a base-byte payment message in the same response: [5](#0-4) 

Unlike a normal wallet's coin-selection (`inputs.js`), which sorts candidate outputs `ORDER BY amount DESC` and caps the count at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` to prefer large coins and stay under the size cap: [6](#0-5) 

the AA's own asset-output query is unbounded and ordered oldest-first (`ORDER BY main_chain_index, unit, output_index`), guaranteeing that any dust previously sent will always be consumed before larger, legitimate outputs.

### Impact Explanation
An attacker can send an AA a large number of minimal-value outputs of a non-base asset (each delivered via a separate trigger, since a single trigger may only contain one output per asset to a given AA address, per `validateAATrigger`): [7](#0-6) 

Once enough dust exists, any future legitimate attempt by the AA to pay out that asset (e.g., returning a user's balance) will pull in most/all of these dust inputs first. This:
1. Inflates the resulting unit's size, increasing the `oversize_fee` charged against the AA's own byte balance (an AA fund loss), because the AA is exempt from the input-count cap that would otherwise bound this cost.
2. Can grow the unit past the protocol's maximum size/messages limits, causing `validateAndSaveUnit` to fail and the trigger to bounce — meaning the AA becomes permanently unable to pay out that asset to anyone until the dust is somehow cleared (an AA fund-freezing condition), exactly mirroring the `liquidity_lockbox` griefing pattern where legitimate withdrawals must "close" attacker-created dust one output at a time.

This qualifies as concrete AA fund loss/freezing under the medium/high impact bar.

### Likelihood Explanation
The attack requires only the ability to trigger the target AA with a payment in the asset it holds/uses, which is available to any unprivileged unit poster/AA trigger sender — no special privilege, node, or peer position is needed. The per-trigger cost is bounded by the AA's declared `bounce_fees` in bytes (checked in `aa_addresses.js: checkAAOutputs`), independent of the asset amount sent, so an attacker can cheaply deposit arbitrarily many 1-unit asset outputs over time. The only defense that exists (`FULL_TRANSFER_INPUT_SIZE` dust filter) explicitly does not apply to this path, confirming the gap is a real oversight rather than a deliberately accepted risk.

### Recommendation
Apply the same dust-filtering principle already used for base-byte outputs to non-base asset outputs in `readStableOutputs()` / `readUnstableOutputsSentByAAs()` in `aa_composer.js` — e.g., ignore/skip asset outputs below a sensible per-asset minimum (or cap the number of inputs collected per payment message, mirroring `inputs.js`'s `MAX_INPUTS_PER_PAYMENT_MESSAGE-2` limit and `ORDER BY amount DESC` selection). Additionally, reconsider exempting AA-generated units from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check in `validatePaymentInputsAndOutputs` (`validation.js`), or bound the number of asset inputs an AA response can consume so a single payout cannot be forced to include an unbounded number of attacker-supplied dust outputs.

### Proof of Concept
1. Attacker repeatedly triggers target AA `X` with trigger units, each including a payment message of custom asset `A` sending the minimum allowed amount (e.g., 1) to `X`, paying only the required `bounce_fees.base` each time — see the bounce-fee check in `aa_addresses.js` (`checkAAOutputs`, lines 138–155) which only validates the byte amount, not per-output size of `A`.
2. Repeat until `X` holds thousands of 1-unit outputs of asset `A` (no filter exists in `aa_composer.js`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` for non-base assets, lines 1140–1173).
3. A legitimate user (or the AA's own logic) triggers `X` to pay out balance in asset `A`. `completePaymentPayload`'s `iterateUnspentOutputs` (lines 1102–1138) consumes the oldest (dust) outputs first, without any cap, since `validatePaymentInputsAndOutputs` skips the "too many inputs" check for AA units (`validation.js`, lines 2137–2138).
4. The resulting response unit becomes abnormally large; if the AA also emits a base-byte payment in the same response, `getOversizeFee()` (lines 1083–1100) charges the AA's own byte balance for the inflated size, or, if the unit exceeds protocol size limits, the response fails entirely, leaving the AA unable to complete payouts of asset `A`.
