### Title
Cross-stack status forgery via unscoped `sha` lookup in `StatusHandler#process` - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The claimed binding in the question ("context string == the CI system operating on S2's own repository") is already broken for a deeper reason than context guessability: `StatusHandler#process` resolves target commits by `sha` alone, with no check against the `repository` field in the payload. Because `sha` is only unique per `(sha, stack_id)` (not globally unique), a validly-signed webhook that genuinely originates from repository A can create a `Status` on every `Commit` row across every stack in the Shipit install that happens to share that sha — including a completely different victim repository S2 — as long as an attacker can get *a real commit with the same sha* recorded under both stacks.

### Finding Description
Binding claimed broken: `context ∈ deploy_spec.required_statuses/blocking_statuses` alone determines "which CI is authoritative for S2".
Actual binding that is broken: `Commit#stack_id (of the row being updated) == origin repository of the webhook`.

`WebhooksController#verify_signature` selects the GitHub App/secret using `repository_owner` from the payload [1](#0-0) , so an attacker without any org's `webhook_secret` cannot forge an arbitrary signature — this guard holds. However, `Status['status']` events are dispatched to `StatusHandler`, whose `process` method does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is scoped only by `sha`, never by the `repository` object present in the same webhook payload. The unique DB index backing `commits` is `(sha, stack_id)`, not `sha` alone [3](#0-2) , confirming that identical `sha` values are expected to coexist across different stacks (and thus potentially different repositories/orgs served by the same Shipit instance).

Exploit flow: an attacker who has ordinary push access to *any* repository A onboarded to the same Shipit instance (fully "unprivileged" per the rules — just a contributor, not an operator) can:
1. Fetch a specific commit object from victim stack S2's public repository (git commit hashes are content-derived, so re-pushing the identical raw commit into repository A reproduces the identical `sha`).
2. Trigger a real, GitHub-signed `status` webhook on that commit in repository A (e.g., via their own CI job, naming its check context identically to a string in S2's `deploy_spec.blocking_statuses`, such as `ci/circleci`).
3. GitHub signs and delivers this webhook using repository A's org-level secret, which `verify_signature` validates successfully because it is legitimately signed for org A.
4. `StatusHandler#process` then updates **every** `Commit` row with that `sha`, including the row belonging to S2's stack, regardless of the fact the payload's `repository` field names A, not S2's repo.
5. `Commit#blocked?` for S2 (via `Status::Group#blocking?` / `statuses.any?(&:blocking?)`) is cleared because the forged/foreign status now satisfies the required context [4](#0-3) .

Existing guards do not catch this: `verify_signature` only authenticates *an* organization, not that the payload's commits belong to that organization's repositories [5](#0-4) ; the `ExplicitParameters` schema for `StatusHandler` only validates field types/presence, not repository ownership [6](#0-5) ; and `Status.replicate_from_github!`/`create_status_from_github!` perform no cross-check against `commit.stack.repository` [7](#0-6) [8](#0-7) .

### Impact Explanation
A payload legitimately authenticated for repository A mutates commit/status state belonging to stack S2 (a different repository/tenant), clearing `blocked?` and unblocking merges/deploys that S2's own deploy spec intended to gate on real CI. This matches the Critical criterion "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." It is repeatable against any pair of stacks sharing a commit sha in the same Shipit install, and blast radius spans all tenants hosted by one Shipit instance/GitHub App installation.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment tracking more than one repository/stack under an org/App the attacker has ordinary push access to, and (b) the ability to get an identical commit sha recorded in both the attacker's repo and the victim stack (trivial for public commits, or achievable by crafting/duplicating commit content). No Shipit secrets, sessions, or API tokens are needed — only normal contributor-level GitHub push/CI access, so attacker cost is low and the technique is repeatable.

### Recommendation
In `StatusHandler#process` (and analogously `CheckSuiteHandler`), scope the `Commit` lookup by the stack(s) whose configured `github_repo_name`/organization matches `params.repository.full_name`, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: repository_from_payload.id })`, rather than a bare `sha` match across the entire commits table.

### Proof of Concept
```ruby
test "a status webhook for repository A must not clear blocked? on an unrelated stack B sharing the same sha" do
  repo_a_stack = shipit_stacks(:shipit)          # attacker-reachable repo
  repo_b_stack = shipit_stacks(:cyclimse)        # victim S2, different repository
  shared_sha = "a" * 40

  commit_a = repo_a_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "x")
  commit_b = repo_b_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "x")

  DeploySpec.any_instance.stubs(:blocking_statuses).returns(['ci/circleci'])

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # webhook validly signed for repo A's org only

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success', context: 'ci/circleci',
    repository: { full_name: repo_a_stack.github_repo_name, owner: { login: repo_a_stack.repository.owner } }
  }.to_json

  refute commit_b.reload.blocked? rescue nil # capture baseline (blocked before)
  post :create, body:, as: :json

  # Binding under test: commit_b.stack_id (S2) must equal the repository that authenticated the webhook (A) for the update to be legitimate.
  assert_not_equal repo_a_stack.id, repo_b_stack.id
  assert commit_b.reload.statuses.exists?(context: 'ci/circleci'), "status leaked into unrelated stack B"
  # This assertion demonstrates the bug: S2's blocked? flips to false due to a webhook authenticated only for repo A.
end
```
