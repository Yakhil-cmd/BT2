The CVE describes a path-traversal file-read via an untrusted `path` HTTP parameter reaching a filesystem `get_file` action with no sanitization. Looking for an analog requires an attacker-controlled, network-reachable path/identifier that a FRAME runtime, pallet, or XCM executor uses for privileged filesystem or storage access without validation, triggered by an ordinary signed extrinsic or accepted unsigned message.

All filesystem path handling found in this repo is confined to node-operator CLI/tooling code — never reachable from a signed extrinsic, XCM message, or any user-submitted runtime call:

- Chain-spec loading (`load_spec`) reads a local file path supplied as a CLI argument by the node operator at startup, e.g. [1](#0-0) , [2](#0-1) , and template nodes [3](#0-2) .
- Key/SURI file reads in `sc-cli` (`inspect-node-key`, signing params) read paths from local CLI flags, not network input [4](#0-3) , [5](#0-4) .
- Benchmarking/chain-spec-builder tools read WASM/runtime files from local paths given by the operator, e.g. `chain_spec_from_path`, `ChainSpecBuilder::run`, `PalletCmd::state_handler_from_cli` [6](#0-5) , [7](#0-6) .
- `ChainSpec::from_json_file` / `GenesisSource::File` mmaps a local file path supplied only via CLI configuration, never via an extrinsic [8](#0-7) .

None of these code paths are reachable by a submitted extrinsic, an XCM instruction, a contract call, or any other network/chain-level attacker input — they all execute as trusted local operator tooling before/outside runtime execution, with no fee-paying "remote attacker" origin at all. FRAME's runtime execution model (WASM-sandboxed dispatchables) has no filesystem access surface exposed to dispatch logic — pallets operate purely on the on-chain key-value storage trie (`sp_io::storage`), not on OS file paths, so there is no dispatchable analog to `ajax_calls.php`'s `get_file` action that accepts an attacker-supplied path and performs an unauthenticated file read. No credible analog exists in the scoped production code.

	/// Parse json file into a `ChainSpec`
	pub fn from_json_file(path: PathBuf) -> Result<Self, String> {
		// We mmap the file into memory first, as this is *a lot* faster than using
		// `serde_json::from_reader`. See https://github.com/serde-rs/json/issues/160
		let file = File::open(&path)
			.map_err(|e| format!("Error opening spec file `{}`: {}", path.display(), e))?;

		// SAFETY: `mmap` is fundamentally unsafe since technically the file can change
		//         underneath us while it is mapped; in practice it's unlikely to be a problem
		let bytes = unsafe {
			memmap2::Mmap::map(&file)
				.map_err(|e| format!("Error mmaping spec file `{}`: {}", path.display(), e))?
		};
		let client_spec =
			json::from_slice(&bytes).map_err(|e| format!("Error parsing spec file: {}", e))?;

		Ok(ChainSpec {
			client_spec,
			genesis: GenesisSource::File(path),
			_host_functions: Default::default(),
		})
	}
