### Title
Cross-organization commit status forgery via webhook signature scoped to organization but `StatusHandler` writes unscoped by repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against based on the *organization* derived from the payload (`repository.owner.login` or `organization.login`), authenticating that the request was signed with that one organization's `webhook_secret`. However, once verification passes, `Webhooks::Handlers::StatusHandler#process` writes commit statuses by querying `Commit.where(sha: params.sha)` **globally, with no repository or organization scoping at all**. The equality the engine is supposed to enforce — "the organization whose secret authenticated this payload" == "the repository/stack this payload is allowed to mutate" — is never checked for this handler.

### Finding Description
Signature verification is organization-scoped: [1](#0-0) 

`repository_owner` is read straight from attacker-controlled JSON fields of the same payload that is being signed: [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks a distinct `GitHubApp`/`webhook_secret` per organization, as shown by the fixture configuring two independent organizations, each with its own `webhook_secret` (one of which can even be `nil`, in which case `verify_webhook_signature` returns `true` unconditionally): [3](#0-2) [4](#0-3) 

Once the request passes verification for *whichever organization it claims to be*, the raw parsed JSON (`params`) is dispatched unchanged to every handler for the event: [5](#0-4) 

Most handlers correctly re-derive the target repository from `payload.dig('repository', 'full_name')` and scope their writes to `Repository.from_github_repo_name(...)`, e.g. `PushHandler`: [6](#0-5) [7](#0-6) 

But `StatusHandler` does not use this scoping mechanism at all — it looks up commits purely by SHA across the entire installation: [8](#0-7) 

Because `repository.owner.login` (used only for selecting the verification secret) and `sha` (used to select which `Commit` row gets mutated) are two independent, attacker-supplied fields in the same JSON body, nothing forces them to refer to the same repository. An attacker who is a legitimate GitHub App administrator/operator for **their own** onboarded organization (and therefore legitimately knows/controls that organization's own `webhook_secret`, or targets an organization configured with no `webhook_secret` at all) can:
1. Craft an arbitrary JSON body with `repository.owner.login` (or `organization.login`) set to their own organization (so `Shipit.github(organization: ...)` resolves to a secret they know, or to an org with no secret configured, which always verifies as `true`).
2. Set `X-Github-Event: status`.
3. Set `sha` to the SHA of any commit belonging to a **different tenant/organization's** stack tracked by this Shipit instance (SHAs are not secrets — they are visible in the Shipit UI, GitHub, git history, etc.).
4. Set `state: success` (or `failure`), `context`, `target_url`, `description` freely.

`verify_signature` passes (their own org's secret, or no secret at all), and `StatusHandler#process` mutates the victim organization's `Commit` row via `commit.create_status_from_github!(params)`, with no check that the commit belongs to a stack under the organization whose secret was actually verified.

### Impact Explanation
Commit statuses are used by Shipit's `ci.require` deployability checks to gate deploys (`commit.deployable?`/CI-required-context logic referenced from `shipit.yml`'s `ci.require`). By forging a `success` status on a victim organization's commit that is missing required CI contexts, an attacker in a separate, unprivileged organization can flip a victim commit into a deployable state and enable/trigger an unauthorized deploy on a stack they have no legitimate relationship to — a cross-repository, cross-organization write and unauthorized-deploy-enabling primitive, matching the Critical impact bar ("cross-repository writes" / "an unauthorized deploy"). At minimum this is a full cross-tenant integrity break of CI/build status data with no authorization boundary respected between organizations sharing one Shipit deployment.

### Likelihood Explanation
The webhook endpoint (`/webhooks`) is a public, unauthenticated HTTP endpoint by design (this is how GitHub itself talks to it) — no session, `ApiClient` token, or privileged Shipit account is required, only knowledge of *some* organization's webhook secret (which the attacker legitimately possesses for their own onboarded org) or targeting an org configured without one. Multi-organization/multi-secret configuration is an explicitly supported, documented deployment shape (evidenced by the dual-org fixture). SHAs are not secret. The only extra requirement is guessing/knowing a target SHA in another tenant's stack, which is realistic in shared or semi-public Shipit instances where commit SHAs and stack pages are visible.

### Recommendation
`StatusHandler` (and any other handler that does not go through `Handler#stacks`/`Repository.from_github_repo_name`) must scope its `Commit` lookup to commits belonging to the repository resolved from the same payload's `repository.full_name`, and that repository's owner must be checked for equality against `repository_owner` (the organization whose secret verified the request) before any mutation occurs. More generally, `WebhooksController#verify_signature` should bind the verified organization to the exact repository being written in every handler, not just implicitly through convention.

### Proof of Concept
Conceptual PoC (Ruby, `ActionController::TestCase` style, analogous to `test/controllers/webhooks_controller_test.rb`):
```ruby
# Attacker only controls "attacker-org" (with its own known webhook_secret,
# or targets an org configured with webhook_secret: nil).
victim_commit = shipit_commits(:some_commit_in_other_org_stack) # sha known publicly

payload = {
  "sha" => victim_commit.sha,
  "state" => "success",
  "context" => "required-ci-context",
  "repository" => { "owner" => { "login" => "attacker-org" }, "full_name" => "attacker-org/whatever" }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, payload)

@request.headers['X-Github-Event'] = 'status'
@request.headers['X-Hub-Signature'] = signature
post :create, body: payload, as: :json

# verify_signature passes because it only checks the "attacker-org" secret.
# StatusHandler#process runs Commit.where(sha: victim_commit.sha) with no
# repository/org check, forging a "success" status on a commit that
# belongs to a completely different organization's stack.
assert_equal "success", victim_commit.reload.statuses.last.state
```
This confirms the org used to select/verify the HMAC secret is never checked against the org that actually owns the mutated `Commit` record.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
