### Title
Webhook signature verification uses a different organization field than the one written by event handlers, allowing team-membership forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the HMAC signature against by reading `repository.owner.login` from the *unauthenticated* JSON body (falling back to `organization.login` only when `repository` is absent). The event handlers that actually mutate application state — e.g. `MembershipHandler` — read `organization.login`, `team.id` and `member.login` directly from the same unauthenticated body, independent of whatever field was used to pick the verification secret. In a multi-organization Shipit deployment this breaks the equality "organization whose secret authenticated the request == organization whose data is written," letting an attacker who can produce *any* validly-signed webhook (e.g. for an org with no `webhook_secret` configured, which the docs describe as optional) forge a `membership` event that grants themselves membership in a `Team` tied to a different, privileged organization.

### Finding Description
`verify_signature` picks the signing secret from attacker-controlled JSON, not from any authenticated channel: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` only special-cases the passed `organization` when the installation is configured with the multi-app schema (top-level keys = org names); otherwise (single-app schema) the parameter is ignored: [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified: [4](#0-3) 

and the setup docs explicitly present `webhook_secret` as optional per-organization, and describe the multi-org config schema keyed by organization name: [5](#0-4) [6](#0-5) 

Meanwhile, the `membership` event handler writes state using `organization.login`, `team.id`, and `member.login`, none of which is the field `verify_signature` inspected to choose the secret (unless `repository` is absent from the payload, in which case they coincide — but nothing prevents an attacker from *adding* a `repository.owner.login` field to steer signature selection): [7](#0-6) 

`Team#add_member` runs unconditionally on both "added" membership actions, whether the `Team` row was newly created or already existed (e.g. a legitimately GitHub-synced required team): [8](#0-7) 

Finally, authorization to use Shipit at all is gated purely on DB-level `Team` membership derived from these webhook-driven records: [9](#0-8) [10](#0-9) 

**Binding broken:** `organization authenticated by verify_signature (repository.owner.login / organization.login, attacker-supplied)` ≠ `organization/team actually written by MembershipHandler (organization.login, team.id, member.login, also attacker-supplied but never covered by the signature check)`. Before the attacker's request, `Team`/`Membership` rows only reflect genuine GitHub organization membership synced via authenticated GitHub API calls or correctly-signed webhooks. After the attacker's forged request, a `Membership` row links the attacker's `User` to a `Team` whose `github_id` matches a real, privileged team, even though the signature that "authenticated" the request was computed with a secret belonging to an unrelated (or secret-less) organization.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization, one of the explicitly listed High-impact outcomes: an attacker with no Shipit session, no API token, and no legitimate GitHub organization membership can add themselves to a `Team` record whose id matches `Shipit.github_teams`, which is the sole check `User#authorized?` performs to grant access to the entire Shipit UI/API (stacks, deploys, rollbacks, task triggering).

### Likelihood Explanation
Exploitability depends on the attacker being able to produce one validly-signed webhook request at all. This is realistic in the documented multi-organization deployment mode (`docs/setup.md`, "Using Multiple Github Applications") where `webhook_secret` is explicitly optional per organization — any organization in the config without a secret set makes `verify_webhook_signature` return `true` unconditionally, letting the attacker pick that organization's name for `repository.owner.login` while placing the real target organization/team/member data in the fields the handler actually reads. I was not able to fully confirm from the available index whether the base `Shipit::Webhooks::Handlers::Handler` params DSL rejects unexpected top-level keys (the file defining it could not be located in this pass); if it strictly rejects unknown keys, the attacker would need the `repository` key to not be flagged as extraneous, which affects likelihood but not the root-cause design flaw itself.

### Recommendation
Use exactly one authoritative field, consistently, for both signature-secret selection and data writing (prefer `organization.login` for org-scoped events, and never let `repository.owner.login` override it when `organization` is present). Additionally, after selecting the app/secret for verification, re-derive and cross-check that the organization actually written by each handler matches the organization that was cryptographically verified, rejecting the webhook if they diverge. Consider making `webhook_secret` mandatory for every configured organization in the multi-app schema.

### Proof of Concept
Conceptual request (assuming a multi-org deployment where org `attacker-org` has no `webhook_secret` configured, and `Victim-Org` is a Shipit-recognized org with `Shipit.github_teams` containing a team of numeric GitHub `github_id` `TEAM_ID`):

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<any value>   (or a valid HMAC computed with attacker-org's known/absent secret)

{
  "action": "added",
  "team": { "id": TEAM_ID, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "Victim-Org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```

`verify_signature` resolves `repository_owner` to `attacker-org` (because `repository.owner.login` is present) and verifies against `attacker-org`'s (missing/known) secret, passing. `MembershipHandler#process` then finds the existing `Team` with `github_id == TEAM_ID` (a real, privileged team belonging to `Victim-Org`) and calls `team.add_member(User.find_or_create_by_login!('attacker-github-login'))`, granting the attacker membership and, transitively, `Shipit.github_teams` authorization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
