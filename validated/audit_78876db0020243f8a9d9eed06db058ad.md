### Title
AA fund payouts can be permanently DOSed/frozen by flooding the AA address with many just-above-dust outputs - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` function, used whenever an AA needs to compose a payment message in its response, selects unspent outputs belonging to the AA in strict FIFO order (`ORDER BY main_chain_index, unit, output_index`) and keeps consuming them one by one via `iterateUnspentOutputs()` with **no cap on the number of inputs it will add**, unlike the equivalent wallet-side function `pickDivisibleCoinsForAmount()` in `inputs.js`, which explicitly limits the selection to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` and orders by `amount DESC` (largest first). [1](#0-0) [2](#0-1) 

### Finding Description
Any unprivileged user (or another AA) can send many small payment outputs to a target AA's address. The only defense against dust is the exclusion of outputs smaller than `FULL_TRANSFER_INPUT_SIZE` (60 bytes), explicitly documented as an anti-dust-attack measure: [3](#0-2) 

This filters out *net-negative* dust, but does nothing to bound the *count* of just-above-threshold outputs an attacker can create at the AA's address (e.g. thousands of 61-byte outputs). When the AA later needs to compose an outgoing payment (triggered legitimately by another user), `iterateUnspentOutputs()` walks the FIFO-ordered output list and keeps adding inputs, one per output, until `total_amount` reaches `target_amount`: [4](#0-3) 

Each input added increases `size` by `FULL_TRANSFER_INPUT_SIZE` and recomputes `target_amount` including the oversize fee, so with enough dust outputs queued ahead of the AA's real (larger) outputs, the payment message can be forced to include far more than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs, which is enforced elsewhere by `validation.js`. There is no fallback to split the payment into multiple units or to select larger outputs first, so the composed unit fails final unit validation, and `sendUnit()`/the AA's payment leg has no way to succeed until the attacker's dust queue is exhausted — exactly analogous to the reported VUSD queue-clogging pattern, where a low minimum amount lets an attacker flood a FIFO-processed structure and starve legitimate users.

### Impact Explanation
An AA that holds or receives funds and whose bytecode relies on paying out balances (a very common pattern - bank/exchange/vault-style AAs) can have its outgoing payments permanently or repeatedly bounced by an attacker who cheaply floods its address with many small (>=60-byte) outputs. Because the AA response engine consumes outputs FIFO and has no per-message input cap analogous to the wallet composer's cap, legitimate users' withdrawal/payout triggers will bounce (their bytes/asset get returned but the requested transfer never executes, or the AA's real balance becomes effectively unspendable/"frozen" until the attacker's outputs are gradually consumed over many bounced attempts). This constitutes AA fund freezing/loss of usability, satisfying the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
The cost to the attacker is low - sending outputs at slightly above 60 bytes each is cheap, and there is no restriction on how many can be sent to the same AA address, similar to the referenced VUSD bug where a low minimum (5 VUSD) let an attacker flood a fixed-size FIFO queue. Any AA that pays out funds accumulated at its own address (a widespread pattern, e.g. banking/vault AAs like the analyzed sample scripts) is exposed. The likelihood is Medium: exploitation requires the attacker to spend real bytes to create the flood and requires the target AA logic to actually try to spend accumulated balance in FIFO order, but no special privilege is needed.

### Recommendation
- In `aa_composer.js`'s output-selection queries (`readStableOutputs`, `readUnstableOutputsSentByAAs`), order by `amount DESC` (or otherwise prioritize larger outputs) instead of FIFO by `main_chain_index`, mirroring the wallet's `pickMultipleCoinsAndContinue` behavior in `inputs.js`.
- Cap the number of inputs consumed per payment message to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE - 2` as is already done in `inputs.js`, and handle the "not enough usable funds within input limit" case gracefully (e.g., bounce with an informative message rather than composing an invalid, oversized unit).
- Consider raising the dust-exclusion threshold or making it configurable so that flooding with many just-above-threshold outputs is economically unattractive.

### Proof of Concept
1. Attacker repeatedly sends payment triggers to AA `X`, each carrying a single 61-byte output (just above the `FULL_TRANSFER_INPUT_SIZE` dust filter) — cheap to do many times, e.g. 500+ times.
2. A legitimate user sends a trigger to AA `X` requesting a payout larger than any single dust output (e.g., withdraw balance of 10,000 bytes).
3. AA `X`'s oscript composes a payment message; `sendUnit()` → `completePaymentPayload()` → `readStableOutputs()` returns outputs ordered oldest-first, so `iterateUnspentOutputs()` consumes the attacker's ~500 dust outputs (each adding to `size`/fee) before or instead of reaching the target amount efficiently.
4. Because the number of required inputs exceeds `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128), the resulting payload/unit fails validation checks in `validation.js`, and the AA's real payout can never be completed in a single unit — the legitimate user's request bounces, and the AA's balance becomes effectively frozen behind the dust queue.
