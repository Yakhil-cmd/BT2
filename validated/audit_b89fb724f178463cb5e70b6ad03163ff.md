### Title
Readiness/liveness endpoint latches "ready" permanently after first sync and never expires, masking indefinite subsequent sync failures - (File: `main.go`)

### Summary
The Olympus finding is a "no-expiration" bug class: once a stateful condition becomes active, nothing ever re-evaluates or expires it, so a state that was only valid at creation time can be relied upon indefinitely, even after conditions that would make it unsafe have changed. The closest reachable analog in `git-sync` is the HTTP readiness/liveness endpoint's "ready" flag, which is set once after the first successful sync and is never revoked, even if the sync loop subsequently fails forever.

### Finding Description
`git-sync`'s HTTP endpoint is documented to return a 5xx error until the first sync completes, "and a 200 status thereafter" [1](#0-0)  . In the main sync loop, `setRepoReady()` is invoked once inside the success branch, with the comment noting "this might have been called before, but also might not have" [2](#0-1)  — i.e., it is a one-way latch, not something that is reverted when a later sync attempt fails.

Meanwhile, `git-sync` explicitly supports unbounded failure tolerance after the initial sync: `--max-failures` can be set to a negative value to "retry forever" [3](#0-2) , and the loop only aborts the process when `maxFails >= 0 && failCount >= maxFails` [4](#0-3) . When `--max-failures=-1` is configured (a supported, documented mode), the process never exits on failure and simply logs "error syncing repo, will retry" indefinitely [5](#0-4) .

Because the readiness state was only ever set to "ready" once, based on conditions that existed at the time of the first successful sync, and is never re-checked or expired as time passes and failures accumulate, the published "ready" signal becomes stale in exactly the same way the Olympus "active" proposal state becomes stale: a one-time condition is treated as perpetually valid with no re-validation or expiration window.

### Impact Explanation
Kubernetes readiness/liveness probes rely on this `/` endpoint to decide whether to route traffic to the pod or restart it [1](#0-0) . If an attacker can cause the remote repo fetch to fail persistently after a legitimate first sync (e.g., by disrupting the upstream ref, poisoning DNS/network path to the remote, or otherwise causing sustained `git fetch`/`git worktree` failures) while `--max-failures` is configured to tolerate/ignore failures, the pod is never marked unready and is never restarted, even though the underlying synced content in `--link` is now indefinitely stale relative to the actual upstream state. This is a persistent sync denial that is invisible to orchestration tooling, because the "ready" signal, once true, has no expiration or re-validation logic tied to the freshness or success of ongoing sync attempts.

### Likelihood Explanation
This requires the operator to have configured `--max-failures` to a permissive (e.g., negative/forever) value and requires an attacker to be able to sustain fetch failures against the configured `--repo` target for an extended period — both are plausible operational configurations that are explicitly supported and documented, but the attack surface for triggering "failure forever" depends on external network/repo conditions that are outside `git-sync`'s own trust boundary control.

### Recommendation
Make the readiness state expire/re-evaluate based on recent successful sync activity rather than being a permanent one-way latch: track the timestamp of the last successful sync and flip the endpoint back to "not ready" once the number of consecutive failures or elapsed time since last success exceeds a bound (analogous to adding an expiration window, as recommended in the original Olympus finding for active proposals).

### Proof of Concept
1. Start `git-sync` with `--max-failures=-1` and a reachable repo; it completes an initial sync and `setRepoReady()` latches the HTTP endpoint to return 200 [6](#0-5) .
2. Disrupt reachability to the configured `--repo` (e.g., block the remote) so subsequent `git.SyncRepo` calls fail.
3. Observe that the loop logs "error syncing repo, will retry" indefinitely without exiting, because `maxFails < 0` bypasses the abort check [4](#0-3) .
4. Query the `/` HTTP endpoint repeatedly during the outage; per the documented contract it continues to return 200 ("ready") [1](#0-0) , even though the synced data under `--link` has not been updated and may be arbitrarily stale.
