### Title
Symlink-following arbitrary file write during `gh skill install` via pre-planted symlink in a cloned attacker repo - ([File: internal/skills/installer/installer.go])

### Summary
`installSkill` (and `installLocalSkill`) resolve the destination path with `safepaths.Absolute.Join`, which only performs lexical path-traversal checks and explicitly does not resolve symlinks, then write file contents with `os.WriteFile`/plain `os.WriteFile`, neither of which reject writes through an existing symlink at the destination. An attacker-controlled repository containing a symlink checked into git at the exact relative path a skill file will be installed to can cause `gh skill install` to write attacker-fetched blob content through that symlink to an arbitrary filesystem location.

### Finding Description
`safepaths.Absolute.Join` documents its own limitation: "Note that this does not handle symlinks." [1](#0-0) 

In `installSkill` (the remote/API install path used by `gh skill install`), the destination is computed purely lexically via `safeSkillDir.Join(relPath)` and then written with `os.WriteFile`, with no `Lstat`/symlink check and no `O_EXCL`: [2](#0-1) 

Contrast this with `internal/zip/zip.go`, where the same class of write is protected by opening the destination with `O_WRONLY|O_CREATE|O_EXCL`, which fails (rather than following) if a file/symlink already exists at that path: [3](#0-2) 

`installLocalSkill` only guards against symlinks encountered while walking the *source* tree (`d.Type()&os.ModeSymlink != 0` → skip), it does not check whether the *destination* path is itself a symlink before calling `os.WriteFile`: [4](#0-3) [5](#0-4) 

Exploit flow: an attacker publishes a repository that (a) is a valid skill repo per `discovery` conventions and (b) has a symlink checked into git at the path that will later become `<installDir>/<skill.Name>/<relPath>` (e.g. `.agents/skills/my-skill/config`), pointing to a file outside the project (e.g. `~/.bashrc`, a CI config, or another sensitive file reachable by the victim's user). The victim clones this repository with an ordinary `git clone`, which materializes the symlink on disk. When the victim later runs `gh skill install <owner>/<repo> <skill>` with project scope while `AgentHost.InstallDir`/`resolveInstallDir` resolves to a directory that already contains this checked-out symlink (e.g. because `GitRoot` is the same checkout, or `--dir` points at it), `installSkill` fetches the (attacker-controlled) blob content over the API and calls `os.WriteFile(destPath, ...)`. Since `destPath` is a pre-existing symlink and `os.WriteFile` does not use `O_EXCL` or check `Lstat`, the write follows the symlink and lands at the attacker-chosen target, outside the confined skill directory that `safepaths` was meant to enforce.

### Impact Explanation
This is an arbitrary file write/overwrite outside the intended installation directory, achievable purely through attacker-published repository content plus a victim performing two ordinary `gh`/`git` operations (clone + skill install) against the same repository/directory. This matches the bounty impact class "file write or overwrite outside the intended path."

### Likelihood Explanation
Requires the victim to have previously checked out the attacker's repository at the exact location that later becomes (or is inside) the resolved skill install directory, and to run `gh skill install` against that same repo/path afterward. This is a realistic but non-default workflow (e.g., testing/installing skills from a repo the user has already cloned, or explicitly pointing `--dir`/project scope at that checkout). It does not require any privilege beyond publishing a public repository.

### Recommendation
Harden the destination write path in `installSkill` (and `installLocalSkill`) the same way `internal/zip/zip.go` does: open the destination with `os.O_WRONLY|os.O_CREATE|os.O_EXCL` (or `Lstat` the destination first and refuse/skip if it is a symlink) before writing fetched skill content, so a pre-existing symlink at the destination causes an error instead of being followed.

### Proof of Concept
```go
func TestInstallSkillRefusesToFollowPreexistingSymlinkAtDestination(t *testing.T) {
    destDir := t.TempDir()
    skillDir := filepath.Join(destDir, "my-skill")
    require.NoError(t, os.MkdirAll(skillDir, 0o755))

    outsideTarget := filepath.Join(t.TempDir(), "victim-file")
    require.NoError(t, os.WriteFile(outsideTarget, []byte("original"), 0o644))

    // Simulate a symlink checked into git and materialized by a prior `git clone`
    // at the exact path installSkill will write to.
    require.NoError(t, os.Symlink(outsideTarget, filepath.Join(skillDir, "config")))

    reg := &httpmock.Registry{}
    defer reg.Verify(t)
    stubTreeAndBlobWithFile(reg, "treeSHA", "config", "PWNED")
    client := api.NewClientFromHTTP(&http.Client{Transport: reg})

    opts := &Options{
        Host: "github.com", Owner: "attacker", Repo: "evil-skills",
        Ref: "main", SHA: "commitsha", Client: client,
    }
    skill := discovery.Skill{Name: "my-skill", Path: "skills/my-skill", TreeSHA: "treeSHA"}

    err := installSkill(opts, skill, destDir)
    require.NoError(t, err) // currently succeeds

    content, _ := os.ReadFile(outsideTarget)
    // Expected (fixed) behavior: write should be rejected, outsideTarget untouched.
    // Actual (vulnerable) behavior: content becomes "PWNED".
    assert.NotEqual(t, "PWNED", string(content), "write followed symlink outside skill dir")
}
```
Expected assertion after fix: `installSkill` returns an error (or skips the entry) instead of writing through the symlink, and `outsideTarget`'s content remains unchanged.
