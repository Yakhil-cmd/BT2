### Title
`min-ustx-for-sats-amount` double-truncating integer division lets a staker register for an sBTC bond and receive full sats-weighted reward shares while posting zero (or near-zero) STX collateral - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `register-for-bond` enforces the STX-collateral floor for an sBTC bond by checking `amount-ustx >= (min-ustx-for-sats-amount sats-total stx-value-ratio min-ustx-ratio)`. `min-ustx-for-sats-amount` performs two sequential floor-divisions, which truncate to `0` for small `sats-amount`/`stx-value-ratio` combinations, letting a staker satisfy the "sufficient STX" check while locking `0` (or far less than proportional) STX, yet still be credited the full `sats-total` weight for reward-share accounting. This mirrors the Aloe-II "strain" bug: a value that should scale with an economic input rounds to zero, breaking the equality between collateral actually locked and rewards/weight credited.

### Finding Description
`min-ustx-for-sats-amount` is defined as: [1](#0-0) 

```
(/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
```

This computes `floor(floor(stx-value-ratio * sats-amount / 100) * min-ustx-ratio / 10000)`. Because Clarity's `/` is integer (floor) division, the *inner* division `(/ (* stx-value-ratio sats-amount) u100)` already truncates to `0` whenever `stx-value-ratio * sats-amount < 100`. Once that intermediate result is `0`, the outer multiplication/division by `min-ustx-ratio`/`u10000` stays `0` regardless of `min-ustx-ratio`. The result is then used directly as the enforced STX floor in `register-for-bond`: [2](#0-1) 

```
;; Verify that they're sending enough STX
(asserts!
    (>= amount-ustx
        (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
            (get min-ustx-ratio bond)
        ))
    ERR_INSUFFICIENT_STX
)
```

`sats-total` itself is taken directly from the caller-supplied `btc-lockup`/`sbtc-amount` argument (via `verify-l1-lockups` or the raw sBTC transfer amount), and is the quantity credited toward the staker's bond membership and used later for reward-weighting (`sats-total` flows into `new-sbtc`, staker membership `amount-sats`, and ultimately into the bond's per-cycle share/reward accounting used by `pox_5_make_signer_set`/`pox_5_stake_entries` in `signer_set.rs`, where entries are aggregated by `stacked_amt` derived from staker records): [3](#0-2) 

Because the STX floor collapses to zero for any `sats-total` small enough (or for a `stx-value-ratio`/`sats-amount` product under 100, which is easily reachable given `stx-value-ratio` is expressed as "uSTX per 100 sats" and bonds can be set up with small ratios), a staker can call `register-for-bond` with `amount-ustx = 0` (or any trivially small amount) while still being credited `sats-total` sats worth of bond membership and reward shares. This breaks the intended equality: *STX locked as collateral for the bond should scale with the BTC value being backed (via `stx-value-ratio`/`min-ustx-ratio`)*. Instead, the sats-weighted reward/signing entitlement is decoupled from the locked STX, i.e., "signing weight or reward slots exceeding locked value" — one of the explicitly in-scope High-impact equalities.

This is structurally identical to the reported Aloe-II bug class: a ratio-based amount (`strain` there, `min-ustx-for-sats-amount` here) is computed via integer division that truncates to zero for small inputs, and the code proceeds to grant/skip an obligation as if the non-zero case held, without a `> 0` sanity check on the computed floor before it's used as a binding constraint.

### Impact Explanation
A staker who can supply (or claims to have locked, in the L1-lockup path) a small enough `sats-total` relative to the bond's `stx-value-ratio` can register for a bond while locking negligible/zero STX, yet receive full sats-weighted reward shares and count toward the bond's total sBTC custody / reward distribution. This is a "signing weight or reward slots exceeding locked value" condition (High severity per the in-scope impact list), since the protocol's economic assumption — that reward/weight entitlement is backed by proportionally locked STX collateral — is violated. Repeated across many small registrations (or split into many small `sats-amount` calls, since `sats-amount` is caller-controlled per registration), this can materially decouple the sBTC-bond reward pool distribution from actual locked STX, diluting honest stakers' rewards and undermining the bond's collateralization guarantee.

### Likelihood Explanation
Likelihood is moderate-to-high: `stx-value-ratio` and `min-ustx-ratio` are bond parameters set by the bond admin at `setup-bond` time (not attacker-controlled), but `sats-amount`/`sats-total` (the BTC-side value) is directly supplied by the registering staker in `register-for-bond`. Any staker on the allowlist can choose to register with a small `sats-amount`, and the double-truncation triggers whenever `stx-value-ratio * sats-amount < 100` (unprivileged, no special role needed) — this is a purely arithmetic edge condition reachable by any allowlisted staker without requiring admin/miner/signer privileges.

### Recommendation
- Round the STX floor up (ceiling) rather than down when converting sats to a minimum uSTX requirement, e.g. compute `ceil(stx-value-ratio * sats-amount / 100)` before applying `min-ustx-ratio`, or perform the multiplication before any intermediate division to avoid compounding truncation.
- Add an explicit check that rejects registrations where `sats-total > 0` but the computed `min-ustx-for-sats-amount` is `0`, forcing a minimum non-zero STX lock proportional to any non-zero sats amount.
- Consider imposing a protocol-level minimum `sats-amount` per registration (or minimum `amount-ustx`) to prevent dust-sized registrations from being used to accumulate reward-share weight with negligible locked collateral.

### Proof of Concept
1. Bond admin calls `setup-bond` with `stx-value-ratio = 10` (10 uSTX per 100 sats) and `min-ustx-ratio = 1000` (10%), as used in the existing `waterfall distributions` test fixture [4](#0-3) .
2. An allowlisted staker calls `register-for-bond` with `sats-total = 9` (or any value where `stx-value-ratio * sats-amount < 100`, e.g. `10 * 9 = 90 < 100`).
3. `min-ustx-for-sats-amount(9, 10, 1000)` evaluates: inner `(/ (* 10 9) 100)` = `(/ 90 100)` = `0`; outer `(/ (* 0 1000) 10000)` = `0`.
4. The `asserts! (>= amount-ustx 0) ...` check in `register-for-bond` [5](#0-4)  passes even with `amount-ustx = 0`.
5. The staker's bond membership is recorded with `amount-sats = 9` (full credit) while `amount-ustx` locked is `0`, and this sats value subsequently participates in reward-share/weight computations, granting the staker sats-based reward entitlement backed by no locked STX.

Note: I could not fully trace the exact downstream code path that converts `amount-sats` into signer reward-weight in `signer_set.rs` (`pox_5_stake_entries`) within the tool budget available; the truncation-to-zero flaw in `min-ustx-for-sats-amount` and its direct use as the sole STX-sufficiency gate in `register-for-bond` is confirmed and cited directly from source.
