### Title
Prefix-matching without boundary check lets a fake "mutually signed" authentifier path bypass arbiter dispute validation - ([File: wallet.js])

### Summary
`wallet.js`'s `arbiter_dispute_request` handler validates that a shared-address unit used in an arbiter dispute was genuinely signed by both contracting parties before accepting the dispute for arbitration. This check uses raw `String.prototype.startsWith` on authentifier path strings without verifying a path-segment boundary (e.g. requiring the next character to be `.` or end-of-string). This is the same bug class as GHSA-84g5-x8j3-7235 (suffixtrie off-by-one letting `fxample.com` match a rule for `example.com`): a prefix/suffix match that should be anchored on a delimiter is instead a naive substring test, allowing an attacker-controlled string to "match" a rule it does not actually satisfy.

### Finding Description
In `wallet.js`, the `arbiter_dispute_request` handler: [1](#0-0) 

```
const author = objUnit.authors.find(author => author.address === body.shared_address);
...
const signing_paths = Object.keys(author.authentifiers);
const isMutuallySigned = signing_paths.find(p => p.startsWith('r.0.0')) && signing_paths.find(p => p.startsWith('r.0.1'));
if (!isMutuallySigned)
    return callbacks.ifError(`signing unit ${body.unit} is not mutually signed, authentifiers: ${JSON.stringify(author.authentifiers)}`);
```

`author.definition` (and hence the authentifier path tree) comes from `objUnit`, a unit fetched from storage/network by `body.unit` — a value fully controlled by whichever party constructs the dispute-triggering unit (an ordinary unit poster, one of the two contracting parties). The nested address paths in an oscript definition are built by string concatenation of numeric indices (`path + '.' + index`) in `definition.js`'s definition/authentifier evaluators: [2](#0-1) 

Because the intended mutual-signature branches live at exact paths `r.0.0` (offeror) and `r.0.1` (acceptor), but the check only verifies a *string prefix* rather than an exact path or a path followed by a `.` delimiter, any authentifier path that merely starts with the literal characters `"r.0.1"` — such as `r.0.10`, `r.0.11`, …, `r.0.19` — will satisfy the acceptor-side check even though it is a completely unrelated sibling branch (index 10, 11, …) inside the same `and`/`or` set, not a descendant of the acceptor's `address` sub-definition at index 1.

An attacker who controls the shared-address `definition` (constrained only by the fact that `definition[1][0][1][0][1]` must equal `offeror_address` and `definition[1][0][1][1][1]` must equal `acceptor_address`, per lines 821-830) can freely add extra sibling options to the `and`/`or` array at path `r.0` (the mutual-signing set). By adding 10 or more options, a sibling branch reaches path `r.0.10`, which the attacker alone can sign (e.g. with their own `sig` condition). `"r.0.10".startsWith('r.0.1')` is `true`, so `isMutuallySigned` becomes truthy even though the real acceptor (`acceptor_address`) never actually signed at `r.0.1`.

### Impact Explanation
`isMutuallySigned` is the gatekeeper for whether the arbiter's wallet accepts a dispute request at all: [3](#0-2) 

Bypassing it lets an attacker submit a forged/self-authored "signing unit" that appears to be jointly agreed by both contract parties when in fact only the attacker signed it. This can mislead the arbiter into treating a one-sided unit as the mutually-endorsed contract execution during dispute arbitration, i.e., influencing the arbiter's decision about fund release/refund for the escrowed payment based on a fabricated agreement — a fund-loss/misdirection risk for the counterparty in the arbitrated escrow contract. Severity is Medium: it requires the attacker to be one of two contracting parties in an arbiter-mediated deal and to control the arbstore-forwarding path, and it does not directly break base-layer DAG consensus, double-spend protection, or AA state — it undermines an application-layer trust check (wallet/contract message handling), consistent with the "Medium" analog category.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a party (offeror or acceptor) in an arbiter contract, to craft a custom shared-address definition with an oversized mutual-signing option set (which the wallet UI likely wouldn't build, but the protocol/message format doesn't forbid it), and to get that definition accepted as the shared address for the contract. No cryptographic break is needed — only building a slightly larger `and`/`or` array and signing the resulting extra branch with the attacker's own key.

### Recommendation
Replace the naive `startsWith` prefix checks with boundary-aware path matching, e.g.:
```js
const isPathOrDescendant = (p, base) => p === base || p.startsWith(base + '.');
const isMutuallySigned = signing_paths.some(p => isPathOrDescendant(p, 'r.0.0')) && signing_paths.some(p => isPathOrDescendant(p, 'r.0.1'));
```
Additionally, consider validating that the mutual-signing set at `r.0` has exactly the two expected options (offeror/acceptor) with no extra attacker-added branches, rather than only checking `mutualPart[0]`/`mutualPart[1]`, to remove the underlying structural ambiguity entirely.

### Proof of Concept
1. Attacker (party A) proposes an arbiter contract where the shared-address `definition` at path `r.0` is an `or`/`and` set containing not just 2 options (offeror/acceptor addresses at indices 0 and 1) but 11+ options, with index 0 = `['address', offeror_address]`, index 1 = `['address', acceptor_address]`, and indices 2–10 = simple `['sig', {pubkey: attacker_pubkey}]` conditions fully controlled by the attacker.
2. `definition[1][0][1][0][1]` and `[1][1]` still equal `offeror_address`/`acceptor_address`, so the `bCorrectParties` check in `wallet.js` passes.
3. Attacker authors a "signing unit" for the shared address where they sign only their own real path (`r.0.0.…`, since they are the offeror) and additionally provide a signature for the extra branch at path `r.0.10` (their own `sig` condition), without any real cooperation from `acceptor_address`.
4. Attacker submits this unit as `body.unit` in an `arbiter_dispute_request` message to the arbiter.
5. `signing_paths` contains `r.0.0…` and `r.0.10`; both `startsWith('r.0.0')` and `startsWith('r.0.1')` return true, so `isMutuallySigned` is `true` despite the acceptor never having signed at `r.0.1`, and the forged dispute request is accepted by the arbiter's wallet.
