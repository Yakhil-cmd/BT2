### Title
`prosaic_contract_response` / `arbiter_contract_response` signed acceptance is not bound to a unique contract identifier and is replayable - ([File: wallet.js])

### Summary
The `prosaic_contract_response` and `arbiter_contract_response` handlers in `wallet.js` accept a peer's `signed_message` as proof of contract acceptance, but the signature is only checked against the contract's `peer_address` and its free-text `title`, never against the contract's own unique `hash`. This mirrors the reported `changeRecipientAddress` flaw: the signed payload is generic (address + title text) rather than bound to a unique, single-use identifier, so a previously captured valid signature can be replayed against a different contract record.

### Finding Description
Both handlers extract a `body.signed_message`, base64-decode/parse it into `objSignedMessage`, and validate it with: [1](#0-0) [2](#0-1) 

The validation performed is:
```js
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
```
`validateSignedMessage` (in `signed_message.js`) only checks that the signature is cryptographically valid for the given address and that the structure is well-formed; it does not tie the message to any specific contract hash, nonce, or `chain`/network context beyond an optional `last_ball_unit` freshness check: [3](#0-2) 

The only binding applied by the caller is a string-equality check between `objSignedMessage.signed_message` and `objContract.title` (free text) plus the address. There is no check that the signature commits to `body.hash` (the specific contract's unique hash) or any single-use nonce. Consequently, exactly like the reported Vault.sol issue, the "message" being authenticated (`peer_address` + `title`) is generic and can be satisfied by more than one contract record if the title text is reused (a common pattern for template/boilerplate contract titles), or if a contract is deleted/recreated with the same title.

### Impact Explanation
If an attacker (or a malicious/compromised counterparty device) can cause or observe a second contract to be created between the same peer addresses with an identical `title`, a previously issued (and possibly reused/leaked) signed acceptance for that title can be replayed to flip the new contract's `status` to `"accepted"` without the peer actually consenting to the new contract's specific terms. For `arbiter_contract`, an accepted status is the trigger that downstream business/payment logic treats as the peer's binding consent, potentially leading to funds being released or a dispute being resolved based on a forged acceptance of terms the peer never agreed to for that particular contract instance.

### Likelihood Explanation
Exploitation requires the ability to get, or already possess, a valid signed acceptance message for a given `title`/`peer_address` pair and for a second contract sharing the same title to exist (e.g., reused templates, re-sent offers after a decline, or a contract recreated after being deleted). This is a device-message-level attack path reachable by any paired-device counterparty (no special privileges beyond normal wallet/contract pairing), matching the "paired device" reachable actor described in scope.

### Recommendation
Bind the signed acceptance to the contract's unique `hash` (and ideally a timestamp or single-use nonce) instead of, or in addition to, the free-text `title`, e.g. require `objSignedMessage.signed_message` to equal `objContract.hash` (or a structured object containing `{hash, title, timestamp}`), so that a signature cannot be replayed across different contract records that happen to share identical title text.

### Proof of Concept
1. Peer A and Peer B negotiate a prosaic/arbiter contract with title `"Standard NDA v1"`; peer B signs and sends `signed_message` accepting it, which is validated and stored as accepted.
2. Later, peer A (or someone who intercepted the wire message) creates a new contract with the same title `"Standard NDA v1"` but different terms/amount, and re-submits the same captured `signed_message` as the `body.signed_message` for the new contract's hash.
3. `validateSignedMessage` succeeds because the signature matches the address, and `objSignedMessage.signed_message != objContract.title` is `false` because titles match — the new, different contract is accepted without peer B's actual consent to its terms. [1](#0-0) [2](#0-1) [3](#0-2) 

Note: I was unable to fully inspect `arbiter_contract.js`/`prosaic_contract.js` (hash computation and downstream fund-release logic tied to `status === "accepted"`) within the available tool calls, so the exact fund-impact chain after a forged "accepted" status could not be fully traced in this session; this should be verified further (e.g., via a Devin session with full file access) before treating this as conclusively High severity.
