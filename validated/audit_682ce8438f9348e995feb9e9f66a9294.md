### Title
Unhandled `throw Error` in Private-Payment Double-Spend Resolution Crashes Full Node - (File: validation.js)

### Summary
`ocore` contains a bug-class analog to CVE-2018-14044: an assertion-style failure (`throw Error(...)`) inside code that processes remote, attacker-influenced input, causing the process to crash instead of gracefully rejecting the invalid input. In `ocore`, the `checkInputDoubleSpend` routine used while validating divisible private-asset payments contains such an unhandled `throw` in its `onDone` callback: [1](#0-0) 

```js
function onDone(err){
    if (err && objAsset && objAsset.is_private && !conf.bLight)
        throw Error("spend proof didn't help: "+err);
    cb2(err);
}
```

### Finding Description
`checkInputDoubleSpend` is invoked while validating each `transfer` input of a private, divisible asset payment via `validatePaymentInputsAndOutputs` → `validatePayment`, both of which are reached directly from `validateInlinePayload` when a peer or private-payment counterparty forwards a chain of private-payment units to be validated on a full (non-light) node: [2](#0-1) [3](#0-2) 

For private, divisible assets, the double-spend detection/resolution flow calls `checkForDoublespends`, and its completion handler `onDone` is supposed to surface validation errors back through the async callback chain (`cb2(err)`). Instead, when the asset `is_private` and the node is a full node (`!conf.bLight`), any error returned from the double-spend proof resolution is turned into a synchronous `throw Error(...)` rather than being propagated as a normal validation failure: [4](#0-3) 

Because this throw occurs inside a deeply nested async/database callback chain (`conn.query` → `checkForDoublespends` → `onDone`), it is not caught by any surrounding `try/catch` in the validation pipeline, so it becomes an uncaught exception. In a standard Node.js process, this results in the node crashing (process exit) — an application-level denial of service directly analogous to the SoundTouch `RateTransposer::setChannels` assertion failure in the CVE, where malformed/attacker-crafted input reaches an `assert`/hard failure instead of being handled as a normal error path.

### Impact Explanation
Any private-payment counterparty who forwards a crafted or inconsistent private-payment chain (one whose "spend proof" fails validation for a private asset input) to a full node can trigger this uncaught `throw`, crashing that node's process. This is a legitimate application-reachable denial-of-service: a single unprivileged private-payment counterparty can halt a full node that attempts to validate the forwarded chain, mirroring the "remote attacker causes application exit via assertion failure" bug class from the CVE.

### Likelihood Explanation
The path is reachable through the standard chain of private-payment validation (`validatePayment` → `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends` → `onDone`) any time a full node is asked to validate a private, divisible-asset payment chain whose spend-proof check fails after being processed as a doublespend, which can be induced by a counterparty deliberately constructing an inconsistent private-payment chain.

### Recommendation
Replace the `throw Error("spend proof didn't help: "+err)` in `onDone` with normal error propagation (`return cb2(err)` or an equivalent transient/permanent validation error), ensuring the failure is treated as a rejected unit rather than an unhandled exception that crashes the node process.

### Proof of Concept
1. As a private-payment counterparty, construct and forward a private, divisible-asset payment chain in which a `transfer` input's underlying spend proof is invalid/inconsistent (so that `checkForDoublespends`'s resolution ultimately returns an error for this private asset).
2. Send this chain to a full node (`conf.bLight === false`) for private-payment validation via the normal private-payment acceptance flow that calls `validatePayment`/`validatePaymentInputsAndOutputs`.
3. When `checkInputDoubleSpend`'s `onDone(err)` executes with a non-null `err` for the private asset, the process executes `throw Error("spend proof didn't help: "+err)` outside of any catching context, crashing the node.

Note: I was not able to fully trace the internal implementation of `checkForDoublespends` (only partial context was retrieved) to enumerate every concrete input combination that produces an `err` here; a Devin session with full file access would be needed to construct an exact minimal reproducing private-payment chain.

function validatePayment(conn, payload, message_index, objUnit, objValidationState, callback){

	if (!isNonemptyObject(payload))
		return callback("payment must be a non-empty object");
	if (!isNonemptyArray(payload.inputs))
		return callback("no inputs");
	if (!isNonemptyArray(payload.outputs))
		return callback("no outputs");

	if (!("asset" in payload)){ // base currency
		if (hasFieldsExcept(payload, ["inputs", "outputs"]))
			return callback("unknown fields in payment message");
		if (objValidationState.bHasBasePayment)
			return callback("can have only one base payment");
		objValidationState.bHasBasePayment = true;
		return validatePaymentInputsAndOutputs(conn, payload, null, message_index, objUnit, objValidationState, callback);
	}
