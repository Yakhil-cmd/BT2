### Title
Cross-organization webhook forgery: signature verified against attacker's org secret, but handlers act on repository/organization fields never covered by that verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC signature against based on an **unauthenticated** field pulled straight out of the still-unverified JSON body (`repository.owner.login` or `organization.login`). The event handlers that actually mutate state (`PushHandler`, `MembershipHandler`, etc.) then act on a *different* field of that same unverified body (`repository.full_name`, `organization.login` for team creation, etc.). Because the field used to pick the verification secret is not the same field — nor cryptographically bound to the same field — used to decide what gets written, an attacker who knows (or controls) the webhook secret for *one* configured GitHub organization can forge a signed payload whose `repository.owner.login`/`organization.login` matches their own org (so verification passes) while `repository.full_name` (or other identifying fields consumed by the handler) points at a stack/team belonging to a *different* organization configured on the same Shipit instance.

### Finding Description
`Shipit.github(organization:)` supports a config schema keyed by organization, each with its own independent `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` derives the organization used to look up the secret purely from the raw, not-yet-verified request body: [2](#0-1) [3](#0-2) 

Once `head(422) unless verified` fails to halt (note: `verify_signature` does not `return` after calling `head(422)`, so execution proceeds to `create` regardless, relying only on Rails' after-render halt as documented in tests), `create` parses the body and dispatches it to handlers: [4](#0-3) 

The base `Handler` class and `PushHandler` resolve the target `Stack`/`Repository` using `repository.full_name`, a completely different field than the one used to select the verification secret: [5](#0-4) [6](#0-5) 

`MembershipHandler` similarly trusts `params.organization.login` (again, part of the same unverified body) to create/attach teams and members: [7](#0-6) 

The equality that should hold — "organization whose secret authenticated the request" == "organization/repository the handler writes to" — is never enforced. The signature only proves *some* secret matches *some* value pulled from the body; it does not prove that value is consistent with the other body fields the handlers trust to select the target repository/organization/stack.

### Impact Explanation
On a multi-tenant Shipit instance (multiple orgs configured under `secrets.github`, each with a distinct `webhook_secret`), an attacker who is a legitimate, low-privilege member of Org A (and therefore knows or can obtain Org A's webhook secret, e.g. by configuring their own webhook receiver/App with that secret, or simply because Org A's webhook secret leaks/is weaker) can craft a POST to `/webhooks` (or the mounted webhook path) with:
- `repository.owner.login` / `organization.login` = `org-a` (so `verify_signature` picks org A's secret, which the attacker controls, and passes),
- `repository.full_name` = `org-b/some-repo` (a repository belonging to a different, unrelated organization B on the same Shipit instance).

This lets the attacker trigger `GithubSyncJob` and other push-driven side effects (which can influence what commit is considered "head" for deploys) on Org B's stack, or — via the `membership` event — create teams/attach members under an arbitrary organization label without ever holding credentials for Org B. This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in the rules, and can lead to actions on stacks/repositories outside the authenticating tenant's authority — effectively a cross-repository/cross-organization write via a forged but "validly signed" webhook.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (config keyed by organization, each with its own `webhook_secret`), and (2) the attacker possessing or being able to obtain one org's webhook secret (a lower bar than repository write access or a Shipit API token — webhook secrets are often set up by any admin of a connected GitHub App/org and are not scoped to prevent this cross-use). Single-organization deployments (the common/default case, where `github_default_organization` is `nil`) are not affected because there is only one secret to select from. Likelihood is therefore contingent on the multi-tenant configuration, but the code path itself has no compensating check.

### Recommendation
After signature verification succeeds for organization `X`, enforce that every identifying field the handlers consume (`repository.owner.login`, `repository.full_name`'s owner segment, `organization.login`) actually belongs to `X` before dispatching to handlers — i.e., bind the verified secret's organization to the same field(s) the handlers use to resolve the target `Repository`/`Stack`/`Team`, rejecting the request if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (multi-org schema per `lib/shipit.rb#github_app_config`).
2. As a holder of `org-a`'s webhook secret, craft a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(org-a's webhook_secret, raw body).
4. POST to the webhooks endpoint with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `org-a`, fetches `org-a`'s `GitHubApp`, and the signature verifies successfully.
6. `create` parses the body and calls `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")` — a repository under `org-b`, whose secret the attacker never had — and enqueues `GithubSyncJob` against it.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
