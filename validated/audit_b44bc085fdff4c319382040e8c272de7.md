### Title
Missing Zero-Address Check in Bridge KAIA Transfer Functions Allows Permanent Burn of Bridge Liquidity - (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`requestKLAYTransfer` and `handleKLAYTransfer` in `BridgeTransferKLAY.sol` accept `_to = address(0)` without validation. Any unprivileged user can call `requestKLAYTransfer(address(0), value, extraData)`, causing the bridge operator to faithfully relay the event and execute `_to.call.value(_value)("")` with `_to = address(0)` on the destination chain. In Solidity 0.5.6 / EVM, a low-level call to `address(0)` succeeds and the KAIA is permanently destroyed from the bridge's liquidity pool.

---

### Finding Description

**Step 1 — Source chain (unprivileged trigger):**

`requestKLAYTransfer` is `external payable` with no access control and no zero-address guard on `_to`:

```solidity
// BridgeTransferKLAY.sol L132-134
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

`_requestKLAYTransfer` also has no zero-address check and emits `RequestValueTransfer` with `_to = address(0)`:

```solidity
// BridgeTransferKLAY.sol L103-124
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal unlockedKLAY nonReentrant
{
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    // ... no require(_to != address(0)) ...
    emit RequestValueTransfer(TokenType.KLAY, msg.sender, _to, address(0), msg.value.sub(_feeLimit), requestNonce, fee, _extraData);
    requestNonce++;
}
``` [1](#0-0) 

**Step 2 — Destination chain (operator relay):**

The bridge operator observes the `RequestValueTransfer` event with `_to = address(0)` and calls `handleKLAYTransfer`. The function has no zero-address guard and executes a low-level KAIA transfer to `address(0)`:

```solidity
// BridgeTransferKLAY.sol L62-99
function handleKLAYTransfer(
    bytes32 _requestTxHash,
    address _from,
    address payable _to,   // <-- no require(_to != address(0))
    uint256 _value,
    ...
) public onlyOperators nonReentrant {
    ...
    (bool ok, ) = _to.call.value(_value)("");   // sends KAIA to address(0)
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [2](#0-1) 

In EVM, `address(0).call{value: v}("")` returns `(true, "")` — the call succeeds and the KAIA is permanently destroyed. The `require(ok, ...)` passes, the handle nonce advances normally, and the loss is irreversible.

**Parallel path — ERC20 in modeMintBurn:**

`_requestERC20Transfer` also has no zero-address check on `_to`. In `modeMintBurn` mode, the source-chain tokens are burned (`ERC20Burnable.burn(_value)`) before the event is emitted. On the destination chain, `handleERC20Transfer` calls `ERC20Mintable(_tokenAddress).mint(address(0), _value)`, which reverts due to OpenZeppelin's guard. The source-chain tokens are permanently destroyed and never reminted — a total loss of bridged ERC20 assets. [3](#0-2) [4](#0-3) 

---

### Impact Explanation

- **KAIA case**: KAIA from the bridge's destination-chain liquidity pool is permanently burned. The source-chain deposit is consumed (`requestNonce++`), the destination-chain handle nonce advances, and the KAIA is irrecoverably sent to `address(0)`. Bridge liquidity providers suffer a direct, unrecoverable loss.
- **ERC20 modeMintBurn case**: Bridged ERC20 tokens are permanently destroyed on the source chain and never reminted on the destination chain.

Both outcomes satisfy the allowed impact gate: *unauthorized burn of KAIA / bridged assets from system-managed bridge funds*.

---

### Likelihood Explanation

`requestKLAYTransfer` is `external payable` with no access control — any EOA or contract can call it with `_to = address(0)`. The operator is a faithful relay and has no independent guard. The path requires only a single user transaction on the source chain and one operator relay transaction on the destination chain. No privileged access, no majority-validator collusion, and no external service compromise is required.

---

### Recommendation

Add zero-address guards in both the request and handle paths:

```solidity
// In _requestKLAYTransfer (BridgeTransferKLAY.sol)
require(_to != address(0), "transfer to the zero address");

// In handleKLAYTransfer (BridgeTransferKLAY.sol)
require(_to != address(0), "transfer to the zero address");

// In _requestERC20Transfer (BridgeTransferERC20.sol)
require(_to != address(0), "transfer to the zero address");
``` [5](#0-4) [6](#0-5) 

---

### Proof of Concept

1. Deploy `BridgeTransferKLAY` on source chain (S) and destination chain (D). Fund D-bridge with 10 KAIA liquidity.
2. On S, call:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(0), 1 ether, "");
   ```
   No revert. `RequestValueTransfer` event emitted with `to = address(0)`, `requestNonce` incremented to 1.
3. Operator observes event and calls on D:
   ```solidity
   bridge.handleKLAYTransfer(txHash, msg.sender, address(0), 1 ether, 0, blockNum, "");
   ```
4. `address(0).call{value: 1 ether}("")` executes, returns `(true, "")`. `require(ok)` passes.
5. D-bridge balance decreases by 1 KAIA. `lowerHandleNonce` advances to 1. KAIA is permanently destroyed. No revert, no recovery path.
