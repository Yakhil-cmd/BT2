### Title
Unscoped `Commit.where(sha: params.sha)` in `StatusHandler#process` lets a status webhook from one repository mutate a commit belonging to any other stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` selects every `Commit` row in the database whose `sha` matches the incoming webhook payload, with no filter on the repository/stack the webhook was signed for. `Commit#create_status_from_github!` then writes a `Status` scoped correctly to that commit's own `stack_id`, but since the *commit selection* was never scoped to the sending repository, the effective write target (which stack gets a new/forged status) is entirely attacker-influenced whenever a sha collides across repositories (forks, shared history, cherry-picked commits).

### Finding Description
The claimed binding is: `Status.stack_id == commit.stack_id` **and** `commit.stack_id == repository_that_sent_the_webhook.stack_id`. The first half holds — `statuses.replicate_from_github!(stack_id, github_status)` in [1](#0-0)  always uses the receiver's own `stack_id`. The second half is false: the commit is picked by [2](#0-1) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no `stack_id`, `repository_id`, or `repository.full_name` constraint tying the lookup to the repository that authenticated the webhook. `params.sha` is attacker-supplied content of a real GitHub commit-status payload, and git commit SHAs are content-addressed, so the same SHA legitimately exists in multiple repositories (a fork of a victim's repo, a repo that merged/cherry-picked the victim's commit, etc.).

Exploit flow:
1. Attacker controls (or is a legitimate collaborator on) Repo A, which is already onboarded as a Shipit stack, so GitHub signs Repo A's webhooks with Repo A's real `webhook_secret` — the attacker never needs to know that secret, GitHub computes it.
2. Attacker forks or otherwise obtains a copy of the victim's repository (Repo B, tracked by a different Shipit stack) such that Repo A shares a commit SHA with Repo B (trivial via forking, since forks share git objects).
3. Attacker sets an arbitrary commit status (e.g., `state: success`) on that shared SHA in Repo A via the ordinary GitHub UI/API — an action fully within an unprivileged repo owner's rights on their own repo.
4. GitHub emits a legitimately signed `status` webhook for Repo A to the shared Shipit host.
5. `verify_signature`/`GitHubApp#verify_webhook_signature` correctly authenticates that the payload came from GitHub for Repo A — it does **not** and cannot verify that `params.sha` "belongs" to Repo A's stack, because Shipit's own model has no such invariant. It authenticates the *sender*, not the *scope of the sha field*.
6. `StatusHandler#process` finds **every** `Commit` row with that sha, including the one in Repo B, and calls `create_status_from_github!` on it, writing a `Status` correctly attributed to Repo B's `stack_id` — a forged status on a repository the attacker never authenticated against.

None of the existing guards prevent this: `verify_signature` only proves "this HTTP request came from GitHub for Repo A," `drop_unhandled_event` only filters event types, and the `ExplicitParameters` schema on `StatusHandler` only validates the shape of `sha`/`state`/etc., not their relationship to a specific repository. The same unscoped pattern also exists in `CheckSuiteHandler` (`where(sha:` per grep results), so this class of bug is systemic, not a one-off.

### Impact Explanation
A forged/legitimate-but-cross-purposed status on Repo A's commit becomes a real `Status` row on Repo B's commit, in Repo B's stack, without Repo B's repository/webhook ever being involved. Because `add_status` (called from `create_status_from_github!`) can flip a commit from non-deployable to deployable and calls `stack.schedule_merges if new_status.pending? || new_status.success?` ( [3](#0-2) ), this can trigger continuous-delivery / auto-merge logic on Repo B's stack based on a status the attacker fabricated on their own, unrelated Repo A. This matches the "Critical - a payload for one repository mutating another's stack, commit, task or team" category: an attacker with control of any single onboarded repository can inject status state into any other stack sharing a commit SHA with it.

### Likelihood Explanation
Preconditions: attacker must control (or have status-write access to) at least one repository that is already an onboarded Shipit stack, and must be able to produce a commit whose SHA also appears in the victim stack's commit history (forking a public repo, or the victim/attacker repos sharing a common ancestor/cherry-pick). No Shipit secrets, sessions, or GitHub App keys are needed — only ordinary GitHub repository status-setting permission on the attacker's own repo, which is well within the described unprivileged attacker capabilities ("push to a fork ... emit webhooks from a repository they own"). This is fully repeatable against any commit SHA the attacker can arrange to share with a target repo.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `CheckSuiteHandler`) by the repository identified in the webhook payload, e.g. resolve the target `Stack`/`Repository` from `payload.repository.full_name` (as already validated by signature verification) and constrain `Commit.where(sha: params.sha, stack: repository.stacks)` (or join through `stack.repository_id`) before mutating any commit, instead of a global unscoped `sha` match.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook for repository A does not mutate a commit belonging to repository B's stack" do
  shared_sha = "a" * 40

  stack_a = shipit_stacks(:shipit)                     # attacker-controlled stack
  stack_b = create_stack(repository: create_repository(full_name: "victim/repo"))
  victim_commit = stack_b.commits.create!(sha: shared_sha, message: "victim commit")

  # attacker forges/sends a *validly signed* status payload for stack_a's repo,
  # but the sha collides with victim_commit's sha in an unrelated stack.
  payload = { sha: shared_sha, state: "success", context: "ci", description: nil, target_url: nil }

  assert_no_difference -> { stack_a.commits.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(
      repository_owner: stack_a.repository.owner,
      repository: stack_a.repository,
      delivery: SecureRandom.uuid,
      params: ExplicitParameters.for(Shipit::Webhooks::Handlers::StatusHandler).from(payload)
    ).process
  end

  victim_commit.reload
  # PROVES the write happened on the victim's stack despite the webhook only
  # having authenticated attacker's stack_a:
  assert_equal stack_b.id, Shipit::Status.last.stack_id
  assert_equal victim_commit.id, Shipit::Status.last.commit_id
  assert_equal "success", victim_commit.status.state
end
```
This demonstrates that `Status.stack_id` always equals `commit.stack_id` (the "locally correct" scoping in `create_status_from_github!`), while the commit selected — and therefore the stack mutated — was never authorized by the attacker's own repository/webhook, confirming the root cause is the unscoped `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb`.
