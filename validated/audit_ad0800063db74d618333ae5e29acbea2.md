### Title
Unvalidated P2P StakingInfo Accepted During Fast/Snap Sync Corrupts Staking DB — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

---

### Summary

The `validate` callback inside `queue.DeliverStakingInfos` is an unimplemented TODO stub that unconditionally returns `nil`. Any P2P peer serving staking info during a fast-sync or snap-sync session can supply arbitrary `RewardAddrs`, `KEFAddr`, `KIFAddr`, and `StakingAmounts` values. Those values are committed verbatim to the staking database via `commitFastSyncData → PutStakingInfoToDB` with no cryptographic or state-root check. Because `GetStakingInfo` trusts the database as authoritative for all pre-Kaia-fork epochs, the corrupted entries are used directly for block reward distribution on every node that fast-synced from the malicious peer.

---

### Finding Description

**Step 1 — No-op validate in `queue.DeliverStakingInfos`** [1](#0-0) 

The `validate` closure at line 956–958 is a permanent no-op (`// TODO-Kaia-Snapsync update validation logic; return nil`). Contrast this with `DeliverBodies`, which verifies `TxHash`, and `DeliverReceipts`, which verifies `ReceiptHash` — both against the already-validated block header. No equivalent check exists for staking info.

**Step 2 — Fast/snap sync unconditionally fetches staking infos from the sync peer** [2](#0-1) 

`fetchStakingInfos` is spawned as a concurrent fetcher for every sync session (FastSync and SnapSync). The peer-supplied `P2PStakingInfo` batch flows through `queue.DeliverStakingInfos` (with the no-op validate) into the result cache.

**Step 3 — `commitFastSyncData` writes peer-supplied staking info to the DB unconditionally** [3](#0-2) 

`result.StakingInfo` is whatever the peer sent. There is no comparison against the block's state root, no re-derivation from the AddressBook contract, and no signature check. The same unconditional write occurs in `commitPivotBlock` at line 1896–1898.

**Step 4 — `GetStakingInfo` treats the database as authoritative for pre-Kaia blocks** [4](#0-3) 

For any block number before the Kaia hardfork, if a DB entry exists it is returned immediately — the state is never consulted. After fast sync the historical state is unavailable (only the pivot-block state was synced), so the node has no way to detect or override the forged DB entry.

---

### Impact Explanation

A malicious fast-sync peer can forge `RewardAddrs` (validator reward destinations), `KEFAddr`/`KIFAddr` (treasury fund addresses), and `StakingAmounts` for every pre-Kaia staking epoch. Those forged entries are persisted to the staking DB and subsequently used by `GetStakingInfo` → `assignStakingRewards` to distribute block rewards. The result is unauthorized redirection of KAIA block rewards (validator share + treasury share) to attacker-controlled addresses on every node that fast-synced from the malicious peer. [5](#0-4) 

The impact is scoped to pre-Kaia-fork epochs. Post-Kaia blocks derive staking info from the previous block's state, bypassing the DB entirely.

---

### Likelihood Explanation

Any node performing fast sync or snap sync is exposed. The attacker only needs to be a reachable P2P peer that the victim selects as its sync source — no privileged key, governance role, or validator majority is required. The attack is silent (no error is returned) and durable (the DB entry persists across restarts).

---

### Recommendation

Implement the missing validation inside `queue.DeliverStakingInfos`. The staking info for a block can be verified by re-deriving it from the AddressBook contract state at the source block (using the already-synced state trie or a Merkle proof), or by committing a hash of the expected staking info into the block header so it can be checked against the validated header. At minimum, remove the unconditional DB write in `commitFastSyncData`/`commitPivotBlock` and instead re-derive staking info from state after the pivot state sync completes.

---

### Proof of Concept

1. Fork the downloader test harness (`downloader_test.go`).
2. Create a `downloadTesterPeer` whose `RequestStakingInfo` returns a `P2PStakingInfo` with `RewardAddrs` replaced by attacker-controlled addresses for every requested block hash.
3. Run a fast-sync session against this peer.
4. After sync, call `staking_impl.ReadStakingInfo(tester.stateDb.GetMiscDB(), epochBlock)` for a pre-Kaia epoch block.
5. Assert that the stored `RewardAddrs` match the attacker-supplied values — demonstrating that forged data was committed to the staking DB with no error and no rejection.

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
