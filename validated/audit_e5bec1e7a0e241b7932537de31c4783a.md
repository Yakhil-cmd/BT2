The reported bug is specific to the `RFPSimpleStrategy.sol` Allo-v2 contract's milestone state machine, where `_distribute` fails to check `milestone.milestoneStatus` before paying out, allowing payout of a milestone that had been explicitly set to `Status.Rejected`. I looked for an analogous state-machine flaw in Polkadot SDK's FRAME "bounty" pallets (`pallet-bounties`, `pallet-child-bounties`, `pallet-multi-asset-bounties`), since these are the closest conceptual match (curator proposes work, funds are distributed on milestone/award completion, and there's a reject/cancel path).

In all three pallets, the award/payout functions gate on the current `BountyStatus`/`ChildBountyStatus` enum via exhaustive `match`/`if let` patterns, and only proceed from the `Active` state: [1](#0-0) [2](#0-1) 

Once a bounty/child-bounty is rejected or cancelled via `close_bounty`/`close_child_bounty`, the entry is either removed from storage entirely or transitioned to a state (e.g. `RefundAttempted`) that the award/payout functions explicitly reject with `Error::UnexpectedStatus`: [3](#0-2) 

There is no persistent "Rejected" status left alongside an separately-indexed "amount to distribute" that an award/payout call could still act on — unlike `RFPSimpleStrategy._distribute`, which reads `milestone.milestoneStatus` but never checks it against `Status.Rejected` before paying out. FRAME's design instead makes state transitions exhaustive and mutually exclusive, so there is no reachable path in these pallets where a rejected milestone/payout can still be distributed by an ordinary signed extrinsic without a privileged role. I found no comparable check-omission in the searched pallets, and no other "milestone"-like payout construct in the indexed codebase that reproduces this exact missing-status-check pattern through a real, unprivileged entry point.
