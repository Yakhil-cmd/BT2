This confirms the vulnerability: `reset_session` is called in `force_github_authentication` only when a *logged-in* user requires fresh login, and in `logout`, but never in `callback` before `session[:user_id]` is assigned.### Title
Session fixation in `Shipit::GithubAuthenticationController#callback` allows pre-authentication session ID to survive login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`#callback` writes `session[:user_id]` and `session[:authenticated] = true` directly into the current session without ever calling `reset_session`, so a session identifier that existed before OAuth completion remains valid and privileged after it. An attacker who fixes a victim's session ID before the OAuth handshake gains full control of that session once the victim authenticates.

### Finding Description
Binding that should hold: `session_id_before_auth != session_id_after_auth` (the identifier must be rotated at the authentication boundary). Binding actually observed: `session_id_before_auth == session_id_after_auth`, since `callback` mutates the existing session hash in place.

Code path: `Shipit::Authentication#force_github_authentication` [1](#0-0)  redirects an unauthenticated visitor to the GitHub OAuth flow, and after GitHub redirects back, `GithubAuthenticationController#callback` runs: [2](#0-1) 

There is no `reset_session` call anywhere in this method (contrast with `logout`, which does call it, and with `force_github_authentication`'s "requires fresh login" branch, which also calls it) [3](#0-2) [4](#0-3) . Because Rails' cookie/redis session store keeps the same session ID unless explicitly regenerated, any anonymous visit that causes Shipit to issue a session cookie (which happens automatically since `force_github_authentication` runs on every request and Rails assigns a session id lazily) gives an attacker a session ID they can plant in a victim's browser via any link back to the Shipit host (no GitHub interaction needed by the attacker).

Exploit flow:
1. Attacker visits Shipit anonymously, obtains session ID `S` (set via `Set-Cookie` on first request).
2. Attacker fixes `S` into the victim's browser (e.g., via a crafted link that sets the cookie, or by knowing the session id if the app doesn't rotate on new visits).
3. Victim, using the browser holding session `S`, is redirected through `force_github_authentication` to the real GitHub OAuth flow and completes it legitimately.
4. `#callback` executes `session[:user_id] = sign_in_github(auth)` on session `S`, and sets `session[:authenticated] = true`, without rotating the session ID.
5. Attacker, who already possesses session ID `S`, can now send requests using cookie `S` and be treated as `current_user` per `find_current_user` (`session[:user_id].present? && User.find_by(id: session[:user_id])`) [5](#0-4) .

Existing guards do not prevent this: `force_github_authentication` only calls `reset_session` when an already-logged-in user needs a fresh login due to token/team changes (`requires_fresh_login?`), not at the point of first successful login [3](#0-2) . `current_user.authorized?` and the GitHub-teams check only gate access after authentication and do nothing to prevent the fixed session ID from becoming a valid authenticated session.

### Impact Explanation
Once the victim completes OAuth on the attacker-controlled session ID, the attacker can replay that session cookie to issue requests as the victim's `User` row against any stack the victim is authorized to deploy, roll back, or merge on — a full authentication bypass matching the "session fixation / forced OAuth completion" and "authentication bypass" categories in scope. Impact is per-victim and repeatable against any operator the attacker can lure into completing OAuth over the fixed session.

### Likelihood Explanation
Preconditions are realistic and low-cost: the victim must not have visited Shipit before in that browser profile (common for first-time SSO logins), the default cookie/redis session store must be in use, and the attacker needs only to get the operator to click a link to the Shipit host to plant the pre-auth session id. No GitHub secrets, Shipit secrets, or privileged roles are required by the attacker. This is a classic, well-understood session-fixation pattern and is straightforward to weaponize.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` immediately before writing `session[:user_id]`/`session[:authenticated]`, so a new session ID is issued at the authentication boundary, e.g.:
```ruby
def callback
  ...
  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```
Note this must be done before setting session values (and `return_url` must be captured before `reset_session` if it depends on prior session state — here it comes from `omniauth.origin`, not the session, so this is safe).

### Proof of Concept
Minitest plan (`test/controllers/github_authentication_controller_test.rb`, functional/controller test, no live GitHub required — OmniAuth mock env):

```ruby
test "callback rotates the session id (no session fixation)" do
  # Simulate a pre-existing (attacker-fixed) session
  session[:marker] = 'preexisting'
  pre_session_id = request.session.id  # or session.id depending on Rails version

  auth_hash = OmniAuth::AuthHash.new(
    extra: { raw_info: { id: 42, login: 'octocat', ... } },
    credentials: { token: 'tok' }
  )
  request.env['omniauth.auth'] = auth_hash
  request.env['omniauth.origin'] = '/'

  get :callback

  # Vulnerable behavior: fixed marker and session id both survive
  assert_equal 'preexisting', session[:marker], "session was not rotated -- fixation possible"
  assert session[:user_id].present?

  # Fixed test (after applying recommendation) should assert:
  # assert_nil session[:marker]  # old session data discarded
  # assert_not_equal pre_session_id, request.session.id
end
```

This demonstrates that `session[:marker]` set before `#callback` (representing the attacker-fixed session content/identity) survives untouched alongside the newly populated `session[:user_id]`, proving `reset_session` is never invoked and the pre-auth and post-auth session identifiers are one and the same.
