### Title
Webhook signature verification is scoped to the wrong field, letting an unauthenticated/under-privileged sender direct a "verified" push event at any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to check a payload's HMAC signature against using `repository_owner`, taken from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  But the code that actually *acts* on the payload — `Handler#stacks`, used by e.g. `PushHandler#process` — resolves the target repository/stack from a completely different field, `payload.dig('repository','full_name')`. [3](#0-2) [4](#0-3)  Nothing ties `owner.login` (the field the signature check is keyed on) to `full_name` (the field the handler trusts), so the "organization whose secret authenticated the request" and "the repository that is written" are two independently attacker-controlled JSON fields in the same unsigned-at-the-field-level payload.

### Finding Description
`GitHubApp#verify_webhook_signature` explicitly treats an org/app config with no configured `webhook_secret` as always verified:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 
`webhook_secret` is explicitly documented and templated as *optional* (`webhook_secret: # nil`), both in the setup guide and in the generated `secrets.yml`. [6](#0-5) [7](#0-6) [8](#0-7) 

The controller's `verify_signature` selects which `Shipit.github(organization:)` config (and thus secret) to check against based on `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the request passes this check, the raw parsed JSON is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [9](#0-8)  The base `Handler` class - used by `PushHandler`, pull-request handlers, etc. - resolves the actual stacks/repository to operate on from a *different* JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the pushed branch. [10](#0-9) 

**Break of the binding:** signature verification is keyed on `repository.owner.login` (or the fallback `organization.login`), while the repository actually acted upon is keyed on `repository.full_name`. These two fields are never cross-checked against each other. In a legitimate GitHub-originated payload they always agree, but nothing in this codebase enforces that — an attacker who can get *any one* configured GitHub App/org in the Shipit installation to "verify" (trivially true if that org has no `webhook_secret` configured, which is the documented optional default) can set `repository.owner.login` to that org while setting `repository.full_name` to `some-other-org/some-other-tracked-repo`. The `verify_signature` before_action passes, and `PushHandler` (or `StatusHandler`/`CheckSuiteHandler`, which use the same `Handler#stacks` helper) will resolve and act on the completely unrelated tracked stack named by `full_name`, including invoking `stack.sync_github(expected_head_sha: ...)` with an attacker-chosen SHA for a repository the attacker never authenticated against.

### Impact Explanation
This lets an attacker who does not hold a webhook secret for the targeted repository/organization forge a "verified" webhook event that resolves and mutates state (triggering `GithubSyncJob`/`sync_github`) for any stack tracked by the Shipit instance, as long as some other configured org in the same instance has no `webhook_secret` set (an explicitly supported/optional configuration per `docs/setup.md`). Because `sync_github` can drive continuous-deployment/undeployed-commit tracking with an attacker-chosen `expected_head_sha`, this can be used to coerce out-of-band syncs/deploy triggers on a repository the attacker has no legitimate relationship to — i.e., an unauthorized deploy trigger against a cross-organization/cross-repository target, achieved purely by crafting an HTTP payload with mismatched `owner.login`/`full_name` fields, with no session, no ApiClient token, no GitHub write access, and no knowledge of the target repository's own webhook secret.

### Likelihood Explanation
Requires a multi-tenant/multi-org Shipit deployment (documented and supported via the `github: { org: {...} }` config format) where at least one configured organization has no `webhook_secret` set — an explicitly optional field in every shipping config template (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `template.rb`) and in the setup docs. No credentials, session, or GitHub write access are required to exploit; a single crafted unauthenticated HTTP POST to `/webhooks` is sufficient.

### Recommendation
Bind signature verification to the same field that handlers trust for repository resolution. Concretely: derive `repository_owner` (or better, the full `owner/repo`) from the same value later used by `Handler#repository_name`, and additionally assert `payload.dig('repository','full_name')&.split('/')&.first == repository_owner` before dispatching to handlers, rejecting (422) on mismatch. Independently, require `webhook_secret` to be present for every configured GitHub App/org (fail closed rather than "verified" when absent) so that verification can never be trivially bypassed.

### Proof of Concept
Given a Shipit instance configured with two orgs, e.g.:
```yaml
github:
  no-secret-org:
    app_id: ...
    installation_id: ...
    webhook_secret: # left blank, per documented optional setting
  victim-org:
    app_id: ...
    installation_id: ...
    webhook_secret: "s3cr3t-the-attacker-does-not-know"
```
and a tracked stack for repository `victim-org/victim-repo`, an attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   (irrelevant, no secret configured for "no-secret-org")

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-existing-sha-in-victim-repo>",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`). The payload is then dispatched to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the request never being authenticated against `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
