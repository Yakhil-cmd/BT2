### Title
Webhook signature is verified for the payload's `repository.owner.login` while all event handlers act on the payload's `repository.full_name` β€” cross-organization/cross-repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to check the HMAC signature against using one field of the untrusted JSON body (`repository.owner.login`, or `organization.login`), but every webhook handler resolves the actual stack/repository to mutate using a *different*, unrelated field of the same body (`repository.full_name`). The signature never binds these two fields together, so an attacker who can produce a validly-signed payload for organization A can freely substitute organization B's `full_name` and have Shipit act on B's repository/stacks.

### Finding Description
The verification step picks the secret to check against based on the owner login taken directly from the JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That organization key is used only to choose which `Shipit.github(organization: ...)` app/secret is applied when calling `verify_webhook_signature`: [3](#0-2) 

Notice line 77: `return true unless webhook_secret` β€” if the organization picked by `repository_owner` has no `webhook_secret` configured (the setup docs explicitly call this field *optional*), verification trivially succeeds: [4](#0-3) [5](#0-4) 

Once "verified" (against the org named by `repository.owner.login`), every handler ignores that field entirely and instead resolves the target repository/stack from `repository.full_name`: [6](#0-5) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` uses this `stacks` helper to trigger `sync_github` with an attacker-controlled `expected_head_sha`: [7](#0-6) 

The pull-request handlers do the same thing explicitly, re-deriving the target `Repository` from `params.repository.full_name` and then creating/mutating review stacks: [8](#0-7) 

Nowhere is `repository.full_name`'s owner segment checked for equality against `repository.owner.login`/`organization.login`, the field that was actually covered by the signature check. This is exactly the "approveDomainBid" bug class from the report: the field that is authorized (`parentId` / here, `repository_owner`) is not the field that is acted upon (`bidIPFSHash`'s bound data / here, `repository.full_name`), so the authorization is purely informational and can be trivially bypassed by supplying mismatched values in the same request.

### Impact Explanation
On a multi-tenant Shipit deployment (the app explicitly documents and supports configuring multiple GitHub organizations, see `config/secrets.development.example.yml:18-38`), a person who can obtain a validly-signed webhook for *any one* configured organization (including one that simply left `webhook_secret` unset, since it is documented as optional) can forge webhook events that are applied to *any other* organization's/repository's stacks tracked by the same Shipit instance β€” a cross-repository/cross-organization write. This can trigger unauthorized `GithubSyncJob` runs with an attacker-chosen `expected_head_sha`, or (via the pull-request handlers) unauthorized creation/mutation of review stacks (which provision infrastructure and run deploy tasks) for a repository the attacker has no relationship with. This falls under the "cross-repository writes" / "unauthorized deploy" impact category, since it forges the trust binding between the authenticated organization and the repository actually written to.

### Likelihood Explanation
Exploitation requires no Shipit session, API token, or repository write access β€” only the ability to send an HTTP POST to the public `/webhooks` endpoint with a JSON body and an `X-Hub-Signature` header. If the attacker legitimately controls any organization configured on the shared Shipit instance (or one whose secret was left blank, which the setup docs allow), they can compute or trivially satisfy the signature check for that organization, then set `repository.full_name` to any other tracked repository. This requires no secret knowledge for the victim organization at all.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the target repository: reject the webhook (or re-derive the app/secret) unless `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login`. Additionally, do not silently treat a missing `webhook_secret` as "always verified" β€” require an explicit opt-in flag for unsigned webhooks per organization, and validate that the resolved `Repository`/`Stack`'s configured owner matches the organization that was actually verified.

### Proof of Concept
1. Shipit instance is configured for two GitHub organizations, `org-attacker` (installed by the attacker, or configured with `webhook_secret: nil`) and `org-victim` (tracks `org-victim/secret-repo`).
2. Attacker computes/obtains a valid `X-Hub-Signature` for `org-attacker`'s secret (or simply omits meaningful verification since it is unset) and POSTs to `/webhooks`:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/secret-repo"
  }
}
```
with header `X-Github-Event: push`.
3. `WebhooksController#verify_signature` verifies against `org-attacker`'s app config and passes (line 25-30 of `app/controllers/shipit/webhooks_controller.rb`).
4. `PushHandler#process` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"org-victim/secret-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack β€” an action the attacker was never authorized to trigger for `org-victim`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
