### Title
Fee-on-Transfer Token Deposits Cause Destination Bridge Liquidity Drain and Deposit DoS — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` do not account for the actual balance received when pulling ERC20 tokens. For fee-on-transfer tokens, the bridge records the caller-supplied `_value` in the `RequestValueTransfer` event, but only holds `(_value + _feeLimit) * (1 - feeRate)`. The counterpart bridge then releases the full `_value` to the recipient, draining more liquidity than was deposited. Additionally, if `feeLimit` exceeds the actual received amount, the fee/refund transfers revert, causing a DoS on deposits.

### Finding Description

In `requestERC20Transfer`:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` from the user. For a fee-on-transfer token, the bridge actually receives `(_value + _feeLimit) * (1 - feeRate)`. The function then calls `_payERC20FeeAndRefundChange`, which attempts to transfer `fee` to `feeReceiver` and `feeRefund = feeLimit - fee` back to the user:

```solidity
IERC20(_token).safeTransfer(feeReceiver, fee);
uint256 feeRefund = _feeLimit.sub(fee);
if (feeRefund > 0) {
    IERC20(_token).safeTransfer(from, feeRefund);
}
``` [2](#0-1) 

Total outgoing from the bridge for fee/refund = `feeLimit`. If `feeLimit > actual_received`, the `safeTransfer` reverts (DoS). Even when it succeeds, the `RequestValueTransfer` event records the caller-supplied `_value`:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← caller-supplied, not actual received delta
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

The bridge manager reads this event and calls `handleERC20Transfer` on the counterpart bridge with `_value`. In non-mintBurn mode, the counterpart bridge releases exactly `_value` to the recipient:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

The source bridge gained `(_value + _feeLimit) * (1 - feeRate) - feeLimit` tokens; the destination bridge lost `_value`. The net drain per transfer equals `(_value + _feeLimit) * feeRate`.

The same flaw exists in the 1-step `onERC20Received` path, which also calls `_requestERC20Transfer` with the caller-supplied `_value` without measuring the actual balance increase. [5](#0-4) 

### Impact Explanation

**Unauthorized drain of bridged assets (destination bridge liquidity).** Each deposit of a fee-on-transfer token causes the destination bridge to release more tokens than the source bridge received. Over repeated transfers, the destination bridge's liquidity is drained by `(_value + _feeLimit) * feeRate` per transfer. Additionally, if `feeLimit > actual_received`, the deposit transaction reverts entirely (DoS), permanently blocking deposits of that token.

### Likelihood Explanation

**Medium.** Requires a fee-on-transfer token to be registered by the bridge owner (a privileged but routine operational action). Once registered, any unprivileged user calling `requestERC20Transfer` or `token.requestValueTransfer` triggers the accounting discrepancy. Fee-on-transfer tokens are common in DeFi (e.g., tokens with auto-staking or deflationary mechanics).

### Recommendation

Measure the actual balance increase after `safeTransferFrom` and use that delta as the bridged amount, rather than the caller-supplied `_value`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // Derive actual _value from actualReceived minus feeLimit portion
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualReceived, _feeLimit, _extraData);
}
```

### Proof of Concept

1. Bridge owner registers a fee-on-transfer token (1% fee) on both source and destination bridges in non-mintBurn mode.
2. User calls `requestERC20Transfer(feeToken, recipient, 100e18, 0, "")`.
3. Bridge calls `safeTransferFrom(user, bridge, 100e18)` but receives only `99e18` (1% fee taken by token).
4. `_payERC20FeeAndRefundChange` is called with `feeLimit = 0`, so no fee/refund transfers occur.
5. `RequestValueTransfer` event emits `_value = 100e18`.
6. Bridge manager reads the event and calls `handleERC20Transfer(…, recipient, 100e18, …)` on the destination bridge.
7. Destination bridge executes `safeTransfer(recipient, 100e18)`, releasing the full `100e18`.
8. **Net result:** Source bridge gained `99e18`; destination bridge lost `100e18`. `1e18` drained per transfer. Repeated transfers drain the destination bridge's entire liquidity.
