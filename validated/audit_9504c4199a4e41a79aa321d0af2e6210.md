### Title
Permanent market freeze: RAY-valued debt overflows `i128` inside accrual before the borrow-index cap can engage - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
Analog of CVE-2020-14323 (null-pointer crash → service DoS): a reachable arithmetic panic that permanently bricks a market. The borrow index is capped at `MAX_BORROW_INDEX_RAY`, but every accrual first computes `scaled_shares * index` as a RAY value (`scaled_to_original` / `calculate_supplier_rewards` / `Cache::calculate_utilization`). For a sufficiently large book, that product overflows `i128` while the index is still far below the cap, so `Ray::mul` widens to `I256`, `to_i128` fails, and `MathOverflow` panics. Since every pool verb accrues before acting, the panic is permanent: no `repay`, `withdraw`, `supply`, `borrow`, `liquidate`, or `clean_bad_debt` ever succeeds again on that market.

### Finding Description
- `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY`, not the scaled value (`common/src/rates/index.rs:13-19`). [1](#0-0) 
- `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` — scaled debt shares times index — which must fit `i128` (`common/src/rates/index.rs:80-81`). [2](#0-1) 
- The same product is computed in `Cache::calculate_utilization` via `scaled_to_original` on every accrual (`contracts/pool/src/cache/scale.rs:23-26`). [3](#0-2) 
- `Ray::mul`/`mul_div_*` panic with `GenericError::MathOverflow` when the widened `I256` result does not fit `i128` (`common/src/math/fp_core.rs:300-303`). [4](#0-3) 
- The repo's own test proves the end state: after ~20–40 years at ~98% utilization on the steep XLM curve, `update_indexes` reverts with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` revert identically — "no repay, no withdraw, no liquidation" (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). [5](#0-4) 

A single unprivileged account reaches this by `supply` + `borrow` (or `multiply`/`flash_position` leverage) to hold a whale book at high utilization, then letting `update_indexes` accrue — no privilege, no oracle manipulation, no leaked keys.

### Impact Explanation
Once the RAY value of scaled debt crosses `i128::MAX` (~1.7e38 raw, i.e. ~170× index growth on a ~1e27-scaled share base), accrual panics deterministically and forever. All supplier funds and unclaimed yield in that market are permanently frozen; borrowers cannot repay and liquidators cannot seize, so the bad-debt path is unreachable too. This is permanent freezing of user funds — qualifying impact.

### Likelihood Explanation
Requires a whale-scale position (on the order of 10⁹ whole tokens at 18 decimals in the test) and years of sustained high utilization on a steep curve, or a high-decimal low-price token where such raw quantities are cheap. The attacker funds the borrow themselves, so it is costly but not privileged; alternatively the cliff can be reached organically in any long-lived, high-utilization market, making it a latent protocol fragility rather than purely attacker-dependent. Medium likelihood, High-severity impact.

### Recommendation
Order the cap before the overflow: compute the accrual in a form that cannot overflow — e.g., detect `I256` overflow of `borrowed * new_index` and clamp the index to `i128::MAX / borrowed_scaled` (below `MAX_BORROW_INDEX_RAY`) instead of panicking; or scale shares down / rebase when a book approaches `i128::MAX / index`. At minimum, make `scaled_to_original`-style products saturating inside accrual so the index cap engages and the market stays operable rather than bricking.

### Proof of Concept
Already encoded in the repository: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`. Steps:
1. Create markets `BIG18` (18 decimals, XLM steep curve, 175% max rate) and `COL`.
2. `supply(BOB, BIG18, 1e9 * 10^18)`; `supply(ALICE, COL, …)`; `borrow(ALICE, BIG18, 98% of supply)`.
3. Advance time year-by-year calling `update_indexes`.
4. At ~170× index growth (still `< MAX_BORROW_INDEX_RAY`), `update_indexes` reverts `#33 MathOverflow`; every subsequent `withdraw`/`repay`/`liquidate` reverts the same way — permanent freeze confirmed by assertions at lines 348–356.

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
