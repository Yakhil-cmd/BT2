### Title
`StatusHandler#process` applies a foreign repository's GitHub status to any commit sharing the same SHA, corrupting `Stack#next_expected_commit_to_deploy` / `UndeployedCommit#expected_to_be_deployed?` and cross-tenant continuous-deployment gating - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with **no filter on the webhook's own `repository.full_name`**, unlike `PushHandler` and `CheckSuiteHandler`, which both scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). Because git commit SHA-1s are content-addressed and identical across forks/mirrors of the same history, a signal that is validly signed for the attacker's own organization can be replicated onto any other stack in the Shipit instance whose commit table contains that same SHA, including a victim's continuous-deployment-enabled stack.

### Finding Description
Binding claimed: `webhook_signing_org == stack_owning_org_for_every_commit_mutated`. This fails.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) only checks that the signature matches `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's own `repository.owner.login` [1](#0-0) [2](#0-1) . This proves only that the payload really came from the org named inside it — it says nothing about which Shipit `Commit`/`Stack` rows may be touched.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no `repository_name`/`stacks` scoping at all [3](#0-2) . Contrast with `PushHandler#process`, which filters via `stacks.not_archived.where(branch:)` [4](#0-3) , and `CheckSuiteHandler#process`, which filters via `stacks.where(branch:...)` before touching `stack.commits.where(sha:...)` [5](#0-4) . Both use the base class's `stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` [6](#0-5) . `StatusHandler` alone omits this scoping.
- `create_status_from_github!` writes a `Status` row unconditionally for the resolved `Commit` [7](#0-6) , which flips `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [8](#0-7) .
- `Stack#next_expected_commit_to_deploy` recomputes over `commits_to_deploy.find(&:deployable?)` [9](#0-8) , and `UndeployedCommit#expected_to_be_deployed?` uses that resolved commit's `id` as the cutoff for every older undeployed commit [10](#0-9) , which is what drives the `"expected to be deployed next"` UI badge [11](#0-10) .
- `Status#schedule_continuous_delivery` (via `after_commit`) delegates to `commit.schedule_continuous_delivery`, which is the mechanism that ultimately invokes `Stack#trigger_continuous_delivery` for `continuous_deployment`-enabled stacks [12](#0-11) [13](#0-12) , matching the previously-established `#10` finding that this same write path enqueues real deploys.

Attacker request: attacker owns/controls an organization/repo that Shipit legitimately tracks (their own stack, correctly configured with its own real `webhook_secret`). They fork or mirror the victim's public repository so a specific commit is byte-for-byte identical (same tree, parents, author/committer metadata, message) and therefore has the identical SHA-1 as a commit tracked under the victim's `continuous_deployment`-enabled stack. The attacker then triggers (via their own CI, a GitHub Action, or a personal token they hold on their *own* repo) a genuine GitHub `status` event with `state: success` on that SHA in their own repository. GitHub signs and delivers this webhook correctly for the attacker's own org. `verify_signature` passes (correct org, correct secret) [1](#0-0) , but `StatusHandler#process` then matches and mutates **every** `Commit` row in the entire database sharing that SHA, including the victim's, regardless of which repository the payload names [3](#0-2) .

Existing guards checked and why they don't help: `verify_signature` validates only the payload's claimed org against that org's secret, never against the `Commit`/`Stack` being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `branches`, etc.) accept and require exactly the fields used, none of which include a repository check; there is no `require_permission!`/`User#authorized?` call anywhere in the webhook path since it is unauthenticated by design (session-independent, secret-based). The only thing that could stop this is a `repository_name`/`stacks` scope such as the one `PushHandler`/`CheckSuiteHandler` already implement, and `StatusHandler` lacks it.

### Impact Explanation
A `Status(success)` row is written for a commit belonging to a repository/org that never authenticated it, and — if `stack.continuous_deployment` is enabled on the victim stack — this directly changes `Commit#deployable?`, `Stack#next_expected_commit_to_deploy`, `UndeployedCommit#expected_to_be_deployed?` (the CD progress display/gating targeted by this question), and can enqueue an unauthorized deploy via `Stack#trigger_continuous_delivery`. This is a "payload for one repository mutating another's stack/commit" and an "unauthorized deploy" per the Critical impact category. It is repeatable against any victim stack whose commit history intersects (via fork/mirror) with a repository the attacker controls, and the blast radius spans every tenant on the shared Shipit instance whose tracked repositories share commit ancestry with any attacker-controlled repository.

### Likelihood Explanation
Preconditions: the attacker must have a Shipit-tracked repository/org of their own with a legitimately configured webhook (a realistic bar for any public/self-service Shipit deployment), the victim stack must have `continuous_deployment` true (stated precondition), and the colliding SHA must exist verbatim in both the attacker's and victim's git history — trivially achieved for any public fork/mirror relationship, since GitHub preserves identical commit objects across forks. No secrets, sessions, or elevated GitHub permissions are needed beyond what the attacker already legitimately has on their own repository. This is a repeatable, low-cost, unauthenticated (from the victim's perspective) attack.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` already do: resolve commits only through `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) and restrict `Commit.where(sha: params.sha)` to `commits` belonging to those stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status payload for repo A must not mutate a commit belonging to repo B's stack" do
          victim_stack = shipit_stacks(:shipit) # continuous_deployment: true
          victim_commit = shipit_commits(:undeployed4) # belongs to victim_stack, shares a SHA with attacker repo

          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'branches' => [{ 'name' => victim_stack.branch }],
            'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
          }

          before_expected = victim_stack.next_expected_commit_to_deploy
          before_undeployed = UndeployedCommit.new(
            victim_commit, index: 1, next_expected_commit_to_deploy: before_expected
          ).expected_to_be_deployed?

          StatusHandler.call(attacker_payload)

          victim_commit.reload
          after_expected = victim_stack.next_expected_commit_to_deploy
          after_undeployed = UndeployedCommit.new(
            victim_commit, index: 1, next_expected_commit_to_deploy: after_expected
          ).expected_to_be_deployed?

          # Binding under test: signing org ('attacker-org') != victim_stack owning org,
          # yet victim state changed solely due to the forged cross-repo payload.
          refute_equal before_undeployed, after_undeployed,
            "expected_to_be_deployed? changed due to a payload naming a different repository"
        end
      end
    end
  end
end
```
