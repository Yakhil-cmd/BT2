### Title
Unbounded recursion over attacker-supplied address definition tree in `handleNewSharedAddress` before complexity limits are enforced - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` is invoked when a paired device sends a `new_shared_address` message, carrying an attacker-controlled `definition` (and `signers` map) [1](#0-0) . Before the definition is passed to `Definition.validateDefinition()` (the function that enforces `MAX_COMPLEXITY`/`MAX_OPS` limits, mirroring wasmd's `ValidateBasic`), the handler first calls `extractAddressPathsFromDefinition(body.definition)`, which recursively walks the entire `or`/`and`/`r of set`/`weighted and` tree with **no size or depth limit** [2](#0-1) . It then iterates over `body.signers` and the returned address map again with no bound [3](#0-2) .

### Finding Description
This is the same bug class flagged in the wasmd advisory: message types accept attacker-controlled address collections that are iterated/validated with no upper bound, causing disproportionate resource consumption relative to a small message.

In ocore, `Definition.validateDefinition()` does enforce `constants.MAX_COMPLEXITY` (100) and `constants.MAX_OPS` while evaluating the tree [4](#0-3) , but that check only happens *after* `extractAddressPathsFromDefinition` has already traversed the full, unbounded tree structure of `body.definition` supplied directly from the network message, and after the `for (var signing_path in body.signers)` and `for (let def_path in assocDefinitionAddresses)` loops have run over an attacker-controlled key set with no cap [5](#0-4) . An `'r of set'` node's `set` array or `'weighted and'` node's `set` array can contain an arbitrarily large number of elements/addresses since these arrays are only bounded later during `evaluate()` in `definition.js`, not during the pre-validation traversal performed by `extractAddressPathsFromDefinition`/`getMemberDeviceAddressesBySigningPaths`.

Because this message is processed on receipt from any paired device (a "paired device" counterparty in a wallet-sharing/multisig setup, which per the analog rules is a permissible unprivileged reach vector — it is not a "malicious node"/"malicious hub"/network-level actor but an application-layer message sender), an attacker who is paired with a victim's wallet (e.g., via an accepted correspondent pairing, common in exchange/wallet integrations) can send a single `new_shared_address` message with a deeply nested or extremely wide definition (many thousands of `r of set` entries or deeply nested `or`/`and` branches) and a correspondingly large `signers` object, forcing the victim's wallet process to perform large in-memory recursive traversal and object allocation before any complexity/op-count rejection occurs.

### Impact Explanation
This causes CPU/memory resource consumption in the victim wallet process disproportionate to the size of the network message, matching CWE-400 (Uncontrolled Resource Consumption) as in the wasmd advisory. This can degrade or stall wallet responsiveness for legitimate operations (composing transactions, processing incoming payments) while it is busy handling the oversized structure, which affects availability of the wallet/AA-fund custody path (not confidentiality/integrity), consistent with a Medium-severity resource-only class of issue.

### Likelihood Explanation
Likelihood is limited to the specific application-layer path where a device is already paired (correspondent) with the target — pairing is required before `device.sendMessageToDevice`/`handleMessageFromHub`-style device message processing accepts unsolicited `new_shared_address` messages, so this is reachable by any already-paired counterparty without further privilege, matching the "AA trigger sender / paired device" unprivileged-reach requirement in scope.

### Recommendation
Add explicit bounds before traversal in `wallet_defined_by_addresses.js`:
- Reject `body.definition` early if it is too deeply nested or contains array/set fields exceeding a sane limit (mirroring `constants.MAX_COMPLEXITY`/`MAX_OPS`), before calling `extractAddressPathsFromDefinition`.
- Cap `Object.keys(body.signers).length` to a small maximum (e.g., matching `MAX_AUTHORS_PER_UNIT` or a dedicated `MAX_SIGNERS_PER_SHARED_ADDRESS` constant) at the very top of `handleNewSharedAddress`, before any iteration.
- Apply the same complexity/op-count guard used in `definition.js`'s `evaluate()` inside `extractAddressPathsFromDefinition` and `getMemberDeviceAddressesBySigningPaths`, or simply run `validateDefinition`'s structural checks first and only proceed to path extraction on success.

### Proof of Concept
A paired attacker device sends over the device-messaging channel:
```
device.sendMessageToDevice(victim_device_address, "new_shared_address", {
    address: <chash of the huge definition>,
    definition: ["r of set", { required: 1, set: [ ["address","A1"], ["address","A2"], ... /* e.g. 100,000 entries or deeply nested or/and wrapping many such sets */ ] }],
    signers: { /* matching huge signers map, or minimal signers map to reach the loops in lines 391-405 */ }
});
```
This reaches `handleNewSharedAddress` [1](#0-0) , which calls `extractAddressPathsFromDefinition(body.definition)` [2](#0-1)  and iterates `body.signers`/`assocDefinitionAddresses` [3](#0-2)  — all before `validateAddressDefinition` → `Definition.validateDefinition` enforces `MAX_COMPLEXITY`/`MAX_OPS` [6](#0-5) [4](#0-3) .

**Note on confidence:** I could not fully trace the exact wiring of `device.sendMessageToDevice(..., "new_shared_address", ...)` to the inbound message dispatcher (e.g., in `device.js`/`wallet.js`) that ultimately calls `handleNewSharedAddress`, due to index/tool-call limits reached during investigation — the grep confirmed matches in `wallet.js` but I was unable to view the exact dispatch lines before the session ended. The core unbounded-traversal issue in `wallet_defined_by_addresses.js` itself, however, is confirmed directly from the code shown above.

function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
