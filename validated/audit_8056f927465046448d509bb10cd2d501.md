### Title
Authentication bypass via unset `webhook_secret` combined with organization/repository field desync in webhook processing allows forged CI status leading to unauthorized PR merges - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login`/`organization.login` in the untrusted payload, while the handlers that actually mutate state (create commits, set CI statuses, merge pull requests) resolve their target `Stack`/`Repository` from an entirely different, equally attacker-controlled payload field: `repository.full_name`. This is the same class of bug as the report: "authorization is checked against one state/identity, but the privileged action is executed against a different state/identity." If any organization configured in `Shipit.github` has no `webhook_secret` set — a state the shipped example configs treat as a normal, supported default — `verify_webhook_signature` unconditionally returns `true`, so an attacker only needs to know that organization's name to have arbitrary unsigned payloads accepted, while directing the actual write (e.g. a forged "status: success" webhook) at a completely unrelated stack belonging to a different, properly-secured organization.

### Finding Description
`WebhooksController#verify_signature` picks the app config purely from payload content: [1](#0-0) [2](#0-1) 

The actual signature check is delegated to `GithubApp#verify_webhook_signature`, which explicitly short-circuits to `true` when the selected organization has no configured secret: [3](#0-2) 

The setup docs and shipped example config treat a blank `webhook_secret` as a legitimate, common configuration (e.g. during setup, for orgs where the secret hasn't been created yet), not as a hard failure: [4](#0-3) 

Once "verified" (trivially, because that org has no secret), the event is dispatched to handlers. Handlers do **not** re-check that the org used for signature selection matches the repository being mutated — they independently resolve the target `Stack` from `repository.full_name`, a separate field of the same attacker-controlled JSON body: [5](#0-4) 

So the binding actually enforced is:
`verified-org(repository.owner.login or organization.login) == config-without-secret`
but the binding that should hold for a safe system is:
`verified-org == owner-of(repository.full_name being written to)`

These are never checked against each other, exactly mirroring the reported desync between the state used for authorization (`EPOCH_END-1` voting power) and the state actually acted upon (`distribute()` at `EPOCH_END+X`).

### Impact Explanation
An attacker who knows the name of any Shipit-configured GitHub organization that has no `webhook_secret` set can send a completely unauthenticated POST to `/webhooks` with:
- `organization.login` (or `repository.owner.login`) = the secret-less org, causing `verify_signature` to pass unconditionally, and
- `repository.full_name` = any other stack's repository already registered in this Shipit instance (belonging to a different, secured organization).

This lets the attacker forge, for example, a `status` webhook event marking an arbitrary commit `success` for a required CI context on a target stack. Because `MergeRequest#all_status_checks_passed?`/`StatusChecker` rely on `Commit#statuses` populated purely from webhook data, this forged status can satisfy the merge-queue's pending checks: [6](#0-5) 

`ProcessMergeRequestsJob` will then invoke `merge_request.merge!`, which calls the real GitHub API with the app's actual installation credentials to merge the pull request on GitHub — an unauthorized merge triggered without any legitimate authorization: [7](#0-6) [8](#0-7) 

This satisfies the "unauthorized deploy, rollback or merge" critical-impact category: the mutation happens against a repository the forged request never legitimately authenticated for.

### Likelihood Explanation
The precondition (one configured org without `webhook_secret`) is realistic and explicitly present in the shipped example/dev secrets file, and setup docs describe it as an acceptable state rather than a hard requirement. Multi-org Shipit deployments are an intended, documented feature (see `Shipit.github(organization:)`), so a mixed environment — one org fully configured, one still mid-setup with no secret — is plausible. No credentials, tokens, or GitHub session are required; only knowledge of a configured org's login name, which is often public.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub App/organization; fail closed (reject the request) instead of returning `true` when it is blank, in `GithubApp#verify_webhook_signature`.
- Bind signature verification and repository resolution to the same identity: after verifying the signature for organization `O`, assert that `repository.full_name`'s owner equals `O` before dispatching to any `Handler`, in `WebhooksController#verify_signature`/`create` or in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two orgs: `secured-org` (has `webhook_secret`) and `unsecured-org` (blank `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), where `secured-org/target-repo` has an active Stack with a pending `MergeRequest` waiting on CI context `ci/required`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": {"login": "unsecured-org"},
  "repository": {"full_name": "secured-org/target-repo", "owner": {"login": "unsecured-org"}},
  "sha": "<head sha of pending PR>",
  "state": "success",
  "context": "ci/required"
}
```
No `X-Hub-Signature` needed (or any arbitrary value) since `verify_webhook_signature` returns `true` because `unsecured-org` has no `webhook_secret`, per `lib/shipit/github_app.rb#L76-83`.
3. `WebhooksController#create` dispatches to `StatusHandler`, which creates a `Status` on `secured-org/target-repo`'s commit, satisfying `MergeRequest#all_status_checks_passed?`.
4. `ProcessMergeRequestsJob` runs and calls `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request(...)` — merging the PR on GitHub using the app's real installation credentials, without any legitimate signature ever having verified a request for `secured-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      merge_requests.each do |merge_request|
