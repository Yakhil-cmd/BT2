### Title
Skill-name collision detection uses exact string equality, allowing case/Unicode-normalization collisions on macOS/Windows to silently merge two skills' files into one directory - (File: internal/skills/discovery/collisions.go, internal/skills/installer/installer.go)

### Summary
`printFileTree` itself (`pkg/cmd/skills/install/install.go:1151`) is a read-only renderer that calls `os.ReadDir` on the already-installed directory; it performs no collision checks or writes and cannot be the enforcement point for a file-overwrite bug. [1](#0-0) 
The actual collision-detection logic that decides whether two skill names may be installed together lives in `discovery.FindNameCollisions` and `checkOverwrite`, and both compare `Skill.Name` values with plain Go string/map-key equality, not case-folded or Unicode-normalized comparison. [2](#0-1) [3](#0-2) 

### Finding Description
A published skills repository provides skill directory names such as `skills/config.yml/SKILL.md` and `skills/Config.yml/SKILL.md` (or NFC/NFD Unicode variants). `matchSkillConventions`/`validateName` derive `Skill.Name` directly from the path segment without any case-folding or Unicode normalization, so both names pass discovery as distinct skills. [4](#0-3) 

When the victim runs `gh skill install <repo> --all`, `selectSkillsWithSelector` calls `checkCollisions`, which calls `discovery.FindNameCollisions`. That function groups skills into a map keyed by the raw `Skill.Name` string, so `"config.yml"` and `"Config.yml"` land in different buckets and are never reported as colliding. [2](#0-1) 

`buildInstallPlans` then calls `checkOverwrite`, which uses `os.Stat(filepath.Join(targetDir, s.Name))` to decide if a skill is "existing" or "fresh." Because this check runs before any of the batch's directories are created, both `config.yml` and `Config.yml` are classified as "fresh" (neither exists yet) and both proceed to installation with no overwrite prompt. [3](#0-2) 

During the actual write phase, `installSkill` computes `skillDir := filepath.Join(baseDir, skill.Name)` and calls `os.MkdirAll` then writes files with `os.WriteFile` for each skill in the batch, in sequence. [5](#0-4) [6](#0-5) 

On the default case-insensitive/normalization-insensitive filesystems used on macOS (APFS default) and Windows (NTFS), `baseDir/config.yml` and `baseDir/Config.yml` (or NFC/NFD equivalents) resolve to the *same* on-disk directory. The second skill's `os.MkdirAll` silently succeeds against the already-created directory, and its files are written into the same location as the first skill - overwriting or intermixing SKILL.md/scripts from an attacker-controlled second skill entry into the directory the user believes belongs to the first, trusted skill, with **no overwrite confirmation at all**, because `checkOverwrite`'s pre-write `os.Stat` check never saw a pre-existing directory (both were "fresh" at check time). `printFileTree` merely renders whatever ended up on disk afterward, so a user inspecting the printed tree sees only the final merged/overwritten result, not two skills.

### Impact Explanation
This is an arbitrary file write/overwrite inside the intended skill directory without user consent or warning, enabling an attacker to smuggle malicious file content (fake `SKILL.md`, scripts referenced by hooks/startup) into a directory the victim believes was populated solely by the first, benign skill entry - a trust/collision-detection bypass matching "Arbitrary file write or overwrite outside the intended directory" impact class, though scoped to files *within* the already-intended skill install directory rather than outside it entirely.

### Likelihood Explanation
Requires only that an attacker publish a repository containing two skill directories whose names collide only under case-folding or Unicode NFC/NFD normalization, and that the victim run `gh skill install <repo> --all` (or otherwise multi-select both names) in a single invocation on macOS or Windows. No special privileges are needed beyond publishing content, matching the stated attacker model, but does depend on `validateName`'s exact pattern permitting mixed case/dotted names (not fully confirmed in this review) and requires the specific `--all`/multi-select batch flow rather than a single named install.

### Recommendation
Normalize `Skill.Name` (Unicode NFC) and case-fold it before using it as a map key in `FindNameCollisions`, and apply the same normalized comparison inside `checkOverwrite` and across all skills in a single install batch (not just against pre-existing on-disk state) so that any two names that would resolve to the same path on a case-insensitive/normalization-insensitive filesystem are rejected as a collision before any writes occur.

### Proof of Concept

1. Build a fake tree JSON with two skill blobs: `skills/config.yml/SKILL.md` and `skills/Config.yml/SKILL.md`.
2. Run `discovery.DiscoverSkillsWithOptions` and assert `FindNameCollisions` returns a non-empty collision list for these two names (currently it returns empty - proving the bypass).
3. Run `TestInstallRun` with `--all` selecting both skills against a `t.TempDir()` target on the test-runner's default filesystem; assert that only one skill's files exist afterward or that an error/prompt is raised (currently both writes succeed silently into the same directory, with the second skill's `SKILL.md` overwriting the first's).
4. Repeat with NFC vs NFD variants of the same skill name (e.g., "café" composed vs decomposed) to demonstrate the same silent-merge behavior on macOS-style normalization-insensitive lookups.

```go
func FindNameCollisions(skills []Skill) []NameCollision {
	byName := make(map[string][]Skill)
	for _, s := range skills {
		byName[s.Name] = append(byName[s.Name], s)
	}

	var collisions []NameCollision
	for name, group := range byName {
		if len(group) <= 1 {
			continue
		}
		names := make([]string, len(group))
		for i, s := range group {
			names[i] = s.DisplayName()
		}
		collisions = append(collisions, NameCollision{Name: name, DisplayNames: names})
	}
```
