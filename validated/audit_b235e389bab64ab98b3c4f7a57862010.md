### Title
Cross-stack/cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler`, amplified by organization-based signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) used to authenticate a `status` webhook based solely on `repository_owner`, which is derived from `params.dig('repository','owner','login')` or, if `repository` is absent, `params.dig('organization','login')` [1](#0-0) . `StatusHandler#process`, however, ignores `repository`/`organization` entirely and updates every `Commit` in the database whose `sha` matches the attacker-supplied `params.sha`, with no stack or repository scoping [2](#0-1) . Because the field used to pick the authenticating secret (`repository_owner`) and the field that actually determines which records are mutated (`sha`, matched globally) are independent, a webhook validly signed for one organization/stack can flip commit status — and therefore trigger merge-queue advancement — on a `Commit` belonging to a completely different stack.

### Finding Description
The broken binding: the code implicitly assumes
`organization_that_authenticated_the_request == organization_that_owns_the_mutated_commit`,
but no code enforces this equality.

- `verify_signature` computes `repository_owner` and uses it to fetch `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature(signature, raw_post)` on that app [3](#0-2) . `repository_owner` falls back to `organization.login` when `repository` is omitted from the payload [4](#0-3) .
- `GitHubApp#verify_webhook_signature` compares the HMAC using that org's configured `webhook_secret`; if no secret is configured for the selected org, it returns `true` unconditionally: `return true unless webhook_secret` [5](#0-4) .
- Once verification passes, `WebhooksController#create` dispatches to all handlers for the event without ever re-checking which repository/stack the payload actually targets [6](#0-5) .
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-stack lookup keyed only on `sha`, with zero reference to `repository_owner`, `organization`, or any stack/repository identifier [2](#0-1) .
- `create_status_from_github!` → `add_status` records the new status and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [7](#0-6) [8](#0-7) . On a stack with `merge_queue_enabled` true, a green head status advances the merge queue, and `merge!` on the queue proceeds.

Exploit flow: an attacker who legitimately controls (or is a contributor on) some organization/repository that is onboarded into the same multi-tenant Shipit instance — call it Org B, distinct from the victim's Org A stack — can send a `status` webhook whose signature is valid for Org B (either because Org B's `webhook_secret` is unset, making `verify_webhook_signature` trivially pass, or because the attacker can otherwise produce an event GitHub signs for Org B, e.g. via their own repo's status API). If a commit exists with the same `sha` in Org A's stack (a realistic condition for forks/shared upstream history, since `Commit.where(sha:)` matches identical git SHAs regardless of which stack synced them), the same forged `state`/`context`/`description` is applied to Org A's commit, potentially flipping it green and triggering `stack.schedule_merges` → merge-queue advancement on Org A's stack, whose secret never authenticated this request.

Existing guards do not close this gap: `verify_signature` only proves the request was signed by *some* configured organization's secret, not that the payload's target commit belongs to that organization's stack; `ExplicitParameters` in `StatusHandler` validates payload shape (`sha`, `state`, etc.) but performs no repository/stack authorization check [9](#0-8) .

### Impact Explanation
A payload authenticated for one repository/organization can mutate commit status state belonging to an entirely different stack, and on a `merge_queue_enabled` stack this can trigger `stack.schedule_merges`/`merge!`, resulting in an unauthorized merge decision driven by forged status data — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge." The blast radius spans all stacks sharing the same Shipit instance and any commit SHA collision across tenants (most realistically shared upstream/base commits between forks of the same public project).

### Likelihood Explanation
Exploitability is conditioned on: (1) a multi-tenant Shipit deployment where the attacker legitimately controls or can trigger status events for at least one onboarded organization whose secret they can satisfy (including the trivial case of an org with no `webhook_secret` configured), and (2) a `sha` collision between a commit the attacker can produce a status for and a commit already present in the victim's `merge_queue_enabled` stack. Condition (2) is realistic for forked/shared-history repositories but not guaranteed for arbitrary unrelated victims, making this a real but preconditioned cross-tenant flaw rather than a universally exploitable single-request bypass. Regardless, the core code defect — `StatusHandler` performing zero repository/stack scoping when applying status webhooks — is present unconditionally.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that queries by `sha` alone) to the repository that authenticated the request: resolve the target stack(s) via the verified `repository_owner`/`repository.full_name` and restrict `Commit.where(sha: params.sha)` to `commits joins(:stack).where(stack: { repository: authenticated_repo })` (or equivalent), rather than matching `sha` globally across all tenants.

3. Assert precondition equality being violated: `commit_a.stack.repository_owner != params.dig('organization','login')` yet the handler still touches `commit_a`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(params)` with `params = { sha: SHARED_SHA, state: 'success', context: 'ci', ... }` (simulating a payload authenticated only for Org B).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
