### Title
Unbounded `account_ids` in `changes`/`EXPERIMENTAL_changes` RPC causes per-request RocksDB scan amplification and resource exhaustion - (File: chain/jsonrpc/src/api/changes.rs)

### Summary
`RpcStateChangesInBlockByTypeRequest::parse` performs no bound check on the number of `account_ids` supplied in a `StateChangesRequestView` variant before dispatching to `ChainStore::get_state_changes`, which loops over every account id and performs a separate RocksDB lookup/prefix scan per entry. A single unauthenticated JSON-RPC caller can submit an array with an extremely large number of (even non-existent) account ids to force the node to perform a correspondingly large number of RocksDB operations in one synchronous request handler call.

### Finding Description
The parse path is:
`RpcStateChangesInBlockByTypeRequest::parse` [1](#0-0)  calls `Params::parse(value)`, which is just `serde_json::from_value(value)` with no length/size validation [2](#0-1) .

The resulting `StateChangesRequestView::AccountChanges { account_ids }` [3](#0-2)  is converted 1:1 into `StateChangesRequest` and passed to `ChainStore::get_state_changes`, which iterates `for account_id in account_ids` and, for each one, builds a `TrieKey`/`KeyForStateChanges` and performs a `find_exact_iter`/`find_iter` RocksDB scan (`chain/chain/src/store/mod.rs`, lines 690-741) [4](#0-3) . The other variants (`AllAccessKeyChanges`, `ContractCodeChanges`, `DataChanges`) do the same pattern with prefix scans (`find_iter`), which are more expensive than exact lookups [5](#0-4) .

The sharded-RPC path in `chain/jsonrpc/src/lib.rs` (`changes_in_block_by_type_sharded`, `extract_target_shards`, `filter_request_to_shard_group`) filters/splits `account_ids` by shard for scatter-gather, but does not impose any cap on the total count either [6](#0-5) [7](#0-6) . There is no evidence of an HTTP body-size limit or per-request account-count limit in the jsonrpc crate configuration that would reject an oversized `account_ids` array before it reaches the handler.

Because each `account_id` triggers a distinct RocksDB key lookup/scan (not merely a cheap in-memory filter), the total handler cost scales linearly (or worse, given RocksDB per-call overhead) with the size of the attacker-controlled `account_ids` array, and this cost is paid synchronously inside the view-client actor handling loop (`GetStateChanges` handler in `chain/client/src/view_client_actor.rs`) [8](#0-7) .

### Impact Explanation
This matches the "node panic or unbounded resource use" impact class for public RPC nodes: an unauthenticated caller can force a node to perform an unbounded number of RocksDB operations per single JSON-RPC request, consuming CPU and I/O and degrading availability of the RPC endpoint (and, since `GetStateChanges` is served by the shared `ViewClientActor`, potentially delaying other view-client-served RPC methods on the same node). This is scoped to RPC/view-client resource exhaustion, not to consensus, balance, or protocol-level state divergence.

### Likelihood Explanation
Feasibility is high and requires no privilege: any client with network access to a public RPC endpoint can send a single `changes` (or `EXPERIMENTAL_changes`) JSON-RPC request with a large `account_ids` array (e.g., 1,000,000 distinct strings) — this is a plain HTTP JSON-RPC call, not a transaction, and needs no signed keys or on-chain balance. It is trivially repeatable and can be automated/parallelized against a node.

### Recommendation
Enforce an explicit upper bound on the number of `account_ids` (and `keys`, for `SingleAccessKeyChanges`) accepted in `StateChangesRequestView` during `RpcStateChangesInBlockByTypeRequest::parse` (or in a shared validation step called from `changes_in_block_by_type`/`changes_in_block_by_type_sharded`), rejecting requests that exceed the limit with a clear `RpcStateChangesError`. Additionally, consider capping overall request payload size at the JSON-RPC transport layer as defense in depth.

### Proof of Concept
Integration test plan (extending the existing `test-loop-tests/src/tests/sharded_rpc.rs` `changes` tests):
1. Set up a single/two-shard test harness as in `test_rpc_changes_empty_account_ids_scatter_gather`.
2. Construct a `RpcStateChangesInBlockByTypeRequest` with `StateChangesRequestView::AccountChanges { account_ids }` where `account_ids` contains a large number (e.g. 100,000–1,000,000) of distinct, non-existent `AccountId` strings.
3. Send the request via `send_jsonrpc_request(Message::request("changes", params), false)` and measure wall-clock time and/or CPU usage of handling the request compared to a baseline single-account request.
4. Assert either that the response is quickly rejected (e.g., an `RpcStateChangesError` such as `TooManyAccounts`) once a fix is applied, or — prior to a fix — demonstrate that handling time grows roughly linearly (or worse) with `account_ids.len()` with no rejection, confirming the absence of any bound.

/// given shard group, returning a new sub-request for just those accounts.
fn filter_request_to_shard_group(
    request: &StateChangesRequestView,
    shard_group: &[ShardId],
    shard_layout: &ShardLayout,
) -> StateChangesRequestView {
    let shard_set: HashSet<&ShardId> = shard_group.iter().collect();
    let filter_accounts = |account_ids: &[AccountId]| -> Vec<AccountId> {
        account_ids
            .iter()
            .filter(|id| shard_set.contains(&shard_layout.account_id_to_shard_id(id)))
            .cloned()
            .collect()
    };

    match request {
        StateChangesRequestView::AccountChanges { account_ids } => {
            StateChangesRequestView::AccountChanges { account_ids: filter_accounts(account_ids) }
        }
        StateChangesRequestView::SingleAccessKeyChanges { keys } => {
            let filtered: Vec<_> = keys
                .iter()
                .filter(|k| shard_set.contains(&shard_layout.account_id_to_shard_id(&k.account_id)))
                .cloned()
                .collect();
            StateChangesRequestView::SingleAccessKeyChanges { keys: filtered }
        }
        StateChangesRequestView::AllAccessKeyChanges { account_ids } => {
            StateChangesRequestView::AllAccessKeyChanges {
                account_ids: filter_accounts(account_ids),
            }
        }
        StateChangesRequestView::ContractCodeChanges { account_ids } => {
            StateChangesRequestView::ContractCodeChanges {
                account_ids: filter_accounts(account_ids),
            }
        }
        StateChangesRequestView::DataChanges { account_ids, key_prefix } => {
            StateChangesRequestView::DataChanges {
                account_ids: filter_accounts(account_ids),
                key_prefix: key_prefix.clone(),
            }
        }
    }
}
