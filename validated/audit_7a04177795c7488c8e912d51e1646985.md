This report describes a pure MEV/front-running arbitrage against a Curve-based AMO rebalancer's slippage math — a class of finding the analysis method explicitly excludes ("pure front-running/economic attacks"). The polkadot-sdk equivalent, `pallet_asset_conversion`, enforces slippage bounds (`amount_out_min`/`amount_in_max`/`amount1_min`/`amount2_min`) atomically within a single extrinsic dispatch [1](#0-0) , unlike the multi-transaction `rebalanceUp`/`rebalanceDown` sequence in the report that a privileged bot executes across separate blocks, creating the sandwich window the PoC exploits. There's no analogous multi-step, cooldown-gated rebalancer pattern in the asset-conversion pallet or elsewhere that reproduces this exact fault (comparing pool ratio against a hardcoded target using a single-block slippage bound while state can be manipulated between dispatches) through a genuine FRAME/XCM boundary without assuming privileged rebalancer logic that doesn't exist in this codebase. Existing tests confirm slippage checks reject swaps exceeding bounds within a single atomic call [2](#0-1) , and liquidity operations similarly check `amount1_min`/`amount2_min` atomically [3](#0-2) , which eliminates the specific "check happens before a later, separately-triggerable mutation" root cause central to the reported bug class.
