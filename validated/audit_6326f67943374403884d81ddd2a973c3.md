## Finding: Confirmed

### Title
Unfiltered pull-request label names leak arbitrary env var keys (e.g. `GIT_CONFIG_GLOBAL`) into `Command#unbundled_env`, enabling fork-controlled git config injection - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every PR label name (uppercased) as an environment variable key with value `"true"`, with no allowlist, and this hash flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn`. An attacker who opens a fork PR and adds a label such as `git_config_global` sets `GIT_CONFIG_GLOBAL=true` in every git/deploy process spawned for that review stack.

### Finding Description
The broken binding: the set of environment variable **keys** reaching `PTY.spawn` should equal the union of `Stack#env` keys, `deploy_spec.machine_env` (shipit.yml-controlled, gated by `allow_all`) keys, and explicitly whitelisted deploy/task/rollback variable names (`EnvironmentVariables#permit`). In practice it also equals `pull_request.labels.map(&:upcase)`, an attacker-controlled, unbounded set.

Path:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]="true" })` — no key restriction at all. [1](#0-0) 
- Labels are persisted verbatim from the webhook payload by `LabelCapturingHandler#capture_labels`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) directly, then merges `deploy_spec.machine_env` and `@task.env`, with **no `EnvironmentVariables.permit` filtering** at this stage — that filtering (`filter_deploy_envs`/`filter_task_envs`) is only applied to user-submitted request params in controllers such as `DeploysController#deploy_params` and `TasksController#task_params`, not to `@stack.env`. [3](#0-2) [4](#0-3) 
- The resulting hash is passed as `env:` into `Command.new`, stored as `@env`, and merged straight into the process environment: `unbundled_env` does `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)`, then `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [5](#0-4) 

Existing guard `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`) enforces an allowlist only when explicitly called with `deploy_variables`/`rollback_variables`/`variables`; it is never invoked on `stack.env`/`ReviewStack#env`, so it does not close this gap. The `test/lib/shipit/deploy_commands_test.rb` and `test/models/shipit/review_stack_test.rb` tests explicitly confirm the intended (unsafe) behavior — `stack.env["WIP"]`/`env["BUG"]` come straight from labels — showing this passthrough is a deliberate feature, not a filtered/whitelisted one. [6](#0-5) 

Exploit flow: attacker opens a PR from their fork against a repo with `provisioning_behavior=allow_all` (so a `ReviewStack` is auto-provisioned) and adds a label named `git_config_global` (case-insensitive, upcased by the code) to their own PR. On the next deploy/task run for that review stack, the spawned process environment contains `GIT_CONFIG_GLOBAL=true`. Because the attacker also controls the checked-out branch content (same fork), they can commit a file literally named `true` in the working directory that is a valid git config defining a malicious `core.fsmonitor` or hook command; subsequent git invocations in that directory pick up `GIT_CONFIG_GLOBAL=true` (a relative path resolved against cwd) and execute the attacker's command.

### Impact Explanation
This is Critical: arbitrary command execution on the Shipit deploy host, triggered purely by an unprivileged fork-PR label plus fork-branch content, with no code review or maintainer action required beyond `allow_all` review-stack provisioning being enabled (a documented, common configuration for review apps). The blast radius is scoped to the repository/stack that has review stacks with `allow_all`, but grants the attacker the same execution context as legitimate deploy commands (host-level RCE), which can be used to exfiltrate `GITHUB_TOKEN` and other deploy-time secrets present in the same process environment.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior_allow_all?` (or another mode where the attacker's own label doesn't block/gate provisioning) — this is a legitimate, documented Shipit feature, not a hardened default. The attacker needs only a GitHub account able to fork and open a PR and to label it, which is unprivileged. Feasibility depends on being able to place a file named exactly `true` (or whatever value collides with the fixed `"true"` env value) at a path git will read as global config in the process cwd — this is straightforward since the attacker controls their fork's file tree. It is fully repeatable per repository with `allow_all` review stacks.

### Recommendation
Restrict `ReviewStack#env` to a fixed, safe allowlist of label-derived variable names (e.g., only names matching a `SHIPIT_LABEL_*` prefix, or run every label-derived key/value pair through `EnvironmentVariables.permit` against an explicit whitelist configured in `shipit.yml`), and additionally strip any known-dangerous env keys (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `LD_PRELOAD`, etc.) before merging into `Command`'s spawned environment, regardless of source.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend)
test "#env does not allow labels to set dangerous keys like GIT_CONFIG_GLOBAL" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_config_global"]

  env = stack.env

  # Broken binding under test: env["GIT_CONFIG_GLOBAL"] should be nil (fork-controlled key
  # must never reach the spawned process), but current code sets it to "true".
  assert_nil env["GIT_CONFIG_GLOBAL"], "fork-controlled label leaked GIT_CONFIG_GLOBAL into env"
end
```
and, tracing further into `Command`:
```ruby
# test/unit/command_test.rb (extend)
test "GIT_CONFIG_GLOBAL from label-derived env reaches unbundled_env passed to PTY.spawn" do
  command = Shipit::Command.new('true', env: { 'GIT_CONFIG_GLOBAL' => 'true' }, chdir: '.')
  assert_equal 'true', command.unbundled_env['GIT_CONFIG_GLOBAL']
end
```
Both assert the equality that should hold — `env["GIT_CONFIG_GLOBAL"] == nil` for label-derived stack env — fails against current code, confirming the vulnerability.
