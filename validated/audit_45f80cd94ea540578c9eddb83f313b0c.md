### Title
Missing duplicate-attestation check in `gh release verify-asset` allows silent selection of an unintended attestation - ([File: pkg/cmd/release/verify-asset/verify_asset.go])

### Summary
`gh release verify-asset` filters candidate attestations down by tag name and then by file digest, and unconditionally trusts `filteredAttestations[0]` as *the* attestation for the asset. The sibling command `gh release verify` performs the analogous computation but explicitly rejects the ambiguous case (`len(filteredAttestations) > 1`) as an error. `verify-asset` has no equivalent guard, so if more than one attestation matches both the tag and the file digest, the command silently verifies against whichever one happens to be first, discarding the rest without telling the user.

### Finding Description
This mirrors the root cause of the Illuminate `Redeemer` bug: one code path (`Redeemer.redeem`) correctly tracks/validates the accounting invariant (`holdings[u][m]`) before acting, while a sibling code path performs a destructive/authoritative action (`authBurn`) using an unchecked, potentially mismatched quantity. Here the "quantity that should be exactly one" is the number of attestations matching a given tag + digest, and the "destructive/authoritative action" is treating index `[0]` as *the* verified provenance record for the asset.

- `shared.FilterAttestationsByTag` and `shared.FilterAttestationsByFileDigest` (`pkg/cmd/release/shared/attestation.go:58-99`) return a slice, with no bound on its length.
- `verifyRun` in `pkg/cmd/release/verify/verify.go:157-169` explicitly checks:
```go
if len(filteredAttestations) == 0 {
    return fmt.Errorf("no attestations found for release %s in %s", tagName, baseRepo.RepoName())
}
if len(filteredAttestations) > 1 {
    return fmt.Errorf("duplicate attestations found for release %s in %s", tagName, baseRepo.RepoName())
}
``` [1](#0-0) 

- `verifyAssetRun` in `pkg/cmd/release/verify-asset/verify_asset.go:169-193` performs the same two filters but has no `> 1` check at all — it goes straight from the `== 0` check to `filteredAttestations[0]`:
```go
if len(filteredAttestations) == 0 {
    return fmt.Errorf("attestation for %s does not contain subject %s", tagName, fileDigest.DigestWithAlg())
}

verified, err := config.AttVerifier.VerifyAttestation(releaseRefDigest, filteredAttestations[0])
``` [2](#0-1) 

The comment in the code even acknowledges the assumption without enforcing it:
```go
// TODO: Allow this value to be set via a flag.
// The limit is set to 100 to ensure we fetch all attestations for a given SHA.
// While multiple attestations can exist for a single SHA,
// only one attestation is associated with each release tag.
``` [3](#0-2) 

That assumption ("only one attestation is associated with each release tag") is exactly what `verify.go` explicitly guards against violating, but `verify-asset.go` does not — an accounting/invariant check present in one function but silently dropped in the sibling function that performs the security-relevant action.

### Impact Explanation
`gh release verify-asset` exists to give users cryptographic assurance that a local file matches an asset published in a specific GitHub Release. If a repository (or an attacker able to publish releases/attestations to it, or if GitHub's own release-attestation pipeline ever emits more than one attestation for the same tag+digest for any reason) has multiple matching attestations, the command does not fail closed like `verify` does — it silently picks index `[0]` from an API response whose ordering is not contractually guaranteed by `GetByDigest`. A user relying on `verify-asset` succeeding as proof of "the" canonical attestation could be shown a success message backed by a non-deterministic pick among several attestations, rather than an explicit ambiguity error. This weakens the integrity guarantee the command is documented to provide ("This command checks that the asset you provide matches a valid attestation for the specified release... It ensures the asset's integrity"). [4](#0-3) 

### Likelihood Explanation
This requires attacker-published content in a repo/host under partial attacker control (e.g., a repo with release automation an attacker can influence, or additional release attestations added over time) to produce more than one attestation matching the same tag and file digest — plausible in CI setups that re-run release/attestation jobs, or if a malicious actor with release/attestation-write access publishes a second attestation. It does not require MITM, local access, or leaked tokens, and is reachable through the documented `gh release verify-asset` command.

### Recommendation
Add the same duplicate-attestation guard used in `verifyRun` to `verifyAssetRun`: after filtering by tag and file digest, return an explicit error (e.g., "duplicate attestations found for release %s asset %s") when `len(filteredAttestations) > 1`, instead of silently using `filteredAttestations[0]`.

### Proof of Concept
1. Set up a repo/release where the GitHub API's `GetByDigest` (via `config.AttClient.GetByDigest`) returns two attestations for the same release tag SHA that both, after `FilterAttestationsByTag` and `FilterAttestationsByFileDigest`, match the target tag and file digest (e.g., two attestations published for the same commit/tag with differing metadata but the same subject digest, which is possible since these filters only compare the `tag` predicate field and the SHA-256 subject digest, not attestation identity).
2. Run `gh release verify-asset <tag> ./asset`.
3. Observe that `verifyAssetRun` proceeds to call `config.AttVerifier.VerifyAttestation(releaseRefDigest, filteredAttestations[0])` and reports success without any indication that a second, distinct attestation for the same tag/digest was discarded — unlike `gh release verify`, which would fail with `"duplicate attestations found for release %s in %s"` in the analogous situation.
