### Title
Webhook signature verification keyed on attacker-controlled organization field diverges from the repository the handlers actually act on, enabling cross-tenant forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate a webhook's HMAC signature against by reading an attacker-supplied field from the *unauthenticated* JSON body (`repository.owner.login`, or `organization.login` as fallback), then verifies the raw body against that org's `webhook_secret`. Every downstream handler, however, determines which `Stack`/`Repository` to act on using a *different* field in the same body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together. In a multi-tenant Shipit deployment configured with `Shipit.github` per-organization secrets (`docs/setup.md`, "Using Multiple Github Applications"), this is the same class of bug as the reported `sy_program` issue: a value that is verified (the org whose secret produced a valid signature) is not the same value that is subsequently acted upon (the repository/org identified by `full_name`).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`verify_signature` computes `repository_owner` straight from the JSON body the attacker fully controls (nothing about this endpoint requires prior authentication — it is a raw, public POST endpoint that only relies on the HMAC as a trust boundary), then does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`Shipit.github(organization:)` looks up the app/secret keyed by that same attacker-supplied string in `secrets.github`, as shown by the multi-org support documented in `docs/setup.md` and exercised in `test/dummy/config/secrets_double_github_app.yml` / `lib/shipit.rb` (`github_app_config`): [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the raw JSON to all registered handlers: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from a *different* key in the same payload: [5](#0-4) 

`PushHandler`, which drives `GithubSyncJob` (fetching commits and appending them to a stack's commit history), is a concrete example of a handler relying purely on `repository_name`/`stacks`: [6](#0-5) 

There is no code anywhere that checks `repository.owner.login == repository.full_name.split('/').first` (or otherwise reconciles the two). The equality that should hold — "organization whose secret authenticated the request" == "organization/repository the handler subsequently writes to" — is never enforced.

### Impact Explanation
In a multi-tenant install (the officially supported configuration where `secrets.github` has one entry per GitHub organization, each with its own `webhook_secret`), any party that legitimately knows the webhook secret for *one* tenant organization (e.g., an org admin who configured that org's GitHub App/webhook integration with Shipit) can:
1. Set `repository.owner.login` (or `organization.login`) in a raw POST to `/webhooks` to their own organization's name, so `verify_signature` selects their own known secret and the HMAC check passes.
2. Set `repository.full_name` in the same payload to `victim-org/victim-repo`, which is what `Handler#stacks` and `#repository_name` actually resolve against.

This lets an attacker who is fully unprivileged with respect to the victim organization forge `push`, `status`, `check_suite`, and other webhook events against stacks belonging to a completely different, unrelated tenant — triggering `GithubSyncJob`, injecting fabricated commit statuses, or otherwise manipulating stack state that influences deploy/merge gating for a repository they have no legitimate access to. This is a cross-tenant/cross-repository write achieved purely by exploiting a verification/action mismatch, matching the "cross-repository writes" and "unauthorized deploy/merge" impact classes.

### Likelihood Explanation
Exploitation only requires: (a) the target Shipit instance be configured for more than one GitHub organization (a documented, supported configuration, not a misconfiguration), and (b) the attacker legitimately controls/knows the webhook secret for any one of the configured organizations. No GitHub-side spoofing is needed because the `/webhooks` endpoint is a raw, unauthenticated HTTP POST target — the attacker fully controls both the JSON body and headers sent to it, they need only compute a correct HMAC using a secret they already know. This is a straightforward mismatch that a single crafted request set can exploit; likelihood is High wherever multi-org mode is used.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the same field the handlers use to resolve the acted-upon repository (`repository.full_name`, not `repository.owner.login`/`organization.login`), or, after a successful signature check, re-derive `repository_owner` from the *same* field the handler will use and reject the request if the two disagree. More robustly, iterate/verify against the secret belonging to the org that actually owns the resolved `Repository`/`Stack` record instead of trusting attacker-supplied lookup keys pre-verification.

### Proof of Concept
Preconditions: Shipit configured with multi-org github secrets, e.g. `OrgA` (victim, tracked stack `OrgA/victim-repo`) and `OrgAttacker` (attacker controls, knows `webhook_secret`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgAttacker_webhook_secret, body)>
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgA/victim-repo"
  }
}
```
`verify_signature` looks up `Shipit.github(organization: "OrgAttacker")`, verifies the HMAC with the secret the attacker knows, and passes. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("OrgA/victim-repo")` and enqueues `GithubSyncJob` for the victim's stack — a forged event accepted for an organization the attacker never authenticated against.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
