### Title
Unprivileged PR label names inject arbitrary env vars (including `GIT_CONFIG_GLOBAL`) into git subprocess environment - ([File: lib/shipit/stack_commands.rb](lib/shipit/stack_commands.rb))

### Summary
`ReviewStack#env` merges every pull-request label name, uppercased, directly into the environment hash used by git operations with no allowlist, unlike the `EnvironmentVariables#permit` allowlist enforced for deploy/task/rollback params. Labels are attacker-controlled (any user who can label their own PR) and are persisted verbatim by `LabelCapturingHandler#capture_labels`, then flow unfiltered into `StackCommands#git_clone`/`fetch`/`fetch_commit` and ultimately into `PTY.spawn`'s environment.

### Finding Description
The broken binding: `Command#env` passed to `PTY.spawn` should equal `EnvironmentVariables.with(source_env).permit(allowlisted_variable_definitions)` for every subprocess Shipit runs, but for git operations on review stacks it instead equals `Shipit.env.merge(...).merge(@stack.env)` with **no `permit` call at all**.

- `ReviewStack#env` merges `super` with `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }`, with no key allowlist: [1](#0-0) 
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body onto `pull_request.labels`: [2](#0-1) 
- `StackCommands#env` merges this unfiltered label-derived hash into the env used for all git operations: [3](#0-2) 
- `fetch_commit`/`fetch` pass this `env:` straight to `git_clone`, which builds the `git clone ... --recursive` command: [4](#0-3) [5](#0-4) 
- `Command#unbundled_env` merges `@env.stringify_keys` (the tainted hash) into the process environment handed to `PTY.spawn`: [6](#0-5) [7](#0-6) 

Contrast this with the guarded paths: `TaskDefinition#filter_envs`, `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` all call `EnvironmentVariables.with(env).permit(variable_definitions)`, which raises `NotPermitted` for any key not in the shipit.yml-defined allowlist: [8](#0-7) [9](#0-8) [10](#0-9) . No equivalent `permit` call exists anywhere between `ReviewStack#env`/`StackCommands#env` and the `Command`/`PTY.spawn` boundary, so **any** uppercased label name becomes an environment variable in the git subprocess, confirmed by the existing test asserting `env["WIP"]`/`env["BUG"]` are set from labels with no filtering: [11](#0-10) .

Attack: an unprivileged fork contributor opens a PR against a repo with review stacks enabled (any `provisioning_behavior`, including `prevent_with_label`, since label capture runs on `opened`/`labeled`/`unlabeled`/`reopened` regardless of whether the stack is archived, per `capture_labels?`: [12](#0-11) ) and applies a label literally named `git_config_global` (case-insensitive since `upcase` is applied). GitHub emits a `pull_request` webhook that Shipit's `LabelCapturingHandler` processes without any additional signature-independent filtering of the label string, storing it verbatim. The next time Shipit runs `fetch`/`fetch_commit`/`git_clone` for that review stack, `GIT_CONFIG_GLOBAL=true` (or any attacker-chosen uppercase value, subject to label-name character constraints) is present in the git subprocess's environment.

### Impact Explanation
This demonstrates that an unprivileged GitHub actor can inject **arbitrary environment variable names** (as uppercased strings, value fixed to `"true"`) into every git subprocess executed for their review stack — a clear violation of the "no fork-controllable variable" invariant, and a real gap compared to the deploy/task/rollback env allowlists. However, achieving full RCE via `GIT_CONFIG_GLOBAL` additionally requires an attacker-controlled file to exist at whatever path the label maps to (the value is hardcoded to the string `"true"` by `ReviewStack#env`, not an attacker-chosen path), and this repo's data model does not let the attacker set the value, only the key. Because `EnvironmentVariables#permit` is bypassed rather than defeated for a specific dangerous key, and the value component is fixed, this is best classified as an environment-variable-injection weakness in the git-subprocess path (a real allowlist bypass with no matching guard) rather than a fully demonstrated Critical RCE chain within this engine's own code — the file-content half of the chain is outside what this codebase controls.

### Likelihood Explanation
Low cost, fully repeatable: any user who can open a PR and add a label to it (including on their own fork PR, since GitHub allows applying existing repo labels to PRs from forks in many configurations, or on same-repo PRs) can trigger this on every `fetch`/`clone` for their stack. No Shipit credentials, GitHub App keys, or maintainer status are required. It requires the target repository to have review stacks enabled (`review_stacks_enabled`), which is a normal, common configuration, not a privileged one.

### Recommendation
Do not merge unfiltered pull-request labels into the environment passed to git subprocesses. Either (a) prefix label-derived env keys with a fixed, git/Shipit-reserved-name-incompatible namespace that cannot collide with sensitive variables like `GIT_*`/`PATH`/`LD_PRELOAD`, or (b) run label-derived env values through an explicit allowlist/denylist (e.g., reject any key matching `^GIT_` or matching Shipit's own reserved variable names) before merging in `ReviewStack#env`, or (c) apply `EnvironmentVariables#permit` against a fixed safe-name pattern before the merge in `StackCommands#env`/`Commands#git`.

### Proof of Concept
```ruby
# test/lib/shipit/stack_commands_test.rb (new/extended)
test "[prevent_with_label] a PR label can inject GIT_CONFIG_GLOBAL into git clone's env" do
  stack = shipit_stacks(:review_stack)
  repository = stack.repository
  configure_provisioning_behavior(repository:, behavior: :prevent_with_label, label: "no-stack")
  stack.pull_request.update!(labels: ["git_config_global"])

  stack.git_path.stubs(:exist?).returns(false)
  command = StackCommands.new(stack).fetch

  # Binding under test: env passed to the git clone Command must equal the
  # allowlisted env only. It does not: the label-derived key leaks through.
  assert_equal "true", command.env["GIT_CONFIG_GLOBAL"],
    "unprivileged PR label controlled the git subprocess's GIT_CONFIG_GLOBAL"
end
```
This proves the divergence: `command.env["GIT_CONFIG_GLOBAL"]` (attacker-influenced) should not exist, but does, because no `EnvironmentVariables#permit` call guards `StackCommands#env`/`ReviewStack#env` before it reaches `Command#unbundled_env` and `PTY.spawn`.
