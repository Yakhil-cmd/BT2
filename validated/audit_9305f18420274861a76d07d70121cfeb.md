### Title
Fail-open exception handling in hookify's `PreToolUse`/`Stop` hook executors allows unsanitized rule-evaluation errors to silently bypass block rules - (File: `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/hooks/stop.py`)

### Summary
The Wido report's root cause is a missing sanitization/validation check on the output of a sensitive operation (the swapped asset type), whose absence causes the system to silently fall through to an unsafe default (funds left unprotected) instead of failing safe. The `hookify` plugin's hook executors exhibit the same class of defect: they never validate that rule evaluation actually completed correctly before deciding to allow a tool call, and any exception during rule loading/evaluation is unconditionally treated as "allow," with `sys.exit(0)` forced in a `finally` block.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` reads the hook JSON from stdin, loads user-authored `.claude/hookify.*.local.md` rules, and evaluates them with `RuleEngine.evaluate_rules` [1](#0-0) . If any exception occurs anywhere in this pipeline (malformed frontmatter causing a `TypeError`/`KeyError` inside `Rule.from_dict`, a bad regex in a condition, an unexpected exception in `_extract_field`, etc.), the `except Exception` branch emits only a `systemMessage` and the `finally: sys.exit(0)` guarantees the hook always reports success/allow, never `permissionDecision: "deny"` [2](#0-1) . The same fail-open pattern is duplicated in `plugins/hookify/hooks/stop.py` for the `Stop` event [3](#0-2) .

Crucially, the engine's blocking decision itself is derived from `hook_event = input_data.get('hook_event_name', '')`, and the resulting `hookSpecificOutput.permissionDecision: "deny"` is only produced when execution reaches that specific branch of `evaluate_rules` cleanly [4](#0-3) . There is no independent check that verifies "rules were actually evaluated and none errored" before deciding to allow the tool call — exactly analogous to the Wido contract never checking that the swap's output asset matched the expected asset before treating the transaction as successful. In both cases, an exceptional/unexpected code path silently degrades to the "safe by default" assumption without being verified, and a user relying on the block rule (e.g., "block-destructive-ops" from the plugin's own README example [5](#0-4) ) can have a destructive command execute unblocked whenever the rule engine throws (e.g. via a crafted `.claude/hookify.*.local.md` rule file, or a condition whose field/tool combination is unhandled and raises rather than returning `None` in some edge case).

### Impact Explanation
Any user or automated workflow that relies on hookify's `PreToolUse`/`Stop` rules as an enforcement/approval gate for dangerous Bash commands or file writes can have that gate silently disabled by any runtime error in rule parsing/evaluation, without any warning beyond an easily-missed `systemMessage`. This is a genuine "hook bypass" trust-boundary issue: a security control that is supposed to deny dangerous tool calls instead defaults to allow on failure, letting an unprivileged prompt-injected or malicious rule file (or malformed configuration) neutralize the block silently — the CLI equivalent of Alice's mis-swapped tokens being silently accepted instead of the transaction reverting.

### Likelihood Explanation
Likelihood is moderate: hookify is an optional third-party plugin (not the core Claude Code engine), and the fail-open behavior is explicitly documented/intentional ("ALWAYS exit 0 - never block operations due to hook errors") rather than an oversight, which lowers exploitability expectations for users who read the code. However, the failure mode is easy to trigger unintentionally (any malformed frontmatter or edge-case exception) and the plugin's own README advertises it for `block-destructive-ops` style protection, so users can reasonably believe they have an enforced block when in fact any parsing exception silently disables it.

### Recommendation
Change the exception-handling policy in `plugins/hookify/hooks/pretooluse.py` and `plugins/hookify/hooks/stop.py` so that failures during rule loading/evaluation for rules with `action: block` result in a safe failure (e.g., `permissionDecision: "ask"` or `"deny"` with a clear error message) rather than defaulting to allow. At minimum, surface loud, non-suppressible warnings (not just `systemMessage`) so users are aware their block rules were not evaluated, and add validation/self-tests in `RuleEngine`/`config_loader` to catch malformed rule files before they can throw during evaluation.

### Proof of Concept
1. Author a rule file `.claude/hookify.block-rm.local.md` with `action: block`, `event: bash`, and a condition matching `rm -rf` (as in the plugin's own example) [5](#0-4) .
2. Introduce a runtime exception during evaluation — e.g., a second local rule file with a condition whose `pattern` is an invalid/pathological regex that raises outside the guarded `re.error` handling in `_regex_match`, or any malformed frontmatter that raises a `TypeError` inside `Rule.from_dict` when parsed by `load_rule_file`.
3. Run a `Bash` tool call containing `rm -rf /important/path`. Because the exception occurs inside `RuleEngine.evaluate_rules`, `pretooluse.py`'s `except Exception` branch fires, printing only a `systemMessage`, and `finally: sys.exit(0)` returns exit code 0 with no `permissionDecision: "deny"` [2](#0-1) .
4. Result: the destructive command is not blocked despite the user having configured an explicit block rule for it, confirming the fail-open bypass.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
