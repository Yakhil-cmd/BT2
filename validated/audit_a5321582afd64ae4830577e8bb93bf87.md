### Title
Unchecked `transfer` results in `claim_child_bounty`/`claim_bounty` let payout state be finalized even when the payout fails, permanently freezing the funds - ([File: substrate/frame/child-bounties/src/lib.rs], [File: substrate/frame/bounties/src/lib.rs])

### Summary
`pallet-child-bounties::claim_child_bounty` (and the structurally identical `pallet-bounties::claim_bounty`) call `T::Currency::transfer(...)` for the curator-fee and beneficiary payouts but only wrap the `Result` in `debug_assert!`, never propagating the error. `debug_assert!` compiles to a no-op in a release build (the normal build used by production runtimes), so in production a failed transfer is silently ignored: the code still deletes the `ChildBounty`/`Bounty` storage entry, decrements the active-count, and emits a `Claimed`/`BountyClaimed` event as if the payout succeeded. The funds that failed to move stay in the bounty's derived, keyless `child_bounty_account_id`/`bounty_account_id`, which becomes permanently unreachable once the corresponding storage record is removed. This mirrors the reported Cooler bug class: a value-transfer's success is never checked, so state that should only be committed on a successful transfer is committed unconditionally.

### Finding Description
In `claim_child_bounty`: [1](#0-0) 
the fee and payout transfers are executed and their results discarded via `debug_assert!`, then unconditionally followed by event emission, count decrement, description removal, and removal of the `ChildBounty` record: [2](#0-1) 

The exact same pattern exists in the parent pallet's `claim_bounty`: [3](#0-2) 

Both derive a pallet-controlled, keyless sub-account to hold the money (`child_bounty_account_id` / `bounty_account_id`), and once the bounty record is deleted there is no dispatchable that can revisit that specific bounty's derived account to retry payment — the funds are stranded.

A concrete way the underlying `Currency::transfer` fails in production is the Existential Deposit rule: if the destination account (curator or beneficiary) has never held a balance and the amount being sent is below `ExistentialDeposit`, `pallet-balances`'s deposit logic returns an error (`TokenError::BelowMinimum` / `ExistentialDeposit`) instead of creating a dust account. This is fully attacker-reachable because:
- Any account that becomes a child-bounty curator (via the normal `propose_curator`/`accept_curator` flow, open to any signed account once selected by the parent curator) freely chooses the child-bounty `fee` when proposing curatorship, and freely chooses the `beneficiary` address in `award_child_bounty`.
- By setting `fee` close to `value` (or, symmetrically, very small), either the curator-fee transfer or the beneficiary-payout transfer can be made to compute an amount below `ExistentialDeposit`, and the beneficiary/curator address can simply be a never-funded account.
- No sudo, governance, or validator privilege is required — this is normal, permitted use of the public `add_child_bounty` → `propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty` extrinsic sequence, all reachable by ordinary signed accounts.

This class of bug was already recognized and fixed for `pallet-broker::do_claim_revenue`, whose current code propagates the transfer error with `?` and has a dedicated regression test (`claim_revenue_reverts_when_pot_cannot_pay`) confirming the storage change reverts and `TokenError::FundsUnavailable` is surfaced: [4](#0-3) [5](#0-4) 

`pallet-bounties`/`pallet-child-bounties` were not updated with the same fix and still rely on `debug_assert!`, which offers no protection in a release build.

### Impact Explanation
When the transfer fails, the code still proceeds to (a) emit an event claiming the payout amount was paid, (b) permanently delete the bounty/child-bounty record, and (c) decrement bookkeeping counters. The actual tokens remain in the pallet-derived sub-account, which after record deletion has no owner reference and no dispatchable path to be reclaimed — this is an irreversible freezing of user/treasury funds, matching the "irreversible freezing" impact class called out as high-severity in the analog-scan criteria. It also creates a state-integrity break: on-chain events/state assert a payout happened that never did.

### Likelihood Explanation
The trigger condition (destination account below Existential Deposit on first deposit) is a standard, well-known Substrate balances behavior, not a hypothetical edge case. It is deterministically reachable by any parent curator picking a small `fee`/`payout` split and a fresh destination address — no governance, no validator collusion, no privileged key required, only ordinary use of the public bounty extrinsics.

### Recommendation
Propagate the `Result` from both `T::Currency::transfer` calls with `?` (as already done in `pallet-broker::do_claim_revenue`) inside the `try_mutate_exists` closure for both `claim_child_bounty` and `claim_bounty`, so a failed payout reverts the storage mutation (record kept, counts unchanged) and the claim can be retried once the pot/preconditions are fixed, instead of silently discarding the transfer outcome via `debug_assert!`.

### Proof of Concept
No PoC could be executed in this environment (no code execution/terminal access). The reasoning above is a static analysis of the exact `debug_assert!`-guarded transfer calls at `substrate/frame/child-bounties/src/lib.rs:726-744` and `substrate/frame/bounties/src/lib.rs:820-826`, contrasted with the corrected, error-propagating pattern already merged for `pallet-broker` (`substrate/frame/broker/src/dispatchable_impls.rs:461-464`, validated by the existing test `claim_revenue_reverts_when_pot_cannot_pay` at `substrate/frame/broker/src/tests.rs:3363-3409`). A concrete reproduction would require a local FRAME test harness for `pallet-child-bounties` that: sets `fee`/`value` so the beneficiary payout is below `ExistentialDeposit`, uses a beneficiary account with zero prior balance, calls `claim_child_bounty`, and observes (in a release-mode/no-`debug_assertions` build) that the `ChildBounty` entry is removed and a `Claimed` event is emitted while the beneficiary's balance remains zero and the child-bounty account retains the stranded funds.

/// A claim removes the contribution and reduces the stored payouts before it pays the payee.
/// If the payment fails, all of these changes must revert. If they do not, the payee keeps no
/// claim and receives no money, and a later attempt reports `UnknownContribution`.
#[test]
fn claim_revenue_reverts_when_pot_cannot_pay() {
	TestExt::new().endow(1, 1000).execute_with(|| {
		// Give account 2 a claim on pool revenue: reserve a pool core, sell a region to
		// account 1, and pool that region with account 2 as the payee.
		let item = ScheduleItem { assignment: Pool, mask: CoreMask::complete() };
		assert_ok!(Broker::do_reserve(Schedule::truncate_from(vec![item])));
		assert_ok!(Broker::do_start_sales(100, 2));
		advance_to(2);
		let region = Broker::do_purchase(1, u64::max_value()).unwrap();
		assert_ok!(Broker::do_pool(region, None, 2, Final));

		// Account 1 buys and spends credit. This sends revenue to the pot, where 4 units
		// belong to account 2 and stay there until it claims them.
		assert_ok!(Broker::do_purchase_credit(1, 20, 1));
		advance_to(8);
		assert_ok!(TestCoretimeProvider::spend_instantaneous(1, 10));
		advance_to(11);
		assert_eq!(pot(), 4);

		// Empty the pot, so the payout to the payee cannot complete.
		burn_from_pot(pot());
		assert_eq!(pot(), 0);

		// Call the extrinsic. It reverts the storage changes when the payout fails.
		// A direct call to `do_claim_revenue` does not revert them.
		let contribution_before = InstaPoolContribution::<Test>::get(region);
		let history_before: Vec<_> = InstaPoolHistory::<Test>::iter().collect();

		// The claim must fail, and it must leave the claim of account 2 in storage.
		assert_err!(
			Broker::claim_revenue(RuntimeOrigin::signed(2), region, 100),
			TokenError::FundsUnavailable
		);

		assert_eq!(balance(2), 0);
		assert_eq!(InstaPoolContribution::<Test>::get(region), contribution_before);
		assert_eq!(InstaPoolHistory::<Test>::iter().collect::<Vec<_>>(), history_before);

		// The claim stays valid. Account 2 receives the full amount after the pot holds
		// funds again.
		mint_to_pot(4);
		assert_ok!(Broker::claim_revenue(RuntimeOrigin::signed(2), region, 100));
		assert_eq!(balance(2), 4);
		assert_eq!(pot(), 0);
	});
}
