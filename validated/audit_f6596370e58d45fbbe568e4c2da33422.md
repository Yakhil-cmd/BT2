### Title
Unauthenticated read of stack update broadcasts via `mount Pubsubstub::StreamAction.new, at: '/events'` bypassing `force_github_authentication` - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack app at `/events` in `Shipit::Engine.routes.draw`, so it never passes through `Shipit::ShipitController`/`Shipit::Authentication#force_github_authentication`. Any unauthenticated request to `GET /events?channel=stack.<id>` subscribes to that stack's live pubsub broadcasts. However, based on the code actually reachable in this engine, the only payload ever published through `Pubsubstub.publish` is the stack "update" event, containing just `id` and `updated_at` — not task output or `GITHUB_TOKEN`-tainted data.

### Finding Description
The broken binding: every other read of stack/task data requires `current_user.authorized?` to be true after `force_github_authentication` (enforced in `Shipit::Authentication#force_github_authentication`, [1](#0-0) ), included via `Shipit::ShipitController` ( [2](#0-1) ). The mounted `Pubsubstub::StreamAction` is not a subclass of `Shipit::ShipitController` — it is mounted as a raw Rack app in `config/routes.rb` ( [3](#0-2) ) — so no `before_action` runs before it services `GET /events?channel=...`.

Tracing what is actually published on that pubsub bus: the only call site found is `Shipit::Stack#broadcast_update`, which publishes `{ id:, updated_at: }.to_json` on channel `"stack.#{id}"` after every stack update ( [4](#0-3) ). There is no `Pubsubstub.publish` call anywhere in `Shipit::Task` or related task/output code; `Task#chunk_output`, `Task#write`, and `Task#tail_output` all read/write Redis directly and are exposed only through the authenticated `tasks#tail` / `api/outputs#show` HTTP endpoints ( [5](#0-4) ), not through the `/events` pubsub channel. Task live output in the browser is polled via `next_chunks_url`/`tail_output` HTTP calls, not SSE ( [6](#0-5) ).

So the premise that `/events` "delivers task output/command output data possibly containing `GITHUB_TOKEN`" is not supported by any reachable code path in this engine. The confirmed leak is limited to the stack-update event payload: numeric `id` (already known/guessed by the attacker to construct the channel name) and `updated_at` timestamp.

### Impact Explanation
An attacker who guesses/enumerates a stack id (stack ids are sequential integers, trivially enumerable) can call `GET /events?channel=stack.<id>` with no session, and receive push notifications each time that stack record is updated, exposing only `id` and `updated_at`. This is unauthenticated read of a small piece of stack state, but it does not expose task output, command output, or `GITHUB_TOKEN`/secrets, and does not allow escalation, mutation, or credential exfiltration. It is repeatable against arbitrary stacks (any guessable numeric id), but the blast radius is limited to leaking "a stack changed at time T", which is materially lower impact than the "task streams or deploy output" / credential-exfiltration scenario the question describes.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host and knowledge/guessing of a stack id (trivial, since ids are small sequential integers). Attacker cost is a single unauthenticated HTTP GET. Feasible and repeatable, but the disclosed data has minimal sensitivity.

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated. Wrap it behind a small controller/rack middleware that enforces `force_github_authentication`/`authorized?` and validates that the requested `channel` corresponds to a stack/task the current user is permitted to view (e.g., check `stack_id` derived from the channel name against `current_user`'s authorization) before allowing the subscription.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create a `Shipit::Stack` fixture with known `id`.
2. Without setting any session (`session[:user_id]` unset), issue `get "/events", params: { channel: "stack.#{stack.id}" }`.
3. Assert response is not `403`/redirect-to-login (i.e., no `force_github_authentication` ran) — proving the auth bypass.
4. In a separate thread/step, trigger `stack.touch` (or an update) to invoke `broadcast_update`, and assert the SSE body received by the unauthenticated request contains `{"id":<stack.id>,"updated_at":...}`.
5. Additionally assert (to bound the impact) that no `Pubsubstub.publish` call exists for `Shipit::Task`/output content by grepping `app/models/shipit/task.rb` and confirming the SSE stream never contains `chunk_output`/Redis `output_key` content — documenting that the "task output/GITHUB_TOKEN" impact claimed in the original question is unsubstantiated, while the lower-severity stack-metadata leak is confirmed.

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else

      end
