### Title
Missing `return` after private-payment hash-calculation error causes double processing/double callback invocation - ([File: network.js])

### Summary
In `network.js`, the `validateAndSave` closure inside `handleSavedPrivatePayments()` computes `json_payload_hash` inside a `try/catch` block. When the hash calculation throws, the `catch` branch logs the error, notifies the peer, and calls `deleteHandledPrivateChain(..., cb)` — but it does **not** `return`. Execution falls through to the code after the `catch` block, which builds `key` using the now-`undefined` `json_payload_hash` and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose own `ifOk`/`ifError` callbacks *also* call `deleteHandledPrivateChain(..., cb)`. This mirrors the RDMA/siw CVE pattern: an error path that fails to short-circuit before reusing/dereferencing state that was only valid on the success path, leading to inconsistent/duplicate processing of attacker-influenced input. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments()` reprocesses private payment chains that were previously queued (received from a hub or peer, including as part of normal wallet-to-wallet private payment forwarding). For each row it defines:

```javascript
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
``` [2](#0-1) 

The catch handler is not the terminal action of the function — unlike the sibling `ifError`/`ifOk` branches later in the same function, which correctly stop after calling `deleteHandledPrivateChain(..., cb)`. Because there is no `return` (or `else`) after the `catch` block:
1. `json_payload_hash` remains `undefined`, and the `key` string used for `eventBus` de-duplication (`'private_payment_validated-...-undefined-...'`) is computed from a value that was never successfully produced.
2. The function proceeds to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on payload data that has already been judged unhashable/invalid, i.e. work continues on a private-payment element whose error path has already fired.
3. `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` from the `catch` block, and the (near-certain) `ifOk`/`ifError` callback from `validateAndSavePrivatePaymentChain`, both eventually invoke `cb` for the same `async.each` iteration — i.e. `cb` for that row can be called twice.

This exact bug class — "an error handler that does not return and lets execution fall through into code that dereferences/reuses state which is now invalid" — is the same root cause described in the CVE: `siw_get_hdr()`'s early error path let `qp->rx_fpdu` be used downstream without being properly finalized/guarded.

`handleSavedPrivatePayments` is reachable purely by delivering private payment chain data through the normal wallet private-payment flow: `network.handleOnlinePrivatePayment` queues payloads into `unhandled_private_payments` even for malformed/rejected-later payloads (`savePrivatePayment`), and `handleSavedPrivatePayments` is invoked afterward to reprocess them, including on `new_my_transactions`/history-download completion events. A payment counterparty (or paired device forwarding a chain) fully controls the shape of `arrPrivateElements[0].payload`, and can craft a payload whose JSON/object-hash calculation throws (e.g., a payload containing values that `object_hash.getBase64Hash` cannot canonicalize/serialize, such as unsupported types nested in `payload`), triggering the faulty catch path.

### Impact Explanation
Calling the `async.each` iteration callback `cb` twice for the same row is a correctness violation of the `async` control-flow contract used throughout `network.js`. Depending on the `async` library version behavior, this can cause: the final completion callback of `handleSavedPrivatePayments` to fire prematurely/multiple times (mishandling `assocNewUnits`, double-emitting `new_my_transactions`), an uncaught "Callback already called" exception that crashes the node process (since this occurs inside a `setImmediate`/async callback outside of any surrounding try/catch that could turn a crash into graceful degradation), or duplicate/racy execution of `deleteHandledPrivateChain` overlapping with a second full validation pass of the same private payment chain. Any of these effects amounts to a wallet/hub node reliably losing the ability to correctly finish processing legitimate queued private payments (funds can remain stuck in `unhandled_private_payments`, i.e., temporarily frozen/unusable for the recipient) whenever a counterparty sends one crafted, unhashable private-payment payload. This matches the "AA/wallet fund freezing" and "network unable to confirm/process a transaction" categories called out as in-scope impacts.

### Likelihood Explanation
High reachability, low complexity: any private-payment counterparty or paired device can supply `arrPrivateElements[0].payload` content. `objectHash.getBase64Hash` throwing is a realistic outcome for a payload crafted with a structurally unusual field (e.g. deeply nested or type-violating values that fail during canonical JSON stringification) — no cryptographic break or privileged access is required, only the ability to send a private-payment JSON message, which is a completely unprivileged, expected interaction of the wallet/hub protocol.

### Recommendation
Add a `return` (or restructure to an `else`) immediately after `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);` inside the `catch` block in `network.js`'s `handleSavedPrivatePayments`, so execution never falls through to build `key` from an undefined hash or to re-invoke `privatePayment.validateAndSavePrivatePaymentChain` (and therefore `cb`) a second time for the same row, mirroring the already-correct early-return pattern used in the neighboring `ifOk`/`ifError` handlers.

### Proof of Concept
1. As a private-payment counterparty (or via a paired device), construct a private payment chain `arrPrivateElements` whose head element's `payload` contains a value that causes `objectHash.getBase64Hash(payload, true)` to throw (e.g., a payload field with a type/shape that the object-hash canonicalization rejects, verified against `object_hash.js`'s `getBase64Hash` implementation — exact byte-for-byte trigger not independently reproduced in this review due to index limitations on `object_hash.js`).
2. Send this chain through the normal wallet private-payment path so it is queued into `unhandled_private_payments` via `handleOnlinePrivatePayment`/`savePrivatePayment`.
3. Trigger reprocessing (`handleSavedPrivatePayments`), e.g. via history-download completion or `new_my_transactions`.
4. Observe that the `catch` block in `validateAndSave` fires, calls `deleteHandledPrivateChain(..., cb)`, but execution continues into `privatePayment.validateAndSavePrivatePaymentChain(...)`, which will invoke `cb` again through `ifOk`/`ifError`/`ifWaitingForChain`, double-invoking the `async.each` iteration callback for that row and corrupting the completion/state tracking (`assocNewUnits`, `eventBus` key emission) of the batch.

Note: I was not able to fully verify the exact conditions under which `objectHash.getBase64Hash` throws (contents of `object_hash.js` were only referenced, not fully inspected) or the exact crash/hang behavior of the specific `async` version in use; a Devin session with full repository access would be needed to confirm the precise triggering payload and runtime consequence.
