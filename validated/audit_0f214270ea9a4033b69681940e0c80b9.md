**Rationale:** CVE-2023-35955 concerns a heap-based buffer overflow in GTKWave's `fstReaderIterBlocks2` FST waveform-file parser, specifically in `LZ4_decompress_safe_partial`. This is a desktop file-format parser vulnerability class with no relationship to Polkadot SDK's runtime/consensus/networking code.

A search of the repository confirms `polkadot-sdk` does not depend on LZ4 at all — no `lz4` references exist anywhere in the codebase. The only decompression-related attacker-reachable paths (PoV blocks, runtime code blobs) use `zstd` via `sp_maybe_compressed_blob::decompress`, which already enforces a strict `bomb_limit` bound before allocating/copying output [1](#0-0) , and is invoked with explicit limits both for PoV data [2](#0-1)  and for runtime code blobs [3](#0-2) .

There is no attacker-reachable LZ4 partial-decompression code path, no missing bounds check analogous to the CVE, and therefore no valid FRAME/XCM/Rust analog to report. Forcing this GTKWave file-parser CVE onto Polkadot SDK's decompression infrastructure (which uses zstd with bomb-limit enforcement, not LZ4) would be an unsupported analogy.

fn read_from_decoder(
	decoder: impl Read,
	blob_len: usize,
	bomb_limit: usize,
) -> Result<Vec<u8>, Error> {
	let mut decoder = decoder.take((bomb_limit + 1) as u64);

	let mut buf = Vec::with_capacity(blob_len);
	decoder.read_to_end(&mut buf).map_err(|_| Error::Invalid)?;

	if buf.len() <= bomb_limit {
		Ok(buf)
	} else {
		Err(Error::PossibleBomb)
	}
}
