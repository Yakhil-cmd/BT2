### Title
Architecture-Dependent G2 Subgroup Check in bn256Pairing Precompile Causes Consensus Divergence — (`crypto/bn256/bn256_slow.go`, `crypto/bn256/gnark/g2.go`, `blockchain/vm/contracts.go`)

### Summary
The `bn256Pairing` precompile dispatches to different cryptographic backends depending on build architecture. The gnark backend (amd64/arm64) rejects G2 points outside the prime-order subgroup during deserialization, causing EVM revert. The cloudflare backend (all other architectures) accepts such points and returns `false32Byte` with no error, causing EVM success. A single crafted transaction can produce different receipts and state roots on honest nodes running different architectures, permanently splitting consensus.

### Finding Description

`crypto/bn256/bn256_fast.go` selects gnark for `amd64 || arm64`: [1](#0-0) 

`crypto/bn256/bn256_slow.go` selects cloudflare for all other architectures: [2](#0-1) 

Gnark's `G2.Unmarshal` enforces a subgroup check: [3](#0-2) 

Cloudflare's `G2.Unmarshal` only checks `IsOnCurve()`, with no subgroup check: [4](#0-3) 

`runBn256Pairing` calls `newTwistPoint`, which propagates the error from `Unmarshal` directly: [5](#0-4) 

On gnark: `newTwistPoint` returns an error → `runBn256Pairing` returns `nil, err` → precompile fails → EVM reverts.
On cloudflare: `newTwistPoint` succeeds → `PairingCheck` runs → returns `false32Byte, nil` → EVM continues.

### Impact Explanation
Two honest validators processing the same block containing a transaction that calls precompile `0x08` with a G2 point on the bn256 twist curve but outside the prime-order subgroup will produce different execution outcomes. One node records a revert receipt; the other records a success receipt. The resulting receipt hashes differ, producing different state roots in the block header. This is a permanent consensus split: neither node is misbehaving, yet they cannot agree on the canonical chain state.

### Likelihood Explanation
The attack requires only a valid transaction submitted via public RPC. Constructing a G2 point on the curve but outside the prime-order subgroup is standard elliptic curve arithmetic (multiply a generator by a cofactor). The only practical constraint is that at least one honest validator must be running on a non-amd64/non-arm64 architecture (e.g., 386, mips, riscv64, s390x). The code path is unconditionally present in the repository and activates on any such node.

### Recommendation
Add an explicit subgroup check to the cloudflare `G2.Unmarshal`, mirroring the gnark implementation. Alternatively, add a post-`Unmarshal` subgroup check inside `newTwistPoint` in `blockchain/vm/contracts.go` so the check is architecture-independent and applied before `PairingCheck` is called.

### Proof of Concept
1. Construct a G2 point `P` on the bn256 twist curve that is NOT in the prime-order subgroup (e.g., take a generator and multiply by the cofactor, or use a known test vector such as those in EIP-197 test suites for subgroup-invalid inputs).
2. Build a transaction calling precompile `0x08` with a valid G1 point and `P` as the G2 component (192 bytes total, length check passes).
3. Submit the transaction to a two-node devnet: one node compiled for amd64/arm64 (gnark), one compiled for a non-amd64/non-arm64 target (cloudflare).
4. Observe: the gnark node reverts the transaction (receipt `status=0`); the cloudflare node succeeds with `false32Byte` output (receipt `status=1`). The receipt hashes and state roots diverge. The nodes cannot reach consensus on the block.
