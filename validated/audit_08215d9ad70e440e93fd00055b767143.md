### Title
Share-Based Payout Formulas in AA Templates Round Down to Zero, Causing Depositors to Lose Funds - (File: test/samples/uniswap_like_market_maker.oscript, test/samples/51_attack_game.oscript)

### Summary
The oscript formula engine evaluates arithmetic using `decimal.js` configured with only **15 significant digits of precision**, and payment amounts derived from these formulas are truncated to integers via `round()`/`floor()`/`ceil()`. Reference AA templates shipped in the repo compute a depositor's/winner's payout as a ratio (`share = contributed_amount / total_amount`) and then multiply that ratio by a pool balance. When the ratio is small enough that the computed amount rounds to `0`, the caller's payment is silently converted into an unauthorized, permanent loss: the trigger's deposited asset/tokens are already consumed by the AA, but the AA sends back `0` bytes/asset, exactly mirroring the reported Solidity bug class.

### Finding Description
`formula/common.js` sets:
```
Decimal.set({ precision: 15, rounding: Decimal.ROUND_HALF_EVEN, ... });
``` [1](#0-0) 

All arithmetic, including division (`/`), is executed through this 15-significant-digit `Decimal` context inside `formula/evaluation.js`'s operator handling (`case '/': f = 'div'; ... prevV = prevV[f](res);`), and the result is later coerced back into JS numbers for payment `amount` fields. [2](#0-1) 

The bundled example AAs use exactly the "share = user_amount / total_amount, then payout = round(share * balance)" pattern from the report:

- `uniswap_like_market_maker.oscript` divest logic:
```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
...
outputs: [{address: "{trigger.address}", amount: "{ round($investor_share * balance[$asset]) }"}]
``` [3](#0-2) 

- `51_attack_game.oscript` payout logic:
```
$share = $asset_amount / var['team_' || $winner || '_amount'];
...
$amount = round(( $share * (1-$founder_tax) + ... ) * var['total']);
``` [4](#0-3) 

If `var['mm_asset_outstanding']` (or the winning team's total contribution) grows large relative to an individual depositor's amount — e.g., ratio smaller than roughly `1e-15` given the engine's 15-digit precision, or simply small enough that `share * balance < 0.5` — the `round()` call yields `0`. The AA already consumed the caller's asset/bytes in the same trigger (the deposited `mm_asset`/team-asset output was received as part of the trigger), but the reciprocal `payment` message pays out `0`, and the state update (`mm_asset_outstanding -= trigger.output[[asset=$mm_asset]]`) still deducts/burns the caller's share bookkeeping. The caller has no way to recover the consumed tokens.

This is the same root cause as the audited report: a share ratio computed by integer/fixed-precision division that can underflow to zero for legitimate, non-malicious amounts, silently zeroing out a payout while the deposit is already spent.

### Impact Explanation
An unprivileged AA trigger sender who deposits a legitimately small (but valid, non-dust) amount relative to the AA's accumulated total balance can have their reward/redemption amount computed as exactly `0`, while their input token/asset/bytes have already been transferred into the AA's balance and their bookkeeping variable decremented. This is a concrete AA fund loss for the depositor — they lose their principal with no recourse, since AA logic itself considers the operation successfully completed (state updated, no bounce triggered).

### Likelihood Explanation
The likelihood is a function of the AA's cumulative scale: as `var['mm_asset_outstanding']` or a team's total pool grows through many rounds of ordinary use, later small depositors are increasingly likely to fall below the precision floor of the 15-significant-digit `Decimal` engine and receive `0` from `round()`. This does not require any attacker action, malicious peer, or privileged actor — it is a naturally reachable condition for any long-lived, actively used AA instance built from these common oscript share-calculation patterns, which are provided as canonical reference designs in the repository for real-world AA authors to copy.

### Recommendation
- In AA templates that compute proportional shares, guard against zero-payout truncation by bouncing the trigger (refusing the deposit) when the computed payout would round to `0` instead of silently accepting the deposit and paying nothing back.
- Where feasible, track balances with higher effective precision (e.g., store amounts scaled up internally, or maintain a remainder/dust variable that carries forward the truncated fractional part) so a shrinking `share` never fully collapses to zero over the life of the AA.
- Document the precision limits of the `decimal.js` (15 significant digits) formula engine prominently for AA authors writing share/ratio-based payout logic, since this differs from fixed-point 1e18 semantics that Solidity developers may assume.

### Proof of Concept
1. Deploy `uniswap_like_market_maker.oscript`; multiple investors deposit over time, growing `var['mm_asset_outstanding']` to a very large value (e.g., `1e18` after enough rounds of legitimate investment/reinvestment).
2. A later investor sends a valid `divest` trigger with `trigger.output[[asset=$mm_asset]]` set to a small but real balance, e.g. `1000`.
3. `$investor_share = 1000 / 1e18` evaluates to `1e-15`, at or below the engine's 15-significant-digit precision floor.
4. `round($investor_share * balance[$asset])` evaluates to `0` for any realistic `balance[$asset]`.
5. The AA's `payment` message sends `0` of `$asset` and `0` bytes to the investor, while `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` still deducts the investor's `mm_asset` amount from the tracked total — the investor's `1000` units of `$mm_asset` are burned/consumed with no compensation.
