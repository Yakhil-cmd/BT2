Based on the analysis, I've confirmed the exploit path. Here is the final analog.

### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while the repository/stack actually acted upon is looked up from the independent, unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or the `organization.login` fallback) straight out of the untrusted, attacker-supplied JSON body itself, before the signature has been verified. [1](#0-0) 
Once the signature check passes for that org, event handlers such as `PushHandler`/`Handler#stacks` resolve the target `Repository`/`Stack` using a completely different, equally attacker-controlled field: `repository.full_name`. [2](#0-1) 
Nothing ties these two fields together, so an entity able to obtain a valid signature for *any* one configured GitHub organization can forge events for a *different* organization's repository/stack.

### Finding Description
`verify_signature` computes the signing org like this:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` trivially returns `true` whenever the resolved org has no configured `webhook_secret`:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

The test fixtures show that Shipit legitimately supports multiple configured GitHub orgs/apps in one deployment, and that some of them can have `webhook_secret: # nil`: [4](#0-3) 

After the request passes `verify_signature`, `create` dispatches to handlers using the **same raw JSON body**, but the repository/stack resolution path is independent of `repository_owner`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` uses this `stacks` scope directly to trigger a GitHub sync for whichever stack it finds:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`Stack#sync_github` enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha`, which fetches commits from GitHub for that stack and appends them, potentially unlocking continuous delivery/auto-deploy for that stack: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used only for signature-org selection) and `repository.full_name` (used to select the acted-upon `Repository`/`Stack`) are two independent keys of the same attacker-supplied JSON body, and the endpoint is a plain public HTTP POST (not literally relayed by GitHub), an attacker who can obtain a valid signature for **any one** configured organization (e.g., one with `webhook_secret` unset/blank, or one whose secret they otherwise know because they legitimately manage that org's own GitHub App/webhook config) can set `repository.owner.login` to that org while setting `repository.full_name` to an entirely different, victim organization's `owner/repo`. The verification binding `organization-that-authenticated == organization-whose-repository-is-acted-upon` is never enforced.

### Impact Explanation
This breaks a core deployment-trust binding: the org whose secret authenticated the webhook is not required to be the org that owns the repository/stack being manipulated. An attacker can inject fabricated push events for a victim stack they don't otherwise have authenticated access to, forcing `GithubSyncJob` to run for that stack with an attacker-chosen `expected_head_sha`. Depending on the stack's continuous-delivery/auto-merge configuration, this can trigger unauthorized syncs, unlock deploy scheduling, or otherwise cause the engine to act on a repository outside the boundary the signature actually authorized — an unauthorized-deploy-adjacent condition matching the "organization that authenticated versus the repository that is written" binding break called out for this class of finding.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a valid signature for at least one configured organization while targeting another. This is realistic in any multi-organization Shipit deployment (as evidenced by the multi-org fixture used in the test suite) where at least one configured org has no `webhook_secret`, or where the attacker legitimately controls/administers one of the configured GitHub App installations and thus knows its webhook secret. No stolen credentials, session, or `ApiClient` token are required — only knowledge of one configured org's webhook secret (or the absence thereof) and the ability to POST to the public webhooks endpoint.

### Recommendation
Cross-check that the organization resolved from `repository_owner` (used for signature verification) matches the organization portion of `repository.full_name` (used for repository/stack resolution) before dispatching to handlers, and reject the request if they differ. Alternatively, verify the signature using the secret associated with the organization derived from `repository.full_name` rather than `repository.owner.login`/`organization.login`, so a single canonical field drives both authentication and repository resolution.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations in `Shipit.github_apps`: `AttackerOrg` (with `webhook_secret` blank/nil, or a secret the attacker knows) and `VictimOrg` (with a stack configured, secret unknown to the attacker).
2. Craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature` computed for `AttackerOrg`'s (nil/known) secret.
4. `verify_signature` resolves `repository_owner` = `AttackerOrg`, verification passes trivially (secret nil) or the attacker computes the correct HMAC.
5. `PushHandler` resolves `repository_name` = `VictimOrg/victim-repo`, finds the real victim `Stack`, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha` for that stack — despite the request never having been authenticated for `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
