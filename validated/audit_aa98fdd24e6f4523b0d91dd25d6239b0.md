### Title
Attacker-triggered `assert_eq!` panic in `build_updated_stake_reward` via mid-window `Split`/`Withdraw` on a rewarded stake account - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
An unprivileged staker can crash validators cluster-wide by submitting a `StakeInstruction::Split` (or any instruction that changes `delegation.stake`, e.g. `Withdraw`/`Redelegate`) against their own stake account in the window between the epoch-boundary reward calculation block and the corresponding distribution block for their partition. This desynchronizes the calculation-time expected delegation from the live `StakesCache` value, tripping the `assert_eq!("stake reward delegation must be consistent...")` panic in `Bank::build_updated_stake_reward`, which is not caught anywhere in `store_stake_accounts_in_partition`.

### Finding Description
`Bank::build_updated_stake_reward` at [1](#0-0)  fetches the *current* `StakesCache` entry for the reward's `stake_pubkey`, which reflects any transactions processed on the chain after reward calculation (the cache is refreshed after every processed transaction via `Bank::update_stakes_cache` → `StakesCache::check_and_store` → `upsert_stake_delegation`, see [2](#0-1)  and [3](#0-2) ).

When the `relax_post_exec_min_balance_check` feature is not active for the bank (`adjust_delegations_for_rent == false`), the function takes this branch: [4](#0-3) 

`expected_delegation` is computed from the *live* cache value (`stake.delegation.stake`, i.e. whatever the account currently holds at distribution time) plus the calculation-time `stake_reward`. `new_stake.delegation.stake` is the value computed by the calculation phase, which is based on the delegation amount observed *at calculation time* plus the same reward. These two are only guaranteed to match if the attacker does not change `delegation.stake` between calculation and distribution.

An attacker who owns the stake account's staker/withdrawer authority can submit `StakeInstruction::Split` (or a `Withdraw`/other instruction reducing the delegated amount) in that window. Splitting moves part of the delegation out of the source account, reducing its `delegation.stake` while keeping it a valid `StakeStateV2::Stake` account (so it stays in `StakesCache`, not removed, and does not hit the `unreachable!` at lines 255-261, which is only reachable if the account leaves the `Stake` variant entirely — that path is already safely guarded because such accounts are dropped from `StakesCache` and produce `DistributionError::AccountNotFound` instead, per [5](#0-4) ).

With a reduced live `delegation.stake`, `expected_delegation != new_stake.delegation.stake`, and the `assert_eq!` panics inside `store_stake_accounts_in_partition`'s per-account loop [6](#0-5) , which is invoked unconditionally from `distribute_epoch_rewards_in_partition` during block processing of the distribution slot for that partition [7](#0-6) . Because every validator processes the same deterministic reward distribution logic for the same slot, this crash is deterministic and cluster-wide — not just a single-node bug.

The `DistributionError::AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` error paths are properly handled as recoverable `Err`s that burn the reward instead of panicking, but the `assert_eq!` inconsistency check has no such `Result`-based fallback; it panics directly instead of returning a `DistributionError`.

### Impact Explanation
This is an epoch-boundary halt: any staker can pick their own delegated stake account, wait for the reward-calculation phase to fix rewards for the current epoch, then split/withdraw from that account before its assigned distribution block, guaranteeing a validator panic at a fixed, attacker-influenced block height. Since state transitions are deterministic, all validators following consensus rules crash identically — a cluster-wide liveness halt, which is the "epoch-boundary halt" bounty category referenced in the question (no reachable instruction sequence should leave epoch processing in a panicking state).

### Likelihood Explanation
This requires only a normal, unprivileged staking authority (staker/withdrawer) over one's own stake account — no validator, leader, or privileged capability is needed. It requires the `relax_post_exec_min_balance_check` feature to not (yet) be active for the affected epoch (this is a feature-gated code path still present and reachable in the current codebase, exercised by existing tests such as `test_build_updated_stake_reward(false)` at [8](#0-7) ). The attacker only needs to time a single `Split`/`Withdraw` transaction within the multi-block calculation→distribution window (which spans `REWARD_CALCULATION_NUM_BLOCKS` blocks and their own partition's distribution block), which is easily observable on-chain, making this highly repeatable on any cluster where the feature is inactive (e.g., devnet/testnet or prior to mainnet activation).

### Recommendation
Replace the `assert_eq!` in `build_updated_stake_reward` (non-`adjust_delegations_for_rent` branch) with a `DistributionError` return (e.g., a new `DistributionError::DelegationMismatch` variant), mirroring how `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` are already handled as recoverable errors in `store_stake_accounts_in_partition`, so any intervening modification to the stake account's delegation between calculation and distribution burns/skips that reward instead of panicking the validator.

### Proof of Concept
Rust unit-test plan (extending the existing test module in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`):
1. Set up a bank with `relax_post_exec_min_balance_check` disabled (default in most test genesis configs).
2. Populate a stake account via `populate_starting_stake_accounts_from_stake_rewards` with a `PartitionedStakeReward` computed for delegation `D`.
3. Simulate the attacker's intervening `Split` by mutating the stakes cache/account directly to a reduced delegation `D' < D` (representing that a `StakeInstruction::Split` transaction executed between calculation and distribution), then re-inserting into `stakes_cache_accounts` (or, for a full integration test with `solana-program-test`: warp to the calculation block, submit `stake_instruction::split` against the attacker's account before the distribution block, then advance to the distribution block).
4. Call `Bank::build_updated_stake_reward` (or `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition`) for that stake_pubkey.
5. Expected (buggy) result: the call panics with `"stake reward delegation must be consistent with the updated stake account lamport balance"` instead of returning `Err(DistributionError::...)`.
6. After the fix, assert instead that `build_updated_stake_reward` returns a handled `Err(DistributionError::DelegationMismatch)` (or similar), and `distribute_epoch_rewards_in_partition` completes without panicking, burning only that account's reward.
