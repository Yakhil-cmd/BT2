### Title
`StatusHandler#process` resolves commits by bare SHA across all stacks instead of scoping to the webhook's own repository, allowing a foreign repository's signed status to trigger another stack's `ContinuousDeliveryJob` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)`, with no filter tying the match to the repository that actually signed the incoming webhook. Because git SHAs are content-addressed and shared across forks/history, an attacker who owns an unrelated repository X can send a validly-signed `status` webhook for X and have Shipit apply that status to an identical-SHA `Commit` row that belongs to a completely different, victim stack Y, which can cascade into `ContinuousDeliveryJob.perform_later(stack)` being enqueued for Y.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])`, i.e., that any `Commit` row matching `params.sha` belongs to the same repository whose webhook secret was just verified. This does not hold.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies the signature via `verify_signature`, which calls `Shipit.github(organization: repository_owner)` where `repository_owner` is read from `payload.dig('repository','owner','login')` — this only proves the payload was legitimately signed **for the org that owns the SHA/status's originating repo**, e.g. attacker's own repo X.
2. It then dispatches to `Shipit::Webhooks.for_event(event)` handlers, calling `StatusHandler.call(params)`.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries the **global** `Commit` table by `sha` only — it never restricts to `stacks` (the `Repository.from_github_repo_name(repository_name)`-derived scope that the base `Handler#stacks` helper exists precisely to provide, and which `CheckSuiteHandler#process` correctly uses: `stacks.where(branch: params.check_suite.head_branch)` in `app/models/shipit/webhooks/handlers/check_suite_handler.rb:14`).
4. If a `Commit` row with the same SHA exists under victim stack Y (plausible when X is a fork of Y, or otherwise shares git history, so the same content-addressed SHA was synced into both stacks' `commits` tables independently by `GithubSyncJob`), `commit.create_status_from_github!(params)` (`app/models/shipit/commit.rb:165-169`) creates a `Status` row on Y's commit.
5. `Status` has `after_commit :schedule_continuous_delivery, on: :create` (`app/models/shipit/status.rb:19,42-44`), which calls `commit.schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`):
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
```
Here `stack` is `commit.stack`, i.e., **Y**, even though only X's webhook secret was ever verified.

Existing guards fail to prevent this because:
- `verify_signature` only proves authenticity of the sender for the *organization named in the payload* (X's org); it says nothing about which `Commit`/`Stack` rows the payload should be allowed to touch.
- `drop_unhandled_event` and `ExplicitParameters` param schema only validate shape, not scope.
- `stacks` scoping helper exists in `Handler` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) and is correctly used by `CheckSuiteHandler`, but `StatusHandler` bypasses it entirely.

### Impact Explanation
An attacker who controls only repository X (and its webhook config for the org that owns X) can cause Shipit to write a `Status` row (`state: success`) against a `Commit` belonging to victim stack Y that never authenticated this webhook. If Y has `continuous_deployment: true` and the shared commit is Y's newest undeployed/deployable commit, this results in `ContinuousDeliveryJob.perform_later(stack)` being enqueued for Y and, if the deployment window/occupancy checks pass, an unauthorized deploy of Y. This is a write for a repository (Y) that never authenticated the payload — matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." It is repeatable against any victim stack whose commit history happens to share a SHA with a repository the attacker controls (most plausibly forks, but any coincidental/engineered shared-history SHA works, since git SHAs are global and content-addressed, not repo-scoped).

### Likelihood Explanation
Preconditions: (1) attacker owns/administers a GitHub repository X registered with a Shipit-recognized GitHub App/org so a genuinely signed `status` webhook can be produced for X (attacker can do this by simply setting a commit status via the GitHub UI/API on any SHA reachable in X — including ancestor commits shared with a fork parent); (2) the victim stack Y independently has a `Commit` row with the identical SHA (realistic for forks or shared history, and the question explicitly allows this precondition: "no push to Y required"); (3) Y has `continuous_deployment: true`. All of this requires zero Shipit credentials, sessions, or secrets — only ownership of an arbitrary GitHub repo that shares commit history with the target. This is directly reproducible with a minitest against `StatusHandler` without live GitHub.

### Recommendation
Scope `StatusHandler#process` to the repository that signed the webhook, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so a status can only ever be applied to commits belonging to the repository that actually signed the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "status for repo X's payload must not affect an unrelated stack Y sharing the same commit sha" do
          victim_stack = shipit_stacks(:shipit) # stack Y, belongs to repo "shopify/shipit-engine"
          shared_sha = victim_stack.commits.first.sha
          victim_stack.update!(continuous_deployment: true)

          # Attacker's payload claims repository X ("attacker/evil-repo"), NOT victim's repo.
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/evil-repo', 'owner' => { 'login' => 'attacker' } }
          }

          assert_no_enqueued_jobs only: ContinuousDeliveryJob do
            StatusHandler.call(ActionController::Parameters.new(payload).permit!.to_h)
          end
        end
      end
    end
  end
end
```
Before the fix, `Commit.where(sha: shared_sha)` matches the victim's commit regardless of the payload's `repository.full_name`, and the assertion fails because `ContinuousDeliveryJob.perform_later(victim_stack)` is enqueued — proving `stack` in `ContinuousDeliveryJob.perform_later(stack)` diverges from the repository actually verified via `webhook_secret`.
