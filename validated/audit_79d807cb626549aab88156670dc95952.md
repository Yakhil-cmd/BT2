### Title
Cross-organization membership hijack via unauthenticated `team.id` in `membership` webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` to check against based on `repository_owner`, which for a `membership` event falls back to `params.dig('organization', 'login')` — a value fully controlled by whoever sends the request. Once verified against the attacker's own organization's secret, `MembershipHandler#find_or_create_team!` looks up `Shipit::Team` purely by the attacker-controlled `params.team.id` (`github_id`), with no check that the matched team's `organization` equals the organization that authenticated the payload, allowing an attacker to add themselves to any pre-existing team from another organization.

### Finding Description
The broken binding, stated explicitly: `organization_that_signed_payload (Shipit.github(organization: params.organization.login).webhook_secret owner)` should equal `organization_owning_the_Team_row_mutated (team.organization for the row matched by github_id)`. Tracing the code shows this equality is never enforced.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` via `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`), which for `membership` events (no top-level `repository` key) resolves to `params.dig('organization', 'login')` — an attacker-supplied JSON field, not derived from any authenticated source. It then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it fetches the config/secret for whatever organization name the attacker put in the payload. Since the attacker legitimately administers that org in Shipit (per the question's premise), this verification succeeds using the attacker's own genuine `webhook_secret`.
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does `Team.find_or_create_by!(github_id: params.team.id)`. `github_id` is a GitHub-wide numeric team ID with no per-organization namespacing in this lookup — it is only scoped by the attacker-supplied `params.team.id` integer, not by `params.organization.login`.
- If `params.team.id` coincides with the `github_id` of a pre-existing `Shipit::Team` row belonging to a different, victim organization (e.g., one already onboarded into `Shipit.github_teams`), `find_or_create_by!` returns that existing row instead of creating a new one (the `organization`/`github_team=` assignment block only runs on creation, so an existing victim team is untouched but matched).
- `process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then calls `team.add_member(member)` with `member = User.find_or_create_by_login!(params.member.login)`, where `params.member.login` is also attacker-controlled and can be the attacker's own GitHub login. `Team#add_member` (`app/models/shipit/team.rb:41-43`) unconditionally appends the membership.

No guard in the chain (`drop_unhandled_event`, `verify_signature`, the `ExplicitParameters` schema in `MembershipHandler.params`, or `Team.find_or_create_by!`) ties the authenticated organization to the team being mutated. The schema only requires `team.id`/`organization.login` to be present and well-typed, not that they correspond to the org whose secret verified the request.

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own org's `webhook_secret` over a JSON body of the form:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "https://api.github.com/teams/x" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-login" }
}
```
This passes `verify_signature` (checked against `attacker-org`'s secret) and is routed to `MembershipHandler`, which matches the existing `Team` row for `victim_team_github_id` (belonging to, e.g., `shopify`) and inserts a `Membership` linking the attacker's `User` to it.

### Impact Explanation
A successful request writes a `Membership` row binding an attacker-controlled `User` to a `Shipit::Team` that belongs to a completely different, victim GitHub organization, without any interaction from that victim organization. If the victim team's `id` is listed in `Shipit.github_teams`, `User#authorized?` (`app/models/shipit/user.rb:80-82`) becomes true for the attacker's user, granting full authenticated access to Shipit (deploys, rollbacks, stack management) across the whole instance — this matches "escalation into `Shipit.github_teams` authorization" (High/Critical per the provided severity rubric). The attack is repeatable against any `Team` row whose `github_id` the attacker can guess or discover (GitHub team IDs/slugs are often discoverable via the GitHub API or UI even for teams the attacker isn't a member of, depending on org visibility settings), and is not limited to a single victim organization — any onboarded org's teams are targets as long as their `github_id` is known or guessable.

### Likelihood Explanation
Preconditions: the attacker must administer at least one organization already configured in Shipit with its own valid `webhook_secret` (a normal, unprivileged setup step available to any org owner who onboards their own repos into a shared Shipit instance), and must know or successfully guess the `github_id` of a target `Shipit::Team` row (obtainable via GitHub's teams API for many orgs, or via brute force since IDs are sequential/enumerable). No Shipit secrets, sessions, or API tokens are required — only the attacker's own legitimately-provisioned org webhook secret, which is exactly the scenario the question describes. This is a plausible, repeatable, cheap attack (a single crafted HTTP POST) rather than a purely theoretical one.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches the organization already stored on any existing `Team` row before mutating it — reject/raise if a `github_id` collision maps to a different organization than the one that signed the request. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the webhook secret is authoritative for every organization-scoped identifier processed later in the handler (not merely used to pick a secret and then discarded).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "membership event cannot bind attacker to a team belonging to another organization" do
  victim_team = shipit_teams(:shopify) # fixture Team with organization: 'shopify', github_id: 4242
  attacker_login = 'attacker-user'

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 't', slug: 't', url: 'https://api.github.com/teams/t' },
    organization: { login: 'attacker-org' },
    member: { login: attacker_login }
  }.to_json

  assert_difference -> { Shipit::Membership.count }, 1 do
    post '/webhooks', params: payload, headers: {
      'X-Github-Event' => 'membership',
      'X-Hub-Signature' => 'sha1=whatever',
      'Content-Type' => 'application/json'
    }
  end

  attacker = Shipit::User.find_by!(login: attacker_login)
  assert_includes victim_team.reload.members, attacker
  # Binding check: the org that verified the payload ('attacker-org') != victim_team.organization ('shopify')
  assert_not_equal 'attacker-org', victim_team.organization
end
```
This demonstrates that a `Membership` is created linking the attacker's `User` to `victim_team` even though `victim_team.organization` (`shopify`) differs from the organization (`attacker-org`) whose `webhook_secret` verified the request — confirming the binding claimed in the question is broken.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|

          end
        end
