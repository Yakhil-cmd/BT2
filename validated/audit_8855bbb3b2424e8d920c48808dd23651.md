### Title
Direct token transfers to the pool are permanently locked — no booked credit, no recovery path — (`contracts/pool/src/ops/recapitalize.rs`)

### Summary
The pool contract custodies all market tokens, but its reserve book only credits tokens received through owner-invoked (controller) entrypoints that measure receipt. Tokens transferred directly to the pool address by anyone are unbooked: they raise the physical balance without raising any market's tracked cash, and no pool or controller entrypoint can debit or transfer unbooked balance back out. Unlike the swap-aggregator, which ships an explicit `sweep_balance` rescue for stray balances, the pool and controller expose no equivalent.

### Finding Description
The pool is the single custody address for all markets; the same token can back several `(hub, asset)` books sharing one physical balance (`docs/reference/architecture.md` lines 57–65). Accounting is book-based: INV-ACCT-02 states "reserve checks use tracked market cash; token donations alone do not increase it" (`docs/reference/invariants.md` lines 104–109), and the money-flow audit test proves a donation "belongs to no market's cash book" (`tests/test-harness/tests/pool_money_flow_audit.rs` lines 86–96).

Every outbound token movement is tied to a booked debit:

- `withdraw` / `borrow` debit tracked `cash`, which donations never increase.
- `recapitalize` credits `min(amount, backing_shortfall)` where `amount` is the receipt of the *new* inbound transfer the controller just made — it refunds `amount - applied` to the payer and never references the pre-existing pool balance (`contracts/pool/src/ops/recapitalize.rs` lines 44–58, `contracts/controller/src/markets.rs` lines 140–163).
- Cash flash loans and liquidation refunds are measured balance-delta settlements scoped to the in-flight operation; "neither category sweeps prior balances" (`docs/explanation/threat-model.md` lines 172–175).
- Pool mutations require the owner (the controller), and the controller exposes no sweep/rescue entrypoint. Contrast with `sweep_balance` on the swap-aggregator (`contracts/swap-aggregator/src/lib.rs` lines 187–203), which exists precisely because stray balances otherwise strand.

The threat model itself documents the symmetric case: venue rewards pushed to the pool arrive "as an unbooked donation" that the pool has no entrypoint to claim or forward (`docs/explanation/threat-model.md` lines 134–140), confirming unbooked pool balances are unrecoverable by design of the current code.

### Impact Explanation
Permanent freezing of funds. Any user who transfers a listed (or unlisted) token directly to the pool address loses it permanently: the tokens are visible in the pool's balance but belong to no cash book, so they cannot be withdrawn, borrowed, liquidated, recapitalized, or swept. There is no governance operation or controller path that moves unbooked pool tokens; absent a Wasm upgrade the funds are locked forever.

### Likelihood Explanation
Reachable by any unprivileged address via a plain token `transfer` to the pool contract — an explicitly in-scope path ("direct token transfers to the pool or controller"). Accidental sends happen via wrong-address mistakes, fee-on-transfer or reward pushes (the Aquarius LP reward case is already documented as an unbooked donation), and users attempting to "top up" a market without going through `controller.supply`. No special positioning is needed.

### Recommendation
Add an owner/governance-authorized recovery entrypoint on the pool that transfers out only the unbooked surplus, i.e. `balance - Σ cash books` per token (a `ReservedTotal`-style counter like the router's `sweep_balance` in `contracts/swap-aggregator/src/lib.rs` lines 187–203). Alternatively, document and accept the loss, or credit direct donations to a protocol-revenue bucket so they remain recoverable through `claim_revenue`.

### Proof of Concept
1. User calls `token.transfer(user, pool_addr, X)` for a listed asset — succeeds unconditionally.
2. `get_reserves(hub_asset).cash` is unchanged (INV-ACCT-02; `pool_money_flow_audit.rs` line 94 shows `balance == cash + 7*UNIT` donation sitting unbooked).
3. `withdraw`/`borrow` revert or are capped at tracked cash; `recapitalize` books only the caller's fresh `received` amount capped by `backing_shortfall` and refunds the rest; `flash_loan` must return its exact principal.
4. No entrypoint decreases the pool balance without a corresponding booked debit → the `X` tokens remain at the pool address permanently.

One caveat: I could not fully enumerate `contracts/pool/src/lib.rs`'s exported function list within the available iterations; this conclusion relies on the documented invariant that all pool mutations are owner-gated and cash-book-bound, and on the docs' explicit statement that no sweep of prior balances exists on any path.
