## Analysis

The SwissBorg loss stemmed from the **Euler Finance donation attack**: an attacker could donate funds directly into a protocol's internally-tracked balance/reserve accounting without going through the normal deposit path, corrupting an invariant (health/ratio check) used elsewhere in the protocol, then exploit the corrupted state for profit.

ocore's Autonomous Agent (AA) framework has the exact same bug-class exposure through the `balance[...]` formula primitive combined with the "silently absorb unmatched payments" behavior of AAs, and this pattern is even shipped as ocore's own reference constant-product market-maker AA.

### Root cause chain

1. Every payment sent to an AA address becomes a primary trigger — any unprivileged unit poster can send an arbitrary payment to any deployed AA, this is detected purely by output address, with no restriction on amount or purpose: [1](#0-0) 

2. `balance[asset]` in oscript is evaluated directly from the AA's **actual on-chain balance** (`aa_balances` table / `assocBalances`), not from the AA's own state-var accounting: [2](#0-1) 

3. When a trigger payload's messages don't match any `if` case in the AA's script, the AA still keeps the money — it "eats" the coins and performs the resulting (empty) balance update, but **no state-variable accounting code runs**: [3](#0-2) 

4. ocore's own bundled reference AMM/bonding-curve sample computes swap and share-issuance math directly from raw `balance[base]` / `balance[asset]`, assuming those balances only ever change through the accounted `invest`/`divest`/`exchange` paths: [4](#0-3) [5](#0-4) 

Because step 3 lets anyone inject bytes/asset into the AA's real balance while bypassing the `var['mm_asset_outstanding']` bookkeeping that the invest/divest/exchange logic relies on, an attacker can desynchronize the constant-product invariant `asset_balance * bytes_balance = k` and the share-price ratio (`balanceOfAsset / mm_asset_outstanding`) from what legitimate depositors actually contributed — exactly the "donate to corrupt an invariant, then exploit" pattern from the Euler incident.

### Title
Unaccounted balance donation corrupts AMM/bonding-curve invariants in AA `balance[]` reads - (File: `formula/evaluation.js`, `aa_composer.js`, `test/samples/uniswap_like_market_maker.oscript`)

### Summary
An unprivileged unit poster can send a payment to a deployed constant-product/bonding-curve AA that matches none of its `if` cases (e.g., ≤1e5 bytes, no asset output). ocore silently absorbs the funds into the AA's real balance (`aa_balances`) without running any state-update code, per [6](#0-5) . Since the AA's pricing/ratio formulas read the real balance via `balance[...]` ( [2](#0-1) ) rather than from the tracked `var['mm_asset_outstanding']`/investor-share state, this "donation" desynchronizes the invariant the AA relies on for fair pricing.

### Finding Description
`balance[asset]` always reflects the true, cumulative on-chain balance of the AA address, updated on every payment received regardless of whether the payment triggers accounted logic (`updateInitialAABalances` in [7](#0-6) ). The market-maker/AMM pattern shipped by ocore as a reference AA computes:
- `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]`
- `$bytes_balance = balance[base] - trigger.output[[asset=base]]`
- `$p = $asset_balance * $bytes_balance` (constant product)
- share issuance ratio = `trigger.output[[asset=base]] / $bytes_balance`

all directly from `balance[]`, per [8](#0-7)  and [9](#0-8) .

Any unit poster can send a payment to this AA that fails every `if` condition (e.g., base output ≤ 1e5 with no asset output, which is below the "exchange bytes to asset" and "invest" thresholds). This falls through to the "no messages after filtering" branch, which still keeps the coins ( `updateInitialAABalances`/`updateFinalAABalances` credit them to the AA's balance) but performs **no** `var[...]` state changes, per [10](#0-9) .

Because the pricing formulas trust `balance[...]` as ground truth, repeated "donation" payments (each only needing to cover the minimal bounce fee) inflate `$bytes_balance` (or, via similar means, `$asset_balance`) without any corresponding increase in `var['mm_asset_outstanding']`. This is structurally identical to Euler's donation-based reserve manipulation: value is pushed into the tracked balance outside of the normal accounting path, corrupting a ratio/invariant that other logic trusts.

### Impact Explanation
Once the invariant is skewed, the attacker can immediately call the AA's `exchange asset to bytes` / `exchange bytes to asset` branches ( [11](#0-10) ). Since `$p = $asset_balance * $bytes_balance` now includes the donated, unaccounted funds, the resulting swap output (`$amount = $bytes_balance - $new_bytes_balance`, or the asset equivalent) no longer reflects genuine liquidity-provider contributions. The attacker can extract bytes/asset from the pool at a price divorced from the true reserve ratio, directly draining AA-held funds — an AA fund loss reachable by any ordinary unit poster with no special privilege, matching the "AA fund loss" impact class.

### Likelihood Explanation
High: this requires only posting ordinary payment units to a publicly reachable AA address — no privileged role, no race condition, no reliance on network timing. The only friction is needing several small donations to move the ratio meaningfully (each ≤100,000 bytes, capped by the "exchange bytes to asset" threshold), which is a purely economic cost, not a technical barrier. Any AA author who follows ocore's own shipped reference pattern (constant-product/bonding-curve math driven by raw `balance[...]`) inherits this exposure by design.

### Recommendation
- In AA templates/documentation, warn against using raw `balance[...]` for invariant-sensitive pricing math; recommend tracking reserves exclusively via `var[...]` state updated only through accounted code paths.
- Consider adding an oscript primitive/pattern that distinguishes "balance accounted for by this AA's own state" from "raw on-chain balance," so bonding-curve AAs can detect and reject/quarantine unaccounted incoming funds (e.g., bounce any payment that doesn't match a case instead of silently absorbing it, when the AA's design depends on strict accounting).
- Update the bundled `uniswap_like_market_maker.oscript` sample (since it is used as a reference/starting point for real AAs) to reconcile `balance[...]` against `var['mm_asset_outstanding']`-implied reserves and bounce/quarantine any mismatch before performing swap or issuance math.

### Proof of Concept
1. Deploy (or use) the reference AA at [12](#0-11) , funded with initial liquidity of asset `A` and bytes `B`, `var['mm_asset_outstanding'] = S`.
2. Attacker repeatedly sends plain payments of ≤100,000 bytes (just above `bounce_fees.base`, e.g. 90,000 bytes) with no asset output and no `data`. Each fails every `if` condition in the AA (`invest` needs asset output>0, `exchange bytes to asset`/`divest` need >1e5 base or an mm_asset output) and is absorbed via the empty-message branch in [3](#0-2) , incrementing `balance[base]` in `aa_balances` with zero effect on `var['mm_asset_outstanding']`.
3. After enough donations, `balance[base]` is materially larger than the fair reserve `B` implied by `var['mm_asset_outstanding']`.
4. Attacker sends a trigger matching "exchange asset to bytes" ( [13](#0-12) ). Because `$bytes_balance` used in `$p = $asset_balance * $bytes_balance` now includes the donated bytes, the computed `$amount` paid out to the attacker no longer matches the true pre-donation reserve ratio, letting the attacker receive a disproportionate payout relative to the asset they supplied — extracting value from the pool that legitimate liquidity providers are entitled to.
