### Title
API client scoped to a single stack can read build status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and `Api::BaseController#stacks` enforces that scope for every controller that resolves the target stack through it. `Api::CCMenuController`, however, overrides `stack` to resolve the requested stack directly from `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` collection, so the stack-scope binding the token was issued for is never checked.

### Finding Description
`Api::BaseController#stacks` is the authoritative scoping mechanism: it restricts the visible stacks to the one referenced by `current_api_client.stack_id` when the client is stack-scoped, and to all stacks otherwise [1](#0-0) . `Api::StacksController#stack` correctly goes through this scoped collection (`stacks.from_param!(params[:id])`) [2](#0-1) .

`Api::CCMenuController`, which only requires the generic `read:stack` permission [3](#0-2) , defines its own `stack` method that bypasses the scoped `stacks` accessor entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This is the exact analog of the AdminVoting bug class: a binding the token issuer expects to hold ("this token authorizes only stack A") is not the binding actually enforced at execution time ("this endpoint touches whichever stack_id is passed in the URL"). Any client holding a valid, but stack-scoped, `ApiClient` token — for example one created automatically and unprivileged-scoped by `CCMenuUrlController` [5](#0-4)  — can substitute any other stack's `stack_id` in the request and receive that stack's build/deploy state, even though `ApiClient#stack_id?` should have confined it to a single stack.

### Impact Explanation
This crosses a repository/stack authorization boundary without any additional credential: an API token that the issuer intended to authorize reads for exactly one stack instead discloses `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for arbitrary stacks in the Shipit instance, as shown by the fields the endpoint renders [6](#0-5) . This matches the High-impact category of "unauthorized/unscoped read of stack state" since the disclosed data is stack build status/activity that the token holder was never granted access to.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a routine, low-privilege credential meant only for CI status badges) can trigger this by simply changing the `stack_id` query parameter on a GET request — no special permission, write access, or session is required, only the `read:stack` permission that the scoped token already legitimately carries for its own stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection, mirroring `Api::StacksController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id` scoping (enforced in `Api::BaseController#stacks`) is honored by every controller, closing the gap between the stack a token is authorized for and the stack the endpoint actually touches.

### Proof of Concept
1. Create an `ApiClient` scoped to stack A (e.g., via `CCMenuUrlController#fetch`, which creates a client with only `read:stack` permission and no explicit stack restriction is enforced by CCMenu) [5](#0-4) .
2. Issue `GET /api/stacks/:stack_id/ccmenu.xml` using that token but substituting a different stack B's `stack_id` in the URL.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`) [4](#0-3) , the request succeeds and returns stack B's build status, activity, and last-deploy metadata, even though the token was never authorized for stack B.
