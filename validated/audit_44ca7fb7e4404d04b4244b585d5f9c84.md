The bug report describes a peer-to-peer "name marketplace" pattern (ENS-style) where a bidder places a higher bid, then withdraws or reassigns the `tokenTo` recipient before the sale settles, griefing the seller. This concept — a two-party seller/buyer marketplace with a withdrawable bid and a `tokenTo` transfer target — has no structural analog in the polkadot-sdk codebase I could locate.

The closest conceptual match is `pallet-auctions` in `polkadot/runtime/common/src/auctions/mod.rs`, which implements parachain slot auctions via `handle_bid` [1](#0-0) . However, its mechanics are fundamentally different from the reported bug class:

- There is no seller being griefed — the auction determines a winning parachain lease, not a bilateral name sale. If a bid is outbid, the "loser" simply has funds automatically unreserved by the runtime itself, not withdrawn by an attacker [2](#0-1) .
- Bids explicitly "cannot be redacted" by the bidder, per the pallet's own documentation, so there is no attacker-controlled "withdraw" action that could be exploited to grief a counterparty [3](#0-2) .
- There is no `tokenTo`-style parameter or arbitrary recipient reassignment in `bid` — funds are reserved from and returned to the same bidding account only [4](#0-3) .

Because the underlying primitives (seller, escrow-style bid withdrawal, transferable payment recipient) that the reported bug class depends on do not exist in this FRAME auction design, there is no demonstrable reachable analog to report here.
