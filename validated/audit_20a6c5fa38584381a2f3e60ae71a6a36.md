### Title
Cross-repository CI status forgery via unscoped commit lookup in webhook `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization/app derived from the payload's own `repository.owner.login` [1](#0-0) . Once that check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update **globally, by SHA alone**, with no constraint tying the write back to the repository/organization that was actually authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . The equality the code implicitly (and incorrectly) assumes is:

`organization authenticated by signature == organization/repository owning the Commit row being written`

but nothing in the handler enforces it — `Commit#stack` (and thus the target repository) is whatever stack happens to contain a commit with that SHA [3](#0-2) , and `Status.replicate_from_github!`/`create_status_from_github!` persist the status under that commit's own `stack_id`, not the webhook sender's stack [4](#0-3) .

### Finding Description
Shipit supports multiple GitHub Apps/organizations in a single instance (documented in `docs/setup.md`, "Using Multiple Github Applications"), each with its own `webhook_secret` looked up per organization via `Shipit.github(organization: repository_owner)` [1](#0-0) . This correctly proves "this request really came from GitHub for organization X's app installation," but it says nothing about *which Shipit stack/repository the status update should apply to* beyond what's in the payload's `repository` field.

`StatusHandler`, however, ignores the payload's own `repository` field entirely for scoping the write. It only requires `sha`/`state`/etc. [5](#0-4)  and resolves target commits with an unscoped, instance-wide query: `Commit.where(sha: params.sha)`. Because Git SHAs are content-addressed, any two repositories that happen to share commit history (forks, mirrors, subtree merges, cherry-picked/rebased identical commits) will have identical SHAs for identical commits. An attacker who legitimately controls repository A (tracked by Shipit under some GitHub App/organization) can craft or obtain a commit whose SHA collides with a commit that exists in a *different*, unrelated stack B (a different repository/organization also tracked by the same Shipit instance), then push a real GitHub commit status (e.g. `success`) on that SHA from repository A. GitHub delivers a legitimately signed webhook using organization A's `webhook_secret`, so `verify_signature` passes. `StatusHandler` then finds Commit B (belonging to stack B, a repository the attacker never had permission to write to) and calls `commit.create_status_from_github!(params)`, persisting a forged CI status against stack B's commit — using stack B's own `stack_id`, entirely bypassing the organization boundary that `verify_signature` was meant to enforce.

Compare with `CheckSuiteHandler`, which correctly scopes: it first filters `stacks.where(branch: params.check_suite.head_branch)` before touching commits [6](#0-5)  (still not perfectly repo-scoped, but at least branch-scoped within a matching stack). `StatusHandler` has no equivalent guard at all.

### Impact Explanation
A forged `success` status on a victim stack's commit can flip `Commit#deployable?` (`success? && !blocked?`) to true [7](#0-6) , and `Status#schedule_continuous_delivery` is triggered on every status create [8](#0-7) , which can cause `Stack#trigger_continuous_delivery` to fire for continuous-deployment-enabled stacks. This is a cross-repository write into another organization's CI/deploy-gating state and can result in an **unauthorized deploy** of a repository the attacker never had write access to — matching the Critical impact bar ("cross-repository writes...unauthorized deploy").

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub Apps/organizations (a documented, supported configuration), (2) the attacker controlling commit-status write access on at least one tracked repository, and (3) a SHA collision with a commit in a victim stack — realistically achievable via forks/mirrors/shared history/subtree merges rather than a cryptographic collision. This is a moderate-likelihood, credible attack path for multi-tenant Shipit deployments, not requiring any Shipit session, API token, or webhook secret leakage — only ordinary GitHub-side repository permissions the attacker already legitimately has.

### Recommendation
Scope `StatusHandler#process` (and ideally all webhook handlers) to the repository asserted by the webhook payload (`params.dig('repository','full_name')`), joining through `Stack`/`Repository` rather than querying `Commit` by SHA alone, e.g. `commit.stack.repository.full_name == payload repository` before applying the status.

### Proof of Concept
1. Configure Shipit with two GitHub Apps for `org-victim` and `org-attacker` per the "Using Multiple Github Applications" setup.
2. Attacker forks/mirrors a repo such that a commit in `org-attacker/repo` has the same SHA as an existing, CI-pending commit tracked in a `org-victim/repo` stack (e.g., by cherry-picking the exact victim commit into their own repo history).
3. Attacker (with normal collaborator/CI permissions on `org-attacker/repo`) posts a `success` commit status for that SHA via the GitHub API/UI.
4. GitHub sends a `status` webhook, signed with `org-attacker`'s `webhook_secret`, to Shipit's `/github/webhooks` endpoint.
5. `verify_signature` succeeds (correct secret for `org-attacker`) [1](#0-0) .
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches the victim's commit in `org-victim`'s stack, and calls `create_status_from_github!`, creating a forged `success` `Status` row scoped to the victim stack [2](#0-1) .
7. If required CI statuses are now satisfied, the victim commit becomes `deployable?` and continuous delivery can trigger an unauthorized deploy of `org-victim/repo`.
