### Title
Cross-Organization Webhook Forgery via Unauthenticated `repository.owner.login` Selecting the Verification Secret While `repository.full_name` Drives the Actual Write - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate the request against using a field taken directly from the unauthenticated JSON body (`repository.owner.login`, or `organization.login` as fallback), *before* the signature has been checked. The handlers that actually mutate state (sync a stack, merge/archive a review stack, record a commit status) instead key off a different, independently-attacker-controlled field, `repository.full_name`. Because these two fields are never bound together by the signature, and because a GitHub App with no `webhook_secret` configured makes `verify_webhook_signature` return `true` unconditionally, an attacker can forge a webhook for any repository in the multi-tenant install as long as **any one** configured organization has a blank `webhook_secret`.

If the organization resolved from the attacker-controlled `repository.owner.login`/`organization.login` field has no `webhook_secret` set (an explicitly supported configuration — the shipped example configs show `webhook_secret: # nil` even in multi-organization setups, e.g. `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`), signature verification is bypassed entirely, regardless of the actual `X-Hub-Signature` header.

Once the request passes `verify_signature`, `create` dispatches the *entire, attacker-supplied* raw payload to the event handlers: [4](#0-3) 

The handlers resolve the target repository/stack from a **different** field, `repository.full_name`, that was never cross-checked against `repository_owner`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

So the binding the engine is supposed to enforce — "the organization whose secret authenticated this webhook == the repository that is actually acted upon" — is broken: an attacker sets `repository.owner.login` (or `organization.login`) to any weakly-configured/secret-less organization to sail through `verify_signature`, while setting `repository.full_name` to a completely different, properly-configured victim organization's repository, which is what `PushHandler`, the `pull_request` handlers, `StatusHandler`, etc. actually operate on.

### Impact Explanation
This lets an unauthenticated attacker deliver forged GitHub webhook events for a repository they don't control, as long as they can guess/know that some other tenant in the same Shipit install has an unset `webhook_secret`:
- Forged `push` events call `stack.sync_github(expected_head_sha:)` via `PushHandler`, which can drive auto-deploys of attacker-chosen commits — an unauthorized deploy.
- Forged `status` events let an attacker fabricate CI/commit statuses (`StatusHandler`) which are commonly used to gate whether a commit is deployable, enabling an unauthorized deploy of a commit that shouldn't be deployable.
- Forged `pull_request` events can archive/unarchive/merge-related review stacks for a victim repository.

This matches the Critical category: "an unauthorized deploy, rollback or merge" achieved without any Shipit session, API token, or the victim organization's own webhook secret.

### Likelihood Explanation
Exploitation requires: (1) a multi-organization Shipit deployment (documented/supported feature), and (2) at least one onboarded organization with a blank `webhook_secret` — a state the shipped example configs (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`) present as normal/acceptable during setup. Given that, the attack requires no credentials at all — just an HTTP POST to the public `/github/webhooks` endpoint with a crafted body and mismatched `repository.owner.login` / `repository.full_name`.

### Recommendation
Do not select the verification secret from an unauthenticated field read before signature verification. Either:
- Verify the signature against all configured organizations' secrets (or against a single, install-wide secret) rather than a payload-selected one, or
- After verifying with the payload-selected secret, additionally assert that `repository.owner.login`/`organization.login` matches the owner embedded in `repository.full_name`, and reject organizations configured with a blank `webhook_secret` outright (treat blank as "reject", not "always verified").

### Proof of Concept
1. Deploy Shipit configured for two organizations, `WeakOrg` (no `webhook_secret` set) and `victim-org` (properly configured with a stack tracking `victim-org/prod-repo`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/prod-repo",
    "owner": { "login": "WeakOrg" }
  }
}
```
No valid `X-Hub-Signature` is required.
3. `verify_signature` resolves `Shipit.github(organization: "WeakOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler` then processes the payload using `repository.full_name = "victim-org/prod-repo"`, triggering `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — an unauthorized deploy trigger for a repository the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
