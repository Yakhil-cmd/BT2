### Title
Attestor-list rotation on `spender_attested` assets permanently freezes existing coin holders' funds - (File: `validation.js`, `storage.js`)

### Summary
This is the direct ocore analog of the `daiJoin.cage` issue: an authority-controlled state change (there: Maker's `cage`, here: the asset definer's `asset_attestors` update) makes previously valid outputs permanently unspendable, because spend-validation always checks attestation against only the *current* attestor list rather than the list in effect when the coins were received.

### Finding Description
For assets defined with `spender_attested: true`, `storage.readAsset()` resolves the attestor list by looking only at the single most recent `asset_attestors` unit for the asset:
<cite repo="Jortegata/ocore--025" path="storage.js" start="1921="/> [1](#0-0) 

This latest list is then used everywhere spend/transfer validity is checked: `filterAttestedAddresses()` restricts matches to `attestor_address IN (?)` using only `objAsset.arrAttestorAddresses` (the latest list): [2](#0-1) 

`validatePayment()` rejects a payment outright if none of the authors/issuer is in the current attested set: [3](#0-2) 

`validatePaymentInputsAndOutputs()` requires every input's owner address and every output address to be in the *current* attested set, both for public transfers and private fixed-denomination transfers: [4](#0-3) [5](#0-4) [6](#0-5) 

The attestor list itself can be freely replaced at any time by the asset definer via an `asset_attestors` message, which only requires the message to come from `objAsset.definer_address` and pass a basic address-list check — there is no restriction preventing the definer from dropping an attestor whose attestations are the sole basis for existing holders' spend rights: [7](#0-6) [8](#0-7) 

Because validation always re-derives attestation eligibility from the attestor list *at validation time* (via `last_ball_mci`) instead of the list that was current when the output was created, a legitimate holder who received (and is holding) coins while properly attested can be locked out of spending them the moment the definer rotates the attestor list — exactly as `daiJoin.cage()` blocks `exit()` for legitimate cToken redeemers after the fact.

### Impact Explanation
Any coin holder of a `spender_attested` asset (public or private, divisible or fixed-denomination) can have their existing, previously-valid balance become permanently unspendable if the asset definer updates the attestor list (intentionally, accidentally, or because an attestor stops operating and the definer swaps it out) such that the holder's original attestation source is dropped:
- Transfers fail with `"owner address is not attested"` on the input side.
- Transfers/issues fail with `"some output addresses are not attested"` on the output side.

There is no fallback or grace mechanism: unlike a bounce (which returns bytes to the sender), a stuck attested balance has no path back to a spendable state short of the definer re-adding a covering attestor and the user obtaining a fresh attestation — both outside the holder's control. This matches the accepted impact category of AA/asset holder fund freezing due to an external, authority-driven action outside the affected user's control.

### Likelihood Explanation
This requires only one `asset_attestors` message from the asset's definer — a single, cheap, always-available action for any asset that opted into `spender_attested`. No special privilege beyond being the asset's own definer is needed, and it can occur unintentionally during routine attestor-list maintenance (e.g., replacing a decommissioned attestor), not only through malicious intent. Given that `spender_attested` assets are an intended, documented ocore feature, this failure mode is readily triggerable in normal usage.

### Recommendation
- Evaluate attestation using the attestor list that was in effect at the time the spent output was created (or at least any list that was valid at some point after receipt), rather than only the single most-recent list, so that legitimately-received balances remain spendable even after later attestor-list rotations.
- Alternatively, provide a grace/migration mechanism (e.g., allow spending against any attestor list still referenced by an unspent output's mci) so holders are not retroactively frozen out.
- At minimum, document this counterparty risk prominently for `spender_attested` assets, similar to the recommendation in the referenced report to warn users of admin/definer-driven freezing risk.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true` and an initial `asset_attestors` unit listing attestor X.
2. Attestor X attests address U (a normal user).
3. Definer issues/transfers asset A to U; validation passes because U is in `arrAttestedAddresses` derived from X's attestation (per `validatePaymentInputsAndOutputs`, `validation.js:2432/2506`).
4. Definer posts a new `asset_attestors` message removing X and adding attestor Y (`validateAttestorListUpdate`, `validation.js:2829`). This is fully valid per `checkAttestorList`.
5. `storage.readAsset()` now resolves `arrAttestorAddresses` to only `[Y]` (`storage.js:1923-1946`).
6. U (still holding unspent asset-A outputs, never attested by Y) attempts to transfer or spend that balance. `filterAttestedAddresses`/`validatePaymentInputsAndOutputs` reject the unit with `"owner address is not attested"` / `"some output addresses are not attested"`, permanently freezing U's balance unless Y (or another current attestor) attests U — an action entirely outside U's control.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
