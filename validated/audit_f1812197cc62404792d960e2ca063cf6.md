### Title
Webhook signature is verified against the organization named in the payload, but events are applied to whatever repository the same payload claims — breaking the "authenticated organization = written repository" binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit.github(organization: ...)` supports configuring multiple independent GitHub Apps/orgs on a single Shipit instance, each with its own `webhook_secret` [1](#0-0) . The webhooks controller picks *which* org's secret to verify a request against by reading an attacker-controlled field of the very payload being verified, but the handlers that actually act on the payload use a *different* attacker-controlled field to select the target repository/stack, and nothing ties the two together.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to check the signature against using `repository_owner`, which is read straight out of the unverified JSON body: [2](#0-1) [3](#0-2) 

Once the HMAC check passes, `create` hands the *entire* raw payload to the event handlers unchanged: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . The base `Handler` class resolves the target `Repository`/`Stack` from a *different* field in the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) . Every concrete handler (`PushHandler`, PR handlers, etc.) inherits this same lookup: [6](#0-5) , [7](#0-6) .

This mirrors exactly the class of bug in the analog report: a field that is checked by validation (`Status`/here, the org used for the HMAC key) is not the same field that is actually acted upon (`blockTime`/here, `repository.full_name`), and an attacker can make the "checked" value pass while the "acted upon" value points somewhere else the check never covered.

**Concretely**, in a multi-org deployment (`config/secrets.*.yml` documents this exact pattern of multiple orgs each with a distinct `webhook_secret`, e.g. `somegithuborg` / `someothergithuborg`) [8](#0-7) :

- Before: org A's webhook secret authenticates only events genuinely originating from org A's repositories; org B's stacks are governed exclusively by org B's own GitHub App/webhook secret.
- After the attack: a party in possession of org A's `webhook_secret` (e.g., a malicious/compromised GitHub App admin for org A, or anyone who can trigger org A's webhook delivery, such as by owning a repo under org A) crafts a raw POST body where `repository.owner.login = "orgA"` (so `verify_signature` fetches and checks against org A's secret and succeeds) but `repository.full_name = "orgB/some-repo"` (a completely different, unrelated organization's repository also configured on the same Shipit instance). The HMAC check passes using org A's secret, yet `PushHandler`/PR handlers resolve and mutate org B's `Stack` — e.g. enqueuing `GithubSyncJob`, unarchiving a review stack, or capturing PR labels for org B's repository — even though the request was never signed by org B's app.

### Impact Explanation
This breaks a repository/organization authentication boundary: an entity trusted only for organization A's webhooks can forge events that create/mutate/unarchive stacks and trigger syncs (`sync_github`) for organization B's repositories on the same Shipit instance. Because `PushHandler#process` calls `stack.sync_github(...)` on stacks matched purely by the forged `full_name`, and syncs feed directly into deployable-commit tracking and, when `continuous_deployment` is enabled, automatic deploy triggering (`Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`) [9](#0-8) [10](#0-9) , this is a cross-repository write with the potential to influence unauthorized deploy scheduling for a repository/org the attacker was never authorized against — matching the "cross-repository writes" / "unauthorized deploy" Critical impact bucket in the rubric.

### Likelihood Explanation
Requires the specific, but explicitly documented and supported, multi-organization configuration (`github: { orgA: {...webhook_secret...}, orgB: {...webhook_secret...} }`) [8](#0-7) , and requires the attacker to know/possess org A's `webhook_secret` (e.g., as an org-A GitHub App admin, or by triggering webhooks legitimately from org A) while targeting org B's repositories on the shared instance. It does not require any Shipit session, `ApiClient` token, or GitHub write access to org B — only knowledge of org A's webhook secret and the ability to send an arbitrary POST to `/webhooks`.

### Recommendation
After successfully verifying the signature for `repository_owner`, additionally verify that the organization/owner used to select the verification key matches the owner segment of `repository.full_name` (and `organization.login`, if present) before dispatching to handlers. Reject the webhook (422) on mismatch, analogous to adding the missing "non-zero/matching" check the external report recommends for the `blockTime`/`Status` binding.

### Proof of Concept
1. Configure Shipit with two orgs, each with its own `webhook_secret`, per the documented multi-org schema (`config/secrets.development.shopify.yml`).
2. As holder of org A's `webhook_secret`, build a `push` payload where `repository.owner.login = "orgA"` and `repository.full_name = "orgB/target-repo"`, `ref = "refs/heads/<orgB-stack-branch>"`.
3. Compute `X-Hub-Signature` using org A's `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up org A's `GitHubApp` via `repository_owner` and the signature validates.
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "orgB/target-repo"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: ...)` on org B's stack, despite the request never being signed with org B's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
