### Title
Wallet accepts sign requests for `signed_message` from any paired device without validating the requester is an authorized cosigner - (File: wallet.js)

### Summary
In `handleMessageFromHub`'s `"sign"` case, a paired device can request that the local wallet sign an arbitrary `unsigned_unit` (including a `signed_message` object) for any local address it owns. The code that would confirm the requesting device is actually a legitimate cosigner of that address is explicitly commented out, and when the payload is a `signed_message` (rather than a real unit with `messages`), it is never routed through `signed_message.validateSignedMessage` or `network.handleOnlineJoint` before the local device is asked to sign it.

### Finding Description
The `"sign"` message handler validates only generic shape constraints (valid address, signing-path regex, non-empty authors array) before proceeding to request a signature: [1](#0-0) 

Crucially, the check that the sending device is actually a co-signer of the target address is disabled: [2](#0-1) 

For the branch where `objUnit.signed_message` is present, the code only checks that no unexpected top-level fields exist (`hasFieldsExcept(objUnit, ["signed_message", "authors", "version"])`) and then immediately emits `"signing_request"` — it never calls `signed_message.validateSignedMessage` to validate the internal structure/semantics of `signed_message`, unlike the path used when actually verifying an already-signed message: [3](#0-2) 

Compare this to `signed_message.js`'s dedicated validator, which enforces field whitelisting, author sorting, definition-hash consistency, and authentifier length/format — none of which is invoked prior to soliciting the signature: [4](#0-3) 

This is structurally analogous to the reported bug: a component signs a payload handed to it by an external, potentially adversarial party without first validating the payload's structure or the sender's authorization to request that specific signature.

### Impact Explanation
Any correspondent ("paired device") — not necessarily a genuine cosigner — can send a crafted `"sign"` request naming one of the victim's own addresses and an arbitrary `signed_message` payload. Because the cosigner-authorization check is disabled and the signed-message structure is unvalidated before the signing prompt/automatic signer is invoked, the attacker can obtain the victim's signature over content it fully controls. Since `signed_message` objects double as portable, verifiable proofs of address ownership/authorization (e.g., for exchange withdrawal confirmation or off-chain authorization flows), a forged signature obtained this way can be replayed to authorize actions the victim never intended, resulting in unauthorized use of funds/permissions tied to that address.

### Likelihood Explanation
Any device already paired with the victim (a normal, low-privilege relationship in Obyte, not requiring being a true multisig cosigner) can trigger this path simply by sending a `"sign"` justsaying/request over the hub. The commented-out authorization check shows this is a known relaxation of intended access control, elevating the likelihood that the attack surface is reachable in production wallets that automatically process signing requests (e.g., headless wallets).

### Recommendation
- Short term: Re-enable verification that the requesting device is a listed cosigner for `body.address` (the code for this exists but is commented out) before proceeding to request/produce a signature.
- Long term: Route the `signed_message` branch through `signed_message.validateSignedMessage` (or an equivalent structural/semantic validator) prior to emitting `"signing_request"`, exactly as is done for message verification, so a device never signs a payload whose structure and authorization have not been fully validated.

### Proof of Concept
1. Device B pairs with Device A (normal correspondent relationship, no multisig setup required).
2. Device B sends a `hub/message` with `subject: "sign"`, `body.address` = one of A's own addresses, a valid-looking `signing_path`, and `body.unsigned_unit = { authors: [{address: A_address, authentifiers: {...}}], signed_message: <attacker-chosen payload>, version: ... }`.
3. Because the cosigner check at [2](#0-1)  is disabled and no structural validation runs at [3](#0-2) , Device A proceeds to the `"signing_request"` flow and signs the attacker-supplied `signed_message`.
4. Device B now holds a validly signed message under A's address for content it fully controls, which it can present elsewhere as proof of authorization from A.
