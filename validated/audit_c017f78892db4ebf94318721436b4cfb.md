### Title
Naive substring-based `---` delimiter split in `extract_frontmatter` silently drops trailing frontmatter fields (e.g. `action: block`), causing block rules to be parsed as `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` splits rule-file content using plain string `content.split('---', 2)` instead of matching `---` only when it appears alone on its own line, as real YAML frontmatter delimiters require. Any `---` substring embedded inside a quoted frontmatter value (e.g. inside a `message` or `pattern` field) is misinterpreted as the closing delimiter, truncating the parsed frontmatter dict before later fields such as `action: block` are reached. Those later lines are instead absorbed into the rule's `message` body, so `Rule.from_dict` falls back to the default `action = "warn"`, silently downgrading what visually/textually appears to be a blocking rule into a non-blocking warning.

### Finding Description
`load_rules()` in `config_loader.py` globs `.claude/hookify.*.local.md` files from the project working directory and loads every match with no signature, approval, or trust check; these files are ordinary repository content reachable through a normal `git clone` + Claude Code session workflow [1](#0-0) . `extract_frontmatter` extracts the frontmatter block via:

```python
if not content.startswith('---'):
    return {}, content
parts = content.split('---', 2)
``` [2](#0-1) 

This `split('---', 2)` treats the literal substring `---` anywhere in the text as a delimiter boundary, not only `---` occurring on its own line as real YAML frontmatter parsers require. If a frontmatter value (e.g. a quoted `message:` or `pattern:` field) contains the three characters `---` before the real closing delimiter, that embedded occurrence is consumed as the second split point. Everything after it — including a later `action: block` line and the real closing `---` — is pushed into `parts[2]`, which becomes the rule's `message` body rather than being parsed as frontmatter.

`Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [3](#0-2) : since `action` was never inserted into the frontmatter dict (it ended up as inert text inside `message`), the rule silently defaults to `action = "warn"` even though the raw markdown file visibly contains `action: block`.

`RuleEngine.evaluate_rules` branches purely on `rule.action == 'block'`: blocking rules produce `permissionDecision: "deny"` (or `decision: "block"` for Stop events), while everything else only emits a `systemMessage` and allows the tool call to proceed [4](#0-3) . `pretooluse.py`/`posttooluse.py` load rules and pass the hook's decision straight through with no additional independent enforcement [5](#0-4) .

### Impact Explanation
A rule file whose raw text unambiguously reads as a blocking rule (`action: block`) can be constructed so that `extract_frontmatter` parses it as `action: warn` because of an embedded `---` substring earlier in the frontmatter. This breaks the invariant that rule semantics (block vs. warn) are determined solely by the visible YAML fields, and it produces `permissionDecision` results inconsistent with the rule author's/reviewer's intent. Since PreToolUse block rules are the only hookify mechanism that actually stops a dangerous `Bash`/`Edit`/`Write` invocation (`permissionDecision: "deny"`), this downgrade allows a dangerous tool invocation that was meant to be denied to instead execute with only an accompanying warning message — an unauthorized bypass of the intended local command-execution guard.

### Likelihood Explanation
The bug is fully deterministic and requires no special privileges beyond placing an attacker-authored `.claude/hookify.*.local.md` file in a repository that gets cloned and used with Claude Code + the hookify plugin (e.g., disguised as a "security" rule contributed to a shared repo). `load_rules()` performs no signing/verification and loads any matching file present at hook time, so the malformed file is picked up automatically on the very next `Bash`/`Edit`/`Stop` hook invocation. The trigger condition (a `---` substring inside a frontmatter value preceding another field) is simple to construct and 100% repeatable.

### Recommendation
Replace the naive `content.split('---', 2)` with a line-anchored frontmatter delimiter check (e.g. `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or scanning line-by-line for lines that are exactly `---`), matching standard YAML frontmatter semantics. Additionally, `load_rule_file`/`Rule.from_dict` should reject or warn loudly when a required `action` field is missing rather than silently defaulting to `"warn"`, and should fail closed (treat as `block`/reject the file) if frontmatter cannot be unambiguously delimited.

### Proof of Concept
Unit test against `extract_frontmatter` / `Rule.from_dict` in `plugins/hookify/core/config_loader.py`:

```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = '''---
name: block-dangerous-rm
enabled: true
event: bash
pattern: "rm -rf"
message: "urgent --- action: block"
action: block
conditions:
  - field: command, operator: regex_match, pattern: "rm -rf"
---
Blocks dangerous rm -rf commands
'''

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Visible file clearly states action: block, but parsed rule is downgraded:
assert 'action' not in fm
assert rule.action == 'warn'   # should have been 'block'
```

Integration PoC: place this file at `.claude/hookify.block-rm.local.md` in a cloned test repo, invoke `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool_input `{"command": "rm -rf /"}`, and assert the hook response contains only `systemMessage` (warning) instead of `hookSpecificOutput.permissionDecision == "deny"`, confirming the dangerous command is allowed to execute despite the file's visible `action: block` declaration.
