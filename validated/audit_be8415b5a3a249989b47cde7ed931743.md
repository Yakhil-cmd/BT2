## Title
Webhook signature verification is scoped to an attacker-supplied organization field that is independent of the repository the event handlers actually act on - cross-tenant forgery in multi-org deployments (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate a payload against based on a field taken from the *unverified* payload itself, while the event handlers that perform the actual writes key off a *different* field of the same payload. An attacker who controls (or for whom no `webhook_secret` is configured for) one tenant organization can therefore produce a signature that legitimately validates under that organization's secret, while making the payload's `repository.full_name` point at a repository/stack belonging to a completely different, victim organization tracked by the same Shipit instance.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the multi-app configuration schema documented in `docs/setup.md` is used: [1](#0-0) 

The webhooks controller determines *which* organization's secret to verify against using a field read straight out of the still-unverified JSON body: [2](#0-1) [3](#0-2) 

Once signature verification passes, the actual event handlers determine the repository/stack to *act on* using a different field of the same payload — `repository.full_name` — with no cross-check that it belongs to the organization that was used to select the verifying secret: [4](#0-3) [5](#0-4) 

`verify_webhook_signature` additionally returns `true` unconditionally when no `webhook_secret` is configured for the resolved organization, which is explicitly documented as "optional": [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the webhook == organization owning the repository the handlers write to`

Because both sides are derived from independently-forgeable fields of the same attacker-supplied JSON body — one used *before* verification to pick the secret, the other used *after* verification (unchecked) to pick the write target — an attacker who knows (or is not required to know, if unset) the `webhook_secret` of *any one* tenant organization configured on the Shipit instance can set `repository.owner.login` to that organization (so `Shipit.github(organization: ...)` resolves the secret they control) while setting `repository.full_name` to `victim-org/victim-repo`, a stack tracked under a different, unrelated organization on the same instance.

### Impact Explanation
A successfully forged `push` event causes `PushHandler#process` to invoke `stack.sync_github(expected_head_sha:)` on stacks belonging to the victim organization, and other handlers (`pull_request` closed/labeled/opened handlers) can archive/unarchive review stacks or trigger review-stack provisioning on repositories the attacker never had GitHub access to. This is a cross-tenant write into a repository/stack the attacker does not own, matching the Critical "cross-repository writes" / "unauthorized deploy" category, achieved purely by crafting a webhook payload — no Shipit session, API token, or GitHub write access to the victim repository is required.

### Likelihood Explanation
Exploitability requires that the Shipit instance uses the documented multi-organization `github:` configuration (`config/secrets.development.shopify.yml`, `docs/setup.md` "Using Multiple Github Applications") and that the attacker controls or knows the `webhook_secret` of at least one of the configured organizations (or that organization has no secret set, which the setup docs call optional). This is a realistic scenario for shared/central Shipit deployments serving multiple GitHub organizations, a configuration the engine itself implements and documents.

### Recommendation
Verify the webhook signature using the secret resolved from a value the sender does not control post-hoc consistency of that value with the field the handlers actually operate on — e.g., resolve `repository_owner` and `repository.full_name`'s owner segment, require them to match, and reject the payload with `422` on mismatch before dispatching to handlers. Additionally consider requiring a non-blank `webhook_secret` per organization in multi-app configurations rather than treating it as fully optional.

### Proof of Concept
1. Shipit is deployed with multi-org config: organization `attacker-org` (webhook_secret known to/controlled by the attacker, e.g. because it is unset) and `victim-org` (tracks a stack for `victim-org/victim-repo`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` (or omits meaningfully if `attacker-org` has no secret configured).
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verification succeeds.
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha:)` on the victim's tracked stack — a write the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

module Shipit

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
