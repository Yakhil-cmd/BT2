### Title
Webhook Signature Verified Against Attacker's Own Organization While `status` Handler Writes to Any Repository's Commits, Enabling CI-Status Forgery Across Tenants - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC signature against using a field taken directly from the *unverified* JSON payload (`repository.owner.login`). Once the signature check passes, the same raw payload is handed to event handlers that act on data (e.g. a commit `sha`) that is never cross-checked against the organization that was actually authenticated. In particular, `Handlers::StatusHandler` matches purely by `sha` across the entire `Commit` table with no repository/organization scoping at all. In a multi-tenant Shipit deployment (Shipit supports multiple GitHub organizations, each with its own independently configured `webhook_secret`), an attacker who legitimately controls one onboarded organization's GitHub App/webhook secret can forge a `status` webhook that authenticates as their own org but writes a fabricated commit status onto a commit belonging to a completely different tenant's repository/stack.

### Finding Description
`Shipit.github(organization:)` supports per-organization configuration (`secrets.github` keyed by org name), each with an independent `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` derives which organization's app/secret to use for HMAC validation directly from the incoming payload, before that payload has been verified at all: [2](#0-1) [3](#0-2) 

Once `verify_webhook_signature` succeeds (proving only that *some* recognized organization's secret produced this exact byte-for-byte body — an org the attacker themselves controls), the full raw payload is dispatched to handlers unmodified: [4](#0-3) 

`Handlers::StatusHandler` then writes a `Status` for **any** commit matching the given `sha`, with no scoping to the organization/repository that authenticated the request: [5](#0-4) 

This breaks the trust binding: `organization that authenticated the webhook (repository.owner.login checked against its own webhook_secret)` ≠ `commit/repository that the handler actually mutates (params.sha, unscoped)`. Other handlers (e.g. `PushHandler`, `Handler#stacks`) at least scope lookups by `repository.full_name`, which is likewise taken from the same unverified payload and never cross-checked against `repository.owner.login`/the authenticating organization — but `StatusHandler` has no scoping whatsoever, making it the most direct exploitation path.

### Impact Explanation
CI status is a security-relevant gate in Shipit: `MergeRequest` and deploy flows rely on `StatusChecker`/`required_statuses`/`blocking_statuses` derived from `shipit.yml` to decide whether commits are deployable or mergeable: [6](#0-5) [7](#0-6) 

By forging a `status` webhook signed with their own organization's legitimately-known secret, an attacker onboarded to only one tenant of a shared Shipit instance can inject a fabricated "success" status (with an attacker-chosen `context` matching another tenant's required CI check) onto a victim tenant's commit. This can cause `any_status_checks_failed?`/`any_status_checks_missing?` to return false for a commit whose real CI never passed, unblocking an unauthorized merge or deploy for a repository/organization the attacker has no legitimate relationship with. This satisfies the "unauthorized deploy, rollback, or merge" High/Critical impact criterion, achieved purely by knowledge of a secret belonging to the attacker's own (unprivileged, in relation to the victim) organization — no `ApiClient` token, GitHub App private key, or repository write access to the victim repo is required.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (supported and documented via `secrets.github` keyed by org) where the attacker administers/controls at least one onboarded organization's GitHub App or webhook configuration — a realistic scenario for shared/hosted Shipit instances serving multiple teams or customers. Given that, forging the payload is trivial: compute an HMAC-SHA1 over an arbitrary crafted JSON body using the attacker's own known secret, set `X-Github-Event: status`, and set `repository.owner.login` to the attacker's own org while setting `sha`/`context`/`state` to target any commit/context known to be tracked in the shared instance (commit SHAs and required-check contexts are discoverable via public GitHub history and public `shipit.yml`).

### Recommendation
Bind the verified webhook signature to the exact scope it authorizes:
1. After signature verification, re-derive the organization solely from the verified request (do not trust `repository.owner.login`/`organization.login` from the payload for any purpose beyond secret selection unless it is re-validated).
2. In every handler (especially `StatusHandler`), scope database lookups (`Commit.where(sha:...)`) to repositories/stacks that belong to the organization whose secret verified the signature — e.g., join through `Repository` and assert `repository.owner == repository_owner` used in `verify_signature`, rejecting the webhook otherwise.
3. Consider validating that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two organizations, e.g. `attacker-org` (attacker controls this GitHub App/webhook secret) and `victim-org` (unrelated tenant), per `lib/shipit.rb#github_app_config`.
2. Victim has a stack tracking commit `abc123...` on `victim-org/victim-repo`, requiring CI context `ci/required-check` per its `shipit.yml`.
3. Attacker crafts payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` selects `Shipit.github(organization: "attacker-org")` (per `repository_owner`), and the signature validates successfully because the attacker legitimately knows this org's secret.
6. `Handlers::StatusHandler#process` runs `Commit.where(sha: "abc123...")` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged "success" status onto the victim's commit, potentially unblocking an unauthorized merge/deploy for `victim-org/victim-repo`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
```
