### Title
CCMenuController ignores an `ApiClient`'s stack scope, allowing a stack-scoped token to read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The engine's normal enforcement of this scope lives in `Api::BaseController#stacks` / `#stack`, which restricts the queryable set of stacks to `current_api_client.stack_id` when the token is scoped:

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController`, however, overrides both the authentication method and never uses the scoped `stacks` helper. It resolves the stack directly from the URL parameter, bypassing the scope entirely:

```
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

The controller only declares `require_permission :read, :stack` [4](#0-3) , which calls `ApiClient#check_permissions!` — a check that only verifies the *permission name* (`read:stack`) is present, never that `current_api_client.stack_id` matches the requested `stack_id`:

```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [5](#0-4) 

The binding that is broken is: **the stack a token authorizes (`ApiClient#stack_id`) ≠ the stack it actually touches (`params[:stack_id]` resolved via unscoped `Stack.from_param!`)**. Any valid `ApiClient` token carrying `read:stack` permission — even one intentionally scoped to a single stack — can be replayed against `Api::CCMenuController#show` with an arbitrary `stack_id` to read deploy/rollback status for any stack in the installation, not just the one it was authorized for.

### Impact Explanation
This crosses the stack-authorization boundary that `Api::BaseController` otherwise enforces for every other API endpoint. A token intended (by its creator or by policy) to expose CI/deploy status for one stack only can be used to read the deploy status of any other stack, including stacks belonging to different, unrelated repositories/teams — an unauthorized disclosure of stack state across a scope boundary the token holder is not supposed to see.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has the `read:stack` permission (a common, low-privilege permission) and knowledge/guessing of another stack's `to_param` (owner/repo/environment, which are often predictable or discoverable via the UI). No write access, no GitHub credentials, and no session are required — only a token that is legitimately scoped to a different single stack.

### Recommendation
`Api::CCMenuController#stack` should reuse the same stack-scoping logic as `Api::BaseController#stack` (i.e., resolve through `stacks.from_param!` so that a stack-scoped `ApiClient` cannot resolve any `stack_id` other than the one it is bound to).

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A (`stack_id = A`) with permission `read:stack`.
2. Send `GET /api/stacks/:B/ccmenu.xml?token=<token-scoped-to-A>` where `B` is a different stack.
3. `authenticate_api_client` successfully authenticates the token via `ApiClient.authenticate(params[:token])`. `require_permission :read, :stack` passes because the token has `read:stack`. `stack` resolves via unscoped `Stack.from_param!(params[:stack_id])` to Stack B, and its deploy/rollback status is rendered — despite the token only being authorized for Stack A.
