### Title
Webhook signature verified against attacker-controlled `organization`/`repository.owner.login` while the handled event acts on an independently attacker-controlled `repository.full_name` — cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on a field read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`), while the actual event handler that runs afterwards resolves the target `Repository`/`Stack` from a *different* field of the same untrusted body (`repository.full_name`). In a multi-organization Shipit deployment these two fields are never cross-checked, so a party who legitimately knows the webhook secret for **one** onboarded organization can sign a payload whose `repository.full_name` points at **another** organization's repository, and Shipit will accept and process it as a genuine event for that other repository/stack.

### Finding Description
`Shipit.github(organization:)` picks a `GitHubApp` (and its `webhook_secret`) per organization in multi-tenant installs: [1](#0-0) 

`WebhooksController#verify_signature` derives the `organization` argument purely from the incoming JSON body: [2](#0-1) [3](#0-2) 

After the signature check passes, `create` dispatches the same raw payload to the event handler(s): [4](#0-3) 

Every handler resolves the actual `Repository`/`Stack` it operates on from a *different* field of the same payload, `repository.full_name`, with no comparison back to the organization used for signature verification: [5](#0-4) [6](#0-5) 

The equality that should hold but does not:
`organization used to select webhook_secret for signature verification == owner of the repository.full_name the handler actually acts on`

Both `repository.owner.login`/`organization.login` (used for verification) and `repository.full_name` (used for the actual database lookup via `Repository.from_github_repo_name`) are independent, attacker-supplied fields inside the same raw POST body. GitHub itself always keeps these consistent in real deliveries, but the controller never enforces that consistency itself — it trusts the body to be internally coherent. `Repository.from_github_repo_name` simply splits the string and looks up by owner/name, with no relation to the field used in `verify_signature`: [7](#0-6) 

This is the same class of bug as the SuperVault issue: `executeOperation()` correctly checks `msg.sender == lendingPool` (a strong, real authentication check) but then blindly trusts attacker-supplied `params` to decide what state-changing operation to perform and against which asset — the "who authenticated" and "what is acted upon" are bound to different, independently attacker-controlled inputs. Here, "who authenticated" (organization whose secret validated the signature) and "what is acted upon" (the repository whose Stack gets mutated) are similarly decoupled.

### Impact Explanation
In a multi-org Shipit configuration (`secrets.github` keyed by multiple organizations, i.e. `github_default_organization` present), any party who is an admin/owner of *one* onboarded organization — and therefore knows that organization's webhook secret, since they configured it on GitHub's side — can forge a webhook body whose `X-Github-Event`/JSON claims to originate from their own org (so `verify_signature` succeeds) but whose `repository.full_name` names a completely different tenant's repository. Handlers such as the `push` handler then act on that unrelated `Stack` (e.g. enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`), the `status` handler can inject fabricated CI statuses that unblock continuous deployment, and PR-lifecycle handlers can archive/create review stacks belonging to another tenant. This crosses a repository/authorization boundary between tenants without any privileged credential against the *victim* tenant, matching the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (the single-org/legacy config path in `github_default_organization` bypasses this by always using the same secret, which is a materially different, lower-impact case). It also requires the attacker to be a legitimate, but unprivileged-relative-to-other-tenants, admin of at least one onboarded GitHub organization — no GitHub App private key, `api_clients_secret`, or Shipit session is needed, only knowledge of a webhook secret they themselves set up for their own org, which is the normal, expected level of access for a tenant onboarding their own repos.

### Recommendation
After parsing the payload, verify that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` that handlers will subsequently use to resolve the target `Stack`, rejecting the request (422) on mismatch. Alternatively, have `verify_signature` and handler `repository_name` resolution derive the organization from the exact same single field, and additionally confirm that the resolved `Repository#owner` equals the authenticated organization before any handler executes.

### Proof of Concept
1. Shipit is deployed with multiple organizations configured, e.g. `secrets.github` containing both `attacker-org` and `victim-org`, each with its own `webhook_secret` (a normal multi-tenant onboarding setup).
2. The attacker is a legitimate admin of `attacker-org` and therefore knows `attacker-org`'s `webhook_secret` (they configured it when wiring up their own GitHub webhook).
3. Attacker crafts a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), successfully verifies the signature with the attacker's own known secret, and lets the request through: [2](#0-1) 
6. The dispatched push handler resolves the target repository from `repository.full_name = "victim-org/victim-repo"` via `Repository.from_github_repo_name`, unrelated to the organization that was actually authenticated, and enqueues a sync/deploy-affecting job against `victim-org`'s stack using attacker-controlled data (e.g. `expected_head_sha`).

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
