### Title
Permanent market freeze at the RAY value ceiling: accrual overflows `i128` before the borrow-index cap, bricking withdraw/repay/liquidate forever — (`common/src/rates/index.rs` / `contracts/pool/src/interest.rs`)

### Summary
Every mutation on a pool market runs `interest::global_sync` first, which calls `accrue_step` → `calculate_supplier_rewards`. That computes `borrowed.mul(new_borrow_index)` and `borrowed.mul(old_borrow_index)` — plain `Ray::mul` in `scaled_to_original`, which widens to `I256` and panics with `GenericError::MathOverflow` when the RAY-denominated debt value exceeds `i128::MAX`. The borrow index is nominally capped at `MAX_BORROW_INDEX_RAY` (10³⁶), but on a whale-sized book the *debt value* crosses the `i128` ceiling long before the index cap can engage. Once the book crosses that line, every subsequent accrual panics, and because every entrypoint accrues first, the market is frozen permanently: no `withdraw`, no `repay`, no `liquidate`/`seize_positions`, no `update_indexes`, no `recapitalize` — all suppliers' tokens are locked in the pool forever. ### Finding Description
- `update_borrow_index` clamps the index at `MAX_BORROW_INDEX_RAY`, which bounds the index itself but not the product `borrowed * index`. [4](#0-3) 
- `calculate_supplier_rewards` multiplies `borrowed` (scaled RAY shares) by the index via `Ray::mul`; `Ray::from_asset` upscales an 18-decimal token by 10⁹, so a 1-billion-unit book is ~10³⁶ raw RAY shares — and `i128::MAX` ≈ 1.7×10³⁸ is exceeded once the index passes ~170×. [1](#0-0) [5](#0-4) 
- The panic is unrecoverable: `global_sync` runs at the head of every flow (`Cache::load` → `global_sync` → mutate → guards → commit), so there is no verb that reduces `borrowed` without first re-running the overflowing computation. `repay`, `withdraw`, `seize_positions`, `net_settle`, `recapitalize`, and `update_indexes` all fail identically. The repo's own regression test proves the cliff: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` advances a 1-billion-unit, 18-decimal market at 98% utilization on the steep rate curve and shows `update_indexes`, `withdraw`, and `repay` all reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — "the index cap did not engage before the value overflow". [6](#0-5) 
- The same overflow exists in `update_supply_index` (`supplied.mul(old_index)`) and `supply_index_reward_shortfall`, so a supply-side whale book independently bricks accrual. [7](#0-6) 
- The threat model acknowledges the general bound ("finite RAY value capacity can be exhausted before the index ceiling"), but the concrete mechanism matters: the panic is fail-permanent, not fail-closed — time alone pushes the committed state past the cliff, and there is no admin or user call that walks it back. [8](#0-7) 

### Impact Explanation
Permanent freezing of all user funds in the affected market (an accepted impact class). Every supplier's claim and every unclaimed-yield revenue share becomes uncallable: exits, repayments, liquidations, bad-debt cleanup, and recapitalization all panic in the same accrual step before any state can change. The borrower's collateral in other markets also stays locked since positions cannot be touched. This is the on-chain analog of CVE-2022-21418's "hang or frequently repeatable crash" — but strictly worse than the source bug's recoverable server restart, because the panic condition is encoded in committed state and compounds.

### Likelihood Explanation
Requires a whale-scale book (order 10³⁶ raw RAY shares, e.g., ~1 billion whole units of an 18-decimal token, or proportionally less for lower-decimal/larger-index markets) at sustained high utilization on a steep interest-rate curve, plus caps set high enough to admit it (`supply_cap`/`borrow_cap` up to `i128::MAX/10^(27−d)` are admitted configurations). A single unprivileged address can set this up with `supply` + `borrow` at high utilization and then simply wait — interest accrual is permissionless and monotonic, so the attacker needs no further transaction, and competing liquidations cannot prevent it. This matches Medium severity: expensive setup, passive trigger, catastrophic but market-scoped impact. [9](#0-8) 

### Recommendation
- In `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall`, compute debt/supply values via a saturating or `Option`-returning multiply (as `mul_div_floor_saturating` already does for caps), and clamp the *value* at `i128::MAX` rather than letting `Ray::mul` panic — e.g., cap the borrow index at the highest index for which `borrowed * index` still fits, or short-circuit accrual once the value saturates so exits remain callable.
- Alternatively, gate `borrow`/`create_strategy` so `calculate_scaled_borrow`-time checks bound `borrowed * MAX_BORROW_INDEX_RAY` (and `supplied * MAX_SUPPLY_INDEX_RAY`) below `i128::MAX`, keeping the ceiling unreachable regardless of configured caps.
- Add a regression asserting that at any admitted cap/configuration the product stays below the `i128` ceiling, or that accrual degrades gracefully at the cliff.

### Proof of Concept
Reproduced by the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321`):
1. List `BIG18` (18 decimals, steep `xlm_curve`) with caps lifted to the admitted maximum; disable `max_utilization`.
2. Unprivileged `supply` of `10⁹` whole units (`1e36` raw RAY shares), then unprivileged `borrow` at 98% utilization.
3. Advance ledger time; `update_indexes` reverts with `MathOverflow` after the index passes ~170×, before `MAX_BORROW_INDEX_RAY`.
4. `withdraw` and `repay` revert with `MathOverflow` identically — the market is permanently frozen.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
