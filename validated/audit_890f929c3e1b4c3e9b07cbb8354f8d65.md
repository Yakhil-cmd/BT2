### Title
Cross-organization forgery of commit statuses via webhook signature/action binding mismatch enables unauthorized merges - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret is used to authenticate an inbound webhook based on a single field of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), while the event handler that actually performs the write (`StatusHandler`) never checks that field, nor any repository field at all. This breaks the equality "organization that authenticated == repository/commit that is written to": an attacker who legitimately controls (and knows the webhook secret of) any single GitHub organization configured in a multi-organization Shipit deployment can forge a `status` event that authenticates as their own org but creates a CI status on a commit belonging to a completely different organization's stack. That forged status can flip a pending `MergeRequest`'s CI-checks to green and cause Shipit to merge a pull request into a repository the attacker has no access to, using that other organization's own GitHub credentials.

### Finding Description
Shipit supports hosting several GitHub organizations from one instance, each with its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb` `github_app_config`, `test/dummy/config/secrets_double_github_app.yml`).

Webhook signature verification only uses the `repository.owner.login` (or `organization.login`) field of the raw, self-authenticated body to decide **which** organization's secret to check the signature against: [1](#0-0) [2](#0-1) 

Because the attacker chooses the entire raw body (and computes the HMAC themselves with their own org's known secret), this field can be set independently of any other field in the same payload — the signature covers the bytes, not any semantic binding between fields.

`StatusHandler`, the handler for the `status` event, does not consult `repository` (or the org) at all. It looks up commits **globally**, across every stack/organization in the whole Shipit instance, purely by `sha`, and writes a `Status` record for whichever commit matches: [3](#0-2) 

Creating that status record schedules CI/merge-queue processing: [4](#0-3) 

Which feeds directly into merge-queue gating: [5](#0-4) 

And into the job that actually merges pull requests on GitHub using the stack's own organization's GitHub App credentials: [6](#0-5) [7](#0-6) 

So the binding that should hold — "the organization whose secret authenticated this webhook" == "the repository/commit this webhook is allowed to affect" — is not enforced anywhere between `verify_signature` and `StatusHandler#process`. This is directly analogous to the `LiquidationLibrary` finding: a value used to authorize an action (the ICR / here, the authenticating organization) is stale/decoupled from the value actually mutated by the action (the redistributed debt / here, the target commit's stack and organization), letting the caller extract more than the protocol/authorization model intends.

### Impact Explanation
This is a cross-organization write and an unauthorized-merge primitive, matching the "Critical" bucket (cross-repository writes / an unauthorized deploy, rollback or merge). Any tenant organization onboarded to a shared, multi-organization Shipit deployment — who legitimately knows only their own `webhook_secret` — can:
1. Forge a `status` webhook, signed with their own org's secret, with `repository.owner.login` set to their own org (to pass `verify_signature`), but `sha` set to the head commit SHA of a pending `MergeRequest` belonging to a different organization's stack (SHAs are often discoverable via the target repo's public commit history / PR head SHA).
2. That forged event creates a `success` `Status` for that commit, which `MergeRequest#all_status_checks_passed?` treats as satisfied.
3. `ProcessMergeRequestsJob`/`MergeRequest#merge!` then merges the PR into the victim organization's repository using the victim organization's own GitHub App token — an unauthorized merge triggered entirely from another tenant's credentials.

Even outside a multi-tenant deployment, the underlying defect — a handler performing a database-wide, unscoped write based on attacker-controlled data with no re-validation against the authenticated organization/repository — is itself the root cause and the multi-org scenario is the cleanest way to demonstrate the boundary crossing without needing any of the excluded credentials (session, ApiClient token, webhook_secret of the victim, GitHub App private key, repository write access).

### Likelihood Explanation
Likelihood is bounded by needing a Shipit instance configured for multiple GitHub organizations (explicitly documented and supported, `docs/setup.md`), and by needing to guess/observe a target commit SHA in another tenant's repo (commonly public / observable via the PR's `head.sha`). No other secret, token, or privileged access is required — only the attacker's own legitimately-provisioned webhook secret for their own organization, which is standard operator-level access, not an elevated Shipit credential.

### Recommendation
- In `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`), scope the lookup by the repository/organization that was actually verified during signature verification, e.g. require and validate `repository.full_name`/`repository.owner.login` against the org used in `verify_signature`, and restrict `Commit.where(sha:)` to `stacks` under that repository.
- In `WebhooksController#verify_signature`, after selecting the organization by `repository_owner`, re-derive and pass down a canonical, verified repository/organization identity to every handler, and have `Webhooks::Handlers::Handler#stacks` (and any handler bypassing it) reject payloads whose repository does not belong to the verified organization.
- Consider signing/binding the organization identity into a value that participates in the HMAC verification path itself (e.g., verifying `repository.full_name` prefix matches the organization key used to select the secret) rather than trusting an independently-controlled field for authorization only.

### Proof of Concept
Preconditions: Shipit instance configured with two organizations, `OrgA` and `OrgB` (per `docs/setup.md` "Using Multiple Github Applications"). Attacker operates/administers `OrgA` and therefore legitimately knows `OrgA`'s `webhook_secret`. `OrgB` has a stack with a pending `MergeRequest` whose head commit SHA is `abc123...` (observable on GitHub).

1. Attacker builds a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "abc123...",              // OrgB's PR head commit
  "state": "success",
  "context": "ci/required-check",
  "created_at": "2026-09-02T00:00:00Z"
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
3. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature verifies successfully (attacker legitimately knows this secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123...")` — with no reference to `OrgA` or the verified organization at all — finds the commit belonging to `OrgB`'s stack, and calls `commit.create_status_from_github!(params)` — `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`.
5. The new `Status` record (`state: success`) is created for `OrgB`'s commit, triggering `schedule_continuous_delivery` / merge-queue processing (`app/models/shipit/status.rb:18-19`, `app/models/shipit/merge_request.rb:193-197`).
6. `ProcessMergeRequestsJob` observes `all_status_checks_passed?` now true and calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(...)` using `OrgB`'s own GitHub App credentials — merging a PR in `OrgB`'s repository that the attacker (a member only of `OrgA`) has no authorization over (`app/models/shipit/merge_request.rb:164-176`, `app/jobs/shipit/process_merge_requests_job.rb:21-31`).

I was not able to execute this end-to-end in a live environment (no filesystem/terminal access), so I could not empirically confirm side effects such as exact CI-check naming requirements from `StatusChecker`/`cached_deploy_spec` (e.g., whether the forged `context` must exactly match a `ci.require` entry) — this would need to be validated by a background agent with an actual Shipit instance and a multi-org test fixture such as `test/dummy/config/secrets_double_github_app.yml`.

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
