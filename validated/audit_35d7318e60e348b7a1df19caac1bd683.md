### Title
Accrual overflow permanently freezes high-utilization markets before the borrow-index cap - (File: common/src/rates/simulate.rs)

### Summary
An unprivileged borrower can grow a valid, very large market position until scaled-debt valuation exceeds `i128::MAX`. After that point, every operation that accrues the market reverts, permanently preventing repayment, withdrawal, liquidation, recapitalization, and index updates. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first multiplies total scaled debt and supply by their current indexes, then calculates utilization and interest. [3](#0-2)  `scaled_to_original` performs a checked `scaled * index` multiplication, so a representable scaled balance can become unrepresentable as the index grows. [4](#0-3)  `update_borrow_index` caps the index itself, but `calculate_supplier_rewards` subsequently multiplies the unchanged scaled debt by that index; the cap therefore does not bound the resulting RAY-denominated debt value. [5](#0-4) [6](#0-5) 

All ordinary pool mutation legs load an interest-synced cache before applying the requested mutation. [7](#0-6)  The public controller exposes the reachable sequence through `supply`, `borrow`, `withdraw`, `repay`, and `liquidate`. [8](#0-7)  Once the next accrual would make `borrowed * borrow_index` overflow, the transaction reverts before committing a new timestamp, so later calls repeat the same failing calculation. [9](#0-8) 

### Impact Explanation
This permanently freezes all funds and debt accounting in the affected `(hub_id, asset)` market. [10](#0-9)  Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce unsafe debt, and index synchronization cannot recover because each path executes the overflowing accrual first. [11](#0-10) [12](#0-11)  The repository’s long-horizon test reaches `MathOverflow` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, then confirms that even a one-unit withdrawal and a minimal repayment fail with the same error. [13](#0-12) 

### Likelihood Explanation
The attack requires a market whose valid caps and token supply allow RAY-scaled totals near the `i128` domain boundary, plus sustained high utilization so interest growth pushes `borrowed * borrow_index` across that boundary. [14](#0-13)  No malformed storage, privileged call, cap bypass, oracle manipulation, or failed invariant is required: ordinary `supply`, `borrow`, and later `update_indexes` calls create the state. [15](#0-14) [16](#0-15)  The capital requirement limits practical exploitability on markets with conservative caps, so the finding is High rather than Critical. [17](#0-16) 

### Recommendation
Enforce a market-wide bound on RAY-denominated supply and debt values before minting positions, accounting for the maximum possible index rather than only the configured token-unit caps. [18](#0-17)  Accrual should also calculate `borrowed * new_borrow_index` and `supplied * new_supply_index` in widened arithmetic or clamp the index to the largest value whose product remains representable before committing it. [6](#0-5)  A recovery path should permit debt reduction or withdrawal without first evaluating an overflowing accrued total, or governance should receive a bounded emergency accrual that safely stops growth at the representable-value ceiling. [7](#0-6) 

### Proof of Concept
The checked-in test constructs an 18-decimal market, supplies one billion whole tokens, supplies collateral, and borrows 98% of the supplied market through the normal controller paths. [19](#0-18) 

```rust
supply(attacker, supply_account, spoke_id, [(BIG18, 1_000_000_000 * 10^18)]);
supply(attacker, borrow_account, spoke_id, [(COL, sufficient_collateral)]);
borrow(attacker, borrow_account, [(BIG18, 980_000_000 * 10^18)], Some(attacker));

// As ledger time advances:
update_indexes([BIG18]); // eventually panics with MathOverflow
withdraw(supplier, supply_account, [(BIG18, 1)], None); // MathOverflow
repay(anyone, borrow_account, [(BIG18, 1)]); // MathOverflow
```

The test then observes `MathOverflow` before `MAX_BORROW_INDEX_RAY` is reached and verifies that both withdrawal and repayment remain blocked by the same accrual failure. [20](#0-19)

    t.supply_raw(BOB, "BIG18", principal);

    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

**File:** docs/reference/formulas.md (L407-417)
```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```
