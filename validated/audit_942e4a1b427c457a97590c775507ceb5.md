### Title
Unhandled `throw` on unvalidated "definition template" re-evaluation causes node crash (partial DoS) - ([File: definition.js])

### Summary
`definition.js` validates address/asset definitions in two separate passes: `validateDefinition()` (structural/type validation) and `validateAuthentifiers()` (actual signature/authentifier evaluation). Both implement their own private `evaluate()` closure and both handle the `'definition template'` op independently by re-querying the DB for the referenced `definition_template` unit. The two implementations diverge in how they treat an unexpected row count from that query: `validateDefinition()` degrades gracefully with a normal validation error, while `validateAuthentifiers()`'s `evaluate()` assumes the invariant "exactly one template row" always holds and calls `throw Error(...)` if it does not. This is the same bug class as the Avo report: code trusts a previously-"validated" piece of user-controlled structure and performs an unsafe, unchecked action on it a second time, and an unexpected value crashes the application (CWE-20 / CWE-470 style unsafe assumption leading to DoS).

### Finding Description
`validateDefinition()`'s `'definition template'` handler fully validates the op's arguments (`unit` must be valid base64 hash, `params` must be a non-empty object of strings/numbers) and, when querying for the referenced template, treats a bad row count as a soft validation error: [1](#0-0) 

But `validateAuthentifiers()` contains its own, independent `evaluate()` closure that re-implements the same `'definition template'` case without re-validating `unit`/`params` and, crucially, on an unexpected row count it does `throw Error("not 1 template")` instead of returning an error through the callback: [2](#0-1) 

`validateAuthentifiers()` does call `validateDefinition()` first and only proceeds to its own `evaluate()` if that succeeds: [3](#0-2) 

However, these are two separate asynchronous DB round-trips (`conn.query(...)` executed twice, once in each `evaluate()`), not one atomic check. The row count depends on `main_chain_index<=? AND is_stable=1` for the referenced template unit: [4](#0-3) [5](#0-4) 

Because validation of a posted unit's authors/definitions is asynchronous and interleaved with other DB activity (unit processing, catchup, other pending validations sharing the same connection/queue), nothing guarantees the second query returns the same row count as the first at the exact moment `validateAuthentifiers()`'s own `evaluate()` runs. If the two reads observe different states (e.g., the template-defining unit's stability/mci bookkeeping changes between the two queries), `validateAuthentifiers()` reaches the `throw Error("not 1 template")` inside an asynchronous DB callback. An exception thrown from inside an async callback is not caught by any surrounding `try/catch` in the caller chain and will propagate as an uncaught exception, crashing the Node.js process that is validating the unit.

This is reachable by any unprivileged unit poster: anyone can construct an address definition containing `['definition template', [unit, params]]`, referencing an already-existing `definition_template` unit, and use that address as an author of a new unit (or as an inner/co-signed address, or in an asset spending condition). Every node that validates the offending unit re-runs `validateAuthentifiers()` and is exposed to the same divergence.

### Impact Explanation
An uncaught `throw` in the unit/asset-condition validation path crashes the validating node process. Since every full node (and asset-issuing/asset-transfer participants relying on that address) performs this same validation when the offending unit propagates, a single crafted unit can be used to attempt to crash multiple full nodes that process it — a network-wide partial denial of service on unit validation/confirmation, matching the "node unable to confirm new units" / "node disagreement/crash" impact class.

### Likelihood Explanation
Likelihood is moderate: the two DB reads in `validateDefinition()` and `validateAuthentifiers()`'s private `evaluate()` are not part of a single atomic transaction/snapshot; they are independent async queries against the same underlying template unit's stability/mci flags. Triggering the divergence reliably (e.g., timing the submission of the offending unit precisely at the boundary of the referenced template becoming/losing stability, or interleaving with a reorg/catchup) requires some precision but is fully within the capability of an unprivileged unit poster who fully controls the timing and content of their own unit and of the address definition it references.

### Recommendation
Make `validateAuthentifiers()`'s `'definition template'` handling in `definition.js` (lines 802-819) consistent with `validateDefinition()`: treat `rows.length !== 1` as a normal validation failure returned through the callback (e.g., `cb2(false)`), never as a `throw`. More generally, remove the duplicate/independent re-implementation of definition-tree evaluation logic between `validateDefinition()` and `validateAuthentifiers()`, or ensure both read the template row inside the same DB snapshot/transaction so that assumptions validated in one pass cannot silently diverge from what the second pass observes.

### Proof of Concept
1. Attacker creates and gets stable a `definition_template` unit `U` with a valid template structure and posts an address definition referencing it: `['definition template', [U, {param1: 'x'}]]` as (part of) the definition for address `A`.
2. Attacker crafts a new unit authored by/spending from `A` (or uses `A` as a co-signer/asset-condition address) and broadcasts it right as `U`'s stability/mci bookkeeping is in flux (e.g., timed near main-chain advancement or during catchup on a light/full node).
3. When a node validates the new unit, `validateAuthentifiers()` first calls `validateDefinition()` (line 1454), which queries and validates the template using the state visible at that instant.
4. `validateAuthentifiers()`'s own `evaluate()` (line 802) re-queries the same template row later in the same validation flow; if the state observed differs (row count != 1), it executes `throw Error("not 1 template")` (line 812) inside the async DB callback, which is uncaught and crashes the node process.
