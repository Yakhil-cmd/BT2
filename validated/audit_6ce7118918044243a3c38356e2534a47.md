This confirms the exact bug described. The `provision?` method's operator precedence causes `review_stacks_enabled` to only gate the `allow_all?` branch:

    repository.provisioning_behavior_allow_all? ||

```

### Title
`review_stacks_enabled` flag bypassed by operator precedence in `provision?` allowing unapproved fork ref provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled && allow_all?` with `||` against the `allow_with_label?`/`prevent_with_label?` clauses, so `review_stacks_enabled` is not required when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`. An attacker who opens a PR with the configured label can get a `ReviewStack` created and queued for provisioning even though review stacks are disabled for the repository, with the stack's `branch` set to the attacker's own fork ref.

### Finding Description
The intended binding is: a `ReviewStack` should only ever be created/provisioned when `repository.review_stacks_enabled == true`, regardless of `provisioning_behavior`. The actual code:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as `(A && B) || C || D`, not `A && (B || C || D)`. Consequently `review_stacks_enabled` gates only the `allow_all?` term; the `allow_with_label?`/`prevent_with_label?` terms are evaluated independent of `review_stacks_enabled`.

Attacker request: a PR opened by any GitHub user against a repository with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-me'`, where the PR carries the label `deploy-me` and `pull_request.head.ref` points at the attacker's own fork branch. `respond_to_pull_request_opened?` calls `provision?`, which returns `true` via the `allow_with_label?` clause. `OpenedHandler#process` then calls `ReviewStackAdapter#find_or_create!` → `create!`, which builds the stack with `branch: params.pull_request.head.ref` [4](#0-3)  and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [5](#0-4) . The queue worker later checks out that branch and invokes `stack.provision` if `stack.provisioner.provision?` [3](#0-2) , which executes deploy-spec-defined steps from the attacker's ref.

No existing guard intercepts this: webhook signature verification only authenticates that the payload came from GitHub for *some* repo (not that review stacks are enabled), `ExplicitParameters` only validates payload shape, and there is no separate check of `review_stacks_enabled` anywhere else in `OpenedHandler`, `ReviewStackAdapter`, or `ReviewStackProvisioningQueue`.

### Impact Explanation
Any GitHub user able to open a PR against a repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) but `review_stacks_enabled: false` can force creation and provisioning of a `ReviewStack` bound to their own fork branch. The resulting `shipit.yml`/deploy spec is read from that attacker-controlled ref via `DeploySpec::FileSystem`, and task steps defined there are ultimately executed on the deploy host through `Command`/`PTY.spawn`. This is repeatable against any repository with this exact configuration and constitutes Critical RCE on the deploy host from an untrusted, unapproved ref.

### Likelihood Explanation
Requires the operator to have set `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while leaving `review_stacks_enabled` false — a plausible misconfiguration since the UI/docs suggest `review_stacks_enabled` is the master switch. No secrets, tokens, or privileged roles are needed; the attacker only needs to open a PR with the configured label from their own fork, which is available to any GitHub user with push access to a fork.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
