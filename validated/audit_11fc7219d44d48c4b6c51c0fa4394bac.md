### Title
Webhook signature is verified against `repository.owner.login`, but the handler resolves the target `Stack` from `repository.full_name` with no cross-check, allowing a payload signed by one organization's `webhook_secret` to sync another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC using `params.dig('repository', 'owner', 'login')`, while `Handler#repository_name` (used to load the target `Repository`/`Stack`) reads `payload.dig('repository', 'full_name')` independently. Since nothing compares these two values, an attacker who genuinely owns and administers `AttackerOrg` (and thus legitimately knows its `webhook_secret`) can sign a payload whose `repository.owner.login` is `AttackerOrg` but whose `repository.full_name` is `VictimOrg/victim-repo`, causing the signature check to pass against `AttackerOrg` while `PushHandler` acts on `VictimOrg`'s stack.

### Finding Description
The claimed binding is: `organization_whose_webhook_secret_verified(request) == organization_named_in(repository.full_name)`.

Tracing the code:
- `WebhooksController#verify_signature` at [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`.
- `repository_owner` is defined as [2](#0-1) , reading only `params.dig('repository', 'owner', 'login')`.
- `GitHubApp#verify_webhook_signature` at [3](#0-2)  verifies the raw body HMAC using the `webhook_secret` configured for whichever organization `Shipit.github(organization:)` resolved — i.e., `AttackerOrg`'s secret if `repository.owner.login == "AttackerOrg"`. This step only proves the request was signed by the org whose `owner.login` was declared, not the org whose repo is actually being processed.
- After signature verification passes, `WebhooksController#create` parses the same raw body a second time and dispatches to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks` and `Handler#repository_name` at [5](#0-4)  load `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login`, under full attacker control within the same request body.
- `PushHandler#process` at [6](#0-5)  then does `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`, operating on whatever `Repository`/`Stack` was found via `full_name`.
- `Repository.from_github_repo_name` at [7](#0-6)  does a plain `find_by(owner:, name:)` lookup with no relation whatsoever to which `GitHubApp`/secret authenticated the incoming request.

No code path reconciles `repository.owner.login` (used for signature/secret selection) with `repository.full_name` (used for stack resolution). `drop_unhandled_event`, `ExplicitParameters` (`PushHandler` only requires `ref`/`after`, not `repository.*`), and `Repository`'s format validators do not perform any cross-org binding check — they validate format/uniqueness at write time, not consistency between these two payload fields at request time.

Attacker's exact request: an unprivileged operator who legitimately administers `AttackerOrg` (and thus knows `AttackerOrg`'s real `webhook_secret`, e.g. via GitHub's org webhook settings UI) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, raw_body)>
Body: {"repository":{"owner":{"login":"AttackerOrg"},"full_name":"VictimOrg/victim-repo"},"ref":"refs/heads/master","after":"<victim_sha>"}
```
`verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, verifies the signature successfully with the attacker's own known secret, and the request proceeds. `PushHandler` then resolves `VictimOrg/victim-repo`'s onboarded `Stack` (assuming it's already onboarded in this Shipit instance) via `full_name` and calls `sync_github`, triggering `GithubSyncJob`/deploy sync activity against a repository the attacker never authenticated for.

### Impact Explanation
This lets a request authenticated with `AttackerOrg`'s credentials mutate/act on `VictimOrg`'s `Stack` state (forcing a GitHub sync, which can trigger CI status checks, deploy eligibility recalculation, and downstream automation depending on stack configuration) — a cross-tenant write against a repository/organization the attacker never proved control over. This matches the Critical category "a payload for one repository mutating another's stack." It's repeatable for any `VictimOrg/repo` combination already onboarded in the same Shipit instance, as long as the attacker owns any single onboarded org to obtain a valid secret to sign with. Blast radius spans every stack onboarded across every organization sharing the same Shipit deployment.

### Likelihood Explanation
Preconditions: attacker must have their own onboarded GitHub organization configured in `Shipit.github_apps`/`Shipit.github` config (a legitimate, low-cost precondition per the rules — "attacker legitimately administers their own onboarded GitHub organization"), and the victim org/repo/stack must already be onboarded in the same Shipit instance. No Shipit secrets, sessions, or elevated GitHub permissions are required beyond the attacker's own org's `webhook_secret`, which they legitimately possess. The attack is a single crafted HTTP POST, fully repeatable and scriptable.

### Recommendation
Bind the two values before dispatching to handlers: after `verify_signature` succeeds, derive the target repository strictly from the same `repository.owner.login` used for authentication (e.g., require `repository.full_name.split('/').first == repository_owner`, or better, pass the already-verified `repository_owner` into the handler and have `Repository.from_github_repo_name`/`stacks` reject repositories whose owner doesn't match the authenticated organization). Reject the webhook (422) on mismatch.

### Proof of Concept
Minitest `ActionDispatch::IntegrationTest` (conceptual, would live under `test/controllers/webhooks_controller_test.rb`, excluded from scope here but describable):
1. Configure `Shipit.github_apps` (or stub `Shipit.github`) with two orgs, `AttackerOrg` (secret `secretA`) and `VictimOrg` (secret `secretB`).
2. Create a `Stack` for `VictimOrg/victim-repo` with `branch: 'master'`.
3. Build body: `{"repository":{"owner":{"login":"AttackerOrg"},"full_name":"VictimOrg/victim-repo"},"ref":"refs/heads/master","after":"deadbeef"}`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'secretA', body)`.
5. POST to `/webhooks` with `X-Github-Event: push` and that signature.
6. Assert response is `200 OK` (signature verified against `AttackerOrg`'s secret only — assert `repository_owner == "AttackerOrg"` while `full_name.split('/').first == "VictimOrg"`, i.e. the equality is broken both before and after the request).
7. Assert `GithubSyncJob` (or `stack.sync_github`) was enqueued/invoked with `VictimOrg`'s `stack.id`, proving cross-tenant mutation despite authentication only covering `AttackerOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
