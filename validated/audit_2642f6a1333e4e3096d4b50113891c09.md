### Title
Unchecked intermediate `u128` overflow in `checked_mul().expect()` reward-scaling formula can panic the bank during epoch-boundary reward redemption - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
`redeem_stake_rewards`'s `AlpenglowEpochType::Tower` (and `MigrationEpoch`) branches scale a stake's accumulated `tower_points` by `point_value.rewards` before dividing by `point_value.points`, using `.checked_mul(...).expect("Rewards intermediate calculation should fit within u128")` [1](#0-0) . As with the `quantize` overflow class in the external report, the formula performs the multiplication step before the division step instead of reordering/scaling to keep the intermediate value bounded, so a sufficiently large `tower_points * point_value.rewards` product panics via `.expect()` instead of returning a graceful error.

### Finding Description
`tower_points` is accumulated per stake account in `tower_epoch_credits_iter`/`calculate_stake_points_for_tower` as a straight (unchecked-overflow-safe but otherwise unbounded) sum of `stake_amount * earned_credits` across every retained epoch-credit entry in the associated vote account that the stake has not yet observed [2](#0-1) . Because `calc_earned_credits` only advances `new_credits_observed`, a stake account whose `credits_observed` lags far behind the vote account's current credits (e.g., a delegation that was deactivated and later reactivated/redelegated, or otherwise skipped several epochs of automatic redemption) will sum contributions from every epoch entry still present in the vote account's history window, each contribution bounded by `stake_amount (up to u64::MAX) * credits_per_epoch`.

This `tower_points` value (`u128`) is then fed into the reward-scaling formula:
```
tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
``` [1](#0-0) 

Mathematically the final result (after division by `point_value.points`, which is the sum of points across the whole network and is therefore comparable in magnitude to `tower_points`) fits well within `u64`/`u128` bounds - the network-wide reward pool per epoch is orders of magnitude smaller than `u128::MAX`. But the code computes the numerator `tower_points * point_value.rewards` in full before dividing, exactly the same "intermediate overflow despite bounded final result" pattern described in the `quantize` report. If `tower_points` is large (accumulated stake Γ— credits Γ— many skipped epochs of history) and `point_value.rewards` (total per-epoch inflation reward pool, itself attacker-uncontrolled but large on a live network) multiply past `u128::MAX` (β‰ˆ3.4Γ—10^38), the `.expect()` call panics.

An identical unchecked-intermediate-overflow pattern recurs in the `MigrationEpoch` branch, which performs `checked_mul` then `checked_div` then a further `checked_mul`/`checked_div`, each of which uses `.unwrap()`/`.expect()` rather than returning an error [3](#0-2) . This particular branch is Alpenglow-migration-specific and is explicitly out of scope per the SECURITY.md exclusions on Alpenglow/votor plumbing, so the primary in-scope finding is the `Tower` branch, which is the reward path used on the current (non-Alpenglow) network.

### Impact Explanation
`redeem_stake_rewards` is invoked deterministically for every active stake delegation during epoch-boundary reward calculation/redemption (`calculate_stake_rewards_and_commissions` β†’ `redeem_delegation_rewards`) [4](#0-3) . Because this computation runs identically on every validator processing the same bank/epoch boundary, a panic here is not a single-node crash but a consensus-breaking, cluster-wide halt at the epoch boundary - matching the "epoch-boundary halt" impact category. Unlike a normal instruction-level panic that would only abort one transaction, this fires inside core bank/runtime reward-distribution code with no `Result`-based recovery at the call site relevant to this `.expect()`.

### Likelihood Explanation
Reaching this requires (a) a very large stake delegation and (b) a large gap between the stake's `credits_observed` and the vote account's current credits, spanning many retained epoch-credit history entries (e.g., via deactivation/reactivation cycles, which any stake authority can perform without special privilege). Both stake size and epoch-credit skew are within the control of an ordinary, unprivileged stake-account owner. Whether realistic economic parameters (current circulating supply, current per-epoch inflation pool, and the vote program's actual epoch-credits retention window) are sufficient to push the product past `u128::MAX` could not be fully confirmed in this pass - I was unable to retrieve the concrete value of `MAX_EPOCH_CREDITS_HISTORY`/the vote program's epoch-credits retention constant from the index to compute an exact bound, so the precision of the required stake size versus current network parameters remains unverified. This is the key open item that would need further confirmation (e.g., via a background Devin session with full repository access) before treating this as a fully proven, currently-exploitable overflow rather than a defense-in-depth gap that is only reachable at extreme (but not per-type-bound-impossible) parameter values.

### Recommendation
Refactor the Tower/MigrationEpoch reward-scaling formulas to avoid computing the full `tower_points * point_value.rewards` product before dividing - e.g., divide first where safe, use wider intermediate arithmetic (e.g., 256-bit via `u128` pairs or a manual mul-div-without-overflow routine), or clamp/saturate instead of `.expect()`/`.unwrap()` panicking, mirroring the recommended fix for the `quantize` overflow (compute bounded sub-terms before combining). Additionally, add property/fuzz tests that exercise stakes with `credits_observed` far behind the vote account's credits combined with large stake amounts and large `point_value.rewards`, to confirm whether the panic is reachable under real epoch-credits retention and inflation-pool bounds.

### Proof of Concept
Not fully constructible without confirming the vote program's exact epoch-credits retention window and current mainnet-scale `point_value.rewards`/`point_value.points` bounds (unresolved research item above). Conceptually: create a large stake delegation, deactivate it, allow the associated vote account to accumulate many epochs of credits while the stake remains deactivated (so `credits_observed` is not advanced), then reactivate/redelegate the stake so it becomes eligible for `Tower` reward redemption; at the next epoch boundary, `calculate_stake_points_for_tower` sums the skipped epochs' `stake_amount * earned_credits` into `tower_points`, and the subsequent `tower_points.checked_mul(point_value.rewards).expect(...)` in `redeem_stake_rewards` panics if the product exceeds `u128::MAX`.
