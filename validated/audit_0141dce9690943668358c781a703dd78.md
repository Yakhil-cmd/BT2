### Title
AA bounce path silently locks trigger funds forever when returning a restricted asset fails - ([File: aa_composer.js])

### Summary
The Sherlock finding is about `SellOrderProcessor`/`BuyOrderIssuer` never validating the `recipient` field before attempting a final token transfer; if the recipient is blocklisted or `address(0)`, the transfer reverts and there is no fallback path, so protocol funds become permanently stuck with no way to distribute or refund them. The `ocore` analog exists in `aa_composer.js`'s AA (Autonomous Agent) trigger-handling / bounce logic, where an AA that receives a restricted asset (one with a `transfer_condition`) and fails to construct a valid response can also fail its fallback ("bounce") path, resulting in the trigger's funds being absorbed into the AA's balance with **no response unit posted at all** and no way to ever release them.

### Finding Description
When a trigger unit sends funds (base bytes and/or a custom asset) to an AA, `handleTrigger()` first tries to build a normal response via `sendUnit(messages)`. If any step fails (bad address, unmet `transfer_condition`, insufficient asset balance, etc.), `bounce(err)` is called to refund the trigger's payment back to `trigger.address` for every asset in `trigger.outputs`: [1](#0-0) 

The `bounce()` function assumes this refund payment will always succeed - it simply loops over `trigger.outputs` and calls `sendUnit(messages)` again. But `sendUnit()` performs the same asset-condition checks as the primary path, including evaluating the asset's `transfer_condition` during `validateAndSaveUnit()`: [2](#0-1) 

If the asset being returned has a `transfer_condition` (set arbitrarily by the asset's *definer*, not the AA or the trigger sender) that rejects payments to `trigger.address` - the exact recipient the bounce is forced to use - then `sendUnit()` inside the bounce call fails again and calls `bounce(err)` a second time. Because `bBouncing` is already `true` at that point, the function short-circuits to `finish(null)`: [3](#0-2) 

`finish(null)` for a primary (non-secondary) trigger does not throw or emit any error to the network; it simply records an empty/failed response with no `objResponseUnit`: [4](#0-3) 

Crucially, the trigger unit's payment to the AA address was already validated and committed to the DAG independently of anything the AA does afterward - `getTrigger()` reads the payment outputs addressed to the AA directly from the already-stable trigger unit: [5](#0-4) 

So once those funds are credited to the AA's balance, the *only* way to move them out is via a future AA-authored payment message that must again satisfy the same `transfer_condition`. If that condition can never be satisfied for any address the AA is capable of computing (e.g., it always requires cosigning by the asset definer, or a specific allow-list that excludes `trigger.address`), the funds are permanently frozen inside the AA with no recipient-validation performed up front and no automatic recovery mechanism - directly analogous to the Solidity issue where an unchecked `recipient` causes an unrecoverable revert deep in the fund-distribution path.

### Impact Explanation
An attacker (or an asset issuer colluding with an attacker) can define a custom asset with a `transfer_condition` designed to reject the AA's own bounce-refund address, then send that asset to any AA that doesn't explicitly whitelist/validate the asset before accepting it. Any legitimate trigger that causes the AA to attempt to forward, refund, or otherwise pay out that asset back to `trigger.address` will fail both the primary response and the bounce fallback, permanently locking that value inside the AA's balance. This matches the "protocol fund lock" severity of the original finding - funds are not spendable ever again through the normal trigger flow, and the loss is silent (no error unit, no bounce record with a non-null `response_unit`).

### Likelihood Explanation
Any address can define an arbitrary asset with a `transfer_condition` (Obyte assets are fully permissionless to create), and any user can send that asset to any AA as part of a trigger, satisfying the "reachable from a single posted unit/trigger" requirement. AAs that don't defensively check `objAsset.transfer_condition` before accepting/handling a foreign asset (which is the common case in ordinary payment-forwarding AAs, as seen in the shipped samples like `forwarder_of_bytes.oscript`/`send_all.oscript`) are exposed whenever a griefer/attacker crafts such an asset and a triggers a scenario in which both the primary and bounce payment attempt to pay it back to the trigger's own address.

### Recommendation
Before crediting non-base asset amounts to an AA's spendable/response logic in `aa_composer.js`, the composer (or a documentation-level requirement enforced by validation) should check whether the asset carries a `transfer_condition`/`issue_condition` and, if so, either reject the trigger outright (bounce immediately without attempting to hold or re-send the asset) or explicitly test-evaluate the condition for `trigger.address` before crediting the AA's balance, so the guaranteed-fallback bounce path can never itself fail. Alternatively, `bounce()` could detect a second failure and emit a distinguishable "unrecoverable/frozen funds" response so downstream tooling and asset holders are aware that these particular units are stuck, rather than silently producing `finish(null)` with no response unit.

### Proof of Concept
1. Define a custom asset `X` with `is_transferrable: true` and a `transfer_condition` such as `["not", ["and", [["address", {equals: "SENDER_ADDRESS"}]]]]`-style logic that always evaluates false for outputs addressed to any ordinary user address (e.g., condition requires the recipient equal the asset definer's own address). [6](#0-5) 
2. Deploy/trigger a generic forwarder-style AA, e.g. `forwarder_of_bytes.oscript`-like AA that echoes back received payments of any asset to `trigger.address`.
3. Post a trigger unit from address `S` that includes a payment of asset `X` to the AA along with enough base bytes to cover `bounce_fees`.
4. The AA's primary response attempts `payment` of asset `X` back to `S`; `sendUnit()` fails asset condition evaluation in `validatePaymentInputsAndOutputs` (`validation.js:2643-2658`), triggering `bounce()`.
5. `bounce()` re-attempts to refund asset `X` (and base bytes) to `trigger.address = S`, again hitting the same `transfer_condition` failure inside the nested `sendUnit()` call.
6. Because `bBouncing` is already `true`, the second `bounce()` call short-circuits straight to `finish(null)` (`aa_composer.js:909-929`, `1671-1699`), producing an AA response with `objResponseUnit === null` and no on-chain record of failure beyond an internal `response.error`.
7. The asset `X` balance credited to the AA from step 3's trigger remains in the AA's balance forever, unspendable, because any future attempt to move it out of the AA is bound by the same unsatisfiable `transfer_condition`.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
