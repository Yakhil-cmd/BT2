### Title
`TaskCommands#env` lets attacker's `shipit.yml` `machine.environment.GIT_ASKPASS` override the trusted git-askpass helper - ([File: lib/shipit/task_commands.rb])

### Summary
`Commands#base_env` sets `GIT_ASKPASS` to the engine's own trusted helper script when `Shipit.use_git_askpass?` is enabled, but `TaskCommands#env` merges `deploy_spec.machine_env` (parsed unfiltered from the checked-out repository's `shipit.yml`) after that assignment. Because later `Hash#merge` arguments win, an attacker-controlled `shipit.yml` can replace `GIT_ASKPASS` with a path to a script committed in the same working directory, which git will then execute in a process that has `GITHUB_TOKEN` in its environment.

### Finding Description
The broken binding: `env['GIT_ASKPASS']` as spawned by `PTY.spawn` should always equal `Shipit::Engine.root.join('lib','snippets','git-askpass')` (the trusted helper) whenever `Shipit.use_git_askpass?` is true, but it instead equals `deploy_spec.machine_env['GIT_ASKPASS']` if the attacker's spec defines it.

Code path:
- `Commands#base_env` sets `env['GIT_ASKPASS']` to the trusted snippet path [1](#0-0) .
- `TaskCommands#env` calls `super` (which returns `base_env`) and then chains `.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)` [2](#0-1) . Since `deploy_spec.machine_env` is merged after the hardcoded hash, any key it defines — including `GIT_ASKPASS` — overwrites the earlier trusted value.
- `deploy_spec.machine_env` reads directly from the parsed `shipit.yml` config with **no whitelist**: `config('machine', 'environment') || {}` [3](#0-2) . Unlike deploy/rollback variables, which are explicitly sanitized via `EnvironmentVariables#permit` (`filter_deploy_envs` / `filter_rollback_envs`) [4](#0-3) [5](#0-4) , `machine_env` has no such filtering — it is passed through raw.
- The resulting env hash flows to `Command`/`PTY.spawn`, which will run git operations. If the attacker's committed askpass script path is set, `GIT_ASKPASS` invocation will execute attacker code in the deploy host's environment, which contains `GITHUB_TOKEN`.

Existing guards do not stop this: `EnvironmentVariables#permit` is only invoked for `deploy_variables`/`rollback_variables`, not for `machine_env`; there is no equivalent whitelist check on `machine.environment` keys in `DeploySpec` or `TaskCommands#env`.

### Impact Explanation
An attacker whose `shipit.yml` is used for a task/deploy (e.g., a review-stack deploy of a pull-request branch, or a stack whose deploy pulls the attacker's own fork checkout) can set `machine.environment.GIT_ASKPASS` to a script they committed inside the working directory. When git subsequently needs credentials (e.g., during `fetch`/`clone`/`push` steps run through `TaskCommands`), it will exec the attacker's script instead of the trusted `lib/snippets/git-askpass`. That script runs with the full merged environment, including `GITHUB_TOKEN`, enabling exfiltration of the token or arbitrary command execution on the deploy host — Critical impact per the `GITHUB_TOKEN` exfiltration / RCE via `PTY.spawn` category.

### Likelihood Explanation
Requires: (1) `Shipit.use_git_askpass?` enabled on the instance, (2) a task/deploy that runs against a working directory containing an attacker-authored `shipit.yml` with `machine.environment.GIT_ASKPASS` set (most plausible for review-stack flows that deploy directly from a PR branch), and (3) the deploy pipeline invoking a git operation that triggers askpass. No Shipit secrets, sessions, or maintainer privileges are needed — only the ability to get a `shipit.yml` from a controlled branch used by a task. This is a repeatable, low-cost attack once those preconditions hold.

### Recommendation
Do not allow `deploy_spec.machine_env` (or `@task.env`) to override reserved/security-sensitive environment keys such as `GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`. Either reorder the merge so the base/trusted env is applied last, or explicitly strip reserved keys from `deploy_spec.machine_env` before merging (mirroring the `EnvironmentVariables#permit` whitelist pattern already used for deploy/rollback variables).

### Proof of Concept
Minitest plan (`test/lib/shipit/task_commands_test.rb`):
```ruby
test "#env does not allow deploy_spec.machine_env to override GIT_ASKPASS" do
  Shipit.stubs(:use_git_askpass?).returns(true)
  trusted_path = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s

  task = shipit_deploys(:shipit_pending)
  commands = TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(stub(machine_env: {'GIT_ASKPASS' => '/attacker/script'}))

  env = commands.env

  assert_equal trusted_path, env['GIT_ASKPASS'],
    "attacker-controlled machine.environment.GIT_ASKPASS must not override the trusted askpass helper"
end
```
Expected current (vulnerable) behavior: `env['GIT_ASKPASS']` equals `/attacker/script`, failing the assertion — confirming the divergence between the intended trusted value and the actual spawned value.
