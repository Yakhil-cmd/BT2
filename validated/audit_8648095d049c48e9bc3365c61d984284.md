### Title
Unbounded HTTP response buffering in arbiter/ArbStore integration flows enables memory-exhaustion DoS - ([File: arbiter_contract.js])

### Summary
When a wallet accepts and processes an arbiter contract (arbitration flow reachable by a private-payment/contract counterparty who is a paired device), ocore fetches data from an "ArbStore" HTTP(S) endpoint whose address is derived from an attacker-influenced `arbiter_address`/`arbstore_address`. The response body is accumulated into memory with no size cap, mirroring the Mattermost CWE-789 bug class (integration action endpoint response size unbounded).

### Finding Description
`arbiter_contract.js` implements `httpRequest()` which issues an HTTP POST to a URL obtained via `device.requestFromHub("hub/get_arbstore_url", ...)` and then buffers the entire response in JS memory before parsing: [1](#0-0) 
This function is called from `getArbstoreAddresses`, `openDispute`, `appeal`, and `getAppealFee`, all of which are triggered as part of normal contract/arbitration workflow after a peer (a "private-payment counterparty" that a user has paired with) sends an `arbiter_contract_offer` / `arbiter_contract_shared` message containing an `arbiter_address` chosen by that peer: [2](#0-1) [3](#0-2) 

Similarly, `arbiters.js` has `requestInfoFromArbStore`, used by `getInfo`/`getArbstoreInfo`, which performs an `http.get` and appends every chunk to a `data` string with no length check before `JSON.parse`: [4](#0-3) 

In all these cases, once the hub resolves an `arbiter_address` to a URL (`hub/get_arbstore_url`), the victim wallet directly issues an HTTP(S) request to that URL and buffers the entire response with no `Content-Length` check, no streaming size limit, and no abort on oversized payloads — unlike other parts of the codebase (e.g. `network.js`'s `maxPayload = 6 * 1024 * 1024` enforced on P2P websocket messages) that do bound message sizes: [5](#0-4) 

A malicious counterparty can register/control an arbitration or ArbStore endpoint (any address value is accepted as `objContract.arbiter_address` from the peer's contract offer) so that the URL the hub resolves for it points to an attacker-controlled HTTP server. When the victim wallet subsequently calls `openDispute`, `appeal`, `getAppealFee`, or simply looks up arbiter info via `getInfo`/`getArbstoreInfo`, the attacker's server can respond with an arbitrarily large (or infinite/streaming) body. Because the response is accumulated fully into a JS string/buffer before any processing, this leads to unbounded memory growth on the victim node/wallet process.

### Impact Explanation
This causes memory exhaustion and denial of service on the victim's wallet process, which can crash or become unresponsive — directly analogous to the Mattermost advisory's "attacker-controlled integration response causes memory exhaustion" impact (CWE-789, resource-only DoS). It does not directly enable double-spend, supply inflation, or fund loss, but does render the affected wallet node unable to operate (crash/OOM), which can disrupt confirmation/relay activity on that node if it also participates as a full node/hub-adjacent process.

### Likelihood Explanation
Reachable by any paired-device counterparty who proposes an arbiter contract with an attacker-chosen `arbiter_address`/`arbstore_address`, requiring only that the victim engage with the arbitration feature (open dispute, appeal, or fetch arbiter info) — actions that are part of the normal, low-privilege arbiter-contract workflow. No special privileges beyond being paired/counterparty are required.

### Recommendation
Impose a maximum response size on all `httpRequest`/`http.get`/`https.get` response accumulation loops in `arbiter_contract.js` and `arbiters.js` (and `uri.js`'s `fetchUrl`), aborting the connection and erroring out once a defined byte threshold (e.g. a few hundred KB) is exceeded, consistent with the `maxPayload` bound already enforced for P2P messages in `network.js`.

### Proof of Concept
1. Attacker pairs with victim device and sends an `arbiter_contract_offer` (via `arbiter_contract.js`'s `store`) with `arbiter_address` set to an address the attacker controls/registers on the hub such that `hub/get_arbstore_url` resolves to `https://attacker.example`.
2. Victim accepts/interacts with the contract and calls a flow that reaches `fillArbstoreAddresses` → `getArbstoreAddresses` → `httpRequest(url, "/api/get_device_address", ...)`, or calls `openDispute`/`appeal`/`getAppealFee`.
3. Attacker's server responds to the HTTP POST with a continuous stream of data (e.g., gigabytes) without closing the connection promptly.
4. Victim's `httpRequest` callback in `arbiter_contract.js` (lines 388-408) keeps appending to the `data` variable with no limit, growing process memory until the process crashes or the host becomes unresponsive (DoS).

function getArbstoreAddresses(arbiter_address, cb) {
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err)
			return cb(err);
		device.requestFromHub("hub/get_arbstore_address", arbiter_address, function(err, arbstore_address){
			if (err) {
				return cb(err);
			}
			httpRequest(url, "/api/get_device_address", "", function(err, arbstore_device_address) {
				if (err) {
					console.warn("no arbstore_device_address", err);
					return cb(err);
				}
				cb(null, { arbstore_address, arbstore_device_address });
			});
		});
	});
}

function fillArbstoreAddresses(objContract, cb) {
	if (!cb)
		return new Promise(resolve => fillArbstoreAddresses(objContract, resolve));
	if (objContract.arbstore_device_address && objContract.arbstore_address)
		return cb();
	getArbstoreAddresses(objContract.arbiter_address, function(err, result) {
		if (err)
			return cb(err);
		var { arbstore_address, arbstore_device_address } = result;
		objContract.arbstore_address = arbstore_address;
		objContract.arbstore_device_address = arbstore_device_address;
		db.query("UPDATE wallet_arbiter_contracts SET arbstore_address=?, arbstore_device_address=? WHERE hash=?", [arbstore_address, arbstore_device_address, objContract.hash], function () { cb(); });
	});
}
