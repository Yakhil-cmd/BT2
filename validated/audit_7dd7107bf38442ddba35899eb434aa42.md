### Title
Address that reverts to its currently-active definition_chash is permanently blocked from posting units - ([File: validation.js])

### Summary
`readDefinitionByAddress()` resolves the *current stable definition_chash* for an address (last stable `address_definition_change`, or the address itself if none) [1](#0-0) . When an author unit explicitly supplies a `definition` for an address whose resolved definition_chash already exists in the `definitions` table, `validateAuthor`'s `validateDefinition()` routes into `handleDuplicateAddressDefinition()`, whose active code path is a hardcoded, unconditional rejection [2](#0-1) . This is the ocore analog of the reported Ethos bug class: a validity flag/condition ("duplicate definition") is set and never relaxed for a legitimate, non-malicious case, permanently preventing an address from taking otherwise-valid action.

### Finding Description
`handleDuplicateAddressDefinition()` is supposed to only reject genuinely conflicting/duplicate definitions (there is a commented-out guard `//if (!bNonserial || ...)` intended to allow the definition through in certain forked-path/nonserial scenarios), but as written the function unconditionally executes:
```
function handleDuplicateAddressDefinition(arrAddressDefinition){
//  if (!bNonserial || objValidationState.arrAddressesWithForkedPath.indexOf(objAuthor.address) === -1)
        return callback("duplicate definition of address "+objAuthor.address+", bNonserial="+bNonserial);
    ...
    callback(); // let it be for now. Eventually, at most one of the balls will be declared good
}
``` [3](#0-2) 

The remainder of the function — which would compare `arrAddressDefinition2` (stored) against `objAuthor.definition` (unit's) and allow the unit through if they hash-match — is unreachable dead code because of the always-executing `return` on the first line. In practice, any unit whose author explicitly re-supplies the `definition` array for an address whose definition_chash is already resolvable by `readDefinitionByAddress` (i.e., the address's currently active/known definition, exactly the situation that occurs when a wallet/AA-author "re-attaches" its already-used definition to a unit, or when an address returns to a previously used key set via `address_definition_change`) is rejected with `"duplicate definition of address"`, regardless of whether the supplied definition matches the stored one and regardless of `bNonserial`.

This mirrors the Ethos `isAddressCompromised` bug: a state (here, "definition_chash already known/used") is used as a blanket block on future legitimate authorization, with no code path to "unmark" or reconsider it, even though the correct/matching definition is being supplied.

### Impact Explanation
Any address that needs to attach its explicit `definition` again — for example after restoring/reusing a previously active definition_chash via `address_definition_change` (switching keys away and back), or any wallet flow that includes the `definition` field for an address whose definition is already known to the node — will have every such unit rejected as invalid ("duplicate definition of address"). This is not a transient failure: the unit is permanently invalid on any node applying this validation, so the address is unable to ever get a transaction confirmed while relying on this code path. This directly matches the "restored address permanently unable to act" class: fund custody/control over an address can be effectively frozen for any usage pattern that re-attaches its own valid definition.

### Likelihood Explanation
This code path is exercised whenever `objAuthor.definition` is present and `readDefinitionByAddress` finds an already-resolvable definition_chash for that address — a state reachable by any ordinary wallet/AA-trigger author that re-includes its definition (a legitimate, spec-supported pattern noted by the surrounding comments: "in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition"). No malicious peer/hub/node behavior is required; it is triggered purely by a single unit author, making it directly reachable from a normal unit-posting flow.

### Recommendation
Restore the intended conditional logic instead of the unconditional `return`: only reject as `"duplicate definition"` when the supplied definition actually differs (hash mismatch) from the stored one, and/or when `bNonserial` and the address is not on `objValidationState.arrAddressesWithForkedPath`. When the supplied definition hashes match the previously stored definition_chash, allow the unit through (as the dead `callback()` at the end already intends), so addresses can legitimately re-attach a currently-valid definition without permanent rejection.

### Proof of Concept
1. Address `A` has definition_chash `D` (its stable, currently active definition), known to `definitions`/`address_definition_changes`.
2. Author of a new unit sets `objAuthor.address = A` and includes `objAuthor.definition = <definition array whose chash160 equals D>` (a perfectly valid, matching definition — e.g. re-attaching after wallet software resends the definition explicitly).
3. In `validateAuthor` → `validateDefinition()`, `storage.readDefinitionByAddress` resolves `definition_chash = D` and finds it in `definitions`, invoking `ifFound` → `handleDuplicateAddressDefinition(arrAddressDefinition2)` [4](#0-3) .
4. `handleDuplicateAddressDefinition` immediately executes `return callback("duplicate definition of address ...")` regardless of whether `arrAddressDefinition2` matches `objAuthor.definition` [5](#0-4) .
5. The unit is rejected as invalid even though the author supplied the correct, currently-valid definition for their own address — the address can never get such a unit accepted.
