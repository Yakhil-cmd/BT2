### Title
Unhandled `throw Error("not 1 template")` in authentifier validation crashes the node — analogous to CVE-2019-2755 repeatable-crash DoS - ([File: definition.js])

### Summary
`definition.js`'s `validateAuthentifiers()` evaluates the `'definition template'` op of an address definition by querying for the referenced template message and throwing a raw, uncaught `Error("not 1 template")` if the row count is not exactly 1, instead of returning an error through the callback chain like every other validation branch does. [1](#0-0) 

### Finding Description
`validateAuthentifiers` is the function that verifies signatures/authentifiers against an address definition whenever a new unit is validated (invoked from `validateAuthor` in `validation.js`, which is on the mandatory unit-validation path for every posted unit).

For the `'definition template'` op, the code queries whether the referenced unit still has a stable, good-sequence `definition_template` message:
```js
conn.query(
    "SELECT payload FROM messages JOIN units USING(unit) \n\
    WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
    [unit, objValidationState.last_ball_mci],
    function(rows){
        if (rows.length !== 1)
            throw Error("not 1 template");
        ...
``` [2](#0-1) 

Every sibling branch in this same `evaluate()` function (e.g. `'address'`, `'sig'`, `'hash'`, `'seen address'`) reports failures through `cb2(false)` or sets `fatal_error`, allowing validation to fail gracefully. Only this branch throws synchronously inside a DB-query callback. Notably, the sibling function `validateDefinition()` (used when a *new* address definition is first being validated/created) runs the exact same query but correctly returns a graceful error (`return cb("template not found or too many")`) instead of throwing. [3](#0-2) 

The condition `rows.length !== 1` can legitimately occur after the address definition (referencing a `definition_template` unit) was already accepted as valid, if the referenced template-defining unit's sequence status later changes from `'good'` to non-`good` (e.g. `'temp-bad'`/`'final-bad'`) as a result of the DAG resolving a double-spend, or if the unit becomes unstable/pruned by the time a later signer uses that address. Since this evaluation runs unconditionally on any unit whose author uses an address containing a `'definition template'` op, any subsequently posted unit signing from that address will hit `rows.length === 0` and throw.

This exception escapes the `async`/DB-callback chain uncaught. `network.js` installs a global `process.on('uncaughtException', ...)` handler that explicitly re-throws to crash the whole node process:
```js
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [4](#0-3) 

This is the same bug class as CVE-2019-2755: a normal, protocol-legal state transition (sequence/stability change caused by conflict resolution) reaching server-side validation logic and causing a deterministic, repeatable crash/hang of the affected node — not a memory-safety or RCE bug, but an availability-impacting logic flaw triggerable by any ordinary unit poster.

### Impact Explanation
Any full node (and any peer relaying/validating the offending unit) that reaches this code path will crash. Because the trigger condition — signing from an address whose definition uses `'definition template'` referencing a unit whose sequence subsequently turns non-good — can be deterministically reproduced by an attacker who controls both: (1) the address definition (crafted at address-creation time) and (2) causing the referenced template unit to be double-spent/marked bad, the crash is reproducible and repeatable across every node that validates the same unit, i.e., a network-wide denial of service against the ability to process new units from that address (or process the specific malicious unit at all), matching the "hang or frequently repeatable crash (complete DOS)" impact described in CVE-2019-2755.

### Likelihood Explanation
Exploitation requires the attacker to construct: an address whose definition contains `['definition template', [template_unit, params]]`, and to subsequently cause `template_unit`'s defining message's containing unit to become non-`good`-sequence (via a standard double-spend) before or while the definition's authentifier is evaluated for a new signed unit. This is a multi-step but fully attacker-controlled sequence using only standard, unprivileged wallet/unit-posting operations (address definition creation + a double-spend attempt) — no special privileges, network position, or malicious peer/node behavior needed. Likelihood is Medium: it requires deliberate crafting but no race against other actors and no privileged access.

### Recommendation
Change the `'definition template'` branch in `validateAuthentifiers()` (`definition.js` lines 802-819) to handle `rows.length !== 1` gracefully instead of throwing, mirroring the graceful handling already implemented in `validateDefinition()`'s identical query (lines 321-342). For example, replace `throw Error("not 1 template")` with `fatal_error = "template not found or too many"; return cb2(false);` (or equivalent), so that a bad/missing template only causes the authentifier evaluation to fail (unit rejected as `ifUnitError`) rather than an uncaught, process-crashing exception.

### Proof of Concept
1. Attacker creates address `A` whose spending definition is `['definition template', [T, {...}]]`, where `T` is a unit that at creation time contains a valid, stable, `sequence='good'` `definition_template` message. This definition is accepted by `validateDefinition` when address `A`'s definition is first established (either as part of an author's own definition or a nested `'address'`/definition-change reference).
2. Attacker causes unit `T` to become non-good sequence: e.g., attacker double-spends an input used by `T` such that DAG conflict resolution marks `T`'s sequence as `'temp-bad'`/`'final-bad'` (this is a normal, unprivileged double-spend scenario supported by the protocol).
3. Attacker (or address `A`'s legitimate owner) posts a new unit signed from address `A`, invoking authentifier evaluation.
4. During validation, `validateAuthor` → `validateAuthentifiers` → `evaluate()` hits the `'definition template'` case; the query `... AND +sequence='good' AND is_stable=1` for unit `T` now returns 0 rows.
5. `throw Error("not 1 template")` fires inside the DB-query callback, uncaught by the surrounding `async`/mutex chain, propagating to Node's `uncaughtException` handler in `network.js`, which re-throws and crashes the process — reproducible on every node that receives and validates this unit.
