### Title
API-scoped CCMenu tokens bypass their stack authorization scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `Shipit::Api::CCMenuController` overrides the base API controller's `stack` lookup with an unscoped `Stack.from_param!(params[:stack_id])` call, breaking the invariant that a stack-scoped `ApiClient` token can only authorize access to the stack it was created for.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the set of visible stacks to `current_api_client.stack_id` when the authenticating `ApiClient` is scoped to a specific stack, and the default `stack` helper (`stacks.from_param!(params[:stack_id])`) is built on top of that scoping. [1](#0-0) 

`CCMenuUrlController#fetch` creates exactly this kind of narrowly-scoped credential: any logged-in Shipit user (no special team/admin privilege beyond ordinary authenticated access) can hit `/ccmenu/*stack_id` for any stack they can view, which `find_or_create_by!`s a shared `ApiClient` named `'CCMenu Client'` with `permissions: %w[read:stack]` and **no `stack_id`** set at all — the token is not even bound to a single stack at the model level, it's simply handed out per fetch. [2](#0-1) 

However, even setting aside that the created client isn't stack-scoped, `Shipit::Api::CCMenuController` explicitly overrides the inherited scoped `stack` method with:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This bypasses `BaseController#stacks`'s `current_api_client.stack_id?` scoping entirely and resolves `params[:stack_id]` against the full, unfiltered `Stack` table. The controller only checks `require_permission :read, :stack`, i.e., that the token has the generic `read:stack` permission string — it never verifies that the token's associated stack (if any) matches the stack being requested. [4](#0-3) [5](#0-4) 

The binding that should hold is: `stack authorized by token == stack acted upon by token`. Before the flaw, `ApiClient#stack_id` (when set) is meant to constrain readable stacks via `BaseController#stacks`. After reaching `CCMenuController#show`, the check silently degrades to "any stack, as long as the token has `read:stack` permission anywhere," because the controller queries `Stack` directly rather than through the scoped `stacks` relation.

### Impact Explanation
An attacker who has (or generates for themselves via `CCMenuUrlController#fetch`) a `read:stack`-permissioned `ApiClient` token can pass any other stack's `stack_id` in the URL to `GET /api/stacks/:stack_id/ccmenu` and read deploy/build status, activity, lock state, and last build metadata for stacks they should not have access to via that scoped token — an unauthenticated-read escalation across the stack-scope boundary the token model is meant to enforce (`Stack a token authorises` vs. `Stack it touches`). This does not require a privileged account, a leaked secret, or GitHub org access — only ordinary Shipit login (or, for install configurations with `Shipit.disable_api_authentication`, none at all).

### Likelihood Explanation
High. The `token` query-string mechanism is specifically designed for lightweight, low-friction consumption (CCTray/CCMenu clients embedding the token in a URL), making leakage/reuse across stacks plausible, and the vulnerable code path (`CCMenuController#stack`) is reached on every request to this endpoint — no race condition or timing dependency is needed.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it to go through `stacks.from_param!(params[:stack_id])` as `BaseController` does) so that a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`. Additionally, consider having `CCMenuUrlController#fetch` set `stack:` on the created `ApiClient` so tokens are stack-bound at the model level, matching the intent of `ApiClient#stack_id`.

### Proof of Concept
1. As any authenticated Shipit user, call `GET /ccmenu/<owner>/<repo-a>/<env>` to obtain a `ccmenu_url` containing a `token` for the shared `'CCMenu Client'` `ApiClient` (`permissions: ['read:stack']`, no `stack_id`). [6](#0-5) 
2. Use that same `token` against a different stack the attacker should not have scoped access to: `GET /api/stacks/<owner>/<repo-b>/<env>/ccmenu?token=<token>`.
3. `CCMenuController#authenticate_api_client` authenticates the token, `require_permission :read, :stack` passes because the token has `read:stack`, and `CCMenuController#stack` resolves `repo-b`'s stack directly via `Stack.from_param!`, bypassing any stack scope. The XML response discloses `repo-b`'s deploy/lock/activity status. [7](#0-6) [8](#0-7)
