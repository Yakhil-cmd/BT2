### Title
Unsanitized homoglyph/impersonation strings in device pairing names allow correspondent-identity spoofing - ([File: device.js])

### Summary
`device.js:handlePairingMessage` accepts an arbitrary `device_name` from any device that presents a valid (possibly one-time or wildcard `'*'`) pairing secret, and stores it as the correspondent's display `name` after only stripping HTML tags. No normalization/confusable-character check is performed, mirroring the CVE-2025-55129 bug class (username impersonation surviving basic sanitization, exploitable via homoglyphs) in Revive Adserver.

### Finding Description
`handlePairingMessage` validates only that `device_name` is a non-empty string ≤100 chars and strips `<...>` tag-like sequences: [1](#0-0) [2](#0-1) 

There is no Unicode normalization, no confusable/homoglyph filtering, and no uniqueness check against existing `correspondent_devices.name` values (`correspondent_devices` schema only requires a `VARCHAR(100)` non-null field, no distinctness constraint): [3](#0-2) 

Any unprivileged peer who obtains (or brute-forces/uses a shared/wildcard `'*'`) pairing secret can pair and set `device_name` to a string that is visually identical (via Unicode homoglyphs, RTL overrides, zero-width characters, etc.) to an already-trusted correspondent's name shown in the wallet UI (`readCorrespondents`/`readCorrespondent`, ordered/displayed by `name`): [4](#0-3) 

This is the same bug class as CVE-2025-55129: a display-name/"username" field is only lightly sanitized (tag-stripping, not homoglyph-aware), enabling an attacker to impersonate an existing, trusted identity in the UI that end users rely on when deciding where to send funds, share private-payment chains, or accept arbiter contracts (`my_party_name`/`peer_party_name` in `arbiter_contract.js`/`wallet_arbiter_contracts` are subject to the same lack of validation).

### Impact Explanation
A successfully-paired malicious device can present itself in the user's correspondent list with a name indistinguishable from a real, previously-trusted correspondent (business partner, exchange support account, arbiter, etc.). Because wallet flows such as sending private payments, sharing multi-sig addresses, or accepting arbiter contracts are driven by the human selecting a correspondent by displayed name, this enables social-engineering-driven misdirection of funds — the user may choose the attacker's device instead of the genuine correspondent, resulting in unauthorized transfer of bytes/assets or private-payment disclosure to the wrong party. This matches the "concrete unauthorized spending" impact bar via user-facing identity confusion, analogous to how the original CVE enabled impersonation-based fraud.

### Likelihood Explanation
Likelihood is limited by the need for the attacker to first obtain a pairing secret (via a link/QR shared by the legitimate correspondent, a leaked/reused secret, or a permanent/wildcard hub-level secret) and for the victim to visually mistake the spoofed name — both plausible in real usage (pairing codes are frequently shared publicly, e.g., support/bot pairing codes), but exploitation still requires an additional social-engineering step, keeping severity at Medium.

### Recommendation
- Apply Unicode normalization (NFKC) and a confusable/skeleton check (e.g., Unicode TR39 "skeleton" comparison) to `device_name` before storing it, rejecting or flagging names that are confusable with existing `correspondent_devices.name` entries.
- Strip/reject bidi-control and zero-width characters, not just HTML-like tags, in `handlePairingMessage` (device.js:823) and in `arbiter_contract.js` `my_party_name`/`peer_party_name` handling.
- Surface a UI warning when a newly paired device's name is confusable with an existing correspondent's name.

### Proof of Concept
1. Attacker obtains any valid (even single-use) pairing secret for the victim's device, e.g. by having the victim scan a pairing QR intended for one purpose, or by reusing a public bot/arbiter pairing code.
2. Attacker sends a `pairing` message with `body.device_name` set to a string using homoglyphs/zero-width characters that renders identically to an already-trusted correspondent's name (e.g., using Cyrillic "а" instead of Latin "a").
3. `handlePairingMessage` (device.js:822-831) only strips HTML-like tags and inserts the value into `correspondent_devices.name`.
4. The victim's wallet UI now lists two entries with visually identical names; the victim selects the attacker's entry to send a payment, share a shared address, or accept an arbiter contract intended for the real correspondent, resulting in funds/private data going to the attacker.
