## Title
Cross-Stack Authorization Bypass in CCMenu API Endpoint - Stack-Scoped `ApiClient` Token Grants Access to Any Stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` checks only that a caller's `ApiClient` token carries the generic `read:stack` permission, but never verifies that the token is scoped to the specific stack being requested. This breaks the same class of binding as the GMX report — the entity that was *authorized* (the stack a token is limited to) is not the entity actually *acted upon* (the `stack_id` supplied in the request).

### Finding Description
`ApiClient` records can be created scoped to a single stack (`stack_id` column), and `Shipit::Api::BaseController` normally enforces this scope by filtering the `stacks` relation through `current_api_client.stack_id?` before resolving `params[:stack_id]`: [1](#0-0) 

`CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` relation, completely bypassing the client's scoping: [2](#0-1) 

The only authorization gate left is `require_permission :read, :stack`, which merely checks that `"read:stack"` is present in the token's `permissions` array — it never compares `current_api_client.stack_id` to the requested `stack.id`: [3](#0-2) 

These "CCMenu" tokens are created and handed out routinely and automatically, scoped to a single stack, via `CCMenuUrlController`: [4](#0-3) 

The equality that should hold is:
`token.stack_id == stack_id_being_read`

Instead, the code only checks:
`"read:stack" ∈ token.permissions`

Any holder of a single-stack CCMenu token (these are widely distributed to CI dashboard tools/browser extensions since they are meant to be embeddable, unauthenticated-by-URL, read-only status feeds) can supply an arbitrary `stack_id` and read build/deploy status for *any* stack in the installation, not just the one the token was issued for. Test coverage confirms the token is accepted via query-string alone: [5](#0-4) 

### Impact Explanation
This is an authorization-scope bypass: possession of a token legitimately issued for stack A yields unauthorized read access to the state (name, last build status/label/time, web URL) of every other stack, including private/production ones. This falls under the "High" impact category defined by the rules — "unauthorized read of stack state ... " — because the check that is supposed to bind the token to a specific stack is never performed, and it directly parallels the GMX pattern of checking one thing (permission) while acting on a different, unguarded field (`stack_id`) that was supposed to be constrained together with it.

### Likelihood Explanation
Likelihood is high: CCMenu tokens are deliberately designed for lightweight, low-friction distribution (embedded in CI status widgets/URLs), so they leak far more easily than API tokens meant for privileged operations. Exploitation requires only a single valid, low-privilege, stack-scoped token — no repository write access, no webhook secret, and no GitHub session are needed.

### Recommendation
In `CCMenuController#stack`, resolve the stack through the same client-scoped relation used elsewhere (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), or explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering, mirroring `Shipit::Api::BaseController#stacks`/`#stack`.

### Proof of Concept
1. Create/obtain a stack-scoped read-only token for `stack_id: A` via `CCMenuUrlController#fetch` (as any authenticated Shipit user can do for any stack they can view): [6](#0-5) 
2. Call `GET /api/stacks/B/ccmenu.xml?token=<token-scoped-to-A>` where `B != A`.
3. `authenticate_api_client` accepts the token (it's a valid `ApiClient`), `require_permission :read, :stack` passes because `"read:stack"` is in its permission list, and `stack` resolves `Stack.from_param!("B")` — an unrelated stack — returning its build status in the XML response, even though the token was never authorized for stack `B`.
