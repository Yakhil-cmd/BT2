### Title
Unauthenticated `/webhooks` endpoint when `webhook_secret` is unset allows forged `membership`/`status` events to grant `Shipit.github_teams` authorization and forge commit statuses across repositories - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as an implicit "trust everything" bypass, and the handlers invoked after that check (`MembershipHandler`, `StatusHandler`) never re-validate that the caller is actually GitHub, nor that the target commit belongs to the org that supposedly authenticated. This mirrors the reported bug class: a restricting check ("only GitHub, with a valid signature, may call these handlers") that silently becomes a no-op, letting any unauthenticated caller invoke privileged setters.

### Finding Description
`WebhooksController#create` dispatches any payload whose `X-Github-Event` matches a registered handler, gated only by `verify_signature`: [1](#0-0) [2](#0-1) 

The signature check delegates to `GitHubApp#verify_webhook_signature`, which explicitly returns `true` — i.e., accepts the request as authentic — whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

`webhook_secret` is documented as **optional** in the setup guide, so this is a supported, documented configuration, not an unmounted/undocumented deployment: [4](#0-3) [5](#0-4) 

Once past this no-op gate, the `membership` handler trusts the payload to create/delete `Team`/`Membership`/`User` records purely from attacker-supplied JSON (no GitHub API cross-check of real org membership is performed by the handler itself — confirmed by test behavior): [6](#0-5) 

Team membership is exactly the binding that `Shipit::Authentication#force_github_authentication` uses to authorize a logged-in `User` to use the app at all: [7](#0-6) 

Separately, `StatusHandler` writes a GitHub commit status onto **any** `Commit` row matching the attacker-supplied `sha`, with no scoping to the repository/org named in the payload (unlike other handlers, it never calls the base `Handler#stacks`/`repository_name` scoping): [8](#0-7) [9](#0-8) 

The binding being broken: **"organization/caller that authenticated" == "GitHub" is assumed by every handler**, but when `webhook_secret` is blank, `verify_webhook_signature` makes that equality trivially true for **any** caller, so `payload attacker controls` == `data acted upon with full trust` for membership grants and commit statuses, without any GitHub-side signing ever happening.

### Impact Explanation
This directly matches the "High" impact bucket "escalation into `Shipit.github_teams` authorization": an anonymous internet caller can POST a forged `membership` event adding their own GitHub login to a team listed in `Shipit.github_teams`, then complete the normal OAuth login flow and be treated as `authorized?`, gaining full deploy/rollback/ship privileges on stacks. It also allows forging arbitrary commit statuses (`StatusHandler`) on commits belonging to repositories/stacks the attacker has no relationship to, since the lookup is global (`Commit.where(sha: params.sha)`), which can be used to fake "green" CI checks that gate merges/deploys elsewhere in the pipeline.

### Likelihood Explanation
Exploitability is entirely dependent on the operator leaving `webhook_secret` unset, which the project's own setup docs mark as optional (not a hardening default), so real-world instances that followed the "optional" guidance are exposed with zero prerequisites (no session, no API token, no GitHub App key). No repository write access, no TLS interception, no social engineering is required — only knowledge of the public `/webhooks` route and the JSON shape expected by `Shipit::Webhooks::Handlers::MembershipHandler`/`StatusHandler`.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional; do not treat an absent secret as automatic trust in `GitHubApp#verify_webhook_signature`.
- Scope `StatusHandler` (and any other handler that doesn't already do so) to only touch commits belonging to `stacks`/`repository_name` derived from the payload, consistent with `Handler#stacks`.
- Consider cross-checking `membership` events against a live GitHub API call rather than trusting webhook payload contents outright for authorization-affecting mutations.

### Proof of Concept
1. Target a Shipit instance configured without `webhook_secret` (per documented "optional" setup).
2. `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": {"login": "<victim-org>"},
  "team": {"id": <existing-team-id>, "slug": "developers", "name": "Developers", "url": "http://example.com"},
  "member": {"login": "<attacker-github-login>"},
  "repository": {"owner": {"login": "<victim-org>"}}
}
```
3. `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request is processed and a `Membership` row is created for the attacker's GitHub login in the team gating `Shipit.github_teams`.
4. Attacker completes normal `/github/auth/github` OAuth login; `current_user.authorized?` now returns true, granting full app access (deploys, rollbacks) without ever having real org membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

      end
```
