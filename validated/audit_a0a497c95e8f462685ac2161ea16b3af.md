### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook authenticated for one repository mutate commit status for any other stack sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository/stack filter, unlike every sibling handler (`CheckSuiteHandler`, `PushHandler`, PR handlers) which scope through `Repository.from_github_repo_name(repository_name)&.stacks`. `WebhooksController#verify_signature` only proves the request came from *some* GitHub organization's webhook secret; it never checks that the `sha` in the payload actually belongs to the repository that authenticated the request. This allows a `status` webhook authenticated for repository A to flip the CI status (`ci/jenkins`, `state: failure`) of a `Commit` row belonging to a completely different stack/repository B, as long as both have a `Commit` record with the same `sha` string.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`commit.stack.repository.full_name == payload['repository']['full_name']`

Trace:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses `params`, dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler.call(params)`. Before this, `verify_signature` (lines 24-49) validates the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e. only checks that *some* org's secret produced this signature - it never checks that the `sha` claimed in the payload is a commit that exists in the authenticating repository.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a bare, global `Commit.where(sha: ...)` lookup with **no repository/stack scoping**. Contrast with the base `Handler` class's `stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-34), which scopes strictly to `Repository.from_github_repo_name(repository_name)&.stacks`, and is used by `CheckSuiteHandler` (`stacks.where(branch: ...)` at app/models/shipit/webhooks/handlers/check_suite_handler.rb:14) and by `PushHandler`/PR handlers. `StatusHandler` is the only handler that bypasses this scoping and queries `Commit` globally.
3. `Commit belongs_to :stack` (app/models/shipit/commit.rb:11) - commits are stored per-stack, not deduplicated globally by SHA. If two stacks (belonging to different repositories, e.g. a victim's `review_stacks_enabled: true, allow_all` stack and an attacker-influenced repository/fork) each contain a `Commit` row with an identical `sha` (e.g., a shared history commit, a cherry-pick, or a rebase preserving the SHA, or any coincidental match), `Commit.where(sha: params.sha)` returns **both** rows.
4. `commit.create_status_from_github!(params)` → `add_status` creates a `Status`, which can flip `commit.state` (as demonstrated by the state-transition tests in test/models/commits_test.rb:678-712, e.g. `pending`→`failure`) and fires `deployable_status`, enqueues `ProcessMergeRequestsJob`, and can drive continuous delivery (`schedule_continuous_delivery` after_create hook, commit.rb:24). This is exactly the mechanism that governs whether a commit is mergeable/deployable.
5. Because `review_stacks_enabled: true, allow_all` auto-provisions a review stack executing `shipit.yml` for any external PR (per `ReviewStackAdapter`/`labeled_handler` logic), the victim stack's `Commit` rows for `ci/jenkins` context can be forced into `failure` by an attacker who merely needs to get *any* signed `status` webhook (from any org/repo combination they control, or any repository sharing the SHA) accepted by `verify_signature` — signature verification is organization-scoped, not commit-ownership-scoped.

Existing guards do not stop this: `verify_signature` checks organization webhook secret validity, not sha-to-repository binding; `drop_unhandled_event` just checks the event type is registered; the `ExplicitParameters` schema (`requires :sha, :state`, etc.) only validates payload shape, not repository ownership of the sha; there is no `stacks` scoping call anywhere in `StatusHandler`.

### Impact Explanation
A `status` payload authenticated for one repository/organization mutates `Commit`/`Status` records that belong to an unrelated stack, changing that stack's computed `deployable_status`/CI state and triggering `ProcessMergeRequestsJob`/continuous-delivery scheduling for a repository that never authenticated the status. This is "a payload for one repository mutating another's stack/commit" — a Critical-class cross-tenant write. It is repeatable against any pair of stacks/repositories whose `commits` table happens to contain matching `sha` values (most plausible via forks/mirrors/cherry-picked histories, or any commit shared across repositories tracked by Shipit), and the blast radius spans all Shipit-managed stacks sharing GitHub org webhook trust boundaries.

### Likelihood Explanation
Preconditions: the victim stack must have a `Commit` row whose `sha` collides with a `sha` for which the attacker can get an authenticated `status` webhook delivered (i.e., the attacker needs write/CI access to *some* repository under an org configured in Shipit, or control of a repository/fork whose commit history intersects the victim's, e.g. via `review_stacks_enabled: true, allow_all` auto-provisioning stacks from external PRs that may reuse identical commits). Attacker cost is low once the sha-sharing condition holds — a single POST to `/webhooks` with `context`, `state: failure`, and the shared `sha` is sufficient, and it is fully repeatable/scriptable against every stack containing that sha.

### Recommendation
Scope `StatusHandler#process` to the authenticating repository, mirroring the pattern used by `CheckSuiteHandler`/`PushHandler`: use `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of the bare `Commit.where(sha: params.sha)`, so a status can only ever update commits belonging to stacks tied to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (models/webhooks/handlers/status_handler_test.rb or controllers/webhooks_controller_test.rb):
1. Create `repository_a` and `repository_b` (different `full_name`s, potentially different orgs) each with a `Stack` (`stack_a`, `stack_b`); set `stack_b.review_stacks_enabled = true` with allow-all PR provisioning config.
2. Create `Commit` rows with the **same** `sha` value, one under `stack_a` (`commit_a`) and one under `stack_b` (`commit_b`), each initially in a passing/`unknown` `ci/jenkins` state on `stack_b` such that `stack_b` is currently deployable/mergeable.
3. Stub `GithubHook`/`verify_signature` to return true for `repository_a`'s organization only.
4. POST `/webhooks` with `X-Github-Event: status`, body `{ sha: <shared_sha>, state: 'failure', context: 'ci/jenkins', repository: { full_name: repository_a.full_name, owner: { login: repository_a_org } } }`.
5. Assert BEFORE: `commit_b.reload.state != 'failure'` and `stack_b` deployable/merge-eligible for that commit.
6. Assert AFTER: `commit_b.reload.state == 'failure'` (i.e., `commit_b.statuses.last.context == 'ci/jenkins'` with `state: 'failure'`) even though the webhook was authenticated only for `repository_a`, proving `commit.stack.repository.full_name == payload['repository']['full_name']` is violated - `commit_b`'s stack (`repository_b`) never authenticated this webhook, yet its status/deployability changed.
