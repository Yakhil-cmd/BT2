### Title
Webhook signature verification selects the wrong organization's secret based on an unverified payload field, allowing signature bypass in multi-organization deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit configurations, the `WebhooksController` picks which GitHub App/webhook secret to verify a webhook against using a field taken directly from the *unverified* raw request body, rather than from any value the HMAC signature actually authenticates. This creates the same "authenticated identity vs. acted-upon identity" mismatch as the external report's malicious-strategy bug: the entity whose credential is checked (`repository_owner` picked from the payload) is not bound to the entity that the handler subsequently trusts and acts on (the full event data, including `repository.full_name`, ref, statuses, etc.).

### Finding Description
`Shipit::WebhooksController#verify_signature` computes `repository_owner` from the raw JSON body before any signature check occurs: [1](#0-0) [2](#0-1) 

`repository_owner` is used only to select which configured GitHub App (and thus which `webhook_secret`) to verify the signature against:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

Shipit explicitly supports configuring **multiple** GitHub Apps, one per organization, each with its own independent `webhook_secret`: [3](#0-2) 

And crucially, `GithubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatically valid: [4](#0-3) 

Because `repository_owner` is read from the attacker-supplied `params.dig('repository', 'owner', 'login')` (or `organization.login`) **before** verification, and because the value used to pick the verification config is not itself checked against anything cryptographically bound to the request, an attacker who knows (or controls, e.g. via a repo they legitimately own) that *some* configured organization on the instance has no `webhook_secret` set can:

1. Craft a webhook body whose `repository.owner.login` is that unprotected organization (making `verify_webhook_signature` return `true` unconditionally, since `webhook_secret` is blank for it), while
2. Populating the rest of the payload (`repository.full_name`, `ref`, `after`, commit `sha`, `state`, etc.) with data belonging to a *different*, protected repository/stack.

The signature check authenticates "this came from organization X" (or, worse, no one, since X has no secret), but the code that actually executes afterward — `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — operates on the full, unverified `params`, including whatever repository/ref/commit data the attacker put there: [5](#0-4) 

Handlers such as `PushHandler` then resolve and mutate stack state using fields from that same unverified payload (branch, `after` SHA, etc.): [6](#0-5) 

This is the exact class of bug in the report: the field that is checked (`repository_owner`, used to pick the verifying secret) is not the same field that downstream code trusts and acts on (the full payload, including which stack/repository is synced). The binding that should hold — "organization whose secret authenticated this request" == "repository/stack whose state is written by this request" — is broken.

### Impact Explanation
On any Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), an unauthenticated attacker can forge webhook events (`push`, `status`, `check_suite`, `commit_status`, `deployable_status`, `merge_status`, etc.) for a victim stack by wrapping them in an owner field belonging to any organization on that instance lacking a `webhook_secret`. This can inject forged CI/commit statuses and push/sync events into a protected stack's history. Since Shipit stacks can be configured for continuous delivery (auto-deploy on passing CI/merge status), this can lead to an **unauthorized deploy** being triggered off forged status data — meeting the High-impact bar defined for this analog ("escalation... or an unauthorized deploy").

### Likelihood Explanation
Exploitability requires: (a) the instance to be configured with more than one GitHub organization (explicitly documented and supported), and (b) at least one configured organization to be missing a `webhook_secret` (also a supported, non-error configuration state per `lib/shipit/github_app.rb:76-83`). Given Shipit ships this multi-org config pattern as a first-class feature, and a misconfigured/optional secret on any one org silently disables verification instance-wide, this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
- Never select the verification secret based on unverified payload content. Instead, either verify against a single global secret, or verify the signature against *all* configured org secrets and only accept the request if at least one matches — do not use payload-derived data to narrow the search space before verification.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank; require every configured organization to have a non-blank secret, or reject requests when one is missing.
- After signature verification succeeds, re-derive `repository_owner`/`repository.full_name` from the verified payload and confirm it matches an organization/repository actually registered in Shipit, rejecting mismatches.

### Proof of Concept
1. Configure two organizations in `secrets.yml`: `victim-org` (with `webhook_secret: s3cr3t`) and `test-org` (with `webhook_secret:` left blank/nil), as shown in `config/secrets.development.example.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "test-org" }
  }
}
```
3. `WebhooksController#repository_owner` returns `"test-org"`; `Shipit.github(organization: "test-org")` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `Shipit::Webhooks.for_event('push')` handlers run with the full unverified `params`, and `PushHandler#process` syncs `victim-org/victim-repo`'s stack using the attacker-supplied `after` SHA, injecting forged push/state data into the protected stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
