### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name`/`organization.login`, allowing any onboarded organization's secret to forge events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-tenant configuration (multiple GitHub Apps/organizations configured under `secrets.github`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the payload against purely from `repository.owner.login` (falling back to `organization.login`). But the handler that then acts on the (fully attacker-controlled, since the request is delivered directly to `/webhooks` and only the signature—not the field consistency—is checked) payload uses a different field, `repository.full_name`, to resolve which `Stack`/`Repository`/`Commit` is mutated. There is no enforcement that `repository.owner.login` is a prefix of `repository.full_name`, so an org whose secret is known (because that org's own admins configured it) can forge a payload that verifies successfully under their own secret while its `full_name` points at a totally different, unrelated organization's repository/stack.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches the corresponding `GitHubApp` config to verify `X-Hub-Signature`: [6](#0-5) 

`repository_owner` reads `repository.owner.login`, defaulting to `organization.login`: [2](#0-1) 

Once verified, the *entire raw payload* (`params = JSON.parse(request.raw_post)`) is dispatched unmodified to the registered handlers: [7](#0-6) 

Handlers derive the target repository from `repository.full_name`, not `repository.owner.login`: [3](#0-2) 

`StatusHandler` writes an arbitrary CI status (`state`, `description`, `context`, `target_url`) for any `Commit` matching `params.sha`, and commits are looked up globally by `sha` (not scoped by the owner used for signature verification): [4](#0-3) 

`PushHandler` triggers `stack.sync_github` for stacks resolved via `repository.full_name`: [8](#0-7) 

`MembershipHandler` similarly trusts `organization.login` from the payload to attribute team membership, independent of which org's secret verified the request: [9](#0-8) 

The multi-org config lookup confirms each organization has an independently configured `webhook_secret`: [5](#0-4) [10](#0-9) 

**Binding broken (equality that must hold but doesn't):**
`organization whose webhook_secret authenticated the request` == `organization/repository the handler subsequently writes to`.

Before the attacker's request: Shipit trusts that a signature verified under org X's secret implies the payload legitimately originates from org X's repositories, and only org X's data is touched.
After the attacker's request: an operator of org X (who legitimately knows/configures org X's `webhook_secret` — e.g. a lower-trust tenant onboarded to the same Shipit instance as higher-trust org Y) can POST a hand-crafted JSON body directly to `/webhooks` with `repository.owner.login: "org-x"` (so `verify_signature` selects and validates against org X's real secret) but `repository.full_name: "org-y/critical-repo"` and an arbitrary commit `sha`/`state`. The signature will verify successfully (org X's secret over the exact bytes sent), yet `StatusHandler`/`PushHandler` act on org Y's `Commit`/`Stack` because they only read `repository.full_name`.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Concretely:
- `StatusHandler` lets the org-X-secret holder inject a fake passing (`state: "success"`) CI status for an arbitrary commit sha belonging to org Y's repository/stack, which can satisfy required-status-check gating used elsewhere in Shipit (deploy/merge safety checks), enabling an unauthorized deploy or merge decision on a stack the attacker has no legitimate access to.
- `PushHandler` lets the same attacker force `sync_github` on org Y's stack with an attacker-chosen `expected_head_sha`.
- `MembershipHandler` lets the attacker fabricate team/organization membership state (`Team`/`User` records) attributed to `organization.login` values unrelated to the org whose secret actually verified the request.

This matches the Critical/High impact classes (escalation into authorization/state that gates unauthorized deploys) because it lets a legitimately-onboarded-but-lower-trust tenant cross into another tenant's repository/stack trust domain purely by mismatching two payload fields, without needing org Y's own secret, `GITHUB_TOKEN`, or any Shipit session/API credential.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (`secrets.github` with more than one org key, as shown in `config/secrets.development.shopify.yml`) and requires the attacker to control (know) at least one onboarded organization's `webhook_secret` — realistic for any tenant who configured their own GitHub App's webhook secret, as documented in `docs/setup.md`. No repository write access, GitHub App private key, or Shipit session is needed; the attacker only needs network access to POST to the public `/webhooks` endpoint with a body they construct and sign with their own known secret.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, require that the resolved `repository_owner` (used to pick the verifying `webhook_secret`) matches the owner portion of `repository.full_name` (and, for membership events, `organization.login`) before dispatching to handlers; reject (422) on mismatch. Alternatively, scope `Repository.from_github_repo_name` and `Commit.where(sha:)` lookups by the verified organization rather than trusting the unauthenticated `full_name`/`sha` fields alone.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-x` (attacker-controlled webhook secret) and `org-y` (victim organization with a Stack tracking `org-y/critical-repo`).
2. Attacker computes `sig = HMAC-SHA1(org-x-secret, body)` for body:
```json
{
  "repository": {"owner": {"login": "org-x"}, "full_name": "org-y/critical-repo"},
  "sha": "<victim-stack-blocking-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` looks up `Shipit.github(organization: "org-x")` and verifies successfully against `org-x`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (matching org-y's commit) and calls `create_status_from_github!`, writing a forged "success" status onto org-y's commit despite the request never being authenticated by org-y's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
