### Title
Bridge Operator Can Drain Entire KAIA/ERC20 Balance via Unconstrained `_value` in `handleKLAYTransfer` / `handleERC20Transfer` — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

The service-chain bridge's `handleKLAYTransfer` and `handleERC20Transfer` functions accept a caller-supplied `_value` parameter that is never validated against any on-chain record of the original `RequestValueTransfer` event. With the default operator threshold of 1, a single bridge operator can call either function with an arbitrarily inflated `_value` and a fresh unused `_requestTxHash`, immediately passing the vote and draining the entire bridge balance to any address.

---

### Finding Description

`BridgeTransferKLAY.handleKLAYTransfer` accepts seven parameters from the operator:

```
_requestTxHash, _from, _to, _value, _requestedNonce, _requestedBlockNumber, _extraData
```

None of these are validated against any on-chain record of what was originally deposited. The bridge contract stores no mapping of `requestNonce → (amount, recipient, txHash)`. The only guards are:

1. `_lowerHandleNonceCheck(_requestedNonce)` — requires `lowerHandleNonce <= _requestedNonce`. Any fresh nonce ≥ `lowerHandleNonce` passes.
2. `_voteValueTransfer(_requestedNonce)` — uses `keccak256(msg.data)` as the vote key. With the **default threshold of 1** (set in `BridgeOperator` constructor), the very first call by any operator immediately returns `true`.
3. `_setHandledRequestTxHash(_requestTxHash)` — marks the operator-supplied hash as handled to prevent replay. An attacker simply uses any bytes32 not previously recorded.

After these checks pass, the contract executes:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

`_value` is completely unconstrained. The bridge holds KAIA deposited by users via `requestKLAYTransfer` / `chargeWithoutEvent`, but no per-nonce accounting of deposited amounts exists. An operator can set `_value` to the entire contract balance.

The same flaw applies to `handleERC20Transfer` in `BridgeTransferERC20.sol`, where `IERC20(_tokenAddress).safeTransfer(_to, _value)` is called with the operator-supplied `_value`.

---

### Impact Explanation

**Unauthorized transfer of all KAIA and ERC20 tokens held by the bridge contract.**

A single operator (the default configuration has threshold = 1) can:
- Supply a fresh unused `_requestTxHash` (any 32 bytes not in `handledRequestTx`)
- Supply `_requestedNonce >= lowerHandleNonce`
- Set `_to` to any address (including their own)
- Set `_value` to `address(this).balance` (entire KAIA balance) or the full ERC20 balance

The bridge's entire liquidity pool — funded by legitimate cross-chain users — is drained in a single transaction. This matches the allowed impact gate: *"Unauthorized transfer… affecting KAIA, bridged assets."*

---

### Likelihood Explanation

The default `operatorThresholds[ValueTransfer] = 1` is set in the `BridgeOperator` constructor and is the live default for any newly deployed bridge. Service-chain operators are semi-trusted off-chain components. A single compromised or malicious operator key is sufficient. The attack requires no special on-chain state, no prior setup, and no interaction with other parties.

---

### Recommendation

1. **Store per-nonce request commitments on-chain.** When `RequestValueTransfer` is emitted, record a commitment `requestCommitments[nonce] = keccak256(abi.encode(tokenType, from, to, value, tokenAddress))`. In `handleKLAYTransfer` / `handleERC20Transfer`, verify the supplied parameters match the stored commitment before executing the transfer.

2. **Enforce a minimum threshold > 1 in the constructor**, or require the owner to explicitly set threshold = 1 as an opt-in rather than the default.

3. **Bound `_value` to the amount recorded in the original request**, preventing operators from inflating the payout beyond what the user deposited.

---

### Proof of Concept

```
Setup:
  - Deploy bridge with default threshold (= 1)
  - User calls requestKLAYTransfer{value: 1000 ether}(user, 1000 ether, "")
    → bridge holds 1000 KAIA, emits RequestValueTransfer(nonce=0, value=1000 ether)

Attack (single operator, threshold=1):
  - operator calls handleKLAYTransfer(
        _requestTxHash = bytes32(0xdeadbeef...),   // any unused hash
        _from          = user,
        _to            = attacker,
        _value         = 1000 ether,               // entire bridge balance
        _requestedNonce = 0,                        // >= lowerHandleNonce (0)
        _requestedBlockNumber = 1,
        _extraData     = ""
    )

Execution path:
  1. _lowerHandleNonceCheck(0): 0 <= 0 → passes
  2. _voteValueTransfer(0): threshold=1, first vote → returns true, closes vote
  3. _setHandledRequestTxHash(0xdeadbeef...): marks hash
  4. _to.call.value(1000 ether)("") → sends 1000 KAIA to attacker

Result: bridge balance = 0, attacker balance += 1000 KAIA
```

The same sequence applies to `handleERC20Transfer` replacing the native KAIA call with `IERC20.safeTransfer(_to, _value)`.
