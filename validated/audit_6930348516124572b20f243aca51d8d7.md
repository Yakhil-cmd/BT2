### Title
Webhook signature verification keys off `repository.owner.login`, but stack mutation keys off `repository.full_name` — cross-organization/repository writes in multi-tenant GitHub App config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (multiple entries under `secrets.github`), `WebhooksController#verify_signature` selects which org's webhook secret to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) pulled from the untrusted JSON body. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves *which* `Repository`/`Stack` to mutate using a different field from the same body: `repository.full_name`. Nothing ties these two fields together, so a signature that is valid for org A's webhook secret can carry a `repository.full_name` pointing at org B's repository, letting an attacker who legitimately controls one onboarded organization (or one with no `webhook_secret` configured) forge writes against any other onboarded stack.

### Finding Description
`verify_signature` derives the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the secret for that specific organization name and instantiates a `GitHubApp` scoped to it: [3](#0-2) 

`GitHubApp#verify_webhook_signature` validates the raw body against *that org's* secret only — and if that org has no `webhook_secret` configured (an explicitly supported, documented configuration, see `test/dummy/config/secrets_double_github_app.yml`), verification is skipped entirely: [4](#0-3) 

Meanwhile, every handler resolves the actual repository/stack to act on from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

The same pattern repeats in the pull-request handlers, which use `params.repository.full_name` to look up the target `Repository` and then archive/unarchive/create a `ReviewStack` (`stack.archive!`, `stack.unarchive!`, `ReviewStackAdapter#create!`), including scheduling provisioning: [6](#0-5) [7](#0-6) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `repository actually mutated by the handler (repository.full_name)`.

Before the attack: an org's webhook secret only ever produces signed payloads whose `repository.full_name` genuinely belongs to that org (GitHub, the real sender, enforces this consistency).
After the attack: an attacker who controls (or has a secret-less) org "attacker-org" — a state that is normal/documented for multi-tenant Shipit — can send a POST to `/webhooks` with `repository.owner.login = "attacker-org"` (satisfying/bypassing `verify_signature`) but `repository.full_name = "victim-org/victim-repo"`. The handler layer, and every handler built on it (`push_handler`, `pull_request/*_handler`, `status`, `check_suite`, etc.), never re-derives or checks the owner from `full_name`, so it operates on `victim-org/victim-repo`'s `Stack`/`Repository` records as if the request were authentically signed for that repo.

### Impact Explanation
This breaks the trust boundary between organizations/repositories hosted on a shared Shipit instance: an attacker with legitimate access to one onboarded (and possibly secret-less) GitHub organization can forge webhook events that write to another organization's stacks — e.g., causing `PullRequest::OpenedHandler` to `find_or_create!` a review stack for a victim repo (triggering `ReviewStackProvisioningQueue.add(stack)`, i.e., provisioning/build execution against attacker-chosen branch data), or archiving/unarchiving a victim's review stacks. This is a cross-repository/cross-organization write achieved purely by exploiting a mismatch between the field used for authentication and the field used for the write, matching the "cross-repository writes" Critical impact class.

### Likelihood Explanation
Requires: (1) the deployment to use the multi-org GitHub App config schema (explicitly supported, see `Shipit.github_app_config`/`github_organizations`), and (2) the attacker to control an onboarded org whose webhook secret they know, or one where `webhook_secret` was left blank (also explicitly supported/documented in `docs/setup.md`). Given this is a standard supported configuration for shared/enterprise Shipit installations serving multiple GitHub orgs, and no code anywhere cross-validates `repository.owner.login` against `repository.full_name`, the precondition is realistic for such installations, though it does not apply to single-org deployments (`github_default_organization.nil?` legacy path uses one shared secret for everything, so the mismatch, while still present in code, can't be exploited across "different" orgs).

### Recommendation
In `WebhooksController#verify_signature`, after determining the signing organization, assert that `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) matches the organization whose secret validated the signature, rejecting the request (422) otherwise. Alternatively, derive `repository_owner` from the same field (`repository.full_name`'s owner segment) that handlers use for repository resolution, so verification and mutation are always keyed off the identical payload field.

### Proof of Concept
1. Configure Shipit with two orgs under `secrets.github`: `AttackerOrg` (attacker knows/controls the webhook secret, or it is unset) and `VictimOrg` (has stacks/review-stacks configured).
2. Attacker computes a valid `X-Hub-Signature` for `AttackerOrg`'s secret (or sends no valid signature if `AttackerOrg.webhook_secret` is blank, since `verify_webhook_signature` returns `true` unconditionally in that case — `lib/shipit/github_app.rb` lines 76-83).
3. Send `POST /webhooks` with header `X-Github-Event: pull_request` and a JSON body where:
   - `repository.owner.login = "AttackerOrg"` (used only for signature org selection)
   - `repository.full_name = "VictimOrg/victim-repo"` (used by the handler to resolve the target repository/stack)
   - `action = "opened"`, plus a crafted `pull_request` object with attacker-chosen `head.ref`.
4. `verify_signature` passes (verified against `AttackerOrg`'s config). `PullRequest::OpenedHandler#process` resolves `Shipit::Repository.from_github_repo_name("VictimOrg/victim-repo")` and, if provisioning conditions are met, creates/provisions a review stack for the victim repository based entirely on attacker-supplied data — without ever having presented a signature tied to `VictimOrg`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
