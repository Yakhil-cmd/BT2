### Title
Uncaught exception on unbounded/non-finite numeric fields in `getHeadersSize` crashes unit validation - ([File: validation.js])

### Summary
The GHSA-ccw9-q5h2-8c2w advisory describes a DoS caused by a logical error in size/length computation during frame parsing: a crafted field causes the parser's length-accounting logic to throw, immediately crashing the process. `ocore`'s unit-commission validation has an analogous size-computation function, `getHeadersSize()` in `object_length.js`, that is invoked from `validation.js` **without** the exception-handling wrapper that its sibling function `getTotalPayloadSize()` receives, allowing a crafted unit posted by any unprivileged peer to trigger an uncaught exception during core validation logic.

### Finding Description
`object_length.js`'s `getLength()` throws hard `Error`s whenever it encounters a value it cannot size deterministically: [1](#0-0) 
- `case "number": if (!isFinite(value)) throw Error("invalid number: " + value);`
- an `undefined` property value throws `Error("undefined at " + key ...)`

`getHeadersSize(objUnit)` calls this length routine over the unit's header fields (including nested arrays such as `earned_headers_commission_recipients`, whose entries carry numeric `earned_headers_commission_share` fields) with no guard against non-finite numbers: [2](#0-1) 

In `validation.js`, the call to `getHeadersSize` used to check `headers_commission` is **not** wrapped in a try/catch, whereas the structurally identical call to `getTotalPayloadSize` immediately below it explicitly is: [3](#0-2) 

At the point `getHeadersSize` executes, `objUnit.earned_headers_commission_recipients` (and other header-region numeric fields) has not yet been validated for finiteness — that per-field validation happens later, in `validateAuthor`/related routines. Because JSON numeric literals with large exponents (e.g. `1e400`) are syntactically valid JSON but parse in JavaScript to `Infinity`, a unit poster can include such a literal in a header numeric field (e.g. `earned_headers_commission_recipients[i].earned_headers_commission_share`) so that when `getHeadersSize` sums the header object's length, it hits the `!isFinite(value)` branch and throws an uncaught `Error` — exactly the "logical error in frame/length parsing causing an immediate crash" pattern described in the advisory, just realized in JS length accounting instead of HTTP/2 frame length accounting.

### Impact Explanation
`validate()` is the central entry point for validating any unit received from a peer/light client/AA trigger before it is accepted into the DAG. An uncaught exception thrown synchronously inside this call path (outside of any try/catch, unlike the parallel `getTotalPayloadSize` path) will propagate up the call stack. Depending on how the calling context (`writer.js`/network layer) handles thrown errors versus promise rejections/callback errors, this can crash the Node.js process handling unit validation, taking down the node's ability to validate/confirm new units — a network-wide denial-of-service analogous to the HTTP/2 crash, reachable purely by posting a specially crafted unit (no special privilege required).

### Likelihood Explanation
Likelihood is high: any unit poster fully controls the JSON of `objUnit`, including nested numeric fields inside `earned_headers_commission_recipients`; JSON permits exponent literals that overflow to `Infinity` on parse, so crafting the payload requires no special access, is a one-shot "send a unit" attack, and hits code that runs unconditionally for every non-genesis serial unit during core validation.

### Recommendation
Wrap the `getHeadersSize(objUnit)` invocation(s) in `validation.js` in the same try/catch pattern already used for `getTotalPayloadSize`, converting any thrown error into a normal `ifJointError`/`ifUnitError` callback instead of letting it propagate as an uncaught exception. Additionally, harden `object_length.js`'s `getLength()` (or add upstream validation) to treat non-finite numbers and other malformed inputs as validation failures rather than throwing raw `Error`s from a function that is not consistently guarded by callers.

### Proof of Concept
Conceptual PoC (not independently executed against the live code in this session — recommend verification via a Devin session with full repo access):
1. Construct a unit JSON where `objUnit.earned_headers_commission_recipients` contains an entry with `earned_headers_commission_share: 1e400`.
2. Ensure the JSON is syntactically valid (it is, per JSON grammar for exponents) so `JSON.parse` yields `earned_headers_commission_share === Infinity`.
3. Submit the unit for validation such that it reaches `validate()` in `validation.js` and proceeds to the unguarded `objectLength.getHeadersSize(objUnit)` call at [4](#0-3) .
4. `getHeadersSize` → `getLength` hits `case "number": if (!isFinite(value)) throw Error(...)`, throwing an uncaught exception instead of returning a validation error, per [5](#0-4) .

**Note on confidence**: I was unable to fully trace, within this session, exactly how `writer.js`/the network dispatch layer handles a synchronously-thrown `Error` from within `validate()` (i.e., whether it is caught by an outer try/catch elsewhere in the call chain, which would reduce this to a validation-failure rather than a process crash). This should be confirmed by reading the full call chain from the P2P/network message handler down into `validation.js`'s `validate()` before treating this as a confirmed high-severity crash; if an outer catch exists, the practical impact would be reduced to a spurious/incorrect validation error rather than a process-level DoS.
