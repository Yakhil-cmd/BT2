## Analysis

I have enough evidence to establish the analog. The core mechanic mirrors the Ichi/vault report: a formula/oracle-style computation derives a price/share ratio from a **raw balance figure that is directly and unconditionally attacker-controllable**, rather than from an internally-tracked accounting variable, allowing donation-style manipulation.

In ocore, the `balance[asset]` formula operator (used pervasively in AA templates, including the officially-shipped reference AA `test/samples/uniswap_like_market_maker.oscript`) resolves to the AA's actual on-chain balance, read straight from `aa_balances` / `objValidationState.assocBalances` [1](#0-0) . Crucially, `updateInitialAABalances()` credits **every** payment sent to an AA address to this balance unconditionally, *before* any `if`-case of the AA is evaluated, and independent of whether any case ends up matching or the AA bounces [2](#0-1) . A bounced trigger (no matching case, or a `bounce()` call) does not return the received coins in general — the balance increase from `trigger.outputs` was already applied to `aa_balances` before the case-matching / bounce logic runs, and only the response unit's own explicit payments (if any) can move funds back out.

This means an attacker can send a plain payment directly to the AA's address that deliberately fails to satisfy any `if` guard (e.g., sending an amount below a threshold like `trigger.output[[asset=base]] > 1e5`, or sending only an asset the AA doesn't inspect) so that the AA bounces or silently accepts with no state update, while `balance[base]` / `balance[asset]` is nevertheless inflated. The reference market-maker AA then computes issuance/exchange amounts directly from these raw balances:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
$current_ratio = $asset_balance / $bytes_balance;
...
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
``` [3](#0-2) 

and for swaps:
```
$p = $asset_balance * $bytes_balance;
$new_asset_balance = round($p / balance[base]);
$amount = $asset_balance - $new_asset_balance;
``` [4](#0-3) 

Because `var['mm_asset_outstanding']` (the tracked "total supply" of MM shares) is updated only inside the matching `state` block of the "invest" case, while `balance[$asset]`/`balance[base]` are updated for *any* incoming payment regardless of case matching, an attacker can pre-inflate `$asset_balance`/`$bytes_balance` via a donation that bounces (or matches an unrelated catch‑all case) and then invoke the real "invest"/"divest"/"exchange" case, exactly as with the Ichi `getTotalAmounts()`/`balanceOf` donation attack: the ratio and constant‑product computations become skewed relative to the true supply of MM shares, letting the attacker mint more shares than deserved, extract more on divestment, or get a favorable swap rate, then withdraw to recover the donated funds.

This is a genuine bug-class match (donation/balance-inflation attack on AA-computed price/share ratios) but I could not find equivalent `balance[...]`-driven pricing logic in ocore's **core validation engine** itself (outside of example/test AA templates) — the vulnerable pattern lives in an AA author's own formula, not in ocore's protocol code. The `balance[asset]` and `var[...]` operators themselves behave exactly as documented and are not bugged; the risk is a design pitfall that AA authors (using this exact ocore-shipped reference implementation) inherit. I was not able to fully verify from the indexed context whether `bounce()` guarantees zero balance rollback in every version (I saw `updateInitialAABalances` apply balances before case matching, and no explicit refund-of-non-base-asset code path for a bounce, but a complete trace of every code path in `sendUnit`/`bounce` was not fully covered by the indexed snippets — this warrants closer, full-file review, e.g. via a Devin session with full-repo access, before treating this as conclusively verified).

Given this, I present it as the closest defensible analog, with the caveat noted above.

### Title
Donation/Balance-Inflation Manipulation of AA-Computed Share/Exchange Prices via `balance[asset]` - (File: test/samples/uniswap_like_market_maker.oscript, aa_composer.js)

### Summary
The Ichi report describes an oracle that derives price from `vault.getTotalAmounts()` (raw `balanceOf`) instead of a tracked reserve, letting an attacker inflate reserves by directly transferring tokens to the vault, thereby skewing `totalReserve / totalSupply`. The oscript analog is any AA (such as ocore's own reference "Uniswap-like market maker" template) that computes share-issuance ratios and swap amounts from `balance[asset]`/`balance[base]` — the AA's raw, unconditionally-credited on-chain balance — while tracking actual outstanding shares in a separate state variable (`var['mm_asset_outstanding']`) that is updated only when a specific `if`-case matches.

### Finding Description
`aa_composer.js`'s `updateInitialAABalances()` adds every payment received in a trigger unit to the AA's balance before any `if`-condition of the AA is evaluated, independent of whether a case matches or the trigger later bounces [2](#0-1) . The `balance[asset]` formula operator simply reads this raw, already-updated balance [5](#0-4) . In the reference market-maker AA, the "invest" and "exchange" branches compute `$asset_balance`/`$bytes_balance` from `balance[...]` and derive `$current_ratio`, `$investor_share_of_prev_balance`, and the constant-product `$p` directly from these values [3](#0-2) [6](#0-5) , while the true "supply" of MM shares is tracked separately in `var['mm_asset_outstanding']`, updated only within the matching case's `state` block [7](#0-6) . An attacker can send a payment that increases `balance[...]` but does not satisfy any `if`-case (so no state update happens), then immediately follow with a legitimate invest/divest/exchange trigger that reads the now-inflated balance to compute a manipulated ratio.

### Impact Explanation
If reachable in a deployed AA following this pattern (a pattern ocore itself ships as an example), the attacker can mint disproportionate MM shares relative to real reserves, extract more base/asset tokens than warranted on divestment, or obtain favorable swap rates in the constant-product branches — a fund-loss/theft outcome for other depositors of the AA, analogous to over-borrowing/mispriced liquidation in the Ichi report.

### Likelihood Explanation
Requires only a single unprivileged posted unit (a payment to the AA's address crafted to miss all `if` conditions) followed by a normal trigger — well within reach of any unit poster/AA trigger sender, with no special privilege needed, though it depends on a specific AA author actually implementing balance-based ratio pricing (as ocore's own shipped example does).

### Recommendation
AA authors should not use raw `balance[asset]` for computing share/exchange ratios; they should maintain and use explicit tracked reserve state variables (`var[...]`) that are updated on every relevant incoming payment (e.g., via a catch-all "accept coins" case, as seen in other ocore samples like `test/ojson.test.js:1353` "silently accept coins" pattern) so that donations cannot desynchronize tracked supply from the balance used in pricing formulas. ocore's documentation/example AAs (`test/samples/uniswap_like_market_maker.oscript`) should be updated to reflect this safer pattern, since it is likely used as a reference by real AA authors.

### Proof of Concept
1. Attacker sends a payment to the market-maker AA's address with `trigger.output[[asset=base]]` below `1e5` (or with an asset the "invest" case doesn't match), so no `if` case matches and the AA bounces or performs no state update — yet `balance[base]` (or `balance[$asset]`) is still incremented per `updateInitialAABalances()` [8](#0-7) .
2. Attacker (or an accomplice) then sends a legitimate "invest" trigger; `$bytes_balance = balance[base] - trigger.output[[asset=base]]` is now inflated relative to `var['mm_asset_outstanding']`, skewing `$current_ratio` and `$issue_amount` [9](#0-8) .
3. Attacker exploits the resulting mispriced issuance/exchange to extract more value than deposited, at the expense of other MM participants.
