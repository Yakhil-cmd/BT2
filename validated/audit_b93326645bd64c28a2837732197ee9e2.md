### Title
Cross-organization webhook authentication bypass: signature verification key selected by `repository.owner.login` while target stack is selected by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used to validate the HMAC signature based on `params.dig('repository','owner','login')` (falling back to `organization.login`), but the handler layer (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target `Repository`/`Stack` to act on using a *different* JSON field, `payload.dig('repository','full_name')`. In a multi-org Shipit deployment (as documented in `docs/setup.md`, "Using Multiple Github Applications"), these two fields are not cryptographically bound to each other by the verification logic — only the whole raw body is HMAC-signed, but the code never asserts that the *organization whose secret validated the signature* is the same organization that owns the *repository the payload will actually mutate*.

### Finding Description
This mirrors the Vault `takeFees` bug class: two values that should be enforced as equal (`fee expected` vs `fee actually minted`) are instead computed via two different formulas/fields, breaking an implicit invariant. Here the broken equality is:

`organization authenticated` (`repository.owner.login` used in `Shipit.github(organization: repository_owner)` → `verify_webhook_signature`) **must equal** `organization/repository written` (`repository.full_name` used in `Handler#stacks` → `Repository.from_github_repo_name`).

Relevant code:
- `app/controllers/shipit/webhooks_controller.rb:24-49` selects the verification key:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` resolves the actual target using a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because a self-hosted, multi-tenant Shipit instance can be configured with multiple GitHub Apps/organizations, each with its own `webhook_secret` (`test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one low-trust organization (e.g. "OrgTwo", for which they know/control the app's `webhook_secret` because they created and configured that GitHub App themselves per `docs/setup.md`) can:
1. Craft a JSON payload where `repository.owner.login` = `"OrgTwo"` (so `verify_signature` selects OrgTwo's `webhook_secret`) but `repository.full_name` = `"OrgOne/target-repo"` (a repository belonging to a different, higher-trust organization hosted on the same Shipit instance).
2. Correctly sign the whole raw body with OrgTwo's `webhook_secret`.
3. Send it to the shared `/webhooks` endpoint.

`verify_signature` succeeds because the signature really was produced with the (attacker-known) secret for OrgTwo. Event dispatch then proceeds with the full `params` unmodified, and handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) resolve `stacks` from `repository.full_name`, i.e. `"OrgOne/target-repo"`, triggering `stack.sync_github(expected_head_sha: params.after)` for a repository never authenticated by OrgTwo's secret.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," as called out in scope. Depending on which event/handler is exploited, this allows an attacker who only controls a low-trust org's GitHub App configuration on a shared Shipit instance to inject webhook events (push/status/check_suite/pull_request/membership) that are processed against a *different* organization's stacks — forcing `Stack#sync_github`, spoofed CI/commit statuses, spoofed `check_suite` refreshes, or fabricated `membership`/`pull_request` events against repositories they do not own or have access to. Combined with `MergeRequest#merge!` / `ProcessMergeRequestsJob`, or `PushHandler`-driven `sync_github`/CI-status forgery, this can enable unauthorized cross-repository actions and potentially unauthorized deploys/merges triggered later by the manipulated state, satisfying the Critical "cross-repository writes / unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
The setup requires the target instance to actually run in the documented multi-organization mode with more than one GitHub App configured (`docs/setup.md`, "Using Multiple Github Applications"). In that configuration, an attacker only needs to control (or have configured) one of the participating GitHub Apps' `webhook_secret` — which is explicitly allowed to be attacker-administered per org in this deployment model — and does not need any Shipit session, `ApiClient` token, or repository write access to the *target* org. This is realistic for any organization that hosts Shipit centrally for multiple, differently-trusted GitHub orgs/customers.

### Recommendation
Bind signature-key selection to the same field used for target resolution: derive both the verification organization and the acted-upon repository from the identical payload field (`repository.full_name`'s owner segment), and after verifying the signature, assert that `repository.owner.login` (or the org used to fetch the app) matches the owner segment parsed out of `repository.full_name` before dispatching to handlers. Reject the webhook if they diverge.

### Proof of Concept
1. Configure Shipit with two GitHub Apps as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with a distinct `webhook_secret`, both stacks (`OrgOne/target-repo`, `OrgTwo/attacker-repo`) hosted on the same Shipit instance.
2. As the administrator of `OrgTwo`'s GitHub App (attacker-controlled), build a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/target-repo"
  }
}
```
3. Sign the raw JSON body with OrgTwo's `webhook_secret` using HMAC-SHA1, and POST it to `/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")` and successfully verifies the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgOne/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgOne`'s stack, an action never authenticated by `OrgOne`'s own webhook secret. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
