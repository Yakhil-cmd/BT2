### Title
Webhook signature is bound to the organization named in the payload, not the repository the webhook handler actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a direct analog of the ContextModules bypass: LavaMoat verified the *loader function's* origin but not the *module path* it ultimately resolved to two different pieces of data governed by two different trust checks. Here, `WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App secret of whichever organization is named in the payload, but the event handlers that actually mutate state (`Repository`, `Stack`, `Team`, `Membership`) select their *target* from a different, unrelated payload field that the signature check never binds to that organization.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification purely from attacker-supplied payload data: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — a field fully controlled by whoever sends the raw POST body. `Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` config (each org can have its own `webhook_secret`, as shown by the multi-org secrets fixture) and verifies the HMAC of the raw body against **that org's** secret: [3](#0-2) [4](#0-3) 

Once verification succeeds, `WebhooksController#create` dispatches the *entire raw payload* to handlers, none of which re-check that the acted-upon resource belongs to the organization whose secret validated the signature: [5](#0-4) 

- `Handler#stacks` / `Handler#repository_name` resolve the target purely from `payload.dig('repository', 'full_name')`: [6](#0-5) 
- `PushHandler#process` calls `stack.sync_github` for every stack matching that `full_name`/branch: [7](#0-6) 
- `MembershipHandler#process` creates/updates `Team`/`Membership` records keyed by `params.team.id` and `params.organization.login`, again independent of which secret validated the request: [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` **==** `repository/organization actually written by the handler (repository.full_name / team.organization / organization.login used for Team/Membership)`.

The signature only proves "this raw body was HMAC-signed with organization X's secret." It proves nothing about which `repository.full_name` or `team`/`organization` object inside that same body the handlers will act on — those are separate JSON fields read independently by the `Handler` subclasses, and GitHub's real webhooks happen to keep them consistent, but the controller itself never enforces that consistency.

**Before the attack:** In a single-tenant Shipit instance this is inert because there's only one org/secret, so `repository_owner` always equals the org that owns the actual target repo. **After the attack:** In any Shipit deployment configured for **multiple GitHub organizations** (the documented multi-org `secrets.yml` schema, each with its own `webhook_secret`/App), an attacker who legitimately controls one configured organization (e.g., they are an admin of a small/test org that this Shipit instance also serves, and therefore know or can trigger genuine signed traffic — or, more critically, who has obtained/knows that org's `webhook_secret` through any means short of full compromise, such as being an authorized webhook admin for their own org's GitHub App) can POST a raw body to `/webhooks` where `repository.owner.login`/`organization.login` = their own org (so `verify_signature` picks and matches their own org's secret), while `repository.full_name`, `team.id`, etc. point at a victim organization's stack/repository/team. The signature check passes, and the handler blindly acts on the victim's resources — e.g. forcing `sync_github`, mutating `Team`/`Membership` records tied to a different org, or archiving a `review_stack` for a repository the attacker's org secret was never meant to authorize.

### Impact Explanation
This crosses the "authentication bypass" boundary the engine relies on: the webhook signature exists specifically to prove a payload came from GitHub for a given org/repo, but the code lets one authenticated organization's credential authorize writes against another organization's `Stack`, `Team`, and `Membership` records. That satisfies the High-impact bar (escalation into `Shipit.github_teams` authorization via forged `membership` events creating/altering `Team`/`Membership`, and unauthenticated write access to another org's stack/task state via forced `sync_github`/archive actions) and, depending on configuration, can trigger unwanted syncs/deploy-flow side effects on stacks that belong to organizations the attacker's credentials were never scoped to.

### Likelihood Explanation
Exploitability requires a Shipit deployment configured for multiple GitHub organizations (documented, supported feature — `Shipit.github_organizations`, `github_app_config`), and requires the attacker to possess a valid webhook secret for at least one of those configured organizations (e.g., because they administer that org's GitHub App installation). This is a narrower precondition than a single-org deployment, but it is a legitimate, in-scope, unprivileged-relative-to-the-victim-organization attack path: the attacker never needs `GITHUB_TOKEN`, an `ApiClient` token, or Shipit session — only their own org's webhook credential, which the engine's own multi-tenant design hands out per-organization.

### Recommendation
In `WebhooksController#verify_signature` and `Shipit::Webhooks::Handlers::Handler`, after signature verification, re-derive and enforce that the organization used to select/verify the webhook secret matches the owner of every repository/organization/team object the payload references before invoking handlers — i.e., reject (422) any payload where `repository.owner.login`/`organization.login` used for other handler-side lookups differs from the `repository_owner` that selected the verifying secret.

### Proof of Concept
```
# Multi-org Shipit instance with orgs "attacker-org" (attacker administers its GitHub App)
# and "victim-org" (the real target), per test/dummy/config/secrets_double_github_app.yml schema.

POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's known webhook_secret>

{
  "action": "added",
  "team": { "id": 999, "name": "Victim Admins", "slug": "victim-admins", "url": "https://x" },
  "organization": { "login": "victim-org" },   # acted upon by MembershipHandler
  "member": { "login": "attacker-github-user" },
  "repository": { "owner": { "login": "attacker-org" } }  # only used by verify_signature
}
```
`WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully because the attacker signed with `attacker-org`'s secret. `MembershipHandler#process` then creates/updates a `Team` with `organization: "victim-org"` and adds `attacker-github-user` as a member — entirely outside the organization whose secret actually authorized the request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
