### Title
Commission/size accounting uses UTF-16 code-unit string length instead of UTF-8 byte length, allowing underpaid commissions and MAX_UNIT_LENGTH bypass - (File: object_length.js)

### Summary
CVE-2017-17784 is a heap over-read in GIMP's `.gbr` parser caused by trusting a declared length field that does not match the real UTF-8 byte length of the embedded string. The analogous root cause in `ocore` is a length/size accounting bug: unit size and commission calculations are computed from the JavaScript string `.length` (UTF-16 code units) rather than the actual UTF-8 byte length that is used everywhere else (hashing, network transport, storage) — a "mishandling of UTF-8 data" that produces a systematic size-accounting mismatch reachable by any unprivileged unit poster.

### Finding Description
`getLength()` in [1](#0-0)  computes the "byte size" of a string field simply as `value.length`, which is the number of UTF-16 code units, not the number of UTF-8 bytes. This function is used to compute `getHeadersSize()` and `getTotalPayloadSize()` [2](#0-1) , which in turn are compared against the author-supplied `headers_commission` and `payload_commission` fields and against `constants.MAX_UNIT_LENGTH` in `validation.js` [3](#0-2) .

Meanwhile, the actual cryptographic hash of the unit — and its actual transmitted/stored representation — is computed over the UTF-8 encoding of the same strings, via `getSourceString`/`getJsonSourceString` and `crypto.createHash(...).update(sourceString, "utf8")` in [4](#0-3) , and `chash.getChash160`/`getChash288` also hash with `"utf8"` encoding [5](#0-4) .

Any string field in a unit's headers or payload that contains characters in the Basic Multilingual Plane outside the ASCII range (e.g., U+0800–U+FFFF, common CJK, many symbols) occupies 3 bytes in UTF-8 but counts as only 1 unit toward `.length`. An attacker can construct a unit whose messages/payloads/data fields are filled with such multi-byte characters so that the "declared" size (`headers_commission` + `payload_commission`, validated to equal `getHeadersSize()`/`getTotalPayloadSize()`) is much smaller than the unit's true UTF-8 byte size that must actually be hashed, transmitted, and persisted by every full node.

This is directly analogous to the GIMP CVE: a size/length value derived without correctly accounting for UTF-8 multi-byte encoding is used to size buffers/require resources, while the real underlying data is UTF-8-encoded and larger than assumed.

### Impact Explanation
Because `MAX_UNIT_LENGTH` and the required commission are checked against the UTF-16-code-unit count rather than the real UTF-8 byte size [3](#0-2) , a malicious poster can craft units that are up to ~3x larger in actual bytes than what they are paying commission for and what the size cap nominally permits. This lets an attacker:
- Underpay `headers_commission`/`payload_commission` relative to the true resource cost imposed on witnesses and the network (economic short-change of the fee model that funds witnesses/headers-commission recipients).
- Smuggle units whose real serialized/hashed byte size exceeds `MAX_UNIT_LENGTH`, degrading storage and bandwidth assumptions across all full nodes, which can be leveraged for a low-cost network-wide resource-exhaustion vector (a network less able to process/confirm new units at expected cost, since actual data volume outpaces the commission collected for it).

This falls under the allowed "payment inputs/outputs and commissions" analog category, since it directly affects the commission accounting that funds the network's unit-processing economy.

### Likelihood Explanation
Any unprivileged unit poster can trigger this by simply including strings with multi-byte UTF-8 characters (e.g., in `data`, `data_feed`, `profile`, or other payload text fields, or in `alt`/`payload_uri` type fields) — no special privileges, race conditions, or peer manipulation are required. The mismatch is deterministic and purely a function of the characters chosen.

### Recommendation
Change `getLength()` (and any other size-accounting logic, including headers/payload commission checks) to compute the true UTF-8 byte length of strings, e.g. `Buffer.byteLength(value, 'utf8')` instead of `value.length`, so that declared/paid commission and `MAX_UNIT_LENGTH` enforcement match the actual UTF-8-encoded size used for hashing and storage.

### Proof of Concept
1. Construct a unit whose payload (e.g., a `data` message) contains a large string composed of repeated 3-byte UTF-8 characters, e.g. `'\u4e2d'.repeat(N)` (Chinese character "中", which is 1 UTF-16 code unit / 3 UTF-8 bytes).
2. Compute `payload_commission` as `objectLength.getTotalPayloadSize(objUnit)` would (i.e. `N`), rather than the true byte size (`3*N`).
3. Submit the unit with the low, "code-unit"-based commission value; `validation.js`'s check `objectLength.getTotalPayloadSize(objUnit) !== objUnit.payload_commission` [6](#0-5)  will pass because it uses the same flawed `getLength()` function, while the unit's real UTF-8 payload (and its hash input) is 3x larger than what was paid for and than what the `MAX_UNIT_LENGTH` check assumed.
