### Title
AA `balance[]` accounting includes dust outputs that are permanently unspendable, making vault-style share/asset conversions inaccurate - (File: `formula/evaluation.js`, `aa_composer.js`)

### Summary
The AA `balance[address][asset]` formula and the underlying `aa_balances` table represent an Autonomous Agent's "total assets" as a running, incrementally-maintained sum of every output ever received. This value is used by AA authors (e.g. vault/DEX-style contracts) to compute share-to-asset conversion ratios. However, when an AA actually tries to spend its bytes balance to build a real payment, tiny ("dust") outputs below `FULL_TRANSFER_INPUT_SIZE` are silently excluded and can never be used as inputs. These dust amounts are nevertheless still counted in `balance[]`/`aa_balances`, so the reported "total assets" is inflated relative to what the AA can actually pay out — exactly the class of bug described in the report (assets locked/unusable still counted in `totalAssets`).

### Finding Description
The `balance[]` oscript formula reads directly from the `aa_balances` accounting table rather than from an on-demand computation of currently spendable outputs: [1](#0-0) 

`aa_balances` is populated/maintained incrementally in `updateInitialAABalances`/`updateFinalAABalances` by summing every output amount the AA address receives, with no lower-bound filter on the output size: [2](#0-1) 

The same unfiltered summation is used when an AA is first defined, backfilling `aa_balances` from all its historical outputs: [3](#0-2) 

By contrast, when the AA actually composes a real payment (spending its bytes balance), `readStableOutputs` explicitly excludes any base-asset output smaller than `FULL_TRANSFER_INPUT_SIZE` ("byte outputs less than 60 bytes ... are ignored to prevent dust attack") because spending them would cost more in fees than they are worth: [4](#0-3) 

So the value reported by `balance[this_address]['base']` (and used by AA logic for computing shares, redemption ratios, "total assets held", etc.) can include an arbitrary amount of dust that is permanently unspendable by the AA, exactly paralleling the reported vault bug where locked/non-transferable assets are still counted in `totalAssets`.

### Impact Explanation
Any AA that implements a vault/pool-style contract and uses `balance[this_address][asset]` to determine a share price or asset/share conversion ratio (a documented and expected pattern in ocore AAs) will compute an inflated "total assets" figure. This causes:
- Overpricing shares for new depositors (existing depositors effectively subsidize the attacker), or
- The AA becoming unable to fully honor share redemptions proportional to its reported balance, since a portion of the "balance" can never actually be spent — a fund-freezing condition for legitimate depositors.

An unprivileged attacker can trigger this simply by sending many tiny payments (below `FULL_TRANSFER_INPUT_SIZE`) to the AA address, which is a normal, permissionless action (posting a payment unit) — no special privilege needed.

### Likelihood Explanation
High reachability: any address can send arbitrarily many sub-threshold payments to any AA at negligible cost (bytes cost approaches the dust amount itself), continuously growing the divergence between `balance[]` and the AA's real spendable funds. Any AA relying on `balance[]` for asset/share accounting (a natural, encouraged pattern) is affected.

### Recommendation
- Either exclude dust outputs (amount < `FULL_TRANSFER_INPUT_SIZE`) from the `balance[]`/`aa_balances` accounting so the reported figure matches actually spendable value, or
- Document explicitly that `balance[]` can diverge from spendable funds due to dust, and provide/require AA authors to use a spendable-balance-aware formula (or a getter that subtracts known unspendable dust) when implementing share/asset conversion logic.

### Proof of Concept
1. Deploy an AA that tracks deposits/shares via `balance[this_address]['base']` (a common vault pattern in oscript, e.g. `order_book_exchange.oscript`'s `balance_` state-var pattern conceptually mirrors reading a running balance).
2. An attacker repeatedly sends many outputs of, say, 10–50 bytes each to the AA address (`amount < FULL_TRANSFER_INPUT_SIZE`, referenced in `aa_composer.js:1144`).
3. Each such payment increases `aa_balances`/`balance[this_address]['base']` via `updateInitialAABalances` (`aa_composer.js:491-524`), inflating the AA's reported total assets.
4. When the AA later composes an actual outgoing payment, `readStableOutputs` (`aa_composer.js:1140-1155`) skips all these dust outputs as inputs, so they can never be spent/withdrawn.
5. Any share/asset ratio computed from `balance[]` is now based on a total that includes funds the AA can never actually distribute, producing incorrect conversions and potential fund freezing for legitimate participants — the same root cause as the reported Vault `totalAssets` issue.
