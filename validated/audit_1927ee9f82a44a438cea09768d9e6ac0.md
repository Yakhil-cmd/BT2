### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` webhook processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` selects which GitHub App/`webhook_secret` to use for HMAC verification based on a payload field (`repository.owner.login`), but `Shipit::Webhooks::Handlers::StatusHandler` — unlike every other webhook handler — never checks that field, or any repository/organization scoping, before mutating state. This breaks the binding "the organization that authenticated the request" == "the repository/commit that is written", exactly analogous to the Connext bug where the signed `invariantData` did not bind the actual caller/parameters that got acted upon.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret to verify against using a value taken straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

This design is intentional to support a single Shipit instance handling several GitHub organizations, each with its own GitHub App/`webhook_secret`, as documented in the multi-org config example: [3](#0-2) 

Once the signature check passes (proving only that *some* configured organization's secret was used — the attacker's own, legitimately-known secret for their org), the request body is dispatched to handlers keyed only by event type: [4](#0-3) 

Every other handler re-derives the target repository from `payload.dig('repository', 'full_name')` and scopes its side effects to that repository's stacks, e.g. the generic base `Handler#stacks`/`repository_name` and `PushHandler`: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, performs **no repository/organization scoping at all** — it looks up commits globally by `sha` across the entire Shipit instance: [7](#0-6) 

`Commit#create_status_from_github!` (via `add_status`) can schedule merges/continuous-delivery deploys once a commit transitions to `pending`/`success`: [8](#0-7) 

Because commit SHAs are public GitHub data, an attacker who controls (or has legitimately configured) the webhook secret for **any one** organization registered on the same multi-tenant Shipit instance can:
1. Sign a `status` webhook payload with `repository.owner.login` set to *their own* organization (so `verify_signature` picks their own valid secret and the HMAC passes).
2. Set `sha` to the known commit SHA of a completely unrelated, victim organization's repository/stack tracked by the same Shipit instance.
3. Set `state: "success"` (or any state) and any `context`.

`verify_signature` never re-checks that the org used to select the secret matches the repository the event claims to describe, and `StatusHandler` never checks repository ownership before writing the status — the two fields (`repository.owner.login` used for authentication, and `sha` used for the write) are never bound together.

### Impact Explanation
This lets a party controlling one organization's webhook secret on a shared Shipit deployment forge CI/commit-status updates for any other organization's stacks. Because `Status` creation can call `stack.schedule_merges` and drive continuous deployment (`add_status` in `commit.rb`), this can result in an **unauthorized deploy** being triggered against a victim's stack from a completely different, non-authorized GitHub organization/credential — matching the "unauthorized deploy" Critical impact bucket, without the attacker ever needing write access, a Shipit session, or an `ApiClient` token for the victim's org.

### Likelihood Explanation
Any Shipit deployment configured for multiple GitHub organizations (the multi-org config format is first-class and documented) is affected. An attacker only needs legitimate control of one organization's GitHub App/webhook secret (e.g. any org they administer that is also configured on the same shared instance) and knowledge of a target commit SHA, which is public on GitHub. No interaction with the victim org is required.

### Recommendation
Bind the authenticated organization to the data being acted upon:
- Require `StatusHandler` (and any other handler) to scope lookups by `repository.full_name`/owner the same way `Handler#stacks` does, rejecting/ignoring events whose payload repository does not belong to the organization whose secret validated the signature.
- Alternatively, have `verify_signature` record the verified organization and pass it down to handlers, asserting `commit.stack.repository.owner == verified_organization` before applying any status/state change.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, tracked stack with `continuous_deployment: true`).
2. Attacker finds a public commit SHA `abcd123` on `orgB/victim-repo` that is the head of an undeployed batch.
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status`, body:
```json
{
  "sha": "abcd123",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
}
```
   signed with `orgA`'s real `webhook_secret` (`X-Hub-Signature` computed over this exact body).
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, verifies successfully against the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: "abcd123")`, finds the victim's commit (in `orgB`'s stack), and calls `create_status_from_github!`, which can flip the commit's CI status to `success` and trigger `stack.schedule_merges`, causing an unauthorized deploy on `orgB`'s stack — despite the attacker never authenticating as, or holding any credential for, `orgB`.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
