This confirms the analog: when a primary AA sends payment to another AA as part of its response (triggering a secondary trigger), if that secondary AA bounces for any reason, the entire primary AA response is rolled back via `revert()`, which calls `revertResponsesInCaches`, wipes all `arrResponses`, clears `stateVars`, and issues `conn.query("ROLLBACK TO SAVEPOINT initial_balances")` before finally sending only a bounce message back to the original trigger sender.

### Title
Malicious secondary AA can force reversion of an unrelated primary AA's entire response, causing denial-of-service on state changes and payments - ([File: aa_composer.js])

### Summary
`handleTrigger` propagates payments from a primary (or any parent) AA to a receiving address; if that address is itself an AA, `handleSecondaryTriggers` invokes `handleTrigger` recursively with `bSecondary=true` [1](#0-0) . If the secondary AA bounces (returns an error via `bounce()`), the error propagates up through `async.eachSeries`'s final callback, and for a non-secondary (primary) caller this results in `revert({message: "one of secondary AAs bounced with error: ", ...})` [2](#0-1) . `revert()` discards all accumulated `arrResponses`, restores `stateVars`, clears the write `batch`, and rolls the database transaction back to the initial savepoint, before turning the whole trigger into a mere bounce [3](#0-2) .

### Finding Description
This is structurally analogous to the reported `AvailBridge::sendETH` issue: a payment to a downstream recipient that can unconditionally "reject" the transfer (by reverting/bouncing) causes the *entire* upstream operation to fail, not just the specific transfer. In ocore, any AA (`primary_aa`) whose logic includes a payment to another AA address (`secondary_address`) as part of a documented flow — e.g., forwarding fees, paying a partner/treasury AA, or any generic "send funds onward to a registered AA" pattern (as shown in `test/aa_composer.test.js:156-252` "chain of AAs" test) — is exposed to this: the receiving AA fully controls whether it bounces on the incoming trigger. Since AA definitions and addresses are permissionless and can be deployed by anyone, an attacker can:
1. Get their address registered as (or pre-deploy) the AA that the victim primary AA is designed to pay (e.g. via governance/config that lets users set a destination AA address, or via any address the victim treats as unprivileged/user-supplied).
2. Make that AA's `bounce_fees`/logic always fail (bounce unconditionally) upon any incoming payment from the victim AA.
3. Every time the victim AA is triggered, its payment to the attacker's AA causes a secondary bounce, which triggers `revert()` on the primary trigger, unwinding all of the primary AA's state changes and turning the whole interaction into a simple bounce of the original user's funds (minus bounce fee) back to them.

This means any legitimate user's trigger to the victim AA never succeeds as long as the attacker's AA is configured as (or reachable as) the downstream recipient — a persistent denial-of-service on the victim AA's core functionality, and any state updates that the AA was supposed to perform (e.g. accounting, distribution logic) never take effect.

### Impact Explanation
This blocks confirmation/execution of the victim AA's intended logic entirely: legitimate triggers systematically bounce, state variables never update, and funds are only returned (minus bounce fee) rather than being put to their intended use. For AAs whose business logic depends on completing a downstream payment (e.g., proxies, fee splitters, escrow/exchange AAs forwarding funds to a partner AA, as illustrated by `test/samples/fundraising_proxy.oscript` forwarding funds to `$destination_aa`), this is a full denial-of-service of the AA's primary function, and it is triggerable by any unprivileged actor who can become (or is already) the configured downstream AA.

### Likelihood Explanation
Reaching this requires only deploying an ordinary AA definition (permissionless, `readAADefinition`/`aa_addresses` have no gating on who can post an AA) that always bounces on receipt of payment, and getting the victim to pay it — which is a design pattern the codebase itself demonstrates as normal usage (chained AA calls, proxy/factory AAs). No privileged access, node compromise, or network-level attack is needed.

### Recommendation
For AAs that need best-effort forwarding of funds to a third-party AA whose behavior is not fully trusted/controlled, the `revert()`-on-secondary-bounce semantics needs a way to be opted out of (e.g., an oscript primitive to catch a failed downstream secondary-trigger send without unwinding the whole primary response), or documentation should more strongly warn that payments to arbitrary/attacker-influenceable AA addresses can be weaponized to permanently DOS the calling AA. At minimum, developers should be warned in the AA composer/documentation that `handleSecondaryTriggers`'s all-or-nothing rollback (`aa_composer.js:1743-1798`) makes any payment to an untrusted or user-configurable AA address a full availability risk to the caller's own logic.

### Proof of Concept
1. Deploy `attacker_aa`: an AA whose only message is one that always calls `bounce(...)` regardless of trigger data (e.g., any AA definition with `messages.cases` guarded by a formula that always evaluates false, forcing the "no messages" bounce path in `aa_composer.js:1869-1870`, or one that explicitly calls `bounce()`).
2. Deploy or identify `victim_aa`, which — as part of normal operation — sends a payment message to `attacker_aa`'s address (this mirrors the "chain of AAs" pattern at `test/aa_composer.test.js:156-186`, where `primary_aa` pays `secondary_address`).
3. Any user sends a trigger unit to `victim_aa` with sufficient bytes to cover `bounce_fees`.
4. `victim_aa`'s response includes a payment to `attacker_aa`; `handleSecondaryTriggers` invokes `attacker_aa` as a secondary trigger, which bounces.
5. `handleSecondaryTriggers`'s `async.eachSeries` final callback sees a non-empty error and, since `bSecondary` is false for `victim_aa`, calls `revert(...)`, which rolls back `victim_aa`'s state changes and turns the whole interaction into a simple bounce of the user's payment back to them [4](#0-3) .
6. Repeat for every subsequent trigger — `victim_aa` can never successfully execute its logic while `attacker_aa` remains the configured/reachable downstream recipient.
