### Title
Wallet Accepts Attacker-Defined "Shared Address" Compositions Binding a Victim's Own Address Under Arbitrary (Including Sole-Custody) Conditions Without Owner Consent - (File: wallet_defined_by_addresses.js)

### Summary
The RustFS bug is caused by an endpoint that accepts an attacker-controlled `parent` value and materializes a new privileged credential under that arbitrary parent without checking that the caller is authorized to act on behalf of that parent. The equivalent trust boundary in ocore is the wallet's peer-to-peer "shared address" protocol: `handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts a definition and a `signers` map from *any* paired correspondent device and, if any leaf `["address", X]` in the supplied definition happens to be one of the receiver's own `my_addresses`, silently registers the whole composite address as a `shared_addresses` entry — without ever confirming that the address owner deliberately agreed to *this specific* boolean composition (e.g. an `"or"` between the victim's key and an attacker's key, instead of the expected `"and"`).

### Finding Description
`handleNewSharedAddress(body, callbacks)` [1](#0-0)  is the handler for network/device messages that create local records of shared (multi-party) addresses. Its checks are purely structural:
- `body.definition` is a 2-element array and `body.address` equals its chash160 (i.e. it just checks internal consistency of attacker-supplied data, not authorization).
- Each `signerInfo.address` in `body.signers` is a syntactically valid address.
- `extractAddressPathsFromDefinition()` [2](#0-1)  is used only to check that the `signers` map is internally self-consistent with the `definition` (path → address correspondence), not that the referenced addresses' real owners approved joining this composition.
- `determineIfIncludesMeAndRewriteDeviceAddress()` [3](#0-2)  only confirms that *some* address in the message already belongs to the local `my_addresses`/`shared_addresses` tables; it does not ask the user whether they consent to be combined with the other, attacker-chosen member(s) under the attacker-chosen operator.
- `validateAddressDefinition()` [4](#0-3)  only checks that the definition is a *syntactically legal* spending condition (via `Definition.validateDefinition`), which happily accepts `["or", [["address", VICTIM], ["address", ATTACKER]]]` — a condition satisfiable by either party alone.

If all these purely-syntactic checks pass, `addNewSharedAddress()` [5](#0-4)  unconditionally inserts the row into `shared_addresses` / `shared_address_signing_paths`, and for light clients even starts watching the address on the network (`network.addLightWatchedAddress`). This is the receive-side path, distinct from the locally-initiated `create_new_shared_address` flow in `wallet.js`, which explicitly emits an event so the UI can show the user a confirmation dialog before creation [6](#0-5) . No analogous confirmation gate exists in the network-triggered `handleNewSharedAddress` path.

This mirrors the RustFS root cause precisely: an endpoint reachable by an unprivileged party (a correspondent device, analogous to a low-privileged IAM user) accepts an attacker-controlled structural definition ("parent"/composition) referencing a victim's own identity/key and, after only syntactic validation, persists a new credential structure that the victim never consciously authorized — enabling the attacker to obtain co-equal or even sole control over what appears to the victim's wallet as one of "its own" addresses.

### Impact Explanation
Once such a spoofed shared address is registered, funds later sent to it (by the victim, believing it to be a legitimate joint/multisig address they participate in, or by any third party who queries the victim's wallet for a payment address) can be spent unilaterally by the attacker if the injected definition uses `"or"` (or any similarly weak boolean combination) instead of the semantically-implied `"and"`. This is a concrete unauthorized-spending / fund-loss vector: the attacker did not need to compromise the victim's private key — the wallet software itself was tricked into recognizing a spending condition that grants the attacker sole custody, purely through an unauthenticated device-protocol message.

### Likelihood Explanation
Any paired correspondent (chat contact) can send this message — pairing between Obyte wallet devices is the normal mechanism for exchanging payment requests and is often established with low friction (QR code / pairing link), making the attacker an "unprivileged" party from the ocore trust-model perspective. The victim's own address does not need to be secret — many Obyte flows involve sharing an address for payment. I was not able to fully verify, within the available investigation, whether a later UI layer built on top of the eventBus (`"new_address"` event fired in `addNewSharedAddress`) additionally warns the user before the shared address is used for outgoing payments; this is a caveat on real-world exploitability that would require examining wallet UI code outside `ocore` itself (this repo is the core library, and the UI/wallet-frontend that consumes these events is likely a separate repository not indexed here).

### Recommendation
In `handleNewSharedAddress`, before calling `addNewSharedAddress`, require explicit local-user confirmation (an event similar to the one already used in the local `create_new_shared_address` flow) whenever the incoming definition combines one of the receiver's own addresses with any signer the receiver does not already trust, and clearly surface the actual boolean logic (in particular flag `"or"`/single-signer-sufficient conditions) so the user can reject compositions that grant sole custody to an unfamiliar counterpart. Additionally, consider rejecting or specially flagging shared-address definitions that permit a *strict subset* of members (fewer than all of them) to unilaterally satisfy the condition, since such compositions are inherently able to bypass the "joint control" expectation that shared addresses normally provide.

### Proof of Concept
1. Attacker pairs with victim's Obyte wallet as a correspondent device.
2. Attacker learns (or infers) `VICTIM_ADDRESS`, one of the addresses in victim's `my_addresses`.
3. Attacker builds `arrDefinition = ["or", [["address","VICTIM_ADDRESS"], ["address","ATTACKER_ADDRESS"]]]` and computes `shared_address = chash160(arrDefinition)`.
4. Attacker sends victim's device a `new_shared_address` message: `{address: shared_address, definition: arrDefinition, signers: {"r.0": {address:"VICTIM_ADDRESS", device_address:"VICTIM_DEVICE"}, "r.1": {address:"ATTACKER_ADDRESS", device_address:"ATTACKER_DEVICE"}}}`.
5. `handleNewSharedAddress` passes all structural checks (definition hashes correctly, signer paths match, `VICTIM_ADDRESS` is found in `my_addresses`), and `addNewSharedAddress` silently records `shared_address` in the victim's `shared_addresses` table, without any confirmation dialog, as observed in `wallet_defined_by_addresses.js` lines 377-415 and 239-268 [1](#0-0) .
6. If the victim (or a third party paying the victim) subsequently sends funds to `shared_address`, the attacker can spend them alone by satisfying the `"or"` branch with `ATTACKER_ADDRESS`.

function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
