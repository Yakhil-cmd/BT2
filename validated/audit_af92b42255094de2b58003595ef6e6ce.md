### Title
CCMenu API token scoped to one stack can read build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolution helper in a way that ignores the stack restriction (`stack_id`) that is normally enforced on an `ApiClient`. This breaks the binding: `current_api_client.stack_id` (the stack a token is authorised for) `== stack` (the stack the request actually reads), and lets a valid, stack-scoped CCMenu token read build/deploy state for stacks it was never granted access to.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column (`belongs_to :stack, optional: true`), and every other API controller enforces this scope through `BaseController#stacks`/`#stack`: [1](#0-0) 

This is a deliberate, tested authorization boundary — a stack-scoped `ApiClient` must only ever "see" the one stack it was authorised for, as verified by: [2](#0-1) 

However, `CCMenuController` (used to expose CCTray/CCMenu build-status XML, and reachable with only a bare `token` query parameter, see `authenticate_api_client` override) redefines `stack` to bypass the `stacks` scope entirely and resolve any stack by parameter: [3](#0-2) 

Whereas the correct/expected behavior (as implemented everywhere else, e.g. `Api::StacksController`) is `stack = stacks.from_param!(params[:stack_id])`, which filters through `Stack.where(id: current_api_client.stack_id)` when the client is scoped. `CCMenuController#stack` instead calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, so `require_permission :read, :stack` only checks that the token has the `read:stack` permission bit — it never checks that the token is authorised for *this* specific stack.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped CCMenu token (e.g. one generated for a public/low-trust integration such as a CI status badge, via `CCMenuUrlController`/an admin-provisioned scoped `ApiClient`) can supply an arbitrary `stack_id` and retrieve `deploys_and_rollbacks` status (last build status/label/time, lock state, etc.) for any stack in the installation, not just the one the token was scoped to. This is an authorization-boundary escape reading stack/task state that the presenter (token) was never granted, matching the "High — unauthenticated/unauthorized read of stack state, task streams or deploy output" impact class.

### Likelihood Explanation
Exploitation only requires possession of any valid CCMenu-style token (these are handed out for read-only CI status widgets and are commonly embedded in less-trusted places, e.g. CI dashboards) and changing the `stack_id` request parameter — no additional privilege or session is required. The scoping bypass is deterministic and always triggers because `stack` is unconditionally overridden.

### Recommendation
Make `CCMenuController#stack` honor the same scope as the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely so it inherits `BaseController#stack`/`#stacks`, restoring the invariant `current_api_client.stack_id == stack.id` (when the client is scoped).

### Proof of Concept
1. Provision (or use fixture-equivalent) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']`, obtaining its `authentication_token`.
2. Call `GET /api/stacks/:B/ccmenu.xml?token=<token>` where `B` is a *different* stack's `to_param`.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (client has `read:stack`), and `stack` resolves to stack `B` via unscoped `Stack.from_param!`, returning `B`'s build status/deploy XML even though the token was only authorised for stack `A`.
