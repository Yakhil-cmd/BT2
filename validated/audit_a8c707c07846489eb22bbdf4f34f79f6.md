### Title
Webhook signature verification is bound to the wrong field — organization used to select the HMAC secret is never checked against the repository the payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the inbound HMAC based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Every event handler, however, resolves the actual repository/stack to mutate from a completely independent field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) , reused identically across `PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ClosedHandler`, `PullRequest::LabelCapturingHandler`, etc. [4](#0-3) [5](#0-4) . Nothing checks that the owner segment of `repository.full_name` is the same organization whose `webhook_secret` was actually used to authenticate the request.

### Finding Description
The HMAC verification proves only "this body was signed with organization X's secret" — it does not prove "this body concerns a repository belonging to organization X." [6](#0-5)  computes the HMAC over the whole raw body using `@webhook_secret`, which is per-organization config `Shipit.github(organization: repository_owner)` [7](#0-6) . The `repository_owner` value used to pick this secret comes straight from `repository.owner.login` in the same JSON body the attacker fully controls (as long as they know a valid secret for *some* configured organization). Since `repository.owner.login` and `repository.full_name` are independent JSON keys inside the same object, an attacker can set:
- `repository.owner.login = "OrgA"` (used only to pick OrgA's `webhook_secret` for the signature check), while
- `repository.full_name = "OrgB/some-tracked-repo"` (used by every `Handler` subclass to look up `Repository.from_github_repo_name` and act on it).

The binding broken is exactly: *organization authenticated* (OrgA, via `webhook_secret` lookup) ≠ *repository that is written* (OrgB, via `repository.full_name` used in `stacks`/handler logic). This satisfies the analog class described in the prompt (organization authenticated vs. repository written).

### Impact Explanation
Given knowledge of any one organization's `webhook_secret` configured in a multi-organization Shipit deployment, an attacker can forge signed webhook deliveries that pass `verify_signature` but drive handlers against a stack belonging to a *different* organization/repository they have no relationship with:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack matching the forged branch on the target repo [8](#0-7) , letting the attacker force syncs/CI/status recomputation on repos outside the org whose secret they hold.
- `PullRequest::OpenedHandler`/`ClosedHandler`/`LabelCapturingHandler` create, archive, or unarchive `ReviewStack`s (which provision/deprovision infrastructure) for the target repo [9](#0-8) [10](#0-9) .

This is a cross-repository write crossing an authorization boundary that the webhook secret was meant to enforce (per-organization isolation), matching the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Exploitability requires the attacker to already possess a valid `webhook_secret` for at least one organization configured in the Shipit instance (e.g., they are an org admin, or a secret leaked/was reused). Given that, the rest of the attack is a single crafted HTTP POST with mismatched `owner.login` vs `full_name` fields — no other credential, session, or GitHub write access is required to affect the second organization's stacks. This is a moderate-likelihood issue specifically for multi-tenant Shipit deployments that host stacks for more than one GitHub organization.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` from the resolved `repository.full_name` (or the `organization` object) and assert that both agree on the authenticated organization before dispatching to handlers; reject the request (422) if they diverge. Additionally, `Handler#stacks`/`repository_name` should validate that `Repository.from_github_repo_name(...).owner` matches the organization whose secret validated the request, rather than trusting the payload's `full_name` unconditionally.

### Proof of Concept
1. Configure two organizations in Shipit, `OrgA` (attacker-controlled webhook secret `secretA`) and `OrgB` (victim, tracked repo `OrgB/victim-repo` with an active stack).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Sign the raw body with `secretA` and send it as `X-Hub-Signature` to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully [11](#0-10) .
5. `PushHandler#process` is invoked with the same payload; `stacks` resolves via `Repository.from_github_repo_name("OrgB/victim-repo")` [3](#0-2)  and triggers `sync_github` on OrgB's stack, despite the request never being authenticated against OrgB's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
