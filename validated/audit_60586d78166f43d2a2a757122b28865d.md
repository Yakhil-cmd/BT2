### Title
Signature verification keyed on `repository.owner.login` while stack resolution keyed on `repository.full_name` lets an attacker forge a `pull_request` `closed` webhook that archives any repository's `ReviewStack` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository','owner','login')`. `ClosedHandler#repository`, however, resolves the actual `Repository`/`ReviewStack` to mutate from an independent field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`. Because these two fields are never checked for consistency, an attacker can pick an org with no configured `webhook_secret` for the "owner" field (which `verify_webhook_signature` accepts unconditionally — `return true unless webhook_secret`) while pointing `full_name` at any other org/repo whose `ReviewStack` they want archived.

### Finding Description
The broken binding is the implicit equality the code assumes but never enforces:
`params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`

Trace:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `github_app = Shipit.github(organization: repository_owner)` using only `repository.owner.login` (or `organization.login`) — line 61: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) explicitly says `return true unless webhook_secret` — i.e. if the org picked by `repository_owner` has no `webhook_secret` configured, the signature check is a no-op and the request is accepted regardless of the actual `X-Hub-Signature` value.
- Once past `verify_signature`, `Shipit::Webhooks.for_event('pull_request')` dispatches to `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler` (app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb).
- `ClosedHandler#repository` (lines 49-53) resolves the repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate field from the one used for signature/org selection.
- `ClosedHandler#process` then calls `review_stack.archive!` (line 44), archiving the `ReviewStack` for the PR number embedded in the payload, scoped to whatever repository `full_name` resolved to.

Exploit: the attacker crafts a POST to `/webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "closed",
  "number": <victim PR number>,
  "pull_request": { ... },
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
with any (or no valid) `X-Hub-Signature`. Because `repository_owner` resolves to `no-secret-org`, `Shipit.github(organization: "no-secret-org")` returns a `GitHubApp` instance with `webhook_secret` nil, so `verify_webhook_signature` short-circuits to `true` and the request is accepted unconditionally. The handler then archives the `ReviewStack` belonging to `victim-org/victim-repo` for the given PR number — a repository whose secret never authenticated this request.

Existing guards fail: `drop_unhandled_event` only checks the event name is handled; `verify_signature` only validates against the org named in `repository.owner.login`; there is no cross-check that this org matches the org embedded in `repository.full_name`; `ClosedHandler`'s `ExplicitParameters` schema only validates types/presence of `full_name`, not that it matches `repository.owner.login`.

### Impact Explanation
An attacker who controls (or names) any organization configured in Shipit without a `webhook_secret` can forge webhooks that are accepted unconditionally, and use the `full_name` field to redirect the mutation to an arbitrary other organization's repository/stack. For the `pull_request`/`closed` event specifically, this lets the attacker archive any `ReviewStack` for any PR number on a victim's tracked repository — a write for a repository that never authenticated the request. This matches "a payload for one repository mutating another's stack" (Critical) in the given impact taxonomy, since the org used for authentication and the org actually mutated diverge.

### Likelihood Explanation
Preconditions: (1) at least one org configured in `Shipit.github_teams`/app config without a `webhook_secret` (a legitimate, documented configuration state — Shipit explicitly supports orgs without a webhook secret, treating them as trusted-by-default for compatibility), and (2) knowledge of the target repository's `owner/name` (public information) and a PR number (also typically public/guessable/enumerable). No Shipit session, API token, or GitHub credentials are required — this is a plain unauthenticated `POST /webhooks`. This is trivially repeatable against any repository/PR as long as one no-secret org exists in the deployment.

### Recommendation
Derive the org used to select the webhook secret consistently with the org that the handler will actually act upon: verify the signature using the secret associated with the org parsed out of `repository.full_name` (not `repository.owner.login`), or better, reject the request if `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, reconsider whether "no webhook_secret configured" should mean "accept any signature" — a safer default is to reject unsigned/unverifiable requests unless explicitly allowed.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in the test `Shipit.github` config: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (with a `webhook_secret`, e.g. `secret123`).
2. Create a `Shipit::Repository` with `owner: "victim-org", name: "victim-repo"`, and an associated `Shipit::ReviewStack` bound to PR number `42` (not archived).
3. Build payload:
```ruby
payload = {
  action: "closed",
  number: 42,
  pull_request: { id: 1, number: 42, url: "...", title: "t", state: "closed",
                   additions: 1, deletions: 1,
                   head: { sha: "abc", ref: "branch" },
                   user: { login: "attacker" }, assignees: [], labels: [] },
  repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" },
  sender: { login: "attacker" }
}.to_json
```
4. Set `request.headers['X-Github-Event'] = 'pull_request'` and `request.headers['X-Hub-Signature'] = 'sha1=deadbeef'` (invalid/garbage signature).
5. `post :create, body: payload, as: :json`.
6. Assert: `assert_response :ok` (request accepted despite bogus signature, because `verify_webhook_signature` short-circuits for `no-secret-org`), and `assert review_stack.reload.archived?` — proving the `victim-org/victim-repo` review stack (authenticated by neither `victim-org`'s secret nor any valid signature) was mutated.

Equality check before/after: before the request, `repository_owner ("no-secret-org") != full_name.split('/').first ("victim-org")` yet the request is accepted; after the request, the `ReviewStack` under `victim-org/victim-repo` is archived — confirming the divergence is exploitable and unguarded.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
