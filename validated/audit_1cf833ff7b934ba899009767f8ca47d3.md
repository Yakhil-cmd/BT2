Front-runnable `address_alias::add()` lets a malicious alias regain permanent, unauthorized control of a victim's address after being "removed" - (`crates/sui-framework/packages/sui-framework/sources/address_alias.move`)

### Summary
The `sui::address_alias` module lets any address `A` designate a set of "alias" addresses whose signatures are accepted in place of `A`'s own signature for any transaction where `A` is `sender` or `gas_owner`. This is architecturally identical to the `Caller.authorize()`/`unauthorize()` delegation pattern from the referenced report, but with far higher stakes: a Sui alias is not scoped to "call on behalf of," it is unconditional, full custody over every coin and object `A` owns, as the docs themselves state. [1](#0-0) 

Any address currently in `A`'s alias set can call `add()` and insert a new address into that same set, exactly like Bob calling `Caller.authorize()` on Alice's behalf. Because the `AddressAliases` object is owned via `party::single_owner`, updates to it are ordered by consensus rather than being instantaneous/local, creating the same front-running window described in the original report: a malicious alias `B` can race the victim's `remove(B)` transaction by inserting a fresh address `E` (which `B` controls) into the alias set first.

### Finding Description
`enable()` creates an `AddressAliases` object for `ctx.sender()` and party-transfers it as `single_owner(ctx.sender())`, seeded with the alias set `{A}`: [2](#0-1) 

`add()`, `remove()`, and `replace_all()` are `entry fun`s that take only `&mut AddressAliases` — there is no check that the caller equals the *original* address that enabled the aliasing; any signer whose address is already an alias of `A` can invoke these functions to mutate `A`'s own alias set: [3](#0-2) 

At the signature-verification layer, any address in the alias set is accepted as a stand-in signer for `A`, and during Move execution `TxContext::sender()` resolves to `A` regardless of which alias signed: [4](#0-3) [5](#0-4) 

This produces the exact same root cause as the `Caller.authorize()`/`unauthorize()` bug:

- Alice (`A`) authorizes Bob (`B`) as an alias.
- Bob turns malicious; Alice submits `remove(aliases, B)`.
- Bob monitors the mempool/consensus queue and races his own `add(aliases, E)` transaction (signing as alias `B`, i.e. as `A`), where `E` is an address whose private key Bob controls.
- Because `AddressAliases` is a `single_owner`-party object, its updates go through the consensus commit path (not the owned-object fast path), so ordering between Alice's `remove` and Bob's `add` is determined by transaction submission/sequencing — the same "gas price"/submission-race dynamic as the Ethereum front-running in the original report.
- If Bob's `add(E)` lands before (or interleaved so as to survive) Alice's `remove(B)`, Alice ends up with alias set `{A, E}` — Bob has smuggled a backdoor address into Alice's permanent trust set, retaining full unilateral control of Alice's entire address, indefinitely, even after `B` itself was successfully removed.

Unlike the original `Caller` contract (where authority was scoped to whatever `callAs` executed), an `address_alias` compromise is a full account takeover — the alias can sign *any* transaction as `A`, spend all of `A`'s coins, transfer all of `A`'s objects, etc.

### Impact Explanation
This is Critical: a malicious delegate can persist unauthorized control over a victim's entire address (not merely a specific contract's permission scope) even after being explicitly "removed," enabling ongoing, effectively irrevocable theft of all coins/objects owned by the victim address, matching the "direct fund theft ... from unauthorized ... transfer" impact class. The victim has no reliable way to fully evict the attacker in one atomic step, since the attacker can always race in a fresh alias before the victim's removal transaction reaches consensus. This mirrors the original finding's "ongoing battle that can last forever" outcome, except the blast radius here is a full account rather than a single delegated contract permission.

### Likelihood Explanation
Likelihood is realistic though it requires an active, previously-trusted alias holder turning malicious (an unprivileged, ordinary caller who was legitimately granted alias status — not a validator, node, or governance actor). This matches the "ordinary SUI holder acting maliciously after being granted delegated authority" attacker model explicitly permitted by the task's scope, and mirrors precisely the front-running trust-boundary bug pattern from the seed report (an authorized/delegated party escalating persistence of their own authority by front-running revocation).

### Recommendation
- Restrict `add()`/`replace_all()` (functions that *grow* or *replace* the trusted alias set) so they can only be invoked by a signature from the "true owner" address itself (the address the `AddressAliases` object is derived for), not by any currently-valid alias. Aliases should be usable to sign on behalf of `A` for external calls, but should not be trusted to expand `A`'s own trust set — this is precisely the mitigation recommended in the original report ("don't allow authorized/delegated users to call `authorize()` on behalf of the original user").
- Alternatively/additionally, provide an atomic `remove_all_except(aliases, keep: address)` or similar "panic button" entry function so a victim can clear out all untrusted aliases (including any smuggled in during a race) in a single transaction, rather than only being able to remove one alias at a time while racing the attacker.

### Proof of Concept
1. Alice calls `sui::address_alias::enable` then `add(aliases, Bob)` — alias set becomes `{Alice, Bob}`.
2. Bob starts behaving maliciously (e.g., draining Alice's coins via signed transactions where `sender = Alice`).
3. Alice submits `sui::address_alias::remove(aliases, Bob)`.
4. Bob observes the pending removal and submits `sui::address_alias::add(aliases, Eve)` — signed with Bob's key, `sender = Alice` (valid, since Bob is currently an alias of Alice) — racing to be sequenced first.
5. If Bob's `add(Eve)` commits before or alongside Alice's `remove(Bob)`, the resulting alias set is `{Alice, Eve}` (Bob removed, but Eve — controlled by Bob — persists).
6. Bob, using Eve's private key, continues to sign transactions as Alice indefinitely, retaining full unauthorized custody of all Alice's coins and objects despite Alice's explicit revocation attempt. [3](#0-2) [6](#0-5)

### Authenticating transactions with aliased addresses

Transactions on Sui are configured with two addresses: a `sender` and a `gas_owner` (which might or might not be the same). For each configured address, a signature is required from one of the signers in its alias set.

For example, with the following transaction and aliases:
```
transaction T {
  sender: A
  gas_owner: X
  ...
}

aliases[A] = {A, B}
aliases[X] = {Y}
```

To be valid, the transaction `T` would require a signature from either `A` or `B`, and a signature from `Y`.

In this example, even if the transaction had signatures from `[B, Y]` and not from `A`, during execution it would nonetheless have access to everything owned by `A`, and during Move call execution its `TxContext::sender` would be `A`.

/// Adds the provided address to the set of aliases for the sender.
entry fun add(aliases: &mut AddressAliases, alias: address) {
    assert!(!aliases.aliases.contains(&alias), EAliasAlreadyExists);
    aliases.aliases.insert(alias);
    assert!(aliases.aliases.length() <= MAX_ALIASES, ETooManyAliases);
}

/// Overwrites the aliases for the sender's address with the given set.
entry fun replace_all(aliases: &mut AddressAliases, new_aliases: vector<address>) {
    let new_aliases = vec_set::from_keys(new_aliases);
    assert!(new_aliases.length() > 0, ECannotRemoveLastAlias);
    assert!(new_aliases.length() <= MAX_ALIASES, ETooManyAliases);
    aliases.aliases = new_aliases;
}

/// Removes the given alias from the set of aliases for the sender's address.
entry fun remove(aliases: &mut AddressAliases, alias: address) {
    assert!(aliases.aliases.contains(&alias), ENoSuchAlias);
    assert!(aliases.aliases.length() > 1, ECannotRemoveLastAlias);
    aliases.aliases.remove(&alias);
}
