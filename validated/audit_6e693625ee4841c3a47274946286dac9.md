### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, breaking the "authenticated organization == repository written" binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed from `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')`. Every webhook `Handler`, however, resolves the actual `Repository`/`Stack` to mutate from a different JSON field in the same attacker-controlled payload: `payload.dig('repository','full_name')`. Nothing ties these two values together, so in a multi-GitHub-App deployment an attacker who legitimately controls the webhook secret for one configured organization can forge a payload whose `repository.owner.login`/`organization.login` matches their own org (so it passes signature verification) but whose `repository.full_name` names a repository belonging to a different, unrelated organization also configured on the same Shipit instance.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

The GitHub App/secret used to verify the HMAC is looked up per-organization via `Shipit.github(organization: repository_owner)`, which is expected in multi-tenant configurations documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised in `test/dummy/config/secrets_double_github_app.yml`.

Once the signature check passes, the raw, fully attacker-controlled JSON body is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [3](#0-2) 

Every handler resolves the target repository/stacks using a *different* field of the same body: [4](#0-3) [5](#0-4) 

Because `Shipit.github` is looked up per-`organization`, GitHub Apps installed for different organizations have independent `webhook_secret`s, but the payload itself is one opaque HMAC-signed blob — nothing forces `repository.owner.login` (used to pick the verifying secret) to equal the owner portion of `repository.full_name` (used to pick the record that gets mutated). An attacker who owns/administers OrgA's GitHub App (and therefore legitimately knows OrgA's `webhook_secret`) can craft a POST body where `repository.owner.login` (or `organization.login`) says `"orgA"`, but `repository.full_name` says `"orgB/some-repo"`. The request signs correctly against OrgA's secret and is accepted, then handlers act on OrgB's `Repository`/`Stack` records as if the event genuinely originated from OrgB.

This mirrors the analog pattern of "an organization that authenticated versus the repository that is written": the equality `verifying_organization == mutated_repository.owner` is assumed but never enforced.

### Impact Explanation
Handlers that key off `repository.full_name` include commit-status and check-suite processing that feeds CI-gating logic for continuous deployment/merge queue, and push handling that syncs branch state for a stack. By forging cross-organization events, an attacker controlling only one configured organization's webhook secret can inject fabricated `status`/`check_suite`/`push` events against a stack belonging to a different organization's repository — e.g., posting a fabricated "success" status for an arbitrary commit SHA, which can influence a stack's `continuous_deployment`/merge-queue gating (an unauthorized/uncontrolled deploy or merge path), or trigger sync jobs against a repo the attacker does not own. This falls under the Critical/High impact of "an unauthorized deploy, rollback or merge" since it lets an attacker who is not privileged on OrgB inject signed-looking webhook state that OrgB's stacks treat as trusted CI/GitHub signal.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md`'s "Using Multiple Github Applications" section and `test/dummy/config/secrets_double_github_app.yml`), and requires the attacker to control (or have compromised) the webhook secret of at least one of those configured organizations while targeting a stack under a different configured organization. This is a realistic multi-tenant scenario but not universal to every single-org Shipit deployment, so likelihood is moderate and configuration-dependent.

### Recommendation
After `verify_signature` succeeds, assert that the organization used to select the verifying GitHub App (`repository_owner`) matches the owner segment of every repository-identifying field consumed downstream (e.g., `payload.dig('repository','full_name')`, and any `organization.login` used elsewhere). Reject the webhook (422) if these do not match, rather than trusting the entire body as internally consistent once any one field passes HMAC verification against a given org's secret.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-app instructions).
2. As the (legitimate) administrator/owner of `orgA`'s GitHub App, craft a `status` (or `push`/`check_suite`) webhook JSON body where:
   - `repository.owner.login = "orgA"` (or omit and set `organization.login = "orgA"`)
   - `repository.full_name = "orgB/target-repo"` (a repo tracked by Shipit under `orgB`)
   - `sha`, `state`, etc. set to whatever forged CI signal is desired.
3. Sign the raw body with `orgA`'s known `webhook_secret` and send it to `WebhooksController#create` with `X-Github-Event: status` and `X-Hub-Signature` set accordingly.
4. `verify_signature` computes `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('status')` handlers resolve the target repository via `payload.dig('repository','full_name')` → `"orgB/target-repo"`, applying the forged status to `orgB`'s stack despite the attacker never possessing `orgB`'s webhook secret.
