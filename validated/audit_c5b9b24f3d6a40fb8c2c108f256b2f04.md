### Title
Unhandled TypeError on `null` values in AA definitions crashes the process during AA definition validation - ([File: formula/common.js])

### Summary
`hasCases()` in `formula/common.js` uses `typeof value === 'object'` to detect dictionary values, which is also true for `null` in JavaScript. When it is called with `value === null`, the immediate `Object.keys(value)` call throws an uncaught `TypeError`. This function is invoked from the generic recursive AA-definition walker in `aa_validation.js`, which is reached while validating any AA definition unit posted by an "AA author" — exactly the kind of type-confusion root cause described in CVE-2017-5836 (treating one value type, an integer/`null`, as another type, a PLIST_KEY/object, and performing an operation only valid for the assumed type).

### Finding Description
`hasCases` is defined as: [1](#0-0) 
`typeof null === 'object'` in JavaScript, so `hasCases(null)` evaluates `Object.keys(null)`, which throws `TypeError: Cannot convert undefined or null to object` synchronously.

This function is used directly in the recursive definition walker `validate()` inside `validateAADefinition`: [2](#0-1) 
The walker sets `var value = obj[name];` and only special-cases `number`, `boolean`, and `string` before calling `hasCases(value)`. If `value` is JSON `null` (which is a completely legal value in a unit's message payload, e.g. under a `data` app payload field), the `hasCases(value)` call throws immediately and unconditionally, before this generic walker has a chance to route it to the trailing "empty object" catch-all (`cb('empty object in ' + name)`), because the throw happens synchronously ahead of any of those later `else` branches.

The upstream per-app payload checks do not forbid `null` values nested inside otherwise-valid payload objects — for example the `data`/`profile`/`temp_data` apps only require the payload itself to be `isNonemptyObject`, without validating the types of its nested values: [3](#0-2) 
So an AA author can define an AA whose `messages` array contains, e.g., `{ app: 'data', payload: { x: null } }`, which passes `validatePayload`, but then the same `arrDefinition` is walked in full by the generic `validate()` walker (via `validateDefinition(arrDefinition, cb)` → `validate(arrDefinition, 1, '', locals, 0, cb)`), which recurses into every nested key/value, including `x: null`, and crashes on `hasCases(null)`.

Because ocore is single-threaded, an uncaught synchronous exception thrown deep inside an async callback chain is not caught by any `try/catch` in this path and bubbles up to Node's `uncaughtException` handler, which is intentionally configured to re-throw and kill the process: [4](#0-3) 

### Impact Explanation
Any full node (or light node performing validation) that processes a unit defining such an AA will crash the entire ocore process while validating the AA definition, before the transaction can even be judged valid or invalid. Since AA definitions are broadcast and validated by every full node in the network as part of normal unit propagation, a single crafted AA-definition unit can be used to crash many/most full nodes that receive it, degrading the network's ability to confirm new units — this is a network-wide denial-of-service triggered by a single unprivileged AA author, directly analogous to the crash-via-type-confusion described in CVE-2017-5836.

### Likelihood Explanation
Likelihood is high: defining an autonomous agent is a permissionless, ordinary operation available to any user; embedding a `null` value inside a `data`/`profile`/`temp_data` (or any other non-strictly-typed) payload field requires no special formula complexity and passes the existing `validatePayload` checks, since those checks validate the payload's outer shape (`isNonemptyObject`) but not the types of arbitrary nested leaf values.

### Recommendation
Add an explicit `value === null` (or `value === undefined`) guard at the top of `validate()` in `aa_validation.js` (mirroring the `typeof value === 'number' || typeof value === 'boolean'` short-circuit) before calling `hasCases(value)`, and/or fix `hasCases()` itself in `formula/common.js` to check `value !== null` alongside `typeof value === 'object'`. Apply the same fix to any other call sites/analogous walkers (e.g., the `replace()` function in `aa_composer.js`) that rely on `typeof value === 'object'` without excluding `null`.

### Proof of Concept
1. As any user, compose and post a unit defining an autonomous agent with a definition such as:
```json
["autonomous agent", {
  "messages": [
    { "app": "data", "payload": { "x": null } }
  ]
}]
```
2. Broadcast the unit to the network.
3. Every full node that validates this AA definition executes `aa_validation.js`'s `validate()` walker, which reaches the `x: null` field, calls `hasCases(null)` from `formula/common.js`, and throws an uncaught `TypeError` from `Object.keys(null)`.
4. The exception is not caught anywhere in the async call chain and reaches `process.on('uncaughtException', ...)` in `network.js`, which deliberately re-throws to crash the node process, taking down validation for the entire node.

(Note: I was not able to execute this locally to confirm the exact runtime stack trace and whether any intermediate `try/catch` — outside the code shown — might catch this specific throw before it reaches the global handler; this should be verified by running the PoC against a live/test ocore node.)
