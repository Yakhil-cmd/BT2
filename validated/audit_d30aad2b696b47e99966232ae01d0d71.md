The root cause is clear: the sender-identity check for a "sign" request is explicitly disabled in `wallet.js`, so `findAddress`'s `ifLocal` path only checks that the requesting device knows a valid `(address, signing_path)` pair, not that the requesting device is actually one of the wallet's registered cosigners.

### Title
Missing cosigner-authorization check in remote "sign" request handling allows any paired device to obtain signing credentials for a shared/multisig address - (File: wallet.js)

### Summary
`handleMessageFromHub`'s `"sign"` case (used for multisig/multilateral co-signing of shared addresses) resolves the signer via `findAddress(body.address, body.signing_path, ...)`. When the requested address/path resolves locally (`ifLocal`), the code that would verify the requesting device (`from_address`) is actually a registered cosigner of that wallet is commented out, with the note that enabling it "would make multilateral signing impossible."

### Finding Description
`findAddress` resolves purely from attacker-supplied fields (`body.address`, `body.signing_path`) against `my_addresses`/`wallet_signing_paths` and returns `ifLocal` whenever this device locally hosts that key at that path — it never checks who sent the request. [1](#0-0) 
In the `"sign"` handler, the code explicitly disables the authorization check that would confirm the sender is one of the wallet's cosigners before proceeding to request a signature/emit `"signing_request"`: [2](#0-1) 
By contrast, the `ifRemote` branch (proxying to another device) *does* enforce `other_device_addresses.includes(from_address)`, confirming that a cosigner check is the intended and available control that was deliberately skipped for the local case: [3](#0-2) 
As a result, any device that is merely paired as a correspondent with the wallet owner (not necessarily an approved cosigner of that specific shared/multisig address) can send a crafted `"sign"` message naming any address/signing_path the device locally controls, causing the device to validate the attacker-supplied unsigned unit and emit `"signing_request"` — effectively obtaining the ability to solicit that device's cryptographic authorization (its "stored credential", i.e. its private key usage) for spending from a shared address it does not legitimately co-own, mirroring the GitLab flaw where improper authorization checks let an actor obtain another party's credentials.

### Impact Explanation
If the host application processes `"signing_request"` autonomously or with insufficiently strict confirmation (a common pattern for headless/automated multisig wallets, exchange hot wallets, and bots built on ocore), an unauthorized paired device can trigger signing/spending operations on a shared address it is not a legitimate cosigner of, leading to unauthorized spending of shared funds. Even where a UI confirmation exists, the missing server-side authorization check removes a defense-in-depth layer explicitly designed to prevent non-cosigners from soliciting signatures, which is precisely the "insufficiently protected credentials" bug class from the report.

### Likelihood Explanation
Any device that has completed device-level pairing with the wallet owner (a normal, lightweight trust relationship, not necessarily wallet cosigner status) can send this message; no on-chain action or elevated privilege is required. Exploitation is fully self-contained to the wallet's message-handling path.

### Recommendation
Re-enable (or replace with an equivalent) verification that `from_address` is a listed cosigner/xpubkey owner of the wallet/shared address for the given signing path before processing a local `"sign"` request — mirroring the same check already applied in the `ifRemote` branch — so that only devices actually party to the address definition can solicit signatures.

### Proof of Concept
1. Device B pairs with Device A as an ordinary correspondent (no wallet/cosigner relationship required).
2. Device A hosts a key for shared address `X` at signing path `r.1`, part of a multisig wallet `W`.
3. Device B crafts and sends a `"sign"` device message: `{address: X, signing_path: "r.1", unsigned_unit: <attacker-crafted spending unit with authors including X>}`.
4. `findAddress(X, "r.1", ...)` resolves `ifLocal` on Device A because A locally hosts that address/path — the disabled cosigner check means B's identity is never validated against `wallet_signing_paths`/`extended_pubkeys` for wallet `W`.
5. Device A validates the unit and emits `"signing_request"`; if the application layer auto-approves or a user is socially engineered to approve, Device A signs the attacker-controlled unit, resulting in unauthorized spend from shared address `X`.
