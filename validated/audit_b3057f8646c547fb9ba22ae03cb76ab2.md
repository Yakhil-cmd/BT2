### Title
Webhook signature verification selects the per-organization secret from an unverified `repository.owner.login` field, while event handlers act on the (equally unverified) `repository.full_name` field - allowing cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate the incoming signature against by reading `repository_owner` out of the *unauthenticated* JSON body itself. Every downstream `Shipit::Webhooks::Handlers::Handler` then resolves the actually-affected `Repository`/`Stack` from a *different* field of that same unauthenticated body: `repository.full_name`. In a multi-organization Shipit configuration these two values are never cryptographically bound together, so an attacker can pick which org's secret is checked while still directing the handler at a completely different org's repository.

### Finding Description
The controller determines the signing secret like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is taken straight from the raw request body, with no cryptographic verification performed before it is used to select the secret: [2](#0-1) 

`Shipit.github` resolves this organization argument against a per-organization config map when running in the documented multi-org mode: [3](#0-2) 

Each organization entry may or may not define its own `webhook_secret`, as shown in the officially documented multi-org config schema: [4](#0-3) 

Critically, if an organization's `webhook_secret` is absent (it is explicitly marked *optional* in `docs/setup.md`), verification is a no-op: [5](#0-4) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, every event handler resolves the target repository/stack from a *different* JSON field — `repository.full_name` — which is not the field used to choose the verification secret: [6](#0-5) 

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```

and the push handler acts on whatever `Repository.from_github_repo_name(repository_name)`-derived stacks it finds: [7](#0-6) 

**The broken binding:** signature verification is keyed on `params.dig('repository','owner','login')` (or `params.dig('organization','login')`), while the repository actually mutated is keyed on `params.dig('repository','full_name')`. Both are attacker-controlled fields inside the same unauthenticated JSON body — GitHub's HMAC signature only proves the byte-for-byte payload was signed by *some* configured app, but the controller lets the attacker's own payload content decide *which* app/secret that check is performed against. In a multi-org install where an organization is registered with Shipit but has no (or a weak) `webhook_secret` configured, an attacker can:

1. Set `repository.owner.login` (or `organization.login`) to that unprotected/no-secret organization, causing `verify_webhook_signature` to `return true unconditionally`.
2. Set `repository.full_name` to `"protected-org/target-repo"` — a repository belonging to a *different*, fully-secured organization that has real stacks configured in Shipit.
3. Send any handled event (e.g. `push`) with these mismatched fields; the controller accepts it (verification passed for the spoofed org), and `PushHandler` resolves `stacks` against `target-repo` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim org's stack.

This effectively forges GitHub-originated events for a repository the attacker has no push access to and no knowledge of that organization's real webhook secret.

### Impact Explanation
Forged `push` events reaching `stack.sync_github` can advance the tracked HEAD SHA of a protected stack and, combined with `continuous_deployment?`/`ContinuousDeliveryJob` (`Shipit::Stack#trigger_continuous_delivery`), can cause an **unauthorized deploy** to be scheduled on a victim organization's stack without the attacker ever possessing that organization's webhook secret, GitHub App credentials, or repository access. Other handlers keyed the same way (`status`, `check_suite`, `pull_request/*`, `membership`) are similarly reachable for the spoofed org, extending the impact to fabricating commit statuses/check results that feed into deploy-eligibility checks, and to creating/removing organization team memberships. This matches the "unauthorized deploy" and "authentication bypass" impact tiers because it lets an unprivileged external actor cross an organization-authentication boundary to act on a different repository's data.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured for multiple GitHub organizations (a supported and documented deployment mode) and for at least one registered organization to have no `webhook_secret` set — explicitly called out as "optional" in `docs/setup.md`. This is a plausible real-world misconfiguration (e.g., a low-value/staging org added without a secret) that silently downgrades security for all other, fully-configured organizations sharing the same webhook endpoint, since the attacker only needs to know that a weak org is registered — no secret material at all.

### Recommendation
Do not let unauthenticated payload content decide which secret is used to authenticate that same payload. Options:
- Verify the webhook signature against *every* configured organization's secret (or require signature to match the specific org derived independently, e.g. from a per-organization webhook URL/path) rather than trusting `repository.owner.login`/`organization.login` from the body.
- After successful verification, additionally assert that the organization used for verification equals the owner segment of `repository.full_name` used by handlers, rejecting the request otherwise.
- Make `webhook_secret` mandatory for every configured organization (fail closed rather than `return true unless webhook_secret`).

### Proof of Concept
Preconditions: multi-org Shipit config with `orgA` (no `webhook_secret` set) and `orgB` (protected, has a real stack tracking `orgB/target-repo`).

```http
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, orgA has no secret

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-in-orgB-repo>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```

`verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` on the real, protected `orgB` stack — an event the attacker could never have produced a valid `orgB` signature for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
