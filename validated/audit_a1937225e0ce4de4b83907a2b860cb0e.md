### Title
Missing `return` after error handling causes double invocation of the async iterator callback in `handleSavedPrivatePayments` - (File: network.js)

### Summary
In `network.js`, the `validateAndSave` closure inside `handleSavedPrivatePayments` catches a hashing exception but fails to `return` afterward, so execution falls through and re-processes the same private-payment chain a second time, invoking the `async.each` iterator callback (`cb`) twice for one item.

### Finding Description
`handleSavedPrivatePayments` iterates rows from `unhandled_private_payments` (populated from private payment messages sent by any wallet/device counterparty, an unprivileged actor) with `async.each`, and for each row defines: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

If `objectHash.getBase64Hash()` throws (e.g. the private element's `payload` contains a value that the hashing/serialization routine cannot handle — malformed field types, non-finite numbers, or structures that make `getSourceString`/`getBase64Hash` throw), the `catch` block:
1. Sends an error result to the peer,
2. Calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which performs a DB `DELETE` and then invokes `cb()` — completing this `async.each` item.

Execution does **not** `return` after the `catch`, so the function falls through and additionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same, already-deleted/already-erroring chain. That call always eventually invokes one of `ifOk`/`ifError`/`ifWaitingForChain`, each of which itself calls `deleteHandledPrivateChain(...)` (a second, redundant `DELETE ... cb()`) or `cb()` directly — resulting in the shared `async.each` iterator callback `cb` being invoked twice for a single row.

This is directly analogous to the CVE's bug class: on an error/decode-failure path, cleanup of a resource happens, but the code doesn't stop there and continues into the normal path, causing the same resource-release/completion callback to fire twice ("put the realm twice").

### Impact Explanation
Because `cb` is `async.each`'s per-item completion callback, invoking it twice violates `async`'s callback contract. Depending on the `async` version's behavior this can:
- Cause the `async.each` final callback (which calls `unlock()` on the `"saved_private"` mutex key and emits `"new_my_transactions"`) to fire prematurely or more than once, unlocking the mutex early while other rows are still being processed — a synchronization/race hazard around private-payment processing.
- Cause `privatePayment.validateAndSavePrivatePaymentChain` to run concurrently with, or after, deletion of the same row, potentially double-processing/double-crediting a private (indivisible/divisible) asset chain or leaving the wallet database in an inconsistent state regarding what private payment chains have been "handled," which can affect balance/asset bookkeeping for private assets.
- An attacker (a private-payment counterparty) fully controls the payload sent in a private_payment message, and can deliberately craft a payload designed to make `objectHash.getBase64Hash` throw (while still being accepted earlier by `handleOnlinePrivatePayment`'s lighter validation, which only checks `unit`, `message_index`, `output_index` before queueing it into `unhandled_private_payments`), reliably triggering this dual-invocation path.

### Likelihood Explanation
Reaching this code requires only sending a private payment message (`private_payment`) with a malformed `payload` for the head element, something that a normal wallet counterparty (private-payment counterparty) can do without any special privilege — this matches the reachable actor set (private-payment counterparty / unit poster). The exact conditions under which `objectHash.getBase64Hash` throws for a crafted payload would need confirmation against `object_hash.js`'s hashing implementation (I was unable to fully view its throwing paths due to tool/iteration limits), but throwing on malformed input is a common and expected characteristic of strict hashing/serialization code, and `getBase64Hash` is called here specifically inside a `try/catch`, indicating the developers anticipated it could throw.

### Recommendation
Add an explicit `return` immediately after `deleteHandledPrivateChain(...)` inside the `catch` block in `network.js`'s `validateAndSave` (around line 2476), so the function does not fall through to compute `key` and call `privatePayment.validateAndSavePrivatePaymentChain` a second time for the same row/`cb`. Additionally, consider auditing all other callers of `async.each`/`async.eachSeries` iterator callbacks in this file for similar missing-`return`-after-error patterns.

### Proof of Concept
1. As any correspondent device (private-payment counterparty), send a `private_payment` message to the victim node whose `arrPrivateElements[0].payload` is a normal-looking indivisible/divisible payload but includes a field designed to throw during `objectHash.getBase64Hash(payload, true)` (e.g. a value type not supported by the object-hash source-string serializer).
2. The victim's `handleOnlinePrivatePayment` queues it into `unhandled_private_payments` since only basic shape checks (`unit`, `message_index`, `output_index`) are performed there.
3. `handleSavedPrivatePayments` later picks up the row and calls `validateAndSave`, hits the `catch` branch, deletes the row and calls `cb()` — but then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain` again on the same `arrPrivateElements`, causing `cb` to be invoked a second time via one of its inner callbacks.
4. Observe (via added logging or by triggering with concurrently queued rows) that the `async.each` final callback executes prematurely/twice, releasing the `"saved_private"` mutex out of turn while sibling rows are still mid-processing, confirming the double-callback race.
