## Analysis

I confirmed a genuine trust-binding break in the webhook signature verification flow that matches the required binding class "an organization that authenticated versus the repository that is written":

- `Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to authenticate the request against based on `repository_owner`, which is read directly from the untrusted JSON body itself (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), *before* any signature has been checked. [1](#0-0) [2](#0-1) 
- The HMAC signature only proves that the raw body was signed with the secret belonging to whichever organization `repository_owner` names — it says nothing about the `repository.full_name` field that handlers actually act on. [3](#0-2) 
- `Handler#stacks` / `Handler#repository_name` (used by `PushHandler` and others) resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, a completely different field from the one used for signature-org selection. [4](#0-3) [5](#0-4) 

This setup is only reachable when a Shipit instance is configured with **multiple** GitHub App organizations sharing one Shipit deployment (a documented, supported configuration), each with its own distinct `webhook_secret`. [6](#0-5) [7](#0-6) 

Given that setup, an attacker who legitimately administers **any one** of the configured organizations (e.g., `OrgA`, which they run their own GitHub org/app for and thus can legitimately read `OrgA`'s `webhook_secret` from their own GitHub App settings) can send a forged webhook `POST /github/webhooks` whose JSON body sets `repository.owner.login = "OrgA"` (so `verify_signature` picks `OrgA`'s secret, which the attacker knows and can compute a valid HMAC with) while `repository.full_name = "OrgB/private-repo"` (a repository belonging to a different, victim organization also configured on the same Shipit instance). The signature check passes because it only validates against `OrgA`'s secret; the handler then acts on `full_name`, targeting `OrgB`'s stack. The binding "organization whose secret authenticated the request" == "organization/repository written by the request" is never enforced.

This lets the attacker enqueue `GithubSyncJob` for a stack under `OrgB` with a forged `after` SHA, causing Shipit to fetch and record fabricated "GitHub commits" (attacker-chosen SHA/metadata) into `OrgB`'s stack history without ever having write access to `OrgB`'s actual repository — a cross-organization write into stack state that the attacker does not own, which can subsequently be deployed by a legitimate `OrgB` user believing it reflects real GitHub history. Because `GithubSyncJob` calls `stack.github_api` (which is itself computed from `Repository#owner`, i.e. `OrgB`), the eventual GitHub API calls fetch real commit data for `OrgB`'s repo using `OrgB`'s own installation credentials, but the injected `expected_head_sha`/triggering ref completely bypasses `OrgB`'s own webhook secret verification. [8](#0-7) [9](#0-8) 

### Title
Webhook Signature Verified Against Attacker-Chosen Organization While Handlers Act on a Different `repository.full_name` — Cross-Organization Stack Write - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook's HMAC signature using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON payload, but the actual event-processing `Handler` classes resolve which `Stack`/`Repository` to mutate using the separate, also attacker-controlled `repository.full_name` field. No code ties these two values together, so the "organization that authenticated" binding does not equal the "repository that is written" binding.

### Finding Description
`verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies `request.headers['X-Hub-Signature']` against that organization's `webhook_secret`. `repository_owner` is computed purely from the request body itself. [10](#0-9) 

Later, in `create`, the same raw JSON body is dispatched to `Shipit::Webhooks.for_event(event)` handlers, which independently look up the target repository/stack from `payload.dig('repository', 'full_name')`. [11](#0-10) [4](#0-3) 

There is no validation that `repository.owner.login`/`organization.login` (used to pick the signing secret) is consistent with `repository.full_name` (used to pick the affected stack). An attacker who can legitimately obtain the `webhook_secret` for any one organization configured on the shared Shipit instance can therefore forge a signature that authenticates as that organization while the payload body directs Shipit to act on a stack belonging to an entirely different, victim organization also hosted on the instance.

### Impact Explanation
This is an unauthorized cross-repository write: an actor with no access whatsoever to a victim organization's repository or GitHub App can cause Shipit to record forged commit data into that organization's stack (`GithubSyncJob`/`PushHandler`), and depending on which event handler is targeted, potentially trigger other cross-organization side effects (e.g., check_suite/status handlers, PR handlers) tied to stacks they do not own. This maps to the required "cross-repository writes" / "unauthorized deploy" impact category, since forged commit history in a stack can subsequently be deployed.

### Likelihood Explanation
Requires that the Shipit instance be configured with multiple GitHub organizations (a documented, supported feature: `docs/setup.md`, "Using Multiple Github Applications"), and requires the attacker to control one organization's `webhook_secret` — something they can legitimately obtain because they are the administrator of their own org's GitHub App, which is not "repository write access" to the victim's repo and not a privileged Shipit account. This satisfies the "unprivileged attacker" constraint of the rules.

### Recommendation
Bind the verified signature to the exact repository/stack acted upon: after successfully verifying the signature against the organization derived from `repository_owner`, re-derive/validate that every subsequent `payload.dig('repository', 'full_name')` used by handlers belongs to that same, already-authenticated organization (e.g., assert `full_name.split('/').first.casecmp(repository_owner).zero?`) before dispatching to handlers, or scope handler repository lookups by both `owner` and `name` matching the authenticated organization.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org config).
2. As the legitimate administrator of `OrgA`'s GitHub App (not a Shipit user, not a member of `OrgB`), read `OrgA`'s `webhook_secret` from GitHub App settings.
3. Craft a JSON body: `{"ref": "refs/heads/main", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner` = `"OrgA"`, loads `OrgA`'s app, and the signature validates successfully.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")`, finds `OrgB`'s stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against a stack the attacker never had access to — despite having authenticated only as `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
