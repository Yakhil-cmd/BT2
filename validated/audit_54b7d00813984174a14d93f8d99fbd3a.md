### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets an attacker's own repository write GitHub statuses onto another tenant's commit/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by `sha`, with no filter on the repository/stack that the (correctly-verified) webhook belongs to. Any commit SHA collision between an attacker-controlled repository and a victim stack's tracked repository (achievable deterministically by re-creating a public/known commit with identical tree/parents/author/committer/message in the attacker's own repo) lets the attacker post a `ci/kubernetes` `failure` status that Shipit attaches to the victim stack's commit.

### Finding Description
The broken binding is: **the equality `commit.stack_id == repository_that_authenticated(webhook)` is never enforced**, whereas the intended invariant states a status should only affect the repository that authenticated it.

Path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the payload and dispatches to `Shipit::Webhooks.for_event(event)`.
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the HMAC signature matches the GitHub App/organization derived from `params.dig('repository','owner','login')`. This proves the request genuinely came from GitHub for the attacker's own repository/org — it does **not** bind the payload to any particular Shipit `Stack`/`Repository` record beyond the owning org's app secret.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This looks up **every** `Commit` row across **all** stacks/repositories matching the bare SHA, with no `stack_id`/`repository` filter tying it to the repository that signed the webhook.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)`, writing the status using the *matched* commit's own `stack_id` — i.e., the victim stack's id, not the attacker's.
- `add_status` (app/models/shipit/commit.rb:366-386) then emits `deployable_status`/`commit_status` hooks and calls `stack.schedule_merges` based on the new status, and `Commit#blocked?`/`#deployable?` (app/models/shipit/commit.rb:227-237) consult `stack.blocking_statuses`/`stack.ignore_ci?` to decide ship/block — exactly the mechanism the question describes as being flipped for a production-environment stack.

Attacker request: the attacker owns a GitHub repository that is configured (by the attacker, legitimately) to send webhooks to the Shipit host — this is permitted under the threat model ("any GitHub user who can ... emit webhooks from a repository they own"). They craft/replicate a commit with identical git metadata (tree, parents, author, committer, timestamps, message) as a commit known to exist in the victim's tracked repository/stack, giving it the same SHA-1 (git commit hashing is fully deterministic, so this is achievable without any secret). They then have GitHub emit (or self-trigger via GitHub Status API on their own repo) a `status` event: `context: ci/kubernetes`, `state: failure`, `sha: <victim commit sha>`. GitHub signs this legitimately for the attacker's own org/app installation, so `verify_signature` passes. `StatusHandler#process` finds the victim's `Commit` row by bare SHA and writes the failing status onto it via the victim stack's `stack_id`, corrupting `required_statuses`/`blocking_statuses` evaluation for that stack and, per `Commit#blocked?`/`#deployable?`, flips deployability/blocking for the victim's production stack.

None of the existing guards prevent this: `verify_signature` authenticates the org, not the target stack; `drop_unhandled_event` only filters unregistered event types; there is no `ExplicitParameters` schema field or model validation that ties the incoming `sha`/`context` to a specific `Repository`/`Stack`; `StatusHandler` performs no `stack.repository`/`commit.stack.repository` cross-check against the webhook's `repository_owner`/`full_name`.

### Impact Explanation
A payload authenticated for one repository (the attacker's) mutates state (`Status` records, deployability, blocking, merge scheduling, hook emissions) belonging to a different repository's/stack's commit — this is a direct instance of the Critical category "a payload for one repository mutating another's stack, commit, task or team." Because the affected commit is on a production-environment stack, this can force a stack to be blocked (denial of legitimate deploys) or, depending on which status the attacker chooses to falsify (`success` vs `failure`) and the stack's continuous-delivery/`schedule_merges` configuration, can influence which commit is considered deployable/mergeable, i.e., unauthorized deploy/rollback/merge behavior. It is repeatable against any stack whose tracked repository's commits an attacker can reproduce the SHA of (any commit an attacker can also legitimately obtain/replicate, e.g. commits from a public upstream, a shared dependency, or any commit visible to the attacker), and generalizes across all tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository under their control with the Shipit webhook configured (self-service, no privilege needed) and needs a target commit SHA from a victim stack that they can reconstruct byte-for-byte as a git commit object (tree + parents + author/committer identities/timestamps + message) — feasible for any commit that is itself public or otherwise known/reproducible by the attacker, at zero cost beyond crafting the commit locally and pushing/tagging it in their own repo, then firing (or waiting for GitHub to fire) a `status` event with the desired `state`/`context`. This requires no Shipit credentials, no webhook secret, and no `Shipit.github_teams` membership, matching the unprivileged attacker model exactly. The attack is fully repeatable for any SHA the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/status refresh paths) to only the commits belonging to stacks/repositories tracked under the organization/repository that authenticated the webhook, e.g. join through `Stack`→`Repository` and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`, using the `repository` object from the webhook payload rather than trusting a bare SHA lookup.

### Proof of Concept
Minitest plan (no live GitHub, uses fixtures):
1. Create two `Stack`/`Repository` fixtures: `attacker_repo` (owned by attacker org) and `victim_repo` with `environment: 'production'`, `required_statuses: ['ci/kubernetes']` (or `ignore_ci?` false and status included in `blocking_statuses`).
2. Create a `Commit` on `victim_repo`'s stack with a known `sha` (e.g. `"a" * 40`) and no statuses yet; assert `commit.deployable?` reflects the pre-attack expectation, e.g. `assert commit.deployable?` if `ignore_ci?` is false but no blocking status exists yet, or set up so pending/success state currently allows deploy.
3. Simulate `StatusHandler.new(payload).call` (bypassing controller-level `verify_signature`, since it is scoped only to org auth and not to this invariant) with `payload = { sha: "a"*40, state: "failure", context: "ci/kubernetes" }`, as if it arrived signed for `attacker_repo`'s org.
4. Assert equality broken: before, `victim_commit.stack_id != attacker_repo.stack.id` and `victim_commit.statuses.count == 0`; after calling `StatusHandler#process`, assert `victim_commit.reload.statuses.exists?(context: 'ci/kubernetes', state: 'failure')` is `true` and `victim_commit.blocked?`/`deployable?` has flipped, even though the webhook never referenced `victim_repo` anywhere in its payload — proving the binding `commit.stack_id == repository_that_authenticated(webhook)` is violated.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
