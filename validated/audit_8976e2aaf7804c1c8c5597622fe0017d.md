### Title
Webhook signature verification is keyed on `repository.owner.login`, but event handlers act on the unpinned `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App / webhook secret to validate a request against using `repository_owner`, a value read from the JSON body itself, while every webhook `Handler` subclass resolves the *actual* `Stack`/`Repository` to act on from a different field in the same body, `repository.full_name`. In Shipit's documented multi-organization configuration (one `webhook_secret` per GitHub org), these two fields are never checked for consistency, so a successfully-verified request for org A can carry a payload whose `repository.full_name` points at a Stack belonging to org B.

### Finding Description
`verify_signature` computes the org used to look up the webhook secret purely from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` then picks the `GitHubApp` (and its distinct `webhook_secret`) keyed by that same attacker-controlled `repository_owner` string: [3](#0-2) 

This per-organization secret scheme is the documented, supported configuration (`docs/setup.md`, "Using Multiple Github Applications"; `test/dummy/config/secrets_double_github_app.yml`).

Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers. Every handler resolves its target `Stack` via `Handler#stacks`/`#repository_name`, which reads `repository.full_name` - a field completely independent of `repository.owner.login`: [4](#0-3) 

For example `PushHandler` triggers `stack.sync_github` for every non-archived stack matching that repo/branch: [5](#0-4) 

and `StatusHandler` writes a CI status onto any `Commit` matching `params.sha` (a global lookup, not scoped to the verified org/repo) via `Commit#create_status_from_github!`: [6](#0-5) 

**Broken binding (as an equality):** the engine implicitly assumes
`organization authenticated by webhook_secret == organization of the repository the handler writes to`,
but nothing enforces `repository.owner.login == repository.full_name`'s owner segment. An operator/attacker who legitimately controls the webhook secret for org A (e.g., they installed/administer their own Shipit-integrated GitHub App on org A) can craft an arbitrary raw payload, set `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against the secret they know) while setting `repository.full_name = "OrgB/victim-repo"` and `sha` to a publicly-known commit SHA belonging to org B's tracked stack. The signature is computed over the full raw body they control, so they can sign any content once they know org A's secret.

### Impact Explanation
This lets a party who only administers org A's GitHub App forge webhook events that mutate Stacks belonging to an unrelated org B tracked by the same Shipit instance:
- Forge `push` events to make `PushHandler` invoke `stack.sync_github` for org B's stacks.
- Forge `status` events to make `StatusHandler` call `Commit#create_status_from_github!`, setting an arbitrary CI/check state (e.g. `success`) on a specific, publicly-known commit SHA in org B's repository - independent of org B's real CI results.

Since Shipit's deploy pipeline consults commit/check statuses to decide whether a commit is deployable, forging a `success` status on a commit can be used to help push it toward becoming deployable through Shipit's merge/deploy workflow, without the attacker ever holding org B's webhook secret or write access to org B's repository. This matches the report's underlying bug class (an authenticated key covering less than what is trusted to act) and rises to unauthorized-deploy-adjacent impact.

### Likelihood Explanation
Low-to-Medium: it requires the Shipit deployment to be configured for multiple GitHub organizations with per-org `webhook_secret`s (a supported, documented mode) and requires the attacker to control one org's webhook secret and know a target commit SHA in another tracked org/repo (SHAs are typically public on GitHub). It does not require compromising GITHUB_TOKEN, an ApiClient token, or any Shipit session.

### Recommendation
After `verify_signature` succeeds, additionally verify that `repository.owner.login` (the org whose secret validated the request) matches the owner segment of `repository.full_name` (and/or `organization.login`) before dispatching to handlers; reject the webhook otherwise. Alternatively, resolve the target `Stack`/`Repository` using the already-verified organization rather than trusting `repository.full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the administrator of OrgA's GitHub App, know OrgA's `webhook_secret`.
3. Craft a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<known public commit sha in OrgB's tracked stack>",
  "state": "success"
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and send it with `X-Github-Event: status` to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "OrgA"`, validates successfully against OrgA's secret (`lib/shipit/github_app.rb` `verify_webhook_signature`), and dispatches the payload.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (no org scoping) and calls `create_status_from_github!`, writing a forged `success` status for OrgB's commit - despite the request never being signed by OrgB's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
