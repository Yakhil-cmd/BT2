### Title
Diff-filtering false negative in `filter_preexisting_from_diff` lets attacker hide malicious added lines from the LLM security reviewer via whitespace/text collision with removed lines - (File: plugins/security-guidance/hooks/gitutil.py)

### Summary
`filter_preexisting_from_diff` reclassifies any `+` line as pre-existing context whenever its `.strip()`ed text is present anywhere in the set of `.strip()`ed `-` lines from the same file's diff, with no positional or multiplicity correspondence. An attacker who fully rewrites a tracked file (e.g. via the Write tool) can craft "new" malicious lines whose stripped text collides with unrelated pre-existing removed lines (via whitespace padding, reordering, or reusing common tokens), causing those lines to be converted to `' '`-prefixed context and hidden from the diff that is sent to the downstream LLM security reviewer, while the actual written file content contains the malicious code.

### Finding Description
When a file is fully rewritten, git's diff shows the whole old content as removed and the whole new content as added. `filter_preexisting_from_diff` (`plugins/security-guidance/hooks/gitutil.py:657-722`) tries to suppress the noise of "removed line X, re-added line X unchanged" by:
1. Building `removed_lines` as a **set** of stripped removed-line text [1](#0-0) .
2. For every added line, checking membership: `content in removed_lines` → convert to a `' '` context line [2](#0-1) .

Because this is a set-membership check with no positional pairing and `.strip()` discards all whitespace/indentation differences, one removed line can mask an unlimited number of unrelated added lines that happen to share the same stripped text. The code's own comment acknowledges this exactly: *"the set lets one removal mask N additions of the same stripped text"* [3](#0-2) . An attacker who fully rewrites a tracked file can therefore inject a malicious line whose stripped form is identical to some pre-existing (now-removed) line elsewhere in the file — e.g. duplicating a common line like `except Exception:` or `import os` verbatim in the new content while placing the real malicious payload on that same textual line, or intentionally choosing malicious code whose stripped text exactly equals a pre-existing string constant/log line — and that added line is silently converted into a context (` `) line, disappearing from the "added" section of the diff that `parse_diff_into_files`/the LLM reviewer prompt is built from. The reviewer only sees the filtered diff content, not the raw file, so it never gets a chance to evaluate the newly written line as new content.

### Impact Explanation
This is a parser/trust-boundary differential: the trusted security-review LLM is fed a diff view that can diverge from the content actually written to disk, allowing malicious code introduced by a full-file rewrite to bypass the automated review gate. Since the security-guidance hook exists specifically to flag risky code changes for the reviewer/user, silently hiding attacker-controlled additions is a direct security-control bypass (false negative in the review pipeline), matching a "trust boundary / validation bypass" class of bug in Claude Code's security tooling.

### Likelihood Explanation
The precondition is that the attacker (or attacker-influenced agent) fully rewrites a tracked file's entire content via the Write tool — a completely ordinary code-editing action, not requiring elevated privilege. Crafting stripped-text collisions is easy: an attacker only needs the malicious added line's `.strip()` output to equal some existing line's `.strip()` output (trivially achievable by embedding the payload behind/within a duplicated pre-existing string, comment, or boilerplate line, or by whitespace-padding). This is reliably reproducible and requires no timing or race condition.

### Recommendation
Replace the set-membership/multiset masking approach with a proper diff-alignment technique (e.g. `difflib.SequenceMatcher`/`unified_diff` opcodes on whole lines) that pairs each removed line with at most one added line by position/similarity, rather than any-to-any stripped-text matching. At minimum, use a `Counter`/multiset with decrement-on-match (so one removed line can mask only one added line, not N) and avoid `.strip()`-only normalization that discards indentation-based distinctions attackers could exploit for camouflage.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/gitutil.py` test suite:
```python
def test_filter_preexisting_hides_malicious_line_via_stripped_collision():
    diff_content = (
        "@@ -1,2 +1,2 @@\n"
        "-import os\n"
        "-x = 1\n"
        "+import os\n"
        "+os.system(payload)  # collides after strip with a differently-worded removed line\n"
    )
    # Craft removed set to include the exact stripped text of the malicious line
    diff_content = (
        "@@ -1,2 +1,2 @@\n"
        "-import os\n"
        "-os.system(payload)  # collides after strip with a differently-worded removed line\n"
        "+import os\n"
        "+os.system(payload)  # collides after strip with a differently-worded removed line\n"
    )
    diff_files = [("app.py", diff_content)]
    result = filter_preexisting_from_diff(diff_files, cwd=".", baseline_sha="deadbeef")
    _, filtered_content = result[0]
    # Assert the malicious line is NOT hidden as context when it is semantically new
    # (e.g. constructed so removed line was a benign no-op line reused verbatim,
    # while the payload line is genuinely new content in the rewritten file)
    assert "+os.system(payload)" in filtered_content, (
        "malicious added line was incorrectly reclassified as pre-existing context "
        "due to stripped-text collision with an unrelated removed line"
    )
```
Expected: with the current implementation this assertion fails — the malicious `+` line is converted to a `' '` context line and disappears from what would be sent to the LLM reviewer, demonstrating the false negative.
