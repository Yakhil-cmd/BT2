### Title
Unauthenticated SSE subscription to any stack's live event channel via `mount Pubsubstub::StreamAction` - (File: config/routes.rb)

### Summary
`Shipit::Engine.routes.draw` mounts the raw `Pubsubstub::StreamAction` Rack app at `/events` [1](#0-0) , completely bypassing `Shipit::Authentication#force_github_authentication`, which is only wired in via `before_action` on controllers that include the `Shipit::Authentication` concern [2](#0-1) . Since the mount is a plain Rack endpoint (not an `ActionController` action), no `before_action` filter ever runs against it, letting anyone open a long-lived SSE stream on any `stack.<id>` channel without a session.

### Finding Description
The claimed binding is: `force_github_authentication` invoked before response == true for every request that reaches views/pages showing stack data (`stacks#show`, `all_tasks`, `merge_requests#index`, etc.), all of which include `Shipit::Authentication` through `Shipit::ShipitController` [3](#0-2) . For the `/events` mount, that binding is false: `Pubsubstub::StreamAction.new` is mounted directly in `Shipit::Engine.routes.draw`, with no `before_action`, no wrapping controller, and no additional Rack middleware constraining channel access [4](#0-3) .

The application itself treats these channels as sensitive-enough to gate behind login for normal browsing: views call `subscribe events_path(channels: ["stack.#{@stack.id}"])` only from pages that require an authenticated, authorized session (e.g. `stacks/show.html.erb`, `stacks/all_tasks.html.erb`, `merge_requests/index.html.erb`) [5](#0-4) [6](#0-5) [7](#0-6) . But nothing prevents a caller from connecting to `events_path` directly with an arbitrary/guessed `channels[]` parameter, since the SSE endpoint itself performs no session or permission check — it is Pubsubstub's generic stream dispatcher, invoked outside the controller stack.

`Stack#broadcast_update` publishes `{id, updated_at}.to_json` on channel `"stack.#{id}"` whenever a stack updates [8](#0-7) , and status/commit updates trigger the same kind of broadcast on `stack.<id>` channels, as shown by the test helpers asserting `Pubsubstub.publish` calls with `channel == "stack.#{stack.id}"` on commit/status creation [9](#0-8) [10](#0-9) . Stack IDs are small sequential integers, so an attacker can enumerate `stack.1`, `stack.2`, … `stack.N` without any prior leak being strictly necessary.

Existing guards that fail to apply here: `force_github_authentication`/`User#authorized?` only run inside controllers using the `Shipit::Authentication` concern [11](#0-10) ; `Shipit::SameSiteCookieMiddleware` and the OmniAuth middleware configured in `lib/shipit/engine.rb` address cookie/OAuth handling, not endpoint authorization [12](#0-11) ; none of these attach to a Rack app mounted directly in the router.

### Impact Explanation
Any unauthenticated caller can open `GET /events?channels[]=stack.<id>` and receive a live stream of update notifications for that stack — deploy/task/commit-status change events — for any stack ID in the system, repeatable indefinitely and across every tenant/stack hosted by the instance. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity category: it does not require credentials, is not rate-limited by any authorization check, and scales to every stack simply by varying the channel parameter.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required; stack IDs are small sequential integers so enumeration is trivial without needing the `MergeStatusController#check` leak mentioned in the scenario. No Shipit configuration disables this (the mount is unconditional in `config/routes.rb`), and the attacker needs zero secrets, tokens, or team membership. This is trivially and repeatably exploitable from any HTTP client capable of holding open a connection.

### Recommendation
Do not mount `Pubsubstub::StreamAction` directly and unauthenticated. Wrap it behind a controller/action that includes `Shipit::Authentication` (or an equivalent Rack middleware) to enforce `force_github_authentication`, and additionally validate that the authenticated user is authorized to view the specific `stack.<id>`/`task.<id>` channel(s) requested (e.g., checking stack visibility/permissions per channel) before allowing the subscription, rather than trusting the raw `channels[]` param.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "GET /events?channels[]=stack.<id> is reachable without any session" do
      stack = shipit_stacks(:shipit)

      # No session[:user_id] set, no api client, no github auth performed.
      get "/events", params: { channels: ["stack.#{stack.id}"] },
          headers: { "Accept" => "text/event-stream" }

      # Binding under test: force_github_authentication ran == true is expected
      # for any Shipit page exposing stack.<id> data; for /events it is false.
      refute_redirected_to Shipit::Engine.routes.url_helpers.github_authentication_path
      assert_response :success # or :ok / streaming, never a redirect to login
    end
  end
end
```
This demonstrates the divergence: every other route touching `stack.<id>` data redirects unauthenticated requests to `github_authentication_path` via `force_github_authentication`, while `/events` accepts the same unauthenticated request and streams the channel's events.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
