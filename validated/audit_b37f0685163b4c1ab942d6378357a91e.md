### Title
Webhook signature verification uses an attacker-chosen organization while status/event processing is applied without matching that organization to the affected repository or commit - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login`/`organization.login` directly from the unauthenticated JSON payload, before the signature check has run. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization's `webhook_secret` is blank — a state the documentation itself calls "optional". Downstream, `StatusHandler#process` applies the payload to any `Commit` matching the SHA globally, without re-checking that the SHA belongs to a repository owned by the organization whose secret was used to authenticate the request. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The binding that is expected to hold is: **organization authenticated by the webhook signature == organization/repository whose state is mutated by the event handler**.

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fields taken from the unverified request body itself. [4](#0-3) [5](#0-4) 

`Shipit.github` supports a multi-organization configuration keyed by organization name, each with its own independent `webhook_secret`: [6](#0-5) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatic success:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

The setup documentation confirms `webhook_secret` is optional for any configured organization: [7](#0-6) 

Once `verify_signature` passes, `create` parses the *same* raw payload and dispatches it to handlers keyed only by `X-Github-Event`, with no re-validation that the event's `repository`/`organization` fields correspond to the organization that was actually used to authenticate the signature: [8](#0-7) 

Critically, `StatusHandler#process` (event `status`) resolves target commits purely by SHA across the entire instance, with no scoping to a repository or organization at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Combined, an unprivileged attacker who knows (a) that a Shipit deployment is configured with multiple GitHub organizations, and (b) that at least one of those organizations has no `webhook_secret` set, can send a forged webhook POST to `/webhooks` with:
- `X-Github-Event: status`
- `repository.owner.login` (or `organization.login`) set to the organization with the blank secret — so `verify_signature` passes unconditionally via the `return true unless webhook_secret` branch,
- `sha` set to the SHA of any commit tracked by *any* stack in the instance, including stacks belonging to a completely different, secret-protected organization,
- `state: "success"` and a matching `context`.

This breaks the equality **organization authenticated == repository/commit written**: the request is authenticated as belonging to the low-security organization, but the mutation (`Commit#create_status_from_github!`) is applied to a commit under an unrelated organization/repository whose real webhook traffic is protected by a secret the attacker never had to satisfy.

### Impact Explanation
Commit statuses are part of the CI-gating mechanism (`required_statuses`/`blocking_statuses` in `DeploySpec`) that determines whether a commit is considered deployable. By forging a `status` event authenticated under a low-security organization but targeting a commit SHA belonging to a different, protected repository, an attacker can inject a fabricated "success" CI status for a commit that never actually passed CI in the real repository. This can cause an otherwise-legitimate, authorized user to deploy an unreviewed/failing commit, which falls under "unauthorized deploy" (High/Critical per the scoring rubric), because it lets the attacker manipulate deploy-gating state for a repository/organization boundary they did not authenticate against.

### Likelihood Explanation
Exploitability depends on:
1. The Shipit instance being configured with the multi-organization `github:` schema (`app/config` — documented and supported first-class functionality, not exotic misuse). [9](#0-8) 
2. At least one configured organization having a blank `webhook_secret` (explicitly documented as "optional"). [7](#0-6) 

Given that webhook secrets are optional and organizations are frequently added incrementally (some fully configured, some not yet), this is a realistic misconfiguration rather than a purely theoretical one, and no attacker credential, session, or GitHub write access is required — only the ability to send an HTTP POST to the public `/webhooks` endpoint and knowledge of a target commit SHA (obtainable from any public GitHub repository).

### Recommendation
- Do not select the verification secret/organization from unauthenticated request body fields. Either verify the signature against every configured organization's secret and require exactly one HMAC match, or bind the request to an organization via a source that cannot be spoofed (e.g., a per-organization webhook path segment established at App configuration time).
- In `StatusHandler` (and other handlers resolving records by fields such as `sha` alone), scope lookups to the repository/organization that was actually authenticated for the request, rejecting events whose payload repository does not match the authenticated organization.
- Treat a blank `webhook_secret` as "verification not required only for that organization's own repositories," not as a blanket bypass usable to authenticate arbitrary payloads referencing other organizations' data.

### Proof of Concept
1. Configure Shipit (per documented multi-org schema) with two organizations: `org-a` (no `webhook_secret` set) and `org-b` (`webhook_secret: <secret>`), with a stack tracking a repository under `org-b`.
2. Note the SHA of a real commit tracked by the `org-b` stack (e.g., from a pushed feature branch that failed CI).
3. Send, without any signature or with an arbitrary bogus `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status

{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/whatever"},
  "sha": "<org-b commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{"name": "some-branch"}]
}
```
4. `verify_signature` calls `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the actual (or missing) signature header. [4](#0-3) [2](#0-1) 
5. `StatusHandler#process` matches `Commit.where(sha: "<org-b commit sha>")` and creates a "success" status on that commit, regardless of it belonging to `org-b`'s repository. [3](#0-2) 
6. If that commit's real CI status was previously failing/pending, the forged "success" status can satisfy `required_statuses` and make the commit appear deployable in the `org-b` stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
