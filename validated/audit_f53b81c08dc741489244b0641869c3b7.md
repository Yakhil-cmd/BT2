### Title
No-secret organization forged `status` webhook lets an attacker mark an arbitrary commit deployable and ship it - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` without any check whenever `webhook_secret` is blank for the resolved organization, and the organization used to resolve the `GitHubApp` instance is taken directly from attacker-controlled JSON (`repository.owner.login`). Combined with the fact that `StatusHandler#process` looks up commits by `sha` alone with no repository scoping, an attacker can forge a `status` webhook, have it accepted unauthenticated because the target org has no configured `webhook_secret`, and write a fabricated CI status onto any commit (including a victim's) purely by knowing its SHA.

### Finding Description
The broken binding is: `verified == (HMAC-SHA1(webhook_secret, raw_body) matches X-Hub-Signature)`. In reality, `verify_webhook_signature` short-circuits this equality: [1](#0-0) 

`return true unless webhook_secret` means when the resolved organization's config has no `webhook_secret`, the equality is never evaluated — `verified` is unconditionally `true` regardless of body or signature.

The organization used to look up the `GitHubApp` (and thus decide whether a secret exists) is derived entirely from the untrusted payload: [2](#0-1) [3](#0-2) 

So an attacker who sets `repository.owner.login` to any org name that is configured in `Shipit.github_configs` but has no `webhook_secret` set causes `Shipit.github(organization: repository_owner)` to return a `GitHubApp` whose `verify_webhook_signature` always passes — no HMAC, no session, no API token needed.

Once accepted, the `status` event is dispatched to `StatusHandler#process`: [4](#0-3) 

This handler resolves target commits **only by `sha`**, with no filter on the owning stack, repository, or the `repository.full_name` in the forged payload. If the attacker knows (or guesses/observes, e.g. from a public PR) the SHA of a victim's commit tracked by an unrelated stack, `Commit.where(sha: params.sha)` will match that victim commit even though the forged payload's `repository.owner.login` is the unrelated no-secret org. `commit.create_status_from_github!(params)` then writes a fabricated status (e.g. `state: "success"` for whatever `context` the victim's deploy gating relies on) onto the victim's commit.

Existing guards do not stop this:
- `drop_unhandled_event` only filters unregistered event types, not authentication.
- `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only rejects organizations that are *not configured at all* — it does nothing for a *configured* org lacking a secret.
- There is no check anywhere in `StatusHandler` or `Commit#create_status_from_github!` that the forged `repository.full_name`/owner actually corresponds to the stack(s) that own the matched commit's SHA.

### Impact Explanation
An unauthenticated attacker can inject a forged, unsigned `status` payload that is accepted as if it originated from GitHub for the misconfigured organization, and use it to write a fabricated commit status onto any commit by SHA across the entire Shipit instance — including commits belonging to stacks/repositories the attacker does not own. If a victim stack's deploy gating depends on a specific status context (a common Shipit pattern for making a commit "deployable"), this forged status can flip that commit into a deployable state, after which a deploy of attacker-influenced/victim code can be triggered through the normal deploy flow. This is a cross-tenant, unauthenticated state-mutation-from-authentication-bypass matching the "Critical: forged webhook accepted / unauthorized deploy of attacker-controlled code" category, repeatable against any commit SHA once at least one org in the Shipit config is missing `webhook_secret`.

### Likelihood Explanation
The attack requires one precondition entirely under the Shipit operator's control and outside the attacker's reach: at least one organization must be present in `Shipit.github_configs` (`TOP_LEVEL_GH_KEYS` includes `webhook_secret`) with a blank/unset `webhook_secret`. If that misconfiguration exists, the rest of the attack is trivial and free for the attacker: no session, no API token, no GitHub App key — just a raw `POST /webhooks` with `X-Github-Event: status` and a JSON body naming the no-secret org and the victim's known commit SHA. It is fully repeatable against arbitrary commits/stacks with no rate limiting beyond normal HTTP throughput.

### Recommendation
- Fail closed instead of open in `GitHubApp#verify_webhook_signature`: if `webhook_secret` is blank, reject the webhook (return `false`) rather than treating it as verified, and require every configured organization to set a `webhook_secret` (fail startup/config validation otherwise).
- Additionally, scope `StatusHandler#process` (and other handlers that key off `sha` alone) to commits belonging to a stack/repository whose `full_name`/owner matches the payload's `repository`, so that even a webhook accepted for organization A cannot mutate state belonging to repository B.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure a test-only org (e.g. `"no-secret-org"`) in `Shipit.github_configs` with `webhook_secret` blank/absent, alongside the existing `"shopify"` config that has a secret.
2. Create a victim commit fixture (`shipit_commits(:first)`) belonging to a stack under a *different* repository/org (e.g. `"shopify/other-repo"`).
3. Build a forged `status` payload: `{ "sha" => commit.sha, "state" => "success", "context" => "<the context the victim stack gates deploy on>", "repository" => { "owner" => { "login" => "no-secret-org" } } }`, with **no** `X-Hub-Signature` header (or an arbitrary bogus one).
4. `post :create, body: payload.to_json, as: :json` with `X-Github-Event: status`.
5. Assert:
   - Left side of the equality (`verified`) is `true` even though no valid HMAC was supplied — assert `response.status == 200` (not `422`).
   - Right side: `commit.statuses.last.state == "success"` and `commit.statuses.last.context == "<context>"` — i.e., the victim commit belonging to a repository that never validated this request now has attacker-controlled state.
   - Optionally, assert the stack's deployability predicate (e.g. `stack.commits.last.deployable?` or equivalent status-aggregation check used by the deploy flow) now returns `true` as a result of the forged status, demonstrating the "mark deployable" claim.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
