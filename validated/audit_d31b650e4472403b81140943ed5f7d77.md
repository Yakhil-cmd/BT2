### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is applied to the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports a multi-organization GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using an unverified JSON field taken from the request body itself, while the handlers that actually mutate state select the target repository/stack using a *different* unverified field from the same body. This mirrors the reported UniswapV2 issue's root cause: a value that is trusted and acted upon (which repo/stack to write to) is not the same value that was actually authenticated (which org's secret validated the signature) — an equality binding that the code assumes but never enforces.

### Finding Description
`verify_signature` picks the GitHub App/secret to validate against via:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github[org]`, meaning distinct GitHub App installations/orgs configured in `credentials.yml` can have distinct `webhook_secret` values [1](#0-0) .

Once the signature check passes, event handlers resolve the actual repository/stack to act on from a **different** JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` splits `"owner/name"` and does a direct DB lookup with no cross-check against the org that was used to select the verification secret [5](#0-4) . `PushHandler` and other handlers (e.g. `StatusHandler`, `PullRequest::*Handler`) then operate on whatever stacks are returned [6](#0-5) .

The binding that should hold is:
`organization whose secret validated the signature == organization that owns the repository/stack being mutated`

Because both `repository.owner.login` (used for auth) and `repository.full_name` (used for the write target) are independent, attacker-controlled fields inside the *same* signed payload, an attacker who possesses (or controls) the webhook secret for **any one** configured organization (e.g. their own org, onto which they installed the Shipit-integrated GitHub App) can craft a payload where:
- `repository.owner.login` / `organization.login` = their own org (so `verify_signature` selects and validates against their own org's secret, which they know), and
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves and mutates a stack belonging to a completely different organization).

The signature only proves "this payload was HMAC-signed with OrgA's secret" — it says nothing about which repository the payload's business fields claim to describe. Nothing in the request pipeline re-validates that `repository.full_name`'s owner segment equals `repository_owner`.

### Impact Explanation
This lets an attacker who controls a webhook secret for one onboarded organization inject forged, signature-valid webhook events (`push`, `status`, `check_suite`, `pull_request` reopened/labeled/unlabeled, `membership`, etc.) that are applied against stacks belonging to a different repository/organization they do not control. Depending on handler, this can:
- Trigger `sync_github` for a target stack with an attacker-chosen `expected_head_sha` [6](#0-5) ,
- Forge commit `status`/`check_run` state for arbitrary commits, potentially unblocking CI gating checks that a stack's merge/deploy pipeline relies on [7](#0-6) ,
- Archive/unarchive review stacks or manipulate PR-provisioning behavior on a foreign repository via label handlers [8](#0-7) .

This is cross-organization/cross-repository interference achieved purely by owning a legitimately-issued webhook secret for a *different* (unrelated) organization, i.e., unauthorized writes/state changes on a stack outside the attacker's authorized scope — matching the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Exploitability depends entirely on the multi-org deployment shape: it requires Shipit to be configured with more than one GitHub organization/App secret (`secrets.github` keyed by org) and the attacker to be an authorized webhook sender for at least one of them (i.e., they administer a GitHub App installation whose webhook deliveries reach this same Shipit instance). This is a realistic deployment pattern for the multi-tenant Shipit configuration schema itself supports, but I could not verify from the indexed code how commonly this multi-org mode is used in practice versus the single-org fallback, nor whether any additional validation exists elsewhere in the request pipeline (e.g., Rails routing constraints) that I may have missed due to index coverage limits.

### Recommendation
After signature verification succeeds for organization `repository_owner`, re-validate that every downstream-trusted field derived from the payload (in particular `repository.full_name`'s owner segment, and any `organization.login`) is consistent with `repository_owner` before dispatching to handlers — reject the webhook if they differ. Alternatively, resolve the target `Repository`/`Stack` using the same organization value that was authenticated, rather than trusting `repository.full_name` independently in `Shipit::Webhooks::Handlers::Handler#repository_name`.

### Proof of Concept
Conceptual reproduction using the existing test scaffolding pattern in `test/controllers/webhooks_controller_test.rb`:
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-org schema per `lib/shipit.rb`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known webhook secret and sets `X-Hub-Signature` accordingly.
4. `WebhooksController#repository_owner` returns `"attacker-org"`; `verify_signature` looks up and validates against `attacker-org`'s secret — signature check passes.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on a stack the attacker does not own [6](#0-5) .

I was not able to fully confirm end-to-end request routing behavior (e.g., whether any Rails-level route/host constraint additionally scopes requests per organization) beyond what's in `app/controllers/shipit/webhooks_controller.rb`, since some configuration/deployment code may be outside indexed scope.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
