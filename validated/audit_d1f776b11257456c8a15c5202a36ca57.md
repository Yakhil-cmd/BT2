### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while the mutated stack is resolved from the independent `repository.full_name` field, allowing an unconfigured/attacker-named org to authorize writes to any other org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to validate `X-Hub-Signature` based solely on `params.dig('repository','owner','login')`, while every pull_request handler (e.g. `EditedHandler`) resolves the actual `Shipit::Repository`/stack to mutate from the separate `params.repository.full_name` field. Because both fields live in the same attacker-controlled JSON body with no cross-check, an attacker can set `repository.owner.login` to an unconfigured organization (whose `webhook_secret` is blank, making `verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to a fully-configured victim organization's repo, bypassing signature verification entirely for that victim.

### Finding Description
The claimed binding is: `organization_authenticating(request) == organization_owning(mutated_row)`, where:
- `organization_authenticating(request)` = the org used to pick the `GitHubApp` in `verify_signature`: `Shipit.github(organization: repository_owner)` with `repository_owner = params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) 
- `organization_owning(mutated_row)` = the org implicit in the repository the handler actually mutates, derived from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , and the base `Handler` class uses the same key independently for its `stacks`/`repository_name` helper [4](#0-3) .

These two reads (`repository.owner.login` vs `repository.full_name`) are independent keys of the same attacker-supplied JSON object; nothing in `verify_signature`, `ExplicitParameters` schemas, or the handlers cross-validates that `owner.login` matches the owner segment implied by `full_name`.

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the app's `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) .

Exploit flow:
1. Shipit is configured with two GitHub Apps: `OrgA` (no `webhook_secret` set - e.g. a demo/legacy/misconfigured org) and `OrgB` (properly configured with a secret, owning the real target repository/stack).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, a garbage `X-Hub-Signature`, and a JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/target-repo"`
   - `action = "edited"`, plus the other fields required by `EditedHandler`'s `ExplicitParameters` schema [6](#0-5) 
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the garbage signature - no `head(422)` [1](#0-0) .
4. `EditedHandler#process` runs, using `params.repository.full_name` ("OrgB/target-repo") to locate `Repository`/`PullRequest` and calls `pull_request.update(github_pull_request: params.pull_request)`, mutating OrgB's `PullRequest` row despite zero valid signature for OrgB [7](#0-6) .

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered [8](#0-7) ; the `ExplicitParameters` schema only validates types/presence, not owner/full_name consistency; and `verify_signature` never inspects `full_name`, only `owner.login`.

### Impact Explanation
An attacker who controls zero secrets can forge a webhook that mutates a `PullRequest` record belonging to any organization/repository configured in Shipit, as long as any other configured (or trivially creatable, if the deployment allows self-registration of GitHub Apps/orgs) GitHub App entry has a blank `webhook_secret`. This is a cross-tenant authentication bypass: signature verification for org B is effectively skipped by routing the "authenticating org" field to org A. The blast radius covers every handler that resolves its target repository from `params.repository.full_name` independently of the org used for signature checks (`EditedHandler`, `ClosedHandler`, `LabelCapturingHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, and the base `Handler#stacks`) . This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one configured `GitHubApp` entry with a blank/unset `webhook_secret` (e.g. an org added to `Shipit.github_apps` config without a secret, which the code explicitly tolerates via `return true unless webhook_secret`). Given that precondition, the attack costs a single unauthenticated HTTP POST, is fully repeatable, and requires no session, token, or knowledge of any secret - only knowledge of the two org names and target repo full name. Whether real-world deployments actually leave an org unconfigured is an operational/config question outside pure code analysis, but the code itself provides no defense-in-depth against it: the binding between the org selected for authentication and the org whose data gets mutated is never enforced.

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner`, cross-validate it against the actual owner segment of `params.repository.full_name` (e.g. `full_name.split('/').first == repository_owner`) and reject (`head 422`) on mismatch. Additionally, consider hardening `GitHubApp#verify_webhook_signature` to fail closed (return `false`) when `webhook_secret` is blank rather than bypassing verification, unless there is an explicit, intentional "unsecured org" opt-in that is documented and scoped.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "signature for org without webhook_secret cannot authorize mutation of another org's stack" do
  # Fixture: OrgA GitHubApp with webhook_secret: nil (or blank)
  # Fixture: OrgB GitHubApp with webhook_secret: "orgb-secret"
  stack = shipit_stacks(:shipit) # belongs to repository owned by OrgB
  pr = create_pull_request(stack: stack, number: 42)

  payload = {
    action: "edited",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "https://api.github.com/...", title: "new title",
      state: "open", additions: 1, deletions: 1,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: { owner: { login: "OrgA" }, full_name: stack.repository.full_name }, # OrgB's repo
    sender: { login: "attacker" }
  }.to_json

  post "/webhooks", params: payload, headers: {
    "Content-Type" => "application/json",
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => "sha1=deadbeef" # garbage signature
  }

  assert_response :ok
  # Binding check: authenticating org (OrgA, unconfigured) != owning org (OrgB, secured)
  assert_equal "new title", pr.reload.title # mutation succeeded despite invalid signature for OrgB
end
```
This demonstrates that `EditedHandler#process` updates a `PullRequest` under `OrgB`'s stack even though the request's `X-Hub-Signature` was never validated against `OrgB`'s `webhook_secret` - only against `OrgA`'s absent one.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
