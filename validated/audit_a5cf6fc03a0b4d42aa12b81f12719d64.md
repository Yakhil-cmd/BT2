### Title
Cross-organization webhook forgery: signature is verified against `repository.owner.login`, but `MembershipHandler` trusts the independent `organization.login` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature against using `repository_owner`, which reads `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')` only if `repository` is absent) [1](#0-0) . When both `repository` and `organization` are present in the JSON body, only `repository.owner.login` is authenticated by the signature; `organization.login` is never checked against it. `Shipit::Webhooks::Handlers::MembershipHandler`, however, uses `params.organization.login` (not `repository.owner.login`) to decide which `Team.organization` to create/mutate and which team a GitHub user is added to or removed from [2](#0-1) . This breaks the binding: `organization authenticated by signature == organization whose Team/membership is written`.

### Finding Description
The verification flow is:
1. `verify_signature` computes `repository_owner` and calls `Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(header, raw_post)` [3](#0-2) .
2. `Shipit.github` resolves the per-organization config/secret keyed strictly by that `organization` argument [4](#0-3) , and `verify_webhook_signature` HMACs against that org's configured `webhook_secret` [5](#0-4) .
3. Once the signature validates, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which reads `params.organization.login` — an entirely separate JSON field that was never used to pick the verifying secret — and uses it to `find_or_create_team!` (`team.organization = params.organization.login`) and to add/remove `params.member.login` from that team [6](#0-5) .

Because a JSON payload can legally contain both a `repository` object and an unrelated `organization` object, an attacker who controls (or has been issued) a valid webhook secret for **any one** organization configured on the Shipit instance (the multi-org config format is explicitly supported, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`) can:
- Set `repository.owner.login` = the organization whose secret they know (so the HMAC verifies).
- Set `organization.login` = a **different**, victim organization also configured on the same Shipit instance, plus an arbitrary `team` and `member.login`.

The signature check passes (it only validates the first org), and `MembershipHandler` creates/updates a `Team` scoped to the victim organization and adds the attacker-chosen GitHub login as a member of that team, with no cross-check that the two organizations match. `GithubOrganizationUnknown` is only raised if `repository_owner`'s org isn't configured at all [7](#0-6) , so it does not protect against this mismatch since the attacker deliberately picks an org they *do* have a valid secret for.

### Impact Explanation
`User#authorized?` gates all Shipit UI/API access on team membership: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) . If any of `Shipit.github_teams` belongs to the victim organization, forging a `membership` webhook lets the attacker add an arbitrary GitHub login (that they control, or that they subsequently authenticate as via GitHub OAuth) as a member of that authorized team — escalating an unprivileged external actor into `Shipit.github_teams` authorization for a multi-tenant Shipit deployment. This matches the High-severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Exploitation requires only:
- Multi-organization Shipit configuration (explicitly documented/supported, e.g. `test/dummy/config/secrets_double_github_app.yml`), and
- The attacker holding a valid webhook secret/signing capability for at least one of the configured organizations — plausible in shared/multi-tenant Shipit installs where different, mutually untrusted GitHub orgs are each given their own App/secret but share one Shipit instance and one `Shipit.github_teams` authorization pool.

No GitHub App private key, `ApiClient` token, or Shipit session is needed — only the ability to send a raw HTTP POST to `/webhooks` with a correctly signed body for one org and attacker-chosen `organization`/`team`/`member` fields for another. This is a code-level binding defect, not a documented/expected admin misconfiguration (unlike a deliberately-nil `webhook_secret`).

### Recommendation
In `MembershipHandler` (and any other handler that reads an `organization`/`repository` field independent of the field used in `WebhooksController#repository_owner`), require that `params.organization.login` (or `repository.owner.login`) equals the `repository_owner` value that was actually verified against the signature, rejecting the event otherwise. Alternatively, pass the authenticated organization explicitly from the controller into every handler and have handlers use that value exclusively instead of re-reading potentially-mismatched fields from the raw payload.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known/controlled by the attacker, e.g. their own GitHub App) and `victim-org` (belongs to `Shipit.github_teams`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature` computed with `attacker-org`'s webhook secret over the body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies the HMAC successfully against `attacker-org`'s secret [3](#0-2) .
4. `MembershipHandler#process` creates/uses a `Team` with `organization = "victim-org"` and adds `attacker-github-login` to it [6](#0-5) .
5. If that team is in `Shipit.github_teams`, the attacker's GitHub account is now authorized against `victim-org`'s Shipit stacks upon logging in via GitHub OAuth.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
