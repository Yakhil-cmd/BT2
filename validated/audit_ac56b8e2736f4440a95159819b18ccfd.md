### Title
Reachable `throw Error` invariant assertions in payment/spend-proof double-spend handling crash the full node process - (File: `validation.js`)

### Summary
The MongoDB advisory describes an authenticated, unprivileged user issuing a crafted aggregation command that triggers an internal invariant inconsistency (engine-selection mismatch), causing `mongod` to abort via an assertion failure and terminate the whole process, denying service to all clients. The analogous class in ocore is a `throw Error(...)` used as an internal-invariant/"can't happen" assertion inside the unit/payment validation pipeline. Because ocore's node treats any uncaught exception as fatal (`process.on('uncaughtException', ...)` re-throws to crash the process, see `network.js:4530-4543`), any code path where an attacker-controlled combination of payment fields can violate one of these validation-time invariants results in the whole node process terminating — a network-wide denial of service until the node operator restarts, exactly mirroring the impact described in the report.

### Finding Description
`validation.js` contains several `throw Error(...)` statements inside `checkForDoublespends` and `validatePaymentInputsAndOutputs` that are meant to be unreachable "should never happen" assertions, guarding assumptions about internal state consistency between separate validation subsystems (double-spend graph lookup, spend-proof bookkeeping, and private/public payment state):

- In `checkForDoublespends`, when a conflicting record's owning address is not among the unit's authors, or when a conflicting record is neither clearly included in an ancestor nor associated with `objValidationState.arrAddressesWithForkedPath`, the code throws instead of returning a normal validation error: [1](#0-0) 

- In `validatePaymentInputsAndOutputs`, when a private, fixed-denomination asset's double-spend check ultimately fails even though a spend proof was supplied and the node is not light, the code asserts `"spend proof didn't help: "+err` and throws: [2](#0-1) 

- Adjacent invariant throws exist for the same code path when transferring private fixed-denomination coins (`no src_coin`, `no src_output`, `no denomination in src coin`, `no src coin amount`) and for public transfers (`more than 1 src output`, `spending a stable temp-bad output`, `src output amount is not a number`): [3](#0-2) [4](#0-3) [5](#0-4) 

These asserts are reached from `validateMessage` → `validateSpendProofs`/`validatePayload` → `validateInlinePayload` → `validatePayment` → `validatePaymentInputsAndOutputs`, all of which are exercised whenever any user posts a unit containing a `payment` message (public or private) — i.e., fully reachable by an ordinary, unprivileged unit poster or a private-payment counterparty, with no special permissions required: [6](#0-5) [7](#0-6) 

The MongoDB bug is specifically about an *engine selection* inconsistency arising from a *particular combination of options* in one command. The structural analog here is the double-spend/spend-proof subsystem maintaining two different "views" of validity (SQL-based conflict lookup in `checkForDoublespends` vs. the `arrAddressesWithForkedPath`/sequence bookkeeping computed elsewhere in `validateAuthors`/`validateParents`) that are assumed to always agree; a unit combining specific input types (e.g., `type=transfer` with a private, fixed-denomination asset lacking a valid `src_coin`, or a `spend_proofs` entry combined with a conflicting `divisible input` for the same address) can desynchronize these two views and hit the `throw Error` guard instead of a graceful validation rejection.

### Impact Explanation
Any of these `throw Error` calls escape all `try/catch` wrapping in `validate()` (there is none around the async series that reaches this deep) and propagate up as an uncaught exception. `network.js` installs a global handler that deliberately re-throws to crash the process rather than attempt recovery, because internal state (mutex locks, caches) may be corrupted: [8](#0-7) 

A crashed full node stops relaying, validating, and confirming units for all peers connected to it until manually restarted — the same "denial of service for all connected clients until the process is restarted" impact described in the advisory. If this can be repeated against enough hub/witness nodes, the network's ability to confirm new units is degraded.

### Likelihood Explanation
Reachability requires only posting a unit with a payment message — no elevated privileges, hub/witness role, or special peer/network position — matching an "authenticated user with read-only-equivalent privileges" analog (an ordinary unit poster). However, precisely engineering the state divergence needed to trip one of these specific throws (rather than a normal, graceful validation error) likely requires crafting inputs referencing specific already-committed conflicting spends/private-payment state, so it is not a one-line trivial reproduction; it depends on database state that an attacker would need to set up first (e.g., prior conflicting inputs, mismatched `src_coin`). This raises the bar somewhat compared to the MongoDB case (a single aggregation command), but the underlying primitive — attacker-reachable `throw Error` "assertions" in unit validation causing full-process termination — is a known, real bug class in this codebase.

### Recommendation
- Replace all internal-invariant `throw Error(...)` calls reachable from untrusted, attacker-supplied unit content in `checkForDoublespends` and `validatePaymentInputsAndOutputs` with graceful `callback("...")` validation-error returns (as is done for the vast majority of other checks in this file), reserving `throw` only for conditions that are provably unreachable regardless of external input (e.g., only reachable via internal-only code paths like `bAA`).
- Audit `validation.js` for the full set of `throw Error` statements inside functions invoked from `validateMessage`/`validatePayment`/`checkForDoublespends`/`validateAuthentifiers`, and reclassify each as either (a) truly internal-only and unreachable from external input, or (b) reachable and therefore needing to become soft validation failures.
- Add defensive fuzz/property tests that post malformed/conflicting payment and spend-proof combinations (mismatched addresses, missing `src_coin` fields, conflicting `type=issue`/`transfer` combos) to confirm none crash the validator.
- Consider wrapping the top-level `validate()` unit-processing path in a `try/catch` that converts any unexpected exception into `ifUnitError`/`ifJointError` for that specific unit (while still logging loudly), rather than allowing it to propagate to the process-level `uncaughtException` handler and take down the whole node.

### Proof of Concept
Not independently reproduced in this repo copy — full reproduction requires constructing the precise prior database state (e.g., an already-accepted conflicting input/spend-proof entry, or a private fixed-denomination transfer with an intentionally malformed `objValidationState.src_coin`) and then submitting a second unit whose payment message hits one of the identified `throw Error` guards during `validatePaymentInputsAndOutputs`/`checkForDoublespends` instead of a normal validation error path. This would need to be exercised in a running test node to confirm which exact combination of `payload.inputs`/`spend_proofs` fields (see line ranges cited above) reaches a `throw` rather than a `cb(err)`.
