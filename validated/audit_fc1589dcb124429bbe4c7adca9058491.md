### Title
Unbounded account creation via 1-unit dust `supply` permanently bloats controller and position-NFT storage - (File: contracts/controller/src/positions/supply.rs)

### Summary
`Controller::supply` accepts `account_id = 0` to create a fresh account, and enforces only that each payment is positive — there is no minimum deposit amount. A single unprivileged address can therefore mint an unbounded number of accounts (each a position-NFT token id) with 1-unit deposits, and every account leaves behind several persistent ledger entries (`AccountMeta`, `SupplyPositions`, NFT `Owner`) that are never garbage-collected.

### Finding Description
The Acala finding concerned `deposit_dex_share` allowing arbitrarily small deposits that bloat runtime storage. The same class exists here in a stronger form: the resource being bloated is not a per-pool position count but the **account namespace itself**.

- `process_supply` routes `account_id == 0` into `account::load_or_create_account`, which mints a new account id (position-NFT token) for the caller (`supply.rs:38-59`). [1](#0-0) 
- The only amount check is `aggregate_positive_payments` / `AmountMustBePositive` on the measured transfer — a deposit of `1` stroop-level unit is accepted (`supply.rs:116-125`). [2](#0-1) 
- Position-count limits (`with_position_limits`, `upsert_or_remove_position`) only cap entries *inside* one account's `Map<HubAssetKey, _>`; they do not bound the number of accounts (`account.rs:190-199`, `storage/account.rs:76-105`). [3](#0-2) 
- Each new account persists `ControllerKey::AccountMeta(id)`, `ControllerKey::SupplyPositions(id)` (written by `write_side_map` because the map is non-empty), `ControllerKey::Delegates(id)` scaffolding, and a position-NFT `Owner(id)` entry — all persistent storage (`storage/account.rs:63-105`, keeper README enumerating these keys). [4](#0-3) 
- The repository's own test suite already demonstrates the primitive: `poc_single_actor_spams_unbounded_dust_accounts` mints the attacker 64 base units of USDC and calls `supply(attacker, 0, 1, [(asset, 1)])` 64 times, asserting each call returns a fresh account id and that every account persists (`tests/test-harness/tests/controller/supply.rs:312-344`). [5](#0-4) 

### Impact Explanation
Every spammed account creates multiple persistent ledger entries on the controller plus an `Owner` entry on the position-NFT contract. These entries have a TTL and must be renewed to stay live — the keeper service explicitly scans and renews `AccountMeta`/`SupplyPositions`/`BorrowPositions`/`Delegates`/`Owner` keys for all ids in `1..=max_account_id` (`keeper/README.md:35-44`, `discovery.rs:821-869`). Because ids are sequential and never reused or reclaimed, an attacker permanently inflates `max_account_id`, which:

- grows archival state and the keeper's renewal footprint linearly in the number of spam accounts (each TTL tick scans and renews a window; a full cycle takes `ceil(max_account_id / max_accounts_scan)` ticks, so spam directly reduces renewal coverage per tick for real users), and
- raises the real cost of keeping the protocol's live state non-archived, while costing the attacker only N base units of the cheapest-listed asset plus transaction fees — e.g. 64 stroop-level units for 64 accounts, per the in-repo PoC.

This is a storage-bloat / griefing DoS matching the accepted category of degraded protocol operation (entries not renewed in time become archived, and operations touching an archived account's keys fail until restored), which is strictly worse than the Acala original since the bloat is per-account across four+ keys rather than per-position within one key.

### Likelihood Explanation
- Fully unprivileged: `supply` requires only `require_authorized_caller` (auth of the caller, not a role) and `account_id = 0` is the documented "create account" path (`supply.rs:38-47`).
- Cost is minimal: one base unit of any listed asset per account; the attacker can even withdraw most of it afterwards — `update_or_remove_supply_position` removes the position map entry at zero scaled amount, but `AccountMeta`, the NFT `Owner` entry, and the consumed id remain forever (`account.rs:189-199`).
- No rate limit, minimum deposit, or fee-on-creation exists in `process_supply` or `process_deposit` (`supply.rs:40-136`).

### Recommendation
Introduce a minimum first-deposit value for account creation, enforced in `process_supply`/`process_deposit` when `account_id == 0` — e.g. require the aggregated USD value (using the already-cached strict prices in `Context`) to meet a floor comparable to `DEFAULT_MIN_BORROW_COLLATERAL_USD_WAD`. Alternatively or additionally:

- charge/burn a small reserve amount on account creation so spam has a non-recoverable cost, or
- allow full withdrawal from a never-borrowed account to tombstone the id (burn the NFT and delete `AccountMeta`) so ids can be reused or at least not renewed.

A per-account minimum mirrors the Acala mitigation ("introduce a minimum deposit amount") but applied at account-creation granularity, which is where this codebase's unbounded growth actually lives.

### Proof of Concept
The existing test is already a working PoC (`tests/test-harness/tests/controller/supply.rs:312-344`): mint the attacker `N` base units, then loop `ctrl.supply(&attacker, &0u64, &1u32, &[(hub_asset, 1i128)])`. Each iteration returns a strictly greater account id and `account_exists(id)` is true — N persistent account sets created for N base units. Setting `N` arbitrarily large shows the account namespace and the keeper renewal surface grow without bound while total attacker spend stays at N units of the cheapest market asset. /// Third parties may only add to existing supply positions. Returns the account id.
pub(crate) fn process_supply(
    env: &Env,
    caller: &Address,
    account_id: u64,
    spoke_id: u32,

    let aggregated = payments::aggregate_positive_payments(env, assets);
    let mut cache = Context::new(env);

    let (acct_id, mut account) = account::load_or_create_account(
        env,
        caller,
        account_id,
        spoke_id,
        PositionMode::Normal,
        account::AccountGuard::Supply,
        &mut cache,
    );

/// Stores a nonempty position map without renewing TTL; deletes an empty map.
fn write_side_map<V: TryFromVal<Env, Val> + IntoVal<Env, Val>>(
    env: &Env,
    key: &ControllerKey,
    map: &Map<HubAssetKey, V>,
) {
    let persistent = env.storage().persistent();
    if map.is_empty() {
        persistent.remove(key);
    } else {
        persistent.set(key, map);
    }
}

#[test]
fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();

    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));
    let asset = usdc.asset.clone();

    let ctrl = t.ctrl_client();
    let mut created: u64 = 0;
    let mut last_id: u64 = 0;
    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
        let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0, "1-unit deposit must be accepted (no dust floor)");

        assert!(id > last_id, "each supply(id=0) must mint a new account id");
        assert!(
            ctrl.account_exists(&id),
            "spammed account persists in storage"
        );
        last_id = id;
        created += 1;
    }

    assert_eq!(
        created, N,
        "one actor created {N} distinct accounts with dust deposits"
    );
}
