### Title
Unbounded swap routes can bind unrelated wallet-token theft to the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-supplied opaque route bytes and forward them to the configured router. The controller validates only the controller’s input/output balances; it does not restrict contracts reached through the route or prevent a malicious hop from attaching an unrelated `token.transfer(victim, attacker, amount)` under the victim’s signed authorization tree. [1](#0-0) 

### Finding Description
`swap_collateral` authenticates `caller`, checks account ownership/delegation, and passes the supplied `swap` bytes into `withdraw_and_swap_from_supply`. [2](#0-1)  The swap helper authorizes only the controller’s exact input transfer, then invokes `router.execute_strategy(controller, amount_in, swap)`; afterward it checks controller token deltas but performs no authorization-tree or route-venue restriction. [3](#0-2) 

A test router/hop demonstrates the resulting behavior: the router decodes the route-supplied `hop_pool` and invokes it, while the malicious pool calls an unrelated token’s `transfer(victim, attacker, amount)`. [4](#0-3) [5](#0-4) 

Soroban records that unrelated transfer as a child of the victim’s `swap_collateral` authorization; if the victim signs the returned tree, enforcing mode executes it. [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary SAC/token balances from a user’s wallet by supplying a route whose venue transfers those assets beneath the user’s signed lending-operation authorization. The stolen asset need not be listed by XOXNO, deposited as collateral, or otherwise related to the lending transaction. The regression test shows Alice’s unrelated `WALLET_BALANCE` reduced to zero and credited to the attacker while the requested swap still completes with fair output. [7](#0-6) [8](#0-7) 

This is theft of user funds, not merely bad routing: the victim can receive the promised swap output and satisfy all protocol risk checks while losing an unrelated wallet token in the same transaction.

### Likelihood Explanation
Any unprivileged user can submit a `swap_collateral` call with attacker-constructed route bytes; an unprivileged attacker can also assemble and submit the transaction once the victim’s authorization entry is signed. The exploit requires the victim to sign an authorization tree containing the extra transfer, which can occur when a wallet or off-chain route builder presents the opaque tree as the result of simulation. The repository’s own test proves that the signed poisoned tree is sufficient for execution. [9](#0-8) 

### Recommendation
Do not expose opaque route execution underneath a broad account-owner authorization. At minimum, enforce an allowlist of route venue contracts and route operation shapes before invoking `execute_strategy`, and surface a machine-readable expected authorization manifest that contains only the intended token movement. Prefer a constrained strategy interface that names approved venues/functions directly rather than arbitrary executable XDR. Clients should also reject any `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization containing unrelated token-transfer children.

### Proof of Concept
1. Deploy a malicious pool that stores `(victim, unrelated_token, attacker, amount)` and, in `swap`, calls `unrelated_token.transfer(victim, attacker, amount)`. The test implementation performs exactly this call. [10](#0-9) 
2. Construct route bytes selecting that pool while still paying a fair `token_out` amount so `verify_router_output` succeeds. The test route uses 5,000 USDC input and returns 2.5 ETH output. [11](#0-10) 
3. Have the victim invoke `swap_collateral(victim, account_id, USDC_key, 50_000_000_000, ETH_key, route)`, authorize `victim`, and sign the authorization tree returned by simulation.
4. The simulation records `unrelated_token.transfer(victim, attacker, WALLET_BALANCE)` beneath `swap_collateral`; signing that tree makes the transfer valid. [12](#0-11) 
5. The transaction succeeds, the account receives the fair swap output, and the attacker receives the victim’s entire unrelated wallet-token balance. [13](#0-12)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
