Based on my investigation, I've identified an analog to the THORChain bug in the `ERC20Transactor` XCM asset transactor.

### Title
ERC20Transactor trusts a locally-deployed ERC20 contract's self-reported `transfer()` return value instead of verifying actual balance deltas, allowing fabricated XCM asset credit for any attacker-controlled contract - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
The THORChain incident exploited a router that trusted a self-reported `msg.value` instead of verifying the actual amount that had moved into the vault. The Polkadot SDK analog is `ERC20Transactor`, the `TransactAsset` implementation used to bridge XCM `withdraw_asset`/`deposit_asset` semantics onto Solidity `IERC20.transfer()` calls executed through `pallet_revive`. It determines whether an asset was actually withdrawn/deposited purely from the callee contract's self-reported outcome (no-revert + ABI-decoded boolean return), never checking that the real on-chain ERC20 balance changed by the claimed `amount`.

### Finding Description
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` implement the `TransactAsset` trait used by the XCM executor for the asset class matched by `ERC20Matcher`: [1](#0-0) 

`IsLocalAccountKey20` matches *any* location of the shape `(0, [AccountKey20 { .. }])` — i.e. any local H160 address, with no allow-list or registry check that it is a "real"/trusted ERC-20 token. This is one of the `AssetTransactors` wired into Asset Hub's XCM config: [2](#0-1) 

For withdraw, the transactor calls the contract's `transfer()` from the user's account to the pallet's `TransfersCheckingAccount`, and *only* checks `did_revert()` and the ABI-decoded boolean return value — it never calls `balanceOf` or otherwise confirms the checking account's balance actually increased by `amount`, nor that the user's balance actually decreased: [3](#0-2) 

The exact same self-reported-success trust pattern is repeated for deposit, transferring from the checking account to the beneficiary: [4](#0-3) 

The credit added to `AssetsInHolding` on a successful "withdraw" is `Erc20Credit(amount)` — a pure imbalance bookkeeping object that is not itself validated against any real balance: [5](#0-4) 

Because a user can deploy an arbitrary contract on Asset Hub via `pallet_revive` (a normal, permissionless action) and that contract's location automatically satisfies `IsLocalAccountKey20`, an attacker can write a `transfer(address,uint256)` function that always returns `true` (per Solidity ABI, `IERC20::transferCall::abi_decode_returns_validate` only checks the boolean was correctly encoded, not that state changed) while performing no actual balance mutation. The XCM executor's `WithdrawAsset`/`DepositAsset` machinery — which underlies `pallet_xcm::execute`, a real signed-extrinsic entry point available to any user — will then treat this as a legitimate transfer of `amount` units of that ERC-20 "asset," producing/consuming `AssetsInHolding` entries with no corresponding real balance movement in the contract.

This exactly mirrors the THORChain violated invariant: the caller/router accepted a self-declared "amount transferred" signal (`msg.value` / boolean `transfer()` return) instead of independently verifying the real balance delta before crediting downstream logic.

### Impact Explanation
On its own, an attacker fabricating credit for their own attacker-deployed token has no victim, since the "asset" carries no external backing. The severity of this finding is conditioned on whether any component in the runtime treats ERC20-Transactor-matched assets as if their balances are trustworthy accounting of real value — for example, a `pallet_asset_conversion` liquidity pool paired against a genuine asset (native token or a `pallet_assets` asset) with `AssetKind = xcm::v5::Location`. In that scenario, an attacker could add "liquidity" consisting of a fabricated ERC20-Transactor credit paired against real DOT/USDC contributed by themselves or drawn from other liquidity providers' pool state, then withdraw the real-asset side, effectively laundering fabricated ERC-20 credit into real value. I was not able to fully trace whether `pallet_asset_conversion::Config::Assets` on Asset Hub actually resolves `Location`-based `AssetKind` through this specific `ERC20Transactor`/XCM executor path versus a separate fungibles abstraction, so I cannot assert High/Critical theft with certainty from static review alone — this requires runtime-level tracing that exceeds what I can verify here.

At minimum, the missing balance-delta check breaks the core `TransactAsset` invariant (`withdraw_asset` must remove exactly `amount` of real value; `deposit_asset` must add exactly `amount` of real value) for any asset matched by `IsLocalAccountKey20`, which is a integrity violation of the AssetsInHolding accounting used throughout the XCM executor for balance-preserving operations, fee refunds, and cross-chain reserve transfers involving this asset class.

### Likelihood Explanation
Reaching this code path requires only a permissionless, unprivileged action: (1) deploy a malicious contract via `pallet_revive::instantiate`, and (2) submit a signed `pallet_xcm::execute` extrinsic with a `WithdrawAsset`/`DepositAsset` program referencing that contract's address as the asset location. No governance, validator, or privileged role is needed. The likelihood of triggering the missing-check condition is high; the likelihood of it translating into loss of real, third-party-owned value depends on further downstream wiring (e.g., asset-conversion pool configuration) that I could not fully confirm.

### Recommendation
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should verify the actual balance delta of the relevant account (via `balanceOf` before/after, or by requiring the contract to be a pre-registered/trusted ERC-20 rather than any arbitrary `AccountKey20` location) instead of relying solely on the contract's self-reported revert status and ABI-decoded boolean return value. Restricting `ERC20Matcher`/`IsLocalAccountKey20` to a governance-curated allow-list of trusted ERC-20 contracts (similar to how `TrustBackedAssetsConvertedConcreteId` restricts by pallet instance) would also close the reachability of this path to arbitrary attacker-deployed contracts.

### Proof of Concept
Deployment evidence: no local execution was performed against this checkout (ask-only static review; per repository guidance, results are not claimed to have executed). A minimal integration reproduction would consist of:
1. Deploy a Solidity contract on Asset Hub's `pallet_revive` whose `transfer(address,uint256)` unconditionally returns `true` (ABI-encoded) and performs no storage mutation.
2. Submit `pallet_xcm::execute` with `Xcm::builder().withdraw_asset((AccountKey20{key: <malicious_addr>, network: None}, AMOUNT)).deposit_asset(AllCounted(1), beneficiary).build()`.
3. Assert the call succeeds (`Outcome::Complete`) and that `beneficiary`'s ERC-20 balance in `pallet_revive` storage did not actually change, while the XCM `AssetsInHolding`/deposit path reported success — demonstrating the fabricated-credit condition described above, following the exact non-checking code paths cited at `erc20_transactor.rs:166-216` and `erc20_transactor.rs:251-298`.

Failed guard: neither `withdraw_asset_with_surplus` nor `deposit_asset_with_surplus` calls `IERC20::balanceOf` before/after the `transfer` call to confirm the claimed `amount` actually moved — this is the "missing check" analogous to THORChain's failure to verify `depositAmount` versus `msg.value`.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}
