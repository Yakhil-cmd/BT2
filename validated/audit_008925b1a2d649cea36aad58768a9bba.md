## Title
Private‑payment‑chain replay bypasses re‑validation via unkeyed `handledChainsCache`, allowing acceptance of already‑double‑spent chains and sender spoofing - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` in [1](#0-0)  memoizes the *result* of validating a set of private‑payment chains in a single global, unkeyed cache `handledChainsCache`, keyed only by the content hash of the chains themselves (`objectHash.getBase64Hash(arrChains)`), completely independent of which peer/device sent them or when. On a cache hit the function skips **all** cryptographic/graph validation (`network.handleOnlinePrivatePayment`, double‑spend checks, output‑ownership checks) and unconditionally calls `callbacks.ifOk()` while emitting `all_private_payments_handled` for whatever `from_address` happened to be attached to *this* call. This is analogous to the LemonLDAP::NG session‑cache‑corruption bug (CVE‑2021‑35472): a shared cache entry that is not scoped to the originating identity/session is reused across unrelated requests, letting one caller "inherit" the previously‑computed authorization result of a different caller.

### Finding Description
The cache is declared at module scope and shared across every call to `handlePrivatePaymentChains`, for every peer/device that talks to this wallet instance: [2](#0-1) 

The cache key is derived purely from the *content* of the chains (`arrChains`), not from the sender (`from_address`), the connection (`ws`), nor any freshness/session token: [3](#0-2) 

On a cache hit, the function returns success immediately, bypassing:
- `network.handleOnlinePrivatePayment` (the actual unit/signature/graph validation loop), and
- `forwardPrivateChainsToOtherMembersOfSharedAddresses` / `forwardPrivateChainsToOtherMembersOfOutputAddresses`, and
- any check that the referenced outputs are still unspent/serial at the time of this specific request.

The first time a given `arrChains` payload is processed, each element is validated in `network.handleOnlinePrivatePayment`, and only after validation succeeds is `handledChainsCache[cache_key]` set: [4](#0-3) 

Since a light wallet does not re-run consensus validation itself (`validation.js` short‑circuits for light clients per [5](#0-4) ), it relies entirely on `network.handleOnlinePrivatePayment`/graph checks executed inside `handlePrivatePaymentChains` to determine whether the referenced output is a legitimate, unspent, serial ("good") output. Because the cache entry never expires the *validity* condition, only the *fact that it was validated once*, an attacker who has previously caused (or observed) a successful validation of a specific chain payload can:
1. Cause the referenced output to become spent/superseded elsewhere (e.g., by getting it consumed in a conflicting/double‑spend unit, or by the underlying unit's sequence flipping to `temp-bad`/`final-bad` after further units arrive — see `checkSerialAddressUse` in [6](#0-5) ), and then
2. Resend the byte‑for‑byte identical `arrChains` (same hash ⇒ same `cache_key`) from any device/hub connection, with an arbitrary `from_address`.

The wallet will accept it immediately without re‑checking sequence/serial state or output‑spent status, and will emit `all_private_payments_handled` and (through the caller's downstream handling) treat the private payment as valid/received, attributing it to whatever `from_address` was supplied on the replay — i.e., the “session” (validation outcome) computed for one context is silently reused/misattributed in a different context, exactly the class of bug described in CVE‑2021‑35472.

### Impact Explanation
This allows a wallet to be tricked into accepting a private payment that is no longer valid (output already spent/superseded) purely because an identical payload was validated once before, without re-verifying current output state, and to misattribute the payment to a spoofed `from_address`. That is a concrete instance of "accept an unconfirmed/double‑spent output as accepted," undermining the wallet’s trust in delivered private payments (fund‑crediting/UX state), and it does so without any special network/hub privilege — a single hub‑posted/forwarded message is enough to reach this code path (`handleMessageFromHub` → `handlePrivatePaymentChains`).

### Likelihood Explanation
Reachable by any unprivileged correspondent device or hub-relayed message that can send `private_payment_chains` to a wallet, requiring only that they replay a previously‑seen valid chain payload (which itself is not secret — it is exchanged in plaintext JSON between devices/hubs for the purpose of delivering private payments). No cryptographic break is required, only causing/observing one prior successful validation and a subsequent state change (e.g. a double spend) before replay.

### Recommendation
Do not use a purely content‑keyed, indefinite‑lifetime cache to skip full re‑validation of private payment chains. At minimum:
- Key the cache by `(cache_key, from_address)` or drop the from‑address bypass entirely (still re-emit the events but do not skip `network.handleOnlinePrivatePayment`/output‑serial checks) so a stale "already validated" result can't be replayed against different senders.
- Re‑validate current serial/spent status of the referenced outputs even on cache hit, or expire cache entries as soon as the underlying `sequence`/spent state of referenced units could have changed (e.g., invalidate on any subsequent conflicting unit touching those outputs), rather than solely on a 1‑hour timer.

### Proof of Concept
1. Device A sends a legitimate `private_payment_chains` message to Wallet W referencing output O; W validates it via `network.handleOnlinePrivatePayment`, accepts it, and caches `handledChainsCache[hash(arrChains)] = now`.
2. Output O is later spent in a conflicting unit elsewhere (double‑spend), or the unit's sequence becomes `temp-bad`/`final-bad`.
3. Attacker (any device, or Device A itself) resends the byte‑identical `arrChains` payload to W, with `from_address` set to any address (e.g., the attacker's own or a spoofed correspondent).
4. `handlePrivatePaymentChains` hits the cache at [7](#0-6) , skips all validation, calls `callbacks.ifOk()`, and emits `all_private_payments_handled` for the attacker‑supplied `from_address` — even though output O is no longer a valid, unspent, serial output.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
	try {
		var cache_key = objectHash.getBase64Hash(arrChains);
	}
	catch (e) {
		return callbacks.ifError("chains hash failed: " + e.toString());		
	}
	if (handledChainsCache[cache_key]) {
		eventBus.emit('all_private_payments_handled', from_address);
		eventBus.emit('all_private_payments_handled-' + arrChains[0][0].unit);
		return callbacks.ifOk();
	}
