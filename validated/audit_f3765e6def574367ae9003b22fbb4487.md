### Title
`CCMenuController` accepts any stack-scoped ApiClient token to read status of any stack, bypassing per-stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` resolution helper used by every other API controller, replacing the scope-checked lookup with an unscoped `Stack.from_param!`. This breaks the binding "the stack a token is authorized for" == "the stack the request actually touches", the exact class of bug described in the analog report (an entity that authorizes an action is checked, but a different entity that the action actually operates on is not verified against it).

### Finding Description
Every other `Shipit::Api::BaseController` subclass resolves the target stack through: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is stack-scoped (`stack_id?`), and only falls back to `Stack.all` for globally-scoped clients. This is the mechanism that binds "the stack(s) a token is authorized to touch" to "the stack the request resolves to."

`CCMenuController`, however, overrides `stack` directly instead of using `stacks.from_param!`: [2](#0-1) 
It also swaps the authentication method to accept a bare `params[:token]` (rather than Basic-Auth), which is how the CCMenu integration is meant to work over an unauthenticated GET. `require_permission :read, :stack` only checks that the client's `permissions` array contains `read:stack` — it never checks `current_api_client.stack_id` against the requested `stack_id`: [3](#0-2) 

Because `stack` is redefined to call `Stack.from_param!(params[:stack_id])` unconditionally, a valid `read:stack` token that was minted and scoped to Stack A (e.g. `stack_id` set to A, as created by `here_come_the_walrus` fixture, or any stack-scoped `ApiClient`) will successfully authenticate against `CCMenuController#show` for **any** `stack_id` in the URL, not just the stack it was scoped to. `ApiClient#check_permissions!` only validates the permission string `"read:stack"`, and the `stacks` scoping method (the only place that would have enforced `stack_id` equality) is never invoked in this controller.

### Impact Explanation
This crosses the "stack a token authorizes vs. stack it touches" trust boundary explicitly called out as in-scope. An `ApiClient` deliberately scoped to a single stack (used precisely so its holder/consumer — e.g. an embedded CI status badge URL — cannot see other stacks) can be replayed against `/ccmenu/*stack_id` for arbitrary other stacks, disclosing their deploy/task status, last build label, activity, and lock state (rendered in `shipit/ccmenu/project.xml.builder`). This is unauthorized cross-stack (cross-repository) read access to stack/task state — matching the High-severity category "unauthenticated/unauthorized read of stack state, task streams or deploy output" once a `read:stack`-scoped token for any single stack is held (the same class of credential the platform is designed to hand out per-stack, e.g. via `CCMenuUrlController`).

### Likelihood Explanation
Likelihood is high for anyone already holding one legitimate, narrowly-scoped `read:stack` CCMenu token (a token type specifically meant to be embedded/shared for one stack's status badge). No repository write access, session, or privileged account is needed beyond possessing that single narrowly-scoped token; the attacker only needs to change the `stack_id` in the URL path to enumerate/read other stacks' build status.

### Recommendation
Have `CCMenuController#stack` reuse the base `stacks` scoping helper (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient`'s `stack_id` is enforced identically to every other API endpoint.

### Proof of Concept
1. Create two stacks, A and B.
2. Mint (or use fixture `here_come_the_walrus`) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
3. Call `GET /ccmenu/<stack_A_param>?token=<token>` → succeeds (expected).
4. Call `GET /ccmenu/<stack_B_param>?token=<token>` → also succeeds and returns Stack B's build/deploy XML, even though the token's `stack_id` only authorizes Stack A, because `CCMenuController#stack` bypasses `BaseController#stacks`'s `current_api_client.stack_id` scoping check.
