### Title
Webhook signature verification authenticates a different payload field than the one used to select the target repository, allowing cross-repository forgery when any configured GitHub organization has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload by looking up the signing secret for the **organization** named in `repository.owner.login` (or `organization.login`), while the handler that actually acts on the payload resolves the **repository to write to** from an independent field, `repository.full_name`. These two fields are never cross-checked against each other, and `GithubApp#verify_webhook_signature` unconditionally bypasses signature checking when the resolved organization has no `webhook_secret` configured — a supported, non-privileged configuration state, not a secret an attacker must know.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using `repository_owner`: [2](#0-1) 

The signature check delegates to `GithubApp#verify_webhook_signature`: [3](#0-2) 
which returns `true` immediately — bypassing all cryptographic verification — whenever the resolved organization's `webhook_secret` is blank. Shipit's own example configuration documents `webhook_secret` as an optional, nilable per-organization field: [4](#0-3) 
so a multi-org deployment can legitimately have some organizations with a secret and others without one — this is not a "secret" the attacker needs to obtain, it's the absence of any check.

Meanwhile, the actual repository/stack acted upon by every webhook handler is resolved from a *different* JSON field, `repository.full_name`, in `Handler#stacks`/`#repository_name`: [5](#0-4) 

`PushHandler#process` then uses that resolved `stacks` scope to call `sync_github` with an attacker-supplied `expected_head_sha`: [6](#0-5) 

**The binding that is broken (as an equality):**
`organization_that_authenticated (payload.repository.owner.login, used to pick the HMAC secret) == repository_that_is_written (payload.repository.full_name, used by Handler#stacks to pick the target Stack)`

Before the attack: for genuine GitHub-delivered webhooks, these two fields always describe the same repository, because GitHub itself populates both consistently.

After the attack: an unprivileged attacker who can reach the mounted webhook endpoint crafts a raw POST body where `repository.owner.login` is set to any organization configured in the instance **without** a `webhook_secret` (bypassing `verify_webhook_signature` entirely, per the `return true unless webhook_secret` early exit), while `repository.full_name` is set to an arbitrary *other* organization's/repository's full name that has real Shipit stacks configured. No signature/secret of any kind is required for this crafted request, because the code path that would have checked one never executes.

### Impact Explanation
This lets an attacker with no credentials, no repository access, and no knowledge of any webhook secret drive Shipit's webhook handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers, etc.) against a repository/stack they do not control, purely by naming it in `repository.full_name` while satisfying the organization-based signature check using an unrelated, secret-less organization entry. This is a cross-repository write via an unauthenticated (for that specific target) webhook injection, matching the report's underlying bug class of "value verified" not matching "value acted upon."

### Likelihood Explanation
Requires only that the Shipit deployment has at least one configured GitHub organization without a `webhook_secret` set (a state explicitly supported and documented by the example config), and that the attacker can reach the mounted webhook route with a raw HTTP POST. No account, token, or repository access is needed.

### Recommendation
When resolving the target for a webhook handler, cross-validate that the organization used to select/verify the signing secret (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` before using it to locate a `Stack`. Additionally, avoid the blanket signature bypass in `GithubApp#verify_webhook_signature` for organizations lacking a `webhook_secret` — either require a secret for all configured organizations or reject/flag webhooks for repositories outside the un-secured organization's own namespace.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-a` (no `webhook_secret`) and `org-b` (has stacks/repositories registered).
2. POST to the mounted webhook endpoint with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and `verify_webhook_signature` returns `true` unconditionally because `org-a` has no `webhook_secret` — no `X-Hub-Signature` header is even required to pass.
4. `PushHandler#process` resolves `repository_name = "org-b/victim-repo"` via `Handler#repository_name`, finds the real stacks for `org-b/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")`, letting the unauthenticated attacker influence sync/deploy state of a repository they never proved control over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
