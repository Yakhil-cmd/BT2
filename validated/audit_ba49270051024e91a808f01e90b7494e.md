### Title
Signature verification keyed on `repository.owner.login` while every `pull_request` handler mutates the repository/stack resolved from `repository.full_name` — cross-tenant webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the org/HMAC secret to validate a webhook against using `repository.owner.login`, while every `pull_request` handler (including `LabelCapturingHandler`) resolves the actual `Repository`/`ReviewStack` it mutates using the completely independent `repository.full_name` field. Because `GitHubApp#verify_webhook_signature` returns `true` when the selected org has no `webhook_secret` configured, an attacker can pick an org with no secret for `repository.owner.login` to trivially pass verification while pointing `repository.full_name` at any other tracked repository, letting the payload mutate a victim stack it never authenticated against.

### Finding Description
The broken binding: the code implicitly assumes `params.dig('repository','owner','login') == owner_of(params.repository.full_name)`, but nothing enforces this equality.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to select the GitHub App/secret: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when that org has no configured secret: `return true unless webhook_secret` [3](#0-2) .
- Every downstream `pull_request` handler, including `LabelCapturingHandler`, resolves the repository/stack it operates on from a *different* field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , and then persists attacker-controlled label names onto that stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [5](#0-4) .
- `ReviewStack#env` later folds those stored labels, uppercased, straight into the stack's execution environment: `.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [6](#0-5) .

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, a body with `action: "unlabeled"`, `repository.owner.login` set to an org configured in `secrets.github` with no `webhook_secret` (so `verify_webhook_signature` returns `true` for any/garbage signature), and `repository.full_name` set to the victim org/repo whose `review_stacks_enabled` is `true` and provisioning behavior `allow_all`. `drop_unhandled_event`/`check_if_ping` do not block this, `verify_signature` passes (since it never checks the org that owns `full_name`), and `LabelCapturingHandler#process` resolves `repository` from `full_name`, finds/creates the review stack via `ReviewStackAdapter`, and overwrites `PullRequest#labels` on that stack. Because `provisioning_behavior_allow_all` auto-provisions review stacks for any PR against that repo and `ReviewStack#env` injects the (now attacker-controlled) label names as environment variables, this compromises the environment under which `shipit.yml`-driven tasks execute for the victim stack.

Existing guards do not prevent this: `verify_signature` never cross-checks `repository.owner.login` against the owner segment of `repository.full_name`; `ExplicitParameters` only validates types/presence, not cross-field consistency [7](#0-6) ; and `Repository.from_github_repo_name` simply looks up whatever repo `full_name` names, with no relation to the org that authenticated the request.

### Impact Explanation
An attacker who can only control a repository in an unrelated, no-secret-configured GitHub org can forge webhook events that write to another tenant's review-stack `PullRequest` records, and — because `ReviewStack#env` promotes label names into environment variables consumed at task execution — influence the environment `shipit.yml` commands run under for that victim's auto-provisioned review stack. This is a payload from one repository/org mutating another's stack state without possessing that stack's webhook secret, matching the "payload for one repository mutating another's stack" Critical category. Impact is repeatable against any repository/org tracked by the same Shipit instance, as long as one org in the multi-tenant `secrets.github` config lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (`secrets.github` keyed by organization) where at least one configured org has no `webhook_secret` set, and (2) a victim repository/stack with `review_stacks_enabled: true` and `provisioning_behavior_allow_all` (so PRs from anyone auto-provision executing stacks). Given these two preconditions — which the question stipulates as given — the attacker's cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub credentials, Shipit session, or API token are needed. This is trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, derive the signing org strictly from the same field the handlers use to resolve the target repository (`repository.full_name`'s owner segment), or better, verify that `repository.owner.login` and `repository.full_name`'s owner segment match before proceeding; reject the request otherwise. Additionally, do not treat a missing `webhook_secret` as "verification passed" — require every configured org to have a secret, or refuse to process webhooks for orgs without one.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.stubs(:github)` such that `Shipit.github(organization: 'no-secret-org')` returns a `GitHubApp` with `webhook_secret` nil (so `verify_webhook_signature` always returns `true`), and a separate `Shipit.github(organization: 'victim-org')` with a real secret that would reject the forged signature.
2. Create a victim `Shipit::Repository` (`victim-org/victim-repo`) with `review_stacks_enabled: true`, `provisioning_behavior: :allow_all`, and an existing `ReviewStack` with a `PullRequest`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and a JSON body: `{"action":"unlabeled","number":<pr>,"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"}, "pull_request": {..., "labels":[{"name":"malicious-flag"}]}, "sender": {"login":"attacker"}}`.
4. Assert `response.status == 200` (bypassed verification) AND assert the victim stack's `pull_request.reload.labels` now equals `["malicious-flag"]` — i.e., `repository.owner.login` ("no-secret-org") authenticated a write to a stack owned by `"victim-org"`, proving the equality `authenticating_org == owner_of(full_name)` does not hold and was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
