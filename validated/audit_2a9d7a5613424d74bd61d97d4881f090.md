### Title
Deterministic, creator-independent `pool_state` PDA lets an attacker front-run `initialize`/`initialize_with_permission` to permanently steal the pool-creator role - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
The Dinari report's root cause is that an off-chain/on-chain identifier (`orderId`) was derived without binding it to the requester, letting an attacker front-run a legitimate request with the same identifier and cheaply grief the honest party. Raydium-cp-swap has the analogous pattern in pool creation: the `pool_state` PDA is derived only from `amm_config`, `token_0_mint`, and `token_1_mint` — never from the transaction sender — so the first `initialize` (or `initialize_with_permission`) call to land for a given (config, mint0, mint1) tuple permanently and irrevocably becomes "the" pool, and its signer becomes the immutable `pool_creator`.

### Finding Description
`Initialize::pool_state` and the vault/lp-mint/observation PDAs are derived purely from public, attacker-known inputs: [1](#0-0) 

`create_pool` only checks that the target account is system-owned/uninitialized before allocating it at the expected PDA (or requires a co-signed random keypair) — it does not check who the signer/creator is, and once initialized the PDA can never be reused: [2](#0-1) 

`PoolState::initialize` then records the transaction's `creator` signer as the permanent `pool_creator`, along with the initial reserve ratio supplied in that same transaction: [3](#0-2) [4](#0-3) 

Because the PDA seeds omit the creator/sender, a malicious actor watching the mempool for a pending `initialize`/`initialize_with_permission` call for a specific token pair can submit their own `initialize` instruction for the same `amm_config`/`token_0_mint`/`token_1_mint` with higher priority fee, using their own token accounts and an arbitrary (even minimal, 1-lamport-scale) `init_amount_0`/`init_amount_1` that only needs to pass `CurveCalculator::validate_supply` and the `lock_lp_amount` (100) subtraction check: [5](#0-4) 

Once the attacker's transaction lands first, the legitimate creator's transaction fails (the `pool_state`, `lp_mint`, vault, and `observation_state` PDAs are already initialized), and the attacker is now permanently recorded as `pool_creator` — the sole address authorized to withdraw accumulated creator fees via `CollectCreatorFee`/`CollectCreatorFeePermissionless`: [6](#0-5) [7](#0-6) 

Since a given (`amm_config`, `token_0_mint`, `token_1_mint`) tuple can never be re-initialized, this is a permanent, one-shot griefing/theft primitive — exactly analogous to the Dinari `orderId` collision bug: an identifier/PDA that should be unique per-requester is instead globally deterministic and public, so it can be claimed first by an unrelated attacker at negligible cost.

### Impact Explanation
This grants the attacker an unauthorized privileged effect that is otherwise reserved for the legitimate pool creator:
- Permanent, exclusive right to collect all future `creator_fees_token_0`/`creator_fees_token_1` accrued on that pool (an ongoing value stream taken from LPs/traders who use the resulting pool).
- Control over the initial reserve ratio and liquidity amount for the pair (the attacker can seed a heavily skewed or dust-level ratio), degrading the pool's usability/pricing for anyone who still uses it.
- Permanent denial of service against the legitimate project/team that wanted to create the "real" pool for that config+mint pair, since the PDA slot is consumed forever (`create_pool` rejects re-initialization of an already-owned account).

This satisfies the "unauthorized privileged effect" acceptance criterion (permanent misappropriation of the `pool_creator` role and its fee stream) without requiring any elevated privileges from the attacker — a single transaction with attacker-chosen accounts and data (their own token accounts, mints already existing) is sufficient.

### Likelihood Explanation
Pool creation transactions are public in the mempool prior to confirmation, and the accounts/PDAs needed to construct a competing `initialize` instruction are fully derivable from the mints alone (no secret salt, no requester binding). Any bot that watches for `Initialize`/`InitializeWithPermission` instructions targeting new token mints can trivially compute the same PDAs and outbid with a higher priority fee. The cost is only the dust-level initial liquidity (bounded above `lock_lp_amount = 100`) plus gas/fees, i.e., cheap and repeatable, similar in spirit to the "cancel and pay nothing" strategy described in the Dinari report.

### Recommendation
- Bind the deterministic pool PDA (and/or an explicit "reservation" step) to the calling `creator`/`payer`, or require an additional attacker-unpredictable component (e.g., a creator-chosen salt or the creator's pubkey) in the `POOL_SEED` derivation so that different creators cannot collide on the same PDA for a given mint pair.
- Alternatively, gate permissionless `initialize` behind a commit-reveal or allow only the mint's designated authority/first depositor of record (verified via an on-chain reservation created before pool bytes are finalized) to become `pool_creator`.
- At minimum, allow governance/admin to reassign or dispute `pool_creator` when a pool is created with abnormal/dust reserves shortly after mint creation, or require a minimum initial liquidity value tied to `token_0_mint`/`token_1_mint` decimals to raise the cost of griefing.

### Proof of Concept
1. Attacker monitors the mempool/RPC for a pending `Initialize` instruction referencing `token_0_mint = M0`, `token_1_mint = M1` for a specific `amm_config`.
2. Attacker computes the same PDAs client-side, exactly as done in `initialize_pool_instr`: [8](#0-7) 
3. Attacker submits their own `Initialize` instruction (or `InitializeWithPermission` if permissioned config) using their own `creator_token_0`/`creator_token_1` accounts, minimal `init_amount_0`/`init_amount_1` (just above `lock_lp_amount = 100` liquidity floor), and a higher compute/priority fee than the victim's transaction.
4. Attacker's transaction lands first, calling `create_pool` which allocates the deterministic `pool_state` PDA and `PoolState::initialize` records the attacker as `pool_creator`.
5. Victim's original `initialize` transaction fails because `pool_state`/`lp_mint`/vault/`observation_state` PDAs already exist (`create_pool`'s `pool_account_info.owner != system_program::ID` check fails).
6. Attacker is now permanently entitled to call `collect_creator_fee`/`collect_creator_fee_permissionless` for all trading activity that subsequently occurs on that pool, while the legitimate project can never create their intended pool for that mint pair under that `amm_config`.

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

    token::create_or_allocate_account(
        &crate::id(),
        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;
