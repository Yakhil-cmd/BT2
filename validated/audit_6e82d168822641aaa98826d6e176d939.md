### Title
Unauthenticated Webhook Injection When `webhook_secret` Is Unconfigured Forges Commit Statuses And Triggers Deploy Pipeline - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever no `webhook_secret` is configured for an organization, meaning `WebhooksController#verify_signature` performs no authentication at all in that mode, exactly mirroring the reported pattern where `permitSigner == address(0)` collapses all signature checks to a no-op.

### Finding Description
`GitHubApp#verify_webhook_signature` is the sole gate protecting `POST /webhooks`: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is read directly from the `github` config block and is explicitly optional/nil-able in every documented and shipped configuration example: [2](#0-1) [3](#0-2) [4](#0-3) 

The controller trusts this return value as the entire authentication boundary and never inspects a fallback secret, an IP allowlist, or any other credential: [5](#0-4) 

This is structurally identical to the analog's binding break: the "signer authenticated" side of the equality (`recovered == permitSigner_`, or here `hmac(webhook_secret, body) == X-Hub-Signature`) is supposed to equal the "signer trusted by the app" side, but when the configured secret is absent, the check degenerates to `true == true` unconditionally — `verified_signer == none-required`, so **any unauthenticated caller becomes equivalent to "the real GitHub App"** for webhook delivery purposes. There is no analog of "empty signature required" (as in the Solidity report's `require(signature.length == 0)`) — an attacker doesn't even need to omit a header, they can send any signature value or none, since the branch short-circuits before ever inspecting it.

### Impact Explanation
With `webhook_secret` unset (a supported, common, and documented configuration — the shipped `config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, and `docs/setup.md` all present it as optional/commented out), an unauthenticated network attacker who can reach `/webhooks` can:

- Forge `push` events to force `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: ...)` for arbitrary branches/stacks: [6](#0-5) 
- Forge `status` events to fabricate arbitrary commit statuses via `Commit#create_status_from_github!`, injecting fake CI "success" states on real commits: [7](#0-6) 

Because Shipit stacks commonly gate deploys/merges on commit status checks, forging success statuses can enable an unauthorized deploy to proceed against a commit that never actually passed CI — directly crossing into "unauthorized deploy" territory named in the impact list. This requires no GitHub credential, no Shipit session, and no repository write access — only network reachability to the public `/webhooks` endpoint, matching the unprivileged-attacker threat model of the analog.

### Likelihood Explanation
Medium-to-High: the vulnerable configuration (`webhook_secret` blank) is not a misuse of the engine — it is the shipped default in every example/config file in this repo (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`, `test/dummy/config/secrets_double_github_app.yml`), and `docs/setup.md` explicitly labels the webhook secret as "(optional)". Any operator who follows the documented quick-start without adding a webhook secret is exposed, and the `/webhooks` route requires no authentication to reach.

### Recommendation
Require `webhook_secret` to be present for any configured GitHub organization and fail closed (reject the request, or refuse to boot) when it is missing, instead of returning `true`:

```ruby
def verify_webhook_signature(signature, message)
  return false if webhook_secret.blank?

  algorithm, signature = signature.to_s.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```
Additionally, update `docs/setup.md` and the shipped example secrets files to mark `webhook_secret` as required rather than optional.

### Proof of Concept
1. Deploy Shipit with a `github` config block that omits `webhook_secret` (as the shipped `config/secrets.development.example.yml` and `docs/setup.md` both suggest is acceptable).
2. As an unauthenticated attacker, send:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{"sha":"<target commit sha>","state":"success","context":"ci/tests","repository":{"owner":{"login":"<victim-org>"}}}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "<victim-org>").verify_webhook_signature(nil_or_garbage, raw_body)`, which returns `true` because `webhook_secret` is `nil` — see [8](#0-7) .
4. `StatusHandler#process` runs unauthenticated and writes a forged "success" status on the target commit: [7](#0-6) , which can unblock deploy/merge gating that depends on commit status checks.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
