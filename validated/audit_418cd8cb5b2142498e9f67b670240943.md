Confirmed: `objValidationState.bNoReferences` is checked individually per-opcode in `Definition.validateDefinition`, but the `formula` case does **not** check it before recursively validating an embedded oscript formula, and that embedded formula is allowed to contain `data_feed`/`in_data_feed`/`attested`-style reference lookups, transitively pulling in exactly the "reference" data that `bNoReferences` was meant to forbid.

### Title
Improper Enforcement of `bNoReferences` on Transitive Formula Sub-Expressions in Address/Asset Definitions - (File: definition.js)

### Summary
`Definition.validateDefinition()` (definition.js) enforces `objValidationState.bNoReferences` on primitive opcodes that pull in chain-state data (`address`, `definition template`, `in data feed`, `in merkle`, `has`, `has one`, `seen`, `has equal`, `has one equal`, `sum` — see the explicit `if (objValidationState.bNoReferences) return cb("no references allowed in address definition");` guards at lines 270-271, 308-309, 402-403, 448-449, 500-501, 524-525, 566-567). The `formula` case (lines 594-614) is missing this same guard: it only checks `formulaUpgradeMci` and string length before delegating to `formulaParser.validate()` with `bAssetCondition` passed through but no propagation of `bNoReferences`. Inside an oscript `formula`, expressions such as `data_feed[[...]]`, `in_data_feed[[...]]`, and other stateful lookups are fully allowed by `formula/validation.js` (see `validateDataFeed`/`validateDataFeedExists`, lines 26-129), so a definition/condition that is supposed to have "no references" can still transitively obtain externally-controlled data via a nested `['formula', "data_feed[[...]]==..."]` sub-expression.

### Finding Description
`bNoReferences` is a validation-state flag that callers set when a definition must be resolvable without consulting external, unit-order-dependent data (references to data feeds, other addresses, definition templates, attestations, etc.). Every direct reference-bearing opcode in `validateDefinition` is individually gated behind this flag. However, the `formula` opcode bypasses this gate entirely and hands control to the independent oscript formula validator/evaluator, which supports the very same reference primitives (`data_feed`, `in_data_feed`, `var`, `balance`, `asset`, etc., see formula/evaluation.js and formula/validation.js). Because the `formula` case does not forward or check `bNoReferences`, wrapping a reference lookup inside `['formula', "..."]` sidesteps the restriction that the direct-opcode form enforces, exactly mirroring the Apollo Federation flaw where dependent/derived fields (reached indirectly, here via a nested formula rather than a directly-listed opcode) do not inherit the access/reference restrictions imposed on the fields/opcodes they are built from.

### Impact Explanation
Wherever `bNoReferences` is required for correctness (definitions that must not depend on data-feed/attestation state, e.g., contexts requiring deterministic, reference-free evaluation), an attacker-crafted definition can smuggle in a `formula` sub-expression that reads `data_feed`/`in_data_feed` values, reintroducing exactly the non-determinism/attacker-influenced-data class that the flag exists to block. Since these definitions gate spending/authentication conditions, this can let an attacker make a definition's satisfiability depend on oracle-controlled or self-posted data feed values in a context where that was explicitly disallowed, undermining the guarantees the caller relied on (e.g., allowing conditional/oracle-influenced authorization in a path meant to be reference-free), which can enable unauthorized spending or authentication bypass depending on the caller context.

### Likelihood Explanation
Medium-High reachability: any unprivileged unit poster who can submit an address/asset definition (or any structure validated via `validateDefinition`/`validateAuthentifiers` with `bNoReferences` set) can trivially wrap a `data_feed`/`in_data_feed` lookup inside a `['formula', ...]` node, since `formula` is a documented, generally-permitted opcode and no additional privilege is needed to trigger the code path — the bug is a straightforward missing-guard, not requiring precise timing or race conditions.

### Recommendation
Add the same `if (objValidationState.bNoReferences) return cb("no references allowed in address definition");` guard to the `formula` case in `Definition.validateDefinition()` (definition.js, before line 594's logic proceeds), and additionally propagate `bNoReferences` (or an equivalent flag) into the `formulaParser.validate()` options so that `data_feed`, `in_data_feed`, `var`, `balance`, `attestation`, `input`/`output` and any other reference-bearing opcodes are rejected inside formulas evaluated under a no-references context. Audit `formula/validation.js` to ensure all reference-capable opcodes there respect this propagated flag.

### Proof of Concept
1. Identify a call site that invokes `Definition.validateDefinition(conn, arrDefinition, objUnit, objValidationState, arrAuthentifierPaths, bAssetCondition, cb)` with `objValidationState.bNoReferences = true`.
2. Submit a definition/condition such as:
   `['formula', "data_feed[[oracles='ORACLE_ADDRESS', feed_name='x']] == 1"]`
3. Observe that `validateDefinition`'s `formula` case (definition.js lines 594-614) does not check `bNoReferences` and delegates straight to `formulaParser.validate`, which accepts the `data_feed` reference (formula/validation.js `validateDataFeed`), whereas the equivalent direct opcode `['in data feed', [...]]` at the same nesting level is correctly rejected with `"no references allowed in address definition"` (definition.js lines 402-403).
4. This demonstrates the definition can obtain reference-bearing data despite `bNoReferences` being set, confirming the inconsistent/transitive enforcement.
