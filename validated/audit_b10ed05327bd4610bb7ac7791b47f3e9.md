### Title
Rounding Distribution of Payload Commission Among Multiple Paid Witnesses Causes Byte Supply Inflation - ([File: paid_witnessing.js])

### Summary
`buildPaidWitnessesForMainChainIndex` in `paid_witnessing.js` splits a stable unit's `payload_commission` equally among all witnesses who are entitled to it, using `Math.round()` independently for each witness rather than rounding down and tracking the remainder. Because every witness receives the *same* rounded fraction, rounding errors are not offsetting but systematic: whenever `payload_commission / count_paid_witnesses` has a fractional part `>= 0.5`, **every** witness's share is rounded up, so the sum distributed exceeds the actual `payload_commission` collected from the paying unit. This is the same bug class as the reported `mulDivRoundingUp` issue — reward/commission index inflation from rounding — except that here it manifests as new "byte" supply being created rather than an underflow revert, since there is no invariant anywhere that checks that `SUM(witnessing_outputs.amount)` for a unit equals its `payload_commission`.

### Finding Description
In `paid_witnessing.js`, once the paying witnesses for a unit are determined, earnings are computed two ways (in-memory `bFaster` path and SQL path), both using rounding on a per-witness basis: [1](#0-0) 

and the equivalent SQL: [2](#0-1) 

`count_paid_witnesses` is the same divisor applied to every witness of a given unit, and `Math.round()` rounds half away from zero. Since **all** witnesses of the unit divide the exact same `payload_commission`, if `payload_commission / count_paid_witnesses` has a fractional part `>= 0.5`, every single witness receives the rounded-up value, so:

```
distributed_total = count_paid_witnesses * round(payload_commission / count_paid_witnesses)
```//
which can exceed `payload_commission` by nearly `count_paid_witnesses / 2` bytes for a single unit. This differs qualitatively from ordinary rounding (which would offset errors across recipients) because the divisor and dividend are identical for every recipient — the bias never cancels out.

These rounded amounts are inserted directly into `witnessing_outputs`, a first-class ledger table: [3](#0-2) 

and later become fully spendable via a `witnessing` payment input, validated in `validation.js` by simply summing `witnessing_outputs.amount` for the requested MCI range with no cross-check against the unit's original `payload_commission`: [4](#0-3) [5](#0-4) 

There is no invariant in the codebase (checked in `balances.js`, `validation.js`, or `paid_witnessing.js` itself) enforcing that the sum of `witnessing_outputs` (or `headers_commission_outputs`, which has an analogous per-recipient `Math.round()` split in `headers_commission.js`) for a paying unit equals the fee actually deducted from the payer when the unit was composed (`objUnit.payload_commission` is simply subtracted from the payer's change in `composer.js` — it isn't tied by any check to the sum eventually paid out to witnesses).

### Impact Explanation
Because the rounding bias is systematic (same divisor/dividend applied to every witness), it is not a negligible, self-cancelling rounding error — it can create new spendable bytes that were never actually removed from any payer's balance. This is repeated on **every stable MC unit**, continuously, across the life of the network, so the aggregate effect compounds over time into a real, though gradual, byte-supply inflation vector — a concrete instance of the "supply inflation" impact category. Any full node deterministically computes the same (inflated) `witnessing_outputs`/`headers_commission_outputs`, so nodes will not disagree on validity, but the DAG's total money supply silently grows beyond `constants.TOTAL_WHITEBYTES` issued at genesis.

### Likelihood Explanation
Likelihood is Medium: it requires no attacker action at all — it triggers automatically whenever a unit's `payload_commission` does not divide evenly among the number of `count_paid_witnesses`, and this condition is common in ordinary network operation (`payload_commission` sizes are essentially arbitrary integers, and `count_paid_witnesses` is typically 1–12). No special unit crafting is even required to trigger the bias, though a poster wishing to *maximize* it could deliberately author units whose `payload_commission` produces a `>=0.5` fractional remainder when divided by the current witness count (which is public information from the current witness list) to compound the systematic bias in their favor over time (as an author is often among the witnesses that get paid, or can direct the winning child via `getWinnerInfo`/best-child selection logic).

### Recommendation
Do not round each witness's share independently. Instead, allocate `payload_commission` using integer division (`Math.floor(payload_commission / count_paid_witnesses)`) and distribute the remainder (`payload_commission % count_paid_witnesses`) deterministically to a subset of witnesses (e.g., sorted by address) so the total distributed exactly equals `payload_commission`. Apply the same fix to the analogous `Math.round(full_amount * share / 100.0)` logic in `headers_commission.js` used to split `earned_headers_commission_recipients`, ensuring the sum of all recipients' rounded shares never exceeds the unit's actual `headers_commission`.

### Proof of Concept
Conceptual trace (deterministic, requires no adversarial unit, only ordinary network conditions):
1. A stable MC unit has `payload_commission = 101` and is witnessed by exactly `count_paid_witnesses = 3` addresses (verified via `graph.readDescendantUnitsByAuthorsBeforeMcIndex`).
2. `buildPaidWitnesses` (paid_witnessing.js, lines 222–287) inserts 3 rows into `paid_witness_events_tmp` for this unit.
3. `updatePaidWitnesses`'s aggregation step computes, for each of the 3 witnesses: `Math.round(101 / 3) = Math.round(33.67) = 34`.
4. Total inserted into `witnessing_outputs` for this unit = `34 * 3 = 102`, i.e., 1 byte more than the `payload_commission` (101) that was ever deducted from the unit's author when it was composed.
5. Each of the 3 witnesses can later spend their 34-byte share via a `witnessing` input, validated only by `mc_outputs.calcEarnings`/`paid_witnessing.calcWitnessEarnings` summing `witnessing_outputs.amount` — with no check anywhere against the original `payload_commission`.
6. Repeated across every stable unit on the DAG whose `payload_commission % count_paid_witnesses >= count_paid_witnesses/2`, this steadily inflates total spendable bytes beyond `constants.TOTAL_WHITEBYTES`. [6](#0-5)
