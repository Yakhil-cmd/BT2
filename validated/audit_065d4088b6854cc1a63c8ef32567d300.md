### Title
Use of Broken/Risky Cryptographic Algorithms (Weak Elliptic Curves) in `is_valid_sig` Oscript Function - (File: signature.js)

### Summary
The `is_valid_sig(message, pem_key, signature)` Oscript function, reachable from any AA definition or trigger evaluation, accepts PEM-encoded public keys using cryptographically broken or extremely weak elliptic curves (e.g. `secp112r1`, `secp112r2`, `secp128r1`, `secp128r2`) with no minimum-strength restriction, mirroring the CWE-327 "broken or risky cryptographic algorithm" class from the referenced advisory.

### Finding Description
`validateAndFormatPemPubKey()` in [1](#0-0)  only checks the DER structure (SEQUENCE tags, identifier length, base64 validity, overall size) but performs no allow-list/minimum bit-length check on the OID of the named curve. Any curve whose OID-length matches 13/16/19/20 bytes is accepted, and `verifyMessageWithPemPubKey` in [2](#0-1)  then dispatches to Node's generic `crypto.createVerify('SHA256')` (or the dedicated secp256k1 fast-path) to check the signature — for any accepted curve, including 112‑bit and 128‑bit curves that are known-broken (ECDLP is feasible with modest compute for ≤128-bit curves, and considered actively at-risk even at ~160 bits).

This is directly reachable from Oscript evaluated in AA logic via the `is_valid_sig` case in the formula evaluator, which only validates that the message/signature are well-formed strings and delegates curve-strength checks entirely to `signature.validateAndFormatPemPubKey()`: [3](#0-2) . This is confirmed by the test suite explicitly demonstrating successful verification with weak curves such as `secp112r1`, `secp112r2`, `secp128r1`, and `secp128r2`: [4](#0-3) [5](#0-4) [6](#0-5) .

If an AA author writes a spending/release condition of the form `is_valid_sig(some_message, stored_pem_pubkey, trigger.data.signature)` intending strong authentication (a common oscript pattern for external attestation/oracle or multi-chain bridging use cases, as seen in sample contracts `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript`), and the associated private key was generated on one of these weak curves (whether by design, misconfiguration, or because the curve choice is attacker-influenced when the AA accepts an externally supplied `pem_key` as trigger data), an attacker can feasibly recover the private key from the public key via ECDLP solvers for curves of ≤128 bits, then forge arbitrary signatures satisfying the condition.

### Impact Explanation
Where an AA's spending or release logic is gated by `is_valid_sig` against a weak-curve key (directly, or because the AA trusts a `pem_key` supplied by a counterparty/oracle in `trigger.data`), an attacker who breaks the curve's discrete log can forge signatures and satisfy the condition without holding the legitimate private key, resulting in unauthorized withdrawal of AA-held funds (AA fund loss). This is a direct violation of the intended cryptographic guarantee the AA author relies on.

### Likelihood Explanation
Exploitation is not automatic — it requires an AA (or, in the arbiter/payment-channel patterns, an off-chain agreement) to actually use `is_valid_sig` with a weak curve key as a security-critical release condition. However, the vulnerability is systemic: the platform imposes no curve-strength policy, silently accepts and *positively verifies* weak-curve signatures (tests assert `true` results for 112–128-bit curves), and nothing in oscript's validation layer (`formula/validation.js`) rejects these curves at AA-definition time either. An AA author (or a malicious counterpart supplying a "trusted" pubkey to an unwary AA author) can trivially choose or induce use of a weak curve, and the resulting condition will validate as intended until exploited.

### Recommendation
Enforce a minimum-security curve/key allow-list in `signature.validateAndFormatPemPubKey()` (e.g., reject curves below 224–256 bits of security, explicitly reject known-broken/deprecated named curves such as `secp112r1/r2`, `secp128r1/r2`, `sect113r1/r2`, wtls curves, etc.), and consider deterministically failing closed at parse time rather than delegating strength checks to `crypto.createVerify`, which has no concept of "acceptable" versus "weak" curves.

### Proof of Concept
Using the existing test harness, `is_valid_sig(message, pem_key, signature)` returns `true` for a `secp112r1` key/signature pair: [4](#0-3) . An attacker who can solve ECDLP over this ~112-bit curve (well within reach of modern hardware/cloud compute) recovers the private key from the public `pem_key`, then forges a signature over any `message`/trigger content, causing `is_valid_sig` to return `true` in an AA condition that relies on it for fund-release authorization.

Note: I could not verify from the index which, if any, of the bundled `test/samples/*.oscript` AA templates ship to production with `is_valid_sig` as a funds-controlling condition using externally-configurable pem keys; that would need direct verification of deployed AA definitions to establish concrete real-world AA exposure of this pattern.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
