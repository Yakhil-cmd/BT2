### Title
Arbitrary wallet token theft through a poisoned swap authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A crafted `swap_collateral` route can place attacker-controlled contract code beneath the victim’s authorized controller invocation. If the victim signs the authorization tree produced by simulation, that code can add a child `token.transfer(victim, attacker, amount)` and steal unrelated wallet tokens while the swap itself remains valid. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authorizes `caller`, permits only the account owner or delegate, and passes the caller-controlled `swap` payload into the router. [3](#0-2) [1](#0-0) 

The controller authorizes only the controller’s exact `token_in.transfer(controller, router, amount_in)` invocation and checks controller balance deltas afterward. [4](#0-3) [5](#0-4) 

Those checks do not prevent the router from invoking a route-selected pool address while the victim’s root authorization remains active. The route’s `assets` registry supplies pool addresses, and each swap instruction dispatches the selected pool to a venue adapter. [6](#0-5) [7](#0-6) [8](#0-7) 

A malicious venue contract can call `token.transfer(victim, attacker, victim_balance)`. Because the token invokes `victim.require_auth()`, the host attaches that transfer as a child of the victim’s `swap_collateral` authorization; simulation records the child, and enforced authorization executes it when the victim signs the poisoned tree. [9](#0-8) [10](#0-9) 

### Impact Explanation
The attacker can drain tokens held directly by the victim, including assets unrelated to the lending account and not supplied as collateral. The loss is bounded only by balances and authorization entries included in the signed tree, not by `amount_in`, minimum output, account health, or the controller’s router-output checks. [11](#0-10) [12](#0-11) 

This is theft of user funds and can be Critical where the victim’s wallet holds material balances. [10](#0-9) 

### Likelihood Explanation
Likelihood is Medium: exploitation requires convincing the victim to sign a transaction whose simulated authorization tree contains the malicious child transfer. No privileged role, leaked key, protocol upgrade, oracle manipulation, or pre-existing token allowance is required; an unprivileged attacker can deploy the hostile route contract and craft the route. [13](#0-12) [10](#0-9) 

The repository’s threat model explicitly recognizes that route-selected code can add a token transfer beneath the caller’s authorization and that clients must reject authorization trees with unexpected children. [14](#0-13) 

### Recommendation
Enforce authorization-tree validation in every wallet, SDK, keeper, and frontend path that submits routed strategies. Reject a signed `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position`, or `migrate_from_blend` authorization whenever simulation reports any child invocation other than the expected protocol token transfers, and display every child contract, function, source, destination, and amount before signing. [14](#0-13) 

Where feasible, restrict route venue contracts to governance-reviewed addresses or route through an authorization-isolating venue adapter that cannot reach user-controlled token authorization. At minimum, make the strict auth-tree check part of transaction generation rather than documentation. [7](#0-6) [8](#0-7) 

### Proof of Concept
1. Victim holds an unrelated token and a valid lending account.
2. Attacker deploys a contract implementing the selected venue’s swap ABI. Its swap implementation also calls `token.transfer(victim, attacker, victim_balance)`.
3. Attacker crafts a `swap_collateral` transaction whose `swap` payload routes through that contract.
4. Simulation executes the malicious contract and records `token.transfer(victim, attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization.
5. The victim signs the poisoned authorization tree.
6. The malicious child transfer succeeds, the swap can still satisfy measured output and final account checks, and the attacker receives the unrelated wallet tokens.

The regression test demonstrates the full sequence: recording mode attaches the rogue transfer to the victim’s controller authorization, an honest root-only tree rejects it, and the poisoned signed tree transfers the victim’s entire `WALLET_BALANCE` to the attacker while crediting the expected swap output. [9](#0-8) [15](#0-14)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
