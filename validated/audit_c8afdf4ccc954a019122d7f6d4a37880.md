### Title
Cross-tenant `Team` membership removal via unvalidated `team.id`/`organization.login` binding in `membership` webhook `'removed'` action - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` looks up the `Team` solely by `params.team.id` (`find_or_create_team!`) and, for `action == 'removed'`, calls `team.members.delete(member)` without ever checking that the org which signed the webhook (`params.organization.login`, used by `WebhooksController#verify_signature`) actually owns that `Team`. Any org configured in Shipit can therefore forge a `membership`/`removed` event naming another org's `github_teams`-mapped `team.id` and remove an arbitrary, publicly-known user from that team, stripping their `authorized?` status.

### Finding Description
Broken binding, stated as an equality that the code fails to enforce:
`org(payload) := Shipit.github(organization: repository_owner).verify_webhook_signature(...)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb` lines 24-30, 59-62), **should equal** `team.organization` for the `Team` fetched in `find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb` lines 38-43). For `membership` events there is no `repository` key, so `repository_owner == params.organization.login` — the same field used inside the handler.

The handler code:
```
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  when 'removed'
    team.members.delete(member)   # <-- no org check
  ...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login   # only set on first create
  end
end
```
`find_or_create_by!(github_id: params.team.id)` matches an **existing** `Team` row purely by `github_id`, ignoring `params.organization.login` entirely once the team already exists. `verify_signature` only proves the request was signed by *some* org configured in Shipit (via that org's `webhook_secret`); it never checks that this org is the one that owns the `Team` row keyed by `github_id`. Consequently the equality "org that signed == org that owns the team" is not enforced by any guard in the reachable path (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema for `MembershipHandler`, or `Team`/`User` validations) — none of them compare `params.organization.login` to `team.organization`.

Attacker's exact request: control (or be a member/admin able to trigger webhooks for) any GitHub organization `evil-org` that is configured in the target Shipit instance (i.e., has a registered `webhook_secret`/GitHub App installation in Shipit — a precondition, not a Shipit secret). Send a `POST /webhooks` with header `X-Github-Event: membership`, correctly HMAC-signed with `evil-org`'s webhook secret, and body:
```
{
  "action": "removed",
  "team": { "id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "evil-org" },
  "member": { "login": "<known-victim-username>" }
}
```
Because `verify_signature` succeeds (signed by `evil-org`'s real secret) and `find_or_create_team!` finds the pre-existing victim `Team` row by `github_id` alone, `team.members.delete(member)` runs against the victim org's team, removing the named user's membership.

### Impact Explanation
This causes a write to a `Team`/`Membership` record belonging to an organization that did not authenticate the request — the victim org's `webhook_secret` was never used. If the removed user's team membership was the sole basis for `User#authorized?` (`Shipit.github_teams` check in `app/models/shipit/user.rb` line 80-82), the operator silently loses authorization to deploy/rollback/approve, a cross-tenant authorization-state mutation. It is repeatable against any victim `team.id` (GitHub team IDs are not secret) and any known `member.login`, and combined with the `added` counterpart it also allows silently inserting a forged member into that same team. This matches the Critical category "a payload for one repository [organization] mutating another's ... team."

### Likelihood Explanation
Preconditions: attacker must control at least one GitHub organization that Shipit has configured with a `webhook_secret`/app installation (this is the org boundary Shipit is supposed to enforce, not a Shipit application secret). No Shipit session, API token, or `Shipit.github_teams` membership is required. The victim's `team.id` is discoverable via GitHub's public API (`GET /orgs/:org/teams` or team URLs), and `member.login` is public. Attacker cost is a single signed HTTP POST; the attack is trivially repeatable and scriptable.

### Recommendation
In `find_or_create_team!`, do not resolve an existing `Team` by `github_id` alone when it belongs to a different organization; instead scope the lookup by both `github_id` and `organization: params.organization.login`, and raise/drop the event (rather than mutate) when a `Team` with that `github_id` exists under a different `organization`. Additionally, in `process`, explicitly assert `team.organization == params.organization.login` before calling `team.add_member` or `team.members.delete`, discarding (logging + no-op) events that fail this check.

### Proof of Concept
Add a minitest in `test/models/webhooks/handlers/membership_handler_test.rb` (or wherever existing handler tests live):
1. Create `team = Team.create!(organization: 'victim-org', github_id: 999, slug: 'ops', name: 'Ops', api_url: '...')`.
2. Create `member = User.create!(login: 'legit-operator')` and `team.add_member(member)`.
3. Build a `membership` payload with `action: 'removed'`, `organization: { login: 'evil-org' }`, `team: { id: 999, ... }`, `member: { login: 'legit-operator' }`.
4. Call `MembershipHandler.new(payload).process` (or however handlers are invoked in existing tests).
5. Assert BEFORE: `team.organization == 'victim-org'` and `params.organization.login == 'evil-org'` (unequal — the binding is violated).
6. Assert AFTER: currently `team.members.reload.include?(member)` is `false` (bug reproduced — member removed despite mismatched org). The fix should assert `team.members.reload.include?(member)` remains `true` because the handler must refuse to mutate `Team#members` when `params.organization.login != team.organization`.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload

    end
