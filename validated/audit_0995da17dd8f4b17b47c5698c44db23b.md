### Title
Precision loss in denomination cap summation allows inconsistent/inflated asset supply - ([File: validation.js])

### Summary
`validateAssetDefinition` in `validation.js` sums the product of `count_coins` and `denomination` for each denomination entry into a plain JS number (`total_cap_from_denominations`) without bounding `count_coins` or the resulting product to `Number.MAX_SAFE_INTEGER`. This mirrors the reported `UniswapV2EthOracle` bug class: two individually-checked values are combined via arithmetic whose result type/range is not validated, producing a silently inaccurate value that is then trusted for a security-relevant comparison.

### Finding Description
In `validateAssetDefinition`, each `denomInfo.denomination` is checked against `constants.MAX_CAP` (conditionally, only after `pemCurvesFixMci`), and `denomInfo.count_coins` is only checked with `isPositiveInteger`, which merely verifies `Math.floor(value) === value && value > 0` — it does not bound the magnitude of `count_coins`: [1](#0-0) 

The running total is accumulated as a plain float: [2](#0-1) 

Because `isPositiveInteger` only checks `typeof value === 'number' && isFinite(value) && Math.floor(value) === value`, an attacker (the asset-issuing unit poster) can supply a `count_coins` value with no explicit maximum, and multiply it by a `denomination` close to `constants.MAX_CAP`: [3](#0-2) 

When `denomInfo.count_coins * denomInfo.denomination` exceeds `Number.MAX_SAFE_INTEGER` (2^53-1), JavaScript's IEEE-754 double arithmetic silently rounds the product, exactly analogous to the reported `uint8` overflow: the summed `total_cap_from_denominations` no longer reflects the true mathematical sum of `count_coins × denomination` across denominations. This rounded/aliased sum is what gets compared against `payload.cap` at: [4](#0-3) 

Because floating-point rounding can make a false statement (`total_cap_from_denominations === payload.cap`) evaluate true while the true integer sum differs, an asset definer can craft a `denominations` array whose declared `cap` does not actually match the true total number of coins mintable across denominations, while passing this validation check.

### Impact Explanation
`asset_denominations.count_coins` is later relied upon during actual indivisible-asset issuance to determine how many coins of a denomination may be issued (validated against `count_coins` at issuance time in `validation.js`'s `validateIndivisibleIssue`, which reads `count_coins` from `asset_denominations` and checks `input.amount !== denomination * denomInfo.count_coins`). If the declared `cap` was accepted despite not matching the true total-supply implied by `denominations` (due to precision loss during registration), the asset's advertised cap invariant is broken: more (or fewer) total base units could ultimately be issuable across all denominations than the `cap` implies. This undermines a fungible-asset supply invariant that wallets, exchanges, and AAs rely on (`cap` is supposed to be an exact, verified upper bound on total issuance) — a form of supply-accounting corruption analogous to the pricing corruption in the original report.

### Likelihood Explanation
Requires the attacker to be the single author defining a new asset (an unprivileged asset issuer, fully reachable by posting a normal `asset` message unit) and to choose `count_coins`/`denomination` values whose product is on the order of `2^53` or larger while individually satisfying `isPositiveInteger` and the (upgrade-gated) `denomination <= MAX_CAP` check. Since `count_coins` itself has no upper bound check at all, this is straightforward to trigger deliberately.

### Recommendation
- Bound `count_coins` explicitly (e.g., to `constants.MAX_CAP`) in the same way `denomination` is bounded.
- Perform the `count_coins * denomination` multiplication and the running summation using an arbitrary-precision integer library (e.g., `BigInt` or a big-number library), and reject the asset definition if the exact sum does not equal `payload.cap`, rather than relying on IEEE-754 double arithmetic.
- Apply the same fix unconditionally (not gated behind `pemCurvesFixMci`) to the denomination magnitude check to avoid depending on the current time/upgrade state.

### Proof of Concept
1. An author posts a unit containing an `asset` message with `cap = C` and `denominations` containing a single entry `{ denomination: D, count_coins: N }` where `D` and `N` are each valid positive integers (`D <= MAX_CAP`), but `D * N` exceeds `Number.MAX_SAFE_INTEGER` (~9.007×10^15).
2. `validateAssetDefinition` computes `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` as a JS double; due to floating-point rounding, the computed product/sum can equal a chosen `C` that does not represent the exact mathematical product of `D` and `N`. [5](#0-4) 
3. The check `total_cap_from_denominations && payload.cap !== total_cap_from_denominations` passes (no error), even though the true (`BigInt`) product `D*N` differs from `C`, allowing an inconsistent cap/denomination declaration to be accepted into the DAG.
