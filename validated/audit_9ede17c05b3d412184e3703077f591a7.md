### Title
Reentrancy in `collect_creator_fee_permissionless` / `collect_creator_fee` via Token-2022 transfer-hook CPI, state cleared after external transfer (checks-effects-interactions violation) - ([File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee_permissionless` (and the creator-gated `collect_creator_fee`) read `pool_state.creator_fees_token_0/1`, perform two external CPI token transfers using those amounts, and only *afterwards* zero the fee counters. If either vault mint is a Token-2022 mint with a `TransferHook` extension, the hook program is invoked as part of `transfer_checked`, before control returns to the cp-swap instruction and before the fee counters are reset — giving an attacker-controlled program a window to re-enter the same instruction while `creator_fees_token_0/1` are still non-zero.

### Finding Description
Both `collect_creator_fee` and `collect_creator_fee_permissionless` follow this order:
1. Read `creator_fees_token_0`/`creator_fees_token_1` from `pool_state`. [1](#0-0) 
2. Transfer both amounts out of the vaults via `transfer_from_pool_vault_to_user`, which performs `token_2022::transfer_checked` CPIs to the (attacker-supplied) `token_0_program`/`token_1_program`. [2](#0-1) 
3. Only after both transfers succeed does the function zero the fee counters. [3](#0-2) 

The transfer helper always calls `token_2022::transfer_checked`, regardless of whether the mint is legacy SPL Token or Token-2022: [4](#0-3) 

Token-2022's `TransferChecked` implementation, when the mint carries the `TransferHook` extension, performs a CPI into the hook program registered on the mint *during* the transfer, after the token balances have already moved but before the outer `transfer_checked` instruction returns control to the caller. Because `pool_state` is held as a `RefMut` (`load_mut()`) across both transfer calls, and Solana's per-CPI-frame account-data borrow tracking does not persist across invocation levels, a re-entrant call into `collect_creator_fee_permissionless` from the hook program can `load_mut()` the same `pool_state` account again and observe `creator_fees_token_0/1` still at their pre-transfer (non-zero) values — the classic checks-effects-interactions violation flagged in the referenced report, applied here to Solana's CPI-based reentrancy model instead of EVM callbacks.

An attacker can construct this scenario entirely with unprivileged instructions in scope: create a Token-2022 mint with a `TransferHook` extension pointing at their own hook program, use it as `token_0_mint`/`token_1_mint` in `initialize`, accumulate creator fees through swaps, then call `collect_creator_fee_permissionless`. `initialize`'s account constraints only check `mint::token_program` ownership and relative mint ordering; they do not exclude the `TransferHook` extension. [5](#0-4) [6](#0-5) 

Whether the program's `is_supported_mint`/extension allow-list explicitly blocks `TransferHook` mints could not be confirmed with the available context (the function body was not fully retrieved), so this is noted as an open verification point rather than an assumption.

### Impact Explanation
Because `transfer_from_pool_vault_to_user` performs no post-transfer solvency check against the remaining vault balance (unlike swap paths, which validate the constant-product invariant), a successful reentrant call can repeatedly request transfers of the stale `creator_fees_token_0/1` amounts, draining vault balance beyond what was actually owed as creator fees — including funds belonging to liquidity providers, not just the intended fee amount. This matches the impact class in the referenced report: drainage of funds beyond what should be withdrawable, via a state-update-after-external-call pattern.

### Likelihood Explanation
The attacker must control both the pool (as `pool_creator`, trivially achievable via permissionless `initialize`) and a Token-2022 mint with a custom `TransferHook` program (a normal, permissionless Token-2022 feature) used as one of the pool's vault mints. `collect_creator_fee_permissionless` requires no privileged signer and can be invoked by anyone once fees have accrued. The main uncertainty is whether `is_supported_mint` in `programs/cp-swap/src/utils/token.rs` filters out `TransferHook`-extension mints at pool-creation time; this could not be verified from the retrieved snippets and would need to be checked directly.

### Recommendation
Re-order the logic so effects precede interactions: zero `pool_state.creator_fees_token_0`/`creator_fees_token_1` (and persist/drop the `load_mut()` borrow) before issuing the `transfer_from_pool_vault_to_user` CPIs. Additionally, consider adding an explicit reentrancy guard (e.g., a busy flag in `PoolState`) around all fee-collection and swap paths that perform token CPIs, since Solana's account-data borrow checks are not a reliable reentrancy defense across CPI frames.

### Proof of Concept
1. Attacker creates a Token-2022 mint `M` with the `TransferHook` extension pointing to a malicious hook program `H` that they control.
2. Attacker calls `initialize` with `M` as `token_0_mint` (or `token_1_mint`), becoming `pool_creator`. [7](#0-6) 
3. Attacker performs swaps to accrue `creator_fees_token_0` (enabled via `enable_creator_fee`/`creator_fee_on`).
4. Attacker calls `collect_creator_fee_permissionless`. During the `transfer_checked` CPI for `token_0`, the Token-2022 program invokes hook `H`.
5. `H` CPIs back into `collect_creator_fee_permissionless` for the same pool; `pool_state.creator_fees_token_0` is still non-zero (not yet reset by the outer call, at lines 125-127), so a second transfer of the same amount is issued against the vault before the outer call resets the counters, draining more than the legitimately accrued fee amount from the vault. [8](#0-7)

pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

    Ok(())
}

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
