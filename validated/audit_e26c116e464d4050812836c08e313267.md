### Title
Missing upper-bound validation on `timestamp`/`mci` conditions in address definitions allows permanent freezing of jointly-owned funds - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` validates the `timestamp`, `mci`, and `age` operators used inside address definitions (the scripts that gate spending from an address, including shared/multisig addresses negotiated between counterparties). The value associated with these operators is only checked to be a non-negative integer, with no upper bound. This mirrors the reported bug class: a numeric parameter that gates when funds become spendable is accepted without any sanity/upper-limit check, so it can be set to an absurdly large (effectively unreachable) value, permanently locking funds that depend on that branch of the definition.

### Finding Description
In `definition.js`, the `case 'mci': case 'age': case 'timestamp':` branch of `evaluate()` (used by `validateDefinition`) only validates:
- that the relation is one of `=, >, <, >=, <=, !=`
- that `value` is a non-negative integer via `isNonnegativeInteger(value)` [1](#0-0) 

There is no upper bound check on `value` for `timestamp` or `mci`. This op is a standard building block for time-locked / HTLC-style shared addresses that two unprivileged parties negotiate off-chain (e.g. atomic-swap refund paths, escrow refund clauses) via `wallet_defined_by_addresses.js`'s shared-address-definition-template mechanism, where one party proposes a definition (e.g. `["or", [ ["and",[<cooperative sig path>]], ["and",[["address", refund_address], ["timestamp", [">", HUGE_NUMBER]]]] ]]`) and the counterparty (or their device) is expected to review and co-sign it.

Because the protocol layer performs no sanity/upper-bound check on the `timestamp`/`mci` threshold, a counterparty who proposes such a shared address can embed a refund/unlock condition with a value so large that it can never realistically be reached (e.g. billions of seconds in the future), while making the definition look superficially like a normal time-locked refund clause. If the honest party signs without independently reasoning about the magnitude of the constant, their portion of the funds locked in that condition can never be recovered through that branch if the cooperative branch stops functioning (e.g., the counterparty goes offline or refuses to cooperate).

This is directly analogous to the reported bug: a value that determines "how long before funds become spendable" is accepted by validation logic with no upper limit, enabling one party to make the wait effectively infinite.

### Impact Explanation
If exploited in a two-party (or more) shared/time-locked address construction, one party can force the other's contribution to be un-refundable except via the cooperative path they control — an equivalent of "AA/definition fund freezing" for the honest counterparty. This can result in permanent loss of access to funds locked at that shared address, which is a fund-freezing/loss condition analogous to the accepted-risk report (impact 4/5 in the original report). It does not create direct double-spend or unauthorized-spend conditions, only a freezing effect for the disadvantaged party.

### Likelihood Explanation
Exploitation requires that a counterparty voluntarily negotiate and sign a jointly-defined address containing a `timestamp`/`mci` (or `age`) condition proposed by an adversarial peer, and that the victim not independently sanity-check the numeric constant before co-signing (wallet UIs typically do not surface or highlight the raw magnitude of definition constants to end users). This requires user/wallet-level participation and is not exploitable purely at the protocol/validation layer against an unwilling party, which lowers likelihood, consistent with the original report's Likelihood 2/5 rating.

### Recommendation
Add an explicit sane upper bound to the `timestamp`/`mci`/`age` operators in `definition.js`'s `validateDefinition()` (e.g., reject `timestamp` values further than some maximum number of years/blocks from now, similar to how `formula/evaluation.js`'s `timestamp_to_string` already rejects timestamps beyond `8640000000000` — see the corresponding test), and have wallet software (e.g. `wallet_defined_by_addresses.js` shared-address proposal flow) surface a clear, human-readable warning of any absolute time/mci thresholds embedded in a proposed shared-address definition before the user is asked to co-sign.

### Proof of Concept
1. Party A proposes a shared address definition template to Party B via `wallet_defined_by_addresses.js` (`createNewSharedAddressByTemplate` / `sendOfferToCreateNewSharedAddress`), of the form:
   ```
   ["or", [
     ["and", [["address","A"], ["address","B"]]],           // cooperative spend
     ["and", [["address","A"], ["timestamp", [">", 99999999999]]]]  // "refund" branch, effectively unreachable
   ]]
   ```
2. `validateAddressDefinitionTemplate` / `validateDefinition` accept this because `isNonnegativeInteger(99999999999)` passes and no upper limit is enforced. [2](#0-1) 
3. Party B, believing the second branch is a normal reasonable-timeout refund clause, co-signs and funds are sent to the resulting shared address.
4. If Party A subsequently refuses to cooperate on the "and" branch requiring both signatures, Party B's funds are locked behind a `timestamp` condition that will not be satisfied for tens of thousands of years, permanently freezing the funds.
