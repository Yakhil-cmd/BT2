### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but the code path that acts on the payload resolves the target `Stack` from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner` (`repository.owner.login` or `organization.login`), while the handlers that actually act on the request (`Handler#stacks`/`Handler#repository_name`) resolve the target `Repository`/`Stack` from a completely different payload field, `repository.full_name`. The field that determines *whose secret authenticates the request* is not the same field that determines *which repository/stack the request acts upon*, which is exactly the "authenticated organization vs. written repository" binding break called out in the task rules.

### Finding Description
`WebhooksController#verify_signature` selects the app config to validate the signature with: [1](#0-0) [2](#0-1) 

Signature verification itself is a raw HMAC compare of the whole payload against the secret configured for the organization picked by `repository_owner`: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization: [4](#0-3) 

The setup docs explicitly document `webhook_secret` as *optional*: [5](#0-4) [6](#0-5) 

Once the request passes `verify_signature`, the handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) never re-checks that the authenticated organization matches the repository the handler is about to act on. Every base `Handler` resolves the target repository purely from `repository.full_name`, a field independent of `repository.owner.login`: [7](#0-6) 

`PushHandler`, for example, uses that repository-derived `stacks` scope to trigger `sync_github` on every matching stack: [8](#0-7) 

Because `verify_signature`'s organization selection (`repository.owner.login` / `organization.login`) and the handler's repository resolution (`repository.full_name`) are independent JSON fields inside the same raw body, an attacker who can get any organization onboarded to this multi-tenant Shipit instance without a configured `webhook_secret` (a documented, supported configuration) can send a payload whose `repository.owner.login` matches that unsecured organization (bypassing signature verification entirely) while setting `repository.full_name` to point at a Stack belonging to an entirely different, secured organization. The `stacks` lookup performs no cross-check that the full_name's owner matches the organization whose secret was used (or skipped) during verification.

### Impact Explanation
This breaks the binding: `organization authenticated == repository written`. An attacker with zero Shipit credentials (no session, no ApiClient token, no webhook_secret, no GitHub App key, no repo write access) can trigger `GithubSyncJob`/`sync_github` (and other handler side effects: creating `Team`/`Membership` records via `MembershipHandler`, refreshing check runs via `CheckSuiteHandler`, updating commit `Status` via `StatusHandler`) against Stacks that belong to a repository/organization that was never part of the verified request, since the verification target and the action target are decoupled fields of the same untrusted payload. This is an authentication-bypass-style confused deputy at the ingress point of the engine, directly analogous to the reported price min/max confusion: the code verifies against the "wrong" field while the impactful action is keyed off a different field that is never covered by that verification decision.

### Likelihood Explanation
Exploitability depends on at least one configured organization lacking a `webhook_secret`, which the engine's own documentation treats as a normal, supported deployment option (not a misconfiguration outside scope). Any installation onboarding multiple organizations with heterogeneous secret configuration is exposed. No privileged credential, session, or write access is required by the attacker to reach `/webhooks` and craft the JSON body.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`), the field used to select and verify the webhook secret, matches the owner segment of `repository.full_name` before dispatching to handlers - and have `Handler#repository_name`/`#stacks` derive the repository strictly from the same field(s) that were authenticated, rejecting payloads with mismatched owner/full_name pairs.

### Proof of Concept
1. Onboard/observe that organization `unsecured-org` is configured in `Shipit.github` without a `webhook_secret` (an explicitly supported/documented configuration). [5](#0-4) 
2. Send `POST /webhooks` with header `X-Github-Event: push` and any `X-Hub-Signature` value (ignored, since verification short-circuits to `true` for orgs without a secret), and a body such as:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `WebhooksController#repository_owner` resolves to `"unsecured-org"`, `Shipit.github(organization: "unsecured-org")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally. [4](#0-3) 
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves via `Repository.from_github_repo_name("secured-org/target-repo")`, completely unrelated to the `unsecured-org` organization that "authenticated" the request, and triggers `stack.sync_github(expected_head_sha: ...)` on that unrelated stack. [7](#0-6) [8](#0-7)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
