### Title
Cross-organization webhook forgery via unscoped `Commit.where(sha:)` lookup enables forged CI status and unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a request against using the organization named in the payload's `repository.owner.login` (or `organization.login`), but the `StatusHandler` that then acts on the payload resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization that was actually authenticated. This breaks the binding between "the organization whose secret validated the signature" and "the repository/stack whose data gets mutated."

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` config (and thus the HMAC secret) to check via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple independent GitHub organizations from a single instance, each with its own `app_id`/`webhook_secret` configured under its own key in `config/secrets.yml`: [3](#0-2) 

Once the signature check passes for whichever organization the payload claims to belong to, `WebhooksController#create` dispatches the raw payload to the registered handler for the event: [4](#0-3) 

For the `status` event, `StatusHandler#process` resolves the target commit(s) using a bare, unscoped `Commit.where(sha: params.sha)` — it never checks `repository`/`organization` from the payload against the stack that owns the matched commit(s): [5](#0-4) 

Contrast this with other handlers in the same directory (e.g. `PullRequest::ClosedHandler`, `PullRequest::EditedHandler`), which correctly resolve the target `repository`/`stack` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting: [6](#0-5) [7](#0-6) 

`StatusHandler` has no equivalent binding: it never calls `stacks`/`repository_name` (inherited from `Handler`) to constrain which commit rows can be affected. This is the direct analog of the reported bug class — the entity being acted on (`Commit`, and by extension its `stack`) is never checked to belong to the entity that was actually verified/trusted (the organization whose secret validated the request signature).

Once a matching `Commit` is found (matching purely by `sha`, which is very plausible across organizations for shared history — e.g. forks, mirrors, or template repositories that copy commits with identical SHAs), `create_status_from_github!` creates a `Status` record for that commit: [8](#0-7) 

`Status` creation has real side effects: `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` on the victim's stack: [9](#0-8) [10](#0-9) 

If the victim stack has `continuous_deployment: true` and the forged status marks the required CI context as `success`, this is sufficient to trigger an actual, unauthorized `Deploy` (existing tests confirm this trigger path for legitimate status creation): [11](#0-10) 

### Impact Explanation
An attacker who legitimately controls one configured GitHub organization/App on a shared, multi-org Shipit instance (and therefore knows that organization's own `webhook_secret`, which they provided to the Shipit operator per the documented multi-org setup) can send a request that passes `verify_signature` (because it is HMAC-valid for their own organization) while the payload's `sha` targets a `Commit` belonging to a completely different organization's stack. Because `StatusHandler` performs no repository/stack scoping, that forged status is applied to the victim stack. If the victim stack uses continuous deployment gated on that CI context, this forged "success" status directly triggers an unauthorized `Deploy` of the victim's stack — matching the Critical impact category "an unauthorized deploy" defined in scope.

### Likelihood Explanation
This requires the attacker to control at least one legitimately configured GitHub organization/App on the same shared Shipit instance (a documented, supported multi-tenant configuration) and for a matching commit SHA to exist for the victim's stack — realistic for forks/mirrors/shared history, and trivially achievable if the attacker can otherwise discover or guess a target SHA (SHAs are often public, e.g. via GitHub's public API/commit pages). No privileged Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only the attacker's own organization's webhook secret, which they legitimately possess. This is a plausible, unprivileged-relative-to-the-victim attack path.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving `Commit`/`Stack` by fields not derived from `repository.full_name`) to the repository/stack identified by the authenticated organization's payload, e.g. filter `Commit.where(sha: params.sha)` through `stacks` (the `repository_name`-scoped relation already provided by `Handler`) rather than a global `Commit` lookup, mirroring the pattern used by `PullRequest::EditedHandler` and similar handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section) — attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `status` event JSON body: `{"sha": "<victim_stack_commit_sha>", "state": "success", "context": "<victim_required_ci_context>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"}}`.
3. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the exact raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature validates successfully (attacker signed it correctly with a secret they legitimately know).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` — matching the victim's `OrgB` commit with no check that it belongs to `OrgA` — and calls `create_status_from_github!`, creating a `Status(state: 'success', context: <required context>)` on the `OrgB` stack.
6. If the `OrgB` stack has `continuous_deployment: true` and this was the last required status, `Status#schedule_continuous_delivery` fires `ContinuousDeliveryJob`, which triggers an unauthorized `Deploy` of `OrgB`'s stack — all without the attacker ever having credentials, `ApiClient` access, or write access to `OrgB`'s repository.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
