### Title
Cross-organization `Team` github_id collision in `MembershipHandler#process` allows privileged-team membership escalation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `github_id` (`Team.find_or_create_by!(github_id: params.team.id)`), with no check that the webhook's authenticated `organization.login` matches the `organization` of the existing `Team` row. An attacker who controls a GitHub organization O that Shipit has legitimately configured (its own `webhook_secret`, but not listed in `Shipit.github_teams`) can send a validly-signed `membership` webhook for org O with `team.id` set to the `github_id` of a *different* org P's privileged `Team`, causing an arbitrary attacker-chosen user to be added as a `Membership` on P's team.

### Finding Description
The broken binding: the organization that authenticated the webhook payload, `params.dig('organization','login')` (== O, verified via `Shipit.github(organization: repository_owner).verify_webhook_signature`), should equal the organization owning the `Team` row that gets mutated (== `Team#organization`, == P). `find_or_create_team!` never enforces this: [1](#0-0) 

`Team.find_or_create_by!(github_id: params.team.id)` looks up by `github_id` alone, a GitHub-wide unique integer that is independent of organization. If a `Team` row for org P already exists in Shipit's database (created e.g. by `Shipit.github_teams` bootstrap via `find_or_create_by_handle`), and the attacker crafts a `membership` payload where `team.id` equals P's `github_id` but `organization.login` is O, `find_or_create_by!` finds the *existing* P row. Because the record already exists, the `do |team| ... team.organization = params.organization.login` block is **not** executed (ActiveRecord only runs the block on creation), so the row keeps `organization = P`. `process` then calls `team.add_member(member)` on that P-owned row: [2](#0-1) 

`member` is resolved from attacker-controlled `params.member.login` via `User.find_or_create_by_login!`, which fetches a real GitHub user by that login and creates/attaches a Shipit `User` row - the attacker can name their own GitHub login here.

Path/guards checked and found insufficient for this specific divergence:
- `WebhooksController#verify_signature` only proves the payload was signed by *some* organization's configured `webhook_secret` (derived from `repository_owner`, which for `membership` events falls back to `params.dig('organization','login')`). It authenticates "this request came from org O", not "team X belongs to org O". [3](#0-2) [4](#0-3) 
- `drop_unhandled_event` and `ExplicitParameters` schema only validate shape/presence, not org-team correlation. [5](#0-4) 
- `Team` has no uniqueness/validation tying `github_id` to `organization`, and no model-level cross-check. [6](#0-5) 
- The privileged set `Shipit.github_teams` is exactly the set of `Team` rows checked in `User#authorized?`: [7](#0-6)  and `Shipit.github_teams` is built once via `find_or_create_by_handle` per configured `oauth.teams`: [8](#0-7) . `force_github_authentication` gates the entire app on `current_user.authorized?`: [9](#0-8) 

Exploit flow: attacker (owner/admin of legitimately-integrated but non-privileged org O, per multi-org support documented in `docs/setup.md`) sends `POST /webhooks` with header `X-Github-Event: membership`, signed with O's own `webhook_secret`, body:
```json
{
  "action": "added",
  "team": {"id": <P_privileged_team_github_id>, "name": "x", "slug": "x", "url": "https://example.com"},
  "organization": {"login": "O"},
  "member": {"login": "attacker-real-github-login"}
}
```
This request passes signature verification (org O is legitimately configured), is dispatched to `MembershipHandler`, and lands a `Membership` on P's `Team` row for the attacker's real GitHub user. Once the attacker later completes normal OAuth login with that same GitHub account, `current_user.authorized?` returns true, granting full access to the Shipit application as if they were a genuine member of the privileged GitHub team.

### Impact Explanation
This is escalation into `Shipit.github_teams` authorization (matches the High severity category explicitly listed in the rules): an attacker who is not, and never was, a member of any team in `Shipit.github_teams` gains `authorized?` status, bypassing the entire authentication gate in `force_github_authentication` and gaining access to stack state, deploys, and other authenticated Shipit functionality reserved for privileged team members. The mutation crosses tenant boundaries: a webhook authenticated as org O's traffic mutates a `Team` record belonging to org P. It is repeatable against any known/guessable `github_id` of a privileged team and any GitHub login the attacker controls, and is a `Membership.count` change per request (add), reversible by a follow-up `removed` action giving the attacker full control over their own presence on the privileged team.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must be configured to accept webhooks from more than one GitHub organization (documented multi-org support, `docs/setup.md`), where attacker's org O is validly configured with its own `webhook_secret`/GitHub App but is not in `Shipit.github_teams`; (2) the attacker must know or guess the numeric `github_id` of a `Team` already tracked by Shipit for the privileged org P - GitHub team IDs are not secrets, and are frequently observable (they appear in past webhook deliveries, GitHub API responses for public/known teams, or are simply small sequential integers easy to enumerate). Given these, the attack costs the attacker nothing beyond crafting one HTTP POST with a valid HMAC computed from their own known secret. Fully repeatable, no live GitHub interaction required beyond what the attacker already legitimately controls.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the authenticated `organization.login`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and raise/reject if an existing `Team` with that `github_id` belongs to a different organization than the one that authenticated the payload. Additionally, add a model-level uniqueness validation on `github_id` scoped to prevent silent reuse across organizations, and consider validating `params.organization.login` against `repository_owner`/the verified signing organization in the base `Handler` for organization-scoped events.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
        test "membership webhook signed for org O cannot mutate org P's privileged team" do
          # Team P belongs to the privileged org "shopify" and has a known github_id
          privileged_team = Team.create!(github_id: 999, organization: "shopify", slug: "admins", name: "Admins", api_url: "https://x")

          payload = {
            "action" => "added",
            "team" => { "id" => 999, "name" => "fake", "slug" => "fake", "url" => "https://example.com" },
            "organization" => { "login" => "attacker-org" }, # authenticated org != privileged_team.organization
            "member" => { "login" => "attacker" }
          }

          User.stubs(:find_or_create_by_login!).with("attacker").returns(shipit_users(:walrus))

          MembershipHandler.call(payload)

          # BROKEN BINDING: organization authenticated (attacker-org) != team.organization (shopify)
          assert_equal "shopify", privileged_team.reload.organization
          assert_includes privileged_team.members, shipit_users(:walrus) # attacker illegitimately added
        end
      end
    end
  end
end
```
This demonstrates that a payload authenticated for `organization.login = "attacker-org"` results in a `Membership` written onto `Team#organization == "shopify"`, confirming the cross-tenant binding failure and the resulting escalation into `Shipit.github_teams` authorization.
