Found: this multi-tenant configuration confirms that each GitHub organization has its own `webhook_secret`, `app_id`, and `private_key` in `github_app_config` [1](#0-0) , and the org is looked up case-insensitively from `secrets.github` [2](#0-1) .

The critical issue is in `WebhooksController#verify_signature`: the organization used to select which secret verifies the HMAC signature is read directly from the unverified request body itself, before any authentication occurs.

### Title
Webhook signature verification selects the HMAC secret from the unauthenticated payload, allowing cross-organization signature confusion - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` determines which GitHub App/organization's `webhook_secret` to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, not-yet-verified JSON body, then uses that attacker-influenced value to pick the secret used to validate the very same body's signature.

### Finding Description
The controller does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization config (each with its own `webhook_secret`, `app_id`, `private_key`) via `github_app_config`, matched case-insensitively on the organization name [4](#0-3) . The dummy multi-tenant configuration confirms Shipit installations commonly configure multiple independent organizations each with their own webhook secret [5](#0-4) .

The binding that should hold is: *the organization whose GitHub App signed the delivery* == *the organization whose secret is used to verify it*. Instead, the code uses *whatever organization name appears inside the payload* to select the verification secret — a value that is part of the data being verified, not an independent, already-authenticated channel (e.g., the URL path, a per-org webhook route, or the `X-GitHub-Hook-Installation-Target-ID` header). Nothing in this codebase binds the selected secret to a channel that is authenticated ahead of time.

Concretely: a holder of Org B's legitimate webhook secret (a bundle admin of any onboarded organization, or anyone who can trigger a GitHub webhook delivery for Org B, e.g., an outside collaborator with a webhook-triggering event on any Org B repo) can craft an arbitrary JSON body — including one whose `repository.owner.login`/`repository.full_name` names a *different, victim* organization's repository — and sign it with Org B's own secret. `repository_owner` will resolve to "Org B" (matching the field the attacker controls), `Shipit.github(organization: 'Org B')` will fetch Org B's webhook secret, and `verify_webhook_signature` will successfully validate the HMAC because it was in fact computed with Org B's own secret over that (attacker-crafted) body. The controller then dispatches the event (`push`, `status`, `pull_request`, `membership`, etc.) to handlers using the arbitrary payload fields, which for events like `push` will resolve the target stack by the (attacker-controlled) `repository.full_name`/`repository.owner.login`/branch in the payload [6](#0-5) , not by anything tied to Org B.

This breaks the deployment-trust binding "organization that authenticated" (Org B, via its own secret) vs "repository that is (subsequently) acted upon" (any repository name embedded in the payload, potentially belonging to a victim organization/stack configured under a different GitHub App).

### Impact Explanation
Depending on which webhook event is spoofed this can:
- Forge `status`/`check_suite` events for a victim stack's commit, marking arbitrary commits as CI-passing, which the merge queue and merge-request status checks rely on (`MergeRequest#all_status_checks_passed?`) [7](#0-6)  — potentially leading to an unauthorized merge for a repository the attacker does not control.
- Forge `push` events causing `GithubSyncJob` to be enqueued against an arbitrary stack, and forge `membership`/`team` events, altering `Team`/`Membership`/`User` records used for authorization (`Shipit.github_teams`) [8](#0-7) .

This matches the "High" bar: escalation into `Shipit.github_teams` authorization and/or an unauthorized deploy/merge path, contingent on the specific webhook handlers reachable through this controller.

### Likelihood Explanation
Requires only that the attacker control (or be authorized to trigger deliveries for) any one organization onboarded to the same Shipit instance — a much lower bar than repository write access to the victim organization, and no Shipit session, `ApiClient` token, or GitHub App private key is needed. The forged request can be sent directly to the `/webhooks` endpoint with an arbitrary `X-Hub-Signature` computed offline using the known secret. Likelihood is Medium, since it presumes multi-organization deployment (as shown by the shipped double-app config) and that the attacker holds/derives at least one organization's own valid webhook secret through legitimate means (e.g., being an admin/collaborator able to trigger events on a real, low-privilege org's repo).

### Recommendation
Do not let payload contents select the verification secret. Bind organization identity to an already-authenticated channel instead, e.g.:
- Route webhooks per organization/app (`/webhooks/:organization`) and verify strictly against that path segment's configured secret, or
- Use `X-GitHub-Hook-Installation-Target-ID` / a similarly out-of-band, GitHub-supplied installation identifier that is registered ahead of time per organization, or
- After verifying with each configured secret in turn (constant-time), cross-check that the payload's `repository.owner.login` actually matches the organization whose secret validated it, and reject otherwise.

### Proof of Concept
1. Attacker is an admin (or has webhook-trigger rights) of "OrgB", legitimately onboarded to the Shipit instance, and knows OrgB's `webhook_secret`.
2. Attacker crafts a JSON payload with `event = status` (or `push`) where `repository.owner.login = "OrgB"` (to select OrgB's secret) — but sets `repository.full_name`/`sha`/`state`/branch fields to reference a stack/commit belonging to a victim organization "OrgA" tracked by the same Shipit instance (Shipit associates stacks by `Repository#owner`/`#name`, not by which GitHub App verified the webhook).
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgB_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `repository_owner` resolves to `"OrgB"` from the payload [9](#0-8) ; `Shipit.github(organization: 'OrgB')` fetches OrgB's secret and the signature verifies successfully [10](#0-9) .
5. The `status` handler processes the forged commit-status update against whichever commit/stack the payload names (OrgA's), because dispatch and downstream stack/commit lookup use the payload's repository fields, not the organization that actually authenticated the request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
