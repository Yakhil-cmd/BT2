### Title
StatusHandler#process resolves target commits by raw `sha` only, letting a status webhook from any attacker-owned repo write forged CI statuses onto a victim stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that a webhook payload was signed by the GitHub organization named in the payload's own `repository.owner.login`/`organization.login` field, it never ties that verification to any specific target stack. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` with no repository or stack scoping at all, unlike `PushHandler` and `CheckSuiteHandler`, which both filter through `stacks` (derived from `Repository.from_github_repo_name(payload_repo)`) before touching any commit. Because git SHAs are content-addressed and identical between a fork and its upstream, an attacker who owns a fork can emit a validly-signed `status` webhook naming their own repo but referencing the SHA of a commit that also exists (with a different, victim-owned `stack_id`) in the `commits` table, and `Status.create` will be written against that victim `stack_id`.

### Finding Description
The broken binding is: `Status.stack_id` (written by `Commit#create_status_from_github!` → `Commit#add_status` → `statuses.replicate_from_github!(stack_id, github_status)`, [5](#0-4) ) should equal the `stack_id` belonging to the organization/repository that `verify_signature` cryptographically authenticated for this request (`repository_owner` in [6](#0-5) , [7](#0-6) ). In practice, `commit.stack_id` is simply whatever stack owned the pre-existing `Commit` row found via a bare `sha` lookup, with no relation to the payload's `repository` field at all.

Path: `POST /webhooks` with `X-Github-Event: status` → `WebhooksController#create` → `verify_signature` (checks HMAC against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload, i.e., the attacker's own org) → `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` → `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  → for every `Commit` row matching that raw SHA — regardless of which stack/repository it belongs to — a `Status` is created scoped to that commit's `stack_id` via `Commit#create_status_from_github!`/`#add_status` [5](#0-4) , [8](#0-7) .

Root cause: `StatusHandler` never calls the `Handler#stacks` helper that other handlers (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) use to scope operations to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. The `sha` param namespace is global across all stacks/repos in the `commits` table, so verifying that the sender legitimately owns *some* repo (their own) says nothing about whether they own the repo tied to the matched `Commit` row.

Attacker's exact request: attacker forks the victim's repo (or the victim's stack tracks a shared upstream the attacker also has push access to), opens a PR against the victim's tracked branch so that a `Commit` row with the PR head SHA gets created scoped to the victim's `stack_id` (via the normal push/PR sync flow). The attacker's fork, being a git object database with the same content, contains an identical commit object with the same SHA. The attacker then sends `POST /webhooks` with `X-Github-Event: status`, a body naming their own fork as `repository`, `sha` equal to that shared commit SHA, `state: 'success'`, and `context` matching the victim's required CI context, signed with the webhook secret for their own org/app installation (which they legitimately possess for their own repo).

Existing guards checked and found insufficient: `verify_signature` only authenticates "this payload came from GitHub for organization X," not "organization X owns the stack this payload is about" [9](#0-8) ; `drop_unhandled_event`/`ExplicitParameters` schema (`requires :sha, :state`, etc. [10](#0-9) ) do not require or check `repository`; and `Handler#stacks`/`Repository.from_github_repo_name` exist but are simply not used by `StatusHandler`.

### Impact Explanation
A single unauthenticated-relative-to-victim webhook request causes a `Status` row with `state: 'success'` and an attacker-chosen `context` to be written against a commit that belongs to a victim's `Stack`, without ever consulting that stack's `Repository` or the organization that actually owns it. Since deployability/CI-gating logic (`Commit#deployable?`, `Commit#blocked?`) and continuous delivery scheduling (`Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`) rely on aggregated `Status`/`Commit#status`, a forged "success" status can make an unmerged/malicious commit appear CI-green and eligible for deploy or auto-merge, directly matching the "unauthorized deploy/merge" critical category. This is repeatable against any stack whose tracked repository accepts PRs from forks or has any commit whose SHA the attacker can reproduce (trivial for any fork-based PR workflow), and requires no privileges beyond opening a PR and owning a signed webhook source for an arbitrary (attacker-owned) repository.

### Likelihood Explanation
Preconditions are all attacker-achievable without any victim/Shipit secret: a fork/PR against the tracked stack (standard, unprivileged GitHub action) to seed the `Commit` row, and a status webhook from the attacker's own repo/org, which the attacker can legitimately sign because it is their own GitHub App installation/webhook secret for their own org — `verify_signature` looks up `Shipit.github(organization: repository_owner)` using the attacker's own org name, not the victim's, so it succeeds using only the attacker's own credentials. No rate limiting or additional checks stand between the request and the write. This is realistically exploitable in any Shipit deployment allowing external PRs.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository/stacks derived from the payload, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits within `stacks.commits.where(sha: params.sha)` (or equivalently verify `commit.stack.github_repo_name == params.repository.full_name` before calling `create_status_from_github!`). Require `repository.full_name` in the `StatusHandler` params schema so it can't be omitted.

### Proof of Concept
Minitest plan (no live GitHub):
1. Fixtures: create `victim_stack` bound to `Repository` `victim/repo`, and a `Commit` row with `sha: "deadbeef"` scoped to `victim_stack.id` (simulating a prior push/PR webhook).
2. Stub `Shipit::GithubApp#verify_webhook_signature` (or whatever `WebhooksController#verify_signature` invokes) to return `true` unconditionally, simulating a validly-signed payload for the attacker's own org `attacker`.
3. POST to `/webhooks` with header `X-Github-Event: status` and JSON body: `{ "sha": "deadbeef", "state": "success", "context": "ci/required", "repository": { "full_name": "attacker/fork", "owner": { "login": "attacker" } } }`.
4. Assertions (the equality from both sides):
   - Before: `victim_stack.commits.find_by(sha: "deadbeef").statuses.count == 0`.
   - After: `Status.where(commit_id: commit.id).last.stack_id` — assert this **equals** `victim_stack.id`, even though `params['repository']['full_name']` never named `victim/repo`.
   - This demonstrates `Status.stack_id == victim_stack.id` while the verified organization/repository in the payload is `attacker/fork`, proving the binding "status.stack_id belongs to the org that signed the request" is broken.
