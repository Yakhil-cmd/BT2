## Analog Found: Unhandled empty-parse-result path can hang oscript/AA formula evaluation (denial of service)

### Title
Oscript formula evaluator silently drops the callback when the nearley parser yields zero results, hanging AA/formula execution - (File: `formula/evaluation.js`)

### Summary
The CVE describes a Mojolicious bug where an ambiguous/incomplete format-detection outcome is not handled correctly, letting a request fall through none of the expected code paths and hang processing (DoS). The ocore analog is in the oscript formula evaluator entry point in `formula/evaluation.js`, where the result of parsing an oscript/AA formula with `nearley` is dispatched only for the "exactly one result" and "more than one result" (ambiguous) cases — the "zero results" case is never handled, so `callback` is never invoked.

### Finding Description
At the end of `formula/evaluation.js`, after parsing a formula with the nearley grammar, the code does: [1](#0-0) 

```js
if (parser.results && parser.results.length === 1 && parser.results[0]) {
    evaluate(parser.results[0], res => { ... callback(...) ... }, true);
} else {
    if (parser.results.length > 1) {
        console.log('ambiguous grammar', parser.results);
        callback('ambiguous grammar', null);
    }
    // no else branch: if parser.results.length === 0, callback is NEVER called
}
```

`nearley.Parser.feed()` does not throw for every malformed/incomplete input; for inputs that end in a dangling/incomplete parse state (e.g., a formula ending with a trailing binary operator or an unterminated sub-expression that the grammar can still tokenize but not reduce to a complete rule), `parser.results` can legitimately be `[]` without an exception being thrown by `feed()`. In that case, neither branch of the `if/else` executes `callback`, so the function that requested formula evaluation is left waiting forever.

This mirrors the CVE's root cause class: a parsing/format-detection path that has more possible outcomes (none, one, many) than the code branches for, so one outcome (zero results) silently falls through instead of erroring out, which can hang processing of attacker-supplied input.

The formula/oscript evaluator is directly reachable by an unprivileged actor:
- AA authors embed formulas in AA definitions, evaluated by `definition.js`/`aa_composer.js` when a trigger unit fires the AA (`aa_composer.js:1800` shows the flow that ultimately depends on `validation`/formula evaluation completing).
- Unit posters can attach `formula` authentifiers evaluated at unit-validation time via `definition.validateAuthentifiers`, as exercised by `test/formulas_in_contracts.test.js:158-176` (formula-based `[[...]]` filters routinely produce "ambiguous" results, demonstrating that malformed/edge-case formula input is a first-class, attacker-reachable condition).

Similar "ambiguous grammar" handling exists elsewhere (e.g. `formula/validation.js:1523-1541` and `formula/parse_ojson.js:35-42`), but those explicitly cover the `length !== 1` case with an `else` fallback ("parser failed"/ambiguous-grammar error). The instance in `formula/evaluation.js:3226-3231` is missing that fallback for the zero-result case.

### Impact Explanation
If a crafted formula causes the parser to return zero results without throwing, the evaluation `callback` is never invoked. Any caller awaiting the result of formula evaluation (unit authentifier validation, or AA trigger response generation in `aa_composer.js`) never receives a response and will hang indefinitely on that unit/trigger. Because AA trigger processing and unit validation are serialized/locked per address or per processing queue (see the `mutex.lock` pattern used throughout `validation.js` and `aa_composer.js`), a hung evaluation can stall the AA execution pipeline or unit-validation pipeline on the node, preventing it from processing subsequent units/triggers — a denial-of-service condition consistent with "network unable to confirm new units" or "AA fund freezing" (triggered but never-responding AA calls).

### Likelihood Explanation
Likelihood is moderate: it requires finding a specific formula-token sequence that the oscript nearley grammar can consume as valid tokens (no lexer error) yet cannot reduce to a complete top-level rule, causing `parser.results` to end up empty rather than triggering a caught exception. This is a known nearley pitfall (incomplete-parse states silently yielding `results = []`) and is plausible to trigger via boundary formulas (e.g. trailing binary/unary operators, unclosed nested function-call arguments that still lex validly). Exact reproduction requires grammar-level analysis of `formula/grammars/oscript.js`, which was not fully explored in this investigation — I could not directly confirm a concrete formula string that reaches the zero-results branch, only that the code path for it is structurally missing an error handler.

### Recommendation
Add an explicit `else` branch for `parser.results.length === 0` (and any other non-1/non->1 case) in `formula/evaluation.js` around line 3226-3231, calling `callback('parser failed', null)` analogous to the handling already present in `formula/validation.js:1539-1540`, to guarantee the callback is always invoked exactly once regardless of parse outcome.

### Proof of Concept
Conceptual (not fully verified against the actual oscript grammar rules):
1. An AA author defines a getter/formula, or a unit poster attaches a `['formula', "<crafted-string>"]` authentifier, where `<crafted-string>` is chosen so the oscript lexer tokenizes it successfully but no grammar rule fully reduces (e.g., a formula ending mid-expression with a dangling operator or incomplete bracket that the `moo` lexer still accepts as valid tokens).
2. When the unit/trigger reaches formula evaluation in `formula/evaluation.js`, `nearleyParser.feed()` completes without throwing, but `parser.results` is `[]`.
3. The dispatch code at `formula/evaluation.js:3205-3231` executes neither branch, and the enclosing `callback` is never called.
4. The caller (unit validation or AA trigger handling), which is under a mutex/serialized lock, never completes, stalling further processing of units/triggers that depend on that lock. [1](#0-0) [2](#0-1) [3](#0-2)
