### Title
`Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, enabling cross-tenant read of any stack's deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by having `#stack` resolve through `#stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped [1](#0-0) . `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly against all stacks, never consulting `current_api_client.stack_id` [2](#0-1) . Any token holder with `read:stack` permission can therefore read any stack's CI status by swapping the `stack_id` in the URL while reusing a token they legitimately obtained for a different stack.

### Finding Description
The intended binding, enforced everywhere else in the API namespace, is:
`current_api_client.stack_id == id of the Stack object returned by #stack` (when `current_api_client.stack_id?` is true).

In `Api::BaseController`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` redefines `#stack` and drops the `stacks` scoping entirely:
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The `require_permission :read, :stack` before_action only checks that the token carries the string permission `"read:stack"` — it performs no per-stack comparison:
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

Call sequence for the exploit: `authenticate_api_client` resolves `@current_api_client` from `params[:token]` via `ApiClient.authenticate` [4](#0-3)  → `require_permission!` passes because the client has `read:stack` [5](#0-4)  → `show` calls the overridden `#stack`, which loads whatever stack the attacker names in the URL, ignoring `current_api_client.stack_id` [6](#0-5) .

Attacker request: `GET /stacks/:owner/:repo-B/:branch/cc_menu.xml?token=<token bound to stack A>` — substitute stack B's owner/repo/branch path segments while reusing the token minted for stack A. The response renders `shipit/ccmenu/project` with `stack.deploys_and_rollbacks.last` for stack B, exposing another tenant's deploy/build status.

Existing guards do not stop this: `authenticate_api_client` only validates token signature/expiry, not stack binding; `require_permission!`/`check_permissions!` is a flat string-membership check with no per-record scope; there is no `before_action` in `CCMenuController` comparing `params[:stack_id]` to `current_api_client.stack_id`.

### Impact Explanation
A token scoped to stack A can be used to read the CI/deploy status (deploy id, running/ended state) of any other stack B on the same Shipit instance, purely by editing the URL path — no additional secrets required. This is a cross-tenant confidentiality break: repository/team boundaries that `stack_id`-scoped tokens are meant to enforce are void for this endpoint. It is fully repeatable against every stack in the instance and does not require privilege beyond possessing any valid `read:stack` token (which, per the engine's own `CCMenuUrlController#fetch`, is designed to be embedded in public README/CI badges). This matches the High-severity category: unauthenticated/cross-boundary read of stack state via a token whose intended authorization did not cover the target resource.

### Likelihood Explanation
Preconditions: attacker needs any valid `read:stack` API token (the engine's own CCMenu badge-URL feature is designed to hand these out and embed them in public artifacts) and knowledge of the target stack's `owner/repo/branch` (which are usually public GitHub identifiers). No Shipit session, GitHub credentials, or Shipit secrets are required — only the token string, which by design ends up in public places (README badges). This makes exploitation cheap and highly feasible wherever CCMenu URLs are used.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to call `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`), so it inherits the same `current_api_client.stack_id` scoping enforced by `Api::BaseController#stack`.

### Proof of Concept
Add a minitest integration test under `test/controllers/api/ccmenu_controller_test.rb` (or wherever existing CCMenu controller tests live):
1. Create `stack_a` and `stack_b` (`Shipit::Stack`).
2. Create `client = Shipit::ApiClient.create!(creator: users(:walrus), name: 'scoped', permissions: %w[read:stack], stack_id: stack_a.id)`.
3. Assert binding before request: `assert_equal stack_a.id, client.stack_id`.
4. `get api_stack_ccmenu_url(stack_id: stack_b.to_param, token: client.authentication_token)`.
5. Assert response is `200` and body corresponds to `stack_b` (e.g., contains `stack_b.deploys_and_rollbacks.last` project name), demonstrating `client.stack_id` (`stack_a.id`) != the stack actually served (`stack_b.id`) — the broken binding.
6. Add a contrasting assertion against a request through a `stacks`-scoped controller (e.g. `Api::StacksController#show` for `stack_b.to_param`) expecting `404`, to show the scoping works everywhere except `CCMenuController`.
