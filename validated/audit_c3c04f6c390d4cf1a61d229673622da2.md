### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler#unarchive?` (and the structurally identical `OpenedHandler#provision?`) combine `review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, then `||` two more clauses that never re-check `review_stacks_enabled`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches, so a repository with `review_stacks_enabled: false` can still have its review stack unarchived/provisioned. The "malformed signature split" part of the combined attack premise does **not** hold: `GitHubApp#verify_webhook_signature` correctly rejects any signature whose `algorithm` (from `signature.split("=", 2)`) is not `'sha1'`, so it does not create a bypass for organizations with a configured `webhook_secret`.

### Finding Description
The invariant the question implies should hold is: `respond_to_pull_request_reopened?` should be `false` whenever `repository.review_stacks_enabled == false`, i.e. `review_stacks_enabled == false ⇒ unarchive? == false`. Tracing `unarchive?`:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby operator precedence this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. If a maintainer sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` and later disables `review_stacks_enabled` (expecting all dynamic provisioning to stop), the second and third clauses still evaluate independently of `review_stacks_enabled`. An attacker who can open a PR against the repository controls the label state (`labeled`/`unlabeled` events, or labels present at PR creation) and thus controls `pull_request_has_provisioning_label?`, satisfying one of those clauses and causing `stack.unarchive!` to run [2](#0-1) . The identical bug pattern exists in `OpenedHandler#provision?` [3](#0-2) , which additionally creates the stack (`ReviewStackAdapter#create!`) with `branch: params.pull_request.head.ref` — fully attacker-controlled — and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) .

By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` at the top level outside the `archive?/unarchive?` OR-chain, so it is not affected: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)`.

Regarding the "nil/malformed signature split" half of the combined premise: `verify_webhook_signature` returns `false` unless `algorithm == 'sha1'`, so a header with no `=` (yielding `algorithm` = the whole header, `signature` = `nil`) is rejected before `SecureCompare.secure_compare` is even reached for organizations with a configured `webhook_secret` [5](#0-4) . For organizations with no `webhook_secret` configured, verification already `return true unless webhook_secret` unconditionally, before the split logic runs at all [6](#0-5) . So the malformed-split detail contributes no additional exploitability; the vulnerability is exercised purely through a legitimately GitHub-signed webhook generated by the attacker's own PR action against the target repository, no signature forgery required.

### Impact Explanation
An attacker who can open/label a pull request against a repository can cause an unarchived (and, via `OpenedHandler`, newly created and enqueued-for-provisioning) `ReviewStack` even though the repository owner explicitly disabled dynamic PR-driven stack provisioning (`review_stacks_enabled: false`). The stack's `branch` is taken directly from `pull_request.head.ref`, i.e., attacker-controlled content [7](#0-6) . Since `ReviewStackProvisioningQueue.add(stack)` triggers host-defined provisioning/deploy behavior, this is an unauthorized provisioning/deploy action the repository owner intended to prevent. This matches the "unauthorized deploy" impact category, though it is scoped to the repository the attacker can already open PRs against (not a cross-tenant/cross-repository mutation), and only manifests when `provisioning_behavior` is `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a specific, non-default configuration state.

### Likelihood Explanation
Requires: (1) the target repository has `review_stacks_enabled: false` but `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (default is `allow_all`, in which case the bug is inert) [8](#0-7) ; (2) attacker can open/label a PR against that repository — an unprivileged, low-cost action; (3) no signature forgery is needed since GitHub sends a correctly-signed webhook for the attacker's own legitimate PR action. This is fully repeatable for any repository left in that specific, non-default configuration combination.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire OR-chain in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`:
```ruby
repository.review_stacks_enabled && (
  provisioning_behavior_allow_all? ||
  (provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
)
```

### Proof of Concept
minitest plan (under `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
```ruby
test "does not unarchive/provision when review_stacks_enabled is false, regardless of provisioning_behavior" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end
  # BEFORE fix: stack.count increases / stack gets provisioned -> assertion fails, proving review_stacks_enabled == false does not imply unarchive? == false
end
```
Assert on both sides of the binding: `repository.review_stacks_enabled` (false) vs. the observed side effect (`Shipit::Stack.count` unchanged / `stack.archived?` unchanged) — currently they diverge for `allow_with_label`/`prevent_with_label` configurations, confirming the precedence bug.
