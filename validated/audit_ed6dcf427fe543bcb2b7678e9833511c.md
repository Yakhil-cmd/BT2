### Title
`buildkite/deploy` status webhook writes across repositories via bare-SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository that authenticated the webhook, unlike every other handler which restricts writes through `Handler#stacks` (which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). Any `Commit` row anywhere in the database whose `sha` column matches the incoming value receives the new status, regardless of which stack/repository it belongs to.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row that gets `create_status_from_github!` called on it, but `StatusHandler#process` never checks this: [1](#0-0) 

Compare this with the base `Handler#stacks` helper, which every other handler (`push_handler.rb`, `check_suite_handler.rb`, `pull_request/*`) uses to restrict effects to the repository whose `full_name` is in the payload: [2](#0-1) 

`StatusHandler` is the outlier: it queries `Commit` directly by bare `sha` with no `stack_id`/`repository` filter, so if two `Commit` rows (belonging to two different `Stack`s / repositories) happen to share the same `sha` value, a status authenticated for repository A also mutates the commit belonging to stack B. Git commit SHAs are content-addressed (tree, parents, author/committer, message, timestamps) and are *preserved* across forks and identical cherry-picks, so a commit already known to a victim stack can trivially reappear with an identical SHA in a second Shipit-tracked repository/stack (e.g., a fork, a mirror, or a second stack pointed at the same underlying repository).

Once `commit.create_status_from_github!(params)` runs on the victim's `Commit` row, `Commit#add_status` recomputes `status`/`new_status` and, if it turns `success`/`pending`, calls `stack.schedule_merges`. Independently, `Commit#schedule_continuous_delivery` (triggered from `after_commit` on creation, and effectively re-evaluated any time the commit becomes `deployable?`) enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `stack.deployable?` are true: [3](#0-2) [4](#0-3) 

Because `deployable?` depends on `success?` derived from the very statuses `StatusHandler` just wrote (`delegate :pending?, :success?, ... to: :status` at commit.rb:219, and `status` recomputed from `statuses_and_check_runs`), flipping the required `buildkite/deploy` context to `success` on a victim's commit can make that commit `deployable?` and trigger the victim stack's continuous-deployment ship path — even though the request never touched the victim's repository or its `verify_signature` check for that organization.

Existing guards do not stop this: `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) validates the HMAC of the raw payload against the secret configured for `repository_owner` (an org-wide GitHub App secret), which authenticates "this came from GitHub for org X" but does **not** scope which repository's commits the handler is allowed to touch — that scoping is left entirely to each handler's own logic, and `StatusHandler` omits it. `ExplicitParameters` only validates the shape/types of `sha`, `state`, `context`, etc., not their relationship to `payload['repository']`.

### Impact Explanation
A `status` webhook legitimately signed for one repository/org can flip commit status and, on a continuous_deployment-enabled victim stack, drive `ContinuousDeliveryJob` to ship (or, with a `failure`/`error` state, to block deploys) a commit the attacker does not control the CI for. This is a cross-tenant write: a payload authenticated for repository A mutates state (`Shipit::Status`) belonging to stack/repository B, matching the "payload for one repository mutating another's stack/commit" Critical category, with potential unauthorized deploy or rollback consequence.

### Likelihood Explanation
Exploitation requires: (1) a `Commit` row with an identical SHA to exist in both the attacker-reachable repository and the victim's tracked stack — realistic via forks/mirrors/duplicate stacks tracking the same underlying repo, since git SHAs are stable under forking/cherry-picking with identical content; (2) the attacker must be able to get a `status` event emitted by GitHub for their own reachable repository within the same org/app installation that Shipit trusts (e.g. via their own CI reporting to GitHub, or via GitHub Actions on a repo they control) with `context: buildkite/deploy` and `state: success`; and (3) the victim stack must have `continuous_deployment` enabled and be otherwise `deployable?`. This does not require the `webhook_secret`, `secret_key_base`, or any Shipit session — only the pre-existing org-wide webhook trust relationship and a naturally shared commit SHA.

### Recommendation
Scope `StatusHandler#process` to only update `Commit` rows belonging to stacks of the repository named in the payload, mirroring the pattern used by other handlers, e.g. restrict the lookup via `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `Handler#stacks`/`repository_name` helpers.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — not present verbatim in the indexed code, would need to be added):
1. Create `stack_a` for repository `attacker/repo` and `stack_b` for repository `victim/repo`, with `stack_b.continuous_deployment` enabled and `required_status: 'buildkite/deploy'`.
2. Create `Commit` rows in both stacks sharing the identical `sha` (simulating a forked/cherry-picked commit).
3. Assert precondition equality: `commit_b.deployable? == false` (no successful `buildkite/deploy` status yet).
4. Invoke `StatusHandler.call('sha' => shared_sha, 'state' => 'success', 'context' => 'buildkite/deploy', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } })`.
5. Assert `commit_b.reload.deployable?` flips to `true` (or that `ContinuousDeliveryJob` was enqueued for `stack_b`) — demonstrating that a payload naming `attacker/repo` mutated `stack_b`'s commit, violating the invariant "a `buildkite/deploy` status affects only the repository that authenticated it."

Note: the full reachability chain through the org-wide `verify_webhook_signature` trust boundary and `ContinuousDeliveryJob`'s exact ship logic was inspected only partially (I was unable to fully trace `ContinuousDeliveryJob`/`stack.deployable?` within the available iterations); the code-level defect in `StatusHandler#process`'s missing repository scoping is confirmed directly from source.
