## Binding (explicit equality checked)

The security invariant the question describes translates to: for a `status` webhook to write a `Shipit::Status` onto commit `C` belonging to `Stack#repository == R_victim`, the payload's `repository.full_name` must equal `R_victim`'s full name. I traced the code to check whether `payload.repository.full_name == commit.stack.repository.full_name` is actually enforced before `Shipit::Status` creation.

It is not.

## Trace

- `WebhooksController#create` dispatches the parsed JSON straight to the registered handler for the event, with no repository binding at the controller level: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` only proves the payload was really signed by *some* GitHub organization/app Shipit recognizes (`Shipit.github(organization: repository_owner)`); it does not bind the payload to a specific repository or stack [2](#0-1) .
- `Handlers::StatusHandler#process` resolves target commits purely by SHA, with **no repository/stack scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
- Contrast this with the other handlers in the same module, which explicitly scope to the repository from the payload via the shared `stacks` helper before touching any record: `PushHandler#process` filters `stacks.not_archived.where(branch:)` [4](#0-3) , and `CheckSuiteHandler#process` filters `stacks.where(branch: ...)` before touching `stack.commits` [5](#0-4) . Both use `Handler#stacks`, which derives from `Repository.from_github_repo_name(repository_name)` [6](#0-5) . `StatusHandler` is the outlier: it never calls `stacks` or checks `repository_name` against the commit's owning stack.
- `Commit#create_status_from_github!` → `Commit#add_status` then unconditionally fires `stack.schedule_merges` on a `pending`/`success` transition and emits `deployable_status` hooks when the simple-state changes [7](#0-6) . `Status` creation itself also triggers `schedule_continuous_delivery` on `after_commit :create` [8](#0-7) .

So the equality `payload.repository.full_name == commit.stack.repository.full_name` is **never checked** before this state-mutating and merge/deploy-triggering side effect runs — the only precondition is a raw SHA string match in the `commits` table.

## Practical reachability

For two different `Stack`/`Repository` rows to share a `Commit.sha`, they need shared git history — e.g., a fork of the victim repository (git forks share the parent's commit objects byte-for-byte, hence identical SHA), or two Shipit stacks tracking the same underlying repository (e.g. staging/production stacks sharing a common base branch). Given a validly-signed GitHub "status" webhook for the attacker's own repo/commit (attacker only needs write access to their own repo/fork to set a commit status via GitHub's API — no Shipit secret needed, since GitHub itself signs the delivery), Shipit's `StatusHandler` will apply that status to **every** `Commit` row across **every** stack sharing that SHA, including the victim's, because filtering is by SHA only. ### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` locates target commits solely by `sha`, without verifying that the webhook's `repository.full_name` matches the repository owning the commit's stack. A validly-signed GitHub "status" webhook from any repository sharing a commit SHA with a victim's tracked commit (trivially achievable via a fork or a second stack on the same base repo) will write a `Status` and trigger `schedule_merges`/`schedule_continuous_delivery` on the victim's stack.

### Finding Description
The broken binding is `payload.repository.full_name == commit.stack.repository.full_name`, which `StatusHandler#process` never checks: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Sibling handlers (`PushHandler`, `CheckSuiteHandler`) correctly scope to `stacks` derived from `Repository.from_github_repo_name(repository_name)` [6](#0-5) , but `StatusHandler` omits this scoping entirely. `verify_signature` only proves the request came from a GitHub org/app Shipit trusts, not that it's authorized for the specific commit's repository [2](#0-1) . Once `Status.replicate_from_github!` creates a record, `Commit#add_status` calls `stack.schedule_merges` and emits `deployable_status` on any simple-state transition [7](#0-6) , and `Status`'s `after_commit` callback schedules continuous delivery on the victim's stack [8](#0-7) .

### Impact Explanation
An attacker who owns a repository sharing a commit SHA with a victim's tracked commit (fork, or shared base commit across two Shipit-tracked stacks of the same underlying repo) can author `success`/`pending`/`failure` status transitions on the victim's `Commit`, triggering `schedule_merges`/`schedule_continuous_delivery` for a stack they don't own. This is "a payload for one repository mutating another's stack/commit," matching the Critical category, and is repeatable indefinitely (each new status POST from the attacker's own repo re-triggers the race against legitimate CI updates).

### Likelihood Explanation
Requires: (1) attacker's repo is covered by the same GitHub App/org installation Shipit already trusts (a normal precondition for shared Shipit instances / org-wide app installs), and (2) a shared commit SHA with the victim (trivial via fork or overlapping stack history). No Shipit secrets, sessions, or API tokens are needed — GitHub itself signs the webhook for the attacker's own repository event.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the reporting repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `Repository.from_github_repo_name(repository_name)` and restrict `Commit.where(sha: params.sha)` to `stack_id: stacks.pluck(:id)` (or iterate `stack.commits.where(sha: ...)`) before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create two `Stack`/`Repository` fixtures, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`), each with a `Commit` sharing the same `sha`.
2. POST a `status` payload with `repository.full_name = "attacker/repo"`, `sha` = shared sha, `state: "success"`.
3. Assert `victim_stack.commits.find_by(sha:).statuses.count` increased and `stack.schedule_merges`/`ProcessMergeRequestsJob` was enqueued for `victim_stack`, even though the payload's `repository.full_name` never equals `victim_stack.repository.full_name` — proving `payload.repository.full_name == commit.stack.repository.full_name` is false yet the mutation still occurred.
