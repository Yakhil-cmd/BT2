### Title
RAY-scaled market value overflow permanently freezes all market operations - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
An unprivileged user can drive a sufficiently large, high-utilization market to an `i128` overflow during compulsory interest accrual, permanently preventing repayment, withdrawal, liquidation, and index updates. The repository’s own long-horizon test demonstrates this cliff before the borrow-index cap engages. [1](#0-0) 

### Finding Description
Every mutating pool operation loads the market and runs `interest::global_sync` before applying the requested action. [2](#0-1)  Each accrual step first computes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`, so it must reconstruct the full RAY-denominated market value even when the caller requests a trivial repayment or withdrawal. [3](#0-2)  `scaled_to_original` delegates to `Ray::mul`, which uses checked `i128` multiply-divide arithmetic and panics with `MathOverflow` when the result does not fit. [4](#0-3) [5](#0-4) [6](#0-5) 

The borrow index is only capped after multiplying the old index by the interest factor. [7](#0-6)  Consequently, a market can reach a state where the stored scaled totals and stored indexes are individually valid, but their product exceeds `i128::MAX`; the next accrual panics before it can update either index. [8](#0-7)  The controller’s permissionless `update_indexes` path authenticates only the caller and then invokes pool accrual, so any user can trigger the transition once time and utilization have produced the overflow condition. [9](#0-8) [10](#0-9) 

The long-horizon test constructs a one-billion-whole-token, 18-decimal market at 98% utilization and repeatedly calls `update_indexes`; it observes `MathOverflow`, confirms the borrow index remains below `MAX_BORROW_INDEX_RAY`, and confirms that subsequent `withdraw` and `repay` calls fail with the same error. [1](#0-0) 

### Impact Explanation
This permanently freezes the affected market’s funds: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot execute a market operation that accrues first, and keepers cannot repair the state through `update_indexes`. [2](#0-1) [11](#0-10)  Because the panic occurs during accrual before the requested mutation, even minimal emergency withdrawals or repayments cannot avoid it. [8](#0-7)  Pool mutations are controller-mediated and pool entrypoints are owner-only, so users also cannot bypass the controller to interact with the frozen market directly. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The trigger requires a very large admitted market position and sustained high utilization, so it is not reachable on arbitrary small markets. However, it uses only ordinary `supply`, `borrow`, and `update_indexes` actions; the demonstrated configuration uses admitted accounting values and fails before the configured index ceiling. [14](#0-13)  The issue is therefore a genuine boundary-condition denial of service rather than speculative memory corruption, but the capital and utilization prerequisites make Medium severity more appropriate than High.

### Recommendation
Make accrual saturation-safe before reconstructing or multiplying total values:

- Clamp `borrow_index` and `supply_index` without evaluating products that can exceed `i128`.
- Store or compute accrual deltas using widened arithmetic, then bound persisted `i128` values before conversion.
- Add a total-value ceiling check when minting supply or debt so `scaled * index` can never exceed `i128::MAX`.
- At minimum, handle `scaled_to_original` overflow in `accrue_step` by clamping affected totals/indexes to their supported ceilings rather than panicking.
- Add regression coverage for repayment, withdrawal, liquidation, recapitalization, and `update_indexes` after the demonstrated cliff.

The affected conversion and accrual logic is in `common/src/rates/scaling.rs`, `common/src/rates/simulate.rs`, and `contracts/pool/src/interest.rs`. [15](#0-14) 

### Proof of Concept
The existing repository test demonstrates the complete user-reachable path:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() {
        break;
    }
}

assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The test’s assertions show that `try_update_indexes_for` fails first, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`; later withdrawals and repayments fail identically because they rerun accrual. [1](#0-0)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }

    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"

    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    while let Some(nonzero) = NonZeroU64::new(remaining) {

        remaining = remaining.saturating_sub(chunk);

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
