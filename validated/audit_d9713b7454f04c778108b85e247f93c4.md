### Title
`review_stacks_enabled` fails to gate stack creation/unarchival in `OpenedHandler#provision?` due to `&&`/`||` precedence - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`LabeledHandler#respond_to_label_change?` correctly requires `repository.review_stacks_enabled` as an unconditional top-level `&&` term gating every code path, but `OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) writes the same intended condition with a Ruby operator-precedence bug: because `&&` binds tighter than `||`, `review_stacks_enabled` only guards the `allow_all?` branch, not the `allow_with_label?`/`prevent_with_label?` branches. This lets an attacker who can label/open their own PR trigger stack creation and provisioning on a repository where an administrator has explicitly disabled review stacks (`review_stacks_enabled=false`).

### Finding Description
The claimed binding is: `review_stacks_enabled == false` implies `Stack.count` unchanged, for both `LabeledHandler` and `OpenedHandler`, given identical `provisioning_behavior`/label state.

`LabeledHandler#respond_to_label_change?` (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:78-83`) is a flat conjunction:
```ruby
params.action == "labeled" &&
  pull_request_state == "open" &&
  repository.review_stacks_enabled &&
  (archive? || unarchive?)
```
Here `review_stacks_enabled` unconditionally gates the whole method — if it's `false`, the method always returns `false`, and `handle` (which calls `stack.archive!`/`stack.unarchive!`) never runs. [1](#0-0) 

`OpenedHandler#provision?` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`) is written with the same visual shape but different grouping:
```ruby
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Because `&&` has higher precedence than `||` in Ruby, this actually parses as:
```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`review_stacks_enabled` only participates in the first disjunct. If `provisioning_behavior` is `allow_with_label` and the PR carries the provisioning label (or `prevent_with_label` and it doesn't), `provision?` returns `true` regardless of `review_stacks_enabled`. [2](#0-1) 

`respond_to_pull_request_opened?` gates `process` solely on `params.action == "opened" && provision?` — there is no separate, unconditional `review_stacks_enabled` check anywhere else in the call path. [3](#0-2)  `ReviewStackAdapter#find_or_create!` then creates a `Stack`, builds the `pull_request`, and adds the stack to `Shipit::ReviewStackProvisioningQueue`, which triggers provisioning tasks. [4](#0-3) 

The identical bug pattern exists in `ReopenedHandler#unarchive?`, which unarchives/re-provisions an existing stack under the same false condition. [5](#0-4) 

Attacker request: on a repository configured with `review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, `provisioning_label_name = "pull-requests-label"`, the attacker (owner of the PR/fork) opens a PR carrying that label, or adds the label to an existing open PR and then closes/reopens it (to hit the `reopened` webhook path), producing a GitHub `pull_request` `opened`/`reopened` webhook. No existing guard (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) checks this business-logic condition — they validate payload shape and webhook authenticity, not the `review_stacks_enabled` semantics, so they don't prevent the divergence.

### Impact Explanation
The repository's own explicit `review_stacks_enabled = false` setting is meant to disable all automatic stack creation, but is silently bypassed for the `opened`/`reopened` entry points when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`. This results in a `Shipit::Stack`/`ReviewStack` being created and queued for provisioning (which runs deploy-spec-defined tasks) despite the repository administrator having disabled the feature. The blast radius is confined to the single repository whose config is misapplied (not cross-tenant), but it results in unauthorized stack provisioning/task execution that the operator explicitly turned off, matching "unauthorized deploy" under the Critical bucket for that repository.

### Likelihood Explanation
Requires: `review_stacks_enabled=false` AND `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible transitional/misconfiguration state, e.g., operator disables review stacks temporarily but leaves behavior config intact) AND the attacker able to open/label a PR against that repository (which they can do on their own fork per the threat model). Cost is a single GitHub PR action; fully repeatable per webhook delivery.

### Recommendation
Add explicit parentheses in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates the entire expression, matching `LabeledHandler`/`UnlabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.
