The premise is technically incoherent and does not match the actual code. `types/src/bytes.rs` contains only a trivial serialization helper `NumToBytes::le_bytes` that calls `u64::to_le_bytes()` — it performs no arithmetic, has no wraparound logic, and cannot make an arbitrary sequence number "alias" to zero's byte representation. [1](#0-0) 

The actual sequence-number gating logic never relies on byte encoding or wraparound arithmetic at all:

- Mempool's `transaction_store.rs` rejects a transaction outright if its sequence number is `<` the account's current sequence number (a plain `u64` comparison), and any u64 value literally equal to 0 cannot alias to a different value via `le_bytes()`. [2](#0-1) 
- The AptosVM prologue (`transaction_validation.move`) explicitly bounds the sequence number below `1u64 << 63` and then requires strict equality `txn_sequence_number == account_sequence_number` against the on-chain sequence number, rejecting both too-old and too-new values before matching. [3](#0-2) 

There is no `u64::MAX + 1` wraparound path in either check — both compare the plain numeric value, not a byte-encoded or modular representation, so an attacker cannot craft a stale sequence number that "wraps" to equal the current expected value. The scenario described conflates the `NumToBytes` serialization helper (used purely for byte-encoding numbers, e.g., for BCS/hashing purposes) with the actual admission-time integer comparisons, which is not how the code operates.
