## Confirmed: multi-org configuration confirms the analog

This confirms the exploit path in a multi-org deployment (`secrets.github` keyed by organization names, as shown in `test/dummy/config/secrets_double_github_app.yml`). `Shipit.github(organization:)` picks a distinct `GitHubApp` instance (and thus a distinct `webhook_secret`) per organization key [1](#0-0) .

### Title
Webhook signature verified against organization-derived key while state-changing handlers act on an unrelated `repository.full_name` field from the same unverified payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to check the HMAC signature against based on `repository_owner`, a field read straight out of the still-unverified JSON body [2](#0-1) [3](#0-2) . Once the signature "passes," every handler (`PushHandler`, `PullRequest::*`, `StatusHandler`, `MembershipHandler`, etc.) resolves the target repository/stack using a *different* field of that same payload, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing cross-checks that `repository.owner.login` (used to select/verify the signing key) matches `repository.full_name`'s owner (used to select the affected stack). This is the same "binding broken by using a field that is set/derived after — or independently of — the value that was actually verified" pattern as the `DOMAIN_SEPARATOR`/`name` bug: the verified key selector and the acted-upon identifier are logically supposed to be the same organization, but the code never enforces that equality.

### Finding Description
In a multi-tenant Shipit deployment (`secrets.github` keyed by org, e.g. `OrgOne` / `OrgTwo` as in `test/dummy/config/secrets_double_github_app.yml`), each organization key maps to its own `GitHubApp` and `webhook_secret` [6](#0-5) . `WebhooksController#verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the app/secret used for `verify_webhook_signature` [7](#0-6) . For any org whose `webhook_secret` is left blank (a documented and exampled configuration state — see `webhook_secret: # nil` in every shipped secrets template, e.g. `test/dummy/config/secrets_double_github_app.yml` lines 7 and 46), `GitHubApp#verify_webhook_signature` returns `true` unconditionally: `return true unless webhook_secret` [8](#0-7) .

An unprivileged, unauthenticated attacker (no session, no token, no secret) can therefore craft a raw webhook POST where `repository.owner.login` (or `organization.login`) is set to the org with no configured secret, causing `verify_signature` to pass trivially — while `repository.full_name` inside the same JSON body is set to `"OtherOrg/critical-repo"`, an entirely different organization/repository that does have real protections configured. `create` then dispatches unconditionally to all registered handlers for the event with the raw, already-"verified" params [9](#0-8) . Every handler resolves its target using `repository.full_name`, not `repository.owner.login`: `PushHandler` enqueues `stack.sync_github(expected_head_sha: params.after)` for any stack matching that repo/branch [10](#0-9) , `PullRequest::OpenedHandler`/`LabeledHandler`/`ClosedHandler` archive/unarchive/create review stacks for that repo [11](#0-10) , and `MembershipHandler` creates users/teams. None of these paths validate that the org used for signature verification equals the org embedded in `repository.full_name`.

### Impact Explanation
This breaks the intended binding "organization whose signature was verified == repository actually written to." An attacker with zero credentials can forge push/pull_request/membership/status events attributed to a repository under a *different*, properly-secured organization, as long as at least one configured org has no `webhook_secret` (a state the shipped example configs explicitly ship as the default/nil value). Consequences include forcing `GithubSyncJob` to sync a stack to an attacker-chosen `expected_head_sha`, forging PR-driven stack archive/unarchive/provisioning actions, and injecting fabricated commit statuses — all without ever needing a `webhook_secret`, `ApiClient` token, or GitHub session, i.e., an unauthorized write/deploy-adjacent action performed cross-repository.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with `webhook_secret` unset. Both are directly reflected in the engine's own shipped example/dummy configs (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) which default `webhook_secret` to nil per-org, so this is not a contrived operator error the engine goes out of its way to discourage — it is the documented default shape for at least one org slot. No attacker credential, session, or secret is required, matching the "unprivileged attacker" bar.

### Recommendation
After determining the app/secret to verify against via `repository_owner`, cross-validate that the same organization also owns `repository.full_name` before dispatching to handlers (or resolve the target stack strictly from the verified organization rather than trusting an independent field of the same unverified payload). Additionally, consider treating a missing `webhook_secret` for any configured organization as a hard misconfiguration (reject events) rather than an automatic pass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `OrgSecure` (has `webhook_secret` set, owns a protected `Stack`) and `OrgOpen` (no `webhook_secret` configured), per the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. As an anonymous attacker, POST to `/github_authentication`-unauthenticated webhook endpoint (mounted webhook route) with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "full_name": "OrgSecure/protected-repo",
    "owner": { "login": "OrgOpen" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgOpen")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the signature header supplied [12](#0-11) .
4. `PushHandler` resolves the target via `repository.full_name` = `"OrgSecure/protected-repo"` [13](#0-12)  and enqueues `sync_github(expected_head_sha: "<attacker_chosen_sha>")` for the matching stack under `OrgSecure` [10](#0-9) , despite the request never being validated against `OrgSecure`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
