### Title
`update_account_threshold` restamps `loan_to_value` unconditionally while the liquidation tuple is gated, letting any caller force a lower LTV onto any account with no health-factor check - (File: contracts/controller/src/risk/params.rs)

### Summary
The external report describes a coupled-parameter update that moves one bound (start time) but not the dependent bound (end time), producing an inconsistent state that benefits the actor at users' expense. The same shape exists in `update_account_threshold`: a permissionless entrypoint that restamps a position's cached `loan_to_value` from current config while the liquidation tuple (`liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`) is either skipped entirely (`LtvOnly`) or gated behind a health-factor check (`FullTuple`). Any unprivileged caller can therefore force a *partial* parameter update onto arbitrary accounts — exactly the "move one bound, leave the other" asymmetry of `rescheduleGame`.

### Finding Description
`refresh_supply_risk_params` applies `loan_to_value` unconditionally at `params.rs:35` and only conditionally applies the liquidation tuple via `apply_gated_liquidation_params` (`params.rs:36-38`, `68-93`). The tuple is skipped whenever the new config `favors_liquidator` (lower threshold, higher bonus, or lower fees — `params.rs:96-100`) and the account's hypothetical HF is below `THRESHOLD_UPDATE_MIN_HF_RAW` (1.05, `params.rs:103-119`).

Two unprivileged exploitation paths exist through `update_account_threshold(caller, has_risks, account_ids)` (`params.rs:124-144`), which only requires `require_authorized_caller` (any authenticated address):

1. `has_risks = false` (`RiskRefreshScope::LtvOnly`): the liquidation tuple is never touched and the final HF assertion at `params.rs:221-234` is skipped entirely. The caller picks which accounts and which scope — the account owner has no say.
2. `has_risks = true` (`FullTuple`): LTV still moves at `params.rs:35` even when `apply_gated_liquidation_params` returns early because the gate rejected the tuple. The unit test `refresh_writes_ltv_but_holds_tuple_when_gate_rejects` (contracts/controller/tests/risk/params.rs:202-280) confirms this asymmetry is real: LTV rides outside the gate while threshold/bonus/fees hold their stamped vintage.

Once a governance listing change reduces an asset's `loan_to_value`, any third party can call `update_account_threshold(attacker, false, [victim_ids])` and permanently stamp the lower LTV onto victims' supply positions. There is no path to restore a higher LTV — restamps only ever write current config (`restamp_listed_supply_ltv` at `params.rs:44-64` skips positions already matching config, never the reverse), and the stamped LTV is what the borrow path uses to compute `min_borrow_collateral_usd` / borrowing capacity per account.

This mirrors the report's mechanism: the "end time" analogue (the liquidation tuple meant to move together with the risk config) is deliberately held while the "start time" analogue (LTV) is pushed through, and the trigger is callable by any address on any account.

### Impact Explanation
Medium. A forced lower LTV stamp freezes part of the victim's borrowing capacity: the account can no longer open or increase borrows against that collateral up to the config's intended-not-gated terms until (if ever) governance raises LTV again. For positions near their borrow limit that depend on drawing additional credit to manage the position (e.g., `swap_debt`, `multiply`, or refinancing during volatility), this constitutes temporary freezing of the position's usable collateral value — the same "users can't participate while the actor benefits" shape as the report, though here the benefit is griefing / capacity denial rather than direct fee theft. Note LTV does not drive liquidation HF (the threshold does), so victims are not pushed into liquidation by this alone; the impact is capacity denial, not insolvency.

### Likelihood Explanation
Requires a governance listing change that lowers an asset's `loan_to_value` — a routine and expected parameter update. Once such a change is queued, the attack is a single permissionless call; `has_risks=false` carries no HF check and no per-account authorization. Any address can grief any set of account IDs in one transaction.

### Recommendation
Couple the updates: apply `loan_to_value` only when the liquidation tuple is also applied (or, for `LtvOnly`, restrict the entrypoint to the account owner/delegate via `require_owner_or_delegate` as in `process_withdraw` at contracts/controller/src/positions/supply.rs:150). Alternatively, when a config change lowers LTV, enforce the same `THRESHOLD_UPDATE_MIN_HF_RAW`-style gate on the LTV leg so a partial restamp cannot be forced onto accounts that would be harmed by it. The cleanest fix matching the report's mitigation is to treat LTV and the liquidation tuple as one unit that either fully restamps or fully holds.

### Proof of Concept
1. Governance executes a listing update lowering `USDC.loan_to_value` from 8_000 to 5_000 (and e.g. raising `liquidation_bonus`, so the tuple "favors liquidator").
2. Attacker (any address) calls `Controller::update_account_threshold(attacker, false, [victim_account_id])` — or `true` on a victim whose HF < 1.05.
3. `refresh_supply_risk_params` writes `loan_to_value = 5_000` on the victim's USDC supply position (`params.rs:35`); the tuple gate either is skipped (`LtvOnly`) or returns early (`params.rs:76-88`).
4. The victim's borrow capacity against USDC is permanently reduced to the new LTV; no subsequent call can restore 8_000, and the victim never authorized the restamp.

Corroborated by the existing unit test `refresh_writes_ltv_but_holds_tuple_when_gate_rejects` showing LTV moves while the tuple holds, and by `update_account_threshold`'s lack of per-account authorization (`params.rs:124-130`).
