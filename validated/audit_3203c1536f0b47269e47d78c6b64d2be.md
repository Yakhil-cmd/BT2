### Title
Asset issuer can retroactively strip "spender_attested" whitelist status from existing holders, permanently freezing their tokens - (File: `storage.js`, `validation.js`)

### Summary
Assets in ocore can be created with `spender_attested: true`, which restricts who may hold/transfer the asset to addresses attested by a trusted attestor list. The asset definer can update this attestor whitelist at any time via an `asset_attestors` message. `storage.readAsset()` always uses the *latest* attestor list unit rather than the list that was valid when a holder acquired the asset [1](#0-0) . Validation of both outgoing outputs and incoming inputs checks attestation against this current list [2](#0-1) [3](#0-2) . If the definer removes an address (or the attestor that vouched for it) from the whitelist after that address has already received the asset, the holder can no longer spend/transfer (or even receive further transfers of) those tokens — they become permanently stuck, mirroring the "Tokens might be stuck in the contract" bug class from the external report.

### Finding Description
When an asset is defined with `spender_attested: true`, an `attestors` list is required [4](#0-3) . This attestor list is not immutable: the definer can publish a new `asset_attestors` message for the same asset to update it, and `readAsset` always fetches the single most-recent `asset_attestors` unit for that asset (`ORDER BY level DESC LIMIT 1`), fully replacing the previous list rather than merging with it [5](#0-4) .

When validating a payment, `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` compute `arrAttestedAddresses` by checking which addresses have an `attestation` from one of the *current* `arrAttestorAddresses` [6](#0-5) . This list is then used to gate:
- the issuer/author of the payment (must be attested to issue or spend) [2](#0-1) ,
- every input's owner address, which must appear in `arrAttestedAddresses` or the input is rejected with `"owner address is not attested"` [3](#0-2) ,
- every output address, which must all be attested or the payment is rejected with `"some output addresses are not attested"` [7](#0-6) .

Because the check always uses the current whitelist (not the one valid at the time the tokens were received), a definer publishing a new `asset_attestors` list that drops a previously-attested address (or drops the attestor who vouched for it) makes that address's existing balance of the asset permanently unspendable: any attempt to include it as an input is rejected during validation, so the holder can never move, redeem, or trade those tokens again. This is directly analogous to the reported vulnerability, where removing an entry from a whitelist blocks operations (there, redemption; here, any future transfer) on already-held balances, with no fallback path or grace period for existing holders.

### Impact Explanation
This is a High severity fund-freezing issue: a single-authored `asset_attestors` unit from the asset definer (an unprivileged action reachable by any asset issuer, not a hub/witness/operator) can retroactively lock any current holder's balance of that asset. Funds are not stolen but are permanently frozen — the holder has no way to spend, transfer or destroy their coins, matching the "AA fund loss or freezing" acceptance criterion, since assets are frequently used as collateral/backing inside AAs and private payment chains.

### Likelihood Explanation
Likelihood is straightforward: any address that defines an asset with `spender_attested: true` inherently has the unilateral ability to publish subsequent `asset_attestors` messages (validated only for well-formedness, not for protecting existing holders) [8](#0-7) . No special network position or malicious peer/hub behavior is required — this is a normal, protocol-sanctioned action by the asset issuer, so the scenario can be triggered at will.

### Recommendation
When validating inputs (spending) of an existing balance, evaluate attestation against the attestor list that was current at the time the output being spent was created (similar to how other historical conditions are evaluated against `last_ball_mci`), rather than always against the latest `asset_attestors` list. Alternatively, allow holders whose attestation was valid at receipt time to still spend/redeem their existing balance (e.g., moving it back to the definer or burning it) even after being removed from the current whitelist, so that a definer-driven whitelist update cannot strand already-issued balances.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and `attestors: [X]`.
2. Attestor `X` attests address `Alice`; Alice receives a payment of asset `A` (validated fine, since `Alice` is in `arrAttestedAddresses` computed from attestor `X`) [2](#0-1) .
3. Definer publishes a new `asset_attestors` message for asset `A` with `attestors: [Y]` (removing `X`). `storage.readAsset` now returns `arrAttestorAddresses = [Y]` as the only valid attestor set going forward [9](#0-8) .
4. Alice attempts to spend her previously received `A` tokens. `filterAttestedAddresses` no longer finds Alice attested (her attestation came from `X`, not `Y`), so `arrAttestedAddresses` excludes her [10](#0-9) .
5. `validatePaymentInputsAndOutputs` rejects the input with `"owner address is not attested"`, because `objAsset.arrAttestedAddresses.indexOf(owner_address) === -1` [3](#0-2) . Alice's balance of asset `A` is now permanently frozen.
