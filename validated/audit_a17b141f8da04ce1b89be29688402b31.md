Let me verify how `appeal_approved`/`appeal_declined` status is consumed downstream to see if it triggers fund movement or role reassignment without further checks, and check `setField`/`getByHash` for completeness before finalizing.### Title
Field-based status-transition check in `arbiter_contract_update` allows a low-privilege cosigner/peer to smuggle unauthorized contract state changes past the per-field OR-composed authorization gate - ([File: wallet.js])

### Summary
`wallet.js`'s `arbiter_contract_update` handler mirrors the Wekan `sort`-field bug class: authorization for a *whole message* is decided by inspecting a single, narrow field name (`body.field === "status"`), and the "who is allowed to send this" check is itself an OR-composition of three independent conditions (peer, cosigner, or arbstore-in-appeal) rather than a single unambiguous authority check tied to the actual state transition being requested. [2](#0-1) 

### Finding Description
The handler first computes `from_cosigner` from a DB join, then gates the whole request with:
```
if (from_address !== objContract.peer_device_address && !from_cosigner &&
    !(from_address === objContract.arbstore_device_address && objContract.status === 'in_appeal' && body.field === 'status'))
    return callbacks.ifError("not an owner");
``` [3](#0-2) 

This is an OR of three disjoint authorities (contract peer, cosigner, arbstore-in-appeal) — structurally identical to Meteor's OR-combined `allow` rules in the Wekan advisory, where a narrow rule meant to authorize one specific field ends up granting broader trust because the composition is evaluated independently of the actual full effect of the update. Once this gate passes, a `switch(objContract.status)` determines which `body.value` is acceptable for `body.field === "status"`:
```
case "in_appeal":
    if (objContract.arbstore_device_address === from_address && (body.value === 'appeal_approved' || body.value === 'appeal_declined'))
        isOK = true;
``` [4](#0-3) 

The critical weakness is that `isOK` is derived purely from `objContract.status` (a value read from the *local* `wallet_arbiter_contracts` table) and `from_address`, but the state machine does not re-validate that the full set of preconditions for a legitimate arbstore decision (e.g., that a real dispute/appeal was actually escalated through the correct multi-party flow, that `shared_address`/`unit` are already consistent, and that the contract counterpart agreed to arbitration) holds atomically with the `status` field update. Once `isOK` is true, `arbiter_contract.setField` is called generically for *any* field name that reached this point:
```
arbiter_contract.setField(objContract.hash, body.field, body.value, function(objContract) {
    eventBus.emit("arbiter_contract_update", objContract, body.field, body.value);
    callbacks.ifOk();
}, from_cosigner);
``` [5](#0-4) 

`setField` itself only checks that the field name belongs to an allow-list, not that the caller is authorized for that specific field/value combination — that responsibility is pushed entirely back onto the caller's OR-gated check in `wallet.js`:
```
function setField(hash, field, value, cb, skipSharing) {
	if (!["status", "shared_address", "unit", "my_contact_info", "peer_contact_info", "peer_pairing_code", "resolution_unit", "cosigners"].includes(field)) {
		throw new Error("wrong field for setField method");
	}
	db.query("UPDATE wallet_arbiter_contracts SET " + field + "=? WHERE hash=?", [value, hash], ...);
``` [6](#0-5) 

Because `store()` accepts and persists an attacker-influenced `status` directly from a cosigner-flagged message (`const status = bFromCosigner ? (objContract.status || status_PENDING) : status_PENDING;`), a device that can get itself flagged as `me_is_cosigner` (via the separately-reachable `arbiter_contract_shared` message, which only requires that `body.my_address` be one of *any* of the recipient's own addresses joined to a wallet signing path — not that the recipient actually agreed to be a cosigner of this specific contract) can pre-seed local contract state, then use the narrow, OR-gated `status`-field rule to push the contract through `pending → accepted` or `dispute_resolved → in_appeal` transitions that should require the genuine counterparty's/arbiter's consent. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who can pair with (or is a legitimate but low-trust cosigner of) an arbiter-contract shared address can manipulate the locally-stored contract status/fields (`shared_address`, `unit`, `resolution_unit`, `cosigners`) through the same generic `setField` sink used for legitimate transitions. Since `shared_address` and `unit` values ultimately drive fund release decisions in the arbitration flow (`handleReceivedSharedAddress`, `handleReceivedSigningUnit`), an attacker able to inject a crafted `status`/`unit`/`shared_address` combination that does not correspond to a real, fully-executed arbitration outcome could mislead a peer's wallet UI into treating a contract as resolved/appealed/signed, potentially leading to fund loss or a frozen dispute for the legitimate parties. This matches the "AA fund loss or freezing" / unauthorized state-change impact class analogous to the Wekan CVE's board takeover.

### Likelihood Explanation
Reaching this code path only requires a paired device that can either (a) be the `peer_device_address` of a contract, (b) get itself recorded as `me_is_cosigner` via the loosely-checked `arbiter_contract_shared` message (checking only that the claimed `my_address` is present in the recipient's own `my_addresses`/`wallet_signing_paths`, not that it was actually designated as a co-signer for this specific contract by its owner), or (c) is legitimately the arbstore device but with a state machine that trusts local, potentially-manipulated `objContract.status`. This is reachable purely through the paired-device messaging layer without needing hub/node compromise.

### Recommendation
Redesign the authorization for `arbiter_contract_update` to avoid single-field OR-gated checks: verify the complete, cryptographically-anchored state transition (e.g., require the actual signed unit / shared-address derivation to match before accepting a `status` change, as is partially done for `unit`/`shared_address` but not for `status`), and tighten `arbiter_contract_shared` to only accept co-signer claims that are cryptographically tied to an existing contract offer, not a broad "my_address is one of my addresses" check.

### Proof of Concept
1. Attacker device pairs with victim and sends `arbiter_contract_shared` for a contract hash it knows/observed, with `me_is_payer` flipped, claiming `my_address` = one of the victim's already-shared wallet addresses; `store()` inserts the contract with `me_is_cosigner=1` because only wallet/signing-path membership is checked, not per-contract cosigner authorization [8](#0-7) .
2. Attacker then sends `arbiter_contract_update` with `body.field = "status"`, `body.value = "accepted"` while `objContract.status === "pending"`; because `from_cosigner` is now true, `isOK` becomes true under `case "pending": if (... from_cosigner && ["accepted","declined"].includes(body.value)) isOK = true;` [9](#0-8) .
3. `arbiter_contract.setField` unconditionally persists the new status and re-shares it to other cosigners via `shareUpdateToCosigners`, propagating the unauthorized state change into the arbitration workflow [6](#0-5) .
