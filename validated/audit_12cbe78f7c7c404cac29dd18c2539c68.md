### Title
Webhook organization used for signature verification is decoupled from the organization whose repository is mutated - ([File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`WebhooksController#verify_signature` selects a GitHub App/secret using `params.dig('repository','owner','login')`, while `LabelCapturingHandler#repository` (and every other `pull_request` handler) resolves the mutated `Shipit::Repository` using `params.repository.full_name` — a completely separate JSON field. Nothing in the code enforces that the org named in `repository.owner.login` matches the org embedded in `repository.full_name`, and if the org picked for verification has no configured `webhook_secret` (a legitimate, documented Shipit configuration state), verification is a no-op, letting an unauthenticated caller freely choose `repository.full_name` to point at any other, unrelated repository in the Shipit database.

### Finding Description
The broken binding, stated as an equality that the code never checks:

`org(params.dig('repository','owner','login'))` (used in `Shipit.github(organization: repository_owner)` for signature verification) **must equal** `org(params.repository.full_name.split('/').first)` (used in `Shipit::Repository.from_github_repo_name` to pick the repository that gets mutated).

Code path:
- `app/controllers/shipit/webhooks_controller.rb` `repository_owner` reads only `params.dig('repository','owner','login')` [1](#0-0) , and `verify_signature` uses it solely to pick which `GitHubApp`/secret to check the signature against [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's config has no `webhook_secret` set: `return true unless webhook_secret` [3](#0-2) . An unconfigured `webhook_secret` is the documented default in every example config (`config/secrets.development.example.yml`, `docs/setup.md`'s multi-org example, and the test fixture `test/dummy/config/secrets_double_github_app.yml`, all of which show `webhook_secret: # nil`) [4](#0-3) [5](#0-4) .
- Once past `verify_signature`, `LabelCapturingHandler#repository` resolves the repository purely from the attacker-controlled `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , and `Repository.from_github_repo_name` does an unscoped, global `find_by(owner:, name:)` lookup with no relation to the org that was checked in `verify_signature` [7](#0-6) .
- `stack` and `capture_labels` then mutate whatever `ReviewStack`/`PullRequest` belongs to that resolved repository, including flipping label-driven behavior gated by `stack.archived?` [8](#0-7) .

Exploit: an attacker crafts a raw JSON POST directly to `/webhooks` (not via real GitHub) with `X-Github-Event: pull_request`, sets `repository.owner.login` to any org name that Shipit has configured without a `webhook_secret` (a state the operator may have set intentionally for a low-priority/test org, or which is simply the shipped default), and sets `repository.full_name` to `victim-org/victim-repo`. `verify_signature` passes unconditionally (no secret exists to check against), `drop_unhandled_event` and `check_if_ping` don't interfere, and `LabelCapturingHandler` (as well as `OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `ClosedHandler`, all following the identical `params.repository.full_name` pattern) resolves and mutates the victim repository's stack/PR state.

Existing guards fail to prevent this: `verify_signature` never cross-checks `repository.full_name`; `ExplicitParameters` schemas for these handlers only require `repository.full_name` to be a String, with no organizational consistency constraint; `Repository.from_github_repo_name` performs a global, unscoped lookup.

### Impact Explanation
An unauthenticated request can mutate `PullRequest#labels` and, via the `capture_labels?`/`archived?` gating logic, influence review-stack provisioning/archival state for a repository the attacker never authenticated against — a payload nominally "from" one (weakly configured or secret-less) organization mutates a different organization's stack. This matches the listed Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is fully repeatable against any repository registered in the Shipit `Repository` table, and the blast radius spans every tenant/org hosted by the same Shipit instance, not just the attacker's own repo.

### Likelihood Explanation
Requires only that: (1) the Shipit deployment hosts more than one GitHub org's repositories (documented, supported use case), and (2) at least one configured org's `webhook_secret` is left unset — which is the shipped default in every example/config file in this repo. No GitHub App private key, `webhook_secret`, session, or API token is needed; the attacker simply POSTs directly to `/webhooks`. This is low-cost and fully repeatable.

### Recommendation
Enforce that the organization used to verify the webhook signature matches the organization portion of `repository.full_name` (and of `organization.login` for org-level events) before any handler runs; reject requests where they diverge. Additionally, require `webhook_secret` to be present for every configured org (fail closed instead of returning `true` when absent), and consider scoping `Repository.from_github_repo_name` lookups by the verified organization.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` or a new test):
1. Configure `Shipit.stubs(:secrets)` (or use `test/dummy/config/secrets_double_github_app.yml`) with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret` set, unknown to the test's "attacker" path).
2. Create `victim_repo = shipit_repositories create(owner: 'victim-org', name: 'victim-repo')` with an existing `ReviewStack`/`PullRequest` fixture (not archived).
3. Build a `pull_request` `labeled` payload with `repository.owner.login = 'attacker-org'` and `repository.full_name = 'victim-org/victim-repo'`, and no valid `X-Hub-Signature` header (or an arbitrary bogus one).
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert `response.status` is `200`/`204` (not `422`), proving `verify_signature` passed without any secret.
6. Assert that `victim_repo.stacks.last.pull_request.reload.labels` changed to reflect the attacker's payload — i.e., `PullRequest#labels` was mutated even though `repository.owner.login` ("attacker-org") does not match the org portion of `repository.full_name` ("victim-org").
7. Contrast with the expected safe behavior: assert this update should NOT occur unless `org(repository.owner.login) == org(repository.full_name)`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
