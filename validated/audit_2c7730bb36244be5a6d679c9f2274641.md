### Title
Node crash / stability-disagreement from partially-initialized unit props exposed via `assocUnstableUnits` before `level`/`witnessed_level` are computed - ([File: writer.js])

### Summary
`writer.js`'s `saveJoint()` synchronously inserts a brand-new, only partially-populated unit-props object into the global in-memory lookup `storage.assocUnstableUnits` before the fields required by every stability/inclusion algorithm (`level`, `witnessed_level`) are actually computed. This mirrors the TIPC bug class: an object is made visible in a shared lookup table before a required sub-component is initialized, so a concurrent consumer that finds the object via the table dereferences the missing field.

### Finding Description
In `writer.js`, `objNewUnitProps` is built with `level: bGenesis ? 0 : null` and `witnessed_level: bGenesis ? 0 : (conf.bFaster ? objValidationState.witnessed_level : null)` [1](#0-0) , and this object is immediately published into the shared cache with `storage.assocUnstableUnits[objUnit.unit] = objNewUnitProps;` [2](#0-1) .

The real `level` and `witnessed_level` values are only filled in later, after further asynchronous DB round-trips (`addInlinePaymentQueries`, `async.series(arrQueries)`), via the `updateLevel`/`updateWitnessedLevel` operations pushed onto `arrOps` [3](#0-2) . Between the synchronous insertion and the completion of these ops there is an event-loop window during which other asynchronous work (e.g. validation of a different, concurrently-arriving unit) can execute and read this same cache entry.

Multiple hot paths trust `assocUnstableUnits`/`assocStableUnits` blindly when `conf.bFaster` is set, without going back to the DB: `storage.readUnitProps()` returns the cached object directly `if (conf.bFaster && assocUnstableUnits[unit]) return handleProps(assocUnstableUnits[unit]);` [4](#0-3) , and `storage.readPropsOfUnits()` does the same `if (conf.bFaster && objEarlierUnitProps2 && arrLaterUnitProps2.every(...)) return handleProps(...)` [5](#0-4) . These feed directly into `graph.determineIfIncluded()`, which computes `max_later_level`/`max_later_wl` by taking `.level`/`.witnessed_level` off of exactly these cached props and compares them against the earlier unit's fields [6](#0-5) , and into `main_chain.determineIfStableInLaterUnits()` which does the same comparisons [7](#0-6) .

Other traversal code explicitly treats a `null` level as a fatal condition, confirming this is a known-hazardous state: `storage.determineWitnessedLevelAndBestParent()` throws `"null level in updateWitnessedLevel"` if `level === null` [8](#0-7) , and `main_chain.findMinMcWitnessedLevel()` throws `"null level in findMinMcWitnessedLevel"` under the same condition [9](#0-8) . If instead the `null` reaches a numeric comparison (as in `graph.js`/`main_chain.js` above) rather than an explicit guard, JavaScript's coercion of `null` to `0` in `Math.max`/relational comparisons silently corrupts the stability/inclusion computation instead of throwing.

### Impact Explanation
Two concrete outcomes are reachable depending on which code path observes the transient state:
1. An explicit `throw Error("null level in ...")` crashes the validation/main-chain routine mid-flight on a node running with `conf.bFaster`, disrupting that node's ability to keep confirming/stabilizing units (network-availability style impact on that node) — directly analogous to the TIPC NULL-pointer crash triggered by the same class of premature cache publication.
2. Where the `null` is silently coerced to `0` in `Math.max`/comparison logic in `graph.determineIfIncluded()` or `main_chain.determineIfStableInLaterUnits()`, the inclusion/stability verdict for the affected unit can be computed incorrectly, causing this node to diverge from nodes that read the fully-computed on-disk values, i.e. a node disagreement on unit validity/stability.

### Likelihood Explanation
This requires `conf.bFaster` (a documented, supported performance mode) to be enabled so that the memory-only fast paths in `readUnitProps`/`readPropsOfUnits` are used instead of the DB round-trip that would otherwise cross-check/repopulate the fields. It also requires two units to be processed close together in time so that a second unit's read of `assocUnstableUnits` interleaves with the first unit's `saveJoint()` write-cache-then-populate-fields window — a timing condition that is plausible under normal network load rather than requiring an adversarial trigger, since ordinary unrelated unit traffic is enough to create the interleaving; no malicious peer/hub cooperation is needed.

### Recommendation
Populate `level` and `witnessed_level` (and any other field relied upon by inclusion/stability comparisons) on `objNewUnitProps` before it is published into `storage.assocUnstableUnits`, or otherwise ensure the object is not visible to `readUnitProps`/`readPropsOfUnits` fast paths until those async `updateLevel`/`updateWitnessedLevel` operations complete — mirroring the fix in the CVE-2022-49664 report, which moved the required initialization step ahead of the point where the object becomes reachable via the shared lookup structure.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires demonstrating the precise event-loop interleaving between `writer.js`'s `saveJoint()` (specifically the gap between line 597's cache insertion and the completion of `updateLevel`/`updateWitnessedLevel` in `arrOps`) and a concurrent call into `storage.readUnitProps`/`readPropsOfUnits`/`graph.determineIfIncluded` on a `conf.bFaster` node, which would need to be validated in a running/instrumented instance rather than through code inspection.
