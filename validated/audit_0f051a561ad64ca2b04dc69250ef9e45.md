### Title
Unvalidated swap routes can execute attacker-controlled contract code below the caller’s authorization and drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller swap strategies forward caller-supplied opaque `swap` bytes to the configured router after authorizing only the routed input transfer; the route may name unallowlisted third-party venues, and code reached through that route can attach additional token transfers from the caller to the caller’s authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
The swap-based entrypoints accept `Bytes`/`StrategySwap` data from the caller and eventually call `router.execute_strategy(controller, amount_in, swap)` without the controller decoding the embedded venue addresses or restricting them to an allowlist. [3](#0-2) [1](#0-0)   
The controller grants the router authority only for one exact `token_in.transfer(controller, router, amount_in)` invocation, but that grant does not constrain which contracts the router subsequently invokes from the opaque payload. [4](#0-3)   
Because Soroban records authorization as an invocation tree rather than as a flat “one transfer only” permission, contract code reached inside the route can call `token.transfer(victim, attacker, amount)` and have that call represented as a child of the victim’s strategy authorization. [5](#0-4)   
The repository’s hostile-route fixture demonstrates the concrete sequence: a route-selected contract invokes an unrelated token’s `transfer(victim, attacker, amount)`, simulation attaches that transfer under the victim’s `swap_collateral` authorization, and enforcing mode executes it when that poisoned tree is signed. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can steal arbitrary victim-held token balances unrelated to the supplied collateral and routed input amount. [8](#0-7)   
The loss is not bounded by `amount_in`, the route’s minimum output, or the controller’s final account-risk checks because the malicious transfer spends tokens directly from the victim’s wallet rather than controller-held strategy funds. [9](#0-8)   
The strategy can still return a valid output and satisfy the controller’s positive-output and solvency checks while the unrelated wallet transfer completes. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
Any unprivileged attacker who can cause a victim to submit or sign a poisoned route through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` can reach the behavior; the attacker does not need protocol privileges or control of the configured router. [12](#0-11) [13](#0-12)   
Simulation does not prevent the attack because it faithfully records the malicious transfer as a child authorization, and enforcing mode accepts that transfer once the poisoned tree is signed. [14](#0-13) [7](#0-6)   
Likelihood is constrained by the need for the victim to authorize the poisoned invocation tree, so this is primarily a route-signing/phishing path rather than an unauthenticated direct drain. [15](#0-14) 

### Recommendation
Do not treat opaque routes as executable templates beneath a caller’s root authorization. [1](#0-0)   
Restrict route venues to governance-approved contract addresses or decode and validate every route-selected contract before invocation; alternatively, isolate route execution so a route cannot induce token transfers requiring the end user’s authorization tree. [2](#0-1)   
At minimum, make the signed authorization tree contain only the expected strategy-root invocation and exact input transfer, and surface or reject any additional child token transfer before signing; an honest composed route should not add a child transfer under the caller’s authorization. [16](#0-15) 

### Proof of Concept
1. Victim holds collateral in `USDC` and an unrelated `wallet_token` balance. [17](#0-16) 
2. Attacker constructs a route whose selected venue is an attacker-controlled contract configured with `(victim, wallet_token, attacker, wallet_balance)`. [18](#0-17) 
3. The malicious venue’s `swap` function calls `wallet_token.transfer(victim, attacker, wallet_balance)`. [19](#0-18) 
4. Victim invokes `swap_collateral(alice, account_id, USDC, 5_000_USDC, ETH, malicious_route)`. [20](#0-19) 
5. Simulation records the unrelated wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [21](#0-20) 
6. If the victim signs that recorded tree, the transaction succeeds, the unrelated wallet balance moves to the attacker, and the strategy still deposits the expected swap output. [7](#0-6)

### INV-STRAT-01 — Controller router authority binds one input transfer

The controller authorizes one exact
`token_in.transfer(controller, configured_router, amount_in)` invocation,
without sub-invocations. This grants invocation authority, without a token
allowance.

The controller ignores the router's return value, rejects input-balance growth

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
