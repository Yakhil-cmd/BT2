### Title
Webhook signature verified against attacker's own organization while target repository is taken from unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) directly out of the still-unauthenticated JSON body, then verifies the raw body against that organization's `webhook_secret`. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the target `Repository`/`Stack` from a *different* field of the same untrusted body: `repository.full_name`. Nothing ties these two fields together, so an attacker who legitimately administers one GitHub organization/App onboarded to a shared Shipit instance (and therefore knows that org's own `webhook_secret`) can forge a signature that Shipit accepts, while pointing `repository.full_name` at a completely different, victim-owned stack.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository the payload actually mutates`. [1](#0-0) [2](#0-1) 
computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is read from `request.raw_post` before any signature has been verified, i.e. it is fully attacker-controlled. `Shipit.github(organization:)` looks up per-organization config (Shipit explicitly supports multiple GitHub orgs each with its own `app_id`/`webhook_secret`, as shown in `config/secrets.development.example.yml`), and `GitHubApp#verify_webhook_signature` performs a straightforward HMAC compare against that organization's secret: [4](#0-3) 

Meanwhile every webhook handler (`PushHandler`, status/check-suite handlers, pull-request handlers, etc.) determines which `Repository`/`Stack` to act on using a *separate* field of the same JSON body: [5](#0-4) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because the field used to pick the *signing secret* (`repository.owner.login`) and the field used to pick the *target repository* (`repository.full_name`) are independent, an attacker only needs to know **one** organization's `webhook_secret` to forge a validly-signed webhook body whose `repository.full_name` names an entirely different, victim stack. This is not a forwarded real GitHub webhook — the attacker crafts the whole JSON body themselves and POSTs it directly to the shared `/webhooks` endpoint, computing the HMAC with their own known secret.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the targeted repository whose branch matches — this is attacker-controlled (`params.ref`, `params.after`) and re-syncs commit history for a victim stack the attacker does not own. Other handlers (`status`, `check_suite`, pull-request handlers) similarly update commit statuses / provisioning / archiving state on the victim's stacks based on entirely attacker-forged content, since the request passed signature verification (using the attacker's own org secret). Because CI/status webhooks gate `Stack#trigger_deploy` and continuous-delivery scheduling in Shipit (deploy safety relies on commit statuses recorded from webhooks), forging commit statuses for a victim repository can be used to make an unsafe/unreviewed commit appear CI-green, enabling an unauthorized deploy to be triggered by the victim's own continuous-deployment configuration. This crosses the "unauthorized deploy" / "cross-repository writes" bar for Critical impact.

### Likelihood Explanation
Exploitability requires the attacker to have legitimate control of at least one organization/GitHub App configured in the same multi-tenant Shipit instance (a documented, supported configuration — see `config/secrets.development.example.yml` multi-org example) so that they know that org's `webhook_secret`, plus knowledge of the victim's `repository.full_name` (typically public information, e.g., `org/repo`). No GitHub, Shipit session, or API token access is required — only the ability to POST directly to the public `/webhooks` endpoint with a self-signed body. This is realistic for any shared/multi-tenant Shipit deployment.

### Recommendation
Bind signature verification to the exact repository being acted upon, not just its declared owner: after computing `repository_owner`, additionally verify that `params.dig('repository','full_name')` belongs to that same organization (e.g., `full_name.split('/').first == repository_owner`), or better, resolve the `github_app`/secret from the persisted `Repository`/`Stack` record (trusted config) rather than from attacker-supplied payload fields, and reject the webhook if the resolved app's organization does not match the owner encoded in `full_name`.

### Proof of Concept
Preconditions: Shipit instance configured with two organizations, `attacker-org` (attacker is an org admin, knows `webhook_secret_A`) and `victim-org` (has a Stack registered in the same Shipit instance).

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` themselves (they know `webhook_secret_A`).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature against `webhook_secret_A`.
5. `PushHandler#process` looks up stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "deadbeef...")` on the victim's stack — a write performed on a repository the attacker never authenticated for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
