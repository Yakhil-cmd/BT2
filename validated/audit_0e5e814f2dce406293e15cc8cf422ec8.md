Confirmed: there is no code anywhere in `app/controllers/shipit/webhooks_controller.rb` or the handler classes that cross-checks `repository.owner.login` (used for signature verification) against `repository.full_name` (used for repository/stack resolution). These are read from the same JSON body independently, with no binding enforced between them.

### Title
Webhook signature verification org is never bound to the repository resolved for stack mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC using `repository.owner.login` (or `organization.login`) from the JSON body, but `Shipit::Webhooks::Handlers::Handler#stacks` and every `PullRequest::*Handler#repository` resolve the actually-mutated `Repository`/`Stack` using a completely independent field, `repository.full_name`. Because both fields are attacker-controlled inside a single signed payload and are never compared to each other, a payload validly signed for one onboarded organization can point `full_name` at a repository belonging to a different organization, letting that request's handler act on a `Stack` it was never authenticated for.

### Finding Description
The broken binding, stated explicitly: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` succeeding for `repository_owner == payload.dig('repository','owner','login')` is assumed to imply `Repository.from_github_repo_name(payload.dig('repository','full_name'))` resolves to a repository owned by that same `repository_owner`. Nothing in the code enforces that equality.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the raw body HMAC against `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` [1](#0-0) [2](#0-1) .
- On success, `create` dispatches the *entire raw JSON body* to every registered handler for the event via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- `Handler#stacks` (used by `PushHandler`) resolves the target repository purely from `payload.dig('repository', 'full_name')`, independent of `repository_owner` used above [4](#0-3) .
- `Repository.from_github_repo_name` performs a case-insensitive, whitespace-naive split/lookup: `github_repo_name.downcase.split('/')` then `find_by(owner:, name:)` [5](#0-4) .
- Every `PullRequest::*Handler` (`OpenedHandler`, `ClosedHandler`, `EditedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `ReopenedHandler`) independently resolves `repository` the same way, from `params.repository.full_name`, and then acts on that repository's `review_stacks`/`stacks`/`PullRequest` records [6](#0-5) .
- Shipit explicitly supports multi-tenant, per-organization GitHub App configuration, each with its own independent `webhook_secret`, exactly the scenario needed for this cross-tenant confusion (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github`/`#github_app_config`) [7](#0-6) [8](#0-7) .

Attacker request: an entity that controls (or knows the `webhook_secret` for) one onboarded organization "org-a" in a multi-org Shipit deployment sends `POST /webhooks` with `X-Github-Event: push`, `X-Hub-Signature` correctly HMAC-signed with org-a's `webhook_secret`, and a body where `repository.owner.login = "org-a"` (so `verify_signature` passes) but `repository.full_name = "org-b/repo"` (a repository belonging to an unrelated organization "org-b"). `verify_signature` passes because it only checks org-a's secret against the raw body; `PushHandler` then calls `stacks` on `Repository.from_github_repo_name("org-b/repo")`, resolving org-b's actual `Stack`, and invokes `stack.sync_github(expected_head_sha: params.after)` on it — a write against a stack the request never authenticated against.

Existing guards do not catch this: `verify_signature` never re-derives `repository_owner` from `full_name` nor checks that the resolved `Repository#owner` matches the org used for signing; `drop_unhandled_event` only checks event name existence; `ExplicitParameters` schemas validate types/presence, not cross-field/tenant consistency; `Repository` model validations only constrain character sets, not signature-vs-lookup binding.

### Impact Explanation
A validly-signed webhook from one tenant organization can trigger `Stack#sync_github` (push handler) or archive/unarchive/label-capture/pull-request-adapter mutations (PR handlers) against a `Stack`/`ReviewStack`/`PullRequest` belonging to a *different* tenant organization, purely by setting `repository.full_name` to that other org's exact repo path. This is a cross-tenant write triggered by a payload that only authenticated for its own organization, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any organization pair configured on the same Shipit instance and any repository whose `owner/name` string is known or guessable (repo names are frequently public).

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented, supported configuration), (2) the attacker having a valid `webhook_secret` for at least one onboarded org (e.g., they are that org's GitHub App administrator, a legitimate but lower-trust tenant on a shared Shipit instance), and (3) knowledge of the target org/repo's exact `full_name`. Once these hold, the attack is a single crafted POST with a correctly computed HMAC — no GitHub-side action or elevated Shipit privilege is needed, and it is trivially repeatable against any other tenant.

### Recommendation
After signature verification, re-derive the owner from `repository.full_name` (or `organization.login`) and require it to match the `repository_owner` used to select the `webhook_secret`/`GitHubApp` before dispatching to handlers; reject (422) on mismatch. Alternatively, have handlers scope their `Repository`/`Stack` lookups by the already-verified organization rather than trusting `full_name` alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push payload signed for org-a cannot mutate org-b's stack via mismatched full_name" do
  repo_a = Repository.create!(owner: 'org-a', name: 'repo')
  repo_b = Repository.create!(owner: 'org-b', name: 'repo-b')
  stack_b = Stack.create!(repository: repo_b, environment: 'production', branch: 'master')

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: { full_name: 'org-b/repo-b', owner: { login: 'org-a' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_webhook_secret, body)
  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  assert_equal repo_b, Repository.from_github_repo_name('org-b/repo-b')
  assert_not_equal repo_a.owner, repo_b.owner # binding under test: org used to sign != owner of resolved repo

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: stack_b.id, expected_head_sha: 'deadbeef']) do
    post :create, body: body, as: :json
  end
  assert_response :ok
end
```
This demonstrates that a request signed only for `org-a` results in a job enqueued against `stack_b`, owned by `org-b`, proving the cross-tenant write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
