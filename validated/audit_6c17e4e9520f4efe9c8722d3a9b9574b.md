### Title
Status webhooks update commits across unrelated repositories - the organization whose GitHub App signature authenticates a webhook is never bound to the commit that gets written - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook against a specific organization's GitHub App secret, derived from `repository.owner.login` in the payload. [1](#0-0)  Every other handler in `app/models/shipit/webhooks/handlers/` scopes its writes to the `Repository` named in the same payload via `Handler#stacks`/`#repository_name`. [2](#0-1)  `StatusHandler`, however, breaks that binding: it looks up commits to update purely `Commit.where(sha: params.sha)` with no repository/stack scoping at all. [3](#0-2) 

### Finding Description
The equality that should hold is: `organization authenticated by verify_signature == repository/stack whose commit is mutated`. For `PushHandler` and `CheckSuiteHandler` this equality is enforced because they resolve `stacks` from `Repository.from_github_repo_name(repository_name)` (the same repository the signature was verified for). [4](#0-3) [5](#0-4) 

`StatusHandler#process` instead does a **global, cross-repository** lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2)  `Commit` belongs to exactly one `Stack`, and `sha` is not scoped/validated as unique to a stack in the model shown. [6](#0-5)  The webhook signature only proves the payload came from the GitHub App installed on organization X (`repository_owner`), but `StatusHandler` never checks that the `Commit` rows it mutates belong to a `Stack`/`Repository` under organization X. If the same commit SHA is present in more than one tracked repository/stack (identical commit objects can exist in multiple repositories through forks, shared subtree history, mirrored/renamed repos, or a repository being renamed/re-owned while an old `Commit` row from the previous owner still exists), a `status` webhook validly signed by organization X's GitHub App can write a `Status` (state, description, target_url, context) onto a `Commit` that actually belongs to a stack owned by a completely different, unrelated organization/repository tracked by the same Shipit instance.

Since `Status` state feeds directly into deploy-gating logic (`required_statuses`, `blocking_statuses`, `hidden_statuses` in `deploy_spec.rb`), this is a genuine deployment-trust binding violation: the organization that authenticated the webhook is not the same as the repository whose commit-status state (and therefore deploy eligibility) gets written.

### Impact Explanation
This can lead to an unauthorized deploy/rollback: an attacker who controls (or merely has push access to) one Shipit-tracked organization/repository can forge a `status` webhook (using their own org's legitimately-verified signature) that sets a passing/green status on a commit that is shared with (or coincidentally shares the SHA of, e.g. through repository transfer/rename reuse) another organization's tracked stack, potentially bypassing that other stack's required/blocking CI statuses and enabling a deploy that should have been blocked. This matches the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires a shared commit SHA to exist across two `Stack`s tracked by the same Shipit instance — this is a realistic scenario in multi-tenant Shipit deployments where forks, template repositories, monorepo extractions, or repository renames/transfers are tracked as separate `Repository`/`Stack` records that still reference historical commits with identical SHAs. It does not require an actual SHA-1 collision, just organic SHA reuse across repositories, making this more likely than the report's bridge-pause race but still conditioned on multi-tenant Shipit usage and repository history overlap.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare `Commit.where(sha:)` lookups) to the repository the webhook's signature was verified for, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` using the existing `Handler#stacks` helper (which already resolves via `Repository.from_github_repo_name(repository_name)`), so a commit is only updated if it belongs to a stack under the same repository/organization that authenticated the webhook.

### Proof of Concept
1. Shipit tracks two stacks: `Stack A` under `org-a/repo` and `Stack B` under `org-b/repo`, both with the Shipit GitHub App installed (each org has its own webhook secret, verified independently in `WebhooksController#verify_signature`). [7](#0-6) 
2. `Stack B` has a `Commit` with `sha = X` (e.g., from a commit shared via fork/history overlap/rename) that is required to have a passing CI status before deploy is allowed.
3. An actor controlling `org-a`'s repository sends a legitimately-signed `status` webhook for `org-a/repo` claiming `sha = X`, `state = "success"`.
4. `WebhooksController#verify_signature` succeeds because the signature matches `org-a`'s secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "X")`, matches the `Commit` belonging to `Stack B`, and calls `create_status_from_github!`, writing a "success" status onto `Stack B`'s commit despite the webhook never being authenticated for `org-b`. [3](#0-2) 
6. `Stack B`'s required-status deploy gate now sees a fabricated "success" status it never legitimately received, potentially allowing an unauthorized deploy.
