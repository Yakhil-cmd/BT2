### Title
Cross-repository status/check-run injection via SHA-scoped, org-unscoped webhook handlers - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController` verifies an inbound GitHub webhook's HMAC signature using the webhook_secret of the organization named *inside the payload itself* (`repository.owner.login`), then dispatches the parsed payload to handlers such as `StatusHandler` and `CheckSuiteHandler`. Those handlers look up target `Commit` records purely by `sha`, with no check that the commit's owning `stack`/`repository` matches the organization/repository that was cryptographically authenticated. This breaks the binding: "organization that authenticated == repository that is written."

### Finding Description
The controller resolves which GitHub App/secret to use for HMAC verification from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

Once the signature checks out (i.e., it matches the secret for whatever organization the payload claims to belong to), the raw JSON is handed to the matching handler: [3](#0-2) 

`StatusHandler` then mutates commit state using only the `sha` field, with no scoping to the repository/organization that was authenticated: [4](#0-3) 

This calls `Commit#create_status_from_github!`, which creates a real `Status` record and immediately evaluates deploy/merge triggers: [5](#0-4) [6](#0-5) 

Because git commit SHAs are content-addressed, an attacker who owns/administers *any* GitHub organization/repo where the Shipit GitHub App is installed (a self-service, unprivileged action available to any GitHub user) can:
1. Identify or reproduce a commit SHA that also exists in a *different*, unrelated stack/repository tracked by the same Shipit instance (e.g. by forking the target public repo, or crafting an identical commit object with matching tree/parents/author/committer metadata under their own account).
2. Trigger (via GitHub's normal Status/Check API against their own repo, which they legitimately control) a `status` or `check_suite` webhook for that SHA. GitHub signs this webhook with the attacker's own org's `webhook_secret`.
3. `WebhooksController#verify_signature` correctly validates this signature, since it looks up the app/secret keyed by the *attacker's own* `repository_owner` claim in the payload.
4. `StatusHandler#process` (or `CheckSuiteHandler`) then updates `Commit.where(sha: params.sha)` — a global, cross-tenant lookup — with no verification that the found commit belongs to the org/repo whose secret actually signed the request.

The `Handler#stacks` helper does apply `Repository.from_github_repo_name` scoping for the `push` handler, but `StatusHandler` bypasses that scoping entirely and queries `Commit` directly by SHA across the whole database: [7](#0-6) 

### Impact Explanation
This is a cross-repository write: an attacker with no privileged Shipit access, no `ApiClient` token, and no access to another org's `webhook_secret` can inject fabricated CI status data (`success`, `failure`, `pending`) onto a commit belonging to a completely different, unrelated organization/stack hosted on the same Shipit instance. Since `Commit#deployable?` and `Commit#schedule_continuous_delivery` react directly to status changes and can enqueue `ContinuousDeliveryJob`, this can force an unauthorized deploy of another organization's stack (by faking a passing status) or block a legitimate deploy (by faking a failing/blocking status). This matches the Critical bucket "unauthorized deploy" and the High bucket "escalation ... unauthenticated ... write of stack state."

### Likelihood Explanation
Requires only: (a) the ability to install/operate the Shipit GitHub App on an attacker-controlled org/repo (self-service, no privileged access to the target Shipit instance), and (b) a colliding SHA with the victim stack's tracked commit, achievable deterministically by forking/mirroring a public target repository (git preserves identical commit SHAs across forks) or replicating identical commit metadata. No secrets, sessions, or GitHub tokens belonging to the victim are needed.

### Recommendation
Scope all webhook-driven commit lookups (`StatusHandler`, `CheckSuiteHandler`, and any handler using `Commit.where(sha: ...)`) to the repository/organization actually authenticated by the verified signature — e.g., join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and constrain the `Commit` query to `stack.repository_id` matching that repository, mirroring what `Handler#stacks` already does for `PushHandler`.

### Proof of Concept
1. Attacker creates/administers `attacker-org/attacker-repo` and installs the Shipit GitHub App there (self-service), obtaining a valid `webhook_secret` for `attacker-org`.
2. Attacker forks (or replicates via identical commit metadata) `victim-org/victim-repo`'s commit `abc123...`, which Shipit already tracks in `victim-org`'s stack.
3. Attacker sets a commit status (`success`) on `abc123...` in `attacker-org/attacker-repo` via the GitHub API (an action they're fully authorized to perform on their own repo).
4. GitHub sends a `status` webhook to Shipit signed with `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` succeeds because it looks up the secret using the attacker's own `repository.owner.login`.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, matches the commit under `victim-org`'s stack, and calls `create_status_from_github!`, injecting a `success` status and potentially triggering `ContinuousDeliveryJob` for the victim's stack — with the attacker never having authenticated against or having write access to `victim-org`.
