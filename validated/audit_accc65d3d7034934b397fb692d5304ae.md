### Title
Cross-repository forgery of commit CI status via webhook signature scoped to repository owner but write scoped only to commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook's authenticity check binds the HMAC signature to the *organization* named in the payload's `repository.owner.login`/`organization.login`, but `StatusHandler#process` writes a `Status` record by looking up `Commit.where(sha: params.sha)` with no scoping to that repository/organization at all. Any GitHub organization/repository with a webhook configured in this Shipit instance can therefore forge a commit-status update for a commit that belongs to a completely different, unrelated stack, because the two fields — the org used to select/verify the signing secret and the SHA used to decide which row gets mutated — are independent and never cross-checked.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the incoming JSON body and uses it purely to pick which configured GitHub App's `webhook_secret` verifies the HMAC: [1](#0-0) [2](#0-1) 

Once verification succeeds, the event is dispatched to registered handlers with the raw parsed payload: [3](#0-2) 

Most handlers scope their write to the repository named in the payload via `Handler#repository_name`/`#stacks` (`payload.dig('repository', 'full_name')`): [4](#0-3) 

`StatusHandler`, however, does not use `repository_name`/`stacks` at all. It looks up every `Commit` in the entire database matching the attacker-supplied `sha` and writes a status onto it, with zero repository/org scoping: [5](#0-4) 

Consequently, the binding that should hold — "the organization whose secret authenticated this webhook == the repository/stack being written to" — does not hold for the `status` event. The signature only proves the payload was signed by *some* org's webhook secret (as selected by `repository_owner`), not that the `sha` referenced in the same payload belongs to a commit within that org's repositories. An entity that legitimately controls a webhook for Org A (any org configured under `Shipit.github`, see `lib/shipit.rb`'s `github_app_config`/`github_organizations`) can:
1. Compute a valid `sha1=` HMAC using Org A's own `webhook_secret` (which they know, since it is their own org's webhook).
2. Set `repository.owner.login` (or `organization.login`) to Org A so `verify_signature` picks Org A's secret and passes.
3. Set `sha` to any commit SHA that exists in Shipit's database for Org B's (victim) stack — SHAs are public git commit hashes, trivially discoverable from the victim's public/private repo history, PRs, or Shipit's own commit list UI.
4. POST this forged `status` payload; `Commit.where(sha: params.sha)` finds the victim commit belonging to a stack the attacker has no access to, and `create_status_from_github!` writes an attacker-chosen `state`/`context`/`description`/`target_url` onto it.

This directly breaks the equality: `organization_that_authenticated (repository_owner used for HMAC secret selection) == repository/stack being written (Commit found solely by global sha lookup)`.

### Impact Explanation
Commit statuses are the mechanism `ci.require`/`ci.blocking` use to gate whether a commit is deployable (documented in `README.md`'s CI section). By forging a passing/matching status context on a victim's commit, an attacker with no relationship to the victim's repository can unblock that commit for deployment on the victim's stack, or — if continuous deployment is enabled — trigger an unauthorized/unattended deploy of a commit that never actually passed the required CI checks. This is a cross-repository write with a path to an unauthorized deploy, matching the report's stated Critical impact criteria (cross-repository writes / unauthorized deploy) without requiring any Shipit session, API token, or `api_clients_secret`/webhook secret belonging to the victim org.

### Likelihood Explanation
Any party who is a legitimate webhook sender for at least one GitHub org/repo configured on this Shipit instance can exploit this — no elevated Shipit privilege, no victim credentials, and no cryptographic break is required, only knowledge of a public commit SHA in the victim stack. In multi-org Shipit deployments (the `github_organizations`/`github_app_config` support in `lib/shipit.rb` exists specifically to host several orgs on one instance), this is a realistic boundary that is expected to isolate tenants from one another, making the likelihood high in that deployment model.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository identified by the authenticated payload (e.g., via `stacks`/`repository_name` as `PushHandler` and other handlers do), rejecting or ignoring commits that do not belong to the repository whose owner was used to verify the signature. More generally, `WebhooksController#verify_signature` should assert that every repository-identifying field consumed by downstream handlers (`repository.full_name`, `sha`'s owning repo, etc.) is consistent with the `repository_owner` used to select the verifying secret, not just the field used for secret selection.

### Proof of Concept
1. Shipit instance configured with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `lib/shipit.rb` `github_app_config`).
2. Attacker controls a repository/webhook under `org-a` and knows `org-a`'s `webhook_secret` (as any legitimate webhook owner does).
3. Attacker finds a public commit SHA `deadbeef...` belonging to a stack tracked under `org-b`.
4. Attacker builds the JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/attacker-repo"}
}
```
5. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `org-a`, verifies successfully against `org-a`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, finds the `org-b` commit, and creates a forged `success` status on it — satisfying `org-b`'s `ci.require` gate despite the attacker having no access to `org-b`.
