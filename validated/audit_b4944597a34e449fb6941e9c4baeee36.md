### Title
Cross-repository CI-bypass via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by matching `params.sha` against the entire `commits` table with no repository/stack filter, then calls `create_status_from_github!` on every match. Because `Status#enable_ci_on_stack` unconditionally flips `commit.stack.enable_ci!` on `after_create`, a webhook whose signed payload names the attacker's own repository can toggle `ignore_ci` on any victim stack whose commit table happens to contain the same SHA.

### Finding Description
The broken binding is: `commit.stack.id` (the stack whose `ignore_ci` gets mutated) should equal the stack that owns the repository named in the *verified* webhook's `repository.full_name`, but the code never establishes that equality.

Path: [1](#0-0) 
`process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is global across all stacks/repositories; it never joins or filters on `repository` from the payload. [2](#0-1) 
`create_status_from_github!` creates a `Status` scoped to `stack_id` (the *matched commit's own* stack, i.e., potentially the victim's stack), not any stack derived from the payload's repository. [3](#0-2) 
`after_create :enable_ci_on_stack` then calls `commit.stack.enable_ci!` unconditionally — no check that `commit.stack.repository` matches the webhook's authenticated repository.

Exploit flow: git blob/tree/commit SHAs are content-addressed and repository-independent. An attacker who owns/forks a public repository that shares history with, or who otherwise learns a commit SHA present in, a victim's Shipit-tracked stack can call GitHub's real Status API (`POST /repos/{attacker}/{repo}/statuses/{sha}`) on their own repository for that arbitrary SHA — GitHub's API does not require the SHA to exist in the target repo. GitHub then delivers a genuinely-signed `status` webhook (signed with Shipit's globally configured `webhook_secret`, which is not repository-specific) whose `repository` field says "attacker/repo" but whose `sha` matches a commit belonging to the victim's stack. Signature verification (`verify_signature`) only proves the request came from GitHub for *some* configured repository/App installation — it says nothing about which stack the SHA belongs to. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not repository ownership of the SHA. Because `StatusHandler#process` does the lookup by bare SHA with no repository scoping, the victim's commit is matched and `enable_ci_on_stack` fires against the victim's stack.

### Impact Explanation
The attacker mutates a persistent boolean (`ignore_ci`) on a victim's `Stack` using a webhook that is authenticated only for the attacker's own repository — this is exactly the "payload for one repository mutating another's stack" critical category. Setting `ignore_ci` to true removes the CI-gate on `Commit#deployable?`, which can enable unwanted continuous deployment/merges on the victim stack once combined with other automation (`schedule_continuous_delivery`, `stack.schedule_merges`). The action is repeatable against any stack whose tracked commit SHAs the attacker can discover or reproduce (e.g. via a shared fork history), and requires no session, API token, or Shipit secret.

### Likelihood Explanation
Preconditions: victim stack has a commit whose SHA the attacker can name (trivial if the attacker forked the victim repository before divergence, since git SHAs are identical across forks for shared history) and `ignore_ci` is currently false/nil. The attacker needs only a GitHub repository they control and permission to hit GitHub's Status API on it — both are unprivileged actions available to any GitHub user. No Shipit secret, session, or API client credential is needed. Cost is low and the attack is repeatable per request.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) by the verified webhook's repository, not by bare SHA alone — e.g., resolve the target `Stack`/`Repository` from the authenticated payload first, then restrict `Commit.where(sha: params.sha, stack_id: matched_stack_ids)` before creating/mutating any status. Additionally, `Status#enable_ci_on_stack` should not unconditionally trust that any status creation implies CI enablement without confirming the originating repository matches the stack's configured repository.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or `test/models/shipit/status_test.rb`) style:
1. Create `victim_stack` with `repository` `victim/repo`, `ignore_ci: false`, and a `Commit` with `sha: "deadbeef" * 5` belonging to `victim_stack`.
2. Create `attacker_stack` (or no stack at all) representing `attacker/repo`.
3. Build a `status` webhook payload where `repository.full_name == "attacker/repo"` but `sha == victim_commit.sha`, and pass GitHub App/webhook signature verification for the attacker's own registered repository/App installation.
4. Assert before: `victim_stack.reload.ignore_ci == false`.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (or POST to `/webhooks` with the crafted, validly-signed body for attacker's repo).
6. Assert after: `victim_stack.reload.ignore_ci == true`, proving `victim_stack.repository.full_name != payload.repository.full_name` yet the mutation occurred — the claimed broken binding.
