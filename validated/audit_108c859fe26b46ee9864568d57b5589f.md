### Title
Missing `contract-caller` authorization gate on `pox-5.clar` staking entry points allows unauthorized STX locking via a confused-deputy contract call - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s staking entry points (`stake`, `register-for-bond`, `update-bond-registration`, and related bond/stake mutators) use `tx-sender` as the staker's identity but, unlike every prior PoX contract (`pox.clar`, `pox-2.clar`, `pox-3.clar`, `pox-4.clar`), do not gate these calls with the `check-caller-allowed` / `allow-contract-caller` mechanism. This removes the protection that previously prevented a third-party contract from initiating a stacking action on a user's behalf without the user's explicit, per-contract consent.

### Finding Description
In every prior PoX version, mutating stacking entry points assert that the call is either issued directly by the `tx-sender` or through a `contract-caller` explicitly whitelisted by that `tx-sender` via `allow-contract-caller`: [1](#0-0) [2](#0-1) 

The doc comment makes the intent explicit: "normally, stacking methods may only be invoked by *direct* transactions (i.e., the tx-sender issues a direct contract-call to the stacking methods); by issuing an allowance, the tx-sender may call through the allowed contract." [3](#0-2) 

`pox-5.clar` has no `check-caller-allowed`, `allow-contract-caller`, or `disallow-contract-caller` definitions at all (confirmed by search over the file). Its public staking entry points such as `stake` and `register-for-bond` read `tx-sender` directly to determine the staker being locked, but never assert `contract-caller` is either equal to `tx-sender` or explicitly permitted: [4](#0-3) [5](#0-4) 

Since Clarity's `tx-sender` is fixed for the whole transaction regardless of how many nested `contract-call?` hops occur, any contract that a user interacts with for an unrelated purpose can, mid-transaction, issue a `contract-call?` into `.pox-5` `stake` or `register-for-bond` using that user's `tx-sender` identity — locking the user's STX, enrolling them in a bond, or attaching them to a signer of the calling contract's choosing — without the user ever intending to invoke PoX-5 at all. This breaks the invariant "a stacking action must be authorized by the staker for that specific action," which the removed `check-caller-allowed` gate previously enforced.

### Impact Explanation
This allows temporary freezing of a user's STX (locked into staking/bonds they never intended to enter, for a lock period and signer chosen by an attacker-controlled intermediary contract) and constitutes an unsigned/unauthorized stacking action, matching the "signing weight or reward slots exceeding locked value... an unsigned stacking action" High-impact category. It can also be leveraged to funnel a victim's stake toward an attacker-controlled `signer-manager`, letting the attacker capture the rewards/signing weight tied to the victim's locked STX.

### Likelihood Explanation
Likelihood is high in principle: any dApp/contract composability scenario where a user signs a transaction that transitively calls an untrusted or later-compromised contract is sufficient — no special privilege is needed beyond the ordinary ability to get a user to sign a transaction that contract-calls into an intermediary. This exactly mirrors the confused-deputy scenario the `check-caller-allowed` mechanism in `pox`, `pox-2`, `pox-3`, and `pox-4` was designed to prevent.

### Recommendation
Add a `check-caller-allowed` predicate to `pox-5.clar`, mirroring `pox-4.clar`, and gate `stake`, `register-for-bond`, `update-bond-registration`, and any other mutating entry point that locks/moves a staker's STX or sBTC behind `(asserts! (check-caller-allowed) ERR_UNAUTHORIZED)`, together with `allow-contract-caller`/`disallow-contract-caller` public functions so stakers can opt in to indirect calls explicitly.

### Proof of Concept
1. Victim holds unlocked STX and has never called `.pox-5`.
2. Victim signs a transaction calling a seemingly unrelated contract `evil.clar`.
3. `evil.clar` contains `(contract-call? .pox-5 stake signer-manager amount-ustx num-cycles start-burn-ht none)`.
4. Because `tx-sender` in `.pox-5`'s `stake` resolves to the victim (the original transaction signer), and there is no `check-caller-allowed`/allowance check, the call succeeds using the victim's identity, balance, and signature-less consent — locking the victim's STX for `num-cycles` under a signer of the attacker's choosing.
5. Contrast with `pox-4.clar`'s `stack-stx`, where the identical call sequence would fail at `(asserts! (check-caller-allowed) (err ERR_STACKING_PERMISSION_DENIED))` unless the victim had previously called `allow-contract-caller` for `evil.clar`.

;;  normally, stacking methods may only be invoked by _direct_ transactions

(define-public (allow-contract-caller (caller principal) (until-burn-ht (optional uint)))
  (begin
    (asserts! (is-eq tx-sender contract-caller)
              (err ERR_STACKING_PERMISSION_DENIED))
    (ok (map-set allowance-contract-callers
               { sender: tx-sender, contract-caller: caller }
               { until-burn-ht: until-burn-ht }))))

(define-private (check-caller-allowed)
    (or (is-eq tx-sender contract-caller)
        (let ((caller-allowed 
                 ;; if not in the caller map, return false
                 (unwrap! (map-get? allowance-contract-callers
                                    { sender: tx-sender, contract-caller: contract-caller })
                          false)))
          ;; is the caller allowance expired?
          (if (< burn-block-height (unwrap! (get until-burn-ht caller-allowed) true))
              false
              true))))
