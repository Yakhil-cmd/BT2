### Title
`push` webhook authentication uses `repository.owner.login` while mutation targets `repository.full_name`, allowing cross-org stack sync - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to authenticate a webhook using `repository_owner`, which reads `payload.dig('repository','owner','login')` [1](#0-0) . But `Handler#stacks`, used by every handler including `PushHandler`, resolves the affected `Repository`/`Stack` using a *different* field, `payload.dig('repository','full_name')` [2](#0-1) . Since both fields are attacker-controlled JSON body values and nothing binds them together, an attacker can authenticate with one org's (no-)secret while mutating a stack belonging to a completely different repository/org.

### Finding Description
The broken binding is the implicit equality the code assumes but never enforces:
`payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`

Trace:
1. `POST /webhooks` is unauthenticated; `WebhooksController#create` parses the raw JSON body without any linkage to session/API-client identity [3](#0-2) .
2. `verify_signature` builds `Shipit.github(organization: repository_owner)` from `repository.owner.login` (or `organization.login`) and calls `verify_webhook_signature` [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org has no `webhook_secret` configured: `return true unless webhook_secret` [5](#0-4) . If the attacker names any onboarded-but-secretless org (or one whose secret they otherwise know) in `repository.owner.login`, signature verification passes unconditionally, independent of the actual signature header.
4. Once verification passes, `PushHandler#process` (inherited `stacks` from `Handler`) resolves the repository via `Repository.from_github_repo_name(repository_name)`, where `repository_name` comes from `payload.dig('repository','full_name')` — a completely separate field from the one used in step 2 [2](#0-1)  and [6](#0-5) .
5. `PushHandler` then iterates every non-archived stack on the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) , which can append commits and drive deploys/rollbacks on a victim repository/stack that never authenticated this request.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates `ref`/`after` are present, not their relationship to authentication; there is no code anywhere that checks `repository.owner.login` equals the owner portion of `repository.full_name`. The signature check and the resolution-of-target-repo check use disjoint payload fields, so an attacker who controls both fields (since both are just JSON body values) can decouple "who authenticated this webhook" from "which repo/stack gets mutated."

### Impact Explanation
This is a payload for one repository/organization mutating another's stack — matching the Critical "payload for one repository mutating another's stack, commit, task or team" category. On a victim stack configured with `review_stacks_enabled: true` and `provisioning_behavior: allow_all`, the impact compounds: external, unauthenticated pushes/PR-driven pushes can auto-provision review stacks that execute the repository's `shipit.yml` (Shipit's deployment DSL, which shells out via `Command`/`PTY.spawn`), turning an authentication bypass into a path toward command execution on the deploy host under the victim stack's configuration. The precondition (an onboarded org with no `webhook_secret`, or any org whose secret the attacker can obtain/guess) determines exploitability but the code path itself has zero binding between the authenticating org and the mutated repository, which is a genuine per-engine bug independent of any specific org's config quality.

### Likelihood Explanation
Requires: (a) at least one org configured in `Shipit.github_teams`/organization list with a blank/missing `webhook_secret` (or a secret the attacker can determine), and (b) a victim repository/stack already registered in Shipit with `review_stacks_enabled: true, provisioning_behavior: allow_all`. Both are plausible operational configurations (some orgs may intentionally run without a webhook secret in staging/dev setups, or the multi-org config in `test/dummy/config/secrets_double_github_app.yml` demonstrates that Shipit explicitly supports per-org differing secrets). No GitHub App private key, session, or API token is needed — only the ability to send an arbitrary HTTP POST to `/webhooks`. This is a low-cost, repeatable attack against any repository/stack whose `full_name` the attacker can guess (GitHub repo names are public information).

### Recommendation
Bind authentication to the actual mutation target: derive the org used for `Shipit.github(organization:)` from the same `repository.full_name` field (owner segment) used by `Handler#stacks`/`Repository.from_github_repo_name`, not from a separate `repository.owner.login`/`organization.login` field. Additionally, refuse orgs with a blank `webhook_secret` from silently passing verification for events carrying a `repository` payload that resolves to a different owner, and/or require explicit cross-checking that `repository.owner.login == repository.full_name.split('/').first` before dispatching handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof sketch)
test "push event authenticated via a no-secret org can mutate a stack under a different org" do
  # attacker-controlled org with no webhook_secret configured
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # no webhook_secret => verify_webhook_signature always true
  )

  victim_stack = shipit_stacks(:shipit) # belongs to repository "victim-org/rails-example"
  before_sha = victim_stack.commits.last.sha

  payload = {
    ref: "refs/heads/#{victim_stack.branch}",
    after: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
    repository: {
      owner: { login: 'attacker-org' },       # used for signature verification (no secret => bypass)
      full_name: 'victim-org/rails-example'   # used to resolve the mutated Repository/Stack
    }
  }.to_json

  post shipit.github_webhooks_path,
    params: payload,
    headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => 'sha1=bogus', 'Content-Type' => 'application/json' }

  assert_response :ok
  # Assert the equality claimed broken: authenticating org != mutated repo owner
  assert_not_equal 'attacker-org', victim_stack.repository.owner
  # Assert the victim stack was in fact synced/mutated despite not authenticating the request
  assert_equal "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
    victim_stack.reload.commits.last.sha # or assert sync_github was invoked with expected_head_sha
end
```
This demonstrates the invariant "a `push` event only affects the repository/stack whose secret authenticated it" is violated: the `attacker-org` (no secret) authenticates the request, but `victim-org/rails-example`'s stack is the one mutated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
