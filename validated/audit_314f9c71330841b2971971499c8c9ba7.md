## Analysis

The webhook signature is verified per-organization: `Shipit.github(organization: repository_owner)` derives the app config purely from `params.dig('repository','owner','login')` in the attacker-controlled JSON body [1](#0-0) . This proves only that the request was signed with **R1's** organization secret — it says nothing about the `sha` field also present in the same JSON body.

`StatusHandler#process` then looks up commits **globally by `sha` alone**, with no scoping to the repository/organization that was authenticated:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit#create_status_from_github!` calls `add_status`, which fires `Hook.emit(:commit_status, stack, ...)` and `Hook.emit(:deployable_status, stack, ...)` using `commit.stack` — the stack that owns whatever commit row matched the sha, regardless of which org's key signed the request [3](#0-2) [4](#0-3) .

**Binding claimed:** `stack (Hook.emit target)` == `stack whose admins authorized events from repository_owner (R1, the verified signer)`.

**Binding as actually enforced:** `stack (Hook.emit target)` == `stack of whichever Commit row has this sha`, entirely independent of `repository_owner`/R1.

These are not equal. Git SHAs are content-addressed, so if S2 (the victim) tracks a repository that a fork/mirror relationship shares history with R1 (e.g., R1 is a fork of S2's tracked repo, or any repo whose early commits are byte-identical), commits imported into S2's `commits` table can have the same `sha` as commits reachable from R1. An attacker who owns R1 can fire a real, correctly-signed `status` webhook from R1 for a sha they know exists in S2's `commits` table (harvested from S2's public GitHub history/PRs). `verify_signature` passes (R1's own secret signs R1's own payload correctly), `drop_unhandled_event` passes (`status` has a handler), and `StatusHandler` blindly updates S2's commit and triggers `Hook.emit(:commit_status, S2, ...)` / `Hook.emit(:deployable_status, S2, ...)`, causing any `Shipit::Hook` configured on S2 to fire against S2's victim-configured webhook URL with attacker-influenced state/description/context/target_url content — with no visibility into the fact that the triggering event originated from R1.

This matches the "payload for one repository mutating another's stack/commit" Critical category: the attacker forges a `Status` record and hook-emission for a stack (S2) that never authenticated the attacker's org, and can potentially inject attacker-controlled `description`/`target_url` text (limited to what fields `StatusHandler` accepts — `state`, `description`, `target_url`, `context`) into S2's outbound hook payload/URL-following systems.

The one real precondition worth flagging as an open question: whether the `Commit#sha` values actually shared across two independently-tracked stacks in realistic operation (shared history via fork/mirror) is common enough to be "repeatable against arbitrary stacks," or whether it requires the specific setup of a forked repo being tracked as a second stack. I was not able to fully verify from the index whether any additional uniqueness constraint ties `sha` to `stack_id` at the DB/model level beyond what's shown (`Commit.by_sha` and other lookups also query by sha without stack scoping, consistent with the schema treating sha as not globally unique per stack, i.e., `(sha, stack_id)` composite index per the changelog entry, not a global uniqueness constraint) [5](#0-4) . This supports that multiple stacks can independently hold rows with the same `sha`.

### Title
`StatusHandler#process` resolves commits by `sha` globally, letting a signed webhook from one organization emit `Hook.emit` on another organization's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook handler matches commits solely by `Commit.sha` with no scoping to the repository/organization whose signature was verified, so a correctly-signed webhook from attacker-owned repo R1 can update the status of, and trigger `Hook.emit(:commit_status/:deployable_status, ...)`, on a victim stack S2 whenever S2 happens to hold a `Commit` row with the same sha (e.g. due to shared/forked git history). This breaks the intended binding that hook targets must belong to the org that was cryptographically verified for the request.

### Finding Description
Broken binding: `stack (target of Hook.emit)` should equal `stack belonging to repository_owner verified by verify_signature`, but actually equals `stack of Commit.where(sha: params.sha).first`, unconstrained by which org signed the request.

Path: `WebhooksController#create` → `verify_signature` checks `request.headers['X-Hub-Signature']` against `Shipit.github(organization: repository_owner).verify_webhook_signature` where `repository_owner` is read straight from the attacker-supplied `params.dig('repository','owner','login')` [6](#0-5) . This only proves the payload was signed by R1's own installed app secret; it never checks that the `sha` inside the same payload belongs to a commit under R1. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`, whose `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, stack-unscoped lookup [2](#0-1) . `create_status_from_github!` → `add_status` uses `commit.stack` (whatever stack that matching Commit row belongs to) as the `Hook.emit` target for both `:commit_status` and `:deployable_status` [3](#0-2) [4](#0-3) .

Attack: attacker controls repo R1 (owns/forks it, can configure the GitHub App/webhook for it per the app's normal installation flow) and knows a sha present in victim stack S2's `commits` table (any git sha shared between the two histories — trivial when R1 is a fork of the repo S2 tracks). Attacker POSTs a `status` event, correctly signed with R1's own webhook secret, containing that sha and arbitrary `state`/`description`/`context`/`target_url`. `verify_signature` passes because it only validates R1's own signature against R1's own secret. `StatusHandler` finds the S2 commit by sha and fires the hooks against S2.

Existing guards don't catch this: `verify_signature` validates authenticity of the sender but never binds the sender's identity to the target stack for the `status` event type (unlike `push`, which resolves stacks by `repository.full_name` before touching any records — see `PushHandler`, not reproduced here but structurally different); `drop_unhandled_event` only filters unregistered event types; the `ExplicitParameters` schema for `StatusHandler` only validates field types/presence, not repo ownership of the sha.

### Impact Explanation
A forged `Hook.emit(:commit_status, S2, ...)` / `Hook.emit(:deployable_status, S2, ...)` causes any `Shipit::Hook` subscriber configured by S2's administrators to receive a webhook delivery describing a status transition that never happened, with attacker-influenced `description`/`context`/`target_url` content, and no indication that it originated from R1. This is a cross-tenant forged write (a `Status` row created under S2 by an unrelated, unauthenticated-for-S2 org) and a forged notification delivered over S2's outbound hook URL — matching "a payload for one repository mutating another's stack/commit." Repeatable for any sha shared between R1 and any tracked victim stack (most straightforwardly, forks of the tracked upstream repo), and can additionally trigger `stack.schedule_merges` and merge-queue processing (`ProcessMergeRequestsJob`) on S2 based on forged state transitions.

### Likelihood Explanation
Preconditions: attacker needs (a) a repository (R1) with a Shipit-recognized GitHub App/organization installation they control (or any repo under an org already configured in Shipit's `github_organizations`), and (b) knowledge of a sha present in the victim stack's `commits` table that is also reachable from R1 — trivially satisfied if R1 is a fork/mirror of the repo S2 tracks, since early history is byte-identical. No Shipit session, token, or secret is required; only the ability to have GitHub deliver (or directly POST, since only signature matters) a `status` event signed with R1's own secret. Cost is low and the attack is repeatable per known shared sha.

### Recommendation
Scope the `StatusHandler` (and any similarly sha-only lookup) to the repository that was authenticated: resolve `commit.stack` via the payload's `repository.full_name`/`repository_owner` and require it to match before calling `create_status_from_github!`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner:, repository_name: })`.

### Proof of Concept
```ruby
# test/models/webhooks_status_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossTenantTest < ActionController::TestCase
    tests WebhooksController

    test "a status webhook signed for R1's org must not emit Hook for S2's stack when shas collide" do
      GithubHook.any_instance.stubs(:verify_signature).returns(true)

      s2_commit = shipit_commits(:first) # belongs to victim stack S2
      s2_stack  = s2_commit.stack

      # attacker's org (R1) is a different, verified organization
      attacker_owner = 'attacker-org'
      Shipit.stubs(:github).with(organization: attacker_owner).returns(
        stub(verify_webhook_signature: true)
      )

      request.headers['X-Github-Event'] = 'status'
      body = {
        sha: s2_commit.sha, # sha collision: same sha exists under S2
        state: 'failure',
        description: 'forged by attacker',
        context: 'ci/attacker',
        repository: { owner: { login: attacker_owner } }
      }.to_json

      # Binding under test: Hook.emit target stack should equal a stack
      # whose admins authorized events from `attacker_owner`. S2 never did.
      Hook.expects(:emit).with(:commit_status, s2_stack, anything).never
      Hook.expects(:emit).with(:deployable_status, s2_stack, anything).never

      post :create, body:, as: :json
    end
  end
end
```
If the assertions `.never` fail (i.e., `Hook.emit` **is** invoked with `s2_stack`), the binding is broken and the vulnerability is confirmed — the current code is expected to fail this test given `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)` lookup.
