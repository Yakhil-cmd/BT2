### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login`/`organization.login` field that is decoupled from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported bug class is a verification routine that omits an identity binding (`address(this)`), letting a proof valid in one context be replayed in another. The engine's webhook signature check has the analogous flaw: it selects **which** GitHub App/organization secret to verify against using a value taken straight from the untrusted JSON body, and that selection is never re-checked against the repository the resulting event handlers actually mutate.

### Finding Description
`WebhooksController#verify_signature` derives the "authenticating organization" purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a distinct `GithubApp` (and thus a distinct `webhook_secret`) per organization when the host is configured for multiple GitHub organizations, as documented: [3](#0-2) 

`verify_webhook_signature` then HMACs the **raw body** with whichever org's secret was picked, and - notably - trivially returns `true` if that org has no secret configured at all: [4](#0-3) 

Once the signature check passes, `create` dispatches the entire, attacker-controlled JSON body to event handlers (e.g. `PushHandler`), which resolve the target `stacks`/`Repository` from the payload independently of the `repository_owner` value used above: [5](#0-4) [6](#0-5) 

Because the field used to pick the verifying secret (`repository.owner.login` / `organization.login`) and the field(s) used to resolve the actual repository/stack that gets written to are never checked for equality, an attacker who legitimately controls a GitHub App installation for one, low-value organization on a shared Shipit instance can craft a raw POST to `/webhooks` where the "owner" used for signing selection points at their own org (whose secret they know, or which has no secret configured) while the repository identification data used by the handler points at a stack belonging to a different, higher-value organization on the same instance. This breaks exactly the documented isolation boundary: "*A Github application can only authenticate to the Github organization it's installed in*" [7](#0-6) .

### Impact Explanation
This crosses the `organization-that-authenticated == repository-that-is-written` binding. On a multi-tenant Shipit instance, it allows a low-privilege organization admin to forge GitHub events (pushes, statuses, check-suites, membership changes) against stacks/repositories that belong to a different organization, potentially triggering `GithubSyncJob`s, status updates or automerge-adjacent flows for a repository they do not control - i.e., cross-repository writes / unauthorized deploy triggers, matching the High/Critical impact bar.

### Likelihood Explanation
Likelihood is Low-to-Medium and conditioned on the host running the documented multi-organization GitHub App configuration and at least one tenant organization either configuring no `webhook_secret` or the attacker legitimately controlling that org's app credentials (not requiring theft of any secret belonging to the victim organization). No session, `ApiClient` token, or victim credentials are required.

### Recommendation
After signature verification succeeds, re-derive the organization from the resolved `Repository`/`Stack` record (not from the raw, attacker-controlled payload) and reject the event if it doesn't match the organization whose secret verified the signature - analogous to binding `address(this)` into the verified hash in the original report.

### Proof of Concept
1. Host configures two GitHub Apps, `OrgA` (attacker's own, secret known to attacker or left blank) and `OrgB` (victim, has a Shipit stack).
2. Attacker POSTs directly to `/webhooks` with `X-Github-Event: push` and a body such as:
```json
{
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies using `OrgA`'s (attacker-known/absent) secret - it passes.
4. `PushHandler` resolves the target stack from the `repository`/`full_name` data belonging to `OrgB` and enqueues `GithubSyncJob` against `OrgB`'s stack, even though the request was never authenticated by `OrgB`'s GitHub App.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
