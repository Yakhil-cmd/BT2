### Title
Stack-scoped ApiClient token can read CI status of any stack via CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true`, and `Api::BaseController#stack` enforces that scope by resolving stacks through `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `current_api_client.stack_id` when present. [1](#0-0) [2](#0-1)  `Api::CCMenuController` overrides `stack` to resolve the stack directly from the global `Stack` model instead of the client-scoped `stacks` relation, breaking the token-to-stack authorization binding. [3](#0-2) 

### Finding Description
This is an analog of the reported bug class: the report's root cause is that `LendStorage::borrowWithInterest()` uses one entity (the same-chain LToken's borrow index) to compute interest for a mapping that should be scoped/authorized by a different entity (the cross-chain borrow's own recorded index) — a binding mismatch between what should authorize an operation and what is actually used.

In this engine, the equivalent binding is: `ApiClient#stack_id` (the stack a token is authorized for) should equal the stack a request actually touches. `Api::BaseController` implements this correctly:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller (`CommitsController`, `DeploysController`, `TasksController`, `StacksController`, `LocksController`, `MergeRequestsController`, `OutputsController`) relies on this inherited `stack` method, so a token restricted to stack A cannot resolve stack B — `stacks.from_param!` will raise `ActiveRecord::RecordNotFound` because stack B is outside the `Stack.where(id: current_api_client.stack_id)` scope.

`Api::CCMenuController` breaks this equality by defining its own `stack` method that bypasses the client-scoped `stacks` relation entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

Before/after the equality is broken:
- Before (intended invariant): `stack resolved == stack authorized by token.stack_id` for every `Api::*Controller`.
- After (in `CCMenuController`): `stack resolved == any Stack matching params[:stack_id]`, independent of `token.stack_id`.

`require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack` — it never checks which stack the token is scoped to. [5](#0-4)  So a token created with `stack_id` set to stack A, and given `read:stack` permission (a normal, legitimate configuration for a stack-restricted CI badge/dashboard integration), can request `GET /ccmenu/:stack_id` for any other stack B and successfully render its status, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This breaks the intended per-stack authorization scope of `ApiClient` tokens, allowing a token holder to read CI/build state (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, `webUrl`, etc., rendered by `shipit/ccmenu/project`) for stacks the token was never authorized to access. This is an "unauthenticated [scope-bypassing] read of stack state" in the sense defined by the rules (escalation beyond the authorization boundary explicitly encoded by `ApiClient.stack_id`), which is a listed High-impact category.

### Likelihood Explanation
Any deployment that issues stack-scoped `ApiClient` tokens (a documented, intended use case — `belongs_to :stack, optional: true` exists specifically to restrict a token to one stack) and grants `read:stack` permission is affected. No special privilege beyond possessing one such legitimately-scoped token is required; the attacker only needs to know or guess another stack's `to_param` (owner/repo/environment), which is generally discoverable/public-ish information within an org. The `token` param authentication path (`ApiClient.authenticate(params[:token])`) further makes this reachable via a simple GET request with a query-string token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the client-scoped `stacks` relation (i.e., remove the override or reuse `stacks.from_param!(params[:stack_id])` from `BaseController`) so the token's `stack_id` scope is honored consistently with every other API controller.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` with `stack_id: stack_a.id` and `permissions: ['read:stack']`; obtain its `authentication_token`.
3. Send `GET /ccmenu/<stack_b_owner>/<stack_b_name>/<stack_b_environment>?token=<token>`.
4. Observe that `Api::CCMenuController#show` renders `stack_b`'s CI status successfully (HTTP 200), even though the token is scoped only to `stack_a`, because `stack` resolves via `Stack.from_param!` instead of the client-scoped `stacks.from_param!` used everywhere else in `Api::BaseController`. # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
