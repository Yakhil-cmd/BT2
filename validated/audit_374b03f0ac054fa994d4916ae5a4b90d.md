### Title
`ERC20Transactor::deposit_asset_with_surplus` silently drops non-ERC20 assets bundled in the same `DepositAsset` holding, causing permanent loss of the un-transferred asset - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::deposit_asset_with_surplus` only performs the ERC20 `transfer` for the *first* fungible asset found in the `AssetsInHolding` it receives, yet returns `Ok(surplus)` — discarding the entire `what` argument, including any other assets that were bundled into the same holding. This mirrors the reported EVM bug class ("depositing two asset types together loses the one that isn't processed") but the Substrate/XCM analog needs further confirmation of end-to-end reachability.

### Finding Description
`deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:225-306` takes ownership of the full `what: AssetsInHolding` value passed to it, but only inspects the *first* fungible asset returned by `what.fungible_assets_iter().next()`: [1](#0-0) 

The comment above the function explicitly documents the danger: [2](#0-1) 

On the success path, the function returns `Ok(surplus)` — a bare `Weight`, with **no accounting of the consumed `what`**: [3](#0-2) 

Compare this with the generic `TransactAsset` trait contract, where `deposit_asset`/`deposit_asset_with_surplus` either fully consumes `what` (returning `Ok`) or returns the *unspent* remainder back to the caller on failure so a tuple of transactors can try the next one: [4](#0-3) 

When composed in a tuple (as `AssetTransactors` is in the asset-hub runtimes), each tuple member receives the **entire** un-filtered `AssetsInHolding` on `deposit_asset`/`deposit_asset_with_surplus` calls, and only reroutes to the next transactor if that member returns `Err((unspent, AssetNotFound | Unimplemented))`: [5](#0-4) 

This means: if a `DepositAsset` XCM instruction targets holding that contains *both* an ERC20-matched asset and some other asset (e.g. the chain's native token, or a foreign PNA), and the `ERC20Transactor` is reached in the tuple with a holding whose first matched fungible asset is the ERC20 one, it will transfer only that ERC20 amount via `IERC20::transferCall` and then return `Ok(surplus)`, unconditionally treating the *whole* holding (including the other, untouched asset) as "deposited". The other asset is never actually transferred to the beneficiary, nor is it returned to the executor to be trapped/refunded — it is silently destroyed inside the `what` value, which goes out of scope.

This is analogous to the reported `BountyCore::receiveFunds` bug: two different asset kinds arrive together in one operation, only one kind is properly accounted for, and the other is irrecoverably lost, with no `require`/check enforcing that only a single, matching asset kind is present.

### Impact Explanation
If reachable, this would be a real, unbacked-loss bug: a user or protocol constructing (or ending up with, e.g. via `ExchangeAsset`, teleport+reserve compositions, or multi-asset `InitiateTransfer`/`DepositReserveAsset`) holding that contains more than one fungible asset and hits a `DepositAsset` filter (e.g. `Wild(All)` or `AllCounted(n)`) that is serviced by the ERC20 transactor tuple member would have any non-ERC20 asset in that batch permanently destroyed, with no path to reclaim it (no `AssetsTrapped` event, since the function returns `Ok`, not an error).

### Likelihood Explanation
Likelihood is **not confirmed**. The critical unresolved question is whether, in the deployed asset-hub `AssetTransactors` tuple configuration, the `ERC20Transactor` can actually be invoked with a holding value that contains a non-ERC20 asset mixed in with an ERC20 asset in a single `deposit_asset`/`deposit_asset_with_surplus` call. This depends on:
- Whether the XCM executor's `DepositAsset` instruction handler passes the whole filtered holding to the tuple as one call (as the tuple-impl code suggests) or whether it splits per-asset before dispatch — I was unable to fully inspect `polkadot/xcm/xcm-executor/src/lib.rs`'s `DepositAsset` handling within the remaining iteration budget, only confirming that `grep` found "DepositAsset" references there.
- Whether the concrete asset-hub `xcm_config.rs` `AssetTransactors` tuple actually orders `ERC20Transactor` alongside other transactors in a way that a mixed holding would reach it (I located references but did not fully read `asset-hub-westend/src/xcm_config.rs`'s tuple definition and ordering before the iteration budget ran out).
- Whether `Matcher::matches_fungibles` for the concrete runtime's ERC20 matcher config would ever be presented a holding containing assets it doesn't recognize as the first element vs. later elements (iteration order of `AssetsInHolding` matters for which asset is "first").

Given these gaps, I cannot assert this is definitively reachable via a real, unprivileged XCM `execute`/reserve-transfer/teleport path today — it requires confirming the exact tuple wiring and the executor's holding-splitting behavior for `DepositAsset`, which the codebase index did not let me fully verify in the time available.

### Recommendation
- In `ERC20Transactor::deposit_asset_with_surplus` (and `deposit_asset`), reject (return `Err`) rather than silently succeed whenever `what.len() != 1`, instead of relying solely on `defensive_assert!` (which is a no-op / soft assertion in production builds and does not prevent the funds loss).
- Alternatively, return any assets beyond the first fungible one as "unspent" so the executor/tuple can route them to the correct transactor or trap them properly, matching the safe pattern used elsewhere in the trait (returning unspent assets on partial failure).
- Confirm and, if necessary, fix the caller in `xcm-executor`'s `DepositAsset` handling to always split holding into single-asset chunks before calling into a `TransactAsset` tuple member that only supports one asset per call, or make `ERC20Transactor`'s "single asset" invariant enforced by its position/matcher configuration in the tuple, with tests exercising a holding containing both an ERC20 asset and a non-ERC20 asset in the same `DepositAsset`/`InitiateTransfer` instruction.

### Proof of Concept
Not executed. I did not have time within the remaining tool-call budget to write and run a concrete `xcm-executor` integration test (e.g., using the existing `deposit_with_retry` test harness style at `polkadot/xcm/xcm-executor/src/tests/deposit_with_retry.rs`) that constructs a two-asset holding (one ERC20-matched, one native/foreign) and drives it through the asset-hub-westend `AssetTransactors` tuple to observe the second asset vanish. This finding is therefore presented as a **code-level structural weakness with a documented self-admitted risk** (the function's own doc-comment acknowledges "the rest will be silently ignored"), but full reachability through the live runtime configuration and a passing/failing PoC test have not been demonstrated. Given the "Reject ... privileged prerequisites ... unless a demonstrable reproduction" requirement, this should be treated as a **candidate Medium/Low finding requiring further verification** rather than a confirmed exploitable bug.
