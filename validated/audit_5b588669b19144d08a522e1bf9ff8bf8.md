### Title
Cross-repository SHA collision lets an attacker's own GitHub webhook trigger `Hook.emit` on a victim's stack with attacker-controlled status data - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commits to update solely by SHA (`Commit.where(sha: params.sha)`), without ever checking that the SHA belongs to the repository/organization that actually authenticated the incoming webhook. `Commit#add_status` then calls `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` using each matched commit's own `stack`, so a genuinely-signed webhook from the attacker's own repository can drive hook emissions — carrying attacker-supplied `description`/`target_url`/`state` — for a completely unrelated victim stack whose commit happens to share the same SHA (e.g. a shared ancestor commit in a fork).

### Finding Description
The binding that must hold is: `repository_owner(payload)` (the org whose webhook secret validated the request in `WebhooksController#verify_signature`) `== stack.repository.owner` for every `Commit` object that `StatusHandler` mutates and for which `Hook.emit` is triggered. In the code, this equality is never enforced.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only proves that the payload was genuinely signed by GitHub for `repository_owner` (attacker's own org/app installation) — it says nothing about which commits/stacks the payload is allowed to affect.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that scopes lookups to `Repository.from_github_repo_name(repository_name)`, i.e., the repository named in the payload. This is the intended scoping mechanism.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** use this `stacks` scope. It runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped query across every `Commit` row in the database that matches the given SHA — including commits belonging to any other stack/organization.
- `Commit#create_status_from_github!` → `Commit#add_status` (`app/models/shipit/commit.rb:165-169, 366-386`) then emits, per matched commit:
```ruby
Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status))
...
Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
```
using `stack` = `commit.stack`, i.e., the **victim's** stack, not the attacker's.

Exploit flow: an attacker forks a victim's public repository (or otherwise obtains a repository that shares a historical commit SHA with the victim's tracked stack, e.g. common ancestor commits, template repos, or repos duplicated via `git clone`/rebase). The attacker's fork/repo is a Shipit-monitored repository under the attacker's own organization (a legitimate, unprivileged onboarding action). The attacker then sets an arbitrary commit status on their own fork's commit — same SHA as the victim's tracked commit — with a crafted `description`/`target_url`/`state`. GitHub sends a genuinely signed `status` webhook naming `repository.full_name = attacker/repo`. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then looks up `Commit.where(sha: ...)`, finds the victim's commit row (same SHA, different `stack_id`), and calls `Hook.emit(:commit_status, victim_stack, ...)` / `Hook.emit(:deployable_status, victim_stack, ...)`, delivering attacker-controlled data to the victim's configured Hook webhook endpoints.

Existing guards fail because: `verify_signature` authenticates *sender identity*, not *object ownership*; `ExplicitParameters` only validates the shape of `sha`/`state`/`description`, not repository binding; and the `stacks`/`repository_name` scoping helper that would normally enforce this binding exists in the base `Handler` class but is bypassed entirely by `StatusHandler`.

### Impact Explanation
The attacker can inject arbitrary `description`, `target_url`, and `state` values into the victim stack's outbound `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` events, which fan out to every `Hook` the victim organization configured for `commit_status`/`deployable_status` (e.g., Slack notifications, internal dashboards, or automation that consumes these webhooks and takes action based on `target_url`/`description`/`state`). This is a payload for one repository (attacker's) mutating another's stack/commit state and driving that stack's own webhook stream — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim stack whose commit SHA the attacker can reproduce (trivial via forking, since forks share full commit history/SHAs up to the fork point), and requires no privileges beyond owning/controlling a GitHub repository.

### Likelihood Explanation
Preconditions: the victim stack must have at least one `Hook` subscribed to `commit_status`/`deployable_status`, and the attacker needs a repository (their own or a fork) that is separately onboarded onto the same Shipit instance and shares a commit SHA with a commit already ingested into the victim's stack — trivially achievable by forking a public victim repository, since GitHub forks retain identical SHAs for all commits prior to divergence. The attacker's cost is minimal: fork the repo, add it to Shipit (if not already possible/needed depending on deployment), and set a commit status via the GitHub API on their own fork (standard, unprivileged GitHub action for a repo owner). This is fully repeatable per commit/SHA and scales to any number of shared-history commits.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to the repository/organization that authenticated the webhook, mirroring the `stacks` helper already provided by `Handler`. For example, restrict the lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or add an explicit join/filter ensuring `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`. Do the same for `refresh_statuses!`/`refresh_check_runs!` callers if they can be reached with cross-repo data.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test 'a status webhook signed for the attacker repo emits Hook events on the victim stack' do
          shared_sha = 'a' * 40

          victim_stack = shipit_stacks(:shipit)
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared ancestor')

          attacker_repo_full_name = 'attacker/repo'

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'description' => 'attacker-controlled description',
            'target_url' => 'https://evil.example/phish',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } },
          }

          emitted = []
          Hook.stub(:emit, ->(event, stack, data) { emitted << [event, stack, data] }) do
            StatusHandler.call(payload)
          end

          victim_events = emitted.select { |(_event, stack, _data)| stack == victim_stack }
          assert victim_events.any?,
            "Expected Hook.emit to fire for victim_stack (#{victim_stack.id}) " \
            "as a side effect of an attacker-signed webhook naming only #{attacker_repo_full_name}"

          _, _, data = victim_events.first
          assert_equal 'attacker-controlled description', data[:commit_status]&.description
          assert_equal victim_commit, data[:commit]
        end
      end
    end
  end
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

      Rails.logger.info([
