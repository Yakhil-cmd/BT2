### Title
Cross-tenant Status write via SHA-only lookup in StatusHandler#process - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, with no constraint tying the lookup to the repository that authenticated the webhook. Any attacker who owns a GitHub repo tracked by the same Shipit instance can produce (or reuse) a commit SHA shared with a victim repository and push a signed `status` webhook that writes a `Status` row onto the victim's commit.

### Finding Description
The broken binding: `request.repository_owner` (used in `verify_signature` to select the `webhook_secret`) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler — but the code never enforces this.

Path: `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) . `verify_signature` only checks the HMAC signature against the `webhook_secret` of the GitHub App/organization derived from `params.dig('repository','owner','login')` in the *attacker's own payload* [2](#0-1)  — this proves the payload was sent by someone who controls `attacker/evil`'s webhook secret, not that it is authorized to mutate any particular commit.

`StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This query is global across all `Stack`/`Repository` records — it does not filter by `params.dig('repository','full_name')`, `repository_owner`, or any stack ownership relation. `create_status_from_github!` writes into `commit.statuses` [4](#0-3) , and `add_status` emits hooks and can affect `stack.schedule_merges` and deployability computations for the commit's actual stack [5](#0-4) .

No other guard closes this gap: `drop_unhandled_event` only checks event type presence; the `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) validates payload shape, not ownership; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` in this unauthenticated webhook path — webhooks are inherently repo-to-Shipit machine calls, and the only trust boundary is the signature, which is scoped to the *sending* repository/org, not to the commit being updated.

### Impact Explanation
An attacker who owns any repository tracked as a Shipit stack (`attacker/evil`) can write arbitrary `Status` rows (state, context, description, target_url) onto any `Commit` record in the entire Shipit instance that happens to share a SHA with a commit they control — including commits belonging to other tenants' private stacks (`victim/secret-repo`). This corrupts CI state Shipit believes is true for another repository, can flip a commit from failing/pending to `success`, and can trigger `stack.schedule_merges` and continuous-delivery evaluation for the victim stack, potentially causing an unauthorized deploy of a commit whose real CI status is failing. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". Blast radius: any tenant sharing the Shipit instance, repeatable per request, requiring only a colliding/shared SHA.

### Likelihood Explanation
Preconditions are modest: the attacker needs a GitHub repo they control that is already tracked as a Shipit stack (a very common precondition — Shipit is typically used by many teams/repos in one instance), and a SHA collision or a shared/borrowed SHA with the victim's tracked commit. The prompt's easiest variant — "simply copies a public SHA that Shipit already tracks for victim/secret-repo" — is realistic if the victim's commit is a merge commit or cherry-pick shared across visible history, or if a SHA is otherwise observable (e.g., via a public fork, shared submodule, or previously public repo). No secrets, sessions, or elevated privileges are needed — only the attacker's own valid `webhook_secret` for their own repo, which they legitimately have. This is repeatable arbitrarily against any other stack whose commit SHA the attacker learns.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to commits belonging to stacks whose repository matches the authenticated webhook's repository, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: ..., name: ... })` using the repository extracted from the verified payload, and propagate that repository context from `WebhooksController` into the handler call rather than trusting `sha` alone as a global key.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "does not write a status onto a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # belongs to victim/secret-repo fixture
  attacker_stack = shipit_stacks(:cyclimse) # belongs to attacker/evil fixture

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  params = ActionController::Parameters.new(
    sha: shared_sha, state: 'success', context: 'ci/attacker'
  )

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(
      params.merge(repository: { full_name: 'attacker/evil' })
    )
  end
end
```
Assert `victim_commit.reload.statuses.count` is unchanged while `attacker_commit.reload.statuses.count` increased, disproving that `repository_owner` used for signature verification is bound to the commit actually mutated (`Commit.where(sha:)` has no repository filter, as shown at `app/models/shipit/webhooks/handlers/status_handler.rb:21`).

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end
