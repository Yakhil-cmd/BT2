### Title
Api::CCMenuController#show discloses any stack's deploy status/sha to a token scoped to a different stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` defines a `stacks` scope that restricts lookups to `current_api_client.stack_id` when the client is stack-scoped, and a `stack` method (`stacks.from_param!(params[:stack_id])`) that enforces this scoping for the rest of the API. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely bypassing the per-client stack restriction.

### Finding Description
The binding that should hold is: `{ stack_id readable via token_A } = { current_api_client(token_A).stack_id }` when the client is stack-scoped, exactly as implemented in `BaseController#stacks`: [1](#0-0) 

However, `CCMenuController` redefines `stack` to skip this scope entirely: [2](#0-1) 

The controller only enforces `require_permission :read, :stack`, which checks whether the *operation* `read:stack` is permitted for the client, not whether the *specific* requested stack matches the client's `stack_id`: [3](#0-2) [4](#0-3) 

Since `require_permission!` only calls `current_api_client.check_permissions!(operation, scope)` (an operation/scope check, not an identity check against `stack_id`), and the controller's own `stack` method resolves against `Stack.from_param!` (unscoped), any client holding a token with `read:stack` permission — even one explicitly created and scoped to a single stack via `stack_id` — can supply an arbitrary `stack_id` in the URL and receive that other stack's CCMenu XML, including `lastBuildStatus`, `lastBuildLabel` (deploy sha), `activity`, and lock status, via `#show`: [5](#0-4) 

Attack flow: attacker holds a legitimately-issued token scoped to stack A (`stack_id = A`). They enumerate `owner/repo/branch` triples for other stacks (e.g., from public GitHub org listings) and issue `GET /stacks/:owner/:repo/:branch/ccmenu.xml?token=<token_A>` (or with Basic Auth) for each guessed `stack_id`. Because `CCMenuController#stack` never consults `current_api_client.stack_id`, every request for an existing stack returns 200 with the real deploy sha/status/build state, rather than 403/404.

### Impact Explanation
This is a cross-tenant, unauthenticated-relative-to-scope read of stack state: a token restricted to one stack can read the latest deploy identity (commit sha), build/deploy status, activity, and lock state of every other stack hosted on the instance. This matches the High severity category "unauthorized read of stack state" via escalation beyond the token's intended `stack_id` scope. It is fully repeatable and scales to systematic enumeration across all stacks (multi-tenant blast radius = entire `Stack.all` set), not limited to a single foreign stack.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs any valid API token with `read:stack` permission for at least one stack (a normal, low-privilege grant many integrations legitimately receive), and the target Shipit instance must host multiple stacks (a typical multi-repo/multi-team deployment). No GitHub secrets, session, or elevated Shipit role is required. The attack is a trivial GET-request loop over guessed `stack_id` values, with no rate limiting or additional authorization barrier in this code path.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on `BaseController#stacks`/`#stack`, i.e. resolve via `stacks.from_param!(params[:stack_id])` so the lookup is scoped to `current_api_client.stack_id` (returning 404 via `Stack::NotFound` when the requested stack falls outside the client's scope), consistent with the rest of the API controllers.

### Proof of Concept
Minitest under `test/controllers/api/ccmenu_controller_test.rb` (already existing test file, extend it):
1. Create three stacks: `stack_1`, `stack_2`, `stack_3` in different repos, each with a deploy having distinct `sha`.
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_1.id`.
3. For `stack_id` in `[stack_1, stack_2, stack_3]`, `GET :show, params: { stack_id: stack.to_param, token: @client.authentication_token }`.
4. Assert: for `stack_1` -> `assert_response :ok` (expected, in-scope).
5. Assert: for `stack_2` and `stack_3` -> current code yields `assert_response :ok` with `lastBuildLabel` matching the foreign stack's deploy sha (demonstrating the leak); the fix should make these return `assert_response :not_found` (or 403), proving the binding `{readable stack_ids} = {current_api_client.stack_id}` is restored.
