### Title
Race between periodic unit-cache eviction (`shrinkCache`) and in-flight AA trigger execution causes a crash via unhandled `throw` - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `handlePrimaryAATrigger` executes an AA trigger asynchronously (potentially long-running oscript evaluation, secondary triggers, DB writes) and, only after the trigger finishes, looks up `storage.assocStableUnits[unit]` to bump `count_aa_responses`. If that cache entry has been evicted in the meantime by the periodic `shrinkCache()` job, the code hits `throw Error(...)`, which is unhandled here and crashes the node process — a remotely triggerable denial of service, analogous to the OpenVPN UAF that fires "during TLS session promotion or expiry" (here: unit promotion to `assocStableUnits` racing with cache expiry/eviction).

### Finding Description
`handlePrimaryAATrigger` reads the trigger's mci/unit from the `aa_triggers` table and, without holding the global `"write"` mutex, performs a chain of async operations (`readMcUnit`, `readUnit`, `handleTrigger` — full oscript evaluation, possibly cascading into secondary AA triggers) before finally doing: [1](#0-0) 

At line 104-106, it unconditionally expects the entry to still exist in `storage.assocStableUnits`:
```
let objUnitProps = storage.assocStableUnits[unit];
if (!objUnitProps)
    throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
``` [2](#0-1) 

Meanwhile, `storage.js`'s `shrinkCache()` runs on a fixed timer (`setInterval(shrinkCache, 300*1000)`) and, after acquiring the `"write"` mutex, deletes stale entries from `assocStableUnits` (and other caches) for any unit whose `main_chain_index` is more than roughly 100+ MCIs behind the current stable point: [3](#0-2) 

`handleAATriggers()` processes ALL pending rows currently in the `aa_triggers` table (across potentially many historical MCIs) serially via `async.eachSeries`, only holding the narrower `['aa_triggers']` mutex, not `"write"`: [4](#0-3) 

Because `handlePrimaryAATrigger` does not hold the `"write"` lock while it performs its (potentially slow) trigger evaluation, `shrinkCache()` can run concurrently on the `"write"` mutex and delete `assocStableUnits[unit]` for a unit whose trigger execution is still in flight (e.g., an old backlog trigger, or one delayed by slow/complex oscript). When execution resumes and reaches the cache lookup, the object it depends on is gone, and the code throws instead of handling this gracefully — the classic "still referencing an object whose lifecycle state changed/expired underneath it" bug class from the OpenVPN CVE, mapped onto ocore's unit-props cache lifecycle (stable-cache population at MCI stabilization vs. periodic expiry/eviction).

### Impact Explanation
An uncaught `throw` inside a deeply nested async callback chain (no surrounding `try/catch`, invoked from `db.query`/`conn.query` callbacks) is not caught by Express/network error handling and results in an uncaught exception that crashes the Node.js process. Any full node processing AA triggers is affected — this is a network-wide "unable to confirm new units"/DoS condition, satisfying the required "network unable to confirm new units" impact bucket, and it is reachable purely by an ordinary AA trigger sender (posting payments that trigger AAs), not by a malicious peer/hub/node.

### Likelihood Explanation
Triggering requires: (1) a backlog of pending `aa_triggers` rows (achievable by an attacker flooding many AA-triggering transactions across several MCIs, since triggers are processed serially and each can itself spawn secondary AA calls/oscript evaluation), and (2) the node's unit caches (`assocCachedUnits`, `assocCachedUnitAuthors`, etc.) growing past `MAX_ITEMS_IN_CACHE`, causing `shrinkCache()` to actually run its eviction branch. Both conditions are plausible under sustained load that an unprivileged party fully controls (posting many units/AA triggers), though it does require timing alignment (the 5-minute `shrinkCache` interval vs. trigger backlog depth), making it a medium-likelihood race rather than a trivially reproducible one-shot bug.

### Recommendation
- Hold the `"write"` mutex (or an equivalent per-unit lock) for the full duration of `handlePrimaryAATrigger`'s critical section that reads/writes `storage.assocStableUnits[unit]`, so `shrinkCache()` cannot run concurrently and evict units that are mid-trigger-execution.
- In `shrinkCache()`, exclude units that currently have a pending row in `aa_triggers`, or otherwise pin/refresh the cache entry while a trigger execution is in flight.
- Replace the `throw Error(...)` at aa_composer.js:106 with a graceful re-fetch of unit props from the DB (or a safe recovery path) instead of crashing the process, to bound the blast radius of any residual race.

### Proof of Concept
1. An attacker posts a large number of units that trigger many distinct AAs across many consecutive MCIs (e.g., hundreds of MCIs' worth of trigger events), causing `aa_triggers` rows to accumulate faster than `handleAATriggers()`'s `async.eachSeries` can drain them (each trigger can itself be complex — nested secondary triggers, expensive oscript loops up to the complexity limit).
2. The attacker also drives normal network traffic/units so that `assocCachedUnits`/`assocCachedUnitAuthors`/etc. on the target node exceed `MAX_ITEMS_IN_CACHE`, which makes the 5-minute `setInterval(shrinkCache, 300*1000)` job actually perform evictions.
3. While `handlePrimaryAATrigger` is deep inside `handleTrigger(...)` for an older backlog trigger unit (older than roughly `COUNT_MC_BALLS_FOR_PAID_WITNESSING + 10` MCIs behind current stable), `shrinkCache()` acquires the `"write"` mutex and deletes that unit from `storage.assocStableUnits`.
4. When `handlePrimaryAATrigger`'s callback reaches `storage.assocStableUnits[unit]` (aa_composer.js:104), it is `undefined`, and the `throw Error(...)` at line 106 fires inside an async DB callback with no enclosing try/catch, crashing the Node process for every full node that races the eviction against trigger processing this way.

Note: I was unable to fully confirm the exact numeric value of `MAX_ITEMS_IN_CACHE` and the precise steady-state cache growth rate under load (index only returned the declaration location, not its value), so the exact conditions needed to reliably trigger `shrinkCache`'s eviction branch during a trigger backlog are inferred from the code logic rather than empirically measured.
