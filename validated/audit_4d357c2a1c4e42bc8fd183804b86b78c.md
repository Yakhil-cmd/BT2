### Title
Per-recipient rounding in headers-commission distribution can mint or destroy bytes - (File: headers_commission.js)

### Summary
When a unit wins another unit's headers commission, the commission amount is split among the recipients listed in `earned_headers_commission_recipients`. Each recipient's share is computed with `Math.round(full_amount * share / 100.0)` independently, with no compensating remainder assigned to a single "last" recipient. Because JavaScript's `Math.round` rounds `.5` up, splitting an odd `full_amount` across recipients whose shares are chosen by the (unprivileged) unit author can make the sum of the rounded per-recipient amounts exceed the original `full_amount`, creating byte-outputs unbacked by an equivalent deduction from the payer. This is the same class of bug as the ToB Umee finding: fixed-precision truncation/rounding of a proportional split causes the total paid out to differ from the true amount owed, and the direction of the rounding benefits the (attacker-controlled) recipient rather than the network.

### Finding Description
`calcHeadersCommissions` distributes the `headers_commission` fee paid by a parent ("payer") unit to the author(s) of the winning child unit. If the winning child specifies multiple recipients via `earned_headers_commission_recipients` (validated only to have shares that are positive integers summing to exactly 100, see `validateHeadersCommissionRecipients`), each recipient's payout is computed independently: [1](#0-0) [2](#0-1) 

Both the in-RAM path and the SQL-derived path use the identical formula `Math.round(full_amount * share / 100.0)` per recipient, with a comment acknowledging the rounding happens *before* summation across payer units: [3](#0-2) 

`earned_headers_commission_recipients` is fully attacker-controlled input on any multi-author unit (and is even accepted, unvalidated for author count, whenever present), the only server-side constraint being that the listed shares are positive integers summing to 100: [4](#0-3) 

An attacker who is the sole author of the *only* child unit built on a given parent within the eligible MC window automatically becomes the headers-commission winner (`getWinnerInfo` returns the sole child without any lottery contest): [5](#0-4) 

The attacker can then pick a two-address, 50/50 split. For any odd `full_amount` (headers commission is a deterministic function of unit byte-size and is easy to steer to an odd value by controlling padding/number of parents/authors), `Math.round(full_amount*0.5)` rounds `.5` up for **both** recipients, so:
`round(full_amount/2) + round(full_amount/2) = full_amount + 1` when `full_amount` is odd.

The resulting `headers_commission_outputs` rows are later spendable as `headers_commission` inputs, i.e., they become real, spendable base-asset (bytes) balance for the attacker's addresses — one extra byte minted per exploit unit, with no corresponding deduction anywhere from the payer (whose `headers_commission` deduction, fixed by `objUnit.headers_commission` at composition time, is unchanged).

This mirrors the ToB Umee finding precisely: a proportional distribution computed with fixed-point rounding, where the rounding direction is chosen ad-hoc per share instead of always favoring the network, and where an unprivileged party (any unit poster who can author both a parent and its sole child, and who freely chooses recipient shares) can repeat the operation to accumulate unbounded gains.

### Impact Explanation
This is a supply-inflation bug in the ocore ledger's native currency. Each exploit round inflates total byte supply by a small, fixed amount (e.g., +1 byte per 50/50 split of an odd-sized headers commission, and potentially larger multi-recipient combinations could yield larger absolute overages, though bounded by the number of recipients and the commission size). Because the attack is fully attacker-controlled (parent unit size, child recipient list, and winning the trivial one-child lottery) and repeatable at will, it satisfies the "supply inflation" acceptance criterion: currency can be created without a matching deduction, breaking the invariant that total headers-commission distributed equals total headers-commission collected from payers. Sustained repetition (automatable, cheap—bounded only by transaction fees for creating parent/child unit pairs) allows continuous, unbounded token creation.

### Likelihood Explanation
High reachability: any address can author units, freely set `earned_headers_commission_recipients` on a multi-author unit it fully controls (both authors can be attacker-owned addresses), and reliably become the sole/winning child of its own parent by not exposing the parent to other authors in the relevant window (or racing them, since being sole child of your own unit is trivial when you don't broadcast intent to compete). Headers-commission size is a deterministic, attacker-influenceable value (via padding/number of parents, authors, witnesses fields), so hitting an odd value is straightforward. No privileged role, hub, or node collusion is required — this is reachable purely by posting units as an ordinary user.

### Recommendation
- Short term: When distributing `full_amount` across multiple recipients, round all shares except the last down (or use `Math.floor`) and assign the remainder (`full_amount - sum_of_floors`) to the last recipient (sorted deterministically, e.g., by address, as already done), guaranteeing the sum of distributed amounts always exactly equals `full_amount`. Apply the same fix consistently to both the in-RAM (`arrValuesRAM`) and SQL-derived (`arrValues`) code paths in `headers_commission.js`.
- Long term: Add invariant checks (e.g., in tests or a periodic consistency audit) asserting that `SUM(headers_commission_contributions.amount)` grouped by payer unit always equals that unit's `headers_commission`, and add fuzz/property-based tests exercising many share combinations (including edge values like 50/50, 33/33/34, and highly skewed splits) to catch any residual rounding drift before deployment.

### Proof of Concept
1. Attacker controls addresses A and B.
2. Attacker crafts unit P (parent) with a byte-size such that `objUnit.headers_commission` is odd (e.g., 157), authored by any of the attacker's addresses.
3. Attacker immediately posts unit C as the sole child unit built directly on P, authored jointly by A and B (2 authors), with:
   `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]`
   — this passes `validateHeadersCommissionRecipients` since shares are positive integers summing to 100: [6](#0-5) 
4. No other child competes for P's headers commission within the MC window, so `getWinnerInfo` trivially selects C: [7](#0-6) 
5. During `calcHeadersCommissions`, `full_amount = 157` is split: `Math.round(157*50/100) = round(78.5) = 79` for A, and `79` for B, for a total of 158 spendable bytes credited to `headers_commission_outputs`, one more than P's actual `headers_commission` of 157: [1](#0-0) 
6. Repeating steps 2–5 across many parent/child pairs accumulates unbacked byte balances, which the attacker later spends normally as `headers_commission` inputs, realizing free, minted currency.

	if (arrChildren.length === 1)
		return arrChildren[0];
	if (arrChildren.length === 0)
		throw Error("no children for hc");
	arrChildren.forEach(function(child){
		child.hash = crypto.createHash("sha1").update(child.child_unit + child.next_mc_unit, "utf8").digest("hex");
	});
	arrChildren.sort(function(a, b){ return ((a.hash < b.hash) ? -1 : 1); });

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
