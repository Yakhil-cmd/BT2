### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` writes a `Status` to every `Commit` row that shares the reported SHA across the entire Shipit installation, without checking that the SHA belongs to the repository named in the verified webhook payload. Since git SHAs (e.g. the universal empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or a cherry-picked commit) can be identical across unrelated repositories, an attacker who legitimately controls a tracked repository B can flip the CI status of a commit belonging to a different tenant's repository A.

### Finding Description
The broken binding: `repository named in the verified payload` (`attacker/B`) `== repository owning the Commit row mutated` (must be A). This equality is guaranteed by `Handler#stacks`/`Handler#repository_name`, which every other handler uses to scope work to `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` [1](#0-0) , as seen in the pull-request handlers, e.g. `OpenedHandler#repository` [2](#0-1) .

`StatusHandler#process`, however, never calls `stacks` or `repository_name`; it looks up commits purely by SHA and mutates all matches: [3](#0-2) 

`Commit.create_status_from_github!` then unconditionally creates the `Status` record for whichever commit was matched: [4](#0-3) 

`WebhooksController#verify_signature` only authenticates that the request was signed by the GitHub App/organization named in the payload's `repository.owner.login` (or `organization.login`) — it never checks that the specific repository named in the payload is the one whose commit gets mutated: [5](#0-4) 

Critically, the webhook secret used for verification is scoped per-organization (or globally, in the common single-app configuration), not per-repository: `Shipit.github(organization:)` resolves one `GitHubApp`/secret per org (or a single global one if `github_default_organization` is nil) [6](#0-5) . Any repository sharing that organization/app installation — including one owned entirely by the attacker — produces a validly-signed webhook.

Exploit flow:
1. Attacker owns/administers repository B, which is tracked by the same Shipit instance/GitHub App (single global app, or same org as tenant A).
2. Attacker uses their own legitimate GitHub credentials for B to set a commit status via the GitHub API (`POST /repos/attacker/B/statuses/4b825dc642cb6eb9a060e54bf8d69288fbee4904` with `state: success`) — the empty-tree SHA exists identically in every git repository, including A's.
3. GitHub delivers a `status` webhook to Shipit, correctly signed with the org/app's `webhook_secret`. `verify_signature` passes because the signature is valid for that organization.
4. `StatusHandler#process` runs `Commit.where(sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904')`, which returns **both** A's and B's `Commit` rows (or any tenant's commit with that SHA), and calls `create_status_from_github!` on all of them — writing a `success` `Status` onto tenant A's commit despite the payload only ever authenticating tenant B.

No existing guard prevents this: `verify_signature` authenticates organization/app identity, not per-repository identity; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository scoping; and `StatusHandler` uniquely omits the `Handler#stacks`/`repository_name` scoping pattern used everywhere else.

### Impact Explanation
A forged/legitimately-sent status from an attacker-controlled repository can flip the recorded CI status (`success`/`failure`/`error`) on another tenant's `Commit` row. Since `deployable?` and continuous-deployment triggers depend on commit `state` [7](#0-6) , and status transitions to `success` enqueue `ProcessMergeRequestsJob`/continuous delivery flows (see `commits_test.rb` transition tests) [8](#0-7) , this can enable an unauthorized deploy of another tenant's commit that never actually passed CI — a cross-tenant write matching the Critical category ("a payload for one repository mutating another's stack, commit, task"). The attack is trivially repeatable against any tenant sharing the empty-tree SHA or any other shared commit (e.g. cherry-picks, common base commits, initial commits from templates).

### Likelihood Explanation
Preconditions: multiple repositories/tenants tracked by the same Shipit instance/GitHub App installation (a common, documented single-app deployment per `docs/setup.md`), and a shared SHA between the attacker's repo and the victim's repo (guaranteed for the empty-tree SHA, or achievable via cherry-picks/shared history). The attacker needs nothing beyond ownership/push access to one tracked repository — no Shipit credentials, no `webhook_secret` knowledge, and no privileged role, since GitHub signs the webhook using the shared org/app secret automatically. This is highly feasible and repeatable at will.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the verified payload, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`, mirroring the `Handler#stacks`/`repository_name` pattern used by all other handlers, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status payload scoped to repository B must not mutate repository A's commit" do
          shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

          repo_a = Repository.create!(owner: 'tenant', name: 'a')
          stack_a = repo_a.stacks.create!(environment: 'production', repository: repo_a)
          commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus))

          repo_b = Repository.create!(owner: 'attacker', name: 'b')
          stack_b = repo_b.stacks.create!(environment: 'production', repository: repo_b)
          stack_b.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus))

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/b', 'owner' => { 'login' => 'attacker' } }
          }

          assert_equal 'unknown', commit_a.reload.state # repository A must not have been authenticated

          StatusHandler.call(payload)

          # BUG: commit_a flips to success even though the payload only authenticated attacker/b
          assert_equal 'unknown', commit_a.reload.state, "cross-tenant write: repo B's payload mutated repo A's commit"
        end
      end
    end
  end
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
