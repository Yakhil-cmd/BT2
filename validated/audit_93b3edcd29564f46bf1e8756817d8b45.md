### Title
Allowlist bypass via flag-value smuggling permits injection of arbitrary `gh` CLI flags (e.g. `--repo`), breaking repository scoping - ([File: scripts/gh.sh])

### Summary
`scripts/gh.sh` validates that only `--comments`, `--state`, `--limit`, `--label` flags are passed to the underlying `gh` CLI call, and documents that "all commands are scoped to the current repository via `GH_REPO`". The flag/positional separation loop blindly appends the token that follows `--state`/`--limit`/`--label` (when not using `=` syntax) to `FLAGS` without ever passing it through the `ALLOWED_FLAGS` check, letting an attacker smuggle in any additional `gh` flag, including `--repo=<other>`, which overrides the intended repository scope.

### Finding Description
The argument-parsing loop in `scripts/gh.sh` treats `--state`, `--limit`, and `--label` as "flags with values" and sets `skip_next=true` after encountering one of them without a literal `=`: [1](#0-0) 

When `skip_next` is `true`, the very next token is appended to `FLAGS` unconditionally, **before** the `-*` / `ALLOWED_FLAGS` check is ever applied:

```
if [[ "$skip_next" == true ]]; then
  FLAGS+=("$arg")
  skip_next=false
```

This means a caller can pass, e.g., `--state --repo=attacker/other-repo` as arguments. `--state` is validated and accepted, then `--repo=attacker/other-repo` is swallowed as `--state`'s "value" and pushed straight into `FLAGS` — it never goes through the `matched=true/false` allowlist logic that would normally reject any flag not in `ALLOWED_FLAGS`.

For `issue list` and `label list`, the wrapper relies solely on the `GH_REPO` env var for scoping (it never appends an explicit `--repo "$REPO"` the way it does for `search issues`): [2](#0-1) 

Since `gh`'s `--repo` command-line flag takes precedence over the `GH_REPO` environment variable, smuggling `--repo=<attacker-controlled-repo>` (or `--repo <value>` via the same trick chained twice) redirects the entire `issue list` / `label list` call to a different repository, defeating the single security invariant the script's own comments claim to enforce ("All commands are scoped to the current repository").

This wrapper is invoked by LLM-driven automation (Claude agent) reading attacker-influenced content: the slash commands `.claude/commands/triage-issue.md` and `.claude/commands/dedupe.md` grant `allowed-tools: Bash(./scripts/gh.sh:*)` and instruct the agent to run `./scripts/gh.sh` based on its own reasoning over issue titles/bodies/comments: [3](#0-2) [4](#0-3) 

An issue body containing a prompt-injection payload instructing the agent to invoke `./scripts/gh.sh issue list --state --repo=<attacker-repo> --limit 5` (or similar) would have that command executed by the agent, since the agent (not a human) constructs the exact CLI invocation and has no reason to suspect the flag-smuggling bypass.

### Impact Explanation
This is a trust-boundary bypass of the repo-scoping guard that `scripts/gh.sh` is explicitly designed to enforce. An attacker who can inject content into an issue/PR that the triage/dedupe automation reads (any unprivileged user who can open an issue) can cause the automation's `gh` calls to target a repository other than the intended one, using whatever GitHub token/credentials the automation environment holds. Depending on the token's access, this can leak data from or query repos the automation was never meant to touch, and more generally demonstrates that the flag allowlist — the only control preventing arbitrary `gh` flag injection — can be defeated to smuggle in *any* single-token flag/value pair (not just `--repo`), undermining the "only specific subcommands and flags are allowed" security guarantee documented at the top of the script.

### Likelihood Explanation
No special privileges are required — only the ability to post issue/PR content that an LLM-driven workflow (`triage-issue.md`, `dedupe.md`) will read and act on with `./scripts/gh.sh`. The bypass itself is a deterministic, always-reproducible parsing bug (any `--state`, `--limit`, or `--label` immediately followed by another `-`-prefixed token without `=` triggers it), requiring no timing or race conditions.

### Recommendation
Validate the "value" token consumed via `skip_next` as well — reject it if it itself starts with `-` (i.e., looks like a flag) rather than unconditionally trusting it. For example:
```bash
if [[ "$skip_next" == true ]]; then
  if [[ "$arg" == -* ]]; then
    echo "Error: flag value cannot start with '-'" >&2
    exit 1
  fi
  FLAGS+=("$arg")
  skip_next=false
```
Additionally, explicitly pass `--repo "$REPO"` on every invocation (as already done for `search issues`) so that even a smuggled `--repo` flag would be overridden/duplicated rather than silently taking effect (note: `gh` generally uses the last `--repo` on the command line, so combining both mitigations is recommended).

### Proof of Concept
Integration test (bash):
```bash
#!/usr/bin/env bash
set -euo pipefail

export GH_REPO="safe-org/safe-repo"

# Stub `gh` to capture the arguments it was invoked with instead of calling GitHub.
mkdir -p /tmp/binstub
cat > /tmp/binstub/gh <<'EOF'
#!/usr/bin/env bash
printf '%s\n' "$@" > /tmp/gh_captured_args
EOF
chmod +x /tmp/binstub/gh
export PATH="/tmp/binstub:$PATH"

./scripts/gh.sh issue list --state --repo=attacker-org/other-repo --limit 5

# Assert the smuggled --repo flag reached the gh invocation, proving allowlist bypass.
grep -qx -- "--repo=attacker-org/other-repo" /tmp/gh_captured_args && \
  echo "VULNERABLE: --repo flag smuggled past allowlist" && exit 1

echo "SAFE: smuggled flag was rejected"
```
Expected (current/vulnerable) behavior: the script exits 0 and `/tmp/gh_captured_args` contains the line `--repo=attacker-org/other-repo`, confirming the disallowed flag reached `gh` unchecked. After the fix, the script should exit non-zero with an error before invoking `gh`.
