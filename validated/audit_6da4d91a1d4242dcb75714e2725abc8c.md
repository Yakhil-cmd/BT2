### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` (used for signature verification) vs `repository.full_name` (used to resolve the target stack) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but the handler that actually acts on the payload resolves the target `Stack` using the independent `repository.full_name` field. Because the HMAC only proves the payload was signed with *some* configured organization's secret — not that the organization used for verification matches the repository the payload claims to affect — an attacker who legitimately controls one tenant/organization configured in this multi-tenant Shipit instance can forge a validly-signed webhook that targets a completely different organization's repository/stack.

### Finding Description
`Shipit.github(organization:)` and `Shipit.github_app_config(organization)` support multiple independent GitHub organizations, each with its own `webhook_secret`, keyed under `secrets.github` [1](#0-0) .

The webhook controller determines *which* organization's secret to verify against purely from attacker-controlled JSON fields:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

and then verifies the signature using that organization's secret:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [3](#0-2) 

Once verification passes, the request body is dispatched to handlers unchanged: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Every handler resolves the affected stacks from a *different* JSON field:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the affected repository/stack) are two unrelated fields in the same JSON body that the attacker fully controls before signing. Nothing ties them together. The `PushHandler`, which triggers `stack.sync_github` and ultimately `GithubSyncJob` [6](#0-5) [7](#0-6) , and every other default handler (`status`, `check_suite`, `pull_request`, `membership`) inherit this same `Handler#stacks`/`#repository_name` resolution, so all of them are affected.

The equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `organization that owns the repository actually acted upon (repository.full_name)`

### Impact Explanation
An attacker who is a legitimate admin of one GitHub organization ("Org A") configured as a tenant in this Shipit instance knows Org A's own webhook secret (since they configure it in their own repo/org's webhook settings on GitHub, or GitHub delivers validly-signed payloads to the endpoint on their behalf). Using that secret, the attacker can POST directly to Shipit's `/webhooks` endpoint with a payload where `repository.owner.login`/`organization.login` = `"OrgA"` (so `verify_signature` picks Org A's secret and the HMAC checks out) but `repository.full_name` = `"OrgB/target-repo"` (a completely different tenant's repository). This lets the attacker:
- Force `push` events to trigger `GithubSyncJob` against Org B's stack (via `PushHandler`), causing Shipit to re-sync commits and re-evaluate deploy state for a repository the attacker has no access to.
- Forge `status`/`check_suite` events against Org B's commits (same `Handler#stacks` resolution), potentially marking arbitrary Org B commit SHAs as passing required checks used to gate whether a commit is deployable, which can enable an unauthorized deploy/merge decision downstream.

This crosses the repository-write/organization-authorization boundary explicitly called out as in-scope ("an organization that authenticated versus the repository that is written"), and can lead to an unauthorized deploy path for a cross-tenant repository — matching the Critical/High impact bar.

### Likelihood Explanation
Exploitability requires the attacker to control/administer at least one GitHub organization already configured as a legitimate tenant in the Shipit instance (i.e., know that organization's `webhook_secret`, which they legitimately have as that org's own webhook administrator). No access to Org B, no Shipit session, and no privileged Shipit account are required — only knowledge of one's own tenant's webhook secret, which is exactly the kind of "unprivileged attacker" boundary this scan targets (a peer tenant, not a Shipit operator). This is realistic for any multi-organization Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, use a single, consistent source of truth for "which organization/repository does this payload belong to," and cross-check it: after verifying the signature with the organization derived from `repository.owner.login`, assert that `repository.full_name` actually belongs to that same organization (e.g., `full_name.split('/').first == repository_owner`) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Shipit is configured with two tenants in `secrets.github`: `orga` (secret `S_A`) and `orgb` (secret `S_B`), each mapped to their own stacks/repositories.
2. Attacker controls `OrgA` (knows `S_A`) but has no access to `OrgB`.
3. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-or-known-sha-in-orgb-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully against `S_A` [3](#0-2) .
6. `PushHandler` resolves `repository_name` = `"OrgB/target-repo"` and enqueues `GithubSyncJob` for `OrgB`'s stack [6](#0-5) , despite the request never being authenticated by anything belonging to `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
