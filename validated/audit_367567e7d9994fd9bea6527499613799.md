Confirmed: Shipit supports **multi-organization GitHub App configs**, each keyed by organization name with its own `webhook_secret` [1](#0-0) . The `WebhooksController#verify_signature` selects which app config (and thus which HMAC secret) to verify against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [2](#0-1) . However, the actual event handlers (e.g. `PushHandler`) locate the target `Stack`/`Repository` using a **different, independently-controlled field**: `payload.dig('repository', 'full_name')` [3](#0-2) [4](#0-3) .

### Title
Cross-Organization Webhook Confusion Triggers Unauthorized Sync/Deploy on Unrelated Repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The organization whose webhook secret authenticates a request (`repository.owner.login` / `organization.login`) is never checked for equality against the repository the handler actually acts on (`repository.full_name`). An attacker who controls one organization onboarded to a multi-tenant Shipit instance can forge a valid signature using their own org's secret while pointing `repository.full_name` at a completely different, unrelated tracked stack.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` used to verify `X-Hub-Signature` [5](#0-4) . This binds "the organization whose secret authenticated the request" to `repository.owner.login`. But once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5)  passes the **entire raw payload** to handlers, which independently resolve the target repository via `payload.dig('repository', 'full_name')` in the base `Handler` class [3](#0-2) .

Nothing enforces `repository.full_name`'s owner segment equals `repository_owner`/`organization.login`. Since `Shipit.github` config is keyed per-organization with independent `webhook_secret` values [1](#0-0) , an attacker who is an admin of Organization A (which has the Shipit GitHub App installed, giving them their own valid webhook secret for A) can send a `push` event with:
- `organization.login` / `repository.owner.login` = `"org-a"` (verified against org‑A's real secret, signed correctly)
- `repository.full_name` = `"org-b/some-other-repo"` (an unrelated stack tracked by the same Shipit instance)

The `PushHandler` will resolve stacks for `org-b/some-other-repo` via `Repository.from_github_repo_name(repository_name)` and enqueue `GithubSyncJob` for that stack [7](#0-6) , which in turn can trigger `stack.trigger_continuous_delivery` via commit-status callbacks and continuous delivery scheduling once new commits are appended (`Stack#trigger_continuous_delivery`, `Stack#trigger_deploy`) [8](#0-7) .

This exactly mirrors the analog bug class: the "authorising" identity (organization whose secret verified the signature) is not the identity ("repository") the code subsequently acts on/writes to.

### Impact Explanation
This breaks tenant isolation between organizations sharing one Shipit instance. An attacker with legitimate but limited access (admin of their own, unrelated GitHub organization onboarded to the shared Shipit deployment) can forge webhook events attributed to any other tracked repository, forcing unscheduled GitHub syncs and, for stacks with `continuous_deployment` enabled, unauthorized/uncontrolled deploy triggering (`Stack#trigger_deploy`) outside of the legitimate repository's own push activity. This qualifies as "an unauthorized deploy" (High/Critical impact per the scope's accepted-impact list), since the deploy trigger path is invoked by an entity that never had write access to, or a valid webhook secret scoped to, the target repository.

### Likelihood Explanation
Requires the attacker to control (or be an authorized contributor on) at least one GitHub organization/repository that is itself legitimately onboarded to the same shared Shipit instance — a realistic scenario for any Shipit deployment servicing multiple orgs/teams (the multi-org config in `lib/shipit.rb` exists specifically for this case). No secrets belonging to the victim organization are needed; only the attacker's own valid webhook secret is used to sign a payload whose `repository.full_name` field is spoofed to reference the victim stack. This is an unprivileged-attacker path from the victim repository's perspective.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, ensure that the identity used to select/verify the webhook signature is the same identity that is authorized to act on the resolved repository/stack. Concretely: after determining the target repository from `repository.full_name`, verify that its owner matches `repository_owner`/`organization.login` (the value used to select the GitHub App config and secret), rejecting the event (422) on mismatch. Alternatively, derive `repository_owner` strictly from `repository.full_name`'s owner segment (not from a separate `organization.login` fallback) so the same value is used consistently for both verification and dispatch, closing the gap between "organization authenticated" and "repository acted upon."

### Proof of Concept
1. Attacker is an authorized admin of `org-a`, which has the Shipit GitHub App installed and thus a valid `webhook_secret_a`.
2. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled-or-real-sha>",
  "organization": { "login": "org-a" },
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker signs the raw JSON body with `webhook_secret_a` and sets `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches org‑A's `GitHubApp`, and the signature verifies successfully (`verify_webhook_signature`) since it matches org‑A's own secret [5](#0-4) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "org-b/victim-repo"` — an entirely different, unrelated tenant — and enqueues `GithubSyncJob`/potential deploy triggers for it [7](#0-6) , despite the attacker having no relationship to `org-b`.

**Note on verification limits:** I was not able to fully trace whether every downstream handler (beyond `PushHandler`) enforces additional constraints that might mitigate the cross-org effect (e.g., commit existence checks in `GithubSyncJob` that could cause a no-op if the sha doesn't exist upstream for `org-b`), and I could not execute this against a live instance to confirm actual deploy triggering end-to-end. This assessment is based on static code tracing of `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`, `app/jobs/shipit/github_sync_job.rb`, and `app/models/shipit/stack.rb`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
