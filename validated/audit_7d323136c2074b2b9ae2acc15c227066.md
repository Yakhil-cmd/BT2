### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for label-gated provisioning behaviors due to `&&`/`||` precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` only ANDs `repository.review_stacks_enabled` with the `allow_all?` branch; the `allow_with_label?` and `prevent_with_label?` branches are evaluated independently of `review_stacks_enabled` because `&&` binds tighter than `||` in Ruby. No existing minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` exercises `review_stacks_enabled: false` together with `provisioning_behavior: :allow_with_label` and a matching label, so this precedence bug is undetected by the current suite.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` must gate *every* provisioning branch — a repository owner who disables review stacks should never get an auto-created stack, regardless of label configuration.

The actual code is: [1](#0-0) 

Due to Ruby operator precedence this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `review_stacks_enabled == false`, `provisioning_behavior == "allow_with_label"`, and the PR carries the configured label, `provision?` evaluates to `(false && false) || (true && true) || (false && …) == true`. The gate is bypassed entirely for the label-based branches.

Attacker path: any GitHub user who can open a pull request against a tracked repository and apply a label to their own PR (a normal, unprivileged PR action) reaches `respond_to_pull_request_opened?` → `provision?` via the `opened` webhook handler, and `ReviewStackAdapter#find_or_create!` creates a live `Shipit::Stack` even though the repository owner set `review_stacks_enabled = false`.

Existing guards do not catch this: `params` validation only checks payload shape (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb#L8-39`), and there is no separate check anywhere else in `process` that re-verifies `review_stacks_enabled` before calling `ReviewStackAdapter#find_or_create!`.

Test coverage confirms the gap: every existing `allow_with_label`/`prevent_with_label` test in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb#L129-187` relies on `configure_provisioning_behavior`'s default `provisioning_enabled: true` [2](#0-1) , and the only test that sets `provisioning_enabled: false` uses `behavior: :allow_all` [3](#0-2) . No test combines `review_stacks_enabled: false` with `allow_with_label` plus a matching label.

### Impact Explanation
For any tracked repository where the maintainer has explicitly disabled review stacks (`review_stacks_enabled = false`) but left a stale/default `provisioning_behavior` of `allow_with_label` with a configured label, an unprivileged PR author can still trigger creation of a `Shipit::Stack` and its downstream provisioning/deploy task pipeline by applying that label to their own PR. This is an unauthorized stack creation/deploy action against a repository that opted out — a write occurring for a repository that did not authenticate/authorize it, matching the "unauthorized deploy" Critical category. It is repeatable for every PR/label combination on any repository misconfigured this way.

### Likelihood Explanation
Requires a repository to have `review_stacks_enabled: false` while `provisioning_behavior` remains `allow_with_label` (or `prevent_with_label`, inverted) with a label configured — a plausible partial-migration/misconfiguration state, not a default. Attacker cost is trivial: open a PR and add a label, both unprivileged actions available to any contributor to a repo that accepts external PRs.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks disabled even if allow_with_label matches" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled == false
  assert_equal false, repository.reload.review_stacks_enabled

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Running this against the current `provision?` implementation fails — `Shipit::Stack.count` increases by 1 — proving `review_stacks_enabled == false` is never enforced on the `allow_with_label` branch.
