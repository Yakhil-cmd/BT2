## Analog Found [1](#0-0) 

### Title
Attacker can spam `stake`/`harvest_rewards` to zero-round `reward_per_token()` and permanently freeze rewards for all stakers in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements the same Synthetix-style JIT reward accounting the Solidity report describes (`reward_per_token_stored`, `last_update_block`, `reward_rate_per_block`). The pallet's `reward_per_token()` performs an integer division that truncates to `0` whenever `elapsed_blocks * reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked`. Because `PRECISION_SCALING_FACTOR` is only `4096` (not `1e18` as in the Solidity/Synthetix design this pallet explicitly models itself on, per the doc comment at line 67), this rounding-to-zero condition is trivially reachable for realistic pools. Any signed account can call `stake` (even with `amount = 0`, since there is no minimum-amount check) or, if already a staker, `harvest_rewards`/`unstake` on itself every block, forcing `last_update_block` to advance by exactly 1 block on each call and permanently pinning `reward_per_token_stored`, freezing reward accrual for every staker in the pool.

### Finding Description
The reward-per-token computation is: [2](#0-1) 

```
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```

`PRECISION_SCALING_FACTOR` is defined as a tiny `u16` constant: [3](#0-2) 

Whenever `rewardable_blocks_elapsed * reward_rate_per_block * 4096 < total_tokens_staked`, this integer division truncates to `0`, exactly the same defect flagged in the original report (`(lastBlockRewardApplicable() - lastUpdateBlock) * rewardRate * 1e18 / total == 0`).

Every call to `stake`, `unstake`, or `harvest_rewards` invokes `update_pool_and_staker_rewards`, which recomputes `reward_per_token` and unconditionally overwrites `pool_info.last_update_block` with the current block, regardless of whether the added reward-per-token delta was `0`: [4](#0-3) 

`stake` has no minimum-amount restriction and is callable by any signed account for itself: [5](#0-4) 

`harvest_rewards` (and `unstake`) only restrict the "on behalf of another account" path; a staker calling for themselves is always permitted regardless of pool expiry: [6](#0-5) 

Since `reward_per_token_stored` is a single value shared by the whole pool (not per-staker), any attacker — needing no privileged role, simply a signed account able to pay a transaction fee and (optionally) stake a token amount as small as `0` — can call `stake(pool_id, 0)` (or `harvest_rewards`) in every block. This keeps `rewardable_blocks_elapsed` at `1` on every update, which is small enough to make the truncation-to-zero condition hold for any pool where `reward_rate_per_block * 4096 < total_tokens_staked` — a condition easily satisfied by typical reward rates and staked-asset supplies (e.g. an 18-decimal staked asset with modest reward rate). The result: `reward_per_token_stored` never advances, and `derive_rewards` for every staker in the pool computes zero incremental reward on every subsequent interaction, because `reward_per_token.ensure_sub(staker_info.reward_per_token_paid)` stays `0`: [7](#0-6) 

This mirrors the reported invariant violation precisely: an unprivileged actor manipulates `last_update_block` cadence to keep `(elapsed * rate * scale) < total_supply`, deterministically zeroing the reward accrual for all participants, not just themselves.

### Impact Explanation
All stakers in an affected `pallet-asset-rewards` pool are permanently denied their accrued rewards for as long as the attacker keeps spamming the low-cost trigger call. This is a direct griefing/denial-of-service of legitimate reward distribution — matching the "Medium" severity and impact ("Users can't receive the reward from rewarder") of the original report. Because the pool's reward-per-token state is global (shared across all stakers), a single attacker griefs every participant, not merely themselves.

### Likelihood Explanation
Likelihood is high in any realistically configured pool: `PRECISION_SCALING_FACTOR = 4096` is drastically smaller than the `1e18` scaling used in the Synthetix design this pallet is explicitly modeled after (see the pallet doc comment referencing `StakingRewards.sol`), making the zero-rounding condition (`elapsed * rate * 4096 < total_staked`) easy to satisfy for common token decimal/rate combinations. The attack requires no special role, no governance, and no stolen keys — only a signed account and the ability to submit a transaction per block, with `stake(pool_id, 0)` costing only the extrinsic fee (no minimum stake amount is enforced).

### Recommendation
Track and carry forward the division remainder (as suggested in the original report) so that no reward is silently lost between updates, and/or substantially increase `PRECISION_SCALING_FACTOR` (or make it configurable per-pool relative to expected `total_tokens_staked`/`reward_rate_per_block` magnitudes) to reduce the practical window of numerator/denominator ratios that truncate to zero. Consider rate-limiting or adding a minimum interval/amount for `stake`/`harvest_rewards` self-calls, or accruing a running remainder across `reward_per_token` calls so that repeated small-interval calls cannot indefinitely reset accrual to zero.

### Proof of Concept
No executable PoC was run against a live node/test harness; this is a static-analysis analog derived from tracing `stake`/`harvest_rewards` → `update_pool_and_staker_rewards` → `reward_per_token` in `substrate/frame/asset-rewards/src/lib.rs`. A concrete integration reproduction would use the pallet's own mock runtime (`substrate/frame/asset-rewards/src/mock.rs`, `tests.rs`) to: (1) create a pool with `total_tokens_staked` and `reward_rate_per_block` chosen so `reward_rate_per_block * 4096 < total_tokens_staked`; (2) have a second staker join; (3) have the attacker call `stake(pool_id, 0)` every block; (4) assert the second staker's `pending_rewards`/`earned` stays at `0` across many blocks despite pool-level rewards notionally accruing. This was not executed in this session — the finding is based on code-path tracing only, and the existing `tests.rs` integration test at lines 1284-1414 shows the intended (non-attacked) accrual behavior for contrast.

		///
		/// A freeze is placed on the staked tokens.
		#[pallet::call_index(1)]
		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		///
		/// Should be called prior to any operation involving a staker.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,

		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.
		fn derive_rewards(

			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
