## Title
Frozen `RewardEpochDelegatedStakes` denominator vs. mutable post-merge `Delegation.stake` numerator can inflate Alpenglow reward points beyond a delegator's true share - ([File: runtime/src/inflation_rewards/points.rs])

## Summary
The `BlackGovernor` finding is a *denominator/numerator base mismatch* bug class: one side of a ratio (quorum) is computed from a monotonically-growing, stale, historical aggregate (`smNFTBalance`), while the other side (proposal threshold, and the actual votes cast) is computed from live, current state. This produces unachievable or exploitable ratios. The closest reachable analog in Agave's stake/reward accounting is in `calculate_alpenglow_points()`, where an individual delegation's numerator (`stake_amount`) is recomputed live via `delegation_effective_stake()` against the *current* `Delegation` struct, while the denominator (`total_stake`) is a frozen, epoch-boundary snapshot (`RewardEpochDelegatedStakes`) that is not re-validated for consistency with the numerator.

## Finding Description
`calculate_alpenglow_points()` computes an individual stake's earned reward points as:

```rust
let stake_amount = u128::from(delegation_effective_stake(
    &stake.delegation, epoch, stake_history, new_rate_activation_epoch, use_fixed_point_stake_math,
));
...
let total_stake = reward_epoch_delegated_stakes.delegated_stakes.get(&stake.delegation.voter_pubkey)...;
earned_credits * stake_amount / total_stake as u128
``` [1](#0-0) 

`stake_amount` (numerator) is derived from `delegation_effective_stake`, which reads the **current** `Delegation.stake` field for the historical `epoch` [2](#0-1) . This differs conceptually from `total_stake` (denominator), which is a pre-computed, frozen snapshot captured once at epoch-boundary time via `RewardEpochDelegatedStakes::set()`/`Stakes::calculate_activated_stake()` [3](#0-2) [4](#0-3) .

Because `Delegation.stake` can be mutated by unprivileged, user-initiated stake-program instructions (`Merge`, `Split`) between the reward-epoch boundary snapshot and the time points are recalculated (e.g., after a snapshot restore triggers `recalculate_stake_rewards`), the numerator computed from the *current* delegation can diverge from what was captured in the frozen denominator snapshot. The code base is explicitly aware of this class of divergence: in the parallel `calculate_block_reward()` path, a comment states "*it's possible to have stake > total_active_stake ... we clamp it just to be safe*" and applies `.min(pending_delegator_rewards)` [5](#0-4) . `calculate_alpenglow_points()`, however, performs the same ratio-style division (`earned_credits * stake_amount / total_stake`) **without any clamp** to `earned_credits` or any bound, meaning if `stake_amount` exceeds `total_stake` (i.e., the individual delegation's current live-computed stake exceeds the frozen aggregate denominator it is being measured against), `earned_points` can exceed the credits legitimately earned for that reward epoch [6](#0-5) .

The `merge` stake-program instruction is an unprivileged, user-callable instruction (available via `agave` CLI's `merge-stake` and directly via `stake_instruction::merge`) that combines two stake accounts' lamports/`Delegation.stake` while preserving activation semantics [7](#0-6) [8](#0-7) , providing the concrete, unprivileged trigger to inflate `Delegation.stake` after the reward-epoch's `RewardEpochDelegatedStakes` denominator snapshot has already been taken.

Existing regression tests (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, `test_calculate_alpenglow_points_uses_current_delegated_stake_denominator`) demonstrate the maintainers are actively guarding against a related recalculation-denominator mismatch [9](#0-8) [10](#0-9) , but none of the tests found assert an upper bound (clamp) on `earned_points` relative to `earned_credits` in `calculate_alpenglow_points`, unlike the equivalent block-reward path.

## Impact Explanation
If `stake_amount` (numerator, live-recomputed) can exceed `total_stake` (denominator, frozen snapshot) for a given vote account's delegator, `earned_points` computed in `calculate_alpenglow_points` is not bounded to `earned_credits`, unlike the analogous `calculate_block_reward` path which explicitly clamps. Inflated points directly translate into inflated lamport rewards paid out during partitioned epoch reward distribution — this is a misattributed/duplicated-rewards class impact (over-crediting one delegator at the expense of protocol reward invariants), matching the severity bar requested (concrete misattributed or duplicated rewards).

## Likelihood Explanation
I was **not able to fully verify** that a live-mutated `Delegation.stake` (via `Merge`/`Split`) can, in practice, produce a `stake_amount` (computed via `delegation_effective_stake` for the historical `rewarded_epoch`) that exceeds the frozen `total_stake` value stored in `RewardEpochDelegatedStakes` for that same vote account, given `RewardEpochDelegatedStakes` sums delegated stakes across *all* delegators, not just the one being examined — inflating one delegator's live stake would need the sum-of-all-others in the frozen snapshot to remain fixed while one delegation's raw `stake` field grows past what was captured. Because `RewardEpochDelegatedStakes.delegated_stakes` is a per-vote-account aggregate (not per-stake-account), and `stake_amount` is only one delegator's stake, exceeding the *aggregate* would require that a single stake account acquire (via merge) essentially all lamports that should be spread across many delegations, or a merge/split sequence that occurs strictly between the snapshot and the recalculation window (only reachable via snapshot-restore-triggered `recalculate_stake_rewards`, a narrow window). This requires further live/testnet verification which I could not perform with the available read-only tools, and the existing tests suggest maintainers may have already reasoned about — and possibly bounded elsewhere — this scenario. I flag this with **medium-to-low confidence** as the closest reachable analog to the reported bug class, not a confirmed, reproduced vulnerability.

## Recommendation
- Audit `calculate_alpenglow_points()` to add an explicit upper bound / clamp analogous to `calculate_block_reward()`'s `.min(pending_delegator_rewards)`, ensuring `earned_points` can never exceed `earned_credits` (or the corresponding bound) regardless of live vs. frozen stake divergence.
- Add a debug assertion / metric that fires if `stake_amount > total_stake` inside `calculate_alpenglow_points`, to detect and quantify real-world occurrences of numerator/denominator divergence between live-recomputed delegation stake and the frozen `RewardEpochDelegatedStakes` snapshot.
- Extend the existing recalculation-denominator regression tests (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) to explicitly cover a `Merge` of two active delegations to the same vote account occurring between the reward-epoch snapshot and a triggered recalculation, verifying no over-crediting occurs.

## Proof of Concept
Not independently reproduced in this pass — a POC would require: (1) activating a delegation to a vote account, (2) advancing to the epoch boundary so `RewardEpochDelegatedStakes` snapshots the vote account's aggregate delegated stake, (3) triggering a scenario that invokes `recalculate_stake_rewards` (e.g., simulated snapshot restore per `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) [11](#0-10) , while (4) issuing a `Merge` stake instruction between the delegation being examined and another activated stake account for the same voter in the intervening window, then (5) asserting whether the resulting `ag_points` computed by `calculate_alpenglow_points` exceeds `earned_credits`. This exact sequence was not executed due to tool limitations (read-only codebase index).

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
        use_fixed_point_stake_math: bool,
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation_activation_status(
                            delegation,
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                            use_fixed_point_stake_math,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        let reward_epoch_delegated_stakes = RewardEpochDelegatedStakes {
            epoch: self.epoch,
            delegated_stakes: effective_delegated_stakes,
        };
        (
            stake_history,
            vote_accounts,
            delegated_stakes,
            reward_epoch_delegated_stakes,
        )
    }
