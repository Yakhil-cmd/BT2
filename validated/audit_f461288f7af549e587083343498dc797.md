### Title
Missing `return` after error path causes double invocation of the async iteratee callback in `handleSavedPrivatePayments` - (File: network.js)

### Summary
The CVE describes a double-`kfree`: an error path in `mpc_rcvd_sweep_req` frees a struct and then the caller frees it again because the caller doesn't know the callee already released it. The structural analog in `ocore` is `network.js`'s `handleSavedPrivatePayments`, where the `catch` block for `objectHash.getBase64Hash()` already "releases" the per-row async resource (deletes the DB row and invokes the `async.each` iteratee callback `cb`), but execution falls through without a `return` and the same row is processed a second time, invoking `cb` (and DB delete / event emissions) again.

### Finding Description
In `validateAndSave()` inside `handleSavedPrivatePayments`: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

There is no `return` statement after the `catch` block. `deleteHandledPrivateChain(unit, message_index, output_index, cb)` deletes the `unhandled_private_payments` row and then calls `cb()` — the row's "resource" is released once here: [2](#0-1) 

Because execution continues past the `catch`, the same row's chain is then also passed to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each independently call `deleteHandledPrivateChain(... , cb)` again (or `cb()` directly) — a second release/second callback invocation on the same async task, the direct analog of the kernel's double-`kfree` on `mpcginfo`.

The rows processed here originate from `unhandled_private_payments`, which is populated by `handleOnlinePrivatePayment` when a private-payment chain arrives from a paired device (through the hub) or directly from a peer: [3](#0-2) 
At that point only structural checks (unit format, message_index/output_index types, non-empty array) are performed before the JSON payload is stored — the payload content itself (`e.payload`) is otherwise only checked with light shape validation in `wallet.js`'s `handlePrivatePaymentChains`: [4](#0-3) 
No check prevents a payload whose contents cause `getBase64Hash`/`getJsonSourceString` to throw (e.g. malformed/self-referential or otherwise unstringifiable payload structures) from being persisted and later dequeued.

### Impact Explanation
`async.each`'s iteratee callback `cb` must be invoked exactly once per item; the framework's completion callback is fired once all items' `cb`s have fired. Double-invoking `cb` for one row: 
- Causes `async.each`'s final callback (`unlock(); eventBus.emit("new_my_transactions", ...)`) to potentially run more than once, since `async`'s internal completion counter can under/over-count, leading to double release of the `saved_private` mutex or double emission of `new_my_transactions`.
- The second, "leaked" call into `privatePayment.validateAndSavePrivatePaymentChain` acts on private-payment DB state (`unhandled_private_payments`, `outputs`/`inputs` in `divisible_asset.js`/`indivisible_asset.js`) after the row was already deleted, which can result in inconsistent/duplicate processing of the private-payment chain and premature or duplicate unlocking of the `saved_private` mutex, causing state corruption in the wallet's private-payment bookkeeping (double-processed or lost private chain state) — the wallet-side analog of "funds loss/freezing" through inconsistent chain-state tracking, since the wallet's belief about which private outputs are spendable becomes wrong.

### Likelihood Explanation
Reachable by any paired device or private-payment counterparty sending a `private_payment` chain through `wallet.handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`, which persists attacker-controlled JSON payload into `unhandled_private_payments` without deep validation. The attacker only needs a payload whose `.payload` object triggers an exception inside `getJsonSourceString`/`getBase64Hash` (e.g., pathological/circular or type-invalid content) at the time `handleSavedPrivatePayments` later processes it. This does not require a malicious node/peer/hub — a normal paired device or payment counterparty suffices, matching the allowed threat model.

### Recommendation
Add a `return` immediately after the `catch` block in `validateAndSave()` in `network.js` so that once `deleteHandledPrivateChain(..., cb)` has consumed the row and invoked `cb`, the function does not fall through to also call `privatePayment.validateAndSavePrivatePaymentChain`. This mirrors the kernel fix of removing the redundant free by ensuring exactly one code path completes/releases the async task for a given row.

### Proof of Concept
1. As a paired device or private-payment counterparty, send a `private_payment_chains` hub message (`wallet.js` `handlePrivatePaymentChains`) whose head element's `payload` is well-formed enough to pass the shallow `ValidationUtils` checks in `wallet.js`/`network.js` (`isNonemptyObject`, `isNonemptyString`, `isNonemptyArray`) but causes `objectHash.getJsonSourceString`/`getBase64Hash` to throw when later serialized (e.g. a payload containing a value that cannot be canonically JSON-stringified by the hashing routine).
2. The chain is queued via `handleOnlinePrivatePayment` → `savePrivatePayment` into `unhandled_private_payments` (`ifQueued`/`ifNew` paths), bypassing deep content validation. [5](#0-4) 
3. When `handleSavedPrivatePayments` later processes this row, `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside the `try` block.
4. The `catch` handler calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which deletes the row and calls `cb()` once.
5. Because there is no `return`, execution proceeds to also call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose completion handlers (`ifOk`, `ifError`, or `ifWaitingForChain`) call `cb()` (directly or via `deleteHandledPrivateChain`) a second time for the same row — demonstrating the double-callback/double-release analogous to the double-`kfree`.

(Note: I could not fully verify, from static inspection alone, a concrete input value that reliably triggers an exception inside `getJsonSourceString`/`getBase64Hash` for a crafted-but-schema-valid payload — this would need to be confirmed by exercising `string_utils.getJsonSourceString` with adversarial payload shapes in a running environment.)
