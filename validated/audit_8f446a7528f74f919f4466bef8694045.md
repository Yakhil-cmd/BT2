### Title
Cross-repository status forgery via SHA collision drives unauthorized victim-stack deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming `status` webhook to **every** `Commit` row that matches `params.sha`, without checking that the webhook's `repository.owner`/`repository.full_name` corresponds to that commit's own `stack`/repository. Signature verification (`WebhooksController#verify_signature`) is scoped only to a GitHub *organization* (and, in the common single-app config, not even that — it uses one global `webhook_secret` regardless of `repository_owner`), not to a specific repository. The binding the question asks about — "the validation event equals a real CI run against the victim's own commit" — does not hold: it degrades to "any commit row in the DB whose `sha` column matches the attacker-supplied value," which is exploitable whenever an attacker can produce a same-SHA commit in a repository covered by the same GitHub App installation/webhook secret as the victim stack.

### Finding Description
Binding claimed: `webhook.repository.full_name == commit.stack.repository.full_name` for the `Status` created by `StatusHandler`. Actual code: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no `repository`/`full_name` field in the `params` schema at all (only `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`), and no comparison against `commit.stack.github_repo_name`. Any DB row with a matching `sha`, in any stack, gets a new `Status` created scoped to that commit's own `stack_id`.

Signature verification is scoped by organization only: [2](#0-1) 
and, in the default single-GitHub-App configuration (the schema documented in `docs/setup.md`), `Shipit.github(organization:)` ignores the `organization` argument entirely and always returns the one globally configured app/secret: [3](#0-2) [4](#0-3) 

So the HMAC check only proves "this event was sent by the one GitHub App Shipit trusts" — it proves nothing about which repository the event concerns. Once inside `create_status_from_github!` → `add_status` → `Status.create!`, the new `Status` is created with `deployable_status`/`schedule_continuous_delivery` hooks firing based purely on the matched `Commit#stack_id`: [5](#0-4) [6](#0-5) 

From there, `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` → `next_commit_to_deploy`/`deployable_commits` → `Stack#deployable?`/`Commit#deployable?` will treat the forged status as legitimate green CI on the victim's commit: [7](#0-6) [8](#0-7) [9](#0-8) 

`trigger_deploy` then builds and runs a real `Deploy` task (using the victim stack's own `cached_deploy_spec`/`GITHUB_TOKEN`), which executes shell commands via `Command`/`PTY.spawn` on the deploy host.

**Exploit path:** an attacker who owns/controls any repository within reach of the same webhook-signing scope (same single global GitHub App secret, or same org if the app is installed "All repositories" — a common configuration) reproduces a commit object with **identical SHA** to a commit already tracked in the victim's stack (git SHAs are a pure hash of tree/parent/author/committer/message/timestamps, so an attacker with read access to that commit's metadata — e.g. because the victim repo is public, or the attacker is a collaborator/fork owner — can trivially recreate an identical commit object in their own repo). They then get GitHub to emit a real, correctly-signed `status` (or `check_run`) webhook for their own repo/commit with `state: success`. Shipit accepts the signature (organization/app-scoped, not repository-scoped) and `StatusHandler` blindly applies it to the victim's `Commit` row because `sha` matches, with no cross-check of `repository.full_name`.

Existing guards do not prevent this: `verify_signature` only authenticates "this event came from a GitHub App Shipit trusts," not "this event is about this specific repository." `ExplicitParameters` schema for `StatusHandler` never requires/validates a repository identifier. `drop_unhandled_event` and `force_github_authentication` are irrelevant here (webhook path, no session). `Commit#locked?`/`Stack#deployable?` guard against locks/active tasks, not against provenance of the status.

### Impact Explanation
A payload forged by controlling an unrelated repository mutates the victim stack's `Commit`/`Status` record and can trigger `Stack#trigger_continuous_delivery`, causing a real deploy task to run on the deploy host using the victim stack's `deploy.yml` commands and its `GITHUB_TOKEN`/deploy credentials — this is "a payload for one repository mutating another's stack, commit, task" and "an unauthorized deploy," matching the Critical impact category (RCE-adjacent execution of victim `shipit.yml` commands via `Command`/`PTY.spawn`, using credentials the attacker never validated). It is repeatable against any stack/commit whose SHA the attacker can reproduce, and the blast radius spans every stack sharing the same GitHub App webhook secret/config (frequently every stack in a Shipit instance, since most deployments use the single-app config shown in `docs/setup.md`).

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository reachable by the same GitHub App installation/webhook secret Shipit trusts (either the default single-secret config, where any org/repo the app happens to be installed on qualifies, or an org-wide "All repositories" installation), and (b) the ability to reconstruct a commit with an identical SHA to a victim commit (feasible when the victim repo/commit content is visible to the attacker, e.g. public repos, forks, or collaborator access to metadata). No Shipit session, API token, or GitHub App secret is required — only ordinary GitHub actions (own a repo, push a commit, have GitHub deliver a real signed status event). This is realistic in common Shipit deployments where one GitHual App/secret is shared across many tracked repositories in an organization.

### Recommendation
In `StatusHandler#process` (and the analogous `check_run`/`check_suite` handlers), require and validate the webhook's `repository.full_name` (or `repository.owner.login` + `repository.name`) against `commit.stack.github_repo_name` before calling `create_status_from_github!`, and skip/ignore the update if they don't match. Additionally, scope webhook signature verification and event routing to the specific repository (not just organization/app), e.g. by resolving the target `Stack` from `repository.full_name` first and verifying/dispatching only against that stack's commits.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (added test)
test ":status from an unrelated repository forges a status onto another stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack
  attacker_full_name = "attacker/unrelated-repo"

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,       # attacker reproduced identical SHA in their own repo
    'state' => 'success',
    'context' => 'ci/attacker',
    'description' => 'forged green',
    'created_at' => Time.now.iso8601,
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => attacker_full_name, 'owner' => { 'login' => 'attacker' } }
  }.to_json

  Shipit::ContinuousDeliveryJob.expects(:perform_later).never # should NOT fire for an unrelated repo

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
end
```
This test currently fails against the existing code (a `Status` row IS created for `victim_commit` and `ContinuousDeliveryJob` IS scheduled), proving the cross-repository forgery: the `sha`-only lookup in `StatusHandler#process` accepts a status payload whose declared `repository` has no relation to the victim stack and still mutates/triggers deploy logic for that victim stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
