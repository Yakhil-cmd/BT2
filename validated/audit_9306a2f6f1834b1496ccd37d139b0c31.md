### Title
Cross-organization webhook forgery via mismatched signature-verification org vs. target-repository binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using one payload field (`repository.owner.login` / `organization.login`), but the event handlers that subsequently mutate state (`StatusHandler`, `PushHandler`) act on a *different* payload field (`sha`, `repository.full_name`) with no re-check that the signing organization actually owns the affected repository/commit. On a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), this breaks the binding "organization that authenticated == repository that is written," letting an attacker who controls one onboarded, low-trust organization forge signed webhooks that mutate CI status / trigger sync for stacks belonging to a *different*, unrelated organization on the same instance.

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from attacker-controlled JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GithubApp` configuration (each with its own `webhook_secret`), as demonstrated by the multi-org test fixture: [3](#0-2) 

`verify_webhook_signature` only proves that the request was signed with *the secret belonging to the org named in `repository_owner`* — nothing more: [4](#0-3) 

Once verification succeeds, `WebhooksController#create` dispatches the entire raw JSON body to the registered handler for the event type, with no further binding of "verified org" to what the handler will act on: [5](#0-4) 

Critically, `StatusHandler` matches purely by commit `sha`, globally, with **no reference to `repository_owner`, `repository.full_name`, or any organization/repository field at all**: [6](#0-5) 

`PushHandler` resolves the target repository from `repository.full_name`, an independent payload field that was never covered by the signature-selection logic beyond "some configured org's secret matched": [7](#0-6) [8](#0-7) 

The equality that should hold but does not: *organization whose secret validated `X-Hub-Signature`* == *organization owning the repository/commit the handler mutates*. Before the PR (attacker action): attacker signs a payload with Org A's secret (an org they legitimately administer on the shared Shipit instance) while populating `sha`/`repository.full_name` referencing a stack/commit that belongs to Org B (a different, more sensitive org tracked by the same instance). `verify_signature` only checks the signature against Org A's secret (matching `repository_owner: "OrgA"` if present, or simply whichever org field is provided) and passes. The handler then acts on Org B's data.

### Impact Explanation
This allows an attacker who controls webhook-secret material for any one organization configured on a shared Shipit instance to:
- Forge a `status` webhook creating an arbitrary commit status (`state: success`, arbitrary `context`) for **any commit SHA in any stack on the instance**, regardless of which org owns it, via `Commit#create_status_from_github!`. Shipit stacks commonly gate deploys/merges on required CI statuses (`ci.require` in `shipit.yml`), so this can be used to fabricate a passing status and enable an **unauthorized deploy or merge** on a repository the attacker does not control.
- Forge a `push` webhook that triggers `Stack#sync_github` for any stack whose `Repository.full_name` the attacker names, causing cross-organization state resync outside the attacker's authorization.

This maps to the "Critical: unauthorized deploy/rollback/merge" and "High: unauthenticated... escalation" impact categories, because it lets an attacker who is not authorized on the target repository/org cause state changes that gate real deploys.

### Likelihood Explanation
Requires the operator to run a multi-organization Shipit deployment (explicitly documented/supported, per `docs/setup.md` and the `secrets_double_github_app.yml` fixture) where the attacker has legitimate access to at least one onboarded organization's GitHub App webhook secret (e.g., as an admin of that org's GitHub App installation) but not to the victim organization. This is a plausible tenancy-isolation failure mode for shared Shipit instances serving multiple orgs/teams, which is the documented use case for the multi-org config format.

### Recommendation
After signature verification, re-derive the organization from the same trusted binding used for verification (`repository_owner`) and enforce that every handler's target repository/stack belongs to that verified organization before mutating any state — e.g., pass the verified `repository_owner` into `Handler.call` and have `Handler#stacks` filter `Repository.from_github_repo_name(repository_name)` to records whose `owner` matches the verified organization, and have `StatusHandler` scope `Commit.where(sha:)` to commits within stacks of the verified organization.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret` values (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
   ```json
   { "sha": "<sha of a commit belonging to a stack under OrgB>", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"} }
   ```
   signed (`X-Hub-Signature`) with `OrgA`'s `webhook_secret`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, validates against `OrgA`'s secret — succeeds.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit (no org check anywhere in this handler), and calls `create_status_from_github!`, injecting a fabricated passing CI status onto a commit in an organization the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
