### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository mutate a commit belonging to a different stack/repository that happens to share the same SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) purely by bare SHA with no repository or stack scoping, unlike other handlers (e.g. `Handler#stacks`) which resolve via `Repository.from_github_repo_name(repository_name)`. Given the question's stated precondition ("shared commit SHA with attacker repo"), an authenticated status webhook from the attacker's own repository will write a `Status` row onto the victim's `Commit` record if both share the same `sha` string, since `Commit.where(sha: params.sha)` does not filter by `stack_id`/repository at all.

### Finding Description
The broken binding is: **"a status for `buildkite/deploy` should only affect the commit belonging to the repository/organization that authenticated the webhook"** ⇔ what the code actually does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  — this query has no `stack_id`/repository predicate, so if the victim's stack and the attacker's own repository each contain a `Commit` row with an identical `sha` value (the question's assumed precondition), **both** commits receive the status update from a single webhook delivery.

Signature verification (`WebhooksController#verify_signature`) authenticates the request against the webhook secret configured for `repository_owner` derived from the payload's own `repository.owner.login` [2](#0-1) , and `GitHubApp#verify_webhook_signature` validates the HMAC against that organization's secret [3](#0-2) . This only proves the payload originated from the attacker's own organization/repo — it says nothing about which repository's commits should be touched. Other handlers correctly derive scope from the payload's `repository.full_name` via `Handler#stacks`/`Repository.from_github_repo_name` [4](#0-3) , but `StatusHandler` bypasses this pattern entirely and queries `Commit` directly by bare `sha`.

`Commit#create_status_from_github!` then appends the attacker-supplied status (`context: buildkite/deploy`, arbitrary `state`) to that commit's status list [5](#0-4) , and `add_status` recomputes `deployable?`/`blocked?`/triggers `stack.schedule_merges` based on the new aggregated status [6](#0-5) , `227" end="229" />. If the injected status flips the commit to `success`, this can unblock a ship/merge on the victim stack; if it flips to `failure`, it can block a legitimate deploy — both without the attacker ever authenticating against the victim's organization or repository.

No existing guard (signature verification, `drop_unhandled_event`, `ExplicitParameters` schema) checks that the resolved `Commit#stack`'s repository matches the payload's `repository.full_name`.

### Impact Explanation
An attacker who owns any repository connected to the same Shipit instance (i.e., has their own valid webhook signature) can inject a forged status onto **any other stack's commit** that happens to share the same SHA, causing an unauthorized ship, merge unblock, or deploy block on a repository they do not control and did not authenticate against. This is a cross-tenant state manipulation: one repository's authenticated payload mutates another repository's `Commit`/`Status` records and downstream deploy state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The exploit strictly depends on the externally-imposed precondition stated in the question — that the victim stack and the attacker's own repository already share an identical commit SHA. Git SHA-1 collisions across unrelated repositories are effectively non-occurring for organically-created commits; this shared-SHA precondition would require either a contrived, unrealistic scenario or an attacker deliberately crafting a commit with the exact same tree/parent/metadata reproduced in both repos (which is possible if the attacker forks/clones the exact same commit object and pushes it, unmodified, into their own repository — genuinely feasible, since cloning and re-pushing an existing commit preserves its SHA). If the attacker forks the victim's public repo (which necessarily preserves the SHA-1 of shared commits) and adds it as a Shipit-tracked repo/stack under their own control, the precondition is trivially satisfiable, making this realistically exploitable, not merely theoretical.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` by repository, matching the pattern used elsewhere in the handler hierarchy: use `stacks` (derived from `payload.dig('repository', 'full_name')`) to load only commits belonging to stacks associated with the authenticated repository, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not affect commits belonging to a different repository sharing the same SHA" do
  shared_sha = 'a' * 40

  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  attacker_stack = create_stack!(repository: create(:repository, owner: 'attacker', name: 'evil-repo'))

  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'buildkite/deploy',
    'repository' => { 'full_name' => 'attacker/evil-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  attacker_commit.reload

  # Binding under test: victim_commit.statuses must remain unaffected by attacker's webhook
  assert_equal 0, victim_commit.statuses.count, "attacker's status webhook must not write to victim's commit"
  assert_equal 1, attacker_commit.statuses.count
end
```
This demonstrates that, as currently written, `Commit.where(sha: params.sha)` [1](#0-0)  would match and update `victim_commit` as well, violating the intended per-repository isolation of status webhooks.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
