### Title
`StatusHandler` writes commit status without scoping to the authenticated webhook's repository, enabling cross-repository status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App/organization derived from the payload's own `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . This correctly proves the request came from GitHub for *that* organization's repository. However, `Shipit::Webhooks::Handlers::StatusHandler#process` never checks that binding when applying the event: it looks up commits purely `Commit.where(sha: params.sha)`, with no filter on `repository`/`stack` at all [3](#0-2) . Every other handler (`PushHandler`, the `PullRequest::*Handler`s) explicitly scopes to `stacks`/`repository` derived from `payload.dig('repository','full_name')` via the shared `Handler#stacks`/`Handler#repository_name` helpers [4](#0-3) [5](#0-4) , but `StatusHandler` breaks this pattern.

### Finding Description
The binding that should hold is: **organization/repository that authenticated the webhook == repository whose commit status is written**. `verify_signature` establishes the left side using `repository_owner` taken straight from the payload [1](#0-0) . That is sufficient only to prove GitHub genuinely delivered this event for a repository owned by that organization — it says nothing about which Shipit `Stack`/`Commit` the event is allowed to affect.

`StatusHandler`'s params schema requires only `sha`, `state`, and optional descriptive fields — it never requires or reads `repository` [6](#0-5) . Its `process` method then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This matches **any** `Commit` row in the entire Shipit installation whose `sha` equals the attacker-influenced value, across all stacks/repositories/organizations, not just the one that was cryptographically authenticated.

Git commit SHAs are content-addressed and are preserved across forks/mirrors. An attacker who owns (or has push/CI access to) any repository forked from, or sharing history with, a repository tracked as a Shipit `Stack` can:
1. Fork or otherwise obtain a repo that shares a commit SHA with a Shipit-tracked target repository (identical SHAs are guaranteed for any commit that hasn't diverged, e.g. every commit up to the fork point).
2. Configure/trigger a GitHub "status" webhook delivery on their own repository/organization (this is fully within their control if they own that repo or its CI integration, or if a GitHub App is installed there under their control), which is authenticated with their own organization's `webhook_secret` — passing `verify_signature` legitimately for their own org.
3. The payload's `sha`/`state`/`context` reach `StatusHandler`, which updates the `Status` for the identically-shaed `Commit` belonging to the **victim's** Shipit `Stack`, because the lookup is not scoped by repository.

### Impact Explanation
`Commit#create_status_from_github!` invokes `add_status`, which can transition the commit's simple state and, per `after_create` callbacks on `Status`, triggers `schedule_continuous_delivery` and, on success, `stack.schedule_merges` [7](#0-6) , and `Status` itself schedules continuous delivery on creation [8](#0-7) . If the victim stack has `continuous_deployment` enabled, `ContinuousDeliveryJob` will call `stack.trigger_continuous_delivery` once the commit is (falsely) marked `success` [9](#0-8) . This is a cross-repository write into another tenant's CI/status state, and — where continuous deployment is on — can produce an unauthorized deploy of a commit whose CI never actually passed in the victim's own pipeline. This satisfies the "cross-repository writes" / "unauthorized deploy" High/Critical impact criteria.

### Likelihood Explanation
Exploitation requires only: (a) an attacker with legitimate delivery rights to *some* GitHub App/organization configured in Shipit's `github` secrets (i.e., any onboarded org, which may be self-service in multi-org deployments), and (b) a commit SHA shared with the victim repository (trivially achievable by forking a public repository before divergence, or via any repository that legitimately shares history, e.g. mirrors/forks). No privileged Shipit credential (`ApiClient` token, `webhook_secret` for the victim's org) is required — only the attacker's own already-authorized webhook channel. This is a realistic, unprivileged-attacker path, not a theoretical one.

### Recommendation
Scope `StatusHandler#process` to commits belonging to repositories/stacks resolved from the authenticated webhook payload, mirroring the pattern used by `Handler#stacks`/`Handler#repository_name`. E.g. require `repository.full_name` in the params schema and change the lookup to `stacks.map(&:commits).flat_map { |c| c.where(sha: params.sha) }` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), ensuring a status update can only affect commits under the repository that the verified webhook signature actually corresponds to.

### Proof of Concept
1. Attacker owns `attacker-org/forked-repo`, a fork of `victim-org/target-repo` (a Shipit-tracked stack), sharing commit `abc123...` prior to divergence.
2. Attacker's own CI/GitHub App posts a commit "status" webhook for `attacker-org/forked-repo` with `sha=abc123...`, `state=success`, to Shipit's `/webhooks` endpoint. `verify_signature` validates it using `Shipit.github(organization: 'attacker-org')`'s `webhook_secret` — passes, since it is genuinely signed by GitHub for the attacker's own org [1](#0-0) .
3. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, matching the corresponding commit under `victim-org/target-repo`'s stack, and creates a `success` `Status` for it [3](#0-2) .
4. If `victim-org/target-repo`'s stack has continuous deployment enabled, this can trigger an unauthorized deploy via `ContinuousDeliveryJob`/`trigger_continuous_delivery` [9](#0-8) .
