## Question 1: Does `check_permissions!` consult `current_api_client.stack_id`?

No. `ApiClient#check_permissions!` only string-matches `"#{operation}:#{scope}"` against the `permissions` array; it never reads `stack_id` or any resolved `stack`: [1](#0-0) 

Scope enforcement for *which* stack a client may act on is delegated entirely to how each controller resolves `stack`/`stacks`. `BaseController#stacks` does filter by `current_api_client.stack_id` when set: [2](#0-1) 

However, `Api::CCMenuController` overrides `stack` to bypass that scoping entirely, resolving straight from the URL param with no reference to `current_api_client.stack_id`: [3](#0-2) 

So for CCMenu, `require_permission :read, :stack` only proves the token has the literal string `read:stack` in its permission list — which is true for every CCMenu client by construction — and the controller's own `stack` resolver imposes no additional binding back to `current_api_client.stack_id`. This is consistent with the question's premise that the permission check is a pure string match with no scope consultation, but by itself this is not exploitable as stated — I could not fully confirm within the available searches whether `ApiClient.stack_id` is ever populated in practice for CCMenu-issued tokens (the `ApiClientsController`/factory code that creates CCMenu tokens was not inspected), which is required to demonstrate that a stack-scoped token can read an *arbitrary* other stack's data through this controller. Without that confirmation I cannot assert a concrete cross-stack exploit for Q1 with confidence.

## Question 2: `identify_user` header spoofing

This is confirmed and is a real bug. `current_user` is derived purely from an unauthenticated request header, independent of the authenticated `ApiClient`: [4](#0-3) 

Any caller who can complete `authenticate_api_client` (i.e., possesses *any* valid API token, however low-privilege) can additionally set `X-Shipit-User: <victim-login>` and have `identify_user` look up and return that `User` by login, with zero verification that the token's owner is that user: [5](#0-4) 

This `current_user` is then used for write-attribution in at least `Api::MergeRequestsController#update`, which passes it straight into `MergeRequest.request_merge!(stack, params[:id], current_user)`: [6](#0-5) 

### Binding broken
Expected: `current_user == ` the GitHub identity that authenticated the request (bound to `current_api_client`).
Actual: `current_user == User.where('lower(login) = ?', request.headers['X-Shipit-User'].downcase).first`, an attacker-controlled value with no cryptographic or session tie to the authenticated `ApiClient`.

### Why existing guards don't stop it
- `authenticate_api_client` only validates the bearer token's signature via `ApiClient.authenticate`; it establishes `current_api_client`, not `current_user`.
- `require_permission!` only checks `operation:scope` strings on `current_api_client.permissions`, never on `current_user`.
- Nothing correlates `current_api_client.creator` (the real, verified identity) with the header-supplied login.

### Impact
Any holder of a low-privilege but valid API token (e.g., one issued only with `read:stack`/`write:hook` for CI integration) can spoof `current_user` to any existing login in `users` and have that identity attributed to actions such as merge-request enqueue in `MergeRequestsController#update`. This is an authentication/identity-binding bypass enabling attribution spoofing for downstream `current_user`-scoped writes — matching the Critical category ("authentication bypass ... accepted").

### Recommendation
Remove or gate `identify_user`'s reliance on the raw `X-Shipit-User` header for API requests; bind `current_user` to `current_api_client.creator` (the verified GitHub identity behind the token) for any attribution-sensitive write, or require that header only be trusted for trusted internal/service tokens with an explicit `impersonate` permission scope, validated against `current_api_client`.

### Proof of Concept sketch
Integration test: create an `ApiClient` for user A with only `read:stack`/minimal permissions; authenticate as A via Basic auth with that token; send the request with header `X-Shipit-User: <victim B's login>`; assert `current_user.login == B.login` while `current_api_client.creator == A`, demonstrating the divergence, then show `MergeRequest.request_merge!` is called with B as the merger even though A is the true caller.

### Title
Attribution spoofing via unauthenticated `X-Shipit-User` header in `Api::BaseController#identify_user` - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Api::BaseController#identify_user` resolves `current_user` directly from the client-supplied `X-Shipit-User` header with no cryptographic binding to the authenticated `ApiClient`, letting any valid-token holder impersonate an arbitrary existing user for attribution purposes such as merge-request enqueueing.

### Finding Description
Broken binding: `current_user` should equal the GitHub identity behind `current_api_client` (e.g. `current_api_client.creator`), but instead equals `User.where('lower(login) = ?', header).first` [7](#0-6) . `authenticate_api_client` only verifies the bearer token [5](#0-4) , and `require_permission!`/`check_permissions!` only check operation:scope strings on the token's permissions [1](#0-0) , so nothing ties the header value to the real caller. `MergeRequestsController#update` uses this spoofable `current_user` for attribution [6](#0-5) .

### Impact Explanation
An attacker holding any valid, even minimally-privileged, API token can spoof identity of any known/guessable existing user for write actions that record `current_user`, corrupting audit trails and misattributing merge-request/hook actions to victims. Repeatable per request, against any stack the token has access to.

### Likelihood Explanation
Requires only possession of one valid low-privilege API token (not a session, not secrets) and knowledge of a victim's login — low cost, fully repeatable, no GitHub interaction needed.

### Recommendation
Bind `current_user` to `current_api_client.creator` for attribution purposes instead of trusting `X-Shipit-User`, or restrict header-based impersonation to an explicit, separately-authorized `impersonate` scope.

### Proof of Concept
Minitest: authenticate with token for user A (`read:stack` only), send request with `X-Shipit-User` set to user B's login, assert `current_user.login == 'B'` while the token's `creator.login == 'A'`; then call `Api::MergeRequestsController#update` and assert `MergeRequest.request_merge!` receives user B, not A.
