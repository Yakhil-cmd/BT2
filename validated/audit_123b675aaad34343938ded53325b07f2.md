### Title
Webhook signature is verified against the organization from `repository.owner.login`, while stack routing trusts the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, but the event handlers that actually mutate stack state use the independent `repository.full_name` field to look up the target `Repository`/`Stack`. Because both fields live in the same signed payload but are never cross-checked against each other, an attacker who legitimately controls one Shipit-tracked organization (and therefore knows/controls that organization's `webhook_secret`) can craft a payload whose `owner.login` names their own org (to pass signature verification) while `repository.full_name` names a different, victim-owned stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the trust anchor from an attacker-influenced field: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body (`repository.owner.login`, falling back to `organization.login`), and is used only to pick which org's `webhook_secret` (`Shipit.github(organization: repository_owner)`) verifies the HMAC over `request.raw_post`: [3](#0-2) 

Once the signature passes, `create` hands the *entire* raw payload to every handler for the event, unconstrained by the organization used for verification: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` from a *different* field, `repository.full_name`, with no linkage back to `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because `Shipit.github(organization:)` supports per-organization configuration (evidenced by the `GithubOrganizationUnknown` rescue path and per-org `webhook_secret` in `GithubApp#initialize`), this is a genuine multi-tenant configuration where distinct organizations have distinct secrets: [7](#0-6) [8](#0-7) 

This breaks the equality that the invariant is supposed to enforce: `organization whose secret authenticated the request == organization that owns the repository being mutated`. The signature only proves "some legitimate holder of `owner.login`'s secret sent this exact byte string"; it says nothing about whether the `repository.full_name` embedded in that same byte string actually belongs to `owner.login`. GitHub itself would never emit such an inconsistent payload, but nothing in this code prevents an attacker who directly POSTs to the webhook endpoint (which is what the signature check is supposed to be the sole gate against) from constructing one.

### Impact Explanation
An attacker who is an admin/owner of one org tracked by this Shipit instance (and thus knows that org's `webhook_secret`, which they configured) can forge a `push`, `status`, or `check_suite` webhook whose `repository.owner.login`/`organization.login` matches their own org (passing `verify_signature`) but whose `repository.full_name` names a victim's stack. For example, `PushHandler` would call `stack.sync_github(expected_head_sha: params.after)` on the victim's stack with an attacker-chosen SHA, and the `status`/`check_suite` handlers can inject fabricated "success" CI statuses for arbitrary commits on the victim stack. If the victim stack has `continuous_deployment` enabled, forged success statuses can trigger an unauthorized deploy of a commit the victim never approved — this crosses the "unauthorized deploy" impact bar.

### Likelihood Explanation
Medium: requires the attacker to be a legitimate, unprivileged (from Shipit's perspective) admin of at least one org already onboarded onto the same Shipit instance, and requires the target instance to host multiple organizations with per-org secrets. This does not require any Shipit session, API token, or repository write access on the victim's repository — only knowledge of a secret the attacker legitimately possesses for their own org, and the ability to POST directly to the public `/webhooks` endpoint.

### Recommendation
Cross-validate `repository.owner.login` (the field used to select the verification secret) against `repository.full_name`'s owner segment before dispatching to handlers, or better, derive the resolved `Repository`/`Stack` and its organization consistently from the same field used for signature verification, rejecting the payload if they disagree.

### Proof of Concept
1. Attacker administers `org-attacker`, which is registered in Shipit with `webhook_secret = S`, and knows `S`.
2. Shipit also tracks `org-victim/critical-repo` (a different org/secret) with continuous deployment enabled.
3. Attacker crafts a `push` (or `status`) JSON body: `{"repository": {"owner": {"login": "org-attacker"}, "full_name": "org-victim/critical-repo"}, "after": "<attacker-chosen-sha>", ...}`.
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `org-attacker`'s app/secret, and the HMAC check passes because the attacker used the correct secret for that org.
6. `Shipit::Webhooks.for_event('push')` handlers run against the full payload; `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-victim/critical-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, despite the request never being authenticated for `org-victim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
