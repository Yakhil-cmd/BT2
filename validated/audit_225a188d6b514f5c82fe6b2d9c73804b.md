## Analysis

Reviewing the CVE's bug class — a low-privileged party can delete another party's authentication/session resource without any ownership check — the closest reachable analog in `ocore--022` is in the shared (multi-signature) address negotiation protocol reachable by any paired correspondent device via `wallet.js`'s `handleMessageFromHub`.

### Title
Broken Access Control on `reject_new_shared_address` allows any paired device to delete another party's pending shared-address negotiation - ([File: wallet.js])

### Summary
The `reject_new_shared_address` device-message handler deletes a `pending_shared_addresses` record and **all** of its `pending_shared_address_signing_paths` rows using only the attacker-supplied `address_definition_template_chash`, without verifying that the sending device (`from_address`) is actually a participant/signer referenced in that pending shared-address negotiation.

### Finding Description
In `wallet.js`, the message handler is: [1](#0-0) 

```
case "reject_new_shared_address":
    // {address_definition_template_chash: "BASE32"}
    if (!ValidationUtils.isValidAddress(body.address_definition_template_chash))
        return callbacks.ifError("invalid addr def c-hash");
    walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash);
    callbacks.ifOk();
    break;
```

`deletePendingSharedAddress` performs an unscoped delete: [2](#0-1) 

```
function deletePendingSharedAddress(address_definition_template_chash){
	db.query("DELETE FROM pending_shared_address_signing_paths WHERE definition_template_chash=?", [address_definition_template_chash], function(){
		db.query("DELETE FROM pending_shared_addresses WHERE definition_template_chash=?", [address_definition_template_chash], function(){});
	});
}
```

Neither the handler nor `deletePendingSharedAddress` checks `from_address` against the `device_address` column of `pending_shared_address_signing_paths` for that `address_definition_template_chash`. This is in stark contrast to the sibling handler `approve_new_shared_address`, whose corresponding function `approvePendingSharedAddress` correctly scopes the update to the sender: [3](#0-2) 

```
function approvePendingSharedAddress(address_definition_template_chash, from_address, address, assocDeviceAddressesByRelativeSigningPaths){
	db.query( // may update several rows if the device is referenced multiple times from the definition template
		"UPDATE pending_shared_address_signing_paths SET address=?, device_addresses_by_relative_signing_paths=?, approval_date="+db.getNow()+" \n\
		WHERE definition_template_chash=? AND device_address=?", 
		[address, JSON.stringify(assocDeviceAddressesByRelativeSigningPaths), address_definition_template_chash, from_address], 
```

Because `deletePendingSharedAddress` is keyed only on the globally-known `address_definition_template_chash` (which is disclosed to every invited co-signer when the offer is sent via `create_new_shared_address`/`sendOfferToCreateNewSharedAddress`), any device that is a correspondent and receives (or otherwise learns) this chash can send a forged `reject_new_shared_address` justsaying and wipe out the entire pending multisig negotiation for **all** other participants, not just cancel its own pending approval row.

### Impact Explanation
An unprivileged paired-device correspondent (one of the invited co-signers, or any device from which such a message is accepted) can unilaterally destroy the shared-address setup state belonging to other, legitimate co-signers who have not yet completed their approval. This directly mirrors the CVE's bug class ("broken access control allowing a low-privileged user to delete another user's resource," forcing state loss for other parties). Depending on the timing of the attack relative to fund deposits made in anticipation of the deterministic shared address, this can cause loss of coordination state for multisig wallets/AA-related shared addresses that other honest devices rely upon, denying legitimate co-signers the ability to complete or recover the negotiation and, if funds are already directed at the not-yet-finalized shared address, complicating or freezing access pending state to that address.

### Likelihood Explanation
Any device already accepted as a correspondent (paired device) of the node — which is the normal operating mode for shared-address participants — can trivially trigger this by sending a single justsaying message with a guessed/known `address_definition_template_chash`. No signature over the deletion action beyond normal device-message authentication is required, and no membership check is performed, making exploitation straightforward for any invited co-signer or any device that otherwise learns the chash.

### Recommendation
Modify `deletePendingSharedAddress` (or the call site in `wallet.js`) to scope both DELETE statements to the sending `from_address`, mirroring the pattern used in `approvePendingSharedAddress` (`WHERE definition_template_chash=? AND device_address=?`), and only remove/cancel the entire pending record once all remaining participant rows have been individually rejected or the initiator explicitly cancels.

### Proof of Concept
1. Device A (initiator) invites devices B and C to create a shared (multisig) address, sending each the `address_definition_template_chash` via `create_new_shared_address`. [4](#0-3) 
2. Device B has not yet approved, but device C (malicious/uninvolved with respect to A–B's pending row) sends a `reject_new_shared_address` message with the same `address_definition_template_chash` it learned from step 1.
3. The handler in `wallet.js` (lines 228-234) accepts the message from C without checking that C's `device_address` appears in `pending_shared_address_signing_paths` for that chash, and calls `deletePendingSharedAddress`, which deletes the `pending_shared_addresses` row and **all** `pending_shared_address_signing_paths` rows (including A's and B's), destroying the negotiation state for A and B.
