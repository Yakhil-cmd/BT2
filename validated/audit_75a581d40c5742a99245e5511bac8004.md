### Title
Precompile signature-verification arrays (secp256k1/ed25519/secp256r1) are processed with attacker-controlled length but consume zero compute units from the per-transaction compute budget - ([File: precompiles/src/secp256k1.rs], [File: precompiles/src/ed25519.rs], [File: program-runtime/src/invoke_context.rs])

### Summary
The external report describes a bug class where an attacker-controlled array length, iterated with expensive per-element operations (crypto verify + token transfer), can consume disproportionate gas/compute relative to what the caller pays. The closest reachable analog in Agave is the precompile instruction path (`secp256k1_program`, `ed25519_program`, `secp256r1_program`): each precompile's `verify()` function loops over an attacker-controlled `count`/`num_signatures` byte (up to 255) and performs an expensive cryptographic operation (ECDSA recovery, Ed25519 `verify_strict`, ECDSA P-256 verify) per iteration, but this loop is executed entirely **outside** of `InvokeContext`'s per-instruction compute meter.

### Finding Description
In `InvokeContext::process_message` (`program-runtime/src/invoke_context.rs:511-525`), when the top-level instruction's program is a precompile, `self.process_precompile(...)` is called instead of `self.process_instruction(&mut compute_units_consumed, ...)`. `process_precompile` (`program-runtime/src/invoke_context.rs:617-631`) never touches `compute_units_consumed`, so it stays `0` — confirmed by the code comment/test `test_builtin_ix_precompiled` in `core/tests/scheduler_cost_adjustment.rs:381-402`: "VM Execution: consume 0 from CU-meter... Result: adjustment = 3_000" (full CU reservation gets refunded).

Each precompile's `verify()` function (`precompiles/src/secp256k1.rs:23-103`, `precompiles/src/ed25519.rs:11-79`) reads the number of signatures from `data[0]` (a single `u8`, so up to 255) and iterates that many times, each iteration doing:
- `secp256k1`: parse signature, `libsecp256k1::recover(...)` (EC point recovery) plus a keccak hash.
- `ed25519`: `ed25519_dalek::PublicKey::from_bytes` + `verify_strict(...)`.

These are real cryptographic operations invoked purely from attacker-supplied instruction data, with no relationship to the transaction's `compute_unit_limit` or the `compute_meter` used elsewhere in `InvokeContext` (e.g. `program-runtime/src/cpi.rs:1016-1019`, which does `compute_meter.consume_checked(...)` for CPI data costs).

The only accounting for this cost happens separately in the *cost model*, not the *execution-time compute meter*: `CostModel::get_signature_cost` (`cost-model/src/cost_model.rs:129-151`) adds `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST` per counted signature to the transaction's estimated cost, which is used for block-packing/leader cost-limit purposes. This is a static, pre-execution estimate derived from `signature_details.rs` (`get_num_signatures_in_instruction` simply reads `instruction.data.first()`), decoupled from the actual runtime compute-unit budget check that governs every other instruction's execution.

### Impact Explanation
Because precompile verification work is unmetered by the compute meter, a single transaction can pack up to 255 secp256k1 or ed25519 signature verifications per precompile instruction (multiple precompile instructions can be included in one transaction, further multiplying the work), consuming substantial CPU time on every validator that processes/replays the transaction, while the transaction's execution reports `compute_units_consumed = 0` for that instruction and the requested `compute_unit_limit` is irrelevant to it. The only throttle is the cost-model's static `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST` constants used at block-packing time (leader-side cost limits) — if those per-signature cost constants under-estimate the real CPU cost of `libsecp256k1::recover` / `ed25519_dalek::verify_strict` at scale, an attacker can cheaply fill a block with maximally-loaded precompile instructions that are underpriced relative to actual leader CPU consumption, degrading block production throughput cluster-wide (a leader-side cost-limit accounting mismatch reachable from a single submitted transaction).

### Likelihood Explanation
Likelihood is Medium: constructing a transaction with the maximum permitted signature count in a precompile instruction is straightforward and requires no special privileges — any transaction sender can do this. However, actual cluster impact depends on whether `SECP256K1_VERIFY_COST` / `ED25519_VERIFY_STRICT_COST` / `SECP256R1_VERIFY_COST` in `cost-model/src/block_cost_limits.rs` are properly calibrated against real-world CPU cost of these crypto primitives at the maximum signature count — a value I was not able to fully verify against a measured benchmark in the given context (the search only located the constant names, not their calibration methodology or the results of the CPU-time correlation).

### Recommendation
- Verify that `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256R1_VERIFY_COST` in `cost-model/src/block_cost_limits.rs` are conservatively calibrated to real wall-clock cost of `libsecp256k1::recover`, `ed25519_dalek::verify_strict`, and the secp256r1 ECDSA verify at the maximum 255-signature case, including on the slowest supported validator hardware.
- Consider metering precompile verification directly against the instruction's `compute_unit_limit` (e.g., via `compute_meter.consume_checked`) rather than relying solely on the separate, pre-execution cost-model estimate, so that a mis-calibrated cost constant cannot desynchronize block-packing cost from actual leader CPU expenditure.
- Add an explicit fuzz/benchmark test that measures wall-clock time for a transaction with the maximum number of secp256k1/ed25519/secp256r1 signature verifications packed into a single transaction, and confirm it stays within the leader's per-slot processing budget implied by the cost-model constants.

### Proof of Concept
1. Construct a `secp256k1_program` (or `ed25519_program`) instruction whose first data byte (`count`/`num_signatures`) is `255`, with `SIGNATURE_OFFSETS_SERIALIZED_SIZE`-sized offset structs for each of the 255 signatures, each pointing to a valid signature/pubkey/message within the transaction's instruction data (per `precompiles/src/secp256k1.rs:44-101` / `precompiles/src/ed25519.rs:30-77`).
2. Submit this as a single transaction from an unprivileged signer; sign it normally so it passes standard signature checks.
3. During `InvokeContext::process_message`, this instruction routes to `process_precompile` (`program-runtime/src/invoke_context.rs:516-524`) instead of `process_instruction`, so `compute_units_consumed` for the instruction remains `0` regardless of how many EC recoveries/verifications are performed.
4. Repeat/pack multiple such instructions or transactions per block; measure the leader's actual CPU time spent in `secp256k1::verify`/`ed25519::verify` versus the cost-model-estimated `signature_cost` used for block-cost-limit accounting to determine whether the estimate under-represents real cost (this final calibration check was not completed within the available search).
