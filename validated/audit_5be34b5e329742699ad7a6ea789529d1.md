### Title
Cross-Stack Read via `Api::CCMenuController` Bypassing Per-Token Stack Scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides both authentication and stack resolution in a way that breaks the "stack a token authorises" vs "stack it touches" binding that the rest of the API enforces. An `ApiClient` token that is scoped to a single stack via `ApiClient#stack_id` can be replayed against any other stack's CCMenu endpoint and will return that other stack's build/deploy status, because the controller never checks the token's `stack_id` against the requested `stack_id` parameter.

### Finding Description
In the base API controller, stack access is always scoped through `current_api_client`: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client has a `stack_id`, and `stack` resolves `params[:stack_id]` only within that restricted scope. This is the intended equality: `token.stack_id == stack.id` (or unrestricted, if `stack_id` is nil).

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
`Stack.from_param!(params[:stack_id])` resolves against **all** stacks, not `stacks` (the scoped relation). The `require_permission :read, :stack` before_action only checks that the token has the `read:stack` permission bit — it never validates that the token's `stack_id` (if any) matches the stack being requested.

The intended workflow that creates these scoped tokens confirms the scoping is meant to be enforced: `CCMenuUrlController` mints an `ApiClient` with only `read:stack` permission (no `stack_id` binding is actually set on creation here, but the general mechanism—and `ApiClient.PERMISSIONS`/`stack_id` column—exists specifically to allow scoping a client to one stack): [3](#0-2) 
`ApiClient` model exposes `belongs_to :stack, optional: true` and `check_permissions!` only validates the operation/scope string, not the stack binding: [4](#0-3) 

Any code path that creates a stack-scoped `ApiClient` (the `stack_id` column exists precisely to let an operator hand out a token restricted to one stack, e.g. for embedding in third-party CI dashboards) is silently un-scoped the moment it's used against `Api::CCMenuController`, because that controller's custom `stack` method does not go through `BaseController#stacks`.

### Impact Explanation
This is an authorization bypass allowing unauthenticated-relative-to-scope read of another stack's task/deploy stream data (last deploy id, status, end time) — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact bucket, since a token meant to be confined to stack A can read stack B's CCMenu/build status data by simply changing the `stack_id` route parameter while reusing the same query-string token.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single stack) and knowledge/guessing of another stack's `owner/repo/environment` param. No privileged access, TLS interception, or GitHub credentials are needed — an attacker who is handed (or leaks) a scoped CCMenu URL/token for one project can pivot to read status of every other stack in the Shipit instance.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped `stacks` relation as `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so that a stack-scoped `ApiClient` cannot be used to access stacks outside its `stack_id` binding.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (e.g., via a CCMenu-URL-style workflow).
2. As an attacker holding this token, issue `GET /api/<StackB-owner>/<StackB-repo>/<StackB-env>/ccmenu.xml?token=<tokenA>` where `stack_id` in the URL now names Stack B instead of Stack A.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`), the request succeeds and returns Stack B's latest deploy/rollback status — data the token was never authorized to read.

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
