## Title
`status` webhook handler resolves target commits globally by SHA, allowing an authenticated organization to forge CI status on commits belonging to other repositories/stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`WebhooksController#verify_signature` authenticates a webhook based on the `organization`/`repository.owner.login` claimed inside the payload, selecting the matching GitHub App/organization secret to validate the HMAC signature. That authentication only proves the sender knows the secret associated with *that* organization/repository. However, `StatusHandler#process` (the code that actually acts on the verified payload) does not scope its write to the authenticated repository at all — it looks up `Commit.where(sha: params.sha)` globally across the entire database and calls `create_status_from_github!` on every match, regardless of which stack/repository that commit belongs to.

## Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload and uses it to pick the GitHub App config/secret to verify against: [1](#0-0) [2](#0-1) 

This only establishes that the sender possesses the webhook secret configured for that particular organization/repository (`Shipit.github(organization: repository_owner)`), i.e. it binds "the organization that authenticated" to the request. It says nothing about which Shipit `Commit`/`Stack` should be affected beyond what the handler itself derives from the payload.

The base `Handler` class does provide a `repository_name`/`stacks` scoping helper based on `payload.dig('repository', 'full_name')`: [3](#0-2) 

`CheckSuiteHandler` correctly uses this scoping (`stacks.where(branch: ...)`) before touching commits: [4](#0-3) 

But `StatusHandler` does not use `stacks`/`repository_name` at all — it queries `Commit` directly by `sha`, with no repository/stack filter: [5](#0-4) 

Because commit SHAs are content-addressed and can collide across repositories tracked by the same Shipit instance (e.g. forks, mirrored/duplicated history, or two independently-hosted repos that happen to share commits after a rebase/cherry-pick, or simply an attacker registering a stack that shares initial commits with a target stack), an attacker who controls the webhook secret for **any** organization/repository configured in this Shipit instance can send a `status` event whose `sha` matches a commit belonging to a **different** organization's stack, and have `create_status_from_github!` write an arbitrary CI status (`state`, `context`, `description`, `target_url`) onto that unrelated commit.

This breaks the required binding: **the organization that authenticated (via the webhook secret matched to `repository_owner`) must equal the repository whose data is written**. Here, the code authenticates organization A but writes to a commit that may belong to stack/repository B.

## Impact Explanation
`Commit#create_status_from_github!` feeds into `add_status`, which can flip a commit's aggregate `state` to `success`, which in turn:
- Marks the commit `deployable?`
- Can trigger `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`, causing an **unauthorized deploy** of a commit that never actually passed CI on its real repository, if the target stack has `continuous_deployment` enabled: [6](#0-5) [7](#0-6) 

This matches the required impact category of "an unauthorized deploy" without requiring any privileged Shipit session, `ApiClient` token, or repository write access on the target repository — only a valid webhook secret for *some* organization registered in the same Shipit instance is needed, and the write lands on a commit/stack outside that organization's authority.

## Likelihood Explanation
Exploitability requires:
1. Multiple organizations/repositories configured in the same Shipit instance (a common deployment pattern for shared internal Shipit installs).
2. A SHA collision between a commit tracked under the attacker's authenticated organization and a commit tracked under the victim stack (achievable deliberately, e.g. by forking/mirroring, cherry-picking, or otherwise causing an identical commit object to be pushed to both a repo the attacker controls and a repo they don't, since git commit objects are portable and identical byte-for-byte SHA when the tree/parent/metadata match).

This is a real, exploitable violation of the intended per-repository trust boundary, though it depends on this multi-tenant deployment scenario, so likelihood is best characterized as **medium**: the fix (scoping to `stacks`/`repository_name`, exactly as `CheckSuiteHandler` already does) is straightforward and clearly intended given the sibling handler's pattern.

## Recommendation
Scope `StatusHandler#process` to the authenticated repository the same way `CheckSuiteHandler` does, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks`/`repository_name` helper from `Handler`, so that a webhook authenticated for organization/repository A can never mutate commit status data belonging to repository B.

## Proof of Concept
1. Configure two organizations/stacks in the same Shipit instance: `attacker-org/repo` (attacker has webhook secret) and `victim-org/repo` (target stack, e.g. with `continuous_deployment: true`).
2. Cause a commit with SHA `X` to exist in both `attacker-org/repo`'s tracked history (e.g. by cherry-picking/porting an identical commit object) and in `victim-org/repo`'s tracked history in Shipit's `commits` table.
3. Send a `status` webhook to `/webhooks` signed with `attacker-org`'s webhook secret, with payload:
   ```json
   { "sha": "X", "state": "success", "context": "ci/forged", "repository": {"owner": {"login": "attacker-org"}} }
   ```
4. `verify_signature` validates successfully against `attacker-org`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "X")`, which matches the commit row belonging to `victim-org/repo`'s stack, and calls `create_status_from_github!`, marking it `success`.
6. If `victim-org/repo`'s stack has `continuous_deployment` enabled, this schedules `ContinuousDeliveryJob`, resulting in an unauthorized deploy triggered entirely by the attacker's forged webhook, with no credentials for `victim-org` ever being used.
