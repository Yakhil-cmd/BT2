### Title
Split during the epoch-reward distribution window triggers `assert_eq!` panic in `build_updated_stake_reward`, causing a cluster-wide validator halt - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`calculate_stake_rewards_and_commissions` snapshots each delegated stake's `delegation.stake` at the epoch-boundary calculation block into an immutable `PartitionedStakeReward` that is applied over many subsequent blocks. `build_updated_stake_reward` later re-reads the *current, live* stake state from `stakes_cache_accounts` and asserts it still equals the snapshotted pre-reward value. A staker can submit an ordinary `Split` instruction against their own stake account after calculation but before their account's distribution block, invalidating that assumption and hitting the `assert_eq!` panic deterministically on every validator.

### Finding Description
At the epoch boundary, `begin_partitioned_rewards` (`runtime/src/bank.rs:1815-1904` calling into `calculation.rs:780`) computes `PartitionedStakeReward` entries for every delegated stake account and freezes them via `set_epoch_reward_status_calculation` [1](#0-0) . Each entry's `inflation.stake` field already contains the pre-reward delegation amount plus the calculated reward, fixed at calculation time [2](#0-1) .

Distribution of these rewards is spread over up to 10% of the epoch's slots (`get_reward_distribution_num_blocks`) [3](#0-2) , with partition assignment (which pubkey is paid in which block) computed deterministically from a public blockhash-derived hash function the very first time `distribute_partitioned_epoch_rewards` is called [4](#0-3) , meaning an attacker can predict exactly which future block will process their own stake account.

For each block in that window, `store_stake_accounts_in_partition` re-reads the **current, live** stakes cache (not a snapshot) via `self.stakes_cache.stakes()` [5](#0-4) , and passes it into `build_updated_stake_reward`. When `relax_post_exec_min_balance_check` (SIMD-0392) is not active, that function does:

```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, ...);
``` [6](#0-5) 

where `stake` is the *live* current on-chain delegation and `new_stake` is the *frozen* `partitioned_stake_reward.inflation.stake` computed at the earlier calculation block [7](#0-6) .

An unprivileged staker/withdrawer authority can submit a `Split` instruction (permissionless native stake-program instruction requiring only their own staker authority) that partially reduces their stake account's `delegation.stake` after the calculation block but before their assigned distribution block. This makes the live `stake.delegation.stake` differ from the value frozen in `partitioned_stake_reward.inflation.stake`, so `expected_delegation != new_stake.delegation.stake`, and the `assert_eq!` fires. No signer/authority/rent-exempt guard in the stake program restricts `Split` during the reward-distribution window; the window (potentially many slots) and the deterministic partition-scheduling make the exact target block precisely predictable.

Because every validator processes the identical `Split` transaction and the identical frozen `PartitionedStakeReward` set before reaching the same distribution block, the panic is fully deterministic and simultaneous across the entire honest validator set — this is a cluster-wide halt, not merely a bank-hash divergence.

### Impact Explanation
This is a liveness-halting bug reachable by any normal staker: submitting one `Split` transaction at a predictable slot during their own reward distribution window crashes every validator that processes that block via a Rust `assert_eq!` panic. This falls under Agave's "Loss of Liveness"/"Bank Hash Divergence" bounty category (deterministic panic that halts the whole cluster), triggered without any privileged, leader, or gossip access — only ordinary stake instructions signed with the attacker's own staker authority.

### Likelihood Explanation
Feasibility is high: `relax_post_exec_min_balance_check` (the feature gate for `adjust_delegations_for_rent`, i.e., SIMD-0392) is a newly introduced feature and likely inactive on many clusters, leaving the `assert_eq!` branch live. The distribution window spans multiple slots (up to 10% of an epoch), partition assignment is deterministically derivable from public data (parent blockhash + pubkey hash), and `Split` is a standard permissionless instruction requiring only staker-authority signature over the attacker's own account. No existing check blocks stake-account mutation during the reward-calculation/distribution interval.

### Recommendation
Either (a) always compute `expected_delegation`/apply rewards against a stable, epoch-boundary snapshot of the stake state rather than the live `stakes_cache_accounts` (mirroring what `adjust_delegations_for_rent`/`recalculate_stake_rewards` already does), or (b) reject/replace the `assert_eq!` with graceful degrade-and-continue handling similar to the `AccountNotFound`/`ArithmeticOverflow` error paths, treating a delegation mismatch as a burn/log event instead of an unconditional panic, and additionally have `build_updated_stake_reward` reconcile using the live delegation as authoritative (as `adjust_delegation_for_rent` already does) regardless of the feature-gate state.

### Proof of Concept
Integration test plan (Rust, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` test module style):
1. Build a `RewardBank` (as in existing tests, e.g. `create_reward_bank_with_specific_stakes`) with several delegated stake accounts and multiple reward-distribution partitions (`num_rewards_per_block` small enough to force >1 distribution block).
2. Advance to the epoch boundary block so `begin_partitioned_rewards` freezes `PartitionedStakeReward`s (`EpochRewardPhase::Calculation`).
3. Using the public `parent_blockhash` and `hash_rewards_into_partitions`, precompute which partition/block a target stake pubkey will be distributed in.
4. Before that block, process a `Split` transaction (via `solana_stake_program::stake_instruction::split`) signed by the staker authority that reduces (not zeroes) the target account's `delegation.stake`.
5. Advance banks until reaching the target distribution block and call `distribute_partitioned_epoch_rewards()` / `store_stake_accounts_in_partition`.
6. Assert: with `relax_post_exec_min_balance_check` disabled, the call panics with `"stake reward delegation must be consistent with the updated stake account lamport balance"` (use `#[should_panic]` or `catch_unwind`), demonstrating the reachable halt. Additionally assert that with `adjust_delegations_for_rent` on, no panic occurs but `post_balance`/`delegation.stake` diverges from the pre-split expected value, showing the parallel value-conservation issue.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
