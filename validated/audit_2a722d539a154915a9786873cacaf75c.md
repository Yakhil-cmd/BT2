### Title
EIP-7702 Authorization Nonce Not Consumed on Non-Legacy Key Rejection, Enabling Replay — (`blockchain/state_transition.go`)

### Summary
`applyAuthorization` returns `ErrAuthorizationNotAllowAccountKeyType` **before** calling `st.state.IncNonce(authority)` when the authority account exists but holds a non-legacy key. The error is silently swallowed by the `TransitionDb` auth-list loop. The authority's nonce is therefore never consumed, and the signed authorization remains permanently replayable until the nonce advances for an unrelated reason.

### Finding Description
In `applyAuthorization` (lines 762–794 of `blockchain/state_transition.go`):

```
authority, err := st.validateAuthorization(auth)   // nonce check PASSES here
if err != nil { return err }

if st.state.Exist(authority) {
    accountKeyType := st.state.GetKey(authority).Type()
    if !accountKeyType.IsLegacyAccountKey() {
        return fmt.Errorf(...)   // ← returns HERE, BEFORE IncNonce
    }
    st.state.AddRefund(...)
}

st.state.IncNonce(authority)   // ← never reached for non-legacy accounts
```

`validateAuthorization` verifies `state.GetNonce(authority) == auth.Nonce` and returns success. Control then reaches the Kaia-specific key-type guard, which returns an error. Because `IncNonce` is placed after that guard, the authority's on-chain nonce stays at `N`. The `TransitionDb` loop discards the error with the comment "Note errors are ignored, we simply skip invalid authorizations here." The signed authorization with `nonce=N` is therefore still valid in every subsequent block.

### Impact Explanation
An attacker who possesses a previously broadcast (on-chain) `SetCodeAuthorization` signed by an authority that held a non-legacy key at submission time can replay it in any future `TxTypeEthereumSetCode` transaction. If the authority subsequently executes a `TxTypeAccountUpdate` to downgrade to `AccountKeyTypeLegacy` (a supported operation), the replayed authorization passes both `validateAuthorization` (nonce still `N`) and the key-type guard (now legacy), and `SetCodeToEOA` installs the delegation. The authority's account is then delegated to an arbitrary address without the authority's current consent, enabling the delegate contract to execute arbitrary logic in the authority's context — including draining KAIA or ERC-20 balances held by that account.

### Likelihood Explanation
The preconditions are:
1. Authority holds a non-legacy key (`AccountKeyTypePublic`, `AccountKeyTypeWeightedMultiSig`, or `AccountKeyTypeRoleBased`) at the time of the first `TxTypeEthereumSetCode` submission.
2. A valid signed authorization for that authority was included in a transaction that was mined (the authorization is publicly extractable from chain data).
3. The authority later performs a `TxTypeAccountUpdate` to a legacy key.

Step 3 is the limiting factor, but it is a normal user operation and requires no attacker privilege. Steps 1 and 2 are straightforward. The attacker's only cost is gas for the replay transaction.

### Recommendation
Move `IncNonce` to immediately after `validateAuthorization` succeeds, before any Kaia-specific key-type check, mirroring the EIP-7702 specification which mandates nonce increment as soon as the nonce check passes:

```go
authority, err := st.validateAuthorization(auth)
if err != nil {
    return err
}

// Consume the nonce unconditionally once validation passes,
// to prevent replay regardless of subsequent checks.
st.state.IncNonce(authority)

if st.state.Exist(authority) {
    accountKeyType := st.state.GetKey(authority).Type()
    if !accountKeyType.IsLegacyAccountKey() {
        return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
    }
    st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
}
// ... rest of delegation installation
```

### Proof of Concept
1. Deploy a test chain with Prague/Osaka rules enabled.
2. Create account `authority` with `AccountKeyTypePublic` and nonce `N`.
3. Sign a `SetCodeAuthorization{nonce: N, address: <malicious_delegate>}` with `authority`'s private key.
4. Submit a `TxTypeEthereumSetCode` transaction (sender ≠ authority) containing that authorization. The tx is mined; `applyAuthorization` returns `ErrAuthorizationNotAllowAccountKeyType` and the loop silently continues.
5. Assert `state.GetNonce(authority) == N` (unchanged).
6. Submit a `TxTypeAccountUpdate` from `authority` to downgrade to `AccountKeyTypeLegacy`. Nonce advances to `N+1` for the sender nonce of that tx, but the authorization nonce `N` was never consumed by step 4.
7. Replay the original authorization (extracted from step 4's on-chain tx) in a new `TxTypeEthereumSetCode`. `validateAuthorization` passes (nonce still `N`), key-type check passes (now legacy), `SetCodeToEOA` installs the delegation.
8. Assert `state.GetCode(authority)` equals the delegation designator for `<malicious_delegate>`.
