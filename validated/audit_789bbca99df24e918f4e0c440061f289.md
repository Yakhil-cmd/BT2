## Analysis

**Binding claimed broken:** `verifying_organization == team.organization`, where `verifying_organization = Shipit.github(organization: repository_owner)` used in `WebhooksController#verify_signature`, and `team.organization` is the `Shipit::Team#organization` column of the record matched by `find_or_create_team!`.

**Trace:**

- `WebhooksController#verify_signature` derives the org whose secret is used to verify the HMAC from `repository_owner`, which for a `membership` event (no `repository` key) falls back to `params.dig('organization','login')` [1](#0-0) .
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }` — a **global**, unscoped lookup on `github_id`, with no `organization:` constraint [2](#0-1) .
- The `teams` table has a unique index on `[organization, slug]`, but **no** uniqueness or scoping constraint tying `github_id` to `organization` [3](#0-2) .
- When `find_or_create_by!` finds an existing row (created earlier by a legitimate webhook from a different, authorized org), the block is **not** executed (block only runs on create), so the pre-existing `team.organization` is left untouched — yet `process` unconditionally calls `team.add_member(member)` [4](#0-3) .
- `Team#add_member` unconditionally appends the member with no organization check: [5](#0-4) .
- Team membership feeds directly into authorization: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and `Shipit.github_teams` resolves configured team handles to `Team` rows via `Team.find_or_create_by_handle` [6](#0-5) [7](#0-6) . `force_github_authentication` gates all app access on this [8](#0-7) .

**Why guards don't stop it:** `verify_signature` only proves the payload was signed with *some* org's secret matching `params.organization.login` — it says nothing about whether `params.team.id` actually belongs to that org. The `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, etc., not their relationship [9](#0-8) . Nothing in the code path ever checks `team.organization == params.organization.login`.

**However**, this requires the attacker to control an organization whose webhook secret is configured in Shipit (`Shipit.github(organization:)` must resolve without raising `GithubOrganizationUnknown`, and `verify_webhook_signature` must pass) — i.e., the attacker must already be an authenticated/verified GitHub organization known to this Shipit instance (per the question's own precondition: "an attacker-verified org"). Given that precondition is asserted by the question rather than independently established as reachable by a fully unprivileged attacker, and Shipit deployments typically host a single organization's app (the multi-org `github:` config with per-org keys is an optional/advanced feature — see `docs/setup.md` "Using Multiple Github Applications"), whether an "attacker-owned, Shipit-verified org" is a realistic precondition depends entirely on host configuration, which is outside this engine's own code. Within the engine's code, though, the guard that the question says should hold (team must belong to the verifying org) genuinely does not exist.

### Title
Unscoped `Team.find_or_create_by!(github_id:)` lets any Shipit-verified organization inject members into another organization's team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by the global `github_id` column with no scoping to the verifying organization. Since webhook signature verification only proves the request was signed by *some* configured organization's secret and never checks that the referenced team actually belongs to that organization, a party controlling any organization configured in Shipit's multi-org `github:` secrets can add arbitrary users to any pre-existing `Team` row by guessing/colliding its `github_id`.

### Finding Description
The broken equality is `verifying_organization (Shipit.github(organization: repository_owner)) == team.organization (Team#organization of the row matched by github_id)`. `WebhooksController#verify_signature` derives the org used for HMAC verification from `params.organization.login` for membership events [1](#0-0) . That is the only organization the request is bound to. `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [10](#0-9) ; the assignment block only executes if a new record is created. If a `Team` with that `github_id` already exists (created earlier for a different, unrelated organization), `find_or_create_by!` returns that pre-existing row unmodified — its `organization` field still reflects the original owning org, not the attacker's org. `process` then unconditionally runs `team.add_member(member)` [4](#0-3) , and `Team#add_member` performs no organization check [5](#0-4) . The `teams` table only enforces uniqueness on `[organization, slug]`, not on `github_id` per organization [3](#0-2) .

Attacker request: from an organization the attacker controls that is configured in Shipit's `github:` secrets (multi-org schema, per `docs/setup.md`), POST to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with that org's `webhook_secret`, and a body `{"action":"added","team":{"id":<guessed integer>,...},"organization":{"login":"<attacker-org>"},"member":{"login":"<attacker-controlled-login>"}}`. If `<guessed integer>` collides with an existing `Team#github_id` for a different, privileged organization, the attacker's chosen member is added as a member of that team.

### Impact Explanation
A successful hit adds an attacker-chosen GitHub user as a member of an authorization-relevant `Shipit::Team`. Since `User#authorized?` grants access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5)  and `force_github_authentication` gates the whole application on this check [8](#0-7) , this is a direct escalation into `Shipit.github_teams` authorization for a team the attacker does not belong to, matching the "High - escalation into `Shipit.github_teams` authorization" category. Repeatable per guessed `github_id`; blast radius is bounded to whichever Team rows happen to collide with guessed IDs.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org `github:` secrets schema so that more than one organization's webhook secret is known to the instance, and (2) the attacker controls one such configured organization (i.e., they are already a "verified" org per this instance's config — a nontrivial precondition set by the deployer, not by this engine's code). Given that, the attacker's cost is low: forge signed JSON payloads and iterate small integers for `team.id`. Feasibility depends entirely on host configuration granting the attacker a legitimately configured organization slot, which is an operational precondition rather than something exploitable by a fully unprivileged internet user against a typical single-org Shipit deployment.

### Recommendation
Scope the team lookup to the verifying organization: `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify `team.organization == params.organization.login` (or `repository_owner`) before calling `add_member`/`members.delete`, raising/dropping the event on mismatch. Add a unique index on `[organization, github_id]` (or at minimum validate uniqueness in the model) to prevent silent cross-org row reuse.
