### Title
Same Bitcoin L1 lockup output can be reused across multiple `register-for-bond` calls to double-count committed sats - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` only deduplicate lockup outpoints *within a single call's fold* (the `seen-outpoints` accumulator starts fresh as `(list)` on every invocation of `verify-l1-lockups`). There is no persistent, contract-wide map recording which Bitcoin outpoints have already been consumed to back a bond registration. As a result, a staker (or any principal, since the merkle proof is a public, replayable artifact once the Bitcoin transaction is confirmed) can present the exact same valid L1 lockup proof in more than one `register-for-bond`/bond-registration call, crediting the same locked sats to multiple bonds.

### Finding Description
`validate-l1-lockup` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:2031-2113`) validates a Bitcoin output against the expected timelock script, checks the merkle proof, and folds the amount into a running `sum`, guarding only against duplicates *inside the same list of outputs passed in the current call* via `seen-outpoints`: [1](#0-0) 

`verify-l1-lockups` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:1984-2019`) initializes `seen-outpoints` to `(list)` for every call: [2](#0-1) 

Because this state is local to the fold and not persisted in any contract map (no `define-map` keyed on `(txid, output-index)` exists anywhere in the file), nothing prevents the same Bitcoin outpoint from being presented again in a *subsequent* transaction. The Bitcoin lockup script and merkle proof are public data once mined, so any principal who observes a successful `register-for-bond` transaction can replay the identical lockup tuple (header, tx, merkle path) into a new bond-registration call. The contract will re-validate the same on-chain P2WSH output and credit its `amount` as freshly-locked sats again, exactly as the `_payment()` bug in LienToken.sol paid out the full amount without checking whether it had already been accounted for against the actual remaining balance.

This breaks the equality the L1-lockup design is meant to enforce: `sum of sats credited across all bonds == sats actually locked on Bitcoin`. With no cross-call ledger of consumed outpoints, one real Bitcoin lockup can back an unbounded number of pox-5 bond registrations.

### Impact Explanation
Each bond registration derived from a replayed lockup proof grants bond membership/signing weight and a claim on sBTC bond rewards (via `calculate-bond-rewards`/`claim-rewards`) that is not backed by any additional locked value — this is unbacked minting of reward entitlement and/or double-counting of a stacking commitment. Depending on how many times the same outpoint is replayed, this can create reward slots/signing weight that exceed the value actually locked on Bitcoin, which maps to the Critical/High impact categories (double-counting a commitment, unbacked reward entitlement).

### Likelihood Explanation
No special privilege is required: any account with knowledge of an already-mined, successful lockup transaction (which is public once broadcast and used once) can submit it again as `register-for-bond` calldata. The only barrier is whatever per-staker/per-bond replay guards exist at the call site of `verify-l1-lockups` (e.g., "already registered" checks for the *same* staker/bond); however, since the dedup implemented in-contract is explicitly scoped to a single call's output list and no global outpoint map exists, a different staker principal (or the same staker registering a second, distinct bond index) is not prevented from reusing the outpoint.

### Recommendation
Persist consumed L1 lockup outpoints in a contract-level map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), and have `validate-l1-lockup` check and set membership in that persistent map (in addition to the local `seen-outpoints` list), asserting `ERR_DUPLICATE_LOCKUP_OUTPOINT` if the outpoint has already been consumed by any prior bond registration.

### Proof of Concept
1. Staker A locks `X` sats on Bitcoin into the timelock P2WSH script for principal A per `construct-lockup-output-script`.
2. Staker A calls `register-for-bond` with the valid merkle proof for that output; `validate-l1-lockup` succeeds, and bond #1 is credited `X` sats via `verify-l1-lockups`.
3. Because the merkle proof, header bytes, and raw transaction are now public on the Bitcoin chain, any principal (or staker A again, for a different bond index / rollover call reachable in pox-5) resubmits the identical lockup tuple in a second `register-for-bond`-style call.
4. `validate-l1-lockup`'s `seen-outpoints` list is freshly initialized to `(list)` for this new call (per `verify-l1-lockups`), so the duplicate check does not fire; the same `X` sats are credited again to a second bond.
5. Net effect: `X` sats locked once on Bitcoin now back `2X` (or more) sats' worth of bond credit/reward entitlement in pox-5, with no corresponding additional Bitcoin lock.

Note: I was unable to fully trace the `register-for-bond` public entry point (repeated searches for it inside `pox-5.clar` returned no matches, likely due to index/content coverage limits) to check whether an additional external guard (e.g., a global "lockup used" check outside `verify-l1-lockups`) exists elsewhere in that function body. If such a guard exists in code outside the sections retrieved, it would mitigate this finding; a full review of `register-for-bond` and any related bond-rollover functions in `pox-5.clar` is recommended to confirm.
