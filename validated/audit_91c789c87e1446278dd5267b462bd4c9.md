### Title
Webhook signature verification binds to `repository.owner.login`, but payload processing writes to a repository chosen by the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` from the JSON body, while every webhook `Handler` resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same body: `repository.full_name`. Because these two fields are never cross-checked against each other, and both are attacker-controlled inside the payload whose integrity is verified, an entity that is a legitimate GitHub organization owner on this Shipit instance (and therefore knows their own `webhook_secret`) can forge a validly-signed webhook that authenticates as their own organization but targets a completely different organization's repository/stack.

### Finding Description
`verify_signature` computes the signing organization from the payload itself: [1](#0-0) [2](#0-1) 

This uses `params.dig('repository', 'owner', 'login')` to look up `Shipit.github(organization: repository_owner)` and its `webhook_secret`, then verifies the HMAC over the *raw* body against that secret: [3](#0-2) 

However, once the signature check passes, the event is dispatched to handlers, and `Handler#stacks` — used by `PushHandler`, `StatusHandler`, etc. — resolves the target repository/stack from a *different* field of the same body: [4](#0-3) [5](#0-4) 

`repository.owner.login` (used for signature verification) and `repository.full_name` (used to resolve the actual stack that gets written to) are independent JSON fields inside the same payload. Because HMAC verification only checks the byte-integrity of the whole raw body against the secret picked via `repository.owner.login`, it does not constrain the *value* of `repository.full_name` to be consistent with that owner. An attacker who legitimately owns/administers an organization "attacker-org" that is configured in this shared Shipit instance (and thus knows or controls their own org's `webhook_secret`, e.g. as configured in their own GitHub App/webhook settings) can craft a payload with:
- `repository.owner.login = "attacker-org"` → signature check passes using attacker-org's own secret
- `repository.full_name = "victim-org/victim-repo"` → the actual write target

This breaks the intended equality `organization_that_authenticated == organization/repository_that_is_written`.

Concretely, `StatusHandler` (exercised by the test at `test/controllers/webhooks_controller_test.rb:42-59`) writes attacker-controlled `state`, `description`, `target_url`, and `context` directly onto a `Commit#statuses` record found in the resolved stack, without any relation to which organization's key signed the request: [6](#0-5) 

`PushHandler` similarly resolves stacks through `Handler#stacks` (i.e., via `repository.full_name`) and enqueues a `GithubSyncJob` for the resolved stack: [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate organization owner onboarded to a shared/multi-tenant Shipit instance (i.e., an unprivileged attacker with respect to any *other* organization's stacks) can forge validly-signed webhooks whose `repository.full_name` points at a stack belonging to a different organization. This allows:
- Forging arbitrary GitHub commit statuses (`state`, `context`, `target_url`, `description`) on commits belonging to another organization's stack, which Shipit's deploy safety checks and merge-request auto-merge logic rely on to decide whether a commit is deployable/mergeable — this can enable an unauthorized deploy or merge decision on a stack the attacker does not own.
- Triggering `GithubSyncJob` / sync operations against another organization's stack out of the intended authorization boundary.

This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope, and the ability to forge a deployability-affecting signal (commit status) that feeds into unattended deploy/merge decisions aligns with the Critical/High impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires only that the attacker control (as a legitimate customer/organization) one organization already configured on the shared Shipit instance with its own `webhook_secret` — which is a standard, non-privileged configuration for any onboarded org, not a stolen victim secret. No access to the victim's secret, session, or `ApiClient` token is needed; only crafting a raw HTTP POST with a body whose `repository.owner.login` and `repository.full_name` diverge, and signing it with the attacker's own known secret.

### Recommendation
`verify_signature` must ensure the field used to select the verifying organization's secret is the *same* field (and same value) used by `Handler#stacks`/`Repository.from_github_repo_name` to resolve the target repository — e.g., derive both from `repository.full_name`'s owner segment, or explicitly cross-validate that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker crafts a raw JSON body for a `status` (or `push`) event:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/tests",
     "description": "forged",
     "target_url": "https://evil.example"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` using their own known secret `S`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully against `S`. [1](#0-0) 
5. `StatusHandler`/`PushHandler` resolve the target stack via `repository.full_name = "victim-org/victim-repo"` through `Handler#stacks` → `Repository.from_github_repo_name`. [4](#0-3) 
6. The forged status/push is applied to `victim-org/victim-repo`'s stack despite the request only being authenticated as `attacker-org`.

Note: I was unable to inspect the full contents of `StatusHandler`/`app/models/shipit/webhooks/handlers/status_handler.rb`, `Shipit.github` / `github_apps` config lookup implementation in `lib/shipit.rb`, or `Commit#deployable?`/merge-request auto-merge logic within this session (index size limits may have excluded some file contents); a Devin session with full repository access would be needed to confirm the exact downstream consumption of forged commit statuses in deploy/merge gating logic.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
