### Equality claimed (stated before tracing)
`cell_indices[i]` as decoded from the identical wire-encoded sidecar bytes (value `18446744073709551615` = `u64::MAX`) must be the *same* 64-bit value in every language binding at the moment it is handed to `verify_cell_kzg_proof_batch`'s C bounds check at [1](#0-0) .

### Trace
- Node.js binding: `get_cell_index` requires the JS value to be a `Napi::Number` (IEEE‑754 double) and does `static_cast<uint64_t>(number)` [2](#0-1) . It is used verbatim in `VerifyCellKzgProofBatch` to populate `cell_indices[i]` before calling the native C function [3](#0-2) .
- `18446744073709551615` (2^64‑1) is not representable as an IEEE‑754 double; the nearest representable double is `2^64` exactly. Converting a double equal to `2^64` to `uint64_t` via `static_cast` is undefined behavior in C++ because `2^64` lies outside `[0, 2^64‑1]`. On common x86‑64 codegen (`cvttsd2si` + glibc-style unsigned conversion), this UB typically resolves to `0`, not to `0xFFFFFFFFFFFFFFFF`.
- The Rust binding passes `cell_indices` as an exact `u64` slice/pointer straight into the FFI call with no floating-point intermediate, so `cell_indices[i]` there stays bit-for-bit `18446744073709551615`.
- Both bindings ultimately call the identical C bounds check `if (cell_indices[i] >= CELLS_PER_EXT_BLOB) return C_KZG_BADARGS;` at [1](#0-0) . For Rust, the value `18446744073709551615 >= CELLS_PER_EXT_BLOB` is true → `C_KZG_BADARGS`, rejected. For Node.js, the truncated/UB value (commonly `0`) is `< CELLS_PER_EXT_BLOB` → passes the check and the sidecar is fully verified against cell/column 0 as if it were a legitimately indexed cell.

### Guards checked and why they don't help
- `bytes_to_bls_field`/`validate_kzg_g1` operate on field/curve bytes, not on the index integer, so they never see or correct the corrupted index. 
- `deduplicate_commitments` only groups commitment bytes; it does not re-validate `cell_indices`. [4](#0-3) 
- The `num_cells == 0` short-circuit doesn't apply (num_cells ≥ 1 here). [5](#0-4) 
- The binding-level "length" checks (`cell_indices_param.Length() != num_cells`, etc.) only check array counts, not per-element value fidelity. [6](#0-5) 
- The C bounds check itself (`cell_indices[i] >= CELLS_PER_EXT_BLOB`) is exactly the check that is bypassed, because it operates on the already-corrupted value handed to it by the Node.js binding — it cannot detect that the original wire value was out of range before the double-conversion mangled it.

### Title
Node.js binding silently truncates out-of-range `u64` cell indices via double-precision `Napi::Number`, causing divergent accept/reject verdicts vs. exact-`u64` bindings (e.g. Rust) - (File: bindings/node.js/src/kzg.cxx)

### Summary
`get_cell_index` in the Node.js addon converts cell indices through a JS `number` (IEEE‑754 double) using `static_cast<uint64_t>(number)`, which cannot represent values like `u64::MAX` and invokes undefined behavior that commonly resolves to an in-range value such as `0`. The Rust binding (and other bindings that pass `u64` directly) preserve the exact out-of-range value and get rejected by the shared bounds check `cell_indices[i] >= CELLS_PER_EXT_BLOB` in `verify_cell_kzg_proof_batch`, so the identical wire-encoded sidecar is accepted by Node.js-based nodes and rejected by exact-integer-based nodes.

### Finding Description
An attacker crafts a data-column sidecar whose `cell_indices` field contains `18446744073709551615` (`u64::MAX`) for one entry, alongside cell/proof bytes that are actually valid for column `0` (or whatever value the UB conversion resolves to on the victim's platform/toolchain). When a Node.js-based consensus client parses the sidecar and calls `verifyCellKzgProofBatch`, the index arrives at `get_cell_index` as a JS `number`; because `2^64‑1` isn't exactly representable, it is rounded to `2^64`, and `static_cast<uint64_t>(2^64)` is undefined behavior that in practice yields `0` (or some other in-range value depending on compiler/CPU) rather than the true value. That corrupted, in-range index then sails through the C bounds check at [1](#0-0)  and the batch verification proceeds and can return `ok = true`. A Rust node (or any binding passing the exact `u64`) receives the untouched `u64::MAX`, fails the same bounds check, and returns `C_KZG_BADARGS`, rejecting the sidecar outright. The two nodes reach different acceptance verdicts for byte-identical wire input, purely due to a binding-layer type-conversion defect, not any difference in the KZG math or in `blst`.

### Impact Explanation
The shared library's cryptographic verification (`verify_cell_kzg_proof_batch`) itself is not broken — but the Node.js binding's handling of the untrusted `cell_indices` input causes it to feed the C function a different (mangled) value than what was actually encoded on the wire and than what other bindings faithfully pass through. This is exactly the "same bytes verify on some nodes and fail on others" Critical category: any consensus client built on the Node.js `c-kzg-4844` addon (e.g., JS/TS Ethereum clients) can accept a data-column sidecar that spec-compliant clients using the Rust (or other exact-`u64`) binding reject, causing an availability/acceptance fork on that sidecar.

### Likelihood Explanation
The attacker needs no privilege beyond publishing a data-column sidecar with a single crafted `cell_indices` entry equal to (or above) `2^53`, ordinary values already outside JS's safe-integer range, with `u64::MAX` being the most extreme/clear-cut case. No cooperation from operators, no special build, and no dependency compromise is required. The divergence is fully repeatable: any Node.js binding build (default compiler settings on typical x86‑64/ARM64 platforms) exhibits the same UB conversion outcome deterministically for the same input, and any Rust-based node will consistently reject it.

### Recommendation
Change `get_cell_index` (and any other place converting untrusted 64-bit values from JS) to require and consume a `BigInt` (`Napi::BigInt` with lossless `Uint64Value`) instead of `Napi::Number`, and reject non-integer/out-of-range values explicitly before ever casting to `uint64_t`; do not rely on `static_cast<uint64_t>(double)` for values that can exceed `Number.MAX_SAFE_INTEGER`.

### Proof of Concept
1. In `bindings/node.js`, call `verifyCellKzgProofBatch(commitments, [18446744073709551615, ...], cells, proofs)` where the sidecar's other cells/proofs are valid for cell index `0`. Assert the JS call returns `true` (or does not throw `BADARGS`), demonstrating `get_cell_index` returning `0` instead of the true out-of-range value.
2. In `bindings/rust`, construct the equivalent `verify_cell_kzg_proof_batch_rust` call with `cell_indices = vec![u64::MAX, ...]` and identical commitment/cell/proof bytes. Assert it returns `Err(...)` corresponding to `C_KZG_BADARGS`, per the bounds check at `src/eip7594/eip7594.c:863`.
3. Compare: Node.js → accept, Rust → reject, for the same conceptual wire-encoded `cell_indices` value, proving the divergence.
