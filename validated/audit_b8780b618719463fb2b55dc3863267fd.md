### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, allowing a token scoped to one stack to read any stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` can be created scoped to a single `Stack` via its `belongs_to :stack, optional: true` association [1](#0-0) . `Api::BaseController` is supposed to enforce that scope for every request by restricting the visible stacks to `Stack.where(id: current_api_client.stack_id)` whenever the client has a `stack_id` [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to look the stack up directly from the unscoped `Stack` model, completely bypassing that restriction [3](#0-2) .

### Finding Description
The intended trust binding is: "stack(s) an `ApiClient` is authorized for" (`client.stack_id`, or all stacks if unscoped) == "stack(s) the request can actually read." `BaseController#stack` maintains this equality by calling `stacks.from_param!(...)`, where `stacks` filters by `current_api_client.stack_id?` [2](#0-1) .

`CCMenuController` redefines `stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This calls `Stack.from_param!` on the entire `Stack` table, not the scoped `stacks` helper. `require_permission :read, :stack` only checks that the `read:stack` string is present in `client.permissions` [5](#0-4) ; it never checks `client.stack_id`. Consequently a token created (e.g. via the CCMenu-URL flow, which mints a `read:stack` client [6](#0-5) ) meant to be presented publicly for exactly one project's CI badge can be replayed with a different `stack_id` in the URL to read *any* stack's CCMenu status — including stacks the token's owner never intended to expose (e.g., private/internal stacks), leaking build state, lock status, and last build label/URL for stacks the client is not authorized for.

The existing test suite even demonstrates the unscoped behavior implicitly: a request for a brand-new, unrelated stack ("foo/bar") that has no relationship to the authenticated client succeeds and renders data [7](#0-6) , confirming that `stack_id` scoping is never enforced in this controller.

### Impact Explanation
This breaks the "stack a token authorizes versus a stack it touches" binding explicitly called out as in-scope. Any holder of a `read:stack`-permissioned `ApiClient` token — even one legitimately scoped to a single, low-sensitivity stack — can enumerate and read status/build/lock information for every other stack in the Shipit instance, an unauthorized cross-stack read of stack state, matching the High-severity bucket "unauthenticated read of stack state, task streams or deploy output" (unauthenticated relative to the stacks it actually reads, since the token was never authorized for them).

### Likelihood Explanation
Likelihood is high: the CCMenu endpoint is specifically designed to be embedded/queried by third-party tools using a bare token in the query string [8](#0-7) , so such tokens are commonly shared outside the trusted operator boundary. Exploiting the bug only requires changing the `stack_id` path parameter to any other stack's identifier — no additional secret or privilege is needed.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that clients scoped to a specific `stack_id` cannot read data for other stacks.

### Proof of Concept
1. An operator creates (or the app auto-creates via `CCMenuUrlController`) an `ApiClient` with permission `read:stack`, intended to be scoped/used for `stack_id = "org/repo-a/production"`.
2. An attacker who obtains that token (it's designed to be embedded in a public CCMenu URL) issues:
   `GET /api/stacks/org/repo-b/production/ccmenu.xml?token=<token>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully [9](#0-8) , and `#stack` resolves `repo-b`'s stack directly from `Stack.from_param!`, bypassing any `client.stack_id` restriction [4](#0-3) .
4. The response renders `repo-b`'s CCMenu XML (name, activity, lastBuildStatus, lock state, etc.), even though the token was never authorized for that stack — as validated by the existing test which fetches an entirely unrelated stack successfully with the same authenticated client [7](#0-6) .
