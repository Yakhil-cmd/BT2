### Title
Unfiltered `machine.environment` from a Review Stack's `shipit.yml` reaches `PTY.spawn` unsanitized, allowing `PYTHONPATH` injection - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim, with no whitelist check, and `TaskCommands#env` merges it directly into the hash used by `Command#start` to call `PTY.spawn`. Because Review Stacks are, by design, tied to a pull request's branch and its `shipit.yml`, whoever controls that branch's `shipit.yml` controls this unfiltered environment, unlike every other env-injection path in Shipit (deploy `env`, task `env`) which is filtered through `EnvironmentVariables#permit`.

### Finding Description
The broken binding: the codebase enforces `env_supplied_by_untrusted_party == permit(env, whitelist)` for every other user-controlled environment injection point, but for `machine.environment` it holds `env_supplied_by_shipit_yml == env_supplied_by_shipit_yml` (i.e., no filtering at all).

- `DeploySpec#machine_env` at [1](#0-0)  returns the `machine.environment` config verbatim with no whitelist, in contrast to `filter_deploy_envs`/`filter_rollback_envs` [2](#0-1)  and `TaskDefinition#filter_envs` [3](#0-2) , both of which route through `EnvironmentVariables#permit` and raise `NotPermitted` for any key not in an explicit `variables` whitelist [4](#0-3) .
- `TaskCommands#env` merges `deploy_spec.machine_env` directly into the environment hash passed to every `Command` for install/deploy/task steps: [5](#0-4) .
- `Command#start` merges `@env` into `unbundled_env` and calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5) , so whatever key/value is in `machine.environment` is passed to the spawned child process unmodified (aside from `to_s` coercion, per `Command#initialize` at [7](#0-6) ).
- Review Stacks are explicitly a feature to dynamically deploy a pull request's branch: `docs/review_stacks.md` describes "A Review Stack is a dynamically managed stack whose lifecycle is tied to a Github Pull Request" and Shipit checks out that PR's branch, and `ReviewStackAdapter#stack_attributes` sets `branch: params.pull_request.head.ref` from the webhook payload on PR creation [8](#0-7) . `DeploySpec::FileSystem` reads `shipit.yml` from the checked-out working tree of that branch, then feeds `discover_machine_env.merge(machine_env)` into the cached spec [9](#0-8) .
- Existing guards (`EnvironmentVariables#permit`, deploy/task variable whitelists demonstrated in `test/controllers/api/deploys_controller_test.rb` and `test/controllers/api/tasks_controller_test.rb`) only protect the `env` parameter supplied via the API/UI at trigger time — they do not apply to `machine.environment` sourced from `shipit.yml`, which is exactly the branch content a review-stack PR author controls.

Exploit flow: attacker opens/updates a PR whose branch's `shipit.yml` contains:
```yml
machine:
  environment:
    PYTHONPATH: "."
```
When the review stack provisions or any task/deploy runs, `TaskCommands#env` merges `PYTHONPATH=.` into the `Command` env, which reaches `PTY.spawn` unmodified. Any deploy/task step that invokes `python` (directly or via a discovered Python toolchain step) will then prepend the checked-out working directory to its module search path, allowing an attacker-planted module in the repository (e.g., a file matching a stdlib or commonly-imported module name) to be imported by the spawned interpreter.

One caveat I could not fully verify from the available index: whether Shipit's git fetch/clone for review stacks (`StackCommands#fetch`/`#git_clone`, using `@stack.repo_git_url` and `@stack.branch`) actually resolves a true cross-repository fork's head branch, or only branches pushed directly to the tracked/base repository. I found no `refs/pull/<n>/head`-style fetch logic in the reachable code, so this exploit's applicability to genuine "external fork" PRs (versus PRs from a branch on the same repository) could not be conclusively confirmed with the tools available; the unfiltered-`machine_env`-into-`PTY.spawn` primitive itself, however, is confirmed directly in code.

### Impact Explanation
If exploitable via any branch whose `shipit.yml` is attacker-controlled (fork or same-repo branch, depending on provisioning behavior configuration — "Allow All" requires no label), the attacker achieves arbitrary code execution in the context of the deploy host process for that stack/repository, matching the Critical RCE class (arbitrary command execution via `Command`/`PTY.spawn`). Blast radius is scoped to the repository/stack whose review stack is provisioned, but is repeatable per PR and per task/deploy run, and the deploy host is shared infrastructure, so compromise there can affect other tenants' credentials and secrets (`GITHUB_TOKEN`, deploy secrets) present on that host.

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled with provisioning behavior "Allow All" (or the attacker's label permission satisfies "Allow With Label"/"Prevent With Label"), documented in `docs/review_stacks.md`. Attacker cost is low — only requires the ability to include a `shipit.yml` on the branch that becomes the review stack's branch. The unresolved question is whether this branch can be a genuine external fork's branch or must be pushed into the tracked repository itself, which materially changes whether an "unprivileged" (no write access) attacker can reach it.

### Recommendation
Apply the same whitelist-based sanitization used for deploy/task envs to `machine.environment`: require repository maintainers to explicitly declare permitted machine-environment variable names (similar to `deploy.variables`/`rollback.variables`), and route `DeploySpec#machine_env` through `EnvironmentVariables#permit` against that maintainer-controlled list before merging into `TaskCommands#env`. At minimum, deny well-known dangerous variable names (`PYTHONPATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `RUBYOPT`, etc.) from `machine.environment` regardless of source, and prevent `shipit.yml`-declared `machine.environment` from being sourced from any PR/review-stack branch without maintainer review/approval.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (conceptual addition)
test "#env passes shipit.yml machine_env PYTHONPATH verbatim to Command/PTY.spawn" do
  deploy_spec = stub(machine_env: { 'PYTHONPATH' => '.' }, directory: nil)
  task_commands = TaskCommands.new(@task)
  task_commands.stubs(:deploy_spec).returns(deploy_spec)

  assert_equal '.', task_commands.env['PYTHONPATH']

  command = Command.new('python -c "import pwn"', env: task_commands.env, chdir: '.')
  assert_equal '.', command.unbundled_env['PYTHONPATH']
  # Demonstrates the value reaching the hash passed to PTY.spawn without any
  # EnvironmentVariables#permit filtering, unlike deploy/task `env` params.
end
```
This proves `machine_env` sourced from `shipit.yml` (attacker-controlled on the review-stack branch) reaches the `Command#unbundled_env` hash passed to `PTY.spawn` with no sanitization, unlike deploy/task envs which raise `EnvironmentVariables::NotPermitted` for non-whitelisted keys.
