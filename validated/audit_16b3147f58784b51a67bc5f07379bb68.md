### Title
Webhook signature verification is keyed on `repository.owner.login`, but handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery when any configured GitHub org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / secret to verify a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, then calls `GitHubApp#verify_webhook_signature`. If that particular org's `webhook_secret` happens to be blank (an explicitly supported, documented configuration), the verifier unconditionally returns `true`. Every webhook handler (`PushHandler`, the `status` handler, etc.), however, resolves which `Repository`/`Stack` to mutate using a *different* payload field, `repository.full_name`, which the attacker can set independently of `repository.owner.login`.

resolves the app config via: [2](#0-1) 

and the actual bypass condition lives here — if the resolved org's secret is blank, no HMAC check is performed at all: [3](#0-2) 

`webhook_secret` is a per-organization, optional field in multi-org configurations, as shown by the fixture where `OrgTwo` has `webhook_secret: # nil`: [4](#0-3) 

Meanwhile, the field that actually drives which database records get written is unrelated to `repository.owner.login`: [5](#0-4) 

and resolution to a concrete `Repository`/`Stack` uses only `owner/name` parsed out of `full_name`: [6](#0-5) 

So the equality the engine implicitly assumes — `organization that authenticated == owner of the repository that is written` — does not hold. An attacker can set `repository.owner.login` to the name of any configured org whose `webhook_secret` is blank (satisfying `verify_signature` trivially, regardless of the `X-Hub-Signature` header value or absence), while setting `repository.full_name` to `victim-org/victim-repo`, a completely different, secret-protected organization's tracked repository. The `PushHandler` will then enqueue a `GithubSyncJob` with an attacker-chosen `after` SHA for that victim stack: [7](#0-6) 

and status-type webhooks can inject arbitrary commit statuses for the victim repository's SHAs, as exercised in the test suite (illustrating that status writes are keyed by SHA/`repository` params, not by the org used to authenticate): [8](#0-7) 

### Impact Explanation
Because `GithubSyncJob` drives commit ingestion and, when `continuous_deployment` is enabled on the target stack, ultimately feeds automatic deploys, and because forged `status` events can mark attacker-chosen commits as passing required CI checks used to gate merges/deploys, this crosses the "unauthorized deploy" bar in a stack the attacker has no legitimate relationship to — reachable purely by an unauthenticated network client with no Shipit session, API token, or GitHub credentials, as long as the deployment has at least one configured GitHub org (or the default single-org config) with a blank `webhook_secret`, which the docs present as an optional, supported setting.

### Likelihood Explanation
This requires only that one configured GitHub App entry in `secrets.github` (single-org or one entry in a multi-org map) has no `webhook_secret` set — which the setup docs describe as optional ("If you've set a webhook secret during the App creation, you should copy it here"), so real-world deployments plausibly satisfy this precondition, especially single-org deployments that never set a webhook secret at all. No credentials, sessions, or write access are needed to exploit it.

### Recommendation
Bind the field used to select the verifying secret to the same field used to resolve the acted-upon repository (i.e., derive both from `repository.full_name`, not `repository.owner.login`/`organization.login` independently), and never let `verify_webhook_signature` silently succeed when `webhook_secret` is blank for events that will mutate cross-organization state — instead require an explicit signature or reject requests naming other organizations' repositories when the resolved org's secret is unset.

### Proof of Concept
1. Deploy Shipit with a multi-org `secrets.github` config where `OrgWithoutSecret` has no `webhook_secret` and `VictimOrg` has a real secret and a tracked stack for `VictimOrg/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "VictimOrg/victim-repo" }
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `verify_signature` resolves `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler` resolves the target stack via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and enqueues `GithubSyncJob` with the attacker's `after` SHA against a repository the attacker never authenticated for.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

          stacks
