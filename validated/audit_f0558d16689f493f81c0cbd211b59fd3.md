### Title
CCMenu API endpoint does not enforce per-stack token scope, breaking the "stack a token authorizes" vs. "stack it touches" binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` authenticates a request using an `ApiClient` token and checks only the generic `read:stack` permission, but the `stack` resolution method it defines bypasses the stack-scoping mechanism (`current_api_client.stack_id`) that every other API controller relies on. As a result, a token that was created/scoped for one stack can be used to read CCMenu build/deploy status for any other stack in the installation, exactly mirroring the reported bug class where a state binding (here, "the stack this token is allowed to touch") silently diverges from the value actually used at execution time.

### Finding Description
Every other resource controller inheriting from `Api::BaseController` resolves the target stack through the scoped helper: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set — this is the binding: **stack the token authorizes == stack_id column on the `ApiClient` record**. `StacksController` and other resource controllers use this `stacks`/`stack` helper, and tests confirm the intended behavior ("an api client scoped to a stack will only see that one stack"): [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to resolve the target directly from the request parameter, never consulting `current_api_client.stack_id`: [3](#0-2) 

The only authorization check performed is `require_permission :read, :stack`, which merely verifies that the string `"read:stack"` is present in `current_api_client.permissions` — a check that is identical regardless of which stack is being requested: [4](#0-3) 

Compounding this, the token normally handed out for this endpoint (`CCMenuUrlController#client`) is created without any `stack_id` at all, and is memoized per user/name rather than per stack, so the same token is reused across every stack a user requests a CCMenu URL for: [5](#0-4) 

So the equality that should hold — `token.stack_id == stack_id_used_in(CCMenuController#show)` — is never enforced. Before the "attack": a leaked/shared CCMenu token for Stack A is presumed by the operator to only reveal Stack A's build status. After: the same token, submitted with a different `stack_id` route param, reveals the CCMenu status (build state, last deploy) of Stack B, C, … — any stack in the installation — because `CCMenuController#stack` never checks `current_api_client.stack_id`.

### Impact Explanation
This breaks the "stack a token authorizes versus a stack it touches" binding explicitly called out as in-scope. CCMenu tokens are designed to be embedded in third-party CI dashboard tools and URLs (this is their whole purpose — machine-readable status badges), making them the token type most likely to be pasted into semi-public locations. An unprivileged holder of any single valid CCMenu (or generically `read:stack`-scoped) token can enumerate and read deploy/build status for every stack managed by the Shipit installation, not just the one the token was meant for. This matches the defined High-severity impact category: "unauthenticated read of stack state, task streams or deploy output" via escalation past the intended per-token authorization scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues scoped `read:stack` tokens (the CCMenu flow is the canonical, documented way this happens): no privileged action beyond possessing one legitimately-scoped, unprivileged token is required, and exploitation is a single parameter change (`stack_id`) on an otherwise normal, already-authenticated request.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the same scoped `stacks` collection used elsewhere (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a token restricted to `stack_id` X cannot resolve stack Y. Additionally, `CCMenuUrlController#client` should create/find an `ApiClient` scoped to the specific stack (`stack: stack`) rather than a single shared, unscoped client per user, so newly issued CCMenu tokens are properly bound to a single stack from creation.

### Proof of Concept
1. Admin/user visits Stack A's settings page, which calls `CCMenuUrlController#fetch` and receives a CCMenu URL containing `token=<T>` (an `ApiClient` with `permissions: ["read:stack"]`, no `stack_id`).
2. That URL/token `T` is pasted into a CI dashboard or otherwise becomes known to a third party.
3. The third party issues `GET /api/stacks/*any-other-stack-id/ccmenu?token=T`.
4. `Api::CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`), `require_permission :read, :stack` passes because `T` has the generic `"read:stack"` permission, and `stack` resolves the arbitrary `stack_id` from the URL (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) — returning build/deploy status for a stack the token was never meant to access.
