### Title
Flag injection via unsanitized linked-branch name in `Client.CheckoutBranch` used by `gh issue develop --checkout` - (File: git/client.go)

### Summary
`gc.CheckoutBranch` builds the git argv as `[]string{"checkout", branch}` with the attacker-influenced branch name as the sole positional argument and no leading-dash guard, unlike the equivalent code path in `pkg/cmd/pr/checkout/checkout.go` which explicitly rejects `strings.HasPrefix(pr.HeadRefName, "-")`. If a branch name obtained from `api.CreateLinkedBranch`/`api.ListLinkedBranches` (or a matching pre-existing local branch of that name) starts with `-`, it can be parsed by `git checkout` as an option instead of a branch name.

### Finding Description
`checkoutBranch` in `pkg/cmd/issue/develop/develop.go:405-417` calls `gc.CheckoutBranch(ctx.Background(), checkoutBranch)` when `gc.HasLocalBranch` returns true for that name, otherwise it falls back to `gc.CheckoutNewBranch`. `Client.CheckoutBranch` (git/client.go:666-677) constructs `args := []string{"checkout", branch}` and executes it via `c.Command`/`cmd.Output()` with no validation that `branch` doesn't begin with `-`. [1](#0-0) [2](#0-1) 

By contrast, `pr checkout` explicitly guards against this exact class of injection: [3](#0-2) 

Because `branch` is passed as `argv[]` (not a shell string), this is not remote code execution but *argument/flag injection* into `git checkout` — e.g. a branch name of `--orphan` or similarly crafted values would be interpreted as options by git rather than as a ref name.

Note: `Client.CheckoutNewBranch` (git/client.go:679-691) is not vulnerable in the same way, because the branch value there is passed as the option-argument to `-b`, which git's option parser consumes literally rather than reparsing as a flag; the `HasPrefix` bypass would need `HasLocalBranch(ctx, checkoutBranch)` to be true, meaning a local branch literally named with a leading dash must already exist for `CheckoutBranch` to be reached in this particular caller.

### Impact Explanation
This is a genuine asymmetry versus the guarded `pr checkout` path and matches a "command/argument injection into git" class finding. However, the exploitability of this specific call site is constrained: `checkoutBranch` invokes `gc.CheckoutBranch` only when `gc.HasLocalBranch(ctx, checkoutBranch)` returns true, i.e., only if the victim's local repository already contains a local branch literally named with a leading dash. In the normal `gh issue develop --checkout` flow (fresh checkout of a newly-fetched linked branch), that condition is false and `CheckoutNewBranch` is used instead, which is not vulnerable to this exact injection. So while the missing guard in `Client.CheckoutBranch` is a real code-hygiene/defense-in-depth gap, the described exploit chain from `gh issue develop --checkout` alone does not reliably reach the vulnerable branch without an additional precondition (pre-existing local branch with a dash-prefixed name) that is not established by the attacker-controlled inputs alone.

### Likelihood Explanation
Low-to-moderate. It requires either (a) the victim already having a local branch whose literal name starts with `-` matching the linked branch name (uncommon), or (b) some other code path invoking `Client.CheckoutBranch` directly with fully attacker-controlled, unvalidated branch text (found also referenced in `pr close` and `pr merge`, not analyzed here in depth). The `gh issue develop --checkout` path as described in the question does not, by itself, guarantee reaching the vulnerable line under normal preconditions.

### Recommendation
Add the same leading-dash validation used in `pkg/cmd/pr/checkout/checkout.go` (`strings.HasPrefix(branch, "-")`) inside `Client.CheckoutBranch` (and ideally centrally in `git/client.go` for all branch-name-consuming methods), or use `--` separator: `args := []string{"checkout", "--", branch}` to prevent git from interpreting the value as an option regardless of caller.
