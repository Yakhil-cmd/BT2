Confirmed vulnerability. The `here_come_the_walrus` `ApiClient` fixture is scoped to the `shipit` stack via `stack_id`, meaning it should only ever be able to touch that one stack [1](#0-0) . The scoping is enforced generically in `Api::BaseController#stack`, which filters through `stacks` (itself filtered by `current_api_client.stack_id`) before calling `from_param!` [2](#0-1) . `Api::CCMenuController` overrides `stack` and calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely bypassing that authorization scoping while still passing the generic `require_permission :read, :stack` check [3](#0-2) .

### Title
Stack-scoped ApiClient token can read CCMenu build status of any stack, bypassing token stack scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` reimplements stack lookup using the global `Stack.from_param!(params[:stack_id])` instead of the scope-aware `stacks.from_param!` used by every other API controller inheriting from `Api::BaseController`. This breaks the equality that should hold: `token.authorized_stack == stack_read_by_token`. Any client holding a token scoped to stack A can pass `stack_id` for stack B and read B's CCMenu XML status.

### Finding Description
`Api::BaseController` defines the generic, scope-respecting accessor: [2](#0-1) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set — this is exactly how stack-scoped tokens (e.g. the tokens minted by `CCMenuUrlController#client`, which creates a `read:stack`-only `ApiClient` bound to one specific stack) are meant to be constrained [4](#0-3) .

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [5](#0-4) 
`require_permission :read, :stack` only checks that the token generically has the `read:stack` permission string in its `permissions` array — it does not check which stack the permission applies to [6](#0-5) . Combined with the `stack` override, any token with `read:stack` permission — even one explicitly minted and distributed for a single stack via `CCMenuUrlController#fetch` — can be replayed with a different `stack_id` in the URL to read another stack's deploy/build status.

### Impact Explanation
This is an unauthorized cross-stack read of stack state (deploy/build status, lock status, last build label/time), matching the High-severity class "unauthenticated/unauthorized read of stack state... task streams or deploy output." A CCMenu token is specifically designed to be embedded in third-party CI-status-monitor tools/URLs and is scoped to one stack precisely because it may leak or be shared more broadly than a full API token; this bypass defeats that scoping guarantee for every such token, and for any other `ApiClient` restricted to a single stack.

### Likelihood Explanation
Trivial to exploit: an attacker who obtains any valid `read:stack`-permissioned token (including a legitimately shared CCMenu URL for stack A) can query `/api/stacks/:any_other_stack_id/ccmenu` with that token and receive the target stack's status, requiring only knowledge/guessing of another stack's `stack_id` (owner/name/environment), which is often predictable or discoverable.

### Recommendation
Have `Api::CCMenuController` reuse the inherited, scope-aware `stack` method from `Api::BaseController` (i.e. remove the local override and rely on `stacks.from_param!(params[:stack_id])`), so the `current_api_client.stack_id` restriction applies uniformly.

### Proof of Concept
1. As an authenticated user, request a CCMenu URL for stack `shipit` via `CCMenuUrlController#fetch`; this mints a `read:stack`-only `ApiClient` with `stack_id` set to `shipit`'s id and returns a token-bearing URL [7](#0-6) .
2. Using that token (via Basic Auth or the `token` query param, both accepted by `CCMenuController#authenticate_api_client` [8](#0-7) ), send `GET /api/stacks/some-other-owner/other-repo/production/ccmenu` for an unrelated stack.
3. Observe the response returns HTTP 200 with that other stack's build status XML, even though the token's `stack_id` only authorizes the original `shipit` stack — confirming the scope bypass.
