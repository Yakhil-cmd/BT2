This confirms the full attack chain. The env override order is unrestricted: `TaskCommands#env` merges `deploy_spec.machine_env` (raw config value, unfiltered) at [1](#0-0) , sourced from `DeploySpec#machine_env` which returns `config('machine', 'environment') || {}` with no allow-list, unlike `deploy_variables` which are filtered via `filter_deploy_envs`/`EnvironmentVariables#permit` [2](#0-1) . `Command#unbundled_env` then does `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)`, so any key in `@env` (including `GIT_PROXY_COMMAND`) overrides `BASE_ENV`/`PATH` and is passed directly into `PTY.spawn` [3](#0-2) [4](#0-3) . `ReviewStack` provides no filtering of `env` beyond adding label-derived vars [5](#0-4) , and `provisioning_behavior` (`allow_all`/`allow_with_label`/`prevent_with_label`) on `Repository` only gates whether/when a review stack is provisioned for a fork PR — it does not filter or sanitize the `shipit.yml` content of the fork branch once the stack exists [6](#0-5) .

Given this is a genuine code-path finding (no filtering exists between the fork-controlled `machine.environment` config and the environment passed to `PTY.spawn`), I'll produce the full report per the audit format.

### Title
Unfiltered `machine.environment` in fork's `shipit.yml` allows `GIT_PROXY_COMMAND` injection into `deploy.override` command execution - (File: app/models/shipit/deploy_spec.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`DeploySpec#machine_env` returns the `machine.environment` map from the review-stack branch's `shipit.yml` verbatim, with no key allow-list, unlike `deploy.variables` which are filtered through `EnvironmentVariables#permit`. `TaskCommands#env` merges this raw map into the environment used for every deploy step, and `Command#unbundled_env` lets `@env` override `BASE_ENV`/`PATH` unconditionally before invoking `PTY.spawn`, so a fork PR author can set `GIT_PROXY_COMMAND` (or any other env var) that is inherited by the `deploy.override` git/shell invocations on the Shipit host.

### Finding Description
The broken binding: the invariant should be `deploy_env(deploy.override) ∩ FORK_CONTROLLED_KEYS = ∅` for security-sensitive keys like `GIT_PROXY_COMMAND`, but in practice `deploy_env(deploy.override) ⊇ config('machine','environment')` verbatim, i.e., every key the fork author writes in `machine.environment` in their `shipit.yml` is passed through unfiltered.

Path: `DeploySpec#machine_env` reads `config('machine', 'environment') || {}` with no filtering [2](#0-1) . This `config` is loaded from the review stack's own branch content via `DeploySpec::FileSystem#load_config`/`cacheable_config`, which explicitly merges `discover_machine_env.merge(machine_env)` under `'machine' => {'environment' => ...}` [7](#0-6) . `TaskCommands#env` merges `deploy_spec.machine_env` into the full env hash used to build every `Command`, including the `deploy.override` steps built in `Shipit::DeployCommands#perform`-equivalent flows [1](#0-0) . Unlike `deploy_variables`, which pass through `filter_deploy_envs`/`EnvironmentVariables#permit` before reaching the task env [8](#0-7) , `machine_env` has no such permit-list step anywhere in this chain. Finally, `Command#unbundled_env` does `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` — `@env` (containing the attacker's `GIT_PROXY_COMMAND`) is merged last and wins over `BASE_ENV`, then is passed directly as the first argument to `PTY.spawn` in `Command#start` [3](#0-2) [9](#0-8) .

`ReviewStack#env` only adds PR-label-derived boolean flags on top of `Stack#env`; it performs no sanitization of `machine_env` content [5](#0-4) . `Repository#provisioning_behavior` (`allow_all`, `allow_with_label`, `prevent_with_label`) only controls whether a `ReviewStack` gets provisioned/deployed for a given fork PR — under `allow_with_label`, once a maintainer or the PR author (depending on label permissions elsewhere) attaches the deploy-enabling label, the stack still loads and executes the fork branch's own `shipit.yml`, including its `machine.environment` and `deploy.override` entries, with no additional content sanitization at that stage [6](#0-5) .

No existing guard (`EnvironmentVariables#permit`, `filter_deploy_envs`, `Repository` validations, `provisioning_behavior`) filters `machine.environment` keys, so the divergence between the intended invariant and actual behavior holds: an attacker who can get their fork branch's `shipit.yml` loaded as the review stack's deploy spec can set arbitrary environment variables — including `GIT_PROXY_COMMAND` — that are inherited by every command Shipit spawns for that stack, including `deploy.override` steps that invoke `git`.

### Impact Explanation
`GIT_PROXY_COMMAND` (or `GIT_SSH_COMMAND`, or arbitrary other env vars) reaching `PTY.spawn` for `deploy.override`/`deploy.pre`/`deploy.post`/`rollback` steps lets a fork PR author cause the Shipit deploy host to execute an attacker-named command whenever `git` opens a transport connection during that stack's task (clone/fetch/checkout use `git` too, per `TaskCommands#clone`/`checkout` [10](#0-9) ). This is arbitrary command execution on the Shipit host under the Shipit process's privileges, matching the Critical/RCE class. Blast radius is scoped to tasks run for that specific review stack (the env hash is stack/task-specific, built fresh in `TaskCommands#env`), but any secrets or credentials accessible to the Shipit worker process during that task execution (e.g., `GITHUB_TOKEN` used for git operations, other environment secrets) are exposed to the attacker-controlled command, and the RCE itself is host-wide once triggered.

### Likelihood Explanation
Preconditions: the repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_with_label` (or `allow_all`), a fork PR must be opened, and (for `allow_with_label`) the deploy-enabling label must be applied to the PR — this is a normal, low-cost workflow that many open-source-style Shipit setups explicitly support to let contributors get review stacks. The attacker needs no Shipit credentials, GitHub App keys, or maintainer role beyond what the `allow_with_label` behavior already grants to labeled fork PRs by design. Setting a `machine.environment` entry in one's own fork's `shipit.yml` costs nothing and is fully repeatable per PR/stack.

### Recommendation
Filter `machine_env`/`config('machine','environment')` through an explicit allow-list (similar to `EnvironmentVariables#permit` used for `deploy_variables`/`rollback_variables`), rejecting or stripping any key that maps to a git/shell transport-control variable (`GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_ASKPASS`, `LD_PRELOAD`, etc.) and, more generally, deny-by-default any key not explicitly declared safe, especially for `ReviewStack`s where the spec file is attacker-controlled. Alternatively, load review-stack `machine.environment` only from a trusted base branch config rather than the fork branch, or sandbox review-stack `deploy`/`rollback` command execution so environment variables cannot influence subprocess/transport behavior.
