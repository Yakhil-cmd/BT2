### Title
Stack-scoped API token can read any stack's build status via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a specific stack (`current_api_client.stack_id`) can only resolve stacks through the `stacks`/`stack` helpers, which filter by `Stack.where(id: current_api_client.stack_id)`. `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, looking the stack up directly from the URL parameter instead of from the authorized/scoped collection.

### Finding Description
`BaseController` defines the trust binding that should hold for every API endpoint: a token whose `stack_id` is set may only touch that one stack. [1](#0-0) 
`Api::CCMenuController`, however, redefines `stack` to resolve directly from `params[:stack_id]` via `Stack.from_param!`, never going through the `stacks` scope that enforces `current_api_client.stack_id`: [2](#0-1) 
The controller's `require_permission :read, :stack` only checks that `"read:stack"` is present in `current_api_client.permissions` via `ApiClient#check_permissions!`, which is agnostic of which stack the client is scoped to: [3](#0-2) 
This exactly mirrors the reported bug class: the code compares/authorizes against the wrong side of an equality. The binding that should hold is `current_api_client.stack_id == accessed_stack.id` (when `stack_id` is present), but `CCMenuController#stack` never evaluates it — it only uses the caller-supplied `stack_id` path parameter, so any stack in the system is reachable regardless of the token's actual scope. Fixture data confirms scoped tokens are a real, intended feature: `here_come_the_walrus` is created with `stack: shipit` and permission `read:stack` only, intended to see just that one stack, as verified in the `api/stacks_controller` tests (`"an api client scoped to a stack will only see that one stack"`). [4](#0-3) 

### Impact Explanation
A holder of a legitimately-issued, stack-scoped `ApiClient` token (e.g. distributed to a CI tool or third party for one project) can use that same token against `GET /api/ccmenu/:stack_id` for any other stack's identifier and obtain that stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock status), i.e. cross-stack unauthorized read of deploy/task state that the token was never granted access to. This matches the in-scope High-severity class: "unauthenticated read of stack state, task streams or deploy output" — here achieved by a token whose read scope is authorized for stack A but is used to read stack B, breaking the deployment-trust binding between the token's granted stack and the stack actually touched.

### Likelihood Explanation
Any holder of a valid `read:stack`-permission `ApiClient` token — even one deliberately scoped to a single, low-sensitivity stack (this is the exact purpose of the `stack_id` column and the `stacks` scoping helper) — can trivially exploit this by supplying a different `stack_id` in the URL. No special privileges, secrets, or race conditions are required beyond possessing one valid, low-privilege token, which is the intended level of access for many CCMenu/CI integrations.

### Recommendation
In `Api::CCMenuController`, resolve `stack` through the base controller's authorized `stacks` scope instead of `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped token can only ever resolve to the stack it was actually issued for.

### Proof of Concept
1. An operator creates a stack-scoped `ApiClient` for `org/project-a` with permission `read:stack` (mirrors fixture `here_come_the_walrus`, `stack: shipit`).
2. The token is handed to a CI/build-monitor tool that is only supposed to see `org/project-a`.
3. The token holder (or anything reusing the token) sends:
   `GET /api/ccmenu/org/project-b/production` (any other stack's `to_param`) with `Authorization: Basic base64(token)` or `?token=<token>`.
4. `Api::CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has `read:stack` in its permission list.
5. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `stacks` scope), returning `org/project-b` even though the token's `stack_id` is `project-a`'s id.
6. The response renders `org/project-b`'s build status, name, lock state and web URL — data the token was never authorized to see.
