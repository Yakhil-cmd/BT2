## Title
Missing `write` mutex when executing AA triggers during stability advancement in `determineIfStableInLaterUnitsAndUpdateStableMcFlag()` - (File: `main_chain.js`)

### Summary
`writer.saveJoint()` treats `objValidationState.bUnderWriteLock === true` as a promise that the caller already holds the `"write"` mutex, and skips acquiring it itself: [1](#0-0) 
This optimization is safe only if every call path that sets `bUnderWriteLock = true` is actually nested inside a held `"write"` lock. AA-trigger execution (`aa_composer.handleTrigger` → `validateAndSaveUnit`) always sets this flag: [2](#0-1) 

That flag is correctly justified when `handleAATriggers()` is invoked from inside `writer.saveJoint()` itself, because the `"write"` lock's `unlock()` is not called until after `handleAATriggers()` returns: [3](#0-2) 

However, there is a second call path to `stabilizeMci()` → `handleAATriggers()` that never takes the `"write"` lock: `determineIfStableInLaterUnitsAndUpdateStableMcFlag()` only acquires the `"handleJoint"` lock before calling `stabilizeMci()` in a loop: [4](#0-3) 
and `stabilizeMci()` itself commits/releases its own connection and then calls `aa_composer.handleAATriggers()` with no `"write"` lock held anywhere in the chain: [5](#0-4) 

`handleAATriggers()` only takes the unrelated `['aa_triggers']` lock: [6](#0-5) 

so when this path eventually reaches `writer.saveJoint(objJoint, objAAValidationState, ...)` with `bUnderWriteLock = true`, the function skips acquiring `"write"` entirely, exactly as the Linux `cpuset_attach()` proceeded on the assumption that `cpus_read_lock()` was already held by the `cgroup_procs_write_start()` path, while the `cgroup_attach_task_all()` path reached the same code without that lock.

### Finding Description
`ocore`'s write path is serialized system-wide by the `"write"` mutex so that concurrent unit/AA-response writes cannot race on the same in-memory caches (`storage.assocStableUnits`, `storage.assocUnstableUnits`, etc.) and on the paired SQL + RocksDB batch commit. `writer.saveJoint()`'s locking logic is a single boolean gate (`bUnderWriteLock`) rather than a real re-entrant/held-lock check, so it silently trusts the caller's claim.

`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` is reached from unit validation when a newly received unit's parents retroactively become stable ("stable in parents") — this is triggered purely by processing an ordinarily attacker-reachable posted unit through `validation.validate()`/`handleJoint()`. That function takes only the `"handleJoint"` lock, then loops calling `stabilizeMci(mci)` for each newly-stabilized MCI. `stabilizeMci()` marks the MCI stable, commits and releases its connection, and — with no lock held at all — invokes `aa_composer.handleAATriggers()`, which executes AA triggers and ultimately calls `writer.saveJoint()` with `bUnderWriteLock = true`. Because of that flag, `saveJoint()` never takes the `"write"` mutex, so this AA-triggered save can run fully concurrently with any other in-flight `saveJoint()` call from the normal `handleJoint()`/`composer.js` paths that *do* hold `"write"`.

### Impact Explanation
Two `saveJoint()` executions running concurrently without a shared `"write"` lock can interleave RocksDB batch writes and SQL commits, and can read/mutate the same shared caches (`storage.assocStableUnits`, `assocUnstableUnits`, `assocBestChildren`) out of order. This breaks the invariant the mutex exists to guarantee and can lead to node disagreement on unit/AA state validity or stability, corrupted cache state causing incorrect balance/asset accounting in later validations, or crashes (`throw Error` guards elsewhere in `writer.js` assume single-writer semantics). This matches "node disagreement on validity or stability" / potential AA fund accounting corruption.

### Likelihood Explanation
This is reachable purely by an unprivileged unit poster: any peer or the node's own network processing that causes a "stable in parents" situation (a common, non-adversarial occurrence when catching up or processing normal DAG growth) drives execution through `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`. No malicious peer/hub behavior is required — it is a normal consequence of unit validation timing, so the race window is regularly reachable under ordinary network conditions, especially the busier the node (more concurrent unit submissions/AA triggers).

### Recommendation
Acquire the `"write"` mutex explicitly in `main_chain.js`'s `stabilizeMci()`/`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` path before calling `aa_composer.handleAATriggers()`, or pass a real lock handle through so `writer.saveJoint()` can verify (not just trust) that the `"write"` lock is held, mirroring the kernel fix that added the missing `cpus_read_lock()` before the shared code path.

### Proof of Concept
1. Node processes a normal unit whose parents become stable ("stable in parents") during `validation.validate()`/`handleJoint()`, invoking `determineIfStableInLaterUnitsAndUpdateStableMcFlag()` (`main_chain.js:1192`) under only the `"handleJoint"` lock.
2. This calls `stabilizeMci(mci)` (`main_chain.js:1263`), which commits/releases its connection and calls `aa_composer.handleAATriggers()` with no `"write"` lock held.
3. `handleAATriggers()` → `handlePrimaryAATrigger()` → `handleTrigger()` → `validateAndSaveUnit()` calls `writer.saveJoint(objJoint, objAAValidationState, ...)` with `objAAValidationState.bUnderWriteLock = true` (`aa_composer.js:1826`).
4. Concurrently, a second unit arrives and is processed via `network.js` `handleJoint()` → `writer.saveJoint()` without `bUnderWriteLock`, which legitimately acquires `"write"` (`writer.js:34`).
5. Because step 3's save never acquired `"write"`, both saves run concurrently against the shared in-memory caches and interleaved DB/kvstore commits, violating the single-writer invariant the mutex is meant to enforce.
