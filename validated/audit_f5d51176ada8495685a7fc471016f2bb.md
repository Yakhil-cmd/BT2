### Title
Unbounded growth of `storage.assocUnstableMessages` inflates AA `data_feed()` lookups and can stall AA trigger processing - (File: `data_feeds.js`, `storage.js`)

### Summary
The `readDataFeedValue()` and `dataFeedExists()` functions used by the AA formula `data_feed[[...]]`/`in_data_feed[[...]]` operators iterate over the entire global in‑memory map `storage.assocUnstableMessages` whenever an AA queries an unstable data feed [1](#0-0) [2](#0-1) . This map accumulates one array entry per unit for every unstable `data_feed`/`definition`/`system_vote`/`system_vote_count` message posted anywhere in the DAG, and entries are only removed when the unit's MCI stabilizes [3](#0-2) [4](#0-3) . This is directly analogous to the OpenQ bug: an unprivileged actor can cheaply keep appending to an unbounded array that is later fully iterated on a hot, gas/time‑sensitive code path.

### Finding Description
Any unprivileged unit poster can post a standalone `data_feed` message (subject only to light per‑message length limits, not a limit on the number of such units) [5](#0-4) , and any unprivileged trigger sender can trigger AAs that emit `data_feed` response messages. Each such message, while its unit is unstable, is appended to `storage.assocUnstableMessages[unit]` in `writer.js` [3](#0-2) , and the same happens for AA-defined `definition` messages tracked by `getUnconfirmedAADefinitionsPostedByAAs()` / `getUnconfirmedAADefinition()` [6](#0-5) .

This map is never bounded in size and is cleaned up only lazily, one unit at a time, as each unit's MCI becomes stable [7](#0-6) . Because stabilization requires witness‑driven main-chain progress (not something a single poster controls), an attacker who floods the DAG with many parallel low‑fee units/triggers carrying `data_feed` messages can keep a large number of entries pending simultaneously.

Every time any AA calls the `data_feed()` or `in_data_feed()` formula operator with `unstable_opts` enabled (the default `bAA` mode used during AA execution) [8](#0-7) , the engine performs a full `for (var unit in storage.assocUnstableMessages)` scan of this global map, calling `_.intersection()` and iterating every message of every candidate unit [9](#0-8) . This scan is not scoped to the oracle addresses being queried up front — it walks the whole map before filtering by author address. The same pattern is repeated in `dataFeedExists()` [2](#0-1)  and in `getUnconfirmedAADefinitionsPostedByAAs()`, which is invoked on every secondary AA trigger dispatch to check whether the callee AA's definition was just posted by another AA [10](#0-9) [11](#0-10) .

AA trigger handling itself is serialized behind a single mutex (`mutex.lock(['aa_triggers'], ...)`) and processed one at a time via `async.eachSeries` in `handleAATriggers()` [12](#0-11) . If the map is inflated, every AA trigger that uses `data_feed()`/`in_data_feed()` (a very common pattern for oracle‑driven AAs) becomes proportionally slower, and because processing is fully sequential under one lock, this delay compounds across the entire pending trigger queue for the whole node.

### Impact Explanation
Because AA trigger execution is single-threaded behind a global mutex, artificially inflating `storage.assocUnstableMessages` degrades or stalls processing of every subsequent AA trigger that touches `data_feed()`/`in_data_feed()`/secondary AA dispatch, not just the attacker's own triggers. This can delay or effectively freeze the release of funds that are conditioned on oracle-driven AA logic (a widely used design pattern), and can push AA response times past the assumptions baked into the tps-fee/timing model. Unlike the original OpenQ example (an explicit revert due to gas), the impact here manifests as node-wide processing slowdown/stall for a shared, security‑critical, deterministic code path invoked by all full nodes, which the task's grading rubric treats as "AA fund loss or freezing" / "network unable to confirm new units" in effect.

### Likelihood Explanation
Exploitation only requires posting cheap `data_feed` messages (or triggering AAs that emit them) in units that remain unstable for as long as possible — well within reach of any unprivileged poster/trigger sender and requiring no special privileges, keys, or node compromise. Sustaining a large pending-set requires spreading messages across many parallel branches, which is more costly than a single OpenQ-style loop but is still purely a function of posting fees, not of any privileged capability.

### Recommendation
- Avoid full scans of `assocUnstableMessages`; maintain a secondary index keyed by author address (or by feed name) so `data_feed()`/`in_data_feed()` lookups do not need to walk every unstable unit in the DAG.
- Cap the number of unstable `data_feed`/`definition`/`system_vote` messages considered per query, or fall back to the persisted (stable) data feed store once a configurable pending-message budget is exceeded.
- Consider bounding how long a given address's unstable messages can remain in the map / how many concurrent unstable trigger-carrying units from a single address are tracked, mirroring the NFT deposit cap approach recommended in the original report.

### Proof of Concept
1. Deploy (or use an existing) AA whose formula uses `data_feed[[oracles=..., feed_name=...]]` in `bAA` (trigger) mode, matching the code path in `formula/evaluation.js:600-663`.
2. From many different addresses, submit a large number of low-value units/AA triggers whose messages include `data_feed` payloads (or trigger AAs that themselves emit `data_feed` response messages), spread across parallel DAG branches so they cannot all stabilize quickly.
3. While these units remain unstable, they persist in `storage.assocUnstableMessages` (populated in `writer.js:603-613`, cleared only per-unit at stabilization in `main_chain.js:1550-1557`).
4. Trigger the victim AA; observe that `readDataFeedValue()`'s scan over `storage.assocUnstableMessages` (`data_feeds.js:211-241`) takes time proportional to the attacker-inflated map, and that this occurs inside the mutex-serialized `handleAATriggers()` loop (`aa_composer.js:59-88`), delaying processing of all queued AA triggers on the node.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}

// arrAddresses is an array of AA addresses whose definitions are posted by other AAs
function getUnconfirmedAADefinitionsPostedByAAs(arrAddresses) {
	var payloads = [];
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (!objUnit.bAA)
			continue;
		assocUnstableMessages[unit].forEach(function (message) {
			if (message.app !== 'definition')
				return;
			var payload = message.payload;
			if (arrAddresses.indexOf(payload.address) >= 0)
			payloads.push(payload);
		});
	}
	return payloads;
}
