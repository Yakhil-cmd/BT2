### Title
`StatusHandler#process` writes GitHub `status` events onto Commit rows by SHA alone, without scoping to the payload's repository, letting a status event for one repo mutate a same-SHA commit belonging to another repo's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, which is not scoped by `repository_name`/`stacks` at all, unlike every other stateful handler (`push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) which all filter through `stacks`. [1](#0-0)  Since `commits.sha` is only unique per `(sha, stack_id)` and not globally unique [2](#0-1) , a `status` webhook whose `sha` collides with a commit tracked by an unrelated stack will write a `Status` row onto that unrelated commit.

### Finding Description
The binding that should hold is: `repository_name` (derived from `payload.dig('repository', 'full_name')` in `Handler#repository_name`) `==` the repository owning every `Commit` row mutated by `process`. [3](#0-2)  This binding is enforced by the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers use, but `StatusHandler#process` never calls it - it queries `Commit` directly by `sha` across the whole table. [1](#0-0) [4](#0-3) 

`WebhooksController#verify_signature` only proves that the payload was legitimately signed by the GitHub App/webhook secret configured for `repository_owner` (the org in the payload); it does not - and cannot - constrain which `Commit` rows the handler is allowed to touch. [5](#0-4)  `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` comes from the found `Commit` (i.e. the victim stack), not from the payload, so the write is attributed to whichever stack happens to own the pre-existing commit row with that SHA. [6](#0-5)  This flips `Commit#deployable?` (which depends on `success?` via `status`) for the victim's commit. [7](#0-6) [8](#0-7) 

Exploit flow: attacker owns/controls `attacker/repo` in the same GitHub organization Shipit is configured for (needed since the org's `webhook_secret` must validly sign the delivered event; the attacker does not need to know the secret - GitHub itself signs and delivers the event for any repo the org-level App/webhook covers). Attacker pushes a commit whose SHA matches one already tracked in `victim/repo`'s Shipit stack (e.g., the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any content-identical commit). GitHub sends a genuinely signed `status` webhook for `attacker/repo` with that `sha` and `state: success`. `StatusHandler#process` finds **all** `Commit` rows with that `sha` regardless of stack/repository and creates a success `Status` on each, including the victim's row.

### Impact Explanation
A cross-repository write: an event correctly authenticated for `attacker/repo` mutates a `Commit`/`Status` belonging to `victim/repo`'s stack, potentially flipping `deployable?` to true and triggering `schedule_continuous_delivery`/merges for a commit that never actually passed the victim's CI. This matches the "payload for one repository mutating another's stack/commit" Critical-impact category. The blast radius is bounded to stacks whose tracked commits happen to share a SHA with a commit in a repo covered by the same GitHub App/webhook installation - most practically exploitable when Shipit's webhook covers an org-wide installation and repos in that org can produce colliding SHAs (trivially, empty-tree/empty-commit SHAs, or duplicate history from forks/templates).

### Likelihood Explanation
Requires the attacker to be able to get a genuinely-signed `status` event delivered to Shipit's endpoint for a SHA that also exists in a Shipit-tracked victim stack. This is straightforward if the GitHub App/webhook is installed at the org level (covering all repos in the org, not just Shipit-tracked ones) and the attacker can create/push to any repo in that org (common for engineers who are not repo maintainers or Shipit operators). Colliding on a SHA present in the victim stack is trivial via the empty-tree constant or template/duplicate-history repos. No secrets, sessions, or privileged roles are needed - only the ability to push a commit and let GitHub emit its own signed webhook.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the other handlers: resolve `stacks` (or the specific `Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup with `stack_id: stacks.pluck(:id)` (or join through `stack: { repository: ... }`) so a `status` event can only mutate commits belonging to stacks of the repository that actually emitted it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event for attacker repo must not mutate victim repo's commit with same sha" do
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

  victim_repo = shipit_repositories(:shipit) # or create Repository.create!(name: 'repo', owner: 'victim')
  victim_stack = create_stack(repository: victim_repo)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')

  attacker_repo = Repository.create!(name: 'repo', owner: 'attacker')
  attacker_stack = create_stack(repository: attacker_repo)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'branches' => [{ 'name' => attacker_stack.branch }],
    'repository' => { 'full_name' => 'attacker/repo' }
  }

  assert_equal false, victim_commit.reload.success?

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding check: repository_name ('attacker/repo') != victim_commit's repository,
  # yet victim_commit's status flips to success.
  assert_equal true, victim_commit.reload.success?, "victim commit's status was mutated by an attacker-repo status event"
end
```
This demonstrates that a `status` payload whose `repository.full_name` is `attacker/repo` still causes `victim_commit.status.success?` to become true, confirming the missing repository-scoping in `StatusHandler#process`.
