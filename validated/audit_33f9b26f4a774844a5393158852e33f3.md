### Title
Webhook signature is verified against an attacker-chosen organization while handlers act on an attacker-chosen repository/commit from the same unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/webhook secret to validate a webhook against using the fully attacker-controlled JSON body itself (`repository.owner.login` / `organization.login`), then hands the same untrusted body to handlers that key their side effects off other, independent fields of that body (`repository.full_name`, `sha`, `organization.login`). Nothing ties the verified signing organization to the repository/organization the handler actually acts on.

### Finding Description
`verify_signature` computes `repository_owner` from the raw payload and fetches the matching `Shipit.github(organization: repository_owner)` config to validate `X-Hub-Signature`: [1](#0-0) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value inside the very body being signed.

Handlers, however, never re-check that the org whose secret validated the request matches the resource the handler mutates:

- `Handler#stacks`/`#repository_name` resolves the target purely from `payload.dig('repository', 'full_name')`: [2](#0-1) 
- `PushHandler#process` uses that resolved `stacks` scope plus the attacker-supplied `after` SHA to enqueue a sync: [3](#0-2) 
- `StatusHandler#process` matches commits **globally** by `sha` with no repository/org scoping at all: [4](#0-3) 
- `MembershipHandler#find_or_create_team!` assigns `team.organization = params.organization.login` taken straight from the payload: [5](#0-4) 

Because Shipit explicitly supports per-organization GitHub Apps, each with its own `webhook_secret` (documented multi-org schema), an entity that legitimately controls one organization's App/webhook secret can freely construct an entirely new JSON body (not tamper with an existing signed one), set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` looks up and validates against the secret they know), while setting `repository.full_name`, `sha`, or `organization.login` used by the handler to reference a **different** organization/repository/stack that the same Shipit instance also tracks: [6](#0-5) 

The bound equality that should hold — *organization whose signature was verified == organization/repository the handler mutates* — is never enforced anywhere in the request pipeline.

### Impact Explanation
- `PushHandler` can enqueue `GithubSyncJob`/`sync_github` for stacks belonging to an organization other than the one whose secret signed the request, with an attacker-chosen `expected_head_sha`, potentially triggering continuous-deployment sync/deploy flows for a repository the caller does not own — an unauthorized deploy trigger across organizational boundaries.
- `StatusHandler` can post/forge commit status records against **any** commit in the database regardless of which org's secret was used, since it is not scoped by repository or organization at all.
- `MembershipHandler` allows a caller controlling only Org A's secret to create/mutate `Team` records tagged with an arbitrary `organization` value, which feeds into `Shipit.github_teams` authorization checks (`User#authorized?`), risking escalation into another organization's authorization boundary.

This meets the Critical/High bar of "cross-repository writes" and "escalation into `Shipit.github_teams` authorization," assuming a multi-organization Shipit deployment (the documented and supported configuration).

### Likelihood Explanation
Requires the attacker to legitimately control a GitHub App/webhook secret for at least one organization onboarded to the same Shipit instance (e.g., a self-service or partner org in a multi-tenant Shipit deployment) — this is not a session, `ApiClient` token, or privileged Shipit account, and does not require compromising another org's secret. Given Shipit's documented support for multiple independent GitHub orgs sharing one deployment, this is a realistic configuration, though exploitability depends on the deployment actually hosting multiple, mutually-untrusted organizations.

### Recommendation
After `verify_signature` succeeds, thread the *verified* organization through to handlers and require that `repository.owner.login`/`organization.login` used by each handler match the organization whose secret validated the signature; reject (422) on mismatch. For `StatusHandler`, scope the `Commit` lookup to commits belonging to a stack whose repository owner equals the verified organization.

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema), both onboarded to the same Shipit instance.
2. Attacker legitimately possesses `orgA`'s `webhook_secret` (e.g., as `orgA`'s GitHub App administrator).
3. Attacker builds body: `{"ref":"refs/heads/master","after":"<attacker sha>","repository":{"owner":{"login":"orgA"},"full_name":"orgB/target-repo"}}`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "orgA"`, fetches `orgA`'s config, and the signature validates successfully: [7](#0-6) 
6. `PushHandler#process` resolves `stacks` via `repository.full_name == "orgB/target-repo"` and enqueues `sync_github` for `orgB`'s stack with the attacker-chosen `after` SHA — despite the request only being authenticated as `orgA`. [3](#0-2) [2](#0-1)

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
