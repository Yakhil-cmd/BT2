Based on my investigation, there's a valid analog to the reported "owner manipulates oracle right before settlement" bug class in Agave's reward-commission accounting logic.

### Title
Vote account withdrawer can redirect inflation-reward commission by changing the commission collector immediately before epoch reward distribution, bypassing the intended anti-rug delay - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Agave delays the *rate* of a validator's inflation-reward commission by at least one epoch specifically to prevent "last minute commission rugs," but the *recipient* of that commission (the "commission collector" pubkey, introduced by SIMD-0232) is not subject to any such delay. The `UpdateCommissionCollector` instruction lets the vote account's authorized withdrawer redirect commission payouts to an arbitrary account at any time, and the runtime always resolves the collector from the live/current vote account state rather than a delayed snapshot.

### Finding Description
The reward calculation intentionally delays the *commission rate* used at epoch-reward time by reading it from a snapshot of vote-account state taken a full epoch earlier when `delay_commission_updates` is active: [1](#0-0) 

This delayed-snapshot mechanism (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) exists explicitly to stop "last minute commission rugs": [2](#0-1) 

However, when computing *who receives* that commission (`commission_pubkey`), the code reads `vote_state.inflation_rewards_collector()` from `vote_state`, which is derived from `distribution_epoch_vote_accounts` — the current/live vote account state at distribution time, not the delayed snapshot used for the rate: [3](#0-2) [4](#0-3) 

The `UpdateCommissionCollector` vote instruction that sets `inflation_rewards_collector` has no epoch-position/timing restriction at all — it only requires the authorized withdrawer's signature: [5](#0-4) 

This is in stark contrast to `UpdateCommission` (the rate-only instruction), which is explicitly gated by `is_commission_update_allowed` so that commission increases cannot happen in the back half of an epoch: [6](#0-5) [7](#0-6) 

The instruction dispatch confirms `UpdateCommissionCollector` performs no such check, unlike `UpdateCommission`, which explicitly consults `delay_commission_updates`: [8](#0-7) [9](#0-8) 

### Impact Explanation
Because the collector pubkey is resolved from live state at reward-distribution time while the rate is deliberately delayed by a full epoch to prevent rug-style manipulation, a validator's withdraw authority can submit a single `UpdateCommissionCollector` transaction just before epoch-boundary reward calculation/distribution and redirect the entire commission portion of that epoch's inflation rewards to any account they choose — including one different from the vote/node identity that delegators expect. This corrupts intended reward/commission accounting semantics: the anti-rug protection for the rate is rendered ineffective because the payout destination for that (delayed, "safe") rate can still be hijacked at the last moment. This falls squarely within the in-scope "stake and reward accounting" category and is reachable purely by a normal signed transaction from the vote account's existing withdraw authority — no cluster-level or operator-only access is required beyond what SIMD-0232 already grants that authority.

### Likelihood Explanation
Likelihood is high for any validator operator who is also the withdraw authority (a very common configuration) and wants to game commission payouts, or in the case of stolen/compromised withdrawer keys, to be a fast way to siphon that epoch's commission before the legitimate operator can react. No feature-gate bypass or special conditions are needed beyond `custom_commission_collector` (SIMD-0232) being active, which is required for the feature to exist at all.

### Recommendation
Apply the same delayed-snapshot resolution used for the commission rate to the commission collector pubkey — i.e., resolve `inflation_rewards_collector` (and `block_revenue_collector`, if it feeds similarly time-sensitive payouts) from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` rather than `distribution_epoch_vote_accounts` when `delay_commission_updates` (or an equivalent feature gate) is active. Alternatively, gate `UpdateCommissionCollector` with the same `is_commission_update_allowed`-style epoch-position restriction already used for `UpdateCommission`.

### Proof of Concept
1. A validator's vote account has `authorized_withdrawer = W` and commission rate `r%`, with `delay_commission_updates` active so `r` used for the current epoch's rewards is fixed from the snapshot taken an epoch prior (per `get_cached_vote_accounts`).
2. Immediately before the epoch boundary at which `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards` runs (still within the "current"/distribution epoch state that `distribution_epoch_vote_accounts` reflects), `W` signs and submits a single `UpdateCommissionCollector(InflationRewards)` transaction pointing `inflation_rewards_collector` at an account `X` controlled by `W`, per `update_commission_collector` in `programs/vote/src/vote_state/mod.rs`.
3. At reward distribution, `redeem_delegation_rewards` computes `commission_pubkey` from the *live* `vote_state.inflation_rewards_collector()` (line 749-756 of `calculation.rs`), which now returns `X` rather than the vote/node identity delegators expected, while the commission *rate* `r` is still correctly the delayed/expected value.
4. Commission lamports for that epoch's distribution are credited to `X` instead of the previously configured collector, with no delay or check preventing this last-minute redirection — mirroring exactly the "owner sets fake oracle right before battle ends" pattern from the external report, but for reward-commission payout destination rather than a price oracle.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    new_collector_index: IndexOfAccount,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let mut vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = validate_and_resolve_collector_key(
        instruction_context,
        &vote_account,
        new_collector_index,
        rent,
    )?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(&mut vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
