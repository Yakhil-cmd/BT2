### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on `repository.full_name` / raw `sha` with no cross-check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` instance (and therefore the HMAC secret used to validate the payload) using `repository_owner`, a value pulled straight out of the unauthenticated JSON body [1](#0-0) . That same field is derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [2](#0-1) . Once the signature check passes (or is skipped), the full, attacker-influenced `params` hash is forwarded unchanged to the event handlers [3](#0-2) , which key off a *different* field, `payload.dig('repository', 'full_name')`, to decide which `Stack`/`Repository` to mutate [4](#0-3) . `StatusHandler` does not even use the repository field — it looks up commits globally by `sha` [5](#0-4) .

This is the same bug class as the Weiroll report: the field that is verified (`organization`/owner used to pick the signing secret) is not the field that is acted upon (the `repository.full_name` / `sha` used to select the resource to write to).

### Finding Description
`GithubApp#verify_webhook_signature` explicitly bypasses HMAC verification when no `webhook_secret` is configured for the resolved organization: `return true unless webhook_secret` [6](#0-5) . The engine supports multi-organization configuration, where each org can independently have a `webhook_secret` set or left blank (`webhook_secret: # nil` is even the documented default in the example configs) [7](#0-6) .

Because `verify_signature` resolves the signing secret purely from the attacker-supplied `repository.owner.login` (or `organization.login`) field, an attacker only needs to know the login of **any** configured organization that has no `webhook_secret` set. Supplying that login satisfies the "authenticated organization" side of the check — the HMAC check short-circuits to `true` — while the "repository that is written" side (`repository.full_name` for push/check_suite handlers, or bare `sha` for `StatusHandler`) can name a completely different, victim organization's repository or an arbitrary commit hash tracked anywhere in the Shipit instance.

Concretely:
- `PushHandler` resolves target stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository','full_name')` [4](#0-3) [8](#0-7)  — unrelated to the org used for signature verification.
- `StatusHandler` looks up commits by `sha` with no repository/org scoping at all and writes attacker-controlled `state`, `context`, `description`, `target_url` via `commit.create_status_from_github!(params)` [9](#0-8) .

### Impact Explanation
An unauthenticated network attacker who knows only the login of one configured Shipit organization that lacks a `webhook_secret` can forge a `status` webhook event, bypass signature verification entirely, and fabricate a "success" commit status for any commit SHA tracked by the Shipit instance — including commits belonging to a completely unrelated, properly-secured organization. Since commit statuses gate deployability in Shipit's UI/CD pipeline, this can make an unreviewed or failing commit appear deployable, leading to an **unauthorized deploy** of that commit — one of the explicitly accepted High/Critical impacts. The same authentication/target mismatch also lets the attacker trigger `stack.sync_github` on stacks belonging to organizations it never authenticated against.

### Likelihood Explanation
Exploitability hinges on at least one configured organization in the Shipit deployment omitting `webhook_secret` — a configuration state explicitly shown as the default/example in this engine's own setup docs and secrets templates [10](#0-9) . Given that, no credentials, session, or GitHub access are required — only an HTTP POST to `/webhooks` with a known org login and a target `sha`/`repository.full_name`.

### Recommendation
Bind the value acted upon to the value verified: `verify_signature` should record which organization/app actually authenticated the request, and every handler (`PushHandler`, `StatusHandler`, etc.) must confirm that the repository/commit being mutated belongs to that same authenticated organization before acting — not merely rely on `webhook_secret` being present. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for any configured organization in production; require an explicit "unsecured webhook" opt-in scoped narrowly, or refuse to process cross-organization payloads regardless of secret presence.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret`) and `org-b` (has a properly tracked `Stack`/commits, with `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=anything`, and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/whatever" },
  "sha": "<victim commit sha belonging to org-b>",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://attacker.example"
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'org-a')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` [6](#0-5) .
4. `StatusHandler.call(params)` runs unfiltered by organization, finds the commit in `org-b` by `sha`, and records the forged "success" status [5](#0-4) , potentially unlocking that commit for deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
