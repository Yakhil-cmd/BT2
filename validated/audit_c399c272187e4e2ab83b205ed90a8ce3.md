### Title
Stop-hook review-set can go empty after a non-linear HEAD move (branch switch/reset+recommit), letting a dangerous committed change bypass Stop-hook security review - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`compute_v2_review_set` only re-includes files changed by a commit made during the turn when `head_at_capture` is a **linear ancestor** of the new `HEAD` [1](#0-0) . If the turn's git activity moves `HEAD` non-linearly (checkout to another branch, `reset --hard` + recommit, rebase onto a different base) while leaving the working tree clean, `dirty_now` stays empty and `review_set = dirty_now ∩ changed_since` collapses to the empty set even though `changed_since` (diff against the stash baseline) correctly shows the file differs. This causes the Stop hook to hit the "empty review set" skip path and never run its LLM security review on the change.

### Finding Description
`consume_stop_state` snapshots `baseline_sha` and `head_at_capture` captured at the prior `UserPromptSubmit` and hands them to `compute_v2_review_set` [2](#0-1) . In `compute_v2_review_set`, `dirty_now` is built from `git status` output (clean after a commit) plus, conditionally, the file list of `head_at_capture..HEAD` — but only if `_is_ancestor(head_at_capture, current_head)` holds [1](#0-0) . `_is_ancestor` uses `git merge-base --is-ancestor`, which is false for sideways/non-linear HEAD moves such as switching to an unrelated branch or `reset --hard` followed by a new commit [3](#0-2) . In that case `dirty_now` remains whatever `git status` reports — empty for a clean tree post-commit — while `changed_since` (built from `git diff --name-only <baseline_sha>` against the current worktree) correctly still includes the file [4](#0-3) . Because `review_set = dirty_now ∩ changed_since`, an empty `dirty_now` forces `review_set` to `∅` regardless of `changed_since`. The Stop hook then hits `if not review_paths: ... _skip(9, ...)` and exits without ever calling `analyze_code_security` [5](#0-4) . This is reachable purely through ordinary git commands (`git checkout <other-branch>`, `git reset --hard`, rebase) that a Claude session can be steered into running via prompt injection embedded in repository content (e.g., README/AGENTS.md instructions, PR descriptions), since the attacker only needs Claude to issue "normal" git operations in the cloned repo — no privileged access is required.

### Impact Explanation
This is a logic-level bypass of a security guard: it allows a dangerous code change to be committed and reach the working tree/HEAD of a Claude Code session without being reviewed by the Stop-hook security-guidance pipeline, because the review-set computation misbinds itself to a stale linear-ancestry assumption about `head_at_capture` rather than the true git baseline/content diff. This matches the "Logic-level service disruption caused by bypassing a required guard" bounty class — the required LLM security review guard is silently skipped for a real, attacker-visible change.

### Likelihood Explanation
Preconditions are low-bar and fully attacker-reachable: the attacker only needs their (unprivileged) repository content to induce Claude to perform ordinary git commands during a turn — switching branches, resetting, or rebasing before/after committing a malicious change — all common, non-suspicious operations that would not by themselves raise alarms. No credentials, admin rights, or social engineering of the human operator are needed beyond normal prompt-injection-style repo content, which is already an accepted reachable vector per the rules. The bug is deterministic given the described git sequence and clean working tree, so it is reliably repeatable.

### Recommendation
Do not gate the `head_at_capture..HEAD` file inclusion on strict linear ancestry alone. Either (a) always union in `_git_name_only(head_at_capture, "HEAD")`-style diff results whenever `head_at_capture != current_head` regardless of ancestry (treating any HEAD movement as potentially containing reviewable content), or (b) derive `review_set` directly as `changed_since` (diff against `baseline_sha`) restricted to files also touched (dirty or committed) this turn, without requiring `dirty_now` to be nonempty from `git status` alone. In general, avoid intersecting with a `dirty_now` set that can go empty independent of whether committed content actually changed relative to baseline.

### Proof of Concept
Integration test in the style of the existing `compute_v2_review_set` tests:
1. Create a git repo, make an initial commit (`H0`).
2. Simulate UPS: call `capture_git_baseline(cwd)` to get `baseline_sha` (stash-create SHA at `H0`), set `head_at_capture = H0`.
3. Create a second, unrelated branch `B` from an ancestor unrelated to `H0` (or `git reset --hard` to a different commit), then on that ref write a dangerous file (e.g. `os.system(user_input)`), `git add` + `git commit` — HEAD is now `C1`, tree is clean, and `_is_ancestor(H0, C1)` is `False`.
4. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture=H0, untracked_at_baseline={})`.
5. Assert: `changed_since` (internal) still shows the dangerous file, but with the current logic `review_paths` is `[]` — i.e., assert the bug reproduces as `review_paths == []` even though `git diff <baseline_sha>` shows the file changed.
6. After applying the fix, assert `review_paths` contains the dangerous file's absolute path, confirming the Stop hook would no longer skip via `_skip(9)` and would proceed to `analyze_code_security` on the change.

def _is_ancestor(cwd, maybe_ancestor, descendant):
    """True if `maybe_ancestor` is reachable from `descendant` (i.e. HEAD
    moved forward via commit/merge, not sideways via checkout)."""
    try:
        result = subprocess.run(
            [*GIT_CMD, "merge-base", "--is-ancestor", maybe_ancestor, descendant],
            cwd=cwd, capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return False
