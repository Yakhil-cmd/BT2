## Title
Asset definer can silently swap the attestor set that gates spending, instantly freezing or re‑authorizing balances of an already‑issued asset - ([File: validation.js])

### Summary
Ocore lets an asset be created with `spender_attested: true`, meaning only addresses attested by a chosen attestor set are allowed to hold/spend it [1](#0-0) . That attestor set, however, is **not fixed at asset creation** — the definer can replace it at any later time with a simple `asset_attestors` message, and every downstream spend/output check resolves against whatever the **latest** attestor list happens to be at validation time [2](#0-1) . This is the same class of bug as "blindly trusts upgradeable proxy tokens": a component (the attestor list) that other users/AAs implicitly trust as fixed can be swapped by its controller with no notice, no timelock, and no automated re‑approval mechanism, instantly changing who is authorized to move value denominated in that asset.

### Finding Description
When an asset is defined with `spender_attested=true`, spend validation requires the input/output owner address to appear in `objAsset.arrAttestedAddresses`, which is computed by `filterAttestedAddresses` against `objAsset.arrAttestorAddresses` [3](#0-2) [4](#0-3) [5](#0-4) .

`arrAttestorAddresses` is not the list published at asset‑definition time — `readAsset` always looks up the **most recently published** `asset_attestors` unit before `last_ball_mci` and uses that: [2](#0-1) .

Updating this list requires nothing more than a single message signed by the asset's definer address: [6](#0-5) 

`checkAttestorList` only validates address format/ordering/count, with no cooldown, no requirement for old attestors' consent, and no way for holders or dependent AAs to block or delay the change: [7](#0-6) .

`filterAttestedAddresses` then simply intersects `attestations` with whichever `arrAttestorAddresses` is currently "latest": [8](#0-7) .

The consequence: an asset that has already been distributed, held, and trusted by third parties (users, an AA acting as a DEX/exchange, or a private‑payment counterparty) as a "compliance-gated" or otherwise attested asset can have its entire authorization semantics rewritten unilaterally and instantly by the definer — precisely analogous to an ERC‑20 proxy admin upgrading implementation logic after tokens have already been deposited into a system that assumed fixed semantics.

### Impact Explanation
- **Fund freezing:** the definer (or an attacker who compromises/controls the definer key, or is simply malicious from the start) can replace the attestor list with one that no longer recognizes previously-attested holders. Every existing balance held by those addresses instantly fails the "owner/output address is not attested" checks [9](#0-8) [10](#0-9) , permanently locking user or AA funds denominated in that asset with no warning and no on-chain recourse.
- **Bypass of compliance/trust assumption:** conversely, the definer can add an address they control to the attestor list and self-attest, retroactively qualifying as an "attested" holder/recipient for an asset that other systems (e.g., an AA-based exchange that only accepted this asset because it assumed a fixed, vetted attestor such as a KYC provider) trusted as gated. This breaks any invariant a dependent AA or counterparty built around "only attestor‑approved addresses can hold/receive this asset."
- Because the check always resolves against the *current* attestor list rather than the list in effect when trust was established, this satisfies "AA fund loss or freezing" and "node disagreement" style impact — no consensus or delay protects existing holders/dependents from a semantics change.

### Likelihood Explanation
Any account that is the `definer_address` of a `spender_attested` asset can trigger this at will — this is an ordinary, unprivileged action available to any asset issuer, requiring only a single signed `asset_attestors` message [11](#0-10)  and, if writing to attestations, a subsequent `attestation` message from the new attestor address (also unprivileged) [12](#0-11) . No special node/hub/network position is needed, matching the report's "no automated upgrade tracking, no pause pending approval" pattern exactly.

### Recommendation
- Pin the attestor set used for validating a given output/spend to the attestor list that was in effect (stable) at the time the output was created (or at issuance), rather than always resolving to the "latest" list, so trust changes cannot retroactively affect already-issued balances.
- Alternatively/additionally, require a timelock or explicit re-approval step (e.g., requiring holders to re-attest or opt in) before a new attestor list becomes effective for existing balances, giving downstream consumers (AAs, wallets, exchanges) a window to detect and react to the change — mirroring the report's recommendation to "pause interactions ... until they have received approval."
- Surface `asset_attestors` updates as a discoverable event so dependent AAs/wallets can programmatically monitor and react to attestor-list changes for assets they hold or accept.

### Proof of Concept
1. Attacker creates asset `A` with `spender_attested: true`, `attestors: [attestor1]` (a reputable-looking attestor) via `asset` message, satisfying `validateAssetDefinition` [13](#0-12) .
2. `attestor1` attests victim address `V` (or an AA relies on `attestor1`'s attestation of counterparties). `V` accumulates a balance of asset `A`, trusting that only `attestor1`-approved addresses can ever hold/spend it.
3. Attacker (definer of `A`) posts `asset_attestors` with `attestors: [attackerAddr]`. This passes validation solely because the author is the definer [6](#0-5) .
4. On stabilization, `readAsset` now resolves `arrAttestorAddresses = [attackerAddr]` for asset `A` for all future validations [14](#0-13) .
5. `V`'s existing balance now fails `filterAttestedAddresses`/spend checks ("owner address is not attested"), permanently freezing `V`'s funds [9](#0-8) ; or, attacker self-attests `attackerAddr` via `attestation` message and can now spend/receive as an "attested" party, defeating whatever compliance/trust guarantee downstream AAs or counterparties assumed when they accepted asset `A`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
