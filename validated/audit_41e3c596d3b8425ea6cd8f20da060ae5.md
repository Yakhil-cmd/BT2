### Title
Forged `pull_request` (`edited`) webhook for a no-webhook-secret organization overwrites `PullRequest` records for arbitrary repositories - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook based solely on `params.dig('repository','owner','login')`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has a blank `webhook_secret`. `EditedHandler`, however, resolves the target repository/stack/`PullRequest` from a completely independent field, `params.repository.full_name`, which is never checked against the org used for signature verification. An attacker can therefore set `repository.owner.login` to a Shipit-configured, secret-less organization to sail through `verify_signature`, while setting `repository.full_name` to any repository (belonging to any other, secret-protected org) to make `EditedHandler` overwrite that victim repository's `PullRequest` record.

### Finding Description
The broken binding: the code implicitly assumes
`params.dig('repository','owner','login') == params.repository.full_name.split('/').first`
but this is never enforced anywhere in the request path.

Path:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (line 61) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) does `return true unless webhook_secret` — if the org identified by `repository.owner.login` is configured in Shipit with a blank/nil `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`, where both `OrgOne` and `OrgTwo` have `webhook_secret:` nil), the request is accepted with **no HMAC check at all**, regardless of the `X-Hub-Signature` header content.
- Once past the filter, `Shipit::Webhooks.for_event('pull_request')` dispatches to `EditedHandler#process` (app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb:41-45), which looks up the target `Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (line 64) — a field that was **never used or validated** during `verify_signature`.
- `EditedHandler#pull_request` (lines 49-61) then finds the `PullRequest` by `number` scoped to that resolved repository/stack, and `process` calls `pull_request.update(github_pull_request: params.pull_request)` (line 44), fully attacker-controlled content.

Exploit: the attacker crafts a JSON body where `repository.owner.login = "OrgOne"` (a Shipit-configured org with no `webhook_secret`) but `repository.full_name = "OrgTwo/victim-repo"` (a different, secret-protected org's repository that has a Shipit stack and an existing PR). They send this as `POST /webhooks` with header `X-Github-Event: pull_request`, any `X-Hub-Signature` value (or none). `verify_signature` authenticates against `OrgOne`'s (secret-less) config and passes unconditionally; `EditedHandler` then updates `OrgTwo/victim-repo`'s `PullRequest` record with attacker-supplied `github_pull_request` data (title, state, additions/deletions, labels, assignees, head sha/ref, etc.) — none of which was authenticated for that repository/org at all.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `EditedHandler` only requires `repository.full_name` to be present as a string, it does not cross-check it against `repository.owner.login`; there is no model validation or controller check tying the two fields together.

### Impact Explanation
This is a cross-tenant forged-webhook write: a request that only authenticated (trivially, due to lack of secret) as belonging to organization A is used to mutate persisted state (`PullRequest#github_pull_request`) belonging to a completely different repository/org B, without B's webhook secret ever being verified. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / authentication bypass via forged webhook. The blast radius is any repository/stack in the Shipit instance whose `PullRequest` records exist, as long as at least one other org configured in the same Shipit instance lacks a `webhook_secret`. Repeatable indefinitely and for any PR number/repository combination.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one GitHub organization configured (`Shipit.github(organization: ...)` config) with a blank/absent `webhook_secret` — this is an operator configuration choice, but the engine does nothing to disallow or warn against it, and the sample dummy config (`secrets_double_github_app.yml`) demonstrates this pattern is supported/expected. Attacker cost is minimal: a single unauthenticated HTTP POST with a crafted JSON body; no credentials, sessions, or knowledge of any real webhook secret are required. Fully repeatable and requires no privileged access.

### Recommendation
Bind the org used for authentication to the org actually acted upon: derive the target repository/organization strictly from the same field used to verify the signature (e.g., verify against `repository.full_name`'s owner, or reject the request if `repository.owner.login` doesn't match the owner segment of `repository.full_name`). Additionally, do not treat a blank `webhook_secret` as an automatic pass — require every configured GitHub organization/app to have a non-blank `webhook_secret`, or reject (422) webhooks for any org without one instead of accepting unconditionally.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb`, using `test/dummy` fixtures/`secrets_double_github_app.yml`-style config with two orgs, both without `webhook_secret`, or one with and one without):

1. Setup: configure Shipit with two orgs, `OrgNoSecret` (no `webhook_secret`) and `OrgVictim` (has repository `OrgVictim/victim-repo` with a `Stack` and an existing `Shipit::PullRequest` #1 with known `github_pull_request` content, e.g. `title: "original title"`).
2. Binding to assert BEFORE: `pull_request.reload.github_pull_request['title'] == "original title"` and `params.dig('repository','owner','login') != params.repository.full_name.split('/').first` is possible without rejection.
3. POST `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or a garbage one), and JSON body:
```json
{
  "action": "edited",
  "number": 1,
  "pull_request": { ...attacker-controlled fields..., "title": "PWNED" },
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgVictim/victim-repo" },
  "sender": { "login": "attacker" }
}
```
4. Assert response is `200 OK` (not `422`).
5. Assert AFTER: `pull_request.reload.github_pull_request['title'] == "PWNED"` — proving the record for `OrgVictim/victim-repo`, whose org config has a webhook secret, was mutated by a request authenticated only against `OrgNoSecret`'s secret-less config, violating the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it."       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
