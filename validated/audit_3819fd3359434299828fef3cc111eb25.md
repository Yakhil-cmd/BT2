### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but the affected `Repository`/`Stack` is selected from the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) . Once the signature is accepted, `Shipit::WebhooksController#create` hands the *entire raw JSON payload* to the registered handlers [2](#0-1) . Every handler resolves the target `Repository`/`Stack` using a *different* field, `payload.dig('repository', 'full_name')` [3](#0-2) , which is never cross-checked against the field that was actually covered by the verified organization/app selection.

### Finding Description
This mirrors the reported bug class: a value is trusted and acted upon without being bound to the value that was actually verified. Here the "verified" side is `repository.owner.login`/`organization.login` (used to pick the GitHub App instance whose `webhook_secret` performs `verify_webhook_signature`) [4](#0-3) , while the "acted upon" side is `repository.full_name` (used to locate and mutate the `Stack`) [3](#0-2) .

Because Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, keyed by organization name [5](#0-4) , an attacker who controls (or is simply the owner of) any one organization configured in Shipit's `github` secrets — e.g., a low-privilege personal org they create and register — can compute a perfectly valid HMAC signature using *their own* `webhook_secret`, while setting `repository.full_name` inside the JSON body to `victim-org/victim-repo`. `verify_signature` will pick `Shipit.github(organization: 'attacker-org')`, verify the signature against the attacker's own secret (which succeeds, since it's their own valid secret and payload), and pass. The handler layer then trusts `repository.full_name` from that same payload to locate and act on the victim's `Stack`, e.g. `PushHandler#process` calling `stack.sync_github(expected_head_sha: params.after)` for stacks whose repository matches `victim-org/victim-repo` [6](#0-5) , or `StatusHandler#process` writing a `Status` on a victim commit by `sha` [7](#0-6) .

The equality that should hold is:
`organization/app whose signature was verified == organization owning the repository the handler mutates`

but the code enforces only:
`organization/app whose signature was verified == params.dig('repository','owner','login') (or organization.login)`
and separately
`repository mutated == payload.dig('repository','full_name')`
with no assertion that these two derived values agree, or that `full_name`'s owner segment matches the verified `repository_owner`.

### Impact Explanation
An attacker with a legitimately-configured (even minimally privileged) GitHub App/organization inside Shipit's multi-org config can forge webhook events that are accepted as validly signed but are attributed to an unrelated, victim-owned repository/stack. This allows triggering `GithubSyncJob` on the victim's stack via forged `push` events, or injecting fabricated commit `Status` records via forged `status` events, on stacks/commits the attacker has no access to — an unauthorized action against a repository the attacker was never authenticated for. This crosses a repository trust boundary (organization that authenticated vs. repository actually written), matching the "unauthorized deploy" surface category.

### Likelihood Explanation
Requires: (1) Shipit configured with more than one GitHub App/organization (a documented, supported configuration), and (2) the attacker controlling or having valid webhook delivery credentials for at least one of those configured organizations/apps (not the victim's). Given multi-org support is a first-class documented feature, this is a realistic deployment scenario, though it does require the operator to have onboarded an organization the attacker controls alongside the victim organization.

### Recommendation
After verifying the signature, re-derive the trusted organization/app and assert that the `repository.full_name` owner segment (and/or `organization.login`) used by handlers matches the organization that successfully verified the signature, rejecting the webhook (422) on mismatch. Do not let handlers independently trust `repository.full_name` without binding it to the already-verified organization context.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `attacker-org` (attacker controls the GitHub App/webhook secret) and `victim-org` (contains the real tracked `Stack`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` over this exact raw body, and sends it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own secret [8](#0-7) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [3](#0-2)  and triggers `sync_github` on the victim's stack, entirely under the attacker's control despite never having produced a signature the victim organization actually issued.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
