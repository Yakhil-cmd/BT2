### Title
BlockToRoot vector fills with duplicate relay-parent entries during relay-parent stalls, silently dropping new storage roots and extending the validity window of stale (possibly revoked) remote-proxy proofs - (File: `pallets/remote-proxy/src/lib.rs`)

### Summary
`OnSystemEvent::on_validation_data` unconditionally `try_push`es every `(block, hash)` pair returned by `RemoteProxyInterface::block_to_storage_root` into the `BoundedVec` `BlockToRoot`, without deduplicating identical `relay_parent_number` values. Because relay-parent repetition across consecutive parachain blocks is a normal condition (async backing routinely produces several parachain blocks on the same relay parent, and relay-chain stalls make it worse), the bounded vector can fill up with duplicate entries for the same block, causing the "we always remove all the old items before, thus there should always be space" assumption to be false, so newer legitimate roots silently fail to be recorded while the stale duplicate root remains queryable via `remote_proxy` for far longer than `MaxStorageRootsToKeep` was designed to allow.

### Finding Description
`on_validation_data` maintains `BlockToRoot` like this: [1](#0-0) 

The eviction logic only prunes entries whose block number is `<= block - MaxStorageRootsToKeep`, i.e. it is a *time/window*-based prune, not a *count*-based or *uniqueness*-based prune. It never checks whether `block` already equals `roots.last().0` before pushing, and the storage type is a fixed-capacity `BoundedVec`: [2](#0-1) 

If `block_to_storage_root` returns the *same* `relay_parent_number` (as it legitimately will across several consecutive parachain blocks under async backing, or during any relay-parent stall — see `RelayChain` proof anchor field usage), each call still does `roots.try_push((block, hash))`, adding a **duplicate row** rather than being deduplicated. Once enough duplicate rows for the same stalled block accumulate to fill the `BoundedVec` to `MaxStorageRootsToKeep` capacity, `try_push` starts returning `Err`, which is discarded: [3](#0-2) 

`debug_assert!` is a no-op in production/release builds, so this failure is completely silent. Crucially, once the vector is saturated with duplicates of stale block `B`, the *next* real block `B+1` will not free space either: `delete_up_to = (B+1) - N` is still smaller than `B` for any `N > 1`, so the while-loop does not evict the `B` duplicates. This condition self-perpetuates until the relay chain advances a full `N` blocks past `B` (`new_block >= B + N`), during which **no new storage root can ever be recorded**, and the stale `B` root remains the newest queryable anchor in `BlockToRoot` for up to `N` extra blocks beyond its intended window.

The unprivileged, attacker-reachable path is `Pallet::remote_proxy` / `remote_proxy_with_registered_proof`, which look up the anchor block via `binary_search_by` against `BlockToRoot::get()`: [4](#0-3) 

Since block `B` is still present (never evicted, never superseded because newer inserts kept failing), a signed attacker can submit `remote_proxy` with `RemoteProxyProof::RelayChain { proof, block: B }`, proving a `ProxyDefinition` that existed at the stale relay block `B` — even though this proxy relationship may have already been revoked at a later, un-recorded relay block — and have it dispatched as `real`.

None of the pallet's existing checks (`UnknownProofAnchorBlock`, trie proof verification, `delay.is_zero()`) address this: the "unknown anchor" check only rejects blocks that are entirely absent from `BlockToRoot`, but `B` is present precisely because of this bug.

### Impact Explanation
The intended security property documented at the top of the file — "the lifetime of a proxy will be `MaxStorageRootsToKeep` in the past" — is violated: the effective window can silently extend well past `MaxStorageRootsToKeep`, and during the widened window no fresh roots are recorded at all, so a revoked-but-still-cached proxy relationship remains authorizable for dispatching arbitrary calls (subject to `InstanceFilter`) as the victim's `real` account.

### Likelihood Explanation
The triggering precondition — repeated/identical `relay_parent_number` across consecutive parachain blocks — is not an exotic attack; it is routine under async backing (multiple parachain blocks per relay block) and guaranteed during any relay-chain block-production stall, both of which are outside attacker control but require no special privilege to observe and exploit. An attacker only needs to wait for such a naturally occurring condition and then submit an ordinary signed `remote_proxy` extrinsic referencing the still-cached stale block. This is realistically reachable, especially on parachains configured with elastic scaling / multiple blocks per relay parent.

### Recommendation
In `on_validation_data`, deduplicate by block number before pushing (e.g., skip the push if `roots.last().map_or(false, |l| l.0 == block)`), and/or evict based on the count of distinct entries rather than solely on the raw block-number window difference, ensuring the invariant "the vector always holds the most recent distinct `MaxStorageRootsToKeep` roots" actually holds even when the same `relay_parent_number` is observed repeatedly. Also stop silently discarding `try_push` errors (`debug_assert!` alone is insufficient for production builds) — handle/replace-in-place instead.

### Proof of Concept
Rust unit test in `pallets/remote-proxy/src/tests.rs` extending `clean_up_works_and_old_blocks_are_rejected`:
```rust
#[test]
fn duplicate_relay_parent_fills_vec_and_drops_new_root() {
    new_test_ext().execute_with(|| {
        let root_old = H256::repeat_byte(1);
        let root_new = H256::repeat_byte(2);

        // Simulate MaxStorageRootsToKeep (10) consecutive parachain blocks
        // built on the SAME relay parent (block 100) — a normal async-backing / stall scenario.
        for _ in 0..10 {
            RemoteProxy::on_validation_data(&PersistedValidationData {
                parent_head: vec![].into(),
                relay_parent_number: 100,
                relay_parent_storage_root: root_old,
                max_pov_size: 5_000_000,
            });
        }

        // Now the relay parent finally advances by one block.
        RemoteProxy::on_validation_data(&PersistedValidationData {
            parent_head: vec![].into(),
            relay_parent_number: 101,
            relay_parent_storage_root: root_new,
            max_pov_size: 5_000_000,
        });

        let roots = BlockToRoot::<Test>::get();
        // BUG: block 101's root was silently dropped because the vec was
        // already full of duplicate (100, root_old) entries that the
        // window-based eviction failed to remove.
        assert!(roots.iter().any(|(b, _)| *b == 101), "newest root was dropped");
        assert!(roots.iter().all(|(b, _)| *b != 100) , "stale root 100 unexpectedly still present");
    });
}
```
Expected (buggy) behavior: the assertion `roots.iter().any(|(b, _)| *b == 101)` fails, proving that the newest legitimate root is dropped while the older duplicate-filled block remains the only queryable anchor — confirming the stale/duplicate accumulation defect described.

	impl<T: Config<I>, I: 'static> OnSystemEvent for Pallet<T, I> {
		fn on_validation_data(validation_data: &PersistedValidationData) {
			let Some((block, hash)) = T::RemoteProxy::block_to_storage_root(validation_data) else {
				return;
			};

			// Update the block to root mappings.
			BlockToRoot::<T, I>::mutate(|roots| {
				let delete_up_to =
					block.clone().saturating_sub(T::MaxStorageRootsToKeep::get().into());

				while roots.first().is_some_and(|f| f.0 <= delete_up_to) {
					roots.remove(0);
				}

				// We always remove all the old items before, thus there should always be space in
				// the vector.
				let _res = roots.try_push((block, hash));
				debug_assert!(_res.is_ok());
			});
