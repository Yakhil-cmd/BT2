### Title
Webhook signature is verified against the organization named in the (unauthenticated) payload's `repository.owner.login`, while every event handler resolves the target repository via `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate the `X-Hub-Signature` against by reading `repository_owner`, which is taken straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the actual repository to act on using a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. Because the field used to select the verifying secret and the field used to select the acted-upon repository are independent and both attacker-controlled, an attacker who knows the `webhook_secret` for one GitHub organization configured in Shipit (e.g., their own org, in a multi-org Shipit deployment as documented in `docs/setup.md`) can forge a signature that is valid for that org while making the payload claim a `repository.full_name` belonging to a completely different, victim organization/repository.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`, where `repository_owner` is derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` only checks that the raw body's HMAC matches the secret of the *organization named in the body itself* - it never asserts that this organization is the one that actually owns the repository the event will be applied to. [3](#0-2) 
- Every event handler (`PushHandler`, and the base `Handler` class used by `PullRequest::*Handler`s, etc.) ignores `repository.owner.login` entirely and instead resolves the repository to act on via `payload.dig('repository', 'full_name')`: [4](#0-3)  and `PushHandler#process` operates on `stacks.not_archived.where(branch:)` derived from that same `stacks` method. [5](#0-4) 
- These two fields (`repository.owner.login` used for auth, `repository.full_name` used for the write) are never cross-checked against each other, and neither is covered by any signature scoping beyond "some configured org's secret matches the raw body." An attacker who is the legitimate owner of one GitHub App/organization onboarded into the same Shipit instance (documented multi-org setup in `docs/setup.md`) knows that org's `webhook_secret` and can compute a valid HMAC over any payload body they construct, including one whose `repository.full_name` names a stack belonging to a different organization.

This breaks the binding: **organization that authenticated == repository that is written**, which the task rules explicitly flag as an in-scope binding.

### Impact Explanation
A forged, validly-signed webhook lets an attacker who administers Org A's GitHub App on a shared Shipit instance push crafted `push` (and other) events that are attributed as authenticated for Org A but whose `repository.full_name` points at Org B's repository/stack. Via `PushHandler`, this reaches `stack.sync_github(expected_head_sha:)` [5](#0-4) , which enqueues `GithubSyncJob` and can alter the recorded commit/deploy state of a stack the attacker does not control, and other handlers (e.g. PR label/unlabel handlers) can archive/unarchive review stacks for repositories the attacker never authenticated for [6](#0-5) . This crosses a repository boundary using credentials scoped to a different repository/organization - an unauthorized cross-repository write.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one GitHub organization/App that is configured in the same multi-tenant Shipit instance (a documented, supported configuration in `docs/setup.md`), which is a plausible "unprivileged w.r.t. the victim org" attacker per the rules (no Shipit session, API token, or victim's webhook secret needed). The only prerequisite is knowledge of one's own org's `webhook_secret`, which the attacker legitimately possesses.

### Recommendation
After verifying the HMAC, re-derive `repository_owner` from the same field the handler will use to select the target repository (`repository.full_name`'s owner segment) and reject the request unless the two agree; alternatively, look up the repository by `full_name` first, resolve its associated organization/app, and verify the signature using that organization's secret exclusively.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App on a Shipit instance also serving `OrgB` (multi-org setup as in `docs/setup.md`), and knows `OrgA`'s `webhook_secret`.
2. Attacker builds a `push` payload: `{"ref": "refs/heads/main", "after": "<attacker-controlled sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "OrgA"`, calls `Shipit.github(organization: "OrgA")`, and the HMAC matches -> request passes. [1](#0-0) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and triggers `sync_github` on `OrgB`'s stack, even though the signature was only ever validated against `OrgA`'s secret. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
