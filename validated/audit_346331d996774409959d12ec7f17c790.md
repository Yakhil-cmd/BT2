### Title
Fee-on-Transfer ERC20 Token Accounting Discrepancy Drains Bridge Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge's `requestERC20Transfer` function pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, but does not verify the actual amount received. When a fee-on-transfer ERC20 token is registered, the bridge receives fewer tokens than expected, yet emits a `RequestValueTransfer` event claiming the full `_value`. The counterpart bridge then releases the full `_value` to the recipient, creating a permanent accounting deficit that drains the bridge's locked liquidity.

---

### Finding Description

`requestERC20Transfer` in `BridgeTransferERC20.sol` executes:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange` (which issues additional `safeTransfer` calls for the bridge fee and feeLimit refund, each also subject to the token's transfer fee), and finally emits `RequestValueTransfer` with the original `_value`: [2](#0-1) 

The fee and refund transfers in `_payERC20FeeAndRefundChange` also deduct from the bridge's balance at face value: [3](#0-2) 

There is no before/after balance check anywhere in this path. The `registerToken` function in `BridgeTokens.sol` imposes no restriction on token type — any ERC20 can be registered: [4](#0-3) 

**Concrete arithmetic (lock mode, `modeMintBurn = false`):**

| Variable | Value |
|---|---|
| `_value` | 100 |
| `_feeLimit` | 0 (simplest case) |
| Token transfer fee rate | 10% |

1. `safeTransferFrom(user, bridge, 100)` → bridge receives **90** tokens.
2. `_payERC20FeeAndRefundChange` with `_feeLimit = 0` → no further transfers.
3. Bridge balance locked: **90** tokens.
4. `RequestValueTransfer` emitted with `_value = 100`.
5. Counterpart bridge operators call `handleERC20Transfer` with `_value = 100`.
6. Counterpart bridge executes `IERC20(_tokenAddress).safeTransfer(_to, 100)` — releasing **100** tokens. [5](#0-4) 

Each round-trip request creates a **10-token deficit** in the source bridge's pool. Repeated transfers progressively exhaust the bridge's liquidity until it cannot fulfill legitimate withdrawal requests.

---

### Impact Explanation

- **Asset impact:** The source-chain bridge's locked ERC20 balance is systematically under-funded relative to the obligations recorded in cross-chain events. Users who later bridge tokens back to the source chain will find the bridge insolvent — their `handleERC20Transfer` calls will revert due to insufficient balance, permanently locking their funds on the counterpart chain.
- **Scope:** Unauthorized effective transfer of bridged assets; bridge liquidity corruption affecting all users of the affected token pair.

---

### Likelihood Explanation

- The bridge owner must register a fee-on-transfer token (a valid, unrestricted owner action — `registerToken` has no token-type guard).
- Once registered, **any unprivileged user** can call `requestERC20Transfer` to trigger the discrepancy.
- Fee-on-transfer tokens (STA, PAXG, and future USDC/USDT variants) are real, deployed assets. The vulnerability is latent in every bridge deployment that registers such a token.

---

### Recommendation

Record the bridge's token balance before and after the `safeTransferFrom` call and use the actual received amount as the canonical transfer value:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value, "fee-on-transfer: insufficient received");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, maintain a token whitelist that explicitly excludes fee-on-transfer, rebasing, and deflationary tokens.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` with a 10% transfer fee.
2. Bridge owner calls `registerToken(FeeToken, cFeeToken)` on the source bridge.
3. User approves the source bridge for 100 `FeeToken` and calls:
   ```
   requestERC20Transfer(FeeToken, recipient, 100, 0, "0x")
   ```
4. Source bridge receives 90 `FeeToken` (10% fee deducted by the token).
5. Bridge emits `RequestValueTransfer(..., value=100, ...)`.
6. Counterpart bridge operators call `handleERC20Transfer(..., value=100, ...)`.
7. Counterpart bridge transfers 100 tokens to `recipient` (recipient gets 90 due to fee again, but bridge balance decreases by 100).
8. Source bridge balance: **90** locked. Counterpart bridge balance: **−100** (net).
9. Repeat 10 times: source bridge has 900 locked, counterpart has released 1000 — **100-token deficit**.
10. Any user attempting to bridge back 100 tokens will cause `handleERC20Transfer` on the source bridge to revert with insufficient balance. [6](#0-5) [7](#0-6)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
