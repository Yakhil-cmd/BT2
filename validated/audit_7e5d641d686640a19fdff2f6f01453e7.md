### Title
Recipient-Controlled Revert in `handleKLAYTransfer` Permanently Locks Bridged KAIA and Stalls Nonce Accounting — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge updates nonce state and then makes an external call to the recipient address. If the recipient is a contract whose fallback reverts, the `require(ok)` guard rolls back the entire transaction — including the nonce update — leaving the nonce permanently unhandleable. Because `lowerHandleNonce` never advances past the stuck nonce, `recoveryBlockNumber` is frozen and the bridged KAIA for that request is locked in the bridge contract indefinitely.

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` follows this sequence:

```solidity
// 1. Nonce state written
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

// 2. External call to recipient
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");   // ← reverts everything above
``` [1](#0-0) 

When `_to` is a contract whose fallback reverts, `ok` is `false` and `require` rolls back the entire transaction. All nonce state written in steps 1 is undone. The nonce is never consumed.

`_updateHandleNonce` advances `lowerHandleNonce` only when consecutive nonces starting from `lowerHandleNonce` are present in `handleNoncesToBlockNums`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because the stuck nonce's entry is never written, `lowerHandleNonce` never advances past it and `recoveryBlockNumber` is frozen at its initial value.

With a multi-operator threshold, operator 1's vote is committed in a separate transaction and is not rolled back when operator 2's threshold-crossing call reverts. Operator 2 can retry indefinitely, but every attempt reverts. The nonce is permanently unresolvable without an admin skip mechanism — which does not exist in this contract.

### Impact Explanation

1. **KAIA locked**: The KAIA allocated to the stuck nonce remains in the bridge contract forever; the intended recipient can never receive it.
2. **`recoveryBlockNumber` frozen**: The bridge recovery scanner always re-scans from block 1, causing unbounded re-processing overhead and preventing the recovery mechanism from making forward progress.
3. **`lowerHandleNonce` stuck**: Nonce accounting is permanently corrupted. Although `_lowerHandleNonceCheck` does not enforce an upper bound, the stuck `lowerHandleNonce` means the bridge's canonical "lowest unhandled nonce" pointer is wrong indefinitely.

These are unauthorized effects on bridged KAIA assets and bridge nonce/state integrity.

### Likelihood Explanation

Any user who initiates a KLAY bridge transfer can set `_to` to a contract they control that reverts on receiving KLAY. No special privilege is required. The attacker only needs to submit one bridge request on the source chain. The cost is the gas for the request transaction plus the KLAY amount (which they lose, but the bridge is stalled). A motivated attacker can do this deliberately; it can also happen accidentally if the recipient is a contract not designed to receive KLAY.

### Recommendation

Apply the same fix class as H02: decouple the external call from the nonce-advancement path.

**Option A — Pull pattern**: Record the owed amount in a mapping and let the recipient claim it separately. Nonce advancement is unconditional.

**Option B — Non-reverting delivery**: Replace `require(ok)` with a logged failure and advance the nonce regardless:
```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    emit KLAYTransferFailed(_requestedNonce, _to, _value);
    // optionally credit to a recoverable escrow
}
```

**Option C — Operator skip**: Add an owner-callable function to forcibly advance `lowerHandleNonce` past a stuck nonce, similar to PoolTogether's `rollover` (though this introduces discretionary admin power and should be a last resort).

### Proof of Concept

1. Attacker deploys `Rejecter` on the child chain:
   ```solidity
   contract Rejecter { receive() external payable { revert(); } }
   ```
2. Attacker calls `requestKLAYTransfer(address(rejecter), value, "")` on the parent-chain bridge, paying `value + fee`. This emits `RequestValueTransfer` with `requestNonce = N`.
3. Bridge operators observe the event and call `handleKLAYTransfer(..., address(rejecter), value, N, ...)` on the child-chain bridge.
4. The call reaches `_to.call.value(_value)("")` → `Rejecter.receive()` reverts → `ok = false` → `require(ok)` reverts the entire transaction.
5. `handleNoncesToBlockNums[N]` is never set; `lowerHandleNonce` stays at `N`; `recoveryBlockNumber` is frozen.
6. Operators retry indefinitely; every attempt reverts. The `value` KAIA is permanently locked in the bridge. The recovery scanner re-scans from block 1 on every cycle. [3](#0-2) [4](#0-3)

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

    function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
        require(lowerHandleNonce <= _requestedNonce, "removed vote");
    }
