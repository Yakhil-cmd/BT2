### Title
Fork-controlled PR label names inject arbitrary environment variables (e.g. `GEM_HOME`, `GIT_SSH_COMMAND`) into `git` subprocess env in `StackCommands#fetch`/`#git_clone` — RCE on deploy host - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment key with no allowlist, and `LabelCapturingHandler#capture_labels` persists those label names verbatim from the webhook body. Because `StackCommands#env` merges `@stack.env` unfiltered and passes it straight into `git` invocations executed by `Command#start` (`PTY.spawn`), a PR author on `allow_all` review stacks can set arbitrary process environment variables — including git-honoured variables like `GIT_SSH_COMMAND`/`GIT_ASKPASS` or `GEM_HOME` — for the `git fetch`/`git clone` subprocess run on the Shipit host.

### Finding Description
The intended binding is: the environment reaching a `git` invocation in `StackCommands#fetch`/`#git_clone` should equal `Shipit.env.merge(stack.env-fixed-keys)`, filtered the same way deploy/rollback/task-trigger envs are filtered via `EnvironmentVariables.permit(variable_definitions)` (see `app/controllers/shipit/deploys_controller.rb:67`, `app/controllers/shipit/rollbacks_controller.rb:30`, `app/models/shipit/task_definition.rb:63-65`). In reality, for `ReviewStack`, this binding is broken:

- `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the base stack env with **no key allowlist whatsoever**.
- `LabelCapturingHandler#capture_labels` [2](#0-1)  writes `params.pull_request.labels.map(&:name)` straight from the webhook JSON body into `pull_request.labels`, and the params schema only requires `name` be a `String` [3](#0-2)  — no character/format restriction.
- `StackCommands#env` [4](#0-3)  merges `@stack.env` unfiltered, and this `env` is passed directly into the `git` calls in `#fetch` and `#git_clone` [5](#0-4) [6](#0-5) .
- `Command#unbundled_env` builds the full subprocess environment by merging `@env.stringify_keys` on top of `BASE_ENV`/`PATH` with **no filtering**, and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) , meaning `@env` becomes (effectively) the complete process environment for the spawned `git` binary.

Exploit flow: an attacker opens a pull request against a repository configured with `provisioning_behavior: allow_all` and `review_stacks_enabled: true`. `OpenedHandler#process` auto-creates the `ReviewStack` with no label requirement under `allow_all` [8](#0-7) . The attacker labels their PR `gem_home` (or `git_ssh_command`); GitHub emits a `pull_request` `labeled` webhook, `LabelCapturingHandler` persists `"gem_home"` into `pull_request.labels` unmodified. On the next deploy/fetch cycle, `PerformTaskJob`/`TaskExecutionStrategy::Default#checkout_repository` calls `@commands.fetch`/`@commands.fetched?` [9](#0-8) , which is `StackCommands#fetch`, whose `env:` now contains `"GEM_HOME" => "true"` (or `"GIT_SSH_COMMAND" => "true"`), unfiltered, reaching the spawned `git` process.

Existing guards that prevent this elsewhere do not apply here: `EnvironmentVariables.permit` is only invoked for deploy/rollback/task-trigger custom variables originating from `params` (controller-level, allowlisted against `shipit.yml`-declared variable names) — it is never applied to `Stack#env`/`ReviewStack#env`, which is the exact code path feeding `StackCommands#fetch`/`#git_clone`. `Repository`/`Stack` validations constrain `environment`/`branch`/`deploy_url`, but nothing constrains PR label content, and the webhook `params` schema (`requires :labels, Array do requires :name, String end`) permits any string.

### Impact Explanation
An attacker with only the ability to open a PR and label it on their own fork can inject arbitrary environment variables into the `git` subprocess spawned on the Shipit host for that repository's review stack. Git honours several security-sensitive environment variables (`GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, etc.) that can be used to execute arbitrary commands as the Shipit process user, which is Critical: Remote Code Execution on the deploy host, matching the stated impact category directly. It is repeatable on every fetch/clone cycle for that stack and, since any `allow_all` repository is affected identically, across every tenant repository configured that way.

### Likelihood Explanation
Requires only: a repository with `review_stacks_enabled: true` and `provisioning_behavior: allow_all` (a supported, documented configuration, not a misconfiguration outside the engine's control), and an attacker who can open/label a PR on that repository (or their own fork feeding into it). No Shipit credentials, GitHub App keys, or maintainer status are needed. Cost is a single PR + one label. This is directly demonstrated by existing repo tests showing arbitrary uppercase label names becoming env keys, e.g. `test/models/shipit/review_stack_test.rb:59-65` and `test/lib/shipit/task_commands_test.rb:6-16`, which already assert `env["WIP"] == "true"` style injection — the only missing piece is naming the label after a security-sensitive variable such as `GEM_HOME`/`GIT_SSH_COMMAND`.

### Recommendation
Apply an explicit allowlist to `ReviewStack#env`/`Stack#env` before merging into `StackCommands#env`, analogous to `EnvironmentVariables.permit`, rejecting or dropping any derived key matching reserved/security-sensitive names (`GIT_*`, `GEM_HOME`, `LD_PRELOAD`, `PATH`, `BUNDLE_*`, etc.), or require a `shipit.yml`-declared allowlist of accepted label names before they are promoted to environment variables at all.

require "test_helper"

module Shipit
  class StackCommandsGemHomeInjectionTest < ActiveSupport::TestCase
    test "a PR label name reaches the git fetch subprocess env unfiltered" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.update!(labels: ["gem_home"])

      command = StackCommands.new(stack).fetch

      # Binding under test: git subprocess env should equal an allowlisted set,
      # but instead contains the attacker-controlled key verbatim.

        "PR label name should not be able to set GEM_HOME in the git subprocess environment"
    end
  end
end
