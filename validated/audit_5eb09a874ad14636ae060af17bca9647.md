### Title
Multi-organization webhook signature verification does not bind the authenticated organization to the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate an inbound webhook's HMAC signature using `repository_owner`, a value read directly out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to mutate using a *different* field of the same body: `repository.full_name`. Because the two fields are never cross-checked, the binding "organization whose secret validated this signature" == "repository the handler will write to" is not enforced.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the JSON payload the caller supplies, and it is used only to select *which* configured GitHub organization's `webhook_secret` (`Shipit.github(organization:)`) is used to verify the HMAC: [3](#0-2) 

Once the signature passes, `create` dispatches the whole raw payload to every registered handler for that event type without any further organization/repo consistency check: [4](#0-3) 

Every handler, however, determines the target repository/stack from a separate field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because Shipit supports one webhook secret *per organization* (`config.github.<org>.webhook_secret`), a tenant who legitimately owns/administers their own GitHub App integration into this shared Shipit instance (i.e. controls only their own organization "OrgB" and its `webhook_secret`) can sign an arbitrary JSON payload with `organization.login`/`repository.owner.login` = `"OrgB"` (so `verify_signature` selects and validates against OrgB's own secret) while setting `repository.full_name` to `"OrgA/some-private-repo"` — a repository/stack belonging to a completely different, unrelated organization "OrgA" that this attacker has no access to. The signature check only proves the request was signed by *some* configured organization's secret; it never proves that organization owns the repository named in `repository.full_name` that the handler will act on.

This is a direct analog of the reported bug class: a value used to derive the "trust" decision (which secret validates the request) is not the same value that is actually acted upon downstream, and the verified signature does not cover/bind the field that determines impact.

### Impact Explanation
Exploiting this lets a tenant organization forge events against any other organization's repository/stack tracked by the same Shipit instance, for every handler registered in `Shipit::Webhooks::DEFAULT_HANDLERS`, including:
- `push` → forces `stack.sync_github(expected_head_sha:)` on an arbitrary stack (`app/models/shipit/webhooks/handlers/push_handler.rb`), which can be used to manipulate another tenant's commit history state used to gate deploys.
- `status` → writes a `Status` for an arbitrary commit sha on another org's stack via `Shipit::Repository.from_github_repo_name(repository.full_name)`, which can be leveraged to set the CI status Shipit relies on (`ci.require`) to satisfied/green for a repo the attacker does not control, enabling an **unauthorized deploy** on that victim stack.
- `pull_request` (`closed`, `labeled`, etc.) → archives/unarchives another tenant's review stacks.
- `membership` → creates arbitrary `User`/`Team` records tied to another org.

This crosses the "unauthorized deploy" / cross-repository-write impact tier defined in scope, because a caller who is only authorized for organization B's webhook secret is able to mutate state (commit statuses, stacks, review-stack lifecycle) belonging to organization A.

### Likelihood Explanation
This only manifests when a Shipit deployment is configured with the multi-organization `github:` schema (`github: { orgA: {...}, orgB: {...} }`, as documented in `docs/setup.md`), which is an explicitly supported and documented configuration for exactly this "multiple GitHub organizations" use case. In that mode, every onboarded organization is, by construction, an independent "unprivileged" tenant relative to every other organization's repositories, and each tenant necessarily knows the `webhook_secret` for its own GitHub App/organization entry (they configure it when installing their App). No secret theft, session, or privileged Shipit account is required — only the ability to craft and send an HTTP POST to `/github_hooks` with a body they've HMAC-signed using their own org's known secret.

### Recommendation
In `WebhooksController#verify_signature` / `create`, after verifying the signature, cross-validate that the resolved `repository_owner` used to select the signing organization actually matches the owner encoded in `repository.full_name` (or `organization.login`) before dispatching to handlers, rejecting (422) any payload where these disagree. More robustly, each `Handler` should resolve the repository using the same organization value that was cryptographically verified, and reject processing if `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s owner does not equal the verified `repository_owner`.

### Proof of Concept
Given a Shipit instance configured with:
```yaml
github:
  orgA:
    webhook_secret: secretA
  orgB:
    webhook_secret: secretB
```
An attacker who administers `orgB` (and thus knows `secretB`) sends:
```
POST /github_hooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(secretB, body)>

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgA/victim-repo", "owner": { "login": "orgB" } },
  "organization": { "login": "orgB" }
}
```
`verify_signature` resolves `repository_owner` = `"orgB"` (from `repository.owner.login`), fetches `Shipit.github(organization: "orgB")`, and validates the signature successfully against `secretB`. `StatusHandler` then resolves the target repository from `repository.full_name` = `"orgA/victim-repo"` and writes a `Status` record for `orgA`'s commit, satisfying a required CI check the attacker has no legitimate access to — enabling deploys on `orgA`'s stack to proceed.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
