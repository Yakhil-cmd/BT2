### Title
Webhook signature verification is bound to an attacker-chosen `repository_owner` field, while the acted-upon repository/commit is taken from an unrelated payload field — cross-repository forged webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to authenticate an incoming webhook based on `repository_owner`, a value read straight out of the **unverified** JSON body [1](#0-0) . Once that check passes, the handler that actually acts on the payload picks its target repository/commit from a **completely separate** field of the same body (`repository.full_name`, or, in `StatusHandler`, only `sha` with no repository scoping at all) [2](#0-1) [3](#0-2) . In a multi-organization deployment, if any configured organization has no `webhook_secret` (a supported, documented configuration — see `docs/setup.md` "Using Multiple Github Applications" and the example configs shipping `webhook_secret: # nil`), signature verification for that organization always succeeds regardless of the actual signature [4](#0-3) . An unauthenticated attacker can therefore craft a payload that claims to originate from that unsecured organization while pointing its `repository`/`sha` fields at a completely different, secured repository managed by Shipit, and have it processed as authentic.

### Finding Description
The trust binding that should hold is:
`organization whose secret verified the signature == repository/commit the handler writes to`

This binding is broken:

1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` — both taken from the raw, unauthenticated body — and uses it purely to pick which `GitHubApp`/secret to check the signature against [5](#0-4) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured [6](#0-5) . This is a legitimate, documented per-organization configuration state (`test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml` both ship with `webhook_secret: # nil`), not a misconfiguration outside the engine's own code [7](#0-6) .
3. Once `verified` is `true`, `create` dispatches to handlers using `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) , and handlers resolve their target repository from `payload.dig('repository', 'full_name')` — a field that is never cross-checked against `repository_owner` [2](#0-1) .
4. `StatusHandler` is worse still: it doesn't even scope by repository — it looks up `Commit.where(sha: params.sha)` across the entire installation and calls `commit.create_status_from_github!(params)` on every match [3](#0-2) .

Because the "authenticating organization" (whatever unsecured org is named in `repository.owner.login`/`organization.login`) is never required to equal the "repository being written to" (`repository.full_name`, or in the status case, nothing at all), any Shipit instance with even one multi-org entry lacking a `webhook_secret` allows an unauthenticated attacker to inject forged `push`, `pull_request`, `check_suite`, and `status` events for any *other* stack/repository configured in the same instance.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar:
- Forged `push` events cause `PushHandler` to call `stack.sync_github(expected_head_sha:)` for stacks on a target repository the attacker does not control, which can trigger `GithubSyncJob` and continuous deployment for a stack unrelated to the (secret-less) organization used to pass authentication [9](#0-8) .
- Forged `status` events let an attacker create arbitrary commit statuses on any commit in the system (`Commit.where(sha: params.sha)` is unscoped by repository), which can satisfy CI/status gating relied upon by continuous deployment/merge-queue logic for a repository the attacker has no access to [3](#0-2) .
- Forged `pull_request` events can create/archive/unarchive review stacks for arbitrary repositories via `ReviewStackAdapter` [10](#0-9) .

### Likelihood Explanation
Requires only: (a) the Shipit deployment to use the documented multi-organization `github:` config, and (b) at least one configured organization to have no `webhook_secret` set — an explicitly supported and exemplified configuration in this engine's own docs and shipped example/test config files. No credentials, tokens, or GitHub App keys are needed by the attacker; the webhook endpoint is public and unauthenticated by design.

### Recommendation
- After verification, require that the field used to select the signing organization (`repository_owner`) matches the repository/organization actually acted upon by each handler (`payload.dig('repository', 'full_name')`'s owner), rejecting mismatches.
- Scope `StatusHandler#process` (and any other handler) lookups to the repository referenced in the payload rather than doing an unscoped `Commit.where(sha:)` lookup across all stacks.
- Consider disallowing/warning on organizations configured without a `webhook_secret` in a multi-org setup, since a single unsecured entry undermines the authentication boundary for every other organization's repositories in the same instance.

### Proof of Concept
1. Configure Shipit with two organizations: `UnsecuredOrg` (no `webhook_secret`) and `SecuredOrg/target-repo` (has a stack tracked by Shipit).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<real-sha-of-a-commit-on-SecuredOrg/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "UnsecuredOrg" } }
}
```
3. `verify_signature` resolves `repository_owner` to `UnsecuredOrg`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) [4](#0-3) .
4. `StatusHandler` then finds and updates the commit belonging to `SecuredOrg/target-repo` because its lookup is unscoped by repository [3](#0-2) , creating an unauthorized "success" status that can unblock CI-gated deploys for a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
