## Finding

The report's underlying issue — a `mint()` entry point that accepts a `0` amount, performs no real state change, but still unconditionally emits a `Minted`/`Issued` style event — has a direct, provable analog in `pallet-assets`.

### Title
`pallet-assets::mint()` allows minting with amount `0`, emitting a spurious `Issued` event with no state change - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
The `mint` extrinsic in `pallet-assets` lets a signed account (the asset's `Issuer` — a role any user can assign to themselves by creating their own asset class) mint an `amount` of `0`. The dispatch succeeds and emits `Event::Issued { asset_id, owner, amount: 0 }` even though no balance or supply actually changed.

### Finding Description
The public extrinsic `mint` forwards directly to `do_mint` without any check that `amount > 0`: [1](#0-0) 

`do_mint` first calls `increase_balance`, which is documented as a no-op when `amount.is_zero()` and returns `Ok(())` immediately without touching `Account` or `Asset` storage: [2](#0-1) 

However, `do_mint` unconditionally emits the `Issued` event after calling `increase_balance`, regardless of whether `amount` was zero and regardless of whether any state actually changed: [3](#0-2) 

This is the same root-cause class as the reported bug: a public mint entry point takes a user-supplied `amount` with no lower-bound check, silently succeeds for `amount == 0`, performs no effective mutation, yet still emits a "successful mint" event for off-chain consumers (indexers, exchanges, notification systems) to observe.

Note that this differs from `pallet-balances`, where the equivalent issue was already fixed: `PositiveImbalance::drop` and `Currency::issue`/`burn` explicitly check `is_zero()` before emitting `Issued`/`Rescinded` events, per the historical fix documented in `prdoc/stable2412/pr_5946.prdoc`: [4](#0-3) 

`pallet-assets::do_mint` never received the equivalent guard.

### Impact Explanation
Off-chain systems that treat `Issued`/`Minted` events as proof of an actual balance change (e.g., triggering deposit confirmations, updating displayed balances, or firing webhooks) can be misled by a zero-amount event that corresponds to no real supply or balance increase. This matches the Medium-severity impact in the original report: it does not directly cause fund loss but can corrupt off-chain integrations' state/assumptions. There is no theft, unauthorized dispatch, or consensus-breaking effect — the on-chain storage itself remains correct because `increase_balance` genuinely no-ops for zero amounts.

### Likelihood Explanation
Any account that is the `Issuer` of an asset (which any user can become by permissionlessly creating their own asset class via `create`/`force_create` and being assigned as issuer) can trivially call `mint(id, beneficiary, 0)` at will, at negligible cost (only transaction fees), with no special privilege over other users' assets. This is fully attacker-reachable through a normal signed extrinsic.

### Recommendation
Add an `ensure!(!amount.is_zero(), Error::<T, I>::...)` check in the `mint` extrinsic (or in `do_mint` before emitting the event), mirroring how `pallet-balances` guards `Issued`/`Rescinded` emission on `is_zero()`, so that zero-amount mints either revert or silently no-op without emitting `Issued`.

### Proof of Concept
- Guard checked: none — `mint()` → `do_mint()` has no `amount > 0` requirement before calling `deposit_event(Event::Issued { .. amount .. })`.
- Reachability: `mint` is a standard signed dispatchable; the caller must equal `details.issuer`, a role self-assignable by creating one's own asset (`create`/`create_asset`), so no privileged/governance access is required.
- State evidence: `increase_balance` returns `Ok(())` immediately at `substrate/frame/assets/src/functions.rs:493-495` for `amount.is_zero()`, meaning `Account`/`Asset` storage is provably untouched, while `do_mint` still executes `Self::deposit_event(Event::Issued { asset_id: id, owner: beneficiary.clone(), amount })` unconditionally at line 474.
- No local Rust reproduction was executed against the tooling described in the prompt (only static code inspection); the finding is supported purely by direct code-path tracing through `mint` → `do_mint` → `increase_balance`, which is sufficient to demonstrate the missing check and its consequence (spurious zero-amount event with no matching state mutation).

			}

			Ok(())
		})?;

		Ok(())
	}
