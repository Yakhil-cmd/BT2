### Title
`Commit.where(sha:)` in `StatusHandler#process` writes CI status onto commits across all repositories/stacks sharing that SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike the base `Handler` class which exposes a `stacks` helper scoped by `payload.dig('repository', 'full_name')`. Any commit sharing that SHA in any stack (e.g. via a fork with identical git history) receives the attacker's status, and on a stack with `merge_queue_enabled: true` this can flip deployability and drive `stack.schedule_merges` / `merge!`.

### Finding Description
The claimed invariant is: `status.context == 'ci/smoke' AND status.sha == commit.sha` should only ever update `commit.stack == Repository.from_github_repo_name(webhook.payload.repository.full_name).stacks`. Instead, `StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This bypasses the `stacks`/`repository_name` scoping helper defined on the base `Handler` class: [2](#0-1) 

`Commit#sha` is a bare SHA1 string with no repository component in the WHERE clause, and `Commit` belongs to a `stack`, not a `repository` uniqueness scope; `Commit.where(sha:)` matches any commit row across any stack in the installation whose `sha` column equals the attacker-supplied value.

`WebhooksController#verify_signature` verifies the HMAC signature using the webhook secret associated with `repository_owner` (`Shipit.github(organization: repository_owner)`), i.e., the org that owns the repository which sent the webhook [3](#0-2) . This only proves the webhook genuinely came from GitHub for *some* repo owned by that org — it does not scope which `Commit` rows the handler is allowed to mutate. So a legitimate, correctly-signed webhook from an attacker-owned repository can still poison a victim's stack, as long as a `Commit` row with the same SHA exists there.

Exploit flow:
1. Attacker forks/clones a public victim repository (or otherwise reproduces an identical commit object — git SHA1s are content-addressed, so a commit copied byte-for-byte into another repo retains the same SHA).
2. Attacker pushes that commit to their own repository and creates/updates a `status` (`context: ci/smoke`, `state: success`) on it via any means they control (their own CI, their own webhook-emitting script, or GitHub Actions in their fork).
3. GitHub sends a `status` webhook to Shipit, correctly signed for the attacker's own org/repo.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which also matches the victim stack's `Commit` row with the identical SHA (created there from a legitimate push/PR).
5. `commit.create_status_from_github!(params)` -> `add_status` recomputes `Status::Group`, and if the new simple_state differs, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [4](#0-3) . On a stack with `merge_queue_enabled: true`, a now-green head can advance the merge queue and trigger `merge!`, or conversely a forged failing/error status can block a legitimate deploy (`deployable?` depends on `success?` and `blocked?`) [5](#0-4) .

Existing guards do not prevent this: `verify_signature` authenticates the sender's org, not the target commit's owning stack; `ExplicitParameters` only validates the shape of `sha`/`state`/`context` strings, not their relationship to any repository; there is no `require_permission!`/`stacks` scoping check inside `StatusHandler` (contrast with the base `Handler#stacks` helper that does scope by `repository_name`, but which `StatusHandler` does not use).

### Impact Explanation
An attacker who controls a repository (any GitHub user) can inject arbitrary CI status (`success`/`failure`/`error`) onto any `Commit` row in any tenant's stack that happens to share a SHA with a commit they control, without holding any Shipit credential. Because commit deployability (`deployable?`, `blocked?`) and merge-queue advancement (`schedule_merges`/`merge!`) key off status state, this is a payload from one repository mutating another's stack/commit and can force an unauthorized deploy, rollback-relevant block, or merge — squarely a Critical-severity finding ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The attack is repeatable against any stack whose commits are (or can be made) SHA-colliding with attacker-controlled content, and scales across all tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the victim stack must have a `Commit` row with the exact SHA the attacker can produce and sign a webhook for. This is trivial for public open-source repositories (fork the repo, the commit SHAs are identical), or for any repository whose commits get mirrored/rebased into a repo the attacker controls. No merge_queue_enabled requirement is needed for a status flip to occur at all — merge_queue_enabled simply upgrades the impact from "commit UI status flip" to "forced merge/ship". Attacker cost is minimal: fork, push (or fabricate) a commit, and cause a `status` event, which GitHub will legitimately sign. This is realistically exploitable, not theoretical.

### Recommendation
Scope the commit lookup by both the reporting repository and SHA. In `StatusHandler#process`, use the `stacks`/`repository_name` helper already available on the base `Handler` (or an equivalent), e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
i.e., only update commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, mirroring the pattern other handlers (`push_handler.rb`, `check_suite_handler.rb`) already use via `Handler#stacks`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repo_a` (`Repository`, owner `attacker/repo`) and `stack_a` on it; create `repo_v` (`Repository`, owner `victim/repo`) and `stack_v` with `merge_queue_enabled: true` and a `required_statuses`/`ci/smoke` requirement.
2. Create `Commit` `c_v` on `stack_v` with `sha: "deadbeef...".` Do NOT create any commit on `stack_a` with that SHA (simulating: only the *webhook payload's* `repository.full_name` is `attacker/repo`, but no `Commit` row tied to `repo_a`'s stack exists with that SHA — this is what makes the write "unscoped").
3. Build a `status` webhook payload: `{ repository: { full_name: 'attacker/repo' }, sha: c_v.sha, context: 'ci/smoke', state: 'success' }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `c_v.reload.status.success?` is `true` even though the payload's `repository.full_name` (`attacker/repo`) never equals `stack_v.repository.full_name` (`victim/repo`) — i.e. `payload.repository.full_name != commit.stack.repository.full_name` yet `commit.status` changed.
6. Additionally assert `stack_v.schedule_merges` (or `merge!`) was invoked/enqueued as a result, demonstrating the merge-queue side effect from an unrelated repository's webhook.
