### Title
Inconsistent sequence/finality filtering between `in_data_feed` and `data_feed` allows an AA to treat a double-spent (non-serial) oracle post as valid data - (File: data_feeds.js)

### Summary
`data_feeds.js` implements two related lookup paths used by AA formulas: `dataFeedExists()` (backs `in_data_feed[[...]]`) and `readDataFeedValue()` (backs `data_feed[[...]]`). Both scan `storage.assocUnstableMessages` to let an AA see not-yet-stable data-feed messages posted by an oracle address (including `this_address`, i.e. a self-chained AA). `readDataFeedValue()` explicitly excludes units whose `sequence` is not `'good'`, but `dataFeedExists()` performs no such check at all. This is the same class of issue as the reported "grace-period enforcement inconsistency": one code path enforces a freshness/validity guard while a sibling path that answers a closely related question does not, so the two can disagree about whether a piece of externally-supplied data is currently trustworthy.

### Finding Description
In `dataFeedExists()` [1](#0-0)  the loop over unstable AA messages only filters by `objUnit.bAA`, `latest_included_mc_index` bounds, and author address — it never inspects `objUnit.sequence`.

In `readDataFeedValue()`, the equivalent loop explicitly skips units that are not `sequence === 'good'`: [2](#0-1) .

Both functions are reachable from AA oscript formulas evaluated during trigger/response processing:
- `in_data_feed[[...]]` → `dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, mci, bAA, cb)` [3](#0-2) 
- `data_feed[[...]]` → `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, ...)` [4](#0-3) 

Since `sequence` (good/temp-bad/final-bad) is assigned to a unit as soon as a conflicting spend (double-spend) is detected — before the unit becomes stable — a still-unstable, currently non-serial unit remains present in `storage.assocUnstableMessages` and is fully visible to `dataFeedExists()`. Because `dataFeedExists()` does not check `sequence`, a `data_feed` message carried by a double-spend loser unit will still satisfy `in_data_feed[[...]]`, even though the same value is correctly excluded from `data_feed[[...]]` by `readDataFeedValue()`'s sequence filter.

### Impact Explanation
An AA author frequently uses `in_data_feed[[...]]` as a pre-check/gate before trusting `data_feed[[...]]`, or uses `in_data_feed` alone as a boolean condition governing fund release, state transitions, or branch selection. Because the two primitives can disagree on the validity of the exact same unstable message, an attacker (as an unprivileged AA-trigger sender or as an oracle-referenced `this_address`/self-chained AA) can craft a double-spending unit carrying a `data_feed` message so that:
- `in_data_feed[[...]]` reports `true` for a value that is really only backed by a non-serial (invalid) unit, while
- `data_feed[[...]]` for the same oracle/feed/value would correctly return "not found."

This lets an attacker force an AA down a code path that assumes the presence check (`in_data_feed`) implies the value is retrievable/valid data, when in fact it is backed by a unit that will never contribute that value once sequence is finalized. Depending on the AA's logic (e.g., "if in_data_feed then release funds using a computed amount", or gating an unlock condition), this can lead to AA fund loss, incorrect state transitions, or a stuck/inconsistent AA state — a concrete fund-safety impact reachable purely by posting units, consistent with Medium severity.

### Likelihood Explanation
The only privilege required is the ability to post two conflicting (double-spending) units, one of which carries a `data_feed` payload from an address the target AA trusts as an oracle (including the common `this_address`/self-referential oracle pattern used for AA-to-AA data chaining). This is achievable by any ordinary unit poster who controls the private key of the referenced oracle address, or by an AA-author-controlled AA that self-references its own author address, and by the AA's own trigger senders when the AA is written to accept `trigger.address` (or similar attacker-controlled input) as the oracle parameter in `in_data_feed[[...]]`. Because `dataFeedExists()`'s bAA-branch has no explicit gate preventing a non-serial-sequence unit from counting, the timing window (before the double-spend resolves to stable) is enough to trigger the inconsistency during AA trigger processing.

### Recommendation
Add the same sequence filter used in `readDataFeedValue()` to `dataFeedExists()`'s unstable-message scan, i.e. skip units where `objUnit.sequence !== 'good'` in the loop at [1](#0-0) , so that `in_data_feed[[...]]` and `data_feed[[...]]` agree on which unstable messages are eligible to be considered valid oracle data. More generally, ensure any new/AA-facing predicate over `assocUnstableMessages` uses one shared "is this unstable message eligible" helper (bAA/author-address/mci-range/**sequence**) so future additions cannot silently diverge from the existing filters.

### Proof of Concept
1. Deploy an AA whose bound/response formula includes a branch such as:
   `if (in_data_feed[[oracles=trigger.address, feed_name='ready', feed_value=1]]) { ... release/trigger action ... }`
   without also confirming via `data_feed[[oracles=trigger.address, feed_name='ready']]`.
2. Attacker (as `trigger.address`) crafts unit A that spends output X and also carries `data_feed` message `{ready: 1}`, and simultaneously broadcasts conflicting unit B that also spends output X (double-spend). One of A/B will be marked `sequence != 'good'` once the conflict is detected, while both remain in `storage.assocUnstableMessages` pending stabilization.
3. Attacker sends an AA trigger unit that, in its bound formula, evaluates `in_data_feed[[oracles=trigger.address, feed_name='ready', feed_value=1]]` while unit A/B is still unstable.
4. Per `dataFeedExists()` [1](#0-0) , the loop finds the `data_feed` message regardless of its unit's `sequence`, returning `true`, even though the same message's unit may be the double-spend loser.
5. Confirm by comparing with `data_feed[[oracles=trigger.address, feed_name='ready']]` evaluated at the same MCI via `readDataFeedValue()` [2](#0-1)  — it correctly excludes the non-serial unit's message, demonstrating the two primitives disagree on validity of identical underlying data, allowing the attacker to abuse the AA branch gated by `in_data_feed`.
