### Title
Cross-tenant CI status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate against using a field taken from the *same* untrusted JSON body: `repository_owner` = `params.dig('repository', 'owner', 'login')`. [1](#0-0) 

In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each GitHub organization has its own independent `webhook_secret`. Any legitimate customer/org admin who owns their own installation therefore legitimately knows their own org's `webhook_secret` and can compute a valid `X-Hub-Signature` HMAC over **any** JSON body they choose, as long as `repository.owner.login` in that body equals their own org — this makes `Shipit.github(organization: repository_owner)` pick their own (correctly-known) secret. [2](#0-1) 

The `status` event is then dispatched to `StatusHandler`, whose `process` method resolves the target `Commit` **only by `sha`**, with no scoping to the `repository`/`organization` that was authenticated by the signature:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This breaks exactly the binding class targeted by this scan: **the organization that authenticated the webhook (via its own `webhook_secret`) ≠ the repository/stack whose data is written** (`Commit`/`Status` belonging to any other org tracked by the same Shipit instance). Unlike other handlers (`PushHandler`, the `pull_request` handlers, `ClosedHandler`, `OpenedHandler`, etc.), which all resolve the target via `Repository.from_github_repo_name(params.repository.full_name)` before acting [4](#0-3) , `StatusHandler` never consults `repository`/`full_name` at all, so it can affect commits belonging to a repository under a completely different, unrelated GitHub organization.

Creating a `Status` record has real side effects: it enables CI on the target stack and schedules continuous delivery: [5](#0-4) 
and a commit is only considered deployable once it has a `success` status: [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate GitHub App owner for organization A (and therefore legitimately knows organization A's own `webhook_secret`) can forge a `status` webhook payload with `repository.owner.login = "orgA"` (so it validates against A's own secret) but `sha` equal to a commit hash belonging to organization B's repository (also hosted on the same shared Shipit instance). Because `StatusHandler` looks up commits globally by `sha` with no cross-check against the authenticated organization, the attacker can inject a fake `state: "success"` CI status onto organization B's commit. This can mark an otherwise unreviewed/failing commit as `deployable?`, and — if continuous delivery/merge-queue is enabled on B's stack — trigger an unauthorized deploy of code the attacker never had commit or CI rights over, purely by knowing a commit SHA (which is often public information, e.g. from GitHub commit URLs, PR pages, or CI logs) belonging to that org. This matches the "unauthorized deploy" Critical-severity impact defined for this assessment.

### Likelihood Explanation
Exploitation only requires: (1) the attacker legitimately runs their own GitHub App installation/org on the same shared Shipit instance (a normal, unprivileged tenant, not a Shipit session or `ApiClient` token), and (2) knowledge of a target commit SHA in another tenant's repository, which is frequently discoverable (public repos, shared CI dashboards, PR links). No repository write access, GitHub App private key, or Shipit login is required — only the attacker's own already-known webhook secret. This is a realistic multi-tenant configuration explicitly documented and supported by the engine (`docs/setup.md`).

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that doesn't already do so) to the repository identified in the signed payload, mirroring the pattern used elsewhere in `Handler#stacks`/`Handler#repository_name`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally, require `repository.full_name` in `StatusHandler`'s param definition and verify that `repository.owner.login` (used to select the webhook secret) is consistent with `repository.full_name`'s owner before processing any event, closing this class of bug across all handlers, not just this one.

### Proof of Concept
1. Attacker legitimately administers GitHub organization `orgA`'s Shipit GitHub App installation and knows `orgA`'s `webhook_secret`.
2. Attacker learns the SHA of a commit `abc123...` in `orgB/important-repo`, a different tenant hosted on the same Shipit instance, e.g. via a public GitHub PR link.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` themselves, since they legitimately know `orgA`'s secret.
5. POST to `/github/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner = "orgA"`, fetches `orgA`'s secret, and the HMAC validates successfully. [1](#0-0) 
7. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `orgB/important-repo`, and creates a forged `success` status on it, potentially making it `deployable?` and triggering continuous delivery for `orgB`'s stack. [3](#0-2)

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
