### Title
Burned or missing position NFT permanently bricks the account: `liquidate`, `clean_bad_debt`, and all position entrypoints revert on the unresolved `Option` owner - (File: contracts/controller/src/storage/account.rs)

### Summary
The kernel bug dereferences an AEN request struct that is legitimately `NULL` because `nvme_fc_io_getuuid()` never validates the pointer. The analog in XOXNO Lending is `get_account`/`account_owner`: every position entrypoint unconditionally resolves NFT ownership through `nft_try_owner_of_call`, which returns `None` whenever the `Owner` entry is missing — and the position NFT owner can create exactly that state by calling `burn` directly on the position-nft contract. Once burned, the controller-side account state (metadata, supply and debt maps) remains fully intact, but every code path that loads the account fails closed with `AccountNotFound`, permanently freezing the collateral and permanently preventing liquidation and bad-debt cleanup.

### Finding Description
`try_account_owner` resolves ownership via `nft_try_owner_of_call`, which returns `None` for a missing token, and `get_account` converts that `None` into `panic_with_error!(AccountNotFound)` — the exact "dereference the request without checking it" shape of the CVE, where the `Option` is the null pointer.

`contracts/controller/src/storage/account.rs`:
```rust
pub(crate) fn try_account_owner(env: &Env, account_id: u64) -> Option<Address> {
    let nft = super::protocol::try_get_position_nft(env)?;
    nft_try_owner_of_call(env, &nft, account_id)
}
pub(crate) fn get_account(env: &Env, account_id: u64) -> Account {
    try_get_account(env, account_id)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::AccountNotFound))
}

`nft_try_owner_of_call` swallows all failure modes into `None` — including "token was burned" — so there is no way for the controller to distinguish "account never existed" from "account exists but NFT is gone".

`contracts/controller/src/external/position_nft.rs`:
```rust
pub(crate) fn nft_try_owner_of_call(env: &Env, nft: &Address, account_id: u64) -> Option<Address> {
    let token_id = u32::try_from(account_id).ok()?;
    match PositionNftClient::new(env, nft).try_owner_of(&token_id) {
        Ok(Ok(owner)) => Some(owner),
        _ => None,
    }
}
``` [3](#0-2) 

The position-nft contract's `burn` is callable by the token owner directly (the harness test invokes `PositionNftClient::burn` with no controller authorization). The existing test `partial_liquidation_resolves_nft_ownership` already proves the impact end-to-end: with `Owner` burned and all controller-side entries intact, `liquidate` reverts with `AccountNotFound`, and the companion test shows `clean_bad_debt`/`force_socialize_bad_debt` fail the same way inside `socialize_bad_debt`. [4](#0-3) 

Notably, `remove_account_entry` deletes all controller-side state but deliberately does not burn the NFT, and nothing symmetrically restores or re-mints a burned NFT for a live account — the two state halves can diverge permanently.

### Impact Explanation
Permanent freezing of funds plus protocol insolvency. The owner of a position NFT (an unprivileged address; `position-nft transfer`/`burn` are in-scope unprivileged surfaces) can burn the NFT on an account that still holds supply and borrow positions. From then on:

- `withdraw`, `repay`, `supply`, `borrow`, `liquidate` all load the account via `get_account`/`account_owner` and revert.
- `clean_bad_debt` — the only permissionless path that writes down unrecoverable debt — also reverts, so the debt shares can never be socialized or written down via the supply-index reduction.
- The collateral tokens remain locked in the pool attributed to a position that can never be touched, while the debt keeps accruing interest in the borrow index.

An attacker can open a maximally leveraged position, wait for (or engineer via their own price exposure) HF < 1, then burn the NFT: no liquidator can ever seize the collateral, and the accruing debt sits on the books forever, degrading supplier share value with no cleanup recourse. This matches the accept criterion "permanent freezing of funds" and contributes to "protocol insolvency".

### Likelihood Explanation
Fully reachable by a single unprivileged address with no privileged role, timing race, or external dependency: `position_nft.burn(token_id)` requires only owner auth on the NFT contract. The only cost to the attacker is that their own position is frozen — but for an already-insolvent position that collateral was forfeit anyway, so the attack converts an ordinary loss into permanent protocol damage at zero marginal cost. Severity Medium: the damage is bounded to the attacker's own account size, but it defeats both liquidation and bad-debt cleanup rather than merely delaying them.

### Recommendation
Do not let the NFT layer be the sole arbiter of account existence for protocol-critical paths. Concretely:

- Gate `burn` on the position-nft contract so it can only be invoked by the controller (e.g., require the controller address as an authorized `from`), or reject `burn` while the controller still stores an `AccountMeta` for that id.
- Alternatively, on the controller side, treat a missing `Owner` entry for an account with existing `AccountMeta` as a distinct failure mode and allow the liquidation/bad-debt paths (`liquidate` in `SeizeMode::Credit` style accounting, `clean_bad_debt`, `socialize_bad_debt`) to proceed using a recovered/self custody rather than unconditionally reverting — mirroring the upstream fix's "validate the request pointer before dereference" by branching on `None` instead of collapsing it into `AccountNotFound` for every flow.

### Proof of Concept
1. `ALICE` calls `supply` then `borrow` to open a leveraged account; receives position NFT `token_id = account_id`.
2. Market moves so `ALICE`'s HF < 1 (or the position is only marginally solvent).
3. `ALICE` calls `PositionNftClient::burn(token_id)` directly on the position-nft contract — succeeds, owner-only auth satisfied.
4. Any liquidator calls `controller.liquidate(liquidator, account_id, payments, SeizeMode::Transfer)` → `get_account` → `try_account_owner` returns `None` → reverts `AccountNotFound`.
5. Anyone calls `clean_bad_debt(account_id)` → `socialize_bad_debt` → `get_account` → reverts `AccountNotFound`.
6. `withdraw`/`repay`/`supply`/`borrow` on that account revert identically. Collateral and debt are permanently frozen; bad debt is never written down. This is exactly the sequence demonstrated by `partial_liquidation_resolves_nft_ownership` and its bad-debt companion test in `tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs`.

/// A partial liquidation resolves NFT ownership: `process_liquidation` calls
/// `storage::get_account`, which reads `owner_of`. With the `Owner` entry
/// burned and every controller-side account entry intact, the liquidation
/// fails with `AccountNotFound`.
#[test]
fn partial_liquidation_resolves_nft_ownership() {
    let mut t = LendingTest::new().standard_two_asset().build();
    t.supply(ALICE, "USDC", 10_000.0);
    t.borrow(ALICE, "ETH", 3.0);
    let id = t.account_id(ALICE);
    let token_id = u32::try_from(id).expect("test ids fit u32");

    t.set_price("USDC", usd_cents(50));
    t.assert_liquidatable(ALICE);

    // Detach the ownership leg, leaving controller state untouched.
    position_nft::PositionNftClient::new(&t.env, &t.position_nft).burn(&token_id);
    assert!(!t.try_nft_owner_of(id), "ownership leg is now unreadable");
    assert!(
        t.account_exists(id),
        "controller-side account state must still be live -- this isolates the \
         NFT read as the only thing that changed"
    );

    // A plain partial liquidation, well under the close factor.
    let result = t.try_liquidate(LIQUIDATOR, ALICE, "ETH", 1.0);
    assert_contract_error(result, errors::ACCOUNT_NOT_FOUND);
}
