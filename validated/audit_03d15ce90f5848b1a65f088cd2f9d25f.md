### Title
Fee-on-Transfer ERC20 Token Accounting Mismatch in Service-Chain Bridge Drains Counterpart Bridge Reserves — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` records the caller-supplied `_value` in the `RequestValueTransfer` event without verifying the amount actually received by the bridge. When a fee-on-transfer (deflationary) ERC20 token is used, the source bridge receives fewer tokens than `_value + _feeLimit`, yet the event broadcasts `_value` as the bridged amount. The counterpart bridge operator faithfully replays that amount via `handleERC20Transfer`, transferring or minting the full `_value` to the recipient. In lock mode this drains the counterpart bridge's token reserves; in mint-burn mode the source-side `burn(_value)` call reverts (self-protecting), but the lock-mode path is fully exploitable.

---

### Finding Description

**Source-side deposit — `requestERC20Transfer`**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

`safeTransferFrom` is called with `_value + _feeLimit`. For a fee-on-transfer token the bridge actually receives `(_value + _feeLimit) × (1 − τ)` where `τ` is the token's transfer-fee rate. No balance snapshot is taken before or after the pull.

**Event emission — `_requestERC20Transfer`**

```solidity
// BridgeTransferERC20.sol L97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← caller-supplied, not actual received amount
    requestNonce, fee, _extraData
);
requestNonce++;
```

The event records the original `_value`, not the actual balance increment.

**Destination-side payout — `handleERC20Transfer`**

```solidity
// BridgeTransferERC20.sol L68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "...");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);   // ← full _value paid out
}
```

The bridge operator reads `_value` from the `RequestValueTransfer` event and calls `handleERC20Transfer` with that same value. In lock mode the counterpart bridge transfers the full `_value` to the recipient regardless of how much collateral the source bridge actually holds.

**Token registration — `BridgeTokens.registerToken`**

```solidity
// BridgeTokens.sol L57-71
function registerToken(address _token, address _cToken)
    external onlyOwner onlyNotRegisteredToken(_token)
{
    require(_cToken != address(0), "counterpart token address is zero");
    registeredTokens[_token] = _cToken;
    ...
}
```

`registerToken` is `onlyOwner`, but it performs no check on the token's transfer semantics. Once a fee-on-transfer token is registered, the `onlyRegisteredToken` modifier in `_requestERC20Transfer` passes, and any unprivileged user can call `requestERC20Transfer` to trigger the accounting mismatch.

---

### Impact Explanation

**Lock mode (non-mintBurn):** Each `requestERC20Transfer` call with a fee-on-transfer token deposits `_value × (1 − τ)` (approximately) into the source bridge but causes the counterpart bridge to pay out `_value`. The shortfall per call is `_value × τ`. Repeated calls drain the counterpart bridge's ERC20 reserves until it cannot fulfill legitimate withdrawals — an unauthorized transfer of bridged assets.

**Mint-burn mode:** The source bridge attempts `burn(_value)` after receiving only `(_value + _feeLimit) × (1 − τ)` tokens. Because the bridge holds fewer tokens than `_value`, the burn reverts and the transaction fails. This mode is self-protecting.

---

### Likelihood Explanation

- The bridge owner must first register a fee-on-transfer token (semi-trusted, privileged step). This can happen inadvertently — many real-world tokens (e.g., tokens with protocol fees) implement transfer fees.
- Once registered, any unprivileged user can call `requestERC20Transfer` repeatedly to widen the accounting gap.
- No balance-before/after guard exists anywhere in the bridge contract to detect or prevent this.

---

### Recommendation

1. **Balance-snapshot check:** Record `balanceBefore = IERC20(_tokenAddress).balanceOf(address(this))` before `safeTransferFrom`, then compute `actualReceived = balanceAfter − balanceBefore` and use `actualReceived` (minus fee) as the bridged amount in the event.
2. **Token whitelist enforcement:** Add a check in `registerToken` (or a separate validation function) that verifies the token does not apply a transfer fee, e.g., by performing a test transfer and comparing balances.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` with a 5% transfer fee.
2. Bridge owner calls `registerToken(FeeToken, counterpartFeeToken)` on the source bridge (lock mode).
3. User approves source bridge for `110` tokens, then calls:
   ```
   requestERC20Transfer(FeeToken, victim, 100, 10, "0x")
   ```
4. Source bridge receives `110 × 0.95 = 104.5` tokens. After fee handling (bridge fee = 10, transferred to feeReceiver with another 5% cut), source bridge retains ≈ `94.5` tokens as collateral.
5. `RequestValueTransfer` event emits `valueOrTokenId = 100`.
6. Bridge operator calls `handleERC20Transfer(..., 100, ...)` on counterpart bridge.
7. Counterpart bridge transfers `100` tokens to the recipient.
8. Net loss to counterpart bridge per call: `≈ 5.5` tokens. Repeat until counterpart bridge is drained.

**Exact corrupted value:** The counterpart bridge's ERC20 balance decreases by `_value` per call, while the source bridge's collateral increases by only `(_value + _feeLimit) × (1 − τ) − fee_outflows`. The cumulative shortfall equals `Σ [_value_i − actual_received_i]` across all such calls, which can reach the full counterpart bridge reserve. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
