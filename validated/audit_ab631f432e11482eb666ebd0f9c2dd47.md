### Title
Webhook signature verification is bound to attacker-controlled `repository.owner.login`, while status/push handlers act on unrelated payload fields (`sha`, `repository.full_name`) - enabling cross-repository commit status forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This is a direct analog of the reported bug class: a value that is *authenticated* (the organization whose `webhook_secret` is used to verify the HMAC) is not cryptographically bound to the value that is *acted upon* (the commit `sha` / repository whose data gets mutated). Just as Aragon's voting contract lets an unprivileged-but-vote-creating actor manipulate on-chain state that isn't properly scoped to a legitimate quorum, Shipit's webhook pipeline lets an actor who legitimately controls one GitHub App/organization forge events that mutate state belonging to a completely different, unrelated stack.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on a field taken directly from the untrusted, attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

Because the HMAC signature only proves "this body was signed by whoever holds the `webhook_secret` for the organization named in `repository.owner.login`", and Shipit supports **multiple independent GitHub Apps for multiple organizations** (each with its own `webhook_secret`), any party that legitimately owns/administers *one* installed GitHub App (e.g. by creating their own throwaway GitHub organization and installing a Shipit-configured GitHub App on it, a routine, unprivileged action) can compute a fully valid signature for **any JSON body of their choosing**, as long as `repository.owner.login` in that body equals their own organization's name (`app/controllers/shipit/webhooks_controller.rb:59-62`, `lib/shipit/github_app.rb:76-83`).

The problem is that `repository.owner.login` (the authenticated field) is never checked for consistency with the *other* repository-identifying fields the handlers actually act on. `Handler#repository_name` and most handlers key their side effects off `repository.full_name`, not `repository.owner.login`: [3](#0-2) 

Worse, `StatusHandler`, which creates/updates CI statuses that feed into deploy-gating logic (`ci.require`), doesn't scope by repository at all - it looks up commits **purely by SHA** across the entire database: [4](#0-3) 

So the equality the system implicitly relies on but never enforces is:
`organization that authenticated the webhook (repository.owner.login, verified via HMAC)` == `repository/commit that gets written (repository.full_name / sha, used by handlers)`

Before the attack: only the legitimate upstream GitHub organization that owns a given repository can produce a validly-signed webhook affecting that repository's commits/stacks, because in normal operation `repository.owner.login` and `repository.full_name` always describe the same repository.

After the attack: an attacker who controls their own GitHub App installation (their own org, their own `webhook_secret`) crafts a `status` event payload with `repository.owner.login` set to their own org (so `verify_signature` picks their own known secret and the HMAC passes) but with `sha` set to a real commit SHA belonging to a victim's unrelated stack/repository. `StatusHandler#process` finds that commit purely by SHA (no repository check) and calls `commit.create_status_from_github!(params)`, letting the attacker write an arbitrary CI status (e.g., forge a "success" for a required context) onto a commit they have no access to.

### Impact Explanation
Shipit's `ci.require` deploy-gating mechanism relies on `CommitStatus`/`Status` records associated with a commit to decide whether a commit is safe/allowed to deploy. Forging a passing status on a victim commit that never actually passed real upstream CI can cause the deploy-gating logic to treat an unvetted/failing commit as deployable, resulting in an unauthorized deploy of code that was never actually approved by the legitimate CI pipeline for that repository. This matches the "High" impact bucket (escalation into a trust decision that gates deploys) and can reach "unauthorized deploy" territory depending on how strictly a given stack's `ci.require` is enforced.

### Likelihood Explanation
The only prerequisite is the ability to install and configure a GitHub App on any organization and register it with a Shipit deployment that supports multiple GitHub orgs (a documented, intended, unprivileged configuration path - see `docs/setup.md` "Using Multiple Github Applications"). No access to the victim's repository, GitHub App, or `webhook_secret` is required; the attacker only needs their own organization's `webhook_secret`, which they legitimately possess. The only unknown is whether a specific deployment operator has configured Shipit with more than one GitHub organization/App - single-org deployments are not exploitable this way, since only one `webhook_secret` exists.

### Recommendation
- In `WebhooksController#verify_signature` / `Handler`, cross-check that `repository.owner.login` used to select the verification secret matches the owner segment of `repository.full_name` used by every handler, rejecting mismatches.
- In `StatusHandler#process`, scope the `Commit` lookup by the stack's repository (derived from `Repository.from_github_repo_name(repository.full_name)`) rather than a bare, cross-tenant `Commit.where(sha:)` query.

### Proof of Concept
1. Attacker registers `attacker-org` on GitHub, creates a Shipit-compatible GitHub App on it, and it gets configured under Shipit's multi-org `secrets.yml` (`github.attacker-org.webhook_secret = S`), per the documented multi-org support (`docs/setup.md:181-209`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/throwaway"},
  "sha": "<victim commit sha, e.g. required by victim-org/prod-stack ci.require>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their own known secret `S`.
4. POST to `/github/webhooks` with event `status`. `verify_signature` reads `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` - matching the victim's real commit regardless of which repository it belongs to - and writes a forged "success" status onto it (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), potentially satisfying `victim-org/prod-stack`'s `ci.require` gate for a commit that never passed real CI.
