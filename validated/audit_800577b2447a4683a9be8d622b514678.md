## Answer

Based on the investigation, the ocore analog of the CoverRightTokenFactory issue is the **asset‑metadata registration flow**, where any unprivileged unit author can permissionlessly attach a fake name/ticker to an *existing* asset, and – if they win the race against the legitimate issuer – that fake name is durably stored and shown to users, exactly mirroring the "anyone can deploy with arbitrary naming, front‑running the legitimate flow" bug class from the report.

### Title
Unauthenticated asset-metadata registration allows front-running and spoofing of asset names/tickers - (File: wallet.js)

### Summary
`fetchAssetMetadata` in `wallet.js` accepts a `registry_address` supplied by an untrusted hub response and only checks that it is a syntactically valid address and that the metadata unit's author matches it [1](#0-0) . It never verifies that this `registry_address` is the asset's `definer_address`, a well-known trusted registry, or otherwise authorized to name that asset. Any address can author a `data` message claiming `{asset: <existing asset hash>, name: ..., decimals: ...}` via the generic content-joint composer [2](#0-1) , and this is recorded into the `asset_metadata` table keyed by `asset` as PRIMARY KEY [3](#0-2) .

### Finding Description
The `asset_metadata` table stores one row per `asset` (PRIMARY KEY (asset)) [3](#0-2) . `fetchAssetMetadata` writes to this table using an `INSERT` (with ignore-on-conflict) unless the registry is "updatable", determined by `isUpdatableRegistry(registry_address)` [4](#0-3) . The only checks performed are: `metadata_unit` exists as a joint, and the unit's author equals the claimed `registry_address` [5](#0-4) . Nothing ties `registry_address` to the asset's actual `definer_address`/issuer, nor is there any on-chain enforcement restricting which address may post metadata for a given asset — the `data` app message type used to carry this payload is a free-form message any single-authored unit can post.

This is structurally identical to `CoverRightTokenFactory.deployCRToken`: a permissionless, unauthenticated "registration" primitive keyed by an identifier that is itself legitimate (a real asset hash, analogous to a real `poolId`), but whose associated display data (`name`, `decimals`, analogous to `poolName`/`tokenName`) can be set arbitrarily by anyone, and once set (for non-updatable/non-trusted registries) is "claimed" first-come-first-served with no re-registration by the true owner.

### Impact Explanation
Because wallets display `asset_metadata.name`/`decimals` to end users for identifying assets in balances and payment history [6](#0-5) , an attacker can race to attach a fake, deceptive ticker/name (e.g., impersonating "USDT" or a well-known token) to a genuine, newly-issued asset before its real issuer publishes correct metadata. Since the row is keyed uniquely by `asset` and the insert only happens if no metadata is present yet (for non-updatable registries), the legitimate issuer may be permanently unable to overwrite the attacker's spoofed name, deceiving users into misidentifying assets — directly enabling the type of "manipulate and trick users by setting their own poolName and tokenName" harm called out in the report.

### Likelihood Explanation
Any single-authored unit can post the required `data` message referencing any existing asset hash; no special privilege, cosigning, or relationship to the asset's definer is required. The race only requires observing a newly created asset unit and posting the fake metadata message before the legitimate registry does — a low-cost, easily automatable front-run, though it requires the legitimate issuer to not already be using a pre-established "updatable" registry.

### Recommendation
Restrict `asset_metadata` acceptance to registries that are cryptographically tied to the asset (e.g., require `registry_address === objAsset.definer_address`, or maintain a config-level allowlist of trusted registries as `isUpdatableRegistry` appears to partially attempt), and/or make the table `REPLACE`-able only by the asset's definer so that legitimate owners can always correct/override spoofed metadata rather than being locked out by a first-claim race.

### Proof of Concept
1. Wait for (or trigger) the definition of a new asset unit `X` (e.g., via an AA's `asset` message as shown in `test/samples/create_an_asset.oscript`) [7](#0-6) .
2. Immediately, from any unrelated address `A` (not the asset's `definer_address`), compose and broadcast a `data` message `{asset: X, name: "USDT", decimals: 2}` using the generic content-joint composer [8](#0-7) .
3. Any hub/wallet client that later calls `hub/get_asset_metadata` for asset `X` and receives `registry_address = A` will accept it because the only check performed is that unit `A` authored the metadata unit — not that `A` is authorized for asset `X` [9](#0-8) .
4. The forged `name`/`decimals` are persisted into `asset_metadata` keyed by `asset = X` and surfaced to end users in balance/transaction displays, before or instead of the legitimate issuer's real metadata.

**Note on completeness**: I was unable to fully inspect the exact definition/allowlist logic of `isUpdatableRegistry(registry_address)` (only its usage sites were found) or the server-side `hub/get_asset_metadata` handler that selects which registry's claim to return to a given client, due to reaching the tool-call budget. If `isUpdatableRegistry` in fact restricts registration to a small, hardcoded, trusted set of registry addresses for all practical asset types, the exploitability of this specific analog would be reduced to assets that are not covered by a designated registry. A Devin session with full repository access is recommended to confirm the exact scope of `isUpdatableRegistry` and the hub-side registry-selection logic before treating this as fully confirmed.

CREATE TABLE asset_metadata (
	asset CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL PRIMARY KEY,
	metadata_unit CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL,
	registry_address CHAR(32) NULL,
	suffix VARCHAR(20) NULL, -- added only if the same name is registered by different registries for different assets, equal to registry name
	name VARCHAR(20) NULL,
	decimals TINYINT NULL,
	creation_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
	UNIQUE byNameRegistry(name, registry_address),
	FOREIGN KEY (asset) REFERENCES assets(unit),
	FOREIGN KEY (metadata_unit) REFERENCES units(unit)
	-- FOREIGN KEY (registry_address) REFERENCES addresses(address) -- addresses is not always filled on light
) ENGINE=InnoDB  DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_520_ci;
