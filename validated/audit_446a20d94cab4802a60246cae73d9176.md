## Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table, without ever calling `Repository.from_github_repo_name`/`Handler#stacks` to scope the lookup to the reporting repository. Any registered repository (attacker's repo B) can send a `status` webhook, signed with its own valid `webhook_secret`, whose `sha` collides with a commit that actually belongs to a different repository/stack (repo A), causing Shipit to write a forged commit status onto repo A's commit.

## Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Commit.where(sha: params.sha)` (the set actually mutated) **should equal** `Handler#stacks.flat_map(&:commits).where(sha: params.sha)` (the set scoped to the repository authenticated by `verify_signature`/`repository_owner`), but it does not.

Every sibling handler (`PullRequest::*Handler`) restricts its writes to `stacks` derived via `Repository.from_github_repo_name(repository_name)` [1](#0-0) , which correctly resolves for any payload containing a `repository.full_name` (proven directly: `Repository.from_github_repo_name('B-owner/B-name')` performs `find_by(owner:, name:)` and returns repo B's record deterministically) [2](#0-1) . `StatusHandler`, however, ignores this entirely:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This is a global, unscoped query against the `commits` table — it is not filtered by `stack_id`, and `stacks`/`repository_name` (available on the base `Handler` class) are never referenced in `StatusHandler`.

Request path: `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which uses `Shipit.github(organization: repository_owner)` derived from `payload.dig('repository','owner','login')` [4](#0-3) [5](#0-4) . Signature verification only proves the webhook was legitimately sent by GitHub for repo B (the org/app whose secret matches) — it does not, and cannot, constrain which rows `StatusHandler` is allowed to touch afterward. Once inside `process`, the handler trusts `params.sha` (attacker-controlled string in the JSON body) as a global primary key into `commits` across all tenants.

Exploit flow: Attacker owns/controls repo B, which is registered in Shipit (has a `webhook_secret` via the configured GitHub App). Attacker discovers or engineers a SHA collision or, more practically, simply knows/guesses a SHA that also exists in repo A's `commits` table (e.g., a shared base commit, a cherry-picked/rebased commit with identical tree+metadata reproduced across forks, or a previously observed SHA from a public PR/status disclosure elsewhere in the app). Attacker POSTs a `status` webhook (`X-Github-Event: status`) to `/webhooks` with `repository.full_name = "attacker/B"`, `sha = "<repoA's commit sha>"`, `state`, `context`, signed correctly for repo B's `webhook_secret`. `verify_signature` passes (correct secret for repo B). `StatusHandler.call` invokes `Commit.where(sha: ...)`, which matches repo A's `Commit` row (regardless of which stack/repository it belongs to), and calls `commit.create_status_from_github!(params)`, writing a forged status onto stack A's commit — potentially flipping `deployable?`/blocking status and triggering `stack.schedule_merges` or continuous deployment via `Hook.emit(:deployable_status, ...)` and `ContinuousDeliveryJob` [6](#0-5) [7](#0-6) .

Why existing guards fail: `verify_signature` authenticates *which repository sent the webhook*, not *which repository's data may be mutated*; `ExplicitParameters` schema only validates shape/types of `sha`/`state`, not tenant ownership; `drop_unhandled_event` only filters by event type. None of these check that the matched `Commit` belongs to a stack under the authenticated repository. The `stacks` scoping helper exists precisely to close this gap and is used by every other handler, but `StatusHandler` never calls it.

## Impact Explanation
A payload legitimately authenticated for repository B results in a database write (a new `Status` row, and potential deployability/merge-scheduling side effects) on a `Commit` belonging to an unrelated repository/stack A — this is a direct "payload for one repository mutating another's stack/commit" case, matching the **Critical** category. Blast radius spans all tenants sharing the Shipit instance: any attacker with one registered repository can attempt to forge statuses on any other repository's commits, limited only by their ability to know/produce a colliding SHA. Repeatable per request; each webhook delivery is independent and requires no session or elevated token.

## Likelihood Explanation
Preconditions: attacker's repo B must be a registered Shipit repository (to obtain a valid `webhook_secret`) — explicitly permitted per the prompt's preconditions. The forgery cost is a single unauthenticated HTTP POST to `/webhooks`, correctly HMAC-signed with repo B's own secret (which the attacker legitimately controls as the repo's GitHub App/webhook owner). The only nontrivial requirement is a SHA that exists in another repository's `commits` table — feasible via known public SHAs (e.g., from shared history, forks, or previously observed SHAs), and requiring no cryptographic secret. This is a pure logic omission rather than a payload-schema limitation, since the payload does carry `repository.full_name` and `Handler#stacks`/`Repository.from_github_repo_name` can resolve it correctly, as used identically by every `PullRequest::*Handler`.

## Recommendation
Scope `StatusHandler#process` to the requesting repository's stacks, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the inherited `stacks` method (already resolves via `Repository.from_github_repo_name(repository_name)`), mirroring the pattern used by `PullRequest::*Handler` subclasses.

## Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of scope for grading per rules but described for validation):

1. Create `repo_a = Shipit::Repository.create!(owner: 'owner-a', name: 'repo-a')`, `stack_a = Shipit::Stack.create!(repository: repo_a, ...)`, `commit_a = Shipit::Commit.create!(stack: stack_a, sha: 'deadbeef'*5, ...)`.
2. Create `repo_b = Shipit::Repository.create!(owner: 'owner-b', name: 'repo-b')`, `stack_b = Shipit::Stack.create!(repository: repo_b, ...)` with no commit with that SHA.
3. Build `payload = { 'repository' => { 'full_name' => 'owner-b/repo-b' }, 'sha' => commit_a.sha, 'state' => 'success', 'context' => 'ci' }`.
4. Instantiate `handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)`.
5. Assert scoping is available and correct: `assert_equal [stack_b], handler.send(:stacks).to_a` (proves `Repository.from_github_repo_name` resolves to repo B, contradicting any claim that the payload lacks enough info).
6. Call `handler.process`.
7. Assert the actual mutation lands outside that scope: `assert commit_a.reload.statuses.exists?(context: 'ci')` while `commit_a.stack_id != stack_b.id` and `stack_b.commits.empty?` — proving repo B's webhook mutated repo A's commit despite `stacks` (scoped to B) never containing it.
