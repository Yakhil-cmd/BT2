### Title
Cross-organization webhook forgery via mismatched signature-scope and payload-target fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC `webhook_secret`) used to validate `X-Hub-Signature` based on `repository_owner`, which is read from the untrusted request body (`repository.owner.login` or `organization.login`). Event handlers, however, act on a *different* untrusted field of the same body — `repository.full_name` — to resolve the `Repository`/`Stack` that gets synced, archived, provisioned, or otherwise mutated. Because the field used to pick the verification secret and the field used to pick the acted-upon repository are independent and both attacker-controlled, a party who legitimately controls the webhook secret for *one* configured GitHub organization in a multi-org Shipit deployment can forge a validly-signed payload whose `repository.owner.login` matches their own org (so it authenticates), while `repository.full_name` points at a completely different organization's repository/stack.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` via [2](#0-1) , then calls `Shipit.github(organization: repository_owner)` to fetch that organization's `GitHubApp` config (including its `webhook_secret`), and verifies the signature with `github_app.verify_webhook_signature` in [3](#0-2) .

Shipit explicitly supports per-organization GitHub App configuration with distinct `webhook_secret`s, as documented in `config/secrets.development.example.yml` (the "multiple Github applications for different Github organizations" schema) — each org can have its own App, `oauth`, and `webhook_secret` [4](#0-3) .

Once the signature passes, `WebhooksController#create` dispatches the parsed JSON body directly to handlers without re-validating that the acted-upon repository belongs to the authenticated organization: [5](#0-4) . All handlers derive the target repository purely from `repository.full_name` in the body, e.g. the base `Handler#repository_name`/`#stacks` [6](#0-5) , `PushHandler#process` which syncs matching stacks [7](#0-6) , and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) which look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive/provision review stacks [8](#0-7) .

The equality that should hold but does not: `organization used to select webhook_secret (repository.owner.login / organization.login) == organization owning repository.full_name`. Since both fields live in the same attacker-supplied JSON body and neither is cross-checked, they can diverge freely as long as the whole payload is HMAC-signed with the secret belonging to the org named in `repository.owner.login`.

### Impact Explanation
An entity that legitimately possesses the webhook secret for one org configured in a multi-tenant Shipit instance (e.g., because they set up that org's GitHub App and its webhook secret) can forge a webhook body where `repository.owner.login`/`organization.login` = their own org (to pass signature verification with their own secret) but `repository.full_name` = a victim org/repo hosted on the same Shipit instance. This can trigger unauthorized cross-repository actions: forcing a `GithubSyncJob` sync of a victim stack via `PushHandler`, or archiving/unarchiving/provisioning a victim's review stacks via the `pull_request` handlers — actions the attacker has no GitHub-side authorization over. This crosses the "cross-repository writes" impact bar defined in scope.

### Likelihood Explanation
Requires the attacker to control a `webhook_secret` for at least one organization configured in the same multi-org Shipit deployment (a legitimate, lower-privileged tenant) and to know the target victim's `repository.full_name`, both of which are realistic in shared/multi-tenant Shipit setups. No GitHub write access to the victim repo, no Shipit session, and no privileged Shipit account are required — only the ability to send an HTTP POST to `/webhooks` with a correctly-HMAC-signed body using a secret the attacker legitimately possesses for their own org.

### Recommendation
Bind webhook signature verification to the same repository/organization the handler will act on: after verifying the signature with the org derived from the payload, also verify that `repository.full_name`'s owner matches the organization used for verification (or, resolve the target `Repository` first and verify using that repository's own configured organization/secret, rejecting the payload if the two are inconsistent).

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `org-attacker` (secret `S_A`, controlled by attacker) and `org-victim` (secret `S_V`, not known to attacker), per the documented multi-org schema.
2. Attacker crafts a `push` webhook JSON body:
   - `"repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" }`
   - `"ref": "refs/heads/main"`, `"after": "<arbitrary sha>"`
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using their own secret `S_A`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "org-attacker"`, fetches `S_A`, verification succeeds.
6. `PushHandler#process` resolves stacks via `repository.full_name = "org-victim/victim-repo"` and enqueues `GithubSyncJob` for the victim's stack — an action the attacker has no legitimate authorization to trigger.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
```

**File:** lib/shipit/github_app.rb (L76-83)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
