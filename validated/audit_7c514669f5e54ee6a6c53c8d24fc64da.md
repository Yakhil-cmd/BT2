### Title
Cross-tenant `Status` write via SHA-only lookup in `StatusHandler` bypassing org-scoped webhook signature - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the organization derived from `repository_owner` (`params.dig('repository', 'owner', 'login')`) to pick which `webhook_secret` to HMAC-check, and never re-validates that the named repository owns the record actually mutated downstream. `StatusHandler#process` compounds this by never even consulting `params.repository` (or the base `Handler#stacks`/`repository_name` helpers) — it looks up commits **globally** by `sha` alone, so a validly-signed webhook from org A can write a `Status` row onto a `Commit` belonging to a completely different stack/repository (org B) if that commit's SHA exists in Shipit's database, which is realistic for forked/mirrored repositories sharing commit history.

### Finding Description
Binding claimed: `repository_owner` (used in `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:25,59-62`) == owner of `repository.full_name` used by the mutated record in `StatusHandler`.

Trace:
- `verify_signature` selects `github_app = Shipit.github(organization: repository_owner)` and HMAC-verifies the raw payload with that org's `webhook_secret` [1](#0-0) [2](#0-1) . This only proves "the sender knows org A's secret" — it says nothing about which `Commit`/`Stack`/`Repository` rows get touched.
- After verification, `create` dispatches to handlers registered for the event: for `X-Github-Event: status`, that's `Handlers::StatusHandler` [3](#0-2) [4](#0-3) .
- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [5](#0-4) 
This query has **no repository/stack scoping whatsoever** — it does not call `repository_name`/`stacks` from the base `Handler` class (unlike every `PullRequest::*Handler`, which does resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before mutating anything, e.g. [6](#0-5) ). `StatusHandler`'s own params schema doesn't even `require :repository` [7](#0-6) , confirming the repository named in the payload is never used to constrain the write.
- `Commit.sha` is a plain string column matched across the entire `commits` table (all stacks, all repos): `Commit.where(sha: params.sha)` returns any commit row anywhere in the instance whose SHA matches, then calls `commit.create_status_from_github!(params)` → `statuses.replicate_from_github!(stack_id, github_status)` [8](#0-7) , writing into that commit's actual `stack_id`, which belongs to whatever repository originally created that `Commit` record — not org A.

Root cause: the controller's authentication is organization-scoped (via `repository_owner` → `webhook_secret`), but `StatusHandler`'s authorization/data-selection is not scoped to any repository at all — it trusts `sha` alone as a global primary key across tenants. Since git SHA1s are content-derived and identical across forks/mirrors of the same commit (a very common real-world case for shared upstream history), an attacker controlling org A's repository (and thus org A's legitimately configured webhook secret) can send a `status` event naming org A's repo but with a `sha` that also exists as a `Commit` in org B's stack, and Shipit will write a `Status` to org B's commit.

Existing guards do not stop this: `verify_signature` only checks the HMAC against the org derived from the payload — it does not know or care which `Commit` rows will be mutated; `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schema for `StatusHandler` doesn't require/validate `repository` at all; no `force_github_authentication`, `User#authorized?`, or `require_permission!` applies to unauthenticated webhook ingestion by design.

### Impact Explanation
An attacker who owns/administers any GitHub repository connected to this Shipit instance (and therefore possesses that repo's org-scoped `webhook_secret`, or simply pushes commits/creates arbitrary `state`/`description`/`target_url` status payloads for their own repo which GitHub relays to Shipit) can inject a forged CI `Status` (e.g., `state: "success"`, arbitrary `target_url`/`description`) onto a `Commit` belonging to a different tenant's stack, as long as that commit's SHA is shared (fork/mirror scenario) or otherwise present in the DB. Since `Commit#deployable?` and continuous delivery gating depend on aggregated `Status` state (`schedule_continuous_delivery`, `blocked?`), this is a payload-for-one-repository-mutates-another's-commit primitive that can influence deploy/merge decisions for a stack the attacker never authenticated against — matching the "Critical: payload for one repository mutating another's ... commit ... or an unauthorized deploy" category. This is repeatable per request against any commit SHA the attacker can guess or that is shared via forking a public upstream repo also tracked by another tenant on the same Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs a repository (or fork) registered with any org whose `webhook_secret` is configured in Shipit, and a target `Commit` row existing in the DB with a matching `sha` (trivially achievable by forking any public repo already tracked by another Shipit-managed stack, since fork SHAs are identical to upstream). No Shipit session, API token, or victim org's secret is required — only the ability to trigger a `status` webhook from the attacker's own connected repository (pushing a commit + using GitHub's own status API/Checks, or any integration that posts a `status` event) at effectively zero cost, fully repeatable.

### Recommendation
In `StatusHandler`, require and validate `params.repository.full_name`, resolve the `Repository`/`Stack` scope from it (mirroring the base `Handler#stacks` helper used elsewhere), and scope the `Commit` lookup to `stacks.commits.where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`, so a `Status` can only ever be attached to a commit under the repository that authenticated the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for org A repo does not mutate commits belonging to org B's stack" do
  org_b_stack = shipit_stacks(:shipit) # belongs to repository owned by "org-b"
  shared_sha = "a" * 40
  org_b_commit = org_b_stack.commits.create!(sha: shared_sha, message: "shared history")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "description" => "forged by org A",
    "target_url" => "http://evil.example",
    "context" => "ci/forged",
    "repository" => { "full_name" => "org-a/attacker-repo", "owner" => { "login" => "org-a" } }
  }

  assert_no_difference -> { org_b_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Currently FAILS: org_b_commit.statuses.count increases by 1,
  # proving org A's signed payload wrote a Status onto org B's commit.
end
```
Both sides of the equality (`repository_owner == "org-a"` used for signature selection, vs. the mutated commit's actual stack owner `== "org-b"`) diverge after `StatusHandler#process` runs, because `Commit.where(sha:)` ignores the payload's `repository` entirely.
