### Title
Single malicious commit causes permanent denial of sync via default `--max-failures=0` - (File: `main.go`)

### Summary
`git-sync`'s sync loop treats every sync failure as fatal by default (`--max-failures` defaults to `0`), and the deterministic per-commit operations performed in `configureWorktree` (in particular `git submodule update --init [--recursive]`) are executed against attacker-controlled repository content. A single commit that is pushed to the tracked ref — containing e.g. a submodule pointing at an unreachable/invalid URL, a malformed `.gitmodules`, or any other content that makes worktree checkout/submodule initialization fail deterministically — will cause every retry of the sync loop to fail identically. Because the failure is deterministic (not transient), the process immediately reaches the failure threshold and calls `os.Exit(1)`, permanently killing `git-sync` instead of just skipping the bad update. This is the git-sync analog of the reported auction DOS: a single "invalid" unit of untrusted input (bid / commit) that is guaranteed to fail is enough to deny service to the whole system, because there is no mechanism to skip/quarantine the bad unit and continue serving the last-good state.

### Finding Description
The steady-state and initial sync loops in `main` treat any error from `git.SyncRepo` as a failure count increment, and abort the whole process once `failCount >= maxFails`: [1](#0-0) 

`--max-failures` (`$GITSYNC_MAX_FAILURES`) defaults to `0`, meaning "any sync failure will terminate git-sync": [2](#0-1) 

`SyncRepo` always re-fetches the ref and, whenever the fetched hash differs from what is currently synced, calls `configureWorktree`, which unconditionally checks out the new hash and initializes submodules unless `--submodules=off`: [3](#0-2) [4](#0-3) 

The submodule URLs, `.gitmodules` content, and any other repository state that drives these commands come directly from the remote repo content that is being synced — i.e., it is attacker-controlled if the attacker can push to (or otherwise influence) the tracked ref (branch/tag/HEAD). If that content makes `git reset --hard`, `git submodule update --init`, or any other command in `configureWorktree`/`fetch` fail unconditionally (e.g., a submodule URL that is unreachable, disallowed by `protocol.*.allow`, or otherwise erroring every time), then:
1. Every sync attempt returns a non-nil error from `SyncRepo`.
2. `failCount` increments each time.
3. Once `failCount >= maxFails` (which is `0` by default, so on the very first failure once `maxFails >= 0` — note default is 0, immediate abort on first failure), `git-sync` logs and calls `os.Exit(1)`.

Unlike a transient network blip, this failure is deterministic per-commit: retrying does not help because the same broken commit content is fetched and processed every time. There is no mechanism to skip a bad commit/ref and fall back to (or stay on) the last known-good published state — the only outcomes are "sync forever with this bad content failing" or "process exits and never syncs again." This mirrors the reported bug class where a single guaranteed-to-fail input (there: an invalid bid; here: a commit that breaks `configureWorktree`) is sufficient to deny service to the whole system, and the affected party is not the attacker but the legitimate consumers of the synced data.

### Impact Explanation
This qualifies as "persistent sync denial": once the poisoned commit is fetched, git-sync will either (a) loop forever failing to converge (if `--max-failures` is set negative), leaving consumers on a stale/never-updated symlink target, or (b) with the documented default configuration (`--max-failures=0`), exit the process entirely after the very first failure, which in a Kubernetes sidecar deployment typically causes the whole pod to be marked unhealthy/restarted, and the same poisoned commit will be re-fetched and fail again on every restart, resulting in a crash loop and permanent denial of service for the application relying on the sidecar. No privileged operator action, leaked credentials, or malicious node/operator is required — only the ability to get a bad commit onto the ref that git-sync is configured to track (the same threat actor implied in the referenced report: someone who can submit "invalid" data that the syncing/aggregating system must process).

### Likelihood Explanation
Any repository where the synced ref (branch/tag/HEAD) can receive commits from a less-trusted party (e.g., PR merges, bots, external contributors with branch push rights, or a compromised upstream/submodule dependency) can trigger this. Submodules are enabled by default (`--submodules=recursive`), so a change to `.gitmodules` or to any second/third-level submodule URL is enough. Because `--max-failures` also defaults to `0`, no special operator misconfiguration is needed to hit the worst-case (immediate process exit) outcome — this is the out-of-the-box behavior.

### Recommendation
- Distinguish between transient (network/auth) failures and deterministic content failures where feasible, and avoid immediately aborting on the very first content-related error when `--max-failures` is left at its default; consider raising or explaining the default more prominently, or defaulting to a small positive retry budget.
- When a fetched commit repeatedly fails `configureWorktree`/submodule initialization, keep serving the last successfully published symlink target instead of leaving the whole process stuck or exiting, and surface a clear, sustained metric/error state for operators (already partially done via `updateSyncMetrics(metricKeyError, ...)`), so a single bad commit degrades to "stale but serving" rather than "denied".
- Consider adding a configurable "quarantine" of a specific hash that has failed N times, so the loop can keep polling for newer commits instead of being wedged on the same broken hash forever.

### Proof of Concept
1. Point `git-sync` at a repo with `--submodules=recursive` (default) and default `--max-failures=0`.
2. Attacker (someone with push rights to the tracked branch, or control of a submodule dependency) pushes a commit that adds/updates `.gitmodules` to reference a submodule URL that will always fail to fetch (e.g., an unreachable host, or a `file://` URL disallowed by `protocol.file.allow` on the git-sync side).
3. `git-sync`'s next `SyncRepo` call fetches the new commit, then `configureWorktree` runs `git submodule update --init --recursive`, which fails every time because the URL/protocol is invalid — see the unconditional submodule step: [5](#0-4) .
4. `SyncRepo` returns an error; the main loop increments `failCount` and, since `--max-failures` defaults to `0`, immediately logs "too many failures, aborting" and calls `os.Exit(1)`: [1](#0-0) .
5. In a Kubernetes sidecar deployment this manifests as a permanent crash-loop of the `git-sync` container, denying the consumer application any further updates (and blocking the initial sync entirely if this is the very first commit ever synced).
