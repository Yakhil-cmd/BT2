### Title
Webhook signature verification org and repository-name org are not bound - forged cross-tenant PR label overwrite - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives the signing organization from `repository.owner.login`, falling back to the top-level `organization.login` when the former is absent, and validates the HMAC against that organization's `webhook_secret`. `LabelCapturingHandler` (and all other PR handlers) resolve the target `Repository`/`Stack` purely from `params.repository.full_name`, with no check that this repository actually belongs to the organization that signed the request. An attacker who owns a legitimately configured Shipit tenant organization can forge a payload naming a victim tenant's repository and PR, and the write succeeds under the attacker's own valid signature.

### Finding Description
The broken binding: `signing_org` (used to select the HMAC secret in `Shipit.github(organization: repository_owner)`) `==` `owning_org` (parsed from `params.repository.full_name` and used to load the `Repository`/`Stack`) is assumed but never enforced.

`repository_owner` is computed as: [1](#0-0) 
falling back to `params.dig('organization', 'login')` only when `repository.owner.login` is absent from the raw JSON body the attacker fully controls (`request.raw_post` is attacker-supplied, this is not a real GitHub relay).

`verify_signature` then authenticates strictly against that resolved organization's own `webhook_secret`: [2](#0-1) 

Meanwhile `LabelCapturingHandler` (and `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) resolve the target repository solely via `params.repository.full_name`: [3](#0-2) 
and `Repository.from_github_repo_name` simply splits and looks up `owner/name` from that string, with no reference to whatever organization authenticated the request: [4](#0-3) 

`opened_active_stack?` then only checks `action == "opened" && stack.present?`: [5](#0-4) 
and `capture_labels` overwrites the pre-existing `PullRequest#labels` for that stack: [6](#0-5) 

Exploit flow: this is only reachable when the Shipit deployment runs in multi-organization mode (`github_default_organization` non-nil, i.e. `secrets.github` keyed by org), where `Shipit.github(organization:)` actually looks up a per-org config and secret: [7](#0-6) 
The attacker owns `attacker-org` as one of the configured tenant organizations (with its own `webhook_secret` that they legitimately possess, not stolen from Shipit). They POST to `/webhooks` a hand-crafted JSON body where `repository.full_name = "victim-org/tracked-repo"`, `repository.owner.login` is omitted (or set to anything), and a top-level `organization.login = "attacker-org"` is included, signed with the `attacker-org` webhook secret. `verify_signature` resolves `repository_owner` to `"attacker-org"` (fallback path) and the HMAC check passes using attacker's own valid secret. `Shipit::Webhooks.for_event('pull_request')` then dispatches to `LabelCapturingHandler`, which loads `victim-org/tracked-repo`'s existing `Stack`/`PullRequest` (already present from a legitimate earlier PR open) and overwrites its `labels` with attacker-controlled values.

No existing guard prevents this: `drop_unhandled_event` only checks event type presence; the `ExplicitParameters` schema in the handler only requires `repository.full_name` as a `String`, with no format or ownership constraint; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` check anywhere in this webhook path; `Repository`'s `owner`/`name` format validators only constrain characters, not which org may reference them; and `verify_signature`'s org resolution is entirely decoupled from the org later used to locate the target record.

### Impact Explanation
A payload authenticated under one tenant organization's own valid webhook secret can mutate a `PullRequest#labels` record belonging to a different tenant's repository (`victim-org/tracked-repo`), which is a cross-tenant write on a record the attacker's org never authenticated for. This is repeatable against any repository/PR number the attacker can guess or observe (PR numbers are small sequential integers, environment name is `pr#{number}`), for every multi-org Shipit deployment. This matches the Critical category: "a payload for one repository mutating another's stack" under a forged/misattributed webhook signature — the signature is technically valid for the sender org but is accepted to authorize a mutation on a completely different org's data.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub organizations (`secrets.github` keyed by org name), and the attacker must control at least one of those configured organizations (i.e., they operate their own legitimate, low-trust GitHub App/org onboarded into the same Shipit instance as the victim org). Given that, the attacker only needs to know their own webhook secret (which they legitimately hold), craft an arbitrary JSON body, and know/guess the victim's `owner/repo` and PR number — no GitHub secrets, sessions, or private keys of the victim or of Shipit itself are required. This is feasible and fully repeatable per request.

### Recommendation
Bind the two identities: require that the resolved signing organization matches the owner segment of `params.repository.full_name` (and/or the `organization.login`/`repository.owner.login` fields) before dispatching to handlers, e.g. reject the request in `WebhooksController#verify_signature` or in `Shipit::Webhooks::Handlers::Handler` if `repository.full_name.split('/').first` does not case-insensitively equal the organization used to verify the signature.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb`):
1. Configure `Shipit.secrets.github` with two orgs: `victim-org` (secret `S_v`) and `attacker-org` (secret `S_a`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create `victim-org/tracked-repo` `Repository`, an existing `ReviewStack` for PR number `N` with `PullRequest#labels = ["legit-label"]` (assert `stack.pull_request.labels == ["legit-label"]` — left side of binding: owning_org = `victim-org`).
3. Build a raw JSON body: `action: "opened"`, `number: N`, `pull_request: {... labels: [{name: "attacker-label"}]}`, `repository: {full_name: "victim-org/tracked-repo"}` (no `repository.owner`), `organization: {login: "attacker-org"}`.
4. Sign the body with `S_a` (attacker-org's own secret) and set `X-Hub-Signature`, `X-Github-Event: pull_request`.
5. POST to `/webhooks`; assert `response.status == 200` (signature verified — right side of binding: signing_org = `attacker-org`, so `signing_org == owning_org` is `false` yet the write proceeds).
6. Reload the victim stack's `pull_request` and assert `labels == ["attacker-label"]`, proving `attacker-org`'s signature mutated `victim-org`'s pre-existing record.
