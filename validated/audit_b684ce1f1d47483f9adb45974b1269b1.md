### Title
Direct SPL-Token burns of LP tokens permanently desynchronize `PoolState.lp_supply` from the real LP mint supply, permanently freezing pool assets - (File: `programs/cp-swap/src/states/pool.rs`, `programs/cp-swap/src/instructions/withdraw.rs`)

### Summary
`PoolState.lp_supply` is a manually maintained field that is supposed to mirror the *true circulating* LP-token supply (its own doc-comment says "True circulating supply without burns and lock ups"), but it is only updated by the program's own `deposit`/`withdraw` instructions. Because LP tokens are ordinary SPL Token / Token-2022 tokens owned by the depositor, any LP holder can call the standard token program's `Burn` instruction directly on their own LP-token account, bypassing `cp-swap` entirely. This permanently reduces the real on-chain mint supply while leaving `pool_state.lp_supply` unchanged, so the constant-product withdrawal math forever uses an inflated denominator and a slice of the vault's real assets becomes permanently unclaimable by anyone.

### Finding Description
`PoolState.lp_supply` is defined and documented as the true circulating supply of LP tokens: [1](#0-0) 

It is only ever mutated inside the program's own `deposit` and `withdraw` handlers, in lock-step with the corresponding `token_mint_to`/`token_burn` CPIs:
- On deposit: [2](#0-1) 
- On withdraw: [3](#0-2) 

Both `deposit` and `withdraw` derive the amount of underlying token_0/token_1 to move using `CurveCalculator::lp_tokens_to_trading_tokens`, which takes `pool_state.lp_supply` (not the LP mint's actual `supply` field) as the denominator: [4](#0-3) 

The underlying formula is a simple ratio: `token_amount = lp_token_amount * vault_amount / lp_token_supply`: [5](#0-4) 

Because LP tokens are minted as ordinary SPL Token / Token-2022 tokens to the depositor's own token account (see the `owner_lp_token` account and `token_mint_to`/`token_burn` calls in `deposit.rs`/`withdraw.rs`), any LP holder is free to submit a standard `Burn` instruction directly against the token program (targeting the pool's `lp_mint` and their own LP token account) without ever calling into the `cp-swap` program. This is a fully permissionless, unprivileged action requiring only the holder's own signature on their own account — no cp-swap instruction is invoked, so `pool_state.lp_supply` is never decremented, while the LP mint's actual `supply` field is reduced by the token program itself.

From that point on, `pool_state.lp_supply` (used by every subsequent `deposit`/`withdraw`) is permanently larger than the real circulating LP-token supply. Every future withdrawal computes `lp_token_amount * vault_amount / lp_supply` with an inflated denominator, so the sum of assets ever redeemable by all remaining LP holders is strictly less than the vault's real balance. The residual assets corresponding to the burned LP tokens' notional share become permanently stranded in the pool vaults — no instruction path exists to reclaim them, since the LP tokens that would represent a claim on them no longer exist and `lp_supply` never self-corrects against the real mint supply.

### Impact Explanation
This breaks the pool's core accounting invariant that `lp_supply` accurately reflects redeemable claims on the vaults. Every direct burn of LP tokens (bypassing `withdraw`) permanently traps a proportional share of both `token_0` and `token_1` vault balances that can never be withdrawn by any party, and permanently degrades the token-per-LP redemption rate for all other current and future liquidity providers. This is a permanent freezing of LP/user funds within the constant-product curve accounting, reachable by any ordinary swapper/LP with a single transaction and no special privileges.

### Likelihood Explanation
High. Burning one's own SPL token balance is a standard, always-available, single-instruction operation on any Solana token; it requires no interaction with `cp-swap`, no special permissions, and no unusual preconditions — only holding LP tokens for a given pool, which any depositor obtains through the normal `deposit` flow.

### Recommendation
Do not rely on a program-maintained shadow counter for a fungible token's supply. Either:
1. Read the LP mint's authoritative `supply` field directly from the `Mint` account at the start of `deposit`/`withdraw` (as is already done for `token_0_vault`/`token_1_vault` balances) instead of trusting `pool_state.lp_supply`, or
2. If a cached field must be kept for compute-unit reasons, reconcile it against the mint's on-chain `supply` on every `deposit`/`withdraw` call and reject/adjust when a discrepancy is detected, or
3. Freeze the LP mint's authority such that only the pool's `authority` PDA can burn LP tokens (removing user-callable `Burn` as an out-of-band mutation path).

### Proof of Concept
1. Alice deposits liquidity via `deposit`, receiving `L` LP tokens; `pool_state.lp_supply` increases by `L`, matching the real LP mint supply.
2. Alice submits a standalone SPL Token (or Token-2022) `Burn` instruction directly to the token program, burning some amount `b` of her own LP tokens from her `owner_lp_token` account. This does not call any `cp-swap` instruction.
3. The LP mint's actual `supply` decreases by `b`, but `pool_state.lp_supply` is untouched (still counts Alice's burned `b` tokens as outstanding).
4. Any subsequent `withdraw` call by any LP holder computes `token_0_amount = lp_token_amount * vault_0_amount / pool_state.lp_supply`, using the stale, inflated `lp_supply`. Summed over all remaining LP holders, the total redeemable amount is short by `b / lp_supply` of each vault's balance — assets that are now permanently stuck in `token_0_vault`/`token_1_vault` with no LP tokens left to redeem them.

    pub fn lp_tokens_to_trading_tokens(
        lp_token_amount: u128,
        lp_token_supply: u128,
        token_0_vault_amount: u128,
        token_1_vault_amount: u128,
        round_direction: RoundDirection,
    ) -> Option<TradingTokenResult> {
        let mut token_0_amount = lp_token_amount
            .checked_mul(token_0_vault_amount)?
            .checked_div(lp_token_supply)?;
        let mut token_1_amount = lp_token_amount
            .checked_mul(token_1_vault_amount)?
            .checked_div(lp_token_supply)?;
