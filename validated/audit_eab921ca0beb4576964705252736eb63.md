### Title
`ReopenedHandler#unarchive?` bypasses `review_stacks_enabled: false` via operator-precedence bug when `provisioning_behavior` is `allow_with_label` or `prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` intends `repository.review_stacks_enabled` to gate *all* provisioning behaviors, but Ruby operator precedence (`&&` binds tighter than `||`) causes it to gate only the `allow_all` branch. When a repository has `review_stacks_enabled: false` but retains a previously-configured `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `provisioning_label_name`, a `reopened` webhook for a correctly-labeled PR still unarchives/provisions the stack.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` ⇒ `unarchive? == false` for every `provisioning_behavior`. The actual code at [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is only ANDed into the first disjunct; the other two disjuncts are evaluated independently of the flag. So with `review_stacks_enabled = false`, `provisioning_behavior = allow_with_label`, `provisioning_label_name = "deploy-preview"`, and the PR carrying that label, `unarchive?` still returns `true`.

`process` then calls `stack.unarchive!` [2](#0-1) , which routes into `ReviewStackAdapter#unarchive!`. If no stack exists it creates one and enqueues provisioning; if an archived stack exists it re-adds it to the provisioning queue and unarchives it [3](#0-2) . Both paths lead to `Shipit::ReviewStackProvisioningQueue.add(stack)`, which drives the deploy pipeline (task execution) for that PR's branch/environment.

Contrast with `LabeledHandler`, which correctly hoists the flag check to the top-level gate `respond_to_label_change?` so it applies uniformly to `archive?`/`unarchive?` [4](#0-3) . `ReopenedHandler` (and identically `OpenedHandler`, out of scope here) instead inlines the flag inside the per-behavior expression, introducing the precedence bug.

Existing guards do not catch this: signature/schema verification only authenticates that the payload came from GitHub for that repository (`params.repository.full_name` resolves the correct `Repository`), it says nothing about `review_stacks_enabled` semantics. `drop_unhandled_event`/`ExplicitParameters` validate shape, not this business-logic gate. The repository's own settings screen is the only control meant to prevent this, and it is exactly what's bypassed.

Exploit flow for an unprivileged attacker:
1. Attacker discovers (via repo's public label list, or by observing behavior) that a `provisioning_label_name` (e.g. `"deploy-preview"`) is configured on a target repository whose maintainers believe review-stack provisioning is fully disabled (`review_stacks_enabled: false`).
2. Attacker opens a PR, has it labeled with that label (per the threat model's stated capability), then closes and reopens it (or it's already closed/archived from prior activity).
3. GitHub sends a `pull_request` `reopened` webhook, which is processed by `ReopenedHandler`.
4. `unarchive?` returns `true` despite `review_stacks_enabled == false`, and the stack is created/unarchived and queued for provisioning — running deploy/build tasks that the operator believed were fully disabled.

### Impact Explanation
An attacker who can label and reopen a PR on any repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) can trigger unauthorized stack creation/unarchival and provisioning-task execution even though the repository operator disabled `review_stacks_enabled`, believing that to be a complete kill switch. This results in unauthorized deploy/provisioning task execution for that repository — matching the Critical category "an unauthorized deploy, rollback ... " since provisioning tasks execute build/deploy commands on the deploy host. It is repeatable against any repository matching this configuration (a plausible, common operational state per the question), but scoped per-repository — it does not let an attacker cross into a different tenant's repository or exfiltrate secrets, only bypass the intended disablement for the repo they target.

### Likelihood Explanation
Requires: target repository previously configured `provisioning_behavior` to `allow_with_label` or `prevent_with_label` with a `provisioning_label_name`, and later set `review_stacks_enabled` to `false` without clearing the behavior/label — a realistic sequence since these are independent, non-atomic settings fields [5](#0-4) . No Shipit credentials are needed; the attacker only needs standard PR/label/webhook-triggering capability against the target repo, consistent with the stated threat model. This is a pure logic bug, deterministically reproducible, no timing or race conditions required.

### Recommendation
Fix the operator precedence in `unarchive?` so `review_stacks_enabled` gates every branch, e.g.:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

Apply the identical fix to `OpenedHandler#provision?`, which has the same bug. Consider refactoring both to hoist the `review_stacks_enabled` check into the top-level `respond_to_pull_request_*?` gate, mirroring `LabeledHandler#respond_to_label_change?`, to prevent recurrence.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:

```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even if allow_with_label matches" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  handler = Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload)
  # Binding under test: review_stacks_enabled(false) must imply unarchive? == false
  assert_equal false, repository.review_stacks_enabled
  assert_equal false, handler.send(:unarchive?), "unarchive? should be false when review_stacks_enabled is false"

  handler.process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```

Before the fix, `unarchive?` returns `true` and the stack is unarchived/queued for provisioning despite `review_stacks_enabled == false`, failing the assertions; after applying the recommended fix, the test passes.
