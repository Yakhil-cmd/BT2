### Title
Webhook signature verification is keyed off an attacker-chosen organization field, letting an unsigned/mis-secured org bypass HMAC checks for other orgs' repos and teams - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to validate the `X-Hub-Signature` HMAC based on a field read directly out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), instead of the organization/repository that the event handler actually mutates. This is the same class of bug as the reported `HookBufferLib.readFrom()` issue: a value used to authorize/validate an operation is decoupled from the value that is actually acted upon, so the two can be made to diverge by an attacker who controls the intervening data.

### Finding Description
`repository_owner` is computed purely from the request body: [1](#0-0) 

That value picks the `GitHubApp` instance (and its `webhook_secret`) used to verify the signature: [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected org's config has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is documented as an optional/nilable field in the multi-org config schema: [4](#0-3) 

Crucially, the field used to select the verifying organization (`repository.owner.login` / `organization.login`) is independent from the field(s) the event handlers use to decide *what gets written*. For example `MembershipHandler` reads its own `organization.login` and `team.id`/`member.login` out of the same JSON body to create/lookup a `Team` and add a member to it: [5](#0-4) 

Because `WebhooksController#create` simply parses the raw JSON and passes it straight to the handlers, an attacker fully controls every key in the body, including adding a `repository.owner.login` key that a real GitHub `membership` webhook would never contain: [6](#0-5) 

**Attack shape:** an attacker (no Shipit session, no webhook secret, no GitHub App key) crafts a POST to the webhooks endpoint with:
- `repository.owner.login` = an org configured in Shipit whose `webhook_secret` is blank/nil (a supported, documented configuration state).
- `organization.login`, `team.id`, `member.login` = values pointing at a *different*, protected org's `Team`/membership record.

`verify_signature` resolves `Shipit.github(organization: "org-without-secret")`, and `verify_webhook_signature` returns `true` unconditionally regardless of the (missing or garbage) `X-Hub-Signature` header. The request then reaches `MembershipHandler#process`, which finds an *existing* `Team` by `github_id` (bypassing the `organization:` assignment, which only runs on creation) and calls `team.add_member(member)` for an attacker-supplied `member.login`, writing directly into the `memberships` table.

### Impact Explanation
If the targeted `Team` is one of `Shipit.github_teams` (the teams gating `User#authorized?`): [7](#0-6) 

then an attacker who has an ordinary, unprivileged Shipit account (created via public GitHub OAuth login, which requires no authorization) can have their own `login` added as a member of an authorization-gating team purely by forging a webhook against a mis-configured (secret-less) sibling organization, without ever presenting a valid HMAC for the org whose team is actually being modified. This is a direct escalation into `Shipit.github_teams` authorization — an explicitly listed High-impact outcome — achieved with no session, no API token, and no valid webhook secret for the affected organization.

### Likelihood Explanation
This requires the operator to run Shipit in the documented multi-organization mode with at least one configured organization lacking a `webhook_secret` — a state the shipped example config explicitly shows as valid (`webhook_secret: # nil`). Given that state, the exploit needs only a single crafted HTTP POST with attacker-controlled JSON; no GitHub infrastructure, TLS interception, or credentials are involved. The root cause is a structural mismatch in the controller/handler split (verification keyed on one payload field, mutation keyed on another, unrelated payload field), not a one-off typo, so it is reachable for every non-repository-scoped event (e.g. `membership`) whenever any org's secret is unset.

### Recommendation
Do not let the JSON body itself choose which secret verifies the JSON body. Bind webhook verification to the event's authoritative organization consistently with what handlers act on (e.g., require a match between `repository_owner`/`organization.login` used for verification and the fields the specific handler consumes, and reject if a `repository` key is present but unexpected for the event type). Additionally, do not allow an organization with a blank `webhook_secret` to implicitly authenticate for other organizations' resources — consider requiring `webhook_secret` to be present for any multi-org configuration, or scoping `verify_webhook_signature`'s bypass to only that organization's own resources.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <id_of_privileged_shipit_team>, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "org-with-no-webhook-secret" } }
}
```
- No `X-Hub-Signature` header (or a garbage value) is required, because `Shipit.github(organization: "org-with-no-webhook-secret")` resolves a `GitHubApp` whose `verify_webhook_signature` returns `true` unconditionally.
- `MembershipHandler` looks up the existing `Team` with `github_id == <id_of_privileged_shipit_team>` (ignoring the injected `repository` key entirely) and executes `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker's Shipit account membership in a team gating `Shipit.github_teams` authorization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
