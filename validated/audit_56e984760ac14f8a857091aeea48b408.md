### Title
Cross-tenant `Status` write via SHA collision in `StatusHandler#process` due to missing repository scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` globally, across all stacks/tenants, and calls `create_status_from_github!` on every matching row, without ever checking that the webhook's `repository.full_name` matches the repository owning that commit. This lets an attacker who controls a repository under any org configured in Shipit push a status webhook for a `sha` value that also exists as a `Commit` row belonging to an unrelated stack, and have Shipit write a forged `Status` to that unrelated stack.

### Finding Description
The broken binding: `payload.dig('repository', 'full_name') == commit.stack.github_repo_name` is asserted implicitly by `verify_signature` (which only checks that the payload is validly signed for `repository_owner`'s org) but is **never checked in `StatusHandler#process`**.

- `WebhooksController#create` → `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)` [1](#0-0) 
- `verify_signature` verifies the HMAC signature using the app configured for `repository_owner` (from `params.dig('repository','owner','login')`), i.e. it authenticates that the request came from *some* GitHub App installation for that org/repo, not that the `sha` inside belongs to that repo [2](#0-1) 
- `StatusHandler#process` ignores `payload`/`repository_name` entirely and queries commits globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) 
- The base `Handler` class provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler` never calls it — unlike `CheckSuiteHandler`, which does scope through `stacks.*` [4](#0-3) 
- `Commit#create_status_from_github!` unconditionally creates the status on whatever commit/stack it's called on: `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [5](#0-4) 
- The `sha` column is only indexed together with `stack_id` (not unique globally): `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, confirming the schema allows the same `sha` to exist as separate `Commit` rows across different stacks — this is expected/normal (e.g., shared history, cherry-picks, or here, an attacker deliberately crafting a content-identical git object).

Exploit flow: attacker crafts (or discovers) a commit whose SHA1 collides with an existing victim `Commit` row (trivial to arrange deliberately since SHA1 is a function of tree/parents/author/committer/timestamps/message — an attacker who controls their own repo and branch can freely choose those fields to match a known victim commit, e.g. reproducing a well-known empty/initial commit). Attacker pushes this to their own repo (which carries the org's installed GitHub App, so the request is normally and correctly signed for that org/repo) and triggers CI to emit `status: success` for that `sha`. `verify_signature` passes because the request truly is from that org. `StatusHandler#process` then finds **all** `Commit` rows with that `sha`, including the victim's, in a completely different stack, and writes a `Status` row there, potentially flipping `deployable?` to true and unblocking `ContinuousDeliveryJob` or unlocking merges on the victim stack.

None of the existing guards catch this: `verify_signature` authenticates the org, not the sha-to-repo binding; `drop_unhandled_event` and `ExplicitParameters` only validate the schema of `state`/`sha`/etc.; there is no `force_github_authentication`, `User#authorized?`, or `stacks`-scoping check inside `StatusHandler`.

### Impact Explanation
An attacker with no privileges beyond controlling their own GitHub repository (with the Shipit GitHub App installed, which is standard for any repo in a configured org) can inject arbitrary `success`/`failure`/`pending` `Status` rows onto commits belonging to stacks/tenants they never touched, as long as they can produce a `Commit` row with a colliding `sha`. This can flip `Commit#deployable?` and trigger `schedule_continuous_delivery`, causing an unauthorized deploy on another tenant's stack — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". This is repeatable against any stack/org configured in the same Shipit instance, and the blast radius spans all tenants sharing the deployment.

### Likelihood Explanation
Preconditions: (1) Shipit hosts ≥2 stacks/orgs, (2) a `Commit` row with a colliding `sha` already exists for the victim stack, (3) attacker can trigger a `status` webhook signed for their own org (trivial — any CI on their own repo does this). The attacker cost is finding/crafting a sha collision — while SHA1 collision is not free in general, this scenario explicitly allows the attacker to construct their own commit object (tree, parents, author, committer, timestamps) to match a pre-existing, often-predictable commit (e.g., an empty initial commit, a well-known vendored commit, or a commit whose git object is publicly known/reused across repos, such as squashed merges, cherry-picks, or common bootstrap commits). This is a real and demonstrable path in the engine, not a theoretical SHA1 break — the actual bug is that even a benign SHA collision (which git allows by design when objects are logically identical) is not repo-scoped by the handler.

### Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to stacks whose repository matches the webhook's `repository.full_name`, mirroring what `stacks` in `Handler` already provides, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

### Proof of Concept
Minitest integration test under `test/controllers/webhooks_controller_test.rb` (or a new `status_handler_test.rb`):
1. Create `stack_a` (org A, repo `org-a/repo`) and `stack_b` (org B, repo `org-b/repo`).
2. Create `commit_b = stack_b.commits.create!(sha: 'deadbeef...')` (simulating the collision, i.e. same `sha` value chosen by the attacker for their own commit).
3. Do NOT create any commit under `stack_a` for that sha (attacker's repo `org-a/repo` doesn't need a matching `Commit` row in Shipit at all — only the webhook payload references `repository.full_name = 'org-a/repo'`).
4. POST a signed `status` webhook to `/webhooks` with `X-Github-Event: status`, signature computed with org A's `webhook_secret`, and body `{ "sha": "deadbeef...", "state": "success", "repository": { "full_name": "org-a/repo", "owner": { "login": "org-a" } } }`.
5. Assert response is 200 OK (signature verified for org A).
6. Assert the binding: BEFORE — `payload['repository']['full_name'] == 'org-a/repo'` while `commit_b.stack.github_repo_name == 'org-b/repo'` (mismatch, i.e. the equality the question posits does NOT hold).
7. Assert AFTER — `commit_b.reload.statuses.last.state == 'success'`, proving Shipit wrote a `Status` to `stack_b` (org B) despite the verified payload only ever naming `org-a/repo`. [3](#0-2) [4](#0-3) [6](#0-5) [5](#0-4)
