### Title
Webhook signature verification is scoped to the payload's `repository.owner.login` while stack routing is scoped to `repository.full_name`, letting an attacker forge events for any repo by naming a no-secret organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the *unauthenticated* request body, while the actual event-processing handlers key off a *different* payload field, `repository.full_name`, to locate the `Repository`/`Stack` that gets acted upon. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches the matching `github_app` config via `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature`: [3](#0-2) 

Crucially, `GithubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is not configured: [4](#0-3) 

Multi-org deployments frequently have some orgs configured with `webhook_secret: nil` (see the double-app fixture) alongside orgs that do have a real secret configured: [5](#0-4) 

The org used to choose the verification config (`repository.owner.login`) is *not* the same field the event handlers use to decide which `Stack`/`Repository` to act on. `Handler#stacks` resolves the target purely from `payload.dig('repository', 'full_name')`: [2](#0-1) 

`PushHandler`, for example, uses that same `stacks` scope to trigger `stack.sync_github` for any matching branch: [6](#0-5) 

`Repository.from_github_repo_name` derives owner/name purely by splitting `full_name` on `/`: [7](#0-6) 

Because the controller's signature check and the handler's target-selection use two independently attacker-controlled JSON fields (`repository.owner.login` vs `repository.full_name`) that need not agree, an attacker can craft a single unsigned POST where:
- `repository.owner.login` = an organization configured in this Shipit instance with `webhook_secret` unset (causing `verify_webhook_signature` to `return true` unconditionally, bypassing the check entirely), and
- `repository.full_name` = `"<org-with-real-secret>/<real-repo>"`, i.e. the actual protected stack the attacker wants to affect.

This breaks the trust binding: *the organization whose webhook secret authenticated the request* ≠ *the repository whose stack is actually written to*. Before the attacker's request, only a validly-signed GitHub webhook for `org-with-real-secret` could trigger `GithubSyncJob`/status updates/etc. for that org's stacks; after this crafted request, an attacker with no credentials can drive the same handlers for that org's stacks by exploiting an unrelated org's missing secret.

### Impact Explanation
This allows an unauthenticated attacker to inject forged GitHub events (push, status, check_suite, membership, pull_request, etc.) against arbitrary tracked repositories/stacks, provided the deployment has at least one configured organization without a `webhook_secret`. Depending on which handler is triggered, this can force `GithubSyncJob` to run against attacker-chosen SHAs, fabricate commit statuses/check runs that gate deploy safety checks, or manipulate team/membership records used for authorization (`Shipit.github_teams`) — i.e., escalation into deploy-gating and authorization state without any valid credential for the targeted organization.

### Likelihood Explanation
Requires no authentication, no token, and no access to any secret — only that the Shipit instance has more than one GitHub App/org configured (a documented, supported configuration, see `secrets_double_github_app.yml`) where at least one has no `webhook_secret` set. This is a realistic, plausible operational configuration (e.g., internal test orgs, staging orgs, or orgs onboarded before a secret was set) that the code explicitly allows (`webhook_secret` is optional, not required).

### Recommendation
Do not let `repository.owner.login`/`organization.login` (used only to pick the verification key) diverge from the entity the handlers actually act upon. Either:
1. Require `webhook_secret` to be configured for every organization (reject with 422 if `webhook_secret` is blank, rather than treating it as "verification passed"), or
2. After verifying the signature, re-derive/cross-check that `repository.full_name`'s owner matches the `repository_owner` used to select and verify the signing key, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (has `webhook_secret` set, owns tracked `secure-org/critical-app` stack) and `open-org` (no `webhook_secret` configured), as supported by `secrets_double_github_app.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/critical-app"
  }
}
```
No `X-Hub-Signature` needed (or any value).
3. `verify_signature` resolves `repository_owner` = `"open-org"`, fetches `open-org`'s `GithubApp`, and `verify_webhook_signature` returns `true` immediately because `open-org`'s `webhook_secret` is blank [8](#0-7) .
4. `PushHandler` then resolves the target stack using `full_name` = `"secure-org/critical-app"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the real `secure-org/critical-app` stack [6](#0-5) , despite the request never being validly signed for `secure-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
