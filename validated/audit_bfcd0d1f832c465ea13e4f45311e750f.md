### Title
CCMenu API token is not stack-scoped, allowing cross-stack disclosure of deploy state - (File: `app/controllers/shipit/ccmenu_url_controller.rb`, `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The `initializeNextEpoch()` bug class described in the report is a binding break between a value that is *believed* to be constrained and the value that is *actually* enforced at execution time. The closest reachable analog in this engine is the CCMenu token issuance flow: the URL handed out by `CCMenuUrlController#fetch` is presented to the user as a **per-stack** read-only credential, but the underlying `ApiClient` it mints is never actually scoped to that stack, and the consuming controller (`Api::CCMenuController`) doesn't enforce stack scoping either. The binding "stack a token authorises" (intended: the single stack in the generated URL) is broken against "stack the token touches" (actual: every stack in the Shipit instance).

### Finding Description
`CCMenuUrlController#fetch` builds a stack-specific URL and appends a token from a lazily created `ApiClient`: [1](#0-0) 

```ruby
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end
...
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

`ApiClient.create_with` sets only `permissions`; it never sets `stack:`, so the created (or found) `ApiClient` record has `stack_id == nil` for every call, no matter which `stack_id` was requested in the URL. Because the lookup key is `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` (no stack in the key), **a single global `ApiClient` per user is reused for every stack** that user ever requests a CCMenu URL for — the token embedded in "stack A's" URL is byte-for-byte identical to the token that would be embedded in "stack B's" URL for the same user.

On the consuming side, `Api::CCMenuController` authenticates purely from this unscoped token and then resolves the target stack without ever checking the token's (non-existent) stack scoping: [2](#0-1) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

This bypasses `Api::BaseController#stack`, which is the method that actually enforces the stack-scoping invariant elsewhere in the API: [3](#0-2) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

So even in the hypothetical case where the token *were* correctly scoped, `CCMenuController` would still ignore that scoping because it defines its own unscoped `stack` method identical to `CCMenuUrlController`'s. Combined with `create_with` never actually persisting `stack:`, there is a double failure: the token is never scoped, and the enforcement point that would have honored scoping is overridden away.

The route confirms the token is usable against arbitrary stacks by simply changing the path segment, independent of the token's origin stack: [4](#0-3) 

### Impact Explanation
Any holder of a single CCMenu token (issued for one specific stack, and commonly pasted into CI dashboards, README badges, or CCTray-compatible tools which are often not access-controlled) can query `GET /api/stacks/:owner/:repo/:env/ccmenu?token=...` for **every other stack in the Shipit instance**, disclosing stack existence, latest build/deploy status, build label, and timestamps for repositories the token was never intended to expose. This is an unauthenticated (from the attacker's perspective, once the token leaks) cross-stack read of stack/deploy state — matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" via a broken token-to-stack authorization binding.

### Likelihood Explanation
No privileged access is required beyond obtaining a single previously-issued CCMenu token — a credential explicitly designed for low-friction embedding into third-party CI status tools, which increases the chance of accidental exposure (e.g., a public build-status page, log, or Slack message). No signature or additional secret guards the stack dimension; the vulnerability is triggered by simply changing the `stack_id` path segment on an otherwise valid, previously observed token.

### Recommendation
Persist the intended stack on the `ApiClient` created by `CCMenuUrlController#client` (e.g., `ApiClient.create_with(permissions: %w[read:stack], stack: stack)`), key the `find_or_create_by!` lookup on the stack as well as the creator, and remove the `stack` override in `Api::CCMenuController` so it uses `Api::BaseController#stack` (which honors `current_api_client.stack_id?`), ensuring the token can only ever resolve to the stack it was issued for.

### Proof of Concept
1. As user Alice, call `GET /ccmenu/acme/repo-a/production` → receive `ccmenu_url` containing `token=T` for stack `acme/repo-a/production`.
2. As the same Alice, call `GET /ccmenu/acme/repo-b/staging` → receive a `ccmenu_url` with the *same* `token=T` (since the underlying `ApiClient` lookup is keyed only on `creator`+`name`, and `stack:` is never set).
3. An attacker who has obtained `T` (e.g., scraped from a publicly embedded CI status widget for `repo-a`) issues `GET /api/stacks/acme/repo-c/production/ccmenu?token=T` for a stack Alice never generated a URL for.
4. `Api::CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate`, and `#stack` resolves `repo-c` directly via `Stack.from_param!` with no scoping check, returning `repo-c`'s build/deploy status to the attacker.
