### Title
Cross-organization webhook confusion: signature validated against `repository.owner.login` while handlers act on unvalidated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App organization secret to check the HMAC signature against using an unauthenticated payload field, while the downstream handlers use a *different*, independently attacker-influenced field from the same payload to select which `Stack`/`Repository` to actually mutate. In multi-tenant configurations these two fields are not the same authority, breaking the binding "organization whose secret authenticated the request" == "repository that gets written to."

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, which is read straight from the unverified request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` is a genuinely multi-tenant lookup: `secrets.github` can be keyed per organization, each with its own independent `webhook_secret`: [3](#0-2) 

Once the signature is accepted, `create` dispatches the *entire* raw JSON payload to event handlers: [4](#0-3) 

The base `Handler` class, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and the pull-request handlers, resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`, with no check that it is consistent with `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

For a legitimate GitHub-issued webhook these two fields are always consistent because GitHub itself populates both `repository.owner.login` and `repository.full_name` from the same repository object. The engine, however, never enforces this consistency itself; it treats `repository.owner.login` purely as a key to pick a secret, and `repository.full_name` purely as a key to pick a target. In a multi-tenant deployment (multiple organizations each with their own GitHub App installation and their own `webhook_secret` configured under `secrets.github`), an administrator of Organization A can craft an arbitrary JSON body directly against the public `/webhooks` endpoint (no session, no `ApiClient` token required — this endpoint is unauthenticated aside from the HMAC), setting:
```
"repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
```
and sign it with Organization A's own, legitimately-known `webhook_secret`. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches Org A's `GitHubApp`, and the HMAC check passes because Org A really does know their own secret. `Shipit::Webhooks.for_event('push')` then invokes `PushHandler`, whose `stacks` lookup uses `repository.full_name` = `"orgB/target-repo"`, i.e. Organization B's stack, entirely unrelated to the organization whose secret actually authenticated the request.

### Impact Explanation
This breaks the intended equality "the organization that authenticated the webhook == the organization whose repository is written to." Concretely, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on Organization B's stack using an attacker-controlled `after` SHA and `ref`, causing `GithubSyncJob` to fetch and append attacker-chosen commits into Org B's stack and re-cache its deploy spec — all without any credential belonging to Org B. `StatusHandler` similarly lets Org A forge arbitrary `commit_status` records (`state`, `context`, `description`) for any commit SHA that exists in Org B's stack merely by guessing/observing a SHA, which can flip CI status checks that gate deploys or merges. `MembershipHandler` and the pull-request handlers are exposed to the same class of confusion for team membership and review-stack provisioning. This falls squarely into the "unauthorized deploy" / cross-repository-write bucket of impact, achieved purely through a payload field that is acted upon but never covered by (i.e., cross-checked against) the field the signature was actually verified with.

### Likelihood Explanation
Exploitability requires the deployment to be configured in the documented multi-tenant mode (`secrets.github` keyed by multiple organizations, each with an independent `webhook_secret` — a first-class, supported configuration per `github_app_config`/`github_organizations` in `lib/shipit.rb`). Any party who legitimately administers one tenant/organization on such a shared Shipit instance already knows their own organization's `webhook_secret` and can freely POST arbitrary bodies to the public `/webhooks` endpoint with a valid signature for their own tenant. No repository write access, session, or `ApiClient` token to the *victim* organization is needed — only knowledge of the victim's `repository.full_name` (a public string). This is a realistic scenario for any shared/multi-org Shipit deployment.

### Recommendation
After signature verification succeeds for organization `O`, verify that every repository-scoped field consumed by the dispatched handler (`repository.full_name`, `organization.login`, `sender`, etc.) actually belongs to `O` — e.g., resolve the target `Repository`/`Stack` and assert `repository.owner == O` before invoking any handler, or better, look up the owning organization from the resolved `Repository`/`Stack` record rather than trusting the payload, and reject the webhook if the two disagree.

### Proof of Concept
1. Deploy Shipit with multi-tenant GitHub config: `secrets.github` containing both `orgA` (attacker-administered) and `orgB` (victim) each with their own `webhook_secret`.
2. Attacker, who legitimately knows `orgA`'s `webhook_secret` (they administer that org's GitHub App installation), builds a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature validates successfully.
5. `PushHandler` resolves `Repository.from_github_repo_name("orgb/target-repo")` and enqueues `GithubSyncJob` for Org B's stack with the attacker-supplied `expected_head_sha`, mutating Org B's stack state despite the request having been authenticated only against Org A's credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
