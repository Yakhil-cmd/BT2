This confirms the vulnerability. `CheckSuiteHandler#process` and `PushHandler#process` both scope their queries through `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), which restricts the effect of a webhook to the repository whose payload/signature authenticated it. `StatusHandler#process`, by contrast, bypasses `stacks` entirely and queries `Commit.where(sha: params.sha)` — a bare, repo-unscoped lookup across the whole `commits` table.

### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each`, with no scoping to the repository that authenticated the incoming webhook, unlike sibling handlers `PushHandler` and `CheckSuiteHandler` which both filter through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). Since git commit SHAs are content-addressed and identical across forks/mirrors that share history, a webhook correctly signed for repository A can create a `Status` row on a `Commit` belonging to stack B, if both repos happen to contain a commit with that SHA.

### Finding Description
The broken binding is: **"a status processed for repository R must only mutate `Commit`/`Status` rows whose `stack.repository == R`."** In code, this should hold as `commit.stack.repository.full_name == payload.dig('repository','full_name')` for every `Commit` touched, but `StatusHandler#process` never checks it: [1](#0-0) 

Compare to the repo-scoped siblings: [2](#0-1) [3](#0-2) 

and the base class helper `stacks`, which is available but unused by `StatusHandler`: [4](#0-3) 

`verify_signature` in the controller only confirms the payload is a valid webhook for `repository_owner` (the org named in the payload) — it says nothing about which SHAs that org is entitled to reference: [5](#0-4) 

Once `StatusHandler#process` finds any `Commit` row (across any stack) with a matching `sha`, it calls `commit.create_status_from_github!(params)`, which creates a `Status` and re-evaluates deployability/CI state for that commit's stack: [6](#0-5) 

That status then participates in `blocked?` and `deployable?` on the victim stack: [7](#0-6) 

and in `blocking?` scoping, gated by the victim stack's own `blocking_statuses` configuration (so the attacker doesn't even need to guess the context name if it's a commonly configured one like `ci/smoke`): [8](#0-7) 

**Exploit flow:** Attacker legitimately owns/controls repository A, which is registered as a Shipit stack (this is attacker-controlled and requires no privileged secret — GitHub issues the correctly-signed webhook itself, or the attacker relies on their own repo's real GitHub App/webhook installation). Victim stack B tracks repository B, which shares commit history with A (fork relationship, shared upstream, cherry-pick, or any scenario producing a byte-identical git commit object, hence identical SHA1). CI (or the attacker) posts a `status` event for that shared SHA, context `ci/smoke`, state `success` or `failure`, signed correctly for organization A. `StatusHandler#process` finds **both** commit A (legitimate target) and commit B (in the victim's stack) because the lookup is a bare `Commit.where(sha:)` with no repository predicate, and writes a `Status` onto commit B too. If stack B has `ci/smoke` in `blocking_statuses`, this flips `blocked?`/`deployable?` on stack B and can force or block a deploy that stack B's own CI never actually reported.

Existing guards do not prevent this: `verify_signature` validates only that the sender is a legitimate webhook source for the *named* organization in the payload, not that the SHA it references belongs exclusively to that organization's repositories; `ExplicitParameters` only validates the shape of `sha`/`context`/`state`, not their repository ownership; and `Handler#stacks` (which would fix this) is simply not invoked by `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository writes `Status` records (and therefore mutates CI/blocking state) for `Commit` rows belonging to a different, unrelated stack/repository — this is the "payload for one repository mutating another's stack/commit" case called out as Critical impact. If the victim stack has `blocking_statuses` configured for the forged context, this can force a deploy to proceed (by injecting a matching `success` status) or force a block/rollback of an otherwise-good deploy (by injecting a `failure`/`error` status), i.e., an unauthorized deploy or block on a stack the attacker does not control. This is repeatable against any victim stack that shares any historical commit SHA with a repository the attacker controls (fork relationships are extremely common and easy for an attacker to set up), and it requires no session, API token, or GitHub App/webhook secret belonging to the victim.

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a GitHub repository that is (or can become) tracked as some Shipit stack, so a genuinely-signed `status` webhook for that org can reach `/webhooks`; (2) attacker can produce or find a commit whose SHA is shared with a commit reachable in the victim's target stack (trivial via forking a public repo the victim also tracks, or common ancestor history, or `git commit --amend`/cherry-pick producing an identical tree+parents+timestamps); (3) victim stack must have `blocking_statuses` (or otherwise CI-gated deploy logic) configured for the forged context to see a ship/block effect, though even without that, an unwanted `Status`/`CheckRun` row is still written to a repo that didn't produce it. Attacker cost is low — no secrets beyond their own legitimate webhook credentials for their own repo, and the action is fully repeatable/scriptable against any stack sharing commit history with an attacker-controlled repo.

### Recommendation
Scope `StatusHandler#process` through the `stacks` helper (as `PushHandler` and `CheckSuiteHandler` already do) so status/commit lookups are restricted to stacks belonging to the repository that authenticated the webhook, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }` instead of the unscoped `Commit.where(sha: params.sha)`.
