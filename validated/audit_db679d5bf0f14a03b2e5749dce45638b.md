### Title
Malicious route venue injects a wallet-draining `transfer` under the caller's signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A route passed to `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` can name arbitrary pool/token contract addresses. Neither the controller nor the router allowlists the venues a hop invokes. Third-party code placed on the call stack below the caller's `require_auth` can issue `token.transfer(caller, attacker, victim_balance)` for any token, and Soroban records it as a child of the caller's signed authorization. A signed route therefore drains the caller's entire wallet — far beyond the routed amount — mirroring the connector-takeover class: a compromised/malicious downstream component executes under the user's ambient authority.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one `token_in.transfer(controller, router, amount_in)` and checks measured input/output deltas, but places no constraint on which contracts the route touches [1](#0-0) . The router's `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs` invokes whichever venue/pool addresses the payload's address registry names; only the router's own balance deltas are measured [2](#0-1) . The threat model itself acknowledges the gap: "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [3](#0-2) . Because every hop executes while the caller's `require_auth` root is on the stack, any contract invoked in a hop may call `require_auth`-protected functions (e.g., `transfer`) as the caller; the host attaches them to the caller's authorization tree, and an unsigned-tree simulation records them so a wallet that signs the recorded tree authorizes the theft.

### Impact Explanation
Theft of user funds exceeding the routed amount. The measured-delta and `RouterOverspend` checks in `swap.rs` only cover `token_in`/`token_out`; a rogue hop transfers arbitrary other tokens the victim holds — the harness test drains `WALLET_BALANCE` of an unlisted wallet token to the attacker while the swap still returns fair output and passes all protocol gates [4](#0-3) . Final account risk checks do not bound the loss either, since the stolen funds never touch the account books.

### Likelihood Explanation
Requires the victim to submit an attacker-crafted route and sign an authorization tree containing the injected child transfer — human interaction, like the CVE. However, routes are opaque XDR built off-chain (`StrategyPayload` registries + instruction stream), so users delegating route construction to a frontend or quote service have no practical way to detect a hostile pool index; the protocol offers no venue allowlist to bound the exposure. Any unprivileged attacker can deploy a rogue pool contract and craft the route.

### Recommendation
Enforce a governance-managed venue/pool allowlist in the swap-aggregator for every address a hop invokes (pool, token, share token), or have the controller simulate and verify that the caller's authorization tree contains exactly the expected `token_in` transfer child and reject otherwise. At minimum, decode and validate the authorization tree client-side and document that signing a tree with unexpected children is equivalent to handing over the wallet.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` implements the attack end-to-end:

1. `UnlistedPoolRouter::execute_strategy` calls whatever `hop_pool` the payload names [5](#0-4) .
2. `RogueHopPool::swap` issues `token.transfer(alice, attacker, WALLET_BALANCE)` for a token the protocol never listed [6](#0-5) .
3. Simulation records the theft as a child of Alice's `swap_collateral` authorization; once signed, Alice's wallet goes to zero while her account still receives fair swap output [7](#0-6) .

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
