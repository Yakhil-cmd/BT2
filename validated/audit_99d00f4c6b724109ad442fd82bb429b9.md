### Title
Encrypted-transaction sender/signer binding check is enforced only at the REST submission layer, not at mempool/VM admission - (File: `api/src/transactions.rs`)

### Summary
`EncryptedPayload::verify` binds a submitted ciphertext to the specific sender address and signer authentication keys via AEAD associated data [1](#0-0) . This binding is only invoked once, inside the REST API's `validate_signed_transaction_payload` before a `SignedTransaction` is handed to mempool [2](#0-1) . Neither `vm-validator/src/vm_validator.rs`, nor the Rust prologue construction in `aptos-move/aptos-vm/src/transaction_validation.rs`, nor the Move `transaction_validation::prologue_common`/`unified_prologue*` functions re-check this binding.

### Finding Description
For every other transaction admission path (peer-to-peer mempool gossip, direct BCS submission bypassing this specific REST handler, JSON-RPC batches routed differently, or any other ingestion path that constructs a `SignedTransaction` and passes it straight to `VMValidator`/`PooledVMValidator`), the associated-data binding check between the ciphertext and the claimed `(sender, signer_auth_keys)` is never performed. The only invariant enforced universally at VM admission (`prologue_common` in `transaction_validation.move`) is the standard signature/auth-key/sequence-number/chain-id/expiration check on the outer `RawTransaction` (via `as_encrypted_variant()`, which only covers the ciphertext's outer commitment fields — `payload_hash`, `encryption_epoch`, `claimed_entry_fun` — not the AEAD associated data) [3](#0-2) . The Move prologue and `TransactionAuthenticator::verify` only prove that the signer(s) signed over the `EncryptedInner` commitment fields; they never invoke `Ciphertext::verify` against `PayloadAssociatedData`. Consequently, admission of an encrypted transaction that reached mempool via any path other than this specific REST handler can succeed with a ciphertext whose AEAD associated data does not match the actual signer set/sender, because that mismatch is never checked outside `api/src/transactions.rs`.

### Impact Explanation
If the AEAD binding is the mechanism preventing a ciphertext produced under one (sender, signer-key) context from being validly decrypted/executed under another, skipping it at the mempool/VM admission boundary means the "should fail admission" invariant depends entirely on which network entry point handled the transaction. This is exactly the "pre-validation mismatch that causes a transaction which should fail admission to execute and commit" category: a transaction can be accepted by consensus/VM validation and executed to completion (its `payload_hash`/`claimed_entry_fun`/signature checks all pass) while bypassing the sender/signer binding that the encrypted-transaction design otherwise relies on for admission-time integrity.

### Likelihood Explanation
Uncertain/Medium: I was not able to fully verify with available tooling (1) whether `Ciphertext::verify`'s AEAD tag actually depends cryptographically on `PayloadAssociatedData` such that a mismatched sender/signer combination would fail decryption anyway at the validator/consensus decryption stage (`decryption_pipeline_builder.rs`), or (2) whether all admission paths in this repo actually funnel through the specific REST handler before reaching mempool (i.e., whether `vm-validator`/mempool truly has no other call site for this check). If the AEAD scheme's confidentiality/integrity already makes the binding self-enforcing at decryption time (independent of this explicit `verify()` call), then this is a defense-in-depth gap rather than an exploitable admission bypass, which would reduce this to informational rather than a proven high/critical finding.

### Recommendation
Move the `EncryptedPayload::verify(sender, signer_auth_keys)` check into a location that is invoked unconditionally on the VM/mempool admission path — e.g., inside `run_prologue_with_payload`/`validate_signed_transaction` in `aptos-move/aptos-vm/src/transaction_validation.rs` for `TransactionExecutable::Encrypted`, or inside `vm-validator/src/vm_validator.rs`'s `validate_transaction` — rather than solely in `api/src/transactions.rs`, so the invariant holds regardless of transaction ingestion path.

### Proof of Concept
Not independently reproducible with the available tools: constructing a valid AEAD ciphertext and confirming whether a mismatched-sender variant is accepted by `VMValidator::validate_transaction` (bypassing `TransactionsApi::validate_signed_transaction_payload`) requires running the encryption/decryption crypto pipeline (`Ciphertext::random`/`verify`) end-to-end, which is outside what I could execute via code search alone. This would need to be validated by a Devin session with actual test execution against `vm-validator` and `aptos-move/e2e-move-tests`.
