### Title
Unauthorized Registration as Cosigner Device Enables Private Payment Chain Exfiltration via `new_shared_address` - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts a peer-supplied shared-address definition and a `signers` map without verifying that the device claiming to control a given member address actually owns/controls it. This is the ocore analog of the n8n CVE-2026-85166 pattern: a reference to a sensitive credential/resource (there: a credential; here: control of an address's signing device) is persisted without checking that the party asserting the reference is actually entitled to it, and it is later resolved/exercised under a different identity's context, leaking sensitive data (private payment chain contents) to the unauthorized party.

### Finding Description
`handleNewSharedAddress(body, callbacks)` [1](#0-0)  validates only:
- that `body.definition` is a 2-element array and hashes to `body.address`,
- that each `signerInfo.address` in `body.signers` is a syntactically valid address (or `'secret'`),
- that the `address` embedded in the definition at a signing path matches the `address` declared in `body.signers` at that same path [2](#0-1) ,
- that the resulting definition is *structurally* valid via `validateAddressDefinition`, which calls `Definition.validateDefinition` with a fake unit (`authors: []`) and `bAllowUnresolvedInnerDefinitions: true` [3](#0-2) .

Nowhere is `signerInfo.device_address` validated against the actual owner of `signerInfo.address`. The sender of the `new_shared_address` device message fully controls the `device_address` field for every signing path in `assocSignersByPath`, including paths pointing at addresses the sender does not own. Once accepted, `addNewSharedAddress()` persists this attacker-supplied `(shared_address, address, signing_path, device_address)` tuple into `shared_address_signing_paths` [4](#0-3) .

This table is later used, without any additional trust check, to decide who receives forwarded private payment chains for that shared address:

These functions send the full private payment chain (unit, payload with inputs/outputs/amounts) to every `device_address` recorded for the shared address in `shared_address_signing_paths`, exactly like the n8n bug resolves an unauthorized credential reference and ships the secret to the referencing party. An attacker who sends an unsolicited `new_shared_address` message referencing a victim's real address, but declaring their *own* `device_address` as controlling that address's signing path, gets silently inserted as a "member device" of that composite address. If the victim's wallet is later a genuine co-signer of the shared address and receives a private payment chain destined for it (a legitimate use case such as an arbiter/bilateral contract or textcoin-based shared address), the victim's node will forward the private chain to the attacker's device, believing it to be a legitimate fellow signer, because `handleNewSharedAddress` never confirmed that the attacker's device actually possesses the signing key for the claimed member address.

### Impact Explanation
Private payment chains contain the amounts, asset identifiers, and previous-unit linkage of a private (denomination-based or divisible) asset transfer, which is precisely the confidential information the private-payment feature is meant to protect. This finding lets any correspondent (or anyone who can reach `handleMessageFromHub`'s `new_shared_address`/`create_new_shared_address`/`approve_new_shared_address` handlers as a paired device) register itself as an illegitimate cosigner device for an address it does not control, resulting in unauthorized disclosure of private transaction data (confidentiality loss on `SC:H`/`SI:H` scope), matching the "private payment chains" and "wallet and contract message handling" categories explicitly in scope. It does not directly enable double-spend or fund theft (the composite address still requires real signatures to spend), but it is a genuine confidentiality breach analogous to the CVE's credential exfiltration.

### Likelihood Explanation
Requires only that the attacker is a paired device (a correspondent) able to send wallet protocol messages (`create_new_shared_address` / `new_shared_address`) to the victim's wallet — no special privilege, hub compromise, or malicious-node capability is needed. The victim wallet processes these messages automatically in `handleMessageFromHub` without user confirmation for `new_shared_address` [7](#0-6) , and the missing ownership check is deterministic, not timing- or race-dependent.

### Recommendation
In `handleNewSharedAddress`, require the peer sending `new_shared_address` (or the underlying `create_new_shared_address`/`approve_new_shared_address` flow) to prove control of each address it claims a `device_address` for — e.g., by requiring the peer's device to be the same device that offered/approved that specific address, or by cryptographically requiring a signature/attestation tying `signerInfo.device_address` to `signerInfo.address` before persisting rows into `shared_address_signing_paths`. Alternatively, only add remote members to the forwarding list if this device independently learned (via its own pairing/wallet flow) that the given device controls the given address, rather than trusting the value asserted inside the incoming `new_shared_address` message.

### Proof of Concept
1. Attacker device A is a paired correspondent of victim V.
2. A crafts `arrDefinition = ["and", [["address", V_ADDRESS], ["address", A_ADDRESS]]]`, computes `shared_address = chash160(arrDefinition)`.
3. A sends V a `new_shared_address` message: `{address: shared_address, definition: arrDefinition, signers: {"r.0": {address: V_ADDRESS, device_address: A_DEVICE}, "r.1": {address: A_ADDRESS, device_address: A_DEVICE}}}`.
4. `handleNewSharedAddress` on V's node passes all checks (structural only) and calls `addNewSharedAddress`, inserting `(shared_address, V_ADDRESS, "r.0", A_DEVICE)` into `shared_address_signing_paths` — falsely recording that V's address's signing path is reachable via A's device.
5. Later, when V (as an actual owner of `V_ADDRESS`) receives/sends a private payment chain related to `shared_address` (e.g., someone pays the shared address a private asset, or V pays out from it), V's node calls `forwardPrivateChainsToOtherMembersOfAddresses`/`forwardPrivateChainsToOtherMembersOfSharedAddresses`, which looks up `shared_address_signing_paths` and sends the full private chain to `A_DEVICE`, disclosing the confidential payment details to the attacker.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function forwardPrivateChainsToOtherMembersOfSharedAddresses(arrChainsOfCosignerPrivateElements, arrPayingAddresses, excluded_device_address, bForwarded, conn, onDone){
	walletDefinedByAddresses.readAllControlAddresses(conn, arrPayingAddresses, function(arrControlAddresses, arrControlDeviceAddresses){
		arrControlDeviceAddresses = arrControlDeviceAddresses.filter(function(device_address) {

		walletDefinedByKeys.readDeviceAddressesControllingPaymentAddresses(conn, arrControlAddresses, function(arrMultisigDeviceAddresses){
