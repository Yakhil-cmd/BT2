### Title
Indirect (unvetted) correspondents are trusted with the full device-message subject set instead of the restricted safe-list - ([File: wallet.js])

### Summary
`handleMessageFromHub` in `wallet.js` is supposed to restrict messages from `bIndirectCorrespondent` devices — i.e., devices that were added automatically as cosigners of a wallet/shared-address (via `device.addIndirectCorrespondents`) and never went through the user's own pairing/confirmation flow — to a small safe subset of subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`). That restriction is dead code: the check is commented out.

### Finding Description
`handleMessageFromHub` receives `bIndirectCorrespondent` as a parameter and originally intended to gate which `subject`s an indirect (not directly paired/approved) correspondent could send: [1](#0-0) 
```
92: //if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
93: //    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
```
Because this check is commented out, an indirect correspondent — a device that the user never explicitly paired with or approved, but which was added to `correspondent_devices` with `is_indirect=1` purely because it was named as a co-signer's cosigner in a multisig wallet/shared-address negotiation (`device.addIndirectCorrespondents`, referenced from `wallet_defined_by_keys.js`) — is now treated with exactly the same trust level as a fully confirmed, user-approved correspondent for every subject in the switch statement, including:
- `sign` — request to sign an arbitrary unsigned unit for a shared/multisig address (`wallet.js` lines 251-330),
- `approve_new_shared_address` / `reject_new_shared_address` — approve or reject shared-address creation on behalf of that device,
- `new_shared_address`, `create_new_shared_address`, `create_new_wallet`, etc.

At the transport layer (`device.js`), the only gate for "unknown" (never-seen) devices is a small whitelist of subjects (`pairing`, `my_xpubkey`, `wallet_fully_approved`): [2](#0-1) 
Indirect correspondents are already present in `correspondent_devices` (added programmatically, not through user pairing), so they pass this "correspondent known" check entirely and reach the `wallet.js` switch with full privileges once the second, more granular gate (the commented-out `bIndirectCorrespondent` check) is disabled.

This is directly analogous to CVE-2024-7049: a principal that is nominally in a "pending"/lesser-trust state (there: a user awaiting admin approval; here: a device that was never directly paired/approved by the wallet owner, only indirectly introduced as a cosigner) is able to obtain the same privileged capability as a fully-approved principal because a confirmation/authorization check that should gate that capability was bypassed (there: token issued before approval; here: the `bIndirectCorrespondent` subject restriction was removed).

### Impact Explanation
An indirect correspondent that a user never actually paired with can send `sign` requests for shared/multisig addresses, or send `approve_new_shared_address` / `new_shared_address` messages, causing the wallet UI's device layer to treat these as coming from a trusted co-signer. Depending on how the UI layer wires these events (`create_new_shared_address`, signing dialogs), this can facilitate confirmation-fatigue driven signing of unauthorized transactions or bogus approval of a shared address definition that the user did not intend, potentially leading to fund loss from a multisig/shared wallet whose membership integrity depended on the disabled trust boundary.

### Likelihood Explanation
Indirect correspondents are added automatically any time a user participates in any multi-device wallet or shared-address negotiation with a cosigner who lists other cosigners (`other_cosigners` in `create_new_wallet`, or `device_addresses_by_relative_signing_paths` in shared address templates) — this is a normal, low-friction, attacker-reachable path (an "AA/wallet cosigner" can name arbitrary device pubkeys as indirect correspondents of the victim). No social engineering beyond initiating a routine multisig/shared-address flow is required.

### Recommendation
Re-enable and enforce the `bIndirectCorrespondent` subject whitelist check in `wallet.js`'s `handleMessageFromHub`, ensuring indirect correspondents can only send `cancel_new_wallet`, `my_xpubkey`, and `new_wallet_address` (or an updated, deliberately-reviewed minimal set), and that all other subjects (especially `sign`, `approve_new_shared_address`, `new_shared_address`) require a fully confirmed, directly-paired correspondent.

### Proof of Concept
1. Attacker crafts a multisig `create_new_wallet` or shared-address definition template that lists the victim device and an attacker-controlled device as indirect cosigners of some other cosigner, causing the victim's node to call `device.addIndirectCorrespondents` and insert the attacker device into `correspondent_devices` with `is_indirect=1`.
2. Attacker device, now "known" but never paired/approved by the victim, sends a `hub/message` with `subject: "sign"` (or `approve_new_shared_address`) addressed to the victim.
3. Because the correspondent is "known" (device.js check passes) and the `bIndirectCorrespondent` restriction in `wallet.js` is commented out, the message is processed with full trust, triggering signing/approval logic intended only for directly-approved correspondents. [3](#0-2) [4](#0-3)
