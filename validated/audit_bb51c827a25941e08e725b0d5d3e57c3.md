### Title
Naive substring-based `---` splitting in `extract_frontmatter` lets a regex `pattern` value silently strip the `action: block` field, downgrading a deny rule to a non-blocking warn - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the frontmatter/body boundary with `content.split('---', 2)`, which matches the literal substring `---` anywhere in the text rather than requiring it to appear as its own line. If a rule's `pattern` (or `message`) field legitimately/maliciously contains a `---` substring before the real closing delimiter, the parser truncates the frontmatter at that point, silently dropping any fields (including `action: block`) that appear after it in the file. `Rule.from_dict` then falls back to the default `action = "warn"`, so a rule file that visibly declares `action: block` is enforced by `RuleEngine.evaluate_rules` as a non-blocking warning.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-103`) does:
```python
if not content.startswith('---'):
    return {}, content
parts = content.split('---', 2)
if len(parts) < 3:
    return {}, content
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

`str.split('---', 2)` splits on every occurrence of the 3-character substring `---`, not on lines that are exactly `---`. Any occurrence of three consecutive dashes inside the `pattern:` value (e.g. a regex for diff hunks, CLI flag separators, or an attacker-crafted pattern) before the real closing `---` line will be treated as the second delimiter. Everything after that point — including a later `action: block` line — falls into `parts[2]`, i.e. the raw message body, and is never parsed into the `frontmatter` dict.

Example:
```
---
name: block-dangerous-rm
event: bash
pattern: "rm -rf ---force"
action: block
---
Blocked!
```
`split('---', 2)` yields `parts[1] = "\nname: block-dangerous-rm\nevent: bash\npattern: \"rm -rf "` and `parts[2] = "force\"\naction: block\n---\nBlocked!"`. The frontmatter dict therefore has no `action` key.

`Rule.from_dict` (`plugins/hookify/core/config_loader.py:75-84`) then does `action=frontmatter.get('action', 'warn')`, defaulting to `"warn"`. [2](#0-1) 

`RuleEngine.evaluate_rules` branches purely on `rule.action == 'block'`; anything else goes to `warning_rules`, which only sets `systemMessage` and does **not** deny the tool call: [3](#0-2) 

`pretooluse.py` prints the engine's result JSON and always `sys.exit(0)`, so a rule silently downgraded to `warn` produces only an informational message while the dangerous `Bash`/`Edit`/`Write` tool call proceeds. [4](#0-3) 

The `/hookify` command (`plugins/hookify/commands/hookify.md`) is the documented entrypoint that authors these `.claude/hookify.*.local.md` files, including the `pattern:` field that end users/agents fill in with arbitrary regex text, and explicitly instructs generating `pattern: {regex pattern}` and `action: {warn|block}` fields adjacent to each other in the same frontmatter block: [5](#0-4) 

No line-anchoring, no YAML library, and no re-validation step exists anywhere in `config_loader.py` to guard against a `---` occurring mid-value; `load_rule_file` only guards against I/O and totally-missing frontmatter, not against a truncated/malformed one. [6](#0-5) 

### Impact Explanation
A hookify rule that a repository maintainer intends as a hard `block` (e.g. against `rm -rf`, `chmod 777`, writing to `.env`, etc.) can be silently coerced into a `warn`-only rule purely by the shape of the `pattern` string (any embedded `---`), without any visible change to the semantically-meaningful part of the file. This breaks the stated invariant that "a deny rule must never be parsed into a non-blocking configuration," and results in unauthorized local command execution: `Bash`/`Edit`/`Write` tool calls that the user believes are hard-blocked by hookify instead execute after showing only a warning message, bypassing the local guardrail that was supposed to stop them.

### Likelihood Explanation
This requires no special privilege beyond the ability to place or influence a `.claude/hookify.*.local.md` file's `pattern`/content (e.g. via the `/hookify` command itself generating a pattern containing `---`, a committed rule file in the repo, or any process — including an LLM-driven agent — that writes such a file based on attacker-influenced input such as diff-like text containing `---`). Because `---` is a common token (diff markers, markdown horizontal rules, CLI separators), it can plausibly appear in generated or hand-written patterns/messages without obvious malicious intent, making the downgrade easy to trigger even unintentionally, and trivially reproducible deliberately.

### Recommendation
Replace the naive substring split with a line-anchored frontmatter parser: split on lines matching `^---\s*$` (e.g., using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` after verifying the first line is exactly `---`), so `---` appearing inside a value/body no longer acts as a delimiter. Additionally, add a post-parse validation in `load_rule_file`/`Rule.from_dict` that rejects or fails closed (i.e., treats unparseable/ambiguous rules as `block` rather than defaulting missing `action` to `warn`), and add a regression test asserting that a `pattern` containing `---` does not change the parsed `action` value.

### Proof of Concept
Unit test to add to `config_loader` tests:
```python
def test_dash_in_pattern_does_not_downgrade_block_action():
    content = (
        "---\n"
        "name: block-dangerous-rm\n"
        "event: bash\n"
        'pattern: "rm -rf ---force"\n'
        "action: block\n"
        "---\n"
        "Blocked!\n"
    )
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)
    # Expected (correct) behavior: action must remain "block"
    assert rule.action == "block", (
        f"Deny rule was downgraded to '{rule.action}' due to '---' inside pattern value"
    )
```
Running this against the current implementation demonstrates `rule.action == "warn"` (the `action` key is missing from `frontmatter` because the split truncated the frontmatter text before the `action:` line), proving the downgrade. An integration-level PoC can further feed the resulting `Rule` into `RuleEngine.evaluate_rules` with a matching `Bash` `tool_input` (`{"command": "rm -rf ---force"}`) and assert that the result lacks `hookSpecificOutput.permissionDecision == "deny"`, confirming the dangerous command would not be blocked by `pretooluse.py`.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
