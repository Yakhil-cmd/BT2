### Title
Webhook signature is validated against the organization derived from an unauthenticated payload field, while handlers act on a different, independently-read repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
The Shipit multi-tenant GitHub App configuration keys webhook secrets per organization: `Shipit.github(organization:)` looks up `secrets.github[organization]` and instantiates a distinct `GitHubApp`/secret per org key. [1](#0-0) 

`WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification by reading `repository_owner`, which is computed directly from the *unverified* JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) before the signature has been checked: [2](#0-1) [3](#0-2) 

After verification succeeds, `#create` dispatches the *same raw payload* to the registered handlers: [4](#0-3) 

Each handler independently derives the repository/stack to act on from a *different* field of the same payload — `payload.dig('repository', 'full_name')` — via the base `Handler#repository_name`/`#stacks` helpers: [5](#0-4) 

and this is what drives real side effects, e.g. `PushHandler#process` calling `stack.sync_github` on the matched stack, or `StatusHandler`/`CheckSuiteHandler` writing commit statuses/check runs on it: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization authenticated (`repository_owner` used to pick the HMAC secret) == organization whose repository is acted upon (`repository.full_name`'s owner segment, used by handlers to select the `Stack`)**. Nothing in the controller enforces that these two independently-read strings agree; `repository.owner.login` and `repository.full_name` are two separate JSON keys in the same attacker-controllable body. Any principal that can produce a validly-signed payload for organization A's webhook secret (e.g. someone with legitimate access to configure/inspect a webhook for a repository under org A that this Shipit instance also serves) can set `repository.owner.login` (or the top-level `organization.login`) to `"orgA"` so that `verify_signature` selects and passes org A's secret, while setting `repository.full_name` to `"orgB/some-repo"` so the dispatched handler resolves and mutates a stack that belongs to an entirely different organization/repository that the attacker has no relationship to. This mirrors the reported bug class: the value the security check is bound to (`repository_owner`) is not the value the subsequent state-changing logic actually consumes (`repository.full_name`), so the "signature verified" guarantee does not transfer to the object being written.

### Impact Explanation
A successful forgery lets an attacker who controls org A's webhook secret trigger `GithubSyncJob`, commit-status writes, check-run refreshes, review-stack open/close/archive actions, or team/membership mutations against stacks/repositories belonging to a *different* organization served by the same Shipit instance, purely by mismatching `repository.owner.login`/`organization.login` against `repository.full_name` in a forged payload. This is a cross-tenant/cross-repository write achieved by exploiting a broken authentication-to-resource binding, matching the "cross-repository writes" Critical-impact category, since the org whose secret authorized the request is not the org/repository whose state is modified.

### Likelihood Explanation
Exploitation requires possession of a valid webhook secret for at least one organization configured in this Shipit instance's `secrets.github` — this is a real prerequisite, but per the audit rules a credential the app itself issues/holds for one tenant being reusable to write to a different tenant's data is precisely the class of trust-boundary break the analog targets (analogous to "org authenticated vs. repo written"). In a genuinely multi-tenant Shipit deployment (multiple orgs each with their own webhook secret, as the `github_app_config`/`TOP_LEVEL_GH_KEYS` design explicitly supports), this is directly reachable without needing a Shipit session, `ApiClient` token, or GitHub App private key — only a webhook secret for any one served organization, which is a much weaker credential than the ones the rules exclude (`api_clients_secret`, GitHub App private key, GITHUB_TOKEN, session).

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after selecting `repository_owner` for HMAC verification, re-derive the owner from `repository.full_name` (or `organization.login`) used by handlers and assert they match before dispatching; alternatively, have `Handler#stacks`/`#repository_name` consume the same authenticated organization value the controller used to pick the webhook secret, rather than independently re-reading `repository.full_name` from the same untrusted payload.

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` and `orgB`, each with distinct `secrets.github[:orgA][:webhook_secret]` / `secrets.github[:orgB][:webhook_secret]`, both served by the same Shipit instance, each with stacks tracked.
2. Attacker possesses `orgA`'s webhook secret (e.g. as an admin of a repo in `orgA` that is one of the tracked stacks — GitHub lets repo/org admins view/regenerate webhook secrets they configured).
3. Attacker crafts a `push` (or `status`/`check_suite`) payload where:
   - `organization.login` / `repository.owner.login` = `"orgA"`
   - `repository.full_name` = `"orgB/victim-repo"`, `after` = attacker-chosen SHA, `ref` = `refs/heads/master`
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` computes `repository_owner` = `"orgA"`, loads `orgA`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the HMAC was computed correctly with `orgA`'s secret over the exact raw body.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"orgB/victim-repo"`, resolving `orgB`'s stacks and calling `stack.sync_github(expected_head_sha: ...)` on `orgB`'s stack — a state change on an organization the request was never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
