### Title
Unrestricted swap routes let malicious venue contracts steal unrelated caller-wallet assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
An attacker can provide a user with a `swap_collateral` route that passes through a malicious venue contract. During execution, that contract calls `token.transfer(victim, attacker, amount)` for an unrelated wallet asset; Soroban simulation records the call beneath the victim's `swap_collateral` authorization, and signing that authorization executes the theft. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authorizes the caller, accepts the caller-provided `swap` route, withdraws collateral, and forwards that route through `withdraw_and_swap_from_supply`. [3](#0-2) 

`swap_tokens` invokes the configured router with the supplied `StrategySwap`, authorizes only the controller's exact input transfer, and afterwards checks only controller input spend, output receipt, and final account risk. [4](#0-3) [5](#0-4) 

The route's venue address is payload-controlled, and venue dispatch invokes the named pool without an allowlist; the Aquarius adapter directly calls that pool's `swap` function. [6](#0-5) [7](#0-6) 

Because `from.require_auth()` is resolved against the transaction authorization tree, a malicious venue can request a transfer from the transaction caller even though it is invoked below the router; the host attaches that transfer to the caller's authorization entry. [8](#0-7) 

### Impact Explanation
A successfully signed malicious route steals arbitrary wallet tokens that may be completely unrelated to the lending position, while still paying a fair swap output and leaving the position healthy. [9](#0-8)  This is direct theft of user funds and is not bounded by `total_in`, `min_out`, controller output measurement, or final health-factor checks. [10](#0-9) 

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-crafted route and sign the simulation-produced authorization containing the extra transfer, so it is not a fully unilateral drain. [11](#0-10)  However, route data is opaque to a normal wallet user, an honest route has no such child authorization, and an interface or route provider can induce the signature while preserving an economically valid swap. [12](#0-11) 

### Recommendation
Restrict execution to governance-registered venue contracts, or cryptographically bind route venues to an allowlisted venue registry before dispatch. [6](#0-5)  At minimum, do not rely on opaque route bytes: return a decoded venue/token manifest for wallet display, and require clients to reject any authorization tree containing child invocations unrelated to the expected input transfer. [12](#0-11) 

### Proof of Concept
1. Alice supplies USDC and owns `WALLET_BALANCE` of a token unrelated to the protocol.
2. The attacker deploys `RogueHopPool` configured with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` and makes its `swap` entrypoint invoke `token.transfer(Alice, attacker, WALLET_BALANCE)`. [13](#0-12) 
3. The attacker constructs a USDC→ETH route naming that contract as the hop pool and has Alice call `swap_collateral(Alice, account_id, USDC_key, amount, ETH_key, route)`. [14](#0-13) [15](#0-14) 
4. Simulation records `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` authorization. [16](#0-15) 
5. Signing that tree executes the legitimate swap while moving Alice's entire unrelated wallet-token balance to the attacker. [11](#0-10)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
