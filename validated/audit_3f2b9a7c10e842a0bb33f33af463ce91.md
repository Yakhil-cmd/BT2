### Title
Webhook signature verification selects the GitHub App/secret from an unsigned payload field that is decoupled from the repository the event handlers actually act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which configured GitHub App (and therefore which `webhook_secret`) to verify the request against based on `repository_owner`, a value read straight out of the untrusted JSON body before any authentication has taken place. The event handlers that subsequently process the webhook, however, resolve the target `Stack`/`Repository` using `repository.full_name` from that same body. Nothing ties the organization used to select/verify the signature to the repository the handler ultimately writes state for. This is the same class of bug as the report: two logically-linked values (the deployed token address vs. the address users hold; here, the "authenticating organization" vs. the "repository being written to") are allowed to diverge because the code trusts a non-authenticated value to make a security decision.

### Finding Description
`verify_signature` derives the org used to fetch the right `GithubApp`/secret purely from the request body: [1](#0-0) [2](#0-1) 

That org selection happens *before* the signature is known to be valid — it is only used to decide which secret to check the signature against, so `repository_owner` itself is completely attacker-controlled. Signature verification for a given org can also be a no-op: `GithubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is not configured, which is an explicitly supported/optional setting per the setup docs and example secrets files: [3](#0-2) 

Once the request passes (or is exempted from) verification, the actual event handling (e.g. resolving the `Stack`/`Repository` to update, enqueue syncs, statuses, etc.) is keyed off `repository.full_name` from the same JSON body — a separate field that is never cross-checked against `repository_owner`: [4](#0-3) 

So the binding that should hold — "the organization whose secret authenticated this request" == "the repository/organization the handler is about to act on" — is never enforced. An attacker who controls (or is a member of) any organization configured in Shipit's multi-org `github:` config with no `webhook_secret` set (or whose secret they know) can send a forged webhook whose `X-Hub-Signature` trivially passes (or is skipped) for that org, while setting `repository.full_name` to point at a completely different stack/repository that Shipit tracks.

### Impact Explanation
This lets an unprivileged external attacker forge GitHub webhook events (`push`, `status`, `check_suite`, `membership`, etc.) for stacks/repositories they do not control, as long as any org in the deployment's multi-org GitHub config has signature verification effectively disabled (no `webhook_secret`) or the attacker knows that org's secret. Depending on which handler is invoked, this can trigger `GithubSyncJob` for an arbitrary stack with an attacker-chosen `expected_head_sha`, inject fabricated commit statuses, or manipulate team/membership state — all without possessing any Shipit session, API token, or the real webhook secret for the targeted repository's GitHub App. This crosses the "organization authenticated vs. repository written" trust boundary called out in the rules.

### Likelihood Explanation
Exploitability depends entirely on the deployment's configuration: Shipit explicitly supports (and documents) multi-org GitHub App setups where `webhook_secret` is optional/nil per org. Any installation with at least one configured org lacking a webhook secret, or where an attacker has visibility into one org's secret, is directly exploitable with a single crafted HTTP request to `/webhooks`; no privileged credential is required.

### Recommendation
After selecting the GitHub App via `repository_owner` and verifying the signature, re-derive the repository's actual owner/org from the verified payload (`repository.full_name`) and require it to match `repository_owner` used for verification — reject the request otherwise. Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-org configuration; instead, fail closed (or require a non-empty secret per configured org) so that "verified" always implies the signature was cryptographically checked against the exact organization whose repository is being mutated.

### Proof of Concept
1. Configure (or find a deployment configured) with two GitHub orgs in `github:` — `orgA` (no `webhook_secret`) and `orgB` (a tracked Shipit stack, e.g. `orgB/victim-repo`).
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `orgA` has no `webhook_secret` [5](#0-4) .
4. The `push` handler resolves the stack via `repository.full_name` = `orgB/victim-repo` and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, even though the request was never authenticated against `orgB`'s GitHub App at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
