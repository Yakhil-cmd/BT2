## Analysis

This is confirmed: the analogous randomness primitive in ocore is the `number_from_seed(seed[, min, max])` oscript formula function used by Autonomous Agents (AAs). The seed is a formula expression evaluated entirely from data that is either fully known in advance to the trigger sender (e.g., `trigger.unit`, `trigger.address`, `params`, trigger `data`) or from the AA-response's own `timestamp`/`mci` (derived from the last stable MC unit at the time the trigger is processed) — both of which an unprivileged trigger sender can predict or influence by choosing when and what to post, exactly analogous to `block.timestamp`/`block.number` misuse in Solidity. [1](#0-0) 
`number_from_seed` hashes the evaluated seed with SHA-256 and maps it into a numeric range — deterministic and fully reproducible off-chain by anyone who knows the seed inputs. [2](#0-1) 
`timestamp`, `mci`, `trigger.unit`, `trigger.address`, `trigger.initial_unit`, `trigger.initial_address` are all formula variables exposed to AA authors as natural "seed" candidates. [3](#0-2)  and [4](#0-3)  show that `timestamp` in an AA response is simply the MC unit's timestamp (attacker can time/observe it, or in dry-run/estimate mode it is even taken from `Math.round(Date.now()/1000)` when no MC unit is yet available, per [5](#0-4) ), and `trigger.unit`/`trigger.address` are chosen or known by the sender before posting the trigger.

### Title
Predictable seed sources for `number_from_seed` in oscript enable trigger senders to precompute favorable AA outcomes - (File: formula/evaluation.js, formula/grammars/oscript.ne)

### Summary
`number_from_seed` is ocore's on-chain "randomness" primitive for AAs. Its output is a pure SHA-256 hash of the evaluated seed expression — it is deterministic, not derived from any unpredictable or committed entropy. If an AA is written to derive perceived "random" outcomes (loot drops, prize amounts, winner selection, etc.) from a seed built out of `trigger.unit`, `trigger.address`, `trigger.initial_unit`, `params`, or the response's own `timestamp`/`mci`, an unprivileged trigger sender can precompute the result before posting, and either post only when it favors them or continue posting new units/authors until they get parameters yielding the desired hash. This exactly mirrors the `block.timestamp`-based randomness bug class from the report, mapped from EVM to ocore's oscript language and AA execution model.

### Finding Description
`number_from_seed` computes `sha256(seed)` and maps the leading 8 bytes onto `[min,max]` via straightforward division/flooring, with no external unpredictability, commit-reveal, or VRF involved [6](#0-5) . AA authors are given only self-referential and publicly known/predictable values as candidate seeds: `timestamp`, `mci`, `trigger.unit`, `trigger.address`, `trigger.initial_unit`, `trigger.initial_address`, `params`, or trigger `data` [2](#0-1) . None of these values are secret or unbiased from the perspective of the party sending the trigger:
- `trigger.unit`/`trigger.address` are determined by the unit the attacker composes and signs themselves before broadcasting it, so the attacker can iterate over multiple candidate units/messages/outputs (each producing a different unit hash) off-chain, compute the resulting `number_from_seed` value for each candidate, and only broadcast the one unit whose seed yields the outcome that favors them.
- `timestamp` is either the last stable MC unit's timestamp at the moment of trigger dry-run/estimate (`Math.round(Date.now()/1000)` when unstabilized, as seen in `estimatePrimaryAATrigger`) [5](#0-4) , or the MC unit's timestamp once processed [3](#0-2) . An attacker with a full/light node can run the estimate/dry-run locally, see the resulting "random" value, and choose to withhold or resend the trigger unit until the timing (and thus the seed) produces a favorable draw, since posting is entirely under their control.
- `mci` is likewise known/predictable ahead of time from the current tip of the attacker's own node.

There is no protocol-level mechanism (VRF, oracle data feed commitment, hash of a future/unknown unit, or witness-signed entropy) forcing the seed to be unknown or fixed before the attacker decides whether/how to post their trigger unit.

### Impact Explanation
Any AA that uses `number_from_seed` seeded (directly or indirectly, e.g., hashed together with other known values) by attacker-controlled or attacker-predictable inputs to decide payouts, item/attribute assignment, or winner selection can be gamed by a single unprivileged trigger sender. This can result in improper fund transfers from the AA's balance (AA fund loss) to the attacker, or systematically unfair/inflated in-AA "asset"/state-variable outcomes (e.g., maximizing minted attributes analogous to `strAnity`/`agiAnity`/`intAnity` in the original report), without needing any special network privilege — purely by choosing when/what to post as a trigger.

### Likelihood Explanation
High for any AA built around `number_from_seed` using these documented, easily-guessable variables as the sole entropy source; this is the natural/idiomatic way to introduce "randomness" in oscript given the exposed variable set, and dry-run/estimate APIs (`aa_composer.estimatePrimaryAATrigger` / `dryRunPrimaryAATrigger`) make it trivial for an attacker to locally simulate outcomes before broadcasting [7](#0-6) .

### Recommendation
- Document prominently (and enforce via linting/validation warnings) that `number_from_seed` must never be seeded solely from attacker-controllable/predictable values such as `trigger.unit`, `trigger.address`, `timestamp`, or `mci`.
- Provide/encourage a commit-reveal pattern (e.g., seed combined with a value from a future not-yet-known stable unit/ball, or an oracle-provided VRF-style value via `data_feed`) so the seed cannot be known at the time the trigger sender decides to broadcast.
- Consider adding a formula-validation-time warning/complexity penalty when `number_from_seed`'s argument list can be statically shown to depend only on `trigger.*`/`timestamp`/`mci` without any external oracle/data-feed input.

### Proof of Concept
1. Deploy an AA whose payout/attribute-generation logic is: `var['roll'] = number_from_seed(trigger.unit, 1, 100);` and pays out a large bonus for `roll == 100`.
2. Attacker builds candidate trigger units off-chain (varying nonce/message fields that don't affect the AA logic — e.g., adding an unused `data` field or altering fee/definition ordering), computing the resulting `unit` hash for each and locally running `sha256(candidate_unit)` to predict `roll` exactly as `number_from_seed` would [8](#0-7) .
3. Attacker keeps iterating locally (no need to broadcast) until finding a candidate unit whose hash yields `roll == 100`.
4. Attacker signs and broadcasts only that winning unit, guaranteeing the maximum payout — equivalent to the reported `block.timestamp` grinding attack.
