### Title
`write:hook` permission lets a stack-scoped ApiClient create a global hook that receives every stack's events - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` scopes hook creation to a stack only by checking whether `params[:stack_id]` is present, not by validating that scoping against what the authenticated `ApiClient` is actually permitted to touch. A token that is bound to a single stack (`ApiClient#stack_id` set) but that carries the generic `write:hook` permission can hit the top-level `/api/hooks` route (which exists alongside the nested `/stacks/*stack_id/hooks` route) and create a hook with `stack_id: nil`, i.e. a "global" hook that is delivered for every stack's `deploy`/`rollback`/`task`/etc. events, not just the stack the token was scoped to.

### Finding Description
`ApiClient` can be scoped to a single stack via its `belongs_to :stack, optional: true` association, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scoping for stack-lookup helpers: [1](#0-0) 

However, permission checks are purely string-based and are not tied to that stack scoping: [2](#0-1) 

`Shipit::Api::HooksController` determines the target stack for a hook purely from whether `params[:stack_id]` happens to be present on the request, independent of whether the authenticated client is stack-scoped: [3](#0-2) 

`config/routes.rb` mounts `resources :hooks` twice: once nested under `/stacks/*stack_id/hooks` and once at the top level `/api/hooks`, both routing to the same `HooksController`: [4](#0-3) 

When a request hits the top-level route, `params[:stack_id]` is absent, so `stack_id` resolves to `nil` and `hooks.create(params)` creates a `Hook` with `stack_id: nil` — a "global" hook: [5](#0-4) 

Global hooks are delivered for every stack's events via `Hook.deliver`, which selects hooks with `stack_id IN (nil, stack_id)`: [6](#0-5) 

This is the same bug class as the analog report: the authorization decision is made on one identifier (the `write:hook` permission string, unqualified by stack), while the mutating action is bound to a different, broader scope (all stacks, via `stack_id: nil`) than what the token holder was provisioned for (a single stack via `ApiClient#stack`). The equality that should hold — "the set of stacks a token is authorized to touch" == "the set of stacks a hook created by that token can affect" — is broken: a client fixture such as `here_come_the_walrus` is scoped to a single stack (`stack: shipit`) via its `ApiClient.stack` association: [7](#0-6) 

If such a client is additionally granted `write:hook`, nothing in `HooksController` or `ApiClient#check_permissions!` prevents it from calling the un-scoped `/api/hooks` route and registering a global hook.

### Impact Explanation
A global hook receives `deploy`, `rollback`, `task`, `commit_status`, `merge`, and other events for every stack managed by the Shipit instance, including the deploy output/log payloads and commit information of stacks the token was never meant to access. Because `Hook#deliver_url` can point to an attacker-controlled endpoint, this becomes an unauthorized read of stack state / deploy output across all repositories managed by the instance — matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" once escalated past the intended per-stack authorization boundary. It does not by itself grant RCE or token exfiltration, so it should be assessed as a scope-escalation / authorization-boundary issue rather than a Critical finding.

### Likelihood Explanation
Exploitability depends entirely on operators issuing an `ApiClient` that is stack-scoped (has `stack_id` set) yet also carries the `write:hook` permission — a plausible but not universal configuration (the `PERMISSIONS` list treats `write:hook` as a standalone capability, not implicitly stack-scoped, and the UI/README present hooks as being registerable "per stack" or "globally" without calling out that a stack-scoped token can still create global hooks). No GitHub-side privilege is required; only an already-issued Shipit `ApiClient` token with `write:hook` is needed, which is consistent with the "attacker already holds some authorization" pattern of the analog bug (an already-authenticated fraud prover reusing its authority against an unintended target).

### Recommendation
In `Shipit::Api::HooksController#create`/`#stacks_id`, forbid creating (or reading) a global hook (`stack_id: nil`) unless the authenticated `ApiClient` is itself unscoped (`current_api_client.stack_id?` is false / `UnlimitedApiClient`). Concretely, when `current_api_client.stack_id?` is true, the resolved `stack_id` for hook operations must equal `current_api_client.stack_id`, and requests to the top-level `/api/hooks` route from a stack-scoped client should be rejected (403) rather than silently defaulting to `stack_id: nil`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A: `stack: stack_a`, `permissions: ['write:hook']` (as modeled by the `here_come_the_walrus` fixture pattern).
2. Authenticate as that client and issue: `POST /api/hooks` (the top-level route, not `/api/stacks/*stack_id/hooks`) with `delivery_url`, `events: ['deploy']`.
3. `HooksController#stack_id` returns `nil` because `params[:stack_id]` is absent, so a `Hook` is created with `stack_id: nil`.
4. Trigger a deploy on Stack B (unrelated to the token's authorized stack A). `Hook.deliver` matches the global hook via `for_stack(stack_id_B)` (`where(stack_id: [nil, stack_id_B])`) and delivers Stack B's deploy payload/output to the attacker-controlled `delivery_url`, even though the token was only ever authorized for Stack A.
