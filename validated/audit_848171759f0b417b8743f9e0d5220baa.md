### Title
AA payouts to multiple recipients in a `spender_attested` asset are merged into one payment message, so one unattested address blocks payment to all other recipients - (File: aa_composer.js, validation.js)

### Summary
When an Autonomous Agent (AA) sends multiple `payment` messages that pay out the same asset to different addresses, ocore automatically merges them into a single payment message with multiple outputs. If that asset requires attestation (`spender_attested: true`) and even one of the output addresses is not on the currently attested list, unit validation rejects the *entire* merged message — not just the offending output. This causes the whole AA response unit to fail and the trigger to bounce, denying payment to every other, perfectly legitimate/attested recipient bundled into the same message.

### Finding Description
`handleTrigger()` in `aa_composer.js` merges all payment messages/outputs paying the same asset into a single message before building the response unit: [1](#0-0) 

This merge is applied unconditionally for any set of AA-generated messages once the upgrade MCI is reached: [2](#0-1) 

Later, when the resulting unit is validated (`validateAndSaveUnit` → `validatePaymentInputsAndOutputs`), assets with `spender_attested = true` require **every** output address of the payment message to be attested, or the whole message — and therefore the whole unit — is rejected: [3](#0-2) 

Because the merge step combines outputs to different recipients into one message/array of `outputs`, a single blacklisted/unattested recipient address is enough to make `filterAttestedAddresses` return a mismatched count, causing `validatePaymentInputsAndOutputs` (and thus the AA-produced unit) to fail as a whole: [4](#0-3) 

Back in `aa_composer.js`, any error from `validateAndSaveUnit` results in the entire trigger being bounced, discarding the response and refunding only the trigger's own inputs (minus bounce fees) — none of the intended recipients, including the attested/legitimate ones, get paid: [5](#0-4) 

This mirrors the reported bug class exactly: a batch-payment loop/merge that is only as strong as its weakest recipient — one restricted (here: unattested) address forces the whole distribution to fail atomically, instead of failing only for that one output.

### Impact Explanation
An AA that pays multiple addresses in a single asset that uses `spender_attested` (e.g., a KYC/whitelisted stablecoin-like asset on Obyte) can have its entire payout batch fail merely because one recipient lost/never had attestation. Since the merge behavior in `mergeMessagesAndOutputs` is enforced by the protocol itself (not something AA authors can opt out of once `pemCurvesFixMci` is active), AA developers cannot isolate the failing recipient from the rest of the batch. Legitimate, attested users are denied their expected payment, bounce fees are consumed, and the AA's stored state changes are reverted, effectively freezing funds intended for uninvolved third parties. If the AA's logic deterministically recomputes the same output set on every trigger, this can create a persistent stuck condition, echoing the "increasing debt / unreachable resolution" scenario from the original report.

### Likelihood Explanation
Any AA using a `spender_attested` asset (a legitimate, publicly documented ocore/AA asset feature; see `oscript` samples that configure `spender_attested`) and paying more than one recipient of that asset in a trigger response is affected as soon as one recipient's attestation is revoked or was never granted — no attacker collusion with the network is required, only that the recipient list contain one non-attested address at validation time (which can be attacker-controlled if the AA lets users nominate payees, e.g. referral/multi-payout AAs).

### Recommendation
- Do not silently merge payment outputs across independent AA `payment` messages when the asset is `spender_attested`; instead, keep outputs to different addresses in a way that a validation failure on one address does not invalidate the others, or
- Have `aa_composer.js` pre-filter/validate attested status of each output address (via `filterAttestedAddresses`) before merging/sending, and route any output to a non-attested address to a separate failure/bounce path instead of failing the whole unit, or
- At minimum, document this coupling clearly so AA authors avoid combining `spender_attested` asset payouts to multiple recipients within a single trigger response, and provide state-var-driven retry/skip logic for addresses that fail attestation.

### Proof of Concept
1. Define an asset `A` with `spender_attested: true` and an attestor list.
2. Deploy an AA that, on a single trigger, sends two `payment` messages in asset `A`: one to address `X` (attested) and one to address `Y` (not attested / attestation revoked before the response unit is built).
3. At response time, `mergeMessagesAndOutputs()` in `aa_composer.js` (lines 1010-1041, invoked at line 1287-1288) merges these into one `payment` message with `outputs: [{address: X, amount: ...}, {address: Y, amount: ...}]`.
4. `validateAndSaveUnit` → `validatePaymentInputsAndOutputs` (`validation.js` lines 2630-2641) calls `storage.filterAttestedAddresses` on `[X, Y]`; since `Y` is not attested, `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, and the callback returns `"some output addresses are not attested"`.
5. `aa_composer.js` treats this as a fatal error and calls `bounce(err)` (lines 1405-1411), discarding the entire response — `X` never receives its otherwise-valid payment, purely because `Y` was bundled into the same merged message.

	// merges payment messages paying in the same asset into a single message,
	// and merges outputs paying in the same asset to the same address into a single output.
	// send-all outputs (amount === undefined) are left as they are and never merged with anything.
	// non-payment messages are left intact.
	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
