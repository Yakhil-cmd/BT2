### Title
CCMenu endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single `Stack` via the `stack_id` column, and every other API controller enforces that scope by resolving the requested stack through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to bypass that scoping entirely, so a token that is only supposed to authorize reads for one stack can be used to read build/deploy status for **any** stack in the installation.

### Finding Description
The binding that should hold for every stack-scoped API request is:

`current_api_client.stack_id (when present) == id of the stack the request actually reads/writes`

`Shipit::Api::BaseController` enforces this equality generically: [1](#0-0) 

Every "normal" API controller relies on this scoped `stacks`/`stack` helper, e.g. `Api::StacksController#stack`: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `#stack` method that calls `Stack.from_param!` directly instead of `stacks.from_param!`, completely skipping the `current_api_client.stack_id` restriction, while still authenticating via the same generic `ApiClient.authenticate(params[:token])` path and the same coarse `require_permission :read, :stack` check (which only checks the permission string, not which stack it applies to): [3](#0-2) [4](#0-3) 

`ApiClient` genuinely supports being scoped to a single stack (`belongs_to :stack, optional: true`, and `Stack has_many :api_clients`), which is the whole reason `BaseController#stacks` conditionally filters by `stack_id?`: [5](#0-4) 

Because `CCMenuController#stack` ignores this scoping, the equality is broken: the stack a token is authorized for (via `stack_id`) is no longer equal to the stack the request actually touches when hitting the CCMenu endpoint.

### Impact Explanation
Any valid `ApiClient` token with the `read:stack` permission — even one deliberately restricted to a single stack via `stack_id` — can enumerate `params[:stack_id]` and retrieve CCMenu XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for every other stack managed by the Shipit instance. This is an authenticated but unauthorized cross-stack read of stack/build state, matching the "High - unauthenticated read of stack state" impact bucket (the intended per-stack authorization boundary is bypassed even though a token is required).

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-permissioned API token (the exact kind of restricted credential the `stack_id` column is designed to support) can trigger this by simply changing the `stack_id` route/query parameter — no additional privilege, race condition, or timing is required, making this trivially and reliably exploitable by anyone possessing such a token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so it respects `current_api_client.stack_id` exactly like every other API controller.

### Proof of Concept
1. Create (e.g., via console/admin flow) a stack-scoped client: `ApiClient.create!(creator: user, name: 'ccmenu', permissions: ['read:stack'], stack: stack_a)`.
2. Using `stack_a`'s client `authentication_token`, request `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` for an unrelated `stack_b`.
3. `authenticate_api_client` succeeds (`ApiClient.authenticate(token)` returns the valid client) and `require_permission :read, :stack` passes because the client has `read:stack` in its permission list.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])`, returning `stack_b` regardless of the client's `stack_id`, and the controller renders `stack_b`'s deploy/build status — data the token was never scoped to access.
