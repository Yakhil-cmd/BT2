### Title
Stale attestation authorization after address definition change bypasses attestor revocation intent in AA `attestation[]` formula — ([File: formula/evaluation.js])

### Summary
The `attestation[...]` oscript/formula function used by Autonomous Agents (AAs) to check attestor-issued claims about an address does not exclude attestations that were issued before the target address's definition (i.e., its controlling keys/signers) was changed. This differs from the equivalent check used elsewhere in the codebase (`storage.filterAttestedAddresses`, used by `definition.js`'s `'attested'` operator and asset `spender_attested` payment validation), which explicitly discards attestations that predate the address's most recent `address_definition_change`. As a result, an AA that gates funds, privileges, or asset transfers on `attestation[...]` can be tricked by an address whose control has since passed to a different key holder but which still benefits from an attestation issued to the previous controller.

### Finding Description
`storage.filterAttestedAddresses` (storage.js) is the sanctioned way to check that an attestation about an address is still valid: it requires the attestation's `main_chain_index` to be **greater** than the `main_chain_index` of the address's last `address_definition_change`, so that any address whose signing definition changed after the attestation was made is no longer considered attested unless re-attested: [1](#0-0) 

This filter is used correctly in the definition-language `'attested'` operator: [2](#0-1) 
and for `spender_attested` assets during payment validation: [3](#0-2) 

However, the `attestation[...]` formula function available to AA oscript/ojson code (`formula/evaluation.js`) queries the `attestations`/`attested_fields` tables directly by `attestor_address` and `address`, bounded only by `mci`, with **no join or filter against `address_definition_changes`**: [4](#0-3) 

Because address definitions in ocore can be changed via an `address_definition_change` message (author.js/composer.js `composeDefinitionChangeJoint`) or via multi-signature "shared address" reconfiguration, control of an address (its effective owner/signers) can be transferred to a completely different party after an attestor has certified something about that address (e.g., KYC status, whitelist membership, reputation score). Once the address changes hands, the `'attested'` operator in a plain address definition would correctly reject the stale attestation (per the `main_chain_index >` filter), but any AA relying on `attestation[...]` in its formula to authorize spending, minting, or state changes will still accept the stale, no-longer-applicable claim.

This is directly analogous to the reported GitLab bug class: authorization (SSO/SCIM trust) tied to an entity persisted after the entity was effectively transferred to a new owner/context, allowing the old owner's previously granted trust to remain exploitable.

### Impact Explanation
Any AA that uses `attestation[...]` to gate privileged actions — e.g., releasing funds only to KYC/whitelisted addresses, allowing asset issuance/transfer only to attested identities, or unlocking escrow to an "approved" address — can have that gate bypassed. An attacker who acquires control of a previously-attested address (through a legitimate definition/key change, e.g., buying/taking over a wallet, or reconfiguring a shared address they are part of) inherits the old attestation and can pass the AA's authorization check without being re-vetted by the attestor. Depending on the AA's logic, this can lead to unauthorized fund release, asset transfer, or state changes controlled by the new (untrusted) key holder — i.e., AA fund loss/theft through an authorization bypass.

### Likelihood Explanation
`attestation[...]` is a documented, commonly used oscript/formula primitive for identity/KYC/whitelist-gated AAs. Reaching the bug requires only: (1) an attestor previously attesting an address, (2) the address's definition being changed afterward (a normal, permissionless operation any address owner/co-signers can perform), and (3) posting a trigger from that address to the vulnerable AA. No special privileges beyond normal user actions are needed, making this readily reachable by any AA trigger sender.

### Recommendation
Modify the `attestation[...]` evaluation in `formula/evaluation.js` to exclude attestations that predate the target address's most recent `address_definition_change`, mirroring the logic already implemented in `storage.filterAttestedAddresses` (storage.js lines 1960-1974). Concretely, both the "recent unstable AA units" query and the "stable units" query (lines 967-1004) should join/filter against `address_definition_changes` for the evaluated address and require `main_chain_index > IFNULL(last_definition_change_mci, 0)`, consistent with how `definition.js`'s `'attested'` operator already treats definition changes as invalidating prior attestations.

### Proof of Concept
1. Attestor `ATT` attests address `A` (owned by key `K1`) as KYC-approved via an `attestation` message.
2. An AA `X` contains formula logic such as `attestation[attestors="ATT", address=trigger.address]` to gate a privileged response (e.g., releasing escrowed funds only to KYC-approved addresses).
3. `K1` posts an `address_definition_change` on address `A`, transferring control to a new definition controlled by key `K2` (owned by an unrelated/untrusted party), e.g. by selling the wallet or via a shared-address reconfiguration.
4. The new controller (`K2`) sends a trigger from address `A` to AA `X`.
5. Because `formula/evaluation.js`'s `attestation[...]` query (lines 966-1004) does not check `address_definition_changes`, it still finds the old attestation issued to `A` while it was controlled by `K1`, and returns `true`/the attested value, letting `K2` pass the AA's gate without ever being vetted by `ATT`.
