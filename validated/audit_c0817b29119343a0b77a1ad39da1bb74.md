### Title
Cross-repository Status forgery via unscoped commit lookup enables unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the commit belongs to the repository that authenticated the webhook. Since `WebhooksController#verify_signature` picks the GitHub App/secret to verify against using the attacker-controlled `repository.owner.login` field of the payload itself, an attacker who owns any repository onboarded into the same Shipit instance can send a validly-signed webhook for their own org and write a forged `Status` row onto a commit that in fact belongs to a victim's stack, provided the sha matches (a routine occurrence for commits shared across forks/PR source branches). That forged status is then consumed by `MergeRequest#all_status_checks_passed?` inside `ProcessMergeRequestsJob#perform`, potentially causing `merge_request.merge!` to call `stack.github_api.merge_pull_request` with the victim's own GitHub credentials.

### Finding Description
The broken binding: `identity that signed/authenticated the Status webhook (attacker's org, verified via Shipit.github(organization: repository_owner))` should equal `identity that owns the Commit the Status is attached to (victim's repository)`, but it does not.

Path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) derives which GitHub App/secret to use for HMAC verification from `repository_owner`, which itself is read straight from the incoming JSON payload: `params.dig('repository', 'owner', 'login')` (app/controllers/shipit/webhooks_controller.rb:59-62). Nothing ties this "owner" to the commit/sha referenced later in the payload — an attacker who legitimately owns a repository/org registered in the same Shipit instance can sign a payload with their own valid `webhook_secret` and put *any* `sha` they want in the body.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then does:
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This is a global, unscoped lookup by `sha` across every stack/repository tracked by the Shipit instance — there is no check that `commit.stack.repository` matches the payload's `repository`/`repository_owner`.
3. Git commit SHAs are content-addressed and identical across forks; a commit pushed to an attacker-owned fork/repo (e.g., because a PR against the victim's stack was raised from that fork, which is standard GitHub workflow) shares the exact same sha as the commit tracked by the victim's `Commit`/`MergeRequest`. The attacker therefore does not need to guess a hash — they legitimately possess a repository containing that same commit object and can emit a real, signed webhook for it.
4. `ProcessMergeRequestsJob#perform` (app/jobs/shipit/process_merge_requests_job.rb:19-31) later runs (queued by ordinary Shipit polling/`Status#schedule_continuous_delivery`, no attacker interaction needed), calls `merge_request.refresh!`, then `merge_request.all_status_checks_passed?`, which is `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` (app/models/shipit/merge_request.rb:193-197) — this reads from the local `Status` rows, including the forged one written in step 2.
5. If the check passes, `merge_request.merge!` (app/models/shipit/merge_request.rb:164-191) calls `stack.github_api.merge_pull_request(...)` using the **victim's** GitHub credentials.

Existing guards that fail to stop this: `verify_signature` only proves the payload was signed by *some* org's secret — it never checks that the signing org matches the org/repository owning the commit the payload claims to update. There is no `repository_id`/`stack_id` filter anywhere in `StatusHandler#process` or `Commit.create_status_from_github!`.

I was not able to fully verify, in the time available, whether `Commit#refresh_statuses!` (invoked by `MergeRequest#refresh!` immediately before the status check, from GitHub using the victim's own credentials) subsequently overwrites/replaces the forged `Status` row before `all_status_checks_passed?` is evaluated, or whether it merely appends alongside existing statuses per-context. This affects exact exploit timing/reliability but does not change the fact that the underlying write in `StatusHandler#process` is unscoped and cross-tenant, which is itself the root-cause bug (a payload for one repository mutating a commit that belongs to another repository/stack).

### Impact Explanation
An attacker (owning any repository/org configured in the same multi-tenant Shipit instance, with no privileges on the victim's repo/team) can write arbitrary `Status` rows against commits belonging to unrelated victim stacks. When combined with a pending merge request whose head shares that sha (a realistic condition given the PR-from-fork workflow), this can cause `ProcessMergeRequestsJob` to execute an unauthorized `merge_pull_request` call using the victim's GitHub credentials — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The write is repeatable against any commit sha the attacker can produce/share with a victim repo, and is not limited to a single victim — it applies instance-wide to every stack sharing the multi-tenant Shipit deployment.

### Likelihood Explanation
Preconditions: multi-tenant Shipit instance with more than one org/repo onboarded (attacker owns at least one), victim stack has `merge_queue_enabled`, a pending `MergeRequest` whose `head` commit sha is also reachable/known to the attacker (typical for PRs raised from forks). Attacker cost is minimal: a single crafted, correctly-signed HTTP `POST /webhooks` request using their own legitimate `webhook_secret`. No Shipit session, API token, or GitHub App key is required. The main uncertainty is whether `Commit#refresh_statuses!`'s GitHub round-trip overwrites the forged status before the merge check — this affects reliability/timing but not the existence of the unscoped write itself.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other sha-keyed webhook handler) to the repository identified in the verified payload, e.g. join through `Commit -> Stack -> Repository` and filter by `repository_owner`/`repository_name` matching the payload's `repository` object, rejecting/ignoring updates for commits belonging to a different repository than the one whose webhook secret validated the signature.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, hypothetical additions):
```ruby
test "process does not attach a status to a commit owned by a different repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  attacker_repository_owner = 'attacker-org' # distinct org/app configured in Shipit
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker-forged',
    'repository' => { 'owner' => { 'login' => attacker_repository_owner } },
  }

  # Signed with attacker-org's own valid webhook_secret (Shipit.github(organization: attacker_repository_owner))
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
And an end-to-end assertion tying it to the merge job:
```ruby
test "forged cross-repo status must not allow ProcessMergeRequestsJob to merge" do
  victim_stack = shipit_stacks(:shipit)
  merge_request = shipit_merge_requests(:shipit_pending)
  # attacker sends a status for merge_request.head.sha signed as a different org
  Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload_for(merge_request.head.sha)).process

  victim_stack.github_api.expects(:merge_pull_request).never
  Shipit::ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
Both assertions should hold `commit.stack.repository != payload.repository` before and after processing; currently the code contains no such equality check, confirming the vulnerability.
