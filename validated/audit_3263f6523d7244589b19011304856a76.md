### Title
Data-feed key injection via unsanitized `feed_name`/value in `data_feed`/`in_data_feed` oscript functions - (File: data_feeds.js)

### Summary
The `feed_name` (and string `feed_value`) parameters accepted by the oscript `data_feed[[...]]` and `in_data_feed[[...]]` formula functions are validated only for non-emptiness/type, unlike the equivalent check applied to a posted `data_feed` message payload, which explicitly rejects embedded `\n` characters. Because the underlying key-value store keys for data feeds are built by naive string concatenation with `\n` as a field separator, an attacker who controls the formula's dynamic input (e.g., an AA trigger sender supplying `feed_name` via `trigger.data`) can inject `\n` separators into the query key, altering the intended query boundary between feed name and value — the same "unescaped delimiter" root cause as CVE-2022-45046's LDAP filter injection.

### Finding Description
Data feed values are stored in the key-value store with keys of the form:
`'df\n'+address+'\n'+feed_name+'\ns\n'+value+'\n'+mci` (or `n\n` for numeric), built in `main_chain.js` `addDataFeeds()`. [1](#0-0) 

When a unit's `data_feed` message payload is validated, the code explicitly guards against this exact class of bug by rejecting `feed_name`/value strings containing `\n`: [2](#0-1) 

However, when `feed_name`/`feed_value` are supplied dynamically through the oscript `data_feed`/`in_data_feed` functions (reachable from AA trigger data, e.g. `data_feed[[oracles=..., feed_name=$trigger.data.name]]`), neither the static formula validator nor the runtime evaluator perform this `\n` check — only emptiness/type checks are done: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

These unsanitized values flow straight into `data_feeds.js`, where the query key/range is built by direct concatenation with `\n`: [7](#0-6) [8](#0-7) 

Because the kvstore performs prefix/range matching (`gte`/`lte`/`lt`) on these composite keys rather than field-aware equality, an attacker-controlled `feed_name` containing embedded `\n` sequences can shift where the "feed_name" and "value" fields boundary is interpreted within the byte string. This lets the crafted query range overlap with keys that were legitimately stored under a *different* feed_name/value pair than the one the AA formula author intended to check, since the store has no schema enforcement beyond string concatenation. The same reachable path (`definition.js` `'in data feed'`, `'in merkle'`) also lacks a `\n` check on `feed_name` at both definition-time validation and evaluation time: [9](#0-8) [10](#0-9) 

This is structurally the same bug class as the reported LDAP injection: a filter/query is built by concatenating attacker-influenced strings with reserved delimiter characters, and the code fails to escape or reject those characters even though the codebase demonstrably knows to do so in a sibling code path (`validation.js`).

### Impact Explanation
An Autonomous Agent that conditions payouts or logic on the result of `data_feed[[...]]` / `in_data_feed[[...]]` with a feed name partly derived from trigger data could be manipulated by an unprivileged trigger sender into matching an oracle-posted key that does not correspond to the semantically intended feed name/value. This can cause an AA to believe a condition (e.g. "oracle confirmed outcome=X") is satisfied when it was not, resulting in AA fund loss/incorrect payout. Address definitions using `'in data feed'`/`'in merkle'` as an authentifier condition are similarly exposed if any part of the arguments can be influenced (directly or via formula) by the spending author, potentially enabling unauthorized fund release.

### Likelihood Explanation
Exploitation requires an AA (or address definition) design that passes attacker/trigger-controlled data into the `feed_name` (or value) argument of `data_feed`/`in_data_feed`/`in data feed` — a realistic but not universal AA pattern (oracle-lookup AAs parameterized by user input are common). Crafting a working collision additionally requires the attacker to know or guess a real, legitimately-posted feed_name/value pair from the relevant oracle to align the injected boundary — this is a moderate additional constraint that lowers but does not eliminate exploitability, since oracle feed names/values are often public/predictable (price feeds, poll results, etc.).

### Recommendation
Apply the same `\n` (and ideally full delimiter-set) rejection used in `validation.js` (`feed_name.indexOf('\n') >= 0`, value `indexOf('\n') >= 0`) uniformly to every code path that accepts `feed_name`/`feed_value` before they are used to build kvstore keys:
- `formula/validation.js`: `validateDataFeed()` and `validateDataFeedExists()`.
- `formula/evaluation.js`: `getDataFeed()` (case `'data_feed'`) and case `'in_data_feed'`.
- `definition.js`: `'in data feed'` and `'in merkle'` validation and evaluation branches.
- `data_feeds.js`: as defense-in-depth, reject/escape `\n` inside `dataFeedExists`, `readDataFeedValue`, and `readDataFeedValueByParams` regardless of caller, since this function is the common sink.

### Proof of Concept
Conceptual (not executed, requires a running node/AA to confirm exact byte-level collision):
1. An oracle regularly posts `data_feed` messages, e.g. `{"outcome": "no"}` from address `ORACLE`.
2. An AA is defined so that a trigger-controlled string is used as `feed_name` in `in_data_feed[[oracles="ORACLE", feed_name=$trigger.data.name, feed_value="yes"]]` (or a `data_feed[[...]]` read followed by comparison), intending to check a specific, distinct feed name chosen by the AA author.
3. An unprivileged user sends a trigger with `data.name` crafted to contain an embedded `\n` sequence reproducing the byte layout of the real key `df\nORACLE\noutcome\ns\nno\n<mci>` for the range query, causing the lookup to match the oracle's actual `outcome=no` post even though the AA logically intended to check for a different, unposted feed_name/value combination.
4. The AA branch depending on the falsely-true `in_data_feed` check executes, releasing funds it should not have.

Note: the precise byte-alignment needed to force a query-range collision was not verified against a live kvstore instance in this analysis (no execution environment available); the vulnerability is established at the level of "missing input sanitization that the codebase itself proves is necessary" (per the parallel `\n` check in `validation.js`), and a background Devin session with code execution would be needed to construct and confirm a concrete colliding key/value pair.
