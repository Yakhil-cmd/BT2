### Title
Cross-organization CI status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
### Finding Description
`WebhooksController#verify_signature` authenticates a webhook by resolving the signing organization strictly from the payload's `repository.owner.login` (or `organization.login`) field and checking the signature with that organization's own `webhook_secret`: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

That verification only proves the request came from a legitimate GitHub App installation belonging to organization *X*. Once verified, the controller dispatches the full JSON payload to the registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

For the `status` event, `Handlers::StatusHandler#process` uses the payload's `sha` field to look up commits **globally, across every stack in the entire Shipit instance**, without any scoping to the repository/organization that the signature verification bound the request to:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Contrast this with `Handlers::CheckSuiteHandler`, which correctly scopes lookups through `stacks`, itself derived from `Repository.from_github_repo_name(repository_name)` (the payload's own `repository.full_name`): [5](#0-4) [6](#0-5) 

`StatusHandler` does not use `stacks`/`repository_name` at all — it is the outlier that breaks the binding between "the organization whose webhook secret signed this request" and "the repository/stack whose commit is written."

Because `Commit#sha` is only unique per `(sha, stack_id)` (not globally), and the same commit SHA can legitimately exist in independent Shipit stacks (e.g., two different organizations each tracking their own fork of the same upstream open-source repository will share identical early/common commit SHAs), an attacker who controls (or has commit-status-writing access to) **any** GitHub repository connected as a Shipit stack can send a `status` webhook (via GitHub's Statuses API on their own repo) containing the SHA of a commit that also exists, unmodified, in a completely unrelated organization's Shipit stack. The webhook signature check passes (it only validates that the payload's declared organization owns that webhook secret — which is true, since it's the attacker's own org), and `StatusHandler` then writes a forged `success` (or any) CI status onto the *other* stack's commit.

### Impact Explanation
A forged `success` status on a foreign stack's commit feeds directly into `Commit#deployable?` (`success? && !blocked?`) and CI-gating logic (`Status.after_create :enable_ci_on_stack`, `schedule_continuous_delivery`), which can enable continuous deployment or bypass merge-queue/CI-required checks (`MergeRequest.required_statuses`, `ignore_ci`) for a stack the attacker has no legitimate access to. This can result in an unauthorized deploy being triggered by continuous delivery, or an unauthorized merge/ship decision being made for a commit that never actually passed the real repository's CI — matching the "unauthorized deploy/ship" and "cross-repository writes" Critical/High impact classes, entirely without needing any Shipit API token, session, or write access to the *victim* repository.

### Likelihood Explanation
The attacker needs only: (1) their own GitHub App/webhook installation on some organization that has at least one Shipit stack (a very low bar for anyone administering or contributing status checks to any tracked repo), and (2) knowledge of a shared commit SHA between their repo and the target stack's repo — which is common for forks of popular open-source projects, or can even be brute-forced/observed from public GitHub history. No interaction with the target organization, its GitHub App, or its Shipit instance credentials is required. This is a straightforward, single-request exploit once the shared-SHA precondition holds.

### Recommendation
Scope `StatusHandler#process` (and any other handler operating on payload SHAs) the same way `CheckSuiteHandler` does: resolve the target stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e., the inherited `stacks` helper) and restrict the `Commit.where(sha: ...)` lookup to `stacks.flat_map(&:commits)` (or `Commit.where(sha: params.sha, stack: stacks)`), so a webhook can only mutate commits belonging to the repository/organization that the verified signature is bound to.

### Proof of Concept
1. Attacker controls Organization A, which has a Shipit stack tracking `orgA/forked-project` (a fork of `upstream/project`). Organization A's GitHub App webhook secret is legitimately theirs.
2. Organization B independently has a Shipit stack tracking `orgB/forked-project`, also forked from `upstream/project`, sharing early commit history/SHAs with `orgA/forked-project`.
3. Attacker, using their own (legitimate) write access to `orgA/forked-project`, posts a commit status via the GitHub Statuses API for SHA `abc123` (a shared ancestor commit) with `state: success`.
4. GitHub delivers a `status` webhook signed with Organization A's `webhook_secret`. `WebhooksController#verify_signature` resolves `repository_owner` as `orgA` and verifies successfully against Org A's secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123')`, which matches the `Commit` row belonging to Organization B's stack (since `sha` is not unique across stacks), and calls `create_status_from_github!` on it. [4](#0-3) 
6. Organization B's commit now shows a forged `success` status it never earned, potentially unblocking CI-gated deploy/merge logic for Organization B's stack — with no credentials or access whatsoever to Organization B's repository or Shipit installation.
