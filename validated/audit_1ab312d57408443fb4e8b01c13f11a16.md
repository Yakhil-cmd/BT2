### Title
`is_valid_signed_package` / `validateSignedMessage` Do Not Bind Signed Packages to the Consuming AA Address, Enabling Cross-Contract Signature Replay - ([File: formula/evaluation.js])

### Summary
The oscript primitive `is_valid_signed_package(signed_package, address)` only verifies that `signed_package` is correctly signed by `address`; it never checks that the signed data was intended for the specific Autonomous Agent (`this_address`) that is evaluating it. Domain separation across different AA deployments must be added manually by the oscript author. Where it is omitted, a counterparty's off-chain signed message (order, channel-state update, price quote, etc.) produced for one AA instance can be replayed as valid input to a different AA instance that accepts the same signer and the same field schema, exactly mirroring the "Renegotiation Replays Possible" bug class in the source report (replay of a signature across multiple coordinator/contract instances because the contract's own address is not part of the signed data).

### Finding Description
`is_valid_signed_package` in `formula/evaluation.js` evaluates the supplied `address_expr`, checks only that it is a syntactically valid address, then hands the package to `signed_message.validateSignedMessage`: [1](#0-0) [2](#0-1) 

`validateSignedMessage` computes the hash-to-sign purely from the `signed_message`/`authors`/`last_ball_unit`/`version` fields of the package itself: [3](#0-2) 

Nothing in this hash, and nothing in `is_valid_signed_package`'s checks, includes the AA's own `this_address`. The only protections built into the primitive are: (1) the claimed signer address must match the signature, and (2) `last_ball_unit`/`version` bound the package to a point in DAG history (basic anti-tampering, not per-contract binding). There is no mechanism forcing the signed payload to identify *which* contract instance it is valid for.

Because of this, contract-level replay protection is entirely opt-in. The ocore reference sample `payment_channels.oscript` demonstrates the developer must manually add a `channel` field equal to `this_address` and explicitly check it: [4](#0-3) 

By contrast, the other reference sample `order_book_exchange.oscript` — shipped as an example of how to build a trading AA on top of `is_valid_signed_package` — does **not** include any such per-contract identifier in the signed order (`$order1`/`$order2`), only asset pair, amounts, price, and `last_ball_unit`: [5](#0-4) 

This is the same pattern as the reported vulnerability: "As more loan types will appear, more loan coordinator contracts could be deployed... this attack works as long as the data provided ... is the same." Here, if a trader signs an order for one order-book AA deployment, and a second, independently deployed order-book AA instance (same or compatible template) exists that accepts the same trader's signing address, that identical signed order remains valid input to the second AA as well, because neither the signature hash nor `is_valid_signed_package`'s validation binds the order to a specific `this_address`.

### Impact Explanation
An attacker (or a counterparty replaying an old but unexpired counter-signed message) can submit a trigger to a *different* AA instance than the one the signature was intended for, causing that AA to execute state transitions (balance debits/credits, channel closures, trade settlement) based on data the signer never authorized for that specific contract instance. This can cause AA fund loss/freezing and unauthorized spending of the counterparty's balance held in the "wrong" AA instance — a concrete violation of the intended authorization scope, matching the Medium severity of the original report.

### Likelihood Explanation
Exploitation requires only: (1) a signer who has funds/relationships with more than one AA instance built from a template that uses `is_valid_signed_package` without embedding `this_address` (or an equivalent unique identifier) in the signed payload, and (2) an attacker posting a normal trigger unit carrying the previously obtained signed package to the second AA. No privileged access, node compromise, or network attack is needed — any unit poster / AA trigger sender can perform the replay, and the primitive's documentation/sample code (`order_book_exchange.oscript`) does not warn against or prevent this, making the mistake easy for oscript authors to repeat.

### Recommendation
- Require or strongly encourage embedding `this_address` (or another AA/domain-specific identifier) inside `signed_message` payloads validated via `is_valid_signed_package`, and document this as a mandatory anti-replay control.
- Consider having `is_valid_signed_package` optionally take/enforce a domain-separation tag (e.g., automatically mixing `this_address` into the hash unless explicitly opted out) so that signed packages are bound to the consuming contract by default, similar to how unit-level `sig` authentifiers are inherently bound to `unit_hash_to_sign` of that specific unit.
- Update the `order_book_exchange.oscript` reference sample to include `this_address` (or a contract-unique salt) in the signed order fields and hash, so it does not model an unsafe pattern for developers to copy.

### Proof of Concept
1. Deploy AA₁ and AA₂ from the same "order book" template (both built on `order_book_exchange.oscript`-style logic), both accepting orders from trader T with signing address `A`.
2. T signs an order package `{sell_asset, buy_asset, sell_amount, price, address: A}` plus `last_ball_unit`, intending it only for AA₁ (e.g., sends it off-chain to a counterparty to fill on AA₁).
3. An attacker (or the counterparty) submits the *same* signed package as `trigger.data.order1` in a trigger unit to AA₂.
4. AA₂'s `is_valid_signed_package(trigger.data.order1, $order1.address)` returns `true` because the signature validly matches `A`, and nothing checks that the order was meant for AA₂ specifically — see `formula/evaluation.js` lines 1660-1699 and `signed_message.js` lines 262-272.
5. AA₂ executes the trade against T's balance stored in AA₂, debiting/crediting funds T never authorized for that specific AA instance — reproducing the "renegotiation replay" scenario from the external report.
