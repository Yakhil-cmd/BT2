### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while event processing acts on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, a value taken from the attacker-supplied JSON body itself (`repository.owner.login` or `organization.login`). The event handlers, however, never look at `repository.owner.login` — they resolve the `Stack`/`Repository` that will actually be mutated using `payload.dig('repository', 'full_name')`. Because these are two independent, attacker-controlled fields in the same unauthenticated POST body, an attacker can pick an organization that has no `webhook_secret` configured (a supported and documented configuration) to satisfy `verify_signature`, while pointing `repository.full_name` at a stack belonging to a *different*, properly-secured organization.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository the request mutates`. In this codebase that equality is never enforced.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and checks `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) .
- `repository_owner` is read straight from the untrusted payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) . The multi-org configuration format explicitly allows per-organization `webhook_secret` to be left empty [6](#0-5) .
- Once `verify_signature` passes, `WebhooksController#create` dispatches the same raw `params` (untouched) to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) .
- Every handler resolves the target repository via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a different field than the one used for signature-org selection — and finds stacks with `Repository.from_github_repo_name(repository_name)` [3](#0-2) .
- `PushHandler#process`, for example, uses this to find matching stacks by branch and immediately calls `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) , which enqueues `GithubSyncJob` to fetch commits and update the target stack's deploy state [9](#0-8) .

This is the same class of bug as LID-15: the authorization check (staking module nonce / active-operator check) is scoped to one entity, but the state-changing operation is actually keyed by a different, unchecked identifier (node operator ID vs. active flag). Here, the HMAC check is scoped by `repository.owner.login`, but the mutating operation is keyed by `repository.full_name` — an independently attacker-supplied field with no cross-check that the two agree.

### Impact Explanation
An unprivileged attacker who knows (a) that the target Shipit instance is configured with multiple GitHub organizations and (b) that at least one configured organization has no `webhook_secret` set, can forge a `push`, `status`, `check_suite`, `membership`, or `pull_request` webhook for a stack belonging to a *different*, secured organization, bypassing GitHub's webhook authenticity guarantee entirely for that repository. Depending on the handler this can: force out-of-band syncing/creation of commits and statuses for a protected stack (`push`, `status`), manipulate check-suite-driven merge/CI gating (`check_suite`), or inject/alter team membership records that back `Shipit.github_teams` authorization (`membership`), which is a listed High-impact escalation path (escalation into `Shipit.github_teams` authorization). Because commit/status state feeds directly into whether a deploy is allowed by Shipit, this can enable an unauthorized deploy path once combined with normal deploy UI actions.

### Likelihood Explanation
Requires only an unprivileged, unauthenticated actor able to send an HTTP POST to `/webhooks` — no Shipit session, API token, or GitHub write access needed. It further requires the target instance to use the (fully documented, supported) multi-organization GitHub App configuration with at least one org lacking a webhook secret, which is a realistic and explicitly documented deployment shape (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). Given this configuration shape, exploitation is a single crafted JSON payload with mismatched `repository.owner.login` and `repository.full_name` values — no timing races, no privileged prerequisites.

### Recommendation
Enforce that the organization used to select/verify the webhook secret is derived from (and matches) the same repository identity that handlers use to locate the target `Stack`/`Repository`. Concretely:
- Derive `repository_owner` from `repository.full_name` (split on `/`) rather than the separate `repository.owner.login`/`organization.login` fields, so both signature verification and repository resolution are keyed off the exact same value.
- Additionally, require that `webhook_secret` be present for every configured organization (fail closed) rather than silently returning `true` when absent, or reject requests when no secret is configured, to remove the two-line early-return bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `PublicOrg` (no `webhook_secret` set) and `SecureOrg` (with a `webhook_secret`) using the documented multi-org schema (`docs/setup.md` lines 182-209).
2. Ensure `SecureOrg/target-repo` is a tracked Shipit stack.
3. POST to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "PublicOrg" },
    "full_name": "SecureOrg/target-repo"
  }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "PublicOrg").verify_webhook_signature` returns `true` (no secret configured for `PublicOrg`) per `lib/shipit/github_app.rb` lines 76-83.
4. `WebhooksController#create` dispatches this payload to `PushHandler`, which resolves the stack via `repository.full_name` = `"SecureOrg/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: ...)`, triggering `GithubSyncJob` against the `SecureOrg` stack — despite the request never being signed by `SecureOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
