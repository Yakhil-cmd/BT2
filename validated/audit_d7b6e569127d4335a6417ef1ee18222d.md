### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` in `MembershipHandler#process` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the `Team` to mutate by `github_id` alone, with no check that the organization whose secret verified the webhook signature actually owns that team. An attacker who configures their own GitHub org in Shipit (a fully legitimate, self-service capability documented for "Using Multiple GitHub Applications") can sign an arbitrary `membership` payload with their own real `webhook_secret` and reuse the `github_id` of a different, already-authorized team, causing themselves to be added as a member of that team.

### Finding Description
The broken binding, stated as an equality: `signing_org (verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` must equal `team.organization (the org whose Team record gets mutated)`. Before tracing the code, this equality is assumed to hold because a webhook is only supposed to represent events from the org that signed it.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For `membership` events (no `repository` key), `repository_owner` resolves to `organization.login` from the payload — i.e., it verifies that the *signer* matches the org *named in the payload*. This check is internally consistent: it only proves "this body was signed by org X's real secret and claims to be about org X." It says nothing about which `Team` record in the database the body is allowed to touch.
2. `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . The `organization:` assignment only happens inside the `create` block, which never runs if a `Team` with that `github_id` already exists. There is no `where(organization: params.organization.login)` scoping the lookup.
3. `#process` then calls `team.add_member(member)` on whatever `Team` was found [4](#0-3) , and `Team#add_member` unconditionally appends the member [5](#0-4) .
4. `Team` records that gate authorization are populated from `Shipit.github_teams`, computed from operator-configured `oauth.teams` handles and their real GitHub `github_id` fetched from the GitHub API [6](#0-5) , [7](#0-6) . `User#authorized?` checks membership against exactly these teams: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) .

Attacker's exact request: the attacker owns/configures their own GitHub org "OrgB" in Shipit's multi-org config (a supported, self-service setup per `docs/setup.md`) and thus legitimately possesses OrgB's real `webhook_secret`. They POST to `/webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id": <victim_team_github_id>, "name":"...", "slug":"...", "url":"..."},"organization":{"login":"OrgB"},"member":{"login":"attacker-login"}}`, signed with `X-Hub-Signature: sha1=HMAC(OrgB_webhook_secret, body)`. `victim_team_github_id` is the real numeric GitHub team id of a team already present in `Shipit.github_teams` (e.g. discovered by enumerating small sequential team ids via the target org's public teams listing, or otherwise known).

`verify_signature` passes because the signature genuinely matches OrgB's secret and the payload's `organization.login` is OrgB — the equality "signer == org named in payload" holds. But the second, unstated equality the handler implicitly relies on — "org named in payload == organization owning the `Team` row keyed by `team.id`" — is never checked, and since `github_id` is a global, org-independent lookup key on `Team`, that equality can be false while the code proceeds as if it were true. This is exactly the binding the question identifies as broken.

Existing guards do not catch this: `verify_signature` only checks org-vs-signer, not org-vs-team; `find_or_create_by!` performs no organization filter on the read path; `Team#add_member` performs no authorization check; there is no `ExplicitParameters` validation tying `params.team.id` to `params.organization.login`.

### Impact Explanation
A successful request adds the attacker's own GitHub login (or any login they choose, provided a corresponding GitHub user is resolvable via `User.find_or_create_by_login!`) as a `Membership` on a `Team` belonging to a different organization. If that `Team` is one of `Shipit.github_teams`, the attacker becomes `authorized?` for the whole Shipit application, since `authorized?` only checks team membership, not which org the team actually belongs to. This matches the High severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any team whose `github_id` the attacker can discover, across any org configured on the same Shipit instance, using only credentials the attacker legitimately controls for their own org.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is configured for multiple GitHub organizations (documented, common for hosted/shared Shipit instances) or the attacker otherwise operates a GitHub org that the operator has genuinely connected to this Shipit instance; (2) the attacker has that org's real `webhook_secret` (trivial — it's their own org's App config); (3) the attacker can learn the numeric `github_id` of a target authorized team (feasible via public/enumerable GitHub team ids as stated in the audit's threat model). No Shipit session, API token, or GitHub App private key of the victim org is required. Cost is a single crafted HTTP POST with a correctly computed HMAC using a secret the attacker legitimately owns.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization`, and reject the event if a `Team` with that `github_id` exists under a different organization than `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  team || Team.create!(github_id: params.team.id, organization: params.organization.login) do |t|
    t.github_team = params.team
  end
end
```
Additionally, `WebhooksController#verify_signature` should ensure `repository_owner` is cross-checked against any organization referenced in team/membership payload fields, not just used to pick the signing key.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs, "orga" and "orgb", each with a distinct `webhook_secret` (via `test/dummy/config/secrets_double_github_app.yml`-style multi-org secrets or stubbing `Shipit.github`).
2. Create `team_a = Team.create!(github_id: 999, organization: "orga", slug: "developers", name: "Developers", api_url: "...")`, and register it as authorized: `Shipit.stubs(:github_teams).returns([team_a])`.
3. Build payload: `{"action"=>"added","team"=>{"id"=>999,"name"=>"Developers","slug"=>"developers","url"=>"http://example.com"},"organization"=>{"login"=>"orgb"},"member"=>{"login"=>"attacker"}}.to_json`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', orgb_webhook_secret, payload)`.
5. `request.headers['X-Github-Event'] = 'membership'; request.headers['X-Hub-Signature'] = signature`.
6. `post :create, body: payload, as: :json`.
7. Assert `assert_response :ok` (signature accepted for orgb).
8. Assert the equality is violated: `attacker = User.find_by(login: 'attacker'); assert_includes team_a.reload.members, attacker` — i.e. a `Membership` was written onto `team_a` (organization "orga") even though the request was signed and provenanced entirely by "orgb". Also assert `attacker.authorized?` is now `true` given `Shipit.github_teams == [team_a]`, demonstrating the authorization escalation.
