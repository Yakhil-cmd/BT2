### Title
Permanent Loss of Creator Fee Claimability When `pool_creator` Address is Blacklisted by Reward Token (e.g. USDT/USDC) - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` hardcode the fee recipient to the pool creator's associated token account, with no ability to redirect funds to another wallet. If `token_0_mint`/`token_1_mint` is a token with a blacklist/freeze feature (e.g. USDT, USDC) and the recorded `pool_creator` becomes blacklisted, all accrued and future `creator_fees_token_0`/`creator_fees_token_1` become permanently unclaimable, since the accounts constrain the recipient ATA to `associated_token::authority = creator` and `creator` is immutably fixed to `pool_state.pool_creator`.

### Finding Description
`PoolState.pool_creator` is set once and stored as an immutable field [1](#0-0) . Both fee-collection paths derive the recipient token accounts strictly from this address:

- `collect_creator_fee`: the `creator` must be a `Signer` whose address equals `pool_state.pool_creator`, and the recipient accounts `creator_token_0`/`creator_token_1` are ATAs with `associated_token::authority = creator` [2](#0-1) .
- `collect_creator_fee_permissionless`: anyone can trigger the call, but the recipient `creator` is still constrained via `#[account(address = pool_state.load()?.pool_creator)]`, and fees are "always sent to the pool creator" [3](#0-2) .

Both functions then execute the actual token movement via `transfer_from_pool_vault_to_user`, which performs an `spl_token_2022::transfer_checked` CPI to the recipient ATA [4](#0-3) [5](#0-4) . If the mint program enforces a blacklist/freeze check on the destination owner (a legitimate Token/Token-2022 extension used by tokens such as USDT/USDC), this CPI reverts whenever `creator`'s account (or its ATA) is blacklisted.

Unlike `collect_protocol_fee`/`collect_fund_fee`, where `recipient_token_0_account`/`recipient_token_1_account` are freely-supplied mutable accounts chosen by the privileged `owner` at call time [6](#0-5) , there is no equivalent flexibility for creator fees: the pool creator can never designate an alternate wallet to receive accrued `creator_fees_token_0`/`creator_fees_token_1`, and no instruction exists to update `pool_creator` in `PoolState`.

### Impact Explanation
This is directly analogous to the referenced FootiumPrizeDistributor issue: a hardcoded recipient baked into on-chain state prevents redirecting claims to an alternate, non-blacklisted address. Here, accrued creator fees (`pool_state.creator_fees_token_0`/`creator_fees_token_1`) become permanently frozen and unclaimable by the legitimate creator once their address is blacklisted by the token issuer, and since `collect_creator_fee`/`collect_creator_fee_permissionless` unconditionally zero out and attempt to transfer the full fee balance in one shot, the funds are effectively locked in the vault forever with no admin recovery path (in contrast to `collect_fund_fee`/`collect_protocol_fee`, which are recipient-flexible and admin-controlled). This is a permanent freezing of legitimate user (pool creator) funds.

### Likelihood Explanation
Likelihood depends on the pool being created for a token pair where the underlying mint is a centrally-controlled token with blacklist capability (USDT/USDC-style Token-2022 extension or wrapped token with freeze authority) and the specific creator address later being blacklisted by that issuer — an externally triggered event outside the protocol's control, but realistic given permissionless pool creation allows any token pair and any creator address.

### Recommendation
Allow the pool creator to specify or update an alternate payout token account/authority for creator-fee collection (analogous to recommending a dynamic `_to` in the referenced report), rather than hardcoding the recipient ATA to `pool_state.pool_creator`. For example, add a creator-controlled "fee recipient" field in `PoolState` that can be rotated, and constrain `creator_token_0`/`creator_token_1` to that configurable recipient instead of unconditionally to `pool_creator`.

### Proof of Concept
1. A pool creator initializes a pool where `token_0_mint` (or `token_1_mint`) is a Token-2022 mint with a permanent-delegate/blacklist-style extension controlled by the token issuer, and `pool_state.pool_creator` is set to the creator's wallet [1](#0-0) .
2. Swaps accumulate `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
3. The token issuer blacklists the creator's wallet/ATA (a legitimate on-chain action for that mint's extension/authority).
4. The creator (or anyone, via `collect_creator_fee_permissionless`) calls `collect_creator_fee`/`collect_creator_fee_permissionless`; the ATA is constrained to `associated_token::authority = creator` [7](#0-6) , so `transfer_checked` to that account fails at the token-program level due to the blacklist.
5. Since no instruction permits redirecting the creator-fee recipient, the accrued fees remain locked in `token_0_vault`/`token_1_vault` indefinitely.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
