## Analysis

The report describes an **incomplete-validation / scope-escape** bug class (a boundary check that fails to bind a resource to a single, intended scope). The closest analog in the in-scope PoX-5 code is in the Bitcoin L1-lockup proof verification path used by `register-for-bond`, where a single Bitcoin UTXO can be re-used as proof of collateral for an unbounded number of separate bond registrations.

### Title
Unbounded reuse of a single Bitcoin L1 lockup proof lets a staker claim sBTC-backed bond collateral/reward shares repeatedly without re-locking BTC - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` accepts either custodied sBTC or a Bitcoin SPV proof (`btc-lockup`) that a given UTXO is time-locked to the staker. The SPV proof is checked by `verify-l1-lockups`/`validate-l1-lockup`, but the only duplicate-outpoint protection is a `seen-outpoints` list built and discarded within the single call's `fold` <cite repo="hirayap/stacks-core--018" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="2021="2030" /> [1](#0-0) . There is no contract-level map persisting which Bitcoin outpoints have already been credited towards a bond — a check across the full contract's ~50 `define-map` declarations turned up no such registry.

### Finding Description
`register-for-bond` computes `sats-total` from the caller-supplied proof via `verify-l1-lockups` [2](#0-1) . `validate-l1-lockup` checks that:
- `unlock-burn-height >= minimum-unlock-height` (i.e. `get-bond-l1-unlock-height` of the **bond currently being registered for**), using `>=`, not an equality tied to a specific bond [3](#0-2) 
- the P2* script matches `construct-lockup-output-script` built from `staker`, `unlock-burn-height`, staker-supplied `staker-unlock-bytes`, and the bond's `early-unlock-bytes` [4](#0-3) [5](#0-4) 
- the outpoint is a valid Bitcoin transaction (merkle proof, header) and hasn't been repeated **within this one call**

None of these checks consume or record the outpoint globally. Because the unlock-height check is `>=` rather than tied to one bond's window, a staker can create a single Bitcoin timelock output with a very distant `unlock-burn-height` (far beyond any single bond's L1-unlock window) and reuse the exact same proof across multiple, serially-created bonds (e.g. bond 0, then bond 6, then bond 12, ...), as long as the bonds share the same `early-unlock-bytes` (plausible/likely, since `early-unlock-bytes` is an operator-chosen constant reused across bond generations — see the test that rolls a staker from bond 0 into bond 6 with identical `earlyUnlockBytes` [6](#0-5) [7](#0-6) ).

`bond-overlaps-new-position?` only prevents the *same principal* from holding two *overlapping* memberships at once [8](#0-7) ; it does not prevent the same underlying BTC collateral from being presented again once the prior bond membership has ended (or been rolled over) — each successful `register-for-bond` call independently increments `protocol-bonds-total-staked` for its bond index and adds fresh per-cycle reward shares via `add-staker-to-bond-cycles` [9](#0-8) , based on a proof of BTC lockup that was never re-locked or re-broadcast.

### Impact Explanation
This breaks the equality the contract is meant to enforce: *sats credited to protocol-bond reward shares (and used to gate signer delegation weight) must correspond to BTC that is actually, currently locked on Bitcoin for that specific bond*. By reusing a single Bitcoin lockup transaction/output across multiple bond registrations over time, a staker obtains `sats-total`-based reward shares (`get-total-shares-staked-for-cycle`, `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`) in more than one bond generation while only ever committing one BTC output. This is "sats credited by an L1 proof that were never locked on Bitcoin (for that bond)" / "double-counting a commitment," which the rules classify as Critical (double-counting a commitment or reward) to High (reward/signing weight exceeding locked value), since it inflates a staker's claim on bond rewards/signer weight without proportional new collateral.

### Likelihood Explanation
The only requirement is that the attacker (any allow-listed staker — no privileged role needed) create one long-duration Bitcoin timelock output up front and reuse the resulting proof bytes for each subsequent `register-for-bond` call across bond generations that share the same `early-unlock-bytes` value (a bond-operator-set constant that is not obviously unique per bond in the current code/tests). This requires no cooperation from signers, delegators, or admins, and no race condition — it is a straightforward repeat of a public tool call with the same calldata.

### Recommendation
Persist consumed Bitcoin outpoints (txid + output-index) in a durable map (e.g. `used-l1-outpoints -> bool` or keyed by staker) and reject any `register-for-bond`/L1 proof that references an outpoint already credited to a prior (even expired) bond membership, rather than only deduplicating within a single call's fold. Alternatively/additionally, bind the lockup script (and thus the outpoint it can satisfy) to a single specific `bond-index` so the same UTXO cannot pass validation for more than one bond's window.

### Proof of Concept
1. Staker creates one Bitcoin timelock output paying to a script derived from `(staker, unlock-burn-height = far_future, staker-unlock-bytes, early-unlock-bytes = E)`, where `far_future` exceeds the L1-unlock height of several future bonds.
2. Operator sets up bond 0 with `early-unlock-bytes = E`; staker calls `register-for-bond` with an SPV proof of the output — `verify-l1-lockups` succeeds since `unlock-burn-height (far_future) >= get-bond-l1-unlock-height(0)` [3](#0-2) ; staker is credited `sats-total` shares for bond 0.
3. Bond 0 ends. Operator sets up bond 6 with the same `early-unlock-bytes = E`. Staker calls `register-for-bond(bond-index=6, ...)` supplying the **identical** SPV proof/outputs from step 1 (same BTC never moved). `verify-l1-lockups` again succeeds (`far_future >= get-bond-l1-unlock-height(6)`, script still matches since `E` is unchanged), and the staker is credited `sats-total` shares again for bond 6, using the same real-world BTC that was already "spent" as collateral for bond 0.
4. Repeat for bond 12, 18, ... — the same single BTC lockup backs an unbounded number of bond reward-share credits over time.

Due to index size limits, some surrounding contract state (e.g. any node-side reconciliation logic outside `pox-locking/src/pox_5.rs` and `pox-5.clar`) may not be fully indexed; a full audit of `register-for-bond`/`verify-l1-lockups` call sites and the bond `early-unlock-bytes` provisioning logic in a live Devin session is recommended to confirm there is no additional out-of-band uniqueness enforcement.
