### Title
Uncaught exception in address-definition evaluation crashes the full node process - (File: definition.js)

### Summary
Kea's CVE-2019-6472 is a "malformed field parsed by an unprivileged peer's message causes an uncaught assertion failure that terminates the daemon" bug class. ocore has the same class of bug: several code paths inside `definition.js`'s recursive definition evaluator use `throw Error(...)` instead of returning an error to the callback, and these throws happen inside asynchronous DB-callback closures that are not wrapped in any `try/catch`. Because ocore installs a global `process.on('uncaughtException', ...)` handler in `network.js` that explicitly re-throws to kill the process [1](#0-0) , any unhandled `throw` reachable from validating an attacker-supplied unit brings the whole node down.

### Finding Description
`validateDefinition()` and `validateAuthentifiers()` in `definition.js` both implement an `'address'` operator that resolves a nested/co-signing address reference. When the referenced address's definition is not found in storage, they look for it among the current unit's authors: [2](#0-1) [3](#0-2) 

In both places, if more than one author in the posted unit matches the `other_address` and both supply a `definition` field whose chash equals the expected `definition_chash`, the code does:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This `throw` executes synchronously inside the `ifDefinitionNotFound` callback of `storage.readDefinitionByAddress`, i.e. inside an asynchronous DB-callback frame. There is no enclosing `try/catch` at this call site (unlike the sibling branch a few lines above, which does wrap the definition-hash computation in `try/catch`). The exception therefore propagates all the way up through the event loop as an "uncaught exception," which is caught only by the global handler in `network.js` that intentionally re-`throw`s to crash the process [1](#0-0) .

An attacker fully controls unit content, including the `authors` array and each author's `definition` field, since this is exactly the data validated by `validate()` in `validation.js` for any freshly posted unit [4](#0-3) . To reach `arrDefiningAuthors.length > 1`, an attacker crafts a unit with two authors sharing the same `address` value and both supplying an identical `definition` array (so both hash to the same `definition_chash`), while a third address's own definition contains an `['address', other_address]` reference to that shared address, and `other_address`'s definition is not yet resolvable in storage. This is fully constructible from a single posted unit/joint without any special privilege — it only requires the poster to define his own address definitions and pack authors accordingly.

### Impact Explanation
An uncaught exception thrown while validating a single, ordinary-looking posted unit crashes the `process` on every full node that processes that unit (via `process.on('uncaughtException')` → `throw err`) [1](#0-0) . This is a network-wide denial of service: a single malicious unit propagated to peers can crash multiple/most full nodes that attempt to validate it, halting DAG progress and confirmation of new units, directly matching the "malformed input crashes core process" impact of CVE-2019-6472.

### Likelihood Explanation
Constructing the unit only requires knowledge of the address-definition and authors format that any wallet or unit-composing client already manipulates; no cryptographic break or privileged role is needed, only a normal unit post. The bug is defense-in-depth-absent: the parallel `'address'` handling code (lines just before) explicitly wraps a very similar computation in `try/catch`, showing the missing guard here is an oversight rather than an intentional invariant.

### Recommendation
Wrap the `arrDefiningAuthors.length > 1` check (and the corresponding chash matching logic) in both `validateDefinition()`'s and `validateAuthentifiers()`'s `'address'` case in `try/catch`, converting the "more than 1 address definition" condition into a normal validation error passed to `cb()`/`cb2()` instead of a synchronous `throw`. More broadly, audit `definition.js` for other bare `throw Error(...)` statements reachable from attacker-controlled unit data inside async callbacks (e.g. the `'definition template'` "not 1 template" throw at line ~812) and convert them to error callbacks as well, since the global `uncaughtException` handler treats any of them as fatal.

### Proof of Concept
1. Attacker creates address `A` whose definition is `['address', 'B']` (referencing address `B`, not yet known to storage).
2. Attacker composes a unit with three authors: author for `A` (empty/placeholder definition since already known), and two authors both with `address: 'B'`, each supplying an identical `definition` field (e.g. `['sig', {pubkey: ...}]`) so both compute the same `chash160` equal to `B`.
3. Posts the unit/joint to the network via the standard joint-posting flow that calls `validate()` in `validation.js`.
4. During authentifier/definition evaluation of `A`'s `'address'` reference to `B`, `storage.readDefinitionByAddress` reports `ifDefinitionNotFound`; the filter over `objUnit.authors` matches both `B`-address authors, so `arrDefiningAuthors.length === 2`, triggering `throw Error("more than 1 address definition")` inside the async callback [5](#0-4) .
5. The exception is uncaught, hits `process.on('uncaughtException')`, and the node process crashes [1](#0-0) .
