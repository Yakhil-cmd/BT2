### Title
StatusHandler mutates Commit rows across GitHub Apps/organizations via unscoped `sha` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository/organization scoping, unlike every other handler in the codebase. Any `status` webhook that is validly signed by one GitHub App/org can mutate `Commit`/`Status` rows belonging to a `Stack` owned by a different, unrelated GitHub App/org, as long as an identical SHA exists in both repositories' commit tables (a realistic condition for forked/mirrored repositories).

### Finding Description
The binding that must hold is: **the GitHub App/org whose `webhook_secret` verified the payload (`Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`) == the GitHub App/org owning the `Stack` of every `Commit` mutated by the resulting handler.**

Trace:
- `WebhooksController#verify_signature` resolves the signing app strictly from `params.dig('repository','owner','login')` and validates the HMAC against that org's `webhook_secret`. [1](#0-0)  This only proves the payload came from the named repository owner's GitHub App - it says nothing about which `Commit` rows may be touched.
- The controller then dispatches `params` (the parsed JSON, including `repository`) to `StatusHandler.call(params)`. [2](#0-1) 
- `StatusHandler`'s param schema never even requires a `repository` field, and `#process` ignores `repository` entirely: [3](#0-2) 
- The base `Handler` class provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` [4](#0-3) , and sibling handlers correctly use it — e.g. `CheckSuiteHandler#process` calls `stacks.where(branch: ...)` before touching any commit [5](#0-4) , and `PullRequest::EditedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before finding a `PullRequest` scoped `joins(:stack, stack: :repository)` [6](#0-5) . `StatusHandler` is the outlier: it never calls `stacks`, never resolves `repository_name`, and queries the global `Commit` table by `sha` alone.
- `Commit#create_status_from_github!` unconditionally writes a new `Status` and fires hooks/schedules deploy jobs against whatever `Stack` the matched `Commit` belongs to [7](#0-6) , [8](#0-7) .

Exploit flow: an attacker with no privileges beyond opening a pull request against a repository owned by org X (App1) triggers org X's own CI to post a commit status for the PR head SHA `S` (a routine, attacker-uncontrolled but attacker-triggerable action). GitHub sends a `status` webhook whose `repository.owner.login == "orgX"`, correctly signed with App1's `webhook_secret`. If `Stack` under org Y (App2) — completely unrelated tenant — independently has a `Commit` row with the same `sha` (e.g., org Y forked/mirrored the same upstream history, a common real-world Shipit deployment pattern), `StatusHandler#process`'s `Commit.where(sha: params.sha)` matches both rows and calls `create_status_from_github!` on org Y's commit too, mutating its `Status`, potentially flipping `deployable?`/`blocked?` state and triggering `stack.schedule_merges` or continuous-delivery jobs for org Y's stack — despite org Y's `webhook_secret` never having verified anything.

None of the existing guards prevent this: `verify_signature` only authenticates the org that sent the request, not which `Commit` rows the handler is allowed to touch; `ExplicitParameters` schema on `StatusHandler` has no `repository` requirement to enforce scoping; and no model validation ties `Commit.sha` uniqueness to a repository/stack boundary.

### Impact Explanation
A payload legitimately signed by one GitHub App/org can write `Status` rows, flip commit deployability, and trigger `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` for a `Stack` belonging to a completely different, unrelated GitHub App/organization — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. The blast radius spans every tenant configured in `Shipit.github` whose commit history happens to overlap by SHA with the attacking org's repository (forks/mirrors of shared upstreams are the common case). It is repeatable per commit/PR the attacker can get org X's CI to report a status for.

### Likelihood Explanation
Preconditions: multiple GitHub Apps/orgs configured (`docs/setup.md`'s "Using Multiple Github Applications" section confirms this is a supported deployment) [9](#0-8) , and at least two tracked repositories across different orgs sharing commit history (fork/mirror relationship) so a SHA collision is a normal git artifact rather than a cryptographic attack. Attacker cost is minimal: opening a PR against a repo they have fork/push access to and letting the org's own CI post a status. No secrets, sessions, or elevated roles are required, matching the described unprivileged attacker. This is fully repeatable against any SHA shared between the two histories.

### Recommendation
Scope `StatusHandler#process` to the repository that signed the webhook, mirroring `CheckSuiteHandler`/`PullRequest` handlers: require `repository.full_name` in the params schema, resolve `stacks` via `Repository.from_github_repo_name(repository_name)`, and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... })`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (controller-level, no live GitHub):
1. Fixtures: two `Shipit::GithubApp`-style secrets/orgs ("orgX" and "orgY") each with a `Repository` and a `Stack`; create `Commit` `commit_x` on `stack_x` (org X) and `commit_y` on `stack_y` (org Y) with the **same** `sha` value `S`.
2. Stub `Shipit.github(organization: 'orgX')` (and `'orgY'`) `#verify_webhook_signature` to return true only for the org matching the request, mirroring `Shipit.github(organization: 'shopify').expects(:verify_webhook_signature)` pattern already used in `test/controllers/webhooks_controller_test.rb` [10](#0-9) .
3. POST `/webhooks` with `X-Github-Event: status`, body `{ sha: S, state: 'success', repository: { full_name: 'orgX/repoX', owner: { login: 'orgX' } } }`, with a signature valid for App1/orgX only.
4. Assert the binding on both sides:
   - Before: `commit_x.statuses.count == 0` and `commit_y.statuses.count == 0`.
   - Equality claimed: `verifying_org(request) == owning_org(mutated_commit.stack)`.
   - After: assert `commit_x.reload.statuses.count == 1` (expected, same org) AND assert `commit_y.reload.statuses.count == 0` (must remain untouched since App2/orgY never verified this payload).
5. Current buggy behavior: `commit_y.reload.statuses.count == 1` — proving the App1-signed payload mutated a Commit belonging to Stack under App2/orgY, breaking the stated binding.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
