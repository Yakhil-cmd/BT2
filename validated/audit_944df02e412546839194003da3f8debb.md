## Analysis Summary

I found a concrete analog of the code-423n4 bug class (a missing/incomplete guard that lets attacker-influenced input diverge from what is actually trusted/verified), located in the webhook signature-verification path combined with the membership-authorization pathway.

### Title
Unauthenticated membership webhook can grant Shipit team authorization when an organization's `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Finding Description
`WebhooksController#verify_signature` resolves which per-organization GitHub App config to check the signature against using `repository_owner`, which falls back to `params.dig('organization', 'login')` when no `repository` key is present [1](#0-0) . Membership events carry only an `organization` key, not a `repository` key [2](#0-1) .

The actual signature check is `GitHubApp#verify_webhook_signature`, which contains an explicit bypass: `return true unless webhook_secret` [3](#0-2) . In a multi-organization deployment (`config/secrets.yml` keyed by org, as documented) it is fully valid configuration for one organization to have no `webhook_secret` set, e.g. the documented templates show `webhook_secret:` left blank [4](#0-3) . For that organization, `verify_signature` always passes regardless of the `X-Hub-Signature` header or payload content.

This creates the trust-binding equality that breaks: *the GitHub identity that authenticated the webhook* (verified against Org A's secret, or not verified at all) is treated as equal to *the organization whose Team/Membership records get written*, purely based on an attacker-controlled `organization.login` JSON field. `MembershipHandler#process` trusts `params.organization.login` and `params.team`/`params.member` wholesale to create/update `Team` and `Membership` records [5](#0-4) , with no re-validation against actual GitHub state.

These `Team` records are exactly what backs authorization: `Shipit.github_teams` maps configured OAuth team handles to `Team` records [6](#0-5) , and `User#authorized?` checks membership in those teams to gate all engine access [7](#0-6) , enforced in `Authentication#force_github_authentication` [8](#0-7) .

### Impact Explanation
An unprivileged network attacker (no session, no `ApiClient` token, no webhook secret) who can reach `/webhooks` can POST a forged `membership` event with `action: 'added'`, an `organization.login` matching the org whose `webhook_secret` is unset, a `team` object matching one of `Shipit.github_teams`' handles, and `member.login` equal to their own already-registered Shipit `User` login. `WebhooksController#verify_signature` will call `Shipit.github(organization: <attacker-chosen org>)`, and because that org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — no signature needed at all. `MembershipHandler` then adds the attacker's `User` to the authorized `Team`, satisfying `authorized?` and granting them full access to the Shipit engine (viewing stacks, triggering deploys/rollbacks, etc.) — this is an authorization-boundary escalation into `Shipit.github_teams`, matching the "High" impact category defined in scope.

### Likelihood Explanation
This is reachable purely over HTTP with no privileged credentials, satisfying the "unprivileged-attacker" and in-scope-impact requirements. The precondition — at least one configured GitHub organization with no `webhook_secret` — is an explicitly supported and documented configuration (the templates ship with the field blank), so it is not a theoretical/misconfiguration-only scenario outside the engine's documented operation; the engine's own code (`return true unless webhook_secret`) is what turns an absent secret into "verification always succeeds" rather than "verification cannot be performed / must fail closed."

### Recommendation
- In `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`), fail closed when `webhook_secret` is blank in a multi-organization setup, or require a `webhook_secret` to be present for every configured organization at boot.
- In `WebhooksController#verify_signature`, do not silently permit unsigned events for events lacking a `repository` key (e.g., `membership`, `organization`); the organization used for secret lookup should not be entirely attacker-supplied without independent verification.
- Consider re-fetching membership/team state from the GitHub API rather than trusting the webhook payload directly for authorization-relevant side effects.

### Proof of Concept
1. Deploy Shipit with two configured organizations in `secrets.yml`: `orgA` (has `webhook_secret` set) and `orgB` (has `webhook_secret` left blank/nil), and set `Shipit.github_teams` to include a team under `orgB`, e.g. `orgb/admins`.
2. As an unauthenticated attacker, register/observe a Shipit `User` login for yourself (e.g., via existing repository contribution or any low-privilege path that creates a `User` record).
3. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or an arbitrary bogus one), body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://github.com/x" },
  "organization": { "login": "orgB" },
  "member": { "login": "<attacker-login>" }
}
```
4. `verify_signature` resolves `repository_owner` to `"orgB"` (no `repository` key present, falls back to `organization.login`), calls `Shipit.github(organization: "orgB")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
5. `MembershipHandler#process` runs, creating/finding the `Team` for `orgb/admins` and adding the attacker's `User` as a member.
6. The attacker's session now passes `User#authorized?` and gains full access to the Shipit UI/API for that install.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
