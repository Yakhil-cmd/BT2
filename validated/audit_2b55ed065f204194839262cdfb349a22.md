### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independent `repository.full_name` field, allowing cross-repository event forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). However, every event handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) resolves the target `Stack`/`Repository` using a *different*, independently-controlled payload field: `repository.full_name`. Because the signature check never binds `repository.owner.login` to `repository.full_name`, an attacker who legitimately controls the webhook secret for *any* organization/app configured on the Shipit instance can forge a signature that is valid for "their" org while pointing `repository.full_name` at a completely different, victim repository tracked by the same Shipit instance.

### Finding Description
- `verify_signature` computes the organization to authenticate against purely from payload content: [1](#0-0) [2](#0-1) 

  It calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, raw_post)`, which does a straightforward HMAC-SHA1 comparison against that organization's configured `webhook_secret`: [3](#0-2) 

- Once the signature is accepted, the raw, attacker-supplied JSON is dispatched unmodified to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [4](#0-3) 

- The base `Handler` class resolves the affected stacks using a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

- `Repository.from_github_repo_name` simply splits `owner/name` out of this attacker-controlled string and looks up any repository row that matches, with no relation to which org's secret authenticated the request: [6](#0-5) 

- Concretely: `PushHandler` triggers `stack.sync_github` for any stack under the resolved repository/branch, and `CheckSuiteHandler` marks commits' check runs for refresh — both keyed off `repository.full_name`, not the authenticated owner: [7](#0-6) [8](#0-7) 

This is directly analogous to the reported bug class: the field the code cryptographically verifies (`repository.owner.login`, used to pick a webhook secret) is not the field the code actually acts on (`repository.full_name`, used to select the target repository/stack). Just as the account-abstraction address used to authorize a transfer differed from the address that ultimately received funds, here the organization whose secret authorized the webhook differs from the repository the payload is allowed to mutate.

### Impact Explanation
On a Shipit instance configured with more than one GitHub App/organization (a normal multi-tenant Shipit deployment, e.g. one entry per org in `config/shipit.yml`), any attacker who can produce a validly-signed webhook for *one* org's app (for example, by owning/administering a repository under that org and configuring a webhook there, which is a normal, unprivileged GitHub capability, not a Shipit privilege) can forge `push`, `status`, and `check_suite` events that name an arbitrary victim repository/stack belonging to a *different* organization tracked by the same Shipit instance. This allows:
- Injecting fabricated commit statuses via `StatusHandler#process`, which can flip CI/check state associated with a victim's commits and influence deploy-gating logic, and
- Forcing `GithubSyncJob`/check-run refresh cycles against a victim stack the attacker has no access to.

This is a cross-repository write crossing an authentication boundary (organization the signature authenticates vs. the repository the payload mutates), matching the required "cross-repository writes" impact category.

### Likelihood Explanation
Requires the attacker to control a legitimately configured webhook secret for at least one organization/app entry configured in the same Shipit deployment (a realistic scenario for any multi-org/enterprise Shipit install, since Shipit is designed to serve many teams/orgs from one instance). No GitHub App private key, Shipit session, or `ApiClient` token is needed — only the ability to sign an HTTP request with a webhook secret the attacker legitimately possesses for their own org, and knowledge of the target repository's `owner/name`.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that the resolved `repository.full_name`'s owner matches `repository_owner` (the same value used to select the signing secret), or better, resolve the target `Repository`/`Stack` in the handler using the same authenticated organization context rather than trusting `repository.full_name` independently. Reject the event if the two disagree.

### Proof of Concept
1. Shipit is configured with two GitHub App entries: `org-attacker` (attacker administers a repo here and knows its `webhook_secret`) and `org-victim` (unrelated org whose repository `org-victim/prod-app` is tracked as a Shipit `Stack`).
2. Attacker crafts a `push` (or `status`/`check_suite`) JSON payload where:
   - `organization.login` / `repository.owner.login` = `org-attacker` (so `verify_signature` picks `org-attacker`'s secret), and
   - `repository.full_name` = `org-victim/prod-app`.
3. Attacker computes `X-Hub-Signature` using `org-attacker`'s known `webhook_secret` over the raw payload, per `GitHubApp#verify_webhook_signature`: [3](#0-2) 
4. POSTs to `/webhooks` (routed to `WebhooksController#create`). `verify_signature` succeeds (signature matches `org-attacker`'s secret).
5. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` invokes `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('org-victim/prod-app')` [5](#0-4)  and triggers `stack.sync_github(expected_head_sha: ...)` for `org-victim`'s stack, entirely outside any binding to `org-attacker`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
