### Title
Webhook signature check keys off `repository.owner.login`/`organization.login`, but handlers act on the unvalidated `repository.full_name` field, letting the org whose secret is used diverge from the repository actually mutated - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook's HMAC against based on `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and `Shipit.github(organization: repository_owner)` [2](#0-1) . All event handlers, however, resolve the actual repository/stack to mutate from a *different* field in the very same attacker-supplied JSON body, `payload.dig('repository','full_name')` [3](#0-2) . Nothing cross-checks that `full_name`'s owner segment matches `repository.owner.login`/`organization.login`. Compounding this, `GitHubApp#verify_webhook_signature` unconditionally returns `true` when `webhook_secret` is blank/nil for the resolved organization [4](#0-3) , and Shipit explicitly supports multi-organization deployments where each org has its own independently configured `webhook_secret` [5](#0-4) [6](#0-5) .

### Finding Description
The binding that should hold is: **organization whose signature verified == organization owning the repository the handler writes to**. In this codebase that equality is never enforced because two disjoint payload fields feed two disjoint code paths:

- Signature verification org selector: `repository.owner.login` (or `organization.login` as a fallback) — `webhooks_controller.rb:59-61`.
- Handler's repository resolver: `repository.full_name` — `handlers/handler.rb:36-38`, consumed by `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) [7](#0-6) , by pull-request handlers via `Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7) , and by `StatusHandler`, which looks commits up globally by SHA with no repository scoping at all [9](#0-8) .

Both `owner.login` and `full_name` are attacker-controlled JSON strings inside the same raw POST body (`JSON.parse(request.raw_post)` at `webhooks_controller.rb:11`). The controller performs no relational check that `full_name` starts with `owner.login/`. Because `Shipit.github(organization:)` returns per-organization app config, and `verify_webhook_signature` no-ops when that organization's `webhook_secret` is not configured (`return true unless webhook_secret`), a request whose `repository.owner.login` names an organization configured with no `webhook_secret` will pass verification with **any** or even absent `X-Hub-Signature`, while `repository.full_name` can reference a completely different, secret-protected organization's repository/stack that Shipit tracks. The install/setup docs and shared secrets fixtures show `webhook_secret` is commonly left unset per-org (`# nil`) in real configurations [10](#0-9) , so this is not a contrived edge case but a state the maintainers' own configuration templates produce.

### Impact Explanation
An attacker who can reach the `/webhooks` endpoint (unauthenticated by design — it's meant to be called by GitHub) can craft a payload with `repository.owner.login` set to any organization Shipit has configured with a blank `webhook_secret`, while setting `repository.full_name` to the full name of a stack belonging to a *different*, security-conscious organization that does have a secret configured. The forged request bypasses signature verification entirely and is then processed as authentic by the handler for whichever repository `full_name` names. Depending on event type this drives unauthorized engine state changes against a repository the attacker does not control: `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)`, which reconciles Shipit's tracked commits/deploy state to attacker-chosen values, and `MembershipHandler` can add/remove memberships using only `organization.login` (no repository check at all, so it is even more directly exploitable if that org's secret is blank) [11](#0-10) . This crosses the "escalation into `Shipit.github_teams` authorization" / unauthorized state-mutation bar for a High-severity finding, since attacker-forged webhook input drives cross-repository writes to stacks/teams that were not authenticated by their own organization's secret.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires (a) a multi-organization Shipit deployment, and (b) at least one onboarded organization lacking a configured `webhook_secret`. Both conditions are explicitly anticipated and supported by the codebase's own multi-org config path (`github_app_config`, `TOP_LEVEL_GH_KEYS`) and example/dummy configs that ship with `webhook_secret` unset. Any organization onboarded without a webhook secret becomes a skeleton key for forging events against every other tracked repository, making exploitation straightforward for an unprivileged attacker who can send arbitrary HTTP requests to the public webhooks endpoint.

### Recommendation
Bind signature verification to the same field used for repository resolution, and refuse to treat a webhook as authenticated for one organization when it is used to act on a repository belonging to another:
1. In `WebhooksController#verify_signature`, derive `repository_owner` consistently from `repository.full_name`'s owner segment (or validate `repository.owner.login` equals the owner parsed out of `full_name`) rather than accepting either field independently.
2. In `Handler#repository_name`/consumers, reject events whose `repository.full_name` owner does not match the organization resolved by `verify_signature`.
3. Do not allow `GitHubApp#verify_webhook_signature` to silently return `true` when `webhook_secret` is unset for a configured organization in a multi-org deployment; require an explicit secret per organization or fail closed.

### Proof of Concept
1. Configure Shipit with two organizations, `TrustedOrg` (has a stack tracked, `webhook_secret` set) and `EmptyOrg` (onboarded but `webhook_secret` left blank, as in the shipped `config/secrets.development.shopify.yml` template).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "EmptyOrg" },
    "full_name": "TrustedOrg/victim-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "EmptyOrg"`, calls `Shipit.github(organization: "EmptyOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("TrustedOrg/victim-repo")` (through `Handler#stacks`/`#repository_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `TrustedOrg`'s stack — an unauthorized write triggered without ever presenting a valid signature for `TrustedOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
