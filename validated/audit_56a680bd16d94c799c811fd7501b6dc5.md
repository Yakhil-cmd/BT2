## Title
Webhook signature verification is scoped to `repository.owner.login`, but event processing acts on the independent `repository.full_name` field, enabling cross-repository webhook forgery when any configured GitHub org has no webhook secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC secret) to verify the inbound signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, attacker-supplied JSON body. The rest of the pipeline (`Handler#stacks` / `Handler#repository_name`, used by `PushHandler`, membership handlers, status handlers, etc.) instead resolves the target `Repository`/`Stack` from a completely separate field of the same payload: `repository.full_name`. Nothing binds these two fields together, so `repository.owner.login` and `repository.full_name` can name different organizations/repositories in a single forged payload.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks a per-organization `GithubApp` config (multi-org config is a documented, supported mode — see `config/secrets.development.shopify.yml`), and `verify_webhook_signature` for that org is used to check `X-Hub-Signature`: [3](#0-2) 

Critically, if that org's `webhook_secret` is unset/blank (a valid, documented configuration — see `webhook_secret: # nil` in `config/secrets.development.shopify.yml`), `verify_webhook_signature` unconditionally returns `true`, regardless of the actual `X-Hub-Signature` header value.

Meanwhile, `Handler#stacks`/`#repository_name` (used by every real event handler, e.g. `PushHandler`) resolves which `Repository`/`Stack` to mutate from a different JSON key, `repository.full_name`: [4](#0-3) [5](#0-4) 

Since `verify_webhook_signature` is looked up using `repository.owner.login` but the mutating action is dispatched using `repository.full_name`, an attacker who knows (or guesses) that any org configured in `Shipit.github` config lacks a `webhook_secret` can craft one payload where `repository.owner.login` = that unsecured org (making signature verification trivially pass) while `repository.full_name` = `"victim-org/victim-repo"` (any real, secured repository/stack hosted on the same Shipit instance). This breaks the intended equality: `organization that authenticated == organization/repository that is written`.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary called out in scope. An unauthenticated attacker (no GitHub App private key, no `webhook_secret`, no repository write access) can forge webhook events — e.g. `push` (triggering `GithubSyncJob`/`sync_github`), `status`, `check_suite`, or `membership` events — against any stack/repository configured on the Shipit instance, as long as the instance hosts at least one additional organization whose webhook secret is not configured. This can be used to spoof CI/commit status data consumed for deploy-gating decisions, trigger `GithubSyncJob` runs prematurely/repeatedly, or manipulate `Team`/`Membership`/`User` records via the `membership` handler — all attributed to a repository the attacker never authenticated for. It does not, by itself, achieve RCE or GITHUB_TOKEN exfiltration, but it does allow unauthorized writes into a repository's Shipit-side state that the attacker does not control, satisfying the "cross-repository writes" bar when a multi-org deployment includes an org without a webhook secret.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: it requires the Shipit instance to be configured with more than one GitHub organization (a documented and supported feature, per `config/secrets.development.shopify.yml` and `docs/setup.md`) where at least one of those orgs has no `webhook_secret` set — itself a documented default (`webhook_secret: # nil`). In such a (not uncommon) multi-tenant configuration, exploitation requires no credentials at all: a single unauthenticated POST to `/webhooks` with a crafted JSON body and the correct `X-Github-Event` header.

### Recommendation
Do not use attacker-controlled payload fields to select the signature-verification key. Bind the verification and processing steps to the same value: after verifying the signature, only ever act on the repository indicated by the same trust context used for verification, and refuse to process events whose `repository.full_name` does not belong to the org used for verification (i.e., reject if `repository.full_name.split('/').first != repository_owner`). Additionally, `verify_webhook_signature` should not silently return `true` when no secret is configured for an org — it should fail closed (reject the event) rather than fail open when `webhook_secret` is blank, since a misconfigured/incomplete org config should not create a bypass for other orgs' repositories.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `victim-org` (fully configured with a `webhook_secret`) and `attacker-org` (installed but with `webhook_secret` left blank/nil — a state explicitly shown as valid in `config/secrets.development.shopify.yml`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `GithubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is required.
4. `PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves stacks under `victim-org/victim-repo` and triggers `stack.sync_github(expected_head_sha: ...)`, causing Shipit to act on the victim's repository state despite the request never being authenticated against `victim-org`'s webhook secret.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
