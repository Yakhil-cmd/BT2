### Title
Webhook authentication is bound to `repository.owner.login`/`organization.login` while writes are bound to the unrelated `repository.full_name` field, letting one org's missing secret forge events for any other stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/`webhook_secret` used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`), but the handler that actually mutates state (creates statuses, enqueues sync/deploy jobs, archives/creates stacks) resolves its target purely from the separate `repository.full_name` field of the same JSON body. These two fields are never cross-validated, so an attacker can pick a "signing" org that happens to have no `webhook_secret` configured while pointing the actual work at a completely different, protected repository/stack.

### Finding Description
`WebhooksController#verify_signature` derives the signing identity like this: [1](#0-0) [2](#0-1) 

`repository_owner` is used to select which `GitHubApp` config/secret verifies the signature: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected org's `webhook_secret` is blank/unset — a supported, documented configuration for multi-org Shipit deployments: [4](#0-3) [5](#0-4) 

Once the request passes this before_action, `WebhooksController#create` dispatches the entire raw JSON body to every registered handler for the event: [6](#0-5) 

Handlers resolve which `Stack`/`Repository` to act on from a *different* field of the same payload — `repository.full_name` — with no relationship enforced to `repository.owner.login`: [7](#0-6) [8](#0-7) 

`Repository.from_github_repo_name` simply splits the string on `/` and looks up by `owner`/`name` — it never checks that this owner equals the `repository.owner.login`/`organization.login` that was used moments earlier to select the verifying secret. For example `PushHandler`, `StatusHandler`, and the pull-request handlers all resolve their target stack this way: [9](#0-8) 

**Binding that should hold:** `organization authenticated by verify_signature == organization owning the repository that gets written`. **Binding that actually holds:** the authenticating field (`repository.owner.login`/`organization.login`) and the acted-upon field (`repository.full_name`) are independent, attacker-controlled parts of the same unsigned-until-verified JSON body, and Shipit never checks they agree.

### Impact Explanation
In any Shipit installation using the multi-org GitHub config (`config/secrets.*.yml` with per-org `github:` blocks), it is a supported and plausible configuration for at least one org to have no `webhook_secret` set (the docs explicitly present it as optional: "If you've set a webhook secret during App creation, you should copy it here."). An unauthenticated attacker who knows (or guesses) that one configured org has no secret can:

1. Set `repository.owner.login`/`organization.login` to that unsecured org (making `verify_webhook_signature` return `true` regardless of/absent `X-Hub-Signature`).
2. Set `repository.full_name` to `victim-org/victim-repo` — any other stack tracked by the Shipit instance, secured or not.
3. Forge `push` events with attacker-chosen `after` SHA (drives `PushHandler` → `Stack#sync_github`/`GithubSyncJob`), `status` events with attacker-chosen `state`/`context` (forges required CI statuses that gate the merge queue and continuous deployment), or `check_suite`/`pull_request` events (archiving/unarchiving/creating review stacks).

Forging "success" statuses for required contexts on a victim stack that has continuous deployment enabled can trigger an unauthorized deploy, and forging statuses that satisfy merge-queue requirements can force an unauthorized merge — both cross-repository, unauthenticated impacts that fall in the Critical/High bucket (unauthorized deploy/merge, escalation across repositories the attacker has no access to).

### Likelihood Explanation
This requires no credentials, no `ApiClient` token, no GitHub App private key, and no TLS interception — only that the operator's multi-org `github:` config contains at least one organization without a `webhook_secret` (an explicitly supported, non-default-forcing configuration per the setup docs). Given that, the request is a single unauthenticated HTTP POST to `/github/webhooks` (or engine-mounted equivalent) with a crafted JSON body; no signature is even required. This is directly analogous to the referenced report's root cause: a value checked at authorization time (`tokenOut`/`repository.owner.login`) is decoupled from the value actually acted upon at execution time (`_tokenOut` used in transfer/`repository.full_name` used to resolve the write target).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks`/`Repository.from_github_repo_name`), enforce that the owner segment of `repository.full_name` matches the `repository.owner.login`/`organization.login` used to select the verifying `webhook_secret` before dispatching to any handler. Additionally, consider requiring a non-blank `webhook_secret` for every configured organization (fail closed) rather than silently accepting unsigned/any-signature requests when `webhook_secret` is absent.

### Proof of Concept
Given a Shipit deployment configured with two orgs, `OrgA` (no `webhook_secret`) and `OrgB` (has a `webhook_secret`, owns `victim-repo` with continuous deployment enabled and a required `ci/travis` status):

```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json
(no X-Hub-Signature header needed)

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/travis",
  "target_url": "https://attacker.example.com",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```

`repository_owner` resolves to `OrgA` → `Shipit.github(organization: "OrgA").verify_webhook_signature` short-circuits `true` because `OrgA` has no `webhook_secret` → request passes `before_action` → `Shipit::Webhooks.for_event('status')` handler creates a `Status` for the sha under `OrgB/victim-repo` (resolved via `repository.full_name`), forging a required CI status the attacker has no access to and no credentials for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
