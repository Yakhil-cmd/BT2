### Title
CCMenu API endpoint bypasses `ApiClient` stack scoping, letting a stack-scoped token read another stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper used by `Shipit::Api::BaseController` in a way that no longer respects the scoping between an `ApiClient`'s authorized stack and the stack whose data is actually rendered. This breaks the binding "stack a token authorises == stack it touches": a `read:stack`-permissioned token minted for stack A can be replayed with a different `stack_id` in the URL to read deploy/build status for stack B.

### Finding Description
`Shipit::Api::BaseController` normally restricts which stacks an `ApiClient` can touch: [1](#0-0) 

`stacks` is scoped to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves the requested `params[:stack_id]` only within that scoped relation (`stacks.from_param!`).

`CCMenuController`, however, overrides `stack` to bypass this relation entirely: [2](#0-1) 

`stack` resolves via `Stack.from_param!(params[:stack_id])`, i.e. against *all* stacks, not `current_api_client`'s scoped relation. The `require_permission :read, :stack` declaration only checks that the authenticated client's `permissions` array includes `"read:stack"`: [3](#0-2) 

It never checks that `current_api_client.stack_id` (if set) matches the stack actually being rendered. Combined with `authenticate_api_client` reading the token from a query-string parameter (as used for the public/unauthenticated cctray-style URL): [4](#0-3) 

...an `ApiClient` token that is legitimately scoped to one stack (e.g., minted by `CCMenuUrlController` at [5](#0-4)  with `stack:` set to a specific record) can be used against `GET /api/v1/:stack_id/ccmenu.xml?token=...` for any other `:stack_id`, rendering that other stack's merge/build status, activity, last build time and label: [6](#0-5) 

### Impact Explanation
This is an unauthenticated (holder of a low-privilege, single-purpose token) read of stack state/deploy status across stack boundaries — the token holder learns build/merge status, activity, and last-deploy metadata for stacks it was never granted access to. This matches the "High" category: "unauthenticated read of stack state, task streams or deploy output," since the CCMenu token is designed to be embedded in unauthenticated CI-dashboard tooling and is not equivalent to a fully privileged Shipit session.

### Likelihood Explanation
Exploitation only requires possession of any valid stack-scoped CCMenu token (these tokens are meant to be shared with external CI dashboard tools and embedded in URLs, so they are more exposed than a general session) and knowledge/guessing of another stack's `stack_id` (repository/stack slug), which is often predictable or discoverable (e.g., via the public repository name). No additional secret, session, or GitHub credential is required beyond the token itself.

### Recommendation
Have `CCMenuController#stack` resolve through the scoped `stacks` relation (as `BaseController#stack` does) instead of calling `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve any stack outside `current_api_client.stack_id`.

### Proof of Concept
1. As an authenticated Shipit user, request a CCMenu URL for Stack A via `GET /:stack_id_A/ccmenu_url` (`CCMenuUrlController#fetch`), which mints an `ApiClient` scoped to Stack A with `permissions: ["read:stack"]` and returns `.../api/v1/A/ccmenu.xml?token=<T>`.
2. Take the token `T` and request `GET /api/v1/B/ccmenu.xml?token=T` for an arbitrary other stack `B`.
3. `authenticate_api_client` accepts `T` (it is a valid, unexpired `ApiClient` token) and `require_permission :read, :stack` passes because the client has `read:stack` in its permissions.
4. `stack` resolves `Stack.from_param!(params[:stack_id])` = Stack B directly (no scoping check against `current_api_client.stack_id == A`), so the response discloses Stack B's `lastBuildStatus`, `activity`, `lastBuildTime`, and `lastBuildLabel` even though the token was only ever authorized for Stack A.
