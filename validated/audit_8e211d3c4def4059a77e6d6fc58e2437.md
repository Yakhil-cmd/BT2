## Finding

### Title
Move package/function loading during PTB translation performs unmetered, potentially expensive work (package fetch, deserialization, verification) before the corresponding gas charge is applied — ([File: sui-execution/latest/sui-adapter/src/static_programmable_transactions/mod.rs])

### Summary
The Sui adapter's programmable-transaction execution pipeline mirrors the SEDA Tally-VM pattern: expensive setup work is performed *before* the gas charge that is supposed to cover it. In `execute()`, the transaction is first translated/loaded (`loading::translate::transaction`), which resolves linkage and loads every `MoveCall` function (`env.load_function`) — an operation that can trigger fetching, deserializing, and bytecode-verifying entire dependency packages from the backing store. Only *after* this loading work is done does `metering::loading::meter` charge gas, and even then it only charges for the number of type nodes and linkage-table entries, not for the actual bytes/complexity of the packages that had to be loaded and verified.

### Finding Description
The execution entry point performs work in this order: [1](#0-0) 

1. `gas_charger.charge_input_objects(temporary_store)` is charged once, early, in `execution_engine.rs`, but this only accounts for objects already present in the `TemporaryStore` (explicit PTB inputs), not for dependency packages that get pulled in later during linkage resolution: [2](#0-1) 

2. `loading::translate::transaction` runs `metering::pre_translation::meter` first, but that pass only charges based on shallow, attacker-supplied counts (number of inputs, pure-byte lengths, number of commands/arguments) — it has no knowledge of which packages a `MoveCall` actually references or how expensive they are to load: [3](#0-2) [4](#0-3) 

3. Immediately after that cheap pre-check, the `command()` translation step calls `env.linkage_analysis.compute_call_linkage(...)` and `env.load_function(...)` for every `MoveCall`, which resolves linkage and loads/verifies the referenced package(s) from the package store — this is the expensive step, analogous to SEDA's "creating the runtime, instantiating environment/module, allocating memory": [5](#0-4) [6](#0-5) 

4. Only *after* all of that loading/verification work has completed does `metering::loading::meter` run, and it charges purely for the count of type nodes and linkage entries — never for the size/complexity of the packages that were fetched, deserialized, and bytecode-verified to get there: [7](#0-6) 

This is the same root cause as the SEDA bug: the gas metering point is placed after the costly setup rather than gating entry into that setup, so a transaction with a small gas budget can still force a validator to perform disproportionate CPU/I/O work (package fetch from storage, module deserialization, Move bytecode verifier passes) before the low budget is detected and the transaction is rejected with `InsufficientGas`.

### Impact Explanation
If a validator's package/module cache does not already contain the referenced dependency package (e.g., a large, complex, but protocol-limit-compliant package that was published once and then evicted from cache, or one that a given validator has simply never processed before), an attacker can submit many transactions with the minimum gas budget, each referencing a `MoveCall` into that package. Each such transaction forces the validator to redo full package deserialization and Move bytecode verification — genuinely expensive operations — before gas exhaustion is detected, and the cost of doing so is not proportional to what the attacker pays. Repeated at scale this is a computation/CPU-based node and chain slowdown reachable from unauthenticated public input, matching the "network and node shutdown classes when reachable from public input" High-severity bounty class.

### Likelihood Explanation
Likelihood depends heavily on cache behavior in the real deployment (whether verified packages remain cached long enough that repeat calls are effectively free) and on any package-size caps that bound the maximum amount of "free" work per transaction. Because the code as inspected clearly performs loading/verification before charging for it, and the metering pass that follows only charges for type-node/linkage counts (not bytes/verification cost), the described gap is real; however I could not fully verify from static inspection alone (a) the exact cache eviction policy/size in production validators, or (b) whether other layers (e.g., transaction size limits, package size limits, or existing computation bucket pricing) already bound the worst case tightly enough to make this impractical as a DoS vector at scale.

### Recommendation
Charge (or reserve) gas for package loading based on package byte-size/complexity *before* invoking `env.load_function` / linkage resolution for referenced dependency packages, mirroring the fix pattern from the SEDA report: reject or short-circuit the loading step if the remaining gas budget cannot plausibly cover the cost of loading and verifying the referenced packages, rather than metering only after the fact based on the already-loaded output shape (type node/linkage counts).

### Proof of Concept
Not constructed — this requires cluster-level testing (cold cache state across validators, package eviction behavior, and measuring actual CPU time spent in `load_and_verify_packages`/`validate_package` versus gas charged) that is outside what can be verified through static code reading alone. This should be validated by a background engineer with access to a running Sui node/testnet to confirm actual exploitability and severity before treating it as confirmed.

pub fn meter<E: ExecutionErrorTrait>(
    meter: &mut TranslationMeter,
    transaction: &ProgrammableTransaction,
) -> Result<(), E> {
    meter.charge_base_inputs(transaction.inputs.len())?;

    for input in &transaction.inputs {
        match input {
            CallArg::Pure(bytes) => {
                meter.charge_pure_input_bytes(bytes.len())?;
            }
            CallArg::FundsWithdrawal(_) | CallArg::Object(_) => (),
        }
    }

    for command in &transaction.commands {
        meter.charge_base_command(arguments_len(command))?;
    }

    Ok(())
}

// Retrieves a set of packages from the cache, attempting to load them from the data store if
// they are not present.
pub(crate) fn resolve_packages(
    store: impl ModuleResolver,
    telemetry: &mut TransactionTelemetryContext,
    cache: &MoveCache,
    natives: &NativeFunctions,
    packages_to_read: BTreeSet<VersionId>,
) -> VMResult<BTreeMap<VersionId, Arc<move_cache::Package>>> {
    dbg_println!("loading {packages_to_read:#?}");

    let initial_size = packages_to_read.len();

    let mut cached_packages = BTreeMap::new();
    let mut pkgs_to_cache = BTreeSet::new();

    // Determine what is already in the cache.
    for pkg_id in packages_to_read {
        if let Some(pkg) = cache.cached_package_at(pkg_id) {
            cached_packages.insert(pkg_id, pkg);
        } else {
            pkgs_to_cache.insert(pkg_id);
        }
    }

    // Load and cache anything that wasn't already there.
    // NB: packages can be loaded out of order here (e.g., in parallel) if so desired.
    for pkg in load_and_verify_packages(store, telemetry, &cache.vm_config, natives, &pkgs_to_cache)
        .map_err(expect_no_verification_errors)?
    {
        let pkg = jit_and_cache_package(telemetry, cache, natives, pkg)?;
        cached_packages.insert(pkg.verified.version_id, pkg);
    }

    // The number of cached packages should be the same as the number of packages provided to
    // us by the linkage context.
    debug_assert!(
        cached_packages.len() == initial_size,
        "Mismatch in number of packages in linkage table and cached packages"
    );
    Ok(cached_packages)
}

    linkage::resolved_linkage::ResolvedLinkage, loading::ast as L,
    metering::translation_meter::TranslationMeter,

use sui_types::error::ExecutionErrorTrait;

/// After loading and before type checking we do a pass over the loaded transaction to charge for
/// types that occured in the transaction and were loaded. We simply charge for the number of type
/// nodes that were loaded.
pub fn meter<E: ExecutionErrorTrait>(
    meter: &mut TranslationMeter,
    transaction: &L::Transaction,
) -> Result<(), E> {
    let inputs = transaction.inputs.iter().filter_map(|i| match &i.1 {
        L::InputType::Bytes => None,
        L::InputType::Fixed(ty) => Some(ty),
    });
    let commands = transaction.commands.iter().flat_map(command_types);
    for ty in inputs.chain(commands) {
        meter.charge_num_type_nodes(ty.node_count())?;
    }

    for linkage in transaction.commands.iter().filter_map(command_linkage) {
        meter.charge_num_linkage_entries(linkage.linkage_resolution.len())?;
    }

    for cmd in &transaction.commands {
        match cmd {
            L::Command::Publish(payload, _, _) | L::Command::Upgrade(payload, _, _, _, _) => {
                meter.charge_package_load(payload)?;
            }
            L::Command::MoveCall(_)
            | L::Command::MakeMoveVec(_, _)
            | L::Command::TransferObjects(_, _)
            | L::Command::SplitCoins(_, _)
            | L::Command::MergeCoins(_, _) => (),
        }
    }

    Ok(())
}
