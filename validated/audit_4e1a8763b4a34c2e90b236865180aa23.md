## Finding [1](#0-0) 

### Title
Webhook organization used for signature verification is decoupled from the repository the payload acts on, allowing signature-check bypass and forged events against any stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which `webhook_secret`) to verify the HMAC signature against using a field pulled straight out of the *unverified* request body, while every downstream `Handler` determines which repository/stack the event actually mutates using a *different* field of the same unverified body. This is the same class of bug as the `DebtManager` report: two different quantities (`repository_owner` used to "authorize" vs. `repository.full_name` used to "act") that should be tied together are computed independently, so satisfying the check on one value does not guarantee the other value is legitimate.

### Finding Description
`verify_signature` derives the organization to authenticate the webhook against entirely from attacker-supplied JSON: [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

It then loads that organization's app config and checks the HMAC: [3](#0-2) 

`Shipit::GithubApp#verify_webhook_signature` unconditionally passes when the selected organization has no `webhook_secret` configured: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is documented and fixture-demonstrated as an optional, per-organization setting in multi-org deployments (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple GitHub Applications").

Meanwhile, every event handler ignores `repository_owner` entirely and resolves the actual target repository/stack from a completely separate field of the same attacker-controlled body: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon stack) are two independent, attacker-controlled JSON fields, an attacker can set them to different values: choose an org with no configured `webhook_secret` for `repository.owner.login` to trivially pass `verify_signature`, while setting `repository.full_name` to point at a stack that belongs to a fully-secured, unrelated organization. `PushHandler` (and other handlers such as the status/check-suite/merge handlers) then act on that forged target: [6](#0-5) 

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```

This breaks the binding the rules describe as "an organization that authenticated versus the repository that is written": the equality `organization used for signature-check == organization that owns the repository acted upon` does not hold, and nothing in the controller or `Handler` base class enforces it.

### Impact Explanation
Once the attacker bypasses signature verification for one loosely-configured org (or any org whose `webhook_secret` is left blank, a legitimate, documented configuration option for multi-org deployments), they can send arbitrary, unauthenticated HTTP POSTs to the public `/webhooks` endpoint that are dispatched as if they came from GitHub for **any** repository, including ones under organizations with a properly-configured secret. Depending on which event type is forged this can:
- Trigger `GithubSyncJob`/`stack.sync_github` for arbitrary stacks (`PushHandler`).
- Forge commit `Status` records for arbitrary commits (seen in `test/controllers/webhooks_controller_test.rb` ":state create a Status for the specific commit"), which can influence deploy-eligibility checks (`Shipit.deployment_checks`), potentially enabling an unauthorized deploy.
- Manipulate pull-request/merge-related state for stacks owned by unrelated organizations via the other `Handlers::PullRequest::*` classes.

This crosses the "unauthorized deploy" / "unauthenticated read of stack state, task streams, or deploy output" thresholds called out as High/Critical impact.

### Likelihood Explanation
No credentials, GitHub App keys, or Shipit session are required — only that at least one organization in the deployment's multi-org GitHub config has an unset `webhook_secret` (explicitly supported/documented) or a secret the attacker can otherwise learn. Given that, exploitation is a single unauthenticated POST to `/webhooks` with attacker-chosen JSON body and headers.

### Recommendation
Bind the two values together instead of trusting them independently:
- After computing the winning `github_app`/organization from the signature check, re-derive `repository.full_name`'s owner and require it to match `repository_owner` (or, better, look up the target `Repository`/`Stack` and confirm its `owner` equals the authenticated organization) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to short-circuit to `true` for organizations with a blank secret in multi-org configurations, or require all organizations in a multi-org config to define a non-blank `webhook_secret`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (has `webhook_secret` and hosts the real, sensitive stack) — a supported configuration per `docs/setup.md`.
2. POST directly to `/webhooks` (no valid GitHub signature needed) with:
   - Header `X-Github-Event: push`
   - Body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`
3. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads `OrgA`'s app config, sees no `webhook_secret`, and returns `true` unconditionally — the request is accepted.
4. `PushHandler` ignores `repository_owner` and instead resolves `stacks` via `repository.full_name` = `"OrgB/target-repo"`, triggering `sync_github`/status updates on the `OrgB` stack despite never having authenticated as `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
