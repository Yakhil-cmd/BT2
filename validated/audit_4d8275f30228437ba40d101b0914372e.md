## Analysis Summary

CVE-2021-4213 describes a memory-leak-driven OOM DoS: a component fails to bound and promptly free accumulated state, letting an attacker who can repeatedly trigger the code path exhaust server RAM. The closest analog reachable by an unprivileged actor (a private-payment counterparty/paired device) in `ocore--020` is the unbounded `handledChainsCache` map in `wallet.js`, which is only pruned on a fixed 1-hour timer and has no cap on total size or entry count, unlike other in-memory caches in the codebase (e.g. `storage.js`'s `MAX_ITEMS_IN_CACHE`-bounded caches) that impose hard size limits.

### Title
Unbounded growth of `handledChainsCache` in private-payment handling enables memory-exhaustion DoS - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` deduplicates incoming private payment chains using an in-memory dictionary `handledChainsCache`, keyed by a hash of the chain content, and only purges entries once per hour based on age — there is no limit on the number of distinct keys the map can hold at any given time.

### Finding Description
`handledChainsCache` is declared as a plain object with only a time-based sweep: [1](#0-0) 

Every time `handlePrivatePaymentChains()` processes a new set of private chains (reachable directly from a paired device / private-payment counterparty via `handleMessageFromHub`), it computes a content hash `cache_key` and, on successful validation, stores it in the cache with the current timestamp — with no check on the overall size of `handledChainsCache` before insertion: [2](#0-1) [3](#0-2) 

Unlike `storage.js`'s in-memory unit caches, which are actively shrunk once they exceed `MAX_ITEMS_IN_CACHE` (300 items) via `shrinkCache()`: [4](#0-3) 

`handledChainsCache` has no equivalent size-based eviction — only a `setInterval` that deletes entries strictly older than 1 hour: [5](#0-4) 

A private-payment counterparty (any device paired with the victim wallet/hub) can generate a large volume of distinct, individually-valid low-value private payment chains (varying amount/asset/unit content so each hashes to a unique `cache_key`) and send them faster than the hourly cleanup can remove them. Because each processed chain permanently occupies a slot in `handledChainsCache` for up to an hour regardless of total memory pressure, the attacker can drive unbounded heap growth within that window.

### Impact Explanation
Sustained memory growth in the wallet/hub process can force it into out-of-memory conditions, crashing the process. If this occurs on a node that is also relaying/writing units (e.g., a full node or hub also participating in the DAG), the crash halts its ability to validate and confirm new units, matching the "network unable to confirm new units" impact class for a node made to run out of memory purely from processing unprivileged private-payment traffic.

### Likelihood Explanation
Any device paired for private payments (a routine, low-privilege relationship) can trigger `handlePrivatePaymentChains()` repeatedly with distinct, well-formed chains without needing any special trust, funds, or witness/AA privileges — validation of each chain, while not free, does not gate insertion into the cache by any global memory or count limit, so the attack is only bounded by the attacker's ability to produce distinct valid payloads within an hour, which is comparatively cheap for a determined peer.

### Recommendation
Bound `handledChainsCache` similarly to `storage.js`'s caches: cap the maximum number of resident entries (e.g., using an LRU eviction or `MAX_ITEMS_IN_CACHE`-style limit checked at insertion time) in addition to the existing age-based purge, so an attacker cannot outpace the hourly cleanup by volume alone. Consider throttling/rate-limiting `handlePrivatePaymentChains` invocations per device/peer.

### Proof of Concept
1. Pair a device with the victim wallet for private payments (standard, unprivileged operation).
2. Repeatedly send `handlePrivatePaymentChains`-triggering messages (`body.chains`) containing well-formed, individually valid private payment chains where each chain's payload differs slightly (e.g., different `amount`/`asset`/synthetic `unit`) so each produces a unique `objectHash.getBase64Hash(arrChains)` cache key.
3. Because `handledChainsCache` entries are removed only by the hourly `setInterval` sweep (`wallet.js:949-953`), the attacker can insert far more entries than any single hour's sweep would clear, causing the map (and the process heap holding it) to grow without bound until the process runs out of memory.
