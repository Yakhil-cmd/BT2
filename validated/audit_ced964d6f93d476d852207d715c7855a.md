### Title
Staled per-position risk params keep revoked liquidation thresholds effective on unhealthy accounts — `update_account_threshold` can never restamp them - ([File: contracts/controller/src/risk/params.rs](contracts/controller/src/risk/params.rs))

### Summary
The controller resolves each supply position's `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` once — at position write time — and persists them inside `AccountPosition`. When governance tightens a listing (e.g., lowers `liquidation_threshold` via `edit_asset_in_spoke`), the running position keeps authorizing itself under the rotated-out, more permissive parameters until the permissionless `update_account_threshold` keeper restamps them. That restamp path is unreachable precisely when it matters: the full-tuple scope required to move `liquidation_threshold` asserts the post-update health factor is ≥ 1.05, and `apply_gated_liquidation_params` additionally skips per-position updates that favor the liquidator when the account fails that gate. An underwater or marginal account therefore keeps its old, higher threshold indefinitely — the revoked config continues to authorize the position's solvency calculation, the exact analog of a rotated-out bearer token remaining valid on the long-lived gateway.

### Finding Description
Supply positions snapshot risk parameters into `AccountPosition` at write time. `sync_account_thresholds` is the only path that refreshes them, reached via the public `update_account_threshold(caller, has_risks, account_ids)` entrypoint:

- `has_risks = false` (`RiskRefreshScope::LtvOnly`) only refreshes `loan_to_value` (`restamp_listed_supply_ltv`, `params.rs:44-64`); `liquidation_threshold`/`bonus`/`fees` never move.
- `has_risks = true` (`RiskRefreshScope::FullTuple`) restamps the tuple, but `apply_gated_liquidation_params` (params.rs:68-93) skips any change that "favors the liquidator" when `clears_min_hf` fails, and then the whole call reverts unless final `hf >= 1.05` (params.rs:229-233):

```rust
assert_with_error!(
    env,
    hf >= Wad::from(THRESHOLD_UPDATE_MIN_HF_RAW),
    CollateralError::HealthFactorTooLow
);
```

A lowered `liquidation_threshold` is a liquidator-favoring change: it makes the account liquidatable sooner. For any account whose hypothetical HF under the new threshold falls below 1.05 — i.e., every account the tighter parameter was meant to constrain — the restamp either silently skips the tuple or the entire transaction reverts. Since `update_account_threshold` is permissionless but monotonic-safe by construction, no caller (keeper, liquidator, or governance) can force the stale threshold off the position. Liquidation reads the per-position cached `liquidation_threshold`, so `health_factor`/`is_liquidatable` continue to be computed under the revoked parameters for the lifetime of the position.

### Impact Explanation
Protocol insolvency / delayed liquidation. Positions retain a rotated-out, more permissive liquidation threshold, so accounts that governance intended to make liquidatable remain unliquidatable (or liquidatable later at worse prices) for the full duration of their underwater drift. Attack cost is zero — the borrower simply does nothing; the stale stamp is self-sustaining because the only refresh mechanism is gated on the account staying healthy. Bad debt accrues while the position's stored threshold keeps the computed HF above the liquidation floor.

### Likelihood Explanation
Triggering requires only a routine risk tightening (`edit_asset_in_spoke` lowering a threshold — a normal governance action during volatility) plus an account whose HF under the new params drops below 1.05 — the exact population the tightening targets. No privileged action, timing race, or leaked key is needed; the borrower's entrypoints are ordinary `supply`/`borrow`, and the stale state persists passively. Medium-high likelihood in stressed markets; severity capped by the fact that LTV cuts still propagate via the ungated `LtvOnly` path and liquidators can still act once price drift pushes the stale-threshold HF below 1.

### Recommendation
- Allow `FullTuple` restamping on accounts below the HF floor when the net effect of applying the new params *reduces* the account's HF (i.e., tightening never needs a health gate), rather than blanket-reverting on `hf < 1.05`.
- Alternatively, fall back to computing health factor from the *listing's* current `liquidation_threshold` (via `Context::cached_spoke_asset`) inside liquidation, treating the stored stamp as an upper bound, so rotated-out parameters cannot outlive the config change.

### Proof of Concept
1. Alice supplies USDC and borrows ETH such that HF ≈ 1.10 under `liquidation_threshold = 9000`.
2. Governance executes `edit_asset_in_spoke` lowering the USDC `liquidation_threshold` to 8000 (new HF ≈ 0.97 — Alice should be liquidatable).
3. Any caller invokes `update_account_threshold(true, [alice_id])`; `apply_gated_liquidation_params` skips the tuple (change favors liquidator, `clears_min_hf` fails) and/or the trailing `hf >= 1.05` assertion reverts the call.
4. Alice's stored `liquidation_threshold` remains 9000; `health_factor` reports ≥ 1 and `liquidate` reverts `NotLiquidatable` — the revoked parameter continues to authorize her position, mirroring the stale bearer token on the OpenClaw gateway.
