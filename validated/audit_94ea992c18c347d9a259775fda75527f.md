### Title
Stack-scoped API tokens can read CI/build status for any stack via CCMenu, bypassing `ApiClient.stack_id` authorization - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) can only resolve/read the single `Stack` it was scoped to, via the `stacks` helper. `Shipit::Api::CCMenuController` overrides the `stack` lookup method and resolves the stack directly from `Stack.from_param!(params[:stack_id])`, without going through the scoped `stacks` relation, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`BaseController` defines the authorization-scoping primitive used by every other API controller: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set, and `stack` resolves the requested `params[:stack_id]` only within that restricted relation. This is the mechanism that makes a stack-scoped token safe to hand out (as exercised by the test "an api client scoped to a stack will only see that one stack").

`CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` against **all** stacks, not the `current_api_client`-scoped relation, and its custom `authenticate_api_client` still authenticates via a normal signed `ApiClient` token (`ApiClient.authenticate(params[:token])`) drawn from the same pool of tokens that can be scoped to a single stack (`app/models/shipit/api_client.rb` `stack` association, and `authenticate_api_client`/`stacks` in `base_controller.rb`). The `require_permission :read, :stack` check only verifies the permission string `"read:stack"` is present on the token (`app/models/shipit/api_client.rb`, `check_permissions!`) — it does not verify the token's `stack_id` matches the requested stack.

The equality that should hold — `current_api_client.stack_id == requested_stack.id` (when `stack_id` is set) — which is enforced in every other stack-scoped endpoint through `BaseController#stack`, is broken specifically in `CCMenuController#stack`.

### Impact Explanation
A stack-scoped `ApiClient` token (issued, e.g., to a CI dashboard integration for one specific stack/environment) can be replayed against `GET /api/*stack_id/cc.xml` (routed via `config/routes.rb`, `Api::CCMenuController#show`) for *any* other stack, disclosing that stack's last build status, last build label/time, and lock status: [3](#0-2) 

This is an authorization-boundary violation: an entity authorized to read state for stack A can read state for stack B, contrary to the design intent visible in `stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" test. This matches the "unauthorized read of stack state" class of impact.

### Likelihood Explanation
Any holder of a valid, scoped `ApiClient` token (which does not require elevated privileges beyond having been issued *some* token with `read:stack` permission for one stack) can trigger this with a single unauthenticated-boundary-crossing HTTP GET request — no additional session, secret, or privileged account is required beyond the token they already legitimately possess for their own stack.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the scoped `stacks` relation inherited from `BaseController` (i.e., remove the override, or reuse `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot access stacks outside their `stack_id` scope.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (as in fixture `here_come_the_walrus`).
2. Using that client's `authentication_token`, issue `GET /api/*stack_id_of_stack_B/cc.xml?token=<token>`.
3. `CCMenuController#authenticate_api_client` successfully authenticates the token via `ApiClient.authenticate`.
4. `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions`, regardless of `stack_id`.
5. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against Stack B directly (unscoped), returning Stack B's build/lock status even though the token is scoped only to Stack A — contrasted with `Api::StacksController#index`/`#show`, which use `BaseController#stack`/`#stacks` and correctly restrict the scoped client to Stack A only.
