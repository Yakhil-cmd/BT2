This confirms the multi-tenant configuration: `Shipit.github(organization:)` looks up per-organization config (`webhook_secret`, credentials) via `github_app_config`, keyed purely by an organization name string supplied by the caller [1](#0-0) . The webhook signature check and the actual repository/stack resolution use two different, independently attacker-controlled fields from the same unsigned-at-selection-time payload.

### Title
Webhook signature verified against `repository.owner.login`'s secret while the acted-upon target is `repository.full_name` from the same forgeable payload, permitting cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, itself read from the unauthenticated JSON body [2](#0-1) [3](#0-2) . Every event handler, however, resolves the actual `Repository`/`Stack` to mutate using `repository.full_name` from that same body, e.g. `Handler#repository_name` and `PushHandler#process` [4](#0-3) [5](#0-4) . Nothing ties `repository.owner.login` (used to choose the verifying secret) to `repository.full_name` (used to pick the object acted upon).

### Finding Description
`Shipit.github(organization:)` looks up a distinct config block (including `webhook_secret`) per organization key in `secrets.github` [1](#0-0) . This is the documented mechanism for a single Shipit instance to serve multiple GitHub organizations, each with their own webhook secret (`docs/setup.md` describes per-org config). An attacker who legitimately administers one such configured organization ("OrgA") — and therefore knows or can compute OrgA's `webhook_secret` because they configured the GitHub App for OrgA themselves — can POST an arbitrary JSON body to `/webhooks` with:
- `repository.owner.login` (or fallback `organization.login`) = `"OrgA"` so `verify_signature` fetches OrgA's secret and the HMAC check passes, since it is computed purely over `request.raw_post` with OrgA's known secret [6](#0-5) .
- `repository.full_name` = `"OrgB/victim-repo"`, an unrelated repository/stack tracked by the same Shipit instance for a different organization ("OrgB") that the attacker does not control.

Because the signature verification's organization-selection field (`repository.owner.login`) and the handlers' target-selection field (`repository.full_name`) are two independent, attacker-supplied strings in the same unverified-until-that-point JSON body, and are never cross-checked for consistency, a validly-signed (by OrgA's secret) webhook can act on OrgB's stack. This mirrors the analog bug class of "the field the deployment-trust check covers versus the field the code acts on": the loop that skips the last finalist in the audit report is the same shape as a check that verifies field X (org for secret selection) but the code path executes on field Y (repo full_name) that was never bound to X.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on the victim stack whenever the `branch` matches, which can trigger `GithubSyncJob`, refresh deployed revisions, and (if `continuous_deployment` is enabled on the target stack) drive continuous deployment flows purely off attacker-crafted `ref`/`after` (commit sha) values [7](#0-6) . Other handlers keyed off `repository.full_name` (pull_request opened/labeled/reopened/unlabeled, review-stack archive/unarchive/create) can similarly create, archive, or unarchive review stacks belonging to a repository the attacker does not own [8](#0-7) . This crosses an authorization boundary between organizations sharing one Shipit deployment and can result in unauthorized state changes (sync/deploy-adjacent actions) on a repository/stack the attacker does not control — matching the "cross-repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Exploitation requires the attacker to control (own, or have compromised) at least one organization that is itself configured in the same shared Shipit instance alongside the victim organization — this is a real, documented multi-tenant setup (`github_organizations`, per-org `secrets.github` keys) but not the default single-org configuration. Given that precondition, forging the payload is trivial (no GitHub involvement needed since the secret is self-known), making likelihood high once the multi-org precondition holds, and low/inapplicable for single-org deployments.

### Recommendation
Bind the two fields together: after computing `repository_owner` for secret selection, verify (before dispatching to handlers) that `repository.full_name`'s owner segment, or the resolved `Repository`'s known organization, actually matches `repository_owner`/the verifying organization. Reject the webhook if they diverge, analogous to "adding the missing check" recommended in the source report (add the final, currently-unchecked binding rather than only checking one side).

### Proof of Concept
1. Configure/observe a Shipit instance with two configured GitHub orgs, `OrgA` and `OrgB`, each with their own `webhook_secret` (per `docs/setup.md`, `secrets.github.orga.webhook_secret`, `secrets.github.orgb.webhook_secret`).
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully [2](#0-1) .
5. `PushHandler` resolves stacks via `repository.full_name` = `"OrgB/victim-repo"` [4](#0-3) , and if the branch matches, calls `sync_github` on OrgB's stack — an action the attacker was never authorized to trigger.
