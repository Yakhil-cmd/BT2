### Title
`MembershipHandler` grants privileged `Team` membership without checking that the webhook-authenticating organization matches the target team's organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the untrusted payload (`repository.owner.login`, falling back to `organization.login`). `MembershipHandler#process` then looks up/creates the target `Team` purely by `params.team.id` (GitHub's numeric team id) and calls `team.add_member(...)`, without ever checking that the organization whose secret verified the request equals the organization that owns that `Team`. An attacker who controls a legitimately-configured org in Shipit can sign a payload with `repository.owner.login` set to their own org while `team.id` names a team belonging to a different, privileged org, and add themselves as a member of that team.

### Finding Description
The binding that must hold is:

`signing_organization` (the org whose `webhook_secret` produced a valid signature in `WebhooksController#verify_signature`, derived from `repository_owner`) `== team.organization` (the org that actually owns the `Team` record being mutated by `MembershipHandler`).

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This value is 100% attacker-controlled request body content and is used only to pick which per-org `webhook_secret` to check against — it never has to relate to any other field in the same payload.
- `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`). The lookup key is exclusively `github_id`. If a `Team` with that `github_id` already exists (which is the normal case for any team enumerated in `Shipit.github_teams`, since those are pre-created at boot via `Shipit.github_teams`/`Team.find_or_create_by_handle` in `lib/shipit.rb:256-258`), the block that assigns `organization` from `params.organization.login` never runs — the existing (correct) `team.organization` is left untouched, and is never compared to anything.
- `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then unconditionally appends the attacker-supplied `member` (`User.find_or_create_by_login!(params.member.login)`, fully attacker-controlled string) to that team's `memberships`.
- Nowhere in this path is `repository_owner`/the signing organization compared against `params.organization.login` or the resolved `team.organization`. `verify_signature` only proves "the request was signed with *some* org's secret"; it never proves that org is the one whose team is being mutated.

Exploit: attacker controls (or is configured as) an org `org-a` with its own `webhook_secret` in Shipit (a legitimate multi-org tenant with no other privilege). They send `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <github_id of a real privileged team in org-b>, "name": "x", "slug": "x", "url": "https://example.com" },
  "organization": { "login": "org-b" },
  "member": { "login": "attacker-handle" },
  "repository": { "owner": { "login": "org-a" } }
}
```
signed with `org-a`'s `webhook_secret`. `verify_signature` authenticates successfully against `org-a`. `MembershipHandler` finds the pre-existing `Team` record for `org-b`'s team by `github_id` and adds `attacker-handle` as a member, with no check that `org-a` (the authenticator) has any relationship to `org-b`'s team.

This also matters independent of cross-org spoofing because `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` if `webhook_secret` is blank for the resolved organization, so any org present in `secrets.github` but without a configured secret amplifies the same gap — but the core defect is the missing equality check in `MembershipHandler`/`find_or_create_team!`.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `MembershipHandler` only validates shape/types, not cross-field consistency; `verify_signature` validates a signature against one attacker-chosen organization but is never re-checked against the team's actual organization downstream.

### Impact Explanation
Membership in a `Team` listed in `Shipit.github_teams` is exactly what `User#authorized?` checks (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`). By exploiting this gap, an attacker-controlled GitHub identity gains `Membership` in a real privileged `Team` record, satisfying `authorized?` and thereby gaining whatever Shipit-wide authorization that grants (stack access, deploy/rollback permissions, etc., depending on how the app uses `authorized?`). This is repeatable for any team whose numeric `github_id` the attacker can learn, and does not require compromising `org-b`'s secret at all — only a valid secret for any org configured in the Shipit instance. This matches the "High - escalation into `Shipit.github_teams` authorization" impact category (and could reach Critical impact depending on what downstream actions `authorized?` unlocks, e.g., deploys).

### Likelihood Explanation
Preconditions: the attacker must be an onboarded org in a multi-org Shipit deployment with a legitimately configured `webhook_secret` for their own org (a precondition stipulated by the question itself, not a privileged Shipit role). They must also know the numeric `github_id` of the target privileged team, which is discoverable via public GitHub team URLs/APIs in many configurations. Given those two low-cost, externally-obtainable pieces of information, the attack requires only a single crafted, self-signed HTTP POST to `/webhooks` — fully repeatable and scriptable, no live GitHub interaction needed for the PoC.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in webhook handlers keyed by GitHub numeric IDs), verify that the authenticated organization for the request (the one used in `WebhooksController#verify_signature`) equals `params.organization.login` (reject/raise if mismatched), and additionally verify that any existing `Team` found by `github_id` has `team.organization == params.organization.login` before allowing `add_member`/`members.delete` to proceed. Consider passing the authenticated organization down from the controller to handlers explicitly instead of re-deriving it from payload fields.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test ":membership cannot add a member to a team owned by a different organization than the one that signed the request" do
  # Configure a second org "acme" with its own webhook_secret distinct from "shopify"
  # (via Shipit.stubs(:github).with(organization: 'acme') returning a GitHubApp with a known secret,
  # or by adding a fixture entry analogous to shopify_membership for "acme").
  team = shipit_teams(:shopify_developers) # organization == "shopify"

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'shopify' },      # claimed org (owns the privileged team)
    member: { login: 'attacker' },
    repository: { owner: { login: 'acme' } } # org whose secret actually signs the request
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', ACME_WEBHOOK_SECRET, payload)
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Membership.where(team:).count } do
    post :create, body: payload, as: :json
  end
end
```
Before the fix, this assertion fails: `Membership.count` for `team` increases by 1 because `MembershipHandler` adds `attacker` as a member of `shopify_developers` despite the request being signed by `acme`'s secret, not `shopify`'s — proving the signing organization and the mutated team's organization are not the same value even though the code implicitly assumes they are.     class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)

    end

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
