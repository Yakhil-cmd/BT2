### Title
Signature verification is scoped to `repository.owner.login` while the acted-upon repository comes from the unvalidated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the inbound HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the untrusted, attacker-suppliable JSON body, and then validates the raw body against that org's secret [1](#0-0) . Once verification passes, every event handler resolves the target `Repository`/`Stack` using a *different, unvalidated* field from the same body: `repository.full_name` [2](#0-1) , and `Repository.from_github_repo_name` splits that string directly into `owner/name` to look up the record [3](#0-2) . Nothing in the controller or the handler base class checks that `repository.owner.login` (the field the signature check is keyed on) and `repository.full_name`'s owner segment (the field that determines which repository/stack is mutated) refer to the same organization.

### Finding Description
This mirrors the reported bug class: a value used to gate/index an operation (`_index` in the Solidity report) is not validated against the value actually used to determine the affected state (the array bounds/ordering). Here, the "index" is `repository.owner.login`, used purely to pick which secret authenticates the request, and the "affected element" is `repository.full_name`, used to pick which `Stack` gets synced, which pull request gets its labels captured, which review stack gets created, etc. `verify_signature` never checks that these two identifiers agree:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`GitHubApp#verify_webhook_signature` additionally short-circuits to `true` whenever no `webhook_secret` is configured for the resolved organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

The `/webhooks` endpoint requires no session, API token, or GitHub App private key (`skip_before_action :verify_authenticity_token` and no other authentication) [6](#0-5) , so any unprivileged network attacker can `POST` a fully attacker-authored JSON body. If any organization configured in this Shipit instance has no `webhook_secret` set (a legitimate, supported configuration per the `return true unless webhook_secret` fallback), the attacker sets `repository.owner.login`/`organization.login` to that org so `verify_signature` passes trivially, while setting `repository.full_name` to `victim-org/victim-repo` — a completely different, secret-protected organization/repository. The push/pull_request/status/membership handlers then act on the victim's `Stack`/`Repository` using only `repository.full_name` [7](#0-6) [8](#0-7) .

This breaks the intended binding: **organization authenticated (`repository.owner.login`) == repository/stack written (`repository.full_name`)**. Before the attack, only webhooks whose HMAC is signed by a repository's own organization secret can influence that repository's stack. After the crafted request, an attacker with knowledge of (or access to) any single secret-less/known-secret organization in the same Shipit deployment can trigger `GithubSyncJob` for, or otherwise mutate state belonging to, an unrelated victim repository/organization, without ever knowing that victim's secret.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy/rollback" bar in scope: `PushHandler#process` enqueues `Stack#sync_github` for any stack matching the forged `full_name`/branch [9](#0-8) , and `Membership`/`PullRequest`/`Status` handlers likewise mutate victim-owned records keyed solely by `full_name`. Because the trust check (signature) and the effect (which repository/stack state changes) are bound to two different, independently attacker-controlled JSON fields, this is a genuine authorization/confused-deputy flaw reachable by an unauthenticated network attacker, not merely a best-practice nit.

### Likelihood Explanation
Exploitability is conditioned on at least one organization in the deployment's GitHub App configuration lacking a `webhook_secret` (explicitly supported by `verify_webhook_signature`'s `return true unless webhook_secret`) or on an attacker who legitimately controls webhooks for one organization onboarded to the same Shipit instance and wants to affect a different organization's stacks. Given that `webhook_secret` is optional per-organization configuration in `GitHubApp.new` [10](#0-9) , and the endpoint is unauthenticated by design (it's meant to receive GitHub's webhooks), this is a realistic multi-tenant Shipit deployment scenario, not a purely theoretical one.

### Recommendation
Bind the signature-verification organization to the same field that determines the affected repository/stack: derive both from `repository.full_name` (or validate that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers. Additionally, avoid the `return true unless webhook_secret` bypass for any organization, or require `webhook_secret` to be mandatory for all configured organizations.

### Proof of Concept
1. Configure Shipit with two orgs: `unsecured-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`, owns stack `victim-org/victim-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "unsecured-org" }
  }
}
```
3. `repository_owner` resolves to `unsecured-org`; `Shipit.github(organization: 'unsecured-org')` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` header is even required [5](#0-4) .
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` [2](#0-1)  and enqueues `sync_github` for the victim's stack, entirely bypassing `victim-org`'s configured secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
