### Title
`recapitalize` refunds the payer based on the declared `amount`, not the measured pool receipt — overstated `amount` drains pool custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`Pool::recapitalize` computes the "excess" refund as `amount - applied` where `amount` is a caller-declared parameter, then transfers that refund out of pool custody. It never measures how many tokens actually arrived. This mirrors the yAxis `setCap` bug class: bookkeeping subtracts a value derived from a parameter rather than the real balance delta, corrupting the cash book and letting tokens leave that were never deposited.

### Finding Description
In `accounting`, the applied credit is capped at the backing shortfall, and `refund` is computed purely arithmetically from `amount`:

```rust
let applied = amount.min(guards::backing_shortfall(&cache));
let refund = amount.checked_sub(applied)...
cache.credit_cash(applied);
```

`apply` then executes `outcome.cache.transfer_out(&payer, outcome.refund)` — a real token transfer out of pool custody — with no `balance_delta_since`-style measurement of what the controller actually moved in before the call. Contrast with `repay_debt_from_controller` in `contracts/controller/src/strategies/legs.rs`, which uses `transfer_amount_measured` and `refund_controller_balance_delta` so refunds track the *actual* balance increase; `recapitalize` has no equivalent guard.

The existing test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3407`) demonstrates the concrete consequence: calling `recapitalize` with no real funding still pays out the full custody as "refund", while the cash book still claims the supplier's deposit is backed — subsequent `withdraw` passes `require_reserves` (which reads the book) and fails inside the SAC transfer, permanently freezing supplier funds.

### Impact Explanation
If the controller's `recapitalize` entrypoint forwards a user-supplied `amount` to the pool without first measuring that exactly `amount` tokens were transferred in (the pool itself does not verify), an unprivileged caller can declare a large `amount`, receive `amount - shortfall` back in real tokens funded by supplier custody, while the book is credited only `shortfall` — or worse, the book is left overstating custody. Result: theft of supplier funds and/or permanent freezing of withdrawals when the book promises cash the pool no longer holds (protocol insolvency shape identical to the yAxis report's locked-funds outcome).

### Likelihood Explanation
`recapitalize` is listed among the unprivileged controller entrypoints and the pool endpoint is reachable in the same transaction as the token transfer. The exploit requires only that the declared `amount` exceed the measured inflow — which the pool never checks. Caveat: I could not fully read `contracts/controller/src/markets.rs`/`lib.rs` to confirm whether the controller wraps the pool call with `transfer_amount_measured` and passes the measured value. If it does, the pool-side arithmetic is safe by construction and this degrades to a defense-in-depth gap rather than an exploitable bug; the divergence from the measured-receipt pattern used everywhere else in the codebase is still a real inconsistency worth flagging.

### Recommendation
Measure the recapitalization inflow the same way `repay` does: snapshot the pool's token balance before the transfer, compute `received = balance_delta_since(...)`, and compute `applied`/`refund` from `received`, not from the declared `amount`. Alternatively have the controller pass the measured amount and assert `received == amount` in the pool.

### Proof of Concept
As encoded in `contracts/pool/tests/flows.rs:3407-3483`:

```rust
// Supplier deposited `deposit`; pool custody == cash book.
let custody = token.balance(&t.pool);
// Call recapitalize with amount == custody and NO funding transfer.
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
// Pool pays out `custody - shortfall` as "refund" — custody is drained.
assert_eq!(token.balance(&t.pool), 0);
// Cash book still claims >= deposit: supplier's withdraw passes
// require_reserves, then reverts inside the SAC transfer (BalanceError=10).
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```

The test exercises the pool entrypoint with mocked owner auth; production reachability hinges on the controller forwarding an unmeasured `amount`, which I was unable to confirm within available iterations.
