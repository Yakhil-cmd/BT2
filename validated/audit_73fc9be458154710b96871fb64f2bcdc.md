### Title
Cross-tenant webhook forgery via `WebhooksController#repository_owner` organization fallback - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to validate a signature against using `repository_owner`, which falls back to the payload's top-level `organization.login` when `repository.owner.login` is absent. Downstream handlers (e.g. `OpenedHandler`) never re-check that the authenticated organization matches the owner encoded in `repository.full_name`, so in a multi-tenant Shipit deployment an attacker can authenticate against any configured organization that has no `webhook_secret` set, while mutating a stack belonging to a completely different, properly-secured organization's repository.

### Finding Description
Binding claimed broken: `Org_auth` (the organization whose `GitHubApp`/`webhook_secret` is used to verify the HMAC) `==` `Org_owner` (the owner of the `Repository` row that `ReviewStackAdapter#create!` mutates).

- `Org_auth = params.dig('repository','owner','login') || params.dig('organization','login')`, computed in `repository_owner` [1](#0-0) , and used to pick the app config via `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `Org_owner` is derived later, independently, from `params.repository.full_name` inside `OpenedHandler#repository`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , then used by `ReviewStackAdapter#create!` to persist a `ReviewStack` row scoped to that repository [4](#0-3) .

These two values are never compared anywhere in the request path (`WebhooksController#create`, `Handler#initialize`, `OpenedHandler`, `ReviewStackAdapter`), so `Org_auth` and `Org_owner` can diverge with no failure.

Root cause: `Shipit.github` resolves credentials per-organization only when Shipit is deployed in **multi-org mode** (`github_default_organization` present) — see `github_app_config`/`github_default_organization` [5](#0-4) . `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization's `webhook_secret` is blank: `return true unless webhook_secret` [6](#0-5) . Every shipped example config defaults `webhook_secret` to nil [7](#0-6) , making this a realistic default state for an onboarded-but-not-yet-secured org in a multi-tenant install.

Exploit flow (multi-org deployment only):
1. Shipit is configured with `github:` keyed by multiple organizations, e.g. `OrgOne`, `OrgTwo` (per `docs/setup.md` "Using Multiple Github Applications" and `secrets_double_github_app.yml`).
2. One configured org (say `attacker-empty-org`) has `webhook_secret` left blank — a supported, documented configuration state, not a secret the attacker needs to know.
3. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and a body: `{"action":"opened","number":<n>,"pull_request":{...,"head":{"ref":"..."}, "user":{"login":"attacker"}, "labels":[]},"repository":{"full_name":"victim-org/target-repo"},"organization":{"login":"attacker-empty-org"},"sender":{"login":"attacker"}}` — note `repository.owner.login` is intentionally omitted.
4. `repository_owner` falls back to `attacker-empty-org`; `Shipit.github(organization: 'attacker-empty-org')` returns the App config with no `webhook_secret`; `verify_webhook_signature` returns `true` unconditionally, regardless of the actual `X-Hub-Signature` header.
5. `Handler#initialize` re-parses the same raw body via `ExplicitParameters`; `OpenedHandler#repository` looks up `Repository.from_github_repo_name('victim-org/target-repo')`, which is a real, provisioned repository belonging to `victim-org` (secured with its own real `webhook_secret` that the attacker never had to supply or guess).
6. If that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all` (or matches a label rule), `ReviewStackAdapter#create!` creates a `ReviewStack`/`Stack` row and enqueues provisioning for `victim-org/target-repo`, entirely off an HMAC validated against an unrelated organization's (non-)secret.

Existing guards don't stop this: `drop_unhandled_event` only checks the event is handled; `verify_signature`'s only failure mode is `GithubOrganizationUnknown`, which only triggers if the *claimed* organization isn't configured at all — it does not check that the claimed organization matches the repository being acted upon. `ExplicitParameters` schemas for pull-request handlers require `repository.full_name` but never require or cross-check `repository.owner.login` against the authenticated organization.

### Impact Explanation
An attacker who owns/controls one poorly-configured tenant org in a multi-org Shipit install can forge webhook events that mutate stack state (create/archive/unarchive review stacks, and depending on handler, merge/update pull request metadata) for a **different, fully-secured** organization's repository, without ever possessing that organization's `webhook_secret`. This is a payload-for-one-repo-mutating-another's-stack scenario, matching the Critical impact category. Blast radius is bounded by the set of repositories tracked under any organization sharing the same Shipit instance; it's repeatable per request/PR number and works for every pull-request handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) since they all resolve the repository the same way.

### Likelihood Explanation
Preconditions are non-trivial but plausible in real deployments: Shipit must be running in the documented multi-org configuration mode, at least one configured organization must have an unset `webhook_secret` (the shipped default in every example config), and the victim repository must already exist in Shipit with review-stack provisioning enabled. Given these, the attacker's cost is a single unauthenticated HTTP POST with a crafted JSON body — no signature, token, or secret is required, and the attack is fully repeatable. In the common single-org deployment mode, `Shipit.github`'s `if github_default_organization.nil?` branch ignores the `organization:` argument entirely and always uses the single configured secret, so this specific bypass does not apply there — likelihood is concentrated in multi-org setups with a misconfigured org.

### Recommendation
Bind the authenticated organization to the resource being mutated: after computing `repository_owner` in `WebhooksController`, validate that it matches (case-insensitively) the owner segment of `payload.dig('repository','full_name')` whenever both are present, and reject (422) on mismatch. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in multi-org mode — require an explicit opt-in (e.g. a `webhook_secret_optional: true` flag) so a blank secret can't be used to authenticate arbitrary payloads for other tenants.

```ruby
require 'test_helper'

module Shipit
  class WebhooksControllerOrgConfusionTest < ActionController::TestCase
    tests Shipit::WebhooksController

    test "cross-org webhook forgery via organization fallback creates stack for unrelated repo" do
      # Precondition: multi-org config with 'attacker-empty-org' having no webhook_secret,
      # and victim repository 'victim-org/target-repo' already provisioned with allow_all.
      repository = shipit_repositories(:shipit) # stands in for victim-org/target-repo
      repository.update!(owner: "victim-org", name: "target-repo",
                          review_stacks_enabled: true, provisioning_behavior: "allow_all")

      request.headers['X-Github-Event'] = 'pull_request'
      payload = {
        action: "opened",
        number: 999,
        pull_request: {
          id: 1, number: 999, url: "https://api.github.com/x", title: "x", state: "open",
          additions: 1, deletions: 0,
          head: { sha: "deadbeef", ref: "feature-branch" },
          user: { login: "attacker" },
          assignees: [], labels: []
        },
        repository: { full_name: "victim-org/target-repo" }, # NOTE: no owner.login
        organization: { login: "attacker-empty-org" },        # unsecured org fallback
        sender: { login: "attacker" }
      }.to_json

      # Org_auth (what verify_signature checks) vs Org_owner (what gets mutated):
      org_auth  = "attacker-empty-org"
      org_owner = "victim-org"
      refute_equal org_auth, org_owner # binding is broken before the request

      assert_difference -> { repository.reload.stacks.count }, 1 do
        post :create, body: payload, as: :json
      end
      assert_response :ok
    end
  end
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
