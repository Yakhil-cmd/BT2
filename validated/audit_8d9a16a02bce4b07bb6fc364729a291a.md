### Title
Unauthenticated NULL/undefined pointer dereference (uncaught TypeError) in asset payment validation crashes the node - ([File: validation.js])

### Summary
`validatePayment()` in `validation.js` dereferences `payload.inputs[0].type` without first checking that `payload.inputs[0]` is a non-null object, mirroring the class of bug in CVE-2025-55904 (dereferencing an attacker-controlled, empty/malformed field before validating its type, leading to a crash). In ocore, any single posted unit containing an asset-payment message can supply `inputs: [null]` (or any non-object primitive as the first element) to trigger a `TypeError` on a node process, and this repo's own uncaught-exception handler intentionally rethrows to crash the whole process.

### Finding Description
`isNonemptyArray()` only checks that `payload.inputs` is a non-empty array; it does **not** validate the type of its elements: [1](#0-0) 

For the base-asset branch, elements are checked with `isNonemptyObject(input)` inside `validatePaymentInputsAndOutputs` before any property access: [2](#0-1) 

However, for the **custom-asset** branch, `validatePayment()` accesses `payload.inputs[0].type` *before* any such object-type check is performed: [3](#0-2) 

If an attacker crafts a unit with a `payment` message referencing any existing/known asset (`"asset": "<valid 44-char asset hash>"`) and `"inputs": [null]` (which satisfies `isNonemptyArray` since it's a non-empty array), execution reaches line 2099 (`payload.inputs[0].type === "issue"`), where `payload.inputs[0]` is `null`. This throws `TypeError: Cannot read properties of null (reading 'type')` inside the asynchronous callback of `storage.loadAssetWithListOfAttestedAuthors`, which is not wrapped in a `try/catch`.

This unhandled exception propagates up through `async`/DB-callback chains from `validateMessage` → `validateInlinePayload`/`validatePayment`, triggered from the normal unit-validation pipeline (`network.handleOnlineJoint`/`handlePostedJoint` → `handleJoint` → `validation.validate` → `validateMessages`). ocore explicitly treats any uncaught exception as fatal and re-throws it to crash the process by design: [4](#0-3) 

This is the direct functional analog of the Open5GS bug class: an unauthenticated/unprivileged actor supplies a minimally-formed field (empty HTTP body → NULL pointer in `parse_multipart`; here, a `null`/non-object array element → dereference of `.type` on `null`) that a validator dereferences without a preceding type/null check, resulting in denial of service.

### Impact Explanation
Any node (full node or hub) that receives and validates such a unit — via a directly posted joint (`handlePostedJoint`), a broadcast `joint` justsaying, or a `get_joint` response — will throw an uncaught `TypeError` during validation and crash the entire node process, per the codebase's own `uncaughtException` handler which deliberately calls `throw err` to terminate the process. This is a network-unable-to-confirm-new-units-class denial of service: a single crafted unit posted by any unprivileged unit poster can repeatedly crash full nodes/witnesses that process it, degrading network availability and confirmation of new units. No spending, definitions, private keys, or special privileges are required — only knowledge of any one valid, existing asset hash.

### Likelihood Explanation
High. The only prerequisites are: (1) knowledge of any existing asset unit hash on the DAG (trivially discoverable, since assets are public on-chain objects), and (2) the ability to submit or broadcast a unit — something any wallet/light client/peer can already do. Building the payload `{ app: "payment", payload: { asset: "<hash>", inputs: [null], outputs: [...] } }` requires no cryptographic material for the malformed field itself (although the surrounding unit still needs valid authors/signatures/parents to pass earlier structural checks up to this point, which is normal unit construction). Because it hits validation code executed on every peer processing the unit, one submission can affect every reachable node that processes it.

### Recommendation
In `validatePayment()` (validation.js), before accessing `payload.inputs[0].type`, validate that `payload.inputs[0]` is a non-empty object (mirroring the guard already present in `validatePaymentInputsAndOutputs`'s per-input loop), e.g.:
```js
if (!isNonemptyObject(payload.inputs[0]))
    return callback("first input must be a non-empty object");
var bIssue = (payload.inputs[0].type === "issue");
```
More generally, audit all early destructive/property-access points on `payload.inputs`/`payload.outputs` elements throughout `validation.js` that occur prior to the per-element `isNonemptyObject` checks in `validatePaymentInputsAndOutputs`, to ensure no code path dereferences array elements before their shape is validated. Consider wrapping validation callbacks in defensive `try/catch` blocks that convert unexpected exceptions into `ifUnitError`/`ifJointError` responses instead of allowing them to become uncaught exceptions that crash the process, consistent with the pattern already used elsewhere in `validation.js` (e.g., the `try { ... } catch(e) { return callbacks.ifJointError(...) }` guards seen around payload-hash calculation).

### Proof of Concept
1. Identify any existing asset unit hash `ASSET_HASH` already confirmed on the network (public information).
2. Construct a unit with a `payment` message:
```json
{
  "app": "payment",
  "payload_location": "inline",
  "payload_hash": "<computed>",
  "payload": {
    "asset": "ASSET_HASH",
    "inputs": [null],
    "outputs": [{ "address": "SOME_VALID_ADDRESS", "amount": 1 }]
  }
}
```
3. Sign/finalize the unit as usual (author signatures, parents, commissions) so it passes earlier structural checks in `validation.js`.
4. Post the unit to a full node (`handlePostedJoint`) or broadcast it as a `joint` justsaying (`handleJustsaying` "joint" case, `network.js:2859`), which routes to `handleOnlineJoint` → `handleJoint` → `validation.validate` → `validateMessages` → `validateMessage` → `validateInlinePayload` → `validatePayment`.
5. During the `storage.loadAssetWithListOfAttestedAuthors` callback, `payload.inputs[0].type` throws `TypeError: Cannot read properties of null (reading 'type')`.
6. The exception is uncaught, is caught only by `process.on('uncaughtException', ...)` in `network.js`, which logs it and then `throw err`s again, crashing the node process.

*Note: I was unable to execute this against a live node in this environment; the analysis is based on static code review of the validation and network modules described above. The reachability chain (`handlePostedJoint`/`handleOnlineJoint` → `validation.validate` → `validatePayment`) and the missing type guard at `validation.js:2099` were directly verified in the indexed source, but dynamic confirmation of the exact crash behavior would require running the code.*
