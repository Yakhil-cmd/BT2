### Title
Stale/manually-posted `data_feed` oracle values allow price-arbitrage draining of AA funds - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
Obyte's `data_feed` / `in_data_feed` oscript primitives let an Autonomous Agent (AA) read the last value an oracle address posted on-chain and use it directly in formulas that determine payouts (exchange rates, settlement amounts, etc.). Unlike Chainlink, there is no protocol-level heartbeat or deviation-triggered update requirement — an oracle updates whenever it likes, and the reader simply returns whichever record is "last" within the requested MCI window. Any AA whose logic uses this raw value to price a swap (a pattern the repo's own reference templates demonstrate) is exposed to the same staleness-arbitrage class described in the KelpDAO/Chainlink report: an unprivileged trigger sender can watch the real market price diverge from the stale on-chain feed and submit a trigger to buy/sell against the AA at the frozen price, extracting value from the AA's pooled funds.

### Finding Description
The oscript `data_feed` case in `formula/evaluation.js` resolves a feed by calling `dataFeeds.readDataFeedValue(...)`, which for stable data ultimately calls `readDataFeedByAddress`: [1](#0-0) 
`readDataFeedByAddress` simply scans the key-value store for entries in `[min_mci, max_mci]` and, when `ifseveral === 'last'`, keeps the record with the highest `mci` — i.e., whatever the oracle most recently chose to post, with no timestamp/age check and no deviation bound against a reference price: [2](#0-1) 
For AAs, `readDataFeedValue` additionally allows picking up not-yet-stable oracle posts by `latest_included_mc_index`/`level` ordering — again purely positional, not price/age aware: [3](#0-2) 

Data-feed posting itself is a completely voluntary act by the oracle author (`addDataFeeds` just writes whatever value/feed_name the oracle unit contains once it stabilizes), so there is no protocol guarantee about how quickly the on-chain price catches up to the real market price: [4](#0-3) 

The repository's own reference/sample AA templates show the exact vulnerable pattern the report describes: an AA computes a swap amount directly from the raw oracle value with no staleness or deviation guard, e.g. `futures_contract.oscript` converts bytes to a USD-pegged asset using `$exchange_rate = data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name='GBYTE_USD_MA_2019_04_30']]`: [5](#0-4) 
and `option_contract.oscript` gates a binary payout purely on whether the last posted feed value crosses a threshold: [6](#0-5) 

Because `data_feed` returns only the single latest posted value (bounded solely by `min_mci`/`max_mci`, not by feed age or deviation), any AA trigger sender can post a trigger the instant they observe (from off-chain markets) that the real price has moved away from the last on-chain feed value, but before the oracle re-posts an updated value, and capture the stale rate — symmetric to the Kelp/Chainlink `[-2%, 2%]`-band arbitrage, except here the divergence window is unbounded because there is no enforced heartbeat at all.

### Impact Explanation
Any AA that uses `data_feed`/`in_data_feed` to price a swap, settlement, or payout (a documented and encouraged usage pattern, as shown by the bundled `futures_contract.oscript`, `option_contract.oscript`, and `sell_asset_for_bytes.oscript` samples) is subject to systematic value extraction: an unprivileged trigger sender who is faster than the oracle can repeatedly trade against the AA at a stale rate, draining base-asset/issued-asset balances held by the AA to the detriment of other depositors/holders — i.e., concrete AA fund loss, matching the "Medium/High" bar required (unauthorized value transfer out of pooled AA funds).

### Likelihood Explanation
Likelihood is high for any deployed AA following this common pricing pattern: the attack requires no privileged access — just an ordinary unit/trigger sender monitoring an external price source and racing the oracle's next post. The wider and less frequent the oracle updates (which ocore does not constrain), the larger and more frequent the exploitable window, mirroring (and arguably worse than) the Chainlink deviation-threshold scenario in the source report.

### Recommendation
- At the oscript/AA-authoring level, provide (and document) a way to require/verify feed freshness inside `data_feed` evaluation, e.g. allow AAs to reject if the winning record's MCI/timestamp is older than a configurable bound, rather than only exposing `min_mci`.
- Encourage/require reference AA templates in the repo (`futures_contract.oscript`, `option_contract.oscript`, etc.) to check feed recency (e.g., compare `what='unit'`-derived timestamp or MCI against `timestamp`/`last_ball_timestamp`) and/or use multiple independent oracles combined with a max-deviation check before using the value to compute payouts.
- Consider exposing feed post frequency/deviation metadata so AA authors can implement circuit breakers against stale-price arbitrage, since `readDataFeedByAddress`/`readDataFeedValue` currently provide no such signal.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/futures_contract.oscript`, which converts a trigger's bytes/USD-asset outputs to a payout using `$exchange_rate = data_feed[[oracles=..., feed_name=...]]` [5](#0-4) .
2. Oracle posts `GBYTE_USD_MA_2019_04_30 = 50` (per the sample comment "1 GB is now 50 USD").
3. Real market price of the underlying moves to, say, 55 USD, but the oracle has not yet re-posted (no heartbeat is enforced anywhere in `data_feeds.js`/`main_chain.js`).
4. An unprivileged trigger sender submits a trigger unit exchanging `usd_asset`/`gb_asset` for bytes using the stale `$exchange_rate = 50`, computed via `readDataFeedByAddress` returning the last stored value regardless of its age [2](#0-1) , capturing the ~10% price difference from the AA's byte balance.
5. Repeat each time the real price diverges beyond the oracle's next update, systematically draining AA funds — the same "features not bug" style arbitrage flagged in the external report, but without even a bounded deviation threshold to limit the window.
