### Title
Stack-scoped ApiClient tokens can read CCMenu status for any stack, bypassing token stack-scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to resolve the target stack directly from the unscoped `Stack` model instead of using the token-scoped `stacks` relation that every other API controller relies on. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` establishes the authorization binding for every API endpoint: an `ApiClient` can optionally be scoped to a single `Stack` via `belongs_to :stack, optional: true`, and lookups are meant to go through: [1](#0-0) 

which restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped, and only falls back to `Stack.all` for unscoped ("global") clients. `require_permission :read, :stack` only checks that the permission string `read:stack` is present on the client: [2](#0-1) 

it performs no per-stack authorization; the actual "which stack can this token see" enforcement lives entirely in the `stacks`/`stack` helper in `BaseController`.

`CCMenuController`, however, overrides `stack` to bypass that helper entirely: [3](#0-2) 

`Stack.from_param!(params[:stack_id])` resolves against the full `Stack` table with no reference to `current_api_client.stack_id`. So for a client created with `stack: stack_A` (as in the `here_come_the_walrus` fixture, and as supported generally by the `ApiClient` model), the CCMenu endpoint will happily resolve and render status/output for `stack_B`, `stack_C`, etc., simply because the caller supplied a different `stack_id` param.

The equality that should hold and is broken:
`{stacks the token authorizes} == {stack the token can act on via CCMenuController}`
Before the request: the token is bound to `stack_id = A` (this is enforced for every other `Api::*Controller` via `BaseController#stacks`). After the request: `CCMenuController#stack` resolves any `stack_id` param against `Stack.from_param!`, independent of `A`. The token's authorization scope and the actually-touched resource diverge — the exact class of binding violation cited by the "stack a token authorises versus a stack it touches" pattern from the analog report (rounding causing a minted/burned amount to diverge from the intended balance-bound amount; here, a param-supplied `stack_id` diverges from the token-bound `stack_id`).

This is also confirmed by the existing test suite: `CCMenuControllerTest` never exercises a scoped client against a `stack_id` different from the one it's scoped to — all fixtures used (`@client`) are exercised only against `@stack = shipit_stacks(:shipit)`, so this gap is untested: [4](#0-3) 

Compare with `StacksControllerTest`, which does explicitly test and enforce the scoping behavior for the analogous, correctly-implemented `stacks` helper: [5](#0-4) 

### Impact Explanation
This satisfies the "High" impact bucket: "unauthenticated read of stack state, task streams or deploy output." An `ApiClient` token deliberately scoped to a single stack (e.g. issued to an external CI dashboard, or generated for that single stack via `CCMenuUrlController`, which mints tokens with `read:stack` permission) can be replayed with an arbitrary `stack_id` query parameter to read the CI/deploy status (name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of every other stack in the Shipit installation, including stacks belonging to unrelated repositories/teams that the token holder was never meant to have visibility into.

### Likelihood Explanation
High likelihood: the endpoint accepts the token via a URL query-string parameter (`token=`) as well as Basic Auth, `stack_id` is a simple public-form path/query param, and no additional secrets, sessions, or privileged access are required beyond possessing any valid, stack-scoped `read:stack` token — which by design is meant to be distributed to lower-trust integrations for a single stack.

### Recommendation
Change `CCMenuController#stack` to resolve through the token-scoped `stacks` relation (the same helper used by `BaseController`, `StacksController`, `TasksController`, etc.) instead of the unscoped `Stack.from_param!`, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a client scoped to a specific stack cannot resolve any other stack's CCMenu status.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController`) an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_A`, and shares the resulting `authentication_token`/CCMenu URL with an external dashboard for stack A only.
2. Attacker (holder of that token, or anyone who obtains the CCMenu URL) sends: `GET /api/stacks/<stack_B_owner>/<stack_B_name>/<stack_B_env>/cc.xml?token=<stack_A_token>`
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully (it's valid, just scoped to stack A).
4. `require_permission :read, :stack` passes because the token has the `read:stack` permission string (no per-stack check).
5. `stack` resolves `Stack.from_param!(params[:stack_id])` for stack B directly, ignoring that the token's `stack_id` is A.
6. The response renders stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, etc.), disclosing deploy state for a stack the token was never authorized for.
