### Title
Cross-stack authorization bypass in CCMenu API — a stack-scoped `ApiClient` token can read the CI/deploy status of any stack (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, and every other API endpoint enforces this scope through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id?` scoping check. As a result, a token that is only supposed to authorize `read:stack` access to one specific stack can be used to fetch build/deploy status for any other stack in the installation.

### Finding Description
`ApiClient` can be created with an optional `stack:` association [1](#0-0) . The intended binding is: *a token scoped to stack A authorizes reads only for stack A*. This binding is enforced generically in `BaseController`: [2](#0-1) 

Every controller that inherits `#stack` from `BaseController` (e.g. `Api::StacksController`) is therefore restricted to the client's authorized stack, as confirmed by the existing test `"an api client scoped to a stack will only see that one stack"` [3](#0-2) .

`Api::CCMenuController`, however, redefines `#stack` to bypass this scoping entirely: [4](#0-3) 

It also overrides `authenticate_api_client` to read the token from a `token` query parameter instead of the `Authorization` header [5](#0-4) , and `#show` uses this unscoped `stack` to render CI status for whatever `stack_id` is supplied [6](#0-5) .

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string, not that it is authorized for the specific stack being requested [7](#0-6) .

The binding broken is: **stack a token authorizes (`current_api_client.stack_id`) ≠ stack it touches (`params[:stack_id]` resolved via unscoped `Stack.from_param!`)**.

### Impact Explanation
Holding any token with `read:stack` permission — including one deliberately scoped by an operator to a single, low-sensitivity stack (e.g., generated through `CCMenuUrlController#fetch`, which mints a `read:stack`-permissioned client [8](#0-7) ) — an attacker can enumerate/query the CCMenu XML endpoint for arbitrary `stack_id` values and obtain another stack's build/deploy status, lock state, and last build label/time. This is an unauthenticated-relative-to-scope read of stack state for stacks the token was never authorized to see, which matches the High-severity class "unauthenticated read of stack state ... or an unauthorized deploy, rollback or merge" scope-escalation criterion (escalation beyond the token's `Shipit.github_teams`/stack authorization).

### Likelihood Explanation
Likely to be triggered whenever a CCMenu-only token exists (these are routinely handed out for CI dashboard/status-monitoring integrations, which is the documented purpose of `CCMenuUrlController`). No special privilege beyond possessing any valid `read:stack` token is required, and stack ids/names are often guessable or discoverable through the UI, so exploitation only requires changing a URL parameter.

### Recommendation
Make `Api::CCMenuController#stack` respect the client's scope by resolving through the shared `stacks` scoping method instead of the unscoped `Stack` model, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits the same `current_api_client.stack_id?` restriction enforced in `BaseController#stacks`.

### Proof of Concept
1. Provision (or obtain) an `ApiClient` scoped to `stack_id: <stack A>` with only `read:stack` permission (as done by `CCMenuUrlController#fetch`, or matching fixture `here_come_the_walrus` which is scoped to the `shipit` stack) [9](#0-8) .
2. Call `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` with `stack_id` set to a different, unauthorized stack B.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!` [10](#0-9) , `current_api_client.stack_id?` is never consulted, and the response returns stack B's build/deploy status even though the token was only authorized for stack A.
