### Title
Unaccounted direct token transfers permanently strand funds in the pool - ([File: contracts/pool/src/cache/cash.rs](contracts/pool/src/cache/cash.rs))

### Summary
An unprivileged user can transfer a market asset directly to `LiquidityPool` outside the measured deposit/recapitalization paths. The transfer increases the contract's token balance, but no market state records it as cash, supply, debt, or revenue. Because every outgoing transfer is bounded by the accounting `cash` book or an explicitly computed revenue/refund amount, the donated balance is not reclaimable through an in-scope entrypoint.

### Finding Description
`LiquidityPool` separates physical token custody from accounting cash: `Cache::cash` is explicitly documented as an accounting book rather than the live token balance. [1](#0-0) 

A direct `token.transfer(user -> pool, amount)` changes only the physical balance. Supply uses the controller-measured amount received, while recapitalization credits only `min(amount, backing_shortfall)` and refunds the declared excess; neither path scans the pre-existing pool balance. [2](#0-1) 

Outbound withdrawals call `require_reserves(net_transfer)` and debit only accounting cash before `transfer_out`; they cannot spend the unbooked surplus. [3](#0-2)  Similarly, `claim_revenue` transfers only the result of `burn_claimable_revenue()` after debiting cash. [4](#0-3) 

The repository's own money-flow audit demonstrates the invariant directly: after an unsolicited donation, the token balance equals both markets' cash plus the donated amount, and comments state that it belongs to no market cash book. [5](#0-4) 

### Impact Explanation
Any asset units sent directly to the pool remain as excess physical custody that no account owns. They cannot be withdrawn as supplier cash, claimed as protocol revenue, or swept by an unprivileged in-scope function. This permanently freezes the sender's funds.

### Likelihood Explanation
The issue requires a user error equivalent to sending Ether to an unnecessary `payable` function: invoking the Stellar asset contract's `transfer` directly against the pool rather than routing through `Controller::supply` or `Controller::recapitalize`. The action is externally reachable and does not require privileged access. The impact is bounded to mistakenly transferred amounts, so this is Medium severity.

### Recommendation
Add an explicit recovery mechanism for surplus token custody—for example, an owner-gated `sweep(asset, to, amount)` capped by `token_balance - sum(market cash for that asset)`—or document and enforce off-chain that direct transfers are irrecoverable. At minimum, expose a view returning `token.balance(pool) - sum(cash)` so accidental deposits can be detected.

### Proof of Concept
1. Deploy the standard `LiquidityPool` with an existing SAC-backed market.
2. From an unprivileged address holding `amount > 0` of the market asset, call the SAC directly:
   `token.transfer(sender, pool_address, amount)`.
3. Observe:
   - `token.balance(pool_address)` increased by `amount`;
   - `pool.get_reserves(hub_asset)` / stored `state.cash` did not increase;
   - `pool.get_revenue(hub_asset)` did not increase.
4. Attempt the reachable exits:
   - `Controller::withdraw` can only withdraw share-backed principal and is limited by `cache.cash`;
   - `Controller::claim_revenue` only pays claimable revenue;
   - `Controller::recapitalize` does not scan the existing physical balance and only credits/refunds its newly declared input.
5. The transferred `amount` remains in the pool balance but belongs to no accounting bucket, so it is permanently stranded.
