### Title
Cross-repository status-webhook confusion enables unauthorized merge via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by SHA — `Commit.where(sha: params.sha)` — with no constraint tying the webhook's `repository` field to the commit's owning stack/repository, unlike every other handler in this engine (`PushHandler`, `PullRequest::*Handler`) which explicitly scope through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. Because commits are only unique per `(sha, stack_id)` [1](#0-0) , and not globally unique, a status event that is validly signed for the attacker's own repository/organization can flip the CI status of a `Commit` row belonging to a completely different stack/repository whenever the SHA happens to coincide — the common case for a PR opened from a fork, where the head commit exists byte-for-byte (and hash-for-hash) in both the fork (attacker-owned) and the upstream (victim) repository.

### Finding Description
The broken binding, stated explicitly: `merge_request.stack.repository.full_name == status_webhook_payload['repository']['full_name']` is **never checked**. The equality that should gate the SHA lookup does not exist in `StatusHandler`.

Path:
1. `WebhooksController#verify_signature` selects the HMAC secret using `repository_owner` taken from the incoming payload (`params.dig('repository','owner','login')`) [2](#0-1) . This only proves the payload was signed for *some* org/app registered with Shipit — it says nothing about which commit/stack the event is allowed to affect.
2. `StatusHandler` params schema requires only `sha`, `state`, and optional CI metadata — notably it never requires/reads a `repository` field, unlike `PushHandler` and the `PullRequest::*` handlers which all require `repository.full_name` and resolve `Repository.from_github_repo_name(...)` before touching any stack-scoped data [3](#0-2)  vs [4](#0-3) .
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped, cross-tenant SHA lookup [5](#0-4) .
4. `Commit#create_status_from_github!` → `add_status` creates the `Status` row and, on a `pending`/`success` transition, calls `stack.schedule_merges`, enqueuing `ProcessMergeRequestsJob` for **the victim's stack** [6](#0-5) [7](#0-6) .
5. `ProcessMergeRequestsJob#perform` then checks `merge_request.all_status_checks_passed?`, which reads `head.statuses_and_check_runs` — i.e. exactly the `Status` row the attacker just wrote via the forged-repository event — and calls `merge_request.merge!` if satisfied [8](#0-7) [9](#0-8) .

Existing guards fail because:
- `verify_signature` authenticates the *organization* of the payload, not the relationship between that organization/repo and the specific `Commit`/`Stack` being mutated.
- `ExplicitParameters` schema for `StatusHandler` performs no validation against `repository`.
- No model-level uniqueness or foreign-key constraint prevents identical SHAs from existing in unrelated stacks — that's expected git behavior for forked commits, and the commits table is intentionally keyed on `(sha, stack_id)`, allowing exactly this collision.

Attacker's exact action: own (or control) a GitHub repository/fork that is any repository configured to deliver webhooks into this Shipit instance (this can be an unrelated, low-value repo the attacker fully controls, and does not require write access to the victim repo). Open a PR against the victim from that fork (a normal, unprivileged action) so the PR's head commit SHA is identical in both repos. Then cause a `status` event with `state: success` to be emitted for that SHA on the attacker's own repo (e.g., by having their own CI, or any integration they control, post a commit status) — GitHub signs and delivers this event legitimately using the attacker-repo's registered secret. `StatusHandler` applies the resulting `Status` to every `Commit` row sharing that SHA, including the victim's, unblocking `all_status_checks_passed?` and causing `ProcessMergeRequestsJob` to merge the PR.

### Impact Explanation
This allows a payload signed for repository/organization A to mutate a `Commit`/`Status`/merge state belonging to stack/repository B, directly matching the specified Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." The immediate consequence is `MergeRequest#merge!` being invoked on the victim repository, merging attacker-influenced code without any check from the victim's actual CI. The attack is repeatable against any victim stack for which the attacker can get a PR's head SHA to coincide with a commit visible in a repository they control (trivially true for the standard "fork and open PR" GitHub flow), so the blast radius spans every Shipit-managed repository that accepts pull requests from forks and uses the merge queue.

### Likelihood Explanation
Preconditions: victim stack has merge queue enabled with a pending `MergeRequest` awaiting CI (a normal, common configuration per the merge-queue docs) [10](#0-9) ; the PR is from a fork (standard open-source contribution flow) so its head commit exists verbatim in the attacker's own repo. Attacker cost is low: no Shipit credentials, no GitHub App keys, no `api_clients_secret` are required — only the ability to open a PR (unprivileged) and to cause a status event on a repo they own (e.g., attach any CI/webhook emitter to their fork). This is fully repeatable and requires no race condition or timing luck beyond normal async job processing.

### Recommendation
`StatusHandler` must resolve commits scoped to the repository named in the payload, mirroring `PushHandler`/`PullRequest::*Handler`: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `commit.stack.repository_id == repository.id` (e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extend `webhooks_controller_test.rb`):
```ruby
test "status event for repo A cannot flip commit status belonging to stack of repo B" do
  victim_stack = shipit_stacks(:shipit)                  # repository: 'shopify/shipit-engine'
  attacker_repo_full_name = 'attacker/evil-fork'

  shared_sha = 'deadbeef' * 5

  # same physical commit SHA exists in the victim stack (this is the PR head under review)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = shipit_merge_requests(:some_pending) # merge_status: 'pending', head: victim_commit

  refute merge_request.all_status_checks_passed?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }

  # signature verification stubbed to simulate a genuinely signed event for the attacker's own org
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true)

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: payload.to_json, as: :json,
         headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => 'sha1=whatever' }
  end

  refute merge_request.reload.all_status_checks_passed?
  # binding checked on both sides:
  assert_not_equal victim_stack.repository.full_name, attacker_repo_full_name
end
```
Before the fix this test fails: `victim_commit.statuses.count` increases and `all_status_checks_passed?` becomes true purely from the attacker-repo event, and `ProcessMergeRequestsJob` would proceed to call `merge_request.merge!` on the victim stack.

      end

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

        stack.schedule_merges if new_status.pending? || new_status.success?
      end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

<h3 id="merge-queue">Merge Queue</h3>

The merge queue allows developers to register pull requests which will be merged by Shipit once the stack is clear (no lock, no failing CI, no backlog). It can be enabled on a per stack basis via the settings page.

It can be customized via several `shipit.yml` properties:

**<code>merge.revalidate_after</code>** a duration after which pull requests that couldn't be merged are rejected from the queue. Defaults to unlimited.

For example:
```yml
merge:
  revalidate_after: 12m30s
```

**<code>merge.require</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) that you want Shipit to consider as failing if they aren't present on the pull request. Defaults to `ci.require` if present, or empty otherwise.

For example:
```yml
merge:
  require:
    - continuous-integration/travis-ci/push
```
