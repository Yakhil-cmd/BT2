### Title
Cross-tenant CI status forgery via webhook — signature verified against org derived from one payload field while state-mutating handlers key off unrelated fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository_owner`, a value read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the *unverified* JSON body. [1](#0-0) [2](#0-1)  Once the signature check passes, the actual event handlers act on a *different* payload field. `StatusHandler`, in particular, never scopes by repository/org/stack at all — it looks up commits globally by SHA and writes the attacker-supplied CI state directly onto them. [3](#0-2)  The binding "organization whose secret authenticated the request" is never checked against "repository/stack actually mutated," which is exactly the deployment-trust binding break called out in scope.

### Finding Description
Shipit supports multiple GitHub organizations configured independently, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, which configures `somegithuborg` and `someothergithuborg` separately). [4](#0-3)  All organizations share the single public `/github/webhooks` endpoint.

`verify_signature` picks which org's secret to use for HMAC verification from a field inside the same untrusted payload it is about to verify:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
``` [1](#0-0) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Additionally, in `lib/shipit/github_app.rb`, if an org has no `webhook_secret` configured, verification is a no-op: `return true unless webhook_secret`. [5](#0-4) 

Downstream, once "verified," the generic `Handler` base class resolves the target repository/stack from a **different** field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Nothing enforces that `repository.owner.login` (used to select the signing org) matches the owner encoded in `repository.full_name` (used to select the actual `Stack`/`Repository`).

Worse, `StatusHandler` does not even use the `stacks`/`repository_name` scoping at all — it writes the incoming, attacker-controlled `state`/`context`/`description` straight onto any `Commit` whose SHA matches, with no org/stack filter whatsoever:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This forged status is later trusted by the merge queue and deploy safety gates: `MergeRequest#all_status_checks_passed?`/`#any_status_checks_failed?`/`#any_status_checks_missing?` are computed from `head.statuses_and_check_runs`, i.e. exactly the rows written by `StatusHandler`. [7](#0-6)  A passing status set feeds directly into `ProcessMergeRequestsJob`, which will call `merge_request.merge!` once `all_status_checks_passed?` is true. [8](#0-7) 

The binding broken, expressed as the required equality: **org that authenticated the webhook (via `repository.owner.login`/`organization.login`) ≠ repository/commit actually written (via `repository.full_name` or bare `sha` lookup)**.

### Impact Explanation
An entity that can produce one valid webhook signature for *any* organization/repository tracked by the shared Shipit instance (e.g., an org with no `webhook_secret` configured, or one whose secret the attacker otherwise possesses through legitimate but low-privileged access to their own org's webhook settings) can forge a `status` event carrying an arbitrary `sha`. Because `StatusHandler` performs no ownership check, this forged "success" status is written onto any commit in the system that matches that SHA, regardless of which org/stack it belongs to. That directly feeds `MergeRequest#all_status_checks_passed?` and the deploy `ci.require`/`blocking_statuses` machinery used across the whole instance, enabling an **unauthorized merge or deploy** in a stack/repository the attacker has no legitimate relationship with. This matches the in-scope Critical impact class ("cross-repository writes ... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires only the ability to produce one valid signature for the shared `/github/webhooks` endpoint (trivial if any configured org has a blank `webhook_secret`, as the sample config shows is a supported/expected state) plus knowledge of a target commit SHA, which is public information on GitHub. No Shipit session, `ApiClient` token, or GitHub write access to the *target* repository is required — matching the "unprivileged attacker" bar. This is a design-level control-flow bug (verification field ≠ authorization/scoping field), not a theoretical or best-practice note.

### Recommendation
- Bind webhook signature verification and event routing to the *same* trusted field: after verifying the signature for the org derived from the request, re-derive/validate `repository.full_name`'s owner segment against that same org before dispatching to handlers, and reject mismatches.
- Make `StatusHandler` (and any other handler that currently skips `stacks` scoping) resolve and filter by `Repository.from_github_repo_name(repository_name)` exactly like other handlers, instead of a global `Commit.where(sha:)` lookup.
- Do not silently treat a missing `webhook_secret` as "always verified"; require an explicit, deliberate opt-out.

### Proof of Concept
1. Shipit instance tracks stacks for two different orgs, `orgA` and `orgB` (multi-tenant deployment, per the sample `secrets.*.yml` structure).
2. `orgA` has no `webhook_secret` configured (a documented/possible config state) — signature checks for any payload naming `orgA` as `repository.owner.login`/`organization.login` always pass.
3. Attacker (no Shipit account, no GitHub access to `orgB`) knows the SHA of a commit belonging to a pull request on `orgB`'s tracked repo (public info on GitHub).
4. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" } },
  "sha": "<target commit sha in orgB repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
5. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. [5](#0-4) 
6. `StatusHandler#process` finds the `Commit` in `orgB`'s stack by bare SHA match (no org/stack filter) and writes the forged `success` status. [3](#0-2) 
7. The next `ProcessMergeRequestsJob` run for `orgB`'s stack observes `all_status_checks_passed?` as true and merges/deploys the PR. [7](#0-6) [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
