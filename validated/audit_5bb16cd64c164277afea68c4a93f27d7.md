Confirmed: `Task#abort!` (`app/models/shipit/task.rb:356-371`) has no `env` parameter at all, and `RollbacksController#create` (`app/controllers/shipit/api/rollbacks_controller.rb:14-32`) computes `rollback_env = stack.filter_rollback_envs(params.env)` but only uses it in the immediate `deploy.trigger_rollback(...)` branch — when a task is already active, it calls `active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)`, silently discarding `rollback_env`. The deferred rollback is later triggered by `Deploy#trigger_revert_if_required` (`app/models/shipit/deploy.rb:301-310`), which reuses `env:` (i.e., `self.env`, the *original deploy's* stored, `deploy_variables`-filtered env) via `trigger_rollback`/`build_rollback` (`app/models/shipit/deploy.rb:90-117`), neither of which ever calls `filter_rollback_envs`. That filtered value is exactly what `TaskCommands#env` merges verbatim into the executed environment (`lib/shipit/task_commands.rb:33-48`, `.merge(@task.env)`).

### Title
Deferred rollback-on-abort executes with the original deploy's env instead of the caller-supplied, rollback-whitelist-filtered env - (File: app/controllers/shipit/api/rollbacks_controller.rb)

### Summary
When a rollback is requested while another task is active, `RollbacksController#create` validates and filters the caller's `env` parameter against `rollback_variables`, but that value is discarded, and the actual rollback later runs with the stale deploy's `deploy_variables`-filtered env instead.

### Finding Description
`app/models/shipit/deploy_spec.rb:174-180` defines two independent whitelists: `filter_deploy_envs` (checked against `deploy_variables`) and `filter_rollback_envs` (checked against `rollback_variables`), which the README documents as separately configurable. `RollbacksController#create` correctly computes `rollback_env = stack.filter_rollback_envs(params.env)` [1](#0-0)  but only passes it through when there is no active task: `response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)` [2](#0-1) . When a task is already active, the controller instead calls `active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)` [3](#0-2) , and `rollback_env` is never used again. `Task#abort!` has no `env` parameter to carry it [4](#0-3) .

When the aborted deploy transitions to `aborted`, `Deploy#trigger_revert_if_required` fires and calls `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)`, where `env:` resolves to `self.env` — the original deploy's own stored env — not the caller's rollback request env [5](#0-4) . `trigger_rollback`/`build_rollback` build the `Rollback` record directly from that value with `env: env.to_h`, never invoking `filter_rollback_envs` [6](#0-5) . That env is exactly what gets merged into the process environment at execution time by `TaskCommands#env` (`.merge(@task.env)`) [7](#0-6) .

The binding broken: **env key permitted (verified against `rollback_variables` for this specific rollback request) ≠ env key spawned (the previously-approved `deploy_variables` env of an unrelated, earlier deploy)**. This mirrors the report's root-cause pattern — a value is checked/computed at one point (`filter_rollback_envs(params.env)`), but a stale/different value ends up actually driving execution because the checked value is dropped along an alternate control-flow branch.

### Impact Explanation
`deploy_variables` and `rollback_variables` are intentionally distinct whitelists (`app/models/shipit/deploy_spec.rb:142-149`) so that operators can permit certain variables only for forward deploys (e.g., feature flags, seeding options) while deliberately excluding them — or including different, more dangerous ones — from rollback context. This bug causes a rollback to execute using an entirely different, previously-committed env blob that was never checked against the rollback-specific whitelist for this rollback request, and simultaneously silently drops the caller's explicit rollback intent. This can result in a rollback step running with environment values that operators specifically intended to keep out of rollback execution (or vice-versa, missing values the operator expected to be present), i.e., an execution that is not authorized under the rollback-specific policy despite being nominally triggered by a `deploy:stack`-permitted actor. This is best characterized as an unauthorized rollback configuration.

### Likelihood Explanation
Any actor holding `deploy:stack` permission (a standard, non-admin API/session permission already required to trigger deploys/rollbacks) can reach this path simply by triggering a rollback via the API while a deploy/task is still active — a very ordinary operational sequence (deploy, then rollback before it finishes). No special privileges beyond the ones already required for rollbacks are needed, and no race condition or timing precision is required.

### Recommendation
Persist the filtered rollback env alongside `rollback_once_aborted_to`/`rollback_once_aborted` on `abort!` (e.g., a `rollback_once_aborted_env` column or transient state), and have `trigger_revert_if_required` use that filtered value — re-validated through `filter_rollback_envs` — instead of reusing the original deploy's own `env` attribute.

### Proof of Concept
1. Configure `shipit.yml` with distinct `deploy.variables` and `rollback.variables` lists (e.g., deploy permits `RISKY_FLAG`, rollback does not).
2. As a user/API client with `deploy:stack` permission, trigger a deploy with `env: { RISKY_FLAG: 1 }` (passes `filter_deploy_envs`), let it start running.
3. While it is still active, call the rollback API (`POST .../rollbacks`) with `sha` of a prior successful deploy and `env: {}` (or any rollback-legal env) — this hits the `stack.active_task?` branch in `app/controllers/shipit/api/rollbacks_controller.rb:23-26`.
4. Observe that `active_task.abort!` is called without any env, and the caller's `rollback_env` (correctly filtered per `rollback_variables`) is discarded.
5. Once the aborted deploy transitions to `aborted`, `trigger_revert_if_required` (`app/models/shipit/deploy.rb:301-310`) creates the rollback using the aborted deploy's own `env` (`{ RISKY_FLAG: 1 }`), never passing it through `filter_rollback_envs`.
6. Inspect `Shipit::Task.last.env` (the resulting `Rollback`) and confirm it contains `RISKY_FLAG`, which is not present in `rollback_variables` and would be rejected with `Variables RISKY_FLAG have not been whitelisted` if submitted directly through `RollbacksController#create`'s non-active-task path.
