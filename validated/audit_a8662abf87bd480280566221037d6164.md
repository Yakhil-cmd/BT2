### Title
Webhook Signature Scoped to Wrong Payload Field Allows Cross-Organization Stack Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, extracted from the untrusted JSON body itself (`payload.dig('repository', 'owner', 'login')` or the `organization.login` fallback). Once the signature check passes, the event is dispatched to a handler (`Shipit::Webhooks::Handlers::Handler`) that resolves the target `Stack`/`Repository` using a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so a party who legitimately controls the `webhook_secret` for one configured GitHub organization can forge a payload whose `repository.owner.login` matches their own org (so it authenticates) while `repository.full_name` names a stack that belongs to a completely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
- Signature verification: `app/controllers/shipit/webhooks_controller.rb` [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the app/secret entry keyed by the org login taken straight from the request body, then `verify_webhook_signature` HMACs the *entire* raw body with that org's secret: [3](#0-2) 

- Handler resolution: `app/models/shipit/webhooks/handlers/handler.rb` resolves the affected `Stack` using `repository.full_name`, a field that is never checked against `repository_owner`: [4](#0-3) 

- `PushHandler#process` then performs a write-triggering action (`stack.sync_github`) against whatever stack matches that attacker-controlled `full_name`: [5](#0-4) 

Deployment configurations such as `test/dummy/config/secrets_double_github_app.yml` show Shipit explicitly supporting multiple independently-configured GitHub organizations (`OrgOne`, `OrgTwo`) in a single instance, each with its own `webhook_secret`: [6](#0-5) 

The trust binding that should hold is: `organization whose webhook_secret authenticated the request == organization that owns the repository being acted upon`. Because the field used to select the verification key (`repository.owner.login`) and the field used to select the target repository/stack (`repository.full_name`) are independently attacker-controlled inside the same signed JSON body, this equality is not enforced anywhere in the code path — only the raw bytes are verified, not any semantic relationship between the two fields.

### Impact Explanation
In a Shipit instance configured with more than one GitHub organization (a documented, supported configuration), an actor who legitimately holds the `webhook_secret` for *their own* configured organization (e.g. by being that org's GitHub App administrator, which is unprivileged with respect to any other tenant/org on the same Shipit instance) can craft and sign a webhook payload where `repository.owner.login` is their own org (so `verify_webhook_signature` succeeds) but `repository.full_name` names a repository/stack belonging to a different tenant organization tracked by the same Shipit deployment. This lets them drive write-triggering webhook handling (e.g. `PushHandler` invoking `Stack#sync_github`) against a repository/stack outside their authorization boundary — a cross-repository write that breaks the organization-authenticated vs. repository-written binding explicitly called out as in-scope.

### Likelihood Explanation
Exploitation only requires knowledge of a valid `webhook_secret` for any one organization configured in the shared Shipit instance and the ability to POST to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub repository write access is needed. Since `webhooks_controller_test.rb` and the code confirm the owner-login lookup and the `full_name`-based stack resolution are independent, forging such a cross-tenant payload is straightforward once one org's secret is known.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` and verifying the signature, re-validate that `payload.dig('repository', 'full_name')` (and any other repository/org identifiers used later by handlers) is actually owned by that same verified organization before dispatching to handlers — i.e., assert `full_name.split('/').first == repository_owner` (case-insensitively) or resolve the target repository strictly from the verified org's known repository list rather than trusting the raw payload field again.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (attacker-controlled, webhook secret known to attacker) and `OrgTwo` (victim, tracks a `Stack` for `orgtwo/victim-repo`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgOne" },
       "full_name": "orgtwo/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgOne_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` and the signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgtwo/victim-repo")` and invokes `stack.sync_github(expected_head_sha: params.after)` on the victim org's stack, despite the request having only ever been authenticated against `OrgOne`'s secret. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
