### Title
Operator-precedence bug in `ReopenedHandler#unarchive?` lets a labeled PR unarchive/create a review stack even when `review_stacks_enabled == false` - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` intends to gate all provisioning behaviors behind `repository.review_stacks_enabled`, but Ruby operator precedence causes `&&` to bind only to the `allow_all?` clause, leaving the `allow_with_label?` and `prevent_with_label?` branches unguarded by `review_stacks_enabled`. As a result, an attacker who closes/reopens a labeled PR on a repository configured with `provisioning_behavior: :allow_with_label` gets a review stack created/unarchived and queued for provisioning even though the repository owner explicitly disabled review stacks (`review_stacks_enabled: false`).

### Finding Description
The intended binding is `repository.review_stacks_enabled == true` is required for *any* provisioning/unarchive action to occur. The actual code in `unarchive?`: [1](#0-0) 
is parsed by Ruby as:
```
(review_stacks_enabled && provisioning_behavior_allow_all?) ||
(provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
because `&&` has higher precedence than `||`. So when `review_stacks_enabled == false`, `provisioning_behavior_allow_with_label? == true`, and the PR carries the provisioning label, the second clause evaluates to `true` independent of `review_stacks_enabled`, and `unarchive?` returns `true`.

The identical pattern exists in `OpenedHandler#provision?`: [2](#0-1) 

Call path: `ReopenedHandler#process` → `respond_to_pull_request_reopened?` (checks `params.action == "reopened"`) → `unarchive?` (bugged) → `stack.unarchive!` on the `ReviewStackAdapter`: [3](#0-2) 
If no stack exists yet, `unarchive!` falls back to `create!`, which creates the `ReviewStack` record and immediately enqueues it: [4](#0-3) 
`ReviewStackProvisioningQueue.add` sets `awaiting_provision: true` on the stack: [5](#0-4) 
The queue worker (invoked periodically, e.g. via `lib/tasks/cron.rake`) later calls `stack.provision`, which drives task/command execution for the repository's provisioning steps.

Attacker request: attacker owns/controls a repository whose Shipit-side configuration has `provisioning_behavior: allow_with_label` (repository-level Shipit setting, not something the PR author controls) but `review_stacks_enabled: false`; attacker opens a PR, adds the provisioning label to it, closes it, then reopens it — sending the webhook payload with `action: "reopened"`. No Shipit session, API token, or webhook secret is needed beyond a validly signed webhook (which GitHub sends for the attacker's own repo events); `verify_signature`/`GitHubApp#verify_webhook_signature` do not protect against this because the request is a legitimate, correctly-signed webhook from GitHub for a repo the attacker owns.

Existing guards do not catch this: `verify_signature` only checks the webhook came from GitHub for that repo (it does, since attacker owns the repo triggering it); `ExplicitParameters` schema validates payload shape, not authorization logic; no other check re-verifies `review_stacks_enabled` before calling `unarchive!`/`create!`.

### Impact Explanation
On any repository configured with `provisioning_behavior: allow_with_label` (a legitimate, common configuration for opt-in review stacks) but with `review_stacks_enabled: false` (i.e., review stacks explicitly turned off at the top level), an attacker who owns/controls that repository (or any repository sharing this configuration) can force the creation and provisioning of a review stack for an arbitrary PR branch by simply labeling and reopening it. This causes the stack's configured provisioning steps to execute against the attacker's branch/environment — matching the Critical impact category of "RCE on the deploy host via `Command`/`PTY.spawn`" once the queue worker processes the stack, since provisioning ultimately runs task steps through the same `Command`/`PTY.spawn` execution path as regular deploys. The blast radius is scoped to repositories with this specific configuration combination, but it is fully repeatable (close/reopen again) and bypasses an explicit administrative safety switch (`review_stacks_enabled`).

### Likelihood Explanation
Preconditions required: repository must have `provisioning_behavior_allow_with_label?` (or `prevent_with_label?`) set while `review_stacks_enabled` is `false`. This is a plausible, low-cost misconfiguration/transition state (e.g., an operator disabling review stacks globally without also resetting `provisioning_behavior`), not a wildly exotic setup. The attacker cost is trivial: label + close + reopen a PR on a repository they control. It is fully repeatable and does not require any secret material.

### Recommendation
Fix operator precedence in both `unarchive?` (`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`) and `provision?` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`), and likely the analogous logic in `labeled_handler.rb`/`unlabeled_handler.rb`, by explicitly parenthesizing so `review_stacks_enabled` gates the entire expression:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style:
1. Create a `Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`.
2. Build `payload_parsed(:pull_request_reopened)` with `action: "reopened"` and `pull_request.labels` including the repository's `provisioning_label_name`.
3. Assert before: `repository.review_stacks_enabled == false` and no `ReviewStack` exists for the PR's environment.
4. POST the payload to `/webhooks`.
5. Assert after: a `Shipit::ReviewStack` now exists (or was unarchived) for `environment: "pr#{number}"`, and `stack.awaiting_provision?` (or equivalent enqueued state) is `true` — demonstrating provisioning proceeded despite `review_stacks_enabled == false`, i.e., the claimed binding `repository.review_stacks_enabled == true` required for provisioning is violated.
