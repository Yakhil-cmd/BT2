### Title
Cross-organization/cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies a GitHub `status` webhook to **every** `Commit` record in the entire Shipit installation that shares the given `sha`, without restricting the update to the repository/organization that the webhook signature actually authenticated for. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects the `GitHub App`/`webhook_secret` to check the HMAC signature based on `repository.owner.login` (or `organization.login`) taken from the payload, and only proves that *some* org's secret matches the *whole* raw body: [1](#0-0) 

Once the signature is accepted, the controller dispatches the parsed JSON to the registered handler for the event, with no further scoping to the repository that owns the webhook: [2](#0-1) 

`StatusHandler#process`, however, ignores the repository entirely (its `params` schema doesn't even require a `repository` field) and matches purely by commit SHA across the whole database: [3](#0-2) 

`Commit#create_status_from_github!` then unconditionally records the new status on whichever `Commit` row matched, regardless of which `Stack`/`Repository` it belongs to: [4](#0-3) 

This means the "identity" that was verified (the organization tied to the webhook_secret) is not the same entity ("commit sha", not scoped by repository) that the write actually targets. Any organization/repository legitimately installed on the same Shipit instance can send a valid, signed `status` event containing an arbitrary `sha` value and `state: "success"` (or `failure`), and Shipit will apply that status to **any** commit row anywhere in the database that happens to have that SHA — including commits belonging to a completely different organization's stack. Because git commit SHAs are content-addressed and repositories are frequently forked/shared (identical commit histories, cherry-picks, or simply guessable/observable SHAs from public repos), an attacker controlling one onboarded organization can forge CI status for commits in another organization's stack that is hosted on the same Shipit instance.

`CheckSuiteHandler` correctly scopes lookups by `stacks.where(branch: ...)` combined with a `sha` match, limiting the blast radius, but `StatusHandler` has no equivalent scoping: [5](#0-4) 

### Impact Explanation
A forged "success" status is consumed directly by `MergeRequest`'s CI-gating logic (`all_status_checks_passed?`, `any_status_checks_missing?`, `any_status_checks_failed?`), which drive `merge!` and therefore an unattended, unauthorized merge/deploy of a pull request whose CI never actually passed: [6](#0-5) [7](#0-6) 

It also feeds `Commit#deployable?` and the continuous-deployment trigger, so a forged status can also trigger an unauthorized automatic deploy for a stack the attacker's organization has no legitimate write access to: [8](#0-7) [9](#0-8) 

This matches the Critical bucket "unauthorized deploy, rollback, or merge" for a repository/organization other than the attacker's own, using only a webhook that the attacker's own (legitimately installed, unprivileged) organization is entitled to send.

### Likelihood Explanation
Exploitability depends on the presence of a colliding commit SHA between the attacker's repository and the victim's repository within the same Shipit deployment. This is realistic in common scenarios: forks that share history with the upstream repo, mirrored/vendored repositories, or monorepo/multi-remote setups tracked by the same Shipit instance across multiple orgs. It requires no Shipit session, no `ApiClient` token, and no elevated GitHub permissions — only that the attacker's own organization/app installation is one of the tenants of the shared Shipit instance and is allowed to send `status` webhooks (which is standard, unprivileged behavior for any onboarded repo). This makes the likelihood moderate-to-high in any multi-tenant Shipit deployment.

### Recommendation
Scope the `StatusHandler` (and any other webhook handler that resolves records purely by `sha`) to the repository asserted in the payload, e.g. require and validate `repository.full_name`/`repository.owner.login` against the authenticated organization, and join through `stack.repository` when querying `Commit.where(sha: ...)`, mirroring the safer pattern already used by `CheckSuiteHandler`. At minimum, restrict the `Commit` lookup to commits belonging to stacks whose `Repository` matches the `repository` object in the verified payload.

### Proof of Concept
1. Organization A and Organization B are both legitimately installed on the same Shipit instance (each with their own GitHub App / `webhook_secret`), each owning a `Stack` for their respective repos.
2. Org B's repository is a fork of (or shares a commit with) Org A's repository, so a specific commit `SHA_X` exists in both `Stack` A's and `Stack` B's `commits` table (same `sha`, different `stack_id`).
3. The attacker, who controls Org B (an ordinary, unprivileged tenant), triggers a genuine GitHub `status` webhook from their own repo/CI (or by pushing a commit/status from a CI provider they control) targeting `SHA_X` with `state: "success"`. GitHub signs this with Org B's `webhook_secret`, which `WebhooksController#verify_signature` validates successfully.
4. `StatusHandler#process` executes `Commit.where(sha: SHA_X)`, which returns **both** the Org A and Org B commit rows, and calls `create_status_from_github!` on each — writing a fabricated "success" status onto Org A's commit as well.
5. Org A's `MergeRequest#all_status_checks_passed?`/`Commit#deployable?` now see a passing status for `SHA_X` that Org A's own CI never produced, enabling an unauthorized merge or continuous deployment on Org A's stack, triggered entirely by Org B's webhook.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
