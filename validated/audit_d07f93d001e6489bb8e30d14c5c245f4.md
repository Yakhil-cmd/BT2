### Title
Webhook signature check authenticates only the claimed organization, not the repository the payload actually writes to — allowing cross-repository status/commit forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects a GitHub App/HMAC secret using only `repository.owner.login` (or `organization.login`) pulled from the raw JSON body, and validates the signature against that value. Every webhook `Handler` then independently reads a *different* field, `repository.full_name`, to decide which `Repository`/`Stack`/`Commit` records to mutate. Nothing binds the org that was cryptographically authenticated to the repository that is actually written, so a party who legitimately owns/administers **any** GitHub organization configured in the same Shipit instance's multi-org `github:` config can forge a signature valid for their own org while pointing the payload at an entirely different (victim) organization's repository.

### Finding Description
- Signature check binds only to organization: `verify_signature` calls `Shipit.github(organization: repository_owner)` and `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 

- The base `Handler` resolves the target repository from a *different* payload field, `repository.full_name`, with no cross-check against the value used for signature verification: [3](#0-2) 

- `StatusHandler` goes further and doesn't even scope by repository at all — it looks up commits globally by SHA across the whole database and writes an attacker-supplied CI status onto them: [4](#0-3) 

Because Shipit supports hosting multiple GitHub organizations behind one instance (each with its own `webhook_secret` in `secrets.yml`), each onboarded organization's administrator legitimately knows their own org's `webhook_secret` — that is expected and not a privilege escalation by itself. The vulnerability is that this per-org secret is only used to authenticate "some request signed with org X's secret", never "a request specifically about org X's repositories". An attacker who administers Org A (their own, unprivileged in Shipit terms) can:
1. Compute a valid `X-Hub-Signature` using Org A's `webhook_secret` for an arbitrary crafted JSON body.
2. Set `repository.owner.login` = `"org-a"` (so `verify_signature` picks Org A's secret and passes).
3. Set `repository.full_name` (used by `Handler#stacks`) — or for `status` events, an arbitrary `sha` (used directly by `StatusHandler`, with no repository field consulted at all) — to target Org B's (the victim's) stack/commit.

This is exactly the same "binding never enforced between the field that was verified and the field that is acted upon" bug class as the report's NFT-delegation griefing: the check (`delegate[tokenId]` uniqueness / owner check) never covered the actual state mutated (the checkpoint array), letting an attacker corrupt someone else's state through a field that was never validated against the authorized one.

### Impact Explanation
This directly matches the Critical "cross-repository writes" impact bucket: an operator of one onboarded GitHub organization can forge commit statuses (`state`, `description`, `target_url`, `context`) for commits belonging to a **different** organization's stack, without ever presenting that victim organization's webhook secret. Since Shipit deploy gating and merge-queue safety checks rely on commit statuses (`Commit#create_status_from_github!`, used by CI-required-status logic elsewhere in the engine), this can be used to spoof a passing CI status on a victim's commit and help unblock/trigger an unauthorized deploy or merge queue advance for a stack the attacker has no legitimate access to. The `push`/`check_suite` handlers are similarly exposed via the `repository.full_name` mismatch, letting an attacker trigger `sync_github`/check-run refresh jobs against arbitrary victim stacks.

### Likelihood Explanation
Requires the attacker to control (administer) at least one GitHub organization already configured in the same multi-tenant Shipit instance — a realistic scenario for any shared/internal Shipit deployment serving several teams/orgs, none of which needs elevated Shipit privileges to exploit this. Crafting the JSON payload and HMAC signature is trivial once the attacker's own org secret is known (which they inherently have, as owners of that org's GitHub App installation).

### Recommendation
- In `WebhooksController#verify_signature`, after selecting the secret via `repository_owner`, also verify that `repository.full_name`'s owner segment matches `repository_owner` before proceeding, rejecting mismatched payloads.
- In `Shipit::Webhooks::Handlers::Handler`, thread the authenticated organization (not just raw payload data) into handlers, and have each handler assert the resolved `Repository`/`Stack`/`Commit` actually belongs to that authenticated organization.
- Fix `StatusHandler#process` to scope `Commit` lookups by the authenticated repository/stack rather than a bare global `sha` lookup.

### Proof of Concept
1. Shipit is configured with two GitHub orgs in `github:` — `org-a` (attacker-administered) and `org-b` (victim), each with its own App and `webhook_secret`.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha from org-b/repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's secret, verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in `org-b`'s stack regardless of the org used for the signature — and writes the forged status via `create_status_from_github!`, with no relation checked to `org-a`.
