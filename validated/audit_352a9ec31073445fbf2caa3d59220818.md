### Title
Webhook organization used for signature verification is decoupled from the repository/organization the payload actually mutates - forged cross-organization webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading an attacker-controlled field (`repository.owner.login`) from the *same* JSON body whose signature is being checked. The various webhook handlers, however, act on a different field of that body (`repository.full_name`, or for membership, `organization.login`) to decide which `Stack`/`Repository`/`Team` to mutate. In a multi-organization Shipit deployment (multiple GitHub Apps configured via `Shipit.github_organizations`/`github_app_config`, each with its own `webhook_secret`), this creates an equality break: **organization authenticated (signature-selection key) ≠ organization/repository actually written**.

### Finding Description
`Shipit.github(organization:)` supports per-organization configuration, each with its own `webhook_secret`: [1](#0-0) 

The webhook signature check picks the organization (and therefore the secret) to verify against using `repository_owner`, which is read straight out of the untrusted request body: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` then just HMAC-validates the *entire raw body* against that selected org's secret: [4](#0-3) 

Once the signature passes, event handlers determine which `Stack`/`Repository` to act on using a *different* field of the same body - `repository.full_name` - completely independent of the `repository.owner.login` field used for signature/org selection: [5](#0-4) [6](#0-5) 

Because the signature is computed over the raw body and the body's `repository.owner.login` and `repository.full_name` fields are independently attacker-controlled (this is a direct HTTP POST to the Shipit webhook endpoint, not a GitHub-authenticated channel), an attacker who knows/controls the `webhook_secret` for *any one* configured organization (e.g., an org they administer that is legitimately integrated with this Shipit instance) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` selects and successfully validates against a secret they know.
2. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`.
3. Sign the crafted raw body with their own known secret and POST it with the appropriate `X-Github-Event` header.

The signature check passes (it only proves the body was signed with *some* org's secret - not necessarily the org the body claims to describe), and the handler then acts on the victim repository/stack because it resolves the target via `repository.full_name`, not `repository.owner.login`.

This is exactly the deployment-trust binding described in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Using this mismatch, a low-privilege actor who only controls one legitimate, Shipit-integrated GitHub organization can forge webhook events targeting a completely unrelated organization/repository tracked by the same Shipit instance:
- Forged `push` events (`PushHandler`) enqueue `GithubSyncJob` for a victim `Stack` with an attacker-chosen `expected_head_sha`, forcing sync activity and status/commit book-keeping on a stack the attacker has no legitimate access to.
- Forged `status`/`check_suite` events can inject fabricated commit statuses/check-run refreshes for a victim commit, which downstream CI-gating logic (`ci.require`, deployability checks) may rely on to decide whether a deploy is "safe," directly corrupting the CI/deployability signal on which the operator's actual deploy decision (manual or continuous-deployment) is based.
- `pull_request` handlers (`opened_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`) resolve their target repository the same way (`params.repository.full_name`) and can be used to provision/archive/unarchive Review Stacks belonging to a victim repository.

This crosses a real trust boundary (forging events attributed to one organization's data while validated under another organization's credential) and can corrupt the state (commits, statuses, sync state, review-stack lifecycle) that feeds Shipit's deploy/rollback decisions for repositories the attacker does not own - satisfying the "cross-repository writes"/unauthorized-state-mutation class of impact this scan targets.

### Likelihood Explanation
This requires:
- The target Shipit instance to be configured for **multiple GitHub organizations** (the per-organization `github` config schema), each with a distinct `webhook_secret` - this is a documented, supported configuration (`Shipit.github_organizations`, `github_app_config`), not a hypothetical.
- The attacker to know (or be the administrator of) at least one of those organizations' `webhook_secret` values - plausible in a shared/multi-tenant Shipit deployment where different business units or partner orgs each own "their" GitHub App/webhook secret but share one Shipit instance covering many other orgs' repositories.

Given those preconditions, exploitation requires only crafting and POSTing a JSON body directly to `/webhooks` - no GitHub session, no privileged Shipit account, and no interaction with the victim organization at all.

### Recommendation
Bind the signature-verification key to the same trust anchor used by the handler, and never let the payload itself choose which secret validates it:
- Verify the signature against the organization derived from the *installation*/App context (e.g., iterate configured organizations' secrets, or use the GitHub App installation ID from the delivery), not from an attacker-suppliable field inside the unsigned-yet-verified payload.
- After verification, cross-check that `repository.full_name`'s owner matches the organization whose secret validated the signature (`repository.full_name.split('/').first == repository_owner`), rejecting the webhook if they diverge.
- Alternatively, if Shipit's threat model intends "any configured org's secret can attest to any payload," that should be an explicit, documented decision - but as implemented it silently allows cross-organization impersonation, which is inconsistent with the tenant-isolation implied by having per-organization secrets at all.

### Proof of Concept
Given a Shipit instance configured with two GitHub organizations, `attacker-org` (secret known to the attacker) and `victim-org` (repository `victim-org/victim-repo` tracked as a Shipit `Stack`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body below using attacker-org's webhook_secret>
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `WebhooksController#verify_signature` computes `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully validates the signature (the attacker signed it with that org's known secret). [2](#0-1) 
- `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository.full_name`, not `owner.login`) and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack. [5](#0-4) [7](#0-6) 

The same construction applies to `status`, `check_suite`, and `pull_request` handlers, all of which resolve their target via `repository.full_name` while the controller authenticates via `repository.owner.login`/`organization.login`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
