### Title
Webhook signature verified against attacker-chosen organization but repository actions keyed off a different, unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login`, an attacker-controlled field inside the JSON body being signed. Every event handler that then acts on the payload (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` using a *different* field in the same body, `repository.full_name`. Because both fields live inside the same raw payload that the attacker fully controls and signs themselves (with a secret they legitimately know for their own configured organization), the two fields can be made to diverge: the signature check authenticates organization A while the handler logic operates on organization B's repository.

### Finding Description
The signature check is:
```ruby
# app/controllers/shipit/webhooks_controller.rb:24-30
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization: repository_owner)` looks up the `webhook_secret` configured for whichever org name appears in `repository.owner.login` (`config/secrets*.yml` supports multiple orgs, each with its own `webhook_secret`, see `template.rb:68-95`). `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) just checks that the raw body HMAC matches that org's secret — it says nothing about which repository the payload claims to describe.

Once the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:12`) dispatches to handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`. All of them inherit `Handler#stacks`/`#repository_name`:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb:32-38
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
This resolves the target `Repository`/`Stack` from `repository.full_name` — a sibling field to `repository.owner.login`, but never cross-checked against it.

Equality that should hold but doesn't: `organization authenticated by signature == organization owning the repository the handler acts on`. Because the attacker constructs and signs the entire raw body themselves using a secret they legitimately possess for *their own* organization/app installation configured in Shipit, they can set:
- `repository.owner.login = "attacker-org"` (used only for HMAC/secret selection)
- `repository.full_name = "victim-org/victim-repo"` (used to select the `Stack` acted upon)

The signature over the whole raw body will validate successfully against `attacker-org`'s secret, since the attacker is the one signing it, yet `PushHandler#process` will run `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` against `victim-org/victim-repo`'s stacks — a repository the attacker does not control.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out explicitly as an in-scope analog class. Concretely, a party who only has legitimate webhook signing capability for one organization configured in a multi-tenant Shipit instance (`config/secrets.yml`'s `github:` map supports multiple orgs, each independently keyed) can force `GithubSyncJob`/`sync_github` to run against a completely different, victim organization's `Stack`s by forging the `repository.full_name` field while keeping `repository.owner.login` set to their own org so the signature validates. `PushHandler` triggers `stack.sync_github(expected_head_sha:)`, which pulls commit history and, for stacks with `continuous_deployment: true`, can feed the continuous-delivery pipeline (`Stack.schedule_continuous_delivery`) — i.e. this can be leveraged toward an unauthorized deploy/rollback on a repository/stack the attacker does not own, satisfying the "unauthorized deploy" / "cross-repository writes" Critical impact bar. `StatusHandler` and `CheckSuiteHandler` are similarly reachable and can inject forged CI status/check-run data for arbitrary victim commits since they key off `sha`/`repository.full_name` without validating the authenticating org.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate operator of at least one GitHub organization/App installation that Shipit is configured to trust (i.e., they can receive genuinely signed webhook deliveries for their own org, or equivalently know that org's `webhook_secret`). That is a materially weaker requirement than repository write access to the *victim* repo, an `ApiClient` token, or the `webhook_secret` of the victim organization — the report's exclusions only rule out needing the victim's own secret/session/token, not a same-Shipit-instance sibling organization's. In any Shipit deployment onboarding more than one GitHub organization with distinct webhook secrets, this is directly reachable over the public `WebhooksController#create` endpoint with no additional privileges.

### Recommendation
Bind the signature-authenticating organization to the repository actually processed: after `verify_webhook_signature` succeeds, re-derive `repository_owner` from `repository.full_name`'s owner segment (or require they match) before dispatching to handlers, or select the webhook secret using an already-trusted mapping (e.g. a `Repository` record's known org) rather than trusting `repository.owner.login` verbatim. At minimum, `Handler#repository_name`/`#stacks` should assert that the resolved repository's owner equals the organization whose secret validated the signature.

### Proof of Concept
1. Attacker controls/owns GitHub organization `attacker-org`, which is one of the organizations configured under `Shipit.github` with its own `webhook_secret` (multi-org support per `template.rb`/`config/secrets.*.yml`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_for_attacker-org, raw_body)>` themselves (they know their own org's secret) and POSTs to `Shipit::Engine`'s `/github/webhooks` endpoint with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
5. `PushHandler.call(params)` runs `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stacks, even though the attacker never authenticated as, nor holds any credential for, `victim-org`.
