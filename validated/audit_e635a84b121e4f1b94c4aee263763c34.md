### Title
Cross-organization webhook forgery via mismatched signature-key/target-repository binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the webhook secret used to verify the HMAC signature from one JSON field (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually act on the payload (create/sync stacks, archive/unarchive review stacks, add team memberships, etc.) select the target repository/organization from a *different*, independently-attacker-controlled field: `repository.full_name`. Because Shipit is designed to host multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately knows (or controls) the webhook secret for **one** configured organization can forge a signed payload whose `repository.owner.login` matches that organization (so the signature check passes) but whose `repository.full_name` names a repository belonging to a **different** configured organization, causing Shipit to act on that other organization's stacks.

### Finding Description
`verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret` used for HMAC verification) using only the owner/organization login found in the payload: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` simply recomputes an HMAC over the raw body with whichever secret was resolved and compares it to the signature header — it has no notion of which repository the payload claims to affect: [4](#0-3) 

Once the signature is accepted, every event handler independently derives the repository/stack to act on from `payload.dig('repository', 'full_name')`, a field that is never cross-checked against `repository.owner.login` or against which organization's secret was actually used to authenticate the request: [5](#0-4) 

For example, `PushHandler` finds stacks purely from `repository_name` (i.e. `full_name`) and triggers a GitHub sync for them: [6](#0-5) 

The pull-request handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`) likewise resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then provision, archive, or unarchive review stacks for that repository — again independent of which org's secret validated the request: [7](#0-6) [8](#0-7) 

**The broken equality:** the engine implicitly assumes `organization_that_authenticated == organization_that_owns_the_written_repository`, but nothing enforces `repository.owner.login == repository.full_name.split('/').first`, nor that the org resolved for signature verification matches the org actually mutated by the handler.

**Attack sequence:**
1. Shipit is configured (as documented/supported) with multiple GitHub organizations, e.g. `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret` [1](#0-0) .
2. An attacker who administers (or otherwise knows the `webhook_secret` of) `OrgOne`'s GitHub App crafts a POST to `/webhooks` (or wherever `WebhooksController` is mounted) with `X-Github-Event: push`, body containing `"repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgTwo/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"`.
3. The attacker signs the raw body with `OrgOne`'s `webhook_secret` and sets `X-Hub-Signature` accordingly.
4. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`) and successfully verifies the signature against `OrgOne`'s secret.
5. `PushHandler` (or the PR handlers) then resolve the target stack from `repository.full_name = "OrgTwo/victim-repo"`, letting the attacker trigger a forged GitHub sync, or archive/unarchive/provision a review stack, for a repository belonging to an organization whose secret they never had.

### Impact Explanation
This breaks the intended boundary that an organization's webhook can only affect its own repositories. It enables cross-organization writes to stack state (forged sync target SHAs, spurious review-stack provisioning/archival) on a multi-tenant Shipit deployment, without possessing the victim organization's webhook secret, GitHub App key, or any Shipit session/API token — matching the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires: (a) Shipit configured with more than one GitHub organization (a supported, documented configuration [9](#0-8) ), and (b) the attacker controlling/knowing the `webhook_secret` for at least one of those organizations (e.g., an organization admin of one tenant attacking another tenant on the same Shipit instance). No Shipit session, repository write access, or private key is needed — only a webhook secret for any one configured org, which is a materially lower privilege bar than the excluded conditions in scope.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, enforce that the organization used to select the webhook secret is the same organization that owns the repository the handler subsequently acts on — e.g., derive `repository_owner` from `repository.full_name.split('/').first` (or validate `repository.owner.login == full_name.split('/').first`) before verification, and have handlers reject payloads where these disagree.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, body)>
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
`verify_signature` validates the signature using `OrgOne`'s secret (via `repository.owner.login`); `PushHandler` then resolves and acts on `OrgTwo/victim-repo` via `repository.full_name`, crossing the organization boundary [2](#0-1) [5](#0-4) [6](#0-5) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
