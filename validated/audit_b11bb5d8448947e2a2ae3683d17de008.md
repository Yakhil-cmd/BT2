### Title
Front-runnable permissionless `Currency<T>` registration permanently squats a coin's `CoinRegistry` entry via unguarded `derived_object::claim` - (File: `crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move`)

### Summary
`sui::coin_registry::new_currency<T>` is a **permissionless** function that computes a deterministic derived address for a coin type's `Currency<T>` object (via `sui::derived_object::claim`) and creates it if not already claimed. Like `LamboFactory.createLaunchPad` → `UniswapV2Factory.createPair`, the address/slot for a given key (`CurrencyKey<T>`) is fully predictable ahead of time and the creation function contains no restriction tying the caller to the legitimate owner/module of `T`. An unprivileged actor can pre-claim the registry slot for any coin type `T`, permanently blocking the real project from ever registering accurate `Currency<T>` metadata for that type.

### Finding Description
`derived_object::claim` (crates/sui-framework/packages/sui-framework/sources/derived_object.move:38-44) computes a deterministic address from `(parent UID, key)`, asserts it hasn't been claimed, and marks it claimed — this is the Sui-native analog of Uniswap's deterministic `create2`-style pair address plus its `PAIR_EXISTS` guard. [1](#0-0) 

`coin_registry::new_currency<T>` uses this primitive with no OTW/witness/package check on `T`: [2](#0-1) 

The doc comment states intent ("This can be called from the module that defines `T` any time after it has been published") but the signature only bounds `T: key` — it does not require an OTW (`is_one_time_witness`), a `Publisher` proof, or any value of type `T`/its module address. In Sui, a caller can invoke a generic public entrypoint with **any** type argument that satisfies the ability bound, regardless of which package published it. This is exactly the "deterministic address, permissionless creation, no identity binding" pattern that caused the LamboFactory front-running DoS: the slot (`CurrencyKey<T>` under the singleton `CoinRegistry` at `0xc`) can be claimed by anyone before the legitimate `T`-defining team calls it, and — per the framework's own documentation — derived objects currently have **no reclaim mechanism** ("Supports reclaiming? ❌ Currently no"). [3](#0-2) 

Once claimed, `registry.exists<T>()` (backed by `derived_object::exists`) will return `true` forever for that `T`, and every subsequent legitimate path (`new_currency`, `new_currency_with_otw`/`finalize_registration`, `migrate_legacy_metadata`) asserts `!registry.exists<T>()` and aborts: [4](#0-3) [5](#0-4) 

The framework's own security-review skill notes for exactly this class explicitly flag it: "predictable derived address can be pre-funded/squatted before the object exists" / "front-run object creation." [6](#0-5) 

### Impact Explanation
If exploitable against a real project's coin type `T`, an attacker can permanently and irreversibly occupy the singleton `CoinRegistry`'s canonical metadata entry for that coin with attacker-chosen `name`/`symbol`/`description`/`icon_url` (impersonation/scam risk), and permanently deny the legitimate issuer the ability to ever register accurate on-chain metadata for their coin (the system-wide `CoinRegistry` at `0xc` is meant to be the canonical, trusted metadata source going forward). This is a permanent, unfixable harmful outcome for the affected coin's canonical registry state, matching the "harmful smart-contract behavior" / permanent-DoS bar.

### Likelihood Explanation
Exploitability hinges on whether real-world coin witness types actually satisfy the `T: key` bound on `new_currency`. Conventional Sui coin patterns (`Coin<T>` via `coin::create_currency`/OTW) use a witness type `T` with only the `drop` ability, not `key` — I could not fully verify within the available index whether `new_currency<T: key>` is the primary/expected path for standard fungible coins or a narrower path for object-backed currencies. This materially affects likelihood: if most coins cannot satisfy `T: key`, the attack surface shrinks to a niche subset of currency types. I was not able to find an additional restriction (module-address check, `Publisher` capability, or OTW requirement) in the portion of the file reviewed, and the doc comment ("internal") suggests an intended-but-unenforced restriction, which is the classic root cause of this bug class. This uncertainty should be resolved by inspecting the full file (particularly any macro/internal helper gating `new_currency`) before treating this as confirmed-High.

### Recommendation
- Require proof of authority to register `T` as a currency: gate `new_currency<T>` behind an OTW check (`sui::types::is_one_time_witness`) as `new_currency_with_otw` already does, or require a `Publisher` object matching `T`'s package address.
- Alternatively, follow the Code4rena judge's guidance from the source report: keep the deterministic-claim design, but never let an unauthenticated claim block the legitimate owner — e.g., allow the true `T`-module to reclaim/overwrite a registry entry that was not created via the authorized path, or restrict `CurrencyKey<T>` claims so only a call originating from `T`'s defining module/package can succeed.

### Proof of Concept
1. Attacker observes an unpublished/soon-to-launch coin's expected type tag `0xABC::mycoin::MYCOIN` (many teams announce package addresses/module names before mainnet launch, or the attacker front-runs the publish transaction in the same or next block once the type exists).
2. Before the legitimate team calls `coin_registry::new_currency<MYCOIN>` (or the OTW path), attacker submits a PTB calling `coin_registry::new_currency<0xABC::mycoin::MYCOIN>(registry, ..., ctx)` with attacker-chosen decimals/symbol/name/description/icon_url (assuming `MYCOIN` satisfies the `key` ability bound).
3. `derived_object::claim(&mut registry.id, CurrencyKey<MYCOIN>())` succeeds and marks the derived slot `Claimed` permanently.
4. When the legitimate team later calls any of `new_currency`, `new_currency_with_otw`/`finalize_registration`, or `migrate_legacy_metadata` for `MYCOIN`, `assert!(!registry.exists<T>())` fails and the transaction reverts every time — the canonical `Currency<MYCOIN>` object now permanently holds the attacker's data with no reclaim path.

**Confidence caveat:** I could not conclusively verify from the indexed code whether typical coin witness types can satisfy `T: key`, nor rule out an unseen internal gate on `new_currency`; a Devin session with full repository access should confirm this before treating the finding as fully proven.

/// Claim a deterministic UID, using the parent's UID & any key.
public fun claim<K: copy + drop + store>(parent: &mut UID, key: K): UID {
    let addr = derive_address(parent.to_inner(), key);
    let id = addr.to_id();
    assert!(!df::exists(parent, Claimed(id)), EObjectAlreadyExists);
    df::add(parent, Claimed(id), ClaimedStatus::Reserved);
    object::new_uid_from_hash(addr)
}

public fun new_currency<T: /* internal */ key>(
    registry: &mut CoinRegistry,
    decimals: u8,
    symbol: String,
    name: String,
    description: String,
    icon_url: String,
    ctx: &mut TxContext,
): (CurrencyInitializer<T>, TreasuryCap<T>) {
    assert!(!registry.exists<T>(), ECurrencyAlreadyExists);
    assert!(is_ascii_printable!(&symbol), EInvalidSymbol);

    let treasury_cap = coin::new_treasury_cap(ctx);
    let currency = Currency<T> {
        id: derived_object::claim(&mut registry.id, CurrencyKey<T>()),
        decimals,
        name,
        symbol,
        description,
        icon_url,
        supply: option::some(SupplyState::Unknown),
        regulated: RegulatedState::Unregulated,
        treasury_cap_id: option::some(object::id(&treasury_cap)),
        metadata_cap_id: MetadataCapState::Unclaimed,
        extra_fields: vec_map::empty(),
    };

    (CurrencyInitializer { currency, is_otw: false, extra_fields: bag::new(ctx) }, treasury_cap)
}
