### Title
Missing upper-bound validation on `timestamp`/`mci`/`age` lock conditions in address definitions can permanently freeze funds - (File: `definition.js`)

### Summary
Address definitions (used for smart/shared addresses, wallet contracts, arbiter/prosaic contracts, and asset spending conditions) support time/height-based lock primitives `['timestamp', [relation, value]]`, `['mci', [relation, value]]` and `['age', [relation, value]]`. When such a definition is validated, `validateDefinition` in `definition.js` only checks that `value` is a non-negative integer and that the relation is one of the allowed operators — there is no upper-bound (sanity) check on the numeric value, mirroring the reported `CrowdSale.closingTime`/`cliff` flaw where a min/max bound was missing.

### Finding Description
In `definition.js`, the `evaluate` function inside `validateDefinition` handles the `mci`, `age`, and `timestamp` operators identically: [1](#0-0) 

The only numeric constraint applied is `isNonnegativeInteger(value)`, with no maximum cap comparable to, e.g., `constants.MAX_CAP` used elsewhere for amounts. Because these operators are evaluated later purely as numeric comparisons against `objValidationState.last_ball_timestamp` / `last_ball_mci`: [2](#0-1) 

a counterparty composing a shared/multisig address (e.g. in `arbiter_contract.js` deriving a shared address, or any wallet-defined-by-addresses flow validated via `wallet_defined_by_addresses.js`'s `validateAddressDefinition`) can embed a `['timestamp', ['>', HUGE_VALUE]]` or `['mci', ['>', HUGE_VALUE]]` clause with an unbounded value (e.g., a typo adding extra digits, or a value expressed in milliseconds instead of seconds). Since there is no protocol-level ceiling, such a condition validates successfully and is accepted into a real address definition used to gate spending of funds sent to that address. [3](#0-2) 

### Impact Explanation
Once funds are sent to an address whose spending condition contains an unbounded `timestamp`/`mci`/`age` clause with an absurdly large value (e.g., far beyond any realistic main chain index or Unix timestamp for centuries), the condition can never be satisfied, and the branch (and potentially the whole `or`/`and` condition, if it's the only usable branch) becomes permanently unspendable. This mirrors the reported issue: high impact because valuable funds can be locked essentially forever due to a configuration/typo error by one of the parties composing the shared address, asset definition, or payment condition.

### Likelihood Explanation
Low, matching the original report: it requires a fat-finger error or deliberate misconfiguration (e.g., entering a millisecond-based value instead of seconds, or an excessive number of leading digits) when constructing a definition that uses `timestamp`/`mci`/`age` conditions. No max-bound check exists to catch this at validation time, so the mistake is only discovered once the funds are already locked.

### Recommendation
Add reasonable upper-bound checks in the `mci`/`age`/`timestamp` case of `evaluate` in `definition.js` (alongside the existing `isNonnegativeInteger(value)` check), e.g., rejecting `mci`/`age` values above a sane maximum expected chain length, and `timestamp` values beyond a reasonable number of years into the future (similar to the future-timestamp check already used for unit timestamps in `validation.js`). [4](#0-3) 

### Proof of Concept
1. Construct an address definition such as `["and", [["address", "SOME_ADDR"], ["timestamp", [">", 99999999999999999]]]]` (a timestamp value far beyond any realistic future date, well past the year 5138 that a naive fat-finger might still type as a plausible-looking large number).
2. Submit it through `validateDefinition`/`validateAddressDefinition` (e.g., via `wallet_defined_by_addresses.js`) — validation succeeds because only `isNonnegativeInteger` is checked, per `definition.js` lines 480-495.
3. Fund the resulting address. Because `last_ball_timestamp` will never reach the huge value, the `timestamp` clause per `definition.js` lines 1036-1048 never evaluates to true, and the funds locked under that branch become permanently unspendable.
