### Title
Stored position risk stamps keep counting collateral after the spoke listing disables `is_collateralizable` — (`File: contracts/controller/src/risk/totals.rs`)

### Summary
The Linux bug: when a format‑0 crycb shadows only a prefix of the apcb, bits 64..255 keep their stale value and the guest retains access to a device that is no longer available. The lending analog: `SpokeAssetConfig.is_collateralizable` can be cleared by `editAssetInSpoke`, but no path zeroes or disqualifies the risk parameters already stamped into `AccountPositionRaw`. `calculate_account_risk_totals` and `calculate_ltv_collateral_wad` value every stored supply leg purely from `position.loan_to_value` / `position.liquidation_threshold` and never consult the live listing's collateral flag. The stale stamp — like the un-zeroed crypto bits — continues to grant collateral weight that the current configuration says is no longer available.

### Finding Description
- `AccountPositionRaw` stores `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`; it has **no field** tracking whether the leg is still collateral-eligible (`common/src/types/pool.rs:235-245`).
- `calculate_account_risk_totals_body` (`contracts/controller/src/risk/totals.rs:171-199`) iterates `supply_positions` and adds `position.liquidation_threshold.apply_to_wad_floor(gate_value)` to `weighted_collateral` and `min(ltv, lt)` to `ltv_collateral`. It never calls `cached_spoke_asset`, so a cleared `is_collateralizable` is invisible to HF and borrow-limit gates.
- `restamp_listed_supply_ltv` / `refresh_supply_risk_params` (`contracts/controller/src/risk/params.rs:25-64`) copy only `loan_to_value` (and, gated, the LT/bonus/fee tuple). They do not check `effective_config.is_collateralizable` and cannot write a zero/disabled stamp — a disabled flag is therefore a smaller "format‑0" shadow that leaves the position's effective collateral weight unchanged forever.
- `is_collateralizable` is only consulted on the supply/admission path (`contracts/controller/src/positions/mod.rs`, `contracts/controller/src/config/asset.rs:80`); it is not consulted at valuation time.
- `remove_asset_from_spoke` requires `supplied_scaled_ray == 0` (`contracts/controller/src/config/asset.rs:196-201`), so delisting cannot orphan a position — the flag-clear path is the only way collateral weight is meant to be revoked, and it does not propagate.

### Impact Explanation
After governance sets `can_collateral = false` on an asset (e.g., a depegging or compromised collateral), every existing supply leg of that asset continues to contribute its stamped LT-weighted value to `weighted_collateral` and `ltv_collateral`. Unprivileged borrowers can keep borrowing against collateral the protocol intended to disqualify, and unhealthy accounts evade liquidation because their HF is inflated by the dead collateral. This produces borrows backed by collateral that should count for zero — direct protocol insolvency / theft of pool funds via undercollateralized borrow or `multiply`/`flash_position` leverage.

### Likelihood Explanation
Medium. Triggering requires a routine, legitimate admin action (`editAssetInSpoke` with `can_collateral = false`), after which any unprivileged account holder of that asset can call `borrow` / `withdraw` / strategy endpoints and pass `require_post_pool_risk_gates` using the stale stamp. The only partial mitigation is that admins would presumably also zero `ltv`/`threshold` in the same edit — but nothing enforces that coupling, and `editAssetInSpoke` explicitly permits tightening edits without them (`asset.rs:29-31`).

### Recommendation
In `refresh_supply_risk_params` and `restamp_listed_supply_ltv`, force `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` to zero (or skip the leg in `calculate_account_risk_totals_body` / `calculate_ltv_collateral_wad`) when `cached_spoke_asset(...).is_collateralizable == false`. Equivalent fix: consult the live flag inside the risk-totals loop, mirroring how the kernel zeroes the unshadowed apcb bits.

### Proof of Concept
1. Alice supplies X Token on spoke S (listing `can_collateral=true, ltv=7500, lt=8000`); position stamps those values via `get_or_create_supply_position`.
2. Governance executes `editAssetInSpoke(spoke_id=S, asset=X, can_collateral=false, ltv=7500, lt=8000, ...)` — flag ratchet only guards `paused/frozen/no_seize`, so this succeeds while positions exist.
3. Any keeper calls `update_account_threshold(caller, has_risks=true, [alice_id])`: `sync_account_thresholds` finds the listing, restamps identical values; `apply_gated_liquidation_params` copies the same tuple — nothing zeroes the leg.
4. Alice calls `borrow(account_id, hub_asset=Y, amount=…)` up to `min(stamp_ltv, stamp_lt) × value(X)`. `calculate_account_risk_totals` (`totals.rs:190-198`) counts X at the stored LT; `require_post_pool_risk_gates` passes despite X being configured as non-collateral.
5. X's price collapses or its redemption is impaired; Alice's debt is backed by collateral the listing marks as zero-weight, and liquidation cannot restore solvency because the same stale stamp keeps HF above 1 until real value is gone.
