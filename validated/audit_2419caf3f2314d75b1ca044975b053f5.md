### Title
i128 overflow in accrual `scaled_to_original` permanently freezes an oversized market — all repay, withdraw, borrow and liquidation calls revert - (File: common/src/rates/scaling.rs)

### Summary

The bug class behind CVE-2021-30516 (memory corruption through an unchecked buffer bound) maps onto XOXNO Lending as unchecked fixed-point magnitude: every interest accrual computes `scaled_amount * index` in `i128` inside `scaled_to_original`, and that product overflows for a market whose scaled debt times the borrow index exceeds `~1.7e38`. Because `global_sync` accrues first in every mutating pool verb, once the ceiling is crossed the market is permanently bricked — no repay, no withdraw, no liquidation, no accrual — even though the `MAX_BORROW_INDEX_RAY` index cap was designed to stop runaway growth and never engages.

### Finding Description

`scaled_to_original` performs the unscaled-value computation with a panicking half-up multiply:

- `common/src/rates/scaling.rs:14-16` — `scaled.mul(env, index)` calls `mul_div_half_up`, which panics with `GenericError::MathOverflow` when `scaled * index / RAY` does not fit `i128` (see `common/src/math/fp_core.rs:108-118`).

`accrue_step` in `common/src/rates/simulate.rs:60-61` calls `scaled_to_original(borrowed, borrow_index)` at the top of every chunk to compute utilization. `contracts/pool/src/interest.rs::global_sync` runs `accrue_step` before state is touched by `supply`, `withdraw`, `repay`, `borrow`, `flash_loan`, liquidation withdrawals, and `claim_revenue` — the accrue-first ordering is stated in `contracts/pool/README.md` (Interest section) and confirmed by the end-to-end test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`), which shows `update_indexes`, `withdraw`, and `repay` all failing with `MATH_OVERFLOW` once `borrowed * borrow_index` crosses `i128::MAX`, while `borrow_index < MAX_BORROW_INDEX_RAY` — the index ceiling never clamps because the value product overflows first.

Root cause: the borrow-index ceiling `MAX_BORROW_INDEX_RAY` (`10^36`, `update_borrow_index`) bounds the index alone, but the invariant that actually breaks is `borrowed_scaled * borrow_index < i128::MAX`, i.e. `borrowed_scaled * index < ~170 RAY` of debt value. For a large market (order 10^9 tokens at 18 decimals), a few years of sustained high utilization at the steep end of the rate curve cross that product bound before the index reaches 10^9×RAY. Nothing in `supply`/`borrow` enforces `borrowed * index` headroom, and `supply_cap`/`borrow_cap` maxima (`i128::MAX / 10^(27-d)`, ~170 billion whole tokens at 18 decimals) admit book sizes far above the threshold.

### Impact Explanation

Permanent freezing of funds, protocol-wide for the affected market. Once `borrowed_scaled * borrow_index` overflows:

- Suppliers cannot `withdraw` any of their deposits in that market — every withdrawal accrues first and panics.
- Borrowers cannot `repay` — their collateral in other markets stays locked against unclosable debt.
- Liquidators cannot `liquidate` the accounts — `build_liquidation_plan` goes through `Context::cached_market_index`, which needs the same (simulated) index math, and the pool-side repay legs revert on accrual anyway.
- `clean_bad_debt` / `recapitalize` cannot recover the market for the same reason, so there is no recovery path; the freeze is permanent, not temporary.

### Likelihood Explanation

Reachable by a single unprivileged address:

1. Supply ~1 billion units of a high-decimals token into a market (admin listing and caps already permit up to ~170 billion whole tokens at 18 decimals; the test uses lifted caps on an ordinary listed market, and the on-chain maximum admitted cap is of the same order). Capital cost is large but no privilege is needed — supplying is permissionless.
2. Borrow near max utilization (98% in the harness test) from a second account with ordinary collateral.
3. Wait for interest accrual at the curve's high-utilization segment (up to 200% APR) to push `borrowed * borrow_index` past `i128::MAX` — the test crosses the cliff within 40 simulated years on the XLM curve, with the borrow index still far below `MAX_BORROW_INDEX_RAY`.
4. From that point every entrypoint touching the market reverts with `MathOverflow` (error propagates from `mul_div_half_up`). The attacker cannot themselves profit directly, but any whale supplier and borrower — attacker included, griefing or simply by organic growth of a large market — permanently locks all supplier deposits and outstanding debt in that market. The test demonstrates the failure end-to-end in production code paths.

### Recommendation

- In `accrue_step` / `update_borrow_index`, clamp or saturate the effective debt valuation: when `borrowed * borrow_index` would overflow `i128`, cap the index at `i128::MAX / borrowed` (or use `mul_div_floor_saturating` for the utilization computation) so accrual can still complete and the market stays operable.
- Alternatively enforce at entry (`supply`, `borrow`, `create_strategy`) a headroom check `borrowed * borrow_index < i128::MAX / SAFETY` so the product bound can never be crossed before `MAX_BORROW_INDEX_RAY` engages.
- At minimum, make `require_reserves`/accrual ordering tolerant: allow `repay` and `withdraw` to skip accrual of a market whose debt value no longer fits, so users can exit a saturated market.

### Proof of Concept

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);            // whale supplier, permissionless
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);               // 98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// All revert with MathOverflow, borrow_index still < MAX_BORROW_INDEX_RAY:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
```

The overflow site is `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) reached from `accrue_step` (`common/src/rates/simulate.rs:60`) inside `pool::interest::global_sync`, which every pool verb invokes before touching state — so once `borrowed * borrow_index > i128::MAX` the market's deposits and debt are frozen permanently.

Confidence caveat: the harness test disables `max_utilization` and lifts caps to extreme values; on a production deployment with conservative admin-set caps the cliff is reached only for very large markets, and the docs acknowledge value-overflow arithmetic limits. Still, the admitted cap domain (~170 billion whole tokens at 18 decimals) is far above the ~170×index overflow threshold, so the freeze is reachable within deployed configuration space and has no recovery path.
