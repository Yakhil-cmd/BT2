### Title
Shared `CLPoolAddr` Between Two Validators Causes Silent KAIA Reward Loss in `assignStakingRewards`/`assignStakingRewardsFlex` — (File: `kaiax/reward/impl/getter.go`)

---

### Summary

In `assignStakingRewards` and `assignStakingRewardsFlex`, the `alloc` map is written with `=` (assignment) instead of `+=` (accumulation) for `CLPoolAddr` entries. If two different consolidated validators share the same `CLPoolAddr` in the CLRegistry, the second validator's CL reward silently overwrites the first validator's entry. The `remaining` counter is still decremented for both, so the discrepancy is invisible to `spec.Validate()`, and the block finalizes normally — but `clAmount_A` worth of KAIA is minted and never credited to anyone.

---

### Finding Description

In both `assignStakingRewardsFlex` and `assignStakingRewards`, the distribution loop writes CL pool rewards with plain assignment:

```go
// assignStakingRewardsFlex  (lines 474-477)
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // ← = not +=
}
```

```go
// assignStakingRewards  (lines 521-525)
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // ← = not +=
}
```

`ConsolidatedNodes()` guarantees unique `RewardAddr` values, so `alloc[cn.RewardAddr]` is safe. However, no such guarantee exists for `CLPoolAddr`. Two distinct consolidated nodes (different `RewardAddr`) can legally have the same `CLPoolAddr` if the CLRegistry does not enforce pool-address uniqueness across validators.

When that collision occurs:

| Iteration | alloc written | remaining reduced |
|-----------|--------------|-------------------|
| CN_A | `alloc[R_A]=cnAmount_A`, `alloc[P]=clAmount_A` | `−reward_A` |
| CN_B | `alloc[R_B]=cnAmount_B`, `alloc[P]=clAmount_B` (**overwrites**) | `−reward_B` |

Final `alloc` sum = `cnAmount_A + cnAmount_B + clAmount_B` = `reward_A + reward_B − clAmount_A`.

`kip82Remainder` = `stakersReward − reward_A − reward_B` (unchanged), so the proposer receives the correct remainder. But the total credited via `state.AddBalance` in `FinalizeState` equals `(Minted + distributableFee) − clAmount_A`. The `clAmount_A` kei is minted but never added to any account — it is effectively burned.

`spec.Validate()` only rejects negative amounts:

```go
func (spec *RewardSpec) Validate() error {
    for addr, amount := range spec.Rewards {
        if amount.Sign() < 0 {
            return errNegativeRewardAmount(addr, amount)
        }
    }
    return nil
}
```

It does not verify that `sum(spec.Rewards) == Minted + TotalFee − BurntFee`, so the discrepancy passes silently. The test helper `sanityCheckRewardSpec` does assert this equality, but no test exercises the shared-`CLPoolAddr` scenario. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

---

### Impact Explanation

Every block in which two eligible validators share the same `CLPoolAddr`, `clAmount_A` kei of KAIA is minted by the protocol but credited to no account. This is an unauthorized, silent reduction of the effective reward distribution — a per-block loss of system-managed KAIA funds. The invariant `sum(spec.Rewards) == Minted + TotalFee − BurntFee` is broken without any error being raised, and the loss accumulates indefinitely.

---

### Likelihood Explanation

The Prague hardfork must be active and `CLStakingInfos` must be non-nil. The CLRegistry comment states "One CLStakingInfo per validator is guaranteed by CLRegistry," but this only prevents a single validator from having two CL entries — it does not prevent two distinct validators from registering the same `CLPoolAddr`. If the CLRegistry contract enforces pool-address uniqueness across all validators, the scenario is unreachable; if it does not, any two validators that happen to point to the same pool contract trigger the bug on every block both are eligible. [5](#0-4) 

---

### Recommendation

Replace the plain assignment with accumulation for `CLPoolAddr`, mirroring the `IncRecipient` pattern already used in `RewardSpec`:

```go
// Before (buggy)
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount

// After (fixed)
if prev, ok := alloc[cn.CLStakingInfo.CLPoolAddr]; ok {
    prev.Add(prev, clAmount)
} else {
    alloc[cn.CLStakingInfo.CLPoolAddr] = new(big.Int).Set(clAmount)
}
```

Apply the same fix to both `assignStakingRewards` and `assignStakingRewardsFlex`. Additionally, add a test case where two validators share the same `CLPoolAddr` and assert that `sanityCheckRewardSpec` passes. [6](#0-5) 

---

### Proof of Concept

1. Prague hardfork is active; `CLStakingInfos` is non-nil.
2. CLRegistry returns two entries: `(NodeId=N_A, CLPoolAddr=P)` and `(NodeId=N_B, CLPoolAddr=P)` — same pool address.
3. Both validators have `StakingAmount >= MinimumStake` and are in `ConsolidatedNodes()` with distinct `RewardAddr` values `R_A` and `R_B`.
4. `assignStakingRewards` iterates:
   - CN_A: `alloc[R_A] = cnAmount_A`, `alloc[P] = clAmount_A`, `remaining -= reward_A`
   - CN_B: `alloc[R_B] = cnAmount_B`, `alloc[P] = clAmount_B` (**overwrites** `clAmount_A`), `remaining -= reward_B`
5. `stakersAlloc` = `{R_A: cnAmount_A, R_B: cnAmount_B, P: clAmount_B}`.
6. `getDeferredRewardFullKore` calls `spec.IncRecipient` for each entry — `clAmount_A` is never passed.
7. `FinalizeState` calls `state.AddBalance` for each `spec.Rewards` entry; `clAmount_A` kei is never added to any account.
8. `spec.Validate()` returns nil (no negative amounts); block is committed with `clAmount_A` kei permanently lost. [7](#0-6) [8](#0-7) [9](#0-8)

func sanityCheckRewardSpec(t *testing.T, spec *reward.RewardSpec, msg interface{}) {
	sumSummary := new(big.Int).Add(spec.Minted, spec.TotalFee)
	sumSummary.Sub(sumSummary, spec.BurntFee)
	assert.True(t, spec.Minted.Sign() >= 0, msg)
	assert.True(t, spec.TotalFee.Sign() >= 0, msg)
	assert.True(t, spec.BurntFee.Sign() >= 0, msg)

	sumParts := new(big.Int).Add(spec.Proposer, spec.Stakers)
	sumParts.Add(sumParts, spec.KIF)
	sumParts.Add(sumParts, spec.KEF)
	sumParts.Add(sumParts, spec.KPF)
	assert.True(t, spec.Proposer.Sign() >= 0, msg)
	assert.True(t, spec.Stakers.Sign() >= 0, msg)
	assert.True(t, spec.KIF.Sign() >= 0, msg)
	assert.True(t, spec.KEF.Sign() >= 0, msg)
	assert.True(t, spec.KPF.Sign() >= 0, msg)

	sumRewards := new(big.Int)
	for _, amount := range spec.Rewards {
		sumRewards.Add(sumRewards, amount)
		assert.True(t, amount.Sign() >= 0, msg)
	}

	assert.Equal(t, sumSummary, sumParts, msg)
	assert.Equal(t, sumSummary, sumRewards, msg)
}
