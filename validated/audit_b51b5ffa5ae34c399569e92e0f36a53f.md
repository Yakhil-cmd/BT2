### Title
Webhook Signature Verified Against `repository.owner.login`/`organization.login` While the Sync Handler Acts On the Unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the webhook secret) used to validate the request's HMAC signature based on `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` or falling back to `params.dig('organization', 'login')`. However, once the signature check passes, every webhook handler resolves the target `Repository`/`Stack` using an entirely different field of the same JSON body: `payload.dig('repository', 'full_name')`. These two identifiers are never cross-checked against each other, and — critically — the app whose secret is used for verification can be configured with **no** `webhook_secret` at all, in which case verification is bypassed unconditionally.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

The verification key comes from `Shipit.github(organization: repository_owner)`, which selects a `GithubApp` instance per configured organization (documented in `docs/setup.md` under "Using Multiple Github Applications"). Signature comparison itself: [3](#0-2) 

Note line 77: `return true unless webhook_secret` — if the organization resolved by `repository_owner` happens to be configured **without** a `webhook_secret` (explicitly shown as optional/`nil` in `config/secrets.development.example.yml` and `docs/setup.md`), signature verification is a no-op and any payload is accepted as "verified" for that organization.

Meanwhile, the actual repository/stack that gets acted upon is resolved from a *different* field of the same attacker-controlled JSON body: [4](#0-3) 

and, for pushes specifically: [5](#0-4) 

There is no assertion anywhere that `params.dig('repository','owner','login')` (used to pick the verifying secret) equals the owner portion of `params.dig('repository','full_name')` (used to pick the `Stack` being synced). The two lookups are logically independent even though they read from the same payload object.

**The broken binding**: "organization that authenticated the webhook" should equal "the repository whose stacks are written to as a result of that webhook" — this is exactly the trust equality called out by the external report's bug class (deployment-trust binding broken between an authenticating identity and the entity that is actually written).

### Impact Explanation
In a multi-organization Shipit deployment (a supported, documented configuration — `docs/setup.md`, "Using Multiple Github Applications"), if **any** configured organization has no `webhook_secret` set (or a leaked/guessable one), an attacker can:
1. Send `POST /webhooks` with `X-Github-Event: push`.
2. Set `repository.owner.login` (or `organization.login`) to the unsecured/known org, causing `verify_signature` to select that org's `GithubApp` and pass verification for free (or with a known secret).
3. Set `repository.full_name` to the full name of a *different, properly secured* repository that has active stacks in Shipit.
4. `PushHandler#process` will locate stacks for that spoofed `repository.full_name` and call `stack.sync_github(expected_head_sha: params.after)`, forcing Shipit to sync/track an attacker-chosen commit SHA as the target head for that stack — which, combined with `continuous_deployment`, can trigger an unauthorized deploy of attacker-influenced state without ever knowing the target organization's real webhook secret.

This satisfies the "unauthorized deploy" impact criterion for unprivileged attackers who never held any Shipit session, API token, or GitHub credentials for the targeted organization.

### Likelihood Explanation
Requires a specific but realistic and documented configuration: multiple GitHub Apps registered in `Shipit.github`, at least one of which lacks a `webhook_secret` (explicitly presented as optional in the shipped example config), or whose secret has otherwise been disclosed/guessed. Given the setup docs explicitly walk through `webhook_secret: # nil` as a valid state and the multi-org feature is a first-class supported mode, this is a plausible operational misconfiguration rather than a purely theoretical scenario, and the underlying code flaw — verifying against one payload field but acting on another — is unconditional regardless of how many orgs are configured with real secrets, since it's the org selection itself (not just the missing-secret edge case) that is unbound from the acted-upon repository.

### Recommendation
After successfully verifying the webhook signature, cross-validate that the resolved verification organization matches the owner segment of `repository.full_name` used by the handlers (or, simpler, derive `repository_owner` in `WebhooksController` from the same `full_name` field the handlers use, so both signature selection and action resolution are bound to a single, consistent identifier). Additionally, `GithubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in the presence of multiple configured organizations — require a secret whenever more than one GitHub App/org is configured, or fail closed instead of open.

### Proof of Concept
Assume `config/secrets.yml` configures two orgs: `unsecured-org` (no `webhook_secret`) and `victim-org` (real secret, has stack `victim-org/app` with `continuous_deployment: true`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/app"
  }
}
```

`verify_signature` resolves `repository_owner` = `"unsecured-org"`, fetches that org's `GithubApp` (no secret) → `verify_webhook_signature` returns `true` unconditionally. `PushHandler#process` then resolves the target stack from `repository.full_name` = `"victim-org/app"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, even though the attacker never had `victim-org`'s webhook secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
