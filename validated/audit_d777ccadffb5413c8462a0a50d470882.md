### Title
Utilization-ceiling griefing: an unprivileged borrower can frontrun exits and drive utilization to `max_utilization`, freezing all non-liquidation withdrawals and revenue claims - (File: contracts/pool/src/guards.rs)

### Summary

The auction report's bug class is "an unprivileged caller moves a shared ratio (`float_`) that a victim's pending transaction depends on, cheapening or blocking that transaction." XOXNO Lending has the same shape: `require_utilization_below_max` is an absolute post-state gate applied to every ordinary `withdraw` and `claim_revenue`, while any collateralized account can push `ceil(debt)/floor(supply)` up to that ceiling via `borrow`, `create_strategy`/`flash_position` debt minting. Once utilization reaches `params.max_utilization`, burning supply shares only raises utilization further, so *every* withdrawal — of any size, by any supplier — reverts with `UtilizationAboveMax` (127). A single attacker can therefore hold all suppliers' funds hostage for the cost of interest on a borrow.

### Finding Description

`require_utilization_below_max` computes `borrowed.div_ceil(supplied)` and asserts it is `<= max_utilization` (guards.rs:19-34). The guard runs after the burn in `withdraw::accounting` → `gate_and_debit` (withdraw.rs:79, 111-119) and in `revenue::accounting` (revenue.rs:44). Because the check is on the *post-withdrawal* state, no exit size helps: reducing `supplied` only increases the ratio. The only skips are liquidation withdrawals and footprint-only closes (withdraw.rs:78-79), so regular users cannot exit at all while utilization sits at or above the cap.

The attacker needs no privilege and no timing beyond ledger ordering:

1. Supply collateral in a different asset/hub via controller `supply` (or reuse an existing healthy account, or open debt via `flash_position`/`multiply`, which mints debt without an origination fee and leaves a solvent position).
2. Call controller `borrow` on the target market until utilization reaches `max_utilization` — the borrow's own copy of the same guard (borrow also runs `require_utilization_below_max` and the 200 BPS `require_liquidation_buffer`) stops it exactly at the ceiling, which is precisely the griefing point.
3. Every subsequent `withdraw` and `claim_revenue` on that market reverts until the attacker repays, interest accrual is offset by repayments, or liquidation withdraws (which bypass the cap) drain debt.

The test suite confirms the mechanics: `withdrawal_ceiling_tracks_one_minus_utilization_over_max` shows withdrawal reverts with `UTILIZATION_ABOVE_MAX` above the closed-form exit ceiling, and `the_exit_is_capped_by_max_utilization_and_the_script_reverts_whole` shows a whole multi-op script reverting. The pool README even states "once utilization reaches the cap no withdrawal of any size passes, and interest accrual alone pushes it there" — i.e., the freeze state, once reached, is self-reinforcing since accrual grows `borrowed` while exits stay blocked.

Note the direct-donation variant of the reported class does *not* work here (INV-ACCT-02: tracked cash ignores donations, and `test_donation_attack_does_not_inflate_share_price` passes), but the utilization path achieves the same outcome through a legitimate operation the protocol must admit.

### Impact Explanation

Temporary freezing of funds for all suppliers and the protocol owner (revenue claims) in the targeted (hub, token) market. Because `supplied` enters the denominator, even dust-sized exits revert; suppliers cannot de-risk during a price move, cannot escape before bad-debt socialization (`clean_bad_debt` writes the supply index down only after suppliers are already locked), and interest keeps compounding against them while they are trapped. The freeze lasts until the attacker chooses to repay or a third party repays/liquidates the attacker's debt — there is no permissionless unwind a victim can trigger.

### Likelihood Explanation

Reachable by any address with collateral for a borrow, or even without idle capital through `flash_position`, which mints debt before a callback and requires only that the resulting account is solvent. The attacker's cost is the borrow interest for the griefing duration (bounded by 200% APR worst case, typically far less), and the attack needs no privileged role, no oracle manipulation, and no race beyond normal transaction ordering. Markets with `max_utilization < RAY` (the standard configuration; presets use 95%) are all exposed. Medium likelihood: it requires capital to sustain and yields no direct profit (pure grief / extortion leverage), matching a Medium severity.

### Recommendation

Make the utilization gate asymmetric, mirroring the existing backing-check policy ("blocks entry, not exit"):

- Apply `require_utilization_below_max` to `withdraw` only when post-state utilization *decreased* or stayed equal — i.e., skip the gate when the withdrawal does not push utilization further above the cap beyond its pre-op value — so exits are never blocked by a ratio the withdrawer did not create. Alternatively, cap each withdrawal at the amount that keeps utilization at `max_utilization` (the current behavior) but let *some* exit through by clamping, and let full exits proceed when utilization was already above the cap before the call.
- At minimum, exempt `claim_revenue` and full-close withdrawals when utilization is already at/above the ceiling, since blocking them provides no solvency benefit (cash is already lent out; the guard does not create liquidity).
- Consider rate-side mitigation: when utilization is pinned at `max_utilization`, the top-slope region should make holding the blocking borrow economically unattractive faster than suppliers' losses accrue.

### Proof of Concept

Setup mirroring `tests/test-harness/tests/controller/bad_debt_netting_and_exit_timing.rs`:

```rust
// Bob is the victim supplier; DAVE is the attacker.
let mut t = LendingTest::new().standard_two_asset().build(); // max_utilization = 95%

t.supply(BOB, "ETH", 100.0);                    // victim liquidity
t.supply(DAVE, "USDC", 95.0 * 2000.0 * 2.0);    // attacker collateral
t.borrow(DAVE, "ETH", 95.0);                    // drive utilization to the cap

// Every victim exit now reverts:
let res = t.try_withdraw(BOB, "ETH", 0.001);    // even a dust exit
assert_contract_error(res, errors::UTILIZATION_ABOVE_MAX);
let res2 = t.try_withdraw(BOB, "ETH", 100.0);   // full exit
assert_contract_error(res2, errors::UTILIZATION_ABOVE_MAX);
// claim_revenue reverts identically (revenue.rs:44).
// While utilization >= cap, interest keeps accruing on Bob's trapped supply,
// and only DAVE's repay or a liquidation (which skips the cap) releases exits.
```

The existing harness test `the_exit_is_capped_by_max_utilization_and_the_script_reverts_whole` (tests/test-harness/tests/composition/supplier_exit_before_socialization_is_bounded_by_utilization.rs:81-107) already demonstrates the revert end-to-end; the missing piece is only that the utilization state is attacker-controllable via an ordinary `borrow`.
