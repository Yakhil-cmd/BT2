### Title
Webhook signature verified against organization-selected secret while downstream handlers act on a repository field from the same unverified payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then verifies the signature against that org's secret. Once verification passes, `create` re-parses the same raw body and dispatches it to handlers (e.g. `PushHandler`) keyed by whatever `repository.full_name`/`ref` values are present in that payload. The equality the app implicitly assumes — "the organization whose secret authenticated this request" == "the repository the handlers act on" — is never actually checked.

### Finding Description
In `Shipit.github(organization:)` (`lib/shipit.rb:170-181`), each configured GitHub organization has its own `webhook_secret` (`lib/shipit.rb:196-200`, `config/secrets.development.example.yml`). `WebhooksController#verify_signature` does: [1](#0-0) 

`repository_owner` is derived purely from the JSON body, before any cryptographic check: [2](#0-1) 

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only proves that the request was signed with the secret belonging to *that* organization — it says nothing about which repository the payload's other fields describe. `create` then re-parses the body and lets handlers act on `repository`/`ref`/`after` fields taken from the same payload: [3](#0-2) [4](#0-3) 

If an attacker controls (or is a legitimate member/webhook-capable actor of) one configured GitHub organization "A" — and thus knows or can obtain "A"'s `webhook_secret` — they can build a POST to `/webhooks` where `repository.owner.login` = `"A"` (so `verify_signature` selects A's secret and the HMAC checks out) while other payload fields (`repository.full_name`, `ref`, `after`, commit shas, statuses, check runs, etc.) describe a completely different, victim-owned repository/stack "B" tracked by the same Shipit instance. The signature check never verifies that the signed org matches the repository that the handler subsequently operates on.

This is the same trust-binding gap named in the report's bug class: the value that is cryptographically checked (organization "A") is not the value that is actually acted upon (repository "B").

### Impact Explanation
Handlers such as `PushHandler` locate stacks purely by `branch` across `stacks` and call `stack.sync_github(expected_head_sha:)`, and `StatusHandler`/`CheckSuiteHandler` mutate commit/check-run state used to gate deploy eligibility. By forging a cross-organization payload that passes signature verification under org A's secret but targets org B's stack/commit, an attacker who only controls org A's webhook secret can inject fabricated push/status/check-run events against org B's stacks — influencing what Shipit considers "green"/deployable and potentially triggering an unauthorized deploy path. This crosses a repository-write/cross-org boundary without holding org B's actual webhook secret, matching the "cross-repository writes / unauthorized deploy" high-impact category.

### Likelihood Explanation
Requires the instance to be configured with the multi-organization `github:` secrets schema (`TOP_LEVEL_GH_KEYS` / `github_app_config`) and the attacker to know (or leak) one configured organization's `webhook_secret` — plausible in a shared/multi-tenant Shipit deployment where different teams/orgs each manage their own GitHub App and its secret is not treated as fully "trusted for all repos." No Shipit session, `ApiClient` token, or GitHub repository write access is needed; only knowledge of one org's `webhook_secret`, satisfying the "unprivileged relative to the target repo" bar since org A's secret grants no legitimate authority over org B's repositories.

### Recommendation
After signature verification succeeds for organization `repository_owner`, re-validate that every repository/organization identifier referenced elsewhere in the payload (e.g. `repository.full_name`, `repository.owner.login` used by the eventual handler) belongs to the same organization whose secret was used to verify the signature. Reject the webhook if these do not match, rather than trusting the raw parsed body uniformly in `create` after only spot-checking `repository_owner`/`organization.login` for secret selection.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (secret `sA`, attacker-known) and `orgB` (secret `sB`, victim's, tracked stack `orgB/victim-repo`).
2. Attacker crafts a `push` JSON payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
   }
   ```
   Note the mismatch: `repository.full_name` says `orgB/victim-repo`, but `repository.owner.login` (used only for secret lookup) says `orgA`.
3. Attacker signs the raw body with `sA` and sets `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, verifies successfully against `sA`.
5. `create` re-parses the body and dispatches to `PushHandler`, which searches `stacks.not_archived.where(branch: "main")` across **all** stacks (not scoped to orgA) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on any matching stack — including `orgB/victim-repo` if its branch matches — despite the request never being signed by `orgB`'s secret.

Note: I could not fully trace whether `PushHandler#stacks`/`Handler` base class scopes results by the specific `repository.full_name` from the payload before matching branch (only `app/models/shipit/webhooks/handlers/push_handler.rb` and `lib/shipit.rb` were inspected); confirming the exact stack-lookup scoping in `app/models/shipit/webhooks/handlers/handler.rb` would strengthen this further, but the core signature/authorization gap — verifying by `repository_owner` while later code acts on other unverified fields of the same payload — is confirmed directly in the cited files.
