### Title
Cross-organization webhook confusion: signature-selecting organization is never bound to the repository the event actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App config/secret to verify the HMAC against using `repository_owner`, which is read straight from the untrusted JSON payload before verification succeeds. Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, etc.) re-reads the repository target from `payload.dig('repository', 'full_name')` via `Handler#repository_name` / `Repository.from_github_repo_name`. Nothing ties the value used to select the verifying secret to the value used to select the repository that is actually written to.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches that organization's GitHub App/secret to check the signature: [1](#0-0) [2](#0-1) 

The signature only proves "this HTTP body was HMAC-signed with organization `repository_owner`'s secret". It does not constrain any other field inside that same body. All downstream handlers, however, resolve the target repository independently, from `repository.full_name`, not from `repository.owner.login`: [3](#0-2) [4](#0-3) 

`PushHandler#process` uses that repository's stacks to trigger `sync_github`, and `StatusHandler#process` writes commit statuses: [5](#0-4) [6](#0-5) 

The binding that is broken (as an equality) is:
`organization whose secret authenticated the request (repository.owner.login) == organization that owns the repository actually mutated (repository.full_name's owner)`

Before the attacker's request: for legitimate GitHub-originated webhooks these two values are always consistent because GitHub itself populates both fields from the same repository object.

After the attacker's request: in a multi-organization Shipit deployment (`config/secrets.yml` supports per-organization `webhook_secret`, see `docs/setup.md`), an attacker who is a legitimate admin of/has webhook access to **one** configured organization (call it `org-A`, whose secret they know) can craft a raw JSON body where `repository.owner.login` (or the `organization.login` fallback) is `org-A` — satisfying `verify_signature`'s config lookup and HMAC check — while `repository.full_name` is set to `org-B/some-repo`, an entirely different organization's repository tracked by the same Shipit instance. `verify_signature` never checks that these two fields agree, and neither do `Handler#repository_name`/`Repository.from_github_repo_name`, so the forged `push`/`status`/`check_suite` event is processed against `org-B`'s stack.

### Impact Explanation
This allows an attacker who only controls one tenant/organization's webhook secret in a multi-org Shipit install to trigger `GithubSyncJob`/`sync_github` or forge commit statuses (`Commit#create_status_from_github!`) for a completely different organization's stacks — an unauthorized cross-repository/cross-organization action driven by a signature that was never meant to authorize it. Depending on which handler is targeted, this can influence CI status gating used for deploy approval (`StatusHandler`) or force a resync of another org's stack head (`PushHandler`), which is a building block toward an unauthorized deploy on a repository the attacker does not control.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls (or has leaked/legitimate access to) one configured organization's `webhook_secret` — a realistic operating condition per `docs/setup.md`'s documented multi-org config format — combined with knowledge of another tracked organization's `owner/name` (both are effectively public GitHub metadata). No repository write access, session, or `ApiClient` token is required; only the ability to sign an arbitrary raw body with one's own org's known webhook secret and POST it to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `github_app` and verifying the signature, re-derive the repository/organization actually referenced by the parsed payload (e.g., `repository.full_name`) and assert its owner matches `repository_owner` (or reject if they differ) before handlers are invoked. Alternatively, have `Handler#repository_name`/`stacks` validate that the resolved `Repository#owner` equals the organization whose secret verified the request, rejecting the event otherwise.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-A` and `org-B`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config).
2. As an attacker who knows `org-A`'s `webhook_secret` (e.g., a legitimate `org-A` GitHub App owner in this shared instance), build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": {"login": "org-A"}, "full_name": "org-B/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-A secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: 'org-A')`, verifies successfully against `org-A`'s secret [1](#0-0) .
5. `PushHandler` resolves `Repository.from_github_repo_name('org-B/target-repo')` and calls `sync_github(expected_head_sha: ...)` on `org-B`'s stacks [5](#0-4) , even though the request was never signed by `org-B`.
