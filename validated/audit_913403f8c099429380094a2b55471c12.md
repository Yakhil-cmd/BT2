## Analog Found: Unbounded Global Scan of Unstable Units in `data_feed`/`in_data_feed` Formula Evaluation

### Title
Denial of Service via Mempool Flooding Causing Unbounded Loop in AA Data-Feed Lookup - (File: `data_feeds.js`)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` iterate over the entire in-memory collection of all currently unstable units (`storage.assocUnstableMessages`) whenever an AA formula evaluates `in_data_feed[[...]]` or `data_feed[[...]]` with `bAA`/unstable lookup enabled. Because any unprivileged user can post large numbers of cheap units to the network, this loop is directly analogous to the reported `getBestOrder()` small-order-spam DoS: an attacker inflates a globally-shared, unbounded collection that every other legitimate operation (here, any AA trigger that reads a data feed) must fully scan.

### Finding Description
`dataFeedExists()` and `readDataFeedValue()` both contain: [1](#0-0) [2](#0-1) 

`for (var unit in storage.assocUnstableMessages)` walks **every unit that is currently unstable network-wide**, regardless of the oracle addresses actually requested, before the address filter (`_.intersection(arrAddresses, objUnit.author_addresses)`) is applied. For each such unit it also calls `.forEach()` over that unit's messages. This is invoked from the formula evaluator whenever an AA's oscript calls `data_feed[[...]]` or `in_data_feed[[...]]`: [3](#0-2) [4](#0-3) 

This is invoked during `handleTrigger()` → `evaluateAA()`, which runs synchronously on Node's single event loop for every AA trigger, including triggers sent by ordinary unprivileged users: [5](#0-4) 

The size of `storage.assocUnstableMessages` is not capped by any per-request or per-address limit — it grows with the total number of currently-unstable units in the entire DAG, which any unprivileged party can increase simply by posting many low-value units (paying only the standard tps/size fee) faster than they stabilize. This exactly mirrors the reported bug class: the attacker cheaply inflates a shared ordered/iterated structure (`priceTree`/order list in the report, `assocUnstableMessages` here) that a victim's normal, unrelated operation (`_makeOrder`/next best-order fill in the report, any AA's data-feed formula evaluation here) must fully traverse.

### Impact Explanation
Every AA that uses `data_feed[[...]]`/`in_data_feed[[...]]` with unstable-inclusive lookup pays an O(N) cost proportional to the attacker-controlled size of the network-wide unstable set on every trigger, not just triggers related to the flooded units. Because AA trigger handling runs synchronously and holds the `['aa_triggers']`/`['write']` mutex while iterating (see `handlePrimaryAATrigger`/`handleAATriggers`): [6](#0-5) 
a sufficiently large unstable set can make evaluation of a single trigger take long enough to stall the node's processing of other triggers and, since JS is single-threaded, block ingestion/validation of new incoming units for the duration of the scan. This can cause legitimate AA triggers to bounce (losing the sender's bytes to bounce fees) or, at sufficient scale, degrade the node's ability to keep processing/confirming new units in a timely manner — the same "normal operation starved by attacker-inflated small-item loop" outcome described in the report.

### Likelihood Explanation
Any unprivileged user can post units to the network at will; the cost is only the standard fee/tps-fee for posting a unit, no special privilege or minimum content is required to keep a unit "in flight" (unstable) long enough to be counted by this loop. An attacker who can sustain unit posting faster than the network stabilizes them (e.g., during periods of high witness latency, or intentionally by delaying inclusion) can keep `assocUnstableMessages` large, which is a comparatively low-cost, self-financed attack similar in spirit and cost profile to submitting many tiny orders in the reported marketplace bug.

### Recommendation
- Filter by oracle `arrAddresses` before iterating unstable messages (e.g., maintain an index from address → its unstable units/messages) instead of scanning the full `assocUnstableMessages` map for every lookup.
- Cap or throttle the number of unstable units considered per data-feed lookup, or fall back to the persisted key-value store path (`readDataFeedByAddress`) once an in-memory scan exceeds a bounded size.
- Consider bounding the total number of concurrently-unstable units/messages tracked in memory, independent of this specific code path, to remove the general DoS surface.

### Proof of Concept
1. Attacker continuously posts many cheap units (minimal payload, paying only the base tps fee) to the network faster than the current witnesses can stabilize them, growing `storage.assocUnstableUnits`/`storage.assocUnstableMessages` to a large size N.
2. A legitimate user triggers any AA whose oscript definition contains `in_data_feed[[oracles=..., feed_name=..., feed_value=...]]` or `data_feed[[...]]` (a common oracle-consuming pattern).
3. `formula/evaluation.js`'s `getDataFeed`/`in_data_feed` handling calls `dataFeeds.readDataFeedValue`/`dataFeedExists` with `bAA`/`unstable_opts` set, which executes the `for (var unit in storage.assocUnstableMessages)` loop over all N attacker-inflated entries before applying the oracle-address filter.
4. As N grows, this single synchronous scan (plus nested `.forEach` over each unit's messages) takes proportionally longer, delaying the response to the legitimate trigger and consuming the single Node.js event loop's time that would otherwise be used to validate/process other incoming units, reproducing the "small-order spam blocks normal operation" effect from the reference report.
