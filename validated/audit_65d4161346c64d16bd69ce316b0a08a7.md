### Title
Tokens delivered to the controller outside the measured collateral/refund lists are permanently stranded — there is no sweep or recovery path — (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` credits the caller's account only with positive balance deltas of tokens declared in `collaterals`, and refunds to the caller only positive deltas of tokens declared in `refund_assets`. Any other token balance the controller holds — extra tokens pushed by the flash receiver during `execute_flash_position`, leftover debt tokens not refund-listed, tokens sent in a token not refundable under the debt-hub/spoke listing rules, or plain unsolicited `token.transfer`s to the controller address — is neither credited nor returned. The controller exposes no sweep/rescue entrypoint, so those tokens are locked in the contract forever. This mirrors the DODO finding where `msg.value` accompanying an ERC20 deposit branch was irretrievably left in the factory: here, value accompanying the operation but not matching the declared lists is irretrievably left in the controller.

### Finding Description
In `process_flash_position`, after the receiver callback returns:

- `collect_collateral_deposits` measures `balance_delta_since` for each declared collateral token and deposits positive deltas into the account [1](#0-0) .
- `refund_listed_assets` → `refund_controller_balance_delta` returns only positive deltas above the pre-callback baseline for assets in `refund_assets` [2](#0-1) [3](#0-2) .
- `validate_refund_assets` restricts `refund_assets` to at most `max_supply_positions` unique tokens, each required to be an actively listed `(debt.hub_id, asset)` in the account's spoke and disjoint from `collaterals` [4](#0-3) .

Anything outside those two sets is ignored: "Returned debt becomes collateral if declared, returns to the caller if refund-listed, or remains uncredited if in neither list. Refunds cover only positive callback balance changes" (INV-STRAT-04) [5](#0-4) , and "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" [6](#0-5) . The baseline semantics of `snapshot_balances`/`balance_delta_since` also mean any pre-existing controller balance is explicitly excluded from refunds [7](#0-6) .

The same holds for the pool: unsolicited `token.transfer`s to the pool sit as unbooked donations that no market's `cash` book can ever pay out [8](#0-7) , and tests assert borrow/withdraw `to` the pool or controller is rejected precisely because such deliveries "strand the tokens" [9](#0-8) . That protection blocks *protocol-driven* deliveries to those addresses, but nothing blocks or recovers *user-driven* deliveries.

### Impact Explanation
Permanent freezing/loss of user funds. A caller (or their flash receiver contract) that delivers tokens to the controller which are not in `collaterals` or `refund_assets` — e.g., a token listed only in a different hub or spoke (which `validate_refund_assets` rejects, so it cannot be refund-declared), an over-return of the debt token omitted from `refund_assets`, an extra hop token from the receiver's own swap, or a mistaken direct `token.transfer` to the controller outside any call — loses those tokens permanently. No entrypoint can move controller-held token balances back out.

### Likelihood Explanation
Medium-low: it requires a caller/receiver mistake, like the original report. However it is easier to hit than in DODO because the refund set is artificially constrained — a token that is not listed in `(debt.hub_id, account.spoke_id)` is unrecoverable even if the caller *wants* to declare it, and `refund_assets` is capped by `max_supply_positions`, so receivers handling more token types than that cap cannot enumerate them all. Direct mistaken transfers to a well-known controller address are a recurring real-world user error.

### Recommendation
Add a bounded recovery mechanism: either (a) extend the refund loop to sweep all positive deltas of any token delivered during the callback back to the caller (bounded by a max-assets limit to keep the footprint sane), or (b) add a permissionless `sweep_stranded(asset, to)`-style entrypoint that only pays out balances not attributable to a pending operation — for the controller this is safe because no legitimate accounting ever relies on the controller holding token balances (all inbound flows are measured deltas consumed in the same call). At minimum, revert when the callback delivers a positive delta of a token in neither list, so mistakes fail loudly instead of silently donating funds to the contract.

### Proof of Concept
1. Alice owns a `Multiply` account. Her flash receiver swaps the minted debt into collateral but also forwards `extra` units of a token `T` that is listed only in hub 2 (or not listed at all) to the controller inside `execute_flash_position`.
2. Alice calls `flash_position(caller=alice, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals=[(XLM, min)], refund_assets=[USDC])`. `T` cannot be added to `refund_assets` because `cache.require_listed_active_config(spoke_id, (debt.hub_id, T))` rejects it [10](#0-9) .
3. The call succeeds; `T`'s delta is never inspected. `balance(T, controller)` permanently retains `extra`; no entrypoint can release it.
4. Simpler variant: any user calls `token::Client::transfer(user, controller, amount)` directly — the tokens are stranded identically, since refunds only cover deltas above a per-call baseline and there is no sweep function.

fn validate_refund_assets(
    env: &Env,
    cache: &mut Context,
    spoke_id: u32,
    hub_id: u32,
    collaterals: &Vec<(HubAssetKey, i128)>,
    refund_assets: &Vec<Address>,
) {
    let limits = storage::get_position_limits(env);
    assert_with_error!(
        env,
        refund_assets.len() <= limits.max_supply_positions,
        GenericError::InvalidPayments
    );

    let mut seen: Map<Address, bool> = Map::new(env);
    for asset in refund_assets.iter() {
        assert_with_error!(
            env,
            !seen.contains_key(asset.clone()),
            GenericError::InvalidPayments
        );
        seen.set(asset.clone(), true);
        // Refund transfers run after the guard; restrict tokens to listed assets.
        cache.require_listed_active_config(
            spoke_id,
            &HubAssetKey {
                hub_id,
                asset: asset.clone(),
            },
        );
        for (collateral, _) in collaterals.iter() {
            assert_with_error!(
                env,
                asset != collateral.asset,
                GenericError::InvalidPayments
            );
        }
    }
}

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
}

pub(crate) fn balance_delta_since(
    env: &Env,
    asset: &Address,
    holder: &Address,
    before: i128,
) -> i128 {
    token::Client::new(env, asset)
        .balance(holder)
        .checked_sub(before)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError))
}

/// Snapshots `holder`'s balance once per distinct asset address.
pub(crate) fn snapshot_balances(
    env: &Env,
    holder: &Address,
    assets: impl IntoIterator<Item = Address>,
) -> Map<Address, i128> {
    let mut snapshot = Map::new(env);
    for asset in assets {
        if snapshot.contains_key(asset.clone()) {
            continue;
        }
        let balance = token::Client::new(env, &asset).balance(holder);
        snapshot.set(asset, balance);
    }
    snapshot
}

pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}

Refund assets must be unique, listed in the debt hub and account spoke, disjoint from collateral declarations, and bounded by the maximum supply-position count. Refund eligibility requires an active spoke and an existing listing; it does not check collateralizable, borrowable, paused or frozen flags.
