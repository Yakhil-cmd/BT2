### Title
Cross-repository `security/scan` status/commit collision via unscoped `Commit.where(sha:)` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, and `Commit.by_sha`/`Commit.where(sha:)` elsewhere in the model has the same property. This means a validly-signed `status` webhook can write a `Status` row onto every `Commit` record across every stack that happens to share that SHA, not just the commit belonging to the repository that authenticated the webhook.

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` is assumed by the system but never enforced. `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` matches on `sha` alone, across the entire `commits` table, spanning all stacks/repositories. `create_status_from_github!` then creates a `Status` and re-evaluates `deployable?`/`blocked?`/merge scheduling for whichever stack the matched commit belongs to: [2](#0-1) [3](#0-2) 

Before reaching the handler, `Shipit::WebhooksController#verify_signature` validates the signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's `repository.owner.login`/`organization.login`: [4](#0-3) [5](#0-4) 

This check validates that the request is a genuine GitHub webhook for the claimed *organization/app installation*, but it never confirms that the SHA in the payload's `status` event actually belongs to the repository that produced the event — that binding is simply absent from the code. Once the organization-level signature check passes (which is standard: GitHub App/webhook secrets are typically configured per organization/installation, not per repository within it), `StatusHandler` will apply the status to any `Commit` row anywhere in the database with a matching `sha`, regardless of which repository/stack it belongs to.

The realistic exploit path requires that the attacker control (or be able to trigger a genuine, correctly-signed) `status` event from a repository within the same GitHub organization/App installation that Shipit trusts, and that a commit with an identical SHA also exists in a victim stack tracking a different repository in that org. Since Git SHAs are content-addressed, this can occur legitimately (e.g., shared boilerplate/initial commits, forks, cherry-picks, rebased history, or repos seeded from a common template) without any hash collision attack — the attacker only needs to discover or engineer such a shared SHA, then fire (or wait for CI to fire) a `security/scan` status with `state: failure` referencing that SHA from their own low-privilege repository. Because `StatusHandler` performs no `repository.full_name` / `stack_id` filtering, the victim's commit gets the same `Status` row, potentially flipping `Commit#deployable?`/`#blocked?` for the victim stack if `security/scan` is one of `stack.required_statuses`/`blocking_statuses`.

None of the existing guards address this: `verify_signature` only authenticates the org/app, not the repository-to-commit binding; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema in `StatusHandler.params` validates `sha`/`state`/`context` types but does not require or check `repository.full_name`; there is no `require_permission!`/`stacks` scope applied in this handler at all.

### Impact Explanation
A `status` payload authenticated for one repository writes a `Status` record for a `Commit` belonging to a completely different repository/stack, matching the "Critical: a payload for one repository mutating another's stack, commit ... " category. Depending on the victim stack's `required_statuses`/`blocking_statuses` configuration, this can force a commit to become blocked (denial of deploy) or, if the injected context happens to satisfy a required status, contribute to making a commit `deployable?` — i.e., cross-tenant state manipulation via `Commit#status`, `Commit#deployable?`, `Commit#blocked?`, and `Stack#schedule_merges`. The blast radius scales to every stack whose tracked repository shares the SHA, and this is repeatable for any SHA collision the attacker can produce or discover.

### Likelihood Explanation
The attacker needs no Shipit credentials, only the ability to trigger (or forge, if they hold a genuine app installation on a repo they control within the trusted organization/installation) a `status` webhook event, and a commit SHA that is shared between their repository and the victim's tracked repository. This second precondition is the limiting factor: it is not guaranteed for arbitrary repositories, but is realistic for forks, shared history, template-seeded repos, or engineered empty/boilerplate commits, especially within organizations that host many repos under one GitHub App installation. Given that constraint is met, exploitation is a single unauthenticated `POST /webhooks` request and is fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other bare-SHA lookups such as `Commit.by_sha`) to the repository that authenticated the webhook, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload)).where(sha: params.sha)`, requiring `repository.full_name` in the `params` schema and validating it against `stack.repository` before applying the status.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process only updates commits belonging to the authenticated repository" do
  victim_stack   = shipit_stacks(:shipit)          # tracks "shopify/shipit-engine"
  attacker_stack = create_stack(repository: "attacker/evil-repo")

  shared_sha = "a" * 40
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared")

  params = ExplicitParameters::Params.new(
    sha: shared_sha, state: "failure", context: "security/scan",
    repository: { full_name: "attacker/evil-repo" }
  )

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(params).call
  end

  # binding under test:
  # webhook.repository.full_name ("attacker/evil-repo") != victim_commit.stack.repository.full_name ("shopify/shipit-engine")
  # currently this equality is NOT checked, so the assertion above fails on unpatched code:
  # victim_commit.statuses.count changes even though repositories differ.
end
```
This demonstrates the missing binding: with the current unscoped `Commit.where(sha:)`, `victim_commit.statuses.count` increases despite the webhook being authenticated for `attacker/evil-repo`, confirming the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
