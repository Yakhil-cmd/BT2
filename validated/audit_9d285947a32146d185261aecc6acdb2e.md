### Title
Missing contract-expiration (TTL) re-validation in arbiter_contract status/unit/shared_address update handling allows a stale contract offer to be accepted and funded after expiry - (File: wallet.js, arbiter_contract.js)

### Summary
The arbiter-contract flow enforces a client-defined `ttl` (default 168 hours) only inside the `arbiter_contract_response` handler when the *initial* accept/decline is processed. Every subsequent state-mutating device message in the same protocol — `arbiter_contract_update` (status/unit/shared_address fields), and the resulting `handleReceivedSharedAddress`/`handleReceivedSigningUnit`/`pay` calls — omits this check entirely, so a peer (or a delayed/replayed message) can push an already-expired contract through acceptance, shared-address derivation, mutual signing, and funding.

### Finding Description
`wallet_arbiter_contracts.ttl` (default 168h) together with `creation_date` is meant to bound how long an offer is "live." The only place that enforces this is inside `processResponse` in the `arbiter_contract_response` case:
```
var objDateCopy = new Date(objContract.creation_date_obj);
if (objDateCopy.setHours(...,(objDateCopy.getSeconds() + objContract.ttl * 60 * 60)|0) < Date.now())
    return callbacks.ifError("contract already expired");
``` [1](#0-0) 

However, the protocol continues to progress a contract's status/derived data through a *different* message type, `arbiter_contract_update`, whose handler validates only sender identity and a hardcoded status-transition table (`pending`→`accepted`/`declined`, `paid`→`in_dispute`, etc.) with no TTL check: [6](#0-5) 
and for the `unit` / `shared_address` fields it only checks `objContract.status !== "accepted"` and whether the field was already set, again without any expiry check: [7](#0-6) 

Downstream, `handleReceivedSharedAddress` and `handleReceivedSigningUnit` in `arbiter_contract.js` derive the shared address and flip `status` to `"signed"` purely as a function of the stored contract row and the received message content, never consulting `ttl`/`creation_date`: [4](#0-3) 

Finally, `pay()` checks only `objContract.status !== "signed"` before composing and sending the funding payment to the shared address: [5](#0-4) 

This mirrors the Cobbler PAM advisory's root cause precisely: an authorization gate (initial accept/decline) enforces the "not expired" invariant, but every other gate that consumes the same authorized/accepted state (`arbiter_contract_update`, shared-address derivation, signing, payment) trusts the previously-set status without re-checking whether the credential (the contract offer) had already expired by the time these downstream actions execute — exactly the "trust cached, unrevalidated authorization state" pattern (CWE-285/863).

### Impact Explanation
A payer's wallet can be induced to finalize a shared multisig address, obtain mutual signatures, and transfer real base/asset funds (`objContract.amount`) into that shared address for a contract offer that both parties should treat as void because it outlived its stated `ttl`. Because none of `arbiter_contract_update`, `handleReceivedSharedAddress`, `handleReceivedSigningUnit`, or `pay` re-check expiry, a slow-walked or replayed sequence of legitimately-signed device messages (from the genuine counterparty device, no MITM needed) can complete funding of a contract the user believed had lapsed, causing unauthorized/uncancellable fund lock-up in a shared address the user did not intend to still be bound by. This is a concrete loss-of-funds/authorization-bypass scenario at the wallet layer, not merely a UX inconvenience.

### Likelihood Explanation
Likelihood is moderate: it requires the counterparty (or a device correspondent) to continue advancing the same `arbiter_contract_update`/`new_shared_address`/signing sequence after the TTL window closes, which is entirely plausible in normal asynchronous wallet-to-wallet flows (e.g., light wallets going offline and resuming, or a counterparty intentionally delaying responses to force completion of a deal the payer considers dead). No cryptographic bypass or privileged access is required — only continuing to send/relay otherwise-valid signed device protocol messages past the TTL boundary.

### Recommendation
Re-validate `ttl`/`creation_date` (or introduce a persisted "expires_at" and check it) at every state-mutating boundary of the arbiter-contract protocol, not just the initial `arbiter_contract_response` handler — specifically in the `arbiter_contract_update` handler (`wallet.js`), and in `handleReceivedSharedAddress`, `handleReceivedSigningUnit`, and `pay` (`arbiter_contract.js`), rejecting/auto-cancelling any transition once the contract has expired.

### Proof of Concept
1. Alice creates and sends an arbiter contract offer to Bob with `ttl` = 1 hour (`createAndSend`).
2. Bob's device is offline/delays and does not send `arbiter_contract_response` within the TTL window (so the `processResponse` TTL check in `wallet.js:909-914` is never exercised — that check only runs when a `response` message is actually processed).
3. After the TTL has elapsed, Bob's device instead directly emits an `arbiter_contract_update` message with `field: "status", value: "accepted"` (a legitimately signed device message from Bob), which Alice's wallet accepts because `arbiter_contract_update`'s handler only checks the status-transition table (`pending`→`accepted`), not TTL (`wallet.js:691-712`).
4. Protocol continues: shared address is derived/confirmed via `new_shared_address`/`arbiter_contract_update {field:"shared_address"}`, mutually signed via `arbiter_contract_update {field:"unit"}` → `handleReceivedSigningUnit`, none of which check TTL.
5. Alice's wallet calls `pay()`, which only requires `status === "signed"`, and transfers `objContract.amount` to the shared address — completing funding of a contract that had already expired.

function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});
			// listen for peer announce to withdraw funds
			storage.readAssetInfo(db, objContract.asset, function(assetInfo) {
				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});
}
