### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` vs `repository.full_name` in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, which is parsed directly out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . Shipit explicitly supports multiple, independently configured GitHub Apps/organizations, each with its own `webhook_secret`, selected by this same organization string [3](#0-2) .

Once the signature check passes, the actual target of the event (which `Stack`/`Repository` gets mutated) is determined by a *different* field of the same attacker-controlled payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name`/`#stacks` [4](#0-3) , or `params.repository.full_name` in the various handlers (`StatusHandler` looks commits up by `sha` globally across all repos, `PushHandler`, pull-request handlers, etc.) [5](#0-4) .

The code never checks that `repository.owner.login` (used to pick the signing secret) is consistent with `repository.full_name`'s owner segment (used to pick the target repository/stack). Because the entire raw body is HMAC-signed with *the secret belonging to whichever organization the attacker names in `repository.owner.login`* [6](#0-5) , any actor who legitimately administers **their own** organization's Shipit GitHub App (and therefore knows/controls their own org's `webhook_secret`, a normal, unprivileged part of the documented multi-org setup) can construct a fully self-signed payload where `repository.owner.login` = their own org (so `verify_signature` selects and validates against their own known secret) while `repository.full_name` = `"victim-org/victim-repo"` (so the handler operates on a stack that belongs to a different organization).

This breaks the intended binding: *the organization that authenticated the webhook* must equal *the organization whose repository is written to*.

### Impact Explanation
Because `StatusHandler` resolves target commits purely by `sha` with no repository/stack scoping check at all (`Commit.where(sha: params.sha)`), a forged `status` event, once signed with any onboarded org's own secret, can inject a fabricated commit status (e.g., a fake "success" CI check) onto a commit belonging to an entirely different stack/repository [7](#0-6) . Since Shipit's continuous-deployment/merge logic gates deploys and merges on required CI statuses (`ci.require`) being green, this can be used to unblock or trigger an unauthorized deploy or merge on a stack the attacker does not own or have credentials for, satisfying the "unauthorized deploy/merge" critical-impact bar. Handlers that key off `repository.full_name` (push, pull-request events) are similarly reachable for any org onboarded to the same Shipit instance, letting an attacker who controls one tenant/org spoof events as if originating from another tenant's repository.

### Likelihood Explanation
This requires the attacker to be an administrator of at least one legitimately configured organization on a multi-org Shipit deployment (a normal, unprivileged position relative to any *other* tenant's repositories) — no GitHub push access, Shipit session, or API token for the victim repo is needed. Given that `docs/setup.md` explicitly documents and encourages multi-org configurations sharing one Shipit instance, this is a realistic deployment shape, and the only barrier is knowledge of one's own org's webhook secret, which the attacker inherently possesses.

### Recommendation
In `WebhooksController`/`Handler`, after verifying the signature for the selected `repository_owner`, validate that the same field used for signature-secret selection (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` (and any other repository identifiers the handlers use) before processing the event. Alternatively, derive the signing organization strictly from the same canonical field the handlers use for repository resolution, so there is a single source of truth instead of two independently trusted fields.

### Proof of Concept
1. Attacker's org `attacker-org` has its own GitHub App configured in Shipit's `secrets.yml` with `webhook_secret: S1` (legitimate, self-administered, per `docs/setup.md` multi-org instructions).
2. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` using their own known secret `S1`.
4. POST to `/github/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature against `S1` [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and writes a fabricated "success" status onto the victim's commit, regardless of `repository.full_name` mismatching the authenticating org [7](#0-6) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
