**Rationale:**

The scenario in `StandardGasAlgebra::new` (`aptos-move/aptos-gas-meter/src/algebra.rs`, lines 84-101) computes `max_execution_gas`/`max_io_gas` via `saturating_mul` with the requested multiplier, but this path is gated by an explicit bounds check that runs earlier in `TransactionMetadata::new` (`aptos-move/aptos-vm/src/transaction_metadata.rs`, lines 104-126): [1](#0-0) 

```
const MIN_MULTIPLIER_PERCENT: u64 = 100; // 1x
const MAX_MULTIPLIER_PERCENT: u64 = 10000; // 100x

let m = request.multipliers();
if m.execution_multiplier_percent() <= MIN_MULTIPLIER_PERCENT
    || MAX_MULTIPLIER_PERCENT < m.execution_multiplier_percent()
    || m.io_multiplier_percent() <= MIN_MULTIPLIER_PERCENT
    || MAX_MULTIPLIER_PERCENT < m.io_multiplier_percent()
{
    return Err(VMStatus::error(
        StatusCode::INVALID_HIGH_TXN_LIMITS_MULTIPLIER,
        ...
    ));
}
``` [2](#0-1) 

Any `TxnLimitsRequest::Staking` multiplier outside the `(100, 10000]` range (i.e. `(1x, 100x]`) is rejected with `INVALID_HIGH_TXN_LIMITS_MULTIPLIER` before `TransactionMetadata` is even built, so `StandardGasAlgebra::new` never sees an "extreme" multiplier from unprivileged input. The comment explicitly notes this runs "before the prologue & gas meter creation, preventing the meter from operating with a 0, nonsensical, or overflowing limit," and that "the Move prologue additionally validates that the multiplier exists in the on-chain config" [3](#0-2) .

Additionally, `saturating_mul` by design cannot overflow/wrap — it clamps to `u64::MAX` rather than corrupting the value via wraparound, so even a hypothetically unbounded multiplier could not produce a smaller-than-intended limit that would "bypass" the execution/IO gas limit check; it can only ever produce a value that is capped, not underflowed [4](#0-3) .

Finally, this code path concerns gas-limit computation for an already-authenticated, already-admitted transaction; it does not touch sender/signer binding, sequence number, expiry, chain-id, or replay-protection logic, which are the required impact categories for this admission-review scope (sender, signer, replay, or domain guarantees). Since both the numeric bound (capped at 100x) and the on-chain config validation via the Move prologue already converge correctly to prevent this, there is no valid admission-bypass finding here.
