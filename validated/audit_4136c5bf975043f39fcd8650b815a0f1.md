### Title
Webhook signature verified against attacker-controlled organization while handlers act on an unverified `repository.full_name` from a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook based on `repository.owner.login` (or `organization.login`), a field taken directly from the unverified request body, and then verifies the whole payload's signature against that org's `GitHubApp#webhook_secret`. Every event handler, however, resolves which `Repository`/`Stack` to act on using a *different* field of the same unverified body: `repository.full_name`. Nothing binds the two fields together, so a request that is legitimately signed for organization A can carry a `repository.full_name` pointing at organization B's repository, and the handler will act on B while the signature only ever proved authenticity for A.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body and fetches the per-organization secret to check against `X-Hub-Signature`: [1](#0-0) 

Multi-tenant Shipit deployments explicitly support one distinct GitHub App (and thus one distinct `webhook_secret`) per organization, configured under `github.<org>` in `secrets.yml`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` does a straightforward HMAC compare of the raw body against whichever org's secret was selected: [3](#0-2) 

After the signature check passes, `create` dispatches the *entire unverified* params hash to the handler for the event: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from `repository.full_name`, a completely independent field from the one used to pick the verification secret: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` looks up the DB record purely by the owner/name parsed out of `full_name`, with no cross-check against the organization whose secret validated the request: [7](#0-6) 

The binding that should hold is: `organization used to verify signature == organization of the repository the handler mutates`. Before an attacker's request, this equality holds naturally because GitHub always sends `repository.owner.login` and `repository.full_name` consistent with the real event. After a forged request from an org admin who legitimately controls their own onboarded GitHub App/secret (organization A) but sets `repository.full_name` to `B/some-repo` (organization B, a different tenant on the same Shipit instance), the signature check passes using A's secret while `PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, etc. all operate on B's `Stack`/`Repository`/`ReviewStack` records — e.g. triggering `stack.sync_github(expected_head_sha: params.after)` on B's stack, creating commits/statuses on B's commits, or auto-provisioning review stacks under B's repository via `ReviewStackAdapter`.

### Impact Explanation
This breaks the tenant isolation the multi-organization webhook secret feature is meant to provide: a party who is only authorized (has only a validly configured GitHub App/secret) for their own organization can forge webhook events that are accepted as authentic and then applied to another organization's stacks. Depending on the handler reached this can drive `GithubSyncJob`/commit creation, fake CI `status` records that unblock merges, or spurious `ReviewStack` provisioning/pull_request state changes on a victim repository the attacker has no access to — i.e. cross-repository writes/state changes attributable to a webhook that was never actually sent by GitHub for that repository.

### Likelihood Explanation
Requires only that the attacker legitimately controls (and has correctly configured within this Shipit instance) a GitHub App for *some* organization — the documented multi-tenant setup explicitly anticipates multiple, mutually distrusting organizations sharing one Shipit instance. No GITHUB_TOKEN, ApiClient token, session, or victim-side credential is needed; only knowledge of the attacker's own webhook secret, which they possess by design.

### Recommendation
Bind the signature-selection organization to the same organization that the handler is permitted to act on: after `verify_signature` resolves `repository_owner`, re-derive/assert that `params.dig('repository','full_name')`'s owner segment matches `repository_owner` (and reject otherwise) before dispatching to handlers, or select/validate the secret using the same `full_name`-derived owner used later by `Repository.from_github_repo_name`, rather than the independently-specified `repository.owner.login`/`organization.login` field.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md` "Using Multiple GitHub Applications") with two tenants: `OrgAttacker` (attacker's own GitHub App/installation, `webhook_secret: secretA`, known to the attacker) and `OrgVictim` (a different customer/org, `webhook_secret: secretV`, unknown to the attacker), each with stacks tracking their own repos.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` using their own known secret and sends it with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgAttacker"`, fetches `Shipit.github(organization: "OrgAttacker")`, and the HMAC check succeeds because the attacker signed with `secretA` [1](#0-0) .
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name = "OrgVictim/victim-repo"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `OrgVictim`'s stack [6](#0-5) , even though the request was never signed by, nor originated from, `OrgVictim`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
