This confirms the multi-org configuration model: `Shipit.github(organization:)` looks up per-organization config (including a distinct `webhook_secret`) via `github_app_config` [1](#0-0) , and `WebhooksController#verify_signature` selects which organization's app (and thus secret) to verify against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')` [2](#0-1) . Meanwhile, all webhook handlers determine which `Stack`/`Repository` to act on using a *different* field, `payload.dig('repository', 'full_name')` [3](#0-2) , and dispatch happens unconditionally after signature check via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

### Title
Webhook signature verified against `repository.owner.login`'s org secret while handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack manipulation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-organization Shipit deployment (each org has its own `github.<org>.webhook_secret` as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`), the webhook signature check and the webhook processing logic key off two different JSON fields from the same untrusted request body, breaking the intended binding "organization whose secret authenticated the request == repository the request is allowed to mutate."

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config (and its `webhook_secret`) using only `repository_owner`: [5](#0-4) 
That value is looked up with `Shipit.github(organization: repository_owner)`, which resolves per-org secrets from `secrets.github` [1](#0-0) .

However, once the HMAC check passes, `create` parses the same raw JSON and dispatches it to every registered handler for the event without re-checking `repository.owner.login`: [4](#0-3) 

Every handler then resolves the target repository/stack using `payload.dig('repository', 'full_name')`, e.g. the base `Handler#stacks`/`#repository_name` [3](#0-2) , and `PushHandler#process`, which calls `sync_github` on every matching stack [6](#0-5) .

Because `repository.owner.login` (used for the signature) and `repository.full_name` (used for dispatch) are independent, attacker-controlled fields in the same JSON body, an attacker who possesses (or can produce) a valid signature for organization A — e.g. because they hold that org's `webhook_secret`, either leaked or because they are a legitimate GitHub App/webhook holder for a small, low-trust org that Shipit also manages — can craft a payload where `repository.owner.login` = "OrgA" (satisfies the signature check) but `repository.full_name` = "OrgB/some-other-repo" (a different, more sensitive organization/repo also configured in the same Shipit instance). The signature check passes using OrgA's secret, yet the handler acts on OrgB's stack.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose webhook secret authenticated the request" and "the repository whose stacks get written to." Depending on the event type this enables: enqueuing `GithubSyncJob` for a foreign stack, archiving/unarchiving review stacks (`PullRequest::ClosedHandler`/`ReopenedHandler`), or capturing labels — i.e., cross-organization writes to state (`Stack`, `PullRequest`, review stacks) that the attacker's organization is not entitled to touch. This matches the "cross-repository writes" Critical impact category, since a request authenticated for one org's webhook boundary results in mutation of a completely different org/repo's Shipit-managed resources.

### Likelihood Explanation
Exploitability requires the attacker to already control a valid `webhook_secret` for at least one organization configured on the shared Shipit instance (a realistic scenario for a Shipit install that manages many orgs/repos with per-org apps, since compromise or misconfiguration of any single org's webhook secret is enough). No repository write access, API token, or GitHub App private key for the *target* org is required — only the ability to sign an arbitrary POST body with someone else's org secret and freely choose a mismatched `full_name`/`owner.login` pair, which nothing in `WebhooksController` or the handlers prevents.

### Recommendation
Cross-validate that `repository.full_name`'s owner segment matches the `repository.owner.login` (or `organization.login`) that was used to select the signing secret before invoking any handler, e.g. re-derive `repository_owner` from `full_name` and assert equality, or refuse events where the two disagree.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org example).
2. Attacker obtains/knows `OrgA`'s `webhook_secret` (e.g., a leaked secret for a low-trust org).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/sensitive-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and passes the check [7](#0-6) .
6. `PushHandler#process` looks up stacks via `Repository.from_github_repo_name("OrgB/sensitive-repo")` and triggers `sync_github` on OrgB's stack [6](#0-5) , even though the signature never involved OrgB's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
