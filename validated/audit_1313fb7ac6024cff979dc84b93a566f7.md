### Title
Headers-commission split rounding can inflate total byte supply - (File: headers_commission.js)

### Summary
When a unit's `headers_commission` is shared among multiple `earned_headers_commission_recipients`, each recipient's portion is computed independently with `Math.round()` and there is no reconciliation of the rounding remainder against the original `headers_commission` amount. A unit poster who defines the `earned_headers_commission_recipients` field on their own unit (an authenticator-controlled, per-unit field) can pick recipient shares that make the sum of the independently-rounded portions exceed the actual commission amount, creating extra spendable bytes out of thin air every time that unit's descendants trigger a headers-commission payout.

### Finding Description
`calcHeadersCommissions()` splits a payer unit's `headers_commission` (an integer number of bytes) among the addresses listed in `assocEarnedHeadersCommissionRecipients` for the winning child unit. This field is populated from `earned_headers_commission_recipients`, which is set by the **author of the unit itself** and is only constrained (elsewhere in validation) to have shares that sum to 100.

For each recipient the code computes: [1](#0-0) 

and, in the SQL/mysql path, the same rounding is applied per row: [2](#0-1) 

Because `Math.round(full_amount * share / 100.0)` is applied to each recipient **independently**, and the shares are chosen by the unit's author, the sum `Σ Math.round(full_amount * share_i / 100.0)` is not guaranteed to equal `full_amount`. There is no clamp, no "give the remainder to the last recipient" logic, and no check that `Σ amounts == full_amount` before the values are inserted into `headers_commission_contributions`.

Example: with `full_amount = 3` and two recipients each with `share = 50`, `Math.round(3 * 0.5) = 2` for each recipient, so `2 + 2 = 4` bytes are created from a commission of only `3` bytes — one byte of pure inflation. By repeating this pattern across many small headers-commission payouts (which recur every time the unit or its descendants win a headers commission from a parent unit) and across many attacker-controlled recipient addresses, an attacker can systematically extract more bytes than were actually earned.

These contributions are later inserted directly into the `headers_commission_contributions` table and become spendable `headers_commission`-type inputs via `mc_outputs.calcEarnings()` / `pickDivisibleCoinsForAmount` → `addHeadersCommissionInputs()`, so the extra bytes are fully spendable, not merely an accounting artifact: [3](#0-2) [4](#0-3) 

The insertion itself happens without any sum/remainder check: [5](#0-4) 

### Impact Explanation
This allows unauthorized inflation of the byte supply. Because every full node computes the same deterministic rounding, all nodes agree on the (incorrect) split — there's no consensus split/fork, but the supply itself grows beyond what was actually paid by the fee-paying (parent) unit. An attacker who controls the `earned_headers_commission_recipients` field of units that repeatedly win headers commissions (which is trivial — headers commission is won essentially at random among children of a parent, and the winner's own recipient list is attacker-controlled) can accumulate systematic rounding-up gains over time, extracting bytes that were never actually paid by any spender. This is a supply-inflation bug, not a resource-only/DoS issue.

### Likelihood Explanation
Likelihood is moderate-to-high: `earned_headers_commission_recipients` is a standard, unprivileged field any unit author can set on their own unit, headers-commission winning happens continuously as part of normal DAG progression, and the rounding-up condition (shares whose fractional remainders sum above 0.5 collectively) is easy to construct deliberately (e.g., two 50/50 recipients on odd-valued commissions, or more sophisticated multi-recipient splits for larger gains). The attacker needs no special privilege beyond being a normal unit poster.

### Recommendation
Do not round each recipient's share independently. Instead:
- Compute all recipients' raw (unrounded) shares of `full_amount`, round using floor for all but the last recipient, and assign the exact remainder (`full_amount - Σ floored amounts`) to the last recipient (or use largest-remainder/Hamilton's method) so `Σ amounts` always equals `full_amount` exactly.
- Add an explicit assertion (as is already done elsewhere in the code, e.g., `throwError` on mismatches) that the summed contributions equal `full_amount` before inserting into `headers_commission_contributions`, in both the RAM and SQL code paths.

### Proof of Concept
1. An attacker posts a unit A with `earned_headers_commission_recipients = [{address: X, earned_headers_commission_share: 50}, {address: Y, earned_headers_commission_share: 50}]` (sum = 100, passes validation).
2. Unit A becomes the "winner" of a headers commission of `full_amount = 3` bytes from some parent unit (headers commissions are typically small integers, e.g. per-unit `headers_commission` values in the hundreds range, so odd values naturally occur).
3. `calcHeadersCommissions()` computes for X: `Math.round(3*50/100) = 2`, and for Y: `Math.round(3*50/100) = 2`, inserting `2 + 2 = 4` bytes total into `headers_commission_contributions` for a commission that was only `3` bytes.
4. X and Y later spend these `headers_commission`-type inputs normally via `pickDivisibleCoinsForAmount` → `addHeadersCommissionInputs`, realizing 1 extra byte of value that was never paid by any unit — repeatable indefinitely to inflate the total byte supply.
