### Title
`StatusHandler` mutates commit statuses across unrelated stacks/repositories because it never scopes to the payload's `stacks` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever calling the inherited `Handler#stacks` to restrict the operation to the repository named in the payload. Any signed `status` webhook whose SHA happens to collide with a `Commit` row belonging to a different stack will write attacker-controlled status data (`state`, `description`, `target_url`, `context`) into that unrelated stack.

### Finding Description
The binding that should hold is: `commits_mutated_by_request == Commit.where(sha:).merge(stacks)` where `stacks == Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` (as implemented for every other handler, e.g. `PushHandler`). Instead the actual code is: [1](#0-0) 

which performs a **global**, unscoped `Commit.where(sha: params.sha)` lookup and mutates every matching row via `Commit#create_status_from_github!`: [2](#0-1) 

`Handler#stacks` exists precisely to bind a webhook to the repository that GitHub says it came from: [3](#0-2) 

but `StatusHandler` never invokes it, so nothing ties the mutated `Commit` rows back to `repository_name` in the payload.

`WebhooksController#verify_signature` only proves the request came from GitHub for the organization named in `payload.dig('repository','owner','login')`; it does not - and cannot - restrict *which repository's commits* the handler is allowed to touch: [4](#0-3) 

Exploit flow: attacker controls (or has commit-status-setting rights on) any repository whose owning GitHub organization is already configured in `Shipit.github_organizations`/App installation (this need not be one of the target stacks). They engineer a commit whose full SHA collides with a `Commit` row already stored for an unrelated stack (feasible when repos share ancestry via templates/forks/monorepo splits, or by reproducing identical tree/parent/author/committer timestamps with `git commit-tree`). They then cause GitHub to deliver (or otherwise produce a validly signed) `status` event referencing that SHA. `StatusHandler.call` finds every `Commit` row across every stack/repository with that SHA and calls `create_status_from_github!(params)` on each, writing the attacker's chosen `state`/`description`/`target_url` into `Status` rows owned by stacks the attacker never touched. This can flip a target stack's commit status (e.g., to `success`), which per `Commit#add_status`/`#schedule_continuous_delivery` and `Stack#continuous_deployment?` can unblock/trigger continuous deployment of that unrelated stack.

No existing guard prevents this: the `ExplicitParameters` schema only validates field shapes, `verify_signature`/`drop_unhandled_event` only authenticate the webhook's origin (organization), and neither validates that the mutated `Commit` rows belong to the repository named in the payload - unlike sibling handlers that call `stacks`.

### Impact Explanation
A single verified webhook request can write to `Status` rows for every stack that happens to contain a `Commit` with the colliding SHA, not just the stack corresponding to the payload's repository. This is a cross-tenant write: one repository's webhook mutates another repository's/stack's commit-status data, and because `Commit#add_status` can trigger `stack.schedule_merges` and `ContinuousDeliveryJob` when the new status becomes `success`, this can influence an unrelated stack's deploy pipeline. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Blast radius is every stack in the database sharing the colliding SHA, and the attack is repeatable per distinct SHA/target.

### Likelihood Explanation
The attacker needs: (1) the ability to send a validly signed `status` webhook for some repository whose organization/App installation matches one configured in Shipit (this can be any repo in that org - not necessarily one of the victim stacks), and (2) a `Commit` row in a target stack sharing the exact SHA. Producing an exact commit SHA collision against an arbitrary unrelated commit is hard in general (SHA-1 preimage), but the scenario described (shared ancestry via forks/templates, or deliberately reproducing identical tree/parent/author/committer/timestamp via `git commit-tree` when those fields are known/public) is a realistic, non-cryptographic collision path that doesn't require breaking SHA-1. Given that, this is feasible but conditioned on organizational/webhook-secret proximity and knowledge of a target commit's exact metadata - moderate-to-low likelihood but a genuine code defect (missing repo scoping) independent of how the SHA collision is achieved.

### Recommendation
Scope `StatusHandler#process` to the payload's repository, mirroring other handlers: use `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the unscoped `Commit.where(sha: params.sha)`, so only commits belonging to stacks of `Repository.from_github_repo_name(repository_name)` are updated.

### Proof of Concept
minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (not currently present per this scope, but illustrating the assertion):
1. Create `repository_a`/`stack_a` and `repository_b`/`stack_b` (different `Repository#full_name`s, e.g. `owner/a`, `owner/b`).
2. Create `Commit.create!(stack: stack_a, sha: SHA)` and `Commit.create!(stack: stack_b, sha: SHA)` with the same `SHA`.
3. Build a `status` webhook payload with `repository.full_name = "owner/a"` and `sha: SHA`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `stack_a.commits.find_by(sha: SHA).statuses.count == 1` (expected, correct) AND `stack_b.commits.find_by(sha: SHA).statuses.count == 0` (this assertion FAILS on current code - `stack_b`'s commit also gets a `Status` row created), demonstrating that the binding "one webhook request mutates exactly one stack's commit" is broken.
