### Title
Open redirect via unvalidated `omniauth.origin` in OAuth callback - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` redirects to `request.env['omniauth.origin']` with no validation that its host matches the Shipit host, so an attacker-supplied `origin` query parameter on the OAuth request phase is echoed back verbatim after a successful login, redirecting the victim's browser to an arbitrary external site immediately after completing GitHub OAuth with Shipit.

### Finding Description
The binding that should hold is `URI(return_url).host == request.host` (or `return_url` must be a same-origin/relative path); this does not hold anywhere in the code. `return_url = request.env['omniauth.origin'] || root_path` is used directly in `redirect_to(return_url)` with zero host/scheme checks [1](#0-0) .

`omniauth.origin` is populated by the OmniAuth gem itself: during the request phase (`/github/auth/github`), OmniAuth reads the `origin` request parameter (or referer) and stores it in the session; on the callback it is restored into `request.env['omniauth.origin']`. The engine's own `force_github_authentication` before_action already demonstrates that this `origin` parameter is attacker-reachable and expected to be a URL, since it builds the same query param itself: `redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))` [2](#0-1) . Nothing in this code path restricts `origin` to Shipit's own host — an attacker can supply `/github/auth/github?origin=https://attacker.example` directly as a link to a victim.

Attack flow: attacker sends victim a link to `/github/auth/github?origin=https://attacker.example`; victim, already having a Shipit account, follows it and authorizes GitHub OAuth; `callback` fires, sets `session[:user_id]`/`session[:authenticated]`, then executes `redirect_to('https://attacker.example')`, sending the victim's browser off-site immediately after completing authentication with Shipit.

No existing guard intercepts this: `force_github_authentication` only triggers the redirect that constructs the `origin` param and does not validate it on the way back; `sign_in_github`/`session[:authenticated]` handling in `callback` has no host check either [3](#0-2) . The existing test suite for this controller does not set or assert on `omniauth.origin` at all [4](#0-3) , confirming this behavior is untested and unguarded.

### Impact Explanation
The vulnerability is a same-engine open redirect: any unauthenticated internet user can craft a link that, once clicked by a logged-in-or-logging-in victim, redirects the victim's browser to an attacker-controlled domain right after OAuth completion. This matches the "session fixation / forced OAuth completion" category defined as High impact. It is fully repeatable against any victim who clicks the crafted link and does not require any Shipit secret, GitHub App key, or privileged role. It does not directly leak the Shipit session cookie (cookies remain host-scoped), but it enables phishing pretexts (e.g., a fake "re-authenticate" or "session expired" page on attacker infrastructure) immediately following a real, trusted Shipit login flow, which is the documented High-severity class for this finding.

### Likelihood Explanation
Preconditions are minimal: no Shipit configuration is required beyond the engine being mounted with OmniAuth as documented, and no secrets or privileged roles are needed. The attacker only needs to send a URL to a victim who has (or is willing to create) a GitHub account and will click through the OAuth flow; GitHub's own consent screen is legitimate, so the attack is not blocked by GitHub. Attacker cost is a single crafted link; the exploit is trivially repeatable against any number of victims.

### Recommendation
Validate `return_url` before redirecting: reject or fall back to `root_path` unless the URL is relative (no scheme/host) or its host exactly matches `request.host`/`Shipit.host`. For example:
```ruby
def callback
  return_url = safe_return_url(request.env['omniauth.origin'])
  ...
  redirect_to(return_url)
end

private

def safe_return_url(url)
  return root_path if url.blank?
  uri = URI.parse(url) rescue nil
  return root_path unless uri && (uri.host.nil? || uri.host == request.host)
  url
end
```
Also apply the same allow-list check wherever `origin` is generated/consumed (e.g. `force_github_authentication`) to ensure only same-host values are ever passed through OmniAuth.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback redirects to attacker-controlled origin (open redirect)" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example/phish'

  get :callback

  # Binding under test: return_url host should equal request.host, but does not.
  assert_not_equal URI.parse(response.location).host, @request.host
  assert_redirected_to 'https://attacker.example/phish'
end
```
