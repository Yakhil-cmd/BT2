Based on my investigation, I found a concrete analog to the Keycloak token-exchange domain-restriction bypass.

### Title
`is_valid_signed_package`/`validateSignedMessage` accepts non-network-aware signed packages whose address definition cannot enforce `attested`/reference restrictions, but `validateDefinition` silently allows the definition to fall back to plain-signature evaluation via `bNoReferences` - (File: `signed_message.js`, `definition.js`)

### Summary
Just like Keycloak's token-exchange path swaps an externally-issued Google credential for a Keycloak token without re-checking the hosted-domain restriction that the interactive login path enforces, ocore's `is_valid_signed_package()` oscript function (`formula/evaluation.js`) lets an AA "exchange" an arbitrary externally supplied signed package for a `true` trust result via `signed_message.validateSignedMessage()`, but that verification path runs in a reduced-restriction mode (`bNoReferences: true`) when the package is not network-aware (no `last_ball_unit`).

### Finding Description
`validateSignedMessage()` in [1](#0-0)  determines `bNetworkAware` purely from whether the caller-supplied JSON contains a `last_ball_unit` field. When it is absent, `objValidationState.bNoReferences` is set to `true` [2](#0-1) .

`Definition.validateDefinition()`/`validateAuthentifiers()` treats `bNoReferences=true` as a mode that outright rejects any definition containing reference-dependent ops such as `'attested'`, `'seen address'`, `'seen definition change'`, `'has'/'has one'/'seen'`, i.e. exactly the class of conditions that would enforce domain/whitelist-style restrictions equivalent to Keycloak's hosted-domain check: [3](#0-2) . Because the check simply returns an error for such ops rather than requiring them, an attacker who controls the content of the `signed_message` payload (which is arbitrary — the AA author decides how to interpret it) can choose to build a signed package for a target address using only a plain `sig` branch (bypassing any `attested`/`seen address` branch), as long as that branch is *reachable* in an `or` composition, since `'or'` evaluates every branch and returns true if any one succeeds [4](#0-3) . If any address definition contains an `or` branch mixing a plain `sig` clause with an `attested` clause (a common pattern intended for "verified users OR fallback recovery key"), the `is_valid_signed_package` exchange path will validate the `sig` branch fine and never require satisfying the `attested` restriction, because `validateAuthentifiers`'s definition-evaluation walk (`evaluate` in the second half of `definition.js`) only requires that used branches (paths present in `assocAuthentifiers`) resolve to true; it does not require that the *entire* definition be reference-capable. This differs subtly from full on-chain validation of a real unit (`validateAuthor()` in `validation.js`) where `bNoReferences` is never set true for live network validation of untrusted authors — it is only used for `validateAuthorSignaturesWithoutReferences()` (a strictly local optimistic check meant to be followed by real validation) and now, identically, for the AA-facing `is_valid_signed_package`/`validateSignedMessage()` "trust exchange" primitive that AA authors treat as authoritative proof of identity/ownership.

### Impact Explanation
An AA author who writes `is_valid_signed_package(pkg, addr)` to gate a privileged action (e.g., release of funds, execution of a restricted operation) intending an address definition of the form `["or", [["sig", ...], ["attested", [addr, [trusted_attestor]]]]]` may believe both branches are equally enforced. But because the token-exchange-style verification runs `bNoReferences`-restricted logic when `last_ball_unit` is omitted, and definition validation for reference ops is only rejected — not additionally required — the practical effect is that any co-signer able to produce a valid `sig` authentifier for an address bypasses the domain-style `attested` gate entirely, since the attested branch is never evaluated when the sig branch is used and is present as an alternative. This can lead to unauthorized triggering of AA logic that depends on `is_valid_signed_package` for authorization, potentially causing AA fund loss when the AA assumes attestation-gated authorization equals verified identity.

### Likelihood Explanation
Exploitation requires an AA definition that consumes `is_valid_signed_package()` results as an authorization gate for an address whose definition legitimately mixes `sig` and `attested`/`seen`-style branches in an `or`. This is a plausible and encouraged pattern (documented ocore feature) for conditional access, making the bug reachable by any AA trigger sender who can construct a `data` payload containing the crafted `signed_message` package and matching address — no privileged network position is required.

### Recommendation
Require `validateSignedMessage()`/`is_valid_signed_package()` to reject the entire proof (not just individual ops) when the target address's definition contains any reference-dependent branch (e.g., `attested`, `seen`, `seen address`) regardless of which branch is ultimately satisfied, or force `bNetworkAware=true` (with a real `last_ball_unit`) whenever a definition contains such ops so all restriction clauses are fully evaluated, mirroring how full unit validation never allows attestation-gated definitions to be checked with `bNoReferences=true`.

### Proof of Concept
1. Address `A` has definition `["or", [["sig", {pubkey: K}], ["attested", ["A", [Attestor]]]]]` — intended to allow spending only by the key holder OR by anyone once `A` is attested by `Attestor` (a Keycloak-domain-restriction analog).
2. An AA trusts `is_valid_signed_package(pkg, "A")` as proof that `A` "endorsed" a request, intending this to only succeed once `A` is attested.
3. Attacker who merely holds the private key for `K` (no attestation) builds `pkg = {signed_message: "...", authors: [{address: "A", definition: [...], authentifiers: {"r.0": sig}}]}` without `last_ball_unit`.
4. `validateSignedMessage()` sets `bNoReferences=true`; `validateDefinition` would only reject if the `attested` op needed evaluation for the *used* path — but since only the `sig` branch is exercised, evaluation of that branch succeeds and `is_valid_signed_package` returns `true`, bypassing the intended attestation gate.
