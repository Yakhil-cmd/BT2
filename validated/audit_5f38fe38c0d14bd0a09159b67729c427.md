### Title
`Handler#stacks` binds only by `payload['repository']['full_name']` with no cross-check against the HMAC-verified `repository_owner`, enabling cross-tenant writes whenever any configured GitHub org has no `webhook_secret` - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects a `GitHubApp` by `repository_owner` (`payload.dig('repository','owner','login')`) and checks the signature against *that org's* `webhook_secret`, but `Handler#stacks` resolves the target repository purely from `payload.dig('repository','full_name')` with no assertion that `Repository.from_github_repo_name(full_name).owner == repository_owner`. Combined with `GitHubApp#verify_webhook_signature` returning `true` unconditionally when `webhook_secret` is blank/nil (the documented default for a fresh installation), an attacker who can reach `POST /webhooks` can pick any org lacking a configured secret as `repository.owner.login` to pass verification, then set `repository.full_name` to any other tenant's `owner/repo` to make every push/status/check_suite/pull_request handler act on that victim's stacks.

### Finding Description
Binding claimed to hold: `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner == repository_owner` where `repository_owner` is the value HMAC-verified in `WebhooksController#verify_signature`.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner` from the payload itself (`params.dig('repository','owner','login')`), then does `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature(signature, raw_post)` [1](#0-0) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is absent: `return true unless webhook_secret` [3](#0-2) . A blank `webhook_secret` is the documented default/optional state (`webhook_secret: # nil` in `config/secrets.development.example.yml` and `docs/setup.md`, and `null` in `test/dummy/config/secrets.test.json`).
- `Handler#stacks` and `#repository_name` never read `repository_owner`; they resolve strictly from `payload.dig('repository','full_name')`: `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) .
- `Repository.from_github_repo_name` splits that `full_name` string on `/` to derive `owner`/`name` and does a straight `find_by`, with no relation back to whatever value was used to select the `GitHubApp`/secret in the controller [5](#0-4) .

Because these two lookups (`repository_owner` for signature/org selection, `repository.full_name` for stack resolution) are read from two independent JSON keys inside the same attacker-supplied `raw_post`, nothing forces them to agree. Attack request: attacker (holding no secrets at all) POSTs to `/webhooks` with header `X-Github-Event: push` (or `status`, `check_suite`, any `pull_request` action) and a body such as:
```json
{
  "repository": { "owner": {"login": "org-with-no-secret"}, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
If `Shipit.github(organization: 'org-with-no-secret')` has no `webhook_secret` configured, `verify_webhook_signature` short-circuits `true` regardless of the (even absent) `X-Hub-Signature` header. The request proceeds to `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }`, and `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` against `victim-org/victim-repo`'s stacks — a repository/org the attacker never authenticated for [6](#0-5) .

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type is handled; `check_if_ping` only special-cases `ping`; `ExplicitParameters` schemas (e.g. in `PushHandler`, `StatusHandler`) only validate presence/type of fields like `ref`/`after`/`sha`, never cross-field consistency between `repository.owner.login` and `repository.full_name` [7](#0-6) [8](#0-7) .

### Impact Explanation
An attacker can trigger `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, or any `PullRequest*Handler` against an arbitrary victim stack/repository they never authenticated for — writing commit status, triggering `sync_github`, refreshing check runs, or manipulating merge-queue/PR state for a repository belonging to a different tenant. This is a payload-for-one-repository-mutating-another's-stack scenario, matching the Critical impact category (cross-tenant write). The precondition is that at least one org configured in Shipit's multi-org (or the single default) GitHub config has no `webhook_secret` set — a state explicitly presented as optional/default in the project's own setup documentation and example/test secrets files, so it is a realistic operational configuration, not a contrived edge case. The blast radius spans every handler subclassing `Handler`, since all of them resolve their target exclusively via `payload['repository']['full_name']`.

### Likelihood Explanation
Feasibility hinges entirely on whether any onboarded GitHub organization is running with `webhook_secret` unset. The default templates (`config/secrets.development.example.yml`, `docs/setup.md`'s "(optional)" wording, `test/dummy/config/secrets.test.json`) all show `webhook_secret: nil` as an acceptable/typical state, so this is not a hypothetical misconfiguration — it's the documented default until an operator explicitly fills it in. Given that state, the attack costs nothing beyond a single unauthenticated HTTP POST with a crafted JSON body; it is fully repeatable against any stack/repository the attacker can name, with no rate limiting or other in-scope-relevant obstruction found in this code path.

### Recommendation
In `Handler#stacks`/`#repository_name`, cross-check that the repository's owner matches the `repository_owner` that was HMAC-verified for the request (pass the verified owner from the controller into the handler and assert `Repository.from_github_repo_name(repository_name)&.owner == verified_owner` before resolving stacks). Separately (and independently critical), `GitHubApp#verify_webhook_signature` should not treat a blank `webhook_secret` as an automatic pass — either require `webhook_secret` presence for orgs receiving webhooks, or reject the request when unset instead of returning `true`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/handler_test.rb`), no live GitHub:
1. Stub two orgs in `Shipit.github`: `org_a` with `webhook_secret: nil`, `org_b` with a real `webhook_secret` and an existing `Stack` for `shipit_repositories(:example)` under `org_b`.
2. Build a push payload: `repository.owner.login = "org_a"`, `repository.full_name = "org_b/example"`, `ref = "refs/heads/master"`, `after = <fresh sha>`. Send with `X-Github-Event: push` and no (or garbage) `X-Hub-Signature`.
3. Assert `response` is `:ok` (i.e., `verify_signature` did not reject it) — proving the org-A "no secret" bypass fires.
4. Assert that `org_b`'s stack received the `sync_github` call / a `Commit` was created for `org_b/example`, e.g. via `Stack.any_instance.expects(:sync_github).with(expected_head_sha: sha)` — proving `Handler#stacks` resolved and mutated `org_b`'s stack despite the request being "verified" under `org_a`'s (absent) secret.
5. Repeat directly against `Handler#stacks` in isolation: instantiate `PushHandler.new(payload)` where `payload['repository']['owner']['login'] != payload['repository']['full_name'].split('/').first`, and assert `handler.send(:stacks)` still returns the `org_b` stack — demonstrating `stacks` is independent of which org's secret authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
