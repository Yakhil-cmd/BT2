## Title
Unrate-limited `private_payments` chat messages allow a paired correspondent to flood a victim node's database and mutex queue, causing resource exhaustion (DoS) - (File: `wallet.js`, `network.js`)

### Summary
Any device that is a correspondent (a private-payment counterparty/paired device) of a victim node can repeatedly send the `private_payments` chat subject with crafted chains referencing fabricated, never-existing unit hashes. There is no rate limiting, per-sender quota, or size cap on the number of chains or on how often this message can be sent, and each occurrence causes a durable, unbounded database write plus serialized, expensive validation work. This mirrors the FreeScout finding: an endpoint that accepts free-form uploads with no rate limiting leads to database overload/DoS.

### Finding Description
The `private_payments` subject is dispatched from `handleMessageFromHub` to `handlePrivatePaymentChains`: [1](#0-0) 

`handlePrivatePaymentChains` only checks structural shape of the chains (non-empty arrays/objects/strings); it never bounds the number of chains, checks that the sender has any real relationship to the referenced units, or throttles how often a given correspondent may send this subject: [2](#0-1) 

Each chain is passed to `network.handleOnlinePrivatePayment`, which validates only that `unit` is base64 of the correct hash length (not that it is a real, existing unit) before deciding whether the unit is new: [3](#0-2) 

If the referenced unit is unknown (the common/attacker case, since the hash is fabricated and will never arrive), the payload is inserted verbatim into the `unhandled_private_payments` table with no cap on row count, no expiry, and no dedup beyond an in-memory hash cache that is trivially bypassed by varying content per message: [4](#0-3) 

The 1‑hour in-memory `handledChainsCache` only blocks byte-identical repeats of the exact same `arrChains` payload — trivially defeated by changing any field (e.g., a random fake unit hash) per message: [5](#0-4) 

All hub messages (including this one) are additionally serialized through a single global mutex key `"from_hub"`, so a flood of these messages also creates a growing backlog that delays/starves processing of legitimate messages from all other correspondents on the same node: [6](#0-5) 

The only size guard is a generic depth/node-count check (depth ≤ 20, ≤ 100000 nodes) applied to the whole hub message, which still permits a large number of small, well-formed-but-bogus chain entries per message: [7](#0-6) 

There is no code path that deletes stale `unhandled_private_payments` rows whose referenced unit never arrives, so rows accumulate indefinitely, and `requestNewMissingJoints` (fired for each "new" unit) adds further wasted network/processing overhead per fabricated hash: [8](#0-7) 

### Impact Explanation
An attacker who is merely a paired correspondent (private-payment counterparty), a status obtainable via the normal pairing flow without any special/administrative privilege, can:
- Repeatedly send `private_payments` messages with fabricated unit hashes, each accepted and durably written to `unhandled_private_payments` with no size/rate limit — unbounded DB growth (disk exhaustion) on the victim node.
- Because all hub messages funnel through a single `"from_hub"` mutex, sustained flooding delays/blocks processing of legitimate chat, signing, and payment messages from other correspondents, degrading or freezing wallet/AA-related device-message handling for the victim.
This matches the reported bug class (unrestricted, unrate-limited endpoint → DB overload → DoS), scoped here to the ocore private-payment/device-message handling path, which is explicitly in scope.

### Likelihood Explanation
Sending `private_payments` messages requires no unit fee, no proof-of-work, and no special privileges beyond being paired with the victim — pairing itself is a low-barrier, user-facing feature. Crafting a fake but well-formed base64 unit hash of the correct length is trivial. The lack of any per-sender throttle or persistent-storage cap makes sustained flooding straightforward and repeatable.

### Recommendation
- Add rate limiting per correspondent device (and/or per hub message) for the `private_payments` subject, and reject bursts beyond a reasonable threshold.
- Cap the number of chains accepted per message and the total size/queue depth of `unhandled_private_payments` per peer/device.
- Periodically purge `unhandled_private_payments` rows whose referenced unit has not arrived after a bounded timeout.
- Avoid serializing all hub message types behind a single global mutex key; isolate/limit per-sender queues so one correspondent cannot stall processing for others.

### Proof of Concept
1. Pair device B with victim device A (normal pairing flow).
2. From B, repeatedly send hub messages with `subject: "private_payments"` and `body: { chains: [[{ unit: <random base64 of HASH_LENGTH>, message_index: 0, payload: { asset: <random base64 hash>, inputs: [{type:"issue", serial_number:1, amount:1}], outputs: [{address:<any valid address>, amount:1}] } }]] }`, varying the random unit/asset hash on every message to bypass the `handledChainsCache` dedup.
3. Observe `unhandled_private_payments` growing without bound on A, and that legitimate chat/signing messages processed via `handleMessageFromHub` on A are delayed due to the shared `"from_hub"` mutex backlog.
