## Confirmed cross-organization confused deputy: signature verified against `repository.owner.login`, but repo written derived from independent `repository.full_name`

### Title
Cross-organization signature confused deputy in `WebhooksController` allows a valid webhook sender for one GitHub organization to write to any other organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once that signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#stacks`, and the `full_name`-based lookups in the pull-request handlers) resolves the repository/stack to act on from a *separately read* field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the field the signature check trusts (`repository.owner.login`) and the field that determines which repository is written to (`repository.full_name`) can diverge inside a single, validly-signed payload.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` from `secrets.github[organization]`:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [2](#0-1) 

This confirms the engine supports multi-tenant GitHub App configuration, where each organization has its own independent `webhook_secret`. Since `X-Hub-Signature` is only checked against the secret belonging to `repository.owner.login`, a signature that validates only proves the payload was signed with *that organization's* secret - it says nothing about the truthfulness of any other field in the same JSON body, including `repository.full_name`.

Every handler that determines what gets mutated reads `repository.full_name` independently, without ever re-checking it matches `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a direct DB lookup with no ownership check against the signature-verified organization:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

The push handler then acts directly on whatever stack that lookup returns:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `label_capturing_handler.rb`, `unlabeled_handler.rb`) all independently re-derive the target repository from `params.repository.full_name` and perform state changes (create/archive/unarchive review stacks) based on it:
```ruby
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
    Shipit::NullRepository.new
end
``` [6](#0-5) 

**Trust binding broken (as equality):** the controller enforces `signature_valid_for(repository.owner.login) == true`, but every handler acts on `repository = from_github_repo_name(repository.full_name)`. The binding `repository.owner.login == owner(repository.full_name)` is never asserted anywhere in the request path, even though the security model (per-organization webhook secrets) depends on it holding.

**Before the attack:** an attacker who is an authorized GitHub App installer/admin for organization `attacker-org` (and thus possesses/derives that org's `webhook_secret` via a legitimate installed webhook, or replays/forges a signature using that secret) can only affect stacks belonging to repositories owned by `attacker-org`.

**After the attack:** by sending a POST to `/webhooks` with `X-Hub-Signature` computed using `attacker-org`'s `webhook_secret`, but setting the JSON body's `repository.owner.login` to `"attacker-org"` (to select the matching secret in `verify_signature`) while setting `repository.full_name` to `"victim-org/victim-repo"`, the attacker causes `Shipit.github(organization: "attacker-org")` to succeed, and then the handler resolves and mutates `victim-org/victim-repo`'s stacks - triggering `sync_github` (which re-fetches commits/state from GitHub for that stack, feeding the CI/merge/deploy pipeline) or, via PR handlers, creating/archiving/unarchiving `ReviewStack`s and mutating pull request records for a repository the attacker never had signature authority over.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" binding explicitly called out as in-scope. It allows an attacker who legitimately controls one organization's webhook secret to force write actions (`sync_github`, review-stack creation/archival, PR label/state mutation) against a completely different organization's stacks and repositories - a cross-repository/cross-organization write achieved purely by crafting the JSON body, without ever possessing `victim-org`'s webhook secret. This matches the "cross-repository writes" Critical impact criterion, since it lets a signature valid for org A drive writes into org B's data.

### Likelihood Explanation
Requires the deployment to use the **multi-organization GitHub App configuration** (`secrets.github` keyed by organization, as shown by `github_default_organization`/`github_app_config`), which is a documented, supported configuration path in `lib/shipit.rb`, not a hypothetical. Any actor holding webhook-secret-equivalent access for even one onboarded organization (e.g., a compromised/malicious org admin, or someone who can trigger that org's real webhook delivery and replay it with a modified body while re-signing, which they can do since they hold that secret) can immediately target any other organization's repositories tracked by the same Shipit instance. No Shipit session, API token, or GitHub token is needed - only knowledge of one org's `webhook_secret`, which is a much lower bar than a full "unauthorized deploy" credential.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatch), enforce that the organization used to select the verification secret is the same organization implied by every repository reference subsequently used by handlers - i.e., derive the owner from `repository.full_name` (or `organization.login`) once, verify the signature against that exact resolved organization, and have `Handler#repository_name`/`stacks` consume the same already-authenticated owner rather than re-reading an independent, unchecked field from the payload. Concretely, assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) before invoking any handler, and reject (422) on mismatch.

### Proof of Concept
1. Onboard/control organization `attacker-org` in the Shipit multi-org GitHub App config, obtaining its `webhook_secret`.
2. Craft a JSON payload for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `attacker-org`'s secret [7](#0-6) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "deadbeef")` on `victim-org`'s stack [5](#0-4) , despite the request never being signed by `victim-org`'s secret.
