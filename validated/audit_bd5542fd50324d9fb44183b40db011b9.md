### Title
`ReopenedHandler#unarchive?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses `a && b || c || d` where `&&` binds tighter than `||`, so `repository.review_stacks_enabled` is only ANDed into the `allow_all` branch and is never checked against the `allow_with_label`/`prevent_with_label` branches. An attacker who owns a PR on a repository with `review_stacks_enabled == false` and `provisioning_behavior == :allow_with_label` can add the provisioning label and reopen the PR to unarchive a previously-archived review stack and re-enqueue provisioning, bypassing the disabled flag entirely.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` at reopen time `⇒` `unarchive? == false` regardless of behavior/label state. Tracing `unarchive?`:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby precedence this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The second and third disjuncts never reference `review_stacks_enabled` at all, so when `provisioning_behavior == :allow_with_label` and the provisioning label is present on the PR, `unarchive?` evaluates to `true` even if `review_stacks_enabled` is `false`.

`respond_to_pull_request_reopened?` calls only `unarchive?` with no separate top-level `review_stacks_enabled` gate [2](#0-1) , so `process` proceeds directly to `stack.unarchive!` [3](#0-2) .

`ReviewStackAdapter#unarchive!` then adds the stack to `Shipit::ReviewStackProvisioningQueue` and calls `stack.unarchive!`, provisioning against the PR's current branch head from the webhook payload (`stack_attributes` sourced `branch` from `params.pull_request.head.ref` at creation time; the stack retains that branch, and reopen re-triggers provisioning using it) [4](#0-3) .

The identical `&&`/`||` precedence bug also exists in `OpenedHandler#provision?` [5](#0-4) , but `LabeledHandler`/`UnlabeledHandler` are unaffected because they gate on `repository.review_stacks_enabled` as an independent top-level `&&` term in `respond_to_label_change?`, outside of `archive?`/`unarchive?` [6](#0-5) .

Exploit flow: attacker with `review_stacks_enabled == false`, `provisioning_behavior == :allow_with_label`, provisioning label already present on a stack that was previously archived (e.g. was provisioned while flag was enabled, or admin archived it) — attacker closes and reopens their own PR (an action any PR author or repo owner can do), triggering a `pull_request.reopened` webhook. `ReopenedHandler#process` calls `unarchive?`, which returns `true` via the `allow_with_label` disjunct regardless of `review_stacks_enabled`, unarchiving the stack and re-queuing provisioning.

No existing guard catches this: `respond_to_pull_request_reopened?` doesn't add its own `review_stacks_enabled` check, and no other layer (signature verification, `ExplicitParameters` schema, model validations) constrains this business-logic condition — those guards authenticate the webhook and payload shape, not the provisioning-behavior semantics.

### Impact Explanation
This causes an unauthorized re-provisioning action (task enqueue via `ReviewStackProvisioningQueue`, which leads to `TaskCommands`/deploy task execution) for a repository/stack whose owner explicitly disabled dynamic review-stack provisioning (`review_stacks_enabled == false`). This is a policy bypass that results in an unauthorized deploy/provisioning action being triggered against the attacker's own branch head, matching "unauthorized deploy" impact. The blast radius is scoped to the attacker's own repository/PR/stack (same-tenant), not cross-repository — the attacker cannot affect other repositories' stacks. It is repeatable for any PR the attacker controls in a repo configured this way.

### Likelihood Explanation
Preconditions: repository must have `review_stacks_enabled == false` AND `provisioning_behavior` set to `:allow_with_label` (or `:prevent_with_label`) AND a previously-created/archived review stack must exist for that PR's environment (`prN`). This requires the repository owner/maintainer to have toggled `review_stacks_enabled` off after a stack existed, or an operator misconfiguration — this is a plausible but not universal configuration. The attacker's cost is trivial: label + close/reopen a PR they control, both routine unprivileged GitHub actions. Fully repeatable per PR/reopen cycle.

### Recommendation
Fix operator precedence in `ReopenedHandler#unarchive?` (and the analogous `OpenedHandler#provision?`) by parenthesizing to require `review_stacks_enabled` across all branches, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Alternatively, add an explicit `repository.review_stacks_enabled` check in `respond_to_pull_request_reopened?` as is already done in `LabeledHandler`/`UnlabeledHandler`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive stacks when review_stacks_enabled is false even with allow_with_label and label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived when review_stacks_enabled is false"
end
```
Assert both sides of the binding: `repository.review_stacks_enabled == false` before the call, and `stack.reload.archived? == true` / no queue add after the call. Under current code this test fails because `unarchive?` returns `true` via the `allow_with_label` branch, unarchiving the stack.
