### Title
Webhook Organization Authentication Not Bound to Payload's Target Repository/Commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The HMAC signature verification in `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against based on `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) . Once that check passes, individual handlers act on a *different* field of the same payload to decide **what to write to** — `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [2](#0-1) , and `StatusHandler#process` looks up commits purely by `sha` with no repository scoping at all [3](#0-2) . Nothing in the code cross-checks that the organization whose secret validated the signature is the same organization that owns the repository/commit actually mutated.

### Finding Description
This mirrors the report's bug class ("all other config fields are covered, except this one field which is used but never validated/bound"). Here, the field used for **authentication** (`repository.owner.login`, used to pick `Shipit.github(organization: repository_owner)` and its `webhook_secret`) is never re-checked for equality against the field used for **effect** (`repository.full_name` in `Handler#repository_name`, or the raw `sha` in `StatusHandler`).

The equality that should hold but does not:
`organization authenticated via repository.owner.login == organization/repository actually mutated by the handler`

Because the HMAC covers the whole raw POST body, an attacker cannot forge an arbitrary payload without knowing a valid `webhook_secret` for *some* organization configured in Shipit. However, if the attacker legitimately administers one GitHub organization (`Org A`) that is integrated with this Shipit instance — meaning they know or set `Org A`'s `webhook_secret` themselves when installing the webhook — they can send a POST directly to Shipit's webhook endpoint with a **hand-crafted JSON body**, not a body generated by GitHub:

- `repository.owner.login = "OrgA"` → selects `OrgA`'s known `webhook_secret`, so `verify_signature` passes [4](#0-3) .
- `repository.full_name = "OrgB/target-repo"` (a repo/stack the attacker does not control) → drives `Repository.from_github_repo_name` lookups in `PushHandler`/`CheckSuiteHandler` via `Handler#repository_name` [2](#0-1) , or
- For the `status` event, `StatusHandler` doesn't even look at the `repository` field: it does `Commit.where(sha: params.sha)` globally, then calls `commit.create_status_from_github!(params)` for every match, regardless of which org/repo the commit belongs to [3](#0-2) .

### Impact Explanation
Via `StatusHandler`, an attacker controlling a signed webhook secret for any single onboarded organization can inject an arbitrary CI status (e.g., `state: "success"`) onto a commit belonging to an unrelated stack/repository they do not own, since the lookup is a global `Commit.where(sha:)` with no organization/repository filter [3](#0-2) . If that stack's deploy readiness gates on CI status (a standard Shipit feature), this can be used to force a commit into a "green"/deployable state it did not actually earn, contributing to an unauthorized deploy path. Via `PushHandler`/`CheckSuiteHandler`, the same cross-organization confusion lets the attacker trigger `GithubSyncJob`/check-run refresh jobs against a stack belonging to a repository they don't administer [5](#0-4) [6](#0-5) .

I was not able to fully trace `Commit#create_status_from_github!` or `Stack#sync_github` bodies within the remaining tool budget to conclusively confirm whether a forged "success" status alone is sufficient to unblock a deploy without any other required gate (e.g., merge-request approval, branch protection mirrored in Shipit) — this should be verified against `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb` before treating the deploy-bypass chain as fully proven.

### Likelihood Explanation
Requires the attacker to legitimately control (or have been given webhook credentials for) at least one GitHub organization that is configured in this Shipit deployment — a real but non-trivial precondition consistent with the "unprivileged attacker" framing only insofar as they hold no privileges on the *target* stack/repository. Multi-tenant Shipit installations (multiple `Shipit.github(organization:)` configs, as evidenced by the `GithubOrganizationUnknown` handling) are the realistic setting for this [7](#0-6) .

### Recommendation
In `Handler#repository_name` and any handler using cross-payload fields (notably `StatusHandler`), verify that the resolved repository's/commit's owning organization matches the `repository_owner`/organization that was used to validate the webhook signature, rejecting the event otherwise. Concretely: after resolving `Commit.where(sha: params.sha)` in `StatusHandler`, filter to commits whose `stack.repository.owner` equals the authenticated `repository_owner`; likewise assert `payload.dig('repository','full_name')`'s owner segment matches `repository_owner` in `Handler`.

### Proof of Concept
1. Attacker administers `OrgA`, a GitHub organization onboarded to this Shipit instance, and knows `OrgA`'s configured `webhook_secret`.
2. Attacker crafts a `status` event JSON body: `{"sha": "<sha-of-a-commit-in-OrgB/some-repo>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"}}`.
3. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over the raw JSON and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes [4](#0-3) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgB` commit — and calls `create_status_from_github!`, injecting a forged success status onto a commit the attacker never authored or had access to [3](#0-2) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
