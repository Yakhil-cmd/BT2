### Title
Cross-repository CI-state collapse via SHA-only scoping in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` [1](#0-0) , and `Shipit::Commit#create_status_from_github!` has no guard tying the update to the commit's own `stack.repository` [2](#0-1) . Any two `Commit` rows across different stacks/repositories that share a SHA (the normal outcome of forking, cherry-picking, or rebase-preserving a commit) will both receive the incoming status, regardless of which repository's webhook produced it.

### Finding Description
Broken binding: `commit.stack.repository` (the tenant that owns the CI-state row) is claimed to equal "the repository that authenticated the webhook," but the only enforced equality in code is `commit.sha == params.sha` [3](#0-2) . The `status` params schema accepts `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — it never even parses a `repository` field to compare against [4](#0-3) .

Upstream, `WebhooksController#verify_signature` only authenticates that the payload was signed for `repository_owner`'s GitHub App/org configuration (`Shipit.github(organization: repository_owner)`), i.e. it establishes "this request genuinely came from GitHub for this org's installation" — it does **not** constrain which `Commit`/`Stack` rows in Shipit's own database the payload is allowed to mutate [5](#0-4) . Once the controller dispatches to `StatusHandler.call(params)`, all per-repository scoping is lost — `process` iterates every `Commit` row with a matching `sha` across the entire installation, spanning all stacks and all repositories tracked by that Shipit instance.

Because Git commit SHAs are content-addressed, an unmodified fork of a repository preserves identical SHAs for identical commits. If a fork (or any other repository sharing history) is also tracked as a Shipit stack — or is otherwise able to deliver a validly-signed status webhook for an org Shipit trusts — a status posted against the fork's copy of a commit will update the `statuses` (and downstream `deployable?`/`schedule_continuous_delivery` logic) of the *original* repository's identical-SHA commit, since `add_status` and `schedule_continuous_delivery` operate purely on the `Commit` row found by SHA [6](#0-5) [7](#0-6) .

None of the listed guards address this: `verify_signature` authenticates the org/installation, not the target commit's owning stack; the `ExplicitParameters` schema for `StatusHandler` has no repository field to check; there is no `before_action`, `belongs_to`-level scoping, or `stack.repository` comparison anywhere in `Shipit::Commit` or `StatusHandler`.

### Impact Explanation
A status posted from a repository whose SHA collides with another tracked stack's commit updates the CI status (`Commit#status`, `deployable?`) for that unrelated stack's commit. Since `schedule_continuous_delivery` gates on `deployable?` (which depends on `success?`) [8](#0-7) [7](#0-6) , an attacker controlling a repository that shares a SHA with a victim stack (typical for forks) can inject a fabricated "success" status that causes the victim stack to treat an unvetted commit as CI-passing, potentially triggering continuous deployment of that commit. This is a payload for one repository mutating another repository's commit/stack state, matching the Critical "payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy" category. It is repeatable against any repository pair sharing a SHA, for as long as both are tracked as Shipit stacks (or one stack tracks a SHA also reachable from an attacker-controlled repo under a trusted org/installation).

### Likelihood Explanation
Exploitation requires: (1) a commit SHA shared between the victim's tracked stack and a repository the attacker can push webhook-triggering events from, and (2) that repository's webhook must pass `verify_signature`, meaning it must belong to an org/installation Shipit already trusts (`Shipit.github(organization: repository_owner)` must resolve without raising `GithubOrganizationUnknown`). This second precondition is the main limiting factor and depends on how the GitHub App/webhook secret is scoped in the deployment (e.g., org-wide app installations that include "all repositories" — which would cover forks created under that org — versus per-repo installations restricted to a fixed set of repos). I could not fully verify `Shipit.github`'s organization-resolution semantics within the available context, so whether an attacker's personal fork (outside the victim's org) can obtain a valid signature is uncertain and deployment-configuration-dependent. Within an org where forks/PRs are auto-covered by the same App installation, the attack is low-cost and fully repeatable; across unrelated orgs with strict per-installation secrets, it would be blocked by `verify_signature` before reaching `StatusHandler`.

### Recommendation
Scope status/check-run handling to the repository that authenticated the webhook: pass the payload's `repository.full_name` through to `StatusHandler#process` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: resolved_repository.id })` (or equivalent), so a status can only ever mutate commits belonging to stacks whose `repository` matches the authenticated webhook's repository.

### Proof of Concept
Under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or `test/models/commits_test.rb`):
1. Create `stack_a` bound to `repository_a` ("acme/widgets") and `stack_b` bound to `repository_b` ("attacker/widgets", a fork).
2. Create `Commit` rows in both stacks with the identical `sha` "deadbeef...".
3. Build a `status` webhook payload for that `sha` with `state: "success"`, whose `repository` field is `repository_b` (i.e., asserting the payload's semantic ownership is `repository_b`/`stack_b` only).
4. Invoke `StatusHandler.call(payload)` (with a valid/mocked signature for `repository_b`'s org).
5. Assert: `stack_b`'s commit now has a `success` status (expected/legitimate) AND `stack_a`'s commit (belonging to `repository_a`, which never authenticated this webhook) also now has a `success` status — demonstrating `commit.stack.repository` for `stack_a` was never checked against the webhook's authenticated repository, i.e. `stack_a.repository != repository_b` yet the state still applied.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
