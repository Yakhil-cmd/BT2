### Title
Stack-scoped ApiClient token can read any stack's CCMenu status, bypassing its `stack_id` authorization scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-lookup method with a version that ignores the `ApiClient#stack_id` scope, letting a token that is restricted to one stack read the deploy/lock status of any other stack.

### Finding Description
`Shipit::Api::BaseController` is designed so that an `ApiClient` can be scoped to a single stack. The scoping is enforced through the `stacks`/`stack` helper pair: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client has a `stack_id` set, and `stack` resolves `params[:stack_id]` only within that restricted set. Every other API controller that needs the current stack goes through this scoped `stack` method (e.g. the assertion in the test suite that "an api client scoped to a stack will only see that one stack" for the stacks index, or the way `hooks_controller.rb` and `stacks_controller.rb` consume `stack_id`).

`CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` looks the stack up globally, with no reference to `current_api_client.stack_id` at all. The only gate left is `require_permission :read, :stack`, declared at the top of the controller: [3](#0-2) 

which only checks that the permission bit `read:stack` is present in `ApiClient#permissions` via `ApiClient#check_permissions!`: [4](#0-3) 

`check_permissions!` never consults `stack_id`, so the permission check and the scope check are two independent bindings, and `CCMenuController` only enforces the former.

**Binding broken:** *stack a token authorises* (`current_api_client.stack_id` = A, as encoded when the client was created, e.g. via `CCMenuUrlController#client` which creates a client `create_with(permissions: %w[read:stack])` bound to a specific stack) **≠** *stack a token touches* (`Stack.from_param!(params[:stack_id])` = any stack B chosen by the caller).

- Before the request: an `ApiClient` with `stack_id = A` and `permissions = ["read:stack"]` is only supposed to be able to read stack A (this is exactly what `CCMenuUrlController#client` mints for the "CCMenu Client" per stack, and what `BaseController#stacks` enforces everywhere else).
- After the request: the same token, presented with `params[:stack_id] = B`, is authenticated (Basic auth token is valid), authorized (`read:stack` permission is present), and `CCMenuController#stack` returns stack B unfiltered, exposing its build/deploy status, lock state and last build label.

### Impact Explanation
This is an authenticated but unauthorized cross-stack read of stack state: any leaked or intentionally shared stack-scoped CCMenu token (these tokens are displayed/shared as CI dashboard URLs, see `CCMenuUrlController`) can be replayed against every other stack in the Shipit instance to read its current build/deploy/lock status, defeating the purpose of the per-stack `stack_id` restriction.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` ApiClient token (which is routinely exposed as a "CCMenu URL" query-string token meant only for CI status widgets) can trivially exploit this by changing the `stack_id` path segment of the request — no additional privilege, secret, or race condition is required.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot address stacks outside their `stack_id`.

### Proof of Concept
1. Create (or obtain) a stack-scoped ApiClient for stack A, e.g. via `CCMenuUrlController#fetch`, which creates `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(stack: A, creator: current_user, name: 'CCMenu Client')`, yielding a token bound to `stack_id = A`.
2. Using that token's `authentication_token` as Basic Auth credentials, send `GET /api/:stack_B_slug/cc.xml` (using the id/param of a different stack B the client was never scoped to).
3. `authenticate_api_client` succeeds (token verifies), `require_permission :read, :stack` succeeds (`read:stack` is present), and `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` to stack B regardless of `current_api_client.stack_id == A`.
4. The response renders stack B's CCMenu XML (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), confirming the token scoped to stack A can read stack B's data.
