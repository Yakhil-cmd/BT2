### Title
Malicious swap route can attach hidden token transfers to the caller’s signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller strategy verbs accept opaque caller-supplied `swap` bytes and execute them through the configured router while the caller’s top-level `require_auth` is active. The controller authorizes only its own exact input transfer to the router, then measures token deltas afterward; it does not constrain what nested authorization requests code reached by the route can add under the caller’s signed invocation. A crafted route/venue can therefore inject an unrelated `token.transfer(victim, attacker, n)` into the same authorization tree during simulation/signing, draining wallet tokens unrelated to the lending position when the signed tree is submitted.

### Finding Description
`swap_collateral` authenticates the caller and requires owner/delegate rights, then forwards the user-controlled `swap` into `withdraw_and_swap_from_supply` (`contracts/controller/src/strategies/swap_collateral.rs:40-65`). The shared swap helper snapshots controller balances, creates exactly one invoker auth for `controller -> router` input, calls `router.execute_strategy(controller, amount_in, swap)` inside the flash guard, and only afterward checks output/overspend (`contracts/controller/src/strategies/swap.rs:24-55`). Account access is gated separately by `require_authorized_caller` / `require_owner_or_delegate` (`contracts/controller/src/risk/validation.rs:13-16`, `contracts/controller/src/strategies/swap_collateral.rs:46-48`), but that top-level caller auth remains the root under which deeper `require_auth` requests are recorded.

The repo’s harness pins the host behavior: a hop pool reached from route bytes can call `token.transfer(caller, attacker, amount)`; in recording mode it is attached beneath the caller’s `swap_collateral` authorized invocation, and Alice’s unrelated wallet balance moves to the attacker while the protocol leg still succeeds (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-226`). The same pattern is reachable through the other routed verbs that take `swap` bytes (`multiply`, `swap_debt`, `repay_debt_with_collateral`) because all converge on `swap_tokens` / `swap_tokens_or_passthrough`.

### Impact Explanation
Theft of user funds: assets in the caller’s wallet that are not protocol collateral, not listed, and not part of the swap can be transferred to an attacker if the victim signs the poisoned auth tree produced for a routed strategy call. The lending accounting can still look consistent because the controller only validates its own input spend and measured output, not the semantics of every nested auth the route caused.

### Likelihood Explanation
Medium. Execution requires no privileged role: the path is a normal caller-owned routed strategy. The constraint is that the victim must submit/sign a transaction whose simulated auth tree includes the injected transfer; wallets or callers that blindly sign simulated auth trees or consume route bytes from an untrusted quote path are exposed. The protocol-side guard does not provide the missing protection because it only prevents controller re-entry, not additional caller-authorized token calls beneath the same root.

### Recommendation
Do not let route execution introduce new caller-authorized operations. Bind routed strategy calls to a fixed authorization shape: reject any attempt by code reached through `swap` to require the caller’s auth for anything other than the explicitly declared strategy transfers; prefer forcing all route pulls to be from the controller/router only and fail if a hop requests `caller.require_auth` or a token transfer whose `from` is the caller. At minimum, decode/validate route venues against an allowlist and surface a canonical expected auth tree for simulation so unexpected sub-invocations are detectable before signing.

### Proof of Concept
Use the existing harness scenario: deploy a router/hop double that pays fair output but, inside the hop, calls `token.transfer(ALICE, attacker, WALLET_BALANCE)` for an unlisted token; submit `swap_collateral` as Alice with route bytes pointing at that hop. In recording mode the unauthorized wallet transfer is attached under Alice’s `swap_collateral` authorization, the swap still returns `FAIR_OUT_ETH`, Alice’s wallet token balance becomes zero, and the attacker receives it (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:33-47`, `:62-70`, `:194-226`). The production-enabling condition is the controller’s forwarding of opaque `swap` bytes after caller auth while only exact-input authorization is created locally (`contracts/controller/src/strategies/swap.rs:33-38`).
