### Title
Cross-organization webhook authentication bypass enables unauthorized status forgery and deploy triggering — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App's `webhook_secret` to use for HMAC verification based on an **unverified** field of the incoming payload (`repository.owner.login` / `organization.login`), while the handlers that subsequently act on the payload key off a **different, independently-controlled** field, `repository.full_name`. This breaks the binding "organization that authenticated == repository that is written," letting an attacker who legitimately controls the webhook secret for *any one* GitHub App/organization configured in Shipit forge events that are attributed to a completely different, unrelated stack/repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against using: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the JSON body before the signature has been checked. The HMAC (`OpenSSL::HMAC.hexdigest`) is computed correctly over the *whole* raw body with that org's `webhook_secret`: [3](#0-2) 

So the signature step only proves "this body was signed by whichever org's secret matches `repository.owner.login`" — it does **not** prove that the rest of the body's fields (in particular `repository.full_name`) actually belong to that organization.

Every handler, however, resolves the target `Stack`/`Repository` purely from `repository.full_name`, a field completely disconnected from the org used for verification: [4](#0-3) 

`StatusHandler` is worse still — it does not scope by repository at all, only by commit SHA, globally across the entire database: [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` scope only via `stacks`, which is derived from the attacker-controlled `repository.full_name`: [6](#0-5) [7](#0-6) 

Concretely: an operator who administers a GitHub App for Organization A (and therefore legitimately knows Organization A's `webhook_secret`, since Shipit supports multiple independently-configured GitHub Apps) can craft a payload with `repository.owner.login = "A"` (so `verify_signature` picks Organization A's secret and the HMAC passes) but `repository.full_name = "victim-org/victim-repo"`. Shipit will accept the request as authentic and route it to the victim organization's stack.

### Impact Explanation
Via `StatusHandler`, the attacker can create/forge CI `Status` records (`state`, `description`, `target_url`, `context`) on **any commit in the entire Shipit instance**, not even limited to a specific repository, simply by knowing a target SHA — SHAs are typically public information. Forged "success" statuses on required CI contexts can satisfy `deployable?`/`required_statuses` checks used by continuous delivery, driving an **unauthorized deploy** of a victim's stack — matching the Critical-impact criterion "an unauthorized deploy, rollback or merge." Via `PushHandler`, the attacker can also force `sync_github`/commit refresh operations against a victim's stack using only their own, unrelated org's webhook credentials.

### Likelihood Explanation
This requires the attacker to control (i.e., know the webhook secret of) at least one GitHub App/organization registered in the Shipit deployment — a materially lower bar than requiring an `ApiClient` token, a Shipit session, or GitHub write access to the *victim* repository, since Shipit explicitly supports many independently-administered organizations sharing a single webhook endpoint. No privileged credential toward the victim stack is needed at all.

### Recommendation
Verify the webhook against the org's secret, then re-derive/require that `repository.owner.login` (or `organization.login`) used for secret selection matches the owner embedded in `repository.full_name` before any handler acts on it. Additionally, `StatusHandler` should scope commit lookups to the repository named in the (now-validated) payload rather than a bare, cross-repository SHA match.

### Proof of Concept
1. Attacker administers GitHub App/org "A" in Shipit's multi-org config and thus knows `webhook_secret_A` (as documented in `docs/setup.md`'s "Using Multiple GitHub Applications").
2. Attacker POSTs to `/webhooks` (or the configured webhook path) with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "A" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha, e.g. from GitHub UI>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `X-Hub-Signature` is computed with `webhook_secret_A` over this exact body.
4. `verify_signature` resolves `Shipit.github(organization: "A")` (from `repository.owner.login`), verifies successfully, and `StatusHandler` writes a forged success `Status` onto the victim's commit, independent of `full_name`/`A` even matching — potentially triggering continuous deployment of `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
