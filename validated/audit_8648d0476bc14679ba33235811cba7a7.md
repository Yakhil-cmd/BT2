### Title
Cross-repository CI status forgery via webhook signature scope mismatch - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the incoming webhook payload was HMAC-signed with the `webhook_secret` configured for **one specific GitHub organization** (chosen from the payload's own `repository.owner.login`/`organization.login` field). It never confirms that the rest of the payload — in particular the commit `sha` — actually belongs to a repository owned by that same, now-authenticated organization. `StatusHandler#process` then updates commit statuses purely by matching `sha` across the **entire** `Commit` table, with no scoping to the repository/organization that was verified. This lets anyone who legitimately controls a webhook secret for *any one* GitHub org configured in a multi-tenant Shipit deployment forge a "success" CI status for a commit SHA belonging to a completely different tracked repository, which can unblock automatic merges and deploys for that unrelated stack.

### Finding Description
Signature verification and event authorization happen at the organization granularity: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-controlled JSON body and used only to select which org's `webhook_secret` to validate the HMAC against: [3](#0-2) 

Once the HMAC checks out for *that* org, the controller dispatches the event to handlers without re-binding any other field of the payload to the verified organization: [4](#0-3) 

Most handlers correctly re-derive scope from `payload.dig('repository', 'full_name')` via the shared `Handler#stacks` helper (e.g. `PushHandler` filters `stacks.not_archived.where(branch:)`): [5](#0-4) [6](#0-5) 

But `StatusHandler` does not use `stacks`/`repository_name` at all — it matches purely on `sha` globally: [7](#0-6) 

This is the same class of bug as H-1: the verification step (`verify_webhook_signature`/`LibMuon.verifyPrices`) authenticates one attribute (organization identity / cryptographic signature) but a downstream consumer (`StatusHandler` / `setSymbolsPrice`) acts on a different, unconstrained attribute (`sha` / `priceSig.upnl`) that was never bound to what was actually verified. The equality that should hold — "organization that authenticated == organization owning the repository the status is written to" — is never checked.

Shipit officially supports multi-organization deployments where each org has its own independent `webhook_secret`, as documented in the example configs: [8](#0-7) 

In that supported topology, org B's legitimately-configured webhook (which org B's own admins control, and whose secret org B knows because they set it themselves) is fully trusted to authenticate `status` events for **any** commit tracked by the shared Shipit instance, including commits belonging to org A's repositories.

### Impact Explanation
A forged "success" status is consumed by `StatusChecker`/`MergeRequest#all_status_checks_passed?`, which `ProcessMergeRequestsJob` uses to decide whether to call `stack.github_api.merge_pull_request` (an unauthorized merge) and which continuous-delivery scheduling / deploy gating logic in this engine also relies on for auto-deploys. This crosses a repository/organization trust boundary using credentials scoped to a different, unrelated repository, resulting in an unauthorized merge or deploy on a stack the attacker has no legitimate access to — matching the Critical impact category (unauthorized merge/deploy across repositories).

### Likelihood Explanation
Requires only that the attacker administers (or has webhook access to) any one GitHub organization/repository that this specific Shipit instance is configured to serve — a normal, documented multi-tenant setup, not a privileged Shipit account, API token, or the target org's own webhook secret. The attacker crafts a standard `status` webhook payload, points `sha` at a commit belonging to a different tracked repository, and signs it with their own legitimately-known secret. No repository write access to the victim repo, no Shipit session, and no knowledge of the victim's `webhook_secret` are needed.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already use `Handler#stacks`), verify that `payload.dig('repository', 'full_name')` matches an actual `Repository`/`Stack` and scope the `Commit` lookup to that repository (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)`), instead of matching `sha` globally. More generally, after `verify_signature` establishes the authenticated organization, every handler should re-derive its target records exclusively from repositories belonging to that organization rather than trusting unscoped identifiers embedded in the payload.

### Proof of Concept
1. Shipit is configured for two orgs, `victim-org` and `attacker-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` layout).
2. Attacker controls `attacker-org` and knows `attacker-org`'s `webhook_secret` (they configured GitHub's webhook for their own repo).
3. Attacker finds/knows the `sha` of an open PR's head commit in `victim-org/some-repo` (public info via GitHub).
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"sha": "<victim_sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}, ...}`, signed with `attacker-org`'s webhook secret via `X-Hub-Signature`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...)`, which succeeds because the signature is valid for `attacker-org`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — it matches the victim commit (no repository check) and calls `commit.create_status_from_github!(params)`, marking that commit's `success` status for whatever context the attacker chose.
7. If this status is one of `victim-org`'s required merge/deploy statuses, `ProcessMergeRequestsJob`/deploy automation subsequently treats the PR as ready and merges/deploys it.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
