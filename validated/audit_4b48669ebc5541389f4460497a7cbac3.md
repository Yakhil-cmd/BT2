### Title
Webhook signature verification failure does not halt request processing, allowing unsigned/forged GitHub events to be handled - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` responds with `head(422)` when the HMAC signature check fails, but it never halts the Rails callback chain (no `throw(:abort)` / no early `return`). Because it is only the last of three `before_action`s, and because calling `head` inside a `before_action` in Rails 5+ does **not** stop the framework from invoking the action, the `create` action still runs and dispatches the payload to `Shipit::Webhooks.for_event(event)` handlers even when `verify_webhook_signature` returned `false`.

### Finding Description
The intended trust boundary is: *"a webhook event is acted upon only if `X-Hub-Signature` verifies against `Shipit.github(organization:).webhook_secret` for the raw request body."* That is enforced (or is supposed to be) by: [1](#0-0) 

```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature
...
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
...
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  Rails.logger.info(...)
end
```

`head(422) unless verified` only writes a response; it does not `throw(:abort)` or otherwise halt the `before_action` chain. Since Rails 5, returning `false` from a filter no longer halts execution — only `throw(:abort)` does (`ActiveSupport::Callbacks`). Because `verify_signature` is the last `before_action`, control proceeds straight into `create`, which parses the raw, **unverified** body and calls every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, per the registered handler table: [2](#0-1) 

This means the equality the engine is supposed to enforce — *"handlers execute" == "signature verified"* — is broken: handlers execute regardless of verification result. The only externally observable symptom is that the second `head`/render call inside `create` (`head(:ok)` after the unsigned payload was already responded to with `head(422)`) will raise `AbstractController::DoubleRenderError`, surfacing as a 500 to the caller — but this happens *after* the handler side effects have already been applied, so the attacker still achieves state changes despite seeing an error response.

Concretely reachable handlers that execute on attacker-forged, unauthenticated payloads include:
- `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the forged branch — an attacker can force Shipit to sync/queue jobs against arbitrary refs/SHAs of a tracked repository. [3](#0-2) 
- `StatusHandler#process`, which creates a `CommitStatus` from arbitrary attacker-supplied `state`/`context`/`target_url` for any existing `Commit` row matching a forged `sha` — this can be used to fabricate a passing CI/deploy-gating status on a commit that never actually passed CI, directly influencing merge-queue/deploy-gating decisions that rely on commit statuses. [4](#0-3) 
- `MembershipHandler` and `PullRequest::*` handlers similarly execute, mutating `Team`/`Membership`/PR-label state as demonstrated in existing tests that stub `verify_signature` to `true` and observe these side effects. [5](#0-4) 

The existing test suite only asserts the HTTP status code for the failure path and never asserts that handler side effects (job enqueue, status creation) do **not** occur, so this gap is untested: [6](#0-5) 

### Impact Explanation
This is an authentication-bypass class issue: it defeats the entire purpose of `verify_webhook_signature`/`webhook_secret` (`lib/shipit/github_app.rb:76-83`), letting any unauthenticated network client that can reach `/webhooks` forge GitHub events. The most severe consequence is forging a `status` event to inject a fabricated "success" `CommitStatus` for an arbitrary commit sha already known to Shipit, which can influence deploy/merge gating decisions that key off commit status — an "unauthorized deploy/merge"-class impact per the engine's own gating logic. It also allows forged `push` events to trigger repository sync jobs and forged `membership` events to add/remove `Team`/`Membership` records outside of real GitHub authorization. [7](#0-6) 

### Likelihood Explanation
No credentials, `ApiClient` token, or GitHub App secret are required — only an HTTP POST to the public `/webhooks` endpoint with a plausible `X-Github-Event` header and JSON body; the `repository_owner`/`organization` fields are attacker-supplied and merely used to pick which `GitHubApp` config to check against, not to gate execution. The bypass triggers on every single request where the signature check fails (i.e., always, for an attacker without the secret), which is the common/default failure path.

### Recommendation
In `verify_signature`, halt the filter chain explicitly instead of relying on `head`'s side effect, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  unless verified
    head(422)
    throw(:abort)
  end
  ...
end
```
Add a regression test asserting that no handler/job/record is created when `verify_webhook_signature` returns `false`.

### Proof of Concept
1. `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{"sha":"<existing-commit-sha>","state":"success","context":"ci/required","repository":{"owner":{"login":"someorg"},"full_name":"someorg/somerepo"}}
```
without a valid `X-Hub-Signature` (or with a garbage one).
2. `verify_signature` calls `github_app.verify_webhook_signature(...)` → `false` → `head(422)` is invoked but the filter chain is not aborted.
3. `create` still executes: `JSON.parse(request.raw_post)` then `Shipit::Webhooks.for_event('status')` → `[Handlers::StatusHandler]` → `StatusHandler.call(params)` runs `Commit.where(sha: ...).each { |c| c.create_status_from_github!(params) }`, persisting an attacker-forged "success" status on the target commit.
4. The response the attacker receives is a 500 (`DoubleRenderError`) or 422 depending on Rails version specifics, but the `CommitStatus` row has already been created/updated in step 3 — confirming the side effect occurred despite the "denied" verification.
