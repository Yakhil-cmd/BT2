### Title
`repository.owner.login` used for signature verification diverges from `repository.full_name` used for stack resolution, allowing cross-tenant `check_suite` mutation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `payload.dig('repository','owner','login')`, while `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target repository/stacks using the independent field `payload.dig('repository','full_name')`. Since both fields are attacker-controlled in the same signed JSON body and are never checked against each other, an org that legitimately knows its own webhook secret can sign a payload whose `owner.login` matches its own org (to pass signature verification) while `full_name` points at a completely different, victim-owned repository.

### Finding Description
The broken binding: the equality the code implicitly assumes is
`payload['repository']['owner']['login'] == owner_of(payload['repository']['full_name'])`
This is never enforced.

- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes only from `params.dig('repository','owner','login')` (or `organization.login`) as defined in [2](#0-1) .
- The HMAC secret is looked up per-organization in `GitHubApp#verify_webhook_signature` [3](#0-2) , keyed strictly by that organization's own configured `webhook_secret`.
- Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create` [4](#0-3)  hands the *entire raw JSON body* (unfiltered by owner) to `CheckSuiteHandler`.
- `Handler#stacks` resolves the repository via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [5](#0-4)  — a field entirely independent of the one used for signature verification.
- `CheckSuiteHandler#process` then does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!) }` [6](#0-5) , with no re-check of ownership against the verified organization.

Exploit flow: attacker controls `org-attacker`, a legitimate Shipit tenant, and therefore knows `org-attacker`'s own configured `webhook_secret` (this is standard — the org admin who configures the GitHub App/webhook chooses/knows this secret). The attacker crafts a body:
```json
{
  "repository": {"owner": {"login": "org-attacker"}, "full_name": "org-victim/repo"},
  "check_suite": {"head_sha": "<victim_commit_sha>", "head_branch": "master"}
}
```
and computes a valid `X-Hub-Signature` using their own known secret. `verify_signature` passes because it only checks the org-attacker secret against `owner.login = "org-attacker"`. `CheckSuiteHandler` then resolves stacks via `full_name = "org-victim/repo"`, entirely decoupled from the verified identity, and calls `schedule_refresh_check_runs!` on org-victim's `Commit` rows.

No existing guard catches this: `drop_unhandled_event` only checks the event type is known; `ExplicitParameters` schema for `CheckSuiteHandler` only validates presence/type of `head_sha`/`head_branch`, not repository consistency; there is no code anywhere that compares `repository.owner.login` to the owner segment of `repository.full_name`.

### Impact Explanation
The attacker forces `schedule_refresh_check_runs!` to run against an arbitrary victim `Commit`/`Stack` that they neither own nor are associated with, using a signature valid only for their own tenant. This job triggers outbound GitHub API calls scoped to the *victim's* GitHub App/token (since `Repository#github_app` in [7](#0-6)  uses `Shipit.github(organization: owner)`, i.e. the victim's org), meaning a payload authenticated for one tenant mutates/triggers actions scoped to another tenant's stack/commit — squarely the "payload for one repository mutating another's stack, commit" Critical category. It is fully repeatable against any `Repository`/`Commit`/branch combination the attacker can guess or enumerate (e.g. common branch names like `master`), and generalizes to any handler that resolves `stacks` via `full_name` after a signature check keyed on `owner.login` (e.g. `PushHandler`, `StatusHandler`), not just `CheckSuiteHandler`.

### Likelihood Explanation
Preconditions are modest: the attacker only needs to be a legitimate, unprivileged tenant admin of *some* org onboarded to the Shipit instance (so they know their own `webhook_secret`), and the victim's repository/stack/commit/branch must already exist in the datastore. No knowledge of the victim's secret, session, or API token is required. The attack is a single crafted HTTP POST to the public `/webhooks` endpoint, trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to select the webhook secret matches the owner parsed from `repository.full_name` before dispatching to handlers — i.e., reject the request if `payload.dig('repository','owner','login')` does not case-insensitively equal the owner segment of `payload.dig('repository','full_name')`. Alternatively, have handlers derive the target repository solely from the same field used for signature verification, and validate that any repository resolved via `full_name` belongs to the verified `repository_owner` before touching `Repository`/`Stack`/`Commit` records.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Fixture setup: `Repository` `org-attacker/attacker-repo` (owned by org-attacker) and `Repository` `org-victim/victim-repo` with a `Stack` on branch `master` and a `Commit` with `sha: "<victim_sha>"`.
2. Build payload:
   ```ruby
   body = {
     repository: { owner: { login: "org-attacker" }, full_name: "org-victim/victim-repo" },
     check_suite: { head_sha: "<victim_sha>", head_branch: "master" }
   }.to_json
   ```
3. Stub `Shipit.github(organization: 'org-attacker').verify_webhook_signature` to return `true` (simulating attacker's valid signature computed with their own known secret).
4. `Commit.any_instance.expects(:schedule_refresh_check_runs!)` (or assert an enqueued `RefreshCheckRunsJob` referencing the victim commit).
5. `post :create, body: body, as: :json` with `X-Github-Event: check_suite`.
6. Assert: **equality before** — `repository_owner` (`"org-attacker"`) used for signature verification ≠ owner parsed from `full_name` (`"org-victim"`) used for stack resolution; **assert this mismatch is never checked** and the job/mutation still fires against the victim's commit, proving the divergence.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
