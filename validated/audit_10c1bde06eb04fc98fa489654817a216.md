### Title
Malicious counterparty AA can permanently block a peer AA's state-changing action (e.g. loan repayment / escrow release) by always bouncing, forcing repeated fund forfeiture - (File: `aa_composer.js`)

### Summary
Any Autonomous Agent (AA) whose business logic sends a payment to a counterparty-controlled address (e.g. a lender, seller, or arbiter address in a P2P lending/escrow AA) is vulnerable to a griefing DoS if that counterparty registers their receiving address as another AA that unconditionally bounces. Because ocore automatically chains a "secondary trigger" to any AA address that receives a payment from another AA's response, and any bounce from that secondary AA forces the *entire* primary AA execution to `revert()`, an attacker-controlled counterparty AA can permanently prevent the primary AA from completing the state update it was trying to perform (e.g., marking a loan repaid and releasing collateral) — mirroring the reported `Cooler.sol` issue where a lender's `onRepay` callback revert blocks the borrower's repayment.

### Finding Description
When an AA's response messages include a `payment` to an address, `handleTrigger()` calls `handleSecondaryTriggers()` after finishing the primary response [1](#0-0) . If the destination address is itself an AA, it is automatically triggered as a secondary trigger with `bSecondary = true` [2](#0-1) .

If that secondary AA's execution bounces (returns an error), the entire outer (non-secondary) trigger chain is forced to `revert()`: [3](#0-2) 

`revert()` rolls back all state variable changes and balances to the savepoint taken before the primary trigger began, and then calls `bounce()`, which only refunds the triggering payment (minus bounce fee) back to the original sender — none of the intended state changes (e.g. recording a repayment, releasing collateral, updating an escrow status) are persisted: [4](#0-3) [5](#0-4) 

Note that a bouncing secondary AA does not even need to hold enough balance to pay its own bounce fees, since "being able to pay for bounce fees is not required for secondary triggers as they never actually send any bounce response or change state when bounced" [6](#0-5) . This means the attacker's malicious secondary AA can cheaply and unconditionally bounce every single time (e.g. an unconditional `bounce()` call in its formula), with no cost or countermeasure available to the victim AA author or the trigger sender, since AA definitions are immutable once posted (an unprivileged AA author can freely deploy such a malicious AA and register it as their "lender"/"counterparty" address before entering into an agreement).

This is directly analogous to the reported `Cooler.sol` bug: a decentralized lending/escrow AA design that forwards funds or notifications to a counterparty-controlled address exposes the borrower/payer to the counterparty's ability to indefinitely block completion of the repayment/release logic by making their AA counterparty always bounce, since ocore's engine treats *any* bounce in the secondary-trigger call chain as fatal to the whole transaction, not just to the misbehaving sub-branch.

### Impact Explanation
Any AA implementing peer-to-peer lending, escrow, marketplaces, or auctions that pushes funds/notifications to a user-supplied counterparty address is at risk: the counterparty can deploy a malicious AA at that address that always bounces on receipt, thereby freezing the primary AA's ability to ever record repayment/settlement and release the payer's locked collateral or funds — leading to unauthorized retention/loss of the payer's funds (AA fund loss/freezing), matching the "High" impact class from the source report. Because reverts extinguish *all* state changes of the primary trigger (not just the payment), the payer cannot even partially update loan/escrow bookkeeping to work around the malicious peer.

### Likelihood Explanation
Reachable by any two unprivileged AA authors/trigger senders: the attacker only needs to (1) author a small AA that unconditionally calls `bounce()`, and (2) have that AA's address accepted as the "lender"/"counterparty" address by a P2P-style AA (this is a common design pattern, as seen in `test/samples/payment_channels.oscript` and `test/samples/fundraising_proxy.oscript`, which forward payments to peer/counterparty addresses). No special privilege, hub/hardware access, or node compromise is required — only standard unit posting.

### Recommendation
- In the AA engine, consider not propagating a bounce of a *secondary* trigger as a fatal error to the primary trigger by default (or make this configurable per-message, e.g. a `"finish_on_bounce": false` message option), so that an AA author can choose to swallow failures from payments to external/counterparty-controlled addresses rather than have the whole execution reverted.
- Document prominently for AA authors that any payment message to a non-fixed/counterparty-supplied address risks being to an AA that bounces, and that doing so reverts the entire trigger; recommend using pull-based patterns (let the counterparty claim funds via their own explicit trigger, rather than push-based forwarding) for any P2P/lending/escrow AA design, analogous to the checks-effects-interactions / pull-payment recommendation for the original `Cooler.sol` report.

### Proof of Concept
1. Author AA `L` ("malicious lender") whose only message formula unconditionally calls `bounce('always fail')`.
2. Author AA `B` ("borrower/escrow") that, upon receiving a `repay` trigger from the borrower, sends the repayment amount to `L` and, in the same response, updates state (`var['repaid']=true`) to release collateral to the borrower.
3. Borrower posts a unit paying `B` with `data:{repay:true}`.
4. `B`'s primary trigger completes and forwards payment to `L`; `L` is auto-triggered as a secondary trigger and bounces.
5. Per `aa_composer.js:1743-1749`, `B`'s entire execution is reverted (`revert()`), so `var['repaid']` is never set and collateral is never released, while the borrower's bytes are refunded minus the bounce fee — the borrower can never successfully complete repayment as long as `L` keeps bouncing, exactly mirroring the `Cooler.sol` `onRepay`-revert scenario.
