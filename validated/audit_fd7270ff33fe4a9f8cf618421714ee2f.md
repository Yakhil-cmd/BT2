### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, unlike other handlers (e.g. `PullRequest::ClosedHandler`) which resolve the target via `Repository.from_github_repo_name(params.repository.full_name)`. Any commit sharing a SHA with a webhook's `sha` field — regardless of which repository the webhook actually originated from — gets a `Status` record created against it, which feeds directly into `Stack#next_expected_commit_to_deploy` and `UndeployedCommit#expected_to_be_deployed?`.

### Finding Description
The claimed binding is: **the Status written for a commit must only be derived from a webhook whose `repository.full_name` matches that commit's own `stack.repository`.** Tracing the code shows this binding is broken.

`Shipit::Webhooks::Handlers::StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha` alone — it never consults `payload.dig('repository','full_name')`, never calls the base `Handler#stacks`/`repository_name` helpers, and never filters to a single stack. Compare with `Handler#stacks`, which other handlers use to correctly scope by repository:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [2](#0-1) 

`Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using the commit's own `stack_id` [3](#0-2) , and `Status.replicate_from_github!` unconditionally creates a `Status` row for that `stack_id`/`state` [4](#0-3) .

That new Status then feeds `Stack#next_expected_commit_to_deploy`, which rejects `active?` commits and finds the first `deployable?` one from `undeployed_commits` [5](#0-4) , which is passed into `UndeployedCommit#expected_to_be_deployed?` [6](#0-5) , driving both the dashboard state and `ContinuousDeliveryJob`/`trigger_continuous_delivery` behind `Stack#continuous_deployment` [7](#0-6) .

**Why existing guards don't help:** `WebhooksController#verify_signature` only checks the HMAC signature against the GitHub App keyed by `repository_owner` taken from the payload itself (`params.dig('repository','owner','login')`) [8](#0-7) . It authenticates that the payload really came from GitHub for *that* repository/organization — it does **not** verify that the `sha` referenced belongs to that same repository. An attacker who owns any repository connected to Shipit (their own fork, or any registered repo/org) can legitimately trigger a real, correctly-signed `status` webhook from GitHub for a commit SHA they control. If that SHA happens to coincide with a commit that also exists in a victim's stack (trivial via a fork sharing unmodified upstream history, or via any other means of SHA collision/coincidence across tracked repos), `Commit.where(sha: params.sha)` matches **every** such commit across **every** stack in the Shipit instance and writes a `Status` for each of them, including the victim's.

Exploit flow:
1. Attacker forks/owns a repository containing a commit whose SHA is identical to a commit already tracked in a victim's `continuous_deployment` stack (e.g., unmodified upstream commit inherited via fork).
2. Attacker's repository is registered as a Shipit-tracked repo (or otherwise wired to fire a legitimately GitHub-signed `status` webhook) targeting that shared SHA with `state: "success"`.
3. `StatusHandler#process` finds all `Commit` rows with that `sha`, including the one belonging to the victim's stack, and creates a `Status` for it.
4. `Stack#next_expected_commit_to_deploy` recomputes using the forged status, `UndeployedCommit#expected_to_be_deployed?` returns `true` for that commit in the victim's dashboard, and continuous delivery logic considers it deployable.

### Impact Explanation
This is a cross-tenant write: a status webhook that GitHub legitimately signs for the attacker's own repository results in a `Shipit::Status` record being written against a commit belonging to a different, unrelated stack that the attacker does not control and never authenticated for. This directly manipulates `deployable?`/`expected_to_be_deployed?` computation used by the dashboard and by `Stack#trigger_continuous_delivery`, i.e., it can influence which commit an operator believes is queued for deploy and can accelerate/mislead automated deploy decisions for a victim's `continuous_deployment` stack — matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Requires: the victim stack tracks a commit whose SHA coincides with a commit in a repository the attacker controls/owns (straightforward via forking a public repo that shares unmodified history, which is a common and cheap scenario for public/OSS-tracked stacks), and the attacker's own repo/org must be Shipit-webhook-connected (achievable by the attacker themselves if they can add a webhook pointing at the Shipit host for a repo they own — no special Shipit privilege is needed, only the ability to configure a webhook on their own GitHub repo). No Shipit session, API token, or secret is needed. This is repeatable for any repo/stack pair with overlapping commit SHAs.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/stacks resolved from the webhook payload (mirroring `Handler#stacks`/`repository_name`) instead of a bare `Commit.where(sha: params.sha)`, e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }`, ensuring a Status is only ever applied to commits whose `stack.repository` matches `payload.dig('repository','full_name')`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "process only updates commits belonging to the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # different repository

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.repository.full_name }
  }

  StatusHandler.call(payload)

  assert_equal 1, attacker_commit.reload.statuses.count
  assert_equal 0, victim_commit.reload.statuses.count, "status must not leak into a different repository's commit"
end
```
Before the fix, both `attacker_commit` and `victim_commit` receive a `Status` (assertion on `victim_commit.statuses.count` fails, proving the binding is broken); after scoping the lookup by `stacks`, only `attacker_commit` gets the status.
