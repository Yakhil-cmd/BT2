Confirmed contrast: `CheckSuiteHandler#process` scopes via `stacks.where(branch: ...)` (i.e., `Repository.from_github_repo_name(repository_name)&.stacks`) before touching commits by sha [1](#0-0) , and `PushHandler` similarly scopes via `stacks` filtered by the payload's `repository.full_name` through the base `Handler#stacks`/`#repository_name` methods [2](#0-1) . `StatusHandler#process`, by contrast, queries `Commit.where(sha: params.sha)` globally across the entire `commits` table with no join to `stacks`/`Repository.from_github_repo_name`, then calls `commit.create_status_from_github!(params)` on every match [3](#0-2) .

### Title
Webhook `status` events create statuses on commits regardless of originating repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `by sha` across the whole `Commit` table and calls `create_status_from_github!` on every match, without ever checking that the webhook's `repository.full_name` corresponds to `commit.github_repo_name`. Since `Commit#sha` is not scoped or validated to be unique to one repository at the application layer, and a legitimate, independently-signed webhook from any repository the attacker controls can carry an arbitrary `sha` value, this lets a payload from repository A silently attach a CI status (and any consequence that flows from it, e.g. `continuous_deployment`) to a commit belonging to an unrelated stack/repository B.

### Finding Description
Binding claimed: `commit.github_repo_name == status_payload.repository.full_name` must hold for every call to `Commit#create_status_from_github!`, since `refresh_statuses!` establishes this by fetching statuses directly `stack.github_api.statuses(github_repo_name, sha, ...)` [4](#0-3)  - the API call is inherently scoped to the commit's own stack's repo.

`StatusHandler#process`, reached from `WebhooksController#create` → `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)` [5](#0-4) [6](#0-5) , does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This never touches `stacks` / `repository_name` (the base `Handler` class exposes exactly this scoping helper, unused here) [2](#0-1) , unlike its siblings: `PushHandler` restricts to `stacks.not_archived.where(branch:)` [7](#0-6)  and `CheckSuiteHandler` restricts to `stacks.where(branch: ...)` before touching `stack.commits` [1](#0-0) .

`Commit#create_status_from_github!` itself has no way to reject foreign-repo data - it just persists whatever `github_status` it is given via `statuses.replicate_from_github!(stack_id, github_status)` [8](#0-7) , and the shared `Status.replicate_from_github!` reads only `state`/`description`/`target_url`/`context`/`created_at` from the object, with no repository field at all [9](#0-8) .

Signature verification (`WebhooksController#verify_signature`) only proves the payload was signed by the GitHub App installation for `repository_owner` (the org/owner of the *sending* repo); it says nothing about which `sha`s that installation is authorized to report statuses for [10](#0-9) . `Commit.sha` has only a `(stack_id, sha)` index for lookup, not a global uniqueness/repo-binding constraint (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), so nothing in the model layer prevents the same `sha` value from resolving to commits belonging to different stacks/repositories (which routinely happens for forked repositories that share git history).

Exploit flow: an attacker forks (or otherwise obtains write access to) a repository that shares git history/commit SHAs with a victim's tracked repository (a very common situation for public projects with Shipit-tracked forks/mirrors), installs/owns a GitHub App/webhook config on their own repo, and triggers (or has GitHub trigger) a `status` event for a shared commit SHA - a fully valid, correctly-signed webhook for the attacker's own repository. Shipit's `StatusHandler` will match that SHA against `Commit` records from any stack in the instance and apply the status, even though the payload's `repository.full_name` never matched `commit.github_repo_name`.

### Impact Explanation
A successful call writes a `Status` row (e.g. `state: 'success'`) onto a commit belonging to a stack the attacker does not control [8](#0-7) . `Status#after_create` schedules `commit.schedule_continuous_delivery`, and `Commit#deployable?`/CD gating relies on `success?` [11](#0-10) [12](#0-11) , so a forged/foreign "success" status can unblock and trigger an unauthorized deploy on a victim stack with `continuous_deployment` enabled - matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). This is repeatable against any stack whose tracked repo shares SHAs with an attacker-controlled repository, and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the Shipit instance must host multiple stacks/tenants, and the target commit SHA must exist in an attacker-reachable repository (trivially true for forks of public/shared repos, since git preserves commit SHAs across forks until history diverges). No Shipit session, API token, or webhook secret theft is required - the attacker only needs a valid, independently-signed webhook for their own repo, which they can legitimately obtain by owning that repo/App installation. This is a real, low-cost, repeatable path, not a theoretical hash-collision scenario.

### Recommendation
In `StatusHandler#process`, scope the lookup through `stacks` (the `repository_name`-derived scope already provided by `Handler`) the same way `PushHandler`/`CheckSuiteHandler` do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to stacks whose `Repository` matches the payload's `repository.full_name` are updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `stack_a` (repo `attacker/repo`) and `stack_b` (repo `victim/repo`), each with a `Commit` sharing identical `sha: 'deadbeef'` (representing a forked shared history).
2. Build a `status` webhook payload with `repository.full_name = 'attacker/repo'` and `sha: 'deadbeef'`, `state: 'success'`.
3. Assert equality-before: `commit_b.github_repo_name != payload['repository']['full_name']` (i.e. `'victim/repo' != 'attacker/repo'`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing controller-level signature check, as in existing handler tests).
5. Assert equality-after is still violated yet the write succeeded: `commit_b.statuses.reload.last.state == 'success'` even though `commit_b.stack.github_repo_name != 'attacker/repo'` - proving the method wrote data for a repository that never authenticated it.
6. Contrast with `commit_a.refresh_statuses!`/`create_status_from_github!` call path already covered by `test/models/commits_test.rb:329-342`, which is correctly scoped via `stack.github_api.statuses(@stack.github_repo_name, ...)`.
