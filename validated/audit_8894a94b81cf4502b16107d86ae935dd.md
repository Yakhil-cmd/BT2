I found a concrete binding break: the webhook signature verification key is chosen based on `repository.owner.login` (or `organization.login`), but the actual write target (which `Stack`/`Repository` gets mutated) is chosen based on `repository.full_name`. These two fields are never required to agree.

### Title
Webhook signature verified against wrong organization's secret allows cross-repository writes via mismatched `repository.owner.login` vs `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` [1](#0-0) . But the handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a completely different field: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing enforces that `repository.owner.login` and the owner embedded in `repository.full_name` refer to the same organization.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` reads `params.dig('repository','owner','login')` [1](#0-0) . In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple GitHub Applications"), each organization has its own `webhook_secret` in `config/secrets.yml`.

Once signature verification passes, `WebhooksController#create` parses the same raw JSON body and dispatches to handlers using `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler resolves the affected repository via `Handler#repository_name`, i.e. `payload.dig('repository', 'full_name')` [4](#0-3) , and looks it up with `Repository.from_github_repo_name(repository_name)&.stacks` [5](#0-4) .

The two lookups—`repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the repository actually acted upon)—are independent JSON fields inside the same signed payload. If an attacker who legitimately controls a webhook secret for "orgA" (e.g., they are an admin of a repo/org that installed the Shipit GitHub App and thus know or can trigger deliveries with `orgA`'s `webhook_secret`) crafts a raw payload where `repository.owner.login == "orgA"` but `repository.full_name == "orgB/other-repo"`, the signature will validate using `orgA`'s secret (which passes, since the attacker signs correctly with the secret they have), yet the `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. will act on `orgB/other-repo`'s `Stack`, e.g. triggering `GithubSyncJob`, creating commit statuses, or driving `check_suite`/`merge`/`pull_request` state transitions for a completely different organization's stack that this attacker was never authorized to write to.

This is the same class of bug as the analog report: a value used for authorization/verification (`webhook_secret` selection keyed by `repository.owner.login`) is decoupled from the value that determines what gets mutated (`repository.full_name`), exactly like the BitVMBridge `mint` call trusting confirmation-count validation while never checking the transaction's actual destination.

### Impact Explanation
This breaks the binding: `organization authenticated (webhook_secret owner)` == `repository written (full_name)`. An attacker holding webhook credentials for one organization installation can force Shipit to process fabricated GitHub events (push, status, check_suite, pull_request, membership) against stacks belonging to a different organization/repository that they do not control, potentially triggering `GithubSyncJob`, fabricating commit statuses that feed into merge-queue/CI gating (`StatusHandler`, `MergeRequest#all_status_checks_passed?`), or otherwise corrupting cross-repository stack state — a cross-repository write, satisfying the Critical impact bar.

### Likelihood Explanation
Requires the attacker to have a legitimate (even low-privilege) webhook secret for at least one organization onboarded to the same Shipit instance — realistic in the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications") where multiple, differently-trusted organizations share one Shipit deployment. No repository write access, `ApiClient` token, or session is needed; only the ability to sign a raw JSON payload with a `webhook_secret` already possessed for one org, and free-form control over the JSON body being signed (since the attacker is constructing the raw payload themselves, e.g. via `curl`, not going through GitHub's UI).

### Recommendation
In `WebhooksController#verify_signature`/`#create`, derive the organization used for signature verification and the repository used for handler dispatch from the same, single trusted field, and cross-check them: e.g., verify that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching, or better, resolve the target `Stack`/`Repository` and confirm its owner matches the `github_app`'s configured organization prior to invoking any handler.

### Proof of Concept
1. Assume Shipit is configured with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker has (or can derive/leak in a low-trust way) `orgA`'s `webhook_secret`.
3. Attacker crafts a raw JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist in orgB/target-repo>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and sends it with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against `orgA`'s secret [6](#0-5) .
6. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/target-repo")` via `full_name` and enqueues `GithubSyncJob`/mutates `orgB`'s stack [2](#0-1) , [7](#0-6) , despite the signature only proving authorization for `orgA`.
