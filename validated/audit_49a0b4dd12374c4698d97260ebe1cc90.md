The `identify_user` mechanism in `app/controllers/shipit/api/base_controller.rb` binds a request's asserted GitHub identity to a `User` record purely by string match on an unauthenticated header, without any verified signature over that value — this is the same class of bug as the report: a value that gets acted upon (attribution/authorization context) is never covered by the thing that actually authenticates the request (the `ApiClient` token).### Title
Unauthenticated `X-Shipit-User` header lets any valid API-token holder attribute deploys, rollbacks, and tasks to an arbitrary Shipit user - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The equality that should hold is: `identity authenticated by the request's credentials == identity recorded as the actor of the resulting deploy/rollback/task`. In Shipit's API, the only thing that is actually authenticated is the `ApiClient` bearer token via HTTP Basic auth (`authenticate_api_client`). The `User` that gets bound to the created `Deploy`/`Rollback`/`Task` record (`current_user`) is instead derived from an arbitrary, unsigned `X-Shipit-User` request header. This breaks the binding described by the report's bug class: a value ("who performed this action") is acted upon by privileged application logic but is never covered by the thing that actually authenticates the request.

### Finding Description
`app/controllers/shipit/api/base_controller.rb` authenticates requests solely via `authenticate_api_client`, which validates an `ApiClient` bearer token: [1](#0-0) 

Separately, `current_user` — the actor that gets persisted on the created resource — is derived from `identify_user`, which trusts a plain, client-supplied header with no signature or verification: [2](#0-1) 

This `current_user` is passed straight through to the model layer as the acting user for privileged operations, e.g. in `Api::DeploysController#create`: [3](#0-2) 

and `Api::TasksController#trigger`: [4](#0-3) 

The engine's own tests confirm the header is taken at face value, matched case-insensitively against `User.login`, with no ownership check tying it to the presenting `ApiClient`: [5](#0-4) 

The `User` model has no secret associated with `login`; anyone who knows (or guesses) a login can be impersonated as `deploy.user`, `rollback.user`, or `task.user`: [6](#0-5) 

The binding that is broken: the `ApiClient` token authorizes "some client with permission `deploy:stack` may act on this stack," but the identity written into the audit trail/authorship (`deploy.user`, used for hooks, notifications, "SHIPIT_USER"/"EMAIL" environment variables injected into the deploy shell environment via `TaskCommands#env`) is an unauthenticated, attacker-chosen value: [7](#0-6) 

### Impact Explanation
Any holder of a valid `deploy:stack`/`lock:stack` `ApiClient` token (which is a lower trust tier than a full user session, and is explicitly the kind of credential many integrations hold) can forge the identity of arbitrary Shipit users for deploys, rollbacks, and custom tasks. This lets an attacker with only an API token:
- Falsely attribute a deploy/rollback/task to another (potentially more privileged-looking or trusted) user in the Shipit UI, hooks payloads, and shell environment (`SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME/EMAIL`), enabling spoofed/unauthorized deploys with a misleading actor identity.
- Undermine any downstream authorization or auditing logic in a host application that trusts `deploy.user`/`task.user` to reflect who actually acted (e.g., "requires approval from someone other than the author" checks, notification routing, or accountability trails).

This does not directly leak `GITHUB_TOKEN` or achieve RCE by itself, but it produces an unauthorized/deceptively-attributed deploy — matching the report's "High" impact bucket around authentication/authorization-context confusion — because the ApiClient's authenticated scope ("this token, this stack, this permission set") is never bound to the identity value it's allowed to assert.

### Likelihood Explanation
Likelihood is high for any deployment where `ApiClient` tokens are distributed to CI systems or third-party integrations (a documented, expected use case) rather than only trusted human sessions. The header is a plain HTTP header with no cryptographic binding, no rate limiting concern being relied upon, and is exercised routinely (it's part of the documented/tested API contract), so exploitation requires no more than an existing valid token and knowledge of another user's `login`.

### Recommendation
Bind the acting identity to the authenticated credential rather than an arbitrary header: either (a) resolve `current_user` from the `ApiClient#creator` association when a claimed user isn't cryptographically tied to the client, (b) restrict honoring `X-Shipit-User` to `ApiClient`s explicitly granted an "impersonation" permission scoped to specific users, or (c) require a signed assertion (e.g. signed by the API-client's own secret, or validated against GitHub) for any claimed identity, and reject the header for tokens lacking that scope.

### Proof of Concept
1. Create/obtain an `ApiClient` token with only `deploy:stack` permission (e.g. issued to a CI pipeline).
2. Send `POST /shipit/:owner/:repo/:env/deploys.json` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim_login>`.
3. Observe that `Deploy.last.user` equals the victim user record, as demonstrated by the engine's own test: [8](#0-7) 
4. The deploy proceeds, its GitHub hooks, UI, and shell environment (`SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME/EMAIL`) all attribute the action to the victim, despite the request having been authenticated only as the CI token holder, not as the victim.
