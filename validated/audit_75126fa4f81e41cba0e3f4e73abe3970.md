### Title
Server-Side Request Forgery via unrestricted `fetchUrl` on attacker-supplied `definition` URL in `uri.js` deep-link parser - (File: `uri.js`)

### Summary
`parseUri()` in `uri.js` accepts `byteball:`/`obyte:` deep links of the form `data?app=definition&definition=<url>`. When the `definition` parameter starts with `https://`, the parser automatically performs an outbound HTTP GET to that attacker-controlled URL via `fetchUrl()`, with no restriction on the target host, port, or IP range, and returns the raw response body to the wallet as the resolved address definition. [1](#0-0) [2](#0-1) 

### Finding Description
`parseUri` is the exported deep-link handler (`exports.parseUri`) used by Obyte wallets/GUIs to interpret `byteball:`/`obyte:` links — e.g. links pasted in chat, embedded in QR codes, or clicked from any source presented to the user. [3](#0-2)  When the link encodes `app=definition` and a `definition` value beginning with `https://`, the code unconditionally calls `fetchUrl(definition, ...)`, which performs `https.get(url, ...)` with no allow-list, no restriction against internal/private IP ranges or non-standard ports, no response-size cap, and no timeout:

This is the direct analog of BIT-gitlab-2022-2527: an attacker crafts malicious content (here, a link/URI rather than an Incident Timeline event) that, once the victim interacts with it in their normal workflow (opening a payment/definition link), causes the victim's client to issue an arbitrary, attacker-directed HTTP request. There is no host validation preventing the target from being `localhost`, cloud-metadata endpoints, or other services reachable only from the victim's network — i.e. a classic SSRF gadget baked into the wallet's own link-handling code, reachable by any unprivileged party who can get a victim to open a link (chat message from a paired device, shared QR code, etc.).

### Impact Explanation
Any party able to deliver such a URI to a victim (a paired device sending it as chat text, a shared link/QR code, etc.) can force the victim's wallet process to make outbound HTTPS requests to arbitrary hosts, including internal/private network addresses reachable from the victim's machine. This enables SSRF-style network reconnaissance/pivoting from the victim's host, and because the fetched response is fed back as the "definition" and surfaced to the wallet flow with no sanitization, a malicious or unexpected response could also mislead the victim into approving an unintended address definition. This falls squarely within "wallet and contract message handling" reachable by an unprivileged paired device or link sender.

### Likelihood Explanation
High. No cryptographic proof or on-chain unit is required — merely convincing a victim to open a crafted `obyte:`/`byteball:` link (a normal wallet workflow for sending/receiving payments or definitions) triggers the request automatically, without further confirmation prompts in the URI-parsing code itself.

### Recommendation
- Remove or gate the automatic `fetchUrl` behavior for `app=definition` links; if remote-fetch is needed, restrict to an explicit allow-list of trusted hosts, enforce HTTPS with certificate pinning, block private/loopback/link-local/metadata IP ranges (SSRF protections), enforce request timeouts and response size limits, and require explicit user confirmation showing the target host before fetching.
- Validate that the fetched content is a well-formed address definition (as done elsewhere via `Definition.validateDefinition`) before accepting it, and never fetch a URL derived directly from unauthenticated input without confirming the target is not an internal resource.

### Proof of Concept
1. Attacker crafts a link: `obyte:data?app=definition&definition=https://attacker.example.com/or/https://169.254.169.254/latest/meta-data/` (URL-encoded as needed) or a link pointing to an internal service, e.g. `https://127.0.0.1:6832/`.
2. Attacker sends this link to a victim (e.g. as chat text via a paired device, or a shared QR code / web link).
3. Victim's wallet calls `uri.parseUri(uri, callbacks)` when the link is opened (as part of normal payment/definition-link handling).
4. `parseUri` detects `app === 'definition'` and `definition.substr(0,8) === 'https://'`, and calls `fetchUrl(definition, ...)`, which issues `https.get()` to the attacker-chosen URL from the victim's machine/network context — demonstrating SSRF. [4](#0-3) [5](#0-4)

function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
