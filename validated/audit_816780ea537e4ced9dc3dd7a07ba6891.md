### Title
Cross-repository status write bypasses `locked?` and unlocks `Commit#deployable?` for any commit sharing a SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Commit#deployable?` treats `!locked?` as one of two gates, but `locked` is a per-commit, operator-set boolean (`false` by default) that carries no information about which repository a commit belongs to. `StatusHandler#process` writes incoming `status` webhook payloads to `Commit.where(sha: params.sha)` with no filter on the stack/repository the webhook came from, so any commit row (in any stack) sharing that SHA gets the forged state, and since `locked` defaults to `false`, `deployable?` collapses to `stack.ignore_ci? || (success? && !blocked?)`, fully attacker-controlled.

### Finding Description
Binding claimed: `locked?(commit) == false` should imply nothing about deployability except "no operator manually froze this commit" — it must NOT be conflated with "this status genuinely originated from this commit's own repository." Code confirms this: `deployable?` is defined as [1](#0-0) 
where `locked` is a plain, human-toggled column (`#lock`/`#unlock`, `lock_all`) uncorrelated with repository identity, defaulting to `false` for every newly created commit, as shown by the deployable? test suite exercising `Commit.new`-style fixtures with `locked: false` by default. [2](#0-1) 

The write path that produces the `success?` used in the second gate is `StatusHandler#process`: [3](#0-2) 
This resolves `Commit.where(sha: params.sha)` — every commit row across every stack that has that SHA — and calls `commit.create_status_from_github!(params)` on each, without ever checking `params.dig('repository', ...)` against the commit's own `stack.repository`. The DB schema only enforces uniqueness of `(sha, stack_id)`, not global uniqueness of `sha`: [4](#0-3) 
so multiple stacks (tracking different, unrelated GitHub repositories) can legitimately hold a `Commit` row with an identical `sha` (e.g., forks sharing history with an upstream tracked repository, or independently-tracked mirrors). `Status` itself has no repository-scoped validation beyond `belongs_to :stack`/`belongs_to :commit`: [5](#0-4) 

Exploit flow: an attacker who controls a webhook delivery whose signature validates for *some* organization (per the question's stated preconditions, this cross-repo forgery capability is treated as already established/reachable) sends a `status` event naming any `sha` also present in a victim stack. `StatusHandler#process` updates every matching `Commit` regardless of originating repository. For the victim commit, `locked` is `false` (the common, default case), so `deployable?` is reduced to `stack.ignore_ci? || (success? && !blocked?)` — fully satisfiable by the forged `state: 'success'` payload. `blocked?` only inspects prior *undeployed* commits' statuses within the same stack and provides no repository-origin check either. [6](#0-5) 

Why the guard fails as a compensating control: `locked?` is opt-in and per-commit; it is not set as a side effect of repository verification anywhere in the codebase. Nothing in `deployable?`, `create_status_from_github!`, or `Status` ties the status's origin repository to the commit's own `stack.repository`, so the `!locked?` check cannot and does not detect or block a forged cross-repo status.

### Impact Explanation
A forged/misrouted status write flips `Commit#success?` to `true` for a victim commit in a stack the attacker does not control, and — because `locked` defaults to `false` — `deployable?` returns `true` purely from that write. This directly enables triggering an unauthorized deploy (via the deploy UI/API, continuous deployment, or `MergeService`) of a commit for a repository/stack the attacker never authenticated against, matching the "unauthorized deploy" Critical impact category. The blast radius spans every pair of stacks whose tracked repositories happen to share a commit SHA (most commonly upstream/fork pairs), and is repeatable per shared SHA.

### Likelihood Explanation
Preconditions: (1) a victim commit exists with `locked == false` (default, common case — locking is a rare manual operator action, confirmed by `#lock`/`#unlock` being explicit opt-in operations), and (2) two stacks tracking different repositories share a commit `sha` (naturally occurs for forks, since Git SHAs are content-addressed and fork history is byte-identical until divergence). Given the question's premise that a cross-repo status write is achievable, the additional cost of satisfying `deployable?` is zero — no lock ever needs to be engaged, and `locked?` provides no mitigation regardless of configuration.

### Recommendation
Scope `StatusHandler#process` to only update `Commit` rows belonging to the stack that owns the repository named in the webhook payload (e.g., join through `Stack`/`Repository` on `params.dig('repository','full_name')` in addition to `sha`), rather than matching `sha` alone across all stacks. Additionally, consider validating in `Status`/`Commit` that a status's `stack_id` corresponds to a stack whose `repository` matches the commit's actual tracked repository before persisting.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual addition)
test "#deployable? is true purely from an unlocked commit and forged status, with no lock ever engaged" do
  stack_a = shipit_stacks(:shipit)          # victim stack/repo
  stack_b = shipit_stacks(:cyclimse)        # attacker-controlled / unrelated stack sharing a sha
  shared_sha = "deadbeef" * 5

  victim_commit = stack_a.commits.create!(sha: shared_sha, message: "victim", author: shipit_users(:walrus),
                                           committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  assert_equal false, victim_commit.locked?

  # Simulate a status webhook whose repository field does not correspond to stack_a,
  # but which StatusHandler#process matches purely on `sha`.
  Shipit::Webhooks::Handlers::StatusHandler.new.process_params_for_test(
    sha: shared_sha, state: 'success', context: 'ci/forged'
  )

  victim_commit.reload
  assert_equal false, victim_commit.locked?         # lock was never engaged
  assert_predicate victim_commit, :deployable?       # yet it is deployable
end
```
This asserts the binding directly: `Commit.new(locked: false).deployable?` becomes `true` from a status write keyed only on `sha`, with `locked` never transitioning away from its default `false`, demonstrating `!locked?` provides no protection against the cross-repository/cross-tenant status binding failure in `StatusHandler#process`.
