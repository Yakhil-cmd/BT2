### Title
Rounding of headers-commission shares can mint extra bytes - ([File: headers_commission.js])

### Summary
`CashAsset.withdraw()`'s bug class is "an amount is rounded before being applied, and the rounding is not reconciled against the real available/owed total, so the rounded value can exceed the true value." The same rounding-without-reconciliation pattern exists in `ocore`'s headers-commission distribution logic, where each recipient's share of a headers commission is independently rounded, and the rounded shares are summed and paid out without ever being capped to the original commission amount.

### Finding Description
When a unit wins the headers commission of a parent unit, the amount (`full_amount`, equal to `punits.headers_commission`) is split among the winning unit's `earned_headers_commission_recipients` according to each recipient's percentage `earned_headers_commission_share`. Each recipient's payout is computed independently with simple rounding: [1](#0-0) 

and, in the SQL/mysql code path, the same independent rounding is applied per row: [2](#0-1) 

`validateHeadersCommissionRecipients()` only checks that the *percentages* sum to exactly 100 — it never checks that the *rounded byte amounts* sum to the original `headers_commission`: [3](#0-2) 

Because `Math.round()` (and SQL `ROUND()`) round `.5` away from zero, a poster can choose shares that make each recipient's fractional allocation land exactly on a half-integer boundary. For example, with `full_amount = 3` and two recipients at `50%`/`50%`, each recipient's exact share is `1.5`, which `Math.round` rounds up to `2`, so `2 + 2 = 4` bytes are paid out for a commission that was only `3` bytes. The extra byte is never subtracted from anywhere — it is simply created and inserted into `headers_commission_contributions` → `headers_commission_outputs`: [4](#0-3) 

Author addresses fully control the `earned_headers_commission_recipients` array of their own multi-authored unit (they just need ≥2 authors and can pick both), and the unit that has no sibling contenders for a parent's commission (the common case where a unit is the sole child built on top of its parent) automatically wins that parent's commission with no external randomness involved. This gives a single poster full control over both the split percentages and (in the common non-competitive case) the winning outcome, letting them deterministically choose an odd `headers_commission` value together with a 50/50 (or similarly crafted) split to mint one extra byte of native currency per exploited unit.

### Impact Explanation
This is a supply-inflation bug: the total `headers_commission_outputs` recorded for the network can exceed the total `headers_commission` actually paid by the parent units, minting bytes out of thin air. Repeated over many units/authors, an attacker (or colluding group of two addresses) can accumulate free bytes indefinitely, which is a Medium/High severity issue on a value-bearing ledger.

### Likelihood Explanation
Likelihood is limited by the size of the gain per exploited unit — at most a fraction of a byte rounded up per recipient (bounded by ~0.5 unit per recipient, so at most `N × 0.5` extra units for `N` recipients) — and by the need to control the odd/even parity of `headers_commission` together with the recipient split, and to actually be selected as the winning child of the parent unit (guaranteed only when there is no other candidate child at that MC index, which is common for a self-built chain of own units but not universal). This makes it a low-magnitude-per-instance but systematically repeatable inflation vector, matching the "unlikely to matter much per instance" character noted for the original CashAsset finding, while still being a genuine protocol invariant violation.

### Recommendation
When distributing `full_amount` among `earned_headers_commission_recipients`, do not round each share independently. Instead, compute all shares, round all but the last recipient, and assign the last recipient the remainder (`full_amount - sum_of_already_rounded_shares`), guaranteeing the total paid always equals `full_amount` exactly. Apply the same fix to both the SQL (mysql) query path and the in-memory/sqlite computation path in `headers_commission.js`.

### Proof of Concept
1. Attacker controls two addresses, A and B.
2. Attacker posts a 2-author unit U (authors A and B) as the sole child built on top of a parent unit P whose `headers_commission` is an odd number, e.g. `3`.
3. U sets `earned_headers_commission_recipients = [{address:A, earned_headers_commission_share:50}, {address:B, earned_headers_commission_share:50}]`, which passes `validateHeadersCommissionRecipients` since `50+50=100`.
4. When U becomes stable and is the only candidate child of P (default case for a unit's own successor), `calcHeadersCommissions()` computes each recipient's payout as `Math.round(3*50/100) = Math.round(1.5) = 2`, for both A and B.
5. `headers_commission_outputs` therefore credits A and B a total of `4` bytes although P's `headers_commission` was only `3`, minting 1 extra byte that A and B can later spend via headers_commission-type inputs.
