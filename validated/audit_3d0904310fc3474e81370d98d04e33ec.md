### Title
Webhook signature is bound to the payload's organization, but handlers act on an unverified `repository.full_name`/global commit `sha` from the same payload, allowing cross-organization commit-status forgery and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` taken from the unverified JSON body, then verifies the *entire* raw body against that secret [1](#0-0) . Once the signature matches, the handlers dispatched by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1)  trust *other* fields of that same JSON body — `repository.full_name` (`Handler#repository_name`) [3](#0-2)  and, worse, an unscoped `sha` for the `status` event — to decide which stack/commit the webhook affects. The binding that is verified (“this payload was signed by organization X’s webhook secret”) is not the same as the binding that is acted upon (“apply this payload to repository/commit Y”), and nothing cross-checks that `Y` belongs to `X`.

### Finding Description
Any organization/repository owner who has legitimately connected their own repository to this Shipit instance (a normal, unprivileged onboarding action, not requiring any Shipit session, API token, or admin access) knows the value that `Shipit.github(organization:)` uses as `webhook_secret` for their own org, because they configured the GitHub App/webhook for their org themselves. That is enough to compute a valid `X-Hub-Signature` for **any** payload body they construct, as long as `repository.owner.login` inside that body matches their own org (so `Shipit.github(organization: repository_owner)` resolves to their own known secret) [1](#0-0) .

Nothing stops that same forged JSON body from carrying a different `repository.full_name` or an arbitrary commit `sha` belonging to a completely different, victim, stack:

- `StatusHandler#process` does `Commit.where(sha: params.sha)` with **no scoping to any repository or stack at all** [4](#0-3) . Since commit SHAs are effectively public (visible via GitHub, PRs, etc.), an attacker who only controls their own org's webhook secret can forge a `status` webhook whose `sha` points at a victim's commit in a completely unrelated stack, and call `commit.create_status_from_github!(params)` to inject an arbitrary CI status (`state`, `context`, `target_url`, `description`) for that commit [5](#0-4) .
- `PushHandler` and `CheckSuiteHandler` at least scope to `Repository.from_github_repo_name(repository_name)` [3](#0-2) , but `repository_name` comes from the same unverified `full_name` field, not from the org that was actually authenticated by the signature — so an attacker who owns org A can address stacks belonging to org B simply by putting `"full_name": "org-b/repo"` in the payload while keeping `"owner": {"login": "org-a"}` for signature purposes.

This breaks the equality that should hold: `organization authenticated by signature == organization owning the repository/commit acted upon`. Before an attacker's request: signature-verified org A can only affect org A's stacks. After: signature-verified org A can affect any stack/commit in the whole Shipit instance because the acted-upon identity (`full_name`/`sha`) is never cross-checked against the authenticated identity (`repository.owner.login`).

### Impact Explanation
Commit deployability is gated by `Commit#deployable?`, which is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?` is derived from `status`, which is populated from `statuses` created via `create_status_from_github!` [6](#0-5) [7](#0-6) . A forged `status` webhook that marks a victim commit “success” for the required status contexts can make an otherwise CI-blocked/undeployed commit `deployable?`, and combined with `continuous_deployment?` this can even auto-trigger `ContinuousDeliveryJob` [8](#0-7) , or simply let a user with UI/API deploy rights trigger a deploy of a commit that never actually passed CI — an unauthorized deploy driven by cross-organization webhook forgery. This qualifies as Critical under the report's rules (“unauthorized deploy”).

### Likelihood Explanation
Requires only that the attacker control (own or administer) any single organization that is legitimately configured with a Shipit `webhook_secret` — a normal, unprivileged use of the product, not a privileged Shipit account, API token, or GitHub write access to the victim repository. Commit SHAs of the target are typically discoverable (public repos, PR pages, CI systems). No TLS interception, session, or social engineering is required, matching the "unprivileged attacker" and "webhook_secret not required to be the victim's" bar the rules ask for.

### Recommendation
After verifying the HMAC signature, cross-check that the resolved `repository_owner` (used to select the secret) actually matches the owner embedded in `repository.full_name` (and, for `StatusHandler`, scope the `Commit` lookup through the stack/repository derived from the verified organization, not a bare global `sha` lookup). Reject the webhook if these identities disagree.

### Proof of Concept
1. Attacker legitimately connects `attacker-org/some-repo` to the shared Shipit instance; this yields a known `webhook_secret` for `attacker-org` in `Shipit.github(organization: 'attacker-org')`.
2. Attacker discovers the SHA of a commit belonging to `victim-org/victim-repo` (e.g., from GitHub’s public commit history or a PR).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status` and a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
   and signs the raw body with `attacker-org`'s known `webhook_secret`, sending the resulting value as `X-Hub-Signature`.
4. `verify_signature` resolves the secret via `repository_owner` = `attacker-org` and successfully validates the signature [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim commit regardless of repository, then calls `create_status_from_github!`, injecting a forged "success" status for `victim-org/victim-repo`'s commit [4](#0-3) [5](#0-4) .
