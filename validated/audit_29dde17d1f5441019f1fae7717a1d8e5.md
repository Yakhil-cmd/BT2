### Title
CCMenuController#stack bypasses scope-restricted `stacks` lookup, allowing an ApiClient token scoped to one stack to read any stack's CCTray XML - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stacks` restricts stack lookups to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a single stack, but `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never invoking `#stacks`. Combined with `require_permission!` only checking the client's permission list (`read:stack`) and never its `stack_id`, this lets a token legitimately scoped to the attacker's own stack retrieve CCTray status for any other stack in the system.

### Finding Description
The intended binding is: `requested_stack ∈ Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true, i.e., a scoped token may only resolve stacks belonging to it, as implemented in `BaseController#stacks`/`#stack`: [1](#0-0) 

`CCMenuController` however redefines `#stack` to bypass this scoping entirely: [2](#0-1) 

The `before_action` `require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, which checks whether `"read:stack"` is present in the `permissions` array — it never compares `current_api_client.stack_id` to the requested stack: [3](#0-2) [4](#0-3) 

`ApiClient.authenticate` simply verifies the signed token and loads the `ApiClient` record by id, with no scope enforcement of its own: [5](#0-4) 

`CCMenuController#authenticate_api_client` reads the token from `params[:token]` (query string) rather than an Authorization header, which is how it supports the CCTray URL format, but this does not change the scoping problem: [6](#0-5) 

Exploit flow: attacker legitimately creates/administers their own repo+stack and obtains a `read:stack` `ApiClient` token scoped to that stack (`stack_id` set to the attacker's stack). Attacker sends `GET /api/stacks/:victim_stack/cc_menu.xml?token=<attacker_scoped_token>`. `authenticate_api_client` succeeds and sets `@current_api_client` with `stack_id = attacker_stack.id`. `require_permission!(:read, :stack)` passes because the client has the `read:stack` permission string, regardless of scope. `#show` calls `#stack`, which resolves via `Stack.from_param!(params[:stack_id])` — completely unscoped — and returns the victim stack. The response renders the victim stack's CCTray XML (deploy/task status), which is a cross-tenant read never authorized for this token.

None of the existing guards catch this: `check_permissions!` checks only the permission name, not `stack_id`; there is no `before_action` in `CCMenuController` re-enforcing `stacks.from_param!`; and the base `#stack`/`#stacks` scoping method is shadowed, not reused.

### Impact Explanation
A token scoped to a single stack can read CCTray XML (deploy status, last build result, activity) for any other stack in the Shipit instance, including stacks belonging to unrelated repositories/organizations that the attacker has no relationship with. This is a cross-tenant unauthorized read of stack/deploy state, matching the "High - unauthorized read of stack state" impact category. It is fully repeatable against arbitrary stack ids/slugs and requires only knowledge or guessing of the victim's stack path segment.

### Likelihood Explanation
Preconditions are low-cost and entirely attacker-controlled: the attacker only needs to be a legitimate creator/administrator of some repository within the same Shipit instance and to obtain a `read:stack` `ApiClient` token scoped to their own stack (a normal, supported workflow via `ApiClientsController`). No GitHub secrets, session, or elevated Shipit role is required. The only extra requirement is guessing/knowing the victim's stack identifier (owner/repo/environment), which is often discoverable or predictable. This is a straightforward, repeatable HTTP GET.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup instead of the unscoped model method, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, removing the private `#stack` override entirely (falling back to `BaseController#stack`), or add an explicit scope check comparing `current_api_client.stack_id` to the resolved stack's id when `current_api_client.stack_id?` is true.

### Proof of Concept
Minitest controller test under `test/controllers/api/ccmenu_controller_test.rb` (outline):
1. Create `attacker_stack` and `victim_stack` (different repositories).
2. Create an `ApiClient` with `stack: attacker_stack`, `permissions: ['read:stack']`; generate its `authentication_token`.
3. Assert precondition: `Stack.where(id: attacker_api_client.stack_id).exists?(id: victim_stack.id)` is `false` (the binding under test).
4. `get shipit.api_stack_cc_menu_url(stack_id: victim_stack.to_param, format: :xml, token: attacker_api_client.authentication_token)`.
5. Assert `response.status == 200` and response body contains `victim_stack`'s name/status — demonstrating the divergence: the equality checked in step 3 is false, yet the controller still returns 200 with the victim's data instead of 403/404.
