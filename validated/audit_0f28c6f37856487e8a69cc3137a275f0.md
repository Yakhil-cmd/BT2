### Title
Cross-organization webhook forgery: signature is verified against the org derived from an unauthenticated payload field, decoupled from the repository/team actually acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook verification path selects which GitHub App/`webhook_secret` to authenticate a delivery with based on a field read out of the *unverified* JSON body (`repository.owner.login` or `organization.login`), then hands the same unverified body to a handler that reads a *different* field (`repository.full_name`, or `organization.login` inside the `membership` payload) to decide what to write. The equality the code implicitly assumes — "the org whose secret verified this signature" == "the org/repository the handler mutates" — is never enforced.

### Finding Description
`WebhooksController#verify_signature` picks the verifying app like this: [1](#0-0) [2](#0-1) 

`repository_owner` is computed by parsing the raw, not-yet-authenticated request body. It is then used to fetch a `GitHubApp` instance keyed by that organization name via `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is used to HMAC-verify the payload: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the *entire* raw payload to the event handler: [4](#0-3) 

But the handlers derive the target of the action from other, independent fields of that same payload:
- `Handler#repository_name` (used by `PushHandler`, `StatusHandler`, PR handlers, etc.) reads `repository.full_name`, not `repository.owner.login`: [5](#0-4) 
- `MembershipHandler` reads `organization.login` to resolve/create a `Team` and then adds or removes a `member.login` from that team: [6](#0-5) 

In Shipit's supported multi-organization configuration (documented and exercised in `test/dummy/config/secrets_double_github_app.yml`), each organization key has its own `webhook_secret`. Because the field used to pick the verifying secret (`repository.owner.login` / top-level `organization.login`) is never checked against the field the handler subsequently trusts (`repository.full_name`, or the nested `organization.login` under `membership` events), an attacker who knows (or can guess/leak) the `webhook_secret` for **any one** configured organization on the instance can:
1. Set the outer `repository.owner.login`/`organization.login` to that known organization so `verify_signature` selects and validates against the secret they know.
2. Set the inner action-relevant fields (`repository.full_name` for push/status/PR events, or `member`/`team` for membership events) to point at a **completely different** organization's repository or team hosted on the same Shipit instance.

The HMAC only proves the raw body was signed by *some* configured org's secret — it says nothing about which repository/team fields inside that body are legitimate for that org. This exactly mirrors the audited bug class: a value is used to authorize a boundary (org secret selection) while a different, unchecked value is what the code actually acts on (target repository/team).

Additionally, `verify_webhook_signature` fails open when a given org's `webhook_secret` is blank/unset (`return true unless webhook_secret`), which lowers the bar further for any org in a multi-tenant instance that has not configured a secret: [7](#0-6) 

### Impact Explanation
This breaks the binding `organization that authenticated == repository/team that is written`, enabling cross-repository/cross-organization writes from an attacker who only controls (or has leaked) a single tenant's webhook secret on a shared Shipit instance:
- Forged `push` webhooks can trigger `GithubSyncJob`/`stack.sync_github` for stacks belonging to any other organization's repository configured on the instance (`PushHandler#process`).
- Forged `membership` webhooks can add or remove arbitrary GitHub users from any `Team` record tracked by Shipit, including teams referenced by `Shipit.github_teams`, which gates application authorization in `Authentication#force_github_authentication` / `User#authorized?`: [8](#0-7) [9](#0-8) 

Being able to add an attacker-controlled GitHub login to a team backing `Shipit.github_teams` is a direct escalation into Shipit's authorization model — matching the specified High-impact category ("escalation into `Shipit.github_teams` authorization"). The push/status cross-repo triggering matches "cross-repository writes."

### Likelihood Explanation
Requires: (a) the instance to use the documented multi-organization GitHub App configuration, and (b) the attacker to know/obtain the `webhook_secret` for at least one of the configured organizations (their own tenant, or one left unset). Given webhook secrets are routinely shared with third-party CI/webhook relays and are lower-value secrets than the GitHub App private key or `GITHUB_TOKEN`, this is a realistic scenario for shared/multi-tenant Shipit deployments, and requires no session, API token, or repository write access.

### Recommendation
After signature verification succeeds for organization `O`, enforce that every organization-identifying field used by the dispatched handler (`repository.owner.login`, the nested `organization.login` on `membership` payloads, etc.) is equal to `O` before invoking the handler. Concretely, in `WebhooksController#verify_signature`/`create`, re-derive and compare the "acting" organization from the handler's own field extraction against the organization used to select the verifying secret, and reject (422) on mismatch, rather than trusting the raw payload's internal consistency implicitly.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both hosted on the same Shipit instance.
2. Attacker knows `OrgA`'s `webhook_secret` (e.g., leaked from a CI system) but not `OrgB`'s.
3. Attacker crafts a `membership` event payload:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "OrgB Admins", "slug": "admins", "url": "https://api.github.com/..."},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker-controlled-login"}
}
```
4. Attacker sets `X-Github-Event: membership` and signs the raw body with `OrgA`'s webhook secret, sending it with header `X-Hub-Signature: sha1=<hmac using OrgA secret>`.
5. `repository_owner` resolves to `nil` for `membership` events since there is no top-level `repository` key handled the same way — but note `repository_owner` falls back to `params.dig('organization', 'login')`, which is `OrgB` here, so `verify_signature` actually selects `OrgB`'s app/secret, not `OrgA`'s, for `membership` events specifically. To exploit the general class, the attacker instead targets `push`/`status`/PR events (where `repository_owner` is taken from `repository.owner.login`) and sets `repository.owner.login` to `OrgA` (the org whose secret they know) while setting `repository.full_name` to `OrgB/target-repo`. `verify_signature` validates the signature using `OrgA`'s secret (success), then `PushHandler#repository_name` uses `repository.full_name` = `OrgB/target-repo` to look up and sync a stack belonging to `OrgB`, which the attacker has no legitimate access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
