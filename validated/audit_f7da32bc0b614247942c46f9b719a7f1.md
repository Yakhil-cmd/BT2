## Analysis

The external report describes a "push" payment pattern that permanently fails once the recipient becomes unauthorized (blacklisted) by the token, with no fallback "pull" mechanism, causing frozen funds. The closest reachable analog in `ocore` is the `spender_attested` asset mechanism combined with AA payment composition, where an AA committed to paying a specific hard-coded address can be permanently blocked if that address's attestation is later revoked by the asset's attestor(s) — with no pull-based recovery path.

### Title
AA payments to a fixed recipient permanently fail and freeze funds if the recipient's attestation for a `spender_attested` asset is later revoked - (File: `validation.js`, `aa_composer.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, every payment message must have **all** output addresses currently attested by one of the asset's attestors, checked freshly at validation time via `storage.filterAttestedAddresses`. An AA that stores a counterparty/beneficiary address in its state (e.g., from an earlier trigger, analogous to "clearing a loan request" with a fixed lender address) and later sends that asset to the stored address has no way to know, at commitment time, whether the recipient will remain attested. If the attestor list is updated (via an `asset_attestors` message) to drop that address before the AA's obligatory payment is sent, the AA's payment permanently fails validation, the response bounces, and the AA has no pull-based alternative to deliver the committed funds — mirroring the original bug's "push reverts, no pull fallback" DoS pattern, but here causing **AA fund freezing** rather than a simple wallet failure.

### Finding Description
`validatePaymentInputsAndOutputs` requires, for `spender_attested` assets, that all payment output addresses be attested as of `last_ball_mci` at the time the unit is validated: [1](#0-0) 

This check is fed by `storage.filterAttestedAddresses`, which looks up current attestations, filtered by the address's most recent definition change — meaning attestation status is a live, mutable property that can be revoked at any time by publishing a new `asset_attestors` message from the definer/attestor: [2](#0-1) [3](#0-2) 

When an AA composes and sends a payment (e.g., fulfilling an earlier commitment stored in a state variable, such as paying back a counterparty address recorded from a prior trigger), it checks only that **the AA itself** (as author) is attested before building the payload — it does not verify that the **recipient** address is currently attested:


The AA then proceeds to `validateAndSaveUnit`, and only there does the full consensus validation (including the attested-output-address check) run: [4](#0-3) 

If validation fails because the recipient is no longer attested, the AA response is bounced: [5](#0-4) 

Because oscript/AA logic can only construct a `payment` message with a fixed `address` field (an AA cannot let the recipient "pull" funds themselves — the AA is the only initiator of its own payments), there is no pull-based recovery path analogous to the recommendation in the original report ("let the lender claim instead of push"). Once an address loses attestation, any AA logic that unconditionally pays that specific address for that asset will bounce indefinitely, and the funds intended for it remain stuck in the AA's balance with no built-in mechanism to redirect them (unless the AA author anticipated this and wrote fallback branches, which is not guaranteed and not enforced by consensus).

### Impact Explanation
This can freeze AA funds indefinitely for any AA design that commits to paying a fixed counterparty address using a `spender_attested` asset (e.g., an escrow, marketplace, or payout AA that stores a beneficiary address from an earlier trigger and pays it out later). If the attestor revokes attestation for that address in the interim, the AA can never complete that specific commitment: the balance owed remains stuck in the AA, unreachable by that recipient and not returnable via the AA's normal payment paths, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
This requires: (1) an AA that pays a `spender_attested` asset to an address it does not control at send time (a realistic and even common pattern for marketplaces/escrows/lending-style AAs), and (2) the asset's attestor updating the attestor list or the recipient's attestation being revoked between commitment and payout. Both are within the reach of an ordinary asset definer/attestor and an ordinary AA author/trigger sender — no privileged network, node, or hub role is needed. Attestor list changes are a standard, unprivileged `asset_attestors` message.

### Recommendation
- When an AA pays a `spender_attested` asset to a stored/fixed recipient address, provide a pull-based fallback (e.g., track an internal "owed" balance and allow the recipient — or a currently-attested substitute address the recipient designates — to claim it later via a separate trigger), rather than relying solely on an unconditional push payment.
- Alternatively, at the protocol level, consider exposing an oscript getter/function that lets AA authors check `is_attested` for a candidate output address before composing the payment, so the AA logic can branch to a safe holding/refund path instead of bouncing and leaving funds stuck.

### Proof of Concept
1. Attestor defines asset `X` with `spender_attested: true` and attestor `A1`. `A1` attests address `L` (the "lender"/beneficiary).
2. An AA is triggered and records `var['beneficiary'] = 'L'` along with an amount owed in asset `X`, expecting to pay `L` on a later trigger (analogous to `clearRequest` locking in the lender/repayTo address).
3. Before the payout trigger fires, `A1` publishes a new `asset_attestors` message for asset `X` that no longer includes `L` in the attestation set (validated per `validation.js` lines 2033-2042).
4. The payout trigger fires; the AA composes `{app:'payment', payload:{asset:'X', outputs:[{address:'L', amount: owed}]}}` per `aa_composer.js` lines 1312-1330, generates and attempts to validate/save the response unit (lines 1405-1411).
5. `validatePaymentInputsAndOutputs` calls `filterAttestedAddresses` (validation.js lines 2630-2641) and finds `L` is no longer attested, returning `"some output addresses are not attested"`.
6. The AA response bounces (`bounce(err)` at line 1410); the amount owed to `L` remains in the AA's balance with no automatic mechanism for `L` to ever claim it, since the AA's only programmed payout path targets the now-unattested address `L`.
