### Title
`DenyReserveTransferToRelayChain` Barrier on Asset Hub Polkadot lacks recursive nesting protection unlike other system chains - (File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs)

### Summary
Asset Hub Polkadot's `Barrier` wraps `DenyReserveTransferToRelayChain` directly, without the `DenyRecursively<...>` wrapper that Bridge Hub Polkadot and Bulletin Polkadot use for the same deny-rule. Since the underlying `xcm-builder::DenyReserveTransferToRelayChain::should_execute` (external `xcm-builder` crate, not vendored in this repo) only scans the top-level instruction slice via `message.iter().any(...)`, a `DepositReserveAsset{dest: Parent, ..}` nested inside a `SetAppendix`/`SetErrorHandler` instruction is not matched at the outer scan, and I was not able to fully verify within this session whether the destination Relay chain's own reserve/teleport acceptance logic would still block or accept the resulting message.

### Finding Description
`asset-hub-polkadot`'s `Barrier` is defined as: [1](#0-0) 
using plain `DenyReserveTransferToRelayChain`, whereas `bridge-hub-polkadot` and `bulletin-polkadot` use `DenyRecursively<DenyReserveTransferToRelayChain>`: [2](#0-1) [3](#0-2) 

Notably, this is inconsistent even within the same chain family: `bridge-hub-kusama` also uses the plain (non-recursive) form, while `bridge-hub-polkadot` uses the recursive form. This asymmetry across otherwise-similar runtimes is consistent with `DenyRecursively` being applied narrowly (e.g., to also cover `DenyExportMessageFrom` in the same tuple on bridge-hub-polkadot) rather than as a universal hardening applied to every chain with a `DenyReserveTransferToRelayChain` deny-rule. I could not retrieve the actual source of `xcm-builder::DenyReserveTransferToRelayChain` or `DenyRecursively` from this repository (they live in the external `xcm-builder` crate dependency, not vendored here), so I cannot cite or confirm from this codebase exactly what instruction-matching/recursion logic those types implement, nor confirm the intended purpose behind selectively adding `DenyRecursively` only to bridge-hub-polkadot/bulletin-polkadot.

Critically, even assuming the barrier-bypass premise is correct, the scoped impact ("double-counting reserve-backed DOT") also depends on the Relay chain's own XCM configuration (its `IsReserve`/`IsTeleporter` filters) accepting a `ReserveAssetDeposited`/`DepositReserveAsset` message purportedly reserve-backed by Asset Hub for DOT. DOT transfers between the Relay and Asset Hub are normally routed via teleport (Asset Hub is not configured as a trusted reserve for DOT), so even if the local Barrier is bypassed on the sending side, the Relay chain independently validates reserve legitimacy on receipt. I was unable to locate or verify the Relay chain's `xcm_config.rs` in this repository within this session to confirm whether it would accept or reject such an inbound reserve-asset message from Asset Hub.

### Impact Explanation
If the bypass and the downstream Relay-side acceptance both hold, an attacker could route a nested reserve-transfer-pattern message toward the Relay chain that the local deny-rule was designed to filter, potentially causing accounting inconsistency for DOT between Asset Hub and Relay. This part of the impact (Relay-side acceptance behavior) is not confirmed with evidence from this repository.

### Likelihood Explanation
Feasibility of the local bypass (constructing `SetAppendix`-wrapped reserve-transfer instructions within `MaxInstructions=100` via an unprivileged `pallet_xcm::execute`-style entry point) is plausible in principle based on how `ShouldExecute::should_execute` is invoked once against the top-level instruction list in the XCM executor pattern used across these configs, but I could not confirm the precise `xcm-builder` implementation details (exact match arms, whether `SetAppendix`/`SetErrorHandler` payloads are excluded from the top-level scan) from within this repository, since that logic resides in the external `xcm-builder` crate not present in this codebase.

### Recommendation
If confirmed against the actual `xcm-builder` source used by this runtime, apply `DenyRecursively<DenyReserveTransferToRelayChain>` consistently across all system-chain `Barrier` definitions that currently use the bare `DenyReserveTransferToRelayChain` (asset-hub-polkadot, asset-hub-kusama, collectives-polkadot, coretime-polkadot, coretime-kusama, people-polkadot, people-kusama, encointer, bridge-hub-kusama), matching the pattern already used in bridge-hub-polkadot and bulletin-polkadot.

### Proof of Concept
An xcm-emulator test on Asset Hub Polkadot submitting a `pallet_xcm::execute` (or equivalent unprivileged entry point) program of the form `Xcm(vec![SetAppendix(Xcm(vec![DepositReserveAsset{dest: Parent, ..}])), <benign top-level instructions>])`, then asserting whether `Barrier::should_execute` rejects it (expected: reject) versus whether it is accepted and the appendix executes, and separately verifying on the Relay-chain emulated instance whether the resulting message is accepted or rejected by its own reserve/teleport filters, is the concrete test needed — this could not be run or fully traced in this session because the relevant Relay-chain `xcm_config.rs` and the external `xcm-builder` crate source were not available for verification here.
