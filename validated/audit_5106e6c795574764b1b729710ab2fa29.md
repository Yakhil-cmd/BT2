### Title
Webhook signature verified against `repository.owner.login`, but handlers act on the unverified `repository.full_name` — cross-organization forged webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug-class in the report (a value trusted for one purpose is not the same value that is actually acted upon, breaking an implicit binding) maps to `Shipit::WebhooksController`. The HMAC signature that authenticates an inbound webhook is selected and checked using `repository.owner.login` (or `organization.login`), but every event handler that actually mutates state (`Repository`, `Stack`, `ReviewStack`, memberships, etc.) resolves its target using the independent, unverified `repository.full_name` field from the same JSON body.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the request against using `repository_owner`: [1](#0-0) [2](#0-1) 

Once the HMAC check passes, `create` dispatches the *entire raw payload* to the registered handler for the event: [3](#0-2) 

But `Shipit::Webhooks::Handlers::Handler`, the base class every handler inherits from, resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

This pattern repeats in every concrete handler (`PushHandler`, and all `PullRequest::*Handler`s), which call `Repository.from_github_repo_name(params.repository.full_name)` to locate the object to write to: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (verified) and `repository.full_name` (acted upon) are two independent fields inside the same attacker-controllable JSON body, and Shipit explicitly supports **multiple organizations** each with its own `webhook_secret` in a single instance (as shown in `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne` and `OrgTwo` side-by-side), nothing prevents these two fields from disagreeing.

**Binding that should hold, but doesn't:**
`organization authenticated by verify_webhook_signature (repository.owner.login)` == `organization/repository actually written by the handler (repository.full_name)`

Before the attack: an org admin of `OrgOne` (who legitimately possesses `OrgOne`'s `webhook_secret`, since they configured the GitHub App/webhook integration for their own org) can only affect `OrgOne`'s stacks.

After the attack: that same admin, using the secret they legitimately own, POSTs a JSON payload where `repository.owner.login = "OrgOne"` (so `verify_signature` picks `OrgOne`'s secret and the HMAC computed over the attacker's own chosen body validates) while `repository.full_name = "OrgTwo/target-repo"` (so the handler resolves and mutates `OrgTwo`'s `Repository`/`Stack`).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out explicitly as in-scope. Concretely, an OrgOne-secret holder can, against OrgTwo's stacks:
- Force `PushHandler` to enqueue `GithubSyncJob` for OrgTwo's stacks with an attacker-chosen `expected_head_sha` [8](#0-7) .
- Archive/unarchive/provision `ReviewStack`s belonging to OrgTwo repositories via the `pull_request` handlers [6](#0-5) .

This is a cross-repository/cross-organization write triggered without any credential belonging to the victim organization, matching the "Critical – cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only that the attacker be a legitimate administrator/owner of *any* organization already onboarded into the same Shipit instance (a normal, unprivileged-relative-to-other-tenants position, not a Shipit session, `ApiClient` token, or the victim org's `webhook_secret`). Multi-org Shipit deployments (as documented/configured in `secrets_double_github_app.yml`) are a realistic and supported topology, so this is directly reachable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), cross-check that the organization/owner used to select the `webhook_secret` for signature verification is the same organization referenced by `repository.full_name` (and `organization.login` for org-level events) before dispatching to handlers. Reject the payload if they diverge.

### Proof of Concept
1. Instance configures two orgs, `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret`, per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, an admin of `OrgOne`, knows `OrgOne`'s `webhook_secret` (they configured it).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgOne_webhook_secret, body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and validates successfully against `OrgOne`'s secret [1](#0-0) .
6. `PushHandler` resolves `stacks` via `full_name = "OrgTwo/target-repo"` [4](#0-3)  and enqueues `GithubSyncJob` for `OrgTwo`'s stack with the attacker's `expected_head_sha`, even though the attacker never proved control of `OrgTwo`.
