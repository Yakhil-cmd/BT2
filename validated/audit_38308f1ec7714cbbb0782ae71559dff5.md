### Title
Opaque swap routes allow injected contracts to steal caller wallet funds through the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-controlled opaque `swap` bytes and forward them to the configured router while the caller’s authorization covers the controller invocation. A malicious route can invoke arbitrary contract code that requests additional token transfers from the caller; those requests appear as child authorizations under the caller’s signed controller authorization.

### Finding Description
`swap_collateral` accepts a caller-supplied `Bytes` route and verifies only caller ownership/delegation before executing the strategy. [1](#0-0) [2](#0-1) 

The common swap path grants the configured router authority for exactly one controller-token input transfer, but forwards the opaque route and does not constrain which downstream contract addresses that route invokes. [3](#0-2) 

Controller-side balance checks bound only the routed input and measured output; they do not prevent route-invoked code from adding an unrelated `token.transfer(caller, attacker, amount)` child invocation to the caller’s authorization tree. [4](#0-3) 

The repository’s threat model explicitly identifies this behavior: routes can place third-party code below the caller authorization, and a wallet transfer executed there can drain assets unrelated to the listed input/output tokens. [5](#0-4) 

### Impact Explanation
A victim signing a poisoned strategy transaction can lose arbitrary wallet tokens, not merely the collateral or debt amount routed through the strategy. The injected transfer is authorized as a child of the victim’s `swap_collateral` authorization and can transfer the victim’s full balance of an unrelated token to the attacker. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
Any unprivileged account can supply the opaque route argument to `swap_collateral`; no special controller role is required. [7](#0-6)  Exploitation requires the victim to sign a transaction containing the malicious route and its additional authorization child, so malicious quote generation, transaction construction, or UI deception can expose multiple users. [8](#0-7) 

### Recommendation
Do not allow opaque routes to introduce arbitrary downstream invocations under a user’s authorization. Constrain route execution to a fixed allowlist of venue contracts, or make the authorization shape impossible to poison by separating route execution from the user-signed controller invocation. Clients should also simulate and reject any authorization tree containing children other than the expected protocol token transfer.

### Proof of Concept
1. The victim owns a `swap_collateral` position and holds `WALLET_TOKEN` unrelated to the swap.
2. An attacker supplies `swap` bytes whose route invokes an attacker-controlled contract during router execution; the controller forwards those bytes after authorizing only the intended input transfer. [9](#0-8) 
3. The invoked contract calls `WALLET_TOKEN.transfer(victim, attacker, victim_balance)` while execution is beneath the victim’s controller authorization. [10](#0-9) 
4. Simulation records the wallet transfer as a child of the victim’s `swap_collateral` authorization, and successful execution moves the full wallet balance to the attacker while still producing a valid swap output. [11](#0-10)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
