### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while writes are keyed only by `repository.full_name` / raw `sha` — cross-organization forged CI status and sync events - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/`webhook_secret` to HMAC-verify a webhook against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`) in the attacker-controlled JSON body itself. [1](#0-0)  Once that signature check passes, the handlers that actually mutate state (`Handler#repository_name`, `PushHandler#process`, `StatusHandler#process`) trust *other, independent* fields of the same payload — `repository.full_name` for stack lookup, and a bare `sha` string with no repository/organization scoping at all for status writes. [2](#0-1) [3](#0-2)  This breaks the binding: `organization authenticated == repository written`.

### Finding Description
Shipit supports multiple GitHub organizations/Apps simultaneously, each with its own `webhook_secret`, as shown in the multi-org secrets template. [4](#0-3)  `verify_signature` picks the app config purely from a payload field it does not otherwise trust for anything else:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature only proves the raw body was HMAC-signed with the secret belonging to whatever organization `repository_owner` names — it does not prove any relationship between that organization and any other field inside the same JSON body. An operator of a legitimate, Shipit-registered organization ("Org A") knows Org A's own `webhook_secret` (it is configured when Org A's GitHub App/webhook is set up) and can therefore compute a valid `X-Hub-Signature` over an arbitrary JSON body, as long as `repository.owner.login`/`organization.login` in that body is `"Org A"`.

Downstream, `Handler#repository_name` (used by `PushHandler`) resolves the target `Stack` from `payload.dig('repository', 'full_name')` — a separate field from `repository.owner.login` used for signing — with no cross-check that this repository actually belongs to Org A. [2](#0-1)  Worse, `StatusHandler#process` does not consult repository identity at all; it matches purely on `sha`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha:...)` is a global (cross-stack, cross-org) lookup, and `create_status_from_github!` writes a `Status` record and can flip a commit's aggregated `status`/`deployable?` state, feed `blocked?` computations, and trigger `stack.schedule_merges` for merge queue processing. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
An operator of any organization that Shipit trusts (Org A, with its own known `webhook_secret`) can forge a validly-signed `status` webhook whose `sha` matches a commit belonging to a *different* organization's tracked repository (Org B). Because `StatusHandler` never checks that the commit's stack/repository corresponds to the authenticating organization, the attacker can inject an arbitrary CI "success" status for that commit. If `ci.require` conditions and `deployable?`/`blocked?` logic are then satisfied purely by the forged status, this can influence merge-queue processing (`stack.schedule_merges`) and continuous-delivery scheduling (`Commit#schedule_continuous_delivery`) for a repository the attacker has no legitimate authority over — i.e., an unauthorized effect on another organization's deploy pipeline using only a signature obtained from an unrelated organization's own webhook secret. This satisfies the "unauthorized deploy" criterion in a limited but concrete way for multi-org Shipit installations. `PushHandler` is comparatively less severe because `sync_github` pulls truth from GitHub's API for the real repository rather than trusting attacker data directly, but it still allows an unrelated organization to trigger sync jobs against a repository it does not own.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment where the attacker legitimately controls/owns one of the configured GitHub organizations (and therefore knows that org's `webhook_secret`), and (2) the attacker knowing/guessing a `sha` of a commit tracked in a different org's stack (commit SHAs are frequently public via GitHub itself, or discoverable via Shipit's own public-ish views). No compromise of TLS, no `ApiClient` token, and no GitHub App private key are needed — only knowledge of one's own legitimately-configured webhook secret. This is a narrower prerequisite than the excluded "requires a GitHub App private key" / "requires repository write access" conditions, and it is not dependent on the host failing to mount the engine as documented.

### Recommendation
Bind the webhook signature verification result to the exact same field(s) used for write-side lookups. Concretely:
- After `verify_webhook_signature` succeeds, re-derive `repository_owner` and require it to equal the owner segment of `repository.full_name` used by `Handler#repository_name` before dispatching to handlers.
- In `StatusHandler#process` (and any handler using bare `sha`/generic identifiers), scope `Commit.where(sha:...)` to commits whose `stack.repository.owner` matches the verified `repository_owner`, rather than a global lookup.
- Alternatively, once `Shipit.github(organization: repository_owner)` is selected for verification, pass that organization down to `Webhooks.for_event(event).each { |handler| handler.call(params, organization: repository_owner) }` and have `Handler` enforce it inside `stacks`/`repository_name` resolution.

### Proof of Concept
1. Shipit configured with two orgs, `org-a` (attacker-controlled, webhook secret `S_A` known to attacker) and `org-b` (victim, stack tracking `org-b/victim-repo`, commit `abc123...` already merged and publicly visible on GitHub).
2. Attacker builds JSON body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner => "org-a"`, loads `Shipit.github(organization: "org-a")`, verifies successfully against `S_A`. [8](#0-7) 
5. `StatusHandler.call(params)` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `org-b/victim-repo`'s stack (no org check), and calls `create_status_from_github!`, injecting a forged "success" status for a commit in `org-b`'s repository despite the signature only proving control of `org-a`. [3](#0-2) 

Note: I could not fully trace `stack.sync_github` / `ContinuousDeliveryJob` execution paths within the remaining exploration budget to confirm the exact downstream consequence chain (e.g., whether this alone can trigger an actual `Deploy`); this should be verified further (e.g., whether `ci.require` gating alone, satisfied by the forged status, is sufficient for `schedule_continuous_delivery` to fire a real deploy without additional legitimate GitHub state).
