### Title
`shipit/checks` status webhook flips deployability for any stack sharing the SHA, not just the authenticating repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a bare, unscoped `Commit.where(sha: params.sha)` lookup, with no join or filter on the repository/stack that the inbound webhook was signed for. Any stack whose `commits` table happens to contain a `Commit` row with that same `sha` (e.g. shared upstream history, mirrored/forked repos, or two Shipit stacks tracking the same commit) will have `create_status_from_github!` invoked on it, even though the request was authenticated only for a different repository's GitHub App/org secret.

### Finding Description
The broken binding is: **the webhook's authenticated repository must equal the repository of every commit that gets mutated** — i.e. `payload.repository.full_name == commit.stack.repository.full_name` for every `commit` touched by the handler. This invariant is never checked.

Trace:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, which is `StatusHandler` (`app/models/shipit/webhooks.rb:19`).
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only validates the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`, line 61). This proves the request came from GitHub for *some* org/app installation — it says nothing about which specific repository/stack should be affected.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a bare SHA lookup across the entire `commits` table, with no `stack_id`/repository filter tying it back to the authenticated payload's `repository.full_name`.
- `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169, 366-386`) creates a `Status` row, recomputes `status`, and if the state transitions to `success`, calls `stack.schedule_merges` and (via `Commit#schedule_continuous_delivery`) enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `stack.deployable?` are true (`app/models/shipit/commit.rb:281-287`). Continuous deployment tasks run under the bot identity configured via `Shipit.user`/`github.bot_login` (`lib/shipit.rb:208-214`), so this directly triggers an auto-ship using the victim stack's credentials/authorization, not the attacker's.
- None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `StatusHandler` (which only validates types of `sha`/`state`/`context`, not repository ownership) constrain the lookup to the authenticating repository. `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) likewise only scopes by `stack_id` derived from whichever `Commit` matched the bare SHA — it never cross-checks the stack's repository against the webhook's `repository` field.

Exploit flow: an attacker who owns/controls a repository whose org has a legitimate GitHub App/webhook secret configured in Shipit (satisfying `verify_signature`) pushes a commit and creates a `success` status with `context: shipit/checks` on that SHA via the real GitHub Status API from their own repo/fork. If that SHA also exists as a `Commit` row belonging to a victim stack (e.g., two stacks tracking a shared upstream/mirrored commit, or a monorepo split into multiple stacks), the resulting webhook is dispatched by GitHub, correctly signed for the attacker's own org, but `StatusHandler#process` applies the `success` status to **every** `Commit` row with that SHA — including the victim's — regardless of which repository actually authenticated the request.

### Impact Explanation
A `success`/`shipit/checks` status forged this way can flip a victim stack's commit from non-deployable to deployable, satisfy a required status check, unblock a blocking commit, or (if `continuous_deployment?` is enabled and `bot_login` is configured) directly trigger `ContinuousDeliveryJob`, causing an unauthorized deploy/rollback running as the configured bot identity. This is a cross-tenant write: a payload authenticated for repository A mutates state (`Status`, deployability, and downstream deploy tasks) belonging to stack/repository B, matching the "Critical — payload for one repository mutating another's stack/commit" category. The attack is repeatable against any stack that shares a commit SHA with an attacker-reachable repository.

### Likelihood Explanation
Preconditions: (1) the attacker's own repository/org must have a valid GitHub App installation/webhook secret already known to Shipit (so `verify_signature` passes) — this is a reasonably common precondition since orgs frequently install the GitHub App organization-wide across all repos rather than per-repo; (2) a shared SHA must exist between the attacker's repository and the victim stack's commit history, which occurs naturally with forks, mirrors, subtree/monorepo splits, or shared base commits across multiple Shipit-tracked stacks. Attacker cost is a normal GitHub status API call on a commit in their own repo — no secrets, no privileged Shipit role required. The finding is fully reproducible without live GitHub, since `StatusHandler#process` can be exercised directly.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to a stack whose repository matches the authenticated webhook's `repository.full_name`/`repository.owner.login`. Concretely, join `Commit` to `Stack`/`Repository` and filter by the payload's `repository` before calling `create_status_from_github!`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_id_from_payload }).each { ... }`, mirroring the repository scoping already implicitly relied upon by `verify_signature`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repo A must not mutate a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # repository == 'shopify/shipit-engine'
  attacker_stack = shipit_stacks(:cyclimse) # repository == 'attacker/other-repo'

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

  before_state = victim_commit.reload.state
  assert_not_equal 'success', before_state

  # Simulate a status webhook whose signature/payload authenticates ONLY attacker_stack's repo
  params = ExplicitParameters::Params.new(
    sha: shared_sha, state: 'success', context: 'shipit/checks', branches: []
  )
  # repository field in the raw payload identifies attacker's repo, not victim's
  Shipit::Webhooks::Handlers::StatusHandler.new(sha: shared_sha, state: 'success', context: 'shipit/checks', repository: { full_name: 'attacker/other-repo' }).call

  victim_commit.reload
  assert_equal before_state, victim_commit.state, "victim stack's commit must not be mutated by a webhook authenticated for a different repository"
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
