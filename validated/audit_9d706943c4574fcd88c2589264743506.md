### Title
`recapitalize` pays out a refund and commits cash credit without verifying any inbound payment — unprivileged pool drain - ([File: contracts/pool/src/ops/recapitalize.rs](contracts/pool/src/ops/recapitalize.rs))

### Summary
CVE-2020-29561's bug class is "acquires a reservation/effect even though the operation that should justify it faults." The XOXNO Lending analog is `recapitalize::apply`: the pool treats `amount` as if the payer already funded it, commits `credit_cash(applied)` to the cash book, and immediately `transfer_out`s the `refund = amount - applied` — yet the pool never measures or requires that `amount` actually arrived. Like the BOOM LR that keeps its reservation after a faulting load, the refund entitlement is acquired regardless of whether the funding leg succeeded.

### Finding Description
`recapitalize::accounting` (contracts/pool/src/ops/recapitalize.rs:44-67) computes:

```rust
let applied = amount.min(guards::backing_shortfall(&cache));
let refund = amount.checked_sub(applied)...;
cache.credit_cash(applied);
cache.commit();
```

then `apply` (lines 26-38) does `outcome.cache.transfer_out(&payer, outcome.refund)`. The doc comment assumes "The controller transfers `amount` into the pool before this call," but nothing in the pool enforces it. An unprivileged caller can invoke `pool.recapitalize(hub_asset, payer, amount)` directly with `payer` = self. With `amount` larger than the backing shortfall (or zero shortfall), `applied` is small or zero and `refund` ≈ `amount`, so the pool transfers real custody to the attacker out of suppliers' funds while the cash book still reports the old balance.

The committed test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3408-3483) demonstrates exactly this: a direct `recapitalize` with `amount = pool_balance` drains custody to 0, leaves `cash` ≥ the supplier's deposit, and the supplier's subsequent `withdraw` passes the pool's own `require_reserves` book check then dies inside the SAC transfer with `BalanceError = 10` — i.e., the protocol becomes silently insolvent rather than failing closed.

### Impact Explanation
Theft of user funds and protocol insolvency. One call extracts up to the pool's full token balance of a hub asset (bounded only by `refund = amount - applied`, so `amount` just needs to exceed the current shortfall — which is normally 0 in a healthy market). Suppliers' share claims survive on the book while custody is gone: later withdrawals revert inside the token transfer, permanently freezing remaining claims for whoever exits last.

### Likelihood Explanation
`recapitalize` is on the in-scope unprivileged surface, takes a caller-chosen `payer`, and requires no collateral, position, oracle price, or timing. The only precondition is that the pool holds token balance for that hub asset, which is the normal state of any live market.

### Recommendation
Have the pool measure the funding leg itself: snapshot the SAC balance before, require `balance_after - balance_before >= applied` (or pull `applied` from `payer` with `require_auth`), and only then commit `credit_cash` and compute the refund from measured receipts rather than the declared `amount`. Alternatively restrict `recapitalize` to the controller, which performs `transfer_amount_measured`.

### Proof of Concept
From the in-repo test (contracts/pool/tests/flows.rs:3408-3483):

```rust
token_admin.mint(&t.pool, &deposit);                    // supplier custody
client.supply(&t.sup(0, deposit));                      // book == custody
client.recapitalize(&hub(&t.asset), &payer, &custody);  // payer funds nothing
assert_eq!(token.balance(&t.pool), 0);                  // custody drained to payer
assert!(t.state_snapshot().cash >= deposit);            // book still solvent
client.try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0))
      // -> SAC BalanceError(10): the exit clears the book guard, fails on custody
```

Assumption I could not fully verify within the available context: whether `Pool::recapitalize` performs a `payer.require_auth()` or controller-only check in `pool/src/lib.rs` (the auth gate was in truncated output). The pool unit test invokes it with a generated `payer` and no funding, indicating no effective payment verification; if the entrypoint turns out to be controller-gated, the residual issue is that any caller able to reach it still drains custody, and the book/custody divergence remains.
