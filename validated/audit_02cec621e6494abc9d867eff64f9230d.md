### Title
Coin deny-list check during signing only validates `tx_data.sender()`, never the actual withdrawal owner (e.g. sponsor), allowing denied addresses to move funds via `WithdrawFrom` - (File: crates/sui-types/src/deny_list_v2.rs, crates/sui-core/src/authority.rs)

### Summary
`handle_coin_deny_list_checks` in `crates/sui-core/src/authority.rs` computes `declared_withdrawals` via `tx_data.process_funds_withdrawals_for_signing(...)`, which yields per-withdrawal tuples `(_, type_tag, _)`. Only the `type_tag` component is kept to build `funds_withdraw_types`; the owner/address component of each declared withdrawal is discarded. The resulting `funds_withdraw_types` set (coin types only, no owner identity) is then passed into `check_coin_deny_list_v2_during_signing(tx_data.sender(), ...)`, which checks `address_denied_by_config` against `tx_data.sender()` for every coin type present, including coin types withdrawn on behalf of a different owner (e.g., the sponsor's address balance via `WithdrawFrom::Sponsor`). [1](#0-0) 

### Finding Description
The enforcement invariant for a regulated `Balance<T>` deny list is: every principal whose address-balance is debited in a transaction must be checked against the coin's deny list for that coin type. `check_coin_deny_list_v2_during_signing` implements the check as "for each coin type present in the tx (from input objects + withdrawal types), check if `address` is denied," but `address` is hardcoded to a single value — the transaction sender — regardless of how many distinct withdrawal owners are actually present: [2](#0-1) 

The caller builds `funds_withdraw_types` by mapping over `declared_withdrawals.values()` and extracting only the type tag, discarding the owner field of each tuple: [3](#0-2) 

Since `WithdrawFrom::Sponsor` (in `crates/sui-types/src/transaction.rs`) allows gas payment to be withdrawn from the sponsor's address balance rather than the sender's, and the sponsor is a distinct identity from `tx_data.sender()`, the deny-list check never binds the sponsor's address to the check at all — it only ever tests `tx_data.sender()`. This breaks identity binding between "the address whose `Balance<T>` is being debited" and "the address checked against `AddressKey`/`GlobalPauseKey`."

### Impact Explanation
If a coin issuer places a sponsor's address on the `AddressKey` deny list (or activates `GlobalPauseKey`) for a regulated coin type, an unprivileged sender can still construct a sponsored PTB where `WithdrawFrom::Sponsor` debits that sponsor's frozen `Balance<T>` for gas payment. The signing-time check (`check_coin_deny_list_v2_during_signing`) will pass because it only evaluates `tx_data.sender()` (a non-denied address), never the sponsor/gas-owner. This is a regulated-coin freeze bypass and harmful smart-contract behavior, matching the "High" impact category for this bounty.

### Likelihood Explanation
The attacker model is an ordinary transaction sender constructing a sponsored transaction with a denied sponsor — no validator, admin, or governance access is required. The bug is deterministic and reachable through the normal signing path (`handle_transaction` → `handle_coin_deny_list_checks`), which is exercised on every signing request.

### Recommendation
`check_coin_deny_list_v2_during_signing` (and its v1 counterpart, `check_coin_deny_list_v1`) should be extended to accept and check every distinct withdrawal-owner address (including `tx.gas_owner()`/sponsor for `WithdrawFrom::Sponsor`, and any other declared withdrawal owners), not just `tx_data.sender()`. The owner component currently discarded in `declared_withdrawals.values().filter_map(|(_, type_tag, _)| ...)` should be retained and cross-checked per coin type.

### Proof of Concept
1. Coin issuer places `sponsor_addr` on `AddressKey` deny list for regulated coin type `T` (which is also the gas/SUI-adjacent balance used for `WithdrawFrom::Sponsor`, or any coin type appearing in `declared_withdrawals`).
2. Attacker (an unprivileged, non-denied sender) builds `TransactionData` with `gas_data.owner = sponsor_addr` and payment mechanism `WithdrawFrom::Sponsor`, sets `sender = attacker_addr` (not denied).
3. Call `handle_coin_deny_list_checks(tx_data, ...)`. `funds_withdraw_types` will contain `T`'s canonical type string but with no owner binding; `check_coin_deny_list_v2_during_signing(tx_data.sender(), ...)` is invoked with `attacker_addr`, which is not denied, so the check returns `Ok(())`.
4. The transaction signs and executes, debiting `sponsor_addr`'s frozen `Balance<T>` despite the active deny entry — confirming the freeze bypass. [4](#0-3) [2](#0-1)

pub fn check_coin_deny_list_v2_during_signing(
    address: SuiAddress,
    input_objects: &CheckedInputObjects,
    receiving_objects: &ReceivingObjects,
    funds_withdraw_types: BTreeSet<String>,
    object_store: &dyn ObjectStore,
) -> UserInputResult {
    let mut coin_types =
        input_object_coin_types_for_denylist_check(input_objects, receiving_objects);
    coin_types.extend(funds_withdraw_types);

    for coin_type in coin_types {
        let Some(deny_list) = get_per_type_coin_deny_list_v2(&coin_type, object_store) else {
            continue;
        };
        if check_global_pause(&deny_list, object_store, None) {
            return Err(UserInputError::CoinTypeGlobalPause { coin_type });
        }
        if check_address_denied_by_config(&deny_list, address, object_store, None) {
            return Err(UserInputError::AddressDeniedForCoin { address, coin_type });
        }
    }
    Ok(())
}
