### Title
Cross-repository commit status forgery via SHA collision in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA across the entire `Commit` table and writes a GitHub-supplied status to every match, without ever checking that the webhook's `repository.full_name` corresponds to the matched commit's stack. Since `WebhooksController#verify_signature` only authenticates the webhook against the *sender's own* GitHub org/repo (attacker-controlled), an attacker owning `attacker/evil` can force a status write onto a commit belonging to `victim/prod`, as long as they can produce a commit with an identical SHA (achievable since Git SHAs are content-addressed and public commits can be copied into an attacker-owned repo).

### Finding Description
The broken binding is: `repository_name` (`payload.dig('repository','full_name')` == `'attacker/evil'`) should equal `commit.stack.repository.full_name` (`'victim/prod'`) before any write proceeds, but it never does.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0)  — this only proves the request was signed by *attacker's own* app config for `attacker`, not anything about victim.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw parsed JSON `params` (the full payload) [2](#0-1) .
3. `Handler` base class exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, which is exactly the mechanism other handlers (e.g., pull_request handlers) use to bind the webhook to the sending repository's stacks [3](#0-2) .
4. `StatusHandler#process`, however, never calls `stacks` or checks `repository_name`. It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) , matching commits by SHA alone across all stacks/tenants.
5. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using the commit's own `stack_id` [5](#0-4) , and `Status.replicate_from_github!` writes `state`, `description`, `target_url`, etc. taken directly from the attacker-controlled payload [6](#0-5) .

Exploit flow: attacker copies a public victim commit's tree/parents so a commit in `attacker/evil` gets the identical SHA as one tracked in `Commit` for `victim/prod`. Attacker triggers (or crafts) a `status` webhook for `attacker/evil` with that SHA and `state: success`, signed with `attacker`'s own `webhook_secret`. `verify_signature` passes (correctly verifying the attacker's own signature), then `StatusHandler` writes a `success` `Status` row tied to the victim's commit/stack — a cross-tenant write authenticated by the wrong party.

No existing guard prevents this: `verify_signature` intentionally only checks the sender's own org, not cross-references matched commits; `Handler#stacks`/`repository_name` binding exists but is simply not invoked by `StatusHandler`; there's no model validation tying `Status` creation to the requesting repository.

### Impact Explanation
An unauthenticated-for-victim attacker can force-create a `Status` record (e.g., `state: 'success'`) on any commit in the system whose SHA they can reproduce in a repo they control, without ever passing signature verification for the victim's GitHub App/org. Because `Status` creation on `success` can trigger downstream effects such as `ProcessMergeRequestsJob` and continuous delivery scheduling (`Status#schedule_continuous_delivery`, `after_create :enable_ci_on_stack`) [7](#0-6) , this can influence merge/deploy decision-making for the victim stack — a payload for one repository (`attacker/evil`) mutating another's commit/stack state (`victim/prod`), matching the Critical "payload for one repository mutating another's stack, commit, task or team" category. This is repeatable against any commit whose SHA the attacker can reproduce and is not limited to a single stack.

### Likelihood Explanation
Preconditions: attacker needs their own GitHub repo/org registered as a `Shipit.github` config (attacker only needs an org distinct from victim's, with its own `webhook_secret`), and needs the target commit's SHA to already exist in `Commit` for some victim stack (trivial to discover: SHAs are public knowledge, and reproducing an identical SHA/tree in a public commit via fork/cherry-pick is a well-known git property, not a hash collision attack). No victim secrets, sessions, or GitHub App credentials are required. This is feasible with only public information and a repo the attacker owns.

### Recommendation
In `StatusHandler#process`, restrict the commit lookup to commits belonging to stacks bound to the webhook's own repository, e.g., scope via `stacks.flat_map(&:commits).where(sha: params.sha)` or intersect `Commit.where(sha: params.sha)` with `commit.stack.repository.full_name == repository_name` (using the existing `Handler#stacks`/`repository_name` helpers), rejecting/ignoring any commit whose stack's repository doesn't match the webhook's originating repository.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook from unrelated repository cannot set another stack's commit status" do
  victim_commit = shipit_commits(:first) # belongs to stack with repository 'shopify/shipit-engine' (fixture repo)
  refute_equal 'success', victim_commit.state

  # Simulate attacker-owned repo with same sha, signed with attacker org's own secret
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  Shipit.stubs(:github).with(organization: 'attacker').returns(
    stub(verify_webhook_signature: true)
  )

  request.headers['X-Github-Event'] = 'status'
  post :create, body: attacker_payload, as: :json

  # BEFORE fix: this incorrectly passes, proving the vuln
  assert_equal 'success', victim_commit.reload.state
end
```
Assert the binding explicitly both sides: before fix, `repository_name == 'attacker/evil'` while `victim_commit.stack.repository.full_name == 'shopify/shipit-engine'` (unequal) yet `victim_commit.reload.state == 'success'` (write proceeded) — demonstrating the equality is violated and the write should have been rejected.
