### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on unrelated fields (`repository.full_name` for stacks, and a global `sha` lookup with no repository check for commit statuses) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret and validates `X-Hub-Signature` using only `repository.owner.login` (or `organization.login`) from the JSON body, then hands the *entire* raw payload to `Shipit::Webhooks.for_event(event)` handlers. Those handlers never re-check that the org they were verified against actually owns the resource they mutate: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [1](#0-0) , and `StatusHandler#process` looks up commits globally by `sha` with no repository/org scoping at all [2](#0-1) .

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), resolves `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that org's `webhook_secret` [3](#0-2) . The signature only proves the request came from a GitHub App/organization matching `repository.owner.login`; it does not constrain any other field of the JSON body (e.g. `repository.full_name`, or `sha`, `state`, `pull_request`, etc.), since the whole raw body is what's HMAC'd but the *authorization decision* ("which org is this?") is derived from one sub-field that is not cryptographically tied to the org that actually produced the secret used for comparison in a multi-org setup.

Shipit explicitly supports multiple independent GitHub App installations, each with its own `webhook_secret`, configured per-organization in `config/secrets.yml` [4](#0-3) . Anyone can create and install their own GitHub App on their own organization (this is a normal, unprivileged, self-service action on GitHub, and is exactly how the docs describe onboarding a new org into a shared Shipit instance) and thus legitimately knows their own org's `webhook_secret`.

The binding that should hold is:
`org authenticated by verify_signature == org/repository that the handler mutates`

But this is never enforced:
1. `PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, etc. all resolve the target `Repository`/`Stack` via `Repository.from_github_repo_name(payload/params.repository.full_name)` [1](#0-0) [5](#0-4)  — an attacker who owns `attacker-org` (and thus its `webhook_secret`) can pass signature verification with `repository.owner.login: "attacker-org"` while setting `repository.full_name: "victim-org/victim-repo"`, causing the handler to act on the victim's stack.
2. `StatusHandler#process` is worse: it does not even use `repository.full_name`; it does `Commit.where(sha: params.sha)` globally across every stack in the installation and calls `commit.create_status_from_github!(params)` [2](#0-1) . Since `verify_signature` only checked that the payload's `repository.owner.login` matches *some* org configured on this Shipit instance, an attacker who controls any one configured org's webhook secret can forge a `status` event carrying an arbitrary `sha` belonging to a commit in a completely different, victim organization's stack, and set an arbitrary `state`/`context`/`description`/`target_url` for it.

### Impact Explanation
Commit statuses feed directly into deployability: `Commit#deployable?` returns true when `stack.ignore_ci? || (success? && !blocked?)` [6](#0-5) , and a status transition to success also triggers `stack.schedule_merges` and `ContinuousDeliveryJob` [7](#0-6)  and [8](#0-7) . Forging a passing status on a victim commit can therefore unlock continuous deployment/merge-queue behavior (an unauthorized deploy or merge) for a repository the attacker has no access to, purely by knowing the webhook secret of an unrelated, self-registered org on the same Shipit instance. This matches the required High/Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the target Shipit instance hosts more than one GitHub organization (an explicitly documented, supported configuration [4](#0-3) ), and (b) the attacker controls at least one of those organizations' GitHub Apps (self-registerable, unprivileged with respect to the victim org). No GitHub write access to the victim repo, no Shipit session, and no victim secrets are needed — only the attacker's own `webhook_secret`, which they legitimately possess. This is a realistic, low-effort attack path in any multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, derive and re-verify the organization from every field the handler consumes to resolve state (particularly `repository.full_name` used for `Repository.from_github_repo_name`, and any commit lookup in `StatusHandler`). Concretely:
- Reject the payload if `repository.owner.login` (the field used for signature verification) does not match the owner segment of `repository.full_name`.
- In `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified payload (`stacks` from `Handler#stacks`) instead of a global `Commit.where(sha: ...)`.

### Proof of Concept
1. Attacker registers/owns `attacker-org` on GitHub and creates a GitHub App for it; installs it and configures Shipit with `github.attacker-org.webhook_secret = S` per `docs/setup.md`'s multi-org instructions.
2. Attacker computes `sha1=HMAC-SHA1(S, body)` for a crafted `status` event body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
     "sha": "<victim commit sha in victim-org/victim-repo>",
     "state": "success",
     "context": "ci/forced"
   }
   ```
3. POSTs to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` from `repository.owner.login`, verifies successfully against the attacker's own `webhook_secret` [9](#0-8) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` [2](#0-1) , finds the victim's commit (regardless of which org/repo it belongs to), and calls `create_status_from_github!`, marking it "success" and potentially triggering continuous deployment on the victim's stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
