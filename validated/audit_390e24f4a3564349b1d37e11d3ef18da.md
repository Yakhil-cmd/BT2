### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to bypass the stack-scoping enforced by `Shipit::Api::BaseController`, letting any `ApiClient` token with the `read:stack` permission read the CCMenu status of **any** stack in the installation, not just the stack it was authorized/generated for.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column [1](#0-0) . `Shipit::Api::BaseController` is designed to enforce this scoping for every resource lookup: it defines `stacks` to be filtered down to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves `params[:stack_id]` only against that filtered relation [2](#0-1) . Permission checking itself, `ApiClient#check_permissions!`, only checks that the permission string (e.g. `read:stack`) is present in the client's `permissions` array — it has no awareness of which specific stack is being accessed [3](#0-2) . So the *only* place the stack-id binding is actually enforced is the `stack`/`stacks` helper methods in `BaseController`.

`CCMenuController`, however, redefines `stack` to look the record up directly against the full `Stack` relation, ignoring `current_api_client.stack_id` entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The controller still calls `require_permission :read, :stack` [5](#0-4) , and authenticates the token from the `token` query param via `ApiClient.authenticate` [6](#0-5) , but since neither `check_permissions!` nor the local `stack` override consult `current_api_client.stack_id`, any valid, unrevoked `read:stack` token — including one deliberately scoped to a single stack (see the `here_come_the_walrus` fixture, which is created with `stack: shipit` [7](#0-6) , and the flow used by `CCMenuUrlController` to mint per-stack tokens [8](#0-7) ) — can be replayed against `GET /api/stacks/:stack_id/ccmenu` with a **different** `stack_id` and will successfully return that other stack's deploy/rollback status.

The binding broken is: *the stack a token authorizes* (`ApiClient#stack_id`, set at token creation) *versus the stack it actually touches* (whatever `stack_id` is supplied in the request path to `CCMenuController#show`).

### Impact Explanation
This is an authenticated but unauthorized cross-stack read: a token minted to expose CI/deploy status for one repository/stack (e.g. shared with an external CI dashboard or status badge) can be reused to read deploy/rollback state — including lock reason, last build status/label/time, and web URL — for any other stack managed by the same Shipit instance. This matches "unauthenticated/unauthorized read of stack state" although here disclosure crosses a client's intended tenant, since normal Shipit API clients (per `BaseController#stacks`) are properly scoped, only this handler is broken.

### Likelihood Explanation
High likelihood: exploitation requires no privilege beyond possession of any single valid CCMenu/`read:stack` token (these tokens are routinely shared externally as CI status URLs per `CCMenuUrlController`), and only requires changing the `stack_id` path parameter — no additional secrets, signatures, or session state are needed.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` unscoped, so a stack-scoped `ApiClient` cannot be used to read a different stack's CCMenu data.

### Proof of Concept
1. As an authorized user, request a CCMenu URL for Stack A via `CCMenuUrlController#fetch`, obtaining a token `T` bound to `ApiClient(stack_id: A.id, permissions: ['read:stack'])`.
2. Send `GET /api/stacks/:B_id/ccmenu?token=T` where `B` is an arbitrary different stack that `T` was never authorized for.
3. Observe `CCMenuController#show` returns HTTP 200 with Stack B's deploy/rollback XML, because `stack` resolves via unscoped `Stack.from_param!` rather than the client-scoped `stacks` relation.
