### Title
Ambiguous concatenation without separator in arbiter contract hash allows contract-terms collision/substitution - (File: arbiter_contract.js)

### Summary
`getHashSrc()` in `arbiter_contract.js` builds the source string that is SHA-256 hashed to produce a contract's canonical `hash` by concatenating variable-length, attacker-controlled text fields with **no separator** whenever `contract.creation_date <= exports.NEW_HASH_DATE`. Since `NEW_HASH_DATE = '2026-11-01'` is still in the future relative to the code's operating date, every contract created today uses this vulnerable, delimiter-less branch. This is the same root-cause pattern as CVE-2019-10911 (Symfony remember-me hash without a field separator): concatenating variable-length fields without a boundary marker before hashing allows different sets of field values to produce an identical digest by shifting characters across field boundaries. [1](#0-0) [2](#0-1) 

### Finding Description
`getHashSrc()` computes, for contracts dated on/before `NEW_HASH_DATE`:
```
[contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("")
```
`title`, `text`, `payer_name`, and `payee_name` are free-form strings supplied by the contract-offering peer (an untrusted "private-payment counterparty") when composing an `arbiter_contract_offer` message. Because these fields are joined with the empty string, no unambiguous boundary exists between them: a byte sequence ending one field can be reinterpreted as the start of the next. This is precisely the boundary-shifting hash-collision technique addressed by CVE-2019-10911 (an explicit separator, `DELIMITER = "[|#|]"`, was added for later contracts on/after `NEW_HASH_DATE`, showing the developers recognized and fixed this exact bug class for the new branch, but left the old, currently-active branch vulnerable). [3](#0-2) 

`getHash()` (built from `getHashSrc()`) is then trusted as the canonical, collision-free identifier of the contract terms throughout the rest of the protocol:
- It is embedded directly into the oscript/AA-style address definition governing release of shared-address funds, as the data-feed key `"CONTRACT_" + contract.hash` and `"CONTRACT_DONE_" + contract.hash`, which the arbiter or private-payment counterparty uses to authorize payout of the escrowed funds. [4](#0-3) 
- It is posted on-chain as `contract_text_hash` inside a `data` message that both peers rely on to prove which contract terms a signed shared-address unit corresponds to. [5](#0-4) [6](#0-5) 
- It is used to look up and match contract records purely by hash (`getByHash`, primary key `hash` in `wallet_arbiter_contracts`), and to parse the arbiter's dispute-resolution winner (`parseWinnerFromUnit` reads `"CONTRACT_" + contract.hash` from the arbiter's `data_feed`). [7](#0-6) 

Because the hash is not a faithful, collision-resistant binding to the exact field values (title/text/party names/amount/asset/arbiter), a malicious contract-offering peer can craft two distinct sets of `(title, text, payer_name, arbiter_address, payee_name, amount, asset)` that hash identically by moving characters across field boundaries (e.g., appending characters to `title` that are removed from the start of `text`, or shifting characters between `payer_name`/`arbiter_address`/`payee_name`). The victim's device displays and stores one set of terms while the on-chain data-feed key and the address-definition escrow condition derived from the identical hash could correspond to a different, attacker-favorable interpretation, or allow the attacker to fabricate a second contract that maps to the same `CONTRACT_<hash>` key used for fund release/dispute resolution.

### Impact Explanation
The bug can cause the escrow release condition embedded in the shared-address definition (`in data feed ... "CONTRACT_"+hash`) and the on-chain proof-of-terms (`contract_text_hash`) to no longer uniquely and faithfully bind to the displayed/agreed contract terms. This can lead to fund loss or misdirected payout at the shared arbiter-escrow address — a concrete unauthorized-spending/fund-loss condition reachable purely by a private-payment counterparty crafting offer text, matching the required "unauthorized spending" or "AA/escrow fund loss" bar.

### Likelihood Explanation
Exploitation requires crafting colliding SHA-256 preimages with a specific empty-separator boundary-shift structure, which is a non-trivial but known and demonstrated attack class (per the CVE analog and general hash-preimage/boundary-shift research for string-concatenation hashing). It does not require any privileged position — any peer able to initiate/negotiate an arbiter contract (title/text/party name fields are free text under attacker control) can attempt it. The vulnerable branch is confirmed to be currently active because `NEW_HASH_DATE` is set in the future, so no contract created today benefits from the already-implemented delimiter fix.

### Recommendation
Change the condition in `getHashSrc()` so the delimiter-based hashing (`exports.DELIMITER`) is used unconditionally (remove/backdate `NEW_HASH_DATE`, or apply the delimiter to all contracts regardless of `creation_date`), eliminating the vulnerable empty-string-join branch entirely. Additionally, apply the same fixed-delimiter approach to `prosaic_contract.js`'s `getHash()`/`getHashV1()`, which concatenate `title + text + creation_date` without any separator. [8](#0-7) 

### Proof of Concept
1. Attacker (contract offeror) chooses `title = "A"`, `text = "BC"`.
2. Attacker chooses an alternate pair `title = "AB"`, `text = "C"`.
3. With the empty-string join (`[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")`), both combinations concatenate to the same string `"ABC" + creation_date + ...` provided the rest of the fields are held constant, producing an **identical SHA-256 digest** and thus an identical `contract.hash`, despite the two offers having different logical `title`/`text` content.
4. This identical hash is embedded as `"CONTRACT_" + hash` in the shared address's escrow release condition and as `contract_text_hash` in the posted `data` message, so a victim who validates/signs based on one interpretation of the fields can be affected by protocol logic (dispute resolution, data-feed matching, cosigner record lookups keyed by `hash`) intended for the other, colliding interpretation. function getHashSrc(contract) {
```javascript
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
```

```javascript
function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
```
