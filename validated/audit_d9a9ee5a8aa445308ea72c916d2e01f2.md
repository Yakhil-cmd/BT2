### Title
Race condition in `dryRunPrimaryAATrigger` allows unprivileged unit posting to corrupt shared AA execution state used by real trigger processing - ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger()` mutates the same global, in-process caches (`storage.assocUnstableUnits`, state-var caches, balance caches) that `handleAATriggers()` uses to execute real, stabilized AA triggers, but unlike `handleAATriggers()` it is not protected by the `mutex.lock(['aa_triggers'])` critical section, creating a stale/leaked shared-state race analogous to CVE-2014-8122 (JBoss Weld's stale conversation state from unsynchronized shared per-conversation state across concurrent requests).

### Finding Description
`handleAATriggers()` explicitly serializes all real AA trigger execution behind `mutex.lock(['aa_triggers'], ...)` [1](#0-0) , because `handleTrigger()` reads and mutates process-wide shared caches (`storage.assocUnstableUnits`, `storage.assocStableUnits`, AA state-var/balance caches) while running formulas and building response units.

`dryRunPrimaryAATrigger()`, however, takes its own DB connection and calls `handleTrigger()` directly with `bDryRun: true`, with **no `mutex.lock(['aa_triggers'])`** around it: [2](#0-1) . It relies solely on `revertResponsesInCaches(arrResponses)` after `handleTrigger` finishes to "undo" the in-memory cache mutations it made [3](#0-2) , and separately rolls back its own DB transaction. This dry run is triggered directly from network-facing unit validation, reachable by any unprivileged unit poster whose unit pays an AA address, whenever `conf.bDryRunNewTriggers` is enabled: [4](#0-3) .

Because `handleAATriggers()`'s real execution and `dryRunPrimaryAATrigger()`'s speculative execution both operate on the same shared, non-cloned in-memory structures (`storage.assocUnstableUnits`, state-var caches) but only the real path takes the `aa_triggers` mutex, a dry run triggered by a posted (not-yet-stable) unit can interleave with a real trigger's execution on another async tick (both are asynchronous, DB-driven, `async.eachSeries`/callback chains). The dry run's `revertResponsesInCaches()` call at the end can revert or leave stale intermediate values in caches that the real execution is concurrently relying on for computing the next AA's balance/state view, which is exactly the "stale thread/conversation state visible across another conversation" bug class described in the JBoss Weld advisory — except here the "conversation" is one AA trigger execution and the "thread" is the shared global cache object, with the race window controlled by an external attacker who simply posts network units with AA outputs.

### Impact Explanation
If a dry run's cache mutation/reversion interleaves with a genuine `handleAATriggers()` execution on the same address(es), the state vars, balances, or unstable-unit metadata used to compute a real AA response can become corrupted or stale. Since AA responses (balances, `var[]` state) are consensus-critical and get committed to the DB/hash tree, this can cause: incorrect AA balance/state computation leading to fund loss or freezing in the AA, or different nodes computing different results for the same trigger (because the race is timing-dependent and depends on concurrent unit posting), producing node disagreement on AA response correctness/validity.

### Likelihood Explanation
Triggering the race requires only posting a normal payment unit whose output goes to an existing AA address while `conf.bDryRunNewTriggers` is enabled on the target node, and timing it so the dry run overlaps with genuine AA trigger execution at MC stabilization — both are routine, attacker-controllable events (any unprivileged peer can post units to AA addresses at will to try to win the race window). No special privileges are needed, only network access and correctly timed unit submission, though winning the exact interleaving window is probabilistic and depends on node load/timing.

### Recommendation
Serialize `dryRunPrimaryAATrigger()` (and `estimatePrimaryAATrigger()`, which has the same pattern) under the same `mutex.lock(['aa_triggers'])` used by `handleAATriggers()`, or otherwise ensure dry-run/estimate executions operate on cloned/isolated copies of `storage.assocUnstableUnits` and the AA state/balance caches instead of the live shared objects, so speculative executions can never interleave with or corrupt genuine trigger processing.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires precise interleaving of two async operations (`handleAATriggers()` execution at MC stabilization and `dryRunPrimaryAATrigger()` invoked from `network.js`'s `ifOk` handler for a freshly posted unit) against the same shared JS objects, which is a timing-dependent condition. The code paths and the missing lock are confirmed by direct comparison of `handleAATriggers` (locked) vs. `dryRunPrimaryAATrigger` (unlocked) in `aa_composer.js`, both operating on `storage`'s shared caches; a full reproduction would require a running two-node testbed with controlled unit timing, which is outside what can be confirmed via code inspection alone.
