Both external reports and this codebase share the same bug shape: a caller-side cap (`plotsAvailablePerSize` enforced only inside `RuniverseLandMinter`) is trivially bypassed because the shared mint entry point (`RuniverseLand.mintTokenId`) accepts calls from *any* authorized minter without itself enforcing the cap. The Polkadot SDK analog is `pallet-psm` (`substrate/frame/psm`): its debt-ceiling invariant (`max_debt` / per-asset ceiling) is enforced only inside `Psm::mint`, but the *same* internal asset can still be minted through a second, independently-authorized entry point — `pallet_assets::mint` — which is completely unaware of `PsmDebt`/`max_debt` and mints unbacked supply.

### Title
PSM debt ceiling is not the sole gate on internal-asset issuance — `pallet_assets::mint` bypasses `pallet-psm`'s reserve-backing invariant - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` maintains a critical invariant: every unit of `internal_asset` minted through the PSM is backed 1:1 by external collateral held in the PSM's reserve, bounded by `PsmInfo::max_debt` and per-asset `AssetCeilingWeight`. This invariant is enforced exclusively inside `Pallet::mint`. However, the underlying `internal_asset` is a normal `pallet_assets` asset that retains its own independent, permissioned `mint` extrinsic gated only by the asset's `Issuer` role — a role the pallet never revokes, transfers, or otherwise binds to the PSM instance when `create_psm` is called.

### Finding Description
`create_psm`'s `EnsureAssetOwner` origin check only verifies that the caller is the *current owner* of `internal_asset` at creation time: [1](#0-0) 

The accompanying comment even acknowledges that "PSM mint/burn bypasses the asset's issuer checks" — i.e., the pallet's own `mint_into` call goes through the low-level `Mutate` trait, not through `pallet_assets`'s issuer-gated dispatchable. What it does *not* address is the inverse direction: nothing strips or reassigns the asset's `Issuer`/`Admin` team after `create_psm`. The same account (or any account subsequently granted the `Issuer` role via `pallet_assets::set_team`) can call `pallet_assets::mint` directly: [2](#0-1) 

That path increases `details.supply` and credits the beneficiary's balance with no reference whatsoever to `PsmDebt`, `PsmInfo::max_debt`, `AssetCeilingWeight`, or the PSM reserve. Compare with `Psm::mint`, where issuance is strictly capped: [3](#0-2) 

Just as `RuniverseLand.mintTokenId` only checks `msg.sender == primaryMinter || msg.sender == secondaryMinter` and lets `secondaryMinter` mint arbitrary token IDs unconstrained by `plotsAvailablePerSize` (which is checked only in `RuniverseLandMinter._mintTokens`), here the shared resource (`internal_asset`'s total issuance) has two independent, individually-valid minting authorities — `pallet-psm`'s `Pallet::mint` and `pallet_assets`'s `Pallet::mint` — but the debt-ceiling / collateral-backing invariant is checked in only one of them.

### Impact Explanation
Any account that retains (or is granted) the `Issuer` role on the internal asset after PSM creation can mint unlimited, completely unbacked units of the "stablecoin" the PSM is supposed to protect. This directly undermines the PSM's core guarantee (1:1 backing, bounded issuance via `max_debt`) and is an unbacked-issuance class bug — one of the impact categories explicitly prioritized as Critical/High. Downstream consumers relying on the PSM's peg guarantee (DEX pools, other protocols pricing the "stablecoin" at $1) would be exposed to silent dilution.

### Likelihood Explanation
This does not require any external/root privilege beyond a role (`Issuer`) that is completely ordinary in a `pallet_assets` deployment and is very likely to be held by the same address that created the PSM (the `EnsureAssetOwner` check only requires *ownership*, and `pallet_assets`'s default team assignment on `create`/`force_create` typically sets owner = issuer = admin = freezer unless explicitly split via `set_team`). No dedicated mechanism in `create_psm`, `add_external_asset`, or elsewhere transfers or revokes this issuer capability, so the gap is present by default in any runtime wiring `pallet-psm` over a `pallet_assets` asset without a separate, disciplined governance process to strip issuer rights. I could not find such an enforcement anywhere else in the file (verified through `set_max_debt`, `add_external_asset`, `remove_external_asset`, admin-management calls, lines 1000–1500).

### Recommendation
`create_psm` (or a companion extrinsic) should require/verify that `internal_asset`'s `Issuer` (and ideally `Admin`) team member is the PSM's own reserve/pallet account (or `None`/unmintable) before activating the instance, and should reject or warn if a live, external issuer capability still exists. Alternatively, document this as a hard deployment precondition and add a `try_state`/`integrity_test` check that fails if the configured internal asset still has an externally-controlled issuer once a PSM is registered for it.

### Proof of Concept
Not independently executed against a live runtime in this pass — the analysis is derived by tracing `Psm::mint`'s cap-enforcement logic (`substrate/frame/psm/src/lib.rs:701-768`) against the completely separate, uncapped `pallet_assets::do_mint` path (`substrate/frame/assets/src/functions.rs:457-477`), and confirming no code in `pallet-psm` transfers or revokes the internal asset's `Issuer` role at `create_psm` time (`substrate/frame/psm/src/lib.rs:942-1009`). A full reproduction would require a minimal test-runtime `TestExternalities` wiring `pallet-assets` + `pallet-psm`, calling `create_psm` from the asset owner, then calling `Assets::mint` directly from that same account/Issuer role to show `Assets::total_issuance` growing without any corresponding `PsmDebt` increase or external collateral deposit — this exact scenario is not present in `substrate/frame/psm/src/tests.rs` (which only tests ceiling/ceiling-redistribution behavior through the PSM's own `mint` extrinsic, e.g. `fails_mint_exceeds_aggregate_psm_ceiling` and `multiple_assets_share_redistributed_ceiling`), so the gap is not covered by existing test harnesses.
