### Title
Webhook signature verification uses an attacker-selectable organization key that is decoupled from the JSON payload actually processed - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) from `repository_owner`, which is read via `params.dig('repository','owner','login')` — i.e. Rails' merged `ActionController::Parameters`, not the raw JSON body. The `create` action, however, re-parses the actual event data straight from `request.raw_post` and dispatches handlers (e.g. `StatusHandler`) based on that body alone. This breaks the equality that should hold: *the organization whose secret validated the signature* == *the repository/commit the dispatched handler actually mutates*.

### Finding Description
`verify_signature` resolves the signing organization like this: [1](#0-0) 
`repository_owner` is derived from the controller's `params`, not from the JSON body that will later be processed: [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved app config has no `webhook_secret` configured, and only checks the HMAC of `algorithm=sha1` otherwise: [3](#0-2) 

Meanwhile, `create` independently parses the same raw body and dispatches handlers directly from it, with no re-check that the event's repository/organization matches the one whose secret was used to authorize the request: [4](#0-3) 

Rails' standard `ActionController::Parameters` are built by merging query-string parameters over the request/body parameters (`request_parameters.merge(query_parameters)`), so a top-level key such as `repository` supplied in the query string overrides the same top-level key parsed from the JSON POST body. This means an attacker can send a request whose query string sets `repository[owner][login]=<org-with-no-webhook_secret-or-known-secret>` (controlling which app config `verify_signature` uses), while the actual JSON body — the thing that is really executed — targets a completely different, victim-tracked repository/commit.

Several event handlers make the impact concrete because they don't re-validate the repository/organization against anything cryptographically bound to the signature: `StatusHandler` updates the status of *any* commit matching `sha`, with no ownership/organization check at all: [5](#0-4) 

So the equality that should hold — *organization authenticated by the verified signature == repository/commit the handler is allowed to act on* — is broken: the signature only proves "someone possessing/omitting-a-secret for org X sent this HTTP request," while the handler acts on whatever `repository`/`sha` is embedded in the JSON body, which can name an entirely different, unrelated tracked repository or commit.

### Impact Explanation
An attacker who identifies (or forces resolution to) any configured GitHub organization/app entry in the Shipit installation lacking a `webhook_secret` can submit a forged `status` webhook for a commit belonging to a completely different, victim-tracked stack, since the signature check for that particular request is bypassed entirely (`return true unless webhook_secret`) while the event body still targets the victim commit/stack. If the targeted stack has continuous deployment enabled and depends on such statuses to consider a commit deployable, this can be used to fake a passing CI status and trigger an unauthorized deploy of a commit that never legitimately passed checks — matching the "unauthorized deploy" impact bucket.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`) and reachable by any unprivileged network attacker; no session, `ApiClient` token, or repository write access is required. The only precondition is the existence of at least one configured organization/app without a `webhook_secret`, which is a realistic operator-configuration state (e.g., orgs onboarded before a secret was set, or public/demo orgs).

### Recommendation
Bind the signature-verification target to the same payload that is actually executed: parse `request.raw_post` once, derive `repository_owner`/`organization` strictly from that parsed JSON (never from `ActionController::Parameters`, which can be polluted by the query string), and re-validate inside each handler that the `repository`/`organization` in the payload used for dispatch matches the one whose secret validated the signature. Additionally, treat a missing `webhook_secret` as a hard configuration error rather than an implicit bypass (`return true unless webhook_secret`).

### Proof of Concept
1. Identify (from Shipit configuration/onboarding) an organization app entry, `org-no-secret`, with `webhook_secret` unset.
2. Send:
   ```
   POST /webhooks?repository[owner][login]=org-no-secret HTTP/1.1
   X-Github-Event: status
   Content-Type: application/json

   {"sha":"<victim-commit-sha>","state":"success","repository":{"full_name":"victim-org/victim-repo","owner":{"login":"victim-org"}}}
   ```
3. `verify_signature` computes `repository_owner` from the merged `ActionController::Parameters`, which resolves to `org-no-secret` (query string wins over the JSON body's `repository.owner.login`), so `Shipit.github(organization: 'org-no-secret').verify_webhook_signature(...)` returns `true` without ever checking an HMAC.
4. `create` re-parses `request.raw_post` (the JSON body naming `victim-org/victim-repo` and `victim-commit-sha`) and dispatches `StatusHandler`, which sets a `success` status on the victim commit — regardless of the organization used to pass step 3.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
