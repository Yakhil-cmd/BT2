### Title
`claim_revenue` payout to an attacker-chosen dust-value payee permanently locks pool revenue instead of allowing retry - ([File: substrate/frame/broker/src/dispatchable_impls.rs])

### Summary
`pallet-broker::do_claim_revenue` mirrors the tbtc bug-class exactly: it performs its bookkeeping mutations first and then, at the very end, does a single push-style `T::Currency::transfer(...)?` to a fully attacker-chosen `payee` account. Because the call site uses `?`, any transfer failure aborts the whole extrinsic (rolled back by FRAME's transactional dispatch), and the *same* deterministic failure will occur every single time anyone re-attempts `claim_revenue` for that contribution, because the payee and the pool mechanics that produce the payout are fixed. This is functionally identical to `liquidationInitiator.transfer(...)` reverting `purchaseSignerBondsAtAuction` forever.

### Finding Description
`InstaPoolContribution` records store a `payee: T::AccountId` that is fully controlled by whoever calls the `pool` extrinsic (`do_pool`, `substrate/frame/broker/src/dispatchable_impls.rs:392-417`) — no permission or existing-account check is made on `payee`. Later, anyone (permissionless) can call `claim_revenue`, which executes `do_claim_revenue`: [1](#0-0) 

The order of operations is:
1. `InstaPoolContribution::<T>::take(region)` — removes the caller's contribution record from storage (in-memory, since the whole call is inside a transactional dispatch envelope).
2. Iterate `InstaPoolHistory` for the covered timeslices, computing `payout` and mutating/removing `InstaPoolHistory` entries.
3. Only at the end: `T::Currency::transfer(&Self::account_id(), &contribution.payee, payout, Expendable)?`.

If `payout` is smaller than the chain's Existential Deposit and `contribution.payee` is an account that does not already exist (or would be pushed below ED), the `fungible::Mutate::transfer` deposit into a non-existent account fails deterministically with `TokenError::BelowMinimum` (or an analogous `DispatchError`). Because of the trailing `?`, this error propagates out of `do_claim_revenue`, and FRAME's default transactional dispatch wrapper reverts *all* storage writes made in steps 1–2 — including the removal of `InstaPoolContribution` and the `InstaPoolHistory` payout bookkeeping.

The critical parallel to the tbtc bug is: the payee, the payout computation inputs (`region.mask.count_ones()`, the fixed historical `InstaPoolHistory` payout/contribution totals), and the account non-existence condition are all deterministic and effectively fixed once the pool contribution is created. This means **every future retry of `claim_revenue` for that region hits the identical failure**, exactly as every future call to `purchaseSignerBondsAtAuction` in tbtc hit the identical `initiator.transfer` revert. There is no fallback path, no pull-based claim, and no way to separate the payment step from the bookkeeping step so that at least the accounting can be finalized while the payment is retried/rerouted.

### Impact Explanation
Unlike a typical “transfer fails, transaction reverts, try again” scenario, the deterministic and payee-fixed nature of the failure means the affected `InstaPoolContribution`/`InstaPoolHistory` payout share becomes **permanently unclaimable** — the revenue sits frozen in the broker pallet's account forever, and the contribution record can never be advanced or cleared through the normal `claim_revenue` path (only `do_drop_contribution`, gated by a `contribution_timeout` window, could eventually clear the record, but the underlying `InstaPoolHistory::maybe_payout` funds are not distributed to the intended payee — they are simply abandoned in the pot). This is a fund-availability / permanent-freezing issue analogous in class to the tbtc auction getting stuck in `*_liquidation_in_progress` forever.

However, the actual monetary impact is bounded by the requirement that `payout < ExistentialDeposit`, i.e. dust-scale amounts per timeslice batch, and the "attacker" is effectively griefing their own claimable revenue share (self-inflicted loss) rather than stealing value from others or blocking a shared/contested auction resource the way tbtc's bug did. Other contributors' `claim_revenue` calls are unaffected since they operate on their own, disjoint `InstaPoolContribution` keys.

### Likelihood Explanation
Low-to-Medium. Triggering it requires the contribution owner to deliberately (or accidentally) set `payee` to a non-existent account and to structure/timeslice their claim such that computed `payout` stays under the existential deposit — a scenario more likely to occur as an unintentional foot-gun (e.g., claiming with `max_timeslices = 1` against a low-yield pool) than as an attack against a third party, since only the caller's own funds are affected.

### Recommendation
- Perform the `T::Currency::transfer` (or `Preservation::Preserve`/existence check) *before* committing to remove `InstaPoolContribution`/mutate `InstaPoolHistory`, or structure the payout so a failed transfer does not silently abandon the underlying accounting; alternatively use a pull-based claim (`Currency::hold`/deferred payment ledger) so the payee can retry independent of the exact same failure condition.
- Explicitly `ensure!` that `payout >= T::Currency::minimum_balance()` (or that the payee account already exists) before attempting the transfer, returning a clear, recoverable error (e.g., `Error::<T>::PayoutTooSmall`) rather than relying on the underlying `Currency::transfer` error to be propagated after mutations are computed.
- Consider accumulating dust below ED instead of attempting a doomed transfer, so it can be combined with future claims once it clears the ED threshold.

### Proof of Concept
No executable PoC was run; this analysis is based on static code reading only, per the constraints of this task (no filesystem/terminal access). The trace was validated by inspecting:
- `pool`/`do_pool` (`substrate/frame/broker/src/dispatchable_impls.rs:392-417`) showing `payee` is fully caller-controlled with no existence/ED validation.
- `do_claim_revenue` (`substrate/frame/broker/src/dispatchable_impls.rs:419-472`) showing storage mutations precede the single `T::Currency::transfer(...)?` payout, with FRAME's default transactional dispatch reverting all of steps 1–2 on transfer failure.
- The commit message associated with `prdoc/pr_13040.prdoc` ("Propagate the revenue claim transfer error ... Return the error when the revenue payout to the payee fails, so the extrinsic reverts and the claimant keeps the entitlement") confirms this exact failure path is intentional current behavior, not a legacy bug already fixed for the deterministic-failure case described here.

Given the self-inflicted nature of the fund lock and the lack of a verified on-chain reproduction (no test harness run confirming the exact `TokenError::BelowMinimum` propagation path end-to-end), I present this with **reduced confidence** as a Low/Medium-severity analog rather than a definitively proven Critical/High finding. A background Devin agent with code-execution access would be needed to build a minimal `pallet-broker` mock-runtime test that: (1) calls `pool` with a fresh non-existent `payee`, (2) drives `InstaPoolHistory` payouts to a sub-ED value, (3) calls `claim_revenue`, and (4) asserts the extrinsic errors while `InstaPoolContribution`/`InstaPoolHistory` remain unchanged and unclaimable on retry — to confirm actual bounty eligibility under the Parity program.

	pub(crate) fn do_claim_revenue(
		mut region: RegionId,
		max_timeslices: Timeslice,
	) -> DispatchResult {
		ensure!(max_timeslices > 0, Error::<T>::NoClaimTimeslices);
		let mut contribution =
			InstaPoolContribution::<T>::take(region).ok_or(Error::<T>::UnknownContribution)?;
		let contributed_parts = region.mask.count_ones();

		Self::deposit_event(Event::RevenueClaimBegun { region, max_timeslices });

		let mut payout = BalanceOf::<T>::zero();
		let last = region.begin + contribution.length.min(max_timeslices);
		for r in region.begin..last {
			region.begin = r + 1;
			contribution.length.saturating_dec();

			let Some(mut pool_record) = InstaPoolHistory::<T>::get(r) else { continue };
			let Some(total_payout) = pool_record.maybe_payout else { break };
			let p = total_payout
				.saturating_mul(contributed_parts.into())
				.checked_div(&pool_record.private_contributions.into())
				.unwrap_or_default();

			payout.saturating_accrue(p);
			pool_record.private_contributions.saturating_reduce(contributed_parts);

			let remaining_payout = total_payout.saturating_sub(p);
			if !remaining_payout.is_zero() && pool_record.private_contributions > 0 {
				pool_record.maybe_payout = Some(remaining_payout);
				InstaPoolHistory::<T>::insert(r, &pool_record);
			} else {
				InstaPoolHistory::<T>::remove(r);
			}
			if !p.is_zero() {
				Self::deposit_event(Event::RevenueClaimItem { when: r, amount: p });
			}
		}

		if contribution.length > 0 {
			InstaPoolContribution::<T>::insert(region, &contribution);
		}
		// The steps above removed the contribution and reduced the stored payouts. If the
		// transfer fails, the error must revert them. The storage changes and the payment
		// must both happen, or neither.
		T::Currency::transfer(&Self::account_id(), &contribution.payee, payout, Expendable)?;
		let next = if last < region.begin + contribution.length { Some(region) } else { None };
		Self::deposit_event(Event::RevenueClaimPaid {
			who: contribution.payee,
			amount: payout,
			next,
		});
		Ok(())
	}
