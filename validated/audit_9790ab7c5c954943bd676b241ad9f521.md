### Title
Accrued market-value overflow permanently freezes an overgrown market - ([File: common/src/rates/simulate.rs])

### Summary
The pool computes each market’s total borrowed and supplied value by multiplying stored RAY-scaled share balances by their RAY indexes. Those products can exceed `i128` before either index reaches its configured ceiling. Once that happens, every state-changing path that loads the market first attempts accrual and aborts with `MathOverflow`, leaving repayment, withdrawal, liquidation, recapitalization, and index synchronization unavailable. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` unconditionally calls `scaled_to_original` for both `borrowed * borrow_index` and `supplied * supply_index`. [3](#0-2)  `scaled_to_original` delegates to `Ray::mul`, which evaluates `x * y / RAY` and returns `MathOverflow` when the exact quotient does not fit `i128`. [4](#0-3) [5](#0-4) [6](#0-5) 

The protocol only caps the resulting indexes at `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`; it does not cap the intermediate market value computed from shares times index. [7](#0-6) [8](#0-7)  The public pool path for `update_indexes` calls `market::accrue`, which loads each market and invokes `interest::global_sync`. [9](#0-8) [10](#0-9)  `global_sync` chunks elapsed time and invokes the same fallible `accrue_step` before committing state. [11](#0-10) 

All ordinary market mutations use `synced_market`, so they perform the same accrual before executing their operation. [12](#0-11)  The controller exposes `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and permissionless `update_indexes` entrypoints that route into those synchronized pool operations. [13](#0-12) [14](#0-13)  The repository’s own long-horizon test demonstrates the exact failure: a one-billion-token, 18-decimal market at 98% utilization later returns `MATH_OVERFLOW` from `update_indexes`, while both withdrawal and repayment fail with the same error and the borrow index remains below its cap. [15](#0-14) 

### Impact Explanation
Once `borrowed * borrow_index` or `supplied * supply_index` crosses the `i128` result limit, the transaction fails before indexes, positions, cash, or bad debt are updated. Because repayment, withdrawal, liquidation, index updates, revenue handling, and recapitalization all load a synced market, there is no unprivileged recovery path through the affected market. Suppliers cannot exit, borrowers cannot reduce debt, liquidators cannot resolve risk, and pool tokens remain custodied without a usable accounting operation. This constitutes permanent freezing of user funds and market operations unless the contracts are upgraded. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
A single unprivileged account can establish the precondition by borrowing a sufficiently large position in a high-decimal, high-rate market whose caps and collateral requirements admit it. The attacker does not need a privileged role: `borrow` is owner/delegate-gated only for the borrowing account the attacker controls, while `update_indexes` is explicitly permissionless. After sufficient elapsed time, the next accrual crosses the representable market-value boundary. The repository test uses valid-looking bounds—an 18-decimal asset, maximum utilization disabled, a 175% maximum borrow-rate curve, one billion supplied tokens, and 98% utilization—and reaches the freeze within its bounded yearly loop. The likelihood is constrained by token supply, collateral availability, governance-configured caps, and the need for prolonged high-utilization accrual, but none of those requirements relies on a privileged action or malformed input. [18](#0-17) [14](#0-13) [19](#0-18) 

### Recommendation
Make accrual value-safe before multiplying scaled balances by indexes. At minimum, compute `borrowed_original` and `supplied_original` with a saturating or reduced-precision path sufficient for utilization, or pre-bound the stored scaled totals and index products so the conversion cannot revert. Keep the existing index ceilings, but enforce the tighter joint bound `scaled_balance * index <= i128::MAX * RAY` before admission and during accrual. The design should preserve an emergency path that can socialize debt, cap utilization, or write indexes without first evaluating an overflowing total; otherwise all recovery operations inherit the same failure. [20](#0-19) [11](#0-10) 

### Proof of Concept
Use an 18-decimal market configured with a cap at least one billion whole tokens and a steep but valid rate curve. A single caller can:

1. Call `supply(caller, 0, spoke_id, [((hub_id, COLLATERAL), 30_000_000_000_000_000_000_000_000_000)])` to create collateral account `A`.
2. Call `supply(caller, 0, spoke_id, [((hub_id, DEBT_ASSET), 1_000_000_000_000_000_000_000_000_000)])` to create market account `B`; in a live market, existing supplier liquidity can replace this self-funded liquidity.
3. Call `borrow(caller, A, [((hub_id, DEBT_ASSET), 980_000_000_000_000_000_000_000_000_000)], None)` to leave the market at approximately 98% utilization.
4. Advance ledger time and repeatedly call `update_indexes(caller, [(hub_id, DEBT_ASSET)])`.
5. When the index has grown enough that `borrowed_scaled * borrow_index / RAY` exceeds `i128::MAX`, `update_indexes` reverts in `scaled_to_original`.
6. Subsequent calls to `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `recapitalize`, and `update_indexes` for that market hit the same accrual first and revert with `MathOverflow`.

The repository test encodes this sequence with `principal = 1_000_000_000 * 10^18`, `debt = principal * 98 / 100`, yearly `update_indexes` calls, and then verifies that `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. [21](#0-20)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
