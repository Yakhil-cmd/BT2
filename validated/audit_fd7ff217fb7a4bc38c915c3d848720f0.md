## Title
Unbounded loop when composing AA payment responses can permanently freeze AA funds - (`aa_composer.js`)

## Summary
The Putty finding is that `_transferERC20sOut`/`_transferERC721sOut`/`_transferFloorsOut` iterate over unbounded, caller-controlled arrays with no upper bound, so gas costs for `exercise()`/`withdraw()` can grow beyond what is feasible, permanently stranding assets owed to a counterparty. The same bug class exists in ocore's Autonomous Agent response-composition logic: the routine that builds an AA's outgoing payment message picks up **all** matching unspent outputs belonging to the AA with no cap on how many inputs can be pulled in, and this generated unit is explicitly exempted from the anti-spam limits (`MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_UNIT_LENGTH`) that apply to ordinary units.

## Finding Description
When an AA needs to pay out bytes/assets in response to a trigger, `aa_composer.js`'s `sendUnit()` -> `completePaymentPayload()` -> `iterateUnspentOutputs()` loops over the full result set returned by `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) 

Unlike the equivalent wallet-side coin-selection routine `pickDivisibleCoinsForAmount()` in `inputs.js`, which explicitly caps the number of rows fetched with `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`: [2](#0-1) 

the AA queries `readStableOutputs`/`readUnstableOutputsSentByAAs` have **no `LIMIT` clause at all**: [3](#0-2) 

Making matters worse, `validatePaymentInputsAndOutputs()` in `validation.js` explicitly **exempts AA-generated payments** from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` anti-spam check: [4](#0-3) 

and the general unit-size validation in `validate()` also exempts both genesis units and AA units from the `MAX_UNIT_LENGTH` cap: [5](#0-4) 

An unprivileged unit poster can send an AA many separate, small trigger payments (each creating its own tiny unspent output owned by the AA's address). Since these outputs are never merged/consolidated on-chain, they simply accumulate. When a trigger later causes the AA to attempt to send-all or pay out a large enough amount that it must sweep across many of these tiny outputs, `iterateUnspentOutputs()` will pull in an unbounded number of inputs — potentially thousands — into a single payment message, exactly the "unlimited number of tokens transferred" pattern from the Putty report, except here the "tokens" are UTXO-style byte/asset outputs.

## Impact Explanation
Because both the per-message input-count cap and the total unit-size cap are bypassed for AA-generated units, there is no mechanism to reject an oversized response before it is built. Constructing, hashing, and saving (`writer.saveJoint`) a response unit with a huge number of inputs is expensive (each input requires a DB write and validation round-trip), and every full node that later re-validates/re-processes this AA response is forced to redo the same unbounded work (the AA exemption from `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH` applies identically on every node validating the unit, since it's derived from `objValidationState.bAA`, not from a trust decision of the composing node). If the AA's logic requires sweeping its full balance (e.g. paying an exercised/withdrawn amount to a user), and that balance is spread across an attacker-inflated number of dust outputs, the response construction can become impractically slow or resource-intensive, effectively preventing the AA from ever completing that response. Since AA fund release is entirely mediated by these auto-generated response units, this can permanently freeze user funds held by the AA, mirroring the "buyer paid the premium but can never receive the assets" impact described in the Putty report.

## Likelihood Explanation
An unprivileged party can cheaply create many small trigger payments to a target AA (bounded only by their own transaction fees, which are far lower than the cost imposed on the AA/network to process the resulting sweep). No special privileges, AA author cooperation, or node compromise are needed — this is reachable purely by a normal AA trigger sender interacting with any AA whose logic can be made to pay out its accumulated balance (e.g. common withdraw/exercise-style AAs).

## Recommendation
- Add an explicit `LIMIT` (mirroring `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`) to the `readStableOutputs`/`readUnstableOutputsSentByAAs` queries in `aa_composer.js`, and implement multi-unit "sweep" logic (splitting large payouts across multiple response units) instead of assuming a single message can always hold all inputs.
- Remove or tighten the `!objValidationState.bAA` and `!bAA` exemptions in `validation.js` (`validatePaymentInputsAndOutputs` line ~2137 and the unit-size check at line ~267) so AA-generated units are still bounded by sane anti-spam limits, or provide an AA-specific, still-finite, cap.
- Consider consolidating/merging an AA's own small outputs opportunistically (e.g., during idle periods) so that dust cannot be trivially made to accumulate to unbounded counts by a third party.

## Proof of Concept
1. Deploy an AA whose logic accepts deposits into per-user balances and pays out the requester's tracked balance (a common "vault"/"exercise" style AA).
2. As an unprivileged attacker, send a very large number of minimal-amount trigger payments to the AA from many distinct source outputs, each just above dust threshold, so each creates a new small unspent output owned by the AA address (`readStableOutputs` query in `aa_composer.js` lines 1140-1155 will later match all of them).
3. Trigger a withdrawal/exercise request (by the attacker or a victim) that requires the AA to send-all or pay an amount that can only be satisfied by consuming a large fraction of these outputs.
4. Observe that `completePaymentPayload` → `iterateUnspentOutputs` (`aa_composer.js` lines 1102-1138) collects all matching rows with no `LIMIT`, and that `validatePaymentInputsAndOutputs` (`validation.js` lines 2137-2140) and the general unit-size check (`validation.js` lines 267-268) do not reject the resulting oversized response unit because `objValidationState.bAA` is true — resulting in an unusually large, expensive-to-process response unit or an outright failure/stall in composing/saving it, leaving the requester's funds unpaid.
