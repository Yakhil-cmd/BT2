### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scoping, letting a stack-scoped token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve the target stack directly from `params[:stack_id]` instead of using the `stack_id`-scoped lookup defined in `BaseController`. As a result, an `ApiClient` token that is supposed to be restricted to a single stack (e.g. a CCMenu token minted by `CCMenuUrlController`) can be replayed against any other stack in the instance to read its build/deploy status.

### Finding Description
`BaseController` defines the intended authorization binding between an `ApiClient` token and the stack(s) it may touch: [1](#0-0) 

`stacks` restricts the resolvable set to `current_api_client.stack_id` when the client is scoped to a stack, and `stack` is derived from that scoped relation via `stacks.from_param!`. This is the equality the rest of the API relies on: `token.stack_id == stack_id_being_accessed` (or the token is unscoped).

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` against the *entire* `Stack` table, not the scoped `stacks` relation. The controller's own `authenticate_api_client` override only checks that `params[:token]` is a valid `ApiClient` token, and `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string — neither checks that `current_api_client.stack_id` matches the requested `params[:stack_id]`: [3](#0-2) 

Tokens intended to be single-stack scoped are created by `CCMenuUrlController`, which mints an `ApiClient` with only `read:stack` permission and hands the resulting token+stack URL to the user for a specific stack: [4](#0-3) 

The stack id embedded in that generated URL is advisory only — the token itself (`ApiClient#authentication_token`) carries no stack restriction enforcement in `CCMenuController`, even though the model has a `stack_id` column and `BaseController#stacks` was built specifically to enforce it.

### Impact Explanation
Before: a CCMenu token created for stack A is expected to only ever return build/deploy status for stack A (`Stack.where(id: current_api_client.stack_id)`), per the binding enforced in `BaseController#stacks`/`#stack`.
After: because `CCMenuController#stack` calls `Stack.from_param!` unscoped, the same token — obtained legitimately for stack A, e.g. from a shared CI status widget URL — can be replayed with any other stack's `stack_id` param to read that unrelated stack's latest deploy id, status, and lock state via the CCMenu XML response. This is an unauthenticated-scope-boundary read: the token authorizes read access to one stack, but it can be used to touch every stack in the Shipit instance, an authorization escalation matching "unauthorized read of stack state" beyond what the token was authorized for.

### Likelihood Explanation
Any holder of a CCMenu token/URL (these are handed out for embedding in CI dashboards, IRC bots, etc., and are visible/known since the URL contains the token as a plain query parameter) can trivially swap the `stack_id` path segment to any other stack in the same Shipit deployment and receive that stack's status, with no further authentication required.

### Recommendation
Make `CCMenuController#stack` resolve through the scoped `stacks` relation (i.e. reuse `BaseController#stack`/`#stacks` instead of overriding it with an unscoped `Stack.from_param!`), so the `current_api_client.stack_id` binding is enforced the same way it is for every other API controller.

### Proof of Concept
1. As a legitimate user, visit a stack and call `CCMenuUrlController#fetch` to obtain a CCMenu URL for stack `org/repoA/production`; this mints an `ApiClient` scoped to `repoA`'s stack with `read:stack` permission and returns a URL like `.../api/stacks/org/repoA/production/ccmenu.xml?token=<token>`.
2. Take the same `token` value and request `.../api/stacks/org/otherRepo/production/ccmenu.xml?token=<token>`.
3. `CCMenuController#authenticate_api_client` validates the token (valid `ApiClient`), `require_permission :read, :stack` passes because the client has `read:stack`, and `stack` resolves `otherRepo/production` unscoped via `Stack.from_param!`, returning that unrelated stack's deploy status instead of a 403/404 — demonstrating the token is not actually confined to the stack it was issued for.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
