### Title

Unbounded RAY-value multiplication can permanently freeze an entire lending market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

The interest-accrual path converts scaled borrow and supply shares into underlying RAY-denominated values before calculating utilization. [1](#0-0)   
When `scaled_shares * index` exceeds `i128::MAX`, the checked fixed-point multiplication panics before the configured borrow-index cap can take effect. [2](#0-1)   
Because all state-changing market operations accrue interest first, this single overflow permanently blocks repayments, withdrawals, liquidations, and further index updates for the affected market. [3](#0-2) 

### Finding Description

`accrue_step` begins each interest chunk by calling `scaled_to_original` separately for total borrowed shares and total supplied shares, then passes both expanded values to `utilization`. [4](#0-3)   
The pool invokes this function for every elapsed chunk in `global_sync`, commits the resulting indexes, and adds the resulting revenue shares. [5](#0-4) [6](#0-5)   
The same unscaled RAY products are also used by cached utilization calculations, so a market whose scaled balances are individually valid can still produce an intermediate product outside the `i128` domain. [7](#0-6)   

The repository’s long-horizon test creates a billion-token, 18-decimal market, borrows at 98% utilization, advances time until `scaled_to_original` returns `MathOverflow`, and observes that the borrow index remains below `MAX_BORROW_INDEX_RAY`. [8](#0-7)   
This mirrors the report’s oversized crafted-input memory corruption class: an input-driven arithmetic expansion overflows the runtime’s representation, but in Soroban the resulting trap becomes a persistent accounting-state denial of service rather than a native heap write. [9](#0-8) 

### Impact Explanation

Once the scaled borrow or supply product reaches the `i128` ceiling, the next accrual panics before updating `last_timestamp` or committing a capped index. [10](#0-9) [11](#0-10)   
Every subsequent accrual repeats the same multiplication on unchanged state, so the failure is not transient and cannot be bypassed by waiting longer. [12](#0-11)   

The regression test confirms that `withdraw` and `repay` both fail with `MATH_OVERFLOW` after the index update fails, and liquidation is likewise blocked because it must synchronize the market before reading or changing debt. [3](#0-2)   
The impact is therefore permanent freezing of all supplier funds and borrower obligations in the affected market, plus an inability to liquidate positions or progress normal market operations. [13](#0-12) 

### Likelihood Explanation

An unprivileged user can drive the market toward this state through ordinary `supply` and `borrow` calls by depositing a very large amount and borrowing at sustained high utilization; no privileged pool entrypoint is required because the controller is the owner-facing caller. [14](#0-13) [15](#0-14)   
The attacker does not need to supply the whole overflow boundary if the market already contains substantial third-party deposits: borrowing enough liquidity to keep utilization on the steep part of the configured curve compounds the borrow index until the existing scaled balances overflow. [16](#0-15)   

The exploit requires extreme token scale, sufficient collateral, and sustained high utilization, so it is more plausible for high-decimal or very-large-supply assets than for ordinary capped markets. [17](#0-16)   
Nevertheless, the demonstrated state is reachable through permitted user actions, and the panic occurs before the intended `MAX_BORROW_INDEX_RAY` safeguard can prevent the overflow. [18](#0-17) 

### Recommendation

Calculate utilization without materializing the full `scaled * index` products, or bound every market so both products provably remain below `i128::MAX`. [19](#0-18)   
The invariant should be enforced when supply or debt shares are minted, when market decimals/index parameters are changed, and before compounding an index. [20](#0-19)   

If a cap is reached, accrual should saturate to a safe index or enter an explicit recovery mode that still permits repayments, withdrawals, and liquidations, rather than trapping before `last_timestamp` can advance. [5](#0-4)   
Regression coverage should assert that the maximum permitted scaled balance and index never make `scaled_to_original` overflow, including boundary values at 18 decimals. [21](#0-20) 

### Proof of Concept

1. Configure an 18-decimal borrowing market using the steep `xlm_curve` rate model and a separate collateral market, matching the repository’s long-horizon scenario. [22](#0-21)   
2. As one unprivileged account or coordinated position owner, call `supply` for `1_000_000_000 * 10^18` raw units of the borrow asset and supply enough collateral to pass the controller’s health checks. [23](#0-22)   
3. Call `borrow` for 98% of that principal. [24](#0-23)   
4. Advance ledger time and repeatedly call `update_indexes` until `scaled_to_original` panics; the test observes `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. [25](#0-24)   
5. Subsequent `update_indexes`, `withdraw`, and `repay` calls all fail because each path retries the same accrual on the unchanged state. [26](#0-25) [27](#0-26)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
