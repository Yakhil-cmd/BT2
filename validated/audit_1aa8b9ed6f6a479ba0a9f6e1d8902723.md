Confirmed. The complete chain is now fully traced:

1. `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body's PR label names, with only a String type check — no charset/key restriction — and this runs on `opened`/`labeled`/`unlabeled`/`reopened` for any active (non-archived) stack, including `allow_with_label` review stacks. [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack's env with **no key allowlist** — unlike the controller-facing `EnvironmentVariables#permit` used for deploy/rollback/task-triggered env params. [2](#0-1) [3](#0-2) 
3. `StackCommands#env` merges `@stack.env` (which is the `ReviewStack#env` above when `@stack` is a `ReviewStack`) into the env passed to `git`/`git_clone` invocations in `#fetch`/`#fetch_commit`/`#git_clone`. [4](#0-3) [5](#0-4) 
4. `Command#unbundled_env` does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the caller-supplied `@env` is merged **last**, so any attacker-controlled key (including `PERL5LIB`) overrides/injects into the environment passed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [6](#0-5) 

So the equality being tested — "the env reaching `PTY.spawn` for a `git` invocation in `StackCommands#fetch`/`#git_clone` == only Shipit/operator-controlled keys" — is **false**: it also includes any uppercased PR label name set by the PR author, unfiltered, for `allow_with_label` (and `allow_all`) review stacks. This matches the existing unit tests confirming label-derived env leaks into `Command#env`. [7](#0-6) [8](#0-7) 

Whether this actually yields RCE depends on `PERL5LIB` (or similarly dangerous vars like `GIT_SSH_COMMAND`, `LD_PRELOAD`) being honored by a subprocess that: (a) invokes perl (git itself doesn't use `PERL5LIB` unless a perl-based git helper/hook runs), and (b) the attacker can place a malicious perl module at a path they control that gets loaded. Nothing in `Command`/`StackCommands` sanitizes or strips `PERL5LIB`, `PERL5OPT`, `RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, etc. from the merged env before spawning `git`.

### Title
Unsanitized PR label names become process environment variables in git subprocess invocations, enabling env-variable injection (e.g. `PERL5LIB`) - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly as an environment variable key with no allowlist, and this env is merged into the env passed to `git` subprocess invocations in `StackCommands#fetch`/`#fetch_commit`/`#git_clone`, which `Command#start` passes verbatim to `PTY.spawn`. An unprivileged PR author can therefore set arbitrary environment variable names (e.g. `PERL5LIB`, `GIT_SSH_COMMAND`, `LD_PRELOAD`) on the git subprocess merely by naming a label on their own PR, on any repository configured with `allow_with_label` or `allow_all` review stacks.

### Finding Description
The broken binding: the env reaching `PTY.spawn` for `StackCommands#fetch`/`#git_clone` should equal `{operator/Shipit-controlled keys only}`, but in practice it equals `{operator keys} ∪ {UPCASE(label) => "true" for every label on the PR}` with no filtering.

Path: A PR author on their own fork opens/labels a PR → GitHub sends a `pull_request` webhook → `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim (only schema-checked as `String`) onto `stack.pull_request.labels` for any active (non-archived) stack, including one gated by `allow_with_label` [9](#0-8) . When any task/deploy/fetch runs against that `ReviewStack`, `ReviewStack#env` calls `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` and merges the result into the stack env with no key allowlist [2](#0-1) . `StackCommands#env` merges `@stack.env` and is used directly by `fetch`/`fetch_commit`/`git_clone` as the `env:` kwarg to the `git` command [4](#0-3) . `Command#unbundled_env` merges `@env.stringify_keys` last, overriding any prior keys, and passes the result straight to `PTY.spawn` [10](#0-9) .

This differs from the (correctly guarded) user-facing paths: deploy/rollback/task env params submitted through controllers are filtered via `EnvironmentVariables#permit` against an explicit `variable_definitions` allowlist [3](#0-2) [11](#0-10) . No equivalent filtering exists for label-derived env in `ReviewStack#env`.

Root cause: `ReviewStack#env` treats attacker-supplied strings (PR label names) as trusted environment-variable keys without any allowlist or key-format restriction.

### Impact Explanation
An attacker who can only open a PR against a repository with review stacks enabled (`allow_with_label`/`allow_all`) can set arbitrary environment variable names on every `git` subprocess invocation for that review stack (fetch, clone, checkout, and any deploy/task steps that use `StackCommands#env`/`TaskCommands#env`), and on `perform`/`install_dependencies` steps too, since `TaskCommands#env` also merges `@stack.env`. Whether this leads to code execution depends on whether the invoked binaries (`git`, or any interpreter run in deploy/task steps, e.g. perl/ruby/bundler) honor the injected variable and whether the attacker can place a payload at a path they control (e.g. a writable path readable by the deploy host, or a repo-relative path checked out during clone). This is scoped to the attacker's own review stack (their own PR/fork), not other tenants' stacks, since `ReviewStack#env` only reads that stack's own `pull_request.labels`.

### Likelihood Explanation
Requires: repository has review stacks enabled with `provisioning_behavior` of `allow_with_label` or `allow_all` (a Shipit operator/repository maintainer configuration, common for review-app workflows). Attacker cost is minimal — just naming a PR label — and is repeatable on every webhook-triggered env recomputation and every task/deploy run against that review stack.

### Recommendation
In `ReviewStack#env`, allowlist/sanitize label-derived keys (e.g. reject known-dangerous variable names like `PERL5LIB`, `PERL5OPT`, `RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, `PATH`, or better, prefix all label keys with a fixed namespace like `SHIPIT_LABEL_<NAME>` so they can never collide with an interpreter/tool-recognized variable), and/or run `EnvironmentVariables.with(...).permit(...)` against an explicit safe list before merging into `StackCommands`/`Command` env.

### Proof of Concept
```ruby

test "#env from a review stack label cannot inject dangerous interpreter env vars" do

  stack.pull_request.labels = ["perl5lib"]  # becomes PERL5LIB=true after upcase
  task = shipit_tasks(:shipit_restart)

  # Binding under test: env reaching the git/PTY.spawn call must NOT contain
```
