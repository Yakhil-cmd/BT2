### Title
A malicious swap-route contract can poison the caller's signed authorization tree and steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-supplied route bytes and authorizes the caller before routing withdrawn collateral through the configured swap aggregator. [1](#0-0) [2](#0-1)  The controller authorizes only its own input transfer, but route-selected third-party code can request an additional token transfer from the original caller while the caller's `swap_collateral` authorization is active. [3](#0-2)  Simulation records that transfer as a child of the caller's authorization entry, and signing the resulting tree makes the unrelated wallet-token transfer part of the successful transaction. [4](#0-3) 

### Finding Description
A victim calls `swap_collateral(caller=victim, account_id, current, amount, new, swap)` with an attacker-supplied `swap` payload. [5](#0-4)  `process_swap_collateral` authenticates `caller`, validates ownership or delegation, withdraws the requested collateral, and passes the opaque route to `swap_tokens`. [6](#0-5) [7](#0-6) 

The swap payload's asset registry supplies each hop's `pool`, `token_in`, and `token_out`, and the router dispatches that hop to venue-specific code without requiring the pool to be a protocol-listed lending asset. [8](#0-7) [9](#0-8)  An attacker can therefore provide a route whose selected hop contract calls `token.transfer(victim, attacker, amount)` for any unrelated token held by the victim. [10](#0-9) 

The controller's measured-input and measured-output checks validate only the router's movement of `token_in` and receipt of `token_out`; they do not bound additional authorization children recorded under the caller's root entry. [11](#0-10)  A benign-looking swap can still pay fair output, deposit it, and pass finalization while the separately signed child transfer steals wallet funds. [12](#0-11) [13](#0-12) 

### Impact Explanation
This is theft of user funds: the stolen asset need not be listed by the protocol, deposited as collateral, or otherwise involved in the lending position. [14](#0-13)  The repository's test demonstrates an unlisted wallet token decreasing from the victim's full balance to zero and arriving at the attacker after the poisoned authorization tree is signed. [15](#0-14) 

### Likelihood Explanation
Exploitation requires social engineering: the attacker must persuade the victim to submit an attacker-constructed route and sign the authorization tree containing the extra child transfer. [16](#0-15)  The attack does not require privileged access, leaked keys, a router compromise, oracle manipulation, or control of the victim's lending account; an unprivileged attacker can deploy the hop contract and distribute the route. [17](#0-16) [18](#0-17) 

### Recommendation
Do not allow user-provided swap payloads to place unreviewed third-party contracts inside a caller-authenticated invocation. [19](#0-18)  Enforce a governance-managed allowlist of route pool addresses, or otherwise restrict route execution to protocol-approved venue contracts. [8](#0-7)  At the wallet/client boundary, simulate every strategy call, decode the returned authorization tree, and reject any child invocation other than the expected strategy-specific token transfers before requesting a signature. [20](#0-19) 

### Proof of Concept
The test fixture deploys a router that reads a route-selected `hop_pool`, invokes it, and returns fair output:

```rust

token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
```

From `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: [21](#0-20) 

The malicious pool is initialized with the victim, an unrelated wallet token, the attacker recipient, and an amount, then performs `token.transfer(victim, attacker, amount)` when the route invokes it. [22](#0-21) 

```rust
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) =
        env.storage().instance().get(&symbol_short!("PLAN")).unwrap();
    if amount > 0 {
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

The fixture then invokes `try_swap_collateral(victim, account_id, USDC, amount, ETH, poisoned_route)`. [23](#0-22)  In recording mode, the unauthorized-looking wallet transfer is attached beneath the victim's `swap_collateral` authorization, the victim's wallet-token balance becomes zero, and the swap still deposits the expected ETH output. [4](#0-3)  In enforcing mode, an honest tree without that child rejects the transfer, while the simulated poisoned tree containing the child succeeds and completes the theft. [24](#0-23)
