## Title
Premature mutex release in `shrinkCache()` causes concurrent cache corruption during unit commit (UAF-style race) - (File: `storage.js`)

### Summary
The CVE describes a UAF where a resource (SMB session) is torn down/freed while another code path still concurrently accesses it because the exiting resource wasn't excluded from a shared list before the lock protecting it was released. The analogous bug class here is a lock-release-before-work-completes race: `shrinkCache()` in `storage.js` acquires the same `"write"` mutex that `writer.js`'s `saveJoint()` uses to serialize mutation of the in-memory unit caches, but releases that mutex before the asynchronous deletions it queued have actually executed, letting a concurrent unit-commit corrupt/interleave with cache state that is supposed to be exclusively owned while held.

### Finding Description
`shrinkCache()` takes the `"write"` mutex, then fires off `db.query()` calls in a loop and calls `unlock()` immediately after the loop — not after the queries' callbacks (which perform the actual `delete assocKnownUnits[...]`, `delete assocCachedUnits[...]`, `delete assocBestChildren[...]`, `delete assocStableUnits[...]`, `delete assocCachedUnitAuthors[...]`, `delete assocCachedUnitWitnesses[...]`) complete: [1](#0-0) 

Because `db.query` is asynchronous, `unlock()` runs synchronously right after the `for` loop schedules the queries, while their callbacks (which mutate the shared caches) remain pending on the event loop. This hands the `"write"` lock to the next waiter while `shrinkCache`'s deferred cache mutations are still in flight.

The same `"write"` mutex is acquired by `writer.js`'s `saveJoint()` specifically to safely commit a new unit and update these very in-memory structures (`assocCachedUnits`, `assocKnownUnits`, `assocUnstableUnits`, `assocBestChildren`, etc.) under the assumption of exclusive access: [2](#0-1) 

`forgetUnit()`, which is used elsewhere under the same lock discipline, illustrates how sensitive these structures are — it deletes from `assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocUnstableUnits`, `assocStableUnits`, and `assocBestChildren` together and explicitly manipulates parent/best-child links: [3](#0-2) 

Because `shrinkCache()` releases the lock early, a unit being committed via `saveJoint()` can run concurrently with `shrinkCache`'s deferred deletions touching the same maps (`assocCachedUnits`, `assocBestChildren`, `assocUnstableUnits`-adjacent structures used for main-chain/stability determination). The freshly written cache entries for the just-committed unit (or its parents) can be wiped out moments after being populated, or a delete meant for an old, already-forgotten unit can race with a new unit reusing related structures, leaving the caches in an inconsistent state that no longer matches the database. `assocBestChildren` in particular is used by main-chain/stability logic, so corrupting it via this unsynchronized race can propagate into main-chain and stability computations.

### Impact Explanation
Corruption of `assocCachedUnits`, `assocBestChildren`, `assocKnownUnits`, `assocUnstableUnits`-related caches while a concurrent unit commit is in progress can desynchronize a node's in-memory view of the DAG from its database state. Since main-chain/stability determination and double-spend detection rely on these caches being consistent under the `"write"` lock, this can lead to a node computing a different main chain / stability point than peers (node disagreement on validity or stability), which is one of the accepted high-severity outcomes.

### Likelihood Explanation
`shrinkCache()` runs automatically every 5 minutes via `setInterval(shrinkCache, 300*1000)` whenever any of the tracked cache maps exceed `MAX_ITEMS_IN_CACHE`: [4](#0-3) [5](#0-4) 

An unprivileged party can reliably grow these caches simply by posting/broadcasting a stream of valid units to the node (each processed unit populates `assocCachedUnits`, `assocKnownUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocStableUnits`), guaranteeing that the size-exceeding branch of `shrinkCache()` executes periodically while the attacker (or any peer) is also causing units to be committed via `saveJoint()`, creating a recurring race window rather than a one-off timing coincidence.

### Recommendation
Do not call `unlock()` until all queued `db.query()` cache-eviction callbacks have actually completed — use `async.each`/`Promise.all` over the chunked queries and only call `unlock()` in the final completion callback, e.g.:
```js
async.each(chunks, function(chunk, cb){
  db.query(sql, [chunk, top_mci], function(rows){
    rows.forEach(function(row){ /* deletes */ });
    cb();
  });
}, function(){ unlock(); });
```
This preserves the exclusivity guarantee the `"write"` mutex is meant to provide to `writer.js`'s `saveJoint()` and other cache-mutating write-lock holders.

### Proof of Concept
1. Continuously post/relay valid units to a full node so that `assocCachedUnits`/`assocKnownUnits`/etc. exceed `MAX_ITEMS_IN_CACHE`.
2. Once `shrinkCache()`'s 5-minute timer fires, it takes the `"write"` lock, fires several `db.query()` calls, and calls `unlock()` before those queries return.
3. Immediately after `unlock()`, trigger (or let naturally arrive) a new unit commit through `writer.saveJoint()`, which re-acquires the now-free `"write"` lock and begins mutating/reading `assocCachedUnits`/`assocBestChildren`/`assocUnstableUnits` for the new unit and its parents.
4. Shortly after, `shrinkCache()`'s pending `db.query()` callbacks fire and delete entries from the same maps — potentially including entries just written by the concurrent commit or entries the commit is currently reading — leaving the in-memory cache inconsistent with the database and with what other nodes computed for the same DAG region.
