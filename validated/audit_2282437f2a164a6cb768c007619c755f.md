### Title
Signature-verification organization is selected from a different data source than the one dispatched to webhook handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` and `#create` derive the "organization" used for two different purposes from two different data sources for the same request. `verify_signature` picks the signing key by calling `Shipit.github(organization: repository_owner)`, where `repository_owner` reads `params.dig('repository','owner','login')` — i.e., the Rails-parsed `params` hash, which is populated from the framework's own request-parameter pipeline (path + query + body). `create`, however, independently re-parses the body with `JSON.parse(request.raw_post)` and dispatches that payload — unconditionally, since Rails' body/query merge for JSON requests is a shallow, top-level `Hash#merge`, not a deep merge — to the event handlers. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the Dahlia report: a security-relevant decision (`verify_signature`, analogous to `BorrowImpl.internalBorrow`'s solvency check) is computed from stale/different data than the data that the subsequent action actually operates on (`create`'s handler dispatch, analogous to `borrowedShares`/`maxBorrowAssets` being computed pre-accrual).

Concretely:
- `repository_owner` (top-level `repository.owner.login`, or fallback `organization.login`) is read from the controller's `params` method, which Rails builds by combining query-string parameters with the parsed JSON body. Because this merge is a plain `Hash#merge` (not recursive), a query-string key `repository[owner][login]=<org>` will *replace* the entire top-level `repository` sub-hash coming from the JSON body when computing `params`. [3](#0-2) 
- `verify_signature` uses that `repository_owner` value to pick which per-organization GitHub App config (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` against `request.raw_post`. [2](#0-1) 
- `create` separately re-parses `request.raw_post` (the real, unmodified body, unaffected by the query string) and hands that payload directly to `Shipit::Webhooks.for_event(event)` handlers, which act on whatever `repository`/`organization`/`team`/`member` fields are present in that raw body. [1](#0-0) 
- `Shipit::GithubApp#verify_webhook_signature` additionally short-circuits to `true` whenever the selected organization's `webhook_secret` is blank/unset — which is the documented default for organizations that don't configure a secret. [4](#0-3) [5](#0-4) 

Combining these: an attacker can craft a POST to the public, unauthenticated `/webhooks` endpoint with a body targeting a victim organization/repository/team, and append a query string such as `?repository[owner][login]=<org-with-no-webhook-secret>` so that `verify_signature` resolves and validates against an organization whose `webhook_secret` is blank (or one the attacker legitimately controls), causing `verify_webhook_signature` to return `true` (or to be trivially satisfiable), while `create`'s handler dispatch still executes against the victim data embedded in the raw body. This breaks the binding "the organization whose secret authenticated the webhook == the organization/repository whose state the handler mutates," exactly the class of binding break the rules describe ("an organization that authenticated versus the repository that is written").

### Impact Explanation
Handlers dispatched from `create` act with real side effects using only the raw-body payload, with no further tie-back to the organization that was actually authenticated:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for any stack matching the branch/repo found in the raw payload. [6](#0-5) 
- `MembershipHandler`-driven events create/remove `Team`/`Membership` records based on the raw payload's `organization`/`team`/`member` fields, which is the same mechanism `Shipit.github_teams` authorization relies on for `current_user.authorized?` in `Authentication#force_github_authentication`. [7](#0-6) 

Forging a `membership` event this way lets an unprivileged attacker grant an arbitrary GitHub identity membership in a team Shipit trusts for access control, escalating into `Shipit.github_teams` authorization — a listed High-severity impact. Forging `push`/`status`/`check_suite` events against a victim's stack can also manipulate the commit/CI state that downstream deploy gating relies on (`Commit#deployable?`), pushing toward an unauthorized deploy/rollback path — a listed Critical-severity impact — since none of this requires an `ApiClient` token, a Shipit session, or repository write access; it only requires knowledge of, or ability to obtain, a valid HMAC for any one configured (or secret-less) organization.

### Likelihood Explanation
The `/webhooks` endpoint is intentionally public/unauthenticated (it skips `verify_authenticity_token` and has no session requirement) [8](#0-7) , so the only guard is `verify_signature`. Multi-organization Shipit deployments are an explicitly documented, supported configuration [9](#0-8) , and leaving `webhook_secret` blank for an organization is shown as the literal default in the shipped example config [10](#0-9) . An attacker only needs the request to include a manipulated query string alongside a crafted JSON body — no credentials, no TLS interception, no prior access to the target Shipit instance are required.

### Recommendation
Compute `repository_owner`/the signing organization strictly from the same parsed `request.raw_post` payload that is passed to `create`'s handlers (i.e., call `JSON.parse(request.raw_post)` once, store it, and derive both the signature-verification organization and the handler payload from that single, canonical value), so the value that authorizes the request and the value the request acts upon can never diverge. As a defense in depth, also verify that the `repository`/`organization` referenced by the dispatched payload matches the organization actually authenticated by the signature check before invoking any handler.

### Proof of Concept
1. Shipit is configured (per documented multi-org support) with at least two organizations, e.g. `trusted-org` (has a real `webhook_secret`) and `open-org` (no `webhook_secret` configured, matching the shipped example defaults).
2. Attacker sends:
   ```
   POST /webhooks?repository[owner][login]=open-org HTTP/1.1
   X-Github-Event: push
   X-Hub-Signature: sha1=anything
   Content-Type: application/json

   {"ref":"refs/heads/master","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"trusted-org"},"full_name":"trusted-org/victim-repo"}}
   ```
3. `verify_signature` computes `repository_owner` from Rails' merged `params`, which (top-level shallow merge of query string over body) resolves to `open-org`. `Shipit.github(organization: 'open-org')` returns a `GithubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus signature.
4. `create` then does `JSON.parse(request.raw_post)`, obtaining the body which references `trusted-org/victim-repo`, and dispatches it to `PushHandler`, which calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack — without ever validating a signature scoped to `trusted-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
