### Title
Unauthenticated `sender` in `StackStxOp` allows an attacker to lock a victim's STX and redirect all PoX rewards to an attacker-controlled address - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::parse_from_tx` derives the `sender` field entirely from the *previous* `PreStxOp`'s first Bitcoin output address, which is never cryptographically bound to any private key — it is simply an arbitrary address chosen by whoever crafts the Bitcoin `OP_RETURN` transaction. This `sender` is later used unmodified as `tx-sender` when the node calls `stack-stx` on the PoX contract, meaning anyone can force-lock a victim's STX balance while independently choosing their own `reward_addr` to receive all PoX payouts.

### Finding Description
The broken equality: **reward-set weight assigned to `reward_addr` == STX actually locked and voluntarily committed by the party who receives payouts for that address.** This is violated because the party whose STX gets locked (`sender`) and the party who is credited the PoX reward weight (`reward_addr`) can be set completely independently by the same attacker, with no signature from `sender` ever required.

Trace:
1. `PreStxOp::parse_from_tx` takes `outputs.get(0)` — an arbitrary Bitcoin output address in a transaction the attacker fully controls (funded by the attacker's own BTC) — and stores it as `PreStxOp.output` with **no check that the attacker controls the corresponding private key**: [1](#0-0) 
2. `Burnchain` op parsing takes `pre_stack_stx.output` and passes it directly as `sender` into `StackStxOp::from_tx`: [2](#0-1) 
3. `StackStxOp::parse_from_tx` sets `reward_addr` from the *first output of the StackStx transaction itself* — fully independent of `sender`/`PreStxOp` — and stores `sender.clone()` verbatim: [3](#0-2) 
4. The only linkage enforced between the `PreStxOp` and `StackStxOp` is that the `StackStxOp`'s Bitcoin input spends **vout=1** (the second output) of the `PreStxOp` transaction — a UTXO the attacker created and controls themselves. This proves nothing about ownership of `output` (vout=0), which became `sender`: [4](#0-3) 
5. `StacksChainState::process_stacking_ops` then executes `stack-stx` using `sender` directly as `tx-sender`: [5](#0-4) 
6. Inside `stack-stx`, the only ownership check is `(>= (stx-get-balance tx-sender) amount-ustx)` — i.e., whatever address `sender` maps to, as long as it has enough unlocked STX, will have it locked, with `add-pox-addr-to-reward-cycles` crediting `pox-addr` (attacker's freely chosen `reward_addr`) with that STX's reward weight: [6](#0-5) 

Exploit flow: the attacker crafts a `PreStxOp` Bitcoin transaction (funded from their own UTXOs) whose first output (`vout=0`) encodes the **victim's** Stacks/Bitcoin address, and whose second output (`vout=1`) pays back to the attacker. The attacker then spends `vout=1` in a `StackStxOp` transaction, setting `reward_addr` = attacker's own PoX/BTC address and `stacked_ustx` = the victim's on-chain unlocked balance. No signature, transaction, or consent from the victim is ever required, since burnchain-op processing authenticates by Bitcoin UTXO ownership of `vout=1` only, not by the `sender` field derived from `vout=0`.

No existing guard (`check()` in `stack_stx.rs`, or `stack-stx`'s asserts) validates that `sender` corresponds to a key the transaction author controls; the only balance-related check is against `tx-sender`'s STX balance, which is the spoofed victim address.

### Impact Explanation
The victim's unlocked STX gets locked for up to `num_cycles` (max `POX_MAX_NUM_CYCLES`) without consent, and 100% of the sBTC/BTC PoX reward weight for that locked STX is credited to the attacker's freely chosen `reward_addr`. This is Critical: theft of PoX/sBTC rewards backed by a victim's unwilling STX lock, and a form of unbacked reward-weight assignment (the attacker's `reward_addr` gains reward-set weight while contributing zero of their own capital). The attack is repeatable against any address with a sufficient unlocked STX balance and costs the attacker only Bitcoin transaction fees for two chained burnchain operations.

### Likelihood Explanation
Preconditions are trivial: the attacker needs their own BTC to fund a `PreStxOp` + `StackStxOp` pair (no special phase/membership state required beyond being outside PoX sunset and within `num_cycles` bounds), and knowledge of a victim address holding unlocked STX (public on-chain information). No privileged role, signature, or victim interaction is required, and the attack can be repeated against any/every eligible STX holder each time their STX is unlocked.

### Recommendation
Bind `sender` cryptographically to the party authorizing the stack: require that the `StackStxOp`/`TransferStxOp`/`DelegateStxOp` `sender` address correspond to the same key(s) that signed the `PreStxOp`'s inputs (e.g., verify `PreStxOp.output` is derived from/matches an input signer's public key hash), rather than accepting an arbitrary, unauthenticated output address as proof of identity.

### Proof of Concept
Rust integration test (e.g. extending `stackslib/src/burnchains/tests/db.rs` patterns and `stacks-node/src/tests/neon_integrations.rs` burn-op helpers):
1. Fund `victim_addr` with `N` STX via `initial_balances`.
2. As attacker, craft `PreStxOp { output: victim_addr, .. }` funded entirely from attacker's own BTC UTXO, submit it.
3. As attacker, craft `StackStxOp` spending `vout=1` of the prior tx, with `reward_addr: attacker_pox_addr`, `stacked_ustx: N`, valid `signer_key`.
4. Mine through processing; assert (a) `victim_addr`'s STX balance shows `N` locked (`STXBalance` locked field for victim increased) despite victim never signing any transaction, and (b) the PoX reward set / `add-pox-addr-to-reward-cycles` entry for `attacker_pox_addr` shows `N` ustx of weight.
5. Assert BTC/sBTC payouts for the cycle are directed to `attacker_pox_addr`, funded by `victim_addr`'s locked STX — violating reward conservation (locked-STX owner ≠ reward recipient).
