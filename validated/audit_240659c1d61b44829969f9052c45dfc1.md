This is confirmed. `Handler` provides a `stacks` helper that scopes to the repository named in the webhook payload via `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and both `PushHandler#process` and `CheckSuiteHandler#process` correctly use this `stacks` scope to restrict lookups to the webhook's own repository [2](#0-1) [3](#0-2) . `StatusHandler#process`, however, ignores this scope entirely and queries `Commit.where(sha: params.sha)` globally across the whole `commits` table, with no join or filter on `repository_name`/`stack` [4](#0-3) .

### Title
Cross-repository `Status` webhook enqueues continuous-delivery for an uninvolved stack via global sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches incoming GitHub `status` webhooks to `Commit` rows using a repository-agnostic `Commit.where(sha: params.sha)` query, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which correctly scope lookups to the webhook's own repository via the `stacks` helper. Since git commit shas are content-derived and identical across any fork/copy of a repository's history, a webhook delivered for one repository can create a `Status` on, and trigger `schedule_continuous_delivery` for, a `Commit`/`Stack` belonging to a completely unrelated repository that happens to share that sha.

### Finding Description
The broken binding: `webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` a `status` event is applied to. This holds for `PushHandler#process`, which restricts to `stacks.not_archived.where(branch:)` where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` [2](#0-1) , and for `CheckSuiteHandler#process`, which restricts to `stacks.where(branch:)` before touching `stack.commits` [3](#0-2) . It does **not** hold for `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This bypasses the `stacks` helper defined in the base `Handler` class entirely, which is exactly the mechanism used by the other handlers to bind the webhook's repository to the correct records [1](#0-0) .

`commit.create_status_from_github!(params)` calls `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) , `Status.replicate_from_github!` creates a `Status` row scoped to whatever `stack_id` that particular `Commit` belongs to [6](#0-5) . The new `Status`'s `after_commit :schedule_continuous_delivery, on: :create` callback fires `commit.schedule_continuous_delivery` [7](#0-6) , which enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` if `deployable? && stack.continuous_deployment? && stack.deployable?` [8](#0-7) . None of these downstream checks verify that `stack`'s repository matches the webhook's originating repository — they only check deploy-readiness state of the victim stack itself.

**Signature verification does not close this gap.** `WebhooksController#verify_signature` only checks that the payload is validly signed for the organization named in the payload (`Shipit.github(organization: repository_owner)` then `verify_webhook_signature`) [9](#0-8) . It authenticates *which organization* sent the webhook, not *which repository's commits may be updated*. Because `Commit.where(sha:)` has no repository/organization filter at all, this authenticates nothing relevant to the actual write.

**Exploit flow:** Attacker controls repo A (any repo where they can create a commit status — e.g., their own repo, or a repo in an org where CI/status-posting is unrestricted to non-maintainers). Victim's stack B tracks repo B and already has a `Commit` row for some sha `S` (e.g. because B is a fork of, or shares history with, A, or the same commit was independently pushed to both — git shas are content-addressed, so this is trivially achievable by attacker forking public repo B into A, giving identical shas for shared history). Attacker creates/updates a commit status on sha `S` in repo A (via GitHub API, using only their own permissions on their own repo). GitHub sends a `status` webhook for repo A, correctly signed for repo A's organization. `WebhooksController#verify_signature` passes (real signature, real org). `StatusHandler#process` runs `Commit.where(sha: S)`, which returns **all** `Commit` rows across **all** stacks/orgs with sha `S`, including victim's commit in stack B. It creates a `Status` for stack B's commit and stack B's `schedule_continuous_delivery` fires, enqueuing `ContinuousDeliveryJob` for stack B — a stack the attacker never authenticated against.

### Impact Explanation
This is a payload for one repository (A) causing a write (`Status` record) and a scheduling side effect (`ContinuousDeliveryJob` enqueue) on another repository's `Stack`/`Commit` (B), which the attacker never authenticated for and does not own. If stack B has `continuous_deployment: true` and the commit is otherwise deployable, this causes an unauthorized deploy to be scheduled for the victim stack purely by manufacturing sha collisions or forks. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The blast radius extends to every stack in the Shipit instance, not just stacks within the attacker's own organization, since `Commit.where(sha:)` has zero organization scoping — only bounded by which orgs already have a configured `GithubApp`/webhook secret for signature verification to pass at all.

### Likelihood Explanation
Preconditions: attacker needs a repo where they can trigger a `status` event with a chosen sha (trivial: post a commit status via GitHub's API on any repo they control, including a fork), and there must exist a `Commit` row elsewhere in the Shipit database with a matching sha (trivial for any repo that is a fork of, or shares history with, a repository already tracked by Shipit — public forking makes this attacker-controllable at will). No Shipit credentials, session, API token, or team membership are required; only the ability to emit a real, validly-signed GitHub webhook from a repo the attacker controls. This is repeatable against arbitrary stacks by simply forking/mirroring any repository already tracked by Shipit and posting statuses to matching shas.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, consistent with `PushHandler`/`CheckSuiteHandler`, e.g. iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or `stacks.joins(:commits).merge(Commit.where(sha: params.sha))`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
test "status webhook for repo A does not schedule continuous delivery for a stack of unrelated repo B" do
  attacker_stack = shipit_stacks(:shipit) # tracks repo A
  victim_stack = shipit_stacks(:cyclimse) # tracks repo B, unrelated
  victim_stack.update!(continuous_deployment: true)

  shared_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared commit")

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'

  body = {
    sha: shared_sha, state: 'success', context: 'ci', target_url: 'http://x',
    created_at: Time.now.iso8601,
    branches: [{ name: attacker_stack.branch }],
    repository: { full_name: attacker_stack.repository.full_name, owner: { login: attacker_stack.repository.owner } }
  }.to_json

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    post :create, body:, as: :json
  end

  refute victim_commit.reload.statuses.exists?(sha_equivalent_query_here: true) # no cross-repo Status created
end
```
This asserts the equality `webhook.repository.full_name == commit.stack.repository.full_name` is preserved: no `ContinuousDeliveryJob` should be enqueued for `victim_stack`, and no `Status` should be created on `victim_commit`, as a result of a webhook that named only `attacker_stack`'s repository.
