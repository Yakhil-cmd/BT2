### Title
Attacker-controlled `organization.login` in webhook payload lets signature verification bind to the wrong org while `repository.full_name` still targets a victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization', 'login')` whenever `params.dig('repository', 'owner', 'login')` is absent, and this value alone selects which `GitHubApp` (and thus which `webhook_secret`) is used to verify the incoming webhook. Because the org used for signature verification is not required to match the org that owns `repository.full_name` used later by the event handlers, an attacker can craft a payload where the verifying org has no secret configured (or is one the attacker controls) while the mutated resource (`repository.full_name`) belongs to a different, victim organization.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`org_used_for_signature_verification (params.dig('organization','login') fallback) == org_that_owns(params.dig('repository','full_name'))`

Trace:
- `WebhooksController#repository_owner` computes: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- `verify_signature` uses that value to select the `GitHubApp` instance: `github_app = Shipit.github(organization: repository_owner)` and then calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) .
- After verification passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers using the *raw* payload, not the verified org [4](#0-3) .
- `ClosedHandler#repository` resolves the mutated repository purely from `params.repository.full_name`, independent of whatever org was used to verify the signature: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) .
- `ClosedHandler#process` then calls `review_stack.archive!` on the resolved victim repository's review stack [6](#0-5) .

Root cause: the org used to select the verifying secret (`repository_owner`, sourced from `organization.login`) is never cross-checked against the org embedded in `repository.full_name`, which is what handlers actually act upon. There is no code anywhere in `WebhooksController`, `ClosedHandler`, or `ReviewStackAdapter` that asserts these two values are the same organization.

Exploit flow: an attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, a body containing `action: "closed"`, `repository.full_name: "victim-org/victim-repo"` (an existing Shipit stack with a review stack), and `organization.login` set to an org string for which `Shipit.github(organization: ...)` resolves to a `GitHubApp` with no `webhook_secret` configured (or one the attacker knows). Because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank, signature verification passes regardless of the actual `X-Hub-Signature` header value (or any header at all). The request proceeds to `ClosedHandler`, which archives the victim's review stack based solely on `repository.full_name`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is handled [7](#0-6) ; `verify_signature` checks a signature but against the wrong/attacker-chosen org's secret; the `ExplicitParameters` schema in `ClosedHandler` only validates types/presence of fields, not organizational consistency [8](#0-7) ; and `GithubOrganizationUnknown` rescue only fires if the org genuinely doesn't exist in `Shipit.github_configs`, not if it exists but lacks a secret.

### Impact Explanation
A payload nominally "verified" against one organization mutates the stack/review-stack of an entirely different (victim) organization's repository — archiving the victim's review stack via `review_stack.archive!`. This is a cross-repository/cross-tenant write triggered by an unauthenticated party, matching the Critical category "a payload for one repository mutating another's stack." The same divergence pattern applies to any other `pull_request` handler that derives its target repository from `params.repository.full_name` (e.g. `OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `UnlabeledHandler`), broadening blast radius across all installed organizations that have any org configured without a `webhook_secret`, or whose secret the attacker can otherwise obtain for a non-victim org.

### Likelihood Explanation
Preconditions: (1) at least one organization configured in `Shipit.github_configs` (or resolvable via `Shipit.github`) that has no `webhook_secret` set, or the attacker's own org's secret which they legitimately know; (2) the victim org/repo has an existing PR/review stack. Both are plausible in real-world multi-tenant Shipit deployments where some orgs are configured loosely (e.g., during setup, testing orgs, or orgs the attacker registers themselves if the host allows organization/app config to be created via non-privileged flow — though that last part is deployment-specific). Attacker cost is a single unauthenticated HTTP POST with a hand-crafted JSON body; no GitHub secrets, sessions, or tokens are required. It is trivially repeatable against any victim repository whose name the attacker knows.

### Recommendation
Bind signature verification to the organization actually owning `params.dig('repository', 'full_name')` (or the primary `repository.owner.login`) rather than trusting a secondary `organization.login` field that isn't cryptographically tied to the request. At minimum, require that when both `repository.owner.login` and `organization.login` are present, they match, and derive `repository_owner` primarily from the repository's owner rather than falling back silently. Additionally, treat `webhook_secret` as mandatory (fail closed instead of `return true unless webhook_secret`) so an org without a configured secret cannot be used to force-pass verification.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "pull_request closed webhook cannot archive victim repo's stack via mismatched organization.login" do
  victim_stack = shipit_stacks(:shipit) # existing stack backed by "victim-org/victim-repo"
  # ensure victim_stack has a review_stack fixture tied to PR #42

  payload = {
    action: "closed",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "https://api.github.com/...", title: "x",
      state: "closed", additions: 1, deletions: 1,
      head: { sha: "abc", ref: "some-branch" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: { full_name: "victim-org/victim-repo" }, # note: no owner.login key
    organization: { login: "attacker-org-with-no-secret" }, # attacker-controlled fallback
    sender: { login: "attacker" }
  }.to_json

  # Assert equality claimed by the binding does NOT hold:
  # verifying_org = "attacker-org-with-no-secret"
  # owning_org(repository.full_name) = "victim-org"
  # verifying_org != owning_org  -> should be rejected, currently is not.

  post shipit.webhooks_path, params: payload, headers: {
    'X-Github-Event' => 'pull_request',
    'Content-Type' => 'application/json'
    # no valid X-Hub-Signature required because attacker-org has no webhook_secret
  }

  assert_response :ok
  assert victim_stack.review_stacks.find_by(...).archived?, "victim stack was archived by a payload verified against a different org"
end
```
This test demonstrates that `repository_owner`'s fallback to `organization.login` breaks the required binding between the verifying organization and the organization whose repository/stack is mutated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
