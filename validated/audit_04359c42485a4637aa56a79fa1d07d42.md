`StatusHandler#process` mutates commit statuses across repositories/organizations by matching only `sha`, bypassing repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` never calls `Handler#stacks` (which derives from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`); it executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no `stack_id` or repository filter whatsoever. Every other handler (`PushHandler`, `CheckSuiteHandler`) correctly scopes its query through `stacks`, but `StatusHandler` is the sole outlier, allowing a correctly-signed webhook for repo/org A to write a `Status` record onto a `Commit` belonging to an unrelated stack B, as long as the two share the same commit `sha`.

### Finding Description
The binding the code is supposed to enforce is: `{commits mutated by StatusHandler#process} == {commits whose stack.repository == authenticated repository_owner}`. Tracing the code shows this equality is broken:

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-38) only authenticates that the payload was signed with the secret configured for `Shipit.github(organization: repository_owner)` — i.e., it proves the payload came from *some* repository belonging to that GitHub organization's App installation. It does not bind the payload to any specific repository or stack.
- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) exists precisely to perform that binding by resolving `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and returning only that repository's stacks. `PushHandler#process` and `CheckSuiteHandler#process` both call `stacks` before doing anything else.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) skips `stacks` entirely and runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped query across the entire `commits` table, spanning every stack/repository/organization tracked by this Shipit installation.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb) calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, which persists a `Status` using the **matched commit's own `stack_id`**, not any stack derived from the webhook payload's repository.

Exploit flow: because git commit SHA-1 is a pure function of tree, parents, message, and timestamps, an attacker who owns/administers any repository under an organization tracked by the same Shipit installation (and thus authenticated by the same per-organization webhook secret) can call GitHub's Status API (`POST /repos/:owner/:attacker-repo/statuses/:sha`) using an arbitrary `sha` string — GitHub's Status API does not require that SHA to exist in the reporting repository. GitHub will then deliver a legitimately signed `status` webhook naming the attacker's repository but carrying a `sha` equal to a commit that actually belongs to a victim stack under the same org (or, in the degenerate/adversarial case, any commit whose SHA the attacker can reproduce, e.g. shared/forked history). `verify_signature` passes because the signature is valid for that organization. `StatusHandler#process` then finds the victim's `Commit` purely by `sha` and writes an attacker-controlled `state`/`description`/`target_url`/`context` status onto it via `create_status_from_github!`.

None of the listed guards prevent this: `verify_signature` authenticates organization-level signing only, not per-repository identity; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`/`state`/etc., not repository scope; there is no `force_github_authentication`, `require_permission!`, or model validation anywhere in this path that ties the resolved `Commit` back to the webhook's `repository.full_name`.

### Impact Explanation
An attacker with legitimate control of one repository under a shared GitHub organization/App installation can write arbitrary `Status` records (state, description, target_url, context) onto commits belonging to a completely different stack/repository under that same installation. Since `Stack#blocked?`/`Commit#deployable?` and `blocking_statuses` (app/models/shipit/commit.rb) drive CI-gating for deploys, this can be used to poison another team's CI status — either to unblock a deploy that should be blocked (forging a `success` status) or to block a legitimate deploy (forging a `failure`/`error` status) — for a repository the attacker never authenticated against. This is a cross-tenant `Commit#statuses` mutation, matching "a payload for one repository mutating another's stack, commit... " under the Critical impact category. It is repeatable against any commit SHA the attacker can compute or observe (all commit SHAs are public via GitHub), for every organization hosting multiple Shipit-tracked repositories.

### Likelihood Explanation
Preconditions: the attacker needs write/admin access to at least one repository under a GitHub organization that Shipit is configured to trust (i.e., they can call the GitHub Status API on their own repo, or are a legitimate maintainer of any repo in a multi-repo org, e.g. via CI integration credentials for that repo). No Shipit secrets, sessions, or `Shipit.github_teams` membership are required — the authentication boundary that's actually crossed is per-organization webhook signing, not per-repository authorization. Any organization onboarding more than one Shipit stack is affected. Cost is low: create/compute a target SHA and issue one GitHub Status API call; fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process`, scope the lookup to the authenticated repository's stacks, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
using the existing `Handler#stacks` helper so the mutation set is bound to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, matching the pattern already used by `PushHandler` and `CheckSuiteHandler`.
