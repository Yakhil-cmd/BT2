### Title
Balance-based share pricing in AMM-style AA lets a first depositor manipulate `mm_asset_outstanding` and steal from later depositors - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The `SafEth` bug (rounding/inflation of a mint-price computed from the *actual on-chain balance* of the contract rather than from internally tracked accounting) has a direct analog in ocore's reference "Uniswap-like market maker" autonomous agent (AA). This AA computes the amount of its own LP-style asset (`mm_asset`) to mint on deposit using `balance[base]` / `balance[$asset]` (the AA address's real ledger balances) instead of a value that is fully reconciled against `var['mm_asset_outstanding']`, exactly the anti-pattern flagged in the external report.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript` [1](#0-0) , the "invest in MM" case computes:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
...
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
``` [2](#0-1) 

This mirrors the SafEth pattern precisely:
- `var['mm_asset_outstanding']` plays the role of `totalSupply`.
- `balance[base]` / `balance[$asset]` (real balances read via `readBalance`/`balance[...]` evaluation, see `formula/evaluation.js` `readBalance`) plays the role of `underlyingValue`, i.e. the raw balance of the AA's address rather than a value strictly bounded by shares issued. [3](#0-2) 
- The `divest MM shares` case pays out a proportional share of `balance[$asset]` and `balance[base]` and decrements `var['mm_asset_outstanding']` by the redeemed amount [4](#0-3) , but rounding in `round($investor_share * balance[...])` leaves residual dust in the AA's real balance that is not reflected by any decrease in `mm_asset_outstanding`.

An attacker who is first (or an early) investor can:
1. Deposit base+paired-asset, receiving `mm_asset_outstanding == balance[base]` from the "initial deposit" branch.
2. Immediately divest all but 1 unit of `mm_asset`. Because payouts are `round(share * balance[...])`, small residual dust of both base and the paired asset is left behind in the AA while `mm_asset_outstanding` drops to 1.
3. Any subsequent, legitimate depositor's `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance` is then multiplied by the now-minuscule `mm_asset_outstanding` and rounds down toward zero, so the depositor receives negligible or zero `mm_asset` for a real deposit of base+asset, while the attacker's single remaining `mm_asset` unit now represents a disproportionate share of the (now larger) pool once further deposits/trading raise `balance[base]`/`balance[$asset]`.

This is the same root cause as SafEth: pricing new issuance off directly-read balances that can be desynchronized from the tracked supply variable through withdrawal rounding, rather than deriving price strictly from `var['mm_asset_outstanding']` and internally-tracked reserve variables.

### Impact Explanation
Because `mm_asset` is a real, transferable asset defined by the AA (`app: 'asset'`) [5](#0-4) , this is a genuine supply/share-accounting bug reachable by any unprivileged AA trigger sender: a later depositor's contributed base/paired-asset value is captured almost entirely by the attacker's disproportionately large remaining share of `mm_asset_outstanding`, i.e. concrete fund loss for the later depositor and an implicit supply-inflation-equivalent mispricing of the share asset. This matches the accepted impact class "AA fund loss."

### Likelihood Explanation
Any user can author or interact with an AA of this exact, documented shape (it is ocore's own reference sample for building Uniswap-like AAs, so it is a realistic template that node operators/users will reuse). The steps (deposit, divest almost all shares, wait for or trigger the next deposit) require only unprivileged trigger units and no special access, matching the reachable-actor profile ("unprivileged... AA trigger sender").

### Recommendation
In AA templates that mint/burn a share asset against pooled reserves, never derive issuance price from raw `balance[...]` reads. Instead:
- Maintain internally tracked reserve state variables (e.g., `var['reserve_base']`, `var['reserve_asset']`) that are updated exactly by the amounts credited/debited in each case, and compute `$investor_share_of_prev_balance` and swap formulas from those tracked reserves instead of `balance[base]`/`balance[$asset]`.
- On divest, round in favor of the pool (round down payouts, or track and periodically sweep dust back into `mm_asset_outstanding`-consistent accounting) so no unaccounted-for balance can accumulate.
- Add a floor/minimum-liquidity check so `mm_asset_outstanding` can never be driven to a value low enough that legitimate deposits round to zero shares relative to `balance[...]`.

### Proof of Concept
Using ocore's own AA test harness (`aa_composer.test.js` style) against the `uniswap_like_market_maker.oscript` definition:
1. Deploy the AA and, via `trigger.data.define`, create `mm_asset`.
2. Attacker sends a trigger with `base` and paired `$asset` outputs to hit the "invest in MM" case while `asset_balance==0 OR bytes_balance==0`; confirms `mm_asset_outstanding` set to `balance[base]` and attacker credited that full amount of `mm_asset`.
3. Attacker sends a second trigger with `trigger.output[[asset=mm_asset]] = mm_asset_outstanding - 1` to hit "divest MM shares"; confirms `mm_asset_outstanding` now `1` while residual `balance[base]`/`balance[$asset]` dust remains in the AA due to `round()` truncation.
4. A second (victim) user sends a normal-sized "invest in MM" trigger; confirms `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` evaluates to `0` (or a negligible number versus the value contributed), demonstrating the value transfer/theft.

This exploit path can only be exercised and confirmed by running the AA formula evaluator (`aa_composer.js`/`formula/evaluation.js`) against a live/test ocore node; the index does not include a runnable numeric trace, so exact numeric rounding thresholds should be validated with an actual test run.
