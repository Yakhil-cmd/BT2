Based on my research, I found a plausible analog to the reported "fee update delay bypass" pattern in the Agave vote program's block-revenue commission handling, but I was unable to fully verify the internals of `calculate_block_reward` due to exhausting available tool calls, so I present this with that caveat.

### Title
Block-Revenue Commission Updates Bypass the One-Epoch Delay Protection Applied to Inflation-Reward Commission - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, `programs/vote/src/vote_state/mod.rs`)

### Summary
The reported bug class describes fees/parameters that are supposed to require a full epoch of delay before taking effect, but can instead be changed and applied almost immediately, letting an account owner "rug" counterparties who had no time to react. In Agave's vote program, `SIMD-0249`/`delay_commission_updates` was introduced specifically to prevent "last-minute commission rugs" for inflation-reward commission [1](#0-0) . However, the analogous `block_revenue_commission_bps` field (SIMD-0291/SIMD-0123) can be set with `update_commission_bps` at any time with no epoch-position restriction [2](#0-1) , and reward-calculation code for block rewards resolves the commission from the current/distribution-epoch vote-account snapshot rather than the delayed snapshot used for inflation rewards.

### Finding Description
For inflation rewards, `calculate_stake_rewards_and_commissions` -> `redeem_delegation_rewards` explicitly looks back through `snapshot_epoch_vote_accounts` (two epochs prior) and falls back to `rewarded_epoch_vote_accounts` (one epoch prior) to compute `commission_bps` when `delay_commission_updates` is enabled, specifically to "delay the effect of commission updates by at least one full epoch" [3](#0-2) . This lookback is fed by `get_cached_vote_accounts`, which documents that the earlier snapshot "is saved a full epoch before being used to prevent last minute commission rugs" [4](#0-3) .

In contrast, the block-reward computation is invoked with `cached_vote_accounts.distribution_epoch_vote_accounts` — the vote-account state at the current/distribution epoch — with no equivalent snapshot lookback: [5](#0-4) . Meanwhile `update_commission_bps` for `CommissionKind::BlockRevenue` explicitly documents "No commission update rule, per SIMD-0249 and SIMD-0291" and applies the new value immediately, with no epoch-half or epoch-delay gate at all [6](#0-5) . A test comment confirms this is treated as intentional for the instruction itself: "Unlike test_update_commission, SIMD-0291 has no timing restrictions (per SIMD-0249). Updates are always allowed regardless of epoch position" [7](#0-6) .

This mirrors the structure of the reported bug: a parameter that is meant to be protected by a one-epoch delay (per the design intent stated in code comments referencing SIMD-0249/"prevent last-minute commission rugs") is not actually delayed for one of its two variants (`BlockRevenue`), only for the other (`InflationRewards`).

### Impact Explanation
If the delay/snapshot protection is not applied to block-revenue commission at distribution time, a vote-account authorized withdrawer could raise `block_revenue_commission_bps` immediately before/at the point block rewards are calculated for the (upcoming) distribution, diverting a larger share of block-reward lamports away from delegated stake accounts to the vote account commission, i.e., misattributed/diverted rewards for stakers with no chance to unstake in response — the same class of harm the original report calls out (users lacking time to react to a fee change).

### Likelihood Explanation
I could not confirm from the available tool budget whether `calculate_block_reward`'s internal implementation independently re-applies a delay (e.g., it might already only use vote-account state that predates the rewarded epoch by design of `distribution_epoch_vote_accounts`'s construction, which is computed once at epoch-boundary transition in `compute_new_epoch_caches_and_rewards` before any commission change made *during* the new epoch could affect it) [8](#0-7) . This significantly affects likelihood: if `distribution_epoch_vote_accounts` is fixed at the start of the rewarded epoch (before any in-epoch commission changes are visible), then the asymmetry may have no practical exploitability, since a manager can only affect the value for a distribution that hasn't started accruing. I was unable to fully trace this call chain (`calculate_block_reward`'s body) before running out of iterations.

### Recommendation
Confirm whether `distribution_epoch_vote_accounts` used for block-reward commission is captured strictly before the commission value can be mutated for the rewarded epoch; if not, apply the same `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` lookback used for `inflation_rewards_commission_bps` to `block_revenue_commission_bps` when computing block rewards, ensuring a symmetric one-epoch delay for both commission kinds as the `delay_commission_updates` feature intends.

### Proof of Concept
Could not be constructed with confidence — this requires tracing `calculate_block_reward`'s internal use of vote-account state and the exact timing of when `distribution_epoch_vote_accounts` is snapshotted relative to in-epoch `UpdateCommissionBps { kind: BlockRevenue }` instructions, which I was unable to complete within the available tool-call budget. A Devin session with repository access would be needed to read the full body of `calculate_block_reward` and write/run a bank-rewards integration test analogous to `test_calculate_stake_vote_rewards_new_vote_account` to empirically verify whether a same-epoch (or last-slot) `UpdateCommissionBps` for `BlockRevenue` affects the reward distributed in the very next partitioned-rewards cycle.

    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
