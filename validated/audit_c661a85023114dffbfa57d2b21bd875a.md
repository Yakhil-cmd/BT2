### Title
Webhook signature validated against `repository.owner.login` but stack lookup keyed on unrelated `repository.full_name` allows cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  The signature itself is an HMAC over the *entire* raw request body, so the check only proves "whoever holds the webhook secret for the organization named in `repository.owner.login` crafted this exact body" — it does not independently constrain which repository the payload's handlers will act on. Every event handler instead resolves the target `Repository`/`Stack` purely from `repository.full_name` in the same payload, via `Handler#repository_name`/`#stacks` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  `PushHandler` uses this to enqueue a sync against whichever stacks match `full_name`+`branch`. [5](#0-4) 

### Finding Description
The equality that should hold is: **organization whose secret authenticated the request == organization owning the repository whose stacks get mutated**. Nothing in the controller enforces `repository.owner.login == repository.full_name.split('/').first`. Because the signature is computed over the raw JSON body as a whole, an attacker who controls (or has legitimately obtained, e.g. by operating their own onboarded organization in this multi-tenant Shipit instance) the `webhook_secret` configured for organization `attacker-org` can freely construct the JSON body themselves before signing it. They can set `repository.owner.login` (or `organization.login`) to `attacker-org` — which is what `repository_owner` reads and what selects the `GitHubApp` used to `verify_webhook_signature` — while setting `repository.full_name` to `"victim-org/victim-repo"`, an entirely different, unrelated organization's repository configured in the same Shipit deployment. [6](#0-5)  `Shipit.github(organization: repository_owner)` only looks up the secret keyed by `attacker-org`; it never checks that `full_name`'s owner segment matches. [7](#0-6)  Since the signature check passes with the `attacker-org` secret, the request reaches `create`, which re-parses the same JSON and dispatches to handlers based on `X-Github-Event`. [8](#0-7)  `PushHandler#process` then does `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and enqueues a sync/deploy job against the resolved stack — that repository lookup and the resulting job execution belong to `victim-org`, not the organization whose secret validated the request. [5](#0-4) [4](#0-3) 

This is the direct analog of the reported bug class: the report's `loss`/`valueAfter` check validated one quantity but let precision loss decouple it from the intended, stricter guarantee; here the signature validates one identity (`repository.owner.login`) but the code that actually mutates state (repository/stack resolution and job dispatch) trusts a different, unauthenticated field (`repository.full_name`) from the same payload.

### Impact Explanation
This breaks tenant isolation between organizations sharing one Shipit deployment (a documented supported configuration via per-organization `github:` secrets, see `config/secrets.development.shopify.yml`). [9](#0-8)  An attacker who legitimately controls the webhook secret for their own onboarded organization can forge push/status/check_suite/pull_request events that are dispatched against a completely different organization's repositories/stacks, triggering unintended `GithubSyncJob` runs, commit status writes, or stack archival/unarchival for a `victim-org` repository they have no access to — i.e., cross-repository writes and potentially unauthorized deploy/rollback triggers, matching the Critical impact bar.

### Likelihood Explanation
Requires the attacker to already possess a valid `webhook_secret` for *some* organization configured in the Shipit instance (e.g., as the owner/admin of their own onboarded org in a shared/multi-tenant deployment) — this is not "privileged" relative to the *victim* organization, only to their own. Given that, forging the raw POST body is trivial (no GitHub interaction needed, since the endpoint is a public HTTP controller that only checks HMAC over the body). No other credential, session, or repository write access to the victim is needed.

### Recommendation
In `WebhooksController#verify_signature`, and/or in `Shipit::Webhooks::Handlers::Handler`, require that the organization used to select/verify the signing secret matches the owner segment of `repository.full_name` (and `organization.login` where present) before dispatching to handlers. Reject the request (422) if they diverge instead of only checking `repository.owner.login`.

### Proof of Concept
1. Attacker operates `attacker-org`, which is configured in Shipit with its own `webhook_secret` (`S_attacker`), known to the attacker as the org's GitHub App owner.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>` and POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner => "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully. [1](#0-0) 
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues a sync job for `victim-org`'s stack with the attacker-chosen `after` SHA — despite the request never being authenticated for `victim-org`. [5](#0-4)
