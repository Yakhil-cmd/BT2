### Title
Explicit `X-Frame-Options: ALLOWALL` on `MergeStatusController#show` enables clickjacking of merge-queue enqueue/dequeue actions - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController#show` unconditionally overrides the frame-ancestors protection by setting `response.headers['X-Frame-Options'] = 'ALLOWALL'`, allowing any third-party site to embed the merge-status widget in an iframe for an arbitrary `stack_id`. Because `enqueue`/`dequeue` are protected only by session authentication (not by any additional interaction proof), an attacker can overlay deceptive UI on top of the iframed widget and induce a logged-in operator's browser to submit the genuine, same-origin `enqueue`/`dequeue` request under the operator's real session.

### Finding Description
The broken binding is: **the visual click the operator believes they are performing on the attacker's page == the actual DOM click landing on Shipit's own `enqueue_merge_request_path`/`dequeue_merge_request_path` control, executed with the operator's live session**. Normally, frame-busting (`X-Frame-Options: SAMEORIGIN` or deny) prevents this equality from holding for a third-party origin, but `show` explicitly nullifies that protection: [1](#0-0) 

`skip_authentication only: %i[check show]` means only `show`/`check` bypass the authentication redirect, while `enqueue` and `dequeue` still run through `Shipit::Authentication`'s `current_user`, which is populated purely from `session[:user_id]` — the browser cookie: [2](#0-1) [3](#0-2) 

The `stack` lookup allows an attacker to target any repository/stack by simply choosing the `stack_id` param when constructing the iframe URL, since `Stack.from_param!` performs no origin/referrer binding check for `show`: [4](#0-3) 

Attack flow: attacker hosts `evil.example` with `<iframe src="https://shipit-host/merge_status?stack_id=victim/app/production">` styled to sit under a decoy "I'm not a robot" or similar button, over the real `enqueue`/`dequeue` control rendered in the frame. Because CSRF tokens are generated by Shipit itself for the embedded page (this is UI redressing, not token forgery), Rails' `protect_from_forgery with: :exception` on `ShipitController` does not block the request — the form/link is legitimate same-origin content, just visually hijacked. When the deceived operator clicks, the browser submits the real request with the real session cookie and real CSRF token, and `MergeRequest.request_merge!(stack, params[:number], current_user)` executes as that operator.

### Impact Explanation
A successful click causes `MergeRequest.request_merge!` (enqueue) or `merge_request.cancel!` (dequeue) to run under the deceived operator's authenticated identity, against a stack the attacker chooses via `stack_id`. This is an unauthorized mutation of another repository/stack's merge queue performed by a session that never intended the action — matching the "unauthorized deploy, rollback or merge" Critical category, though bounded to merge-queue state rather than the deploy/rollback process itself. It is repeatable against any stack the operator has permission to act on, and the attacker can chain multiple iframed controls (enqueue then a second click) to escalate a chosen PR further up the merge queue.

### Likelihood Explanation
Preconditions: the victim must have an active Shipit session and be lured to a page controlled by the attacker while logged in — a plausible scenario for an internal tool used by engineers who click links from Slack/PRs. No GitHub or Shipit secrets are required; the attacker only needs to know or guess a `stack_id` (repo owner/name/environment), which is often not secret. Cost is low: a static HTML page with an iframe and CSS overlay.

### Recommendation
Remove the `X-Frame-Options: ALLOWALL` override in `MergeStatusController#show`, or restrict it to `ALLOW-FROM`/CSP `frame-ancestors` scoped to the exact GitHub PR origin the referrer parser validates, and require an explicit user-interaction proof (e.g., double-confirmation or a non-idempotent token) on `enqueue`/`dequeue` in addition to session authentication.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb (extension)
test "#show sets X-Frame-Options to ALLOWALL enabling framing" do
  stack = shipit_stacks(:shipit)
  session[:user_id] = shipit_users(:walrus).id
  get :show, params: { stack_id: stack.to_param }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
end

test "#enqueue relies solely on session cookie, no interaction proof beyond auth" do
  stack = shipit_stacks(:shipit)
  session[:user_id] = shipit_users(:walrus).id
  post :enqueue, params: { stack_id: stack.to_param, number: 42 }
  assert_response :success # succeeds purely from session, demonstrating clickjack-able binding
end
```

      end
