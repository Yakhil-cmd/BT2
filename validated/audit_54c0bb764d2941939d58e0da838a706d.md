### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while every handler acts on `repository.full_name` — cross-organization signature confusion in a shared multi-tenant Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken from the JSON body, but every webhook `Handler` resolves the actual `Repository`/`Stack` to write to using the sibling field `repository.full_name` from the very same body. Shipit explicitly supports hosting multiple GitHub organizations, each with its own `webhook_secret`, on one shared `/webhooks` endpoint. An attacker who legitimately administers one tenant organization's GitHub App (and therefore knows that organization's `webhook_secret`) can craft a signed payload whose `owner.login`/`organization.login` matches their own org (so the correct secret is used and the signature validates) while `repository.full_name` points at a repository belonging to a *different* tenant organization on the same instance, causing the handler to act on the victim's stack.

### Finding Description
The verified field and the acted-upon field are not the same, and nothing enforces that they must match:

- Verification selects the secret from `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

- The GitHub App/secret lookup is per-organization, and multiple organizations (each with their own independently configured `webhook_secret`) can be hosted by a single Shipit instance sharing the same `/webhooks` route: [3](#0-2) [4](#0-3) 

- Yet every handler determines which `Repository`/`Stack` to mutate from `repository.full_name`, a completely different JSON field within the same signed body: [5](#0-4) [6](#0-5) 

Because HMAC signing covers the whole raw JSON body, the signature *does* protect `full_name` from being altered — but only relative to whichever secret the verifier chose to check against. If a Shipit deployment configures per-organization apps (as `docs/setup.md`'s "Using Multiple Github Applications" section and `test/dummy/config/secrets_double_github_app.yml` demonstrate is a supported configuration), the attacker's own tenant secret is a valid credential for authenticating *a payload whose `repository.full_name` names an entirely different tenant's repository*. The controller never checks that the organization used to select the verifying secret is the same organization embedded in `repository.full_name`.

### Impact Explanation
This breaks the intended binding "organization that authenticated == repository that is written." A user who administers their own tenant organization's GitHub App on a shared Shipit instance can forge `push`, `status`, `check_suite`, or `pull_request` webhook events that are accepted as valid and dispatched against a victim organization's stacks/repositories, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on the victim's stacks [6](#0-5) .
- Pull-request handlers can archive/unarchive review stacks or update PR state for a victim's repository using only `repository.full_name` [7](#0-6) .

This is a cross-repository/cross-organization forgery achievable by any attacker who is a legitimate administrator of just one tenant organization on a multi-org Shipit deployment, satisfying the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Requires the operator to run the documented multi-organization configuration (explicitly supported and documented). Within that configuration, exploitation requires no privileged Shipit account, `ApiClient` token, or GitHub App private key belonging to the victim org — only knowledge of the attacker's own tenant's `webhook_secret`, which they legitimately possess as that org's GitHub App administrator. The `repository_owner`/`full_name` mismatch is never validated anywhere in the request path.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature, additionally assert that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (and of `organization.login` for org-level events) before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Operator runs Shipit configured with two tenant orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret`, per `docs/setup.md`'s multi-app section.
2. Attacker administers `OrgOne`'s GitHub App and therefore knows `OrgOne`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgOne`'s known `webhook_secret` over the raw body.
5. `verify_signature` computes `repository_owner => "OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, and the HMAC validates successfully (app/controllers/shipit/webhooks_controller.rb:24-30).
6. `PushHandler` resolves `repository_name` as `"OrgTwo/victim-repo"` (app/models/shipit/webhooks/handlers/handler.rb:36-38) and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgTwo`'s stack — an action the attacker has no authorization for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
