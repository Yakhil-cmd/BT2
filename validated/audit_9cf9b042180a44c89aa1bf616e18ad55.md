### Title
Optional per-organization `webhook_secret` lets an unauthenticated attacker forge GitHub webhooks (including `membership` events) and bypass `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController` selects which GitHub organization's secret to use for HMAC verification from data taken out of the *unverified* request body, and `GitHubApp#verify_webhook_signature` silently accepts any payload when that organization has no `webhook_secret` configured — a state explicitly supported and documented as "optional." This breaks the binding "organization that is cryptographically authenticated == organization whose webhook payload is trusted and acted upon," exactly analogous to the report's `executionHistory`/`fallback` binding break where a value trusted by one path is never actually the value that was verified.

### Finding Description
`WebhooksController#verify_signature` picks the signer based on a field pulled straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

That app object's `verify_webhook_signature` is intentionally permissive when no secret is configured: [3](#0-2) 

This is a documented, supported configuration path — the setup guide explicitly marks `webhook_secret` as "(optional)" per organization, including in the multi-organization configuration block: [4](#0-3) [5](#0-4) 

Consequently, for any configured organization lacking a `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, so **no cryptographic check is ever performed** for events attributed to that organization. Since `repository_owner`/`organization.login` is attacker-supplied in the body, anyone can POST an arbitrary payload naming that organization to `/webhooks` and have it accepted as authentic.

The most severe consequence is via the `membership` webhook, which is unauthenticated-attacker-reachable and directly manipulates the authorization primitive `Shipit.github_teams`: [6](#0-5) 

`find_or_create_team!` upserts a `Team` keyed by attacker-controlled `github_id`/`organization`, and `team.add_member(member)` adds an attacker-controlled `User` (created via `User.find_or_create_by_login!`, which fetches public GitHub profile data for that login) to that team: [7](#0-6) [8](#0-7) 

Application authorization is then decided purely by team membership: [9](#0-8) [10](#0-9) 

**Binding broken (equality form):**
`organization cryptographically authenticated by verify_signature` ⟺ `organization/team whose membership webhook is trusted and written to the DB`.

Before the attack: only GitHub, holding the real `webhook_secret`, can produce webhook deliveries that pass `verify_signature` for a given org.
After the attack (target org configured without `webhook_secret`, e.g. a secondary org in a multi-org Shipit deployment, or the primary org during initial setup before the secret is set): any unauthenticated client can produce a payload that passes `verify_signature` for that org, because the check is unconditionally `true`.

### Impact Explanation
This maps to the High-impact criterion "escalation into `Shipit.github_teams` authorization." A forged `membership` webhook lets an unauthenticated attacker create/join a `Team` record matching a `github_id` in `Shipit.github_teams`, causing `User#authorized?` to return `true` for a GitHub login of the attacker's choosing — i.e., unauthenticated bypass of the application's team-based access control gate that fronts every Shipit UI/API endpoint (`force_github_authentication`). Other events (`push`, `status`, `check_suite`) are similarly forgeable for that org, letting an attacker inject fake commit statuses or trigger sync/check-run jobs without any GitHub credential.

### Likelihood Explanation
Requires only that one configured GitHub organization in the deployment's `github` secrets section omits `webhook_secret` — an explicitly documented, supported, and easy-to-miss configuration (the sample `config/secrets.development.example.yml` even ships with `webhook_secret:` blank by default). No repository write access, API token, or session is needed; the attacker only needs network access to `/webhooks` and knowledge of the target organization's login name (public information). This does not depend on the engine being mounted non-standardly — it is a gap in the engine's own `verify_signature`/`verify_webhook_signature` logic given a documented optional setting.

### Recommendation
- Do not select the verifying `GitHubApp`/secret from unauthenticated payload content prior to verification; instead require every configured organization to have a mandatory `webhook_secret`, or verify against all configured secrets and reject if none match.
- Change `GitHubApp#verify_webhook_signature` to fail closed (return `false`) when no `webhook_secret` is configured, rather than trusting the request unconditionally.
- Consider validating that the resolved organization from the payload matches an org actually installed/known to Shipit before trusting any downstream `Team`/`User` mutation from `MembershipHandler`.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `github:` in `config/secrets.yml`, where `org-a` has a real `webhook_secret` but `org-b` (also installed, e.g. for testing) has `webhook_secret:` left blank, per the documented multi-org format (`docs/setup.md` lines 182-209).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://x"},
  "organization": {"login": "org-b"},
  "member": {"login": "attacker-github-login"}
}
```
without any `X-Hub-Signature` header (or an arbitrary bogus one).
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-b")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature header (`lib/shipit/github_app.rb:76-83`).
4. `MembershipHandler#process` runs, creating/finding `Team(github_id: 999)` and calling `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
5. If `Shipit.github_teams` includes a team with `github_id: 999` (or the attacker iterates ids to find a match), the attacker's GitHub login is now a member of an authorizing team, and logging in via OAuth as that GitHub user passes `User#authorized?`, granting access to the Shipit application without ever having been legitimately invited to that team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
