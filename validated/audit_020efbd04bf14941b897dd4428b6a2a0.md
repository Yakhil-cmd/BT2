Based on my investigation, I found the key mechanism (`socialize-debt-asset` in `market.clar`/`v0-4-market.clar`) that refreshes the `index-cache` after a write-down, but the `liquidate` and `repay` functions cache indexes via `accrue-and-cache` keyed only by `{ timestamp: stacks-block-time, aid }` — a **global, cross-user cache**, not per-borrower state. This matches the report's core bug class ("shared state not reset/refreshed after a state-changing event, causing incorrect accounting for a different party") more than any per-user "bond curve" analog, since Zest has no per-user risk-curve concept comparable to CSModule's bond curve.

### Title
Stale Global Index Cache Lets a Liquidation or Repay in One Transaction Under-Value zToken Collateral for a Second Borrower Liquidated Later in the Same Block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` caches vault liquidity/borrow indexes in a single global map keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . The cache is primed once per block per asset by whichever caller (borrower, repayer, or liquidator) first touches that asset, and every subsequent caller in the same block — including an unrelated liquidator acting against a different borrower — reads the same cached value via `get-cached-indexes`/`accrue-and-cache` instead of re-accruing the vault [2](#0-1) . The only place the cache is explicitly refreshed mid-block is inside `socialize-debt-asset`, immediately after a bad-debt write-down of `lindex` [3](#0-2) ; no equivalent refresh happens after an ordinary `system-repay` inside `liquidate`, so a first liquidation's repay-driven change to vault utilization/index is invisible to a second liquidation of a different borrower's zToken collateral processed later in the same block via `liquidate-multi`.

### Finding Description
`accrue-and-cache` treats the vault's index as valid for the entire block once cached, regardless of state-changing calls (`system-repay`, `socialize-debt`) that occur between the first and later reads within that same block [1](#0-0) . `liquidate` explicitly documents relying on this cache for zToken price resolution ("accrue FIRST - populates cache for zToken price resolution") [4](#0-3) , and `scale-debt-for-liquidation`/the "other-debt-repayable" computation both pull the borrow index straight from `get-cached-indexes` rather than re-accruing [5](#0-4) [6](#0-5) . In `liquidate-multi`, `call-liquidate` is `map`ped over a list of positions in one transaction/block [7](#0-6) ; the first liquidation calls `vault-system-repay`, which mutates the vault's real accrual state, but the market's `index-cache` for that asset is not invalidated afterward (unlike the explicit refresh performed in `socialize-debt-asset`). Any subsequent liquidation in the same batch, or any independent `liquidate`/`repay` transaction by a different user in the same block that touches the same asset, will read the stale pre-repay liquidity/borrow index for zToken price and debt-scaling math, producing collateral/debt valuations that don't reflect the true post-repay vault state.

### Impact Explanation
Because zToken collateral value is derived as `underlying price × liquidity index` and debt is scaled by the borrow index read from this same stale cache, a second borrower's liquidation in the same block can have their zToken collateral mis-valued (over- or under-seized) relative to the true, updated vault state — one unprivileged liquidator's action (repay) alters shared state that silently changes the outcome for another unrelated borrower's liquidation processed moments later, without either party controlling for it. This is a temporary freezing/incorrect-seizure risk for the second borrower's funds (seizing collateral beyond what the true index implies, or the liquidator receiving less/more collateral than the fresh state warrants), falling under the in-scope "temporary freezing of funds" / "seizure exceeding its bound" impact class.

### Likelihood Explanation
Requires two liquidations (or a liquidation and a repay) touching the same asset within the same block/transaction — realistic via `liquidate-multi`, which is explicitly designed to batch multiple borrower liquidations atomically [8](#0-7) . No special privilege is needed; any liquidator triggering the batch, or two independent liquidators/repayers landing in the same block, can trigger it.

### Recommendation
Invalidate or refresh the per-asset entry in `index-cache` immediately after any state-mutating vault call within the same block (`vault-system-repay`, `vault-socialize-debt`, `vault-deposit`, `vault-redeem`), mirroring the refresh already performed in `socialize-debt-asset` [3](#0-2) , so that every subsequent read of `get-cached-indexes`/`accrue-and-cache` reflects the latest vault state rather than the first cached value of the block.

### Proof of Concept
1. Two borrowers, A and B, both hold zUSDC collateral and USDC debt, both eligible for liquidation.
2. A liquidator calls `liquidate-multi` with positions for A and B in one transaction.
3. `call-liquidate(A)` executes first: `accrue-user-debts`/`accrue-user-collateral` populate `index-cache` for USDC at the current `stacks-block-time`, then `vault-system-repay` is invoked, changing the real vault utilization/index state [9](#0-8) ; the cache entry is never refreshed afterward.
4. `call-liquidate(B)` executes next in the same block: `accrue-and-cache` for USDC returns the cache HIT from step 3, computing B's zToken/debt valuations off the pre-repay index instead of the true post-repay index [1](#0-0) .
5. B's collateral seizure / debt-scaling amounts diverge from what a correctly-refreshed accrual would produce, harming either B (over-seizure) or protocol lenders (under-seizure/under-repayment), depending on index drift direction — with neither B nor B's liquidator having caused or controlled this mispricing.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
