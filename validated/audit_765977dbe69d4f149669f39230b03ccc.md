### Title
`CCMenuController#stack` bypasses `ApiClient` stack scoping, letting any read:stack token read every stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` requires only the generic `read:stack` permission and resolves the target `stack` with `Stack.from_param!(params[:stack_id])`, bypassing the per-client stack scoping (`current_api_client.stack_id`) that every other API controller enforces via `BaseController#stacks`/`#stack`. As a result, an `ApiClient` token that is scoped/intended for a single stack (e.g. a CCMenu monitoring token minted for stack A) can be used to read the build/deploy status of any other stack in the installation.

### Finding Description
The equality binding that should hold is: **the stack an `ApiClient` token authorizes == the stack the endpoint actually touches**.

`Shipit::Api::BaseController` implements this correctly everywhere else: [1](#0-0) 
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
If an `ApiClient` has a `stack_id`, every lookup is confined to that single stack.

`CCMenuController` overrides `stack` and drops this scoping entirely, going straight to the unscoped `Stack` relation: [2](#0-1) 
```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```
The only authorization check performed is `require_permission :read, :stack`, which just checks that the string `read:stack` is present in `permissions` — it never checks that `params[:stack_id]` matches the `ApiClient#stack_id` the token was minted for: [3](#0-2) 
```
belongs_to :stack, optional: true
...
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
```

This is directly exploitable through the built-in CCMenu URL feature, which mints such read-only tokens for end users to embed in third-party CI dashboard/CCTray tools: [4](#0-3) 
```
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end

private

def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
Note this token is also created without any `stack:` binding at all (so even the intended `stack_id` scoping from `ApiClient#belongs_to :stack` is not applied here) — but even if a caller manually scopes an `ApiClient` to one stack (`stack:` set, `deploy:stack`/`read:stack` permission), `CCMenuController` will still happily serve any other stack, because it never consults `current_api_client.stack_id`.

### Impact Explanation
Any holder of a `read:stack`-scoped `ApiClient` token — regardless of whether that token/`ApiClient` record was created bound to one specific stack — can query `GET /api/*/stacks/:stack_id/ccmenu` for **any** stack in the installation and obtain that stack's latest deploy/rollback status (id, timestamps, running/success/failure state). This is an unauthenticated (relative to the intended per-stack scope) read of stack state across the whole instance, matching the in-scope High-severity impact category "unauthenticated read of stack state, task streams or deploy output" — the token that was supposed to authorize reads for stack A ends up touching every other stack.

### Likelihood Explanation
High. CCMenu tokens are explicitly designed by the product to be shared with external CI/status-monitoring tools (embedded in a query string), which is a realistic leak vector (browser history, proxy logs, screen shares, third-party tool configuration exports). Any party who obtains one such token can trivially enumerate other `stack_id` params (stack slugs are typically `owner/repo/environment`, often guessable/enumerable via the public stacks index) and pull cross-stack status data with a single unauthenticated-relative-to-scope HTTP GET — no additional exploitation complexity is required.

### Recommendation
In `Shipit::Api::CCMenuController`, remove the `stack` override and use the scoped lookup from `BaseController` (`stacks.from_param!(params[:stack_id])`) so the endpoint respects `current_api_client.stack_id`. Additionally, `CCMenuUrlController#client` should create the `ApiClient` with `stack: stack` (not stack-less) so CCMenu tokens are hard-bound to the stack they were generated for.

### Proof of Concept
1. As an authenticated Shipit user, request a CCMenu URL for stack A: `GET /stacks/owner/repoA/production` (via `CCMenuUrlController#fetch`) → receive `ccmenu_url` containing `token=<T>`, where `T` authenticates an `ApiClient` with `permissions: ['read:stack']` (unscoped to any stack).
2. Using the same token `T`, call `GET /api/stacks/owner/repoB/staging/ccmenu?token=T` for an unrelated stack B that the token was never intended to access.
3. Observe the request succeeds (HTTP 200, XML build status for stack B returned) because `CCMenuController#stack` resolves `params[:stack_id]` via the unscoped `Stack.from_param!` instead of the api-client-scoped `stacks.from_param!` used elsewhere in `Api::BaseController`, and `check_permissions!` only checks the generic `read:stack` string, not the specific stack.

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

      required_permission = "#{operation}:#{scope}"

      true
