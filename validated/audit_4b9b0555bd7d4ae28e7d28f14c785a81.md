### Title
`StatusHandler#process` mutates commits across repositories/stacks by SHA alone, without repository scoping — unlike `CheckSuiteHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(payload['repository']['full_name'])`, and `CheckSuiteHandler` correctly uses it (`stacks.where(branch: ...)`). `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` directly — completely bypassing `stacks`/`repository_name` — so any commit anywhere in the installation sharing that SHA gets its status mutated regardless of which repository the webhook payload names.

### Finding Description
The claimed binding is: for every `Handler` subclass, `payload['repository']['full_name'] == repository` whose `Stack`/`Commit` is mutated.

- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) enforces this: `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name` is `payload.dig('repository', 'full_name')`. [1](#0-0) 
- `CheckSuiteHandler#process` upholds the binding: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!) }` — the commit set is derived from the repository-scoped `stacks` relation. [2](#0-1) 
- `StatusHandler#process` breaks the binding: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` never consults `repository_name`/`stacks` at all — it is a global, unscoped `Commit` table query by `sha` only. [3](#0-2) 

Root cause: `StatusHandler` never calls `stacks`/`Repository.from_github_repo_name`; it relies solely on global SHA uniqueness, which does not hold across stacks/repositories (forks, mirrors, or repos sharing commit history can have identical commit SHAs recorded as separate `Commit` rows belonging to different `stack_id`s).

Exact attacker request: an unprivileged user who can trigger any legitimate `status` webhook from a GitHub repository they control (e.g., their own fork/repo with a CI integration or the Status API) sets `payload['repository']['full_name']` to their own repo and `sha` to a value that happens to also exist as a `Commit.sha` in an unrelated stack/repository tracked by the same Shipit instance. `WebhooksController#create` dispatches to `StatusHandler.call(params)` after `verify_signature`; `verify_signature` only checks that the payload was signed by the GitHub App/organization named in `payload['repository']['owner']['login']` — it does not validate that the named repository actually owns the `sha`, nor does it prevent cross-stack effects once the payload is authentic for the attacker's own repo/org. [4](#0-3) [5](#0-4) 

`create_status_from_github!` then writes a `Status` and can trigger `Hook.emit(:commit_status/:deployable_status, stack, ...)` and `stack.schedule_merges` on the **victim** stack — i.e., a write to a stack the attacker never named/authenticated in the payload. [6](#0-5) [7](#0-6) 

Why existing guards don't prevent it: `verify_signature` validates the HMAC against the organization derived from the payload's own `repository.owner.login`/`organization.login` — it authenticates "this came from GitHub for org X," not "the named repository is the one whose commit is being mutated." `ExplicitParameters` (`ParamsSchema` in `StatusHandler`) only validates the shape of `sha`/`state`/etc., not repository ownership. There is no model-level constraint preventing two `Commit` rows in different `stack_id`s from sharing the same `sha`.

### Impact Explanation
A `status` webhook honestly signed for repository/stack A can flip the CI status of a commit that also exists (same `sha`) in stack B, triggering `deployable_status`/`commit_status` hooks and `schedule_merges` (which can enqueue `ProcessMergeRequestsJob`) on stack B — a payload for one repository mutating another repository's stack/commit records. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any pair of stacks that ever share a commit `sha` (forks, mirrored repos, repos importing the same history), and confirms the divergence is specific to `StatusHandler`; `CheckSuiteHandler` (and, by the same `stacks`-based pattern, the check_run path) correctly scopes by `repository.full_name` and is not affected.

### Likelihood Explanation
Preconditions: (1) the attacker must control/trigger a genuinely signed `status` webhook, meaning they need a repository under a GitHub organization for which Shipit's GitHub App/webhook secret is configured (or their own account is a `Shipit.github(organization:)`-recognized owner); (2) a `Commit` row with a colliding `sha` must already exist in a different, victim stack — realistic for forks/mirrors/imported-history repos, not for arbitrary unrelated repos. Attacker cost is low once these preconditions hold: no session, API token, or Shipit-side secret is needed, only the ability to cause GitHub to emit a `status` event for a commit they can name (e.g., via a personal CI integration or the GitHub Status API on a repo they can push to). The attack is repeatable per shared-sha pair.

### Recommendation
Make `StatusHandler` scope through the same `stacks`/`repository_name` binding as `CheckSuiteHandler` instead of querying `Commit` globally, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores `payload['repository']['full_name'] == repository` for every commit mutated, consistent with `Handler#stacks` and `CheckSuiteHandler`.

### Proof of Concept
minitest plan (under `test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of audit scope to write but described for reproduction):
1. Create two `Repository`/`Stack` fixtures, `repo_a` (owner `owner-a`) and `repo_b` (owner `owner-b`), each with a `Commit` sharing the identical `sha: "deadbeef..."` but distinct `stack_id`s.
2. Build a `status` payload with `payload['repository']['full_name'] = 'owner-a/repo_a'` and `sha` equal to the shared sha.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert: `commit_b.reload.statuses.count` changed (it should be `0`/unchanged if scoped correctly) — demonstrate it is `> 0`, proving `repo_b`'s commit was mutated by a payload naming `repo_a`.
5. Repeat the same cross-stack sha setup with a `check_suite` payload naming `repo_a` and call `CheckSuiteHandler.call`; assert `commit_b` (stack B) is untouched (`schedule_refresh_check_runs!` not enqueued for it), confirming the asymmetry: `CheckSuiteHandler` respects `payload['repository']['full_name'] == repository`, `StatusHandler` does not.
