### Title
Membership webhook accepted without a real signature when target org has no `webhook_secret`, allowing forged team-membership escalation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` resolves the signing organization purely from the request body (`params.dig('organization','login')` for a `membership` event), and `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success. If any org configured in `Shipit.github_apps` lacks a `webhook_secret`, an attacker can send an unsigned/self-signed `membership` webhook naming that org and a `team.id` colliding with a `Team` gating `Shipit.github_teams`, and `MembershipHandler#process` will add an arbitrary attacker-controlled user to that team, directly affecting `User#authorized?`.

### Finding Description
The broken binding is: **team membership mutation authorized ⇔ request byte-for-byte HMAC-verified with the real `webhook_secret` of the organization owning the team.** The code path breaks this equality when a configured org has no secret.

- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config: `return true unless webhook_secret` [3](#0-2) .
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)` and `#process` calls `team.add_member(User.find_or_create_by_login!(params.member.login))` on `action == 'added'` [4](#0-3) .
- `Team#add_member` unconditionally appends the member [5](#0-4) .
- `User#authorized?` consults exactly this membership: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) .

Exploit flow: attacker POSTs `X-Github-Event: membership` with `action: 'added'`, `organization.login` set to whichever configured org lacks a `webhook_secret`, `team.id` equal to the `github_id` of an existing `Team` referenced in `Shipit.github_teams`, and `member.login: 'attacker-handle'`. Because `repository_owner` resolves to that same `organization.login`, `Shipit.github(organization: repository_owner)` loads that org's config, finds no `webhook_secret`, and `verify_webhook_signature` returns `true` regardless of what signature (or none) was sent. The handler then finds the existing gating `Team` by `github_id` and adds `attacker-handle` as a member, without ever having proven possession of that org's real secret.

This is a genuine authentication bypass on the webhook boundary, but it is conditioned on a specific misconfiguration precondition (an org entry in `Shipit.github_apps` with no `webhook_secret` set) - which is exactly the condition the code explicitly permits (`return true unless webhook_secret`), not a hidden bug elsewhere. Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema) do not check secret presence; they only validate shape, not the binding.

### Impact Explanation
If exploited, an attacker gains membership in a `Team` record that gates access via `Shipit.github_teams`/`User#authorized?`, i.e., escalation into `Shipit.github_teams` authorization, letting `force_github_authentication`-protected areas treat the attacker as authorized. This matches the "High: escalation into `Shipit.github_teams` authorization" impact category. It is repeatable per request against any team whose organization is configured without a `webhook_secret`; blast radius is scoped to that specific misconfigured org's teams, not arbitrary tenants with correctly configured secrets.

### Likelihood Explanation
Exploitability strictly requires operator misconfiguration: at least one org in `Shipit.github_apps` must be present with a blank `webhook_secret` while still being referenced by `Shipit.github_teams` for authorization gating. In a correctly configured deployment (every org entry in `Shipit.github_apps` has a `webhook_secret`), `verify_webhook_signature` always performs a real HMAC check and this path is not reachable — the attacker cannot forge a valid signature without the secret. Given the described precondition is explicitly a config gap (missing secret) rather than a code flaw exploitable under normal/documented configuration, likelihood is low without that misconfiguration, but the underlying behavior (`return true unless webhook_secret`) is real code in this engine and worth flagging as unsafe-by-default rather than fail-secure.

### Recommendation
Make `GitHubApp#verify_webhook_signature` fail closed when `webhook_secret` is missing (raise/return `false` instead of `true`), or require `webhook_secret` presence at boot for any org configuration that is also referenced by `Shipit.github_teams`. Additionally, consider validating that `organization.login` in the membership payload matches an org actually authorized to manage teams referenced by `Shipit.github_teams`, independent of the webhook signature check.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (concept, not asserting a preexisting bug in normal config)
test 'membership webhook is rejected when org webhook_secret is blank' do
  Shipit.github_apps['no-secret-org'] = { app_id: 1, installation_id: 1, private_key: 'x' } # no webhook_secret
  team = shipit_teams(:some_gating_team) # github_id known, referenced by Shipit.github_teams
  Shipit.stubs(:github_teams).returns([team])

  post :create,
    body: {
      action: 'added',
      team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
      organization: { login: 'no-secret-org' },
      member: { login: 'attacker-handle' }
    }.to_json,
    params: {},
    headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => 'sha1=garbage' }

  # BEFORE: attacker-handle is not a member, org secret absent => request should be rejected (422)
  # AFTER (bug): response is 200 and User.find_by(login: 'attacker-handle').authorized? == true
  refute User.find_by(login: 'attacker-handle')&.authorized?
end
```
Both sides of the binding — "verified with real secret" vs "org config has a secret at all" — diverge precisely when `webhook_secret` is blank, confirming the fail-open behavior in `GitHubApp#verify_webhook_signature` [7](#0-6) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
