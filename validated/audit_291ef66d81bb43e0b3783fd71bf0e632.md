### Title
Webhook signature only authenticates the sender organization, not the `repository.full_name` field it authorizes syncing for - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to verify the HMAC signature using `repository.owner.login` (falling back to `organization.login`) taken directly from the still-unverified JSON body, but the event handlers (e.g. `PushHandler`) resolve which `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Nothing binds these two fields together, so a signature that is valid for organization A's webhook secret can carry a forged `repository.full_name` pointing at organization B's stack.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-suppliable JSON before any authentication has occurred: [1](#0-0) [2](#0-1) 

The equality that should hold is:
`organization used to select webhook_secret (repository.owner.login / organization.login)` == `organization embedded in repository.full_name that the handler will act on`.

That equality is never checked. `Handler#repository_name` and `Handler#stacks` resolve the target purely from `repository.full_name`: [3](#0-2) 

`Repository.from_github_repo_name` simply splits that string on `/` with no cross-check against `repository.owner.login`: [4](#0-3) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on whatever stacks match, using the attacker-controlled `after` SHA and `ref`: [5](#0-4) 

Because the HMAC in `verify_webhook_signature` covers the *entire* raw body (using `Shipit.github(organization: repository_owner)`'s secret), an entity that legitimately knows organization A's webhook secret (e.g. an admin/attacker of a self-onboarded, less-trusted organization in a multi-tenant Shipit deployment) can compute a valid signature over a payload whose `repository.owner.login`/`organization.login` is "A" while `repository.full_name` is `"B/victim-repo"`. The signature check passes (it only proves "this body was signed with A's secret"), yet the handler that consumes the same body acts on repository B's stack.

### Impact Explanation
This breaks the binding "the organization whose credentials authenticated the webhook" == "the repository the webhook is allowed to mutate", letting an org that only controls its own webhook secret trigger `sync_github` (and, if `continuous_deployment` is enabled on the target stack, an autodeploy of an attacker-chosen existing commit SHA) on a stack belonging to a completely different, unrelated repository/organization. That is a cross-repository, cross-tenant write/trigger performed with credentials scoped to a different organization — matching the "cross-repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for at least one organization configured in the Shipit instance (their own, in a multi-org/multi-tenant deployment) and the target's `owner/name` (public information). No GitHub session, `ApiClient` token, or repository write access on the victim repo is required — only the ability to POST directly to the public `/webhooks` endpoint with a self-signed body. This is realistic for any Shipit deployment onboarding more than one organization (the exact scenario the `github:` multi-org config in `config/secrets.development.shopify.yml` is designed for).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), require that the organization derived from `repository.full_name` (the part before the `/`) matches `repository.owner.login`/`organization.login` used to select the verifying secret, rejecting the request (422) on mismatch before any handler processes the payload.

### Proof of Concept
1. Attacker controls organization `attacker-org`, which is configured in Shipit with `webhook_secret: S` (e.g., a self-service/onboarded org in a multi-tenant install).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<existing sha from victim repo history>",
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` themselves (they know `S`) and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature verifies successfully against attacker-org's own secret.
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the target stack via `repository.full_name` = `"victim-org/victim-repo"`, not `attacker-org`, and calls `stack.sync_github(expected_head_sha: "<victim sha>")` on the victim's stack — a stack the attacker never authenticated against.
