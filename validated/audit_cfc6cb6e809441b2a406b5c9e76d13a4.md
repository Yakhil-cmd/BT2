### Title
Webhook signature verification is keyed on an unauthenticated `repository.owner.login` field while event handlers act on the independently attacker-controlled `repository.full_name` field, letting a forged webhook targeting one organization be verified against a different organization's (weaker) secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to use for HMAC verification based on `repository_owner`, which is parsed straight out of the unauthenticated request body (`params.dig('repository', 'owner', 'login')`), before the signature has been checked. The event handlers that subsequently act on the payload (creating jobs, statuses, check-runs, users, teams) instead resolve their target `Repository`/`Stack` using a *different* field of the same JSON object: `payload.dig('repository', 'full_name')`. Because both fields live in attacker-supplied JSON and nothing cross-validates that `full_name` is consistent with `owner.login`, an attacker can decouple "which org's secret verifies this request" from "which org's repository/stack the request actually mutates."

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handlers act on`

In `verify_signature`: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The chosen `GitHubApp`'s secret is looked up via `Shipit.github_app_config(organization)` in `lib/shipit.rb`: [3](#0-2) 

If that organization's `webhook_secret` is blank (documented as *optional* in `docs/setup.md`, and left `nil` in every example/dummy config shown, e.g. `secrets_double_github_app.yml`), `verify_webhook_signature` unconditionally returns `true`: [4](#0-3) 

Meanwhile, the actual event handler resolves the target `Repository`/`Stack` using `full_name`, a sibling field in the same attacker-controlled JSON object, never covered by the check above: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find the target repo, independent of `owner.login`: [6](#0-5) 

In a documented multi-organization installation (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), each org has its own `webhook_secret` config, but they all share the single `/webhooks` endpoint: [7](#0-6) [8](#0-7) 

An attacker can therefore submit a payload where `repository.owner.login` is set to an organization whose `webhook_secret` is unset (satisfying `verify_signature` trivially, since GitHub App webhook secrets are optional and commonly left blank per every shipped example config), while `repository.full_name` names a stack belonging to a *different*, properly-secured organization. `verify_signature` only ever authenticates against the org named in `owner.login`; it never confirms that `full_name`'s owner segment matches. This breaks the deployment-trust binding "org authenticated == repo written," letting an attacker with no valid secret at all forge `push`, `status`, `check_suite`, and `membership` events against a victim org's stacks and teams.

### Impact Explanation
This maps to "escalation into `Shipit.github_teams` authorization" and "unauthenticated read/write of stack state" impact tiers: a forged `push` webhook enqueues `GithubSyncJob` against the victim stack (test corroborates this exact flow: `test/controllers/webhooks_controller_test.rb` lines around `":push with the target branch queues a GithubSyncJob"`), a forged `status`/`check_suite` event fabricates commit statuses/check runs that Shipit's deploy-gating logic relies on to decide whether a commit is deployable, and a forged `membership` event creates arbitrary `User`/`Team` records tied to attacker-chosen GitHub logins: [9](#0-8) 

Fabricated passing statuses/check-runs can be leveraged to make a stack appear deployable to a legitimate operator, i.e. contributing to an unauthorized deploy of attacker-influenced state, without ever possessing the target organization's `webhook_secret`.

### Likelihood Explanation
Requires only that the Shipit installation is configured with more than one GitHub organization (a documented, supported configuration) where at least one configured organization's `webhook_secret` is left blank — the state shown by every example/dummy config in the repo (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`). No authentication, session, or existing credential is required; the attacker only needs to know one victim stack's `owner/name` and one "throwaway" org name with no secret configured. This is a realistic, low-effort configuration state given the docs explicitly mark `webhook_secret` as optional.

### Recommendation
- Never select the verification key from unauthenticated payload data whose scope differs from the field the rest of the pipeline trusts. Derive the verifying organization the same way the handlers derive the target repository — i.e., from `repository.full_name`'s owner segment, not from the redundant `repository.owner.login`.
- After signature verification, assert `repository.owner.login == full_name.split('/').first` (or drop reliance on `owner.login` entirely) before dispatching to handlers.
- Treat a missing `webhook_secret` for any one configured organization as making verification universally bypassable only for *that* organization's own repositories, never as means to authenticate requests naming a different organization's repositories.

### Proof of Concept
1. Configure Shipit with two organizations, `WeakOrg` (no `webhook_secret` set) and `VictimOrg` (secret configured and kept private), both installed as GitHub Apps as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "WeakOrg" }, "full_name": "VictimOrg/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>"
}
```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"WeakOrg"`, calls `Shipit.github(organization: "WeakOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) regardless of the (even absent) `X-Hub-Signature` header.
4. `create` proceeds and dispatches to `Handlers::PushHandler`, which resolves the target stack via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), enqueuing a `GithubSyncJob` against `VictimOrg`'s real stack — despite the attacker never possessing `VictimOrg`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
