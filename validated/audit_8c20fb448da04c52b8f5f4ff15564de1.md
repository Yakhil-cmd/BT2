## Valid Analog Found

### Title
Pool creator address is permanently immutable with no recovery/transfer mechanism, permanently freezing creator fees if lost or mis-set - (`programs/cp-swap/src/states/pool.rs`, `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`PoolState.pool_creator` is written exactly once, in `PoolState::initialize`, from the `creator` signer that calls `initialize`, and there is no instruction anywhere in the program that can subsequently change it. This is the exact same bug class as the reported `DepositManagerOwnable` finding: a privileged role address is set at construction time with no "remove"/"transfer" path, so if that address is wrong, lost, or compromised, the role becomes permanently unrecoverable.

### Finding Description
`PoolState::initialize` sets `self.pool_creator = pool_creator.key()` and this field is never mutated elsewhere in the codebase. [1](#0-0) 

By contrast, `AmmConfig`'s equivalent privileged fields (`protocol_owner`, `fund_owner`) do have explicit rotation logic (`set_new_protocol_owner`, `set_new_fund_owner`), reachable via `UpdateAmmConfig`, showing the pattern is understood elsewhere in the program but was omitted for `pool_creator`. [2](#0-1) 

`pool_creator` gates both fee-collection paths:
- `CollectCreatorFee` requires the `creator` signer to match `pool_state.load()?.pool_creator` exactly. [3](#0-2) 
- `CollectCreatorFeePermissionless` can be called by anyone, but the collected fees are always sent to the ATA owned by `pool_state.load()?.pool_creator`, with no way to redirect them. [4](#0-3) 

Since `pool_creator` is taken directly from whichever `creator` signer submits the `initialize` transaction, a pool creator can also accidentally initialize the pool with a `creator` account they don't have exclusive/durable control over (e.g., a multisig with rotated signers, a hardware wallet later lost, or a transient/burner keypair used to bootstrap the pool), permanently locking themselves out of ever collecting `creator_fees_token_0`/`creator_fees_token_1` that accumulate for that pool's lifetime. [5](#0-4) 

### Impact Explanation
Creator fees (`creator_fees_token_0`, `creator_fees_token_1`) accrue in the pool vaults over the pool's entire lifetime. [6](#0-5) 
If the `pool_creator` key is lost, or if the creator initialized the pool with an address they no longer control, these funds become permanently frozen/unclaimable — no admin, protocol owner, or any other instruction in the program can update `pool_creator` or redirect the accrued fees. This is a permanent freezing of legitimate creator funds, which persists for the lifetime of the pool since pools are not closable and `pool_creator` cannot be rotated.

### Likelihood Explanation
Any user who creates a pool via `initialize` sets this field for themselves as a byproduct of an ordinary, unprivileged action — no attacker or privileged signer is required to trigger the exposure. Loss of key access, use of an unintended keypair, or a compromised creator key are realistic, commonly-seen scenarios and the resulting fee lock is deterministic and immediate once it occurs.

### Recommendation
Add a `pool_creator` rotation mechanism analogous to `set_new_protocol_owner`/`set_new_fund_owner`, e.g. an instruction that lets the current `pool_creator` (as a signer) update `PoolState.pool_creator` to a new address, with the standard `require_keys_neq!(new_creator, Pubkey::default())` safety check.

### Proof of Concept
1. Call `initialize` as `creator = A`, creating a pool; `PoolState.pool_creator = A` is stored permanently. [5](#0-4) 
2. Swaps occur against the pool, accumulating `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
3. Key `A` is lost or compromised (analogous to the referenced report's "accidentally transferred to wrong address or lost the address access").
4. `CollectCreatorFee` cannot be called because its `creator` account is constrained to `address = pool_state.load()?.pool_creator == A`. [3](#0-2) 
5. `CollectCreatorFeePermissionless` can still be invoked by any payer, but it unconditionally sends the fees to the ATA of `A`, which is unusable/inaccessible. [7](#0-6) 
6. There is no instruction in `programs/cp-swap/src/instructions` or `programs/cp-swap/src/lib.rs` that can update `PoolState.pool_creator`, so the accrued and future creator fees are permanently unrecoverable.

fn set_new_protocol_owner(amm_config: &mut Account<AmmConfig>, new_owner: Pubkey) -> Result<()> {
    require_keys_neq!(new_owner, Pubkey::default());
    #[cfg(feature = "enable-log")]
    msg!(
        "amm_config, old_protocol_owner:{}, new_owner:{}",
        amm_config.protocol_owner.to_string(),
        new_owner.key().to_string()
    );
    amm_config.protocol_owner = new_owner;
    Ok(())
}
