I have enough evidence to establish the vulnerability now. Let me verify the sync_github behavior triggers real state changes and confirm the GithubSyncJob impact.### Title
Cross-organization webhook forgery: `repository.owner.login` selects the HMAC secret used for verification while `repository.full_name` selects the Stack that is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate the request against using an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`), taken from the still-unauthenticated request body. The event handlers that actually mutate application state (`PushHandler`, pull-request handlers, `StatusHandler`, etc.) look up the target `Stack`/`Repository` using a *different* field from the same unauthenticated body: `repository.full_name`. Because Shipit explicitly supports hosting multiple GitHub organizations behind a single `/webhooks` endpoint (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github_app_config`), a webhook correctly signed with Organization A's secret can freely declare `repository.full_name` pointing at a Stack that belongs to Organization B. The equality that should hold — "the organization whose secret authenticated this request" == "the organization owning the repository being acted upon" — is never enforced.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves the app/secret like this: [1](#0-0) 
`repository_owner` is read straight out of the unverified JSON body: [2](#0-1) 

`Shipit.github(organization:)` maps that attacker-supplied organization name to a configured `GitHubApp` and its `webhook_secret`, supporting exactly this kind of multi-tenant configuration: [3](#0-2) 

Meanwhile, the handlers that perform the actual write (queue syncs, create statuses, provision review stacks, unarchive/archive stacks, update pull request state) resolve their target repository from a **separate** field of the same payload, `repository.full_name`, via `Handler#repository_name`/`Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

For example `PushHandler` uses `stacks` (built from `repository.full_name`) to enqueue a `GithubSyncJob` for whatever branch/stack the attacker names: [6](#0-5) 

There is no code path that checks `repository.owner.login` (used to pick the verifying secret) against `repository.full_name`'s owner segment (used to pick the target Stack). An attacker who legitimately controls a GitHub App/organization onboarded to the same Shipit instance (i.e., knows or can compute a valid `X-Hub-Signature` for **their own** org's `webhook_secret`) can set `repository.owner.login` to their own org while setting `repository.full_name` to `"other-org/other-repo"`. The signature check passes (it's a legitimately signed payload from Org A), but the handler acts on a Stack belonging to Org B — a repository/organization the attacker has no relationship with.

### Impact Explanation
This breaks the "organization authenticated == repository written" binding explicitly called out as an in-scope pattern. Concretely, with a validly-signed webhook from an org the attacker controls, they can, for any other repository tracked by the same Shipit instance:
- Force `PushHandler` to enqueue `GithubSyncJob` for an arbitrary Stack/branch (`stacks.not_archived.where(branch:)`), fabricating an `after` SHA that is not the real GitHub state, feeding a forged `expected_head_sha` into commit sync/locking logic.
- Fabricate `status`/`check_suite` webhook data (`StatusHandler`) to mark a commit's CI as `success` on a repository they don't control, which — combined with `continuous_deployment?` — can automatically trigger `ContinuousDeliveryJob` → `trigger_deploy` on that unrelated stack, i.e., an **unauthorized deploy**, per `Commit#schedule_continuous_delivery` / `Deploy` continuous-delivery flow.
- Manipulate pull-request handlers (`OpenedHandler`, `LabeledHandler`, etc.) to archive/unarchive stacks or provision review-stack deployments for repositories outside their control.

This matches the required Critical/High impact bar: an unauthorized deploy triggered against a stack/repository the attacker does not own, via a security boundary (per-organization webhook signing) that was supposed to isolate tenants from each other.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`), and (2) the attacker being a legitimate administrator/owner of at least one of those onboarded organizations (so they know that org's `webhook_secret`, or can register/replace their own GitHub App's webhook config to set an attacker-known secret). This is a real "unprivileged relative to the victim org" attacker: they have zero privileges on the victim's repository/organization/Shipit account, yet can act on it purely because they administer some other tenant hosted on the same instance. No `ApiClient` token, GitHub App private key, or Shipit session is required — only their own org's webhook secret, satisfying the unprivileged-attacker rule.

### Recommendation
Enforce that the organization used to select/verify the webhook signature matches the owner embedded in `repository.full_name` (and any other repository/org references in the payload) before dispatching to handlers. Concretely, in `WebhooksController`, after successfully identifying `github_app` for `repository_owner`, additionally validate that `repository.full_name.split('/').first` (case-insensitively) equals `repository_owner`, and reject (422) on mismatch. For organization-level events (e.g., `membership`) apply the equivalent check against `organization.login`.

### Proof of Concept
Preconditions: Shipit configured with multi-org GitHub config, e.g. `OrgA` (attacker-administered, webhook_secret known to attacker) and `OrgB` (victim org, repository `orgb/victim-repo` tracked as a Stack with `continuous_deployment: true`).

1. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<current head sha of orgb/victim-repo's branch>",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "orgb/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` using the secret they legitimately possess for `OrgA`.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies successfully against `OrgA`'s secret.
5. `Shipit::Webhooks::Handlers::StatusHandler` (using `repository.full_name` = `orgb/victim-repo`) creates a `success` status on the targeted commit of `OrgB`'s stack.
6. If that stack has `continuous_deployment: true` and this is the last required status, `schedule_continuous_delivery`/`ContinuousDeliveryJob` triggers `trigger_deploy`, producing an unauthorized deploy on `OrgB`'s infrastructure — despite the attacker never being granted access to `OrgB`, its GitHub App, or its Shipit stack.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
