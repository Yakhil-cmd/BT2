## Analysis

### Title
Integer-division truncation in PoX-5 reward-rate accounting permanently strands sBTC/STX rewards in the contract - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`calculate-rewards` and `calculate-bond-rewards` compute per-token reward rates using Clarity's floor-dividing `/` operator. The truncated remainder is never re-credited to the reserve, to any bond, or to any staker, yet the contract's bookkeeping variable `last-accounted-rewards-only` is incremented by the *full, un-truncated* pool amount. This breaks the invariant that "amount marked as accounted for" == "amount actually claimable," permanently stranding the truncated dust inside the contract's sBTC balance every reward-distribution cycle.

### Finding Description
In `calculate-rewards`, the STX-staker rate is derived as: [1](#0-0) 

`accrued-rewards-per-ustx` floors `(stx-staker-rewards * PRECISION) / cycle-staked-ustx`. Any remainder from this division is lost from the per-token rate, but `last-accounted-rewards-only` is nonetheless advanced by the entire `stx-staker-rewards` amount: [2](#0-1) 

The same pattern repeats for bonds, where `target-yield`/`accrued-rewards-per-sat` are computed with nested floor divisions: [3](#0-2) 

Because `get-new-rewards` (used as the input to the *next* `calculate-rewards` call) is `get-rewards() - last-accounted-rewards-only`, and `get-rewards()` subtracts the on-chain sBTC balance against `total-staked-sbtc` and `reserve-balance` only: [4](#0-3) 

the truncated dust remains physically in the contract's sBTC balance forever, but is simultaneously marked as "already accounted for" via `last-accounted-rewards-only`, so it is never picked up as `new-rewards` in any subsequent cycle, never added to `reserve-balance`, and never distributed via any staker's or bond's `rewards-per-token` map. There is no code path that later sweeps this dust into the reserve or into any claimable balance — each cycle it must break by `1..N-1` sats/µSTX depending on the truncation, and this compounds indefinitely.

This is the same bug class as the reported issue (division truncation silently zeroing/rounding down a value that is supposed to sum exactly to the input), except here the truncated remainder is not merely a payee receiving zero — the accounting variable double-counts it as "distributed" while the value is physically un-claimable by any party, breaking the equality `distributed to stakers/bonds + reserve deposit == gross accrued rewards accounted-for`.

### Impact Explanation
Every call to `calculate-rewards` can permanently freeze a small amount of sBTC reward value that can never be claimed by the reserve, any bond, or any staker, since the bookkeeping already marks it as accounted for. This matches the "permanent freezing of reserve or fees" class defined in scope. The amount lost per call is bounded by the number of division operations (a handful of sats/µSTX per call), but it is unrecoverable and accumulates over the life of the contract with no mechanism to reclaim it.

### Likelihood Explanation
This triggers on every single `calculate-rewards` call whenever the numerator is not an exact multiple of the divisor (`cycle-staked-ustx`, `u10000`, `u50`, or `total-sats`), which is the common case given arbitrary sBTC reward amounts and stake totals. No privileged role is required — `calculate-rewards` appears to be callable by any party as part of normal reward-cycle bookkeeping.

### Recommendation
Mirror the fix already applied in `sip-031.clar`'s `calc-total-vested`, which explicitly flushes the truncation remainder once all iterations complete (see `INITIAL_MINT_VESTING_AMOUNT` fallback at the final iteration): [5](#0-4) 

For `pox-5.clar`, either (a) increment `last-accounted-rewards-only` only by the amount actually representable in the per-token rate (i.e., recompute the distributed total as `rate * total-shares / PRECISION` and route the remainder into `reserve-balance` instead of assuming full distribution), or (b) accumulate the floor-division remainder in a small carry-forward variable added to the numerator of the next cycle's rate calculation so it eventually gets distributed rather than silently stranded.

### Proof of Concept
1. Some sBTC rewards accrue to the PoX-5 contract; `calculate-rewards` is called with `cycle-staked-ustx = 3` and `stx-staker-rewards = 10` (arbitrary values chosen so `10 * PRECISION` is not evenly divisible by `3`).
2. `accrued-rewards-per-ustx = (10 * PRECISION) / 3` truncates, discarding a remainder `r > 0` in PRECISION units.
3. `last-accounted-rewards-only` is nonetheless incremented by the full `10` (via `gross-accrued-rewards - reserve-deposit`), so `get-new-rewards` in all future calls treats this `10` as fully spoken-for.
4. When all stakers eventually claim via `compute-earned-rewards`, the sum of `shares * accrued-rewards-per-ustx / PRECISION` across all stakers is strictly less than `10` by the truncated remainder `r`.
5. That remainder `r` remains in the contract's sBTC balance, is never added to `reserve-balance`, and is never picked up by a future `get-new-rewards` call (since `last-accounted-rewards-only` already "spent" it) — it is permanently frozen.
