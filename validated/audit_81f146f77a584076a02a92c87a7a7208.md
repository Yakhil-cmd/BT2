### Title
Unbounded `RemoteProxyProof::RelayChain` proof size with fixed extrinsic weight enables weight/computation mismatch DoS - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` charges a fixed weight (`WeightInfoOf::remote_proxy()` plus the wrapped call's `call_weight`) that is benchmarked against a minimal, single-node trie proof, but the actual `proof: Vec<Vec<u8>>` field accepted from an unprivileged, signed extrinsic is unbounded in size/shape. `Pallet::do_remote_proxy` unconditionally converts the whole proof into a `MemoryDB` via `sp_trie::StorageProof::new(proof).into_memory_db` before attempting `sp_trie::read_trie_value`, so the actual computation scales with the total size of attacker-supplied proof bytes while the charged weight does not.

### Finding Description
The extrinsic `remote_proxy` is reachable by any signed account with no proxy relationship precondition and takes an attacker-controlled `RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, block }`: [1](#0-0) [2](#0-1) 

The `block` parameter only needs to match any entry in the public `BlockToRoot` storage, which is refreshed every block by `on_validation_data`: [3](#0-2) 

Weight for `remote_proxy` is fixed regardless of proof content/size — it's the sum of a constant `WeightInfoOf::<T, I>::remote_proxy()`, a constant DB read/write weight, and the wrapped call's own `call_weight`. Nothing here scales with `proof.len()` or the size of each `Vec<u8>` node: [4](#0-3) 

Inside `do_remote_proxy`, once the block lookup succeeds, the entire supplied `proof` (arbitrary number/size of byte vectors) is converted into an in-memory trie database and then a single value lookup is attempted: [5](#0-4) 

`sp_trie::StorageProof::new(proof).into_memory_db` hashes and inserts every supplied node into the `HashDB`, an O(total proof bytes) operation, independent of whether any of the nodes are actually part of a valid path to the target key. `read_trie_value` can then fail cheaply once it can't find/follow a coherent path, but the up-front `into_memory_db` conversion cost already scales with attacker-controlled data size.

The benchmark that produced the shipped weight uses a *minimal* single-entry trie (one value, one node) via `create_remote_proxy_proof`, both in the pallet's own benchmarking harness and in the relay-chain-specific `RemoteProxyInterface` implementations: [6](#0-5) [7](#0-6) 

The generated weight for `remote_proxy()` is a small constant (~16-20 microseconds, fixed `Weight::from_parts(0, 1846)` PoV component), regardless of the actual `proof` an attacker supplies at call time: [8](#0-7) 

The `RemoteProxyProof` enum places no bound (no `BoundedVec`, no `MaxEncodedLen`-style cap) on the number or size of proof nodes: [9](#0-8) 

There is no additional check in `do_remote_proxy` that limits `proof.len()` or total byte size before the `into_memory_db` conversion is performed, so an unprivileged caller controls the amount of hashing/insertion work the runtime performs for a fixed, low weight charge.

### Impact Explanation
Because per-call weight is fixed and doesn't scale with the actual size of the proof, an attacker can submit `remote_proxy` calls with large `proof` vectors (bounded only by the chain's max extrinsic/block length, not by the pallet's weight metering) that consume real CPU time for `into_memory_db` hashing/insertion disproportionate to the ref_time charged. Since this extrinsic weight class inherits `di.class` from the wrapped call (which could be `Normal`), and the actual work-to-weight ratio is wrong, an attacker can pack the block with calls that look individually cheap to the weight-based block-builder scheduling but are actually expensive to execute, degrading block-authoring/import throughput and potentially delaying legitimate `remote_proxy` users whose freshest `BlockToRoot` entries could roll off before their transaction is included (`BlockToRoot` retains only `MaxStorageRootsToKeep` entries per `on_validation_data`). This is a resource-accounting/DoS issue scoped to remote-proxy transaction processing, not an asset-theft or origin-forgery bug.

### Likelihood Explanation
No proxy relationship is required — only a signed account and a `block` value present in the always-populated `BlockToRoot` storage, both trivially satisfiable by any user. The attack is repeatable across many transactions/blocks. The severity is bounded in practice by the chain's overall max block length (which caps total extrinsic byte size per block, independent of the pallet's declared weight), so this is not an unbounded/catastrophic DoS but a genuine mismatch between charged weight and actual computation for this specific call, which is exactly the kind of gap fuzz/benchmark-based weight validation is meant to catch. I could not verify from the available index whether any global runtime-level extrinsic length limit meaningfully constrains this (chain constants for `BlockLength`/`length_bound` exist in multiple runtimes but their specific values weren't inspected here), so the exact achievable proof size per block is uncertain.

### Recommendation
Benchmark and charge weight for `remote_proxy`/`remote_proxy_with_registered_proof` proportional to the actual size of the supplied `proof` (e.g., a `WeightInfo::remote_proxy_proof_node(n: u32)` component derived from `proof.len()` and/or total byte length), and/or enforce a hard cap on the number/total size of proof nodes accepted (e.g., wrap `proof` in a `BoundedVec` with a `Config::MaxProofNodes`/`MaxProofSize` bound) before calling `into_memory_db`, rejecting oversized proofs early with a cheap length check.

### Proof of Concept
Rust benchmark/fuzz test plan:
1. In `pallets/remote-proxy/src/tests.rs`, construct `RemoteProxyProof::RelayChain` proofs of varying total sizes: (a) the existing minimal single-node valid proof, (b) a large `Vec<Vec<u8>>` of thousands of random garbage 32-1KB byte vectors that do not correspond to a valid trie for the target key, keeping total size within typical max block length.
2. Insert a matching `block`/`storage_root` entry into `BlockToRoot` via `RemoteProxy::on_validation_data` as in existing tests.
3. Measure wall-clock time (or instruction count via a benchmarking harness) of `Pallet::do_remote_proxy` for each proof size, asserting execution time grows materially with proof size (e.g., >10x between minimal and large garbage proof).
4. Assert that `WeightInfoOf::<T, I>::remote_proxy()` returns a constant weight independent of the proof passed to the extrinsic (call the weight function directly with different `call` `DispatchInfo`s but note it never inspects `proof`).
5. Fail the invariant test if `measured_execution_time(large_garbage_proof) > weight_charged_for_call` by more than an acceptable safety margin, confirming a weight-accounting gap.

		fn on_validation_data(validation_data: &PersistedValidationData) {
			let Some((block, hash)) = T::RemoteProxy::block_to_storage_root(validation_data) else {
				return;
			};

			// Update the block to root mappings.
			BlockToRoot::<T, I>::mutate(|roots| {
				let delete_up_to =
					block.clone().saturating_sub(T::MaxStorageRootsToKeep::get().into());

				while roots.first().is_some_and(|f| f.0 <= delete_up_to) {
					roots.remove(0);
				}

				// We always remove all the old items before, thus there should always be space in
				// the vector.
				let _res = roots.try_push((block, hash));
				debug_assert!(_res.is_ok());
			});
		}

		fn create_remote_proxy_proof(
			caller: &AccountId,
			proxy: &AccountId,
		) -> (pallet_remote_proxy::RemoteProxyProof<Self::RemoteBlockNumber>, BlockNumber, Hash) {
			use codec::Encode;
			use sp_trie::TrieMut;

			let (mut db, mut root) = sp_trie::MemoryDB::<BlakeTwo256>::default_with_root();
			let mut trie =
				sp_trie::TrieDBMutBuilder::<sp_trie::LayoutV1<_>>::new(&mut db, &mut root).build();

			let proxy_definition =
				alloc::vec![ProxyDefinition::<AccountId, ProxyType, BlockNumber> {
					delegate: caller.clone(),
					proxy_type: ProxyType::default(),
					delay: 0,
				}];

			trie.insert(&Self::proxy_definition_storage_key(proxy), &proxy_definition.encode())
				.unwrap();
			drop(trie);

			(
				pallet_remote_proxy::RemoteProxyProof::RelayChain {
					proof: db.drain().into_values().map(|d| d.0).collect(),
					block: 1,
				},
				1,
				root,
			)
		}
