### Title
Stale-cache dereference crash when reverting AA response units already stabilized by a nested main-chain rebuild - ([File: aa_composer.js])

### Summary
The reported GPAC CVE is a use-after-free where a PSI/PMT table object is freed by one code path (table re-processing) while a stale reference to it is dereferenced by another path, crashing the parser. The closest reachable analog in ocore is a stale-reference crash in the AA-response rollback path: `revertResponsesInCaches()` in `aa_composer.js` and `forgetUnit()` in `storage.js` unconditionally dereference `storage.assocUnstableUnits[unit]`, but that same unit can already have been removed from `assocUnstableUnits` (moved to `assocStableUnits`) by a nested, synchronous main-chain stabilization that happens *while the same AA trigger chain is still being processed*. This causes an uncaught `TypeError` inside a `mutex.lock("write")` critical section, which crashes the full node process — a concrete denial of service reachable by any unprivileged AA trigger sender / AA author.

### Finding Description
When an AA trigger is processed, each successful response unit is written via `writer.saveJoint()` inside `validateAndSaveUnit()` [1](#0-0) . `writer.saveJoint()` synchronously calls `main_chain.updateMainChain()` on every saved unit [2](#0-1) , which can immediately stabilize prior AA-response units and move them from `storage.assocUnstableUnits` into `storage.assocStableUnits`, deleting them from the unstable cache: `arrStabilizedUnits.forEach(function(unit){ delete storage.assocUnstableUnits[unit]; });` [3](#0-2) . This is a documented, known behavior — the test suite even contains a `fixCache()` hack acknowledging that "an AA-response unit can rebuild the MC to itself" on small-witness networks [4](#0-3) .

If a *later* message/secondary AA in the **same** primary-trigger chain then fails (e.g. storage-size limit exceeded, secondary AA bounces, `max_aa_responses` exceeded), `finish()`/`handleSecondaryTriggers()` invoke `revert(err)` [5](#0-4) [6](#0-5) , which for the primary trigger calls `revertResponsesInCaches(arrResponses)` [7](#0-6) .

`revertResponsesInCaches()` blindly reads `storage.assocUnstableUnits[first_unit].parent_units` and then calls `storage.forgetUnit` on every response unit collected so far, including ones already stabilized in the interim:
```
var objFirstUnit = storage.assocUnstableUnits[first_unit];
var parent_units = objFirstUnit.parent_units;
arrResponseUnits.forEach(storage.forgetUnit);
``` [8](#0-7) 

`storage.forgetUnit()` itself unconditionally dereferences the unstable-cache entry before ever checking whether the unit is already stable:
```
function forgetUnit(unit){
	console.log('forgetting unit '+unit);
	if (!conf.bLight){
		console.log('parents', assocUnstableUnits[unit].parent_units);
		assocUnstableUnits[unit].parent_units.forEach(function(parent_unit){ ... });
	}
	...
	delete assocUnstableUnits[unit];
	if (!conf.bLight && assocStableUnits[unit])
		throw Error("trying to forget stable unit "+unit);
	...
}
``` [9](#0-8) 

The explicit guard `throw Error("trying to forget stable unit ...")` shows the developers anticipated the "already stabilized" case, but the guard is placed *after* the unguarded `assocUnstableUnits[unit].parent_units.forEach(...)` dereference. If `assocUnstableUnits[unit]` is `undefined` (because the unit was already promoted to `assocStableUnits` by the nested stabilization described above, or `objFirstUnit` is `undefined` in `revertResponsesInCaches`), the code throws an unhandled `TypeError: Cannot read properties of undefined (reading 'parent_units')` instead of the intended, safely-thrown `Error`. This happens synchronously inside the process while a database write-lock (`mutex.lock("write")`, implicit in the AA-trigger/`writer.saveJoint` flow) is held, and there is no repo-wide `process.on('uncaughtException')` handler that gracefully recovers state [10](#0-9) . This mirrors the CVE-2019-20628 root cause: a cached/table object is freed on one code path (stabilization removing it from `assocUnstableUnits`) while another code path (the rollback logic holding a stale unit list captured earlier) dereferences it without validating it still exists.

### Impact Explanation
An uncaught exception thrown deep inside AA-trigger processing while a write lock is held crashes the ocore full-node process (no graceful catch exists for this code path). Because AA trigger processing happens automatically for every unit that pays to an AA address, any unprivileged user can post a unit/trigger that drives this code path. A crashed node stops confirming/processing any further units until manually restarted, i.e., "a network unable to confirm new units" on affected nodes, and if triggered broadly (e.g. hubs/witnesses running the AA logic), this constitutes a network-wide availability impact — matching the required Medium+ severity bar (node disagreement/DoS on validity processing).

### Likelihood Explanation
Triggering requires: (1) a small-witness / fast-stabilizing network configuration (explicitly acknowledged as a real, tested scenario in `fixCache()`), (2) a primary AA trigger whose execution produces multiple chained AA-response units such that an early response stabilizes onto the main chain before a later step in the same trigger chain fails and forces `revert()`. Both preconditions are achievable by a determined AA author/trigger sender crafting a multi-hop AA chain (factory/remote-call AAs are demonstrated as reachable patterns in the existing test suite, e.g. AAs that create and call other AAs, or call remote getters that can bounce) combined with deliberately exceeding `max_aa_responses`/storage-size limits on a later hop to force the revert path. This makes the bug reachable, though it depends on witness-count/stabilization-timing conditions that are more easily satisfied on smaller/private networks than on the main Obyte network with many witnesses.

### Recommendation
- In `storage.js`'s `forgetUnit()`, guard the initial dereference: check `if (assocUnstableUnits[unit])` before accessing `.parent_units`, and if the unit is not present in `assocUnstableUnits` (already stable or already forgotten), skip cleanly (or `return`) rather than throwing an unguarded `TypeError`. Keep (or improve) the explicit "trying to forget stable unit" check to run before any dereference.
- In `aa_composer.js`'s `revertResponsesInCaches()`, defensively check that `storage.assocUnstableUnits[first_unit]` exists before reading `.parent_units`, and filter `arrResponseUnits` to only units still present in `assocUnstableUnits` before calling `storage.forgetUnit`.
- More broadly, audit all callers of `forgetUnit`/`fixIsFreeAfterForgettingUnit` (`aa_composer.js`, `joint_storage.js`, `storage.js` archiving functions) for the same "captured unit list may become stale due to nested stabilization" pattern, and add existence checks before dereferencing cached unit props.

### Proof of Concept
1. Configure/run ocore in a low-witness-count test network (as used by `test/aa_composer.test.js`, which documents that AA-response units can synchronously rebuild the main chain onto themselves).
2. Deploy a primary AA that, in a single trigger execution, produces at least two chained AA response units (e.g. a "factory" AA that creates a child AA and immediately sends to it, as in the `AA with generated definition of new AA and immediately sending to this new AA` test pattern) [11](#0-10) , such that the first response unit gets stabilized onto the main chain during `writer.saveJoint`/`main_chain.updateMainChain` processing of a subsequent response.
3. Craft the chain so a later secondary AA invocation fails after that point (e.g. exceed `aa_addresses.storage_size`, or make the secondary AA `bounce()`, or exceed `max_aa_responses`), forcing `handleSecondaryTriggers`'s error path to call `revert()` → `revertResponsesInCaches(arrResponses)` on the primary trigger.
4. Observe that `storage.assocUnstableUnits[first_unit]` (or a later unit in `arrResponseUnits`) is `undefined` because it was already moved to `assocStableUnits`, causing `objFirstUnit.parent_units` (or `assocUnstableUnits[unit].parent_units` inside `forgetUnit`) to throw an unhandled `TypeError`, crashing the node process while holding the write lock.

Note: I was not able to execute this scenario in a live environment (no code execution tooling available in this session); the analysis is based on static tracing of the exact call chain (`writer.saveJoint` → `main_chain.updateMainChain` → `markMcIndexStable` deleting from `assocUnstableUnits`, and `aa_composer.js` `revert`/`revertResponsesInCaches` → `storage.forgetUnit`) and the existing test-suite comment that explicitly documents the underlying stabilization race as a real, previously-encountered condition.

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
