### Title
RAY-scaled debt overflow permanently freezes a market - ([File: common/src/rates/scaling.rs])

### Summary

High. A sufficiently large market can reach the representable RAY-value limit before its borrow index reaches the configured index ceiling. Once that happens, the next index synchronization panics in `scaled_to_original`, and every later operation that must accrue the market fails with the same error. The regression test demonstrates that `update_indexes`, `withdraw`, and `repay` all become unavailable after this state is reached. [1](#0-0) [2](#0-1) 

### Finding Description

The protocol stores debt as RAY-scaled shares and converts it to current debt through `scaled_to_original(env, scaled, index)`, which calls `Ray::mul`. [1](#0-0) 

The multiplication ultimately produces an `i128` result. The widened intermediate arithmetic is exact, but `to_i128` panics with `GenericError::MathOverflow` whenever the final value cannot be represented by `i128`. [3](#0-2) [4](#0-3) 

The borrow-index ceiling therefore does not bound the product `scaled_debt * borrow_index`. A book with sufficiently large scaled debt can cross the `i128` result limit while its index remains below `MAX_BORROW_INDEX_RAY`. [5](#0-4) 

The reachable path is:

1. An unprivileged supplier calls `supply` with a very large admitted amount of an 18-decimal asset.
2. An unprivileged borrower calls `borrow` for a high-utilization amount against separate collateral.
3. Any unprivileged caller repeatedly calls `update_indexes` as ledger time advances.
4. A later index update evaluates `scaled_debt * borrow_index`, produces a value outside `i128`, and panics.
5. Because the panic occurs during mandatory accrual, subsequent calls to `withdraw`, `repay`, `liquidate`, and `update_indexes` for that market fail before their state transitions execute. [6](#0-5) 

The regression test uses a one-billion-token, 18-decimal market, borrows 98% of it, and shows that the market hits the RAY-value ceiling before the borrow-index ceiling. [7](#0-6) 

### Impact Explanation

This permanently freezes all funds and debt associated with the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and index synchronization cannot recover because the same overflow is evaluated before those operations complete. [8](#0-7) 

This is not merely caller-controlled transaction failure. The overflow is stored-state-dependent: once the market crosses the value ceiling, every subsequent caller encounters the same accrual panic. [4](#0-3) [8](#0-7) 

### Likelihood Explanation

The attacker does not need authority, leaked keys, malformed parameters, or contract upgrades. The attack only requires enough capital to create a very large admitted position and drive utilization high enough for interest growth to carry `scaled_debt * borrow_index` beyond `i128`. [9](#0-8) 

Likelihood depends on the deployed asset's decimals, cap, available liquidity, rate curve, utilization, and market lifetime. Those constraints make exploitation capital-intensive, but they do not make it privileged; the cap validation bounds the token-unit input, not the future product of scaled debt and index. [10](#0-9) [11](#0-10) 

### Recommendation

Bound the scaled-value product, not just the token amount and index. Before accrual commits or before the total-debt read is evaluated, compute whether `scaled_debt * borrow_index / RAY` fits `i128`. If the value is near the limit, either cap the book's total value with a deterministic unwind path or reject further debt/index growth before crossing the unrecoverable boundary.

Admission should also enforce a combined invariant based on token decimals, supply/debt cap, initial shares, and the highest permitted index. Listing validation should reject configurations whose admitted scaled debt can exceed `i128::MAX` before the index ceiling can engage.

Add the existing regression scenario to release gating and cover every mandatory accrual entrypoint: `update_indexes`, `withdraw`, `repay`, `liquidate`, `borrow`, and `supply`.

### Proof of Concept

The repository contains a reproducing test named `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [11](#0-10) 

Conceptual call sequence:

```text
supply(BOB, BIG18, 1_000_000_000 * 10^18)
supply(ALICE, COL, sufficient collateral)
borrow(ALICE, BIG18, 98% of BIG18 supply)
advance ledger time
update_indexes([BIG18]) -> GenericError::MathOverflow
withdraw(BOB, BIG18, 1) -> GenericError::MathOverflow
repay(ALICE, BIG18, positive_amount) -> GenericError::MathOverflow
```

The test verifies that the observed borrow index is still below `MAX_BORROW_INDEX_RAY`, proving that the existing index cap does not prevent the fatal scaled-value overflow. [12](#0-11)

```rust
/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
/// Converts an `I256` to `i128`, panicking with `GenericError::MathOverflow` if it does not
/// fit.
fn to_i128(env: &Env, val: &I256) -> i128 {
    val.to_i128()
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```
