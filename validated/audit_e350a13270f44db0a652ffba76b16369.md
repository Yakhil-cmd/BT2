## Analog Found: Double resolution of duplicated XCM asset imbalances on the success/non-transactional path of `transactional_process`

### Title
Un-forgotten `unsafe_clone()` imbalance backups in `XcmExecutor::transactional_process_with_custom_rollback` cause double-resolution (double-mint/double-burn) of holding/fees imbalances - ([File: polkadot/xcm/xcm-executor/src/lib.rs])

### Summary
The strongSwan CVE's root cause is a clone operation that does not neutralize one of the two resulting copies of a resource, so both copies get destroyed/resolved and the destructor runs twice on data that should have owned it only once. The Polkadot SDK analog is in the XCM executor's holding/fees backup mechanism: `BackupAssetsInHolding::safe_backup` deliberately performs an `unsafe_clone()` of every fungible imbalance object currently in holding/fees [1](#0-0) , explicitly documented as unsafe and requiring that "either the backup or the original are dropped without resolving any duplicated imbalances" [2](#0-1) . The type provides a `safe_drop()` helper that must be called manually to neutralize the duplicate before it is dropped [3](#0-2) .

### Finding Description
`transactional_process_with_custom_rollback` is the function used to wrap essentially every stateful XCM instruction (`WithdrawAsset` via `transactional_process`, `DepositAsset`, `DepositReserveAsset`, `PayFees`, `ExchangeAsset`, `BuyExecution`, etc.) [4](#0-3) [5](#0-4) . Its implementation is:

```
fn transactional_process_with_custom_rollback(...) -> Result<(), XcmError> {
    let mut backup_holding = BackupAssetsInHolding::safe_backup(&self.holding);
    let mut backup_fees = BackupAssetsInHolding::safe_backup(&self.fees);
    let result = Config::TransactionalProcessor::process(|| f(self));
    if Config::TransactionalProcessor::IS_TRANSACTIONAL && result.is_err() {
        backup_holding.restore_into(&mut self.holding);
        backup_fees.restore_into(&mut self.fees);
        on_rollback(self);
    }
    result
}
``` [6](#0-5) 

`backup_holding`/`backup_fees` only ever get their imbalances neutralized (`restore_into`, which `mem::swap`s the original into `target`, leaving the *unsafe-cloned* backup content behind to be dropped) when `IS_TRANSACTIONAL && result.is_err()`. On the success path (`result.is_ok()`), and whenever a configured `TransactionalProcessor` reports `IS_TRANSACTIONAL == false`, `backup_holding` and `backup_fees` simply fall out of scope at the end of the function. Nothing calls `BackupAssetsInHolding::safe_drop()` in that path, so the `unsafe_clone()`-duplicated `Box<dyn ImbalanceAccounting>` entries retain their full (non-zero) amount and are destroyed via their ordinary `Drop` impl, which invokes `OnDrop::handle(asset, amount)` a second time for the same value [7](#0-6) . `unsafe_clone()` itself is explicitly documented as producing "double accounting of the imbalance" that only balances out if "one of the duplicates" calls `forget_imbalance()` [8](#0-7) ; in the success/non-transactional path of `transactional_process_with_custom_rollback` neither duplicate ever does.

This is the direct analog of the strongSwan bug: the cloning primitive (`unsafe_clone`) creates a byte-for-byte duplicate resource without neutralizing either copy's ownership state, and the caller destroys both the "live" state (already correctly resolved through the normal XCM instruction path, e.g. by `saturating_take`/`subsume_assets`) and the untouched duplicate, causing the underlying imbalance-resolution logic (analogous to `free()`) to run twice on what is conceptually the same value.

The pattern documented elsewhere in the same codebase confirms the developers are aware this class of bug is dangerous and must be handled explicitly: `pallet_xcm::DropAssets::drop_assets` and `ClaimAssets::claim_assets` go out of their way to call `forget_imbalance()` / `unsafe_clone()` + immediate drop in carefully paired ways specifically to avoid unbalancing total issuance [9](#0-8) [10](#0-9) . The executor's own backup/rollback path lacks the equivalent discipline outside of the failure branch.

### Impact Explanation
If reachable with a non-empty holding/fees register at the point a transactional instruction (e.g. `PayFees`, `DepositAsset`, `ExchangeAsset`, `BuyExecution`) succeeds, the un-neutralized backup's `Drop` invokes the pallet's imbalance-drop handler a second time for an amount that was already correctly resolved through the normal (non-backup) path. Depending on which concrete `Imbalance`/`OnDrop` handler is wired in (balances/assets pallets), this manifests as either unbacked/duplicate issuance or duplicate burning of `TotalIssuance` accounting relative to actual account balances - a total-issuance integrity break reachable from ordinary, permissionless XCM execution (e.g. via `pallet_xcm::execute` or any XCM program that reaches `DepositAsset`/`PayFees`/`BuyExecution`).

### Likelihood Explanation
Every multi-step XCM program with a `WithdrawAsset`/`ReserveAssetDeposited` followed by an instruction wrapped in `transactional_process`/`transactional_process_with_custom_rollback` (i.e. almost any XCM program that moves fungible assets) exercises this code path on its success branch, and no privileged role, governance action, or malicious peer is required — only a normal user submitting a valid XCM message through `pallet-xcm`'s permitted execute/send surface. The `IS_TRANSACTIONAL` guard suggests intent to only protect the rollback branch, but nothing forces `safe_drop()` on the non-rollback branch, so the bug is structural rather than input-dependent, which raises likelihood, but the exact quantitative effect and whether it is neutralized elsewhere (e.g., a possible custom `Drop for BackupAssetsInHolding` outside the section retrieved, or offsetting semantics in specific `OnDrop::handle` implementations for balances/assets) could not be fully confirmed with the tools available in this session.

### Recommendation
Ensure `BackupAssetsInHolding` cannot be dropped while still holding un-neutralized duplicated imbalances in *any* code path — either add a `Drop` impl on `BackupAssetsInHolding` that unconditionally calls `safe_drop()`-equivalent logic, or explicitly call `backup_holding.safe_drop()` / `backup_fees.safe_drop()` on every path in `transactional_process_with_custom_rollback` that does not call `restore_into` (i.e., the success path and the `!IS_TRANSACTIONAL` path).

pub trait UnsafeConstructorDestructor<Balance> {
	/// Duplicates/clones the imbalance type, effectively leading to double accounting of the
	/// imbalance.
	///
	/// Warning: Use with care!!! one of the duplicates should call `self.forget_amount()` for the
	/// double-tracking to be removed.
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<Balance>>;
	/// Forgets about the inner imbalance. Drops the inner imbalance without actually resolving it.
	/// Usually implemented by simply setting the imbalance amount to `zero`.
	///
	/// Note this is not equivalent `mem::forget()` as the destructor is still called, and memory is
	/// freed, but imbalance amount to resolve is zero/noop.
	///
	/// Returns the amount "forgotten".
	fn forget_imbalance(&mut self) -> Balance;
}

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
