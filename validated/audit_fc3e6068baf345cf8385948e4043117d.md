### Title
Opaque swap routes allow nested venue code to drain caller wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-controlled opaque `swap` bytes and executes them through the configured router, while a malicious route-selected contract can add an unrelated `caller` token transfer to the signed authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`StrategySwap` is only a `Bytes` payload, so the controller does not structurally validate the venues, pool addresses, or token calls encoded in the route. [2](#0-1) 

`swap_collateral` authenticates the caller, verifies account ownership or delegation, withdraws the requested collateral into controller custody, and passes the user-supplied route to the swap helper. [3](#0-2) 

`swap_tokens` checks only that the payload is non-empty, authorizes one exact transfer from the controller to the configured router, and forwards the opaque payload to `execute_strategy`; it does not constrain which contracts the route invokes or which additional authorization children the transaction contains. [4](#0-3) 

The exact-transfer authorization protects only the controller’s `token_in` grant and contains no sub-invocations, but it does not prevent route-selected code from requesting a separate transfer authorized by the original caller. [5](#0-4) 

A route hop can therefore invoke a contract that calls `token.transfer(victim, attacker, amount)` for an arbitrary wallet token; simulation records that call as a child of the victim’s `swap_collateral` authorization, and signing the generated tree authorizes the theft. [6](#0-5) [7](#0-6) 

The malicious route can simultaneously return a valid swap output, so the lending operation completes and the account receives the expected collateral while the unrelated wallet transfer also executes. [8](#0-7) 

### Impact Explanation
An attacker can steal unrelated tokens held directly by the account owner or delegate, rather than merely manipulating the routed `token_in` amount. [9](#0-8) 

The tested path transfers the victim’s entire unrelated wallet-token balance while producing the fair swap output and successful collateral deposit. [8](#0-7) 

### Likelihood Explanation
Any unprivileged user-reachable strategy entrypoint that forwards route bytes can carry the malicious payload, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and the conversion paths in `multiply`. [10](#0-9) [11](#0-10) 

Exploitation requires the victim to submit a malicious route and sign the authorization tree generated by simulation, but no protocol privilege, leaked key, upgrade, oracle manipulation, or pre-existing token allowance is required. [12](#0-11) 

A malicious route source can make the poisoned child difficult for a user to notice because the top-level arguments and economic swap result remain plausible. [13](#0-12) 

### Recommendation
Restrict route-selected pool contracts to a governance-managed allowlist or otherwise prevent router venue calls from invoking arbitrary payload-supplied contract addresses. [14](#0-13) 

Until routes are constrained on-chain, clients must decode every route payload and reject any simulated authorization tree containing children other than the expected controller-authorized input transfer. [5](#0-4) 

### Proof of Concept
1. The victim owns a debt-free account with USDC collateral and also holds an unrelated wallet token. [15](#0-14) 

2. The attacker supplies a `swap_collateral` route naming a rogue hop contract; that contract’s `swap` function transfers the victim’s unrelated wallet token to the attacker. [16](#0-15) [6](#0-5) 

3. The victim calls `swap_collateral(caller=victim, account_id, current=USDC market, amount=50_000_000_000, new=ETH market, swap=rogue_route)`. [1](#0-0) [17](#0-16) 

4. Simulation records the unrelated `wallet_token.transfer(victim, attacker, WALLET_BALANCE)` as a child of the victim’s `swap_collateral` authorization. [13](#0-12) 

5. If the victim signs the generated tree, the transaction succeeds: the victim’s wallet balance becomes zero, the attacker receives `WALLET_BALANCE`, and the account receives the expected ETH supply. [18](#0-17)
