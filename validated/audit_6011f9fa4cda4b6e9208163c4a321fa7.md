### Title
Webhook signature verification is keyed on `repository.owner.login` while every handler acts on `repository.full_name` (or `stacks`), allowing forged events for a repository under an org with no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check with using one field of the untrusted payload (`repository.owner.login` / `organization.login`), but every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, `Handler#repository_name`) resolves the target `Repository`/`Stack` from a *different* field of the same payload (`repository.full_name`). These two fields are never checked for consistency, so the identity used to authorize the request and the identity used to act on it can diverge — the same "evaluate the trust anchor once, act on a different value later" pattern as the Vyper double‑evaluation bug, applied to a payload field instead of a contract address.

### Finding Description
`before_action :verify_signature` computes: [1](#0-0) 

`repository_owner` (the value that selects which `GitHubApp`/`webhook_secret` is used) comes from: [2](#0-1) 

`Shipit.github(organization:)` looks up the per‑organization config keyed by this attacker‑supplied string: [3](#0-2) 

Critically, `verify_webhook_signature` treats a blank `webhook_secret` as automatically valid: [4](#0-3) 

`webhook_secret` is explicitly documented as optional per organization: [5](#0-4) 

Meanwhile, every webhook handler that decides *which* repository/stack the event actually applies to reads a completely different payload field, `repository.full_name`: [6](#0-5) 

For example `PushHandler`, `StatusHandler` (matches by `sha` globally), `CheckSuiteHandler`, and the `PullRequest::*` handlers all resolve target state from `repository.full_name` / global commit lookup, never from `repository.owner.login`: [7](#0-6) [8](#0-7) 

In a multi‑organization Shipit deployment (documented, supported configuration where the `github:` section is keyed per org, e.g. `test/dummy/config/secrets_double_github_app.yml`), if **any** configured organization has `webhook_secret` left blank (a documented default — "webhook_secret: # nil"), then: [9](#0-8) 

an unauthenticated attacker can POST to `/webhooks` with:
- `repository.owner.login` = the name of the org that has no `webhook_secret` configured (or `organization.login` for org‑scoped events like `membership`) → `verify_signature` calls `Shipit.github(organization: that_org)`, whose `verify_webhook_signature` short‑circuits `true` regardless of body/signature — no credential of any kind is required.
- `repository.full_name` = `"<other-org>/<target-repo>"` for a completely different, secret‑protected organization → the handler dispatched in `create` resolves the actual `Repository`/`Stack` via this field, entirely decoupled from the org whose (absent) secret was checked. [10](#0-9) 

The equality that should hold but is broken is:
`organization whose signature was verified == organization owning the repository/stack the handler mutates`

Before the attack: only requests carrying a valid HMAC for a given org's secret can affect that org's repositories.
After the attack: any org configured without a `webhook_secret` becomes a skeleton key allowing forged webhook events (push notifications, commit statuses, check‑suite completions, pull‑request open/label/reopen transitions, membership/team changes) to be injected against any *other* org's repositories tracked by the same Shipit instance, without ever presenting a valid signature for that target org.

### Impact Explanation
This breaks the deployment‑trust binding between "organization that authenticated" and "repository that is written," matching the report's specified analog exactly. Concretely reachable, credential‑free consequences on a multi‑org instance with one unsecured org:
- Forged `status`/`check_suite` events can mark arbitrary commits on a victim stack as passing required CI checks (`StatusHandler#process`, `CheckSuiteHandler#process`), which can satisfy `ci.require` gates used to enable continuous deployment/merge-queue automation — an avenue to an unauthorized deploy or merge.
- Forged `push` events (`PushHandler`) can trigger `GithubSyncJob` against arbitrary stacks.
- Forged `pull_request`/`membership` events can create/archive review stacks or create arbitrary `Team`/`User` records tied to the target org.

This lands squarely in the report's Critical category ("an unauthorized deploy, rollback or merge") depending on how `ci.require`/continuous delivery is configured for the victim stack, and at minimum in the High category (unauthenticated manipulation of stack/task state) even where full auto-deploy isn't triggered.

### Likelihood Explanation
Requires: (1) a multi‑organization `github:` configuration (explicitly documented and supported), and (2) at least one configured org with no `webhook_secret` (the documented default value, and plausible for orgs added later or for internal/low‑risk orgs). Given that condition, exploitation needs zero credentials, tokens, or GitHub access — just a crafted HTTP POST to the public `/webhooks` endpoint with mismatched `repository.owner.login` / `repository.full_name` values. The unknown/uncertain factor is how commonly production deployments actually leave a `webhook_secret` blank for any org in a multi-org setup; this cannot be verified from the codebase alone since it depends on operator configuration, but the feature explicitly supports and does not warn against this combination.

### Recommendation
- In `WebhooksController#verify_signature`, require `webhook_secret` to be present for every configured organization (or at least for any organization used as a `repository_owner`), and reject unsigned requests when it's blank rather than treating it as implicitly trusted.
- Cross‑validate that `repository.owner.login`/`organization.login` (the value used to select the verifying `GitHubApp`) matches the owner segment of `repository.full_name` before dispatching to handlers, so the two payload readings can never diverge.
- Update `docs/setup.md` to state that `webhook_secret` is effectively mandatory once multiple GitHub organizations are configured, since a blank secret on any one organization defeats verification for cross‑repository event injection.

### Proof of Concept
Preconditions: Shipit configured with two orgs, `OpenOrg` (no `webhook_secret`) and `SecureOrg` (has repos tracked in Shipit, e.g. `SecureOrg/victim-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
(no X-Hub-Signature needed)

{
  "sha": "<victim-repo commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "SecureOrg/victim-repo",
    "owner": { "login": "OpenOrg" }
  }
}
```

- `verify_signature` computes `repository_owner = "OpenOrg"`, calls `Shipit.github(organization: "OpenOrg")`, and since `OpenOrg.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) — no valid signature is ever presented.
- `create` re-parses the body and dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` (global, not org-scoped) and calls `commit.create_status_from_github!(params)`, forging a passing CI status for a commit that belongs to `SecureOrg/victim-repo`, entirely bypassing `SecureOrg`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
