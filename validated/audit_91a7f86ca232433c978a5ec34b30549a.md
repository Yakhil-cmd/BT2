Based on the investigation, the strongest local admission analog to the PoolTogether "incentive vs. approval mismatch" bug is in Aptos's multisig transaction execution path, where the *approved* payload and the *executed* payload can diverge unless a specific feature flag is enabled.

### Title
Multisig transaction execution can run with a payload different from the one the owners approved - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction` is the VM-invoked prologue check that gates execution of a pending multisig transaction. It verifies quorum/timelock and, if the transaction was created via `create_transaction_with_hash` (payload stored off-chain as a hash), it checks the supplied `payload` against the stored `payload_hash`. However, when the transaction was created via `create_transaction` (full payload stored on-chain, `payload_hash = None`), the comparison between the **stored** `payload` and the **caller-supplied** `payload` used at execution time is only performed when the transient feature `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled.

### Finding Description
`create_transaction` stores the full approved payload on-chain: `payload: option::some(payload), payload_hash: option::none()` [1](#0-0) . At execution time, `validate_multisig_transaction(owner, multisig_account, payload)` receives a caller-supplied `payload` argument that is BCS/hash-checked only in the `payload_hash.is_some()` branch [2](#0-1) . The check that the caller-supplied `payload` matches the on-chain-stored `transaction.payload` is gated behind `features::abort_if_multisig_payload_mismatch_enabled()`: [3](#0-2) 
The feature is explicitly documented as a "fix": *"Whether the multisig v2 fix is enabled. Once enabled, the multisig transaction execution will explicitly abort if the provided payload does not match the payload stored on-chain."* [4](#0-3)  This wording confirms that without the flag active, the VM will execute whatever payload the calling owner supplies at execution time, regardless of whether it matches what the other owners voted to approve. On the VM execution side, `execute_multisig_transaction` similarly defaults to using the caller-provided `TransactionExecutableRef` and only enforces strictness conditionally on the same flag [5](#0-4) .

### Impact Explanation
This is a pre-admission/pre-execution binding mismatch: the multisig approval process (owners voting via `create_transaction`/`vote_transanction`) is supposed to bind approval to a specific `payload`, but the prologue does not enforce that binding for payload-stored (non-hash) transactions unless a specific feature flag is turned on. Any owner with enough approvals to hit quorum (including a single malicious owner in an n-of-m setup, or any owner colluding to submit at the execution step) can submit a different `payload` than what was approved, and it will execute under the multisig account's signer, moving funds or calling arbitrary entry functions that were never actually voted on. This is a direct "wrong signer set/wrong approval set" impact matching the admission gate criteria (approval validation accepting the wrong approval set).

### Likelihood Explanation
This requires the `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature to be disabled on the target network. This is a genuinely gated feature flag (id 70), and I was unable to fully confirm from the truncated `default_features()` list whether it ships enabled by default in current builds; that determination requires checking the full feature list and/or genesis/mainnet feature-flag configuration, which is outside what I could exhaustively verify from search snippets alone. If it is disabled (as its own doc comment strongly implies it is meant to be rolled out gradually), the vulnerability is live; if it is already permanently enabled across all networks, the exploit path is closed and only a "gate off" report is valid documentation of past risk rather than exploitable now.

### Recommendation
Make payload/hash verification for `create_transaction`-style (full-payload) multisig transactions unconditional in `validate_multisig_transaction`, removing the `abort_if_multisig_payload_mismatch_enabled()` gate, so that admission always enforces "executed payload == approved payload" regardless of feature-flag state. Confirm current mainnet/testnet feature-flag state for `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` (feature id 70) to determine current exposure.

### Proof of Concept
1. Owner A creates a multisig account requiring 2-of-3 signatures.
2. Owner A calls `create_transaction(multisig_account, payload_benign)` — a harmless transfer of 1 APT to Owner B.
3. Owners A and B approve (2 approvals reached).
4. If `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled, Owner A executes the transaction supplying `payload_malicious` (e.g., transferring the entire multisig balance to Owner A) instead of `payload_benign`.
5. `validate_multisig_transaction` skips the payload-match check (since `transaction.payload_hash` is `None` and the feature flag gating the payload-equality check is off), and the VM executes `payload_malicious` under the multisig account's signer, draining funds that were never approved for that action [6](#0-5) .
