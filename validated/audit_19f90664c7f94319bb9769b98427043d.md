### Title
Multi-authored trigger units misdirect AA refunds/responses to the wrong author - ([File: aa_composer.js])

### Summary
The external report describes a class of bug where a payment/refund system defaults the recipient of returned funds to an incidental identity present at execution time (`tx.origin`/bootloader) rather than the intended beneficiary (the actual depositor), causing loss of funds whenever the triggering transaction is not a simple single-party call. In `ocore`, the analogous mechanism is `getTrigger()` in `aa_composer.js`, which derives the address that all AA bounce fees and response payments (`trigger.address`) are sent to purely from `objUnit.authors[0].address` — i.e., the alphabetically-first co-author of the triggering unit — rather than from whichever address actually funded/paid for the unit or is the intended counterparty.

### Finding Description
When a unit triggers an Autonomous Agent, the AA composer builds the `trigger` object with: [1](#0-0) 
`trigger.address = objUnit.authors[0].address`. This value is used everywhere the AA framework refers to "the sender" of the trigger — most importantly for bounce refunds: [2](#0-1) 
and it is the value `{trigger.address}` that AA oscript templates use in essentially all sample/response payment logic, e.g. `simple_aa.oscript`, `just_a_bouncer.oscript`, `bounce_half_of_balance.oscript`.

The unit's `authors` array can legitimately contain more than one distinct, unrelated address: `composer.js`'s `composeJoint()` supports "multi-authored" units where `arrFromAddresses = _.union(arrSigningAddresses, arrPayingAddresses).sort()`, and multiple independent addresses can jointly author/pay for a single unit: [3](#0-2) 
The change output (i.e., the address that actually receives the payer's change/refund at composition time, and thus is the economically correct "sender" whose funds should be returned) is explicitly chosen by the composer via `arrChangeOutputs[0].address`, and is even used as the default headers-commission recipient for multi-authored units:
`else if (bMultiAuthored) objUnit.earned_headers_commission_recipients = [{address: arrChangeOutputs[0].address, ...}]`.

However, `getTrigger()` ignores this change-address/payer semantics entirely and just takes `authors[0]` — sorted alphabetically (`validateAuthors` in `validation.js` enforces `author.address <= prev_address` rejection, i.e. authors must be sorted by address): [4](#0-3) 
So if two unrelated addresses A (e.g. `AAAA...`) and B (e.g. `ZZZZ...`) jointly author/sign a unit that pays an AA (B being the actual depositor/payer whose change output returns to B), any funds the AA sends back to "the sender" (via `bounce()` or an oscript template using `{trigger.address}`) will be sent to A instead of B — the party with no economic stake in the payment.

This mirrors the reported bug class precisely: a payment/refund mechanism silently substitutes an incidental "on-unit" identity (first sorted author, analogous to `tx.origin`/bootloader) for the actual party who funded/is entitled to the transaction, whenever the trigger is not a simple single-author call.

### Impact Explanation
Any user who crafts (or is convinced to co-sign) a multi-authored unit that pays an AA can cause that AA's bounce fees, refunds, or oscript-driven response payments (which almost universally target `{trigger.address}`) to be redirected to an author of their choosing, rather than to the address that actually funded the AA trigger. This allows a malicious co-author to divert funds intended for another co-author/depositor — a direct fund-loss/fund-theft vector reachable by an ordinary, unprivileged AA-trigger sender. Because virtually every published AA template (bouncers, escrow-like contracts, DEX-style AAs) returns unused/refunded amounts to `trigger.address`, this affects a broad class of deployed AAs whenever a multi-author trigger unit is used.

### Likelihood Explanation
Composing a multi-authored unit (multiple independent addresses as `authors`) is a fully supported, ordinary feature of `composer.js` (`arrSigningAddresses`/`arrPayingAddresses` union), not a privileged or exotic path. Any unprivileged wallet user (or two colluding/careless users co-signing a joint payment) can trigger this by simply sending a payment to an AA from a unit with more than one author. No node/hub/network privileges are required — only that a unit with 2+ sorted authors reaches an AA as a trigger. This makes the likelihood high in any scenario where multi-authored (jointly signed, non-shared-address) payments to AAs are used.

### Recommendation
Do not rely on `objUnit.authors[0].address` as the canonical "sender"/refund target in `getTrigger()`. Instead:
- Either reject/disallow multi-authored (non-shared-address) units as valid AA triggers, since the AA logic has no unambiguous way to determine the intended beneficiary among unrelated co-authors, or
- Derive `trigger.address` from the actual paying address(es)/change-output address of the triggering unit's payment message (mirroring the `arrChangeOutputs[0].address` logic already used by the composer for headers-commission distribution) rather than from the alphabetically-first author, or
- Explicitly require (and validate) an unambiguous single beneficiary address to be specified in multi-authored trigger units when they pay an AA, so that bounce/response payments cannot be silently redirected to an unrelated co-author.

### Proof of Concept
1. Address A = `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA` (alphabetically first), Address B = `ZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZ` (the actual depositor).
2. B composes a payment to an AA (e.g. `simple_aa.oscript`, which returns `trigger.output[[asset=base]] - 500` to `{trigger.address}`), but asks A to co-sign as an additional, unrelated author via `composer.composeJoint({signing_addresses: [A], paying_addresses: [B], outputs: [...]})`, producing a `bMultiAuthored` unit whose `authors` array (sorted) is `[A, B]` and whose change output correctly returns to B.
3. `aa_composer.getTrigger()` sets `trigger.address = objUnit.authors[0].address` = A (see `aa_composer.js:375-376`).
4. The AA's response payment (`{address: "{trigger.address}", amount: "{trigger.output[[asset=base]] - 500}"}`) is sent to A, not B — despite B being the party who funded the payment and who should receive the AA's output/refund.
