### Title
Missing global de-duplication of Bitcoin lockup outpoints allows the same L1 UTXO proof to be replayed across multiple sBTC stake registrations - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `validate-l1-lockup` / `verify-l1-lockups` functions verify that a submitted Bitcoin transaction output really locks sats into the expected timelock script, but the only duplicate-outpoint check (`seen-outpoints`) is a list that is created fresh inside a single call's `fold` and is never persisted to contract storage. [1](#0-0) [2](#0-1) 

### Finding Description
`verify-l1-lockups` builds the initial fold accumulator with `seen-outpoints: (list)` for every invocation, and `validate-l1-lockup` only checks `(index-of? seen-outpoints outpoint)` against that same in-call accumulator before appending the outpoint to it. [3](#0-2) [4](#0-3) 
Nothing in this code path writes the outpoint (txid, output-index) to a persistent map, and my search for a map keyed on "outpoint" across the repo turned up no other definition guarding this — the only matches for "outpoint" are inside `pox-5.clar`'s local fold logic. This means the duplicate check only prevents the same outpoint from appearing twice *within one list of up to 10 outputs in a single call*; it does nothing to prevent the identical proof (same Bitcoin txid/output-index/header/merkle path) from being resubmitted in a second, independent call to credit sats a second time. Since the credited `sum` from `verify-l1-lockups` feeds directly into staked-share accounting (`add-staker-to-bond-for-cycle`, `total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`), an attacker who locks BTC once can replay the exact same lockup proof in additional registration calls (e.g., for a new/second bond-index, or a repeated registration transaction) to be credited with sats-staked shares multiple times, without ever locking additional BTC. [5](#0-4) 

This breaks the equality between "L1 sats actually locked in this staker's timelock script" and "sats credited toward stacking shares/rewards" in pox-5 — the double-counting-a-commitment class explicitly in scope.

### Impact Explanation
If confirmed reachable from an external registration entry point, this allows a staker to inflate their signer/staker share of the reward pool (and thus their share of sBTC rewards distributed via `calculate-rewards`/`get-rewards`) without locking the corresponding additional BTC — i.e., unbacked crediting of stake and reward dilution against honest stakers. This matches the Critical impact bucket ("double-counting a commitment or reward", "theft ... of sBTC rewards").

### Likelihood Explanation
Exploitability depends entirely on how many times a legitimate operation allows `verify-l1-lockups`/`validate-l1-lockup` to be invoked with attacker-supplied proof data referencing the same underlying Bitcoin transaction (e.g., across separate bond registrations, re-registrations, or rollovers). I was not able to locate and fully trace the outer public entry point (e.g., a `register-*`/`process-lockup` function) within the remaining tool budget to confirm whether an additional gate outside `validate-l1-lockup` (such as a check that a given staker/bond hasn't already registered, or a nonce on the underlying `tx`) prevents resubmission. This is a material gap in my verification — the described bug is a real code-level absence of a global outpoint map, but whether the surrounding registration flow independently blocks resubmission of the exact same tx/output for a *different* bond-index or reward cycle remains unconfirmed from the snippets reviewed.

### Recommendation
Add a persistent contract map, e.g. `used-l1-lockup-outpoints: {txid: (buff 32), output-index: uint} -> bool`, and have `validate-l1-lockup` reject (or `map-insert`-guard) any outpoint that has already been credited in any prior call, not just within the current fold. This closes the replay gap regardless of the outer registration flow's own checks.

### Proof of Concept
1. Staker locks BTC in the correct timelock script for `bond-index`, producing a valid `(header, tx, output-index, leaf-hashes, tx-count, tx-index, amount, unlock-burn-height)` tuple.
2. Staker calls the pox-5 registration entry point (whatever public function ultimately calls `verify-l1-lockups`) with that lockup, receiving credited `sum` sats and staked shares for `bond-index`.
3. Staker calls the same (or an analogous) registration entry point a second time — e.g., registering a second protocol bond, or re-registering with `roll-sbtc`/rollover — supplying the identical `header`/`tx`/`output-index`/proof data. Because `seen-outpoints` is reinitialized to `(list)` on every call, `validate-l1-lockup` again accepts the outpoint and credits `sum` a second time in `add-staker-to-bond-for-cycle`, inflating `total-shares-staked-for-cycle` and the staker's own `staker-shares-staked-for-cycle` without any new BTC being locked.
