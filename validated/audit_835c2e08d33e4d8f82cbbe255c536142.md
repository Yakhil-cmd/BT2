### Title
`Cache::require_reserves` only checks the per-market cash book, so a withdrawal/borrow on one hub's market can drain the shared physical token balance and freeze sibling-market claims on the same asset - (File: contracts/pool/src/cache/cash.rs)

### Summary
The pool keeps a separate `cash` ledger per `HubAssetKey { hub_id, asset }` market, but all markets on the same token share one physical pool token balance (ADR-0002, "central custody, separate market books"). Every outbound path (`borrow`, `withdraw`, `claim_revenue`, `create_strategy`, `flash_loan`) validates only its own market's `cash` via `require_reserves` and then calls `token.transfer`. Nothing checks that the sum of all sibling markets' booked cash fits the actual `token.balance(pool)`. An unprivileged user who supplies collateral and borrows/withdraws on hub A's USDC market can therefore spend tokens that hub B's USDC book counts as its own cash. Subsequent `withdraw`/`borrow`/`claim_revenue`/`flash_loan`/liquidation payouts on the hub-B market revert inside `token.transfer` with insufficient balance, even though every per-market check passes — the same shape as the external report: a first-come claimant empties the shared pot and blocks later legitimate claimants.

### Finding Description
- `Cache::require_reserves` asserts `self.cash >= amount`, where `self.cash` is the single market's book (contracts/pool/src/cache/cash.rs:15-21). `transfer_out` then performs the raw token transfer with no aggregate or balance check (cash.rs:46-53).
- The same asset is explicitly listable in multiple hubs: deployed config already lists `USDC` on `hub_id: 1` and `USDC_HUB2` on `hub_id: 2` at the same token address `CBIELTK6...` (skills/xoxno-lending/addresses.md:140-148), and spoke 3 lists both markets simultaneously.
- Architecture docs confirm "Markets for one token in different hubs keep distinct books but share its pool balance" (docs/explanation/decisions.md ADR-0002; docs/reference/architecture.md:63-65).
- The codebase's own fuzz harness encodes the gap: `assert_cash_matches_balance` sums sibling-market cash against the real balance precisely because "a per-market `cash <= balance` check cannot detect an overdraw" (tests/fuzz/fuzz_targets/pool_native.rs:101-123) — i.e. overdraw is possible in production code and only asserted against in fuzzing.
- The backing guard `require_supply_for_debt`/shortfall check is computed per market (`floor(supply_value) - (cash + ceil(debt_value))`), so it never accounts for sibling cash either (docs/reference/formulas.md:88-100).
- Reachable path for a single unprivileged address: `supply` collateral + `borrow` (or plain `withdraw`) on the hub-1 USDC market via the controller drains the shared USDC balance down to that market's own limits; the hub-2 USDC market still reports positive `cash`, but any `withdraw`, `borrow`, `claim_revenue`, liquidation `SeizeMode::Transfer` payout, or `flash_loan` on it now reverts in `token.transfer` until hub-1 borrowers repay.

### Impact Explanation
Temporary freezing of user funds and partial protocol insolvency: hub-2 USDC suppliers, borrowers, liquidators, and revenue claims are all blocked even though their market book is fully solvent on paper. Because borrow only enforces a 200 BPS liquidation buffer within its own market (INV-ACCT-07 explicitly "does not guarantee enough cash for every subsequent liquidation"), a borrow-driven drain can also make an undercollateralized hub-2 account unliquidatable in `Transfer` mode, worsening bad-debt outcomes. The freeze lifts only when cross-market repayment refills the shared balance — there is no sibling-aware reservation.

### Likelihood Explanation
Requires only that the same token be listed in two hubs — already true on the deployed configuration (USDC on hubs 1 and 2). Any user with collateral can execute the drain through ordinary `borrow`; no privileged role, oracle manipulation, or timing dependency is needed. Cost is the borrower's own collateral and interest. The blocking condition persists for as long as the drawn liquidity stays out, which is the borrower's choice.

### Recommendation
Make outbound liquidity checks sibling-aware. Concretely: in `Cache::require_reserves` (or at each `debit_cash`/`transfer_out` call site), read the token's actual `balance(pool)` or maintain a per-asset aggregate-cash entry, and require `aggregate_booked_cash(asset) >= aggregate_draw(asset)` rather than only `self.cash >= amount`. A cheaper variant is to cap each market's drawable cash at `min(self.cash, token.balance(pool) - cash_reserved_for_siblings)`, maintained on every credit/debit for that asset. Short of code changes, the restriction should at minimum be an explicit documented/accepted-risk ADR; currently INV-ACCT and the fuzz assertion acknowledge the gap without a mitigation.

### Proof of Concept
1. Governance lists USDC in hub 1 and hub 2 (already deployed: `USDC` hub 1, `USDC_HUB2` hub 2, same token address).
2. Victim V calls controller `supply` on the hub-2 USDC market with 1,000 USDC → hub-2 book: `cash = 1,000`, pool token balance = 1,000 (+hub-1 liquidity).
3. Attacker A supplies collateral (e.g. XLM) on a spoke listing the hub-1 USDC market and calls `borrow` on `HubAssetKey { hub_id: 1, asset: USDC }` for an amount up to hub-1's `cash − 200 BPS buffer`. `require_reserves` passes because it reads only hub-1's book; `transfer_out` sends real USDC to A.
4. If hub-1's cash book was large enough (normal pooled liquidity), the pool's actual USDC balance is now < hub-2's booked `cash`.
5. V calls `withdraw` on `HubAssetKey { hub_id: 2, asset: USDC }`. All per-market checks pass (`cash ≥ amount`, utilization, supply-for-debt), then `transfer_out` reverts on `token.transfer` — V's funds are frozen until A (or other hub-1 borrowers) repays.
6. Symmetrically, an unprivileged `claim_revenue` or liquidation collateral payout on hub-2 reverts the same way.
