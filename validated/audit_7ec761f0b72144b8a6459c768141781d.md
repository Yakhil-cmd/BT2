### Title
Cross-Stack Deploy-State Disclosure via Unscoped `Stack.from_param!` in CCMenu API - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The Shipit API layer restricts an `ApiClient` to a single stack by scoping every stack lookup through `stacks.from_param!`, which filters against `current_api_client.stack_id`. The `Api::CCMenuController#stack` method bypasses this scoping and resolves the stack directly with the global `Stack.from_param!(params[:stack_id])`, so a stack-scoped API token can be used to read the build/deploy status of any stack in the installation, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` establishes the trust binding that an `ApiClient` token authorizes access only to the stack it is bound to: [1](#0-0) 

Every other resource controller (`DeploysController`, `TasksController`, `StacksController`, etc.) resolves `stack` (or `stacks`) through this scoped helper, so `current_api_client.stack_id` is enforced before any stack-specific data is rendered — confirmed by the test asserting "an api client scoped to a stack will only see that one stack": [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model, ignoring `current_api_client.stack_id` entirely: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the string permission `read:stack` via `ApiClient#check_permissions!`, which has no notion of which specific stack is permitted: [4](#0-3) 

So the binding that should hold — `stack_id authorized by the token == stack touched by the request` — is broken specifically in this controller. A token created with `stack_id` set to Stack A (and `read:stack` permission) can request `GET /api/stacks/*B/ccmenu` for an unrelated Stack B and receive B's build/deploy status, because `stack` never checks `current_api_client.stack_id` against `params[:stack_id]`.

### Impact Explanation
This is an unauthenticated-scope violation: a legitimately-issued but narrowly-scoped API credential (created via the "Human" `api_clients` flow, intended to expose CI status for one project only) can be replayed against any other stack’s `ccmenu` endpoint to disclose that stack's `merge_status`/lock state, most recent deploy activity (`Building`/`Sleeping`), last build id/time, and its web URL: [5](#0-4) 
This matches the "escalation into stack authorization" / "read of stack state or deploy output" impact class: a token meant for stack A is used to read stack B's deploy/task state.

### Likelihood Explanation
High likelihood for any holder of a scoped API token: the exploit is a single unauthenticated-scope GET request, requiring only knowledge/guessing of another stack's `owner/repo/env` path (which is often discoverable, e.g. via the public stacks list or repository name conventions). No additional credentials, signatures, or write access are needed beyond the attacker's own legitimately scoped token or CCMenu URL/token pair (`test "can authenticate with query string token"` shows tokens are also accepted via query string, increasing exposure via shared/bookmarked CCMenu URLs): [6](#0-5) 

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same scoped `stacks` collection used by `BaseController`, e.g. `stacks.from_param!(params[:stack_id])`, so `current_api_client.stack_id` is enforced consistently with every other API resource.

### Proof of Concept
1. Create/obtain an `ApiClient` token whose `stack_id` is scoped to `Stack A` with `permissions: ['read:stack']`.
2. Send `GET /api/stacks/<owner_b>/<repo_b>/<env_b>/ccmenu` (Stack B, a different, unrelated stack) using that token, via Basic Auth or `?token=`.
3. Observe a `200 OK` response containing Stack B's `lastBuildStatus`, `activity`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — data the token was never authorized to see — because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!` used elsewhere: [7](#0-6)
