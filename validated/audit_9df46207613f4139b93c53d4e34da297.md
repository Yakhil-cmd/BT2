## Confirmed root cause

`Handler#stacks` resolves the target repository purely from `payload.dig('repository', 'full_name')`, while `WebhooksController#verify_signature` selects the secret used to authenticate the request purely from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. These are two independently attacker-controlled fields inside the same unauthenticated (pre-verification) JSON body, and nothing ties them together. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook target-repository confusion — signature verified against `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization (and therefore the HMAC secret) to verify against using `repository_owner`, which is read directly out of the untrusted JSON body via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the HMAC check passes, `create` dispatches the entire raw JSON body to handlers such as `PushHandler`, `StatusHandler`, and the `PullRequest::*` handlers, all of which resolve the actual repository/stack to mutate via `Handler#repository_name` → `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.full_name`'s owner equals `repository.owner.login`/`organization.login`. This is exactly the RFT bug pattern: a value used to satisfy the "authorization" check (`repository_owner` picking the verifying secret) is disjoint from the value the state-mutating logic actually acts on (`repository.full_name`).

### Finding Description
The binding that should hold is: *organization whose webhook secret authenticated the request* == *repository whose stack state is written*. This engine breaks that equality:

- `verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to obtain that organization's `webhook_secret`, then verifies `X-Hub-Signature` against it. [2](#0-1) 
- The same controller then feeds the identical raw JSON to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with no re-derivation or cross-check. [4](#0-3) 
- All default handlers (`PushHandler`, pull-request handlers, etc.) resolve the repository/stack from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`#repository_name`, completely independent of `repository_owner` used above. [1](#0-0) [5](#0-4) 

In a Shipit deployment configured with multiple GitHub organizations (`Shipit.github_app_config(organization)`), each org has its own `webhook_secret`. [6](#0-5) 
Any party who legitimately controls webhook delivery for **one** configured organization (e.g. by owning/administering a repository under `OrgA` that is registered with Shipit, and thus knowing/receiving `OrgA`'s webhook secret through GitHub's normal delivery mechanism to craft a valid `X-Hub-Signature`) can send a POST to `/webhooks` where:
- `repository.owner.login` / `organization.login` = `OrgA` (so `verify_signature` succeeds using OrgA's secret), and
- `repository.full_name` = `OrgB/victim-repo` (a repository/stack the attacker has no access to at all).

Because `repository_name` is read from `repository.full_name` and not cross-checked with `repository_owner`, the handler acts on `OrgB/victim-repo`'s stacks.

### Impact Explanation
This is an authentication-bypass style confused deputy: the cryptographic check is satisfied by binding A, but the mutating logic executes against target B. Concretely, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of the attacker-chosen repository matching the attacker-chosen branch — letting the attacker force a `GithubSyncJob` (and, depending on branch matching, trigger continuous-deployment sync/queue effects) against a stack/repository belonging to a completely different, unauthorized organization/repository, using signing material the attacker only possesses for their own org. Other handlers (`status`, `pull_request/*`) similarly resolve target repository purely from the unauthenticated `full_name` field and mutate commit statuses, pull-request/review-stack state (archive/unarchive, label capture, merge-status) for a repository the sender never proved control of. This crosses the "unauthorized... write" boundary described in the ruleset (writes to a repository/stack the authenticating principal does not control), fitting the High-impact class of "escalation... unauthenticated... state" mutation across a repository/authentication boundary.

### Likelihood Explanation
Likelihood is Medium: it requires the deployer to run Shipit with the multi-organization GitHub config (`secrets.github` keyed by multiple orgs, each with distinct `webhook_secret`s) — a documented and supported configuration (`github_app_config`, `github_organizations`) — and requires the attacker to have legitimate control over at least one such configured organization/repository (enough to receive/replay a validly-signed webhook for it). Given that, no other credential or session is needed; it is purely a payload-crafting/signature-replay issue completely within the engine's own webhook code path, with no dependency on host misconfiguration beyond the intended multi-org feature.

### Recommendation
Bind the value used to select the verifying secret to the value the handlers act on:
- After signature verification, re-extract the repository the handler will act on (`payload.dig('repository','full_name')`) and confirm its owner matches the `repository_owner` (or `organization.login`) that was used to select the webhook secret; reject (422) on mismatch.
- Alternatively, pass the verified `repository_owner`/organization context explicitly into `Handler.call`, and have `Handler#stacks` filter/require that the resolved `Repository`'s owner equals the verified organization, instead of trusting `full_name` in isolation.
- Add regression tests asserting that a validly-signed webhook for `OrgA` cannot mutate stacks belonging to `OrgB`'s repositories.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `orga` and `orgb`, each with its own `webhook_secret`, and a stack for `orgb/victim-repo`.
2. As an administrator/webhook owner of `orga` (attacker), compute a valid HMAC-SHA1 signature for `orga`'s `webhook_secret` over a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed with orga secret>`.
4. `verify_signature` calls `Shipit.github(organization: 'orga')` (from `repository.owner.login`) and successfully verifies the signature using `orga`'s secret. [2](#0-1) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('orgb/victim-repo')` and calls `sync_github` on its non-archived, branch-matching stacks — even though the request was never signed by anyone with authority over `orgb`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
