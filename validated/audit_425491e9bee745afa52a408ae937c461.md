### Title
Cross-repository commit-status forgery via unscoped `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . This is the exact "fee" class of bug from the report: one piece of the payload (`repository_owner`) is what the verification actually covers, while a *different* field in the same payload (`sha`) is what the handler actually acts on, and that acted-upon field is not constrained to belong to the verified organization/repository at all.

### Finding Description
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit purely by SHA, globally, across every stack/repository/organization hosted on the Shipit instance: [3](#0-2) 

Compare this to the sibling handlers in the same file/module, which scope their queries to the stacks associated with the webhook's own repository/branch before touching any records, e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)`) [4](#0-3)  and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`) [5](#0-4) . `StatusHandler` is the outlier: it never checks that the matched `Commit` belongs to a stack owned by the organization that was actually verified by `verify_signature`.

The signature check is scoped to `repository_owner`, i.e. it proves "GitHub signed this JSON for organization X's webhook secret" [6](#0-5) . It never constrains which `sha` value the payload may reference. `sha` is attacker-supplied JSON content within a payload the attacker fully controls for their own, legitimately-configured organization/repo. Because `StatusHandler` looks up `Commit.where(sha: params.sha)` with no repository/owner filter, an operator who legitimately controls a stack/repo X on a shared, multi-tenant Shipit instance (multiple orgs are explicitly supported — see the `GithubOrganizationUnknown` per-organization lookup in `Shipit.github(organization:)` [6](#0-5) ) can send a validly-signed `status` webhook for their own repo X, but with `sha` set to a commit SHA that exists in a *different* organization's stack Y, and have Shipit apply a forged CI status to stack Y's commit.

`Commit#create_status_from_github!` → `add_status` then reacts to the new status: it emits hooks and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [7](#0-6) , which can unblock a pending merge request on the victim stack that was waiting on that CI context (`any_status_checks_missing?` / `all_status_checks_passed?` in `MergeRequest`) [8](#0-7) .

**Binding broken (equality that should hold but doesn't):**
`organization verified by HMAC signature (repository_owner)` == `organization owning the repository/stack whose commit status is mutated (via sha)`

Before the attacker's request: the equality holds trivially because no request has been accepted yet.
After the attacker's request: the webhook is authenticated as organization X (attacker's own), yet the row mutated is a `Status` belonging to a `Commit` under stack Y (victim organization), breaking the equality.

### Impact Explanation
This allows an attacker who controls any single repository/stack hosted on the shared Shipit instance to forge CI status transitions on a completely unrelated organization's commits, without ever obtaining that organization's webhook secret, GitHub App credentials, or Shipit session/API token. Forged `success` statuses can unblock automatic merges (`schedule_merges`) and continuous deployment scheduling on the victim's stack, i.e., an unauthorized merge/deploy triggered through a forged, out-of-scope CI signal. This satisfies the Critical bar of "unauthorized deploy, rollback or merge" from a party with no authorization over the victim repository.

### Likelihood Explanation
Requires only: (1) the attacker legitimately manages at least one org/repo on a shared/multi-tenant Shipit instance (a supported, documented deployment model, not privileged access to the victim), and (2) knowledge of a target commit's SHA in the victim stack, which is public information (visible via GitHub, the Shipit UI, or the Shipit API for any stack a user can view). No signature-secret leakage, no session, no GitHub App key is needed — only a webhook that is validly signed for the attacker's own, unrelated repository. This is a realistic, low-effort path for any tenant on a multi-org Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by content-derived identifiers such as `sha`) to only the stacks associated with the webhook's own `repository`/`repository_owner`, mirroring the pattern already used by `PushHandler` and `CheckSuiteHandler` (i.e., go through the `stacks` helper scoped to the verified repository instead of a bare `Commit.where(sha:)` lookup).

### Proof of Concept
1. Attacker registers/owns repository `attacker-org/attacker-repo` as a valid Shipit stack (legitimate multi-tenant usage), and knows its correctly-configured webhook secret (their own).
2. Attacker looks up the SHA of a commit belonging to `victim-org/victim-repo`'s stack (public git data), call it `VICTIM_SHA`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and JSON body:
```json
{
  "sha": "VICTIM_SHA",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. `verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret [6](#0-5) .
5. `StatusHandler#process` runs `Commit.where(sha: "VICTIM_SHA")` (no owner scoping) [3](#0-2)  and creates a `success` status on the victim's commit, potentially satisfying a required CI check and triggering `schedule_merges`/`schedule_continuous_delivery` on the victim stack.

Note: I could not fully confirm within the indexed code how many distinct webhook secrets/organizations a single Shipit deployment supports in practice (the `GithubOrganizationUnknown`/per-organization `Shipit.github(organization:)` lookup implies multi-org support, but the full multi-tenant configuration logic in `lib/shipit.rb` was not retrievable in this session). If a given deployment is truly single-organization/single-secret only, the practical blast radius is limited to cross-*repository* (not cross-organization) forgery within that one org, which is still a violation of the stated binding but with a narrower attacker population.

      github_app = Shipit.github(organization: repository_owner)

      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
