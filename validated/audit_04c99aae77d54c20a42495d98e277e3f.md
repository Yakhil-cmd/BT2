### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no constraint tying the lookup to the repository that actually sent (and authenticated) the webhook. Any commit belonging to any stack, in any repository, that happens to share a SHA with the attacker's own repository will have its GitHub status overwritten by the attacker's payload, and this write can trigger merge-queue advancement (`merge!`) or deploy blocking on the victim stack.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`commit.stack.repository.full_name == payload.repository.full_name` for every `commit` mutated by `StatusHandler#process`.

The handler is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` performs a global lookup across the `commits` table with no `stack_id`/repository filter, even though `Commit belongs_to :stack` and each stack is bound to one GitHub repository. `create_status_from_github!` then calls `add_status`, which writes into `statuses` scoped to that commit's own `stack_id` and re-evaluates `deployable?`/`blocked?`, and — critically — triggers `stack.schedule_merges` when the new status becomes `pending` or `success`: [2](#0-1) [3](#0-2) 

`MergeRequest.schedule_merges` iterates every stack with `merge_queue_enabled: true` and calls `schedule_merges`, which can lead to `MergeRequest#merge!` firing a real GitHub merge: [4](#0-3) [5](#0-4) 

Root cause: SHAs are git object identifiers, not global unique identifiers across repositories/stacks. Two independent stacks (e.g., a fork and upstream, two stacks tracking the same monorepo path, or any repositories sharing history/cherry-picked commits) can legitimately contain `Commit` rows with an identical `sha`. The webhook signature (`verify_signature`) only proves the payload came from *a* legitimate GitHub sender for *the attacker's own repository* — it does not scope the subsequent database write to that repository. `drop_unhandled_event`, `ExplicitParameters` schema validation, and `force_github_authentication` all operate on request shape/authenticity, not on cross-tenant data scoping, so none of them stop this divergence.

Attacker's exact request: register/own a repository whose Shipit stack has `merge_queue_enabled` (or any stack), obtain a commit SHA that also exists as a `Commit` record in a victim stack (achievable by forking the victim repo, opening a PR against their own fork/mirror stack containing the same base commit, or any shared-history scenario), and `POST /webhooks` with a signed `status` event: `sha: <shared-sha>`, `context: buildkite/deploy`, `state: failure` (or `success`). Because the handler doesn't check which repository owns that SHA's `Commit` row, the victim stack's commit status flips accordingly.

### Impact Explanation
A single unprivileged webhook (properly signed for the attacker's own repository) mutates commit-status state belonging to a different tenant's stack. If the affected commit is a merge-queue head on a victim stack (`merge_queue_enabled: true`), flipping its required status to `success` can trigger `MergeRequest#merge!`, causing GitHub to merge an unrelated/attacker-influenced PR; flipping it to `failure` can block deploys or reject queued merges. This is a "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category (unauthorized deploy/rollback/merge of code the attacker does not control) as long as a SHA collision between attacker-owned and victim-owned `Commit` rows can be engineered.

### Likelihood Explanation
The attacker needs: (1) a webhook properly signed for a repository/stack they control (trivial — they can add their own repo to Shipit or push to a repo already onboarded, or use any repo whose webhook secret they have because they administer it), and (2) a `Commit` record with matching `sha` already existing in the victim's stack. Precondition (2) is the limiting factor — it requires shared git history/shared commit objects between attacker and victim repositories (forks of the same upstream, monorepo split into multiple stacks, cherry-picks, etc.), which is a realistic but not universal precondition. Given that precondition, the attack is fully repeatable and costless (just send more signed webhooks).

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) by the repository that authenticated the webhook, e.g. join through `stack.repository` and filter `where(shipit_stacks: { repository_id: current_repository.id })`, or otherwise verify `commit.stack.repository == webhook_repository` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (illustrative, no live GitHub):
```ruby
test "status webhook does not affect commit in a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires buildkite/deploy
  attacker_stack = create_stack(repository: create_repository(full_name: "attacker/repo"))
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  before_state = victim_commit.reload.status.state # e.g. "success" / deployable?

  Shipit::Webhooks::Handlers::StatusHandler.new(
    payload: { sha: shared_sha, state: "failure", context: "buildkite/deploy" },
    delivery: SecureRandom.uuid,
    event: "status"
  ).process

  after_state = victim_commit.reload.status.state

  assert_equal before_state, after_state, "victim stack's commit status must not change from a webhook authenticated for a different repository"
end
```
Both sides of the equality (`before_state` vs `after_state`) diverge under current code because `Commit.where(sha:)` matches `victim_commit` even though the webhook was never authenticated for the victim repository, confirming the vulnerability.
