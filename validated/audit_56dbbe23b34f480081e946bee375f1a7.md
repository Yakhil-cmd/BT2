### Title
Cross-organization webhook signature confusion allows any GitHub App owner to trigger `GithubSyncJob` against another tenant's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner`, which is read from the same attacker-controlled JSON body (`repository.owner.login`) as the `repository.full_name` used later by `PushHandler` to select the target stack. Because these two fields are never cross-checked against each other, an attacker who controls a GitHub organization/App registered in Shipit's multi-org config can sign an arbitrary payload with their own `webhook_secret` while pointing `repository.full_name` at a different tenant's tracked repository, causing Shipit to enqueue a `GithubSyncJob` against that victim stack.

### Finding Description
The broken binding: `organization_that_signed_bytes` (`repository.owner.login`, used in `Shipit.github(organization: repository_owner)` at [1](#0-0) ) must equal `organization_owning_mutated_stack` (derived from `repository.full_name` inside `PushHandler#process` via `Repository.from_github_repo_name` at [2](#0-1) ). Nothing in the code enforces this equality — the controller reads `repository.owner.login` purely to pick which `GitHubApp`/`webhook_secret` to verify against ( [3](#0-2) ), then passes the *entire raw JSON body* unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` ( [4](#0-3) ), where `PushHandler` independently re-reads `repository.full_name` to resolve the stack ( [5](#0-4) ). This multi-org design is real and documented — Shipit supports per-organization `webhook_secret`s keyed by organization name in `secrets.github` ( [6](#0-5) ), confirmed by `docs/setup.md`'s "Using Multiple Github Applications" section and by `Shipit.github(organization:)`'s lookup logic. An attacker who owns/administers such a registered organization (e.g., `org-with-secret`) knows its `webhook_secret` and can freely craft and sign a payload with `repository.owner.login = "org-with-secret"` but `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/master"`, and an arbitrary `after` SHA. `verify_signature` succeeds because it only checks the bytes against `org-with-secret`'s secret. `drop_unhandled_event`, `ExplicitParameters` schema validation (`PushHandler` only requires `ref`/`after`, not owner/full_name consistency), and `check_if_ping` do not perform any owner-vs-full_name cross-check. The result: `PushHandler` resolves `stacks` for the victim's repository and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `Shipit::GithubSyncJob` with the victim stack's `stack_id` ( [7](#0-6) ).

### Impact Explanation
Once enqueued, `GithubSyncJob` operates entirely on the victim's `Stack`: it calls `stack.github_commits` / `stack&.github_api`, which uses the **victim's own** GitHub App/token (via `repository.owner`, as seen in `Stack#env`'s `GITHUB_REPO_OWNER`/`GITHUB_REPO_NAME` at [8](#0-7) ) to fetch commits and append them to the stack, and can mark the stack accessible/inaccessible ( [9](#0-8) ). This is a cross-tenant trigger: a payload signed by one organization ("org-with-secret") causes state mutation (new commits appended, deploy-spec cache invalidation via `CacheDeploySpecJob`) on a stack belonging to an unrelated organization ("victim-org"), using the victim's own GitHub credentials to do the fetching. This matches the "payload for one repository mutating another's stack" Critical category. It is repeatable against any tracked repository/branch combination the attacker can guess or discover (repo full names are not secret), for every push, provided the attacker controls at least one registered-organization webhook secret in the multi-org deployment.

### Likelihood Explanation
This requires a Shipit deployment configured with the multi-organization GitHub App schema (multiple orgs each with distinct `webhook_secret`s trusted by the same Shipit instance) and requires the attacker to be an authorized owner/admin of at least one of those registered orgs (so they legitimately know that org's `webhook_secret`) — which the threat model here explicitly grants as an "unprivileged" but org-owning attacker. In a single-org deployment (the common `secrets.github` schema without sub-keys), this specific cross-org confusion does not apply, since there's only one webhook secret for everything. Given the multi-org precondition, the attack is cheap: one crafted, HMAC-signed HTTP POST to `/webhooks`, fully repeatable, no rate limiting or additional secrets needed.

### Recommendation
Cross-validate that the organization used to verify the signature matches the resolved repository's actual owner before dispatching to handlers — e.g., after `Repository.from_github_repo_name(payload.dig('repository','full_name'))` resolves a repository, assert `repository.owner.casecmp?(repository_owner)` (the value used in `verify_signature`) and reject (422) on mismatch. Alternatively, thread the verified `organization` through to `Handler#call` and have `stacks`/`Repository.from_github_repo_name` scope lookups to that organization only, rather than trusting the unauthenticated `full_name` string in the body independently of what was cryptographically verified.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
```ruby
test "push webhook signed by org-with-secret cannot sync a stack owned by a different org" do
  # victim stack belongs to 'victim-org/victim-repo', tracking branch 'master'
  victim_repo = shipit_repositories(:shipit) # full_name e.g. "shopify/shipit-engine"
  victim_stack = shipit_stacks(:shipit)

  # Attacker signs the request as 'org-with-secret', but points full_name at the victim repo
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a valid signature for org-with-secret
  Shipit.expects(:github).with(organization: 'org-with-secret').returns(stub(verify_webhook_signature: true))

  payload = JSON.parse(payload(:push_master))
  payload["repository"]["owner"]["login"] = "org-with-secret"
  payload["repository"]["full_name"] = victim_repo.full_name # e.g. "victim-org/victim-repo"
  expected_head_sha = payload["after"]

  request.headers['X-Github-Event'] = 'push'

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha:]) do
    post :create, body: payload.to_json, as: :json
  end
  # Assert: Shipit.github was only ever invoked/stubbed for 'org-with-secret',
  # yet GithubSyncJob was enqueued for victim_stack.id — proving the divergence.
end
```
This demonstrates the equality `organization_that_signed_bytes ('org-with-secret') != organization_owning_stack ('victim-org')` holds both before and after the request, while the job is enqueued against the victim's stack anyway.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
