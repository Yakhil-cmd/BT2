### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled=false` when `provisioning_behavior` is `allow_with_label` or `prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Repository#review_stacks_enabled == false` is supposed to be a global kill-switch preventing any review stack from being provisioned for a repository, independent of `provisioning_behavior`. Because Ruby's `&&` binds tighter than `||`, the `provision?` method only ANDs `review_stacks_enabled` with the `allow_all` disjunct, leaving the `allow_with_label` and `prevent_with_label` disjuncts unguarded, so an attacker's pull request can still trigger stack creation even when review stacks are disabled for that repository.

### Finding Description
The broken binding is: required-for-provisioning = `repository.review_stacks_enabled == true` for **every** provisioning behavior, vs actual = `repository.review_stacks_enabled` is only checked for the `provisioning_behavior_allow_all?` branch.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby operator precedence, this parses as:
```
(review_stacks_enabled && provisioning_behavior_allow_all?) ||
(provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
The second and third disjuncts never reference `review_stacks_enabled` at all. `process` calls `respond_to_pull_request_opened?` which calls `provision?` directly, and if true it calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, building a `ReviewStack` with `branch: params.pull_request.head.ref` taken straight from the attacker's fork/branch name, with no check that review stacks are enabled for that repo. [2](#0-1) [3](#0-2) 

**Exact repro condition (matches the question):** `Shipit::Repository` row has `review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label`. An attacker opens a pull request against this repository with no provisioning label. `pull_request_has_provisioning_label?` returns `false`, so `!pull_request_has_provisioning_label?` is `true`, and `provisioning_behavior_prevent_with_label?` is `true`, making the third disjunct `true` — `provision?` returns `true` regardless of `review_stacks_enabled`.

The enum itself is defined via `enum :provisioning_behavior, ... prefix: :provisioning_behavior` with values `allow_all`, `allow_with_label`, `prevent_with_label`. [4](#0-3) 

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?`; there is no separate `review_stacks_enabled` gate elsewhere in the handler or adapter. [5](#0-4) 

Existing test coverage only exercises `review_stacks_enabled: false` combined with `behavior: :allow_all` (the one disjunct that IS correctly guarded), never with `allow_with_label`/`prevent_with_label`, so this precedence gap has no regression test. [6](#0-5) 

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (or `allow_with_label` combined with adding their own label) can force creation and provisioning of a `Shipit::ReviewStack` for that repository, with `branch` set to their attacker-controlled fork's branch ref. This writes a record and triggers a provisioning task (`Shipit::ReviewStackProvisioningQueue.add`) for a repository whose owner explicitly opted out of review-stack provisioning — an unauthorized write/provisioning action driven entirely by attacker-controlled webhook data (`params.pull_request.head.ref`). This is repeatable against any repository configured this way, and matches "a payload for one repository mutating another's stack" in spirit (the config's opt-out is bypassed), landing in the Critical impact category for unauthorized provisioning stemming from an authorization-equivalent boolean being ignored.

### Likelihood Explanation
Preconditions: a `Shipit::Repository` must have `review_stacks_enabled: false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator/admin misconfiguration or a common intermediate state while transitioning behaviors). No secrets, tokens, or privileged Shipit access are needed — only opening a pull request (or arranging for a `pull_request.opened` webhook payload with matching data) against the target repo. Attacker cost is trivial and fully repeatable per PR/branch.

### Recommendation
Fix operator precedence explicitly, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (extending existing patterns):
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label with no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` increases by 1 and `stack.branch == payload["pull_request"]["head"]["ref"]` despite `review_stacks_enabled == false`, proving the binding `review_stacks_enabled == true` required-for-provisioning is violated. After the fix, `assert_no_difference` passes.
