Confirmed vulnerability: the webhook signature-verification organization is decoupled from the repository that the push handler actually writes to.

### Title
Webhook signature scoped to `repository.owner.login`/`organization.login` but push processing trusts `repository.full_name`, enabling cross-organization sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC against using only `repository.owner.login` (or `organization.login`) from the JSON body, while the actual event handler (`PushHandler` via `Handler#repository_name`) resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same body. Because both fields are attacker-controlled JSON fields inside one HMAC-signed body, an attacker who possesses a valid webhook secret for *any* organization configured in Shipit (e.g. an org they legitimately administer and installed the Shipit GitHub App on) can craft a payload where `repository.owner.login` names their own org (so signature verification passes with a secret they know) while `repository.full_name` names a different, unrelated organization/repository that they do not control.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick `Shipit.github(organization: repository_owner)` for HMAC verification: [2](#0-1) 

Meanwhile, the dispatched handler for `push` events (`Shipit::Webhooks::Handlers::PushHandler`) resolves which `Stack`s to act on purely from `payload.dig('repository', 'full_name')`: [3](#0-2) [4](#0-3) 

`repository.owner.login` and `repository.full_name` are two separate keys inside the same JSON object; nothing forces `full_name` to start with `owner.login`. The HMAC signs the raw request body as a whole (equality: `signature == HMAC(secret_for(owner.login), raw_body)`), but never asserts `full_name.split('/').first == owner.login`. This breaks the intended binding: "the organization whose secret authenticated the request" should equal "the repository being written to."

### Impact Explanation
This is a cross-repository/cross-organization write: `Stack#sync_github` (triggered by `PushHandler`) enqueues `GithubSyncJob` with `expected_head_sha` for stacks belonging to the repository found via `full_name`, and other push-driven side effects (status/commit syncing tied to that stack) run against a repository the attacker does not administer, using only a secret from an org they *do* administer. In a multi-organization Shipit deployment (the engine explicitly supports per-organization `github.<org>.webhook_secret` configuration, see `config/secrets.development.example.yml`), this lets an attacker who legitimately controls Org A force sync/state changes tied to Org B's repositories/stacks, i.e., an unauthorized cross-repository state mutation without ever holding Org B's webhook secret or GitHub credentials.

### Likelihood Explanation
Requires the attacker to be a legitimate GitHub App installer/admin for at least one org configured in the multi-org `Shipit.github` config (so they know that org's `webhook_secret`), and requires the deployment to use multiple GitHub organizations. This is a realistic operating mode documented in the engine's own multi-org config example. No GitHub App private key, no `GITHUB_TOKEN`, no Shipit session or API client token is needed — only knowledge of one organization's webhook secret, which itself is not classified as a privileged Shipit-internal credential in the same sense as `api_clients_secret`/private keys.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, additionally assert that the `repository.full_name` (or `organization.login`) actually belongs to the same organization used to select the webhook secret (e.g., `repository.full_name.split('/').first.casecmp?(repository_owner)`), rejecting the payload with `422` if they diverge. Alternatively, derive `repository_owner` directly from `full_name` instead of the separate `owner.login`/`organization.login` fields so the same value is used both to select the verification secret and to resolve the target repository.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker administers `org-a` and knows `org-a`'s `webhook_secret` (legitimately, as the org's GitHub App installer).
3. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and a JSON body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha of a commit that exists in org-b's repo>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. `verify_signature` computes `Shipit.github(organization: "org-a").verify_webhook_signature(sig, raw_body)` using `org-a`'s secret, which the attacker correctly signs with the known `org-a` secret, so verification passes.
5. `PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')` = `"org-b/target-repo"`) looks up `Repository.from_github_repo_name("org-b/target-repo")` and calls `sync_github(expected_head_sha: ...)` on all matching stacks, causing Shipit to sync/deploy-track state for `org-b`'s repository using attacker-supplied data, despite the attacker never having `org-b`'s webhook secret or any GitHub credentials for `org-b`. module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
