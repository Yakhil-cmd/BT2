### Title
Webhook signature verification is keyed on `repository.owner.login` while stack resolution is keyed on `repository.full_name`, allowing cross-tenant `sync_github` triggering - (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus which `webhook_secret` to validate against) using `payload.dig('repository','owner','login')`, but `Handler#stacks`/`Handler#repository_name` resolve which `Repository`/`Stack` to mutate using `payload.dig('repository','full_name')`. Nothing in the code enforces that these two independently-attacker-supplied fields describe the same repository, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured.

### Finding Description
The binding the code implicitly assumes is:
`org_verifying_signature(payload.dig('repository','owner','login')) == org_owning_stack(payload.dig('repository','full_name'))`

This is never checked. Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)`, then `github_app.verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) does `return true unless webhook_secret`. If the org resolved by `repository_owner` has no `webhook_secret` configured, verification is bypassed entirely, independent of the signature header's validity or absence.
- On success, `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON body and dispatches to handlers, passing the *same* raw `payload`.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) calls `stacks` → `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which resolves `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository','full_name')` (`handler.rb:36-38`) — a completely separate JSON field from `repository.owner.login`.
- Because both `repository.owner.login` and `repository.full_name` are read straight out of the attacker-controlled raw POST body, an attacker who can reach `POST /webhooks` (explicitly listed as an in-scope capability) can set `repository.owner.login` to an organization that has no `webhook_secret` configured, satisfying `verify_signature` trivially, while setting `repository.full_name` to `"orgB/victim-repo"` to target a completely unrelated organization's stack.
- The handler then runs `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack matching that branch, with `params.after` fully attacker-chosen (`push_handler.rb:16`), advancing org B's tracked HEAD sha without org B's or GitHub's involvement.

None of the listed guards close this gap: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` only validates `ref`/`after` are present, not their relationship to `repository.owner`; there is no `Repository#owner` vs `payload.owner.login` cross-check anywhere in `Handler` or `PushHandler`.

### Impact Explanation
An attacker can cause `Stack#sync_github` to execute for an arbitrary organization's stack (one whose repository full name they know/guess) as long as any configured `GitHubApp` organization in `Shipit.github_apps` lacks a `webhook_secret`. This is a cross-tenant "payload for one repository mutating another's stack" — the exact Critical category listed in scope — because the stack's HEAD-tracking sha can be pushed to an attacker-chosen `expected_head_sha`, independent of the actual GitHub state of org B's repository. This is repeatable per request and applies to every not-archived stack on the targeted branch.

### Likelihood Explanation
The attack requires no secrets from the attacker (no `webhook_secret`, no session, no API token) — only that at least one organization entry under `Shipit.github_apps` is configured without a `webhook_secret`. This is a real, easy-to-hit misconfiguration state (the field is optional in the config schema handled by `GitHubApp.new`), and once present, `verify_webhook_signature` unconditionally returns `true` for any payload claiming that `owner.login`, regardless of a signature header being present, malformed, or absent. The attacker only needs to know or guess a target `full_name` (`org/repo`) and craft one raw HTTP POST; no live GitHub interaction, no privileged role, and no TLS interception is needed.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret matches the owner implied by `repository.full_name` before dispatching to handlers (e.g., require `payload.dig('repository','owner','login')` to equal the first segment of `payload.dig('repository','full_name')`, and reject if they diverge). Additionally, remove or gate the `return true unless webhook_secret` fallback in `GitHubApp#verify_webhook_signature` — silently accepting unsigned/any-signature webhooks for orgs without a configured secret should not be the default; require every registered `github_apps` organization to define a `webhook_secret`, or explicitly fail closed when one is missing.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossTenantTest < ActionDispatch::IntegrationTest
    setup do
      # org_a has no webhook_secret configured (simulate misconfiguration)
      Shipit.github_apps # ensure org_a entry present with no webhook_secret, org_b configured normally

      @victim_repo = shipit_repositories(:shipit) # belongs to org_b, e.g. "org_b/shipit"
      @victim_stack = shipit_stacks(:shipit)
      @victim_stack.update!(branch: 'master')
    end

    test 'a push payload claiming owner org_a (no secret) but targeting org_b full_name does not trigger org_b sync_github' do
      payload = {
        ref: 'refs/heads/master',
        after: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
        repository: {
          owner: { login: 'org_a' },       # org with NO webhook_secret -> verify_webhook_signature returns true
          full_name: @victim_repo.full_name # actually "org_b/shipit"
        }
      }.to_json

      Shipit::Stack.any_instance.expects(:sync_github).never
      # or, to demonstrate the vulnerable state, assert it IS called and fail the test intentionally:
      # Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeef...')

      post '/webhooks', params: payload, headers: {
        'X-Github-Event' => 'push',
        'Content-Type' => 'application/json'
        # deliberately no X-Hub-Signature header
      }

      assert_response :ok
    end
  end
end
```
Binding checked on both sides: `payload.dig('repository','owner','login')` (`"org_a"`, used by `verify_signature`) vs. the org implied by `payload.dig('repository','full_name')` (`"org_b"`, used by `Handler#repository_name`/`#stacks`). They diverge, and no code path re-checks this before `PushHandler#process` calls `sync_github`, confirming the vulnerability.
