### Title
Cross-organization webhook forgery via authenticated-org / acted-on-repository mismatch enables forged CI status and unauthorized merges - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. All downstream webhook handlers, however, resolve the `Stack`/`Repository` to act on using a *different* payload field, `payload.dig('repository', 'full_name')`, in `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`. In a multi-organization Shipit deployment (explicitly documented as a supported configuration), an attacker who legitimately possesses the low-trust `webhook_secret` for one configured organization can sign a payload where `repository.owner.login` is their own org (so signature verification passes) while `repository.full_name` names a repository belonging to a different, victim organization. This breaks the equality the app relies on: *organization authenticated (`repository.owner.login`/`organization.login`) == repository acted upon (`repository.full_name`)*.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
picking the app/secret via `repository_owner`: [2](#0-1) 

Once the signature check passes, `WebhooksController#create` dispatches the raw JSON to the relevant handler(s): [3](#0-2) 

Every handler (`push`, `status`, `check_suite`, etc.) resolves the target `Stack`s via `Shipit::Webhooks::Handlers::Handler#stacks`, which is keyed on a *different* field of the same payload — `repository.full_name` — not `repository.owner.login`: [4](#0-3) 

Because the HMAC signature only proves the payload was signed with *some* configured organization's secret, not that `repository.owner.login` matches `repository.full_name`, an attacker holding the secret for organization A can submit a payload with `repository.owner.login = "org-a"` (verifies fine) and `repository.full_name = "victim-org/victim-repo"` (acted upon). This is precisely the "organization that authenticated versus the repository that is written" binding called out as in-scope.

The most severe concrete abuse path is the `status` webhook: it creates a `Commit#statuses` record for the resolved stack/commit based on attacker-controlled `state`/`context`/`sha` fields, scoped only by `repository.full_name`. This is confirmed by the existing test that free-forms a `status` payload merged with arbitrary `repository_params`: [5](#0-4) 

`MergeRequest#all_status_checks_passed?`/`#reject_unless_mergeable!` rely on exactly these `Commit` statuses to decide whether a pending merge request may proceed: [6](#0-5) 

`ProcessMergeRequestsJob` then calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(...)` — an actual write against the victim repository — once required statuses are (falsely) satisfied: [7](#0-6) [8](#0-7) 

Multi-organization configuration, each with its own independent `webhook_secret`, is a first-class documented configuration: [9](#0-8) 

### Impact Explanation
An attacker who is a legitimate (but unprivileged, outside-the-victim-org) user of a shared multi-org Shipit instance — i.e., they only know the `webhook_secret` for their own organization's GitHub App configuration, with zero write access to the victim repository — can forge `status` (or `push`/`check_suite`) webhook events that are accepted as authentic for a completely unrelated victim repository. By injecting a fabricated passing CI status for the head commit of a pending merge request in the victim repository, the attacker can cause Shipit's `ProcessMergeRequestsJob` to merge that pull request via `stack.github_api.merge_pull_request`, i.e., an **unauthorized merge into a repository the attacker has no access to**, performed using the app's legitimate GitHub credentials for the victim org. This matches the Critical impact bar: "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
The only prerequisite is possession of a `webhook_secret` for *any* organization configured in the shared Shipit instance — something an unprivileged tenant legitimately has by design in a multi-org setup. No GitHub write access, no `ApiClient` token, and no privileged Shipit account is required. Because the raw JSON body is fully attacker-controlled at the field level (only the HMAC over the whole body is checked, and it is checked using a key selected from within that same attacker-controlled body), this is a low-effort, deterministic, reliably exploitable inconsistency, not a race condition or edge case.

### Recommendation
Verify the webhook signature against the secret owned by the organization that actually owns the repository being acted upon — i.e., always derive both the "authenticating organization" and the "acted-upon repository" from the same, single trusted field (`repository.full_name` split into owner/name), rather than independently trusting `repository.owner.login`/`organization.login` in `verify_signature` and `repository.full_name` in `Handler#stacks`. Additionally, cross-check that the resolved `Stack`'s `Repository#owner` matches the organization whose secret validated the signature before dispatching to any handler.

### Proof of Concept
1. Shipit is configured for two organizations, `org-a` (attacker-controlled, e.g., attacker is an admin of a Shipit customer org and knows its GitHub App `webhook_secret`) and `victim-org` (has a stack tracking `victim-org/victim-repo` with a pending `MergeRequest` awaiting a `ci/required` status).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<head sha of victim PR>",
     "state": "success",
     "context": "ci/required",
     "target_url": "https://example.com",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully (attacker signed correctly with `org-a`'s secret).
5. The `status` handler resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` and records a `success` status for the victim's commit.
6. `ProcessMergeRequestsJob` later observes `all_status_checks_passed?` returning true for the victim's merge request and calls `merge!`, which merges the PR in `victim-org/victim-repo` — a repository the attacker never had access to.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?

        end
