Confirmed: neither `MultiKey::new` (Rust) nor `new_multi_key_from_single_keys` / `deserialize_multi_key` (Move, `multi_key.move`) reject duplicate entries in `public_keys`. Both only check key count bounds and `signatures_required <= num_keys`.

### Title
MultiKey/MultiKeyAuthenticator accepts duplicate public keys, letting one keyholder satisfy a k-of-n admission threshold alone - (File: types/src/transaction/authenticator.rs, aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move)

### Summary
`MultiKey::new` in `types/src/transaction/authenticator.rs` and `new_multi_key_from_single_keys`/`deserialize_multi_key` in `aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move` build a k-of-n `MultiKey` authentication scheme without checking that `public_keys` entries are unique. `MultiKeyAuthenticator::to_single_key_authenticators` (exercised by `verify_multi_key_auth` in `types/src/transaction/authenticator.rs`) then happily accepts one signature reused against two different indices in the key list that happen to hold the same key, satisfying the required-signature count with a single real signer.

### Finding Description
`MultiKey::new` (`types/src/transaction/authenticator.rs:1241-1264`) only validates:
- `signatures_required > 0`
- `public_keys.len() <= MAX_NUM_OF_SIGS`
- `public_keys.len() >= signatures_required` [1](#0-0) 

There is no uniqueness check across `public_keys`. The Move-side constructor mirrors this: [2](#0-1) 

The existing unit test `verify_multi_key_auth` demonstrates the consequence directly: a `MultiKey` is built with `keys = [any_sender0_pub, any_sender1_pub, any_sender1_pub]` (sender1's key repeated at index 1 and 2) with `signatures_required = 2`. A `MultiKeyAuthenticator` is then constructed using `sender1`'s single signature at *both* index 1 and index 2 (`mk_auth_12`), and `signed_txn.verify_signature().unwrap()` succeeds: [3](#0-2) 

This proves that when an account's authentication key is derived from a `MultiKey` whose key list contains a duplicate, the threshold check (`signatures_required`) can be met by a single private key holder providing one signature counted against two (or more) "slots," even though the nominal intent of a k-of-n scheme is that k *independent* parties must approve. The only rejection path found (`MultiKeyAuthenticator::new(... vec![(0, sig), (0, sig)])`) rejects duplicate *indices* into the bitmap, not duplicate *public keys at different indices* — so the protection is purely against reusing the same bitmap slot, not against a key appearing more than once in the key set.

### Impact Explanation
Any Aptos account (or governance/multisig construction) whose `AuthenticationKey` is derived from a `MultiKey` (`Scheme::MultiKey`, scheme id 3) — including keyless-backup flows built via `multi_key::new_multi_key_from_single_keys` (e.g. `upsert_ed25519_backup_key_on_keyless_account` and `register_ek_and_encrypt_dk` in `account.move`/`keyless_account.move`) — can be configured, accidentally or through social/administrative process where different keys are contributed by different parties, with a repeated public key. In that scenario, the number-of-signatures invariant that downstream logic (and human operators) rely upon for authorization is silently weakened: a party holding just one of the duplicated keys can single-handedly satisfy what appears to be a "2-of-n" or higher threshold, causing the transaction admission/execution path to accept an authenticator that does not actually reflect independent approval by the required number of distinct signers. This is a direct analog of the source report's core defect (a degenerate/duplicated entry in the approval-counting structure lets one identity satisfy multiple required "slots").

### Likelihood Explanation
This requires a `MultiKey` account to be constructed with a duplicate public key in the first place — this is not exploitable against an arbitrary victim account whose key list was built correctly with distinct keys. The risk surfaces specifically in scenarios where the key list is assembled incrementally/collaboratively (e.g., a DAO/custody setup adding member keys over time without dedup checks, or careless key-rotation tooling) and no on-chain or client-side validation prevents duplicates. Given that neither the Rust type nor the Move module enforces uniqueness, likelihood depends entirely on external tooling behavior, which is plausible but not guaranteed to occur, and is not itself an unprivileged attacker forging a signature.

### Recommendation
Add a uniqueness check on `public_keys` in both `MultiKey::new` (`types/src/transaction/authenticator.rs`) and `new_multi_key_from_single_keys`/`deserialize_multi_key` (`aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move`), rejecting construction/deserialization if any two entries are equal. This should be done in a way that's consistent for both the transaction-authenticator construction path and the on-chain authentication-key derivation path, since a chain-side check alone would not prevent a duplicated key from producing a valid-looking authentication key that later fools client tooling.

### Proof of Concept
The existing test `verify_multi_key_auth` in `types/src/transaction/authenticator.rs` is itself the PoC: it constructs `multi_key = MultiKey::new([sender0_pub, sender1_pub, sender1_pub], 2)`, builds `mk_auth_12` using `sender1`'s single signature keyed to indices 1 and 2, wraps it as `AccountAuthenticator::multi_key(mk_auth_12)`, and calls `signed_txn.verify_signature().unwrap()`, which succeeds — proving that a 2-of-3 threshold is satisfiable using only one distinct private key when that key is duplicated in the key list.     /// Creates a new MultiKey public key from a vector of single key public keys and a number representing the number of signatures required to authenticate a transaction.
    public fun new_multi_key_from_single_keys(single_keys: vector<single_key::AnyPublicKey>, signatures_required: u8): MultiKey {
        let num_keys = single_keys.length();
        assert!(
            num_keys > 0,
            error::invalid_argument(E_INVALID_MULTI_KEY_NO_KEYS)
        );
        assert!(
            num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS,
            error::invalid_argument(E_INVALID_MULTI_KEY_TOO_MANY_KEYS)
        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }

    /// Deserializes a MultiKey public key from a BCS stream.
    public fun deserialize_multi_key(stream: &mut bcs_stream::BCSStream): MultiKey {
        let public_keys = bcs_stream::deserialize_vector(stream, |x| single_key::deserialize_any_public_key(x));
        let signatures_required = bcs_stream::deserialize_u8(stream);
        MultiKey { public_keys, signatures_required }
    }
