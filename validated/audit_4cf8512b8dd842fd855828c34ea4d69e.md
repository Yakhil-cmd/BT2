### Title
Permanent Pairing Secret Leaked to Unauthorized Cosigners via Arbiter Contract Sharing - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `shareContractToCosigners()` forwards the entire contract row (via `getByHash`, a `SELECT *`) — including the `my_pairing_code` and `peer_pairing_code` fields, which embed the long‑lived permanent pairing secret (`device_pubkey@hub#pairing_secret`) — to every cosigner device on the contract's `my_address` wallet. This is analogous to the GitLab bug class (BIT‑gitlab‑2021‑39869), where an export/serialization routine indiscriminately included a sensitive authentication token (CI trigger token) that should have been scoped only to privileged parties, exposing it to any actor who could trigger the export.

### Finding Description
When a two-party arbiter contract is created, each side generates (or reuses) its **permanent** pairing secret via `device.getOrGeneratePermanentPairingInfo()`: [1](#0-0) 
This secret is a long-lived credential (expires `2038-01-01`, stored in `pairing_secrets` with `is_permanent=1`) that anyone holding it can use to pair with the device as a fully trusted correspondent — able to receive private payment chains, be offered signing requests, and appear in `arrSubjectsAllowedFromNoncorrespondents` whitelisted flows.

The contract, including `my_pairing_code`/`peer_pairing_code`, is persisted in `wallet_arbiter_contracts`: [2](#0-1) 

When the contract reaches `accepted` status (or whenever `shareContractToCosigners` is invoked, e.g. from `createSharedAddressAndPostUnit`), the *entire* contract row — fetched with `SELECT *` — is sent unfiltered to every cosigner device that is a signer on the wallet owning `my_address`: [3](#0-2) [4](#0-3) 

Unlike `createAndSend`, which explicitly `delete`s the `cosigners` field before sending to the counterparty peer, no equivalent redaction is applied before sharing with cosigners: `my_pairing_code` (the local user's own permanent pairing secret) and `peer_pairing_code` (the counterparty's permanent pairing secret, if already received) are both included in the outbound message body to cosigner devices: [5](#0-4) 

`getAllMyCosigners` resolves cosigner device addresses purely from `wallet_signing_paths`/`my_addresses` for the multisig wallet — these are devices entitled to co-sign transactions from that address, not devices that should be handed a durable pairing credential for the user or the counterparty: [6](#0-5) 

A cosigner who receives this permanent pairing code can pair as a full correspondent of either the contract owner or (once `peer_pairing_code` is populated) the counterparty, without the victim's consent, entirely outside the multisig trust boundary that was supposed to be limited to co-signing transactions on a shared address.

### Impact Explanation
Exposure of a permanent pairing secret to an unentitled cosigner allows that cosigner to pair with the victim device (owner of the contract or the counterparty) as a persistent correspondent. Once paired, the attacker-cosigner can:
- Receive private payment chains and other device messages intended for legitimate correspondents (`arrSubjectsAllowedFromNoncorrespondents` includes `pairing`, so an attacker can complete pairing even as an unknown device, then become a recorded correspondent for subsequent message routing).
- Be offered/forward multisig signing requests and inject itself into the contract/wallet's trust graph.
- Leak or misuse private contract details (title/text, contact info) tied to the arbiter dispute flow.

This constitutes unauthorized access/misuse of wallet and contract communications and can contribute to fund loss or freezing in multisig/arbiter contract flows (e.g., disrupting the mutual-signing process, intercepting private chains needed to complete a private-asset trade), matching the "AA fund loss or freezing" / "unauthorized spending" impact bar for Medium severity.

### Likelihood Explanation
Reachable by any unprivileged wallet participant who is configured as a signing-path cosigner on the multisig wallet used for `my_address` in an arbiter contract — no special privileges beyond being added as a cosigner are required. The offeror side triggers this automatically as part of the normal accept/shared-address flow (`respond()` → `shareContractToCosigners()`, and `createSharedAddressAndPostUnit()` → `shareContractToCosigners()`), so it fires on every ordinary arbiter contract accepted by a multisig wallet with more than one cosigning device — making it a routine, low-effort path to trigger rather than a rare edge case.

### Recommendation
Before sending the contract object to cosigners in `shareContractToCosigners` (and any other `sendMessageToDevice(..., "arbiter_contract_shared"/"arbiter_contract_offer"/"arbiter_contract_update", objContract)` call sites), strip `my_pairing_code` and `peer_pairing_code` (and any other durable secrets) from the payload, mirroring the existing redaction pattern already used for `cosigners` in `createAndSend`. If cosigners genuinely need a way to contact the counterparty, use a scoped/one-time pairing mechanism instead of forwarding the permanent pairing secret.

### Proof of Concept
1. Device A creates a multisig wallet requiring 2 signers: A (owner) and B (cosigner), and uses address from this wallet as `my_address` in an arbiter contract offered to Device C (peer).
2. A calls `arbiter_contract.respond(hash, "accepted", ...)` — this generates/reuses A's permanent pairing info and stores it as `my_pairing_code` on the contract via `setField`, then calls `shareContractToCosigners(hash)`.
3. `shareContractToCosigners` fetches the full row via `getByHash` (SELECT *) and sends it unmodified to cosigner B via `device.sendMessageToDevice(B, "arbiter_contract_shared", objContract)`, including `my_pairing_code = "<A_device_pubkey>@<A_hub>#<A_permanent_pairing_secret>"`.
4. Device B (a cosigner, with no special privilege besides being listed in `wallet_signing_paths`) receives the message and parses out A's permanent pairing secret from `objContract.my_pairing_code`.
5. B uses this secret to send a `pairing` message to A's hub, which is accepted per the whitelisted-subjects logic even for a previously-unknown correspondent, thereby pairing with A outside the intended cosigner-only trust relationship and gaining ongoing access to A's device messaging.

function shareContractToCosigners(hash) {
	getByHash(hash, function(objContract){
		getAllMyCosigners(hash, function(cosigners) {
			cosigners.forEach(function(device_address) {
				device.sendMessageToDevice(device_address, "arbiter_contract_shared", objContract);
			});
		});
	});
}

function getAllMyCosigners(hash, cb) {
	db.query("SELECT device_address FROM wallet_signing_paths \n\
		JOIN my_addresses AS ma USING(wallet)\n\
		JOIN wallet_arbiter_contracts AS wac ON wac.my_address=ma.address\n\
		WHERE wac.hash=?", [hash], function(rows) {
			var cosigners = [];
			rows.forEach(function(row) {
				if (row.device_address !== device.getMyDeviceAddress())
					cosigners.push(row.device_address);
			});
			cb(cosigners);
		});
}
