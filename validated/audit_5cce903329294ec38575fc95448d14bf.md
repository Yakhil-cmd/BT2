This confirms the vulnerability. The `Handler` base class provides a `stacks` helper method that scopes lookups to the repository named in the payload (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler#process` does not use it — it queries `Commit.where(sha: params.sha)` globally across all stacks/repositories.

### Title
StatusHandler#process writes a Status onto commits from any repository whose SHA matches the payload, ignoring `payload['repository']['full_name']` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` with no scoping to the repository named in the webhook payload, unlike the `Handler` base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers use. Any commit sharing that SHA — including one in a completely unrelated stack/repository — receives a `Status` row via `create_status_from_github!`.

### Finding Description
The broken binding: the code should enforce `payload['repository']['full_name'] == commit.stack.repository.full_name` for every `Commit` mutated, but `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` at [1](#0-0)  performs no such filter — it is a bare, instance-wide SQL lookup by `sha` only.

The webhook signature check in `WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App belonging to `repository_owner` (derived from `payload['repository']['owner']['login']`) [2](#0-1) . It authenticates *who sent the payload*, not *which commit rows may be touched*. Nothing after signature verification re-checks that the `sha` in the payload actually belongs to a commit tracked under the repository that was authenticated.

Contrast with the `Handler` base class, which explicitly provides a `stacks` scoping helper: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, where `repository_name` is read from `payload.dig('repository', 'full_name')` [3](#0-2) . Other handlers (e.g. `PushHandler`, `PullRequest` handlers) are built around this `stacks` scoping to constrain effects to the authenticated repository. `StatusHandler` bypasses this helper entirely and queries `Commit` unscoped by repository.

Exploit flow:
1. Attacker owns/controls a public GitHub repository "attacker/repo" with a Shipit-installed GitHub App (or the org's shared App, if Shipit is configured with a single GitHub App for multiple orgs — note: if a single shared App/secret is used across all installed orgs, the attacker only needs push access to any repo under that org to get a validly-signed payload).
2. Attacker pushes/creates a commit whose SHA collides with a commit SHA already tracked in victim stack B — trivially achievable using the empty git tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or by copying any commit verbatim (SHA is content-addressed and independent of origin).
3. Attacker (or their configured CI on that repo) fires a `status` webhook to `POST /webhooks` with `sha` = the colliding value, `state: success`, and `repository.full_name` = "attacker/repo". This payload is legitimately signed by the App tied to `repository_owner` = attacker's own org/login.
4. `verify_signature` passes because the signature genuinely matches attacker's own app's `webhook_secret` for their own repo.
5. `StatusHandler#process` runs `Commit.where(sha: <colliding sha>)`, which returns rows from every stack containing that SHA — including victim stack B's row — and calls `create_status_from_github!(params)` on all of them, writing a passing `Status`.

Existing guards fail because: `drop_unhandled_event` only checks the event type is registered, not the payload's repository; `verify_signature` binds only to `repository_owner`, not to specific commit rows; the `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) validates types but not repository ownership; there is no `Repository`/`Stack` scoping applied in `StatusHandler#process` at all.

### Impact Explanation
An attacker fully controlling their own low-privilege public repository can write arbitrary CI `Status` rows (state/description/context/target_url) onto commits belonging to any other tenant's `Stack` in the same Shipit instance, without ever naming that repository in the webhook payload. Since commit status directly gates `Commit#deployable?` (`success? && !blocked?`) [4](#0-3) , and success-state transitions enqueue `ProcessMergeRequestsJob` for continuous-delivery/merge-queue automation [5](#0-4) , this can push a victim commit into a "deployable" state or trigger merge-queue processing it should never have reached — an unauthorized/forged CI-status leading toward unauthorized deploy or merge decisions. This is a cross-tenant payload-to-mutation mismatch: repository A's authenticated payload mutates repository B's `Commit`/`Status` rows, matching the "payload for one repository mutating another's stack, commit, task or team" Critical category. It is repeatable against arbitrary stacks whenever a SHA collision exists (guaranteed for the empty-tree SHA, or achievable for any known commit hash the attacker copies), and the blast radius spans every stack/tenant hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs any GitHub repository with a Shipit-connected GitHub App (their own account/org, low cost), and at least one other stack in the instance that happens to contain a commit with the same SHA. This is guaranteed for empty-tree commits (very common in git history, e.g. initial commits, squash/rebase artifacts) and otherwise achievable deterministically by copying any known commit object (SHA is purely content-derived, not tied to origin repository). No secrets, sessions, or privileged roles are required — only the ability to push a commit and send a signed webhook from a repo the attacker legitimately owns. This is straightforward and repeatable per victim stack.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the base `Handler#stacks` helper: filter `Commit.where(sha: params.sha)` down to `commit.stack.in?(stacks)` (or `stacks.joins(:commits).where(commits: { sha: params.sha })`) before calling `create_status_from_github!`, so only commits belonging to a `Stack` under `Repository.from_github_repo_name(payload.dig('repository','full_name'))` are mutated.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories, `stack_a` (repo `attacker/repo`) and `stack_b` (repo `victim/repo`), each with a `Commit` sharing the same `sha` value (e.g. `"4b825dc642cb6eb9a060e54bf8d69288fbee4904"`).
2. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha` = the shared value, `state: "success"`.
3. Stub/allow signature verification for `attacker/repo`'s app only (as in existing `GithubHook.any_instance.stubs(:verify_signature).returns(true)` pattern) — do not touch `victim/repo`'s secret.
4. POST to `/webhooks` with the `X-Github-Event: status` header.
5. Assert: `stack_a`'s commit gained a `Status` (expected, same-repo case) AND `stack_b`'s commit also gained a `Status` with `state == "success"` (the violation), even though `payload['repository']['full_name'] != stack_b.repository.full_name`. Before fix both assertions pass (bug); after applying the recommended `stacks` scoping fix, only `stack_a`'s commit should gain the status and `stack_b`'s commit's `statuses.count` should remain unchanged.
