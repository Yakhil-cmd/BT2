### Title
EIP-3541 Validation Misplaced After Snapshot Revert: 0xEF-Prefixed Contract Code Permanently Stored with Value Locked — (`blockchain/vm/evm.go`)

---

### Summary

In `blockchain/vm/evm.go`, the `create()` function implements EIP-3541 (reject code starting with `0xEF`) in two separate locations. The check for the `IsKore && !IsPrague` hardfork window is placed **after** the snapshot-revert guard. When a contract's init code returns bytecode beginning with `0xEF`, the code is written to state and any transferred value is moved to the contract address before the error is set. Because the revert guard has already passed without error, the state is never rolled back. The transaction receipt shows failure, but the contract code and transferred KAIA remain permanently committed to state.

---

### Finding Description

Inside `evm.create()` the execution order is:

```
snapshot := evm.StateDB.Snapshot()                          // line 566
evm.StateDB.CreateSmartContractAccountWithKey(...)          // line 570
evm.StateDB.SetNonce(address, 1)                            // line 571
evm.Context.Transfer(...)                                   // line 573  ← value moved
ret, err = evm.interpreter.Run(contract, nil)               // line 584

// Prague-only 0xEF guard (BEFORE SetCode) — correct placement
if err == nil && ret[0] == 0xEF && evm.chainRules.IsPrague { // line 593
    err = ErrInvalidCode
}

evm.StateDB.SetCode(address, ret)                           // line 604  ← code written

// Snapshot revert guard
if err != nil {                                             // line 620
    evm.StateDB.RevertToSnapshot(snapshot)
}

// Kore 0xEF guard (AFTER SetCode AND AFTER revert guard) — WRONG placement
if err == nil && ret[0] == 0xEF &&
   evm.chainRules.IsKore && !evm.chainRules.IsPrague {      // line 631
    err = ErrInvalidCode
}
```

When `IsKore && !IsPrague` (the current production hardfork window):

1. Init code runs successfully, returning bytecode `0xEF…`.
2. `SetCode` writes the invalid bytecode to state — `err` is still `nil`.
3. The revert guard at line 620 sees `err == nil` and **does not revert**.
4. The Kore 0xEF check at line 631 sets `err = ErrInvalidCode`.
5. `create()` returns `ErrInvalidCode`, but the state mutation is permanent.

The developers acknowledge this in the source comment:

> *"This validation was incorrectly placed after the code was already stored in state DB, which should have been prevented. This is kept for backwards compatibility and will be properly handled after Prague hardfork."*

The existing test `TestEIP3541` in `tests/prague_evm_test.go` explicitly asserts the buggy behavior: `expectDeployed = true` for the `BeforePrague` case, confirming the code is stored in state even though the receipt status is `ReceiptStatusErrDefault`.

---

### Impact Explanation

| Corrupted value | Expected | Actual |
|---|---|---|
| `stateDB.GetCode(contractAddr)` | `nil` (reverted) | `0xEF…` bytecode permanently stored |
| `stateDB.GetBalance(contractAddr)` | `0` (reverted) | Equal to `value` sent with the tx |
| `stateDB.GetBalance(sender)` | Unchanged (reverted) | Reduced by `value` |
| `receipt.Status` | Failure | `ReceiptStatusErrDefault` (failure) — correct, but state is not clean |

- **KAIA locked**: Value transferred in the creation call is moved to the new contract address at line 573 before the snapshot is taken. Because the revert never fires, that KAIA is permanently locked. The contract account is created with `AccountKeyFail`, making it impossible to withdraw.
- **Address poisoning**: The contract address now has non-empty code and nonce = 1. Any future attempt to deploy to the same deterministic address (same sender nonce) will fail with `ErrContractAddressCollision`.
- **State/receipt divergence**: Callers observe a failed receipt but the chain state contains the deployed code, breaking any tooling or contract logic that relies on the invariant "failed deployment ⟹ no code at address."

---

### Likelihood Explanation

- **Hardfork window**: `IsKore` has been active since the Kore hardfork; `IsPrague` is not yet active. The vulnerable window is the entire current production lifetime of the chain.
- **Unprivileged trigger**: Any account can submit a `TxTypeSmartContractDeploy` (or an EVM `CREATE`/`CREATE2` opcode from within a contract) whose init code returns a byte string beginning with `0xEF`. No special role or permission is required.
- **Value at risk**: The bug is most damaging when `value > 0` is included in the creation call, but even a zero-value deployment permanently poisons the address.

---

### Recommendation

Move the Kore-era 0xEF check to the same location as the Prague check — **before** `SetCode` is called and **before** the snapshot-revert guard — so that a failed validation triggers the existing revert path:

```go
// After interpreter.Run() and MaxCodeSize check:

// Reject code starting with 0xEF (EIP-3541, Kore hardfork)
if err == nil && len(ret) >= 1 && ret[0] == 0xEF &&
   evm.chainRules.IsKore {
    err = ErrInvalidCode
}

// Prague-specific check (already correct, can be merged with above)
// ...

if err == nil {
    // SetCode ...
}

if err != nil {
    evm.StateDB.RevertToSnapshot(snapshot)  // now fires for ErrInvalidCode too
    ...
}
// Remove the post-revert 0xEF block entirely.
```

Additionally, add `vm.ErrInvalidCode` to the `errTxFailed2receiptstatus` map in `blockchain/state_transition.go` so the receipt carries a distinct, queryable status code rather than the generic `ReceiptStatusErrDefault`.

---

### Proof of Concept

The existing test `TestEIP3541` in `tests/prague_evm_test.go` already demonstrates the bug. The `"BeforePrague"` sub-case uses init code `610017600081600b8239f3ef01…` which returns runtime bytecode starting with `0xEF`. The test asserts:

```go
// receipt shows failure
assert.Equal(t, receipt.Status, types.ReceiptStatusErrDefault)   // line 117

// BUT the contract is present in state (expectDeployed = true)
assert.Equal(t, tc.expectDeployed, state.IsContractAvailable(deployedAddress))  // line 121

// AND the 0xEF code is stored
assert.Equal(t, expectedCode, state.GetCode(deployedAddress))    // line 124
```

To demonstrate value loss, send a non-zero `value` with the same transaction. After the block is committed, `state.GetBalance(contractAddr)` will equal the sent value, and `state.GetBalance(sender)` will be reduced accordingly, with no mechanism to recover the funds.
