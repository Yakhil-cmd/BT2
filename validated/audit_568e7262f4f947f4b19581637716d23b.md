### Title
Unprivileged label injection sets `LD_PRELOAD=true` in deploy-host process environment via `ReviewStack#env` label-to-env mapping - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` uppercases every PR label and injects it as an environment variable set to `"true"` with no denylist, and `LabelCapturingHandler#capture_labels` unconditionally persists whatever labels GitHub reports for a non-archived review-stack PR. Because `TaskCommands#env` merges `@stack.env` into the environment ultimately passed to `Command#unbundled_env` → `PTY.spawn`, a PR author who can attach the label `ld_preload` to their own PR causes `LD_PRELOAD=true` to be injected into every subsequent task's process environment for that stack.

### Finding Description
The broken binding: `Command#unbundled_env.key?('LD_PRELOAD')` should be `false` unless `deploy_spec.machine_env` (i.e., `shipit.yml`'s `machine.environment`, a repo-maintainer-controlled config) explicitly sets it. Instead, after labeling, `Command#unbundled_env.key?('LD_PRELOAD') == true` and its value is `'true'`.

Code path:
1. `LabelCapturingHandler#capture_labels?` allows label capture for any `labeled`/`unlabeled`/`reopened`/`opened` event as long as `stack.present? && !stack.archived?` — no author/permission check beyond stack existing and not archived: [1](#0-0) 
2. `capture_labels` writes the labels verbatim with no filtering/denylist: [2](#0-1) 
3. `ReviewStack#env` maps every persisted label to `LABEL_UPCASED => "true"` and merges it over the base env: [3](#0-2) 
4. `StackCommands#env` merges `@stack.env` in: [4](#0-3) 
5. `TaskCommands#env` merges `@stack.env` before `deploy_spec.machine_env`, so unless the repo's `shipit.yml` explicitly sets `LD_PRELOAD` (unlikely), the label-derived value survives: [5](#0-4) 
6. `Command#unbundled_env` merges `@env` (the fully-merged task env) over `BASE_ENV`, so `LD_PRELOAD` passes through unmodified into `PTY.spawn`: [6](#0-5) [7](#0-6) 

Exploit flow: attacker opens/owns a PR against a repository configured for review stacks (`provisioning_behavior` allowing stack creation), applies the label `ld_preload` to their own PR (label add on their own PR/fork requires only write access to that PR's labels, which repo owners of review-app-enabled repos commonly grant or which the PR author already has on their own fork-based flows depending on repo settings — this is a precondition, not a Shipit-side control). GitHub sends a signed `pull_request` `labeled` webhook, `LabelCapturingHandler` verifies via existing signature/schema checks (which validate authenticity of the webhook, not the semantic safety of the label string) and persists the label. Every subsequent CI/CD task (deploy, checks, provisioning) for that review stack runs with `LD_PRELOAD=true` in the environment used by `git`, `bundle`, `ruby`, etc.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`, archived-stack check) only validate the webhook's authenticity and that the target stack is not archived — none of them validate or filter the *content* of label names before they are mapped into process environment variables. No denylist/allowlist for label-to-env conversion exists anywhere in the codebase.

### Impact Explanation
Every task-running command (`git`, `bundle`, `ruby`, and any shell steps defined in `shipit.yml`) invoked via `Command#start`/`PTY.spawn` for the affected review stack will have `LD_PRELOAD=true` in its environment. Dynamic linkers generally fail to load a non-existent/invalid shared object named `true`, causing execution failures (denial of the review-stack build/deploy) or, depending on `ld.so` behavior and any attacker-controlled working directory content (e.g. a file literally named `true` reachable via relative resolution, which is non-default but not impossible in some loader configurations), potential preload of attacker-influenced code. This is scoped to the affected repository's review-stack build environment (per-repo blast radius, not cross-tenant) but demonstrates that an unauthenticated-to-Shipit, unprivileged-to-the-engine actor (only needs GitHub label permission on their own PR) can inject arbitrary environment variables into the deploy host's command execution context — a process-tampering primitive on the deploy host.

### Likelihood Explanation
Preconditions: target repository must have review stacks enabled (`provisioning_behavior` permitting), stack must not be archived, and the attacker must be able to add the label `ld_preload` (or any other environment-variable-colliding name) to their PR. Attacker cost is a single label API call/webhook; the injection is fully repeatable and immediately persists on every label toggle. No secrets, sessions, or Shipit privileges are required.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb), sanitize the label-derived environment keys: reject/skip labels whose uppercased name collides with security-sensitive environment variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `BASH_ENV`, `PATH`, etc.), or switch to an explicit allowlist/prefix scheme (e.g. only `LABEL_<name>`) so PR labels can never set raw, security-relevant environment variable names consumed by `Command#unbundled_env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual, not to be placed under excluded test/ path in real repo but illustrating the assertion)
test "PR label 'ld_preload' injects LD_PRELOAD into task command env" do
  stack = create_review_stack # non-archived review stack
  stack.pull_request.update!(labels: ['ld_preload'])

  task = create_task_for(stack)
  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new('true', env: env, chdir: task.working_directory)

  assert command.unbundled_env.key?('LD_PRELOAD')
  assert_equal 'true', command.unbundled_env['LD_PRELOAD']
end
```
This demonstrates: (a) `LabelCapturingHandler#capture_labels` performs no filtering on label content, (b) `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) unconditionally maps the label to `LD_PRELOAD => "true"`, and (c) this value survives all the way to `Command#unbundled_env` (lib/shipit/command.rb:103-105), the exact hash passed to `PTY.spawn`.
