### Title
Hookify PreToolUse/Stop hook rule evaluation fails open on unhandled exceptions, silently bypassing user-defined blocking rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The `hookify` plugin's `PreToolUse` and `Stop` hook executors are meant to enforce user-authored blocking rules (e.g. "deny edits to `.env`", "deny `rm -rf`") before a tool call is allowed to proceed. When rule evaluation raises an *unexpected* exception instead of returning a decision, the hook entry points catch the exception broadly and unconditionally emit an "allow" result (no `hookSpecificOutput.permissionDecision: deny`), exactly mirroring the external report's root cause: a function that is expected to fail closed (revert/deny) on an edge case instead silently returns a benign/neutral value, and the caller treats that as a normal successful outcome and proceeds — resulting in loss of the protection the user relied on.

### Finding Description
`RuleEngine._extract_field` builds the field value used for rule matching. For `MultiEdit`, it assumes every element of `tool_input["edits"]` is a dict and calls `.get()` on it without validation: [1](#0-0) 

If the tool call's `edits` array contains a non-dict element (e.g. a string), this raises an uncaught `AttributeError` inside `_extract_field`, which propagates up through `_check_condition` → `_rule_matches` → `evaluate_rules`: [2](#0-1) 

None of `rule_engine.py` catches this. It propagates to the hook entry point `pretooluse.py::main()`, which wraps `evaluate_rules()` in a broad `except Exception` that only emits a `systemMessage` (no `hookSpecificOutput`/`permissionDecision: "deny"`), and unconditionally exits `0`: [3](#0-2) 

Per `RuleEngine.evaluate_rules`, an empty/`systemMessage`-only result (no `hookSpecificOutput`) is functionally equivalent to "no rule matched → allow the operation": [4](#0-3) 

The same fail-open pattern exists in the `Stop` hook executor, which is meant to block the agent from ending a turn when a user-defined blocking rule matches: [5](#0-4) 

This is the direct analog of the reported bug class: the external report describes a mint function that is *expected* to revert on the final/edge-case call but instead returns a benign value (`0`), and the caller (the market contract) trusts that value and proceeds to disburse funds as if the operation succeeded, causing user loss. Here, the "enforcement function" (`evaluate_rules`) is expected to fail closed (deny) when it cannot properly evaluate a rule against attacker-influenced input, but a crash inside evaluation is caught generically and converted into a benign "allow" result, and the caller (Claude Code's hook runner) trusts that result and lets the tool call/turn-stop proceed — even though a legitimate blocking rule may never have been evaluated because a *different*, earlier or same rule's field-extraction crashed first.

### Impact Explanation
The `model` is the effective attacker in the hook-bypass trust boundary (per this project's own security guidance: "LLM-agent capability gates ... the model is the attacker, the user is the victim"). A model turn that has been prompt-injected, or that is simply exploring edge cases, can issue a `MultiEdit` tool call with a malformed `edits` array. If the user has configured a hookify rule intended to block dangerous edits (e.g. writing secrets, editing protected files, or blocking a compound `Bash`+`MultiEdit` operation matched against the `Stop` event/`transcript`), that rule silently never fires for the current tool call — the local safety-net the user configured is bypassed with no denial, no block, and (via `finally: sys.exit(0)`) no indication beyond a `systemMessage` note, which may not read as an actual denial to a human skimming output. This is a direct, unprivileged-user-facing (Claude Code operator) violation of the hook-bypass/tool-authorization trust boundary — the exact class the project's own `silent-failure-hunter` agent and security-guidance hooks explicitly call out as unacceptable ("Never silently fail in production code").

### Likelihood Explanation
Likelihood is moderate: it requires (a) the user to have installed/enabled the `hookify` plugin with at least one blocking rule, and (b) a tool call (from the model) whose input shape triggers an unhandled exception in field extraction (demonstrated concretely for `MultiEdit`/`edits`, but the same fail-open funnel applies to *any* exception raised anywhere in rule evaluation, e.g. future field types, malformed `input_data`, etc.). Because the model — not the user — constructs `tool_input`, and the model's behavior can be influenced by adversarial content the agent reads (files, web content, MCP tool output), the crash-inducing input is plausibly attacker-influenceable even without the end user's cooperation.

### Recommendation
- In `RuleEngine._extract_field` (and generally, `_check_condition`/`_rule_matches`), validate types defensively — e.g. skip or coerce non-dict elements in `edits` instead of calling `.get()` unconditionally — plugins/hookify/core/rule_engine.py:246-252.
- In `pretooluse.py::main()` and `stop.py::main()`, do not fail open on unexpected exceptions during rule evaluation. At minimum, distinguish "no rules configured/matched" from "evaluation crashed": on crash, either (a) re-raise/emit a blocking decision with a clear error so the user is aware enforcement did not run, or (b) log loudly and require an explicit opt-in for fail-open behavior, consistent with the project's own stated policy that "Never silently fail in production code."
- Add regression tests feeding malformed `tool_input` shapes (non-dict list elements, missing keys, wrong types) through `evaluate_rules` to ensure exceptions cannot silently defeat blocking rules.

### Proof of Concept
1. User creates `.claude/hookify.block-secrets.local.md` with a blocking rule matching `MultiEdit`/`content` containing a secret pattern (`action: block`).
2. The agent (model) issues a `MultiEdit` tool call where `tool_input.edits` is `["not-a-dict"]` instead of a list of edit objects — a shape the model could plausibly produce due to a malformed patch, tool-schema drift, or prompt injection instructing it to smuggle content past the local guard.
3. `pretooluse.py` invokes `RuleEngine.evaluate_rules`, which calls `_extract_field` for the `MultiEdit` `content`/`new_text` field: `' '.join(e.get('new_string', '') for e in edits)` raises `AttributeError: 'str' object has no attribute 'get'`.
4. The exception propagates uncaught out of `rule_engine.py`, is caught by the broad `except Exception` in `pretooluse.py::main()`, which prints `{"systemMessage": "Hookify error: ..."}` and calls `sys.exit(0)` — no `hookSpecificOutput`/`permissionDecision: "deny"` is emitted.
5. Claude Code's hook runner sees no denial from this hook and proceeds to allow the `MultiEdit` tool call, even though the user's blocking rule was never actually evaluated against it.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
