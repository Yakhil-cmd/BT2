### Title
ERC721 Bridge Mint-Burn Mode Permanently Bricked by Overlapping Token ID Mint — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In `modeMintBurn = true`, `handleERC721Transfer` calls `mintWithTokenURI(_to, _tokenId, _tokenURI)` on the destination-chain NFT contract. The underlying `ERC721._mint` unconditionally reverts if the token ID already exists. Because `ServiceChainNFT` inherits `MinterRole` and the deployer retains minter rights by default — and any minter can grant the role to others — a second minter can pre-mint the exact token ID the bridge is about to issue. Every subsequent operator attempt to handle that request nonce will revert with `"mint failed"`, permanently blocking settlement of that transfer while the user's NFT has already been burned on the source chain.

---

### Finding Description

`BridgeTransferERC721.handleERC721Transfer` (mint-burn path):

```solidity
// BridgeTransferERC721.sol lines 66-67
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
}
```

`mintWithTokenURI` delegates to `ERC721._mint`:

```solidity
// ERC721.sol lines 210-212
function _mint(address to, uint256 tokenId) internal {
    require(to != address(0), "ERC721: mint to the zero address");
    require(!_exists(tokenId), "ERC721: token already minted");
```

`ServiceChainNFT` inherits `ERC721MetadataMintable` → `MinterRole`. The `MinterRole` constructor adds `msg.sender` (the deployer) as a minter, and `addMinter` is callable by any current minter:

```solidity
// MinterRole.sol line 26
function addMinter(address account) public onlyMinter { _addMinter(account); }
```

The bridge is added as an additional minter via `erc721.AddMinter(bridgeAddr)`, but the deployer is never removed. Any minter can therefore mint an arbitrary token ID at any time.

**Execution path:**

1. User on source chain calls `requestERC721Transfer` for token ID `T`. In mint-burn mode, `ERC721Burnable(_tokenAddress).burn(T)` is executed — the token is destroyed on the source chain. [1](#0-0) 

2. Before bridge operators reach quorum and call `handleERC721Transfer` on the destination chain, any minter (e.g., the NFT deployer) calls `mintWithTokenURI(anyAddress, T, "")` directly on the destination NFT contract. Token ID `T` now exists.

3. Bridge operators call `handleERC721Transfer(..., T, ...)`. The function passes `_lowerHandleNonceCheck`, passes `_voteValueTransfer` (reaching quorum), updates `handleNoncesToBlockNums`, calls `_updateHandleNonce`, emits `HandleValueTransfer`, then hits: [2](#0-1) 

```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```

This reverts with `"ERC721: token already minted"`. [3](#0-2) 

4. Because the entire transaction reverts, `closedValueTransferVotes[nonce]` is **not** set to `true`. Operators can retry, but every retry will revert identically as long as token ID `T` exists on the destination chain.

5. There is no admin function to skip a nonce, override the token ID, or otherwise recover the stuck transfer. The `lowerHandleNonce` window advances only when `handleNoncesToBlockNums[i] > 0` for a contiguous range — which never happens for this nonce since the transaction always reverts. [4](#0-3) 

---

### Impact Explanation

- **Permanent loss of bridged ERC721 NFT.** The token is burned on the source chain (irreversible) and can never be minted on the destination chain.
- **Bridge nonce permanently stuck.** Because `handleNoncesToBlockNums[nonce]` is never written (transaction always reverts), `lowerHandleNonce` cannot advance past this nonce, blocking recovery accounting for all subsequent nonces in the 200-slot window.
- No admin escape hatch exists in `BridgeTransferERC721` to skip a nonce or substitute a different token ID.

---

### Likelihood Explanation

- The `ServiceChainNFT` deployer is automatically a minter and is never required to renounce that role. [5](#0-4) 
- `addMinter` is callable by any current minter with no owner restriction, so the minter set can grow arbitrarily. [6](#0-5) 
- The deployer could trigger this accidentally (e.g., minting for a test or airdrop) or a second minter added for another purpose could collide with a pending bridge transfer.
- The window of vulnerability is the latency between the source-chain burn event and the destination-chain `handleERC721Transfer` reaching quorum — typically multiple blocks.

---

### Recommendation

1. **Enforce single-minter invariant:** After granting the bridge contract the minter role, the deployer should call `renounceMinter()` to remove themselves. Document this as a required deployment step.
2. **Check-before-mint:** In `handleERC721Transfer`, check `_exists(tokenId)` before calling `mintWithTokenURI`. If the token already exists and is owned by the intended recipient, treat the transfer as already settled. If owned by someone else, revert with a distinct error and provide an admin escape (e.g., `skipHandleNonce`) so the nonce can be manually closed.
3. **Separate minter role per bridge:** Restrict `addMinter` so only the bridge owner (not any minter) can grant the role, preventing uncontrolled minter proliferation.
