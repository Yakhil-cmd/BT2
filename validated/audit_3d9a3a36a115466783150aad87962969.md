### Title
`StatusHandler#process` matches commits globally by `sha` without repository scoping via `#stacks`, allowing cross-tenant forged commit statuses - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every default handler except `StatusHandler` narrows its `Commit`/`Stack` query through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload['repository']['full_name'])`. `StatusHandler#process` instead runs `Commit.where(sha: params.sha)` with no repository filter at all, so any `sha` value that happens to exist on any stack in the Shipit instance — regardless of which repository the webhook claims to be from — will have a status attached to it.

### Finding Description
The claimed binding — "every `Handler` in `Shipit::Webhooks.default_handlers` narrows its `Commit`/`Stack` queries via `#stacks` (i.e. via the payload's own `repository_name`)" — is false specifically for `StatusHandler`.

- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) resolves `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, scoping subsequent queries to the repository named in the payload. [1](#0-0) 
- `PushHandler#process` correctly uses this: `stacks.not_archived.where(branch:)`. [2](#0-1) 
- `StatusHandler#process` never calls `#stacks`; it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, instance-wide lookup keyed only on the git SHA. [3](#0-2) 

Root cause: SHA1 commit hashes are content-derived and are not unique per Shipit installation — the same SHA can legitimately exist across unrelated `Stack`s tracking forks, mirrors, or repositories sharing history (or, in a pathological/attacker-controlled scenario, a fabricated payload can simply name a SHA that is known to exist on a victim stack, e.g., learned from public status pages, PR listings, or the Shipit UI itself). Because `StatusHandler` never checks that the payload's `repository.full_name` actually matches the `stack.github_repo_name` of the commit(s) being updated, a webhook signed for repository A can silently attach a fabricated status to a `Commit` belonging to stack/repository B.

Exploit path: The GitHub webhook signature (`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49`) is computed using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the *same attacker-controlled payload* (`params.dig('repository','owner','login')`). GitHub Apps use a single webhook secret shared across all installations of the App; `verify_signature` only checks that the signature is valid for whatever organization is named in the payload and that Shipit knows about that organization (raises `GithubOrganizationUnknown` otherwise) — it does not verify that the named repository is the one that actually generated the SHA being reported. An attacker who owns/controls any repository where the shared GitHub App is installed (i.e., any org onboarded to this Shipit instance) can therefore submit a validly-signed `status` event whose `sha` and `state` are attacker-chosen, and it will be applied to any `Commit` row in the database matching that SHA, independent of which repository/stack the commit actually belongs to.

Why other guards don't help: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` (the `params do ... end` schema in `status_handler.rb:7-18`) only validates types/presence of `sha`, `state`, etc., not repository ownership; there is no model validation on `Commit#sha` restricting it to one stack.

### Impact Explanation
An attacker with access to any onboarded repository can post a fabricated `success` (or `failure`) status for a commit SHA belonging to a completely different, unrelated tenant's stack. Since `Commit#deployable?` and continuous delivery gating (`Commit#schedule_continuous_delivery`, `Stack#continuous_deployment?`) rely on aggregated status state (`Commit#status`, `blocked?`), forging a `success` status can defeat CI/CD gating on a victim stack and trigger an unauthorized deploy for a commit that never actually passed CI — matching the "unauthorized deploy" Critical impact category. This is repeatable against any commit SHA the attacker can guess or observe (e.g., visible in the victim's Shipit UI, PR page, or shared fork history), and is not limited to a single repository — it works across all repositories/stacks hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs webhook delivery capability for *some* repository/organization already configured with Shipit's GitHub App (i.e., they must be able to trigger a `status` webhook from an org onboarded to the instance — a low bar for any contributor to a monorepo, forked project, or any repo in a multi-tenant Shipit deployment). They need to know or guess a target commit SHA on the victim stack (often publicly discoverable via the victim's own Shipit UI, GitHub, or shared commit history in forks). No Shipit credentials, session, or API token are required — only the ability to cause GitHub to emit a `status` event from an installation of the shared GitHub App. This is feasible and repeatable per commit/target stack.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through `stacks` (the same `Repository.from_github_repo_name(repository_name)`-derived scope used elsewhere), e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or, more efficiently, `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status payload can only affect commits belonging to the repository that the (signature-verified) payload claims to represent.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new)
test "#process does not scope commits by the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_payload = {
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'sha' => victim_stack.commits.last.sha,
    'state' => 'success'
  }

  # Handler#stacks would resolve to Stack.none for 'attacker/unrelated-repo'
  handler = Shipit::Webhooks::Handlers::StatusHandler.new(attacker_repo_payload)
  assert_equal Shipit::Stack.none.to_a, handler.send(:stacks).to_a

  # Yet #process still finds and mutates the victim's commit, proving #stacks is never consulted
  assert_difference -> { victim_stack.commits.last.statuses.count }, 1 do
    handler.process
  end
end

test "contrast: PushHandler#process is scoped via #stacks" do
  handler = Shipit::Webhooks::Handlers::PushHandler.new(
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'ref' => 'refs/heads/master',
    'after' => 'deadbeef'
  )
  assert_no_difference -> { Shipit::Deploy.count } do
    handler.process # no-op because stacks resolves to Stack.none
  end
end
```
