### Title
Webhook signature verification is bound to `repository.owner.login`, but repository resolution uses the independent `repository.full_name` field, allowing cross-organization repository mutation - ([File: app/models/shipit/repository.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate the webhook signature using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')`. But `Repository.from_github_repo_name`, used by every PullRequest handler (`OpenedHandler#repository`, `LabeledHandler`, `UnlabeledHandler`, `Handler#stacks`), resolves the target repository from the independent `params.dig('repository', 'full_name')` field. Since both fields live in the same attacker-supplied JSON body and are never cross-checked, an attacker who controls a webhook secret for one organization can craft a payload whose `owner.login` matches their own org (satisfying signature verification) while `full_name` points at a victim organization's repository (driving the actual database lookup and mutation).

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`Shipit.github(organization: repository_owner).verify_webhook_signature(...)` succeeding **should imply** `Repository.from_github_repo_name(params.repository.full_name).owner == repository_owner`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb` lines 24-30, 59-62: `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to select the org-scoped webhook secret (`Shipit.github(organization: repository_owner)`) for HMAC verification.
- `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` line 52 and `app/models/shipit/webhooks/handlers/handler.rb` line 37: repository resolution uses `params.repository.full_name` / `payload.dig('repository', 'full_name')`.
- `app/models/shipit/repository.rb` lines 53-56: `Repository.from_github_repo_name` downcases and splits on `/` and does a direct `find_by(owner:, name:)` with no comparison to `repository_owner`.

Because `repository.owner.login` and `repository.full_name` are two independently-controlled JSON keys in the same raw POST body, and HMAC verification only checks the byte-for-byte body against a secret keyed off of `owner.login`, an attacker who owns `attacker-org` and has configured a legitimate webhook secret for it can send:
```json
{
  "action": "opened",
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/some-repo" },
  ...
}
```
signed with `attacker-org`'s secret. `verify_signature` passes because it validates using `attacker-org`'s secret against `repository_owner = "attacker-org"`. The handler then resolves `Repository.from_github_repo_name("victim-org/some-repo")`, finding the real victim record, and `ReviewStackAdapter#find_or_create!` creates/mutates a `ReviewStack` under `victim-org`'s repository — a write authenticated only by attacker-org's own secret.

No existing guard prevents this: `verify_signature` never re-checks `full_name`'s owner against `repository_owner`; `ExplicitParameters` schemas (`requires :repository do requires :full_name, String end`) only enforce type/presence, not consistency with `owner.login`; `Repository.from_github_repo_name` performs no organization-scoping check at all.

### Impact Explanation
An attacker with legitimate control of one Shipit-configured organization's webhook secret can forge a payload that creates or mutates `ReviewStack`/`PullRequest` records under a **different, victim** organization's repository. This is a cross-tenant write authenticated by the wrong party's credentials — matching the Critical category "a payload for one repository mutating another's stack." It is repeatable against any repository/organization pair configured on the same multi-tenant Shipit instance, for any PullRequest webhook event (`opened`, `labeled`, `unlabeled`, `edited`, etc.), each invocation costing only one signed HTTP POST.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where the attacker controls (and can sign for) at least one configured organization (`attacker-org`) while a separate victim organization (`victim-org`) is also configured (`Shipit.github_organizations`). This is a realistic and explicitly stated deployment topology. The attacker only needs to compute an HMAC over an arbitrary raw body using their own known secret and POST it to `/webhooks` — no GitHub API access, no victim secret, and no privileged Shipit role are needed. Cost is a single crafted HTTP request; the flaw is deterministic and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`/`Repository.from_github_repo_name`), enforce that the owner parsed from `repository.full_name` matches `repository_owner` used for signature verification before processing the event — e.g., reject the webhook if `params.dig('repository','full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`. Alternatively, make `Repository.from_github_repo_name` (or its callers) take the authenticated `repository_owner` as an explicit argument and scope the `find_by` to that owner, rather than trusting the unauthenticated `full_name` field independently.

### Proof of Concept
Minitest integration test plan (`test/controllers/webhooks_controller_test.rb` style, not to be placed under `test/` per scope rules but described conceptually):
1. Create two `Shipit::Repository` records: `victim-org/some-repo` (with `review_stacks_enabled` and `provisioning_behavior_allow_all`) and stub `attacker-org` as a second configured organization with a known `webhook_secret`.
2. Build a `pull_request` "opened" payload where `params['repository']['owner']['login'] = 'attacker-org'` and `params['repository']['full_name'] = 'victim-org/some-repo'`.
3. Compute `X-Hub-Signature` using `attacker-org`'s webhook secret (stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true`, and ensure `Shipit.github(organization: 'victim-org')` is never invoked/its secret never used).
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert: (a) response is `200 OK` (signature accepted); (b) a `Shipit::ReviewStack` **was** created for `victim-org/some-repo` — demonstrating that `repository_owner` (`"attacker-org"`, the value that authenticated the request) does **not** equal `Repository.from_github_repo_name(params.repository.full_name).owner` (`"victim-org"`), proving the binding is violated and the victim repository was mutated by a payload only the attacker's own secret authenticated.
