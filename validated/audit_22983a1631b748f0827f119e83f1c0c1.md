### Title
Pool repay/recapitalize refund pays out the declared amount's "excess" from real custody without verifying any funds were transferred in - (File: contracts/pool/src/ops/repay.rs)

### Summary
The analog of the Unitas `_swapOut` bug is a payout computed from a declared/request-side number instead of the amount the pool actually holds. In `ops::repay::apply` and `ops::recapitalize::apply`, the pool computes a refund/overpayment as `declared_amount - applied` and immediately transfers it to `payer` via `transfer_out`, trusting that "the controller transfers the repay amount into the pool before this call" [1](#0-0) . The pool never checks the inbound balance delta; the refund is debited neither from the `cash` book nor gated by `require_reserves`, so a direct call with a fabricated `amount` pays real tokens out of the pool's custody.

### Finding Description
`repay::accounting` resolves `action.amount` against the position's debt. On a market with no debt (or after `clean_bad_debt`/`seize_positions` burned it), `resolve_repay` takes the full-close branch: `net_repay = 0` and the entire declared `amount` becomes `overpayment` [2](#0-1) . `apply` then calls `transfer_out(payer, overpayment)`, which executes a real SAC `token.transfer` from the pool to the attacker [3](#0-2) . The same shape exists in `recapitalize`: `applied = amount.min(backing_shortfall)` and `refund = amount - applied`, so on a solvent market `applied = 0` and the whole `amount` is refunded [4](#0-3) . The repo's own test proves the drain: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `pool.repay(payer, amount = pool_balance)` with zero transferred in and zero debt, and custody is emptied while the `cash` book is untouched [5](#0-4) .

### Impact Explanation
Theft of user funds plus a follow-on withdrawal DoS — both accepted impacts. The attacker sets `payer` to an address they control and receives the pool's full token balance. Afterwards the `cash` book still claims the funds exist, so `require_reserves` passes and honest suppliers' `withdraw` calls revert inside the SAC transfer with `BalanceError`, exactly as documented in `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` [6](#0-5) . This is not a fail-closed DoS quirk: real tokens leave the contract for a liability that was never funded.

### Likelihood Explanation
A single unprivileged transaction: call `LiquidityPool::repay` (or `recapitalize`) directly on the pool with `payer = attacker`, `action.amount = token.balance(pool)`, on a market whose `borrowed` scaled amount is zero (fresh market, or after bad-debt seizure). No controller entrypoint, timing, or oracle state is needed; the refund path requires no `require_auth` on the transfer-out and the prefunding invariant is enforced nowhere in the pool.

### Recommendation
Measure the actual inbound balance delta (balance-after minus balance-before the controller's transfer) and cap `overpayment`/`refund` at that delta, or refund only what the bookkeeping credited. Equivalently, restrict `repay`/`recapitalize` to the controller via `require_auth`/caller check so the prefunding invariant is enforced, and debit the refund from `cash`/`require_reserves` like any other outbound transfer.

### Proof of Concept
1. Deploy pool, add a market for `T`; suppliers deposit so `token.balance(pool) = B`, `borrowed = 0` (or seize all debt).
2. Attacker calls `pool.repay(attacker, PoolAction { hub_asset, amount: B })` with no prior transfer.
3. `resolve_repay` returns `overpayment = B`, `net_repay = 0`; `transfer_out` sends `B` to attacker.
4. A supplier's `withdraw` now passes `require_reserves` (book still shows `B`) and reverts inside `token.transfer` — funds are gone.

Confirmed by `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` and `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` [7](#0-6) .

Caveat: whether the pool contract exposes `repay`/`recapitalize` to arbitrary callers or intends controller-only access (enforced off-chain or by address check elsewhere) could not be fully verified within the available context; the repo's own tests demonstrate direct calls succeed and drain custody, which supports unprivileged reachability.

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(position, net_repay);
    RepayOutcome {
        cache,
        mutation,
        snapshot,
        overpayment,
    }
}

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

    RecapitalizationOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: applied,
        },
        refund,
    }

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
