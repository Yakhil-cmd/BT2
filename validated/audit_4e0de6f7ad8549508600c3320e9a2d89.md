### Title
Cross-repository status webhook flips `commit.deployable?` for an unrelated stack because `StatusHandler#process` looks up commits by SHA alone - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no scoping to the repository/stack that the incoming webhook was verified for. Since `WebhooksController#verify_signature` only proves that the payload came from GitHub for the org named in the payload's own `repository.owner.login`, an attacker who owns a repository sharing a commit SHA with a victim's repository (e.g. a public fork) can post a legitimate, correctly-signed `status` event for their own org and flip the state of a `Status` row attached to a completely different stack.

### Finding Description
The intended binding is: `commit.deployable?` for stack `S` may only change as a result of a webhook whose verified signing org equals `S.repository.owner`. Concretely: `verified_org(webhook) == S.repository.owner` must hold before `Status` rows tied to `S`'s commits are written.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` from the **attacker-controlled JSON body** and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0)  This only proves the payload was HMAC-signed by GitHub for *some* org that Shipit knows about - specifically the org the attacker claims to own in the payload. It says nothing about whether the `sha` in the payload actually belongs to a commit tracked under that org's repositories.
2. `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is **global across the entire `commits` table**, not scoped to any stack/repository. `Commit#belongs_to :stack` with no unique-per-repo constraint enforced in this lookup. [3](#0-2) 
3. `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` writes a new `Status` row with `state: github_status.state` for **whatever stack the matched commit belongs to** - not the attacker's stack. [4](#0-3) [5](#0-4) 
4. `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `state`/`success?` are delegated to `status`, which is derived from the most recent, highest-severity `Status` row. [6](#0-5)  Injecting a `failure`/`error` `Status` therefore flips `deployable?` to `false` for the victim stack.
5. `Status#schedule_continuous_delivery` fires on create [7](#0-6) , and downstream `Stack#trigger_continuous_delivery`/`next_expected_commit_to_deploy` uses `commits_to_deploy.find(&:deployable?)` [8](#0-7) , so the victim's continuous delivery is blocked by a commit no longer considered deployable.

Attacker's exact request: fork the victim's public repository (forks retain identical commit SHAs for unmodified history) so the attacker's own repo — already onboarded as a legitimate Shipit stack with a real, correctly configured webhook secret for the attacker's org — shares a SHA with the victim's tracked commit. The attacker then creates a commit status on that SHA within their own fork via the ordinary GitHub API/UI (an action available to any repo owner), causing GitHub itself to emit a genuinely-signed `status` webhook event, `state: 'failure'`, for the attacker's org, naming the attacker's own `repository`. This webhook is correctly signed and passes `verify_signature` because verification is keyed off the payload's *own claimed* `repository.owner.login`, not off any per-commit repository check. `StatusHandler#process` then matches every `Commit` row with that SHA — including the victim's — and writes the failing status to it.

Existing guards do not catch this: `verify_signature` authenticates "a webhook for org X", not "a webhook for the repository that owns this SHA"; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler.params` only validate shape (`sha`, `state`, etc.), not repository ownership; there is no code anywhere in `StatusHandler#process`, `Commit#create_status_from_github!`, or `Status.replicate_from_github!` that cross-checks `params.dig('repository', ...)`/`repository_owner` against `commit.stack.repository`.

### Impact Explanation
A payload verified for one repository (the attacker's) mutates another repository's stack/commit state (`Status` write + resulting `deployable?` flip), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely this lets an attacker block or delay a victim's automated deploy (`Stack#trigger_continuous_delivery`) using only their own, unrelated repository, without any credentials for the victim's org. It is repeatable against any public repository whose history the attacker can fork/replicate SHAs from, and generalizes to any two stacks that end up sharing a commit SHA (forks, cherry-picks, mirrors, monorepo splits, etc.), so the blast radius extends across tenants configured in the same Shipit instance.

### Likelihood Explanation
Preconditions are modest and match the scenario: victim stack has `ignore_ci? == false` and is currently `success?`/deployable; attacker needs only an ordinary public fork of the victim's repository (or any means of sharing a SHA) plus their own repository already onboarded as a Shipit stack with a working webhook (a completely normal, legitimate setup, as stated in the prompt). No Shipit session, API token, or GitHub secret is required — the attacker only needs write access to their own fork, which any GitHub user has by definition. This is a low-cost, fully repeatable action (one API call to set a commit status on their own fork).

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any similar handler) to the repository verified by the signature: resolve `Commit` rows only through `Stack`s whose `Repository` matches `params.dig('repository', 'full_name')`/`repository_owner`, e.g. `Commit.joins(:stack).merge(Stack.where(repository: matched_repository)).where(sha: params.sha)`, rather than a bare global `Commit.where(sha:)`. More generally, every inbound webhook handler that mutates commit/stack state should assert that the payload's declared `repository` corresponds to the actual `Stack`/`Commit` being modified, not merely that the payload is validly signed for *some* org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook for attacker's repo flips deployable? on a victim stack sharing the same sha" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to victim stack, currently success/deployable
  assert_predicate victim_commit, :success?
  assert_predicate victim_commit, :deployable?

  # Simulate a second, unrelated commit row (different stack) sharing the same sha,
  # as would occur via a fork of the victim's repository.
  attacker_stack = shipit_stacks(:attacker) # legitimate, unrelated stack/org
  attacker_commit = attacker_stack.commits.create!(sha: victim_commit.sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => attacker_stack.repository.full_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  # Signature verified genuinely for attacker's org only.
  GitHubApp.any_instance.stubs(:verify_webhook_signature).returns(true)

  post :create, body:, as: :json

  assert_equal 'failure', victim_commit.reload.state
  refute_predicate victim_commit, :deployable?
end
```
This demonstrates the binding equality `verified_org(webhook) == victim_stack.repository.owner` does **not** hold (verified org = attacker's org, victim stack belongs to a different org), yet `victim_commit.deployable?` still flips from `true` to `false`, proving the cross-repository write.
