### Title
Cross-org label mutation via decoupled `repository.owner.login` (signature binding) and `repository.full_name` (data lookup) fields - ([File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to verify the raw payload bytes against using `repository.owner.login` (falling back to `organization.login`), while `LabelCapturingHandler#capture_labels` resolves the target `Repository`/`Stack`/`PullRequest` using the independent `repository.full_name` field from the same JSON body. Because these are two separate, attacker-controlled keys inside one self-crafted request body, an attacker holding a valid webhook secret for their own org (ORG_A) can set `repository.owner.login = "ORG_A"` (so the HMAC verifies) while setting `repository.full_name = "ORG_B/victim-repo"` (so the handler mutates ORG_B's stack).

### Finding Description
The broken binding: `repository_owner` used in `Shipit.github(organization: repository_owner)` / `verify_webhook_signature` at [2](#0-1)  and [3](#0-2)  should equal the org actually addressed by `params.repository.full_name` used in `LabelCapturingHandler#repository` at [4](#0-3) . These are not the same read — `repository_owner` comes from `params.dig('repository','owner','login')`, and `full_name` from `params.dig('repository','full_name')`, both independently settable by whoever crafts the raw JSON body, with no code anywhere enforcing `full_name.split('/').first == owner.login`.

Attack flow: attacker who legitimately administers ORG_A's GitHub integration (and therefore knows ORG_A's `webhook_secret`, which is a value they/the org configured on GitHub's webhook page, per `docs/setup.md` "Using Multiple Github Applications") crafts a raw JSON body directly (bypassing GitHub) with `X-Github-Event: pull_request`, `repository.owner.login = "ORG_A"`, `repository.full_name = "ORG_B/victim-repo"`, `number` matching a real PR on ORG_B's victim stack, and `pull_request.labels` set to attacker-chosen names. They compute `X-Hub-Signature` themselves using ORG_A's secret via HMAC-SHA1 over the exact bytes, matching `GitHubApp#verify_webhook_signature` at [5](#0-4) . `verify_signature` passes because it only checks the signature against ORG_A's config, agreeing with `repository.owner.login = "ORG_A"` in the same body — it never checks `full_name`. The request reaches `LabelCapturingHandler`, which resolves `repository` via `Repository.from_github_repo_name(params.repository.full_name)` — a pure string split with no owner cross-check, per `Repository.from_github_repo_name` at [1](#0-0)  — finds ORG_B's `Repository`/`ReviewStack`, and `capture_labels` calls `pull_request.update!(labels: ...)` at [6](#0-5) , overwriting ORG_B's `PullRequest#labels`.

Existing guards fail to prevent this: `verify_signature` only authenticates that the byte content was signed with *some* org's secret matching the `owner.login`/`organization.login` field of that same body — it establishes no relationship between the authenticated org and the `repository.full_name` field consumed downstream. `ExplicitParameters` schema (`params do ... end`) only validates types/presence, not cross-field consistency. No handler checks that `params.repository.full_name`'s owner segment matches `repository_owner`/the verified org.

### Impact Explanation
An attacker who administers (or self-signs a webhook secret for) one org can silently overwrite the `labels` column of `Shipit::PullRequest` records belonging to a completely different org's stack, without needing that other org's secret, session, or API token. Since labels drive `LabeledHandler`/`UnlabeledHandler` archive/unarchive decisions and merge-queue label rules elsewhere in the engine, this can indirectly flip provisioning/merge-gating behavior for another tenant's PR. This is repeatable against any victim org/repo/PR number the attacker can guess or observe (PR numbers and repo names are typically public), matching the "payload for one repository mutating another's stack" Critical impact category.

### Likelihood Explanation
Preconditions: attacker must know a valid `webhook_secret` for at least one org configured in Shipit (achievable by being that org's own repo/webhook admin, a real-world scenario in multi-tenant Shipit deployments per `docs/setup.md`'s "Using Multiple Github Applications" section), and the victim org must have an active review stack whose `pull_request.number` matches the forged `number`. No GitHub session or API token is required; the attacker POSTs directly to `/webhooks` with a self-computed HMAC-SHA1 signature. This is low-cost and fully repeatable against any org/stack in a multi-org Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature`, or in each handler's repository resolution, enforce that the org segment of `params.repository.full_name` (and any `params.organization.login`) matches the `repository_owner` value that selected the webhook secret used for verification; reject the request (422) on mismatch before dispatching to handlers.

### Proof of Concept
minitest plan (webhooks controller / integration level, no live GitHub):
1. Configure two orgs, `orga` and `orgb`, each with distinct `webhook_secret`s (using the `secrets_double_github_app.yml`-style multi-org config already present in `test/dummy/config`).
2. Create a victim `Shipit::Repository` owned by `orgb` with an active `ReviewStack`/`Shipit::PullRequest` (e.g. `number: 42`, `labels: ["victim-label"]`).
3. Build a raw JSON `pull_request` `labeled` payload body with `repository.owner.login = "orga"`, `repository.full_name = "orgb/victim-repo"`, `number: 42`, `pull_request.labels = [{name: "attacker-label"}]`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', orga_webhook_secret, raw_body)`.
5. `post :create, body: raw_body, as: :json` with `X-Github-Event: pull_request` and `X-Hub-Signature: signature`.
6. Assert response is `:ok` (not `:unprocessable_entity`).
7. Reload the victim `PullRequest` and assert `labels == ["attacker-label"]` (changed from `["victim-label"]`), proving ORG_A's signature was accepted to mutate ORG_B's record — i.e. assert `repository_owner_used_for_verification == "orga"` while `resolved_repository.owner == "orgb"`, demonstrating the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
