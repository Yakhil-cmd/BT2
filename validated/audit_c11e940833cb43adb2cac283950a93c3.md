### Title
Webhook signature verification authenticates the GitHub organization but the event handlers act on a repository named by an unverified field in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by deriving an *organization* from the payload (`repository.owner.login` or `organization.login`) and checking the HMAC signature against that organization's configured `webhook_secret`. However, every event handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, `PullRequest::*`) determines *which repository/stack/team to mutate* using a different, independently attacker-controlled field of the very same JSON body: `repository.full_name` (via `Handler#repository_name`/`Handler#stacks`), or nested `team`/`organization`/`member` objects for `MembershipHandler`. Nothing ties the organization that was cryptographically authenticated to the repository or team that is actually written to.

### Finding Description
The controller's signature check is: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

and is used only to select which per-organization `GitHubApp` (and thus which `webhook_secret`) to verify the HMAC against: [3](#0-2) 

Critically, if the selected organization has no `webhook_secret` configured (a state explicitly presented as a normal/example configuration, e.g. `webhook_secret: # nil` in `config/secrets.development.shopify.yml`), `verify_webhook_signature` returns `true` unconditionally — no signature is checked at all:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [4](#0-3) 

Separately, once `verify_signature` passes, `create` dispatches the parsed body to handlers with no further binding to `repository_owner`: [5](#0-4) 

Every handler determines its mutation target from `repository.full_name` in the same body, not from `repository_owner`: [6](#0-5) 

`PushHandler` uses that repository scoping to trigger a real sync/deploy pipeline job: [7](#0-6) 

`MembershipHandler` creates/looks up `Team` records and adds/removes arbitrary GitHub logins as members purely from body fields, with no cross-check against `repository_owner`: [8](#0-7) 

and `Team` membership feeds directly into the authorization gate used by `Authentication#force_github_authentication` / `User#authorized?`: [9](#0-8) [10](#0-9) 

**The broken equality:** the code implicitly assumes
`organization_that_authenticated(repository_owner) == owner_of(repository.full_name used by handlers)`.
Because both sides of this equality are read from attacker-supplied JSON fields that are never cross-validated, and because the endpoint is public (CSRF-exempt, no session/API token required — only an `X-Hub-Signature` header), an unauthenticated network attacker can decouple them:
1. Pick/point `repository.owner.login` (or `organization.login`) at any organization entry in `Shipit.github` config whose `webhook_secret` is unset/blank — verification then passes for *any* body regardless of the `X-Hub-Signature` header.
2. Set `repository.full_name`, `team`, or `member`/`organization` fields inside the same body to reference a completely different, unrelated organization/repository/team that is actually configured with stacks in Shipit.
3. The handler for the event acts on step 2's target while the security check only ever validated step 1's organization.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" and "unauthorized deploy" bars explicitly listed as valid impacts:
- Via `membership` events, an attacker can add an arbitrary GitHub login to any `Team` tracked by Shipit (including teams listed in `Shipit.github_teams`), directly granting themselves (or an accomplice account) authenticated access to the whole Shipit instance, bypassing the intended GitHub-org-membership gate.
- Via `push`/`status`/`check_suite` events, an attacker can trigger `GithubSyncJob`/CI-status/merge-queue side effects for stacks that belong to an organization whose webhook traffic was never actually authenticated by that organization's secret, effectively achieving an unauthorized deploy-pipeline action.

### Likelihood Explanation
Exploitability is gated on the deployment having at least one configured GitHub organization/app with no `webhook_secret`, which the repository's own example/config templates (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`) show as a normal, supported configuration state, not an edge case. Any Shipit instance onboarding multiple GitHub orgs where even one org's secret is left blank (a common oversight, since Shipit still fully functions without it) becomes fully exploitable by an anonymous network attacker with no session, token, or repository access.

### Recommendation
- Never treat a missing `webhook_secret` as "verification passes"; instead reject (`head 422`) any webhook for an organization without a configured secret, or require a secret to be present for every configured organization at boot.
- After successfully authenticating the payload against `repository_owner`, cross-validate that every repository/team/organization identifier referenced deeper in the payload (`repository.full_name`, `team.*`, `organization.login`, `member.login` context) actually belongs to the authenticated organization before invoking any handler, e.g. by comparing the owner segment of `repository.full_name` to `repository_owner`.
- Prefer scoping `Handler#stacks`/team lookups by the already-authenticated organization rather than re-deriving trust from unauthenticated payload fields.

### Proof of Concept
1. Configure Shipit with two GitHub organizations: `OrgA` (no `webhook_secret` set) and `OrgB` (has a real stack, `webhook_secret` set, is a legitimate target).
2. POST to `/github/webhooks` (or the mounted webhook path) with header `X-Github-Event: membership` and any/garbage `X-Hub-Signature` value, with a JSON body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner = "OrgA"`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — no valid signature needed.
4. `MembershipHandler#process` runs unaffected by the `repository` field, creating/using the `team` (arbitrary `github_id`) and adding `attacker-controlled-login` as a member — with no verification tying `team`/`member` back to `OrgA`.
5. If that team's handle is one of `Shipit.github_teams`, the attacker-controlled login now satisfies `User#authorized?`, granting it access after logging in through the normal OAuth flow — an authentication/authorization bypass achieved with zero credentials, tokens, or repository access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
