**Analysis:**

The premise doesn't hold in production code. Both the `vm-validator` and full VM execution derive their `VerifierConfig` from the same single function, `aptos_prod_verifier_config`, which is deterministically built from on-chain `gas_feature_version`, `features`, and `timed_features` [1](#0-0) . The `PooledVMValidator::validate_transaction` constructs `AptosVM::new(&vm_validator_locked.state.environment)` from that same shared environment and invokes the identical `AptosVM::validate_transaction` / `VMValidator` trait implementation used elsewhere, rather than a separately-parameterized "lightweight" verifier [2](#0-1) . There is no code path in mempool or `vm-validator` that constructs an independent `VerifierConfig` with a different `max_push_size` from the one used at block execution time — `mempool`'s `validate_and_add_transactions` simply calls into this same shared validator [3](#0-2) .

The `MockVMValidator` referenced in the exploit idea (which unconditionally returns `VMValidatorResult::new(None, 0)` without any bytecode verification at all) is a test-only mock used in unit tests, not a production component [4](#0-3) . It cannot be substituted into the real admission path by an unprivileged sender, so it cannot be used to create a real divergence between admission and execution.

Additionally, the arithmetic itself in `StackUsageVerifier::verify_block` is not vulnerable to silent wraparound: it uses `u64::checked_add`, and on overflow it explicitly returns `Err(... VALUE_STACK_PUSH_OVERFLOW ...)` rather than wrapping [5](#0-4) . The comparison `overall_push > max_push_size as u64` also correctly enforces the exact configured boundary (rejecting only when strictly greater, i.e., accepting at exactly `max_push_size`), which is consistent behavior, not a wraparound exploit.

Since production `vm-validator` and VM execution converge on the same `VerifierConfig`/`max_push_size` sourced from identical on-chain state, and the checked-arithmetic path has no overflow/wraparound bug, there is no admission-vs-execution disagreement reachable by an unprivileged sender here.
