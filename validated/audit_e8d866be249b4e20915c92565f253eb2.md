### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled`, allowing an `opened` webhook to create/provision a stack while review stacks are disabled; subsequent no-op `unlabeled` webhook does not remediate it - (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` only ANDs `repository.review_stacks_enabled` with the `allow_all?` branch due to Ruby's `&&`/`||` precedence, so the `allow_with_label?`/`prevent_with_label?` branches are reachable even when `review_stacks_enabled` is `false`. An attacker on a repo with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false` can open a PR (with/without the label) to create a `ReviewStack`, enqueue it via `Shipit::ReviewStackProvisioningQueue.add`, and have it provisioned by `ReviewStackProvisioningQueue#work` / `Task#run` -> `TaskCommands#perform` -> `Command`/`PTY.spawn`, entirely without any `review_stacks_enabled` gate ever passing.

### Finding Description
The claimed binding is: `stack execution authorized == (review_stacks_enabled == true) for the full lifecycle`. Tracing `provision?`: [1](#0-0) 

Due to operator precedence, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is scoped only to the first disjunct. If `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `provision?` can return `true` regardless of `review_stacks_enabled`'s value. `respond_to_pull_request_opened?` gates on this broken `provision?`: [2](#0-1) 

When true, `process` calls `ReviewStackAdapter#find_or_create!`, which creates the `ReviewStack` and immediately enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`) only covers the `allow_all` + `review_stacks_enabled: false` combination ("only provision stacks for repos with auto-provisioning enabled" test), never `allow_with_label`/`prevent_with_label` combined with `review_stacks_enabled: false`, so this gap is untested. The enqueued stack is later picked up by `ReviewStackProvisioningQueue#work`, which calls `stack.provision` if `stack.provisioner.provision?` is true: [4](#0-3) 

Provisioning drives the stack's state machine into `provisioning`, invoking `stack.provisioner.up`, and separately queued/created `Task`s run through `TaskCommands#perform`, which builds `Command` objects that ultimately execute via `PTY.spawn`: [5](#0-4) [6](#0-5) 

The subsequent `unlabeled` webhook does not remediate anything: `UnlabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled`, so if it's `false`, the handler is a pure no-op — it neither archives nor further authorizes the stack: [7](#0-6) 

Thus the stack created and queued for provisioning by the `opened` bypass persists and its queued task execution proceeds, independent of any `LabeledHandler`/`UnlabeledHandler` gate.

**Why existing guards don't help:** `verify_signature`/webhook signature verification is orthogonal (attacker sends a validly-signed webhook from their own repo, which they legitimately own and control — no signature bypass needed since the attacker is the legitimate sender of their own repo's events). `force_github_authentication`, `User#authorized?`, and `require_permission!` are session/API-token gates not involved in webhook processing. The `ExplicitParameters` schema only validates payload shape, not authorization intent. Model validations on `Repository`/`Stack` don't validate `review_stacks_enabled` consistency across the provisioning behaviors. None of these guards inspect the precedence bug in `provision?`.

### Impact Explanation
An attacker who owns/controls a GitHub repository connected to Shipit, where an operator has configured `provisioning_behavior: allow_with_label` (or `prevent_with_label`) but has NOT enabled `review_stacks_enabled`, can still cause Shipit to create a `ReviewStack`, enqueue it for provisioning, and execute deploy-spec-defined commands via `Command`/`PTY.spawn` on the Shipit host — despite the operator's explicit intent (`review_stacks_enabled: false`) to disable this feature entirely. This is repeatable per PR/branch on the same repository (`RCE via execution of a provisioning task queued entirely through the initial bypass`), matching the Critical impact category (`RCE on the deploy host via Command/PTY.spawn`). The blast radius is limited to repositories under this specific misconfiguration (behavior set to a label-based mode while `review_stacks_enabled` is false); it does not cross-tenant into repositories the attacker doesn't control.

### Likelihood Explanation
Preconditions: a Shipit-tracked repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false`. This is a plausible operator misconfiguration — e.g., an operator disables review stacks by flipping `review_stacks_enabled` off but leaves a previously-configured `provisioning_behavior` value in place, unaware that only the `allow_all` code path actually respects the flag. Attacker cost is low (open a PR, optionally add/remove a label) and the action is repeatable across PRs on the same repo. It does not require any Shipit or GitHub secrets.

### Recommendation
Fix the operator precedence in `OpenedHandler#provision?` (and audit `ReopenedHandler#unarchive?`, which has the identical bug) to explicitly scope `repository.review_stacks_enabled` across all three disjuncts, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same parenthesization fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does NOT create/provision stacks when review_stacks_enabled is false, even with allow_with_label behavior" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Expected (broken) behavior today: `Shipit::Stack.count` increases by 1 and `Shipit::ReviewStackProvisioningQueue.add` is called, proving `provision? == true` even though `repository.review_stacks_enabled == false` — violating the binding `respond_to_pull_request_opened? == (review_stacks_enabled == true) AND (behavior-specific rule)`. A second assertion can additionally run `Shipit::ReviewStackProvisioningQueue.work` and confirm a `Task`/`Command` executes, then confirm `UnlabeledHandler.new(payload_with_action_unlabeled).process` is a no-op (`respond_to_label_change? == false`) that does not archive or otherwise revoke the already-queued stack.
