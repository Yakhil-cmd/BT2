### Title
Webhook signature check resolves the signing secret from an unverified `repository.owner.login`/`organization.login` field, letting a request forged for one configured GitHub org drive actions against a different org's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate `X-Hub-Signature` based on `repository_owner`, a value read straight out of the *unverified* request body. `Handler#stacks`, however, resolves which `Stack`/`Repository` the event actually acts on from a different field in the same unverified body, `repository.full_name`. Nothing binds these two fields together, so the "organization whose secret authenticated the request" and "the repository that gets written to" are not the same equality that the signature is supposed to protect.

### Finding Description
`verify_signature` computes the verifying organization purely from request content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up that org's `GitHubApp`, whose `webhook_secret` may be `nil`/blank — this is explicitly documented as optional per organization: [3](#0-2) [4](#0-3) 

Multi-org installs configure a distinct `webhook_secret` (or none) per organization key under `secrets.github`: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (trivially, if the org resolved from `repository.owner.login` has no secret), the request body is dispatched to handlers, e.g. `PushHandler`, which resolves the *actual* target stack from an entirely different, independently-attacker-controlled field — `repository.full_name`: [7](#0-6) [8](#0-7) [9](#0-8) 

The binding that should hold is:
`organization used to select/validate the signing secret == organization portion of repository.full_name that the handler acts on`

Because both values are read from the same unverified JSON body before any cryptographic check occurs, and the check itself is a no-op whenever the resolved org has no `webhook_secret` configured, an attacker can set `repository.owner.login`/`organization.login` to an org with a blank secret while setting `repository.full_name` to any other tracked `owner/repo` (belonging to a *different*, properly-secured org in the same multi-tenant install). The forged POST to `/webhooks` sails through `verify_signature` (secret is blank → `return true unless webhook_secret`) and is then processed by the real handler using the victim `full_name`, e.g. triggering `GithubSyncJob`/`stack.sync_github` for a stack the attacker has no legitimate relationship to.

### Impact Explanation
This is an authentication-bypass / cross-repository-write class issue: a request that never satisfies HMAC verification against the secret that actually protects the target repository's org is nonetheless accepted and used to mutate state (sync commits, potentially feeding into auto-deploy pipelines) scoped to that target repository. This matches the "Critical: cross-repository writes / unauthorized deploy" bucket in a multi-organization Shipit deployment, since the org-secret binding the webhook signature is meant to enforce is not the same org that the mutated repository belongs to.

### Likelihood Explanation
Requires the host to run Shipit in the documented multi-organization mode (`secrets.github` keyed by org) with at least one configured organization lacking a `webhook_secret` — an explicitly supported, "optional" configuration per `docs/setup.md`. No attacker credentials, tokens, or knowledge of any actual secret are needed; only knowledge that such an org exists (discoverable from any real webhook payload from that org, or by trial). Single-org deployments without any secret configured are also fully exposed, since `repository_owner` is attacker-supplied and `verify_webhook_signature` unconditionally returns `true`.

### Recommendation
Do not select the verification secret from unverified request data whose organization can diverge from the data acted upon later in the pipeline. Either (a) require a `webhook_secret` for every configured organization and refuse verification (fail closed) when one is missing rather than treating it as "verified", or (b) verify the signature using the secret bound to the organization actually referenced by `repository.full_name` (the same field handlers use), and reject if the two disagree.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `OrgOne` (no `webhook_secret`) and `OrgTwo` (secured with `webhook_secret: S`), each tracking their own repositories/stacks (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgOne"`, calls `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no signature required at all.
4. Request proceeds to `PushHandler`, which resolves `repository_name` from `full_name` = `"OrgTwo/victim-repo"`, finds the real `Stack`, and enqueues `GithubSyncJob` for it — despite the request never being authenticated against `OrgTwo`'s secret `S`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
