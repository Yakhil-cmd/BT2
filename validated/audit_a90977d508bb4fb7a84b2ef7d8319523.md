### Title
Reachable assertion / uncaught exception in `decryptPackage` on malformed device message crashes the wallet/hub process - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` reaches an unconditional `throw Error(...)` scheduled via `setTimeout` when a device message's `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the recipient's known keys (temp, previous temp, or permanent). This is directly analogous to the OpenVPN CVE-2026-13122 pattern: untrusted, attacker-controlled input (an "authentication"/keying token, here the DH ephemeral pubkey field of a device message) reaches a hard assertion (`throw Error`) instead of being handled as a normal validation failure, causing denial of service.

### Finding Description
`decryptPackage` is invoked with a fully attacker-controlled `objEncryptedPackage` whenever a device message is received, e.g. from `handleJustsaying` on the `hub/message` justsaying subject: [1](#0-0) 

The outer caller wraps the call in `try { var json = decryptPackage(...) } catch(e) { ... }`, but this only protects against *synchronous* exceptions: [2](#0-1) 

Inside `decryptPackage`, if the `recipient_ephemeral_pubkey` supplied in the message doesn't match `objMyTempDeviceKey.pub_b64`, `objMyPrevTempDeviceKey.pub_b64`, or `objMyPermanentDeviceKey.pub_b64`, the function does **not** return an error synchronously. Instead it schedules an unconditional `throw Error(...)` 100ms later via `setTimeout`, then returns `null` immediately: [3](#0-2) 

Because the `throw` executes inside a `setTimeout` callback — outside of any enclosing `try/catch` (the original catch block in `handleJustsaying` has already returned by the time the timer fires) — this becomes an **uncaught exception** at the process level. No global `uncaughtException` handler was found that gracefully recovers this specific case; `network.js` only references `uncaughtException` in what appears to be unrelated/other paths, not this one. By default, Node.js terminates the process on an uncaught exception, causing the wallet/hub to crash.

This function is reachable by any unprivileged correspondent who can send a device message: the attacker only needs to supply an `encrypted_package.dh.recipient_ephemeral_pubkey` value that does not match the victim's currently known keys, which is easily satisfiable (e.g. a stale/garbage value, or one crafted from a wrong keypair). All required prior validations (`missing fields`, `signature`, `hash`) can be trivially satisfied by any device that knows the recipient's device address and can produce a validly-signed device message — this does not require correspondence/pairing, and per the code, `pairing` is one of the subjects allowed even from unknown correspondents.

### Impact Explanation
A single malformed/mis-keyed device message crashes the receiving node process (wallet, hub, or paired device). This is a "network unable to confirm new units" / process-crash class DoS reachable from a device message, which fits the required medium/high impact bar (crash of the local ocore process handling AA triggers, unit relaying, and payment flows). Repeated messages can be used to keep a targeted node down.

### Likelihood Explanation
Likelihood is high for triggering the crash once reached: the "unknown key" branch only requires an ephemeral pubkey not currently recognized by the recipient — trivial to produce and does not require breaking any cryptography. The main precondition is being able to deliver a device message to the target (paired correspondent, or for a subset of whitelisted subjects like `pairing`, even a non-correspondent), which matches the "unprivileged... paired device" trigger surface allowed by the analog scope.

### Recommendation
Replace the delayed, unconditional `throw Error(...)` inside `setTimeout` in `decryptPackage` (device.js, around lines 429-435) with non-throwing error handling: log the event (e.g. via `eventBus.emit('nonfatal_error', ...)`, which is already present but commented out) and return `null` synchronously, exactly like the other failure branches in the same function (e.g. decrypt/parse failures). Ensure no code path in device-message handling can result in an exception thrown outside of a synchronous `try/catch` scope reachable from network input.

### Proof of Concept
1. Attacker knows/derives the victim device's permanent device address and public key (routinely shared for pairing/correspondence).
2. Attacker crafts a device message `objDeviceMessage` with:
   - valid `signature`/`pubkey` (attacker signs with their own key, `pubkey` set to attacker's own device pubkey, message content otherwise passes the `hub/message` field checks),
   - `encrypted_package.dh.recipient_ephemeral_pubkey` set to an arbitrary/garbage/stale base64 pubkey value that does not match the victim's `objMyTempDeviceKey`, `objMyPrevTempDeviceKey`, or `objMyPermanentDeviceKey`,
   - other required `encrypted_package` fields (`iv`, `authtag`, `encrypted_message`, `dh.sender_ephemeral_pubkey`) filled with any well-formed but otherwise arbitrary values (they do not need to decrypt correctly since the "unknown key" branch is hit before decryption is attempted).
3. Attacker sends this message to the victim via the hub (`hub/message` justsaying) or directly if peer-to-peer capable.
4. Victim's `handleJustsaying` passes the message signature/hash checks, then calls `decryptPackage`, which detects the ephemeral key is unrecognized and schedules `throw Error("message encrypted to unknown key...")` via `setTimeout(…, 100)`, returning `null` immediately so the surrounding `try/catch` sees no error.
5. 100ms later, the scheduled exception fires uncaught at the top level of the Node.js event loop, crashing the victim's ocore process (denial of service).

Note: I was unable to fully verify from the indexed portions of `network.js` whether any global `process.on('uncaughtException', ...)` handler exists that might mitigate (rather than merely log) this specific crash; only two references to `uncaughtException` were found in `network.js` and their exact effect on process survival could not be confirmed with the available index. If Devin has full file access, this should be checked explicitly by reading the complete `network.js` `uncaughtException` handler logic before finalizing severity.
