This confirms the vulnerability. `PushHandler#process` correctly scopes to `stacks` (derived from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Handler#repository_name`), but `StatusHandler#process` does not — it queries `Commit.where(sha: params.sha)` globally across the entire database, with no scoping to the repository named in the payload that was actually signature-verified.### Title
`StatusHandler#process` scopes status writes globally by commit sha, not by the webhook's own repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which is unscoped by repository, unlike every other handler in the engine (e.g. `PushHandler`) which restricts work to `stacks` derived from `payload.dig('repository', 'full_name')`. Because `Status.replicate_from_github!`'s `find_or_create_by!` key (`stack_id, state, description, target_url, context, created_at`) also excludes `sha`/`commit_id`, a single signature-verified `status` webhook for one repository can create `Status` rows against commits belonging to any stack in the installation whose commit table happens to contain a matching sha.

### Finding Description
The claimed binding is: `number of repositories a signature-verified "status" webhook is authorized to mutate == 1 (the repository named in payload['repository']['full_name'])`. Tracing the code shows this does not hold.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates `X-Hub-Signature` against the `webhook_secret` configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` comes from `params.dig('repository', 'owner', 'login')`. This proves the request was signed by whoever holds that organization's configured webhook secret, i.e., the org named in the payload - it says nothing about which commits/stacks may be touched.
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) is the engine's mechanism to properly scope work to `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) correctly uses `stacks.not_archived.where(branch:)`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a global query across the `commits` table with no `stack_id`/`repository` filter at all.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` → `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) does `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)`. The `stack_id` here is whatever stack the matched `Commit` belongs to, not the stack tied to the webhook's own repository.
- The `commits` table has a unique index on `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming shas are only unique per-stack, not globally - multiple stacks legitimately can (and, for forked/templated repos sharing history, will) have `Commit` rows with identical `sha`.

Attacker flow: attacker controls (or is any GitHub user emitting webhooks for) a repository/org for which they can produce a validly signed `status` event (e.g., their own repo/org with its own configured `webhook_secret`, or any org whose secret they legitimately hold). They pick a `sha` known to also exist as a `Commit` row in unrelated victim stacks (e.g., a common ancestor commit shared by forks of a popular template that multiple Shipit-tracked repositories forked from). One `POST /webhooks` with `X-Github-Event: status` and that sha causes `Commit.where(sha: params.sha)` to match every stack's commit with that sha, and a `Status` row is written into each victim stack's commit history.

Existing guards do not prevent this: `verify_signature` only authenticates the org named in the payload, not which stacks may be mutated; `ExplicitParameters` (`params do requires :sha ... end`) only validates shape, not authorization scope; there is no `stacks`/`Repository.from_github_repo_name` scoping in `StatusHandler` as there is in `PushHandler` and the `pull_request` handlers.

### Impact Explanation
A single forged/authenticated-as-attacker `status` webhook (signed only for the attacker's own org) can write `Status` records into unrelated stacks/repositories that never authenticated this event. `Status` creation on a commit triggers real side effects: `after_create :enable_ci_on_stack` (enables CI on the victim stack), `schedule_continuous_delivery` (can enqueue `ProcessMergeRequestsJob` / continuous delivery for the victim stack if the injected state is `success`/`pending`), and hook emission (`commit_status`/`deployable_status`) which can influence merge-request auto-merging and downstream automation for a stack the attacker does not control. This is a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Exploitability requires (a) the attacker to be able to produce a validly signed `status` webhook for at least one org configured in `Shipit.github_teams`/`Shipit.github(organization:)` (their own repo/org is sufficient - they don't need any victim secret, since the check only validates against the org named in their own payload), and (b) a `sha` value that collides with a `Commit` row in a different stack. Because commit shas are content-addressed and shared naturally across forks (e.g., a shared upstream/template commit before divergence, or commits cherry-picked/rebased identically across forks), this precondition is realistic for organizations that manage many forked repos from common templates in one Shipit instance, and is fully within attacker control if they can enumerate shas already tracked by Shipit (e.g., via the public UI/API for stacks they can view, or public GitHub history) and open a PR/push to their own repo containing an identical commit. No secrets, sessions, or privileged roles are needed beyond the ability to configure/trigger a webhook for a repo the attacker owns.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `PushHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)`, restrict the commit lookup to `stacks.commits.where(sha: params.sha)` (or equivalently join commits through the stacks scoped from `payload.dig('repository', 'full_name')`) instead of the unscoped `Commit.where(sha: ...)`. Additionally, consider including `commit_id`/`sha` in the `find_or_create_by!` key of `Status.replicate_from_github!` to remove ambiguity, though the primary fix is repository/stack scoping in the handler.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
```ruby
test "status webhook for one repository must not create statuses on commits belonging to another stack with a colliding sha" do
  shared_sha = "deadbeef00112233445566778899aabbccddeeff"

  victim_stack = shipit_stacks(:shipit)          # repo: shopify/shipit-engine (fixture)
  attacker_stack = shipit_stacks(:cyclimse)       # different repo/org

  victim_commit = victim_stack.commits.create!(
    sha: shared_sha, message: "shared ancestor", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now
  )
  attacker_commit = attacker_stack.commits.create!(
    sha: shared_sha, message: "shared ancestor", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now
  )

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # attacker's own org signature verifies fine

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success', description: 'forged', context: 'ci/forged',
    created_at: Time.now.iso8601,
    repository: { full_name: attacker_stack.repository.full_name, owner: { login: attacker_stack.repository.owner } }
  }.to_json

  # Binding under test: number of repos authorized to mutate (1: attacker_stack) == number actually mutated
  assert_difference -> { attacker_commit.reload.statuses.count }, 1 do
    assert_no_difference -> { victim_commit.reload.statuses.count } do
      post :create, body:, as: :json
    end
  end
end
```
