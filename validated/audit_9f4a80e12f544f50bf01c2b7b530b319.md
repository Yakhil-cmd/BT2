### Title
Sandwich/Front-Running Attack on AA-based Exchanges via Predictable Level-Based AA Trigger Ordering - (File: main_chain.js)

### Summary
AA (Autonomous Agent) trigger execution order within a stabilized MCI is fully deterministic and is based purely on `units.level, units.unit, address`, not on causal broadcast/arrival order [2](#0-1) . Because any unit author freely chooses their own `parent_units` when composing a unit, and `level` is simply `max(parent levels) + 1` [3](#0-2) , an attacker who observes a victim's pending (not-yet-stable) trade against an AMM-style or order-book-style AA can craft two of their own units — one built to obtain a lower level than the victim's unit (front-run) and one built on top of the victim's unit to obtain a higher level (back-run) — both landing in the same main-chain index. This is the exact ocore analog of the Uniswap V3 sandwich attack described in the report: the constant-product AMM reference implementation shipped with ocore computes swap output purely from `balance[$asset]`/`balance[base]` at execution time with no minimum-output/maximum-price protection [4](#0-3) , so whichever unit executes immediately before/after the victim's swap can extract the price impact exactly as an MEV bot does on Uniswap.

### Finding Description
Autonomous Agents (AAs) on Obyte, e.g. the shipped `uniswap_like_market_maker.oscript` and `order_book_exchange.oscript` reference AAs, hold pooled/aggregated balances and compute trade outputs from state read at the moment the trigger executes [4](#0-3) . Execution of AA triggers for units sharing the same main_chain_index (MCI) is not first-come-first-served; instead `handleAATriggers` in `main_chain.js` explicitly enumerates all trigger units for the newly-stabilized MCI and inserts them into the `aa_triggers` queue "ORDER BY units.level, units.unit, address // deterministic order" [2](#0-1) . The `aa_composer.js` consumer later drains that queue in the same order via `ORDER BY aa_triggers.mci, level, aa_triggers.unit, address` [5](#0-4) .

`level` is not a network-wide global clock — it is computed locally for every new unit as `max_level + 1` over the poster's freely-chosen `parent_units` [3](#0-2) . Because units remain visible (propagated, but unstable/not yet finalized) for some time before their MCI stabilizes, an attacker monitoring the DAG can see a victim's swap-trigger unit before it becomes stable and can then:
- Compose a "front-run" unit using older/lower-level parents (avoiding the victim's unit as an ancestor) so its `level` is lower than the victim's, guaranteeing it is ordered and executed first when the MCI stabilizes.
- Compose a "back-run" unit that includes the victim's unit (or a descendant of it) as a parent, guaranteeing a strictly higher `level`, so it executes immediately after.

Both attacker units and the victim's unit can land in the same MCI once that batch of the DAG stabilizes, giving the attacker complete sandwich control over the AMM state the victim trades against — identical in effect to a mempool-based sandwich attack, except here the “mempool” is the window between broadcasting a unit and its MCI becoming stable.

### Impact Explanation
Any AA implementing a price-sensitive exchange mechanism (constant-product AMM, order book with taker match, etc.) without slippage/minimum-output protection is exposed to guaranteed value extraction by a sandwiching attacker, exactly mirroring the reported Ethereum Foundation Uniswap V3 sandwich loss. This causes concrete fund loss for genuine traders interacting with such AAs (the attacker's front-run trade worsens the price the victim receives, and the back-run trade captures the reversion), which is a direct AA fund loss/economic harm to unprivileged users triggering the AA — squarely within the accepted impact categories.

### Likelihood Explanation
Likelihood is Medium: it requires (1) an AMM/exchange-style AA lacking output/price bounds (a common and realistic pattern, as evidenced by the reference `uniswap_like_market_maker.oscript` shipped with ocore, which has no min-output check), and (2) an attacker that watches the network for pending trigger units and reacts before MCI stabilization by composing appropriately-parented units — both of which are readily achievable by any ordinary, unprivileged network participant/full node with no special privileges, matching the reachable-actor set (unprivileged AA trigger sender).

### Recommendation
- Document clearly for AA authors that AA trigger execution order within an MCI is level-based and attacker-influenceable, and that any AA computing amounts from mutable pooled state (AMM pricing, matching, auctions) must enforce trader-supplied slippage/minimum-output or maximum-price bounds (as already done correctly in `order_book_exchange.oscript`'s order-matching logic, but absent from `uniswap_like_market_maker.oscript`'s swap cases).
- Consider providing a standard oscript primitive/helper for slippage protection and update the reference `uniswap_like_market_maker.oscript` sample to require `trigger.data.min_amount` (or similar) so developers copying the sample do not inherit the vulnerable pattern.
- Evaluate whether the AA-trigger ordering rule can be made less exploitable by attacker-chosen parent selection, e.g. weighting by unit content_hash/witnessed_level combined with commit-reveal-style ordering, though this is a broader protocol-design change.

### Proof of Concept
1. Deploy an AA equivalent to `test/samples/uniswap_like_market_maker.oscript`, seeded with base/asset liquidity.
2. Victim broadcasts a unit sending `1e6` bytes to the AA to receive `$asset` (triggers "exchange bytes to asset" case) [4](#0-3) .
3. Before the victim's unit's MCI stabilizes, attacker composes unit A (front-run: sell `$asset` for bytes) using parent units chosen so its `level` < victim's unit `level` (e.g., building on an older tip not including the victim's unit).
4. Attacker composes unit B (back-run: buy back `$asset`) using the victim's unit (or a unit that includes it) as a parent, guaranteeing `level` > victim's `level`.
5. When the MCI containing all three units stabilizes, `handleAATriggers`'s `ORDER BY units.level, units.unit, address` [2](#0-1)  guarantees execution order: attacker's front-run → victim's swap (worst price) → attacker's back-run (captures the reverted price), extracting value from the victim exactly as in the reported MEV sandwich incident.
