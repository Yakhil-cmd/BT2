This confirms the finding. `Shipit.github(organization:)` maps an org name to a `GitHubApp` config, and `github_app_config` looks it up from `secrets.github` case-insensitively. The critical piece is `GitHubApp#verify_webhook_signature`:### Title
Unauthenticated forged GitHub webhooks when `webhook_secret` is unset — signature check always passes and lets attacker inject Statuses/Teams/Users - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` mirrors the exact bug class in the report: a security check that unconditionally returns `true` whenever its guarding value is unset. If `webhook_secret` is blank for an organization's GitHub App config, `WebhooksController#verify_signature` passes for *any* request body/signature, letting an unauthenticated attacker post arbitrary forged webhook payloads that are processed by Shipit's built-in handlers.

### Finding Description
`WebhooksController#verify_signature` resolves the app config for the org named in the (attacker-supplied) payload and delegates the actual signature check to it: [1](#0-0) 

The delegated check is: [2](#0-1) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

This is structurally identical to the reported `TokenStaking.recoverStake` flaw: a guard (`undelegationPeriod`/`webhook_secret`) that, when never configured (zero/blank), causes the "is this authorized?" check to unconditionally succeed instead of unconditionally failing. `webhook_secret` is explicitly documented as **optional** during GitHub App setup, and the test/dummy fixtures ship with it set to `null`: [3](#0-2) [4](#0-3) 

Once signature verification is bypassed, `WebhooksController#create` dispatches the fully attacker-controlled JSON body straight to the registered handlers with no further authentication: [5](#0-4) 

Concrete handlers that mutate application state based solely on this payload include:
- `StatusHandler`, which creates a `Status` on any commit matching an attacker-chosen `sha`, with attacker-chosen `state`/`context`/`description` — this can forge a "success" CI status for a malicious commit, defeating `deployable?`/CI-gating checks used to authorize deploys: [6](#0-5) 
- `MembershipHandler`, which creates/updates `Team` and `User` records and adds/removes team membership purely from payload data: [7](#0-6) 
- `PushHandler`, which triggers `stack.sync_github` for any branch/stack matching the (attacker-controlled) `repository.full_name`: [8](#0-7) 

The equality this breaks: **"a payload whose authenticity is verified" should equal "a payload the engine acts on."** When `webhook_secret` is unset, the verification step becomes a no-op, so *every* inbound payload for that org is treated as authenticated, even though nothing about it was actually checked.

### Impact Explanation
This maps to the High/Critical bucket: "unauthenticated read of stack state ... or an unauthorized deploy". Concretely:
- Forging a CI `status` webhook can make a commit appear to pass required checks, which several deploy/merge gating paths rely on (`Commit#create_status_from_github!`, `deployable?`), potentially enabling an **unauthorized deploy** of a commit that never actually passed CI.
- Forging `membership`/`push`/`check_suite` events lets an unauthenticated attacker inject `Team`/`User` records and trigger sync/refresh jobs against real stacks, all without any credential.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: the vulnerability manifests only when an admin leaves `github.<org>.webhook_secret` unset for an organization, which the setup documentation explicitly presents as an optional field, making this a plausible real-world misconfiguration rather than a hypothetical one. No attacker credential, session, or token is required — only knowledge of the target's public `/webhooks` endpoint and the org login used in the payload's `repository.owner.login`/`organization.login`.

### Recommendation
Change `verify_webhook_signature` to fail closed when `webhook_secret` is blank (reject the request / require signature) instead of returning `true`, analogous to the recommended fix in the original report (require the guarding value to be present/non-zero before allowing the privileged action). At minimum, log a startup warning and refuse to mount the webhooks route (or return 4xx for all events) for any organization configured without a `webhook_secret`.

### Proof of Concept
1. Configure (or discover) a Shipit deployment where one organization entry under `secrets.github` has no `webhook_secret` set (as in the shipped test fixture/dummy config, and as explicitly permitted by `docs/setup.md`).
2. Send, with no `X-Hub-Signature` needed to be valid:
```
POST /webhooks
X-Github-Event: status

{
  "sha": "<victim-commit-sha>",
  "state": "success",

```
3. `verify_signature` resolves `Shipit.github(organization: "<org-without-secret>")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `StatusHandler#process` executes and creates a forged "success" `Status` for `victim-commit-sha`, with no attacker credentials ever supplied. [2](#0-1) [1](#0-0) [6](#0-5)

  module Webhooks

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
