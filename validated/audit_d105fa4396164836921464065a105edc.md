## Title
Independent per-recipient rounding of headers-commission shares can mint bytes beyond the payer unit's actual headers_commission - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a winning child unit's earned headers commission among its declared `earned_headers_commission_recipients` by rounding each recipient's share independently with `Math.round(full_amount * share / 100.0)` (JS in-memory path) or `ROUND(punits.headers_commission * earned_headers_commission_share / 100.0)` (SQL path). Because each recipient's amount is rounded up or down independently, with no reconciliation step to force the sum to equal `full_amount`, an attacker who controls a multi-authored child unit can choose the recipient share percentages to make every individual rounding operation round *up*, producing a total payout that exceeds the actual `headers_commission` originally paid by the parent (payer) unit. This is the same class of bug as the reported ERC-4626 issue: a conversion/division that should round in the protocol's favor is instead allowed to round in the user's favor, and because there is no per-unit reconciliation, the rounding excess is realized as new spendable currency.

### Finding Description
`validateHeadersCommissionRecipients()` in `validation.js` only checks that the percentages sum to exactly 100: [1](#0-0) 

It performs no check relating the sum of `earned_headers_commission_share` percentages applied to a specific `full_amount` to the resulting rounded amounts. The actual distribution is computed later, at stabilization time, in `calcHeadersCommissions()`:

- In-memory/"faster" path, each recipient's cut is rounded independently: [2](#0-1) 

- Same independent rounding in the SQL-driven verification path: [3](#0-2) 

- The MySQL query path applies the identical unreconciled `ROUND(...)` per recipient: [4](#0-3) 

Because `Math.round` (and SQL `ROUND`) round each recipient's fractional share independently, and there is no "last recipient gets the remainder" correction, the sum of the rounded amounts for a single winning child unit can be strictly greater than `full_amount` (the winning `headers_commission` actually paid by the payer unit `punits`). A unit author fully controls: (1) the size/commission of a unit they post (hence the numeric value of `headers_commission` that will be earned by whichever child wins it), and (2) the `earned_headers_commission_recipients` percentages of any child unit they multi-author (an author can trivially co-author with additional addresses they themselves control — no third-party cooperation is required). This gives the attacker full control over both operands of the rounding operation, allowing the rounding excess to be maximized deterministically (e.g., splitting recipients so that each per-recipient product lands just above `x.5`, which `Math.round` always rounds up).

The resulting `headers_commission_contributions`/`headers_commission_outputs` rows are inserted unconditionally with the rounded (inflated) amounts, and later become genuinely spendable via `type: "headers_commission"` payment inputs, validated in `validatePaymentInputsAndOutputs`/`mc_outputs.calcEarnings`: [5](#0-4) 

Nothing in that spending-validation path re-derives the amount from the original `headers_commission` value paid by the parent unit(s) — it simply trusts the sum stored in `headers_commission_outputs`, which was already computed with the unreconciled per-recipient rounding.

### Impact Explanation
This allows an unprivileged unit poster to mint additional base-currency ("bytes") units beyond what was actually collected as headers commission from parent units, i.e., a form of protocol-level currency supply inflation. Because the amounts become normal spendable `headers_commission` outputs indexed by main-chain-index, all full and light nodes deterministically compute the same (inflated) value from the same on-DAG data, so the excess is accepted network-wide rather than causing node disagreement — it is a systemic inflation bug rather than a fork-inducing one, but it results in real unauthorized creation of spendable value.

### Likelihood Explanation
The attack requires only posting units — no witness/hub/light-vendor cooperation and no privileged role. An attacker needs to: (1) author a unit that will become the winning child (trivial if it is the only valid child of a chosen parent), (2) make that child multi-authored (by co-signing with additional addresses under their own control) and declare recipient shares chosen to maximize rounding overflow, and (3) control/predict the exact `headers_commission` value of the parent (straightforward, since fee is a deterministic function of unit size the attacker composes). This is within reach of any user with basic knowledge of oscript-independent DAG mechanics; it does not require an AA, an oracle, or any other cooperating party.

### Recommendation
Reconcile the per-recipient rounding so that the sum of the distributed amounts for a given winning child/payer pair never exceeds `full_amount`:
- Round all but the last recipient normally, then set the last recipient's amount to `full_amount - sum_of_others`, or
- Use largest-remainder distribution (compute floor for each share, then distribute the leftover units, at most one extra unit per recipient, deterministically e.g., by address order) to guarantee the total exactly equals `full_amount`.
This mirrors the ERC-4626 fix of rounding in the protocol's favor and eliminates the ability to extract value purely from rounding choices.

### Proof of Concept
1. Attacker creates address A and address B (both attacker-controlled).
2. Attacker posts unit `P` (as sole author) sized so that its `headers_commission` fee, once won, is a value like `1` (or any odd unit) such that a 50/50 split lands exactly on `.5` boundaries.
3. Attacker posts a child unit `C` that is the only valid child candidate of `P` in the relevant MC-index window, authored jointly by A and B, with `earned_headers_commission_recipients = [{address:A, share:50}, {address:B, share:50}]` (sum = 100, passes `validateHeadersCommissionRecipients`).
4. At stabilization, `calcHeadersCommissions()` computes `Math.round(1 * 50/100) = Math.round(0.5) = 1` for A and the same for B, inserting `headers_commission_contributions` totalling `2` instead of the correct `1`.
5. `headers_commission_outputs` are aggregated per address/mci, and both A and B can later spend their `1`-byte inputs of type `headers_commission`, referencing `mc_outputs.calcEarnings`, which accepts the pre-computed (inflated) sum from step 4 without re-validating it against the true fee paid by `P`.
6. Total spendable bytes created (`2`) exceed the fee actually collected from `P` (`1`), demonstrating unauthorized creation of currency. Repeating this with more co-authored recipients and carefully chosen percentages/unit sizes increases the achievable inflation per operation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
