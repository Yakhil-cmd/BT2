### Title
Webhook signature is verified against a secret selected from an unverified organization field, while event handlers act on a different, independently-controlled repository field in the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is a structural analog of the reported bug class: the report's root cause is that `processValidators()` acts on state (`processed`) that is not what was actually verified/committed, breaking the binding between "what was verified" and "what is acted upon". In `WebhooksController`, the field used to *select and verify* the HMAC signature (`repository.owner.login`, resolved into a per-organization `webhook_secret` via `Shipit.github(organization:)`) is not the same field the downstream `Webhooks::Handlers::Handler` uses to *select the target Stack/Repository to mutate* (`repository.full_name`). In a multi-organization Shipit deployment (`Shipit.github_organizations`/`github_app_config`), any org owner who legitimately knows their **own** org's `webhook_secret` can forge a signed payload whose `repository.owner.login` names their own org (so verification succeeds) while `repository.full_name` names an arbitrary tracked repository belonging to a different organization, causing the handler to act on a stack it should never be authorized to touch.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to pick the verifying secret from the unverified request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, which selects the `GitHubApp` (and thus the `webhook_secret`) via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Shipit explicitly supports multiple organizations, each with its own independently configured `webhook_secret` (`TOP_LEVEL_GH_KEYS`, `github_app_config`, `github_organizations`): [4](#0-3) [5](#0-4) 

Once the signature check passes (i.e., proves only that *some* configured organization's secret was used to sign the body), the event is dispatched to handlers that resolve their operating target from a **different** field of the same payload — `repository.full_name` — via `Handler#stacks`/`#repository_name`: [6](#0-5) 

`PushHandler`, for example, uses `stacks` (derived from `repository.full_name`) to look up and mutate stacks, triggering `sync_github`: [7](#0-6) 

`Repository.from_github_repo_name` performs a straightforward DB lookup on `owner/name` parsed from `full_name`, with no cross-check against `repository.owner.login`: [8](#0-7) 

The binding that should hold is:
`organization whose secret authenticated the signature == owner of the repository the handler mutates`

But nothing in the controller or handler pipeline enforces `payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`. Both fields are inside the same HMAC-signed body, but the HMAC only proves "this exact byte string was signed by secret_X"; it says nothing about internal consistency between two independent fields inside that string. Anyone who owns/controls one org's webhook secret (i.e., anyone who has configured a GitHub webhook against this Shipit instance for their own organization) can compute a valid signature over an arbitrary payload that sets `repository.owner.login` to their own org (to pass verification with their known secret) while setting `repository.full_name` to any other tracked `owner/repo` combination in the same Shipit installation.

### Impact Explanation
This lets a low-privilege actor — one with legitimate control of any single organization's webhook configuration on the shared Shipit instance, but with no access to a victim org's `webhook_secret`, GitHub credentials, or Shipit session — forge `push`, `status`, or `check_suite` events attributed to a completely different, unrelated tracked repository/stack. For `PushHandler`, this triggers `stack.sync_github(expected_head_sha: ...)` on stacks that belong to another organization, and for `StatusHandler` it can inject fabricated CI status against arbitrary commits. Depending on how `sync_github`/status ingestion feed into deploy-gating logic, this is a cross-repository write/authorization-escalation primitive: an attacker abuses one weak or attacker-controlled trust boundary (their own org's webhook secret) to influence state belonging to organizations they have no relationship to, which matches the "cross-repository writes" / escalation impact bar.

### Likelihood Explanation
Requires only that the attacker registers/controls a GitHub webhook secret for at least one organization configured on the shared Shipit instance (a normal, unprivileged setup step available to any org owner on a multi-tenant deployment), and no access to the target org's secrets, GitHub tokens, or a Shipit session — satisfying the "unprivileged attacker" and "no session/API token" constraints from the rules.

### Recommendation
Enforce that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers — i.e., reject the webhook if `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name`. Alternatively, resolve the target `Repository`/`Stack` using the same verified field (`repository.owner.login` + `repository.name`) that determined the signing secret, rather than trusting `full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `lib/shipit.rb#github_app_config`).
2. Attacker (owner of `attacker-org`, having configured their own webhook and thus knowing `attacker-org`'s `webhook_secret`) crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and successfully verifies the signature computed with the known `attacker-org` secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which computes `stacks` from `repository.full_name == "victim-org/victim-repo"` (per `Handler#repository_name`/`Repository.from_github_repo_name`) — a repository the attacker has no relationship to — and invokes `stack.sync_github(expected_head_sha: params.after)` on it, all without ever presenting `victim-org`'s webhook secret or any Shipit session/token.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
