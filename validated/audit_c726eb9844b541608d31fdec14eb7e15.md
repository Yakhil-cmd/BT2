### Title
Cross-tenant `Team` mutation via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the `Team` record solely by `Team.find_or_create_by!(github_id: params.team.id)`, with no filter on `params.organization.login` or the organization that authenticated the webhook. Because `WebhooksController#verify_signature` only authenticates that the payload's `organization.login`/`repository.owner.login` matches the signing org's own webhook secret — it never checks that the `team.id` in the payload actually belongs to that org — an attacker who controls a legitimately configured GitHub org in `Shipit.github_organizations` can send a genuinely-signed `membership` webhook naming a `team.id` that collides with a pre-existing `Team` row created earlier from a different (victim) organization's real sync, and add themselves as a member of that `Team`.

### Finding Description
The broken binding: `Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login` is assumed but never enforced; in fact `find_or_create_by!` matches ANY existing row with that `github_id` regardless of which organization created it [1](#0-0) .

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from the payload itself (`params.dig('repository','owner','login') || params.dig('organization','login')`), fetches `Shipit.github(organization: repository_owner)`, and verifies the HMAC signature against that org's own `webhook_secret` [2](#0-1) . This only proves the request was signed by the org named in the payload — it does not bind `team.id` to that org.
2. `MembershipHandler#process` calls `find_or_create_team!`, which looks up by `github_id` only, then calls `team.add_member(member)` on whatever row is returned [3](#0-2) .
3. `Team#add_member` unconditionally appends the member [4](#0-3) .

Attacker's exact request: attacker owns/configures a GitHub App/org ("attacker-org") that is a legitimate entry in Shipit's multi-org config. They construct a `membership` webhook JSON payload with `organization.login = "attacker-org"` (so `verify_signature` correctly authenticates it against attacker-org's own secret) but set `team.id` equal to the victim `Team`'s `github_id` (a `Team` row already persisted from an earlier legitimate sync belonging to the victim org), and `member.login` equal to their own (or a colluding) GitHub username. They sign the raw body with attacker-org's `webhook_secret` and POST to `/webhooks` with `X-Github-Event: membership`.

Why existing guards fail: `verify_signature` only validates that the *signing org* matches the *org named in the payload* — both attacker-controlled/consistent — it never cross-checks the `team.id` against that org. `find_or_create_team!`'s lookup key (`github_id`) is global across all organizations. The `ExplicitParameters` schema only enforces types/presence, not org-team binding [5](#0-4) . No `User#authorized?`/`require_permission!` check applies to this webhook endpoint at all — it's an unauthenticated (session-wise) inbound webhook.

### Impact Explanation
The attacker becomes a member of an arbitrary pre-existing `Team` row as long as they can guess/learn its numeric `github_id` (per the stated precondition). If that `Team` is one of the entries returned by `Shipit.github_teams` (used by `User#authorized?` via `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , gated in `force_github_authentication` [7](#0-6) ), the attacker's own linked GitHub `User` record gains authorization into the entire Shipit application (all stacks, deploys, tasks) it protects — a High/Critical escalation into `Shipit.github_teams` authorization, matching the impact category described in the prompt. This is repeatable against any `Team` github_id the attacker can target, across organizational boundaries, as long as multiple orgs are configured in Shipit and the attacker controls at least one of them.

### Likelihood Explanation
Preconditions required: (1) `Shipit.github_organizations.size > 1` (multi-org deployment), (2) attacker legitimately controls one configured org (able to sign webhooks with its `webhook_secret`), (3) the victim's privileged `Team` row already exists in the `teams` table (created via a prior real `membership` sync or `find_or_create_by_handle`), and (4) attacker knows/guesses that `Team`'s GitHub numeric team `github_id`. Team IDs are often discoverable via public GitHub APIs or incremental guessing, but this is not verified as trivial in all cases — the prompt explicitly grants this as a precondition. Given those preconditions, the attack costs a single crafted, self-signed HTTP POST and is fully repeatable/scriptable.

### Recommendation
Scope the `Team` lookup by both `github_id` and the authenticated organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify in `find_or_create_team!` (or in the controller) that `params.organization.login` matches the `repository_owner`/org used to authenticate the webhook signature, rejecting mismatches. Consider also validating on update that an existing `Team` row's `organization` matches the incoming payload's org before allowing membership mutation, raising/dropping the event otherwise.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot mutate a Team belonging to a different organization" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins', api_url: 'https://example.com')
  attacker_org = 'attacker-org'

  @request.headers['X-Github-Event'] = 'membership'
  Shipit.github(organization: attacker_org) # assume configured with known webhook_secret
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'Admins', slug: 'admins', url: 'https://example.com' },
    organization: { login: attacker_org },
    member: { login: 'attacker-user' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Shipit::Team.count } do
    post :create, body: payload, as: :json
  end
  assert_response :ok

  # Binding check: victim_team's organization is unchanged, but its members were mutated
  # by a request authenticated for attacker_org, not victim-org.
  assert_equal 'victim-org', victim_team.reload.organization
  assert victim_team.members.exists?(login: 'attacker-user')
end
```
This demonstrates the equality `Team.find_or_create_by!(github_id: X).organization == signing_org.login` does NOT hold (the found `Team`'s organization is `victim-org` while the signing/authenticated org is `attacker-org`), proving cross-tenant mutation.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
