### Title
Missing leading-dash guard on branch name before `WorktreeCheckoutCommands` allows git option injection via `gh issue develop --checkout --worktree` - ([File: pkg/cmd/pr/shared/worktree.go])

### Summary
`WorktreeCheckoutCommands` builds git argument slices from a caller-supplied `branch` value without ever validating that it doesn't start with `-`. The only existing caller that adds this validation is `pkg/cmd/pr/checkout/checkout.go`'s `checkoutRun`. A second, independent call site, `pkg/cmd/issue/develop/develop.go`'s `checkoutBranch`, invokes `WorktreeCheckoutCommands` with a branch name derived from GraphQL API data (`api.CreateLinkedBranch` / linked-branch listing) and performs no such dash-prefix check.

### Finding Description
`WorktreeCheckoutCommands` returns, among other things, the bare-argument form `{"-C", target.Path, "checkout", branch}` when reusing an existing worktree with a pre-existing local branch, and `{"worktree", "add", "--", target.Path, branch}` / `{"worktree", "add", "--track", "-b", branch, "--", target.Path, startPoint}` for the other cases [1](#0-0) . The `checkout branch` line (no `--` separator) is the one case where a value beginning with `-` could be parsed by git as an option rather than a ref/pathspec.

`pkg/cmd/pr/checkout/checkout.go` guards against this by rejecting `pr.HeadRefName` with a leading dash before any command list is built [2](#0-1) , and only then calls `shared.WorktreeCheckoutCommands` [3](#0-2) .

`pkg/cmd/issue/develop/develop.go`'s `checkoutBranch` calls `prShared.WorktreeCheckoutCommands` directly with `checkoutBranch` (aliasing `branchName`) and never performs an equivalent dash check [4](#0-3) . `branchName` originates either from `api.CreateLinkedBranch`'s return value or from an existing linked branch's `BranchName` field returned by the GraphQL API (`api.ListLinkedBranches`) [5](#0-4) [6](#0-5) , both of which are values under the control of whatever GitHub host/API endpoint the CLI is pointed at.

### Impact Explanation
If the branch name delivered by the API response begins with `-`, and the target worktree/local-branch state happens to make `WorktreeCheckoutCommands` choose the bare `{"-C", path, "checkout", branch}` form, git could interpret the value as an option instead of a branch name (option injection into `git checkout`), potentially causing unintended git behavior. This matches a git command/option-injection class impact, though it does not by itself demonstrate arbitrary code execution — it requires a `git checkout` option whose semantics are dangerous.

### Likelihood Explanation
Exploitability is limited by several preconditions that are not fully attacker-controlled in the normal (github.com) flow: (1) it requires the branch name to reach `WorktreeCheckoutCommands` via the `checkout` (no `--`) branch of the conditional, which additionally requires `target.Reuse == true` and `client.HasLocalBranch(branch)` to already be true on the victim's machine — i.e., a local branch with that dash-prefixed name must already exist locally, which is not something a remote API response alone can create; and (2) for the `worktree add -b <branch>` forms, the branch value is consumed as the argument to `-b`, which git's flag parser accepts literally regardless of leading dash, so those forms are not exploitable. Genuine control over the branch-name field additionally requires the victim to be pointed at an attacker-influenced GitHub host/API response (e.g., a malicious or compromised GHES instance), which is a narrower attacker model than a standard github.com PR/issue interaction. I could not confirm from the available code that `api.CreateLinkedBranch`/`ListLinkedBranches` GraphQL responses are otherwise validated for ref-name safety before reaching this call site.

### Recommendation
Move the leading-dash validation for the branch value out of `checkout.go` and into `WorktreeCheckoutCommands` itself (or a shared helper called by both `checkout.go` and `develop.go`) so all current and future callers get the same protection. Additionally, prefer inserting `--` before the bare `checkout branch` argument list at `pkg/cmd/pr/shared/worktree.go` line 43 to make that command form inert to leading dashes, consistent with the other three returned command forms.

### Proof of Concept
```go
// pkg/cmd/pr/shared/worktree_test.go
func TestWorktreeCheckoutCommands_DashBranch_NoGuard(t *testing.T) {
    // Simulate a git.Client where HasLocalBranch reports the malicious
    // dash-prefixed branch as already existing locally, and target.Reuse=true.
    client := newTestGitClientWithLocalBranch(t, "--upload-pack=/tmp/evil")
    target := shared.WorktreeTarget{Path: "/tmp/wt", Reuse: true}

    cmds, branchExists := shared.WorktreeCheckoutCommands(
        client, target, "--upload-pack=/tmp/evil", "origin/--upload-pack=/tmp/evil")

    require.True(t, branchExists)
    // Vulnerable assertion: the branch value is passed as a bare arg to
    // `checkout` with no preceding `--`, so git would treat it as an option.
    require.Equal(t, [][]string{
        {"-C", "/tmp/wt", "checkout", "--upload-pack=/tmp/evil"},
    }, cmds)
    // A safe implementation would instead emit something like:
    // {"-C", "/tmp/wt", "checkout", "--", "--upload-pack=/tmp/evil"}
}
```
Expected result on the current code: the assertion demonstrating the bare, unguarded argument passes, confirming `WorktreeCheckoutCommands` alone provides no protection against a leading-dash branch name, and that `pkg/cmd/issue/develop/develop.go`'s call site relies on no such guard at all.
