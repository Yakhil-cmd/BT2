### Title
Webhook Signature Verified Against `repository.owner.login` While Event Is Dispatched Against `repository.full_name`/Global SHA, Enabling Cross-Organization Status Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using `repository_owner`, which is read from the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0)  Once the signature is accepted, the actual handler dispatch resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, via `Handler#repository_name`/`stacks`, and in the case of the `status` event, it does not scope by repository/organization at all. [2](#0-1)  This mismatch breaks the trust binding "organization that authenticated" == "repository whose state is written."

### Finding Description
In a multi-org Shipit deployment (`Shipit.github(organization: ...)` supports per-organization apps/secrets, as documented in `config/secrets.development.example.yml`), each GitHub organization has its own `webhook_secret`. [3](#0-2)  `verify_signature` looks up which secret to validate against solely from `repository.owner.login` in the *attacker-controlled* raw JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

An attacker who legitimately controls a webhook secret for their *own* onboarded GitHub organization (e.g., they installed the Shipit GitHub App on their own org, as intended by the product) can craft a raw JSON body where `repository.owner.login` names their own org (so the signature validates with their own secret) while `repository.full_name` names a victim organization's repository. Because `repository_name` used for dispatch is read independently:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
the signature check and the dispatch target are decoupled — the field verified is not the field acted upon.

For the `status` handler the exposure is worse: it doesn't consult `repository`/`stacks` scoping at all and matches purely by commit SHA across the entire `commits` table:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5)  Since Git SHAs are content-addressed and can collide across repositories sharing history (forks, mirrors, cherry-picked/rebased commits, or an attacker simply pushing the exact same commit to their own attacker-controlled repo to learn or replicate a target SHA), this allows a caller who only has a *different* organization's valid webhook secret to inject a fabricated CI `Status` for a commit belonging to an unrelated stack.

### Impact Explanation
`Commit#deployable?` and `Commit#blocked?` derive from `status`/`blocking_statuses`, and `create_status_from_github!` feeds directly into `Commit#status`, which gates `deployable?`, `blocked?`, and `schedule_continuous_delivery`. [7](#0-6) [8](#0-7)  By forging a passing status for a commit that shares a SHA with a commit in a victim stack (via the attacker's own legitimately-signed webhook), an attacker can flip a blocking/required check to success, unblocking continuous deployment or unblocking a deploy that was previously gated on CI, resulting in an unauthorized deploy path being enabled without ever needing that victim organization's own webhook secret. This is High severity: it escalates trust from "authenticated as org A" to "write state for org B's deploy-gating data," matching the required impact category of an unauthorized deploy/rollback path being unlocked.

### Likelihood Explanation
Exploitation requires only a legitimately-provisioned webhook secret for *some* organization onboarded to the Shipit instance (a realistic scenario for any multi-tenant/multi-org Shipit installation, which the engine explicitly supports) plus the ability to craft an arbitrary JSON POST body and compute HMAC-SHA1 over it — both fully available to any client permitted to send webhooks for their own org. The commit-SHA collision requirement is the main constraining factor (needs a shared/forked/duplicated commit across repos), which lowers likelihood from "trivial" to "plausible" but does not require any privileged Shipit or GitHub App credential beyond the attacker's own org's webhook secret.

### Recommendation
Bind the field used to select the verification secret to the exact same field used for dispatch, and re-validate consistency:
- Derive `repository_owner` for secret selection from the same parsed `full_name` used by `Handler#repository_name` (single source of truth), not from a separate `repository.owner.login`/`organization.login` field.
- In `StatusHandler` (and any other handler not already scoped via `stacks`), scope `Commit` lookups by the repository/stack resolved from the verified organization, e.g. `stacks.flat_map(&:commits).where(sha: ...)` instead of a global `Commit.where(sha:)`.
- Reject payloads where `repository.owner.login` and the owner segment of `repository.full_name` disagree.

### Proof of Concept
1. Attacker legitimately controls Org A, which is configured in Shipit's multi-org `github:` secrets with its own `webhook_secret`.
2. Attacker pushes/forks a commit so that a specific SHA exists both in Org A's repo and Victim Org B's repo/stack tracked by Shipit (e.g., a shared upstream commit, or simply reuses a known public SHA from Org B if Org B's repo is public and history overlaps).
3. Attacker crafts a raw JSON webhook body for the `status` event:
```json
{
  "sha": "<shared-sha>",
  "state": "success",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Attacker signs this body with Org A's `webhook_secret` (`X-Hub-Signature: sha1=...`) and POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's app/secret, and the signature validates successfully. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository scoping, finds the matching commit belonging to Victim Org B's stack, and creates a `success` status for it, potentially unblocking that stack's continuous deployment. [6](#0-5) 

**Uncertainty:** I was not able to fully verify from the index whether `Shipit.github(organization:)` enforces that only one organization's app exists in typical single-tenant deployments (in which case this specific analog requires the multi-org config to be active), nor did I locate the exact production likelihood of duplicate SHAs across distinct tracked stacks in real deployments. These are noted as assumptions inherent to the multi-org feature the engine ships with.
