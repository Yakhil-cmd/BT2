### Title
Cross-organization signature/mutation split allows a no-secret org's webhook to archive a victim `ReviewStack` and trigger bot-authenticated deploy actions - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate a webhook using `repository.owner.login` (via `repository_owner`), while `ClosedHandler` (and its siblings) resolve the repository/stack to mutate using `repository.full_name` alone. Nothing binds these two values together, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured, so an attacker who can get traffic verified against any no-secret org can point `repository.full_name` at an unrelated, fully-configured victim org/repo and have the handler act on it.

### Finding Description
The broken invariant, as an equality that the code never checks:

`Repository.from_github_repo_name(params.repository.full_name).owner == params.repository.owner.login (the org used to verify the signature)`

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` [1](#0-0)  and uses it only to pick which `GitHubApp` config to verify against: `github_app = Shipit.github(organization: repository_owner)` [2](#0-1) .
2. `Shipit::GitHubApp#verify_webhook_signature` short-circuits to `true` when that org's `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) . Multi-org deployments (`docs/setup.md` "Using Multiple Github Applications") explicitly support per-org configs, and the engine's own test fixtures show orgs configured with `webhook_secret: # nil` (`test/dummy/config/secrets_double_github_app.yml`), confirming this is a real, engine-supported configuration state, not merely theoretical.
3. Once `verify_signature` passes, `WebhooksController#create` dispatches the raw payload to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
4. `ClosedHandler#repository` resolves the target repository purely from `params.repository.full_name`, completely independent of `repository_owner`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , and `Repository.from_github_repo_name` splits `full_name` on `/` and looks the repository up by `owner`/`name` alone, with no cross-check against the signer [6](#0-5) .
5. `ClosedHandler#process` then archives whatever `ReviewStack` matches the PR number under that resolved repository: `review_stack.archive!` [7](#0-6) .

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, body containing `action: "closed"`, `repository.owner.login = "no-secret-org"` (an org Shipit has configured without a `webhook_secret`), `repository.full_name = "victim-org/victim-repo"` (a fully-configured org with `bot_login` set), and `number`/`pull_request.number` matching an existing open review-stack PR in the victim repo. No valid `X-Hub-Signature` is required because the no-secret org's check auto-passes.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is registered, not payload consistency; `verify_signature` authenticates against an org chosen entirely by attacker-controlled `repository.owner.login`; there is no `ExplicitParameters` field or model validation tying `repository.owner.login` to `repository.full_name`'s owner; `Repository.from_github_repo_name` performs no ownership/authentication cross-check.

### Impact Explanation
The request lets an attacker who never learns the victim org's `webhook_secret` cause a state mutation (archiving a `ReviewStack`, which is bound to a PR in the victim's repository) to be applied to a repository that did not authenticate the request — matching the Critical category "a payload for one repository mutating another's stack." Because `ReviewStack` archival is one of several mutating operations reachable via the same split-verification path (other `pull_request` handlers — `opened_handler`, `labeled_handler`, `reopened_handler`, `unlabeled_handler` — use the identical `params.repository.full_name`-based resolution pattern), the same confused-deputy path generalizes to provisioning/labeling/reopening review stacks, and when the victim stack has `bot_login` configured, any auto-triggered actions from those state transitions execute under the bot's GitHub identity. This is repeatable against any victim org/repo as long as some org configured in the Shipit instance has a blank `webhook_secret`, and the blast radius spans every tenant repository configured on that Shipit instance.

### Likelihood Explanation
Preconditions: (1) a multi-org Shipit deployment (`secrets.github` keyed by org name, per `docs/setup.md`), (2) at least one configured org with no `webhook_secret` set — an engine-supported, test-fixture-documented configuration, not a contrived edge case, (3) attacker knows/guesses that org's login and the victim's `owner/repo` full name — both are public GitHub information. No GitHub App private key, `webhook_secret`, session, or API token is needed. The attacker cost is a single crafted HTTP POST; the attack is trivially repeatable against any PR number in the victim repository.

### Recommendation
Bind webhook authentication to the exact repository being mutated: derive `repository_owner` for signature lookup from the same value used by handlers (`repository.full_name`'s owner segment), and additionally have each handler verify that the resolved `Repository#owner` matches the org that authenticated the request before performing any mutation. Additionally, treat a blank/missing `webhook_secret` for a configured org as a hard misconfiguration (raise/log and reject) rather than silently short-circuiting `verify_webhook_signature` to `true`.

### Proof of Concept
Minitest plan (extending `test/controllers/webhooks_controller_test.rb` patterns):
1. Configure two orgs via `Shipit.stubs(:secrets)` with a `github` hash: `NoSecretOrg` (no `webhook_secret`, no `bot_login`) and `VictimOrg` (`webhook_secret` set, `bot_login: "shipit[bot]"`).
2. Create `Repository` fixture with `owner: "victimorg"`, `name: "victim-repo"`, and an associated `ReviewStack`/open PR (e.g. PR `#42`) belonging to that repository.
3. Assert binding before: `repository_owner == "no-secret-org"` while `Repository.from_github_repo_name("VictimOrg/victim-repo").owner == "victimorg"` — i.e. `repository_owner != resolved_repository.owner`.
4. POST `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, body: `{"action":"closed","number":42,"pull_request":{...,"number":42,...},"repository":{"full_name":"VictimOrg/victim-repo","owner":{"login":"no-secret-org"}},"sender":{"login":"attacker"}}`.
5. Assert response is `:ok` (200/204), not `:unprocessable_entity`.
6. Assert the `ReviewStack` for PR `#42` under `VictimOrg/victim-repo` is archived (`review_stack.reload.archived?` is `true`), proving the mutation succeeded against a repository whose secret never authenticated the request.
7. Assert binding after: still `repository_owner ("no-secret-org") != resolved_repository.owner ("victimorg")`, yet the mutation occurred — demonstrating the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it" is violated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
