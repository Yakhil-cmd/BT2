### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while all event handlers act on the unvalidated `repository.full_name` field — cross-organization webhook forgery in multi-GitHub-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments (`config/secrets.yml` with one GitHub App per org, see `test/dummy/config/secrets_double_github_app.yml`), `Shipit::WebhooksController#verify_signature` selects which org's HMAC secret to validate the payload against based on a field read out of the *same untrusted JSON body* (`repository_owner`), rather than binding the verified signature to the specific repository that downstream handlers will act on (`repository.full_name`). This breaks the equality "organization whose secret authenticated the request == repository that gets written to," letting a party who legitimately controls one org's GitHub App/webhook secret forge events that make Shipit act on stacks belonging to a *different* organization/repository.

### Finding Description
`verify_signature` picks the app/secret purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback) — a string the requester fully controls in the raw JSON body they are signing. `Shipit.github(organization: repository_owner)` then resolves to a completely independent `GitHubApp` instance/secret per org: [3](#0-2) 

The signature check itself is a straight HMAC over the raw body using that org's secret: [4](#0-3) 

Once the signature passes, `WebhooksController#create` dispatches the parsed JSON to handlers: [5](#0-4) 

But every handler resolves the *target* repository/stack from a different field of the same JSON body — `repository.full_name` — with no check that it matches `repository.owner.login` used for signature selection: [6](#0-5) [7](#0-6) 

Because the attacker constructs the entire JSON body themselves (it isn't a GitHub-generated payload with internally-consistent fields), they can set `repository.owner.login` = `"OrgA"` (the org whose webhook secret they legitimately know/administer) while setting `repository.full_name` = `"OrgB/some-other-repo"` (a repository belonging to a completely different tenant/org configured in the same Shipit instance). The equality that should hold — *the org authenticated by the signature == the repository namespace being acted on* — is never enforced. This is structurally the same defect as the reported `getRestAmount` bug: a value that should be validated/derived consistently across the whole computation (`totalAmount` accumulated per vesting type / here, the repository owner bound to the signature) is instead read independently a second time from attacker-influenced data (`repository.full_name`), producing an inconsistent result.

### Impact Explanation
This allows cross-repository/cross-organization writes: an attacker who administers (or otherwise knows the webhook secret of) *any one* GitHub App configured on the shared Shipit instance can forge webhook deliveries that Shipit treats as authenticated, but whose target repository field points at another tenant's repository/stack. Depending on which event is forged (`push` → `PushHandler#process` calling `stack.sync_github`, or PR events manipulating review stacks/archiving), this can trigger unauthorized syncs, review-stack provisioning/archival, or PR state changes against a stack that belongs to an organization the attacker has no legitimate access to — satisfying the "cross-repository writes" / "unauthorized deploy or rollback" bar, since `sync_github` drives the pipeline that leads to deploy task enqueuing.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one of the GitHub Apps configured under a multi-org Shipit deployment — a realistic scenario for a shared/multi-tenant Shipit instance where separate customer orgs each install their own App per `docs/setup.md`'s "Using Multiple Github Applications" section. No GitHub-side spoofing is needed because the HMAC is computed by the attacker themselves over a JSON body they fully control; they never need to intercept or forge a real GitHub-signed payload — only to have legitimate access to one org's secret.

### Recommendation
Bind the verified signature to the exact repository being acted on: after computing/verifying the signature for `repository_owner`, re-derive `repository.full_name`'s owner segment and reject the request (422) if it does not match `repository_owner`/the resolved organization. Alternatively, resolve the target `Repository`/`Stack` first and check that its owning organization matches the app selected for signature verification before invoking any handler.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgA` and `OrgB`, each with its own GitHub App/webhook_secret (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who administers `OrgA`'s GitHub App (knows `OrgA`'s `webhook_secret`), craft a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `sync_github` on `OrgB`'s stacks — actions performed on a stack the attacker (an OrgA-only party) should have no authority over.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
