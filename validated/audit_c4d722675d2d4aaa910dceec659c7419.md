## Finding

The external report's bug class — a gating function that returns a permissive/zero-cost default in an unhandled state, letting an unprivileged actor bypass the intended restriction "for free" — has a direct analog in this repo's `hookify` plugin, which implements user-configured `PreToolUse` blocking rules (its stated purpose is to deny dangerous `Bash`/`Write`/`Edit` operations).

### Title
Hookify PreToolUse hook fails open on any error, silently bypassing configured block rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The `hookify` plugin's `PreToolUse` hook is designed so that any exception during rule loading or rule evaluation causes the hook to allow the tool call (exit 0, no deny decision) instead of enforcing the user's configured `block` rules.

### Finding Description
`main()` in `pretooluse.py` wraps the entire rule-loading and evaluation pipeline in a single broad `try/except Exception`. On any error it prints a generic `systemMessage` and always calls `sys.exit(0)` without emitting a `hookSpecificOutput.permissionDecision: "deny"`, which is the only way `RuleEngine.evaluate_rules` communicates a block [1](#0-0) . The `finally` block reinforces this: `# ALWAYS exit 0 - never block operations due to hook errors` [1](#0-0) .

The blocking logic itself lives in `RuleEngine.evaluate_rules`, which only emits `permissionDecision: "deny"` when a `block`-action rule successfully matches; any exception raised before that return (in `load_rules`, `load_rule_file`'s custom hand-rolled YAML/frontmatter parser, or in `_rule_matches`/`_check_condition`/`_extract_field`) is caught by the outer handler in `main()` and converted into a silent allow [2](#0-1) . `_extract_field` for `MultiEdit` calls `e.get('new_string', '')` on each item of `tool_input.get('edits', [])` without validating that each item is a dict [3](#0-2) , and `load_rule_file` relies on a custom, non-standard frontmatter/YAML parser prone to producing malformed `Rule`/`Condition` objects on edge-case input [4](#0-3) .

This is analogous to `getPrice()` returning `0` (a permissive default) once the contract entered an unhandled state (`numSales >= SALE_LIMIT`): here, the security control's unhandled/error state resolves to "allow" instead of "deny," silently discarding the enforcement the hook exists to provide.

### Impact Explanation
Because the fallback state is "allow" rather than "deny," any malformed rule file, an unusual/edge-case tool input to `Bash`/`Write`/`Edit`/`MultiEdit`, or a bug anywhere in the custom frontmatter parser causes user-configured `block` rules to be silently skipped for that tool call. A user or org relying on hookify's `block` action to prevent a specific dangerous `Bash` command or file write gets no warning that protection was dropped — the tool call proceeds as if no rule existed. This falls under the "hook bypass" / "tool authorization" trust-boundary category.

### Likelihood Explanation
This is a design choice explicitly documented in the code ("ALWAYS exit 0 - never block operations due to hook errors"), not a rare edge case — it fires on any exception in a hand-rolled parser and loosely-typed evaluation path, both of which have realistic failure modes (malformed rule markdown, unexpected `tool_input` shapes). Likelihood of the failure path being hit under normal usage/misconfiguration is moderate to high; likelihood of it being deliberately triggered by an attacker to defeat a specific block rule is lower, since it requires influencing rule files or tool_input shape.

### Recommendation
Distinguish "no rules matched" from "rule evaluation failed": on any exception, either (a) re-raise/fail closed by emitting `permissionDecision: "ask"` so the user is prompted rather than silently allowed, or (b) at minimum surface a loud, non-suppressible warning distinguishing "hookify errored, no rules were checked" from "hookify checked and approved." Fix the `MultiEdit` field extraction to validate item types, and replace the hand-rolled frontmatter parser with a standard YAML library to reduce parser-differential failure modes.

### Proof of Concept
1. Configure a `.claude/hookify.block-rm.local.md` rule with `action: block` on `Bash` commands matching `rm -rf`.
2. Trigger a `PreToolUse` call for `MultiEdit` (or any tool) with an `edits` array containing a non-dict element, or corrupt one rule file's frontmatter so `load_rule_file` raises inside the custom parser.
3. Observe `pretooluse.py`'s outer `except Exception` catches the error, prints only a `systemMessage`, and exits 0 without `hookSpecificOutput.permissionDecision: "deny"` — the tool call is not blocked despite the `block` rule being configured and even matching the actual `Bash` command in the same batch of rules being evaluated, because the exception aborted `evaluate_rules` before the `rm -rf` rule was checked. def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}

def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value

        # List item (starts with -)
        elif stripped.startswith('-') and in_list:
            # Save previous dict item if any
            if in_dict_item and current_dict:
                current_list.append(current_dict)
                current_dict = {}

            item_text = stripped[1:].strip()

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:
                # Inline comma-separated dict: "- field: command, operator: regex_match"
                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
                        k, v = part.split(':', 1)
                        item_dict[k.strip()] = v.strip().strip('"').strip("'")
                current_list.append(item_dict)
                in_dict_item = False
            elif ':' in item_text:
                # Start of multi-line dict item: "- field: command"
                in_dict_item = True
                k, v = item_text.split(':', 1)
                current_dict = {k.strip(): v.strip().strip('"').strip("'")}
            else:
                # Simple list item
                current_list.append(item_text.strip('"').strip("'"))
                in_dict_item = False

        # Continuation of dict item (indented under list item)
        elif indent > 2 and in_dict_item and ':' in line:
            # This is a field of the current dict item
            k, v = stripped.split(':', 1)
            current_dict[k.strip()] = v.strip().strip('"').strip("'")

    # Save final list/dict if any
    if in_list and current_key:
        if in_dict_item and current_dict:
            current_list.append(current_dict)
        frontmatter[current_key] = current_list

    return frontmatter, message
