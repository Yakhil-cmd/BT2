### Title
`repository_owner` used for webhook signature verification is decoupled from `repository.full_name` used for the mutation, allowing a payload verified under one GitHub org to archive a review stack belonging to a different repository/org - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly from the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The `pull_request` handlers that actually mutate state (e.g. `ClosedHandler` / `ReviewStackAdapter#archive!`) instead resolve the target `Repository` from `params.repository.full_name`, a separate attacker-controlled field. Because these two fields are never required to agree, an attacker who can get any payload verified (trivially so for an org configured with no `webhook_secret`, per `verify_webhook_signature`'s `return true unless webhook_secret`) can set `repository.full_name` to an arbitrary victim repository and archive its active review stack.

### Finding Description
The broken binding: the code implicitly assumes
`repository_owner (used to pick webhook_secret) == repository.full_name's owner (used to find and mutate the Repository)`,
but nothing enforces this equality.

Path:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` (attacker-controlled JSON), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) short-circuits to `true` whenever that org's config has no `webhook_secret` set: `return true unless webhook_secret`. [2](#0-1) 
- Once verification passes, `Shipit::WebhooksController#create` parses `params` and dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw, attacker-supplied body — no re-check ties the payload's `repository.full_name` back to the org that was verified. [3](#0-2) 
- `ClosedHandler#repository` resolves the actual target repository from `params.repository.full_name` — a field completely independent of the `repository.owner.login`/`organization.login` value used for signature routing. [4](#0-3) 
- `ReviewStackAdapter#archive!` then unconditionally archives the resolved stack (`stack.remove_from_provisioning_queue`, `stack.deprovision`, `stack.archive!`) if it exists and isn't already archived. [5](#0-4) 

Exploit request: attacker POSTs to `/webhooks` with `X-Github-Event: pull_request` and a body such as:
```json
{
  "action": "closed",
  "number": 42,
  "pull_request": { ... },
  "repository": { "owner": { "login": "attacker-controlled-or-unsecured-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
If `attacker-controlled-or-unsecured-org` is a GitHub org configured in Shipit without a `webhook_secret` (or one whose secret the attacker knows), `verify_signature` accepts the request regardless of the `X-Hub-Signature` header content — including the malformed no-`=` signature form described in the question, since that branch is never reached when `webhook_secret` is blank. The handler then archives the review stack for `victim-org/victim-repo`, a repository the attacker does not own and whose actual secret was never checked.

Existing guards fail because:
- `drop_unhandled_event` only checks the event *type* is handled, not payload consistency.
- `verify_signature` verifies HMAC using a secret keyed by `repository_owner`, not by the repository that will actually be mutated.
- No handler (`ClosedHandler`, `ReviewStackAdapter`) cross-checks that `params.repository.full_name`'s owner matches the org whose secret verified the request.

### Impact Explanation
An unprivileged attacker who can trigger delivery of a crafted webhook body to `/webhooks` (or send the HTTP request directly, since the endpoint is unauthenticated) can archive/deprovision an active review stack belonging to an arbitrary victim repository/org, provided any org in the Shipit deployment is configured without a `webhook_secret` (or the attacker knows any org's secret). This is a cross-tenant state manipulation: a payload nominally verified for org A mutates a stack belonging to repository/org B, matching the Critical category ("a payload for one repository mutating another's stack"). The action is repeatable against any repository whose `full_name` the attacker chooses to place in the payload, and could similarly be aimed at other `pull_request` handlers (`labeled`, `unlabeled`, `opened`, etc.) that resolve their target the same way.

### Likelihood Explanation
Exploitation requires that at least one GitHub organization/app registered in Shipit's configuration has no `webhook_secret` set (or that the attacker otherwise knows a valid secret for some org) — this is a plausible operational state in multi-org Shipit deployments, and is exactly the condition `return true unless webhook_secret` is designed to permit. No Shipit session, API token, or GitHub credentials for the victim org are needed; the attacker only needs network access to POST to `/webhooks` and knowledge of the victim's `repository.full_name`, which is public information (public repos) or already known to the attacker in a fork/PR scenario. Cost is a single unauthenticated HTTP request per archive action.

### Recommendation
Bind signature verification to the same repository identity used for state mutation: after locating the target repository via `params.repository.full_name`, verify the signature using that repository's owning organization's secret, and reject (422) if `repository.owner.login`/`organization.login` does not match the actual owner of `repository.full_name`. Additionally, do not treat a missing `webhook_secret` as automatic pass-through when other organizations in the same deployment do have secrets configured; require explicit signature validation for every configured org and fail closed if a webhook secret is absent for a production org, or verify against the union of expected secrets rather than a single request-attacker-chosen org.

### Proof of Concept
minitest plan (under `test/`, no live GitHub, using existing test helpers):
1. Configure two organizations in `Shipit.github_apps` test config: `"secured-org"` with a `webhook_secret`, and `"open-org"` with none.
2. Create a `Repository` for `"victim-org/victim-repo"` (unrelated to either config org) with an active, unarchived `ReviewStack` for PR `#42`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body:
   `{"action":"closed","number":42,"pull_request":{...},"repository":{"owner":{"login":"open-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert the binding before: `victim_repo.review_stacks.find_by(environment: "pr42").archived?` is `false`.
5. Assert response status is `200`/`head :ok` (verification bypassed via `open-org`'s missing secret) despite the malformed/absent `X-Hub-Signature`.
6. Assert the binding after: `victim_repo.review_stacks.find_by(environment: "pr42").reload.archived?` is now `true`, proving a payload "verified" under `open-org`'s (non-)secret caused a state change on `victim-org/victim-repo`, whose own secret was never checked.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
