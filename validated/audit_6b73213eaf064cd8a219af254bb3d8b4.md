### Title
Webhook signature verification is keyed to an attacker-chosen organization, but event handlers act on payload data for a different, unverified repository/organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC against using an organization name taken directly from the *unauthenticated* JSON body, and then hands the entire (still forgeable) payload to event handlers that act on repository/commit fields that are never cross-checked against that verified organization. This mirrors the Seaport `AdvancedOrder.numerator`/`denominator` bug: a field that drives a security-relevant decision (which secret to trust) is disconnected from the fields that are ultimately used to perform the state-changing action (which repository/commit gets written), producing a binding break between "the organization that authenticated" and "the repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the signing organization straight from the request body before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, i.e. attacker-controlled content of the very payload being verified. `Shipit.github(organization: repository_owner)` resolves to whichever App config matches that string (Shipit supports multiple GitHub Apps, one per organization key): [3](#0-2) 

If an attacker administers *their own* GitHub App installed on an organization that Shipit is also configured for (a legitimate, unprivileged scenario — they only need to be an app owner/admin of their own org, not of Shipit or of any victim org), they know that organization's `webhook_secret` and can compute a valid `X-Hub-Signature` for **any** payload body, because the signature only proves "the sender knows OrgA's secret," not "the payload's `repository`/`sha`/`branches` fields genuinely originate from OrgA."

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw, attacker-crafted JSON to the matching `Shipit::Webhooks::Handlers::*` handler: [4](#0-3) 

Handlers derive the target `Stack`/`Commit` purely from further fields inside that same unverified payload, with no re-check that they belong to the organization whose secret validated the signature. The base `Handler` looks stacks up by `repository.full_name`: [5](#0-4) 

`StatusHandler` is worse still — it doesn't even scope by repository, it looks up **any** `Commit` matching the given `sha` across the entire installation and writes a CI status to it: [6](#0-5) 

So the equality the design implicitly assumes — `organization authenticated by verify_signature == organization/repository whose commit gets a status/push processed` — is never enforced. An attacker who legitimately controls OrgA's webhook secret can forge a `status` event whose `sha` belongs to a commit tracked under a completely different Stack/organization (OrgB), and Shipit will accept and record it as if it came from OrgB's GitHub App.

### Impact Explanation
Forged commit statuses directly influence `MergeRequest#reject_unless_mergeable!` / `StatusChecker` and `Stack#deployable?` continuous-delivery gating, since deploy/merge decisions are driven by the `Status` records this handler writes. An attacker who only controls a webhook secret for their own, unrelated organization can inject a fabricated `success` status onto an arbitrary tracked commit belonging to a different organization's stack, potentially unblocking a merge or continuous deployment that should have been blocked by failing/missing CI — i.e., an **unauthorized deploy or merge**, matching the Critical severity bucket in the rules. It can equally be used to inject a fabricated `failure`/`error` status to block a legitimate deploy (denial of a specific deploy, a lesser but still unauthorized-state-change impact).

### Likelihood Explanation
Exploitation requires only that the attacker administers a GitHub App/organization that is one of the (potentially many) organizations configured in Shipit's multi-org `github:` secrets block (a normal, unprivileged onboarding scenario for any org that wants to use Shipit — see `docs/setup.md`'s "Using Multiple Github Applications" section and `test/dummy/config/secrets_double_github_app.yml`). No Shipit session, API token, or victim credentials are needed — only knowledge of a `sha` for a targeted commit, which is typically public. This makes the likelihood of a capable attacker in a multi-tenant Shipit deployment realistically high.

### Recommendation
After signature verification succeeds, re-derive and enforce that every payload field used to select a Stack/Commit (`repository.full_name`, `sha`, etc.) actually belongs to the organization whose secret was used to verify the signature — e.g., check that `Repository.from_github_repo_name(repository_name)`'s owner matches `repository_owner`, and scope `StatusHandler`'s commit lookup by repository, not just `sha`, before writing any state.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgA` (attacker-controlled) and `OrgB` (victim), per `test/dummy/config/secrets_double_github_app.yml`-style multi-org config.
2. Attacker knows `OrgA`'s `webhook_secret` (they legitimately set it up for their own org's app).
3. Attacker crafts a `status` webhook JSON body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"}, "sha": "<victim commit sha in OrgB's stack>", "state": "success", ...}`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` (from the payload) and the HMAC checks out, so the request passes.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — finds the victim's commit in `OrgB`'s stack — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status despite the request never being authenticated by `OrgB`'s app.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
