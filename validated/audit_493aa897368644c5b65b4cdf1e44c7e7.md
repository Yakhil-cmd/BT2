### Title
`MembershipHandler#find_or_create_team!` resolves teams by attacker-controlled `github_id` alone, letting a foreign org hijack the `Shipit.github_teams` authorization anchor - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit.github_teams` pins authorization to `Team` rows resolved by `organization/slug` via `Team.find_or_create_by_handle` [1](#0-0) , while `MembershipHandler#find_or_create_team!` resolves/creates `Team` rows keyed solely on the webhook payload's `team.id` (`github_id`) with no check that the payload's `organization.login` matches the existing row's `organization` [2](#0-1) . Any correctly-signed membership webhook whose `team.id` collides with an already-resolved authorization-anchor team's `github_id` will silently add the attacker's chosen `member.login` to that pre-existing, unrelated `Team` row.

### Finding Description
Binding claimed: `Team(organization: O, slug: S)` resolved by `Shipit.github_teams` (boot-time, via `Team.find_or_create_by_handle`, keyed on `organization`+`slug`) must equal the `Team` mutated by the webhook path (keyed on `github_id` only) for every incoming membership event, i.e. `Shipit.github_teams.detect{|t| t.github_id == payload.team.id}.organization/slug == payload.organization.login/payload.team.slug`. This equality is never enforced.

Code path:
- `Team.find_or_create_by_handle` in `app/models/shipit/team.rb:18-21` finds/creates a row by `organization`+`slug`, fetching the real `github_id` from GitHub's API - this is the row memoized by `Shipit.github_teams` (`lib/shipit.rb:256-258`) and used for `User#authorized?` checks in `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`).
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`). Because `find_or_create_by!` first performs a `find_by(github_id:)`, if a row with that `github_id` already exists (e.g. the authorization-anchor team created at boot), the block is **never executed** - the found row's `organization`/`slug`/`name` are left untouched, and the payload's own `organization.login`/`team.slug`/`team.name` are silently discarded.
- `process` then does `team.add_member(User.find_or_create_by_login!(params.member.login))` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-28`), adding whatever GitHub login the attacker names in the payload to that team.

Signature verification does not close this gap: `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` resolves the signing key via `Shipit.github(organization: repository_owner)` where, for a `membership` event, `repository_owner` falls back to `params.dig('organization','login')` (`webhooks_controller.rb:59-62`). In a multi-org deployment (`github_app_config(organization)` in `lib/shipit.rb:196-200`), each configured organization has its own independent `webhook_secret`. An org that is itself a legitimately configured tenant of the Shipit instance (its own webhook secret known only to its own admins) can sign a `membership` webhook with `organization.login` set to its own org, but `team.id` set to the numeric `github_id` value it observed/guessed as belonging to another org's team (e.g. the org whose `org/slug` is pinned in `Shipit.github_teams`). This payload passes `verify_signature` (correctly signed for the attacker's own org) and `drop_unhandled_event`/`ExplicitParameters` schema checks (`membership_handler.rb:7-21` only require types, not cross-field consistency), then reaches `find_or_create_team!`, which matches the pinned row purely on `github_id` and ignores the mismatched `organization`.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `User#authorized?`, model validations) check that the resolved `Team#organization` matches `params.organization.login`, so the divergence is real and exploitable by any tenant/org that is configured in Shipit but is not part of `Shipit.github_teams`.

### Impact Explanation
A successful request adds an attacker-chosen GitHub login as a `member` of the `Team` row that anchors `Shipit.github_teams`-based authorization (`app/controllers/concerns/shipit/authentication.rb:26-30`, `app/models/shipit/user.rb`). Once that GitHub user completes OAuth login to Shipit, `current_user.authorized?` succeeds because they are now a `member` of the pinned team, granting full authenticated access to the Shipit UI/API for every stack/repository hosted on that instance - this is an authorization escalation into `Shipit.github_teams` (High), and if combined with deploy/rollback permissions of that team, becomes an unauthorized-deploy path (Critical). It is repeatable per membership event/action ('added'/'removed') and affects the entire Shipit instance, not just one repository.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization Shipit deployment where more than one GitHub organization/App configuration exists in `secrets.github`, (2) the attacker controlling (or being an admin of) one of those other configured organizations so they know its `webhook_secret` and can emit a validly signed `membership` webhook, and (3) knowledge or a correct guess of the target `Team`'s GitHub `github_id` (GitHub team IDs are integers, not secrets, and may be discoverable via the public GitHub API or UI for public/known teams). Single-tenant deployments (the common case, where `github_default_organization` is `nil`) are not exploitable this way because `Shipit.github(organization:)` ignores the `organization` argument and always uses the single shared secret, so the attacker cannot sign with a different key than the real one. This narrows real-world likelihood to genuinely multi-tenant Shipit setups, but within that configuration the attacker cost is low (no Shipit secrets needed, only their own tenant's webhook secret) and the exploit is trivially repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, do not resolve purely by `github_id`. Require that the found (or created) row's `organization` matches `params.organization.login` before acting on it - e.g. `Team.find_by(github_id: params.team.id)` and raise/ignore if `team.organization != params.organization.login`, or scope the lookup by both `github_id` and `organization`, and reject/ignore membership events whose `organization` doesn't match the persisted record for that `github_id`. Additionally consider adding a uniqueness validation/index on `(organization, github_id)` and re-syncing `organization`/`slug`/`name` fields defensively only when they match the previously trusted tuple.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership cannot add a member to a team belonging to a different organization by colliding github_id" do
  anchor_team = shipit_teams(:shopify_developers) # organization: 'shopify', slug: 'developers', github_id: X
  Shipit.stubs(:github_teams).returns([anchor_team])

  # Attacker's own org "attacker-org" is a configured tenant with its own webhook secret,
  # signs the payload correctly for "attacker-org" but reuses anchor_team.github_id
  request.headers['X-Github-Event'] = 'membership'
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulate correctly-signed request from attacker's own org

  malicious_payload = {
    action: 'added',
    team: { id: anchor_team.github_id, name: 'Attacker Team', slug: 'attacker-team', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-user' }
  }.to_json

  post :create, body: malicious_payload, as: :json

  anchor_team.reload
  # Binding check: the team resolved by github_id must NOT accept members from a mismatched organization
  refute_includes anchor_team.members.map(&:login), 'attacker-user'
  assert_equal 'shopify', anchor_team.organization # organization must remain unchanged
end
```
This test currently fails against the existing implementation because `find_or_create_by!(github_id:)` matches `anchor_team` and adds `attacker-user` as a member without validating `organization.login`, demonstrating the authorization-anchor hijack.
