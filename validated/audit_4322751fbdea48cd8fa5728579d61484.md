## Title
Webhook signature verification binds to `repository.owner.login`, but event handlers act on `repository.full_name` — a payload-controlled organization/repository mismatch enables cross-tenant writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to validate the inbound HMAC signature by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body. Once verification passes, `create` dispatches the *entire* raw payload to handlers, which independently derive the target repository/stack from a *different* field, `repository.full_name` [1](#0-0) . In a multi-organization Shipit deployment (`Shipit.github(organization:)` config schema), nothing ties the organization whose secret validated the request to the repository the handler ultimately writes to.

### Finding Description
`verify_signature` computes the expected HMAC using the GitHub App config resolved for `repository_owner`: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key in `secrets.github` when the multi-org schema is used [4](#0-3) , and `GitHubApp#verify_webhook_signature` simply HMACs the raw body with that org's secret [5](#0-4) .

Crucially, the signature covers the *entire raw body*, but the organization used to pick the secret (`repository.owner.login`) is only one field inside that body — an attacker who legitimately controls a GitHub App installed on Organization A (and therefore knows Org A's `webhook_secret`, since App owners generate/see their own webhook secret) can POST an arbitrary, self-signed JSON body directly to the shared `/github/webhooks` endpoint. They can set `repository.owner.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the HMAC they compute with their own known secret validates), while setting `repository.full_name` = `"OrgB/some-repo"` — an entirely unrelated organization's repository hosted on the same Shipit instance.

`verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner segment. Once the check passes, `create` forwards the full payload to every registered handler for the event [6](#0-5) . All handlers resolve the acted-upon stack via `repository.full_name`, not via the field used for authentication: [1](#0-0) [7](#0-6) 

This breaks the trust equality that should hold: `organization authenticated by signature == organization owning the repository being written to`. Concretely:
- `PushHandler` will call `stack.sync_github(expected_head_sha:)` for any stack under `Repository.from_github_repo_name("OrgB/some-repo")`, forcing a `GithubSyncJob` for OrgB's stack using the attacker's chosen `expected_head_sha`, even though the attacker only authenticated as OrgA [8](#0-7) .
- `Shipit::Webhooks::Handlers::StatusHandler` is even less scoped: it does not use `repository` at all and matches purely on commit SHA across the *entire* installation: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [9](#0-8) . Commit creation triggers `schedule_continuous_delivery` [10](#0-9) , meaning a forged/injected status for a matching SHA belonging to a completely different organization's stack can influence that stack's CI-gated continuous-deployment decision.

### Impact Explanation
This crosses an organizational trust boundary the system is supposed to enforce: an operator who is only entitled to send webhooks (i.e., knows the `webhook_secret`) for their own GitHub organization can cause Shipit to perform writes — commit sync, status injection, membership/team churn (via `MembershipHandler`), pull-request-driven archive/unarchive of review stacks — against stacks belonging to a *different* tenant organization on the same shared Shipit instance. Because CI status (`StatusHandler`) can gate `continuous_deployment`, this can plausibly influence an unauthorized deploy decision for another organization's stack, and at minimum represents cross-repository/cross-organization writes into data the attacker's credentials should not reach. This matches the "cross-repository writes / unauthorized deploy" severity category.

### Likelihood Explanation
Exploitability requires only: (1) that the Shipit instance is configured with the multi-organization GitHub App schema (`config/secrets.yml` `github:` keyed by org, as documented in `docs/setup.md` and exercised in `test/dummy/config/secrets_double_github_app.yml`), and (2) that the attacker legitimately administers one GitHub App/organization on that shared instance (an "unprivileged" actor relative to the *other* organizations, but a normal, expected tenant of this Shipit instance). No compromise of `GITHUB_TOKEN`, session, or `ApiClient` token is required — the attacker uses their own, legitimately-issued webhook secret and the public, unauthenticated `/github/webhooks` HTTP endpoint. The mismatch is deterministic and requires no race condition or timing.

### Recommendation
In `WebhooksController#verify_signature`/`create` (or in the shared `Handler` base class), enforce that the organization resolved for signature verification matches the owner of `repository.full_name` (and `organization.login` where present) before dispatching to handlers — e.g., reject the event if `repository_owner != repository.full_name.split('/').first`. Additionally, `StatusHandler` should scope by `repository.full_name` like every other handler instead of matching commits globally by SHA.

### Proof of Concept
1. Configure Shipit with the multi-org schema, with Org A's app having `webhook_secret = SECRET_A`, and Org B ("victim") having a stack tracking `OrgB/victim-repo`.
2. As the legitimate owner of Org A's GitHub App (who knows `SECRET_A`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and the signature validates against the attacker's own known secret.
5. `PushHandler.call(params)` resolves the stack via `repository.full_name` = `"OrgB/victim-repo"` and enqueues `GithubSyncJob` for Org B's stack with the attacker-supplied `expected_head_sha`, even though the attacker never authenticated as Org B.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
