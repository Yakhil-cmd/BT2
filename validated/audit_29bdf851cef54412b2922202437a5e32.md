### Title
Unsanitized leading/trailing whitespace in device pairing name allows correspondent-identity spoofing - (File: device.js)

### Summary
`handlePairingMessage` in `device.js` accepts an attacker-controlled `device_name` from any device that initiates pairing (a paired-device message, reachable by any peer who obtains/guesses a pairing secret or by any already-paired counterparty performing reverse-pairing), and stores it as the correspondent's display `name` after only stripping HTML tags, without trimming or normalizing whitespace.

### Finding Description
The pairing handler validates `body.device_name` only for non-emptiness and length, then sanitizes it exclusively against HTML injection: [1](#0-0) [2](#0-1) 
The resulting `safe_device_name` is written verbatim (including any leading/trailing whitespace or invisible Unicode space characters) into `correspondent_devices.name`, which is later read back and displayed in wallet UI listings and cosigner/peer name lookups such as `readCorrespondents`, `readSharedAddressPeers`, and `readSharedAddressCosigners`: [3](#0-2) [4](#0-3) 
Because no code path trims or collapses whitespace before storage or display, an attacker who pairs with a victim (or triggers reverse-pairing to a wallet the victim already trusts) can register a correspondent name that is visually indistinguishable from a legitimate correspondent's name (e.g., `"Alice"` vs `"Alice "` or `"Alice\u00A0"`), matching the exact bug class described in CVE-2025-55127.

### Impact Explanation
`correspondent_devices.name` is used to identify counterparties throughout the wallet: shared/multisig address cosigner lists, private-payment counterparty selection, and correspondent pickers all display this field to the user as the trust anchor for who they are paying or co-signing with. A spoofed, whitespace-padded duplicate name can cause a user to mistakenly select a malicious correspondent believing it is a trusted one, leading to private payments being sent to the wrong (attacker-controlled) device address or to confusion when approving a shared/multisig address definition involving supposedly known cosigners. This can result in loss of funds sent via private payment to an impersonated correspondent.

### Likelihood Explanation
Any device can initiate pairing by obtaining a pairing secret (shared out-of-band, e.g., via QR code/link) or via automatic reverse-pairing triggered during shared-address negotiation; the `device_name` field is fully attacker-controlled and only filtered for HTML tags, not whitespace, so exploitation requires no special privilege beyond initiating a normal pairing handshake.

### Recommendation
Trim leading/trailing whitespace (and normalize internal whitespace/invisible Unicode characters) from `body.device_name` before sanitization/storage in `handlePairingMessage`, and apply the same trimming to any user-editable correspondent name set via `updateCorrespondentProps`, so that visually confusable duplicate names cannot be created.

### Proof of Concept
1. Attacker crafts a pairing message body: `{ pairing_secret: "<valid_or_shared_secret>", device_name: "Alice\u00A0" }` (a trailing non-breaking space or trailing regular space) and sends it via `sendMessageToDevice`/hub delivery to the victim.
2. Victim's `handlePairingMessage` accepts it (passes `isNonemptyString` and length checks), strips only HTML tags via `body.device_name.replace(/<[^>]*>?/g, '')`, and inserts the row into `correspondent_devices` with `name = "Alice\u00A0"`.
3. In the victim's wallet UI, `readCorrespondents`/`readSharedAddressPeers` returns both the legitimate `"Alice"` and the attacker's `"Alice\u00A0"` entries, rendered identically, allowing the victim to unknowingly select the attacker's device address for a private payment or multisig signing step.
