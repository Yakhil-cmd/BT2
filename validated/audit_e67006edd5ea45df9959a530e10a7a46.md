### Title
Cross-repository commit status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table, never scoping to the repository named in `payload.dig('repository','full_name')` via `Handler#stacks`/`Repository.from_github_repo_name`. Because git SHA1s are content-addressed and identical across forks/mirrors that share history, a `status` webhook that is validly signed for the attacker's own repository/org can create or overwrite `Status` rows on `Commit` records that belong to a completely unrelated `Stack`, as long as that stack's commit table happens to contain a row with the same SHA (trivially true for any commit the attacker's fork shares with the upstream/target repository).

### Finding Description
The broken binding is: `payload.dig('repository','full_name')` (the repository whose signature was verified) `==` the repository/stack that actually gets mutated. In `StatusHandler`, this equality is never enforced: [1](#0-0) 

Compare this with `PushHandler` and `CheckSuiteHandler`, which correctly restrict mutation to `stacks` (i.e., `Repository.from_github_repo_name(repository_name).stacks`) before touching any `Commit`: [2](#0-1) [3](#0-2) 

`Handler#stacks` exists precisely to bind the payload's repository to the DB rows it's allowed to touch: [4](#0-3) 

`StatusHandler` never calls `stacks` or `repository_name`; it queries `Commit.where(sha: params.sha)` unconditionally and calls `commit.create_status_from_github!(params)` on every matching row, regardless of which stack/repository owns it: [5](#0-4) 

`WebhooksController#verify_signature` only validates that the HMAC signature matches the GitHub App secret associated with `repository_owner` (derived from the payload) — it does **not** and cannot validate that the `sha` in the payload "belongs" to that repository, because GitHub itself never enforces such a binding for status events (a `status` event's `sha` is just whatever commit the sender chose to report status for, and does not have to be unique to one repository): [6](#0-5) 

**Exploit flow:** An attacker forks (or otherwise obtains a copy of) a public repository that is tracked as a Shipit stack. Because forks share git history, many commits in the fork have SHAs identical to commits in the upstream repo (and hence identical to `Commit` rows already stored under the victim's `Stack` in Shipit's database). The attacker's own org/account has the Shipit GitHub App installed (a legitimate, unprivileged, self-service action), so GitHub will deliver a genuinely signed `status` webhook for events triggered on the attacker's own fork (e.g. via `POST /repos/{attacker}/{fork}/statuses/{sha}` using the attacker's own GitHub token, which they are fully entitled to use on their own repository). The `X-Hub-Signature` is valid because it's computed over the attacker's own legitimately-triggered payload; `repository.full_name` in that payload is the attacker's own repo. Shipit's `verify_signature` accepts it. `StatusHandler#process` then finds and mutates any `Commit` row anywhere in the database sharing that `sha` — including the victim's stack's commit — writing an attacker-chosen `state`, `description`, `target_url`, and `context` via `create_status_from_github!`.

### Impact Explanation
This lets an attacker inject a forged CI status (e.g. `success`) onto a commit belonging to a stack/repository they do not control and never authenticated for. Since `Commit#deployable?` and `blocked?` depend on aggregated status state (`stack.ignore_ci? || (success? && !blocked?)`), and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when a commit becomes `deployable?`, a forged "success" status can make an otherwise-unverified/failing commit appear deployable and trigger an unauthorized continuous deployment, or conversely a forged "failure"/"error" status can block/deny legitimate deploys (denial of merge/deploy) for a target repository. This is a cross-tenant write — a payload signed for repository A mutates repository B's commit/status state — matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". It's repeatable against any stack whose tracked repository has publicly-known commit history the attacker can replicate/fork (i.e., broadly, since Shipit primarily targets typical GitHub-hosted repos).

### Likelihood Explanation
Preconditions are modest but nontrivial: (1) the attacker's own GitHub account/org must have the same Shipit GitHub App installed so their events are relayed and signed (a normal, self-service GitHub App installation on their own account, not requiring victim cooperation or any secret); (2) the attacker needs a commit SHA collision with a Commit row already present in Shipit's DB for the target stack — trivially achieved for public repos via forking (shared commit history) or for any repo whose commit objects (tree/parents/author/committer/timestamps/message) the attacker can reproduce. No Shipit credentials, sessions, or `Shipit.github_teams` membership are required. Attacker cost is low (fork + call GitHub's status API on their own repo) and the action is repeatable at will against any commit shared between their fork and the victim stack.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the verified payload before touching any `Commit`, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `payload.dig('repository','full_name') == repository owning the mutated Commit`, closing the cross-repository write.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "does not mutate commits belonging to a different repository than the payload" do
  victim_stack = shipit_stacks(:shipit)          # repository e.g. "shopify/shipit-engine"
  attacker_repo_full_name = "attacker/unrelated-repo"

  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "repository" => { "full_name" => attacker_repo_full_name }
  }

  # Assert the binding: repository_name in payload must never resolve to victim's repo/stack
  Shipit::Webhooks::Handlers::Handler.any_instance.expects(:stacks).never

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Running this against current code fails (the status IS created on `victim_commit` despite the payload naming an unrelated repository), proving the cross-repository mutation. After applying the recommended fix (scoping via `stacks`), the assertion passes.
