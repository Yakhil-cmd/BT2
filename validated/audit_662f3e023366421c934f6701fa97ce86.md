### Title
Cross-repository status/check injection bypasses commit-deployability gating - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `withdraw` bug lets a worker skip the required `deregister → wait lockPeriod` binding because `withdraw` checks `worker.deregisteredAt + lockPeriod()` without verifying `deregisteredAt` was ever set, so a zero/default value trivially satisfies the check. The same class of bug — a security-relevant check operating on a field/scope that isn't actually bound to the authenticated principal — exists in Shipit's webhook handling: signature verification authenticates an *organization* (derived from the payload's `repository.owner.login`), but the handler that mutates commit CI state (`StatusHandler`) does not scope its writes to that repository/stack at all.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App/secret for the organization named in the payload and verifies the HMAC signature over the raw body: [1](#0-0) [2](#0-1) 

This authenticates "this payload really came from a webhook configured for organization X." However, `StatusHandler#process` — the handler invoked for `status` events — updates commit CI state purely by commit SHA, with no repository/organization scoping whatsoever: [3](#0-2) 

The base `Handler` class does define a `stacks`/`repository_name` helper that scopes work to the repository named in the payload [4](#0-3) , but `StatusHandler` does not use it — it queries `Commit.where(sha: params.sha)` across **all** stacks/repositories in the Shipit instance and calls `commit.create_status_from_github!(params)` on every match.

This breaks the intended binding: **organization authenticated (via webhook secret tied to `repository.owner.login`) ≠ repository/stack actually written (any stack containing a commit with a matching SHA)**. An attacker who legitimately controls a webhook for *any* one organization/repo configured in the Shipit instance (i.e., can produce a validly-signed `status` payload for their own org) can set `sha` to a commit hash belonging to a completely different stack/repository, and inject an arbitrary CI status (e.g., `state: "success"`, arbitrary `context`) for that unrelated commit.

### Impact Explanation
Commit status directly gates whether a commit is considered deployable and whether continuous delivery proceeds: [5](#0-4)  (`should_delay_continuous_delivery?` checks CI/statuses) [6](#0-5)  (`deployable?` depends on `deployment_checks_passed?`, which for CI/status-based gating derives from commit state)

Test evidence shows required/blocking statuses are what make a commit `deployable?`: [7](#0-6) . By forging a "success" status for a commit in a target stack (using a validly-signed webhook from an unrelated, attacker-controlled organization/repo), the attacker can flip a commit from non-deployable/pending to deployable, triggering an unauthorized deploy through continuous delivery, or unblocking a manual deploy that a legitimate reviewer/CI would otherwise have prevented. This is a cross-repository write of security-relevant state (CI status) that results in an unauthorized deploy — matching the "cross-repository writes" / "unauthorized deploy" impact criteria.

### Likelihood Explanation
Medium. It requires the attacker to already have webhook access to at least one repository/organization configured on the same Shipit instance (i.e., they can get GitHub to deliver, or replay, a signed `status` webhook for a repo they control) and to know the target commit's SHA (which is often public, e.g. for public repos or repos where SHAs leak via PRs/other statuses). No access to the target repo's webhook secret, GitHub App credentials, or a Shipit session/API token is needed — only a validly-signed payload for a repo the attacker legitimately controls.

### Recommendation
Scope `StatusHandler` (and any other handler that trusts payload-level identifiers like `sha`) to the repository named in the payload, consistent with the base `Handler#stacks`/`repository_name` helper, e.g. restrict `Commit.where(sha: params.sha)` to `commit.stack.repository == Repository.from_github_repo_name(repository_name)` before calling `create_status_from_github!`.

### Proof of Concept
1. Configure Shipit with two organizations/repos: `org-a/repo-a` (attacker-controlled, webhook secret known/derivable by attacker because they own that repo's GitHub App/webhook config) and `org-b/repo-b` (victim stack with a commit `pending`/blocking a deploy).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha in org-b/repo-b>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/repo-a"}
}
```
3. Sign it with `org-a`'s webhook secret and POST to `/github/webhooks`. `verify_signature` passes because it only checks the signature against `org-a`'s secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit in `org-b/repo-b` (unrelated to `org-a`), and creates a `success` status on it — even though the request was never authorized by `org-b`.
5. If `org-b/repo-b`'s stack has continuous delivery enabled and this was the last blocking check, an unauthorized deploy is triggered.
