### Title
Silent 8000-char diff truncation in `build_refute_prompt` lets attacker-controlled padding cause false "PRE-EXISTING" refutation of genuine findings - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_refute_prompt` truncates the diff text embedded in the self-refute prompt to the first 8000 characters with no truncation marker, while the same prompt instructs the model to REFUTE any finding as "PRE-EXISTING" if the cited vulnerable code "does NOT appear on any + line in the DIFF block above." An attacker who controls diff size/ordering (e.g., padding earlier files/hunks) can push their malicious `+` line past byte 8000, causing the refute stage to wrongly conclude the vulnerability is pre-existing context and REFUTE it.

### Finding Description
`build_refute_prompt` builds the adversarial-verification prompt and slices the diff with a hard, silent cutoff: [1](#0-0) 

Unlike `cap_diff_for_prompt`, which is used for the investigate stage and explicitly injects `"... [truncated by security-guidance: ...]"` markers whenever it caps per-file (80,000 bytes) or total (400,000 bytes) content so the model knows data is missing: [2](#0-1) 

`diff_text[:8000]` in `build_refute_prompt` performs no such marking — the model has no signal that the diff shown to it in the refute stage is a small prefix of a possibly much larger (up to 400,000-byte) diff that was already sent to the investigate stage.

The refute system prompt's explicit `PRE-EXISTING` criterion directly keys off this truncated text: [3](#0-2) 

If the vulnerable `+` line sits past the 8000-character mark, it will genuinely be absent from the "DIFF block above," satisfying the literal wording of the `PRE-EXISTING` rule even though the line is a newly added change — not pre-existing context. Because this is a positive rule match (not merely absent evidence), it can override the general "Default = SURVIVES" instruction: [4](#0-3)  and [5](#0-4) .

An attacker controlling the diff (via file naming/ordering or padding content in earlier hunks/files within the same commit/PR) can deterministically place their vulnerable `+` line beyond offset 8000, since diff assembly order is attacker-influenceable through file/hunk placement in the commit being reviewed.

### Impact Explanation
This allows a genuine `in_diff` or `off_diff` security finding (e.g., a real injection, SSRF, or auth bypass introduced by the diff) to be marked `refuted` by the self-refute stage purely due to attacker-controlled truncation, not because the finding is actually invalid. Per the plugin's design, refuted findings are dropped and do not trigger the Stop/commit-review block enforced by `handle_commit_review_posttooluse`, so a real vulnerability silently passes review with no warning shown to the user — a trust-boundary bypass of the security review gate itself.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to control the size/ordering of the diff submitted in the reviewed commit/PR (e.g., via file naming to control diff ordering, or padding an earlier file/hunk with benign content), which is well within an unprivileged contributor's control. No special privileges, exploits, or leaked credentials are required — only diff size ≥ ~8KB with the vulnerable line placed after that offset, which is a routine size for realistic commits.

### Recommendation
- Do not silently truncate the refute-stage diff at a small fixed size; either send the same capped diff used for investigate (with truncation markers, consistent with `cap_diff_for_prompt`) or scope the refute diff per-candidate (only the relevant file's diff, uncapped or capped at the same per-file limit).
- If truncation is necessary, insert an explicit `"[... diff truncated ...]"` marker so the model cannot assume "absent from what I see" means "absent from the diff."
- Change the `PRE-EXISTING` criterion to require reading the actual current file content (via the model's Read/Grep tools) and comparing to a full, untruncated diff rather than relying on the prompt-embedded, size-limited `DIFF:` block.

### Proof of Concept
Unit test plan for `build_refute_prompt`:
```python
def test_build_refute_prompt_truncates_evidence_silently():
    padding = "// benign\n" * 900  # >8000 chars of filler
    vulnerable_line = "+os.system(user_input)  # injected sink"
    diff_text = padding + "\n" + vulnerable_line
    assert len(padding) > 8000  # confirm padding alone exceeds cutoff

    candidates = [{"idx": 0, "vulnerableCode": "os.system(user_input)",
                   "_diff_anchor": "in_diff"}]
    prompt = review_api.build_refute_prompt(candidates, diff_text)

    # The vulnerable + line is truncated out of the prompt's DIFF block.
    assert vulnerable_line not in prompt
    # No truncation marker is present, unlike cap_diff_for_prompt's markers.
    assert "truncated" not in prompt.lower()
```
This proves the vulnerable line is invisible to the refute-stage prompt with no indication of truncation, which — combined with the `PRE-EXISTING` rule text checked in `AGENTIC_REFUTE_SYSTEM`/`build_refute_prompt` — supports the model concluding "does NOT appear on any + line in the DIFF block above" and refuting a genuine finding. An integration-level test would additionally assert that `handle_commit_review_posttooluse`/`agentic_review` callers treat this refutation as final (no fallback re-check against the untruncated diff), confirming the bypass reaches the enforcement gate.
