### Title
Unfiltered pull-request label names inject arbitrary environment variables (e.g. `LD_LIBRARY_PATH`) into review-stack task/deploy `steps` commands - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and `TaskCommands#env`/`DeployCommands#env` merge `@stack.env` unfiltered before building `Command` objects for `tasks.<name>.steps` and `deploy_steps`. Because that merged hash is passed straight to `Command#unbundled_env` and then `PTY.spawn`, a PR label literally named `ld_library_path` becomes `LD_LIBRARY_PATH=true` in the spawned process's environment, unlike the API-triggered `env` parameter (`deploy_params`/`task_params`) which is explicitly filtered through `EnvironmentVariables#permit`/deploy/task `variables` allowlists.

### Finding Description
The broken binding: the code assumes `stack.env keys ⊆ declared deploy/task variable names`, i.e. every key that reaches `Command#env` should have passed through `EnvironmentVariables#permit(variable_definitions)` as it does for the controller-supplied `env` params (`app/controllers/shipit/deploys_controller.rb:67`, `app/controllers/shipit/tasks_controller.rb:81`, enforced by `Shipit::EnvironmentVariables#sanitize_env_vars` at `lib/shipit/environment_variables.rb:35-44`). In reality:

- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |n, h| h[n.upcase] = "true" })
```
with no key allowlist at all — any label name becomes an arbitrary env key.
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` verbatim from the webhook JSON body, with no validation restricting the label's name/charset (confirmed there is no such validator/format check reachable in `PullRequest`).
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env)` — this is the unfiltered `ReviewStack#env`, merged directly into the environment used to build every `Command.new(command_line, env:, chdir: ...)` for `tasks.<name>.steps` (`TaskCommands#perform`, line 24-27) and for `deploy_steps` (`DeployCommands#steps`, line 5-7). No call to `EnvironmentVariables.with(env).permit(...)` occurs on this merged env before it reaches `Command`.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, and `Command#start` (`lib/shipit/command.rb:85-101`) passes this straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`.

Exploit flow: attacker opens/owns a PR against a repository configured with `review_stacks_enabled` and `provisioning_behavior: allow_all` (so a `ReviewStack` is auto-created/provisioned for any PR with no maintainer approval, per `LabeledHandler`/`ReviewStackAdapter` tests showing `allow_all` bypasses label gating). Attacker applies a label named `ld_library_path` (or any case) to their own PR. GitHub's `pull_request` `labeled` webhook fires; `LabelCapturingHandler` persists the label onto `stack.pull_request.labels`. On the next task or deploy run for that review stack (continuous deployment, a triggered task, or the auto-provisioning task), `TaskCommands#env`/`DeployCommands#env` merges `stack.env["LD_LIBRARY_PATH"] = "true"` into the process environment for every command in `tasks.<name>.steps`/deploy steps, redirecting dynamic linking for any dynamically-linked binary invoked by those steps (attacker only needs to also plant a malicious shared library reachable at that path from within their own fork checkout, e.g. via `deploy.override`/`ci.override`, if the value can be templated — although here the value is fixed to `"true"`, showing the underlying issue is that *any* label name, not just `LD_LIBRARY_PATH`, is accepted unfiltered, so any sensitive variable name like `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, etc. can be forced to a fixed benign-looking value by the attacker with no allowlist check).

Why existing guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the webhook truly comes from GitHub — they do not restrict what label names GitHub allows a webhook to report. `EnvironmentVariables#permit` is applied only to the explicit `env` params passed through `deploys_controller.rb`/`tasks_controller.rb`; it is never applied to `stack.env`/`ReviewStack#env`, which is merged directly in `TaskCommands#env`/`StackCommands#env`. No `Stack`/`PullRequest` model validation constrains label name characters. This is confirmed directly by the existing repo tests `test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/deploy_commands_test.rb`, and `test/lib/shipit/task_commands_test.rb`, which assert `stack.env["WIP"]` / `stack.env["BUG"]` are set to `"true"` straight from arbitrary label strings — i.e., the codebase's own test suite documents that any uppercased label name becomes an environment key with no filtering.

### Impact Explanation
Any environment variable name (not limited to `LD_LIBRARY_PATH`, but including it) reaches the process environment of every `Command` spawned for `tasks.<name>.steps` and deploy/rollback steps on a review stack, for any repository with `provisioning_behavior: allow_all`. Since `Command#start` uses `PTY.spawn`, this is a Critical-class primitive: forcing `LD_LIBRARY_PATH` (or `GIT_SSH_COMMAND`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) into the deploy host's spawned process environment is a well-known vector to hijack dynamic linking / interpreter behavior of any binary invoked by the deploy steps, leading to Remote Code Execution on the Shipit deploy host. It is repeatable against any repository configured with `allow_all` review stacks, by any user able to open a PR and apply a label to it, and does not require any Shipit credentials, API token, or GitHub team membership.

### Likelihood Explanation
Requires: (1) the target repository has `review_stacks_enabled` with `provisioning_behavior: allow_all` (an operator/repo-owner configuration choice, not attacker-controlled, but explicitly named as the vulnerable configuration in this question), (2) the attacker can open a PR and add a label to it. Per this audit's stated threat model, "any GitHub user who can... label their own PR" is treated as an unprivileged capability. Cost to the attacker is a single webhook-triggering GitHub action (labeling a PR); the vulnerability is deterministic and repeatable on every subsequent task/deploy run against that stack.

### Recommendation
Filter `ReviewStack#env`'s label-derived keys through an explicit allowlist (e.g., only keys already declared in `deploy_variables`/task `variables`, or a fixed, non-overridable prefix like `LABEL_<name>`) before merging into `super`. Additionally, apply `EnvironmentVariables.with(stack.env).permit(...)` (or an equivalent denylist of sensitive variable names such as `LD_LIBRARY_PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, `PATH`) at the point where `TaskCommands#env`/`DeployCommands#env` merge `@stack.env`, so PR-label-derived keys can never override host-security-sensitive environment variables regardless of `provisioning_behavior`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_injection_test.rb
require "test_helper"

module Shipit
  class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
    test "[allow_all] PR label name injects LD_LIBRARY_PATH into tasks.<name>.steps env reaching Command" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["ld_library_path"]

      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env

      # Binding under test: stack.env keys must be a subset of declared task variable names.
      allowed_keys = task.definition.variables.map(&:name)
      assert_not_includes allowed_keys, "LD_LIBRARY_PATH"
      assert_equal "true", env["LD_LIBRARY_PATH"], "attacker-controlled label leaked into task env"

      command = Shipit::Command.new("true", env:, chdir: Dir.tmpdir)
      assert_equal "true", command.unbundled_env["LD_LIBRARY_PATH"],
                   "LD_LIBRARY_PATH reaches the process env passed to PTY.spawn"
    end
  end
end
```
This demonstrates the equality `allowed_keys ⊇ env.keys` is false — `LD_LIBRARY_PATH` reaches `Command#unbundled_env` (and thus `PTY.spawn`) purely from a pull request label name, with no allowlist enforced anywhere in the `ReviewStack#env` → `TaskCommands#env`/`DeployCommands#env` → `Command#start` path.
