### Title
Attacker-crafted swap route resolves arbitrary external contracts under the caller's authorization tree, draining wallet tokens beyond the routed amount - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
CVE-2018-1000837 is an XXE vulnerability: a parser resolves attacker-chosen *external entities* embedded in a trusted input document, reaching resources outside the intended scope. The analog in XOXNO Lending is the strategy swap path: the caller submits `swap: Bytes` — an opaque route payload parsed by the unallowlisted router — and every venue, hop pool, and token address named inside it acts as an "external entity" that is resolved and invoked on the call stack *below the caller's `require_auth`*. A malicious route can name an attacker-deployed "hop pool" contract whose `swap` performs `token.transfer(caller, attacker, x)` on any token in the caller's wallet. In Soroban recording mode that transfer is attached as a child of the caller's `swap_collateral` (or sibling strategy) authorization entry; if the caller signs the tree, it executes and steals funds completely unrelated to the swap.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` is reached from the unprivileged entrypoints `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. It calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is caller-supplied XDR bytes (line 37). The controller protects only *its own* funds: it grants the router one exact `token_in.transfer(controller, router, amount_in)` invocation via `authorize_transfer_as_current` (line 34), then rejects input growth, overspend, and non-positive output (lines 40–54). Nothing constrains what the route's external entities do to the *caller*.

The router keeps no allowlist of venues or tokens; route bytes name arbitrary pool and token addresses, which are invoked below `sender.require_auth()` in the router. Under Soroban's authorization model, any `require_auth`-protected call a hop contract makes on the caller's address is recorded as a sub-invocation of the caller's controller auth entry. Simulation presents a single innocent-looking root (`swap_collateral`) with hidden children; a wallet or user that signs it authorizes the theft.

This is proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed (line 69), recording mode attaches it under Alice's `swap_collateral` entry (lines 214–222), and the assertion shows Alice's wallet balance of `77_770_000_000` drained to zero while the swap itself settles fairly and passes every controller check (lines 224–226). The threat model acknowledges the router "keeps no allowlist" and that "neither the payload minimum nor the final risk gate bounds" the loss (`docs/explanation/threat-model.md` lines 154–164), but the reachable state is still produced entirely by an in-scope unprivileged entrypoint and attacker-controlled route data — no privileged role, leaked key, or off-chain failure is required.

### Impact Explanation
Theft of user funds. The stolen amount is unbounded by `amount_in`, slippage parameters, or the final account health check — it is the caller's entire balance of any token the attacker names. Any user of `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral` who is served a malicious route (e.g., by a compromised or hostile frontend/route builder) signs one authorization and loses unrelated wallet assets in the same transaction.

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree containing the malicious child invocation. Because Soroban simulation produces the tree and most clients display only the root invocation, a route-assembling front-end or malicious counterparty can plausibly get it signed — this is the standard phishing-adjacent route-injection pattern and is precisely what the repository's own harness demonstrates end-to-end. The attacker needs no protocol privilege and only a deployed hop contract. Likelihood is gated by user signing hygiene rather than by any protocol control, which is why severity is bounded at High rather than Critical: it is opportunistic theft of wallet funds, not pool insolvency.

### Recommendation
Constrain the external-entity surface the way XXE fixes constrain entity resolution:
- Require the router to enforce a governance-maintained venue allowlist so route bytes can only resolve to approved pool/token contracts, or have the controller reject routes decoded outside the router.
- Alternatively/additionally, have the controller compute and publish the expected authorization shape (one input-transfer child) and make clients fail on any extra sub-invocation; the threat model already prescribes this client-side, so enforcing venue restrictions on-chain removes reliance on it.

### Proof of Concept
The repository contains a working PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Deploy `RogueHopPool` with `PLAN = (alice, wallet_token, attacker, WALLET_BALANCE)` where `wallet_token` is any token Alice holds (77,770 units of an unlisted token in the test).
2. Attacker supplies a `swap` route through the `UnlistedPoolRouter` naming `hop_pool = RogueHopPool`. The router executes `sender.require_auth()`, pulls `token_in` from the caller per the controller's authorized transfer, invokes `hop_pool.swap()`, and pays a fair `min_out`.
3. Alice calls `swap_collateral` with that route. Inside the hop, `RogueHopPool::swap` executes `token::Client::new(wallet_token).transfer(alice, attacker, WALLET_BALANCE)`.
4. Recording mode produces exactly one auth entry rooted at `controller.swap_collateral` whose only sub-invocation is the wallet theft. If Alice signs it, enforcing mode executes: `assert_eq!(s.wallet(&s.alice), 0)` and `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)`, while the swap output itself is credited normally (`s.supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH`) — every controller check (overspend, output positivity, final risk) passes.
