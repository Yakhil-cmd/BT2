## Analysis: Signature verified against one field, action performed using another

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` (and `StatusHandler` on no repository at all) — cross-organization/cross-repository forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController` is a public, unauthenticated endpoint (`ActionController::Base`, not `Shipit::Authentication`) whose only protection is an HMAC signature check. [1](#0-0)  The org whose secret is used to verify that signature is picked from `params.dig('repository','owner','login')` (or `organization.login`), a field inside the same attacker-supplied JSON body. [2](#0-1) [3](#0-2)  The event handlers that then execute, however, resolve the target repository/stack from a *different* field of the same body, `repository.full_name`, via `Handler#repository_name`. [4](#0-3)  Nothing ties `repository.owner.login` (used to select the signing secret) to `repository.full_name` (used to select what gets mutated). `StatusHandler` goes further and does not scope by repository at all, matching purely on commit SHA across the entire installation. [5](#0-4) 

### Finding Description
- `WebhooksController#verify_signature` builds a `github_app` for `repository_owner` and checks `X-Hub-Signature` against that org's `webhook_secret`: [6](#0-5) 
- `repository_owner` is read straight from the JSON payload, with a fallback to `organization.login`: [3](#0-2) 
- `GithubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no `webhook_secret` configured: [7](#0-6) 
- Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers: [8](#0-7) 
- The base `Handler` resolves the affected repository/stacks from `payload.dig('repository', 'full_name')`, a field independent from the one used for signature-org selection: [4](#0-3) 
- `PushHandler`, `pull_request/*Handler` (opened/closed/labeled/reopened/edited/label_capturing) all derive the target `Repository` the same way, from `params.repository.full_name`, e.g.: [9](#0-8) [10](#0-9) 
- `StatusHandler` doesn't even use a repository field — it matches by commit SHA globally: [5](#0-4) 

Because a real Shipit deployment configures multiple independent GitHub Apps/organizations (see `config/secrets.development.shopify.yml` listing `somegithuborg`/`someothergithuborg`, each with its own `webhook_secret`) [11](#0-10) , the "organization whose secret authenticated the request" and "the repository/stack that the handler mutates" are two independently attacker-controlled JSON fields inside one request body. An attacker who can produce a valid signature for *any one* configured organization (e.g. one they administer themselves, or one whose `webhook_secret` is blank/misconfigured, which trivially passes verification) can set `repository.owner.login` to that organization while setting `repository.full_name` to point at a stack belonging to a completely different, victim organization also hosted on the same Shipit instance.

### Impact Explanation
This breaks the binding "organization authenticated == repository written." Concretely, with a signature that only proves knowledge of org A's secret, an attacker can:
- Force-sync/trigger deploy pipelines on any stack for any tracked repository (`PushHandler#process` calls `stack.sync_github`) [10](#0-9) .
- Archive/unarchive arbitrary review stacks belonging to any other organization's repository via the `pull_request` handlers [12](#0-11) .
- Forge arbitrary commit statuses for any commit in the entire installation, regardless of repository/org, via `StatusHandler`, since it performs no repository scoping at all [5](#0-4) . Since commit status/deployable status commonly gates merges and deploy eligibility elsewhere in the engine, this can lead to an unauthorized deploy/merge decision being made on falsified CI state.

This satisfies the "High/Critical" bar: escalation across a repository/organization trust boundary leading to unauthorized state changes (stack archival/unarchival, forced sync, forged deploy-readiness signals) on repositories the attacker has no legitimate access to.

### Likelihood Explanation
Requires only:
1. The Shipit instance is multi-tenant (more than one GitHub organization configured) — a documented, supported configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`).
2. The attacker knows (or can trivially satisfy) the `webhook_secret` for *any one* of the configured organizations — including the degenerate case where an org has no secret set, in which case `verify_webhook_signature` returns `true` for any signature value [13](#0-12) .
3. No session, GitHub App private key, or repository write access to the *victim* org/repo is needed — `/webhooks` is unauthenticated (`ActionController::Base`, no `Shipit::Authentication`) [1](#0-0)  and reachable at `POST /webhooks` per the route config [14](#0-13) .

This is a low-effort attack once one org's secret (or lack of secret) is known, entirely bypassing the intended per-organization isolation.

### Recommendation
- Bind the verified signature to the *exact* organization that the handler will act on: derive the acting-organization from the same field used for verification, and reject/short-circuit if `repository.full_name`'s owner segment does not match `repository_owner` used in `verify_signature`.
- Have every handler (in particular `StatusHandler`) validate that the target `Commit`/`Repository`/`Stack` belongs to the organization whose secret produced a valid signature, not merely match by SHA or by an independently-controlled `full_name` string.
- Disallow (or loudly warn/refuse to boot in production) organizations configured with a blank `webhook_secret`, since `verify_webhook_signature` treats that as "always valid."

### Proof of Concept
1. Shipit is configured with two orgs: `orgA` (attacker-controlled GitHub App, secret `sA`, known to attacker) and `orgB` (victim org, with tracked repository `orgB/prod-app` and stacks in Shipit).
2. Attacker crafts a `push` (or `pull_request`) webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/prod-app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(sA, body)` using `orgA`'s known secret.
4. `POST /webhooks` with `X-Github-Event: push` and that signature.
5. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, fetches `Shipit.github(organization: "orgA")`, and successfully verifies the signature against `sA` [2](#0-1) .
6. `PushHandler#process` is invoked with the full payload and resolves `stacks` from `repository.full_name == "orgB/prod-app"` [4](#0-3) , triggering `stack.sync_github` on the victim org's stack — despite the signature only proving control of `orgA`.

Note: this analysis is based on the code available through the index; some request/response wiring details (e.g. exact `GithubSyncJob` downstream effects) were not independently traced in this session, so consider validating the full downstream blast radius (deploy triggering vs. sync-only) in a live/test environment before treating exploitability as fully confirmed end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
