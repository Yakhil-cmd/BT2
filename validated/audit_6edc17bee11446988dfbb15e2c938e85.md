### Title
`with_locked_state` fail-open on `OSError`/`IOError` disables Stop-hook and commit-review rate limits under attacker-induced resource exhaustion - ([File: plugins/security-guidance/hooks/session_state.py])

### Summary
`with_locked_state` in `plugins/security-guidance/hooks/session_state.py` catches `(OSError, IOError)` around the lock-acquire/load/callback/save sequence and returns `None` instead of propagating the failure or a safe "deny" sentinel. [1](#0-0)  Because this is the sole enforcement primitive backing the `atomic_check_counter`/`atomic_check_rate_limit`/`atomic_check_and_mark_warning` helpers in `security_reminder_hook.py`, any condition that makes `os.makedirs`, `os.open`, or `fcntl.flock` on the per-session lock file raise (disk full, out of inodes/fds, permission-denied state dir) collapses the rate-limiting layer to a `None` return.

### Finding Description
`with_locked_state(session_id, callback)` wraps `os.open(lock_file, ...)`, `fcntl.flock`, `load_state`, the caller-supplied `callback`, and `save_state` in a single `try/except (OSError, IOError)` block that on failure just logs via `debug_log` and returns `None`: [1](#0-0) . This is consistent with the broader fail-open posture of this module — `load_state` swallows `(json.JSONDecodeError, IOError, KeyError, TypeError)` and returns an empty default state [2](#0-1) , and `save_state` silently logs and drops `(IOError, OSError)` [3](#0-2) .

The module's own docstring confirms that `atomic_check_counter`, `atomic_check_rate_limit`, and `atomic_check_and_mark_warning` are built directly on top of `with_locked_state` and live in `security_reminder_hook.py`: [4](#0-3) , and `security_reminder_hook.py` imports `with_locked_state` for exactly this purpose [5](#0-4) .

An unprivileged attacker whose repository content is checked out and built/generated locally (e.g., a build step or generated file tree that fills the `~/.claude/security` filesystem, exhausts inodes, or hits the process fd ulimit) can force `os.makedirs`/`os.open`/`fcntl.flock` on the session's lock file to raise `OSError`. Every subsequent `with_locked_state` call then returns `None` instead of executing the counter/rate-limit callback.

### Impact Explanation
**I was not able to directly view the bodies of `atomic_check_counter`, `atomic_check_rate_limit`, and `atomic_check_and_mark_warning` in this session** (ran out of tool-call budget before reading past line 120 of `security_reminder_hook.py`), so I cannot cite the exact line where `None` from `with_locked_state` is coerced to an "allowed"/`True` return. What is concretely confirmed is: (1) `with_locked_state` returns bare `None` on any `OSError`/`IOError` during lock/load/save, and (2) the module design throughout `session_state.py` consistently treats storage/lock failures as "proceed with defaults" rather than "deny," which is the pattern the question's hypothesis depends on. If the downstream `atomic_check_*` wrappers follow this same fail-open convention (as their naming and the file's docstring strongly suggest they're designed to), then a resource-exhaustion condition would cause `MAX_STOP_HOOK_FIRINGS` and `MAX_COMMIT_REVIEWS_PER_HOUR` counters to never increment or never block, allowing unbounded Stop-hook LLM review calls and commit-review LLM calls. This would translate into unbounded ANTHROPIC_API_KEY-backed API spend/DoS-via-cost and defeat of a security control, but does not directly bypass approvals or achieve command execution beyond what's already reachable.

### Likelihood Explanation
Requires the attacker to control repository content that can exhaust disk/inode/fd resources under `~/.claude/security` on the victim's machine (e.g., via a build script executed as part of normal automation) — this is a plausible but non-trivial precondition, and success depends on OS-level resource limits being crossed at the right moment relative to the lock/state directory. **This part is not independently confirmed by the code I reviewed**, since I could not verify the downstream `atomic_check_*` implementations before the session ended.

### Recommendation
Have `with_locked_state` distinguish "lock/storage failure" from "successful check" by returning a distinct sentinel (not `None`) and have every `atomic_check_*` caller treat that sentinel as **deny** (fail-closed) rather than defaulting to "proceed," particularly for the Stop-hook firing counter and commit-review rate limiter, which are the plugin's cost/DoS guardrails.

def load_state(session_id):
    """Load the full state dict from file."""
    state_file = get_state_file(session_id)
    try:
        with open(state_file, "r") as f:
            data = json.load(f)
            if isinstance(data, list):
                return {"shown_warnings": data}
            if isinstance(data, dict):
                data.setdefault("shown_warnings", [])
                return data
    except (json.JSONDecodeError, IOError, KeyError, TypeError):
        pass
    return {"shown_warnings": []}

def save_state(session_id, state):
    """Save the full state dict to file."""
    state_file = get_state_file(session_id)
    try:
        state_dir = os.path.dirname(state_file)
        if state_dir:
            os.makedirs(state_dir, exist_ok=True)

        with open(state_file, "w") as f:
            json.dump(state, f)
    except (IOError, OSError) as e:
        debug_log(f"Failed to save state file {state_file}: {e}")
