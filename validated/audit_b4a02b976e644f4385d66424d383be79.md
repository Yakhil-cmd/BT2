### Title
Cross-organization forged commit status via unscoped `StatusHandler` breaks the webhook-org-to-repository binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a signature against based on the organization embedded in the webhook payload itself (`repository.owner.login` or `organization.login`), then authorizes the request only for that organization's secret. `StatusHandler`, however, applies the event's effects (`Commit.where(sha: params.sha)`) with no scoping back to that organization/repository, breaking the binding between "the organization whose signature was verified" and "the repository whose data actually gets written."

### Finding Description
The webhook signature check picks the org-specific `github_app` purely from payload content: [1](#0-0) [2](#0-1) 

This means the HMAC only proves the payload was signed by *some* organization's configured webhook secret — specifically the one named in the payload — a legitimate binding as long as everything the handler does is scoped to that same organization/repository.

Most handlers respect that scoping through the base `Handler#stacks` helper, which filters by `repository.full_name`: [3](#0-2) 
e.g. `CheckSuiteHandler` uses `stacks.where(branch: ...)` before touching any commit: [4](#0-3) 

`StatusHandler` does not. Its parameter contract requires only `sha`/`state`/etc. — no repository — and it resolves the target purely by SHA across the *entire* `Commit` table, with no relation to the organization whose signature validated the request: [5](#0-4) 

Shipit explicitly supports multiple independently-configured GitHub organizations sharing one instance (each with its own `webhook_secret`), as shown in the double-app fixture: [6](#0-5) 

So the equality that should hold is:
`organization whose webhook_secret verified the signature == organization owning the repository/commit the handler mutates`

For every handler except `StatusHandler` this holds (enforced via `stacks`/`repository_name` scoping). For `StatusHandler` it does not: any organization `B` with a valid webhook installation can sign a `status` event and set `sha` to a commit that belongs to a stack under organization `A`, and `Commit.where(sha: params.sha)` will happily apply it.

Applying a forged status is not inert — `create_status_from_github!` drives real state transitions: [7](#0-6) [8](#0-7) 

and the same `Status` records feed the merge-queue's CI gate: [9](#0-8) 

### Impact Explanation
An attacker who controls (or has legitimately installed the app on) any single GitHub organization configured in a multi-org Shipit instance can forge a `success`/`pending` status for a commit SHA belonging to a completely unrelated organization's repository/stack, without ever holding credentials, webhook secret, or write access for that target repository. Because forged `Status` rows are what `MergeRequest#all_status_checks_passed?` and continuous-delivery scheduling consult, this can push a target repository's merge queue toward `merge!` or trigger continuous delivery for a commit that never actually passed CI — an unauthorized merge/deploy trigger driven entirely by data from an unrelated, unprivileged organization's signed webhook.

### Likelihood Explanation
Requires only that the Shipit instance be configured for more than one GitHub organization (a documented, supported configuration) and that the attacker knows/controls a repository in one of those organizations plus the target commit's SHA (which is not secret — it's visible via GitHub UI/API/PRs for any repo the attacker can view, and via any GitHub App with read access on the org). No privileged Shipit account, `ApiClient` token, or `webhook_secret` for the *target* organization is needed — only a valid webhook signed by the attacker's own (unprivileged) organization.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler`/`PushHandler` do: require and use `repository.full_name` (or `Handler#stacks`) to constrain the `Commit` lookup to the organization/repository whose webhook secret verified the request, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `attacker-org` and `victim-org` (as in `secrets_double_github_app.yml`), each with its own `webhook_secret`.
2. Attacker installs/owns the GitHub App on `attacker-org` and knows its `webhook_secret` (legitimately, e.g. they created the org's own Shipit integration).
3. Attacker finds the SHA of an undeployed commit on a `victim-org` stack (public commit SHA, or leaked via any read access).
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a payload `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim-commit-sha>", "state": "success", "context": "ci/required"}`, and `X-Hub-Signature` computed with `attacker-org`'s own webhook secret.
5. `verify_signature` selects `attacker-org`'s `github_app` (matches the payload's `repository.owner.login`) and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `victim-org` commit, creating a forged `success` status on it, which can advance that commit's merge/deploy eligibility.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
