### Title
Membership webhook grants Shipit.github_teams authorization without validating the signing org owns the target team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up teams globally by `github_id` alone and, for pre-existing rows, never checks that `params.organization.login` (the org whose `webhook_secret` signed the request) matches the `team.organization` already stored on that row. Since `User#authorized?` grants Shipit access based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, any org configured in Shipit's (single- or multi-org) webhook config can add an arbitrary member to any pre-existing `Team` record — including the exact `Team` rows backing `Shipit.github_teams` — as long as it can guess/observe that team's numeric `github_id`.

### Finding Description
The binding that should hold is: `team.organization == params.organization.login` for every `Membership` created by a `membership` webhook, i.e., only the org that actually owns a given GitHub team (as verified by that org's own `webhook_secret`) should be able to write into that `Team`'s roster. This binding is not enforced.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `repository_owner` from `params.dig('organization', 'login')` for membership events (no `repository` key present), fetches `Shipit.github(organization: repository_owner)`, and verifies the HMAC using **that org's own configured `webhook_secret`**. If the attacker controls/owns an org that is itself configured in Shipit's multi-org `secrets.yml` (a legitimate, self-owned tenant), they know their own `webhook_secret` and can produce a request that passes this check. The signature only proves "this JSON body was signed by org X's secret" — it says nothing about whether the JSON content (`team.id`, `member.login`) is truthful.
2. `MembershipHandler#process` calls `find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`):
   ```ruby
   Team.find_or_create_by!(github_id: params.team.id) do |team|
     team.github_team = params.team
     team.organization = params.organization.login
   end
   ```
   The block (which sets `organization`) only runs when the row is *created*. If a `Team` with that `github_id` already exists — e.g., a real team already tracked via `Shipit.github_teams`/`Team.find_or_create_by_handle` (`app/models/shipit/team.rb:18-27`) or created earlier by a legitimate `membership` webhook from the real owning org — `find_or_create_by!` simply returns the existing record, with its original `organization` untouched.
3. Back in `process`, regardless of whether the found team's `organization` matches `params.organization.login`, the code unconditionally executes `team.add_member(member)` for `action == 'added'`, and `member` is `User.find_or_create_by_login!(params.member.login)` — also attacker-controlled and unrelated to any real GitHub team membership.
4. `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants login access solely via `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. Since `Shipit.github_teams` team IDs correspond directly to `Team.github_id` values used above, successfully forging a `Membership` row for one of those `Team` records grants that attacker-chosen `member.login` full authenticated access to Shipit.

None of the existing guards close this gap: `verify_signature` authenticates the *sender org*, not the *semantic ownership* of the `team.id` in the payload; `ExplicitParameters` only validates types/presence, not cross-field ownership; there is no `require_permission!`/`stacks` scope check on webhook processing since webhooks are engine-wide, not per-repository.

### Impact Explanation
An attacker who legitimately controls one org registered in Shipit's multi-tenant GitHub App configuration (a scenario the engine explicitly supports via `docs/setup.md`'s "Using Multiple Github Applications") can escalate an arbitrary GitHub login into every `Team` tracked in `Shipit.github_teams` by replaying crafted `membership` "added" webhooks with guessed/known numeric `github_id` values for other orgs' teams, signed with their own valid secret. This matches the High severity category "escalation into `Shipit.github_teams` authorization" — the attacker (or any login they name) becomes an authorized Shipit user without belonging to the real gating GitHub team of the trusted org. This is repeatable across every configured team, in one attacker-owned-org account, per the proof idea in the question.

### Likelihood Explanation
Requires Shipit to be deployed with the multi-org webhook configuration (`github: <org>: webhook_secret: ...`) and the attacker to be an onboarded org in that configuration (i.e., the attacker's own GitHub organization has a Shipit-configured GitHub App, giving them their own valid `webhook_secret` — a normal, unprivileged tenant, not a Shipit operator). The attacker additionally needs the numeric `github_id` of the target `Team` row(s), which may be discoverable via GitHub's team APIs, prior webhook traffic, or Shipit's own DB/task list if any info leaks; this is a moderate but plausible barrier reducing likelihood somewhat, but the code path itself does not require any secret the attacker doesn't already legitimately hold for their own org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found team's `organization` matches `params.organization.login` before proceeding, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Team #{team.github_id} does not belong to organization #{params.organization.login}" unless team.organization == params.organization.login

  team
end
```
This restores the binding `team.organization == params.organization.login` on every membership mutation, for both `added` and `removed` actions.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot attach a member to a team owned by a different organization" do
  real_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  attacker_org = 'attacker-org' # configured in secrets with its own valid webhook_secret

  @request.headers['X-Github-Event'] = 'membership'
  post :create, body: {
    action: 'added',
    team: { id: real_team.github_id, name: real_team.name, slug: real_team.slug, url: real_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'mallory' }
  }.to_json, as: :json

  assert_response :ok # currently succeeds - vulnerability
  mallory = Shipit::User.find_by(login: 'mallory')
  assert_not real_team.members.include?(mallory), "attacker-org must not be able to add members to shopify's team"
end
```
Assert both sides of the binding: `real_team.organization` ('shopify') must equal the org that signed the request (`attacker_org`) before `Membership` is created — they don't, and yet the membership row is written, confirming the vulnerability. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
