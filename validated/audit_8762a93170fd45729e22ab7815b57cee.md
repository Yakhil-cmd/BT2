### Title
Webhook signature verification keyed on payload's `repository.owner.login`/`organization.login` allows cross-organization forgery of webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App / `webhook_secret` to use for HMAC verification based on an **unauthenticated field read out of the very payload being verified** (`repository.owner.login` or `organization.login`). In a multi-organization Shipit deployment, this creates a binding mismatch: *the organization whose secret authenticated the request* is not enforced to be *the organization/repository the payload subsequently causes Shipit to write to*.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves a **per-organization** `webhook_secret` from `github_app_config(organization)` [3](#0-2) . This is Shipit's supported multi-tenant configuration model (`TOP_LEVEL_GH_KEYS`, `github_organizations`), i.e. a single Shipit instance can serve several distinct GitHub organizations, each with its own App/secret.

Once `verify_signature` succeeds, `create` re-parses the *same* raw body and dispatches it to handlers keyed only by event type, with no re-validation that the organization used for signing matches the organization/repository the handler subsequently acts on: [4](#0-3) 

The handlers derive the actual target purely from other payload fields, e.g. `Handler#repository_name` / `Handler#stacks`: [5](#0-4) 

and `PushHandler#process` looks up stacks by that repository name and branch, then calls `stack.sync_github`: [6](#0-5) 

Nothing ties `repository_owner` (used to pick the verifying secret) to `repository.full_name`/`organization.login` actually consumed by the handler logic. Because the attacker fully controls the raw JSON body they submit directly to `POST /webhooks` (this endpoint is not restricted to GitHub's IP range and doesn't require the request to have originated from GitHub — it only requires a valid HMAC over the raw body), anyone who legitimately controls (or has captured) the `webhook_secret` for **one** configured organization in a multi-org Shipit instance can forge a signed payload whose `repository.owner.login`/`organization.login` field points at their own organization (satisfying signature verification) while its `repository.full_name` (or `team`/`organization` fields consumed by `MembershipHandler`) points at a **different** organization's repository/stack that they have no legitimate access to.

This breaks the intended binding:
```
organization that authenticated (repository_owner used for HMAC lookup)
   ==
organization/repository actually written (repository.full_name / team.organization used by handlers)
```
which the code never enforces as an equality.

### Impact Explanation
Concretely this permits an attacker who holds a valid webhook secret for organization A to:
- Force `PushHandler` to trigger `stack.sync_github(expected_head_sha:)` on any stack belonging to organization B's repositories, causing Shipit to fetch/record arbitrary commit SHAs and drive deploy pipelines for a repository the attacker doesn't control (`Handler#stacks`/`PushHandler#process`).
- Drive `MembershipHandler` to manipulate `Team`/`Membership` records for organization B's teams (Team lookup is keyed by `organization` string, e.g. `Team.find_or_create_by_handle`, `has_many :github_hooks, ... primary_key: :organization`) — potentially adding attacker-controlled GitHub logins into a `Team` that is used by `Shipit.github_teams` for authorization (`User#authorized?` checks `teams.where(id: Shipit.github_teams...)`), i.e. escalation into `Shipit.github_teams` authorization for a foreign organization.
- Trigger PR-based handlers (`opened`/`closed`/`labeled`) to archive/unarchive/create review stacks belonging to other organizations' repositories.

This matches the required High-impact bucket: "escalation into `Shipit.github_teams` authorization" and cross-organization writes to stack/task state, achieved purely by an attacker who is an unprivileged tenant relative to the victim organization but who legitimately possesses a webhook secret for some other configured organization.

### Likelihood Explanation
This is only exploitable on Shipit deployments configured for multiple GitHub organizations (the `github_organizations`/`TOP_LEVEL_GH_KEYS` multi-org schema is a first-class supported configuration, not an edge case) where the attacker controls or can obtain one organization's `webhook_secret` (e.g. because they are an admin of their own low-trust org onboarded into the same Shipit instance). No GitHub App private key, session, or `ApiClient` token is required — only knowledge of one configured webhook secret and the ability to POST directly to the public `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, re-derive and enforce that every organization/repository field the selected handler will act on (`repository.full_name`, `organization.login`, `team.organization`, etc.) belongs to the *same* organization that supplied the verified secret (`repository_owner`), rejecting the webhook otherwise. Alternatively, tie stack/team lookups to the authenticated organization context rather than trusting payload-supplied owner fields independently.

### Proof of Concept
Conceptual outline (requires knowledge of organization A's `webhook_secret`, configured in a multi-org Shipit instance also serving organization B):
1. Craft JSON body: `{"ref":"refs/heads/main","after":"<attacker sha>","repository":{"owner":{"login":"org-A"},"full_name":"org-B/victim-repo"}}`.
2. Compute `X-Hub-Signature: sha1=HMAC(webhook_secret_of_org_A, raw_body)`.
3. `POST /webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-A")` (from `repository.owner.login`) and verifies successfully against org A's secret.
5. `PushHandler#process` looks up `Repository.from_github_repo_name("org-B/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker sha>")` on org B's stack — a cross-organization write the attacker should never have been able to trigger.

Note: I could not retrieve the full body of `app/models/shipit/webhooks/handlers/membership_handler.rb` before running out of tool calls, so the membership/team-escalation portion of the impact is based on `Team`'s organization-keyed lookups (`app/models/shipit/team.rb`) rather than direct inspection of that handler's code; this should be verified in a follow-up review.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
