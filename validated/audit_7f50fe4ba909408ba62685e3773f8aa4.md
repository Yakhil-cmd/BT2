## Finding

### Title
Price/reserve manipulation of AA pools priced via `balance[asset]` through direct payments to the AA address before a trade trigger - (File: formula/evaluation.js, aa_composer.js)

### Summary
The Curve report shows that a price oracle can be moved simply by transferring tokens to the address whose balance the oracle reads (the `Controller`), bypassing the intended `check_lock` protections that only guard `controller_long`/`controller_short` calls. Ocore has the same class of primitive: the `balance[asset]` operator in the oscript formula evaluator returns the AA's raw, live token balance, and that balance can be inflated by *any* unprivileged unit poster simply by sending a payment to the AA address — independent of, and prior to, any trigger that uses the balance in a pricing formula.

### Finding Description
`balance[asset]`/`balance[address][asset]` is implemented by `readBalance()` in `evaluation.js`, which returns the AA's live balance straight from `objValidationState.assocBalances` (backed by the `aa_balances` table), with no distinction between coins that arrived as part of the current trigger, coins from a past legitimate trade, or coins from an arbitrary unrelated payment sent by a third party. [1](#0-0) 

Before an AA's oscript logic is even evaluated, `handleTrigger()`'s `updateInitialAABalances()` unconditionally folds every output sent to the AA address into its balance: [2](#0-1) 

This means any address (an unprivileged unit poster) can send a plain payment to an AA address — with data that doesn't even need to match any `if` case that changes state, e.g. a "silently accept coins" branch or simply an amount that satisfies an "invest"/deposit case — and the AA's `balance[...]` for that asset increases immediately once the unit stabilizes. Any subsequent trigger that computes a price/invariant from `balance[...]` (rather than from an internal state variable that is only updated by matched trades) will use this attacker-inflated balance.

The bundled AMM reference implementation in the same repository demonstrates exactly this pattern: its exchange price is derived directly from `balance[$asset]`/`balance[base]`, not from a reserve state var incremented only on trades: [3](#0-2) 

An attacker can post a plain "donation" output to the AA address, then immediately trigger the swap case; the constant-product invariant `$p = $asset_balance * $bytes_balance` is recomputed off the manipulated balance, letting the attacker extract more from the pool (or set up follow-on trades) than the true reserves justify — the direct oscript analog of manipulating `amm_short.price_oracle()` by transferring tokens straight to `controller_long`.

### Impact Explanation
Any AA that prices trades, collateral, or payouts from `balance[...]` (a common, encouraged pattern per ocore's own sample AAs) inherits a manipulable "oracle": an attacker can shift the effective price/exchange-rate by donating funds directly to the AA address immediately before executing a trade, extracting value from other liquidity providers/traders or draining the pool disproportionately. This is a fund-loss vector for any lending/AMM/vault-style AA built on this idiom, not merely a resource-exhaustion or no-impact issue.

### Likelihood Explanation
The attack requires only posting two ordinary units (a payment plus a trigger) from an unprivileged address — no special permissions, no signature bypass, no reliance on malicious nodes/hubs. Because DAG units from the same author can be chained deterministically before other participants can react, the manipulation and profitable trigger can be composed by a single actor in short order, making this readily reachable and repeatable against any AA using this pricing idiom.

### Recommendation
AA authors should avoid pricing exclusively from `balance[...]`, or the ocore reference examples/documentation should be updated to warn against it; sensitive pricing formulas should instead track reserves through internal state variables (`var[...]`) that are only mutated by validated trade messages, mirroring the recommendation in the original report to use a "more stable" (i.e., non-directly-donatable) source for price computation. Time-weighted or externally-attested `data_feed[...]` values are a safer alternative to raw live balances for price-sensitive logic.

### Proof of Concept
1. Deploy (or use) an AA such as `test/samples/uniswap_like_market_maker.oscript`, whose swap price is computed from `balance[$asset]` / `balance[base]` at trigger time.
2. Attacker unit A: send a plain payment of asset tokens directly to the AA address (no matching "invest"/trade condition needed, or matching a benign accept-coins branch), inflating `balance[$asset]`.
3. Once unit A stabilizes, attacker unit B: trigger the "exchange bytes to asset" (or "asset to bytes") case; `$p = $asset_balance * $bytes_balance` is computed using the inflated balance from step 2, producing a `$amount` payout more favorable to the attacker than the pre-donation reserves would justify.
4. Repeat/adjust ratio of donation vs. trade size to extract value from the pool, analogous to the reported `borrowed_token.transfer(controller_long, amount)` → `amm_short.price_oracle()` shift in the Curve report.
