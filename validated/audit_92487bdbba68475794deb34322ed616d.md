### Title
StatusHandler#process applies attacker-signed statuses to any commit sharing a sha, bypassing per-repository CI gating - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by SHA, with no scoping to the repository that signed the webhook. This lets an attacker who owns any repository containing a commit whose SHA collides with a commit in a victim stack (e.g. via a fork, which preserves identical commit SHAs) push a legitimately-signed status from their own org and have it applied to the victim's `Commit`/`Status` records, changing `Commit#blocked?`/`#deployable?` results for a stack they do not control.

### Finding Description
The broken binding is: `repository that signed/authored the status webhook == repository whose Commit/Status rows are mutated`. In `Shipit::WebhooksController#verify_signature` [1](#0-0)  the signature is checked against `Shipit.github(organization: repository_owner)`, i.e. it only proves the payload was really sent by the org named in the payload's own `repository.owner.login` — it proves nothing about which `Stack`/`Commit` rows should be touched.

Every other handler enforces repository scoping through the base class helper `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` from the webhook's own `repository.full_name` [2](#0-1) , and is used by `push_handler.rb`, `check_suite_handler.rb`, and the pull_request handlers.

`StatusHandler#process` does not use this helper at all: [3](#0-2) 
It instead does a global `Commit.where(sha: params.sha)` lookup across the entire commits table (all repositories, all stacks) and calls `commit.create_status_from_github!(params)` on every match. `create_status_from_github!` in turn calls `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3)  using the **matched commit's own `stack_id`**, not any stack derived from the webhook's repository — so the created `Status` is fully attributed to whatever stack the pre-existing `Commit` row belongs to, regardless of which org signed the webhook.

`Commit#blocked?` and `#deployable?` rely on the `Status`/`Commit#state` computed purely from the DB rows for that stack's blocking contexts (`stack.blocking_statuses`, delegated at `app/models/shipit/commit.rb:57-58`), so injecting a `success` status for the required context on a shared-sha commit flips `blocked?` to `false` for the victim stack, making the next commit `deployable?` and eligible for `Stack#next_commit_to_deploy`.

**Attack**: The attacker forks (or otherwise obtains) a repository sharing history/commit SHAs with the victim's tracked repo — trivial via a GitHub fork, which by design preserves identical commit SHAs for shared history. They connect that fork's CI (or emit `POST /webhooks` with `X-Github-Event: status` and a valid HMAC signed with their own org's `webhook_secret`, since `Shipit.github(organization: repository_owner)` resolves per-org and the attacker owns that org/app installation) with `sha` = the shared SHA, `context` = the victim's configured blocking context (e.g. `ci/travis`), `state` = `success`. `StatusHandler#process` matches the victim's `Commit` row by SHA alone and writes a `success` `Status` scoped to the victim's `stack_id`, unblocking the victim's deploy chain.

Existing guards do not stop this: `verify_signature` only authenticates "this payload came from org X" — it never checks that org X's repository actually owns the matched `Commit`. `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, `context`, etc.), not provenance/ownership. `force_github_authentication`, session/API-client checks are irrelevant since webhooks are unauthenticated by session/token by design and rely solely on HMAC + repository binding, which is exactly the binding missing here.

### Impact Explanation
An attacker who controls an unrelated repository (via fork or by independently creating a commit with a colliding SHA to shared history) can write arbitrary CI status records into another tenant's `Stack`/`Commit`, bypassing the `ci.blocking` deployment safety gate (`Commit#blocked?`) and causing `Stack#next_commit_to_deploy` to select and later deploy a commit that was never actually verified by the victim's CI. This is a cross-tenant write (a payload for one repository mutating another's commit/stack state) leading to an unauthorized deploy decision — matching the Critical category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy"). It is repeatable against any stack whose repository/fork relationship allows shared SHAs, and blast radius spans all stacks tracking commits reachable from a forked/shared history.

### Likelihood Explanation
Preconditions: the victim stack must have `ci.blocking` configured for a guessable/known context (commonly `ci/travis`, `ci/circle`, etc., which are conventional and often visible in the target repo's public CI badges/config), an undeployed blocking commit must exist, and the attacker needs a repository under their control that shares at least one commit SHA with the victim's tracked branch (trivially satisfied for any public GitHub repo via `fork`, since forks retain original SHAs; even for private repos, any contributor/former collaborator with push access to a derived repo, or a commit deliberately cherry-picked/rebased with identical author/committer timestamps, tree, and message can reproduce an identical SHA). No Shipit secrets, sessions, or API tokens are required — only ownership of an org whose `webhook_secret`/GitHub App is legitimately configured to emit signed status webhooks, which the attacker fully controls for their own repository. This makes the attack cheap and highly repeatable.

### Recommendation
Scope `StatusHandler#process` to the reporting repository the same way other handlers do: resolve the stack(s) via `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) and only update/create `Status` rows for `Commit`s that belong to those resolved stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), rejecting or ignoring shas that don't belong to a commit tracked under the webhook's own repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from a foreign repository must not unblock another stack's commit" do
  victim_stack = shipit_stacks(:shipit) # configured with ci.blocking for 'ci/travis'
  blocking_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)
  next_commit = victim_stack.commits.create!(sha: "cafebabe" * 5, ...)
  # no successful ci/travis status yet -> blocked

  assert_predicate next_commit, :blocked? # binding LHS: reporting_repo == mutated_repo (currently violated)

  attacker_payload = ExplicitParameters::Parameters.parse!(
    "sha" => blocking_commit.sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => "attacker/unrelated-fork" }
  )

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  refute_predicate next_commit.reload, :blocked?, "foreign repository webhook should not unblock victim stack"
  assert_equal victim_stack, blocking_commit.reload.statuses.last.stack
end
```
This demonstrates that `StatusHandler#process` currently updates `blocking_commit`'s status (and flips `next_commit.blocked?`) even though the payload's `repository.full_name` does not match `victim_stack`'s repository — confirming the missing binding.
