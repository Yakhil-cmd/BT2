### Title
Stack-scoped ApiClient token authorizes access to any stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` implements per-token stack scoping: any `ApiClient` that has a `stack_id` set is restricted to that single stack via the `stacks`/`stack` helper methods used by every other API resource. `CCMenuController` overrides the `stack` helper with an unscoped lookup, so a token that is only supposed to authorize reads of stack A can be used to read build/deploy state of any other stack B, breaking the binding "stack a token authorises == stack a token touches".

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the resolvable set of stacks to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a stack, and `#stack` resolves `params[:stack_id]` against that restricted set: [1](#0-0) 

`ApiClient` itself models this scoping explicitly (`belongs_to :stack, optional: true`), and `check_permissions!` only checks the operation/scope string (e.g. `read:stack`), not which stack is being touched: [2](#0-1) 

Every other stack-scoped API controller (e.g. `Shipit::Api::StacksController`) relies on the inherited, scoped `stacks`/`stack` helpers to enforce that a stack-restricted token can only see its own stack: [3](#0-2) 

`CCMenuController`, however, re-implements `authenticate_api_client` to accept a `?token=` query parameter and, critically, overrides `stack` to bypass the `stacks` scoping helper entirely, resolving `params[:stack_id]` against the *entire* `Stack` table: [4](#0-3) 

The `here_come_the_walrus` fixture demonstrates the intended stack-scoping feature in use — an `ApiClient` with `stack: shipit` and `permissions: ['read:stack']` — confirming that stack-restricted tokens are a first-class, expected trust boundary in this codebase: [5](#0-4) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, presenting a valid token that only has `read:stack` permission on stack A, together with any other `stack_id` param, returns full build/deploy status for stack B. This is the same class of bug as the reported Sudoswap issue: a permission granted narrowly (router approved for one purpose / a token scoped to one stack) is checked only for its coarse capability (“is this a router at all” / “does this token have `read:stack` at all”) rather than for the specific object it is being exercised against (the specific pair/contract / the specific stack).

### Impact Explanation
Any holder of a valid, narrowly stack-scoped API token (`read:stack` on stack A) can read the build/deploy status, activity, lock state, and last build label/time of any other stack in the Shipit installation by simply varying the `stack_id` request parameter against `GET /api/:stack_id/ccmenu.xml`. This is an authorization-scope escalation that lets a token exceed the stack boundary it was explicitly provisioned for, resulting in unauthorized read of stack state across repositories/stacks the token holder should not have visibility into.

### Likelihood Explanation
Exploitation requires only a valid stack-scoped API token with `read:stack` permission (the minimum permission granted to CCMenu-style integration clients) and knowledge/guessing of another stack's `to_param` identifier (owner/repo/environment/branch), which is often predictable or discoverable. No special privileges beyond holding any single-stack-scoped token are needed.

### Recommendation
Have `CCMenuController#stack` reuse the inherited, scoped `stacks`/`stack` helper (i.e. remove the local override) so that stack resolution is always constrained by `current_api_client.stack_id` exactly as it is for every other API controller.

### Proof of Concept
1. Provision (e.g. via console/admin tooling) a stack-scoped `ApiClient` with `stack_id` = Stack A's id and `permissions: ['read:stack']`, matching the pattern of the `here_come_the_walrus` fixture.
2. Obtain that client's `authentication_token`.
3. Request `GET /api/<stack_B_param>/ccmenu.xml?token=<token>` where stack B is a different stack than the one the token is scoped to.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns stack B's build status, even though the token's `stack_id` only authorizes stack A.

module Shipit
  module Api
    class StacksController < BaseController
      require_permission :read, :stack, only: %i[index show]
      require_permission :write, :stack, only: %i[create update destroy]

      params do
        accepts :repo_owner, String
        accepts :repo_name, String
      end
      def index
        @stacks = stacks
        if params[:repo_owner] && params[:repo_name]
          full_repo_name = [repo_owner, repo_name].join('/')
          @stacks = if (repository = Repository.from_github_repo_name(full_repo_name))
                      stacks.where(repository:)
                    else
                      Stack.none
                    end
        end
        render_resources(@stacks)
      end
