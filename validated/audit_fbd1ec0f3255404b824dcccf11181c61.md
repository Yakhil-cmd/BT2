### Title
AA asset definitions with malformed `issue_condition`/`transfer_condition` pass validation but permanently fail at issue/transfer time, freezing the asset - (File: aa_validation.js)

### Summary
When an autonomous agent (AA) is defined with an `asset` message that includes `issue_condition` or `transfer_condition`, `aa_validation.js` only checks that these fields are an array of length 2, but never validates that they are semantically valid spending-condition definitions. In contrast, the equivalent path for regular (non-AA) asset definitions runs the condition through `Definition.validateDefinition()` before allowing the unit to be accepted. This asymmetry lets an AA definition with a malformed `issue_condition`/`transfer_condition` be accepted as valid, while any subsequent attempt to actually issue or transfer that asset will always fail at runtime, permanently freezing the asset.

### Finding Description
In `aa_validation.js`, the `asset` case of `validatePayload()` only does a shallow structural check on the conditions: [1](#0-0) 
No call is made to `Definition.validateDefinition()` to verify that the array actually represents a well-formed spending-condition expression (valid ops, valid nested addresses, etc.), unlike the non-AA path.

For comparison, the analogous non-AA path in `validateAssetDefinition()` (used when a regular unit defines an asset) fully validates both conditions with `Definition.validateDefinition()` before the unit can be accepted: [2](#0-1) 

Because `validateAADefinition()` is the sole gatekeeper for AA "code" (invoked from `validateInlinePayload()`'s `"definition"` case), an AA whose static template defines an asset with a bogus `issue_condition`/`transfer_condition` (e.g., an unrecognized op, or a reference that can never be satisfied, while still being a 2-element array) will pass definition validation and get installed via `storage.insertAADefinitions()`.

The malformed condition is only actually evaluated later, when a real issue or transfer of that asset is attempted, via `Definition.evaluateAssetCondition()` → `validateAuthentifiers()` → `validateDefinition()`: [3](#0-2) 
`Definition.validateDefinition` re-validates the condition array on every use and will return an error for the malformed condition every single time: [4](#0-3) 

Since the condition is a fixed part of the immutable AA definition, this failure is deterministic and permanent — every future issue or transfer of the asset will bounce/fail with `"transfer or issue condition not satisfied"` or a validation error, exactly mirroring the referenced report's pattern where a missing validation at "construction" time causes a function to always revert afterward.

### Impact Explanation
Any asset that an AA is coded to issue or manage using a malformed `issue_condition`/`transfer_condition` becomes permanently unusable: the AA can never successfully issue units of that asset nor can holders ever transfer it, since every payment message referencing it will fail validation forever. Funds/logic depending on that asset (e.g., reward or LP tokens minted by the AA, deposits meant to be forwarded) are frozen at the protocol level with no recovery path, since the AA's definition cannot be changed after deployment. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
This requires only that an AA author (an in-scope actor per the rules) writes an `asset` message inside the AA template with a syntactically-array-of-2 but semantically invalid `issue_condition`/`transfer_condition` — an easy mistake to make precisely because `aa_validation.js` gives no feedback at definition time (unlike the non-AA path, which would reject such a definition immediately). The bug is not by itself attacker-triggered against a victim AA, but it silently allows deployment of broken AAs whose asset-handling logic is guaranteed to fail forever, which is a realistic and likely occurrence given the validation gap.

### Recommendation
In `aa_validation.js`'s `asset` case, validate `issue_condition` and `transfer_condition` the same way non-AA asset definitions do — by running them through `Definition.validateDefinition()` (with `bAssetCondition = true`) at AA-definition time, so that malformed conditions are rejected before the AA (and its unusable asset) can ever be deployed.

### Proof of Concept
1. Author an AA whose template includes:
```
{
  app: 'asset',
  payload: {
    cap: 1000000,
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: false,
    issued_by_definer_only: true,
    cosigned_by_definer: false,
    spender_attested: false,
    issue_condition: ["bad_op", {}]   // passes isArrayOfLength(x,2) but is not a valid op
  }
}
```
2. Post the `definition` message defining this AA. `aa_validation.validateAADefinition()` accepts it because it only checks `isArrayOfLength(payload.issue_condition, 2)` (`aa_validation.js:289-291`).
3. Trigger the AA so it emits a `payment` message with `inputs[0].type = "issue"` for this asset.
4. `validatePaymentInputsAndOutputs()` calls `Definition.evaluateAssetCondition()` → `validateDefinition()`, which returns `"unknown op: bad_op"` (`definition.js:616-617`), causing the issue to always fail — the asset can never be issued, permanently freezing it.
