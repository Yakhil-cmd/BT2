### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a `status` webhook flip CI state on any repository's commit sharing that SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha).each`, with no filter on the repository that sent the webhook. Combined with `Shipit::WebhooksController#verify_signature`, which authenticates the payload only at the GitHub-organization level (`Shipit.github(organization: repository_owner)`), a status event that is validly signed for one repository in an org is applied to every `Commit` record across every stack sharing that SHA, including stacks in other repositories of the same org.

### Finding Description
The broken binding is: the invariant `status.context == "sonarqube"` and the payload's `repository.full_name` should equal the `full_name` of the repository actually owning the affected `Commit`/`Stack`, i.e. `payload.repository.full_name == commit.stack.repository.full_name`. This binding is never checked.

Trace:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to handlers for the `status` event, after `verify_signature` (line 24-49), which authenticates using `Shipit.github(organization: repository_owner)` — scoped to the *organization*, not the specific repository. `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`).
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
There is no `repository`, `stack`, or `full_name` filter — any `Commit` row in the whole Shipit install whose `sha` column matches the attacker-supplied SHA gets the status attached, regardless of which repository/stack it belongs to.
3. `Commit#create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) updates `statuses`, recomputes `status`, and if the simple state changes to success/pending, calls `stack.schedule_merges` and (via the `after_commit :schedule_continuous_delivery` callback wired at commit-creation time, and re-evaluated through `deployable?`) can trigger `ContinuousDeliveryJob` on the *victim* stack once its aggregate status becomes green, per `Commit#deployable?` (app/models/shipit/commit.rb:227-229) and `Commit#schedule_continuous_delivery` (lines 281-287), which requires `stack.continuous_deployment?` and `stack.deployable?`.

Exploit flow: an attacker with push access to any repository in the same GitHub organization as the victim stack (this need not be the victim's own repo, just any repo in that org where the Shipit GitHub App/webhook is installed) creates or forks a repository containing a commit with an identical SHA to one in the victim's history (trivial via fork/cherry-pick — Git SHAs are content-addressed and preserved across forks/pushes of the same tree), then triggers a `status` event (e.g., via GitHub Actions, GitHub API, or their own CI integration) with `context: "sonarqube"`, arbitrary `state`, on that shared SHA. `verify_signature` validates it because it only checks the organization-level webhook secret, and `StatusHandler` blindly updates the matching `Commit` row wherever it lives in the database.

Existing guards do not close this gap: `verify_signature` authenticates only that *some* app/webhook secret for that organization signed the request, not that the named repository owns that commit; `ExplicitParameters` in `StatusHandler.params` validates types/shape only, not repository identity; there is no `require_permission!`/`stacks` scope check in this webhook pipeline (webhooks are inherently unauthenticated besides the HMAC signature) and no comparison anywhere between `payload.repository.full_name` and `commit.stack.repository.full_name`.

### Impact Explanation
An attacker who can get a validly-signed webhook accepted for *any* repository in the same GitHub organization as a victim can write arbitrary CI status ("sonarqube" or any context) onto a `Commit` belonging to a different stack/repository. If that victim stack has `continuous_deployment` enabled and requires that status context, the forged green status can cause `ContinuousDeliveryJob` to ship attacker-influenced state, or a forged red/blocking status can block legitimate deploys/merges (denial of the victim's release pipeline). This is a cross-tenant write: "a payload for one repository mutating another's stack/commit" — matching the Critical impact category ("an unauthorized deploy, rollback or merge" / "a record written for a repository that did not authenticate it").

### Likelihood Explanation
Preconditions: (1) attacker must have write/push access to at least one repository within the same GitHub organization that has the Shipit GitHub App/webhook installed (this is a much lower bar than being a maintainer of the victim repository itself — could be any public repo in the org, or one the attacker creates if the org allows it); (2) attacker's commit and the victim's commit must share the same SHA, which is straightforward via forking/mirroring/cherry-picking the exact same commit; (3) the victim stack must have `continuous_deployment` enabled and be otherwise deployable. Given these, the attack is cheap and repeatable against any stack in the same org, for any status context.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook: join through `Commit -> Stack -> Repository` and filter `Commit.joins(:stack).merge(Stack.for_repository(params.repository.full_name))` (or equivalent) before applying `create_status_from_github!`, comparing against the `repository.full_name` extracted from the verified payload rather than trusting the org-level signature alone.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_scoping_test.rb
test "status webhook does not affect commits from another repository sharing the same SHA" do
  shared_sha = "a" * 40

  attacker_stack = shipit_stacks(:shipit) # repository: "acme/other-repo"
  victim_stack = create_stack(repository: create_repository(full_name: "acme/victim-repo"))
  victim_stack.update!(continuous_deployment: true)

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker commit")

  payload = {
    sha: shared_sha,
    state: "success",
    context: "sonarqube",
    repository: { full_name: attacker_stack.repository.full_name, owner: { login: attacker_stack.repository.owner } }
  }

  # Binding under test:
  # payload.repository.full_name ("acme/other-repo") == victim_commit.stack.repository.full_name ("acme/victim-repo")
  # should be FALSE, therefore victim_commit.statuses should remain unchanged.
  assert_not_equal payload[:repository][:full_name], victim_commit.stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.new.process # invoked with the payload as in production

  victim_commit.reload
  assert_empty victim_commit.statuses, "status webhook for another repository must not write to victim_commit"
end
```
This test, given the current implementation of `StatusHandler#process` (`Commit.where(sha: params.sha).each`), fails because the victim's commit status is written despite the mismatched `repository.full_name`, confirming the missing repository-scoping check.
