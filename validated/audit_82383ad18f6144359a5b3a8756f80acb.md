### Title
Cross-organization commit status forgery via unscoped `StatusHandler` webhook processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController` authenticates an inbound GitHub webhook by looking up the *organization*'s webhook secret from `repository_owner` (derived from the payload) and verifying the HMAC signature against that secret [1](#0-0) . However, once the signature is verified, `Shipit::Webhooks::Handlers::StatusHandler#process` writes a `Status` to a `Commit` found solely by `sha`, with no check that the commit belongs to the repository/organization whose secret authenticated the request [2](#0-1) . This breaks the binding: `organization authenticated by webhook_secret == organization whose commit status is written`.

### Finding Description
In a multi-tenant Shipit deployment, each GitHub organization has its own webhook secret, configured via `Shipit.github_app_config` / `secrets.github` [3](#0-2) . `WebhooksController#verify_signature` picks the `GitHubApp` instance for `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the raw payload's HMAC signature against that organization's own `webhook_secret` [4](#0-3) , then dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw JSON `params` [5](#0-4) .

The base `Handler` class provides a `stacks` helper that correctly scopes lookups to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [6](#0-5) , and most handlers (e.g. `PushHandler`, `CheckSuiteHandler`) correctly use this `stacks` scope before touching any commit [7](#0-6) [8](#0-7) .

`StatusHandler`, however, bypasses this repository scoping entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` searches the *entire* `Commit` table across all stacks/repositories/organizations, keyed only by `sha` [9](#0-8) . Since the webhook signature only proves the request came from *some* organization onboarded to this Shipit instance (verified against that organization's own secret), but the handler applies the resulting write to any commit sharing the same `sha` regardless of owning organization, the "organization authenticated" side of the trust boundary is decoupled from the "repository (commit) written" side — exactly the class of binding break described in the report (claim tracked by a mutable/unbound key instead of the identity that was actually verified).

### Impact Explanation
Any organization legitimately onboarded to a multi-org Shipit deployment (i.e., an entity that is authorized to send *its own* signed webhooks, but is not authorized to act on other tenants' stacks) can forge a `status` event whose payload references a commit `sha` belonging to a different organization's stack (git SHAs are typically public on GitHub and thus guessable/observable by any GitHub user, not just the stack owner). Because `StatusHandler` performs no repository/organization ownership check, this forged event will successfully create/update a `Status` on a foreign stack's `Commit`. Since commit statuses are used by Shipit's commit-check gating (`commit_checks.rb`, `ephemeral_commit_checks.rb`) to determine whether a commit is deployable, this allows an unprivileged (relative to the victim's stack) organization to manipulate another organization's deploy-readiness state, potentially satisfying required checks and contributing to an unauthorized deploy of a repository the attacker does not own. This matches the High-impact category "escalation into authorization... or unauthorized deploy."

### Likelihood Explanation
Likelihood is Low-to-Medium: exploitation requires the Shipit instance to be configured for multiple GitHub organizations (`github_organizations`/per-org `webhook_secret`) and requires the attacker to control at least one legitimate onboarded organization capable of producing a validly signed webhook, plus knowledge of a target commit `sha` (often discoverable via public GitHub activity). No Shipit session, `ApiClient` token, or GitHub App private key is required — only the ability to send a `status` webhook signed with the attacker's own organization's secret.

### Recommendation
In `StatusHandler#process` (and any other handler that touches commit/stack state), scope the lookup through the authenticated repository, i.e., filter through `stacks.commits.where(sha: params.sha)` (as `CheckSuiteHandler` does) instead of `Commit.where(sha: params.sha)`, so that the commit acted upon must belong to the same repository/organization whose webhook secret produced the verified signature.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` under `secrets.github` [10](#0-9) .
2. `org-b` has a stack tracking commit `sha=deadbeef...` that is pending/failing CI, blocking deploys.
3. An attacker who controls `org-a` (and thus knows `org-a`'s own valid `webhook_secret`) sends a GitHub `status` webhook to `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `org-a`'s secret, and a JSON body containing `{"repository": {"owner": {"login": "org-a"}, ...}, "sha": "deadbeef...", "state": "success", ...}`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `org-a` and successfully verifies the signature using `org-a`'s secret [4](#0-3) .
5. `StatusHandler#process` executes `Commit.where(sha: 'deadbeef...')`, which matches `org-b`'s commit (since the query is global), and writes a `success` status onto it [2](#0-1) , even though the verified signature only proved authenticity for `org-a`, not `org-b`.

module Shipit
  module Webhooks

        def process
          Commit.where(sha: params.sha).each do |commit|

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
