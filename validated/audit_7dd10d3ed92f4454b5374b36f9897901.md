## Finding

### Title
`MultiKey` authenticator allows duplicate public keys, letting a single signer satisfy a k-of-n threshold - ([File: types/src/transaction/authenticator.rs])

### Summary
The external report's bug class is "an invalid/degenerate signing entity gets counted as a distinct, valid vote, reducing the number of unique authorizers actually required to pass a signature-threshold check." The Aptos-native analog is in the `MultiKey`/`MultiKeyAuthenticator` authentication scheme (`types/src/transaction/authenticator.rs`): `MultiKey::new` never rejects duplicate public keys in the key list, and `MultiKeyAuthenticator::new`/`verify` only prevent duplicate **indices**, not duplicate **keys**. As a result, a single private key that appears at two (or more) index slots in the `MultiKey` can supply the *same* signature at each slot and satisfy a `k`-of-`n` threshold with fewer than `k` unique signers.

### Finding Description
`MultiKey::new` (types/src/transaction/authenticator.rs, ~line 1241) validates:
- `signatures_required > 0`
- `public_keys.len() <= MAX_NUM_OF_SIGS`
- `public_keys.len() >= signatures_required` [1](#0-0) 

It does **not** check that the entries of `public_keys` are pairwise distinct.

`MultiKeyAuthenticator::new` (~line 1120) validates that each signature's `idx` is in range and that no two signatures reuse the same **bitmap index**: [2](#0-1) 

This only prevents the same bitmap slot from being counted twice; it does nothing to prevent two *different* slots that happen to reference the *same public key* from both being satisfied by one signature. `to_single_key_authenticators`/`verify` then iterate over the bitmap and treat each set bit as an independent “signer”, counting it toward `signatures_required`: [3](#0-2) 

The existing unit test `verify_multi_key_auth` inadvertently documents (and validates as expected/passing behavior) that this is exploitable: the `MultiKey` is constructed with `keys = [sender0_pub, sender1_pub, sender1_pub]` (index 1 and 2 are the *same* key) with `signatures_required = 2` (a 2-of-3 threshold). A `MultiKeyAuthenticator` is then built using the **same** `signature1` at both index 1 and index 2, and `signed_txn.verify_signature()` succeeds: [4](#0-3) 

Only one private key (`sender1`) ever signed the transaction, yet the 2-of-3 threshold is satisfied, because the "second" required signature is just a second copy of the same valid signature against the duplicated key.

### Impact Explanation
This breaks the core admission-time invariant that a `MultiKey` account's threshold represents `k` independent authorizations. Any Aptos account (an object address, a smart-wallet/vault, or a rotated authentication key) that ends up with a `MultiKey` containing duplicated public keys — whether by user error, key-management-tool mishap, or a malicious co-signer intentionally submitting the same public key twice when a multi-key set is being assembled from externally supplied keys — can be fully controlled and transactions can be admitted/executed by a single key holder even though the account was configured (and is publicly represented on-chain, e.g. via `num_signatures_required`/threshold semantics) as requiring `k` distinct approvers. This is a wrong-approval-set admission bug: the authenticator accepts a signer set that does not match the intended (distinct) signer set, directly weakening custody/multisig-style security guarantees for any account using this authentication scheme. Because control over funds/administrative operations under a `MultiKey` account is the direct impact, this is High severity.

### Likelihood Explanation
Likelihood is Medium: the vulnerability requires a `MultiKey` to actually contain duplicate public keys. This is not stopped by any admission-time or construction-time check (`MultiKey::new`, `MultiKeyAuthenticator::new`, `AuthenticationKey::multi_key`, or the Move-side `0x1::multi_key` construction path), so it silently succeeds whenever duplicates are supplied — whether via `rotate_authentication_key_from_public_key` (`aptos-move/framework/aptos-framework/sources/account/account.move`, scheme `MULTI_KEY_SCHEME` → `multi_key::new_public_key_from_bytes`) or via the API's `MultiKeySignature`→`AccountAuthenticator` conversion. I was unable to fully verify (due to result truncation) whether the Move-side `0x1::multi_key` module performs its own duplicate-key check independent of the Rust-side `MultiKey::new`; this should be confirmed before treating the on-chain enforcement path as identical to the Rust authenticator path.

### Recommendation
- **Short term:** Add a duplicate-public-key check to `MultiKey::new` (and the equivalent Move-side `multi_key`/`multi_ed25519` constructors) so that construction fails if any two entries in `public_keys` are byte-identical (mirrors the existing duplicate-index rejection already present for signatures).
- **Long term:** Add a fuzz/property test asserting that a `MultiKey`/`MultiKeyAuthenticator` with `k` required signatures can never verify using fewer than `k` distinct underlying public keys, and audit `MultiEd25519`/`multi_ed25519.move` for the same class of duplicate-key issue.

### Proof of Concept
The existing test `verify_multi_key_auth` in `types/src/transaction/authenticator.rs` is itself the PoC:
1. Construct `MultiKey::new(vec![sender0_pub, sender1_pub, sender1_pub], 2)` — a 2-of-3 threshold where slots 1 and 2 are the same key.
2. Sign the raw transaction only with `sender1`'s private key, producing `signature1`.
3. Build `MultiKeyAuthenticator::new(multi_key, vec![(1, signature1.clone()), (2, signature1.clone())])`.
4. Wrap in `AccountAuthenticator::multi_key(...)` → `SignedTransaction::new_single_sender(...)`.
5. `signed_txn.verify_signature()` returns `Ok(())`, confirming a "2-of-3" transaction was admitted with only one unique signer. [5](#0-4)

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
