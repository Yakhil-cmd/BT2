Found a concrete instance of the exact binding-mismatch pattern the report describes: an `ApiClient` that is scoped to a single stack (`stack_id`) authorizes based on `Stack.where(id: current_api_client.stack_id)`, but `Api::CCMenuController#stack` bypasses that scoping entirely by loading `Stack.from_param!(params[:stack_id])` directly instead of going through the base controller's `stacks`/`stack` helpers.

### Title
Stack-scoped ApiClient's authorized stack differs from the stack it actually reads via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` defines the authorization binding: an `ApiClient` created with `stack_id` set is only allowed to see `Stack.where(id: current_api_client.stack_id)` [1](#0-0) . `Api::CCMenuController`, however, overrides `stack` to load `Stack.from_param!(params[:stack_id])` directly, never consulting `stacks` (the client-scoped relation) [2](#0-1) . This is exactly the "double subtraction" bug class: one code path (`stacks`) computes the authorized stack set, and a second, supposedly equivalent path (`CCMenuController#stack`) recomputes stack resolution independently and diverges from it, so the stack the token *authorizes* is not the stack the endpoint *touches*.

### Finding Description
`ApiClient#stack_id?`/`stack_id` is the mechanism by which an API token is scoped to a single stack — used by `BaseController#stacks` to restrict `Stack.where(id: ...)` for any client with a non-nil `stack_id` [3](#0-2) . `require_permission :read, :stack` is enforced on `CCMenuController#show` [4](#0-3) , which only checks the `permissions` array (`read:stack`) via `ApiClient#check_permissions!` [5](#0-4)  — it does **not** check `stack_id` scoping. The actual stack-scoping enforcement is supposed to happen entirely inside the `stacks`/`stack` helper chain in `BaseController`. `CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, so any client holding a valid API token with `read:stack` permission — even one deliberately scoped to stack A via `stack_id` — can pass an arbitrary `stack_id` in the URL and read CI status (`show` renders `stack.deploys_and_rollbacks.last`) for any other stack B in the installation [6](#0-5) .

This mirrors the reported bug precisely: `getCurrentBlockNumber()` (≈ `stacks`, the scoped resolution) and `getStageAtBlock()` (≈ `CCMenuController#stack`, a second computation) were each individually correct in isolation, but the call site combining them broke the invariant that only one adjustment (here, only one *scope check*) should apply. Here the scope check that should be shared across both resolution paths is simply missing from the second path.

### Impact Explanation
This is a cross-stack read: a stack-scoped `ApiClient` (e.g. one created via `CCMenuUrlController#client` with `permissions: %w[read:stack]`, scoped to a single stack) can leak deploy/rollback status of any other stack in the same Shipit instance by supplying a different `stack_id` param. Per the impact rubric this qualifies as High — "unauthenticated read of stack state ... deploy output" for a token holder who was only meant to read one stack's state, escalating read access beyond the token's intended stack boundary.

### Likelihood Explanation
Likelihood is high for any deployment using the CCMenu integration: `stack_id`-scoped tokens are a documented, first-class feature (`CCMenuUrlController` mints exactly such a token) [7](#0-6) , and exploitation only requires possessing one such (unprivileged, narrowly-scoped) token and changing the `stack_id` in the request URL — no additional secrets, session, or write access are required.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` relation (i.e. `stacks.from_param!(params[:stack_id])`) exactly like `Api::StacksController#stack` does [8](#0-7) , so there is a single source of truth for "which stacks this `ApiClient` may access" rather than two independently-maintained resolution paths.

### Proof of Concept
1. Create (or obtain) a `stack_id`-scoped `ApiClient` token for Stack A with `read:stack` permission (e.g. via the `/stacks/:stack_id/ccmenu.xml` flow, which mints such a token in `CCMenuUrlController#client`).
2. Note that `Api::BaseController#stacks` would restrict this client to `Stack.where(id: A.id)` for every other endpoint that uses `stacks.from_param!`.
3. Call `GET /api/stacks/:B/ccmenu.xml?token=<A's token>` where `B` is a different stack's id/full name.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped), successfully loading Stack B and rendering its latest deploy/rollback status in the XML response — despite the token being scoped only to Stack A.
