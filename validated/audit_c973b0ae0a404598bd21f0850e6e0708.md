Based on my research, I found a concrete analog to the reported "incomplete input validation before creating/reusing an object from user-supplied params" bug class in the AA (Autonomous Agent) parameterized-definition path of `ocore`.

### Title
Incomplete validation of `params` in parameterized AA definitions allows unvalidated value types to reach AA execution - ([File: aa_validation.js])

### Summary
`validateAADefinition()` in `aa_validation.js` validates a parameterized AA definition (`{base_aa, params}`) far more loosely than the equivalent “definition template” parameter-filling mechanism used for regular addresses. Any unprivileged unit poster can post a `definition` message defining a parameterized AA whose `params` values are not restricted to the primitive types (`string`/`number`) that the rest of the system assumes params will contain.

### Finding Description
When an AA definition has a `base_aa` field (a "parameterized AA", i.e. an AA that is just an alias for a base AA plus a set of parameters), validation is: [1](#0-0) 

This only checks:
- no foreign fields besides `base_aa`/`params`,
- `params` is a non-empty object,
- `variableHasStringsOfAllowedLength(template.params)` (a length check on any strings present),
- `base_aa` is a valid address.

Nowhere does it enforce that every value in `params` is restricted to `string`/`number` primitives. This is inconsistent with the sibling mechanism for regular address definitions — the `'definition template'` operator — which explicitly enforces this constraint before substitution: [2](#0-1) 

Once such a parameterized AA definition passes `validateAADefinition` and is stored, any trigger sent to it is redirected in `aa_composer.js`, which pulls the unvalidated `template.params` object out of storage and hands it directly to the base AA's execution context as `trigger_opts.params`: [3](#0-2) 

These `params` are then exposed inside the base AA's oscript/ojson code via the `params` selector and consumed by the formula evaluator (`formula/evaluation.js`, `formula/validation.js` `case 'params'`), which — like most of the formula engine — is written assuming values coming from user-controlled composite structures (`trigger.data`, `params`, etc.) are always plain JSON primitives (numbers, strings, booleans) or wrapped objects it explicitly checks for, not arbitrary nested objects/arrays smuggled in through an under-validated `params` field.

### Impact Explanation
If a value type other than the expected primitives can be stored inside `params` and later flow unexpectedly into formula evaluation, string concatenation, JSON serialization of response messages, or address/asset comparisons inside the base AA's logic, it can produce divergent behavior between differently-implemented validators/evaluators (since JS's dynamic typing means comparisons and coercions with non-primitive values behave in ways formula authors don't anticipate), potentially causing nodes to disagree on the outcome of AA execution (bounced vs. not bounced, different response amounts/messages) for the same trigger and AA state, or allowing objects/arrays to bypass length/format checks that assume string/number `params`. Disagreement of full nodes on AA-response validity is a stability/consensus-relevant condition.

### Likelihood Explanation
Medium. Reaching this requires only posting a normal AA "definition" message defining a parameterized AA (`base_aa` + `params`), something any unit poster can do, and pointing a trigger at it, or waiting for someone else to. No special privileges are needed. The concrete exploitation path (what exact value type causes a consensus-affecting divergence in a specific base AA) requires further code-level confirmation of how every formula operator handles non-primitive `params` values, which I was not able to fully trace given tool constraints — I could not retrieve the full body of `variableHasStringsOfAllowedLength` in `aa_validation.js` to confirm precisely which types it rejects versus admits.

### Recommendation
Mirror the stricter validation used for the `'definition template'` operator: in `validateAADefinition`, for parameterized AAs, iterate `template.params` and reject any value whose `typeof` is not `"string"` or `"number"` (in addition to the existing length check), matching the invariant the rest of the codebase (and the formula engine) already assumes for such parameter maps.

### Proof of Concept
Not independently verified end-to-end due to tool/access limits (I could not execute the AA formula engine to confirm a concrete divergent-output value). The structural gap is directly demonstrable by comparing the two validators:
- `aa_validation.js:734-744` (parameterized AA `params` — no type restriction on values, only string length check via `variableHasStringsOfAllowedLength`)
- `definition.js:313-320` (`'definition template'` params — explicit `typeof params[key] !== "string" && typeof params[key] !== "number"` rejection)

A `["autonomous agent", {base_aa: <valid_base_aa_address>, params: {x: {nested:"object"}}}]` (or an array-valued param) definition would pass `validateAADefinition` today, since only string entries are length-checked and no explicit primitive-type check exists for non-string values, contrary to the codebase's own established pattern in `definition.js`.
