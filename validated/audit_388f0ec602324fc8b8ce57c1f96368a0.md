## Finding

The bug-class here — a value trusted without validating it stays bound to what authorized it — has a direct analog in `Shipit::Api::CCMenuController`. An `ApiClient` token scoped to a single stack (`api_client.stack_id`) is meant to only ever "touch" that one stack, but `CCMenuController` accepts an arbitrary `params[:stack_id]` without checking it against the token's authorized stack.

### Title
Stack-scoped API token can read CCMenu status of any stack, bypassing its `stack_id` binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds every scoped API client to a single stack via `current_api_client.stack_id`, and enforces it through the `stacks`/`stack` helper methods used by every other API controller. [1](#0-0) 
`CCMenuController` overrides `authenticate_api_client` to accept a bare `params[:token]` (no Basic Auth) and then re-defines `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely skipping the `current_api_client.stack_id` scoping that `BaseController#stacks` normally applies. [2](#0-1) 

### Finding Description
Every other API resource controller (e.g. `StacksController`, `DeploysController`, `TasksController`, `LocksController`, `MergeRequestsController`) resolves the target stack through `stack`/`stacks`, which is defined once in `BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This is the binding the application relies on: `token.stack_id == accessed_stack.id` whenever a token is stack-scoped. `ApiClient#check_permissions!` only checks that the operation string (e.g. `"read:stack"`) is present in the token's `permissions` array — it never checks which stack is being touched. [3](#0-2) 
So the *only* place enforcing "this token may only touch stack X" is the `stacks` scoping in `BaseController`.

`CCMenuController` breaks that binding:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack

  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [2](#0-1) 

`stack` here calls `Stack.from_param!` on the unscoped `Stack` model instead of the scoped `stacks` relation from `BaseController`. `require_permission :read, :stack` still passes for any token that has the generic `read:stack` permission bit, since that check is not stack-specific. As a result, holding a token that was only ever intended to authorize `read:stack` for Stack A is sufficient to request `show` with `stack_id` pointing at Stack B, and successfully read Stack B's deploy status.

### Impact Explanation
This is an authorization-scope escalation: a token deliberately restricted to one stack (`api_client.stack_id`) can be used to read the deploy/task state of any other stack in the installation by simply changing the `stack_id` request parameter. This matches the rule's "escalation into `Shipit.github_teams` authorization[-equivalent]" / "unauthenticated read of stack state, task streams or deploy output" category — the equality the app is supposed to enforce (`token.stack_id == accessed stack`) is silently dropped for this one endpoint, letting a narrowly-scoped credential act like an unscoped one for stack information disclosure.

### Likelihood Explanation
Any organization that issues stack-scoped `ApiClient` tokens (a supported, documented feature — see `stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack") is affected. No special privilege beyond possessing such a legitimately-scoped token is required; only the `stack_id` request parameter needs to be changed to target a different stack; the endpoint is deliberately reachable via URL/token query param rather than Basic Auth. [4](#0-3) 

### Recommendation
Have `CCMenuController#stack` reuse the inherited, correctly-scoped `stacks` relation instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the `current_api_client.stack_id` binding established in `BaseController` is enforced consistently across all API controllers.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
2. Obtain its `authentication_token`.
3. Request `GET /api/<Stack B path>/cc.xml?token=<token>` (i.e. pass Stack B's `stack_id` in the URL rather than Stack A's).
4. Observe that `require_permission :read, :stack` passes (the token does have `read:stack`) and `CCMenuController#stack` resolves Stack B via `Stack.from_param!`, returning Stack B's deploy status even though the token was never authorized for Stack B.
