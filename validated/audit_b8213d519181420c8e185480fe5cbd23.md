### Title
Cross-organization stack takeover via webhook signature/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming GitHub webhook using the organization login parsed from the payload, but the handler that actually performs the write (`Handler#repository_name` / `Handler#stacks`) resolves the target `Repository`/`Stack` from a *different* payload field (`repository.full_name`) without confirming it belongs to the same organization that produced a valid signature. This breaks the binding "organization authenticated == organization whose repository is written," analogous to the Astaria bug where the field acted upon (listing payment) was never covered by the same trust check as the field the signed process assumed (auction stack).

### Finding Description
`verify_signature` computes the organization to use for HMAC verification purely from the payload: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and verifies the raw body against that organization's configured `webhook_secret`. A Shipit deployment can host multiple organizations, each with its own independently-configured `webhook_secret` — this multi-tenant configuration is explicitly supported, as shown by multiple sibling org keys in the secrets template: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the parsed JSON to the event handler: [4](#0-3) 

The handler base class, however, determines *which* repository/stack to act on from a different, independently-controlled field of the same payload — `repository.full_name` — rather than from `repository.owner.login` (the field used for signature verification): [5](#0-4) 

For the `push` event, `PushHandler#process` uses that repository lookup to run `stack.sync_github(expected_head_sha:)` for every matching, non-archived stack, using an attacker-controlled `after` SHA: [6](#0-5) 

Because the signature verification only proves that *some* known organization's secret produced a valid HMAC over the raw body, and does not cross-check that `repository.owner.login` (the field used to pick the secret) matches `repository.full_name`'s owner prefix (the field used to pick the target `Stack`), an actor who legitimately controls one configured organization's GitHub App/webhook secret can forge a payload whose `owner.login` matches their own org (so verification passes with their own known secret) while `repository.full_name` points at a completely different, unrelated organization's repository hosted on the same Shipit instance. The equality that should hold — organization that authenticated == organization whose repository/stack is written — is never enforced.

### Impact Explanation
This allows a user who is legitimately an admin of one configured GitHub organization/App on a shared Shipit instance to force a `push`-triggered sync (`stack.sync_github`) against a stack belonging to a completely different organization, using an attacker-chosen `expected_head_sha`. This is a cross-repository/cross-organization write performed under the wrong authentication scope, and can drive downstream sync/deploy behavior for a stack the attacker was never authorized to touch — meeting the "cross-repository writes / unauthorized deploy" bar for Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately controls (as an org admin) at least one organization configured on the shared Shipit instance — they use their *own* known `webhook_secret`, not a stolen one, and need no Shipit session, `ApiClient` token, or GitHub write access to the victim repository. Any multi-tenant Shipit deployment hosting more than one organization's GitHub App config (a documented, supported setup) is exposed.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner portion of the field the handler will actually act on (`repository.full_name`), and reject the webhook if they diverge. Alternatively, derive the target repository/stack lookup from the same verified organization identity rather than re-parsing an independent field of the payload.

### Proof of Concept
1. Attacker is an admin of `org-attacker`, a GitHub org with its own GitHub App configured on the shared Shipit instance, and therefore knows `org-attacker`'s `webhook_secret`.
2. Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `org-attacker`'s config, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `WebhooksController#create` dispatches to `PushHandler`, whose `repository_name` reads `full_name` = `"org-victim/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), locates the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the attacker having no relationship to `org-victim` beyond the shared Shipit instance.
