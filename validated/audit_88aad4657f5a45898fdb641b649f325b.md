Confirmed: `Shipit.github(organization:)` supports **multi-tenant configuration**, where each GitHub organization can have its own `webhook_secret` under `secrets.github[organization]` [1](#0-0) . This makes the webhook-verification flow a genuine analog of the reported race condition: two independent code paths derive different "authoritative" identifiers from the same untrusted payload, and only one of them is protected by a cryptographic check.

### Title
Webhook membership handler binds team/membership state to an unauthenticated `organization` field, decoupled from the HMAC-verified `repository.owner` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . For `membership` events, GitHub payloads carry an `organization` object separately from any `repository` object. `MembershipHandler#process` then trusts `params.organization.login` to create/find a `Team` and grant/revoke membership, entirely independent of what was used to select the signing secret [3](#0-2) .

### Finding Description
`Shipit.github(organization:)` looks up a per-organization config entry and constructs a `GitHubApp` whose `verify_webhook_signature` compares the `X-Hub-Signature` HMAC against that organization's `webhook_secret` — but returns `true` (i.e., "verified") if that organization has no `webhook_secret` configured at all [4](#0-3) .

In a multi-organization deployment, `repository_owner` in `verify_signature` is computed with a `repository` field taking priority over `organization`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) . GitHub's real `membership` webhook payload does not include a top-level `repository` key, so normally `repository_owner` resolves to `params.organization.login` and the two values match. However, because the webhook endpoint parses `request.raw_post` as arbitrary JSON with no schema enforcement before this dig, an attacker who can produce a validly-signed request for **any** organization configured with a blank/no `webhook_secret` (e.g., an org whose admin left it unset, or a low-security organization onboarded to the same Shipit instance) can inject an unrelated top-level `repository.owner.login` pointing at that unsecured org, while placing a *different* organization's data in the `organization` field that `MembershipHandler` actually consumes. `verify_signature` will pick the unsecured org's key (or accept trivially because `webhook_secret` is blank) while the mutation (`Team.find_or_create_by!`, `team.add_member`/`team.members.delete`) is executed for whatever organization/team appears in `params.organization`/`params.team`, which is not the value that was authenticated [6](#0-5) .

This is structurally the same class of bug as the Lighthouse race condition: one subsystem (signature verification) computes and validates against one selector derived from the payload (`repository.owner`/fallback), while a different subsystem (the membership handler) acts on a different, unguarded selector (`organization`) taken from the very same unauthenticated JSON blob, with no cryptographic binding forcing the two to agree.

### Impact Explanation
If exploitable, this allows an attacker to add or remove arbitrary `User`s from any `Team`'s membership by crafting a webhook payload that authenticates against a weakly-configured/organization-less-secret tenant while asserting membership changes for a different organization's team. Since `Shipit.github_teams` gates access to the entire application via `User#authorized?` [7](#0-6) , forging team membership additions is an authorization-bypass primitive: an attacker-controlled or attacker-named GitHub login could be granted membership in a required team, then authenticate via normal GitHub OAuth login and pass the `force_github_authentication` check [8](#0-7) .

### Likelihood Explanation
This requires (a) a multi-organization Shipit deployment (`secrets.github` keyed by multiple organizations) and (b) at least one configured organization with no `webhook_secret` set, which `verify_webhook_signature` explicitly treats as "always verified" [9](#0-8) . The default/single-tenant configuration documented in `docs/setup.md` (out of scope) uses one `webhook_secret` for everything, which would make `repository_owner` selection immaterial and eliminate the mismatch. I could not verify from the available index whether multi-org configs without secrets are a realistic/supported production posture, since `docs/setup.md` and deployment guidance are excluded from scope — this materially limits confidence in likelihood.

### Recommendation
Verify the webhook signature using the **same field** the handler will act upon (i.e., derive the verification key strictly from `params.organization.login` for `membership`/organization-scoped events, and from `params.repository.owner.login` only for repository-scoped events), and reject `membership` payloads containing an unexpected top-level `repository` key. Additionally, treat a missing `webhook_secret` for any configured organization as a hard configuration error rather than an implicit "signature verified" bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Could not be fully constructed with confidence: exploitation depends on a specific multi-tenant `secrets.github` configuration (organization list, presence/absence of `webhook_secret` per org) that is not visible in the indexed `test/dummy/config/secrets.yml` or `docs/setup.md` (single-org example only) [10](#0-9) . Conceptually: POST `/webhooks` with `X-Github-Event: membership`, a valid HMAC signed for organization `unsecured-org` (or no secret set for it), and a JSON body containing `{"repository": {"owner": {"login": "unsecured-org"}}, "organization": {"login": "victim-org"}, "team": {...}, "member": {"login": "attacker-login"}, "action": "added"}` — `verify_signature` authenticates against `unsecured-org`, but `MembershipHandler` grants `attacker-login` membership in `victim-org`'s team.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
