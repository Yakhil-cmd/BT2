## Title
`StatusHandler` writes GitHub commit statuses matched only by `sha`, letting any onboarded org forge status updates on another org's commits - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no scoping by repository/stack, while the controller layer only proves that the webhook signature matches *some* org's `webhook_secret`, not that it matches the org owning the commit's stack. This lets any onboarded, unrelated org replay a `status` webhook for a `victim_org` commit SHA and have it accepted and written by Shipit as if it came from the repository that legitimately owns that commit.

## Finding Description
The broken binding is: `Shipit.github(organization: repository_owner).verify_webhook_signature(sig, body)` succeeding for `repository_owner = attacker_org` is treated as equivalent to "this payload is authorized to write status for `victim_org`'s stack/commit," i.e. `attacker_org.webhook_secret_valid == true` is conflated with `victim_org.commit.authorized_writer == attacker_org`. These are not equal.

Path:
1. `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` in the *attacker's own* payload [1](#0-0)  and resolves `Shipit.github(organization: repository_owner)` — i.e., the attacker's own org's `GitHubApp`/`webhook_secret` — then verifies the signature against that org's secret [2](#0-1) . Since the attacker legitimately owns `attacker_org` and controls its `webhook_secret` (it's their own onboarded org), this verification trivially succeeds for a payload the attacker crafted themselves.
2. Once verified, `create` dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw parsed JSON, with no re-validation that the payload's `sha`/repository belongs to that org [3](#0-2) .
3. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is global across the entire `commits` table, not scoped to any repository or stack derived from the signature-verified org [4](#0-3) .
4. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, mutating the commit's status/state for whatever stack that commit belongs to — the victim's stack [5](#0-4) .

Contrast with other handlers such as `PullRequest::ClosedHandler`, which explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope all subsequent operations (`review_stacks`) to that repository [6](#0-5) . `StatusHandler` has no equivalent repository-derived scoping despite accepting `sha` as the only correlation key, and SHA1 values are not namespaced per repository/org — an attacker can trivially learn or guess a victim's commit SHA (commits are often public, e.g., via GitHub itself) and include it in their own signed payload.

Exploit: attacker onboards (or already has) their own org `attacker_org` on the shared Shipit instance with a valid `webhook_secret`. They POST to `/webhooks` with `X-Github-Event: status`, a signature computed with `attacker_org`'s own secret, and a JSON body whose `repository.full_name` is `attacker_org/repo` (satisfying `repository_owner` resolution) but whose `sha` is a known commit SHA belonging to `victim_org`'s stack, and `state` set to e.g. `success`. The controller's signature check passes (it's the attacker's own valid secret), and `StatusHandler` finds and mutates the victim's `Commit` record, changing its `create_status_from_github!`-driven status, which can flip `deployable?`/`blocked?` state and potentially trigger `stack.schedule_merges` or continuous deployment via `schedule_continuous_delivery` on the victim's stack [7](#0-6) .

None of the existing guards prevent this: `verify_signature` only checks that *a* known org's secret matches — it does not check that the org matches the commit's owning stack; `drop_unhandled_event` only checks the handler exists for the event type; the `ExplicitParameters` schema (`params do ... end` in `StatusHandler`) only validates shape/types, not repository ownership; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved at all since this is an unauthenticated webhook path by design.

## Impact Explanation
A payload signed by one org's webhook secret can mutate commit-status state for a completely unrelated org's stack/commit, satisfying "a payload for one repository mutating another's stack, commit, task or team." Because commit status feeds directly into `deployable?`, `blocked?`, and `schedule_continuous_delivery`, this can influence whether the victim's stack proceeds with continuous deployment or is blocked/unblocked — a Critical-severity cross-tenant write with potential to trigger unauthorized deploy behavior. This is repeatable against any commit SHA in the shared Shipit instance's `commits` table, for any org onboarded to that instance, regardless of relationship to the victim.

## Likelihood Explanation
Preconditions: the attacker must control at least one org onboarded to the same shared Shipit instance (with its own legitimately configured `webhook_secret`) — a low bar, since Shipit is explicitly designed to host multiple independent orgs/repos, and the attacker only needs their own repo/org onboarded (which the attacker fully controls as an "unprivileged" GitHub user setting up their own org's webhook). The attacker also needs a target commit SHA belonging to the victim's stack, which is generally discoverable (public commit SHAs, GitHub UI/API, or Shipit's own commit listing UI if visible). No GitHub App private key, `secret_key_base`, or victim's `webhook_secret` is required. This is straightforward and repeatable — a single crafted, self-signed HTTP POST per forged status update.

## Recommendation
Scope `StatusHandler` (and ideally all webhook handlers keyed by `sha`) lookups by the repository derived from the verified webhook payload/org, not by `sha` alone. Concretely: resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (or equivalent), verify it belongs to the same org that signed the request, and restrict `Commit.where(sha: ...)` to `commit.stack.repository == resolved_repository` (or query through `stack.commits.where(sha:)` scoped to stacks under that repository) before applying `create_status_from_github!`.

## Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (extend)
test "status webhook signed by attacker_org cannot mutate victim_org's commit" do
  Shipit.instance_variable_set(:@github, nil) # reset cached config if memoized
  # configure two orgs with distinct webhook_secrets: attacker_org, victim_org
  victim_stack = shipit_stacks(:shipit) # belongs to victim_org repository
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  payload = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/forged',
    repository: { owner: { login: 'attacker_org' }, full_name: 'attacker_org/repo' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, payload)

  post shipit.webhooks_path,
    params: payload,
    headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }

  assert_response :ok

  # Binding under test: attacker_org's valid signature must NOT authorize a write to victim_org's commit.
  victim_commit.reload
  assert_not_equal 'success', victim_commit.status.state,
    "attacker_org's signed payload must not be able to set victim_org's commit status"
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
