### Title
Cross-organization webhook signature confusion allows unauthorized writes to another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with multiple GitHub organizations (the documented multi-org `github:` credentials schema), the webhook HMAC signature is verified using a secret selected from the `repository.owner.login` (or `organization.login`) field of the JSON payload, but the actual repository/stack that gets mutated by the handler is selected independently from the `repository.full_name` field of the same, attacker-controlled payload. Nothing binds these two fields together, so a signature that is valid for organization A's webhook secret can be replayed with a `repository.full_name` pointing at organization B's stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using only the owner login embedded in the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (and thus `webhook_secret`) via `github_app_config`, which is how multi-tenant deployments (see `config/secrets.development.example.yml` multi-org example) associate one HMAC secret per organization: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the entire raw payload to handlers: [4](#0-3) 

Handlers such as `PushHandler` resolve the target stacks purely from `repository.full_name` in the payload, via `Handler#stacks`: [5](#0-4) [6](#0-5) 

There is no code anywhere that checks `payload.dig('repository','owner','login')` (used for signature verification) equals the owner portion of `payload.dig('repository','full_name')` (used for stack resolution). These are two independent fields inside the same attacker-supplied JSON body, and only one of them is bound by the cryptographic signature check in a meaningful way — the check itself only verifies that *some* configured organization's secret matches, not that this organization corresponds to the repository actually referenced by the rest of the payload.

**Broken binding (equality that should hold but doesn't):**
`organization whose webhook_secret authenticated the request == organization that owns the repository/stack being written to`

**Before attacker's request:** For every legitimate webhook, `repository.owner.login` and the owner segment of `repository.full_name` are the same organization, and Shipit's config maps a single secret per org, so the equality naturally holds.

**Attacker's request:** An attacker who is a legitimate member/owner of organization "attacker-org" (which is one of several orgs the operator has configured with `github.attacker-org.webhook_secret` in Shipit, e.g. in a shared/multi-tenant Shipit instance) knows or can compute a valid HMAC signature for that secret. They send a POST to `/webhooks` with:
- `X-Github-Event: push`
- `X-Hub-Signature` computed with `attacker-org`'s known `webhook_secret`
- payload body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`

`verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against attacker-org's real secret, so the request passes. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` — completely unrelated to `attacker-org` — and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, which can trigger commit synchronization and (when `continuous_deployment` is enabled on the victim stack) trigger an unauthorized deploy from an attacker-supplied commit SHA on a repository the attacker has no access to.

This matches the analog pattern of "an organization that authenticated versus the repository that is written": the org used to pick/verify the HMAC secret is never validated to be the same org that owns the repository the payload claims to modify.

### Impact Explanation
High/Critical depending on downstream handler: at minimum this is a cross-repository write (an organization can force sync/state changes on stacks belonging to a repository it does not own), and combined with `continuous_deployment`-enabled stacks or `PushHandler`'s `sync_github` triggering deploy pipelines, it can result in an unauthorized deploy on a victim's stack. This satisfies the "cross-repository writes" / "unauthorized deploy" criteria for Critical/High impact.

### Likelihood Explanation
High in any Shipit deployment that uses the documented multi-organization GitHub App configuration (multiple entries under `github:` in secrets, each with its own onboarded organization and `webhook_secret`). Any org onboarded to such a shared Shipit instance can forge a webhook that references any other onboarded org's repository, since it only needs to know its own secret (which it legitimately possesses as the org's own GitHub App/webhook configurer) and the target's public `full_name`/branch.

### Recommendation
After `verify_signature` succeeds, enforce that the organization whose secret was used equals the owner of the `repository`/`organization` object actually referenced in the payload (e.g., compare `repository.owner.login` against the owner segment of `repository.full_name`, or better, resolve the `Repository` first and confirm it belongs to the verified `organization`) before dispatching to any handler in `WebhooksController#create` / `Handler#stacks`.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the code paths cited above):
1. Configure two orgs in `secrets.github`: `org-a` (attacker-controlled) and `org-b` (victim), each with a distinct `webhook_secret`, per `config/secrets.development.example.yml`.
2. Attacker computes `X-Hub-Signature` using `org-a`'s known webhook secret over a payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": {"login": "org-a"},
    "full_name": "org-b/victim-repo"
  }
}
```
3. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-a")` and validates the HMAC against `org-a`'s secret → passes.
5. `PushHandler#process` resolves stacks from `repository.full_name = "org-b/victim-repo"` and calls `sync_github(expected_head_sha: "<attacker_chosen_sha>")` on `org-b`'s stack — a write the attacker was never authorized to make since they only proved control of `org-a`'s secret, not `org-b`'s. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
