### Title
Formula-in-formula re-evaluation lets attacker-supplied `trigger.data` be interpreted as executable oscript when composing dynamically-generated AA definitions - ([File: aa_composer.js])

### Summary
The Crafty Controller CVE describes a webhook "template" that renders user-supplied input as executable template code (SSTI → RCE). The structural analog in ocore's Autonomous Agents (AA) subsystem is `aa_composer.js`'s `replace()`/`evaluateAA()` machinery, which recursively re-interprets any string that is wrapped in `{ ... }` as oscript and evaluates it with the formula engine [1](#0-0) . This same recursive substitution is applied to `app: 'definition'` message payloads that describe a brand-new AA to be created, exactly as demonstrated in the test suite where a factory AA builds a child AA definition containing literal, unevaluated formula text such as `"{'{trigger.address}'}"` [2](#0-1)  and `"{trigger.initial_address}"` style outputs generated at `init`-time [3](#0-2) . If an AA author concatenates untrusted `trigger.data` (attacker-controlled, since anyone can trigger an AA) into a string that ends up wrapped in curly braces inside a generated `definition` message, that string will later be treated as an oscript formula and evaluated with the full authority of the newly created AA (its own balance, state vars, and outputs) — the oscript-engine equivalent of an SSTI-driven RCE.

### Finding Description
`aa_composer.js`'s `replace()` function walks every field of an AA's message payloads, including nested payloads for `app: 'definition'` (used to define new AAs on the fly). For every string field it calls `getFormula()`, which recognizes a formula purely by delimiter: any string whose first character is `{` and whose last character is `}` is stripped of its braces and the interior text is fed straight into `formulaParser.evaluate()` [4](#0-3) . The comment above `replace()` states explicitly: *"app=definition is also replaced using the current trigger and vars, its code has to generate `{}`-formulas in order to be dynamic"* [1](#0-0) .

This means a factory-style AA's `init` code can legitimately build a whole new AA definition (a JS/oscript dictionary) whose leaf fields are string literals of the form `{...}` — these are placed there verbatim so that, once the object becomes a real `definition` payload, the same `replace()` routine will re-parse them as formulas (see `evaluateAA()` / `replace()`) [5](#0-4) [6](#0-5) . This is precisely how the test-suite "hidden definition" AA is written: its `data` payload fields are the strings `"{'{trigger.address}'}"` and `"{'{trigger.output[[asset=base]]}'}"` [2](#0-1)  — an outer formula (evaluated once, at generation time) whose *result* is a literal string still wrapped in braces, deliberately preserved so it is parsed as a *second*, later formula by the freshly created AA.

Because `getFormula()` recognizes formula text solely by presence of leading/trailing braces with no further sanitization or provenance check, any AA author who is not extremely careful can accidentally (or an attacker can deliberately construct trigger.data to) make raw `trigger.data` content become the *content* of such a bracketed string. For example, an AA whose `init` does something like:
```
$note = trigger.data.text;
$child = ['autonomous agent', {
    messages: [{ app: 'data', payload: { text: '{' || $note || '}' } }]
}];
```
produces a child AA definition whose `text` field equals `"{" + trigger.data.text + "}"`. When that child AA is later triggered (by anyone, including the original attacker), `replace()`'s `getFormula()` check strips the braces and evaluates `trigger.data.text` — fully attacker-controlled text from the original triggering unit — as executable oscript in the context of the child AA (its `balance[...]`, `state_vars`, ability to set `outputs[...]`, call `bounce()`, `response[...]`, etc.) [6](#0-5) . This is structurally identical to a template engine that renders raw user input as template syntax rather than as inert data: the "template" here is the oscript formula text embedded inside curly braces, and the neutralization failure is that `getFormula()`/`replace()` cannot distinguish a legitimately-authored brace-wrapped formula from one whose interior was built by string concatenation with untrusted data.

### Impact Explanation
If exploited by tricking (or if the affected code path is reachable through) an AA that dynamically composes child AA definitions from `trigger.data`, an attacker gains formula-execution capability inside the created AA's own execution context. Depending on the surrounding AA logic this can be leveraged to: redirect `outputs[...]` payment destinations/amounts to attacker addresses (unauthorized spending of AA-held funds), manipulate `state`/`response` vars to corrupt AA accounting, or invoke `bounce()`/other primitives to disrupt intended logic — i.e., concrete fund loss or freezing at the AA level, which the validation rules classify as in-scope AA fund loss.

### Likelihood Explanation
This requires a specific, non-trivial AA authoring pattern: a deployed AA must (a) dynamically construct another AA's `definition` message payload and (b) embed attacker-supplied `trigger.data` inside a string that ends up delimited by `{`/`}` without first evaluating/consuming it. The test suite shows this "double-brace" idiom is a known and intentionally supported feature (factory AAs), meaning AA authors are actively encouraged to write code of this shape, which raises the realistic chance that some deployed AA does so carelessly with attacker-controlled data. However, exploitation depends entirely on third-party AA code, not on ocore's core validation/payment/DAG logic itself, so likelihood is moderate rather than "trivial for any unit poster."

### Recommendation
- In `getFormula()` / `replace()` (`formula/common.js`, `aa_composer.js`), disallow (or explicitly flag) formulas whose delimiting braces were introduced dynamically by a prior formula evaluation result rather than present verbatim in the authored ojson/oscript source, e.g. by tracking a "trusted/authored" bit on template strings vs computed string values, so that computed strings are never re-parsed as formulas.
- Alternatively/additionally, restrict `app: 'definition'` payload generation so any leaf string equal to attacker-influenced trigger data cannot itself be wrapped in `{}` and re-interpreted; e.g., require an explicit escape/quoting operator to produce a literal brace-wrapped string that will *not* be re-evaluated, defaulting to "no re-evaluation" unless the AA author opts in with a distinct construct.
- Add oscript-validation-time (`aa_validation.js`) static analysis that flags/rejects `definition` messages whose generated leaf values are built from `trigger.data`/`params` concatenated with literal `{`/`}` characters, since this pattern is the root cause of the injection.

### Proof of Concept
Not directly runnable without deploying and triggering AAs on a testnet, but the exploitation shape mirrors the existing test at `test/aa_composer.test.js:557-649` ("define new AA and activate it") and `test/aa_composer.test.js:566-576` (hidden-definition double-brace idiom). Replace the hardcoded `"{'{trigger.address}'}"` in `data_poster_hidden_definition` with a formula that instead concatenates raw `trigger.data` content, e.g.:
```
var malicious_factory_aa = ['autonomous agent', {
  init: `{
    $child_aa = ['autonomous agent', {
      messages: [{
        app: 'payment',
        payload: {
          asset: 'base',
          outputs: [{ address: '{' || trigger.data.payload || '}', amount: 1000 }]
        }
      }]
    }];
  }`,
  messages: [
    { app: 'definition', payload: { definition: `{$child_aa}` } },
    { app: 'payment', payload: { asset: 'base', outputs: [{ address: `{objectHash.getChash160($child_aa)}`, amount: 9000 }] } }
  ]
}];
```
A trigger with `data.payload = "trigger.address"` (or any more elaborate oscript expression) causes the newly created child AA's `outputs[0].address` field to be re-parsed and evaluated as oscript when the child AA runs, demonstrating attacker-controlled code execution inside the child AA context via `aa_composer.js`'s brace-based `getFormula()`/`replace()` mechanism [6](#0-5) [4](#0-3) .

**Note on confidence:** I was unable to find any explicit sanitization/allow-list in `aa_validation.js` that specifically prevents `trigger.data`/`params` from flowing into brace-delimited leaf values of a dynamically generated `definition` payload; this analysis is based on the mechanics of `getFormula()`, `replace()`, and the pre-existing "hidden definition" test idiom, not a confirmed exploited unit trace on a live/test network.

```javascript
function getFormula(str, bOptionalBraces) {
	if (bOptionalBraces)
		throw Error("braces cannot be optional");
	if (typeof str !== 'string')
		return null;
	if (str[0] === '{' && str[str.length - 1] === '}')
		return str.slice(1, -1);
	else if (bOptionalBraces)
		return str;
	else
		return null;
}
```
