Confirmed: `ApiClient#check_permissions!` only checks the permission string against the `permissions` array, with no stack-scoping logic at all — that isolation is enforced elsewhere, in `BaseController#stacks`/`#stack`.### Title
CCMenuController#stack bypasses stack-scoped ApiClient authorization by calling unscoped `Stack.from_param!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::StacksController` and the base implementation scope stack lookups by `current_api_client.stack_id` via `BaseController#stacks`/`#stack` [1](#0-0) , but `CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping the `stacks` scoping helper entirely [2](#0-1) . Since `check_permissions!` only checks whether the permission string is present in `permissions`, with no stack binding at all, any `ApiClient` with `read:stack` can read any stack's CCMenu status regardless of its own `stack_id`.

### Finding Description
The binding claimed is: permission checked (`read:stack` generically, via `ApiClient#check_permissions!`) == permission needed (`read:stack` scoped to `current_api_client.stack_id == params[:stack_id]`). Tracing the code confirms this equality is broken specifically in `CCMenuController`.

`ApiClient#check_permissions!` is purely string-based and stack-agnostic: [3](#0-2) 

Stack-scoping is enforced only at the resource-resolution layer, in `BaseController#stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped: [1](#0-0) 

`StacksController` correctly uses this scoped `#stack` (inherited, not overridden) [4](#0-3) , so a stack-scoped `ApiClient` requesting a different `stack_id` via `GET /api/stacks/:id` gets a 404 (record not found in the scoped relation), not the target stack's data.

`CCMenuController`, however, defines its own `#stack` that calls `Stack.from_param!` directly on the model class, not through the `stacks` scoping method: [2](#0-1) 

The `before_action` from `require_permission :read, :stack` [5](#0-4)  only calls `current_api_client.check_permissions!('read', 'stack')`, which never inspects `params[:stack_id]` or `current_api_client.stack_id` [6](#0-5) . So any `ApiClient` scoped to stack A, holding `read:stack`, requesting `GET /api/stacks/B/cc.xml?token=<A's token>` will pass the permission check and `#stack` will resolve to stack B unscoped, returning B's CCMenu XML (deploy status, using `NoDeploy` when B has zero deploys) to an attacker who is only authorized for stack A.

Existing guards do not prevent this: `verify_signature`/webhook guards are irrelevant (this is the token-authenticated API path, not webhooks); `ExplicitParameters` isn't declared on this action; `require_permission!` is generic and stack-agnostic by design, relying on callers to use the scoped `stack`/`stacks` helpers, which `CCMenuController` fails to do.

### Impact Explanation
Any `ApiClient` with `read:stack` permission scoped to one stack can enumerate `/api/stacks/:stack_id/cc.xml` for arbitrary other stacks and read their deploy/rollback status (running state, last deploy id, timestamps), which is cross-tenant unauthorized read of stack state. This matches the "High - unauthenticated read of stack state... across tenants" impact category (here it's cross-*tenant* read, not fully unauthenticated, but the client is not authorized for the target stack). It is repeatable against any stack in the installation, for as many `ApiClient` tokens/targets as the attacker controls or has been issued, and requires no privileged Shipit role — only possession of any valid `ApiClient` token with `read:stack`.

### Likelihood Explanation
Preconditions: the attacker (or a party colluding with them) must possess a valid `ApiClient` token with the `read:stack` permission (issued by a Shipit operator for their own stack), and the target stack must exist. No GitHub secrets, session, or `api_clients_secret` knowledge is required beyond the attacker's own legitimately issued token. This is low-cost and fully repeatable — a simple authenticated HTTP GET with a different `stack_id` in the path.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` helper, matching `StacksController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `Stack.where(id: current_api_client.stack_id)` scoping (when the client is stack-bound) so cross-stack lookups 404 instead of succeeding.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (minitest):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b` (a distinct stack).
2. Create `api_client_a = ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: shipit_users(:walrus), name: 'client-a')`.
3. Create `api_client_b = ApiClient.create!(stack: stack_b, permissions: ['read:stack'], creator: shipit_users(:walrus), name: 'client-b')`.
4. Assert stack_b has zero `deploys_and_rollbacks` (so the `NoDeploy` path is exercised).
5. `get "/api/stacks/#{stack_b.to_param}/cc.xml", params: { token: api_client_a.authentication_token }`.
   - **Expected (secure) behavior**: `assert_response :not_found` (stack_a's client should not see stack_b's status).
   - **Current (vulnerable) behavior**: `assert_response :ok` and response body contains `stack_b`'s project name — demonstrating the binding `current_api_client.stack_id == params[:stack_id]` is never checked.
6. Repeat symmetrically with `api_client_b` requesting `stack_a`'s `cc.xml`, asserting it also unexpectedly succeeds, proving cross-tenant read in both directions.
