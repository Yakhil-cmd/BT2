### Title
Cross-organization team-membership forgery via webhook org/team binding confusion grants unauthorized `Shipit.github_teams` access - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` resolves the GitHub App/webhook secret to use for HMAC verification from an attacker-controlled field in the request body (`repository.owner.login`, falling back to `organization.login`), rather than from the organization that actually owns the `Team` record being mutated. `MembershipHandler#find_or_create_team!` then looks up `Team` purely by GitHub's global `team.id`, with no check that the verifying organization matches `team.organization`, letting an attacker who administers *any* configured org add themselves to a `Team` belonging to a different, victim org.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `organization_that_signed_the_webhook == team.organization` for the `Team` record being mutated. In reality these can diverge.

Path: `WebhooksController#create` calls `verify_signature`, which computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) . Both `repository` and `organization` are attacker-supplied JSON fields with no cross-check against the payload's `team` object. An attacker who administers `attacker-org` (one of several orgs configured under `secrets.github`, per `Shipit#github_app_config`/`github_organizations` [4](#0-3) ) can set `repository.owner.login` (or `organization.login`) to `attacker-org`, sign the body with `attacker-org`'s own `webhook_secret`, and pass signature verification legitimately for their own org.

Once past `verify_signature`, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process` [5](#0-4) . `#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [6](#0-5) . The `github_id` is GitHub's globally unique team ID, unscoped to organization. If a `Team` row with that `github_id` already exists (e.g., imported by `lib/tasks/teams.rake`, or created earlier through legitimate `membership`/`Shipit.github_teams` flows for the real owning org), `find_or_create_by!` hits the **find** branch and the block (which sets `team.organization`) never runs — the existing `team.organization` (the victim org) is left untouched, but the record is still mutated via `team.add_member(User.find_or_create_by_login!(params.member.login))` in `#process` [7](#0-6) .

Existing guards don't stop this: `verify_signature` only proves the payload was signed by *some* configured org's secret, not that it's the org that owns the referenced `Team`; the `ExplicitParameters` schema on `MembershipHandler` validates types/presence only, not organization/team ownership [8](#0-7) ; and `Team.find_or_create_by!` never re-validates `organization` on the find path.

Attacker request: `POST /webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<victim_team.github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"},"repository":{"owner":{"login":"attacker-org"}}}`, signed with `attacker-org`'s `webhook_secret`.

### Impact Explanation
The attacker causes `Membership.create!(team: victim_team, user: attacker_user)` for a `Team` that is a member of `Shipit.github_teams` for a completely different, victim organization/installation. Because `User#authorized?` grants full application access whenever `teams.where(id: Shipit.github_teams.map(&:id)).exists?` is true [1](#0-0) , and `force_github_authentication` blocks/allows the entire app based on this check [2](#0-1) , the attacker escalates from unprivileged internet user to an authorized Shipit user with access to stacks/deploys/tasks gated behind that team, without ever being invited to the victim org. This matches the "High - escalation into `Shipit.github_teams` authorization" category, and is repeatable against any known `github_id` of a `Team` row backing another tenant's authorization, across all orgs configured in the multi-org `secrets.github` deployment.

### Likelihood Explanation
Requires: (1) multi-organization `github:` config (`secrets.github` with 2+ org keys, as documented in "Using Multiple Github Applications" [9](#0-8) ); (2) attacker controls a GitHub org/App installation registered as one of those configured orgs (cheap — GitHub orgs are free to create, and Shipit operators may onboard many customer orgs); (3) a pre-existing `Team` row for the victim's `github_id`, which is created automatically the first time `Shipit.github_teams` is evaluated (`Team.find_or_create_by_handle` in `lib/shipit.rb#github_teams` [10](#0-9) ) or via `lib/tasks/teams.rake`, so in any live multi-tenant deployment the row will already exist. The numeric GitHub team ID is discoverable via GitHub's public/team APIs. No secrets, sessions, or privileged roles are needed — only the ability to send a signed webhook from an org the attacker legitimately administers.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved organization for the request (the one that passed signature verification) matches `team.organization` even on the find branch, and reject/ignore the event (or raise) on mismatch. More robustly, have `WebhooksController#verify_signature` compare the verifying organization against the payload's own `organization.login`/`repository.owner.login` fields consistently, and pass that verified organization into handlers so `Team` lookups can be scoped as `Team.find_or_create_by!(github_id:, organization: verified_organization)` instead of `github_id` alone.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest` or `ActionController::TestCase` matching `test/controllers/webhooks_controller_test.rb` conventions), using a `secrets_double_github_app.yml`-style config with `OrgOne`/`OrgTwo` [11](#0-10) :
1. Seed `victim_team = Team.create!(github_id: 999, organization: 'OrgOne', slug: 'core', name: 'Core')`, and configure `OrgOne` as one of `Shipit.github_teams`.
2. Build `body = { action: 'added', team: { id: 999, name: 'x', slug: 'x', url: 'x' }, organization: { login: 'OrgTwo' }, member: { login: 'attacker' }, repository: { owner: { login: 'OrgTwo' } } }.to_json`.
3. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', OrgTwo_webhook_secret, body)`.
4. `post '/webhooks', params: body, headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }`.
5. Assert `response.status == 200`, `victim_team.reload.organization == 'OrgOne'` (unchanged) while `Membership.exists?(team_id: victim_team.id, user: User.find_by(login: 'attacker'))` is true, and `victim_team.organization != body_organization_login` (`'OrgOne' != 'OrgTwo'`), demonstrating the attacker (via `OrgTwo`) mutated `OrgOne`'s team and thereby gained `Shipit.github_teams` authorization for `OrgOne`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
