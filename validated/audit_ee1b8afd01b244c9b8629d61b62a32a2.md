### Title
Cross-tenant CI status forgery via unscoped `StatusHandler` bypasses `ci.require` gating — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the GitHub App configuration keyed by the `organization` derived from the payload itself, but the handler that actually mutates state — `StatusHandler` — never re-checks that the affected `Commit`/`Stack` actually belongs to that authenticated organization. This breaks the binding "organization that authenticated == repository/stack that is written."

### Finding Description
`WebhooksController#verify_signature` picks the webhook secret to validate the HMAC signature based on `repository_owner`, itself read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

Once verified, the raw payload is dispatched unmodified to registered handlers: [3](#0-2) 

`Shipit.github(organization:)` confirms this engine supports a **multi-organization** GitHub App configuration, each with its own independent `webhook_secret`: [4](#0-3) 

Most handlers correctly re-scope the payload to the repository named in the payload via `Handler#stacks`/`repository_name` (e.g. `PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`): [5](#0-4) [6](#0-5) 

However, `StatusHandler` performs **no repository scoping whatsoever**. It matches purely on commit SHA across the *entire* Shipit instance, spanning all organizations and stacks configured on that instance: [7](#0-6) 

`Commit#create_status_from_github!` then unconditionally records the attacker-supplied `state`/`context`/`description` as a real status on that commit: [8](#0-7) 

This status feeds directly into deploy-gating logic (`deployable?`) and continuous-deployment auto-triggering (`schedule_continuous_delivery`): [9](#0-8) [10](#0-9) 

**Attack path (mirrors the report's binding-violation class — "organization that authenticated ≠ repository being written"):**
1. A Shipit deployment is configured with multiple GitHub organizations, each owning its own GitHub App and `webhook_secret` (the documented multi-tenant schema in `lib/shipit.rb#github_app_config`).
2. Attacker legitimately controls (or has collaborator/write access to) a repository in **OrgA**, one of the onboarded orgs, and uses the real GitHub Statuses API to set a commit status on an arbitrary SHA string in their own repo (GitHub's Statuses API does not require the SHA to be reachable in that repo).
3. Attacker sets `sha` = the SHA of a commit belonging to a **victim stack in OrgB** (also hosted on the same Shipit instance), and sets `state: success`, `context: <the exact `ci.require` context configured for OrgB's stack>`.
4. GitHub delivers the "status" webhook to Shipit's shared `/webhooks` endpoint, correctly signed with **OrgA's** real `webhook_secret`. `verify_signature` resolves `repository_owner` = "OrgA" from the payload, fetches OrgA's app config, and successfully verifies the (genuine) signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no organization/repository check, finds the victim's commit (belonging to OrgB's stack), and writes a forged "success" status for the required CI context.
6. If OrgB's stack requires that CI context under `ci.require`, `deployable?` now returns true for a commit that never actually passed CI — and if `continuous_deployment` is enabled, `schedule_continuous_delivery` will automatically ship it.

### Impact Explanation
This lets an attacker with only legitimate control over one tenant's repository (OrgA) forge CI outcomes and bypass deploy-gating checks for a completely unrelated tenant/stack (OrgB) on the same shared Shipit instance, resulting in an **unauthorized deploy** of a commit that did not pass the required CI checks — the impact bar defined by the rules ("Critical: ... an unauthorized deploy"). No compromise of OrgB's GitHub credentials, Shipit session, or `ApiClient` token is required; the trust boundary broken is purely the assumption that webhook-signature-verified-org == the org/stack the payload is allowed to mutate.

### Likelihood Explanation
Requires a multi-organization Shipit configuration (documented and supported) and requires the attacker to control at least one onboarded repository (a realistic scenario for shared/self-service Shipit deployments serving multiple teams/orgs). Setting an arbitrary SHA via the GitHub Statuses API from a controlled repo is a well-known, low-effort GitHub API behavior, requiring no special privilege beyond repo write access on the attacker's own repository. This is a straightforward, deterministic exploit once the multi-org prerequisite is met — no race conditions, no brute forcing.

### Recommendation
`StatusHandler#process` must scope commits to the repository named in the payload, consistent with `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally, consider validating that the `repository_owner` used to select the webhook secret matches the org actually asserted by the verified GitHub App installation (e.g., cross-check `installation.account.login` against the configured organization) rather than trusting the raw JSON `repository.owner.login`/`organization.login` fields for secret selection.

### Proof of Concept
1. Configure Shipit with two orgs, `orga` and `orgb`, each with distinct `webhook_secret`s (per `lib/shipit.rb#github_app_config`), each owning a stack tracking a repo in their org.
2. As a collaborator on `orga/repo`, call GitHub's Statuses API: `POST /repos/orga/repo/statuses/<orgb-victim-commit-sha>` with `state=success`, `context=<orgb's ci.require context>`.
3. GitHub fires the `status` webhook to Shipit's shared `/webhooks` endpoint, signed with `orga`'s webhook secret.
4. Observe in `WebhooksController#verify_signature` that `repository_owner` resolves to `orga` and the signature check passes (real GitHub signature).
5. Observe `StatusHandler#process` creates a `Status` record on the OrgB commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), because the query is not scoped by `stacks`.
6. If `orgb`'s stack has `continuous_deployment: true` and only this one required CI context, observe `ContinuousDeliveryJob` gets scheduled for a commit that never passed real CI (`app/models/shipit/commit.rb:227-229,281-287`).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
