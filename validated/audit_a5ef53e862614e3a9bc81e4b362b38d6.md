Confirmed: `StacksController#stack` uses the base scoping (`stacks.from_param!`, which filters by `current_api_client.stack_id`), while `CCMenuController#stack` explicitly overrides it with the unscoped `Stack.from_param!(params[:stack_id])`. This is a deliberate divergence from the pattern used elsewhere in the same controller family, confirming the reported bug.

### Title
CCMenu status disclosed to any client with `read:stack` regardless of `stack_id` binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController#stack` resolves the target stack via the unscoped `Stack.from_param!(params[:stack_id])` instead of the base controller's tenant-scoped `stacks.from_param!`. Combined with `require_permission :read, :stack`, which only checks that `current_api_client.permissions` contains the generic string `"read:stack"`, any API client holding that permission — no matter which stack it was issued for — can read the CI status (`cc.xml`) of any other stack.

### Finding Description
The broken binding: the permission that should be checked is `client.stack_id == requested_stack.id AND "read:stack" ∈ client.permissions`, but the code only checks `"read:stack" ∈ client.permissions`, i.e. checked ⊊ needed.

- `require_permission :read, :stack` registers a `before_action` that calls `require_permission!(:read, :stack)` → `current_api_client.check_permissions!(:read, :stack)` [1](#0-0) [2](#0-1) .
- `ApiClient#check_permissions!` only checks membership of the string `"read:stack"` in the client's `permissions` array — it never looks at `stack_id` [3](#0-2) .
- The base controller's default `stack` accessor correctly narrows by tenant via `stacks`, which filters `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped [4](#0-3) . `StacksController` relies on exactly this scoped `stack` method [5](#0-4) .
- `CCMenuController` overrides `stack` to bypass that scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [6](#0-5) .

Exploit flow: an operator issues `ApiClient` A scoped to stack 1 (`stack_id: 1`, `permissions: ["read:stack"]`) for a legitimate integration (e.g., a CI badge for stack 1 only). Client A's holder (or anyone who obtains that token through its intended, narrow scope) sends `GET /api/stacks/2/cc.xml?token=<A's token>` for stack 2, which they were never granted access to. `check_permissions!` passes because the permission string matches; `Stack.from_param!(params[:stack_id])` resolves stack 2 unconditionally; `show` renders stack 2's latest deploy/rollback status (or `NoDeploy` if none) [7](#0-6) . No existing guard (`authenticate_api_client`, `require_permission!`, model validations) checks `stack_id` equality for this controller. The existing test suite for this controller only exercises the "correct" stack and never a cross-stack scenario, so it does not catch this [8](#0-7) .

### Impact Explanation
Any `ApiClient` scoped to one stack but holding `read:stack` can read the build/deploy status (name, activity, last build status/label/time, web URL, lock state) of any other stack in the installation by simply changing the `stack_id` in the URL. This is an unauthenticated-for-that-resource read of stack state across tenants — matching the High-severity category "unauthenticated read of stack state, task streams or deploy output." It is fully repeatable against arbitrary stacks and requires no special conditions beyond possessing any valid, stack-scoped token with `read:stack`.

### Likelihood Explanation
Preconditions are modest but plausible in real deployments: an operator must have issued at least one stack-scoped `ApiClient` (a common pattern for exposing narrow CI-badge integrations, per `stacks_controller` and `stacks` scoping logic in the base controller). Given the note in the rules that the attacker holds no `ApiClient` token, this specific proof requires a token that was legitimately issued to a lower-privileged, stack-scoped integration — the vulnerability is that such a token grants more than intended, not that it can be forged. The attacker cost, once such a token is available (e.g., leaked or held by a semi-trusted integration), is trivial — a single unauthenticated GET request with an arbitrary `stack_id`.

### Recommendation
In `app/controllers/shipit/api/ccmenu_controller.rb`, remove the `stack` override and use the base controller's tenant-scoped `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped client cannot resolve stacks outside its `stack_id`.

### Proof of Concept
```ruby
module Shipit
  module Api
    class CCMenuControllerScopingTest < ApiControllerTestCase
      test "a client scoped to one stack cannot read another stack's cc.xml" do
        stack_a = shipit_stacks(:shipit)
        stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

        client_a = ApiClient.create!(
          creator: shipit_users(:walrus),
          name: 'scoped-a',
          stack_id: stack_a.id,
          permissions: ['read:stack']
        )

        # Binding under test: client_a.stack_id (stack_a.id) == requested stack.id (stack_b.id) -> false
        # Expected: request for stack_b using client_a's token must be rejected (403/404).
        get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

        assert_not_equal client_a.stack_id, stack_b.id
        refute_equal 200, response.status, "stack-scoped client must not read a different stack's CC status"
      end
    end
  end
end
```
Currently this request returns `200 OK` with `stack_b`'s CC status because `check_permissions!` never compares `client_a.stack_id` to the requested stack, and `CCMenuController#stack` bypasses the scoped `stacks` helper, confirming the vulnerability.
