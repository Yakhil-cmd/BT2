### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates every `Commit` row across every stack that shares the payload's SHA, instead of scoping the update to the repository that the verified webhook actually belongs to. Every other handler in the same directory (`PushHandler`, `CheckSuiteHandler`, `PullRequest::OpenedHandler`) explicitly scopes to `Repository.from_github_repo_name(payload.repository.full_name).stacks` before touching any records, but `StatusHandler` does not.

### Finding Description
The binding that should hold: `payload.repository.full_name == the single repository whose Commit rows are updated` (cardinality 1). The actual code in `app/models/shipit/webhooks/handlers/status_handler.rb`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

never touches `repository_name`/`stacks`, unlike its siblings:
- `PushHandler#process` uses `stacks.not_archived.where(branch:)` [2](#0-1) 
- `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` before touching commits [3](#0-2) 
- `Handler#stacks` derives strictly from `payload.dig('repository', 'full_name')` [4](#0-3) 

The DB schema also proves SHA is not globally unique: the unique index is `(sha, stack_id)`, not `(sha)` alone, confirming the same SHA is expected to legitimately exist in multiple stacks simultaneously (e.g. a tracked upstream repo and a tracked fork sharing history) [5](#0-4) .

`WebhooksController#verify_signature` only authenticates that the payload's signature matches the GitHub App secret for `repository_owner` (`payload.repository.owner.login`) — it never checks that the SHA being mutated actually belongs to that repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
``` [6](#0-5) 

Exploit flow: an attacker who owns/administers a repository that Shipit tracks as its own stack (fork of, or otherwise sharing git history with, a victim's tracked repository) can, using ordinary GitHub permissions on their own repo (e.g. the GitHub Statuses API), set a `success` status on a commit SHA that is shared history with the victim repo (e.g. a common ancestor commit before the fork point, or a commit cherry-picked/merged into both). GitHub delivers this as a real, validly-signed `status` webhook for the attacker's org/repo. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, which matches the `Commit` row in the attacker's own stack AND the identical-SHA `Commit` row belonging to the victim's unrelated stack, and calls `commit.create_status_from_github!(params)` on all of them. This writes a `Status` for the victim's commit, and via `Commit#add_status` / `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [7](#0-6)  can flip the victim commit to `deployable?`, potentially unblocking automatic/continuous deploys via `schedule_continuous_delivery` [8](#0-7) .

None of the existing guards prevent this: `verify_signature` validates the org that sent the webhook, not the stacks the update lands on; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository scoping; no model validation ties `Status#create` to the requesting repository.

### Impact Explanation
A payload verified for one repository (the attacker's own tracked repo/org) causes a `Status` record to be written for, and `deployable?` state to change on, `Commit` rows belonging to every other stack that happens to share that SHA — a payload for one repository mutating another's stack/commit. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and can lead to an unauthorized deploy being unblocked on a completely unrelated tenant stack. The blast radius scales with N — every tracked stack sharing that SHA is affected by a single webhook POST.

### Likelihood Explanation
Preconditions: the attacker must control (own or administer) at least one repository that is itself tracked as a Shipit stack, and there must exist a SHA shared between that repo's history and a victim stack's tracked repo's history — a common and realistic scenario for forks of tracked upstream repositories, or repos that share submodule/subtree history. No Shipit secrets, sessions, or GitHub App keys are needed; the attacker only uses legitimate GitHub API/UI actions on a repo they control, which GitHub relays to Shipit as an authentically-signed webhook. This is deterministically repeatable against any SHA shared between stacks.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name` and restrict the `Commit` lookup to `stacks.commits.where(sha: params.sha)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), rather than a global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub calls):
1. Seed two `Stack`/`Repository` fixtures, `attacker_stack` (repo `attacker/fork`) and `victim_stack` (repo `victim/upstream`).
2. Create two `Commit` rows with the identical `sha` value, one under `attacker_stack`, one under `victim_stack`, both currently not `deployable?` (e.g. no passing status, `stack.ignore_ci?` false).
3. Build a `status` webhook payload: `{ sha: <shared_sha>, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/fork', owner: { login: 'attacker' } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is orthogonal to this bug and legitimately passes for the attacker's own org).
5. Assert on both sides of the binding:
   - `victim_stack.commits.find_by(sha: shared_sha).statuses.count` increased (expected: 0 if properly scoped; actual: 1).
   - `victim_stack.commits.find_by(sha: shared_sha).deployable?` is `true` (expected: `false`, since the payload's repository is `attacker/fork`, not `victim/upstream`).
   - `attacker_stack.commits.find_by(sha: shared_sha).deployable?` is also `true` (expected side effect, confirming legitimate update path still works).
