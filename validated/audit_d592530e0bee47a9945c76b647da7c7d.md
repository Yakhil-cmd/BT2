### Title
Webhook signature verification selects the trust boundary (GitHub organization/secret) from the same unverified payload used to determine the repository/team acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which HMAC secret) is used to validate `X-Hub-Signature` by reading `repository.owner.login` / `organization.login` straight out of the *unverified* JSON body. If the resolved GitHub App config has no `webhook_secret` set, `GithubApp#verify_webhook_signature` unconditionally returns `true`, skipping verification entirely. Because the field used to pick the trust domain (`repository_owner`) and the fields the downstream handlers use to decide *what to act on* (`repository.full_name`, `member.login`, team info, etc.) come from the same attacker-supplied JSON, an attacker can pick an organization name whose app config has a blank secret to sail through `verify_signature`, while still supplying arbitrary `repository`/`membership`/`team` data that the handler will act on for a completely different, actually-tracked organization/stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [1](#0-0) 

`repository_owner` is derived purely from the untrusted request body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GithubApp#verify_webhook_signature` is a no-op if no secret is configured for that resolved organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

`webhook_secret` is optional and documented/shipped as `nil` by default, both in the single-org and multi-org configuration examples: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization whose secret authenticates the request == organization/repository the handler subsequently mutates state for`. Because both sides are read from the same forgeable JSON body, and the org used for authentication can be freely chosen by the attacker (picking one with no configured secret) while the org/repo/team acted upon by the handler is a separate field in the same body, the two are not actually bound together. The `create` action then dispatches unconditionally once `verify_signature` passes:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

For example, the `membership` event handler creates/deletes `Membership` records straight from the payload's `team`/`member` data, as shown by the controller's own test coverage: [7](#0-6) 
Team membership is exactly the authorization primitive gated by `Shipit.github_teams` for OAuth login.

### Impact Explanation
An unauthenticated attacker who knows (or can guess) the name of any GitHub organization configured in this Shipit instance's `github:` block that has an empty `webhook_secret` (the documented default) can:
1. Set `repository.owner.login` (or `organization.login`) to that "no-secret" organization to make `verify_signature` pass regardless of the actual `X-Hub-Signature` header.
2. Populate the rest of the JSON body (`repository.full_name`, `membership`/`team`/`member` fields, `push`/`status`/`check_suite` payloads) to target any repository/stack/team actually tracked by the instance — including ones belonging to organizations that *do* have a real webhook secret.

This can be used to forge `membership` events that add the attacker's own GitHub login to a `Shipit.github_teams`-authorized team, an explicit escalation into repository/team authorization; or forge `status`/`check_suite` events to fabricate green CI status on arbitrary commits, or forge `push` events to trigger sync jobs against arbitrary tracked stacks — all without holding any session, API token, or the real webhook secret.

### Likelihood Explanation
Requires only that the Shipit deployment has at least one configured GitHub organization (or the single default one) with no `webhook_secret` set — which is the value shown in every shipped example config (`config/secrets.development.example.yml`, `docs/setup.md`, `test/dummy/config/secrets.yml`, `test/dummy/config/secrets.test.json`) — combined with the ability to send an arbitrary HTTP POST to `/github/webhooks` with a spoofed `X-Github-Event` header, both of which are unauthenticated, publicly reachable operations.

### Recommendation
Do not select the verification secret (or organization) from the unverified request body before the signature has been checked. Instead:
- Require `webhook_secret` to be present for every configured GitHub App/organization (fail closed, not open, when absent), and/or
- Verify the signature against every configured secret / a single canonical instance secret rather than one chosen by an attacker-controlled field, and/or
- After signature verification succeeds for organization `O`, assert that every repository/organization/team reference acted upon within the payload actually belongs to `O` before invoking handlers.

### Proof of Concept
1. Configure (or find a Shipit instance configured, per the documented multi-org example) an organization `no-secret-org` with `webhook_secret: nil`, while `victim-org` has stacks tracked and a real secret configured.
2. Send:
```
POST /github/webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything-invalid

{
  "action": "added",
  "team": {"id": 1, "name": "privileged-team", "slug": "privileged-team", "url": "https://example.com"},
  "organization": {"login": "no-secret-org"},
  "repository": {"owner": {"login": "no-secret-org"}},
  "member": {"login": "attacker-github-login"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
4. `MembershipHandler` runs and creates a `Membership` for `attacker-github-login` on `privileged-team`, as demonstrated by `test/controllers/webhooks_controller_test.rb:142-149,159-165`, granting the attacker whatever access that team confers via `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
