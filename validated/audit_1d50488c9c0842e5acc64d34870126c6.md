### Title
Uncaught `throw Error` in oscript `ifelse` evaluation reachable from attacker-controlled AA/definition formulas causes node process crash - (File: `formula/evaluation.js`)

### Summary
CVE-2016-9394 describes JasPer crashing via an unchecked `assert()` triggered by crafted input dimensions in `jas_seq2d_create`, i.e. an attacker-supplied file reaches a code path that assumes an invariant which is not actually guaranteed, and the process aborts. The closest reachable analog in `ocore` is a `throw Error(...)` statement inside the oscript/AA formula evaluator (`formula/evaluation.js`) that is used instead of the evaluator's normal `setFatalError()` error-handling convention. Everywhere else in `evaluate()`, invalid/unexpected values from attacker-supplied formulas are handled gracefully via `setFatalError()`, which safely resolves the callback with a formatted error. A few spots break this pattern and directly `throw`, which — because `evaluate()` is invoked from deep, asynchronous callback chains (`async.eachSeries`, `setImmediate`, etc.) — is not caught by any surrounding `try/catch`, and results in an uncaught exception on the node process, i.e. a crash/DoS, similar in nature to the assertion-failure crash in the CVE.

### Finding Description
`formula/evaluation.js`'s `evaluate()` function is the interpreter for oscript formulas used both in address definitions (`in filter`, `formula` case) and AA definitions/triggers. It is explicitly designed so that any "bad" value coming from evaluating attacker-controlled formula code goes through `setFatalError()`, which safely terminates evaluation and calls back with an error instead of throwing: [1](#0-0) 

However, several branches inside `evaluate()` bypass this convention and use a raw `throw Error(...)` on values that are influenced by the content of the formula/trigger data being evaluated, for example in the `ifelse` case: [2](#0-1) 

and in `evaluateFunctionExpression`/`checkMaxRemoteComplexity`: [3](#0-2) 

These `throw` statements execute inside asynchronous callback chains (`evaluate(test, function(res){...})`, itself invoked via `async.eachSeries`/`setImmediate` deeper in the call graph). A synchronous `throw` inside such an async callback is not caught by any calling `try/catch` further up the stack (Node.js callback-based control flow does not propagate exceptions to callers), so it becomes an uncaught exception, which by default crashes the Node.js process.

This formula evaluator is reachable from:
- Address definitions containing `['formula', ...]` expressions evaluated during authentifier checks, reachable by any unit poster whose unit exercises such a definition (`definition.js` calls `formulaParser.evaluate` at the `'formula'` case).
- AA trigger/getter evaluation (`aa_composer.js`'s `evaluateAA`/`replace`, and `formula/evaluation.js`'s `callGetter`), reachable by anyone who can send a trigger unit to a deployed AA, or by an AA author crafting formulas that call untrusted remote AAs/getters.

An attacker who controls or influences the formula being evaluated (either directly as an AA author, or indirectly via crafted trigger/data-feed values consumed by formula logic) can attempt to drive one of these unguarded throw sites to fire, producing an uncaught exception and crashing the validating node process — the functional equivalent of the JasPer assertion-failure DoS: a document controls program flow and slips through an assumption that the surrounding code presumed could never be reached, causing an abnormal process termination instead of a graceful error result.

### Impact Explanation
An uncaught exception in Node.js terminates the process by default. If a full/hub node crashes while validating a posted unit or executing an AA trigger, this is a denial-of-service against that node: it stops confirming new units until restarted, and if triggered broadly (e.g. via a widely propagated unit or a popular AA that many nodes execute triggers/getters for), it can affect many nodes simultaneously, matching the "network unable to confirm new units" impact bar. This matches the CVSS profile of the CVE (local/AC:L/PR:N/UI:R, availability-only impact via crash) mapped onto ocore's threat model as "a single posted unit/trigger crashes the processing node."

### Likelihood Explanation
The likelihood depends on whether an attacker can actually reach the specific `typeof res === 'object'` branch in `ifelse`, or an inconsistent `max_remote_complexity`/getter-`complexity` type mismatch in `checkMaxRemoteComplexity`, given the surrounding guards (`wrappedObject` is converted to `true` before the check, `Decimal` is converted to boolean, and `isValidValue(res)` is checked earlier). Based on the available code, it is not proven with certainty which exact malformed value can still be `typeof 'object'` at that point (e.g. a bare `null`) or which formula path can cause `props.complexity` in `storage.readAAGetterProps` to not be a number — this would need further tracing through `isValidValue()`, the parser grammar, and `storage.readAAGetterProps`'s DB schema guarantees to determine an exact PoC input. I could not fully confirm a concrete crafted formula string that reaches these unguarded throws within the scope of this analysis; this should be validated with a live formula-evaluation test harness.

### Recommendation
Replace the raw `throw Error(...)` calls in `formula/evaluation.js`'s `evaluate()` (and its nested helpers such as `checkMaxRemoteComplexity`, `evaluateFunctionExpression`) with `setFatalError(...)`/`cb(...)`-based error handling consistent with the rest of the evaluator, so that any value produced by attacker-influenced formula content cannot cause an uncaught exception. Additionally, wrap top-level AA/definition formula evaluation entry points (`aa_composer.js` handlers, `definition.js`'s `'formula'` case) in defensive `try/catch` around the synchronous portion of `evaluate()` invocation so that any residual unexpected throw is converted into a validation/bounce error instead of crashing the process.

### Proof of Concept
Not fully constructible from static analysis alone: reaching the `typeof res === 'object'` throw in the `ifelse` case, or the type-mismatch throws in `checkMaxRemoteComplexity`, requires a formula string/AST and getter/remote-AA state that bypasses the preceding `wrappedObject`/`Decimal`/`isValidValue` guards. Confirming an exact crafted AA definition + trigger (or address-definition `formula`) that drives execution into one of these unguarded `throw` statements would require running the oscript grammar/parser and evaluator locally (e.g. via `test/formula.test.js` harness) to enumerate values that pass `isValidValue()` yet remain `typeof 'object'`, or to control `props.complexity`/`max_remote_complexity` type mismatches through `storage.readAAGetterProps`. This is noted as an open verification step rather than a demonstrated exploit.
