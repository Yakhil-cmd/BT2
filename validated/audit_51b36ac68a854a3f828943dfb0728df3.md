This confirms the vulnerability. The base `Handler` class provides a `stacks` helper that scopes lookups to the requesting repository via `Repository.from_github_repo_name(repository_name)` [1](#0-0) , and `PushHandler` correctly uses this scoped `stacks` relation [2](#0-1) . `StatusHandler`, however, bypasses this scoping entirely and queries `Commit.where(sha: params.sha)` directly across the whole `commits` table, with no repository filter [3](#0-2) .

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any repository's status webhook mutate another stack's commit state - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository scoping, unlike every other handler (e.g. `PushHandler`) which restricts operations to `Repository.from_github_repo_name(repository_name).stacks`. Any `status` webhook payload, if it references a SHA that also exists as a `Commit` row belonging to an unrelated stack/repository, will write a `Status` onto that unrelated commit, potentially flipping its CI state and triggering auto-deploy/merge/block logic for a stack the attacker never authenticated against.

### Finding Description
The broken binding: the code assumes `commit.stack.github_repo_name == payload['repository']['full_name']` (the authenticated repository), but `StatusHandler#process` never checks or enforces this equality — it only matches on `sha` [3](#0-2) .

Path: `POST /webhooks` → `WebhooksController` (verifies signature against the sending repo's `Repository#webhook_secret`, valid) → dispatches to `StatusHandler.call(payload)` → `Handler#initialize` parses params (only `sha`, `state`, `context`, etc., no repository check) [4](#0-3)  → `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Note `Handler` exposes a `stacks` helper precisely for this purpose — filtering by the payload's own `repository.full_name` — but `StatusHandler` is the one handler that does not use it, in contrast to `PushHandler#process` which does (`stacks.not_archived.where(branch:).find_each { ... }`) [2](#0-1) .

`commit.create_status_from_github!` calls `add_status`, which writes the new `Status`, recomputes `status`, and — if the state transition makes the commit deployable — calls `stack.schedule_merges` and fires `deployable_status`/`commit_status` hooks that can drive continuous delivery (`schedule_continuous_delivery` on the commit, gated by `stack.continuous_deployment?` and `stack.deployable?`) [6](#0-5) [7](#0-6) . If auto-triggered, the resulting deploy task runs under the stack's configured deploy identity (`Shipit.user` when `bot_login` is set), i.e. the attacker never needs any credentials of their own — the write is entirely keyed off matching `sha` in the shared `commits` table, regardless of which repository authenticated the webhook.

Why existing guards don't stop this: `verify_signature` only proves the payload came from the GitHub repo it claims to be from — it does not prove that the `sha` inside the payload is unique to that repository. `ExplicitParameters` validates the shape of `params` (`sha`, `state`, `context`, ...) but has no concept of repository ownership of a commit row. There is no `require_permission!` or `stacks` scoping applied in `StatusHandler`, unlike `PushHandler`. The commits table is a single global table keyed by `sha` (not `(stack_id, sha)` uniqueness enforced at the query layer used here), so any repository able to make GitHub sign a status webhook for a SHA that happens to also be a row in another stack's `commits` table can write to it.

### Impact Explanation
A successful match writes a fabricated `Status` (`context: ci/coverage`, arbitrary `state`) onto a commit belonging to a stack the attacker does not control, potentially unblocking/blocking that commit and, when combined with `continuous_deployment?`, causing an unauthorized deploy/rollback to run under the stack's configured bot identity. This is a payload for one repository mutating another's commit/stack, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The blast radius is limited by the practical difficulty of getting a `sha` collision between the attacker's controlled/observed webhook context and a victim's existing commit row (see likelihood), but the code path itself contains no repository check whatsoever.

### Likelihood Explanation
Preconditions: the attacker must cause GitHub to sign and deliver a `status` webhook whose `sha` matches a row already present in the victim stack's `commits` table (e.g., a shared ancestor/base commit that is common between a fork and upstream, or any scenario where the same commit SHA is recorded as a `Commit` for two different stacks — this can legitimately happen for shared history between a fork and its upstream, both of which may be configured as separate Shipit stacks). No Shipit secrets, sessions, or GitHub App/team membership are required; the attacker only needs to control (or be able to trigger a CI status on) a repository whose commit history overlaps with the victim's tracked SHAs. This is a real, repeatable code defect (missing repository scoping) independent of exact SHA-collision feasibility in any given deployment, and it is a one-line divergence from the fixed pattern used elsewhere (`PushHandler`).

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring `PushHandler`: resolve commits via `stacks` (i.e., `Repository.from_github_repo_name(repository_name).stacks`) and only update `Commit` rows belonging to those stacks, e.g. `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, instead of the bare `Commit.where(sha: params.sha)`.
