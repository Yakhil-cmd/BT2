### Title
Meta-transaction (`DelegateAction`/`NEP-366`) signatures lack chain/network binding, enabling cross-network signature replay - ([File: core/primitives/src/action/delegate.rs])

### Summary
`SignedDelegateAction::verify()` checks a signature over a hash computed purely from the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) plus a fixed NEP-based `MessageDiscriminant`, with no chain/network/genesis identifier included in the signed payload.

### Finding Description
The meta-transaction signing scheme (NEP-366/NEP-461/NEP-483) hashes a `SignableMessage` consisting of a `MessageDiscriminant` (a constant derived only from the NEP number, e.g. `366`) and the `DelegateAction` struct itself: [1](#0-0) 

The `SignableMessage` construction and its discriminant derivation contain no chain-specific data (no genesis hash, no network id, no chain id equivalent) — only a NEP number and on-chain/off-chain flag: [2](#0-1) 

The signed `DelegateAction` struct itself also carries no chain-binding field: [3](#0-2) 

This mirrors the reported Hermez bug class precisely: `_checkSig` binds a signature only to application-level data (the babyjub key) without binding it to the deploying contract address or `chainId`, so the same signature validates identically across any deployment/fork. In nearcore, a `DelegateAction` signature validates identically on any NEAR-protocol-compatible network (mainnet, testnet, a private fork, or a copy of a network state) as long as:
- the same `sender_id` account exists there with the same `public_key` registered as an access key,
- the access key's on-chain `nonce` still matches the value in the `DelegateAction`, and
- the current block height on that chain is below `max_block_height`.

None of these conditions require the two networks to be the same network — they are conditions that are trivially satisfiable when a user's account/key is duplicated across networks (e.g. testnet vs. mainnet key reuse, a chain fork/mirror as described in `tools/mirror/README.md`, or a "test copy" of a production account state), exactly the scenario described in the report's exploit narrative (Eve tricking Bob into signing on a "test" fork, then replaying on the real chain).

Note that the outer `SignedTransaction` that wraps the `Action::Delegate(SignedDelegateAction)` is signed by the *relayer*, not by the delegate-action signer, and its `block_hash` field only proves freshness of the relayer's own signature on the target chain — it provides no protection for the inner `DelegateAction` signature, since the relayer can freely wrap and resubmit an unmodified `SignedDelegateAction` on any chain where the preconditions above hold.

### Impact Explanation
If a user signs a `DelegateAction` intending it for use on one NEAR network/deployment (e.g., a testnet, a sandbox/fork, or a "mirrored" chain as supported by `tools/mirror`), and that user's account/access-key state (same `sender_id`, `public_key`, and nonce) exists identically on another network, any party who observes the signed `DelegateAction` can wrap it into a transaction and submit it to the other network, causing the sender's actions (transfers, key additions, function calls, etc.) to execute there without further authorization from the sender. This can result in unauthorized state/balance changes on a network the user never intended to interact with — directly analogous to the Hermez babyjub-association replay scenario where a signature intended for a test deployment is reused on the real one.

### Likelihood Explanation
This requires that a user's account and access key actually be duplicated (same `sender_id` + `public_key` + matching nonce) across two networks, which is a real but non-default scenario: it occurs naturally when developers reuse the same key across mainnet/testnet, or when using chain-forking/mirroring tooling (`tools/mirror`) that explicitly discusses forking chain state and remapping keys. The report's own exploit scenario is exactly this pattern (fork + social engineering to get a victim to sign in a context the victim believes is low-stakes). This is a design-level gap rather than a one-off implementation bug, and it is reachable purely through a normally-submitted RPC transaction with no privileged/validator access required.

### Recommendation
Add a chain-binding value (e.g., the network's genesis hash or a configured chain id) into the `SignableMessage`/`DelegateAction` signing payload used in `SignedDelegateAction::sign`/`verify` (`core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`), so that a `DelegateAction` signature is only valid for the specific chain/network it was created for. This should be versioned similarly to how `DelegateActionV2`/`VersionedDelegateActionPayload` already isolate signing domains by discriminant, to avoid breaking existing protocol behavior. Longer term, any new on-chain signature scheme built on `SignableMessage` should mandatorily include a chain/network identifier by convention, not just an action-type discriminant.

### Proof of Concept
1. Deploy/observe two NEAR-protocol-compatible networks (e.g., mainnet and a forked/mirrored network created via `tools/mirror`, or a testnet where the victim reuses their mainnet key) such that account `alice.near` exists on both with the same `public_key` and access-key nonce.
2. Alice signs a `DelegateAction{sender_id: "alice.near", receiver_id: "attacker.near", actions: [Transfer...], nonce: N, max_block_height: H, public_key: alice_pk}` via `SignedDelegateAction::sign`, believing it is scoped to the "test" network. [4](#0-3) 
3. An attacker who obtains this `SignedDelegateAction` wraps it, unmodified, as `Action::Delegate` inside a new `SignedTransaction` signed by their own relayer key, and submits it to the other network (e.g., mainnet) via RPC.
4. Because `SignedDelegateAction::verify()` only checks the signature against `get_nep461_hash()`, which is chain-agnostic, and the runtime's `apply_delegate_action` only additionally checks nonce/`max_block_height`/receiver-match (not any chain identifier), the delegate action executes successfully on the second network if Alice's account state there still matches, moving real funds from Alice's mainnet account to the attacker without Alice's intended authorization on that chain.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
