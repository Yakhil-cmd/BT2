### Title
Cross-stack commit status forgery via unscoped `sha` lookup in `StatusHandler` breaks the "authenticated repository vs. written repository" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook to a specific GitHub organization/repository by checking `X-Hub-Signature` against that organization's `webhook_secret`, using `repository_owner` extracted from the payload to pick the right `GithubApp` secret. However, once the signature check passes, the `status` event is dispatched to `Shipit::Webhooks::Handlers::StatusHandler`, which processes the event's `sha` field against **every** `Commit` in the database, irrespective of which stack/repository the commit belongs to. The equality the system is supposed to enforce — "organization that authenticated == repository that gets written" — is broken: the signature only proves the payload came from *some* onboarded repository/org, but the write (`commit.create_status_from_github!`) is applied to any commit anywhere in the Shipit instance whose `sha` matches the attacker-chosen value in the payload body.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload and looks up the matching `GithubApp`/secret to validate the HMAC signature: [1](#0-0) [2](#0-1) 

This proves the request was legitimately signed by *an* organization/app installed on the Shipit instance — but says nothing about which repository's commits the payload is allowed to affect. The `status` event handler then processes the request: [3](#0-2) 

Note that `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on `stack_id`, `repository`, or the org that authenticated the webhook. In a Shipit deployment onboarding multiple organizations/repositories with independent GitHub Apps and webhook secrets (as documented in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`), any attacker who controls (or is a member of) **one** onboarded repository/org can send a validly-signed `status` webhook whose `sha` field is set to an arbitrary 40-hex string copied from a **different**, unrelated stack's commit (SHAs are public git metadata, easily obtainable from the target repo's commit history or Shipit's own commit view). Because the handler never checks that the sha actually belongs to a commit in the authenticated org's repository, the forged status is applied to the foreign commit.

A forged `success` status directly affects deploy gating: [4](#0-3) 
and status creation schedules continuous delivery: [5](#0-4) [6](#0-5) 

Tests confirm that creating a `success` `Status` record triggers deploy scheduling logic when continuous deployment is enabled: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who is a legitimate member/webhook source for repository A can forge a `success` (or any state) CI status on a commit belonging to unrelated repository B/stack B, as long as they know B's commit SHA (public information). If stack B has `continuous_deployment` enabled, this can trigger an **unauthorized automatic deploy**. Even without continuous deployment, it removes the CI gate (`deployable?`) that operators rely on before manually deploying, letting an attacker mark a failing/unreviewed commit as "success" and enabling an operator (or the merge queue) to ship it. This matches the Critical impact category "unauthorized deploy."

### Likelihood Explanation
Exploitation requires only that the attacker control (or compromise) one onboarded repository/organization on the shared Shipit instance — a much lower bar than compromising the target stack's own repository, GitHub App, or a Shipit session/API token. Multi-organization Shipit deployments are an explicitly supported and documented configuration, making this a realistic scenario for larger Shipit installations serving multiple teams/repos.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository/organization that the verified webhook belongs to (e.g., resolve the target `Stack`/`Repository` from the authenticated `repository.full_name` in the payload and constrain `Commit.where(sha: params.sha, stack: stack)` or filter `commit.stack.repository == authenticated_repository`), rather than matching `sha` globally across all stacks.

### Proof of Concept
1. Attacker is an admin of `attacker-org/attacker-repo`, which has the Shipit GitHub App installed with its own valid `webhook_secret`.
2. Attacker computes a valid HMAC-SHA1 signature for a crafted `status` event JSON body using their own repo's `webhook_secret`, with:
   - `repository.owner.login = "attacker-org"` (so signature verification picks the attacker's own secret and succeeds)
   - `sha = "<known sha of a commit in victim-org/victim-repo's stack>"`
   - `state = "success"`
3. POST this to `/webhooks` with header `X-Github-Event: status` and the valid `X-Hub-Signature`.
4. `WebhooksController#verify_signature` succeeds (signed with attacker's own valid secret).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (regardless of stack/org), and calls `create_status_from_github!`, creating a forged `success` status on the victim's commit — potentially unblocking or auto-triggering a deploy on the victim's stack.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
