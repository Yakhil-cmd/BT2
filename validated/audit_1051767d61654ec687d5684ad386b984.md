### Title
Operator-precedence bug bypasses `review_stacks_enabled` gate, allowing unauthorized auto-provisioning (deploy) of PR review stacks - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
The intent of `Repository#review_stacks_enabled` is to be a master switch that must be `true` before *any* pull-request-driven review-stack provisioning logic runs, regardless of which `provisioning_behavior` (`allow_all`, `allow_with_label`, `prevent_with_label`) is configured. Because of Ruby operator precedence (`&&` binds tighter than `||`), the guard is only actually applied to the `allow_all` branch. The `allow_with_label` and `prevent_with_label` branches execute independently of `review_stacks_enabled`, so a repository owner who disables review-stack provisioning while using either of those two behaviors gets no protection: any pull request opened/reopened against the tracked repository still triggers automatic review-stack creation (i.e., an automated deploy of the PR's branch).

### Finding Description
`respond_to_pull_request_opened?` gates on `provision?`: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?)`, not `review_stacks_enabled && (allow_all? || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?))`. Whoever wrote this clearly intended `review_stacks_enabled` to be a top-level `&&` that qualifies the entire disjunction — this mirrors the Set.sol pattern where a caller/authorization condition (`caller_ != owner`) was meant to jointly gate the whole branch but a boolean operator error left an alternate path unguarded.

The identical bug is duplicated in the reopen handler: [2](#0-1) 

Confirmation that this is untested/unintended: the only regression test that sets `provisioning_enabled: false` uses `behavior: :allow_all` — the one branch the code accidentally still protects: [3](#0-2) 
There is no test covering `provisioning_enabled: false` combined with `behavior: :allow_with_label` or `:prevent_with_label`, which is exactly the missing regression test the external report recommends for this bug class.

`Repository#review_stacks_enabled` and `#provisioning_behavior_*` predicates are defined here: [4](#0-3) [5](#0-4) 

The binding that is broken: `review_stacks_enabled == true` should be required for `provision?` (and `unarchive?` in the reopen handler) to ever return `true`, but the actual code only enforces `review_stacks_enabled == true` for the `allow_all` sub-clause; the `allow_with_label` and `prevent_with_label` sub-clauses are reachable when `review_stacks_enabled == false`.

### Impact Explanation
When a repository administrator sets `review_stacks_enabled = false` (intending to fully disable auto-provisioning) while `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, any GitHub user able to open (or reopen) a pull request against the tracked repository — an unprivileged, external contributor on a public repo — will still cause Shipit to automatically create and provision (deploy) a review stack for that PR's branch via `ReviewStackAdapter#find_or_create!` and `ReviewStackProvisioningQueue.add(stack)`: [6](#0-5) [7](#0-6) 

This is an unauthorized deploy of attacker-influenced code/branch content that the repository owner explicitly tried to disable, satisfying the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Exploitation requires no special credentials — only the ability to open a pull request (and, for `allow_with_label`, to have the trigger label applied, which for `prevent_with_label` is not even needed since the default no-label state is the triggering condition). The webhook signature is validated normally on genuine PR events from GitHub, so this isn't a signature-forgery attack; it's a logic flaw reachable through the normal, legitimate webhook flow whenever a repo is configured with `review_stacks_enabled: false` plus `allow_with_label`/`prevent_with_label`. Likelihood is moderate — it depends on that specific (but plausible) configuration combination, matching the "moderate risk" categorization of the original external report.

### Recommendation
Fix operator precedence by making `review_stacks_enabled` explicitly gate the whole expression:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

Apply the same fix to `unarchive?` in `reopened_handler.rb`. Add regression tests covering `review_stacks_enabled: false` combined with each of `allow_with_label` and `prevent_with_label`, asserting no stack is created/unarchived.

### Proof of Concept
1. Repository owner configures: `review_stacks_enabled = false`, `provisioning_behavior = "prevent_with_label"`, `provisioning_label_name = "no-deploy"`.
2. An external contributor opens a pull request without the `no-deploy` label (the normal case for most PRs).
3. GitHub sends a legitimate, correctly-signed `pull_request` `opened` webhook.
4. `OpenedHandler#provision?` evaluates: `(false && provisioning_behavior_allow_all?)` → `false`, but `(prevent_with_label? && !label_present?)` → `true`, so `provision?` returns `true` despite `review_stacks_enabled` being `false`.
5. `ReviewStackAdapter#find_or_create!` creates a new `Stack` and `ReviewStackProvisioningQueue.add(stack)` schedules provisioning — an unauthorized automated deploy of the PR branch, exactly what the owner intended to prevent by disabling `review_stacks_enabled`.
