### Title
Unhandled exception during dry-run AA trigger execution leaks the per-author validation mutex lock, permanently blocking confirmation of a poster's units - ([File: network.js])

### Summary
`network.js`'s `handleJoint()` passes an `async` function as the `ifOk` callback to `validation.validate()`. That callback runs an unawaited-for-errors dry-run of any AA trigger contained in the newly-validated unit before calling `validation_unlock()`. If AA formula evaluation throws a JS exception instead of resolving through the normal bounce mechanism, the exception propagates out of the `async ifOk` function as an unhandled rejection, and `validation_unlock()` is never invoked — permanently leaking the author-address mutex lock acquired inside `validation.validate()`.

### Finding Description
`validation.js` locks the unit's author addresses for the whole duration of validation: [1](#0-0) 
and only releases that lock via the `unlock` function it hands to the success callback: [2](#0-1) 

`network.js`'s `handleJoint()` consumes this callback as `ifOk`, an `async` function. When `conf.bDryRunNewTriggers` is enabled and the incoming unit pays into an AA address, it `await`s a dry run of the primary AA trigger *before* the code path that eventually calls `validation_unlock()` inside `writer.saveJoint`'s callback: [3](#0-2) 

The dry run goes through `aa_composer.dryRunPrimaryAATrigger` → `handleTrigger` → `evaluateAA` → `formula/evaluation.js`'s `evaluate()`. That evaluator contains numerous unconditional `throw Error(...)` statements for conditions that are not routed through the `bounce()`/`cb(err)` error-callback mechanism, e.g.: [4](#0-3) [5](#0-4) 
and `aa_composer.js`'s `handleTrigger`/`pickParents`/entry checks also throw directly rather than calling `bounce`: [6](#0-5) [7](#0-6) 

None of these throws are caught anywhere between `dryRunPrimaryAATrigger` and the `await` in `network.js`'s `ifOk`: [8](#0-7) 
There is no `try/catch` around the `await aa_composer.dryRunPrimaryAATrigger(...)` call in `network.js`, and `validate()` in `validation.js` calls `callbacks.ifOk(objValidationState, unlock)` without awaiting it (it is a synchronous, callback-based function), so a rejected promise returned by the async `ifOk` becomes an unhandled rejection rather than a caught error.

This is structurally analogous to the CVE-2024-53198 pattern: a resource is acquired on a "probe"-equivalent step (`validation.validate()` locking the author addresses), and on a subsequent failure branch the code returns/throws without performing the matching "remove"/release step (`validation_unlock()`), leaking the resource (the mutex lock).

### Impact Explanation
Because `mutex.js`'s lock/unlock model requires the captured `unlock` closure to be invoked to remove the key array from `arrLockedKeyArrays`: [9](#0-8) 
a leaked lock on the author address(es) of the triggering unit means `mutex.lock(arrAuthorAddresses, ...)` in `validation.js` will queue indefinitely for **any future unit authored by those same addresses** — they can never again be validated/confirmed by this node. This matches the "node disagreement on validity/stability" / "network unable to confirm new units" impact class for the affected address(es): a specific author becomes permanently unable to get further units accepted by the affected node.

### Likelihood Explanation
Reachable by any ordinary, unprivileged unit poster: simply compose and broadcast a unit whose payment output targets a deployed AA address, where triggering that AA's formula execution reaches one of the numerous unconditional `throw Error(...)` sites in `formula/evaluation.js` or `aa_composer.js` (rather than routing through `bounce()`/error callback). This requires the receiving node to run with `conf.bDryRunNewTriggers` enabled (not confirmed default in this codebase index — this flag's default value could not be located in the available config files, so its prevalence is uncertain).

### Recommendation
- Wrap the `await aa_composer.dryRunPrimaryAATrigger(...)` call in `network.js`'s `ifOk` in a `try/catch`, and on any thrown error still call `validation_unlock()` (and `unlock()`) before propagating/handling the error, mirroring the pattern already used for the `bPosted` non-serial branch just above it.
- Audit `formula/evaluation.js` and `aa_composer.js`'s `handleTrigger`/`evaluateAA`/`pickParents` for internal-invariant `throw Error(...)` sites that can be reached by attacker-controlled AA definitions/trigger data during a dry run, and convert genuinely attacker-reachable ones into `bounce()`/callback-based errors instead of hard throws.
- More generally, ensure every code path following `validation.validate()`'s `ifOk`/`ifOkUnsigned` callback that acquires the author-address lock has a guaranteed `unlock()`/`validation_unlock()` call on all exception paths (e.g., a top-level `try/finally` around the async `ifOk` body).

### Proof of Concept
1. Deploy an AA whose formula, when triggered under a dry run, reaches one of the un-bounced `throw Error(...)` branches in `formula/evaluation.js`'s `evaluate()` (e.g., a construct that reaches the `default: throw Error('unrecognized op '+op)` branch, or a formula expression whose `ifelse` test evaluates to an object as in `formula/evaluation.js:1471-1472`).
2. Ensure the target node runs with `conf.bDryRunNewTriggers = true`.
3. Post a unit from author address `A` with a payment output to that AA address.
4. On `network.js`'s `handleJoint` → `ifOk`, the `await aa_composer.dryRunPrimaryAATrigger(...)` call throws; the `async` function rejects without ever calling `validation_unlock()`.
5. Any subsequent unit authored by address `A` submitted to this node will hang forever in `mutex.lock(arrAuthorAddresses, ...)` inside `validation.js`, since the earlier lock on `A` was never released — the node can no longer confirm any further units from `A`.

Note: I was unable to confirm the default value of `conf.bDryRunNewTriggers` from the indexed configuration files, so whether this path is enabled by default in production deployments remains unverified.
