### Title
Webhook signature verification binds only the payload's declared organization, not the entity a handler actually mutates — cross-organization team/repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub organization used to look up the correct webhook secret from an **unverified** part of the JSON body (`repository.owner.login` or `organization.login`), and only checks that the HMAC matches *that* secret. [1](#0-0) [2](#0-1)  None of the individual `Webhooks::Handlers` re-validate that the organization/team/repository they actually act on is the same one whose secret validated the signature — for example `MembershipHandler` looks up (or reuses) a `Team` purely by `params.team.id` (the GitHub team's numeric `github_id`), independent of which organization's secret signed the request. [3](#0-2)  This is the same class of bug as FrankenDAO's `castVote`: the signature check "authorizes" one field (`repository_owner`), while a completely different, unbound field (`team.id`/`repository.full_name`) drives the state-changing action — exactly the "organization authenticated vs. entity written" mismatch called out as an in-scope analog.

### Finding Description
- The webhook HMAC covers the *entire raw body*, which is good, but the *secret chosen to verify it* is selected using a value taken straight from that same untrusted body (`repository.owner.login`/`organization.login`), before the signature has been proven valid. [1](#0-0) 
- In a multi-organization Shipit deployment (explicitly supported — see `github: OrgOne: ... OrgTwo: ...` in `secrets_double_github_app.yml`), each organization has its own independent `webhook_secret`. [4](#0-3)  An attacker who legitimately controls a repository in "OrgOne" knows OrgOne's webhook secret (it is configured by the org's own GitHub App admin per `docs/setup.md`). [5](#0-4) 
- That attacker can send a POST to `/webhooks` with `X-Github-Event: membership`, `repository.owner.login`/`organization.login` = `"OrgOne"` (so `verify_signature` fetches OrgOne's `GitHubApp` and the HMAC computed with OrgOne's secret validates), while setting `team.id` to the `github_id` of a **team belonging to a different, victim organization** that Shipit already tracks (e.g., a team named in `Shipit.github_teams`), and `member.login` to their own account.
- `MembershipHandler#find_or_create_team!` looks the team up (or creates it) solely by `github_id`; if the victim team already exists in Shipit's DB (common, since teams are synced from real GitHub membership events), the `organization` attribute is not re-validated against the org that authenticated the current request — the found record is reused as-is. [6](#0-5)  `team.add_member(member)` is then called unconditionally for `action == 'added'`. [7](#0-6) 
- The equality that should hold is: `organization whose secret validated the HMAC == organization/team the handler mutates`. It does not — the controller checks a field (`repository.owner.login`) that is disjoint from the field the handler actually trusts (`team.id`), so any org's secret authorizes writes against any other org's team/repository records known to the Shipit instance.
- The same disjunction exists for `PushHandler` (`repository.full_name` picks which `Stack`s get `sync_github` triggered) and `StatusHandler` (`sha` picks which `Commit`s get a status written), neither of which is cross-checked against `repository_owner`. [8](#0-7) [9](#0-8) 

### Impact Explanation
The membership vector directly escalates into `Shipit.github_teams` authorization: gaining membership of a privileged `Team` record grants access decisions made by `Shipit::Authentication#force_github_authentication`/`current_user.authorized?`, which gate access to the entire application (deploys, rollbacks, stack management). [10](#0-9)  This matches the in-scope High-severity category "escalation into `Shipit.github_teams` authorization." The push/status vectors additionally let an attacker with only one org's webhook secret trigger sync jobs or forge commit statuses against stacks belonging to a completely different, unrelated organization onboarded on the same Shipit instance.

### Likelihood Explanation
Requires only knowledge of one organization's webhook secret — something a legitimate, unprivileged administrator of *any* org connected to a shared/multi-tenant Shipit instance already possesses, with no GitHub App private key, no `api_clients_secret`, and no privileged Shipit account needed. The only precondition is that Shipit be configured for more than one GitHub organization (a documented, supported configuration) or that the victim team/repository already exists in the shared database, both realistic for real deployments.

### Recommendation
Bind the verified organization to every field a handler subsequently trusts:
- In `WebhooksController`, after verifying the signature, pass the verified `repository_owner`/organization down to the handler dispatch, and require every handler (`MembershipHandler`, `PushHandler`, `StatusHandler`, PR handlers, `CheckSuiteHandler`) to assert that `params.repository.owner.login` (or `params.organization.login`) equals the organization that was actually used to validate the signature.
- In `MembershipHandler#find_or_create_team!`, reject (rather than silently reuse) an existing `Team` whose stored `organization` differs from the organization verified for this request.
- Consider deriving the webhook-secret lookup key from a value that cannot diverge from the value later trusted by handlers, e.g., verify against every configured secret and record which organization actually matched, then thread that single verified organization through to all handler logic instead of re-reading independent payload fields.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgOne` (attacker-controlled webhook secret `secretA`) and `OrgTwo` (victim), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Shipit already has a `Team` record with `github_id: 555`, `organization: "OrgTwo"`, referenced in `Shipit.github_teams` for privileged access.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` for:
```json
{
  "action": "added",
  "team": { "id": 555, "name": "Privileged Team", "slug": "privileged", "url": "https://example.com" },
  "organization": { "login": "OrgOne" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "OrgOne" } }
}
```
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the HMAC validates against `secretA` — request passes. [1](#0-0) 
5. `MembershipHandler#find_or_create_team!` finds the existing `Team(github_id: 555)` belonging to `OrgTwo` (no re-check against the verified `OrgOne`), and `team.add_member(User.find_or_create_by_login!("attacker"))` adds the attacker to the victim's privileged team. [3](#0-2) 
6. Attacker now authenticates via normal GitHub OAuth as "attacker" and passes `current_user.authorized?` because of the forged team membership, gaining access gated by `Shipit.github_teams`.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
