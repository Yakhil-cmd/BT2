### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but the target repository is resolved from the unchecked `repository.full_name` field, enabling cross-tenant/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), but every event handler resolves the actual `Stack`/`Repository` to mutate using a *different* payload field, `repository.full_name`. Nothing enforces that `full_name`'s owner segment matches the `repository_owner`/`organization.login` used for signature verification. In a multi-tenant Shipit deployment (documented "Using Multiple Github Applications" setup), an attacker who legitimately controls one configured GitHub organization's webhook secret can sign an arbitrary payload with that secret while setting `repository.full_name` to point at a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance.

Every handler (`PushHandler`, `PullRequest::OpenedHandler/ClosedHandler/...`, etc.) resolves its target Stack/Repository via a *separate* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `owner.login` and `full_name`'s owner segment are two independent JSON leaves inside a single HMAC-signed body, and the signature only proves "this body was signed with the secret belonging to the org named in `repository.owner.login`" — not "this body only concerns repositories owned by that org" — an attacker who knows/controls one tenant's `webhook_secret` can freely set `full_name` to reference a stack under any other organization configured on the same Shipit instance. This is exactly the "organization authenticated vs. repository that is written" binding called out as an analog target: the equality that should hold, `verified_org(payload) == owner(target_repository_written)`, is never checked; only `verified_org(payload) == payload['repository']['owner']['login']` (a self-referential, attacker-controlled equality) holds.

### Impact Explanation
Using a webhook secret from organization A, an attacker can forge a `push` event with `repository.full_name = "orgB/victim-repo"` to enqueue `GithubSyncJob`/`stack.sync_github` for a stack belonging to organization B [7](#0-6) , or forge `pull_request`/`check_suite`/`status` events to archive/unarchive review stacks, write commit statuses, or manipulate merge state for repositories that organization A has no legitimate relationship with. This is a cross-repository/cross-tenant write achieved purely by controlling the signing secret of an unrelated, lower-privileged tenant — matching the Critical impact category "cross-repository writes" and potentially "an unauthorized deploy" if the targeted stack has `continuous_deployment` enabled (not independently re-verified in this pass, since tracing the full sync→deploy trigger chain was not completed within the available tool budget).

### Likelihood Explanation
This requires the attacker to possess a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance (per `docs/setup.md`'s "Using Multiple Github Applications" section) — i.e., legitimate, low-privilege access to *their own* org's GitHub App settings, not any privilege over the victim organization. This is a realistic scenario for SaaS-style or internally shared multi-tenant Shipit deployments where separate teams/orgs each own a GitHub App entry in `config/secrets.yml`.

### Recommendation
When resolving the target repository/stack in `Handler#repository_name`/`stacks` (and in every handler that reads `full_name`), require that the owner segment of `repository.full_name` matches the `repository_owner` value that was used to select the verifying `webhook_secret` in `WebhooksController#verify_signature`. Reject (422) any event where these two do not match, rather than trusting `full_name` unconditionally after verifying only `owner.login`.

### Proof of Concept
1. Shipit is configured with two tenants, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker, who administers `orgA`'s GitHub App, knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-existing-sha-in-orgB-repo>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "orgA"`, loads `Shipit.github(organization: "orgA")`, and the HMAC checks out — the request is accepted.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgB/victim-repo")`, enqueuing `GithubSyncJob` for a stack that belongs to `orgB`, an organization the attacker has no legitimate relationship with — a cross-tenant write triggered entirely by knowledge of `orgA`'s secret.
