### Title
Failed liquidation inside `liquidate-multi` still commits partial repay side-effects, corrupting shared vault debt accounting — ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` maps `call-liquidate` (which invokes `liquidate` by direct in-contract call, not `contract-call?`) over a batch of positions and always returns `(ok (map call-liquidate positions))`, regardless of whether any individual `liquidate` invocation errors [1](#0-0) . Because the transaction's top-level function unconditionally returns `ok`, the whole transaction commits, and cross-contract state changes made by an individual, ultimately-failing `liquidate` call — specifically the `vault-system-repay` step, which pulls tokens from the liquidator and decrements the vault's aggregate `principal-scaled`/`total-borrowed` — are **not** reverted even though that same `liquidate` invocation later fails on `debt-remove-scaled`/`collateral-remove` and never actually reduces the borrower's own recorded debt. This is the exact shape of the reported bug class: a "budget"/ledger (here, vault aggregate debt accounting) is partially consumed before a failure flag is raised, but that flag never propagates to zero out/undo the partial consumption for the parent operation.

### Finding Description
Inside `liquidate`, `vault-system-repay` is executed first, and only afterwards are the borrower-specific `debt-remove-scaled` and `collateral-remove` calls made against `market-vault` [2](#0-1) : [3](#0-2) 
`vault-system-repay` pulls real tokens from `tx-sender` and mutates the vault's shared `principal-scaled`/`total-borrowed` state, which is used for every LP's exchange-rate/valuation, as seen in `system-repay` [4](#0-3) . If the subsequent `debt-remove-scaled` (or `collateral-remove`) call against `.v0-market-vault` fails — e.g. because a duplicated/stale position entry in the same `liquidate-multi` batch tries to remove more scaled debt than the borrower now actually has left after an earlier entry in the same batch already reduced it — that `contract-call?` returns `err`, and `try!` returns `err` out of `liquidate` [5](#0-4) .

Crucially, `liquidate` is invoked from `liquidate-multi` via the private wrapper `call-liquidate`, which is a **direct in-contract call**, not a `contract-call?` [6](#0-5)  (equivalent block also present at [7](#0-6) ). Stacks/Clarity atomically rolls back state changes only for the outermost public function invoked by the transaction (or per `contract-call?` boundary for the callee it wraps) — it does not automatically unwind earlier, already-completed `contract-call?`s just because a later, same-contract function subsequently returns `err`. Since `liquidate-multi`'s own top-level return is unconditionally `(ok ...)`, per the explicit design comment "Failed liquidations return error codes but don't revert entire batch" [1](#0-0) , nothing about the transaction gets rolled back, and the already-committed `vault-system-repay` effects for the failing entry persist.

This is the direct analog of the OVM `_useNuisanceGas` bug: the sub-operation's budget consumption (tokens pulled, vault aggregate debt decremented) happens before the failure is detected, and the failure flag (the `err` captured in the returned list) is never used to zero out / undo that partial consumption for the enclosing batch operation.

### Impact Explanation
The vault's aggregate `principal-scaled`/`total-borrowed` — shared state consumed by every LP's redemption/valuation math — gets decremented for a repay that was never matched by an actual reduction of the borrower's real, per-account scaled debt in `market-vault` (that specific `debt-remove-scaled` call failed and rolled back only its own boundary). This creates a permanent desynchronization between the vault's aggregate debt bookkeeping and the sum of real borrower obligations tracked in `market-vault`. When the affected borrower's remaining recorded debt is eventually repaid in full through normal channels, the vault will be repaid/decremented again for debt that its aggregate counters already believe was settled, permanently misstating `total-borrowed`/`total-debt()` used in the zToken exchange-rate calculation for **all other depositors** of that vault. This is an unprivileged-caller-harms-unrelated-parties scenario (other LPs / vault solvency), landing on **Critical — protocol insolvency / permanent freezing of funds** for vault depositors, since zToken share pricing becomes permanently decoupled from real backing.

### Likelihood Explanation
The attacker only needs to submit a single `liquidate-multi` transaction containing at least two entries that target overlapping/stale state for the same `(borrower, debt-asset)` pair (e.g., duplicate entries, or entries computed to intentionally conflict once the first entry's effects apply mid-batch) — no special privileges, DAO action, or oracle manipulation is required, and `liquidate-multi` is a normal permissionless public entry point.

### Recommendation
Do not swallow per-position errors silently in `liquidate-multi`. Either (a) wrap each `call-liquidate` invocation so that a failing entry's `try!`-triggered error causes the ENTIRE transaction to abort (forcing atomic all-or-nothing batches), or (b) if partial batch success is a deliberate design goal, refactor `liquidate` so that all state-mutating steps (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) are only committed after every validation for that specific position has succeeded, e.g. by performing the token-pulling `vault-system-repay` step last, after `debt-remove-scaled`/`collateral-remove` have already succeeded, so a failure in any step cannot leave a partially-applied, uncompensated mutation of the vault's aggregate accounting.

### Proof of Concept
1. Borrower `B` has scaled debt `D` on asset `X` recorded in `market-vault`.
2. Attacker (liquidator) calls `liquidate-multi` with a `positions` list containing two entries both targeting `(borrower: B, debt-ft: X, debt-amount: <most of D>)`.
3. Entry 1 in the batch: `liquidate` runs normally — `vault-system-repay` pulls tokens from the attacker and reduces vault `principal-scaled`/`total-borrowed`; `debt-remove-scaled` succeeds and reduces `B`'s real scaled debt in `market-vault` to a small remainder `r`.
4. Entry 2 in the batch (computed against the pre-batch, now-stale `curr-scaled = D`): `liquidate` runs again — `vault-system-repay` succeeds again, pulling more tokens from the attacker and again decrementing vault `principal-scaled`/`total-borrowed`; then `debt-remove-scaled` is called with a `scaled-to-remove` amount exceeding `B`'s now-reduced remaining debt `r`, causing it to fail/underflow inside `market-vault` and return `err`.
5. `try!` propagates this `err` out of `liquidate` for entry 2, `call-liquidate` returns it as an element of the result list, but `liquidate-multi` still returns `(ok (list ok-result err-result))` — the transaction commits.
6. Net result: vault aggregate debt has been decremented twice (once legitimately, once for a repay whose corresponding borrower-side debt reduction never happened), while `B`'s market-vault-recorded debt was only reduced once. This mismatch is unrecoverable through normal protocol operation and permanently misprices zToken shares for all other LPs of vault `X`.

(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

    (try! (check-caller-auth))
    (asserts! (not (get repay states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-underlying capped-amount tx-sender))
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed total-borrowed-new)
    (var-set assets (+ (var-get assets) interest-paid))
