This is a confirmed, exploitable vulnerability. The `StatusHandler` fails to scope status creation to the reporting repository.

### Title
Cross-repository GitHub status webhook flips `Commit#deployable?` for another stack's commit, triggering an unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook to **every** `Commit` row in the database that shares the same `sha`, without checking that the commit belongs to the repository that the webhook signature was verified against. Because `verify_signature` in `WebhooksController` only proves the payload came from *some* known GitHub organization (the one named in the payload's `repository.owner.login`), an attacker who controls their own repository can send a validly signed `status` event whose `sha` collides with a commit tracked by an unrelated victim stack, flipping that commit's `deployable?` to true and causing `ContinuousDeliveryJob` to deploy it.

### Finding Description
The broken binding: the question assumes `CI success consulted by trigger_continuous_delivery == a status verified as originating from victim/repoB's own GitHub repository`. Tracing the code shows this equality does **not** hold.

- `WebhooksController#verify_signature` selects the GitHub App by `repository_owner` (`payload.dig('repository','owner','login')`) and verifies the HMAC signature against that org's secret: [1](#0-0) . This only proves "the sender legitimately owns/administers the named repository," not "the sha in this payload belongs to that repository."
- The base `Handler` class provides a `stacks` helper that *does* scope by `repository_name` from the payload: [2](#0-1) . `StatusHandler`, however, ignores this scoping entirely and instead looks up commits globally by sha:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- `create_status_from_github!` creates a `Status` row tied to `stack_id` (the commit's own stack, not the reporting repo) via `add_status`/`replicate_from_github!`: [4](#0-3) , [5](#0-4) .
- `Status` creation triggers `schedule_continuous_delivery` → `commit.schedule_continuous_delivery`, which checks `deployable?` and `stack.continuous_deployment?` and enqueues `ContinuousDeliveryJob`: [6](#0-5) [7](#0-6) .
- `Commit#deployable?` becomes true once a `success` status exists and the commit isn't blocked/locked: [8](#0-7) .
- `ContinuousDeliveryJob#perform` then calls `Stack#trigger_continuous_delivery`, which selects `next_commit_to_deploy` and calls `trigger_deploy`: [9](#0-8) , [10](#0-9) .

**Attacker's exact request:** the attacker owns `attacker/repoA`, which has a Shipit stack (or simply a GitHub App installation covering that org, e.g., their own personal fork/org where they installed the app). They push/create a commit whose sha matches a sha already present as an undeployed commit on `victim/repoB`'s stack (achievable whenever the two repos share commit history — forks, shared upstream, cherry-picked/rebased commits, template repos, monorepo splits, etc., since git SHAs are content+metadata addressed and are identical across any repo that has the exact same commit object). The attacker then triggers their own CI to post a `success` status for that sha on `attacker/repoA` — GitHub sends a `status` webhook signed with `attacker`'s org secret, which passes `verify_signature` since it's a legitimate signature for that org. `StatusHandler#process` finds **all** `Commit` rows with that sha, including the one belonging to `victim/repoB`, and creates a `success` `Status` scoped to the victim's `stack_id`, immediately making the victim's commit `deployable?` and (if that stack has continuous deployment enabled) triggering a real deploy.

**Why existing guards fail:** `verify_signature` authenticates the org, not the sha-to-repo binding; `drop_unhandled_event` and `ExplicitParameters` schema only validate the shape of the payload; there is no check equivalent to the `stacks` helper (used by other handlers, e.g. push/pull_request handlers) to constrain `StatusHandler` to commits under the reporting repository.

### Impact Explanation
An attacker-controlled repository's CI status directly causes record writes (`Status` rows) and can trigger an unauthorized deploy task execution on an unrelated `victim/repoB` stack — an unauthorized deploy triggered by a payload for one repository mutating another repository's commit/stack, matching the Critical severity category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). This is repeatable against any stack whose commits share a sha with a repository the attacker controls, and the blast radius spans all tenants/stacks on the Shipit instance since the lookup is entirely global (`Commit.where(sha: ...)` has no stack/repo scope).

### Likelihood Explanation
Preconditions: the victim stack must be in `continuous_deployment` mode with an undeployed commit whose CI is otherwise pending/unknown, and the attacker must be able to produce (or find) a commit with the identical sha in a repository they control that has a GitHub App/webhook integration active for Shipit. Colliding SHAs across repos are not theoretical — they arise naturally from forks, shared upstream history, cherry-picks/rebases preserving original commit metadata, and monorepo-to-polyrepo splits. Attacker cost is low (no privileged Shipit access needed) and the attack is repeatable per matching sha/target stack.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the reporting repository, mirroring the `stacks` helper already defined in the base `Handler` class, e.g. restrict the query to `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` (or join through `stack.repository == Repository.from_github_repo_name(repository_name)`), rather than an unscoped global sha lookup.

### Proof of Concept
minitest plan (e.g. in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create `victim_repo` / `victim_stack` (continuous_deployment: true) and `attacker_repo` / `attacker_stack`, both with a `Commit` row sharing the same `sha` value (`shared_sha`), each tied to its own stack via `stack_id`.
2. Assert precondition: `victim_stack.commits.find_by(sha: shared_sha).deployable?` is `false` (no status yet).
3. Build a `status` webhook payload with `repository.full_name` = `attacker/repoA`, `sha` = `shared_sha`, `state` = `success`, and call `StatusHandler.call(payload)` directly (bypassing controller-level signature verification, which is orthogonal — it only authenticates the org, not the sha scope).
4. Assert both sides of the binding: `victim_stack.commits.find_by(sha: shared_sha).reload.deployable?` is now `true`, and `victim_stack.commits.find_by(sha: shared_sha).statuses.last.stack_id == victim_stack.id` even though the webhook's `repository.full_name` was `attacker/repoA`.
5. Assert `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])` fires (via `schedule_continuous_delivery`), and/or directly call `victim_stack.trigger_continuous_delivery` and assert it selects/deploys the shared-sha commit (`Deploy.count` increments for `victim_stack`), proving the attacker-repo status caused a victim-stack deploy.
