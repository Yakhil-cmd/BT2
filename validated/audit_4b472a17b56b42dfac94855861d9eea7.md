### Title
Webhook signature verification is keyed on `repository.owner.login` but handlers act on the independent `repository.full_name` field, letting any org with its own GitHub App forge status/push/check-suite events for repos owned by other configured organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate the incoming payload against using `repository_owner`, computed as `params.dig('repository','owner','login')`. But every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the actual repository to act on from the independent field `payload.dig('repository','full_name')`. Because a payload is a single free-form JSON body the attacker fully controls, nothing forces `repository.owner.login` to agree with the owner portion of `repository.full_name`. When Shipit is configured for multiple GitHub organizations (a documented, supported configuration), a party who legitimately owns a GitHub App/webhook secret for **one** configured organization can craft a payload whose `repository.full_name` names a repository belonging to a **different** configured organization, sign it with their own org's known secret, and have it accepted.

### Finding Description
The trust binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository the handler mutates`. This is broken:

- Verification: `app/controllers/shipit/webhooks_controller.rb` `verify_signature` calls `Shipit.github(organization: repository_owner)` and validates `request.headers['X-Hub-Signature']` against `request.raw_post` using that org's `webhook_secret` [1](#0-0) . `repository_owner` is read straight from the attacker-controlled JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- Multiple, independently-secreted GitHub Apps per organization is an explicitly documented and supported configuration (`Shipit.github(organization:)`, `github_app_config`) [3](#0-2) , documented in `docs/setup.md` under "Using Multiple Github Applications".
- Action: `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the target repository from a **different** JSON field, `repository.full_name`, via `Repository.from_github_repo_name` [4](#0-3) . Concrete handlers such as `StatusHandler` (writes CI statuses onto commits by SHA, independent of repo ownership check) [5](#0-4) , `PushHandler` (triggers `stack.sync_github`) [6](#0-5) , and `CheckSuiteHandler` (schedules check-run refresh) [7](#0-6)  use `repository.full_name`/`stacks` (derived from `full_name`) to select which stacks/commits to mutate, with no cross-check against `repository.owner.login`.

Since the HMAC signature covers only the raw request bytes and is verified using whichever org's secret `repository.owner.login` names, an attacker who controls **any** one of the multiple configured GitHub organizations (e.g., they were given/installed a Shipit GitHub App on their own low-privilege org, per the documented multi-org setup) knows that org's `webhook_secret` and can self-sign an arbitrary JSON body. They set `repository.owner.login` = their own org (so `verify_signature` fetches and validates against their own known secret) but set `repository.full_name` = `"OtherOrg/other-repo"` — a repository tracked by Shipit under a different, higher-trust organization. `StatusHandler` most notably lets them post arbitrary CI status events (`state`, `context`, `target_url`) for **any** commit SHA already known to Shipit for the victim's stacks: `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` [8](#0-7) , without any ownership check tying the SHA/full_name to the org that actually signed the request.

### Impact Explanation
This crosses the organization/repository authentication boundary described in scope: "an organization that authenticated versus the repository that is written." Forged CI status can satisfy `required_statuses`/CI-gating checks used to determine a commit's `deployable?` state in `Shipit::Commit`/`Shipit::Stack`, which gates whether operators can trigger a deploy. Forging a passing status on a victim organization's commit can enable an otherwise-blocked, unauthorized deploy of that commit, and forged push/check-suite events can trigger unwanted background sync/refresh jobs against a victim stack. This matches "High" severity from the rubric (escalation across a repository/organization trust boundary via unauthenticated cross-org write) and can approach "unauthorized deploy" (Critical) depending on how strictly the operator's `shipit.yml` gates deploys on CI status.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured with more than one GitHub organization (a documented supported setup for multi-tenant Shipit installs), and (2) the attacker controls or has installed the app for at least one of those configured, lower-trust organizations — knowledge of their own org's webhook secret is all that's needed since they can post directly to the `/github/webhooks` endpoint without going through GitHub at all. No `ApiClient` token, session, or GitHub write access to the victim repo is required. Likelihood is moderate-to-high in any multi-org Shipit deployment.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (and/or in `Shipit::Webhooks::Handlers::Handler`), after selecting the GitHub App by `repository_owner`, enforce that the resolved app's organization matches the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers. Reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` via a lookup scoped to the authenticated organization only, rather than trusting `full_name` verbatim.

### Proof of Concept
Given Shipit configured with two GitHub orgs, `AttackerOrg` (attacker-installed app, secret known to attacker) and `VictimOrg` (unrelated, higher-trust org with tracked stacks/commits):

1. Attacker crafts a JSON body:
```json
{
  "sha": "<existing-victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(AttackerOrg_webhook_secret, body)>` themselves (no need to go through GitHub) and sets `X-Github-Event: status`.
3. POST to `/github/webhooks`. `verify_signature` computes `repository_owner` = `"AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the signature validates successfully against the attacker's own known secret [1](#0-0) .
4. `StatusHandler#process` runs against `sha`, matching the victim's commit (via `Commit.where(sha:)`, unscoped to any org check) and marks it with a forged passing status [5](#0-4) , potentially satisfying deploy-gating CI requirements for `VictimOrg`'s stack.

Note: I could not fully verify at what exact point `Commit.create_status_from_github!` intersects with `deployable?`/`required_statuses` gating logic within the tool budget available (the `Commit`/`Stack` deployability code exists but the effort available did not allow full read-through of `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb`); this should be confirmed by whoever remediates this issue.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
