### Title
`Api::CCMenuController` bypasses per-stack `ApiClient` scoping, letting a token authorized for one stack read another stack's state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` (`belongs_to :stack, optional: true`), and `Api::BaseController` enforces that scope by resolving the requested stack only from the client's own set of allowed stacks. `Api::CCMenuController` overrides that resolution method and looks the stack up globally, breaking the binding between "the stack a token is authorized for" and "the stack the endpoint actually reads."

### Finding Description
`Api::BaseController` computes the authorized stack set from the authenticated `ApiClient`: [1](#0-0) 

`current_api_client.stack_id?` is true whenever the client was created with a specific `stack` (as shown by the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack with only `read:stack` permission): [2](#0-1) 

This scoping is verified to work for other endpoints, e.g. `Api::StacksController#index` only returns the one stack the client is bound to: [3](#0-2) 

However, `Api::CCMenuController` redefines `stack` to resolve the stack directly from the URL parameter, completely bypassing the `stacks` scoping helper from `BaseController`: [4](#0-3) 

The `require_permission :read, :stack` check only verifies that the permission string `read:stack` is present on the client's permission list; it does not verify which stack the permission applies to: [5](#0-4) 

Consequently, an `ApiClient` created (via the web UI or `CCMenuUrlController`) and scoped to stack A with only `read:stack` can hit `GET /api/stacks/:stack_id/ccmenu` with `stack_id` pointing at stack B, and the controller will happily render stack B's CI status/name because `stack` no longer routes through `stacks.from_param!`.

This is precisely the "stack a token authorizes vs. stack it touches" binding break: the token is verified/authorized against stack A, but the code acts on whatever stack the caller names in the URL.

### Impact Explanation
This allows a holder of any per-stack-scoped `read:stack` token (including tokens generated automatically for the CCMenu integration) to read CI build status, last build label, and activity/lock status of *any* stack in the Shipit instance, not just the one the token was issued for — an unauthorized cross-stack read of stack state, matching the High-impact "unauthenticated/unauthorized read of stack state" category.

### Likelihood Explanation
The only requirement is possession of a valid `ApiClient` token that was ever scoped to a single stack (a normal, intended usage pattern, e.g. via `CCMenuUrlController#client` or manually via `Api Client` UI + stack assignment). No privileged account, GitHub credentials, or additional access is required beyond a routine, already-issued read-only token — an "unprivileged attacker" holding one legitimate scoped token can query out-of-scope stacks trivially by changing the URL segment.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!(params[:stack_id])`) so CCMenu requests are constrained to the same client-authorized stack set enforced everywhere else in `Api::BaseController`.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to `stack: repo-a/production` with permission `read:stack` only (mirrors fixture `here_come_the_walrus`).
2. Using that client's `authentication_token`, send:
   `GET /api/stacks/org/repo-b/production/ccmenu` with `Authorization: Basic base64("<token>--")` (or as CCMenu's own `?token=` query param, per `Api::CCMenuController#authenticate_api_client`).
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes (permission string present).
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` directly, returning `repo-b/production` even though the client is scoped to `repo-a/production`.
5. The response renders `repo-b/production`'s CI/build status/name — data the token was never authorized to access.
