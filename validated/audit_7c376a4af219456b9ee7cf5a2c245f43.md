### Title
Direct token transfers to the liquidity pool are permanently stranded - (File: contracts/pool/src/lib.rs)

### Summary
Any user can transfer a listed Stellar Asset Contract token directly to `LiquidityPool`, but that transfer does not update the pool’s `cash` accounting and cannot later be recovered through the pool ABI. The result is the Soroban equivalent of sending native assets to a contract with no recovery path: the tokens remain as an unbooked balance at the pool address.

### Finding Description
The pool’s mutating entrypoints are restricted to its controller-owner through `#[only_owner]`, while the public surface contains no sweep, rescue, or donation-claim function. [1](#0-0) 

A normal `supply` does not inspect the token balance or reconcile unsolicited receipts; it simply mints supply shares and credits `cash` by `entry.action.amount`, relying on the controller to have transferred the assets beforehand. [2](#0-1) 

Outbound token transfers are performed through `Cache::transfer_out`, and every spending operation first debits tracked `cash`; therefore a donation above `cash` is not eligible for withdrawal. [3](#0-2) 

For example, `borrow` debits `cash` before transferring the borrowed amount, and `withdraw` rejects payouts above tracked reserves before debiting `cash`. [4](#0-3) [5](#0-4) 

The codebase explicitly treats unsolicited transfers as donations that remain outside the market books. [6](#0-5) 

### Impact Explanation
A user or integrating contract that sends a listed asset directly to the pool permanently loses those tokens under the current code. The pool’s token balance increases, but no supplier share, debt repayment, revenue claim, or other accounting claim is created. Since spending is bounded by tracked `cash`, the unbooked surplus cannot leave through `borrow`, `withdraw`, `claim_revenue`, `recapitalize`, or `flash_loan`.

### Likelihood Explanation
This is reachable by any unprivileged token holder through the token contract’s ordinary `transfer(from, pool, amount)` call. It requires bypassing the controller or mistakenly using the pool address as the recipient, rather than invoking `Controller::supply`, `repay`, or `recapitalize`; integrations and manual transfers can make that mistake.

### Recommendation
Add a controller-mediated recovery mechanism that can transfer only the unbooked surplus for an asset. The recoverable amount should be `token.balance(pool) - sum(cash across every market using that asset)`, not merely `balance - cash` for one `(hub, asset)` book, because multiple hubs share the same physical pool balance. Alternatively, expose an owner-only pool rescue function with the same surplus calculation and have governance/controller authorize it. User-facing documentation should also state that tokens must never be transferred directly to the pool.

### Proof of Concept
```rust
// Pool and market setup omitted: create a listed market for `asset`.
let token = token::Client::new(&env, &asset);
let pool_addr = /* deployed LiquidityPool address */;
let user = Address::generate(&env);

let amount = 1_000_000;
let pool_balance_before = token.balance(&pool_addr);
let reserves_before = pool_client.get_reserves(&hub_asset);

// Direct token transfer; no controller entrypoint is invoked.
token.transfer(&user, &pool_addr, &amount);

assert_eq!(token.balance(&pool_addr), pool_balance_before + amount);
assert_eq!(pool_client.get_reserves(&hub_asset), reserves_before);

// The additional `amount` belongs to no market's `cash` book and no public
// LiquidityPool entrypoint can return it.
```

The same accounting separation is demonstrated by the repository’s own donation test, where a direct pool transfer leaves `cash` unchanged and creates a physical balance surplus. [7](#0-6)

    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Transfers `amount` of the market asset from the pool to `recipient`.
    ///
    /// Rejects negative amounts; zero is a no-op. Does not adjust accounting cash.

        if amount == 0 {
            return;
