### Title
Webhook `X-Hub-Signature` verification is keyed to `repository.owner.login`, but repository lookup uses `repository.full_name` independently, letting a no-secret org's payload spoof a sha1-protected org's repo - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check against using `repository_owner`, which is read from `params.dig('repository','owner','login')`. Every handler that actually mutates state resolves the target `Repository`/`Stack` via `Repository.from_github_repo_name(params.repository.full_name)`, which independently parses the owner from `full_name`. Nothing enforces `repository.owner.login == full_name.split('/').first`, so an attacker who owns an org with no `webhook_secret` configured can set `repository.owner.login` to that org while setting `repository.full_name` to `victim-org/repo`, causing signature verification to trivially pass (`return true unless webhook_secret`) while the handler still mutates the victim org's stack.

### Finding Description
The binding the code is supposed to enforce is:
`organization_used_for_signature_verification (params.dig('repository','owner','login') or params.dig('organization','login')) == organization_owning_the_mutated_repository (owner segment parsed from params.dig('repository','full_name') by Repository.from_github_repo_name)`

Trace:
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`.
- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) reads only `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — a raw, attacker-controlled JSON field, with no cross-check against `full_name`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`): if the org resolved by `repository_owner` has no `@webhook_secret` configured, it returns `true` unconditionally (`return true unless webhook_secret`), regardless of the `X-Hub-Signature` header's algorithm or value (`sha256=...`, empty, malformed, or absent).
- Once verification passes, `create` dispatches to handlers (e.g. `app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:65-68`) that resolve the acted-upon repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (`app/models/shipit/repository.rb:53-56`), which parses `owner/name` purely from `full_name`, completely independent of the `repository_owner` value used for signature checking.

Exploit flow:
1. Attacker directly targets the sha1/secret-protected org (`victim-org`) sending `X-Hub-Signature: sha256=<anything>` or a header with no `=`. `algorithm` becomes `'sha256'` or `nil`; the `return false unless algorithm == 'sha1'` guard correctly rejects it (`head 422`). Direct forgery fails as expected.
2. Attacker pivots: sends a payload where `repository.owner.login` (and/or `organization.login`) = `attacker-org` (an org attacker controls / registered in Shipit with no `webhook_secret`), while `repository.full_name` = `"victim-org/repo"`.
3. `repository_owner` resolves to `attacker-org`; `Shipit.github(organization: 'attacker-org')` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` for any/no signature.
4. The handler then loads `Repository.from_github_repo_name('victim-org/repo')` and mutates `victim-org`'s actual stacks/review stacks (archive/unarchive, label capture, PR review-stack provisioning, etc.) — an unauthenticated cross-tenant mutation.

Existing guards fail to prevent this because `drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schemas only validate shape/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; and `verify_signature`'s sha1-only restriction only protects the org it happens to look up — it has no bearing once the looked-up org and the mutated-repo org can diverge.

### Impact Explanation
An unprivileged attacker who registers/owns any org in Shipit without a configured `webhook_secret` (or exploits any org lacking one) can forge webhook events that mutate a *different*, secret-protected organization's repository stacks — archiving/unarchiving review stacks, triggering label-driven provisioning behavior, or any other action handled by `Shipit::Webhooks::Handlers::PullRequest::*` — without ever needing to compute a valid HMAC. This is a full authentication bypass causing cross-tenant state mutation, matching the Critical category ("a payload for one repository mutating another's stack ... unauthorized deploy/rollback"). It is repeatable against any repository whose `full_name` the attacker can guess/know, for every request.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit-registered org/app config without a `webhook_secret` set (common for orgs that never configured one, or any org the attacker can get onboarded), and knowledge of the target repo's `owner/name` (public information). No secrets, sessions, or tokens are required — just an HTTP POST to `/webhooks` with a crafted JSON body. This is low-cost and fully repeatable.

### Recommendation
Verify webhook signatures using the org actually referenced by `repository.full_name` (or reconcile that `repository.owner.login` matches the owner segment of `full_name` before using either for authorization), and stop treating "no secret configured" as an implicit bypass — either require a configured `webhook_secret` for every org that owns repositories with active stacks, or independently validate `full_name`'s owner against `Shipit.github(organization: ...)`'s configured owner before dispatching to handlers.

### Proof of Concept
```ruby
test "signature verification rejects sha256/no-secret pivot on same secreted repo" do
  # victim-org has a configured webhook_secret
  # direct forgery attempt fails
  post "/webhooks", params: sha1_protected_payload.merge(
    'repository' => sha1_protected_payload['repository'].merge('owner' => { 'login' => 'victim-org' })
  ).to_json, headers: { 'X-Hub-Signature' => 'sha256=deadbeef', 'X-Github-Event' => 'pull_request' }
  assert_response :unprocessable_entity # 422, HMAC guard works as intended

  # pivot: attacker-org has NO webhook_secret, but full_name still points at victim-org/repo
  payload = sha1_protected_payload.deep_dup
  payload['repository']['owner']['login'] = 'attacker-org'
  payload['repository']['full_name'] = 'victim-org/repo'

  post "/webhooks", params: payload.to_json,
       headers: { 'X-Github-Event' => 'pull_request' } # no signature needed at all

  assert_response :ok
  assert victim_org_repo.review_stacks.reload.<mutated_as_expected> # e.g. archived
end
```

This confirms both sides of the equality: signature checking is keyed to `repository_owner` (`attacker-org`), while the actual write targets the repo resolved from `full_name` (`victim-org/repo`) — the two diverge, and the sha1-only algorithm restriction is irrelevant once this divergence is possible.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
