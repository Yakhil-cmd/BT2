Based on my investigation, I found a valid analog matching the "organization authenticated versus the repository that is written" binding.

### Title
Webhook signature verification authenticates the payload's `repository.owner.login` while handlers act on the independently-controlled `repository.full_name` field, allowing cross-tenant repository spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to verify a webhook against using `params.dig('repository', 'owner', 'login')`, but all webhook `Handler` subclasses resolve the actual `Repository`/`Stack` to mutate using the sibling field `params.dig('repository', 'full_name')`. These two fields live in the same attacker-controlled JSON object and are never cross-checked for consistency, so a party who legitimately controls one onboarded GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a valid signature while making the payload's `full_name` point at a stack belonging to a completely different organization.

### Finding Description
`verify_signature` computes the GitHub App/secret to check against based solely on `repository_owner`, derived from the payload itself: [1](#0-0) [2](#0-1) 

Shipit explicitly supports one `webhook_secret` per GitHub organization, configured independently per org: [3](#0-2) 

Meanwhile, every `Webhooks::Handlers::Handler` subclass (and the base `Handler#repository_name`) looks up the `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')`, an entirely separate key nested in the same JSON object: [4](#0-3) , and concretely in the push handler: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find the owner/name pair and does not require it to match `repository.owner.login`: [6](#0-5) 

Because `X-Hub-Signature` is an HMAC over the raw JSON body, the signature only proves that *whoever produced the body* knew the secret associated with the org identified via `repository.owner.login` — it says nothing about which `full_name` the body describes. An org administrator who has legitimate access to their own GitHub App's webhook secret (a normal, documented per-org secret, not a Shipit admin credential) can compute a valid `X-Hub-Signature` for an arbitrary payload, and craft `repository.full_name` to reference any other onboarded repository/stack.

**Binding broken:** `organization authenticated (repository.owner.login → webhook_secret)` ≠ `repository actually written (repository.full_name → Stack/Repository mutated)`.

Before the attacker's request: signature verification and handler dispatch both implicitly assume `repository.owner.login` and `repository.full_name` describe the same repository (true for genuine GitHub-originated webhooks). After a forged request: the attacker satisfies `verify_webhook_signature` using their own org's secret while `full_name` is set to a victim stack, so the two fields diverge and the handler acts on the victim's data anyway.

### Impact Explanation
Depending on which webhook `event`/handler is dispatched, this can be used to inject forged state into a victim organization's stack without any of the victim's credentials:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha:)` on the victim stack, using an attacker-chosen SHA.
- `status`/`check_suite` handlers can be made to write fabricated CI/commit statuses onto a victim commit, which can be used to satisfy `ci.require` checks and enable an unauthorized merge/deploy of a victim's stack (High-severity "escalation" and potentially "unauthorized deploy/merge" class impact) — this is only reachable if the corresponding handler resolves the commit/stack via `full_name` the same way (confirmed pattern for `PushHandler` and the `PullRequest` handlers I reviewed; I did not enumerate every handler in `app/models/shipit/webhooks/handlers/**` exhaustively, so the exact blast radius across event types is not fully confirmed).
- `pull_request` handlers (`OpenedHandler`, `ClosedHandler`, etc.) resolve `repository` the same way via `full_name`, so review-stack creation/archival for a victim's PRs could similarly be spoofed.

### Likelihood Explanation
This requires the attacker to control a GitHub organization/App that is legitimately configured in Shipit's multi-org `secrets.yml` (i.e., they must know their own org's `webhook_secret`), which is a realistic scenario for any multi-tenant Shipit deployment serving several GitHub organizations, each managed by different, mutually-untrusted org admins. No Shipit session, API token, or victim credentials are required — only crafting a raw HTTP POST to `/webhooks` with a forged JSON body and a correctly computed HMAC using the attacker's own known secret.

### Recommendation
After successful signature verification, re-derive `repository_owner` strictly from the same `repository` object used by the handler (i.e., require `repository.owner.login` to equal the owner segment of `repository.full_name`), and reject the webhook if they diverge. Alternatively, always verify against the Shipit-side authoritative owner of the `Repository` matched by `full_name`, not a value pulled directly from the unauthenticated-at-that-point request body.

### Proof of Concept
1. Assume Shipit is configured with two GitHub orgs, `orgA` (attacker-controlled, secret `SECRET_A` known to the attacker) and `orgB/victim-repo` (a stack the attacker does not control).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)` using their own known secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against `SECRET_A`. [1](#0-0) 
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack. [7](#0-6) [4](#0-3)

  module Webhooks
