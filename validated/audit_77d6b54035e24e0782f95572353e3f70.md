### Title
Cross-tenant webhook authentication/authorization mismatch forces `RefreshCheckRunsJob` against an arbitrary victim stack - ([File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the `GitHubApp` config keyed on `repository.owner.login` from the *same* attacker-supplied JSON body, while `CheckSuiteHandler#process` (via `Handler#stacks`) scopes the affected `Stack` by the unrelated `repository.full_name` field of that same body. Nothing binds these two fields together, so in a multi-org Shipit deployment an attacker who can get a webhook accepted for one (weakly-configured) org can point `repository.full_name` at a completely different, victim org's repo/stack.

### Finding Description
The broken binding is: `repository.owner.login` (used to select the `GitHubApp`/secret for HMAC verification in `WebhooksController#verify_signature`) should equal the org encoded in `repository.full_name` (used by `Handler#stacks` / `CheckSuiteHandler#process` to select the affected `Stack`) — but nothing in the code enforces this equality.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- `Handler#stacks` (base class used by `CheckSuiteHandler`) resolves the target repository via `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')` — a *different* field of the same JSON body, never cross-checked against `repository.owner.login`. [4](#0-3) 
- `CheckSuiteHandler#process` then does `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!) }`, operating on whatever `Stack` `full_name` resolved to. [5](#0-4) 
- This forwards to `RefreshCheckRunsJob`, which loads the victim `Commit`/`Stack` and calls `refresh_check_runs!`, an authenticated call using that stack's own GitHub credentials. [6](#0-5) 

Shipit explicitly supports multi-org deployments where each org has its own `GitHubApp` config keyed by org name, and the shipped example/dummy configs show `webhook_secret` as an unset/nil placeholder value. [7](#0-6) [8](#0-7) 

**Exploit flow**: In a multi-org Shipit install where at least one configured org (e.g. `OrgOne`) has no `webhook_secret` set, an internet attacker with no session/token/secret sends `POST /webhooks` with header `X-Github-Event: check_suite` and a JSON body: `{"repository": {"owner": {"login": "OrgOne"}, "full_name": "victim-org/victim-repo"}, "check_suite": {"head_branch": "<victim's stack branch>", "head_sha": "<victim commit sha>"}}`. `verify_signature` resolves `Shipit.github(organization: 'OrgOne')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header. `CheckSuiteHandler#process` then resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues a check-run refresh against the victim's real commit/stack.

**Why existing guards fail**: `drop_unhandled_event`/`check_if_ping` don't inspect payload contents; `ExplicitParameters` only validates types/presence of `check_suite.head_sha`/`head_branch`, not cross-field org consistency; `Repository.from_github_repo_name` performs an exact case-insensitive lookup with no ownership check against the authenticated org; there is no code anywhere that asserts `repository.full_name.split('/').first == repository.owner.login`.

### Impact Explanation
An attacker can force a Shipit instance to enqueue `RefreshCheckRunsJob` against an arbitrary victim stack/commit outside their own tenant, causing the victim's `GitHubApp` credentials to be used to call the GitHub API (`refresh_check_runs!`) for attacker-chosen commits, entirely without knowledge of the victim's webhook secret. This is a cross-tenant authorization break — "a payload for one repository[org] mutating another's stack" — matching the Critical impact category. The blast radius is bounded to whichever GitHub orgs are configured on the same Shipit instance, and is repeatable per request as long as the misconfigured org name and a matching victim branch name are known/guessed.

### Likelihood Explanation
This requires a specific multi-tenant precondition: the Shipit instance must run in the "Using Multiple Github Applications" configuration mode with per-org `webhook_secret`, and at least one configured org's `webhook_secret` must be unset/blank (a plausible operator misconfiguration explicitly modeled by the shipped example configs, which all show `webhook_secret: # nil`). Given that precondition, the attacker's cost is trivial: no secrets, tokens, or privileged roles are needed — only knowledge of the weakly-configured org's login name and a branch name that exists on a victim stack. In a single-org configuration (`github_default_organization.nil?`), `Shipit.github` ignores the `organization:` argument and always uses the single global secret, so this specific bypass does not apply there.

### Recommendation
In `Handler#stacks`/`CheckSuiteHandler#process` (and all other webhook handlers using `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), verify that the org segment of `repository.full_name` matches the `repository.owner.login` that was used to authenticate the webhook, or better, verify the signature using the org derived from `repository.full_name` itself rather than a separately attacker-controlled `owner.login` field. Additionally, treat a blank `webhook_secret` as a configuration error rather than an implicit "always valid" signal (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`), e.g. raise/log a hard warning at boot for any configured org lacking a webhook secret.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style):
1. Configure two orgs via `secrets_double_github_app.yml`-style config: `OrgOne` with `webhook_secret: nil`, and `victim-org` with a real secret configured; stub `Shipit.stubs(:secrets)` accordingly.
2. Create `shipit_stacks(:victim_stack)` under `Repository` with `owner: 'victim-org', name: 'victim-repo'`, `branch: 'main'`, and an associated `Commit` with a known `sha`.
3. POST to `/webhooks` with `X-Github-Event: check_suite`, no/garbage `X-Hub-Signature`, and body:
   `{"repository": {"owner": {"login": "OrgOne"}, "full_name": "victim-org/victim-repo"}, "check_suite": {"head_branch": "main", "head_sha": commit.sha}}`.
4. Assert `response` is `:ok` (signature check passed via `OrgOne`'s blank secret) — i.e. assert `Shipit.github(organization: 'OrgOne').verify_webhook_signature` was never actually validated against the real signature.
5. Assert `RefreshCheckRunsJob` (or the underlying `schedule_refresh_check_runs!` call) was enqueued/invoked for `commit.id` belonging to the victim stack, proving the equality `repository.owner.login ('OrgOne') != full_name's org ('victim-org')` yet the victim's stack was still targeted.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
