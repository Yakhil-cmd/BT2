### Title
AA-composed responses silently drop zero-amount payment outputs without bouncing surviving state updates, letting proportional-share AAs debit user balances/LP shares while paying nothing back - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()` filters zero-amount outputs out of each payment message and only bounces the entire AA response if **every** message ends up with zero outputs. If an AA response contains a payment message whose amount formula rounds down to 0 alongside a separate `state` message (a very common Hubble/Uniswap-style share-accounting pattern), the zero-amount payment silently disappears while the `state` message — which already decremented the user's tracked balance/shares — still executes, exactly mirroring the Sherlock `InsuranceFund` bug where burning happens but the payout is silently 0.

### Finding Description
`aa_composer.js` builds the outgoing response unit from the AA's `messages` array. For every payment message, zero/undefined amounts are computed by the formula engine, then filtered: [1](#0-0) 
Only if the *entire* `messages` array becomes empty does the composer bounce and treat the trigger as producing "no state changes": [2](#0-1) 
This is confirmed by the test `'only 0 output'`, which shows that when the *sole* message in an AA is a payment that evaluates to 0, the whole unit is bounced with `"no messages after removing 0-outputs, then no state changes"`: [3](#0-2) 

However, this all-or-nothing behavior only protects the case where the zero-amount payment is the *only* message. Many real-world AA patterns (share/LP accounting, exactly the class flagged in the external report) pair a payment message with a **separate `state` message** that adjusts an outstanding-shares or balance variable, independent of whether the payment output survives filtering. The bundled sample AA `uniswap_like_market_maker.oscript` demonstrates this exact structure in its "divest MM shares" case: it sends a proportional `$asset` payment, a proportional `base` payment, and then unconditionally decrements `var['mm_asset_outstanding']` by the full amount of shares the user sent in as trigger input: [4](#0-3) 

If `$investor_share * balance[$asset]` (and/or `* balance[base]`) rounds to 0 (e.g., a very small `mm_asset` divestment relative to `mm_asset_outstanding`), the corresponding payment message(s) get filtered out of the final unit by `aa_composer.js`'s 0-output removal logic — but the `state` message remains in the array (since it produces no payment output to strip), so `messages.length !== 0`, no bounce occurs, and `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` still executes and is persisted via `fixStateVars()`.

The user's `mm_asset` (LP-share) tokens were already transferred to the AA as part of the ordinary payment inputs of the triggering unit (this transfer is irreversible and outside the AA's control), so the user has definitively paid in their shares. The AA's own accounting variable is reduced accordingly, but the user receives 0 bytes and 0 of the underlying asset back — funds are effectively trapped in/absorbed by the AA balance while the outstanding-shares ledger is decremented as if a normal payout had occurred.

### Impact Explanation
Any unprivileged user (or another AA acting as a trigger sender) can lose deposited tokens/shares to a share-accounting AA whenever a proportional payout formula rounds to zero, without any protocol-level safeguard forcing the AA response to bounce. This is a direct, permanent loss of user funds/shares (AA fund loss for the depositor, and silent state corruption of the AA's tracked liabilities vs. actual balance) reachable purely by posting a normal payment+trigger to a deployed AA — no privileged role required. The severity depends on how widely such share-based accounting patterns (present in ocore's own bundled sample AAs) are deployed, but the root cause is a general property of `aa_composer.js`'s message-filtering logic, not a bug in any specific AA script.

### Likelihood Explanation
Medium. Exploitation requires an AA whose payout formula can round to zero for small trigger amounts while a companion `state` message unconditionally debits the user's tracked balance/shares — a natural and even officially-demonstrated pattern (`uniswap_like_market_maker.oscript` ships in ocore's own test samples as a reference implementation). Any user can trivially trigger this by sending a very small amount of the share asset (dust divestment), making the precondition easy to hit without special privileges.

### Recommendation
In `aa_composer.js`, when a payment message ends up with zero surviving outputs after filtering, treat this as a hard failure for the *entire trigger response* (i.e., bounce) rather than silently continuing with remaining non-payment messages, unless the AA explicitly guards against zero-amount payouts itself. Alternatively/additionally, document and strongly recommend (and provide as a formula-engine primitive) that AA authors must explicitly `bounce()` when a computed payout amount is 0, so that dependent `state` updates are also rolled back atomically — the current one-message-array-wide filtering makes this too easy to miss, as evidenced by the bundled `uniswap_like_market_maker.oscript` sample not guarding against it.

### Proof of Concept
1. Deploy an AA equivalent to `test/samples/uniswap_like_market_maker.oscript`'s "invest"/"divest" cases (`uniswap_like_market_maker.oscript:33-101`), with an existing `mm_asset_outstanding` balance.
2. An attacker/user first invests to receive a small amount of `mm_asset` shares (or acquires them cheaply).
3. Attacker triggers the "divest MM shares" case with a `trigger.output[[asset=mm_asset]]` small enough that `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])` both evaluate to `0` (possible when `mm_asset_outstanding` is large relative to the divested amount).
4. In `aa_composer.js`, both payment messages get their outputs filtered to empty and are removed from `messages` (aa_composer.js:1274-1281), but the `state` message (`var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]`) remains, so `messages.length !== 0` and no bounce occurs.
5. The trigger unit's `mm_asset` payment to the AA (already an irreversible transfer performed by the user) is now unrecoverable — the user receives nothing back, and `mm_asset_outstanding` is decremented as though a normal payout happened.
