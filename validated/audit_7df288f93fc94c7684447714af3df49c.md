### Title
`Api::CCMenuController#stack` bypasses ApiClient stack scoping, letting a stack-scoped token read any other stack's CI/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` scopes an `ApiClient` to a single `Stack` when the client has a `stack_id` set, by resolving `stack` through the scoped `stacks` relation. `Api::CCMenuController` overrides `stack` and resolves it directly from the global `Stack` relation, ignoring the client's `stack_id` scope entirely while still only checking the coarse `read:stack` permission string. This breaks the binding: *the stack a token authorizes* (its `stack_id`) *must equal the stack it touches* (`params[:stack_id]`).

### Finding Description
`Api::BaseController` defines the scoping used by every other API endpoint: [1](#0-0) 

`current_api_client.check_permissions!` only checks that the string `read:stack` is present in the client's `permissions` array — it never checks `stack_id` itself: [2](#0-1) 

The per-stack restriction therefore depends entirely on `stacks` being used to look up the target stack. `Api::CCMenuController`, however, overrides `stack` to bypass that scoping and resolve directly against the unscoped `Stack` model, using only `params[:stack_id]` supplied by the caller: [3](#0-2) 

It also supports token-in-query-string authentication (`ApiClient.authenticate(params[:token])`), which is how such tokens are normally handed out — e.g. `CCMenuUrlController` auto-creates (or reuses) an `ApiClient` scoped with `permissions: %w[read:stack]` for any Shipit user viewing any stack they can see: [4](#0-3) 

Because `CCMenuController#stack` never checks `current_api_client.stack_id`, any token that carries the `read:stack` permission — even one legitimately minted and scoped to a single, specific stack — can be replayed with a different `stack_id` query parameter to read the CI/build state of an arbitrary, unrelated stack.

### Impact Explanation
This is a cross-stack authorization-scope break: "a stack a token authorizes vs. a stack it touches," matching the High-impact category "unauthenticated read of stack state" via an authorization scope violation. An attacker holding any `read:stack`-scoped CCMenu token (which are widely and automatically distributed to any logged-in user for any stack they can view, per `CCMenuUrlController`) can enumerate other stacks' build/deploy status (`lastBuildStatus`, lock status, deploy history) that they were never authorized to access, including for stacks/repositories they have no legitimate visibility into.

### Likelihood Explanation
High. `CCMenuUrlController#fetch` hands out one of these tokens on-demand to any authenticated Shipit user for essentially any stack (`Stack.from_param!(params[:stack_id])`, gated only by normal Shipit authentication, not per-stack authorization checks beyond what viewing requires). The resulting token is a durable, signed `ApiClient` id (`SimpleMessageVerifier`), and `stack_id` in the CCMenu XML request is fully attacker-controlled. No GitHub credentials, webhook secrets, or elevated privileges are required beyond having obtained any one such token.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so the `current_api_client.stack_id` restriction from `Api::BaseController#stacks` is honored consistently across all API controllers.

### Proof of Concept
1. As a normal, authenticated Shipit user, visit `GET /stacks/:owner/:repo/:env/ccmenu_url` (`CCMenuUrlController#fetch`) for Stack A. This creates/returns an `ApiClient` named "CCMenu Client" scoped to Stack A with `permissions: ['read:stack']`, and returns a URL containing `?token=<token>`.
2. Take the returned `token` and issue: `GET /api/stacks/:owner/:other_repo/:other_env/ccmenu.xml?token=<token>` for Stack B (any other stack in the Shipit instance).
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (unscoped), `require_permission :read, :stack` passes because the token has `read:stack`, and the response discloses Stack B's build/deploy status — despite the token being scoped only to Stack A.
