### Title
Webhook organization-selection uses Content-Type-dependent `params`, while event processing re-parses the raw body — signature is verified against the wrong organization's secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` will be used to validate the signature by reading `repository_owner`, which is derived from Rails' `params` object. [1](#0-0)  `repository_owner` reads `params.dig('repository', 'owner', 'login')` from the same `params`. [2](#0-1)  The action that actually acts on the event, however, does not use that `params` — it independently re-parses the raw HTTP body as JSON: `params = JSON.parse(request.raw_post)` and dispatches handlers with that value. [3](#0-2)  The route for this controller is a plain `resources :webhooks, only: :create` with no `defaults: { format: :json }` constraint, unlike other JSON-only endpoints in the same routes file (e.g. `defaults: { format: :json }` used elsewhere for tail/output actions). [4](#0-3) [5](#0-4) 

### Finding Description
Rails populates `ActionController::Base#params` from the request body only according to the request's `Content-Type` header; if the header is not `application/json` (e.g. `application/x-www-form-urlencoded`, or simply omitted so Rails falls back to form/query parsing), the JSON body is not parsed into `params`, and `params` instead reflects only the query string and any form-encoded fields. Because `repository_owner` — the value used to select which org's `webhook_secret` verifies the signature — is read from this `Content-Type`-dependent `params`, an attacker can decouple the two things that should be the same value:

- The organization used for signature verification: `Shipit.github(organization: repository_owner)` in `verify_signature`. [6](#0-5) 
- The organization/repository actually processed by the event handlers, which always comes from `JSON.parse(request.raw_post)` regardless of `Content-Type`. [3](#0-2) 

Concretely: if an attacker sends a request with `Content-Type: application/x-www-form-urlencoded`, a query string `?repository[owner][login]=attacker-org`, and a raw JSON body whose `repository.owner.login` is some other, victim organization (e.g. one that is actually configured on this Shipit install), then:
1. `verify_signature` computes `repository_owner == "attacker-org"` from the query string (via Rails' `params`), not from the JSON body.
2. `Shipit.github(organization: "attacker-org")` returns the GitHub App config for the attacker's own organization (an org the attacker may legitimately administer on the same multi-tenant Shipit instance, e.g. via `config/secrets*.yml` `github:` map holding multiple orgs) and its `webhook_secret`.
3. The attacker signs `request.raw_post` with the `webhook_secret` they know (their own org's secret) and the signature check passes because `verify_webhook_signature` is only ever checked against that chosen org's secret. [6](#0-5) 
4. `create` then re-parses the same raw body as JSON and dispatches to handlers (e.g. `PushHandler`) using the victim organization's repository name embedded in the JSON body, not the attacker's org. [7](#0-6) 

This breaks the intended binding "organization that authenticated == repository that is written": the signature is authenticated against organization A's secret while the mutation (triggering `sync_github`, creating commits/statuses, `Membership`/`Team`/`User` records for `membership` events, etc.) is performed for organization/repository B, entirely under attacker control of the JSON body.

### Impact Explanation
This allows an attacker who controls one legitimately-configured tenant/organization (and therefore knows its `webhook_secret`) to forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) for any other repository/organization configured on the same Shipit instance, without knowing that other organization's secret. Depending on handler, this can trigger unauthorized `GithubSyncJob` runs, fabricate commit `Status`/`CommitDeployment` state that feeds `continuous_deployment` (`Stack#trigger_continuous_delivery`), or forge `membership`/`pull_request` events that mutate `Team`/`User`/`Membership` records — all cross-tenant writes performed as if GitHub had sent them, satisfying the "cross-repository writes" / "unauthorized deploy" bar since forged `status`/`push` events can drive `continuous_deployment` to trigger an actual deploy on the victim's stack.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (a supported, documented configuration per `config/secrets.development.shopify.yml`), and requires the attacker to control one of those configured organizations (i.e., know its `webhook_secret`) — a realistic scenario for shared/multi-tenant Shipit deployments. No GitHub App private key, `ApiClient` token, or Shipit user session is needed; only an HTTP request with a crafted `Content-Type`/query string is required, satisfying the "unprivileged attacker" bar for this scan.

### Recommendation
Compute `repository_owner` from the exact same parsed payload that is used for event dispatch (the `JSON.parse(request.raw_post)` result), not from the `Content-Type`-dependent `ActionController::Base#params`. Concretely, parse `request.raw_post` once (e.g., in a `before_action` stored on the request, or by making `create` and `verify_signature` share a single `params = JSON.parse(request.raw_post)`), and derive `repository_owner` strictly from that value. Additionally, reject webhook requests whose `Content-Type` is not `application/json`.

### Proof of Concept
1. Have (or control) organization `attacker-org` configured in `Shipit.github` with a known `webhook_secret`.
2. Send `POST /webhooks` with:
   - `Content-Type: application/x-www-form-urlencoded`
   - Query string: `?repository[owner][login]=attacker-org`
   - `X-Github-Event: push`
   - Raw body (JSON): `{"ref":"refs/heads/main","after":"<victim sha>","repository":{"owner":{"login":"victim-org"},"full_name":"victim-org/victim-repo"}}`
   - `X-Hub-Signature: sha1=<HMAC-SHA1 of the raw body using attacker-org's webhook_secret>`
3. In `verify_signature`, `repository_owner` resolves to `"attacker-org"` from the query string (Rails does not JSON-parse the form-content-typed body), so `Shipit.github(organization: "attacker-org")` is used and the signature check passes with the attacker's known secret. [1](#0-0) 
4. `create` re-parses the raw body as JSON (`JSON.parse(request.raw_post)`) and dispatches `PushHandler`, which looks up `victim-org/victim-repo`'s `Stack` and calls `stack.sync_github(expected_head_sha: params.after)` — a write performed under a signature that never actually authenticated `victim-org`. [3](#0-2) [8](#0-7)
