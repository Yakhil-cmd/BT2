### Title
Unbounded regex evaluation in hookify's `_regex_match`/`compile_regex` allows ReDoS-induced hook hang, defeating fail-closed PreToolUse blocking - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`_regex_match` compiles attacker-influenced patterns via `compile_regex` (an `lru_cache`-wrapped `re.compile`) and calls `regex.search(text)` with no timeout, resource limit, or complexity check [1](#0-0) . Rule patterns and event/field bindings come from `.claude/hookify.*.local.md` files, parsed by a hand-rolled YAML parser in `config_loader.py` and turned directly into `Condition.pattern` strings with no complexity validation or sanitization [2](#0-1) [3](#0-2) . The `pretooluse.py` entry point loads these rules and runs `RuleEngine.evaluate_rules`, then wraps everything in a broad `try/except Exception` that always `sys.exit(0)`s on any error, explicitly to "never block operations due to hook errors" [4](#0-3) . That exception handler only helps against `re.error` (invalid syntax); it does nothing for a pattern that compiles fine but exhibits catastrophic backtracking (e.g. `(a+)+$`, `(a|a)*b`) against a crafted `command`/`new_string` field — the process simply hangs inside `regex.search()`, never reaching the except block or emitting the `permissionDecision: deny` JSON that `evaluate_rules` would otherwise return for blocking rules [5](#0-4) . When a hook process hangs past Claude Code's hook timeout, the tool call is unmediated by that hook's decision, which is a fail-open outcome for the pending PreToolUse blocking rule (deny-means-deny is violated). Rules are evaluated sequentially and any earlier condition/rule with a malicious pattern would starve evaluation of later, legitimate blocking rules in the same list as well [6](#0-5) .

### Impact Explanation
If a `.claude/hookify.*.local.md` rule file containing an adversarial `regex_match` pattern is present when `review-pr.md`'s workflow invokes `Bash` (or `Edit`/`Write`/`MultiEdit`), the PreToolUse hookify hook can hang indefinitely on inputs matched against that pattern. Because the hook harness is designed to fail open on error and there is no timeout guard around `regex.search`, this can cause a legitimate `action: block` rule (protecting against e.g. `rm -rf` or credential exfiltration commands) to never render its deny decision in time, allowing a dangerous Bash command to execute. This matches the "trust-boundary / hook-enforcement bypass leading to unauthorized command execution" impact class.

### Likelihood Explanation
Exploitation requires a hookify rule file with an attacker-influenced pattern to be loaded from the working directory's `.claude/` folder at hook-invocation time. Naming convention (`hookify.*.local.md`) suggests these are intended as local/per-developer overrides rather than files ordinarily committed and merged from external PRs, so getting such a file into place typically requires either a maintainer already checking out/merging PR content that includes it, or an existing local misconfiguration — I could not confirm from this repo that `review-pr.md`'s workflow ever performs an automatic `gh pr checkout` of untrusted content that would introduce such a file, so the "attacker submits a PR" precondition is plausible but not fully proven within this repo's code. What is confirmed and reproducible independent of that precondition is the core engine defect: `compile_regex`/`_regex_match` has no bound on evaluation time for any pattern reaching it, which is a real, exploitable weakness whenever the rule content is not fully trusted.

### Recommendation
- Enforce a hard evaluation timeout (e.g. via a separate process/thread with `signal.alarm`, or a regex engine with backtracking guards such as Google's `re2`) around `regex.search()` in `_regex_match`.
- Validate/limit pattern complexity at rule-load time (reject nested quantifiers like `(a+)+`, cap pattern length, disallow patterns without anchors on unbounded input).
- On timeout, treat the hook result as an explicit `deny`/fail-closed for blocking rules rather than the current fail-open default, or at minimum surface a clear "regex evaluation timed out" `systemMessage` and abort only the offending rule rather than exiting silently as if nothing matched.

### Proof of Concept
Add a unit/fuzz test to `plugins/hookify` test suite:
```python
import time
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_regex_match_bounded_time():
    rule = Rule(
        name="redos-rule", enabled=True, event="bash", action="block",
        conditions=[Condition(field="command", operator="regex_match",
                               pattern=r"(a+)+$")],
        message="blocked"
    )
    engine = RuleEngine()
    evil_input = {
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 40 + "!"}  # no match -> triggers backtracking
    }
    start = time.monotonic()
    result = engine.evaluate_rules([rule], evil_input)
    elapsed = time.monotonic() - start
    assert elapsed < 1.0, f"regex evaluation took {elapsed}s, ReDoS not bounded"
```
Expected today: the assertion fails (evaluation time grows exponentially with input length), demonstrating the missing timeout guard. A fuzz harness should additionally iterate several classic catastrophic patterns (`(a|aa)+$`, `([a-zA-Z]+)*$`, `(a+)+b`) against increasing-length non-matching strings and assert wall-clock time stays sub-linear/bounded, and separately assert that a timeout never results in `evaluate_rules` returning `{}` (allow) for a rule with `action: "block"`.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
