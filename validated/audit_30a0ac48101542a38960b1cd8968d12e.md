Confirmed: the vulnerability is real in this multi-org Shipit deployment configuration. The signature-verification binding (`repository.owner.login`) is decoupled from the resource-action binding (`repository.full_name`), so an attacker only needs a webhook secret/organization with no secret configured (or knows it) for `repository.owner.login` while pointing `repository.full_name` at any tracked repository under any other configured organization.

### Title
Webhook signature verified against `repository.owner.login` while handlers act on the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or the top-level `organization.login`) [1](#0-0) [2](#0-1) . However, every webhook `Handler` resolves the repository/stack to act on using a *different* JSON field, `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing enforces that `full_name`'s owner segment matches `repository.owner.login`, so the field that authenticates the request (and picks the secret/app) is not the field the handlers actually trust and mutate.

### Finding Description
Shipit supports multi-organization configuration where each organization has its own `github_app` entry, including its own `webhook_secret`, in `config/secrets.yml` (`Shipit.github(organization:)`, `github_app_config`) [4](#0-3) [5](#0-4) . The setup docs and test fixtures show `webhook_secret` is explicitly optional/nilable per-organization [6](#0-5) [7](#0-6) . When `webhook_secret` is blank for an organization, `verify_webhook_signature` unconditionally returns `true`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [8](#0-7) 

`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the secret used for `verify_webhook_signature`) based on `repository_owner`, which is read from the same untrusted, unauthenticated JSON body being verified:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

But once the signature check passes (trivially, for an org with no configured `webhook_secret`), the payload is dispatched to handlers, which locate the actual `Repository`/`Stack` to act on via a *separate* field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [9](#0-8) 

`PushHandler#process` then triggers `stack.sync_github(expected_head_sha:)` for every non-archived stack matching that repository/branch [10](#0-9) , and other handlers (`PullRequest::LabeledHandler`, `MembershipHandler`, etc.) similarly act on `params.repository.full_name` [11](#0-10) .

**Binding broken:** the organization authenticated (`repository.owner.login`, used to select the verification secret) ≠ the repository written (`repository.full_name`, used by handlers to select the `Stack`/`Repository` to mutate). The signature check never verifies that these two fields are consistent, so authentication of "org A" does not imply authorization over "org B/repo".

### Impact Explanation
On a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration per `docs/setup.md`'s "Using Multiple Github Applications" section), if any one organization has no `webhook_secret` configured (explicitly allowed/nilable per the config schema and shown as an option in the setup docs), an unauthenticated internet attacker can craft a raw webhook POST with:
- `repository.owner.login` = the org with no secret (or any org whose secret the attacker knows), to pass `verify_signature`.
- `repository.full_name` = `victim-org/victim-repo`, an actual tracked repository belonging to a different, properly-secured organization.

This lets the attacker enqueue `GithubSyncJob` for arbitrary target repos (triggering syncing/deploy machinery), or trigger `pull_request` label/edit handlers and `membership` handlers against stacks/teams that belong to organizations the attacker has no legitimate access to — effectively an unauthorized action across organizational trust boundaries, matching the "unauthorized deploy" / cross-repository write class of impact.

### Likelihood Explanation
Requires only a raw HTTP POST to the public `/webhooks` endpoint with no other privileges — the only precondition is a multi-org deployment where at least one configured organization lacks a `webhook_secret` (an explicitly supported, non-default-safe configuration surfaced directly in the documented setup process and default config templates).

### Recommendation
Bind the value used to select the verification secret to the value used for repository resolution: reject the request (or resolve the `Repository`/`Stack` scoping using `repository_owner`+the same key used for verification) unless `repository.full_name`'s owner segment matches the `repository_owner` used to select the `GitHubApp`. Alternatively, require every configured organization to have a non-blank `webhook_secret`, removing the trivial `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with two organizations configured per `docs/setup.md`'s multi-org example, where `OrgAttacker` has `webhook_secret: nil` and `OrgVictim` has a real, unknown-to-attacker secret and a tracked `Stack` for `OrgVictim/victim-repo`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `WebhooksController#create` dispatches to `PushHandler`, which resolves `repository_name` from `full_name` = `"OrgVictim/victim-repo"`, finds the real `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — an action taken against `OrgVictim`'s repository despite the request only ever being "authenticated" against `OrgAttacker`.

      return true unless webhook_secret

    end
