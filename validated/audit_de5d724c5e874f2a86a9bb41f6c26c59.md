### Title
Cross-origin iframe embedding of `/merge_status` leaks authenticated stack/merge-queue state via `postMessage('*')` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#show` explicitly sets `X-Frame-Options: ALLOWALL` and skips authentication enforcement (`skip_authentication only: %i[check show]`), while the session cookie is forced to `SameSite=None; Secure` by `Shipit::SameSiteCookieMiddleware`. Combined with `merge_status.coffee` broadcasting `window.parent.postMessage(..., '*')`, any third-party page can embed the endpoint in a hidden `<iframe>`, cause the victim's browser to send their Shipit session cookie, and receive the authenticated merge status/queue state via the wildcard-targeted `postMessage`.

### Finding Description
The claimed binding is: **stack/merge-queue data leaves the origin only if `current_user.logged_in?` holds for the requesting session** — i.e., `response body/postMessage payload == f(session[:user_id])` should require that `session[:user_id]` was established via the legitimate top-level OAuth login flow at the Shipit origin, not via an implicit cross-site cookie replay.

Tracing the path:
- `force_github_authentication` is skipped for `show`/`check` via `skip_authentication only: %i[check show]` [2](#0-1) , so the controller relies solely on `current_user.logged_in?` inside `show` to gate content: unauthenticated users get `logged_out` template while authenticated ones get the real `stack_status` [3](#0-2) .
- `current_user` is derived purely from `session[:user_id]` [4](#0-3) , i.e., from the session cookie automatically attached by the browser to the request.
- The controller explicitly disables framing protection: `response.headers['X-Frame-Options'] = 'ALLOWALL'` [5](#0-4) .
- The Shipit session cookie is rewritten by `SameSiteCookieMiddleware` to always carry `SameSite=None; Secure` whenever the request is over TLS [1](#0-0) , which means browsers will attach it even to third-party/cross-site iframe subrequests (unlike the default `Lax` behavior that would normally block this for non-navigational cross-site requests).
- The JS (`merge_status.coffee`), running inside the framed document, broadcasts height, `queue_enabled`, and `status` via `postMessage(..., '*')` to `window.parent` on every page change/poll [6](#0-5) , without checking the parent's origin, so whichever page embeds the iframe receives the message regardless of its own origin.

Attacker's exact request: host a page with `<iframe src="https://<shipit-host>/merge_status?referrer=https://github.com/OWNER/REPO/pull/N&branch=BRANCH" style="display:none">`, add a `window.addEventListener('message', ...)` listener, and wait for a logged-in Shipit user to visit that page. The victim's browser, holding a valid Shipit session cookie (`SameSite=None`), automatically authenticates the iframe's GET request; the returned page's `poller.onPageChange()` fires immediately on load and posts `{event: 'hctw:stack:info', queue_enabled, status}` to the attacker's origin.

Existing guards do not stop this: `skip_authentication` intentionally bypasses `force_github_authentication` for this action (by design, this endpoint is meant to be embeddable — see `contrib/browser-extension`), and there is no origin check either on the server (no `Origin`/`Referer` enforcement gating cookie-based auth for `show`) or on the client (`postMessage` target is `'*'`, and no message-origin allowlist exists in the coffee file).

### Impact Explanation
An attacker who lures any logged-in Shipit user (any GitHub org member with a Shipit session) to a malicious web page can extract, for arbitrary `owner/repo/pull/branch` combinations, whether the merge queue is enabled and the current merge/deploy status (`success`, `locked`, `failure`, `backlogged`, etc.) for that stack, without ever holding a Shipit session, API token, or GitHub credentials themselves. This is a read of otherwise-authenticated stack state exposed to an unauthenticated cross-origin party, repeatable against any stack/PR combination and any victim who is logged into Shipit and visits the malicious page. This matches "unauthenticated read of stack state" (High) as defined in the impact taxonomy — no secrets (`GITHUB_TOKEN`, `github_access_token`, `api_clients_secret`) are exposed, and no writes/state mutations are demonstrated (the `enqueue`/`dequeue` actions still require the poll/JS logic and are not directly leveraged here), so this is a High-severity confidentiality leak rather than Critical.

### Likelihood Explanation
Preconditions: default Shipit configuration (the `X-Frame-Options: ALLOWALL` and `SameSite=None` cookie behavior are unconditional, not feature-flagged) and TLS termination (`Rack::Request#ssl?` true) — both standard for a production Shipit deployment reachable at `Shipit.host`. Attacker cost is trivial: a static HTML page with a hidden iframe and a `message` listener, no GitHub or Shipit credentials, and no interaction beyond getting a logged-in user to open a link. This is fully repeatable and requires no race conditions or timing tricks — it fires on the first `poller.onPageChange()` call after page load.

### Recommendation
- Restrict `postMessage` target origin in `merge_status.coffee` to an explicit allowlisted origin (e.g., pass/verify the embedding origin) instead of `'*'`.
- Reconsider unconditional `X-Frame-Options: ALLOWALL`; if third-party embedding is required only for a specific trusted origin (e.g., github.com via the official browser extension), use a `Content-Security-Policy: frame-ancestors` allowlist instead of disabling framing protection entirely.
- Since the endpoint is intentionally unauthenticated-tolerant for UX (shows "please log in" to logged-out users), consider not reflecting authenticated-only data (`queue_enabled`, `status`) through `postMessage` unless the requesting origin is verified.

### Proof of Concept
Minitest (integration/controller test) demonstrating the binding break:
```ruby
test "GET show sets X-Frame-Options: ALLOWALL enabling cross-origin embedding of authenticated content" do
  get :show, params: { referrer: 'https://github.com/Shopify/shipit-engine/pull/42', branch: 'master' }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
  assert_response :ok
  assert_includes response.body, 'Ready to ship!' # authenticated stack_status leaked to any framing origin
end
```
Combined with a browser-based (system) test asserting that a cross-origin parent document receives a `message` event containing `queue_enabled`/`status` from the framed `/merge_status` document without any origin check — this second half requires a JS-capable system test, which is outside a plain minitest but the header/body assertion above is sufficient to prove the server-side removal of framing protection for authenticated content.
