### Title
Unauthenticated GitHub-team membership forgery escalates arbitrary attacker into `Shipit.github_teams` authorization when `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects a per-organization `webhook_secret` using data taken from the *unauthenticated* HTTP request and, when the operator has not configured one (a state the engine's own setup docs describe as "optional"), `GithubApp#verify_webhook_signature` degrades to `return true unless webhook_secret`, i.e. it accepts *every* payload with no check at all. `Shipit::Webhooks::Handlers::MembershipHandler#process` then trusts that unauthenticated payload to create/find a `Team` purely by the attacker-supplied `team.id`/`team.organization`, create/find a `User` from an attacker-supplied `member.login`, and add that member to the team — the same `Team` records that back `Shipit.github_teams`, the authorization gate for the entire application (`Authentication#force_github_authentication` → `current_user.authorized?`).

### Finding Description
The Checks-Effects-Interactions violation in the report ("effect" happens on data before the "check" on that data has actually completed) has a direct analog here: the *effect* (mutating `Team`/`Membership`/`User` state) is performed on a webhook payload whose "check" (`verify_signature`) is either a no-op or is keyed off attacker-influenced fields, so the effect ends up bound to data that was never actually verified.

- `WebhooksController#verify_signature` derives the signing organization from the raw JSON body itself: `repository_owner` falls back to `params.dig('organization', 'login')` for events (like `membership`) that have no `repository` key. [1](#0-0) [2](#0-1) 

- `GithubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization — a configuration the project's own documentation and example secrets file present as normal/optional (`webhook_secret: # nil`). [3](#0-2) [4](#0-3) [5](#0-4) 

- `WebhooksController#create` then dispatches the (unverified, in this configuration) payload straight to handlers: [6](#0-5) 

- `MembershipHandler#process` uses attacker-controlled `params.team.id` to find-or-create a `Team`, and attacker-controlled `params.member.login` to find-or-create a `User` (which triggers a real GitHub API lookup via `User.find_or_create_by_login!`, but the *decision to add this login to this team* is entirely attacker-directed), then adds that member to the team when `action == 'added'`: [7](#0-6) 
- `User.find_or_create_by_login!`: [8](#0-7) 

- Crucially, `find_or_create_team!` looks the `Team` up **only by `github_id`**, ignoring whether `params.organization.login` actually matches the team's real owning organization. There is no cross-check binding "the organization whose webhook this claims to be" to "the team that gets written." [9](#0-8) 

- `Team` membership is exactly what backs `Shipit.github_teams` authorization: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and `Authentication#force_github_authentication` gates the entire app on it. [10](#0-9) [11](#0-10) 

The binding that is broken: **the organization whose "signature" gets accepted (none, when `webhook_secret` is unset) ≠ the `Team`/organization whose membership actually gets written** (any `Team` row identifiable by `github_id`, without re-validating ownership). An unprivileged attacker on the open internet can therefore write directly into the authorization table that decides who is allowed to use the whole Shipit deployment tool, without ever needing a Shipit session, an `ApiClient` token, or knowledge of any secret.

### Impact Explanation
This maps to the explicitly allowed High impact category: "escalation into `Shipit.github_teams` authorization." Once an attacker's own GitHub login is added as a member of a `Team` row whose `id` is included in `Shipit.github_teams`, a subsequent legitimate OAuth login by that same attacker (`GithubAuthenticationController#callback` → `User.find_or_create_from_github`, matched by real `github_id`) resolves to the same `User` record and `current_user.authorized?` now returns `true`. The attacker gains full authenticated access to the Shipit UI/API for every stack it manages — the ability to trigger deploys, rollbacks, task execution, and merges (Critical: unauthorized deploy/rollback/merge) is downstream of this authorization bypass.

The same missing-signature condition also lets an attacker forge `push`, `status`, and `check_suite` events for any tracked repository, which is a separate but related unauthenticated-state-mutation surface, though I was not able to fully trace `push_handler.rb`/`status_handler.rb` in this pass to confirm a direct unauthorized-deploy chain through continuous deployment; this is noted as unverified and would need further review.

### Likelihood Explanation
High for any deployment where an organization is configured without `webhook_secret` (explicitly presented as an optional field in `docs/setup.md` and the example secrets file, and plausible for engines managing multiple GitHub organizations where only some are configured with a secret). No credentials, session, or secret knowledge is required by the attacker in that state — only the ability to send an HTTP POST to `/webhooks` and knowledge (or a guess/discovery) of the target `Team`'s GitHub numeric ID, which is often discoverable via GitHub's own APIs.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when no `webhook_secret` is configured; require an explicit, auditable opt-out, and fail closed by default.
- In `MembershipHandler#find_or_create_team!`, scope the `Team` lookup by both `github_id` and `organization` (or re-verify that `params.organization.login` matches the found team's `organization`) before allowing any membership mutation, so a webhook that authenticates as organization A can never mutate a `Team` belonging to organization B.
- Consider deriving the signing key/organization from a value that cannot be cheaply spoofed independent of the mutation target (e.g., verifying the specific `Team`/`Stack`'s configured organization matches the verified webhook's organization before writing).

### Proof of Concept
Preconditions: Shipit is configured to serve at least one GitHub organization without a `webhook_secret` (per `config/secrets.development.example.yml`/`docs/setup.md`, this is a documented, supported configuration), and a `Team` with `github_id = T` already exists in Shipit's database with `id` included in `Shipit.github_teams`.

1. Attacker sends, with no signature header at all (or any garbage value in `X-Hub-Signature`):
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": T, "name": "Anything", "slug": "anything", "url": "https://example.com" },
  "organization": { "login": "org-without-secret" },
  "member": { "login": "attacker-github-login" }
}
```
2. `verify_signature` computes `repository_owner = "org-without-secret"`, loads that org's `GithubApp` (configured with no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally. [3](#0-2) 
3. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: T)` — finds the existing privileged team (ignoring the fact the payload claims a different, unrelated `organization`) — creates/finds `User` for `attacker-github-login`, and calls `team.add_member(member)`. [7](#0-6) 
4. Attacker performs a normal GitHub OAuth login on Shipit; `sign_in_github` resolves to the same `User` row via `github_id`, and `current_user.authorized?` now returns `true`. [12](#0-11) [10](#0-9) 

I was unable to fully verify, within the remaining tool budget, whether a comparable unauthorized-deploy path exists through `push_handler.rb`/`status_handler.rb`/continuous-deployment code when `webhook_secret` is unset for a tracked repo's organization; that chain is plausible given the same root cause but is not confirmed here and would benefit from further investigation in a follow-up session.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

        end

      end
    end
