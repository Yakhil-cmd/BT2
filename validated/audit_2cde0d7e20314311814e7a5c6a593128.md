## Finding

### Title
Share-price reset via zero-balance "initial deposit" branch in AA liquidity-pool pattern, exploitable atomically through chained AA secondary triggers - (File: test/samples/uniswap_like_market_maker.oscript, aa_composer.js)

### Summary
The bug class in the report is a **share-price reset caused by a "divide-by-zero fallback to a default price"** combined with an **atomic borrow/repay primitive** that lets an attacker manipulate the pool state and revert it within a single logical transaction. Ocore's Autonomous Agent (AA) engine provides exactly this atomic-chaining primitive through secondary AA triggers, and the officially shipped example AA template `test/samples/uniswap_like_market_maker.oscript` implements exactly the same "reset to default price when balance is zero" logic that the Solidity report exploited.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript`, the "invest in MM" case computes the pre-deposit balances by subtracting the current trigger's own output from `balance[...]`, and falls back to a naive 1:1 issuance formula whenever either side of the pool is at zero: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```

This is the same pattern as OpenZeppelin's `ERC4626._convertToAssets`, which falls back to a default 1:1 price whenever `totalAssets`/`totalSupply` are zero — the exact root cause abused in the referenced report. Here, whenever the pool's `$asset_balance` (or `$bytes_balance`) is driven to zero while `var['mm_asset_outstanding']` is still non-zero (e.g., after repeated `divest`/`exchange` operations reduce one side of the pool to zero through rounding, or after a full-redeem call), the very next depositor is minted shares using the "initial deposit" 1:1 branch instead of the correct proportional formula. This effectively **resets the pool's share price**, letting an attacker who controls both the draining and the re-depositing step capture the yield/value that legitimate LPs (`mm_asset_outstanding` holders) are still owed.

What makes this reachable "atomically," analogous to a flash loan, is that Ocore's AA engine natively supports **atomic multi-hop AA execution within a single top-level trigger**: a primary trigger to AA A can cause A to pay AA B, which is automatically re-triggered as a *secondary trigger* in the very same top-level `handlePrimaryAATrigger` transaction (single DB `BEGIN…COMMIT`), and B can pay back into A, re-triggering A again — all validated and committed together before anything becomes visible to other units: [2](#0-1) 

This is demonstrated directly by the `chain of AAs` test, where a primary AA pays a secondary AA which pays back to the original trigger address, entirely inside one atomic response chain: [3](#0-2) 

The whole chain is bounded only by `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, not by any restriction preventing round-trips back into a pool AA: [4](#0-3) 

Combining these two facts: an attacker can build a helper AA that, within one atomic chain, (1) redeems its LP shares in the market-maker AA (driving `$asset_balance` or `$bytes_balance` toward zero due to integer rounding), (2) immediately re-deposits within the same chain hitting the "initial deposit" 1:1 branch, and (3) walks away holding shares priced without regard to `mm_asset_outstanding`'s true backing — diluting/mispricing the remaining LPs' shares, exactly mirroring the flash-loan vault-deflation exploit against `PrincipalToken.flashLoan`.

### Impact Explanation
Because the AA chain execution is atomic and fully deterministic, an attacker who can post a single trigger unit can, in one on-chain operation, force a liquidity-pool AA built on this template into the zero-balance edge case and re-mint pool shares at the naive 1:1 price rather than the fair, balance-proportional price. This directly causes unauthorized redistribution of pooled `base`/asset funds away from honest LPs to the attacker — a concrete fund-loss/mispricing impact for any AA following this officially documented pattern, not merely a resource-only or no-impact issue.

### Likelihood Explanation
The precondition (one side of the pool balance reaching exactly zero while outstanding shares remain non-zero) requires either full-redemption timing or accumulated rounding from `round()` calls in the exchange branches, both of which are achievable by a determined single attacker controlling both the pool and their own helper AA within one atomic multi-hop trigger — no reliance on other users, network conditions, or privileged roles. This mirrors the "low/medium, but real" likelihood acknowledged by the report's own authors for the ERC4626 case.

### Recommendation
- In `uniswap_like_market_maker.oscript`, never fall back to a raw 1:1 issuance ratio when only one side of the pool balance is zero while `var['mm_asset_outstanding']` is non-zero; instead treat that as an invalid/locked state (bounce) or track a persisted invariant (e.g., last-known price) rather than deriving it from `balance[...]` at call time.
- More generally, any AA template shipped as reference documentation that computes share/issue ratios from `balance[...]` should account for the fact that `balance[...]` can be transiently manipulated within the same atomic secondary-trigger chain (see `aa_composer.js` `handleSecondaryTriggers`), and should not treat a zero denominator as "no existing depositors" without also checking that outstanding share/state variables are zero.
- Document explicitly (as done for the Solidity finding) that DApp developers building pooled/share-based AAs on Ocore must guard against this same "vault deflation" pattern, since the AA engine's atomic chained-trigger capability makes it just as exploitable as an EVM flash loan.

### Proof of Concept
1. Attacker deploys `uniswap_like_market_maker.oscript`-style pool AA (or targets an existing one built on this pattern) and becomes essentially the sole/majority LP holder of `mm_asset`.
2. Attacker crafts a helper AA that, when triggered, sends a payment to the pool AA redeeming all of its `mm_asset` for `$asset`/`base` (hitting the "divest MM shares" case), driving `$asset_balance` (or `$bytes_balance`) computed in the pool's "invest in MM" case to `0` due to full withdrawal/rounding, while `var['mm_asset_outstanding']` may still be non-zero for other minor holders.
3. In the same atomic secondary-trigger chain (per `aa_composer.js` `handleSecondaryTriggers`, bounded only by `MAX_RESPONSES_PER_PRIMARY_TRIGGER`), the helper AA immediately re-deposits into the pool, hitting the `$asset_balance == 0 OR $bytes_balance == 0` branch and receiving `$issue_amount = balance[base]` worth of `mm_asset` — priced without regard to the true remaining backing.
4. This chain is committed atomically as part of a single top-level unit-processing transaction (`aa_composer.js` `handlePrimaryAATrigger`, single `BEGIN…COMMIT`), so the attacker never risks losing value to another party front-running the drained state, exactly as in the original flash-loan vault deflation attack.
