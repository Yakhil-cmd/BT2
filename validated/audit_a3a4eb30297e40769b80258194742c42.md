### Title
Unverified `repository.full_name` used for target resolution while webhook signature is verified against an attacker-chosen `repository.owner.login` — cross-organization forged commit status / webhook event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class is: a verification step iterates/validates a claim, but the value used to satisfy that claim is not bound to the value that actually drives the state-changing action, so an attacker can supply extra/mismatched data to make an unrelated, unauthorized action look "verified." In Shipit's webhook pipeline, the same mismatch exists: the field used to select **which organization's webhook secret** must validate the signature (`repository.owner.login` / `organization.login`) is never checked for consistency with the field the event **handlers actually use to locate the target Stack/Commit/Repository** (`repository.full_name`). Both fields are read independently from the same fully attacker-controlled, unsigned-until-verified JSON body.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization config to check the HMAC signature against using a value taken straight from the parsed request body: [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` explicitly **skips verification entirely** when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Shipit supports multiple GitHub App configs keyed by organization, each independently configured (`webhook_secret` documented as optional per organization): [4](#0-3) 

Once the request passes (or trivially bypasses) verification, the **raw, unmodified JSON body** is dispatched to handlers: [5](#0-4) 

Every handler resolves its target `Stack`/`Repository` independently, by re-reading `repository.full_name` from that same untrusted payload — with no check that this value corresponds to the organization (`repository.owner.login`) that was used to select the verifying secret: [6](#0-5) 

`StatusHandler` then writes an attacker-supplied GitHub commit status onto any `Commit` matching the given `sha`, globally, with no repository scoping in the lookup: [7](#0-6) 

This breaks the equality that should hold: `organization authenticated (repository_owner used to pick the verifying webhook_secret) == repository actually written (full_name used by the handler to locate the Stack/Commit)`. An attacker can set `repository.owner.login` to any organization configured in Shipit that lacks a `webhook_secret` (satisfying/bypassing verification trivially, since `verify_webhook_signature` returns `true` unless a secret is set), while setting `repository.full_name` to a completely different, victim organization's tracked repository, whose real GitHub App does have a proper secret that the attacker never needs to know.

### Impact Explanation
Once the loose organization used for signature checking is decoupled from the repository actually acted upon, an unprivileged network attacker (no Shipit session, no `ApiClient` token, no knowledge of the victim org's `webhook_secret`) can inject forged webhook events that affect the victim's tracked repository/stack: forcing `PushHandler`/`GithubSyncJob` re-syncs for the victim's stacks, forging `StatusHandler` commit statuses (fabricating a passing/`success` CI status for a real commit sha in the victim repo), or driving other handlers (`CheckSuiteHandler`, `PullRequestHandlers`) using data purportedly belonging to the victim repository. Where deploy safety/readiness in a stack's `shipit.yml` depends on commit statuses being trustworthy, this can materially undermine the deploy-gating trust model, since the "signed" event was never actually signed by, or authenticated against, the victim organization's credentials — this satisfies the "unauthorized deploy" impact class if status-based gating is relied upon by the target stack.

### Likelihood Explanation
Exploitation requires only that: (1) the Shipit instance is configured with more than one organization's GitHub App (a documented, supported configuration), and (2) at least one configured organization omits `webhook_secret` (an optional field per the setup docs, not itself a secret an attacker must steal). Given that, no credentials, sessions, or tokens are needed — the attacker only needs network access to the public webhook endpoint and knowledge of a target commit sha (obtainable from the victim repo's public GitHub history). This is a plausible, low-effort misconfiguration-adjacent condition rather than a certain default, so likelihood is moderate and contingent on deployment configuration.

### Recommendation
Enforce the same binding on both fields used during webhook processing that the report recommends for campaign IDs vs. the opt-in limit: derive the organization used to locate the target `Stack`/`Repository`/`Commit` from the **same value** that was cryptographically verified (or refuse to skip verification when `webhook_secret` is unset for multi-org deployments), and have `Handler#stacks`/`Handler#repository_name` cross-check that the owner segment of `repository.full_name` matches the `repository_owner` used during `verify_signature`, rejecting the payload otherwise.

### Proof of Concept
1. Shipit is configured with two GitHub App orgs: `attacker-org` (no `webhook_secret` set) and `victim-org` (properly configured with a secret, tracking `victim-org/victim-repo` as a Shipit stack).
2. Attacker sends, with no signature header required:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<known commit sha in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` resolves `repository_owner = "attacker-org"`, calls `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` returns `true` immediately because `attacker-org` has no `webhook_secret` configured — no HMAC needed at all [3](#0-2) .
4. `StatusHandler#process` runs unmodified against the full payload and writes a forged "success" status for the given sha, which belongs to `victim-org/victim-repo`, without ever validating anything against victim-org's real webhook secret [7](#0-6) .

**Uncertainty / unverified aspects:** I was unable to fully trace, within the available iteration budget, the exact downstream logic in `app/models/shipit/deploy_spec.rb` / `status/group.rb` that determines whether a forged commit status of this kind is actually consumed as a required check gating deploy eligibility — this would need direct confirmation before treating the impact as a guaranteed "unauthorized deploy" rather than a "forged/unauthenticated commit status write." I also did not verify the exact webhook route path in `config/routes.rb`. A Devin session with full repository access is recommended to confirm both points and validate the fix end-to-end.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
