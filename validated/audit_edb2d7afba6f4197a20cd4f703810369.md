### Title
Webhook signature verification uses an attacker-controlled `repository.owner.login`/`organization.login` field to select the signing key, while handlers independently trust a different attacker-controlled field (`repository.full_name`, `organization.login`) to pick the `Stack`/`Team` acted upon — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against by reading `repository_owner`, itself taken straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), *before* the body has been authenticated. [1](#0-0) [2](#0-1) 

Every event handler then re-derives which internal object to mutate from a *different* field of the same untrusted body (`repository.full_name` for `Stack`/`Repository` lookups, `organization.login` for `Team` creation in `MembershipHandler`), with no check that this value matches the org whose secret was used for verification. [3](#0-2) [4](#0-3) 

Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved app has no `webhook_secret` configured — which is the documented default/optional configuration shown in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml` — an attacker only has to name, in the `owner.login`/`organization.login` field, any org in the fleet that has no secret configured, while pointing `full_name`/target fields at a *different*, protected org's tracked repository/team. [5](#0-4) [6](#0-5) 

### Finding Description
The engine explicitly supports multi-tenant deployments where each GitHub organization has its own `GitHubApp` config (`app_id`, `installation_id`, `webhook_secret`, `oauth`), selected at runtime via `Shipit.github(organization:)`. [7](#0-6) [8](#0-7) 

The trust binding that should hold is: *"the organization whose secret authenticated this webhook" == "the organization/repository the payload is allowed to mutate."* This binding is never enforced:

1. `WebhooksController#verify_signature` picks the verification key using `repository_owner`, which is read from the raw, unauthenticated JSON body before any cryptographic check occurs: [9](#0-8) 
2. `Handler#stacks` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a completely separate field of the same body: [3](#0-2) 
3. `MembershipHandler#process` creates/updates a `Team` (used for `Shipit.github_teams` authorization) keyed off `params.organization.login`, and adds an arbitrary `member.login` to it: [10](#0-9) 
4. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected app has no `webhook_secret` — a state that is the shown default in every shipped example secrets file: [5](#0-4) 

Because none of these code paths cross-check that the "authenticating" field and the "acted-upon" field name the same organization/repository, an attacker with no credentials at all can craft a webhook POST that:
- Names, in `repository.owner.login` (or `organization.login`), any org configured in the fleet **without** a `webhook_secret` (satisfying the signature check trivially), and
- Names, in `repository.full_name` (or `organization.login` for membership), a **different**, protected org/repo/team that Shipit actually tracks.

The `X-Github-Event`/body then drives real mutations against that unrelated target: `PushHandler` triggers `stack.sync_github(expected_head_sha: <attacker-chosen sha>)`, `StatusHandler`/`CheckSuiteHandler` inject fabricated CI state for arbitrary commits, and `MembershipHandler` can add an arbitrary GitHub login (which the attacker can then authenticate as via the normal OAuth login flow) as a member of a `Team` that backs `Shipit.github_teams` authorization. [11](#0-10) [12](#0-11) 

### Impact Explanation
This is a Critical/High severity authentication-bypass class finding, matching the required impact bar:
- **Escalation into `Shipit.github_teams` authorization**: `MembershipHandler` lets a forged `membership` event add any GitHub login (including the attacker's own, once they log in via the standard OAuth flow) to a `Team` used by `User#authorized?` to gate all engine access. [12](#0-11) 
- **Unauthorized commit-status/CI signal injection** against an arbitrary tracked repository's stack via `StatusHandler`/`CheckSuiteHandler`, which can feed false "green" signals into `shipit.yml`-driven safety checks, contributing to an unauthorized deploy/merge.
- **Forged push/sync triggering** on an unrelated stack via `PushHandler` → `stack.sync_github`.

### Likelihood Explanation
Requires no privileged account, no `webhook_secret` leak of the *targeted* org, no TLS interception, and no host misconfiguration beyond the exact multi-tenant configuration the engine documents and ships example templates for (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`). Any Shipit instance that tracks more than one GitHub organization, where at least one has an unset `webhook_secret` (the shown default), is exploitable by an anonymous, unauthenticated HTTP client against `/webhooks`.

### Recommendation
- Require every configured GitHub App/organization to have a non-blank `webhook_secret`; refuse to boot or refuse all webhook processing for orgs without one, rather than treating "no secret" as "always verified."
- After a signature is verified for organization `O`, enforce (in `WebhooksController` or `Handler`) that every organization-identifying field used later by handlers (`repository.owner.login`, `repository.full_name`'s owner segment, `organization.login`) equals `O`; reject the request otherwise.
- Do not derive the verification key from the same untrusted body used to select the mutation target — bind both to a single, consistently-validated organization identity.

### Proof of Concept
Given a Shipit instance configured with two orgs, `orgNoSecret` (no `webhook_secret` set — the documented default) and `victim-org` (properly secured, with a tracked stack `victim-org/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": { "owner": { "login": "orgNoSecret" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-existing-sha-in-victim-repo>"
}
```
`verify_signature` calls `Shipit.github(organization: 'orgNoSecret')`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), regardless of the `X-Hub-Signature` header or absence thereof. [1](#0-0) [5](#0-4) 
`PushHandler` then resolves the target purely from `repository.full_name`, acting on `victim-org/victim-repo`'s stack even though signature verification never touched `victim-org`'s secret. [3](#0-2) [11](#0-10) 

An equivalent forged `membership` event with `organization.login: "orgNoSecret"` replaced conceptually — note `MembershipHandler` actually keys the `Team` off `params.organization.login` directly (single field, no owner/full_name split), so the stronger cross-organization variant applies to `push`/`status`/`check_suite`/PR handlers which split "owner" (verification) from "full_name" (target) as shown above; the `membership` case is exploitable whenever the *named* organization itself lacks a `webhook_secret`, letting an attacker fabricate arbitrary team membership for that org without any signature at all. [4](#0-3)

```ruby
module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
