### Title
User-controlled swap routes can hide authorized wallet-draining token transfers - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Unauthenticated route-selected venue code can add an unrelated token transfer beneath the caller’s signed `swap_collateral` authorization tree. If the caller signs the simulated transaction without validating every authorization child, the venue can transfer arbitrary wallet tokens to an attacker while still satisfying the controller’s measured swap-output and account-risk checks. This is a wallet-theft analog of SSRF: user-controlled data selects an external endpoint, and that endpoint makes an unauthorized request using ambient authority.

### Finding Description
`process_swap_collateral` accepts a caller-supplied `swap` payload and forwards it into `withdraw_and_swap_from_supply` after authenticating only the position owner or delegate. [1](#0-0)  `swap_tokens` treats that payload as opaque router input, invokes the configured aggregator, and checks only the controller’s token input and output balance deltas. [2](#0-1) 

The route can name third-party venue code. That code can call an unrelated token’s `transfer` with the original caller as `from`; Soroban records that call as a child of the caller’s existing authorization root rather than preventing it merely because the route code initiated it. The harness demonstrates this exact behavior through `swap_collateral`: a route-selected pool requests `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`, simulation records it below Alice’s `swap_collateral` invocation, and signing that tree transfers her entire unrelated wallet balance. [3](#0-2)  The enforced-auth test confirms that the same route succeeds once the returned authorization tree contains the rogue transfer. [4](#0-3) 

The controller’s exact-input authorization does not bound this loss because it authorizes a transfer from the controller to the router, while the malicious venue adds a separate child authorization for a transfer from the caller’s wallet. [5](#0-4)  Positive measured output and final solvency also do not bound it because the rogue venue can provide a valid swap result in addition to the hidden wallet transfer. [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary token balances held directly by the victim’s address, including tokens unrelated to the lending position. The victim’s supplied collateral is swapped normally, so the transaction can appear successful while the separate child authorization transfers the victim’s wallet token to the attacker. The demonstrated loss is the full `WALLET_BALANCE`, with the attacker receiving the same amount and the victim retaining the expected swapped collateral. [7](#0-6) 

This is theft of user funds, not merely poor routing or MEV: the venue extracts assets unrelated to the swap input by smuggling an additional authorization-bearing call into the transaction.

### Likelihood Explanation
Any unprivileged user can reach `swap_collateral` for an account they own or control, and the route payload is supplied by that call. [8](#0-7)  The attacker’s practical path is to distribute a malicious route for a victim’s normal collateral swap; simulation then produces a signed authorization tree containing the attacker’s extra transfer. [9](#0-8) 

Execution requires the victim to sign the poisoned authorization tree, so the attack depends on route provenance and client display/signing behavior rather than being fully unilateral. However, opaque route bytes do not make the hidden child obvious, and a caller expecting a normal swap may approve the simulated authorization. That places the issue in the High/Medium range rather than Critical.

### Recommendation
Do not allow controller strategy payloads to invoke arbitrary venue contracts. Restrict route-selected pool addresses to a governance-maintained allowlist of reviewed venue implementations, or otherwise constrain the router to fixed venue contracts rather than arbitrary payload addresses. Contracts and clients should also decode the route and reject any simulated authorization tree containing children other than the expected input-token transfer. Measuring input/output deltas and applying account-risk checks cannot remediate this issue because they do not inspect unrelated authorization-bearing calls made by route code.

### Proof of Concept
1. Alice owns a debt-free lending account with supplied `USDC` and holds an unrelated `wallet_token` in her wallet.
2. An attacker deploys a route-compatible pool configured with `(victim = Alice, wallet_token, attacker, amount)`.
3. The attacker gives Alice a `swap_collateral` transaction for `USDC -> ETH` whose route selects that pool. The contract call is:

   ```text
   controller.swap_collateral(
       caller = Alice,
       account_id = Alice_account,
       current = USDC_market,
       from_amount = 50_000_000_000,
       new = ETH_market,
       swap = malicious_route_xdr,
   )
   ```

   The caller-controlled `swap` argument reaches the router unchanged through `withdraw_and_swap_from_supply` and `swap_tokens`. [10](#0-9) [5](#0-4) 
4. During route execution, the malicious pool performs the normal venue behavior needed to produce a positive `ETH` delta, then executes:

   ```rust
   token::Client::new(&env, &wallet_token)
       .transfer(&alice, &attacker, &WALLET_BALANCE);
   ```

   The test fixture implements exactly this payload. [11](#0-10) 
5. Simulation records the wallet transfer as a child of Alice’s `swap_collateral` authorization. [12](#0-11) 
6. Alice signs the simulated tree. The transaction completes, Alice’s unrelated wallet token balance becomes zero, the attacker receives `WALLET_BALANCE`, and Alice receives the expected swapped `ETH` collateral. [13](#0-12)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

    let stolen_transfer = AuthorizedInvocation {

        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
