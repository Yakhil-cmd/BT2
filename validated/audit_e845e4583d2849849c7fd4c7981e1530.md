### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook by SHA alone, with no scoping to the repository/stack that the webhook was authenticated for. Since `sha` is only indexed per-stack (not globally unique) [1](#0-0) , any onboarded, low-privilege attacker who can get one signed webhook accepted for their own organization can flip the CI status of a commit belonging to a completely unrelated victim stack, as long as they know its SHA.

### Finding Description
The broken binding: the question implies `attacker's authorized CI system == the CI event source accepted by StatusHandler#process for the target Commit row`. In truth the code enforces only `Shipit.github(organization: repository_owner)`'s webhook secret against the webhook body [2](#0-1) , where `repository_owner` is read straight from the attacker-controlled JSON body [3](#0-2) . Verification only proves "the sender knows organization X's webhook secret" — it says nothing about which `Commit`/`Stack` the payload's `sha` may touch.

`StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This query is **global**, not scoped to any stack/repository — it will match commit rows across every tenant stack that happen to share that `sha`. Since the migration only adds a composite index on `(stack_id, sha)` rather than a global uniqueness constraint [1](#0-0) , multiple stacks/repos legitimately can (and are expected to) have `Commit` rows with the same `sha` (e.g., shared history, forks, cherry-picks, or simply two different repos whose commit content and metadata happen to match). `create_status_from_github!` then calls `Status.replicate_from_github!` unconditionally with `state: params.state` [5](#0-4) [6](#0-5) , which fires `schedule_continuous_delivery` on every commit affected [7](#0-6) .

Once the victim's blocking commit gets a `success` status, `Commit#deployable?` becomes true [8](#0-7) , and `Stack#next_expected_commit_to_deploy`/`#next_commit_to_deploy` will select it for continuous delivery [9](#0-8) [10](#0-9) , causing `Stack#trigger_deploy` to ship it and everything before it in the batch [11](#0-10) .

None of the existing guards close this gap: `verify_signature` only authenticates the sender's organization, not the target commit's owner [2](#0-1) ; the `ExplicitParameters` schema for `StatusHandler` only validates shape (`sha`, `state`, etc.), not ownership [12](#0-11) ; and `drop_unhandled_event`/`check_if_ping` are irrelevant to this path.

### Impact Explanation
An attacker who legitimately owns/administers *any* repository onboarded to the same Shipit instance (a normal, unprivileged action — anyone can add their own repo as a stack if the instance allows self-service onboarding, which is the documented workflow) can send a validly-signed `status` webhook for their own org that carries an arbitrary victim `sha`. This lets them write a `Status` row (and cascade a deploy) for a `Stack`/`Commit` they do not own or control, satisfying the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" Critical impact categories. Because the lookup is a bare `Commit.where(sha:)` with no stack/repo filter, this is repeatable against any victim stack whose blocked commit SHA the attacker can learn (commit SHAs of tracked branches/PRs are typically visible via the Shipit UI, GitHub, or prior webhook broadcasts).

### Likelihood Explanation
Preconditions: (1) attacker has (or can create) an onboarded organization/repo on the target Shipit instance with a known webhook secret (or one where `webhook_secret` is unset, since `verify_webhook_signature` returns `true` when blank [13](#0-12) ); (2) the victim stack has `continuous_deployment` on and an undeployed commit blocked purely on CI state; (3) attacker knows the victim commit's SHA. All three are realistic in a multi-tenant Shipit deployment and require no Shipit session, API token, or GitHub secret belonging to the victim — only the attacker's own legitimately-issued webhook secret for their own onboarded org.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s) whose repository matches the authenticated webhook's `repository_owner`/`full_name`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_for(payload) })`, rather than a bare global `Commit.where(sha:)`. More generally, every webhook handler that resolves records by SHA/branch/repo should filter by the repository identified in the authenticated payload, not rely on a global unique-looking key.

### Proof of Concept
Add a minitest (e.g. `test/models/shipit/webhooks/handlers/status_handler_test.rb` or controller test) that:
1. Creates two stacks/repos: `victim/repo` (fixture with `continuous_deployment: true`, `maximum_commits_per_deploy` set, and an undeployed commit `C` with a blocking/pending status) and `attacker/repo` (onboarded with a known/blank webhook secret).
2. Creates a `Commit` row in `attacker/repo`'s stack with the **same `sha`** as commit `C`.
3. Stubs/uses `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as in `WebhooksControllerTest`) to simulate a validly-signed webhook for `attacker/repo` only — no webhook for `victim/repo` is sent.
4. POSTs a `status` webhook (`X-Github-Event: status`) with `repository.owner.login` = attacker org, `sha` = `C.sha`, `state` = `success`.
5. Asserts: `C.reload.state == 'success'`, `assert_difference('Deploy.count')` on the victim stack, and `victim_stack.deploys.last.until_commit == C` (or the last batched commit under `maximum_commits_per_deploy`) — proving a deploy was triggered on the victim stack from an attacker-only-signed webhook.

    def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
