### Title
Webhook signature verified against the org named in `repository.owner.login` but the event is applied to the stack named in `repository.full_name` — allows cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` HMAC against using an attacker-controlled field of the very same JSON body (`repository.owner.login`, or `organization.login`), while every event handler resolves the *actual* `Stack`/`Repository` that gets mutated from a **different** field of the same body, `repository.full_name` (via `Handler#repository_name`/`Handler#stacks`). Nothing ties these two fields together, so a valid signature computed with organization A's webhook secret is accepted as proof of authenticity for a payload whose `repository.full_name` names a stack that belongs to a completely different organization B hosted on the same Shipit instance.

### Finding Description
`verify_signature` picks the app/secret purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and passed to `Shipit.github(organization: repository_owner)` to fetch that organization's `webhook_secret` for HMAC verification. This is the *only* authentication check performed before the payload is dispatched: [3](#0-2) 

Every downstream handler, however, determines which `Repository`/`Stack` to act on from a *different* field, `repository.full_name`: [4](#0-3) [5](#0-4) 

`PullRequest` handlers (open/reopen/label/close) do the same via `params.repository.full_name`: [6](#0-5) 

The signature-verification path (`repository.owner.login`) and the target-resolution path (`repository.full_name`) are never cross-checked against each other. The binding the app implicitly assumes — "the organization whose secret signed this request" == "the organization that owns the repository being written to" — is never enforced in code.

Each configured GitHub App/organization on a Shipit deployment has its own independently provisioned `webhook_secret`, read from `lib/shipit/github_app.rb`: [7](#0-6) [8](#0-7) 

Because a legitimate administrator of organization A's GitHub App legitimately possesses A's own `webhook_secret` (it is theirs to configure, not a secret of the target), they can construct an arbitrary JSON body, set `repository.owner.login = "orgA"` and `repository.full_name = "orgB/target-repo"`, sign the whole raw body with A's secret, and POST it to the shared `/webhooks` endpoint. `verify_signature` will fetch org A's secret (matching `repository.owner.login`), successfully verify the signature, and then hand the full payload to handlers that act on `orgB/target-repo` — a stack outside org A's ownership.

### Impact Explanation
Depending on the `X-Github-Event` header chosen, this cross-tenant forgery lets an org-A administrator drive Shipit actions against org B's stacks without ever holding org B's credentials:
- `push` → forged `PushHandler` triggers `GithubSyncJob` to ingest attacker-influenced commit history into org B's stack (`app/models/shipit/webhooks/handlers/push_handler.rb`), which can seed data used by later deploy/merge decisions.
- `pull_request` events → forged open/reopen/label/close handlers can unarchive/archive review stacks or manipulate merge-queue label state for org B's repositories.
- `status`/`check_suite` → forge commit statuses/check runs Shipit trusts for deployability (`ignore_ci`/CI gating), potentially enabling an otherwise-blocked deploy to proceed.

This crosses the "cross-repository writes" / "unauthorized deploy or merge" bar (Critical) once combined with existing deploy/merge automation (e.g., continuous deployment, merge queue) that consumes this webhook-driven state, because it lets one tenant's credentials manipulate another tenant's stack state on a shared Shipit instance.

### Likelihood Explanation
Exploitability requires: (1) a Shipit deployment configured with more than one GitHub organization/App (a documented, supported configuration via `Shipit.github(organization:)`), and (2) the attacker being a legitimate admin/holder of one onboarded organization's own webhook secret — not the target's. No Shipit session, ApiClient token, or the target organization's secrets/keys are needed, satisfying the "unprivileged relative to the victim org" bar. The likelihood is moderate: it depends on multi-tenant hosting, but the code path itself has no mitigating check, so any such deployment is affected.

### Recommendation
After verifying the HMAC, cross-check that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) actually matches the owner implied by `repository.full_name` (and, more robustly, that the resolved `Repository`/`Stack` record's own configured organization matches the organization whose secret validated the signature) before dispatching to handlers. Alternatively, resolve the repository/stack first, derive the expected organization from that record, and use it (not attacker-suppliable payload fields) to select the verification secret.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `github_apps.<org>.webhook_secret` (a normal multi-tenant setup).
2. As someone who legitimately controls `orgA`'s GitHub App (and thus knows `orgA`'s `webhook_secret`), build a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, successfully verifies the signature using `orgA`'s secret.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `stacks` from `repository.full_name = "orgB/target-repo"` and enqueues `GithubSyncJob` against `orgB`'s stack — despite the request never being authenticated by anything belonging to `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
