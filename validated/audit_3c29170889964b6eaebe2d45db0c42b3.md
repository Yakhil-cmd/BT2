### Title
Webhook signature verification is silently bypassed for any organization without a configured `webhook_secret` - (File: lib/shipit/github_app.rb)

### Summary
The external report describes a case where signature verification logic fails to correctly validate a cryptographic signature, effectively allowing forged/unsigned payloads to be accepted. The equivalent bug class exists in Shipit's GitHub webhook signature verification: when the per-organization `webhook_secret` is not configured, `verify_webhook_signature` unconditionally returns `true`, treating the request as verified without ever checking `X-Hub-Signature`.

### Finding Description
`GithubApp#verify_webhook_signature` is defined as: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

The webhook secret is optional and only read from config: `@webhook_secret = @config[:webhook_secret].presence` [2](#0-1) . Documentation for `github.webhook_secret` explicitly frames it as optional ("If you've set a webhook secret during the App creation, you should copy it here") [3](#0-2) , and the generated `secrets.yml` template leaves it blank by default [4](#0-3) .

The controller entry point resolves which organization's `GithubApp` (and therefore which `webhook_secret`) to use directly from attacker-controlled JSON body fields, before any signature check occurs: [5](#0-4) [6](#0-5) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Because `repository_owner` is read from the unauthenticated JSON payload, and because `verify_webhook_signature` returns `true` whenever that organization's `webhook_secret` is blank, the equality that should hold — "the organization whose signing key authenticated this request" == "the organization/repository the payload claims to act on" — breaks down: an attacker can pick any organization known to Shipit's multi-tenant config that happens to have no `webhook_secret` set, and the request sails through `verify_signature` with zero cryptographic validation. All subsequent event handlers (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc., dispatched via `Shipit::Webhooks.for_event(event)`) then process the forged, attacker-controlled body as if it were an authentic GitHub webhook.

### Impact Explanation
Once verification is bypassed, the attacker can forge any supported webhook event for any repository/organization lacking a `webhook_secret`, including:
- `push` events that enqueue `GithubSyncJob` against a target branch, influencing what commits Shipit considers deployable.
- `status`/`check_suite` events that fabricate commit statuses/check results, potentially satisfying deploy-safety gates.
- `membership` events that create/delete `Team`/`Membership`/`User` records, which can feed into `Shipit.github_teams` authorization decisions used elsewhere in the app.

This crosses the "unauthenticated write to stack/commit state" and "escalation into `Shipit.github_teams` authorization" impact categories without requiring any Shipit session, API token, or the real `webhook_secret`.

### Likelihood Explanation
Likelihood is high for any installation with more than one configured organization where not every organization has set a `webhook_secret` (which the docs and generator treat as optional/blank by default). No credentials are needed — the attacker only needs network access to `POST /webhooks` and knowledge of an organization name configured in Shipit that has a blank secret.

### Recommendation
- Make `webhook_secret` mandatory for every configured organization, and fail closed (return `false`/reject) when it is missing, instead of returning `true`.
- Do not select the verification key using attacker-supplied payload fields before the signature has been checked; verify against all configured secrets (or a global secret) and only then resolve the organization/repository.

### Proof of Concept
1. Configure Shipit with at least two organizations, where `org-target` has no `webhook_secret` set (the documented default/optional state).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or any garbage value), and a JSON body:
```json
{
  "repository": { "owner": { "login": "org-target" }, "full_name": "org-target/some-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `"org-target"`; `Shipit.github(organization: "org-target")` returns a `GithubApp` whose `webhook_secret` is `nil`; `verify_webhook_signature` returns `true` unconditionally [7](#0-6) ; the forged `push` payload is accepted and dispatched to handlers as a legitimate GitHub webhook.
