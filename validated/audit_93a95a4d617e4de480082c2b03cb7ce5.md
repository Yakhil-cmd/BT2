### Title
Unauthenticated `/debug/pprof` and `/metrics` HTTP endpoints allow anyone with network access to git-sync's HTTP port to dump process memory, disclosing credentials — (File: `main.go`, flags `--http-pprof`/`--http-bind`)

### Summary
The C4 finding is a missing-authorization bug: a function meant to be invoked only by the privileged caller (`rebalance`) can instead be invoked by anyone, letting them observe/benefit from privileged internal state. The closest reachable analog in `git-sync` is the optional HTTP endpoint exposed by `--http-bind`, `--http-metrics`, and `--http-pprof`: once enabled, these handlers are registered with no authentication or authorization check, so any actor who can reach the bound address/port (e.g., another pod on the same node, or any client if bound to a non-loopback address) can call them, just as "anyone" could call `harvest()`.

### Finding Description
`git-sync` optionally starts an HTTP server when `--http-bind` is set [1](#0-0)  and, if `--http-pprof` is also set, exposes the full `net/http/pprof` debug surface at `/debug/pprof` [2](#0-1) . The e2e test suite confirms these routes respond with plain `200 OK` to unauthenticated `curl` requests once the server is up, with no credential, token, or network-policy check performed by git-sync itself: `/`, `/metrics`, and `/debug/pprof/` are all reachable identically [3](#0-2) . Neither the CLI flag definitions nor the HTTP endpoint documentation mention any access control, and the only mitigation suggested in the docs is deployment-level network restriction, which is not enforced by the binary.

Because git-sync's process handles secrets in memory during its lifetime — e.g., `--password`/`--password-file`/`$GITSYNC_PASSWORD`, `--credential` JSON blobs (URL/username/password), `--cookie-file` contents, `--ssh-key-file` material, and short-lived GitHub App tokens obtained via `--github-app-*` flags [4](#0-3) [5](#0-4)  — the pprof `heap` and `goroutine` profiles can capture and expose these secrets to any caller that can reach the endpoint, without needing to compromise the git-sync process itself.

### Impact Explanation
An unauthenticated network peer that can reach the `--http-bind` address can call `/debug/pprof/heap` or `/debug/pprof/goroutine?debug=2` and potentially recover credentials/tokens resident in process memory (passwords, cookies, SSH keys, GitHub App tokens), matching the "credential or token disclosure" impact category. This is analogous to the original bug in that a function/endpoint intended to be operated in a trusted context is reachable by an unprivileged caller, defeating the intended access boundary.

### Likelihood Explanation
This requires the operator to explicitly opt in via `--http-pprof` (and `--http-bind`) — flags that exist for debugging and are documented as needing to be paired with network restrictions. Given git-sync's common sidecar deployment model where the HTTP port may be reachable from other containers/pods in the same namespace or, if misconfigured, from a wider network, this is a realistic but flag-gated and deployment-dependent exposure, not a default-on vulnerability.

### Recommendation
- Do not expose `/debug/pprof` (or `/metrics`) without requiring the caller to authenticate, or bind these endpoints to loopback-only by default.
- Document/require that `--http-bind` be restricted to `127.0.0.1` when `--http-pprof` is enabled, or add a mux-level check (token/allow-list) before pprof handlers execute.
- Consider zeroing or minimizing retention of secret material in memory after use to reduce the blast radius of any memory-dump exposure.

### Proof of Concept
Given the required flags:
```
git-sync \
  --repo=<repo-with-auth> \
  --root=/tmp/root \
  --username=... --password-file=/creds/pass \
  --http-bind=":8080" \
  --http-pprof
```
Any actor with network access to port 8080 can run:
```
curl http://<pod-ip>:8080/debug/pprof/heap -o heap.out
go tool pprof -text heap.out   # or strings heap.out | grep -i pass
```
to attempt extraction of secret material retained in process memory, without any credential of their own — directly analogous to "anyone can call harvest" bypassing the intended privileged-caller restriction. Note: I could not fully trace the exact mux-registration line numbers for `/debug/pprof` in `main.go` within the indexed content; the behavior is confirmed via the README documentation and the e2e test assertions cited above rather than a direct code excerpt of the handler registration.
