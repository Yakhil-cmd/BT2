### Title
Bridge operators can handle value transfers for unregistered tokens, enabling unauthorized asset transfer or mint — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

`handleERC20Transfer` and `handleERC721Transfer` in the Kaia service-chain bridge contracts accept any caller-supplied `_tokenAddress` without verifying it is registered in the bridge's `registeredTokens` mapping. The outbound path (`_requestERC20Transfer` / `_requestERC721Transfer`) correctly enforces `onlyRegisteredToken`, but the inbound handle path has no equivalent guard. A single bridge operator (default threshold = 1) can therefore call either handle function with an arbitrary, unregistered token address and cause the bridge to transfer tokens it holds — or mint tokens for which it has minter role — to any recipient.

### Finding Description

`_requestERC20Transfer` is gated by both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

`handleERC20Transfer`, which executes the actual asset movement, carries only `onlyOperators`: [2](#0-1) 

The same asymmetry exists in `BridgeTransferERC721.sol` — `_requestERC721Transfer` has `onlyRegisteredToken` / `onlyUnlockedToken`: [3](#0-2) 

while `handleERC721Transfer` has only `onlyOperators`: [4](#0-3) 

The actual asset dispatch inside `handleERC20Transfer` unconditionally calls mint or transfer on the caller-supplied address: [5](#0-4) 

The Go relay layer (`bridge_manager.go`) does look up the counterpart token before calling `HandleERC20Transfer`, but this is an off-chain check that any operator can bypass by calling the contract directly: [6](#0-5) 

The default operator threshold is **1**, set in the `BridgeOperator` constructor, and the deployer is automatically an operator: [7](#0-6) 

### Impact Explanation

- **Non-mintBurn mode**: An operator calls `handleERC20Transfer(txHash, from, attacker, unregisteredTokenAddr, amount, nonce, blockNum, data)`. The bridge executes `IERC20(unregisteredTokenAddr).safeTransfer(attacker, amount)`. Any ERC-20 balance the bridge holds for that token (e.g., tokens accidentally sent to the bridge, or tokens held for other bridge purposes) is drained to the attacker's address.
- **MintBurn mode**: The bridge calls `ERC20Mintable(unregisteredTokenAddr).mint(attacker, amount)`. If the bridge has been granted minter role on any token not yet registered (e.g., during a token migration or partial setup), that token can be minted without limit.
- The same applies to ERC-721 tokens via `handleERC721Transfer`.

This constitutes an **unauthorized transfer or mint of bridged assets** — directly within the allowed impact gate.

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is 1, so a single operator acting alone is sufficient.
- Operators are semi-trusted parties (not the owner/admin), and their keys are held by bridge relay nodes that are separate from the chain owner.
- The attack requires no user interaction and no on-chain precondition beyond the operator's key being available.
- The contract is `public`, so the operator can call it directly without going through the Go relay.

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` (and optionally `onlyUnlockedToken(_tokenAddress)`) to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guards already present on the outbound request functions:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
{
    ...
}
```

Apply the same fix to `handleERC721Transfer` in `BridgeTransferERC721.sol`.

### Proof of Concept

1. Deploy the bridge in non-mintBurn mode. Register `tokenA`. Accidentally send `tokenB` (unregistered) to the bridge (e.g., a user mistakenly calls `tokenB.transfer(bridgeAddr, 1000)`).
2. As the single operator (threshold = 1), call:
   ```
   bridge.handleERC20Transfer(
       anyTxHash,
       anyFrom,
       attacker,          // recipient
       tokenB,            // unregistered token
       1000,              // full balance
       unusedNonce,
       anyBlockNum,
       ""
   )
   ```
3. The bridge executes `IERC20(tokenB).safeTransfer(attacker, 1000)` with no revert — `tokenB` is not in `registeredTokens` but the contract never checks.
4. `attacker` receives 1000 `tokenB` tokens that were held by the bridge, with no corresponding cross-chain request having been made.
