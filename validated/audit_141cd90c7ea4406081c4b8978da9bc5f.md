### Title
Third-party collateral top-up can indefinitely block permissionless bad-debt cleanup - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
`clean_bad_debt` is permissionless, but only admits an account while its debt exceeds collateral and its collateral remains at or below the fixed 5 USD dust threshold. A third party can top up an already-held collateral position, moving the account just above that threshold while it remains insolvent; every subsequent cleanup then reverts with `CannotCleanBadDebt`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::clean_bad_debt` delegates to `process_clean_bad_debt`, which requires only the caller’s authorization and then calls `clean_bad_debt_standalone`. [1](#0-0) [4](#0-3) 

The admission gate computes the account’s aggregate debt and unweighted collateral, then admits the dust-capped path only when `total_debt > total_collateral` and `total_collateral <= BAD_DEBT_USD_THRESHOLD`; otherwise it reverts. [5](#0-4) [6](#0-5) 

A caller who is neither the account owner nor a delegate cannot create a new supply leg, but can supply to every `HubAssetKey` already present in the victim’s `supply_positions`. [3](#0-2)  That supply is measured into the pool, converted into supply shares, and merged into the victim’s collateral position. [7](#0-6) [8](#0-7) 

Consequently, for an account with `C <= BAD_DEBT_USD_THRESHOLD` and `D > C`, an attacker can add enough collateral to produce `BAD_DEBT_USD_THRESHOLD < C' < D`; the account remains insolvent, but the permissionless cleanup gate is closed. [2](#0-1)  If the topped-up collateral is `no_seize`, the same newly added leg can also block proportional liquidation, because nonzero `no_seize` collateral aborts seizure while standalone bad-debt cleanup is the path intended to bypass listing flags. [9](#0-8) 

### Impact Explanation
Blocking `clean_bad_debt` prevents the pool seizure/write-down path from running: `execute_bad_debt_cleanup` is what reclassifies remaining collateral as revenue, releases supply and borrow usage, writes off the debt positions, deletes the account, and burns its NFT. [10](#0-9) [11](#0-10) 

The result is continued exposure to an insolvent account and an indefinite inability to use the permissionless cleanup path while the donated collateral keeps `C` above the dust cap. [2](#0-1)  The owner cannot normally withdraw the donated collateral out of an insolvent account because `withdraw` requires owner/delegate authority and re-checks post-withdrawal solvency. [12](#0-11)  Recovery therefore requires collateral value to fall below the threshold, another route such as liquidation to reduce the position, or the owner-gated `force_socialize_bad_debt`, which omits the dust cap. [13](#0-12)  This is a temporary freezing/protocol-insolvency impact consistent with a Medium finding. [14](#0-13) 

### Likelihood Explanation
The attack uses only the public `supply(caller, account_id, spoke_id, assets)` entrypoint with the attacker as `caller`, the victim’s account id, the victim’s stored spoke id, and one existing victim collateral key. [15](#0-14)  No owner, delegate, administrator, leaked key, upgrade, malformed token, or off-chain action is required. [3](#0-2) 

The main prerequisites are that the victim already holds the chosen supply leg, that leg remains open to supply entry, and the donation can raise unweighted collateral above 5 USD while debt remains higher. [16](#0-15) [17](#0-16)  Once the victim is near the threshold, the required top-up can be as small as one token base unit if that unit moves the WAD valuation across `BAD_DEBT_USD_THRESHOLD`. [6](#0-5) 

### Recommendation
Preserve the permissionless cleanup gate against non-rescue collateral donations. For a foreign `supply` top-up into an account that has debt, reject the deposit when the resulting state would remain insolvent (`D > C`) but have `C > BAD_DEBT_USD_THRESHOLD`; allow the top-up when it either stays below the cleanup cap or restores `D <= C`. This check belongs beside `require_third_party_existing_supply` or the post-deposit risk evaluation in `process_supply`, so the attacker cannot use a partial donation solely to disable `clean_bad_debt`. [18](#0-17) [5](#0-4) 

### Proof of Concept
The following scenario uses an existing collateral leg, so the third-party supply restriction passes. [3](#0-2) 

```rust
// Preconditions:
// - victim holds collateral_key in supply_positions
// - debt value D = 10 USD
// - collateral value C = 5 USD
// - D > C, and C <= BAD_DEBT_USD_THRESHOLD
// - collateral_key may additionally be no_seize to block liquidation

let top_up = amount_whose_usd_value_is_at_least(1); // moves C to 5 USD + 1 WAD

controller.supply(
    attacker,
    victim_account_id,
    victim_spoke_id,
    vec![(collateral_key, top_up)],
);

// Now C' > BAD_DEBT_USD_THRESHOLD but C' < D.
// Reverts with CollateralError::CannotCleanBadDebt.
controller.clean_bad_debt(any_caller, victim_account_id);
```

The second call reaches `socialize_bad_debt`, computes `total_debt > total_collateral`, and then fails because `is_socializable_bad_debt` also requires collateral at or below the dust cap. [5](#0-4)  If `collateral_key` is `no_seize`, the added collateral also defeats the ordinary seizure path, leaving the governed `force_socialize_bad_debt` path as the immediate workaround. [19](#0-18) [13](#0-12)

```markdown
### INV-HALT-02 — Frozen, paused, and no_seize gate different legs

Listing flags act independently: entry rejects `paused` and `frozen`; user
```

```markdown
# Force-socialize bad debt

This runbook covers governance-authorized removal of an insolvent account.
Use it when collateral exceeds the fixed $5 dust limit of permissionless
`clean_bad_debt`. Cleanup can also proceed when `no_seize` blocks ordinary
liquidation.

The account must hold debt, with ceil risk debt strictly greater than half-up
unweighted collateral (`D > C`). An unhealthy health factor alone does not
qualify. The forced path has no collateral dust cap.

**Cleanup is irreversible.** All remaining collateral becomes protocol revenue.
All remaining debt is written off against its own markets' supply indexes,
including when collateral and debt share a market. There is no automatic netting
or insurance payment. The account is deleted and its position NFT burns.
```
