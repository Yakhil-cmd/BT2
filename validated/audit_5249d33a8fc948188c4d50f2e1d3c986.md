### Title
Front-running a secondary AA in a multi-AA response chain forces a full revert, causing DoS and fee loss for the trigger sender - (File: `aa_composer.js`)

### Summary
`aa_composer.js` implements chained/secondary Autonomous Agent (AA) invocations: when a primary AA response sends funds to another AA, that AA is automatically re-invoked as a "secondary trigger" (`handleSecondaryTriggers`). If **any** secondary AA in the chain bounces, the entire primary response — including all already-computed side effects (state var updates, asset issuance, intermediate payments) — is rolled back via `revert()`. An unprivileged attacker who observes a pending (not-yet-stable) multi-step AA composition can send a cheap, unrelated trigger to one of the downstream secondary AAs referenced in that chain, deliberately changing shared state so that when the victim's chain reaches that AA it bounces, forcing the whole composed operation to revert. This mirrors the `TOFT`/`lzCompose` bug class where front-running one sub-message in a composed batch nukes the entire batch.

### Finding Description
`handleSecondaryTriggers` in `aa_composer.js` (lines 1702-1757) is invoked whenever a primary AA response produces payments to other AA addresses (`arrOutputAddresses`). For each such address it recursively calls `handleTrigger` with `bSecondary = true`: [1](#0-0) 

The result handler treats any bounce from a secondary AA as fatal to the *entire* primary chain, not just that branch: [2](#0-1) 

`revert()` then unwinds everything that was done by the primary AA and any already-successful secondary AAs in the chain — restoring balances/state vars and rolling back the DB transaction to the savepoint before any of the chain's outputs were produced — before finally bouncing the primary trigger: [3](#0-2) 

AA trigger processing itself operates on **stable** units, but the AA composition a user constructs (e.g. "send bytes/asset to AA A, which forwards to AA B, which does X") is visible on the DAG (and in most deployments, in the network/mempool) well before it becomes stable, since triggers are only executed once the trigger unit's MCI is stable (`handleAATriggers` reads from `aa_triggers` table after stabilization). This is a wide window in which any observer can identify that a specific secondary AA (e.g. AA B) is about to be invoked as part of someone else's multi-AA composition, and can post their own cheap, unprivileged trigger unit to AA B first, altering shared state variables (counters, "only-once" flags, balance thresholds, etc.) that AA B's logic depends on. When the victim's chain later reaches AA B as a secondary trigger, AA B's evaluated formula now takes a different branch (or fails a precondition) and bounces — which, per the code above, reverts the *entire* primary response chain, not just the secondary branch.

### Impact Explanation
This is directly analogous to the reported `TOFT`/`lzCompose` bug: an unprivileged party can grief a benign multi-step operation by manipulating one link in the chain, causing the whole composed operation to fail atomically. Consequences:
- The trigger sender's payload/header commissions paid to post the trigger unit are non-refundable and lost regardless of the bounce.
- Any legitimate multi-AA workflow (asset issuance + forwarding, definition-then-activation flows, cross-AA "remote calls" as seen in the test suite chains) that depends on cooperating secondary AAs can be reliably and repeatedly DoS'd by a griefer at minimal cost (one cheap trigger to the target secondary AA), since `revert()` unconditionally unwinds the whole chain whenever any downstream secondary AA bounces.
- This is a general design property reachable by any unprivileged AA trigger sender against any composed multi-AA transaction, and it results in denial-of-service / loss of fees for victims, matching "AA fund loss" and "network unable to confirm the intended transaction" impact categories.

### Likelihood Explanation
Likelihood is significant wherever AAs are chained (a documented and tested pattern — see `test/aa_composer.test.js` "chain of AAs", "issue recently defined asset", "define new AA and activate it", "calling a chain of remote functions"). Any secondary AA whose branching logic depends on mutable shared state (counters, flags, balances) is a target. The attack requires no privileged role — only the ability to post an ordinary unit/trigger to the target AA, which any user can do, and the timing window (unstable-to-stable transition) is generally on the order of the DAG's finality delay, ample time to react to a visible pending composition.

### Recommendation
- Do not unconditionally revert the entire primary chain when a secondary AA bounces; instead, treat a secondary-AA bounce as a local, contained failure for that branch (already partly true for `bSecondary` sub-branches — extend this containment to the top of the chain as well), so unrelated/independent parts of the response chain are not destroyed by griefing one AA.
- Where full-chain atomicity is required by design, document and mitigate the front-running window: e.g., allow AAs to be written so state-dependent branches that gate secondary calls are not trivially manipulable by third parties (guidance/lint warnings), or introduce a mechanism for the state read used by secondary-trigger gating to be pinned to the trigger unit's inclusion point rather than the AA's state at execution time.
- At minimum, surface this risk to AA authors so compositions relying on secondary AAs' current state (rather than state committed at trigger-unit inclusion) are flagged as unsafe against front-running.

### Proof of Concept
1. Deploy `AA_B` whose logic depends on a state var, e.g. `if: "{trigger.data.x == var['expected']}"` used only in the secondary-call branch, with `var['expected']` mutable by any trigger.
2. Deploy `AA_A` (the "primary") whose response chain forwards funds to `AA_B` expecting `AA_B`'s current `var['expected']` to match, as in the `test/aa_composer.test.js` "chain of AAs" pattern (lines 156-252) but with a data-dependent branch in the secondary AA.
3. Victim posts a trigger unit to `AA_A` intending the standard successful chain (`AA_A` → `AA_B`).
4. Before the victim's trigger unit's MCI stabilizes, attacker posts a low-cost trigger directly to `AA_B` that updates `var['expected']` to a different value.
5. When the victim's unit stabilizes and `AA_A`'s response reaches `handleSecondaryTriggers` → `AA_B`, `AA_B` bounces due to the mismatched state.
6. Per `aa_composer.js:1743-1750` and `revert()` (`aa_composer.js:1759-1783`), the entire `AA_A` response — including any completed side effects — is rolled back and `AA_A`'s trigger bounces, losing the victim's transaction fees for no fault of their own.
