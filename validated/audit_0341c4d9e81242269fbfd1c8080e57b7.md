### Title
Unchecked division by zero in `PoolState::token_price_x32` can permanently brick swaps on a pool - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` computes token prices using the raw `/` operator instead of the `checked_div`/`floor_div`/`ceil_div` helpers used everywhere else in the fee/curve math in this codebase. [1](#0-0) 
Every other division site in the program (curve math, fee math) is guarded against a zero divisor: `CheckedCeilDiv::checked_ceil_div` [2](#0-1) , `Fees::ceil_div`/`floor_div` which explicitly check `fee_denominator == 0` [3](#0-2) , and `ConstantProductCurve::swap_base_input_without_fees`/`swap_base_output_without_fees` which use `checked_div`/`checked_ceil_div` (still `.unwrap()`ed, but at least go through the checked path) [4](#0-3) . `token_price_x32` is the sole exception that performs a bare `u128 / u128` division.

### Finding Description
`token_price_x32` is invoked unconditionally on every swap through `PoolState::get_swap_params`, for both the `ZeroForOne` and `OneForZero` trade directions: [5](#0-4) 

Its divisors, `token_0_amount` and `token_1_amount`, are the results of `vault_amount_without_fee`, i.e. the live vault balance minus the accumulated (unswept) protocol/fund/creator fee ledger for that token: [6](#0-5) 

If either vault's on-chain balance is ever reduced to exactly the sum of its recorded `protocol_fees_*` + `fund_fees_*` + `creator_fees_*` fields, `vault_amount_without_fee` legitimately returns `0` for that token (this is not itself an error condition — `checked_sub` succeeds because the subtraction result is `0`, not negative). The subsequent raw division `token_0_amount as u128 * Q32 as u128 / token_1_amount as u128` (or the symmetric expression) then divides by zero and the instruction panics.

This is called from both `swap_base_input` and `swap_base_output`, before any of the `ok_or(ErrorCode::ZeroTradingTokens)` guards that protect the curve/fee math further down the instruction: [7](#0-6) [8](#0-7) 

Because a panic aborts the whole transaction on Solana, the vault balance that produced the zero divisor is never mutated and persists — every future swap attempt against that pool (in either direction) will re-enter `get_swap_params`, recompute the same zero token amount, and panic again. Deposit and withdraw are unaffected because they route through `lp_tokens_to_trading_tokens`, which uses `checked_div`/`?` and fails gracefully with `ErrorCode::ZeroTradingTokens` instead of panicking. The net effect is that swap functionality for the affected pool becomes permanently unusable (a liquidity-freeze from the swapper's perspective) once this exact vault state is reached, while the underlying tokens remain locked (LPs can still withdraw, but no further trading/price-discovery is possible for that pool).

### Impact Explanation
Any unprivileged swapper who can drive a pool's input or output vault balance down to exactly equal the accumulated fee ledger for that token (via repeated/large `swap_base_input`/`swap_base_output` calls, which are attacker-reachable with attacker-chosen `amount_in`/`amount_out_received`) permanently disables swapping on that pool. This is a availability/fund-freezing impact on the pool's trading function and is analogous to the CVE's root cause: an unchecked, non-`checked_div` integer division whose divisor can become zero under attacker-influenced conditions.

### Likelihood Explanation
Reaching the exact boundary (`vault_balance == fee_ledger_sum`) requires precise sizing of swap amounts, but this is entirely computable off-chain by any user who can read the pool/vault state (all public) and issue a swap with a chosen `amount_in`/`max_amount_in`/`amount_out_received`, i.e. it is reachable from a single, unprivileged, attacker-chosen transaction without any special permissions or non-default build flags.

### Recommendation
Replace the raw division in `PoolState::token_price_x32` with a checked division (`checked_div`) and propagate `None` as `ErrorCode::ZeroTradingTokens`/`ErrorCode::MathOverflow` rather than allowing a panic, mirroring the pattern already used in `Fees::ceil_div`/`floor_div` and `CheckedCeilDiv::checked_ceil_div`.

### Proof of Concept
1. Deploy a pool and let its vault accumulate protocol/fund/creator fee ledger entries via normal swaps (`protocol_fees_token_1`, `fund_fees_token_1`, `creator_fees_token_1` increase via `PoolState::update_fees`).
2. As an unprivileged swapper, submit a `swap_base_output` (or a sequence of `swap_base_input`) with `amount_out_received`/`amount_in` chosen so that `output_vault_amount - (protocol_fees_token_1 + fund_fees_token_1 + creator_fees_token_1) == 0` exactly after the swap.
3. Any subsequent call to `swap_base_input`/`swap_base_output` against that pool now re-computes `total_output_token_amount == 0` inside `get_swap_params`, hits `token_price_x32`'s raw division by that zero value, and the instruction panics, permanently blocking further swaps on the pool (deposit/withdraw remain unaffected since they don't call `token_price_x32`).

Note: I could not fully verify from the indexed code whether an additional lower-bound check elsewhere in `swap_base_output`/`swap_base_input` (beyond what was retrievable) prevents the output vault from reaching exactly the fee-ledger sum in practice; a Devin session with full repository access would be needed to trace all guard conditions in `instructions/swap_base_output.rs` past line 76 to conclusively confirm or rule out this exact boundary is reachable in one or multiple transactions.

impl CheckedCeilDiv for u128 {
    fn checked_ceil_div(&self, rhs: Self) -> Option<Self> {
        let mut quotient = self.checked_div(rhs)?;
        let remainder = self.checked_rem(rhs)?;
        if remainder != 0 {
            quotient = quotient.checked_add(1)?;
        }
        Some(quotient)
    }
}

fn ceil_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(u128::from(fee_numerator))?
        .checked_add(fee_denominator)?
        .checked_sub(1)?
        .checked_div(fee_denominator)
}

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}

    pub fn swap_base_input_without_fees(
        input_amount: u128,
        input_vault_amount: u128,
        output_vault_amount: u128,
    ) -> u128 {
        // (x + delta_x) * (y - delta_y) = x * y
        // delta_y = (delta_x * y) / (x + delta_x)
        let numerator = input_amount.checked_mul(output_vault_amount).unwrap();
        let denominator = input_vault_amount.checked_add(input_amount).unwrap();
        let output_amount = numerator.checked_div(denominator).unwrap();
        output_amount
    }

    pub fn swap_base_output_without_fees(
        output_amount: u128,
        input_vault_amount: u128,
        output_vault_amount: u128,
    ) -> u128 {
        // (x + delta_x) * (y - delta_y) = x * y

        let input_amount = numerator.checked_ceil_div(denominator).unwrap();
        input_amount
