## Finding: Webhook signature verification is bound to `repository.owner.login` / `organization.login`, but event processing acts on `repository.full_name`

### Title
Cross-organization webhook forgery via mismatched signature-verification and repository-resolution fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects the GitHub App/organization (and therefore the `webhook_secret` used to verify the HMAC signature) using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate state resolve the target `Repository`/`Stack` using the unrelated field `repository.full_name`. Because these two fields are never cross-checked, a payload can be signed under one organization's secret while acting on a completely different organization/repository's stack.

### Finding Description
In `WebhooksController#verify_signature`, the organization used to look up the webhook secret is derived like this: [1](#0-0) [2](#0-1) 

That resolved `github_app` (`Shipit.github(organization: repository_owner)`) is only used to validate the HMAC signature via `verify_webhook_signature`, which is itself keyed off that organization's `webhook_secret`: [3](#0-2) 

Critically, if that organization has no `webhook_secret` configured, verification unconditionally returns `true`, i.e. no signature is required at all: `return true unless webhook_secret`.

However, the actual `create` action re-parses the same raw body and dispatches it to handlers, which never look at `repository.owner.login`/`organization.login` again — they resolve the target repository purely from `repository.full_name`: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` looks the repository up purely by `full_name`, with no relation to the organization used for signature verification: [7](#0-6) 

This is the same bug class as the reported `minOutputAmount` issue: a value used for a security check (`minOutputAmount` for slippage / `repository.owner.login` for HMAC key selection) is not the same value acted upon later (post-fee balance / `repository.full_name` used to pick the target). The equality that should hold — "organization whose secret authenticated the payload" == "organization/repository the payload's actions are applied to" — is never enforced.

`Shipit` explicitly supports multi-organization configurations, each with its own `webhook_secret`, as shown in the setup docs and secrets templates: [8](#0-7) 

### Impact Explanation
In a multi-organization Shipit deployment, an attacker who can obtain a validly-signed payload for organization A (e.g., because organization A has no `webhook_secret` configured — which is explicitly supported/`nil`-able per the docs — or because they otherwise know/leak A's secret) can craft a payload whose `repository.owner.login`/`organization.login` is A, but whose `repository.full_name` points at a repository belonging to organization B. The signature check passes (verified against A, or bypassed entirely if A has no secret), while `PushHandler`, `PullRequest::*Handler`, etc. act on B's stack:
- `push` events call `stack.sync_github(expected_head_sha: ...)` on B's stack, which for stacks with `continuous_deployment: true` can trigger an unauthorized deploy of B.
- `pull_request` `labeled`/`closed`/`reopened` events archive/unarchive/provision review stacks belonging to B.
- `membership` events create teams/users based on forged data.

This crosses the "unauthorized deploy" / "cross-repository writes" threshold called out as Critical impact.

### Likelihood Explanation
Exploitability requires: (1) a Shipit instance configured with more than one GitHub organization (a documented, supported configuration), and (2) either one configured organization lacking a `webhook_secret` (explicitly allowed — shown as `# nil` in `config/secrets.development.shopify.yml`) or an attacker who has legitimate signing capability for at least one configured organization (e.g., is an admin of one org's GitHub App webhook, but not others sharing the same Shipit instance). Given multi-tenant Shipit deployments are an intended use case, and per-org `webhook_secret` is optional, this is a realistic misconfiguration/attack surface, not a purely theoretical one.

### Recommendation
Bind the organization used for signature verification to the same field used for repository resolution. Concretely, `WebhooksController` should re-derive/pass through `repository.full_name`'s owner and require it to match the `repository_owner` (or `organization.login`) used to select the `webhook_secret`, rejecting the request (422) on mismatch. Additionally, consider disallowing/warning when a configured organization has a blank `webhook_secret` in production, since that currently causes `verify_webhook_signature` to always return `true`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `org-a` (no `webhook_secret`) and `org-b` (has stacks to protect).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: 'org-a').verify_webhook_signature` returns `true` when `org-a`'s `webhook_secret` is blank.
3. `WebhooksController#create` re-parses the body and dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name('org-b/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on `org-b`'s stack — an org whose secret was never checked — potentially triggering a continuous deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
