### Title
Stack-scoped API token can read any stack's build status via CC.xml due to missing `stack_id` scoping in `CCMenuController#stack` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController#require_permission!` only validates the `operation:scope` string pair (e.g. `read:stack`) and never receives or checks the target stack instance. `CCMenuController` overrides `#stack` to resolve directly via `Stack.from_param!(params[:stack_id])` instead of using the base class's stack-scoped `#stacks` helper, so a token restricted to one stack (`stack_id`) can fetch CI status (`cc.xml`) for any other stack.

### Finding Description
The broken binding is: **the stack touched must belong to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`**, i.e. `stack ∈ current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. This binding holds in `BaseController#stack`: [1](#0-0) 

but `CCMenuController` overrides it, bypassing the scoping entirely: [2](#0-1) 

The permission check that runs before `#show`, `require_permission :read, :stack`, translates into `require_permission!(:read, :stack)` → `current_api_client.check_permissions!('read', 'stack')`: [3](#0-2) [4](#0-3) 

`check_permissions!` builds `"#{operation}:#{scope}"` = `"read:stack"` and checks it's present in the client's `permissions` array — it takes no stack argument and has no knowledge of `params[:stack_id]`. The stack-scoping that is supposed to enforce "this token's `stack_id` limits it to one stack" lives only in `#stacks`/`#stack` in the base controller and is never invoked by `CCMenuController#show`: [5](#0-4) 

Attacker request: holding a legitimate `ApiClient` token created with `stack_id: X` and `permissions: ['read:stack']` (a normal, minimally-privileged, stack-scoped read token — not a stolen secret), the attacker calls `GET /api/stacks/cc.xml?stack_id=Y&token=<token>` for stack `Y` in a different repository. `authenticate_api_client` succeeds (valid token), `require_permission!(:read, :stack)` succeeds (permission string matches), and `#stack` resolves `Y` directly via `Stack.from_param!`, with no comparison against `current_api_client.stack_id`. `#show` renders `Y`'s latest deploy/rollback and build status.

Existing guards do not stop this: `authenticate_api_client` only verifies token validity, not scope; `require_permission!`/`check_permissions!` check only the permission string; and the `stacks` scoping method exists but is dead code for this controller because it defines its own `#stack`.

### Impact Explanation
Any holder of a valid, intentionally stack-scoped, read-only API token for repository X can read build/deploy status (latest deploy/rollback outcome, running state) for any other stack/repository Y on the same Shipit instance, simply by changing the `stack_id` query parameter. This is an authorization bypass across tenant boundaries within the same Shipit deployment — the token's declared scope restriction (`stack_id`) is not enforced by this endpoint. This matches "unauthorized read of stack state" (High) since it exposes cross-repository CI/build state to a token that was never granted access to that repository's stack; it is fully repeatable against any stack ID on the instance.

### Likelihood Explanation
Requires only a legitimate, low-privilege `ApiClient` token scoped to a single stack with `read:stack` permission — a normal, commonly issued credential type in Shipit (e.g. for CI status badges). No secrets, no GitHub access, no operator privileges needed beyond possessing one such token. The attacker simply substitutes `stack_id` in the request URL/query string. Cost is a single HTTP GET; fully repeatable for any target stack ID.

### Recommendation
Change `CCMenuController#stack` to reuse the base controller's scoped resolution, e.g. `def stack; @stack ||= stacks.from_param!(params[:stack_id]); end`, so the `current_api_client.stack_id` restriction from `#stacks` is applied, consistent with `StacksController` and other controllers that rely on `#stacks`/`#stack`.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read a different stack's status" do
  stack_x = shipit_stacks(:shipit)
  stack_y = create_stack(repository: create_repository(name: 'other-repo'))

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-token',
    stack_id: stack_x.id,
    permissions: ['read:stack'],
  )

  get "/#{stack_y.to_param}/cc.xml", params: { token: client.authentication_token }

  # Binding under test: stack ∈ Stack.where(id: current_api_client.stack_id)
  # LHS (actual behavior): response resolves stack_y despite stack_x scoping
  # RHS (expected/secure behavior): request should be rejected (404/403) because stack_y.id != client.stack_id
  assert_response :not_found # currently fails: returns 200 with stack_y's CC status, proving the bypass
end
```
