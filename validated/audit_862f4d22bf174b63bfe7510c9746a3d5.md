### Title
Cross-Organization Webhook Confusion Allows Unauthorized Stack Sync/Deploy Trigger via Organization/Repository Binding Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC `webhook_secret` used to verify a signature) based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. However, once the signature check passes, the actual event handlers (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config(organization)`), these two fields are never required to agree, so a webhook signed with one organization's legitimate secret can be routed to act on a completely different organization's repository/stack.

### Finding Description
`verify_signature` derives the signing organization strictly from `repository.owner.login` (or `organization.login`) and fetches that organization's `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`: [1](#0-0) 

`Shipit.github` / `github_app_config` look up a per-organization webhook secret from `secrets.github`, confirming that distinct organizations onboarded into the same Shipit instance have distinct, independently known secrets: [2](#0-1) 

After the signature check passes, the raw parsed JSON body (fully attacker-controlled, since only the signature over the whole body is checked — not the internal consistency of its fields) is dispatched to handlers: [3](#0-2) 

`Handler#stacks` and `PushHandler#process` resolve the target repository/stack from `repository.full_name`, a field never compared against the `repository.owner.login`/`organization.login` value used for signature verification: [4](#0-3) [5](#0-4) 

**Binding broken (equality that should hold but doesn't):**
`organization_used_for_signature_verification (repository.owner.login) == organization_of_repository_actually_written (repository.full_name)`

Before the attack: signature verification and payload action both implicitly assumed to reference the same repository/organization, because in a legitimate GitHub-originated webhook the two fields are always consistent.

After the attack: an attacker who administers "org-attacker" (a distinct organization legitimately configured in the same multi-tenant Shipit instance, with its own known `webhook_secret`) can send a POST to `/github/webhooks` with `repository.owner.login`/`organization.login` = `org-attacker` (so the signature verifies with the secret they know) while `repository.full_name` = `org-victim/victim-repo`. `verify_signature` succeeds against `org-attacker`'s secret, and `PushHandler` (or other handlers relying on `repository.full_name` / `Repository.from_github_repo_name`) then acts on `org-victim`'s `Stack`, invoking `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA.

### Impact Explanation
This breaks the deployment-trust boundary between organizations sharing a single Shipit installation: an attacker who only controls one organization's webhook secret can force a GithubSyncJob (and, if `continuous_deployment` is enabled on the victim stack, an eventual deploy trigger) against a different organization's repository/stack, at a commit SHA of the attacker's choosing (any commit reachable in the victim repo's history, e.g. from a stale branch/PR). This can result in an unauthorized deploy/redeploy of the victim stack to a commit that was never approved for that pipeline run — directly matching the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Requires the instance to be configured for multiple GitHub organizations/apps (`TOP_LEVEL_GH_KEYS` vs per-org keys in `secrets.github`), which is an explicitly supported configuration (`github_organizations`, `github_app_config`). The attacker only needs legitimate access to one organization's own webhook secret (which they control, since they are the admin of their own onboarded org) — no access to the victim org, no GitHub App private key, and no Shipit session/API token is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the signature-verifying organization and the payload's acted-upon repository together: after `verify_webhook_signature` succeeds, re-derive the repository/stack strictly from data attributable to the verified organization (e.g., require `repository.full_name`'s owner segment to equal `repository_owner` used for verification, or look up the `Repository` scoped to the verified organization only) before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `org-attacker` (secret `S_A`, known/controlled by attacker) and `org-victim` (secret `S_V`, unknown to attacker), each installed as separate GitHub Apps on the same Shipit instance.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-existing-sha-in-victim-repo>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` using their own known secret `S_A`.
4. `POST /github/webhooks` with header `X-Github-Event: push`. `WebhooksController#verify_signature` resolves `repository_owner` = `org-attacker` → fetches `S_A` → signature verifies successfully. [1](#0-0) 
5. `PushHandler#process` resolves the target via `payload.dig('repository', 'full_name')` = `org-victim/victim-repo`, finds `org-victim`'s stacks, and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` — a sync/deploy-relevant action executed on a repository the attacker never authenticated for. [5](#0-4) [4](#0-3)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
