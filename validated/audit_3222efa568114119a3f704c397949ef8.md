### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` and `repository.full_name` in multi-app deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate an incoming webhook against using a single field extracted from the *unverified* JSON body: `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 

Shipit explicitly supports hosting multiple GitHub Apps/organizations from one instance, each with its own independent `webhook_secret`, selected by `Shipit.github(organization:)` / `Shipit.github_app_config(organization)`. [2](#0-1) [3](#0-2) 

The HMAC signature (`X-Hub-Signature`) is only checked against the secret of whichever organization was picked by `repository_owner` — it never confirms that this field agrees with the other repository-identifying field used later, `repository.full_name`, which is what the actual event handlers use to look up the target `Repository`/`Stack` to act on. For example, `PushHandler#repository_name` reads `payload.dig('repository', 'full_name')` independently of `repository_owner`. [4](#0-3) 

Because both `repository.owner.login` (used to select/verify the signing secret) and `repository.full_name` (used to select the repository actually acted upon) are attacker-controlled fields inside the same signed raw JSON body, an attacker who legitimately knows/controls the webhook secret for one organization (`OrgTwo`) hosted on the same Shipit instance can craft a payload where `repository.owner.login = "OrgTwo"` (so the signature verifies against `OrgTwo`'s secret) but `repository.full_name = "OrgOne/some-repo"` (targeting a different organization's repository/stack tracked by the same instance). The controller will accept the request as authentic and dispatch it to handlers, which act on `OrgOne`'s repository based on the forged `full_name`.

This is the same class of bug as the report: a value the signature check is scoped to (`repository_owner`, akin to the deposit-limit's "is there a cap at all" flag) diverges from the value that downstream logic actually mutates state for (`repository.full_name`, akin to `totalDepositedAmountPerUser[_l1Token]`). The binding broken is: **organization authenticated (`repository_owner` used for HMAC secret selection) ≠ repository written (`repository.full_name` used by webhook handlers)**.

### Impact Explanation
This crosses an organizational trust boundary: an attacker with knowledge of one organization's webhook secret (which they may legitimately possess as an admin of that org's GitHub App installation, or which may have leaked) can forge webhook events attributed to a completely different organization/repository hosted on the same Shipit instance. Depending on the handler triggered (`push`, `status`, `check_suite`, `membership`), this can enqueue `GithubSyncJob` for a foreign repository with an attacker-chosen `expected_head_sha`, create/modify commit `Status` records, or otherwise mutate state belonging to a repository/stack the attacker has no legitimate relationship to — a cross-repository/cross-organization write performed without the correct organization's authorization. This matches the "cross-repository writes" Critical impact category, since the write is against `OrgOne` state while only `OrgTwo`'s credential (webhook secret) was actually verified.

### Likelihood Explanation
Exploitability requires the Shipit instance be configured with the multi-organization GitHub App layout (documented and supported feature, see `docs/setup.md` "Using Multiple Github Applications") and requires the attacker to possess a legitimate webhook secret for *any one* of the hosted organizations. Within that scope, no session, API token, or write access to the target repository is needed — only network access to the `/webhooks` endpoint and knowledge of one org's secret. This is plausible in real multi-tenant Shipit deployments where different teams/orgs manage their own GitHub Apps independently but share one Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` and/or `#create`, cross-validate that the organization used to select/verify the signature (`repository_owner`) is consistent with the organization implied by `repository.full_name` (and `organization.login` for org-level events) before dispatching to handlers — reject the request if they disagree. Alternatively, derive the app/secret used for verification strictly from a value that is also authoritative for the repository the handlers act on (e.g., always derive from `full_name`'s owner segment), so a single field cannot be split between "used to pick the secret" and "used to select the target."

### Proof of Concept
Given a Shipit instance configured with `secrets.github` as a hash of `{OrgOne: {...}, OrgTwo: {...}}` (per `test/dummy/config/secrets_double_github_app.yml`), and an attacker who knows `OrgTwo`'s `webhook_secret`:

1. Attacker builds a `push` event JSON body:
```json
{
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  },
  "after": "<attacker-chosen-sha>",
  ...
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
3. `WebhooksController#verify_signature` computes `repository_owner = "OrgTwo"`, calls `Shipit.github(organization: "OrgTwo")`, and `verify_webhook_signature` succeeds because the signature was actually generated with `OrgTwo`'s secret. [5](#0-4) 
4. `create` then dispatches the parsed body to `Handlers::PushHandler`, which resolves the target repository via `payload.dig('repository', 'full_name')` = `"OrgOne/victim-repo"`, i.e., a repository belonging to the un-verified organization, and enqueues a `GithubSyncJob` for it. [4](#0-3) 

Note: I could not fully verify the exact downstream code of `PushHandler#process` and `GithubSyncJob#perform` (their bodies were not retrievable via the available tools before the session ended), so the precise operations performed on `OrgOne`'s stack (e.g., whether it can only trigger a benign re-sync vs. something more consequential like status writes) are not fully confirmed. Due to index size limits, some file contents may not be available — a full Devin session with filesystem access would be needed to inspect `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/jobs/shipit/github_sync_job.rb` bodies to precisely characterize the downstream write impact.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
