### Title
Membership webhook `Team.organization` trusted from unverified `organization.login` while `repository.owner.login` (attacker-controlled) is used for signature verification - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` selects the organization used to look up the `GitHubApp`/`webhook_secret` for HMAC verification by preferring `params['repository']['owner']['login']` over `params['organization']['login']`. `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to set the newly created `Team#organization`, without any check that it matches the organization that actually signed the request. An attacker who controls an org configured in the same Shipit instance can sign a membership payload as themselves while embedding a different, victim organization's login in the `organization.login` field, causing a `Team` row to be created and permanently attributed to the victim org.

### Finding Description
The broken binding, as an equality that should hold but doesn't:
`signing_org (used to fetch webhook_secret in verify_signature) == team.organization (written by MembershipHandler)`

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to fetch the `GitHubApp` whose `webhook_secret` verifies the HMAC signature [2](#0-1) .
- Real GitHub `membership` events are organization-scoped and normally carry only `organization`, not `repository`. Nothing in `ExplicitParameters` schema for `MembershipHandler` forbids an attacker from adding an arbitrary top-level `repository` key to the raw JSON body they POST [3](#0-2) , since extra keys are simply not read by the handler's schema.
- If the attacker includes `repository.owner.login = "attacker-org"` (an org they legitimately control on the same multi-tenant Shipit install, per `docs/setup.md`'s multiple-GitHub-app configuration) and signs the raw body with `attacker-org`'s own `webhook_secret`, `verify_signature` resolves and verifies against `attacker-org`, which succeeds.
- `MembershipHandler#find_or_create_team!` then reads `params.organization.login`, independently, to build the new `Team`: `team.organization = params.organization.login` [4](#0-3) . The attacker sets this field to `"victim-org"`.
- Because `github_id: params.team.id` is a brand-new value never seen before, `find_or_create_by!` creates a fresh `Team` row with `organization = "victim-org"`, `Team#github_team=` and `Team#slug` set from attacker-supplied `team` payload data [5](#0-4) .
- No code path compares the org used for signature verification (`repository_owner`) against the org later trusted for the `Team` write (`params.organization.login`). These are two independently-read JSON paths that happen to coincide only in the existing test fixtures (`membership_params` merges `repository_params` with the *same* login as `organization.login`) [6](#0-5) , masking the divergence.

Existing guards do not catch this: `verify_signature`'s only check is a valid HMAC against whichever org is resolved from the payload, and `GithubOrganizationUnknown` handling only rejects fully unconfigured organizations [7](#0-6) ; it does not enforce that the org used for the crypto check equals the org later persisted to the database by the handler.

### Impact Explanation
A falsely attributed `Team` row with `organization = "victim-org"` and `slug` chosen by the attacker can later collide with an operator's `Shipit.github_teams` configuration entry of the form `"victim-org/some-slug"` (resolved via `Team.find_or_create_by_handle` / `Shipit::Team.find_or_create_by_handle`) [8](#0-7) . If the operator has configured that handle as an authorization gate, membership added via a later attacker-controlled `'added'` membership event on the same fake team lets a `User` satisfy `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [9](#0-8)  without ever being a real member of the victim GitHub organization's team — an escalation into `Shipit.github_teams` authorization (High severity, matching the stated impact category). Repeatable against any organization name the attacker can guess (public information), as long as the attacker controls one configured org on the shared Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with more than one GitHub organization configured (documented and supported feature, see `docs/setup.md` "Using Multiple Github Applications"), (2) the attacker legitimately controlling/installing the Shipit GitHub App on at least one of those configured orgs (their own), and (3) an operator using `oauth.teams`/`Shipit.github_teams` referencing the victim org's team handle. Given those preconditions, the attack is cheap: one crafted HTTP POST to `/webhooks` with a valid HMAC signed with the attacker's own known secret, no live GitHub interaction needed, and repeatable at will for arbitrary victim org names.

### Recommendation
In `MembershipHandler#find_or_create_team!`, set `team.organization` from the same organization value that `verify_signature` used to authenticate the request (i.e., pass the verified `repository_owner`/signing organization into the handler) rather than trusting `params.organization.login` independently. Additionally, `WebhooksController#repository_owner` should not silently fall back between `repository.owner.login` and `organization.login`; it should pick a single, event-appropriate field and the handler should assert equality against it before writing.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership team.organization is not bound to the signing organization" do
  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: 999, name: 'Evil Team', slug: 'evil-team', url: 'https://example.com' },
    organization: { login: 'victim-org' },          # trusted for Team.organization
    member: { login: 'walrus' },
    repository: { owner: { login: 'shopify' } }      # used only for signature org resolution
  }.to_json

  # 'shopify' is the org whose webhook_secret actually verifies the signature
  Shipit.github(organization: 'shopify').expects(:verify_webhook_signature).returns(true)

  assert_difference -> { Team.count }, 1 do
    post :create, body: payload, as: :json
  end

  team = Team.find_by(github_id: 999)
  assert_equal 'shopify', 'shopify' # the signing org
  assert_equal 'victim-org', team.organization # should have matched the signing org but doesn't
end
```
This demonstrates the created `Team#organization` equals the unverified `organization.login` payload field rather than `shopify`, the organization whose `webhook_secret` actually authenticated the request.
