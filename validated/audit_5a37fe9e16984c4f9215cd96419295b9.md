### Title
Webhook signature verification uses an attacker-controlled field decoupled from the resource actually mutated - authentication bypass and `Shipit.github_teams` escalation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App / webhook secret to validate a webhook against using a value read directly out of the same untrusted, unauthenticated JSON body it is about to verify. The `Handler` subclasses that actually mutate state (`PushHandler`, `MembershipHandler`, `StatusHandler`, PR handlers, etc.) then read a *different* field from that same body to decide what repository/organization/team to act on. Nothing binds these two reads together, so the "organization that authenticated" the request is not provably the "organization/repository that is written." This mirrors the report's bug class: a value used for a security-relevant computation (there: rounding order; here: signature-secret selection) is decoupled from the value that ultimately drives the real effect (the amount of FEI paid / here, the repository or team actually mutated), producing a result that violates the intended equality/binding.

### Finding Description
`verify_signature` picks the signing secret this way: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is read from the **unauthenticated request body itself**, and used only to pick which `Shipit.github(organization:)` config (and therefore which `webhook_secret`) to check the signature against: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Critically, if `webhook_secret` is blank for the organization selected via the attacker-controlled `repository_owner` field, verification **unconditionally returns true** — this is documented as optional in `docs/setup.md` ("Webhook secret (optional)"), so a real multi-org deployment can legitimately have one organization configured without a secret while others have one.

Meanwhile, the code that actually performs the mutation looks up the repository from a **different** JSON path in the very same payload: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For the `membership` event, the acted-upon organization/team is read from yet another independent path, and used to create/mutate `Team` and `User`/`Membership` records with no cross-check against the value used for signature selection: [5](#0-4) 

Because `repository.owner.login` (used only for picking the verification secret) and `repository.full_name` / `organization.login` (used for the actual write) are two independently attacker-supplied JSON fields in the same unsigned-until-verified body, there is no cryptographic binding forcing them to refer to the same organization. An attacker can set `repository.owner.login` to an organization configured with a blank/weak `webhook_secret` (satisfying `verify_signature`) while setting `repository.full_name` / `organization.login` / `team` / `member.login` to target a *different*, legitimately-secured organization/repository/team.

`Team.find_or_create_by_handle`/`handle` shows teams are keyed by `"#{organization}/#{slug}"`: [6](#0-5) [7](#0-6) 

and `Shipit.github_teams` (the set of teams that gate application login) is populated from configured OAuth team handles resolved to `Team` records via this same handle scheme: [8](#0-7) 
authorization is then `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: [9](#0-8) 

So a forged, cheaply-authenticated `membership` webhook that references the organization/slug matching one of `Shipit.github_teams`'s handles, with `member.login` equal to the attacker's own real GitHub login, will call `User.find_or_create_by_login!` (fetching the attacker's real GitHub profile via the app's `Shipit.github.api`) and then `team.add_member(member)`, granting that attacker `authorized?` status for the Shipit UI — without ever having produced a valid signature for the secured organization.

### Impact Explanation
This breaks the equality: `organization used to select/verify webhook_secret == organization/team/repository actually mutated by the handler`. Concretely:
- **Escalation into `Shipit.github_teams` authorization** (explicit High-impact bullet): a forged `membership` webhook can add an attacker-controlled `User` to a `Team` matching an authorized team handle, letting the attacker pass `User#authorized?` and log into the protected Shipit application.
- Beyond authorization escalation, the same decoupling lets an attacker forge `push`/`status`/`pull_request`/`check_suite` events targeting any repository configured in Shipit (triggering `GithubSyncJob`, fabricating commit statuses via `StatusHandler#process`, archiving review stacks, etc.), as long as *any one* configured organization in the multi-org config has no `webhook_secret` — a documented, supported configuration.

### Likelihood Explanation
Requires only an unauthenticated HTTP POST to the public `/webhooks` endpoint; no session, API token, or GitHub write access is needed. The only precondition is a plausible, documented Shipit configuration (multi-org GitHub Apps, one of which has an optional/blank `webhook_secret`) — this is explicitly supported by `config/secrets.development.shopify.yml` and `docs/setup.md`, which call the webhook secret "optional." Given this, exploitation is a single crafted JSON payload with mismatched `repository.owner.login` vs. `repository.full_name`/`organization.login` fields.

### Recommendation
Verify the webhook signature using an organization/installation identity that is *not* itself derived from the unauthenticated payload (e.g., verify against every configured secret, or route by an unspoofable server-side mapping such as the delivery's installation ID resolved via GitHub's App API), and, once verified, ensure handlers re-derive the acted-upon organization/repository from the same already-authenticated identity rather than trusting a second, independently-controlled field in the body. Additionally, treat `webhook_secret` as mandatory (fail closed) rather than optional, since a single unsecured org config currently undermines the security of all other configured organizations.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations: `weak-org` (no `webhook_secret` set) and `victim-org` (configured with a real repo/team the attacker wants to influence), as supported by `config/secrets.development.shopify.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://x" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-real-github-login" },
  "repository": { "owner": { "login": "weak-org" } }
}
```
3. `WebhooksController#repository_owner` reads `repository.owner.login` → `"weak-org"`; `Shipit.github(organization: "weak-org")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `MembershipHandler#process` then uses `params.organization.login` (`"victim-org"`) and `params.team` to find-or-create a `Team` matching `victim-org/deployers`, fetches the attacker's real GitHub user via the app's own GitHub API token, and adds them as a member — if `victim-org/deployers` matches a configured `Shipit.github_teams` handle, the attacker becomes `authorized?` and can log into the protected application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
