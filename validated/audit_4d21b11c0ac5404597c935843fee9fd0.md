I found a strong analog to the reported bug class. The relevant code is in `validatePaymentInputsAndOutputs()` in `validation.js`, specifically the check for spender-attested assets.

### Title
All-or-nothing attestation check for spender-attested asset payments causes valid outputs to be blocked by a single unattested recipient - ([File: validation.js])

### Summary
For assets with `spender_attested: true`, `validatePaymentInputsAndOutputs()` requires that **every** output address in a payment message be attested before the entire payment (and hence the whole unit) can be accepted, mirroring the Vault.sol pattern where one bad element in a batch (there: a blacklisted protocol; here: an attestation status controlled by a third-party attestor) causes the entire operation to revert instead of only rejecting/skipping the offending element.

### Finding Description
In `validatePaymentInputsAndOutputs()`, after collecting all unique output addresses of a payment message into `arrOutputAddresses`, the code does: [1](#0-0) 
```js
async.series([
    function(cb){
        if (!objAsset.spender_attested)
            return cb();
        storage.filterAttestedAddresses(
            conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses, 
            function(arrAttestedOutputAddresses){
                if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
                    return cb("some output addresses are not attested");
                cb();
            }
        );
    },
```
`filterAttestedAddresses` (in `storage.js`) queries the `attestations` table and returns only currently-attested addresses. The check requires the returned set to have the *exact same length* as the full `arrOutputAddresses` set — i.e. **all** recipients in the message must be attested, not just the ones that matter to the sender. Attestation status is controlled entirely by third-party attestors defined in the asset (`objAsset.arrAttestorAddresses`, see [2](#0-1)  and [3](#0-2) ), and can be revoked or never granted for an address at any time, independent of the sender.

This is structurally identical to the `Vault.sol` `setDeltaAllocationsInt()` issue: a loop/aggregate check over independent items (protocols there, output addresses here) is validated as an atomic all-or-nothing set instead of item-by-item, and the failing condition for a single item is controlled by an external party (protocol blacklist admin there; asset attestor here), not by the message author.

This same all-or-nothing pattern also appears symmetrically for **inputs** (spender must be attested) at [4](#0-3)  and [5](#0-4) , and is used again when composing wallet payments client-side in `divisible_asset.js`/`indivisible_asset.js`, but the wallet code cannot pre-filter unattested outputs before submission, so users have no way to know in advance which recipient will cause the whole unit to fail.

### Impact Explanation
Any unit (or AA-generated payment message, e.g. a dividend/airdrop payment to a list of addresses) that pays a spender-attested asset to multiple recipients in a single payment message is entirely rejected if even one recipient's attestation is missing or later revoked, even though funds intended for all the other (properly attested) recipients are otherwise valid. For an AA that pays a fixed set of parties (e.g. by iterating over `state` data) in one `payment` message with a spender-attested asset, if one recipient becomes/remains unattested, **every** run of that AA branch bounces, refunding the trigger and never delivering funds to the other, legitimately attested recipients — a denial-of-service/fund-freezing condition triggered by a single third-party-controlled attestation status, not by the sender or the AA logic itself.

### Likelihood Explanation
Any asset issuer can create a `spender_attested` asset (or existing asset's attestor list can revoke an address at any time via `asset_attestors`, see `validateAttestorListUpdate` at [6](#0-5) ). Multi-recipient payments of such an asset (manual multi-output payments, or AA-issued batched payments) are a normal, expected usage pattern, so the condition is easily triggered without any special attacker capability beyond controlling/coordinating with the attestor (or simply having an attestation lapse/never granted for one recipient in a shared payment).

### Recommendation
Instead of requiring `arrAttestedOutputAddresses.length === arrOutputAddresses.length` (all-or-nothing), consider:
- Rejecting/removing the specific unattested output rather than failing the whole payment, when the message allows partial processing (particularly relevant for AA-generated payments), or
- Clearly documenting/enforcing this as intended protocol behavior only for single-recipient transfers, and disallowing multi-recipient payment messages for spender-attested assets to avoid silent DoS surprises, or
- For AA payment composition, validate attestation status of each output individually before adding it to the payment message batch, and only fail/skip the specific unattested output instead of aborting the entire response.

### Proof of Concept
1. Definer creates an asset `A` with `spender_attested: true` and attestor `X`.
2. Attestor `X` attests addresses `B` and `C`.
3. Address `B` posts a divisible-asset payment message of `A` with outputs to both `B'` (change back to self, attested) and `D` (a third address that `X` has never attested).
4. `validatePaymentInputsAndOutputs` collects `arrOutputAddresses = [B', D]`, calls `filterAttestedAddresses`, gets back `[B']` only (length 1 ≠ 2), and returns `"some output addresses are not attested"`, rejecting the **entire** unit — even though the payment to `B'` alone would have been perfectly valid.
5. If this payment is instead generated repeatedly by an AA batching payouts to a fixed list of addresses (one of which, `D`, is unattested or whose attestation is revoked by `X` after the AA's state was set up), every subsequent trigger causes the AA response to bounce, permanently blocking payouts to *all* recipients in that message, not just `D`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
