### Title
Cross-organization webhook trust confusion — signature verified against `repository.owner.login`, but stack/commit actions performed against unrelated `repository.full_name` / global commit SHA - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, a field read directly out of the still-unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  Once "verified", every `Handlers::Handler` subclass resolves the target `Repository`/`Stack` from a *different* field of the same untrusted body, `payload.dig('repository', 'full_name')`, with no check that this value is consistent with the owner used to pick the signing secret. [3](#0-2)  `StatusHandler` goes further and performs no repository scoping at all, matching purely on commit SHA across the whole installation. [4](#0-3) 

### Finding Description
Shipit supports multiple GitHub Apps/organizations in a single deployment, each with its own independently configured `webhook_secret` (see the multi-org fixture with `OrgOne`/`OrgTwo`, each carrying its own — sometimes absent — `webhook_secret`). [5](#0-4)  `Shipit.github(organization:)` looks the app config up by name and is exactly the mechanism `verify_signature` uses. [6](#0-5) 

The equality the engine is supposed to preserve is:
`organization whose secret validated X-Hub-Signature == organization that owns the repository whose stacks/commits are mutated by the handler`.

Before the pull request/attack sequence, in the legitimate flow both sides of that equality are the same GitHub-supplied value, because GitHub always sets `repository.owner.login` consistently with `repository.full_name` for a given repo.

After the attack sequence, the attacker controls the entire raw JSON body before any signature is checked. `verify_signature` computes `repository_owner` from the body and fetches that org's `GitHubApp#verify_webhook_signature`, which:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [7](#0-6) 
so signing is optional per-organization (documented as "if you've set a webhook secret ... copy it here"). An attacker who controls (or has onboarded) any organization in the same Shipit instance — with a blank `webhook_secret`, or with a secret they know because they created that GitHub App — can produce a signature that verifies for `repository.owner.login = "attacker-org"`. The handlers then run against `payload.dig('repository', 'full_name')`, which the attacker sets independently to any other tracked repository, e.g. `"victim-org/victim-repo"`. [3](#0-2) 

`StatusHandler` is the most direct proof: it never touches `stacks`/`Repository` at all, it just does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` across the entire installation, so a signature that verifies for *any* onboarded organization is sufficient to forge a commit status (`state`, `context`, `target_url`, `description`) for any commit SHA tracked by any other tenant's stacks. [4](#0-3)  `PushHandler` and `CheckSuiteHandler` use the cross-org `full_name` lookup to trigger `stack.sync_github(expected_head_sha:)` and `schedule_refresh_check_runs!` on unrelated stacks. [8](#0-7) [9](#0-8) 

This mirrors the CVE's bug class: two values that are supposed to be bound together by validation (bit-length in `Int`/`Dec`; here, "authenticated organization" vs. "acted-upon repository") are validated on different, uncorrelated fields, and the check on one side gives false confidence about the other.

### Impact Explanation
An unprivileged attacker who can create even one organization/repository in a shared multi-tenant Shipit deployment (a supported and documented configuration, `github:` as a map of orgs) can forge GitHub webhooks that mutate state belonging to a completely different, victim organization: injecting fabricated commit statuses (`StatusHandler`) that can flip a commit's deployability, or forcing `sync_github`/check-run refreshes on victim stacks (`PushHandler`/`CheckSuiteHandler`). Since Shipit gates deploy/merge readiness on commit statuses (`deployable_status`/`merge_status` events exist precisely for this), this is a cross-repository write with the potential to enable an unauthorized deploy for a stack the attacker has no access to. This matches the "Critical: cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Requires only that the attacker control one legitimate (even unprivileged) organization onboarded into the same Shipit instance and be able to send an HTTP POST to `/webhooks` — no GitHub App private key, `ApiClient` token, or Shipit session is needed. No knowledge of the victim organization's `webhook_secret` is required at any point, only of the attacker's own org's secret (or exploiting an org that has none configured, which the docs present as optional). This is realistic for any Shipit install serving more than one GitHub organization/team.

### Recommendation
In `Handlers::Handler#repository_name` (and any handler bypassing it, like `StatusHandler`), cross-validate the repository/commit being acted upon against the same organization identity that was used to select the verifying `webhook_secret` in `WebhooksController#verify_signature`, rather than trusting `repository.full_name`/bare commit SHA independently. Concretely, thread the verified `repository_owner` (or the resolved `GitHubApp`) into handler dispatch and reject/ignore any event where `payload.dig('repository','owner','login')` does not match the owner of the resolved `Repository`/`Stack`/`Commit`. Additionally, require `webhook_secret` to be present for every configured organization (treat a missing secret as a hard misconfiguration, not "trust unconditionally").

### Proof of Concept
1. Attacker owns organization `attacker-org`, onboarded into the shared Shipit instance with `webhook_secret` either blank or known to them.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates (trivially, since that org's secret is known/blank to the attacker). [10](#0-9) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit irrespective of `attacker-org` — and calls `create_status_from_github!`, forging a passing status on a commit the attacker never had access to. [4](#0-3)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
