### Title
Missing cosigner-authorization check in `sign` device-message handling allows any paired device to solicit signature/relay of an arbitrary payment unit through a shared/multisig address - ([File: wallet.js])

### Summary
`handleMessageFromHub`'s `"sign"` case in `wallet.js` accepts an attacker-controlled `{address, signing_path, unsigned_unit}` device message from any paired correspondent and, when `findAddress()` resolves the target address to a **locally-held key** (`ifLocal`), immediately proceeds to relay the unit for user confirmation/signing without verifying that the sending device (`from_address`) is actually a cosigner of `body.address`. The equivalent check *does* exist on the `ifRemote` branch, but it is explicitly commented out on the `ifLocal` branch, making the two code paths inconsistent.

### Finding Description
In the coturn CVE, `handle_turn_refresh`'s resume branch located the victim's allocation solely by an attacker-supplied resume identifier, and only copied/verified the *originating* identity when the requesting session was unauthenticated — since the attacker's session was already authenticated (for itself), the copy/verification step was skipped, so `check_stun_auth` validated the request against the attacker's own credentials instead of the real allocation owner's. The authorization decision ended up depending on unrelated pre-existing session state instead of an explicit ownership check tied to the resource being acted upon.

`wallet.js` has the analogous pattern in the `"sign"` message handler [1](#0-0) . `body.address` (and `body.signing_path`) are entirely attacker-controlled by any device that has ever paired with the local wallet (pairing itself requires only a pairing secret exchange, not any relationship to a specific shared address). The handler dispatches to `findAddress()` [2](#0-1) , which returns via `ifRemote` when the signing key lives on another device (and there `from_address` is validated against the list of known cosigners: `if (!other_device_addresses.includes(from_address)) return callbacks.ifError(...)`), but returns via `ifLocal` when the key is stored on the receiving device itself.

On the `ifLocal` branch, the check that would confirm `from_address` is actually one of the address's registered cosigners is explicitly commented out: [3](#0-2) 

The comment "the commented check would make multilateral signing impossible" documents that the authorization gate was intentionally left disabled for this branch to support the "different addresses sign the same message" (multilateral/prosaic/arbiter contract) use case — but this means *any* correspondent device, without being a registered signer of `body.address` at all, can submit a fully-formed `unsigned_unit` (including arbitrary payment outputs) as long as `body.address` merely appears among the unit's `authors`. Because `body.address` need only be an address the local wallet locally controls (which the sender can learn, e.g., via prior shared-address negotiation messages or contract flows that are not gated to a specific counterparty), the sender is not proven to be a party entitled to request a signature over transactions from that address.

This mirrors the coturn root cause precisely: identity/ownership of the resource (allocation in coturn / signing address here) is not re-verified against the requester when a particular internal branch is taken (already-authenticated attacker session in coturn / locally-held key in ocore), even though the parallel branch (`ifRemote`) enforces exactly that check.

### Impact Explanation
If exploited, an arbitrary paired device (not a legitimate cosigner of the multisig/shared address) can trigger the "signing_request" flow for units spending from that shared address, i.e. inject payment requests that reach the user's confirmation UI as if the request were coming from a legitimate cosigner/contract counterparty. Depending on how UI layers surface `from_address` versus `body.address` to the user, this can be leveraged to solicit signatures on transactions the user did not actually intend to sign, potentially leading to unauthorized spending from shared funds. This falls under the accepted impact category of "concrete unauthorized spending" for a paired-device–reachable code path.

### Likelihood Explanation
Requires only a completed device pairing (not membership in the target shared address), which is a low bar to reach for any two obyte wallet users, plus knowledge of a shared address hash the user's wallet locally controls (obtainable from prior contract/shared-address exchanges). No malicious hub or network position is needed — the request travels through the normal hub-relay path and is processed as a valid, correspondent-signed device message.

### Recommendation
Restore/implement an explicit ownership check on the `ifLocal` branch, analogous to `ifRemote`'s cosigner check: verify that `from_address` is a party legitimately entitled to request a signature for `body.address`/`body.signing_path` (e.g., is a registered device in `wallet_signing_paths`/`shared_address_signing_paths` for that address, or is the recognized counterparty for a specific contract instance), before invoking `eventBus.emit("signing_request", ...)` or posting the unit for validation. If multilateral signing genuinely requires accepting requests from addresses outside the local wallet's own address set, that trust decision should be scoped to the specific contract/negotiation context (e.g., require a corresponding contract-hash/allowed-counterparty record) rather than being unconditionally open to any correspondent.

### Proof of Concept
Conceptual (cannot execute against live infra from this analysis):
1. Attacker device pairs with the victim's wallet (a normal, low-privilege interaction).
2. Attacker learns/derives a shared/multisig address `A` that the victim wallet locally holds a signing key for (e.g., previously seen in a `new_shared_address` broadcast or contract negotiation the attacker was privy to as a counterparty in some other flow).
3. Attacker sends a `"sign"` device message: `{address: A, signing_path: "r...", unsigned_unit: {authors: [{address: A, ...}], messages: [...malicious payment...]}}`.
4. `findAddress(A, path, ...)` resolves via `ifLocal` since the key is local to the victim device.
5. The `ifLocal` handler proceeds without checking that the attacker is an authorized cosigner of `A`, emitting `"signing_request"` for the victim's wallet UI, which (depending on UI trust display) may lead the victim to approve a transaction requested by an unauthorized party.
