### Title
Cross-repository commit-status write via SHA-only lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by bare SHA only, with no repository scoping, unlike sibling handlers that scope via `Repository.from_github_repo_name(repository_name)&.stacks`. Because git commit SHAs are content-addressed and identical across forks/mirrors of a public repository, an attacker who controls a repository sharing history with a victim's repository can post a `status` webhook (correctly signed for their own repository/org) whose `sha` also exists on a victim stack, writing a status onto the victim's commit and, if the victim stack has `continuous_deployment` enabled, triggering `ContinuousDeliveryJob` to ship or block that commit.

### Finding Description
The broken binding: the invariant should be `status.repository == commit.stack.repository` for every `Shipit::Status` created from a webhook, i.e., a status for a given SHA should only ever be written against commits whose `stack` belongs to the repository that authenticated the webhook (`payload.dig('repository','full_name')`). Instead, `StatusHandler#process` does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This performs no filter on `repository_name`/`stacks`, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`) that other handlers (e.g. `pull_request/*_handler.rb`) use to scope effects to the authenticating repository [2](#0-1) .

`WebhooksController#verify_signature` only verifies that the HMAC signature is valid for the GitHub App registered to `repository_owner` (the owner of the repository named in the payload) [3](#0-2) . It does not — and cannot — verify that the `sha` in the payload actually belongs to that repository's own commit graph; it only proves the request was legitimately signed for *some* org's webhook, which an attacker satisfies by owning/controlling a repository (e.g., a fork) registered under a GitHub org/app known to Shipit.

Since `Commit` records store the same SHA independently per `stack` (each `belongs_to :stack`, i.e. per repository/branch config) [4](#0-3) , and git SHAs are content-addressed, a commit that exists in a victim's upstream repository/stack will have the identical SHA in any fork/mirror the attacker controls. The attacker triggers a `status` event from their own repository/fork for that shared SHA; Shipit signs/accepts it for the attacker's org, then `StatusHandler` finds and mutates the commit status on **every** stack across the instance that has a `Commit` row with that SHA — including the victim's.

If the victim stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` fires when the aggregated `status` transitions and `deployable?` becomes true, enqueuing `ContinuousDeliveryJob` [5](#0-4) . The `add_status` callback recomputes `status`/`deployable_status` and calls `stack.schedule_merges` whenever the aggregate status becomes pending or success [6](#0-5) , `deployable?` depends on aggregate CI success and lack of blocking statuses [7](#0-6) .

No existing guard prevents this: `verify_signature` authenticates the *sender*, not the *scope* of the SHA being referenced; `ExplicitParameters` only validates `sha`/`state`/`context` types, not repository binding; `stacks`-scoping exists in the codebase (used by other handlers) but is simply not applied in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository (the attacker's own/forked repo) mutates commit-status state — and can drive an automated deploy or block — for a *different* repository's stack that the attacker does not control and never authenticated for. This exactly matches the "payload for one repository mutating another's stack, commit ... an unauthorized deploy" Critical impact category. The blast radius extends to any stack in the Shipit instance whose commit history overlaps (shares SHAs) with a repository the attacker can post signed webhooks for — most plausibly via forks of the victim's public repository, or shared vendored/mirrored commits. This is repeatable per SHA/context and can be used to force-green a required `ci/lint` context to trigger `ContinuousDeliveryJob`, or force a failing/blocking state to halt legitimate deploys (denial of shipping), on stacks the attacker has no authorization over.

### Likelihood Explanation
Preconditions: the attacker needs (1) a repository/org registered with Shipit's GitHub App configuration so `verify_signature` succeeds for their own webhook (a low bar — any onboarded/forkable public repo, or their own repo added as a Shipit-tracked repository), and (2) a shared SHA with the victim stack, which is trivially achievable by forking the victim's public repository (fork commits are byte-identical, same SHA) or otherwise obtaining a commit whose SHA coincides with a victim commit already present in Shipit's `commits` table. The victim stack must have `continuous_deployment` enabled and require the `ci/lint` context for the amplification to result in an actual ship/block, but the underlying cross-repo status write itself succeeds regardless of `continuous_deployment`. Attacker cost is low: standard GitHub fork + one HTTP POST to `/webhooks` with a real GitHub-signed status payload (or self-triggered via GitHub API against their own fork, which GitHub then relays to Shipit).

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, analogous to the `pull_request` handlers' use of `Handler#stacks`. For example, restrict the commit lookup to stacks belonging to `Repository.from_github_repo_name(repository_name)`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status is only applied to commits belonging to the repository/stacks that the signed webhook actually originated from, restoring the invariant that a status for `ci/lint` only affects the repository that authenticated it.
