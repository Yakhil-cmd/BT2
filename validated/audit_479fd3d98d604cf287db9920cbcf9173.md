### Title
Attacker-Controlled PreStxOp `output` Field Lets Anyone Lock a Victim's STX via a Self-Authored StackStxOp - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` sets the `output` field to whatever Bitcoin address appears as vout 0 of the transaction, without any check that the transaction's signer controls that address. `StackStxOp::get_sender_txid` and `Burnchain::classify_transaction` then use that unauthenticated `output` field as the `sender`/`tx-sender` principal for the `stack-stx` Clarity call, so an attacker can lock any funded Stacks address's STX for a reward address and cycle count of their own choosing.

### Finding Description
The broken equality: **STX locked (stacker principal whose `stx-account` is locked) == STX owned and authorized-for-locking by the private-key holder of that principal.**

Trace:
1. `PreStxOp::parse_from_tx` (stackslib/src/chainstate/burn/operations/stack_stx.rs:74-144) takes the *first* Bitcoin output (`outputs.get(0)`) of the PreStx transaction and converts its script hash directly into a `StacksAddress` via `try_into_stacks_address()` — no relationship is checked between this address and the transaction's *inputs* (i.e., whoever signed the PreStxOp). Any attacker who funds their own PreStxOp transaction can set vout 0 to pay to the victim's hash160/address bytes; producing Bitcoin outputs that pay to an arbitrary hash160 requires no private key at all.
2. `StackStxOp::get_sender_txid` (stackslib/src/chainstate/burn/operations/stack_stx.rs:232-247) only requires that the follow-up StackStx transaction's first input spends `vout == 1` of the referenced PreStxOp txid — it does not check any link between vout 1's spending key and vout 0's address (`output`). Since the attacker authored the PreStxOp transaction, they alone chose the script for vout 1 too, and can trivially spend it themselves in the second transaction.
3. `Burnchain::classify_transaction` (stackslib/src/burnchains/burnchain.rs:929-963) resolves `sender = pre_stack_stx.output` (the attacker-chosen victim address) and calls `StackStxOp::from_tx(...)` with that `sender`.
4. `StacksChainState::process_stacking_ops` (stackslib/src/chainstate/stacks/db/blocks.rs:4077-4130) then invokes `tx.run_contract_call(&sender.clone().into(), None, ..., "stack-stx", &args, ...)`, i.e., the victim's principal is passed directly as `tx-sender` into the `pox-*.clar` `stack-stx` function — bypassing normal Stacks transaction signature verification entirely, since this is a burnchain-signaled operation, not a signed Stacks transaction.
5. Inside `stack-stx` (e.g. stackslib/src/chainstate/stacks/boot/pox-4.clar:571-621), the only checks are that `tx-sender` (forged to be the victim) isn't already stacking/delegating and has sufficient balance — there is no cryptographic proof of the victim's consent. `pox_lock_v4`/`pox-locking` then locks the victim's real STX balance for the attacker-chosen `reward_addr` and `num_cycles`.

No existing guard (`check-caller-allowed`, `consume-signer-key-authorization`, PreStxOp/StackStxOp parsing checks) verifies that the entity submitting the Bitcoin transactions controls the Stacks private key of the `sender`/`output` address — `consume-signer-key-authorization` only validates the *signer key* used for slashing/reward-address purposes, not stacker consent.

### Impact Explanation
An attacker can permanently freeze an arbitrary victim's STX for up to `POX_MAX_NUM_CYCLES` reward cycles without the victim's authorization, while directing all PoX/BTC staking rewards associated with that locked STX to a `reward_addr` fully controlled by the attacker. This is a temporary-but-attacker-extendable freezing of the victim's funds and a theft of the staking rewards that should never have accrued to the attacker (since they contributed none of the locked STX) — matching the Critical category ("permanent freezing of staked STX ... unlocking value never locked / double-counting a commitment"). The attack is repeatable against any address with a spare positive STX balance and costs only the dust value of two chained Bitcoin transactions.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) some Bitcoin to fund a PreStxOp transaction and a follow-up StackStxOp transaction, and (b) knowledge of the victim's `StacksAddress` (public information). No pox-4/pox-5 membership, prepare-phase timing, or coordinator state is required. The victim must simply hold unlocked STX and not already be in an active stacking session. This makes the attack cheap, fully attacker-controlled, and repeatable across cycles/addresses.

### Recommendation
Require that the `output`/`sender` principal of a `PreStxOp`/`StackStxOp` pair be cryptographically tied to the party who actually signs the Bitcoin inputs — e.g., require that the hash160 used for `output` (vout 0) match the hash160 derived from the public key(s) that signed the PreStxOp's own inputs (self-attestation), or otherwise require an explicit Stacks-signed authorization (similar to `signer-sig`) proving the `sender` consented to the specific `stacked_ustx`, `reward_addr`, and `num_cycles` before `process_stacking_ops` calls `stack-stx` on their behalf.

### Proof of Concept
Rust integration test (e.g., alongside `stacks-node/src/tests/neon_integrations.rs`):
1. Boot a regtest chainstate with two funded Stacks accounts: `victim` (has STX, no BTC ops) and `attacker` (has BTC UTXOs, no relation to `victim`'s key).
2. Craft `PreStxOp { output: victim_addr, .. }` and submit it signed only by `attacker`'s BTC key (`BurnchainOpSigner::new(attacker_btc_sk)`).
3. Craft the follow-up `StackStxOp { sender-implicit-from-PreStxOp, reward_addr: attacker_reward_addr, num_cycles: N, stacked_ustx: victim_full_balance, .. }`, spending vout 1 of the PreStxOp transaction using `attacker`'s own key.
4. Mine blocks so both ops are processed.
5. Assert: `get_account(&http_origin, &victim_addr).locked > 0` and equals the amount specified by the attacker, and that the corresponding PoX reward set entry references `attacker_reward_addr` — with the equality "`victim` locked amount == amount authorized by `victim`'s private key" being false (`victim` never signed anything), demonstrating the broken invariant.
