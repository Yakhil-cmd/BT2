### Title
Unauthenticated cross-organization commit status/webhook forgery when a configured GitHub App has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using one payload field (`repository.owner.login`, falling back to `organization.login`), while every downstream handler acts on a *different* payload field (`repository.full_name` for `PushHandler`/`CheckSuiteHandler`, or nothing at all for `StatusHandler`, which trusts a bare `sha`). `GitHubApp#verify_webhook_signature` additionally short-circuits to `true` whenever no `webhook_secret` is configured for that organization. This breaks the binding "organization whose secret authenticated the request == repository/commit actually written to."

### Finding Description
`verify_signature` resolves the app/secret to check against purely from attacker-suppliable JSON: [1](#0-0) [2](#0-1) 

and `GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as automatic success: [3](#0-2) 

The setup docs explicitly present `webhook_secret` as **optional**, so multi-org installations (documented feature, see `docs/setup.md` "Using Multiple Github Applications") can legitimately have an organization entry configured with no `webhook_secret`: [4](#0-3) [5](#0-4) 

Once such an org exists, any unauthenticated caller can send `POST /webhooks` with `repository.owner.login` set to that unprotected org (so `verify_webhook_signature` short-circuits `true`) while every other field used by the actual handlers is independently attacker-controlled and unchecked against that org:

- `StatusHandler` does not scope by repository/organization at all — it resolves purely by commit `sha` across the entire installation and writes a forged CI status: [6](#0-5) 

- `PushHandler`/`CheckSuiteHandler` resolve the target stack from `repository.full_name`, a field completely independent from the `repository.owner.login` used for signature-app selection: [7](#0-6) [8](#0-7) 

So the "verified" field (`repository.owner.login`, used only to decide which secret gate to check, and bypassable entirely if that org has no secret) is never equal to the field the handler actually trusts (`repository.full_name` or bare `sha`), reproducing the report's core class of bug: a length/bound-check performed on one thing while the write happens using another, unguarded value.

### Impact Explanation
An attacker can forge a `status` webhook event for **any commit sha tracked by any stack in the installation**, regardless of which repository/organization it belongs to, as long as at least one configured GitHub App organization has no `webhook_secret` (a documented, supported configuration). Forged statuses feed directly into `ci.require`/`ci.allow_failures` merge-queue and deploy gating logic, enabling an attacker to mark required checks as green on a victim repository's commit, driving an unauthorized deploy or merge without ever needing a Shipit session, `ApiClient` token, or the org's real `webhook_secret`. This matches the required High/Critical impact class ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that one org among the (potentially many) configured GitHub Apps omits `webhook_secret` — explicitly documented as optional and a normal state for smaller/simpler installations — with no privileged credential, session, or token needed to exploit it once that precondition holds. This is a design gap in the engine's routing/verification logic itself, not a third-party or host-misconfiguration edge case that voids in-scope status, since the multi-org and optional-secret behavior is both implemented and documented by the engine.

### Recommendation
- Do not resolve the verifying `GitHubApp` from attacker-controlled JSON fields; verify the signature (or reject if no secret is configured, rather than treating "no secret" as "verified") before trusting any content of the payload.
- Require every handler to verify that the repository/organization referenced by the fields it acts on (`repository.full_name` for push/check_suite, and add a repository/org check to `StatusHandler` before touching `Commit` records) matches the organization whose secret validated the webhook.
- Treat a missing `webhook_secret` as "reject all webhooks for this org" by default, or make the currently-optional secret mandatory, closing the unauthenticated bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two GitHub App entries per the documented multi-org setup: `orgA` (attacker-accessible, `webhook_secret` left blank as allowed) and `orgB` (the victim org, with a real Stack tracking commit `abcdef1234...`).
2. Send:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"},
  "sha": "abcdef1234...",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs unauthenticated and creates a `success` status on `orgB`'s tracked commit, satisfying `ci.require` for that commit and enabling deploy/merge.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
