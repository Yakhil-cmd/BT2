### Title
Signature verification keys on `repository.owner.login`/`organization.login` while every webhook handler acts on `repository.full_name` — cross-organization repository confusion in the incoming webhook path - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login') || params.dig('organization','login')`, but every downstream handler resolves the target `Stack`/`Repository`/`ReviewStack` using a *different* field of the same attacker-supplied JSON body: `repository.full_name`. Nothing binds these two fields together, so a payload can be legitimately signed by organization A's secret while acting on organization B's repository.

### Finding Description
`verify_signature` computes the org used to fetch the webhook secret purely from the JSON body itself: [1](#0-0) [2](#0-1) 

Once the signature passes, `create` dispatches the raw, attacker-controlled JSON to handlers unchanged: [3](#0-2) 

But the base `Handler` class — used by every registered handler (`PushHandler`, all `PullRequest::*Handler`s, `StatusHandler`, `CheckSuiteHandler`) — resolves the acted-upon repository from `payload.dig('repository', 'full_name')`, a completely separate JSON field from the one used to pick the signing organization/secret: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally the same class of bug as the GMX report: a struct/computation is only ever populated/validated for "one side" (the org that signs) while the consequential "other side" (the repository that is actually written to) is taken from an unrelated, unchecked field of the same payload. The binding that should hold is:

`organization whose secret validated the signature == owner of repository.full_name acted upon`

This binding is never enforced anywhere in `app/controllers/shipit/webhooks_controller.rb` or `app/models/shipit/webhooks/handlers/handler.rb`.

Concretely, Shipit supports multiple organizations each with their own GitHub App/webhook secret configured under `github:` (as shown in the multi-org config, e.g. `test/dummy/config/secrets_double_github_app.yml`), and a `GithubHook` fixture model can also be scoped per-repository or per-organization with independent secrets (`test/fixtures/shipit/github_hooks.yml`). An entity that is a legitimate GitHub App installer/owner for *its own* org/repo in this Shipit instance (and therefore knows or can derive its own valid `webhook_secret`) can POST directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = its own org, so `verify_signature` succeeds using its own known secret, and
- `repository.full_name` = `"victim-org/victim-repo"`, an entirely different, already-onboarded stack.

`PushHandler` will then look up `Repository.from_github_repo_name("victim-org/victim-repo")` and invoke `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, and `PullRequest::OpenedHandler`/`ReviewStackAdapter#create!` will create a `ReviewStack` on the victim repository using attacker-supplied `pull_request.head.ref` as the deploy `branch`, attacker-supplied `pull_request.number` as environment, and enqueue it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`.

### Impact Explanation
This breaks the intended trust boundary between "organizations onboarded to this Shipit instance" — an org that only owns its own webhook secret can force actions (forced GitHub sync, review-stack creation/archival, provisioning-queue enqueue) against a different organization's `Stack`/`ReviewStack` records that it does not own or have write access to. Review-stack creation ultimately schedules deploy/provisioning tasks, i.e., an unauthorized deploy-adjacent action initiated on a stack the attacker's organization has no legitimate relationship with. This matches the report's "Critical - unauthorized deploy" / "High - unauthenticated read of stack state" categories, since the confused-deputy signature check lets an attacker with only their own org's credentials manipulate another organization's stacks.

### Likelihood Explanation
Requires the attacker to control (or have installed) a GitHub App on at least one organization that Shipit is configured to trust — a realistic scenario for any multi-tenant/multi-org Shipit deployment, since nothing in `verify_signature` or the handlers cross-checks that the signing organization matches the repository owner being acted upon. No GitHub-side repository permissions on the victim repo are needed at all; only the attacker's own already-legitimate webhook secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to validate the signature is the same as (or authorized for) the owner segment of `repository.full_name`, e.g. reject the request if `repository_owner` does not match `payload.dig('repository','full_name').split('/').first`. Alternatively, have handlers resolve the target repository/stack strictly through the already-verified `repository_owner`, not through an independent unchecked field of the same payload.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` (attacker controls the GitHub App/knows `webhook_secret`) and `victim-org` (has an existing onboarded `Stack` for `victim-org/victim-repo`).
2. Attacker crafts a `pull_request` "opened" JSON payload with:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `pull_request.head.ref = "<attacker-chosen-branch>"`, `number = <arbitrary>`
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature`: [8](#0-7) 
4. POST to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and verification succeeds.
5. `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `ReviewStackAdapter#find_or_create!`, creating/enqueuing a `ReviewStack` under the victim's repository using attacker-controlled branch/PR data — despite the request never being signed by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
