### Title
Missing `return` after error path causes duplicate completion callback in private-payment chain handler - ([File: network.js])

### Summary
In `handleSavedPrivatePayments`'s inner `validateAndSave` function, the `catch` block that handles a hashing failure calls `deleteHandledPrivateChain(..., cb)` (which eventually invokes the `async.each` iteratee callback `cb`) but does not `return` afterward. Execution falls through to compute `json_payload_hash` (now `undefined`) and then calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also call `cb()`. This is directly analogous to the Linux `xts` CVE-2023-53494 bug class: a special/error return path is handled and resources are released/completed, but the code does not stop there, so the normal completion path also runs and finalizes the same unit of work a second time, corrupting shared completion-tracking state.

### Finding Description
`network.js` `handleSavedPrivatePayments` iterates unhandled private-payment rows with `async.each`, and per row calls `validateAndSave`: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
```

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws, the `catch` branch already calls `deleteHandledPrivateChain(...)` → `cb()` (analogous to xts's special-cased `EINPROGRESS` completion path). But there is no `return`/`break` after the `catch`, so the function continues and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again on the same `arrPrivateElements`, which will asynchronously invoke `cb()` a second time through one of `ifOk`/`ifError`/`ifWaitingForChain` (the analog of the unhandled `EBUSY` path in the kernel bug — a second legitimate completion signal that the caller wasn't prepared to receive again). `async.each` counts callback invocations to know when all items are done; a double `cb()` call for a single row causes the outer completion handler to fire prematurely — `unlock()` is called and the `saved_private` mutex is released while other rows in the same batch may still be mid-validation. `getBase64Hash` operates on attacker-controlled JSON parsed straight off a `unhandled_private_payments.json` column, which is populated verbatim from wire data supplied by a private-payment counterparty (`handlePrivatePaymentChains` in wallet.js only checks shallow structural types, not hashability), so a crafted payload that fails to json-hash is directly reachable from a remote private-payment peer.

### Impact Explanation
Premature `unlock()` on the `saved_private` mutex key allows a second, concurrent invocation of `handleSavedPrivatePayments` (e.g., triggered by another incoming unit/joint event) to start processing the same `unhandled_private_payments` rows before the first pass has fully finished cleaning up/validating them. This creates a race where private-payment chain validation/insertion for the same private asset transfer can be attempted concurrently from two overlapping executions, undermining the mutex-based serialization that the private-payment save path (`private_payment.js validateAndSavePrivatePaymentChain`, and downstream `divisible_asset.js`/`indivisible_asset.js` output/input insertion) relies on to avoid concurrent double-processing of the same spend-proof/output. Concurrent execution of the input/output insert transactions for the same private chain is the mechanism by which private-asset double-spend or duplicate-crediting bugs typically arise, matching the "double-spend of a stable output" / node-disagreement class called out as in-scope impact.

### Likelihood Explanation
Any correspondent (a private-payment counterparty or a hub relaying a `private_payments` justsaying) can trigger this by sending a private-payment chain whose head payload cannot be json-hashed by `object_hash.getJsonSourceString` (the shallow validation in `wallet.js handlePrivatePaymentChains` only checks that `payload`, `payload.inputs`, `payload.outputs` are nonempty objects/arrays — it does not validate the hashability of nested values). No privileged access or race-winning against the network is required to reach the vulnerable code path; the only requirement is a hash-failing payload, which is a normal, no-cost precondition. Because this requires crafting a value that triggers a runtime exception in the hashing utility, likelihood is more speculative for the exact hash-failure trigger, but the missing-`return` control-flow defect itself is unconditionally present.

### Recommendation
Add a `return` (or restructure with `if/else`) immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave`, so the function does not fall through to compute `json_payload_hash`/call `privatePayment.validateAndSavePrivatePaymentChain` a second time for the same row/`cb`. Ensure `cb` is guaranteed to be invoked exactly once per row, mirroring the kernel fix's principle of correctly handling every legitimate "already completed" signal (`EINPROGRESS` and `EBUSY`) instead of assuming only one path returns.

### Proof of Concept
1. As a correspondent device (or a hub forwarding a `private_payments` justsaying), send a `private_payments` message whose chain's head element payload passes the shallow checks in `wallet.js handlePrivatePaymentChains` (nonempty `inputs`/`outputs` objects) but contains a value that causes `object_hash.getJsonSourceString`/`getSourceString` to throw when hashed (e.g., a deeply/abnormally structured nested value accepted by `JSON.parse` but rejected by the source-string serializer used for hashing). [2](#0-1) 
2. The message is queued into `unhandled_private_payments` and later processed by `handleSavedPrivatePayments`. [3](#0-2) 
3. In `validateAndSave`, `objectHash.getBase64Hash` throws, the `catch` handler calls `deleteHandledPrivateChain(...)` (invoking `cb()`), then execution falls through and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again, invoking `cb()` a second time via one of its callbacks. [4](#0-3) 
4. Send a second batch of rows in the same `handleSavedPrivatePayments` invocation to observe `async.each`'s final callback (and thus `unlock()`) fire before all rows are actually done, opening the race window for a concurrent second invocation of `handleSavedPrivatePayments` to process the same underlying private chain concurrently. [5](#0-4)
