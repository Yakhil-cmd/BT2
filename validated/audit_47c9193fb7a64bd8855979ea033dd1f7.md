## Title
Cross-repository Commit/Status corruption via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, without checking that the commit belongs to a stack for the `repository` named in the verified webhook payload. Because `Commit.sha` is only unique per `(sha, stack_id)` — not globally — and because forks of a public GitHub repository legitimately share identical commit SHAs with the upstream repository, an attacker who controls a fork (and any Shipit-tracked stack pointing at that fork) can send a genuinely GitHub-signed "status" webhook for their own repository with a colliding `sha`, and the handler will overwrite the `Status`/`Commit.state` of an unrelated victim stack's commit.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce:
`payload['repository']['full_name'] (verified, signed org) == commit.stack.repository.full_name (record mutated)`

`StatusHandler#process` does not enforce this equality at all: [1](#0-0) 

Compare this to the base `Handler` class, which other handlers (e.g. `PullRequest` handlers) use to scope by repository via `stacks`: [2](#0-1) 

`StatusHandler` never calls `stacks`/`repository_name` — `params.sha` is the only key used to find commits, and any `Commit` row across any stack/repository with a matching `sha` is fetched and mutated: [3](#0-2) 

The uniqueness constraint on `sha` is scoped to `(sha, stack_id)`, not global, so two different stacks (tenants) legitimately can hold `Commit` rows with the same `sha` — most commonly because a GitHub fork shares full commit history/SHAs with its upstream repository up to the fork point: [4](#0-3) 

The webhook signature check (`WebhooksController#verify_signature`) only proves the payload was signed by GitHub for the organization named in the payload's own `repository.owner.login` field — it says nothing about which specific repository/stack the status applies to, and `StatusHandler` never cross-checks the `repository` field against the commit's stack: [5](#0-4) 

Once the status is applied, `Commit#deployable?` flips to `false` because it derives from `Status#success?`/`blocked?`, silently sabotaging the victim's continuous delivery pipeline for that commit while writing state the victim's org never authorized: [6](#0-5) [7](#0-6) 

**Exploit flow:**
1. Attacker forks a victim's public GitHub repository (or otherwise ends up with a repo sharing an ancestor commit's SHA with the victim's repository/stack).
2. Attacker's fork is tracked as its own Shipit stack under an org that legitimately has Shipit's GitHub App/webhook configured (attacker only needs their own tenant onboarding — no victim secrets needed).
3. Attacker triggers a real GitHub "status" event on their fork for the shared SHA with `state: "error"` (e.g., via their own CI/Actions or the Statuses API on their own repo — something entirely within an unprivileged user's control).
4. GitHub signs and delivers this webhook using the secret configured for the attacker's own organization; `verify_signature` passes because it only validates the org that signed, not which stack's commit is targeted.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns both the attacker's own commit row and the victim's commit row (same sha, different `stack_id`), and calls `create_status_from_github!` on all of them — writing `state: 'error'` into the victim's `Status`/`Commit` data.

No existing guard (`verify_signature`, `ExplicitParameters` schema, model validations) checks that the resolved `Commit#stack` corresponds to the payload's `repository.full_name`.

### Impact Explanation
A payload authenticated for one repository/organization directly mutates another tenant's `Commit`/`Status` records — flipping `Commit#state` from `success` to `error`/`failure` for a victim's commit, which suppresses `Stack#trigger_continuous_delivery`/`schedule_continuous_delivery` and can also spuriously trigger it for unrelated states. This is a cross-repository write of authoritative CI state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim stack that shares a commit SHA with an attacker-controlled fork/stack (a common, low-cost condition for public open-source repos on Shipit).

### Likelihood Explanation
Preconditions: attacker's fork (or any repo they control) must share a `sha` with the victim's tracked commit (trivially true for common ancestor commits in a fork), and attacker's own organization/repo must be a registered Shipit tenant with correctly configured webhook signing (a normal, unprivileged onboarding condition, not a victim secret). Attacker cost is low: fork a public repo, get it onboarded as a stack (or use an existing tenant they legitimately administer), and post a real status via their own CI to the shared sha. This does not require the victim's webhook secret, session, or API token.

### Recommendation
In `StatusHandler#process`, restrict the query to commits belonging to stacks for the repository named in the verified payload, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `payload.repository.full_name == commit.stack.repository.full_name` before any write occurs.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "process does not mutate commits belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse) # different repository, e.g. "attacker/fork"

  colliding_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)
  victim_commit.statuses.create!(stack: victim_stack, state: "success")
  assert_equal "success", victim_commit.reload.state

  attacker_commit = attacker_stack.commits.create!(sha: colliding_sha, author: shipit_users(:walrus), authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now)

  payload = {
    "sha" => colliding_sha,
    "state" => "error",
    "repository" => { "full_name" => attacker_stack.repository.full_name, "owner" => { "login" => attacker_stack.repository.owner } },
    "branches" => [{ "name" => attacker_stack.branch }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal "success", victim_commit.reload.state, "victim commit state must not change from an attacker-controlled repository's webhook"
  assert_equal "error", attacker_commit.reload.state
end
```
Under the current implementation, this test fails: `victim_commit.reload.state` flips to `"error"` even though the payload was for `attacker_stack`'s repository, demonstrating the cross-tenant write.
