### Title
Cross-repository `Commit` status injection via unscoped `Commit.where(sha:)` lookup unblocks victim stack's deploy queue - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha` and never checks that the commit's owning stack/repository matches the `repository.full_name` in the inbound webhook payload, unlike every other handler in the same directory. An attacker who controls any repository sitting on an organization that already has the GitHub App/webhook installed for this Shipit instance can trigger a legitimately-signed `status` event naming an arbitrary `sha`, and if that sha matches a commit belonging to a *different* stack/repository, the status is written onto that foreign commit, letting an attacker manipulate `Commit#blocked?` for a stack they do not own.

### Finding Description
The broken binding is:
`stack_that_owns(commit).id == stack_of(payload['repository']['full_name'])`

`StatusHandler#process` does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This never consults `payload.dig('repository', 'full_name')` or the `stacks`/`repository_name` helpers that the base `Handler` class provides for exactly this purpose: [2](#0-1) 

Every sibling handler enforces this binding explicitly: `PushHandler` scopes via `stacks.where(branch:)` (derived from `Repository.from_github_repo_name(repository_name)`), `CheckSuiteHandler` scopes via `stacks.where(branch: ...)` then filters commits `where(sha:)` inside that scope, and all `PullRequest::*Handler`s resolve `Repository.from_github_repo_name(params.repository.full_name)` before touching any record: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler` is the sole handler with no such scoping.

`Commit#blocked?` and `Status::Common#blocking?` both derive their config from the *commit's own stack*, not from the requesting repository: [6](#0-5) [7](#0-6) 

`WebhooksController#verify_signature` only authenticates *which organization* sent the webhook (looking up `Shipit.github(organization: repository_owner)` and validating the HMAC against that org's configured `webhook_secret`); it does not verify that the `sha`/commit referenced in the payload belongs to a stack under that organization: [8](#0-7) 

**Exploit flow:** An attacker who administers (or has push access to a repo under) any organization already onboarded to this shared Shipit instance can, using their own GitHub credentials (no Shipit secret needed — GitHub computes and signs the webhook legitimately on delivery), fetch the victim's pending PR head commit metadata (tree sha, parent sha, author, committer, timestamps, message — all public for a public PR) via the GitHub API, and reconstruct a bit-for-bit identical commit object (`git commit-tree` with identical inputs produces an identical SHA) inside a repository they control. They then set a commit status (`state: success`, `context: '<the victim stack's blocking context>'`) on that sha in their own repo via the standard GitHub Statuses API. GitHub delivers a correctly signed `status` webhook naming the attacker's own `repository.full_name`, but with the victim's `sha`. `StatusHandler` finds the `Commit` row by `sha` alone (which belongs to the victim stack) and calls `commit.create_status_from_github!(params)`, writing a `success` status for that context onto the victim's commit. Because `blocking?` requires `!success?`, this clears the blocking condition on `stack.commits.reachable.newer_than(last_deployed).older_than(self)`, flipping `Commit#blocked?` to `false` for later commits in the victim's stack and unblocking its deploy queue — a payload from one repository mutating another repository's commit/stack state.

Existing guards do not stop this: `verify_signature` validates sender-org authenticity only, `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape/presence of a handler, and no repository/stack ownership check exists anywhere in `StatusHandler`.

### Impact Explanation
A record (`Shipit::Status`) is written for a repository/commit that never authenticated the request (the webhook was authenticated for the attacker's org, not the victim's), directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or task or team." The concrete consequence is an unauthorized deploy: clearing a required blocking status on a foreign stack's commit unblocks `deployable?`/`blocked?` checks and allows queued deploys to proceed on the victim repository without any legitimate CI/status having passed there. This is repeatable against any stack/commit whose sha the attacker can reproduce, and is not limited to one victim — any tenant sharing the same Shipit instance is exposed, so the blast radius spans all repositories/organizations hosted by that Shipit deployment.

### Likelihood Explanation
Preconditions: (1) attacker needs at minimum push/API access to some repository under an organization that already has a legitimate GitHub App/webhook installation configured in this Shipit instance's `Shipit.github` config (typical for multi-tenant Shipit deployments serving many orgs/teams) — this does not require any Shipit secret, since GitHub itself computes the signature on delivery; (2) attacker needs to reproduce the victim's PR head commit's exact object hash, which is feasible for public repositories/PRs since all inputs (tree, parent, author, committer, timestamps, message) are readable via the public GitHub API and `git commit-tree` deterministically reproduces the same SHA. No Shipit session, API token, or team membership is required. This is a low-cost, repeatable, no-secrets-required attack against any hosted repository whose commit metadata is public.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the requesting repository, mirroring the other handlers: resolve `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, restrict to that repository's `stacks`, and only update `Commit` records belonging to those stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join), rejecting/ignoring statuses for shas that do not belong to a stack under the reporting repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "cross-repository status forgery unblocks a foreign stack's deploy queue" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine" or similar
  blocking_commit = shipit_commits(:soc_second) # belongs to victim_stack, configured with ci.blocking context "soc/compliance"
  next_commit = shipit_commits(:soc_third)

  assert_predicate blocking_commit, :pending? # or missing status
  assert_predicate next_commit, :blocked?      # binding: blocked? governed by victim_stack.blocking_statuses

  # Forged payload: repository is attacker's own org/repo, but sha equals victim's blocking_commit.sha
  forged_payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => 'soc/compliance',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  blocking_commit.reload
  next_commit.reload

  assert_predicate blocking_commit, :success?  # status was written despite payload repository != victim repository
  refute_predicate next_commit, :blocked?       # queue unblocked by a foreign-repo webhook
end
```
This demonstrates the equality `stack_that_owns(commit) == stack_of(payload.repository)` is violated: the status is accepted and applied even though `payload['repository']['full_name']` names a repository unrelated to `blocking_commit.stack`.
