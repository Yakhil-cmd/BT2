### Title
GitHub PR label named `PATH` overrides system `PATH` in `Command#unbundled_env`, enabling RCE on shared deploy host - (File: `lib/shipit/command.rb`)

### Summary
`Shipit::ReviewStack#env` injects PR labels as environment variables using the raw (uppercased) label name as the key and `"true"` as the value, with no key blocklist. Because `Command#unbundled_env` merges the task-provided `@env` hash *after* constructing `PATH` from `Shipit.shell_paths`, a label named `PATH` overwrites the real `PATH` with the literal string `"true"` before `PTY.spawn` runs, letting an attacker-controlled working directory hijack binary resolution for `git`/`bundle`.

### Finding Description
The broken binding: `Command#unbundled_env` is supposed to satisfy `ENV['PATH'] passed to PTY.spawn == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but that only holds if `@env` (the task/stack-provided hash) has no `'PATH'` key.

Path: `Shipit::ReviewStack#env` merges label-derived pairs `labels[label_name.upcase] = "true"` over `super` (Stack's env) with no filtering of reserved keys. [1](#0-0) 

`Shipit::TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review-stack tasks) early, then several hardcoded keys, `deploy_spec.machine_env`, and `@task.env` — none of which reintroduce `'PATH'`, so a `PATH` key injected by `ReviewStack#env` survives unmodified to the final hash returned to `Command.new`. [2](#0-1) 

`Command#initialize` stores this as `@env` (stringified values only, no key filtering): [3](#0-2) 

`Command#unbundled_env` then computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)`. Since `.merge` on the right wins, and `@env` contains `'PATH' => 'true'`, the freshly constructed `PATH` is discarded and `PTY.spawn` receives `PATH=true`. [4](#0-3) [5](#0-4) 

Attacker action: a repository maintainer/owner (or anyone permitted to label PRs on a repo they control, which the rules explicitly grant — "label their own PR") opens a PR against a repository with review stacks enabled, then adds a label literally named `PATH` to that PR. GitHub emits a genuinely-signed `pull_request` `labeled` webhook (no forged signature needed — GitHub computes it with the real `webhook_secret`). `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists the raw label names onto `PullRequest#labels` with no validation/allowlist on label content: [6](#0-5) 

On the next deploy/task, `TaskCommands#env` → `Command#unbundled_env` reproduces the merge above, and `PTY.spawn` runs with `PATH=true`. With `PATH` broken, any relative-lookup binary invocation (`git`, `bundle`, etc.) in `@task.working_directory` (the attacker's own checked-out branch) can be hijacked by placing an executable file named e.g. `git` in the PR branch, since shell/subprocess PATH resolution fails and typical shells fall back to CWD-relative or otherwise attacker-influenced resolution depending on the invoking command's `chdir`.

No existing guard intercepts this: `LabelCapturingHandler`'s `ExplicitParameters` schema only requires `labels[].name` to be a `String`, not restricting its value; `capture_labels?` only gates on `stack.present? && !stack.archived?`; `ReviewStack#env` has no denylist for reserved variable names like `PATH`, `HOME`, `BUNDLE_PATH`, etc.

### Impact Explanation
Critical — this is unsanitized attacker-controlled input (a PR label name) becoming an environment variable that clobbers `PATH` immediately before `PTY.spawn` executes shell commands (`git`, `bundle install`, deploy steps) on the deploy host. Because the deploy host commonly runs tasks for many tenants/stacks, a working-directory PATH-hijack achieved by one tenant's review stack risks broader host compromise (arbitrary code execution as the Shipit deploy user), satisfying the "RCE on the deploy host via `Command`/`PTY.spawn`" Critical category. The attack is repeatable per PR/label add and works against any repository that has review stacks enabled.

### Likelihood Explanation
Preconditions: the target repository must have `Shipit::ReviewStack` support enabled and an active (non-archived) review stack for the PR. The attacker must be able to add a label named `PATH` to that PR — trivial for a repo they maintain/own themselves, and the rules explicitly permit "label their own PR" as an in-scope attacker capability, so no forged webhook signature or secret is required (GitHub signs the real event). Attacker cost is minimal (open a PR, add one label, push a branch with an executable named after a common tool). Fully repeatable.

### Recommendation
In `Shipit::ReviewStack#env` (app/models/shipit/review_stack.rb), reject or filter reserved/sensitive environment variable names (`PATH`, `BUNDLE_PATH`, `HOME`, `LD_PRELOAD`, etc.) before merging label-derived keys, or maintain an explicit allowlist for label-derived env vars. Additionally, harden `Command#unbundled_env` (lib/shipit/command.rb) to compute `PATH` last (i.e., never let arbitrary task/stack `@env` override `PATH`), so the system-selected `PATH` cannot be overwritten by task-supplied environment data regardless of source.

### Proof of Concept
Minitest plan (unit-level, no live GitHub needed):
1. Create a `Shipit::Stack`, its `Shipit::ReviewStack`, and an associated `Shipit::PullRequest`.
2. Directly call `pull_request.update!(labels: ['PATH'])` (equivalent to what `LabelCapturingHandler#capture_labels` would persist from a `labeled` webhook).
3. Create a `Shipit::Deploy` for the review stack and build `Shipit::Commands.for(deploy)` (a `TaskCommands`).
4. Assert `Shipit::Commands.for(deploy).env['PATH'] == 'true'` (or `'true'` upcased-string equivalent), proving `TaskCommands#env['PATH']` no longer equals `nil`/absent from stack.env.
5. Build a `Shipit::Command.new('git --version', env: Shipit::Commands.for(deploy).env, chdir: deploy.working_directory)` and assert `command.unbundled_env['PATH'] == 'true'`, explicitly proving it is **not** equal to `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` — the broken binding.
