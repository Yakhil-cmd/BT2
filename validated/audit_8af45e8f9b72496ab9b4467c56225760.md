## Analog Found: Oracle Can Silently Re-Publish/Override a Data-Feed Value That AAs Have Already Relied On

### Title
Oracle Re-publishing of a Data-Feed Value for an Already-Used Key Retroactively Alters AA Financial State - ([File: data_feeds.js])

### Summary
The reported bug lets a semi-trusted `manager` role overwrite an already-set `monthlyCPI[yearMonth]` value with no restriction, letting them retroactively inflate a period's index and drain more backing tokens than legitimately deposited. The structural analog in `ocore` is the `data_feed` mechanism: an oracle (a semi-trusted external role configured in an AA's `data_feed[[oracles=...]]` clause, exactly analogous to the "manager" role) can post a brand-new value for the same `feed_name` at any later point, and AA formula reads default to picking whichever value is "last" — with no notion that a value for that logical key was "already set" and should require stricter authorization to change.

### Finding Description
`setCPI` in the external report unconditionally overwrites `monthlyCPI[yearMonth]` regardless of whether a value already exists. The `ocore` analog is the data-feed read path used by AAs:

- `formula/evaluation.js` evaluates `data_feed[[...]]` and calls `dataFeeds.readDataFeedValue(...)` with a default `ifseveral = 'last'` [1](#0-0) , meaning when several values exist for the queried oracle/feed_name/mci range, the AA silently accepts the newest one rather than the one that was already relied on for previous triggers.
- `data_feeds.js`'s `readDataFeedByAddress` implements exactly this "last wins" selection with no signal that a value for the same key existed before: `if (objResult.value === undefined || ifseveral === 'last' && mci > objResult.mci){ ... }` [2](#0-1) .
- At stabilization time, `main_chain.js`'s `addDataFeeds` explicitly documents this overwrite-in-place behavior for values that land in the same MCI: "duplicates will be overwritten, that's ok for data feed search" and "if several values posted on the same mci, the latest one wins" [3](#0-2) .
- The unstable-read path (`readDataFeedValue`'s `bIncludeUnstableAAs` branch) similarly collects all unstable candidates for a feed and, with `ifseveral='last'`, just returns the single candidate found (or sorts and takes the last) [4](#0-3) .

Just as `setCPI` has no check for "is a value already set for this yearMonth", the AA-facing data-feed read has no notion of "has this oracle already published an authoritative value for this key that later contract logic already relied on for deposits". An oracle address (the exact "manager"-equivalent trust tier — external, expected to publish routinely, but not the AA's admin/definer) can simply post a second, different value for the identical `feed_name` and have every subsequent AA trigger read pick it up as the current truth, with no admin-only gate analogous to the report's recommended fix.

### Impact Explanation
AAs that use `data_feed[[...]]` results to compute collateral/redemption ratios, exchange rates, or index-like values (the same usage pattern as `monthlyCPI` driving withdrawal amounts) are exposed to the same attack: a user/depositor interacts with the AA while an oracle-posted value A is in effect, then the oracle (compromised, or simply publishing a "correction") posts value B for the same feed. Later AA triggers (e.g., withdrawals) use B, letting an attacker who controls or colludes with the oracle extract more value than was deposited under A — mirroring the CPI exploit path (deposit under low CPI, withdraw under inflated CPI) but via the general `data_feed` primitive relied on by many bots/contracts.

### Likelihood Explanation
Exploitability depends on control of an oracle address that a given AA already trusts (same trust assumption as the compromised "manager" in the original report). No special network position, protocol bug, or multi-party collusion beyond the single oracle key is required — one posted `data_feed` unit is sufficient to shift the value future AA reads observe, because neither `formula/evaluation.js`/`data_feeds.js` nor the AA-facing oscript primitives provide a built-in "already set, admin-only override" guard analogous to the report's recommended fix.

### Recommendation
For financially critical data-feed usages, expose (or encourage AA authors to use) an oscript-level check such as "abort if a value for this feed/period was already read/used by a previous state-changing trigger" rather than relying on default `ifseveral='last'` semantics, and consider adding a stricter/opt-in immutability mode to `readDataFeedValue`/`readDataFeedByAddress` that flags or rejects same-key re-publication after the first value for a period has already been consumed by an AA response, similar to the report's suggestion of requiring elevated authorization for updates to already-set values.

### Proof of Concept
1. An AA defines `data_feed[[oracles='O', feed_name='CPI_2024_01']]` to compute a redemption ratio, with `ifseveral` left at its default (`'last'`).
2. Oracle `O` posts a `data_feed` unit with `{"CPI_2024_01": 100}`; a depositor triggers the AA, and the AA computes and stores state based on CPI=100.
3. Oracle `O` (compromised or simply "correcting") posts a second `data_feed` unit with `{"CPI_2024_01": 150}`.
4. A later withdrawal trigger reads `data_feed[[...]]` again; per `data_feeds.js` `readDataFeedByAddress`/`readDataFeedValue` logic [5](#0-4)  and `formula/evaluation.js`'s default `ifseveral='last'` [1](#0-0) , the AA now sees CPI=150 with no indication that CPI=100 was already relied upon, letting the withdrawer extract 50% more backing value than deposited.
