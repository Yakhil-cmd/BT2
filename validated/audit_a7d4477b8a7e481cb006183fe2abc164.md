### Title
Dust-output threshold in AA payment composition can permanently strand an AA's byte balance and DOS its responses - ([File: aa_composer.js])

### Summary
`sendUnit()`'s `completePaymentPayload()` helper in `aa_composer.js` selects unspent base-asset outputs to fund an AA's outgoing payment. Outputs smaller than the fixed `FULL_TRANSFER_INPUT_SIZE` threshold are unconditionally excluded from the input-selection queries, regardless of how much total balance the AA actually holds. If enough of an AA's balance accumulates as many small (dust) outputs below this cutoff, later triggers that require the AA to send bytes can bounce with "not enough funds", even though `aa_balances` shows sufficient funds. This is directly analogous to the reported `MIN_NOTIONAL_WEI` issue: a single fixed threshold check, applied without regard to the actual composition/state of the pooled funds, can make otherwise-valid spends unexecutable for other, unrelated participants. [1](#0-0) 

### Finding Description
When an AA needs to compose a payment message in response to a trigger, `readStableOutputs()` and `readUnstableOutputsSentByAAs()` query for unspent outputs belonging to the AA's address to use as inputs: [2](#0-1) 

For the base asset, both queries filter out any output with `amount < FULL_TRANSFER_INPUT_SIZE`, explicitly to prevent a dust-spam attack that would force the AA to spend disproportionately on fees: [3](#0-2) 

`iterateUnspentOutputs()` accumulates `total_amount` from these filtered rows until it reaches `target_amount` (the payment amount plus any oversize/change fees). If the sum of all *usable* (i.e., above-threshold) outputs is insufficient, the code falls through to `cb('not enough funds for ' + target_amount + ' bytes')`, which propagates up and causes the whole AA response to bounce: [4](#0-3) 

Crucially, this "not enough funds" check operates purely on the queryable set of eligible UTXOs, not on the AA's aggregate `aa_balances.balance` for the base asset. An unprivileged unit poster can send the AA many outputs each individually below `FULL_TRANSFER_INPUT_SIZE` (accepted freely by any AA whose "accept coins" branch doesn't reject small amounts — a common oscript pattern, e.g. the sample AAs that silently accept any incoming payment regardless of size). Over time, this converts a growing fraction of the AA's nominal on-chain balance into permanently unusable dust, since:
1. Each dust output, once received, sits in the `outputs` table below the input-selection threshold forever (it's never picked, so it's never merged/consolidated).
2. The AA's own state logic and `aa_balances` (or oscript `balance[...]` reads) will still count this dust as spendable, because those are separate accounting mechanisms independent of the UTXO threshold filter.
3. Subsequent legitimate triggers/users needing the AA to send even a modest base-asset amount can be starved of usable inputs and bounce, purely because the composer cannot assemble enough above-threshold UTXOs — mirroring the reported scenario where "other users can't sell ... because their [funds] are worth less than [the threshold]".

This is architecturally the same bug class as the `MIN_NOTIONAL_WEI` issue: a hard-coded minimum-size gate applied at spend-time interacts badly with the aggregate state (total balance/price) that other, unrelated actors can influence, producing denial of service for legitimate operations even though the "notional" balance is sufficient.

### Impact Explanation
Impact is Medium: this does not directly cause double-spending or fund theft, but it can cause a legitimate, funded AA operation to unexpectedly bounce ("not enough funds for N bytes") purely due to fragmentation of its UTXO set by dust, effectively freezing/locking a portion of the AA's byte balance from being spent by the payment-composition logic, and denying service to whichever trigger needed that payment to succeed. Any unprivileged party who can post triggers/payments to the target AA can create or worsen this condition over time.

### Likelihood Explanation
Likelihood is Medium: it requires an attacker (or just organic usage) to accumulate many below-`FULL_TRANSFER_INPUT_SIZE` outputs at the target AA's address — trivial to do since sending small payments to an AA address is unrestricted at the protocol level, and many AA scripts accept arbitrary incoming amounts without a minimum-size check on their own accept-branches (see the "silently accept coins" pattern used across sample AAs). Whether a given AA is actually affected depends on its typical outgoing payment sizes vs. how much dust accumulates, but no privileged access is needed to trigger the underlying condition.

### Recommendation
Reconcile the input-selection threshold with the AA's actual solvency accounting: either (a) periodically or opportunistically consolidate/self-transfer small outputs so they can later be combined above the threshold, (b) allow combining multiple sub-threshold outputs together (summing several dust outputs to exceed `FULL_TRANSFER_INPUT_SIZE` in aggregate) rather than filtering each individually and never revisiting them, or (c) surface a clearer "insufficient spendable (non-dust) balance" distinction so AA authors can defensively reject dust deposits below `FULL_TRANSFER_INPUT_SIZE` in their own accept logic, preventing dust from accumulating in the first place.

### Proof of Concept
Conceptual PoC (not executed, based on code paths):
1. Deploy/target an AA whose "accept coins" branch stores/credits any incoming base-asset amount without a minimum threshold (pattern seen in `test/samples/a_bank_without_percent.oscript` and `test/samples/order_book_exchange.oscript`, which accept and account for `trigger.output[[asset=base]]` unconditionally). [5](#0-4) 
2. Repeatedly send many trigger units to the AA, each carrying a base-asset output smaller than `FULL_TRANSFER_INPUT_SIZE` (defined in `aa_composer.js`, referenced throughout `completePaymentPayload`). [6](#0-5) 
3. Over enough such deposits, most of the AA's on-chain UTXOs for the base asset fall below the threshold and are excluded by `readStableOutputs`/`readUnstableOutputsSentByAAs`.
4. Trigger a legitimate withdrawal/payment from the AA (e.g., the "withdraw funds" branch) whose amount, per the AA's own state accounting, should be fully covered by its balance.
5. `completePaymentPayload` fails to accumulate enough `total_amount` from eligible (non-dust) inputs and calls back `'not enough funds for ' + target_amount + ' bytes'`, causing `sendUnit` to bounce the response via `bounce(err)`, denying the legitimate withdrawal despite sufficient nominal balance. [7](#0-6)
