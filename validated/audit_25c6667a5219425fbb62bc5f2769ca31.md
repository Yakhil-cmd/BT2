### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a restricted ApiClient token to read the status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, and the generic API stack-lookup helper enforces that scope. `Shipit::Api::CCMenuController`, however, overrides the `stack` lookup method with an unscoped `Stack.from_param!(params[:stack_id])`, completely bypassing the `stack_id` binding that every other API controller relies on. This is the same bug class as the reported "deprecated markets" issue: one piece of state (`isBorrowPaused`/deprecation) is checked, but a semantically-linked flag (`isLiquidateBorrowPaused`) that should gate the same resource is not. Here, the "authorised stack" binding is enforced in one controller but silently dropped in a sibling controller that reads the exact same underlying model.

### Finding Description
The base API controller establishes the trust binding "a stack a token authorises == a stack it touches": [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `stack_id` param only within that restricted set. `Shipit::Api::StacksController` (and other API controllers) inherit this and are therefore correctly scoped, as confirmed by the test asserting a scoped client "will only see that one stack": [2](#0-1) 

`Shipit::Api::CCMenuController`, however, redefines `stack` to query `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`: [3](#0-2) 

It only enforces the generic permission string via `require_permission :read, :stack`, which checks that the token has the `read:stack` capability, not that the specific stack matches the token's scope: [4](#0-3) 

The fixture data shows this scoping mechanism is a real, supported feature (`ApiClient#stack` association, `stack_id?`), used elsewhere to restrict a client to one stack: [5](#0-4) 

Because `CCMenuController` also accepts the token via a plain query-string parameter (in addition to Basic Auth), the bypass is trivially reachable: [6](#0-5) [7](#0-6) 

Equality broken: `ApiClient#stack_id` (the stack the token authorises) ≠ `params[:stack_id]` (the stack the CCMenu endpoint actually reads), exactly analogous to `isBorrowPaused` (checked) vs `isLiquidateBorrowPaused` (not checked) guarding the same deprecation action in the external report.

### Impact Explanation
An attacker holding any valid API token restricted to a single stack (e.g., a legitimately-issued CCMenu/CI-status token, which by design is meant to be handed out somewhat freely for build-status widgets) can enumerate and read the CCMenu XML status — including build/lock state (`lastBuildStatus`, `activity`, lock status via `locked stacks show as failed`) — of every other stack in the Shipit instance, including stacks belonging to different repositories/teams they have no authorization to view. This matches the "High" impact category: unauthenticated/unauthorized read of stack state via a credential-boundary bypass.

### Likelihood Explanation
Likelihood is high: it requires only possession of any valid, even minimally-scoped, API token (no elevated privilege, no GitHub App key, no session) and a single unauthenticated GET request with an attacker-chosen `stack_id`. The existing test suite for `CCMenuController` never exercises the cross-stack scoping case, so the gap is untested and would not be caught by CI.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` use the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])` via the inherited `stacks` helper) instead of the raw `Stack.from_param!`, so the `current_api_client.stack_id` binding is honored consistently across all API controllers.

### Proof of Concept
1. Create/obtain two stacks, `stack-A` (owned by org X) and `stack-B` (owned by org Y).
2. Issue (or use an existing) `ApiClient` scoped to `stack-A` only (`stack_id` set, e.g. fixture `here_come_the_walrus` with permission `read:stack`), and obtain its `authentication_token`.
3. Confirm scoping works as intended against a normal API endpoint:
   `GET /api/stacks?...` with this token returns only `stack-A` (per [2](#0-1) ).
4. Send: `GET /api/{stack-B-owner}/{stack-B}/cc.xml?token=<stack-A-scoped-token>` (matching the query-string auth path exercised in [7](#0-6) , but substituting `stack_id` for the unauthorized stack).
5. Observe HTTP 200 with `stack-B`'s CCMenu XML (build status/lock state), even though the token is only authorised for `stack-A` — proving the token-scope-vs-touched-stack binding is not enforced in this controller.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
