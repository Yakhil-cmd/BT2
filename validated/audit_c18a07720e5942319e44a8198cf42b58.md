### Title
Multi-tenant webhook signature verification uses `repository.owner.login` while all handlers act on `repository.full_name` — [File: app/controllers/shipit/webhooks_controller.rb]

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `repository_owner` (`params.dig('repository','owner','login')`), but every `pull_request` handler, including `LabelCapturingHandler`, resolves the target repository/stack from a completely different field, `params.repository.full_name`. If an attacker controls an organization configured in `Shipit.github_organizations` with no `webhook_secret` set (or any org's secret they control), `GitHubApp#verify_webhook_signature` returns `true unless webhook_secret` — signature verification is either bypassed or verified against a secret that has no relationship to the repository actually being mutated.

### Finding Description
The broken binding is: `Shipit.github(organization: repository_owner).webhook_secret` is assumed to authenticate `params.repository.full_name`, but nothing enforces `repository_owner == owner_of(params.repository.full_name)`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) picks the `GitHubApp` for HMAC verification using `repository_owner`: [1](#0-0) 
- `repository_owner` (line 59-62) is read from `params.dig('repository','owner','login')` — fully attacker-controlled JSON, not cross-checked against `full_name`: [2](#0-1) 
- `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb:76-83` **returns `true` unconditionally if `webhook_secret` is blank** for the selected org: [3](#0-2) 
- Once past `verify_signature`, `Shipit::Webhooks.for_event('pull_request')` dispatches to handlers that resolve the repository from `params.repository.full_name`, entirely independent of `repository_owner`: [4](#0-3) 
- `LabelCapturingHandler#capture_labels` then persists attacker-supplied label names onto that resolved stack's `PullRequest`: [5](#0-4) 

Exploit flow: attacker sets `repository.owner.login` to an org configured in Shipit with no `webhook_secret` (or one they control), and sets `repository.full_name` to `victim-org/victim-repo`, `number` to the target PR number matching an existing `pr<N>` review stack. `verify_signature` authenticates against the wrong/absent secret and passes; `LabelCapturingHandler` then finds the victim stack via `full_name` and overwrites its `PullRequest#labels`.

### Why this doesn't necessarily satisfy the "Critical" claim
I could not confirm within this engine that `PullRequest#labels` values are directly promoted into `ReviewStack#env` as uppercased keys, nor that `merge_queue_enabled` stacks call `merge!`/`PTY.spawn` purely off attacker-supplied labels without additional gating (e.g., CI status, required checks, `ContinuousDeliveryLock`, human approval). The question's chain from "labels persisted" to "merge queue advances and merge! fires" requires verifying `ReviewStack#env`'s label-to-env-var behavior and the merge-queue's `MergeRequest`/`merge_status` gating logic — I did not locate and confirm these specific code paths (`ReviewStack#env`, the merge queue advance/`merge!` trigger) in this pass, so I cannot assert the full "unauthorized merge of attacker-controlled code" impact chain is unconditionally true. The signature-verification/owner-mismatch bug itself, however, is real and independently exploitable: it lets an attacker with control over one (no-secret) GitHub org write to a `PullRequest` record belonging to an entirely different org's stack.

### Impact Explanation
Confirmed impact: a payload for one repository (or one weakly-configured org) can mutate another organization's review-stack `PullRequest` record (label list), which is itself a "payload for one repository mutating another's stack" — matching the Critical impact category for cross-tenant record mutation via forged/unauthenticated webhook. Whether this cascades into an unauthorized `merge!` depends on `ReviewStack#env`/merge-queue code not fully traced here.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub orgs (`Shipit.github_organizations`), and at least one of them must have no `webhook_secret` configured (or the attacker must own/control an org's secret) — this is an operator misconfiguration, not solely an engine bug, but the engine does nothing to bind the verifying org to the acted-upon repository, so even a properly-configured multi-org install is exposed if any single org's secret is guessable/leaked/blank. Attacker cost is a single unauthenticated `POST /webhooks` request; fully repeatable against any repository/PR number the attacker can guess.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, after selecting the `GitHubApp` by `repository_owner`, verify that the resolved organization actually matches the owner segment of `params.repository.full_name` before dispatching to handlers (i.e., derive the verifying org strictly from `full_name`'s owner, not a separate `owner.login` field, and reject if they diverge). Additionally, treat a blank `webhook_secret` for a configured org as a hard misconfiguration (fail closed) rather than `return true`.

### Proof of Concept
```ruby
test "pull_request labeled webhook from a different owner.login cannot mutate a repo referenced only by full_name" do
  # Setup: victim org "victim-org" owns repo "victim-org/victim-repo" with an active
  # pr123 review stack whose PullRequest#labels is currently [].
  # Setup: attacker-controlled org "attacker-org" configured in credentials.github
  # with no webhook_secret (or a known secret).

  payload = {
    action: "labeled",
    number: 123,
    pull_request: { ..., head: { sha: "...", ref: "pr-branch" },
                     labels: [{ name: "deploy" }], ... },
    repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  # No valid signature for victim-org is supplied; only a signature (or none)
  # valid for attacker-org.
  post "/webhooks", params: payload,
       headers: { "X-Github-Event" => "pull_request",
                  "X-Hub-Signature" => attacker_org_signature_or_blank }

  assert_response :ok
  victim_pr = shipit_stacks(:victim_pr123).pull_request.reload
  assert_equal ["deploy"], victim_pr.labels  # binding broken: victim-org's PR
                                              # was mutated by a request that
                                              # never authenticated as victim-org
end
```
This proves the record-mutation impact. Extending the assertion to `merge!`/`PTY.spawn` firing requires confirming `ReviewStack#env`'s label→env-var promotion and the merge-queue advance trigger, which were not located/verified in this investigation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
