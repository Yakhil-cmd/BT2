## Confirmed Root Cause

`Handler#stacks` resolves the target `Stack` purely from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC against using a *different* field, `repository_owner`, taken from `params.dig('repository','owner','login')` or `params.dig('organization','login')` [2](#0-1) . The HMAC (`verify_webhook_signature`) only proves the raw body was signed by *some* configured organization's secret — it does not constrain which `repository.full_name` may appear inside that signed body [3](#0-2) . `PushHandler` and `StatusHandler` then act using `repository.full_name` / bare `sha` lookups with no re-check that the owner in `full_name` matches the org whose secret validated the request [4](#0-3) [5](#0-4) .

This is exactly the "organization authenticated versus repository that is written" binding named in the rules, and it is broken: **the org used to authenticate ≠ the repo used to write**.

### Why this is in scope and exploitable
Shipit explicitly supports multi-tenant deployments where `config/secrets.yml` `github:` holds a separate `webhook_secret` per organization [6](#0-5) . Each org's GitHub App owner legitimately possesses their own org's `webhook_secret` (they generate it when creating their App, per the docs) — this is not a privileged secret belonging to the Shipit deployer, it's routinely handed to each tenant org admin. That tenant is an "unprivileged attacker" with respect to *other* tenants' stacks/repos hosted on the same shared Shipit instance.

An attacker who is an admin of "attacker-org" (with a legitimate, self-issued webhook secret for that org) can POST directly to `/webhooks` with `X-Github-Event: status` (or `push`), setting:
```json
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
signed with `attacker-org`'s own webhook secret. `verify_signature` picks `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC check passes because it was genuinely signed by that org's secret — the signature never binds `repository.full_name` to `repository.owner.login`. `StatusHandler` then finds `Commit.where(sha: params.sha)` across **all** stacks (no organization scoping in that query at all) and marks arbitrary commits' CI status `success` [5](#0-4) , or `PushHandler` triggers `sync_github` on victim-org's stack.

### Impact
Forging a `status` event to mark an arbitrary commit "success" on a victim stack directly defeats CI-based deploy/merge gating (`required_statuses`, `blocking_statuses` in `deploy_spec.rb`) and the merge-queue's `all_status_checks_passed?` check that gates `MergeRequest#merge!` [7](#0-6) , enabling an unauthorized deploy or an unauthorized auto-merge on a repository the attacker has no GitHub-side access to. This meets the "unauthorized deploy...or merge" High-impact bar.

### Recommendation
`Handler#stacks` (and `StatusHandler#process`) must verify that the resolved `Repository`/`Stack`'s owner matches the organization whose secret validated the webhook (i.e., cross-check `repository.owner.login` == the owner portion of `repository.full_name`, and scope `Commit.where(sha:)` lookups by the resolved stack's repository) before acting, rather than trusting `full_name` independently of the field used for signature-org selection.

### Proof of Concept (conceptual)
1. Attacker is legitimate admin of `attacker-org`, which has its own GitHub App + `webhook_secret` configured in the shared Shipit instance (per multi-org setup in `docs/setup.md`).
2. Attacker computes `sha256=<hmac>` over a crafted JSON body using `attacker-org`'s webhook secret, with `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"` and `sha` = a real pending/failing commit sha in `victim-org/victim-repo`, `state: "success"`.
3. POST to `/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the victim commit regardless of org — and calls `create_status_from_github!`, flipping the commit's CI status to success, unblocking deploy/merge on `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
