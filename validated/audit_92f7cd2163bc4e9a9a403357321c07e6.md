### Title
Missing Built-in Audience/Instance Binding in `is_valid_signed_package()` Allows Cross-AA Replay of Signed Packages - (File: formula/evaluation.js)

### Summary
`is_valid_signed_package()` (backed by `signed_message.validateSignedMessage()`) verifies only that a `signed_message` payload was signed by a given address and that the referenced `last_ball_unit` is stable — it never binds the signed package to the specific AA/contract instance ("audience") that is supposed to consume it. This mirrors the CXF `JwtAccessTokenValidator` flaw: the signature (like a JWT) is valid, but nothing in the verification path forces it to have been issued *for this particular verifier*. Binding to the verifying instance (`this_address`) is entirely optional and must be re-implemented by every AA author inside oscript.

### Finding Description
`is_valid_signed_package` in the oscript evaluator delegates signature/definition checking to `signed_message.validateSignedMessage`, which only checks:
- that `authors` contains a valid, sorted set of addresses with correct definitions,
- that the signature verifies against `getSignedPackageHashToSign(objSignedMessage)`, and
- that `last_ball_unit` is stable and not from the future. [1](#0-0) [2](#0-1) 

None of these checks reference `this_address` (the AA currently evaluating the package) or any other "audience" concept. The hash that is actually signed (`getSignedPackageHashToSign`) covers `signed_message`, `authors`, `last_ball_unit`, `version` — but not the identity of the intended verifying contract. Consequently, the *only* place any instance/audience binding can be introduced is inside the free-form `signed_message` object itself, and only if the AA author remembers to add and check such a field.

The project's own reference implementation demonstrates this is a manual, easy-to-forget obligation: the sample state-channel AA explicitly re-implements audience binding by checking `signed_message.channel != this_address` and `signed_message.period != var['period']` *before* calling `is_valid_signed_package`, precisely because the underlying primitive does not enforce it: [3](#0-2) [4](#0-3) 

This is structurally identical to the CVE-2026-50627 root cause: `JwtAccessTokenValidator` verifies the JWT signature/issuer trust chain but omits the `aud` claim check, so a token minted for Resource-Server-A is honored by Resource-Server-B. Here, `is_valid_signed_package`/`validateSignedMessage` verify the ECDSA signature and address/definition chain but provide no analogous "intended recipient contract" claim check by default — that check is opt-in oscript logic, not a library guarantee.

### Impact Explanation
Any AA template that authorizes fund movement based on `is_valid_signed_package(pkg, counterparty_address)` without independently re-checking `this_address` (or another instance-unique discriminator) inside `signed_message` is vulnerable to token/authorization confusion across multiple deployments of the same template between the same set of counterparties (e.g., two independent payment-channel instances, two independent order books, or a template AA cloned via `definition template`). A signature legitimately produced by counterparty B authorizing a balance/state transition in instance #1 can be replayed unmodified as trigger data against instance #2, where the base `is_valid_signed_package` check still returns `true` (correct signer, correct message, fresh `last_ball_unit`), letting the attacker force AA #2 into an unauthorized state transition/fund payout that counterparty B never intended for that specific instance. This is a concrete AA fund loss / unauthorized spending vector, not merely a documentation gap, since the vulnerable condition is the default behavior of the primitive and only avoided by defensive coding that is not enforced anywhere in `definition.js` or `signed_message.js`.

### Likelihood Explanation
Exploitation requires only posting a data trigger to an AA — something any unprivileged unit poster can do. It does not require compromising a hub, node, or key; it only requires (a) knowledge of a signed package intended for a sibling AA instance sharing the same counterparties (obtainable off-chain, e.g., an old channel state), and (b) an AA template that omits the manual `this_address`/instance-id check the framework's own sample code warns is necessary. Given that the framework does not surface or enforce this requirement in `is_valid_signed_package`'s validation logic (`formula/validation.js` complexity/type checks also do not require or reference `this_address`), the likelihood of at least some deployed templates missing this defensive check is non-trivial. [5](#0-4) 

### Recommendation
- Add an optional/mandatory "audience" concept to `is_valid_signed_package` (e.g., allow passing an expected `this_address`/scope value that must appear inside `signed_message` and is checked by the primitive itself, not left to oscript).
- At minimum, update documentation/linting for AA authors to always require and check an instance-unique field (address of `this_address` or explicit channel/order id) in every `signed_message`, and add a static-analysis warning (already partially done via `formula/validation.js`) when `is_valid_signed_package` is used without any comparison to `this_address` in the same branch.
- Consider deprecating template-based AA re-use patterns that share the same authorization address/definition across multiple stateful instances unless audience binding is enforced by the platform.

### Proof of Concept
1. Deploy the sample AA in `test/samples/payment_channels.oscript` twice with the same `$addressA`/`$addressB` but at two different AA addresses (Channel-1, Channel-2) — a supported and expected usage pattern for template AAs.
2. Off-chain, party A signs `{signed_message: {channel: <Channel-1 address>, period: 1, amount_spent: 100}, authors: [...]}` and sends it to B as an update proving A owes B 100.
3. If a developer copies the pattern but forgets the `signed_message.channel != this_address` guard shown in `test/samples/payment_channels.oscript:41-46` (i.e., calls only `is_valid_signed_package(trigger.data.sentByPeer, $addressA)` with no `channel` cross-check) inside Channel-2's `close`/`fraud_proof` branch, B can post the exact same trigger data to Channel-2.
4. `is_valid_signed_package` in `formula/evaluation.js:1653-1701` and `signed_message.validateSignedMessage` in `signed_message.js:117-303` will both return `true`, since they never verify that the package was intended for Channel-2's `this_address`, allowing B to force an unauthorized balance/payout in Channel-2 using an authorization A only ever gave for Channel-1.
