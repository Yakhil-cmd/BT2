### Title
Reverting `_to` in `handleKLAYTransfer` permanently locks bridged KAIA and stalls `lowerHandleNonce` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` sends KLAY to `_to` via a bare low-level call and hard-reverts on failure. Because the KLAY delivery is the last step and there is no error-isolation, a user who sets `_to` to a contract whose fallback reverts causes every operator attempt to process that nonce to revert. All state changes — including the nonce accounting — are rolled back, so `lowerHandleNonce` is permanently stuck, `recoveryBlockNumber` never advances, and the deposited KAIA is frozen in the source bridge with no on-chain escape path.

---

### Finding Description

`handleKLAYTransfer` executes the following sequence:

1. `_lowerHandleNonceCheck` — gate check
2. `_voteValueTransfer` — threshold vote, sets `closedValueTransferVotes[N] = true`
3. `_setHandledRequestTxHash` — marks the source tx hash
4. `handleNoncesToBlockNums[N] = _requestedBlockNumber`
5. `_updateHandleNonce(N)` — advances `lowerHandleNonce` and `recoveryBlockNumber`
6. `emit HandleValueTransfer`
7. `(bool ok, ) = _to.call.value(_value)("")`
8. `require(ok, "handleKLAYTransfer: transfer failed")` ← **hard revert** [1](#0-0) 

If step 8 reverts, the EVM rolls back **all** of steps 2–7. `closedValueTransferVotes[N]` returns to `false`, `handleNoncesToBlockNums[N]` returns to `0`, and `lowerHandleNonce` stays at `N`. The `_updateHandleNonce` loop in `BridgeTransfer.sol` advances `lowerHandleNonce` only when `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`: [2](#0-1) 

Because `handleNoncesToBlockNums[N]` is always `0` (every tx reverts), `lowerHandleNonce` can never advance past `N`, even if nonces `N+1`, `N+2`, … are successfully handled. There is no owner/admin function anywhere in `BridgeTransfer`, `BridgeTransferKLAY`, or `BridgeOperator` to forcibly skip or reset `lowerHandleNonce`. [3](#0-2) 

The Go-side bridge manager syncs `lowerHandleNonce` from the contract and uses it as the lower bound for event processing: [4](#0-3) 

The value-transfer recovery (`vt_recovery.go`) uses `hint.blockNumber` — which is sourced from the contract's `recoveryBlockNumber` — as the scan start block. Since `recoveryBlockNumber` never advances past the block before nonce `N`, the recovery loop perpetually re-scans the same range and re-submits the stuck nonce, burning operator gas indefinitely: [5](#0-4) 

---

### Impact Explanation

| Asset / State | Effect |
|---|---|
| User's deposited KAIA | Permanently locked in the source bridge — the source-chain `RequestValueTransfer` event is emitted and the KAIA is held, but the destination-chain handle can never succeed |
| `lowerHandleNonce` / `recoveryBlockNumber` | Frozen at nonce `N`; the recovery subsystem re-scans the same block window forever |
| Operator gas | Drained on every recovery retry; each attempt re-votes and re-executes all state writes before reverting |

This satisfies the "unauthorized … burn … affecting KAIA, bridged assets" and "persistent corruption … that breaks … withdrawals, transfers, or settlement" criteria in the allowed-impact gate.

---

### Likelihood Explanation

Any user who initiates a KLAY transfer on the source chain controls `_to`. Setting `_to` to:

- a contract whose `fallback()` unconditionally reverts, **or**
- a honey-pot contract that succeeds in `eth_call` simulation (e.g., checks `tx.origin == address(this)` or reads a storage slot flipped by a front-run) but reverts on-chain

is sufficient to trigger the stuck state. No special privilege is required — `requestKLAYTransfer` is open to any caller: [6](#0-5) 

The front-running variant (honey-pot) is directly analogous to the PromiseRouter M-19 scenario: the operator simulates the handle tx, it passes, the attacker flips the contract state, and the submitted tx reverts.

---

### Recommendation

Isolate the KLAY delivery from the nonce-accounting path. After all nonce state is committed, attempt the transfer and handle failure gracefully rather than reverting the whole transaction:

```solidity
// After _updateHandleNonce and emit HandleValueTransfer:
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    // Keep KLAY in bridge; emit a recoverable-failure event so
    // the recipient can claim via a separate withdrawal path.
    emit KLAYTransferFailed(_requestTxHash, _to, _value);
}
```

This ensures `lowerHandleNonce` always advances regardless of `_to` behaviour, and the deposited KAIA remains claimable rather than permanently frozen.

### Proof of Concept

```solidity
// Attacker deploys this on the destination chain
contract RevertOnReceive {
    receive() external payable { revert("no KLAY"); }
    fallback() external payable { revert("no KLAY"); }
}
```

1. Attacker calls `requestKLAYTransfer(address(revertOnReceive), value, "")` on the **source** bridge, depositing KAIA.
2. The source bridge emits `RequestValueTransfer` with nonce `N` and `_to = revertOnReceive`.
3. Operators call `handleKLAYTransfer(..., revertOnReceive, value, N, ...)` on the destination bridge.
4. Steps 2–6 of `handleKLAYTransfer` execute; then `revertOnReceive.call.value(value)("")` reverts.
5. `require(ok)` propagates the revert — all state changes roll back.
6. `lowerHandleNonce` remains `N`; `recoveryBlockNumber` remains at the block before `N`.
7. The recovery loop re-submits the same handle tx on every cycle, burning operator gas.
8. The attacker's KAIA is frozen in the source bridge with no on-chain recovery path. [7](#0-6) [8](#0-7)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
