### Title
Unbounded `attested` attestor list in address definitions enables gas/query-cost DoS analogous to `registeredCustodians` loop - (File: `definition.js`)

### Summary
The external report flags unbounded loops over `registeredCustodians` that can exhaust gas and block checkpoint processing. In ocore, the `attested` operator in address-definition evaluation (`definition.js`) accepts an attestor address array (`arrAttestors`) with no length cap and no proportional complexity/ops accounting, unlike the sibling `in data feed` / `in merkle` operators that explicitly charge `complexity += arrAddresses.length-1` for their oracle-address arrays.

### Finding Description
When a new address definition is validated in `validateDefinition`'s `evaluate()` function, the `attested` case only checks that each element of `arrAttestors` is a valid address in a plain loop, and returns: [1](#0-0) 
Unlike `and`/`or`/`r of set`/`weighted and` (which recurse into `evaluate()` for every element, so `complexity++`/`count_ops++` fire per element and are checked against `constants.MAX_COMPLEXITY`/`MAX_OPS`), and unlike `in data feed`/`in merkle` (which explicitly add `arrAddresses.length-1` to `complexity`), the `attested` operator does not recurse or charge complexity per attestor: [2](#0-1) [3](#0-2) 
So a single `evaluate()` invocation for `['attested', ['this address', [addr1, addr2, ..., addrN]]]` costs only 1 unit of complexity/ops regardless of how many attestor addresses `N` are packed in — the array is only bounded indirectly by the overall unit size limit (`constants.MAX_UNIT_LENGTH`), which still permits thousands of base32 addresses.

Later, every time this address signs any unit, `validateAuthentifiers`'s `attested` branch re-executes the check by calling `storage.filterAttestedAddresses` with the full, attacker-controlled `arrAttestors` array as `arrAttestorAddresses`: [4](#0-3) 
This produces a DB query keyed on a potentially very large `IN(...)` list on every validation of every unit signed by that address — directly mirroring the reported bug class: an attacker-controlled, unbounded collection (`registeredCustodians` there, `arrAttestors` here) is iterated/queried inside a hot validation path (`checkpoint`/`evaluateReleaseSchedule` there, unit/author validation here) with no practical cap enforced at registration/definition time.

### Impact Explanation
If an attacker defines (or gets others to define) an address whose definition embeds a very large `attested` attestor array, every future unit authored by (or requiring evaluation of) that address triggers an expensive, attacker-sized DB lookup during core unit validation (`validateAuthentifiers` is invoked for every author on every incoming unit, including via `validateSignedMessage` and witness/AA-adjacent flows). This can degrade validation performance network-wide for units touching that address, and in the worst case (very large attestor lists near the unit-size ceiling) cause resource-heavy queries repeatedly on the hot validation path — a node-level availability/DoS risk on the core unit-validation pipeline, analogous to the `checkpoint` failing to proceed in the original report. It does not by itself enable double-spend or fund theft, so severity is Medium: a network-availability/performance-degradation issue on the shared validation path rather than unauthorized spending.

### Likelihood Explanation
Likelihood is Medium: creating such a definition and getting it accepted is a fully unprivileged action available to any unit poster (address definitions are self-defined, no allow-listing like the DAO-gated custodians in the report). The array is bounded only by the generic unit-size limit, which still permits large attestor sets. The main mitigating factor is that this is a repeated cost per validating unit rather than an immediate hard block, and node operators/witnesses could in principle avoid interacting with such addresses, but ordinary validation of any unit signed by the address is unavoidable for all full nodes.

### Recommendation
Charge complexity/ops proportional to `arrAttestors.length` in the `attested` case of `evaluate()` (as already done for `in data feed`/`in merkle`), and/or enforce an explicit maximum attestor-list length (mirroring `constants.MAX_ATTESTORS_PER_ASSET`, already used for asset attestor lists in `checkAttestorList`) directly in the address-definition `attested` operator validation, so the size of `arrAttestors` cannot scale unboundedly relative to the complexity budget.

### Proof of Concept
1. Attacker crafts an address definition: `['attested', ['this address', [addr_1, addr_2, ..., addr_N]]]` where `N` is chosen to approach `constants.MAX_UNIT_LENGTH` while keeping `complexity`/`count_ops` at the minimum (since the array elements aren't recursively evaluated, they don't count toward `MAX_COMPLEXITY`/`MAX_OPS`).
2. Attacker posts a unit defining this address (`validateDefinition` accepts it since the only checks are per-element `isValidAddress` and the overall unit-size ceiling).
3. Attacker (or any other party) subsequently authors units with this address. Each such unit's validation invokes `validateAuthentifiers` → `attested` branch → `storage.filterAttestedAddresses(conn, {arrAttestorAddresses: arrAttestors}, ...)` with the full large array, executed on every node validating the unit.
4. Repeating step 3 with many units forces repeated expensive queries across the network's validation pipeline, unlike the bounded-cost behavior intended by the complexity/ops accounting elsewhere in `definition.js`.

*Note: I was unable to inspect the exact implementation of `storage.filterAttestedAddresses` (its file could not be retrieved via the available tools before the iteration limit), so the precise query cost/behavior for large `arrAttestorAddresses` inputs is inferred from its usage pattern rather than confirmed line-by-line. This should be verified directly in `storage.js` before treating the query-cost claim as conclusively proven.*
