### Title
Non-constant-time string comparison (`===`/`!==`) in oscript formula evaluator enables timing attack on AA-stored secrets - (File: formula/evaluation.js)

### Summary
The oscript formula evaluator used to run Autonomous Agent (AA) code compares arbitrary strings — including AA state variables that developers commonly use to store secrets, passwords, redemption codes, or one-time claim tokens — with JavaScript's native `===`/`!==` operators. Because native string equality in V8 short-circuits at the first mismatching byte, comparison time is a (weak) function of how many leading characters of the attacker-supplied guess match the secret stored in AA state. Any address can trigger an AA with arbitrary `trigger.data` values, so an attacker can iteratively probe a secret comparison exposed by an AA (e.g., `trigger.data.code == var['secret']`) and use response-latency differences to narrow down the secret, analogous to CVE‑2024‑0436's single-user password check.

### Finding Description
`formula/evaluation.js`'s `'comparison'` case implements `==`/`!=` for strings with plain JS equality: [1](#0-0) 
and the boolean/string fast-path branch used for `==`/`!=` between two strings: [2](#0-1) 

An AA author can write an oscript definition that keeps a secret in a state variable (`var['secret']`) and unlocks funds/state changes only when the trigger-supplied string exactly matches it, e.g. `require(trigger.data.code == var['secret'], 'bad code')`. Any unprivileged address can send arbitrary triggers with `trigger.data.code` and observe how long the AA takes to execute/bounce (via `handleTrigger` in `aa_composer.js`, which is reachable from any posted unit that pays an AA): [3](#0-2) 
Because `===` is not constant-time, guesses that match more leading bytes of the secret take (on average, in aggregate over repeated network conditions) marginally longer to fail than guesses that mismatch early, letting an attacker perform a byte-by-byte brute force of the stored secret across many trigger units, exactly mirroring the pattern described in CVE‑2024‑0436.

This is a direct analog of the reported bug class: single string secret compared with the native `!==`/`===` operator instead of a constant-time comparison, reachable by an unprivileged party (any unit sender that can construct and post an AA trigger unit).

### Impact Explanation
If exploited, an attacker could recover secrets guarded by AA-level string equality checks (e.g., claim codes, referral codes, redemption secrets, password-gated payout AAs), leading to unauthorized fund release from the AA (unauthorized spending / fund loss for the AA and its legitimate beneficiaries). This matches the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Exploitability is significantly dampened by the same mitigating factors noted in the original CVE: each guess requires composing and broadcasting a full unit (with fees, unit validation, DAG inclusion, and AA execution scheduling), all of which introduce large and non-constant latency/jitter that overwhelms the sub-microsecond signal from a JS string comparison. There is no evidence in the codebase of a fast, low-noise oracle for this timing side channel (no synchronous/low latency in-process comparison exposed to a remote caller). Practical exploitation over the network against a live AA is very difficult, though theoretically possible under a controlled/low-jitter environment. This mirrors the CVSS 7.1/AC:L rating rationale in the original report, where the network overhead is explicitly called out as reducing reliability.

### Recommendation
- Add a constant-time string comparison built-in to oscript (e.g., a `constant_time_eq(a, b)` function) for use whenever secret values are compared in AA logic, and document/encourage its use for password/secret-style checks.
- Alternatively, discourage direct secret storage in `var[...]` state; recommend hashing secrets and comparing hash digests (though note hash-vs-hash comparisons are not exploitable by timing since preimage search cannot exploit partial hash matches) — i.e., migrate password-style checks to use `sha256(...)`-based comparisons instead of raw string equality, as already used in `definition.js`'s `'hash'` authentifier pattern: [4](#0-3) 
- Consider adding a fixed per-trigger minimum processing delay for AA responses that fail a comparison to further mask any residual timing signal.

### Proof of Concept
1. Deploy an AA with state logic:
   ```
   {
     if: "{trigger.data.code == var['secret']}",
     messages: [ ... pay out reward ... ]
   }
   ```
   where `var['secret']` was set once via a prior trusted trigger.
2. As an unprivileged attacker, repeatedly send trigger units with `trigger.data.code` values that vary in their matching prefix length against the true secret, measuring time from trigger unit inclusion to AA bounce/response.
3. Statistically aggregate timing samples per guess (to filter DAG/network jitter) and use differential timing to infer which prefix guesses are "closer" to `secret`, iterating character-by-character until the full secret is recovered, consistent with the comparison logic in: [5](#0-4)
