### Title
Webhook Signature Verification Uses Attacker-Controlled Payload to Select the Secret, Decoupling the Authenticated Organization from the Repository Acted On - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/`webhook_secret` to validate the incoming request against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body, before the signature has been checked. Every downstream handler (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`, etc.) then looks up the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` — a field that was never covered by the equality the signature is supposed to enforce. This mirrors the Xave Finance bug class: the value used to authorize the action (which org's secret validated the signature) and the value the action is actually taken against (the repository the webhook manipulates) are not the same field, and the deployment-trust binding "verified signature ⟺ payload acted on" is broken across the organization boundary.

### Finding Description
`Shipit.github` supports a **multi-organization** configuration: `secrets.github` can hold one `webhook_secret` per organization key, resolved via `Shipit.github_app_config(organization)` [1](#0-0) .

In the webhook flow:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` comes from `params`, which is the **attacker-supplied, not-yet-verified** JSON body (`JSON.parse(request.raw_post)` in `#create`) [3](#0-2) . The HMAC is only checked against `request.raw_post` as a whole using the secret belonging to whatever organization the attacker names in that same body — the equality enforced is `HMAC(secret_of(payload["repository"]["owner"]), raw_body) == signature`, not `HMAC(secret_of(the actual target repo being written), raw_body)`.

After verification, the full raw `params` (including `repository.full_name`) is dispatched unchanged to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

And every handler resolves its target purely from `repository.full_name`, e.g.:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
`PushHandler#process` uses this to trigger `stack.sync_github` [5](#0-4) , and other handlers (pull-request assigned/closed/labeled/reopened) similarly resolve repository/stack from `params.repository.full_name` to archive/unarchive/update review stacks [6](#0-5) .

Because `repository.owner.login` (used to select the secret) and `repository.full_name` (used to select the target repository/stack) are two independent, attacker-controlled fields of the same unauthenticated body, nothing forces them to refer to the same repository/organization.

### Impact Explanation
For this to be exploitable, a Shipit deployment must be configured with more than one organization in `secrets.github` (each with its own `webhook_secret`) — this is an explicitly documented and supported configuration (`Shipit.github_organizations`, `github_app_config`) [7](#0-6) . Given that, anyone who legitimately controls (or has leaked/obtained) the GitHub webhook secret for *one* configured organization — which is not a Shipit credential, session, or GitHub App private key, and is not "repository write access" to the target repo — can forge a webhook whose `repository.owner.login`/`organization.login` names their own org (to pass signature verification with their own secret) while setting `repository.full_name` to a *different, unrelated* organization/repository also tracked by the same Shipit instance. This lets an unprivileged-relative-to-the-victim-repo attacker trigger cross-repository state changes: forcing `sync_github` re-fetches, archiving/unarchiving review stacks, or injecting fabricated commit statuses for a repository they do not own — i.e., cross-repository writes through a single shared engine.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-organization mode and requires the attacker to possess a valid webhook secret for at least one of the configured organizations (typically obtainable by anyone who can configure the GitHub App/webhook for their own org in that installation, not by compromising the victim organization). This is a realistic configuration for hosted/shared Shipit deployments serving multiple GitHub orgs.

### Recommendation
Do not let payload fields determine which secret verifies the payload. Either: (1) verify the raw signature against every configured organization's secret and only accept the request if the resulting matched organization's repositories/stacks are the ones actually referenced by `repository.full_name` in the payload, or (2) bind the webhook endpoint to a single org/secret per route (e.g. `/webhooks/:organization`) so the URL — not attacker-controlled JSON — determines the secret, and then assert `payload.dig('repository','owner','login') == organization` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, tracked stacks exist in Shipit).
2. Attacker crafts a `push` payload JSON with `"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}` and other required push fields (`ref`, `after`).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, raw_body)` and POSTs it to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and successfully verifies the signature against `orgA`'s secret [8](#0-7) .
5. `PushHandler` then resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [9](#0-8) , even though the signature never involved `orgB`'s secret.

Uncertain/unverified: I could not confirm in the index whether this specific multi-org configuration is commonly deployed in practice, nor find any additional server-side check elsewhere in the engine that cross-validates `repository.owner.login` against `repository.full_name`'s owner before dispatch — the search of `app/models/shipit/webhooks/**` handlers and `webhooks_controller.rb` found none.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
