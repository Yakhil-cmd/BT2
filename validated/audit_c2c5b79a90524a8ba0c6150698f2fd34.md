Investigation into `runtime/src/bank/partitioned_epoch_rewards/*` and `runtime/src/stake_utils.rs` shows this attack is not free for the attacker and is already economically bounded:

- Every stake account must satisfy both the rent-exempt reserve (`rent.minimum_balance(StakeStateV2::size_of())`) and the protocol-enforced minimum delegation amount, which is `1 SOL` once `stake_raise_minimum_delegation_to_1_sol` / `upgrade_bpf_stake_program_to_v5` is active [1](#0-0) . This means creating N "tiny" stake accounts costs the attacker at least N SOL plus N rent-exempt reserves — real capital that scales linearly with the number of accounts created, not a free amplification vector.
- The reward *distribution* phase already bounds per-epoch work: `get_reward_distribution_num_blocks` computes the number of blocks needed to cover all stake rewards but clamps it to at most 10% of the epoch's slots (`MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH`), so the number of distribution blocks cannot grow unbounded even if the number of stake accounts grows [2](#0-1) .
- The reward *calculation* phase (`calculate_rewards_for_partitioning` / `calculate_stake_rewards_and_commissions`) does scale with the total number of stake delegations network-wide, but this is a known, documented O(n) cost inherent to the design (the code comment explicitly discusses behavior "for N stake delegations, where N is >1,000,000") and is parallelized via rayon [3](#0-2) . This is not something introduced or amplified specifically by an attacker — any real stake growth (legitimate or not) contributes identically, and growth is capital-gated by the minimum-delegation requirement.

Because creating each additional stake-account delegation costs the attacker real, non-recoverable capital (≥1 SOL + rent-exempt reserve) proportional to the desired inflation of iteration count, this does not meet the bug's premise that "epoch-boundary work... cannot be inflated by attacker-created accounts" for free. The cost model make this economically equivalent to organic stake growth, which the protocol is already designed and tested to handle via the block-count clamp and rayon-parallelized calculation. No missing guard, overflow, or exploitable primitive was found in the reachable Rust path.
