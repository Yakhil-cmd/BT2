## Title
Webhook signature verification is scoped to an attacker-controlled organization field while status/commit writes are applied with no repository scoping, enabling cross-organization CI status forgery — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). The `StatusHandler` that actually mutates state (`Commit.where(sha: params.sha)`) performs a **global** commit lookup with no organization/repository binding at all. In a multi-organization Shipit deployment, this breaks the equality "organization that authenticated == repository/commit that is written," letting a user who legitimately controls one configured organization's GitHub App forge a `status` event that is signed with their own (correctly configured) secret but whose `sha` targets a commit belonging to a completely different organization's stack.

## Finding Description
The controller validates the webhook this way: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization:)` resolves to a distinct `GitHubApp`/secret **per organization key** in a multi-org config: [3](#0-2) 

and `verify_webhook_signature` is only checked against whichever org's secret was selected by that attacker-supplied field: [4](#0-3) 

Once the signature (correctly computed for the *claimed* organization) passes, the same raw payload is dispatched to handlers by event type without any re-validation that the organization used for authentication matches the resource the handler will mutate: [5](#0-4) 

Most handlers scope their writes through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (the `Handler` base class), which is a different payload field than the one used for authentication: [6](#0-5) 

Critically, `StatusHandler` doesn't even use `repository_name` — it looks up commits **globally by sha**, with zero repository/organization scoping whatsoever: [7](#0-6) 

`CheckSuiteHandler` is scoped by `stacks` (which is repo-name-based), but `StatusHandler` has no such guard.

**Attack sequence (before/after):**
- Before: Attacker administers a legitimate GitHub App for Organization A, which is configured in this Shipit instance's `secrets.yml` under a distinct multi-org key (`github.orgA.webhook_secret`). Attacker knows/controls this secret because they configured Organization A's App themselves. Organization B is an unrelated, higher-trust org also hosted on the same Shipit instance, with a stack requiring specific CI `context` statuses before continuous deployment proceeds (`ci.require`).
- Attacker crafts a `status` webhook body: `repository.owner.login = "orgA"` (so `verify_signature` looks up and validates against Organization A's known secret — passes) but `sha` = the HEAD sha of an open commit in Organization B's stack, `state = "success"`, `context` = one of Organization B's required CI contexts.
- After: `Commit.where(sha: params.sha)` finds Organization B's commit (global lookup, no owner check) and `create_status_from_github!` records a forged success status for it, satisfying `ci.require` and permitting Shipit to proceed with an otherwise-blocked continuous deploy/merge of that commit — despite the attacker having no relationship to Organization B, its repository, or its GitHub App secret.

## Impact Explanation
This breaks the binding between "the organization that authenticated the webhook" and "the repository/commit whose state is written," which is exactly the class of bug called out in scope (org that authenticated vs. repository that is written). The concrete consequence is that a low-privilege actor (an admin of any one organization hosted on a shared Shipit instance) can forge CI status data for a commit belonging to an entirely different organization, bypassing `ci.require` gating and triggering an unauthorized deploy/merge for a stack they do not own or have any legitimate access to. Per the scope's impact categories, "an unauthorized deploy, rollback or merge" is Critical.

## Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations sharing the same `/webhooks` endpoint (a documented, supported configuration — `config/secrets.development.shopify.yml`), and (2) the attacker to control one such organization's own legitimately-configured GitHub App/webhook secret. No access to Organization B's credentials, private key, or any privileged Shipit account is required — the attacker only signs with their own, correctly-configured secret. This is a realistic misuse scenario for any Shipit deployment that onboards more than one organization, which the codebase explicitly documents and supports.

## Recommendation
Bind signature verification and payload consumption to the same trust anchor:
- After verifying the signature for the resolved organization, re-derive the acting `Repository`/`Stack` strictly from `repository.full_name`, and assert that its owner matches the organization whose secret validated the signature; reject otherwise.
- Fix `StatusHandler#process` to scope the `Commit` lookup through `stacks` (as `CheckSuiteHandler` does) rather than a global `Commit.where(sha:)`, ensuring statuses can only be applied to commits belonging to the repository named in the payload, which itself must match the authenticated organization.

## Proof of Concept
Given a multi-org config:
```yaml
github:
  orgA:
    webhook_secret: "secretA"   # attacker legitimately knows this
  orgB:
    webhook_secret: "secretB"   # attacker does not know this; orgB stack requires ci.require: [ci/tests]
```
1. Attacker computes `sha1=HMAC(secretA, body)` for:
```json
{
  "sha": "<HEAD sha of orgB's pending commit>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "orgA" } }
}
```
2. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, validates against `secretA` — passes. [8](#0-7) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged success status on Organization B's commit, with no check that this commit belongs to `orgA`. [7](#0-6) 

**Uncertainty noted:** I was unable to fully inspect `Commit#create_status_from_github!` and the exact `ci.require` deploy-gating check within the given tool budget, so the precise mechanics tying a forged status to an actual triggered deploy are inferred from `README.md`'s documented `ci.require` behavior rather than directly confirmed in code. If continuous deployment does not automatically re-check statuses at deploy time (e.g., only at manual-deploy UI display), the practical impact would be reduced from "unauthorized deploy" to "spoofed status/CI display data" (still a High-severity write with no repository scoping, but not necessarily Critical). A Devin session with full file access would be needed to confirm the exact deploy-trigger path from `Status` records.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
