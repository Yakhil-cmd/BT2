Based on my investigation, I found a concrete binding-break in the webhook trust model that matches the report's bug class ("a validation function says a state is acceptable, but the code that actually mutates protected state doesn't verify the same thing that was checked").

### Title
Unauthenticated/weakly-authenticated `membership` webhook can grant `Shipit.github_teams` authorization without real GitHub team membership - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` derives *which organization's secret to check against* directly from the untrusted JSON payload, and skips verification entirely whenever that organization's `webhook_secret` is not configured (a documented, optional setting). `MembershipHandler` then uses the same untrusted payload fields (`team.id`, `team.name`, `team.slug`, `organization.login`, `member.login`) to create/update a local `Team` record and add an arbitrary `User` as a member, with no cross-check against GitHub's real team membership. Because Shipit's login-time authorization (`Shipit.github_teams`) is enforced against these locally stored `Team`/membership records rather than a live GitHub check, a forged `membership` webhook lets an attacker bind an arbitrary `User` to a `Team` whose `organization`/`slug` matches a configured restricted team, without ever holding that GitHub team membership.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` intentionally no-ops when `webhook_secret` is blank — a state that is explicitly supported and documented as "optional": [3](#0-2) 

Once past this gate, `MembershipHandler#process` trusts the payload wholesale to mutate authorization-relevant records: [4](#0-3) 

The binding that should hold is: `team membership verified by GitHub` == `team membership recorded in Shipit's Team/User records used to gate Shipit.github_teams access`. Instead, the handler treats an attacker-supplied `organization.login`, `team.slug`, `team.id`, and `member.login` as ground truth, with no re-validation against GitHub's API. `Shipit.github_teams`/`oauth_teams` (used to restrict login) is configured in `lib/shipit.rb` and `lib/shipit/github_app.rb`: [5](#0-4) 

I was not able to fully trace the exact query `app/controllers/concerns/shipit/authentication.rb` runs against `Team`/`Membership` at login time within my remaining tool budget — this should be verified directly, but the surrounding evidence (dedicated `lib/tasks/teams.rake`, `Team#add_member`, and `oauth_teams`/`github_teams` config wired through `GitHubApp`) strongly indicates local `Team` membership is what backs the `Shipit.github_teams` restriction rather than a per-request live GitHub check.

### Impact Explanation
If this local `Team` state is indeed what gates `Shipit.github_teams` login authorization, an attacker who can deliver a `membership` webhook (trivial if the operator leaves `webhook_secret` unset for any configured organization, as the docs describe as a valid option, or if any other org's real secret leaks) can add themselves (or anyone) to any team, including ones whitelisted for admin/deploy access — an escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
Likelihood is contingent on the operator's `webhook_secret` configuration choice (documented as optional in `docs/setup.md`), which weakens confidence this is exploitable in a "secure by default" deployment; when a secret **is** configured, the payload is fully GitHub-signed, and GitHub only emits real `membership` events for real organization changes, closing the gap. The exposure is real only in the optional no-secret configuration, or if the org-level secret is otherwise compromised.

### Recommendation
- Never trust unauthenticated payload fields (`organization.login`, `team.*`, `member.login`) to mutate Shipit's authorization-relevant `Team`/membership records without independently confirming (via the GitHub API, using the app's own installation token) that the reported team/member relationship actually exists.
- Make `webhook_secret` mandatory (fail closed) rather than optional, or at minimum warn loudly / refuse to process authorization-affecting events (`membership`) when no secret is configured.
- Confirm and, if necessary, decouple the mechanism used by `Shipit.github_teams`/`Authentication` from these webhook-populated `Team` records, or re-validate team membership against GitHub at authorization-check time rather than relying solely on cached webhook-driven state.

### Proof of Concept
1. Deploy Shipit with a multi-org config where organization `victim-org`'s `webhook_secret` is left blank (a supported/documented configuration) or is otherwise obtained.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker" }
}
```
3. `verify_signature` resolves `repository_owner` → `victim-org`, finds `webhook_secret` blank, and `verify_webhook_signature` returns `true` unconditionally, so the forged request passes.
4. `MembershipHandler#process` creates `Team(github_id: 999, organization: "victim-org", slug: "admins")` and calls `team.add_member(User.find_or_create_by_login!("attacker"))`, granting the attacker membership in a team that (if it matches a configured `Shipit.github_teams` entry) unlocks restricted authorization — without the attacker ever being a real member of `victim-org/admins` on GitHub.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
