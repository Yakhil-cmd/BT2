### Title
Unchecked database write results when saving private payment chains allow silent persistence failures - ([File: indivisible_asset.js])

### Summary
`validateAndSavePrivatePaymentChain` in `indivisible_asset.js` builds a batch of `INSERT OR IGNORE`/`UPDATE` queries to persist a private payment chain and then unconditionally calls `callbacks.ifOk()` after running them, without checking whether the queries actually succeeded or affected any rows [1](#0-0) . This mirrors the reported ERC20 pattern of ignoring a call's success/failure indicator: a state-changing write ("transfer") can silently no-op, yet the caller proceeds as though it succeeded, leading to incorrect internal accounting.

### Finding Description
When a private payment chain is received (e.g. via `network.handleOnlinePrivatePayment` → `private_payment.js:validateAndSavePrivatePaymentChain` → `indivisibleAsset.validateAndSavePrivatePaymentChain`), the function inserts input/output rows using `db.getIgnore()` ("OR IGNORE" in sqlite, "IGNORE" in MySQL) [2](#0-1) . The `inputs` table enforces uniqueness via `UNIQUE KEY bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)` specifically to prevent double-spends of the same source output when `is_unique=1` (stable chains) [3](#0-2) .

Because the insert uses "OR IGNORE", a conflicting insert (e.g., two different private payment chains both claiming to spend the same already-recorded stable output) is silently dropped by the database instead of raising an error. The code that runs these queries never inspects the query results or `affectedRows`:
```
async.series(arrQueries, function(){
    profiler.stop('save');
    callbacks.ifOk();
});
``` [4](#0-3) 
`callbacks.ifOk()` is invoked regardless of whether the `inputs`/`outputs` rows were actually persisted. The `ifOk` result is what ultimately reports success back through `private_payment.js` (`COMMIT` + `callbacks.ifOk()`) [5](#0-4)  and back to the network layer, which tells the sending peer/hub the payment was "accepted" and forwards/emits it as a new confirmed private transaction [6](#0-5) .

The equivalent pattern also exists in `divisible_asset.js`'s `validateAndSaveDivisiblePrivatePayment`, which runs `async.series(arrQueries, callbacks.ifOk)` directly, again not checking results [7](#0-6) .

### Impact Explanation
A private-payment counterparty (an unprivileged actor who can construct and send private payment chains to a peer/wallet) can craft two chains that both consume the same stable private output. Because the "OR IGNORE" insert on the second, conflicting chain silently does nothing, but `ifOk()` is still invoked, the receiving wallet will:
- Record the second payment as validly "accepted" in its UI/event stream (`callbacks.ifAccepted`, `new_my_transactions` event) even though the underlying `inputs` row for that spend was never written.
- Potentially forward the (unsaved) chain onward to other cosigners/members as if it were durably recorded.

This produces incorrect internal accounting of private balances/inputs at the recipient, and can be leveraged as part of a double-spend of a private asset output, since one of the two conflicting claims is accepted as "ok" without a corresponding durable record enforcing the spend.

### Likelihood Explanation
Reachable directly from any private-payment counterparty via the standard wallet message flow (`handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → `private_payment.validateAndSavePrivatePaymentChain`) without requiring any special privilege, hub/node compromise, or timing race beyond sending two conflicting private chains for the same stable source output. The precondition (a stable `is_unique=1` insert conflict) is a normal outcome of maliciously constructed duplicate/competing private chains, which the API is designed to accept as untrusted input.

### Recommendation
Check the actual result of every write in the batch before calling `ifOk()`. For MySQL, verify `res.affectedRows` (as already done in `storage.js:insertAADefinitions` [8](#0-7) ); for sqlite, verify `changes`. If a required insert/update did not affect the expected number of rows, invoke `callbacks.ifError(...)` (or a distinct "conflict/duplicate" callback) instead of silently proceeding to `ifOk()`. Apply this fix to both `indivisible_asset.js:validateAndSavePrivatePaymentChain` and `divisible_asset.js:validateAndSaveDivisiblePrivatePayment`.

### Proof of Concept
1. Attacker (as a wallet peer) sends private payment chain A to victim wallet, spending stable output O, with `bStable=true` so `is_unique=1` is recorded in `inputs`.
2. Victim's wallet processes chain A: insert succeeds, `ifOk()` called, chain A accepted as a valid received private payment.
3. Attacker sends a second private payment chain B, also spending the same output O (double-spend), also `bStable=true`.
4. `validateAndSavePrivatePaymentChain` attempts `INSERT OR IGNORE INTO inputs (...) VALUES (...)` for chain B's input; the unique constraint `bySrcOutput` conflicts with chain A's row, so the insert is silently ignored.
5. `async.series(arrQueries, function(){ ...; callbacks.ifOk(); })` still calls `ifOk()` because no error propagates from the ignored insert [4](#0-3) .
6. Victim wallet treats chain B as accepted (`ifAccepted`, UI/event notification), while no `inputs` row exists enforcing that output O was spent by chain B — enabling accounting inconsistency / a double-spend claim being reported as valid.
