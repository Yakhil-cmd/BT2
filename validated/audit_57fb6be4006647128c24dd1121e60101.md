### Title
Unauthenticated node crash via unhandled `throw Error("no src_coin")` when validating a normal unit that spends a private fixed-denomination asset - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a code path, guarded only by `objAsset.is_private && objAsset.fixed_denominations`, that assumes `objValidationState.src_coin` was pre-populated. That field is only ever set by the private-payment-chain reconstruction code in `indivisible_asset.js`. When the very same validation function is reached through the ordinary unit-validation pipeline (`validation.validate()` → `validateMessages()` → `validatePayment()`), `objValidationState.src_coin` is never set, so a crafted, ordinary broadcast unit that references a "transfer" input on a private, fixed-denomination asset triggers an uncaught `throw Error("no src_coin")`. This throw happens synchronously inside an `async.forEachOfSeries` iteratee with no surrounding `try/catch` anywhere up the call chain, so it escapes as a Node.js `uncaughtException`, which `network.js`'s handler deliberately re-throws to crash the whole process (`process.on('uncaughtException', ...) { ...; throw err; }`).

### Finding Description [1](#0-0) 
```
// for private fixed denominations assets, we can't look up src output in the database 
// because we validate the entire chain before saving anything.
// Instead we prepopulate objValidationState with denomination and src_output 
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    ...
```
`objValidationState.src_coin` is set in exactly one place, inside the private-payment-chain validator, not in the main unit-validation entry point: [2](#0-1) 
```
arrFuncs.push(validateSourceOutput);
objValidationState.src_coin = {
    src_output: src_output,
    denomination: payload.denomination,
    amount: prev_hidden_output.amount
};
```
The main unit-validation flow (`validate()` → `validateAuthors`/`validateMessages` → `validatePayment` → `validatePaymentInputsAndOutputs`), used for every unit broadcast to the network via `handleJoint` in `network.js`, never constructs or initializes `objValidationState` with a `src_coin` property: [3](#0-2) 
```
var objValidationState = {
    arrAdditionalQueries: [],
    arrDoubleSpendInputs: [],
    arrInputKeys: []
};
```
So if an attacker crafts and posts an ordinary (non-private-chain) unit with a `payment` message that references a private, `fixed_denominations` asset, with an input of `type: "transfer"`, the code enters the `objAsset.is_private && objAsset.fixed_denominations` branch, finds `objValidationState.src_coin` undefined, and throws. That throw occurs inside `async.forEachOfSeries`'s synchronous iteratee call, which is not wrapped in try/catch by `async`, by `validatePaymentInputsAndOutputs`, by `validateMessages`, by the outer `async.series` in `validate()`, or by `handleJoint` in `network.js`. It therefore propagates as an uncaught exception on the Node.js event loop.

`network.js` explicitly turns any uncaught exception into a process crash to avoid running with inconsistent state: [4](#0-3) 
```
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    console.error('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
```
This mirrors the structure of CVE-2021-20297: a specific, syntactically-valid but semantically-unusual combination of fields (there: `match.path` on a connection profile; here: an ordinary unit referencing a private fixed-denomination asset transfer without going through the private-chain reconstruction path) hits an internal invariant assumption that isn't actually guaranteed, causing an unhandled crash of the whole daemon/process.

### Impact Explanation
Any unprivileged unit poster (or peer relaying a received joint) can trigger this by posting a single unit as long as at least one private, fixed-denomination asset has been previously defined on the DAG (asset definitions are permissionless in ocore). This constitutes a full node crash / denial of service: the target node process terminates, so it cannot validate, relay, or confirm any further units until manually restarted — matching the "network unable to confirm new units" impact bar. Because `handleJoint` is invoked for every joint received from any peer or posted by any wallet, this is trivially remotely triggerable and is not merely a peer-only or resource-exhaustion bug — it's a deterministic crash from a single crafted, otherwise well-formed unit.

### Likelihood Explanation
High. No special privileges, private keys, or timing races are required — only the ability to author a unit spending a "transfer" type input against an already-existing private, fixed-denomination asset, and to broadcast/post it. Private fixed-denomination assets are a standard first-class asset type in ocore, so the preconditions are easy to satisfy on mainnet/testnet or any private network without special access.

### Recommendation
Do not `throw` on internal invariant violations reachable from externally-supplied unit data. In `validatePaymentInputsAndOutputs`, guard the `objAsset.is_private && objAsset.fixed_denominations` "transfer" branch by explicitly checking whether the current validation context is inside the private-payment-chain reconstruction flow (e.g., an explicit `objValidationState.bPrivateChainValidation` flag) before assuming `src_coin` is populated. If reached from the normal unit-validation path, either look up the source output the normal way or return a `callback("...")` unit error instead of throwing, so malformed/unexpected input is rejected gracefully rather than crashing the process.

### Proof of Concept
1. Define (or use an existing) asset with `is_private: true` and `fixed_denominations: true` on the DAG (permissionless, standard asset-definition message).
2. Construct a new unit with a `payment` message referencing that asset, containing:
   - `payload.asset` = the private/fixed-denomination asset id,
   - `payload.denomination` set to a valid denomination of that asset,
   - a single `input` of `type: "transfer"` (the default type when `type` is omitted) pointing at some `unit/message_index/output_index`, along with a properly hidden/valid-looking `output` matching asset requirements.
3. Broadcast this unit directly to the network (e.g., via a peer connection posting the joint), i.e., without going through the wallet's private-payment-chain (`private_payment`/`private_payment_chains`) delivery path.
4. `validation.validate()` is invoked from `network.js`'s `handleJoint`, reaches `validatePaymentInputsAndOutputs`, enters the `objAsset.is_private && objAsset.fixed_denominations` branch, finds `objValidationState.src_coin` undefined, and executes `throw Error("no src_coin")`.
5. The thrown error is not caught anywhere in the synchronous call chain, surfaces as a Node `uncaughtException`, and `network.js`'s handler re-throws it, terminating the node process.
