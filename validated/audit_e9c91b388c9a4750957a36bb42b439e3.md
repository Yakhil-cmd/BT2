### Title
Webhook signature verification selects the GitHub App/secret from an unauthenticated `repository.owner.login` field that is decoupled from the `repository.full_name` field the handlers actually act on, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` config (and therefore which `webhook_secret`) to validate the `X-Hub-Signature` HMAC against by reading `repository_owner` straight out of the still-unverified JSON body. [1](#0-0) [2](#0-1)  Every downstream `Handler`, however, resolves which repository/stack to act on from a completely different, equally unauthenticated field of the same body: `repository.full_name`. [3](#0-2)  Nothing ties these two fields together, so the "organization that authenticated" and the "repository that is written" can be made to diverge, exactly the binding class called out in the prompt.

### Finding Description
`Shipit.github(organization:)` looks up a `GitHubApp` object per-organization from `secrets.github`, which is the documented and supported multi-tenant configuration (see `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne`/`OrgTwo` each with independent, optional `webhook_secret`). [4](#0-3)  `GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when that org's `webhook_secret` is blank: `return true unless webhook_secret`. [5](#0-4)  The docs treat the webhook secret as optional ("If you've set a webhook secret ... you should copy it here"). [6](#0-5) 

The controller determines *which* org's secret to check against using `repository_owner`, pulled from the attacker-controlled JSON body before any signature check has passed:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once `verify_signature` passes (trivially, for an org with a blank/known secret), `WebhooksController#create` dispatches the *entire same payload* to the registered handlers for the event. [7](#0-6)  Every handler resolves the target repository independently via `payload.dig('repository', 'full_name')`, e.g. `PushHandler`, `StatusHandler`, `LabelCapturingHandler`, `ReopenedHandler`. [3](#0-2) [8](#0-7) 

There is no code anywhere that checks `repository.full_name.split('/').first == repository.owner.login`. An attacker who knows (or can leave blank) the `webhook_secret` for *any one* configured organization on a multi-org Shipit instance can set `repository.owner.login` to that org (satisfying `verify_signature`) while setting `repository.full_name` to `otherorg/other-repo` for a completely different, strictly-secured organization tracked by the same instance. The signature check authenticates one identity; the handlers act on a different, unauthenticated one — the same "organization that authenticated versus the repository that is written" binding break called out in the rules.

### Impact Explanation
With this divergence an unauthenticated remote attacker can forge:
- `push` events that trigger `stack.sync_github(expected_head_sha:)` for any tracked stack, regardless of which org it belongs to. [9](#0-8) 
- `status` events that create fabricated `CommitStatus` records via `commit.create_status_from_github!(params)` for any commit sha, which feeds into deployability/CI gating used to decide whether a deploy can proceed. [10](#0-9) 
- `pull_request` events that archive/unarchive stacks or mutate labels for arbitrary review stacks tied to any tracked repository. [11](#0-10) 

This is a cross-organization authentication bypass: the attacker never needs the target organization's actual `webhook_secret`, only a usable identity for a *different, weaker or secret-less* org configured on the same Shipit instance. Forging commit statuses that gate deployability can enable an unauthorized deploy to proceed, matching the Critical bucket ("unauthorized deploy") and, at minimum, the High bucket ("unauthenticated read/write of stack state").

### Likelihood Explanation
This requires the deployment to run Shipit's documented multi-org configuration mode (`secrets.github` keyed by organization) with at least one organization having a blank or otherwise attacker-obtainable `webhook_secret` — a configuration explicitly supported and documented (`webhook_secret: # nil` shown as valid in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`). Given that precondition, exploitation requires only a single unauthenticated HTTP POST to `/webhooks` with a crafted `repository.owner.login`/`repository.full_name` mismatch — no session, token, or GitHub credentials needed.

### Recommendation
After determining the repository/stack to act on, verify that the owner encoded in `repository.full_name` (or `organization.login`) matches the `repository_owner` value whose secret was used to validate the signature, before invoking any handler — i.e., bind the authenticated organization to the acted-upon repository the same way `require(_initiator == address(this))` binds the flash-loan initiator to the expected contract in the referenced report. Alternatively, resolve the target `Repository`/`Stack` first, derive its canonical owning organization from that record, and verify the signature using that organization's secret rather than trusting the raw payload field.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (no `webhook_secret` set) and `OrgB` (strict `webhook_secret`), each tracking repositories — this is the exact shape of `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/private-repo" },
  "organization": { "login": "OrgA" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` needs to be valid because `GitHubApp#verify_webhook_signature` returns `true` unconditionally for `OrgA` (blank secret). [5](#0-4) 
3. `WebhooksController#verify_signature` passes (validated against `OrgA`), then `Shipit::Webhooks.for_event('push')` runs `PushHandler`, which resolves the stack via `repository.full_name = "OrgB/private-repo"` and calls `stack.sync_github(...)` [9](#0-8)  — an action on `OrgB`'s stack triggered without ever presenting `OrgB`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
