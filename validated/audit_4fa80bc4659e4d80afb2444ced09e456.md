### Title
First-liquidity-provider donation/inflation attack in `pallet-asset-conversion::do_add_liquidity` mints LP shares from the deposited amount instead of the true post-deposit pool balance - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion::do_add_liquidity` decides how many LP tokens to mint on the *first* deposit purely from `total_issuance(lp_token) == 0`, and then computes the minted amount from the just-transferred `amount1`/`amount2` only, ignoring any asset balance the pool account may already hold. Because the pool account address is deterministic and permissionlessly fundable before any `add_liquidity` call, an attacker can pre-fund ("donate to") the pool account, then become the "first" LP with a tiny deposit and capture LP shares that are redeemable against the entire (donated) reserve — the same root-cause pattern as the referenced wxETH finding: value ("drip") accrues while the accounted supply is 0, and whoever becomes the first depositor after that point can claim it disproportionately.

### Finding Description
`Pools::<T>::insert` + `do_create_pool` create a pool and its deterministic `pool_account` (`T::PoolLocator::address`), and pre-`touch` both asset accounts so they can hold balances immediately: [1](#0-0) 

Any account can permissionlessly transfer `asset1`/`asset2` directly to this `pool_account` (e.g. via `pallet-balances::transfer` or `pallet-assets::transfer`) without ever calling `add_liquidity`. This raises the pool's `reserve1`/`reserve2` balances while the LP token (`pool.lp_token`) total issuance remains exactly `0`.

When `do_add_liquidity` is later called (by the attacker themselves, or by anyone), the reserves are read *before* the transfer: [2](#0-1) 

Crucially, the LP-token minting branch checks only `total_supply.is_zero()`, and — in that branch — computes the minted amount from `amount1`/`amount2`, the *incrementally transferred* amounts, not from the pool account's actual post-transfer balance (`reserve + amount`): [3](#0-2) 

```rust
let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
let lp_token_amount: T::Balance;
if total_supply.is_zero() {
    lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
    T::PoolAssets::mint_into(pool.lp_token.clone(), &pool_account, T::MintMinLiquidity::get())?;
} else { ... }
```
and: [4](#0-3) 

`calc_lp_amount_for_zero_supply` is `sqrt(amount1 * amount2) - MintMinLiquidity`, using only the newly deposited amounts — it never adds the pre-existing `reserve1`/`reserve2` that the pool account may already be holding due to a prior direct transfer. `MintMinLiquidity` is a small, fixed constant (not scaled to the reserve size), so it does not protect against large donations.

The effect: the LP token supply, once minted, no longer reflects the real value backing the pool. `do_remove_liquidity` computes withdrawals strictly as `lp_redeem_amount * reserve / total_supply`: [5](#0-4) 
so an attacker holding almost all of an artificially tiny `total_supply` can redeem almost the entire real reserve (their tiny deposit + the donated amount, or later, any subsequent legitimate LP's diluted deposit).

This is the same bug class as the wxETH finding: value can accumulate in the "vault" (pool account) while the tracked "supply" (`total_issuance`) is still 0, and the code's zero-supply branch fails to reconcile that pre-existing balance when computing the first depositor's shares.

### Impact Explanation
An attacker can:
1. Permissionlessly create or use an existing pool for an arbitrary asset pair, obtain the deterministic `pool_account`.
2. Transfer a large amount of `asset1`/`asset2` directly into `pool_account` (raising reserves, not `total_issuance`).
3. Call `add_liquidity` with a minimal deposit chosen to satisfy the reserve-ratio `quote()` check; `total_issuance` is still `0`, so `lp_token_amount` is computed only from the tiny deposit.
4. Receive LP tokens representing (after the fixed `MintMinLiquidity` lock) essentially 100% of `total_issuance`, entitling redemption of the *entire* reserve (donated + deposited).
5. Any subsequent genuine LP joining this diluted pool receives a share of the artificially low `total_issuance` disproportionate to their real contribution (`side1/side2 = amount * total_supply / reserve`), letting the attacker's existing LP position capture part of the new depositor's funds on `remove_liquidity`.

This is a fund-theft/value-misattribution vector on a permissionless, fee-generating DeFi primitive shipped in-tree (`pallet-asset-conversion`, used by Asset Hub for swaps), not merely an economic/front-running nuisance — the attacker directly extracts assets belonging to reserves they did not legitimately deposit as LP.

### Likelihood Explanation
Requires no privileged role: pool creation, asset transfers, and `add_liquidity`/`remove_liquidity` are all ordinary, permissionless extrinsics available to any signed account with funds. The attacker only needs to know/compute the deterministic `pool_account` address (via `PoolLocator::pool_id`/`address`, public logic) ahead of providing the first liquidity — realistic for any newly created pool, and exploitable opportunistically against any pool that currently has `total_issuance(lp_token) == 0` but has already received a stray/donated balance (e.g., an accidental transfer, or an attacker-created scenario).

### Recommendation
When `total_supply.is_zero()`, compute the initial LP mint from the pool account's actual *total* balances after the transfer (`reserve1 + amount1`, `reserve2 + amount2`), not merely the incremental `amount1`/`amount2`, mirroring Uniswap V2's approach of using `balanceOf(pair)` rather than the caller-supplied amount. Alternatively/additionally, reject `add_liquidity` on a zero-supply pool whose `pool_account` already holds a non-trivial pre-existing balance, or sweep/burn any pre-existing balance into the `MintMinLiquidity` calculation so it cannot be captured disproportionately by the next depositor.

### Proof of Concept
Not executed against a live network; based on static trace through `substrate/frame/asset-conversion/src/lib.rs`:
- `do_create_pool` (lines 729-788) creates `pool_account`, touches it for both assets — reachable, permissionless.
- Direct `Balances::transfer`/`Assets::transfer` of an attacker-chosen amount to `pool_account` — ordinary transfer extrinsic, no guard in `pallet-asset-conversion` prevents this since it doesn't own/lock the account.
- `do_add_liquidity` (lines 791-892): reserves read at lines 813-814 will reflect the donation; the `total_supply.is_zero()` branch (lines 858-867) mints LP tokens from `calc_lp_amount_for_zero_supply(&amount1, &amount2)` (lines 1353-1368), ignoring `reserve1`/`reserve2`.
- `do_remove_liquidity` (lines 894-966) redeems proportionally to `total_supply`, allowing the attacker to withdraw the donated reserve.

I was not able to run this scenario in the pallet's test harness (`substrate/frame/asset-conversion/src/tests.rs`) within this session; existing tests I reviewed (`can_add_liquidity`, `add_and_remove_liquidity_works`) only cover the "clean pool, no pre-existing balance" path and do not test a pre-donated `pool_account`, which is consistent with this gap being unmitigated. A background engineering session with repo access would be needed to write and execute an integration test that: (a) creates a pool, (b) directly transfers assets into `pool_account`, (c) calls `add_liquidity` with a minimal amount, and (d) asserts the minted `lp_token_amount` versus the actual reserve captured on a subsequent `remove_liquidity`, to empirically confirm the share/reserve mismatch and quantify extractable value.

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
