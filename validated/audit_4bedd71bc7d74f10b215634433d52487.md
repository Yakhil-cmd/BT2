### Title
Webhook signature verified against the `repository.owner.login` organization while handlers act on the independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports configuring a distinct GitHub App (and thus a distinct `webhook_secret`) per GitHub organization. When a webhook is delivered, `WebhooksController#verify_signature` picks which app/secret to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Once the signature check passes, `create` hands the *entire raw payload* to `Shipit::Webhooks.for_event(event)` handlers. Those handlers (via `Shipit::Webhooks::Handlers::Handler#repository_name`) determine which repository/stack to mutate using a **different** field: `payload.dig('repository', 'full_name')`. The organization whose secret authenticated the request is never checked against the repository that is actually written to.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and looks up the corresponding GitHub App config to verify `X-Hub-Signature`: [1](#0-0) 

`repository_owner` is derived purely from attacker-controlled JSON fields: [2](#0-1) 

If verification succeeds, `create` dispatches the raw, parsed payload unmodified to every handler for the event: [3](#0-2) 

Handlers (e.g. `PushHandler`) resolve the target repository/stack from a *separate* payload field, `repository.full_name`, via `Handler#stacks`/`#repository_name`, with no re-validation that this repository belongs to the organization that produced a valid signature: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` performs a simple `owner/name` lookup with no ownership binding to the signing organization: [6](#0-5) 

The `docs/setup.md`/`config/secrets.development.example.yml` config schema explicitly documents multi-organization GitHub App configuration, each with its own `webhook_secret`, confirming that per-organization keys are a supported, real deployment shape: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (params.dig('repository','owner','login'))` **≠** `repository actually written by the handler (payload.dig('repository','full_name'))`.

Before the attacker acts: for a legitimate webhook, `repository.owner.login` and `repository.full_name`'s owner segment always refer to the same GitHub repository, because GitHub itself populates both fields consistently for a single delivered event.

After the attacker acts: an attacker who legitimately controls one onboarded organization (Org A, with a Shipit-configured GitHub App and its own `webhook_secret`) can trigger (or directly craft, since only the raw body + a matching HMAC are required, and the attacker knows Org A's real secret because they administer that GitHub App) a webhook whose top-level `repository.owner.login` is `"org-a"` (so `verify_signature` validates it with Org A's real secret) but whose `repository.full_name` is `"org-b/some-repo"` — any other repository/stack already onboarded onto the same Shipit instance. The signature check passes using Org A's legitimate secret, yet the `PushHandler` (or other handlers keyed off `full_name`) will act on Org B's stack, e.g. invoking `stack.sync_github(expected_head_sha: params.after)` for a stack the attacker does not own or control.

### Impact Explanation
This crosses a cross-repository trust boundary: an attacker with legitimate access to only one onboarded GitHub organization's webhook secret can inject events (push/status/check_suite/pull_request/membership, per `Hook::EVENTS`-equivalent webhook event set) that are processed as if they came from a different organization/repository they do not control. Depending on the specific handler this can force syncing of a foreign stack to an attacker-chosen commit SHA (`GithubSyncJob` with attacker-controlled `expected_head_sha`), forge commit statuses on another team's commits, or fabricate `pull_request`/`check_suite`/`membership` events for repositories/organizations the attacker has no authorization over. This is a cross-repository write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the mutation, satisfying the "cross-repository writes" high/critical impact criteria.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub App/organization (a documented, supported configuration) and the attacker to control one such onboarded organization (e.g., being an admin of one of several client orgs sharing the same Shipit deployment) — this is a much weaker precondition than needing the target organization's own webhook secret, an API token, or repository write access on the target repository. No TLS interception, GitHub App private key, or GITHUB_TOKEN access is needed. Likelihood is elevated in any multi-tenant Shipit deployment (the primary use case the multi-org config schema exists for).

### Recommendation
After successfully verifying the signature for `repository_owner`, re-derive and enforce that every field the handlers use to select the target repository/stack (`repository.full_name`, and any `organization.login` used inside handler logic) is consistent with the organization that produced a valid signature — e.g., pass the authenticated organization into `Shipit::Webhooks.for_event(event)`/handler `initialize`, and have `Handler#repository_name` reject/ignore payloads whose repository owner does not match the authenticated organization, rather than trusting the raw payload's `full_name` unconditionally.

### Proof of Concept
1. Configure a Shipit instance (per `docs/setup.md`) with two organizations, `org-a` and `org-b`, each with a distinct GitHub App and distinct `webhook_secret` (`secret_a`, `secret_b`), both with stacks onboarded.
2. As an attacker who administers the GitHub App for `org-a` (and thus legitimately knows `secret_a`), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(secret_a, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "org-a"`, loads Org A's app, and validates the signature successfully using `secret_a`.
5. `PushHandler#process` is invoked with the full payload; `Handler#repository_name` reads `payload.dig('repository','full_name') == "org-b/target-repo"`, resolves Org B's stack via `Repository.from_github_repo_name`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker does not own — demonstrating a cross-organization/cross-repository write authenticated with a key the attacker was only entitled to use for `org-a`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
