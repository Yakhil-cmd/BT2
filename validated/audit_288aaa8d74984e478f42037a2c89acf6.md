This is exactly the "confused deputy" analog for the `TwapOracle` permissioning bug: the field used to select the trust boundary (which webhook secret authenticates the request) is disjoint from the field used to determine what gets written.

### Title
Webhook signature verification selects the GitHub App/secret from an unauthenticated `repository.owner.login`/`organization.login` field, while all event handlers act on the independently attacker-controlled `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to validate the HMAC signature against using a value read out of the *same unauthenticated request body* it is trying to authenticate: `repository_owner`. `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, used by every event handler, instead resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`. These two fields are never cross-checked, so the organization whose secret was used to authenticate the webhook does not have to match the repository that the payload actually mutates.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [2](#0-1) 

Multi-org configuration is a documented, supported feature (`docs/setup.md`, "Using Multiple Github Applications"), and every example secrets file ships `webhook_secret: # nil` as the default for each org. [3](#0-2) 

Meanwhile, every webhook handler resolves the actual target purely from the payload's `repository.full_name`, independent of `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, and `CheckSuiteHandler` all key off this same `full_name`/`repository.full_name`, never off `repository_owner`. For example the push handler:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

and `StatusHandler` writes a `commit_status` for any commit matching the SHA regardless of which org's key verified the request:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

`MembershipHandler` similarly trusts `params.organization.login` only to name the `Team.organization`, never to gate which org's secret was used to authenticate the event, so it can create/modify `Team`/`Membership` records for teams belonging to a different org than the one whose secret verified the signature:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [7](#0-6) 

### Equality broken
Expected binding: `organization whose secret authenticated the request == organization that owns the repository/team the handler writes to`.
Actual binding enforced by the code: `organization used to pick the verification key == payload["repository"]["owner"]["login"] (attacker-controlled)`, while `repository/team actually written == payload["repository"]["full_name"] / payload["organization"]["login"]` (also attacker-controlled, independently). Nothing forces these two attacker-controlled fields to agree.

### Impact Explanation
In any Shipit installation using the documented multi-org GitHub App configuration where at least one configured organization has no `webhook_secret` set (the shipped default in every example secrets file), an unauthenticated, unprivileged attacker can:
- Set `repository.owner.login`/`organization.login` to the unsecured org so `verify_signature` auto-passes (`return true unless webhook_secret`).
- Set `repository.full_name` (push/status/pull_request/check_suite handlers) or `organization.login`/`team` (membership handler) to point at a *different*, secured organization's tracked stack/team.

This lets the attacker forge `push`, `status`, `check_suite`, `pull_request`, and `membership` events against repositories/teams they have no relationship to, causing: forced `GithubSyncJob` re-syncs and continuous-delivery triggers on arbitrary stacks (`stack.sync_github`), injection of forged commit statuses (`Commit#create_status_from_github!`) that can make Shipit believe untested commits are CI-green and deployable, and creation/mutation of `Team`/`Membership` rows tied to `Shipit.github_teams`-based authorization. This crosses the "organization authenticated vs. repository written" boundary called out in scope and can escalate into unauthorized deploys and `Shipit.github_teams` authorization tampering.

### Likelihood Explanation
Requires only that an operator use the (documented, default) multi-org config with at least one org left with `webhook_secret` unset — a configuration shown as the shipped default in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`, and not flagged as insecure anywhere in `docs/setup.md`. No secret, session, or privileged credential is needed by the attacker for the org they impersonate as "owner" in this scenario.

### Recommendation
Verify the webhook signature using the same repository/organization identity that will actually be acted upon (`repository.full_name`'s owner), not a separately-read field, and refuse to process handlers whose `repository.full_name`/`organization.login` don't match the organization whose key verified the signature. Consider also requiring `webhook_secret` to be present for every configured organization rather than allowing silent unauthenticated bypass.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgOpen` (no `webhook_secret`) and `OrgSecure` (a tracked, secured repo `OrgSecure/prod-app` with an active stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgSecure/prod-app" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgOpen")`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` and the request is accepted.
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgSecure/prod-app")` and enqueues `GithubSyncJob` for that stack — a write to `OrgSecure`'s stack authorized only by `OrgOpen`'s (nonexistent) trust.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
