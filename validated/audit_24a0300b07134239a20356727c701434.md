## Title
Unauthenticated `membership` webhook forgery escalates an attacker into `Shipit.github_teams` authorization when an organization has no `webhook_secret` configured - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever an organization's `webhook_secret` is blank, a configuration explicitly shown as valid in the engine's own sample configs. For such an organization, `WebhooksController#verify_signature` accepts any unsigned, unauthenticated payload. `MembershipHandler` then looks up and mutates a `Team` purely by the attacker-supplied `team.id` field, letting an unauthenticated actor add an arbitrary GitHub login to a team that is part of `Shipit.github_teams`, thereby gaining authorization into the application.

### Finding Description
The webhook signature check is meant to bind "the organization that authenticated the request" to "the record that gets written." That binding breaks:

`WebhooksController#verify_signature` picks the GitHub App/secret to check against based only on `repository_owner` (falls back to `organization.login` when no `repository` key is present, which is the case for `membership` events), then calls `verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` skips validation entirely if no secret is configured for that organization: [3](#0-2) 

Leaving `webhook_secret` blank is a supported, documented configuration surfaced directly in the engine's own sample configs: [4](#0-3) [5](#0-4) 

For a `membership` event on such an organization, no HMAC is required at all, so an unauthenticated actor can POST an arbitrary JSON body directly to the webhooks endpoint. `MembershipHandler` then resolves and writes the `Team` record solely from attacker-controlled fields, with no verification that the referenced `team.id` actually belongs to the "authenticated" organization: [6](#0-5) 

Team membership is exactly what backs Shipit's authorization decision: [7](#0-6) 

### Impact Explanation
An attacker who knows (a) that a configured GitHub organization on the target Shipit instance has no `webhook_secret`, and (b) the numeric GitHub `team.id` of one of the teams listed in `Shipit.github_teams`, can forge a `membership` "added" webhook naming that `team.id` and an arbitrary `member.login` (their own GitHub account). `find_or_create_team!` finds the existing privileged `Team` by `github_id` and `team.add_member(member)` adds the attacker's account to it. When the attacker subsequently authenticates through the normal GitHub OAuth login flow (`GithubAuthenticationController#callback`), `User#authorized?` will now return `true`, granting them full authenticated access to the Shipit UI/actions (deploys, rollbacks, task triggering) — an escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
Requires a specific but realistic configuration state (at least one configured org without `webhook_secret`, which the engine's own docs/sample configs present as normal) plus knowledge of a target team's GitHub numeric ID (discoverable via GitHub's public team/organization APIs in many cases). No credentials, session, `ApiClient` token, or knowledge of any secret is needed — the request can be sent directly and unauthenticated. Likelihood is low-to-moderate depending on deployment configuration, similar in spirit to the referenced report's "requires no LP stake" edge-case framing.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization, or refuse to process events for organizations without one (fail closed instead of `return true unless webhook_secret`).
- In `MembershipHandler#find_or_create_team!`, verify that the resolved team's `organization` matches the `organization.login` that was cryptographically authenticated for the request, rejecting membership events where the two diverge, in the same way that `lpFeesTotal` needed to be reset to 0 in all code paths rather than only the "happy path."

### Proof of Concept
1. Configure (or find) a Shipit deployment with an organization entry that has `webhook_secret` unset (as shown in `config/secrets.development.shopify.yml`).
2. Send an unauthenticated `POST` to the engine's webhooks endpoint with header `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "team": { "id": <github_id_of_privileged_team>, "name": "x", "slug": "x", "url": "x" },
  "organization": { "login": "<org-with-blank-webhook_secret>" },
  "member": { "login": "<attacker-github-login>" }
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` short-circuits to `true` for this organization.
3. `MembershipHandler` finds the existing `Team` row by `github_id` and adds `<attacker-github-login>` as a member.
4. The attacker logs into Shipit via GitHub OAuth; `User#authorized?` now returns `true` because the attacker's `User` belongs to a team in `Shipit.github_teams`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
