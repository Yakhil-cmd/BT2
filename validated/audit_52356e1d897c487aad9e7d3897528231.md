### Title
Address-Keyed Validation Mutex Can Be Locked by Any Unauthenticated "Author" Address, Delaying Other Users' Payments - (File: validation.js)

### Summary
`validation.validate()` acquires a global mutex keyed by the unit's declared author addresses *before* verifying that the sender actually controls those addresses (signature/authentifier checks happen much later in the pipeline). Any user who can post a unit to the network can therefore force the mutex for an arbitrary victim address to be held for the full duration of an expensive multi-step async validation, queuing out legitimate validation/spend attempts from that same address — the same "any user can lock a resource belonging to someone else, causing service disruption" bug class as CVE-2021-22906 (Nextcloud E2EE file-locking DoS), but reachable here from a single posted unit rather than an authenticated file API call.

### Finding Description
`validate()` computes `arrAuthorAddresses` directly from the untrusted `objJoint.unit.authors` list, checks only that each is a syntactically valid address, and immediately takes the mutex on those addresses: [1](#0-0) 

```
var arrAuthorAddresses = objUnit.authors ? objUnit.authors.map(...) : [];
...
if (!arrAuthorAddresses.every(isValidAddress))
    return callbacks.ifUnitError("invalid author address");

mutex.lock(arrAuthorAddresses, function(unlock){
```

The lock is held across the entire `async.series` validation pipeline — duplicate check, hash-tree/parent/skiplist validation, witness validation, AA-trigger validation, TPS-fee validation, and only *then* `validateAuthors`, which is where authentifier/signature correctness against the address definition is actually checked: [2](#0-1) 

`mutex.lock()`/`mutex.js` implements simple FIFO exclusion by key: any other job (including validation of a *different, legitimate* unit spending from the same address) that shares a locked key is queued and cannot proceed until the current holder calls `unlock()`: [3](#0-2) [4](#0-3) 

Because ownership of the author address is never verified prior to acquiring the lock, an attacker can craft a syntactically valid unit that names a victim's address as an author (with a garbage/placeholder authentifier) and submit it repeatedly via `network.handleJoint` / `handleOnlineJoint`. Each submission causes the shared `handleJoint`/address-keyed lock queue to serialize behind a full DB-backed validation run before ultimately failing at `validateAuthors`, while the victim's genuine transactions from that same address (or any other unit naming the same author) sit queued behind the attacker's jobs.

### Impact Explanation
This lets an unprivileged network participant selectively delay confirmation of a targeted user's or AA's transactions without needing any key material or authorization over the victim's address — mirroring the CVE's "any user can lock another user's resource" pattern, but instead of a file lock it is the address-level validation mutex. Practical impact is delayed/blocked processing of legitimate payments (and by extension any AA that relies on timely trigger processing) from the targeted address, i.e., a targeted denial-of-service on that unit poster's ability to get new units accepted and confirmed in a timely manner, which is one of the accepted analog impacts (a node/network unable to promptly validate/confirm new units from the affected party).

### Likelihood Explanation
Likelihood is moderate-to-high: crafting a syntactically valid joint naming an arbitrary address as an author requires no special privilege — only a valid-looking address string and a plausible unit structure; the attacker does not need the private key since the lock is acquired before authentifier verification. The attack can be repeated cheaply and directed at any known address (e.g., an exchange hot wallet or a popular AA), and the existing `mutex.checkForDeadlocks()`/logging code even acknowledges long lock hold times are already a known operational risk area.

### Recommendation
Move ownership/authentifier verification (or at least a cheap pre-check that the address's expected definition/signature is plausible) ahead of, or make it a precondition for, acquiring the address-keyed mutex in `validate()`, so that invalid/unauthorized "author" claims are rejected before serializing access to that address's validation queue. Alternatively, bound the time a single unverified unit can hold the per-address lock (e.g., cheap fast-fail signature format checks prior to `mutex.lock`), and rate-limit/deprioritize repeated failed-signature submissions naming the same author address from the same peer.

### Proof of Concept
1. Attacker constructs `objUnit` with `authors: [{ address: <victim_address>, authentifiers: { r: "<64 x '-'>" } }]` and otherwise well-formed messages/parents so it passes the early structural checks in `validate()`.
2. Attacker submits this unit repeatedly to a node via the P2P `handleJoint` path (`network.js`, `handleJoint`), each triggering `validation.validate()`.
3. Each call executes `mutex.lock(arrAuthorAddresses, …)` at `validation.js:357` before signature verification, holding the lock on `victim_address` through the full DB-driven validation pipeline.
4. Meanwhile, the victim broadcasts a legitimate payment from `victim_address`; its `validate()` call, sharing the same mutex key, is queued behind the attacker's jobs per `mutex.js`'s `isAnyOfKeysLocked`/`arrQueuedJobs` logic, delaying its validation and confirmation. [1](#0-0) [5](#0-4)

}

	});
}

function handleQueue(){
	console.log("handleQueue "+arrQueuedJobs.length+" items");
	for (var i=0; i<arrQueuedJobs.length; i++){
		var job = arrQueuedJobs[i];
		if (isAnyOfKeysLocked(job.arrKeys))
			continue;
		arrQueuedJobs.splice(i, 1); // do it before exec as exec can trigger another job added, another lock unlocked, another handleQueue called
		console.log("starting job held by keys", job.arrKeys);
		exec(job.arrKeys, job.proc, job.next_proc);
		i--; // we've just removed one item
	}
	console.log("handleQueue done "+arrQueuedJobs.length+" items");
}

function lock(arrKeys, proc, next_proc){
