### Title
Data-feed key ambiguity via unescaped delimiter in `feed_name` allows forged oracle values to satisfy unrelated "in data feed" conditions - (File: `data_feeds.js`, `string_utils.js`)

### Summary
Data-feed keys are built by naively concatenating `address`, `feed_name`, value-type, value and MCI with the raw `\n` byte as separator, with no restriction preventing `feed_name` from containing `\n` itself. Because address-definition and AA lookups (`["in data feed", ...]`, `data_feed[[...]]`) reconstruct the same delimited string to compute lookup ranges, a poster who controls the `feed_name` field of a `data_feed` message can embed extra `\n`-separated segments inside it, shifting how the fields are subsequently parsed - the same class of bug as the Laravel path-confusion advisory (CWE-116: ambiguous encoding of a delimited resource identifier).

### Finding Description
`dataFeedByAddressExists`/`readDataFeedByAddress` build KV-store keys by string concatenation: [1](#0-0) 
and [2](#0-1) 

The key/prefix format is `df\n<address>\n<feed_name>\n<type>\n<value>\n<reversed_mci>` and range boundaries (`gte`/`lt`) are computed assuming `feed_name` contains no embedded `\n`: [3](#0-2) 

Neither `definition.js`'s validation of the `"in data feed"` / `"in merkle"` operators nor `aa_validation.js`'s validation of AA `data_feed` messages restrict the character set of `feed_name` beyond non-emptiness and length: [4](#0-3) 

This is in stark contrast to `object_hash.js`'s `getSourceString`, which explicitly forbids the `STRING_JOIN_CHAR` (`\x00`) inside any string or key specifically to prevent this class of ambiguous-parsing/injection bug: [5](#0-4) 

Because the data-feed poster fully controls the `feed_name` string of the `data_feed` message they post (any address can post a `data_feed` message; it only needs to match the `oracle` address referenced by a victim's address definition or AA), an attacker acting as (or colluding with) the referenced oracle address can choose a `feed_name` that itself contains embedded `\n` + fabricated type/value segments. When the writer persists the message it will build the KV key by simply joining `feed_name` (containing the attacker's extra `\n`-delimited content) with the real value/mci using the same `\n` delimiter, producing a key whose byte layout can coincide with — or fall inside the lexicographic range used by — a lookup for a *different*, legitimate `feed_name`/`value` pair that a victim's spending condition or AA logic actually queries for.

### Impact Explanation
If a shared/multisig address's spending condition uses `["in data feed", [[oracle_address], "price", ">", 100]]` or an AA reads `data_feed[[oracle=..., feed_name='price']]`, the range-scan logic in `dataFeedByAddressExists`/`readDataFeedByAddress` trusts that everything between the `feed_name` prefix and the MCI suffix in the stored key is exactly the type+value the poster intended for that literal name. A crafted `feed_name` containing embedded delimiters can make an oracle-controlled post be interpreted by these range queries as satisfying (or falsifying) a differently-named/valued condition than the one actually authored, since key comparison is purely lexicographic over the concatenated byte string. This can let an unauthorized party unlock a spending condition guarded by an "in data feed" oracle check, or cause an AA to read a forged/mismatched value — leading to unauthorized spending from a shared address or AA fund loss/miscalculation.

### Likelihood Explanation
Any address can post a `data_feed` message with an attacker-chosen `feed_name` string; the only requirements are that it match the oracle address referenced in the victim's definition/AA and pass the generic length/type checks in `definition.js`/`aa_validation.js`, neither of which filters `\n`. No special privilege, hub cooperation, or race condition is required — this is fully reachable from a single posted unit by an ordinary user acting as the oracle for a spending condition or AA the attacker also controls/targets.

### Recommendation
- Reject `feed_name` (and string `value`) containing the `\n` (and other reserved) byte(s) used as the KV-key delimiter, in both `definition.js` (`"in data feed"`/`"in merkle"` validation) and `aa_validation.js`/`validation.js` (`data_feed` message payload validation).
- Alternatively, switch `data_feeds.js`/`string_utils.js` key construction to a length-prefixed or otherwise unambiguous encoding (mirroring the `STRING_JOIN_CHAR` guard already used in `object_hash.js`/`string_utils.js`'s `getSourceString`) so no combination of attacker-controlled field content can be parsed as a different logical field.

### Proof of Concept
1. Attacker controls address `ORACLE_ADDR`, which is referenced by a victim shared address definition: `["in data feed", [["ORACLE_ADDR"], "price", ">", 100]]`.
2. Attacker posts a `data_feed` message from `ORACLE_ADDR` with payload key `feed_name = "price\nn\n<encoded_101>"` (embedding a fabricated type+value segment matching what a `>` 100 query would look for) and an arbitrary real value.
3. The writer stores the KV key `df\nORACLE_ADDR\nprice\nn\n<encoded_101>\n<type>\n<value>\n<reversed_mci>` (see `data_feeds.js:290-309`), i.e., the literal bytes for `feed_name="price"`, `value>100` are now a strict prefix of the stored key.
4. When the victim's definition is evaluated, `dataFeedByAddressExists`'s range scan for `feed_name="price"`, `relation=">"`, `value=100` (`data_feeds.js:148-155`) performs a lexicographic range check (`gt key_prefix+'\nffffffff'`, `lt 'df\n'+address+'\n'+feed_name+'\n'+type+'\r'`) that can match this attacker-constructed key even though the attacker never posted a genuine `price` feed satisfying that condition, because the range boundaries assume `feed_name` has no embedded `\n`.

Note: Full exploitation requires precisely crafting the byte layout so the forged key falls inside the computed `gte/lt` bounds; I was not able to execute the KV store to confirm the exact byte ranges satisfy the comparison in this environment, so this should be validated with a runnable reproduction (e.g., a Devin session) before being treated as fully confirmed.

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
