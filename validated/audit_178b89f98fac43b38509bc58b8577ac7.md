### Title
Webhook Signature Bypass Enables Cross-Repository Commit Status Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController` selects which GitHub organization's secret to verify a webhook against, and `Webhooks::Handlers::StatusHandler` then writes a commit status keyed only by SHA with no repository scoping. When the organization resolved for signature verification has no `webhook_secret` configured, verification is unconditionally skipped, letting an unauthenticated attacker inject a `status` event that mutates CI state for a commit belonging to *any* stack/repository tracked by the Shipit instance — not just the (unauthenticated) organization the request claims to be from.

### Finding Description
`WebhooksController#verify_signature` picks a `github_app` based on `repository_owner`, derived from the unverified request body, then asks it to verify the signature: [1](#0-0) 

The verification itself, in `GithubApp#verify_webhook_signature`, unconditionally returns `true` when that organization has no `webhook_secret` configured: [2](#0-1) 

This is a documented, non-exotic configuration: the sample secrets files ship with `webhook_secret: # nil`: [3](#0-2) 

Once past `verify_signature`, the raw payload is dispatched to event handlers with no further per-repository authorization check: [4](#0-3) 

`StatusHandler#process` looks up commits **globally by SHA only**, with no scoping to the repository/organization that was (or wasn't) authenticated: [5](#0-4) 

This differs from `Handler#stacks`/`#repository_name`, which do scope lookups to `payload.dig('repository', 'full_name')` in handlers like `PushHandler`: [6](#0-5) [7](#0-6) 

`StatusHandler` never uses this repository scoping — it queries `Commit.where(sha: params.sha)` across the entire database. The binding broken is: *the organization that authenticated the request* (or, when `webhook_secret` is blank, no organization at all) *≠ the repository/commit whose CI state is actually written*. An attacker who can trigger an unauthenticated (secret-less) webhook path can forge a `status` payload naming a `sha` belonging to a completely different, properly secured stack, and the handler will happily create a `Status` record for it via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses feed directly into merge-gating logic used to authorize automatic merges: `MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?` build a `StatusChecker` from `head.statuses_and_check_runs`: [8](#0-7) 

By forging a passing status for a target commit whose SHA is known (commit SHAs are content-addressed and often public), an unauthenticated attacker can make `reject_unless_mergeable!` pass, contributing to an unauthorized merge of a pull request in a repository the attacker has no access to — this satisfies the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) at least one GitHub organization configured in the Shipit instance without a `webhook_secret` (a supported, documented configuration, not a misuse of the engine), and (2) knowledge of a target commit SHA in a different, properly-secured stack. Both are realistic in multi-tenant Shipit deployments where some organizations onboard without configuring webhook secrets.

### Recommendation
- Scope `StatusHandler` (and any handler that resolves records independent of `stacks`) to the repository identified by the verified organization, mirroring `Handler#stacks`.
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; either require a secret for all configured organizations or reject webhooks for organizations without one.
- Bind the verified organization identity to every downstream lookup so a payload field never drives state changes outside the boundary that was actually authenticated.

### Proof of Concept
1. Configure (or find) an organization `org-unsecured` in `Shipit.github` with `webhook_secret: nil`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-unsecured" }, "full_name": "org-unsecured/whatever" }
}
```
3. `verify_signature` resolves `github_app` for `org-unsecured`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and creates a `success` status on the victim commit, independent of `org-unsecured`/`victim-org` having any relationship.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
