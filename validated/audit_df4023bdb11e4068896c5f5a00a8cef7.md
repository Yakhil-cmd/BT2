### Title
Pre-Publish Gate Bypass: Symlink Is Published Before/Regardless of `--pre-publish-exechook-command` Result - ([File: main.go])

### Summary
`git-sync`'s pre-publish exechook is documented and designed as a check that runs "before publishing the symlink" [1](#0-0)  so that operators can gate what content is exposed to consumers. In practice, the gate is fire-and-forget: `syncHooks.beforePublish` only enqueues the hash to an async `HookRunner` and immediately returns `nil`, so `SyncRepo` proceeds to call `git.publishSymlink` without ever waiting for the hook to actually run or succeed.

### Finding Description
`beforePublish` is defined as: [2](#0-1) 

This is invoked in `SyncRepo` immediately before `publishSymlink`: [3](#0-2) 

`HookRunner.Send` only pushes the hash into a non-blocking channel-backed `hookData` and returns instantly; the actual command execution happens asynchronously in `HookRunner.Run`, running in a separate goroutine started at startup: [4](#0-3) [5](#0-4) 

Because `beforePublish` returns `nil` unconditionally regardless of the hook's outcome (success, failure, or even whether it has run at all yet), `git.publishSymlink(newWorktree)` is executed and the symlink is atomically flipped to the new worktree before the pre-publish check has had a chance to complete or reject the content. The only place the hook's result is consulted is in `--one-time` mode, and even then only *after* the publish has already happened, purely to decide the process exit code: [6](#0-5) 

This is confirmed by the project's own e2e test: even when the pre-publish exechook is configured to fail (`EXECHOOK_COMMAND_FAIL_SLEEPY`), the symlink/content from the new (attacker-influenced) commit is published and readable, and only the process exit code reflects the failure after the fact: [7](#0-6) 

### Impact Explanation
An operator who configures `--pre-publish-exechook-command` to gate publication (e.g., a content scanner, signature verifier, or policy check meant to reject a bad/attacker-controlled commit before it becomes visible to consumers) gets no actual protection: the new commit's content is published to the `--link` symlink and readable by consumer containers regardless of whether the check would have failed. In long-running (non `--one-time`) mode there is no exit/abort at all on hook failure — `git-sync` simply logs an error and retries the hook in the background while the bad content remains live at `--link`. This matches the class of "gate that is supposed to run before an action can bypass that action's safety condition," directly analogous to `earlyUnstake()` letting withdrawal proceed before the cooldown/penalty check completes. The concrete impact category here is **publishing wrong/unvetted content** to consumers, since the intended pre-publish validation is not actually blocking.

### Likelihood Explanation
This triggers on every normal sync whenever `--pre-publish-exechook-command` is configured and reacts to any attacker-influenced commit reaching the tracked ref (an entirely realistic scenario for a git-sync deployment pulling from a repo with less-trusted contributors/branches). No special timing race is even needed — the bug is deterministic: `publishSymlink` runs unconditionally right after `Send()`, not after hook completion.

### Recommendation
Make `beforePublish` synchronous and block on the pre-publish hook's result before calling `publishSymlink`, returning its error (instead of always `nil`) so a failing pre-publish check prevents the swap. This requires blocking until the hook actually completes (not just enqueuing it), for every mode, not only `--one-time`, so that the symlink is only ever flipped after the gate has genuinely passed.

### Proof of Concept
1. Start `git-sync` (not `--one-time`) pointed at a repo, with `--pre-publish-exechook-command` set to a script that intentionally fails for a specific commit (simulating a scanner rejecting malicious content).
2. Push a new commit to the tracked ref.
3. Observe (as in `e2e::pre_publish_exechook_fail_once`) that `$ROOT/link` is immediately updated to point at the new worktree/content of that commit and consumers reading through `--link` see the new (rejected) content, even though the pre-publish hook reports failure and keeps retrying in the background — the "gate" never actually blocked the publish. **File:** pkg/hook/hook.go (L122-157)
```go
// Send sends hash to hookdata.
func (r *HookRunner) Send(hash string) {
	r.data.send(hash)
}

// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
```

```shellscript
function e2e::pre_publish_exechook_fail_once() {
    cat /dev/null > "$RUNLOG"

	assert_fail \
        GIT_SYNC \
            --one-time \
            --repo="file://$REPO" \
            --root="$ROOT" \
            --link="link" \
            --pre-publish-exechook-command="/$EXECHOOK_COMMAND_FAIL_SLEEPY" \
            --pre-publish-exechook-backoff=1s

    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file"
    assert_file_eq "$ROOT/link/file" "${FUNCNAME[0]}"
    assert_file_lines_eq "$RUNLOG" 1
}
```
