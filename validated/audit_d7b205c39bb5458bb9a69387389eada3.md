### Title
Asset definer/attestor can freeze a spender's already-owned asset funds by swapping the attestor list, blocking transfers exactly like a pauser blocking `closeTake` - (File: `validation.js`)

### Summary
`ocore` supports "attested" assets (`spender_attested: true`), where every input owner and (for issuance) every output address must be attested by one of the asset's currently-registered attestor addresses before a payment can be validated. The attestor list is a semi-trusted role, separate from the asset holders, and it can be replaced unilaterally by the asset definer at any time via an `asset_attestors` message. Because attestation membership is evaluated against the *current* (latest) attestor list rather than the list that was valid when the attestation was originally granted, a single `asset_attestors` update instantly invalidates the spending rights of every holder who was attested under the old list, until the new attestors re-attest them. This lets a privileged-but-not-holder actor (the definer, or a party who can influence the attestor set) block any pending or intended transfer/close of a position denominated in that asset, mirroring the reported Solidity bug where a "pauser" role (not the owner) can freeze `closeTake`/withdraw calls and trap a user's funds during adverse price movement.

### Finding Description
When an asset is created with `spender_attested: true`, every payment of that asset is checked in `validatePayment`: [1](#0-0) 
and again per-input in `validatePaymentInputsAndOutputs`, where the *owner* of each input being spent must be attested: [2](#0-1) 
and every output address must be attested for transfers: [3](#0-2) 

The attestor list itself is not fixed at asset-creation time; it can be replaced at will by the asset definer through an `asset_attestors` message, validated here: [4](#0-3) 
Only the definer's signature is checked (`objUnit.authors[0].address !== objAsset.definer_address`) — no consent from existing attested holders is required to change or drop attestors.

Critically, when the current attestor list is used to decide whether an address is attested, `storage.readAsset` always fetches the *latest* attestor-list unit rather than the one that existed at the time a particular attestation was made: [5](#0-4) 
and `filterAttestedAddresses` cross-references attestations against only `objAsset.arrAttestorAddresses` (the latest list): [6](#0-5) 

So the set of "attested" addresses recognized by validation is dynamic and tied to whichever attestor list is most recent at validation time — not to the attestor list that was valid when a holder originally acquired/was attested for their coins. A definer (or any party who can get the definer to act, or who controls the attestor addresses that must keep re-attesting) can swap out the attestor list right before a holder's pending payment/close-position transaction confirms, which causes `validatePayment`/`validatePaymentInputsAndOutputs` to reject it with `"owner address is not attested"` / `"none of the authors is attested"`, exactly analogous to the pauser front-running `closeTake` in the Solidity report.

### Impact Explanation
A holder of an attested asset who is legitimately entitled to move (or close out) their position can be blocked from doing so at any time, including during a period of adverse price movement, by a privileged-but-untrusted actor (the definer or the attestor set it controls) simply publishing a new `asset_attestors` unit. This is a High severity freezing/DoS vector on already-owned funds: it can be timed to front-run a user's exit, causing them to be stuck holding a losing position or unable to withdraw, with no emergency recourse for the affected user since spending requires attestation by whichever attestor set is current at validation time.

### Likelihood Explanation
Any asset issuer who wants an "attested" asset (a legitimate, sanctioned use case in `ocore`, e.g. for regulated/KYC'd tokens) has this power by design; the mechanism requires no special exploit, only a single `asset_attestors` unit signed by the definer. If the asset in question is used by an AA/DeFi contract for margin/futures-style positions (the codebase includes `test/samples/futures_contract.oscript` as an example of an AA-based asset flow), a change to the attestor list at the wrong moment reliably blocks users' close/withdraw operations for that asset.

### Recommendation
- Anchor attestation checks to the attestor list version that was current when the attestation was granted, or grandfather previously-attested addresses across attestor-list updates (e.g., require an explicit revoke action rather than implicit invalidation via list replacement).
- Alternatively, require a time-locked/delayed activation for `asset_attestors` updates so holders have a grace period to complete pending transfers, and/or restrict how drastically an attestor-list update can shrink/replace the recognized attestors relative to already-attested addresses.
- Document clearly (and consider enforcing on-chain) that attestor-list changes cannot retroactively strip spending rights from addresses already attested under a prior list, to avoid this owner/definer-level freeze primitive being usable against existing holders' funds.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor set `{X}` (`validateAssetDefinition`, `checkAttestorList`).
2. Attestor `X` attests Bob's address; Bob can freely transfer/spend asset `A` because `filterAttestedAddresses`/`arrAttestedAddresses` includes him under attestor set `{X}` [6](#0-5) .
3. Bob opens a leveraged/derivative position paid in asset `A` (e.g., via an AA) and later needs to close it as the price moves against him.
4. Before Bob's closing payment confirms, the definer posts an `asset_attestors` unit replacing the attestor set with `{Y}`, where `Y` has not attested Bob [4](#0-3) .
5. Once this unit is stable and becomes the "latest" attestor-list unit, `readAsset`/`filterAttestedAddresses` recompute `arrAttestedAddresses` using only `{Y}`'s attestations [5](#0-4) , and Bob's pending/subsequent payment fails validation with `"owner address is not attested"` [2](#0-1) , freezing his ability to close the position exactly as the pauser role froze `closeTake` in the reported bug.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],

			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
