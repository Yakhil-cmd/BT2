### Title
`is_valid_signed_package` / `validateSignedMessage` perform no expiry (deadline) check on signed off-chain packages - (File: signed_message.js)

### Summary
`signed_message.js`'s `validateSignedMessage()` (invoked from the oscript primitive `is_valid_signed_package` in `formula/evaluation.js`) accepts an optional `timestamp` field in the signed package but never validates it against the current time or any deadline supplied by the signer. This is the same class of bug as the reported `_validateSignature` missing `validUntil`/`validAfter` check: a signed authorization can be replayed/executed arbitrarily far in the future at conditions (price, balances) different from what the signer intended.

### Finding Description
`validateSignedMessage(conn, objSignedMessage, address, mci, handleResult)` in [1](#0-0)  explicitly whitelists `timestamp` as an allowed top-level field of a signed package (`hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])`), but nowhere in the function is `objSignedMessage.timestamp` read or compared to the current time, `last_ball_timestamp`, or any deadline. The function only validates author addresses, definitions, and authentifier signatures via `Definition.validateAuthentifiers` [2](#0-1) .

This routine is the sole verification path used by the AA formula primitive `is_valid_signed_package`, which AAs use to accept off-chain-signed data (orders, payment-channel state updates, etc.) as trigger input: [3](#0-2)  calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)` and only checks version/last-ball-unit staleness relative to the *unit*, not any time-based validity of the *signed content itself*.

The repo's own sample contract acknowledges this gap. In `test/samples/order_book_exchange.oscript`, the order-matching case that consumes two `is_valid_signed_package`-verified orders contains the comment `// to do check expiry` immediately before any expiry logic, and no expiry check is ever implemented: [4](#0-3) . The signed order (`$order1`, `$order2`) is a `signed_message` object that an unprivileged unit poster (anyone submitting a trigger unit to the AA) can supply and get executed via `is_valid_signed_package`, with no deadline enforced anywhere in the validation stack (`signed_message.js`, `Definition.validateAuthentifiers`, or the oscript primitive itself).

### Impact Explanation
Because neither the core `validateSignedMessage` routine nor the `is_valid_signed_package`/`is_valid_sig` oscript primitives enforce a signer-specified deadline, any off-chain signed order/instruction (e.g., a limit order, a payment-channel balance attestation) can be submitted and executed by any unprivileged unit poster at an arbitrary point in the future, long after the market/asset conditions the signer intended have changed. This can cause the signer to lose funds by having a stale order matched against unfavorable prices/balances, or a stale payment-channel state accepted after being superseded — this is asset/AA fund loss triggered purely by a single posted unit (trigger), matching the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any AA built on top of `is_valid_signed_package`/`is_valid_sig` (such as the shipped `order_book_exchange.oscript` sample, and the payment-channel sample which also lacks any check binding validity to time) because: (1) the underlying validation library (`signed_message.js`) provides no built-in deadline mechanism at all — contract authors must roll their own, and the reference/sample contract shipped in the repo fails to do so (explicit `// to do` comment); (2) triggering execution only requires posting a normal unit referencing the old signed package — no privileged access needed; (3) the vulnerability requires no race condition beyond simply waiting or choosing an opportune later moment to submit the trigger.

### Recommendation
Add explicit expiry support to the core signed-message primitive so AA authors don't have to reimplement it ad-hoc and error-prone:
- Extend `validateSignedMessage` in `signed_message.js` to optionally validate a `valid_till`/`expiry` field against `last_ball_timestamp` (the network-agreed time available via `objValidationState.last_ball_timestamp`), returning an error if the package is used after expiry.
- Alternatively/additionally, expose the package's `timestamp` (and any signer-chosen deadline field embedded inside `signed_message`) to oscript so that contract authors are required/guided to add `if (timestamp > order.expiry_ts) bounce(...)` checks, and fix the shipped `order_book_exchange.oscript` sample to actually implement the `// to do check expiry` logic, since it is used as a reference implementation.

### Proof of Concept
1. A user signs an order/message with `is_valid_signed_package`-compatible structure (`{signed_message: {..., price: X, sell_amount: Y}, authors: [...]}`) intending it to be matched promptly at price X.
2. The signed package is broadcast/stored off-chain (e.g., in a device chat message or shared out-of-band), as is standard usage for `signed_message.js`/`is_valid_signed_package`.
3. Market conditions change substantially over time (e.g., asset price moves).
4. Any unprivileged party posts a trigger unit to the order-book AA (`test/samples/order_book_exchange.oscript`) referencing that old signed order months later.
5. The AA's `if` clause calls `is_valid_signed_package(trigger.data.order1, $order1.address)` at [5](#0-4) , which succeeds because `validateSignedMessage` in `signed_message.js` never checks any expiry/deadline field — the order is matched at the stale price, causing the original signer to lose funds relative to what they intended when signing.
