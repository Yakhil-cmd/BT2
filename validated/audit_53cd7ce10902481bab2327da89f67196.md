### Title
Unauthenticated P2P Staking Info Recovery Allows Attacker-Controlled Staking Amounts to Be Persisted — (`datasync/downloader/downloader.go`)

### Summary

The `SyncStakingInfo` recovery path accepts `P2PStakingInfo` from a sync peer and persists it via `PutStakingInfoToDB` without any cryptographic verification that the `CouncilStakingAmounts` correspond to the actual staking contract balances at the claimed `BlockNum`. The `P2PStakingInfo` struct contains no block hash commitment, and neither `ToStakingInfo` nor `PutStakingInfoToDB` validate amounts against on-chain state.

### Finding Description

`P2PStakingInfo` carries `CouncilStakingAmounts` as a plain `[]uint64` with no cryptographic binding to the block: [1](#0-0) 

`ToStakingInfo` performs a verbatim field copy — no validation of amounts: [2](#0-1) 

`PutStakingInfoToDB` writes whatever `StakingInfo` it receives directly to the key-value store: [3](#0-2) 

The recovery goroutine in `downloader.go` checks only that `stakingInfo.BlockNum` matches `d.stakingInfoRecoveryBlocks[0]` — there is no hash commitment in the struct and no re-execution of the staking contract to verify amounts. A malicious P2P peer that is selected as the recovery peer can return a `P2PStakingInfo` with the correct `BlockNum` but with `CouncilStakingAmounts` set to attacker-controlled values (e.g., `MaxUint64` for one validator), and the node will persist this to its staking DB. [4](#0-3) 

### Impact Explanation

The staking DB is consumed by the weighted-random proposer selection and block reward distribution. Inflated staking amounts for an attacker-controlled validator grant it disproportionate block proposal rights and block rewards — a direct unauthorized redistribution of block rewards away from honest validators.

### Likelihood Explanation

Any node that connects to the victim as a P2P peer during staking info recovery can serve the malicious response. The `SyncStakingInfo` API is reachable from the P2P layer: [5](#0-4) 

The victim must be in staking info recovery mode (e.g., after fast/snap sync), which is a normal operational state for newly synced nodes.

### Recommendation

Bind the staking info to the canonical block hash. After receiving `P2PStakingInfo`, the node should either:
1. Re-execute the staking contract calls against the canonical state root for `BlockNum` to recompute amounts independently, or
2. Include a Merkle/state proof in `P2PStakingInfo` that the receiver can verify against the known canonical block hash before calling `PutStakingInfoToDB`.

### Proof of Concept

Integration test: connect a malicious peer, trigger staking info recovery, have the peer return `P2PStakingInfo{BlockNum: recoveryBlock, CouncilStakingAmounts: [MaxUint64, 0, 0, ...]}`. Assert that after recovery, the staking module's proposer selection assigns nearly all proposals to the attacker's validator, and that the staking DB entry for `recoveryBlock` contains the inflated amounts rather than the contract-derived amounts. [6](#0-5)
